# CI, maintainability, flakiness and production confidence

---

<a id="test-qual-001"></a>

<details>
<summary><strong>TEST-QUAL-001. What makes tests flaky, and how do you reduce flakiness?</strong></summary>

#### Short answer

Flakiness comes from timing, shared state, environment differences, external dependencies and concurrency; reduce it with isolation and deterministic waiting.

#### Interview answer

Common flaky-test causes are fixed sleeps, async races, shared database state, test order dependence, random ports, real external services, time zone/locale differences and overloaded CI. To reduce flakiness, isolate data, control time/randomness, use unique resources, wait for conditions, avoid real external dependencies and make cleanup reliable.

A flaky test should be treated as a defect in the test or system, not ignored permanently.

#### Deep dive

Retries can reduce noise temporarily, but they should not replace root-cause investigation.

#### Production angle

Flaky tests erode trust in CI and can let real regressions through.

#### Traps / caveats

- Longer sleeps do not fix races.
- Parallel execution exposes hidden shared state.
- Quarantined tests need owners and deadlines.

#### Optional Anki

Q: Main causes of flaky tests?
A: Timing, shared state, environment differences and uncontrolled dependencies.

</details>

<a id="test-qual-002"></a>

<details>
<summary><strong>TEST-QUAL-002. How should test data be isolated between tests?</strong></summary>

#### Short answer

Each test should create or own its data and clean it up or make it uniquely identifiable.

#### Interview answer

Test data isolation can be done with transactions, truncation, cleanup scripts, unique IDs, per-test schemas, per-test topics, fake stores or builders. The choice depends on the dependency and whether tests run in parallel.

The key rule is that a test should not depend on data created by another test or leave data that changes later tests.

#### Deep dive

For multi-tenant systems, include tenant IDs in test data to catch isolation bugs.

#### Production angle

Isolated data makes CI reliable and prevents tests from hiding real state-management bugs.

#### Traps / caveats

- Shared seed data can become hidden coupling.
- Parallel tests need stronger isolation.
- Cleanup must handle failed tests too.

#### Optional Anki

Q: What should each test own?
A: The data needed for its scenario.

</details>

<a id="test-qual-003"></a>

<details>
<summary><strong>TEST-QUAL-003. What problems appear when tests run in parallel?</strong></summary>

#### Short answer

Parallel tests expose shared state, resource conflicts, port collisions, database contention and unsafe static/global configuration.

#### Interview answer

When tests run in parallel, hidden coupling becomes visible. Tests may share static fields, caches, temporary files, database rows, Redis keys, Kafka topics, consumer groups or fixed ports. They can also overload CI resources and make timeouts more likely.

To support parallelism, use unique resources, immutable fixtures, deterministic cleanup and avoid global mutable state.

#### Deep dive

Parallelism can speed CI significantly, but only after isolation problems are addressed.

#### Production angle

Parallel-safe tests are usually better tests because production also has concurrent requests and shared resources.

#### Traps / caveats

- Fixed ports are a common source of collisions.
- Shared containers need isolated data.
- Static mocks and global config can leak across tests.

#### Optional Anki

Q: What does parallel testing commonly expose?
A: Hidden shared state and resource conflicts.

</details>

<a id="test-qual-004"></a>

<details>
<summary><strong>TEST-QUAL-004. How should feature-flagged behavior be tested?</strong></summary>

#### Short answer

Test both flag states, rollout boundaries and safe defaults.

#### Interview answer

Feature flags create multiple runtime behaviors. Tests should cover the old path, new path, default flag value, disabled behavior and any migration or fallback logic. For user- or tenant-targeted rollout, include tests for targeting rules and authorization boundaries.

When a flag guards risky behavior, add integration or smoke tests for both states until the old path is removed.

#### Deep dive

Feature flags should not remain forever. Tests should be cleaned up when the flag is retired.

#### Production angle

Flag mistakes can expose unfinished features, bypass validation or create inconsistent behavior between users.

#### Traps / caveats

- Only testing the enabled state misses rollback behavior.
- Default flag values differ across environments if not controlled.
- Old and new paths can drift if a flag lives too long.

#### Optional Anki

Q: What feature-flag states should be tested?
A: Enabled, disabled and default/rollout behavior.

</details>

<a id="test-qual-005"></a>

<details>
<summary><strong>TEST-QUAL-005. How do you debug a test that only fails in CI?</strong></summary>

#### Short answer

Compare environment, order, parallelism, data, time, resources and dependency versions between local and CI.

#### Interview answer

I start by collecting the exact failure, logs, seed data, test order, parallelism settings and environment details. Then I compare Java version, OS, time zone, locale, CPU/memory, Docker setup, database version, dependency cache and active profiles/properties. I try to reproduce locally with the same command and parallel settings.

CI-only failures often reveal hidden assumptions rather than CI being "wrong".

#### Deep dive

Adding diagnostics around container logs, effective properties and database state can make the failure actionable.

#### Production angle

CI differences often mirror production differences: resource limits, timing, config and dependency versions.

#### Traps / caveats

- Do not just rerun until green without investigation.
- Local IDE test runs may use different config from Maven/Gradle.
- Time zone and locale bugs are easy to miss.

#### Optional Anki

Q: First step for CI-only failures?
A: Compare the failing CI environment and command with local execution.

</details>

<a id="test-qual-006"></a>

<details>
<summary><strong>TEST-QUAL-006. What logs or diagnostics should failed integration tests expose?</strong></summary>

#### Short answer

Expose enough context to diagnose the dependency, request, data and configuration involved in the failure.

#### Interview answer

Failed integration tests should show application logs, container logs, effective test properties, request/response details, database state summaries when safe, broker topic/consumer information and relevant stack traces. For external fake servers, show unmatched requests and stub mappings.

Diagnostics should be useful but not leak secrets.

#### Deep dive

Capturing logs only on failure keeps normal CI output readable.

#### Production angle

Good diagnostics reduce time spent reproducing intermittent integration failures.

#### Traps / caveats

- Avoid logging tokens, passwords or sensitive payloads.
- Too much output can hide the important lines.
- Missing container logs make Docker failures hard to debug.

#### Optional Anki

Q: What should failed Testcontainers tests expose?
A: Container logs and startup/connection diagnostics.

</details>

<a id="test-qual-007"></a>

<details>
<summary><strong>TEST-QUAL-007. How should teams deal with flaky tests without ignoring them forever?</strong></summary>

#### Short answer

Treat them as defects, quarantine only temporarily and assign ownership to fix or delete them.

#### Interview answer

A flaky test should be investigated like a production reliability issue. If it blocks delivery, it can be quarantined temporarily, but there should be an owner, ticket and deadline. The team should collect failure evidence, identify the cause and either fix the test, fix the production code it exposes or remove a test that no longer gives value.

Permanent ignore lists are dangerous.

#### Deep dive

Track flaky tests and recurrence rates so the same class of issue does not keep returning.

#### Production angle

Ignoring flaky tests weakens release gates and normalizes unreliable engineering signals.

#### Traps / caveats

- Blind retries can hide real intermittent bugs.
- Deleting a flaky test without replacing its coverage may create risk.
- Quarantine should not mean forgotten.

#### Optional Anki

Q: What should every quarantined flaky test have?
A: An owner and a plan to fix, replace or delete it.

</details>

<a id="test-qual-008"></a>

<details>
<summary><strong>TEST-QUAL-008. What is a useful code review checklist for tests?</strong></summary>

#### Short answer

Check behavior relevance, readability, determinism, edge cases, failure paths, isolation and maintainability.

#### Interview answer

In review, I ask whether the test protects meaningful behavior, has clear setup, asserts the right outcome, covers important edge/failure cases, avoids implementation coupling and runs deterministically. I also check whether it uses the right test level, isolates data, avoids sleeps and provides useful failure messages.

For integration tests, I check cleanup, external dependency handling and CI cost.

#### Deep dive

Tests are production code for confidence. They deserve the same review seriousness as implementation code.

#### Production angle

Good test review prevents slow, brittle suites and missing coverage for risky behavior.

#### Traps / caveats

- Do not approve tests that only increase coverage numbers.
- Avoid over-mocking important boundaries.
- Make sure negative/security cases are included where relevant.

#### Optional Anki

Q: What should test review prioritize?
A: Meaningful behavior, determinism, isolation and clear assertions.

</details>

<a id="test-qual-009"></a>

<details>
<summary><strong>TEST-QUAL-009. What role do smoke tests, canary checks and post-deploy verification play?</strong></summary>

#### Short answer

They verify that the deployed system is basically healthy and safe to continue rollout.

#### Interview answer

Smoke tests check a small set of critical flows after deployment, such as startup, health, authentication and a core API path. Canary checks compare a small rollout against expected metrics before wider release. Post-deploy verification checks dashboards, logs, error rates, latency, background jobs and dependency connectivity.

These checks complement pre-merge tests because deployment environment issues can only appear after deployment.

#### Deep dive

Post-deploy checks should be automated where possible and tied to rollback or rollout decisions.

#### Production angle

They catch misconfiguration, bad migrations, missing secrets and dependency failures early in rollout.

#### Traps / caveats

- Smoke tests should be small and reliable.
- Do not make smoke tests mutate production data unsafely.
- Health endpoint green does not prove business flows work.

#### Optional Anki

Q: What do smoke tests verify?
A: Basic deployed-system health and critical paths.

</details>

<a id="test-qual-010"></a>

<details>
<summary><strong>TEST-QUAL-010. Where do performance, load and regression tests fit in a backend test strategy?</strong></summary>

#### Short answer

They should run on critical paths in controlled environments, usually outside the fastest pull-request loop.

#### Interview answer

Performance tests measure latency, throughput, resource use and scalability under realistic load. They are important for critical APIs, database-heavy flows, messaging pipelines and code likely to affect CPU, memory or I/O. Because they are slower and environment-sensitive, they often run nightly, pre-release or on demand.

Small microbenchmarks can help for isolated hot code, but system load tests reveal integration bottlenecks.

#### Deep dive

Regression thresholds should account for noise and compare against a stable baseline.

#### Production angle

Performance tests catch slow queries, N+1 problems, memory pressure and unsafe retry behavior before users feel them.

#### Traps / caveats

- Do not trust performance results from an unrealistic environment.
- Warmup, data volume and dependency behavior matter.
- Averages can hide p95/p99 latency regressions.

#### Optional Anki

Q: Why are load tests often not PR tests?
A: They are slower and environment-sensitive.

</details>

<a id="test-qual-011"></a>

<details>
<summary><strong>🧠 TEST-QUAL-011. How do you balance fast feedback with production-like confidence?</strong></summary>

#### Short answer

Use a layered pipeline: fast focused tests first, broader production-like tests later, with clear ownership for failures.

#### Interview answer

I balance speed and confidence by running fast unit, slice and key integration tests on pull requests, then broader container, contract, migration, performance and end-to-end checks on scheduled or pre-release stages. Critical tests should stay close to the change, but not every expensive test has to block every commit.

The suite should make common regressions cheap to catch and rare high-impact regressions still covered before release.

#### Deep dive

The boundary should evolve. If a nightly test catches frequent serious regressions, consider moving a focused version into PR checks.

#### Production angle

A good pipeline supports both developer speed and release safety.

#### Traps / caveats

- Fast but shallow tests give false confidence.
- Production-like but slow tests may be ignored if feedback is too late.
- Every non-PR test still needs an owner and response process.

#### Optional Anki

Q: How do mature pipelines balance test speed?
A: Fast high-signal PR tests plus broader later-stage checks.

</details>
