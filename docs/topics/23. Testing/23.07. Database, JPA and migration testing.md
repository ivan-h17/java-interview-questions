# Database, JPA and migration testing

---

<a id="test-db-001"></a>

<details>
<summary><strong>TEST-DB-001. How do you test repository queries in a Spring application?</strong></summary>

#### Short answer

Use repository integration tests with real mappings, realistic data and preferably the same database engine as production.

#### Interview answer

Repository queries should be tested with Spring Data/JPA infrastructure, entity mappings and a database. `@DataJpaTest` is a common fit. The test should insert representative data, run the query and assert the returned rows, ordering, projections and edge cases.

For native SQL or database-specific behavior, use PostgreSQL Testcontainers or another real test database instead of relying only on H2.

#### Deep dive

Mocks can prove service logic around a repository, but they cannot prove the repository query works.

#### Production angle

Repository tests catch wrong joins, missing filters, bad mappings and dialect differences before deployment.

#### Traps / caveats

- Tiny datasets hide wrong ordering and joins.
- Test both found and not-found cases.
- Do not depend on implicit database row order.

#### Optional Anki

Q: Why test repositories with real persistence?
A: Mocks cannot validate mappings or SQL behavior.

</details>

<a id="test-db-002"></a>

<details>
<summary><strong>TEST-DB-002. Why can H2 hide bugs when production uses PostgreSQL or another real database?</strong></summary>

#### Short answer

H2 differs in SQL dialect, types, locking, constraints, indexes, transactions and query planning.

#### Interview answer

H2 is fast and convenient, but it is not PostgreSQL. It can accept SQL that PostgreSQL rejects, handle types differently, enforce constraints differently, or miss performance and locking behavior. JSON, arrays, case sensitivity, date/time behavior and transaction isolation can also differ.

For important persistence tests, a real production-like database gives better confidence.

#### Deep dive

H2 may still be useful for simple tests, but it should not be the only coverage for production-specific queries.

#### Production angle

Many database bugs appear only after deployment because tests used an engine with different behavior.

#### Traps / caveats

- Compatibility modes do not fully reproduce PostgreSQL.
- Passing H2 tests do not prove query performance.
- Migrations should be tested on the target database engine.

#### Optional Anki

Q: Main risk of H2 for PostgreSQL apps?
A: It does not fully match production database behavior.

</details>

<a id="test-db-003"></a>

<details>
<summary><strong>TEST-DB-003. When should database tests use Testcontainers?</strong></summary>

#### Short answer

When correctness depends on real database behavior, migrations, SQL dialect, locking or infrastructure integration.

#### Interview answer

Testcontainers is useful for repository tests, migration tests and integration tests that need real PostgreSQL, Redis, Kafka or similar infrastructure. For databases, it catches dialect, type, constraint, index and transaction behavior that embedded substitutes may miss.

I use it especially for native queries, complex JPA mappings, migrations and production-critical persistence paths.

#### Deep dive

Container lifecycle should be managed carefully so tests remain fast enough for CI.

#### Production angle

Production-like database tests reduce surprises during release and dependency upgrades.

#### Traps / caveats

- Docker availability must be handled in CI.
- Per-test containers can be very slow.
- Tests still need deterministic data cleanup.

#### Optional Anki

Q: What does Testcontainers improve for DB tests?
A: Production-like database behavior.

</details>

<a id="test-db-004"></a>

<details>
<summary><strong>TEST-DB-004. How should tests apply Flyway or Liquibase migrations?</strong></summary>

#### Short answer

Run the same migrations in tests that production runs, preferably against the same database engine.

#### Interview answer

Integration tests should start from an empty or known database and apply Flyway or Liquibase migrations before using repositories. This verifies that migrations create the schema the application expects. Migration tests should also cover repeatability, ordering and data migration assumptions.

For risky migrations, test both fresh setup and upgrade from a previous schema state.

#### Deep dive

Backfills and long-running schema changes may need separate migration rehearsal tests with realistic data volume.

#### Production angle

Broken migrations can stop deployments or corrupt data before the application even starts.

#### Traps / caveats

- Do not let tests create schema through Hibernate if production uses migrations.
- H2 may not reveal production migration locks or syntax issues.
- Rollback scripts do not replace tested forward recovery plans.

#### Optional Anki

Q: What schema should integration tests use?
A: The schema produced by real migrations.

</details>

<a id="test-db-005"></a>

<details>
<summary><strong>TEST-DB-005. How do you prepare and clean up test data for database integration tests?</strong></summary>

#### Short answer

Use isolated data per test and clean it with rollback, truncation, SQL scripts or unique identifiers.

#### Interview answer

Good database tests control their own data. Options include transactional rollback, explicit cleanup, `@Sql`, repository setup, builders, truncation between tests or unique test identifiers. The best choice depends on transaction behavior, speed and whether commit-time effects must be tested.

The test should not depend on data left by another test.

#### Deep dive

For parallel tests, unique schemas, databases, tenants or IDs may be needed to prevent collisions.

#### Production angle

Reliable data setup prevents flaky CI and gives confidence in persistence behavior.

#### Traps / caveats

- Shared seed data can become hidden coupling.
- Cleanup order must respect foreign keys.
- Rollback can hide behavior that happens after commit.

#### Optional Anki

Q: What should database test data be?
A: Isolated and deterministic.

</details>

<a id="test-db-006"></a>

<details>
<summary><strong>TEST-DB-006. What are the trade-offs between transactional rollback and explicit cleanup in tests?</strong></summary>

#### Short answer

Rollback is fast and convenient; explicit cleanup is more realistic for commit behavior but often slower and harder.

#### Interview answer

Transactional rollback keeps tests isolated by undoing changes after each test. It is convenient for repository tests. But it can hide commit-time constraints, transaction synchronizations, outbox writes, triggers or behavior that depends on a committed transaction.

Explicit cleanup allows real commits, but cleanup must be reliable and ordered.

#### Deep dive

Some tests should deliberately commit to verify behavior. Others can safely use rollback for speed.

#### Production angle

Commit-time behavior matters for data correctness, events and integration with other systems.

#### Traps / caveats

- A test transaction may differ from production transaction boundaries.
- Rollback can prevent asynchronous consumers from seeing data.
- Cleanup failures can pollute later tests.

#### Optional Anki

Q: What can rollback-based tests hide?
A: Behavior that occurs only on commit.

</details>

<a id="test-db-007"></a>

<details>
<summary><strong>TEST-DB-007. How do you test unique constraints, foreign keys and database-generated values?</strong></summary>

#### Short answer

Persist realistic data, flush or commit when needed, and assert database-enforced behavior.

#### Interview answer

Constraints should be tested against the database, not only through application validation. For unique constraints, attempt a duplicate and assert the expected failure. For foreign keys, test valid and invalid references. For generated values, persist and flush the entity, then assert IDs, defaults or timestamps as appropriate.

Some constraint failures appear only on flush or commit.

#### Deep dive

Application validation can improve error messages, but database constraints are the final correctness guard.

#### Production angle

Database constraints prevent race conditions and invalid data when multiple application instances write concurrently.

#### Traps / caveats

- Forgetting `flush()` can hide constraint failures.
- Exception types may be framework-specific.
- Do not assert generated values too tightly if they are implementation details.

#### Optional Anki

Q: When may JPA constraint violations appear?
A: On flush or commit.

</details>

<a id="test-db-008"></a>

<details>
<summary><strong>TEST-DB-008. How can tests catch N+1 query problems or accidental lazy loading?</strong></summary>

#### Short answer

Use realistic datasets and assert query counts, fetch plans or behavior outside the persistence context.

#### Interview answer

To catch N+1 problems, create multiple parent records with children and exercise the service or API path. Then inspect query counts with Hibernate statistics, datasource proxies or test utilities. Also test DTO mapping and serialization boundaries where lazy loading often appears.

The test should fail if one extra parent creates many extra queries unexpectedly.

#### Deep dive

Small datasets with one row will not reveal N+1 behavior.

#### Production angle

N+1 bugs often pass functional tests but cause severe latency and database load in production.

#### Traps / caveats

- Open Session in View can hide lazy loading in tests.
- Query-count assertions can be brittle if too strict.
- Fetch joins and pagination need careful testing.

#### Optional Anki

Q: Why do tiny datasets miss N+1?
A: One parent does not expose per-row extra queries.

</details>

<a id="test-db-009"></a>

<details>
<summary><strong>TEST-DB-009. How do you test commit-time behavior such as outbox writes or transaction synchronizations?</strong></summary>

#### Short answer

Use a Spring-managed transactional path and force a real commit, then assert the committed side effect.

#### Interview answer

Outbox rows, transaction synchronizations and after-commit callbacks often do not behave correctly in rollback-only tests. I test them through the real service with Spring transaction management and either commit the transaction or run the operation outside the test transaction.

Then I assert the outbox row, emitted signal, callback or database state after commit.

#### Deep dive

For outbox patterns, usually test that the service writes the outbox record atomically with business data; a separate test can cover the relay.

#### Production angle

Commit-time bugs can lose events, publish too early or make data and messages inconsistent.

#### Traps / caveats

- `@Transactional` tests that roll back may never trigger after-commit behavior.
- Async relays need bounded waits.
- Do not publish external messages before the database commit is safe.

#### Optional Anki

Q: Why do outbox tests often need real commit?
A: The outbox/after-commit behavior may not occur during rollback.

</details>

<a id="test-db-010"></a>

<details>
<summary><strong>🧠 TEST-DB-010. How do you test concurrent transactions or locking behavior safely?</strong></summary>

#### Short answer

Use separate transactions/connections, coordinate them explicitly and assert outcomes with bounded timeouts.

#### Interview answer

Concurrent transaction tests need real database behavior and careful coordination. I use two threads or transaction templates, separate connections, latches/barriers to control ordering, and a bounded timeout to prevent hanging. The test should assert the expected lock wait, conflict, retry, optimistic lock failure or final state.

These tests should be few, focused and documented because they are slower and easier to make flaky.

#### Deep dive

Use the same isolation level and database engine as production when lock behavior matters.

#### Production angle

Concurrency bugs create duplicate processing, lost updates, deadlocks and inconsistent data.

#### Traps / caveats

- One test transaction cannot simulate two real concurrent transactions.
- Avoid unbounded lock waits.
- Database isolation differs across engines.

#### Optional Anki

Q: What do concurrent DB tests require?
A: Separate transactions and explicit coordination.

</details>
