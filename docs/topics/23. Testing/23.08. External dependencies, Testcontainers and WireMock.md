# External dependencies, Testcontainers and WireMock

<a id="test-ext-001"></a>

<details>
<summary><strong>TEST-EXT-001. What problem does Testcontainers solve in Java backend tests?</strong></summary>

#### Short answer

It lets tests run real infrastructure dependencies in disposable containers.

#### Interview answer

Testcontainers helps integration tests use real PostgreSQL, Kafka, Redis, Elasticsearch or other services without requiring shared manually managed environments. Tests can start containers, get dynamic connection details and run against production-like behavior.

This is stronger than mocking infrastructure when correctness depends on protocol, dialect, persistence or broker behavior.

#### Deep dive

It does not remove the need for good test isolation and lifecycle management.

#### Production angle

Realistic dependency tests catch configuration, schema, serialization and protocol bugs before deployment.

#### Traps / caveats

- Containers add startup time.
- Docker availability must be handled in CI.
- Testcontainers still uses test data, not production scale.

#### Optional Anki

Q: What does Testcontainers provide?
A: Disposable real dependencies for integration tests.

</details>

<details>
<summary><strong>TEST-EXT-002. How do you pass container connection details into a Spring Boot test?</strong></summary>

#### Short answer

Use dynamic properties or Spring Boot service connection support where available.

#### Interview answer

A Testcontainers container usually exposes a dynamic host, port and credentials. In Spring tests, these values can be registered with `@DynamicPropertySource`, such as setting `spring.datasource.url`. Modern Spring Boot also supports service connection integration for supported containers, reducing boilerplate.

The key is that the application under test receives the container's actual runtime connection details.

#### Deep dive

For unsupported or custom containers, dynamic properties remain the general solution.

#### Production angle

Dynamic connection wiring avoids hard-coded ports and makes tests more reliable in CI.

#### Traps / caveats

- Static hard-coded ports can collide in parallel CI.
- Property names must match the client auto-configuration.
- Containers must be started before properties are resolved.

#### Optional Anki

Q: General Spring way to register dynamic container properties?
A: `@DynamicPropertySource`.

</details>

<a id="test-ext-003"></a>

<details>
<summary><strong>TEST-EXT-003. How should container lifecycle be managed across a test suite?</strong></summary>

#### Short answer

Balance isolation and speed by reusing containers at class or suite level while cleaning data deterministically.

#### Interview answer

Starting a container per test method is usually too slow. A static per-class container or shared suite-level container is common. The trade-off is that shared containers require strong data isolation, cleanup and unique identifiers.

For databases, reuse the container but clean schemas or data between tests. For brokers, isolate topics or consumer groups.

#### Deep dive

Container reuse improves speed but can hide order dependence if data cleanup is weak.

#### Production angle

Good lifecycle strategy keeps integration tests realistic enough and fast enough for regular CI use.

#### Traps / caveats

- Shared containers do not mean shared test data.
- Per-test containers can make PR builds too slow.
- Parallel tests need unique resources.

#### Optional Anki

Q: Main trade-off in container lifecycle?
A: Isolation versus startup cost.

</details>

<a id="test-ext-004"></a>

<details>
<summary><strong>TEST-EXT-004. How do you test integration with Redis, Kafka, PostgreSQL or other infrastructure dependencies?</strong></summary>

#### Short answer

Use real local dependencies through Testcontainers or focused fakes when real behavior is not needed.

#### Interview answer

For PostgreSQL, test SQL, migrations, transactions and constraints against a real database. For Kafka, test serialization, producer/consumer behavior, retries and consumer groups with a broker. For Redis, test key format, TTL, serialization and cache invalidation behavior.

Mocks are fine for service unit tests, but infrastructure integration needs tests that exercise the actual client and protocol.

#### Deep dive

The test should focus on the integration contract rather than duplicating every dependency feature.

#### Production angle

Infrastructure differences are a frequent cause of "works locally" production failures.

#### Traps / caveats

- Do not hit shared dev infrastructure from CI tests.
- Clean keys, topics, schemas and data between tests.
- Avoid testing vendor behavior you do not own unless your code depends on it.

#### Optional Anki

Q: What should infrastructure integration tests exercise?
A: The real client, protocol and important configuration.

</details>

<a id="test-ext-005"></a>

<details>
<summary><strong>TEST-EXT-005. What problem does WireMock solve for HTTP client tests?</strong></summary>

#### Short answer

It provides a controllable fake HTTP server for testing client requests and response handling.

#### Interview answer

WireMock lets tests run an HTTP server with predefined stubs. A client can call it as if it were an external service. Tests can verify request method, path, headers, body and how the client handles success, errors, malformed responses and delays.

This is stronger than mocking the client interface when testing serialization, headers or HTTP status handling.

#### Deep dive

WireMock tests should reflect the provider contract and be updated when the real API changes.

#### Production angle

HTTP client tests reduce outages caused by wrong headers, bad error handling or unexpected response shapes.

#### Traps / caveats

- Stubs can drift from the real provider.
- Do not call real external services in ordinary CI.
- Include failure and timeout cases, not only success.

#### Optional Anki

Q: What does WireMock fake?
A: An HTTP server.

</details>

<a id="test-ext-006"></a>

<details>
<summary><strong>TEST-EXT-006. How do you test HTTP client behavior for 4xx, 5xx, malformed and slow responses?</strong></summary>

#### Short answer

Use a fake server to return each response type and assert mapping, retry, fallback and timeout behavior.

#### Interview answer

I configure WireMock or another fake server to return client errors, server errors, invalid JSON, missing fields, slow responses and connection failures if supported. The test should assert how the client maps errors, whether retries happen, whether timeouts are respected and whether sensitive details are hidden.

Different status classes usually mean different behavior: 4xx may be non-retryable, while some 5xx/timeouts may be retryable.

#### Deep dive

Malformed response tests should include parsing failures and semantically invalid payloads.

#### Production angle

External dependency failures are normal. Client tests ensure the service degrades or fails predictably.

#### Traps / caveats

- Retrying all 4xx responses is usually wrong.
- Slow response tests should not rely on long sleeps.
- Verify logs/metrics for important failure paths when useful.

#### Optional Anki

Q: What should HTTP client failure tests cover?
A: Error mapping, retry, fallback and timeout behavior.

</details>

<a id="test-ext-007"></a>

<details>
<summary><strong>TEST-EXT-007. How do you test retries, timeouts and fallback logic?</strong></summary>

#### Short answer

Control the dependency responses and assert retry count, delay policy, final result and side effects.

#### Interview answer

For retry logic, I make the dependency fail then succeed, or fail repeatedly. The test should verify which failures are retryable, how many attempts happen, what happens after exhaustion and whether idempotency is preserved. Timeouts should be configured low enough for tests and verified through controlled slow responses.

Fallback tests should prove the fallback is safe and visible through metrics/logging if required.

#### Deep dive

Retry timing can be tested with configurable backoff or virtual time where available.

#### Production angle

Bad retry logic can amplify outages or duplicate side effects.

#### Traps / caveats

- Retrying non-idempotent operations can create duplicates.
- Fallbacks can return stale or incorrect data.
- Tests should not wait for real production backoff durations.

#### Optional Anki

Q: Main danger of retries?
A: They can amplify failures or duplicate side effects.

</details>

<a id="test-ext-008"></a>

<details>
<summary><strong>TEST-EXT-008. What is the difference between stubbing an external dependency and running a real local dependency?</strong></summary>

#### Short answer

Stubs give control and speed; real local dependencies give stronger protocol and configuration confidence.

#### Interview answer

A stubbed dependency, such as WireMock, is ideal for controlled HTTP responses and failure cases. A real local dependency, such as PostgreSQL or Kafka in Testcontainers, verifies actual client configuration, protocol behavior and storage/broker semantics.

The choice depends on the risk. If the real behavior matters, prefer a real dependency. If you need precise failure scenarios, a stub may be better.

#### Deep dive

Many services need both: unit tests with mocks, client tests with stubs and infrastructure tests with real dependencies.

#### Production angle

Using the right test double avoids both slow over-integration and weak fake confidence.

#### Traps / caveats

- Stubs can drift from provider behavior.
- Real dependencies are slower and need cleanup.
- Do not confuse a fake HTTP server with a full provider contract.

#### Optional Anki

Q: Main advantage of a real local dependency?
A: It exercises real protocol/configuration behavior.

</details>

<a id="test-ext-009"></a>

<details>
<summary><strong>🧠 TEST-EXT-009. How can tests simulate network latency, connection resets or dependency outages?</strong></summary>

#### Short answer

Use fake servers, container/network controls or specialized fault-injection tools with bounded assertions.

#### Interview answer

HTTP fake servers can delay responses, close connections or return malformed data. Some container setups can simulate dependency shutdowns, unavailable ports or network issues. For more advanced cases, fault-injection proxies can add latency, resets or packet loss.

The test should assert timeout, retry, circuit breaker, fallback and cleanup behavior, not just that an exception occurs.

#### Deep dive

These tests are slower and should be targeted at high-risk integration paths.

#### Production angle

Networks fail in partial and messy ways. Tests should prove the service does not hang, leak resources or overload dependencies.

#### Traps / caveats

- Fault tests can become flaky if timing is too strict.
- Simulated faults may not match every production failure mode.
- Always cap waits and cleanup resources.

#### Optional Anki

Q: What should network-failure tests assert?
A: Timeout, retry/fallback behavior and resource cleanup.

</details>

<details>
<summary><strong>🧠 TEST-EXT-010. What common CI problems appear with Docker-based integration tests?</strong></summary>

#### Short answer

Docker may be unavailable, slow, resource-constrained, misconfigured or conflicting under parallel load.

#### Interview answer

Common CI issues include missing Docker permissions, slow image pulls, no network access to registries, low disk space, port conflicts, limited CPU/memory, container startup timeouts and parallel tests fighting over shared resources. Testcontainers-based tests need clear CI setup and useful diagnostics when containers fail.

Images should be pinned or managed deliberately to avoid surprise changes.

#### Deep dive

CI caches can help, but stale images or missing cleanup can create confusing failures.

#### Production angle

If integration tests are unreliable in CI, teams lose trust and may bypass important coverage.

#### Traps / caveats

- Do not assume local Docker performance matches CI.
- Expose container logs on failure.
- Avoid hard-coded ports and shared names.

#### Optional Anki

Q: What should Docker integration tests expose on failure?
A: Useful container logs and startup diagnostics.

</details>
