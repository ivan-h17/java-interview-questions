# Messaging, events and contract testing

---

<a id="test-msg-001"></a>

<details>
<summary><strong>TEST-MSG-001. How should Kafka producers be tested?</strong></summary>

#### Short answer

Test producer decision logic, serialization, topic/key/header choices and broker integration for critical flows.

#### Interview answer

Producer tests should verify when an event is produced, what payload is produced, which topic/key/headers are used and how send failures are handled. Unit tests can capture a publish command or event object. Integration tests with Kafka or Testcontainers verify real serialization and broker behavior.

For transactional/outbox designs, test that business data and the outbox record are stored atomically.

#### Deep dive

Do not rely only on mocking `KafkaTemplate` if topic names, serializers or headers are important.

#### Production angle

Bad producer tests can miss lost events, wrong keys, broken schemas or unsafe publish-before-commit behavior.

#### Traps / caveats

- A successful mocked send does not prove broker integration.
- Keys matter for ordering and partitioning.
- Publishing before transaction commit can create inconsistent events.

#### Optional Anki

Q: What producer details often need tests?
A: Payload, topic, key, headers and failure handling.

</details>

<a id="test-msg-002"></a>

<details>
<summary><strong>TEST-MSG-002. How should Kafka consumers be tested?</strong></summary>

#### Short answer

Unit test processing logic and integration test listener behavior, deserialization, offsets, retries and error handling.

#### Interview answer

For consumers, I separate message processing logic from broker mechanics. The processing function can be unit-tested with events and fake dependencies. Listener integration tests should cover real deserialization, topic subscription, acknowledgment/offset behavior, retry handling and dead-letter behavior.

Use unique topics or consumer groups in tests to avoid cross-test interference.

#### Deep dive

Consumer tests should include duplicate, invalid and out-of-order messages if the system must handle them.

#### Production angle

Consumers are often where idempotency, retries and poison message handling break.

#### Traps / caveats

- Do not assume exactly-once behavior unless the whole design supports it.
- Avoid `Thread.sleep()`; wait for observable processing results.
- Clean or isolate topics between tests.

#### Optional Anki

Q: What should consumer tests separate?
A: Business processing logic from broker/listener mechanics.

</details>

<a id="test-msg-003"></a>

<details>
<summary><strong>TEST-MSG-003. How do you test message serialization and deserialization?</strong></summary>

#### Short answer

Serialize and deserialize representative messages using the real configured serializer and schema settings.

#### Interview answer

Message tests should use the same JSON, Avro, Protobuf or other serializer configuration as production. They should cover required fields, optional fields, unknown fields, enum values, dates, versioned schemas and invalid payloads.

For public event contracts, test both current producers and backward/forward compatibility with stored examples.

#### Deep dive

Schema registry compatibility checks should be part of the pipeline when schemas are governed centrally.

#### Production angle

Serialization bugs can stop consumers, poison topics or silently corrupt data.

#### Traps / caveats

- A test-only mapper or serializer may hide production config drift.
- Avoid exposing internal entity shape as an event contract.
- Test old payloads during schema evolution.

#### Optional Anki

Q: What serializer should message tests use?
A: The real production-configured serializer.

</details>

<a id="test-msg-004"></a>

<details>
<summary><strong>TEST-MSG-004. How do you test idempotent consumers?</strong></summary>

#### Short answer

Process the same message more than once and assert the final state and side effects occur only once.

#### Interview answer

An idempotent consumer test sends or calls processing with duplicate messages that share the same event ID, business key or idempotency key. The test should assert that database state is correct, external side effects are not duplicated and duplicate tracking works across transaction boundaries.

It should include failures around commit points if duplicates are likely during retries.

#### Deep dive

Idempotency is usually enforced with a database constraint, processed-message table or business-state check.

#### Production angle

At-least-once delivery means duplicates are normal, not exceptional.

#### Traps / caveats

- In-memory duplicate tracking is not enough across restarts.
- Mock tests may not catch race conditions around idempotency.
- Retrying after partial success is the hard case.

#### Optional Anki

Q: How do you test idempotency?
A: Process duplicates and assert one final effect.

</details>

<a id="test-msg-005"></a>

<details>
<summary><strong>TEST-MSG-005. How do you test retry topics, dead-letter topics and poison messages?</strong></summary>

#### Short answer

Use controlled failing messages and assert retry attempts, final routing and recoverability.

#### Interview answer

I create messages that fail transiently and messages that always fail. Tests should verify retry count, backoff behavior where practical, whether the message reaches a retry topic or dead-letter topic, and what metadata is preserved. For poison messages, verify the consumer can continue processing later messages.

Unit tests can check error classification; integration tests should verify broker/listener wiring.

#### Deep dive

Dead-letter records need enough context for investigation and replay.

#### Production angle

Without tested poison-message handling, one bad event can block a partition or flood logs.

#### Traps / caveats

- Do not retry non-retryable validation errors forever.
- Avoid long real backoff durations in tests.
- DLQ tests should verify the consumer keeps making progress.

#### Optional Anki

Q: What should DLQ tests prove?
A: Bad messages are isolated and processing continues.

</details>

<a id="test-msg-006"></a>

<details>
<summary><strong>TEST-MSG-006. How do you test ordering assumptions in event-driven code?</strong></summary>

#### Short answer

Send events in expected, duplicate and out-of-order sequences and assert the final state.

#### Interview answer

If code assumes ordering, tests should make that assumption explicit. For Kafka, events with the same key in one partition have ordering guarantees, but cross-key or cross-partition ordering is not guaranteed. Tests should cover normal order, out-of-order arrival, duplicates and missing prior events if those are possible.

The assertion should focus on final state and rejected/ignored stale events.

#### Deep dive

Version numbers, timestamps or sequence numbers are common ways to handle stale events, but they need tests.

#### Production angle

Ordering bugs create stale projections, overwritten state and hard-to-debug data inconsistencies.

#### Traps / caveats

- Do not assume global Kafka ordering.
- Timestamps alone may not be reliable for ordering.
- Rebalances and retries can expose hidden ordering assumptions.

#### Optional Anki

Q: Kafka ordering is strongest within what scope?
A: A partition for records with the same key.

</details>

<a id="test-msg-007"></a>

<details>
<summary><strong>TEST-MSG-007. How does Awaitility or polling help test asynchronous processing?</strong></summary>

#### Short answer

It waits until an observable condition is true instead of sleeping for a guessed time.

#### Interview answer

Messaging tests are asynchronous: a producer sends a message, a listener processes it later, and state eventually changes. Awaitility-style polling lets the test wait until the expected database row, event, metric or side effect appears, with a maximum timeout.

This makes tests faster and less flaky than fixed sleeps.

#### Deep dive

The condition should be meaningful and stable, such as "order status became PAID" rather than "wait two seconds".

#### Production angle

Reliable async tests increase confidence in event-driven flows without slowing CI unnecessarily.

#### Traps / caveats

- Always set a maximum timeout.
- Avoid polling too aggressively against real databases.
- Awaiting does not fix poor test isolation.

#### Optional Anki

Q: Why use Awaitility?
A: To wait for conditions instead of sleeping.

</details>

<a id="test-msg-008"></a>

<details>
<summary><strong>TEST-MSG-008. What is consumer-driven contract testing?</strong></summary>

#### Short answer

Consumers define expectations for a provider contract, and the provider verifies it can satisfy them.

#### Interview answer

In consumer-driven contract testing, each consumer records the requests, responses or messages it depends on. The provider runs tests against those contracts to ensure changes remain compatible. This is useful for HTTP APIs and event contracts across teams.

It complements integration tests; it does not prove the provider is deployed or healthy.

#### Deep dive

Contracts should focus on fields and semantics consumers actually require, not every provider implementation detail.

#### Production angle

Contract tests reduce accidental breaking changes in distributed systems with independently deployed services.

#### Traps / caveats

- Contracts need ownership and versioning.
- Too many overly strict contracts can block harmless provider changes.
- Provider verification must run before release.

#### Optional Anki

Q: Who defines expectations in consumer-driven contracts?
A: The consumer.

</details>

<a id="test-msg-009"></a>

<details>
<summary><strong>🧠 TEST-MSG-009. How should schema compatibility for Avro, Protobuf or JSON Schema be tested?</strong></summary>

#### Short answer

Check old and new schemas/payloads for backward and forward compatibility according to the contract policy.

#### Interview answer

Schema compatibility tests should verify whether new producers can be read by old consumers and whether old messages can still be read by new consumers, depending on the agreed compatibility mode. For Avro or Protobuf, use schema tooling and representative encoded messages. For JSON Schema, validate examples and compatibility rules carefully.

The test should include field additions, removals, defaults, enum changes and type changes.

#### Deep dive

Schema registry compatibility checks are useful, but application-level semantic tests are still needed.

#### Production angle

Schema breaks can stop consumers or corrupt downstream projections during rolling deployments.

#### Traps / caveats

- Adding a required field without a default can break old messages.
- Enum evolution is easy to mishandle.
- Schema compatibility does not prove business semantic compatibility.

#### Optional Anki

Q: What should schema compatibility tests protect?
A: Old and new producers/consumers during evolution.

</details>

<a id="test-msg-010"></a>

<details>
<summary><strong>🧠 TEST-MSG-010. What exactly-once assumptions should tests avoid making?</strong></summary>

#### Short answer

Tests should not assume a message causes exactly one processing attempt or exactly one side effect unless the full system design guarantees it.

#### Interview answer

Kafka and similar systems often provide at-least-once processing at the application level. Even when broker transactions or idempotent producers are used, consumers may still retry after partial failures. Tests should assume duplicates, retries and partial success can happen, then verify idempotency and consistency.

The safe interview answer is: design and test for duplicate delivery unless the boundaries are explicitly controlled.

#### Deep dive

"Exactly once" usually has a scope: broker writes, producer semantics, stream processing topology or external side effects. Tests must match that scope.

#### Production angle

Incorrect exactly-once assumptions lead to duplicate orders, payments, emails or state transitions.

#### Traps / caveats

- A green happy-path consumer test proves little about duplicates.
- External systems usually do not participate in Kafka transactions.
- Idempotency keys and database constraints need tests.

#### Optional Anki

Q: What should event consumers generally tolerate?
A: Duplicate delivery and retries.

</details>
