# Spring Boot testing and test slices

---

<a id="test-spring-001"></a>

<details>
<summary><strong>TEST-SPRING-001. What is `@SpringBootTest`, and when should you use it?</strong></summary>

#### Short answer

`@SpringBootTest` loads a full Spring Boot application context for integration-style tests.

#### Interview answer

`@SpringBootTest` is useful when the test needs real application wiring, auto-configuration, configuration properties, Spring proxies or multiple layers working together. It can run with no web environment, a mock web environment or a real server port depending on the test.

I use it for important integration paths, not as the default for every class.

#### Deep dive

Full context startup is expensive, so context reuse and consistent configuration matter.

#### Production angle

Full-context tests catch missing beans, wrong configuration, broken wiring and framework integration problems before deployment.

#### Traps / caveats

- Overusing it makes the suite slow.
- It can accidentally connect to real external systems if properties are wrong.
- Mocked beans can change what the context actually tests.

#### Optional Anki

Q: What does `@SpringBootTest` load?
A: A full Spring Boot application context.

</details>

<a id="test-spring-002"></a>

<details>
<summary><strong>TEST-SPRING-002. When should you avoid `@SpringBootTest`?</strong></summary>

#### Short answer

Avoid it when plain unit tests or focused slices can verify the behavior with less cost and clearer failures.

#### Interview answer

If I am testing pure business logic, calculations, validation rules or simple service branching, I usually avoid `@SpringBootTest`. Starting the whole context adds time and can make failures harder to understand.

Use the smallest test scope that gives enough confidence. Add full-context tests for wiring and critical integration paths.

#### Deep dive

Many slow Spring test suites come from using `@SpringBootTest` for every controller, service and repository test.

#### Production angle

Fast feedback encourages developers to run tests locally and keep CI useful.

#### Traps / caveats

- Do not avoid Spring tests when Spring behavior is the subject.
- Too many mocks in a full-context test can remove the value of the full context.
- Slice tests may not catch full application wiring issues.

#### Optional Anki

Q: What is the default for pure business logic tests?
A: Plain unit tests without Spring.

</details>

<a id="test-spring-003"></a>

<details>
<summary><strong>TEST-SPRING-003. What are Spring test slices?</strong></summary>

#### Short answer

They load only the Spring components needed for one layer, such as MVC, JPA or JSON.

#### Interview answer

Spring test slices are annotations that configure a focused part of the application context. For example, `@WebMvcTest` loads MVC infrastructure and controllers, while `@DataJpaTest` loads JPA repositories and persistence support.

Slices are faster and more focused than full `@SpringBootTest`, but they intentionally exclude many beans.

#### Deep dive

If a slice requires many imports and mocks, it may be a sign that a different test scope is clearer.

#### Production angle

Slices catch framework integration issues at important boundaries while keeping CI faster.

#### Traps / caveats

- A slice is not the full application.
- Missing beans in a slice may be expected.
- Security, converters or advice must be included if they matter.

#### Optional Anki

Q: Main purpose of a Spring test slice?
A: Focused Spring testing for one application layer.

</details>

<a id="test-spring-004"></a>

<details>
<summary><strong>TEST-SPRING-004. When should you use `@WebMvcTest`?</strong></summary>

#### Short answer

Use it for focused controller tests involving request mapping, validation, serialization, security and exception handling.

#### Interview answer

`@WebMvcTest` loads Spring MVC infrastructure for selected controllers. It is good for verifying URLs, methods, request binding, validation errors, response status, JSON shape and controller advice. Service dependencies are usually mocked or imported deliberately.

It is not meant to test real database, messaging or service integration.

#### Deep dive

Use `MockMvc` or a similar client to exercise the controller through HTTP-like requests.

#### Production angle

Controller slice tests protect API behavior without making every API test a full integration test.

#### Traps / caveats

- Security may be active and affect results.
- Mocked services can hide service/controller integration issues.
- Custom converters and global advice must be part of the test if they are part of production behavior.

#### Optional Anki

Q: What does `@WebMvcTest` focus on?
A: The Spring MVC/controller layer.

</details>

<a id="test-spring-005"></a>

<details>
<summary><strong>TEST-SPRING-005. When should you use `@DataJpaTest`?</strong></summary>

#### Short answer

Use it to test repositories, entity mappings, queries and persistence constraints.

#### Interview answer

`@DataJpaTest` configures JPA-related components such as repositories, entity manager and persistence infrastructure. It is useful for verifying derived queries, JPQL/native queries, mappings, constraints and persistence behavior.

For PostgreSQL-specific behavior, configure it with a real PostgreSQL test database or Testcontainers rather than relying only on H2.

#### Deep dive

Many `@DataJpaTest` tests run transactionally and roll back after each test, which is convenient but can hide commit-time behavior.

#### Production angle

Repository tests catch bugs that mocks cannot, such as wrong joins, missing mappings and dialect differences.

#### Traps / caveats

- H2 can differ from production databases.
- Rollback can hide commit-time failures.
- It does not load ordinary service beans by default.

#### Optional Anki

Q: What does `@DataJpaTest` test?
A: JPA repositories and persistence mapping.

</details>

<a id="test-spring-006"></a>

<details>
<summary><strong>TEST-SPRING-006. How should Spring tests override properties or profiles?</strong></summary>

#### Short answer

Use explicit test properties, active profiles or dynamic properties, and keep them consistent across the suite.

#### Interview answer

Spring tests can override configuration with test property files, `@ActiveProfiles`, inline test properties or `@DynamicPropertySource` for runtime values like container ports. The important part is making test configuration explicit and production-safe.

For external dependencies, tests should point to fakes, containers or disabled integrations, not real production services.

#### Deep dive

Every distinct set of profiles, properties or mocks can affect Spring test context caching.

#### Production angle

Correct test properties prevent accidental external calls and make CI behavior reproducible.

#### Traps / caveats

- Too many unique property combinations slow context caching.
- Test profiles can drift from production assumptions.
- Never let tests use production credentials or endpoints.

#### Optional Anki

Q: What is `@DynamicPropertySource` often used for?
A: Supplying dynamic container URLs or ports to Spring tests.

</details>

<a id="test-spring-007"></a>

<details>
<summary><strong>TEST-SPRING-007. What is `@TestConfiguration`, and when is it useful?</strong></summary>

#### Short answer

It defines test-only Spring beans or overrides that should not become production configuration.

#### Interview answer

`@TestConfiguration` is used to add beans for tests, such as fake clients, test clocks, helper beans or special configuration. It keeps test wiring explicit and separate from production configuration.

It is useful when a Spring test needs a real bean replacement rather than a Mockito mock.

#### Deep dive

Test configuration can be nested in a test class or imported from a separate class.

#### Production angle

Clear test-only wiring helps integration tests run safely without external services.

#### Traps / caveats

- Do not accidentally component-scan test configuration into production.
- Too many test-only beans can make tests unrealistic.
- Prefer simple constructor injection for plain unit tests.

#### Optional Anki

Q: What does `@TestConfiguration` provide?
A: Test-only Spring bean definitions.

</details>

<a id="test-spring-008"></a>

<details>
<summary><strong>TEST-SPRING-008. What is the difference between replacing a Spring bean with a mock and testing with the real bean?</strong></summary>

#### Short answer

A mock isolates one part of the context; a real bean verifies actual wiring and behavior.

#### Interview answer

Replacing a bean with a mock is useful when the dependency is external, slow or irrelevant to the current test. Testing with the real bean gives more integration confidence because Spring wiring, proxies, validation, transactions and configuration are exercised.

The choice depends on what risk the test is meant to cover.

#### Deep dive

Mocking a Spring bean can change the context cache key and may remove proxy/advice behavior you intended to test.

#### Production angle

Real-bean tests catch wiring and framework issues; mock-bean tests keep focused tests fast and controlled.

#### Traps / caveats

- Mocking every layer creates a weak integration test.
- A mocked bean may bypass AOP, transactions or security behavior.
- Real external dependencies should usually be replaced by fakes or containers in CI.

#### Optional Anki

Q: Main trade-off of a mocked Spring bean?
A: More isolation, less integration confidence.

</details>

<a id="test-spring-009"></a>

<details>
<summary><strong>TEST-SPRING-009. When does Spring proxy behavior require a Spring-managed test instead of a plain unit test?</strong></summary>

#### Short answer

When the behavior depends on AOP, transactions, security, caching, validation or async annotations.

#### Interview answer

Plain unit tests construct the class directly, so Spring proxies are not involved. If I need to verify `@Transactional`, `@Cacheable`, method security, `@Async`, validation on method calls or custom aspects, the test must call a Spring-managed bean.

I still unit test the internal business logic separately when possible.

#### Deep dive

Self-invocation can bypass proxy-based advice, so integration tests are useful for catching that class of issue.

#### Production angle

Many serious bugs come from assuming annotations apply when code is not actually going through the proxy.

#### Traps / caveats

- Manually constructing a service will not test transaction advice.
- Mocking the proxied bean can remove advice.
- A passing unit test does not prove Spring annotation behavior.

#### Optional Anki

Q: What is needed to test `@Transactional` proxy behavior?
A: Call a Spring-managed bean through the proxy.

</details>

<a id="test-spring-010"></a>

<details>
<summary><strong>🧠 TEST-SPRING-010. How does Spring test context caching affect test performance and isolation?</strong></summary>

#### Short answer

Spring reuses equivalent test contexts; inconsistent configuration creates many contexts and slows the suite.

#### Interview answer

Starting a Spring context is expensive, so the TestContext framework caches contexts by configuration: loaded classes, profiles, properties, customizers, mocks and related settings. Tests with the same context can reuse it.

If every test uses unique properties or mock declarations, the cache fragments and CI slows down.

#### Deep dive

Context reuse also means mutable singleton state can leak if tests mutate beans without cleanup.

#### Production angle

Efficient context caching can be the difference between a usable test suite and one developers avoid running.

#### Traps / caveats

- Random inline properties can create unique contexts.
- Overusing mock beans fragments the cache.
- Shared singleton state must be reset or avoided.

#### Optional Anki

Q: Why does Spring cache test contexts?
A: To avoid repeated expensive application context startup.

</details>

<details>
<summary><strong>🧠 TEST-SPRING-011. When should a test use `@DirtiesContext`, and why should it be rare?</strong></summary>

#### Short answer

Use it only when a test mutates the Spring context or singleton state so badly that the context cannot be safely reused.

#### Interview answer

`@DirtiesContext` tells Spring that the test context is dirty and should not be reused. It is appropriate when a test changes bean definitions, mutates global singleton state or otherwise corrupts the context for later tests.

It should be rare because it forces context rebuilds and can make the suite much slower.

#### Deep dive

Most database cleanup should be handled with transactions, cleanup SQL or isolated data, not by dirtying the context.

#### Production angle

Overusing `@DirtiesContext` hides poor test isolation and damages CI feedback time.

#### Traps / caveats

- It is not a general cleanup tool.
- It does not clean external systems automatically.
- Frequent use often signals mutable global state or bad test design.

#### Optional Anki

Q: Main cost of `@DirtiesContext`?
A: It prevents context reuse and slows the suite.

</details>
