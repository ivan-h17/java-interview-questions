# Testing strategy and test design

---

<a id="test-strat-001"></a>

<details>
<summary><strong>TEST-STRAT-001. What is the difference between unit, integration, component, contract and end-to-end tests?</strong></summary>

#### Short answer

They test different scopes: one unit, several integrated parts, one deployable service, a service contract, or a full user/business flow.

#### Interview answer

A unit test checks one small piece of logic in isolation. An integration test checks that several real parts work together, such as service code with a database. A component test tests one deployable service through its boundaries while replacing external dependencies. A contract test verifies that provider and consumer agree on request, response or event shape. An end-to-end test exercises a complete flow across multiple services or UI/API boundaries.

The higher the scope, the more confidence in wiring and real behavior, but the slower and more fragile the test usually becomes.

#### Deep dive

The names vary by team, so I clarify the boundary and dependencies rather than arguing labels.

#### Production angle

Balanced scope helps catch real production failures without making CI slow enough that developers stop trusting it.

#### Traps / caveats

- Calling every Spring test a unit test hides the real cost.
- E2E tests should not be the main way to test business rules.
- Contract tests do not prove runtime availability or performance.

#### Optional Anki

Q: What mainly distinguishes test types?
A: Scope and how many real dependencies are exercised.

</details>

<a id="test-strat-002"></a>

<details>
<summary><strong>TEST-STRAT-002. What is the test pyramid, and how does it apply to Java backend services?</strong></summary>

#### Short answer

Use many fast unit tests, fewer integration/component tests and a small number of end-to-end tests for critical flows.

#### Interview answer

The test pyramid is a guideline for balancing speed and confidence. In a Java backend service, most business rules should be covered by fast JUnit tests. Important framework boundaries need focused Spring, database, messaging or HTTP integration tests. Only a few flows should be tested end to end because they are slower, harder to debug and more expensive to maintain.

The point is not a strict ratio. The point is fast feedback plus enough production-like coverage around risky boundaries.

#### Deep dive

For services with complex persistence or messaging, the pyramid may need a larger integration layer than a pure library project.

#### Production angle

A good pyramid catches regressions before deploy while keeping pull requests quick enough to run on every change.

#### Traps / caveats

- High unit coverage cannot replace database or serialization tests.
- Too many full-context tests make feedback slow.
- E2E tests often fail far from the root cause.

#### Optional Anki

Q: Why should most tests be low-level?
A: They are faster, more focused and easier to debug.

</details>

<a id="test-strat-003"></a>

<details>
<summary><strong>TEST-STRAT-003. How do you decide what should be tested with a unit test versus an integration test?</strong></summary>

#### Short answer

Use unit tests for pure business decisions; use integration tests when correctness depends on framework, database, network, serialization or configuration behavior.

#### Interview answer

If I can construct the object with ordinary Java dependencies and assert its behavior clearly, I prefer a unit test. If the behavior depends on Spring proxies, transactions, SQL dialect, JSON mapping, security filters, Kafka, Redis or HTTP client behavior, I add an integration or slice test.

The question is: what could realistically break? If the risk is in branching logic, unit test it. If the risk is at a boundary, test the boundary with real infrastructure or a realistic fake.

#### Deep dive

Service methods often need both: unit tests for cases and a few integration tests for wiring, transactions or persistence side effects.

#### Production angle

Many production bugs happen at boundaries: wrong query, missing bean, mapper mismatch, transaction not applied, timeout not configured.

#### Traps / caveats

- Mocking a repository does not validate the query.
- Starting Spring for every small rule wastes time.
- A fake must behave close enough to the real dependency to be useful.

#### Optional Anki

Q: When should a test become an integration test?
A: When correctness depends on real boundary behavior.

</details>

<a id="test-strat-004"></a>

<details>
<summary><strong>TEST-STRAT-004. What makes a backend test valuable rather than just increasing coverage numbers?</strong></summary>

#### Short answer

It catches meaningful regressions, checks observable behavior and fails with a clear reason.

#### Interview answer

A valuable backend test protects a business rule, API contract, data constraint, integration boundary or failure mode. It should assert something that users, clients or production systems care about, not just execute lines for coverage.

Good tests are deterministic, readable and specific enough that a failure points to the broken behavior.

#### Deep dive

Coverage is useful as a signal for untested areas, but it does not measure assertion quality. A test can cover many lines and still verify nothing important.

#### Production angle

Useful tests prevent incidents such as accepting invalid data, breaking a response contract, losing an event, leaking data or retrying unsafely.

#### Traps / caveats

- Asserting only "no exception" is often weak.
- Tests coupled to private implementation break during harmless refactors.
- Coverage targets can incentivize low-value tests.

#### Optional Anki

Q: What should a backend test protect?
A: Observable behavior, contracts, data correctness or important failure modes.

</details>

<a id="test-strat-005"></a>

<details>
<summary><strong>TEST-STRAT-005. How do naming, Arrange-Act-Assert and Given-When-Then improve test readability?</strong></summary>

#### Short answer

They make the scenario, action and expected result obvious to the reader.

#### Interview answer

Good test names describe the behavior, not just the method name. Arrange-Act-Assert separates setup, the operation under test and verification. Given-When-Then expresses the same idea in scenario language: given some state, when something happens, then an outcome is expected.

This matters because tests are executable documentation. A reviewer should understand the behavior without mentally reverse-engineering a long setup.

#### Deep dive

For complex cases, test data builders and helper methods should hide irrelevant setup but keep important values visible.

#### Production angle

Readable tests make feature changes safer because developers can quickly understand which behavior they are changing.

#### Traps / caveats

- Do not over-abstract test setup until the behavior disappears.
- A long test name is fine if it names the case clearly.
- One test should usually verify one behavior.

#### Optional Anki

Q: What are the three parts of Arrange-Act-Assert?
A: Setup, execute, verify.

</details>

<a id="test-strat-006"></a>

<details>
<summary><strong>TEST-STRAT-006. How do you choose edge cases for a backend method or API?</strong></summary>

#### Short answer

Look at boundaries, invalid inputs, missing data, permissions, concurrency, external failures and persistence constraints.

#### Interview answer

I start with the business rule and ask where behavior changes. For numbers, that means minimum, maximum, zero, negative and limit-plus-one. For strings and collections, empty, null if allowed, duplicates and large sizes matter. For APIs, I test invalid payloads, missing fields, unknown fields, auth failures and not-found cases. For persistence, I include constraints and transaction behavior.

The goal is not every possible input. It is the inputs most likely to break the rule.

#### Deep dive

Equivalence classes help: pick one representative from each behavior group plus boundary values.

#### Production angle

Most defects are not in the happy path; they appear in bad data, limits, retries, stale state and partial failures.

#### Traps / caveats

- Do not forget negative tests.
- Tiny test datasets hide pagination and N+1 issues.
- Null handling should match the API contract, not personal preference.

#### Optional Anki

Q: What edge cases are usually worth testing?
A: Boundaries, invalid input, missing data, permissions and failure paths.

</details>

<a id="test-strat-007"></a>

<details>
<summary><strong>TEST-STRAT-007. Why should tests usually verify behavior instead of implementation details?</strong></summary>

#### Short answer

Behavior-focused tests survive refactoring and protect what users or callers actually depend on.

#### Interview answer

Tests should usually assert observable outcomes: returned values, state changes, saved records, emitted events, HTTP responses or calls to external boundaries. If a test verifies every internal method call, it becomes tied to implementation and fails during harmless refactoring.

Interaction verification is still useful when the interaction is the behavior, such as sending an email, publishing an event or calling a payment provider.

#### Deep dive

The more a test knows about private steps, the less freedom the code has to improve its design.

#### Production angle

Backend systems evolve constantly. Tests should catch broken contracts, not block internal cleanup.

#### Traps / caveats

- Mockito verification is not always a behavior assertion.
- Avoid testing private methods directly.
- Some side effects must be verified through collaborators or persisted state.

#### Optional Anki

Q: What should tests normally assert?
A: Observable behavior and externally meaningful effects.

</details>

<a id="test-strat-008"></a>

<details>
<summary><strong>TEST-STRAT-008. What makes a test deterministic?</strong></summary>

#### Short answer

It gives the same result for the same code and environment, independent of order, timing, random values or shared state.

#### Interview answer

A deterministic test controls its inputs, time, randomness, data, external dependencies and concurrency. It does not depend on test order, real clocks, sleeps, current locale, shared database rows, random ports without coordination or live external services.

When something asynchronous must happen, the test should wait for a condition with a timeout rather than sleep for a guessed duration.

#### Deep dive

Injecting `Clock`, ID generators, executors and clients makes deterministic tests much easier.

#### Production angle

Nondeterministic tests create false confidence or false alarms. Teams eventually ignore flaky tests, which weakens release safety.

#### Traps / caveats

- Passing locally once does not prove determinism.
- Parallel test execution exposes hidden shared state.
- Fixed sleeps make tests both slow and unreliable.

#### Optional Anki

Q: What is a deterministic test?
A: A test that consistently passes or fails for the same behavior.

</details>

<a id="test-strat-009"></a>

<details>
<summary><strong>TEST-STRAT-009. How do you decide which tests belong in pull-request, nightly and pre-release pipelines?</strong></summary>

#### Short answer

Run fast, reliable, high-signal tests on every pull request; move slower broad checks to scheduled or pre-release stages.

#### Interview answer

Pull requests should run unit tests, focused integration tests, static checks and the most important contract tests. Nightly pipelines can run broader Testcontainers suites, slow compatibility checks, mutation testing or larger regression tests. Pre-release pipelines should include production-like smoke, migration, performance or end-to-end checks for critical flows.

The split should be based on feedback speed, reliability and risk.

#### Deep dive

If an important integration test is slow, I first try to optimize it rather than automatically removing it from PR checks.

#### Production angle

The pipeline should catch likely regressions before merge while still giving deeper confidence before release.

#### Traps / caveats

- Moving every slow test out of PRs can hide integration breakage.
- Nightly failures need ownership; otherwise they become noise.
- Rarely run tests often rot.

#### Optional Anki

Q: What should run on every PR?
A: Fast, reliable tests that catch common and high-risk regressions.

</details>

<a id="test-strat-010"></a>

<details>
<summary><strong>🧠 TEST-STRAT-010. What is mutation testing, and when is it worth using?</strong></summary>

#### Short answer

Mutation testing changes code in small ways and checks whether tests fail; it measures test strength, not just coverage.

#### Interview answer

A mutation testing tool creates small changes, such as flipping a condition or changing a return value. If the tests still pass, the mutant survived, which suggests the tests did not verify that behavior well.

It is useful for critical business rules, libraries and areas where coverage is high but confidence is uncertain. It is usually too slow to run everywhere on every pull request.

#### Deep dive

Mutation testing is most valuable after a basic test suite already exists. It helps reveal weak assertions and missing boundary cases.

#### Production angle

For pricing, payments, permissions or compliance rules, stronger tests can prevent expensive correctness bugs.

#### Traps / caveats

- A surviving mutant is a signal to inspect, not automatic proof of a bug.
- Some equivalent mutants cannot be killed meaningfully.
- It can be computationally expensive.

#### Optional Anki

Q: What does mutation testing measure?
A: Whether tests detect small behavioral changes in code.

</details>

<a id="test-strat-011"></a>

<details>
<summary><strong>🧠 TEST-STRAT-011. How do you apply risk-based thinking when deciding what to test first?</strong></summary>

#### Short answer

Prioritize tests where failure impact and failure probability are highest.

#### Interview answer

I look at business criticality, data correctness, security, external contracts, operational risk and change frequency. Payment flows, authorization, migrations, event publishing and public APIs deserve stronger tests than trivial getters or low-impact formatting.

I also consider blast radius: a shared library or framework configuration change needs broader regression coverage than a local UI label.

#### Deep dive

Risk-based testing is not an excuse to skip tests. It is a way to invest effort where it buys the most confidence.

#### Production angle

Teams have limited time. Testing the most dangerous failure modes first reduces incident probability more than chasing uniform coverage.

#### Traps / caveats

- Do not ignore low-risk code if it changes often.
- Risk changes as a feature becomes widely used.
- Security and data-loss risks deserve special weight.

#### Optional Anki

Q: Risk-based testing prioritizes what?
A: High-impact and high-probability failures.

</details>
