# Mockito and test doubles

---

<a id="test-mock-001"></a>

<details>
<summary><strong>TEST-MOCK-001. What is the difference between a mock, stub, fake and spy?</strong></summary>

#### Short answer

A stub returns predefined answers, a mock verifies interactions, a fake has working simplified behavior, and a spy wraps a real object while allowing observation or partial stubbing.

#### Interview answer

A stub is used to supply controlled dependency responses. A mock is usually used to verify that a dependency was called in a certain way. A fake is a lightweight implementation, such as an in-memory repository. A spy calls real methods by default but can verify or override selected behavior.

In practice, the important question is what confidence the test needs: controlled input, behavior verification or realistic collaborator behavior.

#### Deep dive

Mockito often uses the word mock for objects that can act as both mocks and stubs, but the testing concepts are still different.

#### Production angle

Choosing the right double keeps unit tests fast without hiding integration bugs.

#### Traps / caveats

- Over-verifying mocks couples tests to implementation.
- Fakes must preserve important semantics.
- Spies can execute real side effects unexpectedly.

#### Optional Anki

Q: What is a fake?
A: A simplified working implementation used in tests.

</details>

<a id="test-mock-002"></a>

<details>
<summary><strong>TEST-MOCK-002. When should you use Mockito in a unit test?</strong></summary>

#### Short answer

Use Mockito when a collaborator is slow, external, difficult to construct or needs controlled behavior for the scenario.

#### Interview answer

Mockito is useful for isolating a unit from repositories, clients, message publishers, clocks, ID generators or other dependencies. It lets the test force success, failure, empty results or exceptions and then assert how the unit responds.

I avoid mocking simple value objects or every internal helper. If a real object is cheap and stable, using it often produces a clearer test.

#### Deep dive

Constructor injection makes Mockito-based tests straightforward because dependencies are explicit.

#### Production angle

Mocks help cover failure paths that are hard to trigger with real dependencies.

#### Traps / caveats

- Mocking too many layers can test the mock setup more than the code.
- A mocked database does not validate SQL or transactions.
- Mocking static/global dependencies usually points to design friction.

#### Optional Anki

Q: Good reason to use Mockito?
A: Control or observe a dependency in a focused unit test.

</details>

<a id="test-mock-003"></a>

<details>
<summary><strong>TEST-MOCK-003. When is a fake object better than a Mockito mock?</strong></summary>

#### Short answer

When the collaborator has simple reusable behavior that many tests need and interaction details are not important.

#### Interview answer

A fake is often better for in-memory repositories, simple gateways, permission stores or event collectors. It lets tests assert behavior through state and outcomes rather than mock interactions. This can make tests less brittle and closer to real use.

Mocks are better when a specific interaction or failure must be controlled exactly.

#### Deep dive

A fake should model the important contract, not every production detail. If it becomes complex, an integration test may be more honest.

#### Production angle

Good fakes reduce duplicated stubbing and keep business tests readable.

#### Traps / caveats

- A fake that behaves differently from production can create false confidence.
- Fakes need maintenance as contracts evolve.
- Do not use fakes for behavior that depends on database isolation or SQL semantics.

#### Optional Anki

Q: When is a fake preferable?
A: When reusable simplified behavior is clearer than repeated stubbing.

</details>

<a id="test-mock-004"></a>

<details>
<summary><strong>TEST-MOCK-004. How do stubbing and verification differ in Mockito?</strong></summary>

#### Short answer

Stubbing defines what a mock returns or throws; verification checks how the code interacted with the mock.

#### Interview answer

Stubbing sets up collaborator behavior, such as returning a user or throwing a timeout. Verification checks calls after the action, such as whether an event publisher was called once with the right payload.

I stub dependencies to create the scenario and verify interactions only when the interaction is part of the observable behavior.

#### Deep dive

Many tests need stubbing but not verification. If the returned result or persisted state proves the behavior, explicit verification can be unnecessary.

#### Production angle

Good use of verification protects important side effects like publishing events, sending notifications or calling external APIs.

#### Traps / caveats

- Verifying every method call makes tests fragile.
- Unused stubs may indicate dead setup or wrong assumptions.
- `verifyNoMoreInteractions` is often too strict.

#### Optional Anki

Q: What does Mockito stubbing do?
A: Defines mock behavior for the test scenario.

</details>

<a id="test-mock-005"></a>

<details>
<summary><strong>TEST-MOCK-005. What is `ArgumentCaptor`, and when is it useful?</strong></summary>

#### Short answer

`ArgumentCaptor` captures a value passed to a mock so the test can inspect it.

#### Interview answer

`ArgumentCaptor` is useful when the code creates an object internally and sends it to a collaborator. For example, a service creates an event and passes it to a publisher. The test can capture that event and assert its fields.

It should be used for meaningful outputs, not to inspect every internal call.

#### Deep dive

If the expected argument is simple, direct argument matching may be clearer than a captor.

#### Production angle

Captor-based tests can protect integration payloads such as events, commands or emails.

#### Traps / caveats

- Capturing too many internal objects couples tests to implementation.
- Prefer domain-level assertions over checking incidental fields.
- Captors do not validate real serialization or transport behavior.

#### Optional Anki

Q: What does `ArgumentCaptor` inspect?
A: Arguments passed to a mocked collaborator.

</details>

<a id="test-mock-006"></a>

<details>
<summary><strong>TEST-MOCK-006. What are common problems with verifying too many interactions?</strong></summary>

#### Short answer

The test becomes brittle, implementation-focused and hard to refactor.

#### Interview answer

If a test verifies every repository call, helper call and exact ordering, it often checks how the code works internally rather than what it does. A harmless refactor can break the test even though behavior is unchanged.

I reserve interaction verification for externally meaningful effects or collaboration contracts.

#### Deep dive

Strict interaction tests are appropriate for protocol-like code where call order matters, but ordinary service logic usually should be tested through outcomes.

#### Production angle

Over-specified tests slow refactoring and make developers distrust failures.

#### Traps / caveats

- `verifyNoMoreInteractions` can freeze implementation details.
- Verifying calls does not prove correct data was persisted.
- Order verification should be rare.

#### Optional Anki

Q: Main risk of excessive mock verification?
A: Tests become coupled to implementation details.

</details>

<a id="test-mock-007"></a>

<details>
<summary><strong>TEST-MOCK-007. Why are deep stubs often a test smell?</strong></summary>

#### Short answer

They usually mean the code under test knows too much about a dependency chain.

#### Interview answer

Deep stubs allow calls like `mock.getA().getB().doWork()`. They make setup convenient but often expose a Law of Demeter problem: the unit reaches through several objects instead of depending on a clearer abstraction.

Tests with deep stubs are fragile because any change in the chain breaks the test.

#### Deep dive

Sometimes deep stubs are acceptable for fluent third-party APIs, but they should be used cautiously.

#### Production angle

Code that navigates long dependency chains is harder to test, refactor and observe in production.

#### Traps / caveats

- Deep stubs can hide null behavior.
- They encourage testing chained internals.
- A wrapper or adapter may be a better boundary.

#### Optional Anki

Q: What design issue can deep stubs reveal?
A: The code depends on a long collaborator chain.

</details>

<a id="test-mock-008"></a>

<details>
<summary><strong>TEST-MOCK-008. How should tests verify exceptional paths with mocked dependencies?</strong></summary>

#### Short answer

Stub the dependency to fail, then assert the service response, exception mapping, rollback or side effects.

#### Interview answer

For a unit test, I configure the mock to throw a relevant exception or return an error result. Then I assert how the code handles it: propagates a domain exception, returns a fallback, marks a retry, avoids publishing an event or preserves atomicity.

The mocked failure should represent a realistic dependency failure, not an impossible scenario.

#### Deep dive

For retry and timeout behavior, unit tests can verify policy, but integration tests should also verify real client configuration.

#### Production angle

Many backend incidents happen when dependency failures are handled incorrectly.

#### Traps / caveats

- Do not test only happy paths.
- Verify that unsafe side effects do not happen after failure.
- Avoid asserting framework-specific exception text unless required.

#### Optional Anki

Q: What should exceptional-path tests verify besides the exception?
A: Side effects, fallback, rollback or retry behavior.

</details>

<a id="test-mock-009"></a>

<details>
<summary><strong>TEST-MOCK-009. Why can partial mocks and spies make tests fragile?</strong></summary>

#### Short answer

They mix real behavior with mocked behavior, so tests can accidentally execute side effects or depend on internals.

#### Interview answer

A spy calls real methods unless they are stubbed. That can be useful for legacy code, but it is easy to accidentally call real database, network, filesystem or time-dependent behavior. Partial mocks also suggest the class may have too many responsibilities.

I prefer extracting a collaborator or testing through public behavior when possible.

#### Deep dive

Spies can be reasonable for wrapping a real Spring bean in an integration test, but they should be used deliberately.

#### Production angle

Fragile spy tests often miss real integration risks while blocking harmless internal changes.

#### Traps / caveats

- Stubbing spies can call real methods if done incorrectly.
- Real side effects may happen during setup.
- A spy can hide a design issue.

#### Optional Anki

Q: Default behavior of a Mockito spy?
A: It calls real methods unless stubbed.

</details>

<a id="test-mock-010"></a>

<details>
<summary><strong>🧠 TEST-MOCK-010. What are the trade-offs of mocking final, static or constructor calls?</strong></summary>

#### Short answer

It can help with legacy or hard-to-change code, but it often increases coupling to implementation and hides design problems.

#### Interview answer

Modern Mockito can mock some final and static behavior with the right setup. This is useful when testing legacy code that calls static utilities, constructors or final classes directly. The trade-off is that the test becomes tightly coupled to how the code creates and calls dependencies.

For new code, dependency injection, adapters and small interfaces usually produce cleaner tests.

#### Deep dive

Static mocking should have a narrow scope and must be cleaned up reliably.

#### Production angle

Using these tools can unblock safe refactoring, but relying on them everywhere makes tests brittle.

#### Traps / caveats

- Static mocks can leak between tests if not scoped correctly.
- Constructor mocking can freeze implementation choices.
- Mocking time statically is usually worse than injecting `Clock`.

#### Optional Anki

Q: Better design alternative to static time mocking?
A: Inject a `Clock`.

</details>

<a id="test-mock-011"></a>

<details>
<summary><strong>🧠 TEST-MOCK-011. How can over-mocking hide integration problems?</strong></summary>

#### Short answer

Mocks can make collaborators behave ideally, so tests pass while real wiring, SQL, serialization or transactions are broken.

#### Interview answer

If every dependency is mocked, the test only proves that the service works with the assumptions written into the mock setup. It does not prove the repository query exists, the JSON mapper is configured, the transaction starts, security context is present or the Kafka serializer works.

Over-mocking is especially dangerous around framework and infrastructure boundaries.

#### Deep dive

The fix is not to remove mocks entirely. It is to add targeted integration tests for the boundaries that mocks replace.

#### Production angle

Many "worked in unit tests" failures are really contract or configuration failures.

#### Traps / caveats

- A mocked client does not prove real HTTP headers or timeouts.
- A mocked repository does not prove SQL correctness.
- A mocked bean can remove Spring proxy behavior.

#### Optional Anki

Q: What does over-mocking often miss?
A: Real boundary, configuration and integration behavior.

</details>
