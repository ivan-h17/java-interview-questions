<details>
<summary><strong>TEST-API-001. When should you use MockMvc in Spring MVC tests?</strong></summary>

#### Short answer

Use MockMvc to test Spring MVC request handling without starting a real HTTP server.

#### Interview answer

MockMvc is useful for controller and MVC-slice tests. It exercises request mapping, parameter binding, validation, message converters, controller advice and security filters if configured. It gives HTTP-like assertions for status, headers and body while staying faster than a full server test.

It is a good fit for `@WebMvcTest` and some full-context tests with a mock web environment.

#### Deep dive

MockMvc does not test real network behavior, server ports, TLS or actual client libraries.

#### Production angle

MockMvc tests protect API behavior and error contracts cheaply enough to run on every pull request.

#### Traps / caveats

- Standalone MockMvc setup can miss real Spring configuration.
- Mocked service dependencies can hide integration issues.
- Include security and global advice when they are part of the API contract.

#### Optional Anki

Q: What layer does MockMvc exercise?
A: Spring MVC request handling without a real server.

</details>

<details>
<summary><strong>TEST-API-002. What is the difference between MockMvc, WebTestClient and RestAssured-style tests?</strong></summary>

#### Short answer

MockMvc tests MVC without a real server, WebTestClient can test reactive or server-bound APIs, and RestAssured-style tests usually call a real HTTP endpoint.

#### Interview answer

MockMvc is common for Spring MVC controller tests. WebTestClient is common for WebFlux and can also be used against a running server or mock setup. RestAssured-style tests are typically black-box HTTP tests against a real application port.

The broader the test, the more real behavior it covers and the more setup cost it has.

#### Deep dive

For servlet Spring MVC services, MockMvc is often fastest for controller contracts; real-port tests are better when filters, server configuration or client behavior matter.

#### Production angle

Choosing the right tool helps balance confidence and feedback speed.

#### Traps / caveats

- Do not use a real server for every small controller case.
- MockMvc does not prove network or deployment behavior.
- Reactive streaming behavior may need WebTestClient or real client tests.

#### Optional Anki

Q: Which tool usually calls a real HTTP port?
A: RestAssured-style full HTTP tests.

</details>

<details>
<summary><strong>TEST-API-003. How do you test request validation with Bean Validation?</strong></summary>

#### Short answer

Send invalid requests through the API layer and assert status, error body and rejected fields.

#### Interview answer

For Spring MVC, I test validation by sending requests with missing, malformed or invalid fields using MockMvc or an integration test. The assertions should cover the HTTP status, stable error code or field errors, and that the controller/service does not perform unsafe side effects.

For custom validators or validation groups, include cases that prove the correct group and cross-field rules are applied.

#### Deep dive

Pure validator unit tests are useful for complex custom validators, but API tests verify binding plus validation plus error mapping.

#### Production angle

Validation tests prevent bad client data from becoming corrupt database state or unclear 500 errors.

#### Traps / caveats

- Test invalid JSON separately from valid JSON with invalid fields.
- Do not assert unstable localized text unless it is a contract.
- Include authorization and tenant checks where relevant.

#### Optional Anki

Q: What should API validation tests assert?
A: Status, stable error shape and rejected fields.

</details>

<details>
<summary><strong>TEST-API-004. How do you test `@ControllerAdvice` and exception responses?</strong></summary>

#### Short answer

Trigger representative exceptions through the controller layer and assert the mapped HTTP response.

#### Interview answer

I test exception handling by making the controller or mocked service throw domain, validation, not-found and unexpected exceptions. The test should assert the status code, error body, headers if relevant and absence of sensitive details.

The point is to verify the public error contract, not the internal exception stack.

#### Deep dive

Use MVC slice tests when the advice is part of MVC behavior. Full integration tests can verify the real stack for critical errors.

#### Production angle

Consistent error responses make clients reliable and prevent leaking internals.

#### Traps / caveats

- Make sure the advice is actually loaded in the test.
- Do not expose stack traces, SQL details or secrets.
- Test both expected domain errors and unexpected failures.

#### Optional Anki

Q: What does `@ControllerAdvice` testing protect?
A: The public HTTP error contract.

</details>

<details>
<summary><strong>TEST-API-005. How should REST API tests verify status codes, headers and response bodies?</strong></summary>

#### Short answer

Assert the status, required headers and semantic response body fields that form the API contract.

#### Interview answer

A good API test checks the HTTP status, content type, cache or location headers if relevant, and important JSON fields. It should verify both success and failure responses. For collections, assert pagination metadata, ordering rules and item content that matters.

Avoid freezing incidental field order or volatile values unless they are explicitly part of the contract.

#### Deep dive

JSON path assertions, object mapping assertions and schema/contract checks can complement each other.

#### Production angle

API tests protect clients from accidental contract breaks during refactoring.

#### Traps / caveats

- Do not assert only status code.
- Normalize timestamps, IDs or generated values when needed.
- Include negative authorization and validation cases.

#### Optional Anki

Q: API tests should assert more than what?
A: More than just HTTP status.

</details>

<a id="test-api-006"></a>

<details>
<summary><strong>TEST-API-006. How do you test JSON serialization and deserialization behavior?</strong></summary>

#### Short answer

Use the real application mapper or MVC layer and test representative valid and invalid payloads.

#### Interview answer

For DTOs and endpoints, I test that expected JSON is produced and accepted using the same Jackson configuration as production. Important cases include dates, numbers, enums, unknown fields, missing fields, `null`, default values and validation interaction.

For API endpoints, MVC tests verify message converters and error handling, not just `new ObjectMapper()`.

#### Deep dive

Use dedicated JSON tests for mapper behavior and API tests for request/response contracts.

#### Production angle

Serialization tests catch breaking payload changes and mapper configuration drift.

#### Traps / caveats

- A test-only mapper may not match production.
- Snapshot tests can be brittle.
- JPA entities should not usually be serialized directly from controllers.

#### Optional Anki

Q: What mapper should JSON tests use?
A: The real application-configured mapper.

</details>

<a id="test-api-007"></a>

<details>
<summary><strong>TEST-API-007. How do you test pagination, sorting and filtering endpoints?</strong></summary>

#### Short answer

Use realistic data and assert page metadata, ordering, filters, limits and edge cases.

#### Interview answer

I prepare enough data to prove filtering, sorting and pagination behavior. Tests should cover default page size, explicit limits, invalid parameters, stable ordering, empty pages, last page and combinations of filters.

For database-backed endpoints, include enough records to reveal wrong joins or missing deterministic ordering.

#### Deep dive

Offset pagination and cursor pagination have different contracts, so tests should reflect the chosen style.

#### Production angle

Pagination bugs create duplicate or missing results for clients and can cause expensive database queries.

#### Traps / caveats

- Small datasets hide ordering issues.
- Sorting must be deterministic when values tie.
- Validate maximum page size to prevent abuse.

#### Optional Anki

Q: What does pagination testing need besides items?
A: Metadata, ordering, limits and edge cases.

</details>

<a id="test-api-008"></a>

<details>
<summary><strong>TEST-API-008. How do you test authentication and authorization rules at the API layer?</strong></summary>

#### Short answer

Test unauthenticated, unauthorized and authorized requests, including object ownership and tenant boundaries.

#### Interview answer

API security tests should cover no credentials, invalid credentials, valid user without permission and valid user with permission. For real systems, role checks are not enough; test object-level access, tenant isolation and denied cases.

Use Spring Security test support, mock JWTs or real authentication setup depending on the test level.

#### Deep dive

For method security, include tests that call through Spring proxies, not manually constructed services.

#### Production angle

Authorization regressions are high-impact because they can expose user or tenant data.

#### Traps / caveats

- Do not test only the allowed case.
- Mock users must match production authority mapping.
- Filtering unauthorized data after querying can still leak data or hurt performance.

#### Optional Anki

Q: Security API tests must include which cases?
A: Unauthenticated, unauthorized and authorized cases.

</details>

<details>
<summary><strong>TEST-API-009. How can API tests protect backward compatibility for clients?</strong></summary>

#### Short answer

They lock down stable request and response contracts with examples, schema checks and compatibility tests.

#### Interview answer

API compatibility tests verify that existing clients can still send old requests and understand responses. They should cover field names, required fields, enum values, error shapes, status codes and tolerated unknown fields. OpenAPI diffs, golden examples and consumer-driven contracts can help.

The goal is to catch accidental breaking changes before release.

#### Deep dive

Backward compatibility is not only JSON shape. Semantics, default values, pagination and error behavior also matter.

#### Production angle

Compatibility tests reduce client outages during rolling deployments and multi-team API evolution.

#### Traps / caveats

- Snapshot updates should be reviewed, not blindly accepted.
- Adding a required request field is breaking.
- Removing or renaming response fields can break strict clients.

#### Optional Anki

Q: API compatibility tests protect whom?
A: Existing clients and consumers.

</details>

<details>
<summary><strong>🧠 TEST-API-010. When are snapshot tests for API responses helpful, and when are they risky?</strong></summary>

#### Short answer

They are helpful for reviewed public examples, but risky when they freeze incidental details or are updated blindly.

#### Interview answer

Snapshot or golden-file tests are useful for complex response shapes, partner contracts and examples that should be reviewed as API artifacts. They make diffs visible when a response changes.

They become risky when they include volatile IDs, timestamps, field ordering or irrelevant formatting, or when developers accept updates without understanding the compatibility impact.

#### Deep dive

Combine snapshots with semantic assertions for important fields and normalize volatile values.

#### Production angle

Good snapshots catch accidental contract breaks during refactors or dependency upgrades.

#### Traps / caveats

- Do not snapshot everything.
- Avoid freezing internal/debug fields.
- Snapshot changes need code review attention.

#### Optional Anki

Q: Main risk of snapshot API tests?
A: Brittle tests or blindly accepted contract changes.

</details>

<details>
<summary><strong>🧠 TEST-API-011. How do you test asynchronous HTTP endpoints, streaming responses or SSE?</strong></summary>

#### Short answer

Use a client/test tool that can observe completion, chunks, events, timeouts and cancellation behavior.

#### Interview answer

For async HTTP endpoints, tests should verify accepted status, polling or callback behavior, eventual result and timeout/error paths. For streaming or SSE, use WebTestClient or an integration client that can consume multiple events and assert ordering, content, completion and cancellation.

The test should not rely on arbitrary sleeps. It should wait for expected events with bounded timeouts.

#### Deep dive

Backpressure and resource cleanup may need integration-level tests rather than simple controller unit tests.

#### Production angle

Streaming and async endpoints can leak resources or hang clients if cancellation and timeout behavior is wrong.

#### Traps / caveats

- MockMvc may not be enough for real streaming behavior.
- Always test client disconnect or cancellation when relevant.
- Avoid unbounded waits in CI.

#### Optional Anki

Q: What should streaming API tests verify?
A: Events/chunks, order, completion, timeout and cancellation behavior.

</details>
