# Unit testing business logic and asynchronous code

---

<a id="test-unit-001"></a>

<details>
<summary><strong>TEST-UNIT-001. What kind of business logic is easiest to unit test?</strong></summary>

#### Short answer

Logic with explicit inputs, deterministic outputs and dependencies passed from the outside.

#### Interview answer

Business logic is easiest to unit test when it is separated from frameworks, I/O, static state and real time. A domain service or validator that receives inputs and collaborators through constructors can be tested with plain JUnit and simple fakes or mocks.

Pure calculations, decision rules, state transitions and validation rules are ideal unit-test candidates.

#### Deep dive

Good design for testing is usually good design for maintenance: explicit dependencies, small responsibilities and clear boundaries.

#### Production angle

Fast unit tests let teams cover many business cases and edge cases before code reaches integration environments.

#### Traps / caveats

- Static calls, hidden dependencies and global state make tests harder.
- Framework annotations do not replace business tests.
- Do not mock value objects just because they are dependencies.

#### Optional Anki

Q: What makes logic easy to unit test?
A: Explicit inputs, deterministic behavior and injectable dependencies.

</details>

<a id="test-unit-002"></a>

<details>
<summary><strong>TEST-UNIT-002. How do you unit test a service method with several dependencies?</strong></summary>

#### Short answer

Build the service with controlled collaborators, set up only the scenario, call the method and assert the observable result.

#### Interview answer

I construct the service directly, usually with constructor injection. For each dependency, I decide whether a real object, fake or mock is clearest. Then I set up only the data needed for the scenario, call the method and assert the returned result, state change or meaningful interaction.

If the setup is huge, the service may be doing too much or the test may be at the wrong level.

#### Deep dive

Test data builders help keep irrelevant fields out of the test while making important values visible.

#### Production angle

Service tests protect business decisions without paying the cost of starting the whole application.

#### Traps / caveats

- Avoid verifying every dependency call.
- Do not mock the class under test.
- Add integration tests for boundaries replaced by mocks.

#### Optional Anki

Q: How should a service be constructed in a plain unit test?
A: Directly, with controlled constructor dependencies.

</details>

<a id="test-unit-003"></a>

<details>
<summary><strong>TEST-UNIT-003. How should validation rules be tested?</strong></summary>

#### Short answer

Test valid cases, invalid cases, boundaries and how validation errors are reported.

#### Interview answer

Validation tests should cover the accepted path and representative rejected inputs: missing values, invalid format, boundary limits, inconsistent fields and forbidden state transitions. For service validation, assert domain errors or exceptions. For API validation, also test HTTP status and error body shape.

The goal is to verify the rule and the contract of the failure.

#### Deep dive

Bean Validation annotations need integration or slice tests when group validation, custom validators or request binding are important.

#### Production angle

Validation prevents bad data from reaching the database, queues or downstream services.

#### Traps / caveats

- Test cross-field rules, not only field-level annotations.
- Error messages may be localized; assert stable codes if available.
- Missing and explicit `null` may have different API semantics.

#### Optional Anki

Q: What validation cases matter most?
A: Valid, invalid and boundary cases plus error reporting.

</details>

<a id="test-unit-004"></a>

<details>
<summary><strong>TEST-UNIT-004. How should boundary values and invalid inputs be tested?</strong></summary>

#### Short answer

Test values just below, at and just above important limits, plus representative invalid inputs.

#### Interview answer

Boundary value testing focuses on where behavior changes: minimum and maximum, zero, limit values, empty collections, duplicate elements, too-long strings and invalid enum values. Invalid input tests should verify that the system rejects bad data safely and consistently.

I prefer a small set of meaningful examples over a large list of random cases.

#### Deep dive

Equivalence classes help reduce duplicate cases. For example, one invalid negative amount may represent a whole class unless different negatives behave differently.

#### Production angle

Limits and invalid data are common sources of production bugs and client-facing errors.

#### Traps / caveats

- Do not test only happy paths.
- Include large enough data to expose pagination or batching issues.
- Make sure invalid-input tests assert no unsafe side effects.

#### Optional Anki

Q: Boundary testing checks which values?
A: Just below, at and just above important limits.

</details>

<a id="test-unit-005"></a>

<details>
<summary><strong>TEST-UNIT-005. How do you test code that depends on the current time?</strong></summary>

#### Short answer

Inject `Clock` or another time provider and control it in tests.

#### Interview answer

Code that calls `Instant.now()` or `LocalDate.now()` directly is harder to test. I prefer injecting `Clock` and using a fixed clock in tests. Then scenarios like expiration, grace periods, month boundaries and daylight-saving changes can be tested deterministically.

The production code can use `Clock.systemUTC()` or another configured clock.

#### Deep dive

Use explicit time zones for date-based rules. `LocalDate.now()` with a default zone can behave differently across environments.

#### Production angle

Time bugs often appear at midnight, month-end, leap years, time-zone boundaries or after clock skew.

#### Traps / caveats

- Do not sleep in tests to wait for time to pass.
- Avoid default time zone assumptions.
- Use `Instant` for machine time and local date/time types for business calendar rules.

#### Optional Anki

Q: Best Java dependency for testable current time?
A: `Clock`.

</details>

<a id="test-unit-006"></a>

<details>
<summary><strong>TEST-UNIT-006. How do you test code that depends on random values or generated IDs?</strong></summary>

#### Short answer

Inject the generator or wrap it behind an interface so tests can return predictable values.

#### Interview answer

For UUIDs, random tokens, sequence values or generated external IDs, I avoid calling the generator directly inside complex logic. I inject a generator and use a fixed implementation in tests. Then the test can assert the resulting object, event or request without brittle pattern matching.

For security-sensitive randomness, tests should not weaken production randomness; they should replace it only at the boundary.

#### Deep dive

Sometimes the exact generated value is irrelevant. In that case, assert shape or presence instead of a fixed value.

#### Production angle

Generated IDs are often part of idempotency keys, logs, events and external contracts.

#### Traps / caveats

- Do not make production randomness deterministic.
- Avoid asserting a random value that should be opaque.
- Test collision or duplicate handling separately if it matters.

#### Optional Anki

Q: How do you make generated IDs testable?
A: Inject or wrap the ID generator.

</details>

<a id="test-unit-007"></a>

<details>
<summary><strong>TEST-UNIT-007. How do test data builders improve unit tests?</strong></summary>

#### Short answer

They create readable defaults and let each test override only the fields relevant to the scenario.

#### Interview answer

Test data builders reduce noise when objects have many fields. A builder can create a valid default `Order`, `User` or DTO, and each test changes only the important values. This keeps tests focused on behavior rather than object construction.

They are especially useful for domain objects, request DTOs and event payloads.

#### Deep dive

Builders should live in test code unless they are useful production APIs too.

#### Production angle

Readable test data makes business rule changes safer and code reviews faster.

#### Traps / caveats

- Defaults should be realistic and valid.
- Do not hide important scenario values inside builders.
- Too many builder layers can obscure the test.

#### Optional Anki

Q: Main benefit of test data builders?
A: Clear defaults with scenario-specific overrides.

</details>

<a id="test-unit-008"></a>

<details>
<summary><strong>TEST-UNIT-008. Why should unit tests avoid shared mutable state?</strong></summary>

#### Short answer

Shared mutable state makes tests order-dependent, flaky and hard to run in parallel.

#### Interview answer

Each unit test should create or reset the state it needs. If tests share mutable collections, builders, mocks or static state, one test can affect another. That creates failures that depend on execution order or parallelism.

Fresh state per test is usually simpler than complex cleanup.

#### Deep dive

Immutable fixtures are safer than mutable shared fixtures. If setup is expensive, share only truly read-only data.

#### Production angle

Order-dependent tests waste CI time and hide real regressions behind unreliable failures.

#### Traps / caveats

- Static caches can leak between tests.
- Reusing mocks across tests can preserve interactions.
- Parallel execution exposes hidden coupling.

#### Optional Anki

Q: Why avoid shared mutable test state?
A: It causes order-dependent and flaky tests.

</details>

<a id="test-unit-009"></a>

<details>
<summary><strong>TEST-UNIT-009. How do you keep unit tests readable when business rules have many cases?</strong></summary>

#### Short answer

Group cases by rule, use clear names, parameterize simple variations and keep important data visible.

#### Interview answer

For many business cases, I split tests by scenario or rule. If the same rule is checked with many inputs, parameterized tests work well. If each case has different setup, separate named tests are clearer. Builders can reduce setup noise, but the values that explain the case should remain visible.

I also avoid one giant test that checks every case at once.

#### Deep dive

Tables of examples are useful for simple input/output rules, but not for complex workflows.

#### Production angle

Readable tests help future developers understand the business rule and safely extend it.

#### Traps / caveats

- Over-parameterization can make failures hard to understand.
- Too much helper abstraction hides behavior.
- Keep regression tests named after the bug or scenario.

#### Optional Anki

Q: When are parameterized tests good for business rules?
A: Same rule, many simple input/output cases.

</details>

<a id="test-unit-010"></a>

<details>
<summary><strong>TEST-UNIT-010. How do you test asynchronous code without relying on `Thread.sleep()`?</strong></summary>

#### Short answer

Wait for observable conditions, use controlled executors or await futures with timeouts.

#### Interview answer

`Thread.sleep()` guesses timing and makes tests flaky. For async code, I prefer a deterministic executor when possible, or I wait until an observable condition becomes true using Awaitility-style polling. For `CompletableFuture`, I can compose stages and wait with a bounded timeout.

The test should observe the result: saved state, published message, completed future or callback invocation.

#### Deep dive

In unit tests, injecting an executor lets tests run tasks synchronously or with controlled scheduling.

#### Production angle

Async behavior is a common source of race conditions and CI-only failures.

#### Traps / caveats

- Sleeping longer only makes tests slower, not correct.
- Always use a maximum timeout to avoid hanging CI.
- Verify failure paths and not only successful completion.

#### Optional Anki

Q: Better alternative to `Thread.sleep()` in async tests?
A: Wait for a condition with a bounded timeout.

</details>

<a id="test-unit-011"></a>

<details>
<summary><strong>TEST-UNIT-011. How do you test cancellation, interruption and timeout paths?</strong></summary>

#### Short answer

Trigger the condition deliberately and assert cleanup, propagated status and absence of unsafe side effects.

#### Interview answer

For cancellation and timeout logic, I make the dependency block or delay in a controlled way, then cancel the future, interrupt the thread or exceed the timeout. The test should assert that resources are released, interrupted status is handled correctly, transactions are not left inconsistent and callers receive the expected exception or result.

For Java thread interruption, code should usually restore the interrupted flag if it catches `InterruptedException` and cannot fully handle it.

#### Deep dive

Use latches, controllable executors or fake clients instead of real slow sleeps.

#### Production angle

Bad cancellation handling can leak threads, hold locks, keep database connections or produce duplicate side effects.

#### Traps / caveats

- Do not swallow `InterruptedException` silently.
- Avoid relying on exact timing.
- Verify cleanup after failure, not just the thrown exception.

#### Optional Anki

Q: What should cancellation tests verify?
A: Cleanup, propagated outcome and no unsafe side effects.

</details>

<a id="test-unit-012"></a>

<details>
<summary><strong>🧠 TEST-UNIT-012. What is property-based testing, and when can it help?</strong></summary>

#### Short answer

Property-based testing generates many inputs and checks general rules that should always hold.

#### Interview answer

Instead of writing only example-based tests, property-based tests define invariants. For example, sorting should keep the same elements and produce ordered output; encoding then decoding should return the original value; validation should reject all negative amounts.

It helps when many input combinations exist and the rule can be expressed clearly.

#### Deep dive

Property-based testing is strongest for pure functions, parsers, serializers, calculations and data transformations.

#### Production angle

It can find edge cases humans did not think to write manually.

#### Traps / caveats

- The property must be meaningful.
- Generated cases can be hard to debug without shrinking and good reporting.
- It complements examples; it does not replace important business scenarios.

#### Optional Anki

Q: What does property-based testing check?
A: General invariants across generated inputs.

</details>
