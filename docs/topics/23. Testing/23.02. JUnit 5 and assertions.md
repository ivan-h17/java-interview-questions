<a id="test-junit-001"></a>

<details>
<summary><strong>TEST-JUNIT-001. What are the most important JUnit 5 concepts for backend testing?</strong></summary>

#### Short answer

Tests, lifecycle callbacks, assertions, parameterized tests, extensions, tags and test execution configuration.

#### Interview answer

For backend work, the core JUnit 5 concepts are `@Test`, lifecycle annotations, assertions, parameterized tests, nested tests, tags and extensions. JUnit Jupiter provides the programming model, while the platform discovers and runs tests through build tools and IDEs.

The practical skill is knowing when to keep a test plain JUnit and when to combine it with Spring, Mockito, Testcontainers or another integration tool.

#### Deep dive

JUnit 5 is extensible, which is why libraries can integrate cleanly for Mockito, Spring, temporary directories and repeated setup.

#### Production angle

A clear JUnit foundation keeps tests fast, readable and compatible with CI.

#### Traps / caveats

- Do not start Spring when plain JUnit is enough.
- Lifecycle callbacks can hide important setup.
- Tags are useful only if the build uses them consistently.

#### Optional Anki

Q: What is JUnit Jupiter?
A: The JUnit 5 programming model for writing tests.

<details>
<summary><strong>TEST-JUNIT-002. How do `@BeforeEach`, `@AfterEach`, `@BeforeAll` and `@AfterAll` differ?</strong></summary>

#### Short answer

`BeforeEach` and `AfterEach` run around every test; `BeforeAll` and `AfterAll` run once for the test class.

#### Interview answer

`@BeforeEach` prepares fresh state before every test method. `@AfterEach` cleans up after each test. `@BeforeAll` runs once before all tests in the class, commonly for expensive shared setup. `@AfterAll` runs once at the end.

Per-test setup is safer for isolation. Class-level setup is useful for expensive resources but must not create shared mutable state that makes tests order-dependent.

#### Deep dive

By default, `@BeforeAll` and `@AfterAll` methods are static unless the test instance lifecycle is changed.

#### Production angle

Proper lifecycle use prevents test pollution and reduces expensive startup work.

#### Traps / caveats

- Shared mutable state in `BeforeAll` can make tests flaky.
- Cleanup should happen even when a test fails.
- Hidden setup makes tests harder to read.

#### Optional Anki

Q: Which JUnit lifecycle callback runs before every test?
A: `@BeforeEach`.

</details>

<details>
<summary><strong>TEST-JUNIT-003. When are nested tests useful?</strong></summary>

#### Short answer

They group related scenarios under shared context while keeping each test case explicit.

#### Interview answer

Nested tests are useful when a class or method has clear sub-scenarios, such as "when user is inactive" or "when balance is insufficient". They make test output and structure easier to scan.

They are especially helpful for business rules with several contexts and expected outcomes.

#### Deep dive

Nested classes can have their own setup, but overusing nested setup can make state harder to follow.

#### Production angle

Good grouping makes failures easier to understand during code review or CI investigation.

#### Traps / caveats

- Do not create deep nesting.
- Avoid relying on hidden parent state too heavily.
- Nested tests are for readability, not for sharing mutable state.

#### Optional Anki

Q: Main benefit of nested tests?
A: Clear grouping of related scenarios.

</details>

<a id="test-junit-004"></a>

<details>
<summary><strong>TEST-JUNIT-004. When should you use parameterized tests?</strong></summary>

#### Short answer

When the same behavior should be checked across several inputs and expected outputs.

#### Interview answer

Parameterized tests are good for validation rules, boundary values, enum cases, parsing, formatting and mapping logic. They remove duplication while keeping the tested cases visible.

I use them when one test body clearly expresses the rule. If each case needs different setup or different assertions, separate tests may be clearer.

#### Deep dive

Sources include inline values, CSV data, enum values, methods and custom argument providers.

#### Production angle

Parameterized tests make it cheap to cover important edge cases and regression examples.

#### Traps / caveats

- Too many columns make parameterized tests unreadable.
- Case names should make failures understandable.
- Do not hide important business examples in obscure data providers.

#### Optional Anki

Q: Best use of parameterized tests?
A: Same rule, multiple representative inputs.

</details>

<a id="test-junit-005"></a>

<details>
<summary><strong>TEST-JUNIT-005. How do you test that code throws the expected exception?</strong></summary>

#### Short answer

Use `assertThrows` and assert important exception details when they are part of the behavior.

#### Interview answer

In JUnit 5, `assertThrows` verifies that a specific exception type is thrown. I usually keep the act step inside the lambda and then assert meaningful properties, such as error code, message fragment or cause, if callers depend on them.

The test should also ensure the exception comes from the operation under test, not from setup.

#### Deep dive

For APIs, exception tests often belong at two levels: service exception behavior and HTTP error mapping.

#### Production angle

Exception tests protect validation, rollback, retry decisions and client-facing error contracts.

#### Traps / caveats

- Do not assert an entire fragile message unless it is a contract.
- Avoid catching broad `Exception` in tests.
- Verify side effects did not happen when failure should be atomic.

#### Optional Anki

Q: JUnit 5 method for expected exceptions?
A: `assertThrows`.

</details>

<a id="test-junit-006"></a>

<details>
<summary><strong>TEST-JUNIT-006. What is `assertAll`, and when does it improve feedback?</strong></summary>

#### Short answer

`assertAll` groups assertions and reports all failures together instead of stopping at the first one.

#### Interview answer

`assertAll` is useful when several assertions describe one logical result, such as fields of a DTO, response body or database row. It improves feedback because one failing run can show all mismatched fields.

I avoid using it to combine unrelated behaviors into one large test.

#### Deep dive

AssertJ recursive comparison or extracting assertions can sometimes be clearer than many manual field checks.

#### Production angle

Better failure output shortens CI debugging time.

#### Traps / caveats

- Do not hide unrelated checks in one `assertAll`.
- Too many field assertions can indicate brittle tests.
- Prefer semantic assertions over blind object dumps.

#### Optional Anki

Q: What problem does `assertAll` solve?
A: It reports multiple assertion failures from one logical check.

</details>

<a id="test-junit-007"></a>

<details>
<summary><strong>TEST-JUNIT-007. How should tests handle timeouts?</strong></summary>

#### Short answer

Use timeouts as safety limits, not as the main synchronization mechanism.

#### Interview answer

Timeouts prevent tests from hanging forever, especially around asynchronous code, locks, networking and containers. But a timeout should not replace waiting for a real condition. For async behavior, use Awaitility-style polling, futures with controlled executors or explicit latches in test-only code.

Preemptive timeouts can interrupt code from another thread, so use them carefully when transactions or thread-local context matter.

#### Deep dive

Timeout values should be generous enough for CI variance but tight enough to expose hangs quickly.

#### Production angle

Timeout tests catch missing cancellation, blocking calls and unsafe retry behavior.

#### Traps / caveats

- Fixed sleeps are slow and flaky.
- Very tight timeouts fail under CI load.
- Preemptive interruption can create misleading failures.

#### Optional Anki

Q: What should synchronize async tests?
A: A condition or signal, not a guessed sleep.

</details>

<a id="test-junit-008"></a>

<details>
<summary><strong>TEST-JUNIT-008. How does AssertJ improve test readability compared with basic assertions?</strong></summary>

#### Short answer

AssertJ provides fluent, type-specific assertions with clearer failure messages and richer collection/object checks.

#### Interview answer

AssertJ lets tests express expectations close to natural language: contains exactly, has field value, satisfies condition, extracts fields, recursively compares objects. It often makes assertions shorter and failure messages more useful than basic JUnit assertions.

For backend tests, it is especially useful for DTOs, collections, exceptions and database result checks.

#### Deep dive

The value is not the library itself; the value is precise, readable assertions.

#### Production angle

Readable assertions make test failures easier to diagnose during CI and code review.

#### Traps / caveats

- Recursive comparison can hide which fields are intentionally part of the contract.
- Overly clever assertions can become unreadable.
- Do not compare volatile fields unless normalized.

#### Optional Anki

Q: Main benefit of AssertJ?
A: Fluent, precise assertions with useful failure output.

</details>

<a id="test-junit-009"></a>

<details>
<summary><strong>TEST-JUNIT-009. How do you keep assertions focused and useful when a test fails?</strong></summary>

#### Short answer

Assert the behavior that matters, include enough context in failures and avoid broad or incidental checks.

#### Interview answer

I keep each test centered on one scenario and assert the observable outcome. The assertion should tell me what contract broke: status code, error code, saved state, published event or returned value. If a complex object is checked, I prefer extracting meaningful fields or using a well-scoped recursive comparison.

Good test data names also make failure output useful.

#### Deep dive

It is often better to assert a small set of important fields than to freeze every incidental detail.

#### Production angle

Focused assertions reduce time spent debugging unrelated snapshot or object comparison failures.

#### Traps / caveats

- Weak assertions let broken behavior pass.
- Overly broad assertions make harmless changes fail.
- Avoid asserting unstable ordering unless ordering is required.

#### Optional Anki

Q: What should an assertion failure explain?
A: Which meaningful behavior or contract broke.

</details>

<details>
<summary><strong>🧠 TEST-JUNIT-010. How do JUnit 5 extensions such as `ParameterResolver` or `BeforeEachCallback` work at a high level?</strong></summary>

#### Short answer

Extensions hook into the JUnit lifecycle to provide parameters, setup, cleanup, conditions or exception handling.

#### Interview answer

JUnit 5 extensions are a formal way to customize test execution. A `ParameterResolver` can provide objects to test methods or constructors. `BeforeEachCallback` and `AfterEachCallback` run logic around each test. Other extension points handle conditions, exceptions and test instances.

Frameworks use this model to integrate Mockito, Spring, temporary resources and custom test infrastructure.

#### Deep dive

Extensions are powerful, but project-specific extensions should stay small and obvious. Hidden magic can make tests harder to reason about.

#### Production angle

Good extensions reduce duplicate setup for infrastructure-heavy tests, but bad ones can hide shared state or cleanup mistakes.

#### Traps / caveats

- Avoid global extensions that silently change test behavior.
- Make resource ownership and cleanup explicit.
- Prefer standard extensions before building custom ones.

#### Optional Anki

Q: What does a JUnit `ParameterResolver` do?
A: Supplies values for test method or constructor parameters.

</details>
