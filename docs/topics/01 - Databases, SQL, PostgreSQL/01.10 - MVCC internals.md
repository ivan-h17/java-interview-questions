<summary>🔥 <strong>DB-MVCC-001. What is MVCC in PostgreSQL?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Question</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>What is MVCC in PostgreSQL?</p>
</td>
<td valign="top" width="50%">
<p>Что такое MVCC в PostgreSQL?</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>MVCC means Multi-Version Concurrency Control. PostgreSQL keeps multiple row versions and lets each transaction read a consistent snapshot.</p>
</td>
<td valign="top" width="50%">
<p>MVCC означает Multi-Version Concurrency Control. PostgreSQL хранит несколько версий строк и позволяет каждой транзакции читать согласованный snapshot.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>MVCC is PostgreSQL’s main concurrency model. Instead of making readers wait for writers, PostgreSQL usually lets readers see the row version that is visible to their snapshot while writers create newer row versions.</p>
</td>
<td valign="top" width="50%">
<p>MVCC — основная модель concurrency в PostgreSQL. Вместо того чтобы заставлять readers ждать writers, PostgreSQL обычно показывает reader-ам версию строки, видимую их snapshot, а writers создают новые версии строк.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Each heap tuple has MVCC metadata. Visibility is not just “latest row wins”; PostgreSQL checks transaction IDs, snapshots, commit status, and tuple metadata to decide whether a tuple version is visible.</p>
</td>
<td valign="top" width="50%">
<p>У каждой heap tuple есть MVCC metadata. Видимость — это не просто “берём последнюю строку”; PostgreSQL проверяет transaction IDs, snapshots, commit status и metadata tuple, чтобы решить, видима ли версия строки.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>MVCC explains dead tuples, table bloat, autovacuum pressure, old snapshots, index-only scan heap fetches, and why long transactions can hurt the whole database.</p>
</td>
<td valign="top" width="50%">
<p>MVCC объясняет dead tuples, table bloat, нагрузку autovacuum, старые snapshots, heap fetches в index-only scans и то, почему долгие транзакции могут вредить всей базе.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>MVCC reduces read/write blocking, but does not remove all locks.</li><li>Write-write conflicts can still block.</li><li>Dead tuples must be cleaned by VACUUM.</li><li>Long-running snapshots can prevent cleanup.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>MVCC снижает read/write blocking, но не отменяет все locks.</li><li>Write-write conflicts всё равно могут блокироваться.</li><li>Dead tuples должен чистить VACUUM.</li><li>Долгоживущие snapshots могут мешать cleanup.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is MVCC?
A: PostgreSQL’s snapshot-based concurrency model that stores multiple row versions.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое MVCC?
A: Snapshot-based concurrency model PostgreSQL, при которой база хранит несколько версий строк.</p>

<summary>🔥 <strong>DB-MVCC-002. How does MVCC work under the hood?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Question</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>How does MVCC work under the hood?</p>
</td>
<td valign="top" width="50%">
<p>Как MVCC работает под капотом?</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>PostgreSQL stores row versions in heap pages. INSERT creates a tuple, UPDATE creates a new tuple version, and DELETE marks an old tuple version as deleted.</p>
</td>
<td valign="top" width="50%">
<p>PostgreSQL хранит версии строк в heap pages. INSERT создаёт tuple, UPDATE создаёт новую версию tuple, а DELETE помечает старую tuple как удалённую.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A statement reads through a snapshot. During a scan, PostgreSQL checks tuple metadata such as <code>xmin</code> and <code>xmax</code> together with transaction status to decide whether a tuple version is visible.</p>
</td>
<td valign="top" width="50%">
<p>Statement читает через snapshot. Во время scan PostgreSQL проверяет metadata tuple, например <code>xmin</code> и <code>xmax</code>, вместе со статусом транзакций, чтобы решить, видима ли tuple version.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Conceptually, an update is closer to creating a new row version than modifying a row in place. Old snapshots can still see the old version, while new snapshots can see the committed new version.</p>
<pre><code class="language-sql">-- conceptual example
UPDATE accounts SET balance = balance + 100 WHERE id = 1;
-- old tuple version remains for old snapshots
-- new tuple version becomes visible after commit</code></pre>
</td>
<td valign="top" width="50%">
<p>Концептуально update ближе к созданию новой версии строки, чем к изменению строки на месте. Старые snapshots могут видеть старую версию, а новые snapshots — новую committed версию.</p>
<pre><code class="language-sql">-- концептуальный пример
UPDATE accounts SET balance = balance + 100 WHERE id = 1;
-- старая tuple version остаётся для старых snapshots
-- новая tuple version становится видимой после commit</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Under the hood MVCC means update-heavy tables create dead tuples, generate WAL, may update indexes, and require enough autovacuum capacity. HOT updates can reduce index churn only under specific conditions.</p>
</td>
<td valign="top" width="50%">
<p>Под капотом MVCC означает, что update-heavy таблицы создают dead tuples, генерируют WAL, могут обновлять индексы и требуют достаточной autovacuum capacity. HOT updates уменьшают index churn только при определённых условиях.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>UPDATE is not a cheap in-place overwrite.</li><li><code>xmax</code> can also be involved in locking metadata, so do not oversimplify it.</li><li>HOT updates are an optimization, not a guarantee.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>UPDATE — это не дешёвая in-place перезапись.</li><li><code>xmax</code> может участвовать и в locking metadata, поэтому не стоит его упрощать.</li><li>HOT updates — оптимизация, а не гарантия.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why does UPDATE create old versions?
A: To preserve visibility for transactions that still need the old snapshot.</p>
</td>
<td valign="top" width="50%">
<p>Q: Почему UPDATE создаёт старые версии?
A: Чтобы сохранить видимость для транзакций, которым нужен старый snapshot.</p>
</td>
</tr>
</tbody>

<summary><strong>DB-MVCC-003. What is a transaction snapshot?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Question</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>What is a transaction snapshot?</p>
</td>
<td valign="top" width="50%">
<p>Что такое transaction snapshot?</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A transaction snapshot defines which transaction effects are visible to a statement or transaction.</p>
</td>
<td valign="top" width="50%">
<p>Transaction snapshot определяет, эффекты каких транзакций видимы statement-у или транзакции.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>At <code>READ COMMITTED</code>, PostgreSQL generally takes a fresh snapshot for each statement. At <code>REPEATABLE READ</code> and <code>SERIALIZABLE</code>, the transaction sees a stable transaction-level snapshot.</p>
</td>
<td valign="top" width="50%">
<p>На <code>READ COMMITTED</code> PostgreSQL обычно берёт свежий snapshot для каждого statement. На <code>REPEATABLE READ</code> и <code>SERIALIZABLE</code> транзакция видит стабильный transaction-level snapshot.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A snapshot is not a physical copy of rows. It is visibility information that lets PostgreSQL decide whether a tuple version was created by a visible transaction and not removed by a visible transaction.</p>
</td>
<td valign="top" width="50%">
<p>Snapshot — не физическая копия строк. Это visibility information, которая позволяет PostgreSQL решать, создана ли tuple version видимой транзакцией и не удалена ли видимой транзакцией.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Long-lived snapshots are a production problem because they can prevent VACUUM from removing dead tuples and can increase table/index bloat.</p>
</td>
<td valign="top" width="50%">
<p>Долгоживущие snapshots — production-проблема, потому что они могут мешать VACUUM удалять dead tuples и увеличивать table/index bloat.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Snapshot behavior depends on isolation level.</li><li>A snapshot is not a copy of the database.</li><li>Old snapshots can make cleanup impossible for some tuples.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>Поведение snapshot зависит от isolation level.</li><li>Snapshot — не копия базы.</li><li>Старые snapshots могут сделать cleanup некоторых tuples невозможным.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Is a snapshot a physical copy?

</td>
<td valign="top" width="50%">
<p>Q: Snapshot — это физическая копия?
