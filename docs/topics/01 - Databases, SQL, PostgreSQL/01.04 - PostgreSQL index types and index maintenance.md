<tbody>
<tr>
<th colspan="2" align="left">Question</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>What index types does PostgreSQL support?</p>
</td>
<td valign="top" width="50%">
<p>Какие типы индексов поддерживает PostgreSQL?</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>PostgreSQL supports several index access methods: B-tree, Hash, GiST, SP-GiST, GIN and BRIN. B-tree is the default and covers most common equality, range and sorting use cases.</p>
</td>
<td valign="top" width="50%">
<p>PostgreSQL поддерживает несколько index access methods: B-tree, Hash, GiST, SP-GiST, GIN и BRIN. B-tree используется по умолчанию и закрывает большинство обычных случаев: equality, range и sorting.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For a backend interview, I would start with B-tree as the default index type. Then I would mention that other index types exist for special data and operators: GIN for composite values like arrays, <code>jsonb</code> and full-text search, GiST/SP-GiST for specialized structures, and BRIN for very large physically ordered tables.</p>
</td>
<td valign="top" width="50%">
<p>На интервью я бы начал с того, что B-tree — дефолтный тип индекса. Затем стоит сказать, что остальные типы нужны под специальные данные и операторы: GIN для composite values вроде arrays, <code>jsonb</code> и full-text search, GiST/SP-GiST для специализированных структур, BRIN для очень больших физически упорядоченных таблиц.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The index type is selected with <code>USING</code>:</p>
<pre><code class="language-sql">CREATE INDEX idx_users_email ON users USING btree (email);
CREATE INDEX idx_events_payload ON events USING gin (payload);</code></pre>
<p>The important idea is that an index is not only a data structure; it is also tied to supported operators through operator classes.</p>
</td>
<td valign="top" width="50%">
<p>Тип индекса выбирается через <code>USING</code>:</p>
<pre><code class="language-sql">CREATE INDEX idx_users_email ON users USING btree (email);
CREATE INDEX idx_events_payload ON events USING gin (payload);</code></pre>
<p>Важная мысль: индекс — это не только структура данных, он также связан с поддерживаемыми операторами через operator classes.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, most indexes are B-tree. Use other types only when the query operators and data types require them, and confirm the choice with <code>EXPLAIN ANALYZE</code>.</p>
</td>
<td valign="top" width="50%">
<p>В production большинство индексов — B-tree. Другие типы стоит выбирать только когда этого требуют operators и data types, и проверять выбор через <code>EXPLAIN ANALYZE</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not choose GIN, GiST or BRIN just because they sound more advanced.</li>
<li>The same column may need different index types for different query patterns.</li>
<li>Operator class matters as much as index type.</li>
<li>Extra index types often have different write costs and maintenance behavior.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Не выбирай GIN, GiST или BRIN только потому, что они звучат “advanced”.</li>
<li>Для одной и той же колонки могут понадобиться разные типы индексов под разные query patterns.</li>
<li>Operator class так же важен, как и тип индекса.</li>
<li>У специальных типов индексов часто другие write costs и maintenance behavior.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the default PostgreSQL index type?<br>A: B-tree.</p>
</td>
<td valign="top" width="50%">
<p>Q: Какой тип индекса в PostgreSQL используется по умолчанию?<br>A: B-tree.</p>
</td>
</tr>

<summary><strong>DB-IDXTYPE-002. When would you use a B-tree index?</strong></summary>

<table>
<thead>
<tr>
<th align="left" width="50%">EN</th>
<th align="left" width="50%">RU</th>
</tr>
</thead>
<tbody>
<tr>
<th colspan="2" align="left">Question</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>When would you use a B-tree index?</p>
</td>
<td valign="top" width="50%">
<p>Когда стоит использовать B-tree индекс?</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use a B-tree index for the common ordered comparison patterns: equality, range filters, sorting, uniqueness and many foreign-key or join lookups.</p>
</td>
<td valign="top" width="50%">
<p>B-tree индекс используют для обычных ordered comparisons: equality, range filters, sorting, uniqueness и многих lookup-ов по foreign key или join key.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>B-tree is the default because it works well for scalar values that can be ordered: numbers, timestamps, text, UUIDs and many other types. It supports predicates like <code>=</code>, <code>&lt;</code>, <code>&gt;</code>, <code>BETWEEN</code>, <code>IS NULL</code>, and can also help with <code>ORDER BY</code>.</p>
</td>
<td valign="top" width="50%">
<p>B-tree — дефолтный тип, потому что он хорошо работает для scalar values, которые можно упорядочить: числа, timestamps, text, UUID и многие другие типы. Он поддерживает условия вроде <code>=</code>, <code>&lt;</code>, <code>&gt;</code>, <code>BETWEEN</code>, <code>IS NULL</code>, а также может помогать с <code>ORDER BY</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Typical examples:</p>
<pre><code class="language-sql">CREATE INDEX idx_orders_user_id ON orders (user_id);
CREATE INDEX idx_orders_created_at ON orders (created_at DESC);
CREATE UNIQUE INDEX idx_users_email ON users (email);</code></pre>
</td>
<td valign="top" width="50%">
<p>Типичные примеры:</p>
<pre><code class="language-sql">CREATE INDEX idx_orders_user_id ON orders (user_id);
CREATE INDEX idx_orders_created_at ON orders (created_at DESC);
CREATE UNIQUE INDEX idx_users_email ON users (email);</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For Java backend systems, B-tree indexes are usually the first tool for slow endpoints with selective filters, joins by IDs, pagination by timestamp/id, and uniqueness checks. Start with query shape and selectivity, not with “index every column”.</p>
</td>
<td valign="top" width="50%">
<p>В Java backend системах B-tree индекс обычно первый инструмент для медленных endpoints с селективными фильтрами, join-ами по ID, pagination по timestamp/id и проверками uniqueness. Начинать нужно с query shape и selectivity, а не с “индексировать каждую колонку”.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>B-tree is not good for arbitrary substring search like <code>LIKE &#x27;%abc%&#x27;</code> without special extensions/operator classes.</li>
<li>A B-tree on a low-selectivity column may be ignored.</li>
<li>Composite B-tree indexes depend heavily on column order.</li>
<li>An index that helps reads can hurt writes.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>B-tree плохо подходит для произвольного substring search вроде <code>LIKE &#x27;%abc%&#x27;</code> без специальных extensions/operator classes.</li>
<li>B-tree по низкоселективной колонке может игнорироваться.</li>
<li>Composite B-tree indexes сильно зависят от порядка колонок.</li>
<li>Индекс, который помогает чтению, может ухудшать запись.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Common B-tree use cases?<br>A: Equality, ranges, sorting, uniqueness and joins on ordered scalar columns.</p>
</td>
<td valign="top" width="50%">
<p>Q: Типичные случаи для B-tree?<br>A: Equality, ranges, sorting, uniqueness и joins по ordered scalar columns.</p>
</td>
</tr>

<td valign="top" width="50%">

</td>
</tr>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A Hash index is used for equality lookups only. In practice, B-tree is usually preferred unless measurement shows that Hash is better for a very specific equality-only workload.</p>
</td>
<td valign="top" width="50%">
<p>Hash индекс используется только для equality lookups. На практике чаще выбирают B-tree, если измерения не показывают, что Hash лучше для очень конкретной equality-only нагрузки.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Hash indexes store hash values and support equality comparisons. They do not preserve ordering, so they cannot help with range predicates or <code>ORDER BY</code>.</p>
</td>
<td valign="top" width="50%">
<p>Hash indexes хранят hash values и поддерживают equality comparisons. Они не сохраняют порядок, поэтому не помогают с range predicates или <code>ORDER BY</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example:</p>
<pre><code class="language-sql">CREATE INDEX idx_sessions_token_hash
ON sessions USING hash (token);</code></pre>
<p>This can theoretically help for <code>WHERE token = ?</code>, but a B-tree on <code>token</code> often works well too.</p>
</td>
<td valign="top" width="50%">
<p>Пример:</p>
<pre><code class="language-sql">CREATE INDEX idx_sessions_token_hash
ON sessions USING hash (token);</code></pre>
<p>Теоретически это может помочь для <code>WHERE token = ?</code>, но B-tree по <code>token</code> часто тоже работает хорошо.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use Hash indexes carefully. They are a niche option; the cost of surprising future maintainers may be higher than the small performance gain. If you use one, document why and keep the benchmark or <code>EXPLAIN ANALYZE</code> evidence.</p>
</td>
<td valign="top" width="50%">
<p>Hash indexes нужно использовать аккуратно. Это niche option; цена неожиданности для будущих maintainers может быть выше, чем небольшой performance gain. Если используешь — задокументируй почему и сохрани benchmark или <code>EXPLAIN ANALYZE</code> evidence.</p>

<ul>
<li>Hash indexes do not support range scans.</li>
<li>They do not support sorting.</li>
<li>They are not a general replacement for B-tree.</li>
<li>They are usually not the first choice for normal backend schemas.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Hash indexes не поддерживают range scans.</li>
<li>Они не поддерживают sorting.</li>
<li>Они не являются общей заменой B-tree.</li>
<li>Обычно это не первый выбор для обычных backend schemas.</li>

<summary><strong>🔥 DB-IDXTYPE-004. What is a GIN index?</strong></summary>

<table>
<thead>
<tr>
<th align="left" width="50%">EN</th>
<th align="left" width="50%">RU</th>
</tr>
</thead>
<tbody>
<tr>
<th colspan="2" align="left">Question</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>What is a GIN index?</p>
</td>
<td valign="top" width="50%">
<p>Что такое GIN индекс?</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>GIN means Generalized Inverted Index. It is useful when one table row contains multiple searchable elements, such as array elements, <code>jsonb</code> keys/values, full-text lexemes or trigram tokens.</p>
</td>
<td valign="top" width="50%">
<p>GIN означает Generalized Inverted Index. Он полезен, когда одна строка таблицы содержит много searchable elements: элементы массива, ключи/значения <code>jsonb</code>, full-text lexemes или trigram tokens.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>I explain GIN as an inverted index: instead of mapping one row to one key, it maps each contained key or token to the rows that contain it. This is why it works well for “contains” style queries.</p>
</td>
<td valign="top" width="50%">
<p>Я объясняю GIN как inverted index: он мапит каждый вложенный key/token на строки, которые его содержат. Поэтому он хорошо подходит для “contains”-запросов.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Examples:</p>
<pre><code class="language-sql">CREATE INDEX idx_posts_tags ON posts USING gin (tags);
CREATE INDEX idx_events_payload ON events USING gin (payload jsonb_path_ops);
CREATE INDEX idx_documents_search ON documents USING gin (to_tsvector(&#x27;english&#x27;, body));</code></pre>
<p>Common operators include array containment, <code>jsonb</code> containment and full-text search operators. For substring search, GIN is often used together with the <code>pg_trgm</code> extension.</p>
</td>
<td valign="top" width="50%">
<p>Примеры:</p>
<pre><code class="language-sql">CREATE INDEX idx_posts_tags ON posts USING gin (tags);
CREATE INDEX idx_events_payload ON events USING gin (payload jsonb_path_ops);
CREATE INDEX idx_documents_search ON documents USING gin (to_tsvector(&#x27;english&#x27;, body));</code></pre>
<p>Типичные операторы: containment для arrays, containment для <code>jsonb</code>, full-text search. Для substring search GIN часто используют вместе с extension <code>pg_trgm</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>GIN is powerful but not free. It can be larger and more expensive to update than B-tree. For high-write tables, check write overhead, pending list behavior, index size and actual query plans.</p>
</td>
<td valign="top" width="50%">
<p>GIN мощный, но не бесплатный. Он может быть больше и дороже на обновление, чем B-tree. Для high-write tables нужно смотреть write overhead, pending list behavior, index size и реальные query plans.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>GIN is usually not for simple scalar equality; B-tree is often better there.</li>
<li>GIN can be large.</li>
<li>GIN writes can be expensive.</li>
<li>The operator class matters: <code>jsonb_ops</code>, <code>jsonb_path_ops</code>, <code>gin_trgm_ops</code> behave differently.</li>
<li>A GIN index helps only if the query uses compatible operators.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>GIN обычно не нужен для простой scalar equality; там часто лучше B-tree.</li>
<li>GIN может быть большим.</li>
<li>Запись в GIN может быть дорогой.</li>
<li>Operator class важен: <code>jsonb_ops</code>, <code>jsonb_path_ops</code>, <code>gin_trgm_ops</code> ведут себя по-разному.</li>
<li>GIN помогает только если запрос использует compatible operators.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is GIN good for?<br>A: Searching inside composite values: arrays, <code>jsonb</code>, full-text vectors and trigram tokens.</p>
</td>
<td valign="top" width="50%">
<p>Q: Для чего хорош GIN?<br>A: Для поиска внутри composite values: arrays, <code>jsonb</code>, full-text vectors и trigram tokens.</p>
</td>
</tr>

<details>
<summary><strong>DB-IDXTYPE-005. When would you use a GIN index?</strong></summary>

<table>
<thead>
<tr>
<th align="left" width="50%">EN</th>
<th align="left" width="50%">RU</th>
</tr>
</thead>
<tbody>
<tr>
<th colspan="2" align="left">Question</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>When would you use a GIN index?</p>
</td>
<td valign="top" width="50%">
<p>Когда стоит использовать GIN индекс?</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use a GIN index when queries search inside a composite value: array contains element, <code>jsonb</code> contains path/value, full-text search matches lexemes, or trigram search matches text fragments.</p>
</td>
<td valign="top" width="50%">
<p>GIN индекс используют, когда запрос ищет внутри composite value: array содержит элемент, <code>jsonb</code> содержит path/value, full-text search совпадает с lexemes или trigram search ищет text fragments.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Typical use cases are tags, permissions arrays, JSONB metadata, document search and flexible filters over semi-structured data. The key is that the query must use operators supported by the GIN operator class.</p>
</td>
<td valign="top" width="50%">
<p>Типичные случаи: tags, permission arrays, JSONB metadata, document search и гибкие фильтры по semi-structured data. Важно, чтобы запрос использовал операторы, поддерживаемые GIN operator class.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Examples:</p>
<pre><code class="language-sql">-- array containment
SELECT * FROM posts WHERE tags @&gt; ARRAY[&#x27;java&#x27;];

-- JSONB containment
SELECT * FROM events WHERE payload @&gt; &#x27;{&quot;type&quot;: &quot;ORDER_CREATED&quot;}&#x27;;

-- trigram search with pg_trgm
SELECT * FROM users WHERE email ILIKE &#x27;%example%&#x27;;</code></pre>
</td>
<td valign="top" width="50%">
<p>Примеры:</p>
<pre><code class="language-sql">-- array containment
SELECT * FROM posts WHERE tags @&gt; ARRAY[&#x27;java&#x27;];

-- JSONB containment
SELECT * FROM events WHERE payload @&gt; &#x27;{&quot;type&quot;: &quot;ORDER_CREATED&quot;}&#x27;;

-- trigram search with pg_trgm
SELECT * FROM users WHERE email ILIKE &#x27;%example%&#x27;;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Before adding a GIN index, check whether the data should really be stored as JSON/array or modeled relationally. A GIN index can make flexible queries fast, but it can also hide a weak schema design.</p>
</td>
<td valign="top" width="50%">
<p>Перед добавлением GIN индекса нужно понять, должны ли данные действительно храниться как JSON/array или лучше смоделировать их relationally. GIN может ускорить гибкие запросы, но иногда он скрывает слабое schema design решение.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">

<tr>
<th colspan="2" align="left">Question</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Why can LIKE &#x27;abc%&#x27; use an index, but LIKE &#x27;%abc&#x27; usually cannot?</p>
</td>
<td valign="top" width="50%">
<p>Почему LIKE &#x27;abc%&#x27; может использовать индекс, а LIKE &#x27;%abc&#x27; обычно не может?</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>LIKE &#x27;abc%&#x27;</code> has a fixed prefix, so a B-tree index can treat it like a range of values starting with <code>abc</code>. <code>LIKE &#x27;%abc&#x27;</code> has a leading wildcard, so there is no fixed starting point in the B-tree.</p>
</td>
<td valign="top" width="50%">
<p><code>LIKE &#x27;abc%&#x27;</code> имеет фиксированный prefix, поэтому B-tree индекс может рассматривать это как диапазон значений, начинающихся с <code>abc</code>. <code>LIKE &#x27;%abc&#x27;</code> начинается с wildcard, поэтому у B-tree нет фиксированной точки старта.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A B-tree is ordered from left to right. Prefix search can map to a contiguous range: from <code>abc</code> to values before the next prefix. Contains/suffix search does not map to a contiguous B-tree range because the beginning of the string is unknown.</p>
</td>
<td valign="top" width="50%">
<p>B-tree упорядочен слева направо. Prefix search можно превратить в contiguous range: от <code>abc</code> до значений перед следующим prefix. Contains/suffix search не превращается в contiguous B-tree range, потому что начало строки неизвестно.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For contains search, PostgreSQL commonly uses <code>pg_trgm</code> with GIN or GiST:</p>
<pre><code class="language-sql">CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_users_email_trgm
ON users USING gin (email gin_trgm_ops);

SELECT *
FROM users
WHERE email ILIKE &#x27;%example%&#x27;;</code></pre>
</td>
<td valign="top" width="50%">
<p>Для contains search в PostgreSQL часто используют <code>pg_trgm</code> с GIN или GiST:</p>
<pre><code class="language-sql">CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_users_email_trgm
ON users USING gin (email gin_trgm_ops);

SELECT *
FROM users
WHERE email ILIKE &#x27;%example%&#x27;;</code></pre>

</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">
<p>Для API search endpoints нужно осознанно выбирать тип поиска: exact lookup, prefix autocomplete, substring search, full-text search и fuzzy search требуют разных индексов, а иногда и разных систем.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Collation can affect whether a normal B-tree helps prefix <code>LIKE</code>; pattern operator classes may be needed.</li>
<li><code>ILIKE</code> and case-insensitive search may require expression indexes or trigram indexes.</li>
<li>Trigram indexes can be large and write-expensive.</li>
<li>For real full-text search, use full-text search features rather than many <code>ILIKE</code> filters.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Collation может влиять на то, помогает ли обычный B-tree для prefix <code>LIKE</code>; могут понадобиться pattern operator classes.</li>
<li><code>ILIKE</code> и case-insensitive search могут требовать expression indexes или trigram indexes.</li>
<li>Trigram indexes могут быть большими и дорогими на запись.</li>
<li>Для настоящего full-text search лучше использовать full-text search features, а не много <code>ILIKE</code> фильтров.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
