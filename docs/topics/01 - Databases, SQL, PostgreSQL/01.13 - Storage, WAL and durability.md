<td valign="top" width="50%">
<p>WAL, or Write-Ahead Log, is PostgreSQL’s append-only log of changes written before data pages are considered durable.</p>

<td valign="top" width="50%">
<p>WAL, или Write-Ahead Log, — append-only журнал изменений PostgreSQL, который пишется до того, как data pages считаются durable.</p>

<td valign="top" width="50%">
<p>Главная идея: сначала записать изменение в WAL; data pages можно flush-ить позже. После crash PostgreSQL replay-ит WAL, чтобы восстановить consistent state.</p>

<tr>
<th colspan="2" align="left">Deep dive</th>

<p>WAL лежит в основе crash recovery, durability, replication, point-in-time recovery и write performance.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>

</td>
<td valign="top" width="50%">
<p>Для Java backend систем WAL объясняет, почему heavy writes, много indexes, large rows, bulk updates и full-page writes влияют на disk I/O и replication lag.</p>

</tr>
<tr>

<td valign="top" width="50%">

<summary><strong>DB-WAL-002. Why does PostgreSQL use Write-Ahead Logging?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Question</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Why does PostgreSQL use Write-Ahead Logging?</p>
</td>
<td valign="top" width="50%">
<p>Зачем PostgreSQL использует Write-Ahead Logging?</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>PostgreSQL uses WAL to make commits durable without flushing every changed data page immediately.</p>
</td>
<td valign="top" width="50%">
<p>PostgreSQL использует WAL, чтобы делать commits durable без немедленного flush каждой changed data page.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Sequentially writing WAL is usually cheaper than random writes to many table and index pages. Data pages can be written later by background writers and checkpoints.</p>
</td>
<td valign="top" width="50%">
<p>Последовательная запись WAL обычно дешевле random writes во множество table/index pages. Data pages можно записать позже background writers и checkpoints.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>During recovery, PostgreSQL starts from a checkpoint and replays WAL records to redo committed changes that were not fully flushed to data files.</p>
</td>
<td valign="top" width="50%">
<p>Во время recovery PostgreSQL стартует с checkpoint и replay-ит WAL records, чтобы redo committed changes, которые не были полностью flushed в data files.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>WAL is a performance and durability trade-off surface. Monitor WAL generation rate, checkpoint frequency, disk throughput, and replication lag.</p>
</td>
<td valign="top" width="50%">
<p>WAL — поверхность trade-off между performance и durability. Мониторь WAL generation rate, checkpoint frequency, disk throughput и replication lag.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>WAL reduces random data-page fsync pressure, but writes are not free.</li><li>Unlogged tables have different durability trade-offs.</li><li>Bulk operations can generate huge WAL.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>WAL снижает random data-page fsync pressure, но writes не бесплатны.</li><li>Unlogged tables имеют другой durability trade-off.</li><li>Bulk operations могут генерировать огромный WAL.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why write ahead?
A: WAL must be durable before related data-page changes are considered safe.</p>
</td>
<td valign="top" width="50%">
<p>Q: Почему write-ahead?
A: WAL должен быть durable до того, как related data-page changes считаются безопасными.</p>
</td>
</tr>
</tbody>
</table>

<summary><strong>DB-WAL-003. How does WAL help with crash recovery?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Question</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>How does WAL help with crash recovery?</p>
</td>
<td valign="top" width="50%">
<p>Как WAL помогает с crash recovery?</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>After a crash, PostgreSQL replays WAL records from the last checkpoint to restore committed changes.</p>
</td>
<td valign="top" width="50%">
<p>После crash PostgreSQL replay-ит WAL records от последнего checkpoint, чтобы восстановить committed changes.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>At commit, required WAL is made durable according to settings. The actual heap/index pages may still be dirty in memory and flushed later.</p>
</td>
<td valign="top" width="50%">
<p>При commit нужный WAL становится durable согласно settings. Реальные heap/index pages могут всё ещё быть dirty in memory и flush-иться позже.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Recovery uses WAL as redo information. It does not rerun application code; it re-applies low-level database changes.</p>
</td>
<td valign="top" width="50%">
<p>Recovery использует WAL как redo information. Он не запускает application code заново; он re-applies low-level database changes.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Checkpoint tuning affects recovery time. Longer checkpoint intervals can smooth write load but increase WAL replay time after crash.</p>
</td>
<td valign="top" width="50%">
<p>Checkpoint tuning влияет на recovery time. Более длинные intervals могут сгладить write load, но увеличить WAL replay time после crash.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>WAL replay is redo, not business replay.</li><li>Durability depends on <code>fsync</code> and <code>synchronous_commit</code>.</li><li>Replication also consumes WAL.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>WAL replay — redo, а не business replay.</li><li>Durability зависит от <code>fsync</code> и <code>synchronous_commit</code>.</li><li>Replication тоже потребляет WAL.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does PostgreSQL replay after crash?
A: WAL records since the recovery checkpoint.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что PostgreSQL replay-ит после crash?
A: WAL records с recovery checkpoint.</p>
</td>
</tr>
</tbody>
</table>

<summary><strong>DB-WAL-004. What is a checkpoint?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Question</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>What is a checkpoint?</p>
</td>
<td valign="top" width="50%">
<p>Что такое checkpoint?</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A checkpoint is a point where PostgreSQL ensures dirty data pages up to a WAL position are written to disk.</p>
</td>
<td valign="top" width="50%">
<p>Checkpoint — момент, когда PostgreSQL гарантирует, что dirty data pages до WAL position записаны на диск.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Checkpoints limit crash recovery work: after a checkpoint, PostgreSQL normally does not need to replay older WAL for crash recovery.</p>
</td>
<td valign="top" width="50%">
<p>Checkpoints ограничивают работу crash recovery: после checkpoint PostgreSQL обычно не нужно replay-ить более старый WAL для crash recovery.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>During a checkpoint, many dirty pages may be written. PostgreSQL spreads this work, but it can still create I/O pressure.</p>
</td>
<td valign="top" width="50%">
<p>Во время checkpoint могут писаться многие dirty pages. PostgreSQL растягивает эту работу, но она всё равно может создавать I/O pressure.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Frequent checkpoint warnings, write latency spikes, or high WAL churn indicate checkpoint/WAL tuning should be reviewed.</p>
</td>
<td valign="top" width="50%">
<p>Частые checkpoint warnings, write latency spikes или высокий WAL churn говорят, что нужно проверить checkpoint/WAL tuning.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Checkpoint is not transaction commit.</li><li>Too-frequent checkpoints can hurt latency.</li><li>Too-infrequent checkpoints can increase recovery time.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>Checkpoint — не transaction commit.</li><li>Слишком частые checkpoints могут вредить latency.</li><li>Слишком редкие checkpoints могут увеличить recovery time.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does a checkpoint reduce?
A: WAL replay needed during crash recovery.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что уменьшает checkpoint?
A: WAL replay, необходимый при crash recovery.</p>
</td>
</tr>
