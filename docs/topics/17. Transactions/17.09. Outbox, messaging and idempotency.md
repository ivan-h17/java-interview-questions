# Outbox, messaging and idempotency

---

<a id="tx-outbox-001"></a>

<details>
<summary><strong>TX-OUTBOX-001. What is the Transactional Outbox pattern?</strong></summary>

#### Short answer

Transactional Outbox stores messages in the database in the same transaction as business changes, then publishes them later.

#### Interview answer

Instead of writing business data and directly publishing to Kafka in the same code path, the service writes an outbox row in the same local transaction. A separate relay reads outbox rows and publishes them.

#### Deep dive

The pattern avoids the dual-write problem between database and broker. It does not eliminate duplicate delivery, so consumers still need idempotency.

#### Production angle

Use it for integration events after state changes such as order created, payment captured, or inventory reserved.

#### Traps / caveats

- The relay can publish the same message more than once.
- Outbox table growth and lag must be monitored.
- Event schema evolution still matters.

#### Optional Anki

Q: What problem does Outbox solve?
A: Reliable publishing of messages tied to a local database commit.

</details>

<a id="tx-outbox-002"></a>

<details>
<summary><strong>TX-OUTBOX-002. Why is writing to a database and publishing to Kafka not atomic by default?</strong></summary>

#### Short answer

The database and Kafka are separate systems with separate commit mechanisms.

#### Interview answer

If the database commit succeeds and Kafka publish fails, the event is lost. If Kafka publish succeeds and the database rolls back, consumers see an event for state that does not exist.

#### Deep dive

This is the dual-write problem. A local database transaction cannot automatically include the broker unless a distributed transaction protocol is used, which is usually avoided.

#### Production angle

The bug appears as missing events, ghost events, inconsistent read models, and stuck workflows.

#### Traps / caveats

- Publishing "right after commit" still has a crash window.
- Kafka producer success does not prove DB commit.
- Retrying publish can create duplicates.

#### Optional Anki

Q: What is the dual-write problem?
A: Updating two systems without one atomic commit can leave them inconsistent.

</details>

<a id="tx-outbox-003"></a>

<details>
<summary><strong>TX-OUTBOX-003. How does an outbox table participate in the same local transaction as business data?</strong></summary>

#### Short answer

The service inserts the business rows and the outbox row before committing the same database transaction.

#### Interview answer

For order creation, the transaction writes the order and an `order_created` outbox record together. If the transaction rolls back, both disappear. If it commits, the relay can publish the event later.

#### Deep dive

The outbox row should include event ID, aggregate ID, type, payload, timestamps, status, and retry metadata.

#### Production angle

This gives a durable record of what needs to be published and makes event publication recoverable after process crashes.

#### Traps / caveats

- The outbox write must be in the same transaction as business data.
- Do not publish from inside the transaction and assume the outbox is only backup.
- Event IDs should be stable for deduplication.

#### Optional Anki

Q: Why must outbox and business data share a transaction?
A: So commit or rollback applies to both the state change and the event record.

</details>

<a id="tx-outbox-004"></a>

<details>
<summary><strong>🧠 TX-OUTBOX-004. What are the trade-offs between polling publisher and CDC-based outbox publishing?</strong></summary>

#### Short answer

Polling is simpler; CDC can be lower-latency and less intrusive but adds infrastructure complexity.

#### Interview answer

A polling publisher queries the outbox table for unpublished rows. It is easy to understand but adds database load and polling delay. CDC reads database changes from the log and publishes based on those changes, often with better scalability but more moving parts.

#### Deep dive

Polling needs locking/claiming, pagination, retries, and cleanup. CDC needs connector reliability, schema handling, offsets, and operational expertise.

#### Production angle

Start simple unless volume or latency requires CDC. Monitor lag either way.

#### Traps / caveats

- Polling without proper claiming can duplicate work.
- CDC can still duplicate or reorder within practical boundaries.
- Neither removes consumer idempotency requirements.

#### Optional Anki

Q: What is the main trade-off of CDC outbox?
A: Better scalability/latency potential at the cost of more infrastructure complexity.

</details>

<a id="tx-outbox-005"></a>

<details>
<summary><strong>TX-OUTBOX-005. Why does Transactional Outbox still require idempotent consumers?</strong></summary>

#### Short answer

Outbox guarantees durable intent to publish, not exactly-once consumption.

#### Interview answer

The relay can crash after publishing but before marking the outbox row sent. On restart it may publish the same event again. Consumers must handle duplicates safely.

#### Deep dive

At-least-once delivery is usually the practical guarantee. Idempotent consumers use event IDs, processed-message tables, unique constraints, or state checks.

#### Production angle

Without idempotent consumers, duplicate events can double-charge, double-send email, or apply workflow transitions twice.

#### Traps / caveats

- Broker exactly-once features have scope limits.
- Deduplication must be persisted.
- Idempotency should be tested under retries.

#### Optional Anki

Q: Why can Outbox publish duplicates?
A: The relay may publish and crash before recording success.

</details>

<a id="tx-outbox-006"></a>

<details>
<summary><strong>TX-OUTBOX-006. How would you implement an idempotent consumer with a `processed_messages` table?</strong></summary>

#### Short answer

Store each processed message ID under a unique constraint in the same transaction as the consumer's side effects.

#### Interview answer

When a message arrives, the consumer tries to insert its message ID into `processed_messages`. If the insert succeeds, it performs the business update and commits. If the unique constraint fails, the message was already handled and can be acknowledged.

#### Deep dive

The dedup record and business update must be atomic. Otherwise the consumer can record processed without applying the change or apply the change without recording processed.

#### Production angle

This pattern is common for payments, inventory events, read model updates, and integration handlers.

#### Traps / caveats

- Choose the dedup key scope carefully.
- Cleanup must not remove records too early.
- Handler code must still validate state transitions.

#### Optional Anki

Q: Where should a processed message record be written?
A: In the same transaction as the consumer's business update.

</details>

<a id="tx-outbox-007"></a>

<details>
<summary><strong>TX-OUTBOX-007. How would you implement idempotency keys for HTTP commands?</strong></summary>

#### Short answer

Require a client-provided key and store it transactionally with the command result.

#### Interview answer

For a create-order API, store `(client, operation, idempotency_key)` under a unique constraint. If the key is new, process the command and save the response or resulting resource ID. If the same key appears again, return the stored result.

#### Deep dive

The idempotency record must be written in the same transaction as the business change. Otherwise retries can still duplicate work.

#### Production angle

This handles client retries after network timeouts, gateway retries, mobile retries, and user double-clicks.

#### Traps / caveats

- Do not reuse keys across different command payloads.
- Decide expiration carefully.
- Store enough result data to make retries deterministic.

#### Optional Anki

Q: What protects an HTTP idempotency key from races?
A: A unique constraint and transactional storage with the business result.

</details>

<a id="tx-outbox-008"></a>

<details>
<summary><strong>🧠 TX-OUTBOX-008. What is the Inbox pattern, and how does it differ from Outbox?</strong></summary>

#### Short answer

Outbox records messages to send; Inbox records messages received or to be processed.

#### Interview answer

An Outbox table belongs to the producer and makes publishing reliable. An Inbox table belongs to the consumer and makes receiving or processing idempotent and recoverable.

#### Deep dive

Inbox can store incoming event IDs, payloads, status, retries, and processing errors. It is useful when message handling must be durable and replayable.

#### Production angle

For critical consumers, Inbox gives visibility into stuck or failed processing instead of relying only on broker offsets.

#### Traps / caveats

- Inbox is not needed for every simple consumer.
- It still needs cleanup and monitoring.
- It does not remove the need for valid state transitions.

#### Optional Anki

Q: What is the difference between Outbox and Inbox?
A: Outbox makes sending reliable; Inbox makes receiving/processing reliable.

</details>

<a id="tx-outbox-009"></a>

<details>
<summary><strong>TX-OUTBOX-009. What ordering guarantees can and cannot be achieved with Outbox?</strong></summary>

#### Short answer

Outbox can preserve useful ordering per aggregate, but global ordering is usually unrealistic.

#### Interview answer

If events for one aggregate are written with a sequence number and published by key, consumers can process them in order per aggregate. Across all aggregates or services, global ordering is expensive and rarely needed.

#### Deep dive

Ordering depends on database ordering, relay behavior, broker partitioning, retries, and consumer concurrency.

#### Production angle

Design consumers to handle duplicate, late, and possibly out-of-order events unless strong per-key ordering is explicitly guaranteed.

#### Traps / caveats

- Timestamp order is not always reliable.
- Retried failed events can arrive late.
- Kafka ordering is per partition, not global.

#### Optional Anki

Q: What ordering is usually practical?
A: Per-aggregate or per-key ordering, not global ordering.

</details>

<a id="tx-outbox-010"></a>

<details>
<summary><strong>TX-OUTBOX-010. How would you handle failed outbox publishing and monitor outbox lag?</strong></summary>

#### Short answer

Retry with status tracking and monitor the age/count of unpublished rows.

#### Interview answer

The relay should mark attempts, store errors, use retry/backoff, and eventually dead-letter or alert on stuck rows. Lag is measured by oldest unpublished event age, backlog size, publish rate, and error rate.

#### Deep dive

Publishing should be idempotent from the consumer perspective because retries can duplicate events.

#### Production angle

Outbox lag means other services may see stale workflow state. It should be part of service health and alerting.

#### Traps / caveats

- Do not delete failed rows without investigation.
- Avoid one poison event blocking all later events.
- Cleanup must not race with publishing.

#### Optional Anki

Q: What is a key outbox lag metric?
A: Age of the oldest unpublished outbox row.

</details>

<a id="tx-outbox-011"></a>

<details>
<summary><strong>TX-OUTBOX-011. How would you design an event so duplicate delivery is safe?</strong></summary>

#### Short answer

Give it a stable ID, clear aggregate identity, version or sequence, and idempotent semantics.

#### Interview answer

The event should include event ID, aggregate ID, event type, schema version, occurred time, and enough data for consumers to validate state. Consumers should be able to ignore duplicates based on the stable event ID.

#### Deep dive

Events that say "set status to SHIPPED" are often easier to make idempotent than "increment counter" events.

#### Production angle

Good event design reduces duplicate effects, schema migration pain, and debugging time during incidents.

#### Traps / caveats

- Do not generate a new event ID on every retry.
- Include correlation IDs for tracing.
- Avoid leaking internal entity structure unnecessarily.

#### Optional Anki

Q: What makes an event duplicate-safe?
A: Stable identity plus consumer-side deduplication and idempotent semantics.

</details>

<a id="tx-outbox-012"></a>

<details>
<summary><strong>TX-OUTBOX-012. Why does Kafka exactly-once processing not automatically make database writes exactly-once?</strong></summary>

#### Short answer

Kafka's exactly-once guarantees apply within Kafka transaction boundaries, not automatically to your database transaction.

#### Interview answer

Kafka can coordinate producer writes and offsets in certain scenarios. But if a consumer writes to a database and also commits Kafka offsets, those are separate systems unless explicitly coordinated.

#### Deep dive

The database can commit and the Kafka offset commit can fail, causing reprocessing. Or the offset can be committed before a database write is durable if code is wrong.

#### Production angle

Use idempotent consumers, processed message tables, and transactional database writes for reliable handling.

#### Traps / caveats

- "Exactly once" has a scoped meaning.
- Database side effects still need idempotency.
- Offset handling must match DB commit semantics.

#### Optional Anki

Q: Does Kafka exactly-once make DB writes exactly-once?
A: No. Database writes still need their own idempotency and transaction design.

</details>

<a id="tx-outbox-013"></a>

<details>
<summary><strong>TX-OUTBOX-013. Why is a Kafka producer transaction not the same as a database transaction?</strong></summary>

#### Short answer

They commit different resources.

#### Interview answer

A Kafka transaction can atomically publish Kafka records and commit offsets within Kafka. A database transaction atomically changes database state. They are not the same atomic boundary unless a distributed transaction coordinates them.

#### Deep dive

This is why writing business data and publishing a Kafka event still needs Outbox or another consistency pattern.

#### Production angle

Confusing the two creates lost or ghost events during crashes and rollbacks.

#### Traps / caveats

- Kafka transactions do not roll back database writes.
- Database rollback does not undo already published Kafka records.
- Use Outbox when event publication must reflect DB commit.

#### Optional Anki

Q: What does a Kafka transaction not include by default?
A: Your relational database transaction.

</details>

<a id="tx-outbox-014"></a>

<details>
<summary><strong>TX-OUTBOX-014. How should message listener offset commits relate to database transaction commits?</strong></summary>

#### Short answer

Commit the database work before acknowledging or committing the message offset.

#### Interview answer

If the consumer commits the offset before the database transaction commits, a crash can lose the message. If the DB commits and offset commit fails, the message may be redelivered, so the database update must be idempotent.

#### Deep dive

This usually gives at-least-once processing with idempotent side effects. The consumer should treat reprocessing as normal.

#### Production angle

For critical handlers, store processed message IDs and business changes in one database transaction before acknowledging the message.

#### Traps / caveats

- Acknowledging too early loses messages.
- Acknowledging too late creates duplicates.
- Duplicates are safer than loss only if consumers are idempotent.

#### Optional Anki

Q: What should happen before committing a consumed message offset?
A: The database transaction for the message's side effects should commit.

</details>
