# Propagation, rollback and transaction attributes

---

<a id="tx-prop-001"></a>

<details>
<summary><strong>TX-PROP-001. What transaction propagation modes does Spring support, and what is the safest default?</strong></summary>

#### Short answer

Spring supports several propagation modes; `REQUIRED` is the normal safe default for service methods.

#### Interview answer

`REQUIRED` joins an existing transaction or starts a new one. Other modes include `REQUIRES_NEW`, `NESTED`, `SUPPORTS`, `NOT_SUPPORTED`, `MANDATORY`, and `NEVER`. Most service methods should use `REQUIRED` unless there is a clear reason.

#### Deep dive

Propagation controls how method calls interact with an existing transaction in the same Spring call chain. It does not propagate across HTTP, messaging, or arbitrary threads.

#### Production angle

Changing propagation changes correctness, connection usage, rollback behavior, and observability.

#### Traps / caveats

- Do not use `REQUIRES_NEW` everywhere.
- `NESTED` depends on savepoint support.
- Propagation works only when Spring intercepts the call.

#### Optional Anki

Q: What is the usual default propagation?
A: `Propagation.REQUIRED`.

</details>

<a id="tx-prop-002"></a>

<details>
<summary><strong>TX-PROP-002. How does `Propagation.REQUIRES_NEW` work, and why can it exhaust the connection pool?</strong></summary>

#### Short answer

`REQUIRES_NEW` suspends the current transaction and starts a separate one, usually requiring another connection.

#### Interview answer

If an outer transaction is active, Spring suspends it and opens an independent transaction for the inner method. Under load, each request may hold the outer connection while asking for another one, which can exhaust the pool.

#### Deep dive

The inner transaction commits or rolls back independently. That is useful for audit records or outbox-like side work only when independence is truly intended.

#### Production angle

A small pool can deadlock at the application level if many threads hold outer transactions and wait for inner connections.

#### Traps / caveats

- It does not make code safer by default.
- Inner commit can persist even if the outer transaction rolls back.
- Pool sizing must account for nested connection demand.

#### Optional Anki

Q: Why can `REQUIRES_NEW` exhaust a pool?
A: It may need a second connection while the outer transaction still holds one.

</details>

<a id="tx-prop-003"></a>

<details>
<summary><strong>TX-PROP-003. Why do propagation settings not cross HTTP, microservice, or async boundaries?</strong></summary>

#### Short answer

Spring propagation works inside local Spring transaction interception, not across remote calls or arbitrary execution boundaries.

#### Interview answer

Propagation is about how a Spring method call behaves when a transaction is already active in the same application context and execution flow. HTTP calls, Kafka messages, and other services have their own processes and resources.

#### Deep dive

Cross-service consistency requires explicit patterns such as Saga, Outbox, idempotency, and compensation, not Spring propagation.

#### Production angle

Assuming propagation crosses services creates partial commits and inconsistent distributed state.

#### Traps / caveats

- `@Transactional` does not travel in an HTTP header.
- Async execution usually loses thread-bound context.
- Remote rollback is a business compensation problem, not a local transaction rollback.

#### Optional Anki

Q: Does Spring propagation cross microservice calls?
A: No. It applies to local intercepted method calls.

</details>

<a id="tx-prop-004"></a>

<details>
<summary><strong>TX-PROP-004. How would you choose propagation for order creation, audit logging, and outbox writes?</strong></summary>

#### Short answer

Use one main transaction for order state and outbox; use separate propagation only when independent commit is intentional.

#### Interview answer

Order creation and its outbox event should usually be in the same local transaction. Audit logging may be in the same transaction if it should roll back with the order, or `REQUIRES_NEW` if audit must persist even when the order fails.

#### Deep dive

The choice depends on business semantics. If the inner operation should survive outer rollback, a separate transaction can be valid. If atomicity is required, keep it in the same transaction.

#### Production angle

Outbox rows must commit atomically with business data, otherwise events can be lost or published for rolled-back changes.

#### Traps / caveats

- `REQUIRES_NEW` for audit can stress the pool.
- Audit that survives failed operations may expose sensitive or noisy data.
- Notifications should usually run after commit, not inside the transaction.

#### Optional Anki

Q: What propagation should an outbox write usually use?
A: The same transaction as the business data.

</details>

<a id="tx-prop-005"></a>

<details>
<summary><strong>TX-PROP-005. Why can an inner `REQUIRED` method cause `UnexpectedRollbackException` in the outer method?</strong></summary>

#### Short answer

The inner method joins the outer transaction and can mark the shared transaction rollback-only.

#### Interview answer

With `REQUIRED`, inner and outer methods participate in the same transaction. If the inner method fails and Spring marks the transaction rollback-only, the outer method may catch the exception and continue, but commit later fails because the transaction cannot be committed.

#### Deep dive

`UnexpectedRollbackException` is Spring's way of telling the caller that the apparent successful return did not commit because the transaction was already doomed.

#### Production angle

This often appears when code catches exceptions inside transactional flows and returns success.

#### Traps / caveats

- Catching an exception does not clear rollback-only state.
- Logging and swallowing exceptions can create misleading API responses.
- Use separate transactions only when independent commit is intended.

#### Optional Anki

Q: Why does `UnexpectedRollbackException` happen?
A: A joined transaction was marked rollback-only, but the outer code still tried to commit.

</details>

<a id="tx-prop-006"></a>

<details>
<summary><strong>TX-PROP-006. Which exceptions trigger rollback by default in Spring, and how do checked or caught exceptions change that?</strong></summary>

#### Short answer

By default, Spring rolls back on unchecked exceptions and `Error`, but not checked exceptions.

#### Interview answer

Runtime exceptions and errors trigger rollback by default. Checked exceptions do not unless configured with `rollbackFor`. If an exception is caught and not rethrown, Spring sees a normal return unless the transaction is manually marked rollback-only.

#### Deep dive

Rollback rules are evaluated by exception type and inheritance. Custom business exceptions should be designed intentionally: some should roll back, some may represent valid business outcomes.

#### Production angle

Wrong rollback rules can commit failed business operations or roll back expected validation outcomes.

#### Traps / caveats

- A caught exception does not automatically roll back.
- `rollbackFor = Exception.class` can be too broad.
- Exception translation can change checked SQL exceptions into unchecked Spring exceptions.

#### Optional Anki

Q: What exceptions trigger rollback by default in Spring?
A: Runtime exceptions and `Error`, not checked exceptions.

</details>

<a id="tx-prop-007"></a>

<details>
<summary><strong>TX-PROP-007. When would you use `noRollbackFor` for business exceptions?</strong></summary>

#### Short answer

Use it when an exception represents an expected business outcome and the current transaction should still commit.

#### Interview answer

For example, a service might persist an audit or state transition and then throw a domain exception to return a specific response. If that exception should not roll back the persisted state, `noRollbackFor` can express that.

#### Deep dive

This is less common than `rollbackFor`. It should be used carefully because it makes exception handling and commit behavior less obvious.

#### Production angle

Use clear domain naming and tests so maintainers know which failures commit and which roll back.

#### Traps / caveats

- Do not use it to hide real technical failures.
- Be careful with exception inheritance.
- API error response does not always mean database rollback.

#### Optional Anki

Q: What does `noRollbackFor` do?
A: It tells Spring not to roll back for selected exception types.

</details>

<a id="tx-prop-008"></a>

<details>
<summary><strong>TX-PROP-008. How is `@Transactional` timeout different from statement timeout, HTTP timeout, and connection pool timeout?</strong></summary>

#### Short answer

They limit different layers of work.

#### Interview answer

`@Transactional` timeout limits the transaction from Spring's perspective. Statement timeout limits a SQL statement. HTTP timeout limits request or client waiting time. Connection pool timeout limits waiting to borrow a connection.

#### Deep dive

These timeouts can interact. An HTTP request may time out while the transaction keeps running, or a statement may time out and mark the transaction for rollback.

#### Production angle

Set timeouts deliberately at every layer and make cancellation behavior observable.

#### Traps / caveats

- Bigger timeouts are not always safer.
- A timed-out client may retry while the original transaction is still running.
- Timeout exceptions can leave the transaction rollback-only.

#### Optional Anki

Q: What does connection pool timeout mean?
A: The application waited too long to borrow a database connection.

</details>

<a id="tx-prop-009"></a>

<details>
<summary><strong>TX-PROP-009. Why can isolation, timeout, and read-only attributes be ignored when a method joins an existing transaction?</strong></summary>

#### Short answer

When a method joins an existing transaction, the physical transaction has already started.

#### Interview answer

With `REQUIRED`, an inner method joins the outer transaction. The database connection and transaction settings may already be established, so the inner method cannot freely change isolation or timeout for that physical transaction.

#### Deep dive

This is why the outermost transaction boundary is important. Inner annotations may document intent, but they may not control the actual transaction if joining occurs.

#### Production angle

Unexpected attribute inheritance can cause read-only routing mistakes, missing timeouts, or isolation weaker than expected.

#### Traps / caveats

- Inner `readOnly = true` may not matter inside an outer write transaction.
- Stronger isolation should be set at the boundary that starts the transaction.
- Tests should cover actual call chains.

#### Optional Anki

Q: Why can inner transaction attributes be ignored?
A: The method may join an already-started transaction whose settings are fixed.

</details>

<a id="tx-prop-010"></a>

<details>
<summary><strong>TX-PROP-010. What does `readOnly = true` mean in Spring, and what does it not guarantee?</strong></summary>

#### Short answer

It is a hint/attribute for read-oriented work; it is not a security feature or universal write blocker.

#### Interview answer

Spring may pass read-only intent to the transaction manager and ORM. Hibernate may adjust flush behavior. Some systems use it for read replica routing. But it does not guarantee that no write can happen in every database or stack.

#### Deep dive

The effect depends on transaction manager, database, driver, ORM, and routing configuration.

#### Production angle

Use it for clarity and optimization, but rely on permissions, constraints, and tests for correctness.

#### Traps / caveats

- It may be ignored when joining an existing transaction.
- Entity changes can still exist in memory.
- Replica routing can introduce stale reads.

#### Optional Anki

Q: Is `readOnly = true` a write-prevention security feature?
A: No. It is mainly a read-intent hint and optimization attribute.

</details>

<a id="tx-prop-011"></a>

<details>
<summary><strong>TX-PROP-011. What are the risks of routing read-only transactions to replicas?</strong></summary>

#### Short answer

Replica reads can be stale and can break user expectations after writes.

#### Interview answer

If `readOnly = true` causes routing to a replica, the transaction may not see recently committed primary data. This can break read-your-writes, authorization checks, or workflow decisions.

#### Deep dive

Replica lag varies under load. Routing should account for lag, user session consistency, critical reads, and fallbacks to primary.

#### Production angle

After writes, route critical follow-up reads to primary or use lag-aware routing. Expose pending states when eventual consistency is acceptable.

#### Traps / caveats

- Stale reads can look like data loss to users.
- Tests with one database do not catch this.
- Do not run critical command validation against stale replicas.

#### Optional Anki

Q: What is the main risk of read replica routing?
A: Stale reads due to replication lag.

</details>
