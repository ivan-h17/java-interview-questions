# Production troubleshooting and anti-patterns

---

<a id="tx-prod-001"></a>

<details>
<summary><strong>TX-PROD-001. How would you investigate many `idle in transaction` sessions?</strong></summary>

#### Short answer

Find the sessions, their age, last query, application source, and code path holding the transaction open.

#### Interview answer

I would inspect database activity views for `idle in transaction`, transaction start time, query text, application name, user, and client. Then correlate with application logs, traces, pool metrics, and recent deployments.

#### Deep dive

Common causes include missing commit/rollback in manual JDBC, slow external calls inside transactions, forgotten open sessions, or request flows that keep transactions across rendering.

#### Production angle

Mitigate by terminating extreme offenders if safe, then fix transaction boundaries and add timeouts.

#### Traps / caveats

- Killing sessions can roll back work.
- The last query may not be the root cause.
- Read-only idle transactions can still harm MVCC cleanup.

#### Optional Anki

Q: What is the first thing to check for `idle in transaction`?
A: Transaction age, last query, and originating application code path.

</details>

<a id="tx-prod-002"></a>

<details>
<summary><strong>TX-PROD-002. How would you investigate blocked transactions and find the blocking transaction?</strong></summary>

#### Short answer

Inspect database lock wait information and identify blocker sessions.

#### Interview answer

I would look for sessions waiting on locks, identify the blocking PID/session, inspect its transaction age and query, then map it to application logs or traces.

#### Deep dive

Useful information includes lock type, relation, transaction start, query start, wait event, application name, and whether the blocker is idle in transaction.

#### Production angle

After immediate mitigation, fix root causes: missing indexes, inconsistent lock ordering, long transactions, or unsafe migrations.

#### Traps / caveats

- A waiting migration can block later application queries.
- Killing the wrong session can make things worse.
- Blocking is often caused by earlier code, not the query currently waiting.

#### Optional Anki

Q: What do you need for blocked transaction diagnosis?
A: Waiting session, blocking session, lock type, query, transaction age, and application source.

</details>

<a id="tx-prod-003"></a>

<details>
<summary><strong>TX-PROD-003. How would you investigate deadlocks or frequent serialization failures?</strong></summary>

#### Short answer

Collect failing statements, involved rows, transaction order, isolation level, and retry metrics.

#### Interview answer

For deadlocks, inspect database logs and identify inconsistent lock ordering or long lock holding. For serialization failures, check contention hot spots and whether retry logic is working.

#### Deep dive

Deadlocks usually suggest lock order or query-plan issues. Serialization failures can be expected under stronger isolation but should be bounded and retried safely.

#### Production angle

Fixes include consistent ordering, shorter transactions, indexes, reduced contention, and retry with backoff.

#### Traps / caveats

- Retrying is necessary but not always sufficient.
- A spike can indicate a deployment changed access order.
- Logs must include correlation IDs and operation names.

#### Optional Anki

Q: What is the usual fix for recurring deadlocks?
A: Consistent lock ordering, shorter transactions, proper indexes, and bounded retries.

</details>

<a id="tx-prod-004"></a>

<details>
<summary><strong>TX-PROD-004. How would you investigate connection pool exhaustion caused by transactions?</strong></summary>

#### Short answer

Correlate pool metrics with transaction duration, slow queries, lock waits, and thread/request traces.

#### Interview answer

I would inspect active, idle, and pending connection counts, acquisition timeouts, long-running transactions, slow endpoints, and database wait events. Then identify which code path holds connections too long.

#### Deep dive

Pool exhaustion can come from slow SQL, locks, remote calls inside transactions, leaks, `REQUIRES_NEW`, or batch jobs sharing the API pool.

#### Production angle

Mitigate with timeouts, traffic shedding, isolating batch workloads, and fixing transaction boundaries.

#### Traps / caveats

- Increasing pool size can overload the database.
- Thread dumps can show blocked connection acquisition.
- Leak detection helps but does not catch legitimate long holds.

#### Optional Anki

Q: What does pool exhaustion usually indicate?
A: Connections are held too long, leaked, or demand exceeds database capacity.

</details>

<a id="tx-prod-005"></a>

<details>
<summary><strong>TX-PROD-005. How would you investigate `UnexpectedRollbackException` or `@Transactional` not working?</strong></summary>

#### Short answer

Check rollback-only causes, exception handling, proxy interception, and actual call paths.

#### Interview answer

For `UnexpectedRollbackException`, find where the transaction was marked rollback-only, often an inner `REQUIRED` method. For `@Transactional` not working, verify the method is called through a Spring proxy and is not private, final, constructor-called, or self-invoked.

#### Deep dive

Also verify transaction manager selection, multiple data sources, rollback rules, and whether exceptions are caught.

#### Production angle

Add focused logs around transaction boundaries and reproduce with an integration test through real Spring beans.

#### Traps / caveats

- Catching an exception does not clear rollback-only.
- Annotation on a method does nothing if the proxy is bypassed.
- Checked exceptions do not roll back by default.

#### Optional Anki

Q: What are common causes of `@Transactional` not applying?
A: Self-invocation, private/final methods, constructor calls, or not using a Spring proxy.

</details>

<a id="tx-prod-006"></a>

<details>
<summary><strong>🧠 TX-PROD-006. How would you investigate long locks, blocked migrations, or VACUUM not keeping up?</strong></summary>

#### Short answer

Identify long transactions, blockers, lock queues, and cleanup blockers, then map them to application code.

#### Interview answer

I would inspect active transactions, lock waits, transaction age, table activity, and maintenance stats. For migrations, check whether DDL is waiting on application locks. For VACUUM issues, look for old snapshots and long-running transactions.

#### Deep dive

The root cause is often not the maintenance process itself but application transactions that stay open too long.

#### Production angle

Use lock timeouts for migrations, split risky DDL, shorten transactions, and monitor old transaction age.

#### Traps / caveats

- Manual cleanup without fixing long transactions may not help.
- A waiting DDL statement can block new queries behind it.
- Killing a blocker can roll back user work.

#### Optional Anki

Q: What often blocks VACUUM cleanup?
A: Old open transactions or snapshots.

</details>

<a id="tx-prod-007"></a>

<details>
<summary><strong>🧠 TX-PROD-007. How would you investigate slow commits or a high rollback rate?</strong></summary>

#### Short answer

Separate commit latency from query time, then inspect replication, WAL, locks, constraints, and application rollback causes.

#### Interview answer

Slow commits can come from storage, synchronous replication, large transactions, or commit-time constraint checks. High rollback rate can come from validation failures, deadlocks, serialization failures, timeouts, or application exceptions.

#### Deep dive

Look at database commit metrics, logs, transaction size, retry counters, and exception categories.

#### Production angle

If rollback rate spikes after deployment, check new validation logic, retry policy, SQL changes, and lock contention.

#### Traps / caveats

- Rollback rate is not automatically bad without context.
- Slow commit may be outside application CPU.
- Large transactions make commit and rollback more expensive.

#### Optional Anki

Q: What can cause slow commits?
A: Large transactions, storage/WAL pressure, synchronous replication, locks, or commit-time checks.

</details>

<a id="tx-prod-008"></a>

<details>
<summary><strong>TX-PROD-008. How would you debug a lost update or Read Committed anomaly in production?</strong></summary>

#### Short answer

Reconstruct concurrent operations and check whether the invariant was protected by the database.

#### Interview answer

I would inspect logs, audit rows, timestamps, transaction IDs if available, and update statements. Then I would check whether the code used read-then-write without locks, versions, atomic updates, or constraints.

#### Deep dive

The fix usually involves optimistic locking, `SELECT FOR UPDATE`, conditional updates, unique constraints, or stronger isolation plus retries.

#### Production angle

Add regression tests that reproduce the concurrent interleaving.

#### Traps / caveats

- Application logs may not show database interleaving.
- Read Committed can be correct if invariants are database-enforced.
- Fix the data and the code path.

#### Optional Anki

Q: What is a common fix for lost update?
A: Optimistic locking, row locking, atomic conditional update, or stronger isolation.

</details>

<a id="tx-prod-009"></a>

<details>
<summary><strong>TX-PROD-009. How would you debug a message published before rollback or a commit that succeeded before publishing failed?</strong></summary>

#### Short answer

Treat it as a dual-write failure and verify whether Outbox or equivalent reliability exists.

#### Interview answer

If a message was published before rollback, consumers saw an event for nonexistent state. If commit succeeded before publish failed, the event was lost. I would inspect transaction logs, broker publish logs, outbox records, and consumer effects.

#### Deep dive

The durable fix is usually Transactional Outbox plus idempotent consumers.

#### Production angle

Repair may require publishing a corrective event, replaying from outbox, or reconciling downstream state.

#### Traps / caveats

- Do not fix only by reordering code; crash windows remain.
- Manual replay can duplicate events.
- Consumers must handle duplicate or compensating events.

#### Optional Anki

Q: What pattern fixes DB commit and message publish dual-write?
A: Transactional Outbox.

</details>

<a id="tx-prod-010"></a>

<details>
<summary><strong>TX-PROD-010. How would you debug and drain an outbox backlog?</strong></summary>

#### Short answer

Measure backlog, identify the oldest stuck rows, fix the cause, and resume publishing safely.

#### Interview answer

I would check outbox row count, oldest age, relay errors, broker availability, poison messages, lock contention, and publish throughput. Then I would retry safely or move poison rows aside with an audit trail.

#### Deep dive

Draining should preserve ordering requirements where they matter and avoid overwhelming consumers.

#### Production angle

Outbox backlog means downstream systems are stale. Communicate impact and monitor catch-up rate.

#### Traps / caveats

- Do not delete stuck rows blindly.
- One bad event can block a partition or aggregate stream.
- Catch-up can overload consumers.

#### Optional Anki

Q: What does outbox backlog indicate?
A: Events were committed locally but not yet published downstream.

</details>

<a id="tx-prod-011"></a>

<details>
<summary><strong>TX-PROD-011. How would you debug replica lag affecting read-only transactions?</strong></summary>

#### Short answer

Compare primary and replica lag, routing decisions, and user flows that read after write.

#### Interview answer

I would check whether the stale read came from a replica, measure replication lag, inspect read routing rules, and verify whether the request needed read-your-writes consistency.

#### Deep dive

The fix may be primary routing after writes, lag-aware routing, sticky sessions, or user-visible pending states.

#### Production angle

Replica lag often appears as "created object not found" or stale status after an update.

#### Traps / caveats

- Retrying against the same replica may not help.
- Read-only annotations can trigger replica routing.
- Authorization checks should not rely on stale data.

#### Optional Anki

Q: What symptom often indicates replica lag?
A: A user writes data and immediately cannot read it back.

</details>

<a id="tx-prod-012"></a>

<details>
<summary><strong>TX-PROD-012. How would you debug transaction timeout, lock timeout, and statement timeout issues?</strong></summary>

#### Short answer

Identify which timeout fired, then inspect the corresponding layer.

#### Interview answer

For statement timeout, inspect SQL and query plan. For lock timeout, find blockers and lock order. For transaction timeout, inspect the whole method duration and what happened inside the transaction.

#### Deep dive

The exception type, database logs, application trace, and timing metrics should tell which timeout fired first.

#### Production angle

Fix root causes before increasing limits: slow queries, missing indexes, long transactions, or lock contention.

#### Traps / caveats

- Multiple timeouts can cascade.
- Client timeout does not guarantee server work stopped.
- Retrying after timeout needs idempotency.

#### Optional Anki

Q: What should you identify first in timeout debugging?
A: Which timeout fired and at what layer.

</details>

<a id="tx-prod-013"></a>

<details>
<summary><strong>TX-PROD-013. How would you debug a stuck batch job with a very large transaction?</strong></summary>

#### Short answer

Check transaction age, locks, progress, memory, SQL, and rollback risk.

#### Interview answer

I would inspect whether the job is still making progress, what SQL is running, whether it holds locks, how many rows are affected, and whether rollback would be expensive. Then I would decide whether to let it finish, pause traffic, or cancel safely.

#### Deep dive

The design fix is usually chunking, progress checkpoints, idempotency, and restartability.

#### Production angle

Large transactions can block users, exhaust resources, and create massive rollback or replication lag.

#### Traps / caveats

- Killing it can trigger a long rollback.
- Lack of progress metrics makes decisions risky.
- Future jobs should use smaller commits.

#### Optional Anki

Q: What is the usual redesign for a huge batch transaction?
A: Chunked transactions with progress tracking and restartability.

</details>

<a id="tx-prod-014"></a>

<details>
<summary><strong>TX-PROD-014. How would you correlate application logs, database sessions, and metrics for transaction failures?</strong></summary>

#### Short answer

Use correlation IDs, connection/session metadata, tracing, and consistent operation names.

#### Interview answer

I would include request ID, user/tenant, operation name, transaction-relevant errors, retry count, and database application name. On the database side, I would map sessions to application instances and queries.

#### Deep dive

Observability should connect the business operation to SQL, pool behavior, locks, and broker events.

#### Production angle

Good correlation reduces incident time from guessing to reconstructing the exact failing workflow.

#### Traps / caveats

- Do not log sensitive data.
- Database query text may miss business context.
- Async and outbox flows need propagated correlation IDs.

#### Optional Anki

Q: What makes transaction incidents easier to debug?
A: Correlation IDs connecting application logs, traces, DB sessions, and metrics.

</details>

<a id="tx-prod-015"></a>

<details>
<summary><strong>TX-PROD-015. Why can transaction-per-controller and transaction-per-repository-method both be bad designs?</strong></summary>

#### Short answer

One can be too broad, the other too narrow.

#### Interview answer

Controller-level transactions can include request/response work, serialization, and external calls. Repository-level transactions can split one business operation into several independent commits. Service-level boundaries usually better match use cases.

#### Deep dive

The boundary should protect the business invariant while staying as short as practical.

#### Production angle

Bad boundaries cause partial writes, long connection holds, hidden lazy loading, and confusing rollback behavior.

#### Traps / caveats

- There are exceptions for specialized read services.
- Do not follow layers mechanically.
- Measure transaction duration in real endpoints.

#### Optional Anki

Q: Why can repository-only transactions be too narrow?
A: One business operation may require multiple repository calls to commit atomically.

</details>

<a id="tx-prod-016"></a>

<details>
<summary><strong>TX-PROD-016. Why is treating `readOnly = true` as a security feature a trap?</strong></summary>

#### Short answer

`readOnly = true` is not a reliable permission or write-prevention mechanism.

#### Interview answer

It is mainly a transaction hint. Depending on stack and database, writes may still be possible, especially through other connections or when joining an existing transaction.

#### Deep dive

Security should be enforced with authorization, database permissions where appropriate, and constraints. Read-only transaction attributes are for intent and optimization.

#### Production angle

If a bug or attacker can reach write code, `readOnly = true` should not be your last line of defense.

#### Traps / caveats

- Hibernate in-memory state can still mutate.
- Some databases enforce read-only more strongly than others.
- Joining an existing transaction can change behavior.

#### Optional Anki

Q: Is `readOnly = true` a security boundary?
A: No. It is a transaction hint/attribute, not authorization.

</details>
