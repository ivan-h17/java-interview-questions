# Performance and resource usage

---

<a id="tx-perf-001"></a>

<details>
<summary><strong>TX-PERF-001. How do transactions affect database connection usage?</strong></summary>

#### Short answer

An active transaction usually holds a database connection until commit or rollback.

#### Interview answer

In Spring JDBC/JPA, when a transaction needs database access, a connection is borrowed and associated with the transaction. It is not returned to the pool until the transaction completes.

#### Deep dive

The connection can be held while application code does mapping, calls other methods, waits on locks, or performs external work. That means transaction duration directly affects pool availability.

#### Production angle

Long transactions can cause pending connection requests, request latency, and cascading failures.

#### Traps / caveats

- A larger pool is not always the fix.
- A transaction may acquire the connection lazily, but once acquired it remains held.
- Pool metrics should be correlated with transaction duration.

#### Optional Anki

Q: When is a connection usually returned to the pool?
A: After the transaction commits or rolls back.

</details>

<a id="tx-perf-002"></a>

<details>
<summary><strong>TX-PERF-002. Why can long transactions exhaust a connection pool?</strong></summary>

#### Short answer

They keep connections checked out longer, so fewer connections are available for other requests.

#### Interview answer

If each request holds a connection for 2 seconds instead of 50 milliseconds, the same pool supports far fewer concurrent requests. Waiting threads then pile up, causing timeouts and latency spikes.

#### Deep dive

Long transactions can be caused by slow SQL, lock waits, N+1 queries, remote calls, large batches, or serialization inside the transaction.

#### Production angle

Look at Hikari active/pending connections, request latency, database wait events, and transaction duration percentiles.

#### Traps / caveats

- Increasing pool size can overload the database.
- Connection exhaustion is often a symptom, not the root cause.
- `REQUIRES_NEW` can multiply connection demand.

#### Optional Anki

Q: Why do long transactions hurt pools?
A: They keep connections checked out longer.

</details>

<a id="tx-perf-003"></a>

<details>
<summary><strong>TX-PERF-003. Why should external HTTP calls or Kafka publishing usually not block inside a database transaction?</strong></summary>

#### Short answer

They extend the transaction with slow, unreliable, non-transactional work.

#### Interview answer

While the service waits for HTTP or Kafka, it may hold a database connection, locks, and a persistence context. If the external call succeeds but the DB rolls back, the side effect is inconsistent.

#### Deep dive

For reliable events, use Outbox. For external APIs, move calls outside the transaction where possible and use idempotency or workflow state for ambiguous outcomes.

#### Production angle

This pattern causes pool exhaustion, long locks, duplicate side effects, and hard-to-reason failure cases.

#### Traps / caveats

- "Fast most of the time" is not a safe transaction design.
- Kafka publish success is not database commit success.
- Client timeouts can trigger retries while the transaction is still active.

#### Optional Anki

Q: Why avoid external calls inside transactions?
A: They hold DB resources while doing work the DB transaction cannot roll back.

</details>

<a id="tx-perf-004"></a>

<details>
<summary><strong>TX-PERF-004. How can slow queries and N+1 queries increase transaction duration?</strong></summary>

#### Short answer

They keep the transaction and connection open while extra database work completes.

#### Interview answer

A slow query directly extends the transaction. N+1 turns one logical operation into many round trips. Both increase connection hold time and may hold locks or snapshots longer.

#### Deep dive

Performance issues become correctness and availability issues when they increase contention or pool pressure.

#### Production angle

Use query plans, metrics, SQL logging in lower environments, fetch planning, projections, and indexes to reduce transaction time.

#### Traps / caveats

- Caching may hide N+1 in tests.
- OSIV can move N+1 into serialization.
- Slow reads can still harm MVCC cleanup.

#### Optional Anki

Q: Why is N+1 a transaction problem?
A: It extends the transaction with many extra database round trips.

</details>

<a id="tx-perf-005"></a>

<details>
<summary><strong>TX-PERF-005. What are the trade-offs between one huge transaction and many tiny transactions?</strong></summary>

#### Short answer

Huge transactions are atomic but expensive; tiny transactions reduce resource holding but may lose business atomicity.

#### Interview answer

One huge transaction can hold locks, memory, and rollback data for too long. Many tiny transactions improve resource release but may leave partial progress if later steps fail.

#### Deep dive

The right boundary is the smallest unit that preserves the business invariant. Batch jobs often use chunked transactions plus restartability.

#### Production angle

For imports, prefer chunks with progress tracking and idempotent resume instead of one all-or-nothing transaction over millions of rows.

#### Traps / caveats

- Chunking requires recovery design.
- One huge transaction can make rollback painful.
- Tiny transactions can create visible partial state.

#### Optional Anki

Q: What guides transaction size?
A: The smallest boundary that preserves the business invariant.

</details>

<a id="tx-perf-006"></a>

<details>
<summary><strong>TX-PERF-006. How can locks, foreign keys, constraints, and triggers affect transaction performance?</strong></summary>

#### Short answer

They add correctness checks and side effects that can increase write cost and contention.

#### Interview answer

Locks can make transactions wait. Foreign keys and constraints require validation. Triggers can run additional logic. These features are valuable, but they are part of the transaction's work and latency.

#### Deep dive

Indexes supporting foreign keys and predicates can reduce lock duration and validation cost. Poorly designed triggers can hide expensive work.

#### Production angle

When write latency grows, inspect constraints, triggers, lock waits, missing indexes, and cascading operations.

#### Traps / caveats

- Do not remove constraints just for speed without replacing correctness.
- Trigger behavior may be invisible to application logs.
- Cascading deletes can be much larger than expected.

#### Optional Anki

Q: Why can constraints affect performance?
A: The database must validate them within the transaction.

</details>

<a id="tx-perf-007"></a>

<details>
<summary><strong>TX-PERF-007. How does connection pool max size interact with database `max_connections`?</strong></summary>

#### Short answer

The total possible application connections must fit within what the database can safely handle.

#### Interview answer

If each service instance has a pool of 50 and there are 20 instances, the application can open 1000 connections. That may exceed database limits or overload the database even if each local pool looks reasonable.

#### Deep dive

Pool size should be chosen based on database capacity, query latency, concurrency, and workload type, not just application thread count.

#### Production angle

Too many connections can increase context switching, memory use, lock contention, and recovery time.

#### Traps / caveats

- Virtual threads do not mean unlimited database connections.
- More pool connections can make overload worse.
- Include admin, migration, and background job connections in capacity planning.

#### Optional Anki

Q: Why is per-instance pool size dangerous to tune in isolation?
A: Total connections across all instances may exceed database capacity.

</details>

<a id="tx-perf-008"></a>

<details>
<summary><strong>TX-PERF-008. How do virtual threads change, or not change, database transaction bottlenecks?</strong></summary>

#### Short answer

Virtual threads make blocking cheaper for the JVM, but they do not remove database connection or transaction limits.

#### Interview answer

With virtual threads, the application can handle many blocked tasks with fewer platform threads. But a JDBC transaction still needs a database connection, and the database still has finite CPU, locks, I/O, and connection capacity.

#### Deep dive

Virtual threads can increase concurrency pressure on the database if pool sizes and backpressure are not controlled.

#### Production angle

Keep connection pools bounded, monitor database saturation, and avoid assuming virtual threads make slow transactions harmless.

#### Traps / caveats

- JDBC calls still use database connections.
- More concurrent requests can mean more lock contention.
- Backpressure remains necessary.

#### Optional Anki

Q: Do virtual threads remove DB bottlenecks?
A: No. They reduce JVM thread cost, not database connection or transaction limits.

</details>

<a id="tx-perf-009"></a>

<details>
<summary><strong>TX-PERF-009. What metrics would you monitor for transaction duration, lock waits, and rollback rate?</strong></summary>

#### Short answer

Monitor transaction duration, pool usage, lock waits, deadlocks, rollback counts, retry counts, and slow queries.

#### Interview answer

At the application layer, track request latency, transaction timing, Hikari active/idle/pending connections, and retry metrics. At the database layer, track active transactions, lock waits, deadlocks, slow statements, and rollback/commit rates.

#### Deep dive

Percentiles are more useful than averages because a small number of long transactions can cause major contention.

#### Production angle

Correlate metrics with deployment time, endpoint, tenant, query, and trace ID.

#### Traps / caveats

- A high rollback rate may be normal for validation-heavy flows or bad for retry storms.
- Averages hide tail latency.
- Database metrics need application context.

#### Optional Anki

Q: What pool metric indicates connection pressure?
A: Pending connection acquisition count/time.

</details>

<a id="tx-perf-010"></a>

<details>
<summary><strong>TX-PERF-010. How would you prevent one slow transaction from degrading the whole service?</strong></summary>

#### Short answer

Use timeouts, bounded pools, query optimization, short boundaries, and workload isolation.

#### Interview answer

Keep transactions short, avoid external calls inside them, set transaction and statement timeouts, use proper indexes, and isolate batch jobs from user-facing pools when needed.

#### Deep dive

Bulk work should be chunked. High-risk operations should have circuit breakers, backpressure, and clear cancellation behavior.

#### Production angle

Separate pools or workers for batch jobs can prevent one import from starving normal API traffic.

#### Traps / caveats

- Increasing timeouts can make incidents worse.
- One slow query can hold locks needed by many fast queries.
- Retry storms can amplify the original slowdown.

#### Optional Anki

Q: How do you contain slow transaction impact?
A: Short boundaries, timeouts, backpressure, optimized SQL, and workload isolation.

</details>
