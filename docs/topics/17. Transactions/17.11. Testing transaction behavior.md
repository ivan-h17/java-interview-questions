# Testing transaction behavior

---

<a id="tx-test-001"></a>

<details>
<summary><strong>TX-TEST-001. How do you test transactional behavior in Spring?</strong></summary>

#### Short answer

Use integration tests with real Spring transaction infrastructure and a real database when behavior depends on the database.

#### Interview answer

Unit tests can verify business branching, but transaction boundaries, rollback, flush, isolation, locks, and propagation need integration tests. Use Spring test support and Testcontainers when database behavior matters.

#### Deep dive

Test both the successful commit path and failure rollback path. For concurrency, use multiple transactions or threads and assert final database state.

#### Production angle

Transaction bugs often appear only under real database constraints, isolation, and timing.

#### Traps / caveats

- Mocking repositories does not test transactions.
- In-memory databases may not match production behavior.
- Test methods annotated with `@Transactional` can hide commit-time failures.

#### Optional Anki

Q: What kind of test verifies transaction behavior best?
A: Integration tests using real Spring transaction infrastructure and the target database behavior.

</details>

<a id="tx-test-002"></a>

<details>
<summary><strong>TX-TEST-002. Why can `@Transactional` tests hide real production behavior?</strong></summary>

#### Short answer

Spring test transactions often roll back at the end and may run the whole test in one transaction.

#### Interview answer

If the test method is transactional, code that would commit in production may not commit during the test. Commit-time constraints, after-commit events, outbox relay behavior, and lazy loading boundaries may be hidden.

#### Deep dive

The test can also share one persistence context, masking detached entity behavior or missing fetches.

#### Production angle

For important flows, write tests that actually commit and verify post-commit behavior.

#### Traps / caveats

- A passing transactional test may not prove production commit works.
- `@TransactionalEventListener` after-commit may not fire as expected.
- Lazy loading can pass in tests and fail in real controllers.

#### Optional Anki

Q: Why can transactional tests mislead?
A: They may roll back and keep one transaction/persistence context open for the whole test.

</details>

<a id="tx-test-003"></a>

<details>
<summary><strong>TX-TEST-003. How would you test rollback behavior and `rollbackFor` checked exceptions?</strong></summary>

#### Short answer

Trigger the exception path and verify database state after the transaction ends.

#### Interview answer

Call the service method with input that causes a runtime or checked exception. Then query the database outside that transaction to verify what committed and what rolled back. For checked exceptions, test both default behavior and `rollbackFor` configuration.

#### Deep dive

If the test method itself is transactional, it may see uncommitted state or roll everything back later. Use a separate verification transaction or no test transaction.

#### Production angle

Rollback tests are important for payment, inventory, and multi-row writes where partial commits are dangerous.

#### Traps / caveats

- Catching the exception inside the service changes rollback behavior.
- Flush may be needed to expose some constraint failures.
- Verify the durable database state, not only mock calls.

#### Optional Anki

Q: How do you verify rollback?
A: Assert database state after the transactional method has ended.

</details>

<a id="tx-test-004"></a>

<details>
<summary><strong>TX-TEST-004. How would you test `REQUIRES_NEW`, `NESTED`, or self-invocation behavior?</strong></summary>

#### Short answer

Test through real Spring beans and verify committed database state for each boundary.

#### Interview answer

For `REQUIRES_NEW`, make the inner transaction commit and the outer transaction roll back, then verify the inner change survived if intended. For `NESTED`, verify savepoint rollback behavior. For self-invocation, call the real public method path and check whether the annotation was applied.

#### Deep dive

These tests must use Spring proxies, not direct `new` instances or mocks.

#### Production angle

Propagation and proxy bugs are common and expensive because code looks annotated but behaves differently.

#### Traps / caveats

- `NESTED` support depends on transaction manager and database.
- Self-invocation tests should match production call paths.
- Test data cleanup should not hide commits.

#### Optional Anki

Q: Why test transactional self-invocation through Spring?
A: The bug depends on proxy interception, which direct object calls bypass.

</details>

<a id="tx-test-005"></a>

<details>
<summary><strong>TX-TEST-005. Why should transaction isolation tests use a real database, often with Testcontainers?</strong></summary>

#### Short answer

Isolation and locking behavior are database-specific.

#### Interview answer

In-memory databases do not faithfully reproduce PostgreSQL or MySQL transaction semantics. If the test checks lost updates, lock waits, deadlocks, or isolation anomalies, it should run against the real database engine.

#### Deep dive

Testcontainers makes it practical to run integration tests against a production-like database in CI.

#### Production angle

This catches bugs that only appear under real MVCC, locking, indexes, and isolation implementation.

#### Traps / caveats

- H2 compatibility mode is not enough for serious concurrency tests.
- Concurrency tests can be flaky if timing is uncontrolled.
- Use barriers/latches to control transaction interleaving.

#### Optional Anki

Q: Why use Testcontainers for isolation tests?
A: To test against real database transaction semantics.

</details>

<a id="tx-test-006"></a>

<details>
<summary><strong>TX-TEST-006. How would you test lost update prevention, optimistic locking, and deadlock retry?</strong></summary>

#### Short answer

Run concurrent transactions with controlled interleaving and assert final state plus retry behavior.

#### Interview answer

For lost updates, have two transactions read the same row and update it, then verify one conflict or correct final value. For optimistic locking, expect an optimistic lock exception. For deadlock retry, force conflicting lock order and verify the retry wrapper succeeds or fails cleanly after max attempts.

#### Deep dive

Use latches or barriers so the test controls when each transaction reads and writes.

#### Production angle

These tests protect high-risk flows like inventory reservation, account updates, and job claiming.

#### Traps / caveats

- Sleeping in tests is flaky.
- Make final assertions from a fresh transaction.
- Retry tests must avoid non-idempotent side effects.

#### Optional Anki

Q: What makes a good concurrency test?
A: Controlled transaction interleaving and final durable-state assertions.

</details>

<a id="tx-test-007"></a>

<details>
<summary><strong>TX-TEST-007. How would you test outbox atomicity and idempotency under retries?</strong></summary>

#### Short answer

Verify business data and outbox rows commit together, and duplicate delivery is safe.

#### Interview answer

Test that when business transaction commits, the outbox row exists; when it rolls back, neither exists. Then simulate relay retry or duplicate message delivery and verify the consumer applies the change once.

#### Deep dive

Consumer tests should use a processed-message table or equivalent deduplication mechanism in the same transaction as side effects.

#### Production angle

This protects against lost events, ghost events, duplicate processing, and retry storms.

#### Traps / caveats

- Mocking Kafka does not prove database atomicity.
- Duplicate delivery must be tested deliberately.
- Event IDs should remain stable across retries.

#### Optional Anki

Q: What should an outbox atomicity test prove?
A: Business data and outbox record commit or roll back together.

</details>

<a id="tx-test-008"></a>

<details>
<summary><strong>TX-TEST-008. How can mocking repositories give false confidence about transactional code?</strong></summary>

#### Short answer

Mocks do not exercise transactions, database constraints, flush, locking, or isolation.

#### Interview answer

A mocked repository can verify that a method was called, but it cannot show whether the transaction committed, rolled back, violated a constraint, triggered flush, or lost an update under concurrency.

#### Deep dive

Unit tests are still valuable for business branching. They just are not sufficient for transaction semantics.

#### Production angle

Relying only on mocks leaves critical persistence bugs for staging or production.

#### Traps / caveats

- Mock tests often miss `@Transactional` proxy issues.
- They do not catch mapping or constraint errors.
- Use integration tests for persistence boundaries.

#### Optional Anki

Q: What do repository mocks not test?
A: Real transaction and database behavior.

</details>

<a id="tx-test-009"></a>

<details>
<summary><strong>TX-TEST-009. What should be unit-tested versus integration-tested in transactional code?</strong></summary>

#### Short answer

Unit-test decision logic; integration-test transaction, persistence, and concurrency behavior.

#### Interview answer

Use unit tests for pure business rules, validation decisions, and branching. Use integration tests for `@Transactional`, rollback, propagation, JPA flush, constraints, locks, isolation, outbox, and idempotency.

#### Deep dive

The more the behavior depends on Spring infrastructure or the database engine, the more it needs an integration test.

#### Production angle

This keeps tests fast where possible and realistic where correctness depends on infrastructure.

#### Traps / caveats

- Do not try to mock your way into confidence about isolation.
- Do not make every test a slow full-stack test.
- Focus integration tests on high-risk boundaries.

#### Optional Anki

Q: What transactional behavior needs integration tests?
A: Rollback, propagation, flush, constraints, locks, isolation, outbox, and concurrency.

</details>
