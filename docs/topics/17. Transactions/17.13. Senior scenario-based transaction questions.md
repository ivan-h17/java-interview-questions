# Senior scenario-based transaction questions

<a id="tx-scenario-001"></a>

<details>
<summary><strong>TX-SCENARIO-001. A payment transaction writes to the database and the service crashes before publishing an event. How would you fix the design?</strong></summary>

#### Short answer

Use Transactional Outbox so the event is stored with the payment update before commit.

#### Interview answer

The failure is a classic dual-write gap. The payment state committed, but the event was not durably recorded for publishing. Write the payment update and an outbox row in the same transaction, then publish asynchronously from the outbox.

#### Deep dive

The outbox relay can retry publishing after crash. Consumers still need idempotency because the relay may publish duplicates.

#### Production angle

Add monitoring for oldest unpublished outbox age and failed publish attempts.

#### Traps / caveats

- Publishing after commit still has a crash window.
- Publishing before commit can create ghost events.
- Outbox is not a replacement for idempotent consumers.

#### Optional Anki

Q: What pattern fixes DB commit followed by failed event publish?
A: Transactional Outbox.

</details>

<a id="tx-scenario-002"></a>

<details>
<summary><strong>TX-SCENARIO-002. A service publishes a Kafka event and then the database transaction rolls back. What went wrong?</strong></summary>

#### Short answer

The service emitted an external side effect before the database state was committed.

#### Interview answer

Kafka publish is not rolled back with the database transaction. Consumers can observe an event for data that never committed. The design should publish only from durable committed state, usually through Outbox.

#### Deep dive

Even if the publish call is inside a `@Transactional` method, it is not part of the relational database transaction.

#### Production angle

Repair may require a compensating event or downstream cleanup if consumers already acted on the ghost event.

#### Traps / caveats

- Kafka producer transactions do not automatically include the database.
- After-commit callbacks can still lose work on crash if not durable.
- Consumers should validate current state when possible.

#### Optional Anki

Q: Why is publishing Kafka inside a DB transaction unsafe?
A: Kafka publish is an external side effect not rolled back with the DB transaction.

</details>

<a id="tx-scenario-003"></a>

<details>
<summary><strong>TX-SCENARIO-003. Two users reserve the last available item at the same time. How would you prevent overselling?</strong></summary>

#### Short answer

Protect the inventory invariant with an atomic database operation, lock, constraint, or optimistic version.

#### Interview answer

I would avoid a separate "read stock then update" race. Use an atomic update like `UPDATE inventory SET stock = stock - 1 WHERE id = ? AND stock > 0`, or lock the row with `SELECT FOR UPDATE` before checking and decrementing.

#### Deep dive

If reservations are separate rows, use constraints or Serializable isolation to ensure total reservations do not exceed stock.

#### Production angle

Also use idempotency keys so client retries do not reserve twice.

#### Traps / caveats

- Java `synchronized` does not protect multiple service instances.
- Read Committed alone may be insufficient.
- Always test with concurrent requests.

#### Optional Anki

Q: What is a simple safe stock decrement?
A: A conditional atomic update that decrements only when stock is positive.

</details>

<a id="tx-scenario-004"></a>

<details>
<summary><strong>TX-SCENARIO-004. Two workers process the same job row. How would you fix it?</strong></summary>

#### Short answer

Use atomic claiming so only one worker can own the job.

#### Interview answer

Workers should claim jobs with a transaction: select pending rows with `FOR UPDATE SKIP LOCKED` or perform an atomic status update from `PENDING` to `IN_PROGRESS`. Only the worker that successfully claims the row processes it.

#### Deep dive

Add lease timestamps, retry counts, and failure states so jobs claimed by crashed workers can be recovered.

#### Production angle

The job handler should still be idempotent because crashes can happen after partial side effects.

#### Traps / caveats

- Do not hold row locks during long external processing.
- Claims need expiration or manual repair.
- Queue ordering and starvation need thought.

#### Optional Anki

Q: How do workers avoid duplicate processing?
A: Atomically claim jobs before processing.

</details>

<a id="tx-scenario-005"></a>

<details>
<summary><strong>TX-SCENARIO-005. A batch import holds locks for minutes and blocks the application. How would you redesign it?</strong></summary>

#### Short answer

Split it into smaller transactions with progress tracking and restartability.

#### Interview answer

A long all-or-nothing import should usually become chunked. Each chunk validates, writes, commits, and records progress. Use smaller batches, proper indexes, and avoid locking hot rows for the whole import.

#### Deep dive

If all-or-nothing semantics are required, consider staging tables and a short final swap or activation step.

#### Production angle

Run heavy jobs off-peak, throttle them, and isolate their database pool if needed.

#### Traps / caveats

- Chunking means partial progress, so recovery design is required.
- Killing a huge transaction can cause long rollback.
- Missing indexes can make each chunk still too expensive.

#### Optional Anki

Q: How do you redesign a lock-heavy batch import?
A: Use chunked transactions, progress tracking, throttling, and restartability.

</details>

<a id="tx-scenario-006"></a>

<details>
<summary><strong>🧠 TX-SCENARIO-006. A transaction stays idle for 20 minutes and autovacuum cannot clean old tuples. What is happening?</strong></summary>

#### Short answer

An old open transaction is holding a snapshot that prevents MVCC cleanup.

#### Interview answer

The session is likely `idle in transaction`. Even though it is not actively running SQL, its transaction is still open. PostgreSQL must keep old row versions visible to that snapshot, so cleanup is delayed.

#### Deep dive

If this repeats, tables and indexes can bloat, autovacuum falls behind, and transaction ID wraparound risk can increase in extreme cases.

#### Production angle

Find the application path, close transactions promptly, add timeouts, and avoid waiting on external work inside transactions.

#### Traps / caveats

- Read-only transactions can cause this.
- Killing the session is mitigation, not root-cause fix.
- Connection pool reuse can obscure the original request.

#### Optional Anki

Q: Why can an idle transaction block cleanup?
A: Its old snapshot may still need old row versions.

</details>

<a id="tx-scenario-007"></a>

<details>
<summary><strong>TX-SCENARIO-007. An API retries after timeout and creates duplicate orders. How would you make it safe?</strong></summary>

#### Short answer

Use idempotency keys stored transactionally with the order creation result.

#### Interview answer

The client should send an idempotency key for create-order. The service stores that key under a unique constraint in the same transaction as the order. A retry with the same key returns the original result instead of creating another order.

#### Deep dive

Timeout does not prove the first attempt failed. It may have committed after the client stopped waiting.

#### Production angle

This is essential for payment, checkout, subscription, and provisioning APIs.

#### Traps / caveats

- Reject same key with a different payload.
- Store enough response data to return consistent results.
- Cleanup must respect retry windows.

#### Optional Anki

Q: How do you make create-order retry-safe?
A: Use a transactionally stored idempotency key with a unique constraint.

</details>

<a id="tx-scenario-008"></a>

<details>
<summary><strong>TX-SCENARIO-008. A read-only endpoint sometimes does not see the object it just created. What could cause it?</strong></summary>

#### Short answer

The read may be routed to a lagging replica.

#### Interview answer

If the create operation writes to primary but a follow-up read-only endpoint uses a replica, replication lag can make the new object temporarily invisible.

#### Deep dive

This is a read-your-writes consistency problem, not necessarily a failed transaction.

#### Production angle

Route reads after writes to primary, use sticky sessions, lag-aware routing, or return a pending state.

#### Traps / caveats

- `readOnly = true` can trigger replica routing.
- Retrying immediately may hit the same stale replica.
- Authorization and critical workflow reads should avoid stale replicas.

#### Optional Anki

Q: Why can a created object not appear on a read-only endpoint?
A: The read may hit a replica that has not caught up.

</details>

<a id="tx-scenario-009"></a>

<details>
<summary><strong>TX-SCENARIO-009. A migration waits for a long time because application transactions hold locks. What would you check?</strong></summary>

#### Short answer

Find blocking sessions, their transaction age, queries, and application endpoints.

#### Interview answer

I would inspect database locks and waiting DDL, identify blockers, check whether they are active or idle in transaction, and map them to application logs. Then I would decide whether to wait, cancel the migration, or terminate a blocker if safe.

#### Deep dive

For future migrations, use lock timeout, short steps, online/concurrent patterns, and maintenance planning.

#### Production angle

A waiting migration can create a lock queue and degrade normal traffic.

#### Traps / caveats

- Do not run risky DDL without timeout.
- Killing a blocker can roll back user work.
- Test lock behavior in staging with realistic load.

#### Optional Anki

Q: What should migrations use to avoid waiting forever?
A: Lock timeouts and safe online/expand-and-contract migration patterns.

</details>

<a id="tx-scenario-010"></a>

<details>
<summary><strong>TX-SCENARIO-010. A supposedly atomic operation touches two databases. What are your options?</strong></summary>

#### Short answer

Use distributed transactions only if justified, or redesign with local transactions and eventual consistency.

#### Interview answer

Options include XA/2PC, combining data into one transactional boundary, using a Saga, writing an outbox event, or accepting eventual consistency with reconciliation. The best option depends on the business invariant and failure tolerance.

#### Deep dive

If the operation truly requires immediate atomicity, service/database boundaries may be wrong. If eventual consistency is acceptable, design states, retries, compensation, and monitoring.

#### Production angle

Make the failure modes explicit before implementation.

#### Traps / caveats

- Two `@Transactional` methods do not create atomicity across databases by default.
- Chained local transactions can leave partial commits.
- Reconciliation is not optional in eventual workflows.

#### Optional Anki

Q: What are alternatives to atomic two-database commit?
A: XA/2PC, redesign into one boundary, Saga, Outbox, idempotency, and reconciliation.

</details>

<a id="tx-scenario-011"></a>

<details>
<summary><strong>🧠 TX-SCENARIO-011. How would you explain the lifecycle of a Spring transactional service method from proxy call to commit?</strong></summary>

#### Short answer

The proxy intercepts the call, the transaction manager starts or joins a transaction, the method runs, then Spring completes the transaction if this boundary started it.

#### Interview answer

A caller invokes the Spring proxy. The transaction interceptor reads metadata from `@Transactional`, asks the transaction manager to start a transaction or join an existing one, binds resources such as a connection or persistence context, calls the target method, then commits or rolls back only if this boundary owns the physical transaction. If it joined an outer transaction, the outer boundary decides the final outcome.

#### Deep dive

With JPA, changes may be dirty-checked and flushed before commit. If an inner method marks rollback-only, the final commit can throw `UnexpectedRollbackException`.

#### Production angle

This lifecycle explains self-invocation bugs, checked-exception rollback surprises, connection hold time, and commit-time failures.

#### Traps / caveats

- The lifecycle only applies when the call goes through the proxy.
- Commit can fail after the method body completes.
- External side effects inside the method are not rolled back.

#### Optional Anki

Q: What starts a typical Spring transaction?
A: The transaction interceptor on the Spring proxy asks the transaction manager to start or join one.

</details>
