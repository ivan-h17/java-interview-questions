# Spring transaction model

---

<a id="tx-spr-001"></a>

<details>
<summary><strong>TX-SPR-001. What does `@Transactional` do at a high level?</strong></summary>

#### Short answer

`@Transactional` tells Spring to run a method inside a transaction boundary.

#### Interview answer

When a proxied method is called, Spring starts a new transaction or joins an existing one according to the annotation attributes. If this boundary started the transaction, Spring commits on success or rolls back on a rollback-triggering exception; if it joined an existing transaction, the outer boundary decides the final commit or rollback.

#### Deep dive

The annotation is metadata. The actual work is done by Spring transaction infrastructure, a transaction manager, and the underlying resource such as JDBC or JPA.

#### Production angle

It is useful for service-level use cases such as creating an order, updating account state, or writing business data plus an outbox row.

#### Traps / caveats

- It works only when Spring intercepts the call.
- It does not make remote calls or Kafka publishes part of the database transaction.
- Default rollback behavior depends on exception type.

#### Optional Anki

Q: What does `@Transactional` do?
A: It lets Spring start or join a transaction and apply commit or rollback rules at the correct transaction boundary.

</details>

<a id="tx-spr-002"></a>

<details>
<summary><strong>TX-SPR-002. Why does `@Transactional` usually rely on a Spring proxy?</strong></summary>

#### Short answer

Spring commonly applies transaction logic by wrapping the bean in a proxy that intercepts method calls.

#### Interview answer

The proxy starts a new transaction or joins an existing one before invoking the target method, then applies completion rules at the correct boundary. Without a call through the proxy, the transaction advice is not applied.

#### Deep dive

Spring can use JDK dynamic proxies or CGLIB proxies. Proxy-based interception works well for external calls to Spring beans, but not for every kind of method call.

#### Production angle

Many "transaction did not work" bugs are really proxy bypass bugs.

#### Traps / caveats

- Self-invocation bypasses the proxy.
- Private methods are not intercepted.
- Constructor calls happen before proxy interception.

#### Optional Anki

Q: Why can `@Transactional` fail silently?
A: The method call may bypass the Spring proxy that applies transaction advice.

</details>

<a id="tx-spr-003"></a>

<details>
<summary><strong>TX-SPR-003. Why do self-invocation, private methods, final methods, and constructor calls often bypass `@Transactional`?</strong></summary>

#### Short answer

They are not normal external calls through the transactional proxy.

#### Interview answer

With proxy-based Spring AOP, transaction advice runs when another bean calls the proxied method. A call from one method to another method on the same instance uses `this`, not the proxy. Private, final, and constructor-time methods also cannot be intercepted reliably by the proxy.

#### Deep dive

The usual fix is to move the transactional method to another bean, restructure the service boundary, or use programmatic transactions. AspectJ mode can handle some cases but is less common.

#### Production angle

This bug often appears as data committed when it should roll back, missing lazy-loading context, or a method that appears annotated but runs without a transaction.

#### Traps / caveats

- Injecting a self-proxy can work but often signals poor design.
- Tests may not cover the actual call path.
- Annotation on a private helper is misleading.

#### Optional Anki

Q: Why does self-invocation bypass `@Transactional`?
A: The call uses `this`, so it does not pass through the Spring proxy.

</details>

<a id="tx-spr-004"></a>

<details>
<summary><strong>TX-SPR-004. Why is `@Transactional` usually placed on service methods instead of controllers or repositories only?</strong></summary>

#### Short answer

Service methods usually represent the business operation that should be atomic.

#### Interview answer

Controllers are too close to transport concerns, while repositories are often too small. A service method can include all database changes for one use case without including request parsing, serialization, or external calls.

#### Deep dive

Repository-level transactions can accidentally create several small transactions inside one business operation. Controller-level transactions can hold connections across web concerns and serialization.

#### Production angle

Good placement prevents partial writes while keeping transactions short and focused.

#### Traps / caveats

- Some read-only query services can have their own boundaries.
- Do not put slow external calls inside the service transaction.
- Service boundaries should follow business invariants, not arbitrary layers.

#### Optional Anki

Q: Why prefer service-level transaction boundaries?
A: They usually match the full business unit of work.

</details>

<a id="tx-spr-005"></a>

<details>
<summary><strong>TX-SPR-005. What is `PlatformTransactionManager`, and how does Spring choose one?</strong></summary>

#### Short answer

`PlatformTransactionManager` is Spring's abstraction for beginning, committing, and rolling back transactions.

#### Interview answer

Spring delegates transaction control to a transaction manager. For JDBC it may use `DataSourceTransactionManager`; for JPA it may use `JpaTransactionManager`. Spring Boot usually auto-configures a suitable manager based on the available beans.

#### Deep dive

If multiple transaction managers exist, selection may depend on bean name, `@Primary`, explicit annotation attributes, or transaction management configuration.

#### Production angle

Wrong manager selection can make transactions not cover the resource you think they cover, especially in multi-database applications.

#### Traps / caveats

- Multiple data sources need explicit configuration.
- A JPA transaction and a JDBC transaction must coordinate on the same underlying connection if mixed.
- Auto-configuration is convenient but should be verified.

#### Optional Anki

Q: What does `PlatformTransactionManager` abstract?
A: Starting, committing, and rolling back transactions for a resource.

</details>

<a id="tx-spr-006"></a>

<details>
<summary><strong>TX-SPR-006. When would you use `TransactionTemplate` instead of `@Transactional`?</strong></summary>

#### Short answer

Use `TransactionTemplate` when transaction boundaries need to be explicit in code.

#### Interview answer

`@Transactional` is best for declarative service boundaries. `TransactionTemplate` is useful when only a small block should be transactional, when you need clear programmatic control, or when proxy-based annotations are awkward.

#### Deep dive

It can help avoid self-invocation issues and can make retry or nested operation boundaries more visible. The trade-off is more transaction code mixed into business logic.

#### Production angle

It is useful for separating a database transaction from a slow external call in the same method.

#### Traps / caveats

- Do not overuse it as a replacement for clean service boundaries.
- It still uses a transaction manager and follows the same database semantics.
- Side effects inside the callback have the same risks as with `@Transactional`.

#### Optional Anki

Q: When is `TransactionTemplate` useful?
A: When transaction boundaries need explicit programmatic control.

</details>

<a id="tx-spr-007"></a>

<details>
<summary><strong>TX-SPR-007. Why does `@Transactional` not automatically work across threads or async boundaries?</strong></summary>

#### Short answer

Spring transaction context is usually bound to the current thread.

#### Interview answer

When a transaction starts, Spring binds resources such as the database connection to the executing thread. If work moves to another thread with `@Async`, an executor, or a reactive pipeline, that thread does not automatically inherit the same transaction.

#### Deep dive

Cross-thread propagation would be unsafe for normal JDBC connections. Each thread should have its own explicit transaction boundary if it performs database work.

#### Production angle

Async work started inside a transaction can observe uncommitted data incorrectly, run outside a transaction, or publish side effects before commit.

#### Traps / caveats

- `@Async` and `@Transactional` order matters.
- ThreadLocals do not cross executor boundaries.
- Use after-commit events or outbox for post-commit work.

#### Optional Anki

Q: Why does `@Transactional` not cross async boundaries?
A: The transaction context is usually thread-bound.

</details>

<a id="tx-spr-008"></a>

<details>
<summary><strong>TX-SPR-008. When would you use `@TransactionalEventListener` for after-commit work?</strong></summary>

#### Short answer

Use it when work should run only after the surrounding transaction successfully commits.

#### Interview answer

`@TransactionalEventListener` can defer handling an application event until a transaction phase such as after commit. It is useful for cache invalidation, lightweight notifications, or scheduling work that should not run if the transaction rolls back.

#### Deep dive

It is not a durable messaging pattern by itself. If the process crashes after commit but before the listener completes, the work can be lost unless it is persisted elsewhere.

#### Production angle

For reliable integration events, use Transactional Outbox. For local after-commit callbacks, `@TransactionalEventListener` can be enough.

#### Traps / caveats

- It depends on an active transaction unless configured otherwise.
- It does not make external side effects atomic.
- Listener failures after commit cannot roll back the original transaction.

#### Optional Anki

Q: When is `@TransactionalEventListener` useful?
A: For local work that should run only after transaction commit.

</details>

<details>
<summary><strong>🧠 TX-SPR-009. How does reactive or R2DBC transaction management differ from thread-bound transaction management?</strong></summary>

#### Short answer

Reactive transactions use reactive context instead of relying on one blocking thread and JDBC connection model.

#### Interview answer

Traditional Spring JDBC/JPA transactions are commonly thread-bound. Reactive stacks cannot assume one request stays on one thread, so transaction context must flow through the reactive pipeline.

#### Deep dive

With R2DBC, transaction management is non-blocking and must be composed correctly. Blocking JPA transaction assumptions do not directly apply.

#### Production angle

Mixing blocking database access and reactive code can break scalability and transaction expectations. Use the transaction model appropriate for the stack.

#### Traps / caveats

- ThreadLocal-based assumptions are wrong in reactive pipelines.
- Not all JDBC/JPA features have direct R2DBC equivalents.
- Transaction boundaries must be part of the reactive chain.

#### Optional Anki

Q: Why are reactive transactions different?
A: They propagate through reactive context, not a single thread-bound JDBC context.

</details>
