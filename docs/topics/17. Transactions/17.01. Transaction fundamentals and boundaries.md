# Transaction fundamentals and boundaries

---

<a id="tx-fund-001"></a>

<details>
<summary><strong>TX-FUND-001. What problem do transactions solve in backend applications?</strong></summary>

#### Short answer

Transactions group related database changes so they succeed or fail as one consistent unit.

#### Interview answer

In backend applications, many operations need several writes to represent one business action. For example, creating an order may insert an order, order items, payment state, inventory reservation, and an outbox event. A transaction prevents the system from committing only half of that change.

#### Deep dive

A transaction gives a boundary for atomicity, isolation, and commit/rollback. It does not make code correct by itself; the application still needs proper constraints, isolation choices, locking, idempotency, and side-effect handling.

#### Production angle

Good transaction design protects money movement, inventory, account state, workflow transitions, and audit data from partial writes and race conditions.

#### Traps / caveats

- Transactions usually cover database resources, not HTTP calls, emails, Kafka publishes, or another service's database.
- A transaction that is too broad can hold locks and connections too long.
- A transaction that is too narrow may not protect the full business invariant.

#### Optional Anki

Q: What problem do transactions solve?
A: They group related database changes into one consistent commit or rollback boundary.

</details>

<a id="tx-fund-002"></a>

<details>
<summary><strong>TX-FUND-002. How would you explain ACID without only listing the acronym?</strong></summary>

#### Short answer

ACID means a transaction should be all-or-nothing, preserve valid state, isolate concurrent work, and survive after commit.

#### Interview answer

Atomicity means partial writes are rolled back. Consistency means constraints and invariants should hold after commit. Isolation controls how concurrent transactions interact. Durability means committed data survives crashes according to the database's guarantees.

#### Deep dive

ACID is not one switch. Isolation depends on the configured level. Consistency depends on database constraints and application logic. Durability depends on database, storage, and replication configuration.

#### Production angle

A senior answer should connect ACID to real flows: payments should not partially update, inventory should not oversell, concurrent writes should not silently overwrite each other, and committed orders should not disappear after restart.

#### Traps / caveats

- ACID does not mean Serializable isolation by default.
- Consistency is not only a database feature; business rules still matter.
- External side effects are outside a normal database transaction.

#### Optional Anki

Q: What are the practical ACID guarantees?
A: All-or-nothing changes, valid final state, controlled concurrency, and persistence after commit.

</details>

<details>
<summary><strong>TX-FUND-003. What is a transaction boundary, and why is it usually placed at the service layer?</strong></summary>

#### Short answer

A transaction boundary defines where a unit of work starts and ends; the service layer usually owns the business use case.

#### Interview answer

Repositories are usually too small because one use case may need several repository calls. Controllers are often too broad because they include request parsing, authorization, serialization, and sometimes external calls. A service method often maps best to the business operation that must commit or roll back together.

#### Deep dive

Good boundaries should include the database changes required for one invariant, but exclude slow or non-transactional work when possible. In Spring, this often means `@Transactional` on application service methods.

#### Production angle

Wrong boundaries cause partial writes, lazy loading leaks, connection pool exhaustion, long lock waits, and hard-to-debug rollback behavior.

#### Traps / caveats

- Service-layer transactions are a rule of thumb, not a law.
- Do not wrap an entire HTTP request in a transaction by habit.
- Avoid starting transactions deep inside small repository helpers if the caller needs a larger atomic operation.

#### Optional Anki

Q: Why put transaction boundaries on service methods?
A: Service methods usually represent the full business operation that should commit or roll back together.

</details>

<a id="tx-fund-004"></a>

<details>
<summary><strong>TX-FUND-004. How do commit, rollback, and savepoints differ?</strong></summary>

#### Short answer

Commit makes changes permanent, rollback cancels the transaction, and a savepoint allows rollback to a point inside a transaction.

#### Interview answer

Commit is the successful end of a transaction. Rollback discards uncommitted work. A savepoint is a marker inside a transaction that lets the code undo part of the work without aborting everything.

#### Deep dive

Savepoints are useful for nested or partial recovery scenarios, but they still live inside the same physical database transaction. Locks and resources may still be held until the outer transaction finishes.

#### Production angle

Most business code should not need manual savepoints. If savepoints appear often, the use case may be doing too much in one transaction or mixing independent concerns.

#### Traps / caveats

- Rolling back to a savepoint is not the same as committing an inner transaction.
- Savepoints do not make external side effects reversible.
- ORM behavior around savepoints can be surprising if the persistence context still contains changed entities.

#### Optional Anki

Q: What is the difference between rollback and savepoint rollback?
A: Rollback aborts the transaction; savepoint rollback undoes work after a marker inside the same transaction.

</details>

<a id="tx-fund-005"></a>

<details>
<summary><strong>TX-FUND-005. How does JDBC autocommit affect transaction behavior?</strong></summary>

#### Short answer

With autocommit enabled, each SQL statement commits automatically unless an explicit transaction disables it.

#### Interview answer

JDBC connections usually default to autocommit. That means each statement is its own transaction. Frameworks like Spring turn autocommit off while a transaction is active, then commit or roll back at the boundary.

#### Deep dive

Autocommit is fine for simple single-statement operations, but it is dangerous when several statements must succeed together. In a pool, the framework must also restore connection state before returning the connection.

#### Production angle

Autocommit mistakes can create partial writes, especially in hand-written JDBC code, migration scripts, or batch jobs outside normal Spring transaction management.

#### Traps / caveats

- Do not assume several JDBC calls are atomic unless a transaction is active.
- Connection pools reuse connections, so leaked autocommit state is dangerous.
- Some DDL behavior is database-specific.

#### Optional Anki

Q: What does JDBC autocommit do?
A: It commits each statement automatically unless an explicit transaction controls the connection.

</details>

<details>
<summary><strong>TX-FUND-006. What is the difference between local, global, and distributed transactions?</strong></summary>

#### Short answer

A local transaction involves one resource; a global or distributed transaction coordinates multiple transactional resources.

#### Interview answer

A local transaction might be one database connection. A distributed transaction tries to coordinate several resources, such as two databases or a database and a message broker, so they commit or roll back together.

#### Deep dive

Distributed coordination usually requires protocols such as XA or two-phase commit. These add operational complexity, blocking behavior, and failure modes that are not attractive in many microservice systems.

#### Production angle

Most Java backend systems prefer local transactions plus patterns such as Outbox, Saga, idempotency, and reconciliation instead of broad distributed transactions.

#### Traps / caveats

- Calling two repositories is not distributed if they use the same database transaction.
- Calling two services is not automatically transactional.
- A local DB transaction cannot roll back another service's committed work.

#### Optional Anki

Q: What is a local transaction?
A: A transaction controlled over one transactional resource, usually one database connection.

</details>

<a id="tx-fund-007"></a>

<details>
<summary><strong>🧠 TX-FUND-007. What is the Unit of Work pattern, and how is it related to transactions?</strong></summary>

#### Short answer

Unit of Work tracks changes made during a business operation and flushes them as one unit, often inside a transaction.

#### Interview answer

In ORM-based applications, the persistence context behaves like a Unit of Work. It tracks loaded entities, detects changes, and writes them to the database during flush or commit.

#### Deep dive

The pattern separates in-memory changes from database synchronization. This is useful, but it also means SQL may execute later than the line where an entity field changed.

#### Production angle

Understanding Unit of Work helps explain dirty checking, flush surprises, memory growth in large transactions, and why exceptions may appear at commit time.

#### Traps / caveats

- It is not a replacement for database constraints.
- Large units of work can consume memory and hold locks too long.
- Delayed flush can hide SQL errors until later.

#### Optional Anki

Q: How is Unit of Work related to JPA?
A: The JPA persistence context tracks entity changes and flushes them as one unit.

</details>

<details>
<summary><strong>TX-FUND-008. Why are long-running transactions dangerous?</strong></summary>

#### Short answer

They hold connections, locks, snapshots, and database resources longer than necessary.

#### Interview answer

A long transaction increases contention and makes failures more expensive. It can block other requests, exhaust the connection pool, delay cleanup in MVCC databases, and make retries expensive.

#### Deep dive

The transaction duration is not just SQL time. It includes any work done while the transaction is open: mapping, remote calls, loops, serialization, waits, and application logic.

#### Production angle

Long transactions often show up as lock waits, high request latency, pool exhaustion, `idle in transaction`, bloat, and migration blocking.

#### Traps / caveats

- Read-only transactions can still be harmful if they hold old snapshots.
- Slow external calls inside transactions are a common root cause.
- Increasing pool size may hide the symptom while increasing DB pressure.

#### Optional Anki

Q: Why are long transactions risky?
A: They hold database resources longer, increasing contention, latency, and cleanup problems.

</details>

<a id="tx-fund-009"></a>

<details>
<summary><strong>TX-FUND-009. What is the difference between database consistency and application-level business consistency?</strong></summary>

#### Short answer

Database consistency enforces structural rules; business consistency enforces domain rules.

#### Interview answer

The database can enforce constraints such as primary keys, foreign keys, uniqueness, checks, and not-null rules. Business consistency includes rules like "an order cannot be shipped before payment is captured" or "inventory cannot be reserved twice."

#### Deep dive

Good systems use both. Put critical invariants in database constraints when possible, and use application code for workflow and domain decisions that are too complex for constraints.

#### Production angle

Relying only on Java validation is risky under concurrency. Two requests can pass the same check before either commits unless the database also enforces the invariant.

#### Traps / caveats

- ORM validation does not protect against all concurrent writes.
- Database constraints do not understand every business workflow.
- Distributed business consistency needs more than one local transaction.

#### Optional Anki

Q: What is application-level consistency?
A: Domain invariants and workflow rules that may not be fully represented by database constraints.

</details>

<a id="tx-fund-010"></a>

<details>
<summary><strong>TX-FUND-010. Why do transactions not solve all distributed consistency problems?</strong></summary>

#### Short answer

A normal transaction protects one local resource boundary, not independent services and side effects.

#### Interview answer

If one service commits to its database, another service cannot automatically roll that commit back. Network calls, message brokers, emails, and external payment providers are outside a local database transaction.

#### Deep dive

Distributed consistency needs explicit design: Outbox for reliable publish, Saga for multi-step workflows, idempotency for retries, compensation for committed steps, and reconciliation for ambiguous failures.

#### Production angle

Assuming a transaction spans microservices leads to lost events, duplicate commands, stuck workflows, and inconsistent user-visible state.

#### Traps / caveats

- `@Transactional` does not cross HTTP boundaries.
- Kafka exactly-once does not make database writes exactly-once.
- Rollback is not available after another service has committed local state.

#### Optional Anki

Q: Why do local transactions not solve distributed consistency?
A: They do not atomically cover independent services, networks, brokers, or external systems.

</details>
