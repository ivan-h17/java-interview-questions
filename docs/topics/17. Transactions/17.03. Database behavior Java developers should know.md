# Database behavior Java developers should know

---

<a id="tx-db-001"></a>

<details>
<summary><strong>TX-DB-001. Why can the same isolation level behave differently in PostgreSQL and MySQL?</strong></summary>

#### Short answer

Isolation level names are common, but each database implements them differently.

#### Interview answer

PostgreSQL and MySQL/InnoDB both support common isolation levels, but their MVCC and locking behavior differ. The same label, such as Repeatable Read, can produce different behavior around snapshots, locks, phantoms, and gap locking.

#### Deep dive

Frameworks expose isolation enums, but the database is responsible for semantics. Exact behavior comes from the database engine, storage engine, indexes, and query plan.

#### Production angle

Concurrency-sensitive code should be tested against the production database, not only an in-memory test database.

#### Traps / caveats

- Do not assume isolation behavior is portable.
- A migration from MySQL to PostgreSQL can change concurrency outcomes.
- ORM abstractions do not hide database isolation semantics.

#### Optional Anki

Q: Why can isolation differ between PostgreSQL and MySQL?
A: The isolation names are similar, but MVCC and locking implementations differ.

</details>

<a id="tx-db-002"></a>

<details>
<summary><strong>TX-DB-002. What is MVCC, and how is it related to transaction isolation?</strong></summary>

#### Short answer

MVCC lets transactions see appropriate versions of rows instead of one global mutable row state.

#### Interview answer

Multi-Version Concurrency Control keeps multiple row versions so readers and writers can often proceed without blocking each other. A transaction sees rows according to its snapshot and isolation level.

#### Deep dive

MVCC improves concurrency but creates cleanup work. Old row versions cannot be removed while old snapshots still need them.

#### Production angle

Long transactions can keep old versions alive, increasing bloat and maintenance pressure. This is why transaction duration matters even for reads.

#### Traps / caveats

- MVCC does not prevent every anomaly.
- It reduces some blocking, but locks still exist.
- Long snapshots can harm cleanup.

#### Optional Anki

Q: What does MVCC provide?
A: Versioned row visibility so transactions can read consistent data while other work proceeds.

</details>

<a id="tx-db-003"></a>

<details>
<summary><strong>TX-DB-003. What is `idle in transaction`, and why is it dangerous?</strong></summary>

#### Short answer

It means a session opened a transaction and is doing nothing while the transaction remains active.

#### Interview answer

`idle in transaction` often means application code started a transaction, ran some SQL, then waited or forgot to finish. The connection, transaction snapshot, and possibly locks remain open.

#### Deep dive

In MVCC databases, an old open transaction can prevent cleanup of old row versions. If it holds locks, it can block writes or migrations.

#### Production angle

Investigate transaction start time, application name, last query, stack traces, connection pool leaks, slow external calls, and missing transaction boundaries.

#### Traps / caveats

- It can happen in read-only flows too.
- Killing the session may fix the symptom but not the code path.
- A pool can keep the bad behavior recurring.

#### Optional Anki

Q: What is `idle in transaction`?
A: An open transaction whose session is currently idle but still holding transaction resources.

</details>

<a id="tx-db-004"></a>

<details>
<summary><strong>TX-DB-004. How do transaction timeout, statement timeout, lock timeout, and connection pool timeout differ?</strong></summary>

#### Short answer

They time out different waits: whole transaction, individual SQL, lock acquisition, or borrowing a connection.

#### Interview answer

A transaction timeout limits the transactional work. A statement timeout limits one SQL statement. A lock timeout limits how long SQL waits for a lock. A connection pool timeout limits how long the application waits to borrow a connection.

#### Deep dive

These timeouts can fail at different layers and throw different exceptions. They also need different fixes: tune query, reduce lock contention, reduce transaction duration, or adjust pool/database capacity.

#### Production angle

When debugging, identify which timeout fired before changing numbers. Increasing all timeouts often makes incidents last longer.

#### Traps / caveats

- HTTP timeout is another separate layer.
- A transaction timeout may not interrupt every blocking call immediately.
- Pool timeout usually means connections are busy or leaked, not that the database is necessarily down.

#### Optional Anki

Q: What does lock timeout limit?
A: How long a statement waits to acquire a database lock.

</details>

<a id="tx-db-005"></a>

<details>
<summary><strong>🧠 TX-DB-005. How should a Java service handle PostgreSQL SQLSTATE `40001` and `40P01`?</strong></summary>

#### Short answer

Treat `40001` serialization failure and `40P01` deadlock detected as retryable transaction failures when the command is safe to retry.

#### Interview answer

The service should roll back the failed transaction and retry the entire business operation with backoff and a limit. The retry must be safe: no duplicate external side effects and idempotent command handling where needed.

#### Deep dive

Retrying the failed SQL inside the same transaction is wrong because the transaction is already aborted. Retry should happen outside the transaction boundary.

#### Production angle

Track frequency. Occasional retries are normal; spikes may indicate hot rows, inconsistent lock ordering, missing indexes, or a bad isolation choice.

#### Traps / caveats

- Do not retry indefinitely.
- Do not retry non-idempotent operations blindly.
- Preserve observability so retries do not hide user-visible latency.

#### Optional Anki

Q: What are PostgreSQL SQLSTATE `40001` and `40P01` usually treated as?
A: Retryable transaction failures, if the operation is safe to retry.

</details>

<a id="tx-db-006"></a>

<details>
<summary><strong>TX-DB-006. How can application transactions block DDL or database migrations?</strong></summary>

#### Short answer

Open transactions can hold locks or old snapshots that conflict with schema changes.

#### Interview answer

DDL often needs locks on tables or metadata. If application transactions are reading or writing the same objects, the migration may wait. In the other direction, a waiting migration can become a blocker for later application queries.

#### Deep dive

Even "small" migrations can be risky on hot tables. Lock acquisition timing, transaction duration, and database-specific DDL behavior matter.

#### Production angle

Use lock timeouts, online/concurrent migration patterns, batching, expand-and-contract changes, and monitoring before running migrations.

#### Traps / caveats

- A migration waiting for a lock can cause a lock queue.
- Long read transactions may still matter.
- Test migration lock behavior on production-like data.

#### Optional Anki

Q: Why can a migration block or be blocked?
A: DDL often needs locks that conflict with application transactions.

</details>

<a id="tx-db-007"></a>

<details>
<summary><strong>TX-DB-007. What transaction behavior should a Java developer not assume when switching from MySQL to PostgreSQL?</strong></summary>

#### Short answer

Do not assume the same isolation, locking, DDL, upsert, timeout, or error behavior.

#### Interview answer

The application may use the same Spring and JPA code, but the database semantics change. Isolation names, lock behavior, constraint timing, upsert syntax, deadlock handling, and timeout configuration can differ.

#### Deep dive

Database migration requires concurrency tests, integration tests, and review of SQL and transaction assumptions. Hiding SQL behind JPA does not remove these differences.

#### Production angle

High-risk areas include inventory, money movement, idempotency, batch jobs, migrations, and queue-like worker patterns.

#### Traps / caveats

- Passing unit tests is not enough.
- Different default isolation levels are only one part of the problem.
- Retry and exception translation may need adjustment.

#### Optional Anki

Q: What should not be assumed when switching databases?
A: That isolation, locking, DDL, timeout, and error semantics stay the same.

</details>
