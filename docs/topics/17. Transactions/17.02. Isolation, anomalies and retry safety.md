# Isolation, anomalies and retry safety

---

<a id="tx-iso-001"></a>

<details>
<summary><strong>TX-ISO-001. What SQL transaction isolation levels exist, and what trade-offs do they represent?</strong></summary>

#### Short answer

The common SQL isolation levels are Read Uncommitted, Read Committed, Repeatable Read, and Serializable.

#### Interview answer

Lower isolation usually gives more concurrency but allows more anomalies. Higher isolation prevents more anomalies but can increase locking, conflicts, latency, or retry requirements.

#### Deep dive

The exact behavior is database-specific. PostgreSQL, MySQL, Oracle, and SQL Server do not implement every level identically. In practice, many systems use Read Committed plus constraints, explicit locks, optimistic locking, and retries.

#### Production angle

Isolation is a correctness decision. Payment, inventory, and ledger flows usually need stronger protection than dashboards or reporting queries.

#### Traps / caveats

- `@Transactional` does not imply Serializable.
- Database defaults differ.
- Higher isolation does not remove the need for retry handling.

#### Optional Anki

Q: What is the trade-off of higher isolation?
A: More correctness guarantees, but usually more conflicts, locking, latency, or retries.

</details>

<a id="tx-iso-002"></a>

<details>
<summary><strong>TX-ISO-002. How do dirty reads, non-repeatable reads, phantom reads, lost updates, and write skew differ?</strong></summary>

#### Short answer

They are different ways concurrent transactions can observe or create inconsistent results.

#### Interview answer

A dirty read sees uncommitted data. A non-repeatable read sees the same row change between reads. A phantom read sees new matching rows appear. A lost update overwrites another transaction's change. Write skew happens when concurrent transactions each make a valid local decision but together violate an invariant.

#### Deep dive

Lost update and write skew are especially important for backend systems because they can silently corrupt business state without obvious exceptions.

#### Production angle

Examples include overselling inventory, double booking, duplicate order creation, and two doctors going off-call because each transaction sees the other still on-call.

#### Traps / caveats

- Not every anomaly is prevented by every "repeatable read" implementation.
- Lost updates often need optimistic locking, explicit locks, or atomic SQL updates.
- Write skew often requires constraints, Serializable isolation, or careful locking.

#### Optional Anki

Q: What is a lost update?
A: Two transactions update the same logical data and one overwrites the other's change.

</details>

<a id="tx-iso-003"></a>

<details>
<summary><strong>TX-ISO-003. Which anomalies can still happen at Read Committed?</strong></summary>

#### Short answer

Read Committed prevents dirty reads but can still allow non-repeatable reads, phantoms, lost updates, and write skew depending on the operation.

#### Interview answer

At Read Committed, each statement usually sees only committed data, but different statements inside the same transaction may see different committed snapshots. That means decisions based on a previous read can become stale.

#### Deep dive

Read Committed is often a good default for throughput, but correctness must be protected with constraints, conditional updates, locks, optimistic version checks, or retries.

#### Production angle

Common bugs include checking available stock and then inserting a reservation, or checking uniqueness in application code without a unique constraint.

#### Traps / caveats

- "Committed data only" does not mean "repeatable business decision."
- Read Committed can be safe when the database enforces the invariant.
- Application-level checks alone are weak under concurrency.

#### Optional Anki

Q: What does Read Committed usually prevent?
A: Dirty reads, but not all concurrency anomalies.

</details>

<a id="tx-iso-004"></a>

<details>
<summary><strong>TX-ISO-004. Why does Repeatable Read not mean exactly the same thing in every database?</strong></summary>

#### Short answer

The SQL names are standardized, but database implementations differ.

#### Interview answer

One database may implement Repeatable Read with snapshot behavior, another may use locking or gap locks, and each can allow or prevent different anomalies. For example, PostgreSQL Repeatable Read and MySQL InnoDB Repeatable Read are not identical.

#### Deep dive

This matters when moving applications between databases or relying on vendor-specific behavior such as gap locks, snapshot isolation, or phantom prevention.

#### Production angle

Do not assume a concurrency test that passed on one database proves correctness on another. Test isolation-sensitive logic against the real target database.

#### Traps / caveats

- H2 tests can hide real database behavior.
- Documentation matters for exact isolation semantics.
- Framework isolation enums are not a full portability guarantee.

#### Optional Anki

Q: Why is Repeatable Read database-specific?
A: Different databases implement isolation using different snapshot and locking mechanisms.

</details>

<a id="tx-iso-005"></a>

<details>
<summary><strong>TX-ISO-005. What does Serializable isolation guarantee, and what does it cost?</strong></summary>

#### Short answer

Serializable makes concurrent transactions behave as if they executed one at a time, but it can increase conflicts and retries.

#### Interview answer

Serializable is the strongest common isolation level. It prevents many anomalies by ensuring the final result is equivalent to some serial order. The cost is lower concurrency, more blocking or serialization failures, and a need for retry logic.

#### Deep dive

Modern databases may implement Serializable with predicate locks, SSI, range locks, or other mechanisms. The application still must handle retryable failures correctly.

#### Production angle

Serializable is useful for small, critical sections with complex invariants, but using it everywhere can hurt throughput and create operational surprises.

#### Traps / caveats

- Serializable failures are expected under contention.
- Retry code must be idempotent at the command boundary.
- Serializable does not make external side effects transactional.

#### Optional Anki

Q: What is the main cost of Serializable isolation?
A: More conflicts, blocking, or retries under concurrent load.

</details>

<a id="tx-iso-006"></a>

<details>
<summary><strong>🧠 TX-ISO-006. How is Snapshot Isolation different from Serializable isolation?</strong></summary>

#### Short answer

Snapshot Isolation gives a transaction a stable snapshot, but it may still allow anomalies such as write skew.

#### Interview answer

Under Snapshot Isolation, a transaction reads from a consistent snapshot and usually detects direct write conflicts. Serializable isolation goes further: it prevents outcomes that could not be produced by any serial execution.

#### Deep dive

Snapshot Isolation is very useful because readers and writers can often proceed without blocking each other. The trade-off is that independent writes based on the same old snapshot can still violate cross-row or cross-table invariants.

#### Production angle

If two transactions both check "at least one approver remains" and update different rows, Snapshot Isolation may allow both updates unless constraints or Serializable isolation prevent it.

#### Traps / caveats

- A stable snapshot does not mean all business invariants are safe.
- Direct write conflicts are easier to catch than predicate-based conflicts.
- Database product names may not map cleanly to the theory terms.

#### Optional Anki

Q: What anomaly can Snapshot Isolation allow?
A: Write skew.

</details>

<a id="tx-iso-007"></a>

<details>
<summary><strong>TX-ISO-007. What is a serialization failure, and why should applications usually retry it?</strong></summary>

#### Short answer

A serialization failure means the database rejected a transaction because it could not safely serialize concurrent work.

#### Interview answer

The database detects that committing the transaction would break the isolation guarantee, so it aborts one transaction. Retrying the whole transaction is usually correct because the next attempt reads a newer state and may succeed.

#### Deep dive

Retry must start from the transaction boundary, not from the failed SQL statement only. The application should avoid side effects inside the retried block or make them idempotent.

#### Production angle

Serialization failures are normal in high-contention flows. Alerting should distinguish occasional retryable conflicts from a sudden spike caused by a design or load problem.

#### Traps / caveats

- Retrying inside the same failed transaction does not work.
- Retrying non-idempotent commands can duplicate work.
- Backoff and max-attempt limits are important.

#### Optional Anki

Q: How should a service handle a serialization failure?
A: Roll back and retry the whole transaction if the command is safe to retry.

</details>

<a id="tx-iso-008"></a>

<details>
<summary><strong>TX-ISO-008. How is a deadlock different from a serialization failure?</strong></summary>

#### Short answer

A deadlock is a lock cycle; a serialization failure is an isolation conflict.

#### Interview answer

In a deadlock, transaction A waits for B while B waits for A, so the database aborts one. In a serialization failure, the database aborts a transaction because concurrent reads and writes cannot be ordered safely under the chosen isolation level.

#### Deep dive

Both are usually retryable, but the root causes differ. Deadlocks often suggest inconsistent lock ordering or long lock holding. Serialization failures may be expected under Serializable isolation.

#### Production angle

Deadlock fixes often include consistent update order, smaller transactions, proper indexes, and fewer wide locks. Serialization fixes often include retry policy and contention reduction.

#### Traps / caveats

- Do not blindly retry forever.
- Deadlocks can happen even with simple code under load.
- Log enough context to know which rows or operations were involved.

#### Optional Anki

Q: What is a deadlock?
A: A cycle where transactions wait on locks held by each other.

</details>

<a id="tx-iso-009"></a>

<details>
<summary><strong>TX-ISO-009. How would you choose an isolation level for money transfer and reporting use cases?</strong></summary>

#### Short answer

Money transfer needs correctness-first protection; reporting usually favors consistent-enough reads with lower impact.

#### Interview answer

For money transfer, I would rely on constraints, row locks or optimistic locking, atomic SQL, and possibly stronger isolation for critical invariants. For reporting, Read Committed or a stable read snapshot is often enough, especially if stale data is acceptable.

#### Deep dive

The right answer depends on the invariant. Moving money between two accounts must avoid lost updates and partial state. A dashboard can usually tolerate slightly stale data but should avoid blocking production writes.

#### Production angle

Critical flows should be tested under concurrency. Reporting should avoid long transactions that hold snapshots and harm cleanup.

#### Traps / caveats

- Do not solve money transfer correctness with Java `synchronized`.
- Reporting transactions can still be harmful if they run too long.
- "Use Serializable" is not enough without retry design.

#### Optional Anki

Q: What isolation style fits money transfer?
A: Correctness-first: constraints, locks or optimistic locking, and retry-aware stronger isolation when needed.

</details>

<a id="tx-iso-010"></a>

<details>
<summary><strong>TX-ISO-010. How can replica reads violate read-your-writes expectations?</strong></summary>

#### Short answer

A replica may lag behind the primary, so a user can write data and then read from a replica that has not received it yet.

#### Interview answer

Read-your-writes means after I create or update something, my next read should see it. If read-only transactions are routed to replicas, replication lag can break that expectation.

#### Deep dive

This is not usually a transaction isolation issue inside one database connection. It is a topology and routing issue: writes go to primary, reads may go elsewhere.

#### Production angle

User flows often need primary reads after writes, session consistency, sticky routing, lag-aware routing, or explicit "pending" UI states.

#### Traps / caveats

- `readOnly = true` can trigger replica routing in some systems.
- Tests with one database will not expose replica lag.
- A retry may still hit the same stale replica.

#### Optional Anki

Q: Why can replica reads break read-your-writes?
A: The replica may lag behind the primary and not contain the latest committed write yet.

</details>

<a id="tx-iso-011"></a>

<details>
<summary><strong>TX-ISO-011. How can unique constraints prevent some concurrency anomalies?</strong></summary>

#### Short answer

Unique constraints let the database reject duplicate states even when concurrent requests race.

#### Interview answer

If two requests both check "does this order number exist?" and both see no row, application checks can race. A unique constraint on the order number makes the database the final authority and allows one insert to succeed while the other fails.

#### Deep dive

Constraints are often better than application-level locks because they protect all writers, including other services, scripts, imports, and manual operations.

#### Production angle

Use unique constraints for idempotency keys, business identifiers, usernames, processed message IDs, and "one active record" rules when the model supports it.

#### Traps / caveats

- You still need to handle duplicate-key exceptions.
- Constraints do not replace all business logic.
- Partial or composite unique indexes may be needed for real rules.

#### Optional Anki

Q: Why are unique constraints important under concurrency?
A: They let the database reject duplicate states even when application checks race.

</details>

<a id="tx-iso-012"></a>

<details>
<summary><strong>TX-ISO-012. How can `SELECT FOR UPDATE` help prevent lost updates?</strong></summary>

#### Short answer

It locks selected rows so competing transactions cannot update them until the current transaction finishes.

#### Interview answer

If a service reads a row, makes a decision, and writes it back, another transaction could change the row in between. `SELECT FOR UPDATE` prevents that by taking a row lock during the transaction.

#### Deep dive

It is useful when the application must read current state and then perform dependent updates. Alternatives include atomic `UPDATE ... WHERE ...`, optimistic locking, constraints, or Serializable isolation.

#### Production angle

Use it carefully on narrow indexed queries. Locking too many rows or locking in inconsistent order can reduce throughput or cause deadlocks.

#### Traps / caveats

- The lock lasts until transaction end.
- It does not protect rows that were not selected.
- Missing indexes can make locking much wider or slower than expected.

#### Optional Anki

Q: What does `SELECT FOR UPDATE` do?
A: It locks selected rows for update until the transaction ends.

</details>

<a id="tx-iso-013"></a>

<details>
<summary><strong>TX-ISO-013. How would you explain isolation anomalies with a concrete order or payment example?</strong></summary>

#### Short answer

Use a small concurrent story where two transactions make decisions from stale or conflicting data.

#### Interview answer

For example, two users try to buy the last item. Both read stock = 1. Both create an order and decrement stock. If nothing protects the invariant, the system oversells. That can be a lost update or check-then-act race depending on the implementation.

#### Deep dive

A good explanation names the invariant, the concurrent steps, the bad final state, and the mitigation: unique constraint, conditional update, row lock, optimistic version, or stronger isolation.

#### Production angle

Interviewers want to see that you can move from theory to a production-safe design.

#### Traps / caveats

- Do not only define anomaly names.
- Always identify what invariant was violated.
- Pick a mitigation that actually protects the data under concurrency.

#### Optional Anki

Q: What makes a good isolation anomaly example?
A: A clear invariant, concurrent steps, bad final state, and a concrete prevention strategy.

</details>
