# Locking and transactional consistency patterns

---

<a id="tx-lock-001"></a>

<details>
<summary><strong>TX-LOCK-001. When is optimistic locking better than pessimistic locking, and vice versa?</strong></summary>

#### Short answer

Optimistic locking fits rare conflicts; pessimistic locking fits high-contention or must-not-race critical sections.

#### Interview answer

Optimistic locking lets transactions proceed and detects conflicts at update time, usually with a version column. Pessimistic locking locks data before changing it, preventing other transactions from modifying it until the lock is released.

#### Deep dive

Optimistic locking scales well when conflicts are uncommon. Pessimistic locking can be simpler when conflicts are frequent or the cost of retrying is high.

#### Production angle

Use optimistic locking for editing records or low-contention state. Use pessimistic locking for inventory claims, queue row claims, or financial state transitions when you must serialize access.

#### Traps / caveats

- Pessimistic locks can deadlock or reduce throughput.
- Optimistic locking needs conflict handling.
- Versioning must cover the actual invariant.

#### Optional Anki

Q: When is optimistic locking best?
A: When conflicts are uncommon and retry or user conflict handling is acceptable.

</details>

<a id="tx-lock-002"></a>

<details>
<summary><strong>TX-LOCK-002. How can version columns prevent lost updates?</strong></summary>

#### Short answer

They make updates conditional on the version read earlier.

#### Interview answer

A transaction reads row version 5. When it updates, the SQL includes `WHERE id = ? AND version = 5`. If another transaction already updated the row to version 6, this update affects zero rows and the application detects a conflict.

#### Deep dive

This prevents silent overwrites. It does not block readers and does not require holding locks while the user or application computes the change.

#### Production angle

Version columns are common for JPA aggregates, admin screens, and APIs where concurrent edits should be detected.

#### Traps / caveats

- Blind automatic retry may overwrite newer intent.
- Every update path must respect the version.
- Some bulk updates bypass ORM version checks.

#### Optional Anki

Q: How does a version column prevent lost updates?
A: Updates succeed only if the stored version still matches the version that was read.

</details>

<a id="tx-lock-003"></a>

<details>
<summary><strong>TX-LOCK-003. When would you use `SELECT FOR UPDATE`?</strong></summary>

#### Short answer

Use it when a transaction must read current rows and then safely update decisions based on them.

#### Interview answer

`SELECT FOR UPDATE` locks selected rows until the transaction ends. It is useful for reserving inventory, claiming a row, updating account balances, or preventing another transaction from changing a row between read and write.

#### Deep dive

It should be used with selective indexed queries and consistent lock ordering. Alternatives include atomic updates, optimistic locking, or unique constraints.

#### Production angle

It can fix correctness bugs but also introduce contention, lock waits, and deadlocks if used broadly.

#### Traps / caveats

- The lock scope depends on the query and database.
- It does not lock rows that do not yet exist.
- The lock is held until transaction completion.

#### Optional Anki

Q: What is the purpose of `SELECT FOR UPDATE`?
A: To lock selected rows so a transaction can safely make dependent updates.

</details>

<a id="tx-lock-004"></a>

<details>
<summary><strong>🧠 TX-LOCK-004. How can `SKIP LOCKED` be used for worker queues?</strong></summary>

#### Short answer

Workers can select unlocked jobs, skip rows already claimed by other workers, and process work concurrently.

#### Interview answer

A worker transaction selects pending jobs `FOR UPDATE SKIP LOCKED`, marks them claimed, commits, and processes them. Other workers skip the locked rows instead of blocking.

#### Deep dive

This pattern can scale simple database-backed queues, but it needs retry, visibility timeout, status transitions, and cleanup for crashed workers.

#### Production angle

It is useful for internal jobs and migrations, but Kafka or a real queue may be better for high-throughput event processing.

#### Traps / caveats

- Rows can starve if ordering is not handled.
- Do not hold locks while doing slow external work.
- Failed workers need a recovery mechanism.

#### Optional Anki

Q: What does `SKIP LOCKED` allow?
A: It lets workers skip rows locked by other transactions instead of waiting.

</details>

<a id="tx-lock-005"></a>

<details>
<summary><strong>TX-LOCK-005. How do unique constraints and upserts prevent check-then-insert races?</strong></summary>

#### Short answer

They let the database atomically enforce uniqueness instead of relying on a separate read check.

#### Interview answer

The unsafe pattern is "check if row exists, then insert." Two transactions can both see no row and both insert. A unique constraint makes one insert fail, and an upsert can turn the race into a deterministic insert-or-update operation.

#### Deep dive

Upsert is useful for idempotency keys, counters, deduplication, and first-writer-wins behavior. The exact syntax and semantics are database-specific.

#### Production angle

Prefer database-enforced uniqueness for critical business identifiers and idempotency records.

#### Traps / caveats

- Always handle duplicate-key exceptions.
- Upsert can hide unintended overwrites if update logic is careless.
- The unique constraint must match the actual business rule.

#### Optional Anki

Q: What is wrong with check-then-insert?
A: Concurrent transactions can both pass the check before either inserts.

</details>

<a id="tx-lock-006"></a>

<details>
<summary><strong>TX-LOCK-006. How would you prevent two workers from processing the same record?</strong></summary>

#### Short answer

Use an atomic claim operation protected by a lock, status update, or unique processing record.

#### Interview answer

A common approach is to select pending rows with `FOR UPDATE SKIP LOCKED`, mark them `IN_PROGRESS`, commit the claim, then process. Another option is an atomic `UPDATE ... WHERE status = 'PENDING'` that returns only successfully claimed rows.

#### Deep dive

The system also needs recovery for workers that crash after claiming. That usually means timestamps, leases, retry counts, and dead-letter handling.

#### Production angle

Worker concurrency bugs create duplicate charges, duplicate emails, or inconsistent workflow state.

#### Traps / caveats

- Do not hold a DB lock during long processing unless it is truly short.
- Claims need expiration or manual recovery.
- Processing itself should still be idempotent.

#### Optional Anki

Q: What is the core idea of safe worker claiming?
A: Make claim transition atomic so only one worker owns a record.

</details>

<a id="tx-lock-007"></a>

<details>
<summary><strong>TX-LOCK-007. How would you implement a safe money transfer between two accounts?</strong></summary>

#### Short answer

Use one transaction, lock or conditionally update both accounts, enforce invariants, and write an audit/ledger record.

#### Interview answer

I would debit and credit in a single transaction, lock accounts in a deterministic order, check sufficient funds, update balances, and insert ledger entries. For higher correctness, a ledger-based model is better than only mutable balances.

#### Deep dive

Consistent lock ordering prevents deadlocks. Constraints and idempotency keys protect against duplicate transfer commands.

#### Production angle

Money movement needs auditability, idempotency, reconciliation, and clear handling of retryable failures.

#### Traps / caveats

- Do not update accounts in arbitrary order.
- Do not call external payment systems inside the DB transaction without a workflow model.
- Avoid silent balance overwrite bugs.

#### Optional Anki

Q: How do you reduce deadlocks in account transfer?
A: Lock accounts in a consistent deterministic order.

</details>

<a id="tx-lock-008"></a>

<details>
<summary><strong>TX-LOCK-008. How do consistent lock ordering and short transactions reduce deadlocks?</strong></summary>

#### Short answer

They reduce circular waits and shorten the time locks are held.

#### Interview answer

Deadlocks happen when transactions hold locks and wait for each other in a cycle. If every transaction locks resources in the same order, cycles are much less likely. Keeping transactions short also reduces the overlap window.

#### Deep dive

Indexes matter because slow scans can hold locks longer or lock more rows than expected.

#### Production angle

When deadlocks occur, inspect the conflicting statements, resource order, transaction duration, and query plans.

#### Traps / caveats

- Deadlocks can still happen; retry handling is required.
- Consistent ordering must be applied across all code paths.
- Long non-SQL work inside transactions increases risk.

#### Optional Anki

Q: Why does lock ordering reduce deadlocks?
A: It prevents transactions from waiting on each other in opposite resource order.

</details>

<a id="tx-lock-009"></a>

<details>
<summary><strong>TX-LOCK-009. Why is database-level locking usually better than `synchronized` for shared database state?</strong></summary>

#### Short answer

Database locks protect the data for all application instances and writers.

#### Interview answer

Java `synchronized` only protects threads inside one JVM. It does not protect other service instances, other processes, scripts, or direct database writes. Database locking and constraints protect the shared data where it lives.

#### Deep dive

Application-level locks can be useful for local memory state, but database state should usually be guarded by database mechanisms.

#### Production angle

In horizontally scaled systems, relying on JVM locks for database correctness breaks as soon as there is more than one instance.

#### Traps / caveats

- Distributed locks also need careful failure handling.
- Database locks can still hurt throughput.
- Use constraints where possible instead of procedural locking.

#### Optional Anki

Q: Why is `synchronized` insufficient for DB state?
A: It only protects one JVM, not all writers to the database.

</details>

<a id="tx-lock-010"></a>

<details>
<summary><strong>TX-LOCK-010. How would you choose between constraints, explicit locks, optimistic locking, and Serializable isolation?</strong></summary>

#### Short answer

Use the simplest mechanism that reliably protects the invariant under expected contention.

#### Interview answer

Use constraints for hard data rules. Use optimistic locking when conflicts are rare. Use explicit locks when a read-then-write decision must be serialized. Use Serializable when the invariant is complex and cannot be easily protected with targeted locks or constraints.

#### Deep dive

These mechanisms can be combined. For example, idempotency may use a unique constraint plus transactional insert; account transfer may use locks plus ledger constraints.

#### Production angle

The choice affects throughput, retry behavior, operational complexity, and debugging.

#### Traps / caveats

- Do not choose locks for everything.
- Do not rely only on application checks.
- Serializable still requires retry logic.

#### Optional Anki

Q: What should guide consistency mechanism choice?
A: The invariant, contention level, and operational cost.

</details>

<a id="tx-lock-011"></a>

<details>
<summary><strong>TX-LOCK-011. How can idempotency keys and unique constraints enforce transactional command safety?</strong></summary>

#### Short answer

Store the idempotency key transactionally with the command result and enforce uniqueness.

#### Interview answer

When a request arrives with an idempotency key, insert a record for that key in the same transaction as the business operation. A unique constraint prevents two concurrent requests with the same key from both executing.

#### Deep dive

The stored record can contain status and response data. A retry can return the original result instead of repeating the operation.

#### Production angle

This is critical for payment, order creation, and any API where clients may retry after timeouts.

#### Traps / caveats

- The key scope matters: user, endpoint, tenant, and operation.
- Store enough result data to handle retries consistently.
- Expiration and cleanup must not break active retry windows.

#### Optional Anki

Q: How do idempotency keys prevent duplicate commands?
A: A unique transactional record ensures the same command key is processed once.

</details>
