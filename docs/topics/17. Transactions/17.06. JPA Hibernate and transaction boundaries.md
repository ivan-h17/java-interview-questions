# JPA/Hibernate and transaction boundaries

---

<a id="tx-jpa-001"></a>

<details>
<summary><strong>TX-JPA-001. How is the JPA persistence context scoped in a typical Spring transaction?</strong></summary>

#### Short answer

In typical Spring JPA usage, one transaction has one persistence context bound to it.

#### Interview answer

The persistence context tracks managed entities loaded or persisted during the transaction. Within that context, the same entity identity maps to the same managed object instance.

#### Deep dive

The persistence context enables first-level caching, dirty checking, cascading, and delayed SQL execution. It is synchronized with the database during flush and commit.

#### Production angle

Understanding the scope helps explain stale managed entities, memory usage in batch jobs, lazy loading behavior, and why SQL may be delayed.

#### Traps / caveats

- The persistence context is not a distributed cache.
- Large transactions can accumulate many managed entities.
- Managed object state can differ from committed database state until flush/commit.

#### Optional Anki

Q: What does the JPA persistence context track?
A: Managed entities and their changes within a unit of work.

</details>

<a id="tx-jpa-002"></a>

<details>
<summary><strong>TX-JPA-002. How do dirty checking, flush, and commit differ?</strong></summary>

#### Short answer

Dirty checking detects changes, flush sends SQL, and commit finalizes the transaction.

#### Interview answer

Hibernate tracks managed entities. If a field changes, dirty checking notices it. Flush synchronizes those changes to the database with SQL, but the transaction is still not committed until commit succeeds.

#### Deep dive

Flush can happen before commit, such as before certain queries. Commit may also trigger flush. A flushed change can still be rolled back if the transaction fails.

#### Production angle

SQL errors can appear at flush time or commit time, not necessarily where the entity was modified.

#### Traps / caveats

- Flush is not commit.
- Dirty checking only applies to managed entities.
- Large dirty persistence contexts can create unexpected SQL bursts.

#### Optional Anki

Q: Is flush the same as commit?
A: No. Flush sends SQL, but commit makes the transaction durable.

</details>

<a id="tx-jpa-003"></a>

<details>
<summary><strong>TX-JPA-003. When can Hibernate flush before transaction commit?</strong></summary>

#### Short answer

Hibernate may flush before queries or when the flush mode requires synchronization.

#### Interview answer

Hibernate flushes before commit, but it can also flush earlier to make query results consistent with pending changes. For example, a JPQL query may trigger a flush so it sees data that would affect the query.

#### Deep dive

Flush behavior depends on flush mode, query type, transaction state, and provider behavior. Native queries and bulk operations can have additional caveats.

#### Production angle

An innocent-looking read query can trigger writes and expose constraint violations earlier than expected.

#### Traps / caveats

- SQL may execute before the end of the method.
- Flush can happen even if code looks read-only.
- Bulk operations can bypass the persistence context.

#### Optional Anki

Q: Why can a query trigger flush?
A: Hibernate may need database state to reflect pending changes before executing the query.

</details>

<a id="tx-jpa-004"></a>

<details>
<summary><strong>TX-JPA-004. How can `readOnly = true` interact with Hibernate flush mode and dirty checking?</strong></summary>

#### Short answer

It may reduce flushing or dirty checking work, depending on Spring and Hibernate configuration.

#### Interview answer

For read-only transactions, Spring/Hibernate may use a flush mode that avoids automatic flushing. This can improve performance for read paths, but it does not mean entity mutations are a valid design.

#### Deep dive

If code modifies a managed entity in a read-only transaction, the in-memory object can still change. Whether SQL is flushed depends on provider behavior and configuration.

#### Production angle

Use read-only transactions to document read paths and reduce overhead, not to enforce security or business rules.

#### Traps / caveats

- In-memory changes can confuse later code in the same persistence context.
- Joining an existing write transaction may ignore read-only intent.
- Do not rely on read-only as a write prevention guarantee.

#### Optional Anki

Q: What can `readOnly = true` change in Hibernate?
A: It may adjust flush behavior and reduce dirty checking overhead.

</details>

<a id="tx-jpa-005"></a>

<details>
<summary><strong>TX-JPA-005. How is `LazyInitializationException` related to transaction boundaries and Open Session in View?</strong></summary>

#### Short answer

It happens when lazy data is accessed after the persistence context is closed.

#### Interview answer

Lazy associations need an active persistence context to load. If a service returns an entity and the web layer accesses a lazy relation after the transaction closes, Hibernate can throw `LazyInitializationException`.

#### Deep dive

Open Session in View keeps the persistence context open into the web layer. It hides lazy loading errors but can cause SQL during rendering and blur transaction boundaries.

#### Production angle

Prefer fetching what the use case needs inside the service and returning DTOs or well-shaped responses.

#### Traps / caveats

- OSIV can hide N+1 queries.
- Lazy loading during serialization is risky.
- Adding `@Transactional` everywhere is not a clean fix.

#### Optional Anki

Q: Why does `LazyInitializationException` happen?
A: Lazy data is accessed without an open persistence context.

</details>

<a id="tx-jpa-006"></a>

<details>
<summary><strong>TX-JPA-006. Why is keeping a transaction open during JSON serialization dangerous?</strong></summary>

#### Short answer

Serialization can trigger lazy loading, long transactions, and unpredictable database access.

#### Interview answer

If entities are serialized while the transaction is open, JSON serialization may walk lazy associations and execute queries. This can extend transaction duration and produce N+1 queries outside the intended service logic.

#### Deep dive

Serialization is presentation work, not business persistence work. It should not decide what SQL runs.

#### Production angle

Under load, this can cause slow endpoints, connection pool pressure, lock duration growth, and unstable response shapes.

#### Traps / caveats

- Bidirectional entity graphs can recurse or explode response size.
- Lazy loading can happen after service logic appears finished.
- DTO mapping inside the service boundary is usually safer.

#### Optional Anki

Q: Why avoid serializing entities inside a transaction?
A: Serialization can trigger hidden lazy loads and extend transaction duration.

</details>

<a id="tx-jpa-007"></a>

<details>
<summary><strong>TX-JPA-007. How does optimistic locking with `@Version` work, and how should `OptimisticLockException` be handled?</strong></summary>

#### Short answer

`@Version` detects concurrent updates by checking that the row version has not changed.

#### Interview answer

When Hibernate updates a versioned entity, it includes the current version in the update condition and increments it. If another transaction already changed the row, the update affects no rows and Hibernate throws an optimistic locking exception.

#### Deep dive

Optimistic locking is good when conflicts are uncommon. It avoids holding locks while users or services think, but requires conflict handling.

#### Production angle

Handle conflicts with retry, merge, or a user-facing "data changed, reload" response depending on the use case.

#### Traps / caveats

- Blind retry can overwrite a user's intent.
- It protects versioned rows, not arbitrary aggregates unless modeled correctly.
- Long conversations need careful UX.

#### Optional Anki

Q: What does `@Version` protect against?
A: Lost updates on versioned entities.

</details>

<a id="tx-jpa-008"></a>

<details>
<summary><strong>TX-JPA-008. Why should external service calls usually not happen inside a JPA transaction?</strong></summary>

#### Short answer

They keep the database transaction open while waiting on an unreliable remote system.

#### Interview answer

External calls can be slow, fail, or time out. If they happen inside a transaction, the service holds a connection, locks, and persistence context state while doing non-database work.

#### Deep dive

External side effects also cannot be rolled back with the database. If the remote call succeeds but the DB transaction rolls back, state diverges.

#### Production angle

Move remote calls before or after the transaction when possible, or use outbox/workflow patterns when reliability matters.

#### Traps / caveats

- Payment calls are not part of your DB transaction.
- Timeouts can create ambiguous outcomes.
- Retrying can duplicate external effects without idempotency.

#### Optional Anki

Q: Why avoid remote calls inside a DB transaction?
A: They extend transaction duration and are not rolled back with the database.

</details>

<a id="tx-jpa-009"></a>

<details>
<summary><strong>TX-JPA-009. How can N+1 queries or a large persistence context increase transaction duration?</strong></summary>

#### Short answer

They add many SQL calls or many managed entities while the transaction remains open.

#### Interview answer

N+1 turns one logical read into many database round trips. A large persistence context increases dirty checking, memory use, and flush cost. Both make the transaction longer.

#### Deep dive

Longer transactions hold connections longer and may hold locks or snapshots longer. Performance problems become concurrency problems.

#### Production angle

Use fetch joins, entity graphs, projections, pagination, batching, and explicit persistence-context clearing for large jobs.

#### Traps / caveats

- OSIV can hide N+1 until production.
- Large batch imports can run out of memory.
- More eager fetching is not always the answer.

#### Optional Anki

Q: Why does N+1 affect transactions?
A: It extends transaction duration by adding many database round trips.

</details>

<a id="tx-jpa-010"></a>

<details>
<summary><strong>TX-JPA-010. How should large batch imports manage transaction boundaries and persistence-context memory?</strong></summary>

#### Short answer

Process in chunks, commit regularly, and clear the persistence context.

#### Interview answer

A huge import in one transaction holds too much memory, locks, and rollback work. A better design processes batches: validate input, write a chunk, flush, clear, commit, and continue with restartability.

#### Deep dive

Chunk size is a trade-off: too large hurts memory and lock duration; too small adds overhead and may reduce throughput.

#### Production angle

Batch jobs need progress tracking, idempotency, retry strategy, and monitoring.

#### Traps / caveats

- One giant rollback can be expensive.
- Clearing the persistence context detaches entities.
- Partial commits require a recovery model.

#### Optional Anki

Q: How should large JPA imports handle transactions?
A: Use chunked transactions with flush/clear and restartability.

</details>

<details>
<summary><strong>TX-JPA-011. What is the difference between database constraints and JPA validation during a transaction?</strong></summary>

#### Short answer

JPA validation checks objects; database constraints enforce stored data.

#### Interview answer

Bean Validation can catch invalid entity state before SQL, but the database is the final authority for constraints such as uniqueness, foreign keys, not-null, and checks.

#### Deep dive

Validation and constraints complement each other. Validation gives user-friendly errors; constraints protect correctness under concurrency and from all writers.

#### Production angle

Critical invariants should usually be backed by database constraints, not only Java annotations.

#### Traps / caveats

- JPA validation does not prevent concurrent races.
- Constraint violations may appear at flush or commit.
- Other services or scripts can bypass application validation.

#### Optional Anki

Q: Why keep database constraints if JPA validation exists?
A: Database constraints protect stored data under concurrency and from all writers.

</details>
