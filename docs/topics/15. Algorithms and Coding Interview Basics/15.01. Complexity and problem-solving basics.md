# 15.01. Complexity and problem-solving basics

<a id="alg-fund-001"></a>

<details>
<summary><strong>ALG-FUND-001. What is Big O notation, and what does it describe?</strong></summary>

#### Short answer

Big O describes how an algorithm's resource usage grows as input size grows.

#### Interview answer

Big O is a way to talk about growth rate, usually time or memory, independent of machine speed and small constants. For example, `O(n)` grows roughly with input size, while `O(n^2)` grows much faster when input doubles.

In interviews I use it to explain why one approach scales better than another, not as an exact runtime promise.

#### Deep dive

Big O is an upper-bound style notation. In practical interview discussion, it usually means the dominant term after dropping constants and smaller terms.

#### Production angle

Complexity predicts which code may fail when test data becomes production data: nested scans, unbounded sorting, large maps or repeated database-style lookups in memory.

#### Traps / caveats

- `O(1)` does not mean instant.
- Constants still matter for small inputs.
- Worst-case, average-case and amortized behavior may differ.

#### Optional Anki

Q: What does Big O describe?
A: Resource growth as input size grows.

</details>

<details>
<summary><strong>ALG-FUND-002. How do time complexity and space complexity differ?</strong></summary>

#### Short answer

Time complexity measures work done; space complexity measures extra memory used.

#### Interview answer

Time complexity answers "how many operations grow with input size?" Space complexity answers "how much additional memory does the algorithm allocate?" A solution can trade one for the other. For example, Two Sum can be `O(n^2)` time and `O(1)` extra space with nested loops, or `O(n)` time and `O(n)` space with a hash map.

#### Deep dive

Space complexity usually means auxiliary space, not always counting the input itself. Recursion stack space also counts.

#### Production angle

Backend code often trades memory for latency: indexes, maps, caches and precomputed lookup tables can speed up requests but increase heap pressure.

#### Traps / caveats

- Recursion uses stack space.
- Streams and collectors can materialize large structures.
- Lower time complexity may be worse if memory exceeds limits.

#### Optional Anki

Q: What is auxiliary space?
A: Extra memory used by the algorithm beyond the input.

</details>

<details>
<summary><strong>ALG-FUND-003. How do you estimate complexity from loops, nested loops and recursion?</strong></summary>

#### Short answer

Count how often the dominant operation runs as a function of input size.

#### Interview answer

One loop over `n` items is usually `O(n)`. Nested independent loops over the same input are often `O(n^2)`. Two separate loops are still `O(n)`, not `O(2n)` in Big O terms. For recursion, define the recurrence: binary search is `T(n)=T(n/2)+O(1)`, so `O(log n)`; merge sort is `T(n)=2T(n/2)+O(n)`, so `O(n log n)`.

#### Deep dive

Loops that multiply or divide the index often produce logarithmic complexity. Loops over different inputs should be expressed separately, such as `O(n + m)` or `O(n * m)`.

#### Production angle

Many backend performance bugs are accidental nested loops: for every request item, scan every database row, DTO, config rule or permission.

#### Traps / caveats

- Nested loops are not always `O(n^2)` if pointers only move forward.
- Hidden work inside helper methods matters.
- Recursion may revisit the same state unless memoized.

#### Optional Anki

Q: What is a common accidental `O(n^2)` pattern?
A: Calling linear search inside a loop.

</details>

<a id="alg-fund-004"></a>

<details>
<summary><strong>ALG-FUND-004. What is amortized complexity, and where does it appear in Java collections?</strong></summary>

#### Short answer

Amortized complexity is the average cost over a sequence of operations, even if some individual operations are expensive.

#### Interview answer

`ArrayList.add` is amortized `O(1)` because most appends write into free capacity, but sometimes the backing array must grow and copy existing elements. Spread over many appends, the average cost is constant.

`HashMap` has a similar idea: ordinary puts are expected `O(1)`, but resizing and rehashing are occasional expensive operations.

#### Deep dive

Amortized does not mean average over random inputs. It means the total cost of a sequence divided across operations.

#### Production angle

Occasional resize operations can still create latency spikes. Pre-size collections when size is known and large.

#### Traps / caveats

- Amortized `O(1)` does not remove tail latency.
- Resizing large collections creates allocation and copy cost.
- Bad hashing can degrade map behavior.

#### Optional Anki

Q: Why is `ArrayList.add` amortized `O(1)`?
A: Most appends are cheap, but occasional growth cost is spread over many appends.

</details>

<details>
<summary><strong>ALG-FUND-005. How should input constraints influence your choice of algorithm?</strong></summary>

#### Short answer

Constraints tell you which complexity is acceptable and which edge cases matter.

#### Interview answer

If `n` is 100, a simple `O(n^2)` solution may be fine. If `n` is 100,000, it usually is not. Constraints also reveal value ranges: a small integer range can allow counting arrays, while huge or sparse values push you toward hash maps or sorting.

I usually ask about input size, value range, duplicates, ordering, nulls and memory limits before choosing the approach.

#### Deep dive

For multiple inputs, use separate variables. A solution might be good for `n` but bad for `m`, such as scanning all rules for every event.

#### Production angle

Real systems need explicit limits: page size, batch size, payload size, queue depth and timeout.

#### Traps / caveats

- Hidden constraints may appear in tests.
- Value range can matter as much as item count.
- Memory constraints can reject an otherwise fast solution.

#### Optional Anki

Q: First question before optimizing a coding task?
A: What are the input constraints?

</details>

<a id="alg-fund-006"></a>

<details>
<summary><strong>ALG-FUND-006. How do you move from a brute-force solution to an optimized solution?</strong></summary>

#### Short answer

Identify repeated work, then replace it with precomputation, indexing, sorting, pruning or a better data structure.

#### Interview answer

I start with the brute-force idea because it clarifies correctness. Then I ask what work is repeated. If I repeatedly search, I may use a hash map. If I repeatedly compute a range sum, I may use prefix sums. If order helps, I may sort and use two pointers or binary search.

The optimized solution should preserve the same invariant as the brute-force one.

#### Deep dive

Good optimizations usually come from changing access patterns: lookup by key, monotonic movement, divide-and-conquer, or dynamic programming over repeated states.

#### Production angle

This is the same mental model used in service code: add indexes, cache stable data, batch calls, remove repeated serialization or avoid N+1 queries.

#### Traps / caveats

- Do not optimize before understanding correctness.
- Sorting changes order and costs `O(n log n)`.
- Extra memory may be unacceptable.

#### Optional Anki

Q: What is the usual first optimization question?
A: What work am I repeating?

</details>

<details>
<summary><strong>ALG-FUND-007. How do you explain a coding solution before writing code?</strong></summary>

#### Short answer

State the approach, data structures, invariants, complexity and edge cases.

#### Interview answer

I would first restate the problem and assumptions. Then I describe the algorithm step by step, name the data structures, explain why it is correct, and give time and space complexity. Before coding, I mention edge cases like empty input, duplicates, negative numbers, overflow or invalid values.

This lets the interviewer correct assumptions early.

#### Deep dive

A concise dry run on a small example often exposes off-by-one errors before code is written.

#### Production angle

Clear explanation mirrors real engineering: design reviews should make behavior, constraints and trade-offs visible before implementation.

#### Traps / caveats

- Do not jump into code with unclear requirements.
- Do not over-explain obvious syntax.
- Complexity without correctness is incomplete.

#### Optional Anki

Q: What should a pre-code explanation include?
A: Approach, structures, invariant, complexity and edge cases.

</details>

<a id="alg-fund-008"></a>

<details>
<summary><strong>ALG-FUND-008. How do you identify and test edge cases in a coding task?</strong></summary>

#### Short answer

Test boundaries: empty, one element, duplicates, extremes, invalid input and cases that exercise each branch.

#### Interview answer

I derive edge cases from the algorithm's assumptions. If the algorithm uses indexes, test empty and one-element input. If it compares values, test equal values and extremes. If it uses a hash map, test duplicates and missing keys. If it uses arithmetic, test overflow and negative values.

Good tests prove the invariant, not just the happy path.

#### Deep dive

For pointer algorithms, test crossing pointers and minimum valid windows. For graph traversal, test disconnected nodes and cycles.

#### Production angle

Backend failures often come from edge data: empty pages, duplicate IDs, null optional fields, giant payloads or integer boundaries.

#### Traps / caveats

- Do not only test sample input.
- Edge cases depend on the chosen algorithm.
- Invalid input behavior should be explicit.

#### Optional Anki

Q: Good edge cases for index logic?
A: Empty, one element, first element, last element and off-by-one boundaries.

</details>

<details>
<summary><strong>🧠 ALG-FUND-009. How can you argue that an algorithm is correct without writing a formal proof?</strong></summary>

#### Short answer

Use an invariant, explain why it starts true, stays true and gives the right result at the end.

#### Interview answer

For interviews, I do not need a formal proof, but I should explain the key invariant. For example, in a sliding window, the invariant may be "the current window contains only valid characters." In binary search, it may be "the answer is always inside the remaining search range."

Then I show how each step preserves that invariant and why termination produces the answer.

#### Deep dive

Correctness arguments are especially useful for greedy algorithms, binary search boundaries and graph traversal.

#### Production angle

This habit reduces fragile code because the implementation follows a clear contract rather than a pile of conditions.

#### Traps / caveats

- A dry run is not a proof by itself.
- Greedy algorithms need a safety argument.
- Termination must be clear for loops and recursion.

#### Optional Anki

Q: What is an algorithm invariant?
A: A property that remains true through the algorithm and leads to correctness.

</details>
