# 15.08. Recursion, backtracking and dynamic programming basics

---

<a id="alg-dp-001"></a>

<details>
<summary><strong>ALG-DP-001. How do you reason about recursion and base cases?</strong></summary>

#### Short answer

Define the smaller subproblem, the base case and how results combine.

#### Interview answer

For recursion, I ask: what does the function mean, what is the simplest input it can answer directly, and how does it reduce the problem? The base case stops recursion. The recursive case must move toward that base case.

For example, tree depth is base case `null -> 0`, recursive case `1 + max(left, right)`.

#### Deep dive

A clear function contract is more important than tracing every recursive call manually.

#### Production angle

Recursive code is readable for tree-like data, but large or untrusted depth may require an iterative version.

#### Traps / caveats

- Missing base case causes infinite recursion.
- No progress toward base case causes failure.
- Recursion uses stack space.

#### Optional Anki

Q: Three recursion essentials?
A: Function meaning, base case and progress.

</details>

<a id="alg-dp-002"></a>

<details>
<summary><strong>ALG-DP-002. What is the difference between recursion and iteration?</strong></summary>

#### Short answer

Recursion uses function calls to repeat work; iteration uses loops and explicit state.

#### Interview answer

Recursion can express tree, graph and divide-and-conquer logic naturally. Iteration usually gives more direct control over memory and avoids call-stack overflow. Many recursive algorithms can be rewritten with an explicit stack or queue.

The better choice depends on clarity, depth and performance constraints.

#### Deep dive

Java does not guarantee tail-call optimization, so tail-recursive code can still overflow the stack.

#### Production angle

In backend services, prefer iterative traversal or explicit depth limits for user-provided nested data.

#### Traps / caveats

- Recursive code is not automatically slower.
- Iterative code is not automatically clearer.
- Stack depth matters in Java.

#### Optional Anki

Q: Why can recursion be risky in Java?
A: Deep calls can cause `StackOverflowError`.

</details>

<a id="alg-dp-003"></a>

<details>
<summary><strong>ALG-DP-003. What is memoization?</strong></summary>

#### Short answer

Memoization caches results of subproblems so repeated calls are not recomputed.

#### Interview answer

In recursive solutions with overlapping subproblems, memoization stores answers in a map or array keyed by state. If the same state appears again, return the cached result. This can turn exponential recursion into polynomial time.

Classic examples include Fibonacci, grid paths and many DP problems.

#### Deep dive

The key must include every part of the state that affects the answer.

#### Production angle

Memoization resembles caching, so the same concerns apply: key correctness, memory bounds and invalidation.

#### Traps / caveats

- Incomplete keys return wrong answers.
- Unbounded memo maps can grow too much.
- Memoization only helps with repeated states.

#### Optional Anki

Q: Memoization helps when subproblems are what?
A: Repeated or overlapping.

</details>

<a id="alg-dp-004"></a>

<details>
<summary><strong>🧠 ALG-DP-004. What is the basic backtracking pattern?</strong></summary>

#### Short answer

Choose an option, recurse, then undo the choice before trying the next option.

#### Interview answer

Backtracking explores combinations, permutations or constraint-satisfaction states. The usual pattern is: if the current state is complete, record it; otherwise iterate candidates, skip invalid ones, apply a choice, recurse, and undo the choice.

It is DFS over a decision tree.

#### Deep dive

Pruning invalid branches early is what makes backtracking practical for many interview tasks.

#### Production angle

Backtracking is less common in ordinary backend services, but the idea appears in rule search, scheduling and constraint exploration.

#### Traps / caveats

- Forgetting to undo state corrupts later branches.
- Copying state everywhere can be expensive.
- Exponential complexity is common.

#### Optional Anki

Q: Backtracking loop shape?
A: Choose, recurse, undo.

</details>

<a id="alg-dp-005"></a>

<details>
<summary><strong>ALG-DP-005. What makes a problem a dynamic programming problem?</strong></summary>

#### Short answer

It has overlapping subproblems and optimal substructure.

#### Interview answer

Dynamic programming fits when the answer can be built from smaller states and the same states are needed repeatedly. "Optimal substructure" means an optimal answer contains optimal answers to subproblems. "Overlapping subproblems" means caching or tabulation avoids recomputing them.

DP is usually about defining the right state and transition.

#### Deep dive

DP can be top-down with memoization or bottom-up with a table.

#### Production angle

DP is not a daily backend tool, but the thinking helps with cost optimization, planning and stateful calculations.

#### Traps / caveats

- If subproblems do not repeat, memoization may not help.
- Bad state definition makes DP impossible or too large.
- Greedy may be simpler if a safe greedy choice exists.

#### Optional Anki

Q: Two DP signals?
A: Overlapping subproblems and optimal substructure.

</details>

<a id="alg-dp-006"></a>

<details>
<summary><strong>ALG-DP-006. How do you define DP state and transitions?</strong></summary>

#### Short answer

State represents the minimum information needed to answer a subproblem; transition explains how states depend on smaller states.

#### Interview answer

I first define `dp[...]` in plain English. For example, `dp[i]` might mean "best answer using the first `i` elements." Then I decide how to compute it from previous states and what base cases initialize the table.

If the state definition is vague, the code usually becomes wrong.

#### Deep dive

State dimensions often come from position, remaining capacity, previous choice, count or target sum.

#### Production angle

Clear state modeling is also valuable outside DP: workflow state, retry state and aggregation state all need precise definitions.

#### Traps / caveats

- Do not write recurrence before defining state.
- Base cases must match the definition.
- Large state spaces can exceed memory.

#### Optional Anki

Q: First step in DP?
A: Define what each state means.

</details>

<a id="alg-dp-007"></a>

<details>
<summary><strong>🧠 ALG-DP-007. When is dynamic programming overkill for a backend coding interview?</strong></summary>

#### Short answer

DP is overkill when simpler data structures, sorting, greedy logic or direct scanning solve the problem clearly.

#### Interview answer

For most Java backend roles, interview coding tends to favor practical patterns: maps, sets, sorting, two pointers, BFS, heaps and clean code. DP can appear, but complex DP is usually less relevant than writing correct, readable Java under constraints.

I would not force DP unless the problem has repeated states and asks for an optimal/counting result.

#### Deep dive

Simple DP like memoized recursion or one-dimensional tables is worth knowing. Advanced DP optimizations are second-pass material.

#### Production angle

Overly clever algorithms can make code hard to maintain if the real input size is small or constraints are different.

#### Traps / caveats

- Do not avoid DP when it is actually the right tool.
- Do not memorize formulas without state reasoning.
- Communicate complexity and trade-offs.

#### Optional Anki

Q: DP is usually justified by what?
A: Repeated states plus an optimal/counting subproblem structure.

</details>
