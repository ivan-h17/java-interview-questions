# 15.09. Backend-oriented coding tasks and data processing

---

<a id="alg-be-001"></a>

<details>
<summary><strong>ALG-BE-001. How do you process large input without loading everything into memory?</strong></summary>

#### Short answer

Stream, page, chunk or iterate through the data while keeping only bounded state.

#### Interview answer

If input can be large, I avoid `readAll`, huge lists and unbounded collectors. I process records one by one or in batches, keeping only the state needed for the result: counters, a small heap, current aggregate or bounded buffer. If data comes from a database or API, I use pagination or streaming APIs with clear resource ownership.

#### Deep dive

Some tasks require full materialization, such as global sorting. Then I need external sorting, database sorting or explicit size limits.

#### Production angle

This prevents heap pressure, long GC pauses and request timeouts in batch endpoints, imports and report jobs.

#### Traps / caveats

- Streams can still materialize with `toList()` or grouping collectors.
- Database cursors and files must be closed.
- Batch size needs tuning.

#### Optional Anki

Q: Main rule for large input?
A: Keep bounded state instead of loading all data.

</details>

<details>
<summary><strong>ALG-BE-002. How do you deduplicate objects by business key while preserving deterministic order?</strong></summary>

#### Short answer

Use a `LinkedHashMap` keyed by the business key and define the merge policy.

#### Interview answer

I would choose a stable key, such as user ID or normalized email, then insert into a `LinkedHashMap`. It preserves insertion order. If the key already exists, I must decide whether to keep the first value, keep the last, merge fields or reject the duplicate.

That policy is part of correctness, not an implementation detail.

#### Deep dive

For stream code, `Collectors.toMap` needs a merge function and `LinkedHashMap::new` if order matters.

#### Production angle

Deterministic deduplication matters for APIs, audit reports and batch reconciliation.

#### Traps / caveats

- Do not silently hide unexpected data bugs.
- Entity `equals()` may not match business identity.
- `HashMap` order should not be exposed.

#### Optional Anki

Q: Ordered deduplication by key?
A: `LinkedHashMap<BusinessKey, Value>`.

</details>

<a id="alg-be-003"></a>

<details>
<summary><strong>ALG-BE-003. How do you merge multiple sorted lists or streams efficiently?</strong></summary>

#### Short answer

Use a min-heap containing the current item from each sorted source.

#### Interview answer

For `k` sorted lists, put the first element of each list into a `PriorityQueue`. Repeatedly poll the smallest item, output it, and insert the next item from the same source. This produces a merged sorted stream.

Complexity is `O(n log k)`, where `n` is total elements.

#### Deep dive

For only two sorted lists, a two-pointer merge is simpler and `O(n)`.

#### Production angle

K-way merge appears in log merging, paged API aggregation, search shards and sorted export generation.

#### Traps / caveats

- Define tie-breaking for equal keys.
- Avoid loading all streams if sources can be lazy.
- Close resources for exhausted sources.

#### Optional Anki

Q: Data structure for k-way merge?
A: Min-heap / `PriorityQueue`.

</details>

<a id="alg-be-004"></a>

<details>
<summary><strong>ALG-BE-004. How would you implement a simple in-memory rate limiter?</strong></summary>

#### Short answer

Use a per-key counter with a time window, or a token bucket for smoother limiting.

#### Interview answer

For a simple fixed-window limiter, store `(windowStart, count)` per key. On each request, reset if the current time is outside the window, otherwise increment and allow only if count is within the limit. For smoother behavior, a token bucket refills tokens over time and consumes one per request.

The map must be bounded and cleaned up.

#### Deep dive

Use a monotonic time source for elapsed-time calculations where possible, and define behavior at window boundaries.

#### Production angle

In a multi-instance service, local in-memory limiting is per instance. Distributed rate limiting needs shared storage or gateway support.

#### Traps / caveats

- Fixed windows allow boundary bursts.
- Per-key maps can leak memory.
- Thread-safety must be explicit.

#### Optional Anki

Q: Fixed-window rate limiter stores what?
A: Window start and count per key.

</details>

<a id="alg-be-005"></a>

<details>
<summary><strong>ALG-BE-005. How do you design a bounded cache or bounded queue to avoid memory growth?</strong></summary>

#### Short answer

Set a capacity and define what happens when the capacity is reached.

#### Interview answer

For a cache, choose an eviction policy such as LRU, TTL or size-by-weight. For a queue, choose backpressure behavior: block, reject, drop oldest, drop newest or spill to durable storage. The important part is that growth is bounded and observable.

An unbounded cache or queue is a common memory leak pattern.

#### Deep dive

Capacity should match memory budget and workload, not just an arbitrary number.

#### Production angle

Bounded structures protect services during traffic spikes, downstream outages and retry storms.

#### Traps / caveats

- Eviction can drop data if used incorrectly.
- Queue bounds need producer behavior.
- Cache size by entry count may miss large values.

#### Optional Anki

Q: Why avoid unbounded queues?
A: They can convert overload into memory failure.

</details>

<a id="alg-be-006"></a>

<details>
<summary><strong>ALG-BE-006. How do stable ordering and tie-breakers affect paginated results?</strong></summary>

#### Short answer

Pagination needs deterministic order; tie-breakers prevent records from moving unpredictably between pages.

#### Interview answer

If results are ordered only by a non-unique field like `createdAt`, records with the same timestamp can appear in different orders across requests. Add a stable tie-breaker such as ID: `ORDER BY createdAt DESC, id DESC`. For cursor pagination, the cursor should include all ordering fields.

The same idea applies to in-memory sorting.

#### Deep dive

Offset pagination is also sensitive to inserts and deletes between page requests. Keyset pagination can be more stable.

#### Production angle

Unstable pagination causes duplicates, missing records and confusing API behavior.

#### Traps / caveats

- Sorting by timestamp alone is often not deterministic.
- Comparator tie-breakers must match database ordering.
- Cursor fields must be immutable enough for the use case.

#### Optional Anki

Q: Why add ID to timestamp ordering?
A: To make ordering deterministic when timestamps tie.

</details>

<a id="alg-be-007"></a>

<details>
<summary><strong>🧠 ALG-BE-007. How should thread-safety change a shared cache or counter coding task?</strong></summary>

#### Short answer

Shared mutable state needs atomicity, visibility and a clear concurrency strategy.

#### Interview answer

For a shared counter, `int++` is not atomic; use `AtomicInteger`, `LongAdder` or synchronization depending on semantics. For a shared cache, `HashMap` is unsafe under concurrent mutation; use `ConcurrentHashMap`, locks or a real cache library. Compound operations like "check then put" need atomic methods such as `computeIfAbsent` or explicit locking.

#### Deep dive

Thread-safe collections do not make multi-step business logic automatically atomic.

#### Production angle

Concurrency bugs in caches and counters create wrong limits, duplicate work, stale data and rare incidents.

#### Traps / caveats

- `volatile` does not make increments atomic.
- `ConcurrentHashMap` iteration is weakly consistent.
- Eviction plus concurrency is hard to implement correctly.

#### Optional Anki

Q: Is `count++` atomic?
A: No.

</details>

<a id="alg-be-008"></a>

<details>
<summary><strong>🧠 ALG-BE-008. What algorithmic traps appear when code moves from an in-memory task to a backend service?</strong></summary>

#### Short answer

Real services add limits, concurrency, partial failure, persistence, ordering, observability and security concerns.

#### Interview answer

An in-memory algorithm may assume all data fits in memory, runs once, and has one thread. In a backend service, input may be huge, requests run concurrently, retries create duplicates, data lives in a database, and failures happen midway. The algorithm must define bounds, idempotency, transaction behavior, deterministic ordering and monitoring.

#### Deep dive

The right optimization may move work to the database, message broker or cache rather than making Java code more clever.

#### Production angle

This is a key senior signal: connect coding tasks to real failure modes and operational constraints.

#### Traps / caveats

- In-memory uniqueness does not replace database constraints.
- Local cache state is not shared across instances.
- Retrying non-idempotent operations can corrupt data.

#### Optional Anki

Q: Senior backend addition to coding tasks?
A: Discuss limits, concurrency, idempotency and failure modes.

</details>
