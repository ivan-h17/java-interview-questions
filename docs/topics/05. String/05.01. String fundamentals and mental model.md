# 05.01. String fundamentals and mental model

---

<a id="str-fund-001"></a>

<details>
<summary><strong>STR-FUND-001. What is `String` in Java, and what does it represent?</strong></summary>

#### Short answer

`String` is Java's immutable object type for representing text as a sequence of characters.

#### Interview answer

In Java, `String` is a final class in `java.lang` used for textual values such as names, IDs, messages, SQL fragments, JSON fields and HTTP headers. It is not a primitive type. A variable of type `String` holds a reference to a `String` object.

Conceptually, a string represents text, but that text may contain Unicode characters that do not map one-to-one to Java `char` values or to bytes on the wire.

#### Deep dive

`String` exposes many APIs for comparison, searching, slicing, encoding, formatting and conversion. It implements `CharSequence`, `Comparable<String>` and `Serializable`.

A key mental model is to separate three ideas: the Java object, the logical text value and the encoded bytes used for storage or network transfer.

#### Production angle

Strings appear at almost every backend boundary: HTTP, JSON, databases, configuration, logs and security tokens. Many production bugs come from assuming strings are just simple ASCII text.

#### Traps / caveats

- `String` is an object, not a primitive.
- `String.length()` counts UTF-16 code units, not user-visible characters.
- A string is not the same thing as encoded bytes.

#### Optional Anki

Q: What does Java `String` represent?
A: An immutable object representing textual data.

</details>

<a id="str-fund-002"></a>

<details>
<summary><strong>STR-FUND-002. Why is `String` immutable and declared `final`?</strong></summary>

#### Short answer

`String` is immutable and final so text values can be safely shared, cached, interned, used as keys and trusted by security-sensitive APIs.

#### Interview answer

Immutability means a `String` value cannot change after construction. Operations such as `replace`, `substring` or `toLowerCase` return a new string when the value changes.

`String` is also final, so subclasses cannot violate this guarantee. That matters because many platform and application APIs rely on strings for class names, file paths, URLs, system properties, map keys and permissions.

#### Deep dive

If a string value could change, cached hash codes could become invalid, interned literals could be corrupted, and code that validates a path or class name could later use a different value. Being final protects the contract from a malicious or broken subclass.

#### Production angle

This design makes strings safe to pass through layers without defensive copying in most cases. It is one reason strings are common in maps, caches, DTOs and request context.

#### Traps / caveats

- Immutability of the `String` object does not make surrounding data structures immutable.
- Reflection or unsafe tricks are not normal Java code and must not be used as a design argument.
- Immutable strings can still leak secrets because they remain in memory until collected.

#### Optional Anki

Q: Why is `String` final?
A: To preserve its immutability and security-sensitive behavior.

</details>

<a id="str-fund-003"></a>

<details>
<summary><strong>STR-FUND-003. What are the main consequences of `String` immutability for sharing, hashing and the String Pool?</strong></summary>

#### Short answer

Immutable strings can be safely shared, interned and used as hash keys because their contents do not change.

#### Interview answer

Because `String` values are immutable, multiple references can point to the same object without risk that one caller changes the value for another caller. This makes the String Pool practical: literals and interned strings can be shared globally.

Immutability also makes `String` suitable as a `HashMap` key. Once inserted, its equality and hash code remain stable, so lookup keeps working.

#### Deep dive

`String` caches its hash code after computing it. That would be dangerous if the content could change. Immutability also allows APIs to return existing strings or share backing data internally when the implementation can do so safely.

#### Production angle

Stable string values reduce defensive copying and make strings reliable for routing keys, cache keys, map keys and configuration keys. The trade-off is that many transformations allocate new objects.

#### Traps / caveats

- Stable string keys are still vulnerable to bad normalization choices.
- Sharing is safe for correctness, but it can make secret leakage harder to control.
- Interning unbounded user input can create memory pressure.

#### Optional Anki

Q: Why can `String` be shared safely?
A: Its value cannot change after construction.

</details>

<a id="str-fund-004"></a>

<details>
<summary><strong>STR-FUND-004. What would break if `String` were mutable?</strong></summary>

#### Short answer

Hash maps, the String Pool, security checks, class loading, path validation and many APIs would become unsafe or unreliable.

#### Interview answer

If strings were mutable, code could validate one value and later use another. A `HashMap` key could be changed after insertion, making the entry hard to find. Interned literals could be modified globally. Class names, file paths, URLs and permission names could be changed after a security decision.

#### Deep dive

The problem is aliasing: many parts of a program may hold references to the same string. With mutation, any holder could affect all other holders. To remain safe, Java would need defensive copies almost everywhere, which would be expensive and error-prone.

#### Production angle

Mutable identity keys are a common source of subtle production bugs. Java avoids that entire class for strings by making them immutable.

#### Traps / caveats

- `StringBuilder` is mutable; do not use it as if it were a stable string value.
- Immutability protects the string value, not the variable reference. A variable can be reassigned.
- A mutable object containing a string field can still change which string it references.

#### Optional Anki

Q: What breaks if a hash key changes after insertion?
A: The collection may search the wrong bucket and fail to find the entry.

</details>

<details>
<summary><strong>STR-FUND-005. What is the difference between an empty string, a blank string and `null`?</strong></summary>

#### Short answer

`null` means no string object. An empty string is `""` with length zero. A blank string contains only whitespace according to `isBlank()`.

#### Interview answer

`null` is absence of a value and calling instance methods on it causes `NullPointerException`. `""` is a real `String` object with `length() == 0`. A blank string such as `"   "` or a newline-only string has content, but no non-whitespace characters according to `isBlank()`.

#### Deep dive

The distinction matters in validation. A missing optional field, an explicitly empty value and a whitespace-only value may have different business meaning. Java 11 added `isBlank()` to check Unicode whitespace more directly than `trim().isEmpty()`.

#### Production angle

APIs should document whether fields are required, nullable, empty-allowed or blank-allowed. Ambiguity causes broken validation, inconsistent database values and surprising client behavior.

#### Traps / caveats

- `isEmpty()` checks length only.
- `isBlank()` is not the same as `trim().isEmpty()`.
- Converting `null` to `""` can hide a missing required value.

#### Optional Anki

Q: What is the difference between `isEmpty()` and `isBlank()`?
A: `isEmpty()` checks length zero; `isBlank()` checks whether the string contains only whitespace.

</details>

<a id="str-fund-006"></a>

<details>
<summary><strong>STR-FUND-006. How should nullable strings be handled at Java API boundaries?</strong></summary>

#### Short answer

Define the null contract explicitly, validate at boundaries and normalize once where appropriate.

#### Interview answer

A backend API should make it clear whether a string can be `null`, empty or blank. At external boundaries, validate input and convert it into an internal representation with clear meaning. For example, reject missing required fields, trim only when business rules require it, and avoid passing ambiguous raw strings deep into the domain model.

#### Deep dive

For internal Java APIs, annotations such as `@Nullable` and `@NotNull`, Bean Validation and clear method contracts help. `Optional<String>` can be useful as a return type, but it is usually not ideal for fields or method parameters in ordinary DTOs.

#### Production angle

Consistent null handling prevents scattered `NullPointerException`s and inconsistent persistence. It also improves API compatibility because clients learn exactly which values are valid.

#### Traps / caveats

- Do not blindly call `trim()` or lower-case every input; normalization is domain-specific.
- `Optional` does not remove the need for validation.
- `String.valueOf(null)` returns `"null"`, which is rarely the desired domain value.

#### Optional Anki

Q: Where should external string validation usually happen?
A: At the boundary, before raw input spreads into domain code.

</details>

<a id="str-fund-007"></a>

<details>
<summary><strong>STR-FUND-007. What is the difference between character data, binary data and textual representation?</strong></summary>

#### Short answer

Character data is logical text, binary data is bytes, and textual representation is a string form of some value or data.

#### Interview answer

A `String` represents text. A `byte[]` represents raw bytes. Encoding converts text to bytes, and decoding converts bytes to text. A textual representation is when non-text data is expressed as text, for example a UUID, JSON document, Base64 value or decimal number.

#### Deep dive

Confusing these layers causes bugs. Encrypted data, compressed data, image bytes and serialized binary formats should not be treated as strings. If binary data must travel through text-only systems, use an explicit representation such as Base64.

#### Production angle

HTTP, Kafka, databases and files all force boundary decisions: is the payload text, binary, or a text encoding of binary data? The wrong choice can corrupt data or create security issues.

#### Traps / caveats

- Do not use `new String(bytes)` without a charset for protocol data.
- Not every byte sequence is valid text.
- Base64 is an encoding, not encryption.

#### Optional Anki

Q: What converts text to bytes?
A: Character encoding, for example UTF-8.

</details>

<details>
<summary><strong>STR-FUND-008. What production bugs happen when strings are treated as "simple text" only?</strong></summary>

#### Short answer

Common bugs include wrong encodings, bad equality checks, invalid length validation, locale issues, unsafe concatenation and unbounded memory usage.

#### Interview answer

Strings look simple, but backend systems use them for user input, identifiers, logs, SQL, JSON, paths, tokens and cache keys. Bugs happen when code ignores encoding, Unicode normalization, locale-specific case conversion, escaping, validation order or memory cost.

#### Deep dive

Examples: a username fails login because it has a composed Unicode form; a Turkish locale breaks upper-casing; a database limit is in characters or bytes but Java validation uses `length()`; a regex on untrusted input causes latency spikes; a log accidentally stores tokens forever.

#### Production angle

String bugs are often boundary bugs. The safest approach is to define contracts, normalize intentionally, use proper libraries for structured formats and profile before optimizing.

#### Traps / caveats

- ASCII-only tests miss many real-world failures.
- Manual SQL, JSON, HTML or shell command construction is dangerous.
- Small temporary strings can dominate allocation rate in hot paths.

#### Optional Anki

Q: Name three production risks of string handling.
A: Encoding bugs, unsafe escaping/concatenation and memory/allocation pressure.

</details>
