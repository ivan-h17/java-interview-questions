# 05.09. CharSequence, API design and domain modeling

---

<a id="str-type-001"></a>

<details>
<summary><strong>STR-TYPE-001. What is `CharSequence`, and which common classes implement it?</strong></summary>

#### Short answer

`CharSequence` is an interface for readable character sequences. Common implementations include `String`, `StringBuilder`, `StringBuffer` and `CharBuffer`.

#### Interview answer

`CharSequence` provides a small common API: `length()`, `charAt()`, `subSequence()` and `toString()`. `String` implements it as an immutable text value. `StringBuilder` and `StringBuffer` implement it as mutable builders.

#### Deep dive

The interface says very little about mutability, thread-safety, equality or storage. That makes it flexible but weaker than accepting `String` when you need a stable value.

#### Production angle

`CharSequence` is useful for APIs that only need to read characters and want to avoid forcing callers to create a `String`. But for domain values, persistence keys and long-lived storage, copying to `String` is usually safer.

#### Traps / caveats

- Not every `CharSequence` is immutable.
- `CharSequence.equals()` does not define content equality across implementations.
- `subSequence()` may return another mutable or view-like object depending on implementation.

#### Optional Anki

Q: Is every `CharSequence` immutable?
A: No.

</details>

<a id="str-type-002"></a>

<details>
<summary><strong>STR-TYPE-002. When should an API accept `CharSequence` instead of `String`?</strong></summary>

#### Short answer

Accept `CharSequence` when the API only needs to read characters immediately and does not require a stable, immutable value.

#### Interview answer

`CharSequence` is useful for low-level formatting, appending, validation or library APIs that can operate on any readable character sequence. It avoids forcing callers with a `StringBuilder`, `StringBuffer` or `CharBuffer` to convert first.

If the API stores the value, uses it as a key, compares it later or exposes it across threads, accepting `String` or copying to `String` is safer.

#### Deep dive

An API that accepts `CharSequence` inherits weaker guarantees. The input can mutate while being processed if the implementation is mutable and shared.

#### Production angle

For domain models, DTOs, cache keys and persistence values, prefer `String` or a typed value object. For utility methods that only inspect text, `CharSequence` can be appropriate.

#### Traps / caveats

- Do not store a mutable `CharSequence` reference directly.
- Document whether null is allowed.
- Content equality must be handled explicitly.

#### Optional Anki

Q: When is `CharSequence` a good parameter type?
A: When the method only reads characters and does not retain the value.

</details>

<a id="str-type-003"></a>

<details>
<summary><strong>STR-TYPE-003. Why can mutable `CharSequence` implementations cause bugs, and how should you defensively copy them?</strong></summary>

#### Short answer

Mutable implementations can change after validation or storage. Copy them with `toString()` when you need a stable value.

#### Interview answer

If an API accepts `CharSequence` and stores the reference, a caller may pass a `StringBuilder` and mutate it later. The stored value then changes unexpectedly. To defend against that, convert to `String` at the boundary: `this.value = input == null ? null : input.toString()`.

#### Deep dive

This is similar to defensive copying for collections or arrays. Accepting a broad interface is fine, but retaining it requires protecting invariants.

#### Production angle

Mutable text references can break cache keys, audit messages, validation results and asynchronous processing. These bugs are hard to reproduce because the mutation may happen in another layer.

#### Traps / caveats

- `toString()` on a `String` returns the same object, so copying is cheap for already-stable strings.
- Copying does not validate encoding, normalization or allowed content.
- Null handling should be explicit.

#### Optional Anki

Q: How do you defensively copy a `CharSequence` to a stable value?
A: Convert it to `String` with `toString()`.

</details>

<a id="str-coll-001"></a>

<details>
<summary><strong>STR-COLL-001. Why should string keys often be normalized before storing them in a map?</strong></summary>

#### Short answer

Normalization ensures that values considered equivalent by the business map to the same key.

#### Interview answer

Raw strings can differ by case, whitespace, Unicode form or formatting while representing the same logical value. If a map key should be case-insensitive or whitespace-insensitive, normalize once before insertion and lookup.

#### Deep dive

The normalization pipeline must be domain-specific. For a country code, upper-case with `Locale.ROOT` may be correct. For a username, you may need Unicode normalization plus case policy. For a free-form name, normalization may be inappropriate.

#### Production angle

Without consistent key normalization, caches miss, deduplication fails and uniqueness checks behave inconsistently.

#### Traps / caveats

- Normalize both write and read paths.
- Do not use default locale for technical keys.
- Over-normalization can merge distinct business values.

#### Optional Anki

Q: Why normalize map keys?
A: So equivalent business values use the same lookup key.

</details>

<a id="str-coll-002"></a>

<details>
<summary><strong>STR-COLL-002. What are the risks of using raw user input strings as map or cache keys?</strong></summary>

#### Short answer

Raw user strings can be unbounded, inconsistent, attacker-controlled and expensive to store or compare.

#### Interview answer

User input may vary by case, whitespace, Unicode representation or irrelevant formatting. It can also be very long or high-cardinality. If used directly as map or cache keys, it can cause low hit rates, memory growth, denial-of-service risk and inconsistent behavior.

#### Deep dive

Cache keys should usually be structured and bounded: include tenant, purpose, normalized parameters and versioning where needed. Avoid storing raw payloads or secrets in keys.

#### Production angle

A cache keyed by raw request strings can grow without bound under normal traffic or attack. Add size limits, TTLs, metrics and normalization.

#### Traps / caveats

- Key normalization must preserve business meaning.
- Long keys increase memory and hashing cost.
- Keys often appear in metrics and logs, so avoid PII and secrets.

#### Optional Anki

Q: Why are raw request strings bad cache keys?
A: They are often unbounded, inconsistent and high-cardinality.

</details>

<a id="str-coll-003"></a>

<details>
<summary><strong>STR-COLL-003. When would you use an enum or value object instead of a plain string?</strong></summary>

#### Short answer

Use an enum for a closed set of values and a value object when the string has domain rules or behavior.

#### Interview answer

If a field can only be one of a few known values, an enum gives type safety and prevents typos. If a value is still textual but has validation, normalization or meaning, such as `EmailAddress`, `CurrencyCode` or `OrderId`, a value object can protect invariants better than a raw string.

#### Deep dive

Enums are not always good for externally extensible values because adding a new enum constant may require deployment. Value objects are better for values with open sets but strict rules.

#### Production angle

Typed values make APIs clearer, reduce scattered validation and prevent mixing unrelated strings such as user IDs and order IDs.

#### Traps / caveats

- Do not use enums for data that changes frequently outside deployment.
- Value objects should define equality and serialization carefully.
- Avoid wrapping every string without a real invariant.

#### Optional Anki

Q: When is an enum better than a string?
A: When the allowed value set is closed and known.

</details>

<a id="str-coll-004"></a>

<details>
<summary><strong>STR-COLL-004. Why is a stringly typed domain model dangerous?</strong></summary>

#### Short answer

It hides domain meaning and allows invalid or mixed-up values to flow through the system.

#### Interview answer

A stringly typed model represents too many concepts as plain `String`: user ID, tenant ID, email, status, currency and phone number all look the same to the compiler. That makes it easy to pass the wrong value, skip validation or duplicate parsing rules.

#### Deep dive

Good domain types encode invariants at construction. For example, a `CurrencyCode` can enforce ISO-like format and normalization once. A raw string requires every caller to remember the rules.

#### Production angle

Stringly typed models lead to data-quality problems, authorization bugs, invalid persistence state and unclear APIs. Type-safe modeling makes code review easier.

#### Traps / caveats

- Do not over-model throwaway DTO fields.
- Value objects must be easy to serialize and map.
- Domain type boundaries should match real business invariants.

#### Optional Anki

Q: What is stringly typed code?
A: Code that uses raw strings for many distinct domain concepts.

</details>

<a id="str-coll-005"></a>

<details>
<summary><strong>STR-COLL-005. What are the risks of canonicalizing unbounded user input?</strong></summary>

#### Short answer

It can create memory leaks, high-cardinality caches and security issues if the canonical store grows without limits.

#### Interview answer

Canonicalization stores or reuses one representative object for equal values. That is useful for small repeated sets. With unbounded user input, most values may be unique, so the canonicalization map grows continuously and retains data that would otherwise be garbage collected.

#### Deep dive

Canonicalization also has security and privacy implications: canonical values may contain secrets or PII and may live longer than expected.

#### Production angle

If canonicalization is needed, use bounded caches, TTLs, metrics and a clear value domain. Avoid canonicalizing raw request payloads, tokens and free-form text.

#### Traps / caveats

- `intern()` is also canonicalization and has similar risks.
- Weak references do not automatically make the design safe.
- Canonicalization should be justified by measured duplication.

#### Optional Anki

Q: Why is unbounded canonicalization dangerous?
A: It can retain high-cardinality user data indefinitely.

</details>
