# 05.13. Concurrency and production scenarios

---

<a id="str-conc-001"></a>

<details>
<summary><strong>STR-CONC-001. Is `String` thread-safe, and why is it safely shareable between threads?</strong></summary>

#### Short answer

Yes. `String` is thread-safe because it is immutable.

#### Interview answer

A `String` object's content cannot change after construction. That means multiple threads can read and share the same string without synchronization. There is no risk that one thread mutates the string while another reads it.

#### Deep dive

Thread-safe sharing of the string does not make the reference holder thread-safe. If a mutable object has a `String` field and multiple threads update the field, normal concurrency rules still apply.

#### Production angle

Strings are safe to put in immutable DTOs, request context snapshots and configuration objects. Be careful with mutable containers around them.

#### Traps / caveats

- The variable reference can change even though the string cannot.
- `StringBuilder` is not thread-safe.
- Do not synchronize on strings.

#### Optional Anki

Q: Why is `String` safely shareable?
A: Its content is immutable.

</details>

<a id="str-conc-002"></a>

<details>
<summary><strong>STR-CONC-002. Does using `StringBuffer` make a whole multithreaded workflow thread-safe?</strong></summary>

#### Short answer

No. `StringBuffer` synchronizes individual methods, but larger workflows can still need external synchronization or redesign.

#### Interview answer

`StringBuffer` methods are synchronized, so individual calls are protected. But a sequence of operations can still race. For example, checking length and then appending based on that check is not atomic unless the whole sequence is protected.

#### Deep dive

A better design is usually thread confinement: each thread or request uses its own `StringBuilder`. If shared state is truly needed, use a proper concurrency abstraction and synchronize the whole invariant.

#### Production angle

Shared mutable builders are rare in good backend code. They can create mixed output, contention and hard-to-debug races.

#### Traps / caveats

- Method-level synchronization is not workflow-level correctness.
- `StringBuffer` can still be a performance bottleneck.
- Thread-local builders can leak memory if oversized buffers are retained.

#### Optional Anki

Q: What does `StringBuffer` synchronize?
A: Individual methods, not arbitrary multi-step workflows.

</details>

<a id="str-scenario-001"></a>

<details>
<summary><strong>STR-SCENARIO-001. A service returns corrupted characters for non-English users. How would you debug it?</strong></summary>

#### Short answer

Trace the bytes and charset at every boundary: client, HTTP, application decoding, persistence and response encoding.

#### Interview answer

I would reproduce with a known non-ASCII sample and check whether corruption happens on input, storage or output. Then inspect `Content-Type`, request decoding, file/database encoding, JSON handling and response headers. If possible, compare raw bytes before and after each boundary.

#### Deep dive

The bug may be double-encoding, implicit default-charset use, database/client mismatch, bad file import encoding or incorrect logging/display. On Java 17 and earlier the default charset could vary by environment; on Java 18+ it is UTF-8 by default, which can still be wrong for legacy data. Keeping the original bytes helps distinguish storage corruption from rendering problems.

#### Production angle

Add tests with Cyrillic, accented text and emoji. Make charsets explicit and add observability that does not itself corrupt or hide text.

#### Traps / caveats

- ASCII tests will pass.
- Logs may show already-decoded text, not raw bytes.
- The frontend is not always the source of encoding issues.

#### Optional Anki

Q: What is the first debugging question for corrupted text?
A: At which boundary did bytes get decoded or encoded incorrectly?

</details>

<a id="str-scenario-002"></a>

<details>
<summary><strong>STR-SCENARIO-002. A service has high allocation rate and many short-lived strings. How would you debug it?</strong></summary>

#### Short answer

Use allocation profiling or JFR to find where strings are created, then optimize the hot paths.

#### Interview answer

I would check GC metrics and allocation rate, capture a JFR or allocation profile, and identify methods allocating `String` or backing arrays. Common causes are regex splitting, formatting, logging, JSON parsing, repeated concatenation and unnecessary conversions.

#### Deep dive

A heap dump may not show short-lived allocation pressure because objects die quickly. Allocation profiling is the right tool for temporary strings.

#### Production angle

Fixes might include parameterized logging, streaming parsers, precompiled patterns, `StringBuilder`, avoiding repeated `getBytes()`/`new String()`, or reducing mapped fields.

#### Traps / caveats

- High allocation can hurt latency even if heap is not full.
- Do not optimize cold allocation sites.
- Caching temporary strings may create retention problems.

#### Optional Anki

Q: Which tool helps find short-lived string allocations?
A: Allocation profiling, such as JFR allocation events.

</details>

<a id="str-scenario-003"></a>

<details>
<summary><strong>STR-SCENARIO-003. A heap dump shows millions of duplicate strings. What would you check?</strong></summary>

#### Short answer

Check what the duplicate values are and which objects retain them.

#### Interview answer

I would use duplicate-string reports and the dominator tree. Then I would inspect whether duplicates are cache keys, parsed JSON fields, database values, enum-like statuses, log messages or raw payloads. The key question is who keeps them alive.

#### Deep dive

Solutions depend on the source. Bounded repeated values may benefit from canonicalization or deduplication. Raw payload retention needs lifecycle fixes. Cache keys need eviction and normalization.

#### Production angle

Measure before and after. Watch retained heap, GC behavior and CPU because deduplication and canonicalization have costs.

#### Traps / caveats

- Duplicate strings are not automatically a leak.
- Interning unbounded duplicates can be unsafe.
- The retaining collection is usually more important than the string value.

#### Optional Anki

Q: What question matters most for duplicate strings?
A: Who is retaining them?

</details>

<a id="str-scenario-004"></a>

<details>
<summary><strong>STR-SCENARIO-004. A login check fails for visually identical usernames. What could be wrong?</strong></summary>

#### Short answer

The strings may differ by Unicode normalization, case, whitespace, invisible characters or database collation.

#### Interview answer

I would compare code points, not just visual rendering. The stored username and submitted username may use different composed/decomposed Unicode forms, different case rules, leading/trailing spaces or lookalike characters.

#### Deep dive

A robust login design usually stores the display username separately from a canonical lookup key. The canonical key applies documented normalization and case policy.

#### Production angle

Add tests for composed characters, Turkish locale, whitespace and confusable characters. Ensure database uniqueness rules match application lookup behavior.

#### Traps / caveats

- `trim()` and lower-case are not a complete identity policy.
- Default locale can break technical normalization.
- Do not destroy the original display value if users need it.

#### Optional Anki

Q: Why can two visible usernames fail `equals()`?
A: They can contain different Unicode sequences or normalization forms.

</details>

<a id="str-scenario-005"></a>

<details>
<summary><strong>STR-SCENARIO-005. An endpoint accepts emoji, but validation rejects valid input. What could be wrong?</strong></summary>

#### Short answer

Validation may be counting UTF-16 code units, rejecting surrogate pairs or using an ASCII-only regex.

#### Interview answer

Emoji often use supplementary code points, surrogate pairs, variation selectors or multi-code-point grapheme clusters. If validation assumes one `char` equals one character, uses `String.length()` for user-visible length, or uses a restrictive regex, valid input can be rejected.

#### Deep dive

Check the API contract: does the limit mean bytes, code points, grapheme clusters or database characters? Also check database encoding and client/server JSON handling.

#### Production angle

Use Unicode test cases in validation tests and align UI, API and database limits. Rejecting emoji may be acceptable only if explicitly part of product rules.

#### Traps / caveats

- `codePoints().count()` is still not grapheme count.
- Truncating by `substring()` can split user-visible characters.
- Database limits may differ from Java validation.

#### Optional Anki

Q: Why can emoji break Java length validation?
A: They may use multiple UTF-16 code units or multiple code points.

</details>

<a id="str-scenario-006"></a>

<details>
<summary><strong>STR-SCENARIO-006. A regex used on user input causes latency spikes. How would you investigate it?</strong></summary>

#### Short answer

Profile the endpoint, inspect the regex for backtracking risk, reproduce with worst-case inputs and add limits or safer parsing.

#### Interview answer

I would confirm CPU time is spent in regex matching, then review the pattern for nested quantifiers and ambiguous alternatives. I would test crafted long inputs, set input length limits and consider possessive quantifiers, atomic groups or a non-regex parser.

#### Deep dive

Precompiling a pattern helps repeated compilation cost, but it does not fix catastrophic backtracking. The pattern itself may need redesign.

#### Production angle

Add request size limits, timeouts at the request layer, metrics for validation failures and tests for malicious input shapes.

#### Traps / caveats

- Happy-path regex tests do not prove safety.
- Dynamic user-provided regexes need strict controls.
- ReDoS can exhaust request threads.

#### Optional Anki

Q: What regex issue causes extreme CPU on crafted input?
A: Catastrophic backtracking.

</details>

<a id="str-scenario-007"></a>

<details>
<summary><strong>STR-SCENARIO-007. A batch job builds a huge string and crashes with `OutOfMemoryError`. How would you redesign it?</strong></summary>

#### Short answer

Stream the output or processing instead of accumulating everything in memory.

#### Interview answer

I would identify why the job needs one huge string. For exports, write records to a `Writer`, output stream or object storage incrementally. For JSON, use a streaming generator. For CSV, use a CSV writer. For imports, process records one at a time.

#### Deep dive

Also add batching, backpressure, checkpointing and size limits. Avoid keeping raw payloads, transformed payloads and final output all at once.

#### Production angle

Streaming reduces peak memory and improves restartability. It also makes it easier to handle partial failures in long-running jobs.

#### Traps / caveats

- Increasing heap may only delay failure.
- `StringBuilder` still holds the whole output.
- Partial output needs clear error-handling semantics.

#### Optional Anki

Q: What is the main fix for huge generated strings?
A: Stream output incrementally.

</details>

<a id="str-scenario-008"></a>

<details>
<summary><strong>STR-SCENARIO-008. A cache keyed by raw request strings grows without bound. How would you fix it?</strong></summary>

#### Short answer

Define structured bounded keys, normalize inputs, add eviction and avoid caching unbounded high-cardinality values.

#### Interview answer

I would inspect key cardinality and hit rate. Raw request strings often include irrelevant ordering, whitespace, tracking parameters or unique values. Replace them with a structured key built from allowed normalized fields, then enforce max size, TTL and metrics.

#### Deep dive

Some requests should not be cached at all. Values containing secrets, user-specific tokens or huge free-form filters can create memory and privacy risks.

#### Production angle

Monitor cache size, evictions, hit rate and top key patterns. Add tenant separation where needed.

#### Traps / caveats

- Normalization must not merge different business requests.
- Unbounded caches are memory leaks.
- Cache keys can leak PII into metrics and logs.

#### Optional Anki

Q: What is wrong with raw request strings as cache keys?
A: They are often high-cardinality, unnormalized and unbounded.

</details>

<a id="str-scenario-009"></a>

<details>
<summary><strong>STR-SCENARIO-009. A service compares strings with `==` and behaves inconsistently. How would you explain the bug?</strong></summary>

#### Short answer

`==` compares references, so behavior depends on whether two equal strings happen to be the same object.

#### Interview answer

I would explain that `"OK" == "OK"` can be true because literals are interned, but a value from JSON or a database is usually another object with the same content. Business logic needs `equals()` or `Objects.equals()`.

#### Deep dive

This explains why the bug may pass tests using hardcoded literals and fail in production using runtime-created strings. The fix is not to intern everything; the fix is content comparison.

#### Production angle

Search for `==` and `!=` comparisons involving strings, add tests using runtime-created values and consider static analysis rules.

#### Traps / caveats

- `==` is correct only for intentional identity comparison.
- `equalsIgnoreCase()` also needs null handling.
- Interning can mask the bug without fixing the design.

#### Optional Anki

Q: Why does string `==` behave inconsistently?
A: It tests identity, and equal strings may or may not be the same object.

</details>

<a id="str-scenario-010"></a>

<details>
<summary><strong>🧠 STR-SCENARIO-010. A service migrated from Java 8 to Java 17/21/25. What String-related behavior would you review?</strong></summary>

#### Short answer

Review internals-sensitive assumptions: Compact Strings, concat implementation, strong encapsulation, substring history, Java 18+ UTF-8 default charset behavior, GC options and performance profiles.

#### Interview answer

Most correct String code should keep working. I would review code that depends on internals or old behavior: reflection into `String` fields, assumptions about `char[]` storage, hand-written concat micro-optimizations, GC string deduplication settings, memory estimates and old substring-leak workarounds.

#### Deep dive

Java 9 introduced Compact Strings and `invokedynamic` string concatenation. Modern Java also strongly encapsulates JDK internals, so reflective access to private `String` fields is not portable. Java 18 specified UTF-8 as the standard default charset, so code that relied on Java 8-17 environment-dependent defaults should be reviewed together with library and framework behavior in the actual runtime.

#### Production angle

After migration, compare allocation rate, heap usage, GC logs and latency. Update old advice in code comments and documentation.

#### Traps / caveats

- Do not rely on private `String` fields.
- Old Java 8 microbenchmarks may not apply.
- Most migration risk is in assumptions around internals, not normal `equals()` or `substring()` use.

#### Optional Anki

Q: What String-related migration area is most suspicious?
A: Code depending on `String` internals or old JVM behavior.

</details>
