# 05.07. Concatenation, formatting and builders

---

<a id="str-concat-001"></a>

<details>
<summary><strong>STR-CONCAT-001. What happens when strings are concatenated using the `+` operator?</strong></summary>

#### Short answer

Java creates a new string value from the operands; the compiler and JVM optimize the mechanics.

#### Interview answer

`+` is overloaded for string concatenation. If either operand is a string, Java converts the other operand to a string and combines them. Since `String` is immutable, concatenation produces a new string value rather than modifying an existing one.

#### Deep dive

For simple expressions, `+` is the most readable option and is usually optimized well. For repeated concatenation across loop iterations, each iteration can create temporary strings unless you use a builder or another streaming approach.

#### Production angle

Use `+` for simple messages and one-off expressions. Revisit it in hot loops, large exports, import pipelines or debug-disabled logging.

#### Traps / caveats

- `null` operands become `"null"` through string conversion.
- `+` is not escaping for JSON, SQL, HTML or shell commands.
- Performance depends on context, not just the operator.

#### Optional Anki

Q: Does `+` mutate an existing `String`?
A: No. Strings are immutable, so a new value is produced.

</details>

<a id="str-concat-002"></a>

<details>
<summary><strong>STR-CONCAT-002. What is the difference between compile-time and runtime string concatenation?</strong></summary>

#### Short answer

Compile-time concatenation of constants is folded by the compiler. Runtime concatenation happens when values are known only during execution.

#### Interview answer

`"a" + "b"` becomes `"ab"` at compile time. But `"a" + variable` must be evaluated at runtime. The runtime expression may allocate or be optimized by the JVM depending on context.

#### Deep dive

Compile-time folding also affects interning because the resulting constant is a string literal-like value. Runtime concatenation does not automatically mean the result is interned.

#### Production angle

This distinction is mostly useful for understanding bytecode, identity examples and performance in hot paths. Normal code should prioritize readability and use `equals()` for comparison.

#### Traps / caveats

- Do not rely on constant folding for `==`.
- A `final` variable is a compile-time constant only when initialized with a constant expression.
- Runtime concat implementation has changed across JDK versions.

#### Optional Anki

Q: What happens to `"a" + "b"`?
A: It is folded to `"ab"` at compile time.

</details>

<a id="str-concat-003"></a>

<details>
<summary><strong>🧠 STR-CONCAT-003. What changed about string concatenation in Java 9 with `invokedynamic`?</strong></summary>

#### Short answer

Java 9 changed string concatenation bytecode to use `invokedynamic`, letting the JDK choose optimized concatenation strategies at runtime.

#### Interview answer

Before Java 9, the compiler commonly translated runtime concatenation into `StringBuilder` operations. Since Java 9, javac can emit an `invokedynamic` call that links to `StringConcatFactory`. This gives the JDK more freedom to optimize concatenation without changing source code.

#### Deep dive

The important interview point is not to manually rewrite every `+` into `StringBuilder`. Modern Java can optimize straightforward concatenation well. Builders still matter when accumulating across loop iterations or controlling capacity.

#### Production angle

Use readable `+` for simple expressions. Profile before changing code for micro-optimization, especially on modern JDKs.

#### Traps / caveats

- `invokedynamic` does not make repeated loop concatenation always free.
- Bytecode details depend on compiler and target version.
- Old Java 8 advice may be too broad for Java 17+.

#### Optional Anki

Q: What JDK feature powers Java 9+ string concat bytecode?
A: `invokedynamic` via `StringConcatFactory`.

</details>

<a id="str-concat-004"></a>

<details>
<summary><strong>STR-CONCAT-004. When should you use `StringBuilder` instead of repeated concatenation?</strong></summary>

#### Short answer

Use `StringBuilder` when building a string incrementally, especially in loops or large outputs.

#### Interview answer

`StringBuilder` is mutable, so appending many pieces can reuse one buffer instead of creating many intermediate strings. It is a good fit for loops, generated messages, simple reports and controlled text assembly.

#### Deep dive

The builder eventually creates a `String` when `toString()` is called. Choosing an initial capacity can reduce buffer resizing when the approximate final size is known.

#### Production angle

In import/export pipelines and high-throughput endpoints, builders can reduce allocation rate. For structured formats like JSON or CSV, prefer streaming libraries over hand-built text.

#### Traps / caveats

- `StringBuilder` is not thread-safe.
- Do not reuse one builder across unrelated requests without clearing and controlling ownership.
- Do not use builders to manually escape complex formats.

#### Optional Anki

Q: Why can `StringBuilder` be faster in loops?
A: It appends into a mutable buffer instead of creating many intermediate strings.

</details>

<a id="str-concat-005"></a>

<details>
<summary><strong>STR-CONCAT-005. What is the difference between `StringBuilder` and `StringBuffer`?</strong></summary>

#### Short answer

`StringBuilder` is unsynchronized and usually faster. `StringBuffer` synchronizes its methods.

#### Interview answer

Both classes are mutable character-sequence builders. `StringBuilder` is the normal choice for single-threaded or thread-confined building. `StringBuffer` is older and synchronizes individual methods, which adds overhead.

#### Deep dive

Synchronized methods do not make a whole workflow correct. A sequence of calls like check-then-append can still need external synchronization if shared across threads.

#### Production angle

Most backend code should use local `StringBuilder` instances. Shared mutable builders are usually a design smell.

#### Traps / caveats

- `StringBuffer` method synchronization is not transaction-level thread safety.
- A local `StringBuilder` is safe even in multithreaded services because it is not shared.
- `StringBuilder` implements `CharSequence`, but it is mutable.

#### Optional Anki

Q: Which builder is synchronized?
A: `StringBuffer`.

</details>

<a id="str-concat-006"></a>

<details>
<summary><strong>🧠 STR-CONCAT-006. How do `StringBuilder` capacity and growth affect performance?</strong></summary>

#### Short answer

If a builder outgrows its buffer, it allocates a larger buffer and copies existing content. A good initial capacity can reduce this overhead.

#### Interview answer

`StringBuilder` has an internal mutable buffer. Appending is cheap while capacity is enough. When capacity is exceeded, the builder grows, allocates new storage and copies old content. If you know the approximate final size, passing an initial capacity can avoid repeated growth.

#### Deep dive

Over-sizing wastes memory; under-sizing causes copying. The right choice depends on workload size and frequency. For occasional small strings, default capacity is fine.

#### Production angle

Initial capacity matters in large CSV exports, generated SQL-like diagnostic text, log aggregation or serialization-like code. Profile allocation rate before tuning.

#### Traps / caveats

- Capacity is not length.
- Large retained builders can hold large buffers if reused carelessly.
- Tuning builders is secondary to using the right parser/serializer.

#### Optional Anki

Q: What happens when `StringBuilder` exceeds capacity?
A: It grows storage and copies existing content.

</details>

<a id="str-concat-007"></a>

<details>
<summary><strong>STR-CONCAT-007. Why should you avoid `+` concatenation in large loops?</strong></summary>

#### Short answer

It can create many intermediate strings and increase allocation and CPU cost.

#### Interview answer

When concatenation accumulates across loop iterations, each step may produce a new string containing all previous content plus the new part. That can become quadratic copying and high allocation. `StringBuilder` or streaming output is usually better.

#### Deep dive

Modern compilers optimize a single expression well, but they cannot always turn a loop-carried string accumulation into the best possible builder pattern across iterations.

#### Production angle

This matters in report generation, imports, exports and response construction. In extreme cases it can cause latency spikes or `OutOfMemoryError`.

#### Traps / caveats

- `+` inside one simple expression is usually fine.
- `+` in a loop is not always bad if the loop is tiny and cold.
- Use real serializers for large JSON/XML/CSV output.

#### Optional Anki

Q: What is the main risk of loop concatenation?
A: Many intermediate strings and repeated copying.

</details>

<a id="str-concat-008"></a>

<details>
<summary><strong>STR-CONCAT-008. When is `+` concatenation perfectly fine?</strong></summary>

#### Short answer

It is fine for simple, readable, non-hot expressions and small strings.

#### Interview answer

For one-off messages, exception text, simple DTO display values and short expressions, `+` is clear and modern Java handles it well. Replacing every `+` with `StringBuilder` often makes code worse without measurable benefit.

#### Deep dive

The performance question depends on frequency, size and context. A single concatenation in a request handler is usually irrelevant. A million concatenations in a parser is different.

#### Production angle

Prefer readability until profiling shows string allocation or concatenation is a bottleneck. Optimization should be targeted, not mechanical.

#### Traps / caveats

- Avoid eager concatenation in disabled log statements.
- Avoid manual concatenation for structured formats.
- Do not build SQL by concatenation just because it is "small."

#### Optional Anki

Q: Should every `+` be replaced with `StringBuilder`?
A: No. Use builders where accumulation or profiling justifies it.

</details>

<a id="str-concat-009"></a>

<details>
<summary><strong>STR-CONCAT-009. What is the difference between `String.concat()` and `+`?</strong></summary>

#### Short answer

`concat()` appends another string to a string. `+` is language syntax that handles many operand types and null conversion.

#### Interview answer

`"a".concat("b")` returns `"ab"`. The `+` operator can concatenate strings with primitives or objects by converting them to strings. `+` also treats null as `"null"` in string concatenation, while calling `concat()` with null throws `NullPointerException`.

#### Deep dive

In normal code, `+` is more flexible and readable. `concat()` is rarely needed directly.

#### Production angle

The main practical difference is null behavior and readability. Neither API escapes structured data.

#### Traps / caveats

- `"a" + null` gives `"anull"`.
- `"a".concat(null)` throws `NullPointerException`.
- Neither is appropriate for safe SQL or JSON construction.

#### Optional Anki

Q: What happens with `"a" + null`?
A: It produces `"anull"`.

</details>

<details>
<summary><strong>STR-CONCAT-010. Why can `String.format()` be slower than simple concatenation?</strong></summary>

#### Short answer

It parses a format pattern, handles formatting rules and may allocate more supporting objects.

#### Interview answer

`String.format()` is powerful but heavier than simple concatenation. It supports format specifiers, locale behavior, width, precision and type conversions. That work has overhead compared with a small `+` expression.

#### Deep dive

The cost matters mainly in tight loops, hot request paths and high-volume logging. For occasional human-readable messages, clarity can be worth the overhead.

#### Production angle

If profiling shows formatting as a bottleneck, consider simple concatenation, prebuilt formatters, builders or structured logging depending on the use case.

#### Traps / caveats

- Do not optimize formatting without measurement.
- Format strings can fail at runtime if arguments mismatch.
- Formatting does not sanitize untrusted data.

#### Optional Anki

Q: Why is `String.format()` relatively heavy?
A: It parses and applies formatting rules, not just append values.

</details>

<a id="str-concat-011"></a>

<details>
<summary><strong>STR-CONCAT-011. Why should backend logging prefer parameterized logging over eager string concatenation?</strong></summary>

#### Short answer

Parameterized logging can avoid building messages when the log level is disabled and keeps structured values clearer.

#### Interview answer

With eager concatenation like `log.debug("User " + userId + " loaded")`, the string is built before the logger decides whether debug logging is enabled. Parameterized logging like `log.debug("User {} loaded", userId)` lets the logging framework defer formatting.

#### Deep dive

Parameterized logging also makes it easier to keep messages consistent and can integrate better with structured logging. Expensive argument computation still needs guarding with `isDebugEnabled()` or lazy suppliers if available.

#### Production angle

In high-throughput services, disabled debug logs with eager concatenation can create surprising allocation and CPU overhead.

#### Traps / caveats

- Do not log secrets or PII just because formatting is lazy.
- Expensive method calls used as arguments may still execute.
- String interpolation before calling the logger is still eager.

#### Optional Anki

Q: What is the benefit of `log.debug("id={}", id)`?
A: Message formatting can be skipped when debug logging is disabled.

</details>

<details>
<summary><strong>STR-CONCAT-012. How would you build a large CSV or JSON-like string safely?</strong></summary>

#### Short answer

Use a proper CSV or JSON library, preferably streaming for large output.

#### Interview answer

For JSON, use Jackson or another JSON library so escaping, Unicode, nulls and types are handled correctly. For CSV, use a CSV library because quoting and delimiter escaping are tricky. For large output, write to a stream or writer instead of building one huge string in memory.

#### Deep dive

Manual concatenation breaks when values contain quotes, delimiters, newlines, backslashes or special Unicode characters. It also risks memory spikes if the full output is accumulated before sending.

#### Production angle

Streaming output reduces peak memory and avoids `OutOfMemoryError` in exports. Libraries also reduce injection and malformed-output bugs.

#### Traps / caveats

- JSON-like is not JSON.
- CSV escaping rules are easy to get wrong.
- Prepared statements are required for SQL; string construction is not enough.

#### Optional Anki

Q: What should you use for large JSON output?
A: A JSON library, ideally with streaming when the output is large.

</details>
