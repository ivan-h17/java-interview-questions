# 05.06. Comparison, ordering and locale

---

<a id="str-i18n-001"></a>

<details>
<summary><strong>STR-I18N-001. How does `String.compareTo()` order strings, and is it locale-aware?</strong></summary>

#### Short answer

`String.compareTo()` compares strings lexicographically by Unicode code-unit values. It is not locale-aware.

#### Interview answer

`compareTo()` implements natural ordering for `String`. It compares characters in sequence and returns a negative, zero or positive value depending on the first difference, or length if one string is a prefix of the other.

This is useful for deterministic technical ordering, but it is not human-language sorting.

#### Deep dive

Because Java exposes strings through UTF-16 code units, natural ordering is based on that representation. It does not know that some languages sort accents, case or compound characters differently.

#### Production angle

Use `compareTo()` for technical keys, deterministic ordering, internal maps and protocols. Use locale-aware collation for user-facing sorted lists.

#### Traps / caveats

- Natural order is not alphabetical order for every language.
- Case and accents may sort unexpectedly.
- Database collation may order strings differently from Java.

#### Optional Anki

Q: Is `String.compareTo()` locale-aware?
A: No.

</details>

<a id="str-i18n-002"></a>

<details>
<summary><strong>STR-I18N-002. What is the difference between binary or code-unit ordering and human-language ordering?</strong></summary>

#### Short answer

Binary or code-unit ordering sorts by encoded values. Human-language ordering follows locale-specific collation rules.

#### Interview answer

Code-unit ordering treats strings as sequences of numeric values. Human-language ordering considers language rules: accents, case, digraphs, punctuation and cultural expectations.

For example, a user may expect accented variants to appear near the base letter, while code-unit order may place them elsewhere.

#### Deep dive

There is no single correct human order for all languages. The same characters can sort differently depending on locale and collation strength.

#### Production angle

Search results, customer lists and reports should use the appropriate database collation or Java `Collator` behavior. Internal IDs and protocol values usually need deterministic technical ordering instead.

#### Traps / caveats

- User-facing sort order must be tested with real locale examples.
- Java and database collation can differ.
- Case-insensitive ordering is not always language-neutral.

#### Optional Anki

Q: What does human-language sorting require?
A: Locale-aware collation rules.

</details>

<a id="str-i18n-003"></a>

<details>
<summary><strong>STR-I18N-003. When should you use `Collator` instead of `String.compareTo()`?</strong></summary>

#### Short answer

Use `Collator` when sorting or comparing user-facing text according to a locale.

#### Interview answer

`Collator` applies locale-sensitive comparison rules. It is appropriate for names, titles, labels and other human-language text. `String.compareTo()` is better for deterministic technical values such as IDs, codes and protocol constants.

#### Deep dive

`Collator` supports strengths that control whether case, accents and variants affect comparison. This makes it more flexible but also more expensive and policy-heavy than simple string comparison.

#### Production angle

For large datasets, sorting often belongs in the database or search engine with a defined collation. Java-side `Collator` is useful for smaller in-memory lists or when behavior must match application locale settings.

#### Traps / caveats

- Choose the locale explicitly.
- Collation can affect equality-like comparisons and sorting differently.
- Do not mix database and Java ordering without tests.

#### Optional Anki

Q: What API supports locale-aware string comparison in Java?
A: `Collator`.

</details>

<a id="str-i18n-004"></a>

<details>
<summary><strong>STR-I18N-004. What is the difference between case-sensitive and case-insensitive comparison?</strong></summary>

#### Short answer

Case-sensitive comparison treats uppercase and lowercase as different. Case-insensitive comparison treats them as equivalent according to defined rules.

#### Interview answer

For case-sensitive comparison, `"abc"` and `"ABC"` are different. For case-insensitive comparison, they may be considered equal. The tricky part is defining which case rules apply: simple Java rules, locale-specific rules, or a domain-specific normalization.

#### Deep dive

Identifiers such as HTTP methods, header names or internal codes often need simple case-insensitive handling. User names, search queries and human text may require locale and normalization decisions.

#### Production angle

Store a canonical lookup value when needed. For example, preserve the display name but store a normalized key for uniqueness and login.

#### Traps / caveats

- Lower-casing with default locale can be wrong.
- Case-insensitive does not mean whitespace-insensitive.
- Case-insensitive does not mean Unicode-normalized.

#### Optional Anki

Q: What is the main risk in case-insensitive comparison?
A: The case rules must be defined explicitly.

</details>

<a id="str-i18n-005"></a>

<details>
<summary><strong>STR-I18N-005. Why can `toLowerCase()` and `toUpperCase()` be locale-sensitive?</strong></summary>

#### Short answer

Some languages have casing rules that differ from English-like assumptions, so default-locale case conversion can change behavior.

#### Interview answer

`toLowerCase()` and `toUpperCase()` can use locale-specific rules. The classic example is Turkish dotted and dotless `i`, where converting `"id"` or `"TITLE"` under Turkish rules can produce results that break technical identifiers.

#### Deep dive

For machine identifiers, use `Locale.ROOT` to get locale-neutral behavior. For user-visible text, use the user's locale where that is the intended behavior.

#### Production angle

Default-locale bugs appear when services run in different regions or containers with different locale settings. They can break login, authorization, routing and cache keys.

#### Traps / caveats

- Do not use default locale for protocol identifiers.
- `equalsIgnoreCase()` is not a complete locale-aware solution.
- Tests should include at least one non-English locale case.

#### Optional Anki

Q: What locale should technical identifier normalization usually use?
A: `Locale.ROOT`.

</details>

<a id="str-i18n-006"></a>

<details>
<summary><strong>STR-I18N-006. When should you use `Locale.ROOT`, and when should you use a user-specific `Locale`?</strong></summary>

#### Short answer

Use `Locale.ROOT` for locale-neutral technical values. Use a user locale for user-visible language behavior.

#### Interview answer

Technical identifiers such as enum-like strings, protocol values, cache keys and database lookup keys should not depend on the server's default locale. Use `Locale.ROOT` for normalization.

For user-facing text, sorting, formatting and display, use the user's locale or product locale.

#### Deep dive

The default locale is rarely the correct implicit policy in backend services. It is hidden global state. Explicit locale choice makes behavior reviewable and testable.

#### Production angle

Use `Locale.ROOT` for things like role names, feature flags and normalized slugs. Use user locale for sorting a contact list or formatting messages in a UI.

#### Traps / caveats

- `Locale.ENGLISH` is not the same as locale-neutral, though it is sometimes used historically.
- User locale should not affect security identifiers.
- Locale policy should be consistent between app, database and search.

#### Optional Anki

Q: What is `Locale.ROOT` for?
A: Locale-neutral behavior, especially for technical strings.

</details>

<a id="str-i18n-007"></a>

<details>
<summary><strong>🧠 STR-I18N-007. How would you design case-insensitive search or identifier normalization without locale bugs?</strong></summary>

#### Short answer

Define a canonical form explicitly: normalize Unicode if needed, trim only by rule, case-fold with `Locale.ROOT` for technical identifiers, and align database/search behavior.

#### Interview answer

For identifiers, I would preserve the original display value and store a canonical key. The canonicalization pipeline should be documented and tested: maybe trim, normalize Unicode, lower-case with `Locale.ROOT`, and reject unsupported characters. For user-facing search, I would rely on database or search-engine collation/analyzers configured for the target languages.

#### Deep dive

The rules depend on domain. Email, usernames, SKU codes and human names have different semantics. One-size-fits-all lower-casing can be incorrect.

#### Production angle

Add uniqueness constraints on the canonical key, test with Turkish locale and composed Unicode examples, and ensure Java and storage-layer behavior do not disagree.

#### Traps / caveats

- Do not use JVM default locale.
- Do not destroy display values when normalizing lookup keys.
- Do not assume database `LOWER()` matches Java behavior exactly.

#### Optional Anki

Q: What is a safe pattern for case-insensitive identifiers?
A: Store original display value plus a canonical lookup key with explicit normalization rules.

</details>
