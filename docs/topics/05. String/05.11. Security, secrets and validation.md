# 05.11. Security, secrets and validation

---

<a id="str-sec-001"></a>

<details>
<summary><strong>STR-SEC-001. Why is string validation security-sensitive?</strong></summary>

#### Short answer

Strings often carry untrusted input used in commands, queries, paths, logs and output, so validation mistakes can become injection or access-control bugs.

#### Interview answer

Backend services receive strings from users, headers, JSON, files and messages. Those strings may later be used as SQL values, paths, HTML, JSON, XML, shell arguments or log entries. Each target context has different safety rules.

Validation should define allowed values, length, format and normalization before dangerous use.

#### Deep dive

Validation is not the same as escaping. Validation decides whether data is acceptable. Output encoding or parameterization makes data safe in a specific sink.

#### Production angle

Many serious vulnerabilities are string-boundary bugs: SQL injection, path traversal, command injection, log injection and XSS in rendered output.

#### Traps / caveats

- Rejecting bad input is not enough if output encoding is missing.
- Regex validation can itself be vulnerable to ReDoS.
- Normalize before validation when alternate representations can bypass checks.

#### Optional Anki

Q: Why are strings security-sensitive?
A: They often carry untrusted data into sensitive sinks.

</details>

<a id="str-sec-002"></a>

<details>
<summary><strong>STR-SEC-002. What is canonicalization before validation, and why does the order matter?</strong></summary>

#### Short answer

Canonicalization converts input to a standard form before validation so alternate representations cannot bypass checks.

#### Interview answer

If input can be represented in multiple ways, validate the canonical form. For example, URL-encoded path segments, Unicode normalization forms or case variants can hide dangerous values. If you validate before decoding or normalizing, an attacker may pass validation and become dangerous later after transformation.

#### Deep dive

The rule is: decode and canonicalize according to the boundary contract, then validate, then use safe APIs for the target sink.

#### Production angle

This matters in path traversal, URL handling, authentication identifiers, file names and access-control checks.

#### Traps / caveats

- Avoid double-decoding bugs.
- Canonicalization rules are domain-specific.
- Validation is still not a replacement for parameterized SQL or output encoding.

#### Optional Anki

Q: Why validate after canonicalization?
A: To prevent alternate representations from bypassing validation.

</details>

<a id="str-sec-003"></a>

<details>
<summary><strong>STR-SEC-003. How can path traversal attacks involve string processing?</strong></summary>

#### Short answer

Attackers use crafted path strings such as `../` or encoded variants to access files outside the intended directory.

#### Interview answer

If a service builds file paths from user strings, an attacker may include `../`, absolute paths, separators, symlinks or encoded characters to escape the allowed directory. Simple string prefix checks are often insufficient.

#### Deep dive

Use path APIs to resolve and normalize paths, then verify the final canonical path is inside the allowed base directory. Also validate filenames with an allowlist when possible.

#### Production angle

Path traversal can expose configuration, secrets, uploaded files or host filesystem data. It is common in download endpoints and file import features.

#### Traps / caveats

- Validate after decoding.
- Beware symlinks and platform-specific path separators.
- `startsWith()` on raw strings is not enough.

#### Optional Anki

Q: What is the safe pattern for user file paths?
A: Resolve and normalize with path APIs, then verify the final path stays under the allowed base.

</details>

<a id="str-sec-004"></a>

<details>
<summary><strong>STR-SEC-004. Why should you not build shell commands, HTML, JSON or XML by concatenating untrusted strings?</strong></summary>

#### Short answer

Each context has syntax where untrusted strings can escape their intended position and change meaning.

#### Interview answer

Shell, HTML, JSON and XML all have special characters and escaping rules. Concatenating untrusted values directly can create command injection, XSS, malformed JSON or XML injection. Use APIs that separate data from syntax or apply context-specific encoding.

#### Deep dive

For shell commands, avoid shell interpretation and pass arguments as an array to process APIs. For HTML, use template engines with escaping. For JSON/XML, use serializers.

#### Production angle

Injection vulnerabilities often appear when a quick string concatenation grows into a production feature. Treat untrusted strings as data, not syntax.

#### Traps / caveats

- Escaping rules differ by context.
- JSON escaping does not make HTML safe.
- Validation allowlists are helpful but not a substitute for safe sinks.

#### Optional Anki

Q: What is the core injection defense?
A: Keep untrusted data separate from executable or structured syntax.

</details>

<a id="str-sec-005"></a>

<details>
<summary><strong>STR-SEC-005. What is output encoding, and how does it relate to strings?</strong></summary>

#### Short answer

Output encoding converts untrusted string data into a safe representation for a specific output context.

#### Interview answer

When a string is placed into HTML, JavaScript, JSON, XML, SQL or a shell command, special characters may have syntax meaning. Output encoding escapes those characters so the value remains data. The encoding must match the destination context.

#### Deep dive

Validation checks whether input is acceptable. Output encoding protects the output sink. Both may be needed. For SQL, parameterization is preferred over manual encoding.

#### Production angle

Wrong or missing output encoding causes XSS, malformed responses, injection vulnerabilities and broken integrations.

#### Traps / caveats

- There is no universal escaping function.
- Encode as late as possible for the actual sink.
- Do not double-encode already encoded data.

#### Optional Anki

Q: Is there one escaping method for every context?
A: No. Encoding must be context-specific.

</details>

<a id="str-sec-006"></a>

<details>
<summary><strong>STR-SEC-006. How can log injection or CRLF injection involve strings?</strong></summary>

#### Short answer

Untrusted strings can contain newline or control characters that forge log entries or inject headers.

#### Interview answer

If user input is written directly to logs, an attacker can include `\r` or `\n` to create fake log lines. In protocols using CRLF as a delimiter, such as HTTP headers, injected CRLF can alter message structure if not prevented by libraries.

#### Deep dive

Log injection damages auditability and incident response. CRLF injection can be more serious when it affects headers or downstream parsers.

#### Production angle

Sanitize or encode control characters in logs, use structured logging and avoid placing raw untrusted values into headers. Frameworks often protect header APIs, but do not bypass them with raw string construction.

#### Traps / caveats

- Logs are a security boundary for audit integrity.
- Redaction and control-character escaping are separate concerns.
- Structured logging still needs PII and secret controls.

#### Optional Anki

Q: What characters are central to CRLF injection?
A: Carriage return and line feed: `\r\n`.

</details>

<a id="str-sec-007"></a>

<details>
<summary><strong>STR-SEC-007. Why is `String` not ideal for passwords, tokens or long-lived cryptographic secrets?</strong></summary>

#### Short answer

Strings are immutable and cannot be reliably cleared from memory after use.

#### Interview answer

Once a secret is stored in a `String`, the application cannot overwrite its contents. The string may remain in memory until garbage collected and may appear in heap dumps, logs, exception messages or interned/cached values if mishandled.

#### Deep dive

For some APIs, strings are unavoidable. But for secrets under your control, prefer types that minimize exposure, avoid logging, avoid interning and clear mutable buffers where meaningful.

#### Production angle

Heap dumps and debug logs often contain secrets because everything is a string somewhere: tokens, passwords, Authorization headers and connection URLs. Treat diagnostic artifacts as sensitive.

#### Traps / caveats

- `char[]` is not magic, but it can be cleared.
- Avoid putting secrets into exception messages.
- Redact secrets before logging structured payloads.

#### Optional Anki

Q: Why are strings poor for secrets?
A: They are immutable and cannot be explicitly wiped.

</details>

<a id="str-sec-008"></a>

<details>
<summary><strong>STR-SEC-008. Is `char[]` always safer than `String` for secrets, and what are the limitations?</strong></summary>

#### Short answer

`char[]` can be cleared, so it can reduce exposure, but it is not automatically safe.

#### Interview answer

A `char[]` lets code overwrite secret contents after use. That is useful for passwords and similar short-lived secrets. But it only helps if all copies are controlled. If the secret is converted to `String`, logged, copied by a library or stored in a heap dump before clearing, exposure remains.

#### Deep dive

Modern JVMs, libraries and frameworks may copy data internally. Garbage collectors may also move objects. Clearing arrays is still a good practice in sensitive code, but it is not a complete memory-safety guarantee.

#### Production angle

Use secret-management systems, minimize lifetime, avoid logs, restrict heap dump access and prefer APIs designed for credentials.

#### Traps / caveats

- Clearing one array does not clear copies.
- Many framework APIs accept only `String`.
- Operational controls are as important as data type choice.

#### Optional Anki

Q: What advantage does `char[]` have for secrets?
A: It can be overwritten after use.

</details>
