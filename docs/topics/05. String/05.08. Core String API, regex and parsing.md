# 05.08. Core String API, regex and parsing

<a id="str-api-001"></a>

<details>
<summary><strong>STR-API-001. What is the difference between `isEmpty()`, `isBlank()`, `trim()` and `strip()`?</strong></summary>

#### Short answer

`isEmpty()` checks length zero. `isBlank()` checks only whitespace. `trim()` removes older ASCII-style leading/trailing whitespace. `strip()` uses Unicode-aware whitespace rules.

#### Interview answer

`isEmpty()` returns true only for `""`. `isBlank()` returns true for empty or whitespace-only strings. `trim()` returns a string with leading and trailing characters less than or equal to U+0020 removed. `strip()` uses Unicode whitespace detection and is usually better for modern text.

#### Deep dive

`stripLeading()` and `stripTrailing()` remove only one side. These methods do not change the original string because strings are immutable.

#### Production angle

Validation should define whether blank values are allowed and which whitespace rules apply. Do not trim identifiers blindly if spaces may be meaningful.

#### Traps / caveats

- `trim()` and `strip()` return a string; they do not mutate.
- `isBlank()` is not the same as `isEmpty()`.
- Removing whitespace can change user input semantics.

#### Optional Anki

Q: Which method checks for whitespace-only strings?
A: `isBlank()`.

</details>

<a id="str-api-002"></a>

<details>
<summary><strong>STR-API-002. What are text blocks, and what are their traps for SQL or JSON?</strong></summary>

#### Short answer

Text blocks are multi-line string literals. They improve readability but do not provide escaping, parameterization or validation for SQL or JSON.

#### Interview answer

Text blocks use triple quotes and are useful for multi-line text such as test JSON, SQL templates or documentation snippets. They handle indentation more conveniently than ordinary string literals.

The trap is thinking they make embedded formats safe. A SQL text block still needs prepared statement parameters. JSON should still be generated or parsed by a JSON library when values are dynamic.

#### Deep dive

Text blocks have rules for incidental indentation and line terminators. Methods such as `stripIndent()` and `translateEscapes()` relate to text-block handling, but most backend developers mainly need to understand readability and safety boundaries.

#### Production angle

Text blocks are useful for static queries, test fixtures and templates. Avoid concatenating untrusted data into them.

#### Traps / caveats

- Text blocks are still strings.
- They do not escape SQL, JSON, HTML or XML.
- Whitespace and trailing newlines can matter.

#### Optional Anki

Q: Do text blocks make SQL injection-safe?
A: No. Use prepared statements.

</details>

<a id="str-api-003"></a>

<details>
<summary><strong>STR-API-003. What is the difference between `chars()` and `codePoints()`?</strong></summary>

#### Short answer

`chars()` returns UTF-16 code units. `codePoints()` returns Unicode code points.

#### Interview answer

Both return an `IntStream`, but they operate at different levels. `chars()` emits each Java `char` value, which can split surrogate pairs. `codePoints()` combines surrogate pairs and emits actual Unicode code points.

#### Deep dive

Use `chars()` for low-level UTF-16 operations or ASCII-only processing. Use `codePoints()` when the text may contain supplementary characters and your logic is meant to operate on Unicode code points.

#### Production angle

Choosing the wrong API can break validation and sanitization for emoji and non-BMP characters.

#### Traps / caveats

- `codePoints()` is still not grapheme-cluster iteration.
- Both streams produce `int`, not `char` objects.
- ASCII-only tests hide the difference.

#### Optional Anki

Q: Which method should you prefer for Unicode code point iteration?
A: `codePoints()`.

</details>

<a id="str-api-004"></a>

<details>
<summary><strong>STR-API-004. What do `toCharArray()` and `getBytes(Charset)` return, and why does copying matter?</strong></summary>

#### Short answer

They return new arrays containing a copy or encoding of the string content.

#### Interview answer

`toCharArray()` returns a new `char[]` with the string's UTF-16 code units. `getBytes(Charset)` returns a new `byte[]` containing the string encoded with the given charset. The returned arrays can be modified without changing the original string.

#### Deep dive

Copying protects string immutability. But it also means these methods allocate memory. For large strings or high-frequency paths, repeated conversion can be expensive.

#### Production angle

Use explicit charsets and avoid unnecessary conversions in hot paths. For secrets, remember that converting to or from `String` can create extra copies that are difficult to erase.

#### Traps / caveats

- `getBytes()` without charset uses the default charset.
- `toCharArray()` does not give access to internal storage.
- Byte length can differ from string length.

#### Optional Anki

Q: Does `toCharArray()` expose the internal string buffer?
A: No. It returns a copy.

</details>

<a id="str-ops-001"></a>

<details>
<summary><strong>🧠 STR-OPS-001. How did old `substring()` sharing cause memory leaks, and how does modern `substring()` differ?</strong></summary>

#### Short answer

Older Java versions could let substrings share a large backing array, keeping the whole original string alive. Modern Java generally copies the needed data.

#### Interview answer

In older JDKs, `substring()` could create a lightweight view into the original string's backing array. That made substring cheap but dangerous: a tiny substring could retain a huge original string in memory.

Modern JDKs changed this behavior so substrings normally have their own storage, avoiding that retention problem.

#### Deep dive

This is a historical implementation detail, but it explains old memory-leak advice and why version context matters. The public API never promised backing-array sharing.

#### Production angle

If maintaining old Java applications, substring retention may matter. On modern Java, focus more on large strings, parsing strategies and allocation rate.

#### Traps / caveats

- Do not rely on substring internal sharing for performance.
- Old blog posts may describe obsolete behavior.
- Slicing still creates strings and can allocate.

#### Optional Anki

Q: What was the old substring memory issue?
A: A small substring could keep a large original backing array alive.

</details>

<a id="str-ops-002"></a>

<details>
<summary><strong>STR-OPS-002. Why can `split(".")` or `split("|")` be wrong?</strong></summary>

#### Short answer

`split()` takes a regex, and `.` and `|` are regex metacharacters.

#### Interview answer

`"a.b".split(".")` does not mean split on a literal dot. In regex, `.` means any character. `|` means alternation. To split on a literal dot or pipe, escape the regex or use `Pattern.quote(delimiter)`.

#### Deep dive

For a dot, use `split("\\.")`. For a dynamic delimiter, prefer `split(Pattern.quote(delimiter))`. Regex behavior also affects empty results and limits.

#### Production angle

This bug appears in CSV-like parsing, version parsing, IP address splitting and pipe-delimited integrations. It can silently produce wrong fields.

#### Traps / caveats

- `split()` is regex-based, not literal.
- Backslashes need Java string escaping and regex escaping.
- Use a real parser for CSV or complex formats.

#### Optional Anki

Q: How do you split on a literal dot?
A: Use `split("\\.")` or `split(Pattern.quote("."))`.

</details>

<a id="str-ops-003"></a>

<details>
<summary><strong>STR-OPS-003. What is the difference between splitting by a regex and splitting by a literal delimiter?</strong></summary>

#### Short answer

Regex splitting interprets the delimiter as a pattern. Literal splitting treats the delimiter as exact text.

#### Interview answer

`String.split()` uses a regular expression, so characters like `.`, `|`, `*`, `+` and `?` have special meaning. Literal splitting needs escaping through `Pattern.quote()` or a non-regex utility.

#### Deep dive

Regex splitting is powerful for flexible separators, such as multiple whitespace characters. Literal splitting is safer when the delimiter comes from configuration or data.

#### Production angle

For high-volume parsing, regex splitting can also create many temporary strings and pattern work. Consider precompiled patterns, manual parsing or a format-specific parser.

#### Traps / caveats

- Dynamic delimiters should usually be quoted.
- `split()` has special behavior for trailing empty strings unless a limit is used.
- Regex is not a CSV parser.

#### Optional Anki

Q: How do you make a dynamic split delimiter literal?
A: Wrap it with `Pattern.quote(delimiter)`.

</details>

<a id="str-ops-004"></a>

<details>
<summary><strong>STR-OPS-004. What is the difference between `replace()`, `replaceAll()` and `replaceFirst()`?</strong></summary>

#### Short answer

`replace()` uses literal characters or literal text. `replaceAll()` and `replaceFirst()` use regex patterns.

#### Interview answer

`replace(old, new)` replaces literal occurrences. `replaceAll(regex, replacement)` replaces every regex match. `replaceFirst(regex, replacement)` replaces only the first regex match.

Use `replace()` when you do not need regex.

#### Deep dive

The replacement string in regex methods has its own special handling for `$` and backslash references. That is why literal replacement text sometimes needs `Matcher.quoteReplacement()`.

#### Production angle

Use literal replacement for simple sanitization or formatting. Use regex deliberately and test it with edge cases.

#### Traps / caveats

- `replaceAll(".", "x")` replaces every character.
- Regex replacement strings are not always literal.
- Regex on untrusted input can be expensive.

#### Optional Anki

Q: Which replacement method is regex-based?
A: `replaceAll()` and `replaceFirst()`.

</details>

<a id="str-ops-005"></a>

<details>
<summary><strong>STR-OPS-005. Why can regex replacement strings require escaping, and what does `Matcher.quoteReplacement()` do?</strong></summary>

#### Short answer

In regex replacement strings, `$` and backslash have special meaning. `Matcher.quoteReplacement()` makes replacement text literal.

#### Interview answer

When using `replaceAll()` or `Matcher.replaceAll()`, the replacement string can refer to capture groups using `$1` and can use backslash escaping. If user-provided replacement text contains `$` or backslashes, it may be interpreted unexpectedly or throw an error.

`Matcher.quoteReplacement(text)` returns a safe literal replacement string.

#### Deep dive

This is separate from quoting the regex pattern. Use `Pattern.quote()` for literal patterns and `Matcher.quoteReplacement()` for literal replacement values.

#### Production angle

This matters in templating, masking, text cleanup and user-configurable replacement rules. Incorrect escaping can corrupt output or create runtime failures.

#### Traps / caveats

- Pattern escaping and replacement escaping are different.
- `replace()` avoids regex replacement semantics.
- Do not use regex replacement as an output-encoding strategy.

#### Optional Anki

Q: What quotes a literal regex replacement string?
A: `Matcher.quoteReplacement()`.

</details>

<details>
<summary><strong>STR-OPS-006. What is the difference between `contains()`, `indexOf()`, `startsWith()`, `endsWith()` and `matches()`?</strong></summary>

#### Short answer

They test different string conditions; `matches()` is regex-based and must match the whole string.

#### Interview answer

`contains()` checks whether a literal sequence exists. `indexOf()` returns the position of a character or substring, or `-1`. `startsWith()` and `endsWith()` check prefixes and suffixes. `matches()` treats the argument as a regex and returns true only if the entire string matches.

#### Deep dive

A common trap is expecting `matches("abc")` to mean "contains abc." It means the whole string must match the pattern `abc`. Use `Pattern` and `Matcher.find()` for regex search.

#### Production angle

Pick the simplest API that expresses the rule. Literal APIs are usually clearer and safer than regex when no pattern matching is needed.

#### Traps / caveats

- `matches()` compiles a regex each call.
- `contains()` is literal, not regex.
- Prefix checks may need normalization or case policy first.

#### Optional Anki

Q: Does `matches()` search for a substring?
A: No. It matches the entire string against a regex.

</details>

<a id="str-ops-007"></a>

<details>
<summary><strong>STR-OPS-007. When should you precompile a `Pattern`?</strong></summary>

#### Short answer

Precompile when the same regex is used repeatedly or on a hot path.

#### Interview answer

Methods like `matches()`, `split()` and `replaceAll()` compile regex patterns internally. If the same regex is used many times, compiling it once as a `Pattern` avoids repeated parsing and can improve performance.

#### Deep dive

Precompiled patterns also make flags explicit and improve readability for complex regexes. Store them as `private static final Pattern` when they are constant and thread-safe to reuse.

#### Production angle

This matters in validators, parsers, log processors and request filters. Profile if regex processing appears in CPU hotspots.

#### Traps / caveats

- Precompilation does not fix catastrophic backtracking.
- Dynamic user-supplied regexes need strict controls.
- Complex regexes still need tests.

#### Optional Anki

Q: Is `Pattern` reusable across threads?
A: Yes, `Pattern` is immutable and reusable.

</details>

<a id="str-ops-008"></a>

<details>
<summary><strong>🧠 STR-OPS-008. What is catastrophic backtracking, and how can regex cause denial-of-service risk?</strong></summary>

#### Short answer

Catastrophic backtracking happens when a regex engine explores too many matching paths, causing extreme CPU time for certain inputs.

#### Interview answer

Some regex patterns with nested quantifiers or ambiguous alternatives can take exponential time on inputs that almost match. If attackers can control the input, they can cause latency spikes or thread exhaustion. This is often called ReDoS.

#### Deep dive

Patterns like nested `.*`, `(a+)+`, or ambiguous alternations can be dangerous. Safer designs use simpler patterns, possessive quantifiers, atomic groups, bounded lengths or non-regex parsers.

#### Production angle

Validate input size before regex matching, test worst-case strings, add timeouts at higher levels where possible and avoid user-supplied regexes unless sandboxed.

#### Traps / caveats

- A regex can be correct functionally but unsafe operationally.
- Precompiling does not prevent backtracking.
- Short unit tests with happy-path inputs miss ReDoS risks.

#### Optional Anki

Q: What is ReDoS?
A: Regex denial of service caused by expensive regex behavior on crafted input.

</details>

<details>
<summary><strong>🧠 STR-OPS-009. How would you parse a large text file without creating too many intermediate strings?</strong></summary>

#### Short answer

Stream the file, use explicit charset handling, parse incrementally and avoid regex splitting of every line when it is too costly.

#### Interview answer

I would read with a buffered reader or streaming parser using the correct charset. Then process records one at a time, avoid loading the whole file into one string, and use a format-specific parser for CSV, JSON or logs. If manual parsing is necessary, reuse buffers carefully and avoid creating substrings for fields that can be processed directly.

#### Deep dive

The best approach depends on the format. For CSV, use a CSV parser. For JSON, use Jackson streaming. For fixed delimiters, manual scanning can reduce allocations compared with `split()`.

#### Production angle

Large imports should have backpressure, metrics, size limits, error reporting and memory profiling. The goal is bounded memory and predictable throughput.

#### Traps / caveats

- `Files.readString()` is wrong for huge files.
- `String.split()` on every line may allocate heavily.
- Reusing mutable buffers across records can create bugs if references escape.

#### Optional Anki

Q: What is the first rule for huge text files?
A: Stream them instead of loading the whole file into one `String`.

</details>
