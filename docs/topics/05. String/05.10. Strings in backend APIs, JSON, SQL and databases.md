# 05.10. Strings in backend APIs, JSON, SQL and databases

---

<a id="str-be-001"></a>

<details>
<summary><strong>STR-BE-001. How should HTTP API boundaries define charset and media type for textual payloads?</strong></summary>

#### Short answer

APIs should declare the media type and encoding explicitly, usually using UTF-8 for textual payloads.

#### Interview answer

HTTP payloads are bytes. The `Content-Type` tells the receiver how to interpret those bytes, for example `application/json` or `text/plain; charset=utf-8`. The service should parse only supported media types and should encode responses consistently.

#### Deep dive

JSON is normally UTF-8 in modern APIs, but legacy text formats and file uploads may still need explicit charset handling. The key is that the byte-to-string conversion must happen according to the contract, not the server default.

#### Production angle

Charset ambiguity causes corrupted non-English text, broken signatures and failed integrations. Contract tests should include non-ASCII examples.

#### Traps / caveats

- HTTP headers are metadata; they do not fix already-misencoded bytes.
- Default charset assumptions vary by library and format.
- Media type validation is separate from business validation.

#### Optional Anki

Q: What does `Content-Type` define?
A: The media type, and sometimes the charset, used to interpret the payload.

</details>

<a id="str-be-002"></a>

<details>
<summary><strong>STR-BE-002. How should backend code read and write request, response and file bytes as text safely?</strong></summary>

#### Short answer

Use explicit charsets, stream large data and validate at the boundary.

#### Interview answer

When reading bytes as text, choose the charset from the protocol or file format. For most modern APIs, use UTF-8. Avoid default charset APIs. For large bodies or files, stream through readers/writers rather than loading everything into one string.

#### Deep dive

Use `InputStreamReader(input, charset)`, `Files.newBufferedReader(path, charset)`, `Files.newBufferedWriter(path, charset)` or framework-level APIs that make encoding explicit.

#### Production angle

Safe text IO prevents corruption and memory spikes. Large request bodies also need size limits, timeouts and backpressure.

#### Traps / caveats

- `Files.readString()` is convenient but not always appropriate for large files.
- Decoding errors may be replaced silently depending on API.
- Text IO does not validate business content.

#### Optional Anki

Q: What is the safe rule for byte-to-text conversion?
A: Use the charset defined by the boundary contract.

</details>

<a id="str-be-003"></a>

<details>
<summary><strong>STR-BE-003. How do JSON libraries handle Java strings, and what can go wrong with manual JSON concatenation?</strong></summary>

#### Short answer

JSON libraries escape and encode strings according to JSON rules. Manual concatenation can produce invalid JSON or injection bugs.

#### Interview answer

A JSON library like Jackson knows how to quote strings, escape quotes and backslashes, handle control characters, encode Unicode and represent nulls. If you build JSON by concatenating strings, values containing quotes, newlines or special characters can break the output or change its meaning.

#### Deep dive

JSON strings are not just Java strings with quotes around them. They have specific escaping rules. Libraries also handle nested structures, types and streaming.

#### Production angle

Manual JSON building can break clients, leak data or create security issues. Use serializers for responses and parsers for requests.

#### Traps / caveats

- JSON-like text is not necessarily valid JSON.
- Escaping is different for JSON, HTML, SQL and shell.
- Do not concatenate untrusted values into JSON templates.

#### Optional Anki

Q: Why use a JSON library for strings?
A: It handles quoting and escaping according to JSON rules.

</details>

<a id="str-be-004"></a>

<details>
<summary><strong>STR-BE-004. Why should SQL be built with prepared statements instead of string concatenation?</strong></summary>

#### Short answer

Prepared statements separate SQL structure from values, preventing SQL injection and avoiding escaping mistakes.

#### Interview answer

When SQL is built by concatenating strings, user input can change the query structure. Prepared statements use placeholders for values, so the database treats input as data, not SQL syntax.

They also improve type handling and can help plan reuse depending on the database and driver.

#### Deep dive

Escaping manually is brittle because SQL dialects and data types differ. Prepared statements are the default safe approach. Dynamic SQL may still be needed for table names or optional clauses, but identifiers must be allowlisted and values must stay parameterized.

#### Production angle

SQL injection is a critical security risk. Even trusted-looking input can become unsafe through bugs, integrations or future code changes.

#### Traps / caveats

- Prepared statement placeholders cannot replace table or column names.
- Do not concatenate values into a text block.
- Logging full SQL with values can leak PII or secrets.

#### Optional Anki

Q: What is the key benefit of prepared statements?
A: They separate query structure from data values.

</details>

<details>
<summary><strong>STR-BE-005. How should string length validation be designed for API inputs?</strong></summary>

#### Short answer

Define the unit of length, validate before storage or processing, and align with database and product rules.

#### Interview answer

A length rule must say whether it counts bytes, UTF-16 code units, code points or user-visible characters. For example, a database column may limit characters or bytes, while a UI may care about grapheme clusters.

Validation should also consider trimming, normalization and maximum payload size.

#### Deep dive

For security and performance, validate both field length and whole request size. For user-visible limits, test emoji and composed characters. For storage limits, validate against the database's actual behavior.

#### Production angle

Bad length validation causes truncation, database errors, rejected valid input and inconsistent API behavior. It can also allow oversized payloads to consume memory.

#### Traps / caveats

- `String.length()` is not byte length.
- Normalization can change length.
- Truncating blindly can split Unicode sequences.

#### Optional Anki

Q: What must a string length rule define?
A: The unit being counted.

</details>

<a id="str-be-006"></a>

<details>
<summary><strong>STR-BE-006. Why can database column length checks differ from Java `String.length()`?</strong></summary>

#### Short answer

Databases may count characters, bytes or collation-specific values, while Java `length()` counts UTF-16 code units.

#### Interview answer

Java `String.length()` is not necessarily the same as a database column's length semantics. A database column may limit characters, encoded bytes or a type-specific size. Unicode characters and encodings can make these counts differ.

#### Deep dive

For example, UTF-8 byte length varies by character. Some database collations also affect comparison and uniqueness differently from Java. The application should validate according to the database contract or let database constraints reject invalid values with clean error handling.

#### Production angle

Mismatched validation causes inserts to fail in production or values to be truncated by legacy systems. Integration tests should include non-ASCII values and boundary lengths.

#### Traps / caveats

- ASCII tests usually do not reveal the mismatch.
- `varchar(255)` semantics depend on the database.
- Index length limits may differ from column length limits.

#### Optional Anki

Q: Why can Java and DB string lengths differ?
A: Java counts UTF-16 code units; databases may count characters or bytes.

</details>

<a id="str-be-007"></a>

<details>
<summary><strong>STR-BE-007. How can string truncation cause production bugs?</strong></summary>

#### Short answer

Truncation can corrupt Unicode, break uniqueness, change identifiers, lose meaning or hide data-quality problems.

#### Interview answer

If a service truncates strings blindly, it may split a surrogate pair, cut a combining sequence, create duplicate normalized values or remove important suffixes. Truncating IDs, tokens, emails or JSON fragments is especially dangerous.

#### Deep dive

Truncation should be a deliberate product decision. For display, truncate by grapheme cluster if possible. For storage, reject too-long values or store them in a suitable field rather than silently cutting.

#### Production angle

Silent truncation leads to failed lookups, broken audit trails, duplicate records and hard-to-debug integration issues.

#### Traps / caveats

- Never silently truncate security tokens or identifiers.
- Truncating before normalization may not enforce the final length.
- Database-side truncation may hide application validation bugs.

#### Optional Anki

Q: Why is blind string truncation risky?
A: It can corrupt text or change business meaning.

</details>

<a id="str-be-008"></a>

<details>
<summary><strong>STR-BE-008. When should you stream textual data instead of loading it into one `String`?</strong></summary>

#### Short answer

Stream when data can be large, unbounded or processed incrementally.

#### Interview answer

If a file, request, response or export may be large, loading it into one string creates high peak memory usage. Streaming lets the service process chunks or records one at a time and apply backpressure.

#### Deep dive

Streaming is common for file imports, report exports, large JSON arrays, CSV processing and log pipelines. Use buffered readers/writers, streaming JSON parsers or framework support for streaming responses.

#### Production angle

Streaming prevents `OutOfMemoryError`, reduces latency to first byte and improves stability under large inputs.

#### Traps / caveats

- Streaming code still needs limits and timeouts.
- Error handling is more complex after partial output.
- Some formats require full context unless using a streaming parser.

#### Optional Anki

Q: Why avoid one huge `String` for large payloads?
A: It increases peak memory and GC pressure.

</details>

<details>
<summary><strong>🧠 STR-BE-009. How can database encoding, collation or normalization differ from Java string behavior?</strong></summary>

#### Short answer

The database may encode, compare, sort and enforce uniqueness differently from Java.

#### Interview answer

Java `equals()` compares string content exactly by code-unit sequence. A database collation may be case-insensitive, accent-insensitive or locale-aware. Database encoding controls which characters can be stored and how many bytes they use. Normalization behavior may also differ.

#### Deep dive

This means Java may think two strings are different while a database unique index rejects them as equal, or Java may sort values differently from an `ORDER BY`.

#### Production angle

For login names, search, tags and unique fields, align application normalization with database constraints. Add tests that cover case, accents, composed characters and non-English text.

#### Traps / caveats

- Do not assume Java equality matches DB uniqueness.
- Do not assume Java sorting matches `ORDER BY`.
- Search engines add another layer of analyzers and normalization.

#### Optional Anki

Q: Why can Java allow a value that a DB unique index rejects?
A: The database collation may consider two strings equal when Java does not.

</details>
