# 05.05. Unicode, charsets and normalization

---

<a id="str-unicode-001"></a>

<details>
<summary><strong>STR-UNICODE-001. What is the difference between Unicode, a character set and a character encoding?</strong></summary>

#### Short answer

Unicode defines characters and code points. A character set is a repertoire of characters. A character encoding maps characters or code points to bytes.

#### Interview answer

Unicode is the standard that assigns code points to characters, symbols and many text elements used by writing systems. A charset describes which characters are representable. An encoding such as UTF-8 or UTF-16 defines how those code points are represented as bytes or code units.

In day-to-day Java work, the most important distinction is text versus bytes.

#### Deep dive

People often say "charset" and "encoding" interchangeably, and Java's `Charset` API represents a named mapping between bytes and characters. In protocols, the important thing is to specify the actual encoding used for bytes, for example UTF-8.

#### Production angle

If one system writes bytes as UTF-8 and another reads them as Windows-1251 or ISO-8859-1, text gets corrupted. This shows up in APIs, file imports, Kafka messages and database integrations.

#### Traps / caveats

- Unicode is not the same thing as UTF-8.
- Java `String` is text, not encoded bytes.
- Always define the encoding at system boundaries.

#### Optional Anki

Q: What does an encoding define?
A: How text is represented as bytes or code units.

</details>

<a id="str-unicode-002"></a>

<details>
<summary><strong>STR-UNICODE-002. What is the difference between UTF-8 and UTF-16, and how does Java represent text conceptually?</strong></summary>

#### Short answer

UTF-8 is a variable-length byte encoding. UTF-16 represents text as 16-bit code units. Java strings expose a UTF-16 code-unit model.

#### Interview answer

UTF-8 uses one to four bytes per Unicode code point and is dominant for files, HTTP and JSON. UTF-16 uses one or two 16-bit code units per code point. Java's `String` API historically exposes text through UTF-16 code units: `charAt()` returns a `char`, and `length()` counts code units.

#### Deep dive

Modern JDKs may store strings internally more compactly for Latin-1-compatible content, but the public API still behaves according to the UTF-16 code-unit model. That is why supplementary characters require surrogate pairs.

#### Production angle

Use UTF-8 at external boundaries unless a protocol says otherwise. Inside Java, remember that `length()` and `charAt()` are not always user-character operations.

#### Traps / caveats

- Compact Strings do not mean the public Java API became UTF-8.
- One Unicode code point may be two Java `char` values.
- One user-perceived character may be multiple code points.

#### Optional Anki

Q: What does Java `String.length()` count?
A: UTF-16 code units.

</details>

<a id="str-unicode-003"></a>

<details>
<summary><strong>STR-UNICODE-003. What is a Java `char`, and how is it related to code units, code points and surrogate pairs?</strong></summary>

#### Short answer

A Java `char` is a 16-bit UTF-16 code unit, not necessarily a complete Unicode character.

#### Interview answer

For characters in the Basic Multilingual Plane, one Java `char` can represent one code point. For supplementary Unicode characters, UTF-16 uses two code units: a high surrogate and a low surrogate. That pair represents one code point.

So `char` is a low-level unit, not a reliable model of a user-visible character.

#### Deep dive

`String.codePointAt()`, `codePoints()` and related APIs work at the code point level. They are safer than iterating with `charAt()` when text can contain emoji, historic scripts or other supplementary characters.

#### Production angle

Validation, truncation and parsing code that assumes one `char` equals one character can break emoji, names and international text.

#### Traps / caveats

- A surrogate alone is not a complete Unicode scalar value.
- `char` iteration can split a supplementary character.
- Code points are still not the same as grapheme clusters.

#### Optional Anki

Q: Is Java `char` always a full Unicode character?
A: No. It is a UTF-16 code unit.

</details>

<a id="str-unicode-004"></a>

<details>
<summary><strong>STR-UNICODE-004. What is a grapheme cluster?</strong></summary>

#### Short answer

A grapheme cluster is what a user typically perceives as one character, even if it is made from multiple code points.

#### Interview answer

Some visible characters are built from multiple Unicode code points. For example, a base letter plus a combining accent can display as one character. Some emoji sequences also combine multiple code points into one user-perceived symbol.

A grapheme cluster is the user-facing unit, while Java `char` and Unicode code point are lower-level units.

#### Deep dive

Counting or truncating by grapheme cluster requires Unicode text-boundary logic. The JDK has `BreakIterator`, and specialized libraries may be used for stricter modern Unicode behavior.

#### Production angle

User-facing length limits, cursor movement, UI truncation and validation can be wrong if they count code units instead of grapheme clusters.

#### Traps / caveats

- One grapheme cluster can contain multiple code points.
- `codePoints().count()` is still not the same as user-visible character count.
- Database and API limits may not be defined in grapheme clusters.

#### Optional Anki

Q: What is a grapheme cluster?
A: A user-perceived character, possibly made from multiple code points.

</details>

<a id="str-unicode-005"></a>

<details>
<summary><strong>STR-UNICODE-005. Why is `String.length()` not the number of user-perceived characters?</strong></summary>

#### Short answer

`String.length()` counts UTF-16 code units, while users perceive grapheme clusters.

#### Interview answer

Java's `length()` returns the number of UTF-16 code units. A supplementary character such as many emoji uses two code units, so length can be 2 for one code point. A composed visual character can be even more complex because one grapheme cluster may contain multiple code points.

#### Deep dive

There are several possible "lengths": byte length after encoding, UTF-16 code-unit length, code point count and grapheme cluster count. Each is correct for a different purpose.

#### Production angle

APIs should define which length limit they enforce. For database columns, transport payloads and UI fields, the right unit may differ. Wrong truncation can break Unicode or reject valid user input.

#### Traps / caveats

- `length()` is fine for many internal operations, but not always for user-facing limits.
- Truncating by code unit can split surrogate pairs.
- Byte limits must be checked after encoding.

#### Optional Anki

Q: What does `String.length()` count?
A: UTF-16 code units, not grapheme clusters.

</details>

<a id="str-unicode-006"></a>

<details>
<summary><strong>STR-UNICODE-006. How should you iterate over Unicode code points in a `String`?</strong></summary>

#### Short answer

Use `codePoints()` or code point APIs instead of naïve `charAt()` iteration.

#### Interview answer

For text that may contain supplementary characters, iterate with `string.codePoints()` or use methods such as `codePointAt()` and `offsetByCodePoints()`. These APIs treat surrogate pairs as one code point.

#### Deep dive

`chars()` returns an `IntStream` of UTF-16 code units, not Unicode code points. Its name is easy to misread. `codePoints()` is the safer default when actual Unicode code points matter.

#### Production angle

Correct code point iteration matters in validation, sanitization, tokenization and text analytics. For user-visible character boundaries, code points may still not be enough; use grapheme-aware logic.

#### Traps / caveats

- `chars()` is not code point iteration.
- Code point iteration can still split grapheme clusters.
- Some validation should work on normalized text.

#### Optional Anki

Q: Which API returns code points?
A: `String.codePoints()`.

</details>

<a id="str-unicode-007"></a>

<details>
<summary><strong>STR-UNICODE-007. How do you convert `String` to `byte[]` and back safely?</strong></summary>

#### Short answer

Use explicit charsets, usually `StandardCharsets.UTF_8`, for both encoding and decoding.

#### Interview answer

Convert text to bytes with `s.getBytes(StandardCharsets.UTF_8)`. Convert bytes to text with `new String(bytes, StandardCharsets.UTF_8)`. The charset must match the protocol, file format or database encoding.

#### Deep dive

If you encode with one charset and decode with another, characters may be corrupted. Invalid byte sequences can be replaced or rejected depending on decoder configuration. For strict protocols, use `CharsetDecoder` if you need explicit error handling.

#### Production angle

This is critical in REST APIs, file imports, Kafka consumers, message signatures and integrations. Encoding mismatches can break only for certain languages, making them easy to miss in tests.

#### Traps / caveats

- Avoid platform default charset.
- Do not convert arbitrary binary data to `String`.
- Be careful with BOMs and legacy encodings in file imports.

#### Optional Anki

Q: What charset should most modern text protocols use?
A: UTF-8, unless the protocol explicitly requires something else.

</details>

<a id="str-unicode-008"></a>

<details>
<summary><strong>STR-UNICODE-008. Why should backend code avoid the platform default charset?</strong></summary>

#### Short answer

Because relying on the JVM default charset hides the real data contract. Java 18+ defaults to UTF-8, but Java 17 and earlier were environment-dependent, and configured runtimes or legacy data can still surprise you.

#### Interview answer

Using APIs such as `new String(bytes)` or `s.getBytes()` without a charset relies on the JVM's default charset. In Java 17 and earlier, that default depended on the operating system, locale and runtime environment. In Java 18+, the standard default is UTF-8 unless configured otherwise, but the code still fails to state what the file, protocol or integration actually requires.

Explicit charsets make behavior stable.

#### Deep dive

Even with Java 18+ specifying UTF-8 as the default, code should express boundary contracts explicitly. Protocols and file formats are not "whatever this runtime defaults to", and legacy files may intentionally use another encoding.

#### Production angle

Default charset bugs appear during Java upgrades, mixed Java-version deployments, legacy file imports and cross-system integrations. They often corrupt only non-ASCII text.

#### Traps / caveats

- Tests with ASCII-only data will not catch charset bugs.
- Java 18+ made the standard default UTF-8, but explicit charset arguments are still clearer at boundaries.
- Files from legacy systems may not be UTF-8.
- Explicit charset is documentation and correctness.

#### Optional Anki

Q: Why is default charset risky?
A: It hides the required encoding; Java 17 and earlier were environment-dependent, and Java 18+ UTF-8 still may not match legacy data.

</details>

<a id="str-unicode-009"></a>

<details>
<summary><strong>STR-UNICODE-009. What can go wrong when text is decoded with the wrong charset?</strong></summary>

#### Short answer

The text can become corrupted, rejected, silently changed or impossible to compare correctly.

#### Interview answer

If bytes encoded as UTF-8 are decoded as another charset, non-ASCII characters can become mojibake, replacement characters or invalid data. The resulting string may look wrong and may fail equality checks, signatures, search and database constraints.

#### Deep dive

Some encodings can map every byte to some character, so decoding may not fail loudly. That is dangerous because corrupted text can flow into databases or downstream systems before anyone notices.

#### Production angle

Encoding problems commonly show up in customer names, addresses, localized content, CSV imports and message integrations. Keep raw samples and verify bytes when debugging.

#### Traps / caveats

- Display issues are not always frontend bugs.
- Once corrupted text is persisted, recovery may require original bytes.
- Logs can hide the real bytes by rendering replacement characters.

#### Optional Anki

Q: What is mojibake?
A: Garbled text caused by decoding bytes with the wrong character encoding.

</details>

<a id="str-unicode-010"></a>

<details>
<summary><strong>STR-UNICODE-010. What is Unicode normalization, and why can two visually identical strings be unequal?</strong></summary>

#### Short answer

Unicode normalization converts equivalent text representations into a standard form. Two strings can look identical but use different code point sequences.

#### Interview answer

Some characters can be represented in more than one way. For example, an accented letter may be a single precomposed code point or a base letter plus a combining mark. They may render the same, but `String.equals()` compares code-unit sequences, so they can be unequal.

Normalization can convert text into a chosen form before comparison or storage.

#### Deep dive

Java provides normalization through `java.text.Normalizer`. Common forms include NFC and NFD. The right choice depends on the domain, database behavior and integration requirements.

#### Production angle

Normalization affects login names, search, uniqueness constraints, filenames and identifiers. Without a consistent policy, users may create visually duplicate values or fail to log in.

#### Traps / caveats

- Normalization can change string length.
- It is not the same as case folding.
- Do not normalize blindly when exact original text must be preserved.

#### Optional Anki

Q: Why can visually identical strings be unequal?
A: They may use different Unicode code point sequences.

</details>

<details>
<summary><strong>🧠 STR-UNICODE-011. What is the difference between NFC and NFD normalization, and where can it matter?</strong></summary>

#### Short answer

NFC prefers composed characters where possible. NFD decomposes characters into base characters plus combining marks.

#### Interview answer

NFC is often used for general storage and comparison because it keeps text in a composed form when possible. NFD decomposes characters and can appear in some filesystem or text-processing contexts. Both can represent canonically equivalent text.

#### Deep dive

The important backend decision is consistency. If Java normalizes one way, the database or filesystem compares another way, equality and uniqueness can diverge.

#### Production angle

This matters for usernames, filenames, search indexes and uniqueness checks. A service should document and test the chosen normalization policy with real Unicode examples.

#### Traps / caveats

- NFC/NFD do not solve all confusable-character issues.
- Compatibility forms such as NFKC can change meaning more aggressively.
- Normalization policy must be coordinated with storage and search.

#### Optional Anki

Q: What does NFC generally do?
A: It uses composed character forms where possible.

</details>

<a id="str-unicode-012"></a>

<details>
<summary><strong>STR-UNICODE-012. How can Unicode normalization affect login, search and uniqueness checks?</strong></summary>

#### Short answer

Without consistent normalization, equivalent-looking input may fail to match or may bypass uniqueness rules.

#### Interview answer

If a username is stored in one Unicode representation and a login attempt uses another visually identical representation, raw `String.equals()` may fail. Search can miss results for the same reason. Unique constraints may allow values that users perceive as duplicates.

#### Deep dive

Correct design usually stores a canonical searchable key separately from the display value. The display value preserves what the user entered; the canonical key applies normalization, case policy and possibly trimming according to business rules.

#### Production angle

Identity systems, customer records and search features should have explicit normalization tests. The database collation and application comparison policy must agree enough to prevent surprises.

#### Traps / caveats

- Email normalization is provider-specific and should be handled carefully.
- Case-insensitive search is not just lower-casing in the default locale.
- Over-normalization can merge values that the business considers distinct.

#### Optional Anki

Q: What is a common design for normalized login names?
A: Store a display value and a canonical lookup key.

</details>

<details>
<summary><strong>🧠 STR-UNICODE-013. What are homoglyph or confusable-character attacks?</strong></summary>

#### Short answer

They use different characters that look similar to trick users or bypass simple string checks.

#### Interview answer

Unicode contains characters from many scripts that can look alike, such as Latin, Cyrillic and Greek letters. An attacker can create a username, domain, path or label that visually resembles a trusted value but is a different string.

#### Deep dive

Normalization does not fully solve confusables because different characters can be intentionally distinct but visually similar. Defenses depend on context: restrict allowed scripts, use allowlists, display warnings, canonicalize identifiers or rely on established IDNA/security libraries.

#### Production angle

This matters for usernames, tenant names, public URLs, admin panels, payment labels and audit logs. Security-sensitive identifiers need stricter rules than free-form display names.

#### Traps / caveats

- `equals()` correctly sees different code points as different strings.
- Visual inspection of logs may be misleading.
- Blocking all non-ASCII text is not acceptable for many products.

#### Optional Anki

Q: What is a homoglyph attack?
A: Using different but visually similar characters to impersonate another string.

</details>
