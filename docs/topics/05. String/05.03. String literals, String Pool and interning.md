# 05.03. String literals, String Pool and interning

---

<a id="str-pool-001"></a>

<details>
<summary><strong>STR-POOL-001. How does the String Pool work?</strong></summary>

#### Short answer

The String Pool is a JVM-managed set of canonical `String` objects used mainly for literals and explicitly interned strings.

#### Interview answer

String literals are interned: the JVM keeps one canonical object for a given literal value. When the same literal appears again, code can reference the existing pooled object. You can also call `intern()` on a runtime string to get the canonical pooled instance for the same content.

#### Deep dive

The pool reduces duplicate literal objects and makes string constants efficient. It relies on immutability: sharing a pooled string is safe only because no code can change its content.

The pool is not a general-purpose cache for all text. It is global enough that careless interning of unbounded data can create memory pressure.

#### Production angle

Understanding the pool explains why `==` sometimes appears to work, why `new String("x")` is wasteful and why locking on string literals is dangerous.

#### Traps / caveats

- The pool does not mean all equal strings are automatically the same object.
- Interning is about identity canonicalization, not normal equality.
- Do not intern unbounded user input casually.

#### Optional Anki

Q: What does the String Pool store?
A: Canonical string instances for literals and interned strings.

</details>

<a id="str-pool-002"></a>

<details>
<summary><strong>STR-POOL-002. What is the difference between a string literal and `new String(...)`?</strong></summary>

#### Short answer

A literal uses an interned pooled string. `new String(...)` creates a new distinct `String` object with the same content.

#### Interview answer

`String s = "abc";` refers to the pooled literal `"abc"`. `String s = new String("abc");` creates a new object whose content equals `"abc"` but whose identity is different from the pooled literal.

The second form is almost always unnecessary.

#### Deep dive

The literal itself is interned. The `new String(...)` wrapper object is not the pooled object unless you call `intern()` and use that returned reference. Calling `new String` can be useful only in rare cases where a true separate object is intentionally needed, which is uncommon in backend code.

#### Production angle

`new String("...")` adds allocation noise and can confuse people into thinking identity comparison should work. Code reviews should usually reject it unless there is a very specific reason.

#### Traps / caveats

- `new String("abc").equals("abc")` is true.
- `new String("abc") == "abc"` is false.
- Calling `intern()` returns the pooled reference; it does not mutate the existing variable unless assigned.

#### Optional Anki

Q: Is `new String("abc")` usually needed?
A: No. The literal already provides a `String`.

</details>

<a id="str-pool-003"></a>

<details>
<summary><strong>STR-POOL-003. What is the difference between compile-time string constants and runtime concatenation?</strong></summary>

#### Short answer

Compile-time constant concatenation is folded by the compiler and interned as a literal-like constant; runtime concatenation creates a value at runtime.

#### Interview answer

If all parts are compile-time constants, `"a" + "b"` becomes `"ab"` during compilation. That result is a constant string and is interned. If any part is a runtime variable, concatenation happens at runtime and the result is an ordinary string unless interned separately.

#### Deep dive

This distinction explains identity examples. `("a" + "b") == "ab"` can be true when both parts are constants. But `String x = "a"; (x + "b") == "ab"` is not guaranteed because the expression is evaluated at runtime.

#### Production angle

This is mostly an interview and debugging concept. In production code, compare content with `equals()` and let the compiler/JVM optimize normal readable concatenation.

#### Traps / caveats

- Do not depend on `==` even if constant folding makes a demo pass.
- `final` variables initialized with compile-time constants can participate in constant expressions.
- Runtime concatenation behavior has changed internally across JDK versions.

#### Optional Anki

Q: Is `"a" + "b"` a runtime concatenation?
A: No, it is folded to `"ab"` at compile time.

</details>

<a id="str-pool-004"></a>

<details>
<summary><strong>STR-POOL-004. What does `String.intern()` return, and when is manual interning useful?</strong></summary>

#### Short answer

`intern()` returns the canonical pooled string equal to the receiver. It is useful only when canonicalizing many repeated bounded values is proven beneficial.

#### Interview answer

When you call `s.intern()`, the JVM checks the String Pool. If an equal string is already present, it returns that pooled instance. Otherwise it adds a canonical instance and returns it.

Manual interning can help when a service has many duplicate strings from a small known set and identity sharing reduces memory enough to justify the complexity.

#### Deep dive

Interning is not an equality mechanism. It changes reference identity only if all code uses the interned result. The pool also has lifecycle and memory implications, so it should be driven by measurement, not habit.

#### Production angle

Manual interning may help in parsers, imports or dictionaries with bounded repeated values. It is usually a bad default for request parameters, IDs, free-form text and anything unbounded.

#### Traps / caveats

- Always use the returned value: `s = s.intern()`.
- Interning unbounded input can increase memory pressure.
- `equals()` remains the correct comparison for normal business logic.

#### Optional Anki

Q: What does `intern()` return?
A: The canonical pooled `String` equal to the original string.

</details>

<a id="str-pool-005"></a>

<details>
<summary><strong>STR-POOL-005. How can excessive or unbounded interning cause memory problems?</strong></summary>

#### Short answer

Interning keeps canonical strings reachable from the pool, so unbounded unique values can accumulate and pressure the heap.

#### Interview answer

The pool is useful when many strings repeat. It is harmful when most interned strings are unique or come from unbounded user input. In that case, the application pays pool lookup overhead and retains many values that may not otherwise have stayed alive.

#### Deep dive

Interning is a form of global canonicalization. Any canonicalization cache needs a bounded key space, eviction policy or lifecycle strategy. The built-in pool is not a business cache with tenant-aware limits.

#### Production angle

Interning request IDs, usernames, search terms or payload fragments can turn normal traffic into heap growth. Use heap dumps and allocation profiling before enabling interning as an optimization.

#### Traps / caveats

- "Fewer duplicates" does not help if values are mostly unique.
- Interning can also increase CPU cost.
- String deduplication may be a better measured option for some duplicate-heavy services.

#### Optional Anki

Q: When is interning risky?
A: When values are unbounded, mostly unique or controlled by users.

</details>

<a id="str-pool-006"></a>

<details>
<summary><strong>STR-POOL-006. What is the difference between string deduplication and interning?</strong></summary>

#### Short answer

Interning canonicalizes `String` objects by identity. GC string deduplication shares duplicate backing storage while keeping separate `String` objects.

#### Interview answer

`intern()` returns one canonical pooled `String` reference for equal content. Code using interned values may see reference identity sharing.

G1 String deduplication is a GC optimization. It can make multiple equal strings share the same underlying byte array, but the `String` objects remain distinct and `==` does not become true.

#### Deep dive

Interning is explicit and changes which reference the application uses. Deduplication is automatic JVM work after strings exist and is focused on memory footprint, not application-level canonical identity.

#### Production angle

If you only need to reduce heap usage from many duplicate strings, deduplication may be less invasive than changing application logic to intern values. It still has CPU and GC costs and should be measured.

#### Traps / caveats

- Deduplication does not make `a == b` true.
- Interning can affect object identity; deduplication should not.
- Both are optimizations, not substitutes for correct equality.

#### Optional Anki

Q: Does G1 string deduplication deduplicate `String` objects?
A: No, it can share backing storage while objects remain separate.

</details>

<a id="str-pool-007"></a>

<details>
<summary><strong>STR-POOL-007. Why should you not synchronize on string literals or interned strings?</strong></summary>

#### Short answer

Because pooled strings can be shared globally, unrelated code may accidentally use the same lock.

#### Interview answer

Synchronizing on `"LOCK"` or an interned string uses a shared object that other code may also reference. Since literals are pooled, two libraries using the same literal can unknowingly synchronize on the same monitor. This can cause contention, deadlocks or security issues.

#### Deep dive

Locks should be private implementation details. Use a private final lock object, a `ReentrantLock`, or a keyed lock design with controlled lifecycle. Interned strings violate that privacy because their identity is globally discoverable by content.

#### Production angle

Accidental lock sharing is hard to debug. Thread dumps may show blocking on a `String`, but the real cause can be a collision between unrelated code paths.

#### Traps / caveats

- `synchronized("x")` is a code smell.
- `synchronized(userInput.intern())` is worse because users influence lock identity.
- `StringBuffer` synchronization does not solve workflow-level locking.

#### Optional Anki

Q: Why is synchronizing on string literals dangerous?
A: The same pooled object may be shared by unrelated code.

</details>

<a id="str-pool-008"></a>

<details>
<summary><strong>🧠 STR-POOL-008. Where is the String Pool stored in modern JVMs, and how did this change historically?</strong></summary>

#### Short answer

In modern HotSpot JVMs, pooled strings are heap objects managed through the JVM string table; historically, older JVM versions had PermGen-related behavior around interned strings.

#### Interview answer

The practical modern answer is that interned strings are normal heap objects, so they contribute to heap pressure. Dynamically interned strings are not automatically immortal; they can be reclaimed when no strong references keep them alive. String literals from live classes, however, are normally reachable as long as the defining class or class loader remains live.

Historically, the implementation changed across Java versions, which is why old advice about PermGen and string interning can be misleading.

#### Deep dive

Older Java versions had PermGen for class metadata and related runtime structures. Modern HotSpot removed PermGen and uses Metaspace for class metadata, while string objects themselves are heap objects. The exact string-table and class-loading details are not something most backend code should depend on.

#### Production angle

For current services, think of excessive interning as a heap/memory-retention concern, not only a legacy PermGen concern.

#### Traps / caveats

- Old blog posts about PermGen may be obsolete for Java 8+.
- Dynamically interned values and literals from live classes can have different reachability behavior.
- JVM implementation details can differ outside HotSpot.
- This is a second-pass topic unless diagnosing memory behavior.

#### Optional Anki

Q: Is the modern HotSpot String Pool a normal application design cache?
A: No. It is JVM-managed canonicalization, and excessive interning can pressure memory.

</details>

<a id="str-pool-009"></a>

<details>
<summary><strong>🧠 STR-POOL-009. How does the String Pool interact with class loading?</strong></summary>

#### Short answer

String literals from loaded classes are interned, so class loading can create or reference pooled string constants.

#### Interview answer

When a class containing string literals is loaded and its constants are resolved, those literal values are represented as interned strings. If another class uses the same literal value, it can reference the same canonical pooled object.

#### Deep dive

This is why string literals are shared across code that never directly communicates. The pool is keyed by string content, not by source file. Class unloading and pool cleanup are JVM implementation details, but the high-level point is that literals are not recreated for every use.

#### Production angle

This matters mostly for understanding memory dumps, classloader leaks and why string literals should not be used as locks. If a classloader leak keeps classes alive, related constants and referenced strings may also stay alive.

#### Traps / caveats

- Do not assume a separate pool per class.
- Do not lock on literals because unrelated loaded code can share them.
- Classloader memory issues often involve more than strings.

#### Optional Anki

Q: Are string literals generally interned?
A: Yes, string literals are represented by interned strings.

</details>

<a id="str-pool-010"></a>

<details>
<summary><strong>🧠 STR-POOL-010. How would you design a safe custom string canonicalization cache?</strong></summary>

#### Short answer

Make it bounded, measured, domain-specific and thread-safe, with clear normalization and eviction rules.

#### Interview answer

A custom canonicalization cache should only be used for a known repeated value set. Define how values are normalized, bound the cache by size or lifecycle, use a thread-safe implementation, and measure memory savings against CPU overhead.

For example, a CSV import might canonicalize country codes or known categories, but not arbitrary names or descriptions.

#### Deep dive

Important design choices include maximum size, eviction policy, weak versus strong references, tenant isolation, metrics, and whether canonical identity is exposed to callers. In many cases a normal cache such as Caffeine is safer than relying on `String.intern()`.

#### Production angle

Canonicalization can reduce memory, but an unbounded cache becomes a memory leak. Add metrics for size, hit rate, eviction and memory behavior.

#### Traps / caveats

- Do not canonicalize secrets or unbounded free text.
- Canonicalization must not change business meaning.
- Weak references are not a substitute for understanding lifecycle.

#### Optional Anki

Q: What is the first rule for a custom canonicalization cache?
A: Bound it and measure that it actually helps.

</details>
