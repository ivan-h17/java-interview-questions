# 05.12. Memory, GC and diagnostics

---

<a id="str-mem-001"></a>

<details>
<summary><strong>🧠 STR-MEM-001. How is a `String` represented in memory conceptually?</strong></summary>

#### Short answer

Conceptually, a `String` object stores immutable text plus metadata such as length-related state and cached hash information; actual storage is JVM-version dependent.

#### Interview answer

At the API level, a `String` is an object representing a sequence of UTF-16 code units. Internally, modern HotSpot stores string content in a byte array with a coder flag that distinguishes compact Latin-1-compatible content from UTF-16 content.

The exact fields are implementation details, but the practical point is that a string has object overhead plus backing storage.

#### Deep dive

Before Java 9, common HotSpot implementations used a `char[]` backing array. Java 9 introduced Compact Strings, allowing many strings to use one byte per character internally. The public API still behaves as a UTF-16 code-unit sequence.

#### Production angle

String memory can dominate heap usage in APIs, caches, JSON-heavy services and import pipelines. Heap dumps often show both `String` objects and backing arrays.

#### Traps / caveats

- Do not write code depending on private `String` fields.
- Compact storage is an implementation detail.
- `String.length()` is not memory size.

#### Optional Anki

Q: What are the two main parts of string memory cost?
A: The `String` object overhead and the backing storage.

</details>

<a id="str-mem-002"></a>

<details>
<summary><strong>🧠 STR-MEM-002. What are Compact Strings in Java 9+, and do they mean Java stores strings as UTF-8 internally?</strong></summary>

#### Short answer

Compact Strings let the JVM store Latin-1-compatible strings in one byte per character. They do not mean Java stores strings as UTF-8.

#### Interview answer

Java 9 introduced Compact Strings to reduce memory footprint. If a string's characters fit in Latin-1, HotSpot can store them in a byte array with a Latin-1 coder. Otherwise it uses UTF-16-style storage. The public `String` API still exposes UTF-16 code-unit semantics.

#### Deep dive

This optimization helps because many backend strings are ASCII or Latin-1-compatible: IDs, headers, JSON field names, SQL names and configuration keys. For non-Latin text, memory savings may be smaller or absent.

#### Production angle

Compact Strings reduce heap usage automatically in many services. It is usually not something application code should manage directly.

#### Traps / caveats

- Compact Strings are not UTF-8 strings.
- Do not assume one byte per user character.
- The optimization is JVM-specific.

#### Optional Anki

Q: Do Compact Strings change `String.length()` semantics?
A: No. The public API still uses UTF-16 code-unit semantics.

</details>

<a id="str-mem-003"></a>

<details>
<summary><strong>🧠 STR-MEM-003. Why is measuring or estimating `String` memory footprint non-trivial?</strong></summary>

#### Short answer

String memory depends on object headers, alignment, references, backing storage, compact encoding, JVM options and object sharing.

#### Interview answer

A string is not just `length * 2` bytes. It has object header overhead, fields, alignment padding and backing array overhead. Compact Strings may use one byte per character for some values. References may be compressed or not. Duplicate strings may or may not share backing storage through deduplication.

#### Deep dive

Heap dump tools report shallow size and retained size differently. Shallow size is the object itself; retained size includes objects only reachable through it. Shared backing data and references from collections complicate interpretation.

#### Production angle

Use tools such as heap dumps, JFR allocation profiling and object layout tools when memory footprint matters. Estimate only for rough reasoning.

#### Traps / caveats

- `String.length()` is not heap size.
- Retained size depends on the object graph.
- Version and JVM settings matter.

#### Optional Anki

Q: Why is string memory more than character count?
A: Objects have headers, fields, alignment and backing storage overhead.

</details>

<a id="str-mem-004"></a>

<details>
<summary><strong>STR-MEM-004. How do many short or duplicate strings affect heap usage?</strong></summary>

#### Short answer

Many short strings have high per-object overhead, and duplicate strings waste backing storage unless shared or removed.

#### Interview answer

A short string can cost much more than its text bytes because each string is an object with metadata and storage. Millions of small strings can dominate heap even when each value is tiny. Duplicate strings multiply the same content across many objects.

#### Deep dive

Common sources include JSON field names, CSV values, database result mapping, cache keys, tags, status values and log messages. Some duplicates are expected; the question is whether they are retained long enough to matter.

#### Production angle

Use heap dumps to identify duplicate values and retainers. Fixes can include better data modeling, canonicalization of bounded sets, avoiding unnecessary copies, streaming parsers or enabling GC string deduplication after measurement.

#### Traps / caveats

- A few duplicates do not justify complex optimization.
- Interning unbounded values can worsen memory.
- Sometimes the real leak is the collection retaining the strings.

#### Optional Anki

Q: Why are many short strings expensive?
A: Per-object overhead can dominate the actual text content.

</details>

<a id="str-mem-005"></a>

<details>
<summary><strong>STR-MEM-005. How can large strings or temporary string creation affect allocation rate, GC pressure and latency?</strong></summary>

#### Short answer

Large or frequent temporary strings increase allocation, memory bandwidth and GC work, which can increase latency.

#### Interview answer

Temporary strings are collected eventually, but high allocation rate keeps the GC busy. Large strings can also create high peak memory usage and expensive copies. In hot paths, repeated parsing, splitting, formatting and concatenation can become a latency problem.

#### Deep dive

Even if most objects die young, allocation is not free. It consumes CPU, memory bandwidth and young-generation space. Large objects may also be treated differently by the GC depending on size and collector.

#### Production angle

Look at allocation profiling, GC logs, JFR events and p95/p99 latency. Fixes include streaming, builders, avoiding regex in hot paths, reducing logging allocation and using parsers that avoid unnecessary materialization.

#### Traps / caveats

- Low retained heap does not mean low allocation rate.
- Manual caching can create leaks.
- Optimize based on profiles, not style preferences.

#### Optional Anki

Q: What is allocation rate?
A: The amount of memory allocated per unit of time.

</details>

<a id="str-mem-006"></a>

<details>
<summary><strong>STR-MEM-006. How would you reduce memory usage in a string-heavy service?</strong></summary>

#### Short answer

Measure first, then reduce retention, duplicates, unnecessary copies and huge in-memory strings.

#### Interview answer

I would start with a heap dump and allocation profile. Then identify whether the problem is many duplicates, large strings, temporary strings, caches, logs or parsing. Fixes could include bounded caches, streaming processing, avoiding raw payload retention, normalizing bounded repeated values, using value objects, or enabling string deduplication after testing.

#### Deep dive

The best fix depends on retainers. If a cache keeps strings alive, tune eviction. If JSON parsing creates too many copies, use streaming or avoid mapping unused fields. If duplicate small values dominate, canonicalize a bounded dictionary or test G1 deduplication.

#### Production angle

Add metrics for cache size, payload sizes, allocation rate and GC. Roll out memory optimizations carefully because they can trade memory for CPU.

#### Traps / caveats

- Do not intern all strings.
- Do not optimize without knowing retainers.
- Do not keep raw request/response bodies in logs or exceptions.

#### Optional Anki

Q: What is the first step in reducing string memory?
A: Measure with heap dumps or allocation profiling.

</details>

<a id="str-gc-001"></a>

<details>
<summary><strong>🧠 STR-GC-001. What is G1 String deduplication, and does it deduplicate `String` objects or backing storage?</strong></summary>

#### Short answer

G1 String deduplication is a JVM optimization that can make equal strings share backing storage; it does not merge the `String` objects themselves.

#### Interview answer

With G1 String deduplication enabled, the JVM can detect strings with equal content and point them to shared backing storage. The `String` objects remain separate, so reference identity does not change and `==` remains false for distinct objects.

#### Deep dive

The goal is reducing heap usage for duplicate string contents. The JVM does additional work to inspect strings and manage deduplication candidates, so it is not free.

#### Production angle

It can help services with many retained duplicate strings, such as import jobs, JSON-heavy services or caches. It should be tested with real workloads.

#### Traps / caveats

- It is not the same as `intern()`.
- It does not fix unbounded retention.
- It can increase CPU or GC work.

#### Optional Anki

Q: Does G1 string deduplication make `a == b` true?
A: No. It can share backing storage, not object identity.

</details>

<a id="str-gc-002"></a>

<details>
<summary><strong>🧠 STR-GC-002. When can String deduplication help, and what are its costs?</strong></summary>

#### Short answer

It can help when many equal strings are retained long enough. Its costs are extra GC work, CPU and bookkeeping.

#### Interview answer

String deduplication is useful when heap dumps show many duplicate string values retained in memory. It is less useful when strings are mostly unique, very short-lived or not a major part of the heap.

The cost is that the JVM must identify candidates, compare contents and update references to backing storage.

#### Deep dive

Deduplication benefits depend on workload, string lifetime and duplicate ratio. It should be evaluated with memory, CPU, GC pause and throughput metrics.

#### Production angle

Enable it only after testing on realistic traffic or data. Watch heap usage, allocation rate, GC CPU, pause times and service latency.

#### Traps / caveats

- It does not replace fixing leaks.
- It may not help short-lived temporary strings.
- It should not change application equality behavior.

#### Optional Anki

Q: What workload benefits from string deduplication?
A: One with many retained duplicate string values.

</details>

<a id="str-gc-003"></a>

<details>
<summary><strong>STR-GC-003. How can caches, interning, `ThreadLocal` values or log buffers keep strings alive?</strong></summary>

#### Short answer

They can hold strong references to strings longer than the business operation, preventing garbage collection.

#### Interview answer

A string is collectable only when nothing reachable references it. Caches may retain keys and values. Interning may retain canonical values. `ThreadLocal` values can live as long as pooled threads. Async log buffers or queues can hold messages and payloads.

#### Deep dive

The string itself may not be the leak's root cause. The real problem is the owner object that keeps it reachable. Heap dumps should be analyzed by retainers, not just by counting strings.

#### Production angle

Add cache bounds, remove `ThreadLocal` values, avoid logging raw payloads and monitor queue sizes. Be especially careful with request bodies, headers and tokens.

#### Traps / caveats

- A heap dominated by strings often points to a retaining collection.
- Thread pools make `ThreadLocal` leaks long-lived.
- Logging can retain sensitive strings as well as memory.

#### Optional Anki

Q: What should you inspect when strings dominate a heap dump?
A: Retainers: who is keeping those strings alive.

</details>

<a id="str-diag-001"></a>

<details>
<summary><strong>🧠 STR-DIAG-001. How would you inspect string-heavy memory usage in a heap dump?</strong></summary>

#### Short answer

Look at histogram, dominator tree, duplicate strings and retained paths to find who owns the strings.

#### Interview answer

I would start with a class histogram to see how much memory is in `String` and backing arrays. Then I would use the dominator tree to find retaining objects. I would inspect duplicate string reports and paths to GC roots to understand why values stay alive.

#### Deep dive

Important questions: are there many duplicate small strings, a few huge strings, or strings retained by a cache/list/map/thread? Are they payloads, keys, log messages, parsed fields or secrets?

#### Production angle

Heap dumps may contain PII and credentials, so handle them as sensitive artifacts. Capture them securely and delete them according to policy.

#### Traps / caveats

- Class histogram alone does not show ownership.
- Retained size is often more useful than shallow size.
- Duplicate strings are not always worth optimizing.

#### Optional Anki

Q: What heap-dump view helps find who owns memory?
A: The dominator tree and paths to GC roots.

</details>

<a id="str-diag-002"></a>

<details>
<summary><strong>🧠 STR-DIAG-002. How can Java Flight Recorder or allocation profiling reveal string hot spots?</strong></summary>

#### Short answer

They show where strings and backing arrays are allocated and which code paths produce allocation pressure.

#### Interview answer

Heap dumps show what is retained at a point in time. Allocation profiling shows what is being created over time. JFR can capture allocation events, hot methods, GC behavior and allocation pressure related to string-heavy code.

#### Deep dive

A service can have low retained string memory but high allocation rate from temporary strings. Allocation profiling reveals operations such as regex splitting, formatting, JSON parsing, logging or repeated concatenation.

#### Production angle

Use low-overhead profiling in staging or production-like environments. Optimize the paths that show meaningful allocation or CPU impact.

#### Traps / caveats

- Sampling profilers may miss some allocations.
- Debug builds or synthetic tests can mislead.
- Do not optimize a cold path just because it allocates.

#### Optional Anki

Q: What does allocation profiling show that a heap dump may not?
A: Short-lived allocations and their source code paths.

</details>

<a id="str-diag-003"></a>

<details>
<summary><strong>STR-DIAG-003. How do you find who keeps a string alive?</strong></summary>

#### Short answer

Use heap dump reference paths, dominator tree and GC-root analysis.

#### Interview answer

In a heap analyzer, select the string or group of strings and inspect incoming references or paths to GC roots. The goal is to find the owning collection, cache, thread, classloader, queue or object graph that retains the value.

#### Deep dive

A string may be retained directly as a value, as a map key, inside a DTO, inside a log event, or through a thread-local context. The shortest path to a GC root is useful, but the dominator tree often gives a better view of bulk retention.

#### Production angle

Once the retainer is known, the fix is usually a lifecycle fix: eviction, clearing, scoping, streaming, removing unnecessary fields or redacting logs.

#### Traps / caveats

- The string class is rarely the root cause.
- Multiple retainers can keep the same value alive.
- Interned strings and literals need careful interpretation.

#### Optional Anki

Q: What does "path to GC root" answer?
A: Why an object is still reachable and cannot be collected.

</details>

<a id="str-diag-004"></a>

<details>
<summary><strong>STR-DIAG-004. How should heap dumps that may contain sensitive strings be handled?</strong></summary>

#### Short answer

Treat heap dumps as sensitive data: restrict access, store securely, redact when possible and delete them when no longer needed.

#### Interview answer

Heap dumps can contain passwords, tokens, PII, request payloads, database URLs and session data as strings. They should be captured only when necessary, transferred securely, stored with limited access and removed according to incident or retention policy.

#### Deep dive

Automatic heap dumps on `OutOfMemoryError` are useful but risky. Production systems should define where dumps are written, who can read them and how they are protected.

#### Production angle

A heap dump can be as sensitive as a database snapshot. Include heap-dump handling in operational runbooks.

#### Traps / caveats

- Do not upload raw heap dumps to random tools.
- Be careful sharing dumps in tickets or chat.
- Redaction after capture may be difficult.

#### Optional Anki

Q: Why are heap dumps sensitive?
A: They can contain secrets, tokens, PII and raw request data.

</details>
