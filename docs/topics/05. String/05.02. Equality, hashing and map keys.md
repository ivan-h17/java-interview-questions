# 05.02. Equality, hashing and map keys

---

<a id="str-eq-001"></a>

<details>
<summary><strong>STR-EQ-001. What is the difference between `==` and `equals()` for strings?</strong></summary>

#### Short answer

`==` compares object references. `equals()` compares string content.

#### Interview answer

For objects in Java, `==` answers "are these references pointing to the same object?" `String.equals()` answers "do these strings contain the same sequence of characters?" Business string comparison almost always needs `equals()`.

Two separate string objects can contain the same text, so `a == b` can be false while `a.equals(b)` is true.

#### Deep dive

String literals are interned, so two equal literals may point to the same object. Runtime-created strings usually are not the same object unless interned or reused by the program. This is why `==` creates inconsistent behavior.

#### Production angle

Using `==` for request parameters, roles, IDs or status values can cause logic to pass in tests and fail in production when the string comes from JSON, a database or a network request.

#### Traps / caveats

- Use `Objects.equals(a, b)` when either value may be `null`.
- `==` is fine only when identity is intentionally being tested.
- Interning does not justify using `==` for business values.

#### Optional Anki

Q: What should you use for string content comparison?
A: `equals()` or `Objects.equals()`.

</details>

<a id="str-eq-002"></a>

<details>
<summary><strong>STR-EQ-002. Why can comparing strings with `==` appear to work sometimes and fail later?</strong></summary>

#### Short answer

It can appear to work because literals are interned, but fail when strings are created dynamically.

#### Interview answer

String literals like `"OK"` are placed in the String Pool, so two references to the same literal often point to the same object. But strings read from HTTP, JSON, databases, files or built at runtime are separate objects unless explicitly interned or reused.

So `status == "OK"` may pass for a hardcoded test value and fail for the same text read from a request.

#### Deep dive

Compile-time constants can also be interned. Runtime concatenation or decoding from bytes creates ordinary strings. `intern()` can canonicalize a value, but it is not a general solution for equality because it has memory and coupling risks.

#### Production angle

This bug is especially dangerous because it is nondeterministic from the business perspective: the same visible value behaves differently depending on how it was created.

#### Traps / caveats

- Unit tests with literals may miss the bug.
- `new String("x") == "x"` is false unless interned.
- Do not "fix" this by interning all user input.

#### Optional Anki

Q: Why does `==` sometimes work for strings?
A: Some strings, especially literals, may reference the same interned object.

</details>

<a id="str-eq-003"></a>

<details>
<summary><strong>STR-EQ-003. What does `equalsIgnoreCase()` do, and what are its limitations?</strong></summary>

#### Short answer

`equalsIgnoreCase()` compares two strings while ignoring case, but it is not a full locale-aware or normalization-aware text comparison.

#### Interview answer

`equalsIgnoreCase()` is useful for simple case-insensitive comparisons such as protocol constants or internal identifiers. It compares same-length strings by Unicode code points ignoring case, but it does not take locale into account and does not handle all human-language expectations, collation, Unicode normalization or domain-specific equivalence.

#### Deep dive

Case-insensitive comparison is harder than just lower-casing both values. Some languages have special casing rules, visually identical text can use different Unicode representations, and some case mappings are multi-character mappings. For example, one character such as German sharp S is not generally equal to the two-character string `"SS"` under `equalsIgnoreCase()`.

For user-facing text, use locale-aware APIs such as `Collator` where appropriate.

#### Production angle

For internal constants like `"GET"` or `"application/json"`, `equalsIgnoreCase()` is often fine. For usernames, names, search and user-visible sorting, define explicit normalization and locale behavior.

#### Traps / caveats

- It does not trim whitespace.
- It does not normalize Unicode.
- It does not perform full multi-character case folding.
- It is not a replacement for `Collator` in human-language sorting.

#### Optional Anki

Q: Is `equalsIgnoreCase()` locale-aware sorting?
A: No. It is a case-insensitive equality check, not human-language collation.

</details>

<a id="str-eq-004"></a>

<details>
<summary><strong>STR-EQ-004. How does `String.hashCode()` work conceptually, and is it cached?</strong></summary>

#### Short answer

`String.hashCode()` computes a deterministic hash from the string content, and Java caches the computed hash in the `String` object.

#### Interview answer

The hash code is based on the characters in the string, so equal strings have equal hash codes. It is used by hash-based collections such as `HashMap` and `HashSet` to choose a bucket before confirming equality with `equals()`.

Because strings are immutable, the computed hash can be cached safely.

#### Deep dive

The exact algorithm is specified by the Java API and is stable for `String`. It is not cryptographic and does not prove uniqueness. A cached zero hash has special handling in modern JDKs so strings whose actual hash is zero can still be represented correctly.

#### Production angle

String hashing is central to maps, caches and routing tables. Heavy use of very long string keys can make hashing and equality checks visible in CPU profiles.

#### Traps / caveats

- Equal strings must have equal hash codes.
- Equal hash codes do not mean equal strings.
- Java hash codes are not security hashes.

#### Optional Anki

Q: Why can `String` cache its hash code?
A: Because its content is immutable.

</details>

<a id="str-eq-005"></a>

<details>
<summary><strong>STR-EQ-005. Can two different strings have the same hash code, and why does that matter?</strong></summary>

#### Short answer

Yes. Hash collisions are possible and normal, so `HashMap` must still use `equals()`.

#### Interview answer

`hashCode()` returns an `int`, but there are far more possible strings than integer hash values. Therefore different strings can share the same hash code. Hash-based collections use the hash to narrow the search and then use `equals()` to find the exact key.

#### Deep dive

Collisions do not cause data loss by themselves. They affect performance because more candidates must be checked. Pathological collisions can make hash-heavy code slower, though modern `HashMap` has collision mitigation for certain bucket shapes.

#### Production angle

For normal business strings this is usually not a concern. For untrusted high-volume input, cache keys and request maps, avoid designs that allow attackers or bad data to create huge collision-heavy maps.

#### Traps / caveats

- Never compare hash codes instead of calling `equals()`.
- Hash collisions are expected.
- A hash code is not a unique ID.

#### Optional Anki

Q: Does same `hashCode()` prove strings are equal?
A: No. `equals()` is still required.

</details>

<a id="str-eq-006"></a>

<details>
<summary><strong>STR-EQ-006. Why is `String` commonly used as a `HashMap` key?</strong></summary>

#### Short answer

Strings are immutable, have value-based equality and provide stable hash codes, which makes them reliable map keys.

#### Interview answer

A good `HashMap` key needs stable equality and a stable hash code while it is in the map. `String` satisfies this because its content cannot change and its `equals()` and `hashCode()` are based on content.

Strings are also convenient for names, identifiers, headers, configuration keys and protocol values.

#### Deep dive

The risk is not the `String` class itself, but key design. Raw user input may differ by case, whitespace, Unicode normalization or encoding. A string key may also be too broad when the domain really needs a typed value object.

#### Production angle

String map keys work well for controlled identifiers. For user-controlled keys, normalize and bound input carefully. For domain concepts like `UserId` or `CurrencyCode`, a value object may be safer and clearer.

#### Traps / caveats

- Raw strings can make domain models stringly typed.
- Normalize before lookup when business equality requires it.
- Unbounded string keys can make caches grow without limit.

#### Optional Anki

Q: Why is `String` a stable `HashMap` key?
A: It is immutable and has content-based `equals()` and `hashCode()`.

</details>

<a id="str-eq-007"></a>

<details>
<summary><strong>STR-EQ-007. How should you compare strings safely when either value can be `null`?</strong></summary>

#### Short answer

Use `Objects.equals(a, b)` or call `constant.equals(value)` when comparing to a non-null constant.

#### Interview answer

If either reference may be `null`, calling `a.equals(b)` can throw `NullPointerException`. `Objects.equals(a, b)` handles nulls: it returns true if both are null, false if one is null, and otherwise delegates to `equals()`.

For constants, `"ACTIVE".equals(status)` is also safe because the constant is never null.

#### Deep dive

Null-safe comparison should not replace clear validation. Sometimes `null` and empty are different states, and treating both as equal can hide data-quality problems.

#### Production angle

Null-safe comparisons reduce incidental runtime failures in request mapping, configuration parsing and DTO processing. Boundary validation should still define which values are allowed.

#### Traps / caveats

- `Objects.equals(null, "")` is false.
- `equalsIgnoreCase()` still needs null handling.
- Avoid normalizing nulls to empty strings unless that is the actual business rule.

#### Optional Anki

Q: What is a null-safe way to compare two strings?
A: `Objects.equals(a, b)`.

</details>
