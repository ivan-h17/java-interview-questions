# JWT, OAuth2 and OpenID Connect

---

<a id="sec-oauth-001"></a>

<details>
<summary><strong>SEC-OAUTH-001. What is OAuth2, and what problem does it solve?</strong></summary>

#### Short answer

OAuth2 is an authorization framework for delegated access to protected resources.

#### Interview answer

OAuth2 lets a client obtain limited access to a resource without handling the user's primary credentials directly. Instead of giving an application a password, the user authorizes access through an authorization server, and the client receives tokens with limited lifetime and scope.

For backend services, OAuth2 is commonly used for API access, third-party integrations, service-to-service calls and resource-server protection.

#### Deep dive

OAuth2 is about authorization and delegation. It does not by itself define a complete user identity protocol; OpenID Connect adds that layer.

#### Production angle

OAuth2 reduces credential sharing, enables scoped access and centralizes token issuance, but incorrect token validation or scope design can still create serious authorization bugs.

#### Traps / caveats

- OAuth2 is not the same as login by itself.
- Scopes are not a replacement for object-level authorization.
- Bearer tokens must be protected like credentials.

#### Optional Anki

Q: What problem does OAuth2 mainly solve?
A: Delegated limited access without sharing primary credentials.

</details>

<a id="sec-oauth-002"></a>

<details>
<summary><strong>SEC-OAUTH-002. How is OpenID Connect different from OAuth2?</strong></summary>

#### Short answer

OpenID Connect adds an identity layer on top of OAuth2.

#### Interview answer

OAuth2 provides delegated authorization. OpenID Connect, or OIDC, adds standardized authentication information, especially the ID token, which tells a client who the user is and how authentication happened.

In simple terms: OAuth2 answers "can this client access this resource?" while OIDC helps answer "who is the user?"

#### Deep dive

APIs should usually use access tokens for authorization. ID tokens are intended for clients, not as general-purpose API access tokens.

#### Production angle

Confusing access tokens and ID tokens can cause APIs to accept tokens that were not meant for them.

#### Traps / caveats

- Do not use an ID token as an API authorization token unless the architecture explicitly supports it.
- Validate issuer, audience and lifetime.
- Authentication does not prove permission to every resource.

#### Optional Anki

Q: What does OIDC add to OAuth2?
A: A standardized identity/authentication layer.

</details>

<a id="sec-oauth-003"></a>

<details>
<summary><strong>SEC-OAUTH-003. What is the difference between an access token, ID token and refresh token?</strong></summary>

#### Short answer

Access tokens call APIs, ID tokens describe authentication to clients, and refresh tokens obtain new tokens.

#### Interview answer

An access token is presented to a resource server to access an API. An ID token is used by a client to learn authenticated user identity in OIDC. A refresh token is held by a client to get new access tokens without making the user log in again.

They have different audiences, lifetimes and security risks.

#### Deep dive

Access tokens should be short-lived. Refresh tokens are more sensitive because they can mint new access tokens and should be stored and rotated carefully.

#### Production angle

Logging or storing any of these tokens unsafely can lead to account takeover or API abuse.

#### Traps / caveats

- A signed token is not necessarily encrypted.
- Do not put secrets or unnecessary PII into tokens.
- Check the token audience before trusting it.

#### Optional Anki

Q: Which token is normally sent to an API?
A: Access token.

</details>

<a id="sec-oauth-004"></a>

<details>
<summary><strong>SEC-OAUTH-004. What is the difference between a resource server, authorization server, OAuth2 client and API gateway?</strong></summary>

#### Short answer

The authorization server issues tokens, the client obtains tokens, the resource server protects APIs, and the gateway routes or enforces edge policy.

#### Interview answer

An authorization server authenticates users or clients and issues tokens. An OAuth2 client requests and uses tokens. A resource server validates access tokens and protects resources. An API gateway sits at the edge and may route traffic, validate tokens, rate limit or add headers.

These roles can be separate services or combined in simple systems, but the responsibility boundaries should be clear.

#### Deep dive

Spring Boot services are commonly resource servers when they expose protected APIs, and OAuth2 clients when they call another protected API.

#### Production angle

Confusing these roles leads to misplaced trust, such as assuming the gateway's token check replaces service authorization.

#### Traps / caveats

- A gateway is not automatically the source of truth for business permissions.
- Resource servers must validate tokens meant for them.
- Client credentials identify a client, not an end user.

#### Optional Anki

Q: Which OAuth2 role protects an API?
A: Resource server.

</details>

<a id="sec-oauth-005"></a>

<details>
<summary><strong>SEC-OAUTH-005. How does JWT authentication work in a Spring Boot resource server?</strong></summary>

#### Short answer

The resource server reads the bearer token, validates it and converts claims into an authenticated principal and authorities.

#### Interview answer

In a Spring Boot resource server, a request includes an `Authorization: Bearer ...` token. Spring Security validates the JWT signature and important claims, then builds an `Authentication`. Claims such as subject, scopes or roles can be converted into authorities used by authorization rules.

Only after validation should the application trust token contents.

#### Deep dive

JWT validation often depends on issuer metadata and JWK keys. Authority mapping may need customization because identity providers use different claim names.

#### Production angle

Bad JWT setup can accept expired tokens, tokens from the wrong issuer, or tokens intended for another API.

#### Traps / caveats

- Do not parse JWT claims manually and skip validation.
- Validate audience when the API requires it.
- Test real authority mapping, not only mock users.

#### Optional Anki

Q: What must happen before trusting JWT claims?
A: Signature and claim validation.

</details>

<a id="sec-oauth-006"></a>

<details>
<summary><strong>SEC-OAUTH-006. Which JWT claims and token properties must a resource server validate?</strong></summary>

#### Short answer

Validate signature, issuer, audience, expiration, token timing, algorithm/key assumptions and the claims used for authorization.

#### Interview answer

At minimum, a resource server should verify that the token signature is valid, the issuer is trusted, the token is not expired, the audience matches the API and the algorithm/key are expected. Claims such as subject, scopes, roles, tenant and client ID should be interpreted according to the authorization server's contract.

The exact set depends on the identity provider and API security model.

#### Deep dive

Useful timing claims include expiration and sometimes not-before or issued-at checks. Clock skew should be bounded rather than ignored.

#### Production angle

Audience or issuer mistakes can let tokens from another environment, client or API access production resources.

#### Traps / caveats

- Signature validation alone is not enough.
- Do not accept unexpected algorithms.
- Do not trust authorization claims without knowing who issued them.

#### Optional Anki

Q: JWT validation beyond signature?
A: Issuer, audience, expiry, timing and trusted authorization claims.

</details>

<a id="sec-oauth-007"></a>

<details>
<summary><strong>SEC-OAUTH-007. What is the difference between JWT validation and opaque token introspection?</strong></summary>

#### Short answer

JWT validation is local cryptographic validation; opaque token introspection asks the authorization server about the token.

#### Interview answer

A JWT is self-contained and signed, so a resource server can validate it locally using trusted keys and claims. An opaque token has no useful meaning to the resource server, so the server calls an introspection endpoint to learn whether it is active and what it represents.

JWTs reduce runtime dependency on the authorization server, while introspection gives stronger central control and revocation behavior.

#### Deep dive

Opaque tokens can be easier to revoke quickly. JWTs often rely on short lifetimes, revocation lists or key rotation for early invalidation.

#### Production angle

Introspection adds latency and dependency risk; JWTs add cache/key rotation and revocation trade-offs.

#### Traps / caveats

- Do not treat an opaque token as a JWT.
- Cache introspection carefully.
- Short JWT lifetime helps but does not replace all revocation needs.

#### Optional Anki

Q: JWT validation vs introspection?
A: Local validation vs remote active-token check.

</details>

<a id="sec-oauth-008"></a>

<details>
<summary><strong>SEC-OAUTH-008. What are scopes, authorities and roles, and how are they mapped in Spring Security?</strong></summary>

#### Short answer

Scopes describe granted token permissions; Spring maps claims into authorities used by authorization rules.

#### Interview answer

OAuth scopes are permissions granted to a client or token, such as `orders:read`. Spring Security authorization decisions use `GrantedAuthority`. A resource server usually converts token claims such as `scope`, `scp`, `roles` or custom claims into authorities. Roles are a common authority convention, often prefixed with `ROLE_`.

The mapping must match the identity provider and application policy.

#### Deep dive

Scopes usually express API-level permissions, while domain authorization still checks ownership, tenant and object state.

#### Production angle

Wrong claim mapping can make valid users forbidden or, worse, grant access too broadly.

#### Traps / caveats

- `hasRole` and `hasAuthority` have different conventions.
- Scope names should be designed, not copied randomly.
- Roles alone rarely solve object-level authorization.

#### Optional Anki

Q: What does Spring Security check in authorization rules?
A: Authorities, often mapped from token claims.

</details>

<a id="sec-oauth-009"></a>

<details>
<summary><strong>SEC-OAUTH-009. What OAuth2 flow should a backend use for service-to-service calls, and when is client credentials appropriate?</strong></summary>

#### Short answer

For machine-to-machine calls without an end user, client credentials is commonly appropriate.

#### Interview answer

The client credentials flow lets a service authenticate as itself and obtain an access token for another service. It is suitable for backend jobs, internal service calls and integrations where the action is performed by the service, not on behalf of a user.

If the downstream call must preserve user intent, use a design that carries delegated user context explicitly, such as token relay or token exchange, depending on the platform.

#### Deep dive

Client credentials tokens should have narrow scopes and identify the calling service clearly. They should not be used to fake a human user.

#### Production angle

Service-to-service identity makes audit and least privilege possible across microservices.

#### Traps / caveats

- Client credentials has no user by default.
- Do not share one client secret across many services.
- Downstream services still need authorization rules.

#### Optional Anki

Q: What does client credentials identify?
A: The client/service, not an end user.

</details>

<a id="sec-oauth-010"></a>

<details>
<summary><strong>🧠 SEC-OAUTH-010. How should a backend safely propagate user identity or authorization context to downstream services?</strong></summary>

#### Short answer

Propagate only verified context through a deliberate mechanism, and let downstream services enforce their own authorization.

#### Interview answer

Common patterns include token relay, token exchange, signed internal tokens or gateway-added identity headers protected by network and service identity controls. The backend should not forward arbitrary client-supplied headers as identity. It should preserve enough context for audit and authorization without leaking excess PII or over-broad permissions.

Downstream services must still validate the caller and enforce resource-level rules.

#### Deep dive

Sometimes the downstream operation should run as the service rather than the user. That decision affects audit logs, permissions and incident analysis.

#### Production angle

Unsafe propagation creates confused-deputy bugs, where one service uses its authority to perform actions the user was not allowed to do.

#### Traps / caveats

- Do not trust `X-User-*` headers from clients.
- Avoid forwarding long-lived user tokens everywhere.
- Audit both user identity and calling service identity when relevant.

#### Optional Anki

Q: Main danger in downstream identity propagation?
A: Confused-deputy or spoofed identity bugs.

</details>

<a id="sec-oauth-011"></a>

<details>
<summary><strong>SEC-OAUTH-011. What are refresh tokens, and what risks do they introduce?</strong></summary>

#### Short answer

Refresh tokens let clients obtain new access tokens, so they are long-lived sensitive credentials.

#### Interview answer

Access tokens are usually short-lived. Refresh tokens let a client get new access tokens without sending the user through login every time. This improves usability, but a stolen refresh token may provide ongoing access until revoked, expired or detected.

Refresh tokens should be stored securely, scoped carefully and rotated or invalidated according to the client type and risk.

#### Deep dive

Browser, mobile and backend clients have different storage options. Public clients cannot protect secrets the way backend clients can.

#### Production angle

Refresh-token compromise can survive password changes unless session and token revocation behavior is designed correctly.

#### Traps / caveats

- Do not expose refresh tokens to logs or JavaScript unless the architecture explicitly accepts that risk.
- Use short access-token lifetimes.
- Logout should consider refresh token invalidation.

#### Optional Anki

Q: Why are refresh tokens sensitive?
A: They can mint new access tokens.

</details>

<a id="sec-oauth-012"></a>

<details>
<summary><strong>🧠 SEC-OAUTH-012. What is refresh token rotation?</strong></summary>

#### Short answer

Refresh token rotation issues a new refresh token on use and invalidates or marks the old one as used.

#### Interview answer

With rotation, each refresh request returns a new access token and a new refresh token. The previous refresh token should not be accepted again except possibly within a small controlled race window. Reuse of an old token can indicate theft and trigger revocation of the token family.

This limits the useful lifetime of a stolen refresh token.

#### Deep dive

Rotation needs server-side state to track token families, reuse and invalidation. It also needs careful handling of network retries and parallel refreshes.

#### Production angle

Rotation improves compromise detection, but bad implementation can log users out randomly or fail under concurrent client requests.

#### Traps / caveats

- Handle retry races intentionally.
- Store token identifiers or hashes, not raw tokens when possible.
- Alert on suspicious reuse.

#### Optional Anki

Q: What does refresh token reuse after rotation suggest?
A: Possible token theft or a race condition.

</details>

<a id="sec-oauth-013"></a>

<details>
<summary><strong>🧠 SEC-OAUTH-013. What is PKCE, and why is it important for public clients?</strong></summary>

#### Short answer

PKCE binds the authorization request to the token exchange so intercepted authorization codes are less useful.

#### Interview answer

Public clients such as SPAs and mobile apps cannot safely keep a client secret. PKCE adds a generated code verifier and code challenge to the authorization-code flow. The token endpoint requires the verifier, so stealing only the authorization code is not enough to redeem it.

PKCE is especially important when the authorization code travels through browser or app redirects.

#### Deep dive

PKCE improves the authorization-code flow for public clients, but it does not protect tokens after they are issued.

#### Production angle

Without PKCE, interception of an authorization code can lead to token theft in public-client flows.

#### Traps / caveats

- PKCE is not a substitute for redirect URI validation.
- It does not solve XSS token theft.
- Backend confidential clients may still use client authentication.

#### Optional Anki

Q: What does PKCE protect?
A: The authorization code exchange for public clients.

</details>

<a id="sec-oauth-014"></a>

<details>
<summary><strong>🧠 SEC-OAUTH-014. What are JWK sets and key rotation, and how can they break services?</strong></summary>

#### Short answer

JWK sets publish cryptographic keys, commonly public keys used by resource servers to validate signed tokens; rotation changes those keys over time.

#### Interview answer

A JWT resource server validates token signatures using public keys from a trusted JWK set. During key rotation, the authorization server may start signing tokens with a new key while old tokens signed by the previous key are still valid. Resource servers need to refresh keys and handle overlap correctly.

If caching, network access or key IDs are misconfigured, valid tokens may suddenly fail.

#### Deep dive

A good rotation process has overlap: publish the new key before using it, keep old keys until old tokens expire and monitor validation failures.

#### Production angle

Bad key rotation can cause a fleet-wide authentication outage.

#### Traps / caveats

- Do not cache JWKs forever.
- Do not remove old keys before old tokens expire.
- Monitor spikes in token validation errors.

#### Optional Anki

Q: Why keep old JWKs during rotation?
A: Existing unexpired tokens may still be signed with old keys.

</details>
