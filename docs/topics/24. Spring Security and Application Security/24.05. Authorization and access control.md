# Authorization and access control

---

<a id="sec-authz-001"></a>

<details>
<summary><strong>SEC-AUTHZ-001. What is the difference between role-based and attribute-based access control?</strong></summary>

#### Short answer

RBAC uses roles; ABAC uses attributes of the user, resource, action and environment.

#### Interview answer

Role-based access control grants permissions through roles such as `ADMIN`, `MANAGER` or `SUPPORT`. Attribute-based access control makes decisions from richer context: user department, tenant, resource owner, operation type, time, risk score or record status.

RBAC is simpler and common. ABAC is more flexible for complex domains, but it needs clear policy design and good tests.

#### Deep dive

Real systems often combine both: a role allows access to a feature, then attributes decide which records or actions are allowed.

#### Production angle

RBAC alone often fails in multi-tenant or ownership-heavy systems because two users with the same role may need access to different resources.

#### Traps / caveats

- Roles are not object ownership.
- ABAC policies can become hard to reason about.
- Permission names should map to business actions, not UI buttons only.

#### Optional Anki

Q: RBAC vs ABAC?
A: Roles vs contextual attributes.

</details>

<a id="sec-authz-002"></a>

<details>
<summary><strong>SEC-AUTHZ-002. What is method security in Spring Security?</strong></summary>

#### Short answer

Method security applies authorization checks around method calls, commonly with annotations such as `@PreAuthorize`.

#### Interview answer

Spring method security lets you protect service methods using expressions that check roles, authorities, arguments or custom policy methods. It is useful when authorization belongs near business operations rather than only at the HTTP route.

For example, a service method can require a scope and also check whether the current user may access the requested account ID.

#### Deep dive

Method security is often proxy-based, so calls must pass through the Spring-managed proxy for the advice to run.

#### Production angle

Method security protects code paths reused by controllers, messaging handlers, scheduled jobs or other services, assuming the call path is designed correctly.

#### Traps / caveats

- Self-invocation can bypass proxy-based checks.
- Method security does not automatically constrain repository queries.
- Complex authorization should be tested with denied cases.

#### Optional Anki

Q: Where is method security commonly used?
A: Around service-layer methods.

</details>

<a id="sec-authz-003"></a>

<details>
<summary><strong>SEC-AUTHZ-003. How does `@PreAuthorize` differ from URL-based authorization rules?</strong></summary>

#### Short answer

URL rules protect request paths; `@PreAuthorize` protects method invocations and can use method arguments.

#### Interview answer

URL-based rules are good for coarse web boundaries, such as requiring authentication for `/api/**` or admin role for `/admin/**`. `@PreAuthorize` runs before a method call and can check authorities, arguments and custom expressions, such as whether the current user can access a specific account ID.

They solve different layers and are often used together.

#### Deep dive

URL rules may not protect non-HTTP entry points. Method rules may not run if the method is called inside the same class without going through the proxy.

#### Production angle

Layered authorization reduces accidental exposure when a new controller calls an existing sensitive service method.

#### Traps / caveats

- URL patterns can be too broad or too narrow.
- `@PreAuthorize` must be enabled and tested.
- Neither replaces database-level tenant constraints where needed.

#### Optional Anki

Q: Main advantage of `@PreAuthorize`?
A: It can use method arguments and protect business methods.

</details>

<a id="sec-authz-004"></a>

<details>
<summary><strong>SEC-AUTHZ-004. When should authorization checks happen in controllers, services or repositories?</strong></summary>

#### Short answer

Use controllers for coarse request checks, services for business authorization and repositories/queries for data constraints.

#### Interview answer

Controllers can enforce route-level requirements and reject obviously invalid access. Services should enforce the real business rule: who can perform this action on this resource in this state. Repositories or queries should include tenant and ownership predicates when broad data access would be unsafe.

Important authorization should not live only in the controller.

#### Deep dive

The right placement depends on what information is needed. Object-level checks often require loading resource metadata or querying within a tenant boundary.

#### Production angle

Service-level and query-level authorization protect reuse through batch jobs, message consumers and new API endpoints.

#### Traps / caveats

- Controller-only checks are easy to bypass later.
- Repository-only checks can hide business policy.
- Filtering after loading can leak data and waste resources.

#### Optional Anki

Q: Where should business authorization usually live?
A: In the service/domain layer, with query constraints where needed.

</details>

<a id="sec-authz-005"></a>

<details>
<summary><strong>SEC-AUTHZ-005. What are BOLA / IDOR vulnerabilities, and why are they more than missing authentication?</strong></summary>

#### Short answer

BOLA/IDOR happens when an authenticated user can access another user's object by changing an identifier.

#### Interview answer

Broken object-level authorization, also called IDOR, occurs when an API checks that the caller is logged in but does not verify access to the specific object. For example, changing `/orders/123` to `/orders/124` should not return another user's order unless the caller has permission.

The bug is not missing login; it is missing per-object authorization.

#### Deep dive

Random UUIDs reduce guessing but do not fix the authorization problem. The service still must check ownership, tenant, relationship or policy.

#### Production angle

BOLA is one of the most common and damaging API issues because it can leak large amounts of customer data through simple enumeration.

#### Traps / caveats

- Do not rely on unguessable IDs alone.
- Test negative ownership cases.
- Admin support flows need explicit policy too.

#### Optional Anki

Q: Why is IDOR not just authentication failure?
A: The user is authenticated but not authorized for that object.

</details>

<a id="sec-authz-006"></a>

<details>
<summary><strong>SEC-AUTHZ-006. How do you enforce object ownership and tenant boundaries before returning data?</strong></summary>

#### Short answer

Constrain queries and service checks by user, tenant and policy before mapping or returning results.

#### Interview answer

For a single object, load it through a query that includes tenant or ownership where possible, or load minimal metadata and run a policy check before returning data. For lists and searches, include tenant and permission constraints in the query instead of loading everything and filtering later.

The authorization decision should happen before sensitive data leaves the data access boundary.

#### Deep dive

For complex permissions, a dedicated policy service or specification can keep checks consistent without scattering ad hoc `if` statements.

#### Production angle

Query-level constraints prevent cross-tenant leaks, reduce data exposure in memory and make pagination/counts correct for the caller.

#### Traps / caveats

- Filtering after pagination can return wrong pages.
- Do not trust tenant ID only from the request path.
- Cache keys must include tenant and authorization context.

#### Optional Anki

Q: Why authorize before querying broadly?
A: To prevent leaks and keep result sets correct.

</details>

<a id="sec-authz-007"></a>

<details>
<summary><strong>SEC-AUTHZ-007. What is broken function-level authorization?</strong></summary>

#### Short answer

It is when a user can call a function or endpoint they should not be allowed to use.

#### Interview answer

Broken function-level authorization happens when access to an operation is not enforced correctly. For example, a normal user discovers `/admin/recalculate-prices` or sends a hidden UI action and the backend executes it. Unlike BOLA, the issue is about permission to invoke a function, not only access to a specific object.

Backends must check permissions for each sensitive action.

#### Deep dive

Function-level authorization is common in admin APIs, support tools, state transitions and bulk operations.

#### Production angle

One missing function check can allow data deletion, privilege changes, financial actions or operational disruption.

#### Traps / caveats

- Hiding admin buttons is not enough.
- HTTP method and URL naming do not enforce security.
- Internal functions should still have explicit access rules.

#### Optional Anki

Q: Broken function-level authorization means what?
A: A caller can execute an operation they should not.

</details>

<a id="sec-authz-008"></a>

<details>
<summary><strong>SEC-AUTHZ-008. How should multi-tenant access control be implemented and tested?</strong></summary>

#### Short answer

Resolve tenant context securely, enforce it in every data path and test cross-tenant denial.

#### Interview answer

Tenant identity should come from trusted context such as token claims, authenticated membership or validated routing, not blindly from a request parameter. Queries should include tenant constraints, write operations should validate tenant ownership, and background jobs should operate within an explicit tenant scope.

Tests must prove that tenant A cannot read, update, delete or infer tenant B's data.

#### Deep dive

Some systems use separate databases or schemas per tenant; others use tenant columns. Both need clear isolation and operational controls.

#### Production angle

Cross-tenant leaks are high-severity incidents because they expose customer data and damage trust quickly.

#### Traps / caveats

- Do not trust `tenantId` from the client without verification.
- Include tenant in cache keys.
- Test list, search, export and count endpoints, not only single-object reads.

#### Optional Anki

Q: Key multi-tenant test?
A: One tenant cannot access another tenant's data.

</details>

<a id="sec-authz-009"></a>

<details>
<summary><strong>SEC-AUTHZ-009. What is the difference between `401 Unauthorized` and `403 Forbidden`?</strong></summary>

#### Short answer

`401` means authentication is missing or invalid; `403` means the caller is known but not allowed.

#### Interview answer

Despite the name, `401 Unauthorized` usually means the client needs valid authentication, such as a token or session. `403 Forbidden` means the request was understood and the caller may be authenticated, but the action is not permitted.

For sensitive resources, APIs sometimes return `404` instead of `403` to avoid revealing that a resource exists.

#### Deep dive

In Spring Security, `403` can also come from CSRF failure, not only missing roles.

#### Production angle

Correct status codes help clients know whether to re-authenticate, request different permissions or stop retrying.

#### Traps / caveats

- Do not use `403` for expired or missing tokens.
- Avoid leaking resource existence in error details.
- Keep gateway and service behavior consistent.

#### Optional Anki

Q: `401` vs `403`?
A: Not authenticated vs authenticated/known but forbidden.

</details>

<details>
<summary><strong>SEC-AUTHZ-010. Why is deny-by-default important for new endpoints?</strong></summary>

#### Short answer

It prevents new routes from becoming public just because nobody added a security rule yet.

#### Interview answer

In a deny-by-default design, every endpoint requires an explicit decision: public, authenticated, role-protected, scope-protected or business-policy protected. This is safer than broad allow rules because new controllers and paths do not accidentally inherit public access.

Public endpoints such as health checks and login should be explicitly listed.

#### Deep dive

Deny-by-default should also apply to methods, admin operations, message handlers and feature-flagged code paths.

#### Production angle

Many security incidents come from adding a new endpoint under a path pattern that was accidentally permitted.

#### Traps / caveats

- Broad `permitAll()` rules are dangerous.
- Tests should enumerate public endpoints.
- Documentation should make public access intentional.

#### Optional Anki

Q: What should happen to an endpoint without a rule?
A: It should be denied by default.

</details>

<a id="sec-authz-011"></a>

<details>
<summary><strong>🧠 SEC-AUTHZ-011. What can go wrong with `@PreAuthorize` and self-invocation or proxy-based method security?</strong></summary>

#### Short answer

If a secured method is called without going through the Spring proxy, the security advice may not run.

#### Interview answer

Spring method security is often implemented with proxies. A call from another bean usually goes through the proxy, so `@PreAuthorize` can run. But a method calling another method on the same object, private methods, final methods or manually constructed objects may bypass proxy advice depending on configuration.

The result is a method that looks protected but is not protected on some call paths.

#### Deep dive

This is similar to common `@Transactional` self-invocation issues. Design service boundaries so protected methods are invoked through Spring-managed beans.

#### Production angle

Proxy bypass bugs are dangerous because code review sees the annotation and assumes the check always executes.

#### Traps / caveats

- Test through the Spring context, not only direct Java calls.
- Do not put critical checks only on private helper methods.
- Consider explicit policy calls for complex authorization.

#### Optional Anki

Q: Why can self-invocation bypass `@PreAuthorize`?
A: The call may not pass through the Spring proxy.

</details>

<a id="sec-authz-012"></a>

<details>
<summary><strong>🧠 SEC-AUTHZ-012. How do you avoid leaking data by authorizing after broad queries instead of constraining queries?</strong></summary>

#### Short answer

Push authorization constraints into the query or data access boundary whenever the result set can contain unauthorized data.

#### Interview answer

Loading all rows and filtering unauthorized ones in Java is risky. Data may appear in logs, metrics, caches, memory dumps, pagination counts or timing behavior before filtering. It is also inefficient. A better approach is to include tenant, owner, visibility or permission predicates in the query, then apply service-level policy checks for edge cases.

Authorization should shape what is fetched, not only what is returned.

#### Deep dive

This matters for search, exports, pagination and analytics endpoints because filtering after the fact can produce incorrect totals and pages.

#### Production angle

Broad queries increase both security risk and database load, especially under abuse or scraping.

#### Traps / caveats

- Do not page before authorization filtering.
- Cache only authorization-scoped results.
- Search indexes need tenant and permission constraints too.

#### Optional Anki

Q: Why avoid filtering unauthorized data after broad queries?
A: It can leak data and produce wrong or expensive results.

</details>
