# Security testing, dependencies and secure delivery

---

<a id="sec-test-001"></a>

<details>
<summary><strong>SEC-TEST-001. How should Spring Security rules be tested with MockMvc or WebTestClient?</strong></summary>

#### Short answer

Test unauthenticated, unauthorized and authorized cases through the web layer.

#### Interview answer

Security tests should prove what happens with no credentials, invalid credentials, valid credentials without permission and valid credentials with permission. With MockMvc or WebTestClient, use Spring Security test support to attach mock users, CSRF tokens or JWTs, then assert status codes and response behavior.

For critical APIs, include at least some integration tests that use realistic token and authority mapping.

#### Deep dive

Slice tests are useful for controller/security behavior, but full-context tests may be needed for real filter chains and custom configuration.

#### Production angle

Route security regressions can expose endpoints silently unless denied cases are tested.

#### Traps / caveats

- Do not test only the happy path.
- Mock users may not match production JWT claims.
- CORS and CSRF failures can look like auth failures.

#### Optional Anki

Q: Security API tests should cover which cases?
A: Unauthenticated, unauthorized and authorized.

</details>

<a id="sec-test-002"></a>

<details>
<summary><strong>SEC-TEST-002. How do you test method-level authorization?</strong></summary>

#### Short answer

Call secured methods through Spring-managed beans and assert both allowed and denied behavior.

#### Interview answer

Method security should be tested through the Spring context so proxy-based advice actually runs. Tests should set up a security context or use Spring Security test annotations, then call the service method and assert success for allowed users and denial for users without required roles, scopes or ownership.

For object-level checks, include realistic domain data.

#### Deep dive

Directly instantiating the service with `new` can bypass Spring method security and give false confidence.

#### Production angle

Method security often protects reused business operations, so missing tests can expose paths outside the original controller.

#### Traps / caveats

- Test self-invocation-sensitive code paths.
- Include denied cases, not only allowed cases.
- Verify exception handling does not leak details.

#### Optional Anki

Q: Why test method security through Spring?
A: Proxy-based security must be applied.

</details>

<a id="sec-test-003"></a>

<details>
<summary><strong>SEC-TEST-003. How do you test CSRF behavior?</strong></summary>

#### Short answer

Test state-changing requests with and without a valid CSRF token under the real authentication model.

#### Interview answer

For cookie/session-based flows, tests should verify that unsafe methods such as POST, PUT, PATCH and DELETE are rejected without a CSRF token and accepted with a valid token when the user is authorized. For stateless bearer-token APIs where CSRF is disabled intentionally, tests should document that behavior.

The point is to prove the configured model, not blindly require CSRF everywhere.

#### Deep dive

Spring Security test support can add CSRF tokens in MockMvc tests. Browser-level tests may be useful for complex SPA flows.

#### Production angle

CSRF misconfiguration either breaks clients with unexpected `403` responses or allows unwanted authenticated actions.

#### Traps / caveats

- CORS tests do not prove CSRF behavior.
- CSRF failures can be mistaken for missing role failures.
- Login and logout flows may need separate tests.

#### Optional Anki

Q: Which requests need CSRF testing most?
A: Authenticated state-changing browser requests.

</details>

<a id="sec-test-004"></a>

<details>
<summary><strong>SEC-TEST-004. How do you test that one user cannot access another user's resources?</strong></summary>

#### Short answer

Create data for multiple users or tenants and assert cross-user access is denied for read, write, list and search paths.

#### Interview answer

The test should not only check that Alice can read Alice's order. It should also check that Alice cannot read, update, delete, export or discover Bob's order by changing IDs, filters or pagination parameters. For multi-tenant systems, create at least two tenants and assert isolation across single-object and collection endpoints.

This is one of the highest-value security test categories.

#### Deep dive

Use real database constraints or query behavior where possible, because ownership bugs often live in repository predicates.

#### Production angle

Cross-user and cross-tenant leaks are high-severity incidents and are easy to miss with only happy-path tests.

#### Traps / caveats

- Test lists and search, not only `GET /id`.
- Random IDs do not replace authorization tests.
- Verify counts and pagination metadata too.

#### Optional Anki

Q: Core BOLA test?
A: User A cannot access User B's resource by changing identifiers.

</details>

<a id="sec-test-005"></a>

<details>
<summary><strong>SEC-TEST-005. How do you test JWT validation and authority mapping?</strong></summary>

#### Short answer

Test valid tokens, invalid tokens and claim-to-authority conversion with realistic issuer claims.

#### Interview answer

JWT tests should cover missing token, expired token, wrong issuer, wrong audience, bad signature and a valid token. They should also verify that scopes or roles from the identity provider are converted into the authorities your application expects.

For critical systems, include integration tests using real or realistic JWKs and claim shapes, not only mock annotations.

#### Deep dive

Authority mapping is a common source of bugs because providers differ in claim names and prefix conventions.

#### Production angle

Bad JWT tests can let an API accept tokens from the wrong environment or reject legitimate users after identity-provider changes.

#### Traps / caveats

- Mock users can hide real claim mapping problems.
- Validate audience and issuer, not only signature.
- Test denied access for missing scopes.

#### Optional Anki

Q: Common JWT test gap?
A: Realistic claim-to-authority mapping.

</details>

<a id="sec-test-006"></a>

<details>
<summary><strong>SEC-TEST-006. What is dependency vulnerability scanning, and why does transitive dependency risk matter?</strong></summary>

#### Short answer

It checks dependencies for known vulnerabilities, including libraries pulled in indirectly.

#### Interview answer

Java services rely on direct and transitive dependencies from Maven or Gradle. A vulnerability may exist in a library you never declared directly but received through another starter or framework. Scanners compare dependency versions against vulnerability databases and help teams decide whether to upgrade, exclude, patch or accept risk temporarily.

Scanning is useful, but findings need triage.

#### Deep dive

Not every CVE is exploitable in your application. Exposure depends on code path, configuration, reachable endpoints and runtime environment.

#### Production angle

Dependency vulnerabilities are common because backend services include web servers, parsers, serializers, database drivers and security libraries.

#### Traps / caveats

- Do not ignore transitive dependencies.
- Do not blindly suppress findings without an owner and reason.
- Upgrades need tests because security fixes can change behavior.

#### Optional Anki

Q: What is a transitive dependency?
A: A dependency brought in indirectly by another dependency.

</details>

<a id="sec-test-007"></a>

<details>
<summary><strong>SEC-TEST-007. How should security tests fit into pull requests and CI/CD?</strong></summary>

#### Short answer

Run fast security regression tests on every PR and heavier scans or dynamic checks in staged pipelines.

#### Interview answer

Every PR should run focused tests for authorization, validation, security configuration and critical denied cases affected by the change. CI should also run dependency scanning, secret scanning and static checks where useful. Heavier DAST, container scans or penetration-style checks can run on schedules or pre-release environments.

Security checks should block high-confidence critical issues and produce actionable feedback.

#### Deep dive

Security tests should be close to the feature they protect. A central checklist is useful, but regressions need executable tests.

#### Production angle

CI/CD is where teams catch accidental public endpoints, leaked secrets and vulnerable dependency upgrades before deployment.

#### Traps / caveats

- Too many noisy scanner failures cause alert fatigue.
- Do not rely only on periodic scans.
- Protect CI secrets and logs too.

#### Optional Anki

Q: Which security tests belong on every PR?
A: Fast, focused tests for changed authorization and validation behavior.

</details>

<a id="sec-test-008"></a>

<details>
<summary><strong>🧠 SEC-TEST-008. What should be included in a security-focused code review checklist?</strong></summary>

#### Short answer

Check trust boundaries, authentication, authorization, input handling, data exposure, secrets, logging, resource limits and tests.

#### Interview answer

For backend code, I review who controls each input, whether authentication is required, whether object and function authorization are enforced, whether tenant constraints are in queries, whether DTOs expose or accept safe fields, whether inputs are validated, whether secrets or PII can reach logs, and whether expensive operations have limits.

I also check that denied cases are tested.

#### Deep dive

The checklist should be adapted to the change type: API endpoint, background job, file handling, external call, admin function or data migration.

#### Production angle

A good review checklist catches business-logic security bugs that automated scanners often miss.

#### Traps / caveats

- Do not only search for obvious injection patterns.
- Review new config and route patterns.
- Ask "what can an authenticated but malicious user do?"

#### Optional Anki

Q: Most important security review question?
A: Can this caller perform this action on this resource?

</details>

<details>
<summary><strong>🧠 SEC-TEST-009. What is DAST, and when does it complement unit and integration tests?</strong></summary>

#### Short answer

DAST tests a running application from the outside and can find runtime/configuration issues missed by code-level tests.

#### Interview answer

Dynamic Application Security Testing sends requests to a deployed application and looks for vulnerabilities such as missing headers, reflected input, weak TLS, exposed endpoints, injection behavior or auth mistakes. It complements unit and integration tests because it observes the running system through real HTTP behavior.

It does not understand all business authorization rules, so it cannot replace targeted tests.

#### Deep dive

DAST works best in a controlled environment with test accounts, seeded data and safe scanning limits.

#### Production angle

It catches deployment and configuration problems that are invisible in isolated unit tests.

#### Traps / caveats

- Do not scan production aggressively without approval.
- DAST can be noisy and miss domain-specific flaws.
- Authenticated scanning needs carefully scoped test users.

#### Optional Anki

Q: What does DAST test?
A: A running application from the outside.

</details>
