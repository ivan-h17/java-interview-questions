# Security fundamentals and threat modeling

---

<a id="sec-fund-001"></a>

<details>
<summary><strong>SEC-FUND-001. What is the difference between authentication and authorization?</strong></summary>

#### Short answer

Authentication proves who the caller is. Authorization decides what that caller may do.

#### Interview answer

Authentication answers "who are you?" using credentials such as passwords, sessions, tokens, certificates or identity-provider login. Authorization answers "are you allowed to perform this action on this resource?" using roles, scopes, permissions, ownership, tenant membership and business rules.

A user can be correctly authenticated and still forbidden from a specific operation.

#### Deep dive

In Spring Security, authentication usually produces an `Authentication` object with a principal and authorities. Authorization then evaluates those authorities plus request, method or domain context.

#### Production angle

Many serious backend security bugs are authorization bugs: the system knows the user, but fails to check whether that user owns the resource or may perform the action.

#### Traps / caveats

- Login success is not permission.
- Frontend-hidden buttons are not authorization.
- Gateway authentication does not remove the need for service-side authorization.

#### Optional Anki

Q: Authentication vs authorization?
A: Authentication identifies the caller; authorization permits or denies actions.

</details>

<a id="sec-fund-002"></a>

<details>
<summary><strong>SEC-FUND-002. What is the principle of least privilege?</strong></summary>

#### Short answer

Least privilege means giving users, services and processes only the permissions they need, for only as long as they need them.

#### Interview answer

The principle of least privilege limits blast radius. A backend service should not use a database superuser if it only needs reads and a few writes. A user token should not contain admin permissions for ordinary workflows. A CI job should not have production deploy credentials unless it performs production deploys.

The goal is not inconvenience. The goal is making mistakes and compromises less damaging.

#### Deep dive

Least privilege applies to application roles, OAuth scopes, database grants, cloud IAM, Kubernetes service accounts, secret access and operational tooling.

#### Production angle

If a service is compromised, least privilege can be the difference between one table being exposed and the whole production environment being controlled.

#### Traps / caveats

- Shared admin credentials defeat least privilege.
- Permissions tend to grow unless periodically reviewed.
- Too many tiny permissions can become unmanageable without clear ownership.

#### Optional Anki

Q: Why use least privilege?
A: To reduce blast radius when credentials, code or users are compromised.

</details>

<a id="sec-fund-003"></a>

<details>
<summary><strong>SEC-FUND-003. What is defense in depth?</strong></summary>

#### Short answer

Defense in depth means using multiple independent controls so one failure does not expose the whole system.

#### Interview answer

Instead of relying on a single check, a backend system layers controls: network restrictions, TLS, authentication, authorization, input validation, database permissions, rate limits, logging, monitoring and secure defaults. If one layer is misconfigured, another layer may still reduce damage.

For example, an internal admin endpoint should not rely only on being "hidden"; it should also require authentication, authorization, network restrictions and audit logging.

#### Deep dive

Good layers should not all fail for the same reason. A frontend check and a backend check are not equal layers if the backend trusts the frontend blindly.

#### Production angle

Defense in depth is useful because production systems fail through configuration mistakes, dependency bugs, credential leaks and human error.

#### Traps / caveats

- More layers do not help if they are all bypassed by the same trust mistake.
- Defense in depth is not an excuse for weak primary authorization.
- Controls should be observable and testable.

#### Optional Anki

Q: What is defense in depth?
A: Multiple independent security controls that reduce reliance on one layer.

</details>

<a id="sec-fund-004"></a>

<details>
<summary><strong>SEC-FUND-004. What security responsibilities belong in the application versus infrastructure?</strong></summary>

#### Short answer

Infrastructure can enforce coarse boundaries, but application code must enforce business authorization, validation and data-specific security rules.

#### Interview answer

Infrastructure is good for TLS termination, network segmentation, WAF rules, gateway authentication, rate limiting, secret delivery and runtime isolation. The application is responsible for knowing whether user A can approve invoice B, whether tenant X can read document Y, which fields are sensitive and which state transitions are valid.

A gateway can authenticate a token, but it usually cannot understand every domain object permission.

#### Deep dive

The safest design uses both: infrastructure reduces exposure, while the service still validates identity, permissions and inputs at the business boundary.

#### Production angle

Relying only on infrastructure often causes authorization bypasses when a new route, background handler or internal caller skips the assumed path.

#### Traps / caveats

- Network location is not identity.
- Internal endpoints still need authorization when they affect sensitive data.
- Infrastructure policies must be documented so application teams know what they can rely on.

#### Optional Anki

Q: What must usually stay in application code?
A: Business authorization and data-specific security decisions.

</details>

<a id="sec-fund-005"></a>

<details>
<summary><strong>SEC-FUND-005. What is a trust boundary, and why does it matter in backend design?</strong></summary>

#### Short answer

A trust boundary is a place where data or control crosses from one trust level to another.

#### Interview answer

Examples include browser to API, API gateway to service, service to database, service to message broker, and one microservice to another. At each boundary, the receiver must decide what it can trust and what it must verify: identity, authorization, input shape, signatures, tenant, rate limits and data ownership.

Trust boundaries matter because many security bugs happen when code treats external input as internal truth.

#### Deep dive

Headers, IDs, roles, tenant names and callback URLs are especially risky when they cross trust boundaries. A service should know whether a header was added by trusted infrastructure or supplied by the client.

#### Production angle

Clear trust boundaries make code reviews sharper: reviewers can ask "who controls this value?" before accepting it.

#### Traps / caveats

- Do not trust client-supplied user IDs or tenant IDs by default.
- Internal network traffic can still be malicious or malformed.
- Proxies and gateways can obscure the true origin of data.

#### Optional Anki

Q: Key trust-boundary question?
A: Who controls this value, and has it been verified?

</details>

<a id="sec-fund-006"></a>

<details>
<summary><strong>SEC-FUND-006. What is threat modeling at a practical level?</strong></summary>

#### Short answer

Threat modeling is a structured way to ask what can go wrong, who can cause it and which controls reduce the risk.

#### Interview answer

Practically, I start with a feature diagram: actors, data, components and trust boundaries. Then I ask how a caller could spoof identity, access another user's data, tamper with input, abuse resources, leak secrets or bypass expected workflow. For each realistic risk, I choose controls such as authorization checks, validation, rate limits, audit logs, safe defaults or design changes.

The output should be actionable, not a huge document nobody reads.

#### Deep dive

Threat modeling is most useful before implementation, but it also helps during code review and incident review.

#### Production angle

It catches design flaws early, before they become scattered fixes across controllers, repositories, queues and clients.

#### Traps / caveats

- Do not model only network attackers; model authenticated users too.
- Focus on plausible abuse cases, not every theoretical risk.
- Track unresolved risks explicitly.

#### Optional Anki

Q: Practical threat modeling output?
A: Concrete risks and controls for a feature.

</details>

<a id="sec-fund-007"></a>

<details>
<summary><strong>SEC-FUND-007. What is fail-safe or deny-by-default security?</strong></summary>

#### Short answer

Deny by default means access is blocked unless an explicit rule allows it.

#### Interview answer

Fail-safe security chooses the safer behavior when configuration, code or dependencies are incomplete. For authorization, that means new endpoints, unknown roles, failed policy lookups and missing tenant context should usually deny access rather than silently allow it.

This is the opposite of "allow unless blocked", which tends to expose new functionality by accident.

#### Deep dive

Deny-by-default should appear in route security, method security, data queries, feature flags and error handling. It also needs tests so new endpoints do not slip through.

#### Production angle

Accidental public endpoints are common during fast development. A default deny policy reduces this class of release mistake.

#### Traps / caveats

- Failing closed can affect availability, so user-facing behavior and alerts should be planned.
- Health endpoints may need explicit unauthenticated access.
- Broad `permitAll()` rules can undermine deny-by-default.

#### Optional Anki

Q: What should happen when no auth rule matches?
A: Deny unless there is an explicit allow rule.

</details>

<a id="sec-fund-008"></a>

<details>
<summary><strong>SEC-FUND-008. Why should security checks be server-side even if the frontend hides actions?</strong></summary>

#### Short answer

The client is not trusted. Attackers can call the backend directly or modify frontend behavior.

#### Interview answer

Hiding a button improves UX, but it is not a security control. A user can send HTTP requests with curl, browser dev tools, a script or a modified client. The backend must verify authentication, authorization, input validity and ownership for every sensitive operation.

Frontend checks should mirror backend rules for usability, not replace them.

#### Deep dive

This applies to disabled fields, hidden form inputs, route guards, feature flags and client-side role checks. Anything sent by the client can be changed.

#### Production angle

Server-side checks prevent simple privilege escalation, over-posting and IDOR attacks where users manipulate requests manually.

#### Traps / caveats

- Client-side feature flags are not permissions.
- Hidden IDs and prices can be modified.
- Mobile and SPA clients can lag behind backend security changes.

#### Optional Anki

Q: Why are frontend security checks insufficient?
A: Clients can be modified or bypassed.

</details>

<a id="sec-fund-009"></a>

<details>
<summary><strong>🧠 SEC-FUND-009. How do STRIDE-style threat categories help review a backend feature?</strong></summary>

#### Short answer

STRIDE gives reviewers a checklist of common threat types so they do not focus only on one kind of bug.

#### Interview answer

STRIDE stands for spoofing, tampering, repudiation, information disclosure, denial of service and elevation of privilege. For a backend feature, it prompts questions like: can someone fake identity, modify input, deny performing an action, read data they should not, exhaust resources or gain higher permissions?

It is useful because security reviews often over-focus on authentication and miss logging, resource limits or data leakage.

#### Deep dive

STRIDE is a thinking tool, not a scoring system. It works best when applied to data flows and trust boundaries rather than to code files mechanically.

#### Production angle

It helps teams catch cross-cutting issues before release: missing audit logs, weak ownership checks, unbounded queries and unsafe callbacks.

#### Traps / caveats

- Do not turn STRIDE into paperwork without decisions.
- Some threats overlap; that is fine.
- Use it to find actionable controls.

#### Optional Anki

Q: What does STRIDE help with?
A: Systematically checking common threat categories.

</details>

<details>
<summary><strong>🧠 SEC-FUND-010. How do you prioritize security work when not every risk can be fixed immediately?</strong></summary>

#### Short answer

Prioritize by impact, likelihood, exploitability, exposure, compensating controls and business context.

#### Interview answer

I start with what data or capability is at risk: customer data, money movement, admin access, credentials or availability. Then I look at how exposed the weakness is, whether exploitation is easy, whether it affects many tenants, whether monitoring exists and whether temporary controls can reduce risk.

Critical authorization bypasses and secret leaks usually outrank theoretical hardening work. Lower-risk items should still have owners and dates.

#### Deep dive

Risk prioritization should be explicit. Teams can use severity labels, threat models, vulnerability scores and security-owner review, but the final decision should be tied to real system impact.

#### Production angle

Clear prioritization prevents teams from spending all their time on low-impact scanner noise while serious business-logic flaws remain open.

#### Traps / caveats

- Do not ignore medium issues forever.
- Compensating controls must be real and monitored.
- Public exploitability changes priority quickly.

#### Optional Anki

Q: What drives security priority?
A: Impact, likelihood, exposure and available controls.

</details>
