# Browser, web and API boundary security

---

<a id="sec-web-001"></a>

<details>
<summary><strong>SEC-WEB-001. What is CSRF, and when is CSRF protection needed?</strong></summary>

#### Short answer

CSRF tricks a browser into sending an authenticated state-changing request; it matters when credentials are sent automatically, usually cookies.

#### Interview answer

Cross-Site Request Forgery happens when a malicious site causes the user's browser to send a request to your application with the user's ambient credentials. If authentication uses cookies or other automatically attached browser credentials, state-changing endpoints may need CSRF protection.

Bearer-token APIs using explicit `Authorization` headers are less exposed to classic CSRF, but they have different token-theft risks.

#### Deep dive

CSRF is about causing an action, not reading the response. CORS does not by itself stop CSRF.

#### Production angle

Disabling CSRF blindly in a cookie-based Spring app can turn normal browser behavior into unauthorized actions.

#### Traps / caveats

- CSRF mainly affects unsafe methods like POST, PUT, PATCH and DELETE.
- `SameSite` helps but must match login and cross-site flows.
- XSS can bypass many CSRF defenses.

#### Optional Anki

Q: CSRF mainly matters with which auth style?
A: Browser credentials sent automatically, especially cookies.

</details>

<a id="sec-web-002"></a>

<details>
<summary><strong>SEC-WEB-002. When is it reasonable to disable CSRF protection in a backend API?</strong></summary>

#### Short answer

It can be reasonable for stateless APIs that do not use browser-automatically-sent credentials.

#### Interview answer

If an API is consumed by non-browser clients or uses bearer tokens in the `Authorization` header and does not rely on cookies, classic CSRF risk is usually much lower. In that case, disabling Spring CSRF protection may be appropriate.

If the API uses session cookies, browser cookies, basic auth in browsers or mixed browser flows, disabling CSRF needs much more caution.

#### Deep dive

The decision should be based on credential transport, not on whether the API returns JSON or calls itself "REST".

#### Production angle

Wrong CSRF configuration either breaks legitimate clients with unexpected `403` responses or weakens protection for cookie-based flows.

#### Traps / caveats

- JSON APIs can still be CSRF-relevant if they use cookies.
- CORS is not CSRF protection.
- Document why CSRF is disabled and test the auth model.

#### Optional Anki

Q: Main question before disabling CSRF?
A: Are credentials automatically sent by the browser?

</details>

<a id="sec-web-003"></a>

<details>
<summary><strong>SEC-WEB-003. How should CORS be configured in Spring Security, and why is it not an authentication mechanism?</strong></summary>

#### Short answer

Configure trusted origins, methods, headers and credentials explicitly; CORS only controls browser cross-origin access.

#### Interview answer

CORS tells browsers which origins may read responses from an API. In Spring applications, CORS should be configured consistently with Spring MVC and Spring Security so preflight requests and secured endpoints behave correctly. Allowed origins should be explicit when credentials are involved.

CORS is not authentication. Non-browser clients can call the API regardless, so server-side auth and authorization are still required.

#### Deep dive

Wildcard origins with credentials are unsafe and often invalid in browser behavior. Environment-specific origins should be managed carefully.

#### Production angle

Bad CORS config can either break frontend deployments or expose credentialed browser responses to unintended origins.

#### Traps / caveats

- CORS is enforced by browsers, not by curl.
- Do not use CORS as an API permission system.
- Avoid duplicating conflicting CORS config at gateway and app layers.

#### Optional Anki

Q: Is CORS authentication?
A: No, it is browser cross-origin response access control.

</details>

<a id="sec-web-004"></a>

<details>
<summary><strong>SEC-WEB-004. Why should CORS preflight requests pass before normal authentication logic?</strong></summary>

#### Short answer

Preflight `OPTIONS` requests usually do not include application credentials, so blocking them prevents the real browser request.

#### Interview answer

Before sending some cross-origin requests, a browser sends an `OPTIONS` preflight asking whether the origin, method and headers are allowed. If Spring Security treats this like a normal authenticated API call and rejects it, the browser never sends the actual request.

Security configuration should let valid preflights be answered while still protecting the real endpoint.

#### Deep dive

Preflight success does not authorize the actual business action. It only lets the browser proceed with the real request, which must still authenticate and authorize.

#### Production angle

Misconfigured preflight handling often appears as frontend-only failures while backend logs show `401` or `403` on `OPTIONS`.

#### Traps / caveats

- Allowing preflight is not allowing the API action.
- Do not blindly permit all `OPTIONS` without reviewing paths and headers.
- Gateway and app CORS behavior should be consistent.

#### Optional Anki

Q: Does successful preflight authorize the actual API action?
A: No.

</details>

<a id="sec-web-005"></a>

<details>
<summary><strong>SEC-WEB-005. What are XSS risks for backend APIs that return JSON or HTML?</strong></summary>

#### Short answer

Backends can enable XSS by returning unsafe HTML, wrong content types or untrusted data that clients render unsafely.

#### Interview answer

XSS happens when attacker-controlled content executes as script in another user's browser. Backend APIs contribute when they store unsafe content, return HTML without encoding, use incorrect `Content-Type`, include user input in error pages, or serve JSON that a frontend renders with dangerous APIs.

Even if the backend returns JSON, stored data may become XSS when displayed by web clients.

#### Deep dive

Output encoding should match the context: HTML text, attribute, URL, JavaScript and CSS contexts have different rules.

#### Production angle

XSS can steal tokens, perform actions as users, alter displayed data and bypass many browser-side protections.

#### Traps / caveats

- Input validation alone is not output encoding.
- `HttpOnly` cookies reduce token theft but not all XSS impact.
- Error pages can be XSS surfaces.

#### Optional Anki

Q: Backend XSS rule?
A: Treat stored and reflected user content as unsafe until encoded for its output context.

</details>

<a id="sec-web-006"></a>

<details>
<summary><strong>🧠 SEC-WEB-006. How do output encoding and content type headers reduce XSS risk?</strong></summary>

#### Short answer

Encoding prevents untrusted data from becoming executable markup, and content types tell browsers how to interpret responses.

#### Interview answer

Output encoding transforms characters such as `<`, `>`, quotes and ampersands so user data is displayed as text rather than interpreted as HTML or script. Correct `Content-Type` prevents browsers from guessing dangerous formats. `X-Content-Type-Options: nosniff` can reduce MIME sniffing risk.

Encoding must match where the value is placed, not just be applied generically.

#### Deep dive

HTML escaping is not enough for JavaScript string context, URL context or CSS context. Template engines and frontend frameworks help when used correctly.

#### Production angle

One unencoded error message, admin page or email template can expose privileged users to stored XSS.

#### Traps / caveats

- Do not build HTML by string concatenation.
- Sanitization and encoding solve different problems.
- Wrong content type can make a safe-looking response executable.

#### Optional Anki

Q: Why context-specific encoding?
A: Different browser contexts interpret characters differently.

</details>

<a id="sec-web-007"></a>

<details>
<summary><strong>🧠 SEC-WEB-007. What are security headers such as HSTS, CSP, X-Frame-Options and X-Content-Type-Options used for?</strong></summary>

#### Short answer

They harden browser behavior around HTTPS, script execution, framing and MIME sniffing.

#### Interview answer

HSTS tells browsers to use HTTPS for future requests. CSP limits which scripts, styles and resources may load, reducing XSS impact when configured well. `X-Frame-Options` or CSP `frame-ancestors` helps prevent clickjacking. `X-Content-Type-Options: nosniff` reduces content-type confusion.

These headers are defense in depth, not a replacement for secure coding.

#### Deep dive

CSP can break applications if introduced too aggressively. It is often rolled out with reporting first, then enforcement.

#### Production angle

Security headers reduce browser-side exploitability of mistakes in HTML, static assets and embedded pages.

#### Traps / caveats

- Bad CSP with `unsafe-inline` everywhere gives weak protection.
- HSTS must be deployed carefully for real domains.
- Headers may be added by app, gateway or CDN; avoid conflicts.

#### Optional Anki

Q: Which header helps prevent clickjacking?
A: `X-Frame-Options` or CSP `frame-ancestors`.

</details>

<a id="sec-web-008"></a>

<details>
<summary><strong>SEC-WEB-008. How should file upload endpoints be secured?</strong></summary>

#### Short answer

Authenticate, authorize, limit size/type, scan or validate content, store safely and never trust filenames.

#### Interview answer

A secure upload endpoint checks who may upload, what they may upload and where the file will be used. It should enforce size limits, allowed content types, extension rules, virus/malware scanning where appropriate, safe storage names, metadata validation and rate limits. Files should not be stored directly under executable web paths.

Original filenames are untrusted user input.

#### Deep dive

Content type headers can lie. For high-risk files, inspect magic bytes or use specialized parsers in a sandboxed processing pipeline.

#### Production angle

Upload bugs can cause storage exhaustion, malware distribution, path traversal, XSS, parser exploits or unauthorized data association.

#### Traps / caveats

- Do not trust `Content-Type` alone.
- Strip or normalize filenames.
- Enforce authorization again when processing or downloading.

#### Optional Anki

Q: Should uploaded filenames be trusted?
A: No, treat them as untrusted input.

</details>

<a id="sec-web-009"></a>

<details>
<summary><strong>SEC-WEB-009. How should file download endpoints be secured against path traversal and unauthorized access?</strong></summary>

#### Short answer

Authorize the file as a domain object and resolve storage paths safely without trusting user-provided paths.

#### Interview answer

A download endpoint should not accept arbitrary filesystem paths. It should take a file ID or domain identifier, verify the caller has access, resolve the stored object from metadata, normalize and constrain paths if the filesystem is used, and set safe response headers.

The user should never be able to request `../../etc/passwd` or another tenant's file by changing a path.

#### Deep dive

Object storage keys should also be treated as sensitive. Signed URLs need short lifetimes and proper authorization before issuance.

#### Production angle

Download bugs can leak private documents, backups, configuration files or cross-tenant data.

#### Traps / caveats

- Do not concatenate request parameters into filesystem paths.
- Check authorization before streaming.
- Include tenant/user context in metadata lookups.

#### Optional Anki

Q: Safer download input: path or file ID?
A: File ID with server-side metadata lookup and authorization.

</details>

<a id="sec-web-010"></a>

<details>
<summary><strong>🧠 SEC-WEB-010. What are special security considerations for SPAs that use cookies?</strong></summary>

#### Short answer

Cookie-based SPAs need deliberate CSRF, CORS, SameSite and session/logout design.

#### Interview answer

An SPA using cookies gets browser-managed credential storage and can use `HttpOnly` cookies, which reduces token theft through JavaScript. But cookies are sent automatically, so CSRF must be considered. Cross-origin SPAs also need strict CORS with credentials and compatible `SameSite` settings.

Logout, refresh, tab behavior and API error handling should be designed as part of the authentication flow.

#### Deep dive

Some SPA designs use a backend-for-frontend to keep tokens away from browser JavaScript and expose session-based APIs to the frontend.

#### Production angle

Small cookie/CORS/SameSite mistakes can break login in production or weaken cross-site protections.

#### Traps / caveats

- `HttpOnly` helps with token theft but not CSRF.
- `SameSite=None` requires `Secure` and careful CSRF design.
- Local development origins can hide production CORS issues.

#### Optional Anki

Q: Main extra risk for cookie-based SPAs?
A: CSRF and cross-origin credential handling.

</details>

<a id="sec-web-011"></a>

<details>
<summary><strong>🧠 SEC-WEB-011. How do SameSite cookies change CSRF and login-flow behavior?</strong></summary>

#### Short answer

`SameSite` controls when cookies are sent cross-site, reducing CSRF but sometimes affecting redirects and embedded flows.

#### Interview answer

`SameSite=Strict` sends cookies only in same-site contexts, which is strong but can break flows that rely on cross-site navigation. `Lax` is a common balance for top-level navigations while reducing many CSRF risks. `None` allows cross-site cookies and must be paired with `Secure`, but it increases the need for CSRF controls.

Login redirects, OAuth flows and iframes must be tested with the chosen setting.

#### Deep dive

Same-site is based on site rules, not just exact origin. Browser behavior and deployment domains matter.

#### Production angle

Changing SameSite can cause users to appear logged out after redirects or can expose state-changing endpoints to cross-site requests.

#### Traps / caveats

- `SameSite` is not a complete CSRF solution.
- Cross-site SSO flows need explicit testing.
- Different environments may use different domains and schemes.

#### Optional Anki

Q: Which SameSite value allows cross-site cookies?
A: `SameSite=None` with `Secure`.

</details>

<details>
<summary><strong>🧠 SEC-WEB-012. How does clickjacking protection apply to browser-facing Java applications?</strong></summary>

#### Short answer

Clickjacking protection prevents attackers from embedding your pages in frames and tricking users into clicking hidden UI.

#### Interview answer

If a browser-facing admin page or user settings page can be framed by an attacker's site, the attacker may overlay deceptive UI and cause the user to click sensitive actions. Protections include `X-Frame-Options` or CSP `frame-ancestors`, plus avoiding dangerous state-changing GET requests.

APIs that only return JSON are less directly affected, but embedded pages, dashboards and admin consoles matter.

#### Deep dive

Some products intentionally allow embedding. In that case, allowed frame ancestors should be explicit and narrow.

#### Production angle

Clickjacking can turn a valid logged-in session into unauthorized actions without stealing credentials.

#### Traps / caveats

- Do not rely on JavaScript frame-busting.
- Avoid state changes via GET.
- Review admin and internal UIs, not only public pages.

#### Optional Anki

Q: Header/policy used against clickjacking?
A: `X-Frame-Options` or CSP `frame-ancestors`.

</details>
