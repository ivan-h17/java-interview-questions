# Production security scenarios and incident response

---

<a id="sec-prod-001"></a>

<details>
<summary><strong>SEC-PROD-001. A user can access another user's data by changing an ID in the URL. What is wrong?</strong></summary>

#### Short answer

The API has broken object-level authorization, also known as BOLA or IDOR.

#### Interview answer

Authentication is working because the user is logged in, but authorization is incomplete because the service does not verify access to the specific object. The fix is to enforce ownership, tenant membership or policy before returning the resource. Ideally the query itself includes the authorized tenant/user boundary.

I would also add negative tests proving user A cannot access user B's resources.

#### Deep dive

Opaque IDs reduce guessing but do not fix the authorization flaw. Admin/support exceptions need explicit policy, not accidental bypass.

#### Production angle

This is usually a high-severity data leak. Incident response should assess affected records, logs, exploitability and whether bulk enumeration occurred.

#### Traps / caveats

- Do not fix only one endpoint if the pattern exists elsewhere.
- Check list, search, export and update paths too.
- Avoid logging sensitive leaked data during investigation.

#### Optional Anki

Q: Changing an ID reveals another user's data. What bug?
A: Broken object-level authorization / IDOR.

</details>

<a id="sec-prod-002"></a>

<details>
<summary><strong>SEC-PROD-002. A JWT is valid but should no longer grant access. What options exist?</strong></summary>

#### Short answer

Use short lifetimes, revocation state, introspection, token versioning, permission refresh or key rotation depending on the reason.

#### Interview answer

JWTs are self-contained, so a valid unexpired token may continue working after logout, role removal or account compromise. Options include short access-token lifetimes, refresh-token revocation, a token denylist by `jti`, user/session version checks, opaque tokens with introspection, permission checks against current state for sensitive actions, or signing-key rotation for broad compromise.

The right option depends on scale and how fast revocation must take effect.

#### Deep dive

Putting too much mutable authorization data into long-lived JWTs makes revocation and permission changes harder.

#### Production angle

For compromised accounts or leaked tokens, incident response needs a way to invalidate access quickly without taking down all users unnecessarily.

#### Traps / caveats

- Key rotation revokes broadly and can cause outages if mishandled.
- Denylists add state and lookup cost.
- Short lifetime shifts risk to refresh-token security.

#### Optional Anki

Q: Why are JWTs hard to revoke?
A: They can be valid locally until expiration unless extra state is checked.

</details>

<a id="sec-prod-003"></a>

<details>
<summary><strong>SEC-PROD-003. Sensitive data appears in logs after an exception. How do you fix and prevent it?</strong></summary>

#### Short answer

Stop the leak, rotate exposed secrets if needed, redact existing logs where possible and add safer logging controls and tests.

#### Interview answer

First identify what leaked: password, token, PII, request body, SQL parameter or secret. Stop the source by changing exception handling, logging filters, serializers or request logging. If credentials or tokens leaked, rotate or revoke them. Then assess where logs were shipped, who could access them and retention. Add redaction, structured logging rules and tests for sensitive fields.

Do not only remove one log line and declare it fixed.

#### Deep dive

Error responses should also be checked because the same exception may leak data to clients.

#### Production angle

Logs are often copied to centralized systems with broad access, so leaked secrets can remain exposed beyond the application.

#### Traps / caveats

- Stack traces can include sensitive exception messages.
- Request/response body logging is high risk.
- Redaction should happen before data leaves the service.

#### Optional Anki

Q: If a secret appears in logs, what must usually happen?
A: Rotate or revoke the secret and fix the logging source.

</details>

<a id="sec-prod-004"></a>

<details>
<summary><strong>SEC-PROD-004. A new endpoint is accidentally deployed without authentication. How do you prevent this class of issue?</strong></summary>

#### Short answer

Use deny-by-default security, explicit public endpoint lists, route tests and security review in CI.

#### Interview answer

The root problem is usually an allow-by-default rule, broad `permitAll()`, missed path matcher or no test for the new route. I would change configuration so endpoints require authentication unless explicitly marked public. Then add tests that enumerate public endpoints and verify sensitive routes reject unauthenticated requests.

Code review should include security rules whenever routes are added.

#### Deep dive

Actuator, Swagger, admin and internal endpoints should be reviewed separately because they often live outside normal API paths.

#### Production angle

Accidental public endpoints can expose data or operations immediately after deployment, before anyone notices.

#### Traps / caveats

- Do not rely on naming conventions alone.
- Broad path patterns can shadow stricter rules.
- API gateway rules and service rules can drift.

#### Optional Anki

Q: Best default for new endpoints?
A: Deny unless explicitly allowed.

</details>

<a id="sec-prod-005"></a>

<details>
<summary><strong>SEC-PROD-005. Users are being brute-forced through the login endpoint. What controls do you add?</strong></summary>

#### Short answer

Add throttling, detection, MFA or step-up checks, safe lockout behavior and monitoring without leaking account validity.

#### Interview answer

I would add rate limits by account, IP, device or risk signal, progressive delays, credential-stuffing detection, MFA or CAPTCHA for suspicious attempts, alerting on failure spikes and safe generic error messages. Password hashing cost should be appropriate, but login must also be protected from resource exhaustion.

Account lockout should be temporary and designed to avoid easy denial of service.

#### Deep dive

Known breached password checks and impossible-travel/device signals can improve detection in mature systems.

#### Production angle

Brute force can become both an account takeover incident and an availability incident because password verification is CPU-expensive.

#### Traps / caveats

- Do not reveal whether the username exists.
- Per-IP rate limiting alone is weak.
- Monitor successful logins after many failures.

#### Optional Anki

Q: Why rate-limit login?
A: To reduce credential guessing and protect expensive password checks.

</details>

<a id="sec-prod-006"></a>

<details>
<summary><strong>SEC-PROD-006. A signing key or client secret is leaked. What is the incident response?</strong></summary>

#### Short answer

Contain, rotate, revoke, assess misuse, deploy safely, monitor and document the incident.

#### Interview answer

First determine which secret leaked, where, when and who could access it. Contain exposure by removing it from the source and restricting access. Rotate or revoke the secret using a safe overlap process when needed. For signing keys, publish new keys, switch signing, keep or revoke old keys based on compromise severity and token lifetime, and monitor validation failures. For client secrets, create new credentials and disable old ones after clients move.

Then check logs for misuse and complete incident review.

#### Deep dive

If a secret was committed to Git, removing it from the latest commit is not enough; assume history and clones may contain it.

#### Production angle

Poor rotation can turn a security incident into an outage, so emergency rotation procedures should be tested beforehand.

#### Traps / caveats

- Do not delay rotation because cleanup feels complete.
- Identify all consumers before revoking.
- Rotate derived tokens or sessions if needed.

#### Optional Anki

Q: Why is deleting a leaked secret from Git not enough?
A: It may remain in history, clones, logs or caches.

</details>

<a id="sec-prod-007"></a>

<details>
<summary><strong>SEC-PROD-007. An old vulnerable dependency is discovered in production. How do you triage it?</strong></summary>

#### Short answer

Assess reachability, exposure, severity and available fixes, then patch or mitigate based on real risk.

#### Interview answer

I would identify the vulnerable component, version, CVE, affected code paths, whether the service uses the vulnerable feature, whether it is reachable from untrusted input and whether exploits exist. Then I would choose the response: upgrade, override a transitive dependency, disable a feature, add a compensating control or temporarily accept risk with an owner and deadline.

Critical reachable vulnerabilities should be patched quickly.

#### Deep dive

Dependency upgrades need regression tests because security fixes can change parsing, serialization or protocol behavior.

#### Production angle

The goal is fast risk reduction without creating a worse production outage through an untested emergency change.

#### Traps / caveats

- CVSS alone is not application risk.
- Do not ignore transitive dependencies.
- Suppressions need expiration and justification.

#### Optional Anki

Q: Key dependency triage question?
A: Is the vulnerable code reachable and exposed in this application?

</details>

<a id="sec-prod-008"></a>

<details>
<summary><strong>SEC-PROD-008. How should security-relevant events be logged and monitored?</strong></summary>

#### Short answer

Log important security decisions and changes with enough context for investigation, but without secrets or excessive PII.

#### Interview answer

Useful events include login success/failure, MFA changes, password reset, token revocation, role/permission changes, admin actions, denied authorization, suspicious rate-limit hits, secret/config changes and sensitive exports. Logs should include timestamp, actor, tenant, target resource, action, decision and correlation ID where appropriate.

Monitoring should alert on unusual spikes, high-risk actions and policy failures.

#### Deep dive

Audit logs should be tamper-resistant enough for the system's risk level and should have clear retention.

#### Production angle

Good security logs reduce incident investigation time and help detect active abuse.

#### Traps / caveats

- Do not log raw tokens, passwords or full sensitive payloads.
- Avoid high-cardinality metrics with raw user IDs if not designed.
- Denied events can be noisy; alert thresholds matter.

#### Optional Anki

Q: What should security logs include?
A: Actor, action, target, decision, time and correlation context.

</details>

<a id="sec-prod-009"></a>

<details>
<summary><strong>SEC-PROD-009. How do you avoid leaking authorization details in error responses?</strong></summary>

#### Short answer

Return minimal, consistent errors to clients and keep detailed reasons in protected logs.

#### Interview answer

A response should not reveal more than the client needs. For authentication failures, return a generic invalid credentials/token response. For authorization failures, use `403` or sometimes `404` when revealing resource existence is sensitive. Do not say "order exists but belongs to another tenant" unless the product intentionally exposes that.

Detailed denial reasons can go to secure audit logs.

#### Deep dive

Consistency matters. Different messages, status codes or timing can leak whether an object exists.

#### Production angle

Careful errors reduce enumeration risk while still giving support and security teams enough information through internal logs.

#### Traps / caveats

- Do not leak role names or policy internals casually.
- Avoid exposing stack traces.
- Keep client behavior usable for legitimate authorization failures.

#### Optional Anki

Q: Where should detailed authorization denial reasons go?
A: Protected logs, not public error responses.

</details>

<a id="sec-prod-010"></a>

<details>
<summary><strong>🧠 SEC-PROD-010. How do you design graceful degradation without weakening security?</strong></summary>

#### Short answer

Degrade features, not security decisions; fail closed for high-risk authorization and fail predictably with clear alerts.

#### Interview answer

If an optional recommendation service fails, the application can omit recommendations. If an authorization provider, key service or policy store fails, blindly allowing requests is usually unsafe. Options include cached decisions with short TTLs for low-risk reads, read-only mode, reduced functionality, service-account fallback for internal jobs or clear failure responses.

The design should state which dependencies fail open or fail closed and why.

#### Deep dive

Cached authorization decisions must be scoped by user, tenant, resource and permission, and must expire quickly enough for revocation needs.

#### Production angle

During outages, pressure to "just allow traffic" can create a security incident larger than the availability incident.

#### Traps / caveats

- Do not fail open for admin or write operations.
- Cached permissions can become stale.
- Alert when security dependencies degrade.

#### Optional Anki

Q: Security degradation rule of thumb?
A: Degrade functionality, not authorization guarantees.

</details>

<a id="sec-prod-011"></a>

<details>
<summary><strong>🧠 SEC-PROD-011. What should a post-incident review cover after an authorization bug?</strong></summary>

#### Short answer

Cover impact, root cause, detection gaps, missing controls, tests, process changes and owner-backed follow-ups.

#### Interview answer

For an authorization bug, the review should identify what data or actions were exposed, which users or tenants were affected, how long the issue existed, how it was found, why existing tests or reviews missed it and whether similar endpoints share the pattern. Follow-ups should include code fixes, regression tests, monitoring, route/policy review and documentation updates.

The goal is learning and prevention, not blame.

#### Deep dive

Look for systemic causes: controller-only checks, broad queries, missing tenant predicates, copy-pasted security config or unclear ownership of authorization policy.

#### Production angle

Authorization bugs often repeat across endpoints unless the underlying pattern is fixed.

#### Traps / caveats

- Do not stop at "developer forgot a check".
- Verify whether data was actually accessed or only exposed.
- Track remediation to closure.

#### Optional Anki

Q: Key post-incident question for authorization bugs?
A: Where else could the same pattern exist?

</details>
