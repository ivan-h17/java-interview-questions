# Spring Security architecture and configuration

---

<a id="sec-spr-001"></a>

<details>
<summary><strong>SEC-SPR-001. How does the Spring Security filter chain work?</strong></summary>

#### Short answer

Spring Security protects servlet requests through a chain of filters that runs before Spring MVC controllers.

#### Interview answer

In a servlet Spring Boot application, requests pass through `DelegatingFilterProxy`, which delegates to Spring Security's `FilterChainProxy`. `FilterChainProxy` selects the matching `SecurityFilterChain`. Filters then load or create the security context, authenticate credentials, process sessions or bearer tokens, apply CSRF/CORS-related behavior, authorize the request and handle authentication or access-denied failures.

Because this happens before controller invocation, a rejected request may never reach Spring MVC.

#### Deep dive

The exact filters depend on configuration: form login, session auth, resource server, CSRF, remember-me, anonymous auth and custom filters all affect the chain.

#### Production angle

Understanding the chain helps debug unexpected `401`, `403`, missing principals, broken CORS preflights and custom filter ordering issues.

#### Traps / caveats

- MVC interceptors are not a replacement for security filters.
- Filter order matters.
- Enabling debug logs can help, but should be used carefully outside production.

#### Optional Anki

Q: Does Spring Security usually run before controllers?
A: Yes, through servlet filters.

</details>

<a id="sec-spr-002"></a>

<details>
<summary><strong>SEC-SPR-002. What is `SecurityFilterChain`, and how are multiple chains selected, ordered and matched?</strong></summary>

#### Short answer

`SecurityFilterChain` defines security filters for matching requests; the first matching ordered chain is applied.

#### Interview answer

A Spring application can define one or more `SecurityFilterChain` beans. Each chain has request matching rules and a set of security behavior. For each request, Spring Security evaluates chains in order and uses the first matching chain.

This lets an application secure API endpoints, Actuator endpoints, admin routes and static resources differently.

#### Deep dive

Multiple chains are powerful but risky. More specific matchers should normally have higher precedence than broad catch-all chains.

#### Production angle

Wrong chain ordering can accidentally leave endpoints public or apply the wrong authentication mechanism to a sensitive path.

#### Traps / caveats

- A broad matcher first can shadow later chains.
- Chain matching is separate from MVC controller matching.
- Tests should prove protected and public paths explicitly.

#### Optional Anki

Q: Which `SecurityFilterChain` handles a request?
A: The first matching ordered chain.

</details>

<a id="sec-spr-003"></a>

<details>
<summary><strong>SEC-SPR-003. What is the difference between `permitAll()` and ignoring a request from Spring Security?</strong></summary>

#### Short answer

`permitAll()` allows access while still running the security chain; ignoring bypasses Spring Security for that request.

#### Interview answer

With `permitAll()`, the request still passes through Spring Security filters, so security headers, context handling, CSRF-related behavior and logging may still apply. Ignoring a request removes it from Spring Security entirely.

Ignoring can be reasonable for static assets, but it is dangerous for application endpoints because none of the security infrastructure runs.

#### Deep dive

For public API endpoints, `permitAll()` is usually safer than ignoring because it keeps the request inside the same security model.

#### Production angle

Over-broad ignored paths can silently disable security for endpoints added later under the same URL prefix.

#### Traps / caveats

- Do not ignore `/api/**` just to make one endpoint public.
- Ignored paths may miss security headers.
- Public does not mean unmonitored.

#### Optional Anki

Q: Which still runs security filters: `permitAll()` or ignored paths?
A: `permitAll()`.

</details>

<a id="sec-spr-004"></a>

<details>
<summary><strong>🧠 SEC-SPR-004. What is `HttpSecurity`, and what does `http.build()` create?</strong></summary>

#### Short answer

`HttpSecurity` is the fluent builder used to configure web security; `http.build()` creates a `SecurityFilterChain`.

#### Interview answer

In modern Spring Security configuration, a `SecurityFilterChain` bean is often declared by customizing an `HttpSecurity` object. You configure request matching, authorization rules, authentication mechanisms, CSRF, CORS, sessions, headers and resource-server behavior, then call `http.build()` to produce the actual chain.

The result is not "global security" by itself; it is one filter chain with matching behavior.

#### Deep dive

Multiple `SecurityFilterChain` beans can each build from their own `HttpSecurity` configuration, typically with different request matchers and order.

#### Production angle

Knowing that `HttpSecurity` builds chains helps review whether rules are attached to the right chain and path scope.

#### Traps / caveats

- Builder order and matcher scope matter.
- A chain without a clear matcher may become too broad.
- Copy-pasted config can accidentally protect or expose the wrong paths.

#### Optional Anki

Q: What does `http.build()` return?
A: A `SecurityFilterChain`.

</details>

<a id="sec-spr-005"></a>

<details>
<summary><strong>SEC-SPR-005. What is `SecurityContext`, and how is it stored during a request?</strong></summary>

#### Short answer

`SecurityContext` holds the current `Authentication` for the request.

#### Interview answer

Spring Security stores the authenticated principal and authorities in a `SecurityContext`. During a servlet request, filters load, set and clear this context around request processing. Depending on configuration, the context may be associated with a session, request, bearer token or other authentication mechanism.

Application code can read the current principal through Spring Security APIs or controller method arguments.

#### Deep dive

The context is not a business object. It should identify the caller and permissions, while domain authorization still checks actual resources and operations.

#### Production angle

Incorrect context handling can cause missing users, wrong audit logs or authorization decisions based on stale authentication.

#### Traps / caveats

- Do not store large mutable domain objects in the principal.
- Do not trust context across async boundaries automatically.
- Always clear context when manually setting it in custom code.

#### Optional Anki

Q: What does `SecurityContext` contain?
A: The current `Authentication`.

</details>

<a id="sec-spr-006"></a>

<details>
<summary><strong>SEC-SPR-006. What is `SecurityContextHolder`, and why does thread-local storage matter?</strong></summary>

#### Short answer

`SecurityContextHolder` provides access to the current security context, commonly using thread-local storage in servlet applications.

#### Interview answer

In the usual servlet model, Spring Security associates the current `SecurityContext` with the request thread through `SecurityContextHolder`. This makes access convenient inside controllers and services, but it also means the context does not automatically follow work submitted to a different thread.

Thread pools make this especially important because reused threads must not keep another user's context.

#### Deep dive

Spring provides delegation helpers for some async use cases, but propagation should be explicit and reviewed.

#### Production angle

Security context mistakes can produce wrong audit attribution, authorization failures or, in the worst case, cross-request context leakage.

#### Traps / caveats

- `@Async` does not magically preserve the security context.
- Thread-local data must be cleared.
- Background jobs should often use service identity, not an end-user context.

#### Optional Anki

Q: Why does `SecurityContextHolder` matter with thread pools?
A: Context is often thread-local and must not leak between reused threads.

</details>

<a id="sec-spr-007"></a>

<details>
<summary><strong>SEC-SPR-007. What are `AuthenticationManager`, `AuthenticationProvider` and `UserDetailsService` responsible for?</strong></summary>

#### Short answer

They participate in authenticating credentials and loading user identity data.

#### Interview answer

`AuthenticationManager` is the entry point for authentication. It delegates to one or more `AuthenticationProvider`s that know how to verify a particular credential type, such as username/password, LDAP or custom tokens. `UserDetailsService` is commonly used by username/password authentication to load user data by username.

After successful authentication, Spring Security gets an authenticated principal and authorities.

#### Deep dive

For JWT resource servers, authentication often comes from token validation and claim conversion rather than `UserDetailsService`.

#### Production angle

Clear separation helps debug login failures: user not found, bad password, disabled account, wrong provider, or wrong authority mapping.

#### Traps / caveats

- `UserDetailsService` loads users; it does not by itself authorize actions.
- Do not store plaintext passwords.
- Avoid doing expensive remote calls on every request unless cached and controlled.

#### Optional Anki

Q: What does an `AuthenticationProvider` do?
A: Verifies a specific kind of credential and produces authentication.

</details>

<a id="sec-spr-008"></a>

<details>
<summary><strong>🧠 SEC-SPR-008. What is the difference between authentication filters and authorization filters?</strong></summary>

#### Short answer

Authentication filters establish who the caller is; authorization filters decide whether that caller may access the request.

#### Interview answer

Authentication filters process credentials such as form login, basic auth, bearer tokens or session data and populate the `SecurityContext`. Authorization filters use the resulting authentication plus request rules to allow or deny access.

In a typical flow, authorization depends on authentication having already produced a principal, although anonymous access may also be represented.

#### Deep dive

Custom filters should be placed deliberately. A token-parsing filter belongs before authorization, while logging or enrichment filters may have different constraints.

#### Production angle

Wrong filter placement can lead to every request being anonymous, authorization running too early or failures being handled inconsistently.

#### Traps / caveats

- Do not put business authorization into random custom filters.
- Authentication success does not prove object-level access.
- Error handling differs depending on where the exception is thrown.

#### Optional Anki

Q: Authentication filter vs authorization filter?
A: Identify caller vs decide access.

</details>

<a id="sec-spr-009"></a>

<details>
<summary><strong>SEC-SPR-009. How do you secure Actuator, Swagger/OpenAPI, admin and internal endpoints in production?</strong></summary>

#### Short answer

Expose only what is needed, protect sensitive endpoints explicitly and test them separately from normal API routes.

#### Interview answer

Production operational endpoints should be reviewed as first-class attack surfaces. Actuator exposure should be minimal, sensitive endpoints should require authentication and authorization, and management endpoints may use a separate port, path or network policy. Swagger/OpenAPI UI should not expose private APIs publicly unless intended. Admin endpoints need strong roles, audit logs and often stricter network controls.

Internal endpoints should not rely only on "nobody knows the URL".

#### Deep dive

Health and readiness endpoints may be public to infrastructure, while env, config, mappings, logs, heap dumps and shutdown-style operations are sensitive.

#### Production angle

Exposed diagnostics can reveal secrets, routes, dependencies, configuration and operational state useful to attackers.

#### Traps / caveats

- Do not expose all Actuator endpoints by default.
- Swagger UI can leak private contracts.
- Internal network access is not sufficient authorization.

#### Optional Anki

Q: How should sensitive operational endpoints be handled?
A: Minimize exposure, authenticate, authorize and audit them.

</details>

<a id="sec-spr-010"></a>

<details>
<summary><strong>🧠 SEC-SPR-010. How do you safely add a custom Spring Security filter?</strong></summary>

#### Short answer

Add it only when needed, place it deliberately and make its behavior narrow, tested and observable.

#### Interview answer

First I check whether Spring Security already has a built-in mechanism. If a custom filter is still needed, I define exactly what it does: parse a header, authenticate a token, add correlation data or reject a request. Then I place it relative to known filters with `addFilterBefore`, `addFilterAfter` or `addFilterAt`, and test both success and failure paths.

The filter should not mix authentication, domain authorization and business logic.

#### Deep dive

Filters run for many requests, so they must handle missing data, exceptions and idempotency carefully.

#### Production angle

Bad custom filters cause hard-to-debug outages: swallowed exceptions, broken CORS, missing context, duplicate authentication or bypassed authorization.

#### Traps / caveats

- Do not trust custom headers unless added by trusted infrastructure.
- Clear context on failure if you set it manually.
- Keep filter matching narrow.

#### Optional Anki

Q: First question before adding a custom security filter?
A: Is there a built-in Spring Security mechanism for this?

</details>

<a id="sec-spr-011"></a>

<details>
<summary><strong>🧠 SEC-SPR-011. What can go wrong with security context propagation in async code?</strong></summary>

#### Short answer

The context can be missing, stale, leaked to another task or incorrectly treated as valid outside the request.

#### Interview answer

Servlet request handling commonly relies on thread-local security context. When work moves to `@Async`, executors, schedulers, `CompletableFuture` or message listeners, the original request thread changes. Without deliberate propagation, downstream code may see no user. With careless propagation, it may see the wrong user or use end-user identity after the request is over.

Some background work should run under a service identity instead of an end-user identity.

#### Deep dive

Propagation also interacts with MDC, tracing and transaction boundaries. Copying context blindly can make audit data misleading.

#### Production angle

Async context bugs break authorization checks, produce incorrect audit logs and create rare cross-user failures that are difficult to reproduce.

#### Traps / caveats

- Thread pools reuse threads.
- Context propagation is not the same as authorization.
- Long-running tasks should not hold stale user permissions forever.

#### Optional Anki

Q: Main async security-context risk?
A: Missing or wrong user context across thread boundaries.

</details>

<details>
<summary><strong>🧠 SEC-SPR-012. How does reactive Spring Security context differ from servlet thread-local `SecurityContext`?</strong></summary>

#### Short answer

Reactive security context is propagated through the reactive execution context, not ordinary servlet thread-local assumptions.

#### Interview answer

In servlet applications, code often thinks in terms of one request thread and `SecurityContextHolder`. In reactive applications, execution can move across threads as part of a reactive pipeline, so the security context is associated with Reactor context and accessed through reactive APIs.

Blocking or jumping out of the reactive chain can lose context or create misleading assumptions.

#### Deep dive

Reactive method signatures should keep security-dependent work inside the reactive pipeline. Mixing blocking code, thread locals and reactive security needs careful review.

#### Production angle

Incorrect context access in WebFlux can cause missing principals, broken authorization and bugs that appear only under concurrency.

#### Traps / caveats

- Do not assume thread-local context behaves like servlet MVC.
- Avoid blocking calls inside reactive security flows.
- Test reactive endpoints with realistic authentication setup.

#### Optional Anki

Q: Where is reactive security context propagated?
A: Through the reactive context, not ordinary thread-local request assumptions.

</details>
