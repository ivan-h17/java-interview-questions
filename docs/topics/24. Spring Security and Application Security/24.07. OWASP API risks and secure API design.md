# OWASP API risks and secure API design

---

<a id="sec-api-001"></a>

<details>
<summary><strong>SEC-API-001. What are the most important OWASP API Security Top 10 risks for Java backend engineers?</strong></summary>

#### Short answer

The most practical risks are broken authorization, excessive exposure, unsafe input, resource abuse, misconfiguration and weak inventory/governance.

#### Interview answer

For Java backend work, I focus first on broken object-level authorization, broken function-level authorization, broken object property-level authorization, excessive data exposure, unrestricted resource consumption, mass assignment, SSRF, injection, security misconfiguration and unsafe authentication/token handling. In the 2023 OWASP API list, some older categories such as excessive data exposure and mass assignment are grouped under object property-level authorization.

The exact OWASP names matter less than recognizing the failure modes in code reviews and tests.

#### Deep dive

Many API risks are business-logic bugs, not just framework bugs. They require domain-aware tests and review.

#### Production angle

These issues commonly lead to cross-user data leaks, account takeover, expensive abuse, tenant isolation failures and public exposure of internal functionality.

#### Traps / caveats

- Do not treat OWASP as a checklist separate from design.
- Authentication does not solve object-level authorization.
- Rate limits and payload limits are security controls.

#### Optional Anki

Q: Most common severe API risk?
A: Broken authorization, especially object-level authorization.

</details>

<a id="sec-api-002"></a>

<details>
<summary><strong>SEC-API-002. What is broken object property-level authorization?</strong></summary>

#### Short answer

It is when a user can read or change fields of an object that they should not access.

#### Interview answer

Object property-level authorization is about fields, not only whole objects. A user may be allowed to view an order but not internal fraud flags. A support agent may update a customer's email but not their account balance or role. If the API exposes or accepts fields without checking field-level permission, authorization is broken.

This appears in both response DTOs and request DTOs.

#### Deep dive

Field-level rules can depend on role, tenant, ownership, object state or operation type. They should be explicit and tested.

#### Production angle

Property-level bugs leak sensitive fields or allow privilege escalation through fields that were never meant to be client-controlled.

#### Traps / caveats

- Serializer annotations are not authorization by themselves.
- Admin DTOs should not be reused for normal users.
- Partial updates need field-level review.

#### Optional Anki

Q: Property-level authorization protects what?
A: Individual fields within an otherwise accessible object.

</details>

<a id="sec-api-003"></a>

<details>
<summary><strong>SEC-API-003. What is excessive data exposure, and how do DTOs help prevent it?</strong></summary>

#### Short answer

Excessive data exposure is returning more data than the client should see or need; DTOs make the response explicit.

#### Interview answer

If an API returns a JPA entity or broad internal model, it may expose fields like password hash, internal notes, permissions, cost price, tokens or tenant metadata. Response DTOs define the public contract intentionally and make it easier to review which fields are exposed.

DTOs also decouple API shape from persistence shape.

#### Deep dive

DTOs help, but they do not replace authorization. A field can be in a DTO and still require role or ownership checks.

#### Production angle

Data exposure bugs often persist because clients start depending on leaked fields, making removal harder.

#### Traps / caveats

- `@JsonIgnore` is fragile as the only defense.
- Do not expose JPA entities directly.
- Logs and traces can also expose excessive data.

#### Optional Anki

Q: Why use response DTOs?
A: To make exposed API fields explicit and reviewable.

</details>

<a id="sec-api-004"></a>

<details>
<summary><strong>SEC-API-004. How do prepared statements prevent SQL injection?</strong></summary>

#### Short answer

Prepared statements separate SQL structure from parameter values, so user input is treated as data.

#### Interview answer

SQL injection happens when user input becomes part of the SQL command text. Prepared statements use placeholders for values and send parameters separately, so an input like `' OR 1=1 --` is treated as a string value rather than SQL syntax.

In Java, this usually means using `PreparedStatement`, JPA parameters, Spring JDBC parameters or safe query builder bindings.

#### Deep dive

Prepared statements protect values, not every dynamic SQL part. Table names, column names, sort fields and operators still need whitelisting if dynamic.

#### Production angle

SQL injection can lead to data theft, data modification, authentication bypass or expensive database abuse.

#### Traps / caveats

- String concatenation around "mostly parameterized" SQL can still be injectable.
- Dynamic `ORDER BY` fields need allowlists.
- ORM does not automatically make all custom queries safe.

#### Optional Anki

Q: Why do prepared statements stop SQL injection?
A: They bind user input as data, not SQL code.

</details>

<a id="sec-api-005"></a>

<details>
<summary><strong>🧠 SEC-API-005. What other injection risks exist besides SQL injection?</strong></summary>

#### Short answer

Injection can affect any interpreter: shell, LDAP, NoSQL, SpEL, templates, logs, headers, XML or query languages.

#### Interview answer

A backend is vulnerable when untrusted input is inserted into a command language or interpreted context. Examples include shell command injection, LDAP injection, JPQL/HQL injection, NoSQL query injection, template injection, expression-language injection, XML external entity issues, log injection and HTTP response header injection.

The defenses are context-aware escaping, parameterization, allowlists and avoiding interpreters where possible.

#### Deep dive

The dangerous pattern is not SQL specifically. The dangerous pattern is string-building commands from untrusted input.

#### Production angle

Non-SQL injection often appears in "internal tools", search filters, report generation, webhook processing and admin features.

#### Traps / caveats

- Escaping for one context does not protect another.
- Avoid shelling out with user-controlled values.
- Log forging can damage audit integrity.

#### Optional Anki

Q: General injection rule?
A: Never concatenate untrusted input into an interpreted command.

</details>

<a id="sec-api-006"></a>

<details>
<summary><strong>SEC-API-006. What is SSRF, and why are URL-fetching features dangerous?</strong></summary>

#### Short answer

SSRF lets attackers make your server send requests to targets they choose.

#### Interview answer

Server-Side Request Forgery happens when an API fetches a user-provided URL, and attackers use it to reach internal services, cloud metadata endpoints, admin panels or private network addresses. A feature like "import from URL" or "render image from URL" can become a network pivot.

Defenses include allowlists, protocol restrictions, DNS/IP validation, metadata-service blocking, redirects control and strict timeouts.

#### Deep dive

SSRF is hard because DNS can change, redirects can jump to internal addresses and private IP ranges must be handled carefully.

#### Production angle

SSRF can expose cloud credentials, internal APIs and management interfaces that were never meant to be public.

#### Traps / caveats

- Blocking only `localhost` is insufficient.
- Validate after redirects and DNS resolution.
- Do not allow arbitrary protocols.

#### Optional Anki

Q: SSRF turns your server into what?
A: A requester/proxy to attacker-chosen destinations.

</details>

<a id="sec-api-007"></a>

<details>
<summary><strong>SEC-API-007. How do rate limiting and quotas reduce abuse and resource exhaustion?</strong></summary>

#### Short answer

They bound how much work a caller can force the system to do.

#### Interview answer

Rate limiting controls request frequency, while quotas limit total usage over a period or resource dimension. They protect login, search, file upload, report generation, password hashing, expensive queries and third-party integrations from brute force, scraping and denial-of-service abuse.

Good limits are scoped by user, IP, tenant, API key or endpoint depending on the threat.

#### Deep dive

Distributed rate limiting needs shared state or approximate algorithms. It should fail in a way that does not create a security bypass or total outage.

#### Production angle

Without limits, one client can exhaust CPU, memory, database connections, queues or paid downstream APIs.

#### Traps / caveats

- Per-IP limits alone are weak and can hurt shared networks.
- Return clear `429` responses when appropriate.
- Monitor rejected and near-limit traffic.

#### Optional Anki

Q: Why are rate limits security controls?
A: They reduce brute force and resource-exhaustion abuse.

</details>

<a id="sec-api-008"></a>

<details>
<summary><strong>SEC-API-008. What is mass assignment, and how can request DTOs prevent it?</strong></summary>

#### Short answer

Mass assignment lets clients set fields they should not control; narrow request DTOs expose only allowed inputs.

#### Interview answer

If an API binds request JSON directly into an entity or broad model, an attacker may send extra fields like `role`, `balance`, `tenantId` or `approved=true`. Request DTOs define exactly what the client is allowed to send for that operation, and explicit mapping controls what is changed.

Validation is not enough if the field should not be client-controlled at all.

#### Deep dive

Mass assignment often appears later when a new sensitive field is added to a model that is already used for binding.

#### Production angle

This can cause privilege escalation, data corruption and bypass of approval workflows.

#### Traps / caveats

- Do not bind public requests directly to JPA entities.
- Separate create, update and admin DTOs.
- Unknown JSON fields should be considered intentionally.

#### Optional Anki

Q: Main defense against mass assignment?
A: Narrow request DTOs and explicit mapping.

</details>

<a id="sec-api-009"></a>

<details>
<summary><strong>SEC-API-009. How do validation, normalization, sanitization and authorization differ?</strong></summary>

#### Short answer

Validation checks acceptability, normalization canonicalizes, sanitization removes dangerous content, and authorization decides permission.

#### Interview answer

Validation answers "is this input allowed by the contract?" such as size, format and required fields. Normalization converts equivalent forms into a canonical form, such as trimming or normalizing case where appropriate. Sanitization removes or transforms unsafe content, often for rich text or HTML. Authorization decides whether this caller may perform the operation on the resource.

These are different controls and should not be mixed casually.

#### Deep dive

Normalization should happen before checks that depend on equality, uniqueness or policy, but it must not change business meaning silently.

#### Production angle

Confusing validation with authorization creates bugs like accepting a valid `tenantId` that belongs to someone else.

#### Traps / caveats

- A valid request can still be unauthorized.
- Sanitization is context-dependent.
- Normalize consistently before persistence and lookup.

#### Optional Anki

Q: Does validation prove authorization?
A: No.

</details>

<a id="sec-api-010"></a>

<details>
<summary><strong>🧠 SEC-API-010. How do you prevent replay attacks in webhooks or signed API requests?</strong></summary>

#### Short answer

Use signatures over the request, timestamps, nonces or event IDs, short acceptance windows and idempotency tracking.

#### Interview answer

In a replay attack, a valid request is captured and sent again. For webhooks or signed requests, the receiver should verify a signature over the body and relevant headers, reject old timestamps, track unique event IDs or nonces and make processing idempotent.

The signature proves authenticity, while replay controls prove freshness or single use.

#### Deep dive

Use constant-time comparison for signatures and verify against the raw body bytes expected by the signing scheme.

#### Production angle

Replay bugs can duplicate payments, repeat account changes or trigger repeated expensive processing.

#### Traps / caveats

- Signature validation alone may not stop replay.
- Clock skew needs a bounded tolerance.
- Store processed event IDs long enough for the replay window.

#### Optional Anki

Q: Signature plus what prevents replay?
A: Timestamp/nonce/event ID checks and idempotency.

</details>

<a id="sec-api-011"></a>

<details>
<summary><strong>🧠 SEC-API-011. How do GraphQL or flexible query APIs change authorization and resource-limit risks?</strong></summary>

#### Short answer

They move risk from fixed endpoints to field-level authorization, query complexity and data-shape control.

#### Interview answer

GraphQL and flexible query APIs let clients choose fields, filters and nesting. That flexibility can bypass assumptions in fixed REST DTOs. Each field or relation may need authorization, and the server must limit query depth, breadth, cost, pagination and expensive filters.

The API should control what can be selected and how much work one request can trigger.

#### Deep dive

N+1 query problems and authorization checks can interact badly when nested graphs are resolved field by field.

#### Production angle

Flexible APIs can leak hidden fields or let clients create very expensive requests that degrade the whole service.

#### Traps / caveats

- Do not authorize only the top-level object.
- Field selection can bypass DTO assumptions.
- Add query cost and depth limits.

#### Optional Anki

Q: Main GraphQL security shift?
A: Field-level authorization and resource limits become critical.

</details>

<a id="sec-api-012"></a>

<details>
<summary><strong>🧠 SEC-API-012. How can pagination, filtering and search endpoints leak unauthorized data?</strong></summary>

#### Short answer

They can leak through missing tenant filters, counts, suggestions, timing, sorting and unauthorized result snippets.

#### Interview answer

Search and list endpoints often touch many records. If authorization constraints are not part of the query, users may see other tenants' results, counts or metadata. Even when rows are filtered later, total counts, page gaps, facets, autocomplete suggestions or timing can reveal that hidden data exists.

Authorization must be built into the search/index/query model.

#### Deep dive

Search indexes need the same tenant and permission model as the primary database, or a safe denormalized equivalent.

#### Production angle

Leaky search endpoints are attractive because they allow large-scale enumeration and scraping.

#### Traps / caveats

- Do not compute total counts over unauthorized data.
- Sort fields must be whitelisted.
- Pagination after filtering can produce missing or inconsistent pages.

#### Optional Anki

Q: Search endpoint authorization belongs where?
A: In the query/index constraints, not only response filtering.

</details>

<a id="sec-api-013"></a>

<details>
<summary><strong>🧠 SEC-API-013. What insecure deserialization risks matter in Java backend services?</strong></summary>

#### Short answer

Deserializing untrusted data into powerful object graphs can cause code execution, data tampering or denial of service.

#### Interview answer

Java native serialization and unsafe polymorphic deserialization are risky when data comes from untrusted sources. Attackers may exploit gadget chains, force unexpected types, create huge object graphs or bypass validation. Safer designs use explicit DTOs, limited formats, type allowlists and validation after parsing.

The rule is simple: do not deserialize arbitrary trusted-looking objects from clients.

#### Deep dive

JSON libraries can also be risky if polymorphic typing is enabled broadly and accepts attacker-chosen classes.

#### Production angle

Deserialization bugs can be severe because they may execute before business validation or authorization is reached.

#### Traps / caveats

- Do not accept Java serialized objects from external clients.
- Avoid broad default typing for JSON.
- Apply size and depth limits to parsed input.

#### Optional Anki

Q: Main Java deserialization rule?
A: Do not deserialize arbitrary untrusted object graphs.

</details>
