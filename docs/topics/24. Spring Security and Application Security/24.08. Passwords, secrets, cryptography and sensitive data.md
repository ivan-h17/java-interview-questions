# Passwords, secrets, cryptography and sensitive data

---

<a id="sec-data-001"></a>

<details>
<summary><strong>SEC-DATA-001. Why should passwords be stored with `PasswordEncoder` using slow salted hashing algorithms such as BCrypt, Argon2, scrypt or PBKDF2?</strong></summary>

#### Short answer

Passwords should be stored as slow salted hashes so a database leak does not immediately expose user passwords.

#### Interview answer

Spring Security's `PasswordEncoder` verifies passwords without storing plaintext. Algorithms such as BCrypt, Argon2, scrypt and PBKDF2 are intentionally slow and use salts, which makes offline cracking much more expensive after a hash leak. A fast hash like plain SHA-256 is inappropriate for password storage because attackers can try huge numbers of guesses quickly.

Use a current encoder and parameters suitable for production latency.

#### Deep dive

`DelegatingPasswordEncoder` supports algorithm identifiers in stored hashes, which helps migrate hashing algorithms over time.

#### Production angle

Password hashing cost must balance security and availability: too weak helps attackers, too expensive can overload login during abuse.

#### Traps / caveats

- Never store plaintext passwords.
- Do not encrypt passwords reversibly.
- Rate limiting is still needed because hashing is expensive.

#### Optional Anki

Q: Why slow password hashing?
A: To make offline cracking expensive after a leak.

</details>

<a id="sec-data-002"></a>

<details>
<summary><strong>SEC-DATA-002. What is the difference between hashing, encryption and encoding?</strong></summary>

#### Short answer

Hashing is one-way, encryption is reversible with a key, and encoding is reversible formatting without secrecy.

#### Interview answer

Hashing maps input to a fixed-size value and is generally one-way. Password storage uses slow salted hashing. Encryption protects confidentiality and can be reversed only with the correct key. Encoding changes representation, such as Base64 or URL encoding, and provides no security by itself.

Choosing the wrong one is a common security mistake.

#### Deep dive

Signing and MACs are related but different: they provide integrity/authenticity, not confidentiality.

#### Production angle

Calling Base64 "encryption" often leads to secrets being stored or transmitted as if they were protected when they are not.

#### Traps / caveats

- Base64 is not encryption.
- Hashing sensitive data can still be reversible by guessing if the input space is small.
- Encryption key management is part of the security design.

#### Optional Anki

Q: Is encoding secrecy?
A: No, encoding is only representation.

</details>

<a id="sec-data-003"></a>

<details>
<summary><strong>SEC-DATA-003. How should secrets be handled in local, CI and production environments?</strong></summary>

#### Short answer

Keep secrets out of code and images; provide them through environment-specific secret management with least privilege and auditability.

#### Interview answer

Secrets such as passwords, API keys, tokens and private keys should not be committed to Git, baked into container images or printed in logs. Local development can use clearly separated local secrets or mock credentials. CI should use scoped secret variables with masking and restricted access. Production should use a secret manager, Kubernetes secrets with proper controls, cloud IAM or workload identity where possible.

Each environment should have separate credentials.

#### Deep dive

Short-lived credentials and workload identity reduce the need to distribute long-lived secrets to applications.

#### Production angle

Good secret handling limits blast radius and makes rotation possible after a leak or employee/offboarding event.

#### Traps / caveats

- Do not reuse production secrets in tests.
- Avoid passing secrets through command-line arguments.
- Masking in CI is helpful but not a full security boundary.

#### Optional Anki

Q: Where should secrets not live?
A: Git, logs, container images or public config files.

</details>

<a id="sec-data-004"></a>

<details>
<summary><strong>SEC-DATA-004. How do you rotate application secrets without downtime?</strong></summary>

#### Short answer

Use an overlap period where old and new secrets are both accepted, then switch producers and revoke the old secret.

#### Interview answer

Safe rotation usually needs stages: create a new secret, deploy consumers that can use or validate both old and new values, switch producers to the new secret, verify traffic, then remove the old secret. For database passwords, this may involve a second user or password overlap. For signing keys, publish the new public key before signing with it and keep old keys until old tokens expire.

The details depend on the secret type.

#### Deep dive

Automation, ownership and observability are more important than a theoretical rotation policy nobody has tested.

#### Production angle

Bad rotation can create outages, while no rotation makes leaks much more damaging.

#### Traps / caveats

- Do not revoke the old secret before all consumers are updated.
- Test rotation before an emergency.
- Alert on secret expiration.

#### Optional Anki

Q: Core zero-downtime rotation pattern?
A: Overlap old and new secrets, then revoke old after verification.

</details>

<a id="sec-data-005"></a>

<details>
<summary><strong>SEC-DATA-005. What sensitive data should not appear in logs, metrics, traces or error responses?</strong></summary>

#### Short answer

Avoid passwords, tokens, secrets, private keys, session IDs, sensitive PII, payment data and internal security details.

#### Interview answer

Logs and telemetry should not contain raw credentials, bearer tokens, refresh tokens, API keys, authorization headers, cookies, private keys, password reset links, full card numbers, sensitive personal data or detailed authorization internals. Error responses should be useful but not expose stack traces, SQL, secrets or object existence unnecessarily.

Redaction should happen close to logging and tracing boundaries.

#### Deep dive

Structured logging helps, but fields must be classified. Free-form exception messages can still leak sensitive values.

#### Production angle

Observability systems often have broad access and long retention, so leaked secrets in logs become a second data breach.

#### Traps / caveats

- Do not log request/response bodies by default.
- Trace attributes can leak the same data as logs.
- Redact before data leaves the service where possible.

#### Optional Anki

Q: Why are logs security-sensitive?
A: They can store secrets and PII with broad access and retention.

</details>

<a id="sec-data-006"></a>

<details>
<summary><strong>SEC-DATA-006. How should personally identifiable information be protected in backend systems?</strong></summary>

#### Short answer

Collect only necessary PII, restrict access, protect it at rest and in transit, audit use and avoid leaking it through secondary systems.

#### Interview answer

PII protection starts with data minimization: do not collect or store what you do not need. Access should be role- and purpose-limited. Sensitive fields may need encryption, masking, tokenization, retention limits and audit logs. APIs should expose only necessary fields, and logs, metrics, traces, exports and test data must be reviewed for accidental leakage.

Security and privacy are both design concerns.

#### Deep dive

Different data has different sensitivity: email, phone, government ID, health, financial and location data may require different controls.

#### Production angle

PII leaks create customer harm, regulatory risk and incident-response obligations.

#### Traps / caveats

- Masking in the UI does not protect backend storage.
- Analytics pipelines can leak PII.
- Backups and exports need the same data protection thinking.

#### Optional Anki

Q: First PII protection principle?
A: Data minimization.

</details>

<a id="sec-data-007"></a>

<details>
<summary><strong>🧠 SEC-DATA-007. What is TLS responsible for, and what does it not solve?</strong></summary>

#### Short answer

TLS protects data in transit between endpoints; it does not fix application authorization or data handling after receipt.

#### Interview answer

TLS provides encryption in transit, integrity and server authentication. With mutual TLS, it can also authenticate clients or services. It prevents passive network observers from reading traffic and helps detect tampering.

But TLS does not validate business permissions, prevent SQL injection, sanitize input, secure logs, encrypt data at rest or protect against a compromised endpoint.

#### Deep dive

Certificate validation matters. Disabling certificate checks in clients removes much of TLS's value.

#### Production angle

TLS is mandatory for sensitive APIs, but teams still need application-layer security and secret/data handling controls.

#### Traps / caveats

- HTTPS is not authorization.
- Do not disable certificate validation for convenience.
- Terminating TLS at a proxy means internal traffic security must be considered separately.

#### Optional Anki

Q: What does TLS protect?
A: Data in transit, not application correctness.

</details>

<a id="sec-data-008"></a>

<details>
<summary><strong>🧠 SEC-DATA-008. What are common mistakes when developers implement cryptography themselves?</strong></summary>

#### Short answer

Common mistakes include custom algorithms, wrong modes, bad randomness, hardcoded keys and missing authentication.

#### Interview answer

Application developers should usually use vetted libraries and high-level APIs. Mistakes include inventing encryption schemes, using ECB mode, reusing nonces, using weak randomness, storing keys next to ciphertext, ignoring authentication/integrity, comparing signatures unsafely and misunderstanding encoding as encryption.

Good crypto depends on correct algorithms, parameters, key management and protocol design.

#### Deep dive

Even strong primitives can be unsafe when composed incorrectly. Prefer established protocols such as TLS, JOSE libraries for JWT-related work and platform secret managers.

#### Production angle

Custom crypto often fails silently until a breach, and the failure is hard to detect with normal tests.

#### Traps / caveats

- Do not design your own crypto protocol.
- Key management is not optional.
- Encryption without integrity can still be dangerous.

#### Optional Anki

Q: Best default for application crypto?
A: Use vetted libraries and established protocols.

</details>
