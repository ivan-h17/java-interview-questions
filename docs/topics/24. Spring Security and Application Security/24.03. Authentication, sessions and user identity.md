# Authentication, sessions and user identity

---

<a id="sec-auth-001"></a>

<details>
<summary><strong>SEC-AUTH-001. What is the difference between stateful session authentication and stateless token authentication?</strong></summary>

#### Short answer

Stateful sessions keep authentication state on the server; stateless tokens carry enough signed information for the server to validate each request.

#### Interview answer

With server-side sessions, the client usually stores a session cookie, while the server stores session state. The server can invalidate the session centrally, but scaling needs shared session storage or sticky sessions. With stateless bearer tokens such as JWTs, each request includes a token the resource server validates. This scales well, but revocation and logout are harder before token expiry.

The right choice depends on clients, logout requirements, browser risks and operational model.

#### Deep dive

Many systems are hybrid: short-lived access tokens plus server-side refresh token state, or browser sessions backed by distributed storage.

#### Production angle

Authentication style affects CSRF, XSS impact, token theft, revocation, horizontal scaling and incident response.

#### Traps / caveats

- Stateless does not mean no server-side authorization.
- JWTs are not automatically safer than sessions.
- Session cookies need secure attributes.

#### Optional Anki

Q: Main session vs token trade-off?
A: Easy revocation and server state vs scalability and harder revocation.

</details>

<a id="sec-auth-002"></a>

<details>
<summary><strong>SEC-AUTH-002. When is server-side session authentication still a good choice?</strong></summary>

#### Short answer

It is a good choice for browser-based applications that need simple logout, central invalidation and strong server control.

#### Interview answer

Server-side sessions work well for traditional web apps, admin panels and browser clients where cookies are natural and the backend controls login and logout. They make it straightforward to invalidate a session, rotate session IDs and store small server-side authentication metadata.

They are not outdated; they just need proper cookie settings, CSRF protection and scalable session storage if multiple instances are used.

#### Deep dive

For SPAs, sessions can still work if CORS, CSRF and SameSite behavior are designed deliberately.

#### Production angle

Sessions simplify emergency invalidation after account compromise or permission changes, but create operational needs around session storage availability.

#### Traps / caveats

- Do not store large or sensitive domain data in the session.
- Stateless APIs often disable CSRF, but session-based browser apps usually should not.
- Sticky sessions can complicate scaling and failover.

#### Optional Anki

Q: Session auth is especially useful for what?
A: Browser apps needing central logout and invalidation.

</details>

<a id="sec-auth-003"></a>

<details>
<summary><strong>SEC-AUTH-003. What should be stored in an HTTP session, and what should not?</strong></summary>

#### Short answer

Store minimal identity/session metadata; avoid sensitive, large, mutable or business-critical data.

#### Interview answer

A session may store a user identifier, authentication state, CSRF token, small preference data or a reference to server-side state. It should not store raw passwords, full domain aggregates, large carts, sensitive documents, authorization decisions that must always be current, or objects that become stale across deployments.

The session is a convenience boundary, not a database.

#### Deep dive

Distributed sessions must serialize data, so storing complex Java objects can create versioning and memory problems.

#### Production angle

Bloated sessions increase memory use, slow replication and make deployments risky when serialized classes change.

#### Traps / caveats

- Do not store secrets or raw credentials.
- Do not assume session data updates when database permissions change.
- Keep session contents compatible across rolling deploys.

#### Optional Anki

Q: What belongs in a session?
A: Minimal authentication/session metadata, not large domain state.

</details>

<a id="sec-auth-004"></a>

<details>
<summary><strong>SEC-AUTH-004. What are common session fixation risks?</strong></summary>

#### Short answer

Session fixation happens when an attacker makes a victim authenticate using a session ID the attacker already knows.

#### Interview answer

If the application keeps the same session ID after login, an attacker who planted or learned that ID may reuse it after the victim authenticates. The defense is to change the session ID on successful authentication, set secure cookie attributes, avoid accepting session IDs from URLs and expire old sessions appropriately.

Spring Security normally has protections, but custom login flows should be reviewed.

#### Deep dive

Session fixation is different from session hijacking. Fixation controls the session before login; hijacking steals an already-authenticated session.

#### Production angle

Session fixation can turn a successful login into account compromise without stealing the user's password.

#### Traps / caveats

- Do not preserve anonymous session IDs across login without protection.
- Avoid URL-based session IDs.
- Regenerating session IDs must keep only safe state.

#### Optional Anki

Q: Key defense against session fixation?
A: Change the session ID after successful login.

</details>

<a id="sec-auth-005"></a>

<details>
<summary><strong>SEC-AUTH-005. How do `HttpOnly`, `Secure` and `SameSite` cookie attributes improve security?</strong></summary>

#### Short answer

They reduce token theft, plaintext transport and some cross-site request risks for cookies.

#### Interview answer

`HttpOnly` prevents JavaScript from reading the cookie, reducing damage from many XSS attacks. `Secure` tells browsers to send the cookie only over HTTPS. `SameSite` controls when cookies are sent with cross-site requests and can reduce CSRF exposure.

These attributes are important, but they do not replace backend authorization or input validation.

#### Deep dive

`SameSite=Lax`, `Strict` and `None` have different effects on login redirects, embedded flows and cross-site clients. `SameSite=None` requires `Secure` in modern browsers.

#### Production angle

Wrong cookie attributes can either expose sessions or break legitimate browser flows after deployment.

#### Traps / caveats

- `HttpOnly` does not stop CSRF.
- `SameSite` behavior must match OAuth/login redirects.
- Cookies still need server-side validation.

#### Optional Anki

Q: What does `HttpOnly` protect against?
A: JavaScript reading the cookie.

</details>

<a id="sec-auth-006"></a>

<details>
<summary><strong>🧠 SEC-AUTH-006. What is multi-factor authentication, and where does it fit in a backend system?</strong></summary>

#### Short answer

MFA requires more than one kind of proof before granting access, usually after primary authentication and before sensitive actions.

#### Interview answer

MFA combines factors such as something the user knows, has or is. In backend systems, MFA may be required during login, privilege escalation, account recovery, payment setup or admin actions. The backend must track whether the session or token has satisfied the required assurance level.

MFA is a risk reduction control, not a replacement for authorization.

#### Deep dive

Stronger designs use phishing-resistant factors for high-risk users or admin access. Recovery flows must be protected because attackers often target them.

#### Production angle

MFA reduces account takeover impact, especially for admin panels and sensitive customer operations.

#### Traps / caveats

- SMS MFA has weaknesses and operational dependencies.
- Remembered devices need expiration and risk checks.
- Recovery codes are sensitive credentials.

#### Optional Anki

Q: Does MFA replace authorization?
A: No, it strengthens authentication.

</details>

<a id="sec-auth-007"></a>

<details>
<summary><strong>SEC-AUTH-007. How should login failures, lockouts and brute-force protection be handled?</strong></summary>

#### Short answer

Use rate limits, monitoring, safe error messages and carefully designed lockouts that do not create easy denial of service.

#### Interview answer

Login protection should slow attackers without letting them lock out every user cheaply. Controls include per-account and per-IP throttling, progressive delays, CAPTCHA or step-up checks for suspicious traffic, MFA, credential-stuffing detection and alerting. Error responses should not reveal whether the username or password was wrong.

Lockout can help, but it must be balanced against denial-of-service risk.

#### Deep dive

The strongest design combines signals: account, IP, device, ASN, user agent, failed/success ratio and known breached credentials.

#### Production angle

Credential stuffing can create both security incidents and availability incidents because password hashing is intentionally expensive.

#### Traps / caveats

- Do not leak valid usernames through error messages.
- Do not use unlimited expensive password checks.
- Monitor spikes and distributed attacks.

#### Optional Anki

Q: Why can account lockout be risky?
A: Attackers can use it to deny service to real users.

</details>

<a id="sec-auth-008"></a>

<details>
<summary><strong>🧠 SEC-AUTH-008. What is the difference between account lockout and rate limiting?</strong></summary>

#### Short answer

Account lockout blocks a target account; rate limiting slows requests by caller, account, IP or other dimensions.

#### Interview answer

Account lockout focuses on protecting an account after repeated failures, but it can be abused to lock out legitimate users. Rate limiting controls request volume and can be applied per IP, account, device, API key, tenant or endpoint. In practice, systems often combine progressive delays, risk-based challenges and temporary throttling rather than permanent lockouts.

The goal is to increase attacker cost while preserving legitimate access.

#### Deep dive

Rate limits should consider distributed attacks. Per-IP limits alone are weak against botnets and can hurt users behind shared networks.

#### Production angle

Good controls protect both security and availability of the login path.

#### Traps / caveats

- Permanent lockouts create support and DoS problems.
- Per-IP limits can block NATed offices.
- Limits need metrics and alerting.

#### Optional Anki

Q: Lockout vs rate limiting?
A: Lockout blocks accounts; rate limiting controls request volume.

</details>

<a id="sec-auth-009"></a>

<details>
<summary><strong>🧠 SEC-AUTH-009. How do distributed sessions affect security and invalidation?</strong></summary>

#### Short answer

Distributed sessions make horizontal scaling easier, but they add consistency, storage and invalidation concerns.

#### Interview answer

When multiple service instances handle the same user, session state must be shared, replicated or pinned to one instance. Shared stores such as Redis allow any instance to read the session and invalidate it centrally. But they introduce dependency availability, serialization, TTL and race-condition concerns.

Security-sensitive changes such as logout, password reset or role removal must invalidate or refresh sessions reliably.

#### Deep dive

Rolling deployments can break serialized sessions if classes change. Session contents should stay small and version-tolerant.

#### Production angle

If the session store is slow or down, authentication can become an application-wide availability problem.

#### Traps / caveats

- Sticky sessions do not solve failover well.
- Invalidation must work across all instances.
- Session stores need secure access and TTL policies.

#### Optional Anki

Q: Main distributed-session risk?
A: Invalidation and consistency across instances.

</details>

<a id="sec-auth-010"></a>

<details>
<summary><strong>🧠 SEC-AUTH-010. What security risks appear when user identity is trusted from headers added by a gateway?</strong></summary>

#### Short answer

If services trust identity headers blindly, attackers may spoof users unless those headers are only accepted from trusted infrastructure.

#### Interview answer

Gateways often authenticate a request and pass identity, tenant or scopes to downstream services in headers. That can work, but services must reject direct external traffic, strip user-controlled versions of those headers at the edge and verify the call came from trusted infrastructure. Otherwise a client may send `X-User-Id: admin` directly.

Header-based identity is a trust-boundary decision, not a free shortcut.

#### Deep dive

Better designs may use signed tokens, mTLS, service mesh identity or explicit internal authentication between services.

#### Production angle

Misconfigured routing or a new public ingress can turn trusted internal headers into a complete authorization bypass.

#### Traps / caveats

- Do not trust headers just because they have internal-looking names.
- Strip or overwrite identity headers at the edge.
- Downstream services still need authorization checks.

#### Optional Anki

Q: Key rule for gateway identity headers?
A: Accept them only from verified trusted infrastructure.

</details>
