# 03.08. Concurrent collections and synchronization

---

<a id="col-conc-001"></a>

<details>
<summary><strong>COL-CONC-001. What is the difference between synchronized collections and concurrent collections?</strong></summary>

#### Short answer

Synchronized collections wrap ordinary collections with coarse locking; concurrent collections are designed for scalable concurrent access with specialized algorithms.

#### Interview answer

`Collections.synchronizedMap(new HashMap<>())` synchronizes individual method calls on one lock. `ConcurrentHashMap` allows concurrent reads and updates with finer-grained coordination. Concurrent collections also define iterator semantics such as weak consistency instead of fail-fast behavior.

#### Deep dive

Synchronized wrappers can be enough for simple low-contention cases, but compound operations still need external locking. Concurrent collections often provide atomic methods such as `compute`, `merge` and `putIfAbsent`.

#### Production angle

Choose based on access pattern and invariants. A collection can be thread-safe internally while the business operation around it remains unsafe.

#### Traps / caveats

- Synchronized wrappers need manual locking during iteration.
- Concurrent collections do not make multi-step business rules atomic.
- Thread-safe does not mean lock-free.

#### Optional Anki

Q: Main difference?
A: Wrapper-level locking vs collections designed for concurrent access.

</details>

<a id="col-conc-002"></a>

<details>
<summary><strong>🧠 COL-CONC-002. What is the correct way to iterate over a synchronized collection?</strong></summary>

#### Short answer

Synchronize manually on the wrapper for the entire iteration.

#### Interview answer

The wrapper synchronizes individual method calls, but iteration is a sequence of calls. Another thread could modify the collection between iterator calls. The usual pattern is `synchronized (syncCollection) { for (...) { ... } }`.

#### Deep dive

The monitor should be the synchronized wrapper object documented by the wrapper API. Locking the wrong object does not protect iteration. Also, avoid calling slow external code while holding the lock.

#### Production angle

Long iterations under a global lock can block writers and readers. If iteration is frequent, consider snapshots or concurrent collections.

#### Traps / caveats

- Method-level synchronization is not enough for iteration.
- Locking during slow I/O can cause contention.
- Do not synchronize on the backing collection if callers use the wrapper.

#### Optional Anki

Q: How do you safely iterate a synchronized wrapper?
A: Synchronize on the wrapper around the whole iteration.

</details>

<a id="col-conc-003"></a>

<details>
<summary><strong>COL-CONC-003. What is `ConcurrentHashMap`?</strong></summary>

#### Short answer

`ConcurrentHashMap` is a thread-safe hash map designed for concurrent reads and updates.

#### Interview answer

It is the standard map for shared mutable key-value data when many threads may access it. It supports safe concurrent operations and atomic map updates such as `putIfAbsent`, `compute`, `computeIfAbsent` and `merge`.

#### Deep dive

Unlike `Hashtable` or a synchronized map wrapper, it does not synchronize the entire map for every ordinary operation. Its iterators are weakly consistent and do not throw `ConcurrentModificationException`.

#### Production angle

Use it for simple shared indexes, registries and counters, but think carefully about memory growth, key design and multi-step invariants.

#### Traps / caveats

- It does not allow null keys or values.
- It does not make contained values thread-safe.
- It does not protect invariants involving multiple keys or fields.

#### Optional Anki

Q: Standard concurrent map implementation?
A: `ConcurrentHashMap`.

</details>

<a id="col-conc-004"></a>

<details>
<summary><strong>COL-CONC-004. How does `ConcurrentHashMap` provide thread-safety at a high level?</strong></summary>

#### Short answer

It coordinates updates internally while allowing concurrent access, and provides atomic operations for common compound map updates.

#### Interview answer

Reads can usually proceed concurrently with updates. Updates coordinate only the necessary parts of the table rather than locking the entire map for every operation. Methods like `compute` and `merge` let code update a key atomically relative to other map updates.

#### Deep dive

A high-level interview answer does not need to recite internal fields. The key point is that the map's internal structure remains safe under concurrent access and provides well-defined memory visibility for operations.

#### Production angle

Use atomic methods instead of manual get-then-put. Keep mapping functions short and avoid blocking calls inside them.

#### Traps / caveats

- Atomic per-key operations are not whole-application transactions.
- Mapping functions should avoid side effects.
- Values stored inside may still need their own thread-safety.

#### Optional Anki

Q: Why prefer `merge` over get-then-put in a concurrent map?
A: It performs the update atomically for the key.

</details>

<a id="col-conc-005"></a>

<details>
<summary><strong>COL-CONC-005. How is `ConcurrentHashMap` different from `Hashtable` and `Collections.synchronizedMap`?</strong></summary>

#### Short answer

`ConcurrentHashMap` is designed for scalable concurrent access; `Hashtable` and synchronized wrappers use coarser synchronization.

#### Interview answer

`Hashtable` is legacy and synchronizes methods. `Collections.synchronizedMap` wraps a map and synchronizes individual calls. `ConcurrentHashMap` provides better concurrent behavior, weakly consistent iterators and atomic update methods.

#### Deep dive

The practical difference is not just speed. `ConcurrentHashMap` has different null rules and iterator behavior. It avoids fail-fast iteration and forbids nulls to avoid ambiguity under concurrent access.

#### Production angle

Prefer `ConcurrentHashMap` for shared mutable maps unless you specifically need one external lock around a larger invariant.

#### Traps / caveats

- `ConcurrentHashMap` is not drop-in identical to `HashMap`.
- Null key/value behavior differs.
- Synchronized maps still need manual synchronization for iteration.

#### Optional Anki

Q: Which map is legacy: `Hashtable` or `ConcurrentHashMap`?
A: `Hashtable`.

</details>

<a id="col-conc-006"></a>

<details>
<summary><strong>🧠 COL-CONC-006. Why does `ConcurrentHashMap` not allow null keys or null values?</strong></summary>

#### Short answer

To avoid ambiguity between absence and null values under concurrent access.

#### Interview answer

In a `HashMap`, `get(key)` returning null can mean the key is absent or the key maps to null, so callers can use `containsKey` to distinguish. In a concurrent map, another thread can change the map between those calls. Forbidding null makes null return mean absent.

#### Deep dive

This rule simplifies atomic operations and concurrent reasoning. It also catches accidental null values earlier.

#### Production angle

Represent missing values explicitly with `Optional` at API boundaries, sentinel values, or separate state when appropriate. Do not try to store nulls in `ConcurrentHashMap`.

#### Traps / caveats

- `HashMap` allows one null key and null values.
- `ConcurrentHashMap` rejects both.
- `Optional` as a map value has trade-offs and should be used deliberately.

#### Optional Anki

Q: Can `ConcurrentHashMap` store null values?
A: No.

</details>

<a id="col-conc-007"></a>

<details>
<summary><strong>COL-CONC-007. What are atomic compound operations in `ConcurrentHashMap`?</strong></summary>

#### Short answer

They are methods that combine read and write logic atomically for a key, such as `putIfAbsent`, `compute`, `computeIfAbsent` and `merge`.

#### Interview answer

Instead of doing `get`, checking the result and then `put`, use the map's atomic methods. They prevent another thread from interleaving an update for the same key in a way that breaks the operation.

#### Deep dive

These methods make the map update atomic, but not arbitrary side effects inside the mapping function. Keep functions short, deterministic and local to the map update.

#### Production angle

Frequency counters often use `computeIfAbsent(key, k -> new LongAdder()).increment()` or `merge` for simpler cases.

#### Traps / caveats

- Do not perform slow remote calls in mapping functions.
- Per-key atomicity is not a transaction across keys.
- Recursive updates can be problematic.

#### Optional Anki

Q: Atomic insert-if-missing method?
A: `putIfAbsent`.

</details>

<a id="col-conc-008"></a>

<details>
<summary><strong>COL-CONC-008. Why is get-then-put not always thread-safe even with `ConcurrentHashMap`?</strong></summary>

#### Short answer

Because another thread can change the same key between the `get` and the `put`.

#### Interview answer

`ConcurrentHashMap` makes individual operations safe, but a sequence of separate operations is not automatically atomic. Two threads can both read "missing" and then both create or overwrite values.

#### Deep dive

This is a check-then-act race. Use `putIfAbsent`, `computeIfAbsent`, `compute` or `merge` to express the compound operation as one map operation.

#### Production angle

This bug appears in caches, counters, registries and lazy initialization. It can cause duplicate initialization, lost updates or inconsistent values.

#### Traps / caveats

- Thread-safe data structures do not make all usage patterns safe.
- Values may need their own synchronization.
- Atomic map methods should be chosen by desired semantics.

#### Optional Anki

Q: What race is get-then-put?
A: Check-then-act.

</details>

<a id="col-conc-009"></a>

<details>
<summary><strong>🧠 COL-CONC-009. What is `CopyOnWriteArrayList`, and when should you use or avoid it?</strong></summary>

#### Short answer

It is a thread-safe list where writes copy the backing array; use it for small read-mostly lists and avoid it for frequent writes or large lists.

#### Interview answer

Readers and iterators can access stable snapshots without locking. Every mutation creates a new array, so writes are expensive. This makes it good for listener lists and configuration snapshots, not queues or constantly changing collections.

#### Deep dive

Iteration sees old state from iterator creation time. That is safe but stale. It also means iterator removal is unsupported.

#### Production angle

It can simplify code in read-heavy scenarios. In write-heavy paths, it creates allocation pressure and poor latency.

#### Traps / caveats

- Writes copy the array.
- Iterators are snapshot-based.
- It does not make mutable elements thread-safe.

#### Optional Anki

Q: Best use case for `CopyOnWriteArrayList`?
A: Small read-mostly lists such as listener registries.

</details>

<a id="col-conc-010"></a>

<details>
<summary><strong>🧠 COL-CONC-010. What are `ConcurrentSkipListMap` and `ConcurrentLinkedQueue`?</strong></summary>

#### Short answer

`ConcurrentSkipListMap` is a sorted concurrent map; `ConcurrentLinkedQueue` is a non-blocking concurrent FIFO queue.

#### Interview answer

Use `ConcurrentSkipListMap` when you need concurrent access plus sorted key navigation. Use `ConcurrentLinkedQueue` when multiple threads need a non-blocking FIFO queue and you do not need blocking backpressure.

#### Deep dive

`ConcurrentSkipListMap` is useful for concurrent range queries. `ConcurrentLinkedQueue` is unbounded and does not block producers or consumers. If consumers should wait for work or producers should be bounded, use `BlockingQueue`.

#### Production angle

These are specialized tools. Choose them when their semantics match, and add external limits or metrics where needed.

#### Traps / caveats

- Concurrent sorted maps cost more than hash maps.
- `ConcurrentLinkedQueue` is unbounded.
- Non-blocking queue does not provide backpressure by itself.

#### Optional Anki

Q: Concurrent sorted map?
A: `ConcurrentSkipListMap`.

</details>

<a id="col-conc-011"></a>

<details>
<summary><strong>COL-CONC-011. How is `BlockingQueue` used in producer-consumer designs?</strong></summary>

#### Short answer

Producers put work into the queue and consumers take work from it, with blocking behavior coordinating availability and capacity.

#### Interview answer

A bounded `BlockingQueue` can slow producers when consumers lag, and consumers can wait without busy-spinning when no work exists. It is often used inside executors or custom worker loops.

#### Deep dive

A complete design also needs worker lifecycle, shutdown signals, interruption handling, error handling, retries and metrics. Poison pills can work for simple shutdown, but executor shutdown APIs are often cleaner.

#### Production angle

Bounded queues help protect memory, but when full they require a policy: block, reject, drop or retry later.

#### Traps / caveats

- Blocking while holding locks can deadlock.
- Ignoring `InterruptedException` breaks shutdown.
- Queueing does not make work idempotent.

#### Optional Anki

Q: Why use bounded `BlockingQueue`?
A: To coordinate producers and consumers while limiting backlog.

</details>

<a id="col-conc-012"></a>

<details>
<summary><strong>COL-CONC-012. Can a thread-safe collection make the whole class thread-safe?</strong></summary>

#### Short answer

No. It only protects the collection's internal structure, not the owning class's full invariants.

#### Interview answer

A class may have a `ConcurrentHashMap` plus counters, flags or other fields. If an operation must update several things consistently, the collection alone is not enough. You need locking, immutable state replacement or a redesign.

#### Deep dive

Thread-safety is about invariants and visibility across the whole object. A concurrent collection helps with one component. It does not protect relationships such as "map size equals counter" or "user appears in only one of two maps."

#### Production angle

This is a common source of subtle race conditions in caches, registries and stateful Spring singletons.

#### Traps / caveats

- Atomic collection operations are usually per key or per method.
- Mutable values inside the collection may be unsafe.
- Compound business rules need explicit design.

#### Optional Anki

Q: What does a thread-safe collection protect?
A: Its own internal data structure, not every owner invariant.

</details>

<a id="col-conc-013"></a>

<details>
<summary><strong>COL-CONC-013. How would you choose between locking, `ConcurrentHashMap` and immutable snapshots?</strong></summary>

#### Short answer

Use `ConcurrentHashMap` for independent key-based updates, locking for compound invariants, and immutable snapshots for read-mostly state with atomic replacement.

#### Interview answer

If many threads update independent keys, `ConcurrentHashMap` is usually good. If several fields or collections must change together, use a lock or redesign the invariant. If reads dominate and updates can replace the whole state, immutable snapshots through an `AtomicReference` can be simple and safe.

#### Deep dive

The choice depends on contention, consistency needs and update cost. Immutable snapshots can be expensive for very large state. Locks can be simple but may reduce throughput. Concurrent maps scale but only for suitable operations.

#### Production angle

Prefer the simplest design that preserves correctness. Measure contention before introducing complex lock-free patterns.

#### Traps / caveats

- Do not split one invariant across unsynchronized structures.
- Immutable snapshots can create allocation spikes.
- Concurrent maps can still leak memory if never cleaned.

#### Optional Anki

Q: Which approach for read-mostly replaceable state?
A: Immutable snapshots, often through an atomic reference.

</details>

<a id="col-conc-014"></a>

<details>
<summary><strong>COL-CONC-014. How can collection usage cause memory leaks in concurrent services?</strong></summary>

#### Short answer

Shared collections can grow forever when entries are never removed, keys are too broad, tasks backlog, or values keep large object graphs alive.

#### Interview answer

Static maps, global caches, per-user registries and unbounded queues are common leak sources. In concurrent services, growth may be faster under load and harder to reproduce in tests.

#### Deep dive

Leaks are often logical, not JVM bugs. The collection is still reachable, so everything inside is reachable. Keys can also prevent cleanup when they include request objects, security contexts or large DTOs.

#### Production angle

Use bounded caches, eviction, TTLs, queue limits and cleanup on lifecycle events. Monitor sizes, key cardinality and memory retained by values.

#### Traps / caveats

- `ConcurrentHashMap` has no automatic eviction.
- ThreadLocal maps can retain values in pooled threads.
- Queued tasks retain their captured data.

#### Optional Anki

Q: Why does a static map leak?
A: It remains reachable for the life of the classloader and keeps entries alive.

</details>

<a id="col-conc-015"></a>

<details>
<summary><strong>COL-CONC-015. What are common race conditions involving collections?</strong></summary>

#### Short answer

Common races include check-then-act, lost updates, unsafe iteration, mutable shared values and inconsistent updates across multiple collections.

#### Interview answer

Examples: two threads both see a key missing and create duplicate values; two increments overwrite each other; one thread iterates while another mutates; a mutable object stored in a concurrent map is changed unsafely; one map is updated but a related set is not.

#### Deep dive

The fix is not always "use a concurrent collection." Use atomic map methods, immutable values, locks around invariants, or redesign state ownership.

#### Production angle

Race bugs often appear only under load. Add logging around state transitions, metrics for impossible states and tests that exercise concurrent access.

#### Traps / caveats

- `containsKey` then `put` is not atomic.
- Thread-safe collection values may still be mutable.
- Tests may pass for years and still miss races.

#### Optional Anki

Q: Common collection race pattern?
A: Check-then-act, such as `containsKey` followed by `put`.

</details>
