# 03.01. Collections Framework fundamentals and selection

---

<a id="col-fund-001"></a>

<details>
<summary><strong>COL-FUND-001. What is the Java Collections Framework?</strong></summary>

#### Short answer

The Java Collections Framework is the standard set of interfaces, implementations and algorithms for working with groups of objects in Java.

#### Interview answer

It gives Java a common vocabulary for data structures: `List`, `Set`, `Queue`, `Deque`, `Map`, iterators, sorting utilities and many concrete implementations. Code can depend on contracts such as `List` or `Map` while switching implementations such as `ArrayList`, `LinkedHashMap` or `ConcurrentHashMap` when requirements change.

#### Deep dive

The framework is centered on interfaces, implementations and utility algorithms. Interfaces define behavior and guarantees. Implementations provide storage and performance characteristics. Utility methods in `Collections` and factory methods such as `List.of()` provide common operations and convenient construction.

`Map` is part of the framework but is not a subtype of `Collection`, because it stores key-value mappings rather than individual elements.

#### Production angle

Most backend code uses collections in DTO mapping, request validation, caches, deduplication, batching and query result processing. Choosing the wrong collection can create slow lookups, memory pressure, broken ordering or concurrency bugs.

#### Traps / caveats

- The interface name does not define all performance behavior.
- `Collection` and `Collections` are different things.
- Standard collections store object references, not primitive values directly.

#### Optional Anki

Q: What are the main parts of the Java Collections Framework?
A: Interfaces, implementations and algorithms/utilities for working with groups of objects.

</details>

<a id="col-fund-002"></a>

<details>
<summary><strong>COL-FUND-002. What are the main interfaces in the Java Collections Framework?</strong></summary>

#### Short answer

The core interfaces are `Iterable`, `Collection`, `List`, `Set`, `SortedSet`, `NavigableSet`, `Queue`, `Deque`, `Map`, `SortedMap` and `NavigableMap`.

#### Interview answer

`Iterable` means an object can be iterated. `Collection` is the root interface for groups of individual elements. `List` adds positional order and duplicates. `Set` adds uniqueness. `Queue` and `Deque` model processing order. `Map` stores key-value mappings and has its own hierarchy with sorted and navigable variants.

#### Deep dive

The interfaces encode different contracts. A `List` can answer "what is element at index 5?" A `Set` answers "is this unique value present?" A `Queue` answers "what should be processed next?" A `Map` answers "what value belongs to this key?"

Sorted and navigable interfaces add ordering and range lookup operations. Concurrent variants live mostly under `java.util.concurrent`.

#### Production angle

Choosing the most honest interface improves maintainability. If callers only need iteration, returning `Iterable` or `Collection` may be better than leaking `ArrayList`.

#### Traps / caveats

- `Map` is not a subtype of `Collection`.
- `List` order is not the same as sorted order.
- Some interfaces allow optional operations that an implementation may reject.

#### Optional Anki

Q: Which interface represents key-value mappings?
A: `Map`, not `Collection`.

</details>

<a id="col-fund-003"></a>

<details>
<summary><strong>COL-FUND-003. What is the difference between `Collection`, `Collections` and `Collector`?</strong></summary>

#### Short answer

`Collection` is an interface for groups of elements. `Collections` is a utility class. `Collector` is a Stream API abstraction for reducing stream elements into a result.

#### Interview answer

`Collection<E>` is the root interface for many containers such as lists and sets. `Collections` contains static helpers such as `sort`, `unmodifiableList`, `synchronizedMap`, `emptyList` and `binarySearch`. `Collector<T, A, R>` describes how a stream accumulates elements into a result, for example with `Collectors.toList()` or `Collectors.groupingBy()`.

#### Deep dive

The naming is easy to confuse because all three are common in backend code. `Collection` is about data structure contracts. `Collections` is about algorithms and wrappers. `Collector` is about stream reduction and has supplier, accumulator, combiner and finisher functions.

#### Production angle

Confusing these concepts leads to unclear APIs. A method should not accept `Collector` when it needs a collection, and a returned `Collection` does not imply mutability, ordering or thread-safety unless documented.

#### Traps / caveats

- `Collections.unmodifiableList()` returns a wrapper view, not necessarily an immutable copy.
- `Collectors.toList()` historically did not promise a specific list implementation.
- `Collection` does not include `Map`.

#### Optional Anki

Q: `Collection` vs `Collections`?
A: `Collection` is an interface; `Collections` is a utility class.

</details>

<a id="col-fund-004"></a>

<details>
<summary><strong>COL-FUND-004. Why does `Map` not extend `Collection`?</strong></summary>

#### Short answer

Because `Map` stores mappings from keys to values, not a simple group of elements.

#### Interview answer

A `Collection` represents individual elements and has operations such as `add(E)`, `contains(Object)` and iteration over elements. A `Map` represents associations: key to value. Its natural operations are `put(K, V)`, `get(K)`, `containsKey` and views such as `keySet`, `values` and `entrySet`.

#### Deep dive

If `Map` extended `Collection`, it would be unclear what an "element" means: key, value or entry. Java solves this by making map views collections. `map.keySet()` is a `Set<K>`, `map.values()` is a `Collection<V>`, and `map.entrySet()` is a `Set<Map.Entry<K,V>>`.

#### Production angle

This distinction matters in API design. Passing a `Map` communicates lookup by key. Passing a `Collection` communicates traversal or membership, not key-based access.

#### Traps / caveats

- `values()` can contain duplicates even when keys are unique.
- Map views are usually backed by the original map.
- `Map.Entry` is the element type only for the entry view, not for `Map` itself.

#### Optional Anki

Q: Why is `Map` separate from `Collection`?
A: A map stores key-value associations, so "the element" is ambiguous.

</details>

<a id="col-fund-005"></a>

<details>
<summary><strong>COL-FUND-005. How are `Iterable`, `Collection`, `List`, `Set`, `Queue` and `Map` related?</strong></summary>

#### Short answer

`Collection` extends `Iterable`; `List`, `Set` and `Queue` extend `Collection`; `Map` is separate but provides collection views.

#### Interview answer

`Iterable` is the minimal contract for enhanced `for` loops. `Collection` adds size, containment, add/remove and bulk operations. `List`, `Set` and `Queue` specialize `Collection` for positional order, uniqueness and processing order. `Map` is a separate key-value abstraction.

#### Deep dive

This hierarchy lets generic code work at the right level. A method that only loops can accept `Iterable`. A method that needs size and containment can accept `Collection`. A method that needs index access should accept `List`. A method that needs uniqueness should use `Set`.

`Map` participates through views: keys, values and entries.

#### Production angle

Using the narrowest useful type makes APIs easier to change. For example, accepting `Collection<Long>` instead of `List<Long>` lets callers pass a `Set` of IDs without copying.

#### Traps / caveats

- `Iterable` has no `size()` method.
- `Collection` does not guarantee order.
- `Map.values()` is a `Collection`, not a `Set`.

#### Optional Anki

Q: Which core collection interface extends `Iterable`?
A: `Collection`.

</details>

<a id="col-fund-006"></a>

<details>
<summary><strong>🧠 COL-FUND-006. What are optional operations in collection interfaces, and why can they throw `UnsupportedOperationException`?</strong></summary>

#### Short answer

Some interface methods are optional because not every collection supports mutation or every kind of mutation.

#### Interview answer

The collection interfaces include methods such as `add`, `remove` and `clear`, but immutable, fixed-size or special-purpose implementations may not support them. In that case the implementation can throw `UnsupportedOperationException`.

#### Deep dive

This design lets read-only views, fixed-size views and special collections still share common interfaces. For example, `Arrays.asList()` returns a fixed-size list backed by an array, so `set` works but `add` and `remove` do not. `List.of()` returns an unmodifiable list, so structural mutation methods fail.

#### Production angle

This often appears when code assumes a returned `List` is always mutable. A service may work in tests with `ArrayList` and fail in production when another component returns `List.of()` or an unmodifiable view.

#### Traps / caveats

- A variable typed as `List` does not guarantee mutability.
- `UnsupportedOperationException` is runtime, not compile-time.
- Fixed-size, unmodifiable and immutable are different ideas.

#### Optional Anki

Q: Why can `list.add()` throw `UnsupportedOperationException`?
A: The `List` implementation may not support mutation.

</details>

<a id="col-fund-007"></a>

<details>
<summary><strong>COL-FUND-007. What is the difference between a collection interface and a collection implementation?</strong></summary>

#### Short answer

An interface defines the contract; an implementation defines storage, performance, ordering, mutability and concurrency behavior.

#### Interview answer

`List` says elements are ordered by position and can be accessed by index. `ArrayList` implements that contract with a resizable array. `LinkedList` implements it with linked nodes. The same interface can hide very different performance and memory behavior.

#### Deep dive

Interfaces are useful for API boundaries because callers do not need to know the concrete class. Implementations matter inside performance-sensitive code. For example, `list.get(i)` is cheap for `ArrayList` but expensive for `LinkedList`; `Set` membership is usually cheap for `HashSet` but sorted range operations require `TreeSet`.

#### Production angle

Expose interfaces, choose implementations deliberately. A senior answer should discuss required guarantees: ordering, uniqueness, random access, lookup speed, insertion/removal pattern, memory footprint and thread-safety.

#### Traps / caveats

- Programming to an interface does not remove performance differences.
- Returning a concrete mutable implementation can leak too much.
- Changing implementation can change iteration order or null support.

#### Optional Anki

Q: Interface vs implementation?
A: Interface defines behavior; implementation defines how it is stored and what it costs.

</details>

<details>
<summary><strong>🧠 COL-FUND-008. Why are `Vector`, `Stack`, `Hashtable` and `Enumeration` considered legacy?</strong></summary>

#### Short answer

They are older APIs largely superseded by `ArrayList`, `ArrayDeque`, `HashMap`, `ConcurrentHashMap` and `Iterator`.

#### Interview answer

`Vector` and `Hashtable` synchronize most methods, but that coarse synchronization is rarely the right concurrency design. `Stack` extends `Vector`, which is an awkward inheritance model for a stack. `Enumeration` is an older traversal API with fewer capabilities than `Iterator`.

#### Deep dive

Modern Java separates concerns better. If you need a list, use `ArrayList`. If you need stack or deque operations, use `ArrayDeque`. If you need a map, use `HashMap`, `LinkedHashMap`, `TreeMap` or `ConcurrentHashMap` based on semantics. If you need iteration, use `Iterator`, enhanced `for` or streams.

#### Production angle

Legacy classes still appear through old libraries. Do not rewrite blindly, but avoid introducing them in new code unless a specific API requires them.

#### Traps / caveats

- Synchronized methods do not automatically make compound workflows safe.
- `Stack` is not the preferred stack abstraction.
- `Hashtable` does not allow null keys or values, unlike `HashMap`.

#### Optional Anki

Q: What should usually replace `Stack`?
A: `ArrayDeque`.

</details>

<details>
<summary><strong>COL-FUND-009. What is the difference between ordered, sorted and encounter-ordered collections?</strong></summary>

#### Short answer

Ordered means iteration has a defined order. Sorted means order is based on natural ordering or a comparator. Encounter order is the order in which traversal operations observe elements.

#### Interview answer

`ArrayList` is ordered by index. `LinkedHashSet` is usually ordered by insertion order. `TreeSet` is sorted by comparison. A collection with encounter order defines how iteration, `forEach`, `stream` and related operations see elements.

#### Deep dive

These terms matter because "ordered" does not mean "sorted". A list of `[3, 1, 2]` is ordered because its order is defined, but it is not sorted. A `HashSet` has no useful guaranteed order. A `TreeSet` is sorted but may reject elements that compare as equal even when `equals()` says they are different.

#### Production angle

Ordering leaks into API responses, tests, pagination and cache keys. If clients rely on order, document it and choose an implementation that guarantees it.

#### Traps / caveats

- Do not rely on `HashMap` or `HashSet` iteration order.
- Sorted collections use comparison, not necessarily `equals()`.
- Encounter order can affect stream results and parallel stream performance.

#### Optional Anki

Q: Is insertion order the same as sorted order?
A: No. Insertion order follows insertion sequence; sorted order follows comparison.

</details>

<details>
<summary><strong>🧠 COL-FUND-010. What are `SequencedCollection`, `SequencedSet` and `SequencedMap`?</strong></summary>

#### Short answer

They are Java 21 interfaces that model collections and maps with a well-defined encounter order and operations for first, last and reversed views.

#### Interview answer

Before Java 21, many collections had a defined order but there was no common interface for first/last operations across lists, deques, sorted sets and linked maps. Sequenced interfaces add a shared vocabulary: get first, get last, add/remove at ends where supported, and view the collection in reverse order.

#### Deep dive

`SequencedCollection` extends `Collection`. `SequencedSet` extends both `Set` and `SequencedCollection`. `SequencedMap` adds ordered map operations and sequenced views. Ordered collection and map types such as `List`, `Deque`, `LinkedHashSet`, `SortedSet`, `LinkedHashMap` and `SortedMap` can expose these interfaces when their ordering semantics support them.

The operations may still be optional. For example, an unmodifiable sequenced collection can expose first/last reads while rejecting writes.

#### Production angle

These interfaces are useful when a public API needs to express "ordered with meaningful first and last" without tying itself to `List` or `LinkedHashMap`.

#### Traps / caveats

- They require Java 21 or newer.
- Sequenced does not mean sorted.
- Reversed views may be backed by the original collection.

#### Optional Anki

Q: What problem do sequenced collections solve?
A: They provide common first/last/reversed operations for ordered collections and maps.

</details>

<details>
<summary><strong>COL-FUND-011. How do collection implementations define equality and `hashCode`?</strong></summary>

#### Short answer

`List` equality is order-sensitive, `Set` equality is based on same elements regardless of order, and `Map` equality is based on same mappings.

#### Interview answer

Two lists are equal if they contain equal elements in the same order. Two sets are equal if they contain the same elements, independent of iteration order. Two maps are equal if their entry sets are equal. Hash codes follow those contracts so equal collections have equal hash codes.

#### Deep dive

These contracts allow different implementations to compare meaningfully. An `ArrayList` can equal a `LinkedList` with the same elements in the same order. A `HashSet` can equal a `TreeSet` with the same elements. A `HashMap` can equal a `LinkedHashMap` with the same key-value mappings.

#### Production angle

Collection equality is often used in tests, cache keys, DTO comparison and change detection. If elements have broken `equals()` or `hashCode()`, collection equality becomes unreliable.

#### Traps / caveats

- List equality cares about order.
- Set equality does not care about iteration order.
- Mutable elements can make equality change over time.

#### Optional Anki

Q: Can an `ArrayList` equal a `LinkedList`?
A: Yes, if they contain equal elements in the same order.

</details>

<details>
<summary><strong>COL-FUND-012. What does it mean that most collection implementations are not synchronized by default?</strong></summary>

#### Short answer

It means multiple threads must not concurrently mutate or access mutable collections without proper synchronization or a concurrent design.

#### Interview answer

Classes such as `ArrayList`, `HashMap` and `HashSet` are optimized for ordinary single-threaded access or externally controlled access. If multiple threads modify them at the same time, behavior is not safe. You may see stale reads, lost updates, corrupted invariants or runtime exceptions.

#### Deep dive

Thread-safety can be achieved in different ways: confine the collection to one thread, publish immutable copies, use external locks, use synchronized wrappers, or choose concurrent collections. The right choice depends on access patterns and invariants.

Concurrent collections are not magic. They protect the data structure's internal state, but business rules involving multiple operations may still need locking or redesign.

#### Production angle

This is a common Spring service bug when mutable collections are stored in singleton beans, static fields or shared caches without a clear concurrency policy.

#### Traps / caveats

- `volatile List` does not make the list contents thread-safe.
- A thread-safe collection does not make the owner object thread-safe.
- Fail-fast exceptions are bug signals, not synchronization mechanisms.

#### Optional Anki

Q: Is `ArrayList` thread-safe?
A: No. Use confinement, locking, immutable snapshots or a suitable concurrent collection.

</details>

<a id="col-fund-013"></a>

<details>
<summary><strong>COL-FUND-013. How would you choose the right collection for a use case?</strong></summary>

#### Short answer

Choose based on required semantics first, then performance: order, uniqueness, lookup pattern, mutation pattern, size, memory, concurrency and API guarantees.

#### Interview answer

Start with the question the data structure must answer. Need indexed ordered data? `List`. Need uniqueness? `Set`. Need lookup by key? `Map`. Need processing order? `Queue` or `Deque`. Then choose implementation: `ArrayList` for compact random-access lists, `HashSet` or `HashMap` for fast membership or lookup, `LinkedHashSet` or `LinkedHashMap` for insertion order, `TreeSet` or `TreeMap` for sorted/range operations, and concurrent collections for shared mutable access.

#### Deep dive

A senior answer should include trade-offs. `ArrayList` has good locality but costly middle insertions. `HashMap` is fast on average but depends on good keys and sizing. `TreeMap` costs `O(log n)` but supports ordering. `CopyOnWriteArrayList` is great for read-heavy snapshots and terrible for write-heavy workloads.

#### Production angle

Validate assumptions with data size, hot-path profiling and failure mode analysis. For very large data, the right answer may be pagination, streaming, SQL filtering or a cache library, not a different in-memory collection.

#### Traps / caveats

- Do not choose only by Big-O.
- Do not rely on unspecified iteration order.
- Do not use collections to hide missing domain modeling.

#### Optional Anki

Q: What comes first when choosing a collection?
A: Semantics: ordering, uniqueness, lookup and mutation requirements.

</details>
