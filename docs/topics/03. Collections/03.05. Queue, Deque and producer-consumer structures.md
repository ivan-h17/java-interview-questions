# 03.05. Queue, Deque and producer-consumer structures

---

<a id="col-queue-001"></a>

<details>
<summary><strong>COL-QUEUE-001. What is a `Queue`?</strong></summary>

#### Short answer

A `Queue` is a collection designed for holding elements before processing, usually in first-in-first-out order.

#### Interview answer

`Queue<E>` models processing order: producers add elements, consumers remove or inspect the next element. Common operations are `offer`, `poll` and `peek`. Not all queues are FIFO: `PriorityQueue` orders by priority, and concurrent queues have their own behavior.

#### Deep dive

The interface separates exception-throwing methods from special-value methods. For bounded queues, `offer` can report failure without throwing. For empty queues, `poll` and `peek` return null.

#### Production angle

Queues are used in background work, buffering, handoff between threads and local algorithms. In distributed systems, in-memory queues are not durable message brokers.

#### Traps / caveats

- Queue order depends on implementation.
- Null elements are usually forbidden because null is used as an empty result marker.
- A queue can hide overload if it grows without bounds.

#### Optional Anki

Q: What are the preferred non-throwing queue methods?
A: `offer`, `poll` and `peek`.

</details>

<a id="col-queue-002"></a>

<details>
<summary><strong>🧠 COL-QUEUE-002. What is the difference between `add`, `offer`, `remove`, `poll`, `element` and `peek`?</strong></summary>

#### Short answer

`add`, `remove` and `element` throw on failure; `offer`, `poll` and `peek` return special values.

#### Interview answer

`add(e)` inserts or throws if insertion fails. `offer(e)` inserts or returns false if it cannot. `remove()` removes the head or throws if empty. `poll()` removes the head or returns null if empty. `element()` reads the head or throws if empty. `peek()` reads the head or returns null if empty.

#### Deep dive

For bounded queues, `offer` is usually better than `add` because a full queue can be a normal condition. For empty queues, `poll` and `peek` avoid exception-driven control flow.

#### Production angle

Use return-value methods in worker loops and overload handling. Throwing methods are fine when failure indicates a programming error rather than an expected state.

#### Traps / caveats

- Null return from `poll` means empty, so queues usually disallow null elements.
- `offer` false should be handled, not ignored.
- Blocking queues also have `put` and `take`.

#### Optional Anki

Q: Empty queue: `remove()` vs `poll()`?
A: `remove()` throws; `poll()` returns null.

</details>

<a id="col-queue-003"></a>

<details>
<summary><strong>COL-QUEUE-003. What is a `Deque`, and how is it different from `Queue`?</strong></summary>

#### Short answer

A `Deque` is a double-ended queue that supports insertion and removal at both the front and the back.

#### Interview answer

`Queue` mainly models adding at one end and removing from the head. `Deque` generalizes this with `addFirst`, `addLast`, `pollFirst`, `pollLast`, `peekFirst` and `peekLast`. It can support FIFO queue behavior and LIFO stack behavior.

#### Deep dive

`Deque` replaces legacy `Stack` for stack-style operations. `ArrayDeque` is the common implementation for local use. `LinkedList` also implements `Deque`, but usually has worse memory locality.

#### Production angle

Use deques for local algorithms such as BFS, DFS, parsing, sliding windows and undo-like structures. For cross-thread blocking handoff, use `BlockingDeque` implementations.

#### Traps / caveats

- `Deque` is an interface, not necessarily thread-safe.
- Method pairs differ in throwing vs returning special values.
- `ArrayDeque` does not support null elements.

#### Optional Anki

Q: What does `Deque` stand for?
A: Double-ended queue.

</details>

<a id="col-queue-004"></a>

<details>
<summary><strong>COL-QUEUE-004. When would you use `ArrayDeque`?</strong></summary>

#### Short answer

Use `ArrayDeque` for efficient single-threaded queue, deque or stack behavior.

#### Interview answer

`ArrayDeque` is a resizable-array implementation of `Deque`. It is usually a better local FIFO queue than `LinkedList` and a better stack than legacy `Stack`. It supports operations at both ends efficiently.

#### Deep dive

It has no index access and no capacity bound by default. It also rejects null elements. Because it is not synchronized, it should not be shared for concurrent mutation without external coordination.

#### Production angle

Good examples include graph traversal, parsing, in-memory scheduling within one thread and temporary stacks in algorithms.

#### Traps / caveats

- Not thread-safe.
- No null elements.
- Not durable and not suitable as an application-wide work queue.

#### Optional Anki

Q: `ArrayDeque` or `LinkedList` for local FIFO?
A: Usually `ArrayDeque`.

</details>

<a id="col-queue-005"></a>

<details>
<summary><strong>COL-QUEUE-005. What is `PriorityQueue`, and what are its ordering caveats?</strong></summary>

#### Short answer

`PriorityQueue` removes the least or highest-priority element according to natural ordering or a comparator, but it does not keep all elements fully sorted in iteration order.

#### Interview answer

It is useful when you repeatedly need the next best element, such as the smallest timestamp or highest-priority task. `peek()` and `poll()` return the head according to priority. Iterating the queue does not produce sorted order.

#### Deep dive

`PriorityQueue` allows duplicates but not null elements. Elements must be comparable or a comparator must be supplied. If priorities change after insertion, the queue does not automatically reorder the element.

#### Production angle

Use it for in-memory scheduling, top-N algorithms or shortest-path style algorithms. For thread-safe priority handoff, consider `PriorityBlockingQueue`, but understand its unbounded nature.

#### Traps / caveats

- Iteration is not sorted.
- Mutating priority fields breaks ordering.
- It is not thread-safe.

#### Optional Anki

Q: Does `PriorityQueue` iteration return sorted elements?
A: No. Only head operations respect priority.

</details>

<a id="col-queue-006"></a>

<details>
<summary><strong>🧠 COL-QUEUE-006. How does `PriorityQueue` work under the hood?</strong></summary>

#### Short answer

It is typically implemented as a binary heap stored in an array.

#### Interview answer

The heap invariant keeps the highest-priority head at the root. In Java's natural min-heap behavior, the smallest element is at the head. Adding and removing require reheapifying, usually `O(log n)`. Reading the head with `peek()` is `O(1)`.

#### Deep dive

The internal array is not sorted. It only satisfies the heap property: each parent is ordered before its children. That is enough to find the next element efficiently but not enough for sorted traversal.

#### Production angle

A heap is good when you repeatedly poll the next item. If you need sorted iteration of all elements, sort a list or use a sorted set/map depending on duplicate and lookup requirements.

#### Traps / caveats

- Heap order is not full sort order.
- Comparator must be stable while elements are in the queue.
- Removing arbitrary elements can be more expensive than polling.

#### Optional Anki

Q: What is the usual data structure behind `PriorityQueue`?
A: A binary heap in an array.

</details>

<a id="col-queue-007"></a>

<details>
<summary><strong>COL-QUEUE-007. What is `BlockingQueue`, and when is it useful?</strong></summary>

#### Short answer

`BlockingQueue` is a thread-safe queue that can block producers when full and consumers when empty.

#### Interview answer

It is designed for producer-consumer coordination. Producers can `put` work into the queue, blocking if a bounded queue is full. Consumers can `take` work, blocking if the queue is empty. Non-blocking and timed variants also exist.

#### Deep dive

Blocking queues combine a data structure with coordination. They are useful for handoff between threads and for applying limits when bounded. They do not automatically handle task cancellation, retries, persistence or distributed processing.

#### Production angle

Use bounded blocking queues to avoid unlimited memory growth. Pair them with clear shutdown, interruption handling and backpressure or rejection behavior.

#### Traps / caveats

- Unbounded blocking queues can still exhaust memory.
- Blocking forever can break shutdown.
- They are not message brokers.

#### Optional Anki

Q: What does `take()` do on an empty `BlockingQueue`?
A: Blocks until an element is available or the thread is interrupted.

</details>

<a id="col-queue-008"></a>

<details>
<summary><strong>🧠 COL-QUEUE-008. What is the difference between `ArrayBlockingQueue` and `LinkedBlockingQueue`?</strong></summary>

#### Short answer

`ArrayBlockingQueue` is array-backed and always bounded; `LinkedBlockingQueue` is node-backed and can be bounded or effectively unbounded.

#### Interview answer

`ArrayBlockingQueue` uses a fixed-size array, so capacity is explicit. `LinkedBlockingQueue` uses linked nodes and has an optional capacity; without specifying one, it can grow very large. Both support producer-consumer patterns, but their memory and locking behavior differ.

#### Deep dive

`ArrayBlockingQueue` is predictable in memory. `LinkedBlockingQueue` may allow higher throughput in some producer-consumer patterns but creates node allocations and can hide overload if unbounded.

#### Production angle

For services, explicit bounds are usually important. An unbounded queue converts overload into memory growth and latency instead of a visible rejection signal.

#### Traps / caveats

- Always check whether capacity is bounded.
- Queue size metrics should be monitored.
- Bigger queues increase latency under load.

#### Optional Anki

Q: Which blocking queue is always bounded?
A: `ArrayBlockingQueue`.

</details>

<a id="col-queue-009"></a>

<details>
<summary><strong>🧠 COL-QUEUE-009. What are `DelayQueue`, `SynchronousQueue` and `PriorityBlockingQueue` used for?</strong></summary>

#### Short answer

They are specialized concurrent queues for delayed availability, direct handoff and priority-ordered blocking retrieval.

#### Interview answer

`DelayQueue` holds delayed elements that become available only after their delay expires. `SynchronousQueue` has no internal capacity; each insert waits for a matching take. `PriorityBlockingQueue` orders elements by priority and supports blocking retrieval, but it is unbounded by default.

#### Deep dive

These are not everyday collections. They encode coordination policies. `SynchronousQueue` is used by some executor configurations for direct handoff. `DelayQueue` can support scheduled expiration-like workflows. `PriorityBlockingQueue` can prioritize work but does not solve starvation by itself.

#### Production angle

Use them only when the coordination semantics are exactly what you need. For general scheduling, executor services or dedicated schedulers are often clearer.

#### Traps / caveats

- `PriorityBlockingQueue` is unbounded.
- Priority queues can starve low-priority work.
- Delayed queues are not durable timers.

#### Optional Anki

Q: Which queue has no internal capacity?
A: `SynchronousQueue`.

</details>

<a id="col-queue-010"></a>

<details>
<summary><strong>COL-QUEUE-010. What is the difference between queue-based buffering and backpressure?</strong></summary>

#### Short answer

Buffering stores excess work temporarily; backpressure slows, rejects or limits producers when the system cannot keep up.

#### Interview answer

A queue can smooth short bursts, but if producers are consistently faster than consumers, the queue grows and latency increases. Backpressure is the policy that tells producers to slow down, block, fail fast, shed load or retry later.

#### Deep dive

Unbounded buffering often hides the real problem until memory or latency collapses. Bounded queues make overload visible. The application must then decide what to do: reject requests, return 429/503, drop low-priority work, or apply rate limits.

#### Production angle

Healthy backend systems use queues with limits, metrics and clear overload behavior. A queue without backpressure is often just delayed failure.

#### Traps / caveats

- More queue capacity can increase tail latency.
- Blocking producers can exhaust request threads.
- Retrying rejected work without limits can amplify overload.

#### Optional Anki

Q: What does backpressure do?
A: It limits or signals producers when consumers cannot keep up.

</details>

<a id="col-queue-011"></a>

<details>
<summary><strong>COL-QUEUE-011. How would you choose a queue for a producer-consumer problem?</strong></summary>

#### Short answer

Choose by concurrency needs, capacity, blocking behavior, ordering, fairness, shutdown behavior and overload policy.

#### Interview answer

For in-thread local processing, use `ArrayDeque`. For cross-thread producer-consumer, start with a bounded `BlockingQueue`. If ordering is FIFO, `ArrayBlockingQueue` or bounded `LinkedBlockingQueue` can fit. If work has priorities, consider priority queues carefully. If producers must hand off directly, `SynchronousQueue` may fit.

#### Deep dive

The queue is only one part of the design. You also need worker count, rejection policy, timeouts, metrics, interruption handling, graceful shutdown and idempotent task behavior if retries are possible.

#### Production angle

Prefer bounded queues and explicit failure behavior. Monitor queue depth, age of oldest item, processing rate and rejection count.

#### Traps / caveats

- Unbounded queues hide overload.
- Priority can cause starvation.
- Blocking in request threads can cascade failures.

#### Optional Anki

Q: First production question for a worker queue?
A: Is it bounded, and what happens when it is full?

</details>

<a id="col-queue-012"></a>

<details>
<summary><strong>COL-QUEUE-012. What can go wrong if an application uses an unbounded queue?</strong></summary>

#### Short answer

It can accumulate unlimited work, causing memory growth, high latency, stale tasks and eventual `OutOfMemoryError`.

#### Interview answer

An unbounded queue looks safe because producers rarely block or fail. But if consumers cannot keep up, the queue becomes a growing backlog. Requests may appear accepted while the system is already overloaded.

#### Deep dive

Large queues also increase time-in-queue. Work can become obsolete before processing. Retries can multiply queued tasks. If tasks hold request data, payloads or entity graphs, memory usage grows quickly.

#### Production angle

Use capacity limits, rejection policies, timeouts, cancellation and backpressure. Track queue depth and age, not just worker CPU.

#### Traps / caveats

- "No rejections" is not necessarily healthy.
- More memory only delays failure.
- Queue backlog can violate SLAs even before errors appear.

#### Optional Anki

Q: Main risk of an unbounded queue?
A: Overload turns into memory growth and latency instead of controlled rejection.

</details>
