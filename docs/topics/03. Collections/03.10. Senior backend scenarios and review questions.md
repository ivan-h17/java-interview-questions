# 03.10. Senior backend scenarios and review questions

---

<a id="col-scenario-001"></a>

<details>
<summary><strong>COL-SCENARIO-001. How would you debug `ConcurrentModificationException` in production?</strong></summary>

#### Short answer

Find who is iterating, who is structurally modifying, and whether the collection ownership or concurrency policy is wrong.

#### Interview answer

Start with the stack trace. Identify the collection and the iteration path. Check for enhanced `for` loops that call `remove`, nested methods that mutate the same collection, map view iteration, and shared mutable collections accessed by multiple threads.

#### Deep dive

Fix depends on intent: use `Iterator.remove`, `removeIf`, build a new collection, synchronize around iteration, use a concurrent collection, or publish immutable snapshots. Do not just catch and ignore the exception.

#### Production angle

Add temporary logging around collection size, owner and mutation path if the stack trace is not enough. Check recent deployments for changed iteration or filtering logic.

#### Traps / caveats

- The exception can happen in a single thread.
- Fail-fast detection is best-effort.
- Concurrent collections may hide the exception but not the logic bug.

#### Optional Anki

Q: First thing to inspect for `ConcurrentModificationException`?
A: The iterator path and structural mutation path.

</details>

<a id="col-scenario-002"></a>

<details>
<summary><strong>COL-SCENARIO-002. How would you debug memory growth caused by a collection?</strong></summary>

#### Short answer

Measure which collection is growing, what retains it, and whether entries have a lifecycle or bound.

#### Interview answer

Check heap usage, allocation rate, GC logs and application metrics such as cache size, queue depth or session count. Take a heap dump and inspect retained objects. Look for static maps, unbounded queues, caches without eviction, request data retained by tasks, and collections stored in singleton services.

#### Deep dive

Determine whether growth is expected cardinality, a missing cleanup path or a leak through references. Inspect keys and values: a small map key can retain a large object graph through the value.

#### Production angle

Mitigate with bounds, eviction, TTL, pagination, cleanup hooks or backpressure. Then add metrics so the same class of bug becomes visible earlier.

#### Traps / caveats

- `System.gc()` is not a fix.
- A collection can leak logically while the JVM works correctly.
- `clear()` helps only if no other references retain the data.

#### Optional Anki

Q: Best diagnostic for retained collection memory?
A: Heap dump with retained-size analysis.

</details>

<a id="col-scenario-003"></a>

<details>
<summary><strong>COL-SCENARIO-003. How would you handle duplicate entities from a database query?</strong></summary>

#### Short answer

First understand why duplicates exist, then deduplicate by the correct business key or fix the query.

#### Interview answer

Duplicates may come from joins, fetch joins, missing `DISTINCT`, data quality issues or legitimate one-to-many relationships. If duplicates are not expected, fix the SQL or ORM query. If deduplication is required in Java, use a `LinkedHashMap` or `LinkedHashSet` keyed by stable ID or business key to preserve order.

#### Deep dive

Do not rely blindly on entity `equals()` if JPA equality is tricky. Prefer explicit IDs or value keys. Decide whether to keep first, keep last, merge fields or throw an error.

#### Production angle

For large datasets, deduplicate in SQL or with database constraints where possible. In-memory deduplication can hide data problems and increase memory usage.

#### Traps / caveats

- `HashSet` may reorder results.
- Entity equality may change around persistence.
- Silent deduplication can hide query bugs.

#### Optional Anki

Q: Ordered deduplication by ID?
A: Use `LinkedHashMap<ID, Entity>` or `LinkedHashSet` of IDs.

</details>

<a id="col-scenario-004"></a>

<details>
<summary><strong>COL-SCENARIO-004. What collection-related issues commonly appear in Hibernate/JPA entities?</strong></summary>

#### Short answer

Common issues include mutable entity equality, lazy collections, proxy behavior, cascading side effects, duplicate children and exposing persistent collections directly.

#### Interview answer

JPA entities often have generated IDs, proxies and lifecycle states. Equality and hash codes are tricky, especially before an ID is assigned. Entity collections can be lazy-loaded, dirty-checked and managed by Hibernate-specific implementations, so treating them like ordinary detached lists can cause bugs.

#### Deep dive

Problems include `LazyInitializationException`, N+1 queries while iterating, `HashSet` membership breaking after ID assignment, and `MultipleBagFetchException` style mapping problems. Collection mutation can also trigger cascading persistence operations.

#### Production angle

Map entities to DTOs inside transaction boundaries. Be deliberate about fetch plans, ownership and collection type.

#### Traps / caveats

- Do not expose managed collections directly from APIs.
- Be careful using entities as map keys or set elements.
- Lazy loading inside streams can hide N+1 queries.

#### Optional Anki

Q: Why are JPA entities risky in `HashSet`?
A: Equality/hashCode may depend on mutable or generated identity.

</details>

<a id="col-scenario-005"></a>

<details>
<summary><strong>COL-SCENARIO-005. What collection choices can cause latency spikes in request processing?</strong></summary>

#### Short answer

Large resizing, in-memory sorting, repeated linear scans, huge materialization, copy-on-write mutation and lock contention can all spike latency.

#### Interview answer

Examples include building a huge `ArrayList` without limits, resizing a large `HashMap`, sorting thousands of records per request, doing `list.contains` inside a loop, mutating `CopyOnWriteArrayList`, or synchronizing around a shared collection in a hot path.

#### Deep dive

Latency spikes often come from occasional work: resize copies, GC after allocation bursts, cache eviction scans, large JSON serialization or blocking on collection locks.

#### Production angle

Use profiling, allocation tracking and request traces. Fixes include pre-sizing, using maps for lookup, pagination, database sorting, bounded caches and removing shared mutable hot-path state.

#### Traps / caveats

- Average latency can hide tail spikes.
- Big-O does not show resize pauses.
- "Small in tests" may be huge in production.

#### Optional Anki

Q: Common accidental `O(n^2)` pattern?
A: `list.contains()` inside a loop over another list.

</details>

<a id="col-scenario-006"></a>

<details>
<summary><strong>COL-SCENARIO-006. How would you review code that uses collections heavily?</strong></summary>

#### Short answer

Review semantics, ownership, size bounds, algorithmic complexity, mutability, concurrency and failure modes.

#### Interview answer

Ask whether each collection type matches the requirement: order, uniqueness, lookup, queueing or grouping. Check for repeated linear scans, unbounded accumulation, leaking mutable internals, unsafe iteration, broken equality, unspecified ordering in APIs and shared mutable state.

#### Deep dive

Also inspect stream pipelines and collectors. Look for `Collectors.toMap` duplicate-key assumptions, external mutation in streams, sorting huge data in memory and `Map<String,Object>` hiding domain concepts.

#### Production angle

Tie review comments to risk: latency, memory, correctness, API compatibility, data loss or race conditions.

#### Traps / caveats

- Do not optimize harmless small lists prematurely.
- Do not accept unspecified order in stable APIs.
- Do not let a map replace a domain model accidentally.

#### Optional Anki

Q: Main review dimensions for collection code?
A: Semantics, ownership, size, complexity, mutability and concurrency.

</details>

<a id="col-scenario-007"></a>

<details>
<summary><strong>COL-SCENARIO-007. A service uses a `List` for repeated lookups by ID. What would you check?</strong></summary>

#### Short answer

Check whether repeated linear scans are causing `O(n^2)` behavior and whether a `Map<ID, Value>` or `Set<ID>` would fit better.

#### Interview answer

If code repeatedly does `list.stream().filter(x -> x.id().equals(id)).findFirst()` or `contains` inside loops, it may be slow for large inputs. Build an index map once, then perform `O(1)` average lookups.

#### Deep dive

Also check duplicate IDs. If duplicates are possible, decide whether to keep first, keep last, group into `Map<ID, List<Value>>` or reject the data.

#### Production angle

This pattern often appears in DTO enrichment after database queries or remote calls. Replacing nested scans with a map can reduce CPU and latency significantly.

#### Traps / caveats

- Building the map has memory cost.
- Key equality must match business identity.
- Duplicate-key policy must be explicit.

#### Optional Anki

Q: What replaces repeated list lookup by ID?
A: A `Map<ID, Value>`.

</details>

<a id="col-scenario-008"></a>

<details>
<summary><strong>COL-SCENARIO-008. A cache is implemented with a plain `HashMap`. What questions would you ask?</strong></summary>

#### Short answer

Ask about concurrency, eviction, expiration, size bounds, key stability, invalidation, metrics and lifecycle.

#### Interview answer

A plain `HashMap` may be fine for local temporary lookup inside one method. It is not enough for a shared application cache. You need to know who writes, who reads, how stale entries are removed, what happens under load, and whether keys are immutable and correctly implement equality.

#### Deep dive

If multiple threads access it, `HashMap` is unsafe. If it lives forever, it can leak memory. If values depend on external data, invalidation policy matters. A real cache library often solves these concerns better.

#### Production angle

Ask for metrics: size, hit rate, eviction count, load latency and failures. Add bounds before production traffic.

#### Traps / caveats

- `WeakHashMap` is not a complete cache fix.
- `ConcurrentHashMap` adds thread-safety but not eviction.
- Static maps can retain data until classloader cleanup.

#### Optional Anki

Q: What does plain `HashMap` not provide as a cache?
A: Thread-safety, eviction, expiration, metrics or invalidation policy.

</details>

<a id="col-scenario-009"></a>

<details>
<summary><strong>COL-SCENARIO-009. A response endpoint returns thousands of items in memory. How would you redesign it?</strong></summary>

#### Short answer

Add limits and deterministic pagination, and push filtering/sorting to the data source where appropriate.

#### Interview answer

First check whether clients really need all items. Most endpoints should return pages with a stable sort key and total/count strategy if needed. For exports, use asynchronous jobs or streaming downloads with resource controls.

#### Deep dive

Avoid fetching all rows, mapping all entities to DTOs, sorting in memory and then slicing. That wastes memory and can produce incorrect pagination. Use database indexes and keyset pagination for large changing datasets when possible.

#### Production angle

Set maximum page sizes, response size limits, timeouts and monitoring for result counts. Large responses hurt server memory, network time and clients.

#### Traps / caveats

- Offset pagination can be slow at high offsets.
- Pagination without stable order is incorrect.
- Streaming still needs backpressure and resource cleanup.

#### Optional Anki

Q: What must pagination always define?
A: Stable ordering and size limits.

</details>

<a id="col-scenario-010"></a>

<details>
<summary><strong>COL-SCENARIO-010. What are the most common collection anti-patterns in Java backend code?</strong></summary>

#### Short answer

Common anti-patterns include unbounded collections, wrong collection type, mutable leaks, unsafe concurrency, bad keys, unspecified order and overuse of generic maps.

#### Interview answer

Examples: `List` for repeated key lookup, `HashSet` where response order matters, `Map<String,Object>` for domain models, `HashMap` as a shared cache, mutable objects in `HashSet`, collecting huge query results into memory, and modifying collections during iteration incorrectly.

#### Deep dive

Most collection bugs are not about obscure APIs. They are mismatches between data structure semantics and the real business or production requirement.

#### Production angle

A senior engineer should connect each anti-pattern to failure modes: memory leaks, latency spikes, data corruption, duplicate handling bugs, race conditions or unstable APIs.

#### Traps / caveats

- Do not replace every list with a map without a lookup requirement.
- Do not make everything immutable if copying cost dominates.
- Do not assume tests catch ordering and concurrency bugs.

#### Optional Anki

Q: What is the core collection anti-pattern?
A: Using a data structure whose semantics do not match the requirement.

</details>
