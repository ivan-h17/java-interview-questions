# 03.07. Mutability, wrappers and API design

---

<a id="col-mut-001"></a>

<details>
<summary><strong>COL-MUT-001. What is the difference between mutable, unmodifiable and immutable collections?</strong></summary>

#### Short answer

Mutable collections can change. Unmodifiable collections reject mutation through that reference. Immutable collections cannot be structurally changed after creation.

#### Interview answer

A mutable `ArrayList` can add and remove elements. An unmodifiable wrapper blocks writes through the wrapper but may still reflect changes to its backing collection. An immutable or unmodifiable-copy style collection owns fixed structure after creation, though contained elements may still be mutable.

#### Deep dive

Java APIs often use "unmodifiable" rather than "deeply immutable". `List.copyOf()` creates an unmodifiable shallow copy. If the elements are mutable objects, their internal state can still change and be observed through the list.

#### Production angle

This matters when returning DTO fields, cache values or domain state. The collection structure and element mutability both need a policy.

#### Traps / caveats

- `final List<T>` does not make the list immutable.
- Unmodifiable views can reflect backing changes.
- Shallow immutability is not deep immutability.

#### Optional Anki

Q: Is an unmodifiable list deeply immutable?
A: No.

</details>

<a id="col-mut-002"></a>

<details>
<summary><strong>COL-MUT-002. What does `Collections.unmodifiableList` do, and why is it not the same as an immutable copy?</strong></summary>

#### Short answer

It returns a read-only view of an existing list, not a detached immutable copy.

#### Interview answer

`Collections.unmodifiableList(list)` prevents mutation through the returned wrapper. But if another reference modifies the original list, the unmodifiable view reflects those changes. That is why it is not a full defensive copy.

#### Deep dive

The wrapper is useful when the owner controls the backing list and wants to expose a read-only view. It is dangerous if the backing list is still reachable by untrusted callers or can change unexpectedly.

#### Production angle

In constructors and service returns, prefer `List.copyOf(input)` when you need a stable snapshot. Use unmodifiable views only when live view semantics are intentional.

#### Traps / caveats

- It does not copy the original list.
- It is shallow even as a view.
- It throws at mutation time, not compile time.

#### Optional Anki

Q: Does `Collections.unmodifiableList()` copy?
A: No. It wraps.

</details>

<a id="col-mut-003"></a>

<details>
<summary><strong>COL-MUT-003. What is the difference between `Collections.unmodifiableList`, `List.copyOf`, `List.of` and `Arrays.asList`?</strong></summary>

#### Short answer

`unmodifiableList` wraps, `copyOf` snapshots, `of` creates a fixed unmodifiable list from elements, and `Arrays.asList` creates a fixed-size array-backed view.

#### Interview answer

Use `Collections.unmodifiableList(existing)` for a read-only view of a controlled backing list. Use `List.copyOf(existing)` for an unmodifiable snapshot. Use `List.of(a, b)` for small unmodifiable literals. Use `Arrays.asList(array)` only when you understand it is backed by the array and fixed-size.

#### Deep dive

`List.of` and `List.copyOf` reject nulls. `Arrays.asList` can contain nulls and supports `set`, but not add/remove. None of these deep-copy mutable elements.

#### Production angle

For API boundaries and immutable DTOs, `List.copyOf` is often the safest standard-library choice.

#### Traps / caveats

- `Arrays.asList` is not an `ArrayList`.
- `unmodifiableList` is live if the backing list changes.
- All are shallow with respect to element objects.

#### Optional Anki

Q: Which creates an unmodifiable snapshot?
A: `List.copyOf`.

</details>

<a id="col-mut-004"></a>

<details>
<summary><strong>COL-MUT-004. How can you protect a collection field from external modification?</strong></summary>

#### Short answer

Copy incoming collections and expose unmodifiable copies or controlled behavior instead of raw mutable references.

#### Interview answer

In a constructor, use `this.items = List.copyOf(items)` for a stable unmodifiable snapshot. In a getter, return the stored unmodifiable list or a defensive copy depending on semantics. If elements are mutable, also protect or copy the elements.

#### Deep dive

The goal is to prevent aliasing: the caller should not keep a reference that can mutate your object's internal state. Sometimes the best API is not a getter at all, but domain methods such as `itemCount()` or `containsItem(id)`.

#### Production angle

This prevents cached DTO mutation, invalid domain state and thread-safety bugs when objects are shared.

#### Traps / caveats

- Copy on input is often more important than wrapping on output.
- Mutable elements remain mutable.
- Repeated copying can be expensive for huge collections.

#### Optional Anki

Q: What does defensive copying prevent?
A: External aliases mutating internal state.

</details>

<a id="col-mut-005"></a>

<details>
<summary><strong>COL-MUT-005. What is defensive copying?</strong></summary>

#### Short answer

Defensive copying means creating a copy of mutable input or output to protect object boundaries.

#### Interview answer

If a constructor receives a `List`, storing the caller's list directly lets the caller mutate your object later. A defensive copy breaks that connection. Similarly, returning a copy from a getter prevents callers from mutating internal storage.

#### Deep dive

In modern Java, `List.copyOf`, `Set.copyOf` and `Map.copyOf` are common for unmodifiable shallow copies. `new ArrayList<>(input)` is useful when the object needs its own mutable internal copy.

#### Production angle

Defensive copying is important for immutable objects, cache values, configuration snapshots and API response models.

#### Traps / caveats

- It is usually shallow.
- Copying can cost memory and CPU.
- Do not copy blindly if ownership is already clear and performance matters.

#### Optional Anki

Q: Input defensive copy example?
A: `this.items = List.copyOf(items);`

</details>

<a id="col-mut-006"></a>

<details>
<summary><strong>COL-MUT-006. When do you need shallow copy vs deep copy for collections?</strong></summary>

#### Short answer

Use a shallow copy to protect collection structure; use a deep copy when mutable elements also need independent state.

#### Interview answer

A shallow copy creates a new collection containing references to the same elements. This is enough when elements are immutable or shared intentionally. A deep copy also copies the elements or object graph, which is needed when element mutation would break invariants.

#### Deep dive

Deep copying is domain-specific. There is no universal safe deep-copy operation for arbitrary objects. You need to know how to copy each element and whether nested objects, IDs or external resources should be copied.

#### Production angle

Deep copying can be expensive and error-prone. Prefer immutable element types where possible.

#### Traps / caveats

- `List.copyOf` is shallow.
- Serialization-based deep copy is usually a smell.
- Copying entities can break persistence identity.

#### Optional Anki

Q: Does a shallow copy copy element objects?
A: No.

</details>

<a id="col-mut-007"></a>

<details>
<summary><strong>COL-MUT-007. How can mutable elements break an immutable collection design?</strong></summary>

#### Short answer

Even if the collection cannot add or remove elements, mutable element objects can still change observable state.

#### Interview answer

An unmodifiable `List<Address>` prevents `add`, but if `Address` has setters, callers can still mutate an address already in the list. The collection structure is protected, but the aggregate is not deeply immutable.

#### Deep dive

This matters for equality, hash codes, cache keys and thread-safety. If a collection contains mutable elements used by a `Set` or `Map`, mutation can break lookup even when the collection wrapper is unmodifiable.

#### Production angle

For immutable DTOs and domain snapshots, use immutable element types or copy elements into immutable representations.

#### Traps / caveats

- Unmodifiable is not deep immutable.
- Records can contain mutable components.
- Mutable elements can break cached hash codes.

#### Optional Anki

Q: What remains mutable in `List.copyOf(mutableObjects)`?
A: The element objects themselves.

</details>

<a id="col-mut-008"></a>

<details>
<summary><strong>COL-MUT-008. How should DTOs and records handle collection fields?</strong></summary>

#### Short answer

They should document mutability and usually copy collection fields on construction to avoid representation exposure.

#### Interview answer

Records are shallowly immutable: their component references are final, but referenced collections can still be mutable. A record with a `List` component should often use a compact constructor with `List.copyOf(items)` to protect the collection structure.

#### Deep dive

DTOs used only within serialization frameworks may be mutable for framework convenience. But API response DTOs and command objects are often safer with unmodifiable collection fields.

#### Production angle

Copying DTO collection fields prevents later service code from mutating already validated or cached request/response data.

#### Traps / caveats

- Record accessors return the same reference unless you copy in the constructor.
- JSON frameworks may require constructors or annotations.
- Copying does not deep-copy mutable elements.

#### Optional Anki

Q: Are records deeply immutable?
A: No. They are shallowly immutable by default.

</details>

<a id="col-mut-009"></a>

<details>
<summary><strong>🧠 COL-MUT-009. What are synchronized collection wrappers?</strong></summary>

#### Short answer

They are wrappers from `Collections` that synchronize access to an underlying collection.

#### Interview answer

Examples include `Collections.synchronizedList`, `synchronizedSet` and `synchronizedMap`. They wrap a collection so individual method calls synchronize on the wrapper's monitor.

#### Deep dive

Iteration still requires manual synchronization around the whole traversal. Also, method-level synchronization does not automatically make compound actions atomic, such as check-then-put.

#### Production angle

They can be useful for simple legacy integration or low-contention shared collections. For scalable concurrent access, prefer concurrent collections or immutable snapshots.

#### Traps / caveats

- Synchronize manually during iteration.
- Keep and use the wrapper reference, not the original backing collection.
- Compound invariants still need external locking.

#### Optional Anki

Q: Are synchronized wrappers enough for safe iteration?
A: Not by themselves; synchronize around iteration.

</details>

<a id="col-mut-010"></a>

<details>
<summary><strong>🧠 COL-MUT-010. What are checked collection wrappers, and when are they useful?</strong></summary>

#### Short answer

Checked wrappers enforce runtime type checks for collection elements.

#### Interview answer

`Collections.checkedList(list, Type.class)` returns a wrapper that checks inserted elements at runtime. It is mostly useful when working with raw types, legacy APIs or dynamically typed boundaries where generic compile-time checks are not enough.

#### Deep dive

Java generics use type erasure, so raw or unchecked code can pollute a collection with wrong element types. Checked wrappers fail earlier at insertion time rather than later with a confusing `ClassCastException`.

#### Production angle

They are uncommon in modern application code but can help protect boundaries around old libraries or reflection-heavy integration.

#### Traps / caveats

- They do not replace proper generics.
- They check runtime class, not arbitrary generic nested types.
- Existing wrong elements may still be present.

#### Optional Anki

Q: Why use a checked wrapper?
A: To catch wrong runtime element types at a boundary.

</details>

<a id="col-api-001"></a>

<details>
<summary><strong>COL-API-001. What collection type should a method return: `List`, `Set`, `Collection`, `Iterable` or `Stream`?</strong></summary>

#### Short answer

Return the narrowest type that honestly expresses the contract callers can rely on.

#### Interview answer

Return `List` when order and duplicates matter. Return `Set` when uniqueness matters. Return `Collection` when callers need size or containment but not list/set specifics. Return `Iterable` for simple traversal. Return `Stream` only when lazy processing or resource ownership is clearly documented.

#### Deep dive

API return types are contracts. If you return `List`, callers may rely on ordering and positional access. If you return `Set`, callers may assume no duplicates. Avoid returning concrete implementations unless callers need implementation-specific behavior.

#### Production angle

For repository or service APIs, consider result size and lifecycle. Returning `Stream` from a database-backed method can leak open resources if transaction boundaries are unclear.

#### Traps / caveats

- Do not return mutable internals.
- `Collection` does not guarantee order.
- `Stream` is single-use and may need closing.

#### Optional Anki

Q: What should API collection return types express?
A: Ordering, uniqueness, mutability and lifecycle guarantees.

</details>

<a id="col-api-002"></a>

<details>
<summary><strong>COL-API-002. When should method parameters use `Collection` instead of `List`?</strong></summary>

#### Short answer

Use `Collection` when the method only needs a group of elements and does not require index access or list-specific ordering.

#### Interview answer

If a method just validates, iterates, counts or builds a `Set` from inputs, `Collection<T>` is more flexible than `List<T>`. It lets callers pass lists, sets or other collections without unnecessary copying.

#### Deep dive

Use `Iterable` if even size is not needed. Use `List` if the method needs stable positional order, random access, duplicates by position or indexed operations.

#### Production angle

Flexible parameter types reduce allocation and make APIs easier to use. But do not make the type so broad that requirements become hidden.

#### Traps / caveats

- `Collection` can be unordered.
- `Collection` can be mutable or unmodifiable.
- Null elements may or may not be allowed by callers.

#### Optional Anki

Q: Parameter type for "any group of IDs"?
A: Often `Collection<ID>`.

</details>

<a id="col-api-003"></a>

<details>
<summary><strong>COL-API-003. How should APIs express ordering, uniqueness and mutability guarantees?</strong></summary>

#### Short answer

Use appropriate types, method names and documentation, and return defensive or unmodifiable copies when needed.

#### Interview answer

Types communicate part of the contract: `List` suggests order, `Set` suggests uniqueness, `SortedSet` suggests sorted uniqueness, and `Map` suggests lookup by key. Mutability and ownership should be documented or enforced with unmodifiable results.

#### Deep dive

Sometimes types are not enough. A `List` can be insertion-ordered, sorted or arbitrary. A `Set` can be hash-ordered, insertion-ordered or sorted. If clients rely on order, say exactly what order.

#### Production angle

Ambiguous contracts lead to fragile clients and tests. Stable API responses should define ordering explicitly.

#### Traps / caveats

- Interface type does not fully define iteration order.
- Returning unmodifiable does not mean elements are immutable.
- Changing order can be a breaking API change.

#### Optional Anki

Q: Does `Set` imply sorted order?
A: No.

</details>

<a id="col-api-004"></a>

<details>
<summary><strong>COL-API-004. Should APIs return `null` or an empty collection?</strong></summary>

#### Short answer

Usually return an empty collection, not null.

#### Interview answer

An empty collection means "there are no elements" and lets callers iterate safely. Returning null forces every caller to add null checks and creates easy `NullPointerException` bugs.

#### Deep dive

Use null only if it has a distinct meaning from empty, and document it clearly. In most APIs, absence of results and zero results should be represented by an empty collection.

#### Production angle

Empty collections reduce defensive boilerplate in controllers, mappers and service code. They also work better with JSON serialization and stream pipelines.

#### Traps / caveats

- Do not return a shared mutable empty collection.
- Empty does not mean success in every domain; validate semantics.
- Some legacy APIs still return null and need adaptation.

#### Optional Anki

Q: Preferred "no results" return?
A: Empty collection.

</details>

<a id="col-api-005"></a>

<details>
<summary><strong>COL-API-005. How would you design an API that returns a large number of elements?</strong></summary>

#### Short answer

Avoid unbounded in-memory results; use pagination, streaming, cursors, limits or asynchronous export depending on the use case.

#### Interview answer

A method returning `List<T>` implies the full result is materialized. For large data, define limits and ordering, return pages, stream carefully with resource boundaries, or move long-running exports to background jobs.

#### Deep dive

Pagination requires deterministic ordering. Streaming requires clear ownership of database connections, transactions and close behavior. For APIs, cursor or keyset pagination is often better than loading all rows and slicing in memory.

#### Production angle

Unbounded list returns cause memory pressure, slow requests and unstable latency. Add limits at repository, service and HTTP layers.

#### Traps / caveats

- Offset pagination can become slow and inconsistent for large changing datasets.
- Returning `Stream` can leak resources.
- Sorting all data in memory is often wrong.

#### Optional Anki

Q: What is dangerous about `List<T> findAll()`?
A: It can imply unbounded materialization.

</details>

<a id="col-api-006"></a>

<details>
<summary><strong>COL-API-006. How would you represent a cache of values by key?</strong></summary>

#### Short answer

Use a map-like abstraction, but prefer a real cache library when eviction, expiration, concurrency or metrics matter.

#### Interview answer

For simple local lookup, `Map<K,V>` may be enough. For concurrent access, `ConcurrentHashMap` can work for simple cases. But once you need TTL, maximum size, eviction policy, refresh, loading, metrics or stampede control, use a cache library.

#### Deep dive

A cache key should be immutable and stable. The value lifecycle should be clear: when is it invalidated, refreshed or evicted? A plain `HashMap` does not answer those questions.

#### Production angle

Cache bugs create stale data, memory leaks and race conditions. Monitor hit rate, size, eviction, load failures and latency.

#### Traps / caveats

- A map is not a cache policy.
- Static maps can leak memory.
- Weak references are not a business eviction strategy.

#### Optional Anki

Q: When is `Map` not enough for caching?
A: When eviction, expiration, concurrency or metrics matter.

</details>

<a id="col-api-007"></a>

<details>
<summary><strong>COL-API-007. How would you choose between `List` and `Set` for DTO fields?</strong></summary>

#### Short answer

Use `List` when order and duplicates are meaningful; use `Set` when uniqueness is part of the contract.

#### Interview answer

DTO fields should match API semantics, not just internal implementation. JSON arrays are ordered, so `List` is often clearer for responses. Use `Set` when the API explicitly promises unique values and clients should not depend on duplicates.

#### Deep dive

Be careful with `Set` in serialized APIs: iteration order may be unstable unless you use an ordered set or sort before returning. Also consider validation: duplicate input may need a clear error, not silent deduplication.

#### Production angle

Changing a DTO field from list to set can change JSON output order and compatibility. Keep API contracts stable.

#### Traps / caveats

- Plain `HashSet` can produce unstable response order.
- Silent deduplication can hide client bugs.
- DTO equality may change if collection type changes.

#### Optional Anki

Q: Which DTO type when order matters?
A: `List`.

</details>

<a id="col-api-008"></a>

<details>
<summary><strong>COL-API-008. How would you safely expose collection data from a Spring service?</strong></summary>

#### Short answer

Return owned snapshots or unmodifiable results, and avoid exposing mutable internal state from singleton services or caches.

#### Interview answer

A Spring singleton service may serve many requests concurrently. It should not return internal mutable collections that callers can mutate. Build a result object, copy data as needed, and document ordering and mutability.

#### Deep dive

If data comes from JPA entities, avoid exposing live persistent collections directly. Map entities to DTOs inside a well-defined transaction boundary and return DTO collections with stable semantics.

#### Production angle

This prevents cross-request mutation, lazy-loading surprises and cache corruption. It also keeps controller code from depending on persistence internals.

#### Traps / caveats

- Spring singleton beans are shared objects.
- Unmodifiable views of mutable internal lists can still change.
- JPA lazy collections can fail outside transactions.

#### Optional Anki

Q: Should a service return an internal mutable list?
A: No. Return a snapshot or controlled view.

</details>

<a id="col-api-009"></a>

<details>
<summary><strong>COL-API-009. What are the most common collection anti-patterns in API design?</strong></summary>

#### Short answer

Common anti-patterns include returning null, leaking mutability, relying on unspecified order, using generic maps for domain data and returning unbounded lists.

#### Interview answer

Other common problems are accepting overly specific types, silently deduplicating client input, using `List` for repeated lookup, returning JPA collections directly and exposing `Map<String,Object>` instead of typed DTOs.

#### Deep dive

Good collection APIs make guarantees explicit: what order, whether duplicates are allowed, whether result is mutable, how large it can be, and who owns the returned data.

#### Production angle

These anti-patterns create flaky tests, compatibility breaks, memory issues and security bugs from representation exposure.

#### Traps / caveats

- "Works with current implementation" is not an API contract.
- Hidden mutability becomes a concurrency risk.
- Generic containers make validation and refactoring harder.

#### Optional Anki

Q: Name one API collection anti-pattern.
A: Returning an internal mutable collection.

</details>
