# 03.09. Performance, memory and Streams integration

---

<a id="col-perf-001"></a>

<details>
<summary><strong>COL-PERF-001. What are the typical time complexities of common `List`, `Set` and `Map` operations?</strong></summary>

#### Short answer

`ArrayList` has `O(1)` indexed access and amortized append, hash collections have average `O(1)` lookup, and tree collections usually have `O(log n)` lookup and updates.

#### Interview answer

`ArrayList.get` is `O(1)`, middle insert/remove is `O(n)`. `LinkedList.get(index)` is `O(n)`, but end operations are `O(1)`. `HashSet` and `HashMap` are average `O(1)` for add/get/contains with good hashes. `TreeSet` and `TreeMap` are typically `O(log n)`.

#### Deep dive

Complexity depends on operation and data quality. Bad hash distribution, expensive equality, resizing, allocation and cache misses can dominate. `contains` on a list is `O(n)`.

#### Production angle

The most common bug is using a list for repeated lookup in a loop, creating accidental `O(n^2)` behavior. Use a `Set` or `Map` when lookup by key matters.

#### Traps / caveats

- Average `O(1)` is not guaranteed worst case.
- Big-O hides memory and CPU locality.
- Complexity tables do not replace profiling.

#### Optional Anki

Q: Typical `HashMap.get()` complexity?
A: Average `O(1)`, assuming good hashing.

</details>

<a id="col-perf-002"></a>

<details>
<summary><strong>COL-PERF-002. Why is Big-O not enough to choose a collection?</strong></summary>

#### Short answer

Big-O ignores constants, memory layout, allocation, GC pressure, concurrency, data size and actual access patterns.

#### Interview answer

Two operations with the same Big-O can have very different real performance. `ArrayList` and `LinkedList` both have `O(n)` traversal, but `ArrayList` is usually faster because it scans contiguous references. A hash lookup can be slow if hashing or equality is expensive.

#### Deep dive

Big-O describes growth as input size changes. It does not say whether data fits in cache, whether objects are boxed, whether the collection resizes, or whether lock contention exists.

#### Production angle

Choose by semantics first, then validate performance with representative data and measurements. Avoid "LinkedList is faster for inserts" style answers without context.

#### Traps / caveats

- Constants matter for small and medium collections.
- Memory locality can dominate.
- Wrong semantics are not fixed by good Big-O.

#### Optional Anki

Q: What does Big-O miss for collections?
A: Constants, memory, allocation, cache locality and workload shape.

</details>

<a id="col-perf-003"></a>

<details>
<summary><strong>🧠 COL-PERF-003. How do memory overhead and CPU cache locality affect collection performance?</strong></summary>

#### Short answer

Collections with fewer objects and contiguous storage are often faster and use less memory than pointer-heavy structures.

#### Interview answer

`ArrayList` stores references in an array, which is compact and easy to scan. `LinkedList` stores a node per element, adding object headers and pointers. Hash maps store table arrays plus nodes or entries. More objects mean more memory and more GC work.

#### Deep dive

CPU caches favor predictable sequential access. Pointer chasing through many heap objects can cause cache misses. This is why array-backed structures often outperform linked structures even when Big-O looks similar.

#### Production angle

Large collections can dominate heap profiles. Use heap dumps and allocation profiling to see retained objects and object counts.

#### Traps / caveats

- Standard collections store object references, not primitive values inline.
- Memory cost depends on JVM and object layout.
- Compact code can still allocate too much.

#### Optional Anki

Q: Which usually has better locality, `ArrayList` or `LinkedList`?
A: `ArrayList`.

</details>

<a id="col-perf-004"></a>

<details>
<summary><strong>COL-PERF-004. How do boxing and unboxing affect collection memory usage?</strong></summary>

#### Short answer

Standard generic collections store objects, so primitive values are boxed into wrapper objects such as `Integer` or `Long`.

#### Interview answer

`List<Integer>` stores references to `Integer` objects, not raw `int` values. Boxing increases memory usage and allocation pressure. Unboxing can add CPU cost and can throw `NullPointerException` if a wrapper is null.

#### Deep dive

Some wrapper values may be cached, but code should not depend on caching for memory design. Large primitive-heavy datasets can be much more compact in primitive arrays or specialized primitive collections.

#### Production angle

Boxed IDs, counters and numeric time series in huge collections can create major heap pressure. Consider arrays, database aggregation or primitive collection libraries if this is a hot area.

#### Traps / caveats

- `List<int>` is not valid Java.
- Unboxing null throws `NullPointerException`.
- `Integer` identity comparisons are dangerous.

#### Optional Anki

Q: What does `List<Integer>` store?
A: References to `Integer` objects.

</details>

<a id="col-perf-005"></a>

<details>
<summary><strong>COL-PERF-005. What is the cost of storing millions of objects in standard collections?</strong></summary>

#### Short answer

The cost includes collection structure, object headers, references, boxed values, retained object graphs and GC overhead.

#### Interview answer

A collection does not only store "values." It stores references and internal structures. Each object may reference more objects. A million entries in a `HashMap` can mean a table, entry nodes, keys, values and nested fields.

#### Deep dive

The retained size can be much larger than expected. Memory also affects CPU through cache misses and GC. Large collections can move from young generation to old generation and increase pause times or concurrent GC work.

#### Production angle

Use heap dumps, allocation profiling and cardinality metrics. For large datasets, prefer streaming, pagination, indexes, compression or purpose-built storage.

#### Traps / caveats

- `size()` is not memory size.
- Values can retain large object graphs.
- Clearing a collection helps only if no other references remain.

#### Optional Anki

Q: What is retained size?
A: Memory kept alive by an object and everything reachable from it.

</details>

<a id="col-perf-006"></a>

<details>
<summary><strong>COL-PERF-006. How would you reduce memory usage of large collections?</strong></summary>

#### Short answer

Reduce element count, avoid unnecessary objects, pre-size appropriately, use compact structures, stream data and remove references when no longer needed.

#### Interview answer

First ask whether all data must be in memory. Push filtering and aggregation to the database when appropriate. Use pagination or streaming. Use `ArrayList` instead of node-heavy structures when order is enough. Avoid boxing-heavy collections for primitive data. Pre-size hash maps or lists when large size is known.

#### Deep dive

Also review key and value design. Avoid storing whole entities when IDs or small DTOs are enough. Remove expired cache entries. Use bounded caches instead of plain maps.

#### Production angle

Heap dumps should guide changes. Measure before and after, especially for GC pause time, allocation rate and retained heap.

#### Traps / caveats

- Pre-sizing can waste memory if estimates are too high.
- Compacting data can hurt readability if premature.
- Weak references are not a substitute for lifecycle management.

#### Optional Anki

Q: First question for a huge in-memory collection?
A: Does all this data need to be in memory?

</details>

<a id="col-perf-007"></a>

<details>
<summary><strong>COL-PERF-007. How would you avoid loading an entire dataset into memory?</strong></summary>

#### Short answer

Use database filtering, pagination, streaming cursors, batching or asynchronous export instead of materializing everything into a collection.

#### Interview answer

Do not call `findAll()` and then filter in Java if the database can filter. For APIs, return pages with stable ordering. For batch jobs, process chunks. For large exports, stream carefully or generate asynchronously.

#### Deep dive

Streaming is not free. It must manage resources such as database connections and transactions. Pagination must be deterministic. Batch processing must handle partial failures and retries.

#### Production angle

Large materialized lists cause memory growth and slow endpoints. Put limits in repository queries and HTTP endpoints.

#### Traps / caveats

- Java streams over database results may keep connections open.
- Offset pagination can degrade at high offsets.
- In-memory sorting after pagination gives wrong global order.

#### Optional Anki

Q: Best place to filter large database data?
A: Usually in the database query.

</details>

<a id="col-perf-008"></a>

<details>
<summary><strong>COL-PERF-008. When would you prefer streaming or pagination over a collection?</strong></summary>

#### Short answer

When the result may be large, expensive to materialize, or consumed incrementally.

#### Interview answer

Use pagination for user-facing APIs and query results where clients need chunks. Use streaming for internal pipelines or file/database processing where each item can be handled and discarded. Use a collection when the full result is small and genuinely needed for random access or repeated use.

#### Deep dive

Pagination gives clear boundaries and retry behavior. Streaming can reduce peak memory but complicates resource ownership and error handling.

#### Production angle

For backend APIs, pagination is usually easier to operate than streaming because it limits response size and request duration.

#### Traps / caveats

- Stream results are often single-use.
- Pagination needs stable ordering.
- Collecting a stream back to a list removes the memory benefit.

#### Optional Anki

Q: What does pagination protect?
A: Memory, latency and response size.

</details>

<a id="col-perf-009"></a>

<details>
<summary><strong>COL-PERF-009. How can collection choice affect GC pressure?</strong></summary>

#### Short answer

Collections with more allocation, resizing, node objects, boxed values or copy-on-write behavior create more garbage and retained heap.

#### Interview answer

`LinkedList` allocates nodes. `HashMap` allocates internal structures and may resize. `CopyOnWriteArrayList` allocates a new array on writes. Boxing primitives creates wrapper objects. Temporary collections in stream pipelines or nested loops can increase allocation rate.

#### Deep dive

GC pressure comes from both live data and allocation churn. Short-lived temporary collections stress young generation. Long-lived large maps increase old-gen occupancy and marking work.

#### Production angle

Watch allocation rate, GC pause time, old-gen usage and heap dumps. Reducing collection churn can improve tail latency.

#### Traps / caveats

- Lower allocation is not always worth worse code.
- Object pooling collections is usually a bad fix.
- `clear()` does not reduce `ArrayList` capacity.

#### Optional Anki

Q: Which list allocates a node per element?
A: `LinkedList`.

</details>

<a id="col-perf-010"></a>

<details>
<summary><strong>COL-PERF-010. How can collection resizing cause latency spikes?</strong></summary>

#### Short answer

Resizing allocates larger internal storage and copies or redistributes existing entries, which can be slow for large collections.

#### Interview answer

`ArrayList` growth copies existing references to a new array. `HashMap` resize allocates a larger table and redistributes entries. These operations are occasional, but when they happen on a large collection in a request path, they can create visible latency.

#### Deep dive

Pre-sizing can reduce resizing when expected size is known. But over-sizing wastes memory, so use it for large or hot paths, not everywhere.

#### Production angle

Latency spikes during aggregation or response building can come from repeated resizing. Allocation profiles and flame graphs can reveal this.

#### Traps / caveats

- Amortized cost hides individual slow operations.
- Exact growth factors are implementation details.
- Pre-sizing does not fix unbounded data.

#### Optional Anki

Q: Why pre-size a large `ArrayList`?
A: To reduce repeated reallocations and copies.

</details>

<a id="col-perf-011"></a>

<details>
<summary><strong>🧠 COL-PERF-011. How would you benchmark collection performance correctly?</strong></summary>

#### Short answer

Use realistic data and a proper JVM benchmark harness such as JMH, with warmup, measurement iterations and dead-code prevention.

#### Interview answer

Microbenchmarks in plain loops are often wrong because the JIT can optimize away work, startup effects dominate, and data does not match production. JMH handles warmup, forks and measurement more reliably.

#### Deep dive

Benchmark the actual operation: building, lookup, iteration, mutation, sorting or memory behavior. Include realistic element types, key distributions, collision patterns and sizes.

#### Production angle

Use benchmarks for local decisions and production profiling for real incidents. They answer different questions.

#### Traps / caveats

- Do not benchmark only tiny collections.
- Consume results so work is not optimized away.
- Include allocation and GC metrics when memory matters.

#### Optional Anki

Q: Standard Java microbenchmark harness?
A: JMH.

</details>

<a id="col-perf-012"></a>

<details>
<summary><strong>🧠 COL-PERF-012. What can go wrong with microbenchmarks for collections?</strong></summary>

#### Short answer

They can measure JVM warmup, dead code, unrealistic data, allocation artifacts or the wrong operation.

#### Interview answer

A naive benchmark might run once, use `System.currentTimeMillis`, ignore warmup, let the JIT eliminate unused results, or test tiny data that fits in cache. It may conclude `LinkedList` is better in a scenario that never occurs in production.

#### Deep dive

Collection performance depends on size, data distribution, element equality cost, mutation frequency, memory pressure and CPU cache behavior. A benchmark that ignores these is misleading.

#### Production angle

Use JMH for micro-level comparisons and production profiling for application-level effects.

#### Traps / caveats

- One run is not a benchmark.
- Random data generation inside the measured section can dominate.
- Results on one JDK or hardware may not generalize.

#### Optional Anki

Q: Biggest naive benchmark risk?
A: Measuring optimized-away or unrealistic work.

</details>

<a id="col-perf-013"></a>

<details>
<summary><strong>COL-PERF-013. What production metrics can reveal collection-related memory problems?</strong></summary>

#### Short answer

Heap usage, allocation rate, GC pauses, old-gen occupancy, object counts, cache sizes, queue depths and endpoint latency can all point to collection issues.

#### Interview answer

A growing map or queue may show as rising heap, old-gen growth, longer GC pauses and increasing latency. Cache metrics can show size and eviction. Queue metrics can show backlog and age. Heap dumps can reveal which collection retains memory.

#### Deep dive

Metrics should include cardinality of key collections where possible: cache entries, in-flight tasks, sessions, pending messages, batch sizes and response list sizes.

#### Production angle

During an incident, combine metrics with heap dumps or Java Flight Recorder. Look for unexpected retained paths and object counts.

#### Traps / caveats

- Total heap alone does not identify the owner.
- GC tuning will not fix unbounded collections.
- Queue depth without item age can hide stale backlog.

#### Optional Anki

Q: Best artifact for finding retained collection memory?
A: A heap dump.

</details>

<a id="col-stream-001"></a>

<details>
<summary><strong>COL-STREAM-001. How are collections related to Streams?</strong></summary>

#### Short answer

Collections store data; streams process data from a source such as a collection.

#### Interview answer

`collection.stream()` creates a stream pipeline over the collection's elements. The stream is not a data structure and does not store the elements itself. It processes elements through intermediate and terminal operations.

#### Deep dive

The collection's spliterator provides stream characteristics such as order, size, distinctness or sortedness. That can affect stream behavior and parallel performance.

#### Production angle

Streams are good for transformations and aggregation when readable. They are not a replacement for choosing the right collection or for database-side filtering.

#### Traps / caveats

- A stream is single-use.
- Mutating the source during stream execution is dangerous.
- Collecting a stream materializes data.

#### Optional Anki

Q: Is a Stream a collection?
A: No.

</details>

<a id="col-stream-002"></a>

<details>
<summary><strong>COL-STREAM-002. When should you use a Stream instead of explicit iteration?</strong></summary>

#### Short answer

Use streams when they make transformation, filtering or aggregation clearer without hiding side effects or resource boundaries.

#### Interview answer

Streams are good for declarative pipelines such as filter, map, sort and collect. A loop is often better for complex branching, checked exceptions, early mutation, debugging or business workflows with side effects.

#### Deep dive

The choice is readability and correctness first. Streams should be stateless and non-interfering. If the pipeline becomes long and hard to name, extract methods or use a loop.

#### Production angle

Avoid doing database calls, HTTP calls or writes inside stream `map` or `forEach` unless the side effects are intentional and controlled.

#### Traps / caveats

- Streams are not automatically faster.
- Parallel streams can hurt server throughput.
- Complex exception handling can make streams unreadable.

#### Optional Anki

Q: Stream or loop for complex side effects?
A: Usually a loop.

</details>

<a id="col-stream-003"></a>

<details>
<summary><strong>COL-STREAM-003. What is the difference between `stream().toList()`, `Collectors.toList()` and collecting to a specific collection?</strong></summary>

#### Short answer

In Java 16+, `stream().toList()` returns an unmodifiable list; `Collectors.toList()` does not guarantee a specific implementation or mutability; `toCollection` lets you choose.

#### Interview answer

Use `stream().toList()` on Java 16+ when an unmodifiable result is fine. Use `collect(Collectors.toList())` when compatibility with older Java or collector composition is needed, but do not rely on mutability as a contract. Use `Collectors.toCollection(ArrayList::new)` or similar when you need a specific mutable collection.

#### Deep dive

This distinction matters because later code may call `add`. If mutability is required, request it explicitly instead of relying on current implementation behavior.

#### Production angle

Stable mutability contracts avoid runtime `UnsupportedOperationException` after Java upgrades or refactors.

#### Traps / caveats

- `toList()` result is unmodifiable.
- `Collectors.toList()` should not be treated as a guaranteed `ArrayList`.
- All are shallow collections.

#### Optional Anki

Q: How to collect to a specific collection?
A: `Collectors.toCollection(Supplier)`.

</details>

<a id="col-stream-004"></a>

<details>
<summary><strong>COL-STREAM-004. What can go wrong with `Collectors.toMap`, and how do you handle duplicate keys?</strong></summary>

#### Short answer

`Collectors.toMap` throws on duplicate keys unless you provide a merge function.

#### Interview answer

If two stream elements produce the same key, the simple `toMap(keyMapper, valueMapper)` collector fails. Provide a merge function such as keep first, keep last, combine values or throw a domain-specific exception.

#### Deep dive

You can also supply a map factory to choose `LinkedHashMap`, `TreeMap` or another implementation. This matters when output order or sorted keys are required.

#### Production angle

Duplicate-key failures often appear with real database data that violates assumptions. Decide whether duplicates are invalid data or expected business cases.

#### Traps / caveats

- Duplicate keys may be caused by null normalization or case-insensitive business keys.
- Default map type does not preserve insertion order as an API guarantee.
- Merge functions should be deterministic.

#### Optional Anki

Q: Why can `Collectors.toMap` throw?
A: Duplicate keys without a merge function.

</details>

<a id="col-stream-005"></a>

<details>
<summary><strong>🧠 COL-STREAM-005. How do you preserve ordering when collecting stream results?</strong></summary>

#### Short answer

Use ordered stream sources and collect into order-preserving collections such as `List` or `LinkedHashMap` when map order matters.

#### Interview answer

A list source has encounter order. Collecting to a list preserves that order for sequential streams. For maps, use a collector overload with a map supplier such as `LinkedHashMap::new` if iteration order matters.

#### Deep dive

Parallel streams and unordered sources complicate ordering. `HashSet` source order is not a stable API guarantee. Sorting before collecting can define order explicitly, but it may buffer and cost memory.

#### Production angle

Stable ordering matters for API responses, pagination, tests and signatures. Make it explicit rather than relying on incidental `HashMap` behavior.

#### Traps / caveats

- `HashMap` order is not a contract.
- Parallel operations may require `forEachOrdered` or ordered collectors.
- Sorting in memory can be expensive.

#### Optional Anki

Q: Which map preserves insertion order when collecting?
A: `LinkedHashMap`.

</details>

<a id="col-stream-006"></a>

<details>
<summary><strong>🧠 COL-STREAM-006. How do parallel streams interact with collection implementations?</strong></summary>

#### Short answer

Parallel stream performance depends heavily on how well the source collection's spliterator can split and what ordering constraints exist.

#### Interview answer

Array-backed collections such as `ArrayList` split efficiently. Linked structures are harder to split. Ordered sources can impose extra coordination, especially for operations like `limit`, `findFirst` or ordered collection.

#### Deep dive

Concurrent modification rules still matter. Parallel streams require stateless, non-interfering operations. Mutating a shared `ArrayList` inside parallel `forEach` is a classic bug.

#### Production angle

Parallel streams can hurt backend request latency by using common pool threads and competing with other work. Use them only after measuring.

#### Traps / caveats

- Parallel is not automatically faster.
- Blocking I/O inside parallel streams is dangerous.
- Source splitting quality matters.

#### Optional Anki

Q: Which list usually splits better for parallel streams?
A: `ArrayList`.

</details>

<a id="col-stream-007"></a>

<details>
<summary><strong>COL-STREAM-007. Why is mutating shared collections inside streams dangerous?</strong></summary>

#### Short answer

It introduces side effects, interference and possible race conditions, especially with parallel streams.

#### Interview answer

Adding to an external `ArrayList` inside `stream().forEach(...)` mixes traversal with mutation. In a sequential stream it may still be unclear or cause concurrent modification if mutating the source. In a parallel stream it can corrupt results because `ArrayList` is not thread-safe.

#### Deep dive

Use collectors to accumulate results instead of mutating external collections. For complex stateful workflows, a loop may be clearer.

#### Production angle

This bug creates missing elements, duplicate elements, random exceptions and hard-to-reproduce production behavior.

#### Traps / caveats

- Thread-safe external collections can still make logic unclear.
- Mutating the stream source is interference.
- Side effects may execute in unexpected order.

#### Optional Anki

Q: Preferred way to accumulate stream results?
A: Use `collect`, not external mutation.

</details>
