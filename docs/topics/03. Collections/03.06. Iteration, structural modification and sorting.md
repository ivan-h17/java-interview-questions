# 03.06. Iteration, structural modification and sorting

---

<a id="col-iter-001"></a>

<details>
<summary><strong>COL-ITER-001. What is `Iterator`?</strong></summary>

#### Short answer

`Iterator` is the standard object for traversing elements one by one.

#### Interview answer

An `Iterator<E>` exposes `hasNext()`, `next()` and optional `remove()`. It decouples traversal from the collection implementation, so code can iterate a list, set or other collection without knowing how it is stored.

#### Deep dive

Many collections return fail-fast iterators that detect structural modification by the collection during iteration. Some concurrent collections return weakly consistent or snapshot iterators instead.

#### Production angle

Use iterators when you need controlled removal during traversal or when enhanced `for` does not give enough control.

#### Traps / caveats

- Calling `next()` without checking can throw `NoSuchElementException`.
- `remove()` is optional and has strict call-order rules.
- Iterator behavior differs for concurrent collections.

#### Optional Anki

Q: What are the core iterator methods?
A: `hasNext()`, `next()` and optional `remove()`.

</details>

<a id="col-iter-002"></a>

<details>
<summary><strong>🧠 COL-ITER-002. How does the enhanced `for` loop use `Iterable`?</strong></summary>

#### Short answer

The enhanced `for` loop calls `iterator()` on an `Iterable` and repeatedly uses the returned iterator.

#### Interview answer

Any type implementing `Iterable<T>` can be used in `for (T item : items)`. The compiler translates that loop into iterator-based traversal. Arrays are handled specially by the language.

#### Deep dive

Enhanced `for` is clean for read-only traversal, but it does not expose the iterator variable. If you need to call `iterator.remove()`, use an explicit iterator.

#### Production angle

Enhanced `for` keeps service code readable, but avoid modifying the underlying collection inside the loop unless the collection explicitly supports that pattern.

#### Traps / caveats

- Removing with `collection.remove()` inside enhanced `for` can fail.
- `Iterable` does not imply reusable traversal for every custom type.
- Iteration order depends on implementation.

#### Optional Anki

Q: What method enables enhanced `for`?
A: `Iterable.iterator()`.

</details>

<a id="col-iter-003"></a>

<details>
<summary><strong>COL-ITER-003. What is structural modification?</strong></summary>

#### Short answer

Structural modification is a change that adds, removes or otherwise changes the collection's structure, not merely replacing an existing value.

#### Interview answer

For lists, adding or removing elements is structural because it changes size and traversal structure. Setting an existing list element is usually not structural. For maps, adding or removing mappings is structural; changing the value for an existing key may not be.

#### Deep dive

Fail-fast iterators use structural modification tracking to detect that a collection was changed unexpectedly during iteration. Exact definitions can vary by implementation.

#### Production angle

Understanding structural modification helps debug `ConcurrentModificationException` and safe cleanup logic.

#### Traps / caveats

- Value replacement is not always structural.
- Structural modification can happen in one thread.
- View collections can structurally modify their backing collection.

#### Optional Anki

Q: Is `list.add(x)` structural?
A: Yes.

</details>

<a id="col-iter-004"></a>

<details>
<summary><strong>COL-ITER-004. What is fail-fast behavior, and is it guaranteed?</strong></summary>

#### Short answer

Fail-fast iterators try to throw `ConcurrentModificationException` when they detect unexpected structural modification, but detection is best-effort.

#### Interview answer

Many non-concurrent collections track a modification count. An iterator remembers the expected count and checks it during traversal. If the collection is structurally changed outside the iterator, the iterator may throw `ConcurrentModificationException`.

#### Deep dive

Fail-fast is a bug-detection feature, not a correctness guarantee. The JVM and implementation do not promise to detect every race or every illegal modification. Correct code must not depend on the exception being thrown.

#### Production angle

Treat fail-fast exceptions as symptoms of unsafe iteration or unclear ownership. Fix the mutation pattern instead of catching and ignoring the exception.

#### Traps / caveats

- It is best-effort.
- It does not mean the collection is thread-safe.
- It can happen without multiple threads.

#### Optional Anki

Q: Is fail-fast behavior guaranteed?
A: No. It is best-effort.

</details>

<a id="col-iter-005"></a>

<details>
<summary><strong>COL-ITER-005. What is `ConcurrentModificationException`, and does it always mean multiple threads are involved?</strong></summary>

#### Short answer

It signals that a collection was structurally modified during iteration in an unsupported way; it can happen in a single thread.

#### Interview answer

Despite the name, `ConcurrentModificationException` often comes from code like removing from an `ArrayList` inside an enhanced `for` loop. It means the iterator detected modification outside its allowed path.

#### Deep dive

The exception is common with list filtering, map cleanup and nested methods that mutate a collection being iterated by the caller. Concurrent threads can also trigger it, but the core issue is unsupported structural modification during traversal.

#### Production angle

In incidents, inspect stack traces and ownership. Find who is iterating and who is mutating. Avoid broad catch blocks around it.

#### Traps / caveats

- It is not a synchronization tool.
- Catch-and-retry can hide data races.
- Concurrent collections usually have different iterator semantics.

#### Optional Anki

Q: Can `ConcurrentModificationException` happen in one thread?
A: Yes.

</details>

<a id="col-iter-006"></a>

<details>
<summary><strong>COL-ITER-006. How do you correctly remove elements during iteration?</strong></summary>

#### Short answer

Use `Iterator.remove()`, `removeIf()`, collect into a new collection, or use a collection that explicitly supports the concurrent mutation pattern.

#### Interview answer

For ordinary mutable collections, explicit iterator removal is safe after `next()`. For simple predicates, `collection.removeIf(predicate)` is usually clearer. For transformations, building a new collection often avoids side effects.

#### Deep dive

For maps, iterate `entrySet()` and use the iterator's `remove()`, or use supported view operations. For concurrent maps, use their atomic operations or weakly consistent iteration semantics intentionally.

#### Production angle

Prefer clear mutation boundaries. Filtering a list in place can surprise callers if the list is shared.

#### Traps / caveats

- `Iterator.remove()` can be called only once per `next()`.
- `removeIf()` mutates the collection.
- Unmodifiable collections reject removal.

#### Optional Anki

Q: Cleanest simple in-place filter?
A: `removeIf(predicate)`.

</details>

<a id="col-iter-007"></a>

<details>
<summary><strong>COL-ITER-007. What is the difference between `collection.remove`, `iterator.remove` and `removeIf`?</strong></summary>

#### Short answer

`collection.remove` mutates directly, `iterator.remove` removes the current iterator element safely, and `removeIf` removes all elements matching a predicate.

#### Interview answer

During fail-fast iteration, `collection.remove(x)` can invalidate the iterator. `iterator.remove()` updates the iterator's expected state and removes the last returned element. `removeIf()` is a collection-level bulk operation intended for predicate-based removal.

#### Deep dive

`removeIf()` is usually clearer than manual iterator code for simple conditions. Manual iterator code is useful when removal depends on traversal state that is awkward to express as a predicate.

#### Production angle

Use the simplest operation that makes mutation explicit. For shared collections, consider copying first.

#### Traps / caveats

- `removeIf()` may throw on unmodifiable collections.
- `collection.remove()` removes by equality, not by index.
- `List.remove(int)` and `List.remove(Object)` overloads can confuse boxed integers.

#### Optional Anki

Q: Which removal is safe during explicit iteration?
A: `iterator.remove()`.

</details>

<a id="col-iter-008"></a>

<details>
<summary><strong>COL-ITER-008. How do concurrent collections behave during iteration?</strong></summary>

#### Short answer

Many concurrent collections use weakly consistent or snapshot iterators instead of fail-fast iterators.

#### Interview answer

`ConcurrentHashMap` iterators are weakly consistent: they do not throw `ConcurrentModificationException` and may reflect some concurrent updates. `CopyOnWriteArrayList` iterators are snapshot-based: they traverse the array state from iterator creation time.

#### Deep dive

This is a trade-off. Concurrent iteration avoids crashing under concurrent updates, but it may not show a perfectly current view. If the operation requires a consistent point-in-time snapshot, create one explicitly or use locking.

#### Production angle

Good enough for metrics, cleanup scans or best-effort observation may be wrong for financial or security invariants.

#### Traps / caveats

- No exception does not mean a consistent snapshot.
- Weakly consistent iterators may miss or include concurrent changes.
- Snapshot iterators can be stale.

#### Optional Anki

Q: Do `ConcurrentHashMap` iterators fail fast?
A: No. They are weakly consistent.

</details>

<a id="col-iter-009"></a>

<details>
<summary><strong>🧠 COL-ITER-009. What are weakly consistent iterators and snapshot iterators?</strong></summary>

#### Short answer

Weakly consistent iterators tolerate concurrent changes and may reflect some of them; snapshot iterators traverse a fixed copy or array state.

#### Interview answer

Weakly consistent iteration is used by collections such as `ConcurrentHashMap`. It avoids fail-fast exceptions but does not promise to show every update. Snapshot iteration is used by copy-on-write collections, where the iterator sees the state that existed when it was created.

#### Deep dive

Weak consistency favors scalability and progress. Snapshot iteration favors stable traversal but can be stale and expensive on writes because snapshots or copied arrays must be maintained.

#### Production angle

Choose based on correctness requirements. Monitoring can often tolerate weak consistency; billing calculations usually cannot.

#### Traps / caveats

- Weakly consistent does not mean eventually complete.
- Snapshot does not mean live.
- Both can surprise code expecting fail-fast behavior.

#### Optional Anki

Q: Which iterator sees old state in `CopyOnWriteArrayList`?
A: A snapshot iterator.

</details>

<a id="col-iter-010"></a>

<details>
<summary><strong>COL-ITER-010. What can go wrong if you expose a mutable collection from an object?</strong></summary>

#### Short answer

Callers can modify internal state, break invariants, create races or observe changes the owner did not intend to expose.

#### Interview answer

Returning an internal `List` field gives the caller direct access to mutate it. That can bypass validation and make the owning object inconsistent. Passing internal mutable collections across layers also makes ownership unclear.

#### Deep dive

This is representation exposure. Protect against it with immutable copies, defensive copies, unmodifiable views when appropriate, or methods that expose behavior rather than raw storage.

#### Production angle

Common symptoms are DTOs changing after validation, cached objects being mutated by callers and shared state bugs in singleton services.

#### Traps / caveats

- `final List` does not make the list immutable.
- Unmodifiable views can still reflect backing changes.
- Deep copying may be needed if elements are mutable.

#### Optional Anki

Q: What is representation exposure?
A: Leaking internal mutable state to callers.

</details>

<a id="col-iter-011"></a>

<details>
<summary><strong>COL-ITER-011. How would you safely iterate and update a collection in a multi-threaded service?</strong></summary>

#### Short answer

Use one clear strategy: confinement, locking, concurrent collections, immutable snapshots or copy-on-write, depending on correctness and performance requirements.

#### Interview answer

If all access is inside one thread, no shared concurrency problem exists. If shared state is required, synchronize around the whole invariant, use a concurrent collection with atomic methods, or publish immutable snapshots. For read-mostly lists, copy-on-write can be appropriate.

#### Deep dive

The key is whether you need a consistent snapshot or just safe progress. A `ConcurrentHashMap` scan is not a transaction. If updates must be coordinated with other fields, external locking or immutable state replacement may be required.

#### Production angle

Document ownership and thread-safety policy. Add tests for concurrent access only after the design is clear.

#### Traps / caveats

- A synchronized collection still needs manual synchronization during iteration.
- Concurrent collections do not protect multi-field invariants.
- Copying huge collections on every update can be expensive.

#### Optional Anki

Q: What should come first in shared collection design?
A: A clear ownership and concurrency policy.

</details>

<a id="col-order-001"></a>

<details>
<summary><strong>COL-ORDER-001. What is the difference between `Comparable` and `Comparator`?</strong></summary>

#### Short answer

`Comparable` defines a type's natural ordering; `Comparator` defines an external ordering strategy.

#### Interview answer

A class implements `Comparable<T>` when it has one obvious natural order, such as numbers or dates. A `Comparator<T>` is supplied when different orderings are needed, such as sorting users by name, age or creation time.

#### Deep dive

`Comparable` implements `compareTo`. `Comparator` implements `compare` and can be composed with helpers such as `comparing`, `thenComparing`, `reversed`, `nullsFirst` and `nullsLast`.

#### Production angle

Use comparators for service-specific sorting to avoid baking one business view into the domain class.

#### Traps / caveats

- Comparison must be transitive and stable for sorted collections.
- Natural ordering should be documented.
- Comparator equality semantics affect `TreeSet` and `TreeMap`.

#### Optional Anki

Q: Natural ordering interface?
A: `Comparable`.

</details>

<a id="col-order-002"></a>

<details>
<summary><strong>COL-ORDER-002. What does it mean for a comparator to be consistent with `equals()`?</strong></summary>

#### Short answer

It means `compare(a, b) == 0` exactly when `a.equals(b)` is true.

#### Interview answer

Consistency with `equals()` matters because sorted sets and maps treat comparison result zero as equality for storage. If the comparator says two objects compare equal but `equals()` says they differ, a `TreeSet` may keep only one of them.

#### Deep dive

Inconsistent comparators can be intentional, for example deduplicating by a business key. But then the collection is enforcing comparator-based uniqueness, not object equality.

#### Production angle

Always ask whether a comparator is for display order or uniqueness. If it is for display, add tie-breakers to avoid accidental drops in sorted collections.

#### Traps / caveats

- `Comparator.comparing(User::email)` deduplicates by email in `TreeSet`.
- BigDecimal natural ordering and equality differ.
- Inconsistency should be documented if intentional.

#### Optional Anki

Q: What does `compare(a,b)==0` mean in `TreeSet`?
A: The set treats the elements as the same.

</details>

<a id="col-order-003"></a>

<details>
<summary><strong>COL-ORDER-003. What can happen if a comparator violates transitivity?</strong></summary>

#### Short answer

Sorting and sorted collections can behave unpredictably, including wrong order, lost elements or runtime exceptions.

#### Interview answer

Transitivity means if `a` is before `b` and `b` is before `c`, then `a` should be before `c`. If a comparator breaks that rule, sorting algorithms and tree structures cannot reason consistently about element order.

#### Deep dive

Common causes include subtraction-based integer comparison that overflows, inconsistent null handling, comparing mutable fields and comparators that depend on external changing state.

#### Production angle

Comparator bugs can appear only with certain data combinations. Test edge cases: equal fields, nulls, extreme numbers, reversed sort and tie-breakers.

#### Traps / caveats

- Avoid `a - b` for integer comparison.
- Do not depend on current time or mutable external state.
- Broken comparator effects can be intermittent.

#### Optional Anki

Q: Safe integer comparison helper?
A: `Integer.compare(a, b)`.

</details>

<a id="col-order-004"></a>

<details>
<summary><strong>🧠 COL-ORDER-004. How do `List.sort` and `Collections.sort` work?</strong></summary>

#### Short answer

Both sort lists in place; `Collections.sort` delegates to list sorting in modern Java.

#### Interview answer

`List.sort(comparator)` is the instance method. `Collections.sort(list, comparator)` is the older utility method. If the comparator is null, natural ordering is used. Sorting mutates the list unless you first copy it.

#### Deep dive

Java's object list sorting is stable, so equal elements keep their relative order. The exact algorithm is an implementation detail, but stability is important for multi-pass sorting and predictable output.

#### Production angle

Be careful when sorting lists passed into a method. You may be mutating caller-owned data. If not intended, copy first.

#### Traps / caveats

- The list must be modifiable.
- Elements must be comparable if no comparator is supplied.
- Sorting huge lists in memory can hurt latency and memory.

#### Optional Anki

Q: Does `List.sort` mutate the list?
A: Yes.

</details>

<a id="col-order-005"></a>

<details>
<summary><strong>COL-ORDER-005. How do you handle nulls and multiple fields in comparators?</strong></summary>

#### Short answer

Use comparator helpers such as `nullsFirst`, `nullsLast`, `comparing` and `thenComparing`.

#### Interview answer

For multiple fields, compose comparators: compare primary field first, then tie-breakers with `thenComparing`. For nullable fields, wrap the field comparator with `Comparator.nullsFirst(...)` or `Comparator.nullsLast(...)`.

#### Deep dive

Example: `Comparator.comparing(User::lastName, Comparator.nullsLast(String::compareTo)).thenComparing(User::id)`. Tie-breakers are important when sorted collections use the comparator for uniqueness.

#### Production angle

Null ordering must match product expectations and database ordering if results are combined or compared with SQL output.

#### Traps / caveats

- `Comparator.comparing(User::name)` throws if name is null.
- Missing tie-breakers can collapse keys in `TreeSet`.
- Reversed null handling can be surprising if applied at the wrong level.

#### Optional Anki

Q: Comparator helper for nullable values?
A: `Comparator.nullsFirst` or `Comparator.nullsLast`.

</details>

<a id="col-order-006"></a>

<details>
<summary><strong>COL-ORDER-006. Why can `TreeSet` or `TreeMap` keep only one of two unequal objects if comparison returns zero?</strong></summary>

#### Short answer

Because sorted sets and maps use comparison result zero as the uniqueness rule.

#### Interview answer

If a comparator compares users only by email, then two user objects with the same email compare as zero. A `TreeSet` will treat them as duplicates, and a `TreeMap` will treat their keys as the same key, even if `equals()` compares IDs and says they differ.

#### Deep dive

This behavior is not a bug in `TreeSet`; it follows the sorted collection contract. The bug is usually using a display comparator as a uniqueness comparator without realizing it.

#### Production angle

This can drop data during deduplication or report generation. Add tie-breakers or use a different collection if duplicates by that comparator are allowed.

#### Traps / caveats

- `compare()==0` is not just "same sort position" in sorted maps/sets.
- `equals()` is not consulted for `TreeMap` key uniqueness.
- Inconsistency may be intentional but must be documented.

#### Optional Anki

Q: What defines duplicate keys in `TreeMap`?
A: Key comparison returning zero.

</details>

<a id="col-order-007"></a>

<details>
<summary><strong>🧠 COL-ORDER-007. What is stable sorting, and when does it matter?</strong></summary>

#### Short answer

Stable sorting preserves the original relative order of elements that compare equal.

#### Interview answer

If two elements compare equal under the current comparator, a stable sort keeps them in the same relative order they had before sorting. This matters when sorting by one field after data is already ordered by another field.

#### Deep dive

Stable sorting enables multi-pass sorting, although composing a single comparator with `thenComparing` is usually clearer. It also helps keep output deterministic when equal keys appear.

#### Production angle

Stable sorting affects pagination, reports and user-visible lists. If equal elements appear to jump around between requests, clients may see confusing output.

#### Traps / caveats

- Stability only applies to elements that compare equal.
- It does not make an unstable data source deterministic.
- A missing tie-breaker can still make pagination inconsistent.

#### Optional Anki

Q: What does stable sort preserve?
A: Relative order of elements that compare equal.

</details>

<a id="col-order-008"></a>

<details>
<summary><strong>COL-ORDER-008. How would you sort without mutating the original collection?</strong></summary>

#### Short answer

Create a copy and sort the copy, or stream into a new sorted result.

#### Interview answer

For a list, use `var copy = new ArrayList<>(original); copy.sort(comparator);`. With streams, use `original.stream().sorted(comparator).toList()`, understanding the mutability of the result. The original collection remains unchanged.

#### Deep dive

Copying is shallow: elements are the same objects unless you explicitly deep-copy them. If elements are mutable and later changed, both collections observe those object changes.

#### Production angle

Avoid mutating caller-owned collections unless the method contract clearly says it does. Sorting in place can create subtle bugs in shared DTOs or cached values.

#### Traps / caveats

- `stream().sorted()` still buffers data.
- `Stream.toList()` is Java 16+ and returns an unmodifiable list.
- Shallow copies do not protect mutable elements.

#### Optional Anki

Q: Simple non-mutating sort pattern?
A: Copy the list, then sort the copy.

</details>

<a id="col-order-009"></a>

<details>
<summary><strong>COL-ORDER-009. What are common comparator bugs in Java backend code?</strong></summary>

#### Short answer

Common bugs include integer overflow, null mishandling, missing tie-breakers, mutable comparison fields, inconsistent equality and reversed-order mistakes.

#### Interview answer

Avoid `a - b` for numeric comparison because it can overflow. Decide null ordering explicitly. Add tie-breakers for deterministic output. Do not use comparators that depend on mutable or external changing state. Be careful when using the comparator in `TreeSet` or `TreeMap`, because it controls uniqueness.

#### Deep dive

Comparator bugs often pass small tests and fail with edge-case production data: duplicate names, null timestamps, large IDs or equal priorities. Sorting and pagination should be tested together.

#### Production angle

Bad comparators can break reports, API ordering, cache keys and deduplication. They can also create inconsistent pagination where records move between pages.

#### Traps / caveats

- Comparator for display order may be wrong for set uniqueness.
- Database and Java null ordering may differ.
- Time-dependent comparators are unsafe.

#### Optional Anki

Q: Why avoid `a - b` in comparators?
A: It can overflow and violate comparator rules.

</details>
