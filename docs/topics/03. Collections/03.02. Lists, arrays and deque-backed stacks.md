# 03.02. Lists, arrays and deque-backed stacks

---

<a id="col-list-001"></a>

<details>
<summary><strong>COL-LIST-001. What is a `List`?</strong></summary>

#### Short answer

A `List` is an ordered collection that allows duplicates and provides positional access by index.

#### Interview answer

`List<E>` represents a sequence of elements. It preserves element order, supports duplicates, and exposes operations such as `get(index)`, `set(index, value)`, indexed insertion and removal. Common implementations are `ArrayList`, `LinkedList`, immutable factory lists and `CopyOnWriteArrayList`.

#### Deep dive

The `List` contract is about sequence semantics, not about storage. An `ArrayList` stores references in an array, while `LinkedList` stores nodes. Both are lists, but their performance and memory behavior differ sharply.

`List` equality is order-sensitive: two lists are equal only if they contain equal elements in the same positions.

#### Production angle

Use `List` when order and possible duplicates matter, such as ordered API responses, validation errors, batch items or ordered steps. Do not use it for repeated key lookup if a `Map` would express the intent better.

#### Traps / caveats

- `List` does not imply mutability.
- Index operations can be expensive for some implementations.
- Order is insertion or positional order, not necessarily sorted order.

#### Optional Anki

Q: What are the main `List` guarantees?
A: Positional order, duplicate elements and index-based operations.

</details>

<a id="col-list-002"></a>

<details>
<summary><strong>COL-LIST-002. What is the difference between `List`, `ArrayList` and `LinkedList`?</strong></summary>

#### Short answer

`List` is the interface; `ArrayList` is an array-backed implementation; `LinkedList` is a node-backed implementation.

#### Interview answer

`List` defines sequence behavior. `ArrayList` stores elements in a resizable array, so random access is fast and iteration has good memory locality. `LinkedList` stores elements as linked nodes, so it has higher memory overhead and poor random access, but can add or remove efficiently at known node positions or at deque ends.

#### Deep dive

The common oversimplification is "`LinkedList` is faster for inserts." It is only fast if you already have the position through an iterator or you operate at the ends. Finding a middle index is still `O(n)`, and node allocation plus pointer chasing can dominate.

#### Production angle

If code receives `List` but depends on random access, consider checking for `RandomAccess` or copying to `ArrayList` in hot paths. Avoid exposing `LinkedList` as an implementation detail unless it is genuinely needed.

#### Traps / caveats

- `List` does not tell you complexity.
- `LinkedList.get(i)` is `O(n)`.
- `ArrayList` middle insertions shift elements.

#### Optional Anki

Q: `List` vs `ArrayList`?
A: `List` is the contract; `ArrayList` is a resizable-array implementation.

</details>

<a id="col-list-003"></a>

<details>
<summary><strong>COL-LIST-003. How does `ArrayList` work under the hood?</strong></summary>

#### Short answer

`ArrayList` stores elements in an internal object array and grows that array when more capacity is needed.

#### Interview answer

An `ArrayList` has a size and a backing array capacity. `get(index)` reads from the array, so it is fast. Appending is usually cheap until the backing array fills. When capacity is exhausted, a larger array is allocated and existing references are copied.

#### Deep dive

The list stores object references, not objects inline. Removing from the middle shifts later references left. Adding into the middle shifts later references right. Removing also clears obsolete array slots so objects can be garbage-collected.

Growth policy is an implementation detail, so answers should avoid relying on exact formulas unless the question is explicitly version-specific.

#### Production angle

`ArrayList` is excellent for building result lists and iterating them. In hot paths with known sizes, pre-sizing can reduce repeated allocations and copy spikes.

#### Traps / caveats

- Capacity is not the same as size.
- Large growth copies can cause latency spikes.
- It is not thread-safe for concurrent mutation.

#### Optional Anki

Q: Why is `ArrayList.get(i)` fast?
A: It reads directly from an internal array by index.

</details>

<a id="col-list-004"></a>

<details>
<summary><strong>🧠 COL-LIST-004. How does `LinkedList` work under the hood?</strong></summary>

#### Short answer

`LinkedList` stores each element in a node that points to the previous and next nodes.

#### Interview answer

Java's `LinkedList` is a doubly linked list. It can add and remove at the head or tail efficiently, and it can remove through an iterator efficiently once the iterator is positioned. But index-based access requires walking nodes from the head or tail.

#### Deep dive

Each node has object overhead plus references to the item, previous node and next node. That makes memory use much higher than an array-backed list. Traversal jumps between objects in memory, which is usually worse for CPU cache locality than scanning an array.

`LinkedList` also implements `Deque`, but `ArrayDeque` is often better for stack and queue operations.

#### Production angle

Use `LinkedList` only when its semantics genuinely fit. In many backend services it is chosen because of a theoretical insert/remove advantage that does not appear in real profiling.

#### Traps / caveats

- It has poor random access.
- It allocates a node per element.
- It is not thread-safe by default.

#### Optional Anki

Q: What is the main cost of `LinkedList`?
A: Node allocation, pointer chasing and `O(n)` indexed access.

</details>

<a id="col-list-005"></a>

<details>
<summary><strong>COL-LIST-005. When should you use `ArrayList`, and when should you avoid it?</strong></summary>

#### Short answer

Use `ArrayList` for most mutable ordered data. Avoid it when frequent middle insert/remove, thread-safe mutation, bounded queue semantics or very large unbounded accumulation are required.

#### Interview answer

`ArrayList` is a good default when you append, iterate, sort, map or access by index. It is compact and cache-friendly. It is weaker when many operations insert or remove near the beginning or middle, because shifting is required.

#### Deep dive

For stack/queue ends, `ArrayDeque` is often better. For uniqueness, use `Set`. For lookup by key, use `Map`. For concurrent reads and writes, use synchronization, immutable snapshots or a concurrent structure depending on the use case.

#### Production angle

The main production risk is accidentally collecting too much into memory: huge database results, massive API responses, or unbounded per-request lists. The fix is often pagination, streaming or pushing work to SQL.

#### Traps / caveats

- `ArrayList` is not synchronized.
- Removing many elements one by one can be expensive.
- Holding a large list also holds references to all its elements.

#### Optional Anki

Q: When is `ArrayList` usually right?
A: Ordered mutable data with appends, iteration and random access.

</details>

<a id="col-list-006"></a>

<details>
<summary><strong>COL-LIST-006. Why is `LinkedList` often a bad default choice in modern Java applications?</strong></summary>

#### Short answer

Because its theoretical insertion advantages often disappear due to traversal cost, memory overhead and poor cache locality.

#### Interview answer

`LinkedList` looks attractive because node insertion can be `O(1)`, but you usually must first find the insertion point, which is `O(n)` for indexed access. Every element also needs a node object with extra references. `ArrayList` is usually faster for iteration and random access because data references are stored contiguously.

#### Deep dive

Modern CPUs reward sequential memory access. `LinkedList` traversal follows pointers across heap objects, causing cache misses. Garbage collection also has more objects to track. Unless you are doing many iterator-positioned insertions/removals, `LinkedList` is often slower and larger.

#### Production angle

In code review, challenge `LinkedList` unless the author can explain the access pattern and has measured it. For queues and stacks, prefer `ArrayDeque`.

#### Traps / caveats

- Big-O hides constants and memory locality.
- `LinkedList` is not a low-memory structure.
- It is rarely better for ordinary service-layer lists.

#### Optional Anki

Q: Why can `LinkedList` be slower than `ArrayList`?
A: Pointer chasing, node allocation and `O(n)` traversal.

</details>

<a id="col-list-007"></a>

<details>
<summary><strong>COL-LIST-007. What are the time complexity trade-offs of `ArrayList` and `LinkedList`?</strong></summary>

#### Short answer

`ArrayList` has fast random access and amortized fast append; `LinkedList` has fast end operations but slow indexed access.

#### Interview answer

For `ArrayList`, `get` and `set` are `O(1)`, append is amortized `O(1)`, and insert/remove in the middle is `O(n)` because elements shift. For `LinkedList`, add/remove at head or tail is `O(1)`, iterator-positioned removal is `O(1)`, but `get(index)` and index-based insert/remove are `O(n)`.

#### Deep dive

Complexity does not include memory locality, allocation rate or GC cost. `ArrayList` may occasionally pay a resize cost. `LinkedList` pays steady overhead for node objects and pointer traversal.

#### Production angle

When performance matters, measure the actual pattern. A list used for `contains` in a loop may need a `Set` or `Map`, not a different list implementation.

#### Traps / caveats

- Amortized `O(1)` append can still have occasional slow copies.
- `LinkedList` index access is not constant time.
- `contains` is `O(n)` for both.

#### Optional Anki

Q: What is `ArrayList` append complexity?
A: Amortized `O(1)`, with occasional resize cost.

</details>

<details>
<summary><strong>🧠 COL-LIST-008. How do `ArrayList` capacity, growth, pre-sizing and trimming work?</strong></summary>

#### Short answer

Size is the number of elements; capacity is the backing array length. `ArrayList` grows by allocating a larger array and copying references. Pre-sizing can reduce growth, and trimming can release unused capacity.

#### Interview answer

When an `ArrayList` needs more space, it allocates a new backing array and copies existing references. If you know roughly how many elements you will add, using the constructor with expected capacity or `ensureCapacity()` can reduce repeated reallocations. `trimToSize()` can shrink excess capacity after a large temporary buildup.

#### Deep dive

Pre-sizing is useful for large, known batches. It is not worth cluttering ordinary small code. Trimming is also situational: it can save memory, but it may cost a copy and can hurt if the list grows again soon.

#### Production angle

In hot request paths or batch jobs, repeated resizing can create latency spikes and allocation pressure. For massive lists, rethink whether all data should be in memory at once.

#### Traps / caveats

- `new ArrayList<>(1000)` sets capacity, not size.
- Exact growth rules are implementation details.
- Trimming every time can make performance worse.

#### Optional Anki

Q: Size vs capacity in `ArrayList`?
A: Size is element count; capacity is backing array space.

</details>

<details>
<summary><strong>COL-LIST-009. What is the difference between `Arrays.asList`, `List.of`, `List.copyOf` and `new ArrayList<>()`?</strong></summary>

#### Short answer

`Arrays.asList` is a fixed-size array-backed list; `List.of` creates an unmodifiable list; `List.copyOf` creates an unmodifiable copy; `new ArrayList<>()` creates a mutable list.

#### Interview answer

Use `new ArrayList<>(source)` when you need mutable independent storage. Use `List.of(...)` for small fixed unmodifiable lists. Use `List.copyOf(source)` when you want an unmodifiable snapshot. `Arrays.asList(array)` is backed by the original array, so element replacement is reflected both ways, but add/remove are unsupported.

#### Deep dive

Null handling differs. `List.of` and `List.copyOf` reject null elements. `Arrays.asList` can contain null if the array contains null. `List.copyOf` may reuse the input if it is already an unmodifiable suitable collection.

#### Production angle

A common bug is passing `Arrays.asList()` or `List.of()` into code that tries to add elements. Another is assuming `Arrays.asList()` copied the array.

#### Traps / caveats

- `Arrays.asList(int[])` produces `List<int[]>`, not `List<Integer>`.
- `List.of()` is unmodifiable.
- `List.copyOf()` is shallow, not deep.

#### Optional Anki

Q: Which creates a mutable copy?
A: `new ArrayList<>(source)`.

</details>

<a id="col-list-010"></a>

<details>
<summary><strong>COL-LIST-010. Why are `Vector` and `Stack` poor defaults, and what should be used instead?</strong></summary>

#### Short answer

They are legacy synchronized classes with awkward semantics; use `ArrayList`, `ArrayDeque` or proper concurrent structures instead.

#### Interview answer

`Vector` is like an older synchronized `ArrayList`, but method-level synchronization is rarely the right concurrency model. `Stack` extends `Vector`, which exposes list operations that do not fit a strict stack abstraction. For normal lists use `ArrayList`; for LIFO stack behavior use `ArrayDeque`; for shared concurrent access choose a concurrent collection or external synchronization deliberately.

#### Deep dive

The problem is not only performance. Coarse synchronized methods do not make multi-step workflows atomic. For example, checking size and then popping still needs a consistent synchronization strategy.

#### Production angle

Legacy APIs may still return these types. In new code, prefer modern alternatives and document concurrency semantics explicitly.

#### Traps / caveats

- Synchronized methods do not solve compound races.
- `Stack` exposes inherited methods that break stack-only intent.
- `ArrayDeque` is not thread-safe either.

#### Optional Anki

Q: Preferred replacement for `Stack`?
A: `Deque`, usually `ArrayDeque`.

</details>

<a id="col-list-011"></a>

<details>
<summary><strong>COL-LIST-011. When should you use `ArrayDeque` for stack-like or queue-like behavior?</strong></summary>

#### Short answer

Use `ArrayDeque` for fast non-thread-safe LIFO or FIFO operations at both ends.

#### Interview answer

`ArrayDeque` implements `Deque` with a resizable array. It is usually faster and more memory-efficient than `LinkedList` for stack and queue use in a single thread. For stack behavior use `push`, `pop` and `peek`; for queue behavior use `offer`, `poll` and `peek`.

#### Deep dive

It does not support indexed access and does not permit null elements. Null is reserved by many queue methods as a signal that no element exists, for example `poll()` returning null.

#### Production angle

Good uses include local algorithms, parsing, breadth-first traversal queues and temporary stacks. For cross-thread producer-consumer designs, use `BlockingQueue` or another concurrent structure instead.

#### Traps / caveats

- It is not thread-safe.
- It does not allow null elements.
- It is not a `List`.

#### Optional Anki

Q: Why prefer `ArrayDeque` over `Stack`?
A: It is modern, faster for typical use and avoids legacy `Vector` inheritance.

</details>

<a id="col-list-012"></a>

<details>
<summary><strong>COL-LIST-012. What are the traps of `List.subList()`?</strong></summary>

#### Short answer

`subList()` returns a view backed by the original list, not an independent copy.

#### Interview answer

Changes through the sublist write through to the original list, and changes to the original list can invalidate the sublist. This is useful for range operations, but surprising when code expects an independent list.

#### Deep dive

For example, `list.subList(0, 10).clear()` removes the first ten elements from the original list. If the original list is structurally modified outside the sublist, later operations on the sublist can throw `ConcurrentModificationException`.

Create `new ArrayList<>(list.subList(from, to))` if you need a detached copy.

#### Production angle

Sublist views can accidentally retain a reference to a much larger backing list, depending on implementation. That can keep more memory alive than expected.

#### Traps / caveats

- It is a backed view.
- Structural changes outside the view can break it.
- Copy it when returning across API boundaries.

#### Optional Anki

Q: Does `subList()` copy elements?
A: No. It returns a view backed by the original list.

</details>

<a id="col-list-013"></a>

<details>
<summary><strong>🧠 COL-LIST-013. How do memory locality and CPU cache behavior affect `ArrayList` and `LinkedList` performance?</strong></summary>

#### Short answer

`ArrayList` usually has better locality because references are stored in a contiguous array; `LinkedList` spreads nodes across the heap.

#### Interview answer

Modern CPUs are fast when scanning nearby memory. `ArrayList` iteration reads adjacent references from an array, which is cache-friendly. `LinkedList` traversal follows pointers from node to node, often jumping around the heap and causing cache misses.

#### Deep dive

Both collections still store references to objects, not objects inline. But `LinkedList` adds a node object per element. That means more allocation, more pointers, more GC work and less predictable traversal.

#### Production angle

This is why real benchmarks often show `ArrayList` beating `LinkedList` even in cases where Big-O looks similar. For hot paths, measure with realistic data and JVM warmup.

#### Traps / caveats

- Big-O ignores memory locality.
- Small data sizes may hide differences.
- Object layout is JVM-specific, so avoid exact byte claims unless measured.

#### Optional Anki

Q: Which is usually more cache-friendly, `ArrayList` or `LinkedList`?
A: `ArrayList`.

</details>

<a id="col-list-014"></a>

<details>
<summary><strong>COL-LIST-014. What are common production mistakes with large `List`s?</strong></summary>

#### Short answer

Common mistakes are loading too much data, doing repeated linear scans, keeping references too long, sorting huge lists in memory and returning unbounded responses.

#### Interview answer

Large lists are simple but dangerous. They can cause high heap usage, long GC pauses, slow `contains` checks, expensive sorting and bad tail latency. A list that is fine in tests can fail when a query returns millions of rows.

#### Deep dive

Watch for nested loops over lists, `list.contains()` in a loop, collecting stream results just to iterate once, and converting database result sets into full in-memory objects. Often the fix is a `Set` or `Map` for lookup, database filtering, pagination, streaming or batch processing.

#### Production angle

Symptoms include `OutOfMemoryError`, rising old-gen usage, long GC pauses, slow endpoints and high allocation rate. Add limits to request sizes and response sizes.

#### Traps / caveats

- A `List` can hide an accidental in-memory database.
- Sorting and deduplication may belong in SQL.
- Returning all rows from an API is rarely safe.

#### Optional Anki

Q: What is a common fix for repeated list lookup by ID?
A: Build a `Map<ID, Value>` or `Set<ID>`.

</details>
