# Caching and advanced Hibernate features

<a id="jpa-cache-001"></a>

<details>
<summary><strong>🧠 JPA-CACHE-001. What is the second-level cache in Hibernate, and when should it be used or avoided?</strong></summary>

#### Short answer

The second-level cache stores entity data beyond one persistence context; use it for stable, frequently read data and avoid it for volatile or externally updated data.

#### Interview answer

The first-level cache is per persistence context. The second-level cache is shared at the session factory level and can store entity or collection data across transactions. It can reduce database reads for cache-friendly data.

It should be avoided for high-write tables, data updated by other services, tenant-sensitive data without careful keys, or queries where staleness is unacceptable.

#### Deep dive

Second-level cache is not automatically enabled for everything. It needs provider configuration, cache regions and concurrency strategy choices.

#### Production angle

Caching can improve latency but also introduce stale data, invalidation complexity and harder incident debugging.

#### Traps / caveats

- It does not fix poor query design.
- It can hide N+1 in tests.
- It is risky when multiple apps update the same tables.

#### Optional Anki

Q: What is the scope of Hibernate second-level cache?
A: Session factory / application-level, beyond one persistence context.

</details>

<a id="jpa-cache-002"></a>

<details>
<summary><strong>🧠 JPA-CACHE-002. What are cache regions, cache providers and cache concurrency strategies?</strong></summary>

#### Short answer

Regions partition cached data, providers implement storage, and concurrency strategies define consistency behavior for cached entities.

#### Interview answer

A cache region is a named area for entities, collections or query results. A cache provider is the actual cache implementation integrated with Hibernate. Concurrency strategies such as read-only, read-write and nonstrict read-write describe how Hibernate coordinates cached data with database changes.

The strategy should match data mutability and consistency requirements.

#### Deep dive

Read-only cache is appropriate for immutable reference data. Read-write provides stronger coordination but costs more. Nonstrict strategies trade consistency for speed.

#### Production angle

Wrong strategy choice can create stale reads or unnecessary cache overhead.

#### Traps / caveats

- Do not cache mutable high-write entities casually.
- Cache configuration must be monitored.
- Clustered caches add operational complexity.

#### Optional Anki

Q: What is a Hibernate cache region?
A: A named partition of cached data.

</details>

<a id="jpa-cache-003"></a>

<details>
<summary><strong>🧠 JPA-CACHE-003. Why is second-level cache risky when other applications update the same database?</strong></summary>

#### Short answer

Hibernate may not know about external updates, so cached entity data can become stale.

#### Interview answer

Hibernate invalidates or updates its cache when changes go through Hibernate in the same application/session factory. If another service, script or direct SQL update changes the table, this cache may not be invalidated automatically.

The application can then read old data from cache even though the database changed.

#### Deep dive

Solutions include avoiding second-level cache for externally updated tables, using short TTLs, explicit invalidation, event-driven cache eviction or making one service the data owner.

#### Production angle

Stale cache bugs are severe when they affect permissions, prices, feature flags, inventory or workflow state.

#### Traps / caveats

- Database truth does not automatically invalidate ORM cache.
- Cache TTL is not correctness unless staleness is acceptable.
- Multi-service writes require explicit ownership/invalidation design.

#### Optional Anki

Q: Why can external DB writes make Hibernate cache stale?
A: Hibernate does not automatically observe those writes.

</details>

<a id="jpa-cache-004"></a>

<details>
<summary><strong>🧠 JPA-CACHE-004. What is the difference between query cache and entity cache, and how does invalidation work conceptually?</strong></summary>

#### Short answer

Entity cache stores entity data by ID; query cache stores query result identifiers and depends on invalidation of affected tables/regions.

#### Interview answer

The second-level entity cache can return an entity by ID. The query cache stores the result of a query, often as IDs plus metadata, not a fully independent snapshot of all entity data. Those IDs may still require entity cache or database access.

When tables involved in cached queries change, cached query results must be invalidated or considered stale.

#### Deep dive

Query cache works best for stable, repeated queries with low write frequency. It can hurt performance if invalidated often.

#### Production angle

Query cache is easy to misuse for dynamic filters, high-cardinality parameters or frequently changing tables.

#### Traps / caveats

- Query cache is not the same as result DTO cache.
- It can add overhead with poor hit rate.
- Invalidation granularity may be broader than expected.

#### Optional Anki

Q: What does Hibernate query cache commonly store?
A: Query result identifiers/metadata, not a magic full read model.

</details>

<a id="jpa-cache-005"></a>

<details>
<summary><strong>JPA-CACHE-005. How do JPA/Hibernate caches compare to Redis or application-level response caches?</strong></summary>

#### Short answer

Hibernate caches are persistence-layer caches for entities/query results; Redis or response caches are application-level caches designed around use-case keys and invalidation rules.

#### Interview answer

Hibernate's first-level cache is a unit-of-work cache. The second-level cache stores mapped entity data. Redis can cache computed DTOs, API responses, permissions, counters or cross-service values with explicit keys, TTLs and invalidation.

The right cache depends on what is being reused and what consistency is required.

#### Deep dive

Entity cache keys are tied to ORM identity. Response cache keys should include tenant, user/permission context, locale, query params and version where needed.

#### Production angle

Application-level caches can be easier to reason about for read APIs because they cache the exact response shape.

#### Traps / caveats

- Do not cache sensitive data without tenant/user context.
- Do not use Redis to hide bad database modeling.
- Cache invalidation must match data ownership.

#### Optional Anki

Q: What does Hibernate first-level cache scope?
A: One persistence context/unit of work.

</details>

<a id="jpa-cache-006"></a>

<details>
<summary><strong>JPA-CACHE-006. What cache metrics would you monitor, and can cache solve N+1 queries?</strong></summary>

#### Short answer

Monitor hit/miss rate, evictions, size, latency and invalidations; cache may reduce repeated reads but does not fix bad fetch plans.

#### Interview answer

Useful metrics include hit ratio, miss count, put count, eviction count, memory usage, region size, query cache stats and cache provider latency. Also monitor database query counts because cache can hide but not remove inefficient access patterns.

Second-level cache can reduce some repeated entity loads, but it is not a proper N+1 solution. The query pattern is still wrong.

#### Deep dive

An endpoint doing 500 lazy loads may become faster when cache is warm, but cold cache and invalidations still suffer.

#### Production angle

Cache metrics should be tied to endpoint latency and database load, not viewed in isolation.

#### Traps / caveats

- High hit rate is not useful if stale data is unacceptable.
- Query cache with low hit rate can hurt performance.
- Cache does not reduce row/object graph size when data must be loaded.

#### Optional Anki

Q: Should second-level cache be the main fix for N+1?
A: No. Fix the fetch/query plan.

</details>

<details>
<summary><strong>🧠 JPA-ADV-001. What is Hibernate `StatelessSession`, and when might it help?</strong></summary>

#### Short answer

`StatelessSession` is a Hibernate API without a normal persistence context, useful for some bulk or streaming work where entity lifecycle features are unnecessary.

#### Interview answer

A `StatelessSession` does not provide first-level cache, dirty checking, transparent persistence context management or normal cascades. Operations are closer to direct row operations through Hibernate mapping.

It can help with large imports, exports or batch transformations where full ORM unit-of-work behavior would be too heavy.

#### Deep dive

Because it bypasses many Hibernate features, application code must handle associations, validation and consistency explicitly.

#### Production angle

It is a performance tool for specialized paths, not a replacement for normal JPA repositories.

#### Traps / caveats

- Hibernate-specific.
- No transparent dirty checking.
- No normal persistence-context identity guarantees.

#### Optional Anki

Q: What is missing from `StatelessSession`?
A: Normal first-level cache and dirty checking.

</details>

<a id="jpa-adv-002"></a>

<details>
<summary><strong>🧠 JPA-ADV-002. What inheritance strategies does JPA support, and what are their trade-offs?</strong></summary>

#### Short answer

JPA supports single table, joined and table-per-class inheritance, each trading simplicity, normalization and query cost differently.

#### Interview answer

`SINGLE_TABLE` stores a hierarchy in one table with a discriminator. It is fast to query but can have many nullable columns. `JOINED` normalizes subclass fields into separate tables but requires joins. `TABLE_PER_CLASS` stores each concrete class separately and can make polymorphic queries expensive.

Use inheritance mapping only when it truly matches the domain and query patterns.

#### Deep dive

Composition or explicit type fields are often simpler than JPA inheritance for backend systems.

#### Production angle

Inheritance mappings can make queries harder to tune and migrations harder to reason about.

#### Traps / caveats

- Do not model every polymorphism with JPA inheritance.
- `JOINED` can produce expensive joins.
- `SINGLE_TABLE` can weaken column constraints.

#### Optional Anki

Q: Which inheritance strategy uses one table and a discriminator?
A: `SINGLE_TABLE`.

</details>

<a id="jpa-adv-003"></a>

<details>
<summary><strong>JPA-ADV-003. How is `@MappedSuperclass` different from entity inheritance, and when should you avoid JPA inheritance?</strong></summary>

#### Short answer

`@MappedSuperclass` shares mapped fields but is not an entity; avoid JPA inheritance when polymorphic persistence adds query and schema complexity without clear value.

#### Interview answer

A mapped superclass contributes fields such as `id`, `createdAt` or `version` to subclasses, but it cannot be queried as an entity and has no table of its own. Entity inheritance models a polymorphic entity hierarchy.

Avoid JPA inheritance when simple composition, an enum type, separate tables or explicit relationships would be clearer.

#### Deep dive

Mapped superclass is useful for technical common fields. It should not become a dumping ground for unrelated domain behavior.

#### Production angle

Inheritance can complicate migrations, indexes, constraints and query plans.

#### Traps / caveats

- Mapped superclass is not polymorphic query support.
- Deep entity hierarchies are hard to maintain.
- Shared base fields still need consistent schema migration.

#### Optional Anki

Q: Can you query a `@MappedSuperclass` directly?
A: No.

</details>

<details>
<summary><strong>🧠 JPA-ADV-004. What are the risks of provider-specific annotations?</strong></summary>

#### Short answer

They can solve real problems but couple the code to Hibernate behavior, affecting portability, upgrades and team understanding.

#### Interview answer

Hibernate annotations such as `@BatchSize`, `@Formula`, filters or soft-delete features are often useful. The risk is that they are not portable JPA and may behave differently across Hibernate versions or dialects.

Use them deliberately, document why and cover them with integration tests.

#### Deep dive

Provider-specific annotations are acceptable in many Spring Boot systems because Hibernate is the chosen provider. The mistake is pretending they are standard JPA.

#### Production angle

Upgrade validation should include generated SQL, fetch behavior and mapping behavior for these features.

#### Traps / caveats

- Do not mix provider-specific behavior into generic libraries casually.
- Check behavior on the production database dialect.
- Avoid clever mappings that hide important SQL.

#### Optional Anki

Q: Main cost of Hibernate-specific annotations?
A: Provider coupling.

</details>

<a id="jpa-adv-005"></a>

<details>
<summary><strong>🧠 JPA-ADV-005. How would you implement soft delete with Hibernate, and what are the traps?</strong></summary>

#### Short answer

Soft delete marks rows as deleted instead of removing them; traps include hidden filters, uniqueness, cascades, queries and data retention.

#### Interview answer

Soft delete can be implemented with a `deleted` flag, custom SQL delete, Hibernate-specific soft delete support or filters/restrictions. All normal queries must exclude deleted rows where appropriate.

The hard part is not the flag. It is making uniqueness, foreign keys, indexes, admin queries, restores, cascades and reporting behave correctly.

#### Deep dive

Soft-deleted rows still exist, so unique constraints may need partial indexes or business-specific handling.

#### Production angle

Soft delete is often required for audit/recovery, but it increases query complexity and table growth.

#### Traps / caveats

- Deleted rows can still affect unique constraints.
- Hidden filters can surprise maintenance jobs.
- Cascading soft delete semantics must be explicit.

#### Optional Anki

Q: Why is soft delete more than a boolean flag?
A: Queries, constraints, indexes, cascades and retention rules must all account for it.

</details>

<details>
<summary><strong>🧠 JPA-ADV-006. How can Hibernate filters or SQL restrictions support tenant, security or visibility predicates?</strong></summary>

#### Short answer

They can automatically add predicates to entity queries, but correctness depends on reliable activation and database-level defense when needed.

#### Interview answer

Hibernate filters or SQL restrictions can apply conditions such as tenant ID, active flag or visibility state to entity loading. This can reduce repeated query predicates.

For security and multi-tenancy, application filters should not be the only line of defense if stronger isolation is required. Database constraints, row-level security or separate schemas may be needed.

#### Deep dive

Filters must be enabled with correct parameters for every relevant context. Connection/thread context leaks are dangerous.

#### Production angle

Tenant or permission filter failures can become cross-tenant data leaks.

#### Traps / caveats

- Do not trust client-provided tenant filters.
- Test background jobs and admin paths.
- Hidden predicates can affect query plans.

#### Optional Anki

Q: Main risk of tenant filters?
A: Missing or wrong activation can leak data.

</details>

<details>
<summary><strong>🧠 JPA-ADV-007. When would you use Envers or another auditing approach?</strong></summary>

#### Short answer

Use auditing when you need historical changes, accountability or compliance; choose the approach based on query needs, volume and correctness requirements.

#### Interview answer

Hibernate Envers can track revisions of audited entities. It is useful when the application needs to see who changed what and when, or reconstruct prior states. Alternatives include explicit audit tables, domain events, outbox records or event sourcing.

The right tool depends on whether audit is operational, legal, analytical or domain behavior.

#### Deep dive

Auditing every entity automatically can create large audit tables and performance overhead.

#### Production angle

Audit data needs retention, access control, PII handling, migration strategy and query performance planning.

#### Traps / caveats

- Audit logs should not silently fail if they are compliance-critical.
- Automatic auditing may miss business intent.
- Large audit tables may need partitioning or archiving.

#### Optional Anki

Q: What does Envers provide?
A: Hibernate-based entity revision auditing.

</details>

<details>
<summary><strong>🧠 JPA-ADV-008. What are entity listeners and lifecycle callbacks, and when are they risky?</strong></summary>

#### Short answer

They run code on entity lifecycle events such as persist, update or load; they are risky when they hide business logic or perform heavy side effects.

#### Interview answer

JPA supports callbacks such as `@PrePersist`, `@PreUpdate`, `@PostLoad` and entity listener classes. They are useful for technical concerns like timestamps or simple audit metadata.

They become risky when they call external services, perform complex queries, mutate unrelated entities or hide important business rules.

#### Deep dive

Callbacks run as part of persistence operations, so exceptions and side effects affect flush behavior.

#### Production angle

Hidden callback work can make a simple save unexpectedly slow or fragile.

#### Traps / caveats

- Keep callbacks small and deterministic.
- Avoid network calls from entity listeners.
- Be careful with dependency injection in listeners.

#### Optional Anki

Q: Good use for entity callbacks?
A: Simple technical metadata such as created/updated timestamps.

</details>
