# Performance, observability and senior scenarios

<a id="jpa-perf-001"></a>

<details>
<summary><strong>JPA-PERF-001. What are the most common Hibernate performance problems?</strong></summary>

#### Short answer

N+1 queries, over-fetching, slow pagination/counts, missing indexes, excessive flushing, large persistence contexts and connection pool pressure.

#### Interview answer

Most Hibernate performance issues are not caused by Hibernate being slow by itself. They come from poor query shape: too many queries, too many rows, too much object graph, bad pagination, inefficient generated SQL or long transactions.

The fix is usually better fetch plans, projections, indexes, batching, transaction boundaries and measurement.

#### Deep dive

Always check query count, row count, execution plan, connection usage and heap allocation before choosing an optimization.

#### Production angle

Hibernate issues commonly show up as high database CPU, slow endpoints, pool exhaustion and memory growth.

#### Traps / caveats

- Reducing query count can increase row count.
- Caching can hide bad query design.
- Local small data rarely reveals production behavior.

#### Optional Anki

Q: What are the top Hibernate performance smells?
A: N+1, over-fetching, slow queries/counts, large transactions and connection pool pressure.

</details>

<a id="jpa-perf-002"></a>

<details>
<summary><strong>JPA-PERF-002. How do you enable SQL logging safely without leaking sensitive data?</strong></summary>

#### Short answer

Log SQL shape in lower environments and be careful with bind parameters, sampling and sensitive fields in production.

#### Interview answer

For development, Hibernate SQL logs, formatted SQL, bind parameter logs or datasource proxies can show generated SQL. In production, full parameter logging can expose passwords, tokens, PII and business secrets. Prefer safe sampling, query fingerprints, timings and trace correlation.

Use database monitoring and APM to see slow queries without dumping sensitive payloads.

#### Deep dive

SQL with bind values is often more sensitive than application logs because it contains raw customer data.

#### Production angle

A safe observability setup gives query timing and correlation without violating security or compliance.

#### Traps / caveats

- Do not enable verbose bind logging broadly in production.
- Mask or omit sensitive parameters.
- Correlate SQL with request IDs/traces.

#### Optional Anki

Q: Why is SQL parameter logging risky?
A: It can expose PII, secrets and business-sensitive data.

</details>

<a id="jpa-perf-003"></a>

<details>
<summary><strong>🧠 JPA-PERF-003. What Hibernate, database and connection pool metrics would you collect, and what is the Hibernate statistics API useful for?</strong></summary>

#### Short answer

Collect query counts/timings, entity/cache stats, transaction metrics, pool usage and database wait/query metrics; Hibernate statistics helps inspect ORM-level behavior.

#### Interview answer

At the ORM layer, track statement counts, slow queries, flushes, entity loads, collection loads, second-level cache hits/misses and batch behavior. At the pool layer, track active/idle connections, wait time and timeouts. At the database, track CPU, locks, slow queries, buffers and execution plans.

Hibernate statistics can expose loads, fetches, cache activity and query metrics for diagnostics.

#### Deep dive

Enable detailed statistics carefully because it can add overhead. Use it in lower environments or targeted production diagnostics.

#### Production angle

Combining these metrics helps distinguish ORM misuse from database saturation or pool misconfiguration.

#### Traps / caveats

- One metric alone rarely explains latency.
- Cache hit rate without correctness is meaningless.
- Pool exhaustion is often caused by slow queries or long transactions.

#### Optional Anki

Q: What does Hibernate statistics help reveal?
A: Entity loads, collection fetches, query counts and cache behavior.

</details>

<a id="jpa-perf-004"></a>

<details>
<summary><strong>JPA-PERF-004. How do you connect Hibernate-generated SQL with PostgreSQL `EXPLAIN ANALYZE`?</strong></summary>

#### Short answer

Capture the actual SQL and bind values safely, run it with representative parameters, and inspect the execution plan, timing, rows and buffers.

#### Interview answer

First correlate the endpoint to the generated SQL. Then reproduce the query against production-like data with realistic bind values. Use `EXPLAIN ANALYZE` carefully in a safe environment, or `EXPLAIN` where executing is risky. Compare estimated vs actual rows, indexes used, join strategy, sort/hash operations and buffer reads.

Then adjust query, indexes, statistics or data model.

#### Deep dive

Generated SQL may include aliases and joins that differ from hand-written expectations. Use exactly what Hibernate sends.

#### Production angle

This bridges Java-level symptoms with database-level evidence.

#### Traps / caveats

- `EXPLAIN ANALYZE` runs the query.
- Parameter values can change plans.
- Development data plans may be irrelevant.

#### Optional Anki

Q: What SQL should you explain?
A: The actual SQL Hibernate sends with representative parameters.

</details>

<a id="jpa-perf-005"></a>

<details>
<summary><strong>JPA-PERF-005. Why can a query be fast in development but slow in production?</strong></summary>

#### Short answer

Production has different data volume, distribution, indexes, statistics, concurrency, cache state and hardware pressure.

#### Interview answer

Development data is often tiny and uniform. Production data may have millions of rows, skewed tenants, different parameter values, stale statistics, missing indexes, lock contention and cold caches. A query that scans 100 rows locally may scan millions in production.

Always test important queries with production-like data and plans.

#### Deep dive

Skew matters: the same query can be fast for a small tenant and slow for a huge tenant.

#### Production angle

Performance validation should include realistic cardinality, representative filters and expected concurrency.

#### Traps / caveats

- H2 performance means little for PostgreSQL.
- Warm cache hides I/O cost.
- Generic plans can behave differently from custom plans.

#### Optional Anki

Q: Why is production-like data important?
A: Query plans depend on real cardinality and distribution.

</details>

<a id="jpa-perf-006"></a>

<details>
<summary><strong>JPA-PERF-006. What are over-fetching and under-fetching?</strong></summary>

#### Short answer

Over-fetching loads more data than needed; under-fetching loads too little and causes additional queries later.

#### Interview answer

Over-fetching happens when an endpoint loads full entities, large collections or unused associations. Under-fetching happens when required associations are lazy and each access triggers another query, causing N+1.

Good query design loads exactly what the use case needs.

#### Deep dive

Over-fetching and under-fetching are both fetch-plan failures. Fixes include projections, fetch joins, entity graphs, batch fetching and separate queries.

#### Production angle

Over-fetching causes heap/network load; under-fetching causes query storms and latency.

#### Traps / caveats

- EAGER often turns under-fetching into over-fetching.
- One endpoint's perfect fetch plan may be wrong for another.
- Measure data volume, not only query count.

#### Optional Anki

Q: What is under-fetching?
A: Loading too little initially, causing extra queries later.

</details>

<a id="jpa-perf-007"></a>

<details>
<summary><strong>JPA-PERF-007. How can large transactions and long persistence contexts hurt performance?</strong></summary>

#### Short answer

They hold connections/locks longer, grow memory, slow dirty checking and increase failure/rollback cost.

#### Interview answer

A large transaction may keep a database connection for a long time and hold locks until commit. A long persistence context accumulates managed entities and snapshots. Flush becomes more expensive, memory grows and stale data risk increases.

Batch work should use chunks with bounded transaction and persistence context size.

#### Deep dive

Long read transactions can also interfere with database cleanup mechanisms depending on the database.

#### Production angle

Large transactions often cause pool exhaustion, lock waits and memory pressure during imports or scheduled jobs.

#### Traps / caveats

- Do not process millions of rows in one transaction.
- Avoid external calls inside DB transactions.
- Use `flush()`/`clear()` carefully in batch loops.

#### Optional Anki

Q: Why are large persistence contexts slow?
A: They retain many managed entities and increase dirty-checking/memory cost.

</details>

<a id="jpa-perf-008"></a>

<details>
<summary><strong>JPA-PERF-008. How do connection pools and application thread counts limit JPA scalability?</strong></summary>

#### Short answer

JPA work needs database connections; too many application threads can just create more waiting, contention and database overload.

#### Interview answer

A request using JPA usually needs a connection during transaction work. The pool limits how many concurrent database operations can run. If the application has many request threads but the pool is small, threads wait. If the pool is too large, the database can be overwhelmed.

Scalability depends on query speed, transaction length, pool sizing and database capacity.

#### Deep dive

Nested transactions such as `REQUIRES_NEW` can temporarily require more connections per request.

#### Production angle

Pool wait time is often a symptom of slow queries, long transactions or too much concurrency.

#### Traps / caveats

- Increasing threads does not increase database capacity.
- A bigger pool can make the database slower.
- Monitor connection wait time and active count.

#### Optional Anki

Q: What happens when more threads need DB work than pool connections?
A: Threads wait for connections.

</details>

<a id="jpa-perf-009"></a>

<details>
<summary><strong>JPA-PERF-009. How do indexes, column types and functions in `WHERE` clauses interact with ORM-generated queries?</strong></summary>

#### Short answer

The database can use indexes only when query predicates and column types match the index design; functions or casts can prevent index usage.

#### Interview answer

Hibernate-generated SQL still follows database rules. If a predicate uses the wrong type, applies a function to an indexed column, casts values, or filters on low-selectivity columns, the database may scan instead of using an index.

ORM mappings should use correct column types, and queries should match available indexes.

#### Deep dive

For common multi-column filters, composite index order and selectivity matter. For function-based filters, expression indexes may be needed.

#### Production angle

A small mapping mismatch, such as storing numbers as strings or timezone values inconsistently, can become a slow-query issue.

#### Traps / caveats

- `lower(column)` may prevent normal index usage.
- Implicit casts can hurt plans.
- Indexes must match real query patterns.

#### Optional Anki

Q: Why can functions in `WHERE` hurt indexes?
A: They may prevent use of the plain column index.

</details>

<details>
<summary><strong>🧠 JPA-PERF-010. How do traces help diagnose ORM latency, and how would you prove that a Hibernate optimization helped?</strong></summary>

#### Short answer

Traces show where time is spent per request; prove improvement by comparing query count, latency, row counts and resource metrics before and after.

#### Interview answer

Distributed traces can show controller, service, repository, JDBC and database spans. They help identify whether latency is in query execution, connection wait, serialization, external calls or application code.

To prove an optimization helped, measure baseline and after-change under comparable load. Track p50/p95/p99 latency, SQL count, DB time, rows fetched, pool wait and error rate.

#### Deep dive

An optimization that improves average latency but worsens p99 or database CPU may not be acceptable.

#### Production angle

Evidence-based tuning prevents cargo-cult changes like adding eager fetches or cache without proving benefit.

#### Traps / caveats

- Compare under similar data and traffic.
- Include cold and warm cache behavior if relevant.
- Watch for shifted bottlenecks.

#### Optional Anki

Q: What proves a Hibernate performance fix?
A: Before/after measurements of latency, SQL behavior and resource usage.

</details>

<a id="jpa-scenario-001"></a>

<details>
<summary><strong>JPA-SCENARIO-001. A list endpoint executes 501 SQL queries for 500 rows. How do you diagnose and fix it?</strong></summary>

#### Short answer

It is likely N+1. Identify the lazy access, then use a projection, fetch join, entity graph or batch fetching.

#### Interview answer

I would first correlate SQL to the endpoint and confirm the repeated query pattern. Then I would inspect DTO mapping and serialization to see which association is accessed per row. For a list endpoint, I would usually prefer a DTO projection or a query that fetches only required fields. If entities are needed, use a targeted fetch plan or batch fetching.

Add a query-count regression test.

#### Deep dive

Check row volume too. One join fetch might reduce queries but multiply rows.

#### Production angle

N+1 fixes should reduce database round trips without creating over-fetching or broken pagination.

#### Traps / caveats

- Do not make every association eager.
- Include mapper/serializer in the test.
- Validate with realistic parent count.

#### Optional Anki

Q: 501 queries for 500 rows usually means what?
A: N+1 query problem.

</details>

<a id="jpa-scenario-002"></a>

<details>
<summary><strong>JPA-SCENARIO-002. A `@Transactional` service returns DTOs but sometimes throws `LazyInitializationException`. What went wrong?</strong></summary>

#### Short answer

DTO mapping likely happens after the transaction closes, or the DTO contains lazy entity access deferred until later.

#### Interview answer

I would check whether the service actually maps DTOs inside the transaction or returns a stream/lazy mapper that executes later. I would also check self-invocation, missing transaction proxying and whether nested DTO fields access lazy associations after return.

Fix by fetching required data and fully materializing DTOs inside the service transaction, or by using projections.

#### Deep dive

Java Streams are lazy. Returning a stream from a transactional method can move mapping outside the transaction.

#### Production angle

This usually appears after refactoring DTO mapping or disabling OSIV.

#### Traps / caveats

- `@Transactional` must be applied through Spring proxy.
- Do not return lazy entity-backed DTOs.
- Avoid entity references inside DTOs.

#### Optional Anki

Q: Why can DTO mapping still throw lazy errors?
A: Mapping may execute after the persistence context is closed.

</details>

<a id="jpa-scenario-003"></a>

<details>
<summary><strong>JPA-SCENARIO-003. A production endpoint became slow after adding a new `@OneToMany` field to a DTO. What do you check?</strong></summary>

#### Short answer

Check whether the new field triggers lazy loading, collection fetch joins, row multiplication or excessive serialization.

#### Interview answer

I would compare SQL before and after the change. The new field may access a lazy collection for every row, causing N+1. Or a fetch join may load a large collection for each parent, causing over-fetching and duplicates. I would also inspect response size and JSON serialization time.

For list endpoints, use a summary projection or separate child count/query instead of embedding large collections.

#### Deep dive

Adding one DTO field changes the data contract and therefore the query contract.

#### Production angle

Small API changes can drastically increase DB rows, heap usage and response payload size.

#### Traps / caveats

- Do not fetch full collections for list rows casually.
- Check count query behavior too.
- Add performance/query-count tests for DTO changes.

#### Optional Anki

Q: What is the first suspicion after adding a collection field to a DTO?
A: N+1 or over-fetching.

</details>

<a id="jpa-scenario-004"></a>

<details>
<summary><strong>JPA-SCENARIO-004. A pageable query with `JOIN FETCH` returns duplicates or wrong pages. How do you redesign it?</strong></summary>

#### Short answer

Page root IDs first, then fetch required associations for those IDs, or use DTO projections designed for pagination.

#### Interview answer

Collection fetch joins multiply SQL rows, so database pagination can page over parent-child rows instead of unique parents. I would split the query: first select stable ordered parent IDs with limit/offset or keyset pagination, then load details for those IDs with a fetch join, entity graph or batch fetching.

For list screens, a projection may be better.

#### Deep dive

Use stable ordering with a unique tie-breaker. Avoid sorting by unbounded child collections.

#### Production angle

Wrong pagination creates missing/duplicate results and can become very expensive on large tables.

#### Traps / caveats

- JPQL `distinct` does not fully solve pagination semantics.
- Count query must be reviewed separately.
- Maintain result order after second-step fetch.

#### Optional Anki

Q: Safe pattern for collection data with pagination?
A: Page root IDs first, then fetch associations.

</details>

<a id="jpa-scenario-005"></a>

<details>
<summary><strong>JPA-SCENARIO-005. An entity update unexpectedly updates many columns. How do you investigate?</strong></summary>

#### Short answer

Check dirty checking, entity mutations, mapping, dynamic update settings and whether Hibernate updates all mapped columns by default.

#### Interview answer

I would inspect the SQL and identify whether many columns are updated because Hibernate's normal update statement includes all columns or because many fields were actually changed. Then I would look for mappers, setters, lifecycle callbacks and mutable embedded objects.

If wide updates are a real problem, consider `@DynamicUpdate` after measuring.

#### Deep dive

Updating many columns is not always wrong. It becomes a problem when it triggers conflicts, writes large values or causes unnecessary database work.

#### Production angle

Unexpected updates can cause lock contention, audit noise and replication volume.

#### Traps / caveats

- `@DynamicUpdate` is not always faster.
- The mutation may happen earlier than the flush.
- Check optimistic locking behavior.

#### Optional Anki

Q: Why can SQL update happen without calling update?
A: Dirty checking of a managed entity.

</details>

<a id="jpa-scenario-006"></a>

<details>
<summary><strong>JPA-SCENARIO-006. A batch import becomes slower over time and memory usage grows. What is likely wrong?</strong></summary>

#### Short answer

The persistence context is likely growing because entities are not flushed and cleared in chunks.

#### Interview answer

In a batch import, every persisted entity can remain managed. As the persistence context grows, memory usage and dirty-checking cost increase. I would process in chunks: persist a batch, flush, clear, commit or continue carefully, and avoid loading unnecessary associations.

Also verify JDBC batching and ID strategy.

#### Deep dive

For very large imports, `StatelessSession`, native SQL or database bulk loading may be better.

#### Production angle

Unbounded imports can exhaust heap, hold locks and starve online traffic.

#### Traps / caveats

- Do not import millions of rows in one transaction.
- `IDENTITY` can limit insert batching.
- Validate error handling and resumability.

#### Optional Anki

Q: Common fix for growing JPA batch memory?
A: Process in chunks with periodic flush and clear.

</details>

<a id="jpa-scenario-007"></a>

<details>
<summary><strong>JPA-SCENARIO-007. A migration changes an enum mapping and data becomes corrupted. What probably happened?</strong></summary>

#### Short answer

The enum was likely stored as ordinal and constants were reordered or inserted, changing the meaning of stored numbers.

#### Interview answer

With `EnumType.ORDINAL`, the database stores enum positions. If the enum order changes, old values can map to different constants. That silently corrupts business meaning.

The fix is to use stable string values or explicit codes with a converter and migrate existing data carefully.

#### Deep dive

Even string enum renames need planned migrations. Stable business codes are often best for long-lived data.

#### Production angle

Enum corruption can affect order status, payment state, permissions or workflow logic.

#### Traps / caveats

- Do not rely on enum declaration order for persisted meaning.
- Add tests around enum migrations.
- Validate data after migration.

#### Optional Anki

Q: Why is `EnumType.ORDINAL` migration-risky?
A: Stored numbers depend on enum constant order.

</details>

<a id="jpa-scenario-008"></a>

<details>
<summary><strong>JPA-SCENARIO-008. Two users update the same entity and one update is silently lost. How do you fix it?</strong></summary>

#### Short answer

Add optimistic locking with `@Version` and handle conflicts, or use a stronger locking/atomic update strategy if needed.

#### Interview answer

This is a lost update. I would add a version column and ensure update DTOs carry the version read by the user. If another transaction commits first, the second update fails with a conflict instead of silently overwriting.

For high-conflict short operations, consider pessimistic locking or atomic SQL.

#### Deep dive

The user experience matters: show a conflict, refresh data, or merge changes only when business-safe.

#### Production angle

Lost updates are critical in money, inventory, workflow and admin configuration.

#### Traps / caveats

- Do not retry blindly.
- Include version in detached update flows.
- Add database constraints for invariants beyond one row.

#### Optional Anki

Q: What JPA feature detects lost updates?
A: Optimistic locking with `@Version`.

</details>

<a id="jpa-scenario-009"></a>

<details>
<summary><strong>JPA-SCENARIO-009. A transaction with `REQUIRES_NEW` causes connection pool exhaustion. Why?</strong></summary>

#### Short answer

Each inner `REQUIRES_NEW` transaction may need its own connection while the outer transaction still holds one.

#### Interview answer

`REQUIRES_NEW` suspends the outer transaction and starts a separate transaction. Under load, one request can occupy more than one database connection. If this happens inside loops or slow flows, the pool can exhaust quickly.

I would inspect transaction propagation, connection pool metrics, stack traces and nested transaction frequency.

#### Deep dive

Audit or notification code often introduces `REQUIRES_NEW` without considering pool capacity.

#### Production angle

Pool exhaustion causes blocked request threads, timeouts and cascading failures.

#### Traps / caveats

- Avoid `REQUIRES_NEW` in loops.
- Keep transactions short.
- Size the pool for worst-case connection use or redesign.

#### Optional Anki

Q: Why can `REQUIRES_NEW` double connection demand?
A: The outer transaction is suspended while the inner transaction uses another connection.

</details>

<details>
<summary><strong>JPA-SCENARIO-010. A method marked `@Transactional(readOnly = true)` still causes writes. What do you check?</strong></summary>

#### Short answer

Check whether managed entities are mutated, whether read-only is actually applied, and how Hibernate flush mode is configured.

#### Interview answer

First verify the method is called through the Spring proxy. Then inspect the code for setters, collection mutations, lifecycle callbacks or mappers changing managed entities. Also check whether the transaction joins an existing non-read-only transaction.

`readOnly = true` is a hint/optimization, not a guarantee that Java code cannot mutate objects.

#### Deep dive

Some providers/configurations suppress flushing in read-only transactions, but relying on that hides bad design.

#### Production angle

Unexpected writes from reads can trigger audit events, locks and cache invalidation.

#### Traps / caveats

- Self-invocation may bypass `@Transactional`.
- Existing transaction settings may win.
- Read-only does not mean immutable.

#### Optional Anki

Q: What is the first code smell in a read-only transaction that writes?
A: Mutating a managed entity.

</details>

<details>
<summary><strong>JPA-SCENARIO-011. A production deadlock involves Hibernate-generated SQL. How do you debug and fix it?</strong></summary>

#### Short answer

Identify the conflicting SQL and lock order, map it to code paths, then reduce transaction scope or enforce consistent ordering.

#### Interview answer

I would collect database deadlock logs, blocked statements, transaction IDs and application traces. Then map SQL back to Hibernate operations and service methods. Common fixes include consistent update order, shorter transactions, better indexes, fewer rows locked, retrying deadlock victims and avoiding external calls while holding locks.

Deadlocks are database-level events even if SQL is generated by Hibernate.

#### Deep dive

Hibernate flush order can influence when locks are acquired. Explicit flush points can help but should be used carefully.

#### Production angle

Deadlock handling should include safe retry policy and alerting on spikes.

#### Traps / caveats

- Do not guess without DB deadlock details.
- Retrying must be idempotent.
- Missing indexes can increase locked rows.

#### Optional Anki

Q: First evidence for deadlock debugging?
A: Database deadlock report plus application trace correlation.

</details>

<a id="jpa-scenario-012"></a>

<details>
<summary><strong>🧠 JPA-SCENARIO-012. A second-level cache returns stale data after another service updates the same table. What are options?</strong></summary>

#### Short answer

Disable cache for that data, add explicit invalidation, shorten staleness window, or enforce single-writer ownership.

#### Interview answer

The problem is that Hibernate's cache does not automatically know about external writes. Options include removing second-level cache for that entity, routing all writes through one service, publishing invalidation events, using TTL where stale reads are acceptable, or moving to an application-level cache with clear ownership.

For sensitive data, prefer correctness over cache hit rate.

#### Deep dive

The right answer depends on whether stale data is acceptable and for how long.

#### Production angle

Stale permissions, prices or inventory can be serious incidents.

#### Traps / caveats

- TTL is not strong consistency.
- Manual DB scripts also bypass cache.
- Monitor stale-data symptoms, not only cache hit rate.

#### Optional Anki

Q: Why did Hibernate cache become stale?
A: Another writer changed the database outside Hibernate's cache invalidation path.

</details>

<details>
<summary><strong>JPA-SCENARIO-013. A JSON serializer causes thousands of lazy loads. How do you prevent it?</strong></summary>

#### Short answer

Stop serializing entities directly; return DTOs or projections prepared with an explicit fetch plan.

#### Interview answer

Jackson is likely traversing lazy associations for each entity. I would replace entity responses with DTOs, disable accidental entity serialization, and load only required data in the service/repository query. Add query-count tests around the endpoint.

If needed, use `@JsonIgnore` as a temporary guard, but not as the main design.

#### Deep dive

OSIV can make this worse by allowing serializer-triggered SQL instead of failing fast.

#### Production angle

Serializer-driven queries are hard to see in code review and can create large p99 latency spikes.

#### Traps / caveats

- Do not solve by making everything eager.
- Avoid Lombok `toString()` and JSON over entities.
- Verify response size and SQL count.

#### Optional Anki

Q: Best prevention for JSON lazy-load storms?
A: DTOs/projections with explicit fetch plans.

</details>

<a id="jpa-scenario-014"></a>

<details>
<summary><strong>JPA-SCENARIO-014. A many-to-many mapping starts deleting shared records. What likely caused it?</strong></summary>

#### Short answer

`CascadeType.REMOVE` or `CascadeType.ALL` was likely applied to a shared many-to-many target.

#### Interview answer

In a direct many-to-many, deleting one side should usually delete join table rows, not the shared target records. If remove cascade is configured, Hibernate may propagate deletes to entities still used by others.

Fix by removing dangerous cascade, restoring data, adding constraints/tests and possibly modeling the join as an explicit entity.

#### Deep dive

Many-to-many is often too simplistic once the relationship has lifecycle or attributes.

#### Production angle

This can delete roles, tags, categories or permissions across users/items.

#### Traps / caveats

- `CascadeType.ALL` includes remove.
- DB foreign keys may block but should not be the design.
- Audit delete operations.

#### Optional Anki

Q: Why is `CascadeType.ALL` dangerous on many-to-many?
A: It includes remove cascade to shared entities.

</details>

<a id="jpa-scenario-015"></a>

<details>
<summary><strong>JPA-SCENARIO-015. A service uses `merge()` on a request body entity and overwrites fields with nulls. How do you redesign it?</strong></summary>

#### Short answer

Use a command DTO, load the managed entity, validate permissions/version and apply only allowed fields.

#### Interview answer

The request body is incomplete detached state. `merge()` copies that state, including nulls, into a managed entity. I would stop binding requests to entities. Define a DTO for the operation, fetch the existing entity in a transaction, check ownership/version and call domain methods or setters for explicit fields only.

This turns a dangerous full-state replace into an intentional update.

#### Deep dive

For PATCH, distinguish absent fields from explicit nulls.

#### Production angle

This prevents mass assignment, lost updates and accidental association rewrites.

#### Traps / caveats

- Do not use entity classes as request schemas.
- Do not treat `merge()` as patch.
- Add tests for forbidden/null fields.

#### Optional Anki

Q: Safe replacement for merging request entities?
A: Command DTO plus explicit update of a managed entity.

</details>

<details>
<summary><strong>JPA-SCENARIO-016. An entity in a `HashSet` disappears after being persisted. What could be wrong?</strong></summary>

#### Short answer

Its `hashCode()` likely changed after persistence, often because generated ID became part of equality/hash code.

#### Interview answer

If an entity is added to a `HashSet` while its ID is null, then persisted and assigned an ID, an ID-based `hashCode()` changes. The object is now in the wrong hash bucket and lookup/removal can fail.

Use stable equality rules and avoid mutable fields in hash code.

#### Deep dive

The same issue occurs when business-key fields used in hash code are editable.

#### Production angle

This breaks association sets, caches and domain collections in subtle ways.

#### Traps / caveats

- Generated IDs are not stable before persist.
- Mutable fields should not be hash keys.
- Proxies also affect equality.

#### Optional Anki

Q: Why can an entity vanish from `HashSet` after persist?
A: Its `hashCode()` changed after ID assignment.

</details>

<a id="jpa-scenario-017"></a>

<details>
<summary><strong>JPA-SCENARIO-017. A query uses an entity graph and suddenly returns much more data. What do you check?</strong></summary>

#### Short answer

Check graph attributes, nested subgraphs, default eager mappings, collection cardinality and generated SQL.

#### Interview answer

An entity graph changes the fetch plan. I would inspect which associations were added, whether nested subgraphs pull large collections, and whether `loadgraph` preserves default eager attributes. Then I would compare generated SQL, row count and response size.

If the endpoint is a list, switch to projection or a narrower graph.

#### Deep dive

Entity graphs can be reused too broadly, causing one endpoint to inherit another endpoint's fetch needs.

#### Production angle

Bad graphs can cause over-fetching, memory spikes and slow serialization.

#### Traps / caveats

- Graphs do not automatically respect pagination safely.
- Default eager mappings can still apply.
- Measure rows fetched, not just query count.

#### Optional Anki

Q: What should you inspect after adding an entity graph?
A: Generated SQL, associations fetched and row count.

</details>

<a id="jpa-scenario-018"></a>

<details>
<summary><strong>JPA-SCENARIO-018. A service needs to export millions of rows. Would you use entities, projections, streaming or native SQL?</strong></summary>

#### Short answer

Usually projections or native SQL with streaming/chunking, not full managed entities.

#### Interview answer

For millions of rows, full entities are usually too heavy because they fill the persistence context and allocate large graphs. I would use a projection or native SQL that selects only export columns, stream or page results in chunks, and write output incrementally.

Keep transactions/resource lifetimes controlled and avoid lazy associations.

#### Deep dive

Database cursors/streaming need open resources. The export pipeline must close resources and handle backpressure/failures.

#### Production angle

Exports can overload the primary database. Consider replicas, rate limits and job isolation.

#### Traps / caveats

- Do not collect all rows into memory.
- Do not keep one huge transaction open.
- Avoid entity graphs for flat exports.

#### Optional Anki

Q: Best data shape for huge exports?
A: Flat projections/native SQL streamed or paged in chunks.

</details>

<a id="jpa-scenario-019"></a>

<details>
<summary><strong>🧠 JPA-SCENARIO-019. A service needs strict write consistency across two aggregates. Would you use one JPA transaction, optimistic locking, pessimistic locking or outbox?</strong></summary>

#### Short answer

It depends on whether both aggregates are in one database boundary, conflict rate, invariant type and whether external messages are involved.

#### Interview answer

If both aggregates are in the same database and one business invariant requires atomic change, one transaction may be appropriate. Use optimistic locking for normal conflicts and pessimistic locking for short high-contention critical sections. Use database constraints where possible.

If consistency involves publishing events or another service, use outbox/idempotency rather than pretending a local JPA transaction covers external systems.

#### Deep dive

Cross-aggregate consistency can signal a modeling issue. Sometimes the invariant belongs inside one aggregate or needs a process manager/saga.

#### Production angle

Correct design balances consistency, contention, failure recovery and operational complexity.

#### Traps / caveats

- A JPA transaction cannot atomically commit another service's database.
- Pessimistic locks can deadlock.
- Outbox gives reliable messaging, not instant global consistency.

#### Optional Anki

Q: What pattern helps reliably publish events after DB commit?
A: Transactional outbox.

</details>

<a id="jpa-scenario-020"></a>

<details>
<summary><strong>JPA-SCENARIO-020. A team wants to remove all database constraints because JPA validates entities. How do you argue against it?</strong></summary>

#### Short answer

JPA validation is not enough; database constraints enforce integrity for all writers and under concurrency.

#### Interview answer

Application validation improves error messages and catches mistakes early, but it only runs in that application path. Database constraints protect data from bugs, concurrent races, imports, scripts, other services and future code. Critical invariants such as foreign keys, uniqueness and non-null requirements belong in the database.

JPA mappings and database constraints should complement each other.

#### Deep dive

Without constraints, the database can contain impossible states that every future query and migration must handle.

#### Production angle

Removing constraints trades short-term convenience for long-term data corruption and incident risk.

#### Traps / caveats

- Bean Validation is not a concurrency control mechanism.
- ORM mappings do not protect direct SQL writers.
- Constraint violations should be translated cleanly at API boundaries.

#### Optional Anki

Q: Why keep database constraints with JPA?
A: They enforce data integrity for all writers, not only validated application code.

</details>
