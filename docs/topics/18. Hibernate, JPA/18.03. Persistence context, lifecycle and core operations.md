# Persistence context, lifecycle and core operations

---

<a id="jpa-pc-001"></a>

<details>
<summary><strong>JPA-PC-001. What is a persistence context, and why is it called the first-level cache?</strong></summary>

#### Short answer

A persistence context is the set of managed entities tracked by an `EntityManager`; it is called the first-level cache because it stores loaded entities for that context.

#### Interview answer

When an entity is loaded or persisted, it becomes managed by the persistence context. Within that context, JPA tracks identity and changes. If the same entity is requested again by ID, the provider can return the already managed instance instead of hitting the database again.

This cache is mandatory and scoped to the persistence context, not shared globally.

#### Deep dive

The first-level cache is also where dirty checking works. Hibernate keeps enough state to compare changes and flush SQL later.

#### Production angle

A long-lived persistence context can grow large, return stale data, consume memory and slow dirty checking.

#### Traps / caveats

- First-level cache is not the same as second-level cache.
- It is not a general application cache.
- It can return stale data if the database is changed outside the context.

#### Optional Anki

Q: What is stored in the first-level cache?
A: Managed entity instances inside one persistence context.

</details>

<a id="jpa-pc-002"></a>

<details>
<summary><strong>JPA-PC-002. What are the transient, managed, detached and removed entity states?</strong></summary>

#### Short answer

Transient means not persisted or managed, managed means tracked by the persistence context, detached means previously persistent but no longer managed, and removed means scheduled for deletion.

#### Interview answer

A transient entity is just a Java object with no persistence context identity. A managed entity is associated with an open persistence context and participates in dirty checking. A detached entity has an ID and may represent a database row, but changes are not tracked. A removed entity is managed but marked for deletion on flush.

Understanding these states explains `persist()`, `merge()`, lazy loading and dirty checking behavior.

#### Deep dive

Entity state is not the same as transaction state. An object can be managed inside a context, while commit or rollback is controlled by the transaction.

#### Production angle

Many bugs come from assuming detached objects are still tracked, or from merging request objects that should have been mapped onto a managed entity.

#### Traps / caveats

- Detached changes are not saved automatically.
- Managed changes can be saved even without calling `save()`.
- Removed entities may still exist in memory until flush/commit.

#### Optional Anki

Q: Which entity state participates in dirty checking?
A: Managed.

</details>

<a id="jpa-pc-003"></a>

<details>
<summary><strong>JPA-PC-003. What do `persist()`, `find()`, `getReference()`, `remove()` and `refresh()` do?</strong></summary>

#### Short answer

They make new entities managed, load entities, obtain lazy references, mark entities for deletion and reload state from the database.

#### Interview answer

`persist()` makes a new entity managed and schedules it for insert. `find()` loads an entity by primary key or returns an already managed instance. `getReference()` can return a proxy without immediately loading all state. `remove()` marks a managed entity for deletion. `refresh()` discards local changes and reloads state from the database.

These operations affect entity state, but SQL is usually sent on flush.

#### Deep dive

`getReference()` is useful when only a foreign key reference is needed, but accessing the proxy requires an open persistence context.

#### Production angle

Misusing `refresh()` or `remove()` can overwrite local work or delete more than expected when cascades are involved.

#### Traps / caveats

- `persist()` is for new entities, not detached updates.
- `getReference()` can throw when the row is missing and the proxy is initialized.
- `refresh()` can discard unsaved in-memory changes.

#### Optional Anki

Q: Which operation reloads database state into a managed entity?
A: `refresh()`.

</details>

<a id="jpa-pc-004"></a>

<details>
<summary><strong>JPA-PC-004. What is the difference between `persist()` and `merge()`?</strong></summary>

#### Short answer

`persist()` makes a new entity managed; `merge()` copies state from a detached object into a managed instance and returns that managed instance.

#### Interview answer

`persist()` should be used for new entities. The same object becomes managed. `merge()` is for detached state. It does not reattach the given object directly; it copies its state into a managed entity and returns the managed copy.

This difference is important because continuing to modify the detached argument after `merge()` does not update the managed entity.

#### Deep dive

`merge()` may cascade through a detached graph and can overwrite fields with nulls if the detached object is incomplete.

#### Production angle

Blindly merging request bodies is a common bug that causes lost fields, mass assignment vulnerabilities and unexpected SQL.

#### Traps / caveats

- Use the return value of `merge()`.
- Do not treat `merge()` as a patch operation.
- Prefer loading a managed entity and applying validated DTO changes.

#### Optional Anki

Q: Does `merge()` make the passed object managed?
A: No. It returns a managed copy.

</details>

<a id="jpa-pc-005"></a>

<details>
<summary><strong>🧠 JPA-PC-005. How do Hibernate `Session.save()` and `Session.update()` differ from portable JPA operations?</strong></summary>

#### Short answer

They are Hibernate-specific APIs with semantics that differ from JPA `persist()` and `merge()`, so they reduce portability.

#### Interview answer

JPA defines `persist()` and `merge()` as portable operations. Hibernate also has native methods such as `save()` and `update()` from older Hibernate APIs. `save()` returns an identifier and has Hibernate-specific behavior. `update()` tries to reassociate a detached instance and can fail if the session already contains another instance with the same identity.

In new Spring/JPA code, prefer portable JPA operations unless a Hibernate-specific behavior is intentionally needed.

#### Deep dive

Many teams encounter these methods in legacy code. Understanding them helps during migrations, but they should not be mixed casually with JPA semantics.

#### Production angle

Confusion around `update()` vs `merge()` can cause non-unique object exceptions or lost changes.

#### Traps / caveats

- Hibernate native APIs are not provider-portable.
- `update()` is not the same as JPA `merge()`.
- Mixing APIs can confuse code review and tests.

#### Optional Anki

Q: Which operation is portable JPA for detached state?
A: `merge()`.

</details>

<a id="jpa-pc-006"></a>

<details>
<summary><strong>JPA-PC-006. What do `detach()`, `clear()`, `contains()` and `close()` do?</strong></summary>

#### Short answer

`detach()` removes one entity from management, `clear()` detaches all, `contains()` checks management, and `close()` closes the `EntityManager`.

#### Interview answer

`detach(entity)` makes that entity detached, so changes are no longer tracked. `clear()` detaches every managed entity in the persistence context. `contains(entity)` tells whether the entity is currently managed. `close()` closes an application-managed `EntityManager`; after that it cannot be used.

These operations are useful in batch processing and lifecycle control.

#### Deep dive

In Spring, application code rarely calls `close()` directly because Spring manages transaction-bound entity managers.

#### Production angle

Batch jobs often call `flush()` and `clear()` periodically to avoid unbounded persistence context growth.

#### Traps / caveats

- Clearing detaches all entities, including ones you may still expect to be tracked.
- Detached lazy associations cannot initialize without a context.
- Do not close a container/Spring-managed `EntityManager` manually.

#### Optional Anki

Q: What does `clear()` do?
A: It detaches all entities from the current persistence context.

</details>

<a id="jpa-pc-007"></a>

<details>
<summary><strong>JPA-PC-007. What happens to managed entities when a transaction commits or rolls back?</strong></summary>

#### Short answer

On commit, changes are flushed and committed; on rollback, database changes are discarded, but in-memory entity objects may not automatically revert to old values.

#### Interview answer

Before commit, Hibernate usually flushes pending changes to the database. If the database commit succeeds, the changes become durable. If the transaction rolls back, uncommitted database changes are undone.

However, Java objects in memory are still just objects. Their fields may still contain changed values even though the database rollback happened.

#### Deep dive

After rollback, the persistence context may be inconsistent with the database or unusable depending on the error. Many applications end the transaction and discard that context.

#### Production angle

Do not continue business work with entities after a failed transaction as if they represent committed database state.

#### Traps / caveats

- Rollback does not reset Java object fields.
- Flush can happen before commit.
- Exceptions during flush often require abandoning the current session/context.

#### Optional Anki

Q: Does transaction rollback reset entity field values in memory?
A: No. It rolls back database changes, not Java object state.

</details>

<a id="jpa-pc-008"></a>

<details>
<summary><strong>🧠 JPA-PC-008. What is the difference between transaction-scoped and extended persistence contexts?</strong></summary>

#### Short answer

A transaction-scoped persistence context lives for one transaction; an extended persistence context can live across multiple transactions.

#### Interview answer

Most Spring backend applications use transaction-scoped persistence contexts: the `EntityManager` is bound to the current transaction and closed afterward. An extended persistence context keeps managed entities around longer, often in stateful component models.

Extended contexts can be useful in long conversations, but they increase stale data and memory risks.

#### Deep dive

A long-lived persistence context is not the same as a long-running database transaction. It may span transactions while keeping entity identity and state in memory.

#### Production angle

For stateless web services, extended persistence contexts are rarely the right default because they conflict with request isolation and horizontal scaling.

#### Traps / caveats

- Extended context can return stale entities.
- It can grow in memory over time.
- It is not a solution for lazy-loading issues in REST APIs.

#### Optional Anki

Q: What persistence context scope is common in Spring services?
A: Transaction-scoped.

</details>

<a id="jpa-pc-009"></a>

<details>
<summary><strong>JPA-PC-009. How does Spring usually bind an `EntityManager` to a transaction?</strong></summary>

#### Short answer

Spring opens or obtains an `EntityManager`, binds it to the current thread for the transaction, and repositories use that same context.

#### Interview answer

With Spring transaction management, a `@Transactional` method starts a transaction and Spring coordinates an `EntityManager` for that transaction. Spring Data repositories and injected `EntityManager` proxies participate in the same persistence context.

That is why multiple repository calls inside one transaction can see the same managed entities.

#### Deep dive

The injected `EntityManager` is often a proxy that delegates to the transaction-bound actual entity manager.

#### Production angle

Understanding this explains first-level cache behavior, lazy loading inside service methods and why async threads do not automatically inherit the persistence context.

#### Traps / caveats

- Thread-bound context does not cross `@Async`.
- Self-invocation can bypass `@Transactional`.
- OSIV can extend context into web rendering if enabled.

#### Optional Anki

Q: Why do repository calls in one Spring transaction share managed entities?
A: They use the same transaction-bound persistence context.

</details>

<details>
<summary><strong>JPA-PC-010. Why should a persistence context usually not be kept open for too long?</strong></summary>

#### Short answer

It can grow in memory, return stale data, slow dirty checking and hide lazy-loading or transaction boundary problems.

#### Interview answer

A persistence context stores managed entities and their tracking state. If it stays open too long, more entities accumulate, dirty checking takes more work, and data may become stale compared with the database.

Long contexts also make it easier for code outside the intended service boundary to trigger lazy database access.

#### Deep dive

Keeping a context open is different from keeping a transaction open, but both can be harmful when they span too much work.

#### Production angle

Large imports, exports and request flows can run out of memory or degrade over time if they never clear the persistence context.

#### Traps / caveats

- OSIV can hide bad fetch planning.
- Batch jobs need periodic `flush()`/`clear()`.
- Long contexts are not a cache replacement.

#### Optional Anki

Q: What is a common memory risk in long JPA batch jobs?
A: The persistence context grows with every managed entity.

</details>

<a id="jpa-pc-011"></a>

<details>
<summary><strong>JPA-PC-011. How do you process large result sets without filling the persistence context forever?</strong></summary>

#### Short answer

Use pagination, streaming/cursors carefully, DTO projections, read-only hints, and periodic `flush()`/`clear()` when processing entities.

#### Interview answer

For large data, avoid loading all entities into memory. Prefer database-side filtering and projections when possible. If entity processing is needed, process in pages or use streaming APIs with a clear transaction/resource boundary. In write batches, flush and clear periodically.

For pure export/reporting, native SQL or projections may be better than full entities.

#### Deep dive

Streaming results still need an open connection and transaction in many setups, so it must be consumed promptly and closed.

#### Production angle

Large jobs can exhaust heap, connections or transaction timeouts if they treat millions of rows like a normal list endpoint.

#### Traps / caveats

- Java streams do not automatically solve database memory problems.
- Lazy associations inside a loop can create N+1.
- Long transactions can hold locks and block vacuum/cleanup in some databases.

#### Optional Anki

Q: What is a common JPA batch pattern to control memory?
A: Process in chunks and periodically `flush()` and `clear()`.

</details>

<a id="jpa-pc-012"></a>

<details>
<summary><strong>JPA-PC-012. Why can detached entities be dangerous at API boundaries?</strong></summary>

#### Short answer

Detached entities mix persistence state with external input and can cause stale updates, null overwrites, mass assignment and lazy-loading failures.

#### Interview answer

When entities leave the service layer, they are often detached. If they are serialized, modified by a client and later merged, the application may overwrite fields it did not intend to change. Detached graphs may also contain stale data or missing lazy associations.

DTOs are safer because they explicitly define what crosses the boundary.

#### Deep dive

Detached entities are not tracked. Calling `merge()` later copies their state into managed instances, including nulls and associations unless carefully controlled.

#### Production angle

This is a common source of accidental privilege changes, lost updates and security issues in REST APIs.

#### Traps / caveats

- Do not deserialize request bodies directly into entities.
- Do not merge incomplete objects as patches.
- Do not expose internal lazy graphs as API contracts.

#### Optional Anki

Q: Safer alternative to passing detached entities through REST?
A: Use command/query DTOs.

</details>

<a id="jpa-pc-013"></a>

<details>
<summary><strong>JPA-PC-013. What happens when a lazy proxy is accessed outside an open persistence context?</strong></summary>

#### Short answer

Hibernate cannot initialize the proxy and typically throws `LazyInitializationException`.

#### Interview answer

Lazy associations are loaded on demand. If code accesses a lazy property after the persistence context is closed, Hibernate no longer has a session to issue the SQL. The result is usually `LazyInitializationException`.

The fix is not to make everything eager, but to load the required data inside the transaction using fetch joins, entity graphs, projections or explicit mapping.

#### Deep dive

OSIV keeps the session open longer, but it can move database access into controllers, serializers and views, which makes performance harder to reason about.

#### Production angle

Lazy-loading failures often appear only after refactoring transaction boundaries or disabling OSIV.

#### Traps / caveats

- EAGER can create bigger performance problems.
- JSON serializers can trigger lazy loading.
- DTO mapping should happen within a controlled transaction/fetch plan.

#### Optional Anki

Q: What exception commonly happens when accessing lazy data after the session closes?
A: `LazyInitializationException`.

</details>

<a id="jpa-pc-014"></a>

<details>
<summary><strong>JPA-PC-014. Are `EntityManager` and Hibernate `Session` thread-safe?</strong></summary>

#### Short answer

No. `EntityManager` and `Session` are not thread-safe and should not be shared across threads.

#### Interview answer

An `EntityManager` represents mutable unit-of-work state: managed entities, snapshots, pending actions and flush behavior. Sharing it across threads can corrupt state or create unpredictable behavior.

In Spring, the persistence context is normally bound to the current transaction/thread. Async code should open its own transaction and load its own data if needed.

#### Deep dive

Entities themselves are also usually mutable and not thread-safe. Passing managed entities to async tasks is a persistence boundary smell.

#### Production angle

Thread leaks of persistence context show up as random lazy-loading failures, stale data, concurrent modification issues or connection misuse.

#### Traps / caveats

- Do not use managed entities in `@Async` tasks.
- Do not cache `EntityManager`.
- DTO snapshots are safer for async work.

#### Optional Anki

Q: Is `EntityManager` thread-safe?
A: No.

</details>

<a id="jpa-pc-015"></a>

<details>
<summary><strong>🧠 JPA-PC-015. How can persistence exceptions leave a Hibernate `Session` in an unusable state?</strong></summary>

#### Short answer

After some persistence failures, Hibernate's in-memory action queue and entity state may no longer match the database, so the session should be discarded.

#### Interview answer

If a flush fails because of a constraint violation, stale state, SQL error or connection problem, Hibernate may not be able to safely continue with the same session. The database transaction is usually marked rollback-only, and the persistence context may contain entities whose state does not reflect committed data.

The safe approach is usually to roll back and end the unit of work.

#### Deep dive

This is why catching a persistence exception and continuing to use the same `EntityManager` inside the same transaction is risky.

#### Production angle

Continuing after failed flush can produce misleading logs, repeated failures or partially inconsistent in-memory decisions.

#### Traps / caveats

- Do not swallow persistence exceptions and keep writing.
- Roll back the transaction.
- Start a fresh transaction/context for retry logic.

#### Optional Anki

Q: What should you usually do after a failed Hibernate flush?
A: Roll back and discard the current persistence context/session.

</details>
