# Mapping, identity and entity design

---

<a id="jpa-map-001"></a>

<details>
<summary><strong>JPA-MAP-001. What requirements must a JPA entity class satisfy?</strong></summary>

#### Short answer

A JPA entity needs an entity annotation, an identifier, a non-private no-argument constructor, and persistent state that JPA can access.

#### Interview answer

A JPA entity is usually a regular class annotated with `@Entity`. It must have a primary key, normally with `@Id`, and a no-argument constructor that is at least protected so the provider can instantiate it. The provider must be able to access persistent fields or properties, depending on access mode.

Entities should generally not be final because proxies and lazy loading may require subclassing. Methods and fields used by the provider should also avoid designs that block persistence.

#### Deep dive

Hibernate can sometimes support cases beyond strict portable JPA, but portable code should follow the specification-friendly model: class-based entities, stable identifier, accessible constructor and predictable access strategy.

#### Production angle

Bad entity design often appears as startup mapping failures, lazy-loading failures, reflection issues, proxy problems or hard-to-test domain logic.

#### Traps / caveats

- A public no-arg constructor is not required; protected is usually enough.
- `final` entities can break proxy-based lazy loading.
- Entity constructors should not perform expensive infrastructure work.

#### Optional Anki

Q: Why does a JPA entity need a no-argument constructor?
A: The persistence provider needs to instantiate it reflectively.

</details>

<a id="jpa-map-002"></a>

<details>
<summary><strong>JPA-MAP-002. How do field access, property access and `@Access` differ?</strong></summary>

#### Short answer

Field access reads/writes fields directly; property access uses getters/setters; `@Access` can override the default.

#### Interview answer

JPA chooses access mode based on where mapping annotations such as `@Id` are placed. If annotations are on fields, field access is used. If annotations are on getters, property access is used. With field access, business getters can contain logic without changing persistence access. With property access, getters and setters become part of persistence behavior.

`@Access` is used when you need to override or mix access modes deliberately.

#### Deep dive

Mixing annotations on fields and methods accidentally can produce confusing mapping behavior. Pick one default style per entity hierarchy unless there is a clear reason.

#### Production angle

Wrong access mode can cause fields not to persist, computed getters to be persisted accidentally, or lazy loading to trigger in surprising places.

#### Traps / caveats

- Do not randomly place annotations on both fields and getters.
- Property access can call business logic during persistence operations.
- `@Access` should be explicit and rare.

#### Optional Anki

Q: How does JPA choose field vs property access?
A: Usually by where the `@Id` mapping is placed.

</details>

<a id="jpa-map-003"></a>

<details>
<summary><strong>JPA-MAP-003. Why should entity mapping metadata not be treated as a replacement for database schema design?</strong></summary>

#### Short answer

Entity mappings describe how Java maps to the database; they do not replace careful schema, index, constraint and migration design.

#### Interview answer

Annotations such as `@Column(nullable = false)` or relationship mappings help Hibernate understand the model, but the database still needs real constraints, indexes, correct types and safe migrations. The database is the final authority for integrity, concurrency and query execution.

Good mapping and good schema design should support each other.

#### Deep dive

An entity model can be valid Java but poor relational design. For example, missing foreign keys, weak uniqueness rules, wrong data types or absent indexes can still break production even if Hibernate starts successfully.

#### Production angle

Relying only on ORM metadata creates data corruption risks during bulk imports, manual fixes, other services, migrations or direct database access.

#### Traps / caveats

- ORM validation is not the same as database enforcement.
- `ddl-auto=update` is not a production migration strategy.
- Index design should follow real query patterns.

#### Optional Anki

Q: Why are database constraints still needed with JPA?
A: They enforce integrity for all writers, not only Hibernate-managed code.

</details>

<a id="jpa-map-004"></a>

<details>
<summary><strong>JPA-MAP-004. What is the difference between JPA nullability metadata and real database constraints?</strong></summary>

#### Short answer

JPA nullability metadata informs the provider; a database `NOT NULL` constraint enforces the rule in the database.

#### Interview answer

`@Column(nullable = false)` or `optional = false` helps describe expected mapping and may influence generated DDL or provider behavior. But if the database column is nullable, another writer can still insert nulls. A real `NOT NULL` constraint is enforced by the database for every client.

In production, both should usually agree.

#### Deep dive

Relationship optionality and join-column nullability are related but not identical. One describes object model expectations; the other describes the physical foreign key column.

#### Production angle

Mismatches cause bugs where application validation passes in one path but bad data enters through another path, a migration or a bulk operation.

#### Traps / caveats

- `nullable = false` alone is not enough if schema is not generated from it.
- Bean Validation is also not a database constraint.
- Schema drift can make mappings lie.

#### Optional Anki

Q: What enforces non-null data for all writers?
A: A database `NOT NULL` constraint.

</details>

<a id="jpa-map-005"></a>

<details>
<summary><strong>JPA-MAP-005. When would you use an embeddable value object instead of a separate entity?</strong></summary>

#### Short answer

Use an embeddable when the object has no independent identity and lives as part of its owning entity.

#### Interview answer

An embeddable is good for values such as address, money, date range or audit metadata when they are conceptually part of the parent row or parent lifecycle. It keeps domain concepts explicit without creating a separate table and identity.

Use a separate entity when the object has its own lifecycle, identity, relationships, sharing rules or querying needs.

#### Deep dive

Embeddables can improve domain modeling, but they are still mapped into the owning entity's persistence model. Collections of embeddables often use a collection table and need performance review.

#### Production angle

Correctly choosing entity vs embeddable reduces unnecessary joins, avoids fake IDs and keeps aggregate ownership clearer.

#### Traps / caveats

- Do not make everything an entity just because it has fields.
- Do not embed values that need independent updates or references.
- Large embeddable collections can be expensive.

#### Optional Anki

Q: What is the key sign something should be embeddable?
A: It has no independent identity outside the owning entity.

</details>

<a id="jpa-map-006"></a>

<details>
<summary><strong>🧠 JPA-MAP-006. Can Java records be used with JPA entities, IDs or embeddables?</strong></summary>

#### Short answer

Records are generally not a good fit for JPA entities, but modern Jakarta Persistence allows records for some value-like mapping roles such as embeddables and ID classes.

#### Interview answer

JPA entities need identity, lifecycle, provider construction and usually mutable persistent state. Java records are final, shallowly immutable data carriers, so they do not fit normal entity requirements well.

Records are much better for DTOs, projections and value objects. Jakarta Persistence 3.2 allows record types for embeddables and primary key classes in specific cases, but support depends on provider and version.

#### Deep dive

Hibernate has provider-specific capabilities around records and embeddables, but a senior answer should separate portable JPA from Hibernate-specific support.

#### Production angle

Record support is version-sensitive. During upgrades, verify provider compatibility and tests around construction, mapping and serialization.

#### Traps / caveats

- Records are final, which conflicts with proxy-style entity behavior.
- Do not assume older JPA providers support record embeddables.
- Records are excellent DTO/projection candidates.

#### Optional Anki

Q: Are records a natural fit for JPA entities?
A: No. They are better suited to DTOs, projections and some value mappings.

</details>

<a id="jpa-map-007"></a>

<details>
<summary><strong>JPA-MAP-007. How are common Java basic types, dates, timestamps and enums mapped?</strong></summary>

#### Short answer

Basic Java types map to database column types; modern date/time classes and enums need deliberate column choices.

#### Interview answer

Strings, numbers, booleans and common temporal types are mapped as basic attributes. Java time types such as `LocalDate`, `LocalDateTime`, `Instant` and `OffsetDateTime` are supported by modern JPA/Hibernate stacks, but the exact SQL type and timezone behavior should be checked.

Enums should usually be mapped as strings with `EnumType.STRING`, or with a deliberate converter when database representation needs stability.

#### Deep dive

Temporal mapping is not only a Java issue. You must decide whether a value is a local date, local wall-clock time, instant in time or offset-aware timestamp.

#### Production angle

Wrong time or enum mapping causes migration bugs, reporting errors, timezone defects and corrupted historical data.

#### Traps / caveats

- Avoid storing business enums by ordinal.
- Be explicit about UTC and timezone policy.
- Database column type should match query and indexing needs.

#### Optional Anki

Q: What enum mapping is usually safer than ordinal?
A: `EnumType.STRING` or a stable explicit converter.

</details>

<a id="jpa-map-008"></a>

<details>
<summary><strong>JPA-MAP-008. Why is `EnumType.ORDINAL` risky?</strong></summary>

#### Short answer

`EnumType.ORDINAL` stores enum position, so reordering or inserting enum constants can silently corrupt meaning.

#### Interview answer

With ordinal mapping, the database stores numbers like `0`, `1`, `2`. If a developer adds a new enum constant in the middle or reorders constants, old rows may map to the wrong business value. This is especially dangerous because the database values still look valid.

Prefer string mapping or a converter with stable codes.

#### Deep dive

Ordinal can be compact, but compactness rarely justifies the migration risk for business values such as status, type, role or state.

#### Production angle

Enum corruption can affect payments, orders, permissions and workflow state. It is hard to detect because no exception is necessarily thrown.

#### Traps / caveats

- Adding enum constants at the end is safer but still fragile.
- Renaming string values also needs migration planning.
- Stable explicit codes are often best for long-lived data.

#### Optional Anki

Q: Main danger of `EnumType.ORDINAL`?
A: Enum reordering changes the meaning of existing stored numbers.

</details>

<a id="jpa-map-009"></a>

<details>
<summary><strong>JPA-MAP-009. When would you use an attribute converter, JSON mapping or a database-specific Hibernate type?</strong></summary>

#### Short answer

Use converters for simple value transformations, JSON mapping for structured document-like columns, and provider/database-specific types when standard JPA cannot express the mapping well.

#### Interview answer

An attribute converter maps between a domain type and a database column type, for example `Money` to a decimal/string pair representation, or a status code to a string. JSON mapping is useful when the database supports JSON columns and the data is naturally semi-structured. Hibernate-specific types help with database features such as arrays, JSON, inet, enums or custom SQL types.

The decision should consider querying, indexing and portability.

#### Deep dive

If the application needs to filter or join on nested JSON fields, plain entity mapping may not be enough; database indexes and native SQL may be needed.

#### Production angle

Custom mappings should have migration tests and query tests. Otherwise type changes can break reads, writes or indexes after deployment.

#### Traps / caveats

- Do not hide complex schema design inside a converter.
- JSON columns are not a replacement for relational modeling.
- Provider-specific types affect portability and upgrades.

#### Optional Anki

Q: When is an attribute converter useful?
A: When a domain value needs a simple stable conversion to one database column.

</details>

<a id="jpa-id-001"></a>

<details>
<summary><strong>JPA-ID-001. What is entity identity, and how is it different from Java object identity?</strong></summary>

#### Short answer

Entity identity is the persistent database identity; Java object identity is whether two references point to the same object instance.

#### Interview answer

In JPA, an entity is identified by its type and primary key. Two Java objects may be different instances but represent the same database row. Inside one persistence context, JPA maintains identity so repeated loads of the same entity usually return the same managed instance.

Java identity, tested with `==`, only means two references point to the same object in memory.

#### Deep dive

Detached entities make this distinction visible: two detached objects may have the same ID but be different Java instances.

#### Production angle

Confusing identity models leads to duplicate objects, broken sets/maps, wrong equality logic and merge bugs.

#### Traps / caveats

- `==` is not entity equality.
- A generated ID may be null before persist.
- Proxies complicate class and equality checks.

#### Optional Anki

Q: What defines JPA entity identity?
A: Entity type plus primary key.

</details>

<a id="jpa-id-002"></a>

<details>
<summary><strong>JPA-ID-002. What identifier generation strategies does JPA support, and how do you choose between them?</strong></summary>

#### Short answer

JPA supports identity, sequence, table and auto strategies; choose based on database support, batching, portability and operational needs.

#### Interview answer

`IDENTITY` relies on database identity columns and gets the ID on insert. `SEQUENCE` uses database sequences and can allocate IDs before insert. `TABLE` uses a table to emulate generation and is rarely preferred. `AUTO` lets the provider choose.

For high-throughput Hibernate applications, sequence-based generation is often better because it works well with batching.

#### Deep dive

ID strategy affects insert ordering, batching, index locality, sharding, external references and equality behavior before persistence.

#### Production angle

Changing ID strategy after production launch is hard because it touches schema, migrations, foreign keys and sometimes external API contracts.

#### Traps / caveats

- `AUTO` can behave differently across providers/databases.
- `IDENTITY` often reduces insert batching opportunities.
- UUIDs avoid central coordination but can hurt index locality if random.

#### Optional Anki

Q: Which common strategy works better with Hibernate insert batching?
A: `SEQUENCE`, especially with allocation/pooled optimization.

</details>

<a id="jpa-id-003"></a>

<details>
<summary><strong>JPA-ID-003. How do `IDENTITY` and `SEQUENCE` differ for batching and insert performance?</strong></summary>

#### Short answer

`IDENTITY` usually requires insert execution to obtain the ID; `SEQUENCE` can get IDs before inserts, which helps Hibernate batch statements.

#### Interview answer

With `IDENTITY`, the database generates the ID during insert. Hibernate often needs to execute the insert immediately to know the primary key. That makes batching harder.

With `SEQUENCE`, Hibernate can request identifiers before executing inserts. With allocation or pooled optimizers, it can reserve blocks of IDs and batch multiple insert statements efficiently.

#### Deep dive

The exact behavior depends on database, JDBC driver and Hibernate version, but the general interview point is that sequence generation is friendlier to batched writes.

#### Production angle

For imports or write-heavy services, the wrong ID strategy can limit throughput even when JDBC batching is enabled.

#### Traps / caveats

- Enabling batching does not guarantee batching happens.
- Flush order and entity relationships also affect batching.
- Sequence allocation size must be coordinated with database sequence increment expectations.

#### Optional Anki

Q: Why can `IDENTITY` hurt batching?
A: The insert often must execute immediately so Hibernate can obtain the generated ID.

</details>

<a id="jpa-id-004"></a>

<details>
<summary><strong>🧠 JPA-ID-004. How do sequence allocation size and pooled optimizers improve insert throughput?</strong></summary>

#### Short answer

They let Hibernate reserve a range of sequence values and assign IDs without a database round trip for every row.

#### Interview answer

If allocation size is greater than one, Hibernate can fetch a sequence value and use it to allocate a block of identifiers. Pooled optimizers reduce database sequence calls and allow Hibernate to batch inserts more effectively.

This improves throughput for write-heavy workloads, but the database sequence increment and Hibernate allocation settings must be aligned.

#### Deep dive

Gaps in IDs are normal with pooled allocation, especially after rollbacks, crashes or unused reserved values. IDs should not be treated as gapless business numbers.

#### Production angle

For high-volume imports, allocation tuning can significantly reduce database round trips and sequence contention.

#### Traps / caveats

- Do not promise gapless IDs with sequences.
- Misaligned allocation settings can create duplicate or surprising ID ranges.
- This is a performance tuning topic, not usually needed for simple CRUD apps.

#### Optional Anki

Q: What does sequence allocation size reduce?
A: The number of database sequence calls needed for inserts.

</details>

<a id="jpa-id-005"></a>

<details>
<summary><strong>JPA-ID-005. What are the trade-offs of UUIDs versus sequential numeric identifiers?</strong></summary>

#### Short answer

UUIDs are globally unique and hard to guess, but larger and often worse for index locality; sequential IDs are compact and index-friendly but easier to enumerate.

#### Interview answer

Sequential numeric IDs are simple, small and efficient for B-tree indexes. They are good primary keys in many relational schemas. Their downside is predictability and the need for central generation or database coordination.

UUIDs can be generated outside the database and are useful for distributed systems or public identifiers. Random UUIDs increase index size and can fragment indexes. Time-ordered UUID variants reduce some of that cost.

#### Deep dive

Public API identifiers and internal database primary keys do not have to be the same. Many systems use numeric primary keys internally and opaque IDs externally.

#### Production angle

ID choice affects index size, cache keys, API security, sharding, debugging and migration strategy.

#### Traps / caveats

- Random UUID primary keys can hurt write locality.
- Sequential IDs can leak business volume or allow enumeration.
- Do not use IDs as authorization.

#### Optional Anki

Q: Main database cost of random UUID primary keys?
A: Larger indexes and poorer insertion locality.

</details>

<a id="jpa-id-006"></a>

<details>
<summary><strong>JPA-ID-006. What are natural keys, surrogate keys, business keys and assigned identifiers?</strong></summary>

#### Short answer

A surrogate key is artificial, a natural/business key comes from the domain, and an assigned ID is provided by the application rather than generated by the database/provider.

#### Interview answer

A surrogate key is a technical primary key like `user_id`. A natural or business key is meaningful in the domain, like email, SKU or external order number. An assigned identifier is set by application code before persisting.

Surrogate keys are stable and simple for relationships. Business keys are useful for uniqueness and lookup, but may change or have complex rules.

#### Deep dive

Even when using surrogate primary keys, business keys often need unique constraints. They protect domain invariants that the surrogate key alone cannot express.

#### Production angle

A missing unique constraint on a business key causes duplicate accounts, orders, products or idempotency records under concurrency.

#### Traps / caveats

- Natural keys can change despite initial assumptions.
- External IDs may not be globally unique without source/tenant context.
- Business uniqueness should be enforced in the database.

#### Optional Anki

Q: Why use a surrogate key?
A: It gives a stable technical identity independent of mutable business fields.

</details>

<a id="jpa-id-007"></a>

<details>
<summary><strong>🧠 JPA-ID-007. When are composite identifiers useful, and when should they be avoided?</strong></summary>

#### Short answer

Composite IDs are useful when identity is naturally made of multiple stable columns, but they add mapping, equality and relationship complexity.

#### Interview answer

Composite identifiers appear in join tables, legacy schemas, multi-tenant keys or domain tables where several fields define identity. JPA supports approaches such as `@EmbeddedId` and `@IdClass`.

They should be avoided when a simple surrogate key plus unique constraint gives clearer relationships and simpler code.

#### Deep dive

Composite IDs affect foreign keys, repository methods, URL design, equality, caching and DTO mapping. They also make refactoring harder if part of the key changes.

#### Production angle

Legacy database integration often forces composite IDs. New application schemas should use them only when the domain or access pattern strongly justifies it.

#### Traps / caveats

- Composite key classes need correct equality.
- Mutable key fields are dangerous.
- Composite IDs often leak schema complexity into APIs.

#### Optional Anki

Q: What is a common alternative to composite primary keys?
A: A surrogate primary key plus a unique constraint over the business columns.

</details>

<a id="jpa-eq-001"></a>

<details>
<summary><strong>JPA-EQ-001. How should `equals()` and `hashCode()` be implemented for JPA entities?</strong></summary>

#### Short answer

Entity equality should be stable across lifecycle states and must not depend on mutable fields or trigger lazy loading.

#### Interview answer

There is no one perfect implementation for every entity. Common approaches use a stable business key if one exists, or use database ID carefully after it is assigned. `hashCode()` must not change while the entity is inside a `HashSet` or `HashMap`.

The implementation must also account for Hibernate proxies and should avoid traversing associations.

#### Deep dive

Generated IDs are null before persist, so ID-based equality has a lifecycle problem. Business-key equality works only if the key is immutable and truly unique.

#### Production angle

Bad equality causes disappearing set elements, duplicate collection entries, failed cache lookups and lazy-loading surprises.

#### Traps / caveats

- Do not include mutable fields in `hashCode()`.
- Do not include lazy associations.
- Be careful with `getClass()` when proxies are involved.

#### Optional Anki

Q: What must be true of fields used in entity `hashCode()`?
A: They must be stable while the entity is in hash-based collections.

</details>

<a id="jpa-eq-002"></a>

<details>
<summary><strong>JPA-EQ-002. Why are generated IDs and mutable business keys problematic for entity equality?</strong></summary>

#### Short answer

Generated IDs may be null before persist, and mutable business keys can change after the entity is placed in hash-based collections.

#### Interview answer

If equality uses a generated ID, two new unsaved entities may both have null IDs, or an entity's equality behavior may change after persist. If equality uses a mutable business key, changing that field can move the object to the wrong hash bucket.

Both cases can break sets, maps and association collections.

#### Deep dive

The safest design uses immutable business keys when available, or carefully handles generated IDs without treating all transient entities as equal.

#### Production angle

These bugs are subtle: an entity can appear to vanish from a `HashSet`, duplicate children can be inserted, or deletes can fail to match expected collection entries.

#### Traps / caveats

- Do not use database ID blindly before it is assigned.
- Do not use fields that users can edit as hash keys.
- Tests should cover entity state transitions.

#### Optional Anki

Q: Why can generated IDs break equality before persist?
A: The ID may be null until the entity is inserted or persisted.

</details>

<a id="jpa-eq-003"></a>

<details>
<summary><strong>🧠 JPA-EQ-003. How do Hibernate proxies affect `equals()`, `hashCode()` and `getClass()` checks?</strong></summary>

#### Short answer

Hibernate proxies may be subclasses or proxy objects, so strict class checks and lazy field access can break equality or trigger initialization.

#### Interview answer

A lazy association may be represented by a proxy rather than the concrete entity instance. If `equals()` uses `getClass()` strictly, a proxy and the real entity class may not compare as expected. If equality reads lazy fields or associations, it may trigger SQL or fail outside a persistence context.

Good equality logic should use stable identifiers or business keys without forcing lazy loading.

#### Deep dive

Hibernate utilities and provider-aware patterns can help, but the best solution is to keep equality simple and avoid association traversal.

#### Production angle

Proxy-sensitive equality bugs often appear in sets, caches, DTO mapping, serialization and authorization checks.

#### Traps / caveats

- `instanceof` and `getClass()` both have trade-offs.
- Avoid lazy associations in equality.
- Test equality with proxied references, not only new objects.

#### Optional Anki

Q: Why can `getClass()` be risky in entity equality?
A: Hibernate may compare a proxy subclass with the real entity class.

</details>

<a id="jpa-eq-004"></a>

<details>
<summary><strong>JPA-EQ-004. Why are Lombok `@Data`, `@EqualsAndHashCode` and `@ToString` risky on entities?</strong></summary>

#### Short answer

They may include mutable fields and lazy associations in generated methods, causing broken equality, recursion, lazy loads or huge logs.

#### Interview answer

`@Data` generates getters, setters, `equals()`, `hashCode()` and `toString()`. On entities this is dangerous because generated equality may include IDs, mutable fields or associations. Generated `toString()` may traverse bidirectional relationships or initialize lazy collections.

For entities, methods should be written deliberately or Lombok should be configured narrowly.

#### Deep dive

The problem is not Lombok itself; the problem is generic code generation on classes with persistence lifecycle, proxies and lazy associations.

#### Production angle

Bad generated methods can trigger thousands of SQL queries from logging, stack traces, debugging or JSON serialization.

#### Traps / caveats

- Exclude lazy associations from `toString()`.
- Avoid generated equality over all fields.
- Do not expose public setters for every invariant by habit.

#### Optional Anki

Q: Why is Lombok `@Data` risky on JPA entities?
A: It generates equality and string methods that may include mutable fields and lazy associations.

</details>

<a id="jpa-eq-005"></a>

<details>
<summary><strong>JPA-EQ-005. How do you design entities to protect invariants without fighting JPA?</strong></summary>

#### Short answer

Keep JPA requirements minimal, but expose domain methods that enforce valid state instead of uncontrolled setters.

#### Interview answer

Entities can have protected no-arg constructors for JPA and public constructors or factories for valid creation. Instead of public setters for everything, expose methods such as `confirm()`, `cancel()`, `changeAddress()` or `addLine()` that enforce business rules and maintain both sides of associations.

This keeps the model meaningful while still allowing Hibernate to persist it.

#### Deep dive

Field access helps because Hibernate can set fields directly while application code uses controlled methods. Invariants that must be globally enforced still need database constraints or transactional logic.

#### Production angle

Entity methods make state transitions easier to audit, test and protect from accidental invalid combinations.

#### Traps / caveats

- Do not put service dependencies into entities.
- Do not rely only on entity methods for cross-row invariants.
- Keep entity logic focused on local domain state.

#### Optional Anki

Q: How can entities protect invariants?
A: Use controlled domain methods instead of unrestricted setters.

</details>
