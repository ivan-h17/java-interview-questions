# Dirty checking, flush and transaction boundaries

---

<a id="jpa-flush-001"></a>

<details>
<summary><strong>JPA-FLUSH-001. What is dirty checking in Hibernate?</strong></summary>

#### Short answer

Dirty checking is Hibernate's ability to detect changes to managed entities and generate SQL updates during flush.

#### Interview answer

When an entity is managed, Hibernate tracks its loaded state. If application code changes a field, it usually does not need to call an explicit update method. At flush time, Hibernate compares current state with tracked state and issues SQL for changed entities.

This is convenient, but it means modifying a managed entity has persistence consequences.

#### Deep dive

Dirty checking applies to managed entities inside a persistence context. Detached entities are not checked unless their state is merged into a managed instance.

#### Production angle

Unexpected updates often come from helper methods, mappers, logging/debug code or "read" service methods mutating managed entities.

#### Traps / caveats

- Dirty checking is not triggered for detached entities.
- Updates may happen on flush, not immediately when a setter is called.
- Mutable embedded values and collections need careful handling.

#### Optional Anki

Q: When does Hibernate usually generate SQL for dirty managed entities?
A: During flush.

</details>

<a id="jpa-flush-002"></a>

<details>
<summary><strong>🧠 JPA-FLUSH-002. How can bytecode enhancement change dirty tracking behavior?</strong></summary>

#### Short answer

Bytecode enhancement can let Hibernate track changed attributes more directly instead of relying only on snapshot comparison.

#### Interview answer

By default, Hibernate can compare an entity's current state with a snapshot taken when it was loaded. With bytecode enhancement, entity classes can be instrumented so Hibernate knows which fields were changed. This can improve dirty tracking and enable advanced lazy attribute behavior.

It is an optimization and provider-specific feature, not something most interview answers should depend on.

#### Deep dive

Enhancement can happen at build time or runtime depending on setup. It must be configured and tested because it changes how entity classes are instrumented.

#### Production angle

For large entities or high-throughput systems, enhanced dirty tracking can reduce overhead, but it adds build/configuration complexity.

#### Traps / caveats

- Do not assume enhancement is enabled.
- It is Hibernate-specific.
- Always validate behavior after framework upgrades.

#### Optional Anki

Q: What does Hibernate bytecode enhancement help with?
A: More direct dirty tracking and some advanced lazy-loading features.

</details>

<a id="jpa-flush-003"></a>

<details>
<summary><strong>JPA-FLUSH-003. How does flush differ from commit?</strong></summary>

#### Short answer

Flush sends pending SQL to the database; commit ends the transaction and makes changes durable.

#### Interview answer

Flush synchronizes the persistence context with the database by executing pending inserts, updates and deletes. The transaction is still active afterward. Commit is the final transaction operation that makes the changes permanent.

Hibernate may flush before commit, for example before executing a query that needs consistent results.

#### Deep dive

After flush, constraints can fail even before commit. If the transaction later rolls back, flushed changes are still undone by the database.

#### Production angle

Knowing the difference helps debug constraint violations, unexpected SQL timing and `saveAndFlush()` behavior.

#### Traps / caveats

- Flush does not mean commit.
- Flush can happen automatically.
- A failed flush usually marks the transaction for rollback.

#### Optional Anki

Q: Does flush commit the transaction?
A: No. It sends SQL within the still-active transaction.

</details>

<a id="jpa-flush-004"></a>

<details>
<summary><strong>JPA-FLUSH-004. Why can Hibernate flush before transaction commit or before a query?</strong></summary>

#### Short answer

Hibernate may flush early so database queries see changes already made in the persistence context.

#### Interview answer

With automatic flush mode, Hibernate tries to keep query results consistent with pending entity changes. If a query might depend on tables affected by pending inserts, updates or deletes, Hibernate can flush before executing that query.

This means SQL can appear earlier than the developer expects.

#### Deep dive

Flush timing depends on flush mode, query type, transaction state and provider behavior. It is not limited to commit time.

#### Production angle

An innocent-looking read query can trigger pending writes and expose constraint violations earlier in the method.

#### Traps / caveats

- A query can cause SQL writes first.
- Manual flush mode can hide pending changes from queries.
- Early flush does not make changes durable until commit.

#### Optional Anki

Q: Why can a select query trigger a flush?
A: To make query results consistent with pending persistence-context changes.

</details>

<a id="jpa-flush-005"></a>

<details>
<summary><strong>🧠 JPA-FLUSH-005. What are common flush modes, and when is manual flush risky?</strong></summary>

#### Short answer

Common modes include automatic and commit-oriented flushing; manual flush gives control but can make queries see stale data.

#### Interview answer

`AUTO` lets the provider flush before commit and sometimes before queries. `COMMIT` delays flushing closer to transaction commit, though provider behavior can vary. Hibernate also has manual modes where application code controls flushing explicitly.

Manual flush is risky because developers must remember when synchronization is required.

#### Deep dive

Read-only transactions or query hints may reduce dirty checking or flushing, but they are not a substitute for clear code that avoids mutation in read paths.

#### Production angle

Manual flush can improve batch performance in expert code, but it can also cause stale reads, late failures and confusing tests.

#### Traps / caveats

- Flush mode behavior is provider-sensitive.
- Manual flush should be localized and tested.
- Do not use flush mode to hide bad transaction design.

#### Optional Anki

Q: What is the default practical expectation with automatic flush?
A: Hibernate may flush before commit and before some queries.

</details>

<a id="jpa-flush-006"></a>

<details>
<summary><strong>JPA-FLUSH-006. What are transactional write-behind and SQL statement ordering?</strong></summary>

#### Short answer

Hibernate queues entity changes and writes them later during flush, ordering SQL to respect dependencies and improve batching.

#### Interview answer

When managed entities change, Hibernate does not always execute SQL immediately. It collects actions in the persistence context and flushes them as a unit. This is transactional write-behind.

During flush, Hibernate orders inserts, updates and deletes to satisfy foreign keys where possible and improve batching. However, complex relationships and constraints can still produce ordering issues.

#### Deep dive

Write-behind is why `persist()` may not immediately insert a row and why constraint errors can appear later than the line that changed the entity.

#### Production angle

Understanding write-behind helps debug foreign key failures, batch behavior and unexpected SQL order.

#### Traps / caveats

- Statement ordering is not magic for every schema design.
- Database constraints still decide validity.
- Early flush can reveal queued changes.

#### Optional Anki

Q: What is transactional write-behind?
A: Hibernate queues entity changes and executes SQL later during flush.

</details>

<a id="jpa-flush-007"></a>

<details>
<summary><strong>JPA-FLUSH-007. When is explicit `flush()` useful, and when does it hurt performance?</strong></summary>

#### Short answer

Explicit flush is useful to force SQL and catch errors at a known point; excessive flushing hurts batching and adds round trips.

#### Interview answer

Calling `flush()` can be useful before returning from a method that must detect constraint violations early, or inside batch processing before `clear()`. It can also help tests verify actual database behavior.

It hurts performance when called after every entity change because Hibernate loses opportunities to batch and reorder statements.

#### Deep dive

`flush()` should usually be a deliberate boundary, not a habit after `save()`.

#### Production angle

Over-flushing can turn a batch job into thousands of small database interactions and degrade throughput.

#### Traps / caveats

- `flush()` does not commit.
- `saveAndFlush()` is not "more correct" than `save()`.
- Flushing can trigger constraint exceptions.

#### Optional Anki

Q: Why can excessive flush calls hurt performance?
A: They reduce batching and force more database synchronization.

</details>

<a id="jpa-flush-008"></a>

<details>
<summary><strong>🧠 JPA-FLUSH-008. What are the pros and cons of Hibernate `@DynamicUpdate`?</strong></summary>

#### Short answer

`@DynamicUpdate` updates only changed columns, but can reduce statement reuse and should not be applied blindly.

#### Interview answer

Normally Hibernate may generate update SQL that includes many mapped columns. With `@DynamicUpdate`, Hibernate creates SQL containing only changed columns. This can help when rows are wide, columns have triggers, or concurrent partial updates matter.

The downside is more SQL variants, less statement plan reuse and extra dirty-column calculation complexity.

#### Deep dive

`@DynamicUpdate` is Hibernate-specific. It should be based on measurement and real update patterns.

#### Production angle

It may help write-heavy systems with wide tables, but can hurt if it creates too many unique SQL shapes.

#### Traps / caveats

- It is not portable JPA.
- It does not replace optimistic locking.
- Measure before and after.

#### Optional Anki

Q: What does `@DynamicUpdate` change?
A: Hibernate generates update SQL with only changed columns.

</details>

<a id="jpa-flush-009"></a>

<details>
<summary><strong>JPA-FLUSH-009. How can modifying a managed entity in a read path still produce an update?</strong></summary>

#### Short answer

If the entity is managed, Hibernate tracks the mutation and may flush it even if the method was intended as a read.

#### Interview answer

Inside a transaction, a loaded entity is managed. If code normalizes a field, calls a setter, updates a timestamp or mutates a collection, dirty checking can detect that change and issue an update on flush.

This can happen in service methods, mappers, validators or helper methods that were not intended to write.

#### Deep dive

`@Transactional(readOnly = true)` may reduce flush behavior depending on framework/provider settings, but it is not a license to mutate managed entities.

#### Production angle

Unexpected writes from read endpoints can invalidate caches, trigger audit events, cause lock contention and surprise users.

#### Traps / caveats

- Avoid entity mutation during DTO mapping.
- Be careful with lazy collection initialization and helper methods.
- Read-only transaction settings are not a complete guardrail.

#### Optional Anki

Q: Why can a read method update the database?
A: It modified a managed entity and dirty checking flushed the change.

</details>

<a id="jpa-flush-010"></a>

<details>
<summary><strong>JPA-FLUSH-010. What is the difference between a read-only transaction and an immutable entity?</strong></summary>

#### Short answer

A read-only transaction is a transaction hint/setting; an immutable entity is a mapping/design statement that the entity should not be updated.

#### Interview answer

`@Transactional(readOnly = true)` tells Spring and sometimes Hibernate/database that the transaction is intended for reads. It can optimize flush behavior, but exact effects depend on configuration.

An immutable entity or Hibernate `@Immutable` marks entity state as not meant to be changed. This is more about mapping and domain behavior than transaction intent.

#### Deep dive

A read-only transaction can still load managed entities. Mutating them is a bug even if no update is flushed.

#### Production angle

Use read-only transactions for read paths, but also design code to avoid mutation and use projections where possible.

#### Traps / caveats

- Read-only does not replace access control.
- It does not make Java objects immutable.
- Provider behavior can differ.

#### Optional Anki

Q: Does `readOnly = true` make loaded entities immutable?
A: No.

</details>

<a id="jpa-flush-011"></a>

<details>
<summary><strong>JPA-FLUSH-011. Why do bulk JPQL updates bypass the persistence context, and how do you handle stale managed entities afterward?</strong></summary>

#### Short answer

Bulk JPQL operates directly in the database, so already managed entities are not automatically updated in memory; clear or refresh the context afterward.

#### Interview answer

JPQL bulk update/delete statements are translated to SQL and executed against rows. They do not load each entity, apply lifecycle callbacks or update every managed instance in the persistence context.

If the same transaction already loaded affected entities, those objects may now be stale. The usual fix is to flush before the bulk operation and clear or refresh afterward.

#### Deep dive

Bulk operations are efficient but bypass normal entity-level behavior such as dirty checking, some cascades and optimistic version handling unless explicitly handled.

#### Production angle

Stale managed entities after bulk updates can make APIs return old values or overwrite new database state later in the transaction.

#### Traps / caveats

- Flush pending changes before bulk updates.
- Clear the persistence context after bulk updates when affected entities may be loaded.
- Do not assume entity listeners run for bulk updates.

#### Optional Anki

Q: Why can bulk JPQL leave entities stale?
A: It updates database rows directly without updating managed objects in the persistence context.

</details>

<a id="jpa-flush-012"></a>

<details>
<summary><strong>JPA-FLUSH-012. How would you debug unexpected `INSERT`, `UPDATE` or `DELETE` statements?</strong></summary>

#### Short answer

Inspect SQL logs, transaction boundaries, dirty entity mutations, cascades, flush timing and entity mappings.

#### Interview answer

First enable safe SQL logging or statement counting in a lower environment. Identify when the SQL appears: method entry, query execution, flush or commit. Then inspect managed entities, setters, mappers, callbacks, cascades, orphan removal and collection changes.

For deletes, check cascade configuration and relationship ownership. For updates, check dirty checking and mutable values.

#### Deep dive

Hibernate statistics, datasource proxies, tests with explicit `flush()` and breakpoints in setters/callbacks can help locate the mutation.

#### Production angle

Unexpected SQL can cause data loss, audit noise, lock contention, cache invalidation and performance regressions.

#### Traps / caveats

- Logging SQL with parameters can leak sensitive data.
- The line that triggers flush may not be the line that changed the entity.
- Cascades and orphan removal can amplify one operation.

#### Optional Anki

Q: What is the first thing to identify for unexpected SQL?
A: When it is flushed and which managed entity or cascade caused it.

</details>

<a id="jpa-tx-001"></a>

<details>
<summary><strong>JPA-TX-001. Where should JPA transaction boundaries usually be placed?</strong></summary>

#### Short answer

Usually at the service/application use-case layer, where the full business operation is known.

#### Interview answer

A transaction should cover the database work that must commit or roll back together. In Spring, this is often a service method because it coordinates repositories, domain logic and consistency rules.

Repositories are often too fine-grained; controllers are often too broad and may include serialization or external calls.

#### Deep dive

Good boundaries include required database changes but avoid slow network calls, user interaction and unrelated work while holding a connection.

#### Production angle

Bad boundaries cause partial writes, lazy loading leaks, long lock waits and connection pool exhaustion.

#### Traps / caveats

- `@Transactional` on private/self-invoked methods may not work with proxy-based Spring AOP.
- Do not put transactions around entire web requests by default.
- External side effects need separate reliability patterns.

#### Optional Anki

Q: Why are transactions often placed at service methods?
A: Service methods usually represent the full business unit of work.

</details>

<a id="jpa-tx-002"></a>

<details>
<summary><strong>JPA-TX-002. How do database isolation, persistence context state and JPA lock modes differ?</strong></summary>

#### Short answer

Isolation is a database transaction rule, persistence context state is Hibernate's in-memory unit of work, and JPA lock modes request specific concurrency control for entities.

#### Interview answer

Database isolation controls what concurrent transactions can observe and which anomalies are possible. The persistence context controls managed entity identity, dirty checking and first-level cache behavior. JPA lock modes such as optimistic or pessimistic locks add entity-level concurrency controls on top of the transaction.

They interact, but they are not the same thing.

#### Deep dive

Optimistic locking detects conflicting updates through a version column. Pessimistic locking asks the database to acquire locks. Isolation level defines broader visibility and concurrency behavior.

#### Production angle

Choosing the wrong mechanism can cause lost updates, deadlocks, unnecessary blocking or false confidence about consistency.

#### Traps / caveats

- Optimistic locking does not make all reads serializable.
- First-level cache can return stale data inside a transaction.
- Database behavior differs by vendor.

#### Optional Anki

Q: Is JPA optimistic locking the same as database isolation?
A: No. It is an entity version conflict-detection mechanism.

</details>

<a id="jpa-tx-003"></a>

<details>
<summary><strong>🧠 JPA-TX-003. Why can `REQUIRES_NEW` inside an existing transaction exhaust the connection pool?</strong></summary>

#### Short answer

`REQUIRES_NEW` suspends the outer transaction and starts a new one, often needing an additional database connection while the outer connection is still held.

#### Interview answer

If a method with an active transaction calls another method using `REQUIRES_NEW`, Spring suspends the outer transaction and opens a separate transaction for the inner work. The outer transaction may still hold its connection. Under concurrency, each request can need more than one connection, exhausting the pool.

This is common in audit logging, outbox-like code or nested service calls used without capacity planning.

#### Deep dive

The issue is worse when outer transactions are long or many nested `REQUIRES_NEW` calls happen in loops.

#### Production angle

Pool exhaustion appears as request latency spikes, timeouts and blocked threads waiting for connections.

#### Traps / caveats

- `REQUIRES_NEW` is not free isolation.
- Avoid it inside large loops.
- Size pools and transactions based on worst-case nested connection use.

#### Optional Anki

Q: Why can `REQUIRES_NEW` need another connection?
A: The outer transaction is suspended while still holding its resources, and the inner transaction starts separately.

</details>
