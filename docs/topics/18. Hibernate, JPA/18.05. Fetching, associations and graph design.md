# Fetching, associations and graph design

---

<a id="jpa-fetch-001"></a>

<details>
<summary><strong>JPA-FETCH-001. What is the N+1 query problem?</strong></summary>

#### Short answer

N+1 means one query loads parent rows and then one extra query is executed for each parent to load related data.

#### Interview answer

For example, a service loads 100 orders with one query. Then while mapping DTOs it accesses `order.getCustomer()` or `order.getLines()` for each order. If those associations are lazy, Hibernate may execute 100 more queries. That is N+1.

The problem is not lazy loading itself; it is accessing lazily loaded data one row at a time without an appropriate fetch plan.

#### Deep dive

N+1 can happen with entities, collections, DTO mappers, JSON serializers, logging and templates. It also happens in loops over repository results.

#### Production angle

N+1 often looks fine in development with small data but becomes severe under production cardinality.

#### Traps / caveats

- EAGER is not a universal fix.
- Caching can hide N+1 during tests.
- Count queries and pagination can have separate performance problems.

#### Optional Anki

Q: What is N+1 in Hibernate?
A: One query for parents plus one query per parent for related data.

</details>

---

<a id="jpa-fetch-002"></a>

<details>
<summary><strong>JPA-FETCH-002. How would you detect N+1 queries in code, tests or production?</strong></summary>

#### Short answer

Count SQL statements, inspect logs/traces, use Hibernate statistics or datasource proxies, and test query counts for important endpoints.

#### Interview answer

In development, enable SQL logging or a datasource proxy and look for repeated similar selects. In tests, assert the number of SQL statements for a repository/service method. In production, use traces, database monitoring, query fingerprints and Hibernate metrics to spot repeated queries per request.

The key is correlating SQL back to the endpoint or service method.

#### Deep dive

N+1 detection should be part of performance-sensitive repository tests. It is easier to prevent with a query budget than to debug during an incident.

#### Production angle

N+1 causes high database CPU, network chatter, connection pool pressure and p95/p99 latency spikes.

#### Traps / caveats

- Do not enable verbose parameter SQL logs with sensitive data in production.
- Test data must include multiple parent rows.
- The serializer or mapper may be the trigger, not the repository call itself.

#### Optional Anki

Q: What should a test use to catch N+1?
A: SQL statement count with realistic parent/child data.

</details>

<a id="jpa-fetch-003"></a>

<details>
<summary><strong>JPA-FETCH-003. How can fetch joins, entity graphs, batch fetching and projections solve different N+1 cases?</strong></summary>

#### Short answer

Fetch joins load associations in one query, entity graphs define fetch plans, batch fetching groups lazy loads, and projections avoid loading full entities.

#### Interview answer

Use `JOIN FETCH` when a specific query always needs a related entity or collection. Use entity graphs when you want a reusable or dynamic fetch plan without changing query text too much. Use batch fetching when lazy loading is acceptable but should be grouped into fewer queries. Use projections when the endpoint only needs selected fields.

The best solution depends on response shape, pagination, cardinality and whether entities are needed.

#### Deep dive

Collection fetch joins can multiply rows and break pagination. Projections are often better for list endpoints. Batch fetching is useful for many-to-one or collections accessed across several parents.

#### Production angle

Choosing the wrong fix can trade N+1 for over-fetching, duplicates or memory pressure.

#### Traps / caveats

- Do not `JOIN FETCH` every association.
- Entity graphs can still fetch too much.
- Projections can still produce N+1 if they navigate nested lazy associations badly.

#### Optional Anki

Q: What is often best for read-only list endpoints?
A: DTO projections or carefully designed query DTOs.

</details>

<a id="jpa-fetch-004"></a>

<details>
<summary><strong>JPA-FETCH-004. What is the difference between lazy and eager loading?</strong></summary>

#### Short answer

Lazy loading loads related data on demand; eager loading loads it immediately with the owning entity.

#### Interview answer

Lazy associations are initialized only when accessed, usually through a proxy or collection wrapper. Eager associations are loaded when the entity is loaded, either by join or additional selects depending on provider/query.

Lazy is generally preferred for associations because it avoids loading data that might not be needed. The actual query should decide the fetch plan for each use case.

#### Deep dive

JPA defaults are not ideal: many-to-one and one-to-one are eager by default, while collections are lazy by default. Many teams explicitly make most associations lazy and fetch intentionally.

#### Production angle

Eager defaults can create huge object graphs and slow endpoints even if code never uses the data.

#### Traps / caveats

- Lazy loading needs an open persistence context.
- Eager loading can still produce multiple queries.
- Fetch type is a default, not a full query design strategy.

#### Optional Anki

Q: Which fetch style is usually safer as a default for associations?
A: Lazy, with explicit fetch plans per use case.

</details>

<a id="jpa-fetch-005"></a>

<details>
<summary><strong>JPA-FETCH-005. What is `LazyInitializationException`, and how do you avoid it correctly?</strong></summary>

#### Short answer

It happens when Hibernate tries to initialize lazy data after the persistence context is closed; avoid it by fetching and mapping required data inside the transaction.

#### Interview answer

`LazyInitializationException` is a symptom of accessing lazy associations outside an active session. Correct fixes include query-specific fetch joins, entity graphs, DTO projections or mapping to DTOs inside a transactional service.

Making everything eager or enabling OSIV just to hide the exception often creates worse performance and boundary problems.

#### Deep dive

The service layer should define what data the caller needs. Controllers and serializers should not discover missing data by triggering lazy SQL.

#### Production angle

This exception often appears after disabling OSIV, moving DTO mapping outside a transaction or returning entities directly from controllers.

#### Traps / caveats

- Do not fix by calling lazy getters randomly.
- Do not expose entities to JSON serialization.
- Do not use EAGER everywhere.

#### Optional Anki

Q: Correct way to avoid lazy initialization failures?
A: Load and map required data inside a controlled transaction/fetch plan.

</details>

<a id="jpa-fetch-006"></a>

<details>
<summary><strong>JPA-FETCH-006. What is Open Session in View, and why is it controversial?</strong></summary>

#### Short answer

OSIV keeps the persistence context open during web view/response rendering; it prevents some lazy errors but can hide inefficient database access.

#### Interview answer

Open Session in View lets controllers or serializers access lazy associations after the service transaction has returned. This avoids `LazyInitializationException` in some cases, but it moves database queries outside the service boundary and makes endpoint SQL harder to reason about.

Many production APIs disable OSIV and require services to return fully prepared DTOs.

#### Deep dive

OSIV does not necessarily keep one database transaction open the whole time, but it does keep persistence access available longer than the business transaction.

#### Production angle

OSIV can cause unexpected queries during JSON serialization, connection usage after service logic and inconsistent performance.

#### Traps / caveats

- OSIV hides missing fetch plans.
- It can make read paths depend on serialization shape.
- Disabling it requires fixing service DTO preparation.

#### Optional Anki

Q: Why is OSIV risky for REST APIs?
A: It can trigger database access during controller/serialization instead of inside the service use case.

</details>

<a id="jpa-fetch-007"></a>

<details>
<summary><strong>JPA-FETCH-007. How does `JOIN FETCH` work, and what are its risks?</strong></summary>

#### Short answer

`JOIN FETCH` tells JPA to load an association together with the root entity, but it can duplicate rows, over-fetch and break pagination with collections.

#### Interview answer

A normal join filters or combines data for the query. A fetch join also initializes the association in the returned entity graph. It is useful when the use case definitely needs that association.

The risk is using it everywhere. Fetch joining large collections or many associations can create Cartesian products, duplicate root rows and large memory usage.

#### Deep dive

Fetch joins are often good for many-to-one associations or detail screens, but collection fetch joins need careful cardinality analysis.

#### Production angle

A fetch join added to fix N+1 can become a slow endpoint when production data has many child rows per parent.

#### Traps / caveats

- Collection fetch join plus pagination is dangerous.
- Multiple collection fetch joins can explode result size.
- `distinct` in JPQL may not solve the database work.

#### Optional Anki

Q: What does `JOIN FETCH` initialize?
A: The joined association in the returned entity graph.

</details>

<a id="jpa-fetch-008"></a>

<details>
<summary><strong>JPA-FETCH-008. Why can collection fetch joins break pagination or produce duplicates?</strong></summary>

#### Short answer

A collection join returns one SQL row per parent-child combination, so database pagination applies to multiplied rows, not unique parent entities.

#### Interview answer

If one order has ten lines, a join fetch returns ten SQL rows for that order. Applying `limit` and `offset` at the SQL level can page over joined rows instead of distinct orders. Hibernate may deduplicate entities in memory, but the page can have fewer roots or wrong boundaries.

The usual fix is two-step loading: page root IDs first, then fetch associations for those IDs.

#### Deep dive

DTO projections, keyset pagination, batch fetching or separate detail queries are often better than one giant fetch join for list pages.

#### Production angle

This bug shows up as missing rows, duplicate-looking results, unstable pages or slow memory-heavy queries.

#### Traps / caveats

- JPQL `distinct` does not always fix pagination semantics.
- Sorting by child fields changes meaning.
- Count queries may also become expensive.

#### Optional Anki

Q: Why does collection fetch join distort pages?
A: The SQL result has one row per parent-child pair, not one row per parent.

</details>

<a id="jpa-fetch-009"></a>

<details>
<summary><strong>JPA-FETCH-009. How does batch fetching with `@BatchSize` or `hibernate.default_batch_fetch_size` work?</strong></summary>

#### Short answer

Batch fetching groups lazy association loads for multiple entities into fewer `IN` queries.

#### Interview answer

Instead of loading one lazy association at a time, Hibernate can collect several pending proxies or collections and initialize them with a query like `where id in (...)`. `@BatchSize` configures this for specific entities/associations; `hibernate.default_batch_fetch_size` provides a default.

It reduces N+1 without always using join fetches.

#### Deep dive

Batch fetching is useful when code naturally accesses lazy associations for a set of already loaded entities. It does not reduce data volume; it reduces query count.

#### Production angle

It is often a pragmatic default for many-to-one lookups and moderate collections, especially in APIs with varied fetch needs.

#### Traps / caveats

- Very large batch sizes can create huge `IN` clauses.
- It still loads entities, not custom DTO shapes.
- It may hide poor query design if overused.

#### Optional Anki

Q: What problem does Hibernate batch fetching reduce?
A: Query count from lazy association initialization.

</details>

<a id="jpa-fetch-010"></a>

<details>
<summary><strong>🧠 JPA-FETCH-010. What is subselect fetching, and when can it help?</strong></summary>

#### Short answer

Subselect fetching initializes collections for a group of previously loaded parents using a subquery based on the original parent query.

#### Interview answer

With subselect fetching, Hibernate can load collections for all parent entities returned by a previous query using one secondary query. It can reduce N+1 for collections when a page or result set of parents needs their children.

It is provider-specific and should be tested with real query shapes.

#### Deep dive

Subselect fetching can be efficient when many parents from one query need the same collection. It can be poor if the original parent query is broad or if only a few collections are accessed.

#### Production angle

It is a tuning tool for specific access patterns, not a default replacement for query design.

#### Traps / caveats

- Hibernate-specific.
- Can fetch more child data than expected.
- Must be tested with pagination and filters.

#### Optional Anki

Q: What does subselect fetching try to avoid?
A: One collection query per parent.

</details>

<a id="jpa-fetch-011"></a>

<details>
<summary><strong>🧠 JPA-FETCH-011. What are entity graphs, `fetchgraph` and `loadgraph`?</strong></summary>

#### Short answer

Entity graphs define which attributes should be fetched for an operation; `fetchgraph` is stricter, while `loadgraph` adds to default eager behavior.

#### Interview answer

An entity graph is a JPA mechanism for specifying a fetch plan separately from query text. It can be named or built dynamically. `fetchgraph` treats listed attributes as the fetch graph and leaves unspecified attributes lazy where possible. `loadgraph` treats listed attributes as additional eager attributes while respecting default eager mappings.

Entity graphs are useful when the same query needs different fetch plans.

#### Deep dive

Provider behavior and default eager mappings matter. Entity graphs are not magic; they can still over-fetch or produce complex SQL.

#### Production angle

They are useful in Spring Data JPA with `@EntityGraph`, but should be covered by query-count tests.

#### Traps / caveats

- Graphs can become hard to reason about if reused broadly.
- They do not solve bad pagination automatically.
- Defaults still matter with `loadgraph`.

#### Optional Anki

Q: What does an entity graph define?
A: A fetch plan for attributes of an entity.

</details>

<a id="jpa-fetch-012"></a>

<details>
<summary><strong>JPA-FETCH-012. How would you design fetch plans for list pages versus detail pages?</strong></summary>

#### Short answer

List pages should fetch small, bounded summaries; detail pages can fetch a richer graph for one root entity.

#### Interview answer

For list endpoints, avoid full entity graphs and large collections. Use projections or fetch only many-to-one data needed for the row. Keep pagination stable and count queries cheap.

For detail endpoints, loading one aggregate with selected associations may be reasonable using fetch joins, entity graphs or separate queries.

#### Deep dive

Different API shapes should have different query shapes. One repository method should not try to serve every screen.

#### Production angle

Most performance regressions happen when a list endpoint starts returning detail-level data for many rows.

#### Traps / caveats

- Do not fetch collections for every list row by default.
- Avoid entity serialization as a fetch-plan strategy.
- Keep query budgets per endpoint.

#### Optional Anki

Q: What should list endpoints usually return?
A: Bounded DTO/projection summaries, not full entity graphs.

</details>

<a id="jpa-fetch-013"></a>

<details>
<summary><strong>JPA-FETCH-013. When should you use DTO projections instead of entities?</strong></summary>

#### Short answer

Use DTO projections when the use case is read-only and needs a specific subset or shape of data.

#### Interview answer

Entities are useful when you need managed state and domain changes. For read APIs, list pages, reports and search results, DTO projections can fetch only the required columns and avoid lazy-loading traps.

They make the query shape explicit and reduce memory used by the persistence context.

#### Deep dive

DTO projections can be JPQL constructor expressions, Spring Data interface/class projections, native mappings or query-tool projections.

#### Production angle

Projection-based reads often reduce database load, serialization size and heap pressure.

#### Traps / caveats

- Projections are not managed entities.
- Nested projections can still generate joins or extra queries.
- Keep projection constructors stable and tested.

#### Optional Anki

Q: When are entities the wrong read model?
A: When the endpoint only needs a small read-only data shape.

</details>

<a id="jpa-fetch-014"></a>

<details>
<summary><strong>JPA-FETCH-014. How do you avoid Cartesian product explosions in fetch joins?</strong></summary>

#### Short answer

Avoid fetching multiple large collections in one query; split queries, use projections, batch fetching or fetch details separately.

#### Interview answer

If a query fetch joins several collections, SQL rows multiply by the number of child combinations. For example, an order with 10 lines and 5 comments can produce 50 joined rows. Add more collections and the result grows quickly.

The fix is to fetch only what the use case needs, often in multiple targeted queries.

#### Deep dive

Entity deduplication in Hibernate does not remove the database work, network transfer or memory pressure caused by the multiplied result set.

#### Production angle

Cartesian explosions can turn a small endpoint change into a database and heap incident.

#### Traps / caveats

- `distinct` may hide duplicates in Java but not the SQL cost.
- Multiple bags have additional Hibernate limitations.
- Large graphs are rarely appropriate for list endpoints.

#### Optional Anki

Q: Why are multiple collection fetch joins risky?
A: They multiply SQL rows by child combinations.

</details>

<a id="jpa-fetch-015"></a>

<details>
<summary><strong>🧠 JPA-FETCH-015. What is `MultipleBagFetchException`, and how do you avoid it?</strong></summary>

#### Short answer

It is a Hibernate exception thrown when trying to fetch multiple bag collections at once; avoid it by changing collection mapping or splitting fetches.

#### Interview answer

A bag is an unordered collection that may allow duplicates and has no index column. Hibernate cannot reliably fetch multiple bags in one query because the SQL result cannot be disambiguated safely.

Solutions include using `Set`, using indexed `List` with `@OrderColumn`, avoiding multiple collection fetch joins, or loading collections separately with batch/subselect fetching.

#### Deep dive

Changing `List` to `Set` is not just a technical fix; it changes collection semantics and requires correct equality.

#### Production angle

This usually appears after adding a new collection to an entity graph or detail endpoint.

#### Traps / caveats

- Do not switch to `Set` if ordering or duplicates matter.
- Multiple collection fetches can still be slow even without this exception.
- Test realistic data sizes.

#### Optional Anki

Q: Common fix for multiple bag fetch?
A: Split fetches or change collection semantics deliberately.

</details>

<a id="jpa-fetch-016"></a>

<details>
<summary><strong>🧠 JPA-FETCH-016. What is the difference between a bag, list and set in Hibernate collections?</strong></summary>

#### Short answer

A bag is unordered and can contain duplicates; a list has order/index semantics; a set enforces uniqueness based on equality.

#### Interview answer

In Hibernate, a plain `List` without an order column can behave like a bag. A true ordered list usually uses an order column or ordering. A `Set` relies on `equals()` and `hashCode()` to avoid duplicates.

The collection type affects SQL, fetch joins, duplicate handling and update behavior.

#### Deep dive

Using `Set` to avoid `MultipleBagFetchException` only makes sense if uniqueness is part of the domain model and entity equality is correct.

#### Production angle

Wrong collection semantics cause duplicate children, unstable ordering, excessive updates or hard-to-debug fetch exceptions.

#### Traps / caveats

- `@OrderBy` sorts by SQL expression; `@OrderColumn` persists list order.
- `Set` needs stable equality.
- Bags can be problematic with multiple fetch joins.

#### Optional Anki

Q: What does `Set` association correctness depend on?
A: Correct and stable `equals()` / `hashCode()`.

</details>

<a id="jpa-fetch-017"></a>

<details>
<summary><strong>🧠 JPA-FETCH-017. How do lazy proxies affect `equals()`, `toString()`, logging and JSON serialization?</strong></summary>

#### Short answer

Accessing proxy fields can trigger SQL or fail outside a persistence context, and generated methods may accidentally traverse lazy graphs.

#### Interview answer

Lazy proxies stand in for entities or collections until accessed. If `equals()`, `toString()`, logging, debugger views or Jackson serialization touches lazy properties, Hibernate may issue extra SQL or throw `LazyInitializationException`.

Methods on entities should avoid traversing associations unless the behavior is deliberate.

#### Deep dive

Lombok-generated `toString()` and equality are common causes because they include fields automatically.

#### Production angle

A harmless log statement can become thousands of queries or expose sensitive data from associated entities.

#### Traps / caveats

- Exclude associations from `toString()`.
- Do not serialize entities directly.
- Keep equality based on stable identifiers/keys, not graph traversal.

#### Optional Anki

Q: Why can entity `toString()` be dangerous?
A: It may traverse lazy associations and trigger SQL or recursion.

</details>

<a id="jpa-fetch-018"></a>

<details>
<summary><strong>JPA-FETCH-018. How would you troubleshoot a slow endpoint caused by Hibernate fetching?</strong></summary>

#### Short answer

Correlate the endpoint to SQL, count queries and rows, inspect fetch plans and compare the actual data shape to what the API needs.

#### Interview answer

Start with traces or logs to see how many SQL statements run and how long they take. Check for N+1, collection fetch joins, large result sets, slow count queries and unexpected lazy loads during mapping or serialization. Then inspect indexes and query plans for the expensive SQL.

Fix by changing fetch plan, using projections, splitting queries or redesigning pagination.

#### Deep dive

Always measure before and after. A fix that reduces query count may increase row count dramatically.

#### Production angle

Fetching issues usually affect tail latency and database load more than CPU in the Java service.

#### Traps / caveats

- Do not optimize only by looking at Java code.
- Check row counts, not just query counts.
- Watch serialization and mapper access.

#### Optional Anki

Q: What two counts matter in fetch troubleshooting?
A: SQL statement count and rows/data volume fetched.

</details>

<a id="jpa-rel-001"></a>

<details>
<summary><strong>JPA-REL-001. What relationship types does JPA support, and which side owns a relationship?</strong></summary>

#### Short answer

JPA supports one-to-one, one-to-many, many-to-one and many-to-many; the owning side is the side that controls the foreign key or join table update.

#### Interview answer

`@ManyToOne` usually owns the foreign key because the many-side table contains the FK column. In bidirectional relationships, `mappedBy` marks the inverse side. Only changes on the owning side are used to update the database relationship.

This is why helper methods should update both sides in memory.

#### Deep dive

Ownership is about database mapping, not business ownership. A parent aggregate can be the business owner even if the child side owns the FK.

#### Production angle

Updating only the inverse side can make the object graph look correct in memory while no relationship change is persisted.

#### Traps / caveats

- `mappedBy` means "the other side owns the relationship".
- Many-to-many ownership can be misleading.
- Keep both sides consistent in domain methods.

#### Optional Anki

Q: Which side updates the FK in a bidirectional JPA relationship?
A: The owning side.

</details>

<a id="jpa-rel-002"></a>

<details>
<summary><strong>JPA-REL-002. How should `@ManyToOne` and `@OneToMany` usually be modeled?</strong></summary>

#### Short answer

Usually put the foreign key on the many side with `@ManyToOne`; add `@OneToMany` only when parent-to-children navigation is needed.

#### Interview answer

The relational model naturally stores the foreign key on the child/many side. In JPA, that maps well to `@ManyToOne`. A bidirectional `@OneToMany(mappedBy = "...")` is useful when the parent aggregate needs to manage children in memory.

Avoid unidirectional one-to-many with join tables unless it is really intended.

#### Deep dive

For high-traffic read APIs, object navigation is less important than explicit query design. You do not need a collection association for every possible database relationship.

#### Production angle

Large parent collections can cause accidental loading, slow deletes, memory pressure and serialization problems.

#### Traps / caveats

- Do not expose huge child collections casually.
- Bidirectional associations need helper methods.
- Make fetch plans explicit.

#### Optional Anki

Q: Where is the FK usually stored for one-to-many?
A: On the many/child side.

</details>

<a id="jpa-rel-003"></a>

<details>
<summary><strong>JPA-REL-003. What are `mappedBy`, the owning side and bidirectional helper methods for?</strong></summary>

#### Short answer

`mappedBy` marks the inverse side; helper methods keep both sides of a bidirectional relationship consistent in memory.

#### Interview answer

In a bidirectional relationship, one side owns the database mapping. The inverse side uses `mappedBy` to point to the owning field. If code only updates the inverse collection but not the owning reference, the database FK may not change.

Helper methods such as `order.addLine(line)` should set `line.setOrder(order)` and add the line to the collection.

#### Deep dive

JPA does not automatically keep both sides of a normal Java object graph consistent for you. That is still application code's job.

#### Production angle

Inconsistent sides produce confusing tests: memory state looks right but flush writes different database state.

#### Traps / caveats

- Ownership is not the same as aggregate ownership.
- Avoid public setters that bypass helpers.
- Test relationship persistence with flush and clear.

#### Optional Anki

Q: What does `mappedBy` indicate?
A: This side is inverse; the other side owns the database relationship.

</details>

<a id="jpa-rel-004"></a>

<details>
<summary><strong>JPA-REL-004. When should a direct `@ManyToMany` be replaced by an explicit join entity?</strong></summary>

#### Short answer

Use an explicit join entity when the relationship has attributes, lifecycle, auditing, permissions or business meaning.

#### Interview answer

Direct `@ManyToMany` is only suitable for simple link tables with no extra data and simple lifecycle. If the join has fields like role, quantity, created date, status or ordering, model it as an entity such as `Membership`, `OrderLine` or `Enrollment`.

Explicit join entities make cascades, constraints and queries clearer.

#### Deep dive

Many real many-to-many relationships become two one-to-many relationships once business rules are added.

#### Production angle

Direct many-to-many mappings often create accidental deletes of shared records, inefficient fetches and hard-to-audit relationship changes.

#### Traps / caveats

- Avoid `CascadeType.REMOVE` on shared many-to-many targets.
- Join table uniqueness still matters.
- Explicit join entities need their own identity/equality design.

#### Optional Anki

Q: When is direct many-to-many usually too weak?
A: When the relationship itself has data or lifecycle.

</details>

<a id="jpa-rel-005"></a>

<details>
<summary><strong>JPA-REL-005. What association mapping defaults and collection choices commonly cause bugs?</strong></summary>

#### Short answer

Default eager to-one fetching, lazy collections, unordered bags, mutable sets and broad cascades commonly cause performance or correctness bugs.

#### Interview answer

JPA defaults `@ManyToOne` and `@OneToOne` to eager, which can over-fetch. Collections default to lazy, which is usually good but can cause lazy initialization problems when boundaries are unclear. `List` without order can behave like a bag, and `Set` depends on correct equality.

Cascades and orphan removal should match ownership, not be copied everywhere.

#### Deep dive

Mapping choices define default behavior, but query design still controls production performance.

#### Production angle

Bad defaults show up as N+1, huge responses, recursive serialization, accidental deletes or unstable collection behavior.

#### Traps / caveats

- Make to-one associations lazy where appropriate.
- Do not use `Set` without stable equality.
- Do not add cascade all by habit.

#### Optional Anki

Q: Which JPA relationship default is often dangerous?
A: EAGER fetching on to-one relationships.

</details>
