# API boundaries, serialization and DTO mapping

---

<a id="jpa-api-001"></a>

<details>
<summary><strong>JPA-API-001. Why should entities usually not be returned directly from REST controllers?</strong></summary>

#### Short answer

Entities are persistence objects, not API contracts; exposing them leaks internals and can trigger lazy loading, recursion and security bugs.

#### Interview answer

A JPA entity may contain lazy associations, bidirectional graphs, internal IDs, version fields, audit fields and fields clients should never see. Returning it directly couples the public API to persistence mapping and makes serialization shape depend on entity relationships.

DTOs let the service expose a deliberate, stable response shape.

#### Deep dive

Entities also carry lifecycle behavior. A small mapping change can accidentally change public JSON if entities are returned directly.

#### Production angle

Direct entity serialization often causes huge responses, N+1 queries, `LazyInitializationException` and data leaks.

#### Traps / caveats

- `@JsonIgnore` on entities is a patch, not a clean API design.
- Public API shape should not change with ORM mapping.
- Do not expose security-sensitive associations accidentally.

#### Optional Anki

Q: Why use DTOs instead of returning entities?
A: DTOs define an explicit API boundary and avoid persistence leaks.

</details>

<a id="jpa-api-002"></a>

<details>
<summary><strong>JPA-API-002. What can go wrong when Jackson serializes lazy or bidirectional associations?</strong></summary>

#### Short answer

Jackson can trigger lazy SQL, fail outside the session, recursively serialize graphs or produce huge JSON.

#### Interview answer

When Jackson calls getters, it may access lazy associations. If the session is closed, that can throw `LazyInitializationException`. If OSIV is enabled, it may instead issue many SQL queries during serialization. Bidirectional relationships can recurse forever unless handled.

The better design is usually DTO mapping inside the service boundary.

#### Deep dive

Annotations such as `@JsonManagedReference`, `@JsonBackReference`, `@JsonIdentityInfo` or `@JsonIgnore` can control serialization, but they do not solve the deeper boundary problem.

#### Production angle

Serialization-driven lazy loading can create N+1 incidents and expose fields not intended for clients.

#### Traps / caveats

- Getters are not harmless on entities.
- OSIV can hide serialization SQL.
- JSON annotations can become tangled with persistence concerns.

#### Optional Anki

Q: Why can Jackson trigger SQL?
A: It calls entity getters that may initialize lazy associations.

</details>

<a id="jpa-api-003"></a>

<details>
<summary><strong>JPA-API-003. Why are Jackson annotations on entities often not the best design?</strong></summary>

#### Short answer

They mix API serialization concerns into persistence classes and often hide rather than fix boundary problems.

#### Interview answer

Jackson annotations can be useful for small internal cases, but using them heavily on entities couples JSON shape to ORM mapping. It becomes hard to support different views, versions, permissions or client-specific response shapes.

DTOs or projections are usually clearer because they define exactly what leaves the service.

#### Deep dive

Entity annotations often accumulate: `@JsonIgnore`, identity annotations, managed/back references and custom serializers. That is a smell that the boundary is wrong.

#### Production angle

API changes become risky because persistence mapping changes can alter serialized output.

#### Traps / caveats

- Serialization annotations do not fix N+1.
- They do not protect request mass assignment.
- They can hide fields globally when only one endpoint needed different behavior.

#### Optional Anki

Q: What is the cleaner alternative to many Jackson annotations on entities?
A: Purpose-built DTOs or projections.

</details>

<a id="jpa-api-004"></a>

<details>
<summary><strong>JPA-API-004. How do DTOs protect persistence boundaries?</strong></summary>

#### Short answer

DTOs define explicit input/output shapes and prevent persistence internals from leaking across API or service boundaries.

#### Interview answer

Read DTOs expose only fields the client needs. Command DTOs contain only fields the client is allowed to change. This avoids direct serialization of lazy graphs and prevents clients from setting entity fields such as ID, owner, status, version or audit data unless explicitly allowed.

DTOs also decouple API evolution from database mapping.

#### Deep dive

DTO mapping should happen inside a transaction when it needs entity data. For read-heavy queries, DTO projections can avoid loading entities altogether.

#### Production angle

DTOs reduce mass assignment, accidental data exposure and lazy-loading failures.

#### Traps / caveats

- DTOs should not blindly mirror entities.
- Mapping can still trigger N+1 if it touches lazy associations.
- Validate command DTOs before applying changes.

#### Optional Anki

Q: What is a command DTO?
A: A DTO describing allowed input for a state-changing operation.

</details>

<a id="jpa-api-005"></a>

<details>
<summary><strong>JPA-API-005. How would you map entities to DTOs, and what are the trade-offs of MapStruct versus manual mapping?</strong></summary>

#### Short answer

Map inside a controlled transaction or query projection; MapStruct reduces boilerplate, while manual mapping gives explicit control.

#### Interview answer

For simple mappings, manual code is clear and easy to debug. For many repetitive mappings, MapStruct generates type-safe mapping code at compile time and avoids reflection. It is useful when mapping rules are stable.

Manual mapping is often better when the mapping contains business decisions, conditional fetches, security filtering or complex aggregation.

#### Deep dive

Mapping should not accidentally initialize lazy associations one row at a time. Query shape and mapper shape must agree.

#### Production angle

Bad mapping is a common source of N+1 and large API responses.

#### Traps / caveats

- Do not hide database access inside mapping.
- Generated mappers still need review.
- Avoid mapping detached entities after the transaction closes.

#### Optional Anki

Q: Main benefit of MapStruct?
A: Compile-time generated mapper code with less boilerplate.

</details>

<a id="jpa-api-006"></a>

<details>
<summary><strong>JPA-API-006. How do you handle partial updates without blindly merging detached entities?</strong></summary>

#### Short answer

Load the managed entity, validate the command DTO, apply only allowed fields, and let dirty checking persist the changes.

#### Interview answer

For a PATCH-like update, do not deserialize into an entity and call `merge()`. Instead, fetch the entity in a transaction, check permissions and version, validate the request, then set only fields the operation allows to change.

This keeps invariants and authorization explicit.

#### Deep dive

For complex patches, use explicit patch commands or field masks rather than treating null as both "clear" and "not provided".

#### Production angle

This prevents null overwrites, privilege escalation and accidental association changes.

#### Traps / caveats

- Distinguish absent fields from explicit nulls.
- Include optimistic version checks when needed.
- Avoid generic reflection-based patching for domain updates.

#### Optional Anki

Q: Safer partial update pattern with JPA?
A: Load managed entity and apply validated allowed DTO fields.

</details>

<a id="jpa-api-007"></a>

<details>
<summary><strong>JPA-API-007. Why can `merge()` with request DTO data be dangerous?</strong></summary>

#### Short answer

`merge()` copies detached state wholesale, so request data can overwrite fields, associations or internal state unintentionally.

#### Interview answer

If a request body is bound to an entity and merged, missing fields may become null, malicious fields may be accepted and stale associations may be copied. `merge()` does not know which fields the client intended to update.

For APIs, use DTOs and explicit application of allowed changes to a managed entity.

#### Deep dive

`merge()` returns a managed copy; the request object remains detached. Continuing to use the detached object is another common mistake.

#### Production angle

Blind merge causes lost updates, mass assignment, broken ownership and security incidents.

#### Traps / caveats

- `merge()` is not PATCH.
- Do not expose entity setters to clients.
- Validate ownership and version before applying changes.

#### Optional Anki

Q: Why is blind merge unsafe for REST updates?
A: It copies all detached state, including nulls or fields the client should not control.

</details>

<a id="jpa-api-008"></a>

<details>
<summary><strong>JPA-API-008. How do you avoid mass assignment vulnerabilities with entities?</strong></summary>

#### Short answer

Never bind untrusted request bodies directly to entities; use command DTOs and apply only allowed fields.

#### Interview answer

Mass assignment happens when a client can set fields that should be controlled by the server, such as `id`, `ownerId`, `role`, `status`, `balance`, `createdAt` or `version`. With entities, broad setters and automatic binding make this easy.

Use DTOs, validation, authorization checks and explicit mapping.

#### Deep dive

Even if JSON ignores some fields, security should not rely on serializer configuration alone. The update command should define what is writable.

#### Production angle

Mass assignment can become privilege escalation, account takeover, incorrect payments or data ownership violations.

#### Traps / caveats

- Do not trust hidden form fields or JSON omissions.
- Do not expose ownership/status setters casually.
- Test forbidden fields in API tests.

#### Optional Anki

Q: Best defense against mass assignment?
A: Command DTOs plus explicit allowed-field mapping.

</details>

<a id="jpa-api-009"></a>

<details>
<summary><strong>JPA-API-009. How should API validation interact with database constraints?</strong></summary>

#### Short answer

API validation gives friendly early errors; database constraints enforce final correctness under all writers and concurrency.

#### Interview answer

Validate request DTOs for required fields, format, ranges and business rules that can be checked before persistence. Still enforce critical invariants with database constraints such as not-null, unique, check and foreign key constraints.

When a constraint violation happens, translate it into a safe API error.

#### Deep dive

Some rules require both application validation and database enforcement. For example, unique email should be checked for user experience and enforced with a unique index for concurrency.

#### Production angle

Database constraints protect against race conditions, bugs, scripts and other services.

#### Traps / caveats

- Application validation alone is not enough.
- Constraint messages may expose internal schema details.
- Validation groups should not hide critical DB invariants.

#### Optional Anki

Q: Why keep database constraints if API validates?
A: They enforce correctness for all concurrent writers.

</details>

<a id="jpa-api-010"></a>

<details>
<summary><strong>JPA-API-010. How do you avoid exposing internal IDs, audit fields, version fields or lazy-loaded internals?</strong></summary>

#### Short answer

Use explicit DTOs, authorization-aware mapping and separate public identifiers when needed.

#### Interview answer

Do not serialize entities directly. Response DTOs should include only fields appropriate for the client and operation. Internal IDs may be replaced with public opaque IDs. Audit fields and version fields should be exposed only when they are part of the API contract, such as optimistic locking.

Lazy internals should never leak by accidental getter traversal.

#### Deep dive

Whether to expose database IDs is a product/security decision. IDs are not authorization; every request still needs permission checks.

#### Production angle

Leaking internal fields can expose business volume, tenant data, workflow state or implementation details attackers can use.

#### Traps / caveats

- Do not rely only on `@JsonIgnore`.
- Include tenant/security context in mapping decisions.
- Version fields may be needed for updates but not every read.

#### Optional Anki

Q: What should decide API response fields?
A: The API contract and authorization context, not the entity mapping.

</details>

<a id="jpa-api-011"></a>

<details>
<summary><strong>JPA-API-011. What is the difference between command DTOs and query DTOs?</strong></summary>

#### Short answer

Command DTOs represent input for changes; query DTOs represent output/read models.

#### Interview answer

A command DTO contains fields needed to execute an operation, such as creating an order or changing an address. It should include only writable fields and validation rules. A query DTO is shaped for reads, such as list rows or detail responses.

Separating them prevents accidental reuse of a response shape as an update contract.

#### Deep dive

Command DTOs often map onto domain methods; query DTOs often map from projections or carefully fetched entities.

#### Production angle

Separate DTOs improve backward compatibility, authorization and auditability.

#### Traps / caveats

- Do not use one giant DTO for every endpoint.
- Read DTO fields are not automatically writable.
- Command DTOs should carry version/idempotency fields when needed.

#### Optional Anki

Q: What is a command DTO for?
A: Input to a state-changing operation.

</details>

<a id="jpa-api-012"></a>

<details>
<summary><strong>JPA-API-012. How does transaction boundary relate to DTO creation and lazy-loading prevention?</strong></summary>

#### Short answer

DTOs should be created while required data is available inside a controlled transaction and fetch plan.

#### Interview answer

If a service returns entities and mapping happens later, lazy associations may fail or trigger SQL in the wrong layer. A service should fetch the data required for the response and map it to DTOs before leaving the persistence boundary.

Alternatively, repository queries can return DTO projections directly.

#### Deep dive

The transaction boundary should match the use case: fetch data, apply permissions, map response and close persistence access cleanly.

#### Production angle

This prevents OSIV reliance, serializer-driven queries and `LazyInitializationException`.

#### Traps / caveats

- Streams over entities can execute after the transaction closes.
- Mapping inside a transaction can still cause N+1 if fetch plan is wrong.
- Do not keep transactions open just for slow serialization.

#### Optional Anki

Q: Where should DTO mapping that needs lazy data happen?
A: Inside the service transaction with an explicit fetch plan.

</details>
