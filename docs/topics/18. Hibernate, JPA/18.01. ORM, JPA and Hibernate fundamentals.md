# ORM, JPA and Hibernate fundamentals

---

<a id="jpa-fund-001"></a>

<details>
<summary><strong>JPA-FUND-001. What problem does ORM solve, and what problems does it not solve?</strong></summary>

#### Short answer

ORM maps Java objects to relational tables and reduces boilerplate persistence code, but it does not remove the need to understand SQL, transactions, constraints or database performance.

#### Interview answer

ORM lets a Java application work with entities and associations instead of manually converting every row to objects and every object change to SQL. It handles identity, change tracking, relationships and common CRUD operations.

It does not make the database disappear. Query shape, indexing, locking, transaction boundaries, isolation, constraints and data modeling still matter. In senior backend work, Hibernate is useful because it automates routine persistence, but dangerous if the team stops looking at generated SQL.

#### Deep dive

The object model and relational model optimize for different things. Java objects use references and behavior; relational databases use tables, rows, joins and set operations. ORM bridges that gap, but some use cases are still better expressed as SQL, projections or specialized database features.

#### Production angle

Most ORM production issues come from hidden SQL: N+1 queries, over-fetching, slow count queries, bad pagination, long transactions and accidental updates through dirty checking.

#### Traps / caveats

- ORM is not a query optimizer.
- ORM mappings are not a replacement for real database constraints.
- Loading entities is not always the right choice for read-heavy endpoints.

#### Optional Anki

Q: What does ORM solve?
A: It maps objects to relational data and handles routine persistence mechanics, but SQL and database behavior still matter.

</details>

<a id="jpa-fund-002"></a>

<details>
<summary><strong>JPA-FUND-002. What are the main benefits and risks of using ORM in a Java backend application?</strong></summary>

#### Short answer

ORM improves productivity and consistency for entity persistence, but can hide expensive SQL and create performance or correctness bugs if used blindly.

#### Interview answer

The benefits are less boilerplate, automatic dirty checking, identity management, relationship mapping, transaction integration and a common programming model across databases. It also works well with Spring transactions and repository abstractions.

The risks are hidden queries, accidental lazy loading, large object graphs, confusing merge behavior, expensive cascades, overuse of entities for API responses and generated SQL that does not match the database access pattern.

#### Deep dive

ORM works best for transactional domain changes and moderate object graphs. It is weaker for reporting, analytics, bulk updates, complex joins, high-throughput imports and read models that need only a few columns.

#### Production angle

A good team measures query count, query time, lock waits, connection pool usage and memory retained by persistence contexts. They also review mappings and generated SQL during code review.

#### Traps / caveats

- Convenience repository methods can still produce poor SQL.
- Lazy loading can move database access into serializers, logs or mappers.
- Cascades can modify more rows than expected.

#### Optional Anki

Q: What is the main risk of ORM?
A: Hidden database behavior, especially unexpected queries, large fetches and accidental writes.

</details>

<details>
<summary><strong>JPA-FUND-003. What is the difference between JPA / Jakarta Persistence, Hibernate and provider-specific behavior?</strong></summary>

#### Short answer

JPA / Jakarta Persistence is the standard API and specification; Hibernate is a provider that implements it and adds non-portable features.

#### Interview answer

JPA defines the standard annotations, entity lifecycle, `EntityManager`, JPQL, mappings and persistence contracts. Jakarta Persistence is the modern name and package namespace. Hibernate is a concrete implementation of that specification and also exposes extra APIs and annotations.

A portable JPA feature should work across providers. A Hibernate-specific feature may be powerful, but it couples the application to Hibernate behavior.

#### Deep dive

Examples of provider-specific behavior include Hibernate fetch modes, `@BatchSize`, `@Formula`, filters, soft delete support, `StatelessSession`, custom type mappings and some caching behavior. These can be valuable, but they should be chosen deliberately.

#### Production angle

Most Spring Boot Java services use Hibernate, so knowing Hibernate behavior is practical. Still, code should make provider-specific choices explicit because they affect upgrades, migrations and team expectations.

#### Traps / caveats

- Do not assume every Hibernate annotation is part of JPA.
- Provider defaults may change across Hibernate versions.
- "Works with Hibernate" does not always mean "portable JPA".

#### Optional Anki

Q: Is Hibernate the same as JPA?
A: No. JPA is the specification; Hibernate is a provider and adds extra features.

</details>

<details>
<summary><strong>JPA-FUND-004. What are `EntityManagerFactory`, `EntityManager`, `SessionFactory` and `Session` responsible for?</strong></summary>

#### Short answer

`EntityManagerFactory` and Hibernate `SessionFactory` are heavyweight factories; `EntityManager` and `Session` represent a unit-of-work persistence context.

#### Interview answer

`EntityManagerFactory` is created per persistence unit and is expensive to build. It holds metadata and creates `EntityManager` instances. Hibernate `SessionFactory` is the corresponding native Hibernate concept.

`EntityManager` is the JPA interface used to persist, find, remove, query and manage entities. Hibernate `Session` is Hibernate's native API. In a Spring application, an `EntityManager` is usually bound to the current transaction.

#### Deep dive

`EntityManagerFactory` and `SessionFactory` are thread-safe and usually application-scoped. `EntityManager` and `Session` are not thread-safe and should be scoped to a transaction or request/unit of work, depending on the environment.

#### Production angle

Creating factories repeatedly is a startup/performance bug. Sharing an `EntityManager` across threads or requests is a correctness and memory leak risk.

#### Traps / caveats

- Do not store an `EntityManager` in static state.
- Do not use the same persistence context across async threads.
- `unwrap(Session.class)` should be used only when Hibernate-specific behavior is intentional.

#### Optional Anki

Q: Which JPA object is heavyweight and usually application-scoped?
A: `EntityManagerFactory`.

</details>

<details>
<summary><strong>JPA-FUND-005. Why should backend developers still understand SQL when using JPA/Hibernate?</strong></summary>

#### Short answer

Hibernate generates SQL, but the database executes it. Performance and correctness depend on SQL, indexes, constraints, joins, locks and transaction behavior.

#### Interview answer

A backend developer needs to understand the SQL produced by JPQL, repository methods, entity graphs and lazy loading. Without SQL knowledge, it is hard to detect N+1 queries, bad joins, missing indexes, slow count queries, lock contention or broken pagination.

JPA is an abstraction over SQL, not a replacement for it.

#### Deep dive

The same entity model can produce very different SQL depending on fetch plan, query shape, flush timing and transaction state. Developers should be comfortable reading SQL logs, using `EXPLAIN`, understanding indexes and knowing when to use native SQL.

#### Production angle

SQL literacy is often the difference between a quick fix and a long incident. It helps diagnose high database CPU, connection pool exhaustion, deadlocks and slow endpoints.

#### Traps / caveats

- JPQL works with entities, but the final query still uses tables.
- A query that is fast on test data may be slow on production cardinalities.
- Database constraints are still required for data integrity.

#### Optional Anki

Q: Why must JPA users know SQL?
A: Because Hibernate-generated SQL determines database performance and correctness.

</details>

<details>
<summary><strong>JPA-FUND-006. What is the difference between an entity, a DTO and a value object?</strong></summary>

#### Short answer

An entity has persistent identity and lifecycle, a DTO carries data across boundaries, and a value object is identified by its values.

#### Interview answer

A JPA entity represents persisted domain state and is managed by the persistence context. It usually has an identifier and participates in dirty checking, relationships and transactions.

A DTO is a boundary object used for API requests, API responses, projections or service contracts. It should not be managed by JPA. A value object represents a concept like money, email or address where equality is based on values, not database identity.

#### Deep dive

Entities are mutable enough for persistence and lifecycle changes. DTOs are shaped for external or read use cases. Value objects should usually be immutable and can often be embedded into entities.

#### Production angle

Confusing these roles causes mass assignment bugs, lazy-loading during JSON serialization, API coupling to internal schema and accidental persistence of request data.

#### Traps / caveats

- Do not expose entities directly as public API contracts.
- Do not use request DTOs as detached entities to merge blindly.
- Value objects can still need careful mapping and validation.

#### Optional Anki

Q: What is the main difference between an entity and a value object?
A: Entity equality is based on identity; value object equality is based on values.

</details>

<details>
<summary><strong>🧠 JPA-FUND-007. What changed when JPA moved from `javax.persistence` to `jakarta.persistence`, and when is `persistence.xml` still relevant?</strong></summary>

#### Short answer

The API package moved from `javax.persistence` to `jakarta.persistence`; `persistence.xml` is still relevant for explicit JPA bootstrapping and some non-Spring or container-managed setups.

#### Interview answer

Jakarta Persistence 3.x uses the `jakarta.persistence` namespace. Older Java EE / JPA 2.x applications used `javax.persistence`. This is a source and dependency migration concern because imports, providers and framework versions must align.

`persistence.xml` defines a persistence unit, provider, entity classes, mapping files, data source and properties. Spring Boot often configures JPA without hand-written `persistence.xml`, but the file still matters in standard Jakarta EE, Java SE bootstrapping, tests, libraries or legacy apps.

#### Deep dive

The namespace migration is not just a search-and-replace if libraries still depend on older `javax` APIs. Mixed dependency trees can fail at runtime.

#### Production angle

During framework upgrades, mismatched Jakarta and Javax dependencies can break startup, entity scanning, validation or provider integration.

#### Traps / caveats

- Do not mix `javax.persistence` entities with a Jakarta-only provider stack.
- Spring Boot convention does not mean `persistence.xml` disappeared from the specification.
- Migration should include dependency and plugin checks, not only source imports.

#### Optional Anki

Q: What package namespace does modern Jakarta Persistence use?
A: `jakarta.persistence`.

</details>
