# Queries, projections, pagination and bulk work

---

<a id="jpa-query-001"></a>

<details>
<summary><strong>JPA-QUERY-001. What is JPQL, and how is it different from SQL?</strong></summary>

#### Short answer

JPQL queries entities and their fields; SQL queries database tables and columns directly.

#### Interview answer

JPQL is the standard JPA query language. It is written in terms of entity names, mapped attributes and associations. Hibernate translates JPQL to SQL for the target database.

SQL is the database's native language. It can use database-specific functions, hints, CTEs, window functions and features that JPQL may not express well.

#### Deep dive

JPQL is portable and entity-aware, but portability has limits. The generated SQL still needs to be reviewed for performance.

#### Production angle

A JPQL query can look simple while producing inefficient SQL or bad joins. Always inspect generated SQL for important paths.

#### Traps / caveats

- JPQL does not query table names by default.
- JPQL joins are based on mapped associations or entity paths.
- Portability may cost access to database-specific optimizations.

#### Optional Anki

Q: What does JPQL query?
A: Entities and their mapped attributes.

</details>

<a id="jpa-query-002"></a>

<details>
<summary><strong>🧠 JPA-QUERY-002. What is HQL, and what portability trade-offs does it introduce?</strong></summary>

#### Short answer

HQL is Hibernate's query language; it includes JPQL-like querying plus Hibernate-specific extensions.

#### Interview answer

Hibernate Query Language predates and extends JPQL. In Hibernate applications, HQL and JPQL often look similar, but HQL may support provider-specific syntax or features. Using those features can be practical, but the query is no longer portable to another JPA provider.

Use HQL extensions deliberately and document why they are needed.

#### Deep dive

With Hibernate as the standard provider in Spring Boot apps, HQL-specific features may be acceptable when they produce clearer or faster code.

#### Production angle

Provider-specific queries need upgrade tests because Hibernate version changes can affect parsing or generated SQL.

#### Traps / caveats

- Do not call Hibernate-specific HQL "portable JPQL".
- Generated SQL still matters.
- Native SQL may be clearer for heavily database-specific logic.

#### Optional Anki

Q: What is the main trade-off of HQL-specific features?
A: Less JPA provider portability.

</details>

<a id="jpa-query-003"></a>

<details>
<summary><strong>JPA-QUERY-003. When should native SQL be preferred over JPQL?</strong></summary>

#### Short answer

Use native SQL when the query needs database-specific features, complex reporting, tuned plans or SQL that JPQL cannot express cleanly.

#### Interview answer

JPQL is good for entity-oriented queries. Native SQL is often better for window functions, CTEs, recursive queries, advanced PostgreSQL features, bulk/reporting queries, database-specific JSON operations or heavily optimized read models.

The trade-off is less portability and more manual result mapping.

#### Deep dive

Native SQL should still be parameterized and tested. It should live near migration/schema ownership because it depends on physical table and column names.

#### Production angle

Native SQL can be the right tool for high-value endpoints where performance and explicit plans matter more than provider abstraction.

#### Traps / caveats

- Do not concatenate user input.
- Keep native queries covered by integration tests.
- Review indexes and execution plans.

#### Optional Anki

Q: When is native SQL justified?
A: When database-specific features or precise SQL control are needed.

</details>

<a id="jpa-query-004"></a>

<details>
<summary><strong>JPA-QUERY-004. How does parameter binding help prevent SQL injection?</strong></summary>

#### Short answer

Parameter binding sends values separately from query structure, so user input is treated as data rather than executable SQL.

#### Interview answer

Instead of building `"... where name = '" + input + "'"`, use named or positional parameters. The provider/driver binds the value safely, handling escaping and types. This prevents an attacker from changing the query structure through input.

This applies to JPQL and native SQL.

#### Deep dive

Parameter binding protects values, not identifiers. Dynamic table names, column names or sort fields must be whitelisted.

#### Production angle

SQL injection is still possible in JPA apps if developers concatenate strings for dynamic filters, order by clauses or native queries.

#### Traps / caveats

- Bind parameters, do not concatenate values.
- Whitelist dynamic sort/property names.
- Be careful with `LIKE` patterns and wildcards.

#### Optional Anki

Q: What does parameter binding separate?
A: Query structure from input values.

</details>

<a id="jpa-query-005"></a>

<details>
<summary><strong>JPA-QUERY-005. What is the difference between `JOIN` and `JOIN FETCH` in JPQL?</strong></summary>

#### Short answer

`JOIN` affects query filtering/navigation; `JOIN FETCH` also initializes the association in returned entities.

#### Interview answer

A regular join lets a query filter or sort based on related entities. It does not necessarily load the association into the persistence context as initialized. `JOIN FETCH` tells JPA to fetch that association as part of the result graph.

Use join fetch when the returned entity graph needs the association immediately.

#### Deep dive

Fetch joins change loading behavior and can affect duplicates, row counts and pagination, especially with collections.

#### Production angle

Confusing joins and fetch joins is a common source of N+1 bugs or over-fetching.

#### Traps / caveats

- `JOIN FETCH` is not for every association.
- Collection fetch joins and pagination are risky.
- Regular joins can still produce duplicate root rows depending on query.

#### Optional Anki

Q: What extra behavior does `JOIN FETCH` add?
A: It initializes the joined association in the returned entity graph.

</details>

<a id="jpa-query-006"></a>

<details>
<summary><strong>JPA-QUERY-006. What are constructor expressions and DTO projections?</strong></summary>

#### Short answer

They let a query return DTOs or selected fields instead of full managed entities.

#### Interview answer

A JPQL constructor expression creates a DTO directly from selected fields, for example `select new com.example.OrderDto(o.id, o.status)`. Spring Data also supports interface and class-based projections.

Projections are useful for read-only screens where loading full entities and associations is unnecessary.

#### Deep dive

DTO projections are not managed by the persistence context. They do not participate in dirty checking, which is a benefit for reads.

#### Production angle

They reduce heap usage, serialization size and lazy-loading problems for list endpoints.

#### Traps / caveats

- Constructor signatures must match.
- Nested projections can still be expensive.
- Do not use projections when you need to modify managed state.

#### Optional Anki

Q: Are DTO projections managed entities?
A: No.

</details>

<a id="jpa-query-007"></a>

<details>
<summary><strong>🧠 JPA-QUERY-007. What are the pros and cons of Criteria API?</strong></summary>

#### Short answer

Criteria API builds type-aware dynamic queries in Java, but it is verbose and harder to read than JPQL for simple queries.

#### Interview answer

Criteria API is useful when query predicates are dynamic and composable, such as optional filters. It can reduce string concatenation and help with refactoring if using metamodels.

The downside is verbosity. Complex Criteria queries can be harder to understand than JPQL, QueryDSL, jOOQ or native SQL.

#### Deep dive

Spring Data Specifications are built on Criteria API and can work well for moderate dynamic filtering.

#### Production angle

Criteria-generated SQL still needs plan review. Type-safe construction does not guarantee efficient queries.

#### Traps / caveats

- Avoid building unreadable query trees.
- Do not compose filters blindly without index awareness.
- Consider QueryDSL or jOOQ for complex query-heavy modules.

#### Optional Anki

Q: What is Criteria API best at?
A: Programmatic dynamic query construction.

</details>

<a id="jpa-query-008"></a>

<details>
<summary><strong>🧠 JPA-QUERY-008. How would you choose between JPQL, Criteria, QueryDSL, jOOQ and native SQL?</strong></summary>

#### Short answer

Choose based on query complexity, dynamic needs, type safety, database-specific features and team familiarity.

#### Interview answer

JPQL is good for straightforward entity queries. Criteria/Specifications help with dynamic optional filters. QueryDSL provides a fluent type-safe query style. jOOQ is strong when SQL is central and database-specific features matter. Native SQL is direct and useful for tuned or specialized queries.

The best choice is the one that makes behavior explicit, testable and performant.

#### Deep dive

It is fine for one application to use several approaches: JPA for writes, projections for reads, and jOOQ/native SQL for reporting.

#### Production angle

Critical queries should be easy to inspect, explain and tune. Abstraction should not hide execution plans.

#### Traps / caveats

- Do not force every query through repositories.
- Do not use native SQL unsafely.
- Avoid fragmented query styles without team conventions.

#### Optional Anki

Q: What query tool is often strong for SQL-heavy modules?
A: jOOQ or native SQL.

</details>

<a id="jpa-query-009"></a>

<details>
<summary><strong>JPA-QUERY-009. How do you express dynamic optional filters safely?</strong></summary>

#### Short answer

Use parameterized queries, Specifications/Criteria, QueryDSL or a controlled query builder with whitelisted fields.

#### Interview answer

For optional filters, avoid string concatenation with raw input. Build predicates only for provided filters and bind values as parameters. For sorting, whitelist allowed properties and directions. For complex filtering, use Specifications, QueryDSL, jOOQ or native SQL with a safe builder.

The query should remain readable and index-aware.

#### Deep dive

Dynamic filters can produce many query shapes. Production data distribution and composite indexes matter.

#### Production angle

Bad dynamic filters cause slow endpoints, injection vulnerabilities and query plan instability.

#### Traps / caveats

- Parameter binding does not protect dynamic column names.
- Optional filters need pagination limits.
- Test common and worst-case filter combinations.

#### Optional Anki

Q: How should dynamic sort fields be handled?
A: Whitelist allowed fields and directions.

</details>

<a id="jpa-query-010"></a>

<details>
<summary><strong>🧠 JPA-QUERY-010. How do you call database functions from JPQL?</strong></summary>

#### Short answer

Use standard JPQL functions when available, or provider-supported function invocation for database-specific functions.

#### Interview answer

JPQL has standard functions for common string, numeric and date operations. For database-specific functions, modern JPA supports function invocation syntax and Hibernate can register or call dialect functions.

Use this sparingly because database functions can reduce portability and sometimes prevent index usage.

#### Deep dive

Function calls in `WHERE` clauses can make indexes unusable unless expression indexes or generated columns are designed for them.

#### Production angle

Database-specific functions should be covered by integration tests against the production database engine.

#### Traps / caveats

- Do not assume H2 supports the same functions as PostgreSQL.
- Functions on indexed columns can force scans.
- Native SQL may be clearer for complex function-heavy queries.

#### Optional Anki

Q: What is a risk of database functions in JPQL predicates?
A: They may reduce portability and prevent index usage.

</details>

<a id="jpa-query-011"></a>

<details>
<summary><strong>JPA-QUERY-011. How can JPQL hide inefficient SQL, and how do you debug it?</strong></summary>

#### Short answer

JPQL abstracts tables and joins, so generated SQL may be more complex than expected; debug by logging SQL and using database execution plans.

#### Interview answer

A simple JPQL path expression can generate joins. Fetch plans can add selects. Pagination can add count queries. Criteria or derived queries can hide query details behind Java method names.

To debug, capture generated SQL, bind values safely, run `EXPLAIN ANALYZE`, check indexes and compare actual row counts with expected data shape.

#### Deep dive

Look at both number of SQL statements and rows returned. One query can still be worse than several targeted queries.

#### Production angle

The database does not execute JPQL; it executes SQL. Senior troubleshooting follows the SQL.

#### Traps / caveats

- Do not optimize without the actual SQL.
- Development data may hide bad plans.
- Generated count queries can be the slow part.

#### Optional Anki

Q: What should you inspect when JPQL is slow?
A: Generated SQL and its execution plan.

</details>

<a id="jpa-query-012"></a>

<details>
<summary><strong>JPA-QUERY-012. Why should filtering and sorting usually happen in the database rather than in Java?</strong></summary>

#### Short answer

The database can use indexes, statistics and set-based execution; filtering in Java requires fetching too much data first.

#### Interview answer

If a service loads thousands of entities and then filters or sorts them in Java, it pays for extra I/O, network transfer, heap, dirty checking and CPU. Pagination becomes wrong because the database did not limit the correct result set.

Filtering and sorting should usually be in SQL/JPQL where the database can optimize.

#### Deep dive

Java-side filtering is acceptable only for small in-memory data or rules that cannot reasonably be expressed in the database.

#### Production angle

Moving filters to Java is a common cause of slow endpoints and memory spikes.

#### Traps / caveats

- Filtering after pagination changes results.
- Sorting in Java may break stable pagination.
- Fetching full entities just to discard most rows is wasteful.

#### Optional Anki

Q: Why is Java filtering after loading entities often bad?
A: It fetches too much data and bypasses database indexes.

</details>

<a id="jpa-dto-001"></a>

<details>
<summary><strong>JPA-DTO-001. What projection types exist in JPA and Spring Data JPA, and what are their limitations?</strong></summary>

#### Short answer

Common projections include JPQL constructor DTOs, Spring Data interface/class projections, dynamic projections and native query mappings.

#### Interview answer

JPQL constructor expressions create DTOs directly. Spring Data supports interface-based projections, class/record DTO projections and dynamic projection methods. Native queries can map scalars, DTOs or entities depending on setup.

Limitations include constructor fragility, nested projection complexity, provider-specific behavior and lack of managed entity state.

#### Deep dive

Projection choice should match API shape and query performance, not just reduce code.

#### Production angle

Good projections reduce over-fetching and lazy loading. Bad projections can hide complex joins or still produce N+1.

#### Traps / caveats

- Projections are read models, not update models.
- Nested interface projections may fetch more than expected.
- Native mappings need integration tests.

#### Optional Anki

Q: What is the main benefit of projections?
A: Fetching only the data shape required for a read use case.

</details>

<a id="jpa-dto-002"></a>

<details>
<summary><strong>JPA-DTO-002. How would you design a query model for a list endpoint versus a detail endpoint?</strong></summary>

#### Short answer

Use small projections and stable pagination for list endpoints; use richer fetch plans or targeted queries for detail endpoints.

#### Interview answer

A list endpoint should return a bounded summary: IDs, names, statuses, timestamps and small related fields. It should avoid large collections and expensive graphs. A detail endpoint can load one root and selected associations because the cardinality is small.

This often means separate repository methods and DTOs.

#### Deep dive

Trying to reuse one entity graph for both list and detail views causes either under-fetching or over-fetching.

#### Production angle

List endpoints are hit often and can dominate database load, so they need tight query shapes and predictable limits.

#### Traps / caveats

- Do not fetch child collections for every list row by default.
- Count queries need review.
- Detail queries should still avoid unbounded graphs.

#### Optional Anki

Q: What is the best shape for list endpoint reads?
A: A bounded summary projection with stable sorting/pagination.

</details>

<a id="jpa-page-001"></a>

<details>
<summary><strong>JPA-PAGE-001. How does offset pagination work, and why can it become slow?</strong></summary>

#### Short answer

Offset pagination skips N rows and returns the next page; deep offsets become slow because the database still scans or sorts skipped rows.

#### Interview answer

Offset pagination uses `limit` and `offset`, often exposed as page number and page size. It is simple and flexible, but deep pages require the database to walk past many rows before returning results.

It can also produce duplicates or missing items if ordering is unstable while data changes.

#### Deep dive

Indexes can help, but they do not eliminate all deep-offset costs, especially with joins and complex sorting.

#### Production angle

Deep pagination is common in admin screens, exports and search APIs. Consider keyset pagination or cursor-based designs.

#### Traps / caveats

- Always use deterministic ordering.
- Avoid huge page sizes.
- Review count query cost separately.

#### Optional Anki

Q: Why does deep offset pagination get slow?
A: The database must still process skipped rows.

</details>

<a id="jpa-page-002"></a>

<details>
<summary><strong>JPA-PAGE-002. What is keyset pagination, and when is it a better fit?</strong></summary>

#### Short answer

Keyset pagination uses the last seen sort key as a cursor instead of skipping rows by offset.

#### Interview answer

Instead of `offset 10000`, keyset pagination asks for rows after the last item from the previous page, such as `where (created_at, id) < (?, ?) order by created_at desc, id desc limit ?`. It is efficient for deep scrolling because the database can continue from an indexed position.

It is best for "next page" or infinite-scroll flows.

#### Deep dive

Keyset pagination requires stable, unique ordering and does not jump easily to arbitrary page numbers.

#### Production angle

It is a strong choice for large event feeds, audit logs, transactions and search-like APIs with ordered results.

#### Traps / caveats

- Include a tie-breaker such as ID.
- Cursor values must match sort order.
- It is less convenient for "go to page 57".

#### Optional Anki

Q: What does keyset pagination avoid?
A: Scanning/skipping deep offsets.

</details>

<a id="jpa-page-003"></a>

<details>
<summary><strong>JPA-PAGE-003. Why is stable ordering important for pagination correctness?</strong></summary>

#### Short answer

Without stable ordering, rows with equal sort values can move between pages or appear twice.

#### Interview answer

Pagination requires deterministic order. If sorting only by `createdAt` and many rows share the same timestamp, the database may return ties in arbitrary order. Between requests, inserts or updates can also shift rows.

Add a unique tie-breaker, commonly ID, and use ordering supported by indexes.

#### Deep dive

Stable ordering matters for both offset and keyset pagination, but keyset pagination depends on it especially strongly.

#### Production angle

Unstable pagination creates user-visible duplicates, missing rows and inconsistent exports.

#### Traps / caveats

- Sorting by non-unique columns is not enough.
- Client-side sorting after database pagination is wrong.
- Changing default sort order can break cursors.

#### Optional Anki

Q: What should be added to non-unique sort columns?
A: A unique tie-breaker such as ID.

</details>

<a id="jpa-page-004"></a>

<details>
<summary><strong>JPA-PAGE-004. How can `Page` count queries become a performance bottleneck, and when would you use `Slice`?</strong></summary>

#### Short answer

`Page` usually needs a total count query, which can be expensive; `Slice` avoids total count and only checks whether another page exists.

#### Interview answer

Spring Data `Page` returns content plus total elements and total pages. That often requires a generated count query. With joins, filters, distinct or large tables, the count can be slower than the data query.

Use `Slice` when the UI only needs "has next page", such as infinite scroll or load-more buttons.

#### Deep dive

For complex queries, write an explicit count query or avoid total counts when exact totals are not worth the cost.

#### Production angle

Slow count queries are a common hidden bottleneck in list APIs.

#### Traps / caveats

- Count query can differ from data query plan.
- Fetch joins and counts do not mix cleanly.
- Exact totals may be stale immediately anyway.

#### Optional Anki

Q: What does `Slice` avoid compared with `Page`?
A: The total count query.

</details>

<a id="jpa-bulk-001"></a>

<details>
<summary><strong>JPA-BULK-001. How do JPQL bulk updates, deletes and Hibernate batching behave with the persistence context?</strong></summary>

#### Short answer

Bulk JPQL bypasses managed entity state; Hibernate batching groups normal entity SQL statements during flush.

#### Interview answer

JPQL bulk update/delete statements execute directly in the database and do not update already managed entities in memory. Hibernate batching is different: it groups many insert/update/delete statements generated from normal entity changes.

Bulk operations are efficient for set-based changes. Batching is useful when processing many entities through the ORM.

#### Deep dive

For bulk JPQL, flush before and clear after when affected entities may be managed. For batching, tune batch size, flush intervals and ID strategy.

#### Production angle

Mixing bulk operations with managed entities can return stale data or overwrite changes later.

#### Traps / caveats

- Bulk operations may bypass callbacks and version handling.
- Batching may not work with `IDENTITY` generation.
- Large persistence contexts still need clearing.

#### Optional Anki

Q: What should you often do after a JPQL bulk update?
A: Clear or refresh affected persistence context state.

</details>

<a id="jpa-bulk-002"></a>

<details>
<summary><strong>JPA-BULK-002. How do JDBC batching settings and ID generation strategy interact?</strong></summary>

#### Short answer

Hibernate can batch similar SQL statements, but identity-based ID generation often forces immediate inserts and limits batching.

#### Interview answer

JDBC batching groups multiple inserts or updates into fewer database round trips. Hibernate needs batching enabled and statements must be batchable. Sequence-based IDs work well because identifiers can be allocated before insert. `IDENTITY` often requires executing each insert to obtain the generated ID.

Ordered inserts/updates and periodic flush/clear can improve batching.

#### Deep dive

Batch size is not the only setting. SQL shape, flush order, cascades, entity types and driver support matter.

#### Production angle

For imports and high-volume writes, verify batching with logs/metrics instead of assuming it works.

#### Traps / caveats

- Enabling batch size is not enough.
- ID strategy can disable effective insert batching.
- Too-large batches can increase memory and lock time.

#### Optional Anki

Q: Which ID strategy commonly limits insert batching?
A: `GenerationType.IDENTITY`.

</details>
