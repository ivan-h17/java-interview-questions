<details>
<summary><strong>JPA-SPRING-001. How do derived query methods work, and when do they become a liability?</strong></summary>

#### Short answer

Spring Data parses repository method names into queries; they become a liability when names are long, ambiguous or hide complex performance behavior.

#### Interview answer

A method such as `findByStatusAndCreatedAtAfter` is parsed into a query based on entity properties and supported keywords. This is convenient for simple lookups.

For complex filtering, joins, sorting, fetch plans or performance-critical queries, derived method names become hard to read and review. At that point use explicit JPQL, Specifications, QueryDSL, jOOQ or native SQL.

#### Deep dive

Derived queries do not automatically solve N+1, indexing, count-query cost or pagination correctness.

#### Production angle

Long method names often hide slow SQL because reviewers focus on Java naming rather than generated database behavior.

#### Traps / caveats

- Method parsing depends on entity property names.
- Renames can break startup.
- Simple-looking methods can still produce expensive queries.

#### Optional Anki

Q: When should derived query methods be replaced?
A: When query behavior needs explicit control or the method name becomes complex.

</details>

<details>
<summary><strong>JPA-SPRING-002. When should derived queries be replaced with `@Query`, Specifications, native SQL or another query tool?</strong></summary>

#### Short answer

Replace them when the query needs explicit joins, dynamic filters, custom fetch plans, database-specific SQL or careful performance tuning.

#### Interview answer

Use `@Query` for clear fixed JPQL or native SQL. Use Specifications or Criteria for composable optional filters. Use QueryDSL for fluent type-safe queries. Use jOOQ or native SQL when SQL features and exact control matter.

The goal is readable, testable and explainable query behavior.

#### Deep dive

Repository method names are not a substitute for query design. The more important the endpoint, the more explicit the query should be.

#### Production angle

Explicit queries are easier to inspect, explain, tune and regression-test.

#### Traps / caveats

- Native SQL needs migration awareness.
- Specifications can still create poor plans.
- `@Query` still needs fetch and count-query review.

#### Optional Anki

Q: Best replacement for many optional filters in Spring Data?
A: Specifications, Criteria, QueryDSL or a controlled query builder.

</details>

<details>
<summary><strong>JPA-SPRING-003. What is `@Modifying`, and why do modifying queries need transactions?</strong></summary>

#### Short answer

`@Modifying` marks a repository query as update/delete SQL rather than a select, and it needs a transaction because it changes database state.

#### Interview answer

Spring Data repository methods with `@Query` are normally treated as reads. `@Modifying` tells Spring Data that the query changes data, such as JPQL update/delete or native DML. The operation must run in a transaction so the database can commit or roll back the change.

Bulk modifying queries also bypass normal managed entity state.

#### Deep dive

Spring Data offers options to flush before and clear after modifying queries. Use them deliberately when persistence context staleness matters.

#### Production angle

Bulk repository updates can leave already loaded entities stale and produce confusing API responses in the same transaction.

#### Traps / caveats

- Do not forget `@Transactional`.
- Clear the persistence context when affected entities may be managed.
- Bulk updates may bypass optimistic locking.

#### Optional Anki

Q: What does `@Modifying` indicate?
A: A Spring Data query changes data rather than selecting it.

</details>

<a id="jpa-spring-004"></a>

<details>
<summary><strong>JPA-SPRING-004. What are `@EntityGraph`, projections and Specifications in Spring Data JPA?</strong></summary>

#### Short answer

They are Spring Data tools for fetch planning, read shaping and dynamic query predicates.

#### Interview answer

`@EntityGraph` applies a JPA entity graph to a repository method to control fetched associations. Projections return DTO-like shapes or selected fields instead of full entities. Specifications build dynamic Criteria predicates, often for optional filters.

They solve different problems and can be combined carefully.

#### Deep dive

Entity graphs affect loading of entities. Projections change the selected result shape. Specifications construct the query predicate, not necessarily the fetch plan.

#### Production angle

These tools can reduce N+1 and over-fetching when used deliberately, but they should be validated with SQL count and plan tests.

#### Traps / caveats

- `@EntityGraph` can fetch too much.
- Interface projections may hide nested queries.
- Specifications can become unindexed dynamic SQL.

#### Optional Anki

Q: Which Spring Data feature defines fetch plans?
A: `@EntityGraph`.

</details>

<details>
<summary><strong>JPA-SPRING-005. What transactional behavior do Spring Data repository methods have by default?</strong></summary>

#### Short answer

Spring Data JPA repository methods have default transaction settings, but service-layer transactions usually define the real business boundary.

#### Interview answer

Simple repository read methods are typically read-only transactional by default, while write methods run with transactions. If a repository method is called inside an existing service transaction, it participates in that transaction.

For business operations, place `@Transactional` on the service method that coordinates the full use case.

#### Deep dive

Repository defaults are convenient, but relying on them for multi-step workflows can create too-narrow transaction boundaries.

#### Production angle

Incorrect boundaries cause partial writes, lazy-loading failures and inconsistent repository behavior between callers.

#### Traps / caveats

- Service transaction overrides repository defaults.
- Self-invocation can bypass transactional advice.
- Read-only does not mean immutable Java objects.

#### Optional Anki

Q: Where should transaction boundaries usually be defined?
A: At the service/use-case layer.

</details>

<a id="jpa-spring-006"></a>

<details>
<summary><strong>JPA-SPRING-006. Where should transaction boundaries usually live: repository or service layer?</strong></summary>

#### Short answer

Usually at the service layer, because it knows the full business operation that should commit or roll back together.

#### Interview answer

A repository method usually represents one persistence operation. A service method often coordinates several repositories, validation and domain state transitions. The service method is the natural transaction boundary for the complete unit of work.

Repositories can still have transactional metadata, but they should not force every use case into tiny transactions.

#### Deep dive

Long transactions are also harmful. Keep the service transaction focused on database work required for the invariant.

#### Production angle

Good boundaries reduce partial writes, lock time, connection usage and lazy-loading leaks.

#### Traps / caveats

- Do not include slow HTTP calls inside a DB transaction.
- Avoid transaction annotations scattered randomly.
- Test rollback behavior at the service level.

#### Optional Anki

Q: Why service-layer transactions?
A: They cover the full business use case rather than one repository call.

</details>

<a id="jpa-spring-007"></a>

<details>
<summary><strong>JPA-SPRING-007. Why can `@Transactional(readOnly = true)` matter for JPA/Hibernate?</strong></summary>

#### Short answer

It signals read intent and may let Spring/Hibernate optimize flush behavior and connection settings.

#### Interview answer

`readOnly = true` tells Spring the transaction should not write. Depending on Spring and Hibernate integration, it can set Hibernate/session read-only behavior or flush mode optimizations. It also documents intent.

However, it does not make entities immutable or replace code discipline.

#### Deep dive

If code mutates managed entities in a read-only transaction, behavior can vary by configuration, but the design is still wrong.

#### Production angle

Read-only transactions can reduce accidental flushes and clarify read routing or monitoring policies.

#### Traps / caveats

- Do not rely on it as a security control.
- It does not prevent all writes in every configuration.
- Mutating in read paths is still a bug.

#### Optional Anki

Q: Does `readOnly = true` make Java objects immutable?
A: No.

</details>

<a id="jpa-spring-008"></a>

<details>
<summary><strong>JPA-SPRING-008. What is Open EntityManager in View / Open Session in View in Spring Boot?</strong></summary>

#### Short answer

It keeps the JPA persistence context available during web request rendering, allowing lazy loading outside service transactions.

#### Interview answer

Open EntityManager in View binds an `EntityManager` for the duration of a web request. This lets controllers or serializers initialize lazy associations after service methods return.

It is convenient, but it hides missing fetch plans and can cause SQL during JSON serialization.

#### Deep dive

Many teams disable OSIV for REST APIs and require services to return DTOs that are fully prepared inside transactional boundaries.

#### Production angle

OSIV makes SQL per endpoint depend on serialization shape, which complicates performance review.

#### Traps / caveats

- OSIV is not a substitute for query design.
- Disabling it requires fixing DTO/fetch boundaries.
- It can hide N+1 until production.

#### Optional Anki

Q: What does OSIV allow?
A: Lazy loading during web response rendering.

</details>

<details>
<summary><strong>JPA-SPRING-009. How would you review repository code for N+1 queries, count-query bottlenecks and transaction leaks?</strong></summary>

#### Short answer

Review generated SQL, fetch plans, pagination/count behavior, DTO mapping, transaction boundaries and tests that assert query counts.

#### Interview answer

I would look for repository methods returning entities for list endpoints, lazy associations accessed in mappers, derived queries with hidden joins, `Page` methods with expensive counts, missing entity graphs/projections and service methods without clear transaction boundaries.

Then I would add integration tests with realistic data and statement-count assertions for important paths.

#### Deep dive

Repository review should connect Java method signatures to SQL shape and endpoint behavior.

#### Production angle

This review prevents the most common Spring Data JPA production failures: N+1, slow counts, connection pool pressure and lazy-loading exceptions.

#### Traps / caveats

- Do not trust repository names as performance documentation.
- Check both content query and count query.
- Include serialization/DTO mapping in the review.

#### Optional Anki

Q: What should repository performance review connect?
A: Repository method, generated SQL, fetch plan and endpoint data shape.

</details>
