# Testing, migrations and production safety

---

<a id="jpa-test-001"></a>

<details>
<summary><strong>JPA-TEST-001. How do you test JPA repository code?</strong></summary>

#### Short answer

Use integration-style tests with a real or production-like database, verify mappings, queries, constraints and transaction behavior.

#### Interview answer

Repository code should be tested against a database because JPA behavior depends on SQL dialect, schema, constraints and transactions. Test important derived queries, JPQL/native queries, projections, pagination, locking and fetch behavior.

For Spring Boot, `@DataJpaTest` is useful for focused repository tests; Testcontainers is often better than H2 for production-like behavior.

#### Deep dive

Tests should call `flush()` and sometimes `clear()` to force SQL and avoid passing only because entities are still managed.

#### Production angle

Good persistence tests catch schema drift, bad mappings, N+1 regressions and transaction assumptions before deployment.

#### Traps / caveats

- Mocking repositories does not test mappings or SQL.
- H2 may not behave like PostgreSQL.
- Rollback-based tests can hide commit-time issues.

#### Optional Anki

Q: Why should repository tests use a database?
A: JPA behavior depends on real SQL, schema and transaction behavior.

</details>

<a id="jpa-test-002"></a>

<details>
<summary><strong>JPA-TEST-002. What is the difference between `@DataJpaTest` and a full integration test?</strong></summary>

#### Short answer

`@DataJpaTest` loads a JPA-focused slice; a full integration test loads the broader application context and more real wiring.

#### Interview answer

`@DataJpaTest` is optimized for repository and persistence tests. It usually configures repositories, entity manager and database-related beans, often with transactional rollback after each test.

A full integration test loads controllers, services, security, messaging and other application wiring. Use it when behavior depends on the full stack.

#### Deep dive

Slice tests are faster and focused, but they can miss service transaction boundaries, security filters and production configuration.

#### Production angle

Use a mix: focused repository tests for query correctness and full tests for end-to-end transactional use cases.

#### Traps / caveats

- `@DataJpaTest` may replace the database unless configured not to.
- Rollback can hide commit/constraint behavior.
- Full tests are slower and should be targeted.

#### Optional Anki

Q: What is `@DataJpaTest` best for?
A: Focused JPA repository and mapping tests.

</details>

<a id="jpa-test-003"></a>

<details>
<summary><strong>JPA-TEST-003. Why can H2 tests differ from PostgreSQL production behavior, and when should you use Testcontainers?</strong></summary>

#### Short answer

H2 has different SQL dialect, types, locking, indexes and constraints; use Testcontainers when production behavior matters.

#### Interview answer

H2 is fast and convenient, but it is not PostgreSQL. Differences appear in JSON, arrays, enums, timestamp behavior, locking, isolation, sequences, generated SQL compatibility, indexes and query plans.

Use Testcontainers for repository behavior that depends on the real database dialect, migrations, locking, native SQL or performance-sensitive queries.

#### Deep dive

Compatibility modes help but do not make H2 identical to PostgreSQL.

#### Production angle

Tests that pass on H2 can still fail at startup or behave differently in production.

#### Traps / caveats

- Native SQL should be tested on the real engine.
- Locking tests need production-like database behavior.
- Flyway/Liquibase migrations should run in tests.

#### Optional Anki

Q: Why use Testcontainers for JPA tests?
A: To test against the same database engine behavior used in production.

</details>

<a id="jpa-test-004"></a>

<details>
<summary><strong>JPA-TEST-004. How do you test mappings and database constraints?</strong></summary>

#### Short answer

Persist representative entities, force flush, clear the context, reload data and verify database-enforced constraints fail when violated.

#### Interview answer

A good mapping test does not only call `save()`. It flushes to force SQL and constraints, clears to avoid reading from first-level cache, and reloads from the database. For constraints, intentionally insert invalid data and assert the expected exception or translated error.

Run migrations before tests so mappings and schema are checked together.

#### Deep dive

Testing only managed in-memory entities can pass even if columns, joins or constraints are wrong.

#### Production angle

Mapping/constraint tests catch startup failures, missing foreign keys, wrong nullability and enum/schema drift.

#### Traps / caveats

- Without flush, SQL may not run.
- Without clear, reload may come from first-level cache.
- Exception types may differ by provider/database.

#### Optional Anki

Q: Why call `flush()` in mapping tests?
A: To force SQL and database constraints to execute.

</details>

<a id="jpa-test-005"></a>

<details>
<summary><strong>JPA-TEST-005. How do you test N+1 query prevention and SQL statement counts?</strong></summary>

#### Short answer

Use realistic parent/child data and assert query counts with a datasource proxy, Hibernate statistics or test helper.

#### Interview answer

Create several parent rows with related data, execute the service/repository method, map the DTOs, and count SQL statements. The test should include the code that actually accesses associations, not only the initial repository call.

If query count grows with row count, N+1 is likely.

#### Deep dive

Statement count tests are best for important endpoints where query budgets matter. They should be stable and not overfit unrelated SQL.

#### Production angle

These tests prevent performance regressions when someone adds a field to a DTO mapper.

#### Traps / caveats

- Test with multiple rows.
- Include serialization/mapping access if that is where lazy loading happens.
- Clear cache between tests if needed.

#### Optional Anki

Q: What pattern indicates N+1 in tests?
A: SQL count grows linearly with number of parent rows.

</details>

<a id="jpa-test-006"></a>

<details>
<summary><strong>JPA-TEST-006. How do you test optimistic and pessimistic locking?</strong></summary>

#### Short answer

Use separate transactions or entity managers to simulate concurrent access and verify conflict, blocking or timeout behavior.

#### Interview answer

For optimistic locking, load the same entity in two transactions, update and commit one, then try to commit the other and expect an optimistic locking failure. For pessimistic locking, use separate transactions and verify lock wait, timeout or blocked update behavior.

These tests should use the production database engine when possible.

#### Deep dive

Concurrency tests need careful coordination with latches or transaction templates so operations overlap predictably.

#### Production angle

Lock tests catch lost update risks and database-specific locking behavior before incidents.

#### Traps / caveats

- H2 may not match PostgreSQL/MySQL locking.
- Transactional test rollback can hide timing.
- Avoid flaky sleeps; use coordination primitives.

#### Optional Anki

Q: What do optimistic locking tests need?
A: Two separate transactions modifying the same versioned row.

</details>

<a id="jpa-test-007"></a>

<details>
<summary><strong>JPA-TEST-007. Why can rollback-after-test hide real transaction behavior?</strong></summary>

#### Short answer

Rollback avoids commit, so commit-time constraints, after-commit hooks and transaction synchronization behavior may not run as in production.

#### Interview answer

Spring transactional tests often roll back automatically after each test. That keeps the database clean, but it can hide behavior that happens at commit time, such as constraint checks in some databases, transaction synchronizations, outbox publishing triggers or application code after commit.

Some tests should commit or use separate transactions deliberately.

#### Deep dive

Rollback tests can also pass because the persistence context still contains data that was never committed and reloaded.

#### Production angle

Commit behavior matters for messaging, auditing, constraints, locks and integration flows.

#### Traps / caveats

- Not every persistence bug appears before commit.
- Use `flush()` to catch many SQL errors earlier.
- Use full integration tests for after-commit behavior.

#### Optional Anki

Q: What can rollback-based tests miss?
A: Commit-time behavior and after-commit side effects.

</details>

<a id="jpa-test-008"></a>

<details>
<summary><strong>JPA-TEST-008. When should tests explicitly call `flush()` and `clear()`?</strong></summary>

#### Short answer

Call `flush()` to force SQL execution and `clear()` to ensure later reads come from the database, not the first-level cache.

#### Interview answer

Use `flush()` when testing constraints, generated SQL, dirty checking, cascades, orphan removal or optimistic locking. Use `clear()` before reloading an entity to prove the data was actually persisted and mapped correctly.

This is especially important in repository tests that otherwise inspect managed in-memory objects.

#### Deep dive

`flush()` catches SQL and constraint issues, while `clear()` catches mapping and reload issues.

#### Production angle

These calls make tests closer to real transaction/database behavior.

#### Traps / caveats

- `flush()` is not commit.
- `clear()` detaches everything.
- Do not sprinkle them without knowing what behavior is being tested.

#### Optional Anki

Q: Why call `clear()` before assertions?
A: To avoid reading from the first-level cache.

</details>

<a id="jpa-test-009"></a>

<details>
<summary><strong>JPA-TEST-009. How do you test custom JPQL, native queries and projections?</strong></summary>

#### Short answer

Run them against realistic schema/data, assert returned shape, edge cases, sorting, pagination and database-specific behavior.

#### Interview answer

For JPQL and projections, test constructor/interface mapping, null values, joins and filters. For native queries, run against the production database engine because syntax and types are database-specific. For pagination, verify ordering and count behavior.

Use data that exercises joins, missing relationships and multiple rows.

#### Deep dive

Native queries should be tested with migrations because they depend on physical table and column names.

#### Production angle

Custom queries often power important endpoints and can fail silently with wrong result shapes or slow plans.

#### Traps / caveats

- Do not test only the happy path.
- Include multiple rows with same sort value.
- Verify projection field ordering/names.

#### Optional Anki

Q: Why test native queries with Testcontainers?
A: Native SQL depends on the real database dialect.

</details>

<a id="jpa-test-010"></a>

<details>
<summary><strong>JPA-TEST-010. How do you test database migrations together with JPA mappings?</strong></summary>

#### Short answer

Run migrations on an empty database, start the JPA context with validation, and execute mapping/query tests against the migrated schema.

#### Interview answer

The test should apply Flyway/Liquibase migrations, then let Hibernate validate mappings against the schema. After startup, run representative repository tests to verify constraints, joins, indexes where relevant and query compatibility.

This catches drift between entity annotations and real schema.

#### Deep dive

For rolling deployments, also test compatibility between old/new application versions and expand-contract migration steps when possible.

#### Production angle

Mapping/migration drift can cause startup failures or runtime SQL errors immediately after deployment.

#### Traps / caveats

- Do not rely on `ddl-auto=update` in tests if production uses migrations.
- Validate native queries too.
- Include enum and column rename migrations.

#### Optional Anki

Q: What should own production schema changes?
A: Versioned migrations such as Flyway or Liquibase.

</details>

<a id="jpa-mig-001"></a>

<details>
<summary><strong>JPA-MIG-001. What is Hibernate DDL auto-generation, and why is `ddl-auto=update` dangerous in production?</strong></summary>

#### Short answer

Hibernate can generate or update schema from mappings, but `ddl-auto=update` is unsafe for controlled production migrations.

#### Interview answer

DDL auto-generation uses entity mappings to create, validate or update database schema. It is useful for demos or local development. In production, `update` can make unexpected schema changes, miss complex migrations, fail on data changes or produce different results across versions.

Production schema should be changed through reviewed, versioned migrations.

#### Deep dive

Hibernate mappings do not express every migration concern: backfills, lock avoidance, concurrent index creation, data conversion and rolling compatibility.

#### Production angle

An automatic schema update can break startup, lock tables or corrupt assumptions during deployment.

#### Traps / caveats

- Use `validate` in production-like environments.
- Use migrations for actual changes.
- Generated DDL may not match DBA/platform requirements.

#### Optional Anki

Q: Why avoid `ddl-auto=update` in production?
A: Schema changes need reviewed, versioned, data-safe migrations.

</details>

<a id="jpa-mig-002"></a>

<details>
<summary><strong>JPA-MIG-002. Why should Flyway or Liquibase own production schema changes?</strong></summary>

#### Short answer

They provide explicit, versioned, reviewed migrations that can handle data, rollout order and rollback planning.

#### Interview answer

Production schema changes are more than matching annotations. They may require adding nullable columns first, backfilling data, creating indexes safely, changing constraints later and supporting old/new app versions during rolling deployment.

Flyway or Liquibase makes these changes explicit and repeatable.

#### Deep dive

Migration tools also create a history of applied changes, which helps audits and environment consistency.

#### Production angle

Controlled migrations reduce deployment risk, table locks and schema drift.

#### Traps / caveats

- Migrations must be idempotent in operational process, not necessarily in SQL text.
- Rollback strategy should be planned before deploy.
- Application and DB changes must be ordered.

#### Optional Anki

Q: What is the main benefit of versioned migrations?
A: Repeatable, reviewed schema evolution across environments.

</details>

<a id="jpa-mig-003"></a>

<details>
<summary><strong>JPA-MIG-003. How do you safely add a non-null column used by an entity?</strong></summary>

#### Short answer

Add it nullable or with a safe default, deploy compatible code, backfill data, then add the non-null constraint.

#### Interview answer

A safe rollout is usually expand and contract. First add the column in a way old code still works. Backfill existing rows in batches. Deploy code that writes the column. After all rows are populated and all app versions are compatible, add the `NOT NULL` constraint.

Avoid one big blocking migration on a large table.

#### Deep dive

Some databases can add defaults efficiently, others rewrite tables depending on version and operation. Verify with the target database.

#### Production angle

Large table changes can lock writes or overload the database if done in one step.

#### Traps / caveats

- Old application versions must tolerate the new column.
- Backfills should be batched.
- Entity validation should align with rollout stage.

#### Optional Anki

Q: Safe pattern for non-null column rollout?
A: Add nullable/default, backfill, deploy writers, then enforce non-null.

</details>

<a id="jpa-mig-004"></a>

<details>
<summary><strong>JPA-MIG-004. How do you safely rename a column, change a relationship mapping or add an index?</strong></summary>

#### Short answer

Use expand-contract migrations, support old and new schema during rollout, and create indexes safely for the database.

#### Interview answer

For renames, add the new column, dual-write or backfill, switch reads, then remove the old column later. For relationship changes, introduce new foreign keys/tables without breaking old code, migrate data, then switch application logic. For indexes, create them in a way that avoids blocking normal traffic where the database supports it.

JPA mappings should change only when the schema and deployment order are ready.

#### Deep dive

Rolling deployments mean old and new app versions may run at the same time, so compatibility windows matter.

#### Production angle

Unsafe schema changes are a frequent cause of failed deploys and table locks.

#### Traps / caveats

- A column rename can break old app versions immediately.
- Adding an index can be expensive on large tables.
- Foreign key validation may need staged rollout.

#### Optional Anki

Q: What migration pattern helps rolling deployments?
A: Expand and contract.

</details>

<a id="jpa-mig-005"></a>

<details>
<summary><strong>JPA-MIG-005. How can entity changes break old application versions during rolling deployment?</strong></summary>

#### Short answer

Old and new versions may run against the same database, so incompatible schema or mapping changes can break one of them.

#### Interview answer

If a new version renames a column, changes enum representation or expects a non-null field before old versions write it, rolling deployment can fail. Old code may not know about new constraints; new code may not tolerate old data.

Schema changes should be backward and forward compatible during the rollout window.

#### Deep dive

This is why destructive changes usually happen after all app instances have moved to the compatible version and data has been migrated.

#### Production angle

In Kubernetes or blue/green deploys, mixed versions are normal, so migration ordering is part of application design.

#### Traps / caveats

- Do not drop columns in the same deploy that stops writing them.
- Do not add strict constraints before data is ready.
- Test rollback paths.

#### Optional Anki

Q: Why are destructive DB changes delayed?
A: Old app versions may still need the old schema during rollout.

</details>

<a id="jpa-mig-006"></a>

<details>
<summary><strong>JPA-MIG-006. How do you handle enum changes and large data backfills safely?</strong></summary>

#### Short answer

Use stable enum storage and deploy-compatible values; run large backfills in bounded batches with monitoring and throttling.

#### Interview answer

For enums, avoid ordinal storage. Add new values in a way old code can tolerate or gate rollout carefully. If renaming/removing values, migrate data explicitly and handle unknown values defensively where needed.

For backfills, process rows in batches, commit frequently, monitor load, avoid long locks and make the operation resumable.

#### Deep dive

Backfills should have idempotent logic, progress tracking and a way to pause or roll back/compensate.

#### Production angle

Backfills can compete with online traffic and cause replication lag, lock waits or connection pool pressure.

#### Traps / caveats

- `EnumType.ORDINAL` makes enum migrations dangerous.
- Do not update millions of rows in one transaction.
- Coordinate application code with data state.

#### Optional Anki

Q: How should large backfills usually run?
A: In small monitored batches with resumability.

</details>

<a id="jpa-mig-007"></a>

<details>
<summary><strong>🧠 JPA-MIG-007. How can Hibernate naming strategies affect migrations and startup validation?</strong></summary>

#### Short answer

Naming strategies map Java names to database names; changes can make Hibernate expect different tables/columns than migrations created.

#### Interview answer

Hibernate has implicit and physical naming strategies that determine table, column, join table and constraint names when names are not explicit. If strategy changes during a framework upgrade or configuration change, Hibernate may look for different schema objects.

This can break startup validation or generated SQL.

#### Deep dive

Explicit names reduce surprises for important schema objects, especially when migrations are hand-written.

#### Production angle

Naming mismatches can cause deployment startup failures even though code compiled and migrations ran.

#### Traps / caveats

- Framework upgrades can change defaults.
- Case sensitivity and quoting vary by database.
- Validate mappings against migrated schema in CI.

#### Optional Anki

Q: Why care about Hibernate naming strategy?
A: It determines expected physical database object names.

</details>
