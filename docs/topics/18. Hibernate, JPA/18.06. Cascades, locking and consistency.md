# Cascades, locking and consistency

---

<a id="jpa-cascade-001"></a>

<details>
<summary><strong>JPA-CASCADE-001. When are cascading operations useful, and when are they dangerous?</strong></summary>

#### Short answer

Cascades are useful when child lifecycle is owned by the parent; they are dangerous when applied to shared or independent entities.

#### Interview answer

Cascading lets an operation on one entity propagate to related entities, for example persisting an `Order` with new `OrderLine` children. This is appropriate when the parent owns the child lifecycle.

It is dangerous when used on shared references such as users, roles, products or tags. A parent operation can accidentally update, merge or delete data that should live independently.

#### Deep dive

Cascade should express lifecycle ownership, not convenience. Different operations may need different cascade types.

#### Production angle

Bad cascade settings can cause accidental mass deletes, huge merge graphs and unexpected SQL storms.

#### Traps / caveats

- Do not use `CascadeType.ALL` everywhere.
- Be especially careful with remove cascades.
- Test cascades with `flush()` and `clear()`.

#### Optional Anki

Q: What should cascade usually represent?
A: Lifecycle ownership.

</details>

<a id="jpa-cascade-002"></a>

<details>
<summary><strong>JPA-CASCADE-002. Why is `CascadeType.REMOVE` dangerous on `@ManyToMany`?</strong></summary>

#### Short answer

Many-to-many targets are usually shared, so removing one entity can accidentally delete records still used by others.

#### Interview answer

In a many-to-many relationship, both sides often have independent lifecycle. For example, deleting a user should remove rows from `user_role`, not delete the shared `Role` entity itself. `CascadeType.REMOVE` can propagate deletes to shared target rows.

Usually the join table row should be deleted, not the target entity.

#### Deep dive

If the relationship has ownership, metadata or lifecycle, model the join table as an explicit entity instead of direct many-to-many.

#### Production angle

This bug can delete shared roles, tags, categories or permissions and cause broad data loss.

#### Traps / caveats

- Do not cascade remove to shared lookup/reference data.
- Database foreign keys may block the delete, but do not rely on failure as design.
- Direct many-to-many is often too weak for real domains.

#### Optional Anki

Q: What should deleting a many-to-many relation usually remove?
A: The join row, not the shared target entity.

</details>

<a id="jpa-cascade-003"></a>

<details>
<summary><strong>JPA-CASCADE-003. How is `orphanRemoval = true` different from `CascadeType.REMOVE`?</strong></summary>

#### Short answer

`CascadeType.REMOVE` propagates parent removal; `orphanRemoval` deletes a child when it is removed from the owning collection/reference.

#### Interview answer

With `CascadeType.REMOVE`, deleting the parent deletes the child too. With `orphanRemoval = true`, a child is deleted when it no longer belongs to the parent, even if the parent remains.

This is useful for parent-owned children such as `OrderLine` records.

#### Deep dive

Orphan removal means the child cannot exist independently from the parent. It should not be used for shared references.

#### Production angle

It makes aggregate cleanup easy, but a mistaken collection update can delete rows permanently.

#### Traps / caveats

- Removing from a collection can delete from the database.
- It requires clear ownership semantics.
- It should be tested with flush/clear and real constraints.

#### Optional Anki

Q: What triggers orphan removal?
A: A child being disassociated from its owning parent.

</details>

<a id="jpa-cascade-004"></a>

<details>
<summary><strong>JPA-CASCADE-004. How do orphan removal, aggregate ownership and database `ON DELETE CASCADE` relate?</strong></summary>

#### Short answer

All can delete dependent rows, but they operate at different layers and should match the ownership model.

#### Interview answer

Orphan removal is ORM-level lifecycle behavior: removing a child from the parent collection deletes it. Aggregate ownership is a domain concept: the parent controls child lifecycle. Database `ON DELETE CASCADE` is a database constraint action when a referenced parent row is deleted.

They should be aligned, but they are not the same mechanism.

#### Deep dive

Database cascade may bypass ORM callbacks and in-memory state. ORM cascade may issue explicit deletes and participate in entity lifecycle behavior.

#### Production angle

Mixing both without understanding can produce missing audit events, stale persistence context state or unexpected delete order.

#### Traps / caveats

- DB cascade does not update already managed entities in memory.
- ORM cascade can be slower for huge child sets.
- Use database constraints regardless of ORM cascade.

#### Optional Anki

Q: What layer enforces `ON DELETE CASCADE`?
A: The database.

</details>

<a id="jpa-cascade-005"></a>

<details>
<summary><strong>JPA-CASCADE-005. Why can cascading `merge()` over a detached graph be expensive or unsafe?</strong></summary>

#### Short answer

It may traverse a large detached graph, load many managed instances and copy stale or null state into the database.

#### Interview answer

`merge()` copies detached state into managed entities. If merge cascades across associations, Hibernate may process a large object graph, issue many selects and updates, and overwrite fields the caller did not intend to change.

This is especially dangerous when detached objects come from API requests.

#### Deep dive

Merge is not a patch operation. It copies state. Partial DTO data should be applied explicitly to a managed entity.

#### Production angle

Cascading merge can cause lost updates, mass assignment vulnerabilities, slow requests and high memory usage.

#### Traps / caveats

- Do not merge request JSON entities.
- Be careful with null fields.
- Avoid cascading merge to large shared graphs.

#### Optional Anki

Q: Why is cascading merge risky?
A: It can copy stale or incomplete detached graph state into managed entities.

</details>

<a id="jpa-lock-001"></a>

<details>
<summary><strong>JPA-LOCK-001. What is optimistic locking, and how does `@Version` work?</strong></summary>

#### Short answer

Optimistic locking detects conflicting updates using a version column checked during update/delete.

#### Interview answer

An entity has a `@Version` field. When Hibernate updates the row, it includes the old version in the `WHERE` clause and increments the version. If another transaction already changed the row, the version no longer matches and no row is updated. Hibernate then throws an optimistic locking exception.

This is good when conflicts are possible but not constant.

#### Deep dive

Optimistic locking does not block readers or writers in advance. It detects conflicts at flush/commit time.

#### Production angle

It protects against lost updates in workflows such as profile edits, order changes and admin screens.

#### Traps / caveats

- You need a version field on the entity being updated.
- Bulk updates can bypass version handling.
- The application must decide retry or user conflict behavior.

#### Optional Anki

Q: What does `@Version` help detect?
A: Concurrent updates to the same entity row.

</details>

<a id="jpa-lock-002"></a>

<details>
<summary><strong>JPA-LOCK-002. What is a lost update, and how can JPA help prevent it?</strong></summary>

#### Short answer

A lost update happens when two transactions read the same value and one overwrites the other's change; JPA can prevent it with optimistic or pessimistic locking.

#### Interview answer

Example: two users load the same order, both change the status, and the last commit overwrites the first without detecting a conflict. With optimistic locking, the second commit fails because the version changed. With pessimistic locking, one transaction can lock the row before updating.

The right choice depends on conflict frequency and user experience.

#### Deep dive

Database isolation alone may not protect every application-level lost update pattern, especially when read-modify-write spans user think time or detached DTOs.

#### Production angle

Lost updates are severe in money, inventory, workflow and approval systems.

#### Traps / caveats

- Version must be included in DTO/update flows.
- Retrying blindly can overwrite user intent.
- Atomic SQL updates or constraints may be better for counters.

#### Optional Anki

Q: What is the usual JPA mechanism for lost update detection?
A: Optimistic locking with `@Version`.

</details>

<a id="jpa-lock-003"></a>

<details>
<summary><strong>JPA-LOCK-003. Can optimistic locking protect against all consistency problems?</strong></summary>

#### Short answer

No. It detects conflicting updates to versioned rows, but it does not enforce every business invariant or multi-row consistency rule.

#### Interview answer

Optimistic locking works well when concurrent changes target the same versioned entity. It does not automatically protect constraints across multiple rows, aggregate boundaries, external systems or read-only decisions that depend on a set of rows.

For those cases you may need database constraints, unique indexes, pessimistic locks, serializable isolation, atomic SQL, outbox patterns or explicit domain design.

#### Deep dive

Write skew is a classic example where two transactions update different rows while violating a shared invariant.

#### Production angle

Senior engineers should combine JPA locking with database-level invariants and retry/idempotency policies.

#### Traps / caveats

- Versioning one row does not protect all rows.
- Detached updates must carry version information.
- Retries must be safe and business-aware.

#### Optional Anki

Q: Does optimistic locking enforce all business invariants?
A: No. It detects conflicts on versioned entities.

</details>

<a id="jpa-lock-004"></a>

<details>
<summary><strong>JPA-LOCK-004. How should an application handle `OptimisticLockException`?</strong></summary>

#### Short answer

Roll back the transaction and either ask the user to retry/merge changes or perform a safe automated retry if the operation is idempotent.

#### Interview answer

An optimistic lock conflict means the data changed since the caller read it. The current transaction should be rolled back. For user-driven edits, return a conflict response and let the user refresh or resolve differences. For background jobs, retry only when the operation is idempotent and still valid with fresh data.

Do not swallow the exception and continue in the same persistence context.

#### Deep dive

HTTP APIs often map this to `409 Conflict`. The response should not leak internal details but should clearly signal concurrent modification.

#### Production angle

Conflict rates should be monitored. A spike may indicate a workflow design issue or a hot row.

#### Traps / caveats

- Blind retry can reapply stale intent.
- The transaction is usually rollback-only.
- The version field should be part of update protocols.

#### Optional Anki

Q: Common HTTP status for optimistic update conflict?
A: `409 Conflict`.

</details>

<a id="jpa-lock-005"></a>

<details>
<summary><strong>JPA-LOCK-005. How do detached DTO updates interact with optimistic locking?</strong></summary>

#### Short answer

The DTO must carry enough version information so the update can detect whether the entity changed since it was read.

#### Interview answer

If a client reads an entity and later sends an update, the server should compare the version from the client with the current version. With JPA, this usually means loading the managed entity, checking/applying the version, then applying allowed DTO fields.

If the version is omitted, the update can overwrite newer data without detecting conflict.

#### Deep dive

Do not rely on merging a detached entity from the request. Use command DTOs and explicit field updates.

#### Production angle

Detached update conflicts are common in admin UIs and REST APIs where users edit stale forms.

#### Traps / caveats

- Include version in update DTOs where lost update matters.
- Do not expose version as authorization.
- Handle conflict response deliberately.

#### Optional Anki

Q: Why include version in update DTOs?
A: To detect stale client updates.

</details>

<a id="jpa-lock-006"></a>

<details>
<summary><strong>JPA-LOCK-006. What is pessimistic locking, and what do the main pessimistic lock modes mean?</strong></summary>

#### Short answer

Pessimistic locking asks the database to lock rows before updating, commonly with read/write lock modes.

#### Interview answer

Pessimistic locking assumes conflict is likely, so it prevents concurrent access by acquiring database locks. `PESSIMISTIC_WRITE` usually maps to an exclusive row lock for updates. `PESSIMISTIC_READ` is a shared/read-oriented lock where supported. `PESSIMISTIC_FORCE_INCREMENT` also forces version increment.

Use it for short critical sections where waiting is acceptable.

#### Deep dive

Exact SQL and behavior depend on the database dialect. It may use `SELECT ... FOR UPDATE` or similar constructs.

#### Production angle

Pessimistic locks can protect hot resources but can also reduce throughput and create deadlocks.

#### Traps / caveats

- Keep locked transactions short.
- Always set timeouts where appropriate.
- Know database-specific behavior.

#### Optional Anki

Q: What does pessimistic locking do?
A: It acquires database locks before concurrent changes happen.

</details>

<a id="jpa-lock-007"></a>

<details>
<summary><strong>JPA-LOCK-007. When should pessimistic locking be used, and what risks does it introduce?</strong></summary>

#### Short answer

Use it for short high-conflict critical sections; risks include blocking, deadlocks, timeouts and lower throughput.

#### Interview answer

Pessimistic locking is appropriate when conflicts are frequent and retrying optimistic failures would be worse. Examples include selecting the next job, reserving a scarce resource or protecting a small hot aggregate.

It introduces blocking. If locks are held during slow code or external calls, the system can degrade quickly.

#### Deep dive

Pessimistic locking should be combined with consistent lock ordering, small transaction scope and timeout handling.

#### Production angle

Lock waits can cause connection pool exhaustion and tail latency spikes.

#### Traps / caveats

- Never hold database locks while calling slow external services.
- Deadlocks can still happen.
- Pessimistic locking is not a replacement for constraints.

#### Optional Anki

Q: Main operational risk of pessimistic locking?
A: Blocking and deadlocks.

</details>

<a id="jpa-lock-008"></a>

<details>
<summary><strong>🧠 JPA-LOCK-008. How do lock timeouts and JPA lock modes map to database behavior?</strong></summary>

#### Short answer

JPA lock modes are provider-level requests that Hibernate translates to database-specific locking SQL and timeout settings where supported.

#### Interview answer

A lock mode such as `PESSIMISTIC_WRITE` may become `SELECT ... FOR UPDATE`, but exact syntax differs by database. Lock timeout hints may map to database wait policies, driver settings or provider behavior. Some databases support `NOWAIT` or skip-locked semantics; others differ.

A senior answer should say: check the dialect and generated SQL.

#### Deep dive

Timeout exceptions do not necessarily mean the transaction can continue safely. Treat them as failed unit-of-work events unless carefully designed otherwise.

#### Production angle

Lock timeout behavior affects user errors, retries, job workers and incident diagnosis.

#### Traps / caveats

- JPA abstracts locking but does not erase database differences.
- Test with the production database.
- Lock timeout settings may not work identically in H2.

#### Optional Anki

Q: How do you verify a pessimistic lock mode?
A: Inspect generated SQL and test on the production database engine.

</details>

<a id="jpa-lock-009"></a>

<details>
<summary><strong>JPA-LOCK-009. What is the difference between database isolation level and JPA lock mode?</strong></summary>

#### Short answer

Isolation level controls transaction visibility/anomalies; JPA lock mode requests specific locking or version checks for entities.

#### Interview answer

Isolation is configured at the database transaction level, such as read committed or serializable. It affects what reads can observe and how concurrent transactions interact. JPA lock modes are explicit operations on entities or queries, such as optimistic version checks or pessimistic row locks.

They can be used together but solve different parts of concurrency control.

#### Deep dive

Some anomalies require database constraints or stronger isolation, not just entity locks.

#### Production angle

Using a lock mode without understanding isolation can still leave reporting, aggregate or multi-row invariants exposed.

#### Traps / caveats

- Read committed plus optimistic locking is common but not universal.
- Serializable may require retry handling.
- Pessimistic locks can still deadlock.

#### Optional Anki

Q: What does isolation level control?
A: Visibility and anomalies across database transactions.

</details>

<a id="jpa-lock-010"></a>

<details>
<summary><strong>🧠 JPA-LOCK-010. How do bulk updates interact with optimistic locking?</strong></summary>

#### Short answer

Bulk updates bypass normal entity dirty checking and may also bypass automatic version checks unless the query updates versions deliberately.

#### Interview answer

JPQL bulk updates operate directly on database rows. They do not load each entity and compare its `@Version` field like normal managed updates. That means optimistic locking semantics may not apply unless the bulk query explicitly includes version predicates and increments.

After a bulk update, managed entities may also be stale.

#### Deep dive

Bulk operations are powerful for maintenance and batch updates, but they are closer to SQL than normal entity changes.

#### Production angle

A bulk status change can silently overwrite rows that another transaction updated unless version handling is part of the query design.

#### Traps / caveats

- Flush before bulk operations.
- Clear after bulk operations when affected entities may be managed.
- Add version predicates when conflict detection matters.

#### Optional Anki

Q: Do JPQL bulk updates automatically behave like normal versioned entity updates?
A: No.

</details>

<a id="jpa-lock-011"></a>

<details>
<summary><strong>JPA-LOCK-011. How would you design concurrent update handling for an aggregate?</strong></summary>

#### Short answer

Define the invariant, choose optimistic or pessimistic locking based on conflict rate, enforce database constraints, and design retry/conflict behavior.

#### Interview answer

I would first identify what must stay consistent. For normal user edits, optimistic locking with `@Version` is often enough. For high-conflict short operations, pessimistic locking or atomic SQL may be better. For uniqueness or state rules, add database constraints. For cross-aggregate workflows, consider outbox, idempotency and eventual consistency.

The API should expose conflict behavior clearly.

#### Deep dive

Concurrency design is not only an annotation choice. It includes transaction scope, isolation, lock ordering, retries and user experience.

#### Production angle

Monitoring conflict rates, deadlocks and retries tells whether the strategy fits real traffic.

#### Traps / caveats

- Do not lock more rows than necessary.
- Do not retry non-idempotent operations blindly.
- Do not rely only on application checks for uniqueness.

#### Optional Anki

Q: First step in aggregate concurrency design?
A: Identify the invariant that must be protected.

</details>

<a id="jpa-lock-012"></a>

<details>
<summary><strong>🧠 JPA-LOCK-012. How can constraints or atomic database updates prevent concurrency anomalies that JPA alone cannot?</strong></summary>

#### Short answer

Database constraints and atomic SQL enforce invariants at the data layer, even under concurrent access and from non-JPA writers.

#### Interview answer

For example, a unique constraint prevents duplicate usernames under concurrent registration. An atomic update like `update account set balance = balance - ? where id = ? and balance >= ?` can prevent negative balances without read-then-write races. Foreign keys and check constraints protect structural rules.

JPA is useful, but database invariants are the final safety net.

#### Deep dive

Some invariants require exclusion constraints, partial indexes, serializable isolation or explicit locks depending on the database and rule.

#### Production angle

Database constraints prevent corruption from bugs, scripts, imports, other services and race conditions.

#### Traps / caveats

- Application validation improves UX but does not replace constraints.
- Constraint errors must be translated into useful API errors.
- Atomic updates need row-count checks.

#### Optional Anki

Q: Why use database constraints with JPA?
A: They enforce invariants for all concurrent writers.

</details>
