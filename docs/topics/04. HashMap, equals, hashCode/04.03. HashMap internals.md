# 04.03. HashMap internals

---

<a id="hm-internal-001"></a>

<details>
<summary><strong>HM-INTERNAL-001. How is `HashMap` structured internally?</strong></summary>

#### Short answer

`HashMap` stores entries in an internal table of buckets. Each entry stores hash, key, value and a link to the next node; heavily collided buckets can become tree bins.

#### Interview answer

At a high level, a `HashMap` is an array of buckets. A key's hash determines which bucket to use. If the bucket is empty, the entry is stored there. If multiple keys land in the same bucket, entries are kept in a chain or, after specific thresholds, in a red-black tree-like bin.

The map also tracks size, load factor, resize threshold and structural modification count.

#### Deep dive

In OpenJDK, ordinary bucket entries are nodes containing `hash`, `key`, `value` and `next`. Tree bins use a specialized tree node structure. The internal table is allocated lazily, so an empty `HashMap` does not immediately allocate the bucket array.

`HashMap` is optimized for expected constant-time lookup when hashes are well distributed.

#### Production angle

Understanding the structure helps explain memory overhead, iteration cost, latency spikes during resize, and why bad key equality can break lookups.

#### Traps / caveats

- `HashMap` is not just "an array"; collisions require extra structures.
- Capacity is bucket count, not number of stored entries.
- The internal structure is implementation detail, not API contract.

#### Optional Anki

Q: What does a normal `HashMap` node store?
A: Hash, key, value and a reference to the next node in the bucket.

</details>

<a id="hm-internal-002"></a>

<details>
<summary><strong>HM-INTERNAL-002. How does `HashMap` turn a key into a bucket index?</strong></summary>

#### Short answer

It computes a hash for the key, applies a spreading step, then maps it to an index using the table capacity.

#### Interview answer

Modern `HashMap` gets the key's `hashCode()`, mixes high bits into low bits, and then uses `(capacity - 1) & hash` to choose a bucket. This works efficiently because the table capacity is a power of two.

The null key is handled specially with hash `0`.

#### Deep dive

The spreading step helps because a power-of-two table index uses low bits. If a key's `hashCode()` has useful variation only in high bits, simple masking would distribute poorly. Mixing high bits into low bits improves common cases.

After the bucket is selected, `HashMap` still uses hash and `equals()` to find the exact key.

#### Production angle

If a custom key returns poor low-bit hashes or constant hashes, many entries can land in the same bucket. The spreading step helps but cannot fix a bad key model.

#### Traps / caveats

- `hashCode()` is not used directly as an array index.
- Bucket index changes when the table resizes.
- A matching bucket does not prove key equality.

#### Optional Anki

Q: Why can `HashMap` use `(n - 1) & hash`?
A: Because its table capacity is a power of two.

</details>

<a id="hm-internal-003"></a>

<details>
<summary><strong>HM-INTERNAL-003. Why is `HashMap` capacity usually a power of two?</strong></summary>

#### Short answer

Power-of-two capacity allows fast index calculation with a bit mask and efficient redistribution during resize.

#### Interview answer

When capacity is a power of two, `HashMap` can compute the bucket index as `(capacity - 1) & hash` instead of using modulo. This is fast and works well with the hash spreading step.

It also makes resizing efficient: when capacity doubles, an entry either stays in the same bucket or moves by the old capacity.

#### Deep dive

The trade-off is that low hash bits matter a lot. That is why `HashMap` mixes high bits into low bits before indexing. The map rounds requested capacities to a power of two internally.

#### Production angle

This is why initial capacity values are not always used exactly. Asking for capacity 100 does not mean the table will have exactly 100 buckets.

#### Traps / caveats

- Power-of-two capacity does not make bad hashes good.
- Initial capacity is bucket capacity, not expected mappings.
- Resizing changes bucket indexes.

#### Optional Anki

Q: What is the main benefit of power-of-two `HashMap` capacity?
A: Fast masking for bucket index and efficient resize splitting.

</details>

<a id="hm-internal-004"></a>

<details>
<summary><strong>🧠 HM-INTERNAL-004. What hash spreading does `HashMap` perform?</strong></summary>

#### Short answer

Modern `HashMap` mixes a key's high hash bits into its low bits, commonly with `h ^ (h >>> 16)`.

#### Interview answer

Because the bucket index uses the low bits of the hash, `HashMap` applies a small spreading function before indexing. This reduces problems when user `hashCode()` implementations vary mostly in higher bits.

It is a defensive improvement, not a replacement for a good `hashCode()`.

#### Deep dive

The spreading function is intentionally cheap. It does not try to be a cryptographic or perfect hash. Its job is to improve distribution for common keys without adding much overhead to every map operation.

If many keys return the same `hashCode()`, spreading cannot help because there is no information to spread.

#### Production angle

In interviews, this shows that `HashMap` performance depends on both implementation and key design. For hot maps, key hash quality still matters.

#### Traps / caveats

- Spreading is implementation detail.
- It does not make hash codes unique.
- It cannot fix constant hash codes.

#### Optional Anki

Q: Why does `HashMap` spread hash bits?
A: To make power-of-two bucket indexing less sensitive to poor low-bit variation.

</details>

<a id="hm-internal-005"></a>

<details>
<summary><strong>HM-INTERNAL-005. How does `put()` work for new and existing keys?</strong></summary>

#### Short answer

`put()` computes the key hash, finds the bucket, inserts a new node if no equal key exists, or replaces the value if an equal key is found.

#### Interview answer

On `put(k, v)`, `HashMap` initializes or resizes the table if needed, computes the spread hash, and chooses a bucket. If the bucket is empty, it stores a new node. If not, it checks existing nodes with matching hash and `equals()`. If an equal key exists, the value is replaced. Otherwise a new node is appended or inserted into the tree bin.

After adding a new mapping, size increases and resize may be triggered.

#### Deep dive

Replacing a value for an existing key is not a structural modification in the same sense as adding or removing a mapping. Adding a new key changes size and may change iteration behavior.

When a chain becomes long enough, `HashMap` may treeify the bucket if the table is already large enough.

#### Production angle

`put()` can be cheap on average but expensive during resize or heavy collisions. This matters in request paths that build large maps repeatedly.

#### Traps / caveats

- `put()` returns the previous value, or null if none existed or the old value was null.
- Existing key detection checks identity first, then uses `equals()` when needed.
- A mutable key can make later updates miss the original entry.

#### Optional Anki

Q: What happens when `put()` finds an equal existing key?
A: It replaces the value for that key.

</details>

<a id="hm-internal-006"></a>

<details>
<summary><strong>HM-INTERNAL-006. How does `get()` work internally?</strong></summary>

#### Short answer

`get()` computes the key hash, finds the bucket, and searches candidates by hash and `equals()`.

#### Interview answer

`HashMap.get(key)` calculates the spread hash and bucket index. It checks the first node in that bucket, then searches the rest of the chain or tree bin. A candidate matches when the stored hash matches and the keys are identical or equal by `equals()`.

If no matching key is found, it returns null.

#### Deep dive

Returning null is ambiguous because null can mean "absent" or "present with null value." Use `containsKey()` when that distinction matters.

The lookup cost depends on bucket size, equality cost and whether the bucket is a list or tree.

#### Production angle

In hot paths, expensive key equality or bad hash distribution can dominate CPU. Profiling often points to key `equals()` rather than `HashMap` itself.

#### Traps / caveats

- `get()` may call the lookup key's `equals()` against stored candidate keys.
- Null return does not always mean absent.
- Lookup is not thread-safe against concurrent mutation.

#### Optional Anki

Q: What confirms a key match during `HashMap.get()`?
A: Matching stored hash plus key identity or `equals()`.

</details>

<a id="hm-internal-007"></a>

<details>
<summary><strong>🧠 HM-INTERNAL-007. How does `remove()` work internally?</strong></summary>

#### Short answer

`remove()` computes the hash, finds the matching node in the bucket, unlinks it from the list or tree, decrements size and returns the old value.

#### Interview answer

`HashMap.remove(key)` follows the same lookup path as `get()`: hash, bucket, candidate search by hash and equality. If a node is found, it is removed from the bucket structure. For a list bin that means relinking nodes. For a tree bin that means tree removal and possible untreeification.

The map then updates size and structural modification count.

#### Deep dive

There are also conditional removal forms such as `remove(key, value)`, which remove only if both key and value match. Value matching uses equality too, with null-safe handling.

Removal does not usually shrink the internal table. A map that once grew large can remain large after many removals.

#### Production angle

Long-lived maps that grow and shrink may retain a large table. For cache-like behavior, a real cache library with eviction and sizing is usually better.

#### Traps / caveats

- Removing a mutated key may fail because the bucket path changed.
- Removing during iteration must use the iterator's `remove()` or safe collection APIs.
- `remove(key)` returning null can mean absent or removed value was null.

#### Optional Anki

Q: Does `HashMap` automatically shrink after removals?
A: Generally no; the internal table can remain large.

</details>

<a id="hm-internal-008"></a>

<details>
<summary><strong>HM-INTERNAL-008. What is the difference between table capacity and map size?</strong></summary>

#### Short answer

Capacity is the number of buckets in the internal table. Size is the number of key-value mappings stored in the map.

#### Interview answer

`size()` returns how many mappings are present. Capacity is an internal implementation detail: how many bucket slots the table currently has. A map with size 10 can have capacity 16, 32 or more depending on construction and resizing.

#### Deep dive

Load factor and threshold connect the two. With default load factor `0.75`, a capacity of 16 has a resize threshold around 12 mappings. When size exceeds the threshold, the table grows.

Capacity also affects iteration because `HashMap` iterators scan the table and entries.

#### Production angle

Oversized maps waste memory and can slow iteration. Undersized maps resize repeatedly while being populated. Pre-sizing can help when expected size is known.

#### Traps / caveats

- `new HashMap<>(100)` is initial capacity, not exact expected size.
- `size()` does not reveal capacity.
- Removing entries does not necessarily reduce capacity.

#### Optional Anki

Q: What does `HashMap.size()` return?
A: The number of mappings, not bucket capacity.

</details>

<a id="hm-internal-009"></a>

<details>
<summary><strong>🧠 HM-INTERNAL-009. When is the internal table allocated?</strong></summary>

#### Short answer

In modern `HashMap`, the internal table is allocated lazily, usually on first insertion.

#### Interview answer

Constructing an empty `HashMap` does not necessarily allocate the bucket array immediately. The constructor records configuration such as load factor and threshold-related information. The table is created when the map needs storage, typically during the first `put()` or bulk insertion.

#### Deep dive

This lazy allocation avoids wasting arrays for maps that are created but never populated. The exact path depends on the constructor and operation, but the important interview point is that object construction and table allocation are not always the same moment.

#### Production angle

Creating many empty maps still allocates map objects, but lazy table allocation reduces the cost until entries are added. For DTOs with optional maps, this can matter at scale.

#### Traps / caveats

- Initial capacity does not mean the bucket array is immediately allocated.
- The first insertion may include allocation and resize setup cost.
- This is implementation behavior, not a reason to create unnecessary maps.

#### Optional Anki

Q: Does `new HashMap<>()` immediately allocate the bucket table?
A: Modern implementations allocate the table lazily, usually on first insertion.

</details>

<a id="hm-internal-010"></a>

<details>
<summary><strong>HM-INTERNAL-010. Does `HashMap` preserve insertion order, and why should you not rely on its iteration order?</strong></summary>

#### Short answer

No. `HashMap` does not guarantee insertion order or any stable iteration order.

#### Interview answer

`HashMap` iterates according to internal bucket layout, not insertion order. That layout depends on capacity, hashes, resize history and implementation details. The order may look stable in a small test, but it is not part of the contract.

Use `LinkedHashMap` for insertion order and `TreeMap` for sorted key order.

#### Deep dive

Resizing can move entries to different buckets. Different Java versions or key hash behavior can also change iteration order. Relying on accidental order makes tests and APIs fragile.

#### Production angle

Unspecified order can break pagination, JSON snapshots, signing logic or tests that compare serialized output. If order matters, choose an ordered map explicitly.

#### Traps / caveats

- Stable-looking local order is still not guaranteed.
- Sorting after reading from a `HashMap` is different from using a sorted map.
- API responses should not accidentally depend on `HashMap` iteration.

#### Optional Anki

Q: Which map preserves insertion order?
A: `LinkedHashMap`.

</details>

<a id="hm-internal-011"></a>

<details>
<summary><strong>HM-INTERNAL-011. How do `keySet()`, `values()` and `entrySet()` views work, and are they backed by the map?</strong></summary>

#### Short answer

They are backed views over the map. Changes in the map are reflected in the views, and supported removals through the views affect the map.

#### Interview answer

`keySet()` returns a set view of keys, `values()` returns a collection view of values, and `entrySet()` returns a set view of key-value entries. They are not independent copies. Removing from a view removes from the underlying map where supported.

Adding directly to these views is generally not supported because a key-value mapping cannot be inferred from only a key or value.

#### Deep dive

`entrySet()` is usually the best view for iterating when both key and value are needed. `values()` can contain duplicates because different keys can map to equal values. Modifying entry values through `Map.Entry.setValue()` may be supported by mutable map implementations.

#### Production angle

Backed views are useful but can surprise API authors. Returning a live view from internal state can allow callers to mutate the map unless it is wrapped or copied.

#### Traps / caveats

- Views are backed, not snapshots.
- `values()` is a `Collection`, not a `Set`.
- Structural changes during iteration can trigger fail-fast behavior.

#### Optional Anki

Q: Does removing from `map.keySet()` affect the map?
A: Yes, it removes the corresponding mapping.

</details>

<a id="hm-internal-012"></a>

<details>
<summary><strong>HM-INTERNAL-012. Are `HashMap` iterators fail-fast?</strong></summary>

#### Short answer

Yes. `HashMap` iterators are fail-fast on a best-effort basis when the map is structurally modified outside the iterator.

#### Interview answer

If a `HashMap` is structurally modified after an iterator is created, except through that iterator's own `remove()`, the iterator may throw `ConcurrentModificationException`. This is designed to catch bugs, not to provide thread-safety.

#### Deep dive

Fail-fast behavior is implemented using a structural modification count. The iterator records the expected count and compares it while iterating. If it sees a mismatch, it fails.

The behavior is best-effort. You must not write logic that depends on the exception being thrown.

#### Production angle

This commonly appears when code removes entries inside an enhanced `for` loop over `entrySet()`. Use an explicit iterator, `removeIf` on suitable views, or collect keys to remove after iteration.

#### Traps / caveats

- `ConcurrentModificationException` does not always mean multiple threads.
- Fail-fast is not synchronization.
- Updating an existing value is different from adding/removing mappings.

#### Optional Anki

Q: What is the safe iterator removal method?
A: Use the iterator's own `remove()` method.

</details>

<a id="hm-internal-013"></a>

<details>
<summary><strong>🧠 HM-INTERNAL-013. What is `modCount`, and what structural modifications affect `HashMap` iterators?</strong></summary>

#### Short answer

`modCount` is an internal structural modification counter used by fail-fast iterators. Adding or removing mappings changes it; replacing a value usually does not.

#### Interview answer

When a `HashMap` iterator is created, it records the map's current modification count. If the map is structurally changed during iteration, the count changes and the iterator can throw `ConcurrentModificationException`.

Structural modifications are operations that change the number of mappings or otherwise structurally alter the map. Simple value replacement for an existing key is not normally structural.

#### Deep dive

Operations such as `put` for a new key, `remove`, `clear` and computations that add or remove mappings are structural. A `put` that only replaces the value for an existing key is usually not structural from the iterator's perspective.

This is an implementation mechanism, not a public API guarantee.

#### Production angle

Knowing this helps explain why some mutations during iteration fail and others appear to work. The correct practice is still to avoid mutating the map outside supported iterator or collection methods.

#### Traps / caveats

- `modCount` is not a thread-safety mechanism.
- Fail-fast checks are best-effort.
- Depending on exact internal counts is brittle.

#### Optional Anki

Q: Does replacing a value for an existing key usually change `modCount`?
A: No; adding or removing mappings is the usual structural change.

</details>

<a id="hm-internal-014"></a>

<details>
<summary><strong>🧠 HM-INTERNAL-014. What are common wrong explanations of `HashMap` internals?</strong></summary>

#### Short answer

Common wrong explanations include treating hash codes as unique indexes, confusing capacity with size, assuming order is stable, or saying collisions overwrite data.

#### Interview answer

A solid answer should avoid several myths: `hashCode()` is not a unique ID; a bucket can hold multiple entries; collisions do not overwrite values unless keys are equal; `HashMap` does not preserve insertion order; capacity is not size; and modern `HashMap` may use tree bins, not only linked lists.

#### Deep dive

Another wrong explanation is that `HashMap` always calls `equals()` for every lookup. It first narrows by bucket and hash. Also, resizing does not call user `hashCode()` for every key in modern implementations; it can redistribute using stored hash values.

#### Production angle

Bad mental models lead to bad fixes: changing random fields in `hashCode()`, relying on iteration order in API responses, or ignoring key immutability.

#### Traps / caveats

- Collision is not data loss.
- Treeification has thresholds and does not happen for every collision.
- `HashMap` is not thread-safe.

#### Optional Anki

Q: Does a hash collision overwrite an existing `HashMap` entry?
A: No; overwrite happens only when the keys are equal.

</details>
