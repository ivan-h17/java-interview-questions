# 04.10. Performance, memory and security

---

<a id="hm-perf-001"></a>

<details>
<summary><strong>HM-PERF-001. What is the average time complexity of `get()` and `put()` in `HashMap`?</strong></summary>

#### Short answer

Expected average complexity is `O(1)` for `get()` and `put()` when hashes are well distributed.

#### Interview answer

`HashMap` is designed for expected constant-time key lookup and insertion. The hash directs the operation to a bucket, so the map usually inspects only a small number of candidates. This assumes good `hashCode()` distribution, stable keys and reasonable load.

Worst-case behavior can be worse under heavy collisions or resize.

#### Deep dive

`put()` can occasionally trigger resize, which is proportional to the number of existing entries. Heavy collisions can make bucket search more expensive. Modern tree bins improve collision-heavy worst cases but add their own overhead.

#### Production angle

Average `O(1)` is a useful model, but production latency depends on key hashing, equality cost, allocation, GC, cache locality and table resizing.

#### Traps / caveats

- `O(1)` does not mean zero cost.
- One `put()` can be expensive during resize.
- Bad keys can defeat expected performance.

#### Optional Anki

Q: What is expected average `HashMap.get()` complexity?
A: `O(1)` with good hash distribution.

</details>

<a id="hm-perf-002"></a>

<details>
<summary><strong>HM-PERF-002. When can `HashMap` operations become `O(n)`?</strong></summary>

#### Short answer

They can become linear during resize, iteration, `containsValue()`, or collision-heavy bucket scanning.

#### Interview answer

`containsValue()` is linear because values are not indexed. Iteration is linear in table capacity plus entries. A `put()` that triggers resize must visit existing entries. If many keys collide into one list bin, lookup in that bucket can become linear in the number of collided entries.

Modern tree bins reduce some collision-heavy cases, but not every operation is constant time.

#### Deep dive

Worst-case analysis also depends on implementation and key comparability. Tree bins help only after thresholds are met. Small maps, poor hashes or mutable keys can still produce expensive behavior.

#### Production angle

Unexpected linear behavior appears in request validation loops, repeated `containsValue()`, large map construction and collision-heavy workloads.

#### Traps / caveats

- `containsValue()` is not hash-based lookup.
- Resize is an occasional linear operation.
- Tree bins do not make all map operations `O(1)`.

#### Optional Anki

Q: Is `HashMap.containsValue()` expected `O(1)`?
A: No, it is usually `O(n)`.

</details>

<a id="hm-perf-003"></a>

<details>
<summary><strong>HM-PERF-003. Why is `HashMap` performance still not just `O(1)`?</strong></summary>

#### Short answer

Big-O hides constants and real costs: hashing, equality, allocation, cache misses, resize, GC and collisions.

#### Interview answer

`O(1)` describes expected scaling, not absolute latency. A lookup still computes a hash, indexes the table, follows references, compares keys and may call expensive `equals()`. CPU cache locality is not ideal because entries are objects linked by references.

For `put()`, allocation and resize can also matter.

#### Deep dive

A tiny `ArrayList` scan can beat a `HashMap` for very small data because it is compact and simple. A large `HashMap` can be fast for lookup but memory-heavy. Performance depends on workload shape.

#### Production angle

When a map is hot, profile actual CPU and allocation. Do not rely only on complexity labels in performance-sensitive code.

#### Traps / caveats

- Big-O ignores memory overhead.
- Hashing and equality can dominate runtime.
- Small data structures can outperform theoretically better ones.

#### Optional Anki

Q: Name one hidden cost in `HashMap.get()`.
A: Key hash computation, key equality, pointer chasing or cache misses.

</details>

<a id="hm-perf-004"></a>

<details>
<summary><strong>HM-PERF-004. How do `hashCode()` quality, allocation and `equals()` cost affect performance?</strong></summary>

#### Short answer

Poor hashes increase collisions, allocation increases GC pressure, and expensive `equals()` makes collision checks costly.

#### Interview answer

Good hash codes keep buckets short. If many keys collide, `HashMap` must compare more candidates. If key creation allocates objects for every lookup, GC pressure increases. If `equals()` walks large object graphs or collections, every collision becomes expensive.

The map's performance is only as good as the key type.

#### Deep dive

Common performance smells include building string keys by concatenation on every lookup, using large request objects as keys, deep equality over collections, and boxing-heavy primitive keys in huge maps.

#### Production angle

Profilers often show time in key methods rather than `HashMap` itself. Optimize the key path before changing the data structure.

#### Traps / caveats

- Constant hash codes are correctness-compatible but performance-bad.
- Expensive key creation can dominate a cache lookup.
- Do not include mutable fields just to improve hash distribution.

#### Optional Anki

Q: What happens when `equals()` is expensive and collisions are high?
A: Lookup/update CPU can increase sharply.

</details>

<a id="hm-perf-005"></a>

<details>
<summary><strong>HM-PERF-005. How can expensive `equals()` hurt `HashMap` performance?</strong></summary>

#### Short answer

`equals()` is called to distinguish candidate keys in a bucket, so expensive equality makes collisions and lookups slower.

#### Interview answer

In an ideal lookup, the bucket is short and `equals()` is cheap. If equality compares many fields, collections, arrays or lazy-loaded data, each candidate check can be expensive. Under collisions, that cost is multiplied.

Keys should have equality that is correct and reasonably cheap.

#### Deep dive

Even without many collisions, `equals()` can be called for existing-key updates or lookups with equivalent but different key instances. Deep object graph equality is especially dangerous because it can allocate, recurse or touch external state.

#### Production angle

Slow equality can appear as high CPU in request deduplication, grouping collectors, entity sets or cache lookups.

#### Traps / caveats

- `equals()` should not perform I/O or lazy loading.
- Arrays need content comparison only when intended.
- Equality over mutable collections is risky for keys.

#### Optional Anki

Q: Why should map key equality be cheap?
A: It may run during every lookup/update candidate comparison.

</details>

<a id="hm-perf-006"></a>

<details>
<summary><strong>HM-PERF-006. How does key object allocation affect GC pressure?</strong></summary>

#### Short answer

Creating new key objects for every operation adds allocation rate and can increase GC frequency and latency.

#### Interview answer

If a hot path builds composite keys, boxed numbers or concatenated strings for every lookup, those temporary objects must be allocated and collected. Even when map lookup is fast, the surrounding allocation can dominate CPU and GC.

Use stable key objects, records, interning only when appropriate, or alternative structures when allocation is measurable.

#### Deep dive

Some temporary allocation may be optimized by the JIT, but do not assume it disappears. Allocation inside lambdas, stream grouping, string concatenation and boxing can still be visible at scale.

#### Production angle

High allocation from key creation shows up in JFR, allocation profilers and GC logs. It can cause throughput loss and tail-latency spikes.

#### Traps / caveats

- Avoid premature object pooling; it can make things worse.
- Boxing primitive keys can be expensive in huge maps.
- String key concatenation can create ambiguous keys and allocation.

#### Optional Anki

Q: What is a common hidden cost around map lookup?
A: Allocating temporary key objects.

</details>

<a id="hm-perf-007"></a>

<details>
<summary><strong>🧠 HM-PERF-007. What is the memory overhead of `HashMap` entries?</strong></summary>

#### Short answer

Each mapping needs bucket-table space plus an entry node object containing hash, key reference, value reference and next reference; tree nodes cost more.

#### Interview answer

A `HashMap` is memory-heavier than a compact array. It has an internal table array of references, and each stored mapping normally has a node object. The node stores metadata and references in addition to the actual key and value objects.

Exact byte size depends on JVM, object headers, compressed references, alignment and implementation.

#### Deep dive

Tree bins add more fields for tree links and ordering, so they are larger than ordinary nodes. Boxed primitive keys and values add even more objects. For millions of entries, this overhead is significant.

#### Production angle

Large maps can dominate heap usage. Heap dumps often show the table, nodes, keys and values as separate contributors. For primitive-heavy or dense data, specialized collections or arrays may be much smaller.

#### Traps / caveats

- Do not estimate memory from key/value payload only.
- Treeified buckets have extra overhead.
- JVM layout details change exact numbers.

#### Optional Anki

Q: Why is `HashMap` memory-heavy?
A: It stores a bucket array plus per-entry node objects and references.

</details>

<a id="hm-perf-008"></a>

<details>
<summary><strong>HM-PERF-008. How can pre-sizing a `HashMap` improve performance?</strong></summary>

#### Short answer

Pre-sizing can avoid repeated resizes and reduce allocation and redistribution work while populating the map.

#### Interview answer

If you know a map will hold many entries, choosing an initial capacity based on expected mappings lets the map allocate a suitable table earlier. That avoids growth steps where a `put()` triggers a new table and redistribution of existing entries.

#### Deep dive

Pre-sizing should account for load factor. With default `0.75`, expected mappings require more bucket capacity than the raw mapping count. Modern `HashMap.newHashMap(expectedMappings)` can express this intent when available.

#### Production angle

This helps in batch transformations, collecting database rows by ID, deserializing large payloads and building indexes on request paths.

#### Traps / caveats

- Over-sizing wastes memory and can slow iteration.
- Pre-sizing does not fix poor hash codes.
- Small maps usually do not need manual sizing.

#### Optional Anki

Q: What cost does pre-sizing reduce?
A: Resize allocation and entry redistribution.

</details>

<a id="hm-perf-009"></a>

<details>
<summary><strong>HM-PERF-009. How can an unbounded or static `HashMap` cause a memory leak?</strong></summary>

#### Short answer

It keeps strong references to keys and values forever unless entries are removed, preventing garbage collection.

#### Interview answer

A static or long-lived map becomes a leak when entries accumulate without eviction or cleanup. Since `HashMap` holds strong references, anything reachable from keys or values stays alive. If the key space is unbounded, memory grows over time.

This is common in homemade caches and registries.

#### Deep dive

Leaks can also happen through class loaders, thread context data, user sessions or values that reference large object graphs. A `WeakHashMap` only weakens keys and is not a general cache solution.

#### Production angle

Use bounded caches with eviction, TTL, metrics and cleanup. Libraries such as Caffeine are usually safer than a raw static map for caching.

#### Traps / caveats

- `clear()` may remove entries but capacity can remain high.
- Weak keys do not help if values strongly reference keys.
- Static maps can cause redeploy/classloader leaks.

#### Optional Anki

Q: Why does a static `HashMap` leak memory?
A: It keeps strong references for the lifetime of the classloader unless entries are removed.

</details>

<a id="hm-perf-010"></a>

<details>
<summary><strong>HM-PERF-010. How would you profile `HashMap`-related memory growth?</strong></summary>

#### Short answer

Track map size and allocation, then inspect heap dumps or JFR data to find retaining maps, keys and values.

#### Interview answer

I would start with metrics: map size, cache hit/miss, eviction count if any, and heap usage. Then I would take a heap dump and inspect dominator trees to find large `HashMap` instances, retained keys and retained values. JFR or allocation profilers can show where entries are created.

#### Deep dive

Important questions are: is the map bounded, who owns it, what are key cardinality and value size, are entries removed, and do values reference large graphs or class loaders?

Compare heap dumps over time to confirm growth.

#### Production angle

For production, use safe dump procedures and avoid causing an outage. Add lightweight metrics before waiting for the next incident.

#### Traps / caveats

- Heap used by a map includes keys, values and objects reachable from them.
- A small map can retain huge values.
- High capacity after `clear()` can still retain bucket-array memory.

#### Optional Anki

Q: What heap-dump view helps find leaking maps?
A: Dominator tree / retained-size analysis.

</details>

<a id="hm-perf-011"></a>

<details>
<summary><strong>🧠 HM-PERF-011. What are hash collision denial-of-service attacks?</strong></summary>

#### Short answer

They are attacks where an input creates many colliding hash keys, forcing hash tables into expensive collision handling and consuming CPU.

#### Interview answer

If an attacker can submit many parameter names, JSON fields or form keys that collide, a server may spend excessive CPU inserting and looking them up in hash maps. Older hash-table implementations with linked collision chains were especially vulnerable.

Modern Java `HashMap` tree bins reduce the impact, but limits and validation are still important.

#### Deep dive

Collision attacks exploit algorithmic complexity, not memory corruption. They turn expected fast operations into slow ones by controlling key distribution. Frameworks and runtimes often add mitigations, but application-level request limits still matter.

#### Production angle

Protect public endpoints with body size limits, parameter count limits, timeouts, rate limits and up-to-date runtimes.

#### Traps / caveats

- Tree bins mitigate; they do not remove all cost.
- Attack surface includes parsers before your business code.
- Do not expose unbounded map-building from untrusted input.

#### Optional Anki

Q: What does a hash collision DoS exploit?
A: Worst-case hash table behavior under many colliding keys.

</details>

<details>
<summary><strong>HM-PERF-012. How would you choose between `HashMap`, a cache library and a database lookup?</strong></summary>

#### Short answer

Use `HashMap` for simple scoped in-memory lookup, a cache library for bounded cached data, and a database for authoritative durable shared state.

#### Interview answer

A plain `HashMap` is fine for local temporary indexes, request processing or immutable lookup tables. If data is cached across requests, use a cache library when you need eviction, TTL, refresh, size limits, metrics or concurrency behavior. Use the database when correctness requires durable, shared, transactional state.

#### Deep dive

The main questions are ownership, lifetime, consistency, cardinality and failure behavior. A raw map has no eviction, no persistence, no distribution and no built-in observability.

#### Production angle

Many incidents start as "just a map cache." If the data can grow, go stale or be shared across nodes, choose a real cache or database-backed design.

#### Traps / caveats

- Static `HashMap` is rarely a production cache.
- Cache invalidation must be designed.
- Database lookup may be slower but authoritative.

#### Optional Anki

Q: When is a cache library better than `HashMap`?
A: When you need eviction, TTL, bounds, metrics or concurrent loading behavior.

</details>
