# 04.04. Collisions and tree bins

---

<a id="hm-coll-001"></a>

<details>
<summary><strong>HM-COLL-001. How does `HashMap` handle collisions?</strong></summary>

#### Short answer

It stores multiple entries in the same bucket and distinguishes them using stored hash and `equals()`. Heavily collided buckets can become tree bins.

#### Interview answer

When two keys map to the same bucket, `HashMap` does not overwrite automatically. It keeps multiple nodes in that bucket. During lookup or update, it checks candidates with matching hash and key equality.

In modern Java, if a bucket becomes too crowded and the table is large enough, the bucket can be converted from a linked chain into a tree bin to improve worst-case lookup.

#### Deep dive

Collision handling is required because bucket indexes are limited. A collision can mean same bucket with different full hashes or same full hash. Either way, `equals()` remains the final key check.

#### Production angle

Normal collisions are harmless. Excessive collisions increase CPU and can expose expensive `equals()` implementations.

#### Traps / caveats

- Collisions do not lose entries.
- Same bucket does not mean same key.
- Tree bins reduce worst-case cost but do not make poor key design free.

#### Optional Anki

Q: What resolves a collision in `HashMap`?
A: Candidate comparison using hash and `equals()`.

</details>

<a id="hm-coll-002"></a>

<details>
<summary><strong>HM-COLL-002. What is separate chaining?</strong></summary>

#### Short answer

Separate chaining stores colliding entries in a secondary structure attached to the same bucket.

#### Interview answer

In a chained hash table, each bucket can hold multiple entries. Instead of probing other array slots, colliding entries are linked from the bucket. Java `HashMap` uses this idea with node chains and, for heavily collided buckets, tree bins.

#### Deep dive

Separate chaining differs from open addressing, where collisions are resolved by searching for another empty slot in the table itself. Chaining makes deletion simpler and supports multiple entries per bucket without tombstones.

#### Production angle

The cost of lookup depends on the length or shape of the bucket's chain/tree. Good hash distribution keeps chains short.

#### Traps / caveats

- Chaining uses extra node objects and references.
- It can hurt cache locality compared with compact arrays.
- Long chains make `equals()` cost visible.

#### Optional Anki

Q: What does separate chaining do with colliding entries?
A: Stores them in a per-bucket chain or related structure.

</details>

<a id="hm-coll-003"></a>

<details>
<summary><strong>HM-COLL-003. What happens when many keys land in the same bucket?</strong></summary>

#### Short answer

Operations in that bucket become slower, and modern `HashMap` may convert the bucket to a tree bin after thresholds are met.

#### Interview answer

If many keys land in one bucket, `get()` and `put()` must inspect many candidates. With a linked chain, this can approach linear time for that bucket. Modern `HashMap` can treeify a long bucket when the table is large enough, reducing lookup inside the bucket to roughly logarithmic time.

#### Deep dive

Before treeification, `HashMap` may prefer resizing because a small table can cause collisions simply because there are too few buckets. After resizing, entries may spread out naturally.

#### Production angle

Many entries in one bucket can show up as CPU hotspots in `equals()`, tree comparisons or `HashMap` methods. The root cause is often bad key hashing or low-cardinality key fields.

#### Traps / caveats

- Treeification is not immediate for every long bucket.
- Resizing may fix bucket collisions caused by small capacity.
- If all keys have the same hash, resize cannot spread them.

#### Optional Anki

Q: What is the main performance risk of many keys in one bucket?
A: More candidate comparisons per lookup/update.

</details>

<a id="hm-coll-004"></a>

<details>
<summary><strong>HM-COLL-004. What is treeification in `HashMap`?</strong></summary>

#### Short answer

Treeification is converting a heavily collided bucket from a linked chain into a tree bin.

#### Interview answer

When a bucket's chain becomes long enough and the table has sufficient capacity, `HashMap` can replace the linked nodes with tree nodes. This improves worst-case lookup for that bucket from linear scanning to tree search behavior.

The tree is an internal collision-management structure, not a sorted map API.

#### Deep dive

Treeification was added to modern `HashMap` implementations to reduce the impact of collision-heavy cases. If the map later shrinks in that bucket, the bin can be converted back to ordinary nodes.

Tree bins still live inside one hash bucket. They do not make the whole map ordered.

#### Production angle

Tree bins protect services from some collision-heavy inputs, but they add overhead. A treeified bucket is usually a sign to inspect key design or input patterns.

#### Traps / caveats

- Treeification does not preserve global sorted order.
- It has both chain-length and table-capacity conditions.
- It is a fallback, not the normal fast path.

#### Optional Anki

Q: What does treeification improve?
A: Worst-case search cost inside a heavily collided bucket.

</details>

<a id="hm-coll-005"></a>

<details>
<summary><strong>🧠 HM-COLL-005. What are `TREEIFY_THRESHOLD`, `UNTREEIFY_THRESHOLD` and `MIN_TREEIFY_CAPACITY`?</strong></summary>

#### Short answer

In modern OpenJDK `HashMap`, `TREEIFY_THRESHOLD` is 8, `UNTREEIFY_THRESHOLD` is 6, and `MIN_TREEIFY_CAPACITY` is 64.

#### Interview answer

`TREEIFY_THRESHOLD` is the bucket size at which a long chain may be converted to a tree bin. `UNTREEIFY_THRESHOLD` is the lower size at which a tree bin can be converted back to ordinary nodes. `MIN_TREEIFY_CAPACITY` prevents treeification while the table is still small; below that capacity, `HashMap` prefers resizing.

#### Deep dive

The gap between 8 and 6 avoids rapid flipping between list and tree around a single boundary. The minimum capacity rule exists because collisions in a small table are often solved better by adding buckets than by creating a tree.

These constants are implementation details, not general `Map` API rules.

#### Production angle

You rarely tune these directly. They are useful for explaining why a bucket with several entries may not become a tree and why pre-sizing can affect collision behavior.

#### Traps / caveats

- Thresholds are implementation details.
- Treeification requires both a long bin and enough table capacity.
- A tree bin is not the same as `TreeMap`.

#### Optional Anki

Q: What is `MIN_TREEIFY_CAPACITY` commonly in OpenJDK `HashMap`?
A: 64.

</details>

<a id="hm-coll-006"></a>

<details>
<summary><strong>🧠 HM-COLL-006. Why does `HashMap` resize instead of treeifying when the table is still small?</strong></summary>

#### Short answer

Because collisions in a small table are often caused by too few buckets, and resizing may spread entries more cheaply than building a tree.

#### Interview answer

When capacity is low, many keys can share buckets even with decent hashes. Doubling the table gives entries more buckets and may split a long chain into shorter chains. Treeifying too early would add tree overhead when a simple resize could restore normal performance.

#### Deep dive

This is why `MIN_TREEIFY_CAPACITY` exists. `HashMap` treats a long bucket in a small table as a capacity problem first and a pathological collision problem second.

If keys truly have identical or very poor hashes, resizing will not help much, and treeification can eventually provide protection.

#### Production angle

If a map grows large in a hot path, correct initial sizing can reduce both resize spikes and collision-heavy intermediate states.

#### Traps / caveats

- Resizing is not free; it can cause latency spikes.
- Treeification is also not free.
- Bad `hashCode()` can defeat the benefits of resizing.

#### Optional Anki

Q: Why not treeify every long bucket immediately?
A: In a small table, resizing may spread entries more cheaply.

</details>

<a id="hm-coll-007"></a>

<details>
<summary><strong>🧠 HM-COLL-007. How does `HashMap` compare keys inside a tree bin, and do keys need to implement `Comparable`?</strong></summary>

#### Short answer

Keys do not need to implement `Comparable`. `HashMap` first uses hash and equality, then uses comparable ordering when available, otherwise an internal tie-breaker.

#### Interview answer

Inside a tree bin, `HashMap` still respects map equality semantics. A key match is based on hash plus identity or `equals()`. For tree navigation among non-equal keys with the same bucket, it may use `Comparable` when keys are comparable in a compatible way. If not, it falls back to an internal tie-break ordering.

So ordinary non-comparable keys can still be used in a `HashMap`.

#### Deep dive

This differs from `TreeMap`, where keys must be mutually comparable or a comparator must be supplied. `HashMap` tree bins are internal collision structures; they cannot require all keys to be comparable because that would break the normal `HashMap` API.

#### Production angle

You should not implement `Comparable` just to make keys usable in `HashMap`. Focus on correct, stable `equals()` and `hashCode()`.

#### Traps / caveats

- Tree bin ordering is not exposed as map iteration order.
- `Comparable` inconsistent with `equals()` can still cause confusion in sorted collections.
- Internal tie-break behavior is implementation detail.

#### Optional Anki

Q: Must `HashMap` keys implement `Comparable` for tree bins?
A: No.

</details>

<a id="hm-coll-008"></a>

<details>
<summary><strong>HM-COLL-008. How does treeification affect worst-case lookup time?</strong></summary>

#### Short answer

It improves lookup inside a heavily collided bucket from linear chain scanning toward logarithmic tree search.

#### Interview answer

Without treeification, a bucket with many entries is searched like a list, so the bucket cost can be `O(n)` in the number of colliding entries. With a tree bin, search is closer to `O(log n)` for that bucket.

The whole map still depends on hashing, capacity and key comparison costs.

#### Deep dive

The improvement matters most under collision-heavy conditions. In normal maps with well-distributed keys, most buckets are empty or short, so tree bins are rarely used.

Tree nodes have more memory and maintenance overhead than list nodes, which is why treeification is delayed until thresholds are met.

#### Production angle

Tree bins reduce the damage from pathological input but should not be used as an excuse for poor hash functions or unbounded maps.

#### Traps / caveats

- Average-case `HashMap` performance is still expected `O(1)`.
- Treeification improves one bucket, not global ordering.
- `equals()` and comparison cost still matter.

#### Optional Anki

Q: What worst-case bucket lookup improvement does treeification target?
A: From linear scanning toward logarithmic tree search.

</details>

<a id="hm-coll-009"></a>

<details>
<summary><strong>HM-COLL-009. Can a poor `hashCode()` still hurt performance even with tree bins?</strong></summary>

#### Short answer

Yes. Tree bins reduce worst-case lookup but still add overhead, comparisons and memory cost.

#### Interview answer

If many keys have the same poor hash, they still land in the same bucket. Treeification can make lookup less terrible, but every operation still pays for tree navigation, equality checks, more pointer chasing and larger node objects.

Good hash distribution remains the normal performance strategy.

#### Deep dive

Tree bins are a defensive fallback. They do not reduce key allocation, do not make expensive `equals()` cheap, and do not help if the map is too large or used incorrectly under concurrency.

#### Production angle

If profiles show tree bin or collision-heavy map costs, fix the key design or data structure choice. Do not rely on `HashMap` internals to mask a broken `hashCode()`.

#### Traps / caveats

- Constant hash codes are still bad.
- Tree bins do not fix mutable keys.
- Security-sensitive input may still need limits and validation.

#### Optional Anki

Q: Are tree bins a substitute for good `hashCode()`?
A: No; they are a fallback for heavy collisions.

</details>

<a id="hm-coll-010"></a>

<details>
<summary><strong>HM-COLL-010. How does modern `HashMap` mitigate collision-heavy cases compared to older Java versions?</strong></summary>

#### Short answer

Modern `HashMap` uses hash spreading and tree bins to reduce the impact of heavy collisions.

#### Interview answer

Compared with older linked-chain-only implementations, modern `HashMap` can convert heavily collided buckets into tree bins. It also applies a hash spreading function before bucket indexing. Together these features improve distribution in common cases and reduce worst-case behavior for pathological buckets.

#### Deep dive

The normal path is still bucket array plus short chains. Tree bins are only used after thresholds are met. This preserves good average performance while protecting against extreme collision cases better than older implementations.

#### Production angle

This matters for services that process untrusted or high-cardinality input, but it is only one layer of defense. Use request limits, proper keys and appropriate data structures.

#### Traps / caveats

- Modern `HashMap` is still not thread-safe.
- Tree bins do not guarantee constant time for all bad inputs.
- Internal behavior can vary by JDK implementation and version.

#### Optional Anki

Q: What major collision defense was added to modern `HashMap`?
A: Tree bins for heavily collided buckets.

</details>
