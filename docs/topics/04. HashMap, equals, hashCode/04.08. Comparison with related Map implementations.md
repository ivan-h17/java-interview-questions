# 04.08. Comparison with related Map implementations

---

<a id="hm-comp-001"></a>

<details>
<summary><strong>HM-COMP-001. How do `HashMap`, `LinkedHashMap` and `TreeMap` differ?</strong></summary>

#### Short answer

`HashMap` is unordered hash lookup, `LinkedHashMap` preserves predictable iteration order, and `TreeMap` keeps keys sorted.

#### Interview answer

`HashMap` gives expected constant-time lookup with no order guarantee. `LinkedHashMap` extends hash-map behavior with a linked list of entries, preserving insertion order by default or access order if configured. `TreeMap` is a balanced tree map with keys sorted by natural order or comparator and operations typically `O(log n)`.

#### Deep dive

`LinkedHashMap` costs extra memory for links. `TreeMap` costs more per operation but supports range queries such as `subMap`, `floorKey` and `ceilingKey`. `HashMap` is the default when order and range operations are not required.

#### Production angle

Choose based on requirements: fast lookup, stable API output, LRU-like order, sorted display, or range operations.

#### Traps / caveats

- `HashMap` order is not reliable.
- `TreeMap` sorted equality follows comparator behavior for keys.
- `LinkedHashMap` is not a cache library by itself.

#### Optional Anki

Q: Which map should you choose for sorted keys?
A: `TreeMap`.

</details>

<a id="hm-comp-002"></a>

<details>
<summary><strong>HM-COMP-002. When should you choose `LinkedHashMap` or `TreeMap` instead of `HashMap`?</strong></summary>

#### Short answer

Choose `LinkedHashMap` for predictable insertion/access order and `TreeMap` for sorted keys or range operations.

#### Interview answer

Use `LinkedHashMap` when iteration order matters but hash lookup is still desired: stable JSON, preserving input order, or simple access-order eviction. Use `TreeMap` when you need sorted traversal, nearest-key lookup or key ranges.

If you only need key lookup and order does not matter, `HashMap` is usually simpler and faster.

#### Deep dive

`TreeMap` depends on `Comparable` or `Comparator`, while `HashMap` depends on `equals()` and `hashCode()`. That difference can affect equality semantics for tricky types such as `BigDecimal`.

#### Production angle

Choosing the wrong map often shows up as flaky tests, unstable API output or inefficient manual sorting/range filtering.

#### Traps / caveats

- Do not rely on accidental `HashMap` order.
- `TreeMap` is not a performance upgrade for direct lookup.
- Access-order `LinkedHashMap` changes order on reads.

#### Optional Anki

Q: Which map supports range views such as `subMap`?
A: `TreeMap`.

</details>

<a id="hm-comp-003"></a>

<details>
<summary><strong>HM-COMP-003. What is the difference between `HashMap`, `Hashtable` and `Collections.synchronizedMap()`?</strong></summary>

#### Short answer

`HashMap` is unsynchronized and allows nulls. `Hashtable` is legacy synchronized and forbids nulls. `synchronizedMap()` wraps a map with synchronized method access.

#### Interview answer

`HashMap` is the normal non-thread-safe map. `Hashtable` is an older synchronized class from before the Collections Framework style; it is generally avoided in new code. `Collections.synchronizedMap(new HashMap<>())` creates a synchronized wrapper around a normal map.

For modern concurrent access, `ConcurrentHashMap` is usually preferred.

#### Deep dive

The synchronized wrapper synchronizes individual method calls. Iteration still requires external synchronization on the wrapper while traversing. Otherwise another thread can modify the map during iteration.

#### Production angle

Using `Hashtable` or synchronized wrappers can serialize all access and become a bottleneck. `ConcurrentHashMap` usually scales better for concurrent reads and updates.

#### Traps / caveats

- `Hashtable` is legacy.
- `synchronizedMap` iteration needs manual synchronization.
- Synchronizing individual methods does not make multi-step invariants atomic.

#### Optional Anki

Q: What map is usually preferred for concurrent access?
A: `ConcurrentHashMap`.

</details>

<a id="hm-comp-004"></a>

<details>
<summary><strong>HM-COMP-004. What is the difference between `HashMap` and `ConcurrentHashMap`?</strong></summary>

#### Short answer

`HashMap` is not thread-safe. `ConcurrentHashMap` supports concurrent access with internal synchronization/CAS techniques and no null keys or values.

#### Interview answer

Use `HashMap` when access is single-threaded, externally synchronized or effectively immutable after construction. Use `ConcurrentHashMap` when multiple threads need to read and update the map concurrently.

`ConcurrentHashMap` provides atomic methods such as `putIfAbsent`, `compute` and `merge`, and its iterators are weakly consistent rather than fail-fast.

#### Deep dive

`ConcurrentHashMap` does not make arbitrary business workflows atomic. It makes individual map operations and certain compound map operations thread-safe. Multi-object or multi-map invariants still need higher-level locking or transactions.

#### Production angle

Replacing `HashMap` with `ConcurrentHashMap` can fix data races around map state, but not all concurrency bugs. Review the full invariant.

#### Traps / caveats

- `ConcurrentHashMap` forbids nulls.
- Its size-related methods can be approximate under concurrent mutation.
- Mapping functions must be short and side-effect safe.

#### Optional Anki

Q: Are `HashMap` iterators and `ConcurrentHashMap` iterators the same?
A: No; `HashMap` iterators are fail-fast, while `ConcurrentHashMap` iterators are weakly consistent.

</details>

<a id="hm-comp-005"></a>

<details>
<summary><strong>HM-COMP-005. What is the difference between `HashMap` and `Map.of()`?</strong></summary>

#### Short answer

`HashMap` is mutable and allows nulls. `Map.of()` creates an unmodifiable map and rejects null keys, null values and duplicate keys.

#### Interview answer

`Map.of()` is a convenient factory for small fixed maps. The returned map cannot be structurally modified. It also does not allow nulls and throws on duplicate keys.

`HashMap` is mutable, supports nulls and is better when entries are added, removed or updated over time.

#### Deep dive

The concrete implementation returned by `Map.of()` is unspecified. Its iteration order should not be relied on unless the API specifically guarantees it, which `Map.of()` does not.

For copying an existing map into an unmodifiable map, use `Map.copyOf()`.

#### Production angle

Use `Map.of()` for constants, test data and small lookup maps. Use `HashMap` for dynamic state.

#### Traps / caveats

- `Map.of()` is unmodifiable, not a `HashMap`.
- Nulls are rejected.
- Duplicate keys are rejected.

#### Optional Anki

Q: Can `Map.of()` contain null values?
A: No.

</details>

<a id="hm-comp-006"></a>

<details>
<summary><strong>🧠 HM-COMP-006. How do `Map.equals()` and `Map.hashCode()` work across different map implementations?</strong></summary>

#### Short answer

Maps are equal if they contain the same mappings, regardless of implementation. A map's hash code is defined from its entries.

#### Interview answer

`Map.equals()` is based on mappings, not concrete class. A `HashMap` and `TreeMap` can be equal if they contain the same keys mapped to equal values. The `Map` hash code is defined as the sum of entry hash codes, and each entry hash is based on key and value hashes.

This lets different `Map` implementations interoperate logically.

#### Deep dive

The tricky part is key equality semantics. A `TreeMap` uses comparator equality for key uniqueness, while `HashMap` uses `equals()` and `hashCode()`. If a comparator is inconsistent with `equals()`, cross-map behavior can surprise you.

#### Production angle

This matters in tests and API contracts. Comparing maps is usually fine across implementations, but be careful with sorted maps using custom comparators or tricky keys such as `BigDecimal`.

#### Traps / caveats

- Map equality ignores iteration order.
- Comparator inconsistency can create surprises.
- Values are compared with equality, including null-safe handling.

#### Optional Anki

Q: Can a `HashMap` equal a `TreeMap`?
A: Yes, if they contain the same mappings.

</details>

<a id="hm-comp-007"></a>

<details>
<summary><strong>HM-COMP-007. What is the difference between `HashMap` and an `ArrayList` of key-value pairs?</strong></summary>

#### Short answer

`HashMap` provides key-based lookup with unique keys. An `ArrayList` of pairs preserves sequence but lookup is usually linear and duplicates are possible.

#### Interview answer

If you frequently look up by key, `HashMap` is the natural structure. It gives expected constant-time lookup and replaces values for equal keys. A list of pairs is useful when order, duplicates or very small size matter more than lookup speed.

#### Deep dive

A list can represent repeated headers, query parameters or ordered operations where duplicate keys are meaningful. A map represents the latest or unique value for each key.

The best choice depends on the domain, not only performance.

#### Production angle

Using a list for repeated key lookup can create `O(n^2)` behavior. Using a map when duplicates matter can silently drop data.

#### Traps / caveats

- `HashMap` cannot store duplicate equal keys.
- A list of pairs may be simpler for tiny data.
- Preserve input order explicitly when it matters.

#### Optional Anki

Q: Which structure is better for frequent key lookup?
A: `HashMap`.

</details>

<a id="hm-comp-008"></a>

<details>
<summary><strong>🧠 HM-COMP-008. When are `IdentityHashMap`, `WeakHashMap` or `EnumMap` better than a normal `HashMap`?</strong></summary>

#### Short answer

Use them for special semantics: identity-based keys, weakly referenced keys, or enum keys.

#### Interview answer

`IdentityHashMap` compares keys with `==`, useful for object graph processing or reference tracking. `WeakHashMap` stores keys weakly so entries can disappear when keys are no longer strongly reachable. `EnumMap` is optimized for enum keys and is usually faster and smaller than `HashMap` for that case.

#### Deep dive

These are not general replacements. `IdentityHashMap` ignores logical equality. `WeakHashMap` is not a full cache because values can keep keys reachable indirectly and cleanup depends on GC. `EnumMap` only accepts keys from one enum type and follows enum order.

#### Production angle

Choose these when the semantics match exactly. Otherwise they create surprising bugs: entries disappearing, equality mismatch or invalid key types.

#### Traps / caveats

- `WeakHashMap` needs careful value references.
- `IdentityHashMap` intentionally violates normal logical key equality.
- `EnumMap` requires non-null enum keys.

#### Optional Anki

Q: Which map is best for enum keys?
A: `EnumMap`.

</details>
