# 04.05. Capacity, load factor and resizing

---

<a id="hm-cap-001"></a>

<details>
<summary><strong>HM-CAP-001. What are capacity, size, load factor and resize threshold in `HashMap`?</strong></summary>

#### Short answer

Capacity is bucket count, size is mapping count, load factor controls how full the table may get, and the resize threshold is roughly `capacity * loadFactor`.

#### Interview answer

`HashMap.size()` is the number of stored key-value mappings. Capacity is the internal number of buckets. The load factor is a density setting that trades memory for fewer collisions. When size grows beyond the threshold, the table is resized, usually doubled.

With the default load factor `0.75`, a table of capacity 16 resizes after it grows beyond about 12 mappings.

#### Deep dive

Capacity is rounded to powers of two in modern implementations. The threshold is an internal value based on capacity and load factor. A lower load factor means more empty buckets and fewer collisions. A higher load factor means less table memory but potentially longer buckets.

#### Production angle

If you know you will insert many entries, pre-sizing avoids repeated resizes. If a long-lived map becomes huge and later small, capacity may remain large and waste memory.

#### Traps / caveats

- Size is public; capacity is internal.
- Initial capacity is not expected number of mappings.
- Load factor tuning should be based on measurement.

#### Optional Anki

Q: What is the default `HashMap` load factor?
A: `0.75`.

</details>

<a id="hm-cap-002"></a>

<details>
<summary><strong>HM-CAP-002. What is the default load factor in `HashMap`, and why is it a trade-off?</strong></summary>

#### Short answer

The default load factor is `0.75`, a balance between memory usage and collision rate.

#### Interview answer

Load factor controls how full the table can get before resizing. At `0.75`, `HashMap` keeps enough empty buckets to maintain good lookup performance without using too much memory. Lower values use more memory but may reduce collisions. Higher values save bucket-array memory but can increase collision cost.

#### Deep dive

The default is a general-purpose choice. It is not optimal for every workload. If keys are well distributed and memory is tight, a higher factor may be acceptable. If latency is critical and memory is available, a lower factor may help, but it should be benchmarked.

#### Production angle

Most services should keep the default. Bigger wins usually come from good keys, pre-sizing, avoiding unnecessary maps and using the right data structure.

#### Traps / caveats

- Load factor does not limit total map size.
- Very low load factors waste memory and slow iteration over sparse tables.
- Very high load factors can increase collisions.

#### Optional Anki

Q: What trade-off does load factor control?
A: Memory usage versus collision probability.

</details>

<a id="hm-cap-003"></a>

<details>
<summary><strong>HM-CAP-003. When does resizing happen, and what happens during resize?</strong></summary>

#### Short answer

Resizing happens when adding a new mapping makes size exceed the threshold. The table grows and entries are redistributed into the new bucket array.

#### Interview answer

On insertion, if the map size passes the resize threshold, `HashMap` allocates a larger table, usually double the previous capacity. Existing nodes are moved to buckets in the new table based on their stored hashes.

This is why a single `put()` can occasionally be much more expensive than usual.

#### Deep dive

In Java 8+ style implementations, when capacity doubles, an entry either stays at the old index or moves to `oldIndex + oldCapacity`, based on one hash bit. That avoids recomputing user hash codes for every key.

#### Production angle

Resize spikes can matter when building large maps on request threads. Pre-sizing based on expected entries reduces repeated allocation and redistribution.

#### Traps / caveats

- Resizing changes internal bucket positions.
- Resizing is not thread-safe in `HashMap`.
- Removing entries does not normally shrink the table.

#### Optional Anki

Q: Why can one `HashMap.put()` be slow?
A: It may trigger table resize and entry redistribution.

</details>

<a id="hm-cap-004"></a>

<details>
<summary><strong>HM-CAP-004. Why can resizing be expensive and cause latency spikes?</strong></summary>

#### Short answer

Resizing allocates a new bucket array and redistributes existing entries, so one insertion can do work proportional to the current map size.

#### Interview answer

Most `put()` calls are cheap, but the call that crosses the threshold must grow the table. That means allocating memory and moving bucket contents. For a large map, this can create a visible pause on the request thread or job worker.

#### Deep dive

Resizing can also increase GC pressure because it allocates a new table and may temporarily keep old structures reachable. The node objects are usually reused, but the table array changes.

The cost is amortized over many inserts, but tail latency cares about the expensive individual operation.

#### Production angle

In batch processing, indexing, grouping or request aggregation, pre-size maps when expected count is known. For very large workloads, consider streaming, chunking or specialized data structures.

#### Traps / caveats

- Amortized `O(1)` does not mean every operation is constant time.
- Resize spikes are more visible in low-latency services.
- Pre-sizing too large can waste memory.

#### Optional Anki

Q: What does resizing cost?
A: New table allocation plus redistribution of existing entries.

</details>

<a id="hm-cap-005"></a>

<details>
<summary><strong>HM-CAP-005. How would you choose initial capacity for a `HashMap`?</strong></summary>

#### Short answer

Estimate expected mappings and choose enough bucket capacity so `expectedMappings <= capacity * loadFactor`.

#### Interview answer

If I expect `n` entries and use the default load factor, I want capacity around `ceil(n / 0.75)`, rounded up to the implementation's power-of-two capacity. For example, 100 expected entries need more than 100 buckets to avoid resizing with the default load factor.

In modern Java, `HashMap.newHashMap(expectedMappings)` can do this calculation for expected mappings.

#### Deep dive

The constructor `new HashMap<>(initialCapacity)` accepts bucket capacity, not expected number of mappings. Passing the expected number directly may still resize when the threshold is crossed.

For small maps, the default is usually fine. For large known sizes, pre-sizing is useful.

#### Production angle

Pre-sizing helps in hot paths that build maps from database rows, message batches or large request payloads. It reduces allocation churn and tail latency.

#### Traps / caveats

- Do not blindly over-allocate for uncertain sizes.
- Account for load factor.
- If the map is short-lived and small, readability may matter more than tuning.

#### Optional Anki

Q: With load factor `0.75`, do 100 mappings need exactly 100 buckets?
A: No; they need capacity above `100 / 0.75` to avoid resize.

</details>

<a id="hm-cap-006"></a>

<details>
<summary><strong>🧠 HM-CAP-006. Why is `new HashMap<>(expectedSize)` often not the exact final capacity you need?</strong></summary>

#### Short answer

Because the constructor argument is initial bucket capacity, not expected mappings, and resize threshold depends on load factor.

#### Interview answer

If you pass `new HashMap<>(100)`, you are not saying "I will store 100 entries without resizing." You are requesting an initial capacity, which is rounded internally. With default load factor `0.75`, the map may resize before or around 100 entries depending on the actual rounded capacity and threshold.

To hold `n` mappings without resizing, capacity must be based on `n / loadFactor`.

#### Deep dive

Modern implementations also allocate the table lazily, so constructor configuration and actual table allocation can happen at different times. The important point is that expected mappings and bucket capacity are different concepts.

#### Production angle

This mistake is common in performance-sensitive batch code. It gives a false sense of pre-sizing while still allowing resize spikes.

#### Traps / caveats

- `expectedSize` is not the same as constructor `initialCapacity`.
- Capacity is rounded to a power of two.
- Oversizing can be worse for memory and iteration.

#### Optional Anki

Q: What does `new HashMap<>(100)` configure?
A: Initial bucket capacity, not guaranteed storage for exactly 100 mappings.

</details>

<a id="hm-cap-007"></a>

<details>
<summary><strong>🧠 HM-CAP-007. In modern Java, when is `HashMap.newHashMap(expectedMappings)` useful?</strong></summary>

#### Short answer

It is useful when you know the expected number of mappings and want a map sized to avoid resizing under the default load factor.

#### Interview answer

`HashMap.newHashMap(expectedMappings)` treats the argument as expected mappings, not bucket capacity. It computes an appropriate initial capacity for the default load factor. That is clearer than manually doing `ceil(n / 0.75)` and relying on constructor behavior.

Use it for large known collections, batch transformations or grouping logic where avoiding resize matters.

#### Deep dive

It improves readability because the API name documents intent: expected mappings. It also avoids common off-by-load-factor mistakes. It is still a standard `HashMap`, not a fixed-size map.

#### Production angle

This is a good fit when building a map from a list whose size is known, for example indexing database results by ID. It is less important for small maps.

#### Traps / caveats

- It does not cap the map size.
- It still allocates memory proportional to the estimate.
- Check the Java version used by your project before using newer APIs.

#### Optional Anki

Q: What is the semantic difference between `new HashMap<>(n)` and `HashMap.newHashMap(n)`?
A: The constructor takes capacity; `newHashMap` takes expected mappings.

</details>

<a id="hm-cap-008"></a>

<details>
<summary><strong>🧠 HM-CAP-008. How does Java 8+ `HashMap` redistribute nodes during resize?</strong></summary>

#### Short answer

When capacity doubles, each node either stays in its old bucket or moves to `oldIndex + oldCapacity` based on one hash bit.

#### Interview answer

Java 8+ `HashMap` can split each old bucket into two groups during resize. Because capacity doubles, only one additional hash bit matters. If that bit is zero, the node stays at the old index. If it is one, it moves to the old index plus the old capacity.

This avoids recomputing user hash codes and preserves relative order within split groups.

#### Deep dive

The optimization depends on power-of-two capacity. It is one reason modern `HashMap` resize is more efficient than a naive reinsert-everything approach.

The map still has to visit existing nodes, so resize cost is still proportional to stored entries.

#### Production angle

This implementation detail explains why resize is optimized but still visible for large maps. Pre-sizing remains useful when building large maps in latency-sensitive code.

#### Traps / caveats

- Stored hash values are reused.
- The optimization does not make resize free.
- It is implementation detail, not a public guarantee.

#### Optional Anki

Q: On capacity doubling, where can an entry move?
A: It stays at old index or moves to old index plus old capacity.

</details>

<a id="hm-cap-009"></a>

<details>
<summary><strong>HM-CAP-009. How do capacity and load factor trade memory for speed?</strong></summary>

#### Short answer

More capacity or lower load factor uses more memory but usually reduces collisions. Less capacity or higher load factor saves memory but can slow lookup.

#### Interview answer

Capacity is the number of buckets. A sparse table gives entries more room, so buckets are shorter on average. That improves lookup but wastes empty bucket slots and can slow iteration over the table. A dense table uses less bucket-array memory but increases collision probability.

#### Deep dive

The total memory cost also includes node objects, keys and values. For many maps, node and object overhead dominates. For large sparse maps, the bucket array itself becomes significant.

The default load factor is a reasonable general-purpose balance.

#### Production angle

In backend code, tune only when profiles show map cost. Better key design, avoiding unnecessary maps or using specialized structures often matters more.

#### Traps / caveats

- Lower load factor is not always faster overall.
- Higher load factor can make latency less predictable.
- Iteration cost depends partly on capacity.

#### Optional Anki

Q: What does lower load factor usually buy?
A: Fewer collisions at the cost of more bucket memory.

</details>

<a id="hm-cap-010"></a>

<details>
<summary><strong>HM-CAP-010. Can very high or very low load factors be a problem?</strong></summary>

#### Short answer

Yes. Very high load factors increase collisions; very low load factors waste memory and can slow iteration.

#### Interview answer

A high load factor lets the table get dense before resizing. That saves bucket memory but can produce longer chains or more tree bins. A low load factor keeps the table sparse, but uses more memory and makes iteration scan more empty buckets.

The default `0.75` is usually the right starting point.

#### Deep dive

Extreme settings can also affect GC and CPU cache behavior. Huge sparse tables consume memory and may reduce locality. Dense tables can shift cost into equality checks and pointer chasing.

#### Production angle

Do not tune load factor by intuition alone. Use realistic data, production-like key distributions and benchmark or profile the actual workload.

#### Traps / caveats

- Load factor does not fix bad `hashCode()`.
- Low load factor does not remove node overhead.
- High load factor can hurt tail latency.

#### Optional Anki

Q: What is the main risk of a very high load factor?
A: More collisions and slower operations.

</details>

<a id="hm-cap-011"></a>

<details>
<summary><strong>HM-CAP-011. Why can an oversized `HashMap` make iteration slower?</strong></summary>

#### Short answer

`HashMap` iteration scans the internal table as well as entries, so excessive capacity can increase work over empty buckets.

#### Interview answer

A `HashMap` iterator walks through the bucket table and entries inside buckets. If the table is much larger than needed, iteration touches many empty bucket slots. That can make iterating an oversized map slower than iterating a correctly sized one.

#### Deep dive

This is different from lookup, where more buckets may reduce collisions. Iteration has to traverse the table structure, so sparse capacity can become overhead.

`LinkedHashMap` maintains a linked order of entries, but it has its own memory overhead.

#### Production angle

Oversized maps often appear after a long-lived map once held many entries and then most were removed. Rebuilding the map can reclaim table size if needed.

#### Traps / caveats

- `clear()` removes mappings but may keep capacity.
- Oversizing can hurt memory and scan time.
- Use ordered or compact structures if iteration dominates.

#### Optional Anki

Q: Why can sparse `HashMap` iteration be slow?
A: Iterators still traverse the bucket table, including empty slots.

</details>

<a id="hm-cap-012"></a>

<details>
<summary><strong>HM-CAP-012. How would you optimize a `HashMap` used in a hot path?</strong></summary>

#### Short answer

Measure first, then improve key design, pre-size appropriately, avoid unnecessary allocation, and consider a better data structure.

#### Interview answer

I would start with profiling to confirm the map is the bottleneck. Then I would check key `hashCode()` distribution and `equals()` cost, pre-size the map if expected size is known, avoid creating temporary key objects repeatedly, and remove unnecessary map construction.

If the key domain allows it, I might use `EnumMap`, arrays, primitive-specialized collections, or a cache library instead.

#### Deep dive

Hot-path map cost can come from resizing, collisions, key allocation, boxing, expensive `equals()`, memory overhead or iteration. The fix depends on which cost is visible. For example, `EnumMap` is excellent for enum keys, while a `HashMap<Long, V>` may suffer from boxing and object overhead.

#### Production angle

Optimization should preserve correctness and readability. In critical services, validate with realistic benchmarks and production profiles, not only microbenchmarks.

#### Traps / caveats

- Do not replace a map with a clever structure without tests.
- Avoid mutable keys.
- Do not tune load factor before fixing obvious allocation or key issues.

#### Optional Anki

Q: What is the first step before optimizing a hot `HashMap`?
A: Profile or benchmark to identify the real cost.

</details>
