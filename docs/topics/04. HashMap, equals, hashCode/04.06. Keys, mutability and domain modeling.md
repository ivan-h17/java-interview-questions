# 04.06. Keys, mutability and domain modeling

---

<a id="hm-key-001"></a>

<details>
<summary><strong>HM-KEY-001. Can you use a mutable object as a `HashMap` key?</strong></summary>

#### Short answer

You can, but it is safe only if the fields used by `equals()` and `hashCode()` do not change while the object is in the map.

#### Interview answer

`HashMap` does not forbid mutable keys. The problem is mutation of equality-relevant state. If a key's hash or equality changes after insertion, the map may no longer find, remove or deduplicate it correctly.

So in practice, keys should be immutable or have immutable identity fields.

#### Deep dive

Mutating non-key fields is less dangerous if those fields are not used in `equals()` or `hashCode()`. But this requires discipline and clear class design. Exposed setters, mutable collections and arrays make the risk high.

#### Production angle

Mutable key bugs are common in request-object caches, entity maps and composite key classes with setters. They cause intermittent cache misses and memory growth.

#### Traps / caveats

- Final reference fields do not make the referenced object immutable.
- Changing a key value object inside a map does not rehash the map.
- Prefer records or explicit immutable key classes.

#### Optional Anki

Q: What mutation is dangerous for a `HashMap` key?
A: Mutation of fields used by `equals()` or `hashCode()`.

</details>

<a id="hm-key-002"></a>

<details>
<summary><strong>HM-KEY-002. What happens if a key is mutated after being added to `HashMap`?</strong></summary>

#### Short answer

The entry can become unreachable by normal lookup because the key may now hash to a different bucket or compare differently.

#### Interview answer

When a key is inserted, `HashMap` stores it in a bucket based on its hash at that time. If the key's hash changes later, `get()` computes a different bucket path and cannot find the old entry. If equality changes, matching can also fail or collide with another logical key.

The map is not notified and does not repair itself.

#### Deep dive

The corrupted entry still occupies memory. Iterating the map may reveal it, but `containsKey()` can return false for the mutated key. Removing it can also fail unless you find the exact old path or remove through iteration.

#### Production angle

This often appears as unbounded cache growth: entries are inserted but cannot be removed by the mutated key object later.

#### Traps / caveats

- The bug can be invisible when using the same object before mutation.
- Mutating a value object stored as a value is different from mutating a key.
- Remove-before-mutate-then-reinsert is the safe pattern when mutation is unavoidable.

#### Optional Anki

Q: Does `HashMap` re-index a key after the key changes?
A: No.

</details>

<a id="hm-key-003"></a>

<details>
<summary><strong>HM-KEY-003. What are the requirements for a good `HashMap` key?</strong></summary>

#### Short answer

A good key has stable equality, a consistent well-distributed hash code, and fields that accurately represent lookup identity.

#### Interview answer

Good keys are usually immutable, have correct `equals()` and `hashCode()`, use the same stable fields in both methods, and avoid external state. They should be cheap enough to compare and hash in the expected workload.

The key should also include all context needed for uniqueness, such as tenant ID, locale or version when those affect the mapped value.

#### Deep dive

Records are often good key classes because they make component-based equality easy. Domain-specific keys are better than reusing large mutable request or entity objects.

For special domains, consider specialized maps: `EnumMap` for enum keys, `IdentityHashMap` for identity semantics, or a cache library for eviction.

#### Production angle

Good key design prevents cache leakage, cross-tenant data bugs, deduplication mistakes and performance problems.

#### Traps / caveats

- Do not omit tenant or authorization context from cache keys.
- Do not use mutable collections or arrays without defensive copying.
- Do not use object identity accidentally when logical equality is required.

#### Optional Anki

Q: What are three traits of a good map key?
A: Immutable identity, correct equality/hash, and all required uniqueness context.

</details>

<a id="hm-key-004"></a>

<details>
<summary><strong>HM-KEY-004. Why are `String` and records often good `HashMap` keys?</strong></summary>

#### Short answer

`String` is immutable with well-defined equality and hashing, and records generate component-based equality for stable value-like data.

#### Interview answer

`String` is a classic key because its content does not change, its equality is value-based, and its hash behavior is optimized by the JDK. Records are good for composite keys because the compiler generates `equals()` and `hashCode()` from the declared components.

Both reduce the chance of accidentally using identity-based equality.

#### Deep dive

Records are only shallowly immutable. If a record component is a mutable list, array or request object, the record key can still be unsafe. `String` is safe as a value, but string normalization still matters: case, whitespace, Unicode normalization and locale rules can affect logical identity.

#### Production angle

Use clear normalized keys for caches and grouping. For example, a record `CacheKey(String tenantId, Long userId, String feature)` is better than using a whole request object.

#### Traps / caveats

- Records with mutable components are not deeply immutable.
- `String` keys may need normalization.
- Do not concatenate strings into ambiguous composite keys without separators or escaping.

#### Optional Anki

Q: Why are records useful for composite map keys?
A: They generate component-based `equals()` and `hashCode()`.

</details>

<a id="hm-key-005"></a>

<details>
<summary><strong>HM-KEY-005. What can go wrong when using arrays as `HashMap` keys?</strong></summary>

#### Short answer

Arrays use identity-based `equals()` and `hashCode()`, so different arrays with the same contents are different keys.

#### Interview answer

In Java, arrays do not override `Object.equals()` for content. If you use `byte[]` or `String[]` directly as a key, lookup with another array containing the same elements will fail. The default hash is identity-based too.

Arrays are also mutable, so content-based wrappers must be careful.

#### Deep dive

If content equality is needed, wrap the array in an immutable key object that defensively copies the array and uses `Arrays.equals()` and `Arrays.hashCode()`. For nested arrays, use deep variants where appropriate.

#### Production angle

This matters for binary IDs, hashes, serialized payloads and composite keys. Direct array keys can create duplicate cache entries and missed lookups.

#### Traps / caveats

- `Objects.equals(array1, array2)` is not content equality.
- `List.of(array)` creates a list containing the array, not a list of array elements.
- Defensive copies are needed if the source array can be mutated.

#### Optional Anki

Q: Do arrays compare contents with `equals()`?
A: No; array `equals()` is reference equality.

</details>

<a id="hm-key-006"></a>

<details>
<summary><strong>HM-KEY-006. What can go wrong when using `List` or `Set` as `HashMap` keys?</strong></summary>

#### Short answer

Collections can work as keys if they are not mutated, but mutable collection keys are easy to break.

#### Interview answer

`List` and `Set` define content-based equality and hash codes. A list compares ordered elements; a set compares membership. So they can be valid keys if their contents and contained elements remain stable.

The risk is mutation. Adding, removing or mutating an element can change the collection's hash code and equality.

#### Deep dive

A list key also depends on element order. A set key depends on element equality and hashing. If elements themselves are mutable, the collection's key behavior can change even when the collection object is not structurally modified.

Immutable copies such as `List.copyOf()` or a purpose-built record are usually safer.

#### Production angle

Using request parameter lists directly as cache keys can fail if the list is later sorted, filtered or reused. Normalize and copy key components at the boundary.

#### Traps / caveats

- `List` equality is order-sensitive.
- `Set` equality is order-insensitive but element-based.
- Mutating elements can break the key even if the collection size is unchanged.

#### Optional Anki

Q: When is a `List` safe as a map key?
A: When the list and all equality-relevant elements remain unchanged.

</details>

<a id="hm-key-007"></a>

<details>
<summary><strong>HM-KEY-007. Can `BigDecimal` be tricky as a `HashMap` key?</strong></summary>

#### Short answer

Yes. `BigDecimal.equals()` includes scale, so numerically equal values with different scales can be different keys.

#### Interview answer

`new BigDecimal("1.0")` and `new BigDecimal("1.00")` compare as equal by `compareTo()`, but they are not equal by `equals()`. `HashMap` uses `equals()` and `hashCode()`, so those values are distinct keys.

#### Deep dive

This becomes subtle when values come from different sources: JSON, database, calculations or UI input. One path may produce scale 2, another scale 4.

Normalize scale before using `BigDecimal` as a key, or wrap it in a domain type that defines the intended equality.

#### Production angle

Money, tax and pricing caches should define scale and rounding rules explicitly. Otherwise equivalent amounts can miss cache or group separately.

#### Traps / caveats

- `HashMap` does not use `compareTo()`.
- `TreeMap` with natural ordering can behave differently from `HashMap`.
- Normalization rules must be domain-specific.

#### Optional Anki

Q: Which method does `HashMap` use for `BigDecimal` key equality?
A: `equals()`, not `compareTo()`.

</details>

<a id="hm-key-008"></a>

<details>
<summary><strong>HM-KEY-008. Should JPA entities be used as `HashMap` keys?</strong></summary>

#### Short answer

Usually avoid it unless entity equality is carefully designed, stable and tested across lifecycle states and proxies.

#### Interview answer

JPA entities are mutable, may have generated IDs, and can be represented by proxies. That makes them risky as hash keys. If equality depends on a generated ID, the ID may be null before persistence and assigned later. If equality touches lazy fields, it can trigger SQL or fail outside a session.

Prefer immutable IDs or dedicated key objects.

#### Deep dive

Entity identity has multiple meanings: Java object identity, persistence identity, database primary key and business identity. Mixing them in `equals()` can break collections. Many teams avoid putting entities in hash-based collections or use stable business keys where appropriate.

#### Production angle

Entity-key bugs show up as duplicate children in sets, failed removals, cache misses and unexpected lazy loading. They are especially painful in Hibernate collections.

#### Traps / caveats

- Generated IDs can change equality after persist.
- Proxies can break strict class checks.
- Lazy associations should not participate in equality.

#### Optional Anki

Q: What is safer than using a JPA entity as a map key?
A: Use its stable ID or a dedicated immutable key object.

</details>

<a id="hm-key-009"></a>

<details>
<summary><strong>HM-KEY-009. What are `equals()` and `hashCode()` pitfalls for Hibernate entities?</strong></summary>

#### Short answer

Pitfalls include generated IDs, proxies, lazy associations, mutable fields, inheritance and bidirectional relationship recursion.

#### Interview answer

Hibernate entities are not simple value objects. A generated ID may be null before flush and non-null afterward. Proxies may be subclasses. Lazy associations can trigger database access during equality. Bidirectional relationships can recurse. Mutable fields can change while the entity is inside a set.

So entity equality must be deliberately designed, not generated from all fields.

#### Deep dive

Using all fields in entity equality is usually wrong. Using only generated ID also needs care for transient entities. A stable natural key can work if it is immutable and truly unique. Otherwise, avoid relying on entity equality in hash-based structures.

#### Production angle

Bad entity equality can break Hibernate dirty checking assumptions, collection synchronization, orphan removal behavior and application-level deduplication.

#### Traps / caveats

- Do not include lazy collections in `equals()` or `hashCode()`.
- Test transient, managed, detached and proxy cases.
- Lombok `@Data` on entities is often dangerous.

#### Optional Anki

Q: Why is "all fields" equality bad for Hibernate entities?
A: It can include mutable fields, lazy associations and recursive relationships.

</details>

<a id="hm-key-010"></a>

<details>
<summary><strong>HM-KEY-010. How do generated IDs affect `equals()` and `hashCode()` in entities?</strong></summary>

#### Short answer

Generated IDs are often null before persistence and assigned later, so ID-based equality or hashing can change during the entity lifecycle.

#### Interview answer

If `equals()` and `hashCode()` use a generated ID, a new entity may have no ID when it is added to a `HashSet`. After persistence assigns the ID, its hash code can change and the set may no longer find it.

This is one reason generated-ID entities are risky in hash-based collections before they are persisted.

#### Deep dive

Common approaches include using immutable natural keys, using ID equality only after assignment with careful null handling, or avoiding entity instances as map keys altogether. Some designs use a stable class-based hash for entities to avoid hash changes, but that has performance trade-offs and still needs careful equality rules.

#### Production angle

Lifecycle-sensitive equality bugs often appear during create/update workflows, tests with cascading persistence, and Hibernate `Set` mappings.

#### Traps / caveats

- Null IDs do not prove two transient entities are equal.
- Hash code must not change while the entity is in a hash collection.
- Proxy behavior must be considered.

#### Optional Anki

Q: Why can generated IDs break entity hash codes?
A: The ID may be assigned after the entity is already inside a hash-based collection.

</details>

<a id="hm-key-011"></a>

<details>
<summary><strong>HM-KEY-011. What key would you choose for a cache map?</strong></summary>

#### Short answer

Use an immutable, normalized key that includes every input dimension affecting the cached value.

#### Interview answer

For a cache, I would create a small key type, often a record, with fields such as tenant ID, entity ID, method parameters, locale, feature flags or version if those affect the result. The key should be immutable, have stable equality, avoid large object graphs and avoid mutable request/entity objects.

#### Deep dive

Cache key design is about correctness first. If tenant, permission scope or data version is missing, the cache can return the wrong data. If too many irrelevant fields are included, hit rate drops.

Keys should also be cheap to allocate, hash and compare.

#### Production angle

Bad cache keys cause cross-tenant leaks, stale data, low hit rate or memory growth. For real production caches, also use eviction, TTL, size limits and metrics.

#### Traps / caveats

- Do not key by raw request objects.
- Include tenant/security context when required.
- Normalize strings and numbers consistently.

#### Optional Anki

Q: What is the main correctness rule for cache keys?
A: Include every input that can change the cached result.

</details>

<a id="hm-key-012"></a>

<details>
<summary><strong>HM-KEY-012. How do you design a composite key class?</strong></summary>

#### Short answer

Make it immutable, include exactly the identity fields, implement consistent equality and hashing, and normalize inputs at construction.

#### Interview answer

A good composite key is usually a record or final class with final fields. It should defensively copy mutable inputs, normalize values such as case or scale where needed, and use all identity fields in `equals()` and `hashCode()`.

For example, `record UserFeatureKey(String tenantId, long userId, String featureName)`.

#### Deep dive

Avoid ambiguous string concatenation such as `tenant + ":" + id` unless escaping is handled. A structured key avoids collisions like `("a:b", "c")` versus `("a", "b:c")`.

Composite keys should be small and cheap; do not embed full request or entity graphs.

#### Production angle

Composite keys are common in caches, grouping, database result indexing and idempotency maps. Good design prevents subtle correctness bugs.

#### Traps / caveats

- Include tenant or namespace when data is multi-tenant.
- Defensively copy arrays and collections.
- Keep key equality independent from external state.

#### Optional Anki

Q: Why prefer a structured composite key over concatenated strings?
A: It avoids ambiguity and gives correct typed equality.

</details>

<a id="hm-key-013"></a>

<details>
<summary><strong>🧠 HM-KEY-013. Should `hashCode()` be cached, and when can cached hash codes be safe?</strong></summary>

#### Short answer

Cache a hash code only for immutable objects where computing the hash is expensive or very frequent.

#### Interview answer

Caching `hashCode()` can be safe when the object's equality-relevant state never changes. `String` is the classic example. It can help for large immutable keys such as long strings, byte sequences or complex value objects.

For mutable objects, cached hash codes are dangerous because the cached value can become inconsistent with equality.

#### Deep dive

Lazy hash caching should be implemented carefully. A benign race that computes the same value twice may be acceptable for immutable objects, but publication and sentinel values need thought. Eager computation can be simpler if construction cost is acceptable.

Most ordinary key classes do not need cached hashes.

#### Production angle

Consider cached hashes only after profiling shows hash computation is material. Otherwise it adds state and complexity without benefit.

#### Traps / caveats

- Never cache hash code for mutable equality state.
- Arrays and collections require defensive copies before cached content hashes are safe.
- Cached hash code does not fix poor distribution.

#### Optional Anki

Q: When is cached `hashCode()` safe?
A: When all equality-relevant state is immutable.

</details>

<a id="hm-key-014"></a>

<details>
<summary><strong>HM-KEY-014. What can go wrong if `equals()` or `hashCode()` depend on external state?</strong></summary>

#### Short answer

Equality can become inconsistent, slow or side-effecting, which breaks collections and makes behavior unpredictable.

#### Interview answer

`equals()` and `hashCode()` should be deterministic for the object's stable state. If they depend on the database, clock, locale, configuration, remote service, security context or lazy-loaded association, the result can change between calls or trigger unexpected work.

Hash-based collections assume these methods are cheap and stable.

#### Deep dive

External state also creates testing and concurrency problems. Two equal objects might become unequal after config changes. Equality might throw because a Hibernate session is closed. A remote lookup inside `equals()` can turn a set operation into an unreliable network call.

#### Production angle

These bugs cause latency spikes, deadlocks, lazy-loading failures and inconsistent cache behavior. Equality should not surprise the caller.

#### Traps / caveats

- Do not perform I/O in `equals()` or `hashCode()`.
- Avoid locale-sensitive normalization at comparison time.
- Keep equality based on local immutable state.

#### Optional Anki

Q: Why should `equals()` avoid external state?
A: Collections require equality to be stable, cheap and side-effect free.

</details>
