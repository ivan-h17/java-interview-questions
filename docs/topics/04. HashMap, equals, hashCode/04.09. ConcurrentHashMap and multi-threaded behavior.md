# 04.09. ConcurrentHashMap and multi-threaded behavior

---

<a id="hm-conc-001"></a>

<details>
<summary><strong>HM-CONC-001. Is `HashMap` thread-safe?</strong></summary>

#### Short answer

No. `HashMap` is not thread-safe for concurrent mutation.

#### Interview answer

Multiple threads can read a safely published, effectively immutable `HashMap`. But if at least one thread mutates the map while others read or write without synchronization, behavior is unsafe. You can see lost updates, stale reads, inconsistent iteration or internal corruption.

For concurrent updates, use `ConcurrentHashMap`, external locking or another concurrency design.

#### Deep dive

Thread-safety is not only about exceptions. Without a happens-before relationship, one thread may not see another thread's changes correctly. `HashMap` has no internal synchronization, volatile publication guarantees for all operations, or atomic compound operations.

#### Production angle

Unsynchronized `HashMap` mutation often appears in static caches, request-scoped objects accidentally shared between threads, scheduled jobs and lazy initialization.

#### Traps / caveats

- "Reads are safe" only if the map is not being concurrently mutated and is safely published.
- Fail-fast iterators are not a concurrency control mechanism.
- `volatile Map` does not make the map contents thread-safe.

#### Optional Anki

Q: Is `HashMap` safe for concurrent writes?
A: No.

</details>

<a id="hm-conc-002"></a>

<details>
<summary><strong>HM-CONC-002. What can go wrong if multiple threads modify a `HashMap` concurrently?</strong></summary>

#### Short answer

Updates can be lost, reads can see inconsistent state, iteration can fail, and internal structure can become corrupted.

#### Interview answer

`HashMap` assumes single-threaded or externally synchronized mutation. Concurrent `put`, `remove` or resize can interleave in ways the implementation does not protect against. Results can include missing entries, incorrect size, `ConcurrentModificationException`, stale values or much worse undefined behavior from the application's perspective.

#### Deep dive

Even if corruption does not happen in a particular run, check-then-act logic can still race. For example, two threads can both see a missing key and both compute/insert different values.

The Java Memory Model also matters: without synchronization, visibility is not guaranteed.

#### Production angle

These bugs are usually intermittent and load-dependent. They often disappear under debugging and reappear under real traffic.

#### Traps / caveats

- Passing tests once does not prove thread-safety.
- Concurrent reads during writes are unsafe.
- A synchronized method around one call may not protect a multi-call workflow.

#### Optional Anki

Q: What should you use for concurrent map updates?
A: Usually `ConcurrentHashMap` or explicit synchronization.

</details>

<a id="hm-conc-003"></a>

<details>
<summary><strong>HM-CONC-003. How does `ConcurrentHashMap` provide thread-safety at a high level?</strong></summary>

#### Short answer

It coordinates access internally using volatile reads, CAS and fine-grained locking around updates rather than synchronizing the whole map for every operation.

#### Interview answer

Modern `ConcurrentHashMap` allows many reads and updates to proceed concurrently. Reads are generally non-blocking. Updates coordinate at a fine-grained level, often per bucket/bin, using CAS and synchronization where needed.

It also provides atomic compound operations such as `putIfAbsent`, `compute` and `merge`.

#### Deep dive

The implementation is more complex than `HashMap`: table initialization, resizing, bin updates and tree bins are all designed for concurrent access. Iterators are weakly consistent, so they do not throw `ConcurrentModificationException` for concurrent updates.

#### Production angle

`ConcurrentHashMap` is a good default for shared in-memory indexes and counters, but it does not provide eviction, TTL or distributed consistency.

#### Traps / caveats

- It forbids null keys and values.
- Atomic map operations do not make external side effects atomic.
- Mapping functions must be short and safe.

#### Optional Anki

Q: Are `ConcurrentHashMap` reads usually globally locked?
A: No; reads are designed to be highly concurrent.

</details>

<a id="hm-conc-004"></a>

<details>
<summary><strong>🧠 HM-CONC-004. What changed in `ConcurrentHashMap` after Java 8?</strong></summary>

#### Short answer

Java 8-style `ConcurrentHashMap` moved away from fixed segments and uses a table of bins with CAS, synchronized bin updates and tree bins.

#### Interview answer

Older `ConcurrentHashMap` designs are often described as segmented: the map was divided into segments that acted like smaller locked maps. Modern implementations no longer expose that model internally. They use finer-grained coordination around table bins, CAS for some updates, cooperative resizing and tree bins for heavy collisions.

#### Deep dive

This is why old interview answers like "ConcurrentHashMap locks one of 16 segments" are outdated for modern Java. The constructor parameter historically called concurrency level is no longer the simple segmentation count people often imagine.

#### Production angle

The practical message is that modern `ConcurrentHashMap` scales well for many common workloads, but contention can still happen on hot keys or long-running mapping functions.

#### Traps / caveats

- Do not explain modern `ConcurrentHashMap` only with segments.
- Hot keys can still serialize updates.
- Internal details remain implementation-specific.

#### Optional Anki

Q: What is outdated about saying Java 8+ `ConcurrentHashMap` uses fixed segments?
A: Modern implementations coordinate around table bins rather than the old fixed segment model.

</details>

<a id="hm-conc-005"></a>

<details>
<summary><strong>HM-CONC-005. What are atomic operations in `ConcurrentHashMap`?</strong></summary>

#### Short answer

They are operations that perform a compound map action safely as one operation, such as `putIfAbsent`, `compute`, `computeIfAbsent`, `merge` and conditional `remove`.

#### Interview answer

Atomic map operations prevent common races where code checks a key and then acts on the result. For example, `putIfAbsent` inserts only if no mapping exists. `compute` recalculates a value while coordinating with other updates for that key. `merge` is useful for adding or combining values.

Use these instead of manual check-then-act code.

#### Deep dive

Atomicity is scoped to the map operation and usually the affected key/bin. It does not make arbitrary external operations atomic. If the mapping function writes to a database or mutates another object, that side effect has its own concurrency rules.

#### Production angle

Atomic operations are essential for shared caches, registries and counters. They reduce race bugs and usually make code clearer.

#### Traps / caveats

- Mapping functions can be invoked under internal coordination, so keep them short.
- Returning null from some remapping functions can remove or skip mappings.
- Atomic map operation does not equal distributed lock.

#### Optional Anki

Q: Which method atomically inserts only when absent?
A: `putIfAbsent()`.

</details>

<a id="hm-conc-006"></a>

<details>
<summary><strong>HM-CONC-006. Why is check-then-act unsafe with maps?</strong></summary>

#### Short answer

Another thread can change the map between the check and the action.

#### Interview answer

Code like `if (!map.containsKey(k)) map.put(k, v)` is two operations. In concurrent code, two threads can both see the key as absent and both insert or compute values. This creates lost work, duplicate initialization or inconsistent state.

Use atomic methods such as `putIfAbsent()` or `computeIfAbsent()`.

#### Deep dive

Even if each individual call is thread-safe, the sequence is not automatically atomic. This is true for synchronized wrappers too unless the entire sequence is protected by the same lock.

#### Production angle

Check-then-act races appear in lazy caches, singleton registries, token stores and rate limiter state.

#### Traps / caveats

- `containsKey()` plus `put()` is not atomic.
- `get()` plus `put()` is not atomic.
- Atomic map methods still need safe mapping functions.

#### Optional Anki

Q: What replaces `containsKey()` then `put()` in concurrent code?
A: `putIfAbsent()` or `computeIfAbsent()`.

</details>

<a id="hm-conc-007"></a>

<details>
<summary><strong>HM-CONC-007. How should you implement a frequency map with `ConcurrentHashMap`?</strong></summary>

#### Short answer

Use `ConcurrentHashMap<K, LongAdder>` with `computeIfAbsent()` and increment the adder.

#### Interview answer

A common scalable pattern is:

```java
ConcurrentHashMap<K, LongAdder> counts = new ConcurrentHashMap<>();
counts.computeIfAbsent(key, k -> new LongAdder()).increment();
```

`LongAdder` reduces contention compared with repeatedly replacing boxed `Long` values under heavy updates.

#### Deep dive

For low contention, `merge(key, 1L, Long::sum)` can be simpler. Under high contention on hot keys, it creates boxed values and contention around updates. `LongAdder` spreads updates internally and is designed for counters.

#### Production angle

Use this for metrics-like counters, event counts and in-memory aggregations. For exact transactional counts across nodes, use a database or distributed system with the right consistency model.

#### Traps / caveats

- `LongAdder.sum()` is not an atomic snapshot with concurrent updates.
- The adder object is mutable, so expose it carefully.
- Clean up keys if the key space is unbounded.

#### Optional Anki

Q: What value type is commonly used for high-contention frequency maps?
A: `LongAdder`.

</details>

<a id="hm-conc-008"></a>

<details>
<summary><strong>HM-CONC-008. What are `computeIfAbsent()`, `compute()`, `merge()` and `putIfAbsent()` used for?</strong></summary>

#### Short answer

They are compound map operations for lazy creation, recalculation, combining values and insert-if-missing behavior.

#### Interview answer

`putIfAbsent(k, v)` inserts a ready value only when the key has no value. `computeIfAbsent(k, f)` creates a value lazily when missing. `compute(k, f)` recalculates the value whether it is present or absent. `merge(k, value, f)` inserts the given value if absent or combines it with the old value if present.

#### Deep dive

Null behavior matters. In many map methods, a null result from a mapping/remapping function means no mapping should be recorded or an existing mapping should be removed. In `HashMap`, "absent" and "mapped to null" can interact subtly; in `ConcurrentHashMap`, null values are not allowed.

#### Production angle

These methods simplify caches, grouping and counters, but mapping functions should be deterministic and side-effect safe.

#### Traps / caveats

- Do not call slow I/O inside mapping functions for hot shared maps.
- `computeIfAbsent()` may not store anything if the function returns null.
- `merge()` is often the cleanest counter update for simple values.

#### Optional Anki

Q: Which method lazily creates a value only when missing?
A: `computeIfAbsent()`.

</details>

<a id="hm-conc-009"></a>

<details>
<summary><strong>🧠 HM-CONC-009. What concurrency caveats exist with `ConcurrentHashMap` mapping functions?</strong></summary>

#### Short answer

Mapping functions should be short, deterministic and avoid updating the same map or doing blocking side effects.

#### Interview answer

Methods such as `compute`, `computeIfAbsent` and `merge` may run the mapping function while coordinating updates for a key or bin. A slow function can block other updates. A function that mutates the same map recursively can fail or cause confusing behavior. External side effects are also outside the map operation's atomicity, so the map cannot roll them back or make them consistent with other systems.

#### Deep dive

The safest mapping function computes a value from its arguments and returns quickly. Avoid database calls, remote calls, waiting on locks, publishing half-built objects, or modifying other mappings in the same map.

#### Production angle

Bad mapping functions create throughput collapses, deadlocks or duplicate side effects. For expensive loading, consider a cache library that handles single-flight loading, timeouts and eviction.

#### Traps / caveats

- Atomic map update does not make external side effects atomic.
- Recursive updates can be rejected or deadlock-like in practice.
- Long-running functions create contention on hot keys.

#### Optional Anki

Q: What should a `ConcurrentHashMap` mapping function avoid?
A: Blocking work, side effects and recursive updates to the same map.

</details>

<a id="hm-conc-010"></a>

<details>
<summary><strong>HM-CONC-010. Why should `ConcurrentHashMap` mapping functions be short and side-effect safe?</strong></summary>

#### Short answer

Because they may run while other map operations are waiting for the affected key/bin, and side effects are not protected by the map's atomicity.

#### Interview answer

A mapping function is part of a coordinated map update. If it blocks on I/O, sleeps, grabs unrelated locks or performs slow computation, it can reduce concurrency. If it performs side effects, failures or retries can leave the external world inconsistent with the map.

Keep mapping functions small and pure where possible.

#### Deep dive

For lazy cache loading, it is tempting to call a remote service inside `computeIfAbsent()`. That can make all requests for the same hot key wait inside the map operation. A dedicated cache abstraction may provide better timeout, refresh and error handling.

#### Production angle

This affects shared registries, caches and counters under load. A single hot key with slow computation can become a throughput bottleneck.

#### Traps / caveats

- Do not hold application locks and then call map compute methods casually.
- Do not assume the map rolls back external side effects.
- Publish fully initialized values only.

#### Optional Anki

Q: Why keep map compute functions short?
A: They can block coordinated updates for related map state.

</details>

<a id="hm-conc-011"></a>

<details>
<summary><strong>🧠 HM-CONC-011. What are weakly consistent iterators in `ConcurrentHashMap`?</strong></summary>

#### Short answer

They are iterators that do not throw `ConcurrentModificationException` and may reflect some concurrent updates without guaranteeing a fixed snapshot.

#### Interview answer

`ConcurrentHashMap` iterators are designed for concurrent traversal. They can proceed while the map is being updated. They may see entries that existed when iteration began and may also see some updates made during iteration, but they do not promise a consistent snapshot.

#### Deep dive

This is different from `HashMap` fail-fast iterators and from snapshot iterators such as `CopyOnWriteArrayList`. Weak consistency favors progress and concurrency over a frozen view.

#### Production angle

Weakly consistent iteration is fine for metrics, cleanup scans and approximate reporting. It is not enough for exact accounting or transactional decisions.

#### Traps / caveats

- No `ConcurrentModificationException` does not mean snapshot consistency.
- Size and iteration can disagree during concurrent updates.
- Use locks or copies when an exact snapshot is required.

#### Optional Anki

Q: Do `ConcurrentHashMap` iterators throw `ConcurrentModificationException` on concurrent updates?
A: No; they are weakly consistent.

</details>

<a id="hm-conc-012"></a>

<details>
<summary><strong>HM-CONC-012. When would you still use external locking around a map?</strong></summary>

#### Short answer

Use external locking when you need to protect a larger invariant than a single map operation can guarantee.

#### Interview answer

`ConcurrentHashMap` protects individual map operations and some per-key compound operations. If the business rule spans multiple keys, multiple maps, a map plus another object, or a check followed by external side effects, you may still need a lock, transaction or other coordination mechanism.

#### Deep dive

Examples include moving capacity between accounts, enforcing "at most N active sessions" across several keys, or updating a map and database consistently. A concurrent map does not make those workflows atomic.

#### Production angle

Choose the synchronization scope based on the invariant. Sometimes a per-user lock, striped lock, database constraint or transaction is a better fit than a global lock.

#### Traps / caveats

- External locking can reduce concurrency.
- Always define the invariant before choosing a lock.
- Avoid mixing locks and compute functions without a clear order.

#### Optional Anki

Q: What does external locking protect that `ConcurrentHashMap` may not?
A: Multi-step or multi-object business invariants.

</details>

<a id="hm-conc-013"></a>

<details>
<summary><strong>HM-CONC-013. Can `ConcurrentHashMap` make a multi-step business invariant thread-safe?</strong></summary>

#### Short answer

No. It can make map operations thread-safe, but larger invariants need their own coordination.

#### Interview answer

For example, `ConcurrentHashMap` can atomically update one key. But if the invariant says "create an order only if user quota, account balance and reservation map all agree," the map alone cannot protect that. You need a transaction, lock, compare-and-set state machine or another consistency mechanism.

#### Deep dive

The danger is assuming thread-safe data structures automatically make the algorithm thread-safe. They only protect their own operations. The correctness boundary may be much larger.

#### Production angle

This distinction matters in rate limiting, inventory reservation, session limits and idempotency. Many production race bugs survive because each individual collection is thread-safe.

#### Traps / caveats

- Thread-safe collection does not imply thread-safe workflow.
- Per-key atomicity is not global atomicity.
- Database constraints may be the correct final guard.

#### Optional Anki

Q: Does `ConcurrentHashMap` make a whole business transaction atomic?
A: No.

</details>

<a id="hm-conc-014"></a>

<details>
<summary><strong>HM-CONC-014. How would you debug race conditions involving maps?</strong></summary>

#### Short answer

Look for unsynchronized shared mutation, check-then-act sequences, mutable keys, unsafe publication and incorrect assumptions about atomicity.

#### Interview answer

I would first identify who owns the map and which threads access it. Then I would inspect all writes, compound operations and iterations. I would search for `containsKey` plus `put`, `get` plus mutation, lazy initialization, mutable keys and map replacement without safe publication.

Then I would reproduce under stress with targeted tests and add logging around key operations if needed.

#### Deep dive

Useful tools include thread dumps for deadlocks/contention, profilers for hot locks, stress tests, concurrency test frameworks, and production telemetry. The fix might be `ConcurrentHashMap`, an atomic method, external locking, immutable snapshots or moving state to a database.

#### Production angle

Race bugs are timing-sensitive. Capture enough context: key, thread, operation, old/new value, request ID and whether the map is shared across requests.

#### Traps / caveats

- Do not assume `ConcurrentModificationException` is required for a race.
- Do not fix by adding random `synchronized` blocks without defining the invariant.
- Verify key immutability as part of the investigation.

#### Optional Anki

Q: What map pattern is a common race smell?
A: Check-then-act, such as `containsKey()` followed by `put()`.

</details>
