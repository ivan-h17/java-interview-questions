# 04.01. Equality and hashing fundamentals

---

<a id="hm-fund-001"></a>

<details>
<summary><strong>HM-FUND-001. What is the difference between object identity, logical equality and `==`?</strong></summary>

#### Short answer

Object identity means two references point to the same object. Logical equality means two objects represent the same value according to `equals()`. For objects, `==` checks identity; for primitives, it compares primitive values.

#### Interview answer

In Java, every object has identity: two references are identical if they refer to the same instance. Logical equality is domain-specific and is implemented through `equals()`, for example two `String` objects can be different instances but equal text values.

The `==` operator is often the trap. With primitives, `==` compares values. With object references, it compares whether both references point to the same object, not whether their content is equal.

#### Deep dive

The default `Object.equals()` implementation uses identity, so if a class does not override `equals()`, `a.equals(b)` behaves like `a == b`. Value-like classes such as `String`, `Integer`, `BigDecimal` and records usually override equality to compare meaningful state.

Object identity can still be useful for synchronization, reference tracking, object graphs and identity-based maps, but most business keys need logical equality.

#### Production angle

Confusing identity and logical equality breaks deduplication, cache lookup, `HashSet`, `HashMap`, authorization checks and request matching. It often appears as "the object is clearly there, but lookup returns null" because the key instance is different or equality is wrong.

#### Traps / caveats

- Use `equals()` for logical equality of objects, not `==`.
- `==` sometimes appears to work with interned strings or cached boxed integers, which makes the bug harder to notice.
- The default `equals()` is identity-based.

#### Optional Anki

Q: What does `==` compare for object references?
A: Object identity: whether both references point to the same instance.

</details>

<details>
<summary><strong>HM-FUND-002. What is `hashCode()`, and how is hash-code equality different from object equality?</strong></summary>

#### Short answer

`hashCode()` returns an integer used by hash-based structures to choose a search area. Equal objects must have equal hash codes, but equal hash codes do not prove objects are equal.

#### Interview answer

`hashCode()` is a fast, coarse grouping function. `HashMap` uses it to find a bucket and then uses `equals()` to find the exact key. The contract is one-way: if `a.equals(b)` is true, then `a.hashCode() == b.hashCode()` must be true. The reverse is not required because many different objects can produce the same `int` hash code.

#### Deep dive

There are only about four billion possible `int` values and potentially unlimited object states, so collisions are unavoidable. A good hash code spreads common values well enough to keep buckets small. It does not need to be unique, cryptographic or stable across JVM runs unless a specific API says so.

#### Production angle

Poor or inconsistent hash codes cause slow lookups, missed keys and broken sets. In backend systems this can affect caches, request deduplication, grouping logic and Hibernate collections.

#### Traps / caveats

- Same hash code does not mean same object.
- Equal objects must have the same hash code.
- Do not persist Java hash codes as stable business identifiers.

#### Optional Anki

Q: If two objects have the same `hashCode()`, are they equal?
A: Not necessarily; `equals()` still decides logical equality.

</details>

<details>
<summary><strong>HM-FUND-003. Why do hash-based collections need both `equals()` and `hashCode()`?</strong></summary>

#### Short answer

`hashCode()` narrows the search to a bucket, and `equals()` confirms the exact matching element or key.

#### Interview answer

A hash-based collection uses `hashCode()` for performance and `equals()` for correctness. `hashCode()` tells the collection where to look. Because collisions are possible, the collection then compares candidates with `equals()`.

For a `HashMap`, lookup roughly means: compute the key hash, choose a bucket, scan or tree-search that bucket, and compare matching-hash candidates with `equals()`.

#### Deep dive

Without `hashCode()`, every lookup would need to compare against many or all entries. Without `equals()`, the collection could not distinguish two different keys that land in the same bucket or have the same hash.

This is why overriding only one method is usually a bug. Hash-based structures depend on the two methods being consistent with each other.

#### Production angle

Broken `equals()` or `hashCode()` can make values impossible to find, duplicate "unique" entries, or produce intermittent behavior after object mutation. These bugs are common in cache keys, DTO keys and entity collections.

#### Traps / caveats

- Hashing is an optimization; equality is the final correctness check.
- Collisions are normal and must be handled correctly.
- Mutating a key field after insertion breaks the lookup path.

#### Optional Anki

Q: What roles do `hashCode()` and `equals()` play in `HashMap`?
A: `hashCode()` selects the bucket; `equals()` confirms the exact key.

</details>

<details>
<summary><strong>HM-FUND-004. What are a hash table, a hash function and a bucket?</strong></summary>

#### Short answer

A hash table stores entries in an array-like table. A hash function converts a key into a hash value. A bucket is the table slot where entries with a matching bucket index are stored.

#### Interview answer

In a hash table, the key is passed through a hash function. The resulting hash is converted into an index in an internal table. That index points to a bucket. If the hash function distributes keys well, entries spread across many buckets and lookup is fast.

`HashMap` is Java's general-purpose hash table implementation for key-value mappings.

#### Deep dive

A bucket can contain zero, one or multiple entries. Multiple entries in the same bucket are called collisions. Java `HashMap` handles bucket collisions with linked nodes and, under heavy collision conditions, tree bins.

The table capacity controls how many buckets exist. The map size controls how many mappings are stored.

#### Production angle

Understanding buckets helps explain why `HashMap` is usually fast but not magic. Capacity, load factor, key distribution and equality cost all affect real latency and memory usage.

#### Traps / caveats

- A bucket is not the same thing as a key.
- A hash code is not directly the bucket index; it is transformed to fit table capacity.
- More buckets usually reduce collisions but increase memory and iteration cost.

#### Optional Anki

Q: What is a bucket in a hash table?
A: A table slot that stores entries mapped to the same bucket index.

</details>

<a id="hm-fund-005"></a>

<details>
<summary><strong>HM-FUND-005. What is a hash collision, and why are collisions unavoidable?</strong></summary>

#### Short answer

A collision happens when different keys end up in the same bucket or have the same hash code. Collisions are unavoidable because many possible keys must be mapped into a limited number of hash values and buckets.

#### Interview answer

Hashing compresses a large key space into an `int` hash and then into a finite table index. Because there are more possible objects than hash values, different objects can share a hash. Even different hashes can map to the same bucket when the table has fewer buckets than possible hash values.

Collisions are expected; the goal is to keep them rare and cheap.

#### Deep dive

There are two related ideas. A hash-code collision means two unequal objects return the same `hashCode()`. A bucket collision means two entries are placed into the same table bucket. Bucket collisions can happen even when full hash codes differ because the bucket index uses only the current table size.

#### Production angle

Normal collisions are fine. Pathological collisions cause CPU spikes in request parsing, caches, grouping logic or any hot map-heavy path. This is why key design and input validation matter for untrusted data.

#### Traps / caveats

- Collision handling is part of normal `HashMap` behavior.
- Unique hash codes are not required and usually impossible.
- A collision does not mean data loss; `equals()` still distinguishes keys.

#### Optional Anki

Q: Why are hash collisions unavoidable?
A: A limited number of hash values and buckets must represent a much larger set of possible keys.

</details>

<details>
<summary><strong>HM-FUND-006. What does it mean for a hash function to be well-distributed?</strong></summary>

#### Short answer

A well-distributed hash function spreads typical keys evenly across the available hash space so buckets stay small.

#### Interview answer

For `HashMap`, a good `hashCode()` should use the fields that define equality and should produce varied results for common real-world values. It does not need to be random, but similar objects should not all collapse into a few hash codes.

The practical measure is bucket distribution: lookups stay close to constant time when entries are spread across the table.

#### Deep dive

Bad examples include returning a constant, using only a low-cardinality field such as `status`, or ignoring fields that actually distinguish keys. Good examples combine stable, equality-relevant fields such as tenant ID plus business ID.

Java `HashMap` applies a small spreading step to improve use of high hash bits, but it cannot fix a fundamentally poor `hashCode()`.

#### Production angle

Poor distribution can turn a normally cheap cache or aggregation map into a CPU-heavy hotspot. The issue may only appear at production scale when many keys share the same prefix, type or status.

#### Traps / caveats

- A hash function should be deterministic while the key is in the map.
- Do not include mutable or external state just to improve distribution.
- Cryptographic hashing is usually unnecessary and too expensive for normal map keys.

#### Optional Anki

Q: What is the practical goal of a good `hashCode()`?
A: Spread common unequal keys across buckets while staying consistent with `equals()`.

</details>

<details>
<summary><strong>HM-FUND-007. How does bad hash distribution affect `HashMap` performance?</strong></summary>

#### Short answer

Bad distribution puts too many entries into the same buckets, increasing collision checks and making operations slower.

#### Interview answer

`HashMap` is fast when buckets are small. If many keys produce the same or poorly spread hashes, `get()` and `put()` must compare more candidates with `equals()`. In extreme cases, operations can degrade from expected constant time toward linear time for a bucket, although modern Java can treeify heavily collided buckets.

#### Deep dive

Tree bins reduce worst-case lookup inside a heavily populated bucket, but they do not make poor hashing free. The map still has extra pointer chasing, comparisons, memory overhead and more expensive insertion/removal behavior.

Bad distribution is often accidental: using only one field, using mutable fields, or using objects whose `hashCode()` is identity-based when logical equality was expected.

#### Production angle

Symptoms include high CPU in `HashMap.get`, `HashMap.put`, key `equals()` methods, request deserialization maps or grouping collectors. Profilers and allocation tools usually reveal the hot map or key type.

#### Traps / caveats

- Average `O(1)` assumes reasonable distribution.
- `HashMap` cannot fully compensate for a bad key model.
- Expensive `equals()` makes collisions even more costly.

#### Optional Anki

Q: What happens when many keys land in the same `HashMap` bucket?
A: Lookup and update must inspect more candidates, increasing CPU and latency.

</details>

<details>
<summary><strong>HM-FUND-008. How do records generate `equals()` and `hashCode()`?</strong></summary>

#### Short answer

Records generate value-based `equals()` and `hashCode()` from their record components.

#### Interview answer

A Java record automatically gets `equals()`, `hashCode()` and `toString()` based on the components declared in the record header. Two record instances are equal when they have the same record type and their corresponding component values are equal.

This makes records convenient for immutable keys and DTO-like value objects.

#### Deep dive

Records are shallowly immutable: component fields are final, but referenced objects can still be mutable. For example, a record containing a `List` or array can still observe mutations inside that component. Array components are especially tricky because arrays use reference equality unless the record overrides the generated methods.

You can override generated methods when you need custom normalization, deep equality or different domain semantics, but then you own the contract.

#### Production angle

Records are often good cache keys, grouping keys and composite IDs when components are stable and already have correct equality. They are risky if they wrap mutable collections, arrays or request objects that can change after being used as keys.

#### Traps / caveats

- Record equality uses the declared components, not derived business meaning.
- Final component references do not make the referenced object immutable.
- Arrays inside records usually surprise people in equality and hashing.

#### Optional Anki

Q: What fields do generated record `equals()` and `hashCode()` use?
A: The record components declared in the record header.

</details>

<details>
<summary><strong>🧠 HM-FUND-009. How can Lombok-generated `equals()` and `hashCode()` break domain objects or collections?</strong></summary>

#### Short answer

Lombok can generate technically valid methods from the wrong fields, which breaks domain equality, mutable keys, JPA entities, lazy associations or collection behavior.

#### Interview answer

Lombok is useful, but generated equality is only as good as the fields and options selected. Problems appear when `@EqualsAndHashCode` includes mutable fields, database-generated IDs, bidirectional associations, lazy-loaded relations, or fields that are not part of the real identity.

The result can be duplicate set entries, missing map keys, recursive calls, unexpected database loading, or equality changing after persistence.

#### Deep dive

For JPA entities, including all fields is especially dangerous. A lazy collection can trigger SQL during equality. A bidirectional relationship can recurse. A generated ID may be null before persist and non-null afterward, changing the hash code while the entity is inside a `HashSet`.

Lombok options such as `onlyExplicitlyIncluded`, `callSuper` and exclusion annotations must match the domain model. They do not replace thinking about identity.

#### Production angle

These bugs often surface as duplicate domain objects in sets, cache misses, slow requests caused by lazy loads, or stack overflows from recursive associations. They are painful because the generated code is hidden during normal review.

#### Traps / caveats

- Do not use "all fields" equality by default for entities.
- Be explicit about superclass equality.
- Generated code can still violate domain identity even when it compiles.

#### Optional Anki

Q: Why is Lombok `@EqualsAndHashCode` risky on JPA entities?
A: It may include mutable IDs, lazy associations or bidirectional relationships that break equality, hashing or performance.

</details>
