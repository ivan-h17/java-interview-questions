# 04.02. equals() and hashCode() contract

---

<a id="hm-contract-001"></a>

<details>
<summary><strong>HM-CONTRACT-001. What is the `equals()` and `hashCode()` contract?</strong></summary>

#### Short answer

`equals()` must be reflexive, symmetric, transitive, consistent and return false for null. If two objects are equal, they must have the same `hashCode()`.

#### Interview answer

The contract has two parts. First, `equals()` must behave like a stable equivalence relation: an object equals itself, equality is symmetric and transitive, repeated comparisons give the same result while relevant state does not change, and no object equals null.

Second, `hashCode()` must be consistent with equality: equal objects must return the same hash code. Unequal objects may still return the same hash code.

#### Deep dive

Hash-based collections rely on both rules. If equality is unstable or hashes differ for equal objects, a `HashMap` can put a key in one bucket and later search for it in another, or fail to match an equivalent key.

The contract does not require a globally unique or permanently stable hash code. It only needs to be stable while equality-relevant state is stable, especially while an object is used as a key.

#### Production angle

Contract bugs break deduplication, caching, grouping, entity collections and security checks. They are also hard to debug because the data may look correct when printed.

#### Traps / caveats

- Overriding `equals()` without `hashCode()` is usually broken.
- Equal objects must have equal hashes; equal hashes do not imply equality.
- Mutable equality fields are dangerous in hash-based collections.

#### Optional Anki

Q: What must be true if `a.equals(b)` is true?
A: `a.hashCode()` must equal `b.hashCode()`.

</details>

<a id="hm-contract-002"></a>

<details>
<summary><strong>HM-CONTRACT-002. If two objects are equal by `equals()`, what must be true about `hashCode()`?</strong></summary>

#### Short answer

They must return the same `hashCode()`.

#### Interview answer

The `hashCode()` contract says equal objects must have equal hash codes. This is required so hash-based collections can find equivalent objects in the same bucket. If two equal keys return different hashes, a `HashMap` may store one key in one bucket and look for the other key in a different bucket.

#### Deep dive

This rule is one-way. It is legal and expected for unequal objects to share a hash code because collisions are unavoidable. `equals()` remains the final comparison.

The hash code also should not change while the object is being used as a map key or set element.

#### Production angle

Violating this rule usually appears as cache misses, duplicate keys, failed removals from `HashSet`, or broken `Stream.distinct()` behavior.

#### Traps / caveats

- Same equality state must feed both `equals()` and `hashCode()`.
- Do not include extra fields in `hashCode()` that `equals()` ignores.
- Do not use random or time-dependent values in `hashCode()`.

#### Optional Anki

Q: Can equal objects have different hash codes?
A: No, that violates the Java contract.

</details>

<a id="hm-contract-003"></a>

<details>
<summary><strong>HM-CONTRACT-003. If two objects have the same `hashCode()`, must they be equal by `equals()`?</strong></summary>

#### Short answer

No. Same hash code only means they may be in the same hash bucket; `equals()` decides actual equality.

#### Interview answer

Hash codes are not unique identifiers. Many unequal objects can have the same hash code. A hash-based collection treats a matching hash as a reason to check candidates, not as proof of equality.

This is why collision handling exists.

#### Deep dive

The `hashCode()` method returns a 32-bit `int`, while object state can be much larger. Even a perfect hash function for one domain may collide in another. Therefore Java collections must always handle collisions correctly.

#### Production angle

Using hash codes as IDs can corrupt data or merge unrelated requests. For example, a cache key should not be only `payload.hashCode()` unless collisions are acceptable and handled.

#### Traps / caveats

- Hash codes are not database keys.
- Hash codes are not cryptographic digests.
- `HashMap` compares keys with `equals()` after narrowing by hash.

#### Optional Anki

Q: Does equal `hashCode()` prove object equality?
A: No; it only creates a possible match.

</details>

<a id="hm-contract-004"></a>

<details>
<summary><strong>HM-CONTRACT-004. What happens if only one of `equals()` or `hashCode()` is overridden?</strong></summary>

#### Short answer

Overriding only one usually breaks hash-based collections because equality and hashing become inconsistent.

#### Interview answer

If you override `equals()` but keep identity-based `hashCode()`, two logically equal objects may produce different hashes and land in different buckets. `HashMap` and `HashSet` can then fail to find or deduplicate them.

If you override `hashCode()` but not `equals()`, objects may group by hash but still compare by identity, so logical duplicates remain distinct.

#### Deep dive

There are rare identity-based designs where overriding neither method is correct. But once a class defines logical equality, both methods should be implemented from the same stable fields.

IDE-generated methods, records and libraries can help, but the field choice still needs review.

#### Production angle

This bug is common in DTOs, cache keys and test fixtures. Unit tests may pass when using the same instance and fail in production when equivalent data arrives as a new instance.

#### Traps / caveats

- Always review `equals()` and `hashCode()` together.
- Same fields, same null handling, same domain identity.
- Tests should use different instances with equal values.

#### Optional Anki

Q: If a class overrides `equals()`, what else should it usually override?
A: `hashCode()`.

</details>

<a id="hm-contract-005"></a>

<details>
<summary><strong>HM-CONTRACT-005. What properties must `equals()` satisfy: reflexive, symmetric, transitive, consistent and non-null?</strong></summary>

#### Short answer

`equals()` must return true for self, behave the same in both directions, preserve equality chains, stay stable while relevant state is unchanged, and return false for null.

#### Interview answer

The five rules are:

- Reflexive: `x.equals(x)` is true.
- Symmetric: if `x.equals(y)` is true, `y.equals(x)` is true.
- Transitive: if `x.equals(y)` and `y.equals(z)`, then `x.equals(z)`.
- Consistent: repeated calls return the same result while compared state does not change.
- Non-null: `x.equals(null)` is false.

#### Deep dive

These rules let collections and algorithms treat equality as a reliable partitioning of objects into equivalence groups. If equality is asymmetric or non-transitive, a set can behave differently depending on insertion order or lookup direction.

#### Production angle

Broken equality rules produce unpredictable deduplication and authorization decisions. They are especially risky in polymorphic models where base and subclass equality are mixed.

#### Traps / caveats

- `equals()` should normally start with identity and type checks.
- Do not throw for null.
- Avoid equality based on changing external state.

#### Optional Anki

Q: What should `x.equals(null)` return?
A: Always false.

</details>

<a id="hm-contract-006"></a>

<details>
<summary><strong>HM-CONTRACT-006. What are common symmetry and transitivity violations in `equals()`?</strong></summary>

#### Short answer

They often come from inheritance, loose `instanceof` checks, subclasses adding fields, or equality rules that depend on different types in different ways.

#### Interview answer

A common symmetry bug is a base class that says it equals a subclass because shared fields match, while the subclass says it does not equal the base class because extra fields are missing. A transitivity bug appears when two objects both equal a middle object but not each other.

These bugs are usually caused by trying to make value equality work across an inheritance hierarchy.

#### Deep dive

Example: `Point(x, y)` and `ColorPoint(x, y, color)`. If `Point.equals()` uses `instanceof Point`, then a `Point` may equal a `ColorPoint`. But if `ColorPoint.equals()` includes color, symmetry or transitivity can break.

Composition often avoids this problem better than inheritance for value objects.

#### Production angle

Polymorphic equality bugs can break maps keyed by base type, sets of domain objects, cache keys and security rules where subclass-specific state matters.

#### Traps / caveats

- Adding fields in subclasses is hard to reconcile with base-class equality.
- `instanceof` can be too permissive for value classes.
- `getClass()` can be too strict for ORM proxies.

#### Optional Anki

Q: What is a classic source of broken `equals()` symmetry?
A: A superclass and subclass using different equality rules.

</details>

<a id="hm-contract-007"></a>

<details>
<summary><strong>HM-CONTRACT-007. Why can inheritance make `equals()` difficult to implement correctly?</strong></summary>

#### Short answer

Inheritance makes it hard to decide whether base and subclass instances can be equal, especially when subclasses add equality-relevant state.

#### Interview answer

For value classes, equality usually means "same type and same values." Inheritance weakens that because a subclass is also an instance of the base type but may carry additional fields. If the base class ignores subclass fields, equality may be too broad. If the subclass includes them, symmetry or transitivity can break.

#### Deep dive

Using `getClass()` preserves strict type equality but rejects subclass/proxy equality. Using `instanceof` supports polymorphism but can break when subclasses add state. The `canEqual` pattern is one attempt to make polymorphic equality explicit, but it adds complexity.

For many domain value objects, making classes final or using records is simpler.

#### Production angle

Backend teams see this with DTO inheritance, entity inheritance and generated proxy classes. A small equality mistake can produce duplicate set elements or cache misses.

#### Traps / caveats

- Prefer composition or final value classes when possible.
- Be careful with JPA proxies before choosing `getClass()`.
- Never let subclasses silently change equality semantics.

#### Optional Anki

Q: Why is `equals()` harder with subclasses?
A: Subclasses may add state while still being instances of the parent type.

</details>

<a id="hm-contract-008"></a>

<details>
<summary><strong>🧠 HM-CONTRACT-008. What is the `canEqual` pattern?</strong></summary>

#### Short answer

`canEqual` is a pattern where an object explicitly says whether it can be equal to another object's type, helping preserve equality rules in inheritance hierarchies.

#### Interview answer

The pattern adds a method such as `canEqual(Object other)`. In `equals()`, both objects participate: the current object checks normal fields, and the other object must confirm it can be equal to this type. This helps avoid a superclass claiming equality with a subclass that does not accept the superclass as equal.

It is associated with languages and libraries that support generated equality across inheritance, including Lombok in some configurations.

#### Deep dive

`canEqual` can reduce symmetry issues, but it also makes equality more complex and easier to misunderstand. It does not automatically solve domain modeling. If subclass-specific state changes the identity, the team still must define the desired semantics.

#### Production angle

In normal Java backend code, a simpler design is often better: final value classes, records, or explicit identity fields. Use `canEqual` only when polymorphic equality is intentional and tested.

#### Traps / caveats

- `canEqual` is not required for most classes.
- It can hide a design smell: value objects with inheritance.
- Generated implementations still need tests with superclass and subclass instances.

#### Optional Anki

Q: What problem does `canEqual` try to solve?
A: Preserving equality symmetry when inheritance and generated equality interact.

</details>

<a id="hm-contract-009"></a>

<details>
<summary><strong>HM-CONTRACT-009. Should `equals()` use `getClass()` or `instanceof`?</strong></summary>

#### Short answer

It depends on the equality model. `getClass()` enforces exact type equality; `instanceof` allows subtype equality. Each has trade-offs.

#### Interview answer

For final value classes and records, exact type equality is usually natural. `getClass()` prevents a subclass with extra state from being equal to a base instance.

`instanceof` is useful when equality is intentionally defined by a common interface or base type. But it can cause symmetry and transitivity problems if subclasses add fields.

#### Deep dive

JPA entities complicate the decision because runtime proxies may be subclasses. A strict `getClass()` check may reject a proxy representing the same row. Some teams use Hibernate-aware class checks or business keys, while others avoid putting entities in hash-based collections.

#### Production angle

This choice affects cache keys, sets and entity collections. The right answer should mention the domain model and framework behavior, not a universal rule.

#### Traps / caveats

- `getClass()` can be unfriendly to proxies.
- `instanceof` can be unsafe with subclass state.
- For records, generated equality is exact record type equality.

#### Optional Anki

Q: What is the trade-off between `getClass()` and `instanceof` in `equals()`?
A: Exact type safety versus polymorphic equality.

</details>

<a id="hm-contract-010"></a>

<details>
<summary><strong>HM-CONTRACT-010. How should `equals()` and `hashCode()` handle nullable fields and arrays?</strong></summary>

#### Short answer

Use null-safe comparisons for nullable fields and use array-specific methods when array contents should matter.

#### Interview answer

For nullable object fields, `Objects.equals(a, b)` is the standard null-safe comparison, and `Objects.hashCode(field)` is null-safe for hashing. For arrays, plain `equals()` compares array references, not contents. If content equality is intended, use `Arrays.equals()` and `Arrays.hashCode()`, or deep variants for nested arrays.

#### Deep dive

A common bug is generating equality for a class with `byte[]`, `String[]` or `Object[]` fields and accidentally comparing references. Two different arrays with the same contents will not be equal unless array content methods are used.

For mutable arrays, content-based equality is still risky if the object is used as a map key.

#### Production angle

This matters for keys containing binary IDs, checksums, request payload fragments or composite values. Array reference equality can silently break cache hits and deduplication.

#### Traps / caveats

- `array.equals(otherArray)` is reference equality.
- `Objects.equals(array1, array2)` is also reference equality for arrays.
- Mutable arrays should usually be defensively copied in key objects.

#### Optional Anki

Q: Which method compares array contents?
A: `Arrays.equals()` or `Arrays.deepEquals()` depending on the array shape.

</details>

<details>
<summary><strong>HM-CONTRACT-011. Why is `BigDecimal` tricky in equality and hash-based collections?</strong></summary>

#### Short answer

`BigDecimal.equals()` considers both numeric value and scale, so `1.0` and `1.00` compare equal by `compareTo()` but not by `equals()`.

#### Interview answer

`BigDecimal` has two equality notions. `compareTo()` is numeric comparison and treats `1.0` and `1.00` as equal. `equals()` is stricter and includes scale, so those two objects are not equal and can have different hash codes.

Since `HashMap` and `HashSet` use `equals()` and `hashCode()`, scale differences matter.

#### Deep dive

This also creates surprises between `HashSet` and sorted structures such as `TreeSet`. A `TreeSet` using natural ordering may treat `1.0` and `1.00` as duplicates because `compareTo()` returns zero, while a `HashSet` treats them as distinct.

#### Production angle

Money and pricing code should normalize values before using them as keys or define a domain value type with clear scale rules. Otherwise cache lookups, grouping and uniqueness checks can disagree.

#### Traps / caveats

- `equals()` and `compareTo()` are not consistent for `BigDecimal`.
- Normalization with `stripTrailingZeros()` may change scale representation.
- Always define money scale and rounding rules explicitly.

#### Optional Anki

Q: Are `new BigDecimal("1.0")` and `new BigDecimal("1.00")` equal?
A: `compareTo()` says yes; `equals()` says no.

</details>

<a id="hm-contract-012"></a>

<details>
<summary><strong>HM-CONTRACT-012. What fields should be included in `equals()` and `hashCode()`?</strong></summary>

#### Short answer

Include the stable fields that define the object's logical identity, and use the same fields in both methods.

#### Interview answer

The selected fields should answer: when are two instances considered the same value or same domain object? For a value object, that is usually all significant components. For a domain entity, it may be a stable business key or carefully handled identifier. For technical keys, it should be the exact fields needed for lookup.

The key rule is consistency: fields used by `equals()` and `hashCode()` must match.

#### Deep dive

Avoid including derived, cached, mutable, transient or external-state fields unless they are truly part of identity. Including too many fields makes equality unstable and expensive. Including too few fields can merge distinct values.

#### Production angle

Wrong field choice causes real bugs: tenant leakage when tenant ID is omitted from a cache key, duplicate entries when a unique field is ignored, or lookup failures when a mutable status field is included.

#### Traps / caveats

- Do not include fields in `hashCode()` that `equals()` ignores.
- Do not include mutable fields for map keys.
- Domain identity and database identity are not always the same.

#### Optional Anki

Q: What fields should `equals()` and `hashCode()` share?
A: The same stable fields that define logical identity.

</details>

<a id="hm-contract-013"></a>

<details>
<summary><strong>HM-CONTRACT-013. Why are mutable fields dangerous in `equals()` and `hashCode()`?</strong></summary>

#### Short answer

If a field used in equality or hashing changes while the object is in a hash-based collection, the collection may no longer find or remove it correctly.

#### Interview answer

`HashMap` chooses a bucket based on the key's hash at insertion time. If the key's hash changes later, lookup computes a different path. The entry still exists physically, but normal `get`, `containsKey` or `remove` may fail.

This is why map keys should be immutable or at least have immutable equality-relevant fields.

#### Deep dive

Even if the hash stays the same, changing equality fields can corrupt logical behavior. A set may contain duplicates according to the new state, or a key may start comparing equal to another existing key.

The collection does not re-index itself when key state changes.

#### Production angle

Mutable key bugs appear in caches keyed by request objects, entities whose IDs are assigned later, and composite keys that expose setters. They cause hard-to-reproduce misses and memory growth.

#### Traps / caveats

- `final` reference fields are not enough if the referenced object is mutable.
- Mutating values is fine; mutating keys is the problem.
- Removing before mutation and reinserting after mutation can be safe if done carefully.

#### Optional Anki

Q: What happens if a key's hash changes after insertion?
A: The map may not find or remove the entry using that key anymore.

</details>

<a id="hm-contract-014"></a>

<details>
<summary><strong>🧠 HM-CONTRACT-014. How can `Objects.equals()` and `Objects.hash()` help, and what are the performance trade-offs?</strong></summary>

#### Short answer

`Objects.equals()` gives null-safe equality, and `Objects.hash()` is convenient for combining fields, but `Objects.hash()` allocates a varargs array and may be too costly in hot paths.

#### Interview answer

`Objects.equals(a, b)` avoids manual null checks. `Objects.hash(field1, field2)` is readable and consistent for simple classes. For many domain objects this is perfectly fine.

The trade-off is performance. `Objects.hash()` uses varargs, which creates an array. In heavily used keys or hot loops, a manual `31 * result + fieldHash` implementation can reduce allocation and CPU.

#### Deep dive

`Objects.hashCode(field)` is different from `Objects.hash(field)`: the first hashes one nullable field without varargs, while the second creates a combined hash from varargs.

Modern JIT optimizations may remove some overhead in simple cases, but relying on that for hot key types should be measured.

#### Production angle

Use the readable standard helpers by default. For cache keys, aggregation keys or millions of map operations per request, benchmark and consider a manual hash implementation or a record with stable components.

#### Traps / caveats

- `Objects.equals()` does not perform array content comparison.
- `Objects.hash()` is not a cryptographic hash.
- Do not optimize hash code style without profiling.

#### Optional Anki

Q: Why can `Objects.hash()` be slower than manual hashing?
A: It uses varargs, which can allocate an array.

</details>

<a id="hm-contract-015"></a>

<details>
<summary><strong>HM-CONTRACT-015. How would you test an `equals()` and `hashCode()` implementation?</strong></summary>

#### Short answer

Test the equality contract, matching hash codes for equal objects, negative cases, null handling, mutation risks and collection behavior.

#### Interview answer

I would create separate instances with the same logical identity and verify they are equal and have the same hash code. Then I would vary each identity field and verify inequality. I would test null fields, subclass or proxy cases if relevant, and put the objects into `HashSet` or `HashMap` to verify lookup, deduplication and removal.

#### Deep dive

Good tests cover reflexivity, symmetry, transitivity and consistency. Libraries such as EqualsVerifier can automate many checks and catch subtle mistakes such as non-final fields, inheritance issues or missing hash fields.

For entities, tests should include lifecycle states if IDs are generated.

#### Production angle

Equality tests are cheap and prevent expensive bugs in caches, collections and persistence layers. They are especially valuable for key classes and domain value objects.

#### Traps / caveats

- Do not test only the same instance.
- Include negative cases for every identity field.
- Test with real collection operations, not only direct method calls.

#### Optional Anki

Q: What is a minimal collection test for equality?
A: Put one equal instance into a `HashSet` and verify another equal instance is found.

</details>
