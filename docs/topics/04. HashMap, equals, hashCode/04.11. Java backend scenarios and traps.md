<a id="hm-scen-001"></a>

<details>
<summary><strong>HM-SCEN-001. How would you choose between `ArrayList` and `HashMap` for storing key-value pairs?</strong></summary>

#### Short answer

Use `HashMap` for frequent lookup by unique key; use `ArrayList` of pairs when order, duplicates or tiny size matter more.

#### Interview answer

If the main operation is "find value by key," `HashMap` is the right default. If the data is very small, ordered, allows duplicate keys, or represents a sequence of events/headers, a list of pairs can be more accurate.

The choice should reflect the domain and access pattern.

#### Deep dive

`HashMap` overwrites values for equal keys. A list can keep repeated keys and insertion sequence. But repeated scans of a list for lookup can become slow quickly.

#### Production angle

Using a list for lookup-heavy code can create quadratic behavior. Using a map for duplicate-sensitive data can silently drop information.

#### Traps / caveats

- A map enforces one value per equal key.
- A list preserves duplicates and order.
- For tiny fixed lists, simplicity can beat theoretical complexity.

#### Optional Anki

Q: What is the deciding question between list pairs and map?
A: Is the primary access pattern lookup by unique key?

</details>

<details>
<summary><strong>HM-SCEN-002. How would you group objects by a field efficiently?</strong></summary>

#### Short answer

Use a `Map<Key, List<Value>>`, often with `computeIfAbsent()` or `Collectors.groupingBy()`.

#### Interview answer

For imperative code:

```java
Map<K, List<T>> grouped = new HashMap<>();
for (T item : items) {
    grouped.computeIfAbsent(keyOf(item), k -> new ArrayList<>()).add(item);
}
```

For streams, `Collectors.groupingBy(classifier)` is convenient. Choose `LinkedHashMap` or `TreeMap` if group order matters.

#### Deep dive

Consider key normalization, null keys, expected group count and list sizing. For concurrent grouping, use concurrent collectors or `ConcurrentHashMap` carefully.

#### Production angle

Grouping large result sets can consume a lot of memory. For huge data, push grouping to SQL or process in chunks.

#### Traps / caveats

- The common `groupingBy()` overload uses `HashMap` in the current JDK implementation, but the API does not guarantee a specific returned map type.
- `Collectors.groupingBy()` rejects null classifier results.
- Do not group unbounded streams fully in memory.

#### Optional Anki

Q: What map shape is used for grouping by key?
A: `Map<K, List<T>>`.

</details>

<a id="hm-scen-003"></a>

<details>
<summary><strong>HM-SCEN-003. How would you count occurrences in a collection?</strong></summary>

#### Short answer

Use `Map<T, Integer/Long>` with `merge()`, or `ConcurrentHashMap<T, LongAdder>` for concurrent high-contention counting.

#### Interview answer

For single-threaded counting:

```java
Map<T, Integer> counts = new HashMap<>();
for (T item : items) {
    counts.merge(item, 1, Integer::sum);
}
```

For concurrent counters, use `ConcurrentHashMap<T, LongAdder>` and increment the adder from `computeIfAbsent()`.

#### Deep dive

Streams can use `groupingBy(classifier, counting())`, but imperative code is often clearer and avoids some allocation. For primitive-heavy workloads, specialized primitive maps may reduce boxing.

#### Production angle

Counting unbounded cardinality can become a memory leak. Add limits or aggregate elsewhere when keys come from untrusted or high-cardinality input.

#### Traps / caveats

- `Integer` counters can overflow for large counts.
- `merge()` with boxed numbers allocates replacement values.
- Concurrent counting needs atomic updates.

#### Optional Anki

Q: Which method is concise for incrementing a map counter?
A: `merge(key, 1, Integer::sum)`.

</details>

<details>
<summary><strong>HM-SCEN-004. How do `computeIfAbsent()`, `merge()` and `putIfAbsent()` differ, especially around nulls?</strong></summary>

#### Short answer

`putIfAbsent` inserts a ready value if missing or mapped to null; `computeIfAbsent` lazily computes for missing/null values; `merge` inserts or combines and can remove on null remap result.

#### Interview answer

`putIfAbsent(k, v)` uses an already-created value. In `HashMap`, it puts when the key is absent or currently mapped to null. `computeIfAbsent(k, f)` calls the function only when there is no non-null value, and stores the result if it is non-null. `merge(k, v, f)` stores `v` if absent or null, otherwise combines old and new values; if the remapping function returns null, the mapping is removed.

#### Deep dive

For `ConcurrentHashMap`, null keys and values are not allowed, so null behavior is simpler but mapping functions still must be short and safe.

#### Production angle

Choose based on intent: lazy initialization, counter update, or insert-if-missing. Misunderstanding null behavior causes missing cache entries or accidental removals.

#### Traps / caveats

- `computeIfAbsent()` does not store null results.
- `merge()` can remove a mapping when remapper returns null.
- `putIfAbsent()` evaluates the value before the call.

#### Optional Anki

Q: Which method avoids constructing the value unless needed?
A: `computeIfAbsent()`.

</details>

<a id="hm-scen-005"></a>

<details>
<summary><strong>HM-SCEN-005. How would you build a cache key for a Spring service method?</strong></summary>

#### Short answer

Use a small immutable key containing all parameters and context that affect the result.

#### Interview answer

I would avoid using the raw request or entity object. Instead, create a record such as:

```java
record UserPermissionsKey(String tenantId, long userId, String locale, int rulesVersion) {}
```

The key should include tenant/security context, normalized parameters, versioning inputs and any flags that change the result.

#### Deep dive

Spring cache keys often fail because a method parameter is mutable, equality is identity-based, or context is implicit. If user permissions, locale or feature flags affect the result, they belong in the key or the cache should not be shared across those dimensions.

#### Production angle

A missing key dimension can cause cross-tenant data leaks or stale authorization decisions. A noisy key with irrelevant fields causes low hit rate.

#### Traps / caveats

- Do not key only by user ID in multi-tenant systems.
- Normalize strings and numeric scales.
- Include data/schema/rules versions when needed for invalidation.

#### Optional Anki

Q: What must a cache key include?
A: Every input and context value that can change the cached result.

</details>

<a id="hm-scen-006"></a>

<details>
<summary><strong>HM-SCEN-006. What can go wrong with map keys based on request objects?</strong></summary>

#### Short answer

Request objects are often mutable, too large, identity-based, context-dependent or contain irrelevant fields.

#### Interview answer

A request object may not override `equals()` and `hashCode()`, so lookup becomes identity-based. It may include mutable collections, timestamps, headers, security context or body streams. It may also contain fields that do not affect the result, reducing cache hits.

Use a normalized key object built from the relevant request data.

#### Deep dive

Request objects can also retain large graphs: body buffers, authenticated principals, servlet objects or tracing metadata. Using them as keys can create memory leaks in long-lived maps.

#### Production angle

This is a common cache bug. It causes low hit rate, stale or leaked data, and high memory usage.

#### Traps / caveats

- Object identity is rarely the desired request key.
- Mutable request fields can corrupt map lookup.
- Large keys retain large object graphs.

#### Optional Anki

Q: What should replace a request object as cache key?
A: A small immutable key with normalized relevant fields.

</details>

<details>
<summary><strong>HM-SCEN-007. How can `equals()` and `hashCode()` bugs break `HashSet`, `HashMap` or `Stream.distinct()`?</strong></summary>

#### Short answer

They can cause duplicates, missed lookups, failed removals or incorrect deduplication.

#### Interview answer

`HashSet` and `Stream.distinct()` use equality semantics to decide uniqueness. `HashMap` uses them to find keys. If equal objects have different hash codes, duplicates can appear. If unequal objects compare equal, distinct data can be collapsed. If equality changes after insertion, lookup and removal can fail.

#### Deep dive

`Stream.distinct()` is stateful and uses equality to remember seen elements. It has the same key-quality issues as hash-based collections.

#### Production angle

These bugs affect import deduplication, idempotency, fraud checks, user permissions and batch processing.

#### Traps / caveats

- Testing with the same instance hides equality bugs.
- Mutability can break collections after insertion.
- Arrays and `BigDecimal` often surprise people.

#### Optional Anki

Q: What does `Stream.distinct()` rely on?
A: `equals()` and `hashCode()`.

</details>

<a id="hm-scen-008"></a>

<details>
<summary><strong>HM-SCEN-008. How can `equals()` and `hashCode()` bugs break Hibernate collections?</strong></summary>

#### Short answer

They can make Hibernate `Set` collections lose, duplicate or fail to remove entities because collection membership depends on stable equality.

#### Interview answer

Hibernate often uses Java collections to represent associations. If an entity's hash changes after ID assignment, a `Set` may no longer find it. If equality includes lazy associations, it can trigger SQL or fail. If equality includes bidirectional relationships, it can recurse.

Entities need carefully designed identity semantics.

#### Deep dive

Generated IDs, proxies and lifecycle states make entity equality difficult. A transient entity, managed entity and proxy for the same row can behave differently if equality is naive.

#### Production angle

Symptoms include duplicate child rows, orphan removal not working, unexpected deletes/inserts and slow flushes caused by lazy equality.

#### Traps / caveats

- Avoid Lombok `@Data` equality on entities.
- Do not include mutable associations.
- Test entity equality across persistence lifecycle states.

#### Optional Anki

Q: Why can generated entity IDs break a `HashSet`?
A: The hash code may change after the ID is assigned.

</details>

<a id="hm-scen-009"></a>

<details>
<summary><strong>HM-SCEN-009. How can `equals()` and `hashCode()` bugs break deduplication logic?</strong></summary>

#### Short answer

Deduplication may keep duplicates or drop distinct records if equality does not match the deduplication rule.

#### Interview answer

Deduplication is only as correct as the key. If equality omits an important field, different records merge. If it includes irrelevant fields, duplicates remain. If hashing is inconsistent with equality, hash-based deduplication can fail even when equality appears correct.

Define the deduplication key explicitly.

#### Deep dive

For imports, the key might be external ID plus tenant. For events, it may be message ID plus source. For people, names alone are usually not enough. The domain rule should drive equality or a separate key extractor.

#### Production angle

Wrong deduplication causes duplicate charges, missed events, merged accounts or broken idempotency.

#### Traps / caveats

- Do not reuse object equality if the dedup rule is different.
- Include tenant/source/version when needed.
- Normalize fields before comparing.

#### Optional Anki

Q: What should drive deduplication equality?
A: The explicit domain deduplication key.

</details>

<a id="hm-scen-010"></a>

<details>
<summary><strong>HM-SCEN-010. How would you review a custom `equals()` and `hashCode()` implementation?</strong></summary>

#### Short answer

Check the contract, field choice, null/array handling, mutability, inheritance/proxies, performance and tests.

#### Interview answer

I would verify that equal objects have equal hash codes and that `equals()` is reflexive, symmetric, transitive, consistent and null-safe. Then I would check that both methods use the same stable identity fields, handle nullable fields and arrays correctly, and do not touch external state.

I would also review inheritance, JPA proxies and generated code assumptions.

#### Deep dive

Tests should use separate equal instances, field-by-field negative cases, collection behavior and lifecycle/proxy cases where relevant. A library such as EqualsVerifier can help.

#### Production angle

Equality bugs are small code mistakes with large blast radius in caches, sets, maps and persistence collections.

#### Traps / caveats

- Do not include mutable collections without a clear reason.
- `Objects.equals()` does not compare array contents.
- `getClass()` versus `instanceof` is a domain decision.

#### Optional Anki

Q: What is the first hash contract check?
A: Equal objects must have equal hash codes.

</details>

<a id="hm-scen-011"></a>

<details>
<summary><strong>HM-SCEN-011. How would you migrate from mutable keys to immutable keys?</strong></summary>

#### Short answer

Introduce a new immutable key type, populate maps from stable values, and stop mutating equality-relevant state.

#### Interview answer

I would first identify the real lookup identity. Then I would create a record or final key class with normalized immutable fields. Existing maps would be rebuilt using the new key type. Call sites would construct keys from stable data instead of using mutable objects directly.

Tests should prove lookup before and after mutations of the original objects.

#### Deep dive

Migration can be incremental: add adapter methods, deprecate old map APIs, convert at boundaries and add assertions or tests that catch mutable key usage. Avoid changing unrelated domain equality just to fix one map.

#### Production angle

This reduces cache misses, leaks and hard-to-debug lookup failures. Roll it out carefully if serialized keys or cache compatibility are involved.

#### Traps / caveats

- Do not mutate keys already inside a map during migration.
- Include all old key dimensions.
- Watch for distributed cache key compatibility.

#### Optional Anki

Q: What is the core migration step away from mutable keys?
A: Replace them with immutable keys built from stable identity fields.

</details>

<details>
<summary><strong>HM-SCEN-012. How would you test map behavior under concurrency?</strong></summary>

#### Short answer

Use stress tests with coordinated threads, atomic assertions and production-like access patterns; test invariants, not just absence of exceptions.

#### Interview answer

I would define the invariant first: no lost increments, single initialization, max sessions, consistent removal, and so on. Then I would run many threads with barriers or latches to start together, repeat operations many times, and assert final state. For counters, compare expected totals. For lazy initialization, assert only one value is installed.

Use `ConcurrentHashMap` atomic methods where appropriate.

#### Deep dive

Concurrency tests are probabilistic unless using specialized tools, so run them repeatedly and keep them focused. For low-level concurrency libraries, tools such as JCStress are more appropriate. For application code, integration stress tests often catch wrong check-then-act logic.

#### Production angle

Add metrics and logs for anomalies: duplicate initialization, negative counts, unexpected map growth and retry storms.

#### Traps / caveats

- Passing once does not prove correctness.
- Testing only with `HashMap` exceptions misses races.
- Thread-safe collections do not prove workflow invariants.

#### Optional Anki

Q: What should a concurrency map test assert?
A: The business invariant under concurrent access.

</details>

<details>
<summary><strong>HM-SCEN-013. What are the most common `HashMap` interview traps?</strong></summary>

#### Short answer

The common traps are equality/hash contract mistakes, mutable keys, null ambiguity, order assumptions, resizing cost, collision behavior and thread-safety.

#### Interview answer

A strong answer should mention: `==` versus `equals()`, overriding both `equals()` and `hashCode()`, equal objects requiring equal hashes, collisions being normal, mutable keys breaking lookup, `HashMap` not preserving order, `get()` null ambiguity, `ConcurrentHashMap` null restrictions, and `HashMap` not being thread-safe.

For senior interviews, also discuss capacity/load factor, tree bins, JPA entity pitfalls and cache key design.

#### Deep dive

Many traps come from relying on behavior seen in small examples: stable iteration order, no collisions, same key instance, no null values and single-threaded use. Production breaks those assumptions.

#### Production angle

The practical senior-level point is not memorizing internals; it is designing stable keys, choosing the right map implementation and recognizing when a raw map is not a cache or concurrency solution.

#### Traps / caveats

- Do not claim same hash means equal.
- Do not rely on `HashMap` order.
- Do not use mutable request/entity objects as keys.

#### Optional Anki

Q: What are the three biggest `HashMap` traps?
A: Broken equality/hash contract, mutable keys and assuming order/thread-safety.

</details>
