# 10.07. Performance, memory and backend boundaries

---

<a id="stream-perf-001"></a>

<details>
<summary><strong>STREAM-PERF-001. Are streams faster than loops?</strong></summary>

#### Short answer

Not inherently. Streams can be faster, similar or slower depending on the workload.

#### Interview answer

Streams improve expression and can benefit from laziness and pipeline fusion, but loops have simpler control flow and may have less overhead. Performance depends on data size, operation cost, boxing, stateful operations, allocation, JIT optimization and whether the stream is sequential or parallel.

#### Deep dive

For tiny transformations, loop overhead may be lower. For clear pipelines over moderate data, readability may matter more than small performance differences.

#### Production angle

Choose for clarity first, then profile hot paths with representative data.

#### Traps / caveats

- Do not claim streams are always faster.
- Do not claim loops are always faster.
- Avoid micro-optimizing code that is not hot.

#### Optional Anki

Q: Are streams automatically faster than loops?
A: No.

</details>

<a id="stream-perf-002"></a>

<details>
<summary><strong>STREAM-PERF-002. How do lazy evaluation and pipeline fusion help performance?</strong></summary>

#### Short answer

They avoid unnecessary work and avoid building intermediate collections between stages.

#### Interview answer

A lazy pipeline can process one element through several stages before moving to the next. `filter().map().findFirst()` may stop after the first match. The implementation can fuse stages so it does not create a list after each intermediate operation.

#### Deep dive

Fusion helps most for stateless operations such as `filter` and `map`. Stateful operations like `sorted` and `distinct` can require buffering.

#### Production angle

This makes streams good for simple transformations, but collecting too early with `collect(toList()).stream()` often defeats the benefit.

#### Traps / caveats

- Fusion is not a promise that all allocations disappear.
- Stateful operations can break one-element-at-a-time processing.
- Terminal operation choice determines how much work is needed.

#### Optional Anki

Q: What is pipeline fusion?
A: Combining stream stages during execution without materializing intermediate collections.

</details>

<a id="stream-perf-003"></a>

<details>
<summary><strong>STREAM-PERF-003. Which stream operations may need buffering?</strong></summary>

#### Short answer

Stateful operations such as `sorted`, `distinct`, `limit`, `skip`, `takeWhile` and `dropWhile` may require buffering or coordination.

#### Interview answer

`sorted` often needs all elements before producing ordered output. `distinct` tracks seen values. `limit` and `skip` are cheap in some sequential ordered cases, but can be expensive in ordered parallel streams.

#### Deep dive

Buffering depends on source, order and execution mode. Unordered streams can sometimes reduce coordination costs.

#### Production angle

Sorting or de-duplicating large in-memory data can produce high heap usage and GC pressure. Push work to the database when possible.

#### Traps / caveats

- `distinct` memory grows with unique elements.
- `sorted` on an infinite stream never completes.
- `limit` is not always cheap in parallel.

#### Optional Anki

Q: Name one buffering stream operation.
A: `sorted()`.

</details>

<a id="stream-perf-004"></a>

<details>
<summary><strong>STREAM-PERF-004. How do boxing and primitive streams affect performance?</strong></summary>

#### Short answer

Boxing creates wrapper objects; primitive streams avoid that for `int`, `long` and `double`.

#### Interview answer

`Stream<Integer>` processes `Integer` objects. `IntStream` processes primitive `int` values and provides numeric operations. Boxing and unboxing can add CPU, memory and null-unboxing risks.

#### Deep dive

Use `mapToInt`, `mapToLong` or `mapToDouble` for numeric extraction. Convert back with `boxed()` only when an object stream is needed.

#### Production angle

Boxing overhead matters in high-volume metrics, scoring, ID processing and analytics-like jobs.

#### Traps / caveats

- Unboxing null throws `NullPointerException`.
- Primitive streams do not cover all primitive types.
- Overflow remains possible.

#### Optional Anki

Q: Which stream avoids `Integer` boxing for ints?
A: `IntStream`.

</details>

<a id="stream-perf-005"></a>

<details>
<summary><strong>STREAM-PERF-005. How can lambda allocation and JIT optimization affect stream performance?</strong></summary>

#### Short answer

The JVM can optimize many lambdas and stream pipelines, but not all overhead disappears.

#### Interview answer

Non-capturing lambdas and method references can be cheap. Capturing lambdas may require objects or harder optimization. The JIT can inline and optimize simple pipelines after warmup, but complex lambdas, megamorphic calls or allocation-heavy mappers can still cost.

#### Deep dive

Performance depends heavily on the exact JVM, code shape and runtime profile. This is why naive conclusions from tiny examples are unreliable.

#### Production angle

If stream overhead appears in profiles, inspect allocation hot spots, boxing, lambda captures and expensive mappers before rewriting everything.

#### Traps / caveats

- Cold-start behavior can differ from warmed-up behavior.
- Capturing large objects can retain memory.
- Readability should not be sacrificed without evidence.

#### Optional Anki

Q: Why is stream performance JVM-dependent?
A: JIT inlining and optimization depend on runtime profiles and code shape.

</details>

<a id="stream-perf-006"></a>

<details>
<summary><strong>🧠 STREAM-PERF-006. How do you benchmark Stream performance correctly?</strong></summary>

#### Short answer

Use JMH for microbenchmarks and production-like load tests for service behavior.

#### Interview answer

Correct benchmarking needs warmup, enough iterations, realistic data, result consumption and isolation from dead-code elimination. JMH handles many microbenchmark pitfalls. For backend services, measure throughput, p95/p99 latency, CPU, allocation, GC and database impact under realistic concurrency.

#### Deep dive

Compare stream, loop and SQL alternatives only when they produce the same result and use the same input conditions.

#### Production angle

The right benchmark is often not "stream vs loop"; it is "in-memory processing vs pushing work to storage or batching."

#### Traps / caveats

- One `System.nanoTime()` run is not a benchmark.
- Printing inside benchmarks invalidates results.
- Parallel stream benchmarks must include system contention.

#### Optional Anki

Q: Standard Java microbenchmark tool?
A: JMH.

</details>

<a id="stream-perf-007"></a>

<details>
<summary><strong>STREAM-PERF-007. How can collect(), toList() or groupingBy() create memory pressure?</strong></summary>

#### Short answer

They materialize results and may retain all elements, groups and intermediate containers.

#### Interview answer

`toList()` stores every element in memory. `groupingBy()` stores a map plus per-group containers. `toMap()` stores keys and values. If the stream is huge, these terminal operations can dominate heap usage or cause `OutOfMemoryError`.

#### Deep dive

Memory pressure also comes from boxed values, DTO creation, nested collections and retained entity graphs.

#### Production angle

For large datasets, use pagination, database aggregation, streaming writers, bounded buffers or incremental processing.

#### Traps / caveats

- A lazy source does not help if the terminal operation materializes everything.
- Grouping by high-cardinality keys can explode memory.
- ORM entities may retain more graph than expected.

#### Optional Anki

Q: Why can `groupingBy()` use much memory?
A: It retains a map and accumulated values for every group.

</details>

<a id="stream-perf-008"></a>

<details>
<summary><strong>STREAM-PERF-008. How can you process large datasets without collecting everything into memory?</strong></summary>

#### Short answer

Process incrementally with pagination, batching, cursors, streaming writers or bounded chunks.

#### Interview answer

Avoid `toList()` on huge sources. Fetch pages from the database, process batches, write output incrementally, aggregate in SQL, or use a cursor/stream inside a controlled transaction. Keep memory bounded and release resources promptly.

#### Deep dive

Streams are pull-based, so they can help process one item at a time, but stateful operations and materializing terminals remove that benefit.

#### Production angle

Add limits, progress metrics, timeouts and failure recovery for long-running jobs.

#### Traps / caveats

- `sorted`, `distinct` and `groupingBy` may retain large state.
- Database cursors can hold connections for a long time.
- A single transaction over millions of rows can be dangerous.

#### Optional Anki

Q: What defeats memory-bounded streaming?
A: Materializing terminals like `toList()` or stateful operations over huge data.

</details>

<a id="stream-perf-009"></a>

<details>
<summary><strong>STREAM-PERF-009. When should filtering, sorting or aggregation be done in SQL instead of Java streams?</strong></summary>

#### Short answer

When the data is in the database and the operation can be expressed efficiently by the database.

#### Interview answer

Databases are built for filtering, joining, sorting, grouping and aggregation using indexes, statistics and query plans. Pulling rows into Java just to filter or sort them wastes network, memory and CPU and can produce stale or inconsistent results.

#### Deep dive

Use Java streams for business transformations after the right data has been selected. Use SQL for data reduction close to storage.

#### Production angle

In-memory filtering of endpoint data causes slow responses, large heaps and pagination bugs.

#### Traps / caveats

- Java-side pagination after fetching all rows is not real pagination.
- Database sort order should be explicit.
- Some business rules may still belong in Java after query narrowing.

#### Optional Anki

Q: Why push filtering to SQL?
A: To reduce data at the source using indexes and query planning.

</details>

<a id="stream-perf-010"></a>

<details>
<summary><strong>STREAM-PERF-010. Why is Stream API not a replacement for database query design?</strong></summary>

#### Short answer

Streams operate after data is fetched; query design controls what data is fetched and how efficiently.

#### Interview answer

A stream can transform rows already in memory. It cannot replace indexes, join strategy, selective predicates, pagination, isolation or query plans. If the query returns too much data, streams only move the cost into the application.

#### Deep dive

ORMs can make this worse by hiding lazy loads inside mapping lambdas. The pipeline looks compact while issuing many queries.

#### Production angle

Review stream-heavy repository/service code for missing `WHERE`, `ORDER BY`, `LIMIT`, joins, projections and indexes.

#### Traps / caveats

- `stream().filter()` is not equivalent to indexed database filtering.
- In-memory sorting can produce wrong pagination.
- Mapping entities is not free.

#### Optional Anki

Q: What does Stream API not replace?
A: Good SQL query design and database indexing.

</details>

<a id="stream-backend-001"></a>

<details>
<summary><strong>STREAM-BACKEND-001. How can Stream API accidentally trigger N+1 queries with JPA entities?</strong></summary>

#### Short answer

Mapping lambdas can access lazy associations once per entity, triggering extra queries.

#### Interview answer

Code like `orders.stream().map(o -> o.getCustomer().getName())` may look like simple mapping. If `customer` is lazy and not fetched, each access can execute another query. That turns one query plus N lazy loads into a production performance problem.

#### Deep dive

The stream is not the root cause; it hides repeated access compactly. The fix is proper fetch joins, entity graphs, projections, batch fetching or query redesign.

#### Production angle

Symptoms include many similar SQL statements, slow DTO mapping and database load spikes.

#### Traps / caveats

- `flatMap` over lazy collections can be worse.
- Parallel streams with JPA entities are usually unsafe.
- LazyInitializationException can occur if the session is closed.

#### Optional Anki

Q: What JPA problem can DTO mapping streams hide?
A: N+1 queries from lazy association access.

</details>

<a id="stream-backend-002"></a>

<details>
<summary><strong>STREAM-BACKEND-002. Why should remote calls inside map() or forEach() usually be avoided?</strong></summary>

#### Short answer

They hide I/O, failure handling and concurrency inside a data transformation pipeline.

#### Interview answer

`map(id -> client.fetch(id))` looks concise, but it performs remote calls. Sequentially it may be slow. With parallel streams it can overload downstream services and lacks clear timeouts, retries, rate limits and cancellation.

#### Deep dive

Remote fan-out should be explicit. Use batching, bulk APIs, bounded concurrency, `CompletableFuture`, virtual threads or reactive clients depending on architecture.

#### Production angle

Remote calls in streams often create latency spikes, retry storms and poor observability.

#### Traps / caveats

- Do not use `parallelStream()` as a bulkhead.
- Side effects may partially complete before failure.
- Thread-local tracing may not propagate.

#### Optional Anki

Q: Why is HTTP inside `map()` risky?
A: It hides remote I/O and lacks explicit concurrency/failure control.

</details>

<a id="stream-backend-003"></a>

<details>
<summary><strong>STREAM-BACKEND-003. How do you design readable stream pipelines in service-layer code?</strong></summary>

#### Short answer

Keep each stage simple, name complex logic, and keep side effects outside transformations.

#### Interview answer

A readable service-layer stream has a clear source, a few obvious transformations and a clear terminal operation. Predicates and mappers with business meaning should be extracted into named methods. Avoid nesting collectors and lambdas until the intent disappears.

#### Deep dive

Pipelines should read like a data transformation, not a compressed workflow language.

#### Production angle

Readable streams are easier to review for N+1 queries, null handling, duplicate keys and memory pressure.

#### Traps / caveats

- Long chains can hide important validation.
- Avoid method names like `process` or `handle` inside streams.
- Do not mix DTO mapping, persistence and remote calls in one chain.

#### Optional Anki

Q: What improves stream readability?
A: Small stages and named predicates/mappers.

</details>

<a id="stream-backend-004"></a>

<details>
<summary><strong>STREAM-BACKEND-004. When should a stream pipeline be split into named methods or replaced by a loop?</strong></summary>

#### Short answer

When the pipeline hides business rules, complex branching, indexing, side effects or error handling.

#### Interview answer

Split a pipeline when lambdas become multi-line, nested collectors become hard to parse, or reviewers cannot name each stage. Replace it with a loop when control flow, partial failure, retries, transaction steps or mutation are the core logic.

#### Deep dive

Named methods keep the fluent shape while improving testability. A loop is better when imperative state is honest and clearer.

#### Production angle

Maintainable code reduces incident time. During debugging, a clear loop can be more valuable than compact fluent code.

#### Traps / caveats

- Do not extract tiny obvious lambdas unnecessarily.
- Do not keep streams just for style consistency.
- Be careful that refactoring does not change laziness or ordering.

#### Optional Anki

Q: When should stream code become a loop?
A: When imperative control flow is the main logic.

</details>

<a id="stream-backend-005"></a>

<details>
<summary><strong>STREAM-BACKEND-005. How would you review a Stream-heavy pull request?</strong></summary>

#### Short answer

Check correctness, readability, data size, side effects, resource boundaries, nulls, ordering, collectors and database access.

#### Interview answer

I would identify the source and terminal operation first. Then I would check whether data should be filtered in SQL, whether mapping triggers lazy loads, whether collectors handle duplicates, whether nulls are possible, whether ordering is required, and whether any lambdas have side effects or remote calls.

#### Deep dive

For parallel streams, I would additionally check source splitting, shared state, collector correctness, common-pool impact and benchmarks.

#### Production angle

A review should ask what happens with empty input, huge input, duplicate keys, failed lambdas and slow downstream calls.

#### Traps / caveats

- Compact code is not necessarily simple.
- `toList()` can hide full materialization.
- `peek()` and `parallelStream()` deserve extra scrutiny.

#### Optional Anki

Q: First thing to identify in stream review?
A: The source and terminal operation.

</details>
