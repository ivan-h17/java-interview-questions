# 10.03. Operations, mapping, ordering and Optional

---

<a id="stream-ops-001"></a>

<details>
<summary><strong>STREAM-OPS-001. What is the difference between intermediate and terminal operations?</strong></summary>

#### Short answer

Intermediate operations return another stream and are usually lazy. Terminal operations consume the stream and produce a result or side effect.

#### Interview answer

`filter`, `map`, `flatMap`, `sorted` and `distinct` are intermediate operations. They build the pipeline. `toList`, `collect`, `reduce`, `count`, `findFirst` and `forEach` are terminal operations. They start execution and consume the stream.

#### Deep dive

Intermediate operations can be stateless or stateful. Terminal operations can be short-circuiting, such as `findFirst` or `anyMatch`, or full traversal, such as `collect`.

#### Production angle

Knowing where execution starts helps debug exceptions, resource use and surprising side effects in stream code.

#### Traps / caveats

- No terminal operation means no processing.
- After a terminal operation, the stream cannot be reused.
- `iterator()` and `spliterator()` are terminal escape hatches.

#### Optional Anki

Q: What kind of operation is `map()`?
A: Intermediate.

</details>

<a id="stream-ops-002"></a>

<details>
<summary><strong>STREAM-OPS-002. How do filter(), map() and flatMap() differ?</strong></summary>

#### Short answer

`filter` keeps or removes elements, `map` transforms one element to one value, and `flatMap` transforms one element to many values and flattens the result.

#### Interview answer

Use `filter` for selection, `map` for transformation, and `flatMap` for nested or optional data. For example, users to emails is `map(User::email)`. Orders to all order lines is `flatMap(order -> order.lines().stream())`.

#### Deep dive

`flatMap` expects each input to produce a stream. It then concatenates those inner streams logically into a single stream.

#### Production angle

Clear use of these three operations makes DTO mapping and validation pipelines readable. Misusing `map` to return collections often produces awkward `Stream<List<T>>` results.

#### Traps / caveats

- A mapper returning null creates null elements.
- `flatMap` can hide expensive nested lazy loads.
- Complex mappers should be named methods.

#### Optional Anki

Q: What does `flatMap()` do?
A: It maps each element to a stream and flattens the inner streams into one stream.

</details>

<a id="stream-ops-003"></a>

<details>
<summary><strong>STREAM-OPS-003. When should you use flatMap() instead of nested loops or nested streams?</strong></summary>

#### Short answer

Use `flatMap()` when the natural operation is one input element producing zero, one or many output elements.

#### Interview answer

`flatMap` is good for flattening `List<List<T>>`, order-to-lines, user-to-roles, optional values and parsed records that can produce multiple outputs. It keeps the pipeline linear when nested loops would only gather nested values.

#### Deep dive

Nested loops can still be clearer when the inner logic has branching, mutation, error handling or multiple side effects. `flatMap` should express data shape, not hide a workflow.

#### Production angle

In JPA code, `flatMap(entity -> entity.getChildren().stream())` can trigger N+1 queries if children are lazy-loaded one entity at a time.

#### Traps / caveats

- Do not use `flatMap` to hide remote calls.
- Be careful with null collections.
- Inner streams from resources must be closed if they own resources.

#### Optional Anki

Q: Common `flatMap()` use case?
A: Flattening nested collections, such as `List<List<T>>` to `Stream<T>`.

</details>

<a id="stream-ops-004"></a>

<details>
<summary><strong>STREAM-OPS-004. What is peek() for, and why is it dangerous for business logic?</strong></summary>

#### Short answer

`peek()` is mainly for debugging observation, not required business effects.

#### Interview answer

`peek` is an intermediate operation that lets you observe elements as they pass through the pipeline. It is useful for temporary debugging or tracing. It is dangerous for business logic because intermediate operations are lazy and may be skipped, short-circuited, optimized, or run in unexpected order.

#### Deep dive

In parallel streams, `peek` may run on multiple threads. If the terminal operation does not need all elements, not every element is peeked.

#### Production angle

Do not use `peek` for auditing, persistence, publishing events or validation that must always happen. Make those effects explicit.

#### Traps / caveats

- `peek()` without a terminal operation does nothing.
- `count()` and optimizations can make debugging output surprising.
- Side effects in `peek()` are hard to test reliably.

#### Optional Anki

Q: What is `peek()` mainly for?
A: Debugging or observing elements, not business logic.

</details>

<a id="stream-ops-005"></a>

<details>
<summary><strong>STREAM-OPS-005. What is the difference between forEach() and forEachOrdered()?</strong></summary>

#### Short answer

`forEach()` does not guarantee encounter order in parallel streams. `forEachOrdered()` preserves encounter order when one exists.

#### Interview answer

In sequential streams they often look the same. In parallel streams, `forEach` may process elements in any order for performance. `forEachOrdered` preserves encounter order, but that ordering constraint can reduce parallel performance.

#### Deep dive

`forEach` is a terminal operation intended for side effects. If you are building a result, prefer `collect` instead of mutating an external collection.

#### Production angle

Use `forEachOrdered` only when ordering is part of the contract, such as writing ordered output. Otherwise avoid relying on side-effect order.

#### Traps / caveats

- `HashSet` may not have meaningful encounter order.
- `forEachOrdered` can serialize parts of a parallel pipeline.
- External mutation inside either method can still be unsafe.

#### Optional Anki

Q: Which terminal operation preserves encounter order?
A: `forEachOrdered()`.

</details>

<a id="stream-ops-006"></a>

<details>
<summary><strong>STREAM-OPS-006. What is the difference between findFirst() and findAny()?</strong></summary>

#### Short answer

`findFirst()` returns the first element in encounter order. `findAny()` may return any matching element.

#### Interview answer

Use `findFirst` when the first element according to encounter order matters. Use `findAny` when any result is acceptable, especially in parallel pipelines where it can avoid ordering constraints.

Both return `Optional<T>`.

#### Deep dive

On unordered streams, `findFirst` behaves like finding some element because no meaningful first element exists. On ordered parallel streams, `findFirst` may be slower.

#### Production angle

For "does a matching item exist?" use `anyMatch`. For "give me one candidate" use `findAny`. For deterministic API behavior, use an ordered source or explicit sort with `findFirst`.

#### Traps / caveats

- `findAny` can return different elements across runs.
- `findFirst` may force ordering work in parallel.
- Empty streams return `Optional.empty()`.

#### Optional Anki

Q: Which is usually more parallel-friendly: `findFirst()` or `findAny()`?
A: `findAny()`.

</details>

<a id="stream-ops-007"></a>

<details>
<summary><strong>STREAM-OPS-007. What do anyMatch(), allMatch() and noneMatch() return for an empty stream?</strong></summary>

#### Short answer

For an empty stream, `anyMatch` returns false, `allMatch` returns true, and `noneMatch` returns true.

#### Interview answer

This follows logical quantification. "Any element matches" is false when there are no elements. "All elements match" is vacuously true. "No elements match" is also true.

#### Deep dive

All three are short-circuiting terminal operations. `anyMatch` stops on the first true predicate result, while `allMatch` and `noneMatch` stop when their condition is disproven.

#### Production angle

Empty-input behavior matters in authorization, validation and filtering. A wrong assumption can accidentally allow or reject a request.

#### Traps / caveats

- `allMatch` on empty input returning true can surprise reviewers.
- Side effects in predicates may not run for all elements.
- Parallel evaluation can run predicates out of order.

#### Optional Anki

Q: What does `allMatch()` return on an empty stream?
A: `true`.

</details>

<a id="stream-ops-008"></a>

<details>
<summary><strong>STREAM-OPS-008. How do min(), max() and sorted() differ?</strong></summary>

#### Short answer

`min` and `max` find one extremum. `sorted` orders the whole stream.

#### Interview answer

Use `min(comparator)` or `max(comparator)` when you only need the smallest or largest element. Use `sorted(comparator)` when you need all elements in order. `sorted().findFirst()` is usually more expensive than `min()` because sorting requires more work.

#### Deep dive

`min` and `max` are terminal operations returning `Optional<T>`. `sorted` is a stateful intermediate operation and may buffer all elements.

#### Production angle

Avoid sorting large in-memory datasets just to get one element. Push ordering and limiting to the database when the dataset is large.

#### Traps / caveats

- Natural sorting requires elements to be `Comparable`.
- Nulls need explicit comparator handling.
- Sorting can change memory behavior significantly.

#### Optional Anki

Q: Better for finding the smallest element: `sorted().findFirst()` or `min()`?
A: `min()`.

</details>

<a id="stream-ops-009"></a>

<details>
<summary><strong>STREAM-OPS-009. How does distinct() determine uniqueness?</strong></summary>

#### Short answer

For object streams, `distinct()` uses `equals()` and `hashCode()`.

#### Interview answer

`distinct` removes duplicate elements according to object equality. For ordered streams, it preserves the first occurrence of each distinct element. For unordered streams, no stable "first" occurrence is promised.

#### Deep dive

`distinct` is stateful because it tracks seen values. It can require significant memory for large streams.

#### Production angle

If uniqueness is based on business keys rather than full object equality, use an explicit map or grouping strategy. Do not rely on accidental entity equality.

#### Traps / caveats

- Broken `equals()` or `hashCode()` breaks distinctness.
- JPA entity equality can be tricky before IDs are assigned.
- Distinct over huge streams can become a memory problem.

#### Optional Anki

Q: What methods does object-stream `distinct()` rely on?
A: `equals()` and `hashCode()`.

</details>

<a id="stream-ops-010"></a>

<details>
<summary><strong>STREAM-OPS-010. How do limit(), skip(), takeWhile() and dropWhile() behave?</strong></summary>

#### Short answer

They reduce a stream by position or prefix, not by arbitrary matching like `filter()`.

#### Interview answer

`limit(n)` keeps at most the first `n` elements. `skip(n)` discards the first `n`. `takeWhile(predicate)` keeps elements from the start while the predicate is true. `dropWhile(predicate)` discards elements from the start while the predicate is true, then keeps the rest.

#### Deep dive

For ordered streams, prefix semantics are well-defined. For unordered streams, `takeWhile` and `dropWhile` are less intuitive because there is no meaningful prefix.

#### Production angle

These operations are useful for paging-like transformations, bounded generation and parsing ordered input, but database pagination should usually happen in the query.

#### Traps / caveats

- `takeWhile` is not the same as `filter`.
- `limit` on ordered parallel streams can be expensive.
- Negative `limit` or `skip` values are invalid.

#### Optional Anki

Q: How is `takeWhile()` different from `filter()`?
A: `takeWhile()` stops at the first false predicate in encounter order; `filter()` checks all elements.

</details>

<a id="stream-ops-011"></a>

<details>
<summary><strong>STREAM-OPS-011. What does unordered() change?</strong></summary>

#### Short answer

`unordered()` removes the requirement to preserve encounter order.

#### Interview answer

Calling `unordered()` tells the stream pipeline that order does not matter. This can enable faster execution for some parallel operations, especially `distinct`, `limit`, `skip` and matching operations.

It does not randomly shuffle elements; it removes an ordering constraint.

#### Deep dive

The source may still have order, but downstream operations are no longer required to respect it unless order is reintroduced, such as by `sorted()`.

#### Production angle

Use it only when the result contract is genuinely order-independent. It can improve throughput but weaken deterministic behavior.

#### Traps / caveats

- Do not use `unordered()` on response data where clients expect stable order.
- It may not improve sequential pipelines.
- It does not fix unsafe side effects.

#### Optional Anki

Q: Does `unordered()` shuffle the stream?
A: No. It removes the obligation to preserve encounter order.

</details>

<a id="stream-ops-012"></a>

<details>
<summary><strong>STREAM-OPS-012. What is the difference between Stream.toList(), Collectors.toList() and unmodifiable collectors?</strong></summary>

#### Short answer

`Stream.toList()` returns an unmodifiable list. `Collectors.toList()` does not guarantee mutability or implementation. Unmodifiable collectors explicitly reject mutation.

#### Interview answer

`stream.toList()` is concise and returns an unmodifiable `List`. `collect(Collectors.toList())` returns a list but its exact type and mutability are not specified by the contract. `Collectors.toUnmodifiableList()` explicitly collects into an unmodifiable list and rejects null elements.

#### Deep dive

`Stream.toList()` permits null elements, while unmodifiable collectors reject nulls. If you need a mutable `ArrayList`, use `collect(Collectors.toCollection(ArrayList::new))`.

#### Production angle

Mutability matters at API boundaries. Returning unmodifiable results prevents accidental caller changes, but it can break code that expects to append.

#### Traps / caveats

- Do not rely on `Collectors.toList()` returning `ArrayList`.
- Unmodifiable is shallow; elements can still be mutable.
- Java version matters for `Stream.toList()`.

#### Optional Anki

Q: Is `Stream.toList()` mutable?
A: No, it returns an unmodifiable list.

</details>

<a id="stream-ops-013"></a>

<details>
<summary><strong>STREAM-OPS-013. When should you prefer primitive stream operations such as mapToInt()?</strong></summary>

#### Short answer

Prefer primitive streams for numeric-heavy processing to avoid boxing and use numeric terminals.

#### Interview answer

Use `mapToInt`, `mapToLong` or `mapToDouble` when the pipeline extracts primitive numeric values and then sums, averages, summarizes or compares them. Primitive streams avoid wrapper objects and provide methods like `sum()` and `summaryStatistics()`.

#### Deep dive

You can move back to object streams with `boxed()` or `mapToObj()`. Keep conversions minimal in hot paths.

#### Production angle

For small DTO lists the difference may be irrelevant. For high-volume metrics, IDs or scoring pipelines, boxing can create measurable CPU and GC overhead.

#### Traps / caveats

- Primitive streams cannot represent null values.
- `average()` returns an optional primitive result.
- Overflow can still happen with `sum()`.

#### Optional Anki

Q: What method converts object stream values to primitive ints?
A: `mapToInt()`.

</details>

<a id="stream-ops-014"></a>

<details>
<summary><strong>STREAM-OPS-014. How should null values be handled in stream pipelines?</strong></summary>

#### Short answer

Avoid nulls when possible; otherwise filter or normalize them explicitly near the source.

#### Interview answer

Streams can technically contain null elements, but many operations and method references fail with `NullPointerException`. Common approaches are `filter(Objects::nonNull)`, `Stream.ofNullable(value)`, mapping to `Optional`, or validating inputs before streaming.

#### Deep dive

Null-returning mappers are a common smell because downstream stages must remember to handle nulls. Prefer explicit empty streams, optionals or domain defaults when they express intent.

#### Production angle

Null behavior should be part of API contracts. Silent filtering can hide data quality problems if null means corrupt input.

#### Traps / caveats

- `findFirst()` throws if the selected element is null.
- `Collectors.toUnmodifiableList()` rejects nulls.
- `Optional` references themselves should not be null.

#### Optional Anki

Q: Common way to remove nulls from a stream?
A: `filter(Objects::nonNull)`.

</details>

<a id="stream-ops-015"></a>

<details>
<summary><strong>STREAM-OPS-015. How do you flatten Stream<Optional<T>> safely?</strong></summary>

#### Short answer

Use `stream.flatMap(Optional::stream)`.

#### Interview answer

`Optional.stream()` turns a present value into a one-element stream and an empty optional into an empty stream. Therefore `Stream<Optional<T>>` can become `Stream<T>` with `flatMap(Optional::stream)`.

This avoids `filter(Optional::isPresent).map(Optional::get)`.

#### Deep dive

The same idea works for nullable values with `flatMap(value -> Stream.ofNullable(value))`, though avoiding null-producing mappers is usually cleaner.

#### Production angle

This is useful when mapping records to optional derived values, optional validation errors or optional relationships that should simply disappear from the result.

#### Traps / caveats

- Do not call `get()` without checking presence.
- Do not use null `Optional` references.
- Consider whether dropping absent values hides a business issue.

#### Optional Anki

Q: Preferred way to flatten `Stream<Optional<T>>`?
A: `flatMap(Optional::stream)`.

</details>

<a id="stream-ops-016"></a>

<details>
<summary><strong>STREAM-OPS-016. How do you convert a Stream to an array safely?</strong></summary>

#### Short answer

Use `toArray(Type[]::new)` when you need a typed array.

#### Interview answer

`stream.toArray()` returns `Object[]`. If the caller needs a typed array, use the generator overload, for example `stream.toArray(String[]::new)`. The generator lets the Stream API allocate an array of the correct runtime component type and size.

#### Deep dive

The no-argument form is fine only when `Object[]` is really acceptable. In most backend code, collecting to a `List` is more flexible than converting to an array. Arrays are useful at API boundaries, legacy APIs, varargs-oriented code or performance-sensitive places where an array is the expected representation.

#### Production angle

Avoid array conversion just because it looks compact. It materializes the whole stream, so it has the same memory concern as `toList()` for large sources.

#### Traps / caveats

- Do not cast `Object[]` from `toArray()` to `String[]`; it fails with `ClassCastException`.
- `toArray(String[]::new)` still consumes the stream.
- Prefer a collection unless an array is part of the contract.

#### Optional Anki

Q: How do you get a typed array from `Stream<String>`?
A: `stream.toArray(String[]::new)`.

</details>
