# 10.04. Collectors, maps, grouping and reduction

---

<a id="stream-col-001"></a>

<details>
<summary><strong>STREAM-COL-001. What does collect() do?</strong></summary>

#### Short answer

`collect()` is a terminal operation that accumulates stream elements into a result container or final value.

#### Interview answer

`collect` performs mutable reduction. It is commonly used to build lists, sets, maps, grouped results, joined strings or custom aggregate objects. It works with a `Collector`, such as `Collectors.toList()` or `Collectors.groupingBy(...)`.

#### Deep dive

A collector defines how to create an accumulator, add elements, combine partial results and optionally finish the result. This design supports sequential and parallel collection.

#### Production angle

Most backend stream bugs around `collect` involve duplicate map keys, unexpected mutability, memory pressure or unsafe external mutation.

#### Traps / caveats

- `collect` is terminal and consumes the stream.
- Collecting everything materializes data in memory.
- Do not confuse `collect` with `reduce` for mutable containers.

#### Optional Anki

Q: What type of operation is `collect()`?
A: A terminal mutable-reduction operation.

</details>

<a id="stream-col-002"></a>

<details>
<summary><strong>STREAM-COL-002. What are the main parts of a Collector?</strong></summary>

#### Short answer

A collector has a supplier, accumulator, combiner, finisher and characteristics.

#### Interview answer

The supplier creates a mutable accumulation container. The accumulator adds one element. The combiner merges two partial containers, mainly for parallel execution. The finisher converts the accumulator into the final result. Characteristics describe optimization properties.

#### Deep dive

For `toList()`, the supplier creates a list, the accumulator adds elements, the combiner merges lists, and the finisher may be identity depending on collector design.

#### Production angle

Understanding these parts is important when reviewing custom collectors or parallel collection failures.

#### Traps / caveats

- The combiner must be correct even if tests only run sequentially.
- The accumulator must not corrupt shared state.
- The finisher may make a result immutable or transformed.

#### Optional Anki

Q: Which collector function merges partial results?
A: The combiner.

</details>

<a id="stream-col-003"></a>

<details>
<summary><strong>🧠 STREAM-COL-003. What do Collector characteristics such as IDENTITY_FINISH, UNORDERED and CONCURRENT mean?</strong></summary>

#### Short answer

They describe whether finishing is identity, order is irrelevant, or accumulation can happen concurrently.

#### Interview answer

`IDENTITY_FINISH` means the accumulator type can be returned directly as the result. `UNORDERED` means the collector does not depend on encounter order. `CONCURRENT` means multiple threads may accumulate into the same result container when other conditions allow it.

#### Deep dive

`CONCURRENT` is useful mostly with unordered streams or collectors that also do not require encounter order. It does not magically make an unsafe container safe.

#### Production angle

Wrong characteristics can create subtle parallel bugs or missed optimizations. Custom collectors should be conservative unless the guarantees are proven.

#### Traps / caveats

- Do not mark a collector `CONCURRENT` unless the accumulator is thread-safe.
- `UNORDERED` changes result-order guarantees.
- `IDENTITY_FINISH` is wrong if the finisher wraps or transforms the result.

#### Optional Anki

Q: What does `IDENTITY_FINISH` mean?
A: The accumulator object is already the final result type.

</details>

<a id="stream-col-004"></a>

<details>
<summary><strong>STREAM-COL-004. What guarantees do Collectors.toList(), Stream.toList() and Collectors.toSet() provide?</strong></summary>

#### Short answer

`Stream.toList()` returns an unmodifiable list. `Collectors.toList()` and `toSet()` do not guarantee concrete implementation.

#### Interview answer

`Collectors.toList()` collects into a `List`, but the specification does not promise `ArrayList` or mutability. `Stream.toList()` returns an unmodifiable list. `Collectors.toSet()` returns a `Set`, but does not guarantee implementation, mutability or encounter order.

#### Deep dive

If you need a specific type, use `toCollection(ArrayList::new)` or another supplier. If you need immutability, use `Stream.toList()`, `toUnmodifiableList()` or copy factories deliberately.

#### Production angle

Unexpected mutability assumptions create runtime failures when code appends to an unmodifiable result or relies on set ordering.

#### Traps / caveats

- Unmodifiable collections are shallow.
- `toSet()` can remove duplicates.
- `Stream.toList()` requires a newer Java version than Java 8.

#### Optional Anki

Q: How do you request a specific collection type?
A: Use `Collectors.toCollection(...)`.

</details>

<a id="stream-col-005"></a>

<details>
<summary><strong>STREAM-COL-005. What happens when duplicate keys appear in Collectors.toMap()?</strong></summary>

#### Short answer

The simple `toMap(keyMapper, valueMapper)` overload throws an exception on duplicate keys.

#### Interview answer

`Collectors.toMap()` needs unique keys unless you provide a merge function. If two elements produce the same key, the default collector cannot decide which value to keep and throws `IllegalStateException`.

#### Deep dive

Duplicate keys are often business data issues: duplicate IDs, normalized emails, case-insensitive names or many-to-one mappings.

#### Production angle

Never assume uniqueness blindly for user or database data. Decide whether duplicates should fail, keep first, keep last, merge values or group into lists.

#### Traps / caveats

- The exception can happen only with certain data.
- Keeping "last" can be nondeterministic in unordered or parallel streams.
- Null keys/values have collector-specific behavior to check.

#### Optional Anki

Q: What does default `Collectors.toMap()` do on duplicate keys?
A: Throws `IllegalStateException`.

</details>

<a id="stream-col-006"></a>

<details>
<summary><strong>STREAM-COL-006. How do you handle key collisions and choose the Map implementation in toMap()?</strong></summary>

#### Short answer

Provide a merge function and, when needed, a map supplier.

#### Interview answer

Use `toMap(keyMapper, valueMapper, mergeFunction)` to handle duplicate keys. Add a fourth argument, `mapSupplier`, to choose the implementation, such as `LinkedHashMap::new`, `TreeMap::new` or `EnumMap` with a supplier.

#### Deep dive

The merge function must express business intent. Examples are keeping the first value, keeping the newest value, summing counts or combining lists.

#### Production angle

Choose `LinkedHashMap` when output order matters, `TreeMap` for sorted keys, and `HashMap` for ordinary lookup. Document collision behavior in service code.

#### Traps / caveats

- Merge functions must be associative for parallel correctness.
- Returning null from merge can remove mappings.
- "Keep first" depends on encounter order.

#### Optional Anki

Q: Which `toMap` argument chooses the map implementation?
A: The map supplier.

</details>

<a id="stream-col-007"></a>

<details>
<summary><strong>STREAM-COL-007. What is the difference between groupingBy(), groupingByConcurrent() and partitioningBy()?</strong></summary>

#### Short answer

`groupingBy` groups by arbitrary keys, `groupingByConcurrent` groups into a concurrent map, and `partitioningBy` splits by a boolean predicate.

#### Interview answer

`groupingBy(classifier)` produces a `Map<K, List<T>>` by default. `partitioningBy(predicate)` produces two boolean buckets. `groupingByConcurrent` is designed for concurrent grouping in parallel-friendly cases.

#### Deep dive

All can use downstream collectors. For example, group by status and count, or partition users by active flag and map to IDs.

#### Production angle

Grouping can consume large memory because every group and list is retained. For huge datasets, prefer database aggregation or streaming summaries.

#### Traps / caveats

- `groupingByConcurrent` does not preserve encounter order like ordinary grouping.
- `partitioningBy` always uses boolean keys.
- Classifier functions must handle nulls deliberately.

#### Optional Anki

Q: Which collector groups into true/false buckets?
A: `partitioningBy()`.

</details>

<a id="stream-col-008"></a>

<details>
<summary><strong>STREAM-COL-008. How do downstream collectors work?</strong></summary>

#### Short answer

Downstream collectors define what to accumulate inside each group or partition.

#### Interview answer

By default, `groupingBy` stores grouped elements in lists. A downstream collector changes that. You can group by department and count employees, sum salaries, map to names, collect to sets or compute summaries.

#### Deep dive

Downstream collectors compose. For example, `groupingBy(Order::status, mapping(Order::id, toSet()))` groups by status and keeps only IDs.

#### Production angle

Downstream collectors reduce post-processing and often avoid storing full objects when only counts, IDs or summaries are needed.

#### Traps / caveats

- Downstream `toList()` can still create large lists.
- Nested collectors can become unreadable.
- The classifier and downstream mapper can trigger lazy loads.

#### Optional Anki

Q: What does a downstream collector do?
A: It controls the result accumulated for each group.

</details>

<a id="stream-col-009"></a>

<details>
<summary><strong>STREAM-COL-009. How do you count, sum, average or summarize values with collectors?</strong></summary>

#### Short answer

Use collectors such as `counting`, `summingInt`, `averagingLong` and `summarizingDouble`.

#### Interview answer

Collectors provide aggregation helpers for grouped and ungrouped pipelines. `counting()` counts elements. `summingInt(User::age)` sums values. `averagingInt` computes averages. `summarizingInt` returns count, sum, min, max and average in one result.

#### Deep dive

Primitive streams also have direct operations like `mapToInt(...).sum()` and `summaryStatistics()`. Collectors are especially useful downstream of `groupingBy`.

#### Production angle

For database-sized data, SQL aggregation is usually better. For already-loaded business data, collectors can keep code concise.

#### Traps / caveats

- Numeric overflow is still possible.
- Averages over empty data need defined behavior.
- `Double` aggregation can have precision caveats.

#### Optional Anki

Q: Which collector gives count, sum, min, max and average?
A: `summarizingInt`, `summarizingLong` or `summarizingDouble`.

</details>

<a id="stream-col-010"></a>

<details>
<summary><strong>🧠 STREAM-COL-010. What do Collectors.mapping(), filtering(), flatMapping() and collectingAndThen() solve?</strong></summary>

#### Short answer

They adapt downstream collection by transforming, filtering, flattening or finishing grouped results.

#### Interview answer

`mapping` maps elements before downstream collection. `filtering` filters elements within each group. `flatMapping` flattens nested values into each group. `collectingAndThen` applies a final transformation, such as wrapping a list as unmodifiable.

#### Deep dive

These collectors are most useful inside `groupingBy` or `partitioningBy`, where a normal stream-level `map` or `filter` would change which groups exist or what reaches grouping.

#### Production angle

They reduce awkward post-processing maps after grouping, but deeply nested collector expressions should be extracted for readability.

#### Traps / caveats

- Downstream filtering preserves empty groups that stream-level filtering might remove.
- `flatMapping` must handle null nested collections.
- `collectingAndThen` means `IDENTITY_FINISH` does not apply.

#### Optional Anki

Q: What does `Collectors.mapping()` do?
A: It maps elements before passing them to a downstream collector.

</details>

<a id="stream-col-011"></a>

<details>
<summary><strong>STREAM-COL-011. When should you use Collectors.joining()?</strong></summary>

#### Short answer

Use `joining()` to concatenate character sequences, optionally with delimiter, prefix and suffix.

#### Interview answer

`Collectors.joining(", ")` is the standard way to join a stream of strings. It is clearer and usually more efficient than reducing with string concatenation because it uses mutable accumulation internally.

#### Deep dive

For non-string values, map them to strings first. For very large outputs, consider streaming to a writer instead of building one huge string.

#### Production angle

Useful for log messages, CSV-like small output, display labels and validation summaries. Avoid it for unbounded or huge response generation.

#### Traps / caveats

- `joining()` expects `CharSequence` elements.
- Null elements can produce `"null"` or fail depending on mapping.
- Huge joined strings can create memory pressure.

#### Optional Anki

Q: Why prefer `joining()` over string `reduce()`?
A: It is clearer and avoids repeated immutable string concatenation.

</details>

<a id="stream-col-012"></a>

<details>
<summary><strong>🧠 STREAM-COL-012. What does Collectors.teeing() do?</strong></summary>

#### Short answer

`teeing()` runs two downstream collectors on the same input and merges their results.

#### Interview answer

`Collectors.teeing(a, b, merger)` is useful when you need two independent aggregations from one stream pass, such as min and max, count and sum, or valid and invalid summaries. The merger combines the two collector results.

#### Deep dive

It is not always more readable than a small custom accumulator. It shines when both downstream collectors are standard and the merge is simple.

#### Production angle

Use it for compact one-pass summaries, but avoid clever collector expressions that obscure business intent.

#### Traps / caveats

- Requires Java 12+.
- Both downstream collectors see the same input.
- Complex teeing can be harder to debug than a named summary class.

#### Optional Anki

Q: What does `teeing()` combine?
A: The results of two downstream collectors over the same stream.

</details>

<a id="stream-col-013"></a>

<details>
<summary><strong>🧠 STREAM-COL-013. When would you write a custom Collector, and when should you avoid it?</strong></summary>

#### Short answer

Write one for reusable, well-tested accumulation logic that standard collectors cannot express clearly.

#### Interview answer

A custom collector can be appropriate for a domain summary, specialized immutable result, efficient aggregation or reusable library behavior. Avoid it when a simple loop, standard collector or named accumulator class is clearer.

#### Deep dive

Custom collectors must handle supplier, accumulator, combiner, finisher and characteristics correctly. Parallel behavior is part of the contract, even if you expect sequential use.

#### Production angle

A broken custom collector can pass unit tests and fail under parallel streams or larger data. Treat it like shared infrastructure.

#### Traps / caveats

- Always test combiner behavior.
- Be conservative with characteristics.
- Do not expose mutable accumulator internals accidentally.

#### Optional Anki

Q: What is the hardest part of a custom collector?
A: Correct combiner and characteristics, especially for parallel execution.

</details>

<a id="stream-col-014"></a>

<details>
<summary><strong>🧠 STREAM-COL-014. Why can a wrong combiner break parallel collection?</strong></summary>

#### Short answer

Parallel streams create partial results that must be merged correctly by the combiner.

#### Interview answer

In sequential collection, the combiner may not be used, so a bad combiner can go unnoticed. In parallel, each worker may accumulate a partial result. The combiner must merge those partial results without losing data, duplicating data or violating result invariants.

#### Deep dive

The combiner must be compatible with the accumulator and finisher. It should usually mutate and return one accumulator or create a correct merged one depending on collector design.

#### Production angle

This is a classic "works in tests, fails in production" issue when test data is small or always sequential.

#### Traps / caveats

- Returning the left accumulator without merging loses data.
- Sharing one accumulator between workers causes races.
- Merge order should not affect the logical result unless ordering is part of the contract.

#### Optional Anki

Q: Why test custom collectors in parallel?
A: To verify the combiner correctly merges partial results.

</details>

<a id="stream-col-015"></a>

<details>
<summary><strong>STREAM-COL-015. Why can collecting into a shared mutable object be wrong?</strong></summary>

#### Short answer

It introduces side effects, data races and ordering assumptions outside the collector contract.

#### Interview answer

Code like `stream.forEach(list::add)` mutates an external list. It may work sequentially but can fail in parallel and makes ownership unclear. Use `collect(toList())` or a proper collector so the Stream API manages accumulation and combination.

#### Deep dive

Adding synchronization around external mutation can make the code slower and still less clear than a collector.

#### Production angle

External mutation produces missing elements, duplicates, `ConcurrentModificationException` or lock contention under load.

#### Traps / caveats

- `Collections.synchronizedList` does not make ordering semantics obvious.
- Mutating maps in `forEach` has the same problem.
- Side effects hide the actual result-building contract.

#### Optional Anki

Q: Preferred alternative to `forEach(list::add)`?
A: `collect(Collectors.toList())` or `toList()`.

</details>

<a id="stream-col-016"></a>

<details>
<summary><strong>STREAM-COL-016. How do you collect immutable results safely?</strong></summary>

#### Short answer

Use unmodifiable collectors, `Stream.toList()`, `List.copyOf()` or `collectingAndThen()` deliberately.

#### Interview answer

For lists, `stream.toList()` returns an unmodifiable list. For explicit unmodifiable collection factories, use `Collectors.toUnmodifiableList()`, `toUnmodifiableSet()` or `toUnmodifiableMap()`. You can also collect into a mutable structure and finish with `List.copyOf()` or `collectingAndThen`.

#### Deep dive

Unmodifiable collection does not mean deeply immutable. Mutable elements can still be changed.

#### Production angle

Immutable result boundaries prevent accidental caller mutation, especially for cached results, DTO lists and service return values.

#### Traps / caveats

- Some unmodifiable collectors reject nulls.
- `Stream.toList()` result cannot be appended to.
- Copying huge collections has cost.

#### Optional Anki

Q: How can a collector create an immutable list result?
A: Use `Collectors.toUnmodifiableList()` or finish with `List.copyOf()`.

</details>

<a id="stream-col-017"></a>

<details>
<summary><strong>STREAM-COL-017. What is the difference between reduce() and collect()?</strong></summary>

#### Short answer

`reduce()` combines values into an immutable-style result. `collect()` accumulates into a mutable container.

#### Interview answer

Use `reduce` for reductions like sum, product, min-like combinations or immutable value aggregation. Use `collect` for lists, maps, strings, grouped results and mutable accumulation. A mutable container as a `reduce` identity is a common bug.

#### Deep dive

`reduce` requires identity and accumulator rules that work with sequential and parallel execution. `collect` separates accumulator and combiner to support mutable containers safely.

#### Production angle

Using `reduce(new ArrayList<>(), ...)` can corrupt results in parallel. Use collectors for container-building.

#### Traps / caveats

- `reduce` functions should be associative.
- The identity must be neutral.
- `collect` can still create large memory pressure.

#### Optional Anki

Q: Should you use `reduce()` to build a mutable list?
A: No. Use `collect()`.

</details>

<a id="stream-col-018"></a>

<details>
<summary><strong>STREAM-COL-018. What are the identity and associativity rules for reduce()?</strong></summary>

#### Short answer

The identity must be neutral, and the accumulator/combiner must be associative and compatible.

#### Interview answer

An identity is a value that does not change the result, such as `0` for addition or `1` for multiplication. Associativity means grouping does not change the result: `(a op b) op c` equals `a op (b op c)`. This is essential because parallel streams can split and combine work in different groupings.

#### Deep dive

Subtraction is a classic bad parallel reduce example because it is not associative. Mutable identity values are also dangerous because multiple partial computations can share or merge state incorrectly.

#### Production angle

Wrong reductions produce silent data correctness bugs, often only after switching to `.parallel()` or changing data size.

#### Traps / caveats

- Floating-point arithmetic has precision and associativity caveats.
- Identity must be valid for empty streams.
- Combiner must be compatible with accumulator in three-argument `reduce`.

#### Optional Anki

Q: Why is subtraction bad for parallel `reduce()`?
A: It is not associative, so different grouping can change the result.

</details>
