# 10.05. Parallel streams, ForkJoinPool and Spliterator

---

<a id="stream-par-001"></a>

<details>
<summary><strong>STREAM-PAR-001. What are parallel streams?</strong></summary>

#### Short answer

Parallel streams split stream processing across multiple threads.

#### Interview answer

A parallel stream lets the Stream API divide work into chunks, process chunks concurrently and combine results. You can create one with `collection.parallelStream()` or `stream.parallel()`.

The goal is throughput improvement for suitable CPU-bound workloads.

#### Deep dive

Parallel streams depend on source splitting, operation cost, ordering constraints, collector behavior and available CPU. They are not a general asynchronous programming model.

#### Production angle

In backend services, parallel streams can compete with request-handling threads and other common-pool users, so they must be justified by measurement.

#### Traps / caveats

- Parallel does not mean faster.
- Side effects must be thread-safe and semantically correct.
- Blocking work can starve the pool.

#### Optional Anki

Q: How do you create a parallel stream from a collection?
A: `collection.parallelStream()`.

</details>

---

<a id="stream-par-002"></a>

<details>
<summary><strong>STREAM-PAR-002. When should you consider using parallel streams?</strong></summary>

#### Short answer

Consider them for large, CPU-bound, independent work with a splittable source and cheap result combination.

#### Interview answer

Good candidates have many elements, expensive per-element CPU work, no shared mutable state, no blocking I/O, no strict order requirement and an efficient source such as an array or `ArrayList`.

#### Deep dive

The computation must be large enough to offset splitting, scheduling and combining overhead. Benchmark with realistic data before keeping it.

#### Production angle

Batch processing, offline analytics and controlled worker jobs are better candidates than request-path web code.

#### Traps / caveats

- Small collections often get slower.
- Ordered operations reduce benefit.
- Parallel streams still run inside the JVM process and consume CPU from other work.

#### Optional Anki

Q: Best workload for parallel streams?
A: Large CPU-bound independent work over a well-splittable source.

</details>

---

<a id="stream-par-003"></a>

<details>
<summary><strong>STREAM-PAR-003. When should you avoid parallel streams?</strong></summary>

#### Short answer

Avoid them for blocking I/O, small datasets, shared mutable state, strict ordering, transactions or request-path latency-sensitive work.

#### Interview answer

Parallel streams are poor for database calls, HTTP calls, synchronized mutation, tiny transformations, long ordered pipelines and code that depends on thread-local context. They also make debugging and observability harder.

#### Deep dive

The default execution pool is shared. A single endpoint using parallel streams can interfere with unrelated tasks using the same pool.

#### Production angle

For blocking fan-out, prefer bounded executors, `CompletableFuture`, virtual threads or reactive APIs depending on the system model.

#### Traps / caveats

- `parallelStream()` does not make JDBC or HTTP calls safe.
- ThreadLocal security/logging context may not propagate.
- More threads can increase latency through contention.

#### Optional Anki

Q: Should blocking I/O usually go inside `parallelStream()`?
A: No.

</details>

<a id="stream-par-004"></a>

<details>
<summary><strong>STREAM-PAR-004. Why can parallel streams hurt latency in a web application?</strong></summary>

#### Short answer

They consume shared CPU/pool resources and add coordination overhead inside request handling.

#### Interview answer

Web applications already handle many requests concurrently. If each request starts parallel stream work, the service can oversubscribe CPUs, increase context switching and contend for the common `ForkJoinPool`. Tail latency often gets worse even if one isolated request looks faster.

#### Deep dive

Parallel streams optimize a computation, not whole-service capacity. They do not know about request deadlines, bulkheads or downstream limits.

#### Production angle

Check p95/p99 latency, CPU saturation, common-pool activity and request concurrency before accepting a parallel stream in a controller or service path.

#### Traps / caveats

- Load tests matter more than microbenchmarks.
- Parallel streams can hide work from request-level tracing.
- Blocking operations can starve unrelated common-pool tasks.

#### Optional Anki

Q: Main web-app risk of parallel streams?
A: Worse tail latency from CPU and common-pool contention.

</details>

<a id="stream-par-005"></a>

<details>
<summary><strong>STREAM-PAR-005. Why is blocking I/O inside a parallel stream dangerous?</strong></summary>

#### Short answer

Blocking tasks occupy worker threads and can starve the pool.

#### Interview answer

Parallel streams are designed mainly for CPU-bound fork/join work. If lambdas perform database calls, HTTP requests or file I/O, worker threads block while waiting. This reduces parallelism and can interfere with other common-pool users.

#### Deep dive

The pool may compensate in some managed-blocking cases, but ordinary blocking calls inside stream lambdas are not a good concurrency design.

#### Production angle

Use explicit concurrency controls for I/O: bounded executors, rate limits, timeouts, circuit breakers, `CompletableFuture`, virtual threads or reactive clients.

#### Traps / caveats

- Parallel streams do not provide backpressure.
- Downstream services can be overwhelmed.
- Transactions and security context may not propagate.

#### Optional Anki

Q: What workload are parallel streams mainly designed for?
A: CPU-bound independent work.

</details>

<a id="stream-par-006"></a>

<details>
<summary><strong>🧠 STREAM-PAR-006. Which ForkJoinPool is commonly used by parallel streams?</strong></summary>

#### Short answer

Parallel streams commonly use the common `ForkJoinPool`.

#### Interview answer

Unless execution is arranged specially, parallel stream tasks run on the JVM-wide `ForkJoinPool.commonPool()`. This pool is shared by other framework and application tasks that also use the common pool.

#### Deep dive

The common pool parallelism is usually related to available processors. It is not request-scoped and does not know about application-level bulkheads.

#### Production angle

Common-pool interference can explain unrelated latency spikes when one code path introduces heavy parallel streams.

#### Traps / caveats

- Do not assume every parallel stream has a private pool.
- Thread-local context usually does not automatically follow.
- Tuning common pool globally affects the whole JVM.

#### Optional Anki

Q: What pool do parallel streams commonly use?
A: `ForkJoinPool.commonPool()`.

</details>

<a id="stream-par-007"></a>

<details>
<summary><strong>🧠 STREAM-PAR-007. How does data source splitting affect parallel stream performance?</strong></summary>

#### Short answer

Parallel streams need the source to split efficiently into balanced chunks.

#### Interview answer

A parallel stream uses the source `Spliterator` to divide work. Arrays and `ArrayList` split well because ranges are cheap. `LinkedList`, I/O streams and unknown-size sources split poorly, causing imbalance or overhead.

#### Deep dive

Good splitting creates enough chunks to keep workers busy without creating excessive scheduling overhead. Accurate size estimates help planning.

#### Production angle

If a parallel stream over one source is slower than another with the same elements, source splitting is a key suspect.

#### Traps / caveats

- Poor splitting can leave one worker doing most work.
- Unknown-size spliterators limit optimization.
- Expensive combining can erase splitting benefits.

#### Optional Anki

Q: Which common collection splits well for parallel streams?
A: `ArrayList`.

</details>

<a id="stream-par-008"></a>

<details>
<summary><strong>STREAM-PAR-008. Which sources are usually good or bad for parallel streams?</strong></summary>

#### Short answer

Arrays, ranges and `ArrayList` are usually good; linked, I/O, cursor and unknown-size sources are usually bad.

#### Interview answer

Good sources are finite, sized and cheaply splittable. Examples are arrays, `IntStream.range`, `LongStream.range` and `ArrayList`. Bad sources are hard to split or slow to traverse independently, such as `LinkedList`, file lines, database cursors and generated iterative streams.

#### Deep dive

Hash-based collections can split reasonably but may not preserve order. Source quality is only one part; operation cost and collection strategy also matter.

#### Production angle

Do not add `.parallel()` to file or database streams expecting faster I/O. Measure source behavior with representative data.

#### Traps / caveats

- `parallel()` on a sequential-looking pipeline can change thread use deeply.
- `iterate()` streams are not naturally parallel-friendly.
- An ordered source may impose ordering costs.

#### Optional Anki

Q: Why is `LinkedList` often poor for parallel streams?
A: It does not split into balanced indexed ranges cheaply.

</details>

<a id="stream-par-009"></a>

<details>
<summary><strong>🧠 STREAM-PAR-009. How do ordering and stateful operations affect parallel streams?</strong></summary>

#### Short answer

They add coordination, buffering and constraints that reduce parallel efficiency.

#### Interview answer

Ordered streams must preserve encounter order for operations that care about it. Stateful operations such as `sorted`, `distinct`, `limit` and `skip` may need cross-element coordination. In parallel, this often means buffering and merging partial results carefully.

#### Deep dive

Removing order with `unordered()` can improve some operations when order is irrelevant, but it changes guarantees.

#### Production angle

If a parallel stream is slow, inspect ordered sources, `findFirst`, `forEachOrdered`, `limit`, `skip`, `distinct` and `sorted`.

#### Traps / caveats

- `limit()` can be expensive on ordered parallel streams.
- `findAny()` may be faster than `findFirst()`.
- `unordered()` is only correct if result order does not matter.

#### Optional Anki

Q: Why can `findFirst()` be slow in parallel?
A: It must respect encounter order.

</details>

<a id="stream-par-010"></a>

<details>
<summary><strong>STREAM-PAR-010. Why must operations in parallel streams be stateless and non-interfering?</strong></summary>

#### Short answer

Because elements may be processed concurrently, in chunks and in a different order.

#### Interview answer

Stateless lambdas do not depend on mutable shared state. Non-interfering lambdas do not modify the source. Parallel streams rely on these properties to split work safely. Mutable counters, external lists and source mutation can create races or incorrect results.

#### Deep dive

Sequential streams can accidentally tolerate stateful lambdas, but parallel execution exposes the invalid assumptions.

#### Production angle

Random missing elements after switching to `parallel()` often come from external mutable accumulation or non-thread-safe objects.

#### Traps / caveats

- Thread-safe does not always mean semantically correct.
- `AtomicInteger` does not provide deterministic encounter-order indexing.
- Mutating entity objects can still create shared-state bugs.

#### Optional Anki

Q: What kind of lambda is safest in a parallel stream?
A: Stateless and non-interfering.

</details>

<a id="stream-par-011"></a>

<details>
<summary><strong>🧠 STREAM-PAR-011. What are the requirements for a Collector to perform concurrent reduction?</strong></summary>

#### Short answer

It needs a concurrent collector, safe accumulation and compatible ordering conditions.

#### Interview answer

A collector marked `CONCURRENT` can allow multiple threads to accumulate into the same result container when the stream is unordered or the collector is also unordered. The accumulator and container must be safe for concurrent updates.

#### Deep dive

`toConcurrentMap` and `groupingByConcurrent` are examples designed for concurrent maps. Ordinary `toMap` or `groupingBy` combine isolated partial results instead.

#### Production angle

Concurrent reduction is useful for high-volume grouping or map building, but it can introduce contention. It still needs benchmarking.

#### Traps / caveats

- A concurrent map does not make the downstream list thread-safe unless designed.
- Ordering requirements can disable concurrent accumulation.
- Wrong collector characteristics can corrupt results.

#### Optional Anki

Q: Which collector characteristic signals concurrent accumulation?
A: `CONCURRENT`.

</details>

<a id="stream-par-012"></a>

<details>
<summary><strong>STREAM-PAR-012. Why is parallelStream() not a silver bullet?</strong></summary>

#### Short answer

It adds overhead and correctness constraints, and only helps suitable workloads.

#### Interview answer

`parallelStream()` has splitting, scheduling, synchronization and combining costs. It can slow down small or cheap computations, break side-effect-heavy code, overload shared CPU, and interfere with other common-pool work.

#### Deep dive

Parallelism improves throughput only when enough independent work exists and coordination costs stay low.

#### Production angle

Keep parallel streams out of latency-sensitive code unless load tests and profiling show a clear benefit.

#### Traps / caveats

- One fast benchmark on a laptop is not enough.
- It does not control downstream concurrency.
- It can make failures nondeterministic.

#### Optional Anki

Q: Why can `parallelStream()` be slower?
A: Overhead and coordination can exceed saved computation time.

</details>

<a id="stream-par-013"></a>

<details>
<summary><strong>🧠 STREAM-PAR-013. How do you benchmark sequential vs parallel streams correctly?</strong></summary>

#### Short answer

Use a proper benchmark, realistic data and compare end-to-end behavior under load.

#### Interview answer

For microbenchmarks, use JMH to handle warmup, dead-code elimination and measurement noise. Compare sequential and parallel versions with realistic data sizes, operation costs and collectors. For services, run load tests and check tail latency, CPU, GC and pool contention.

#### Deep dive

Parallel streams may win in isolation but lose in a real server where many requests compete for CPU.

#### Production angle

The final decision should come from representative measurements, not intuition or tiny examples.

#### Traps / caveats

- Do not benchmark with `System.nanoTime()` around one cold run.
- Ensure results are consumed so work is not optimized away.
- Measure p95/p99 latency, not only average time.

#### Optional Anki

Q: What tool is standard for Java microbenchmarks?
A: JMH.

</details>

<a id="stream-par-014"></a>

<details>
<summary><strong>STREAM-PAR-014. Why can small collections be slower with parallel streams?</strong></summary>

#### Short answer

The overhead of splitting, scheduling and combining can exceed the work saved.

#### Interview answer

If each element is cheap to process or there are few elements, parallelism has little useful work to distribute. The JVM still pays for task creation, coordination and result merging.

#### Deep dive

JIT warmup, allocation and CPU cache behavior can dominate small pipelines. Sequential loops or sequential streams are often better.

#### Production angle

Do not parallelize ordinary DTO mapping of a few hundred items in a web request. The overhead and contention can hurt more than help.

#### Traps / caveats

- "More cores" does not remove coordination cost.
- Cheap lambdas rarely benefit.
- Small local tests can mislead either way.

#### Optional Anki

Q: Main reason small parallel streams are often slower?
A: Parallel overhead is larger than the work being parallelized.

</details>

<a id="stream-par-015"></a>

<details>
<summary><strong>STREAM-PAR-015. How do virtual threads change the decision around parallel streams for blocking tasks?</strong></summary>

#### Short answer

Virtual threads make blocking concurrency cheaper, but they do not make parallel streams the right abstraction for blocking fan-out.

#### Interview answer

Virtual threads are useful for many blocking tasks because they avoid tying up platform threads while waiting. Parallel streams still use fork/join-style data parallelism and are not designed for request fan-out, timeouts, cancellation, rate limits or structured concurrency.

#### Deep dive

For blocking calls, prefer a design that explicitly models concurrency and failure: virtual-thread executors, structured concurrency where available, `CompletableFuture` or reactive APIs.

#### Production angle

The question becomes less "can I get more threads?" and more "how do I bound, cancel, observe and protect this concurrency?"

#### Traps / caveats

- `parallelStream()` is not automatically virtual-thread-based.
- Virtual threads do not remove downstream rate limits.
- Thread-local context still needs attention.

#### Optional Anki

Q: Do virtual threads make `parallelStream()` ideal for blocking I/O?
A: No.

</details>

<a id="stream-par-016"></a>

<details>
<summary><strong>🧠 STREAM-PAR-016. Can you control the ForkJoinPool used by a parallel stream?</strong></summary>

#### Short answer

Parallel streams use the common pool by default; custom-pool workarounds exist, but explicit concurrency APIs are usually clearer.

#### Interview answer

Parallel streams commonly use `ForkJoinPool.commonPool()`. Some code submits a task to a custom `ForkJoinPool` and runs the parallel stream inside that task, but this is a workaround rather than a simple per-stream configuration knob.

If thread ownership, isolation, naming, context propagation or queue limits matter, a dedicated executor or another explicit concurrency model is usually easier to reason about.

#### Deep dive

Global common-pool tuning affects the whole JVM. Custom pools can reduce interference, but they do not fix poor source splitting, blocking I/O, side effects, ordering constraints or incorrect collectors.

#### Production angle

In backend services, the real question is usually not only "which pool?" but "what concurrency budget, cancellation, timeout, context propagation and observability model owns this work?"

#### Traps / caveats

- Global common-pool tuning affects the whole JVM.
- Custom pools can hide resource usage unless named, monitored and bounded.
- Submitting a parallel stream to a custom pool is not a substitute for a clean async design.
- Do not use custom pools to paper over a poor parallel-stream fit.

#### Optional Anki

Q: Best answer to "Can I control parallel stream threads?"
A: Prefer explicit concurrency APIs if thread ownership matters.

</details>

<a id="stream-par-017"></a>

<details>
<summary><strong>🧠 STREAM-PAR-017. How can parallel streams affect MDC/logging context propagation?</strong></summary>

#### Short answer

Parallel stream work runs on worker threads where thread-local logging context may be absent or stale.

#### Interview answer

Logging MDC, security context and tracing context are often stored in `ThreadLocal`. Parallel streams execute lambdas on different worker threads, so the original request context may not be present unless explicitly propagated.

#### Deep dive

Even if context appears in tests, pooled worker threads can retain unrelated context if cleanup is wrong.

#### Production angle

Symptoms include missing trace IDs, wrong tenant IDs in logs, confusing audit records or broken authorization assumptions.

#### Traps / caveats

- `ThreadLocal` is not automatically copied.
- Context propagation libraries may not hook into parallel streams.
- Avoid security-sensitive logic that assumes request thread context inside parallel lambdas.

#### Optional Anki

Q: Why can MDC disappear in a parallel stream?
A: Work runs on different worker threads without the request thread's `ThreadLocal` context.

</details>

<a id="stream-split-001"></a>

<details>
<summary><strong>🧠 STREAM-SPLIT-001. What is a Spliterator, and how is it different from Iterator?</strong></summary>

#### Short answer

A `Spliterator` traverses elements and can split itself for parallel processing.

#### Interview answer

An `Iterator` mainly supports sequential traversal with `hasNext()` and `next()`. A `Spliterator` supports traversal with `tryAdvance()` and can optionally split work with `trySplit()`. It also reports characteristics such as ordered, sized or immutable.

#### Deep dive

Collections expose spliterators, and streams are built on them. The stream implementation uses spliterator metadata to plan traversal and optimization.

#### Production angle

Most developers do not implement spliterators, but understanding them explains why some sources parallelize well and others do not.

#### Traps / caveats

- A spliterator that cannot split may still work sequentially.
- Characteristics must be accurate.
- Spliterator internals are advanced interview material.

#### Optional Anki

Q: What is the key extra ability of `Spliterator` over `Iterator`?
A: It can split traversal work.

</details>

<a id="stream-split-002"></a>

<details>
<summary><strong>🧠 STREAM-SPLIT-002. What do tryAdvance(), trySplit(), estimateSize() and Spliterator characteristics do?</strong></summary>

#### Short answer

They define traversal, splitting, size estimation and source properties.

#### Interview answer

`tryAdvance()` processes the next element if one exists. `trySplit()` attempts to split off part of the remaining elements for parallel work. `estimateSize()` reports an estimated remaining size. Characteristics tell the Stream API facts such as `ORDERED`, `SIZED`, `SUBSIZED`, `DISTINCT`, `SORTED`, `IMMUTABLE`, `CONCURRENT` or `NONNULL`.

#### Deep dive

Accurate `SIZED` and `SUBSIZED` help preallocation and parallel planning. `ORDERED` affects operations like `findFirst` and `limit`.

#### Production angle

For custom data sources, conservative and correct metadata is better than optimistic metadata that enables wrong optimizations.

#### Traps / caveats

- `estimateSize()` can be an estimate unless `SIZED` is claimed.
- `trySplit()` returning null limits parallelism.
- `NONNULL` must not be claimed if nulls are possible.

#### Optional Anki

Q: Which `Spliterator` method enables parallel decomposition?
A: `trySplit()`.

</details>

<a id="stream-split-003"></a>

<details>
<summary><strong>🧠 STREAM-SPLIT-003. What bugs can incorrect Spliterator characteristics cause?</strong></summary>

#### Short answer

Wrong characteristics can cause incorrect results, missed checks, bad ordering, memory waste or poor parallel performance.

#### Interview answer

If a spliterator claims `SIZED` incorrectly, the stream may allocate or count incorrectly. If it claims `SORTED` or `DISTINCT` falsely, operations may skip work they should perform. If it claims `NONNULL` falsely, null-sensitive assumptions can break.

#### Deep dive

Characteristics are a contract with the stream implementation. They can enable optimizations, so false claims are correctness bugs, not only performance bugs.

#### Production angle

Custom spliterators should have focused tests for characteristics, traversal order, size, splitting and parallel results.

#### Traps / caveats

- Being too conservative may reduce performance but is safer.
- `CONCURRENT` and `IMMUTABLE` have different meanings.
- `ORDERED` should reflect encounter order, not sorted order.

#### Optional Anki

Q: Why are false spliterator characteristics dangerous?
A: The Stream implementation may trust them for optimization and skip necessary work.

</details>
