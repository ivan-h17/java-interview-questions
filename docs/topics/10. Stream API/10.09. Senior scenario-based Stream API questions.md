# 10.09. Senior scenario-based Stream API questions

---

<a id="stream-scenario-001"></a>

<details>
<summary><strong>STREAM-SCENARIO-001. A Stream pipeline is slower than a loop in production. How would you investigate it?</strong></summary>

#### Short answer

Measure first, then inspect allocation, boxing, stateful operations, data size, lambdas and whether the work belongs elsewhere.

#### Interview answer

I would reproduce with realistic data and profile CPU and allocation. I would compare the stream and loop under the same conditions, check for boxing, `sorted`, `distinct`, `groupingBy`, excessive DTO allocation, expensive mappers and accidental database or network calls.

#### Deep dive

If the source is database data, I would ask whether filtering or aggregation should happen in SQL. If the pipeline is in a request path, I would also inspect latency and GC.

#### Production angle

The fix might be a loop, primitive stream, query redesign, batching or simply clearer code. The answer should not be "streams are slow" by default.

#### Traps / caveats

- Do not benchmark with toy data.
- Do not ignore allocation profiles.
- Do not optimize away readability without evidence.

#### Optional Anki

Q: First step when stream code is slow?
A: Measure with realistic data and profile CPU/allocation.

</details>

<a id="stream-scenario-002"></a>

<details>
<summary><strong>STREAM-SCENARIO-002. A parallelStream() made the service slower. What would you check?</strong></summary>

#### Short answer

Check workload fit, common-pool contention, blocking calls, ordering, source splitting and benchmark quality.

#### Interview answer

I would ask whether the work is CPU-bound and large enough. Then I would inspect the source type, stateful operations, ordering constraints, collectors, shared mutable state and any blocking I/O. In a service, I would check CPU saturation, request concurrency and common `ForkJoinPool` interference.

#### Deep dive

Parallel streams can improve one isolated computation while hurting whole-service tail latency.

#### Production angle

Use load tests, not only local microbenchmarks. Remove `.parallel()` unless it has a proven benefit under realistic load.

#### Traps / caveats

- Small collections often get slower.
- Blocking I/O inside parallel streams is dangerous.
- `findFirst`, `limit` and `forEachOrdered` can add ordering cost.

#### Optional Anki

Q: What is the usual first suspicion when `parallelStream()` slows a web service?
A: Overhead and common-pool/CPU contention.

</details>

<a id="stream-scenario-003"></a>

<details>
<summary><strong>STREAM-SCENARIO-003. A parallel stream causes random missing elements in the result. What is the likely cause?</strong></summary>

#### Short answer

Shared mutable state or an incorrect collector/reduction is the likely cause.

#### Interview answer

The classic bug is mutating an external `ArrayList` from `parallelStream().forEach(...)`. `ArrayList` is not thread-safe, so additions race and elements are lost. Another cause is a bad combiner in a custom collector or a non-associative reduction.

#### Deep dive

Replacing the external list with `Collections.synchronizedList` may remove races but still leaves unclear ordering and performance. A proper collector is the normal fix.

#### Production angle

Look for nondeterministic tests, result size mismatches and pipelines that mutate maps, lists or counters.

#### Traps / caveats

- Sequential streams can hide the bug.
- Atomic variables do not fix collection mutation.
- Missing elements may appear only at larger data sizes.

#### Optional Anki

Q: Common cause of missing elements in parallel stream output?
A: Mutating a non-thread-safe external collection.

</details>

<a id="stream-scenario-004"></a>

<details>
<summary><strong>STREAM-SCENARIO-004. A Collectors.toMap() call fails in production with a duplicate key. How would you fix it?</strong></summary>

#### Short answer

Decide the business rule for duplicates, then use a merge function or group values.

#### Interview answer

First I would inspect why duplicates exist: data issue, wrong key, normalization, or valid many-to-one relationship. Then I would choose behavior: fail with a clearer error, keep first, keep last, merge values, or use `groupingBy` to collect a list per key.

#### Deep dive

If output order matters, choose a map supplier such as `LinkedHashMap::new`. If the merge function is used in parallel, it should be associative.

#### Production angle

Duplicate keys often expose missing uniqueness constraints or wrong domain assumptions.

#### Traps / caveats

- Silently keeping last can hide data corruption.
- Merge behavior may depend on encounter order.
- Null keys or values need explicit handling.

#### Optional Anki

Q: How do you handle duplicate keys in `toMap()`?
A: Provide a merge function or use grouping if duplicates are valid.

</details>

<a id="stream-scenario-005"></a>

<details>
<summary><strong>STREAM-SCENARIO-005. A stream over Files.lines() leaks file descriptors. What went wrong?</strong></summary>

#### Short answer

The resource-backed stream was not closed.

#### Interview answer

`Files.lines()` opens a file and returns a lazy stream. If it is not used in try-with-resources or otherwise closed, the file descriptor can remain open. This is especially easy to miss when returning the stream from a helper method.

#### Deep dive

Short-circuiting terminal operations still require closing. The stream may not read the whole file, but the file resource still needs cleanup.

#### Production angle

In import jobs, repeated leaks eventually cause "too many open files" and unrelated file operations fail.

#### Traps / caveats

- Collection streams do not need closing; file streams do.
- `readAllLines()` closes but loads everything.
- Returning the stream shifts close responsibility to the caller.

#### Optional Anki

Q: Correct pattern for `Files.lines()`?
A: Use try-with-resources around stream creation and consumption.

</details>

<a id="stream-scenario-006"></a>

<details>
<summary><strong>STREAM-SCENARIO-006. A service maps JPA entities to DTOs with streams and becomes slow. What would you suspect?</strong></summary>

#### Short answer

N+1 lazy loads, excessive entity graphs, in-memory filtering or DTO allocation.

#### Interview answer

I would check SQL logs and query counts first. The mapper may access lazy associations for each entity, causing N+1 queries. The service may also be fetching full entities when projections would be enough, or filtering/sorting in Java instead of SQL.

#### Deep dive

The stream is just the shape hiding repeated access. Fixes include fetch joins, entity graphs, batch fetching, projections, query DTOs and moving filters to the query.

#### Production angle

Symptoms are slow mapping, high database load, many similar selects and latency growth with result size.

#### Traps / caveats

- Parallel streams with JPA entities can make things worse.
- LazyInitializationException can appear outside transactions.
- `flatMap` over lazy collections can multiply queries.

#### Optional Anki

Q: What should you check first for slow JPA stream mapping?
A: SQL query count and lazy association access.

</details>

<a id="stream-scenario-007"></a>

<details>
<summary><strong>STREAM-SCENARIO-007. A stream pipeline loads millions of rows into memory. How would you redesign it?</strong></summary>

#### Short answer

Move reduction to the database where possible, or process data in bounded pages/batches.

#### Interview answer

I would remove full materialization such as `toList()` if possible. Filtering, sorting and aggregation should usually happen in SQL. If Java processing is needed, use pagination, batch processing, cursors within controlled transactions, streaming output or bounded queues.

#### Deep dive

Avoid stateful operations that retain all data, such as `sorted`, high-cardinality `groupingBy` or global `distinct`, unless the memory budget supports them.

#### Production angle

Add row limits, metrics, checkpoints and failure recovery for long jobs.

#### Traps / caveats

- A lazy stream does not help if the terminal operation collects everything.
- Long database cursors hold resources.
- One huge transaction is often unsafe.

#### Optional Anki

Q: What is the usual replacement for loading millions of rows into a list?
A: Database aggregation, pagination, batching or controlled streaming.

</details>

<a id="stream-scenario-008"></a>

<details>
<summary><strong>STREAM-SCENARIO-008. A reduce() works sequentially but gives wrong results in parallel. What would you check?</strong></summary>

#### Short answer

Check identity neutrality, associativity, combiner compatibility and mutable state.

#### Interview answer

Parallel reduction splits work and combines partial results. If the accumulator is not associative, the identity is not neutral, or the combiner is inconsistent with the accumulator, results can change. Subtraction and mutable containers are common examples.

#### Deep dive

Three-argument `reduce` is often misused to build lists or maps. Use `collect` for mutable accumulation.

#### Production angle

These bugs are dangerous because they produce plausible but wrong totals or summaries.

#### Traps / caveats

- Floating-point sums can vary due to precision.
- Mutable identity values are unsafe.
- Tests should include parallel execution if parallel use is possible.

#### Optional Anki

Q: What property must a parallel `reduce` operation have?
A: Associativity.

</details>

<a id="stream-scenario-009"></a>

<details>
<summary><strong>🧠 STREAM-SCENARIO-009. A custom Collector works in tests but fails with parallel streams. What is likely wrong?</strong></summary>

#### Short answer

The combiner, characteristics or accumulator thread-safety is likely wrong.

#### Interview answer

Sequential collection may never exercise the combiner. In parallel, partial accumulators must be merged correctly. A custom collector can fail if the combiner drops data, duplicates data, mutates the wrong object, or if `CONCURRENT` is declared without a safe accumulator.

#### Deep dive

The finisher and `IDENTITY_FINISH` characteristic must also match. False characteristics can let the stream implementation make invalid optimizations.

#### Production angle

Test custom collectors with empty, single, large, ordered, unordered and parallel streams.

#### Traps / caveats

- Do not mark characteristics optimistically.
- Shared mutable accumulators are dangerous.
- Small tests can pass while production data fails.

#### Optional Anki

Q: Why can a custom collector fail only in parallel?
A: Parallel execution uses the combiner and may expose unsafe characteristics.

</details>

<a id="stream-scenario-010"></a>

<details>
<summary><strong>STREAM-SCENARIO-010. A findFirst() call is slow on a parallel ordered stream. What alternative could help?</strong></summary>

#### Short answer

Use `findAny()` or remove ordering with `unordered()` if any matching element is acceptable.

#### Interview answer

`findFirst()` must respect encounter order, which can force coordination in a parallel stream. If the business rule only needs any match, `findAny()` is more parallel-friendly. If order does not matter anywhere downstream, `unordered()` may help.

#### Deep dive

If determinism matters, keep `findFirst()` or sort explicitly and accept the cost.

#### Production angle

This is common in search-like code where the first result is not actually required, only one valid candidate.

#### Traps / caveats

- `findAny()` can return different elements across runs.
- Do not change semantics for performance without confirming requirements.
- `anyMatch()` may be better for existence checks.

#### Optional Anki

Q: Parallel-friendly alternative to `findFirst()` when order does not matter?
A: `findAny()`.

</details>

<a id="stream-scenario-011"></a>

<details>
<summary><strong>STREAM-SCENARIO-011. A pipeline uses peek() for auditing. Why is this dangerous?</strong></summary>

#### Short answer

`peek()` is an intermediate observation operation and is not reliable for required side effects.

#### Interview answer

Because streams are lazy and can short-circuit, `peek` may not run for every element. In parallel, it can run on different threads and in nondeterministic order. Auditing is a required business side effect and should be explicit.

#### Deep dive

Some terminal operations and optimizations can make `peek` behavior surprising. Even when it runs, failures can leave partially written audit records.

#### Production angle

Auditing needs transactional, idempotent and observable design. Put it in a service boundary, event handler or explicit loop.

#### Traps / caveats

- `peek()` without terminal operation does nothing.
- Logs from `peek` are not proof of complete processing.
- Parallel streams can break audit ordering.

#### Optional Anki

Q: Why should auditing not be in `peek()`?
A: `peek()` may be skipped, short-circuited or reordered.

</details>

<a id="stream-scenario-012"></a>

<details>
<summary><strong>STREAM-SCENARIO-012. A pipeline uses AtomicInteger to assign indexes. What are the risks?</strong></summary>

#### Short answer

Indexes can become nondeterministic, especially in parallel or unordered streams.

#### Interview answer

`AtomicInteger` makes increments atomic, but it does not guarantee that indexes match encounter order in parallel. It also introduces hidden mutable state into the pipeline. If indexing is part of the business result, use an indexed source or a loop.

#### Deep dive

For lists, `IntStream.range(0, list.size())` can be appropriate. For arbitrary streams, real indexing may require collecting, zipping support or a custom approach.

#### Production angle

Wrong indexes can break CSV line error reporting, ordered responses and validation messages.

#### Traps / caveats

- Atomic does not mean ordered.
- It can serialize a hot part of the pipeline.
- Sequential success can hide future parallel bugs.

#### Optional Anki

Q: Why is `AtomicInteger` indexing in streams risky?
A: Atomic increments do not guarantee encounter-order indexes.

</details>

<a id="stream-scenario-013"></a>

<details>
<summary><strong>STREAM-SCENARIO-013. A stream transformation is hard to debug. How would you make it maintainable?</strong></summary>

#### Short answer

Name the steps, reduce pipeline length, add focused tests and use a loop if control flow is complex.

#### Interview answer

I would extract predicates and mappers into named methods, split the transformation into meaningful stages, and test edge cases such as empty input, nulls, duplicates and ordering. If debugging still requires mental gymnastics, I would rewrite it as a loop.

#### Deep dive

Temporary `peek` logging can help diagnose, but it should not remain as business logic.

#### Production angle

Maintainability matters during incidents. Clear intermediate names and domain methods make stack traces and logs easier to interpret.

#### Traps / caveats

- Do not keep clever fluent code just because it is shorter.
- Avoid huge nested collector expressions.
- Preserve ordering and laziness when refactoring.

#### Optional Anki

Q: How do you improve a hard-to-debug stream?
A: Extract named steps, test edge cases, or use a clear loop.

</details>

<a id="stream-scenario-014"></a>

<details>
<summary><strong>STREAM-SCENARIO-014. A team uses Stream API for validation and error collection. What design would you propose?</strong></summary>

#### Short answer

Use streams for simple independent validations, but keep complex validation flows explicit.

#### Interview answer

For simple checks, each validator can return `Optional<Error>` or `List<Error>`, then the stream can flatten errors. For complex validations with dependencies, short-circuiting, database checks or transaction rules, use named validation methods or a validation service.

#### Deep dive

Avoid hiding business-critical validation inside dense filters. Validation should explain what failed and where.

#### Production angle

Good validation code needs stable error ordering, context, localization and testability.

#### Traps / caveats

- Do not drop errors silently with `filter`.
- Preserve input indexes when needed.
- Avoid remote/database calls inside simple-looking stream validators.

#### Optional Anki

Q: Stream-friendly validation shape?
A: Validators returning optional or list errors, then flattening results.

</details>

<a id="stream-scenario-015"></a>

<details>
<summary><strong>STREAM-SCENARIO-015. A backend endpoint sorts and filters data in memory instead of SQL. What are the risks?</strong></summary>

#### Short answer

It wastes resources, breaks pagination semantics and ignores database indexes.

#### Interview answer

If the endpoint fetches many rows and then streams them through `filter` and `sorted`, the application pays network, heap and CPU costs. Pagination after in-memory filtering can be wrong because the database did not limit the correct result set.

#### Deep dive

Databases can use indexes, statistics and query plans. Java streams only work after data is fetched.

#### Production angle

Risks include slow endpoints, high GC, database overload from broad queries and inconsistent API results.

#### Traps / caveats

- In-memory sorting large results can exhaust memory.
- Missing `ORDER BY` makes paging unstable.
- Some final business transformations can still belong in Java.

#### Optional Anki

Q: Why is Java-side filtering bad for large DB results?
A: It fetches too much data and bypasses database filtering/indexes.

</details>

<a id="stream-scenario-016"></a>

<details>
<summary><strong>STREAM-SCENARIO-016. A stream pipeline returns different results after switching to parallel(). Why?</strong></summary>

#### Short answer

The pipeline likely relied on ordering, shared state, non-associative reduction or unsafe side effects.

#### Interview answer

Switching to parallel changes execution order and thread use. Different results suggest invalid assumptions: mutable external state, order-dependent `findAny`, non-associative `reduce`, unsafe collector, or lambdas that depend on timing.

#### Deep dive

Correct stream pipelines should usually produce equivalent logical results sequentially and parallel, except where operations explicitly allow nondeterminism such as `findAny`.

#### Production angle

Remove `.parallel()` first to stabilize behavior, then fix the underlying contract before considering parallelism again.

#### Traps / caveats

- Atomic variables may still produce different ordering.
- Hash-based sources may have no stable order.
- Floating-point reductions can differ slightly.

#### Optional Anki

Q: What does changed output after `.parallel()` suggest?
A: Order dependence, shared mutable state or invalid reduction/collector logic.

</details>

<a id="stream-scenario-017"></a>

<details>
<summary><strong>STREAM-SCENARIO-017. A DTO mapping stream triggers LazyInitializationException. What happened?</strong></summary>

#### Short answer

The mapper accessed a lazy JPA association outside an open persistence context.

#### Interview answer

The stream likely maps entities to DTOs and calls a lazy getter after the transaction/session is closed. Since the association was not loaded, the ORM cannot initialize it and throws `LazyInitializationException`.

#### Deep dive

Streams are lazy, so mapping may happen later than the developer expects if the stream was returned from a repository or service.

#### Production angle

Fix by fetching required data within the transaction, using projections, fetch joins, entity graphs or mapping before leaving the persistence boundary.

#### Traps / caveats

- Opening session in view can hide design issues.
- Parallel streams with JPA entities are unsafe.
- DTO mapping should not accidentally query per field.

#### Optional Anki

Q: Why can lazy loading fail in a stream mapper?
A: The stream may execute after the persistence context is closed.

</details>

<a id="stream-scenario-018"></a>

<details>
<summary><strong>STREAM-SCENARIO-018. A pipeline creates high GC pressure. What Stream-specific causes would you check?</strong></summary>

#### Short answer

Check boxing, DTO churn, collectors, grouping, sorting, lambdas and intermediate materialization.

#### Interview answer

I would inspect allocation profiles for boxed primitives, temporary DTOs, string concatenation, `collect(toList())`, `groupingBy`, `sorted`, `distinct`, `flatMap` creating many small streams, and `collect(toList()).stream()` patterns.

#### Deep dive

JIT may optimize some pipelines, but object creation in mappers and collectors can still dominate.

#### Production angle

Fixes include primitive streams, avoiding unnecessary materialization, pushing aggregation to SQL, batching and simplifying transformations.

#### Traps / caveats

- Heap pressure can come from retained entity graphs.
- `groupingBy` can retain many lists.
- Do not guess; use allocation profiling.

#### Optional Anki

Q: Stream operation often causing high retained memory?
A: `groupingBy()` over high-cardinality data.

</details>

<a id="stream-scenario-019"></a>

<details>
<summary><strong>STREAM-SCENARIO-019. How would you decide between Stream API, CompletableFuture and reactive streams?</strong></summary>

#### Short answer

Use Stream for in-memory data transformation, `CompletableFuture` for async task composition, and reactive streams for asynchronous pipelines with backpressure.

#### Interview answer

Stream API is synchronous pull-based data processing. `CompletableFuture` models async completion and composition, often for a bounded number of tasks. Reactive streams model asynchronous event/data pipelines with backpressure, useful for streaming I/O and high-concurrency systems.

#### Deep dive

They solve different problems. Do not use `parallelStream()` as a substitute for explicit async, cancellation, timeout or backpressure design.

#### Production angle

Choose based on workload: CPU transformation, blocking I/O fan-out, streaming responses, message processing, downstream limits and observability needs.

#### Traps / caveats

- Reactive is not automatically faster.
- `CompletableFuture` still needs executor control.
- Stream API has no built-in backpressure.

#### Optional Anki

Q: What is Stream API best for?
A: Synchronous in-memory data transformation.

</details>

<a id="stream-scenario-020"></a>

<details>
<summary><strong>STREAM-SCENARIO-020. What would you expect from a senior-level answer about Stream API?</strong></summary>

#### Short answer

A senior answer connects stream syntax to correctness, performance, resources and production boundaries.

#### Interview answer

I would expect more than `map/filter/collect`. A senior candidate should explain laziness, terminal operations, one-use streams, ordering, collectors, duplicate keys, reduce contracts, side effects, resource-backed streams, primitive streams and why parallel streams require caution.

#### Deep dive

Strong answers include examples: `Files.lines()` needs closing, `toMap` needs duplicate-key policy, JPA mapping can trigger N+1, and `parallelStream()` can hurt web latency.

#### Production angle

The best answer shows judgment: streams are useful, but not for every problem, and not a replacement for SQL, batching, async design or clear imperative code.

#### Traps / caveats

- Syntax-only answers are junior.
- "Parallel is faster" is a weak answer.
- Ignoring resource and transaction boundaries is a red flag.

#### Optional Anki

Q: What distinguishes a senior Stream API answer?
A: It explains production trade-offs, not only syntax.

</details>
