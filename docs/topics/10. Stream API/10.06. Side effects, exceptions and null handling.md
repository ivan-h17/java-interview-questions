# 10.06. Side effects, exceptions and null handling

---

<a id="stream-side-001"></a>

<details>
<summary><strong>STREAM-SIDE-001. Can you modify external state inside stream operations?</strong></summary>

#### Short answer

You can, but it is often a code smell and can be incorrect, especially in parallel streams.

#### Interview answer

Stream lambdas can technically mutate external variables or collections if Java allows the capture pattern. But stream operations are designed around non-interfering, mostly stateless behavior. Mutating external state makes ordering, concurrency and testability harder.

#### Deep dive

The common bad example is `stream.forEach(result::add)`. A collector expresses result accumulation more safely and clearly.

#### Production angle

External mutation causes random missing results, data races, lock contention and hidden side effects during refactoring.

#### Traps / caveats

- "Works sequentially" does not mean correct.
- Synchronizing external mutation can destroy performance.
- Mutating the stream source is worse: it violates non-interference.

#### Optional Anki

Q: Preferred way to build a list from a stream?
A: Use `toList()` or `collect(...)`, not external `forEach(list::add)`.

</details>

<a id="stream-side-002"></a>

<details>
<summary><strong>STREAM-SIDE-002. Why should side effects usually be avoided in stream pipelines?</strong></summary>

#### Short answer

They make stream behavior harder to reason about, optimize, parallelize and test.

#### Interview answer

Stream pipelines work best as transformations from input values to output values. Side effects such as writes, network calls, mutations or auditing introduce hidden behavior. Laziness and short-circuiting mean the side effect may happen later, fewer times than expected, or not at all.

#### Deep dive

Parallel execution adds thread-safety and ordering concerns. Even sequential execution can be unclear when side effects are buried inside `map` or `peek`.

#### Production angle

Keep side effects at explicit boundaries: terminal operations, service methods, batch steps or named commands.

#### Traps / caveats

- `peek()` is not an auditing API.
- `map()` should usually transform, not write.
- Side effects can make retries non-idempotent.

#### Optional Anki

Q: Why avoid side effects in stream pipelines?
A: They interact badly with laziness, short-circuiting, ordering and parallelism.

</details>

<a id="stream-side-003"></a>

<details>
<summary><strong>STREAM-SIDE-003. Why can stateful lambdas break sequential or parallel stream code?</strong></summary>

#### Short answer

They make results depend on mutable state instead of each element independently.

#### Interview answer

A stateful lambda captures and changes data outside the current element, such as a counter, set, list or last-seen value. In parallel streams this can create races. In sequential streams it can still be fragile because changing operation order or adding short-circuiting changes behavior.

#### Deep dive

Some state belongs in a collector, reducer or explicit loop. The Stream API's own stateful operations are controlled internally; user stateful lambdas are not.

#### Production angle

Stateful lambdas are hard to code review because the pipeline no longer shows all dependencies locally.

#### Traps / caveats

- Atomic classes solve only low-level races, not ordering semantics.
- Captured collections can grow unexpectedly.
- Stateful predicates can make repeated runs produce different results.

#### Optional Anki

Q: What is a stateful lambda?
A: A lambda whose result depends on mutable state outside the current element.

</details>

<a id="stream-side-004"></a>

<details>
<summary><strong>STREAM-SIDE-004. Is using AtomicInteger inside a stream pipeline a good way to keep an index?</strong></summary>

#### Short answer

Usually no. It is a workaround that can break ordering assumptions and readability.

#### Interview answer

`AtomicInteger` may make increments thread-safe, but it does not make indexing semantically correct in parallel or unordered streams. The assigned numbers may not match encounter order. Even sequentially, it signals that a loop or indexed range may be clearer.

#### Deep dive

For index-based processing, use `IntStream.range(0, list.size())` when the source supports random access, or a loop when indexing is central to the logic.

#### Production angle

Indexing bugs often appear in CSV imports, validation error positions and response ordering. Make index semantics explicit.

#### Traps / caveats

- `AtomicInteger` can serialize part of the work.
- It can assign nondeterministic indexes in parallel.
- It hides mutable state in a supposedly functional pipeline.

#### Optional Anki

Q: Better alternative for indexed list processing?
A: `IntStream.range(0, list.size())` or a loop.

</details>

<a id="stream-side-005"></a>

<details>
<summary><strong>STREAM-SIDE-005. How do you collect results without mutating external state?</strong></summary>

#### Short answer

Use terminal operations such as `toList()`, `collect()`, `reduce()` or built-in collectors.

#### Interview answer

Instead of creating a list and adding to it in `forEach`, return the result from the pipeline: `stream.map(...).toList()`. For maps, use `toMap`. For grouping, use `groupingBy`. For custom accumulation, use a collector or a clear loop.

#### Deep dive

The collector pattern lets the stream framework manage accumulators and merge partial results correctly.

#### Production angle

This makes code easier to parallelize, test and refactor because result construction is explicit in the terminal operation.

#### Traps / caveats

- Do not use `reduce` with mutable containers.
- Choose duplicate-key behavior for maps.
- Watch memory when collecting large streams.

#### Optional Anki

Q: What replaces external list mutation in a stream?
A: `toList()` or `collect(Collectors.toList())`.

</details>

<a id="stream-side-006"></a>

<details>
<summary><strong>STREAM-SIDE-006. When are side effects acceptable in stream code?</strong></summary>

#### Short answer

When they are explicit, controlled, ordered if needed, and not hidden in intermediate transformations.

#### Interview answer

Some terminal operations exist for side effects, especially `forEach`. Writing each line to a file, sending a result to a sink or logging at a clear boundary can be acceptable. The key is that side effects should be intentional and safe for the chosen execution mode.

#### Deep dive

If side effects require transactions, retries, idempotency or error handling, a loop or explicit workflow is often clearer than a stream.

#### Production angle

Side effects must be observable and controllable: metrics, retries, failure handling and ordering should be designed, not incidental.

#### Traps / caveats

- Avoid side effects in `map`, `filter` and `peek`.
- Do not use parallel streams for unordered writes unless safe.
- Consider what happens after partial failure.

#### Optional Anki

Q: Where are stream side effects least surprising?
A: In an explicit terminal boundary, such as controlled `forEach`.

</details>

<a id="stream-side-007"></a>

<details>
<summary><strong>STREAM-SIDE-007. Can a lambda be invoked fewer times or in a different order than expected?</strong></summary>

#### Short answer

Yes. Laziness, short-circuiting, optimization and parallel execution can change invocation count or order.

#### Interview answer

`findFirst`, `anyMatch`, `limit` and `takeWhile` may stop early. Some pipelines can avoid operations whose results are not needed. Parallel streams can invoke lambdas on different threads and in a different order than the pipeline text suggests.

#### Deep dive

The Stream API specifies results, not a simple statement-by-statement execution trace for every lambda.

#### Production angle

Required behavior such as validation, auditing or database writes should not depend on "this lambda will run once for every element" unless the terminal operation and pipeline guarantee that.

#### Traps / caveats

- `peek` output is not a reliable execution trace.
- Matching operations short-circuit.
- Parallel evaluation order can differ from result order.

#### Optional Anki

Q: Why can a stream lambda run fewer times than elements?
A: Short-circuiting or optimization can stop or skip work.

</details>

<a id="stream-side-008"></a>

<details>
<summary><strong>STREAM-SIDE-008. How do transactions interact with stream pipelines that perform side effects?</strong></summary>

#### Short answer

Side effects inside streams must run inside a clear transaction boundary, or failures can leave partial work.

#### Interview answer

If a stream writes to a database, publishes events or modifies entities, transaction behavior must be explicit. Lazy execution means the work happens at terminal operation time. Parallel execution can break assumptions about thread-bound transactions and persistence contexts.

#### Deep dive

Spring transactions are commonly thread-bound. Work moved to other threads by parallel streams does not automatically share the same transaction context.

#### Production angle

For transactional workflows, prefer explicit service logic, batch processing or loops with clear rollback, retry and idempotency rules.

#### Traps / caveats

- Exceptions halfway through a stream can leave external side effects already performed.
- Parallel streams and JPA persistence contexts are a poor mix.
- Auditing in `peek()` is especially dangerous.

#### Optional Anki

Q: Why are parallel streams risky inside Spring transactions?
A: Transaction context is often thread-bound and not automatically propagated.

</details>

<a id="stream-side-009"></a>

<details>
<summary><strong>STREAM-SIDE-009. How do you avoid ConcurrentModificationException when streaming collections?</strong></summary>

#### Short answer

Do not structurally modify the source while streaming it.

#### Interview answer

If you need removal, use collection APIs such as `removeIf`, collect elements to remove and apply changes afterward, or use an iterator where appropriate. If multiple threads access the collection, define synchronization or use a concurrent collection with understood semantics.

#### Deep dive

`ConcurrentModificationException` is fail-fast behavior for many collections. It detects bugs but is not guaranteed in every race.

#### Production angle

Source mutation during streaming often appears in cleanup jobs, cache maintenance and request filtering. Keep traversal and mutation phases separate.

#### Traps / caveats

- `list.stream().forEach(list::remove)` is wrong.
- Concurrent collections may not throw but can produce weakly consistent results.
- Mutating element fields is different from structural source mutation but can still be risky.

#### Optional Anki

Q: Safe method for removing list elements by predicate?
A: `removeIf(predicate)`.

</details>

<a id="stream-side-010"></a>

<details>
<summary><strong>STREAM-SIDE-010. Why is mutating stream elements risky?</strong></summary>

#### Short answer

It mixes transformation with side effects and can break equality, caching, persistence or concurrency assumptions.

#### Interview answer

Changing objects inside `map`, `peek` or `forEach` may seem convenient, but it means the stream does not produce new values; it mutates existing ones. If those objects are shared, cached, used as map keys or managed by JPA, mutation can have broad side effects.

#### Deep dive

Mutation is especially dangerous before `distinct`, grouping, sorting or map collection if equality or comparator-relevant fields change.

#### Production angle

Prefer mapping entities to DTOs or creating new value objects. Use explicit domain methods when mutation is the business operation.

#### Traps / caveats

- Mutating `HashMap` keys can make entries unreachable.
- JPA dirty checking may persist changes unexpectedly.
- Parallel mutation needs thread-safety and ownership.

#### Optional Anki

Q: Safer alternative to mutating elements in `map()`?
A: Return new DTOs or values from `map()`.

</details>

<a id="stream-side-011"></a>

<details>
<summary><strong>STREAM-SIDE-011. Why must local variables captured by stream lambdas be effectively final?</strong></summary>

#### Short answer

Java lambdas can capture local variables only when those variables are final or effectively final.

#### Interview answer

A local variable is effectively final when it is assigned once and not changed afterward. Stream lambdas can read such variables, but cannot capture a local variable that is later reassigned. This avoids unclear mutable state and lifetime problems around local stack variables.

For example, `prefix` can be captured if it is not reassigned before or after the lambda. A local `counter++` inside `forEach` does not compile because the lambda would need to mutate a captured local variable.

#### Deep dive

The restriction is about the local variable reference, not the object behind it. A lambda can call methods on a captured mutable object, such as `list.add(...)` or `atomic.incrementAndGet()`, because the local reference is still effectively final. That does not make the code a good stream design: mutating captured objects creates side effects and can break badly in parallel streams.

#### Production angle

When a developer reaches for a one-element array, `AtomicInteger` or external list to bypass the rule, review the pipeline carefully. Usually the right answer is `map`, `filter`, `collect`, `reduce`, `count`, an indexed loop or `IntStream.range`.

#### Traps / caveats

- `final` is not required syntactically; "effectively final" is enough.
- Capturing a mutable object can compile while still being unsafe.
- `AtomicInteger` gives atomic increments, not correct encounter-order indexing.

#### Optional Anki

Q: What does effectively final mean for a captured local variable?
A: It is assigned once and not reassigned after that.

</details>

<a id="stream-err-001"></a>

<details>
<summary><strong>STREAM-ERR-001. Can a Stream contain null elements, and should it?</strong></summary>

#### Short answer

Object streams can contain nulls, but they usually should not.

#### Interview answer

The Stream API does not globally forbid null elements. However, many operations become fragile: method references throw `NullPointerException`, `findFirst` cannot return a null value in an `Optional`, and unmodifiable collectors reject nulls.

#### Deep dive

Prefer null-free streams. Use `filter(Objects::nonNull)`, `Stream.ofNullable`, validation or domain defaults.

#### Production angle

Null filtering should be intentional. If null indicates corrupt data, fail fast or record a validation error instead of silently dropping it.

#### Traps / caveats

- Do not use `Stream.of(null)` to handle nullable values; use `Stream.ofNullable(value)`.
- `Stream.of((Object) null)` creates one null element, but null-free streams are usually clearer.
- `Optional` should not be null.
- Primitive streams cannot contain null.

#### Optional Anki

Q: Can `Stream<T>` contain null?
A: Technically yes, but it is usually a bad idea.

</details>

<a id="stream-err-002"></a>

<details>
<summary><strong>STREAM-ERR-002. How should checked exceptions be handled inside stream lambdas?</strong></summary>

#### Short answer

Handle them explicitly, wrap them carefully, or move exception-heavy logic out of the stream.

#### Interview answer

Standard stream functional interfaces do not declare checked exceptions. Options include catching inside the lambda, calling a helper that wraps exceptions in a domain/runtime exception, or using a loop when error handling is central.

#### Deep dive

Generic "sneaky throw" helpers can make code obscure. Wrapping should preserve cause and context, such as filename, line number or record ID.

#### Production angle

Good exception handling needs observability and recoverability. A compact stream chain should not hide which element failed.

#### Traps / caveats

- Do not swallow exceptions inside lambdas.
- Avoid wrapping everything as a generic `RuntimeException` without context.
- Partial side effects may already have happened.

#### Optional Anki

Q: Why are checked exceptions awkward in streams?
A: Standard stream functional interfaces do not declare checked exceptions.

</details>

<a id="stream-err-003"></a>

<details>
<summary><strong>STREAM-ERR-003. How do exceptions behave in parallel streams?</strong></summary>

#### Short answer

An exception from a worker fails the terminal operation, but other work may already be running or completed.

#### Interview answer

If a lambda throws, the terminal operation propagates an exception to the caller. In parallel streams, multiple tasks may be active, so side effects from other elements may already have occurred. The exact failing element can be harder to identify.

#### Deep dive

Parallel execution can wrap or suppress details depending on where the exception occurs. Preserve context inside exceptions.

#### Production angle

Avoid non-idempotent side effects inside parallel streams. For batch processing, design explicit error collection or fail-fast behavior.

#### Traps / caveats

- Do not assume no other element was processed after the first failure.
- Logs may appear from multiple threads.
- Debugging stack traces can be less direct.

#### Optional Anki

Q: What is a key exception risk in parallel streams?
A: Other tasks and side effects may already have happened when one task fails.

</details>

<a id="stream-err-004"></a>

<details>
<summary><strong>STREAM-ERR-004. How do you close resources created inside a stream pipeline?</strong></summary>

#### Short answer

Prefer creating and closing resources outside the pipeline or use try-with-resources inside a clearly scoped helper.

#### Interview answer

Do not casually open resources in `map()` and hope the stream cleans them up. If each element needs a resource, use a helper method with try-with-resources. If the stream itself owns a resource, wrap the whole stream in try-with-resources.

#### Deep dive

For nested resource-backed streams, `flatMap` can be tricky because inner streams need closing. Often a loop is clearer.

#### Production angle

Resource leaks inside pipelines can exhaust file descriptors, sockets or database connections under load.

#### Traps / caveats

- Closing the outer stream does not automatically close arbitrary resources opened inside lambdas.
- Short-circuiting can skip cleanup if it is not scoped correctly.
- Avoid long-lived resources in parallel lambdas.

#### Optional Anki

Q: Safest pattern for a resource-backed stream?
A: try-with-resources around stream creation and terminal consumption.

</details>

<a id="stream-err-005"></a>

<details>
<summary><strong>STREAM-ERR-005. When should exception-heavy stream code be rewritten as a loop?</strong></summary>

#### Short answer

When error handling is central to the algorithm or needs per-element control flow.

#### Interview answer

Use a loop when each element needs try/catch, retries, fallback, error accumulation, metrics, cleanup or different branches after failure. A stream with nested try/catch blocks in lambdas is usually harder to read than a straightforward loop.

#### Deep dive

Streams are strongest for transformations. Complex operational workflows often benefit from imperative structure.

#### Production angle

Clear failure handling matters in imports, migrations, messaging consumers and batch jobs. A loop can make partial failure policy obvious.

#### Traps / caveats

- Do not hide failures by returning null or empty optional everywhere.
- Avoid generic wrappers that erase business context.
- Keep stream pipelines boring when reliability matters.

#### Optional Anki

Q: When is a loop better than a stream for exceptions?
A: When per-element failure handling is part of the main logic.

</details>
