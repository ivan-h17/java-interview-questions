# 10.02. Stream sources, lifecycle and resource boundaries

---

<a id="stream-src-001"></a>

<details>
<summary><strong>STREAM-SRC-001. How can you create streams from collections, arrays and explicit values?</strong></summary>

#### Short answer

Use `collection.stream()`, `Arrays.stream(array)` or `Stream.of(values)`.

#### Interview answer

The common sources are collections, arrays and explicit values. A `Collection` exposes `stream()` and `parallelStream()`. Arrays can use `Arrays.stream(array)`. A few known values can be wrapped with `Stream.of(a, b, c)`, and an empty stream with `Stream.empty()`.

#### Deep dive

Primitive arrays have primitive stream overloads, such as `Arrays.stream(int[])` returning `IntStream`. Object arrays produce `Stream<T>`.

#### Production angle

Use the source that communicates ownership. If data is already materialized in a collection, streaming it is fine. If the source is I/O or database-backed, lifecycle and closing matter.

#### Traps / caveats

- `Stream.of(array)` with an object array streams its elements, but with primitive arrays it produces one element: the array object.
- `parallelStream()` changes execution semantics.
- A stream created from a mutable collection can observe later changes before terminal execution.

#### Optional Anki

Q: How do you create a stream from a collection?
A: `collection.stream()`.

</details>

<a id="stream-src-002"></a>

<details>
<summary><strong>STREAM-SRC-002. How do Stream.generate() and Stream.iterate() differ?</strong></summary>

#### Short answer

`generate()` repeatedly calls a supplier. `iterate()` repeatedly applies a function to the previous value.

#### Interview answer

`Stream.generate(supplier)` creates values independently, often for random or constant data. `Stream.iterate(seed, next)` starts with a seed and derives each next element from the previous one. The three-argument `iterate(seed, hasNext, next)` adds a stopping predicate.

#### Deep dive

Both can create infinite streams. Infinite streams must be bounded by operations such as `limit`, `takeWhile` or a finite `iterate` predicate.

#### Production angle

Infinite streams are useful for controlled generation, polling-like logic or tests, but they are dangerous if collected or sorted without a bound.

#### Traps / caveats

- `generate()` has no natural ordering relationship between values.
- `iterate()` can be harder to parallelize well.
- `toList()` on an unbounded stream never finishes or exhausts memory.

#### Optional Anki

Q: Main difference between `generate()` and `iterate()`?
A: `generate()` uses a supplier; `iterate()` derives each value from the previous one.

</details>

<a id="stream-src-003"></a>

<details>
<summary><strong>STREAM-SRC-003. What is the difference between Stream<Integer> and IntStream?</strong></summary>

#### Short answer

`Stream<Integer>` contains boxed objects. `IntStream` processes primitive `int` values.

#### Interview answer

`Stream<Integer>` stores references to `Integer` objects and may involve boxing and unboxing. `IntStream` avoids that overhead and provides numeric operations such as `sum`, `average`, `min`, `max` and `summaryStatistics`.

Use primitive streams for numeric-heavy pipelines.

#### Deep dive

Primitive stream types are `IntStream`, `LongStream` and `DoubleStream`. You can convert with `mapToInt`, `boxed` and `mapToObj`.

#### Production angle

For small lists, the difference rarely matters. For millions of IDs, counters or measurements, boxing can add CPU, memory and GC pressure.

#### Traps / caveats

- Primitive streams are less generic and support fewer object-style operations.
- `OptionalInt` is different from `Optional<Integer>`.
- Boxed null values fail during unboxing.

#### Optional Anki

Q: Why use `IntStream`?
A: To avoid boxing and use primitive numeric operations.

</details>

<a id="stream-src-004"></a>

<details>
<summary><strong>STREAM-SRC-004. How do you create streams from nullable values and Optional?</strong></summary>

#### Short answer

Use `Stream.ofNullable(value)` for nullable values and `optional.stream()` for `Optional`.

#### Interview answer

`Stream.ofNullable(value)` returns a one-element stream if the value is non-null, otherwise an empty stream. `Optional.stream()` returns a one-element stream when present, otherwise empty. These APIs are useful when flattening optional values into a larger pipeline.

#### Deep dive

Before these APIs, code often used ternary expressions or `filter(Optional::isPresent).map(Optional::get)`. `flatMap(Optional::stream)` is cleaner and avoids `get()`.

#### Production angle

This helps normalize "zero or one" values without null checks scattered through mapping code.

#### Traps / caveats

- Do not use `Stream.of(null)` for nullable values. Use `Stream.ofNullable(value)` instead.
- `Stream.of((Object) null)` creates one null element, but that is rarely useful.
- `Optional` itself should not be null.
- Do not use `Optional` fields just to make stream code convenient.

#### Optional Anki

Q: How do you flatten a stream of optionals?
A: `stream.flatMap(Optional::stream)`.

</details>

<a id="stream-src-005"></a>

<details>
<summary><strong>STREAM-SRC-005. Which streams should be closed, and why?</strong></summary>

#### Short answer

Close streams backed by resources such as files, sockets, database cursors or I/O channels.

#### Interview answer

Most collection streams do not need closing. Resource-backed streams do. For example, `Files.lines(path)` opens a file and returns a stream that must be closed. Repository streams may hold a JDBC result set, connection or persistence context.

Use try-with-resources when the stream owns something outside memory.

#### Deep dive

`Stream` extends `BaseStream`, which extends `AutoCloseable`. Closing invokes registered close handlers.

#### Production angle

Leaks show up as open file descriptor exhaustion, stuck database connections, long transactions or memory retained by open cursors.

#### Traps / caveats

- `list.stream()` does not need try-with-resources.
- Resource streams can leak when returned across layers.
- Short-circuiting still requires closing the stream.

#### Optional Anki

Q: Which stream commonly needs try-with-resources?
A: `Files.lines(path)`.

</details>

<a id="stream-src-006"></a>

<details>
<summary><strong>STREAM-SRC-006. Why should Files.lines() usually be used with try-with-resources?</strong></summary>

#### Short answer

Because `Files.lines()` opens a file-backed stream that must be closed.

#### Interview answer

`Files.lines(path)` lazily reads lines from a file. That is efficient, but the stream holds an open file resource. try-with-resources ensures the file is closed whether the pipeline completes normally, short-circuits or throws.

#### Deep dive

The terminal operation drives reading, but closing is separate. If you return the stream and the caller forgets to close it, the file descriptor can remain open.

#### Production angle

In batch jobs and import workers, leaking line streams can eventually fail unrelated file operations with "too many open files."

#### Traps / caveats

- `readAllLines()` closes the file but materializes all lines.
- `Files.lines()` is lazy but needs lifecycle management.
- Do not store the stream for later outside the resource scope.

#### Optional Anki

Q: Why does `Files.lines()` need closing?
A: It holds an open file resource while the stream is consumed.

</details>

<a id="stream-src-007"></a>

<details>
<summary><strong>STREAM-SRC-007. What risks appear when streaming over a mutable collection?</strong></summary>

#### Short answer

The stream may observe inconsistent state or fail if the collection is modified during execution.

#### Interview answer

Streams over mutable collections are fine if the collection is stable during pipeline execution. Problems appear when another thread or the pipeline itself mutates the source. This can cause `ConcurrentModificationException`, missed elements, duplicated elements or nondeterministic results.

#### Deep dive

Streams are lazy, so changes made after creating the stream but before the terminal operation may be visible. The exact behavior depends on the source and its spliterator.

#### Production angle

Take a snapshot, synchronize ownership, use immutable data or use concurrent collections deliberately when shared mutation is unavoidable.

#### Traps / caveats

- `final List<T>` does not mean immutable list.
- Concurrent collections have different consistency semantics.
- Parallel streams make source mutation bugs more visible.

#### Optional Anki

Q: Safe rule for mutable stream sources?
A: Do not mutate the source while the stream pipeline is executing.

</details>

<a id="stream-src-008"></a>

<details>
<summary><strong>STREAM-SRC-008. What happens if the source is modified during stream execution?</strong></summary>

#### Short answer

It violates non-interference; results become unpredictable and may throw `ConcurrentModificationException`.

#### Interview answer

For most non-concurrent collections, modifying the source while streaming violates non-interference. The stream may fail fast, produce inconsistent results or appear to work until a data size or timing change exposes the bug.

#### Deep dive

Fail-fast behavior is a best-effort bug detector, not a correctness guarantee. Concurrent sources such as `ConcurrentHashMap` have spliterators designed for concurrent access, but their semantics are weakly consistent.

#### Production angle

This often happens during cleanup code like `list.stream().filter(...).forEach(list::remove)`. Use `removeIf`, collect IDs to remove, or iterate with the proper owner.

#### Traps / caveats

- Sequential execution does not make source mutation correct.
- Parallel execution can turn rare bugs into frequent bugs.
- Mutating a different collection can still be a side effect, but not source interference.

#### Optional Anki

Q: What rule is violated by modifying the stream source?
A: Non-interference.

</details>

<a id="stream-src-009"></a>

<details>
<summary><strong>STREAM-SRC-009. What is StreamSupport.stream(), and when is it useful?</strong></summary>

#### Short answer

`StreamSupport.stream()` creates a stream from a `Spliterator` or spliterator supplier.

#### Interview answer

It is the low-level bridge for custom sources. If you have a domain-specific cursor, tree, paging iterator or generated source, you can expose a `Spliterator` and turn it into a sequential or parallel stream with `StreamSupport.stream(...)`.

#### Deep dive

The quality of the `Spliterator` matters. Accurate size, splitting and characteristics help the Stream implementation optimize, especially in parallel.

#### Production angle

Use it when a stream is a natural consumption API over a custom source, but be explicit about resource ownership and close behavior.

#### Traps / caveats

- A poor spliterator can make parallel streams slower or wrong.
- Characteristics must be truthful.
- A stream wrapper does not automatically solve backpressure or resource cleanup.

#### Optional Anki

Q: What API creates a Stream from a Spliterator?
A: `StreamSupport.stream(...)`.

</details>

<a id="stream-src-010"></a>

<details>
<summary><strong>🧠 STREAM-SRC-010. When would you implement a custom stream source?</strong></summary>

#### Short answer

Only when a custom data source benefits from lazy, stream-like traversal and existing adapters are not enough.

#### Interview answer

Examples include traversing a custom tree, wrapping a cursor-like source, streaming generated records or exposing chunks from a proprietary file format. You usually implement a `Spliterator`, then use `StreamSupport.stream()`.

#### Deep dive

A custom source must define traversal, ordering, size estimation, splitting and closing behavior. If parallelism matters, `trySplit()` must divide work efficiently.

#### Production angle

Custom stream sources are library-level code. They need tests for empty, single, large, short-circuiting, close and parallel scenarios.

#### Traps / caveats

- Do not implement a custom stream source just to avoid writing an iterator.
- Incorrect `SIZED`, `ORDERED` or `NONNULL` flags can break assumptions.
- Resource-backed sources need clear ownership.

#### Optional Anki

Q: What is the usual basis for a custom stream source?
A: A custom `Spliterator`.

</details>

<a id="stream-src-011"></a>

<details>
<summary><strong>STREAM-SRC-011. How should APIs that return Stream be designed?</strong></summary>

#### Short answer

Return `Stream` only when one-shot lazy consumption is intentional and lifecycle rules are clear.

#### Interview answer

For ordinary data, returning `List`, `Set`, `Collection`, `Page` or an iterator-like abstraction is often safer. Returning `Stream` exposes a one-time pipeline and pushes terminal-operation choice to the caller.

If the stream is resource-backed, document that the caller must close it or keep consumption inside the method.

#### Deep dive

An alternative is `Supplier<Stream<T>>` when repeated fresh streams are needed. For database data, a callback style can keep transaction and connection ownership local.

#### Production angle

Bad stream-returning APIs commonly leak database resources or fail when the caller consumes the stream outside a transaction.

#### Traps / caveats

- Do not return a stream created inside a closed try-with-resources block.
- Do not expose streams in REST DTOs.
- Do not cache a stream for reuse.

#### Optional Anki

Q: When is returning `Stream` risky?
A: When the caller cannot clearly manage one-shot use and resource closing.

</details>

<a id="stream-src-012"></a>

<details>
<summary><strong>STREAM-SRC-012. Why can returning Stream from a repository method be dangerous?</strong></summary>

#### Short answer

The stream may depend on an open transaction, JDBC connection, result set or persistence context.

#### Interview answer

Repository streams often represent lazy database access. If the method returns a stream and the transaction closes before the caller consumes it, you may get failures such as closed result sets or lazy-loading exceptions. If the transaction stays open too long, it can hold locks, connections and memory.

#### Deep dive

JPA and JDBC streaming behavior depends on provider, driver, fetch size and transaction settings. It is not just a Java Stream concern.

#### Production angle

Prefer consuming the stream within a controlled transaction boundary, using pagination, batching, callbacks or explicit cursor management.

#### Traps / caveats

- A stream is lazy; the query may not be fully consumed at repository return time.
- Mapping entities inside the stream can trigger lazy loads.
- Closing must happen on every path, including exceptions.

#### Optional Anki

Q: Main risk of repository methods returning `Stream`?
A: The stream may outlive the database resources or transaction it needs.

</details>

<a id="stream-src-013"></a>

<details>
<summary><strong>STREAM-SRC-013. How should a finite stream differ from an infinite stream in API design?</strong></summary>

#### Short answer

A finite stream has a known or naturally ending source; an infinite stream must require or document a bound.

#### Interview answer

Finite streams are typical for collections, files and query results. Infinite streams come from generators, iterative sequences or open-ended event-like sources. APIs that expose infinite streams must make termination explicit through `limit`, `takeWhile`, cancellation or another boundary.

#### Deep dive

Many terminal operations on infinite streams never complete, such as `toList`, `count` or `sorted`.

#### Production angle

Unbounded streams can create CPU loops, memory growth and stuck requests. Backend APIs should enforce limits near the source.

#### Traps / caveats

- `filter()` does not make an infinite stream finite.
- `findFirst()` may finish only if a match appears.
- `sorted()` on an infinite stream cannot produce a result.

#### Optional Anki

Q: What must an infinite stream have in production code?
A: A clear bound or cancellation condition.

</details>

<a id="stream-src-014"></a>

<details>
<summary><strong>STREAM-SRC-014. What are the caveats of Stream.concat()?</strong></summary>

#### Short answer

`Stream.concat()` lazily appends two streams, but both are consumed and deep concatenation can be problematic.

#### Interview answer

`Stream.concat(a, b)` creates a stream that traverses `a` then `b`. It preserves ordering if the inputs are ordered. It is useful for combining two simple streams, but chaining many `concat` calls can produce deep pipelines and poor readability.

#### Deep dive

Both input streams are consumed when the concatenated stream is consumed. Closing the concatenated stream closes both input streams.

#### Production angle

For many sources, prefer `Stream.of(streams...).flatMap(Function.identity())` or collect source collections first if lifecycle is simple.

#### Traps / caveats

- Do not reuse input streams after concatenation is consumed.
- Be careful when either input is resource-backed.
- Infinite first stream means the second stream is never reached.

#### Optional Anki

Q: What does `Stream.concat(a, b)` do?
A: It creates a stream that traverses `a` and then `b`.

</details>

<a id="stream-src-015"></a>

<details>
<summary><strong>STREAM-SRC-015. How should large file or database streams be bounded in production?</strong></summary>

#### Short answer

Use explicit limits, batching, pagination, backpressure-aware designs or controlled resource scopes.

#### Interview answer

Large streams should not be casually collected into memory. File processing should close resources and process incrementally. Database processing should use pagination, fetch-size tuning, batching or cursor APIs within a clear transaction boundary.

#### Deep dive

Streams are pull-based and do not provide full backpressure semantics like reactive streams. A slow consumer or expensive mapper can still hold resources for a long time.

#### Production angle

Protect endpoints and jobs with maximum row counts, timeouts, cancellation handling, metrics and memory-aware processing.

#### Traps / caveats

- `toList()` defeats streaming by materializing everything.
- Sorting/grouping may buffer all data.
- Long database streams can hold connections and snapshots.

#### Optional Anki

Q: What is the main danger of large streams?
A: Accidentally holding too much data or too many resources for too long.

</details>
