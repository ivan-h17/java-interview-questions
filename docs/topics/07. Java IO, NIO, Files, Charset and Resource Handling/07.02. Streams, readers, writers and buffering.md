# 07.02. Streams, readers, writers and buffering

---

<a id="jio-stream-001"></a>

<details>
<summary><strong>JIO-STREAM-001. How does the Java I/O decorator model work with wrappers like `BufferedInputStream`, `InputStreamReader` and `GZIPInputStream`?</strong></summary>

#### Short answer

Java I/O wrappers add behavior around another stream or reader: buffering, decoding, compression, encryption, counting or filtering.

#### Interview answer

Classic Java I/O uses the Decorator pattern heavily. A base stream provides bytes from a file, socket or memory. Wrappers add behavior without changing the underlying source. For example, `BufferedInputStream` reduces small system calls, `GZIPInputStream` decompresses bytes, and `InputStreamReader` decodes bytes into characters.

The order matters because each wrapper transforms what the next layer sees.

#### Deep dive

A common text pipeline is `Files.newInputStream(path)` -> `BufferedInputStream` -> `InputStreamReader` with UTF-8 -> `BufferedReader`. A compressed text file might require `GZIPInputStream` before the reader layer.

#### Production angle

Understanding wrapper order helps debug corrupted data, slow I/O and resource leaks. It also makes ownership clear: closing the outermost wrapper normally closes the wrapped resource chain.

#### Traps / caveats

- Do not decode compressed bytes before decompression.
- Do not wrap binary data in text readers unless it is actually encoded text.
- Closing the wrong layer too early can break callers that still own the stream.

#### Optional Anki

Q: What pattern is common in Java I/O stream wrappers?
A: Decorator.

</details>

<a id="jio-stream-002"></a>

<details>
<summary><strong>JIO-STREAM-002. Why should binary data not be processed through `Reader` or `Writer`?</strong></summary>

#### Short answer

`Reader` and `Writer` treat bytes as encoded text, so arbitrary binary data can be corrupted by decoding or encoding.

#### Interview answer

Binary data is just bytes. A `Reader` converts bytes into characters using a charset, and a `Writer` converts characters back into bytes. That process is not reversible for arbitrary binary payloads. Invalid byte sequences may be replaced, normalized or rejected depending on the decoder.

For images, PDFs, ZIP files, encrypted data, hashes and signatures, use byte streams or channels.

#### Deep dive

Text APIs may also change line endings, buffer partial characters, or lose exact byte representation. This is fine for text processing but wrong when exact bytes matter.

#### Production angle

This bug shows up as broken downloads, corrupted archives, invalid digital signatures, failed checksum validation or files that open locally but fail after passing through a service.

#### Traps / caveats

- Base64 text is text, but the decoded payload is binary.
- JSON strings are text; attached files are often binary.
- `String` is not a safe container for arbitrary bytes.

#### Optional Anki

Q: Why not store arbitrary binary data in a `String`?
A: Decoding and re-encoding can corrupt bytes.

</details>

<a id="jio-stream-003"></a>

<details>
<summary><strong>JIO-STREAM-003. What does buffering solve in Java I/O?</strong></summary>

#### Short answer

Buffering reduces many small reads or writes into fewer larger operations and can improve throughput.

#### Interview answer

Without buffering, code that reads or writes one byte, character or line at a time may cause many expensive calls into the operating system or underlying stream. A buffer stores a chunk in memory so application code can consume small pieces while the underlying I/O happens in larger blocks.

`BufferedInputStream`, `BufferedOutputStream`, `BufferedReader` and `BufferedWriter` are common wrappers for this.

#### Deep dive

Buffering does not make slow storage or a slow network fast; it reduces overhead when the access pattern is small and repetitive. Buffer size should be reasonable and sometimes tuned based on payload size and throughput measurements.

#### Production angle

Missing buffering can create unnecessary latency and CPU overhead in imports, exports and proxying. Excessive buffering can increase memory usage, especially with many concurrent requests.

#### Traps / caveats

- Buffered output may not be visible until `flush()` or `close()`.
- More buffering is not always better.
- Frameworks may already buffer, so adding another layer may not help.

#### Optional Anki

Q: What is the main benefit of buffering?
A: Fewer underlying I/O operations for small repeated reads or writes.

</details>

<a id="jio-stream-004"></a>

<details>
<summary><strong>JIO-STREAM-004. What is the difference between `flush()` and `close()`?</strong></summary>

#### Short answer

`flush()` pushes buffered output without releasing the resource. `close()` releases the resource and usually flushes first.

#### Interview answer

`flush()` is used on output abstractions to force buffered data to be written to the next layer. The stream remains usable afterward. `close()` ends the resource lifecycle. It releases file descriptors, sockets or other resources and usually flushes pending output before closing.

Use `flush()` when data must be sent before the stream is closed, for example interactive protocols or long responses. Use `close()` when ownership ends.

#### Deep dive

`flush()` does not necessarily mean data is durable on disk or received by the peer. It often means data moved from a Java buffer to the next OS or library layer. Durability may require file-system specific syncing such as `FileChannel.force()`.

#### Production angle

Missing `close()` causes leaks. Missing or misplaced `flush()` can delay responses, logs or protocol messages. Assuming `flush()` means durable storage can cause data-loss bugs.

#### Traps / caveats

- Do not use `flush()` as a substitute for `close()`.
- `close()` can throw; try-with-resources handles this cleanly.
- `flush()` on a wrapper may flush only to the wrapped stream.

#### Optional Anki

Q: Does `flush()` close a stream?
A: No. It pushes buffered output but keeps the stream open.

</details>

<a id="jio-stream-005"></a>

<details>
<summary><strong>JIO-STREAM-005. Why should code not assume that one `read()` call fills the entire buffer?</strong></summary>

#### Short answer

`read()` returns however many bytes or characters are currently available, which may be less than the buffer size.

#### Interview answer

The contract of `read(buffer)` is not "fill this buffer". It returns the number of bytes or characters actually read, or `-1` at end of stream. Network packets, file boundaries, buffering, compression and OS behavior can all produce partial reads.

Correct code loops until it has enough data, reaches EOF, or meets a protocol/record boundary.

#### Deep dive

This is especially important for fixed-size protocol headers, binary formats and file copy loops. The caller must use the returned count and should not process stale bytes left in the buffer from previous iterations.

#### Production angle

Incorrect read loops cause truncated uploads, corrupted protocol frames, flaky tests and bugs that appear only under load or on slower networks.

#### Traps / caveats

- Always check the integer returned by `read()`.
- A buffer can contain old data beyond the returned count.
- `available()` is not a reliable total-size indicator.

#### Optional Anki

Q: What does `InputStream.read(byte[])` return?
A: The number of bytes read, or `-1` at EOF.

</details>

<a id="jio-stream-006"></a>

<details>
<summary><strong>JIO-STREAM-006. Why can `readAllBytes()`, `readAllLines()` or `readString()` be dangerous for large inputs?</strong></summary>

#### Short answer

They load the whole input into memory, which can cause high allocation, GC pressure or `OutOfMemoryError`.

#### Interview answer

These methods are convenient when the input is small and bounded. They are risky for user uploads, large files, object-storage downloads, logs and exports because the entire content must fit in memory at once.

In backend services, prefer streaming, chunked copying or record-by-record parsing for large or untrusted inputs. Pair that with maximum size limits.

#### Deep dive

The memory impact is often worse than the raw file size. Text decoding, line lists, strings and intermediate arrays can multiply peak memory. For CSV or JSON, parsing may allocate additional objects on top of the loaded content.

#### Production angle

These methods are common root causes of memory spikes during imports and downloads. They also make backpressure harder because the service accepts all data before processing it.

#### Traps / caveats

- "Works in tests" usually means the test file was tiny.
- Streaming still needs timeout and size enforcement.
- Some files are small enough that convenience methods are acceptable.

#### Optional Anki

Q: What is the main risk of `readAllBytes()` on request input?
A: Unbounded memory consumption.

</details>

<a id="jio-stream-007"></a>

<details>
<summary><strong>JIO-STREAM-007. How should backend code copy data between request bodies, files, object storage and HTTP responses?</strong></summary>

#### Short answer

Copy data as a stream in bounded chunks, preserve bytes when the payload is binary, close owned resources, and enforce limits/timeouts.

#### Interview answer

For large or binary payloads, backend code should avoid loading the whole content into a byte array or `String`. Use stream copying such as `InputStream.transferTo()`, framework streaming APIs, object-storage streaming clients or chunked loops with a fixed buffer.

Also define ownership: who opens and closes the source and destination. Add size limits, content validation, timeouts and error handling for partial writes.

#### Deep dive

For simple file-to-file copies, `Files.copy()` may be enough. For HTTP responses, the framework may provide a streaming response abstraction. For object storage, prefer APIs that stream and expose content length or metadata when available.

#### Production angle

Good copy design prevents memory spikes, slow-client pileups and leaked file descriptors. It also makes cancellation and retry behavior explicit.

#### Traps / caveats

- Do not convert binary payloads through text APIs.
- Do not trust client-provided content length alone.
- Streaming a response may still tie up request resources while the client is slow.

#### Optional Anki

Q: What is the safe default for large file transfers?
A: Stream in bounded chunks instead of loading everything into memory.

</details>
