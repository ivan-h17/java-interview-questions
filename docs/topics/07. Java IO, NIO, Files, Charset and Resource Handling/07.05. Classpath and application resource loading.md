# 07.05. Classpath and application resource loading

---

<a id="jio-cp-001"></a>

<details>
<summary><strong>JIO-CP-001. What is the difference between a filesystem path and a classpath resource?</strong></summary>

#### Short answer

A filesystem path points to a file in the OS filesystem. A classpath resource is loaded from the application's runtime classpath, often from a JAR.

#### Interview answer

Filesystem paths are resolved by the operating system and current process environment. Classpath resources are resolved by a class loader from directories, JARs or other runtime locations.

This distinction matters because a resource in `src/main/resources` during development is usually packaged inside `target/classes` or inside a JAR after build. It may not exist as a normal file path in production.

#### Deep dive

Use filesystem paths for external mutable data: uploads, mounted config, generated files and logs. Use classpath resources for packaged immutable data: templates, seed files, embedded certificates or static metadata.

#### Production angle

Confusing the two causes "works in IDE, fails in Docker/JAR" bugs. It also affects whether a resource can be modified at runtime.

#### Traps / caveats

- `src/main/resources` is a source-tree path, not a production path.
- Classpath resources are often read-only.
- A classpath resource may not be convertible to `File`.

#### Optional Anki

Q: Where should packaged templates usually be loaded from?
A: The classpath.

</details>

<a id="jio-cp-002"></a>

<details>
<summary><strong>JIO-CP-002. How do `Class.getResource()` and `ClassLoader.getResource()` differ?</strong></summary>

#### Short answer

`Class.getResource()` can resolve paths relative to the class package. `ClassLoader.getResource()` always uses classpath-root-relative names without a leading slash.

#### Interview answer

`SomeClass.class.getResource("file.txt")` looks relative to `SomeClass`'s package. `SomeClass.class.getResource("/file.txt")` looks from the classpath root.

`SomeClass.class.getClassLoader().getResource("file.txt")` also looks from the classpath root, but the name should not start with `/`.

#### Deep dive

The class loader used matters in containers, test frameworks, application servers and plugin systems. The thread context class loader may also be relevant for frameworks, but application code should keep resource lookup simple when possible.

#### Production angle

Wrong leading slash or relative lookup commonly breaks resource loading after refactoring packages or packaging into a JAR.

#### Traps / caveats

- `getResource()` returns `null` if not found.
- URL does not guarantee a normal filesystem file.
- Class loaders can differ in modular or container environments.

#### Optional Anki

Q: Is `Class.getResource("x")` package-relative?
A: Yes, unless the name starts with `/`.

</details>

<a id="jio-cp-003"></a>

<details>
<summary><strong>JIO-CP-003. Why can `new File("src/main/resources/...")` fail after a Java application is packaged?</strong></summary>

#### Short answer

Because `src/main/resources` exists in the source tree, not necessarily in the runtime working directory or packaged JAR.

#### Interview answer

In an IDE, the project source tree is nearby, so `new File("src/main/resources/foo.txt")` may accidentally work. After packaging, resources are copied into the classpath, often inside a JAR. There may be no `src/main/resources` directory at runtime.

Use classpath resource loading for packaged resources, or external configuration paths for files that are meant to be changed after deployment.

#### Deep dive

Relative filesystem paths also depend on the current working directory. That may differ between IDE, Maven, Docker, Kubernetes, systemd and a manual shell launch.

#### Production angle

This is a common deployment-only failure for templates, certificates, SQL seed files and test data accidentally used by production code.

#### Traps / caveats

- Do not depend on the source layout at runtime.
- Do not write back into classpath resources.
- Test packaged artifacts, not only IDE runs.

#### Optional Anki

Q: Why is `src/main/resources` not a production path?
A: It is a source-tree directory; packaged resources are loaded from the classpath.

</details>

<a id="jio-cp-004"></a>

<details>
<summary><strong>JIO-CP-004. How should code read configuration templates, certificates or seed data packaged inside a JAR?</strong></summary>

#### Short answer

Load them as classpath resources, usually through `getResourceAsStream()` or a framework resource abstraction.

#### Interview answer

Packaged resources should be treated as read-only classpath resources. Use `ClassLoader.getResourceAsStream("path")`, `SomeClass.class.getResourceAsStream(...)`, or framework APIs such as Spring's `ResourceLoader`.

Read them as streams and specify charsets for text. Check for missing resources and fail with a clear startup or configuration error.

#### Deep dive

For certificates or templates, avoid assuming a `File`. Many libraries accept `InputStream`; use that if available. If a library truly requires a file path, copy the resource to a secure temp file and clean it up.

#### Production angle

Classpath resource loading makes the packaged artifact self-contained and avoids dependency on local checkout paths.

#### Traps / caveats

- Always handle `null` from resource lookup.
- Do not expose secrets just because they are bundled in a JAR.
- Packaged resources are not a good place for environment-specific mutable config.

#### Optional Anki

Q: What API is safe for reading a JAR-packaged resource?
A: `getResourceAsStream()`.

</details>

<a id="jio-cp-005"></a>

<details>
<summary><strong>🧠 JIO-CP-005. Why should code not assume that a classpath resource can always be converted to `Path` or `File`?</strong></summary>

#### Short answer

Because classpath resources may live inside JARs, modules or custom class loaders, not as ordinary filesystem files.

#### Interview answer

A classpath resource is an abstraction over where the class loader found bytes. In development it may be a loose file under `target/classes`, but in production it may be an entry inside a JAR. A JAR entry is not a normal `File`.

Code should usually consume classpath resources as streams or URLs, not convert them to `Path` or `File`.

#### Deep dive

There are ways to access JAR filesystems through NIO, but that adds complexity and is rarely needed for normal resource reading. If another API requires a real file, copy the resource to a controlled temp file.

#### Production angle

This mistake causes failures after switching packaging style, using Spring Boot executable JARs, running tests from different class loaders or deploying to containers.

#### Traps / caveats

- `resource.toURI()` to `Paths.get(...)` can fail for non-file schemes.
- A URL scheme like `jar:` is not a plain file.
- Avoid APIs that require files when streams are enough.

#### Optional Anki

Q: What is the safest abstraction for reading classpath resources?
A: `InputStream`.

</details>
