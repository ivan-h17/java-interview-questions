# 07.10. Backend production traps and scenarios

---

<a id="jio-prod-001"></a>

<details>
<summary><strong>JIO-PROD-001. How can file uploads or downloads accidentally consume too much memory?</strong></summary>

#### Short answer

They consume too much memory when code buffers entire payloads, converts bytes to strings, uses unbounded multipart storage, or queues data faster than it can be written.

#### Interview answer

The common mistake is treating a large payload like a small object: `readAllBytes()`, `byte[]`, `String`, base64 conversion, `readAllLines()` or collecting chunks into a list. Downloads can also buffer full responses before sending them to the client.

Good backend design streams data in bounded chunks, enforces maximum sizes, and avoids unnecessary copies.

#### Deep dive

Multipart frameworks may store parts in memory until a threshold is crossed. Base64 increases size. Text decoding creates additional objects. Antivirus scanning, checksum calculation and upload-to-object-storage flows must be designed as pipelines rather than all-at-once transformations.

#### Production angle

Symptoms include allocation spikes, long GC pauses, OOMs, high p99 latency and container OOMKills during imports or large downloads.

#### Traps / caveats

- Streaming still needs slow-client protection.
- Content length can be missing or false.
- One extra copy per request becomes large under concurrency.

#### Optional Anki

Q: What is the default safe shape for large upload handling?
A: Stream with size limits and bounded buffering.

</details>

<a id="jio-prod-002"></a>

<details>
<summary><strong>JIO-PROD-002. What is path traversal, and how can backend code avoid it?</strong></summary>

#### Short answer

Path traversal is when user input escapes an intended directory, often using `..`, absolute paths or symlinks. Avoid it by resolving against a trusted base and validating the resolved target.

#### Interview answer

If a service accepts a filename and simply appends it to a directory, an attacker may pass values like `../../secret` or an absolute path to read or write outside the allowed area.

Safer code uses an approved base directory, resolves user input under it, normalizes or resolves the result, checks that the final target remains inside the base, and controls symlink behavior. Often the best design is to ignore user filenames for storage and generate server-side IDs.

#### Deep dive

Archive extraction is a special case because every entry name is user-controlled. File permissions, symlinks and races also matter.

#### Production angle

Path traversal can expose secrets, overwrite application files or corrupt tenant data. Treat user-controlled paths as security-sensitive input.

#### Traps / caveats

- String prefix checks are not enough.
- URL decoding can reveal hidden `..` segments.
- Normalization alone does not handle symlinks safely.

#### Optional Anki

Q: What is the safest storage filename for user uploads?
A: A server-generated name or ID, not the raw client filename.

</details>

<a id="jio-prod-003"></a>

<details>
<summary><strong>JIO-PROD-003. What is Zip Slip, and why is archive extraction security-sensitive?</strong></summary>

#### Short answer

Zip Slip is path traversal through archive entry names that write files outside the intended extraction directory.

#### Interview answer

Archive entries can have names like `../../app/config.yml` or absolute paths. If extraction code blindly resolves each entry under the target directory, it may overwrite files elsewhere on the filesystem.

Safe extraction validates each entry path after resolving and normalizing against the destination directory. The final path must remain inside the destination. Also handle symlinks, permissions, file size limits and total extracted size.

#### Deep dive

Archive extraction has multiple resource risks: many small files, huge compressed-to-uncompressed ratios, duplicate entries, nested archives and special files. Security is not only about `..`.

#### Production angle

Unsafe extraction can become remote file overwrite or denial of service. Treat uploaded archives as untrusted input.

#### Traps / caveats

- Validate each entry, not only the archive filename.
- Limit both compressed and uncompressed sizes.
- Beware of symlink entries and duplicate target paths.

#### Optional Anki

Q: What is the core Zip Slip defense?
A: Ensure each resolved entry path stays inside the extraction directory.

</details>

<a id="jio-prod-004"></a>

<details>
<summary><strong>JIO-PROD-004. A Java service fails with `Too many open files`. How would you investigate it?</strong></summary>

#### Short answer

Check descriptor limits and current open descriptors, identify which files or sockets are growing, then trace them back to unclosed resources or excessive concurrency.

#### Interview answer

First confirm the OS limit and current descriptor count for the process. Use tools such as `lsof`, `/proc/<pid>/fd` on Linux, container metrics, JFR or runtime diagnostics. Look at what descriptors are open: files, sockets, pipes, JARs, deleted temp files or repeated paths.

Then inspect recent code paths for missing try-with-resources, unclosed HTTP responses, `Files.lines()`/`walk()` streams, socket leaks, connection pool leaks or too many concurrent transfers.

#### Deep dive

Also check whether traffic or concurrency changed. A service may not leak but may legitimately exceed limits because each request opens several files or sockets.

#### Production angle

Mitigation may include restarting, reducing traffic, raising limits temporarily or disabling a faulty feature. The durable fix is clear resource ownership and metrics around open resources.

#### Traps / caveats

- Raising `ulimit` alone can hide the bug.
- Deleted temp files can still consume disk while open.
- Connection leaks and descriptor leaks often look similar initially.

#### Optional Anki

Q: What command is commonly used to inspect open files for a process?
A: `lsof`.

</details>

<a id="jio-prod-005"></a>

<details>
<summary><strong>JIO-PROD-005. A CSV import causes a memory spike. What I/O design problems would you check?</strong></summary>

#### Short answer

Check for whole-file loading, unbounded parsed records, expensive string splitting, large batches, retained errors, and missing backpressure.

#### Interview answer

I would first check whether the import uses `readAllLines()`, `readString()` or a full in-memory list of records. Then I would inspect parsing: regex `split()`, duplicated strings, keeping raw lines plus DTOs plus validation errors, and building one giant batch before writing.

The better design is streaming line or record processing with bounded batches, explicit charset, size limits, validation, checkpointing and backpressure.

#### Deep dive

CSV is deceptively hard: quoted fields can contain delimiters and newlines, so a real CSV parser is safer than naive line splitting for non-trivial files.

#### Production angle

Import jobs should report records processed, errors, memory, batch latency and downstream write rates. This makes it easier to distinguish parser memory from database or queue backpressure.

#### Traps / caveats

- Streaming by lines may be wrong for CSV with quoted newlines.
- A small memory leak per row becomes large over millions of rows.
- Error reporting can retain too much raw data.

#### Optional Anki

Q: What is the first thing to check in a memory-heavy import?
A: Whether it loads the whole file or all parsed records into memory.

</details>

<a id="jio-prod-006"></a>

<details>
<summary><strong>JIO-PROD-006. A service cannot find a resource file after deployment, although it worked in the IDE. What would you check?</strong></summary>

#### Short answer

Check whether the code uses source-tree filesystem paths instead of classpath resources, and verify the resource is actually packaged.

#### Interview answer

I would inspect the failing path and loading code. If it uses `new File("src/main/resources/...")` or another relative filesystem path, that is likely the problem. Packaged resources should be loaded from the classpath.

Then I would verify the resource exists in the built artifact, check case sensitivity, leading slash behavior in `getResource()`, working directory differences, Docker mounts and environment-specific configuration.

#### Deep dive

IDE classpaths are forgiving. A packaged JAR has a different layout, and Linux filesystems are usually case-sensitive. Spring Boot executable JARs also make resource-to-file conversion unreliable.

#### Production angle

Build and smoke-test the actual artifact that will be deployed. Startup checks should fail clearly when required resources are missing.

#### Traps / caveats

- Do not depend on current working directory.
- Resource names are case-sensitive in many deployments.
- A resource inside a JAR may not have a normal `Path`.

#### Optional Anki

Q: What is the likely bug if `src/main/resources` is used in production code?
A: Confusing source-tree paths with runtime classpath resources.

</details>

<details>
<summary><strong>JIO-PROD-007. A service writes corrupted or half-written export files during restarts. What design problems would you check?</strong></summary>

#### Short answer

Check whether it writes directly to the final file, fails to close/flush, has concurrent writers, or lacks an atomic publish step.

#### Interview answer

I would look for direct writes to the final export path. If the process stops mid-write, readers can see partial content. The safer pattern is writing to a temp file in the same directory, closing it successfully, optionally syncing if durability matters, and publishing it with an atomic move where supported.

I would also check whether multiple instances write the same path, whether readers can open in-progress files, and whether cleanup handles abandoned temp files.

#### Deep dive

If export files are part of an external integration, naming and lifecycle should communicate state: temporary/in-progress names should not be consumed. The final name should appear only after the file is complete.

#### Production angle

This affects reports, batch exports, generated feeds and file-based partner integrations. Atomic publication prevents consumers from processing half data.

#### Traps / caveats

- `flush()` is not necessarily durable.
- Atomic move may fail across filesystems.
- File locks do not fix bad publication design by themselves.

#### Optional Anki

Q: How should a complete export be published?
A: Write temp file, then atomically move to the final name.

</details>
