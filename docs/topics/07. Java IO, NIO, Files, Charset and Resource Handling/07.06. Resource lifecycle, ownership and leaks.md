# 07.06. Resource lifecycle, ownership and leaks

---

<a id="jio-res-001"></a>

<details>
<summary><strong>JIO-RES-001. What kinds of Java objects represent external resources that must be closed?</strong></summary>

#### Short answer

Objects that hold OS, network, filesystem, database or native resources usually must be closed.

#### Interview answer

Common examples are `InputStream`, `OutputStream`, `Reader`, `Writer`, `Channel`, `Socket`, `ServerSocket`, `ZipFile`, `DirectoryStream`, `WatchService`, JDBC `Connection`/`Statement`/`ResultSet`, and many framework clients or responses.

The common signal is `AutoCloseable` or `Closeable`. If an object represents something outside the heap, assume lifecycle matters.

#### Deep dive

Some Java objects hold resources indirectly. A `Stream<String>` returned by `Files.lines()` is a Java Stream, but it may hold an open file. HTTP client response bodies often need closing even when the request failed.

#### Production angle

Unclosed resources produce file descriptor leaks, connection pool exhaustion, stuck deployments and slow failure after traffic accumulates.

#### Traps / caveats

- Garbage collection is not deterministic cleanup.
- Not every `Stream<T>` is resource-backed, but some are.
- Framework abstractions may hide closeable response bodies.

#### Optional Anki

Q: What interface usually signals explicit cleanup in Java?
A: `AutoCloseable`.

</details>

<a id="jio-res-002"></a>

<details>
<summary><strong>JIO-RES-002. How does try-with-resources work?</strong></summary>

#### Short answer

It declares resources in a `try (...)` header and automatically closes them when the block exits.

#### Interview answer

Try-with-resources works with `AutoCloseable`. Java closes each declared resource at the end of the block whether execution finishes normally or with an exception. Resources are closed in reverse order of declaration.

This is the standard way to manage streams, readers, channels, JDBC resources and other closeable objects.

#### Deep dive

If both the block and `close()` throw exceptions, the exception from the block remains primary and close failures are attached as suppressed exceptions. This preserves the original failure while keeping cleanup errors visible.

#### Production angle

Try-with-resources prevents common leaks during error paths. It also makes ownership local and reviewable.

#### Traps / caveats

- Only declare resources the method owns.
- Closing order matters for wrapped resources.
- Suppressed exceptions should not be ignored during debugging.

#### Optional Anki

Q: In what order does try-with-resources close multiple resources?
A: Reverse order of declaration.

</details>

<a id="jio-res-003"></a>

<details>
<summary><strong>🧠 JIO-RES-003. What are suppressed exceptions, and why do they matter in resource cleanup?</strong></summary>

#### Short answer

Suppressed exceptions are secondary exceptions attached to a primary exception, commonly when cleanup fails after the main operation already failed.

#### Interview answer

In try-with-resources, if the try block throws and then `close()` also throws, Java keeps the try-block exception as the main exception and records the close exception as suppressed. You can inspect them with `Throwable.getSuppressed()`.

This avoids losing the real root cause while still exposing cleanup failures.

#### Deep dive

Before try-with-resources, a `finally` block that threw could accidentally mask the original exception. Suppressed exceptions were added to preserve both pieces of information.

#### Production angle

Suppressed exceptions can reveal important issues such as failed flush, failed socket close, broken commit/rollback cleanup or filesystem errors during export finalization.

#### Traps / caveats

- Logging only `e.getMessage()` may hide suppressed exceptions.
- A close failure can matter if it means buffered data was not written.
- Manual `finally` cleanup can still mask exceptions if written poorly.

#### Optional Anki

Q: Where can cleanup exceptions be found after try-with-resources?
A: In `Throwable.getSuppressed()`.

</details>

<a id="jio-res-004"></a>

<details>
<summary><strong>JIO-RES-004. What is a file descriptor leak, and how can it appear in a Java service?</strong></summary>

#### Short answer

A file descriptor leak happens when a process keeps opening files, sockets or pipes without closing them.

#### Interview answer

Operating systems represent open files, sockets and similar resources with descriptors. Java wraps them in streams, channels, sockets and framework objects. If code does not close those wrappers, descriptors remain open until the process hits its limit.

In Java services this can come from unclosed file streams, directory streams, HTTP responses, sockets, log files, JAR files or database/network clients.

#### Deep dive

Symptoms include `Too many open files`, failed accepts, failed outgoing connections, inability to read config, and strange cascading errors. Use logs, metrics, `lsof`, `/proc`, JFR, thread dumps and code review to find the leak.

#### Production angle

Descriptor leaks often grow slowly and fail under load. They should be treated as resource ownership bugs, not fixed only by raising OS limits.

#### Traps / caveats

- Increasing `ulimit` can delay but not fix a leak.
- Some Java streams returned by `Files` must be closed.
- Connection pools can hide leaks until the pool is exhausted.

#### Optional Anki

Q: What error often indicates descriptor exhaustion?
A: `Too many open files`.

</details>

<a id="jio-res-005"></a>

<details>
<summary><strong>JIO-RES-005. Should a method close a stream it received from its caller?</strong></summary>

#### Short answer

Usually no, unless the method's contract clearly says it takes ownership of the stream.

#### Interview answer

Resource ownership should be explicit. If a caller passes an `InputStream` into a helper method, the caller often still owns the stream and may want to continue using it or close several related resources together. The helper should not close it unless documented.

If the method opens the stream, the method should close it. If the method accepts a stream and consumes it fully, the contract should say whether it closes it.

#### Deep dive

Wrappers complicate this because closing an outer wrapper usually closes the underlying stream. Sometimes you need a non-closing wrapper or a clear boundary method such as `processAndClose(...)`.

#### Production angle

Unclear ownership causes both leaks and premature closes. Premature close bugs appear in HTTP responses, multipart uploads and libraries that reuse streams.

#### Traps / caveats

- "Consumes" and "closes" are different promises.
- Frameworks may own request and response streams.
- Try-with-resources should match ownership.

#### Optional Anki

Q: Who should close a resource?
A: The code that owns it, according to the API contract.

</details>

<a id="jio-res-006"></a>

<details>
<summary><strong>JIO-RES-006. Why is relying on finalizers, cleaners or garbage collection unsafe for resource cleanup?</strong></summary>

#### Short answer

GC cleanup is nondeterministic, may run too late, and may not run before the process exhausts external resources.

#### Interview answer

Garbage collection manages heap memory. External resources such as file descriptors, sockets and native memory need deterministic release. Finalizers are deprecated and unsafe. Cleaners are better for fallback cleanup, but still run asynchronously and are not a substitute for `close()`.

Use explicit lifecycle management: try-with-resources, framework lifecycle hooks and clear ownership.

#### Deep dive

The heap may have plenty of space while the process is out of descriptors or native memory. That means GC pressure may not happen soon enough to trigger fallback cleanup.

#### Production angle

Depending on GC for cleanup creates intermittent failures under load and makes shutdown or redeploy behavior unpredictable.

#### Traps / caveats

- `finalize()` should not be used for normal cleanup.
- Cleaners are safety nets, not contracts.
- Native memory and descriptors can exhaust before heap memory.

#### Optional Anki

Q: What is the correct primary mechanism for closing I/O resources?
A: Explicit `close()`, usually via try-with-resources.

</details>
