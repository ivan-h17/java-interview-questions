# 07.09. Advanced file-system and NIO topics

---

<a id="jio-adv-001"></a>

<details>
<summary><strong>JIO-ADV-001. What are `FileChannel` and `SocketChannel` used for?</strong></summary>

#### Short answer

`FileChannel` performs channel-based file I/O. `SocketChannel` performs channel-based network socket I/O and can be used in blocking or non-blocking mode.

#### Interview answer

`FileChannel` is useful for reading, writing, positioning, transferring, locking and memory-mapping files. It works with `ByteBuffer` and can support operations that classic streams do not expose cleanly.

`SocketChannel` represents a TCP socket in NIO. It can be configured as blocking or non-blocking and, in non-blocking mode, registered with a selector.

#### Deep dive

Both channels transfer bytes through buffers, but their capabilities differ. File channels have file positions and mapping. Socket channels have connection state and readiness events.

#### Production angle

Most backend services use these through libraries, but direct knowledge helps when debugging large transfers, networking frameworks, file locks or direct-buffer memory behavior.

#### Traps / caveats

- A `FileChannel` is not selectable with `Selector`.
- A `SocketChannel` read can return partial data or `-1` on close.
- Channels still need explicit close.

#### Optional Anki

Q: Which channel type can be registered with a selector for network reads?
A: `SocketChannel`.

</details>

<details>
<summary><strong>🧠 JIO-ADV-002. What are `transferTo()` and `transferFrom()`, and when can they be useful?</strong></summary>

#### Short answer

They transfer bytes directly between channels and can be useful for efficient file copying or file-to-socket transfer.

#### Interview answer

`FileChannel.transferTo()` transfers bytes from a file channel to another writable channel. `transferFrom()` transfers bytes from a readable channel into a file channel. They can let the operating system optimize copying, sometimes reducing user-space buffer copies.

They are useful for serving files, copying large files or moving data between channels when the application does not need to inspect every byte.

#### Deep dive

These methods are not magic. They may transfer fewer bytes than requested, and behavior can depend on OS, filesystem, channel type and file size. Correct code checks returned counts and loops until done.

#### Production angle

They can improve throughput for large static transfers, but application-level concerns still matter: range requests, cancellation, rate limits, TLS, checksums and error handling.

#### Traps / caveats

- Always handle partial transfers.
- TLS or wrapper layers may prevent true zero-copy behavior.
- Do not use transfer methods when the application must transform the content.

#### Optional Anki

Q: What must code check after `transferTo()`?
A: The number of bytes actually transferred.

</details>

<details>
<summary><strong>🧠 JIO-ADV-003. What is memory-mapped I/O, and what risks come with memory-mapped files?</strong></summary>

#### Short answer

Memory-mapped I/O maps file content into virtual memory so code can access it through a buffer. Risks include native memory pressure, page faults, hard cleanup, file-change surprises and platform-specific behavior.

#### Interview answer

With `FileChannel.map()`, Java can create a `MappedByteBuffer` representing a region of a file. The OS loads pages as they are accessed, which can be efficient for large files, random access or shared read-only data.

The trade-off is complexity. The mapping consumes address space, can affect process RSS, may fault pages lazily, and historically has not had a simple deterministic unmap API in ordinary application code.

#### Deep dive

If the mapped file is truncated or changed unexpectedly, reads can fail in surprising ways. Mapping very large files in many processes can also create memory and operational confusion.

#### Production angle

Use memory mapping only when it solves a measured problem. For normal uploads, CSV imports and HTTP responses, streaming is usually simpler and safer.

#### Traps / caveats

- Mapped memory is not counted like normal heap objects.
- Closing the channel does not necessarily unmap the buffer immediately.
- Page faults can appear as latency spikes.

#### Optional Anki

Q: Which class represents a memory-mapped byte buffer?
A: `MappedByteBuffer`.

</details>

<details>
<summary><strong>🧠 JIO-ADV-004. What is `WatchService`, and what are its limitations?</strong></summary>

#### Short answer

`WatchService` watches filesystem directories for changes, but events can be coalesced, missed through overflow, platform-dependent and not recursively watched by default.

#### Interview answer

`WatchService` lets Java code register directories for events such as create, modify and delete. It is useful for configuration reloads, import directories or local development tooling.

It is not a perfect event log. Events may be coalesced, an overflow event may indicate missed changes, and behavior differs across operating systems. Recursive watching requires registering subdirectories yourself.

#### Deep dive

Robust code treats watch events as hints. On startup and after overflow, rescan the directory and reconcile actual state. Debounce rapid modifications because writers may produce multiple events for one logical change.

#### Production angle

For critical distributed workflows, do not rely only on local filesystem watching. Use durable queues, databases or object-storage notifications where appropriate.

#### Traps / caveats

- Watching a directory does not automatically watch all descendants.
- A modify event may fire before a writer has finished writing.
- Overflow means you need a rescan.

#### Optional Anki

Q: What should code do after a `WatchService` overflow?
A: Rescan and reconcile actual filesystem state.

</details>

<details>
<summary><strong>🧠 JIO-ADV-005. How do file locks work in Java, and why are they easy to misuse?</strong></summary>

#### Short answer

Java file locks are acquired through `FileChannel`, usually as OS-level advisory locks. They are not normal Java thread locks and can behave differently by platform and filesystem.

#### Interview answer

`FileChannel.lock()` blocks until a lock is acquired, while `tryLock()` attempts without blocking. Locks can cover a whole file or region and are released when the lock or channel is closed.

They are easy to misuse because they coordinate file access at the OS/filesystem level, not arbitrary Java objects. Other processes must respect the locking convention, and network filesystems or platforms may behave differently.

#### Deep dive

Within one JVM, overlapping locks may fail because locks are often process-wide rather than thread-owned in the way Java monitors are. File locks also do not replace atomic file creation, atomic rename or database coordination.

#### Production angle

Use file locks only when filesystem coordination is truly required and tested on the deployment filesystem. For service coordination, a database, distributed lock or queue is often clearer.

#### Traps / caveats

- Advisory locks do not stop code that ignores them.
- Locks may be released when the channel closes.
- Do not hold file locks during slow unrelated work.

#### Optional Anki

Q: Which Java class is used to acquire file locks?
A: `FileChannel`.

</details>
