# 07.07. NIO channels and buffers

---

<a id="jio-nio-001"></a>

<details>
<summary><strong>JIO-NIO-001. What is Java NIO, and how does it differ from classic `java.io`?</strong></summary>

#### Short answer

Java NIO is a set of APIs around buffers, channels, selectors and modern file APIs. It supports block-oriented and non-blocking styles that classic stream I/O does not model directly.

#### Interview answer

Classic `java.io` is stream-oriented: code reads or writes bytes or characters sequentially through `InputStream`, `OutputStream`, `Reader` and `Writer`. Java NIO uses buffers and channels. Data is read from a channel into a buffer, then consumed from the buffer, or written from a buffer into a channel.

NIO also introduced selectors for multiplexing many network channels with fewer threads, and NIO.2 added `Path`, `Files` and improved filesystem APIs.

#### Deep dive

NIO is not a universal replacement for `java.io`. It is useful when you need selectors, file channels, memory-mapped files, direct buffers, richer filesystem behavior or precise control over buffer state.

#### Production angle

Most backend teams use NIO indirectly through frameworks such as Netty, servlet containers, HTTP clients and file APIs. A senior answer should explain trade-offs, not just say "NIO is faster".

#### Traps / caveats

- NIO can be blocking or non-blocking depending on the channel.
- More complex buffer handling can introduce bugs.
- `Files`/`Path` are NIO.2 even when used for simple blocking file operations.

#### Optional Anki

Q: What are the core NIO abstractions?
A: `Buffer`, `Channel`, `Selector`, plus NIO.2 `Path`/`Files`.

</details>

<a id="jio-nio-002"></a>

<details>
<summary><strong>JIO-NIO-002. What is a `ByteBuffer`?</strong></summary>

#### Short answer

`ByteBuffer` is a mutable byte container used by NIO channels for reading, writing and parsing bytes.

#### Interview answer

A `ByteBuffer` stores bytes and tracks three main state values: `position`, `limit` and `capacity`. Channels read bytes into buffers and write bytes from buffers. Application code then flips, clears, compacts or rewinds the buffer depending on whether it is producing or consuming data.

`ByteBuffer` can be heap-based or direct, and it also provides typed methods like `getInt()` and `putLong()` that interpret bytes using a byte order.

#### Deep dive

The most important mental model is mode switching. After writing data into a buffer, call `flip()` before reading it. After reading, call `clear()` if all data was consumed, or `compact()` if unconsumed bytes must be kept.

#### Production angle

Incorrect buffer state management causes corrupted protocols, lost bytes, infinite loops and high CPU in networking code.

#### Traps / caveats

- `clear()` does not erase bytes; it resets position and limit.
- `ByteBuffer` is mutable and not generally thread-safe.
- `remaining()` is often more important than raw capacity.

#### Optional Anki

Q: What method prepares a written `ByteBuffer` for reading?
A: `flip()`.

</details>

<a id="jio-nio-003"></a>

<details>
<summary><strong>🧠 JIO-NIO-003. How do `position`, `limit` and `capacity` work in a buffer?</strong></summary>

#### Short answer

`capacity` is fixed size, `position` is the next index to read or write, and `limit` is the boundary beyond which reads or writes should not go.

#### Interview answer

A buffer has a fixed `capacity`. The `position` moves as data is read or written. The `limit` marks the end of the active region. `remaining()` is `limit - position`.

In write mode, `position` advances as bytes are put into the buffer, and `limit` usually equals `capacity`. After `flip()`, `limit` becomes the old write position and `position` becomes zero, so the buffer is ready to be read.

#### Deep dive

These values let one object represent both a destination for incoming bytes and a source of outgoing bytes. That power is why buffer code is compact, but also why it is easy to get wrong.

#### Production angle

Protocol parsers and high-throughput clients often fail because code reads beyond the valid region or overwrites bytes that were not fully processed.

#### Traps / caveats

- `capacity` does not mean valid data length.
- `limit` changes meaning depending on read or write mode.
- Always use `remaining()` or returned read/write counts.

#### Optional Anki

Q: What does `remaining()` return?
A: `limit - position`.

</details>

<a id="jio-nio-004"></a>

<details>
<summary><strong>🧠 JIO-NIO-004. What do `flip()`, `clear()`, `rewind()` and `compact()` do?</strong></summary>

#### Short answer

`flip()` switches from writing to reading, `clear()` prepares for fresh writing, `rewind()` rereads existing data, and `compact()` keeps unread data while preparing for more writes.

#### Interview answer

After writing bytes into a buffer, `flip()` sets `limit` to the current position and `position` to zero. `clear()` sets `position` to zero and `limit` to capacity, but does not erase bytes. `rewind()` sets position to zero while keeping the same limit. `compact()` copies unread bytes to the beginning, then prepares the buffer to receive more data after them.

#### Deep dive

Use `clear()` only when all data has been consumed. Use `compact()` when a partial message remains and more bytes must be read before parsing can continue.

#### Production angle

Wrong use of `clear()` instead of `compact()` is a classic cause of losing partial protocol frames under load.

#### Traps / caveats

- `clear()` name is misleading; old bytes may remain.
- `rewind()` does not switch from write mode to read mode.
- `compact()` involves copying remaining bytes.

#### Optional Anki

Q: Which method preserves unread bytes and prepares for more writes?
A: `compact()`.

</details>

<a id="jio-nio-005"></a>

<details>
<summary><strong>🧠 JIO-NIO-005. What is the difference between heap buffers and direct buffers?</strong></summary>

#### Short answer

Heap buffers store bytes in the Java heap. Direct buffers store bytes in native memory outside the Java heap and can reduce copying for some I/O operations.

#### Interview answer

`ByteBuffer.allocate()` creates a heap buffer backed by a Java byte array. It is cheap to allocate and easy for Java code to access. `ByteBuffer.allocateDirect()` creates a direct buffer whose data is stored outside the heap. Native I/O can sometimes work with direct memory more efficiently.

The trade-off is that direct buffers are more expensive to allocate, consume native memory, and are released only when their buffer objects become unreachable and cleanup runs.

#### Deep dive

Direct buffer memory still matters for process RSS and container limits. It is often pooled by networking frameworks to avoid repeated allocation cost.

#### Production angle

Direct buffer leaks or excessive allocation can cause native memory growth or `OutOfMemoryError: Direct buffer memory` even when Java heap looks healthy.

#### Traps / caveats

- Direct memory is not "free" because it is outside the heap.
- Do not allocate direct buffers per small operation in hot paths.
- Heap buffers are often perfectly fine for application-level code.

#### Optional Anki

Q: Which method creates a direct `ByteBuffer`?
A: `ByteBuffer.allocateDirect()`.

</details>

<a id="jio-nio-006"></a>

<details>
<summary><strong>JIO-NIO-006. How do channels and buffers work together, and how is a `Channel` different from a stream?</strong></summary>

#### Short answer

A channel transfers bytes to or from a buffer. A stream exposes sequential byte or character operations, while a channel is block-oriented and may support bidirectional, positional or selectable operations.

#### Interview answer

With NIO, data usually moves between a `Channel` and a `Buffer`: `channel.read(buffer)` fills a buffer, and `channel.write(buffer)` drains bytes from a buffer. The buffer owns the current data state; the channel represents the connection to a file, socket or other I/O source.

Streams are simpler sequential abstractions. Channels are more flexible: some support both read and write, file position, scattering/gathering, transfer operations or non-blocking selection.

#### Deep dive

The difference is not simply "channel is faster". The useful distinction is control. Channels make buffer state, readiness, file position and transfer behavior explicit.

#### Production angle

A backend developer may not hand-write channels daily, but this mental model helps understand Netty, servlet containers, file copying and memory-mapped or zero-copy style APIs.

#### Traps / caveats

- Not every channel is selectable.
- Channels can still be blocking.
- A channel operation may transfer fewer bytes than requested.

#### Optional Anki

Q: In NIO, where does a channel read data into?
A: Into a `Buffer`, commonly a `ByteBuffer`.

</details>

<a id="jio-nio-007"></a>

<details>
<summary><strong>JIO-NIO-007. Why must NIO code handle partial reads, partial writes and zero-byte operations?</strong></summary>

#### Short answer

NIO operations are allowed to transfer fewer bytes than requested, and non-blocking channels may transfer zero bytes when no progress is currently possible.

#### Interview answer

`read()` and `write()` return counts. A read may return part of a message, a write may write only part of a buffer, and a non-blocking operation may return zero. Correct NIO code loops based on buffer state, returned counts and readiness events instead of assuming the operation completed.

For sockets, `-1` from read means end-of-stream. For writes, remaining bytes must stay in the buffer until the channel is writable again.

#### Deep dive

Selector readiness means "likely possible to make progress", not "your whole message can be read or written now". Application protocols need framing and output queues.

#### Production angle

Ignoring partial writes causes truncated responses. Ignoring zero-byte operations can cause busy loops. Ignoring partial reads breaks protocols when messages are split across packets.

#### Traps / caveats

- Never discard a buffer until `hasRemaining()` is false after writes.
- Do not spin on zero-byte reads or writes.
- A successful readiness event does not guarantee full completion.

#### Optional Anki

Q: What must code do after a partial NIO write?
A: Keep the remaining bytes and write again later.

</details>

<details>
<summary><strong>🧠 JIO-NIO-008. What is `ByteBuffer` byte order, and when does endianness matter?</strong></summary>

#### Short answer

Byte order controls how multi-byte primitive values are encoded and decoded. It matters for binary protocols, file formats and cross-platform data exchange.

#### Interview answer

A `ByteBuffer` can read and write primitive values such as `int`, `long` and `double`. Byte order decides whether the most significant byte or least significant byte comes first. Java `ByteBuffer` defaults to big-endian, and you can change it with `order(ByteOrder.LITTLE_ENDIAN)`.

This matters only when interpreting groups of bytes as larger values. Raw byte copying is unaffected.

#### Deep dive

Network protocols often use big-endian "network byte order". Some file formats and hardware-oriented formats use little-endian. The protocol or file format should define the order; code should not guess.

#### Production angle

Wrong byte order causes corrupted numeric values that may look plausible but are wrong, which is dangerous in financial, telemetry or binary integration systems.

#### Traps / caveats

- Byte order affects `getInt()`, `putLong()` and similar methods, not individual bytes.
- Do not rely on CPU native endianness unless the format explicitly says so.
- Document byte order in binary contracts.

#### Optional Anki

Q: What byte order does `ByteBuffer` use by default?
A: Big-endian.

</details>
