# 07.08. Blocking, non-blocking and asynchronous I/O

---

<a id="jio-async-001"></a>

<details>
<summary><strong>JIO-ASYNC-001. How do blocking, non-blocking and asynchronous I/O differ?</strong></summary>

#### Short answer

Blocking waits in the calling thread. Non-blocking returns if it cannot progress now. Asynchronous starts an operation and reports completion later.

#### Interview answer

In blocking I/O, a call such as `read()` waits until it can complete or fail. In non-blocking I/O, the call returns immediately if no data or capacity is available, often with zero bytes transferred. The application uses selectors, polling or event loops to try again when ready.

Asynchronous I/O separates starting an operation from completing it. The completion may arrive through a callback, `Future` or completion handler.

#### Deep dive

These models solve different problems. Blocking code is simple. Non-blocking code can multiplex many connections with fewer threads. Asynchronous APIs can let the OS or runtime notify the application when operations complete.

#### Production angle

The choice affects thread count, debugging, backpressure, cancellation, timeouts and complexity. Most teams use frameworks rather than hand-writing event loops.

#### Traps / caveats

- Non-blocking is not the same as asynchronous.
- Async code still needs capacity limits.
- Blocking can be a good choice with bounded concurrency or virtual threads.

#### Optional Anki

Q: What does non-blocking I/O do when no progress is possible?
A: It returns without waiting, often transferring zero bytes.

</details>

<a id="jio-async-002"></a>

<details>
<summary><strong>🧠 JIO-ASYNC-002. What is a `Selector`, and what problem does it solve?</strong></summary>

#### Short answer

A `Selector` lets one thread monitor many selectable channels for readiness events such as accept, connect, read or write.

#### Interview answer

A selector is used with non-blocking selectable channels, commonly socket channels. Channels register interest in operations such as `OP_READ` or `OP_WRITE`. The selector waits until one or more channels are ready, then application code handles the selected keys.

This avoids needing one platform thread blocked on each connection.

#### Deep dive

Selectors report readiness, not completion. A readable key means a read may make progress; a writable key means a write may make progress. The application still must handle partial transfers and maintain per-connection state.

#### Production angle

Selectors are the low-level idea behind many event-loop networking frameworks. They are powerful, but application teams usually use Netty, servlet containers or reactive runtimes instead of raw selectors.

#### Traps / caveats

- Registering `OP_WRITE` all the time can create busy loops because sockets are often writable.
- Selected keys must be processed and cleared correctly.
- Blocking operations inside the selector loop can stall all connections on that loop.

#### Optional Anki

Q: What does a selector multiplex?
A: Readiness events from multiple selectable channels.

</details>

<a id="jio-async-003"></a>

<details>
<summary><strong>JIO-ASYNC-003. How do virtual threads change the trade-off between blocking I/O and non-blocking I/O?</strong></summary>

#### Short answer

Virtual threads make blocking-style code much cheaper to scale, reducing the need to choose non-blocking I/O only to save platform threads.

#### Interview answer

With platform threads, many blocking I/O operations can require many OS threads. Virtual threads let Java park a waiting operation without dedicating an expensive platform thread for the whole wait in many common cases. That makes simple blocking code viable for much higher concurrency.

However, virtual threads do not make slow dependencies faster. You still need timeouts, bulkheads, connection limits, memory limits and backpressure.

#### Deep dive

Non-blocking I/O still has value for event-loop frameworks, very high connection counts, streaming protocols and libraries already built around reactive pipelines. Virtual threads mainly change the cost/complexity trade-off.

#### Production angle

For many backend services, virtual threads allow simpler request-per-task code. But database pools, HTTP client pools and downstream capacity remain hard limits.

#### Traps / caveats

- Virtual threads are not unlimited capacity.
- Pinning or blocking in native/synchronized regions can still matter.
- Reactive/non-blocking frameworks do not disappear; they solve more than thread count.

#### Optional Anki

Q: What do virtual threads mainly reduce for blocking I/O?
A: The cost of tying up a platform thread while waiting.

</details>

<a id="jio-async-004"></a>

<details>
<summary><strong>JIO-ASYNC-004. When is simple blocking I/O a better engineering choice than NIO selectors?</strong></summary>

#### Short answer

Blocking I/O is often better when concurrency is moderate, the code is simpler, and existing frameworks or virtual threads handle scaling well enough.

#### Interview answer

Raw selectors add complexity: event loops, state machines, partial writes, output queues, backpressure and careful error handling. If the service handles typical HTTP requests, file imports, JDBC calls or object-storage streams, straightforward blocking code may be easier to maintain and safer.

The right question is whether non-blocking complexity solves a real bottleneck.

#### Deep dive

Use selectors or event-loop frameworks when you need many long-lived connections, custom protocols, high network concurrency or integration with a non-blocking stack. Even then, prefer proven libraries over custom selector code.

#### Production angle

Maintainability is a production feature. Teams debug simple blocking stack traces more easily than broken event-loop state machines unless the performance need is real.

#### Traps / caveats

- Do not block inside event-loop threads.
- Do not choose selectors just because they sound advanced.
- Blocking still needs timeouts and bounded concurrency.

#### Optional Anki

Q: What is the main downside of raw selector code?
A: Complexity around state, partial I/O and backpressure.

</details>

<a id="jio-async-005"></a>

<details>
<summary><strong>🧠 JIO-ASYNC-005. How are asynchronous channels different from selector-based non-blocking I/O?</strong></summary>

#### Short answer

Selector-based non-blocking I/O tells you when a channel is ready. Asynchronous channels let you start an operation and receive completion later.

#### Interview answer

With selectors, application code reacts to readiness events and then performs reads or writes itself. It must handle partial progress and keep connection state.

With asynchronous channels such as `AsynchronousSocketChannel` or `AsynchronousFileChannel`, code submits an operation and gets completion through a `Future` or `CompletionHandler`. The runtime reports when that operation completes or fails.

#### Deep dive

Asynchronous does not mean no threads are involved. Implementations may use OS async facilities or thread pools depending on operation and platform. The application still needs ordering, cancellation, error handling and capacity control.

#### Production angle

Async channels are lower-level than most backend teams need directly. Frameworks often provide a higher-level async or reactive model on top of event loops, pools and backpressure.

#### Traps / caveats

- Readiness is not completion.
- Async callbacks can still overwhelm memory if submissions are unbounded.
- Completion order may differ from submission order unless controlled.

#### Optional Anki

Q: What does a selector report?
A: Readiness, not operation completion.

</details>
