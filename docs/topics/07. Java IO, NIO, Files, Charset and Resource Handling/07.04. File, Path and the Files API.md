# 07.04. File, Path and the Files API

---

<a id="jio-files-001"></a>

<details>
<summary><strong>JIO-FILES-001. What is the difference between `java.io.File` and `java.nio.file.Path`?</strong></summary>

#### Short answer

`File` is the older file abstraction. `Path` is the modern NIO.2 path abstraction used with `Files` and richer file-system APIs.

#### Interview answer

`java.io.File` represents a filesystem path, despite its name. It can point to a file or directory, existing or not. Its API is limited and often reports failures as `false`.

`java.nio.file.Path` represents a path in a file system and is designed to work with `Files`, `FileSystem`, `FileStore`, attributes, symbolic links and better exception reporting. In modern Java code, prefer `Path` and `Files`.

#### Deep dive

`Path` is not the file content; it is a location. Operations such as read, write, copy and delete are done mostly through `Files`.

#### Production angle

Better exceptions from `Files` make operational failures easier to diagnose: permission denied, file exists, not a directory, directory not empty and so on.

#### Traps / caveats

- `File` and `Path` can both refer to non-existing locations.
- A path string is not automatically safe to use.
- `File.exists()` and `Files.exists()` checks can race with later operations.

#### Optional Anki

Q: Which Java API is the modern file-path abstraction?
A: `java.nio.file.Path`.

</details>

<a id="jio-files-002"></a>

<details>
<summary><strong>JIO-FILES-002. How does the `Files` API help with practical file operations such as create, copy, move, delete, attributes and opening streams?</strong></summary>

#### Short answer

`Files` provides static methods for common filesystem operations around `Path`, with clearer exceptions and options.

#### Interview answer

`Files` is the main utility class for NIO.2 file operations. It can create files and directories, copy, move, delete, read and write small files, open streams, list directories, walk trees, inspect attributes and handle options such as `CREATE_NEW`, `REPLACE_EXISTING` or link following.

The practical benefit is that backend code can express filesystem intent directly and receive meaningful exceptions instead of boolean failure signals.

#### Deep dive

Use convenience methods for small bounded files, and stream-based methods for large content. For example, `Files.readString()` is convenient for a small config, while `Files.newInputStream()` or `Files.copy()` is better for large payloads.

#### Production angle

`Files` helps implement safe upload staging, exports, cleanup jobs and diagnostics, but code still needs permissions, path validation, error handling and cleanup.

#### Traps / caveats

- Convenience read methods can load whole files into memory.
- Recursive operations need symlink and permission decisions.
- `Files.move(..., ATOMIC_MOVE)` can fail if the filesystem does not support it.

#### Optional Anki

Q: Which class is usually used with `Path` for file operations?
A: `java.nio.file.Files`.

</details>

<a id="jio-files-003"></a>

<details>
<summary><strong>JIO-FILES-003. What is the difference between relative, absolute, normalized and real paths?</strong></summary>

#### Short answer

A relative path is resolved against a base. An absolute path starts from a filesystem root. A normalized path removes redundant `.` and `..`. A real path resolves the actual existing path, often including symlinks.

#### Interview answer

`Path` values can be relative or absolute. A relative path like `logs/app.log` depends on the current working directory or another base path. An absolute path identifies a location from the filesystem root.

Normalization is string/path cleanup: it removes redundant elements like `.` and collapses `a/../b` where possible. A real path requires filesystem access and resolves the real existing location, commonly following symbolic links.

#### Deep dive

Normalization alone is not a security check. A normalized user path may still escape a base directory through symlinks or races. Real path resolution can fail if the file does not exist.

#### Production angle

Backend services should resolve user-controlled paths against an approved base directory and carefully decide how to handle symlinks. This matters for uploads, exports and archive extraction.

#### Traps / caveats

- Current working directory may differ between IDE, tests, Docker and systemd.
- `normalize()` does not touch the filesystem.
- `toRealPath()` can throw if the path does not exist or is inaccessible.

#### Optional Anki

Q: Does `Path.normalize()` resolve symbolic links?
A: No. It is a path cleanup operation, not filesystem resolution.

</details>

<a id="jio-files-004"></a>

<details>
<summary><strong>JIO-FILES-004. Why can checking `Files.exists()` before opening a file still be unsafe?</strong></summary>

#### Short answer

Because the filesystem can change between the check and the later operation. This is a time-of-check/time-of-use race.

#### Interview answer

`Files.exists(path)` tells you something about a moment in time. Another process or thread can create, delete, replace or change permissions on the path before your code opens it. For correctness and security, prefer doing the intended operation directly and handling the resulting exception.

For example, use `CREATE_NEW` to create a file only if it does not already exist instead of checking and then creating.

#### Deep dive

Existence checks can still be useful for diagnostics or optional behavior, but they should not be treated as a lock or guarantee. The operation itself must enforce the invariant.

#### Production angle

TOCTOU bugs appear in upload handling, archive extraction, temp-file creation and security checks. Attackers can exploit races with symlinks or path replacement.

#### Traps / caveats

- `exists()` can return `false` when access is denied.
- `notExists()` is not simply the opposite in all cases.
- Check-then-act filesystem code is usually suspicious.

#### Optional Anki

Q: What option helps create a file only if it does not already exist?
A: `StandardOpenOption.CREATE_NEW`.

</details>

<a id="jio-files-005"></a>

<details>
<summary><strong>JIO-FILES-005. How do symbolic links affect file access, deletion and directory traversal?</strong></summary>

#### Short answer

Symbolic links can make a path point somewhere else, which affects security checks, recursive traversal and what file is actually opened or deleted.

#### Interview answer

A symlink is a filesystem entry that refers to another path. If backend code accepts paths from users, symlinks can bypass simple prefix checks. For example, a path under an upload directory may resolve to `/etc/passwd` through a symlink.

Java APIs often follow links by default for access operations, while some methods allow `LinkOption.NOFOLLOW_LINKS`. Code must choose the intended behavior.

#### Deep dive

Recursive traversal is especially sensitive. Following symlinks can create cycles or leave the intended tree. Deleting a symlink usually deletes the link itself, not the target, but APIs and platform behavior must be understood.

#### Production angle

Symlink handling is central to preventing path traversal and unsafe cleanup jobs. Always validate resolved paths against a trusted base and avoid following links unless required.

#### Traps / caveats

- String prefix checks are not enough.
- `normalize()` does not resolve symlinks.
- Link behavior can differ by operation and platform.

#### Optional Anki

Q: What option tells many `Files` APIs not to follow symlinks?
A: `LinkOption.NOFOLLOW_LINKS`.

</details>

<details>
<summary><strong>JIO-FILES-006. Why must streams returned by `Files.lines()`, `Files.list()`, `Files.walk()` and `Files.find()` usually be closed?</strong></summary>

#### Short answer

They may hold open file descriptors or directory handles until the stream is closed.

#### Interview answer

These methods return lazy streams backed by filesystem resources. For example, `Files.lines()` may keep a file open while lines are consumed, and `Files.list()` or `Files.walk()` may keep directory handles open during traversal.

Use try-with-resources around the returned stream so resources close even when processing stops early or throws.

#### Deep dive

This is easy to miss because the returned type is `Stream<T>`, not an obvious `InputStream`. Terminal operations do not always make ownership clear, especially when the stream escapes the method.

#### Production angle

Leaking these streams can eventually produce `Too many open files`, failed deployments, broken cleanup jobs or flaky tests on systems with lower descriptor limits.

#### Traps / caveats

- Do not return a filesystem-backed stream from a method unless ownership is explicit.
- Short-circuiting operations still require close.
- `try (Stream<String> lines = Files.lines(path))` is the usual shape.

#### Optional Anki

Q: Why close `Files.walk()` streams?
A: They may hold directory handles.

</details>

<a id="jio-files-007"></a>

<details>
<summary><strong>JIO-FILES-007. How can backend code create a file safely without accidentally overwriting an existing file?</strong></summary>

#### Short answer

Create the file atomically with options such as `CREATE_NEW`, or use `Files.createFile()` and handle `FileAlreadyExistsException`.

#### Interview answer

Safe creation should make "must not overwrite" part of the filesystem operation. Do not check `exists()` and then create. Use `Files.createFile(path)` or `Files.newOutputStream(path, CREATE_NEW, WRITE)`. If the file already exists, Java throws `FileAlreadyExistsException`.

For user uploads, generate unpredictable names or use `Files.createTempFile()` in a controlled directory.

#### Deep dive

Permissions matter too. Creating a file safely includes choosing a directory not writable by attackers, setting appropriate permissions where supported, and avoiding symlink surprises.

#### Production angle

This prevents accidental data loss, race-condition vulnerabilities and upload collisions. It also gives a clear error path for duplicate names.

#### Traps / caveats

- `CREATE` may open an existing file; `CREATE_NEW` refuses.
- User-provided filenames need validation and usually normalization.
- Safe file creation does not validate file content.

#### Optional Anki

Q: Which open option refuses to overwrite an existing file?
A: `StandardOpenOption.CREATE_NEW`.

</details>

<details>
<summary><strong>JIO-FILES-008. How should a service write or replace a file when partial writes or crashes matter?</strong></summary>

#### Short answer

Write to a temporary file in the target directory, flush/sync if durability matters, then atomically move it into place when complete.

#### Interview answer

Do not overwrite the final file directly if readers must never see partial content. Write the new content to a temp file in the same directory, close it successfully, optionally force data to disk, and then publish it with an atomic move where supported.

This gives an all-or-nothing publication step: readers see either the old file or the new complete file.

#### Deep dive

Durability is harder than atomic visibility. If power loss matters, you may need `FileChannel.force(true)` and directory sync behavior, which is platform-sensitive. If replacing an existing file, check the filesystem provider's behavior with `ATOMIC_MOVE`; if atomic move is unsupported or replacement is not guaranteed, design a fallback or fail safely.

#### Production angle

This pattern matters for exports, generated configuration, reports, file-based integrations and cache snapshots.

#### Traps / caveats

- `ATOMIC_MOVE` can fail across filesystems or behave differently across providers.
- Closing a stream is not always the same as durable persistence.
- Cleanup temp files after failures.

#### Optional Anki

Q: What is the common safe-replace pattern?
A: Write temp file, close/sync if needed, then atomic move into place.

</details>

<details>
<summary><strong>JIO-FILES-009. What are temporary files and directories used for, and what cleanup or permission risks do they create?</strong></summary>

#### Short answer

Temporary files store intermediate data such as uploads, generated exports or processing state. They must be created securely, cleaned up and bounded.

#### Interview answer

Use temp files when data is too large to keep in memory, when work should be staged before publishing, or when an external library needs a file. Java provides `Files.createTempFile()` and `Files.createTempDirectory()`.

The risks are leaking disk space, exposing sensitive data through permissions, using shared temp locations unsafely, and leaving stale files after crashes.

#### Deep dive

Prefer application-controlled temp directories for service data. Set restrictive permissions where supported, avoid predictable names, and design cleanup for both normal completion and abandoned files.

#### Production angle

Temp-file leaks can fill container disks and take a service down. Sensitive uploads or reports in `/tmp` may violate security expectations if permissions and cleanup are weak.

#### Traps / caveats

- `deleteOnExit()` is usually wrong for long-running services.
- A temp file is still persistent until deleted.
- Container ephemeral storage has limits.

#### Optional Anki

Q: Why is `deleteOnExit()` often bad in services?
A: It keeps registrations until JVM exit and does not help long-running processes.

</details>
