# 07.03. Charsets, Unicode and text boundaries

---

<a id="jio-char-001"></a>

<details>
<summary><strong>JIO-CHAR-001. What is a charset, and why does it matter when converting bytes to text?</strong></summary>

#### Short answer

A charset defines how bytes are encoded as characters and how characters are decoded from bytes.

#### Interview answer

Files, sockets and HTTP bodies carry bytes. To interpret those bytes as text, Java must use a charset such as UTF-8, ISO-8859-1 or Windows-1251. The same byte sequence can mean different characters under different charsets, and some byte sequences may be invalid for a charset.

In Java, use `Charset` or constants such as `StandardCharsets.UTF_8` when converting between `byte[]` and `String`, or when creating readers and writers.

#### Deep dive

Unicode is a character set assigning code points. UTF-8 and UTF-16 are encodings for representing Unicode. Java `String` stores text internally, but whenever text crosses a byte boundary, encoding is involved.

#### Production angle

Charset mistakes break APIs, CSV imports, logs, signatures and non-English user data. Good contracts specify encoding explicitly.

#### Traps / caveats

- Do not rely on "it works on my machine" default charset behavior.
- Some legacy systems do not use UTF-8.
- Invalid byte handling may replace characters unless configured strictly.

#### Optional Anki

Q: What charset is usually the default choice for modern backend APIs?
A: UTF-8.

</details>

<details>
<summary><strong>JIO-CHAR-002. What problems can relying on the platform default charset create, and why should backend code specify charsets explicitly?</strong></summary>

#### Short answer

The platform default charset can differ between machines, containers and Java versions, so byte/text conversion can become environment-dependent.

#### Interview answer

If code calls APIs that use the default charset, the same file or payload may decode differently in local development, CI, a Linux container or a legacy server. That creates subtle data corruption and integration bugs.

Backend code should specify the charset at boundaries: `new String(bytes, UTF_8)`, `getBytes(UTF_8)`, `Files.newBufferedReader(path, UTF_8)` and HTTP content types where relevant.

#### Deep dive

Modern Java has moved toward UTF-8 defaults in more places, but relying on that still makes contracts implicit. External systems and file formats may require a specific charset regardless of the JVM default.

#### Production angle

Explicit charsets make deployments reproducible. They also make tests meaningful because the expected byte representation is part of the contract.

#### Traps / caveats

- A default changing to UTF-8 does not fix legacy input encoded differently.
- Logs and terminals may use their own display encoding.
- Database encoding is another boundary to verify.

#### Optional Anki

Q: Why specify `StandardCharsets.UTF_8` explicitly?
A: To make byte/text conversion independent of the runtime environment.

</details>

<a id="jio-char-003"></a>

<details>
<summary><strong>JIO-CHAR-003. Why is UTF-8 commonly used for APIs, configuration files, logs and data exchange?</strong></summary>

#### Short answer

UTF-8 supports all Unicode characters, is ASCII-compatible, compact for common English text, and is widely standardized across modern systems.

#### Interview answer

UTF-8 is the practical default for modern backend text. It can represent international text, works well with JSON and web protocols, keeps ASCII characters as single bytes, and avoids many legacy encoding ambiguities.

Using UTF-8 consistently across APIs, files, logs and message payloads simplifies contracts and reduces integration failures.

#### Deep dive

UTF-8 is variable-length: ASCII characters use one byte, while other characters use more. That means byte length and character count are not the same. Protocols that limit byte length must count encoded bytes, not Java `String.length()`.

#### Production angle

Consistent UTF-8 contracts make non-English names, currency symbols and emoji predictable in logs, databases, APIs and exports.

#### Traps / caveats

- UTF-8 does not solve normalization issues by itself.
- Byte length can exceed character count.
- Some legacy integrations still require a different charset.

#### Optional Anki

Q: Is UTF-8 fixed-width?
A: No. It is variable-length.

</details>

<a id="jio-char-004"></a>

<details>
<summary><strong>JIO-CHAR-004. What is mojibake, and how would you debug text decoded with the wrong charset?</strong></summary>

#### Short answer

Mojibake is garbled text caused by decoding bytes with the wrong charset.

#### Interview answer

Mojibake happens when bytes encoded with one charset are decoded as another. For example, UTF-8 bytes displayed as a legacy single-byte encoding can produce strange characters.

To debug it, inspect the raw bytes, identify the expected source encoding, check HTTP headers or file metadata, verify the code path where bytes become text, and reproduce with known non-ASCII samples.

#### Deep dive

Good debugging separates storage from display. The bytes may be correct but the viewer wrong, or the bytes may already be corrupted before storage. Test with characters that reveal mistakes, such as Cyrillic, accents, currency symbols or emoji.

#### Production angle

Mojibake affects customer names, addresses, logs, exports and signatures. Once bad text is persisted, recovery may require knowing the original mistaken conversion.

#### Traps / caveats

- Do not "fix" by guessing replacements without checking bytes.
- Multiple bad conversions can stack.
- Logs may hide the original byte sequence.

#### Optional Anki

Q: What causes mojibake?
A: Decoding bytes with the wrong charset.

</details>

<details>
<summary><strong>🧠 JIO-CHAR-005. How can BOM markers, line endings or invisible Unicode characters break file parsing?</strong></summary>

#### Short answer

They add characters or byte sequences that parsers may not expect, causing mismatched headers, failed comparisons or incorrect records.

#### Interview answer

A BOM can appear at the start of some text files and may become part of the first token if not handled. Different line endings such as LF and CRLF can affect splitting, checksums or strict parsers. Invisible Unicode characters such as zero-width spaces or non-breaking spaces can make two strings look identical while comparing differently.

Robust file parsing should define encoding, line-ending handling, trimming rules and validation.

#### Deep dive

CSV headers are a common example: the first column may look like `id`, but actually be prefixed with a BOM. Another example is copied configuration values containing non-breaking spaces.

#### Production angle

These issues create confusing import failures where the file "looks right" in an editor. Good diagnostics should show code points or escaped values for suspicious input.

#### Traps / caveats

- Do not blindly strip all whitespace if whitespace is meaningful.
- Normalization and trimming are business rules, not always safe defaults.
- Editors may hide the character that breaks parsing.

#### Optional Anki

Q: Why can a CSV header named `id` fail to match?
A: It may contain a BOM or invisible character.

</details>
