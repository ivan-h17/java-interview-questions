# 07.01. I/O fundamentals and mental model

---

<a id="jio-fund-001"></a>

<details>
<summary><strong>JIO-FUND-001. What is the difference between byte-oriented I/O and character-oriented I/O?</strong></summary>

#### Short answer

Byte-oriented I/O works with raw bytes. Character-oriented I/O works with decoded text characters using a charset.

#### Interview answer

In Java, `InputStream` and `OutputStream` are byte-oriented. They are appropriate for binary data such as images, compressed files, request bodies, encrypted payloads or protocol bytes. `Reader` and `Writer` are character-oriented. They convert between bytes and characters using a charset and are appropriate for text.

The key boundary is encoding. Bytes are what files, sockets and HTTP bodies physically carry. Text only exists after those bytes are decoded with the correct charset, for example UTF-8.

#### Deep dive

Using character APIs on binary data can corrupt it because decoding treats byte sequences as encoded text. Using byte APIs for text is fine if you explicitly decode later, but the code must preserve record boundaries and charset rules.

#### Production angle

Backend services often handle both: binary upload/download streams and text formats such as JSON, CSV, logs and config. Mixing them incorrectly causes corrupted files, broken signatures, invalid checksums and unreadable non-English text.

#### Traps / caveats

- Do not use `Reader` or `Writer` for arbitrary binary payloads.
- Always know which charset is used when crossing the byte/text boundary.
- `char` is a UTF-16 code unit, not a full Unicode character in every case.

#### Optional Anki

Q: Which Java APIs are byte-oriented?
A: `InputStream` and `OutputStream`.

</details>

<details>
<summary><strong>JIO-FUND-002. What is the difference between `InputStream`/`OutputStream` and `Reader`/`Writer`?</strong></summary>

#### Short answer

`InputStream` and `OutputStream` read and write bytes. `Reader` and `Writer` read and write characters and require character encoding or decoding.

#### Interview answer

`InputStream` represents a source of bytes, and `OutputStream` represents a destination for bytes. They are the right abstraction for binary data and low-level transport.

`Reader` and `Writer` sit at the text level. A `Reader` decodes bytes into characters, and a `Writer` encodes characters into bytes. The bridge classes are `InputStreamReader` and `OutputStreamWriter`, preferably created with an explicit `Charset`.

#### Deep dive

For files, Java also provides convenience methods such as `Files.newBufferedReader(path, charset)` and `Files.newBufferedWriter(path, charset)`. These hide the wrapper creation but not the encoding decision.

#### Production angle

Correct API choice protects data correctness. For example, a PDF response should stay on byte streams, while a CSV import should use text APIs with the expected charset and record parsing.

#### Traps / caveats

- Platform default charset can vary by runtime and deployment image.
- `Reader`/`Writer` do not make parsing safe; they only handle character conversion.
- Closing a wrapper usually closes the underlying stream.

#### Optional Anki

Q: Which classes bridge byte streams and character streams?
A: `InputStreamReader` and `OutputStreamWriter`.

</details>

<details>
<summary><strong>JIO-FUND-003. What is blocking I/O, and what does it mean for a Java thread?</strong></summary>

#### Short answer

Blocking I/O makes the calling thread wait until data is available, space is available, the operation completes, or an error occurs.

#### Interview answer

In blocking I/O, a call such as `read()` or `write()` does not return immediately if it cannot make progress. The Java thread is parked or blocked while the operating system waits for file, socket or device readiness.

This is simple to reason about: the code reads like normal sequential code. The trade-off is that each blocked operation occupies a thread. With platform threads, too many blocked threads can consume memory and scheduling capacity. With virtual threads, blocking I/O becomes cheaper, but timeouts, cancellation and capacity limits still matter.

#### Deep dive

Blocking is not always bad. Most backend code uses blocking JDBC, blocking file APIs and blocking HTTP clients successfully. It becomes a problem when concurrency is high, latency is unbounded, or thread pools are shared with unrelated work.

#### Production angle

Thread dumps often show many request threads blocked in socket reads, file reads or pool acquisition. The fix may be timeouts, bulkheads, smaller concurrency, streaming, backpressure or a different I/O model.

#### Traps / caveats

- Blocking does not mean CPU is busy.
- A blocked thread can still hold locks, transactions or request resources.
- Non-blocking I/O is not automatically faster; it is more complex.

#### Optional Anki

Q: What is the main cost of blocking I/O on platform threads?
A: Each waiting operation occupies a thread.

</details>

<details>
<summary><strong>JIO-FUND-004. How should backend code choose between reading all data at once and processing data incrementally?</strong></summary>

#### Short answer

Read all data only when the size is small, bounded and needed as a whole. Use incremental processing for large, untrusted or streaming inputs.

#### Interview answer

Reading all data into memory is convenient and sometimes correct: small config files, small templates, test fixtures or bounded payloads. But for request bodies, exports, imports, object-storage files and logs, the safer default is streaming or chunked processing.

The decision should be based on size limits, memory budget, latency, parsing needs, retry behavior and whether downstream consumers can keep up.

#### Deep dive

Incremental processing can mean copying bytes in chunks, parsing records one by one, using a bounded buffer, or streaming directly from an upstream source to a response. It reduces peak memory but requires careful error handling and cleanup.

#### Production angle

Unbounded `readAllBytes()`, `readString()` or `collect(toList())` on large input can create allocation spikes and OOMs. Good backend code sets maximum sizes, applies backpressure, closes resources and records metrics for bytes, records and failures.

#### Traps / caveats

- Streaming does not remove the need for size limits.
- Incremental parsing must handle records split across buffers.
- Reading all data may be fine for a 2 KB config file.

#### Optional Anki

Q: When is reading all input at once acceptable?
A: When the input is small, trusted or bounded, and needed as a whole.

</details>
