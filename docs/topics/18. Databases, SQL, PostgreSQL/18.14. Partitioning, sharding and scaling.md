# Partitioning, sharding and scaling

<a id="db-scale-001"></a>

<details>
<summary><strong>DB-SCALE-001. What is table partitioning in PostgreSQL?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Table partitioning is splitting one logical table into multiple physical child tables called partitions, while querying through the parent table.</p>
</td>
<td valign="top" width="50%">
<p>Секционирование таблицы (table partitioning) — это разбиение одной логической таблицы на несколько физических дочерних таблиц — секции (partitions), при этом приложение обычно обращается к родительская таблица (parent table).</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In PostgreSQL, a partitioned table is a logical parent. Actual rows live in partitions. A row is routed to a partition based on the partition key, for example date, region, tenant, or hash value.</p>
<p>Partitioning is usually used for very large tables, time-series data, audit logs, and workloads where queries naturally target a subset of data.</p>
</td>
<td valign="top" width="50%">
<p>В PostgreSQL секционированная таблица (partitioned table) — это логический родительская таблица. Реальные строки лежат в секции (partitions). Строка попадает в секция (partition) по ключ секционирования (partition key): например по дате, региону, tenant или hash-значению.</p>
<p>Partitioning обычно используют для очень больших таблиц, временных рядов (time-series) данных, журналов аудита и нагрузок, где запросы естественно читают только часть данных.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The key mechanism is partition pruning: the planner or executor can skip partitions that cannot contain matching rows. For example, a query for one month can avoid scanning partitions for other months.</p>
<p>Partitioning is not the same as an index. It reduces the number of physical relations to scan; indexes inside relevant partitions still matter.</p>
</td>
<td valign="top" width="50%">
<p>Ключевой механизм — отсечение секций (partition pruning): planner или executor может пропустить секции (partitions), которые точно не содержат нужные строки. Например, запрос за один месяц может не читать секции (partitions) за другие месяцы.</p>
<p>Partitioning — это не индекс. Оно уменьшает число физических relation для сканирования; индексы внутри нужных секции (partitions) всё равно важны.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, partitioning is useful for lifecycle management: dropping or detaching an old partition is often safer and faster than deleting millions of rows.</p>
<p>Before partitioning, check query patterns, partition count, maintenance overhead, indexes, constraints, and operational tooling.</p>
</td>
<td valign="top" width="50%">
<p>В production partitioning полезно для управления жизненным циклом данных: удаление или отсоединение старой секция (partition) часто безопаснее и быстрее, чем удаление миллионов строк.</p>
<p>Перед partitioning нужно проверить паттерны запросов, количество секции (partitions), overhead обслуживания, индексы, constraints и tooling.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Partitioning does not automatically make every query faster.</li>
<li>Bad partition key selection can make performance worse.</li>
<li>Too many partitions can slow planning and operations.</li>
<li>Unique constraints on partitioned tables have limitations.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Partitioning не ускоряет автоматически все запросы.</li>
<li>Плохой ключ секционирования (partition key) может ухудшить performance.</li>
<li>Слишком много секции (partitions) может замедлить planning и операции.</li>
<li>У unique constraints на partitioned tables есть ограничения.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is PostgreSQL table partitioning?<br>A: One logical parent table split into multiple physical partitions, with rows routed by a partition key.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое секционирование таблицы (table partitioning) в PostgreSQL?<br>A: Одна логическая родительская таблица (parent table), разделенная на физические секции (partitions), куда строки маршрутизируются по ключ секционирования (partition key).</p>
</td>
</tr>
</tbody>
</table>

</details>

<details>
<summary><strong>DB-SCALE-002. What is the difference between partitioning and sharding?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Partitioning usually splits data inside one database cluster; sharding splits data across multiple independent database nodes or clusters.</p>
</td>
<td valign="top" width="50%">
<p>Partitioning обычно делит данные внутри одного database cluster, а шардирование (sharding) — между несколькими независимыми database nodes или clusters.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Partitioning is a database-internal scaling and maintenance technique. The application may still see one logical table.</p>
<p>Sharding is a distributed architecture technique. Data is divided across separate database instances, and the application or infrastructure must route requests to the correct shard.</p>
</td>
<td valign="top" width="50%">
<p>Partitioning — это database-internal техника масштабирования и обслуживания. Приложение может видеть одну логическую таблицу.</p>
<p>Sharding — это distributed architecture technique. Данные разделены между отдельными database instances, а приложение или инфраструктура должны маршрутизировать запросы в правильный shard.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Partitioning helps when one table is too large to manage efficiently or queries naturally filter by partition key. Sharding helps when one database instance is not enough for storage, write throughput, or tenant isolation.</p>
<p>Partitioning does not remove the limits of one primary database server. Sharding introduces cross-shard query, transaction, rebalancing, and operational complexity.</p>
</td>
<td valign="top" width="50%">
<p>Partitioning помогает, когда одна таблица слишком большая для эффективного обслуживания или запросы естественно фильтруются по ключ секционирования (partition key). Sharding помогает, когда одного database instance недостаточно по storage, write throughput или tenant isolation.</p>
<p>Partitioning не снимает ограничения одного primary database server. Sharding добавляет сложности: межшардовый queries, distributed transactions, rebalancing и operations.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For a senior backend answer, explain the trade-off: partitioning is easier operationally but has limited scale-out; sharding scales further but makes consistency and queries harder.</p>
<p>Many systems should exhaust indexing, query optimization, read replicas, partitioning, and vertical scaling before introducing sharding.</p>
</td>
<td valign="top" width="50%">
<p>Для senior-ответа важно объяснить trade-off: partitioning проще операционно, но ограничено одним cluster; шардирование (sharding) масштабирует сильнее, но усложняет consistency и queries.</p>
<p>Многие системы должны сначала использовать indexes, query optimization, реплики для чтения (read replicas), partitioning и vertical scaling, а не сразу вводить шардирование (sharding).</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not call every partitioning scheme sharding.</li>
<li>Sharding usually changes application architecture.</li>
<li>Cross-shard joins and transactions are expensive or avoided.</li>
<li>Bad shard key selection is hard to fix later.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Не называй любое partitioning шардированием.</li>
<li>Sharding обычно меняет архитектуру приложения.</li>
<li>Cross-shard joins и transactions дороги или избегаются.</li>
<li>Плохой ключ шарда (shard key) потом трудно исправить.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Partitioning vs sharding?<br>A: Partitioning splits data inside one DB cluster; sharding splits data across independent DB nodes/clusters.</p>
</td>
<td valign="top" width="50%">
<p>Q: Partitioning vs шардирование (sharding)?<br>A: Partitioning делит данные внутри одного DB cluster; шардирование (sharding) делит данные между независимыми DB nodes/clusters.</p>
</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>DB-SCALE-003. What are range, list and hash partitioning?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Range partitions by value intervals, list partitions by explicit value lists, and hash partitions by hash remainder.</p>
</td>
<td valign="top" width="50%">
<p>Range делит по диапазонам значений, list — по заданным спискам значений, hash — по результату hash/remainder.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Range partitioning is common for dates: one partition per month or day. List partitioning is common for categories like country or region. Hash partitioning spreads data more evenly when no natural range exists.</p>
<p>Choosing the type depends on query predicates, data distribution, retention, and operational tasks.</p>
</td>
<td valign="top" width="50%">
<p>Секционирование по диапазону (range partitioning) часто используют для дат: секция (partition) на месяц или день. Секционирование по списку (list partitioning) подходит для категорий вроде country или region. Хеш-секционирование (hash partitioning) равномернее распределяет данные, когда нет естественного range.</p>
<p>Выбор типа зависит от query predicates, распределения данных, retention и операционных задач.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Range works best when queries contain conditions like <code>created_at &gt;= ... AND created_at &lt; ...</code>. List works when partitions map to known values. Hash can distribute writes but gives less natural pruning for range queries.</p>
<p>Composite partitioning is also possible through subpartitioning, but it increases complexity.</p>
</td>
<td valign="top" width="50%">
<p>Range лучше всего работает с условиями вроде <code>created_at &gt;= ... AND created_at &lt; ...</code>. List работает для фиксированных значений. Hash распределяет writes, но хуже подходит для range queries.</p>
<p>Также возможно subpartitioning, но оно увеличивает complexity.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use range partitioning for time-based retention. Use list partitioning when operations are naturally grouped by category. Use hash partitioning when you need distribution but not time-window lifecycle management.</p>
<p>Always test with production-like queries.</p>
</td>
<td valign="top" width="50%">
<p>Секционирование по диапазону (range partitioning) удобно для time-based retention. Секционирование по списку (list partitioning) — когда операции группируются по категории. Хеш-секционирование (hash partitioning) — когда нужно распределение, но не lifecycle по времени.</p>
<p>Всегда тестируй на production-like queries.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Hash partitioning is not the same as sharding.</li>
<li>Range partitions can become unbalanced if recent data is much hotter.</li>
<li>List partitions need a strategy for new values.</li>
<li>Default partitions can hide routing mistakes.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Хеш-секционирование (hash partitioning) — не то же самое, что шардирование (sharding).</li>
<li>Range секции (partitions) могут быть неравномерными, если свежие данные сильно горячее.</li>
<li>List секции (partitions) требуют стратегии для новых значений.</li>
<li>Default секции (partitions) могут скрывать ошибки маршрутизации.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Name three PostgreSQL partitioning strategies.<br>A: Range, list, and hash partitioning.</p>
</td>
<td valign="top" width="50%">
<p>Q: Назови три стратегии partitioning в PostgreSQL.<br>A: Range, list и hash partitioning.</p>
</td>
</tr>
</tbody>

<summary><strong>DB-SCALE-004. What is partition pruning?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Partition pruning is PostgreSQL skipping partitions that cannot contain rows matching the query conditions.</p>
</td>
<td valign="top" width="50%">
<p>Partition pruning — это когда PostgreSQL пропускает секции (partitions), которые не могут содержать строки, подходящие под условия запроса.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If a table is partitioned by <code>created_at</code> and the query asks for January only, PostgreSQL can avoid scanning February, March, and other partitions.</p>
<p>Pruning can happen during planning or execution, depending on whether partition key values are known early enough.</p>
</td>
<td valign="top" width="50%">
<p>Если таблица partitioned по <code>created_at</code> и запрос ищет только январь, PostgreSQL может не сканировать февраль, март и другие секции (partitions).</p>
<p>Pruning может происходить на этапе planning или execution, в зависимости от того, когда известны значения ключ секционирования (partition key).</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Partition pruning requires predicates that the planner can relate to the partition key. Functions or expressions around the partition key can prevent effective pruning.</p>
<p>Prepared statements and parameters can also affect whether pruning happens at planning time or execution time.</p>
</td>
<td valign="top" width="50%">
<p>Partition pruning требует predicates, которые planner может связать с ключ секционирования (partition key). Функции или выражения вокруг ключ секционирования (partition key) могут мешать effective pruning.</p>
<p>Подготовленные запросы (prepared statements) и параметры тоже влияют на то, произойдет pruning при planning или при execution.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, inspect plans to verify that only relevant partitions are scanned. If all partitions are scanned, the partitioning may not match the query pattern.</p>
<p>Poor pruning is a common reason partitioned tables disappoint.</p>
</td>
<td valign="top" width="50%">
<p>В production нужно смотреть планы и проверять, что сканируются только нужные секции (partitions). Если сканируются все секции (partitions), partitioning может не соответствовать query pattern.</p>
<p>Плохой pruning — частая причина, почему partitioned tables не дают ожидаемого эффекта.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Partitioning helps only when pruning actually works.</li>
<li>Wrapping partition keys in functions can block pruning.</li>
<li>Queries without partition-key filters may scan many partitions.</li>
<li>Too many partitions can increase planning overhead.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Partitioning помогает только когда pruning реально работает.</li>
<li>Функции вокруг ключ секционирования (partition key) могут мешать pruning.</li>
<li>Запросы без фильтра по ключ секционирования (partition key) могут сканировать много секции (partitions).</li>
<li>Слишком много секции (partitions) увеличивает planning overhead.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is partition pruning?<br>A: Skipping partitions that cannot match the query predicates.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое отсечение секций (partition pruning)?<br>A: Пропуск секции (partitions), которые не могут соответствовать predicates запроса.</p>
</td>

<details>
<summary><strong>DB-SCALE-005. When does partitioning improve query performance?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Partitioning improves performance when queries can prune most partitions or when maintenance operations become cheaper.</p>
</td>
<td valign="top" width="50%">
<p>Partitioning улучшает performance, когда запросы могут отсеять большинство секции (partitions) или когда maintenance операции становятся дешевле.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The best case is a large table with clear partition-key filters. For example, querying one month in a table partitioned by month can scan one partition instead of many years of data.</p>
<p>Partitioning can also help with bulk deletion, archiving, index maintenance, and vacuum pressure by isolating data into smaller physical units.</p>
</td>
<td valign="top" width="50%">
<p>Лучший случай — большая таблица с явным фильтром по ключ секционирования (partition key). Например, запрос за один месяц в таблице, partitioned by month, может читать одну секция (partition) вместо данных за годы.</p>
<p>Partitioning также помогает с bulk deletion, archiving, index maintenance и vacuum pressure, потому что данные разделены на меньшие physical units.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Performance benefit depends on pruning, partition-local indexes, partition count, and data distribution. Partitioning often improves predictable range queries but does not help arbitrary filters.</p>
<p>Partitioning can also reduce index height and index bloat per partition.</p>
</td>
<td valign="top" width="50%">
<p>Выигрыш зависит от pruning, секция (partition)-local indexes, количества секции (partitions) и распределения данных. Partitioning часто помогает predictable range queries, но не arbitrary filters.</p>
<p>Также partitioning может уменьшить высоту индекса и index bloat на секция (partition).</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Good use cases: time-series events, audit logs, large append-only tables, tenant or region separation with natural filters.</p>
<p>Measure with <code>EXPLAIN (ANALYZE, BUFFERS)</code>; do not assume partitioning is a free optimization.</p>
</td>
<td valign="top" width="50%">
<p>Хорошие use cases: временных рядов (time-series) events, журналов аудита, большие append-only таблицы, tenant/region separation с естественными фильтрами.</p>
<p>Нужно измерять через <code>EXPLAIN (ANALYZE, BUFFERS)</code>; не стоит считать partitioning бесплатной оптимизацией.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Partitioning helps fewer queries than people expect.</li>
<li>If queries do not filter by partition key, benefit may be small.</li>
<li>Local indexes still need to be designed.</li>
<li>Partitioning can increase operational complexity.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Partitioning помогает меньшему числу запросов, чем кажется.</li>
<li>Если запросы не фильтруют по ключ секционирования (partition key), benefit может быть маленьким.</li>
<li>Local indexes всё равно нужно проектировать.</li>
<li>Partitioning увеличивает operational complexity.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: When does partitioning improve query performance?<br>A: When predicates allow pruning most partitions or maintenance benefits dominate.</p>
</td>
<td valign="top" width="50%">
<p>Q: Когда partitioning улучшает query performance?<br>A: Когда predicates позволяют prune большинство секции (partitions) или важны maintenance benefits.</p>
</td>

<details>
<summary><strong>DB-SCALE-006. When can partitioning make performance worse?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Partitioning can hurt when pruning does not work, there are too many partitions, or queries need to touch most partitions.</p>
</td>
<td valign="top" width="50%">
<p>Partitioning может ухудшить performance, если pruning не работает, секции (partitions) слишком много или запросы всё равно читают большинство секции (partitions).</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Each partition is a separate relation with its own metadata and often its own indexes. Queries touching many partitions can have more planning and execution overhead.</p>

<summary><strong>🧠 DB-SCALE-008. What are the limitations of unique constraints on partitioned tables?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In PostgreSQL, unique or primary key constraints on partitioned tables generally must include all partition key columns.</p>
</td>
<td valign="top" width="50%">
<p>В PostgreSQL unique или primary key constraints на partitioned tables обычно должны включать все ключ секционирования (partition key) columns.</p>

</tr>
<tr>
<td valign="top" width="50%">

<p>For example, if orders are partitioned by <code>created_at</code>, a global unique constraint on just <code>order_number</code> is problematic unless the partition key is included or uniqueness is enforced differently.</p>
</td>
<td valign="top" width="50%">
<p>Причина в том, что PostgreSQL enforce-ит uniqueness через per-секция (partition) indexes. Если ключ секционирования (partition key) не входит в unique constraint, две строки в разных секции (partitions) могут иметь одинаковое значение, и одного global index для проверки нет.</p>
<p>Например, если orders partitioned by <code>created_at</code>, global unique constraint только по <code>order_number</code> проблематичен, если ключ секционирования (partition key) не включён или uniqueness не enforce-ится другим способом.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>This affects primary keys too. A primary key on a partitioned table must be compatible with the partitioning strategy.</p>
<p>Design identifiers and partition keys together, especially for multi-tenant or time-based tables.</p>
</td>
<td valign="top" width="50%">
<p>Это касается и primary keys. Primary key на секционированная таблица (partitioned table) должен быть совместим с partitioning strategy.</p>
<p>Идентификаторы и секция (partition) keys нужно проектировать вместе, особенно для multi-tenant или time-based tables.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, this limitation can surprise teams during migration to partitioning. If the existing table has a unique key that does not include the new partition key, migration may require application or schema redesign.</p>
<p>Possible alternatives include including the partition key, using a separate lookup table, or enforcing uniqueness at the application/service layer with care.</p>
</td>
<td valign="top" width="50%">
<p>В production это ограничение часто удивляет при миграции на partitioning. Если existing table имеет unique key без нового ключ секционирования (partition key), может потребоваться redesign приложения или схемы.</p>
<p>Варианты: включить ключ секционирования (partition key), использовать отдельную lookup table или аккуратно enforce uniqueness на уровне application/service.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>

<ul>
<li>Do not assume partitioned tables support arbitrary global unique constraints.</li>
<li>Adding the partition key to a primary key changes foreign keys and application references.</li>
<li>Application-level uniqueness is harder under concurrency.</li>
<li>A separate non-partitioned lookup table can help for global uniqueness.</li>

</td>
<td valign="top" width="50%">
<ul>
<li>Не стоит думать, что partitioned tables поддерживают любые global unique constraints.</li>

</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Bad keys also hurt operations: backups, restores, tenant moves, analytics, and incident debugging.</p>

</td>
<td valign="top" width="50%">
<p>Плохие keys вредят operations: резервные копии, restores, tenant moves, analytics и инцидент debugging.</p>

</td>
<td valign="top" width="50%">
<p>В production нужно моделировать load distribution и growth. Думай о крупнейших tenants/users, а не только о средних.</p>

<summary><strong>🧠 DB-SCALE-014. How do you handle cross-shard queries?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Usually by avoiding them in the hot path, denormalizing/read-modeling data, using async aggregation, or accepting fan-out for rare admin/reporting queries.</p>
</td>
<td valign="top" width="50%">
<p>Обычно их избегают в hot path, используют denormalized/модели чтения (read models), async aggregation или принимают fan-out для редких admin/reporting queries.</p>

</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Cross-shard queries are expensive because data is not local. The system may need to send queries to many shards, merge results, sort globally, and handle partial failures.</p>
<p>Design should prefer shard-local transactions and reads.</p>
</td>
<td valign="top" width="50%">
<p>Cross-shard queries дорогие, потому что data не local. Система может отправлять запросы на много shards, merge results, globally sort и обрабатывать partial failures.</p>

<td valign="top" width="50%">

</td>
<td valign="top" width="50%">
<p>Подходы: дублировать small reference data, поддерживать global indexes/search indexes, строить analytics pipelines, использовать materialized модели чтения (read models) или всегда routing by ключ шарда (shard key).</p>

</td>
<td valign="top" width="50%">
<p>В production нужно определить, разрешены ли межшардовый queries, их SLA и failure behavior. Нельзя допускать accidental unbounded fan-out в request path.</p>
<p>Нужно мониторить fan-out count, latency и partial errors.</p>

<summary><strong>🧠 DB-SCALE-015. What are the trade-offs between vertical scaling, read replicas, partitioning and sharding?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Vertical scaling is simplest but finite; read replicas scale reads; partitioning helps large-table pruning/maintenance; sharding scales writes/storage but is most complex.</p>
</td>
<td valign="top" width="50%">
<p>Vertical scaling проще всего, но ограничен; реплики для чтения (read replicas) масштабируют чтение; partitioning помогает pruning/maintenance больших таблиц; шардирование (sharding) масштабирует writes/storage, но сложнее всего.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Vertical scaling means bigger hardware. It is operationally simple but eventually hits cost or physical limits.</p>
<p>Read replicas offload reads but introduce replication lag and do not scale writes.</p>
<p>Partitioning improves large-table management and pruning inside one cluster.</p>
<p>Sharding distributes data across nodes but introduces distributed-systems complexity.</p>
</td>
<td valign="top" width="50%">
<p>Vertical scaling — это более мощное железо. Он прост операционно, но упирается в cost или physical limits.</p>
<p>Read replicas разгружают чтения, но дают задержка репликации (replication lag) и не масштабируют writes.</p>
<p>Partitioning улучшает управление большими таблицами и pruning внутри одного cluster.</p>
<p>Sharding распределяет data по nodes, но приносит distributed-systems complexity.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A senior answer should choose the least complex option that solves the actual bottleneck. If the bottleneck is CPU for reads, replicas may help. If it is old-data cleanup, partitioning may help. If writes and storage exceed one primary, sharding may be needed.</p>
<p>Each option affects consistency, operations, failure modes and cost differently.</p>
</td>
<td valign="top" width="50%">
<p>Senior-ответ должен выбирать наименее сложный вариант, который решает реальный узкое место. Если узкое место — CPU на чтениях, помогут replicas. Если old-data cleanup — partitioning. Если writes/storage больше одного primary — может понадобиться шардирование (sharding).</p>
<p>Каждый вариант по-разному влияет на consistency, operations, failure modes и cost.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use metrics before picking a scaling strategy: CPU, IO, locks, buffer hit ratio, query plans, connection pool, and write throughput.</p>
<p>Do not jump to sharding before optimizing schema, queries, indexes, and operational practices.</p>
</td>
<td valign="top" width="50%">
<p>Перед выбором scaling strategy нужны metrics: CPU, IO, locks, buffer hit ratio, query plans, пул соединений (connection pool) и write throughput.</p>
<p>Не переходи к шардирование (sharding) до оптимизации schema, queries, indexes и operations.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Read replicas can return stale data.</li>
<li>Partitioning is not horizontal write scaling.</li>
<li>Vertical scaling can hide inefficient queries temporarily.</li>
<li>Sharding has the highest long-term complexity.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Read replicas могут возвращать устаревшие данные (stale data).</li>
<li>Partitioning — не horizontal write scaling.</li>
<li>Vertical scaling может временно скрыть inefficient queries.</li>
<li>Sharding имеет самую высокую long-term complexity.</li>
</ul>
</td>
</tr>

</tr>
<tr>

</td>
<td valign="top" width="50%">
<p>Q: Расположи scaling options по сложности.<br>A: Vertical scaling/реплики для чтения (read replicas)/partitioning обычно проще; шардирование (sharding) обычно самый сложный.</p>
