# Pagination and query patterns in backend APIs

<a id="db-api-001"></a>

<details>
<summary><strong>DB-API-001. What is OFFSET/LIMIT pagination?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>OFFSET/LIMIT pagination returns a page by skipping N rows and then taking a limited number of rows.</p>
</td>
<td valign="top" width="50%">
<p>Пагинация <code>OFFSET/LIMIT</code> возвращает страницу, пропуская N строк и затем забирая ограниченное число строк.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example: <code>LIMIT 20 OFFSET 100</code> means skip the first 100 rows and return the next 20.</p>
<p>It is simple and supports page numbers, which makes it common in admin tables and small datasets.</p>
</td>
<td valign="top" width="50%">
<p>Пример: <code>LIMIT 20 OFFSET 100</code> означает пропустить первые 100 строк и вернуть следующие 20.</p>
<p>Этот подход простой и поддерживает номера страниц, поэтому часто встречается в административных таблицах и на небольших наборах данных.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The database still has to identify and discard skipped rows. With large offsets, work grows with the offset.</p>
<p>Results also require stable ordering, otherwise pages can be inconsistent.</p>
</td>
<td valign="top" width="50%">
<p>База всё равно должна найти и отбросить пропущенные строки. При больших offset объём работы растёт вместе с offset.</p>
<p>Также нужен стабильный порядок сортировки, иначе страницы могут быть неконсистентными.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use OFFSET/LIMIT for small datasets, internal tools, or shallow pages. For infinite scroll or large tables, prefer keyset/cursor pagination.</p>
<p>Always include deterministic ORDER BY.</p>
</td>
<td valign="top" width="50%">
<p>Используй <code>OFFSET/LIMIT</code> для маленьких наборов данных, внутренних инструментов или неглубоких страниц. Для infinite scroll или больших таблиц лучше keyset/курсорная пагинация.</p>
<p>Всегда добавляй детерминированный <code>ORDER BY</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Without ORDER BY, page order is not guaranteed.</li>
<li>Large offsets are slow.</li>
<li>Concurrent inserts/deletes can shift rows between pages.</li>
<li>COUNT(*) for total pages may be expensive.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Без <code>ORDER BY</code> порядок страниц не гарантирован.</li>
<li>Большие offset становятся медленными.</li>
<li>Конкурентные вставки и удаления могут сдвигать строки между страницами.</li>
<li><code>COUNT(*)</code> для общего числа страниц может быть дорогим.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does OFFSET do?<br>A: Skips a number of rows before returning the limit.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что делает OFFSET?<br>A: Пропускает заданное число строк перед возвратом результата.</p>
</td>
</tr>
</tbody>
</table>

</details>

<details>
<summary><strong>DB-API-002. Why can OFFSET pagination become slow on large tables?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Because PostgreSQL must still walk through the skipped rows before returning the requested page.</p>
</td>
<td valign="top" width="50%">
<p>Потому что PostgreSQL всё равно должен пройти пропущенные строки перед возвратом нужной страницы.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>With <code>OFFSET 100000 LIMIT 20</code>, the database cannot simply jump to row 100001 unless the access path supports it perfectly. It often reads many index/table entries and discards them.</p>
<p>The deeper the page, the more work.</p>
</td>
<td valign="top" width="50%">
<p>С <code>OFFSET 100000 LIMIT 20</code> база не может просто “прыгнуть” к строке 100001, если путь доступа не поддерживает это идеально. Часто она читает много записей индекса или таблицы и отбрасывает их.</p>
<p>Чем глубже страница, тем больше работы.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Even with an index, PostgreSQL may scan through index entries to reach the offset. If heap visits are needed, it can be even more expensive.</p>
<p>Large OFFSET also creates unstable UX under concurrent changes.</p>
</td>
<td valign="top" width="50%">
<p>Даже с индексом PostgreSQL может сканировать записи индекса, пока не дойдёт до offset. Если нужны обращения к таблице, это ещё дороже.</p>
<p>Большой <code>OFFSET</code> также создаёт нестабильный UX при конкурентных изменениях.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production APIs, large offsets can become a hidden denial-of-service vector. Add maximum page depth, use keyset pagination, or use search/index systems for deep browsing.</p>
<p>Monitor queries with high offsets.</p>
</td>
<td valign="top" width="50%">
<p>В production API большие offset могут стать скрытым denial-of-service вектором. Добавь максимальную глубину страниц, используй keyset-пагинацию или отдельные search/index системы для глубокого просмотра.</p>
<p>Мониторь запросы с большими offset.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Index does not eliminate offset cost completely.</li>
<li>Page number UX conflicts with performance on large data.</li>
<li>Deletes/inserts can duplicate or skip rows across pages.</li>
<li>Deep pagination should be restricted.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Индекс не полностью устраняет стоимость offset.</li>
<li>UX с номерами страниц конфликтует с производительностью на больших данных.</li>
<li>Вставки и удаления могут приводить к дублям или пропускам между страницами.</li>
<li>Глубокую пагинацию нужно ограничивать.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why is OFFSET slow for deep pages?<br>A: Rows before the requested page still need to be scanned/skipped.</p>
</td>
<td valign="top" width="50%">
<p>Q: Почему OFFSET медленный для глубоких страниц?<br>A: Строки перед запрошенной страницей всё равно нужно просканировать или пропустить.</p>
</td>
</tr>
</tbody>
</table>

<a id="db-api-003"></a>

<details>
<summary><strong>DB-API-003. What is keyset pagination?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Keyset pagination uses the last seen sort key instead of OFFSET to fetch the next page.</p>
</td>
<td valign="top" width="50%">
<p>Keyset-пагинация использует последний увиденный ключ сортировки вместо <code>OFFSET</code>, чтобы получить следующую страницу.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Instead of saying “skip 100000 rows”, the query says “give me rows after this last value”.</p>
<p>Example: <code>WHERE (created_at, id) &lt; (:last_created_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20</code>.</p>
</td>
<td valign="top" width="50%">
<p>Вместо “пропусти 100000 строк” запрос говорит: “дай строки после этого последнего значения”.</p>
<p>Пример: <code>WHERE (created_at, id) &lt; (:last_created_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Keyset pagination works best with a stable, indexed order. It can use an index range scan and does not pay the cost of skipping previous pages.</p>
<p>It is ideal for feeds, event streams, audit logs, and infinite scroll.</p>
</td>
<td valign="top" width="50%">
<p>Keyset-пагинация лучше всего работает со стабильным индексированным порядком. Она может использовать range scan по индексу и не платит стоимость пропуска предыдущих страниц.</p>
<p>Она хорошо подходит для лент, event streams, журналов аудита и infinite scroll.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, return an opaque cursor containing the last key values and sort direction. Keep cursor validation and versioning in mind.</p>
<p>Keyset pagination is usually not good for jumping to arbitrary page number.</p>
</td>
<td valign="top" width="50%">
<p>В production возвращай opaque cursor с последними значениями ключей и направлением сортировки. Учитывай валидацию и версионирование курсора.</p>
<p>Keyset-пагинация обычно плохо подходит для перехода к произвольному номеру страницы.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Ordering must be unique or have a tie-breaker.</li>
<li>Cursor values must match ORDER BY exactly.</li>
<li>Changing filters invalidates cursors.</li>
<li>Backward pagination needs separate design.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Порядок должен быть уникальным или иметь дополнительный ключ сортировки.</li>
<li>Значения курсора должны точно соответствовать <code>ORDER BY</code>.</li>
<li>Изменение фильтров делает курсор недействительным.</li>
<li>Обратная пагинация требует отдельного дизайна.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is keyset pagination?<br>A: Fetching the next page using the last seen sort key instead of OFFSET.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое keyset-пагинация (keyset pagination)?<br>A: Получение следующей страницы через последний увиденный ключ сортировки вместо OFFSET.</p>
</td>
</tr>
</tbody>
</table>

</details>

<details>
<summary><strong>DB-API-004. How would you implement cursor/keyset pagination?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Choose a deterministic ORDER BY, add a tie-breaker, index it, and use the last returned key values as the next cursor.</p>
</td>
<td valign="top" width="50%">
<p>Нужно выбрать детерминированный <code>ORDER BY</code>, добавить дополнительный ключ сортировки, создать индекс и использовать последние возвращённые значения ключей как следующий курсор.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For ordering by newest first, use <code>ORDER BY created_at DESC, id DESC</code>. The next page condition is <code>(created_at, id) &lt; (:lastCreatedAt, :lastId)</code>.</p>
<p>Encode cursor values into an opaque token so clients do not depend on internal details.</p>
</td>
<td valign="top" width="50%">
<p>Для сортировки “сначала новые” используй <code>ORDER BY created_at DESC, id DESC</code>. Условие следующей страницы: <code>(created_at, id) &lt; (:lastCreatedAt, :lastId)</code>.</p>
<p>Закодируй значения курсора в opaque token, чтобы клиенты не зависели от внутренних деталей.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The index should match filtering and ordering, for example <code>(tenant_id, created_at DESC, id DESC)</code> for tenant-scoped feeds.</p>
<p>Use a unique tie-breaker like id because timestamps can have duplicates.</p>
</td>
<td valign="top" width="50%">
<p>Индекс должен соответствовать фильтрации и сортировке, например <code>(tenant_id, created_at DESC, id DESC)</code> для tenant-scoped лент.</p>
<p>Используй уникальный дополнительный ключ сортировки вроде <code>id</code>, потому что timestamp-ы могут повторяться.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, include filters in cursor or reject cursor/filter mismatches. Sign or encrypt cursors if tampering matters.</p>
<p>Define cursor expiration and backward navigation separately.</p>
</td>
<td valign="top" width="50%">
<p>В production включай фильтры в курсор или отклоняй несовпадение курсора и фильтров. Подписывай или шифруй курсоры, если важна защита от подмены.</p>
<p>Отдельно определи срок действия курсора и обратную навигацию.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not use non-deterministic ordering.</li>
<li>Do not expose raw sensitive fields in cursor.</li>
<li>Null sort values require explicit handling.</li>
<li>Use consistent ASC/DESC semantics.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Не используй недетерминированный порядок.</li>
<li>Не раскрывай чувствительные поля в курсоре в сыром виде.</li>
<li>Значения <code>NULL</code> в сортировке требуют явной обработки.</li>
<li>Используй согласованную семантику <code>ASC</code>/<code>DESC</code>.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Keyset pagination needs what tie-breaker?<br>A: A unique stable column like id after the main sort key.</p>
</td>
<td valign="top" width="50%">
<p>Q: Какой дополнительный ключ сортировки нужен keyset-пагинации?<br>A: Уникальная стабильная колонка, например <code>id</code>, после основного ключа сортировки.</p>
</td>
</tr>
</tbody>
</table>

<summary><strong>DB-API-005. What are the trade-offs between OFFSET pagination and keyset pagination?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>OFFSET is simpler and supports page numbers; keyset is faster and more stable for large/deep pagination but does not support arbitrary page jumps easily.</p>
</td>
<td valign="top" width="50%">
<p><code>OFFSET</code> проще и поддерживает номера страниц; keyset быстрее и стабильнее для большой или глубокой пагинации, но плохо поддерживает произвольные переходы по номерам страниц.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>OFFSET is good for admin lists, small tables, and shallow pages. Keyset is good for user feeds, infinite scroll, large tables, and high-traffic endpoints.</p>
<p>OFFSET works with arbitrary sorting more easily; keyset requires a careful indexed ordering.</p>
</td>
<td valign="top" width="50%">
<p><code>OFFSET</code> хорош для админских списков, маленьких таблиц и неглубоких страниц. Keyset хорош для пользовательских лент, infinite scroll, больших таблиц и высоконагруженных endpoint-ов.</p>
<p><code>OFFSET</code> проще работает с произвольной сортировкой; keyset требует аккуратного индексированного порядка.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>OFFSET page N can be requested directly. Keyset uses cursor chain: next page depends on previous page's last key.</p>
<p>Under concurrent writes, keyset is usually less prone to duplicates/skips when ordered by immutable keys.</p>
</td>
<td valign="top" width="50%">
<p>Страницу N через <code>OFFSET</code> можно запросить напрямую. Keyset использует цепочку курсоров: следующая страница зависит от последнего ключа предыдущей страницы.</p>
<p>При конкурентных записях keyset обычно меньше подвержен дублям и пропускам, если порядок строится по неизменяемым ключам.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For public APIs, choose based on UX: page numbers vs endless scrolling. For performance-critical endpoints, keyset is usually safer.</p>
<p>Document cursor semantics in API contracts.</p>
</td>
<td valign="top" width="50%">
<p>Для публичных API выбирай по UX: номера страниц или бесконечная прокрутка. Для критичных к производительности endpoint-ов keyset обычно безопаснее.</p>
<p>Документируй семантику курсора в API-контрактах.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Keyset is not always trivial with complex sorting.</li>
<li>OFFSET can be acceptable with small limits and max page depth.</li>
<li>Keyset requires stable order.</li>
<li>Total count can be expensive for both.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Keyset не всегда прост при сложной сортировке.</li>
<li><code>OFFSET</code> приемлем при маленьких лимитах и ограниченной глубине страниц.</li>
<li>Keyset требует стабильного порядка.</li>
<li>Точный общий count может быть дорогим для обоих подходов.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: OFFSET vs keyset?<br>A: OFFSET is simple/page-number based; keyset is faster for deep pages but cursor-based.</p>
</td>
<td valign="top" width="50%">
<p>Q: OFFSET vs keyset?<br>A: OFFSET проще и основан на номерах страниц; keyset быстрее для глубоких страниц, но основан на курсоре.</p>
</td>
</tr>
</tbody>

<details>
<summary><strong>DB-API-006. How can indexes support pagination?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Indexes can provide rows in the required filter and sort order, reducing scanning and sorting work.</p>
</td>
<td valign="top" width="50%">
<p>Индексы могут отдавать строки в нужном порядке фильтрации и сортировки, уменьшая объём сканирования и сортировки.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For pagination, the index should often start with equality filters, then sorting keys. Example: <code>(tenant_id, created_at DESC, id DESC)</code>.</p>
<p>This lets PostgreSQL quickly find the next rows for a tenant in the correct order.</p>
</td>
<td valign="top" width="50%">
<p>Для пагинации индекс часто должен начинаться с фильтров по равенству, а затем содержать ключи сортировки. Пример: <code>(tenant_id, created_at DESC, id DESC)</code>.</p>
<p>Так PostgreSQL может быстро найти следующие строки для tenant в правильном порядке.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For OFFSET, an index may avoid a sort but still has to skip rows. For keyset, the index can do a range scan starting after the cursor.</p>
<p>Index-only scans can help if selected columns are covered and visibility map allows it.</p>
</td>
<td valign="top" width="50%">
<p>Для <code>OFFSET</code> индекс может убрать сортировку, но строки всё равно придётся пропускать. Для keyset индекс может выполнить range scan, начиная после курсора.</p>
<p>Index-only scan помогает, если выбранные колонки покрыты индексом и visibility map это позволяет.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, always inspect the query plan. If the database sorts large result sets or scans many rows, index design may not match pagination pattern.</p>
<p>Use realistic filters and data distribution when testing.</p>
</td>
<td valign="top" width="50%">
<p>В production всегда проверяй план запроса. Если база сортирует большие результаты или сканирует много строк, дизайн индекса может не соответствовать паттерну пагинации.</p>
<p>Тестирование должно использовать реалистичные фильтры и распределение данных.</p>

</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Index column order matters.</li>
<li>ORDER BY direction can matter.</li>
<li>Covering too many columns increases index size.</li>
<li>Dynamic filters make one perfect index impossible.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Порядок колонок в индексе важен.</li>
<li>Направление <code>ORDER BY</code> тоже может быть важным.</li>
<li>Покрытие слишком большого числа колонок увеличивает размер индекса.</li>
<li>Динамические фильтры делают “один идеальный индекс” почти невозможным.</li>

<summary><strong>DB-API-007. Why is stable ordering important for pagination?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Stable ordering prevents rows from appearing in random order, being duplicated, or being skipped between pages.</p>
</td>
<td valign="top" width="50%">
<p>Стабильный порядок предотвращает случайную сортировку, дубли и пропуски строк между страницами.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If multiple rows have the same sort value, ordering only by that value is not deterministic. Add a unique tie-breaker like <code>id</code>.</p>
<p>Without ORDER BY, PostgreSQL does not guarantee row order at all.</p>
</td>
<td valign="top" width="50%">
<p>Если несколько строк имеют одинаковое значение сортировки, сортировка только по этому значению недетерминирована. Добавь уникальный дополнительный ключ, например <code>id</code>.</p>
<p>Без <code>ORDER BY</code> PostgreSQL вообще не гарантирует порядок строк.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For keyset pagination, cursor condition must match ORDER BY exactly. For example, if ORDER BY is <code>created_at DESC, id DESC</code>, cursor comparison should use both fields.</p>
<p>Stable ordering is also important for caching and reproducible API behavior.</p>
</td>
<td valign="top" width="50%">
<p>Для keyset-пагинации условие курсора должно точно соответствовать <code>ORDER BY</code>. Например, если порядок <code>created_at DESC, id DESC</code>, сравнение курсора должно использовать оба поля.</p>
<p>Стабильный порядок также важен для кэширования и воспроизводимого поведения API.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production APIs, always specify deterministic ordering. Avoid relying on physical table order or implicit primary-key order.</p>
<p>Document ordering so clients understand page behavior.</p>
</td>
<td valign="top" width="50%">
<p>В production API всегда задавай детерминированный порядок. Не полагайся на физический порядок таблицы или неявный порядок первичного ключа.</p>
<p>Документируй порядок сортировки, чтобы клиенты понимали поведение страниц.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>ORDER BY created_at alone is not stable if timestamps duplicate.</li>
<li>Concurrent writes still affect pagination, but stable order reduces surprises.</li>
<li>NULL ordering should be explicit.</li>
<li>Changing default order is a breaking API change.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li><code>ORDER BY created_at</code> без дополнительного ключа нестабилен, если timestamp-ы повторяются.</li>
<li>Конкурентные записи всё равно влияют на пагинацию, но стабильный порядок уменьшает сюрпризы.</li>
<li>Порядок <code>NULL</code> должен быть явным.</li>
<li>Изменение порядка по умолчанию — ломающая смена API.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: How make pagination order stable?<br>A: Add a deterministic ORDER BY with a unique tie-breaker.</p>
</td>
<td valign="top" width="50%">
<p>Q: Как сделать порядок пагинации стабильным?<br>A: Добавить детерминированный ORDER BY с уникальным дополнительным ключом сортировки.</p>

<summary><strong>DB-API-008. How would you paginate by created_at and id?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Order by created_at plus id as a tie-breaker, and use both values in the cursor condition.</p>
</td>
<td valign="top" width="50%">
<p>Сортируй по <code>created_at</code> плюс <code>id</code> как дополнительному ключу и используй оба значения в условии курсора.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For newest first: <code>ORDER BY created_at DESC, id DESC</code>. Next page: rows where <code>(created_at, id) &lt; (:lastCreatedAt, :lastId)</code>.</p>
<p>Use a matching index, often <code>(created_at DESC, id DESC)</code> or with tenant/filter columns before it.</p>
</td>
<td valign="top" width="50%">
<p>Для “сначала новые”: <code>ORDER BY created_at DESC, id DESC</code>. Следующая страница: строки, где <code>(created_at, id) &lt; (:lastCreatedAt, :lastId)</code>.</p>
<p>Используй подходящий индекс, часто <code>(created_at DESC, id DESC)</code> или тот же порядок с tenant/filter колонками перед ним.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The tuple comparison must match direction. For ascending order, use <code>&gt;</code> instead of <code>&lt;</code>.</p>

</td>
<td valign="top" width="50%">
<p>Сравнение кортежей должно соответствовать направлению сортировки. Для ascending order используй <code>&gt;</code> вместо <code>&lt;</code>.</p>
<p>Если <code>created_at</code> может быть <code>NULL</code>, либо запрети <code>NULL</code>, либо явно определи порядок <code>NULL</code> и логику курсора.</p>

</tr>

<th colspan="2" align="left">Production angle</th>
</tr>

</td>
<td valign="top" width="50%">
<p>В production возвращай курсор в ответе API как opaque token. Проверяй, что клиент использует его с теми же фильтрами.</p>
<p>Используй <code>id</code> как стабильный дополнительный ключ сортировки, потому что <code>created_at</code> не гарантированно уникален.</p>

<li>Do not let clients edit cursor internals.</li>

<td valign="top" width="50%">
<ul>

<li>Направление <code>ORDER BY</code> имеет значение.</li>
<li>Точность часов может создавать одинаковые timestamp-ы.</li>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
