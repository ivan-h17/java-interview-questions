# Replication and high availability

<a id="db-repl-001"></a>

<details>
<summary><strong>🧠 DB-REPL-001. What is physical replication?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Physical replication copies PostgreSQL data at the storage/WAL level, producing a byte-for-byte compatible standby.</p>
</td>
<td valign="top" width="50%">
<p>Физическая репликация (physical replication) копирует данные PostgreSQL на уровне storage/WAL, создавая byte-compatible standby.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In PostgreSQL, physical replication streams WAL records from primary to standby. The standby replays the same low-level changes and becomes a copy of the primary cluster.</p>
<p>It is commonly used for high availability, failover, backups, and read-only replicas.</p>
</td>
<td valign="top" width="50%">
<p>В PostgreSQL физическая репликация (physical replication) передаёт записи WAL с primary на standby. Standby replay-ит те же низкоуровневые изменения и становится копией primary cluster.</p>
<p>Её часто используют для высокая доступность (high availability), переключение при отказе (failover), резервные копии и read-only replicas.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Physical replication is usually database-cluster oriented, not selective per table. The standby has the same database structure and cannot independently change replicated data.</p>
<p>Because changes are WAL-level, this replication is efficient and faithful but less flexible than logical replication.</p>
</td>
<td valign="top" width="50%">
<p>Физическая репликация (physical replication) обычно работает на уровне database cluster, а не выборочно по таблицам. Standby имеет ту же структуру БД и не может независимо менять replicated data.</p>
<p>Поскольку изменения идут на WAL-level, replication эффективная и точная, но менее гибкая, чем логическая репликация (logical replication).</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, physical replication is the standard building block for hot standby and failover. You must monitor lag, WAL retention, replication slots, disk usage, and failover procedures.</p>
<p>Read-only traffic can be sent to standbys, but the application must tolerate lag.</p>
</td>
<td valign="top" width="50%">
<p>В production физическая репликация (physical replication) — стандартный building block для hot standby и переключение при отказе (failover). Нужно мониторить lag, WAL retention, слоты репликации (replication slots), disk usage и переключение при отказе (failover) procedures.</p>
<p>Read-only traffic можно отправлять на standbys, но приложение должно учитывать lag.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Physical replication is not table-level filtering.</li>
<li>Standby queries are read-only.</li>
<li>Replica lag can break read-after-write expectations.</li>
<li>A failed replication slot can retain WAL and fill disk.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Физическая репликация (physical replication) — не table-level filtering.</li>
<li>Запросы на standby read-only.</li>
<li>Replica lag может сломать read-after-write expectations.</li>
<li>Проблемный слот репликации (replication slot) может удерживать WAL и заполнить disk.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does physical replication copy?<br>A: WAL/storage-level changes, producing a standby copy of the primary.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что копирует физическая репликация (physical replication)?<br>A: WAL/storage-level изменения, создавая standby-копию primary.</p>
</td>
</tr>
</tbody>
</table>

</details>

<details>
<summary><strong>🧠 DB-REPL-002. What is logical replication?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Logical replication replicates data changes in logical form, usually per table/publication, rather than copying the whole storage layout.</p>
</td>
<td valign="top" width="50%">
<p>Логическая репликация (logical replication) реплицирует изменения данных в logical форме, обычно по tables/publications, а не копирует весь storage layout.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>PostgreSQL logical replication uses publications and subscriptions. A publisher defines which tables to publish, and a subscriber receives row-level changes.</p>
<p>It is useful for selective replication, migrations, data distribution, integration pipelines, and some zero-downtime upgrade scenarios.</p>
</td>
<td valign="top" width="50%">
<p>PostgreSQL логическая репликация (logical replication) использует publications и subscriptions. Publisher определяет, какие tables публиковать, а subscriber получает row-level changes.</p>
<p>Она полезна для selective replication, migrations, распределение данных, integration pipelines и некоторых zero-downtime upgrade scenarios.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Logical replication is based on logical decoding of WAL. It can replicate INSERT/UPDATE/DELETE/TRUNCATE operations, but schema changes require separate handling.</p>
<p>It can work across different major versions more flexibly than physical replication, but it has its own limitations.</p>
</td>
<td valign="top" width="50%">
<p>Логическая репликация (logical replication) основана на logical decoding WAL. Она может реплицировать INSERT/UPDATE/DELETE/TRUNCATE, но schema changes нужно обрабатывать отдельно.</p>
<p>Она гибче физическая репликация (physical replication) между разными major versions, но имеет свои ограничения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, logical replication needs careful monitoring: replication lag, slot retention, conflicts, missing primary keys, schema drift, and initial data copy.</p>
<p>It is not a magic distributed database.</p>
</td>
<td valign="top" width="50%">
<p>В production логическая репликация (logical replication) требует monitoring: задержка репликации (replication lag), slot retention, conflicts, missing primary keys, расхождение схем (schema drift) и initial data copy.</p>
<p>Это не magic distributed database.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>DDL is not automatically handled like DML.</li>
<li>Tables usually need replica identity for updates/deletes.</li>
<li>Large transactions can create lag.</li>
<li>Conflicts and schema drift must be managed.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>DDL не обрабатывается автоматически как DML.</li>
<li>Для updates/deletes обычно нужна replica identity.</li>
<li>Большие transactions могут создать lag.</li>
<li>Conflicts и расхождение схем (schema drift) нужно управлять.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is logical replication useful for?<br>A: Selective table-level replication, migrations, integrations, and data distribution.</p>
</td>
<td valign="top" width="50%">
<p>Q: Для чего полезна логическая репликация (logical replication)?<br>A: Selective table-level replication, migrations, integrations и распределение данных.</p>
</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>🧠 DB-REPL-003. What is streaming replication?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Streaming replication continuously sends WAL records from a primary server to standby servers.</p>
</td>
<td valign="top" width="50%">
<p>Streaming replication непрерывно отправляет записи WAL с primary server на standby servers.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Instead of waiting for WAL archive files, standby servers receive WAL over a replication connection and replay it quickly.</p>
<p>This is the common mechanism behind hot standby replicas in PostgreSQL.</p>
</td>
<td valign="top" width="50%">
<p>Вместо ожидания WAL archive files, standby servers получают WAL по replication connection и быстро replay-ят его.</p>
<p>Это common mechanism behind hot standby replicas в PostgreSQL.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Streaming replication can be asynchronous or synchronous. In asynchronous mode, primary commits do not wait for standby. In synchronous mode, commits can wait for acknowledgements from configured synchronous standbys.</p>
<p>The trade-off is latency vs durability/consistency.</p>
</td>
<td valign="top" width="50%">
<p>Streaming replication может быть asynchronous или synchronous. В asynchronous mode primary commits не ждут standby. В synchronous mode commits могут ждать acknowledgements от configured synchronous standbys.</p>
<p>Trade-off — latency vs durability/consistency.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Monitor replication lag, WAL sender/receiver status, network, disk IO, and standby replay delay.</p>
<p>Do not send latency-sensitive read-after-write traffic to a lagging replica.</p>
</td>
<td valign="top" width="50%">
<p>Нужно мониторить задержка репликации (replication lag), процесс отправки WAL (WAL sender)/receiver status, network, disk IO и standby replay delay.</p>
<p>Не отправляй latency-sensitive read-after-write traffic на lagging replica.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Network issues can cause lag.</li>
<li>Synchronous replication can add commit latency.</li>
<li>A standby can be available but stale.</li>
<li>Replication does not replace backups.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Network issues могут создать lag.</li>
<li>Synchronous replication может добавить commit latency.</li>
<li>Standby может быть available, но stale.</li>
<li>Replication не заменяет резервные копии.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does streaming replication stream?<br>A: WAL records from primary to standby.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что передает потоковая репликация (streaming replication)?<br>A: записи WAL с primary на standby.</p>
</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>🧠 DB-REPL-004. What is a replication slot?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A replication slot tells PostgreSQL to retain WAL needed by a replica or logical consumer until that consumer confirms it has received it.</p>
</td>
<td valign="top" width="50%">
<p>Replication slot говорит PostgreSQL удерживать WAL, нужный replica или logical consumer, пока consumer не подтвердит получение.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Slots prevent a replica or logical subscriber from falling behind and losing required WAL. Without a slot, old WAL might be removed before the consumer reads it.</p>
<p>Slots can be physical or logical.</p>
</td>
<td valign="top" width="50%">
<p>Slots предотвращают ситуацию, когда replica или logical subscriber отстаёт и теряет нужный WAL. Без slot старый WAL может быть удалён до чтения consumer.</p>
<p>Slots бывают physical и logical.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A slot has a restart position. PostgreSQL keeps WAL from that point so the consumer can resume.</p>
<p>This reliability comes with a risk: if a slot is inactive or consumer is broken, WAL can accumulate and fill disk.</p>
</td>
<td valign="top" width="50%">
<p>У slot есть restart position. PostgreSQL хранит WAL с этой точки, чтобы consumer мог продолжить.</p>
<p>Эта надежность имеет risk: если slot inactive или consumer сломан, WAL может накапливаться и заполнить disk.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, monitor inactive slots, retained WAL size, lag, and disk usage. Drop unused slots intentionally.</p>
<p>Useful checks include <code>pg_replication_slots</code> columns such as <code>active</code>, <code>restart_lsn</code>, <code>confirmed_flush_lsn</code>, and retained WAL estimated with <code>pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)</code>.</p>
<p>Slots are powerful but dangerous when ignored.</p>
</td>
<td valign="top" width="50%">
<p>В production нужно отслеживать неактивные slots, объем удержанного WAL, lag и свободное место на диске. Неиспользуемые slots удаляют только осознанно.</p>
<p>Практичные проверки: <code>pg_replication_slots</code>, поля <code>active</code>, <code>restart_lsn</code>, <code>confirmed_flush_lsn</code>, а также оценка retained WAL через <code>pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)</code>.</p>
<p>Slots мощные, но опасны, если их игнорировать.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Slots protect consumers but can fill disk.</li>
<li>Dropping a slot can break a lagging consumer.</li>
<li>Logical slots are common for CDC tools.</li>
<li><code>max_slot_wal_keep_size</code> can limit damage, but the consumer can still break if required WAL is removed.</li>
<li>Slots are not backups.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Slots защищают consumers, но могут заполнить disk.</li>
<li>Drop slot может сломать lagging consumer.</li>
<li>Logical slots часто используются CDC tools.</li>
<li><code>max_slot_wal_keep_size</code> ограничивает ущерб, но consumer всё равно может сломаться, если нужный WAL удалён.</li>
<li>Slots — не резервные копии.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Main risk of replication slots?<br>A: An inactive slot can retain WAL until disk fills up.</p>
</td>
<td valign="top" width="50%">
<p>Q: Главный риск слоты репликации (replication slots)?<br>A: Inactive slot может удерживать WAL, пока disk не заполнится.</p>
</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>DB-REPL-005. What is replication lag?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Replication lag is how far a replica is behind the primary in receiving, writing, flushing, or replaying changes.</p>
</td>
<td valign="top" width="50%">
<p>Replication lag — это насколько replica отстает от primary по receiving, writing, flushing или replaying changes.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A replica may have received WAL but not replayed it yet. From the application point of view, the important question is usually: can a read from replica see the write that just committed on primary?</p>
<p>Lag can be measured in bytes, time, or LSN difference, depending on the view and metric.</p>
</td>
<td valign="top" width="50%">
<p>Replica может уже получить WAL, но ещё не replay-ить его. С точки зрения приложения важный вопрос: увидит ли чтение с replica запись, только что committed на primary?</p>
<p>Lag может измеряться в bytes, time или LSN difference, в зависимости от view и metric.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Lag sources include network, standby IO, long-running queries on standby, high write volume, checkpoints, replication slot retention, and CPU pressure.</p>
<p>In physical streaming replication, monitor write_lag, flush_lag, replay_lag and LSN positions.</p>
<p>On the primary, <code>pg_stat_replication</code> exposes <code>sent_lsn</code>, <code>write_lsn</code>, <code>flush_lsn</code>, <code>replay_lsn</code>, <code>write_lag</code>, <code>flush_lag</code>, and <code>replay_lag</code>. <code>pg_wal_lsn_diff</code> helps estimate byte lag.</p>
</td>
<td valign="top" width="50%">
<p>Источники lag: network, standby IO, long-running queries на standby, high write volume, checkpoints, слот репликации (replication slot) retention и CPU pressure.</p>
<p>В physical потоковая репликация (streaming replication) мониторят write_lag, flush_lag, replay_lag и LSN positions.</p>
<p>На primary view <code>pg_stat_replication</code> показывает <code>sent_lsn</code>, <code>write_lsn</code>, <code>flush_lsn</code>, <code>replay_lsn</code>, <code>write_lag</code>, <code>flush_lag</code> и <code>replay_lag</code>. <code>pg_wal_lsn_diff</code> помогает оценить lag в bytes.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, lag affects correctness. After a user writes data, routing the next read to a lagging replica can show stale data.</p>
<p>Solutions include read-your-writes routing to primary, sticky sessions, lag-aware routing, waiting for replay, or accepting eventual consistency.</p>
</td>
<td valign="top" width="50%">
<p>В production lag влияет на correctness. После записи пользователя следующий read на lagging replica может показать устаревшие данные (stale data).</p>
<p>Решения: routing read-your-writes на primary, sticky sessions, lag-aware routing, waiting for replay или acceptance согласованность в конечном счёте (eventual consistency).</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>A replica can be healthy but stale.</li>
<li>Time lag and byte lag tell different things.</li>
<li>Long standby queries can delay replay.</li>
<li>Read replicas do not scale writes.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Replica может быть healthy, но stale.</li>
<li>Time lag и byte lag говорят о разном.</li>
<li>Long queries на standby могут задерживать replay.</li>
<li>Read replicas не масштабируют writes.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is replication lag?<br>A: How far a replica is behind the primary in applying changes.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое задержка репликации (replication lag)?<br>A: Насколько replica отстает от primary в применении изменений.</p>
</td>
</tr>
</tbody>

<a id="db-repl-006"></a>

<details>
<summary><strong>DB-REPL-006. Why can reading from replicas be dangerous after writes?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Because replicas may be stale due to replication lag, so a read immediately after a write may not see the committed data.</p>
</td>
<td valign="top" width="50%">
<p>Потому что replicas могут быть stale из-за задержка репликации (replication lag), поэтому read сразу после write может не увидеть committed data.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The primary commits the transaction first, and the replica applies WAL later. In asynchronous replication this delay is expected.</p>
<p>This can break user flows like create order → redirect to order page if the order page reads from replica.</p>
</td>
<td valign="top" width="50%">
<p>Primary сначала commit-ит transaction, а replica применяет WAL позже. В асинхронная репликация (asynchronous replication) такая задержка ожидаема.</p>
<p>Это может сломать flows вроде create order → redirect to order page, если page читает с replica.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The problem is read-after-write consistency. The system may be eventually consistent, but users often expect their own writes to be visible immediately.</p>
<p>Different consistency requirements can apply to different reads.</p>
</td>
<td valign="top" width="50%">
<p>Проблема называется консистентность чтения после записи (read-after-write consistency). Система может быть согласованной в конечном счёте (eventually consistent), но пользователи часто ожидают сразу видеть свои writes.</p>
<p>У разных reads могут быть разные consistency requirements.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Production patterns: route reads after writes to primary for a period, use sticky sessions, check replica lag, include causal tokens/LSNs, or block until replica catches up.</p>
<p>Do not blindly load-balance all reads to replicas.</p>
</td>
<td valign="top" width="50%">
<p>Production patterns: временно route reads после writes на primary, использовать sticky sessions, check replica lag, causal tokens/LSNs или ждать catch-up replica.</p>
<p>Нельзя blind load-balance все reads на replicas.</p>

<summary><strong>🧠 DB-REPL-014. How would you design application behavior when a read replica is lagging?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use lag-aware routing: send consistency-sensitive reads to primary, avoid lagging replicas, or degrade gracefully.</p>
</td>
<td valign="top" width="50%">
<p>Использовать lag-aware routing: consistency-sensitive reads отправлять на primary, избегать lagging replicas или degrade gracefully.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The application should know which reads require freshness. For example, after a write, read the user's own data from primary for a short time.</p>
<p>For less critical pages, stale data may be acceptable with clear semantics.</p>
</td>
<td valign="top" width="50%">
<p>Приложение должно знать, какие reads требуют freshness. Например, после write читать данные этого user с primary некоторое время.</p>
<p>Для менее критичных страниц устаревшие данные (stale data) может быть acceptable с clear semantics.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Implementation options: track replica lag metrics, set a maximum lag threshold, remove lagging replicas from read pool, use sticky primary reads after writes, or wait until a replica reaches a known LSN.</p>
<p>A common senior-level design is a causal token: after a write, remember an LSN/timestamp and route reads only to replicas that have replayed at least that point; otherwise use primary.</p>
<p>Some systems use causal tokens to route reads safely.</p>
</td>
<td valign="top" width="50%">
<p>Варианты реализации: отслеживать lag replicas, задать максимальный порог lag, убирать отстающие replicas из read pool, читать с primary после writes или ждать, пока replica достигнет известного LSN.</p>
<p>Частый senior-level подход — causal token: после write запомнить LSN/timestamp и читать только с replicas, которые replay-нули хотя бы эту точку; иначе читать с primary.</p>
<p>Некоторые системы используют causal tokens для безопасного read routing.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">

<p>Test how the app behaves when replica lag spikes.</p>
</td>
<td valign="top" width="50%">
<p>В production lag behavior должен быть visible: metrics, alerts, feature flags, fallback to primary и load protection, чтобы fallback не перегрузил primary.</p>
<p>Нужно тестировать app behavior при replica lag spikes.</p>

<td valign="top" width="50%">
