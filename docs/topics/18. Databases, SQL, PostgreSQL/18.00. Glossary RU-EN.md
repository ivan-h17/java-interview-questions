<tr>
<th colspan="3" align="left">Core SQL And Relational Model</th>
</tr>
<tr>
<td>декларативный язык</td>
<td>declarative language</td>
<td>Describes the desired result, not step-by-step execution.</td>
</tr>
<tr>
<td>реляционная база данных</td>
<td>relational database</td>
<td>A database model based on tables, rows, columns, relations, and constraints.</td>
</tr>
<tr>
<td>СУБД</td>
<td>DBMS</td>
<td>Database Management System.</td>
</tr>
<tr>
<td>отсутствующее / неизвестное значение</td>
<td>NULL</td>
<td>SQL marker for absent, unknown, or not applicable value.</td>
</tr>
<tr>
<td>трехзначная логика</td>
<td>three-valued logic</td>
<td>SQL boolean logic with <code>TRUE</code>, <code>FALSE</code>, and <code>UNKNOWN</code>.</td>
</tr>
<tr>
<th colspan="3" align="left">SQL Command Groups</th>
</tr>
<tr>
<td>определение данных / изменение структуры</td>
<td>DDL / Data Definition Language</td>
<td>SQL commands for schema objects: <code>CREATE</code>, <code>ALTER</code>, <code>DROP</code>.</td>
</tr>
<tr>
<td>манипуляция данными / работа со строками</td>
<td>DML / Data Manipulation Language</td>
<td>SQL commands for reading and modifying rows: <code>SELECT</code>, <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code>.</td>
</tr>
<tr>
<td>управление доступом</td>
<td>DCL / Data Control Language</td>
<td>SQL commands for permissions: <code>GRANT</code>, <code>REVOKE</code>.</td>
</tr>
<tr>
<td>управление транзакциями</td>
<td>TCL / Transaction Control Language</td>
<td>SQL commands for transaction boundaries: <code>BEGIN</code>, <code>COMMIT</code>, <code>ROLLBACK</code>, <code>SAVEPOINT</code>.</td>
</tr>
<tr>
<th colspan="3" align="left">Constraints And Keys</th>
</tr>
<tr>
<td>ограничение</td>
<td>constraint</td>
<td>Database rule that protects data integrity.</td>
</tr>
<tr>
<td>первичный ключ</td>
<td>primary key</td>
<td>Main non-null unique identifier of a table row.</td>
</tr>
<tr>
<td>уникальное ограничение</td>
<td>unique constraint</td>
<td>Rule that prevents duplicate values according to DBMS null semantics.</td>
</tr>
<tr>
<td>внешний ключ</td>
<td>foreign key</td>
<td>Constraint that enforces referential integrity between tables.</td>
</tr>
<tr>
<td>суррогатный ключ</td>
<td>surrogate key</td>
<td>Artificial identifier without business meaning.</td>
</tr>
<tr>
<td>естественный ключ</td>
<td>natural key</td>
<td>Business-meaningful unique identifier.</td>
</tr>
<tr>
<td>составной ключ</td>
<td>composite key</td>
<td>Key made from multiple columns.</td>
</tr>
<tr>
<th colspan="3" align="left">Querying And Execution</th>
</tr>
<tr>
<td>план выполнения запроса</td>
<td>query execution plan</td>
<td>Physical plan chosen by the database optimizer.</td>
</tr>
<tr>
<td>оптимизатор запросов</td>
<td>query optimizer</td>
<td>DBMS component that chooses how to execute a query.</td>
</tr>
<tr>
<td>агрегатная функция</td>
<td>aggregate function</td>
<td>Function that calculates one value from multiple rows.</td>
</tr>
<tr>
<td>операция над множествами</td>
<td>set operation</td>
<td>SQL operations such as <code>UNION</code>, <code>INTERSECT</code>, and <code>EXCEPT</code>.</td>
</tr>
<tr>
<td>физический алгоритм соединения</td>
<td>physical join algorithm</td>
<td>Execution strategy used by the database, for example nested loop, hash join, or merge join.</td>
</tr>
<tr>
<td>nested loop join</td>
<td>nested loop join</td>
<td>Join algorithm that probes the inner side for each row from the outer side.</td>
</tr>
<tr>
<td>hash join</td>
<td>hash join</td>
<td>Join algorithm that builds a hash table for one side of an equality join.</td>
</tr>
<tr>
<td>merge join</td>
<td>merge join</td>
<td>Join algorithm that combines sorted inputs.</td>
</tr>
<tr>
<td>LATERAL join</td>
<td>LATERAL join</td>
<td>Join form where the right-side subquery can reference columns from the left side.</td>
</tr>
<tr>
<td>оконная рамка</td>
<td>window frame</td>
<td>Subset of rows inside a window partition used by frame-sensitive window functions.</td>
</tr>
<tr>
<td>равные строки сортировки / peers</td>
<td>peer rows</td>
<td>Rows equal according to the window function <code>ORDER BY</code> keys.</td>
</tr>
<tr>
<td>DISTINCT ON</td>
<td>DISTINCT ON</td>
<td>PostgreSQL-specific way to keep the first row per distinct key according to <code>ORDER BY</code>.</td>
</tr>
<tr>
<td>Memoize</td>
<td>Memoize</td>
<td>PostgreSQL plan node that caches repeated parameterized lookups, often under nested loops.</td>
</tr>
<tr>
<td>generic plan</td>
<td>generic plan</td>
<td>Prepared-statement plan reused without optimizing for concrete parameter values.</td>
</tr>
<tr>
<td>custom plan</td>
<td>custom plan</td>
<td>Prepared-statement plan optimized for concrete parameter values.</td>
</tr>
<tr>
<td>режим кэширования плана</td>
<td>plan_cache_mode</td>
<td>PostgreSQL setting used to diagnose or control generic vs custom prepared-statement plans.</td>
</tr>
<tr>
<td>статистика запросов</td>
<td>pg_stat_statements</td>
<td>PostgreSQL extension view for aggregated SQL execution statistics.</td>
</tr>
<tr>
<td>множитель памяти hash operations</td>
<td>hash_mem_multiplier</td>
<td>PostgreSQL setting that lets hash operations use more memory than the base <code>work_mem</code>.</td>
</tr>
<tr>
<td>рабочая память операции</td>
<td>work_mem</td>
<td>PostgreSQL setting that limits memory for operations such as sorts and hash tables before spilling to disk.</td>
</tr>
<tr>
<td>UNION ALL</td>
<td>UNION ALL</td>
<td>Set operation that appends result sets without removing duplicate rows.</td>
</tr>
<tr>
<td>общее табличное выражение</td>
<td>CTE / Common Table Expression</td>
<td>Named temporary result inside one SQL statement, defined with <code>WITH</code>.</td>
</tr>
<tr>
<td>представление</td>
<td>view</td>
<td>Named saved query used like a virtual table.</td>
</tr>
<tr>
<td>материализованное представление</td>
<td>materialized view</td>
<td>Database object that physically stores a query result.</td>
</tr>
<tr>
<td>условие / предикат</td>
<td>predicate</td>
<td>Boolean condition used in <code>WHERE</code>, <code>JOIN</code>, <code>CHECK</code>, partial indexes, and query planning.</td>
</tr>
<tr>
<th colspan="3" align="left">Data Modeling</th>
</tr>
<tr>
<td>нормализация</td>
<td>normalization</td>
<td>Schema design approach that reduces duplication and update anomalies.</td>
</tr>
<tr>
<td>денормализация</td>
<td>denormalization</td>
<td>Intentional duplication or derived data storage for read or reporting needs.</td>
</tr>
<tr>
<td>связь один-к-одному</td>
<td>one-to-one relationship</td>
<td>Relationship where one row maps to at most one row on the other side.</td>
</tr>
<tr>
<td>связь один-ко-многим</td>
<td>one-to-many relationship</td>
<td>Relationship where one parent row can have many child rows.</td>
</tr>
<tr>
<td>связь многие-ко-многим</td>
<td>many-to-many relationship</td>
<td>Relationship modeled with a junction table in a relational database.</td>
</tr>
<tr>
<td>связующая таблица</td>
<td>junction table</td>
<td>Table that connects two sides of a many-to-many relationship.</td>
</tr>
<tr>
<td>мягкое удаление</td>
<td>soft delete</td>
<td>Marking a row as deleted instead of physically deleting it.</td>
</tr>
<tr>
<td>поля аудита</td>
<td>audit fields</td>
<td>Metadata columns such as <code>created_at</code>, <code>updated_at</code>, <code>created_by</code>, <code>updated_by</code>.</td>
</tr>
<tr>
<td>мультитенантность</td>
<td>multi-tenancy</td>
<td>Design where one system stores data for multiple tenants/customers.</td>
</tr>
<tr>
<th colspan="3" align="left">Transactions And Concurrency</th>
</tr>
<tr>
<td>перекос записи / write skew</td>
<td>write skew</td>
<td>Snapshot-isolation anomaly where concurrent transactions update different rows after reading the same invariant.</td>
</tr>
<tr>
<td>оптимистичная блокировка</td>
<td>optimistic locking</td>
<td>Concurrency control where updates verify a version or condition instead of taking a long lock first.</td>
</tr>
<tr>
<td>блокировка строки для изменения</td>
<td>SELECT FOR UPDATE</td>
<td>SQL clause that locks selected rows for update until transaction end.</td>
</tr>
<tr>
<td>Serializable Snapshot Isolation</td>
<td>Serializable Snapshot Isolation</td>
<td>PostgreSQL Serializable implementation that detects unsafe dependency patterns and may abort a transaction.</td>
</tr>
<tr>
<th colspan="3" align="left">Indexes And Storage</th>
</tr>
<tr>
<td>индекс</td>
<td>index</td>
<td>Auxiliary data structure used to speed up selected reads, ordering, joins, and uniqueness checks.</td>
</tr>
<tr>
<td>B-tree индекс</td>
<td>B-tree index</td>
<td>Default PostgreSQL index type for equality, ranges, ordering, and uniqueness.</td>
</tr>
<tr>
<td>последовательное сканирование</td>
<td>sequential scan</td>
<td>Reading table pages directly and checking rows without using an index.</td>
</tr>
<tr>
<td>сканирование по индексу</td>
<td>index scan</td>
<td>Reading matching index entries and then visiting heap rows when needed.</td>
</tr>
<tr>
<td>сканирование только по индексу</td>
<td>index-only scan</td>
<td>Scan that can return required columns from the index when visibility information allows it.</td>
</tr>
<tr>
<td>heap / куча таблицы</td>
<td>heap</td>
<td>PostgreSQL table storage where row versions are stored.</td>
</tr>
<tr>
<td>tuple / версия строки</td>
<td>tuple</td>
<td>Physical row version in PostgreSQL MVCC terminology.</td>
</tr>
<tr>
<td>страница</td>
<td>page</td>
<td>Fixed-size storage block used by tables and indexes.</td>
</tr>
<tr>
<td>корневая страница</td>
<td>root page</td>
<td>B-tree entry page used to start index navigation.</td>
</tr>
<tr>
<td>внутренняя страница</td>
<td>internal page</td>
<td>B-tree page that routes search to child pages.</td>
</tr>
<tr>
<td>листовая страница</td>
<td>leaf page</td>
<td>B-tree page that stores actual sorted index entries.</td>
</tr>
<tr>
<td>split страницы</td>
<td>page split</td>
<td>B-tree page split that happens when a page lacks room for a new entry.</td>
</tr>
<tr>
<td>составной индекс</td>
<td>composite index</td>
<td>Index over multiple columns where column order affects filtering and ordering.</td>
</tr>
<tr>
<td>правило левого префикса</td>
<td>leftmost prefix rule</td>
<td>Rule of thumb: composite B-tree indexes are most efficient when leading columns are constrained.</td>
</tr>
<tr>
<td>кардинальность</td>
<td>cardinality</td>
<td>Number of distinct values in a column or index key.</td>
</tr>
<tr>
<td>селективность</td>
<td>selectivity</td>
<td>Fraction of rows matched by a predicate. A smaller fraction means a more selective predicate.</td>
</tr>
<tr>
<td>перекос данных</td>
<td>data skew</td>
<td>Uneven value distribution that can make plans differ by parameter value.</td>
</tr>
<tr>
<td>частичный индекс</td>
<td>partial index</td>
<td>Index built only for rows that satisfy a <code>WHERE</code> predicate.</td>
</tr>
<tr>
<td>индекс по выражению</td>
<td>expression index</td>
<td>Index on a computed expression, for example <code>lower(email)</code>.</td>
</tr>
<tr>
<td>покрывающий индекс</td>
<td>covering index</td>
<td>Index that contains all columns needed by a query, enabling possible index-only scans.</td>
</tr>
<tr>
<td>включённые колонки</td>
<td>INCLUDE columns</td>
<td>PostgreSQL non-key payload columns stored in an index.</td>
</tr>
<tr>
<td>карта видимости</td>
<td>visibility map</td>
<td>PostgreSQL structure tracking all-visible/all-frozen heap pages; important for index-only scans.</td>
</tr>
<tr>
<td>класс операторов</td>
<td>operator class</td>
<td>Defines which operators an index supports for a data type.</td>
</tr>
<tr>
<td>раздувание индекса</td>
<td>index bloat</td>
<td>Wasted index space caused by updates, deletes, page splits, and maintenance lag.</td>
</tr>
<tr>
<td>HOT update</td>
<td>HOT update</td>
<td>PostgreSQL update that can avoid new index entries when indexed columns do not change.</td>
</tr>
<tr>
<td>журнал предзаписи</td>
<td>WAL / Write-Ahead Log</td>
<td>PostgreSQL durability and replication log; index maintenance increases WAL volume.</td>
</tr>
<tr>
<td>перестроение индекса</td>
<td>REINDEX</td>
<td>Operation that rebuilds an existing index.</td>
</tr>
<tr>
<td>concurrent index build</td>
<td>concurrent index build</td>
<td>Index build mode that avoids blocking normal writes but is slower and operationally more complex.</td>
</tr>
<tr>
<td>список ожидания GIN</td>
<td>GIN pending list</td>
<td>GIN structure used to buffer index entries when fast update behavior is enabled.</td>
</tr>
<tr>
<td>summarization BRIN</td>
<td>BRIN summarization</td>
<td>Maintenance of block-range summaries used by BRIN indexes.</td>
</tr>
<tr>
<td>индекс partitioned table</td>
<td>partitioned index</td>
<td>Parent-level index definition represented by physical indexes on table partitions.</td>
</tr>
<tr>
<th colspan="3" align="left">Pagination And API Query Patterns</th>
</tr>
<tr>
<td>пагинация со смещением</td>
<td>OFFSET/LIMIT pagination</td>
<td>Pagination that skips N rows and returns the next limited set.</td>
</tr>
<tr>
<td>keyset-пагинация</td>
<td>keyset pagination</td>
<td>Pagination based on the last seen sort key instead of row offset.</td>
</tr>
<tr>
<td>курсорная пагинация</td>
<td>cursor pagination</td>
<td>API pagination where the next page is requested using an opaque cursor token.</td>
</tr>
<tr>
<td>стабильный порядок сортировки</td>
<td>stable ordering</td>
<td>Deterministic ordering that prevents duplicates/skips between pages.</td>
</tr>
<tr>
<td>дополнительный ключ сортировки</td>
<td>tie-breaker</td>
<td>Extra unique sort key, often <code>id</code>, added to make ordering deterministic.</td>
</tr>
<tr>
<td>непрозрачный курсор</td>
<td>opaque cursor</td>
<td>Cursor token whose internal fields are not part of the public API contract.</td>
</tr>
<tr>
<td>опциональные фильтры</td>
<td>optional filters</td>
<td>Request filters that may or may not be present, creating multiple query shapes.</td>
</tr>
<tr>
<td>форма запроса</td>
<td>query shape</td>
<td>Structural form of a query: predicates, joins, ordering, limits, and selected paths.</td>
</tr>
<tr>
<th colspan="3" align="left">Migrations And Production Safety</th>
</tr>
<tr>
<td>миграция базы данных</td>
<td>database migration</td>
<td>Versioned schema or data change applied in a controlled and repeatable way.</td>
</tr>
<tr>
<td>миграция без простоя</td>
<td>zero-downtime migration</td>
<td>Migration that keeps old and new application versions working while traffic continues.</td>
</tr>
<tr>
<td>expand-and-contract</td>
<td>expand-and-contract migration</td>
<td>Multi-step migration: add compatible schema, migrate usage/data, then remove old schema.</td>
</tr>
<tr>
<td>дозаполнение</td>
<td>backfill</td>
<td>Populating new or corrected values for existing rows.</td>
</tr>
<tr>
<td>план отката</td>
<td>rollback plan</td>
<td>Operational plan for safely reverting or mitigating a failed migration/deploy.</td>
</tr>
<tr>
<td>расхождение схем</td>
<td>schema drift</td>
<td>Difference between expected version-controlled schema and actual database schema.</td>
</tr>
<tr>
<td>онлайн-создание индекса</td>
<td>CREATE INDEX CONCURRENTLY</td>
<td>PostgreSQL index build mode that avoids blocking normal writes but has operational restrictions.</td>
</tr>
<tr>
<td>таймаут блокировки</td>
<td>lock_timeout</td>
<td>PostgreSQL setting limiting how long a statement waits to acquire a lock.</td>
</tr>
<tr>
<td>таймаут запроса</td>
<td>statement_timeout</td>
<td>PostgreSQL setting limiting how long a statement may run.</td>
</tr>
<tr>
<th colspan="3" align="left">Troubleshooting And Operations</th>
</tr>
<tr>
<td>медленный запрос</td>
<td>slow query</td>
<td>Query whose latency is too high for the workload or SLO.</td>
</tr>
<tr>
<td>узкое место</td>
<td>bottleneck</td>
<td>Resource, plan node, lock, or dependency that limits end-to-end performance.</td>
</tr>
<tr>
<td>ожидание блокировки</td>
<td>lock wait</td>
<td>Time spent waiting for another transaction/session to release a conflicting lock.</td>
</tr>
<tr>
<td>исчерпание пула соединений</td>
<td>connection pool exhaustion</td>
<td>Condition where all pool connections are busy and new requests wait or fail.</td>
</tr>
<tr>
<td>ожидание события</td>
<td>wait event</td>
<td>PostgreSQL diagnostic field showing what a backend process is waiting for.</td>
</tr>
<tr>
<td>нормализованный SQL</td>
<td>normalized SQL</td>
<td>Query text with literal values normalized, useful for grouping similar statements.</td>
</tr>
<tr>
<td>отпечаток запроса</td>
<td>query fingerprint</td>
<td>Normalized identity of a query shape used by monitoring and tracing tools.</td>
</tr>
<tr>
<th colspan="3" align="left">Security</th>
</tr>
<tr>
<td>SQL-инъекция</td>
<td>SQL injection</td>
<td>Vulnerability where user-controlled input changes SQL code instead of being treated as data.</td>
</tr>
<tr>
<td>подготовленный запрос</td>
<td>prepared statement</td>
<td>SQL statement with placeholders where parameter values are bound separately.</td>
</tr>
<tr>
<td>bind-параметр</td>
<td>bind parameter</td>
<td>Parameter value sent separately from SQL text to avoid mixing code and data.</td>
</tr>
<tr>
<td>allowlist</td>
<td>allowlist</td>
<td>Explicit list of allowed values, used for dynamic identifiers and sort options.</td>
</tr>
<tr>
<td>минимально необходимые права</td>
<td>least privilege</td>
<td>Security principle of granting only the permissions needed for the workload.</td>
</tr>
<tr>
<td>защита на уровне строк</td>
<td>Row-Level Security / RLS</td>
<td>PostgreSQL feature that restricts visible/modifiable rows using table policies.</td>
</tr>
<tr>
<td>политика RLS</td>
<td>RLS policy</td>
<td>Rule that defines which rows are visible or allowed for a table operation.</td>
</tr>
<tr>
<td>маскирование / редактирование чувствительных данных</td>
<td>redaction</td>
<td>Removing or masking sensitive values before logs/traces leave the service boundary.</td>
</tr>
<tr>
<td>чувствительные данные</td>
<td>sensitive data</td>
<td>Passwords, tokens, PII, financial data, secrets, tenant data, and regulated fields.</td>
</tr>
<tr>
<td>ротация секретов</td>
<td>secret rotation</td>
<td>Regular replacement of credentials/tokens to reduce compromise impact.</td>
</tr>
</tbody>
</table>
