# Slow query and production troubleshooting

<a id="db-prod-001"></a>

<details>
<summary><strong>DB-PROD-001. How would you investigate a slow PostgreSQL query in production?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Start with the exact query and context, then inspect EXPLAIN ANALYZE, buffers, row estimates, locks, resource metrics, and application behavior.</p>
</td>
<td valign="top" width="50%">
<p>Начать с точного запроса и контекста, затем проверить EXPLAIN ANALYZE, buffers, оценки числа строк, locks, ресурсные метрики и поведение приложения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>First identify whether it is one slow query, many slow queries, or general database saturation. Capture the normalized SQL, parameters, frequency, latency percentiles, and affected endpoint.</p>
<p>Then run <code>EXPLAIN (ANALYZE, BUFFERS)</code> safely on representative data if possible.</p>
</td>
<td valign="top" width="50%">
<p>Сначала определить: это one медленный запрос, many медленные запросы или общая перегрузка БД. Собери нормализованный SQL, параметры, частоту, перцентили задержки и затронутый endpoint.</p>
<p>Then run <code>EXPLAIN (ANALYZE, BUFFERS)</code> safely on representative данных if possible.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Look for scan type, join algorithm, estimated vs actual rows, sort/hash spills, buffer reads, loops, rows removed by filter, and index usage.</p>
<p>Also check locks, connection pool wait, CPU, IO, replication lag, autovacuum, and recent schema/data/statistics changes.</p>
</td>
<td valign="top" width="50%">
<p>Смотри тип сканирования, алгоритм соединения, estimated vs фактическое число строк, сбросы сортировки или хеша на диск, чтения буферов, loops, строки, отброшенные фильтром и использование индекса.</p>
<p>Также проверь блокировки, пул соединений (connection pool) wait, CPU, IO, задержка репликации (replication lag), autovacuum и недавние изменения схемы, данных или статистики.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, avoid guessing. Use metrics and traces. If the immediate impact is high, mitigate first: timeout, reduce traffic, disable feature, add index concurrently, or route heavy workload away.</p>
<p>Then fix root cause.</p>
</td>
<td valign="top" width="50%">
<p>В production не угадывай. Используй метрики и трассировки. Если влияние большое, сначала снижай ущерб: timeout, снизь трафик, отключи фичу, создай индекс concurrently или уведи тяжёлую нагрузку в сторону.</p>
<p>Then fix корневая причина.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Slow query may be blocked, not CPU-heavy.</li>
<li>Dev data often hides bad plans.</li>
<li>EXPLAIN without ANALYZE can be misleading.</li>
<li>Adding an index blindly can hurt writes and not fix the root cause.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Медленный запрос может быть заблокированным, а не CPU-bound.</li>
<li>Данные в dev often hides bad plans.</li>
<li>EXPLAIN without ANALYZE can be misleading.</li>
<li>Слепое добавление индекса может навредить записям и не исправить корневая причина.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>

</td>
<td valign="top" width="50%">

<summary><strong>DB-PROD-004. How do you find blocked queries?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">
<p>Ищи sessions ожидающие блокировки в pg_stat_activity и join with pg_locks или use pg_blocking_pids(pid).</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Blocked queries often have wait_event_type = 'Lock'. PostgreSQL provides <code>pg_blocking_pids(pid)</code> to identify blockers.</p>
<p>You want both the blocked query and the blocking session.</p>
</td>
<td valign="top" width="50%">
<p>Blocked queries often have wait_event_type = 'Lock'. PostgreSQL provides <code>pg_blocking_pids(pid)</code> to identify blockers.</p>
<p>Нужно найти и заблокированный запрос, и блокирующую сессию.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Lock wait diagnosis includes transaction start time, query start time, state, relation, lock mode, and whether the blocker is idle in transaction.</p>
<p>A short query can be blocked by an old forgotten transaction.</p>
<pre><code>SELECT a.pid AS blocked_pid,
       pg_blocking_pids(a.pid) AS blocker_pids,
       now() - a.query_start AS blocked_for,
       a.wait_event_type,
       a.wait_event,
       a.query
FROM pg_stat_activity a
WHERE cardinality(pg_blocking_pids(a.pid)) &gt; 0;</code></pre>
</td>
<td valign="top" width="50%">
<p>При диагностике ожидание блокировок смотрят transaction start time, query start time, state, relation, lock mode и не является ли blocker idle in transaction.</p>
<p>Короткий query может ждать старую забытую transaction.</p>
<pre><code>SELECT a.pid AS blocked_pid,
       pg_blocking_pids(a.pid) AS blocker_pids,
       now() - a.query_start AS blocked_for,
       a.wait_event_type,
       a.wait_event,
       a.query
FROM pg_stat_activity a
WHERE cardinality(pg_blocking_pids(a.pid)) &gt; 0;</code></pre>
</td>
</tr>

<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, killing blockers is risky. First understand what work will be rolled back and whether the blocker is part of critical flow.</p>
<p>Set lock_timeout for migrations to avoid blocking traffic.</p>
</td>
<td valign="top" width="50%">
<p>В production killing blockers risky. First understand what work will be rolled back and whether blocker part of critical flow.</p>

<li>Lock queues can create cascading incidents.</li>

<summary><strong>DB-PROD-006. How do you detect missing indexes?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Look for slow queries doing large scans or expensive joins where selective predicates or join keys are not indexed.</p>
</td>
<td valign="top" width="50%">
<p>Ищи медленные запросы doing large scans или expensive joins, где selective predicates или join keys not indexed.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use <code>EXPLAIN (ANALYZE, BUFFERS)</code>, slow query logs, pg_stat_statements, and workload analysis.</p>
<p>A missing index is suggested when many rows are scanned/filtered to return few rows, or joins repeatedly scan a large table.</p>
<p>With <code>pg_stat_statements</code>, start from the workload cost, then inspect the plans of the top statements.</p>
<pre><code>SELECT query, calls, total_exec_time, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;</code></pre>
</td>
<td valign="top" width="50%">
<p>Используют <code>EXPLAIN (ANALYZE, BUFFERS)</code>, медленный запрос logs, <code>pg_stat_statements</code> и анализ реального workload.</p>
<p>Missing index подозревают, когда query сканирует или фильтрует много rows ради малого результата, либо join многократно сканирует большую table.</p>
<p>С <code>pg_stat_statements</code> начинают с самых дорогих statements по workload, а затем разбирают их plans.</p>
<pre><code>SELECT query, calls, total_exec_time, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Index design depends on predicates, selectivity, ordering, joins and write cost. A composite index may be better than separate indexes.</p>
<p>Always check existing indexes for redundancy.</p>
</td>
<td valign="top" width="50%">
<p>Index design depends on predicates, selectivity, ordering, joins and write cost. Composite index may be better than separate indexes.</p>
<p>Always check existing indexes for redundancy.</p>
</td>

<tr>
<th colspan="2" align="left">Production angle</th>
