<details>
<summary><strong>🧠 DB-JOINALG-002. What is a Nested Loop Join?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Nested Loop Join iterates rows from the outer input and searches matching rows in the inner input for each outer row.</p>
</td>
<td valign="top" width="50%">
<p>Nested Loop Join перебирает строки внешнего входного набора и для каждой из них ищет подходящие строки во внутреннем входном наборе.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Conceptually it is like a loop inside a loop, but the inner side can be an efficient index lookup. Modern PostgreSQL may add <code>Memoize</code> to cache repeated inner lookups.</p>
</td>
<td valign="top" width="50%">
<p>Концептуально это цикл внутри цикла, но доступ к внутренней стороне может быть дешёвым поиском по индексу. Современный PostgreSQL может добавить <code>Memoize</code>, чтобы кэшировать повторные обращения к внутреннему набору.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>It is excellent when the outer side is small and the inner access path is cheap; it is terrible when the outer side is huge and inner lookup repeats many times. In plans, the total cost is often hidden in <code>loops</code>, not in one execution of the inner node.</p>
</td>
<td valign="top" width="50%">
<p>Он отлично работает, когда внешняя сторона маленькая, а путь доступа к внутреннему набору дешёвый. И наоборот, он становится опасным, когда внешняя сторона огромная и поиск во внутреннем наборе повторяется много раз. В планах общая стоимость часто скрыта в <code>loops</code>, а не в одном выполнении внутреннего узла.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In <code>EXPLAIN ANALYZE</code>, pay attention to <code>loops</code>, actual rows on the outer side, and <code>Memoize</code> hit/miss counters when present. A node that is fast once can be expensive when executed hundreds of thousands of times.</p>
</td>
<td valign="top" width="50%">
<p>В <code>EXPLAIN ANALYZE</code> смотри <code>loops</code>, фактическое число строк на внешней стороне и счётчики попаданий/промахов <code>Memoize</code>, если они есть. Узел, быстрый при одном выполнении, может стать дорогим при сотнях тысяч повторов.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Nested Loop is not always bad.</li><li>Large unexpected outer rows make it dangerous.</li><li>Inner side usually needs a good index.</li><li><code>Memoize</code> can help repeated lookups, but it does not fix a fundamentally huge outer input.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>Nested Loop не всегда плох.</li><li>Неожиданно большое число строк на внешней стороне делает его опасным.</li><li>Для внутренней стороны обычно нужен хороший индекс.</li><li><code>Memoize</code> помогает при повторных обращениях, но не исправляет слишком большой внешний входной набор.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is a Nested Loop Join?<br>A: Nested Loop Join iterates rows from the outer input and searches matching rows in the inner input for each outer row.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое Nested Loop Join?<br>A: Он перебирает строки внешнего входного набора и для каждой ищет подходящие строки во внутреннем наборе.</p>
</td>
</tr>

<details>
<summary><strong>🧠 DB-JOINALG-005. What is a Hash Join?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Hash Join builds a hash table from one input and probes it with rows from the other input.</p>
</td>
<td valign="top" width="50%">
<p>Hash Join строит хеш-таблицу по одному входному набору и проверяет её строками другого входного набора.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>It is usually used for equality joins over medium/large inputs when nested loops would be too expensive and useful ordering is not available.</p>
</td>
<td valign="top" width="50%">
<p>Обычно используется для соединений по равенству на средних и больших входных наборах, когда Nested Loop слишком дорогой и полезного порядка сортировки нет.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>PostgreSQL usually builds the hash table on the smaller side. If the hash table does not fit memory, it may use batches and temporary files. In a plan, look for <code>Hash Cond</code>, <code>Buckets</code>, <code>Batches</code>, and memory usage.</p><pre><code class="language-text">Hash Join
  Hash Cond: (line_items.order_id = orders.id)
  -&gt; Seq Scan on line_items
  -&gt; Hash
       Buckets: 262144  Batches: 1  Memory Usage: 12000kB</code></pre>
</td>
<td valign="top" width="50%">
<p>PostgreSQL обычно строит хеш-таблицу по меньшей стороне. Если хеш-таблица не помещается в память, используются пакеты (batches) и временные файлы. В плане смотри <code>Hash Cond</code>, <code>Buckets</code>, <code>Batches</code> и использование памяти.</p><pre><code class="language-text">Hash Join
  Hash Cond: (line_items.order_id = orders.id)
  -&gt; Seq Scan on line_items
  -&gt; Hash
       Buckets: 262144  Batches: 1  Memory Usage: 12000kB</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>When debugging, check hash memory usage, buckets, batches, temp reads/writes, <code>work_mem</code>, <code>hash_mem_multiplier</code>, and whether inputs can be filtered earlier.</p>
</td>
<td valign="top" width="50%">
<p>При отладке смотри использование памяти хешем, <code>Buckets</code>, <code>Batches</code>, чтения и записи временных файлов, <code>work_mem</code>, <code>hash_mem_multiplier</code> и можно ли раньше фильтровать входные наборы.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Mostly for equality joins.</li><li>Can spill to disk.</li><li>Indexes are not required for Hash Join, but can reduce inputs.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>В основном для соединения по равенству.</li><li>Может сбрасываться на диск.</li><li>Индексы не обязательны для Hash Join, но могут уменьшить входные наборы.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">
<p>Q: Что такое Hash Join?<br>A: Он строит хеш-таблицу по одному входному набору и проверяет её строками другого входного набора.</p>
</td>

</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">

<td valign="top" width="50%">
