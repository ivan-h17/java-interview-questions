# SQL basics and relational model

<a id="db-sql-001"></a>

<details>
<summary><strong>DB-SQL-001. What is SQL?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>SQL is a declarative language for working with relational databases. We use it to define schemas, query data, change data, manage permissions, and control transactions.</p>
</td>
<td valign="top" width="50%">
<p>SQL — это декларативный язык для работы с реляционными базами данных. С его помощью описывают схемы, читают и изменяют данные, управляют правами и транзакциями.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>SQL stands for Structured Query Language. In backend development, I mostly use it to query and modify data in relational databases like PostgreSQL.</p>
<p>The important point is that SQL is declarative: I describe what result I want, not exactly how to iterate over rows. The database optimizer decides the execution plan: which indexes to use, which join algorithm to choose, and whether a sequential scan is cheaper.</p>
<p>SQL is also broader than <code>SELECT</code>. It includes schema changes like <code>CREATE TABLE</code>, data changes like <code>INSERT</code> and <code>UPDATE</code>, access control like <code>GRANT</code>, and transaction control like <code>COMMIT</code> and <code>ROLLBACK</code>.</p>
</td>
<td valign="top" width="50%">
<p>SQL расшифровывается как Structured Query Language. В backend-разработке его чаще всего используют для чтения и изменения данных в реляционных БД, например PostgreSQL.</p>
<p>Главная идея в том, что SQL — декларативный язык: мы описываем, какой результат хотим получить, а не пишем пошаговый обход строк. Как именно выполнить запрос, решает оптимизатор базы данных: использовать ли индекс, какой join выбрать, делать ли sequential scan.</p>
<p>SQL — это не только <code>SELECT</code>. В него входят команды для изменения схемы, например <code>CREATE TABLE</code>, изменения данных, например <code>INSERT</code> и <code>UPDATE</code>, управления правами через <code>GRANT</code>, а также управления транзакциями через <code>COMMIT</code> и <code>ROLLBACK</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>SQL works with tables, rows, columns, constraints, relations, and result sets. A query is usually written as a logical expression over sets of rows, while the database engine converts it into a physical execution plan.</p>
<p>For example:</p>
<pre><code class="language-sql">SELECT id, email
FROM users
WHERE status = 'ACTIVE'
ORDER BY created_at DESC
LIMIT 50;</code></pre>
<p>This query describes the required result. PostgreSQL may execute it using an index scan, a sequential scan plus sort, or another plan depending on indexes, table size, statistics, and selectivity.</p>
<p>Different databases support the SQL standard with dialect-specific extensions. PostgreSQL SQL is not identical to MySQL, Oracle, or SQL Server SQL.</p>
</td>
<td valign="top" width="50%">
<p>SQL работает с таблицами, строками, колонками, ограничениями, связями и результирующими наборами. Запрос обычно описывает логическое условие над множеством строк, а движок базы превращает его в физический план выполнения.</p>
<p>Например:</p>
<pre><code class="language-sql">SELECT id, email
FROM users
WHERE status = 'ACTIVE'
ORDER BY created_at DESC
LIMIT 50;</code></pre>
<p>Этот запрос описывает нужный результат. PostgreSQL может выполнить его через index scan, sequential scan с сортировкой или другим способом — в зависимости от индексов, размера таблицы, статистики и селективности условия.</p>
<p>Разные базы поддерживают SQL-стандарт со своими расширениями. SQL в PostgreSQL не полностью совпадает с SQL в MySQL, Oracle или SQL Server.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For a Java backend developer, SQL matters even when using JPA or another ORM. Production issues often require reading generated SQL, checking execution plans with <code>EXPLAIN</code>, understanding indexes, avoiding N+1 queries, and making safe schema changes.</p>
<p>Good SQL usage also includes parameterized queries to avoid SQL injection, clear transaction boundaries, migrations through tools like Flyway or Liquibase, and awareness of database-specific behavior.</p>
</td>
<td valign="top" width="50%">
<p>Для Java backend-разработчика SQL важен даже при использовании JPA или другого ORM. В production часто приходится читать сгенерированный SQL, смотреть планы через <code>EXPLAIN</code>, понимать индексы, находить N+1 queries и безопасно менять схему.</p>
<p>Хорошая работа с SQL также включает параметризованные запросы против SQL-инъекция (SQL injection), понятные границы транзакций, миграции через Flyway или Liquibase и знание особенностей конкретной базы данных.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>SQL is declarative, but performance depends heavily on physical details: indexes, statistics, row counts, data distribution, and locks.</li>
<li>SQL is not the same in every database. Dialects and transaction behavior differ.</li>
<li>ORM knowledge does not replace SQL knowledge for serious backend work.</li>
<li><code>NULL</code> has special three-valued logic and often surprises developers.</li>
<li>A query can be logically correct and still be dangerous in production if it scans too much data or locks too many rows.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>SQL декларативный, но производительность сильно зависит от физических деталей: индексов, статистики, количества строк, распределения данных и блокировок.</li>
<li>SQL не одинаковый во всех базах. Диалекты и поведение транзакций отличаются.</li>
<li>Знание ORM не заменяет знание SQL для серьезной backend-разработки.</li>
<li><code>NULL</code> работает через трехзначную логику и часто приводит к неожиданным результатам.</li>
<li>Запрос может быть логически правильным, но опасным в production, если читает слишком много данных или блокирует слишком много строк.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is SQL?<br>A: SQL is a declarative language for defining, querying, modifying, securing, and transactionally managing data in relational databases.</p>
<p>Q: Why is SQL called declarative?<br>A: Because the query describes the desired result, while the database optimizer decides how to execute it.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое SQL?<br>A: SQL — декларативный язык для описания, чтения, изменения, защиты данных и управления транзакциями в реляционных БД.</p>
<p>Q: Почему SQL называют декларативным языком?<br>A: Потому что запрос описывает нужный результат, а база данных сама выбирает способ выполнения.</p>
</td>
</tr>

<details>
<summary><strong>DB-SQL-002. What are DDL, DML, DCL and TCL?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>DDL changes database structure, DML works with data, DCL manages permissions, and TCL controls transactions.</p>
</td>
<td valign="top" width="50%">
<p>DDL изменяет структуру базы, DML работает с данными, DCL управляет правами, а TCL управляет транзакциями.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>These are common categories of SQL commands.</p>
<p>DDL means Data Definition Language. It is used for schema objects: <code>CREATE TABLE</code>, <code>ALTER TABLE</code>, <code>DROP TABLE</code>, <code>CREATE INDEX</code>.</p>
<p>DML means Data Manipulation Language. It is used to work with rows: <code>SELECT</code>, <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code>, and <code>MERGE</code>. Some classifications separate <code>SELECT</code> into DQL, but in interviews it is often discussed together with DML.</p>
<p>DCL means Data Control Language. It manages access: <code>GRANT</code> and <code>REVOKE</code>.</p>
<p>TCL means Transaction Control Language. It manages transaction boundaries and savepoints: <code>BEGIN</code>, <code>COMMIT</code>, <code>ROLLBACK</code>, <code>SAVEPOINT</code>.</p>
</td>
<td valign="top" width="50%">
<p>Это распространенная классификация SQL-команд.</p>
<p>DDL означает Data Definition Language. Эти команды работают со структурой базы: <code>CREATE TABLE</code>, <code>ALTER TABLE</code>, <code>DROP TABLE</code>, <code>CREATE INDEX</code>.</p>
<p>DML означает Data Manipulation Language. Эти команды работают со строками данных: <code>SELECT</code>, <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code>, <code>MERGE</code>. Иногда <code>SELECT</code> выделяют отдельно в DQL, но на интервью его часто обсуждают вместе с DML.</p>
<p>DCL означает Data Control Language. Это управление доступом: <code>GRANT</code> и <code>REVOKE</code>.</p>
<p>TCL означает Transaction Control Language. Это управление границами транзакций и savepoint-ами: <code>BEGIN</code>, <code>COMMIT</code>, <code>ROLLBACK</code>, <code>SAVEPOINT</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example DDL:</p>
<pre><code class="language-sql">CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    email TEXT NOT NULL UNIQUE
);</code></pre>
<p>Example DML:</p>
<pre><code class="language-sql">INSERT INTO users (email) VALUES ('alice@example.com');

UPDATE users
SET email = 'alice.new@example.com'
WHERE id = 1;</code></pre>
<p>Example DCL:</p>
<pre><code class="language-sql">GRANT SELECT ON users TO reporting_user;
REVOKE SELECT ON users FROM reporting_user;</code></pre>
<p>Example TCL:</p>
<pre><code class="language-sql">BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;</code></pre>
<p>The categories are useful for communication, but exact behavior depends on the DBMS. For example, PostgreSQL supports transactional DDL for many operations, while some databases auto-commit DDL statements.</p>
</td>
<td valign="top" width="50%">
<p>Пример DDL:</p>
<pre><code class="language-sql">CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    email TEXT NOT NULL UNIQUE
);</code></pre>
<p>Пример DML:</p>
<pre><code class="language-sql">INSERT INTO users (email) VALUES ('alice@example.com');

UPDATE users
SET email = 'alice.new@example.com'
WHERE id = 1;</code></pre>
<p>Пример DCL:</p>
<pre><code class="language-sql">GRANT SELECT ON users TO reporting_user;
REVOKE SELECT ON users FROM reporting_user;</code></pre>
<p>Пример TCL:</p>
<pre><code class="language-sql">BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;</code></pre>
<p>Классификация полезна для общения, но точное поведение зависит от конкретной СУБД. Например, PostgreSQL поддерживает транзакционный DDL для многих операций, а некоторые базы автоматически коммитят DDL-команды.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, DDL is usually handled through migrations and requires extra care because schema changes can lock tables, rewrite data, or break application compatibility.</p>
<p>DML is the everyday workload of the application, so it must be written with indexes, transaction boundaries, batching, and locking behavior in mind.</p>
<p>DCL should follow least privilege: application users should not usually have owner-level permissions.</p>
<p>TCL matters for correctness. A money transfer, order creation, or outbox write usually must be atomic, and rollback behavior must be understood together with the Java transaction manager.</p>
</td>
<td valign="top" width="50%">
<p>В production DDL обычно выполняют через миграции, потому что изменения схемы могут блокировать таблицы, переписывать данные или ломать совместимость с приложением.</p>
<p>DML — это обычная нагрузка приложения, поэтому запросы нужно писать с учетом индексов, границ транзакций, batch-операций и блокировок.</p>
<p>DCL должен следовать принципу минимальных прав: пользователь приложения обычно не должен иметь owner-level permissions.</p>
<p>TCL важен для корректности. Перевод денег, создание заказа или запись в outbox обычно должны быть атомарными, а поведение rollback нужно понимать вместе с Java transaction manager.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>The categories are not always perfectly consistent across books and databases. <code>SELECT</code> may be called DML or DQL.</li>
<li>DDL behavior differs between DBMSs. PostgreSQL supports transactional DDL for many commands, but not every database does.</li>
<li><code>TRUNCATE</code> is often grouped with DDL, but its transactional and locking behavior is database-specific.</li>
<li>DCL changes are security-sensitive and should be reviewed like application permission changes.</li>
<li>TCL commands may be hidden by frameworks like Spring <code>@Transactional</code>, but the database transaction still exists.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Классификация не всегда одинаковая в книгах и разных базах. <code>SELECT</code> могут относить к DML или выделять в DQL.</li>
<li>Поведение DDL зависит от СУБД. PostgreSQL поддерживает транзакционный DDL для многих команд, но так делают не все базы.</li>
<li><code>TRUNCATE</code> часто относят к DDL, но его транзакционность и блокировки зависят от конкретной базы.</li>
<li>DCL связан с безопасностью, поэтому изменения прав нужно ревьюить так же внимательно, как изменения permissions в приложении.</li>
<li>TCL-команды могут быть скрыты фреймворком, например Spring <code>@Transactional</code>, но транзакция в базе все равно существует.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is DDL?<br>A: Data Definition Language: SQL commands that define or change database structure, such as <code>CREATE</code>, <code>ALTER</code>, and <code>DROP</code>.</p>
<p>Q: What is DML?<br>A: Data Manipulation Language: SQL commands that read or modify data rows, such as <code>SELECT</code>, <code>INSERT</code>, <code>UPDATE</code>, and <code>DELETE</code>.</p>
<p>Q: What is DCL?<br>A: Data Control Language: SQL commands that manage permissions, mainly <code>GRANT</code> and <code>REVOKE</code>.</p>
<p>Q: What is TCL?<br>A: Transaction Control Language: SQL commands that control transactions, such as <code>BEGIN</code>, <code>COMMIT</code>, <code>ROLLBACK</code>, and <code>SAVEPOINT</code>.</p>

</td>
<td valign="top" width="50%">
<p>Q: Что такое DDL?<br>A: Data Definition Language: SQL-команды для описания или изменения структуры базы, например <code>CREATE</code>, <code>ALTER</code>, <code>DROP</code>.</p>
<p>Q: Что такое DML?<br>A: Data Manipulation Language: SQL-команды для чтения и изменения строк данных, например <code>SELECT</code>, <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code>.</p>
<p>Q: Что такое DCL?<br>A: Data Control Language: SQL-команды для управления правами, в основном <code>GRANT</code> и <code>REVOKE</code>.</p>
<p>Q: Что такое TCL?<br>A: Transaction Control Language: SQL-команды для управления транзакциями, например <code>BEGIN</code>, <code>COMMIT</code>, <code>ROLLBACK</code>, <code>SAVEPOINT</code>.</p>

</td>
</tr>

<details>
<summary><strong>DB-SQL-003. What is NULL in SQL?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>NULL</code> means that a value is absent, unknown, or not applicable. It is not the same as zero, an empty string, or <code>false</code>.</p>
</td>
<td valign="top" width="50%">
<p><code>NULL</code> означает, что значение отсутствует, неизвестно или неприменимо. Это не то же самое, что ноль, пустая строка или <code>false</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In SQL, <code>NULL</code> is a special marker for missing information. For example, a user may not have a middle name, or an order may not yet have a delivery date.</p>
<p>The important part is that comparisons with <code>NULL</code> do not behave like normal comparisons. <code>column = NULL</code> does not return true; it returns <code>UNKNOWN</code>. To check for nulls, we use <code>IS NULL</code> and <code>IS NOT NULL</code>.</p>
<p>Aggregates also have special behavior: most aggregate functions ignore <code>NULL</code>, while <code>COUNT(*)</code> counts rows regardless of null values.</p>
</td>
<td valign="top" width="50%">
<p>В SQL <code>NULL</code> — это специальный маркер отсутствующего значения. Например, у пользователя может не быть отчества, а у заказа может еще не быть даты доставки.</p>
<p>Важно, что сравнения с <code>NULL</code> работают не как обычные сравнения. <code>column = NULL</code> не возвращает true, а дает <code>UNKNOWN</code>. Для проверки используют <code>IS NULL</code> и <code>IS NOT NULL</code>.</p>
<p>У агрегатных функций тоже есть особенности: большинство агрегатов игнорируют <code>NULL</code>, а <code>COUNT(*)</code> считает строки независимо от null-значений.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example:</p>
<pre><code class="language-sql">SELECT *
FROM users
WHERE deleted_at IS NULL;</code></pre>
<p>This means “users that are not deleted yet” if <code>deleted_at</code> is used for soft deletes.</p>
<p><code>NULL</code> is part of SQL three-valued logic: predicates may evaluate to <code>TRUE</code>, <code>FALSE</code>, or <code>UNKNOWN</code>. In a <code>WHERE</code> clause, only <code>TRUE</code> rows are returned.</p>
</td>
<td valign="top" width="50%">
<p>Пример:</p>
<pre><code class="language-sql">SELECT *
FROM users
WHERE deleted_at IS NULL;</code></pre>
<p>Так можно получить пользователей, которые еще не удалены, если <code>deleted_at</code> используется для soft delete.</p>
<p><code>NULL</code> связан с трехзначной логикой SQL: условие может быть <code>TRUE</code>, <code>FALSE</code> или <code>UNKNOWN</code>. В <code>WHERE</code> попадают только строки, для которых условие равно <code>TRUE</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In schema design, nullable columns should be intentional. If a field is mandatory for business logic, use <code>NOT NULL</code> and ideally enforce it at the database level.</p>
<p>In application code, nullable database columns must map clearly to Java types: plain nullable reference, <code>Optional</code> at boundaries, or a domain-specific state.</p>
</td>
<td valign="top" width="50%">
<p>При проектировании схемы nullable-колонки должны быть осознанным выбором. Если поле обязательно для бизнес-логики, лучше поставить <code>NOT NULL</code> и зафиксировать это на уровне базы.</p>
<p>В Java-коде nullable-колонки должны явно маппиться в модель: nullable reference, <code>Optional</code> на границах или отдельное доменное состояние.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>NULL = NULL</code> is not true; it is <code>UNKNOWN</code>.</li>
<li>Use <code>IS NULL</code>, not <code>= NULL</code>.</li>
<li><code>NOT IN</code> can behave unexpectedly if the subquery contains <code>NULL</code>.</li>
<li>Most aggregates ignore <code>NULL</code>, but <code>COUNT(*)</code> does not.</li>
<li><code>NULL</code> may mean different business states, so avoid using it when a clearer domain value exists.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li><code>NULL = NULL</code> не true, а <code>UNKNOWN</code>.</li>
<li>Нужно использовать <code>IS NULL</code>, а не <code>= NULL</code>.</li>
<li><code>NOT IN</code> может работать неожиданно, если подзапрос возвращает <code>NULL</code>.</li>
<li>Большинство агрегатов игнорируют <code>NULL</code>, но <code>COUNT(*)</code> — нет.</li>
<li><code>NULL</code> может смешивать разные бизнес-состояния, поэтому иногда лучше завести явное доменное значение.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is <code>NULL</code> in SQL?<br>A: A marker for an absent, unknown, or not applicable value.</p>
<p>Q: How do you check for <code>NULL</code>?<br>A: With <code>IS NULL</code> or <code>IS NOT NULL</code>.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое <code>NULL</code> в SQL?<br>A: Маркер отсутствующего, неизвестного или неприменимого значения.</p>

<p>Nullable foreign keys полезны для опциональных связей, черновиков, отложенного назначения и workflow-состояний. Но их нужно проектировать осознанно, потому что они влияют на join-ы, API-ответы и бизнес-инварианты.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Foreign key does not automatically mean <code>NOT NULL</code>.</li>
<li>For mandatory relationships, use both <code>REFERENCES</code> and <code>NOT NULL</code>.</li>
<li>With composite foreign keys, null handling depends on match rules such as <code>MATCH SIMPLE</code> and <code>MATCH FULL</code>.</li>
<li>With PostgreSQL default <code>MATCH SIMPLE</code>, the foreign key check can pass if at least one referencing column is <code>NULL</code>.</li>
<li>Use <code>MATCH FULL</code> when a composite relationship should be all-or-none: either all referencing columns are <code>NULL</code>, or all of them must match a parent row.</li>
<li>Nullable foreign keys can turn inner joins into missing rows if the query is not written carefully.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Foreign key не означает автоматически <code>NOT NULL</code>.</li>
<li>Для обязательных связей нужны и <code>REFERENCES</code>, и <code>NOT NULL</code>.</li>
<li>Для composite foreign keys поведение с null зависит от match rules, например <code>MATCH SIMPLE</code> и <code>MATCH FULL</code>.</li>
<li>При PostgreSQL default <code>MATCH SIMPLE</code> foreign key check может пройти, если хотя бы одна referencing колонка равна <code>NULL</code>.</li>
<li><code>MATCH FULL</code> используют, когда composite relationship должен быть all-or-none: либо все referencing колонки <code>NULL</code>, либо все они должны ссылаться на родительская таблица row.</li>
<li>Nullable foreign keys могут привести к потере строк при неаккуратном inner join.</li>
</ul>
</td>

<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Can a foreign key be null?<br>A: Yes, if the foreign key column is nullable.</p>
<p>Q: How do you make a foreign key relationship mandatory?<br>A: Add <code>NOT NULL</code> to the foreign key column.</p>
</td>
<td valign="top" width="50%">
<p>Q: Может ли foreign key быть null?<br>A: Да, если колонка nullable.</p>

<details>
<summary><strong>DB-SQL-009. What are NOT NULL, CHECK, UNIQUE, PRIMARY KEY and FOREIGN KEY constraints?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>They are database rules that protect data integrity: required values, valid values, uniqueness, row identity, and relationships between tables.</p>
</td>
<td valign="top" width="50%">
<p>Это правила базы данных, которые защищают целостность данных: обязательность значений, допустимые значения, уникальность, идентичность строки и связи между таблицами.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>NOT NULL</code> means the column must have a value.</p>
<p><code>CHECK</code> validates a condition, for example positive price.</p>
<p><code>UNIQUE</code> prevents duplicate values.</p>
<p><code>PRIMARY KEY</code> uniquely identifies a row and implies <code>NOT NULL</code>.</p>
<p><code>FOREIGN KEY</code> ensures that a value references an existing row in another table, or another column set in the same table.</p>
</td>
<td valign="top" width="50%">
<p><code>NOT NULL</code> означает, что колонка обязана иметь значение.</p>
<p><code>CHECK</code> проверяет условие, например положительную цену.</p>
<p><code>UNIQUE</code> запрещает дубликаты.</p>
<p><code>PRIMARY KEY</code> уникально идентифицирует строку и подразумевает <code>NOT NULL</code>.</p>

<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>

    sku TEXT NOT NULL,
    quantity INT NOT NULL CHECK (quantity &gt; 0),
    UNIQUE (order_id, sku)
);</code></pre>
<p>This schema says that every item belongs to an order, quantity must be positive, and the same SKU cannot be duplicated inside one order.</p>

<td valign="top" width="50%">

    id BIGSERIAL PRIMARY KEY,

    quantity INT NOT NULL CHECK (quantity &gt; 0),
    UNIQUE (order_id, sku)
);</code></pre>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>Для production migrations на больших таблицах constraints нужно добавлять аккуратно. В PostgreSQL есть паттерны вроде <code>NOT VALID</code> constraints с последующим <code>VALIDATE CONSTRAINT</code>, а некоторые constraints могут быть <code>DEFERRABLE</code> и проверяться на commit транзакции.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Application validation and database constraints solve different problems; often both are needed.</li>
<li>Adding constraints to large existing tables may require careful migration and validation.</li>
<li><code>CHECK</code> constraints interact with <code>NULL</code>: if the check evaluates to <code>UNKNOWN</code>, the row may pass unless <code>NOT NULL</code> is also used.</li>
<li>Foreign keys improve correctness but can affect writes and deletes due to checks and locks.</li>
<li>PostgreSQL also supports exclusion constraints, which are useful for rules like preventing overlapping time ranges.</li>
<li><code>DEFERRABLE</code> constraints can be checked at transaction commit, which is useful for some bulk changes or circular references.</li>
<li>On large existing tables, adding a constraint with <code>NOT VALID</code> and validating it later can reduce migration risk.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Application validation и database constraints решают разные задачи; часто нужны оба уровня.</li>
<li>Добавление constraints на большие существующие таблицы требует аккуратной миграции и валидации.</li>
<li><code>CHECK</code> взаимодействует с <code>NULL</code>: если условие дает <code>UNKNOWN</code>, строка может пройти, если нет <code>NOT NULL</code>.</li>
<li>Foreign keys улучшают корректность, но могут влиять на записи и удаления из-за проверок и блокировок.</li>
<li>PostgreSQL также поддерживает exclusion constraints, которые полезны для правил вроде запрета пересекающихся временных интервалов.</li>
<li><code>DEFERRABLE</code> constraints могут проверяться на commit транзакции, что полезно для некоторых bulk changes или циклических ссылок.</li>
<li>На больших существующих таблицах constraint часто безопаснее добавлять через <code>NOT VALID</code> и позже выполнять <code>VALIDATE CONSTRAINT</code>.</li>
</ul>

<summary><strong>DB-SQL-011. What is the difference between DELETE, TRUNCATE and DROP?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>DELETE</code> removes selected rows, <code>TRUNCATE</code> quickly removes all rows from a table, and <code>DROP</code> removes the database object itself.</p>
</td>
<td valign="top" width="50%">
<p><code>DELETE</code> удаляет выбранные строки, <code>TRUNCATE</code> быстро очищает всю таблицу, а <code>DROP</code> удаляет сам объект базы данных.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>DELETE</code> is DML. It can use <code>WHERE</code>, deletes rows one by one logically, fires delete triggers, and can be rolled back inside a transaction.</p>
<p><code>TRUNCATE</code> removes all rows from a table and is usually much faster for full cleanup. In PostgreSQL it is transactional, but it takes stronger locks and has different trigger behavior.</p>
<p><code>DROP</code> removes the table, index, view, or another object definition, not just its data.</p>
</td>
<td valign="top" width="50%">
<p><code>DELETE</code> — это DML. Он может использовать <code>WHERE</code>, логически удаляет строки, вызывает delete triggers и может быть откатан внутри транзакции.</p>
<p><code>TRUNCATE</code> удаляет все строки из таблицы и обычно намного быстрее для полной очистки. В PostgreSQL он транзакционный, но берет более сильные блокировки и имеет другое поведение triggers.</p>
<p><code>DROP</code> удаляет определение таблицы, индекса, view или другого объекта, а не только данные.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<pre><code class="language-sql">DELETE FROM sessions WHERE expires_at &lt; now();
TRUNCATE TABLE staging_events;
DROP TABLE old_import_buffer;</code></pre>
<p><code>DELETE</code> is for selective removal. <code>TRUNCATE</code> is for full table cleanup. <code>DROP</code> is a schema operation.</p>
</td>
<td valign="top" width="50%">
<pre><code class="language-sql">DELETE FROM sessions WHERE expires_at &lt; now();
TRUNCATE TABLE staging_events;
DROP TABLE old_import_buffer;</code></pre>
<p><code>DELETE</code> нужен для выборочного удаления. <code>TRUNCATE</code> — для полной очистки таблицы. <code>DROP</code> — операция со схемой.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">

<td valign="top" width="50%">

<p>Для большой исторической очистки часто безопаснее делать batch deletes или удаление или отсоединение старых секции (partitions), чем один огромный <code>DELETE</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>DELETE</code> without <code>WHERE</code> removes all rows.</li>
<li><code>TRUNCATE</code> is not a filtered operation.</li>
<li><code>TRUNCATE</code> may restart identity sequences if requested with <code>RESTART IDENTITY</code>.</li>
<li><code>DROP ... CASCADE</code> can remove dependent objects.</li>
<li>Behavior differs across DBMSs, especially transaction behavior around DDL.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li><code>DELETE</code> без <code>WHERE</code> удаляет все строки.</li>
<li><code>TRUNCATE</code> не умеет фильтровать строки.</li>
<li><code>TRUNCATE</code> может сбросить identity sequences, если использовать <code>RESTART IDENTITY</code>.</li>
<li><code>DROP ... CASCADE</code> может удалить зависимые объекты.</li>
<li>Поведение отличается между СУБД, особенно транзакционность DDL.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>

<summary><strong>DB-SQL-012. What is the difference between UNION and UNION ALL?</strong></summary>

<table>
<tbody>
<tr>

</tr>
<tr>
<td valign="top" width="50%">
<p><code>UNION</code> combines result sets and removes duplicates. <code>UNION ALL</code> combines result sets and keeps duplicates.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">
<pre><code class="language-sql">SELECT email FROM customers
UNION
SELECT email FROM newsletter_subscribers;</code></pre>
<p>Этот запрос вернет уникальные email. С <code>UNION ALL</code> повторяющиеся email останутся.</p>

</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">
<p>Лучше использовать <code>UNION ALL</code>, если дубликаты невозможны или допустимы. <code>UNION</code> нужен только когда deduplication требуется бизнес-логикой.</p>
</td>
</tr>

<th colspan="2" align="left">Traps / caveats</th>

<p>Recursive CTE состоит из двух частей: нерекурсивного base query и recursive query, который ссылается на имя CTE. База повторяет recursive part, пока не перестают появляться новые строки.</p>
<p>Типичные примеры: дерево категорий, оргструктура, комментарии с ответами и обход графа.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<pre><code class="language-sql">WITH RECURSIVE category_tree AS (
    SELECT id, parent_id, name
    FROM categories
    WHERE id = 10

    UNION ALL

    SELECT c.id, c.parent_id, c.name
    FROM categories c
    JOIN category_tree t ON c.parent_id = t.id
)
SELECT *
FROM category_tree;</code></pre>
</td>
<td valign="top" width="50%">
<pre><code class="language-sql">WITH RECURSIVE category_tree AS (

<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Recursive CTEs are convenient, but for deep or frequently queried hierarchies, consider indexing parent columns, limiting depth, caching, closure tables, materialized paths, or denormalized read models.</p>
</td>
<td valign="top" width="50%">
<p>Recursive CTE удобны, но для глубоких или часто читаемых иерархий стоит подумать об индексах по родительская таблица-колонкам, ограничении глубины, кэше, closure tables, materialized path или денормализованных модели чтения (read models).</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Cycles can cause repeated traversal unless handled.</li>
<li>Use <code>UNION ALL</code> when deduplication is not required; <code>UNION</code> adds deduplication cost.</li>
<li>For graph-like data, add explicit cycle protection; PostgreSQL also supports <code>SEARCH</code> and <code>CYCLE</code> syntax in modern versions.</li>
<li>Recursive queries can become expensive on large graphs.</li>
<li>Use indexes on parent/reference columns.</li>
<li>Consider adding depth limits for safety.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Циклы могут привести к повторному обходу, если их не обработать.</li>
<li>Используй <code>UNION ALL</code>, если deduplication не нужен; <code>UNION</code> добавляет стоимость удаления дубликатов.</li>
<li>Для graph-like данных нужна явная защита от циклов; в современных версиях PostgreSQL также есть syntax <code>SEARCH</code> и <code>CYCLE</code>.</li>
<li>Recursive queries могут стать дорогими на больших графах.</li>
<li>Нужны индексы по родительская таблица/reference колонкам.</li>
<li>Для безопасности часто стоит добавлять ограничение глубины.</li>
</ul>
</td>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A view is a named saved SQL query that can be used like a virtual table. It usually stores the query definition, not the data.</p>
</td>
<td valign="top" width="50%">
<p>View — это именованный сохраненный SQL-запрос, который можно использовать как виртуальную таблицу. Обычно view хранит определение запроса, а не данные.</p>

</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A view hides query complexity behind a database object. Instead of repeating a complex join or filter in many places, we can define it once and query the view.</p>
<p>Views are also useful for access control: we can expose only certain columns or rows to some users.</p>
</td>
<td valign="top" width="50%">
<p>View скрывает сложность запроса за объектом базы данных. Вместо повторения сложного join или filter в разных местах можно один раз определить view и читать из него.</p>
<p>Views также полезны для access control: можно показать пользователю только определенные колонки или строки.</p>

<details>
<summary><strong>🧠 DB-SQL-020. What is a materialized view in PostgreSQL?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A materialized view stores the result of a query physically. It can make expensive reads faster, but the data becomes stale until the materialized view is refreshed.</p>
</td>
<td valign="top" width="50%">
<p>Materialized view физически хранит результат запроса. Она может ускорить дорогие чтения, но данные устаревают, пока view не обновят через refresh.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In PostgreSQL, a materialized view is similar to a cached table created from a query. Unlike a regular view, it stores data on disk.</p>
<p>We use it when the query is expensive and the application can tolerate stale data, for example reports, dashboards, or precomputed search data.</p>
<p>To update the data, we run <code>REFRESH MATERIALIZED VIEW</code>. PostgreSQL also supports <code>REFRESH MATERIALIZED VIEW CONCURRENTLY</code>, but it requires a suitable <code>UNIQUE</code> index on the materialized view that covers all rows and uses only column names, not an expression or partial index.</p>
</td>
<td valign="top" width="50%">
<p>В PostgreSQL materialized view похожа на cached table, созданную из запроса. В отличие от обычной view, она хранит данные на диске.</p>
<p>Ее используют, когда запрос дорогой, а приложение может терпеть устаревшие данные, например для отчетов, dashboards или precomputed search data.</p>
<p>Чтобы обновить данные, выполняют <code>REFRESH MATERIALIZED VIEW</code>. PostgreSQL также поддерживает <code>REFRESH MATERIALIZED VIEW CONCURRENTLY</code>, но для него нужен подходящий <code>UNIQUE</code> index на materialized view, который покрывает все строки и использует только имена колонок, а не expression или partial index.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">

       SUM(total_amount) AS revenue
FROM orders
GROUP BY date_trunc('day', created_at);</code></pre>
<pre><code class="language-sql">REFRESH MATERIALIZED VIEW daily_sales;</code></pre>
</td>

<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Materialized views are useful for read-heavy reporting workloads. The key production questions are refresh frequency, refresh duration, locking behavior, staleness tolerance, and whether indexes are needed on the materialized view.</p>
</td>
<td valign="top" width="50%">
<p>Materialized views полезны для read-heavy отчетов. Главные production-вопросы: частота refresh, длительность refresh, блокировки, допустимая устаревшие данные (stale data) и нужны ли индексы на materialized view.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Materialized views are not updated automatically when base tables change.</li>
<li>Data can be stale between refreshes.</li>
<li>Refresh can be expensive and may need scheduling.</li>
<li><code>REFRESH ... CONCURRENTLY</code> requires at least one suitable <code>UNIQUE</code> index on the materialized view that includes all rows and is not an expression or partial index.</li>
<li><code>REFRESH ... CONCURRENTLY</code> can reduce read blocking, but it is usually slower and still consumes resources.</li>
<li>Indexes on base tables do not replace indexes on the materialized view itself.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Materialized views не обновляются автоматически при изменении базовых таблиц.</li>
<li>Данные могут быть stale между refresh-ами.</li>
<li>Refresh может быть дорогим и требовать расписания.</li>
<li><code>REFRESH ... CONCURRENTLY</code> требует хотя бы один подходящий <code>UNIQUE</code> index на materialized view, который включает все строки и не является expression или partial index.</li>
<li><code>REFRESH ... CONCURRENTLY</code> может уменьшить read blocking, но обычно работает дольше и всё равно потребляет ресурсы.</li>
<li>Индексы на базовых таблицах не заменяют индексы на самой materialized view.</li>
</ul>
