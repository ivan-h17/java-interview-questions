# Configuration fundamentals and principles

---

<a id="conf-fund-001"></a>

<details>
<summary><strong>CONF-FUND-001. What is externalized configuration?</strong></summary>

#### Short answer

Externalized configuration means values that vary between environments are supplied from outside the application code and artifact.

#### Interview answer

In a Java backend service, externalized configuration includes database URLs, credentials, timeouts, endpoints, feature switches and deployment-specific settings. The code is built once, and each environment provides its own values through files, environment variables, Kubernetes ConfigMaps or Secrets, config servers or cloud secret managers.

#### Deep dive

The key idea is separating stable behavior from deploy-specific values. The application still needs defaults, validation and clear ownership, but it should not require a code change or rebuild just to point to another database or change a timeout.

#### Production angle

Externalized configuration enables artifact promotion, safer rollbacks and easier incident mitigation because runtime settings can be inspected and changed independently from code.

#### Traps / caveats

- Externalizing everything creates chaos; not every value should be configurable.
- Secrets are configuration-like, but need stronger handling.
- Config changes still need review, validation and observability.

#### Optional Anki

Q: What is externalized configuration?
A: Deploy-specific values supplied outside the application code and artifact.

</details>

<details>
<summary><strong>CONF-FUND-002. Why should configuration be separated from application code, and what goes wrong when environment-specific values are hardcoded?</strong></summary>

#### Short answer

Hardcoded environment values make releases brittle, unsafe and hard to promote across environments.

#### Interview answer

Configuration should be separate because code changes and environment settings change for different reasons. If a database URL, API endpoint, timeout or secret is hardcoded, every environment change requires a rebuild and redeploy. That increases release risk and can accidentally ship staging values, debug settings or secrets to production.

#### Deep dive

A clean service should let the same artifact run in local, test, staging and production with different inputs. This also makes containers and CI/CD pipelines simpler: build once, deploy many times.

#### Production angle

Hardcoded values often cause incidents during migrations, region failovers, credential rotation and emergency timeout changes.

#### Traps / caveats

- Constants are fine for domain invariants that do not vary by deploy.
- Do not replace hardcoded values with undocumented magic environment variables.
- Moving a secret from code to plain Git config is not a real fix.

#### Optional Anki

Q: Why avoid hardcoded environment-specific values?
A: They force rebuilds, break artifact promotion and can leak wrong or sensitive settings into production.

</details>

<a id="conf-fund-003"></a>

<details>
<summary><strong>🧠 CONF-FUND-003. What is the difference between build-time, startup-time, and runtime configuration?</strong></summary>

#### Short answer

Build-time config affects the artifact, startup-time config is read when the app starts, and runtime config can change while the app is running.

#### Interview answer

Build-time configuration includes dependency versions, compiler options and image build settings. Startup-time configuration includes Spring profiles, datasource URLs, credentials and pool sizes loaded before beans are created. Runtime configuration includes feature flags, kill switches or dynamic limits that can change without restarting.

#### Deep dive

The later a value can change, the more guardrails it needs. Runtime changes are powerful, but they can create inconsistent behavior across replicas or update objects that were not designed to be refreshed.

#### Production angle

Timeouts, retry counts and pool sizes are tempting to make dynamic, but changing them during traffic can cause retry storms, connection churn or uneven behavior.

#### Traps / caveats

- Do not assume every Spring property can be safely refreshed.
- Build-time secrets can leak into images or artifacts.
- Runtime config must have validation, audit and rollback.

#### Optional Anki

Q: Why is runtime configuration riskier than startup-time configuration?
A: It changes live behavior and can make replicas inconsistent unless guarded.

</details>

<a id="conf-fund-004"></a>

<details>
<summary><strong>CONF-FUND-004. What is the difference between static and dynamic configuration, and what are the trade-offs?</strong></summary>

#### Short answer

Static configuration changes only with restart or redeploy; dynamic configuration can change while the service is running.

#### Interview answer

Static configuration is simpler and easier to reason about because every instance starts with a known set of values. Dynamic configuration gives faster operational control, such as disabling a feature or lowering a limit during an incident, but adds consistency, validation and observability problems.

#### Deep dive

Static config is a good default for structural settings like datasource setup, bean wiring and core integration choices. Dynamic config fits operational toggles, kill switches, throttles and safe rollout controls.

#### Production angle

Dynamic config can reduce recovery time, but a bad dynamic value can instantly affect the whole fleet.

#### Traps / caveats

- Dynamic config should not bypass normal change control.
- Static config can still be dangerous if defaults are unsafe.
- Avoid making irreversible behavior depend only on a live toggle.

#### Optional Anki

Q: Static vs dynamic configuration?
A: Static changes at restart or deploy; dynamic can change while running.

</details>

<a id="conf-fund-005"></a>

<details>
<summary><strong>CONF-FUND-005. Why should the same artifact be deployable to multiple environments?</strong></summary>

#### Short answer

It proves the artifact is environment-independent and lets teams promote the same tested build to production.

#### Interview answer

A service should be built once and configured per environment. If staging and production use different artifacts, you are not testing what you deploy. The same JAR or container image should move through the pipeline while external configuration supplies environment-specific values.

#### Deep dive

This reduces hidden build differences, improves traceability and makes rollbacks more reliable. It also supports container and Kubernetes practices where images are immutable deployment units.

#### Production angle

During an incident, you can compare image version and configuration version separately. That makes it easier to know whether a failure came from code, deployment config or runtime flags.

#### Traps / caveats

- Environment-specific config is still allowed; environment-specific builds are the problem.
- Do not bake secrets into images to achieve "self-contained" deployments.
- Native images and build-time optimizations need care because some settings may become fixed at build time.

#### Optional Anki

Q: Why promote the same artifact across environments?
A: So production runs the exact build that was tested, with only external config changing.

</details>

<a id="conf-fund-006"></a>

<details>
<summary><strong>CONF-FUND-006. What is configuration drift, and how can it cause production incidents?</strong></summary>

#### Short answer

Configuration drift is when environments or replicas unintentionally diverge in settings.

#### Interview answer

Drift happens when staging, production, regions or pods have different values that nobody intended or documented. One region may use a different timeout, one pod may have an old secret, or staging may miss a security setting. This causes behavior that is hard to reproduce and easy to misdiagnose.

#### Deep dive

Drift often comes from manual changes, copied config files, profile explosion, partially rolled out config or undocumented emergency fixes.

#### Production angle

A service can fail only in one region, one tenant or one replica because the effective configuration differs from the expected baseline.

#### Traps / caveats

- "It works in staging" does not mean production config is equivalent.
- Config drift can hide for months until traffic hits the affected path.
- Runtime flags can create drift if targeting is unclear.

#### Optional Anki

Q: What is configuration drift?
A: Unintended differences in effective configuration across environments, regions or replicas.

</details>

<details>
<summary><strong>CONF-FUND-007. What configuration values should be environment-specific, and what should usually not be configurable?</strong></summary>

#### Short answer

Environment-specific values are external endpoints, credentials, resource limits and operational thresholds; domain invariants and core rules should usually stay in code.

#### Interview answer

Good configuration candidates are database URLs, queue names, credentials, external service endpoints, timeouts, pool sizes, log levels, feature rollout settings and region-specific resource names. Values that express business invariants, data model assumptions or required security behavior usually should not be freely configurable.

#### Deep dive

The decision depends on how often a value changes, who owns it, whether invalid values are dangerous and whether changes need code review.

#### Production angle

Too little configuration makes operations slow. Too much configuration turns production into an untyped programming language with weak review.

#### Traps / caveats

- Do not make authorization rules configurable without strong controls.
- Do not hide business behavior behind undocumented flags.
- Defaults should be safe, not just convenient.

#### Optional Anki

Q: What values are usually environment-specific?
A: Endpoints, credentials, resource names, timeouts, limits and operational settings.

</details>

<a id="conf-fund-008"></a>

<details>
<summary><strong>CONF-FUND-008. How do you decide whether a value should be hardcoded, configured, or feature-flagged?</strong></summary>

#### Short answer

Hardcode invariants, configure deploy-specific settings, and use feature flags for controlled behavior changes.

#### Interview answer

If a value is a stable rule of the system, keep it in code. If it varies by environment or deployment, make it configuration. If it controls rollout, exposure, mitigation or experimentation, use a feature flag with ownership and cleanup.

#### Deep dive

I also ask who should change it, how fast it must change, what happens if it is wrong and whether it needs audit. A timeout may be configuration; enabling a new algorithm for 5 percent of users is a feature flag; a tax calculation rule should normally be code with tests.

#### Production angle

This distinction prevents both extremes: rebuilding for every operational tweak and letting production behavior mutate without engineering review.

#### Traps / caveats

- Feature flags are not a substitute for permissions.
- Configuration is not a place for complex business logic.
- Hardcoded does not mean untested or undocumented.

#### Optional Anki

Q: Configure or feature-flag?
A: Configure deploy settings; feature-flag controlled behavior rollout or mitigation.

</details>

<a id="conf-fund-009"></a>

<details>
<summary><strong>🧠 CONF-FUND-009. How do ownership, documentation, and safe defaults reduce configuration risk?</strong></summary>

#### Short answer

They make it clear who can change a value, what it means and what happens when it is missing.

#### Interview answer

Every important setting should have an owner, purpose, valid range, default behavior and operational impact. Documentation should say whether restart is needed and whether the value is safe to change during traffic. Safe defaults reduce the chance that a missing or typoed value creates unsafe behavior.

#### Deep dive

Typed configuration classes, generated metadata, runbooks and config review templates all help. For high-risk settings, the default should usually fail closed or fail fast rather than silently enabling risky behavior.

#### Production angle

During incidents, clear ownership prevents guessing and shortens recovery time.

#### Traps / caveats

- Defaults can hide missing config if they are too permissive.
- Ownership without audit is weak.
- Documentation must track real behavior, not ideal behavior.

#### Optional Anki

Q: What should a critical config key document?
A: Owner, purpose, valid values, default, restart needs and operational risk.

</details>

<details>
<summary><strong>🧠 CONF-FUND-010. How can configuration become a hidden dependency between services?</strong></summary>

#### Short answer

Services become secretly coupled when one service's behavior depends on another service using compatible config values.

#### Interview answer

Examples include matching topic names, timeout assumptions, feature flags, schema versions, route names or shared credentials. If these dependencies are not documented or validated, one service can change a value and break another service without a code change.

#### Deep dive

Hidden config dependencies are common in microservices because each service may be deployed independently but still shares runtime assumptions with other services.

#### Production angle

A rollout may fail only when producer and consumer configs are incompatible, even though both services pass their own tests.

#### Traps / caveats

- Shared config can reduce duplication but increase coupling.
- Names like queues, topics and buckets are API contracts in practice.
- Feature flags used across services need a compatibility plan.

#### Optional Anki

Q: Give an example of a hidden config dependency.
A: Producer and consumer using matching Kafka topic names or compatible feature-flag states.

</details>

<details>
<summary><strong>🧠 CONF-FUND-011. How do you safely rename, deprecate, or remove configuration keys without breaking deployments?</strong></summary>

#### Short answer

Support both old and new keys temporarily, warn on old usage, migrate deployments, then remove the old key after validation.

#### Interview answer

I would introduce the new key while keeping the old key as a fallback. The app should log a non-sensitive deprecation warning or expose a config validation warning when the old key is used. Then update deployment config across environments, verify effective config, and remove old support in a later release.

#### Deep dive

For risky keys, treat the migration like an API change. Version it, document it and test mixed rollout states where old and new app versions run at the same time.

#### Production angle

This prevents startup failures during rolling deployments or GitOps sync delays.

#### Traps / caveats

- Do not let old and new keys silently disagree.
- Do not remove a key in the same release that introduces its replacement.
- Avoid logging secret values while warning about deprecated keys.

#### Optional Anki

Q: Safe config key rename pattern?
A: Add new key, keep old fallback, warn, migrate deployments, verify, then remove later.

</details>
