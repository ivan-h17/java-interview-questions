# Security and compliance traps

---

<a id="conf-comp-001"></a>

<details>
<summary><strong>CONF-COMP-001. What is secret scanning, and why is it important?</strong></summary>

#### Short answer

Secret scanning detects credentials accidentally committed to code, logs or artifacts.

#### Interview answer

Secret scanners look for tokens, private keys, API keys and credential patterns in repositories, CI logs, images and artifacts. They help catch leaks early, before a credential spreads or gets abused.

#### Deep dive

Scanning should run before merge and on existing repositories. For known provider tokens, some scanners can trigger alerts or revocation workflows.

#### Production angle

Secret scanning reduces the time between accidental exposure and response.

#### Traps / caveats

- Scanning does not replace secret managers.
- False positives need triage, not blanket ignoring.
- A detected real secret must usually be rotated.

#### Optional Anki

Q: What should happen after detecting a real committed secret?
A: Rotate or revoke it and remove the leak source.

</details>

<a id="conf-comp-002"></a>

<details>
<summary><strong>CONF-COMP-002. What should happen if a secret is committed to Git, and why must it be rotated even after history cleanup?</strong></summary>

#### Short answer

Remove the exposure, rotate the secret and assume copies may exist outside the current branch.

#### Interview answer

If a secret is committed, first stop further exposure and rotate or revoke the credential. Then remove it from the repository and history if needed, notify affected owners and check audit logs. Rotation is required because Git history, clones, forks, CI caches and backups may still contain the old value.

#### Deep dive

History cleanup reduces future accidental discovery, but it cannot prove all copies are gone.

#### Production angle

The only reliable containment is making the leaked credential useless.

#### Traps / caveats

- Do not only amend the latest commit.
- Coordinate rotation before breaking clients.
- Preserve enough evidence for incident review.

#### Optional Anki

Q: Why rotate after removing a secret from Git?
A: Because old copies may still exist in clones, caches and history.

</details>

<a id="conf-comp-003"></a>

<details>
<summary><strong>CONF-COMP-003. How should applications avoid exposing secrets in error responses?</strong></summary>

#### Short answer

Return safe error messages and keep detailed sensitive diagnostics in protected logs.

#### Interview answer

Error responses should not include connection strings, tokens, stack traces, SQL details, headers or config values. Use generic client-facing errors with correlation IDs, and log only sanitized diagnostic context.

#### Deep dive

Framework default error pages and exception mappers need review. In Spring Boot, production error responses should avoid stack traces and internal messages unless explicitly safe.

#### Production angle

External error responses are visible to users and attackers, so they must not reveal secrets or internal topology.

#### Traps / caveats

- Exception messages from libraries can contain URLs or credentials.
- Correlation IDs are safer than raw diagnostic dumps.
- Logs still need redaction.

#### Optional Anki

Q: What should a production error response expose instead of internals?
A: A safe message and correlation ID.

</details>

<a id="conf-comp-004"></a>

<details>
<summary><strong>CONF-COMP-004. How can configuration mistakes create authorization bypasses?</strong></summary>

#### Short answer

Bad config can disable security checks, trust wrong headers, expose endpoints or misapply tenant boundaries.

#### Interview answer

Examples include enabling a public profile, misconfiguring `permitAll`, trusting identity headers from untrusted networks, disabling CSRF where cookies are used, setting a broad CORS policy or pointing to the wrong policy source.

#### Deep dive

Security configuration is code-like behavior. It needs tests, review and deny-by-default assumptions.

#### Production angle

Authorization bypasses from config are common because they may happen without changing application code.

#### Traps / caveats

- Feature flags are not permissions.
- Gateway auth does not remove service-side authorization needs.
- Local dev security shortcuts must not reach production.

#### Optional Anki

Q: What is a config-caused auth bypass example?
A: Accidentally permitting a protected endpoint or trusting untrusted identity headers.

</details>

<a id="conf-comp-005"></a>

<details>
<summary><strong>🧠 CONF-COMP-005. How do you remove a secret from Git history, and why is that not enough?</strong></summary>

#### Short answer

Rewrite history with appropriate tooling, force-update affected refs carefully, but still rotate the secret.

#### Interview answer

Tools like `git filter-repo` or repository-hosting cleanup workflows can remove a secret from history. After rewriting, coordinate with collaborators because clones and branches may still contain old commits. The secret must be rotated because history cleanup cannot erase all copies.

#### Deep dive

History rewrites can disrupt teams, tags and open branches. For public or widely cloned repos, assume the secret is permanently exposed.

#### Production angle

Rotation is the security fix; history cleanup is hygiene and exposure reduction.

#### Traps / caveats

- Do not run destructive Git cleanup casually.
- CI caches and artifacts may still contain the secret.
- Notify owners and audit usage.

#### Optional Anki

Q: Is Git history cleanup enough after a secret leak?
A: No, the credential must be rotated or revoked.

</details>

<a id="conf-comp-006"></a>

<details>
<summary><strong>🧠 CONF-COMP-006. How can container image layers or CI logs leak secrets?</strong></summary>

#### Short answer

Secrets can persist in build layers, command history, rendered manifests, test output or masked-but-transformed logs.

#### Interview answer

If a Dockerfile copies a secret and later deletes it, the value may still exist in an earlier image layer. CI logs can leak secrets through `echo`, failed commands, debug output, rendered Helm templates, stack traces or dependency tooling.

#### Deep dive

Use build secret mounts, avoid passing secrets as build args, restrict logs and ensure masking handles common variants.

#### Production angle

Build systems and registries often have broader access than production secret stores.

#### Traps / caveats

- Docker build args are not a safe secret mechanism.
- Masking may fail if secrets are encoded, split or transformed.
- Rendered manifests can expose Kubernetes Secret data.

#### Optional Anki

Q: Why is deleting a copied secret in a later image layer unsafe?
A: It may remain in an earlier image layer.

</details>

<a id="conf-comp-007"></a>

<details>
<summary><strong>🧠 CONF-COMP-007. What are the risks of passing secrets through command-line arguments, environment variables, or JVM system properties?</strong></summary>

#### Short answer

They can appear in process metadata, diagnostics, dumps, scripts, logs or inherited environments.

#### Interview answer

Command-line arguments may be visible through process listings or startup logs. Environment variables can appear in container specs, diagnostics or crash reports. JVM system properties can show up in thread dumps, logs or Actuator-style diagnostics.

#### Deep dive

Mounted files or secret manager integration may be better for high-value secrets, especially certificates and private keys.

#### Production angle

The delivery path must match the sensitivity of the secret and the observability tools in use.

#### Traps / caveats

- Environment variables are common but not automatically safe.
- Avoid putting secrets in URLs.
- Redact startup command logging.

#### Optional Anki

Q: Why avoid secrets in command-line arguments?
A: They may be visible in process listings or logs.

</details>

<a id="conf-comp-008"></a>

<details>
<summary><strong>🧠 CONF-COMP-008. What are the risks of encrypting secrets for Git without controlling who can decrypt or apply them?</strong></summary>

#### Short answer

Encrypted secrets in Git are only safe if decryption keys and apply permissions are tightly controlled.

#### Interview answer

Tools that encrypt secrets for Git can be useful, but they move the trust boundary to key management. If every developer or CI job can decrypt production secrets, the encrypted repository does not provide strong separation.

#### Deep dive

Good designs restrict decryption by environment, role and automation identity. They also audit who applied or decrypted secrets.

#### Production angle

Encrypted Git secrets can support GitOps, but careless key distribution recreates the same broad access problem.

#### Traps / caveats

- Encryption is not a substitute for least privilege.
- Rotating the secret may also require rotating encryption keys.
- Do not print decrypted manifests in CI.

#### Optional Anki

Q: Main risk of encrypted secrets in Git?
A: Too many people or jobs may have decrypt/apply access.

</details>
