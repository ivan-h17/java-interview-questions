# Testing configuration, secrets and flags

---

<a id="conf-test-001"></a>

<details>
<summary><strong>CONF-TEST-001. How do you test that required configuration is present?</strong></summary>

#### Short answer

Start the application context with production-like config and assert that missing required values fail startup.

#### Interview answer

Required config should be represented by validated `@ConfigurationProperties`. Tests should load the context with missing values and verify startup failure, and load it with valid values and verify success. CI can also validate deployment manifests or environment templates.

#### Deep dive

For critical services, add smoke tests that run the packaged artifact with realistic config before production rollout.

#### Production angle

This catches missing secrets or properties before a pod reaches production.

#### Traps / caveats

- Tests can hide missing config by using test defaults.
- Do not use real production secrets in tests.
- Validate optional config only when the feature is enabled.

#### Optional Anki

Q: Best way to catch missing required config?
A: Validated config classes plus startup tests.

</details>

<a id="conf-test-002"></a>

<details>
<summary><strong>CONF-TEST-002. How do you test invalid configuration values and @ConfigurationProperties validation?</strong></summary>

#### Short answer

Run focused context or binder tests with invalid values and assert validation errors.

#### Interview answer

I would test invalid timeouts, negative pool sizes, blank URLs, missing credentials for enabled integrations and bad enum values. The test should prove the application fails fast with a useful error, not that it fails later during a request.

#### Deep dive

For complex validation, unit test the validator and add a context startup test to prove it is wired.

#### Production angle

Invalid config tests prevent dangerous defaults and misconfigured deployments.

#### Traps / caveats

- Do not test only happy-path config.
- Ensure test overrides do not bypass validation.
- Error messages must not print secrets.

#### Optional Anki

Q: What should invalid config tests prove?
A: The app fails fast before serving traffic.

</details>

<a id="conf-test-003"></a>

<details>
<summary><strong>🧠 CONF-TEST-003. How do you override configuration in Spring Boot tests?</strong></summary>

#### Short answer

Use test properties, `@TestPropertySource`, `@DynamicPropertySource`, profiles or test-specific config files.

#### Interview answer

For simple overrides, `@SpringBootTest(properties = "...")` works. `@TestPropertySource` can load properties. `@DynamicPropertySource` is useful when values are known only at runtime, such as Testcontainers ports. Test profiles can select test-specific configuration.

#### Deep dive

Prefer focused overrides close to the test. Too many global test properties can hide production behavior.

#### Production angle

Correct test overrides let integration tests use realistic dependencies without committing secrets or fixed local ports.

#### Traps / caveats

- Test property precedence can hide mistakes.
- Avoid broad test profiles that disable too much behavior.
- Do not hardcode production-like credentials.

#### Optional Anki

Q: Which annotation helps inject Testcontainers dynamic ports?
A: `@DynamicPropertySource`.

</details>

<a id="conf-test-004"></a>

<details>
<summary><strong>CONF-TEST-004. How do you test code paths behind feature flags?</strong></summary>

#### Short answer

Test both enabled and disabled states, plus fallback behavior for important flags.

#### Interview answer

For feature-flagged code, unit tests should cover old and new behavior. Integration tests should verify routing, side effects and compatibility when the flag is on and off. For risky flags, test gradual rollout assumptions and idempotency.

#### Deep dive

A feature flag is a branch in production code. Treat it like any other branch that needs coverage.

#### Production angle

Testing only the enabled state makes rollback dangerous; testing only disabled state makes rollout dangerous.

#### Traps / caveats

- Do not leave stale flag branches untested.
- Test fallback when the flag provider is unavailable.
- Use stable decisions for workflows and side effects.

#### Optional Anki

Q: What two states must feature-flagged code test?
A: Enabled and disabled.

</details>

<a id="conf-test-005"></a>

<details>
<summary><strong>CONF-TEST-005. How do you avoid using production secrets in tests or local development?</strong></summary>

#### Short answer

Use local fake credentials, test-only secret stores, ephemeral resources and clear environment separation.

#### Interview answer

Tests should use generated credentials, Testcontainers, mock servers, local emulators or dedicated non-production accounts. Local development should never require production secrets. CI should inject only scoped test secrets when absolutely needed.

#### Deep dive

If developers need production-like access, use controlled break-glass processes or read-only sanitized environments, not copied secrets.

#### Production angle

Production secrets in tests often leak through logs, workstations, CI caches and local config files.

#### Traps / caveats

- Do not commit sample config with real-looking secrets.
- Avoid shared long-lived test credentials.
- CI logs must still mask test secrets.

#### Optional Anki

Q: What should local development use instead of production secrets?
A: Fake, local, ephemeral or scoped non-production credentials.

</details>

<a id="conf-test-006"></a>

<details>
<summary><strong>CONF-TEST-006. How do you test code that uses a feature-flag abstraction without depending on a vendor SDK?</strong></summary>

#### Short answer

Mock or fake the application-owned flag interface, not the vendor SDK.

#### Interview answer

If business code depends on a `FeatureDecisions` interface, tests can provide a simple fake implementation that returns enabled or disabled values. This keeps tests fast and independent from provider details.

#### Deep dive

Integration tests can separately verify the adapter that maps the vendor SDK or OpenFeature provider into the application interface.

#### Production angle

This makes provider migration and fallback behavior easier to test.

#### Traps / caveats

- Do not mock many string flag names in every test.
- Keep fallback values centralized.
- Test evaluation context construction.

#### Optional Anki

Q: What should business tests mock for flags?
A: The application-owned feature decision interface.

</details>

<a id="conf-test-007"></a>

<details>
<summary><strong>🧠 CONF-TEST-007. How does @DynamicPropertySource help with Testcontainers?</strong></summary>

#### Short answer

It registers properties whose values are known only after containers start.

#### Interview answer

Testcontainers often picks random ports or generates connection URLs at runtime. `@DynamicPropertySource` lets tests register those values into Spring's environment before the application context binds configuration.

#### Deep dive

This is useful for database URLs, Kafka bootstrap servers, Redis ports or WireMock endpoints.

#### Production angle

It enables integration tests with realistic dependencies without hardcoded local ports.

#### Traps / caveats

- Static container lifecycle and context caching can surprise tests.
- Dynamic properties can override production-like config unintentionally.
- Still validate required production config elsewhere.

#### Optional Anki

Q: Why use `@DynamicPropertySource` with Testcontainers?
A: To inject runtime container connection values into Spring config.

</details>

<a id="conf-test-008"></a>

<details>
<summary><strong>🧠 CONF-TEST-008. How do you test fallback behavior when a feature flag or configuration provider is unavailable?</strong></summary>

#### Short answer

Simulate provider failure and assert explicit fallback, cached, degraded or fail-fast behavior.

#### Interview answer

Tests should cover provider timeouts, errors, empty responses and stale cache. For each important flag or dynamic config, verify whether the service uses last-known-good, safe default, degraded mode or startup failure.

#### Deep dive

Fallback behavior should be part of the application contract, not an accidental SDK default.

#### Production angle

Provider outage tests prevent a config or flag provider from becoming a single point of failure.

#### Traps / caveats

- Test fallback metrics and logs too.
- Different flags may need different fallbacks.
- Do not assume network failures are fast.

#### Optional Anki

Q: What should provider outage tests verify?
A: Safe fallback or fail-fast behavior, plus observability.

</details>

<a id="conf-test-009"></a>

<details>
<summary><strong>🧠 CONF-TEST-009. How can contract tests or CI checks catch configuration-related integration failures?</strong></summary>

#### Short answer

They verify that service assumptions, config keys and dependency contracts match before deployment.

#### Interview answer

Contract tests can catch mismatched endpoints, topics, schema versions, auth expectations or required headers. CI checks can validate config files, required secrets, Kubernetes manifests and compatibility between app versions and config versions.

#### Deep dive

Configuration often encodes integration contracts, such as queue names or base URLs. Those values should be tested like API contracts where they affect behavior.

#### Production angle

This prevents deployments where each service passes alone but fails when wired together.

#### Traps / caveats

- Static config validation does not prove dependency behavior.
- Contract tests need representative config.
- Avoid exposing secrets in CI output.

#### Optional Anki

Q: What can config contract tests catch?
A: Mismatched integration assumptions like endpoints, topics, schemas or auth settings.

</details>
