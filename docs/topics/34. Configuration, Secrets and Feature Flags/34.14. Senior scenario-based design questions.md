# Senior scenario-based design questions

<a id="conf-scen-001"></a>

<details>
<summary><strong>CONF-SCEN-001. How would you design a kill switch for a failing third-party integration?</strong></summary>

#### Short answer

Wrap outbound calls with a runtime flag that can disable or degrade the integration safely.

#### Interview answer

I would identify the smallest behavior to disable, such as sending notifications or calling a recommendation API. The flag should have a safe fallback, cached local evaluation, metrics, audit and a runbook. The code path should return degraded responses or queue work only if that is safe.

#### Deep dive

The kill switch should be tested and should not require the failing third-party to be available.

#### Production angle

During an incident, this lets the service protect itself and users without a code rollback.

#### Traps / caveats

- Do not hide failed critical writes silently.
- Make the kill-switch state visible.
- Define behavior for queued or in-flight work.

#### Optional Anki

Q: What should a third-party kill switch include?
A: Safe fallback, metrics, audit, cached evaluation and a runbook.

</details>

<a id="conf-scen-002"></a>

<details>
<summary><strong>CONF-SCEN-002. How would you design configuration validation so broken config cannot reach production?</strong></summary>

#### Short answer

Validate config at multiple layers: schema, application startup, CI, deployment and canary.

#### Interview answer

I would use typed `@ConfigurationProperties` with Bean Validation, CI checks for config files and Kubernetes manifests, secret reference validation, startup smoke tests and staged rollout. High-risk config should have policy checks and approval.

#### Deep dive

Validation should include semantic rules, such as timeout ranges, required credentials for enabled features and compatibility with application version.

#### Production angle

The goal is to fail before replacing healthy pods, not after traffic reaches broken instances.

#### Traps / caveats

- YAML syntax validation is not enough.
- Defaults can hide missing values.
- Do not validate by printing secrets.

#### Optional Anki

Q: Where should config validation happen?
A: In CI, deployment checks and application startup.

</details>

<a id="conf-scen-003"></a>

<details>
<summary><strong>CONF-SCEN-003. How would you design a migration from hardcoded configuration to externalized configuration?</strong></summary>

#### Short answer

Introduce typed config with defaults, externalize values gradually, validate, and remove hardcoded fallbacks after rollout.

#### Interview answer

I would inventory hardcoded values, classify which should remain constants and which should become config. Then create typed properties with safe defaults or required validation, update deployments to supply values, add tests and observability, and remove old hardcoded behavior after all environments migrate.

#### Deep dive

For risky keys, support both old and new paths temporarily and verify effective config in staging and production.

#### Production angle

Gradual migration avoids breaking environments that have not yet supplied the new values.

#### Traps / caveats

- Do not externalize domain invariants unnecessarily.
- Do not move secrets from code to plaintext Git config.
- Update runbooks and examples.

#### Optional Anki

Q: First step in externalizing hardcoded config?
A: Inventory and classify values by whether they should be constants, config or flags.

</details>

<a id="conf-scen-004"></a>

<details>
<summary><strong>CONF-SCEN-004. How would you decide whether a new behavior should be a profile, a property, or a feature flag?</strong></summary>

#### Short answer

Use profiles for environment shape, properties for deploy settings, and feature flags for controlled behavior exposure.

#### Interview answer

If the behavior depends on local/test/prod environment shape, a profile may fit. If it is a parameter like timeout, endpoint or limit, use configuration. If it controls rollout, mitigation, experiment or targeted exposure, use a feature flag.

#### Deep dive

I also consider ownership, lifecycle, risk, audit and whether the value must change without deployment.

#### Production angle

Choosing correctly avoids profile explosion, flag debt and accidental runtime business logic.

#### Traps / caveats

- Do not use profiles for tenant targeting.
- Do not use feature flags as permissions.
- Do not make everything runtime-editable.

#### Optional Anki

Q: What should control gradual rollout?
A: A feature flag, not a Spring profile.

</details>

<a id="conf-scen-005"></a>

<details>
<summary><strong>CONF-SCEN-005. How would you migrate from long-lived shared secrets to workload identity or short-lived credentials?</strong></summary>

#### Short answer

Introduce service identities, grant least privilege, update clients, monitor access, then revoke shared secrets.

#### Interview answer

I would map which services use the shared secret, create per-service identities or roles, grant minimal permissions, update deployments and libraries to use workload identity, verify access logs, then remove the old shared credential.

#### Deep dive

Migration should be staged because libraries may need token refresh support and local development needs a safe alternative.

#### Production angle

This reduces blast radius and makes audit meaningful.

#### Traps / caveats

- Do not leave the old shared key active forever.
- Ensure token refresh works under load.
- IAM misconfiguration can be as dangerous as leaked keys.

#### Optional Anki

Q: Why migrate to workload identity?
A: To avoid distributing long-lived shared static credentials.

</details>

<a id="conf-scen-006"></a>

<details>
<summary><strong>🧠 CONF-SCEN-006. How would you design configuration management for 50 Spring Boot microservices?</strong></summary>

#### Short answer

Use typed service-owned config, centralized secret/config delivery, validation, audit and observable effective versions.

#### Interview answer

I would standardize naming, typed `@ConfigurationProperties`, validation, secret delivery, config version reporting and rollout practices. Each service owns its config contract, while platform tooling provides secure distribution, CI checks, audit and templates.

#### Deep dive

Avoid one giant shared config file. Shared defaults are fine, but service-specific behavior should remain owned and versioned by the service.

#### Production angle

At scale, config management is both a developer-experience and incident-response problem.

#### Traps / caveats

- Centralization should not erase ownership.
- Shared config can create hidden coupling.
- Secrets and normal config need different controls.

#### Optional Anki

Q: Key principle for many-service config?
A: Central tooling with service-owned typed config contracts.

</details>

<a id="conf-scen-007"></a>

<details>
<summary><strong>🧠 CONF-SCEN-007. How would you design secret management for services running in Kubernetes?</strong></summary>

#### Short answer

Use least-privilege service identities, external secret stores or controlled Kubernetes Secrets, rotation and audit.

#### Interview answer

I would avoid plaintext secrets in Git and images. Services would get secrets through external secret operators, cloud secret managers, Vault or workload identity. Kubernetes RBAC would restrict access, and deployments would mount or inject only the secrets a service needs.

#### Deep dive

Rotation strategy, diagnostics redaction, local development and incident response must be designed upfront.

#### Production angle

Secret management must support day-two operations: rotation, leak response and audit.

#### Traps / caveats

- Kubernetes Secret base64 is not encryption.
- Broad service account permissions defeat the design.
- Mounted secrets still need reload or restart strategy.

#### Optional Anki

Q: What should not be in Kubernetes deployment repositories?
A: Plaintext production secrets.

</details>

<a id="conf-scen-008"></a>

<details>
<summary><strong>🧠 CONF-SCEN-008. How would you design a safe feature flag rollout system for backend APIs?</strong></summary>

#### Short answer

Use server-side evaluation, deterministic targeting, safe defaults, audit, metrics, gradual rollout and cleanup.

#### Interview answer

The system should support per-flag ownership, default values, deterministic targeting by user or tenant, percentage rollout, kill switches, audit logs and SDK caching. Backend code should call an application-owned abstraction rather than vendor SDKs everywhere.

#### Deep dive

For APIs, authorization must remain separate. For data-changing paths, decisions should be stable for the request or workflow.

#### Production angle

Metrics should show error rate, latency and business impact by flag variation without high-cardinality labels.

#### Traps / caveats

- Do not evaluate remotely on every request.
- Do not leave temporary flags forever.
- Do not use client-side flags for authorization.

#### Optional Anki

Q: What makes backend flag rollout safe?
A: Deterministic server-side evaluation, safe defaults, metrics, audit and cleanup.

</details>

<a id="conf-scen-009"></a>

<details>
<summary><strong>🧠 CONF-SCEN-009. How would you design secret rotation for database, Kafka, and HTTP client credentials?</strong></summary>

#### Short answer

Use per-service credentials, overlap periods, automated rollout, client refresh strategy and usage monitoring.

#### Interview answer

For databases, create new credentials, roll clients, then revoke old ones. For Kafka, coordinate SASL credentials or certificates with producers and consumers. For HTTP clients, rotate API keys or OAuth client secrets with provider overlap. Each client type needs a plan for cached credentials and long-lived connections.

#### Deep dive

Automation should track which services still use old credentials before revocation.

#### Production angle

Rotation must be tested before emergency incidents.

#### Traps / caveats

- Connection pools may keep old sessions.
- Kafka clients may need restart.
- Shared credentials make partial rotation difficult.

#### Optional Anki

Q: Common zero-downtime rotation requirement?
A: A temporary overlap where old and new credentials both work.

</details>

<a id="conf-scen-010"></a>

<details>
<summary><strong>🧠 CONF-SCEN-010. How would you design feature flags so they do not become permanent technical debt?</strong></summary>

#### Short answer

Require ownership, purpose, type, expiry, cleanup workflow and tests for each flag.

#### Interview answer

Every flag should have metadata: owner, creation date, flag type, expected removal date and final state. Release flags should have cleanup tickets tied to rollout completion. Dashboards should show stale flags and code references.

#### Deep dive

Long-lived ops or permission flags are acceptable, but they need documentation and monitoring.

#### Production angle

Flag debt makes incidents harder because nobody knows which switches are safe to change.

#### Traps / caveats

- Cleanup should remove both flag rules and dead code.
- Do not delete a flag before all environments converge.
- Stale flags can hide untested code paths.

#### Optional Anki

Q: What metadata prevents flag debt?
A: Owner, purpose, type, expiry and cleanup plan.

</details>

<a id="conf-scen-011"></a>

<details>
<summary><strong>🧠 CONF-SCEN-011. How would you design a feature-flag abstraction in a Spring Boot codebase so it remains testable and provider-independent?</strong></summary>

#### Short answer

Define domain-specific decision interfaces and isolate provider SDKs in adapter beans.

#### Interview answer

Business code should depend on interfaces like `CheckoutFeatureDecisions`, not raw flag names or SDK clients. The adapter builds evaluation context, calls the provider or OpenFeature client, applies fallback values and records metrics.

#### Deep dive

Tests can replace the interface with a fake. Provider integration can be tested separately.

#### Production angle

This centralizes fallback policy, observability and future provider migration.

#### Traps / caveats

- Avoid a generic `isEnabled(String flagName)` scattered everywhere.
- Keep flag names and defaults centralized.
- Do not let flag evaluation leak PII unnecessarily.

#### Optional Anki

Q: Best dependency for business code needing flags?
A: An application-owned feature decision interface.

</details>

<a id="conf-scen-012"></a>

<details>
<summary><strong>🧠 CONF-SCEN-012. How would you design compatibility checks between application versions, configuration versions, and feature-flag states during rolling deployments?</strong></summary>

#### Short answer

Ensure old and new app versions can run with the config and flag states present during the rollout.

#### Interview answer

I would treat config and flag changes like API changes. Add support before requiring new keys, keep old and new behavior compatible during rollout, validate config against both versions, and only remove old keys or branches after all instances and environments have migrated.

#### Deep dive

For flags controlling schemas or side effects, use versioned decisions and staged rollout. For config keys, use expand-and-contract migration.

#### Production angle

Rolling deployments fail when new pods require config that old deployment templates do not supply, or old pods cannot tolerate new flag states.

#### Traps / caveats

- Do not change config and code incompatibly in one step.
- Check background workers and consumers.
- Rollback must be compatible with current data and flags.

#### Optional Anki

Q: What is config compatibility during rolling deploys?
A: Both old and new app versions can run safely with rollout-time config and flag states.

</details>
