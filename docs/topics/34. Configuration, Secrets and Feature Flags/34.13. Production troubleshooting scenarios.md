# Production troubleshooting scenarios

---

<a id="conf-prod-001"></a>

<details>
<summary><strong>CONF-PROD-001. A service works locally but uses wrong configuration in production. What do you check?</strong></summary>

#### Short answer

Check active profiles, property sources, environment variables, deployment manifests, config imports and effective config diagnostics.

#### Interview answer

I would compare local and production active profiles, image version, environment variables, command-line args, ConfigMaps, Secrets, mounted files and external config provider values. Then I would inspect effective non-sensitive config through secure diagnostics or startup logs.

#### Deep dive

The key is to compare effective runtime config, not just source files.

#### Production angle

Most wrong-config incidents come from precedence, typos, stale pods or unexpected overrides.

#### Traps / caveats

- Do not expose secrets while debugging.
- `application.yml` may not be the winning source.
- Check whether pods restarted after config changes.

#### Optional Anki

Q: What matters when debugging config?
A: The effective runtime value and its source.

</details>

<a id="conf-prod-002"></a>

<details>
<summary><strong>CONF-PROD-002. A bad feature flag value causes errors. How do you recover safely?</strong></summary>

#### Short answer

Stop exposure, roll back the flag, verify propagation and check for side effects.

#### Interview answer

First disable or roll back the bad flag value, ideally to the previous known good version. Then verify all affected replicas or services received the change. Watch error rate, latency and business metrics. If the flag caused writes or external calls, check whether data repair or compensation is needed.

#### Deep dive

If the flag provider is unreliable, use local fallback, kill switch or deployment rollback depending on design.

#### Production angle

A flag rollback can be faster than code rollback, but only if the code checks the flag correctly.

#### Traps / caveats

- Turning off a flag does not undo completed side effects.
- Some services may cache old flag values.
- Preserve audit trail for the bad change.

#### Optional Anki

Q: First action for a bad flag rollout?
A: Stop or roll back exposure and verify propagation.

</details>

<a id="conf-prod-003"></a>

<details>
<summary><strong>CONF-PROD-003. A required property is missing and the service fails to start. What do you check?</strong></summary>

#### Short answer

Check property name, source, profile, precedence, secret reference, mount path and recent deployment changes.

#### Interview answer

I would inspect startup logs for the missing key, then verify the deployment manifest, ConfigMap or Secret contains the expected name. I would check active profiles, environment-variable mapping, config imports, mounted files and whether the secret exists in the namespace.

#### Deep dive

If a key was renamed, verify old and new app versions are compatible during rolling deployment.

#### Production angle

Failing startup is often safer than starting with wrong defaults, but rollout should stop before replacing healthy pods.

#### Traps / caveats

- Environment variable names may be misspelled.
- Secrets may exist in one namespace but not another.
- Optional imports can hide missing critical config.

#### Optional Anki

Q: Missing property during startup: what do you inspect?
A: Key name, source, profile, precedence, mounts and secret references.

</details>

<a id="conf-prod-004"></a>

<details>
<summary><strong>CONF-PROD-004. A service suddenly cannot connect to the database after secret rotation. What do you check?</strong></summary>

#### Short answer

Check whether the new credential is valid, deployed, picked up by pods and compatible with connection pools.

#### Interview answer

I would verify the DB user/password, permissions, secret version, deployment rollout, pod environment or mounted file, and application logs. Then I would check whether existing pools still use old connections and whether old credentials were revoked too early.

#### Deep dive

Rotation should include overlap and monitoring of old versus new credential usage.

#### Production angle

Database credential rotation can break both startup and existing traffic if pools reconnect under load with bad values.

#### Traps / caveats

- Updating the secret object may not update running env vars.
- New pods may fail while old pods still work.
- Permissions may differ from password validity.

#### Optional Anki

Q: Why can DB secret rotation break only new pods?
A: Existing pods may still use old env vars or old pooled connections.

</details>

<a id="conf-prod-005"></a>

<details>
<summary><strong>CONF-PROD-005. A feature flag rollout causes high latency. How do you investigate?</strong></summary>

#### Short answer

Compare latency by flag state, inspect new code paths, provider latency and downstream dependency impact.

#### Interview answer

I would segment metrics by flag variation, rollout cohort, endpoint and dependency. Then I would check whether the enabled path calls slower services, increases database queries, causes cache misses or waits on the flag provider.

#### Deep dive

If the provider is evaluated remotely per request, provider latency itself may be the cause.

#### Production angle

Gradual rollout lets you stop exposure before all users are affected.

#### Traps / caveats

- Avoid high-cardinality user labels in metrics.
- The flag may correlate with a cohort that already has different behavior.
- Rollback may not clear caches or queues immediately.

#### Optional Anki

Q: How to debug flag-caused latency?
A: Compare metrics by flag variation and inspect new dependencies or provider calls.

</details>

<a id="conf-prod-006"></a>

<details>
<summary><strong>CONF-PROD-006. A configuration change causes a retry storm. How do you recover?</strong></summary>

#### Short answer

Roll back the bad config, reduce load, protect dependencies and verify clients stop retrying.

#### Interview answer

First revert retry, timeout or concurrency values to known good settings. If dependencies are overloaded, apply rate limits, disable non-critical traffic, open circuit breakers or scale carefully. Then monitor request rate, retry count, saturation and error rates.

#### Deep dive

After recovery, review why validation allowed the value and whether rollout lacked guardrails.

#### Production angle

Retry storms can continue even after the original dependency starts recovering.

#### Traps / caveats

- Increasing timeout may reduce retries but increase resource holding.
- Scaling callers can make downstream overload worse.
- Verify all replicas picked up rollback.

#### Optional Anki

Q: First step for config-caused retry storm?
A: Revert the bad retry/timeout/concurrency config.

</details>

<a id="conf-prod-007"></a>

<details>
<summary><strong>🧠 CONF-PROD-007. An environment variable typo silently changes application behavior. How do you prevent this?</strong></summary>

#### Short answer

Use typed validated config, CI manifest checks, metadata, and effective config diagnostics.

#### Interview answer

A typo may mean the intended property is ignored and a default stays active. Prevention includes `@ConfigurationProperties` validation, tests with deployment-like config, schema or policy checks for manifests, and alerts for unexpected default usage.

#### Deep dive

For critical values, fail startup if the configured source is missing rather than relying on implicit defaults.

#### Production angle

This class of issue is common in Kubernetes because environment variable names are manually written and transformed.

#### Traps / caveats

- Relaxed binding helps but does not catch every typo.
- Unknown map keys may be valid by design.
- Do not expose secret values in diagnostics.

#### Optional Anki

Q: How to catch env var typos?
A: Typed validation, CI checks and effective config verification.

</details>

<a id="conf-prod-008"></a>

<details>
<summary><strong>CONF-PROD-008. A feature flag provider, configuration provider, or secret manager is unavailable. How should the application behave?</strong></summary>

#### Short answer

Use predefined behavior: cached values, safe defaults, degraded mode or fail fast depending on criticality.

#### Interview answer

For request-time flags, the app should usually use cached rules and safe fallbacks. For startup secrets, a missing provider may require fail-fast if core dependencies cannot be configured. Optional integrations can degrade if that behavior is explicit and observable.

#### Deep dive

Provider unavailability should trigger alerts and metrics, not silently disappear.

#### Production angle

External config systems should not accidentally become a single point of total application failure.

#### Traps / caveats

- Cached values may be stale.
- Security-sensitive flags should usually fail closed.
- Different providers may fail in different ways: timeout, auth error, stale data.

#### Optional Anki

Q: What determines provider outage behavior?
A: Whether the missing config is critical and what the safe fallback is.

</details>

<a id="conf-prod-009"></a>

<details>
<summary><strong>CONF-PROD-009. Secrets are accidentally printed to logs. What immediate actions do you take?</strong></summary>

#### Short answer

Stop the leak, rotate or revoke exposed secrets, restrict log access and assess exposure.

#### Interview answer

First disable or patch the logging source. Identify exactly what leaked, where logs were shipped, who had access and retention scope. Rotate or revoke affected credentials, restrict access to existing logs where possible, and add redaction and tests.

#### Deep dive

Centralized logs, backups and exports may contain the secret even after the app stops logging it.

#### Production angle

Logs often have broader access than production systems, so leaked secrets must be treated seriously.

#### Traps / caveats

- Do not only redact future logs.
- Check traces and error reports too.
- Preserve incident timeline.

#### Optional Anki

Q: If a secret is printed to logs, what must usually happen?
A: Rotate or revoke it and fix the logging source.

</details>

<a id="conf-prod-010"></a>

<details>
<summary><strong>🧠 CONF-PROD-010. A ConfigMap update does not appear in a running Pod. What do you check?</strong></summary>

#### Short answer

Check whether it was consumed as env vars or files, mount type, update delay and whether the app rereads the value.

#### Interview answer

If the value was injected as an environment variable, it will not change until the pod restarts. If it was mounted as a file, check the mount, `subPath` usage, kubelet update timing and whether the application reloads the file or still holds old config.

#### Deep dive

Many teams intentionally restart pods on config changes to avoid ambiguous live refresh behavior.

#### Production angle

The Kubernetes object may be updated correctly while the Java process still uses old values.

#### Traps / caveats

- `kubectl describe` shows object state, not necessarily app state.
- File update does not recreate Spring beans.
- Multiple replicas may update at different times.

#### Optional Anki

Q: Why does a ConfigMap env var not update in a running pod?
A: Process environment is fixed at startup.

</details>

<a id="conf-prod-011"></a>

<details>
<summary><strong>🧠 CONF-PROD-011. Different replicas appear to use different feature flag values. What do you check?</strong></summary>

#### Short answer

Check SDK sync status, cache age, targeting context, app versions, fallback behavior and provider rules.

#### Interview answer

Replicas may have different cached flag data, provider connection status, application versions or evaluation context. I would compare config and flag versions per replica, provider errors, fallback metrics and whether the same user or tenant key is used consistently.

#### Deep dive

If rollout rules changed recently, propagation delay may explain temporary differences.

#### Production angle

Replica disagreement can cause inconsistent user experience and data compatibility problems.

#### Traps / caveats

- Different context attributes can produce different valid decisions.
- Provider outage may trigger fallbacks only on some replicas.
- Clock or SDK version differences can matter.

#### Optional Anki

Q: What helps diagnose flag drift across replicas?
A: Flag/config version, SDK sync status and evaluation context.

</details>

<a id="conf-prod-012"></a>

<details>
<summary><strong>🧠 CONF-PROD-012. A runtime configuration change is visible in diagnostics, but behavior does not change. What do you check?</strong></summary>

#### Short answer

Check whether the relevant code reads config dynamically or cached it at startup.

#### Interview answer

The diagnostics may show a new property value, but a bean may have already copied the old value into a field, client, pool or scheduler. I would check binding lifecycle, refresh scope, cached snapshots and whether a restart or bean recreation is required.

#### Deep dive

Some runtime config only changes the environment, not already-created objects. Stateful clients often need explicit rebuild or restart.

#### Production angle

This explains incidents where operators "changed the config" but the application kept old behavior.

#### Traps / caveats

- Actuator `env` does not prove all beans updated.
- Background jobs may hold old references.
- Restart may be safer than live refresh.

#### Optional Anki

Q: Why can diagnostics show new config while behavior stays old?
A: Beans or clients may have cached the old value at startup.

</details>
