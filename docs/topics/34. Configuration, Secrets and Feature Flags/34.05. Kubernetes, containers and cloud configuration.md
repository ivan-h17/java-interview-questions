<details>
<summary><strong>CONF-K8S-001. What is the difference between a Kubernetes ConfigMap and a Secret?</strong></summary>

#### Short answer

A ConfigMap stores non-sensitive configuration; a Secret is intended for sensitive data, though it still needs proper access controls.

#### Interview answer

ConfigMaps commonly hold non-sensitive values like URLs, feature defaults or config files. Secrets hold credentials, tokens, certificates and keys. Kubernetes Secrets are base64-encoded by default, not automatically safe from everyone; security depends on RBAC, encryption at rest, namespace boundaries and how they are mounted.

#### Deep dive

Both can be consumed as environment variables or mounted files. The main difference is intended sensitivity and platform handling.

#### Production angle

Treat Secrets as sensitive operational assets. Limit who can read them and avoid putting them into logs, images or broad deployment manifests.

#### Traps / caveats

- Base64 is not encryption.
- Anyone with read access to a Secret can usually recover its value.
- ConfigMaps can still contain sensitive data by mistake.

#### Optional Anki

Q: ConfigMap vs Secret?
A: ConfigMaps are for non-sensitive config; Secrets are for sensitive values with stricter handling.

</details>

<details>
<summary><strong>CONF-K8S-002. What are the trade-offs between environment variables and mounted configuration files?</strong></summary>

#### Short answer

Environment variables are simple and common; mounted files handle larger or structured config and can support file-based secret loading.

#### Interview answer

Environment variables work well for small scalar values and Spring Boot relaxed binding. Mounted files are better for certificates, keys, config trees or larger structured files. Files can also be read by libraries that expect paths instead of inline values.

#### Deep dive

Environment variables are captured at process start. Mounted ConfigMap or Secret volumes may update eventually, but the application must reread files and know how to apply changes.

#### Production angle

For Java services, environment variables are convenient for standard properties, while mounted files are usually better for TLS material and secret directories.

#### Traps / caveats

- Environment variables may appear in diagnostics or process metadata.
- File permissions and mount paths matter.
- Updates do not automatically reconfigure already-created beans.

#### Optional Anki

Q: When are mounted secrets better than env vars?
A: For certificates, keys, config trees and libraries that need file paths.

</details>

<details>
<summary><strong>CONF-K8S-003. What happens when a ConfigMap or Secret changes after a Pod has already started?</strong></summary>

#### Short answer

Environment-variable values do not change; mounted volume data may update eventually, but the app may not automatically use it.

#### Interview answer

If a ConfigMap or Secret is consumed as environment variables, the running process keeps the old values until restart. If consumed as mounted files, Kubernetes can update the files eventually, but the application must reread and apply them safely.

#### Deep dive

Many teams restart pods after config changes because startup-time configuration is simpler and avoids inconsistent live state.

#### Production angle

A ConfigMap change may appear correct in Kubernetes but not affect existing pods, causing confusion during incidents.

#### Traps / caveats

- Mounted file updates are not instant.
- `subPath` mounts have special update limitations.
- Spring beans may not refresh just because a file changed.

#### Optional Anki

Q: Do env vars in a running Pod update when a Secret changes?
A: No, the process keeps the old environment until restart.

</details>

<a id="conf-k8s-004"></a>

<details>
<summary><strong>CONF-K8S-004. How can a wrong ConfigMap or Secret break a Kubernetes rollout or cause CrashLoopBackOff?</strong></summary>

#### Short answer

Bad config can make the container fail startup, fail readiness, or connect to the wrong dependency.

#### Interview answer

Examples include missing required keys, invalid YAML, wrong environment variable names, bad database credentials, invalid URLs or a profile that enables missing beans. The app may crash immediately, fail health checks, or run but fail traffic.

#### Deep dive

CrashLoopBackOff is often a symptom, not the cause. You need to inspect pod events, container logs, environment variables, mounts, active profiles and recent config changes.

#### Production angle

A safe rollout should validate manifests and application config before pods replace healthy instances.

#### Traps / caveats

- A typo can leave a default value active instead of failing.
- Health checks can be green while an optional integration is broken.
- Secrets rotation can break only new pods if old pods keep old values.

#### Optional Anki

Q: What config issues commonly cause CrashLoopBackOff?
A: Missing keys, bad credentials, invalid values, wrong profiles or failed startup validation.

</details>

<details>
<summary><strong>CONF-K8S-005. What are the risks of storing secrets in Helm values files, Kubernetes manifests, or deployment repositories?</strong></summary>

#### Short answer

Secrets in deployment files are easy to commit, copy, review too broadly and leak through history or tooling.

#### Interview answer

Helm values and manifests often live in Git and CI systems. If they contain plaintext secrets, the secrets can spread into Git history, pull requests, logs, artifact stores and developer machines. Even encrypted secrets require careful control over who can decrypt and apply them.

#### Deep dive

Safer patterns include external secret operators, cloud secret managers, sealed secrets with controlled keys, SOPS with strict key access, or workload identity.

#### Production angle

Secret delivery should support rotation, audit and least privilege, not just "make the pod start."

#### Traps / caveats

- Removing a secret from the latest commit does not remove it from history.
- Encrypted Git secrets are only as safe as key access.
- Avoid printing rendered manifests with secrets in CI logs.

#### Optional Anki

Q: Why are plaintext secrets in Helm values dangerous?
A: They can leak through Git history, CI logs, reviews and artifacts.

</details>

<details>
<summary><strong>🧠 CONF-K8S-006. How would you pass a directory of secrets to a Spring Boot application?</strong></summary>

#### Short answer

Mount the secret as files and import it as a config tree or read the files through explicit paths.

#### Interview answer

In Kubernetes, a Secret can be mounted as a volume where each key becomes a file. Spring Boot can consume such directories through config tree imports, or the application can configure file paths for libraries that need certificates or keys.

#### Deep dive

Config trees are useful because file names become property names. For example, a file containing a password can be bound into a typed configuration property without putting the value in an environment variable.

#### Production angle

Mounted secret directories work well for TLS certificates and secret managers that sync values into files.

#### Traps / caveats

- Protect file permissions and mount paths.
- Do not log file contents.
- Rotation still needs reload or pod restart strategy.

#### Optional Anki

Q: What Spring Boot feature can read a directory of mounted secret files?
A: Config tree imports.

</details>

<details>
<summary><strong>🧠 CONF-K8S-007. How do cloud parameter stores and secret managers fit into application configuration?</strong></summary>

#### Short answer

They provide managed storage, access control, audit and rotation for configuration values or secrets.

#### Interview answer

A service can receive values from AWS Secrets Manager, AWS Parameter Store, Google Secret Manager, Azure Key Vault, Vault or similar systems through platform injection, sidecars, operators or Spring integration. Non-sensitive parameters and sensitive secrets may use different stores or policies.

#### Deep dive

The app should not call a secret manager on every request. Usually values are loaded at startup, cached, mounted, or refreshed through controlled mechanisms.

#### Production angle

Managed secret stores help enforce least privilege and auditing across many services.

#### Traps / caveats

- Provider outages can affect startup or refresh.
- IAM mistakes can expose secrets broadly.
- Cached values complicate rotation.

#### Optional Anki

Q: Why use a cloud secret manager?
A: For managed access control, audit, storage and rotation of secrets.

</details>

<a id="conf-k8s-008"></a>

<details>
<summary><strong>🧠 CONF-K8S-008. How do workload identity and short-lived cloud credentials reduce secret-management risk?</strong></summary>

#### Short answer

They let workloads obtain temporary credentials based on identity instead of storing long-lived secrets.

#### Interview answer

With workload identity, a pod or service account can exchange its runtime identity for short-lived credentials to access cloud resources. This reduces the need to distribute static access keys in Kubernetes Secrets or config files.

#### Deep dive

The security boundary moves to IAM, service account binding, token lifetime and trust policy. It still needs least privilege and audit.

#### Production angle

If a temporary credential leaks, its lifetime and scope are limited compared with a long-lived shared key.

#### Traps / caveats

- Misconfigured IAM can still grant too much access.
- Local development needs a separate safe path.
- Some libraries cache credentials and need refresh support.

#### Optional Anki

Q: Main benefit of workload identity?
A: Avoid distributing long-lived static credentials to workloads.

</details>

<details>
<summary><strong>🧠 CONF-K8S-009. How do you validate Kubernetes configuration before deployment?</strong></summary>

#### Short answer

Validate manifests, schemas, policy, secret references and application startup behavior before production rollout.

#### Interview answer

I would run YAML/schema validation, Helm template checks, policy checks, secret existence checks, resource validation and deployment dry-run where appropriate. Then I would run application startup tests or smoke tests with production-like config.

#### Deep dive

For Spring Boot, validation should include required properties, active profiles, mounted paths and connectivity assumptions. For high-risk changes, canary rollout and fast rollback are important.

#### Production angle

Many config incidents are preventable if broken manifests and missing keys fail CI instead of failing pods.

#### Traps / caveats

- Syntax validation does not prove semantic correctness.
- Do not expose secrets in rendered manifest logs.
- Validate both config and the app's interpretation of it.

#### Optional Anki

Q: What should Kubernetes config validation catch?
A: Invalid manifests, missing references, policy violations and app-level config failures.

</details>
