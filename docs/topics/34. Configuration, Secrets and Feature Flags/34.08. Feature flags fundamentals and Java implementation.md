# Feature flags fundamentals and Java implementation

---

<a id="conf-flag-001"></a>

<details>
<summary><strong>CONF-FLAG-001. What are feature flags?</strong></summary>

#### Short answer

Feature flags are runtime controls that enable, disable or vary behavior without deploying new code.

#### Interview answer

A feature flag lets a service choose between code paths based on configuration, user, tenant, percentage rollout or operational state. They are used for gradual releases, experiments, kill switches and operational controls.

#### Deep dive

Good flags have names, owners, defaults, cleanup dates and tests for both states. They should not become permanent hidden business logic.

#### Production angle

Flags reduce release risk by decoupling deploy from exposure.

#### Traps / caveats

- Flags add code paths and testing burden.
- Stale flags create technical debt.
- Client-side flags are not security controls.

#### Optional Anki

Q: What do feature flags decouple?
A: Code deployment from feature exposure.

</details>

<a id="conf-flag-002"></a>

<details>
<summary><strong>CONF-FLAG-002. What is a kill switch?</strong></summary>

#### Short answer

A kill switch is a flag or control that quickly disables risky behavior during an incident.

#### Interview answer

Kill switches are usually operational flags for integrations, expensive jobs, new algorithms or high-risk features. They should be easy to activate, safe by default and observable, so operators can confirm that the failing behavior actually stopped.

#### Deep dive

A kill switch should wrap the smallest useful behavior. If it is too broad, it may take down important functionality. If it is too narrow, it may not stop the incident.

#### Production angle

Kill switches can reduce recovery time without a rollback or emergency deployment.

#### Traps / caveats

- The failing code must actually check the kill switch.
- Defaults and provider failure behavior matter.
- Test kill switches before incidents.

#### Optional Anki

Q: What is a kill switch for?
A: Quickly disabling risky behavior during an incident.

</details>

<a id="conf-flag-003"></a>

<details>
<summary><strong>CONF-FLAG-003. What is the difference between a feature flag and configuration?</strong></summary>

#### Short answer

Configuration sets service parameters; feature flags control behavior exposure or rollout.

#### Interview answer

A timeout, endpoint or pool size is configuration. A switch that enables a new checkout flow for 10 percent of users is a feature flag. The difference is not technical storage, but intent: operational parameter versus controlled behavior variation.

#### Deep dive

Some flags behave like configuration, especially ops flags. The important part is lifecycle: flags need owners, targeting, observability and cleanup.

#### Production angle

Misclassifying flags as normal config often leaves old branches in code forever.

#### Traps / caveats

- Feature flags are not authorization.
- Configuration should not become an unreviewed business rules engine.
- Some values need both config validation and flag governance.

#### Optional Anki

Q: Feature flag vs config?
A: Config sets parameters; flags control behavior exposure or rollout.

</details>

<a id="conf-flag-004"></a>

<details>
<summary><strong>CONF-FLAG-004. When should you use a feature flag, and when should you avoid one?</strong></summary>

#### Short answer

Use flags for controlled rollout, mitigation or experiments; avoid them for permanent complexity or security decisions.

#### Interview answer

Feature flags are useful for risky releases, canaries, A/B tests, kill switches and gradual tenant enablement. Avoid flags when a normal deployment is enough, when the behavior must be permanent immediately, or when the flag would hide a long-lived fork in business logic.

#### Deep dive

Every flag adds at least two states to test. Long-lived flags should be treated as design decisions, not temporary switches.

#### Production angle

Good flags reduce release risk; bad flags create unknown production states.

#### Traps / caveats

- Do not use flags as permissions.
- Do not leave release flags after rollout completes.
- Avoid flags around irreversible side effects without careful design.

#### Optional Anki

Q: When is a flag useful?
A: Gradual rollout, mitigation, experiments or controlled exposure.

</details>

<a id="conf-flag-005"></a>

<details>
<summary><strong>🧠 CONF-FLAG-005. How does percentage rollout work, and why should targeting be deterministic?</strong></summary>

#### Short answer

Percentage rollout assigns a stable subset of users or entities to a flag state.

#### Interview answer

A flag system usually hashes a stable key, such as user ID or tenant ID, into buckets. If the rollout is 10 percent, users in the first 10 percent of buckets get the feature. Deterministic targeting keeps the same user in the same experience across requests.

#### Deep dive

The choice of targeting key matters. User-based rollout and tenant-based rollout have different consistency and blast-radius properties.

#### Production angle

Non-deterministic rollout can produce confusing behavior, duplicate side effects or inconsistent UI/API flows.

#### Traps / caveats

- Do not use random per-request targeting for stateful behavior.
- Changing the hash key reshuffles cohorts.
- Percentage rollout is not equal to canarying infrastructure.

#### Optional Anki

Q: Why deterministic feature rollout?
A: So the same target sees stable behavior across requests.

</details>

<a id="conf-flag-006"></a>

<details>
<summary><strong>CONF-FLAG-006. What is a feature flag default value, and how do you decide whether a flag should fail open or fail closed?</strong></summary>

#### Short answer

The default is used when no rule or provider value is available; fail-open or fail-closed depends on safety.

#### Interview answer

A flag needs a safe fallback. For risky new features, default disabled is usually safer. For emergency kill switches, the safe default may depend on whether disabling behavior protects the system. For security-sensitive behavior, fail closed is usually required.

#### Deep dive

The fallback should be explicit in code and tests. A provider outage should not accidentally enable unreviewed behavior.

#### Production angle

During a flag provider outage, fallback decisions become real production behavior.

#### Traps / caveats

- Do not rely on vendor SDK defaults without reviewing them.
- Different flags may need different fallback policies.
- Fail-open may be acceptable for availability but bad for security.

#### Optional Anki

Q: What is a feature flag fallback?
A: The value used when evaluation cannot get a configured value.

</details>

<a id="conf-flag-007"></a>

<details>
<summary><strong>CONF-FLAG-007. What is flag debt, and why should temporary flags have an owner and expiration date?</strong></summary>

#### Short answer

Flag debt is the complexity left by stale flags and old code paths.

#### Interview answer

Temporary release flags should be removed after rollout finishes. If they stay, the code has extra branches, tests, metrics and mental overhead. Owners and expiration dates make cleanup part of the rollout plan.

#### Deep dive

Some flags are long-lived, like ops kill switches or permission flags. They still need ownership and documentation.

#### Production angle

Stale flags can hide behavior nobody understands and can be accidentally toggled during incidents.

#### Traps / caveats

- Removing a flag requires knowing the final intended state.
- Do not delete observability before verifying cleanup.
- Flag debt grows quietly.

#### Optional Anki

Q: What is flag debt?
A: Maintenance and risk from stale flags and old code branches.

</details>

<a id="conf-flag-008"></a>

<details>
<summary><strong>CONF-FLAG-008. Why are feature flags not a substitute for server-side authorization?</strong></summary>

#### Short answer

Flags control exposure, but authorization controls whether an action is allowed.

#### Interview answer

A user can sometimes manipulate clients, requests or flag context. Even server-side flags should not replace permission checks. If an endpoint changes data, the server must verify authentication, authorization, tenant ownership and business rules regardless of flag state.

#### Deep dive

Client-side flags are especially unsafe for permissions because users can inspect or change frontend behavior.

#### Production angle

Using flags as authorization can create broken access control vulnerabilities.

#### Traps / caveats

- Hiding a UI button is not access control.
- A flag may enable a route, but authorization still runs inside it.
- Permission flags need policy-level design, not casual feature toggles.

#### Optional Anki

Q: Are feature flags authorization?
A: No, server-side authorization must still enforce access.

</details>

<a id="conf-flag-009"></a>

<details>
<summary><strong>CONF-FLAG-009. How should feature flag checks be structured in Java or Spring code so vendor SDK calls are not scattered through business logic?</strong></summary>

#### Short answer

Wrap flag evaluation behind an application-owned interface or policy service.

#### Interview answer

Instead of calling a vendor SDK from every service method, define an interface such as `FeatureDecisions` or `CheckoutFeatures`. Business code asks domain-specific questions like `isNewPricingEnabled(customerId)`. The implementation can use LaunchDarkly, Unleash, OpenFeature or local config behind the scenes.

#### Deep dive

This keeps tests simple and prevents vendor lock-in from spreading through the codebase. It also centralizes fallback values and evaluation context.

#### Production angle

During a provider outage or migration, one abstraction is easier to control than many direct SDK calls.

#### Traps / caveats

- Do not create a generic stringly typed flag helper everywhere.
- Keep flag names centralized.
- Test both enabled and disabled behavior.

#### Optional Anki

Q: Why wrap feature flag SDK calls?
A: To keep business code testable and provider-independent.

</details>

<a id="conf-flag-010"></a>

<details>
<summary><strong>CONF-FLAG-010. How do you avoid feature flag provider latency on the request path?</strong></summary>

#### Short answer

Use local SDK caching, preloaded rules, timeouts and safe fallbacks instead of remote calls per request.

#### Interview answer

Most backend flag SDKs are designed to evaluate locally after synchronizing rules in the background. I would avoid making an HTTP call to the flag provider for every request. The service should have a short timeout, cached last-known values and explicit fallback behavior.

#### Deep dive

For critical decisions, evaluate once per request or workflow and pass the decision along instead of reevaluating unpredictably.

#### Production angle

Flag provider latency should not become user-facing API latency or an outage amplifier.

#### Traps / caveats

- Do not ignore stale-cache behavior.
- Do not put high-cardinality contexts into metrics.
- Fallback values must be tested.

#### Optional Anki

Q: Should a backend call a flag provider remotely on every request?
A: No, prefer local cached evaluation with safe fallbacks.

</details>

<a id="conf-flag-011"></a>

<details>
<summary><strong>🧠 CONF-FLAG-011. What are release flags, ops flags, experiment flags, and permission flags?</strong></summary>

#### Short answer

They are flag categories with different lifecycles and risks.

#### Interview answer

Release flags hide incomplete or risky features during rollout and should be temporary. Ops flags control operational behavior, like kill switches or throttles. Experiment flags support A/B testing. Permission flags control product entitlements or access-like behavior and need careful design.

#### Deep dive

The flag type determines ownership, cleanup, monitoring and fallback. A release flag without cleanup becomes debt; an ops flag may be intentionally long-lived.

#### Production angle

Classifying flags prevents treating all toggles as the same risk.

#### Traps / caveats

- Permission flags still need authorization checks.
- Experiment flags may involve privacy concerns.
- Ops flags need runbooks.

#### Optional Anki

Q: Which flag type should usually be temporary?
A: Release flags.

</details>

<a id="conf-flag-012"></a>

<details>
<summary><strong>🧠 CONF-FLAG-012. What is feature flag targeting and evaluation context?</strong></summary>

#### Short answer

Targeting chooses who gets a flag value using context such as user, tenant, region or request attributes.

#### Interview answer

Evaluation context is the data passed to the flag system: identifiers, groups, tenant, country, app version or plan. Targeting rules use that context to decide the flag value. The context should include only necessary, privacy-safe attributes.

#### Deep dive

Good targeting keys are stable and low-cardinality when possible. Avoid sending raw PII unless there is a clear need and policy approval.

#### Production angle

Bad context can cause inconsistent rollout, privacy exposure or high-cardinality metrics.

#### Traps / caveats

- Do not target on mutable values if consistency matters.
- Do not leak sensitive attributes to third-party flag providers unnecessarily.
- Tenant and user targeting have different blast radius.

#### Optional Anki

Q: What is flag evaluation context?
A: The attributes used to evaluate targeting rules.

</details>

<a id="conf-flag-013"></a>

<details>
<summary><strong>🧠 CONF-FLAG-013. What is OpenFeature, and what problem does it try to solve?</strong></summary>

#### Short answer

OpenFeature is a vendor-neutral API for feature flag evaluation.

#### Interview answer

OpenFeature defines common concepts such as clients, providers, evaluation context and hooks. The goal is to let application code depend on a standard API while the provider implementation can be changed.

#### Deep dive

It does not remove the need to design flag ownership, defaults, testing or rollout strategy. It mainly addresses SDK portability and consistent instrumentation points.

#### Production angle

It can reduce vendor lock-in and make flag evaluation easier to standardize across services.

#### Traps / caveats

- Provider behavior can still differ.
- A standard API does not make bad flags safe.
- Domain-specific wrappers may still be useful.

#### Optional Anki

Q: What problem does OpenFeature address?
A: Vendor-neutral feature flag evaluation APIs.

</details>

<a id="conf-flag-014"></a>

<details>
<summary><strong>🧠 CONF-FLAG-014. How should feature flags be used around data migrations or irreversible side effects?</strong></summary>

#### Short answer

Use flags carefully with backward-compatible changes and avoid toggling irreversible actions casually.

#### Interview answer

For database migrations, flags can help move reads or writes gradually, but the schema and code must support both old and new states during rollout. For irreversible effects like charging money or sending emails, the flag decision should be stable and idempotency must be designed.

#### Deep dive

Common patterns include expand-and-contract migrations, dual writes with verification, read switching and staged cleanup.

#### Production angle

A rollback flag cannot undo already-written data or external side effects.

#### Traps / caveats

- Do not toggle midway through a transaction.
- Make decisions stable per entity or workflow.
- Plan rollback before enabling the flag.

#### Optional Anki

Q: Why are flags risky around irreversible effects?
A: Turning the flag off does not undo completed side effects.

</details>

<a id="conf-flag-015"></a>

<details>
<summary><strong>🧠 CONF-FLAG-015. How do you keep a flag decision stable during one request, transaction, or workflow?</strong></summary>

#### Short answer

Evaluate once at the boundary and pass the decision or store it in workflow state.

#### Interview answer

If code reevaluates a flag multiple times, a provider update can change behavior halfway through a request or workflow. I would evaluate once at the controller, service boundary or workflow start, then pass a decision object to downstream code.

#### Deep dive

For long-running workflows, persist the decision or version so retries continue with the same behavior.

#### Production angle

Stable decisions prevent partial execution under mixed old and new logic.

#### Traps / caveats

- Thread-local context can be fragile in async code.
- Do not reevaluate before every side effect.
- Make the chosen decision observable for debugging.

#### Optional Anki

Q: How to avoid mid-request flag changes?
A: Evaluate once and pass or persist the decision.

</details>

<a id="conf-flag-016"></a>

<details>
<summary><strong>🧠 CONF-FLAG-016. How do you avoid inconsistent feature-flag behavior across multiple services participating in one user flow?</strong></summary>

#### Short answer

Use shared targeting rules, stable context, versioned decisions or pass the chosen decision through the workflow.

#### Interview answer

If service A and service B evaluate the same flag independently with different context, cache state or SDK versions, they may disagree. For critical flows, evaluate at the edge or orchestrator and propagate the decision, or ensure all services use the same targeting key, provider rules and fallback.

#### Deep dive

For asynchronous workflows, include the decision or behavior version in the event or command so consumers process consistently.

#### Production angle

Inconsistent flags can cause one service to write new-format data while another expects old-format data.

#### Traps / caveats

- Do not rely on eventually consistent flag updates for strict workflows.
- Watch provider outage fallback differences.
- Keep app version and flag rules compatible.

#### Optional Anki

Q: How can services keep flag behavior consistent?
A: Use stable context or propagate a versioned decision.

</details>
