# Secret rotation and lifecycle

---

<a id="conf-rot-001"></a>

<details>
<summary><strong>CONF-ROT-001. What is secret rotation, and why is it important?</strong></summary>

#### Short answer

Secret rotation replaces an existing credential with a new one to reduce exposure and recover from compromise.

#### Interview answer

Secrets should not live forever. Rotation limits the damage from leaks, old employee access, vulnerable dependencies or accidental exposure. It also proves that the system can change credentials without emergency improvisation.

#### Deep dive

Rotation includes creating a new credential, distributing it, switching clients, verifying usage and revoking the old credential.

#### Production angle

Untested rotation often causes outages when a real leak forces emergency rotation.

#### Traps / caveats

- Rotation is not complete until old credentials are disabled.
- Rotating too often without automation causes fatigue and mistakes.
- Some clients cache credentials longer than expected.

#### Optional Anki

Q: What is secret rotation?
A: Replacing an old credential with a new one and retiring the old credential.

</details>

<a id="conf-rot-002"></a>

<details>
<summary><strong>CONF-ROT-002. How can secret rotation work without downtime?</strong></summary>

#### Short answer

Use overlap: make old and new credentials valid temporarily, move clients, verify, then revoke the old credential.

#### Interview answer

For zero-downtime rotation, the provider should accept both old and new credentials for a short period. Deploy or refresh services to use the new credential, monitor that they are authenticating successfully, then revoke the old one after all clients have moved.

#### Deep dive

Some systems support multiple active keys; others require creating a new user or credential. The exact steps depend on the dependency.

#### Production angle

Overlap avoids breaking running pods, connection pools and rolling deployments that still use the old value.

#### Traps / caveats

- Do not leave overlap forever.
- Verify actual usage, not just deployment success.
- Long-lived connections may keep using old credentials.

#### Optional Anki

Q: What is the main zero-downtime rotation pattern?
A: Temporary overlap where both old and new credentials work.

</details>

<a id="conf-rot-003"></a>

<details>
<summary><strong>CONF-ROT-003. How would you rotate a database password used by a Spring Boot service?</strong></summary>

#### Short answer

Create a new credential, update the service config, roll or refresh the service, verify connections, then revoke the old credential.

#### Interview answer

I would avoid changing a single shared password in place if possible. A safer pattern is to create a new DB user or password, grant required permissions, store it in the secret manager, restart or refresh pods so the datasource uses it, monitor connection success, then disable the old credential.

#### Deep dive

Connection pools complicate rotation because existing connections may remain open with the old credential. A restart or pool eviction may be needed.

#### Production angle

Coordinate rotation with rolling deployments and readiness checks so bad credentials do not replace healthy pods.

#### Traps / caveats

- Do not revoke the old password before all clients move.
- Check background workers as well as HTTP services.
- Avoid sharing one DB password across services.

#### Optional Anki

Q: What makes DB password rotation tricky?
A: Connection pools and running instances may keep old connections or credentials.

</details>

<a id="conf-rot-004"></a>

<details>
<summary><strong>CONF-ROT-004. What is the dual-secret or overlap-period rotation pattern?</strong></summary>

#### Short answer

It is a rotation pattern where old and new secrets are both accepted for a limited period.

#### Interview answer

The provider first starts accepting a new secret while still accepting the old one. Clients switch to the new secret gradually. After verification, the old secret is revoked. This avoids downtime during rolling deployments and client refresh delays.

#### Deep dive

This pattern appears in API key rotation, signing key rotation, database credentials and webhook secrets.

#### Production angle

Overlap is essential when not all clients can update atomically.

#### Traps / caveats

- Overlap increases exposure while both secrets are valid.
- You need monitoring to know when the old secret is no longer used.
- Some systems do not support overlap directly.

#### Optional Anki

Q: Why use a dual-secret pattern?
A: To rotate credentials without breaking clients that have not switched yet.

</details>

<a id="conf-rot-005"></a>

<details>
<summary><strong>CONF-ROT-005. What should happen if a secret is leaked?</strong></summary>

#### Short answer

Contain the leak, rotate or revoke the secret, investigate exposure, and prevent recurrence.

#### Interview answer

First identify what leaked, where it leaked and who could access it. Stop the leak source, remove public exposure, rotate or revoke the credential, check logs and audit trails for misuse, and update controls so it does not happen again.

#### Deep dive

If the secret was committed to Git or printed in logs, assume copies may exist outside the original location. Deleting the visible value is not enough.

#### Production angle

Fast rotation matters, but rushed rotation can cause outages if dependencies and clients are not understood.

#### Traps / caveats

- Do not delay rotation because the secret was deleted from Git.
- Consider downstream systems and backups.
- Preserve evidence for incident analysis.

#### Optional Anki

Q: What usually must happen after a real secret leak?
A: Rotate or revoke the secret and fix the leak source.

</details>

<a id="conf-rot-006"></a>

<details>
<summary><strong>CONF-ROT-006. How should a service behave if a required secret is missing or invalid?</strong></summary>

#### Short answer

If the secret is required for core behavior, fail fast and do not serve traffic.

#### Interview answer

For core dependencies like the main database, missing or invalid secrets should fail startup or readiness. For optional integrations, the service may start in degraded mode if that behavior is explicit, observable and safe.

#### Deep dive

The service should avoid silently using insecure defaults or local credentials. Error messages should identify the missing key without printing secret values.

#### Production angle

Failing fast prevents a bad pod from receiving traffic and failing real requests.

#### Traps / caveats

- Do not default to test credentials in production.
- Degraded mode must be visible in health or metrics.
- Invalid secrets during rotation may affect only new pods.

#### Optional Anki

Q: Missing required production secret: start or fail?
A: Fail fast or fail readiness.

</details>

<a id="conf-rot-007"></a>

<details>
<summary><strong>🧠 CONF-ROT-007. How would you rotate JWT signing keys or TLS certificates?</strong></summary>

#### Short answer

Use key overlap: publish new verification material before signing or serving with it, and keep old material until old tokens or connections expire.

#### Interview answer

For JWTs, publish the new public key in the JWK set before using the private key to sign tokens. Then start signing new tokens with the new key while resource servers can still validate old tokens. Remove the old key only after old tokens expire. For TLS, install the new certificate and key, reload or restart safely, and monitor handshake errors.

#### Deep dive

JWT emergency compromise may require faster revocation, shorter token lifetimes or token deny lists depending on risk.

#### Production angle

Bad key rotation can cause fleet-wide authentication or HTTPS outages.

#### Traps / caveats

- Do not remove old verification keys before old tokens expire.
- Ensure clients refresh JWK caches.
- Certificate chains and trust stores matter, not just leaf certificates.

#### Optional Anki

Q: Why keep old JWT verification keys during rotation?
A: To validate still-valid tokens signed with the old key.

</details>

<a id="conf-rot-008"></a>

<details>
<summary><strong>🧠 CONF-ROT-008. What are the risks of long-lived credentials?</strong></summary>

#### Short answer

Long-lived credentials increase the window of compromise and are harder to track, revoke and audit.

#### Interview answer

If a credential is valid for months or years, any leak remains useful for a long time. It may be copied into many systems, forgotten by owners and shared by services. Short-lived credentials reduce exposure and make rotation routine.

#### Deep dive

Long-lived credentials are especially risky when they are broad in scope, shared across services or stored in many places.

#### Production angle

An old leaked key can become a production incident long after the original mistake.

#### Traps / caveats

- Short-lived credentials require automation and refresh support.
- Rotation without monitoring can still fail silently.
- Do not confuse expiration with revocation.

#### Optional Anki

Q: Why are long-lived credentials risky?
A: They remain useful to attackers for a long time after a leak.

</details>

<a id="conf-rot-009"></a>

<details>
<summary><strong>🧠 CONF-ROT-009. How does secret rotation interact with connection pools, HTTP clients, Kafka producers, and cached credentials?</strong></summary>

#### Short answer

Long-lived clients may keep using old credentials until recreated, refreshed or reconnected.

#### Interview answer

Many Java clients load credentials at startup. A datasource pool may keep old DB connections. An HTTP client may keep an authorization provider or TLS context. A Kafka producer may keep SASL settings until restarted. Rotation must include how these clients pick up new credentials.

#### Deep dive

Some clients support dynamic credential providers; others need restart or bean recreation. The rotation plan should specify this.

#### Production angle

A secret can be updated in the secret manager while the running service still uses the old value.

#### Traps / caveats

- Updating a mounted file is not enough if the client never rereads it.
- Pool eviction may be required.
- Revoking the old credential too early can break long-lived connections.

#### Optional Anki

Q: Why can a rotated secret not take effect immediately?
A: Clients and pools may cache credentials or connections.

</details>
