# Secrets management fundamentals

---

<a id="conf-sec-001"></a>

<details>
<summary><strong>CONF-SEC-001. What is the difference between configuration and secrets?</strong></summary>

#### Short answer

Configuration is any deploy-specific setting; secrets are sensitive values that grant access or prove identity.

#### Interview answer

A timeout, endpoint or feature flag is configuration. A password, API key, private key, token or client secret is a secret. Secrets need stricter handling: limited access, encryption, rotation, redaction, audit and avoidance in logs or source control.

#### Deep dive

Secrets are often delivered through the same configuration path as normal settings, but they should not be treated the same operationally.

#### Production angle

Leaked normal config may reveal topology; leaked secrets can lead to data access, account takeover or production compromise.

#### Traps / caveats

- A value can become sensitive by context, such as internal hostnames.
- Do not store secrets in normal config repositories.
- Secret names can also reveal useful information.

#### Optional Anki

Q: What makes a value a secret?
A: It grants access, proves identity or must remain confidential.

</details>

<a id="conf-sec-002"></a>

<details>
<summary><strong>CONF-SEC-002. Why should secrets not be stored in Git, committed application.yml, or container images?</strong></summary>

#### Short answer

Because they spread through history, copies, caches and artifacts, making rotation and containment hard.

#### Interview answer

Git repositories are cloned, forked, cached and backed up. Container images have layers and are pushed to registries. If a secret is committed or baked into an image, removing the latest file does not remove all copies. The secret must be considered compromised.

#### Deep dive

Even private repositories and internal registries often have broad access compared with a secret manager. CI systems can also expose values in logs or build artifacts.

#### Production angle

Leaked credentials should be rotated or revoked, not just deleted from the file.

#### Traps / caveats

- `.gitignore` does not protect already committed secrets.
- Deleting a file from a Docker layer may not remove it from image history.
- Sample config should use placeholders, not real credentials.

#### Optional Anki

Q: Why is deleting a leaked secret from Git not enough?
A: It may still exist in history, clones, caches and backups.

</details>

<a id="conf-sec-003"></a>

<details>
<summary><strong>CONF-SEC-003. How should secrets be provided in Kubernetes or cloud environments?</strong></summary>

#### Short answer

Use Kubernetes Secrets, external secret managers, workload identity or mounted secret files with least privilege.

#### Interview answer

In Kubernetes, secrets can be mounted as files or exposed as environment variables, though mounted files are often better for certificates and private keys. In cloud environments, managed secret stores or workload identity reduce the need for long-lived static credentials.

#### Deep dive

Access should be scoped to the service that needs the secret. The deployment system should avoid rendering plaintext secrets into logs or broadly readable manifests.

#### Production angle

Secret delivery should support rotation, audit and controlled access, not just initial injection.

#### Traps / caveats

- Kubernetes Secrets are not safe unless RBAC and storage encryption are configured.
- Environment variables can appear in diagnostics.
- Local development should not use production secrets.

#### Optional Anki

Q: What is a safer alternative to long-lived cloud keys in Kubernetes?
A: Workload identity with short-lived credentials.

</details>

<a id="conf-sec-004"></a>

<details>
<summary><strong>CONF-SEC-004. Why is base64 encoding not encryption?</strong></summary>

#### Short answer

Base64 is reversible encoding, not cryptographic protection.

#### Interview answer

Base64 only converts bytes into text-safe characters. Anyone can decode it without a key. Kubernetes Secret values are commonly represented as base64 in manifests, but that does not mean they are encrypted or safe to commit.

#### Deep dive

Encryption requires a key and a cryptographic algorithm. Base64 is useful for transport and formatting, not confidentiality.

#### Production angle

Treat base64-encoded secrets as plaintext for logging, Git, code review and access control purposes.

#### Traps / caveats

- Base64 can make secrets look less obvious in diffs.
- "Encoded" should not be used as a security claim.
- Storage encryption protects at-rest storage, not everyone who can read the API object.

#### Optional Anki

Q: Does base64 protect a secret?
A: No, it is reversible encoding.

</details>

<a id="conf-sec-005"></a>

<details>
<summary><strong>CONF-SEC-005. How do RBAC, least privilege, and secret scope apply to secrets?</strong></summary>

#### Short answer

Only identities that need a secret should be able to read it, and each secret should have the smallest useful scope.

#### Interview answer

RBAC controls who can access secrets. Least privilege means a service should get only the credentials it needs, not all environment secrets. Scope means limiting credentials by service, environment, tenant, database permissions or API permissions.

#### Deep dive

Per-service credentials are usually safer than shared credentials. If one service is compromised, the attacker gets a smaller set of permissions.

#### Production angle

Good secret scoping reduces blast radius and makes incident response easier.

#### Traps / caveats

- Read access to Kubernetes Secrets is very powerful.
- Shared credentials make audit and revocation harder.
- Secret scope should match actual application responsibility.

#### Optional Anki

Q: Why prefer per-service credentials?
A: They reduce blast radius and improve auditability.

</details>

<a id="conf-sec-006"></a>

<details>
<summary><strong>CONF-SEC-006. Why should each service have its own credentials where possible?</strong></summary>

#### Short answer

Separate credentials limit blast radius, improve audit and allow independent rotation.

#### Interview answer

If many services share one database password or API key, one leak compromises all users of that credential. Separate credentials let you revoke or rotate only the affected service and understand which service performed which action.

#### Deep dive

Credentials should also have minimal permissions. A read-only service should not receive write credentials just because another service needs them.

#### Production angle

During a breach, per-service credentials help identify impact and recover without a fleet-wide emergency.

#### Traps / caveats

- More credentials require automation.
- Do not create unique credentials but give them all admin access.
- Rotation procedures must handle each credential class.

#### Optional Anki

Q: Main benefit of per-service credentials?
A: Smaller blast radius and better auditability.

</details>

<a id="conf-sec-007"></a>

<details>
<summary><strong>CONF-SEC-007. How can logs and exception messages accidentally expose secrets?</strong></summary>

#### Short answer

Secrets can appear in request dumps, config objects, URLs, headers, stack traces and error responses.

#### Interview answer

Logging full configuration, HTTP headers, connection strings, exception messages or serialized DTOs can leak passwords, tokens and API keys. Generated `toString()` methods, including record `toString()`, can also print sensitive fields.

#### Deep dive

Redaction should happen centrally where possible: logging filters, structured logging policies, HTTP client interceptors and safe exception handling.

#### Production angle

Logs are copied to centralized systems with many readers and long retention, so a log leak often expands the exposure.

#### Traps / caveats

- Do not log `Authorization`, `Cookie`, `Set-Cookie` or secret config values.
- Query strings can contain tokens.
- Redaction must cover custom field names, not only `password`.

#### Optional Anki

Q: If a real secret appears in logs, what should usually happen?
A: Stop the leak source and rotate or revoke the secret.

</details>

<a id="conf-sec-008"></a>

<details>
<summary><strong>🧠 CONF-SEC-008. How can heap dumps, thread dumps, crash reports, and diagnostic endpoints expose secrets?</strong></summary>

#### Short answer

Diagnostics can contain in-memory objects, system properties, headers, stack frames and configuration values.

#### Interview answer

Heap dumps may contain strings with passwords, tokens, config objects or HTTP payloads. Thread dumps can include request data in thread names, stack traces or MDC. Diagnostic endpoints can expose environment values, beans, logs, heap dumps or thread dumps.

#### Deep dive

Even if application logs are redacted, diagnostics may bypass the normal logging path. Access to these artifacts must be restricted.

#### Production angle

Heap dumps are often shared for debugging, so they should be handled like sensitive data.

#### Traps / caveats

- Sanitized Actuator output does not sanitize heap dumps.
- JVM system properties can expose secrets if used carelessly.
- Crash reports may be uploaded to external tools.

#### Optional Anki

Q: Why treat heap dumps as sensitive?
A: They can contain secrets and user data from memory.

</details>

<a id="conf-sec-009"></a>

<details>
<summary><strong>🧠 CONF-SEC-009. What is the difference between a secret, token, password, API key, certificate, and private key?</strong></summary>

#### Short answer

They are all sensitive credentials, but they serve different authentication and cryptographic roles.

#### Interview answer

A password is usually a shared human or service credential. A token is often a time-bound bearer credential. An API key identifies and authenticates a client to an API. A certificate contains public identity material and is often paired with a private key. A private key proves possession and must remain secret.

#### Deep dive

Rotation and storage differ. Private keys and signing keys need careful overlap. Bearer tokens are dangerous because possession is enough to use them.

#### Production angle

Confusing these terms leads to bad incident response, such as rotating a certificate but not the private key that leaked.

#### Traps / caveats

- Public certificates are not usually secret; private keys are.
- API keys often need rate limits and scopes.
- Tokens should have expiration and audience constraints.

#### Optional Anki

Q: Is a TLS certificate always secret?
A: The public certificate is not usually secret; the private key is.

</details>

<a id="conf-sec-010"></a>

<details>
<summary><strong>🧠 CONF-SEC-010. How do you avoid keeping sensitive values longer than needed in Java application memory?</strong></summary>

#### Short answer

Avoid unnecessary copies, avoid logging, prefer scoped use, and clear mutable buffers where practical.

#### Interview answer

Java often represents secrets as `String`, which is immutable and may remain in memory until garbage collection. For very sensitive short-lived values, `char[]` or `byte[]` can be cleared after use, but many libraries require `String`, so this is not a complete solution. The bigger wins are minimizing copies, avoiding dumps, redacting logs and using short-lived credentials.

#### Deep dive

Secrets used by connection pools, clients and crypto libraries may need to stay in memory while the service runs. That risk is managed with process isolation, least privilege and diagnostic controls.

#### Production angle

Memory hygiene matters most when heap dumps, crash dumps or broad debug access exist.

#### Traps / caveats

- `char[]` is not magic if the value is converted to `String`.
- Do not overcomplicate normal service credentials while ignoring logs and dumps.
- Generated `toString()` can expose secret fields.

#### Optional Anki

Q: Why is `String` imperfect for secrets?
A: It is immutable and cannot be reliably cleared from memory.

</details>
