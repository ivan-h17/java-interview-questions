# Spring Boot externalized configuration

---

<a id="conf-sprboot-001"></a>

<details>
<summary><strong>CONF-SPRBOOT-001. How does Spring Boot externalized configuration work at a high level?</strong></summary>

#### Short answer

Spring Boot reads configuration from multiple property sources and exposes resolved values through the Spring `Environment`, `@Value`, and `@ConfigurationProperties`.

#### Interview answer

Spring Boot collects values from sources such as `application.yml`, profile-specific files, environment variables, JVM system properties, command-line arguments, config imports and test overrides. Those values become part of the application `Environment`. Beans can consume them directly with `@Value`, through the `Environment`, or by binding groups of properties into typed `@ConfigurationProperties` classes.

#### Deep dive

Boot also uses configuration to drive auto-configuration. For example, datasource, server, logging, actuator and client settings can change which beans are created or how they are initialized.

#### Production angle

Understanding this helps debug why the value in a file is not the value the app actually uses at runtime.

#### Traps / caveats

- The same property can exist in several places.
- Some properties are read very early in startup.
- Secrets can be exposed if config diagnostics are not secured.

#### Optional Anki

Q: What abstraction holds resolved Spring configuration?
A: The Spring `Environment`.

</details>

<details>
<summary><strong>CONF-SPRBOOT-002. How does Spring Boot configuration property precedence work at a high level?</strong></summary>

#### Short answer

When the same key appears in multiple property sources, the higher-precedence source wins.

#### Interview answer

Spring Boot has an ordered set of property sources. Defaults, packaged files, external files, environment variables, system properties, command-line arguments and test overrides do not all have the same priority. In practice, operational sources often override values packaged with the application.

#### Deep dive

The exact order depends on Boot version and source type, so I do not rely on memory for every detail. For a production issue, I inspect the effective environment or Actuator diagnostics.

#### Production angle

Many incidents happen because a property was changed in `application.yml` but overridden by an environment variable, command-line argument or Kubernetes setting.

#### Traps / caveats

- Test overrides can hide production configuration problems.
- Environment-variable naming can cause accidental overrides.
- Actuator `env` is useful but sensitive.

#### Optional Anki

Q: What happens when the same Spring property is set in multiple sources?
A: The highest-precedence property source wins.

</details>

<details>
<summary><strong>🧠 CONF-SPRBOOT-003. What are the common Spring Boot configuration sources?</strong></summary>

#### Short answer

Common sources include config files, profile files, environment variables, system properties, command-line arguments, config imports, config trees and test overrides.

#### Interview answer

Typical sources are `application.properties` or `application.yml`, `application-{profile}.yml`, external files, OS environment variables, Java system properties, command-line arguments, `SPRING_APPLICATION_JSON`, ConfigData imports, Kubernetes mounted config trees and test annotations like `@TestPropertySource` or `@DynamicPropertySource`.

#### Deep dive

Spring Boot normalizes many property names through relaxed binding, but source precedence still matters. Some sources are better for local defaults, others for deployment-specific values.

#### Production angle

A good incident checklist includes checking the file, active profile, environment variables, container spec, command-line args and external config provider.

#### Traps / caveats

- Packaged config is often not the final value.
- Do not put secrets in source-controlled files.
- Avoid mixing `.properties` and YAML casually in the same config location.

#### Optional Anki

Q: Name three common Spring Boot config sources.
A: `application.yml`, environment variables and command-line arguments.

</details>

<details>
<summary><strong>CONF-SPRBOOT-004. What is relaxed binding, and how are environment variable names mapped to Spring Boot properties?</strong></summary>

#### Short answer

Relaxed binding lets Spring map equivalent property-name styles, including environment variables, to the same Java property.

#### Interview answer

Spring Boot can bind names such as `client.connect-timeout`, `client.connectTimeout` and environment-variable style names to the same configuration property. For environment variables, dots are usually replaced by underscores, dashes are removed or normalized, and names are uppercase, for example `MY_SERVICE_BASE_URL` maps to `my.service.base-url`.

#### Deep dive

This is convenient in Kubernetes and CI/CD because environment variables cannot always contain dots or dashes. It also means naming collisions and typos need attention.

#### Production angle

A typo in an environment variable may be ignored or may override a different property than intended.

#### Traps / caveats

- Relaxed binding is helpful, but not a substitute for config validation.
- List and map binding from environment variables can be awkward.
- Use consistent prefixes to avoid collisions.

#### Optional Anki

Q: How is `my.service.base-url` often represented as an environment variable?
A: `MY_SERVICE_BASE_URL`.

</details>

<details>
<summary><strong>CONF-SPRBOOT-005. How do profile-specific configuration files work in Spring Boot?</strong></summary>

#### Short answer

Spring Boot can load files such as `application-prod.yml` when the `prod` profile is active.

#### Interview answer

Profile-specific files override or supplement base configuration for active profiles. A common pattern is to keep shared defaults in `application.yml` and environment-specific overrides in `application-local.yml`, `application-test.yml` or `application-prod.yml`.

#### Deep dive

Profiles can also control beans with `@Profile`, but that should be used carefully. Profiles are best for coarse environment differences, not for every feature or tenant.

#### Production angle

Wrong active profiles can enable local settings, disable security or point production at the wrong service.

#### Traps / caveats

- Profile explosion makes behavior hard to reason about.
- Secrets should not be committed in profile files.
- Multiple active profiles can produce surprising merges.

#### Optional Anki

Q: What file might Boot load for the `prod` profile?
A: `application-prod.yml` or `application-prod.properties`.

</details>

<details>
<summary><strong>CONF-SPRBOOT-006. How do you make a Spring Boot application fail fast on missing required configuration?</strong></summary>

#### Short answer

Bind required settings to validated `@ConfigurationProperties` and fail startup when values are missing or invalid.

#### Interview answer

For important settings, I create a typed properties class with validation annotations such as `@NotBlank`, `@NotNull`, `@Positive` or custom checks. If configuration is missing or invalid, the application context should fail during startup instead of waiting for the first real request.

#### Deep dive

You can also validate relationships between fields in a custom validator or constructor. Examples include `maxRetries >= 0`, timeout ranges, required credentials for enabled integrations and valid URLs.

#### Production angle

Failing fast prevents a bad deployment from passing health checks and then failing under traffic.

#### Traps / caveats

- Defaults can accidentally hide missing critical values.
- Do not fail on optional integrations unless they are enabled.
- Make validation messages useful but non-sensitive.

#### Optional Anki

Q: Best Spring Boot pattern for required config validation?
A: Validated `@ConfigurationProperties`.

</details>

<a id="conf-sprboot-007"></a>

<details>
<summary><strong>🧠 CONF-SPRBOOT-007. How can you debug which configuration value Spring Boot actually used?</strong></summary>

#### Short answer

Check the effective environment, active profiles, property sources and bound `@ConfigurationProperties`.

#### Interview answer

I start by confirming active profiles, container environment variables, command-line args and external config imports. In a safe environment, Actuator `env` and `configprops` can show effective values and binding. Logs at startup may also show active profiles and config import behavior.

#### Deep dive

For a specific property, I look for all possible sources and compare precedence. In tests, I check `@SpringBootTest(properties=...)`, `@TestPropertySource` and `@DynamicPropertySource`.

#### Production angle

This is useful when `application.yml` says one thing but the service behaves as if another value is set.

#### Traps / caveats

- Do not expose Actuator config endpoints publicly.
- Sanitized output can hide values but still reveal key names.
- A value may be bound once at startup and not reflect later changes.

#### Optional Anki

Q: Which Actuator endpoints help debug effective config?
A: `env` and `configprops`, if securely exposed.

</details>

<details>
<summary><strong>🧠 CONF-SPRBOOT-008. How can Actuator env and configprops endpoints help debug configuration, and what are their security risks?</strong></summary>

#### Short answer

They show effective environment and bound configuration, but can expose sensitive operational data.

#### Interview answer

The `env` endpoint helps inspect property sources and resolved values. The `configprops` endpoint shows values bound to `@ConfigurationProperties` beans. They are very useful for diagnosing wrong values, missing bindings and unexpected overrides.

#### Deep dive

In production, these endpoints should be disabled, restricted or strongly protected. Even sanitized output can reveal internal hostnames, feature names, dependency structure and secret key names.

#### Production angle

Debugging configuration should not create a security incident. Operational endpoints need authentication, authorization, network controls and redaction.

#### Traps / caveats

- Do not expose all Actuator endpoints by default.
- Sanitization patterns must cover custom secret names.
- Heap dump, thread dump and log endpoints can also leak config or secrets.

#### Optional Anki

Q: Why are Actuator config endpoints sensitive?
A: They can reveal effective values, secret names, dependencies and internal topology.

</details>

<details>
<summary><strong>🧠 CONF-SPRBOOT-009. What is Spring Boot ConfigData, and when are config imports or config trees useful?</strong></summary>

#### Short answer

ConfigData is Spring Boot's mechanism for loading configuration files and imports early in startup.

#### Interview answer

ConfigData supports standard config files and imports through properties like `spring.config.import`. It is useful when configuration needs to come from external files, config servers, secret stores or Kubernetes-style config trees before beans are created.

#### Deep dive

Config trees map files in a directory to property names, which fits mounted Kubernetes Secrets or ConfigMaps. For example, a mounted file named `db.password` can become a property value.

#### Production angle

This lets a container image stay immutable while environment-specific config is mounted or imported at deployment time.

#### Traps / caveats

- Missing imports may fail startup unless marked optional.
- Config tree file names and permissions matter.
- Imported secrets must still be protected from logs and diagnostics.

#### Optional Anki

Q: When is a config tree useful?
A: When mounted files, such as Kubernetes secrets, should be read as configuration properties.

</details>

<details>
<summary><strong>🧠 CONF-SPRBOOT-010. How do Spring Cloud Config, Vault, or cloud secret manager integrations change startup, fail-fast, and refresh behavior?</strong></summary>

#### Short answer

They add external dependency and refresh semantics to configuration, so startup and runtime behavior must handle provider failures.

#### Interview answer

With external config providers, the app may need remote configuration before it can start. You must decide whether missing config should fail startup or allow degraded mode. Some integrations also support refresh, but refreshing values does not automatically rebuild every bean safely.

#### Deep dive

Config servers centralize values but add availability, latency, authentication and audit concerns. Secret managers improve credential handling but require IAM, token renewal and fallback decisions.

#### Production angle

If the config provider is down during deployment, the service may fail to start across the fleet unless there is caching, optional imports or a clear fail-fast policy.

#### Traps / caveats

- Do not assume all beans support live refresh.
- Avoid making startup depend on a remote system without timeouts.
- Cached secrets can become stale during rotation.

#### Optional Anki

Q: What risk does external config add at startup?
A: The application may depend on a remote provider being available and authorized.

</details>
