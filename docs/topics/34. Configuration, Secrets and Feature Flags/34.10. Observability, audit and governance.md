# Observability, audit and governance

---

<a id="conf-obs-001"></a>

<details>
<summary><strong>CONF-OBS-001. Why should services expose their effective non-sensitive configuration version?</strong></summary>

#### Short answer

It helps operators know which config each instance is actually running.

#### Interview answer

A service can expose a config version, checksum, timestamp or source revision without exposing secret values. This lets engineers compare replicas, correlate incidents and confirm that a rollout or rollback reached all instances.

#### Deep dive

The version should represent effective config, not just the Git revision of a file that may have been overridden.

#### Production angle

When two pods behave differently, config version is often as important as application version.

#### Traps / caveats

- Do not expose secret values.
- A version without source details may not be enough.
- Runtime flags may need separate versioning.

#### Optional Anki

Q: Why expose non-sensitive config version?
A: To diagnose drift and correlate behavior with config changes.

</details>

<a id="conf-obs-002"></a>

<details>
<summary><strong>CONF-OBS-002. What configuration information is safe to log, and what should never be logged?</strong></summary>

#### Short answer

Log non-sensitive versions and decisions; never log secrets, tokens, passwords, private keys or sensitive user data.

#### Interview answer

Safe logs include config version, active profile, feature decision name, rollout stage and non-sensitive source identifiers. Unsafe logs include credentials, authorization headers, cookies, private keys, database passwords, raw secret values and sensitive payloads.

#### Deep dive

For sensitive settings, log presence or source, not value. For example, "database password loaded from secret version X", not the password.

#### Production angle

Logs are widely copied and retained, so log leaks are difficult to contain.

#### Traps / caveats

- URLs can contain credentials or tokens.
- Generated `toString()` may leak fields.
- Sanitization must cover custom key names.

#### Optional Anki

Q: What config detail is usually safe to log?
A: A non-sensitive config version or source revision.

</details>

<a id="conf-obs-003"></a>

<details>
<summary><strong>CONF-OBS-003. How do you audit who changed configuration values or feature flags?</strong></summary>

#### Short answer

Record actor, time, old and new non-sensitive values, reason, approval and rollout scope.

#### Interview answer

Every production config or flag change should be traceable. The audit log should include who changed it, what key changed, before and after values where safe, target environment, approval, ticket or incident link and whether the change succeeded.

#### Deep dive

For secrets, log metadata and version changes, not secret values. For feature flags, record targeting rules and rollout percentages.

#### Production angle

Audit makes incident correlation and accountability possible.

#### Traps / caveats

- A config UI without audit is risky.
- Audit logs must not contain plaintext secrets.
- Automation identities should still be traceable to a workflow.

#### Optional Anki

Q: What should a config audit event include?
A: Actor, time, key, environment, safe diff, reason and approval.

</details>

<a id="conf-obs-004"></a>

<details>
<summary><strong>CONF-OBS-004. How do you correlate a production incident with a configuration change?</strong></summary>

#### Short answer

Compare incident timing, affected services, config versions, flag changes and deployment events.

#### Interview answer

I would check recent config and flag audit logs, deployment history, config version by instance, metrics around the change time and whether only targeted users or regions were affected. If rollback changes metrics quickly, that strengthens the correlation.

#### Deep dive

Good dashboards should show app version, config version, flag state and major dependency health together.

#### Production angle

Many incidents are caused by config changes without a code deployment, so deployment history alone is not enough.

#### Traps / caveats

- Correlation is not proof; check metrics and logs.
- Flag targeting can affect only part of traffic.
- Config provider lag can shift timing by instance.

#### Optional Anki

Q: What timeline should incident review include besides deployments?
A: Configuration and feature flag changes.

</details>

<a id="conf-obs-005"></a>

<details>
<summary><strong>🧠 CONF-OBS-005. What metrics would you track for feature flag usage, provider latency, fallback behavior, and reload failures?</strong></summary>

#### Short answer

Track evaluation counts, error rates, fallback counts, provider sync health, reload success and config version.

#### Interview answer

Useful metrics include flag evaluations by flag name, enabled/disabled decision counts, provider sync latency, provider error rate, fallback usage, config reload attempts, reload failures, last successful refresh age and current config version.

#### Deep dive

Avoid tagging metrics with high-cardinality user IDs or raw targeting attributes. Use logs or traces carefully for detailed investigations.

#### Production angle

Fallback spikes or stale refresh age can reveal provider outages before users report problems.

#### Traps / caveats

- High-cardinality flag metrics can overload monitoring.
- Do not expose sensitive targeting data.
- A green provider metric does not prove business behavior is correct.

#### Optional Anki

Q: What feature-flag metric signals provider trouble?
A: Fallback count or provider sync error rate.

</details>

<a id="conf-obs-006"></a>

<details>
<summary><strong>🧠 CONF-OBS-006. How do you detect unused feature flags or stale configuration keys?</strong></summary>

#### Short answer

Track runtime usage, code references, config references and ownership metadata.

#### Interview answer

For flags, record evaluations and compare against code references and expected cleanup dates. For config keys, compare deployment files, binding metadata and runtime access. Stale values should have owners and cleanup tickets.

#### Deep dive

Some keys are only used on rare paths, so usage windows must be long enough. Static analysis helps but cannot prove everything.

#### Production angle

Removing stale flags and keys reduces accidental toggles and cognitive load.

#### Traps / caveats

- Do not remove a rarely used incident flag without confirming purpose.
- Runtime usage can miss startup-only config.
- Cleanup should be tested like any change.

#### Optional Anki

Q: What indicates a stale feature flag?
A: No evaluations or code references after the intended cleanup date.

</details>

<a id="conf-obs-007"></a>

<details>
<summary><strong>🧠 CONF-OBS-007. What approval workflow should high-risk configuration changes have?</strong></summary>

#### Short answer

High-risk changes should require validation, peer review, explicit approval, rollout plan and rollback plan.

#### Interview answer

Settings that affect security, retries, rate limits, credentials, data writes or broad traffic should not be changed casually. I would require automated validation, ownership, peer approval, change reason, staged rollout and monitoring.

#### Deep dive

Approvals should be proportional. A low-risk UI experiment does not need the same workflow as changing global retry behavior.

#### Production angle

Good governance prevents a config console from becoming an unreviewed production deployment system.

#### Traps / caveats

- Approval without validation is weak.
- Emergency changes still need after-the-fact audit.
- Too much process pushes people toward bypasses.

#### Optional Anki

Q: What should high-risk config changes include?
A: Validation, approval, rollout plan, rollback plan and audit.

</details>
