# Profiles, environments and organization

---

<a id="conf-prof-001"></a>

<details>
<summary><strong>CONF-PROF-001. What are Spring profiles, and when should you use them?</strong></summary>

#### Short answer

Spring profiles are named conditions that activate specific beans or configuration for a runtime environment or mode.

#### Interview answer

Profiles are useful for coarse differences such as local development, tests or production. With Spring Boot, an active profile can load profile-specific files like `application-prod.yml`, and `@Profile` can include or exclude beans.

#### Deep dive

Profiles should be used sparingly. They are good for environment shape, not for every feature, tenant or customer behavior.

#### Production angle

Wrong profiles can enable local-only beans, unsafe defaults or test integrations in production.

#### Traps / caveats

- Profiles are not a secrets mechanism.
- Too many profiles make behavior hard to predict.
- Multiple active profiles can interact unexpectedly.

#### Optional Anki

Q: What property commonly activates Spring profiles?
A: `spring.profiles.active`.

</details>

<a id="conf-prof-002"></a>

<details>
<summary><strong>CONF-PROF-002. What are the risks of profile explosion?</strong></summary>

#### Short answer

Profile explosion creates too many environment combinations to understand, test or operate safely.

#### Interview answer

If a service has profiles like `prod-eu-blue-premium-legacy`, behavior becomes a hidden matrix. Developers may not know which config applies, tests cover only a subset, and production may run combinations nobody expected.

#### Deep dive

Profile explosion often means profiles are being used for features, tenants, regions and release states. Those may need typed config, feature flags or data-driven configuration instead.

#### Production angle

Incidents become hard to reproduce because "production" is not one behavior but many profile combinations.

#### Traps / caveats

- Avoid copying whole config files for small differences.
- Do not encode customer identity as profiles.
- Do not use profiles as a release-management system.

#### Optional Anki

Q: What is profile explosion?
A: Too many profiles or profile combinations to reason about safely.

</details>

<a id="conf-prof-003"></a>

<details>
<summary><strong>CONF-PROF-003. How can profiles make tests pass while production fails?</strong></summary>

#### Short answer

Tests may run with different beans, properties or defaults than production.

#### Interview answer

A test profile can use an embedded database, disabled security, fake clients, lower validation or different transaction behavior. That is useful, but it can hide missing production properties, wrong profiles, invalid external endpoints or startup failures.

#### Deep dive

The more the test profile differs from production, the more integration and smoke tests need to verify production-like configuration.

#### Production angle

A service can pass CI and fail at startup because the real production profile requires a secret or property that the test profile never used.

#### Traps / caveats

- Test convenience should not bypass config validation.
- Avoid production code paths that exist only under untested profiles.
- Use Testcontainers or realistic stubs where config matters.

#### Optional Anki

Q: Why can a test profile hide production problems?
A: It may use different beans, defaults and required properties.

</details>

<a id="conf-prof-004"></a>

<details>
<summary><strong>CONF-PROF-004. When should you prefer feature flags over profiles?</strong></summary>

#### Short answer

Use feature flags for controlled behavior rollout; use profiles for coarse environment setup.

#### Interview answer

If a behavior needs gradual rollout, quick rollback, tenant targeting or experiment control, a feature flag is usually better. Profiles are activated at startup and apply broadly. They are a poor fit for enabling a new API path for 5 percent of users or disabling one integration during an incident.

#### Deep dive

Profiles express where or how the app runs. Feature flags express whether a behavior is enabled for a request, user, tenant or cohort.

#### Production angle

Using profiles for releases often forces redeploys and creates too many profile combinations.

#### Traps / caveats

- Feature flags need cleanup and ownership.
- Feature flags are not authorization.
- Profiles may still be appropriate for local fake clients or test infrastructure.

#### Optional Anki

Q: Profiles or feature flags for gradual rollout?
A: Feature flags.

</details>

<a id="conf-prof-005"></a>

<details>
<summary><strong>🧠 CONF-PROF-005. How do you keep configuration changes reviewable?</strong></summary>

#### Short answer

Keep config in structured, versioned, validated files or systems with ownership, diffs and approvals.

#### Interview answer

Configuration changes should be small, named and reviewed like code when they can affect production behavior. Use typed keys, clear descriptions, pull requests or audited change workflows, validation in CI, and non-sensitive effective-config reporting.

#### Deep dive

For high-risk settings like retries, credentials, authorization behavior or kill switches, require stronger approval and rollback instructions.

#### Production angle

Reviewability makes it possible to correlate incidents with configuration changes.

#### Traps / caveats

- A web UI without audit can hide dangerous changes.
- Large copied YAML files are hard to review.
- Do not include plaintext secrets in review diffs.

#### Optional Anki

Q: What makes config changes reviewable?
A: Versioning, diffs, ownership, validation, audit and clear rollback.

</details>

<a id="conf-prof-006"></a>

<details>
<summary><strong>🧠 CONF-PROF-006. How do you handle tenant-specific, region-specific, or customer-specific configuration without profile explosion?</strong></summary>

#### Short answer

Use typed data-driven configuration or a controlled config service instead of one Spring profile per tenant or region.

#### Interview answer

Tenant and region behavior often changes independently from deployment environment. I would model it as validated data or dynamic configuration keyed by tenant or region, with ownership, audit and defaults. Profiles should remain coarse, like `prod` or `test`.

#### Deep dive

For high-volume tenant config, consider caching, versioning, limits and fallback. For security-sensitive differences, avoid making access control depend on weak external config.

#### Production angle

This avoids creating hundreds of profile combinations that nobody can test or reason about.

#### Traps / caveats

- Per-tenant config can become a hidden product rule engine.
- Validate tenant config before rollout.
- Avoid leaking tenant identifiers in high-cardinality metrics.

#### Optional Anki

Q: Why avoid one profile per tenant?
A: It creates profile explosion and untestable behavior combinations.

</details>

<a id="conf-prof-007"></a>

<details>
<summary><strong>🧠 CONF-PROF-007. What are common anti-patterns when using Spring profiles?</strong></summary>

#### Short answer

Common anti-patterns are too many profiles, profile-based releases, hidden security differences and storing secrets in profile files.

#### Interview answer

Profiles become dangerous when they decide business features, customers, authorization rules or release state. They also cause trouble when local/test profiles disable validation or security in ways production never exercises.

#### Deep dive

A healthy profile strategy keeps base config common and uses profiles for limited environment differences. Feature flags, typed config and deployment configuration handle the rest.

#### Production angle

Many "works locally" failures come from local profiles that are too different from production.

#### Traps / caveats

- Do not use `prod` profile as a substitute for real production secrets.
- Do not add a new profile for every small override.
- Be careful with multiple active profiles and order.

#### Optional Anki

Q: What should profiles mainly represent?
A: Coarse runtime environments or modes, not every feature or tenant.

</details>
