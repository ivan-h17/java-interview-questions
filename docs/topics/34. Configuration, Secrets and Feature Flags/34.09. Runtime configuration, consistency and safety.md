# Runtime configuration, consistency and safety

---

<a id="conf-dyn-001"></a>

<details>
<summary><strong>CONF-DYN-001. How can runtime configuration changes cause incidents?</strong></summary>

#### Short answer

Runtime config can immediately change live behavior across traffic without a code deploy.

#### Interview answer

A bad runtime value can increase retry rates, remove limits, change timeouts, overload dependencies, disable validation or route traffic incorrectly. Because changes may apply while requests are running, they can create mixed behavior across replicas or workflows.

#### Deep dive

Runtime config is powerful for mitigation, but it needs validation, audit, rollout controls, blast-radius limits and rollback.

#### Production angle

A config UI can become as dangerous as a deployment pipeline if it can alter critical behavior instantly.

#### Traps / caveats

- Do not allow arbitrary values without range checks.
- Do not update high-risk settings globally in one step.
- Runtime changes need observability and ownership.

#### Optional Anki

Q: Why is runtime config risky?
A: It can change live production behavior instantly.

</details>

<a id="conf-dyn-002"></a>

<details>
<summary><strong>CONF-DYN-002. How do you prevent stale or inconsistent dynamic configuration across replicas?</strong></summary>

#### Short answer

Use versioned config, controlled rollout, refresh monitoring and clear consistency requirements.

#### Interview answer

Replicas may not update at exactly the same time. To manage this, include config versions, expose the effective version, monitor refresh success and design changes so temporary mixed versions are acceptable. If mixed behavior is unsafe, use a coordinated rollout or restart.

#### Deep dive

Some config can be eventually consistent, like a UI experiment. Other config, like message schema mode or payment behavior, may need strict coordination.

#### Production angle

During incidents, seeing config version by instance helps identify split-brain behavior.

#### Traps / caveats

- Do not assume push updates are perfectly simultaneous.
- Cache TTLs create stale windows.
- Fallback values can differ between app versions.

#### Optional Anki

Q: What helps diagnose inconsistent dynamic config?
A: Exposing effective config version per instance.

</details>

<a id="conf-dyn-003"></a>

<details>
<summary><strong>CONF-DYN-003. How do you validate dynamic configuration before applying it?</strong></summary>

#### Short answer

Validate type, range, relationships, safety rules and compatibility before publishing or accepting the value.

#### Interview answer

Dynamic config needs the same or stronger validation than startup config. A service should reject invalid values, and the config management system should prevent publishing dangerous values. Examples include max retry counts, timeout bounds, rate limits and required fields.

#### Deep dive

For high-risk config, use staged rollout, dry-run checks, policy approval and automated canary analysis.

#### Production angle

Validation prevents one bad value from creating a fleet-wide incident.

#### Traps / caveats

- Type-correct does not mean safe.
- Validate cross-field relationships.
- Do not apply partially invalid config snapshots.

#### Optional Anki

Q: What should dynamic config validation check besides type?
A: Range, relationships, compatibility and operational safety.

</details>

<a id="conf-dyn-004"></a>

<details>
<summary><strong>CONF-DYN-004. How do you roll back a bad runtime configuration change?</strong></summary>

#### Short answer

Revert to a known good version, verify propagation and monitor recovery.

#### Interview answer

Runtime config should be versioned so rollback means selecting the previous known good version, not guessing values manually. After rollback, verify that all replicas received it and that metrics return to normal.

#### Deep dive

For dangerous changes, rollback should be part of the change plan. Some effects, such as already-sent messages or data writes, may need repair, not just rollback.

#### Production angle

Fast rollback is one reason to use centralized config, but only if it is tested and observable.

#### Traps / caveats

- Rollback may not undo side effects.
- Some clients cache old values until TTL expires.
- Manual hot fixes can create more drift.

#### Optional Anki

Q: Best rollback target for dynamic config?
A: A known good version.

</details>

<a id="conf-dyn-005"></a>

<details>
<summary><strong>CONF-DYN-005. How can bad dynamic configuration create a retry storm?</strong></summary>

#### Short answer

Bad retry, timeout or concurrency settings can cause clients to amplify load on failing dependencies.

#### Interview answer

If a timeout is too low, clients may retry requests that would have succeeded. If retries are too high or backoff is missing, each failure creates more requests. A dynamic config change can spread this behavior across all replicas quickly.

#### Deep dive

Retry settings must be designed with idempotency, backoff, jitter, deadlines and dependency capacity in mind.

#### Production angle

During a partial outage, bad retry config can turn a dependency problem into a system-wide outage.

#### Traps / caveats

- More retries do not always improve reliability.
- Retry storms may appear as increased traffic, CPU and latency.
- Changing pool sizes can also amplify pressure.

#### Optional Anki

Q: What config values can cause retry storms?
A: Timeouts, retry counts, backoff, concurrency limits and pool sizes.

</details>

<a id="conf-dyn-006"></a>

<details>
<summary><strong>CONF-DYN-006. How should a service behave when the dynamic configuration provider is unavailable?</strong></summary>

#### Short answer

Use explicit fallback behavior: cached last-known-good values, safe defaults, or fail fast depending on criticality.

#### Interview answer

The service should not block every request waiting for a config provider. For most dynamic config, use cached values and alert on provider failure. If required startup config is unavailable, decide whether to fail startup or start in a clearly degraded mode.

#### Deep dive

Fallback policy should be per config type. A security policy might fail closed; an experiment flag can use default off.

#### Production angle

Provider outages should be visible but should not automatically become application outages unless the missing config is truly critical.

#### Traps / caveats

- Last-known-good can become stale.
- Silent fallback hides incidents.
- Different app versions may have different defaults.

#### Optional Anki

Q: Common fallback for dynamic config provider outage?
A: Cached last-known-good values with alerts.

</details>

<a id="conf-dyn-007"></a>

<details>
<summary><strong>CONF-DYN-007. How do you keep application version and configuration version compatible during rolling deployments?</strong></summary>

#### Short answer

Design config changes to be backward-compatible across old and new app versions during the rollout window.

#### Interview answer

During rolling deployment, old and new versions run together. Config must be valid for both, or the rollout must coordinate config and code carefully. For key renames, support both keys temporarily. For behavior changes, use explicit compatibility flags or versioned config.

#### Deep dive

This is similar to database expand-and-contract migrations: add support, migrate config, then remove old support later.

#### Production angle

Without compatibility, half the pods may start or behave differently from the other half.

#### Traps / caveats

- Do not remove old config support in the same release that introduces new keys.
- Validate config against both versions when possible.
- Watch background workers and consumers too.

#### Optional Anki

Q: What is the safe pattern for config key migration?
A: Support both old and new keys during rolling deployment.

</details>

<a id="conf-dyn-008"></a>

<details>
<summary><strong>🧠 CONF-DYN-008. What are the trade-offs between polling and push-based configuration updates?</strong></summary>

#### Short answer

Polling is simpler and predictable; push is faster but adds connection and coordination complexity.

#### Interview answer

With polling, each service checks for updates periodically, so changes take effect after a delay. It is easy to reason about but creates staleness. Push-based updates reduce delay, but need reliable delivery, reconnect behavior and backpressure.

#### Deep dive

Polling with jitter avoids thundering herds. Push still needs fallback because connections can drop.

#### Production angle

The choice depends on how quickly updates must apply and how dangerous temporary inconsistency is.

#### Traps / caveats

- Push is not automatically consistent across all replicas.
- Polling too often can overload the provider.
- Both need versioning and observability.

#### Optional Anki

Q: Polling trade-off for dynamic config?
A: Simpler but stale between polls.

</details>

<a id="conf-dyn-009"></a>

<details>
<summary><strong>🧠 CONF-DYN-009. How do you safely change timeout, retry, or pool-size configuration at runtime?</strong></summary>

#### Short answer

Use strict ranges, gradual rollout, metrics and client-specific refresh behavior.

#### Interview answer

These settings directly affect load and latency. I would validate ranges, change gradually, monitor dependency errors and latency, and know whether the Java client actually applies the new value. Some settings may require rebuilding clients or restarting pods.

#### Deep dive

Retries and timeouts should align with request deadlines. Pool-size changes should consider dependency capacity, not only local throughput.

#### Production angle

Unsafe runtime tuning can create overload faster than a normal deployment.

#### Traps / caveats

- Increasing pool size can overload downstream systems.
- Shorter timeouts can increase retries.
- Some clients read config only at construction.

#### Optional Anki

Q: Why are retry and timeout configs high risk?
A: They can amplify load and change failure behavior.

</details>

<a id="conf-dyn-010"></a>

<details>
<summary><strong>🧠 CONF-DYN-010. How do you make dynamic configuration updates atomic from the service perspective?</strong></summary>

#### Short answer

Apply a complete validated snapshot, not individual fields one by one.

#### Interview answer

If related fields update separately, the service can observe invalid combinations. A better approach is to load a versioned snapshot, validate it fully, then publish it as one immutable object to readers.

#### Deep dive

In Java, this often means building a new immutable config object and swapping an `AtomicReference` or volatile reference after validation.

#### Production angle

Atomic updates avoid transient states like new retry count with old timeout or new endpoint with old credentials.

#### Traps / caveats

- Partial updates can be worse than stale config.
- Validate before publishing, not after.
- Readers should use one snapshot for a logical operation.

#### Optional Anki

Q: How should related dynamic config fields update?
A: As one validated immutable snapshot.

</details>

<a id="conf-dyn-011"></a>

<details>
<summary><strong>🧠 CONF-DYN-011. How do you safely publish a new immutable configuration snapshot in Java code?</strong></summary>

#### Short answer

Build and validate a new immutable object, then swap a volatile or atomic reference.

#### Interview answer

I would represent runtime config as an immutable value object. A refresh thread loads raw config, validates it, constructs the new object and updates an `AtomicReference<ConfigSnapshot>`. Request threads read the reference once and use that snapshot.

#### Deep dive

This avoids locking on the request path and prevents readers from seeing half-updated mutable state.

#### Production angle

It gives predictable behavior under concurrent traffic while still allowing runtime updates.

#### Traps / caveats

- Do not mutate shared maps in place.
- Read one snapshot per operation if consistency matters.
- Include version and timestamp for diagnostics.

#### Optional Anki

Q: Java pattern for safe dynamic config publication?
A: Immutable snapshot plus `AtomicReference` or volatile reference.

</details>

<a id="conf-dyn-012"></a>

<details>
<summary><strong>🧠 CONF-DYN-012. What Java objects or Spring beans are risky to refresh dynamically?</strong></summary>

#### Short answer

Stateful clients, pools, schedulers, security components and caches are risky to refresh live.

#### Interview answer

Examples include `DataSource`, connection pools, HTTP clients, Kafka producers and consumers, executors, schedulers, TLS contexts, caches and security filters. They may hold connections, threads, credentials or internal state that cannot safely change just because a property changed.

#### Deep dive

Some objects need graceful recreation. Others should change only on restart. The refresh plan must match the component lifecycle.

#### Production angle

Refreshing a pool incorrectly can leak resources, drop traffic or use mixed credentials.

#### Traps / caveats

- `@RefreshScope`-style behavior is not magic.
- Background workers may keep old references.
- Restart may be safer than live refresh for structural settings.

#### Optional Anki

Q: Name a bean risky to refresh dynamically.
A: `DataSource`, HTTP client, Kafka producer, executor or scheduler.

</details>

<a id="conf-dyn-013"></a>

<details>
<summary><strong>🧠 CONF-DYN-013. How do you design blast-radius limits for centralized configuration changes?</strong></summary>

#### Short answer

Limit who can change high-risk config, validate values, roll out gradually and cap the scope of changes.

#### Interview answer

Centralized config can affect many services at once. To limit blast radius, use per-service ownership, environment separation, approval gates, canaries, tenant or region targeting, maximum allowed values and automatic rollback triggers.

#### Deep dive

High-risk settings should not be editable globally by default. Changes should be versioned and attributable to a person or automation.

#### Production angle

Blast-radius control prevents one bad config edit from becoming a fleet-wide outage.

#### Traps / caveats

- Self-service without guardrails is dangerous.
- Global defaults can surprise services.
- Approval alone is weaker than automated validation.

#### Optional Anki

Q: How to reduce centralized config blast radius?
A: Scope changes, validate them, roll out gradually and audit ownership.

</details>
