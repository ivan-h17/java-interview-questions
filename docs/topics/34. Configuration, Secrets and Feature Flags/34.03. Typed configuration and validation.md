# Typed configuration and validation

---

<a id="conf-typed-001"></a>

<details>
<summary><strong>CONF-TYPED-001. When should you use @ConfigurationProperties instead of @Value, and what advantages does type-safe configuration provide?</strong></summary>

#### Short answer

Use `@ConfigurationProperties` for grouped or important config; use `@Value` only for simple one-off values.

#### Interview answer

`@Value` injects individual values and is fine for very small cases. `@ConfigurationProperties` binds a whole prefix into a typed object, which is better for client settings, timeouts, retry policies, feature groups and service integrations. It supports validation, metadata, nested structures and clearer ownership.

#### Deep dive

Typed config makes invalid values visible at startup. It also centralizes names and defaults, so properties are not scattered across services and components.

#### Production angle

For production services, typed validated config catches bad values before traffic arrives.

#### Traps / caveats

- Do not put business logic in properties classes.
- Do not log properties objects that contain secrets.
- `@Value` expressions can be hard to find and validate.

#### Optional Anki

Q: Which annotation is preferred for structured Spring Boot config?
A: `@ConfigurationProperties`.

</details>

<a id="conf-typed-002"></a>

<details>
<summary><strong>CONF-TYPED-002. How do you validate @ConfigurationProperties at startup with Bean Validation?</strong></summary>

#### Short answer

Annotate the properties class for validation and add constraints to fields or constructor parameters.

#### Interview answer

In Spring Boot, a `@ConfigurationProperties` class can be validated with Bean Validation constraints such as `@NotBlank`, `@NotNull`, `@Positive` or `@Min`, plus provider-specific constraints such as Hibernate Validator's `@DurationMin` where available. When the application context starts, binding and validation happen, and invalid config fails startup.

#### Deep dive

For cross-field validation, use a custom validator, constructor checks or an assertion method. For example, require `apiKey` only when an integration is enabled, or ensure `connectTimeout` is less than `readTimeout`.

#### Production angle

This prevents bad deployments from becoming runtime incidents.

#### Traps / caveats

- Validation messages should not include secret values.
- Default values can bypass missing-value checks.
- Validate ranges, not just presence.

#### Optional Anki

Q: Why validate configuration at startup?
A: To fail fast before invalid settings affect production traffic.

</details>

<a id="conf-typed-003"></a>

<details>
<summary><strong>CONF-TYPED-003. How do you provide safe default values for typed configuration?</strong></summary>

#### Short answer

Put conservative defaults in the properties class or base config, and validate that required overrides are present.

#### Interview answer

Defaults should be explicit and safe. For example, a feature flag can default to disabled, a timeout can have a reasonable upper bound, and an optional integration can default to off. Required values like production credentials should not silently default to local placeholders.

#### Deep dive

Defaults can live in constructor parameters, field initializers or base `application.yml`. The important part is distinguishing safe defaults from fake values.

#### Production angle

Safe defaults reduce blast radius when a property is missing. Unsafe defaults can connect to the wrong system or enable risky behavior.

#### Traps / caveats

- Never default production secrets.
- Avoid infinite or very high timeouts as defaults.
- Defaulting enabled behavior is often riskier than defaulting disabled behavior.

#### Optional Anki

Q: What is a safe feature default?
A: Usually disabled unless explicitly enabled.

</details>

<a id="conf-typed-004"></a>

<details>
<summary><strong>CONF-TYPED-004. What are the risks of scattering many @Value fields across services?</strong></summary>

#### Short answer

Scattered `@Value` usage makes configuration hard to discover, validate, rename and test.

#### Interview answer

If every service class injects strings with `@Value`, there is no central model of configuration. You may miss validation, duplicate defaults, typo keys and make refactoring risky. It also hides operationally important settings inside business classes.

#### Deep dive

Grouped typed config gives better cohesion: one prefix, one owner, one validation model and easier metadata generation.

#### Production angle

Scattered config often causes incidents where a missing value is discovered only when a rarely used code path executes.

#### Traps / caveats

- `@Value` is not bad for a trivial one-off value.
- Do not replace scattered `@Value` with a giant unrelated config object.
- Keep config classes focused by domain or integration.

#### Optional Anki

Q: Main problem with many `@Value` fields?
A: Configuration becomes scattered and hard to validate.

</details>

<a id="conf-typed-005"></a>

<details>
<summary><strong>🧠 CONF-TYPED-005. How do you avoid mixing business logic into configuration classes?</strong></summary>

#### Short answer

Keep configuration classes as typed values with validation, not as services that make business decisions.

#### Interview answer

A properties class should describe configured values: timeouts, URLs, limits and flags. It can validate invariants, but it should not call repositories, clients or implement domain workflows. Business logic should consume configuration through explicit services or policies.

#### Deep dive

It is acceptable to expose small derived values if they are purely local and deterministic, but complex branching belongs outside configuration classes.

#### Production angle

Mixing logic into config makes changes hard to test and can make runtime refresh unexpectedly alter behavior.

#### Traps / caveats

- Validation is not the same as business logic.
- Do not inject many application services into properties classes.
- Avoid hiding feature behavior inside getters.

#### Optional Anki

Q: What should a configuration class primarily contain?
A: Typed values, defaults and validation.

</details>

<a id="conf-typed-006"></a>

<details>
<summary><strong>🧠 CONF-TYPED-006. How would you model nested configuration, collections, maps, durations, sizes, and enums?</strong></summary>

#### Short answer

Use structured `@ConfigurationProperties` classes with nested objects and typed fields.

#### Interview answer

For a group like `clients.payment`, I would create a properties class with nested classes or records for each client, using `Duration` for timeouts, `DataSize` for sizes, enums for modes and `List` or `Map` for repeated client definitions. This avoids parsing strings manually.

#### Deep dive

Typed fields let Spring's binder handle conversion and let Bean Validation enforce constraints. Maps are useful for named integrations or tenants, but they need clear ownership and limits.

#### Production angle

Typed durations and sizes avoid unit mistakes like treating milliseconds as seconds.

#### Traps / caveats

- Collections from environment variables can be awkward to maintain.
- Enum changes can break startup if old config uses removed values.
- Huge maps of tenant behavior may be better stored in data or a config service.

#### Optional Anki

Q: Why use `Duration` in config?
A: To avoid manual parsing and unit confusion.

</details>

<a id="conf-typed-007"></a>

<details>
<summary><strong>🧠 CONF-TYPED-007. How do you validate relationships between multiple configuration fields?</strong></summary>

#### Short answer

Use constructor checks, custom validators or class-level Bean Validation constraints.

#### Interview answer

Single-field annotations catch simple problems, but many settings depend on each other. For example, if `enabled=true`, then `baseUrl` and credentials must exist. Or `maxBackoff` should be greater than `initialBackoff`. I would validate those rules during startup.

#### Deep dive

For immutable properties, constructor validation is often clear. For more reusable checks, a class-level constraint or Spring validator can report structured errors.

#### Production angle

Cross-field validation prevents broken integrations that are syntactically valid but operationally impossible.

#### Traps / caveats

- Do not make validation depend on remote systems unless intentionally doing a readiness check.
- Avoid error messages that print secrets.
- Test invalid combinations, not only missing fields.

#### Optional Anki

Q: Example of cross-field config validation?
A: If an integration is enabled, require its URL and credentials.

</details>

<a id="conf-typed-008"></a>

<details>
<summary><strong>🧠 CONF-TYPED-008. How would you prevent unknown or misspelled configuration keys from being ignored silently?</strong></summary>

#### Short answer

Use typed config, metadata, validation, startup checks and CI checks to catch unknown or unused keys.

#### Interview answer

A typo like `connection-timeuot` can silently leave the real timeout at its default. To reduce that, I use `@ConfigurationProperties`, generated metadata for IDE support, tests that load production-like config, and CI validation for deployment manifests. For critical config, I also expose effective non-sensitive config versions or checksums.

#### Deep dive

Spring Boot binding can be permissive in some cases, so relying on startup alone is not enough. Repository checks and deployment validation are useful.

#### Production angle

Misspelled keys are a common cause of "we changed the value but nothing happened" incidents.

#### Traps / caveats

- Unknown-key detection can be harder when using maps or flexible config.
- Do not expose secret values while validating config.
- Removing stale keys should be a controlled cleanup.

#### Optional Anki

Q: What is the risk of a misspelled config key?
A: The intended setting may be ignored while the default remains active.

</details>
