# 11.02. Threads, lifecycle, interruption and cancellation

---

<a id="mt-thread-001"></a>

<details>
<summary><strong>MT-THREAD-001. What is the difference between a process and a thread?</strong></summary>

#### Short answer

A process is an isolated running program. A thread is an execution path inside a process.

#### Interview answer

Processes usually have separate address spaces and resources. Threads in the same process share heap memory, open files and process resources, but each thread has its own stack and execution state.

In Java, a JVM process can contain many application, GC, JIT and runtime threads. Sharing memory makes threads efficient, but it also creates concurrency risks.

#### Deep dive

Threads are cheaper than processes but not free. Platform threads map to operating-system threads and consume stack memory and scheduler resources.

#### Production angle

Too many platform threads can increase memory usage and context switching. Thread dumps show what the JVM's threads are doing inside one process.

#### Traps / caveats

- Thread isolation is weaker than process isolation.
- A crashing native thread can affect the whole process.
- Shared heap requires synchronization or immutability.

#### Optional Anki

Q: What do Java threads in one process share?
A: The process heap and resources.

</details>

<a id="mt-thread-002"></a>

<details>
<summary><strong>MT-THREAD-002. What is the difference between `Thread` and `Runnable`?</strong></summary>

#### Short answer

`Thread` is the execution mechanism. `Runnable` is a task with no result and no checked exception.

#### Interview answer

A `Thread` represents a thread of execution. A `Runnable` represents work to run, via its `run()` method. Usually you separate task from execution by implementing `Runnable` or using executors instead of subclassing `Thread`.

This keeps code composable: the same task can run in a raw thread, a pool, a scheduler or a virtual thread.

#### Deep dive

Extending `Thread` couples work to the execution resource and prevents extending another class. Modern Java code usually uses `ExecutorService`, `CompletableFuture`, schedulers or framework-managed executors.

#### Production angle

Use named thread factories or framework executors so operations are visible in logs, metrics and thread dumps.

#### Traps / caveats

- Calling `run()` directly does not start a new thread.
- Raw thread creation is rarely appropriate in request paths.
- `Runnable` cannot return a value directly.

#### Optional Anki

Q: Preferred way to model work?
A: Implement `Runnable`/`Callable` and submit it to an executor.

</details>

<a id="mt-thread-003"></a>

<details>
<summary><strong>MT-THREAD-003. What is the difference between `Runnable`, `Callable` and `Future`?</strong></summary>

#### Short answer

`Runnable` is work without a result, `Callable` is work with a result or checked exception, and `Future` represents the eventual result.

#### Interview answer

`Runnable.run()` returns `void` and cannot declare checked exceptions. `Callable.call()` returns a value and can throw checked exceptions. When you submit a task to an `ExecutorService`, you usually get a `Future` that lets you wait for completion, retrieve the result, observe failure or request cancellation.

#### Deep dive

`Future` is a result handle, not the task itself. It is also hard to compose, which is why `CompletableFuture` exists for richer async pipelines.

#### Production angle

Do not ignore returned futures for important work. Otherwise failures can be lost and shutdown may not wait for in-flight tasks.

#### Traps / caveats

- `Future.get()` blocks.
- `Future.cancel(true)` is cooperative and depends on interruption handling.
- Exceptions from `Callable` are wrapped in `ExecutionException`.

#### Optional Anki

Q: Which interface returns a value?
A: `Callable`.

</details>

<a id="mt-thread-004"></a>

<details>
<summary><strong>MT-THREAD-004. What is the difference between `Thread.start()` and `Thread.run()`?</strong></summary>

#### Short answer

`start()` creates a new execution thread. `run()` is just a normal method call on the current thread.

#### Interview answer

Calling `start()` asks the JVM to start a new thread and eventually invoke that thread's `run()` method. Calling `run()` directly executes the code synchronously in the caller.

A `Thread` can be started only once. Calling `start()` a second time throws `IllegalThreadStateException`.

#### Deep dive

`start()` also creates a happens-before relationship: actions before starting the thread are visible to actions in the started thread.

#### Production angle

Accidentally calling `run()` instead of `start()` can serialize work and hide concurrency bugs in tests.

#### Traps / caveats

- `run()` does not create concurrency.
- A thread cannot be restarted.
- Prefer executors for most application code.

#### Optional Anki

Q: What starts a new Java thread?
A: `Thread.start()`.

</details>

<a id="mt-thread-005"></a>

<details>
<summary><strong>MT-THREAD-005. What are the main thread states in Java?</strong></summary>

#### Short answer

The main states are `NEW`, `RUNNABLE`, `BLOCKED`, `WAITING`, `TIMED_WAITING` and `TERMINATED`.

#### Interview answer

`NEW` means created but not started. `RUNNABLE` means ready or running from the JVM perspective. `BLOCKED` means waiting to acquire a monitor. `WAITING` means waiting indefinitely for another action, such as `join()` or `wait()`. `TIMED_WAITING` is waiting with a timeout, such as `sleep()` or timed `poll()`. `TERMINATED` means execution finished.

#### Deep dive

`RUNNABLE` does not always mean using CPU. A Java thread doing blocking native I/O can appear runnable depending on the stack and JVM state.

#### Production angle

Thread states are clues, not conclusions. Always inspect stack traces, lock owners, pool metrics and external dependency latency.

#### Traps / caveats

- Many `WAITING` threads can be normal in idle pools.
- `BLOCKED` on the same monitor suggests contention.
- `RUNNABLE` plus high CPU points to hot loops or CPU-heavy work.

#### Optional Anki

Q: Which state means waiting for a monitor?
A: `BLOCKED`.

</details>

<a id="mt-thread-006"></a>

<details>
<summary><strong>MT-THREAD-006. What is a daemon thread, and when would you use one?</strong></summary>

#### Short answer

A daemon thread is a background thread that does not keep the JVM alive.

#### Interview answer

When all non-daemon user threads finish, the JVM can exit even if daemon threads are still running. Daemon threads are useful for background support work where abrupt termination is acceptable, such as housekeeping.

For important business work, use user threads or managed executors and shut them down explicitly.

#### Deep dive

Daemon status must be set before the thread starts. Executors can create daemon threads through a custom `ThreadFactory`, but this should be deliberate.

#### Production angle

Do not run payment processing, file writes or message acknowledgments only on daemon threads; work can be abandoned during shutdown.

#### Traps / caveats

- Daemon threads may not finish finally blocks before JVM exit.
- Daemon does not mean low priority.
- Framework lifecycle is usually better than raw daemon threads.

#### Optional Anki

Q: Do daemon threads keep the JVM alive?
A: No.

</details>

<a id="mt-thread-007"></a>

<details>
<summary><strong>MT-THREAD-007. What do `Thread.sleep()`, `Thread.join()` and `Thread.yield()` do?</strong></summary>

#### Short answer

`sleep()` pauses the current thread, `join()` waits for another thread to finish, and `yield()` hints to the scheduler.

#### Interview answer

`Thread.sleep()` puts the current thread into timed waiting and does not release monitors. `join()` lets one thread wait until another terminates and creates useful completion visibility. `yield()` is only a hint that the current thread is willing to let others run; correctness must never depend on it.

#### Deep dive

Both `sleep()` and `join()` can throw `InterruptedException`. Sleeping is not a coordination mechanism because it does not prove the condition you need has become true.

#### Production angle

Use latches, futures, queues or Awaitility in tests instead of sleeps for coordination.

#### Traps / caveats

- `sleep()` does not release locks.
- `yield()` has no strong guarantee.
- `join()` can block forever without timeout or cancellation.

#### Optional Anki

Q: Does `sleep()` release a monitor lock?
A: No.

</details>

<a id="mt-thread-008"></a>

<details>
<summary><strong>MT-THREAD-008. What is thread interruption?</strong></summary>

#### Short answer

Interruption is Java's cooperative signal that a thread should stop or change what it is doing.

#### Interview answer

Calling `interrupt()` sets the target thread's interrupt status. Blocking methods such as `sleep`, `wait`, `join` and many blocking queue operations respond by throwing `InterruptedException` and clearing the status.

Interruption does not forcibly kill a thread. Code must check the status or handle `InterruptedException` and exit, propagate or restore the interrupt.

#### Deep dive

Good cancellation design is cooperative. Long CPU loops should check interruption periodically. Blocking calls should be chosen with interruption behavior in mind.

#### Production angle

Ignoring interruption breaks graceful shutdown, request cancellation and structured concurrency cleanup.

#### Traps / caveats

- `interrupt()` is not `stop()`.
- Catching and ignoring `InterruptedException` loses cancellation.
- Some I/O APIs are not interruptible in the way you expect.

#### Optional Anki

Q: Is Java interruption cooperative?
A: Yes.

</details>

<a id="mt-thread-009"></a>

<details>
<summary><strong>MT-THREAD-009. What is the difference between `interrupt()`, `isInterrupted()` and `interrupted()`?</strong></summary>

#### Short answer

`interrupt()` sets the flag, `isInterrupted()` reads another thread's flag, and static `interrupted()` reads and clears the current thread's flag.

#### Interview answer

`thread.interrupt()` requests interruption. `thread.isInterrupted()` checks whether that specific thread is interrupted without clearing the flag. `Thread.interrupted()` checks the current thread and clears the interrupted status.

That clearing behavior is a common source of bugs.

#### Deep dive

When a blocking method throws `InterruptedException`, it usually clears the interrupted status. If the current method cannot propagate the exception, it often should restore it with `Thread.currentThread().interrupt()`.

#### Production angle

Preserving interrupt status lets outer layers, executors and shutdown logic respond correctly.

#### Traps / caveats

- Static `interrupted()` affects only the current thread.
- It clears the flag.
- Do not swallow interruption in library code.

#### Optional Anki

Q: Which method clears interrupt status?
A: `Thread.interrupted()`.

</details>

<a id="mt-thread-010"></a>

<details>
<summary><strong>MT-THREAD-010. How should `InterruptedException` be handled?</strong></summary>

#### Short answer

Either propagate it, treat it as cancellation and exit, or restore the interrupt status if you cannot throw it.

#### Interview answer

The best handling depends on the method contract. If the method can throw `InterruptedException`, propagate it. If the operation should stop, clean up and return. If you catch it inside a method that cannot throw it, usually call `Thread.currentThread().interrupt()` before returning or throwing another exception.

Empty catch blocks are almost always wrong.

#### Deep dive

Restoring the flag preserves the signal for outer code. Do not convert interruption into a generic failure without preserving cancellation semantics.

#### Production angle

Good interrupt handling is essential for Kubernetes shutdown, executor shutdown, client disconnects and timeouts.

#### Traps / caveats

- Do not retry forever after interruption.
- Avoid logging interruption as an unexpected error if it is normal cancellation.
- Cleanup should not block indefinitely.

#### Optional Anki

Q: If you catch `InterruptedException` and cannot rethrow?
A: Restore status with `Thread.currentThread().interrupt()`.

</details>

<a id="mt-thread-011"></a>

<details>
<summary><strong>MT-THREAD-011. Why is `Thread.stop()` deprecated and dangerous?</strong></summary>

#### Short answer

It can kill a thread at an arbitrary point and leave shared state inconsistent.

#### Interview answer

`Thread.stop()` throws an asynchronous error into the target thread and releases monitors as the stack unwinds. The thread may be in the middle of updating an object invariant, writing a file or holding resources. Other threads can then observe corrupted state.

Use cooperative cancellation through interruption, flags, futures, structured scopes or application lifecycle hooks.

#### Deep dive

The problem is not just resource cleanup; it is breaking invariants while making partially updated objects visible.

#### Production angle

For stuck work, prefer timeouts, interruptible APIs, circuit breakers and process-level restart if the thread is truly unrecoverable.

#### Traps / caveats

- `stop()` is not a safe timeout mechanism.
- Killing threads can corrupt shared caches.
- Some blocking calls need resource closing rather than interruption.

#### Optional Anki

Q: Why avoid `Thread.stop()`?
A: It can leave shared state inconsistent.

</details>

<a id="mt-thread-012"></a>

<details>
<summary><strong>MT-THREAD-012. What happens when an uncaught exception is thrown in a thread, and why do thread names matter?</strong></summary>

#### Short answer

The thread terminates, and the exception is handled by its `UncaughtExceptionHandler` or default handler. Thread names make failures diagnosable.

#### Interview answer

An uncaught exception does not normally kill the JVM; it kills that thread. For raw threads, the uncaught exception handler can log or record the failure. For executor tasks submitted with `submit()`, exceptions are captured in the `Future` instead of going to the handler.

Thread names matter because logs, metrics and thread dumps are much easier to interpret when names identify the pool and workload.

#### Deep dive

For background loops, an uncaught exception can silently stop processing unless supervisors restart the work or alerts detect it.

#### Production angle

Use named thread factories and make sure async failures are observed, logged and connected to the task or request context.

#### Traps / caveats

- `submit()` can hide exceptions until `Future.get()`.
- A dead background thread may look like lost work.
- Names should avoid sensitive data.

#### Optional Anki

Q: What happens to a thread after an uncaught exception?
A: It terminates.

</details>
