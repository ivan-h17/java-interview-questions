# 11.07. ThreadLocal, context propagation and backend boundaries

---

<a id="mt-ctx-001"></a>

<details>
<summary><strong>MT-CTX-001. What is `ThreadLocal`, and when is it useful?</strong></summary>

#### Short answer

`ThreadLocal` stores a separate value per thread.

#### Interview answer

A `ThreadLocal<T>` lets code associate data with the current thread without passing it through method parameters. It is useful for infrastructure context such as logging MDC, security context, request metadata or framework internals.

It should be used sparingly because it hides dependencies and interacts badly with thread reuse if not cleaned up.

#### Deep dive

Each thread has its own map of thread-local values. The `ThreadLocal` object acts as a key.

#### Production angle

ThreadLocal is common in frameworks, but business code should usually prefer explicit parameters or request-scoped abstractions.

#### Traps / caveats

- Values can leak between tasks in pools.
- It hides coupling.
- It does not automatically cross async boundaries.

#### Optional Anki

Q: What does `ThreadLocal` scope data to?
A: The current thread.

</details>

---

<a id="mt-ctx-002"></a>

<details>
<summary><strong>MT-CTX-002. Why can `ThreadLocal` cause memory leaks or user-context leaks in thread pools?</strong></summary>

#### Short answer

Pool threads are reused, so a value can remain attached to a thread after the request that set it is finished.

#### Interview answer

If a task sets a `ThreadLocal` and does not remove it, the worker thread can keep that value for the lifetime of the pool. Later unrelated tasks on the same worker may see old context, such as user ID, tenant ID or security data. Large values can also be retained in memory.

Always clean up in `finally` or use framework-supported context management.

#### Deep dive

The leak is often logical: the value is still reachable from a live thread, so GC cannot collect it.

#### Production angle

Leaked context can cause security bugs, wrong logs, wrong tenant routing and memory pressure.

#### Traps / caveats

- `set(null)` is not always equivalent to `remove()`.
- Cleanup must run on success and failure.
- Async callbacks may run on different workers.

#### Optional Anki

Q: Why call `ThreadLocal.remove()` in pools?
A: To prevent values leaking into later tasks on reused threads.

</details>

<a id="mt-ctx-003"></a>

<details>
<summary><strong>🧠 MT-CTX-003. What is `InheritableThreadLocal`, and why can it be dangerous?</strong></summary>

#### Short answer

`InheritableThreadLocal` copies a parent thread's value to child threads, but this can propagate stale or unintended context.

#### Interview answer

It was designed so a newly created child thread can inherit context from the parent. In thread pools, this model is often wrong because workers are created before requests and reused across many tasks. It can also spread security or tenant context farther than intended.

#### Deep dive

Inheritance happens at thread creation, not every task submission. That distinction makes it unreliable for executor-based request context propagation.

#### Production angle

Use framework-provided context propagation, task decorators or explicit context objects instead of relying on inheritable thread locals.

#### Traps / caveats

- Bad fit for thread pools.
- Can leak privileged context.
- Values may be stale.

#### Optional Anki

Q: When does `InheritableThreadLocal` copy values?
A: At child thread creation.

</details>

<a id="mt-ctx-004"></a>

<details>
<summary><strong>MT-CTX-004. How do MDC, tracing context and security context usually propagate across async boundaries?</strong></summary>

#### Short answer

They must be captured from the submitting thread and restored around execution in the worker thread.

#### Interview answer

MDC, tracing and security contexts are often stored in thread-local state. When work moves to another thread, that state does not automatically follow. A common solution is a task wrapper or Spring `TaskDecorator` that captures context, sets it before running the task, and clears/restores it in `finally`.

Tracing libraries may also provide executor instrumentation.

#### Deep dive

Context propagation should be deliberate. Not every context is safe to copy.

#### Production angle

Without propagation, async logs lose request IDs, traces break and authorization decisions can run without expected authentication.

#### Traps / caveats

- Always clear restored context.
- Avoid propagating stale mutable objects.
- Transaction context is not just another MDC value.

#### Optional Anki

Q: Basic async context propagation pattern?
A: Capture, restore before execution, clear in `finally`.

</details>

<a id="mt-ctx-005"></a>

<details>
<summary><strong>MT-CTX-005. Why can async execution lose `SecurityContext` or transaction context?</strong></summary>

#### Short answer

Because those contexts are usually bound to the current thread.

#### Interview answer

Spring Security and Spring transactions commonly use thread-local context. When code runs in another executor thread, that thread has a different thread-local map. Without explicit propagation, the async task may not see the authentication. Transaction state also does not automatically move to the worker thread.

Even when security context can be propagated, transaction context usually should not be blindly copied.

#### Deep dive

A transaction is tied to resources such as a database connection and persistence context. Sharing that across threads can break assumptions.

#### Production angle

Async code should start its own transaction when needed and pass explicit IDs/DTOs rather than live persistence objects.

#### Traps / caveats

- Missing context can bypass or fail authorization.
- Blind propagation can leak privileges.
- JPA `EntityManager` is not thread-safe.

#### Optional Anki

Q: Why does `@Transactional` not automatically cross threads?
A: Transaction context is thread-bound.

</details>

<a id="mt-ctx-006"></a>

<details>
<summary><strong>🧠 MT-CTX-006. What are Scoped Values?</strong></summary>

#### Short answer

Scoped Values are a Java mechanism for sharing immutable data within a bounded dynamic scope and with child threads.

#### Interview answer

Scoped Values provide an alternative to some uses of `ThreadLocal`. A value is bound for the duration of a lexical/dynamic scope, can be read by code called inside that scope, and is automatically unavailable after the scope ends.

They are designed to be easier to reason about and efficient with virtual threads and structured concurrency.

#### Deep dive

Scoped Values are finalized in JDK 25. They support one-way sharing rather than arbitrary mutation through `set()`.

#### Production angle

They are promising for framework context like request metadata, but adoption depends on runtime version and framework support.

#### Traps / caveats

- They are not a drop-in replacement for mutable thread-local state.
- They require newer Java.
- Existing frameworks may still use `ThreadLocal`.

#### Optional Anki

Q: Main idea of Scoped Values?
A: Bounded, immutable context sharing.

</details>

---

<a id="mt-ctx-007"></a>

<details>
<summary><strong>🧠 MT-CTX-007. When would Scoped Values be preferable to `ThreadLocal`?</strong></summary>

#### Short answer

When context is immutable, passed from caller to callees, and should have a clearly bounded lifetime.

#### Interview answer

Scoped Values are preferable for request metadata, tenant IDs or framework context that should be readable by downstream code but not mutated from anywhere. Their lifetime follows code structure, so cleanup is automatic when the scope exits.

`ThreadLocal` remains useful for legacy frameworks or cases requiring mutable per-thread state.

#### Deep dive

Scoped Values also compose with structured concurrency: child tasks can inherit bindings safely within the parent scope.

#### Production angle

They reduce accidental leaks and make context ownership easier to audit in virtual-thread-heavy applications.

#### Traps / caveats

- Do not use them for mutable accumulators.
- Scope boundaries must be designed.
- Framework support may lag Java support.

#### Optional Anki

Q: Scoped Values are best for what kind of data?
A: Immutable caller-to-callee context.

</details>

<a id="mt-ctx-008"></a>

<details>
<summary><strong>MT-CTX-008. How would you propagate request context safely across async boundaries?</strong></summary>

#### Short answer

Pass explicit context where possible; otherwise use a tested capture/restore/clear wrapper.

#### Interview answer

For business data, pass explicit values such as request ID, user ID or tenant ID. For infrastructure context like MDC or tracing, wrap tasks with code that captures the current context, restores it in the worker, and clears it in `finally`.

Be selective: propagate only what the async operation needs and is allowed to use.

#### Deep dive

Context should be immutable or treated as immutable. Mutable shared context objects can create races.

#### Production angle

Tests should verify context appears in async logs and is cleaned before the next task.

#### Traps / caveats

- Do not propagate transaction context blindly.
- Do not store request objects in long-lived tasks.
- Cleanup must happen after exceptions too.

#### Optional Anki

Q: Safest business context propagation?
A: Explicit immutable parameters.

</details>

<a id="mt-ctx-009"></a>

<details>
<summary><strong>MT-CTX-009. Why should transaction context not be blindly propagated to another thread?</strong></summary>

#### Short answer

Because transaction context is tied to thread-bound resources and persistence assumptions.

#### Interview answer

Spring transactions commonly bind a connection and persistence context to the current thread. Moving that context to another thread can violate resource ownership, thread-safety and transaction lifecycle expectations. JPA `EntityManager` is not designed for concurrent use.

Async work should usually use its own transaction, or be triggered after commit through events, messaging or the outbox pattern.

#### Deep dive

Starting async side effects before commit can expose data that later rolls back or duplicate work after retries.

#### Production angle

For reliable side effects, coordinate with transaction boundaries explicitly.

#### Traps / caveats

- Lazy-loaded entities may fail outside the original transaction.
- Sharing `EntityManager` across threads is unsafe.
- Async failure may be lost after the main transaction commits.

#### Optional Anki

Q: Should Spring transaction context be copied to worker threads?
A: Usually no.

</details>

<a id="mt-be-001"></a>

<details>
<summary><strong>MT-BE-001. Is a Spring singleton bean thread-safe by default, and why should it usually be stateless?</strong></summary>

#### Short answer

No. A Spring singleton has one shared instance, so mutable fields are shared across threads.

#### Interview answer

Spring singleton scope means one bean instance per application context, not one per request. Multiple request threads can call the same service bean concurrently. If it stores request-specific or temporary mutable state in fields, requests can interfere with each other.

Singleton services should usually be stateless, with state kept in local variables, immutable collaborators or thread-safe components.

#### Deep dive

Constructor-injected dependencies in final fields are fine; mutable per-request fields are the risk.

#### Production angle

Stateful singleton bugs appear only under concurrent traffic and often cause user data leaks or corrupted responses.

#### Traps / caveats

- `@Service` does not imply thread-safe.
- Local variables are per-call stack.
- Caches inside beans need explicit concurrency design.

#### Optional Anki

Q: Is Spring singleton per request?
A: No, it is shared in the application context.

</details>

<a id="mt-be-002"></a>

<details>
<summary><strong>MT-BE-002. How does `@Async` work in Spring, and why should its executor be configured explicitly?</strong></summary>

#### Short answer

`@Async` runs a method through a Spring proxy on an executor; the executor should be explicit so capacity and behavior are known.

#### Interview answer

When a proxied `@Async` method is called from outside the bean, Spring submits it to an executor and returns immediately or returns a future-like result. The default executor may be unsuitable for production. Configure pool size, queue capacity, thread names and rejection behavior.

Exceptions differ: `void` async methods need an async exception handler; future-returning methods report failures through the future.

#### Deep dive

Self-invocation inside the same bean bypasses the proxy, so `@Async` may not apply.

#### Production angle

Every async workload needs metrics, timeout policy, context propagation and shutdown behavior.

#### Traps / caveats

- Self-invocation bypasses `@Async`.
- Default executor may be unbounded or poorly named.
- Exceptions can be lost in fire-and-forget methods.

#### Optional Anki

Q: Why configure `@Async` executor?
A: To control concurrency, queueing, naming and rejection.

</details>

<a id="mt-be-003"></a>

<details>
<summary><strong>MT-BE-003. What can go wrong if async code is started inside a transaction or uses JPA entities across threads?</strong></summary>

#### Short answer

Async work can observe inconsistent transaction state, lose failures, or use non-thread-safe persistence objects.

#### Interview answer

If async work starts before the surrounding transaction commits, it may act on data that later rolls back. If it uses JPA entities after the transaction ends, lazy loading can fail or stale data can be used. Sharing `EntityManager` or managed entities across threads is unsafe.

Prefer passing IDs or immutable DTOs and starting a clear transaction in the async worker if needed.

#### Deep dive

For durable side effects, publish after commit or use the transactional outbox pattern.

#### Production angle

This shows up as missing audit logs, duplicate messages, stale reads and rare `LazyInitializationException`.

#### Traps / caveats

- Async failure may not roll back the original transaction.
- Entity state is not a thread-safe DTO.
- Transaction synchronization must be explicit.

#### Optional Anki

Q: What should async JPA work usually receive?
A: IDs or immutable DTOs, not live managed entities.

</details>
