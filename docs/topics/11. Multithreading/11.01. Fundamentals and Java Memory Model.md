# 11.01. Fundamentals and Java Memory Model

---

<a id="mt-fund-001"></a>

<details>
<summary><strong>MT-FUND-001. What is concurrency, and how is it different from parallelism?</strong></summary>

#### Short answer

Concurrency is structuring a program to handle multiple tasks in overlapping time. Parallelism is executing multiple tasks at the same instant on multiple cores.

#### Interview answer

Concurrency is about dealing with many things at once: requests, background jobs, messages or timers. Parallelism is about doing many things at once physically. A single-core machine can run concurrent code by switching between tasks, but true parallelism needs multiple execution resources.

In backend work, concurrency is often used to keep the system responsive while I/O waits. Parallelism is useful when CPU-heavy work can be split safely.

#### Deep dive

Concurrency introduces coordination problems even without speedup. Shared state, ordering, cancellation, visibility and lifecycle must still be designed.

#### Production angle

Do not assume concurrent code is faster. For I/O-heavy services it can improve throughput; for CPU-heavy services it can increase contention and latency if overused.

#### Traps / caveats

- Concurrent does not mean parallel.
- Async does not automatically mean non-blocking.
- More threads can make a service slower.

#### Optional Anki

Q: Concurrency vs parallelism?
A: Concurrency overlaps tasks logically; parallelism runs tasks physically at the same time.

</details>

<a id="mt-fund-002"></a>

<details>
<summary><strong>MT-FUND-002. What is thread-safety?</strong></summary>

#### Short answer

Thread-safety means code behaves correctly when accessed by multiple threads according to its intended contract.

#### Interview answer

A class is thread-safe if concurrent use cannot corrupt its state, break invariants, expose partially initialized data or produce invalid results. Thread-safety is not only about avoiding exceptions; it is about preserving correctness under interleavings.

Common ways to achieve it are immutability, confinement, synchronization, atomic variables and concurrent collections.

#### Deep dive

The scope of the guarantee matters. A collection may be thread-safe internally while the business operation around it is not. For example, two separate map updates can still break an invariant.

#### Production angle

Thread-safety bugs often appear only under load. Review mutable fields in singletons, caches, request context, lazy initialization and callback code.

#### Traps / caveats

- Thread-safe data structure does not make all usage patterns safe.
- Read-only access is safe only if publication was safe.
- Thread-safety should be documented at API boundaries.

#### Optional Anki

Q: What does thread-safe mean?
A: Correct behavior under allowed concurrent access.

</details>

<a id="mt-fund-003"></a>

<details>
<summary><strong>MT-FUND-003. What is shared mutable state, and why is it dangerous?</strong></summary>

#### Short answer

Shared mutable state is data that multiple threads can access and at least one thread can modify.

#### Interview answer

It is dangerous because threads can interleave reads and writes in unexpected ways. One thread may see stale data, partially updated state or overwrite another thread's change. The result can be lost updates, broken invariants, duplicate work or corrupted objects.

The safest designs avoid sharing, avoid mutation, or coordinate access explicitly.

#### Deep dive

Shared mutable state is not limited to static fields. It can be a Spring singleton field, a cached object, a collection value, a request object captured by an async task, or a mutable object stored in a concurrent map.

#### Production angle

Many production races come from "small" mutable fields added to otherwise stateless services: counters, last result, temporary buffers or reused DTOs.

#### Traps / caveats

- `final` on a reference does not make the referenced object immutable.
- Concurrent collections do not make mutable values safe.
- Logging can hide timing bugs.

#### Optional Anki

Q: Safest way to handle shared mutable state?
A: Avoid sharing, avoid mutation, or synchronize access.

</details>

<a id="mt-fund-004"></a>

<details>
<summary><strong>MT-FUND-004. What is a race condition, and how is it different from a data race?</strong></summary>

#### Short answer

A race condition is a correctness bug caused by timing. A data race is unsynchronized conflicting access to the same variable.

#### Interview answer

A race condition happens when the result depends on an unsafe ordering of operations. A data race is more specific: two threads access the same variable, at least one writes, and there is no proper happens-before relationship.

Every data race is suspicious, but not every race condition is a low-level data race. For example, two requests can both pass a "does order exist?" check and create duplicate orders even if database operations are individually safe.

#### Deep dive

Common race patterns are check-then-act, read-modify-write and unsafe publication.

#### Production angle

Race conditions often show up as duplicate payments, stale cache values, impossible state transitions or rare test failures.

#### Traps / caveats

- Thread-safe methods can still be composed unsafely.
- Database uniqueness may be the correct guard for business races.
- Reproducing a race locally is not proof that it is fixed.

#### Optional Anki

Q: Race condition vs data race?
A: Race condition is timing-dependent incorrect behavior; data race is unsynchronized conflicting variable access.

</details>

<a id="mt-fund-005"></a>

<details>
<summary><strong>MT-FUND-005. What are atomicity, visibility and ordering in concurrent programs?</strong></summary>

#### Short answer

Atomicity means an operation happens as one indivisible action. Visibility means one thread can see another thread's writes. Ordering means operations are observed in a valid sequence.

#### Interview answer

Concurrent correctness needs all three. `count++` is not atomic because it is read, increment and write. A non-volatile flag may have visibility problems because another thread may not see the update promptly. Ordering matters because compilers and CPUs can reorder operations as long as single-thread behavior is preserved.

Java synchronization tools create rules that provide the needed guarantees.

#### Deep dive

`volatile` helps visibility and ordering for a variable, but not compound atomicity. Locks provide mutual exclusion plus visibility at lock boundaries.

#### Production angle

When reviewing a concurrency bug, ask which property is missing: indivisible update, visibility of writes, or ordering between actions.

#### Traps / caveats

- Atomicity and visibility are different.
- Atomicity of one field does not protect a multi-field invariant.
- Reordering is constrained by the JMM, not eliminated.

#### Optional Anki

Q: Why is `volatile int count; count++` unsafe?
A: `volatile` gives visibility, but `count++` is still a compound operation.

</details>

<a id="mt-jmm-001"></a>

<details>
<summary><strong>MT-JMM-001. What is the Java Memory Model?</strong></summary>

#### Short answer

The Java Memory Model defines how threads interact through memory and what visibility and ordering guarantees Java programs can rely on.

#### Interview answer

The JMM is the contract between Java code, the compiler, the JVM and hardware. It defines when writes by one thread must be visible to another and which reorderings are allowed. Without it, correct concurrent Java code would depend on CPU and JVM implementation details.

The key practical concept is happens-before: if action A happens-before action B, B must see the effects of A that are relevant to memory visibility.

#### Deep dive

The JMM is not the same as heap, stack or garbage collection memory areas. It is about consistency rules for shared memory.

#### Production angle

Understanding the JMM prevents common mistakes such as unsafe lazy initialization, non-volatile stop flags and incorrect double-checked locking.

#### Traps / caveats

- The JMM is a specification-level model, not a picture of RAM.
- Tests may pass despite missing happens-before.
- Logging and debugging can accidentally change timing.

#### Optional Anki

Q: What does the JMM define?
A: Visibility and ordering rules for memory shared between threads.

</details>

<a id="mt-jmm-002"></a>

<details>
<summary><strong>MT-JMM-002. What is the happens-before relationship, and why does it matter?</strong></summary>

#### Short answer

Happens-before is a JMM ordering relation that guarantees visibility of earlier writes to later actions.

#### Interview answer

If action A happens-before action B, then effects of A are visible to B and A is ordered before B for memory consistency. It does not necessarily mean A happened earlier in wall-clock time; it is a rule for legal observations.

Examples include unlocking a monitor before another thread locks the same monitor, writing to a volatile field before another thread reads it, and actions before `Thread.start()` being visible to the started thread.

#### Deep dive

Happens-before is transitive. If A happens-before B and B happens-before C, then A happens-before C.

#### Production angle

Use happens-before to reason about publication, shutdown flags, executor handoff and visibility after `join()`.

#### Traps / caveats

- Time order is not enough.
- Sleeping does not create happens-before.
- Thread-safe handoff mechanisms are often easier than manual reasoning.

#### Optional Anki

Q: What does happens-before guarantee?
A: Ordering and visibility for memory effects.

</details>

<a id="mt-jmm-003"></a>

<details>
<summary><strong>MT-JMM-003. What happens-before rules matter most in everyday Java backend code?</strong></summary>

#### Short answer

The most common rules involve thread start, thread join, volatile read/write, monitor unlock/lock, final fields, class initialization and concurrent utilities.

#### Interview answer

Actions before `Thread.start()` are visible to the new thread. A thread's actions happen-before another thread successfully returns from `join()`. A volatile write happens-before a later volatile read of the same variable. Exiting a synchronized block happens-before a later synchronized block on the same monitor.

Thread-safe queues, futures, latches and executor handoff also provide memory-consistency guarantees through their APIs.

#### Deep dive

Class initialization safely publishes static final constants. Final fields have special initialization safety when the object is constructed correctly.

#### Production angle

Prefer higher-level utilities like `BlockingQueue`, `Future`, `CompletableFuture`, latches and executors over ad hoc flags and sleeps.

#### Traps / caveats

- The lock object must be the same.
- The volatile field must be the same field.
- Safe publication does not make later mutation safe.

#### Optional Anki

Q: Does `Thread.sleep()` publish writes?
A: No.

</details>

<a id="mt-jmm-004"></a>

<details>
<summary><strong>MT-JMM-004. What guarantees does `volatile` provide, and what does it not provide?</strong></summary>

#### Short answer

`volatile` provides visibility and ordering for reads and writes of one variable, but it does not make compound actions atomic.

#### Interview answer

When one thread writes a volatile field, another thread reading that same field sees the latest write according to the volatile ordering rules. Volatile is useful for simple state flags, one-time publication patterns and references to immutable snapshots.

It does not protect multi-step updates like `count++`, check-then-act logic, or invariants involving several fields.

#### Deep dive

Volatile read/write has memory effects similar to acquire/release boundaries around that variable. It is lighter than a lock but less expressive.

#### Production angle

Use volatile for simple visibility, not as a replacement for locking business invariants.

#### Traps / caveats

- `volatile` does not make `ArrayList` thread-safe.
- `volatile` references do not make referenced objects immutable.
- Multiple volatile fields do not automatically form one atomic state.

#### Optional Anki

Q: Main limitation of `volatile`?
A: It does not make compound actions atomic.

</details>

<a id="mt-jmm-005"></a>

<details>
<summary><strong>MT-JMM-005. Why is `volatile` not enough for compound actions like `count++`?</strong></summary>

#### Short answer

Because `count++` is a read-modify-write sequence, not one atomic operation.

#### Interview answer

`count++` reads the current value, adds one, and writes the new value. With a volatile field, each read and write is visible, but two threads can read the same old value and both write the same incremented value. One update is lost.

Use `AtomicInteger.incrementAndGet()`, `LongAdder`, or a lock depending on the required semantics.

#### Deep dive

Volatile fixes stale reads but not interleaving. Atomic classes use CAS or other internal coordination to make the update atomic.

#### Production angle

Lost updates show up in counters, rate limits, cache statistics and sequence generation. Choose the primitive based on whether exactness and contention matter.

#### Traps / caveats

- `++`, `+=`, check-then-act and lazy init are compound.
- `AtomicLong` can contend heavily under high write load.
- `LongAdder` is great for statistics, not strict sequencing.

#### Optional Anki

Q: Why can volatile increments lose updates?
A: Visibility does not make read-modify-write atomic.

</details>

<a id="mt-jmm-006"></a>

<details>
<summary><strong>MT-JMM-006. What is the difference between `synchronized` and `volatile`?</strong></summary>

#### Short answer

`synchronized` provides mutual exclusion and visibility. `volatile` provides visibility and ordering for one variable without mutual exclusion.

#### Interview answer

Use `synchronized` when a block of code must execute atomically or protect an invariant. It ensures only one thread holds the monitor and it publishes changes at lock boundaries.

Use `volatile` for simple state publication such as a stop flag or current immutable snapshot reference, where no compound invariant needs protection.

#### Deep dive

Both create happens-before relationships, but with different mechanisms: unlock/lock on the same monitor versus write/read of the same volatile field.

#### Production angle

For business state, prefer clarity. A small synchronized block is often safer than clever volatile logic.

#### Traps / caveats

- Volatile does not guard a critical section.
- Synchronizing on different objects gives no protection.
- Locks can hurt scalability if held too long.

#### Optional Anki

Q: Which gives mutual exclusion: `volatile` or `synchronized`?
A: `synchronized`.

</details>

<a id="mt-jmm-007"></a>

<details>
<summary><strong>MT-JMM-007. What is safe publication?</strong></summary>

#### Short answer

Safe publication means making an object reference visible to other threads so they see a correctly initialized object.

#### Interview answer

If an object is constructed in one thread and used in another, the receiving thread must not see a partially initialized state. Safe publication can happen through class initialization, final fields, volatile references, locks, thread-safe collections or concurrency utilities.

Immutable objects are easier to publish safely, but changing the reference to a new immutable object still needs visibility.

#### Deep dive

Publication is about both the reference and the object state reachable through it. Mutable reachable state still needs its own thread-safety policy.

#### Production angle

Safe publication matters for caches, configuration snapshots, singleton initialization and objects submitted to executors.

#### Traps / caveats

- Assigning to an ordinary shared field is not always safe publication.
- Publishing `this` from a constructor is dangerous.
- Safe publication does not protect later mutation.

#### Optional Anki

Q: Name one safe-publication mechanism.
A: A volatile reference, lock, static initialization or thread-safe collection.

</details>

<a id="mt-jmm-008"></a>

<details>
<summary><strong>MT-JMM-008. What can go wrong if `this` escapes during construction?</strong></summary>

#### Short answer

Another thread can observe the object before construction is complete.

#### Interview answer

`this` escapes when the constructor publishes the object before it finishes, for example by registering a listener, starting a thread, submitting a task, or storing `this` in a shared static collection. Another thread may see default values, broken invariants or fields that are not safely initialized.

This also weakens the practical safety of final-field initialization guarantees.

#### Deep dive

Constructors should build the object, not start concurrent behavior that can call back into the object.

#### Production angle

This bug appears in listener registration, Spring lifecycle hooks, metrics callbacks and async startup code.

#### Traps / caveats

- Starting a thread in a constructor is risky.
- Passing `this` to overridable methods can also expose incomplete state.
- Factories can separate construction from registration.

#### Optional Anki

Q: What is constructor escape?
A: Publishing `this` before the constructor finishes.

</details>

<a id="mt-jmm-009"></a>

<details>
<summary><strong>🧠 MT-JMM-009. What special visibility guarantees do `final` fields have?</strong></summary>

#### Short answer

Correctly initialized final fields are guaranteed to be visible after construction, assuming `this` does not escape.

#### Interview answer

The JMM gives final fields initialization safety. If an object is constructed properly, other threads that obtain the reference will see the values assigned to final fields in the constructor. This is one reason immutable objects with final fields are reliable to share.

The guarantee does not make mutable objects referenced by final fields safe for later mutation.

#### Deep dive

Final-field semantics cover initialization, not arbitrary future updates. Non-final lazy caches and mutable collections inside the object still need normal synchronization or defensive copying.

#### Production angle

Use final fields heavily in immutable DTOs, configuration snapshots, value objects and cache keys.

#### Traps / caveats

- `final List<T>` does not make the list immutable.
- Constructor escape can break assumptions.
- Reflection and unsafe mechanisms can complicate guarantees.

#### Optional Anki

Q: Main condition for final-field visibility guarantees?
A: The object must be constructed correctly and `this` must not escape.

</details>

<a id="mt-jmm-010"></a>

<details>
<summary><strong>🧠 MT-JMM-010. What is double-checked locking, and why does it require `volatile`?</strong></summary>

#### Short answer

Double-checked locking lazily initializes a shared value with an outer null check and an inner locked check. The shared reference must be volatile for safe publication.

#### Interview answer

The pattern avoids locking after initialization:

```java
if (instance == null) {
    synchronized (lock) {
        if (instance == null) {
            instance = new Service();
        }
    }
}
```

Without `volatile`, another thread can observe the reference before the constructed object's state is safely visible. Volatile prevents unsafe publication of the reference.

#### Deep dive

Often simpler alternatives are better: eager initialization, enum singleton, static holder idiom or dependency injection.

#### Production angle

Incorrect lazy initialization can produce rare startup or first-request failures that disappear under debugging.

#### Traps / caveats

- The second null check is required.
- The reference must be volatile.
- Avoid hand-written lazy init unless it is really needed.

#### Optional Anki

Q: Why does DCL need `volatile`?
A: To safely publish the initialized object reference.

</details>

<a id="mt-jmm-011"></a>

<details>
<summary><strong>🧠 MT-JMM-011. How would you explain the JMM without treating "flush to main memory" as a literal implementation detail?</strong></summary>

#### Short answer

Explain it as a set of visibility and ordering guarantees, not as literal copying between thread caches and main memory.

#### Interview answer

The useful interview explanation is: the JMM defines which writes one thread is guaranteed to observe from another thread. Synchronization actions such as volatile reads/writes, monitor lock/unlock, thread start and join create happens-before relationships.

Implementation may involve CPU caches, compiler barriers and hardware fences, but the Java programmer should reason in terms of happens-before and safe publication.

#### Deep dive

"Flush to main memory" is an oversimplification because modern CPUs and JVMs do not operate as a simple per-thread cache copied to RAM. The spec is about legal observations.

#### Production angle

Using the correct model helps avoid unreliable fixes like adding sleeps, logging or arbitrary reads to "force visibility."

#### Traps / caveats

- Do not reason from one machine's behavior.
- Sleeps and yields are not memory barriers.
- The same bug can disappear after adding logs.

#### Optional Anki

Q: Better mental model for the JMM?
A: Happens-before visibility and ordering guarantees.

</details>
