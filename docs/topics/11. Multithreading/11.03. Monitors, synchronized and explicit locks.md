# 11.03. Monitors, `synchronized` and explicit locks

---

<a id="mt-lock-001"></a>

<details>
<summary><strong>MT-LOCK-001. What are a monitor and an intrinsic lock in Java?</strong></summary>

#### Short answer

Every Java object can be used as a monitor, and its intrinsic lock is the built-in lock used by `synchronized`.

#### Interview answer

When a thread enters a synchronized block or method, it acquires the monitor associated with the target object. Only one thread can own that monitor at a time. Other threads trying to enter synchronized code guarded by the same object must wait.

The monitor also supports condition-style coordination through `wait()`, `notify()` and `notifyAll()`.

#### Deep dive

The lock protects only code that uses the same monitor object. Synchronizing on different objects gives no mutual exclusion.

#### Production angle

Use clear, private lock objects when the lock is part of your class's internal implementation.

#### Traps / caveats

- Every object can be a lock, but not every object should be used as one.
- Lock identity matters.
- Holding locks during slow I/O hurts scalability.

#### Optional Anki

Q: What does `synchronized(lock)` acquire?
A: The intrinsic lock for `lock`.

</details>

---

<a id="mt-lock-002"></a>

<details>
<summary><strong>MT-LOCK-002. What object is locked by `synchronized` instance methods, static methods and blocks?</strong></summary>

#### Short answer

An instance synchronized method locks `this`; a static synchronized method locks the `Class` object; a synchronized block locks the object in parentheses.

#### Interview answer

`synchronized void m()` is equivalent to synchronizing on the current instance. `static synchronized void m()` synchronizes on `MyClass.class`. A block such as `synchronized (lock) { ... }` uses exactly the object referenced by `lock`.

This distinction matters because only code locking the same object coordinates with each other.

#### Deep dive

Two different instances with synchronized instance methods do not block each other. Static synchronized methods do coordinate across all instances of that class.

#### Production angle

Make the lock choice explicit in code reviews. Accidental use of `this` can expose lock ownership to external callers.

#### Traps / caveats

- Static and instance locks are different.
- Reassigning a lock reference can break synchronization.
- Locking boxed primitives or strings is dangerous.

#### Optional Anki

Q: What does a static synchronized method lock?
A: The class object, such as `MyClass.class`.

</details>

<a id="mt-lock-003"></a>

<details>
<summary><strong>MT-LOCK-003. Why might a private lock object be better than synchronizing on `this`, a `String` literal or a public object?</strong></summary>

#### Short answer

A private lock prevents outside code from accidentally or maliciously using the same lock.

#### Interview answer

Synchronizing on `this` exposes your lock to any code that has the object reference. Synchronizing on a public object has the same problem. `String` literals are interned, so unrelated code can accidentally share the same lock.

A `private final Object lock = new Object();` makes lock ownership local and easier to reason about.

#### Deep dive

Private locks reduce lock-order surprises and external blocking. They also let you document exactly which state the lock protects.

#### Production angle

Unexpected external lock usage can cause rare deadlocks and latency spikes that are hard to trace.

#### Traps / caveats

- The lock object should be `final`.
- Do not expose it through getters.
- Do not lock on mutable or pooled objects.

#### Optional Anki

Q: Why avoid locking on string literals?
A: Interning can make unrelated code share the same lock.

</details>

<a id="mt-lock-004"></a>

<details>
<summary><strong>MT-LOCK-004. What does it mean that `synchronized` and `ReentrantLock` are reentrant?</strong></summary>

#### Short answer

Reentrant means a thread that already owns the lock can acquire it again.

#### Interview answer

If a synchronized method calls another synchronized method on the same object, the same thread can enter without deadlocking itself. The JVM tracks a hold count and releases the lock only when the matching number of exits occurs. `ReentrantLock` behaves similarly with explicit `lock()` and `unlock()` calls.

#### Deep dive

Reentrancy helps object-oriented code because public synchronized methods can call private synchronized helpers. It does not prevent deadlocks involving multiple locks.

#### Production angle

Reentrancy is convenient, but deep reentrant call chains can make lock scope harder to see.

#### Traps / caveats

- Reentrant does not mean safe from deadlock.
- `ReentrantLock` must be unlocked the same number of times.
- Reentrancy can hide overly broad locking.

#### Optional Anki

Q: Can a thread re-enter a synchronized block guarded by a lock it already owns?
A: Yes.

</details>

<a id="mt-lock-005"></a>

<details>
<summary><strong>MT-LOCK-005. What visibility guarantees does `synchronized` provide?</strong></summary>

#### Short answer

Unlocking a monitor happens-before a later lock of the same monitor.

#### Interview answer

When a thread exits a synchronized block, its writes inside and before the block become visible to a later thread that enters a synchronized block guarded by the same monitor. This is why `synchronized` provides both mutual exclusion and visibility.

The guarantee depends on using the same lock consistently for all accesses to the protected state.

#### Deep dive

Locking only writes but reading without the same lock can still be unsafe. Every access participating in the invariant should follow the same synchronization policy.

#### Production angle

Document which fields are guarded by which lock. This makes code review and thread-dump analysis easier.

#### Traps / caveats

- Same monitor is required.
- Visibility does not help if some paths bypass the lock.
- Holding a lock too long can block unrelated work.

#### Optional Anki

Q: What happens-before rule does `synchronized` create?
A: Unlock happens-before later lock on the same monitor.

</details>

<a id="mt-lock-006"></a>

<details>
<summary><strong>MT-LOCK-006. What are `wait()`, `notify()` and `notifyAll()` used for?</strong></summary>

#### Short answer

They coordinate threads waiting for a condition protected by a monitor.

#### Interview answer

`wait()` releases the monitor and suspends the current thread until it is notified, interrupted or times out. `notify()` wakes one waiting thread. `notifyAll()` wakes all waiting threads. They are low-level condition coordination tools tied to intrinsic locks.

They should be used around a real condition, not as a general message mechanism.

#### Deep dive

Modern code often uses higher-level utilities such as `BlockingQueue`, `CountDownLatch`, `Semaphore`, `Condition` or futures instead of raw wait/notify.

#### Production angle

Correct wait/notify code needs lifecycle, interruption, timeouts and shutdown behavior.

#### Traps / caveats

- `wait()` releases the monitor.
- `notify()` does not release the monitor immediately.
- Notifications can be missed if the condition is not checked correctly.

#### Optional Anki

Q: What does `wait()` release?
A: The monitor lock.

</details>

<a id="mt-lock-007"></a>

<details>
<summary><strong>MT-LOCK-007. Why must `wait()`, `notify()` and `notifyAll()` be called while holding the monitor?</strong></summary>

#### Short answer

Because they operate on the monitor's wait set and must be coordinated with the protected condition.

#### Interview answer

Java requires the current thread to own the object's monitor before calling `wait()`, `notify()` or `notifyAll()`. Otherwise it throws `IllegalMonitorStateException`.

More importantly, holding the monitor ensures the condition check, state change and wait/notify operation are atomic relative to other synchronized code using the same monitor.

#### Deep dive

The standard pattern is: acquire lock, check condition in a loop, wait while false, then proceed. Producers change state under the same lock and notify.

#### Production angle

Getting this wrong can produce rare hangs, missed signals or corrupted producer-consumer state.

#### Traps / caveats

- Locking the wrong object is equivalent to not locking.
- `notify()` before a thread waits can be lost.
- Use higher-level primitives when possible.

#### Optional Anki

Q: Exception when calling `wait()` without owning monitor?
A: `IllegalMonitorStateException`.

</details>

<a id="mt-lock-008"></a>

<details>
<summary><strong>MT-LOCK-008. What is the difference between `wait()` and `sleep()`?</strong></summary>

#### Short answer

`wait()` releases the monitor and waits for coordination. `sleep()` pauses the current thread and keeps any locks it holds.

#### Interview answer

`wait()` must be called while holding a monitor and is used to wait for a condition related to that monitor. While waiting, the thread releases the monitor so other threads can change the condition.

`Thread.sleep()` is just a timed pause. It does not require a monitor and does not release locks.

#### Deep dive

Both can be interrupted. `wait()` is a coordination primitive; `sleep()` is not a reliable coordination mechanism.

#### Production angle

Sleeping while holding a lock can block progress and increase latency. Sleeping to "wait until something happens" is usually a flaky design.

#### Traps / caveats

- `sleep()` does not publish state.
- `wait()` should be in a condition loop.
- Timed waits still need condition checks.

#### Optional Anki

Q: Which releases a monitor: `wait()` or `sleep()`?
A: `wait()`.

</details>

<a id="mt-lock-009"></a>

<details>
<summary><strong>MT-LOCK-009. What is the difference between `notify()` and `notifyAll()`?</strong></summary>

#### Short answer

`notify()` wakes one waiting thread; `notifyAll()` wakes all waiting threads waiting on that monitor.

#### Interview answer

Use `notify()` only when one waiting thread is definitely enough and all waiters are waiting for the same condition. Use `notifyAll()` when different conditions may be involved or when waking the wrong single waiter could cause progress problems.

After notification, awakened threads still must reacquire the monitor and re-check the condition.

#### Deep dive

`notifyAll()` can cause extra wakeups, but it is often safer for correctness in complex guarded blocks.

#### Production angle

Prefer higher-level queues and synchronizers. They encode these policies more safely.

#### Traps / caveats

- Notification is not a stored message.
- Awakened thread may still not be able to proceed.
- `notify()` can cause missed progress in multi-condition code.

#### Optional Anki

Q: Safer default for complex wait conditions?
A: `notifyAll()`.

</details>

<a id="mt-lock-010"></a>

<details>
<summary><strong>🧠 MT-LOCK-010. Why should `wait()` normally be used inside a `while` loop?</strong></summary>

#### Short answer

Because a thread can wake up even when the condition is still false.

#### Interview answer

The condition must be checked before and after waiting:

```java
synchronized (lock) {
    while (!condition) {
        lock.wait();
    }
}
```

The loop handles spurious wakeups, notifications meant for other conditions, timeouts, interrupts and races where another thread consumes the state first.

#### Deep dive

The condition, not the notification, decides whether the thread can proceed. Notifications are only hints to re-check.

#### Production angle

Using `if` instead of `while` can cause rare incorrect behavior under load.

#### Traps / caveats

- Spurious wakeups are allowed.
- `notifyAll()` wakes threads whose condition may still be false.
- Conditions must be protected by the same lock.

#### Optional Anki

Q: Why `while`, not `if`, around `wait()`?
A: To re-check the condition after every wakeup.

</details>

<a id="mt-lock-011"></a>

<details>
<summary><strong>MT-LOCK-011. What is a guarded block, and how would you implement a bounded buffer with `wait()` and `notifyAll()`?</strong></summary>

#### Short answer

A guarded block waits until a condition protected by a lock becomes true.

#### Interview answer

A bounded buffer has producers wait while the queue is full and consumers wait while it is empty. Both conditions are checked in loops under the same lock. Producers add an item and call `notifyAll()`. Consumers remove an item and call `notifyAll()`.

This coordinates capacity and availability.

#### Deep dive

Correct implementation must handle interruption and shutdown. It should avoid calling slow external code while holding the buffer lock.

#### Production angle

In real backend code, prefer `ArrayBlockingQueue` or `LinkedBlockingQueue` unless writing the primitive is the interview task.

#### Traps / caveats

- Use `while`, not `if`.
- Use `notifyAll()` for full/empty dual conditions.
- Bounded queues need a policy for shutdown and rejection.

#### Optional Anki

Q: What Java utility usually replaces a hand-written bounded buffer?
A: `BlockingQueue`.

</details>

<a id="mt-lock-012"></a>

<details>
<summary><strong>MT-LOCK-012. How can locks cause deadlocks, and how can lock ordering prevent them?</strong></summary>

#### Short answer

Deadlock can happen when threads wait forever for locks held by each other. A consistent global lock order prevents circular waits.

#### Interview answer

If thread A holds lock 1 and waits for lock 2 while thread B holds lock 2 and waits for lock 1, neither can proceed. One prevention technique is to always acquire locks in the same order everywhere.

Deadlock requires mutual exclusion, hold-and-wait, no preemption and circular wait. Breaking any condition prevents deadlock.

#### Deep dive

Other strategies include reducing lock scope, using `tryLock()` with timeout, avoiding nested locks or redesigning ownership.

#### Production angle

Thread dumps can often identify deadlocked monitors and owning threads. Capture dumps before restarting the process.

#### Traps / caveats

- Ordering must be consistent across the whole codebase.
- Database locks and JVM locks can combine into deadlocks.
- Timeouts turn deadlock into failure handling, not correctness by themselves.

#### Optional Anki

Q: Which deadlock condition does lock ordering break?
A: Circular wait.

</details>

<a id="mt-lock-013"></a>

<details>
<summary><strong>MT-LOCK-013. What is the difference between `synchronized` and `ReentrantLock`?</strong></summary>

#### Short answer

`synchronized` is built into the language; `ReentrantLock` is an explicit lock with more features.

#### Interview answer

`synchronized` is simpler and automatically releases the monitor when leaving the block. `ReentrantLock` must be unlocked in `finally`, but it supports interruptible lock acquisition, timed `tryLock()`, optional fairness, multiple `Condition`s and some introspection methods.

Use `synchronized` for simple mutual exclusion. Use `ReentrantLock` when the extra behavior is needed.

#### Deep dive

Since JDK 24, virtual-thread pinning is no longer a reason by itself to replace ordinary synchronized code with `ReentrantLock`.

#### Production angle

The best lock is usually the simplest one that expresses the required semantics and is easy for the team to maintain.

#### Traps / caveats

- Forgetting `unlock()` causes permanent blocking.
- Fair locks can reduce throughput.
- More flexible locks are easier to misuse.

#### Optional Anki

Q: Why use `ReentrantLock` over `synchronized`?
A: Timed, interruptible, fair locking or multiple conditions.

</details>

<a id="mt-lock-014"></a>

<details>
<summary><strong>MT-LOCK-014. When are `tryLock()`, `lockInterruptibly()` and fair locks useful?</strong></summary>

#### Short answer

They are useful when waiting for a lock needs timeout, cancellation or stricter acquisition order.

#### Interview answer

`tryLock()` attempts acquisition without waiting forever, optionally with a timeout. It can help avoid deadlock or return a controlled failure. `lockInterruptibly()` lets a waiting thread respond to interruption, which is important for cancellation and shutdown. A fair lock tries to grant access in waiting order.

#### Deep dive

Fairness can reduce starvation but often reduces throughput because it limits barging and scheduler flexibility.

#### Production angle

Timed lock acquisition is useful in systems that must fail fast rather than hang indefinitely.

#### Traps / caveats

- Always release a successfully acquired lock.
- Timeout handling must leave state consistent.
- Fairness is not a general performance optimization.

#### Optional Anki

Q: Which lock method supports interruption while waiting?
A: `lockInterruptibly()`.

</details>

<a id="mt-lock-015"></a>

<details>
<summary><strong>MT-LOCK-015. How is `Condition` different from `wait()`/`notify()`?</strong></summary>

#### Short answer

`Condition` is the explicit-lock equivalent of monitor wait sets, with support for multiple condition queues per lock.

#### Interview answer

With `ReentrantLock`, you create conditions using `newCondition()`. Threads call `await()`, `signal()` and `signalAll()`. Unlike an object's single wait set, one lock can have several conditions, such as `notFull` and `notEmpty` in a bounded buffer.

This can reduce unnecessary wakeups and make intent clearer.

#### Deep dive

`await()` releases the associated lock while waiting and reacquires it before returning, similar to `wait()`.

#### Production angle

Use `Condition` when raw monitor methods are too limited but a higher-level queue is not a fit.

#### Traps / caveats

- The associated lock must be held.
- Use loops around `await()`.
- Signal the right condition.

#### Optional Anki

Q: Main advantage of `Condition`?
A: Multiple wait queues for one explicit lock.

</details>

<a id="mt-lock-016"></a>

<details>
<summary><strong>MT-LOCK-016. When does `ReadWriteLock` help, and when can it make performance worse?</strong></summary>

#### Short answer

It can help when reads dominate and are long enough to benefit from concurrent read access. It can hurt when writes are frequent or critical sections are tiny.

#### Interview answer

`ReadWriteLock` allows multiple readers or one writer. It helps for read-heavy shared state where reads need locking and writes are relatively rare. It can be worse when contention is low, writes are frequent, upgrade patterns are complex or lock overhead exceeds the benefit.

#### Deep dive

Reader-writer locks can also suffer from writer starvation depending on fairness policy and workload.

#### Production angle

Measure before replacing a simple lock. Immutable snapshots through `AtomicReference` are often simpler for read-mostly state.

#### Traps / caveats

- Lock upgrade can deadlock if done incorrectly.
- More lock types make code harder to review.
- Concurrent reads are useful only if reads are actually protected and meaningful.

#### Optional Anki

Q: Best workload for `ReadWriteLock`?
A: Many reads, few writes, meaningful read critical sections.

</details>

<a id="mt-lock-017"></a>

<details>
<summary><strong>🧠 MT-LOCK-017. What is `StampedLock`, and what are its pitfalls?</strong></summary>

#### Short answer

`StampedLock` is a lock supporting write, read and optimistic read modes, but it is easier to misuse than simpler locks.

#### Interview answer

`StampedLock` can improve some read-heavy workloads with optimistic reads. An optimistic read obtains a stamp, reads data, then validates that no write occurred. If validation fails, the code must retry under a proper read lock.

It is not reentrant, uses stamps that must be handled correctly, and can make code harder to maintain.

#### Deep dive

Optimistic reads are only safe when all read data is validated before being trusted. Complex object graphs make this tricky.

#### Production angle

Use it only after measuring contention and proving simpler designs are not enough.

#### Traps / caveats

- It is not reentrant.
- Incorrect validation gives stale or inconsistent reads.
- Always unlock with the correct stamp.

#### Optional Anki

Q: What must optimistic reads in `StampedLock` do?
A: Validate the stamp before trusting the read data.

</details>
