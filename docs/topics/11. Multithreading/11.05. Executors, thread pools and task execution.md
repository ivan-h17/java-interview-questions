# 11.05. Executors, thread pools and task execution

---

<a id="mt-exec-001"></a>

<details>
<summary><strong>MT-EXEC-001. What is a thread pool, and why do backend services use thread pools?</strong></summary>

#### Short answer

A thread pool reuses worker threads to execute tasks and control concurrency.

#### Interview answer

Creating platform threads for every task is expensive and can overwhelm the OS. A thread pool keeps a bounded set of workers, accepts tasks and runs them according to queueing and rejection rules.

Backend services use pools to handle requests, async work, scheduled jobs, message processing and external calls while limiting resource usage.

#### Deep dive

A pool is also a backpressure boundary. Its size, queue and rejection policy decide what happens under overload.

#### Production angle

Every important pool should have clear ownership, naming, lifecycle, metrics and overload behavior.

#### Traps / caveats

- A thread pool does not create unlimited capacity.
- Unbounded queues can hide overload.
- Sharing one pool across unrelated work creates coupling.

#### Optional Anki

Q: Why use a thread pool?
A: To reuse threads and control concurrency.

</details>

<a id="mt-exec-002"></a>

<details>
<summary><strong>MT-EXEC-002. What is the difference between `Executor`, `ExecutorService` and `ThreadPoolExecutor`?</strong></summary>

#### Short answer

`Executor` runs commands, `ExecutorService` adds lifecycle and futures, and `ThreadPoolExecutor` is the configurable pool implementation.

#### Interview answer

`Executor` has a simple `execute(Runnable)` method. `ExecutorService` adds `submit`, `shutdown`, `invokeAll`, `Future` results and lifecycle management. `ThreadPoolExecutor` is the concrete class where you configure core size, max size, keep-alive, queue, thread factory and rejection policy.

#### Deep dive

Factory methods in `Executors` return preconfigured executors, but some hide dangerous defaults such as unbounded queues.

#### Production angle

For production services, explicit `ThreadPoolExecutor` configuration is often clearer than using convenience factories.

#### Traps / caveats

- `Executor` has no shutdown method.
- `submit()` hides task exceptions in the returned `Future`.
- Defaults should be reviewed, not assumed.

#### Optional Anki

Q: Which type exposes pool sizing and queue configuration?
A: `ThreadPoolExecutor`.

</details>

<a id="mt-exec-003"></a>

<details>
<summary><strong>MT-EXEC-003. What is the difference between `execute()` and `submit()`, especially for exception handling?</strong></summary>

#### Short answer

`execute()` runs a `Runnable` without returning a result. `submit()` returns a `Future` and captures exceptions inside it.

#### Interview answer

With `execute()`, an uncaught runtime exception from the task reaches the thread's uncaught exception handling path and may be logged by the executor/thread. With `submit()`, the exception is stored in the `Future`; it is rethrown only when calling `get()` as an `ExecutionException`.

If you ignore the future, you can lose the failure.

#### Deep dive

`submit()` also accepts `Callable<T>` and returns a typed result. `execute()` is fire-and-forget at the API level.

#### Production angle

Important async work should have explicit error handling, logging, metrics and retry/dead-letter policy.

#### Traps / caveats

- Ignored futures hide exceptions.
- Fire-and-forget is risky for business side effects.
- Logging in the task may duplicate logs if callers also handle failures.

#### Optional Anki

Q: Where does `submit()` store task exceptions?
A: In the returned `Future`.

</details>

<a id="mt-exec-004"></a>

<details>
<summary><strong>MT-EXEC-004. What are the risks of blocking on `Future.get()`, and what does `cancel(true)` mean?</strong></summary>

#### Short answer

`Future.get()` blocks the caller. `cancel(true)` requests cancellation and may interrupt the running task.

#### Interview answer

Blocking on `get()` ties up the calling thread and can cause thread starvation, especially when tasks wait for other tasks in the same pool. Use timeouts where possible.

`cancel(true)` means cancel if not started, or interrupt the running thread if already running. It does not guarantee the task stops; the task must cooperate with interruption.

#### Deep dive

`cancel(false)` cancels only if the task has not started. Once running, cancellation depends on task code and blocking APIs.

#### Production angle

Use deadlines and cancellation propagation for request fan-out. Never wait forever in request or shutdown paths.

#### Traps / caveats

- `get()` without timeout can hang forever.
- `cancel(true)` is not `Thread.stop()`.
- Blocking in the same pool can deadlock.

#### Optional Anki

Q: Does `cancel(true)` forcibly kill a thread?
A: No, it requests interruption.

</details>

<a id="mt-exec-005"></a>

<details>
<summary><strong>MT-EXEC-005. How do `corePoolSize`, `maximumPoolSize`, `keepAliveTime` and the work queue interact?</strong></summary>

#### Short answer

The pool creates core threads first, then queues tasks, then may grow toward maximum depending on queue type and saturation.

#### Interview answer

`ThreadPoolExecutor` creates workers up to `corePoolSize`. After that, new tasks usually go into the queue. If the queue cannot accept more tasks, the pool may create additional threads up to `maximumPoolSize`. If both queue and max threads are exhausted, rejection occurs. Threads above core can be removed after `keepAliveTime`.

#### Deep dive

With an unbounded queue, `maximumPoolSize` is often irrelevant because the queue never fills.

#### Production angle

Pool behavior is determined by size plus queue plus rejection policy. Review all three together.

#### Traps / caveats

- Unbounded queues can cause memory pressure.
- Large max size can cause too many threads.
- Queueing increases latency.

#### Optional Anki

Q: When does a pool grow beyond core size?
A: Usually when the queue is full and max size allows more threads.

</details>

<a id="mt-exec-006"></a>

<details>
<summary><strong>MT-EXEC-006. What is the difference between bounded and unbounded executor queues?</strong></summary>

#### Short answer

A bounded queue limits backlog; an unbounded queue can grow until memory or latency collapses.

#### Interview answer

Bounded queues make overload visible. When full, the application must block, reject, shed load or apply another policy. Unbounded queues avoid immediate rejection but can accumulate tasks faster than workers process them.

That increases latency, memory usage and failure amplification.

#### Deep dive

Queue capacity is part of the service's concurrency contract. It should reflect acceptable waiting time and memory footprint.

#### Production angle

For request-driven systems, bounded queues plus clear rejection often fail faster and recover better.

#### Traps / caveats

- Unbounded does not mean safe.
- Huge queues can violate timeouts before work starts.
- Queue size metrics are required.

#### Optional Anki

Q: Main risk of unbounded executor queues?
A: Hidden overload leading to memory pressure and high latency.

</details>

<a id="mt-exec-007"></a>

<details>
<summary><strong>MT-EXEC-007. What happens when an executor queue is full, and what are common rejection policies?</strong></summary>

#### Short answer

When the queue is full and the pool cannot grow, the executor calls its `RejectedExecutionHandler`.

#### Interview answer

Common policies are abort with `RejectedExecutionException`, run the task in the caller thread, discard the task or discard the oldest queued task. The right policy depends on workload semantics.

For backend request handling, rejection should usually become a controlled failure such as HTTP 429/503 rather than silently dropping important work.

#### Deep dive

`CallerRunsPolicy` applies backpressure to submitters but can also block event loops or request threads if used carelessly.

#### Production angle

Rejections should be counted, logged at a controlled rate and reflected in SLO/error metrics.

#### Traps / caveats

- Silent discard loses work.
- Caller-runs can spread latency upstream.
- Retrying rejected work immediately can create storms.

#### Optional Anki

Q: Default rejection policy?
A: Abort with `RejectedExecutionException`.

</details>

<a id="mt-exec-008"></a>

<details>
<summary><strong>MT-EXEC-008. What are the risks of `Executors.newFixedThreadPool()` and `Executors.newCachedThreadPool()`?</strong></summary>

#### Short answer

`newFixedThreadPool()` uses an unbounded queue; `newCachedThreadPool()` can create too many threads.

#### Interview answer

`newFixedThreadPool(n)` limits workers but uses an unbounded `LinkedBlockingQueue`, so overload becomes queue growth and latency. `newCachedThreadPool()` uses a direct handoff queue and can create a large number of threads under bursty blocking work.

Both are convenient but often too implicit for production.

#### Deep dive

These factories hide key choices: queue capacity, thread naming, rejection policy and lifecycle.

#### Production angle

Prefer explicit `ThreadPoolExecutor` configuration for services where overload behavior matters.

#### Traps / caveats

- Fixed pool can run out of memory through queued tasks.
- Cached pool can exhaust threads or downstream resources.
- Defaults rarely match SLOs.

#### Optional Anki

Q: Hidden risk of `newFixedThreadPool`?
A: Unbounded queue.

</details>

<a id="mt-exec-009"></a>

<details>
<summary><strong>MT-EXEC-009. What is the difference between `scheduleAtFixedRate()` and `scheduleWithFixedDelay()`?</strong></summary>

#### Short answer

Fixed rate schedules based on start times. Fixed delay waits a delay after one run finishes before starting the next.

#### Interview answer

`scheduleAtFixedRate()` tries to maintain a regular period. If a run is slow, the next run may start immediately after it finishes, but executions of the same task do not overlap in a single-threaded scheduled executor. `scheduleWithFixedDelay()` spaces executions by waiting after completion.

#### Deep dive

If a scheduled task throws an uncaught exception, later executions can be suppressed.

#### Production angle

Scheduled backend jobs need timeouts, error handling, metrics and cluster coordination if multiple instances run.

#### Traps / caveats

- Fixed rate can bunch executions after delays.
- Fixed delay drifts with task duration.
- Scheduled jobs should not run forever without cancellation.

#### Optional Anki

Q: Which waits after task completion?
A: `scheduleWithFixedDelay()`.

</details>

<a id="mt-exec-010"></a>

<details>
<summary><strong>MT-EXEC-010. How should thread pool sizing differ for CPU-bound and I/O-bound work?</strong></summary>

#### Short answer

CPU-bound pools should be near available cores. I/O-bound pools may be larger but must respect downstream limits.

#### Interview answer

CPU-bound tasks need CPU time, so too many threads mostly add context switching. Start around the number of available cores and measure. I/O-bound tasks spend time waiting, so more threads can improve throughput, but only until another resource becomes the bottleneck: DB pool, remote service, network or memory.

#### Deep dive

Classic sizing formulas are starting points, not guarantees. Real workloads include mixed CPU, blocking, queueing and tail latency.

#### Production angle

Pool size should be validated with load tests and production metrics, not copied from examples.

#### Traps / caveats

- More I/O threads can overload dependencies.
- CPU-heavy work in request pools hurts latency.
- Container CPU limits affect effective core count.

#### Optional Anki

Q: CPU-bound pool starting point?
A: Around available processor cores, then measure.

</details>

<a id="mt-exec-011"></a>

<details>
<summary><strong>MT-EXEC-011. Why is "one pool for everything" often a bad design?</strong></summary>

#### Short answer

It lets one slow or noisy workload starve unrelated work.

#### Interview answer

If request handling, database work, external HTTP calls, Kafka processing and scheduled jobs all share one executor, a slow dependency or retry storm can consume the pool and block everything. Separate pools act as bulkheads, isolating failure and making metrics meaningful.

#### Deep dive

Isolation is not only about thread count. Queue capacity, rejection policy, timeout budget and downstream limits must match each workload.

#### Production angle

Use dedicated executors for different blocking profiles and importance levels.

#### Traps / caveats

- Too many pools can also waste resources.
- Isolation without monitoring hides problems.
- Shared common pools are easy to abuse.

#### Optional Anki

Q: What pattern does separate executors support?
A: Bulkhead isolation.

</details>

<a id="mt-exec-012"></a>

<details>
<summary><strong>MT-EXEC-012. How do you shut down an `ExecutorService` gracefully?</strong></summary>

#### Short answer

Stop accepting new tasks, wait for existing tasks, then force cancellation if needed.

#### Interview answer

The usual sequence is `shutdown()`, `awaitTermination(timeout)`, then `shutdownNow()` if tasks do not finish in time. Tasks should handle interruption and clean up. The application should stop submitting work before shutdown starts.

#### Deep dive

`shutdownNow()` returns tasks that never started and interrupts running workers, but it cannot force non-cooperative tasks to stop.

#### Production angle

In Kubernetes, graceful shutdown must fit within the termination grace period and coordinate with readiness, request draining and message acknowledgments.

#### Traps / caveats

- Forgetting shutdown can keep the JVM alive.
- Ignoring interruption blocks shutdown.
- New tasks after shutdown are rejected.

#### Optional Anki

Q: First graceful executor shutdown call?
A: `shutdown()`.

</details>

<a id="mt-exec-013"></a>

<details>
<summary><strong>MT-EXEC-013. Why should custom executors use named threads through a `ThreadFactory`?</strong></summary>

#### Short answer

Named threads make logs, metrics and thread dumps understandable.

#### Interview answer

A custom `ThreadFactory` can set thread names, daemon status, priority and uncaught exception handling. Names like `payment-http-io-3` or `kafka-worker-7` reveal what work a thread belongs to. Generic names like `pool-4-thread-9` slow down incident response.

#### Deep dive

Thread names should identify the pool and workload, not individual user data or secrets.

#### Production angle

Good names help correlate pool metrics, log lines, JFR events and thread dumps during latency incidents.

#### Traps / caveats

- Avoid sensitive data in names.
- Name every important custom pool.
- Daemon setting should be deliberate.

#### Optional Anki

Q: Why use `ThreadFactory`?
A: To control thread names and lifecycle details.

</details>

<a id="mt-exec-014"></a>

<details>
<summary><strong>MT-EXEC-014. How can thread pools create deadlocks or starvation?</strong></summary>

#### Short answer

Pools can deadlock when tasks occupy all workers while waiting for other tasks queued to the same pool.

#### Interview answer

A common failure is a small fixed pool where each task submits subtasks to the same pool and blocks on their results. All workers become blocked, but subtasks cannot start because no worker is free. Starvation can also happen when long tasks monopolize workers and short important tasks wait behind them.

#### Deep dive

This is not a lock deadlock, but a resource deadlock. The scarce resource is worker threads.

#### Production angle

Avoid blocking on same-pool work. Use separate executors, async composition, structured concurrency or larger designs with bounded fan-out.

#### Traps / caveats

- `Future.get()` inside pool tasks is suspicious.
- Unbounded queues can hide starvation.
- Mixing long and short tasks increases tail latency.

#### Optional Anki

Q: What is thread starvation deadlock?
A: Workers block waiting for tasks that cannot run because workers are occupied.

</details>

<a id="mt-exec-015"></a>

<details>
<summary><strong>MT-EXEC-015. How would you isolate slow external calls with a separate executor?</strong></summary>

#### Short answer

Use a dedicated, bounded executor for that dependency, with timeouts, metrics and rejection behavior.

#### Interview answer

Slow external calls should not consume the same pool used for unrelated request handling. Put them behind a separate executor or bulkhead with a bounded queue and sensible size. Add HTTP client timeouts, overall request deadlines and fallback or failure mapping.

#### Deep dive

The executor limit should align with downstream capacity and connection pool limits. Otherwise you only move overload from one queue to another.

#### Production angle

Expose active threads, queue depth, rejections, latency and timeout counts per dependency.

#### Traps / caveats

- Retrying inside the same saturated pool worsens overload.
- A huge executor can overwhelm the dependency.
- Timeouts must stop or bound underlying work.

#### Optional Anki

Q: What pattern isolates a slow dependency?
A: A bulkhead, often using a dedicated bounded executor.

</details>

<a id="mt-exec-016"></a>

<details>
<summary><strong>MT-EXEC-016. How do timeouts and retries relate to thread pool exhaustion?</strong></summary>

#### Short answer

Missing timeouts keep threads blocked; uncontrolled retries add more work to already saturated pools.

#### Interview answer

If remote calls have no timeout, worker threads can wait indefinitely. If failures trigger immediate retries, the system submits more tasks exactly when capacity is low. This can turn a dependency slowdown into a retry storm and pool exhaustion.

Retries need deadlines, backoff, jitter, idempotency and concurrency limits.

#### Deep dive

Timeouts should be layered: connection/read timeouts, per-call timeout and overall request budget.

#### Production angle

Monitor timeouts, retries, active threads, queue depth, rejection count and downstream latency together.

#### Traps / caveats

- Timeout on a future may not cancel the underlying I/O.
- Retrying non-idempotent operations can duplicate side effects.
- Infinite retry loops are production incidents.

#### Optional Anki

Q: Why can retries exhaust pools?
A: They add more work during failure or saturation.

</details>

<a id="mt-exec-017"></a>

<details>
<summary><strong>MT-EXEC-017. What metrics should you monitor for a thread pool, and how would you configure an executor in Spring Boot?</strong></summary>

#### Short answer

Monitor active threads, pool size, queue depth, completed tasks, rejections and task latency; configure Spring executors explicitly.

#### Interview answer

Useful metrics include current pool size, active count, queue size/capacity, completed task count, rejection count, execution time and wait time. In Spring Boot, define a named `ThreadPoolTaskExecutor` or `Executor` bean with explicit core/max size, queue capacity, thread name prefix and rejection policy, then reference it from `@Async`.

#### Deep dive

For scheduled tasks, configure scheduler pool size and error handling separately.

#### Production angle

Executor metrics should be tagged by workload so you can identify which dependency or feature is saturating.

#### Traps / caveats

- Default `@Async` executor may be unsuitable.
- Queue time is as important as run time.
- Rejections should alert before users report failures.

#### Optional Anki

Q: Key executor overload metric?
A: Queue depth and rejections, together with active threads.

</details>
