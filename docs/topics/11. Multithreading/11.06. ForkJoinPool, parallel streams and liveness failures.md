# 11.06. ForkJoinPool, parallel streams and liveness failures

---

<a id="mt-fj-001"></a>

<details>
<summary><strong>🧠 MT-FJ-001. What is `ForkJoinPool`, and what is work stealing?</strong></summary>

#### Short answer

`ForkJoinPool` is a pool designed for recursive parallel tasks. Work stealing lets idle workers take tasks from busy workers.

#### Interview answer

Fork/join workloads split a problem into smaller tasks, run them in parallel, then combine results. Each worker has a deque of tasks. When a worker runs out of work, it can steal tasks from another worker's deque.

This model works well for CPU-bound divide-and-conquer algorithms with many small independent subtasks.

#### Deep dive

`RecursiveTask` returns a result; `RecursiveAction` does not. Parallel streams also use fork/join mechanics.

#### Production angle

Fork/join is not a general backend request orchestration tool. Blocking I/O in it can starve unrelated work.

#### Traps / caveats

- Best for CPU-bound splitting.
- Task granularity matters.
- Blocking calls reduce pool effectiveness.

#### Optional Anki

Q: What is work stealing?
A: Idle workers take queued tasks from busy workers.

</details>

<a id="mt-fj-002"></a>

<details>
<summary><strong>🧠 MT-FJ-002. How is `ForkJoinPool` related to parallel streams and `CompletableFuture`?</strong></summary>

#### Short answer

Parallel streams use the common `ForkJoinPool`; many async `CompletableFuture` methods without an executor also use it.

#### Interview answer

By default, `parallelStream()` executes work in the common `ForkJoinPool`. `CompletableFuture.supplyAsync()` and other async methods without an explicit executor also use the common pool in normal configurations. That means unrelated code can accidentally share the same execution resource.

#### Deep dive

Common-pool saturation can make different features interfere with each other. A blocking parallel stream can affect async futures elsewhere.

#### Production angle

Provide explicit executors for blocking or business-critical async work. Avoid hidden reliance on shared global pools.

#### Traps / caveats

- Common pool is process-wide.
- It is tuned for CPU-style tasks, not blocking I/O.
- Parallel streams hide executor choice.

#### Optional Anki

Q: Default pool for parallel streams?
A: The common `ForkJoinPool`.

</details>

<a id="mt-fj-003"></a>

<details>
<summary><strong>🧠 MT-FJ-003. Why should blocking I/O be avoided in the common `ForkJoinPool`?</strong></summary>

#### Short answer

Blocking I/O occupies workers that are expected to execute CPU tasks, reducing progress for all common-pool users.

#### Interview answer

The common `ForkJoinPool` has limited parallelism. If workers block on HTTP calls, database calls or `Future.get()`, they cannot execute other tasks. Because the pool is shared by parallel streams and default async futures, this can create latency spikes in unrelated code.

#### Deep dive

`ManagedBlocker` exists for some advanced blocking cases, but ordinary backend code should usually use a dedicated executor or virtual threads for blocking I/O.

#### Production angle

Thread dumps showing common-pool workers blocked on sockets are a strong signal to isolate the workload.

#### Traps / caveats

- "Async" futures can still block common-pool workers.
- Parallel streams over blocking operations are risky.
- More parallelism can overload downstream systems.

#### Optional Anki

Q: Why not block common-pool workers?
A: It can starve shared fork/join work.

</details>

<a id="mt-fj-004"></a>

<details>
<summary><strong>MT-FJ-004. Should backend request handling use parallel streams by default?</strong></summary>

#### Short answer

No. Parallel streams should be used deliberately after checking correctness, workload type and executor impact.

#### Interview answer

Parallel streams can help CPU-bound in-memory processing when the data set is large enough and operations are independent. In request handling, they often hurt throughput by using the common pool, adding overhead and competing with other requests.

For blocking remote calls, use explicit async orchestration, virtual threads or a dedicated executor with limits.

#### Deep dive

Parallel streams require stateless, non-interfering operations. Side effects, mutable collectors and ordering requirements can break correctness.

#### Production angle

Measure with production-like load. A faster single request can still reduce total service throughput.

#### Traps / caveats

- Parallel does not mean faster.
- Common-pool interference is hidden.
- Side effects become much more dangerous.

#### Optional Anki

Q: Default stance on parallel streams in backend requests?
A: Avoid by default; use only after measuring and validating.

</details>

<a id="mt-fj-005"></a>

<details>
<summary><strong>🧠 MT-FJ-005. How do custom `ForkJoinPool`s interact with parallel streams?</strong></summary>

#### Short answer

Parallel streams are designed around the common pool, and relying on custom-pool tricks is fragile.

#### Interview answer

Developers sometimes submit a parallel stream operation into a custom `ForkJoinPool` hoping the stream uses that pool. This has worked in common implementations, but it is not a clean API contract to build business design on.

If executor control matters, prefer explicit task submission, `CompletableFuture` with an executor, or another design.

#### Deep dive

Parallel stream APIs do not accept an executor parameter. That is the core limitation.

#### Production angle

Hidden executor behavior makes incidents harder to reason about. Use explicit ownership for important workloads.

#### Traps / caveats

- Do not depend on implementation quirks.
- Parallel stream cancellation and error handling are limited.
- Custom pools still need lifecycle and metrics.

#### Optional Anki

Q: Do parallel streams accept an executor parameter?
A: No.

</details>

<a id="mt-live-001"></a>

<details>
<summary><strong>MT-LIVE-001. What conditions are necessary for deadlock, and how can deadlocks be prevented?</strong></summary>

#### Short answer

Deadlock needs mutual exclusion, hold-and-wait, no preemption and circular wait. Prevent it by breaking one of those conditions.

#### Interview answer

The most common Java prevention technique is consistent lock ordering: every code path acquires locks in the same order. Other approaches are reducing nested locks, using `tryLock()` with timeout, avoiding shared locks, or redesigning ownership so one component owns the state.

#### Deep dive

Deadlocks can involve JVM locks, database locks, distributed locks and external calls. The cycle can cross layers.

#### Production angle

Capture thread dumps and database lock views before restarting. They are often the only evidence.

#### Traps / caveats

- Timeouts do not make logic correct by themselves.
- Lock ordering must be global.
- Calling external services while holding locks is risky.

#### Optional Anki

Q: Deadlock prevention by lock ordering breaks what?
A: Circular wait.

</details>

<a id="mt-live-002"></a>

<details>
<summary><strong>MT-LIVE-002. What are livelock and starvation?</strong></summary>

#### Short answer

Livelock means threads keep acting but make no progress. Starvation means a thread cannot get resources it needs.

#### Interview answer

In livelock, threads respond to each other forever, such as both backing off and retrying in sync. In starvation, some work is continually delayed because other work keeps winning CPU, locks, queue slots or pool threads.

Both are liveness failures: the system is not necessarily corrupted, but it fails to make useful progress.

#### Deep dive

Fairness policies, jittered backoff, queues and bounded retries can reduce these risks.

#### Production angle

Symptoms include high CPU with low throughput, growing queues and tasks that never complete.

#### Traps / caveats

- Livelock can look busy.
- Starvation can be caused by priority, locks or pool design.
- More retries can worsen livelock.

#### Optional Anki

Q: Busy but no progress is what?
A: Livelock.

</details>

<a id="mt-live-003"></a>

<details>
<summary><strong>MT-LIVE-003. What is lock contention, and how can it be reduced?</strong></summary>

#### Short answer

Lock contention happens when multiple threads frequently wait for the same lock.

#### Interview answer

Contention reduces parallelism and increases latency. Reduce it by narrowing critical sections, avoiding blocking calls while holding locks, splitting independent locks, using immutable snapshots, using concurrent collections where appropriate, or redesigning ownership.

Sometimes the best fix is removing shared mutable state.

#### Deep dive

Fine-grained locking can improve concurrency but increases complexity and deadlock risk.

#### Production angle

Look for many `BLOCKED` threads on one monitor, JFR lock events and latency spikes around synchronized paths.

#### Traps / caveats

- Do not optimize locks without measuring.
- More locks can make correctness harder.
- Contention can be caused by logging or metrics locks too.

#### Optional Anki

Q: Best first way to reduce lock contention?
A: Shorten the critical section and avoid blocking inside it.

</details>

<a id="mt-live-004"></a>

<details>
<summary><strong>MT-LIVE-004. What are lost updates and thread starvation deadlocks?</strong></summary>

#### Short answer

A lost update overwrites another thread's change. Thread starvation deadlock happens when pool workers wait for tasks that cannot start.

#### Interview answer

A lost update is a read-modify-write race: two threads read the same value, both compute a new value, and one write overwrites the other. A thread starvation deadlock is a pool resource problem: tasks occupy all workers while blocking for subtasks queued to the same pool.

#### Deep dive

Lost updates are safety failures. Starvation deadlocks are liveness failures. They need different fixes.

#### Production angle

Lost updates appear as wrong counts or state. Starvation deadlocks appear as full pools, queued tasks and blocked workers.

#### Traps / caveats

- Volatile does not fix lost updates.
- Increasing pool size may only delay starvation.
- Same-pool blocking is a design smell.

#### Optional Anki

Q: `x = x + 1` race can cause what?
A: Lost update.

</details>

<a id="mt-live-005"></a>

<details>
<summary><strong>MT-LIVE-005. How can unbounded task submission or blocking inside a small pool cause cascading failures?</strong></summary>

#### Short answer

They let work accumulate or block until one slow dependency consumes shared capacity and spreads failure.

#### Interview answer

If tasks are submitted without limits, queues grow, memory rises and latency increases. If a small pool blocks on slow downstream calls, workers are occupied and cannot process new work. Retries add even more tasks. Eventually unrelated requests fail because they share the same pool or dependency.

#### Deep dive

Cascading failure is often a queueing problem plus missing timeouts and isolation.

#### Production angle

Use bounded queues, bulkheads, timeouts, circuit breakers, backpressure and load shedding.

#### Traps / caveats

- Queues can hide overload.
- Retrying immediately worsens saturation.
- Slow failures are often more damaging than fast failures.

#### Optional Anki

Q: What protects against unbounded task growth?
A: Bounded queues and explicit overload policy.

</details>

<a id="mt-live-006"></a>

<details>
<summary><strong>MT-LIVE-006. How do timeouts and cancellation help preserve liveness?</strong></summary>

#### Short answer

They prevent work from waiting forever and release resources for other work.

#### Interview answer

Timeouts define how long an operation is allowed to consume resources. Cancellation tells work that it no longer matters and should stop. Together they prevent hung calls, abandoned fan-out tasks and shutdown delays.

They must be cooperative: code must use interruptible APIs, propagate cancellation and clean up resources.

#### Deep dive

Timeouts should be budgeted across nested calls. If every layer uses its own full timeout, total latency can exceed the user's deadline.

#### Production angle

Liveness depends on bounded waits. Every remote call, queue wait and task join should have a clear deadline in critical paths.

#### Traps / caveats

- Timeout of a wrapper may not stop underlying work.
- Cancellation without cleanup can leak resources.
- Ignored interruption defeats shutdown.

#### Optional Anki

Q: Why use deadlines?
A: To bound waiting and resource use.

</details>

<a id="mt-live-007"></a>

<details>
<summary><strong>MT-LIVE-007. How would you review code for concurrency risks?</strong></summary>

#### Short answer

Look for shared mutable state, unsafe publication, blocking, missing timeouts, ignored cancellation and unclear ownership.

#### Interview answer

I would identify mutable fields, especially in singletons and callbacks; check whether all accesses follow one synchronization policy; look for check-then-act races; verify executor sizing, queueing and shutdown; inspect async boundaries for context and transaction leaks; and ensure remote calls have timeouts.

#### Deep dive

Also check whether tests rely on sleeps, whether futures are ignored, and whether logs/metrics can reveal saturation.

#### Production angle

Concurrency review should include failure modes: slow downstreams, retries, shutdown, duplicate work and partial failure.

#### Traps / caveats

- "Works in tests" is weak evidence.
- Thread-safe components can be composed unsafely.
- Hidden global pools are easy to miss.

#### Optional Anki

Q: First question in concurrency review?
A: What shared mutable state exists and who owns it?

</details>
