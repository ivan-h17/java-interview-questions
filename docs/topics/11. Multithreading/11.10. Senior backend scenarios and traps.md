# 11.10. Senior backend scenarios and traps

---

<a id="mt-scen-001"></a>

<details>
<summary><strong>MT-SCEN-001. A service has high latency and many threads in `WAITING` state. How would you investigate?</strong></summary>

#### Short answer

Check what they are waiting on, whether it is normal idle waiting, and whether queues or dependencies are saturated.

#### Interview answer

I would take several thread dumps and group waiting threads by stack. `WAITING` in idle executor workers can be normal. Suspicious waits include `Future.get()`, `CountDownLatch.await()`, connection pool acquisition, queue operations, or joins without timeout. Then I would correlate with executor queue depth, database pool metrics, external dependency latency and request traces.

#### Deep dive

High latency plus waiting often means blocked resources, missing timeouts or fan-out tasks not completing.

#### Production angle

Mitigate with timeouts, bulkheads, backpressure or disabling the problematic dependency path.

#### Traps / caveats

- `WAITING` alone is not a bug.
- One dump is not enough.
- The real bottleneck may be outside the JVM.

#### Optional Anki

Q: First question for many waiting threads?
A: What are they waiting on?

</details>

<a id="mt-scen-002"></a>

<details>
<summary><strong>MT-SCEN-002. A service has high CPU and many `RUNNABLE` threads. How would you investigate?</strong></summary>

#### Short answer

Find hot stacks with CPU profiling or repeated dumps, then check for loops, contention, serialization, GC or retry storms.

#### Interview answer

I would capture CPU profiles or JFR, plus several thread dumps. If the same stacks dominate, inspect those code paths. Common causes are busy retry loops, accidental spin waits, CPU-heavy serialization, regex, compression, encryption, large in-memory processing or parallel streams competing with request work.

Also check GC, allocation rate and container CPU throttling.

#### Deep dive

`RUNNABLE` does not always mean CPU burn, but high CPU plus repeated runnable stacks is strong evidence.

#### Production angle

Short-term mitigation may be rate limiting, disabling a feature, reducing retries or scaling out while fixing the hot code.

#### Traps / caveats

- Logs can add CPU under error storms.
- More threads usually worsens CPU saturation.
- CPU throttling can look like app slowness.

#### Optional Anki

Q: Best tool for high CPU root cause?
A: CPU profile or JFR, supported by thread dumps.

</details>

<a id="mt-scen-003"></a>

<details>
<summary><strong>MT-SCEN-003. A thread pool queue grows without bound. What could be wrong?</strong></summary>

#### Short answer

Tasks are arriving faster than they complete, and the queue lacks an effective capacity or rejection policy.

#### Interview answer

I would check whether workers are blocked on slow dependencies, whether pool size is too small, whether tasks are too slow, and whether retries are adding extra load. An unbounded queue hides overload until latency and memory explode.

The fix is usually bounded queueing, proper rejection/backpressure, faster task processing, better isolation or reducing submission rate.

#### Deep dive

Queue growth is a symptom. Increasing pool size may help only if another resource is not already saturated.

#### Production angle

Alert on queue depth and queue wait time, not only active thread count.

#### Traps / caveats

- Queued tasks retain captured memory.
- Work may time out before it starts.
- Retrying queued tasks worsens backlog.

#### Optional Anki

Q: What does a growing executor queue mean?
A: Arrival rate exceeds completion rate.

</details>

<a id="mt-scen-004"></a>

<details>
<summary><strong>MT-SCEN-004. A small fixed thread pool processes tasks that submit more tasks to the same pool and wait. What can go wrong?</strong></summary>

#### Short answer

It can create thread starvation deadlock.

#### Interview answer

If all workers are occupied by parent tasks waiting on child tasks, and the child tasks are queued to the same pool, no worker is free to run the children. The system appears hung even though no Java monitor deadlock exists.

Avoid blocking on same-pool subtasks. Use a different executor, async composition, structured concurrency, or redesign the task graph.

#### Deep dive

This often appears after adding parallelism inside already-concurrent request or batch processing.

#### Production angle

Thread dumps show pool workers blocked on futures or latches, with queued tasks waiting.

#### Traps / caveats

- Increasing pool size may only delay the bug.
- Unbounded queues hide it.
- Same-pool `Future.get()` is suspicious.

#### Optional Anki

Q: Parent tasks waiting for same-pool child tasks can cause what?
A: Thread starvation deadlock.

</details>

<a id="mt-scen-005"></a>

<details>
<summary><strong>MT-SCEN-005. An endpoint fans out to 20 downstream services. How would you limit concurrency and handle timeouts?</strong></summary>

#### Short answer

Use per-call timeouts, an overall deadline, concurrency limits and clear partial-failure semantics.

#### Interview answer

I would define which downstreams are required and optional. Each call gets a timeout derived from the request deadline. Concurrency should be bounded with a semaphore, executor, virtual-thread scope plus limits, or resilience bulkhead. Optional failures can return partial results; required failures fail the request. Outstanding work should be cancelled when the deadline or request ends.

#### Deep dive

Launching all calls at once without limits can overload dependencies and the caller.

#### Production angle

Record per-dependency latency, timeout, cancellation, retry and fallback metrics.

#### Traps / caveats

- Timeout wrapper may not stop the HTTP request.
- Retries need idempotency and budget.
- Partial results must be explicit in the API.

#### Optional Anki

Q: Fan-out needs what two timeout levels?
A: Per-call timeouts and an overall deadline.

</details>

<a id="mt-scen-006"></a>

<details>
<summary><strong>MT-SCEN-006. A downstream service becomes slow and your application runs out of threads. What design changes would you make?</strong></summary>

#### Short answer

Add timeouts, bulkheads, bounded concurrency, circuit breaking and load shedding.

#### Interview answer

First, stop waiting forever: configure connection/read timeouts and request deadlines. Isolate that dependency with a dedicated bounded executor, semaphore or bulkhead. Add circuit breaking or fast failure when it is unhealthy. Avoid immediate retries; use backoff and jitter. Return fallback or controlled failure if the dependency is optional.

#### Deep dive

Slow dependencies are worse than fast failures because they retain resources longer.

#### Production angle

Watch active threads, queue depth, connection pool waits, timeout rate and dependency latency.

#### Traps / caveats

- More threads can overload the downstream further.
- Retrying inside saturation causes storms.
- Fallbacks must be safe and observable.

#### Optional Anki

Q: Main pattern for isolating slow dependencies?
A: Bulkhead with bounded concurrency and timeouts.

</details>

<a id="mt-scen-007"></a>

<details>
<summary><strong>MT-SCEN-007. A scheduled job runs on every application instance and causes duplicate work. How would you fix it?</strong></summary>

#### Short answer

Use cluster coordination or make the job idempotent and partitioned.

#### Interview answer

If only one instance should run the job, use a distributed lock, leader election or scheduler that supports single execution. If many instances may run it, partition the work so each item has one owner. In either case, make the operation idempotent with database constraints or state transitions.

#### Deep dive

Scheduling and execution are separate concerns. Even with a lock, a crashed worker can leave partial work.

#### Production angle

Track job owner, start/end time, lock acquisition, processed item IDs and failures.

#### Traps / caveats

- In-memory locks do not coordinate across pods.
- Clock skew can affect naive locks.
- Idempotency is still needed for retries.

#### Optional Anki

Q: Why is `@Scheduled` risky in a cluster?
A: Every instance may run the job.

</details>

<a id="mt-scen-008"></a>

<details>
<summary><strong>MT-SCEN-008. A Spring singleton service stores mutable state in a field and fails under load. How would you refactor it?</strong></summary>

#### Short answer

Move request-specific state to local variables or explicit request-scoped objects.

#### Interview answer

I would identify which field is shared across requests and why. If it is temporary request state, make it a local variable. If it is cached shared state, use an immutable snapshot, proper concurrent collection or lock around the invariant. If it is truly per-request, use request scope or pass a context object explicitly.

#### Deep dive

Spring singleton services should usually be stateless. Dependencies can be fields; per-call data should not.

#### Production angle

Add concurrency tests or load tests that call the service with different users/inputs simultaneously.

#### Traps / caveats

- `volatile` does not fix compound mutable state.
- ThreadLocal may hide the same design issue.
- Caches need eviction and metrics.

#### Optional Anki

Q: Where should request-specific state live in a singleton service?
A: Local variables or explicit context, not shared fields.

</details>

<a id="mt-scen-009"></a>

<details>
<summary><strong>MT-SCEN-009. A cache implementation sometimes returns stale or corrupted values. How would you review it?</strong></summary>

#### Short answer

Check publication, mutation, compound operations, invalidation and value ownership.

#### Interview answer

I would inspect whether cached values are immutable or defensively copied, whether updates use atomic cache operations, whether invalidation races with reads, and whether multi-key invariants are protected. I would also check TTLs, refresh behavior, exception handling and memory growth.

If using `ConcurrentHashMap`, I would look for get-then-put races and mutable values changed outside synchronization.

#### Deep dive

Cache correctness is often about lifecycle and ownership, not just map thread-safety.

#### Production angle

Add metrics for hit rate, size, eviction, refresh failures and impossible state detection.

#### Traps / caveats

- Concurrent map values can still be unsafe.
- Stale may be acceptable only if documented.
- Refresh storms can overload dependencies.

#### Optional Anki

Q: Does `ConcurrentHashMap` make cached values immutable?
A: No.

</details>

<a id="mt-scen-010"></a>

<details>
<summary><strong>MT-SCEN-010. A code path uses `CompletableFuture` but still blocks request threads. How would you find and fix it?</strong></summary>

#### Short answer

Look for `join()`, `get()`, blocking calls in async stages and use of the wrong executor.

#### Interview answer

I would inspect thread dumps and code for `Future.get()`, `join()`, blocking HTTP/DB calls wrapped in `supplyAsync`, and stages using the common pool. If request threads call `join()` before responding, the endpoint is still synchronous from their perspective.

Fixes include using non-blocking composition, virtual threads, explicit executors, request deadlines and bounded fan-out.

#### Deep dive

`CompletableFuture` represents async completion; it does not make blocking I/O non-blocking by itself.

#### Production angle

Measure request-thread occupancy, common-pool saturation and downstream latency.

#### Traps / caveats

- Async wrapper around blocking code still consumes a thread.
- Common pool is bad for blocking I/O.
- Timeout on future may not stop underlying call.

#### Optional Anki

Q: Common blocking methods in future code?
A: `get()` and `join()`.

</details>

<a id="mt-scen-011"></a>

<details>
<summary><strong>MT-SCEN-011. A virtual-thread migration increased database timeouts. What would you check?</strong></summary>

#### Short answer

Check DB pool wait time, query concurrency, database saturation and removed application-level limits.

#### Interview answer

Virtual threads may allow many more requests to reach the JDBC pool concurrently. I would inspect connection acquisition time, active/pending connections, query latency, DB CPU/locks, transaction duration and request fan-out. The old platform-thread pool may have accidentally limited DB concurrency.

Fix by adding explicit concurrency limits and tuning the pool based on DB capacity.

#### Deep dive

Virtual threads make waiting cheaper; they do not make the database faster.

#### Production angle

Run load tests with realistic DB data and connection limits before migration.

#### Traps / caveats

- Do not size JDBC pool to virtual thread count.
- More concurrent queries can reduce throughput.
- Long transactions hold connections.

#### Optional Anki

Q: Why can virtual threads increase DB timeouts?
A: More work reaches the limited DB pool concurrently.

</details>

<a id="mt-scen-012"></a>

<details>
<summary><strong>MT-SCEN-012. A service uses `ThreadLocal` for user context and sometimes leaks users between requests. What happened?</strong></summary>

#### Short answer

A pooled worker thread kept the previous request's ThreadLocal value.

#### Interview answer

If request handling sets user context in a ThreadLocal but does not remove it in `finally`, the thread returns to the pool with that value still attached. A later request on the same worker can read the wrong user.

Fix by clearing context reliably, using framework filters/interceptors, or passing explicit immutable context.

#### Deep dive

Async boundaries can make this worse: context may be copied to workers and not cleaned there.

#### Production angle

This is a security incident. Add tests using reused workers and audit all context propagation code.

#### Traps / caveats

- Cleanup must run on exceptions.
- `InheritableThreadLocal` can spread stale context.
- Logs may reveal the leak before users do.

#### Optional Anki

Q: Root cause of ThreadLocal user leak in pools?
A: Missing `remove()` on reused worker threads.

</details>

<a id="mt-scen-013"></a>

<details>
<summary><strong>MT-SCEN-013. A transaction starts in one thread and async work runs in another. What problems can happen?</strong></summary>

#### Short answer

The async work may not participate in the transaction, may see uncommitted assumptions, and may fail independently.

#### Interview answer

Spring transaction context is thread-bound. Async work in another thread usually runs outside that transaction unless it starts its own. It may use entities after the persistence context closes, trigger side effects before commit, or fail after the caller already returned.

Use after-commit hooks, messaging/outbox or explicit new transactions with IDs/DTOs.

#### Deep dive

Transaction boundaries should be part of the async design, not an accidental framework detail.

#### Production angle

Watch for duplicate messages, missing audits, lazy-loading failures and inconsistent reads.

#### Traps / caveats

- Async failure does not roll back the original transaction.
- Managed JPA entities are not safe async DTOs.
- Blind context propagation is risky.

#### Optional Anki

Q: Is Spring transaction context automatically propagated to async threads?
A: No.

</details>

<a id="mt-scen-014"></a>

<details>
<summary><strong>MT-SCEN-014. A race condition only appears in production. How would you approach debugging and mitigation?</strong></summary>

#### Short answer

Collect evidence, identify the shared state and interleaving, add safe mitigation, then redesign or synchronize correctly.

#### Interview answer

I would look for impossible states, duplicate actions, stale values and shared mutable objects. Add targeted logging with correlation IDs, metrics for invariant violations, and thread dumps if liveness is involved. Then mitigate with a lock, atomic operation, database constraint, idempotency key or feature flag while preparing a proper fix.

#### Deep dive

Do not rely on reproducing the race locally before adding protective invariants if production impact is high.

#### Production angle

Use database uniqueness or state transitions for business-critical races like duplicate payments.

#### Traps / caveats

- Logging can hide the race.
- Tests may never hit the bad interleaving.
- Fix the invariant, not only the symptom.

#### Optional Anki

Q: Strong mitigation for business races?
A: Enforce the invariant at the database or ownership boundary.

</details>

<a id="mt-scen-015"></a>

<details>
<summary><strong>MT-SCEN-015. A deadlock appears once a week. What data would you collect?</strong></summary>

#### Short answer

Collect thread dumps, lock owners, database lock information, request IDs and recent deployment/config changes.

#### Interview answer

Before restart, capture multiple thread dumps and JFR if possible. If database work is involved, collect lock wait and transaction views from the DB. Correlate blocked threads with request logs, lock order, code paths and timing. Identify whether the cycle is JVM locks, DB locks, distributed locks or a combination.

#### Deep dive

Rare deadlocks often require a specific order of requests, scheduled jobs or retries.

#### Production angle

Add temporary instrumentation around lock acquisition order and long-held locks if evidence is insufficient.

#### Traps / caveats

- Restart removes evidence.
- JVM deadlock detector may not see DB cycles.
- Timeouts can mask but not solve lock-order bugs.

#### Optional Anki

Q: Key artifact for JVM deadlock?
A: Thread dump with lock ownership.

</details>

<a id="mt-scen-016"></a>

<details>
<summary><strong>MT-SCEN-016. A retry storm causes thread pool exhaustion. How would you redesign retries?</strong></summary>

#### Short answer

Use bounded retries with backoff, jitter, deadlines, idempotency and concurrency limits.

#### Interview answer

Immediate retries multiply load when the system is already failing. I would classify retryable errors, cap attempts, add exponential backoff with jitter, respect an overall deadline, and stop retrying when the dependency is unhealthy. Non-idempotent operations need idempotency keys or should not be retried blindly.

Retries should also use bulkheads so they cannot consume all workers.

#### Deep dive

Sometimes the right retry policy is no retry in the synchronous path and recovery through messaging.

#### Production angle

Track retry attempts, final failures, latency added by retries and duplicate side effects.

#### Traps / caveats

- Retrying timeouts can duplicate work.
- Retrying rejected tasks can amplify overload.
- Backoff without jitter can synchronize clients.

#### Optional Anki

Q: Retry storm fix basics?
A: Backoff, jitter, deadlines, caps and idempotency.

</details>

<a id="mt-scen-017"></a>

<details>
<summary><strong>MT-SCEN-017. A bounded executor rejects tasks during traffic spikes. How should the application respond?</strong></summary>

#### Short answer

Treat rejection as controlled overload and respond according to workload semantics.

#### Interview answer

For synchronous requests, return a clear overload response such as 429 or 503. For optional work, drop or degrade with metrics. For durable work, enqueue to a real message broker or return retry-after guidance. Do not silently lose critical tasks.

Rejection means the system is protecting itself; the response should be explicit and observable.

#### Deep dive

Caller-runs can apply backpressure but may be unsafe on event loops or request threads.

#### Production angle

Alert on rejection rate and correlate with traffic, dependency latency and queue depth.

#### Traps / caveats

- Silent discard is rarely acceptable.
- Immediate client retries can worsen the spike.
- Rejected work may need audit records.

#### Optional Anki

Q: What does rejection usually signal?
A: Controlled overload.

</details>

<a id="mt-scen-018"></a>

<details>
<summary><strong>MT-SCEN-018. A Java service must shut down gracefully in Kubernetes. What should happen to executors and in-flight tasks?</strong></summary>

#### Short answer

Stop receiving new work, let in-flight work finish within a deadline, then cancel and release resources.

#### Interview answer

The service should fail readiness first so traffic drains, stop schedulers and consumers, reject new async submissions, call executor shutdown, wait with a bounded timeout, and interrupt/cancel remaining work if necessary. Message consumers should commit/ack only completed work according to semantics.

All of this must fit within Kubernetes termination grace period.

#### Deep dive

Tasks must handle interruption. If they ignore it, shutdown can hang until the pod is killed.

#### Production angle

Test shutdown under active load, slow dependencies and stuck tasks.

#### Traps / caveats

- Daemon threads can abandon work.
- `shutdownNow()` is cooperative.
- Readiness and shutdown hooks must be coordinated.

#### Optional Anki

Q: First graceful shutdown step in Kubernetes?
A: Stop receiving new traffic, usually by failing readiness.

</details>

<a id="mt-scen-019"></a>

<details>
<summary><strong>MT-SCEN-019. A rare memory visibility bug disappears when logging is added. Why can that happen?</strong></summary>

#### Short answer

Logging changes timing and may introduce synchronization, allocation or I/O that alters thread interleavings.

#### Interview answer

Concurrency bugs can depend on very specific timing. Adding logs slows code, changes scheduling, adds locks inside the logging framework, performs volatile reads/writes or changes memory pressure. That can accidentally create visibility or ordering effects that hide the original bug.

The fix is to add proper happens-before relationships, not keep the logging.

#### Deep dive

This is why reproducing visibility bugs is hard: observation changes execution.

#### Production angle

Use targeted diagnostics, but reason from the synchronization contract and invariants when fixing the bug.

#### Traps / caveats

- "Cannot reproduce with logs" does not mean fixed.
- Sleeps and debuggers can also hide races.
- The correct fix is synchronization, immutability or safe publication.

#### Optional Anki

Q: Why can logging hide concurrency bugs?
A: It changes timing and may add synchronization.

</details>
