# 11.08. Virtual threads and structured concurrency

---

<a id="mt-vt-001"></a>

<details>
<summary><strong>MT-VT-001. What are virtual threads in Java 21+, and how are they different from platform threads?</strong></summary>

#### Short answer

Virtual threads are lightweight JDK-managed threads. Platform threads are wrappers around operating-system threads.

#### Interview answer

A platform thread is expensive because it maps to an OS thread. A virtual thread is scheduled by the JDK and mounted onto a smaller set of carrier platform threads when it runs. When it blocks on supported operations, it can unmount so the carrier can run other virtual threads.

Virtual threads preserve the normal blocking programming model while allowing many more concurrent blocking tasks.

#### Deep dive

Virtual threads are still `Thread` instances. They are not faster CPU workers; they are cheaper waiting workers.

#### Production angle

They fit request-per-thread and blocking I/O services, but resource limits such as database pools still matter.

#### Traps / caveats

- They do not increase CPU cores.
- Blocking work still consumes downstream resources.
- ThreadLocal use can become expensive at massive scale.

#### Optional Anki

Q: What schedules virtual threads?
A: The JDK, not directly the OS scheduler.

</details>

---

<a id="mt-vt-002"></a>

<details>
<summary><strong>MT-VT-002. What are the main benefits of virtual threads, and when should you use them?</strong></summary>

#### Short answer

They make blocking I/O concurrency cheap and keep code simple.

#### Interview answer

Virtual threads are useful when an application has many concurrent tasks that spend most time waiting: HTTP calls, database calls, file or network I/O. They let developers write straightforward blocking code instead of complex callback or reactive chains for many use cases.

They are a good fit for thread-per-request servers and fan-out workflows with proper limits.

#### Deep dive

Virtual threads reduce the cost of waiting, not the cost of the external resource being waited on.

#### Production angle

Use them when platform-thread pools are mostly blocked and code simplicity matters. Validate with load tests and dependency metrics.

#### Traps / caveats

- Do not remove connection limits.
- Do not launch unbounded fan-out.
- Some libraries may still have blocking or native limitations.

#### Optional Anki

Q: Best workload for virtual threads?
A: Many concurrent blocking I/O tasks.

</details>

<a id="mt-vt-003"></a>

<details>
<summary><strong>MT-VT-003. When should you not use virtual threads, and why do they not make CPU-bound work faster?</strong></summary>

#### Short answer

Avoid expecting virtual threads to speed CPU-bound work; CPU throughput is limited by available cores.

#### Interview answer

Virtual threads are cheap to block, but CPU-bound work needs CPU time. Running 100,000 CPU-heavy virtual threads on 8 cores just creates scheduling overhead and contention. For CPU-heavy computation, use bounded parallelism sized around cores, batching or dedicated worker pools.

Also be careful with code that relies on thread pooling semantics, heavy ThreadLocal state or unsupported blocking operations.

#### Deep dive

Virtual threads improve scalability when platform threads would otherwise sit idle waiting.

#### Production angle

Measure CPU, run queue, GC allocation and dependency throughput before and after migration.

#### Traps / caveats

- Virtual threads do not replace backpressure.
- CPU-heavy fan-out can hurt latency.
- Thread-per-task does not mean unlimited concurrency.

#### Optional Anki

Q: Why do virtual threads not speed CPU-bound work?
A: They do not add CPU cores.

</details>

<a id="mt-vt-004"></a>

<details>
<summary><strong>MT-VT-004. How do you create virtual threads, and what is `Executors.newVirtualThreadPerTaskExecutor()`?</strong></summary>

#### Short answer

Create them with `Thread.ofVirtual()` or use `Executors.newVirtualThreadPerTaskExecutor()` to run each task in a new virtual thread.

#### Interview answer

Examples include `Thread.ofVirtual().start(runnable)` and `Executors.newVirtualThreadPerTaskExecutor()`. The executor creates a fresh virtual thread per submitted task and is usually used with try-with-resources or explicit shutdown.

Unlike platform-thread pools, virtual threads are cheap enough that pooling them is usually unnecessary.

#### Deep dive

You still need to limit the number of concurrent operations when they use scarce resources like database connections or remote APIs.

#### Production angle

Use semaphores, rate limiters, connection pools or structured concurrency policies to bound fan-out.

#### Traps / caveats

- The executor still has lifecycle.
- New virtual thread per task is not new connection per task.
- ThreadLocal values belong to each virtual thread.

#### Optional Anki

Q: Standard virtual-thread executor?
A: `Executors.newVirtualThreadPerTaskExecutor()`.

</details>

<a id="mt-vt-005"></a>

<details>
<summary><strong>MT-VT-005. Should virtual threads be pooled, and how should concurrency be limited instead?</strong></summary>

#### Short answer

Virtual threads usually should not be pooled. Limit the scarce resource, not the virtual thread object.

#### Interview answer

Platform threads are pooled because they are expensive. Virtual threads are cheap and intended to be created per task. Pooling them often recreates the old thread-pool bottleneck without solving the real constraint.

Limit concurrency with database pools, semaphores, rate limiters, bounded queues, structured scopes or downstream-specific bulkheads.

#### Deep dive

The key question is "what resource can be exhausted?" Usually it is DB connections, remote service capacity, memory, CPU or queue length.

#### Production angle

Virtual-thread migrations often fail when a service suddenly sends far more concurrent work to a database or dependency.

#### Traps / caveats

- Do not use a fixed pool of virtual threads as a rate limiter.
- Limit fan-out explicitly.
- Monitor downstream saturation.

#### Optional Anki

Q: What should be limited with virtual threads?
A: The scarce resource, not the virtual thread count itself.

</details>

<a id="mt-vt-006"></a>

<details>
<summary><strong>🧠 MT-VT-006. What are carrier threads, mounting and unmounting?</strong></summary>

#### Short answer

A carrier thread is a platform thread that temporarily runs a virtual thread. Mounting assigns the virtual thread to a carrier; unmounting releases it.

#### Interview answer

The JDK scheduler runs virtual threads by mounting them onto carrier platform threads. When a virtual thread blocks on supported operations, it can unmount and free the carrier. Later, when ready, it is mounted again, possibly on a different carrier.

This is how many virtual threads can share fewer platform threads.

#### Deep dive

Application code should not depend on carrier identity. Thread identity remains the virtual thread's identity.

#### Production angle

This model explains why blocking I/O can scale better with virtual threads than with one platform thread per blocked request.

#### Traps / caveats

- Carrier threads are implementation details.
- ThreadLocal belongs to the virtual thread, not carrier reuse.
- Some operations can still pin or block carriers.

#### Optional Anki

Q: What does unmounting release?
A: The carrier platform thread.

</details>

<a id="mt-vt-007"></a>

<details>
<summary><strong>🧠 MT-VT-007. What is virtual-thread pinning?</strong></summary>

#### Short answer

Pinning means a virtual thread cannot unmount from its carrier while blocked.

#### Interview answer

If a virtual thread is pinned and then blocks, its carrier platform thread is blocked too. This reduces scalability because carriers are the limited execution resource for running virtual threads.

In Java 21-23, blocking inside `synchronized` code was a common pinning concern. JDK 24 improved this with JEP 491.

#### Deep dive

Remaining pinning cases can involve native calls or foreign-function interactions.

#### Production angle

JFR events and thread dumps can help identify pinning or carrier blockage in virtual-thread services.

#### Traps / caveats

- Pinning is a scalability issue, not usually a correctness issue.
- Not all blocking pins.
- JDK version matters.

#### Optional Anki

Q: What does pinning prevent?
A: Unmounting a virtual thread from its carrier.

</details>

<a id="mt-vt-008"></a>

<details>
<summary><strong>🧠 MT-VT-008. What did JEP 491 in JDK 24 improve about virtual threads and `synchronized` code?</strong></summary>

#### Short answer

JEP 491 changed the JVM so virtual threads can block in most `synchronized` code without pinning their carriers.

#### Interview answer

Before JDK 24, a virtual thread that blocked while inside a synchronized method or block could remain pinned to its carrier, reducing scalability. JEP 491, delivered in JDK 24, changed monitor handling so virtual threads can acquire, hold and release monitors independently of carriers in these cases.

This means `synchronized` is no longer automatically a virtual-thread migration blocker.

#### Deep dive

`ReentrantLock` still has features `synchronized` lacks, but avoiding synchronized solely because of old pinning advice is outdated on JDK 24+.

#### Production angle

For JDK 21-23 services, pinning concerns still matter. For JDK 24+, focus more on lock scope, blocking duration and contention.

#### Traps / caveats

- Native calls can still pin.
- Long synchronized sections can still hurt scalability through contention.
- Know the production JDK version.

#### Optional Anki

Q: Which JDK delivered JEP 491?
A: JDK 24.

</details>

<a id="mt-vt-009"></a>

<details>
<summary><strong>🧠 MT-VT-009. How do virtual threads interact with native calls or foreign functions?</strong></summary>

#### Short answer

Native or foreign calls can pin a virtual thread or block a carrier because the JVM cannot always unmount safely.

#### Interview answer

When Java code enters native code, the JVM may not be able to capture and resume the continuation like it can for normal Java blocking operations. If the native call blocks, the carrier can remain occupied.

This matters for libraries that use JNI, foreign functions, OS calls or drivers with native blocking behavior.

#### Deep dive

JDK diagnostics can report remaining pinning cases. The exact behavior depends on the operation and JDK version.

#### Production angle

Before migrating critical services, load test with the actual drivers and native libraries used in production.

#### Traps / caveats

- "Virtual thread compatible" depends on dependencies.
- A small amount of pinning may be harmless.
- Native blocking can look like ordinary latency.

#### Optional Anki

Q: Remaining virtual-thread pinning concern after JDK 24?
A: Native or foreign-function blocking.

</details>

<a id="mt-vt-010"></a>

<details>
<summary><strong>MT-VT-010. Why do virtual threads not remove the need for JDBC connection pool limits?</strong></summary>

#### Short answer

Virtual threads make waiting cheaper, but database connections are still limited.

#### Interview answer

A virtual thread blocked waiting for a DB connection may not waste an OS thread, but it still represents work queued for the database. If a service creates far more concurrent DB operations than the database can handle, latency and timeouts increase.

The JDBC pool remains the real concurrency limit for database work.

#### Deep dive

Virtual threads can expose a too-small or overloaded pool because more request threads can reach the pool concurrently.

#### Production angle

Monitor connection acquisition time, active connections, pending requests, query latency and DB saturation after migration.

#### Traps / caveats

- Do not size the pool to virtual thread count.
- More concurrency can hurt the database.
- Pool timeout is a backpressure signal.

#### Optional Anki

Q: What limits DB concurrency with virtual threads?
A: Database and JDBC connection pool capacity.

</details>

<a id="mt-vt-011"></a>

<details>
<summary><strong>🧠 MT-VT-011. How do virtual threads affect `ThreadLocal` usage, observability and thread dumps?</strong></summary>

#### Short answer

They reduce thread reuse leaks but make per-thread state and thread dumps much larger at scale.

#### Interview answer

Virtual threads are usually short-lived, so classic ThreadLocal leaks from pooled workers are less severe. But millions of virtual threads with large ThreadLocal values can consume significant memory. Observability also changes: thread dumps may contain many virtual threads, so tools need filtering, grouping and correlation.

#### Deep dive

Scoped Values are often a better model for immutable request context in virtual-thread code.

#### Production angle

Watch memory retained by ThreadLocals, request IDs in logs, virtual-thread counts and blocked/pinned virtual-thread diagnostics.

#### Traps / caveats

- Do not store large request graphs in ThreadLocal.
- Thread dumps can become noisy.
- Context propagation still needs design.

#### Optional Anki

Q: Main ThreadLocal risk with many virtual threads?
A: Memory footprint from per-thread values.

</details>

<a id="mt-vt-012"></a>

<details>
<summary><strong>🧠 MT-VT-012. How do virtual threads compare with reactive programming?</strong></summary>

#### Short answer

Virtual threads keep blocking-style code scalable; reactive programming provides non-blocking streams, backpressure and event-driven composition.

#### Interview answer

Virtual threads are often simpler for request/response services doing blocking I/O. Reactive systems can be better for streaming, high fan-in/fan-out event flows, backpressure-aware pipelines and integrations already based on reactive libraries.

The choice depends on team skill, ecosystem, latency goals, streaming needs and library support.

#### Deep dive

Virtual threads reduce the need to wrap blocking calls in callback chains, but they do not provide reactive-streams backpressure by themselves.

#### Production angle

Do not rewrite a stable reactive system just because virtual threads exist. Evaluate operational behavior and complexity.

#### Traps / caveats

- Reactive is not automatically faster.
- Virtual threads are not streaming backpressure.
- Mixing models needs clear boundaries.

#### Optional Anki

Q: What does reactive provide that virtual threads do not inherently provide?
A: Stream-oriented backpressure and non-blocking composition.

</details>

<a id="mt-vt-013"></a>

<details>
<summary><strong>🧠 MT-VT-013. What is structured concurrency, and what problem does `StructuredTaskScope` solve?</strong></summary>

#### Short answer

Structured concurrency treats related concurrent tasks as one scoped unit of work.

#### Interview answer

Without structure, a request can submit child tasks that outlive the request, fail silently or keep running after a sibling fails. `StructuredTaskScope` gives the subtasks a lexical scope: fork children, join them, handle success/failure, and ensure unfinished work is cancelled and joined when the scope closes.

This improves cancellation, error handling and observability.

#### Deep dive

It fits virtual threads well because each subtask can cheaply get its own thread.

#### Production angle

It is useful for fan-out/fan-in request logic where child work should not leak beyond the parent request.

#### Traps / caveats

- It is not a replacement for all executor use.
- Child tasks must still respond to interruption.
- API version matters while preview evolves.

#### Optional Anki

Q: Main goal of structured concurrency?
A: Make lifetimes of child tasks bounded by parent scope.

</details>

<details>
<summary><strong>🧠 MT-VT-014. Why is structured concurrency still a preview API in JDK 26, and what should production teams consider?</strong></summary>

#### Short answer

The API is still being refined, so production teams must account for preview-feature risk and JDK version compatibility.

#### Interview answer

Structured concurrency has gone through multiple preview rounds. In JDK 26 it is a sixth preview, with API refinements such as changes around joiners. Preview APIs require `--enable-preview` and can change between releases.

Teams should separate the concept from the exact API: the design idea is valuable, but direct use in long-lived production code needs upgrade planning.

#### Deep dive

Some frameworks and libraries may offer stable structured-concurrency-like abstractions before the JDK API is finalized.

#### Production angle

Use preview APIs only with clear ownership, compatibility testing and a plan for JDK upgrades.

#### Traps / caveats

- Preview is not final API.
- Syntax and behavior can change.
- Build and runtime flags are required.

#### Optional Anki

Q: Structured concurrency status in JDK 26?
A: Sixth preview API.

</details>

<a id="mt-vt-015"></a>

<details>
<summary><strong>🧠 MT-VT-015. How do structured concurrency, cancellation and timeouts help avoid task leaks?</strong></summary>

#### Short answer

They ensure child tasks are cancelled or completed before the parent scope exits.

#### Interview answer

A task leak happens when child work continues after the request or parent operation no longer cares. Structured concurrency bounds child lifetimes to a scope. If the parent is cancelled, times out or one critical child fails, sibling tasks can be interrupted and the parent waits for cleanup before exiting.

Timeouts provide the deadline; cancellation communicates that work should stop.

#### Deep dive

Cancellation remains cooperative. Blocking calls and loops must respond to interruption or deadlines.

#### Production angle

This prevents abandoned remote calls, duplicate side effects and background work continuing after client disconnects.

#### Traps / caveats

- Closing a scope may wait for non-cooperative children.
- Timeout wrappers must cancel underlying work.
- Idempotency is still needed for side effects.

#### Optional Anki

Q: What is a task leak?
A: Child work outliving the parent operation that started it.

</details>
