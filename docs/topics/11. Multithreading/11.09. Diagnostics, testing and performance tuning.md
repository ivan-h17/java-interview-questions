# 11.09. Diagnostics, testing and performance tuning

---

<a id="mt-diag-001"></a>

<details>
<summary><strong>MT-DIAG-001. How do you get and read a Java thread dump?</strong></summary>

#### Short answer

Use tools such as `jcmd`, `jstack`, JVM signals or platform diagnostics, then inspect thread names, states, stacks and locks.

#### Interview answer

For a local JVM, `jcmd <pid> Thread.print` is usually a good option; `jstack <pid>` is also common. In containers, use the process ID inside the container or platform tooling. To read the dump, group threads by pool name, look at states, stack traces, blocked monitors, waiting calls and repeated stack patterns.

#### Deep dive

One dump is a snapshot. Several dumps seconds apart are better for distinguishing stuck work from normal waiting.

#### Production angle

Capture dumps before restart when possible. Pair them with CPU, pool, GC and dependency metrics.

#### Traps / caveats

- Many idle waiting threads can be normal.
- Thread names matter.
- A dump shows symptoms, not always root cause.

#### Optional Anki

Q: Useful modern command for a thread dump?
A: `jcmd <pid> Thread.print`.

</details>

<a id="mt-diag-002"></a>

<details>
<summary><strong>MT-DIAG-002. How can a thread dump reveal deadlocks or thread pool starvation?</strong></summary>

#### Short answer

Deadlocks show lock cycles; starvation shows workers blocked or waiting while queued work cannot run.

#### Interview answer

JVM thread dumps can explicitly report monitor deadlocks. You can also see threads `BLOCKED` on the same monitor and identify lock owners. For pool starvation, look for all worker threads in a pool blocked on `Future.get()`, queues, locks or remote I/O while more tasks are waiting.

#### Deep dive

Starvation may not be reported as a JVM deadlock because no monitor cycle exists. The blocked resource is pool capacity.

#### Production angle

Correlate dump evidence with executor queue depth, active count and dependency latency.

#### Traps / caveats

- A database deadlock may not appear as a JVM monitor deadlock.
- One dump may catch a transient wait.
- Common-pool starvation can affect unrelated code.

#### Optional Anki

Q: Does thread starvation deadlock always appear as JVM deadlock?
A: No.

</details>

<a id="mt-diag-003"></a>

<details>
<summary><strong>MT-DIAG-003. What thread states are most important in production diagnostics?</strong></summary>

#### Short answer

`RUNNABLE`, `BLOCKED`, `WAITING` and `TIMED_WAITING` are usually the most useful states.

#### Interview answer

`RUNNABLE` can indicate CPU work or native blocking. `BLOCKED` means waiting to acquire a monitor, so many blocked threads on one lock suggest contention. `WAITING` means indefinite wait, such as `join()` or queue take. `TIMED_WAITING` means sleep, timed wait or timed blocking.

Interpret states with stack traces and metrics.

#### Deep dive

Thread state names are JVM-level categories, not a full scheduler explanation.

#### Production angle

Repeated stacks with many threads in the same state are more useful than one isolated thread.

#### Traps / caveats

- `RUNNABLE` does not always mean burning CPU.
- `WAITING` is normal in idle pools.
- `BLOCKED` requires finding the owner.

#### Optional Anki

Q: Which state suggests monitor contention?
A: `BLOCKED`.

</details>

<a id="mt-diag-004"></a>

<details>
<summary><strong>MT-DIAG-004. How can `jstack`, `jcmd` and Java Flight Recorder help with concurrency issues?</strong></summary>

#### Short answer

Thread dumps show current stacks; JFR records events over time with low overhead.

#### Interview answer

`jstack` and `jcmd Thread.print` help inspect what threads are doing now. `jcmd` can also start or dump JFR recordings. JFR can capture lock contention, thread parking, CPU samples, allocation, socket I/O and virtual-thread events depending on configuration.

Together they help connect symptoms to code paths.

#### Deep dive

Thread dumps are snapshots; JFR gives a timeline. Profiling high CPU or latency spikes often needs both.

#### Production angle

Keep a safe runbook for collecting dumps and JFR in production without exposing secrets.

#### Traps / caveats

- Stack traces may include sensitive data.
- JFR settings affect overhead and detail.
- Sampling can miss very short events.

#### Optional Anki

Q: Snapshot vs timeline tool?
A: Thread dump is snapshot; JFR is timeline recording.

</details>

<a id="mt-diag-005"></a>

<details>
<summary><strong>MT-DIAG-005. What metrics should be collected for platform-thread pools and virtual-thread workloads?</strong></summary>

#### Short answer

For pools, track active threads, queue depth, rejections and latency. For virtual threads, track concurrency, blocking, downstream limits and pinning.

#### Interview answer

Platform-thread pools need active count, pool size, queue size, queue wait time, execution time, completed tasks and rejections. Virtual-thread workloads need request concurrency, number of virtual threads, blocked/pinned virtual-thread signals, connection pool waits, downstream latency and memory from ThreadLocal/captured data.

#### Deep dive

Virtual threads shift the bottleneck from OS threads to dependencies, memory, CPU and application-level limits.

#### Production angle

Metrics should be tagged by workload or dependency. Aggregate JVM thread count alone is not enough.

#### Traps / caveats

- Queue time is often hidden.
- No rejection metric means overload is invisible.
- Virtual-thread count without resource metrics is incomplete.

#### Optional Anki

Q: Key thread-pool saturation metrics?
A: Active threads, queue depth and rejections.

</details>

<a id="mt-diag-006"></a>

<details>
<summary><strong>MT-DIAG-006. How can you detect lock contention or blocking calls in a latency-sensitive path?</strong></summary>

#### Short answer

Use thread dumps, JFR lock events, profiling, metrics and targeted instrumentation.

#### Interview answer

Lock contention often appears as many threads `BLOCKED` on the same monitor, high lock wait events in JFR, or latency around synchronized sections. Blocking calls in sensitive paths show as stacks waiting on sockets, database pools, queues, futures or locks.

Add timing around suspected sections and correlate with request latency.

#### Deep dive

A path can block indirectly through logging, metrics exporters, DNS, connection pools or lazy initialization.

#### Production angle

Collect evidence under load. Contention often appears only at realistic concurrency.

#### Traps / caveats

- Local tests may not create contention.
- CPU profilers alone can miss waiting time.
- Blocking in a shared pool affects unrelated traffic.

#### Optional Anki

Q: Best JVM tool for lock events over time?
A: Java Flight Recorder.

</details>

<a id="mt-diag-007"></a>

<details>
<summary><strong>MT-DIAG-007. How would you test code that uses `ExecutorService` without making tests flaky?</strong></summary>

#### Short answer

Use controllable executors, futures, latches and time-bounded assertions instead of arbitrary sleeps.

#### Interview answer

For unit tests, inject the executor so tests can use a direct executor or a small controlled executor. Assert on futures or callbacks. Use `CountDownLatch`, barriers or Awaitility for synchronization. Always use timeouts so a failed test does not hang forever.

#### Deep dive

Separate orchestration from business logic. Then most logic can be tested synchronously, with a smaller number of concurrency-focused tests.

#### Production angle

Tests should cover shutdown, rejection and exception handling, not only successful execution.

#### Traps / caveats

- Do not depend on scheduling order.
- Avoid `Thread.sleep()` as proof of completion.
- Clean up executors after tests.

#### Optional Anki

Q: Why inject executors?
A: To make async behavior controllable in tests.

</details>

<a id="mt-diag-008"></a>

<details>
<summary><strong>MT-DIAG-008. How would you test timeout, cancellation and `ThreadLocal` cleanup behavior?</strong></summary>

#### Short answer

Use controlled blocking tasks, explicit deadlines and assertions that cleanup happens in `finally`.

#### Interview answer

For timeouts, use fake clocks or short controlled waits where possible. For cancellation, create a task that blocks interruptibly and assert it observes interruption and exits. For ThreadLocal cleanup, run two tasks on the same single-thread executor: the first sets context, the second asserts it is absent.

#### Deep dive

Testing cleanup after exceptions is as important as cleanup after success.

#### Production angle

These tests protect graceful shutdown, request cancellation and user-context isolation.

#### Traps / caveats

- Tests must not hang indefinitely.
- Cancellation is cooperative.
- ThreadLocal cleanup must happen on the worker thread.

#### Optional Anki

Q: Simple ThreadLocal leak test?
A: Reuse one worker thread and assert the next task sees no previous context.

</details>

<a id="mt-diag-009"></a>

<details>
<summary><strong>MT-DIAG-009. Why are `Thread.sleep()`-based tests flaky, and when is Awaitility useful?</strong></summary>

#### Short answer

Sleeps guess timing instead of observing conditions. Awaitility waits until a condition becomes true or times out.

#### Interview answer

If a test sleeps too little, it fails randomly under load. If it sleeps too long, the suite becomes slow. Sleep also does not prove the async operation reached the expected state.

Awaitility is useful when a condition should eventually become true, such as a message processed, metric incremented or future completed.

#### Deep dive

Prefer deterministic coordination when possible. Use Awaitility for integration-style eventual assertions.

#### Production angle

Flaky concurrency tests reduce trust in CI and hide real races.

#### Traps / caveats

- Awaitility is not a substitute for correctness.
- Use meaningful timeouts.
- Avoid asserting on exact scheduling order.

#### Optional Anki

Q: Why avoid sleeps in tests?
A: They guess timing instead of waiting for a condition.

</details>

<details>
<summary><strong>🧠 MT-DIAG-010. What is jcstress, and when would you use it?</strong></summary>

#### Short answer

jcstress is an OpenJDK concurrency stress-testing harness for low-level memory model and race behavior.

#### Interview answer

jcstress runs small concurrent tests many times under varied interleavings to detect outcomes allowed by the JMM. It is useful when developing low-level concurrency utilities, lock-free code or code relying on subtle publication guarantees.

Most ordinary service logic does not need jcstress.

#### Deep dive

It helps answer "is this outcome possible?" rather than "does this web endpoint work?"

#### Production angle

Use it for shared libraries or concurrency primitives where a rare wrong outcome would be costly.

#### Traps / caveats

- It is not a normal unit-test replacement.
- Tests must be very small and carefully written.
- Passing stress tests does not prove all production logic correct.

#### Optional Anki

Q: Main purpose of jcstress?
A: Stress-test low-level concurrent outcomes under the JMM.

</details>

<a id="mt-diag-011"></a>

<details>
<summary><strong>MT-DIAG-011. Why are concurrency tests hard to make deterministic?</strong></summary>

#### Short answer

Because thread scheduling, timing, CPU load and memory interleavings vary between runs.

#### Interview answer

Concurrency bugs often require a rare ordering of events. Tests may pass thousands of times and still miss it. Adding logs, sleeps or a debugger changes timing and can hide the bug.

To improve tests, reduce nondeterminism with injected executors, deterministic clocks, barriers and explicit state assertions.

#### Deep dive

Stress tests increase the chance of finding races but do not replace reasoning about happens-before and invariants.

#### Production angle

For critical concurrency, combine design review, focused tests, stress tests and production monitoring for impossible states.

#### Traps / caveats

- Passing tests are not proof of thread-safety.
- Failing tests may be hard to reproduce.
- Logs can change behavior.

#### Optional Anki

Q: Why can logging hide a race?
A: It changes timing and can introduce synchronization.

</details>

<a id="mt-diag-012"></a>

<details>
<summary><strong>MT-DIAG-012. How would you debug a request that hangs forever or high CPU caused by a busy retry loop?</strong></summary>

#### Short answer

Capture thread dumps and metrics, identify the stuck or hot stack, then trace waits, retries and missing timeouts.

#### Interview answer

For a hang, check request logs, active thread stacks, pool queues, locks, futures, database pool waits and external calls without timeouts. For high CPU, take CPU profiles or repeated dumps and look for tight loops, immediate retries, spin waits or serialization hotspots.

Then stop the bleeding with timeouts, cancellation, backoff, limits or feature disablement before deeper refactoring.

#### Deep dive

Repeated snapshots are more useful than one. If the same stack appears over time, it is likely stuck or hot.

#### Production angle

Collect enough evidence before restart: dumps, JFR, metrics, request IDs and dependency status.

#### Traps / caveats

- A hang may be waiting on a pool, not a lock.
- Retry loops need jitter and deadlines.
- Killing the process loses evidence.

#### Optional Anki

Q: First artifact for a hanging Java request?
A: Thread dump, ideally several over time.

</details>

<a id="mt-perf-001"></a>

<details>
<summary><strong>MT-PERF-001. What is Little's Law, and how can load testing prove a concurrency change helped?</strong></summary>

#### Short answer

Little's Law relates concurrency, throughput and latency: in steady state, concurrency is roughly throughput times latency.

#### Interview answer

If a service handles 100 requests/sec and average latency is 200 ms, it has about 20 requests in flight. This helps reason about required concurrency and queueing. A concurrency change helped only if production-like load tests show better throughput, latency, tail latency, resource usage or failure behavior.

#### Deep dive

Average latency is not enough. Tail latency and saturation points matter for user-facing services.

#### Production angle

Validate changes with realistic downstream behavior, retries, timeouts, payload sizes and container limits.

#### Traps / caveats

- Synthetic tests can miss dependency bottlenecks.
- More concurrency can increase tail latency.
- Measure error rate and saturation, not only throughput.

#### Optional Anki

Q: Little's Law simplified?
A: In-flight work = throughput x latency.

</details>
