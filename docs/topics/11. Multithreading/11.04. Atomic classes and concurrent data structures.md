# 11.04. Atomic classes and concurrent data structures

---

<a id="mt-atom-001"></a>

<details>
<summary><strong>MT-ATOM-001. What are Atomic classes, and how does CAS work conceptually?</strong></summary>

#### Short answer

Atomic classes provide thread-safe operations on single variables, often using compare-and-swap.

#### Interview answer

Classes like `AtomicInteger`, `AtomicLong` and `AtomicReference` support atomic updates without using an explicit lock in user code. CAS means "change this value to a new value only if it is still equal to the expected old value."

If another thread changed the value first, the CAS fails and the caller can retry or choose another action.

#### Deep dive

CAS is usually implemented with CPU atomic instructions and JVM memory semantics. It works well for simple independent updates.

#### Production angle

Atomic variables are good for counters, state flags and immutable snapshot references, but they do not automatically protect larger object invariants.

#### Traps / caveats

- Atomicity is usually per variable.
- High contention can cause retry cost.
- Avoid building complex lock-free algorithms casually.

#### Optional Anki

Q: What does CAS check?
A: That the current value still equals the expected value before updating.

</details>

<a id="mt-atom-002"></a>

<details>
<summary><strong>MT-ATOM-002. What is a CAS retry loop, and why is CAS called optimistic?</strong></summary>

#### Short answer

A CAS retry loop repeatedly computes a new value and tries to install it, assuming contention is rare.

#### Interview answer

CAS is optimistic because it does not lock first. It reads the current value, calculates an update and attempts `compareAndSet`. If another thread changed the value, the operation fails and the loop retries with the new current value.

This is efficient under low/moderate contention but can waste CPU under heavy contention.

#### Deep dive

The update function in a retry loop should be side-effect free because it may run more than once.

#### Production angle

CAS loops are useful for small state transitions. Under heavy write load, a lock, queue or `LongAdder` may be better.

#### Traps / caveats

- Retry loops can spin under contention.
- Side effects inside retry computation can duplicate work.
- CAS does not solve multi-object transactions.

#### Optional Anki

Q: Why is CAS optimistic?
A: It proceeds without locking and retries only if the value changed.

</details>

<a id="mt-atom-003"></a>

<details>
<summary><strong>MT-ATOM-003. What are the advantages and disadvantages of Atomic classes compared with locks?</strong></summary>

#### Short answer

Atomics can be lightweight for simple updates, but locks are better for compound invariants and larger critical sections.

#### Interview answer

Atomic classes avoid explicit lock management and can perform well for independent variables. They also avoid blocking a thread on a monitor. But they are limited: they usually update one value, can spin under contention, and can make complex logic harder to understand.

Locks are simpler when several fields or operations must change together.

#### Deep dive

Lock-free primitives are not automatically faster. Performance depends on contention, cache behavior and amount of work in the critical section.

#### Production angle

Prefer atomics for simple counters or state references; prefer locks or immutable state replacement for business invariants.

#### Traps / caveats

- Atomic code can still be wrong.
- CAS retries can burn CPU.
- Exact multi-field consistency usually needs a different design.

#### Optional Anki

Q: When are locks usually better than atomics?
A: When protecting an invariant involving multiple fields or steps.

</details>

<a id="mt-atom-004"></a>

<details>
<summary><strong>MT-ATOM-004. When would you use `LongAdder` instead of `AtomicLong`?</strong></summary>

#### Short answer

Use `LongAdder` for high-contention counters where exact instantaneous reads are less important than update throughput.

#### Interview answer

`AtomicLong` updates one shared value, so many writers contend on the same memory location. `LongAdder` spreads updates across internal cells and sums them when read, reducing contention under heavy concurrent increments.

It is a good fit for metrics, statistics and frequency counters.

#### Deep dive

`LongAdder.sum()` is not a linearizable snapshot relative to concurrent updates. That is usually fine for approximate metrics but not for strict sequence numbers.

#### Production angle

Use `LongAdder` for counters exposed to monitoring. Use `AtomicLong` when each update must produce an exact globally ordered value.

#### Traps / caveats

- Not suitable for ID generation.
- More memory overhead than one atomic value.
- Reads are eventually consistent under concurrent updates.

#### Optional Anki

Q: Best use case for `LongAdder`?
A: High-contention metrics counters.

</details>

<a id="mt-atom-005"></a>

<details>
<summary><strong>MT-ATOM-005. How can `AtomicReference` help publish immutable snapshots safely?</strong></summary>

#### Short answer

It can atomically replace the current immutable object with a new immutable object.

#### Interview answer

If state is represented as an immutable snapshot, readers can safely use the snapshot without locking. Writers build a new snapshot and publish it with `AtomicReference.set()` or a CAS update. This separates state consistency from reference coordination.

For example, routing rules or feature flags can be held in an immutable object and swapped atomically.

#### Deep dive

If updates depend on the old state, use `updateAndGet` or a CAS loop. The update function should avoid side effects because it may retry.

#### Production angle

This pattern is useful for read-mostly configuration, caches of metadata and small state machines.

#### Traps / caveats

- Snapshots can become stale after a reader obtains them.
- Large snapshots can increase allocation pressure.
- Multiple references are not atomic together.

#### Optional Anki

Q: Why combine immutable snapshots with `AtomicReference`?
A: To safely replace whole consistent state at once.

</details>

<a id="mt-atom-006"></a>

<details>
<summary><strong>🧠 MT-ATOM-006. What is the ABA problem, and how can it be mitigated?</strong></summary>

#### Short answer

ABA happens when a value changes from A to B and back to A, so CAS cannot detect that an intermediate change occurred.

#### Interview answer

CAS only checks the current value against the expected value. If a thread reads A, another thread changes A to B and then back to A, the first thread's CAS may succeed even though the state changed in between.

Mitigations include version stamps, `AtomicStampedReference`, `AtomicMarkableReference`, immutable nodes, hazard-pointer-like designs or avoiding custom lock-free structures.

#### Deep dive

ABA matters most in lock-free data structures where object identity or pointer links carry meaning.

#### Production angle

Most backend code should use existing concurrent data structures rather than implementing lock-free stacks or queues.

#### Traps / caveats

- Atomic references do not track history.
- Object reuse can make ABA easier.
- Versioning must be updated atomically with the reference.

#### Optional Anki

Q: What does ABA hide from CAS?
A: A change away from and back to the expected value.

</details>

<a id="mt-atom-007"></a>

<details>
<summary><strong>🧠 MT-ATOM-007. What is `VarHandle`, and how is it related to Atomic classes?</strong></summary>

#### Short answer

`VarHandle` is a low-level API for typed access to variables with different memory ordering and atomic operations.

#### Interview answer

`VarHandle` can access fields, array elements and other variables using operations such as plain, opaque, acquire, release, volatile and compare-and-set. Atomic classes use similar low-level mechanisms internally, but expose simpler high-level classes.

Most application code should prefer `AtomicInteger`, `AtomicReference` or locks unless building infrastructure.

#### Deep dive

`VarHandle` replaced many direct uses of `sun.misc.Unsafe` for supported low-level variable access.

#### Production angle

Reach for `VarHandle` only when designing highly specialized libraries, data structures or runtime utilities.

#### Traps / caveats

- Memory ordering modes are easy to misuse.
- Harder to read than atomic classes.
- Requires careful benchmarking and correctness testing.

#### Optional Anki

Q: Common higher-level alternative to `VarHandle`?
A: Atomic classes or locks.

</details>

<a id="mt-atom-008"></a>

<details>
<summary><strong>🧠 MT-ATOM-008. What is the difference between lock-free and wait-free progress?</strong></summary>

#### Short answer

Lock-free means at least one thread makes progress. Wait-free means every thread completes its operation in a bounded number of steps.

#### Interview answer

A lock-free algorithm prevents system-wide blocking: even if one thread stalls, another can still make progress. Wait-free is stronger because each participating thread is guaranteed to finish in bounded time.

Wait-free algorithms are harder to design and often more expensive.

#### Deep dive

Lock-free does not mean starvation-free. One unlucky thread can repeatedly lose CAS races while others succeed.

#### Production angle

For normal backend code, use proven JDK concurrent structures. Do not implement custom lock-free algorithms unless there is a strong measured need.

#### Traps / caveats

- Lock-free does not mean no contention.
- Lock-free does not mean faster.
- Wait-free is a stronger guarantee than most libraries provide.

#### Optional Anki

Q: Which is stronger: lock-free or wait-free?
A: Wait-free.

</details>

<a id="mt-atom-009"></a>

<details>
<summary><strong>MT-ATOM-009. What is the difference between atomicity of one variable and atomicity of an invariant involving multiple variables?</strong></summary>

#### Short answer

An atomic variable protects one value; a multi-variable invariant needs one coordinated update policy.

#### Interview answer

`AtomicInteger` can update a counter atomically, but it cannot by itself maintain rules like "map size equals counter" or "balance and ledger entry change together." Those require a lock, a transaction, immutable aggregate replacement or another design that updates the whole invariant consistently.

#### Deep dive

Splitting one invariant across multiple atomics often creates subtle races because each atomic operation is correct individually but the combination is not.

#### Production angle

This matters in caches, quota systems, in-memory registries and domain state machines.

#### Traps / caveats

- Several atomics do not equal one transaction.
- Reads must also observe a consistent state.
- Database constraints may be the right consistency boundary.

#### Optional Anki

Q: What protects a multi-field invariant?
A: One coordinated synchronization or state-update strategy.

</details>

<a id="mt-coll-001"></a>

<details>
<summary><strong>MT-COLL-001. What is the difference between synchronized collections and concurrent collections?</strong></summary>

#### Short answer

Synchronized collections wrap ordinary collections with coarse locking; concurrent collections are designed for concurrent access.

#### Interview answer

`Collections.synchronizedMap(new HashMap<>())` synchronizes individual method calls on one lock. `ConcurrentHashMap` is built for concurrent reads and updates and provides atomic methods such as `putIfAbsent`, `compute` and `merge`.

Concurrent collections also have different iterator semantics, often weakly consistent rather than fail-fast.

#### Deep dive

Synchronized wrappers still need external locking for iteration and compound operations.

#### Production angle

Choose based on invariants and access patterns, not just performance. Sometimes one coarse lock is clearer.

#### Traps / caveats

- Method-level synchronization is not enough for compound logic.
- Concurrent collections do not make values thread-safe.
- Iterator behavior differs from ordinary collections.

#### Optional Anki

Q: Standard concurrent map?
A: `ConcurrentHashMap`.

</details>

<a id="mt-coll-002"></a>

<details>
<summary><strong>MT-COLL-002. What is `ConcurrentHashMap`, and are compound operations automatically atomic?</strong></summary>

#### Short answer

`ConcurrentHashMap` is a thread-safe map for concurrent access, but separate compound operations are not automatically atomic.

#### Interview answer

Individual map operations are safe, and methods like `compute`, `merge` and `putIfAbsent` provide atomic per-key updates. But code such as `get`, then check, then `put` is still a race because another thread can change the key between calls.

Also, invariants involving multiple keys or external state are outside the map's guarantee.

#### Deep dive

`ConcurrentHashMap` forbids null keys and values to avoid ambiguity under concurrent access.

#### Production angle

Use atomic map methods for caches, registries and counters. Keep mapping functions short and local.

#### Traps / caveats

- Per-key atomicity is not whole-system atomicity.
- Values can still be mutable and unsafe.
- Do not run slow I/O inside map computations.

#### Optional Anki

Q: Is `containsKey()` then `put()` atomic?
A: No.

</details>

<a id="mt-coll-003"></a>

<details>
<summary><strong>MT-COLL-003. What pitfalls exist when using `computeIfAbsent()`?</strong></summary>

#### Short answer

The mapping function should be short, deterministic and free of slow side effects.

#### Interview answer

`computeIfAbsent()` atomically installs a value for a key if missing. It is useful for lazy per-key initialization, but the mapping function runs while the map coordinates that key. Slow calls, recursive map updates or side effects can cause contention, surprises or exceptions.

The returned value may also be mutable, so its own thread-safety still matters.

#### Deep dive

Mapping functions may be invoked under internal synchronization. They should not call back into code that may try conflicting map updates.

#### Production angle

For expensive initialization, consider doing work outside the map with futures, locks or explicit cache libraries.

#### Traps / caveats

- Do not block on remote calls in mapping functions.
- Avoid recursive updates.
- Thread-safe map does not make created values thread-safe.

#### Optional Anki

Q: What kind of function belongs in `computeIfAbsent()`?
A: Short, deterministic and local.

</details>

<a id="mt-coll-004"></a>

<details>
<summary><strong>MT-COLL-004. How can `ConcurrentHashMap` and `LongAdder` implement a scalable frequency map?</strong></summary>

#### Short answer

Use the map for per-key counters and `LongAdder` for high-throughput increments.

#### Interview answer

A common pattern is:

```java
freq.computeIfAbsent(key, k -> new LongAdder()).increment();
```

`computeIfAbsent()` safely creates one counter per key. `LongAdder` reduces contention when many threads increment the same counter.

#### Deep dive

This is good for approximate statistics. If a strict linearizable count is required at every read, `LongAdder` may not be the right choice.

#### Production angle

Frequency maps should also have a cleanup strategy. `ConcurrentHashMap` will not evict keys automatically.

#### Traps / caveats

- High-cardinality keys can leak memory.
- `LongAdder.sum()` is not a strict snapshot.
- The key type must have stable `equals()` and `hashCode()`.

#### Optional Anki

Q: Why combine `ConcurrentHashMap` with `LongAdder`?
A: Safe per-key creation plus scalable increments.

</details>

<details>
<summary><strong>MT-COLL-005. What is `CopyOnWriteArrayList`, and when should you use or avoid it?</strong></summary>

#### Short answer

It is a thread-safe list where each write copies the backing array; use it for small read-mostly lists.

#### Interview answer

Readers and iterators see stable snapshots without locking. Writes are expensive because they copy the array. This makes it good for listener lists, plugin registries and small configuration snapshots.

Avoid it for large lists or frequent writes.

#### Deep dive

Iterators do not reflect later modifications and do not support mutation operations like normal iterators.

#### Production angle

It can simplify read-heavy code but create allocation pressure in write-heavy paths.

#### Traps / caveats

- Writes copy the array.
- Iterators see snapshots.
- Elements themselves may still be mutable and unsafe.

#### Optional Anki

Q: Best use case for `CopyOnWriteArrayList`?
A: Small read-mostly lists.

</details>

<a id="mt-coll-006"></a>

<details>
<summary><strong>MT-COLL-006. How is `BlockingQueue` used in producer-consumer designs?</strong></summary>

#### Short answer

Producers put work into the queue and consumers take work from it, with blocking behavior coordinating availability and capacity.

#### Interview answer

A bounded `BlockingQueue` lets producers wait or fail when the queue is full, and lets consumers wait efficiently when the queue is empty. This avoids busy spinning and provides backpressure when capacity is limited.

Executors use this idea internally to manage submitted tasks.

#### Deep dive

A full design needs interruption handling, worker lifecycle, shutdown policy, error handling, retries and metrics.

#### Production angle

Bounded queues protect memory but require a clear overload policy: block, reject, drop or retry later.

#### Traps / caveats

- Ignoring `InterruptedException` breaks shutdown.
- Unbounded queues can hide overload until memory fails.
- Queueing does not make work idempotent.

#### Optional Anki

Q: Why use a bounded queue?
A: To coordinate producers and consumers while limiting backlog.

</details>

<a id="mt-coll-007"></a>

<details>
<summary><strong>MT-COLL-007. What are weakly consistent iterators, and how would you choose between `ConcurrentHashMap`, synchronized maps and immutable maps?</strong></summary>

#### Short answer

Weakly consistent iterators tolerate concurrent modification and may reflect some, all or none of the changes made during iteration.

#### Interview answer

`ConcurrentHashMap` iterators do not throw `ConcurrentModificationException` and can proceed while updates happen. A synchronized map wrapper needs manual locking during iteration. Immutable maps avoid concurrent mutation entirely.

Choose `ConcurrentHashMap` for independent concurrent key updates, a synchronized map when one external lock must guard a broader invariant, and immutable maps for read-only or snapshot state.

#### Deep dive

Iterator semantics are part of correctness. If you need an exact stable view, take a snapshot or use immutable replacement.

#### Production angle

Weakly consistent iteration is fine for metrics or best-effort scans, but not for exact billing or permissions decisions.

#### Traps / caveats

- No fail-fast exception does not mean exact view.
- Synchronized wrappers need external iteration locking.
- Immutable snapshots can become stale.

#### Optional Anki

Q: What iterator does `ConcurrentHashMap` provide?
A: Weakly consistent.

</details>
