<summary><strong>🔥 DB-JOIN-001. What types of JOIN exist?</strong></summary>

<table>
<tbody>
<tr>

</tr>
<tr>
<td valign="top" width="50%">
<p>The main SQL join types are INNER JOIN, LEFT OUTER JOIN, RIGHT OUTER JOIN, FULL OUTER JOIN and CROSS JOIN. There are also self joins and logical semi/anti joins expressed with <code>EXISTS</code>, <code>IN</code>, <code>NOT EXISTS</code> or <code>LEFT JOIN ... IS NULL</code>.</p>
</td>
<td valign="top" width="50%">
<p>Основные SQL join types: INNER JOIN, LEFT OUTER JOIN, RIGHT OUTER JOIN, FULL OUTER JOIN и CROSS JOIN. Также есть self joins и логические semi/anti joins, выражаемые через <code>EXISTS</code>, <code>IN</code>, <code>NOT EXISTS</code> или <code>LEFT JOIN ... IS NULL</code>.</p>

</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A join combines rows from two relations based on a condition. <code>INNER JOIN</code> returns matched rows only. Outer joins preserve unmatched rows from one or both sides. <code>CROSS JOIN</code> creates a Cartesian product.</p>
</td>
<td valign="top" width="50%">
<p>Join объединяет строки из двух relations по условию. <code>INNER JOIN</code> возвращает только совпавшие строки. Outer joins сохраняют unmatched rows с одной или обеих сторон. <code>CROSS JOIN</code> создаёт Cartesian product.</p>

</tr>

</tr>

</td>
<td valign="top" width="50%">
<p>Примеры:</p>
<pre><code class="language-sql">SELECT * FROM orders o INNER JOIN customers c ON c.id = o.customer_id;
SELECT * FROM customers c LEFT JOIN orders o ON o.customer_id = c.id;

</td>
<td valign="top" width="50%">
<p>В production correctness join-а так же важна, как performance. Неправильное условие outer join может незаметно потерять или размножить данные. Для performance важны join cardinality, indexes, statistics и join algorithm.</p>

<td valign="top" width="50%">

<li>Join может размножить строки, если relation не one-to-one.</li>
<li>Join может быть логически корректным, но медленным из-за missing indexes или bad estimates.</li>
<li>SQL join type — не то же самое, что physical join algorithm.</li>

<details>
<summary><strong>🔥 DB-JOIN-002. What is the difference between INNER JOIN and LEFT JOIN?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>INNER JOIN</code> returns only rows that have a match on both sides. <code>LEFT JOIN</code> returns all rows from the left table and fills right-side columns with <code>NULL</code> when there is no match.</p>
</td>
<td valign="top" width="50%">
<p><code>INNER JOIN</code> возвращает только строки, у которых есть совпадение с обеих сторон. <code>LEFT JOIN</code> возвращает все строки из левой таблицы, а при отсутствии совпадения заполняет правую сторону <code>NULL</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use <code>INNER JOIN</code> when the relationship must exist and unmatched rows should be excluded. Use <code>LEFT JOIN</code> when you want to keep the left-side rows even if related data is missing.</p>
</td>
<td valign="top" width="50%">
<p>Используй <code>INNER JOIN</code>, когда связь должна существовать и unmatched rows нужно исключить. Используй <code>LEFT JOIN</code>, когда нужно сохранить строки левой таблицы даже без related data.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example:</p>
<pre><code class="language-sql">-- only customers with orders
SELECT c.id, o.id
FROM customers c
INNER JOIN orders o ON o.customer_id = c.id;

-- all customers, even without orders
SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;</code></pre>
</td>
<td valign="top" width="50%">
<p>Пример:</p>
<pre><code class="language-sql">-- only customers with orders
SELECT c.id, o.id
FROM customers c
INNER JOIN orders o ON o.customer_id = c.id;

-- all customers, even without orders
SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A common production bug is accidentally turning a <code>LEFT JOIN</code> into an <code>INNER JOIN</code> by filtering the right table in <code>WHERE</code>. This can remove rows that should have been preserved.</p>
</td>
<td valign="top" width="50%">
<p>Частая production bug — случайно превратить <code>LEFT JOIN</code> в <code>INNER JOIN</code>, отфильтровав правую таблицу в <code>WHERE</code>. Это может удалить строки, которые должны были сохраниться.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Right-side columns in unmatched <code>LEFT JOIN</code> rows are <code>NULL</code>.</li>
<li>Filters on right-side columns must be placed carefully.</li>
<li>A <code>LEFT JOIN</code> can still multiply rows if the right side has multiple matches.</li>
<li>Do not use <code>LEFT JOIN</code> when an <code>INNER JOIN</code> expresses the business rule better.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Right-side columns в unmatched <code>LEFT JOIN</code> rows равны <code>NULL</code>.</li>
<li>Filters по right-side columns нужно размещать аккуратно.</li>
<li><code>LEFT JOIN</code> всё ещё может размножить строки, если справа несколько matches.</li>
<li>Не используй <code>LEFT JOIN</code>, если business rule лучше выражается через <code>INNER JOIN</code>.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Difference between INNER and LEFT JOIN?<br>A: <code>INNER JOIN</code> returns matched rows only; <code>LEFT JOIN</code> keeps all left rows and uses NULLs for missing right rows.</p>
</td>
<td valign="top" width="50%">
<p>Q: Разница между INNER и LEFT JOIN?<br>A: <code>INNER JOIN</code> возвращает только matches; <code>LEFT JOIN</code> сохраняет все left rows и ставит NULL для missing right rows.</p>
</td>
</tr>
</tbody>

<a id="db-join-003"></a>

<details>
<summary><strong>DB-JOIN-003. What is the difference between LEFT JOIN, RIGHT JOIN and FULL OUTER JOIN?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>LEFT JOIN</code> preserves all rows from the left side, <code>RIGHT JOIN</code> preserves all rows from the right side, and <code>FULL OUTER JOIN</code> preserves unmatched rows from both sides.</p>
</td>
<td valign="top" width="50%">
<p><code>LEFT JOIN</code> сохраняет все строки слева, <code>RIGHT JOIN</code> сохраняет все строки справа, а <code>FULL OUTER JOIN</code> сохраняет unmatched rows с обеих сторон.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>RIGHT JOIN</code> is usually avoidable by swapping table order and using <code>LEFT JOIN</code>. <code>FULL OUTER JOIN</code> is useful when comparing two datasets and you need matched and unmatched rows from both sides.</p>
</td>
<td valign="top" width="50%">
<p><code>RIGHT JOIN</code> обычно можно заменить, поменяв порядок таблиц и использовав <code>LEFT JOIN</code>. <code>FULL OUTER JOIN</code> полезен при сравнении двух datasets, когда нужны matched и unmatched rows с обеих сторон.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example full join for reconciliation:</p>
<pre><code class="language-sql">SELECT a.id AS source_id, b.id AS target_id
FROM source_data a
FULL OUTER JOIN target_data b ON b.id = a.id
WHERE a.id IS NULL OR b.id IS NULL;</code></pre>
</td>
<td valign="top" width="50%">
<p>Пример full join для reconciliation:</p>
<pre><code class="language-sql">SELECT a.id AS source_id, b.id AS target_id
FROM source_data a
FULL OUTER JOIN target_data b ON b.id = a.id
WHERE a.id IS NULL OR b.id IS NULL;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production code, prefer the join form that makes the preserved side obvious. Many teams avoid <code>RIGHT JOIN</code> for readability and use <code>LEFT JOIN</code> consistently.</p>
</td>
<td valign="top" width="50%">
<p>В production code лучше выбирать форму join-а, где preserved side очевидна. Многие команды избегают <code>RIGHT JOIN</code> для читаемости и consistently используют <code>LEFT JOIN</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Outer joins introduce <code>NULL</code>s for missing sides.</li>
<li><code>FULL OUTER JOIN</code> can be expensive on large datasets.</li>
<li>Filters after a full join can accidentally remove the unmatched rows you wanted.</li>
<li><code>RIGHT JOIN</code> often reduces readability.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Outer joins добавляют <code>NULL</code> для missing sides.</li>
<li><code>FULL OUTER JOIN</code> может быть дорогим на больших datasets.</li>
<li>Filters после full join могут случайно удалить unmatched rows, ради которых join и делался.</li>
<li><code>RIGHT JOIN</code> часто ухудшает readability.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does FULL OUTER JOIN preserve?<br>A: Matched rows plus unmatched rows from both sides.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что сохраняет FULL OUTER JOIN?<br>A: Matched rows плюс unmatched rows с обеих сторон.</p>
</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>DB-JOIN-004. What is CROSS JOIN?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>CROSS JOIN</code> returns the Cartesian product of two tables: every row from the first table combined with every row from the second table.</p>
</td>
<td valign="top" width="50%">
<p><code>CROSS JOIN</code> возвращает Cartesian product двух таблиц: каждая строка первой таблицы комбинируется с каждой строкой второй таблицы.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If table A has 100 rows and table B has 50 rows, a cross join returns 5,000 rows. It has no join condition by itself.</p>
</td>
<td valign="top" width="50%">
<p>Если в таблице A 100 строк, а в B 50, cross join вернёт 5,000 строк. Сам по себе он не имеет join condition.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example:</p>
<pre><code class="language-sql">SELECT d.day, r.room_id
FROM days d
CROSS JOIN rooms r;</code></pre>
</td>
<td valign="top" width="50%">
<p>Пример:</p>
<pre><code class="language-sql">SELECT d.day, r.room_id
FROM days d
CROSS JOIN rooms r;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Cross joins are valid for generating combinations, calendars, grids or test data. They are dangerous when they happen accidentally because row counts can explode.</p>
</td>
<td valign="top" width="50%">
<p>Cross joins полезны для генерации combinations, calendars, grids или test data. Они опасны, когда возникают случайно, потому что row count может взорваться.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Missing join conditions can create accidental cross joins.</li>
<li>Cross joins can produce huge intermediate results.</li>
<li>Always estimate cardinality.</li>
<li>Use it intentionally and usually with small inputs or later filters.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Missing join conditions могут создать accidental cross joins.</li>
<li>Cross joins могут дать huge intermediate results.</li>
<li>Всегда оценивай cardinality.</li>
<li>Используй его осознанно и обычно с маленькими inputs или последующими filters.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is CROSS JOIN?<br>A: A Cartesian product of two inputs.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое CROSS JOIN?<br>A: Cartesian product двух inputs.</p>

<a id="db-join-006"></a>

<details>
<summary><strong>🔥 DB-JOIN-006. What is the difference between putting a condition in ON vs WHERE for a LEFT JOIN?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For a <code>LEFT JOIN</code>, a condition in <code>ON</code> controls which right-side rows match. A condition in <code>WHERE</code> is applied after the join and can remove rows with no match, effectively turning the outer join into an inner join.</p>
</td>
<td valign="top" width="50%">
<p>Для <code>LEFT JOIN</code> условие в <code>ON</code> определяет, какие строки справа матчатся. Условие в <code>WHERE</code> применяется после join-а и может удалить строки без match, фактически превратив outer join в inner join.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>This is one of the most important join traps. If you want all customers and only their paid orders, put <code>o.status = &#x27;PAID&#x27;</code> in <code>ON</code>. If you put it in <code>WHERE</code>, customers without paid orders disappear.</p>
</td>
<td valign="top" width="50%">
<p>Это одна из самых важных join traps. Если нужны все customers и только их paid orders, условие <code>o.status = &#x27;PAID&#x27;</code> нужно класть в <code>ON</code>. Если положить его в <code>WHERE</code>, customers без paid orders исчезнут.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Correct for preserving all customers:</p>
<pre><code class="language-sql">SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id
 AND o.status = &#x27;PAID&#x27;;</code></pre>
<p>Different semantics:</p>
<pre><code class="language-sql">SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = &#x27;PAID&#x27;;</code></pre>
</td>
<td valign="top" width="50%">
<p>Корректно, если нужно сохранить всех customers:</p>
<pre><code class="language-sql">SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id
 AND o.status = &#x27;PAID&#x27;;</code></pre>
<p>Другая семантика:</p>
<pre><code class="language-sql">SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = &#x27;PAID&#x27;;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>This bug often appears in reporting endpoints, exports and dashboards: numbers are lower than expected because rows with missing right-side data were filtered out.</p>
</td>
<td valign="top" width="50%">
<p>Этот bug часто встречается в reporting endpoints, exports и dashboards: цифры меньше ожидаемых, потому что rows без right-side data были отфильтрованы.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>For inner joins, optimizer can often move predicates around more freely.</li>
<li>For outer joins, predicate placement can change semantics.</li>
<li>Use <code>WHERE o.id IS NULL</code> intentionally for anti-join patterns.</li>
<li>Always test outer joins with rows that have no match.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Для inner joins optimizer часто может свободнее переносить predicates.</li>

<p>For example, <code>EXISTS</code> may become a semi-join and <code>NOT EXISTS</code> may become an anti-join. Some <code>IN</code> queries can be rewritten similarly. But not every subquery can be decorrelated or flattened.</p>
</td>
<td valign="top" width="50%">
<p>Например, <code>EXISTS</code> может стать semi-join, а <code>NOT EXISTS</code> — anti-join. Некоторые <code>IN</code> queries могут быть переписаны похожим образом. Но не каждый subquery можно decorrelate или flatten.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Reasons a subquery may not be freely rewritten include aggregation, volatile functions, limits, ordering requirements, outer joins, lateral dependencies, and semantic differences around duplicates or <code>NULL</code>.</p>
</td>
<td valign="top" width="50%">
<p>Причины, почему subquery нельзя свободно переписать: aggregation, volatile functions, limits, ordering requirements, outer joins, lateral dependencies и semantic differences вокруг duplicates или <code>NULL</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For production tuning, do not guess whether PostgreSQL rewrote a query. Check the actual plan with <code>EXPLAIN</code>. If the plan is poor, try alternative equivalent forms and compare with <code>EXPLAIN ANALYZE</code>.</p>
</td>
<td valign="top" width="50%">
<p>Для production tuning не нужно гадать, переписал ли PostgreSQL запрос. Смотри actual plan через <code>EXPLAIN</code>. Если plan плохой, пробуй альтернативные equivalent forms и сравнивай через <code>EXPLAIN ANALYZE</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Rewrites must preserve semantics, including duplicates and <code>NULL</code> behavior.</li>
<li>A prettier SQL query may not produce a better plan.</li>
<li>A CTE or subquery can help readability but may affect optimization depending on structure.</li>
<li>Use plans, not assumptions.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Rewrites должны сохранять semantics, включая duplicates и <code>NULL</code> behavior.</li>
<li>Более красивый SQL не обязательно даёт лучший plan.</li>
<li>CTE или subquery может улучшить readability, но повлиять на optimization в зависимости от структуры.</li>
<li>Используй plans, а не assumptions.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">
<p>Q: Во что <code>EXISTS</code> может превратиться internally?<br>A: Часто в semi-join, если rewrite semantically safe.</p>

<a id="db-join-019"></a>

<details>
<summary><strong>DB-JOIN-019. What is the difference between JOIN and UNION?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A <code>JOIN</code> combines columns from related rows side by side. A <code>UNION</code> combines rows from compatible result sets one after another.</p>
</td>
<td valign="top" width="50%">
<p><code>JOIN</code> объединяет columns связанных rows side by side. <code>UNION</code> объединяет rows из совместимых result sets one after another.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use a join when the business question needs data from related tables in the same result row, for example order plus customer email. Use a union when two queries produce the same shape and you want one combined list.</p>
</td>
<td valign="top" width="50%">
<p>Join используют, когда business question требует данные из связанных таблиц в одной result row, например order плюс customer email. Union используют, когда два запроса дают одинаковую shape и нужен один combined list.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Examples:</p>
<pre><code class="language-sql">-- add columns from customers
SELECT o.id, c.email
FROM orders o
JOIN customers c ON c.id = o.customer_id;

-- append rows from two sources
SELECT email FROM customers
UNION
SELECT email FROM newsletter_subscribers;</code></pre>
</td>
<td valign="top" width="50%">
<p>Примеры:</p>
<pre><code class="language-sql">-- add columns from customers
SELECT o.id, c.email
FROM orders o
JOIN customers c ON c.id = o.customer_id;

-- append rows from two sources
SELECT email FROM customers
UNION
SELECT email FROM newsletter_subscribers;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Confusing these operations is a design smell. A join can multiply rows because of relationship cardinality. A union can hide duplicates or force expensive duplicate elimination depending on whether you use <code>UNION</code> or <code>UNION ALL</code>.</p>
</td>
<td valign="top" width="50%">
<p>Путаница между этими operations — design smell. Join может размножить rows из-за relationship cardinality. Union может скрыть duplicates или заставить дорогую duplicate elimination, в зависимости от <code>UNION</code> или <code>UNION ALL</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Set operation inputs must have compatible column counts and types.</li>
<li>Output column names come from the first query.</li>
<li><code>UNION</code> removes duplicates; <code>UNION ALL</code> does not.</li>
<li>Final <code>ORDER BY</code> applies to the combined result.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Inputs set operation должны иметь совместимое количество columns и types.</li>
<li>Output column names берутся из первого запроса.</li>
<li><code>UNION</code> удаляет duplicates; <code>UNION ALL</code> — нет.</li>
<li>Final <code>ORDER BY</code> применяется к combined result.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: JOIN vs UNION?<br>A: JOIN combines columns horizontally; UNION combines compatible rows vertically.</p>
</td>
<td valign="top" width="50%">
<p>Q: JOIN vs UNION?<br>A: JOIN объединяет columns horizontally; UNION объединяет compatible rows vertically.</p>
</td>
</tr>

<a id="db-join-020"></a>

<details>
<summary><strong>🔥 DB-JOIN-020. What is the difference between UNION and UNION ALL?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>UNION</code> appends result sets and removes duplicate rows. <code>UNION ALL</code> appends result sets and keeps duplicates, so it is usually faster.</p>
</td>
<td valign="top" width="50%">
<p><code>UNION</code> объединяет result sets и удаляет duplicate rows. <code>UNION ALL</code> объединяет result sets и сохраняет duplicates, поэтому обычно быстрее.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>My default is <code>UNION ALL</code> unless the business requirement explicitly says duplicates must be removed. Duplicate elimination can require sorting or hashing and can be expensive for large result sets.</p>
</td>
<td valign="top" width="50%">
<p>Мой default — <code>UNION ALL</code>, если business requirement явно не требует убрать duplicates. Duplicate elimination может требовать sorting или hashing и быть дорогой для больших result sets.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example:</p>
<pre><code class="language-sql">SELECT user_id FROM web_events
UNION ALL
SELECT user_id FROM mobile_events;</code></pre>
<p>Use <code>UNION</code> instead only when one row per distinct result is required.</p>
</td>
<td valign="top" width="50%">
<p>Пример:</p>
<pre><code class="language-sql">SELECT user_id FROM web_events
UNION ALL
SELECT user_id FROM mobile_events;</code></pre>
<p>Используй <code>UNION</code> вместо этого только когда нужен один row на distinct result.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production analytics and feeds, accidentally using <code>UNION</code> can add a large hidden cost. Accidentally using <code>UNION ALL</code> can double-count data. Choose based on correctness first, then performance.</p>
</td>
<td valign="top" width="50%">
<p>В production analytics и feeds случайный <code>UNION</code> может добавить большой hidden cost. Случайный <code>UNION ALL</code> может double-count data. Выбирай сначала по correctness, потом по performance.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>UNION</code> removes duplicates across the full output row, not one selected key unless only that key is selected.</li>
<li>For duplicate elimination, set operations treat rows with the same values as duplicates, including <code>NULL</code> values in corresponding columns.</li>
<li><code>UNION ALL</code> is not a safe optimization if duplicates change business results.</li>
<li>Use parentheses when combining set operations with local <code>ORDER BY</code> or <code>LIMIT</code>.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li><code>UNION</code> удаляет duplicates по всей output row, а не по одному key, если выбран не только key.</li>
<li>Для duplicate elimination set operations считают rows с одинаковыми values duplicates, включая <code>NULL</code> в соответствующих columns.</li>
<li><code>UNION ALL</code> не безопасная optimization, если duplicates меняют business results.</li>
<li>Используй parentheses, когда комбинируешь set operations с local <code>ORDER BY</code> или <code>LIMIT</code>.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why is <code>UNION ALL</code> usually faster than <code>UNION</code>?<br>A: It does not remove duplicates.</p>
</td>
<td valign="top" width="50%">
<p>Q: Почему <code>UNION ALL</code> обычно быстрее, чем <code>UNION</code>?<br>A: Он не удаляет duplicates.</p>
</td>
</tr>

<details>
<summary><strong>DB-JOIN-021. What are INTERSECT and EXCEPT used for?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>INTERSECT</code> returns rows common to both result sets. <code>EXCEPT</code> returns rows from the first result set that are not present in the second. By default they remove duplicates; <code>INTERSECT ALL</code> and <code>EXCEPT ALL</code> preserve duplicate counts.</p>
</td>
<td valign="top" width="50%">
<p><code>INTERSECT</code> возвращает rows, общие для обоих result sets. <code>EXCEPT</code> возвращает rows из первого result set, которых нет во втором. По умолчанию они удаляют duplicates; <code>INTERSECT ALL</code> и <code>EXCEPT ALL</code> сохраняют duplicate counts.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>I use them for reconciliation, data-diff queries, permissions and validation checks. <code>INTERSECT</code> answers “what is shared?”, while <code>EXCEPT</code> answers “what is missing from the other side?”</p>
</td>
<td valign="top" width="50%">
<p>Их используют для reconciliation, data-diff queries, permissions и validation checks. <code>INTERSECT</code> отвечает “что общее?”, а <code>EXCEPT</code> — “чего нет на другой стороне?”</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Examples:</p>
<pre><code class="language-sql">-- users present in both sources
SELECT user_id FROM crm_users
INTERSECT
SELECT user_id FROM billing_users;

-- users missing from billing
SELECT user_id FROM crm_users
EXCEPT
SELECT user_id FROM billing_users;</code></pre>
</td>
<td valign="top" width="50%">
<p>Примеры:</p>
<pre><code class="language-sql">-- users present in both sources
SELECT user_id FROM crm_users
INTERSECT
SELECT user_id FROM billing_users;

-- users missing from billing
SELECT user_id FROM crm_users
EXCEPT
SELECT user_id FROM billing_users;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For large datasets, set operations can require sorting or hashing large intermediate results. Sometimes a join, semi-join or anti-join is clearer or faster, especially when indexes and filters can reduce one side early.</p>
</td>
<td valign="top" width="50%">
<p>На больших datasets set operations могут требовать sorting или hashing больших intermediate results. Иногда join, semi-join или anti-join яснее или быстрее, особенно когда indexes и filters могут рано сократить одну сторону.</p>

</tr>

<td valign="top" width="50%">

<li>Columns are matched by position, not by name.</li>
<li>Input column types must be compatible.</li>
<li><code>INTERSECT</code> has higher precedence than <code>UNION</code> and <code>EXCEPT</code> in PostgreSQL; use parentheses for clarity.</li>
<li>Default set operations remove duplicates; use <code>ALL</code> variants when duplicate counts matter.</li>
<li>Final ordering is not guaranteed unless you add a final <code>ORDER BY</code>.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Columns сопоставляются по position, а не по name.</li>
<li>Input column types должны быть compatible.</li>
<li>В PostgreSQL <code>INTERSECT</code> имеет higher precedence, чем <code>UNION</code> и <code>EXCEPT</code>; для ясности используй parentheses.</li>
<li>Default set operations удаляют duplicates; используй <code>ALL</code> variants, когда duplicate counts важны.</li>
<li>Final ordering не гарантирован без final <code>ORDER BY</code>.</li>

</td>
<td valign="top" width="50%">
