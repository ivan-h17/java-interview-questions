<summary><strong>DB-TX-002. What is Atomicity?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Atomicity means a transaction is all-or-nothing.</p>
</td>
<td valign="top" width="50%">
<p>Atomicity означает all-or-nothing.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Either all changes commit or none of them do.</p>
</td>
<td valign="top" width="50%">
<p>Либо все changes commit, либо ни одно.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If creating an order writes an order row, items, and an outbox event, atomicity prevents only part of that data from being committed.</p>
</td>
<td valign="top" width="50%">
<p>Если создание order пишет order row, items и outbox event, atomicity предотвращает commit только части данных.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In Java/Spring, atomicity depends on correct transaction boundaries and avoiding side effects outside the transaction model.</p>
</td>
<td valign="top" width="50%">
<p>В Java/Spring atomicity зависит от правильных transaction boundaries и отсутствия side effects вне transaction model.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Wrong transaction boundaries break atomicity.</li><li>External calls are not automatically part of DB transactions.</li><li>Rollback rules in Spring matter.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>Неправильные transaction boundaries ломают atomicity.</li><li>External calls не являются частью DB transaction автоматически.</li><li>Rollback rules в Spring важны.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>

<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>

<td valign="top" width="50%">

</td>
<td valign="top" width="50%">
<p>Consistency означает, что транзакция переводит базу из одного valid state в другой.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Validity is defined by constraints, foreign keys, unique constraints, checks, and business invariants.</p>
</td>
<td valign="top" width="50%">
<p>Validity задаётся constraints, foreign keys, unique constraints, checks и business invariants.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The database can enforce structural invariants, but the application must model business rules correctly.</p>
</td>
<td valign="top" width="50%">
<p>База может enforce structural invariants, но приложение должно корректно моделировать business rules.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For senior backend work, push critical invariants into DB constraints when possible, especially uniqueness and referential integrity.</p>
</td>
<td valign="top" width="50%">
<p>Для senior backend важно переносить critical invariants в DB constraints, когда возможно, особенно uniqueness и referential integrity.</p>

</tr>

<td valign="top" width="50%">
<ul><li>DB consistency — не то же самое, что distributed consistency.</li><li>Application bugs всё равно могут нарушать business consistency.</li><li>Не полагайся только на Java validation для critical invariants.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>

<td valign="top" width="50%">

<th colspan="2" align="left">Optional Anki</th>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Repeatable Read gives a transaction a stable snapshot for its lifetime.</p>
</td>
<td valign="top" width="50%">
<p>Repeatable Read даёт транзакции стабильный snapshot на всё время жизни.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In PostgreSQL, Repeatable Read is snapshot isolation: it gives a stable transaction snapshot and prevents phantom reads, but it is still not Serializable.</p>
</td>
<td valign="top" width="50%">
<p>В PostgreSQL Repeatable Read — это snapshot isolation: он даёт stable transaction snapshot и предотвращает phantom reads, но всё равно не является Serializable.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The transaction does not see changes committed after its snapshot was taken. However, snapshot isolation can still allow write-skew-style business invariant bugs when two transactions update different rows after reading the same predicate.</p>
