# Query planner, statistics and EXPLAIN

<a id="db-plan-001"></a>

<details>
<summary><strong>DB-PLAN-001. What is the PostgreSQL query planner?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The query planner chooses a physical execution plan for a SQL query.</p>
</td>
<td valign="top" width="50%">
<p>Query planner выбирает физический план выполнения SQL-запроса.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Because SQL is declarative, PostgreSQL must decide which scans, indexes, join order, join algorithms, sorts, aggregates, and memory strategies to use.</p>
</td>
<td valign="top" width="50%">
<p>Поскольку SQL декларативный, PostgreSQL должен решить, какие scans, indexes, join order, join algorithms, sorts, aggregates и memory strategies использовать.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The planner is cost-based. It estimates row counts and costs using statistics, table/index metadata, configuration, and query predicates. The cheapest estimated plan wins.</p>
</td>
<td valign="top" width="50%">
<p>Planner cost-based. Он оценивает row counts и costs через статистику, metadata таблиц/индексов, настройки и predicates запроса. Побеждает самый дешёвый estimated plan.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Bad production plans usually come from bad estimates, stale statistics, skewed data, missing indexes, generic prepared plans, or non-representative parameters.</p>
</td>
<td valign="top" width="50%">
<p>Плохие production plans обычно возникают из bad estimates, stale statistics, skewed data, missing indexes, generic prepared plans или нерепрезентативных параметров.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Cost is an estimate, not milliseconds.</li><li>The planner can choose a valid but slow plan.</li><li>Planner behavior depends on data distribution.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>Cost — оценка, не миллисекунды.</li><li>Planner может выбрать валидный, но медленный план.</li><li>Planner behavior зависит от распределения данных.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the PostgreSQL query planner?<br>A: The query planner chooses a physical execution plan for a SQL query.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое PostgreSQL query planner?<br>A: Query planner выбирает физический план выполнения SQL-запроса.</p>
</td>
</tr>
</tbody>
</table>

<summary><strong>🔥 DB-PLAN-002. How does PostgreSQL decide whether to use an index?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>It compares estimated costs of sequential scan, index scan, bitmap scan, and other paths.</p>
</td>
<td valign="top" width="50%">
<p>Он сравнивает estimated costs sequential scan, index scan, bitmap scan и других paths.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>PostgreSQL estimates predicate selectivity and decides whether using the index plus heap access is cheaper than reading the table sequentially.</p>
</td>
<td valign="top" width="50%">
<p>PostgreSQL оценивает selectivity predicate и решает, дешевле ли индекс плюс heap access, чем последовательное чтение таблицы.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The decision uses statistics such as <code>n_distinct</code>, MCVs, histograms, null fraction, table size, index structure, correlation, and cost parameters like random/sequential page cost.</p><pre><code class="language-sql">EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = &#x27;ACTIVE&#x27;;</code></pre>
</td>
<td valign="top" width="50%">
<p>Решение использует statistics: <code>n_distinct</code>, MCVs, histograms, null fraction, размер таблицы, структуру индекса, correlation и cost parameters вроде random/sequential page cost.</p><pre><code class="language-sql">EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = &#x27;ACTIVE&#x27;;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If PostgreSQL ignores an index, inspect <code>EXPLAIN (ANALYZE, BUFFERS)</code>, selectivity, stale stats, expression mismatch, composite index order, heap fetches, and whether a partial/expression index is needed.</p>
</td>
<td valign="top" width="50%">
<p>Если PostgreSQL игнорирует индекс, проверь <code>EXPLAIN (ANALYZE, BUFFERS)</code>, selectivity, stale stats, expression mismatch, order composite index, heap fetches и нужен ли partial/expression index.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Index existence does not imply index usage.</li><li>Low selectivity can make Seq Scan cheaper.</li><li>A function on a column may require an expression index.</li><li>Stale statistics can mislead the planner.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>Наличие индекса не означает его использование.</li><li>Low selectivity может сделать Seq Scan дешевле.</li><li>Функция над колонкой может требовать expression index.</li><li>Stale statistics могут обмануть planner.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: How does PostgreSQL decide whether to use an index?<br>A: It compares estimated costs of sequential scan, index scan, bitmap scan, and other paths.</p>
</td>
<td valign="top" width="50%">
<p>Q: Как PostgreSQL решает, использовать ли индекс?<br>A: Он сравнивает estimated costs sequential scan, index scan, bitmap scan и других paths.</p>
</td>
</tr>

<details>
<summary><strong>DB-PLAN-003. What statistics does PostgreSQL use to estimate selectivity?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>PostgreSQL uses statistics collected by <code>ANALYZE</code>: row counts, null fraction, distinct values, most common values, histograms, and correlation.</p>
</td>
<td valign="top" width="50%">
<p>PostgreSQL использует статистику, собранную <code>ANALYZE</code>: row counts, null fraction, distinct values, most common values, histograms и correlation.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>These statistics help estimate how many rows a predicate will return and therefore influence scan type, join order, join algorithm, and memory-heavy nodes.</p>
</td>
<td valign="top" width="50%">
<p>Эти statistics помогают оценить, сколько строк вернёт predicate, и поэтому влияют на scan type, join order, join algorithm и memory-heavy nodes.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Single-column stats may fail for correlated columns. Extended statistics can help with dependencies, ndistinct combinations, and MCV lists across multiple columns.</p><pre><code class="language-sql">CREATE STATISTICS users_tenant_status_stats
  (dependencies, ndistinct, mcv)
  ON tenant_id, status
  FROM users;

ANALYZE users;</code></pre>
</td>
<td valign="top" width="50%">
<p>Single-column stats могут ошибаться на correlated columns. Extended statistics помогают с dependencies, ndistinct combinations и MCV lists по нескольким колонкам.</p><pre><code class="language-sql">CREATE STATISTICS users_tenant_status_stats
  (dependencies, ndistinct, mcv)
  ON tenant_id, status
  FROM users;

ANALYZE users;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If actual rows differ greatly from estimated rows, inspect <code>pg_stats</code>, run <code>ANALYZE</code>, and consider extended statistics or a higher per-column statistics target.</p><pre><code class="language-sql">ALTER TABLE users ALTER COLUMN tenant_id SET STATISTICS 1000;
ANALYZE users;</code></pre>
</td>
<td valign="top" width="50%">
<p>Если actual rows сильно отличаются от estimated rows, проверь <code>pg_stats</code>, запусти <code>ANALYZE</code> и подумай об extended statistics или higher per-column statistics target.</p><pre><code class="language-sql">ALTER TABLE users ALTER COLUMN tenant_id SET STATISTICS 1000;
ANALYZE users;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Statistics are sampled, not exact.</li><li>Multi-column correlation can break estimates unless extended stats exist.</li><li>Large imports/deletes can make stats stale.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>Statistics sampled, не exact.</li><li>Multi-column correlation может ломать estimates, если нет extended stats.</li><li>Большие imports/deletes могут сделать stats stale.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What statistics does PostgreSQL use to estimate selectivity?<br>A: PostgreSQL uses statistics collected by ANALYZE: row counts, null fraction, distinct values, most common values, histograms, and correlation.</p>
</td>
<td valign="top" width="50%">
<p>Q: Какую статистику PostgreSQL использует для оценки селективности?<br>A: PostgreSQL использует статистику, собранную ANALYZE: row counts, null fraction, distinct values, most common values, histograms и correlation.</p>
</td>
</tr>
</tbody>
