# Migrations and production safety

This section covers versioned migrations, zero-downtime schema evolution, safe DDL, backfills, and deployment sequencing.

<a id="db-mig-001"></a>

<details>
<summary><strong>DB-MIG-001. What is a database migration?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A database migration is a versioned change to database schema or data that is applied in a controlled, repeatable way.</p>
</td>
<td valign="top" width="50%">
<p>Database migration — versioned изменение schema или data, применяемое controlled и repeatable способом.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Migrations include actions like creating tables, adding columns, creating indexes, changing constraints, or backfilling data.</p>
<p>They are stored in version control and applied consistently across environments.</p>
</td>
<td valign="top" width="50%">
<p>Migrations включают create tables, add columns, create indexes, change constraints или backfill data.</p>
<p>Они хранятся в version control и применяются consistently across environments.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A migration system tracks which migrations were applied, prevents accidental reordering, and makes deployments reproducible.</p>
<p>Schema changes are part of application delivery and need review like code.</p>
</td>
<td valign="top" width="50%">
<p>Migration system tracks applied migrations, prevents accidental reordering и makes deployments reproducible.</p>
<p>Schema changes — часть application delivery и должны review like code.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, migrations must be safe for live traffic: avoid long locks, table rewrites, unbounded backfills and breaking old app versions.</p>
<p>Large migrations need rollout plans, monitoring, and rollback/recovery strategy.</p>
</td>
<td valign="top" width="50%">
<p>В production migrations должны быть safe for live traffic: avoid long locks, table rewrites, unbounded backfills и breaking old app versions.</p>
<p>Large migrations требуют rollout plan, monitoring и rollback/recovery strategy.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Migrations are not only DDL; they can include data changes.</li>
<li>A migration that works locally can lock production.</li>
<li>Manual hotfixes cause schema drift.</li>
<li>Rollback is not always the reverse SQL.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Migrations — не только DDL; могут include data changes.</li>
<li>Migration that works locally can lock production.</li>
<li>Manual hotfixes cause schema drift.</li>
<li>Rollback не всегда reverse SQL.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>

</td>
<td valign="top" width="50%">

<summary><strong>🔥 DB-MIG-003. What is a zero-downtime migration?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A zero-downtime migration changes schema or data without breaking old or new application versions while traffic continues.</p>
</td>
<td valign="top" width="50%">
<p>Zero-downtime migration меняет schema или data, не ломая old/new application versions при продолжающемся traffic.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The core idea is backward and forward compatibility. During deployment, old and new code may run at the same time, so the database must support both.</p>
<p>Typical strategy: expand schema, deploy code that supports both, backfill, switch reads/writes, then contract old schema later.</p>
</td>
<td valign="top" width="50%">
<p>Core idea — backward и forward compatibility. During deployment old and new code могут run simultaneously, поэтому database должна support both.</p>
<p>Typical strategy: expand schema, deploy code supporting both, backfill, switch reads/writes, затем contract old schema later.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Zero-downtime migrations avoid destructive changes in the first step. Do not rename/drop/change meaning of a column while old code still uses it.</p>
<p>Data backfills should be chunked and observable.</p>
</td>
<td valign="top" width="50%">
<p>Zero-downtime migrations avoid destructive changes at first step. Не rename/drop/change meaning column, пока old code uses it.</p>
<p>Data backfills should be chunked and observable.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, plan deployments as multiple releases. Use feature flags, dual-write/dual-read carefully, validation queries, and rollback points.</p>
<p>Define what zero-downtime means for your SLA: no app errors, no write blocking, no read inconsistency.</p>
</td>
<td valign="top" width="50%">
<p>В production plan deployments as multiple releases. Use feature flags, dual-write/dual-read carefully, validation queries и rollback points.</p>
<p>Define what zero-downtime means для SLA: no app errors, no write blocking, no read inconsistency.</p>

</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Zero-downtime is a process, not one SQL trick.</li>
<li>Rollback after partial data migration may be hard.</li>
<li>Dual writes can create inconsistencies.</li>
<li>Long locks can still cause downtime.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Zero-downtime — process, не one SQL trick.</li>
<li>Rollback после partial data migration can be hard.</li>

<li>Long locks всё равно cause downtime.</li>

<summary><strong>DB-MIG-004. What is expand-and-contract migration?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Expand-and-contract is a multi-step migration pattern: add new schema first, migrate usage, then remove old schema later.</p>
</td>
<td valign="top" width="50%">
<p>Expand-and-contract — multi-step migration pattern: сначала add new schema, migrate usage, потом remove old schema later.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Expand phase adds backward-compatible objects: new columns, tables, indexes or constraints. Migration phase updates code and backfills data. Contract phase removes old objects after they are unused.</p>
<p>It is the standard approach for zero-downtime schema evolution.</p>
</td>
<td valign="top" width="50%">
<p>Expand phase добавляет backward-compatible objects: new columns, tables, indexes или constraints. Migration phase updates code и backfills data. Contract phase removes old objects после unused.</p>
<p>Это standard approach for zero-downtime schema evolution.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example: add <code>full_name</code> while old <code>first_name</code>/<code>last_name</code> still exist; deploy code that writes both; backfill; read new column; remove old columns later.</p>
<p>Each step should be deployable and reversible enough.</p>
</td>
<td valign="top" width="50%">
<p>Пример: add <code>full_name</code>, пока old <code>first_name</code>/<code>last_name</code> still exist; deploy code writes both; backfill; read new column; remove old columns later.</p>
<p>Каждый step should be deployable and reversible enough.</p>

<p>Keep compatibility across rolling deployments.</p>
</td>
<td valign="top" width="50%">
<p>В production separate expand and contract минимум by one release. Verify metrics и logs перед dropping old columns.</p>

</tr>
<tr>
<td valign="top" width="50%">

<li>Dual-write logic must be tested.</li>
<li>Backfills can take longer than planned.</li>
<li>Old data and new data must be reconciled.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Contract too early ломает old code.</li>
<li>Dual-write logic must be tested.</li>

<summary><strong>DB-MIG-006. How would you add a NOT NULL column to a huge table safely?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Add it nullable, backfill in batches, validate data, then add NOT NULL or a validated constraint in a separate step.</p>
</td>
<td valign="top" width="50%">
<p>Добавить nullable, backfill in batches, validate data, затем add NOT NULL или validated constraint separate step.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Adding a NOT NULL column with a value for every existing row can be risky on a huge table. The safe pattern is multi-step.</p>
<p>First add nullable column. Then deploy code writing it. Then backfill old rows in chunks. Then enforce non-null.</p>
</td>
<td valign="top" width="50%">
<p>Adding NOT NULL column with value for every existing row can be risky on huge table. Safe pattern is multi-step.</p>
<p>Сначала add nullable column. Затем deploy code writing it. Then backfill old rows in chunks. Then enforce non-null.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For enforcement, a common PostgreSQL pattern is: add <code>CHECK (new_col IS NOT NULL) NOT VALID</code>, validate it separately with <code>VALIDATE CONSTRAINT</code>, then set <code>NOT NULL</code> in a short controlled step.</p>
<p>Test the exact PostgreSQL version and lock behavior on staging before running it on a hot table.</p>
</td>
<td valign="top" width="50%">
<p>Для enforcement часто используют PostgreSQL pattern: добавить <code>CHECK (new_col IS NOT NULL) NOT VALID</code>, отдельно выполнить <code>VALIDATE CONSTRAINT</code>, затем коротким контролируемым шагом поставить <code>NOT NULL</code>.</p>
<p>Перед запуском на hot table нужно проверить точную версию PostgreSQL и lock behavior на staging.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">
<p>Backfill должен быть rate-limited, resumable и monitored. Маленькие transactions помогают избежать long locks, WAL spikes и replication lag.</p>
<p>Для DDL steps стоит задавать <code>lock_timeout</code> и <code>statement_timeout</code>, чтобы migration быстро падала, а не вставала в production lock queue. Application должна уметь работать с NULL до финального enforcement step.</p>

</tr>

<li>NOT NULL too early breaks old writes.</li>

<li>Validation can still consume resources.</li>

<td valign="top" width="50%">

<summary><strong>🔥 DB-MIG-007. How would you add a new index on a large production table?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use CREATE INDEX CONCURRENTLY when possible, run it separately, monitor progress, and validate it with real query plans.</p>
</td>
<td valign="top" width="50%">
<p>Использовать CREATE INDEX CONCURRENTLY где возможно, run separately, monitor progress и validate with real query plans.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A regular CREATE INDEX can block writes to the table. On large hot tables, that can cause downtime.</p>
<p><code>CREATE INDEX CONCURRENTLY</code> avoids blocking normal writes for most of the build, but takes longer and has its own restrictions.</p>
</td>
<td valign="top" width="50%">
<p>Regular CREATE INDEX может block writes to table. На large hot tables это can cause downtime.</p>
<p><code>CREATE INDEX CONCURRENTLY</code> avoids blocking normal writes for most build, но takes longer и имеет restrictions.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Before adding the index, confirm it is needed: inspect slow query, expected selectivity, existing indexes, write overhead, and possible redundancy.</p>
<p>After creation, run <code>EXPLAIN (ANALYZE, BUFFERS)</code> on representative queries.</p>
</td>
<td valign="top" width="50%">
<p>Перед adding index confirm needed: inspect slow query, expected selectivity, existing indexes, write overhead и possible redundancy.</p>
<p>After creation run <code>EXPLAIN (ANALYZE, BUFFERS)</code> on representative queries.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, avoid wrapping CREATE INDEX CONCURRENTLY in a transaction block. Schedule it, monitor locks/progress, disk usage, replication lag and failure cleanup.</p>
<p>If it fails, it may leave an invalid index that needs cleanup.</p>
</td>
<td valign="top" width="50%">
<p>В production avoid wrapping CREATE INDEX CONCURRENTLY in transaction block. Schedule it, monitor locks/progress, disk usage, replication lag and failure cleanup.</p>
<p>If it fails, it may leave invalid index requiring cleanup.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
