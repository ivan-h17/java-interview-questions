# Data modeling and schema design

<a id="db-model-001"></a>

<details>
<summary><strong>DB-MODEL-001. What is database normalization?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Database normalization is a way to design relational schemas so data is stored with less duplication and fewer update anomalies.</p>
</td>
<td valign="top" width="50%">
<p>Нормализация базы данных — это подход к проектированию реляционной схемы, который уменьшает дублирование данных и снижает риск update anomalies.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Normalization means organizing tables and relationships so each fact is stored in one logical place. Instead of duplicating customer data in every order row, we store customers separately and reference them from orders.</p>
<p>The goal is correctness and maintainability: fewer duplicated values, fewer inconsistent updates, and clearer relationships between entities.</p>
<p>In practice, I usually aim for a reasonably normalized OLTP schema first, and denormalize only when there is a clear read-performance or reporting reason.</p>
</td>
<td valign="top" width="50%">
<p>Нормализация означает, что таблицы и связи организованы так, чтобы каждый факт хранился в одном логическом месте. Например, данные клиента не дублируются в каждой строке заказа, а хранятся отдельно и связываются с заказами.</p>
<p>Цель — корректность и поддерживаемость: меньше дублирования, меньше inconsistent updates и понятнее связи между сущностями.</p>
<p>На практике для OLTP-системы обычно сначала делают достаточно нормализованную схему, а денормализуют только при понятной причине: производительность чтения или отчетность.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Without normalization, one business fact may appear in many rows. If it changes, every copy must be updated correctly.</p>
<p>Typical anomalies:</p>
<ul>
<li>Update anomaly: one copy changes, another copy stays stale.</li>
<li>Insert anomaly: cannot add a fact without unrelated data.</li>
<li>Delete anomaly: deleting one row accidentally removes the only copy of another fact.</li>
</ul>
<p>Normalization is based on functional dependencies: which attributes determine other attributes. At senior level, the important part is not memorizing forms mechanically, but understanding which table owns each business fact.</p>
</td>
<td valign="top" width="50%">
<p>Без нормализации один бизнес-факт может повторяться во многих строках. Если он меняется, нужно корректно обновить все копии.</p>
<p>Типичные anomalies:</p>
<ul>
<li>Update anomaly: одна копия обновилась, другая осталась старой.</li>
<li>Insert anomaly: нельзя добавить один факт без несвязанных данных.</li>
<li>Delete anomaly: удаление строки случайно удаляет единственную копию другого факта.</li>
</ul>
<p>Нормализация основана на functional dependencies: какие атрибуты определяют другие атрибуты. На senior-уровне важнее не механически помнить формы, а понимать, какая таблица владеет каждым бизнес-фактом.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Normalized schemas are usually easier to keep correct under concurrent writes. They also make constraints and foreign keys more meaningful. The trade-off is that reads may require more joins.</p>
</td>
<td valign="top" width="50%">
<p>Нормализованные схемы обычно проще держать корректными при concurrent writes. Constraints и foreign keys становятся более осмысленными. Компромисс — чтение может требовать больше join-ов.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Normalization is not a goal by itself; it supports correctness.</li>
<li>Over-normalization can make reads and application code unnecessarily complex.</li>
<li>Analytics schemas are often intentionally denormalized.</li>
<li>Do not denormalize before measuring or having a clear access pattern.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Нормализация не самоцель; она поддерживает корректность.</li>
<li>Избыточная нормализация может усложнить чтение и application code.</li>
<li>Аналитические схемы часто специально денормализованы.</li>
<li>Не стоит денормализовать без измерений или понятного access pattern.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is normalization mainly for?<br>A: Reducing duplication and update anomalies.</p>
</td>
<td valign="top" width="50%">
<p>Q: Для чего в основном нужна нормализация?<br>A: Чтобы уменьшить дублирование и update anomalies.</p>
</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>DB-MODEL-002. What are 1NF, 2NF and 3NF?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>1NF means atomic column values, 2NF removes partial dependency on a composite key, and 3NF removes transitive dependency between non-key attributes.</p>
</td>
<td valign="top" width="50%">
<p>1NF означает атомарные значения в колонках, 2NF убирает partial dependency от составного ключа, а 3NF убирает transitive dependency между non-key атрибутами.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>First normal form says that columns should contain atomic values, not repeating groups or arrays of independent facts.</p>
<p>Second normal form matters when the table has a composite key: every non-key column should depend on the whole key, not just part of it.</p>
<p>Third normal form means non-key columns should depend on the key, not on other non-key columns. For example, if <code>customer_id</code> determines <code>customer_email</code>, order rows should usually store <code>customer_id</code>, not duplicate the email as an authoritative fact.</p>
</td>
<td valign="top" width="50%">
<p>Первая нормальная форма говорит, что колонки должны содержать атомарные значения, а не повторяющиеся группы или массивы независимых фактов.</p>
<p>Вторая нормальная форма важна, когда у таблицы составной ключ: каждая non-key колонка должна зависеть от всего ключа, а не от его части.</p>
<p>Третья нормальная форма означает, что non-key колонки должны зависеть от ключа, а не от других non-key колонок. Например, если <code>customer_id</code> определяет <code>customer_email</code>, в заказах обычно стоит хранить <code>customer_id</code>, а не дублировать email как источник истины.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example 2NF issue: table key is <code>(order_id, product_id)</code>, but <code>order_date</code> depends only on <code>order_id</code>. It belongs in <code>orders</code>, not in <code>order_items</code>.</p>
<p>Example 3NF issue: <code>zip_code</code> determines <code>city</code>. If every customer row stores both and city changes/corrects, updates can become inconsistent.</p>
<p>3NF is not the final possible normal form. BCNF is stricter and removes more dependency anomalies, but real OLTP schemas are usually designed by balancing correctness, simplicity, and access patterns.</p>
</td>
<td valign="top" width="50%">
<p>Пример проблемы 2NF: ключ таблицы — <code>(order_id, product_id)</code>, но <code>order_date</code> зависит только от <code>order_id</code>. Значит, ему место в <code>orders</code>, а не в <code>order_items</code>.</p>
<p>Пример проблемы 3NF: <code>zip_code</code> определяет <code>city</code>. Если каждая строка customer хранит оба значения, исправления city могут стать inconsistent.</p>
<p>3NF — не последняя возможная normal form. BCNF строже и убирает больше dependency anomalies, но реальные OLTP-схемы обычно проектируют как баланс correctness, простоты и access patterns.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In interviews, the exact academic definitions matter less than recognizing duplication and dependency problems in real schemas.</p>
</td>
<td valign="top" width="50%">
<p>На интервью точные академические определения обычно менее важны, чем способность увидеть дублирование и dependency problems в реальной схеме.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>2NF is mainly relevant for composite keys.</li>
<li>3NF does not mean there is no duplication anywhere; it means dependencies are modeled correctly.</li>
<li>Real production schemas may intentionally violate normal forms for performance.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>2NF в основном актуальна для составных ключей.</li>
<li>3NF не означает, что дублирования нет вообще; она про корректные зависимости.</li>
<li>Production-схемы иногда осознанно нарушают normal forms ради производительности.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is 1NF?<br>A: Atomic values and no repeating groups.</p>
<p>Q: What does 3NF remove?<br>A: Transitive dependencies between non-key attributes.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое 1NF?<br>A: Атомарные значения и отсутствие repeating groups.</p>
<p>Q: Что убирает 3NF?<br>A: Transitive dependencies между non-key атрибутами.</p>
</td>
</tr>
</tbody>
</table>

</details>

<details>
<summary><strong>🔥 DB-MODEL-003. When would you intentionally denormalize a schema?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>I would denormalize when a normalized model is correct but too slow or inconvenient for a proven read pattern, and the team can safely maintain the duplicated data.</p>
</td>
<td valign="top" width="50%">
<p>Я бы денормализовал схему, когда нормализованная модель корректна, но слишком медленная или неудобная для подтвержденного read pattern, и команда может безопасно поддерживать дублированные данные.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Denormalization means storing derived or duplicated data intentionally. Typical reasons are faster reads, fewer joins, reporting needs, cached counters, search views, or preserving historical snapshots.</p>
<p>I would not denormalize only because “joins are bad”. I would first understand the access pattern, check the execution plan, add proper indexes, and measure. If reads are still too expensive, denormalization can be a valid trade-off.</p>
</td>
<td valign="top" width="50%">
<p>Денормализация означает осознанное хранение derived или duplicated data. Типичные причины: ускорение чтения, меньше join-ов, отчеты, cached counters, search views или сохранение исторических snapshots.</p>
<p>Я бы не денормализовал просто потому что “join-ы плохие”. Сначала нужно понять access pattern, посмотреть execution plan, добавить нужные индексы и измерить. Если чтение все еще дорогое, денормализация может быть нормальным trade-off.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Examples:</p>
<ul>
<li>Store <code>orders.total_amount</code> instead of summing items every time.</li>
<li>Store customer name in an invoice snapshot because invoices must preserve historical data.</li>
<li>Create a read model for a dashboard or search page.</li>
</ul>
</td>
<td valign="top" width="50%">
<p>Примеры:</p>
<ul>
<li>Хранить <code>orders.total_amount</code>, а не каждый раз суммировать позиции.</li>
<li>Хранить имя клиента в invoice snapshot, потому что invoice должен сохранять исторические данные.</li>
<li>Создать read model для dashboard или search page.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The hard part is keeping denormalized data consistent. You need a clear owner, update strategy, backfill plan, reconciliation checks, and monitoring for drift.</p>
<p>Common maintenance strategies are transactional updates in the same write path, database triggers, background jobs, CDC/event-driven updates, batch rebuilds, and periodic reconciliation against the source-of-truth tables.</p>
</td>
<td valign="top" width="50%">
<p>Сложность в том, чтобы держать denormalized data консистентной. Нужен понятный owner, стратегия обновления, backfill plan, reconciliation checks и мониторинг drift.</p>
<p>Типичные стратегии поддержки: transactional updates в том же write path, database triggers, background jobs, CDC/event-driven updates, batch rebuilds и периодическая reconciliation со source-of-truth таблицами.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Denormalization improves some reads but makes writes and consistency harder.</li>
<li>It can create stale data and race conditions.</li>
<li>It should be documented as an intentional decision, not accidental duplication.</li>
<li>Sometimes a materialized view, cache, or index is a better first step.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Денормализация ускоряет некоторые чтения, но усложняет записи и consistency.</li>
<li>Она может привести к stale data и race conditions.</li>
<li>Ее нужно документировать как осознанное решение, а не случайное дублирование.</li>
<li>Иногда materialized view, cache или индекс — лучший первый шаг.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Main risk of denormalization?<br>A: Duplicated data can become inconsistent.</p>
</td>
<td valign="top" width="50%">
<p>Q: Главный риск денормализации?<br>A: Дублированные данные могут стать inconsistent.</p>
</td>
</tr>
</tbody>

<a id="db-model-004"></a>

<details>
<summary><strong>DB-MODEL-004. What are one-to-one, one-to-many and many-to-many relationships?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>They describe cardinality between entities: one row relates to one row, one row relates to many rows, or many rows relate to many rows.</p>
</td>
<td valign="top" width="50%">
<p>Они описывают cardinality между сущностями: одна строка связана с одной строкой, одна строка связана со многими строками или многие строки связаны со многими строками.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>One-to-one means one row in table A corresponds to at most one row in table B, for example user and user profile.</p>
<p>One-to-many means one parent row has many child rows, for example customer and orders.</p>
<p>Many-to-many means rows on both sides can have many related rows, for example students and courses. In a relational database this is modeled with a junction table.</p>
</td>
<td valign="top" width="50%">
<p>One-to-one означает, что одна строка таблицы A соответствует максимум одной строке таблицы B, например user и user profile.</p>
<p>One-to-many означает, что одна parent-строка имеет много child-строк, например customer и orders.</p>
<p>Many-to-many означает, что строки с обеих сторон могут иметь много связанных строк, например students и courses. В реляционной базе это моделируется через junction table.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<pre><code class="language-sql">-- one-to-many
orders.customer_id REFERENCES customers(id)

-- one-to-one
user_profiles.user_id UNIQUE REFERENCES users(id)

-- many-to-many
student_courses(student_id, course_id)</code></pre>
</td>
<td valign="top" width="50%">
<pre><code class="language-sql">-- one-to-many
orders.customer_id REFERENCES customers(id)

-- one-to-one
user_profiles.user_id UNIQUE REFERENCES users(id)

-- many-to-many
student_courses(student_id, course_id)</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Cardinality should be enforced by constraints, not only by ORM mappings. For example, one-to-one needs a unique constraint on the foreign key.</p>
<p>Delete behavior should be chosen deliberately with options such as <code>ON DELETE RESTRICT</code>, <code>CASCADE</code>, <code>SET NULL</code>, or <code>NO ACTION</code>. Foreign key columns often need indexes when they are used for joins, parent-child lookups, or delete checks.</p>
</td>
<td valign="top" width="50%">
<p>Cardinality нужно enforce-ить constraints, а не только ORM mapping-ами. Например, для one-to-one нужен unique constraint на foreign key.</p>
<p>Delete behavior нужно выбирать осознанно через варианты вроде <code>ON DELETE RESTRICT</code>, <code>CASCADE</code>, <code>SET NULL</code> или <code>NO ACTION</code>. Foreign key колонки часто требуют индексов, если используются для join-ов, parent-child lookups или delete checks.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>A foreign key alone usually models many-to-one from child to parent.</li>
<li>One-to-one requires uniqueness on the foreign key.</li>
<li>Many-to-many should not be modeled as comma-separated ids or arrays for core relational data.</li>
<li>Relationships can be optional or mandatory depending on nullability.</li>
<li>A many-to-many relationship can become a real domain entity if it has status, lifecycle, audit fields, permissions, or other attributes.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Один foreign key обычно моделирует many-to-one от child к parent.</li>
<li>Для one-to-one нужна уникальность foreign key.</li>
<li>Many-to-many не стоит моделировать comma-separated ids или arrays для core relational data.</li>
<li>Связи могут быть optional или mandatory в зависимости от nullability.</li>
<li>Many-to-many relationship может стать полноценной domain entity, если у связи есть status, lifecycle, audit fields, permissions или другие атрибуты.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: How do you enforce one-to-one with a foreign key?<br>A: Add a unique constraint on the foreign key.</p>
</td>
<td valign="top" width="50%">
<p>Q: Как enforce-ить one-to-one через foreign key?<br>A: Добавить unique constraint на foreign key.</p>
</td>
</tr>
</tbody>
</table>

</details>

<a id="db-model-005"></a>

<details>
<summary><strong>DB-MODEL-005. How do you model a many-to-many relationship in a relational database?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use a junction table with foreign keys to both tables. Usually the pair of foreign keys is unique or is the primary key.</p>
</td>
<td valign="top" width="50%">
<p>Используют junction table с foreign keys на обе таблицы. Обычно пара foreign keys уникальна или является primary key.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For example, users can have many roles and roles can belong to many users. I would create <code>user_roles</code> with <code>user_id</code> and <code>role_id</code>, both referencing parent tables.</p>
<p>If the relationship has attributes, such as assignment time or status, those attributes belong in the junction table.</p>
</td>
<td valign="top" width="50%">
<p>Например, у users может быть много roles, и одна role может быть у многих users. Я бы создал <code>user_roles</code> с <code>user_id</code> и <code>role_id</code>, которые ссылаются на parent tables.</p>
<p>Если у связи есть свои атрибуты, например время назначения или статус, эти атрибуты хранятся в junction table.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<pre><code class="language-sql">CREATE TABLE user_roles (
    user_id BIGINT NOT NULL REFERENCES users(id),
    role_id BIGINT NOT NULL REFERENCES roles(id),
    assigned_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, role_id)
);</code></pre>
</td>
<td valign="top" width="50%">
<pre><code class="language-sql">CREATE TABLE user_roles (
    user_id BIGINT NOT NULL REFERENCES users(id),
    role_id BIGINT NOT NULL REFERENCES roles(id),
    assigned_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, role_id)
);</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Add indexes for both access directions if the application queries both “roles by user” and “users by role”. The primary key on <code>(user_id, role_id)</code> helps the first direction, but not always the second.</p>
</td>
<td valign="top" width="50%">

<details>
<summary><strong>🔥 DB-MODEL-010. Why can random UUIDs be bad for B-tree indexes?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Random UUIDs insert into random positions in a B-tree, causing poor locality, more page splits, more cache misses, and larger indexes.</p>
</td>
<td valign="top" width="50%">
<p>Random UUID вставляются в случайные места B-tree, из-за чего ухудшается locality, растут page splits, cache misses и размер индекса.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A B-tree index is ordered. With sequential ids, new entries usually go near the end of the index. With random UUIDv4, each insert may target a different page.</p>
<p>That random write pattern is harder for memory cache and storage. It can fragment the index, increase page splits, and make the primary key and all referencing foreign-key indexes larger.</p>
</td>
<td valign="top" width="50%">
<p>B-tree индекс упорядочен. С sequential ids новые записи обычно попадают ближе к концу индекса. С random UUIDv4 каждая вставка может попадать на другую страницу.</p>
<p>Такой random write pattern хуже для memory cache и storage. Он может фрагментировать индекс, увеличивать page splits и делать primary key и все referencing foreign-key индексы больше.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The issue is not uniqueness itself. The issue is randomness combined with an ordered index structure. Time-ordered identifiers such as UUIDv7 reduce this problem because nearby inserts have similar prefixes.</p>
</td>
<td valign="top" width="50%">
<p>Проблема не в уникальности как таковой. Проблема в случайности вместе с ordered index structure. Time-ordered identifiers вроде UUIDv7 уменьшают проблему, потому что близкие вставки имеют похожий prefix.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For high-write large tables, random UUID primary keys should be a conscious decision. Benchmark with production-like data, monitor index bloat, and consider UUIDv7, ULID-like ids, or internal numeric keys.</p>
</td>
<td valign="top" width="50%">
<p>Для больших high-write таблиц random UUID primary key должен быть осознанным решением. Нужны benchmark на production-like данных, мониторинг index bloat и рассмотрение UUIDv7, ULID-like ids или internal numeric keys.</p>
</td>

<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Small tables may not notice the difference.</li>
<li>The problem is worse on high-write and large indexed tables.</li>
<li>UUID as public id can be separate from internal primary key.</li>
<li>The problem is mostly about random UUIDv4 locality; UUIDv7/ULID-style ids reduce locality issues but still use wider keys than <code>BIGINT</code>.</li>
<li>Use PostgreSQL native <code>uuid</code>, not text, when using UUIDs.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>На маленьких таблицах разница может быть незаметна.</li>
<li>Проблема сильнее на больших high-write таблицах с индексами.</li>
<li>UUID как public id может быть отдельным от internal primary key.</li>
<li>Проблема в основном про locality random UUIDv4; UUIDv7/ULID-style ids уменьшают locality issues, но всё равно шире, чем <code>BIGINT</code>.</li>
<li>В PostgreSQL лучше использовать native <code>uuid</code>, а не text.</li>
</ul>

Для shared tables индексы часто должны включать <code>tenant_id</code>, если запросы tenant-scoped, но порядок колонок всё равно должен следовать реальным query patterns: equality filters, range filters, ordering и selectivity.</p>
<p>Tenant isolation стоит enforce-ить на нескольких уровнях: application authorization, tenant-scoped queries, tenant-scoped unique constraints, tenant-scoped foreign keys, optional PostgreSQL Row Level Security и тесты на cross-tenant access.</p>
