# Aggregation, GROUP BY and window functions

<a id="db-agg-001"></a>

<details>
<summary><strong>🔥 DB-AGG-001. What is the difference between WHERE and HAVING?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>WHERE</code> filters rows before grouping; <code>HAVING</code> filters groups after aggregation.</p>
</td>
<td valign="top" width="50%">
<p><code>WHERE</code> фильтрует строки до группировки; <code>HAVING</code> фильтрует группы после агрегации.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use <code>WHERE</code> for row-level filters and <code>HAVING</code> for conditions on aggregate results like <code>COUNT(*)</code> or <code>SUM(amount)</code>.</p>
</td>
<td valign="top" width="50%">
<p>Используй <code>WHERE</code> для row-level filters, а <code>HAVING</code> для условий по агрегатам вроде <code>COUNT(*)</code> или <code>SUM(amount)</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Logical order matters: <code>FROM/JOIN</code> produce rows, <code>WHERE</code> filters rows, <code>GROUP BY</code> creates groups, aggregates are computed, and <code>HAVING</code> filters groups.</p><pre><code class="language-sql">SELECT customer_id, COUNT(*)
FROM orders
WHERE status = &#x27;PAID&#x27;
GROUP BY customer_id
HAVING COUNT(*) &gt; 10;</code></pre>
</td>
<td valign="top" width="50%">
<p>Логический порядок важен: <code>FROM/JOIN</code> создают строки, <code>WHERE</code> фильтрует строки, <code>GROUP BY</code> создаёт группы, считаются агрегаты, затем <code>HAVING</code> фильтрует группы.</p><pre><code class="language-sql">SELECT customer_id, COUNT(*)
FROM orders
WHERE status = &#x27;PAID&#x27;
GROUP BY customer_id
HAVING COUNT(*) &gt; 10;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Move non-aggregate filters from <code>HAVING</code> to <code>WHERE</code> when it preserves semantics; it reduces rows before grouping.</p>
</td>
<td valign="top" width="50%">
<p>Переноси non-aggregate filters из <code>HAVING</code> в <code>WHERE</code>, если смысл не меняется; так меньше строк группируется.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li><code>WHERE COUNT(*) > 10</code> is invalid.</li><li>Using <code>HAVING</code> for simple filters can force unnecessary aggregation.</li><li>Do not move conditions between WHERE and HAVING if it changes semantics.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li><code>WHERE COUNT(*) > 10</code> невалиден.</li><li>Использование <code>HAVING</code> для простых фильтров может заставить БД делать лишнюю агрегацию.</li><li>Не переноси условия между WHERE и HAVING, если меняется смысл.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the difference between WHERE and HAVING?<br>A: WHERE filters rows before grouping; HAVING filters groups after aggregation.</p>
</td>
<td valign="top" width="50%">
<p>Q: В чём разница между WHERE и HAVING?<br>A: WHERE фильтрует строки до группировки; HAVING фильтрует группы после агрегации.</p>
</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>DB-AGG-002. What does GROUP BY do?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>GROUP BY</code> groups rows by key so aggregates can be calculated per group.</p>
</td>
<td valign="top" width="50%">
<p><code>GROUP BY</code> группирует строки по ключу, чтобы агрегаты считались по каждой группе.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use it when you need one result row per customer, status, day, tenant, or another grouping key.</p>
</td>
<td valign="top" width="50%">
<p>Используй его, когда нужна одна строка результата на customer, status, day, tenant или другой grouping key.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Selected columns must be either grouped or aggregated, unless PostgreSQL can prove functional dependency in specific cases.</p><pre><code class="language-sql">SELECT status, COUNT(*)
FROM orders
GROUP BY status;</code></pre>
</td>
<td valign="top" width="50%">
<p>Selected columns должны быть либо grouped, либо aggregated, если только PostgreSQL не может доказать functional dependency в отдельных случаях.</p><pre><code class="language-sql">SELECT status, COUNT(*)
FROM orders
GROUP BY status;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Large grouping can require sort/hash aggregate and may spill to disk; check plan, rows, memory, and indexes.</p>
</td>
<td valign="top" width="50%">
<p>Большая группировка может требовать sort/hash aggregate и spill to disk; проверяй plan, rows, memory и indexes.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>GROUP BY changes result cardinality.</li><li>GROUP BY is not the same as DISTINCT intent.</li><li>For detailed rows plus totals, window functions may be better.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>GROUP BY меняет cardinality результата.</li><li>GROUP BY не то же самое по intent, что DISTINCT.</li><li>Для детальных строк плюс totals лучше может быть window function.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does GROUP BY do?<br>A: GROUP BY groups rows by key so aggregates can be calculated per group.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что делает GROUP BY?<br>A: GROUP BY группирует строки по ключу, чтобы агрегаты считались по каждой группе.</p>
</td>
</tr>
</tbody>
</table>

<summary><strong>DB-AGG-003. When should you use HAVING?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use <code>HAVING</code> when a filter depends on an aggregate or group-level value.</p>
</td>
<td valign="top" width="50%">
<p>Используй <code>HAVING</code>, когда фильтр зависит от агрегата или group-level значения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Typical examples are customers with more than 10 orders or days where revenue exceeds a threshold.</p>
</td>
<td valign="top" width="50%">
<p>Типичные примеры — клиенты с более чем 10 заказами или дни, где revenue выше порога.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A <code>HAVING</code> predicate is evaluated after grouping, so it can reference aggregate expressions.</p><pre><code class="language-sql">SELECT customer_id, SUM(amount)
FROM payments
GROUP BY customer_id
HAVING SUM(amount) &gt; 10000;</code></pre>
</td>
<td valign="top" width="50%">
<p>Predicate в <code>HAVING</code> применяется после grouping, поэтому может ссылаться на aggregate expressions.</p><pre><code class="language-sql">SELECT customer_id, SUM(amount)
FROM payments
GROUP BY customer_id
HAVING SUM(amount) &gt; 10000;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Prefer <code>WHERE</code> for row filters to reduce data before aggregation.</p>
</td>
<td valign="top" width="50%">
<p>Для row filters предпочитай <code>WHERE</code>, чтобы уменьшить данные до агрегации.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Do not use HAVING as a replacement for WHERE.</li><li>HAVING can be expensive if it forces grouping many unnecessary rows.</li><li>Aliases and HAVING behavior can differ between DBMS dialects.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>Не используй HAVING как замену WHERE.</li><li>HAVING может быть дорогим, если заставляет группировать много лишних строк.</li><li>Aliases и HAVING behavior могут отличаться между DBMS dialects.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: When should you use HAVING?<br>A: Use HAVING when a filter depends on an aggregate or group-level value.</p>
</td>
<td valign="top" width="50%">
<p>Q: Когда использовать HAVING?<br>A: Используй HAVING, когда фильтр зависит от агрегата или group-level значения.</p>
</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>DB-AGG-004. What is the difference between GROUP BY and DISTINCT?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>DISTINCT</code> removes duplicate result rows; <code>GROUP BY</code> creates groups, usually for aggregation.</p>
</td>
<td valign="top" width="50%">
<p><code>DISTINCT</code> удаляет дубликаты строк результата; <code>GROUP BY</code> создаёт группы, обычно для агрегации.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>They can sometimes produce similar output, but communicate different intent.</p>
</td>
<td valign="top" width="50%">
<p>Иногда они дают похожий результат, но выражают разный intent.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>PostgreSQL may implement both via sorting or hashing. <code>GROUP BY</code> also allows aggregate expressions per group.</p><pre><code class="language-sql">SELECT DISTINCT status FROM orders;
SELECT status, COUNT(*) FROM orders GROUP BY status;</code></pre>
</td>
<td valign="top" width="50%">
<p>PostgreSQL может реализовать оба через sorting или hashing. <code>GROUP BY</code> также позволяет считать aggregates по группам.</p><pre><code class="language-sql">SELECT DISTINCT status FROM orders;
SELECT status, COUNT(*) FROM orders GROUP BY status;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If <code>DISTINCT</code> is used to hide duplicates from a join, first check whether the join condition is wrong.</p>
</td>
<td valign="top" width="50%">
<p>Если <code>DISTINCT</code> используется, чтобы скрыть дубликаты от join, сначала проверь join condition.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>DISTINCT is not a universal performance fix.</li><li>GROUP BY without aggregates can resemble DISTINCT but intent differs.</li><li>Both can be expensive on large data.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>DISTINCT — не универсальный performance fix.</li><li>GROUP BY без агрегатов может быть похож на DISTINCT, но intent отличается.</li><li>Оба могут быть дорогими на больших данных.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the difference between GROUP BY and DISTINCT?<br>A: DISTINCT removes duplicate result rows; GROUP BY creates groups, usually for aggregation.</p>
</td>
<td valign="top" width="50%">
<p>Q: В чём разница между GROUP BY и DISTINCT?<br>A: DISTINCT удаляет дубликаты строк результата; GROUP BY создаёт группы, обычно для агрегации.</p>
</td>
</tr>
</tbody>
</table>

<tr>

</td>
<td valign="top" width="50%">
<p>При группировке все <code>NULL</code> в grouping column попадают в одну группу.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>This differs from normal equality comparison where <code>NULL = NULL</code> is unknown.</p>
</td>
<td valign="top" width="50%">
<p>Это отличается от обычного equality comparison, где <code>NULL = NULL</code> даёт unknown.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Grouping treats nulls as not distinct for grouping purposes, so reports can contain one null bucket.</p><pre><code class="language-sql">SELECT region, COUNT(*)
FROM customers
GROUP BY region;</code></pre>
</td>
<td valign="top" width="50%">
<p>Для целей группировки nulls считаются одной группой, поэтому отчёты могут содержать один null bucket.</p><pre><code class="language-sql">SELECT region, COUNT(*)
FROM customers
GROUP BY region;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Decide whether NULL means unknown, not applicable, or unassigned; sometimes use <code>COALESCE</code> for clearer reports.</p>
</td>
<td valign="top" width="50%">
<p>Реши, означает ли NULL unknown, not applicable или unassigned; иногда используй <code>COALESCE</code> для понятных отчётов.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Do not confuse GROUP BY behavior with equality comparison.</li><li>A NULL bucket can hide data quality issues.</li><li>COALESCE can make business meaning explicit.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>Не путай GROUP BY behavior с equality comparison.</li><li>NULL bucket может скрывать data quality issues.</li><li>COALESCE может явно показать business meaning.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>

</td>
<td valign="top" width="50%">
<p>Q: Как GROUP BY обрабатывает NULL?<br>A: При группировке все NULL в grouping column попадают в одну группу.</p>

</tr>

<details>
<summary><strong>🔥 DB-AGG-006. What are window functions?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Window functions calculate values across rows related to the current row while keeping individual rows in the result.</p>
</td>
<td valign="top" width="50%">
<p>Оконные функции считают значения по строкам, связанным с текущей строкой, но сохраняют отдельные строки результата.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>They use an <code>OVER</code> clause with optional <code>PARTITION BY</code>, <code>ORDER BY</code>, and frame definition.</p>
</td>
<td valign="top" width="50%">
<p>Они используют <code>OVER</code> с опциональными <code>PARTITION BY</code>, <code>ORDER BY</code> и frame definition.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Unlike <code>GROUP BY</code>, window functions do not collapse rows. PostgreSQL computes them over the virtual table produced after <code>FROM</code>, <code>WHERE</code>, grouping, and <code>HAVING</code>.</p><pre><code class="language-sql">SELECT order_id, customer_id, amount,
       SUM(amount) OVER (PARTITION BY customer_id) AS customer_total
FROM orders;</code></pre>
</td>
<td valign="top" width="50%">
<p>В отличие от <code>GROUP BY</code>, window functions не схлопывают строки. PostgreSQL считает их по virtual table после <code>FROM</code>, <code>WHERE</code>, grouping и <code>HAVING</code>.</p><pre><code class="language-sql">SELECT order_id, customer_id, amount,
       SUM(amount) OVER (PARTITION BY customer_id) AS customer_total
FROM orders;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Useful for rankings, running totals, latest row per group, top-N per group, deduplication, and reports; they may require large sorts.</p>
</td>
<td valign="top" width="50%">
<p>Полезны для rankings, running totals, latest row per group, top-N per group, дедупликации и отчётов; могут требовать больших сортировок.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Window functions cannot be used directly in WHERE.</li><li>Default frames can surprise with last_value and running aggregates.</li><li>ORDER BY inside OVER is separate from final ORDER BY.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>Window functions нельзя использовать напрямую в WHERE.</li><li>Default frames могут удивить с last_value и running aggregates.</li><li>ORDER BY внутри OVER отделён от финального ORDER BY.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What are window functions?<br>A: Window functions calculate values across rows related to the current row while keeping individual rows in the result.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое оконные функции?<br>A: Оконные функции считают значения по строкам, связанным с текущей строкой, но сохраняют отдельные строки результата.</p>
</td>
</tr>
</tbody>

<a id="db-agg-007"></a>

<details>
<summary><strong>🔥 DB-AGG-007. What is the difference between GROUP BY and window functions?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>GROUP BY</code> returns one row per group; window functions return row-level results plus calculations over related rows.</p>
</td>
<td valign="top" width="50%">
<p><code>GROUP BY</code> возвращает одну строку на группу; window functions возвращают row-level результат плюс вычисления по связанным строкам.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use <code>GROUP BY</code> for summaries and window functions for contextual values on each row.</p>
</td>
<td valign="top" width="50%">
<p>Используй <code>GROUP BY</code> для summaries, а window functions — для contextual values на каждой строке.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A window aggregate such as <code>SUM(x) OVER (...)</code> is calculated over a window but does not remove individual rows.</p><pre><code class="language-sql">SELECT customer_id, SUM(amount) FROM orders GROUP BY customer_id;

SELECT order_id, customer_id, amount,
       SUM(amount) OVER (PARTITION BY customer_id)
FROM orders;</code></pre>
</td>
<td valign="top" width="50%">
<p>Window aggregate вроде <code>SUM(x) OVER (...)</code> считается по окну, но не удаляет отдельные строки.</p><pre><code class="language-sql">SELECT customer_id, SUM(amount) FROM orders GROUP BY customer_id;

SELECT order_id, customer_id, amount,
       SUM(amount) OVER (PARTITION BY customer_id)
FROM orders;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Window functions can replace correlated subqueries/self-joins, but they may sort large data; verify with <code>EXPLAIN ANALYZE</code>.</p>
</td>
<td valign="top" width="50%">
<p>Window functions могут заменить correlated subqueries/self-joins, но могут сортировать большие данные; проверяй через <code>EXPLAIN ANALYZE</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
