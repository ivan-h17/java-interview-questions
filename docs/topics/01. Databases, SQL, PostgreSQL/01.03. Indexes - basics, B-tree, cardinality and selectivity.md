# Indexes: basics, B-tree, cardinality and selectivity

<a id="db-idx-001"></a>

<details>
<summary><strong>🔥 DB-IDX-001. What are indexes used for?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Indexes are auxiliary data structures that help PostgreSQL find rows faster than reading the whole table. They are mainly used to speed up selective filters, joins, ordering, uniqueness checks, and some access patterns like pagination.</p>
</td>
<td valign="top" width="50%">
<p>Индексы — это вспомогательные структуры данных, которые помогают PostgreSQL находить строки быстрее, чем при полном чтении таблицы. Они ускоряют селективные фильтры, join-ы, сортировку, проверки уникальности и некоторые паттерны вроде pagination.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>An index is similar to an ordered lookup structure. Instead of scanning every row, PostgreSQL can search the index, find matching index entries, and then fetch the corresponding table rows.</p>
<p>For a backend developer, the important point is that an index is not “just performance magic”. It must match real queries: <code>WHERE</code> predicates, join columns, <code>ORDER BY</code>, uniqueness constraints, and data distribution.</p>
</td>
<td valign="top" width="50%">
<p>Индекс похож на упорядоченную lookup-структуру. Вместо просмотра каждой строки PostgreSQL может найти подходящие записи в индексе и затем получить соответствующие строки таблицы.</p>
<p>Для backend-разработчика важно понимать: индекс — это не “магическое ускорение”. Он должен соответствовать реальным запросам: условиям <code>WHERE</code>, колонкам join-а, <code>ORDER BY</code>, unique constraints и распределению данных.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>PostgreSQL stores table data in the heap and stores indexes separately. A typical B-tree index contains sorted keys and references to heap tuples. For a query like:</p>
<pre><code class="language-sql">SELECT *
FROM users
WHERE email = 'alice@example.com';</code></pre>
<p>an index on <code>email</code> can let PostgreSQL locate the matching key quickly instead of scanning all users.</p>
</td>
<td valign="top" width="50%">
<p>PostgreSQL хранит данные таблицы в heap, а индексы — отдельно. Типичный B-tree индекс хранит отсортированные ключи и ссылки на heap tuples. Для запроса:</p>
<pre><code class="language-sql">SELECT *
FROM users
WHERE email = 'alice@example.com';</code></pre>
<p>индекс по <code>email</code> позволяет быстро найти нужный ключ вместо просмотра всех пользователей.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, indexes should be added based on measured query patterns, not by guessing. Use <code>EXPLAIN</code> / <code>EXPLAIN ANALYZE</code>, check selectivity, table size, write rate, and existing indexes.</p>
<p>Indexes also cost disk space and slow down writes, because PostgreSQL must maintain them on <code>INSERT</code>, <code>UPDATE</code>, and <code>DELETE</code>.</p>
</td>
<td valign="top" width="50%">
<p>В production индексы нужно добавлять по реальным query patterns, а не наугад. Нужно смотреть <code>EXPLAIN</code> / <code>EXPLAIN ANALYZE</code>, селективность, размер таблицы, write rate и уже существующие индексы.</p>
<p>Индексы занимают место и замедляют запись, потому что PostgreSQL должен поддерживать их при <code>INSERT</code>, <code>UPDATE</code> и <code>DELETE</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>An index does not guarantee that PostgreSQL will use it.</li>
<li>Predicates that match a large fraction of the table may still be faster with a sequential scan.</li>
<li>Too many indexes can hurt write performance and increase maintenance cost.</li>
<li>Indexes should be designed for concrete queries, not for every column.</li>
<li>A missing index and a wrong index are both common production problems.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Наличие индекса не гарантирует, что PostgreSQL его использует.</li>
<li>Для условий, которые матчятся с большой долей таблицы, sequential scan может быть быстрее.</li>
<li>Слишком много индексов ухудшает write performance и усложняет обслуживание.</li>
<li>Индексы проектируются под конкретные запросы, а не “на каждую колонку”.</li>
<li>Отсутствующий индекс и неправильный индекс — обе частые production-проблемы.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the main purpose of an index?<br>A: To find matching rows faster by using an auxiliary data structure instead of scanning the whole table.</p>
<p>Q: Are indexes free?<br>A: No. They cost disk space and add write/maintenance overhead.</p>
</td>
<td valign="top" width="50%">
<p>Q: Главная цель индекса?<br>A: Быстрее находить подходящие строки через вспомогательную структуру, а не сканировать всю таблицу.</p>
<p>Q: Индексы бесплатны?<br>A: Нет. Они занимают место и добавляют overhead на запись и обслуживание.</p>
</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>DB-IDX-002. How does an index lookup differ from a sequential table scan?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A sequential scan reads table pages one by one and checks rows. An index lookup first searches an index and then reads only the table rows that match the index entries.</p>
</td>
<td valign="top" width="50%">
<p>Sequential scan читает страницы таблицы подряд и проверяет строки. Index lookup сначала ищет в индексе, а затем читает только строки таблицы, соответствующие найденным index entries.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A sequential scan is simple: PostgreSQL walks through the table and evaluates the filter for each row. It is often good when the table is small or the query returns a large part of it.</p>
<p>An index lookup is more targeted: PostgreSQL uses the index to find candidate row locations. It is usually good when the predicate is selective and returns a small fraction of rows.</p>
</td>
<td valign="top" width="50%">
<p>Sequential scan устроен просто: PostgreSQL проходит по таблице и проверяет условие для каждой строки. Это часто хорошо для маленькой таблицы или запроса, который возвращает большую часть строк.</p>
<p>Index lookup более точечный: PostgreSQL использует индекс, чтобы найти candidate row locations. Обычно это хорошо, когда predicate селективный и возвращает небольшую долю строк.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In PostgreSQL, a normal index scan usually needs two structures:</p>
<ul>
<li>the index, where matching keys are found;</li>
<li>the heap, where the actual table rows are checked and returned.</li>
</ul>
<p>This means an index scan can involve random heap reads. For many matching rows, that can be more expensive than reading the table sequentially.</p>
</td>
<td valign="top" width="50%">
<p>В PostgreSQL обычный index scan обычно использует две структуры:</p>
<ul>
<li>индекс, где находятся matching keys;</li>
<li>heap, где проверяются и возвращаются реальные строки таблицы.</li>
</ul>
<p>Из-за этого index scan может делать random heap reads. Если строк много, это может быть дороже, чем последовательное чтение таблицы.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>When debugging performance, do not assume “index scan is always better”. Compare plans with <code>EXPLAIN ANALYZE</code>, look at actual rows, buffers, and whether the query reads a large percentage of the table.</p>
</td>
<td valign="top" width="50%">
<p>При отладке performance нельзя считать, что “index scan всегда лучше”. Нужно сравнивать планы через <code>EXPLAIN ANALYZE</code>, смотреть actual rows, buffers и понимать, читает ли запрос большую часть таблицы.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Sequential scan is not automatically bad.</li>
<li>Index scan is not automatically good.</li>
<li>Index lookup may cause many random heap reads.</li>
<li>Index-only scan is a special case and requires all needed columns plus visibility information.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Sequential scan не всегда плохой.</li>
<li>Index scan не всегда хороший.</li>
<li>Index lookup может привести к множеству random heap reads.</li>
<li>Index-only scan — особый случай: нужны все колонки в индексе и visibility information.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: When can a sequential scan be better than an index scan?<br>A: When the query reads a large fraction of the table or the table is small.</p>
</td>
<td valign="top" width="50%">
<p>Q: Когда sequential scan может быть лучше index scan?<br>A: Когда запрос читает большую часть таблицы или таблица маленькая.</p>
</td>
</tr>
</tbody>
</table>

<a id="db-idx-003"></a>

<details>
<summary><strong>🔥 DB-IDX-003. How does a B-tree index work?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A B-tree index keeps keys sorted in a balanced tree. PostgreSQL can navigate from the root page through internal pages to leaf pages and find matching keys efficiently.</p>
</td>
<td valign="top" width="50%">
<p>B-tree индекс хранит ключи в отсортированном сбалансированном дереве. PostgreSQL может пройти от root page через internal pages к leaf pages и эффективно найти нужные ключи.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>B-tree is the default PostgreSQL index type and fits the most common cases: equality, range queries, sorting, uniqueness, and prefix-like access patterns.</p>
<p>Conceptually, PostgreSQL searches the tree by comparing the query value with separator keys until it reaches the leaf page containing matching index entries.</p>
</td>
<td valign="top" width="50%">
<p>B-tree — индекс по умолчанию в PostgreSQL, подходящий для самых частых случаев: equality, range queries, sorting, uniqueness и prefix-like access patterns.</p>
<p>Концептуально PostgreSQL сравнивает значение из запроса с разделительными ключами дерева, пока не дойдёт до leaf page с подходящими index entries.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A B-tree is balanced, so all leaf pages are at the same depth. This keeps lookup cost predictable even as the table grows.</p>
<p>For an equality predicate:</p>
<pre><code class="language-sql">WHERE email = 'alice@example.com'</code></pre>
<p>PostgreSQL descends to the leaf page for that key and reads matching entries. For a range predicate:</p>
<pre><code class="language-sql">WHERE created_at &gt;= now() - interval '1 day'</code></pre>
<p>it finds the lower bound and scans forward through leaf entries until the range ends.</p>
</td>
<td valign="top" width="50%">
<p>B-tree сбалансирован: все leaf pages находятся на одной глубине. Это делает стоимость поиска предсказуемой при росте таблицы.</p>
<p>Для equality predicate:</p>
<pre><code class="language-sql">WHERE email = 'alice@example.com'</code></pre>
<p>PostgreSQL спускается к leaf page для этого ключа и читает matching entries. Для range predicate:</p>
<pre><code class="language-sql">WHERE created_at &gt;= now() - interval '1 day'</code></pre>
<p>он находит нижнюю границу и сканирует leaf entries дальше до конца диапазона.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, B-tree indexes are the first choice for common OLTP filters and joins. But they are not ideal for every use case: full-text search, JSONB containment, arrays, geospatial search, or huge naturally ordered time-series data may need other index types.</p>
</td>
<td valign="top" width="50%">
<p>В production B-tree индексы — первый выбор для обычных OLTP-фильтров и join-ов. Но они не идеальны для всего: full-text search, JSONB containment, массивы, geospatial search или огромные time-series данные могут требовать других типов индексов.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>B-tree is great for equality, ranges, ordering, and uniqueness, but not for every predicate.</li>
<li>It stores sorted keys, not full table rows.</li>
<li>PostgreSQL indexes are secondary structures separate from the heap.</li>
<li>A B-tree index can still be ignored if the predicate is not selective enough.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>B-tree хорош для equality, ranges, ordering и uniqueness, но не для любого predicate.</li>
<li>Он хранит отсортированные ключи, а не полные строки таблицы.</li>
<li>PostgreSQL indexes — вторичные структуры, отдельные от heap.</li>
<li>B-tree индекс всё равно может быть проигнорирован, если predicate недостаточно селективный.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the default index type in PostgreSQL?<br>A: B-tree.</p>
<p>Q: What query patterns are B-tree indexes good for?<br>A: Equality, ranges, ordering, uniqueness, and common join/filter predicates.</p>
</td>
<td valign="top" width="50%">
<p>Q: Какой тип индекса в PostgreSQL используется по умолчанию?<br>A: B-tree.</p>
<p>Q: Для каких запросов хорошо подходит B-tree?<br>A: Equality, ranges, ordering, uniqueness и обычные join/filter predicates.</p>
</td>
</tr>
</tbody>
</table>

<a id="db-idx-004"></a>

<details>
<summary><strong>DB-IDX-004. How does a B-tree index work under the hood?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Under the hood, a PostgreSQL B-tree index is a set of pages organized as a balanced tree. Pages contain sorted index tuples. Leaf tuples point to heap tuples by row location.</p>
</td>
<td valign="top" width="50%">
<p>Под капотом PostgreSQL B-tree индекс — это набор страниц, организованных как сбалансированное дерево. Страницы содержат отсортированные index tuples. Leaf tuples указывают на heap tuples через location строки.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>At a high level, B-tree lookup has three steps: start at the root, follow internal page pointers based on key comparisons, then scan leaf entries that match the predicate.</p>
<p>Each index entry stores key data and a reference to the table row. PostgreSQL still needs MVCC visibility checks, so a normal index scan may need to visit the heap.</p>
</td>
<td valign="top" width="50%">
<p>На высоком уровне B-tree lookup состоит из трёх шагов: начать с root, идти по internal page pointers на основе сравнений ключей, затем сканировать leaf entries, подходящие под predicate.</p>
<p>Каждая index entry хранит key data и ссылку на строку таблицы. PostgreSQL всё равно должен проверить MVCC visibility, поэтому обычный index scan может обращаться к heap.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Important internal concepts:</p>
<ul>
<li><strong>Pages</strong>: fixed-size blocks that store index tuples.</li>
<li><strong>Root page</strong>: entry point into the tree.</li>
<li><strong>Internal pages</strong>: route the search to the right child page.</li>
<li><strong>Leaf pages</strong>: contain actual index entries pointing to heap tuples.</li>
<li><strong>Page splits</strong>: happen when a page does not have enough room for a new entry.</li>
</ul>
<p>Page splits, WAL records, vacuum, deduplication, and bloat all affect real production behavior.</p>
</td>
<td valign="top" width="50%">
<p>Важные внутренние понятия:</p>
<ul>
<li><strong>Pages</strong>: блоки фиксированного размера, где хранятся index tuples.</li>
<li><strong>Root page</strong>: точка входа в дерево.</li>
<li><strong>Internal pages</strong>: направляют поиск к нужной child page.</li>
<li><strong>Leaf pages</strong>: содержат реальные index entries со ссылками на heap tuples.</li>
<li><strong>Page splits</strong>: происходят, когда на странице не хватает места для новой записи.</li>
</ul>
<p>Page splits, WAL records, vacuum, deduplication и bloat влияют на реальное production-поведение.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For a high-write table, random key insertion can cause frequent page splits and poor locality. This is one reason random UUIDv4 primary keys can be problematic for very large high-write tables.</p>
</td>
<td valign="top" width="50%">
<p>Для high-write таблицы вставка случайных ключей может вызывать частые page splits и плохую locality. Поэтому random UUIDv4 primary keys могут быть проблемой для очень больших таблиц с интенсивной записью.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>“B-tree is O(log n)” is useful conceptually, but real cost also depends on cache, heap fetches, bloat, and visibility checks.</li>
<li>Indexes are updated by writes and can become bloated.</li>
<li>Normal index scans do not avoid MVCC visibility checks.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>“B-tree — O(log n)” полезно концептуально, но реальная стоимость зависит от cache, heap fetches, bloat и visibility checks.</li>
<li>Индексы обновляются при записях и могут раздуваться.</li>
<li>Обычные index scans не избавляют от MVCC visibility checks.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does a B-tree leaf entry point to in PostgreSQL?<br>A: It points to a heap tuple location, not to an embedded full row.</p>
</td>
<td valign="top" width="50%">
<p>Q: На что указывает leaf entry B-tree индекса в PostgreSQL?<br>A: На location heap tuple, а не на встроенную полную строку.</p>
</td>
</tr>

<a id="db-idx-005"></a>

<details>
<summary><strong>DB-IDX-005. What are root, internal and leaf pages in a B-tree?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Root, internal, and leaf pages are levels of a B-tree. The root is the entry point, internal pages route the search, and leaf pages contain the actual sorted index entries.</p>
</td>
<td valign="top" width="50%">
<p>Root, internal и leaf pages — это уровни B-tree. Root — точка входа, internal pages направляют поиск, а leaf pages содержат реальные отсортированные index entries.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>When PostgreSQL uses a B-tree index, it begins at the root page. Based on key comparisons, it follows child pointers through internal pages until it reaches a leaf page.</p>
<p>Leaf pages contain entries for indexed values and references to heap rows. For range scans, PostgreSQL can continue through neighboring leaf pages.</p>
</td>
<td valign="top" width="50%">
<p>Когда PostgreSQL использует B-tree индекс, он начинает с root page. На основе сравнения ключей он идёт по child pointers через internal pages, пока не достигнет leaf page.</p>
<p>Leaf pages содержат entries для индексируемых значений и ссылки на heap rows. Для range scans PostgreSQL может продолжать чтение соседних leaf pages.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><strong>Root page</strong>: top of the tree, usually small and heavily cached.</li>
<li><strong>Internal page</strong>: contains separator keys and child page links.</li>
<li><strong>Leaf page</strong>: contains index entries for actual searchable keys.</li>
</ul>
<p>A balanced tree keeps the path length from root to leaf roughly the same for all keys.</p>
</td>
<td valign="top" width="50%">
<ul>
<li><strong>Root page</strong>: верх дерева, обычно маленький и хорошо кэшируется.</li>
<li><strong>Internal page</strong>: содержит separator keys и ссылки на child pages.</li>
<li><strong>Leaf page</strong>: содержит index entries для реальных searchable keys.</li>
</ul>
<p>Сбалансированное дерево сохраняет примерно одинаковую длину пути от root до leaf для всех ключей.</p>

WHERE tenant_id = ?
  AND status = ?
  AND created_at &gt;= ?

-- Weaker fit for the same index
WHERE status = ?</code></pre>
<p>Modern PostgreSQL can sometimes use later columns via skip scan or filtering, but the leading columns are still the main design factor.</p>

<td valign="top" width="50%">

<pre><code class="language-sql">-- Хорошее совпадение

  AND status = ?

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">

<p>Проектировать его нужно от точного паттерна <code>WHERE</code>, <code>JOIN</code>, <code>ORDER BY</code> и <code>LIMIT</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>The most selective column is not automatically first.</li>
<li>Equality filters, range filters, and ordering all matter.</li>

<li>Важны equality filters, range filters и ordering.</li>

<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">

  AND status = ?
  AND created_at &gt;= ?</code></pre>
<p><code>tenant_id</code> и <code>status</code> — equality predicates. Они задают узкий prefix. <code>created_at</code> — range predicate. Он определяет интервал внутри prefix.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Columns after the first range predicate can still help with ordering, index-only scans, or additional filtering, but they often cannot reduce the scanned range as efficiently as earlier equality columns.</p>
<p>This is why an index like <code>(tenant_id, status, created_at)</code> is often better than <code>(created_at, tenant_id, status)</code> for tenant-scoped time queries.</p>
</td>
<td valign="top" width="50%">
<p>Колонки после первого range predicate всё ещё могут помогать с ordering, index-only scans или дополнительной фильтрацией, но часто не могут так же эффективно уменьшать scanned range, как earlier equality columns.</p>
<p>Поэтому индекс <code>(tenant_id, status, created_at)</code> часто лучше, чем <code>(created_at, tenant_id, status)</code>, для tenant-scoped time queries.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>This distinction matters for API filters like “orders for tenant by status in a date range”. A wrong column order can cause PostgreSQL to scan a much larger part of the index than expected.</p>
</td>
<td valign="top" width="50%">
<p>Это различие важно для API filters вроде “orders for tenant by status in a date range”. Неправильный порядок колонок может заставить PostgreSQL сканировать гораздо большую часть индекса, чем ожидалось.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Equality predicates are usually best before range predicates.</li>
<li>Multiple range predicates are harder to optimize with one B-tree index.</li>
<li>Additional columns after a range can still be useful, but understand why.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Equality predicates обычно лучше ставить до range predicates.</li>
<li>Несколько range predicates сложнее оптимизировать одним B-tree index.</li>
<li>Дополнительные колонки после range всё ещё могут быть полезны, но важно понимать зачем.</li>
</ul>
</td>

<th colspan="2" align="left">Optional Anki</th>
</tr>

<td valign="top" width="50%">

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Indexes make writes more expensive because PostgreSQL must keep index entries consistent with table rows.</p>
</td>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>On <code>INSERT</code>, PostgreSQL adds a new heap tuple and creates entries in relevant indexes. On <code>DELETE</code>, row versions become dead and index cleanup happens later through vacuum-related maintenance.</p>
</td>
<td valign="top" width="50%">
<p>При <code>INSERT</code> PostgreSQL добавляет новую heap tuple и создаёт entries в relevant indexes. <th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>

<td valign="top" width="50%">

<details>
<summary><strong>🔥 DB-IDX-020. What is column selectivity?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Selectivity is the fraction of rows that match a concrete predicate. Technically, a lower selectivity value means fewer matched rows; in interviews, people often call such predicates highly selective.</p>
</td>
<td valign="top" width="50%">
<p>Селективность — это доля строк, которые подходят под конкретное условие. Технически меньшее значение selectivity означает меньше найденных строк; в интервью такие predicates часто называют highly selective.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Examples:</p>
<pre><code class="language-sql">-- very selective: low selectivity value
WHERE email = 'alice@example.com'

-- broad predicate: matches many rows
WHERE status = 'ACTIVE'</code></pre>
<p>If <code>email</code> is unique, the predicate returns at most one row. If 90% of orders are <code>ACTIVE</code>, the status predicate returns most of the table.</p>
</td>
<td valign="top" width="50%">
<p>Примеры:</p>
<pre><code class="language-sql">-- очень селективно: низкое значение selectivity
WHERE email = 'alice@example.com'

-- широкий predicate: матчится со многими строками
WHERE status = 'ACTIVE'</code></pre>
<p>Если <code>email</code> уникален, predicate вернёт максимум одну строку. Если 90% заказов имеют статус <code>ACTIVE</code>, status predicate вернёт большую часть таблицы.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>PostgreSQL estimates predicate selectivity using planner statistics collected by <code>ANALYZE</code>, such as distinct counts, most common values, frequencies, and histograms.</p>
<p>Selectivity directly affects cost estimates: if the estimated matching fraction is tiny, index access is often attractive; if the predicate returns most rows, sequential scan may be cheaper.</p>
</td>
<td valign="top" width="50%">
<p>PostgreSQL оценивает selectivity predicate через planner statistics, собранные <code>ANALYZE</code>: distinct counts, most common values, frequencies и histograms.</p>
<p>Selectivity напрямую влияет на cost estimates: если estimated matching fraction очень маленькая, index access часто выгоден; если predicate возвращает большинство строк, sequential scan может быть дешевле.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, selectivity explains why an index on <code>status</code> may be ignored. A better solution can be a partial index for rare values:</p>
<pre><code class="language-sql">CREATE INDEX idx_orders_failed_created_at
ON orders (created_at)
WHERE status = 'FAILED';</code></pre>
</td>
<td valign="top" width="50%">
<p>В production selectivity объясняет, почему индекс по <code>status</code> может игнорироваться. Лучшим решением может быть partial index для редких значений:</p>
<pre><code class="language-sql">CREATE INDEX idx_orders_failed_created_at
ON orders (created_at)
WHERE status = 'FAILED';</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">

<summary><strong>🔥 DB-IDX-029. What is an index-only scan?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>An index-only scan is a scan where PostgreSQL can return the required columns using the index without fetching every matching row from the heap.</p>
</td>
<td valign="top" width="50%">
<p>Index-only scan — это scan, при котором PostgreSQL может вернуть нужные колонки из индекса без чтения каждой matching row из heap.</p>

<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A normal index scan finds matching index entries and then visits the heap to get row data and check visibility. An index-only scan can avoid heap visits when:</p>
<ul>
<li>the index contains all columns needed by the query;</li>
<li>the index type supports index-only scans;</li>
<li>the visibility map says the heap page is all-visible.</li>
</ul>
</td>
<td valign="top" width="50%">
<p>Обычный index scan находит matching index entries, а затем идёт в heap за данными строки и visibility check. Index-only scan может избежать heap visits, когда:</p>
<ul>
<li>индекс содержит все колонки, нужные запросу;</li>
<li>тип индекса поддерживает index-only scans;</li>
<li>visibility map говорит, что heap page all-visible.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example:</p>
<pre><code class="language-sql">CREATE INDEX idx_users_email_id
ON users (email) INCLUDE (id);

SELECT id
FROM users
WHERE email = 'alice@example.com';</code></pre>
<p>The index has <code>email</code> for searching and <code>id</code> as payload. If visibility conditions are satisfied, PostgreSQL can answer mostly from the index.</p>
</td>
<td valign="top" width="50%">
<p>Пример:</p>
<pre><code class="language-sql">CREATE INDEX idx_users_email_id
ON users (email) INCLUDE (id);

FROM users
WHERE email = 'alice@example.com';</code></pre>
<p>Индекс имеет <code>email</code> для поиска и <code>id</code> как payload. Если visibility conditions выполнены, PostgreSQL может ответить в основном из индекса.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>

<td valign="top" width="50%">

<th colspan="2" align="left">Traps / caveats</th>

<li>Vacuum helps maintain visibility map information.</li>
<li>Index-only scans can be worse if the index becomes too large.</li>

</td>
<td valign="top" width="50%">
<ul>
<li>“Все колонки есть в индексе” необходимо, но недостаточно.</li>

<details>
<summary><strong>DB-IDX-040. What is the difference between a unique index and a unique constraint?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A unique constraint is a schema-level integrity rule; PostgreSQL enforces it using a unique index. A unique index is the physical/index mechanism and can be more flexible, for example partial or expression-based.</p>
</td>
<td valign="top" width="50%">
<p>Unique constraint — это schema-level integrity rule; PostgreSQL enforce-ит его через unique index. Unique index — физический/index mechanism и может быть гибче, например partial или expression-based.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>When you write:</p>
<pre><code class="language-sql">ALTER TABLE users
ADD CONSTRAINT users_email_key UNIQUE (email);</code></pre>
<p>PostgreSQL creates a unique index to enforce the constraint. The constraint communicates a data model invariant.</p>
<p>When you write:</p>
<pre><code class="language-sql">CREATE UNIQUE INDEX ux_users_lower_email
ON users (lower(email));</code></pre>
<p>you create an index directly, which can enforce uniqueness on an expression.</p>
</td>
<td valign="top" width="50%">
<p>Когда ты пишешь:</p>
<pre><code class="language-sql">ALTER TABLE users
ADD CONSTRAINT users_email_key UNIQUE (email);</code></pre>
<p>PostgreSQL создаёт unique index для enforcement. Constraint выражает invariant модели данных.</p>
<p>Когда ты пишешь:</p>
<pre><code class="language-sql">CREATE UNIQUE INDEX ux_users_lower_email
ON users (lower(email));</code></pre>
<p>ты создаёшь индекс напрямую, который может enforce-ить uniqueness по expression.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use a unique constraint for normal relational model invariants. Use a unique index directly when you need features not expressible as a standard constraint, such as partial uniqueness or expression-based uniqueness.</p>
<p>Foreign keys generally reference primary keys, unique constraints, or suitable non-partial unique indexes on referenced columns; partial/expression uniqueness is not a general replacement for relational keys.</p>
</td>
<td valign="top" width="50%">
<p>Unique constraint лучше использовать для обычных invariants реляционной модели. Unique index напрямую — когда нужны возможности, которые не выражаются стандартным constraint, например partial uniqueness или expression-based uniqueness.</p>
<p>Foreign keys обычно ссылаются на primary keys, unique constraints или подходящие non-partial unique indexes по referenced columns; partial/expression uniqueness не является общей заменой relational keys.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">
<p>В production constraints легче понимать как business rules, и они видны в schema modeling. Direct unique indexes очень полезны для advanced patterns, но их нужно понятно называть и документировать.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>

<td valign="top" width="50%">
<ul>
