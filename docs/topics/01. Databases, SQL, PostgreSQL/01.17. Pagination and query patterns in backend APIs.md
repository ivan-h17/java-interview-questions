# Pagination and query patterns in backend APIs

This section covers OFFSET/LIMIT pagination, keyset/cursor pagination, stable ordering, index support and dynamic filter pitfalls.

<a id="db-api-001"></a>

<details>
<summary><strong>DB-API-001. What is OFFSET/LIMIT pagination?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>OFFSET/LIMIT pagination returns a page by skipping N rows and then taking a limited number of rows.</p>
</td>
<td valign="top" width="50%">
<p>OFFSET/LIMIT pagination возвращает page, пропуская N rows и беря limited number rows.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example: <code>LIMIT 20 OFFSET 100</code> means skip the first 100 rows and return the next 20.</p>
<p>It is simple and supports page numbers, which makes it common in admin tables and small datasets.</p>
</td>
<td valign="top" width="50%">
<p>Пример: <code>LIMIT 20 OFFSET 100</code> означает skip first 100 rows and return next 20.</p>
<p>Это просто и supports page numbers, поэтому common in admin tables и small datasets.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The database still has to identify and discard skipped rows. With large offsets, work grows with the offset.</p>
<p>Results also require stable ordering, otherwise pages can be inconsistent.</p>
</td>
<td valign="top" width="50%">
<p>Database всё равно должна identify and discard skipped rows. При large offsets work grows with offset.</p>
<p>Также нужен stable ordering, иначе pages могут быть inconsistent.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use OFFSET/LIMIT for small datasets, internal tools, or shallow pages. For infinite scroll or large tables, prefer keyset/cursor pagination.</p>
<p>Always include deterministic ORDER BY.</p>
</td>
<td valign="top" width="50%">
<p>Используй OFFSET/LIMIT для small datasets, internal tools или shallow pages. Для infinite scroll или large tables лучше keyset/cursor pagination.</p>
<p>Всегда добавляй deterministic ORDER BY.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Without ORDER BY, page order is not guaranteed.</li>
<li>Large offsets are slow.</li>
<li>Concurrent inserts/deletes can shift rows between pages.</li>
<li>COUNT(*) for total pages may be expensive.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Без ORDER BY order pages не guaranteed.</li>
<li>Large offsets slow.</li>
<li>Concurrent inserts/deletes могут shift rows between pages.</li>
<li>COUNT(*) для total pages может быть expensive.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does OFFSET do?<br>A: Skips a number of rows before returning the limit.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что делает OFFSET?<br>A: Пропускает заданное число rows before returning limit.</p>

<summary><strong>🔥 DB-API-002. Why can OFFSET pagination become slow on large tables?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Because PostgreSQL must still walk through the skipped rows before returning the requested page.</p>
</td>
<td valign="top" width="50%">
<p>Потому что PostgreSQL всё равно должен пройти skipped rows перед возвратом нужной page.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>With <code>OFFSET 100000 LIMIT 20</code>, the database cannot simply jump to row 100001 unless the access path supports it perfectly. It often reads many index/table entries and discards them.</p>
<p>The deeper the page, the more work.</p>
</td>
<td valign="top" width="50%">
<p>С <code>OFFSET 100000 LIMIT 20</code> database не может просто jump to row 100001, если access path не supports it perfectly. Часто она читает много index/table entries и discards them.</p>
<p>Чем deeper page, тем больше work.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Even with an index, PostgreSQL may scan through index entries to reach the offset. If heap visits are needed, it can be even more expensive.</p>
<p>Large OFFSET also creates unstable UX under concurrent changes.</p>
</td>
<td valign="top" width="50%">
<p>Даже с index PostgreSQL может scan through index entries to reach offset. Если нужны heap visits, это ещё дороже.</p>
<p>Large OFFSET также creates unstable UX при concurrent changes.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production APIs, large offsets can become a hidden denial-of-service vector. Add maximum page depth, use keyset pagination, or use search/index systems for deep browsing.</p>
<p>Monitor queries with high offsets.</p>
</td>
<td valign="top" width="50%">
<p>В production APIs large offsets могут стать hidden denial-of-service vector. Добавь maximum page depth, use keyset pagination или search/index systems for deep browsing.</p>
<p>Monitor queries with high offsets.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Index does not eliminate offset cost completely.</li>
<li>Page number UX conflicts with performance on large data.</li>
<li>Deletes/inserts can duplicate or skip rows across pages.</li>
<li>Deep pagination should be restricted.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Index не полностью устраняет offset cost.</li>
<li>Page number UX конфликтует с performance on large data.</li>
<li>Deletes/inserts могут duplicate/skip rows across pages.</li>
<li>Deep pagination should be restricted.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why is OFFSET slow for deep pages?<br>A: Rows before the requested page still need to be scanned/skipped.</p>
</td>
<td valign="top" width="50%">
<p>Q: Почему OFFSET slow для deep pages?<br>A: Rows before requested page всё равно нужно scan/skip.</p>
</td>
</tr>

<details>
<summary><strong>🔥 DB-API-003. What is keyset pagination?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Keyset pagination uses the last seen sort key instead of OFFSET to fetch the next page.</p>
</td>
<td valign="top" width="50%">
<p>Keyset pagination использует last seen sort key вместо OFFSET для получения next page.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Instead of saying “skip 100000 rows”, the query says “give me rows after this last value”.</p>
<p>Example: <code>WHERE (created_at, id) &lt; (:last_created_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20</code>.</p>
</td>
<td valign="top" width="50%">
<p>Вместо “skip 100000 rows” query говорит “дай rows after this last value”.</p>
<p>Пример: <code>WHERE (created_at, id) &lt; (:last_created_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Keyset pagination works best with a stable, indexed order. It can use an index range scan and does not pay the cost of skipping previous pages.</p>
<p>It is ideal for feeds, event streams, audit logs, and infinite scroll.</p>
</td>
<td valign="top" width="50%">
<p>Keyset pagination лучше всего работает со stable indexed order. Она может использовать index range scan и не платит cost skipped previous pages.</p>
<p>Она ideal for feeds, event streams, audit logs и infinite scroll.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, return an opaque cursor containing the last key values and sort direction. Keep cursor validation and versioning in mind.</p>
<p>Keyset pagination is usually not good for jumping to arbitrary page number.</p>
</td>
<td valign="top" width="50%">
<p>В production возвращай opaque cursor с last key values и sort direction. Учитывай cursor validation и versioning.</p>
<p>Keyset pagination обычно not good for jumping to arbitrary page number.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Ordering must be unique or have a tie-breaker.</li>
<li>Cursor values must match ORDER BY exactly.</li>
<li>Changing filters invalidates cursors.</li>
<li>Backward pagination needs separate design.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Ordering должен быть unique или иметь tie-breaker.</li>
<li>Cursor values должны match ORDER BY exactly.</li>
<li>Changing filters invalidates cursors.</li>
<li>Backward pagination требует separate design.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is keyset pagination?<br>A: Fetching the next page using the last seen sort key instead of OFFSET.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое keyset pagination?<br>A: Получение next page через last seen sort key вместо OFFSET.</p>
</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>DB-API-004. How would you implement cursor/keyset pagination?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Choose a deterministic ORDER BY, add a tie-breaker, index it, and use the last returned key values as the next cursor.</p>
</td>
<td valign="top" width="50%">
<p>Выбрать deterministic ORDER BY, добавить tie-breaker, создать index и использовать last returned key values как next cursor.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For ordering by newest first, use <code>ORDER BY created_at DESC, id DESC</code>. The next page condition is <code>(created_at, id) &lt; (:lastCreatedAt, :lastId)</code>.</p>
<p>Encode cursor values into an opaque token so clients do not depend on internal details.</p>
</td>
<td valign="top" width="50%">
<p>Для ordering newest first используй <code>ORDER BY created_at DESC, id DESC</code>. Next page condition: <code>(created_at, id) &lt; (:lastCreatedAt, :lastId)</code>.</p>
<p>Encode cursor values в opaque token, чтобы clients не зависели от internals.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The index should match filtering and ordering, for example <code>(tenant_id, created_at DESC, id DESC)</code> for tenant-scoped feeds.</p>
<p>Use a unique tie-breaker like id because timestamps can have duplicates.</p>
</td>
<td valign="top" width="50%">
<p>Index должен match filtering и ordering, например <code>(tenant_id, created_at DESC, id DESC)</code> для tenant-scoped feeds.</p>
<p>Use unique tie-breaker вроде id, потому что timestamps могут duplicate.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, include filters in cursor or reject cursor/filter mismatches. Sign or encrypt cursors if tampering matters.</p>
<p>Define cursor expiration and backward navigation separately.</p>
</td>
<td valign="top" width="50%">
<p>В production include filters in cursor или reject cursor/filter mismatches. Sign/encrypt cursors, если tampering matters.</p>
<p>Определи cursor expiration и backward navigation separately.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not use non-deterministic ordering.</li>
<li>Do not expose raw sensitive fields in cursor.</li>
<li>Null sort values require explicit handling.</li>
<li>Use consistent ASC/DESC semantics.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Не используй non-deterministic ordering.</li>
<li>Не expose raw sensitive fields in cursor.</li>
<li>Null sort values требуют explicit handling.</li>
<li>Используй consistent ASC/DESC semantics.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Keyset pagination needs what tie-breaker?<br>A: A unique stable column like id after the main sort key.</p>
</td>
<td valign="top" width="50%">
<p>Q: Какой tie-breaker нужен keyset pagination?<br>A: Unique stable column вроде id после main sort key.</p>
</td>
</tr>

<details>
<summary><strong>DB-API-007. Why is stable ordering important for pagination?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Stable ordering prevents rows from appearing in random order, being duplicated, or being skipped between pages.</p>
</td>
<td valign="top" width="50%">
<p>Stable ordering предотвращает random order, duplicates и skipped rows between pages.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If multiple rows have the same sort value, ordering only by that value is not deterministic. Add a unique tie-breaker like <code>id</code>.</p>
<p>Without ORDER BY, PostgreSQL does not guarantee row order at all.</p>
</td>
<td valign="top" width="50%">
<p>Если multiple rows имеют same sort value, ordering only by that value non-deterministic. Добавь unique tie-breaker вроде <code>id</code>.</p>
<p>Без ORDER BY PostgreSQL вообще не гарантирует row order.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For keyset pagination, cursor condition must match ORDER BY exactly. For example, if ORDER BY is <code>created_at DESC, id DESC</code>, cursor comparison should use both fields.</p>
<p>Stable ordering is also important for caching and reproducible API behavior.</p>
</td>
<td valign="top" width="50%">
<p>Для keyset pagination cursor condition должен match ORDER BY exactly. Например, если ORDER BY <code>created_at DESC, id DESC</code>, cursor comparison должен использовать оба fields.</p>
<p>Stable ordering также важно для caching и reproducible API behavior.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production APIs, always specify deterministic ordering. Avoid relying on physical table order or implicit primary-key order.</p>
<p>Document ordering so clients understand page behavior.</p>
</td>
<td valign="top" width="50%">
<p>В production APIs всегда specify deterministic ordering. Не rely on physical table order или implicit primary-key order.</p>
<p>Document ordering, чтобы clients понимали page behavior.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>ORDER BY created_at alone is not stable if timestamps duplicate.</li>
<li>Concurrent writes still affect pagination, but stable order reduces surprises.</li>
<li>NULL ordering should be explicit.</li>
<li>Changing default order is a breaking API change.</li>
</ul>
