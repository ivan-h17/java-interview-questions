<details>
<summary><strong>🔥 DB-JOINALG-002. What is a Nested Loop Join?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Nested Loop Join iterates rows from the outer input and searches matching rows in the inner input for each outer row.</p>
</td>
<td valign="top" width="50%">
<p>Nested Loop Join перебирает rows outer input и ищет matching rows в inner input для каждой outer row.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Conceptually it is like a loop inside a loop, but the inner side can be an efficient index lookup. Modern PostgreSQL may add <code>Memoize</code> to cache repeated inner lookups.</p>
</td>
<td valign="top" width="50%">
<p>Концептуально это loop внутри loop, но inner side может быть эффективным index lookup. Modern PostgreSQL может добавить <code>Memoize</code>, чтобы cache repeated inner lookups.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>It is excellent when the outer side is small and the inner access path is cheap; it is terrible when the outer side is huge and inner lookup repeats many times. In plans, the total cost is often hidden in <code>loops</code>, not in one execution of the inner node.</p>
</td>
<td valign="top" width="50%">
<p>Он отличен, когда outer side маленькая и inner access path дешёвый; ужасен, когда outer side огромная и inner lookup повторяется много раз. В plans total cost часто скрыт в <code>loops</code>, а не в одном execution inner node.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In <code>EXPLAIN ANALYZE</code>, pay attention to <code>loops</code>, actual rows on the outer side, and <code>Memoize</code> hit/miss counters when present. A node that is fast once can be expensive when executed hundreds of thousands of times.</p>
</td>
<td valign="top" width="50%">
<p>В <code>EXPLAIN ANALYZE</code> смотри <code>loops</code>, actual rows на outer side и <code>Memoize</code> hit/miss counters, если они есть. Node, быстрый один раз, может быть дорогим при сотнях тысяч executions.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Nested Loop is not always bad.</li><li>Large unexpected outer rows make it dangerous.</li><li>Inner side usually needs a good index.</li><li><code>Memoize</code> can help repeated lookups, but it does not fix a fundamentally huge outer input.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>Nested Loop не всегда плох.</li><li>Большое unexpected число outer rows делает его опасным.</li><li>Inner side обычно требует хороший index.</li><li><code>Memoize</code> помогает repeated lookups, но не исправляет fundamentally huge outer input.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is a Nested Loop Join?<br>A: Nested Loop Join iterates rows from the outer input and searches matching rows in the inner input for each outer row.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое Nested Loop Join?<br>A: Nested Loop Join перебирает rows outer input и ищет matching rows в inner input для каждой outer row.</p>
</td>

<details>
<summary><strong>🔥 DB-JOINALG-005. What is a Hash Join?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Hash Join builds a hash table from one input and probes it with rows from the other input.</p>
</td>
<td valign="top" width="50%">
<p>Hash Join строит hash table по одному input и probe-ит её строками другого input.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>It is usually used for equality joins over medium/large inputs when nested loops would be too expensive and useful ordering is not available.</p>
</td>
<td valign="top" width="50%">
<p>Обычно используется для equality joins по medium/large inputs, когда nested loops слишком дорогие и useful ordering недоступен.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>PostgreSQL usually builds the hash table on the smaller side. If the hash table does not fit memory, it may use batches and temporary files. In a plan, look for <code>Hash Cond</code>, <code>Buckets</code>, <code>Batches</code>, and memory usage.</p><pre><code class="language-text">Hash Join
  Hash Cond: (line_items.order_id = orders.id)
  -&gt; Seq Scan on line_items
  -&gt; Hash
       Buckets: 262144  Batches: 1  Memory Usage: 12000kB</code></pre>
</td>
<td valign="top" width="50%">
<p>PostgreSQL обычно строит hash table по меньшей стороне. Если hash table не помещается в memory, могут использоваться batches и temporary files. В plan смотри <code>Hash Cond</code>, <code>Buckets</code>, <code>Batches</code> и memory usage.</p><pre><code class="language-text">Hash Join
  Hash Cond: (line_items.order_id = orders.id)
  -&gt; Seq Scan on line_items
  -&gt; Hash
       Buckets: 262144  Batches: 1  Memory Usage: 12000kB</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>When debugging, check hash memory usage, buckets, batches, temp reads/writes, <code>work_mem</code>, <code>hash_mem_multiplier</code>, and whether inputs can be filtered earlier.</p>
</td>
<td valign="top" width="50%">
<p>При отладке смотри hash memory usage, buckets, batches, temp reads/writes, <code>work_mem</code>, <code>hash_mem_multiplier</code> и можно ли раньше фильтровать inputs.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li>Mostly for equality joins.</li><li>Can spill to disk.</li><li>Indexes are not required for Hash Join, but can reduce inputs.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li>В основном для equality joins.</li><li>Может spill to disk.</li><li>Indexes не обязательны для Hash Join, но могут уменьшить inputs.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is a Hash Join?<br>A: Hash Join builds a hash table from one input and probes it with rows from the other input.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое Hash Join?<br>A: Hash Join строит hash table по одному input и probe-ит её строками другого input.</p>
</td>
</tr>

<details>
<summary><strong>DB-JOINALG-007. How does work_mem affect Hash Join?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>work_mem</code> and <code>hash_mem_multiplier</code> influence how much memory a Hash Join can use before PostgreSQL uses batches/temp files.</p>
</td>
<td valign="top" width="50%">
<p><code>work_mem</code> и <code>hash_mem_multiplier</code> влияют на то, сколько memory Hash Join может использовать перед batches/temp files.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If the hash table is too large, PostgreSQL partitions it into batches and reads/writes temporary data, which can be slow. A jump from <code>Batches: 1</code> to many batches is a strong spill signal.</p>
</td>
<td valign="top" width="50%">
<p>Если hash table слишком большая, PostgreSQL делит её на batches и читает/пишет temporary data, что может быть медленно. Переход от <code>Batches: 1</code> к множеству batches — сильный spill signal.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A single query can use multiple memory allocations, and concurrency multiplies memory demand. Hash joins may use <code>work_mem * hash_mem_multiplier</code>, so changing memory globally can have a large blast radius.</p>
</td>
<td valign="top" width="50%">
<p>Один query может использовать несколько memory allocations, а concurrency умножает memory demand. Hash joins могут использовать <code>work_mem * hash_mem_multiplier</code>, поэтому global memory changes имеют большой blast radius.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Tune carefully: raising global <code>work_mem</code> can hurt stability; prefer reducing inputs or session-level tuning when appropriate.</p><pre><code class="language-sql">BEGIN;
SET LOCAL work_mem = '256MB';
-- one heavy analytical query
COMMIT;</code></pre>
</td>
<td valign="top" width="50%">
<p>Настраивай осторожно: raising global <code>work_mem</code> может повредить stability; лучше уменьшать inputs или tuning на session-level.</p><pre><code class="language-sql">BEGIN;
SET LOCAL work_mem = '256MB';
-- one heavy analytical query
COMMIT;</code></pre>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul><li><code>work_mem</code> is per operation.</li><li>Hash nodes also depend on <code>hash_mem_multiplier</code>.</li><li>Parallel/concurrent queries multiply usage.</li><li>Spill may indicate too much input, not only too little memory.</li></ul>
</td>
<td valign="top" width="50%">
<ul><li><code>work_mem</code> per operation.</li><li>Hash nodes также зависят от <code>hash_mem_multiplier</code>.</li><li>Parallel/concurrent queries умножают usage.</li><li>Spill может означать слишком большой input, а не только мало memory.</li></ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: How does work_mem affect Hash Join?<br>A: work_mem limits memory available for hash tables before PostgreSQL uses batches/temp files.</p>
</td>
<td valign="top" width="50%">
