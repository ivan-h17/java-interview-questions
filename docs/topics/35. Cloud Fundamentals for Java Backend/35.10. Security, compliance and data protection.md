# Security, compliance and data protection

<a id="cloud-sec-001"></a>

<details>
<summary><strong>CLOUD-SEC-001. What security responsibilities remain with the application team in the cloud?</strong></summary>

#### Short answer

The team still owns secure code, data protection, identity, access, configuration, dependency security and application-level controls.

#### Interview answer

The cloud provider may secure the underlying infrastructure, but the application team owns authentication, authorization, input validation, secrets use, IAM scope, dependency updates, logging hygiene, data classification and correct configuration of managed services.

#### Deep dive

Responsibilities vary by IaaS, PaaS, SaaS and managed services, but customer data and access decisions remain the customer's responsibility.

#### Production angle

Most application security incidents come from bad access control, leaked secrets, public resources, vulnerable dependencies or unsafe logs.

#### Traps / caveats

- Managed services do not secure bad application logic.
- Encryption does not fix overbroad access.
- Security settings need audit and drift detection.

#### Optional Anki

Q: What remains app-owned in cloud security?
A: Code, data, identity, access, configuration and dependency security.

</details>

<a id="cloud-sec-002"></a>

<details>
<summary><strong>CLOUD-SEC-002. How should encryption in transit be handled between clients, services and managed resources?</strong></summary>

#### Short answer

Use TLS for external traffic and protect internal service or managed-resource traffic according to trust boundaries and compliance.

#### Interview answer

Client-to-edge traffic should use HTTPS. Service-to-service and service-to-managed-resource traffic should use TLS or private trusted networking depending on policy. Sensitive systems often require TLS all the way to the backend.

#### Deep dive

Encryption in transit includes certificate validation, hostname verification, modern TLS settings and safe handling of internal CAs.

#### Production angle

Misconfigured TLS causes outages, weak security or failed compliance audits.

#### Traps / caveats

- Do not disable certificate validation in Java clients.
- Internal traffic can still be exposed through compromised networks.
- TLS termination points must be documented.

#### Optional Anki

Q: What should Java HTTP clients never disable in production?
A: Certificate and hostname validation.

</details>

<a id="cloud-sec-003"></a>

<details>
<summary><strong>CLOUD-SEC-003. What is KMS, and why is key management not just encryption?</strong></summary>

#### Short answer

KMS manages cryptographic keys, access policies, rotation and audit; encryption is only one use of those keys.

#### Interview answer

A Key Management Service stores or protects keys used by databases, storage, queues or application encryption. Key management includes who can use keys, who can administer them, rotation, deletion protection, audit logs and separation of duties.

#### Deep dive

KMS can support envelope encryption, where data keys encrypt data and master keys protect data keys.

#### Production angle

Losing key access can make data unavailable; overbroad key access can expose encrypted data.

#### Traps / caveats

- Encryption at rest does not help if every role can decrypt.
- Key deletion can be catastrophic.
- Key rotation needs compatibility planning.

#### Optional Anki

Q: Why is KMS more than encryption?
A: It controls key access, rotation, audit and lifecycle.

</details>

<a id="cloud-sec-004"></a>

<details>
<summary><strong>🧠 CLOUD-SEC-004. How should certificates and TLS renewal be managed?</strong></summary>

#### Short answer

Automate issuance and renewal, monitor expiry and document ownership for every certificate.

#### Interview answer

Certificates should be managed through platform certificate managers, ACME automation, service mesh or controlled PKI processes. Services need alerts before expiry and deployment paths for renewed certificates.

#### Deep dive

Internal certificates matter too: database TLS, mTLS, private APIs and webhook signing certificates can all expire.

#### Production angle

Certificate expiry is a common avoidable outage.

#### Traps / caveats

- Renewal automation can fail silently.
- Java truststores may need updates for private CAs.
- Long-lived certificates increase exposure.

#### Optional Anki

Q: What prevents certificate-expiry outages?
A: Automated renewal plus expiry monitoring and ownership.

</details>

<a id="cloud-sec-005"></a>

<details>
<summary><strong>🧠 CLOUD-SEC-005. How do network segmentation and private subnets reduce risk?</strong></summary>

#### Short answer

They reduce which systems can reach sensitive services and limit lateral movement after compromise.

#### Interview answer

Segmentation separates public entry points, application services, databases, admin access and third-party connectivity. Private subnets keep internal services away from direct internet exposure.

#### Deep dive

Segmentation should be paired with IAM, authentication and observability. Network boundaries alone do not prove the caller is authorized.

#### Production angle

If a public API is compromised, segmentation can prevent direct access to databases or admin services.

#### Traps / caveats

- Private network does not mean trusted caller.
- Overly complex segmentation can block operations.
- Egress paths need controls too.

#### Optional Anki

Q: What does network segmentation limit?
A: Reachability and lateral movement.

</details>

<a id="cloud-sec-006"></a>

<details>
<summary><strong>CLOUD-SEC-006. What are WAF, DDoS protection and rate limiting used for?</strong></summary>

#### Short answer

They protect public endpoints from common web attacks, traffic floods and abusive request rates.

#### Interview answer

A WAF can block known malicious patterns, DDoS protection absorbs or filters large attacks, and rate limiting controls per-client or per-token request volume. They complement application validation and authorization.

#### Deep dive

Rate limits should match business semantics: per user, API key, IP, tenant or endpoint.

#### Production angle

These controls reduce risk of overload, scraping, brute force and expensive downstream calls.

#### Traps / caveats

- WAF rules can create false positives.
- IP-based limits are weak behind NAT or proxies.
- Rate limiting should return clear HTTP responses.

#### Optional Anki

Q: What is rate limiting for?
A: Controlling request volume to protect services and enforce fair use.

</details>

<a id="cloud-sec-007"></a>

<details>
<summary><strong>🧠 CLOUD-SEC-007. How should vulnerability scanning apply to cloud images, dependencies and managed runtimes?</strong></summary>

#### Short answer

Scan application dependencies, container images, base images, IaC and runtime configurations continuously.

#### Interview answer

For Java services, scanning should cover Maven or Gradle dependencies, container layers, OS packages, IaC templates and deployed resources. Findings need severity, exploitability, ownership and remediation timelines.

#### Deep dive

Managed runtimes reduce OS patching work, but application libraries and configuration remain team-owned.

#### Production angle

Scanning only at build time misses drift, new CVEs and changed runtime resources.

#### Traps / caveats

- CVE count alone is not risk.
- Suppressions need expiration and justification.
- Scanning does not replace secure coding.

#### Optional Anki

Q: What should Java cloud vulnerability scanning cover?
A: Dependencies, images, OS packages, IaC and deployed configuration.

</details>

<a id="cloud-sec-008"></a>

<details>
<summary><strong>🧠 CLOUD-SEC-008. How do patching responsibilities differ for VMs, containers and managed services?</strong></summary>

#### Short answer

VMs require OS patching by the team, containers require rebuilding images, and managed services shift more platform patching to the provider.

#### Interview answer

With VMs, teams manage operating system updates and hardening. With containers, teams update base images and dependencies, then redeploy. With managed services, providers handle more infrastructure patching, while teams still manage versions, maintenance windows and application dependencies.

#### Deep dive

Patching affects availability. Rolling updates, blue-green deployment and maintenance windows reduce disruption.

#### Production angle

Unpatched base images and stale Java dependencies are common security findings.

#### Traps / caveats

- Rebuilding an image is required to consume base image patches.
- Managed service patches can still cause restarts or failovers.
- Emergency patches need tested deployment paths.

#### Optional Anki

Q: How do containers consume OS patches?
A: By rebuilding and redeploying images with patched base layers.

</details>

<a id="cloud-sec-009"></a>

<details>
<summary><strong>CLOUD-SEC-009. What sensitive data should not appear in logs, metrics, traces or error responses?</strong></summary>

#### Short answer

Secrets, tokens, passwords, private keys, personal data, payment data and sensitive business data should not be exposed.

#### Interview answer

Telemetry should not include access tokens, session cookies, API keys, authorization headers, full request bodies with personal data, passwords, private keys, card data or detailed internal security errors.

#### Deep dive

Metrics labels and trace attributes are easy to overlook. A user ID or email in a high-cardinality label can create both privacy and cost problems.

#### Production angle

Centralized logs are widely accessible and retained, so leaks there expand incident scope.

#### Traps / caveats

- Error responses can leak stack traces and internal resource names.
- Redaction should happen before data leaves the process.
- Debug logging often reintroduces leaks.

#### Optional Anki

Q: What should never be logged?
A: Secrets, tokens, passwords, private keys and sensitive personal or payment data.

</details>

<a id="cloud-sec-010"></a>

<details>
<summary><strong>CLOUD-SEC-010. How do compliance and data residency requirements influence cloud architecture?</strong></summary>

#### Short answer

They constrain where data is stored, processed, logged, backed up and accessed.

#### Interview answer

Compliance may require specific regions, encryption, retention, audit logs, deletion support, access controls and separation of duties. Data residency means certain data must remain in approved jurisdictions.

#### Deep dive

Residency applies not only to primary databases but also backups, logs, analytics exports, caches, traces and support access.

#### Production angle

Architecture must make data location and access auditable, not just intended.

#### Traps / caveats

- Cross-region replication can violate residency.
- Logs can accidentally move sensitive data.
- Provider region choice does not solve application-level compliance alone.

#### Optional Anki

Q: What does data residency constrain?
A: Where data is stored, processed, backed up, logged and accessed.

</details>

<a id="cloud-sec-011"></a>

<details>
<summary><strong>CLOUD-SEC-011. Why are cloud metadata services and SSRF important security risks?</strong></summary>

#### Short answer

SSRF can let an attacker reach internal metadata endpoints and steal workload credentials.

#### Interview answer

Cloud runtimes often expose metadata services to workloads so SDKs can obtain identity tokens or configuration. If an application has Server-Side Request Forgery, an attacker may trick it into calling those internal endpoints.

#### Deep dive

Defenses include SSRF-safe URL validation, denylisting link-local metadata addresses, egress controls, metadata service protections, least-privilege roles and avoiding generic URL fetchers.

#### Production angle

A simple URL preview or webhook feature can become a cloud-account compromise if it can reach metadata credentials.

#### Traps / caveats

- Blocking only hostnames is insufficient; IP encodings and redirects matter.
- Least privilege limits damage if credentials are stolen.
- Metadata tokens may still be valid long enough for abuse.

#### Optional Anki

Q: Why is SSRF dangerous in cloud?
A: It can expose internal metadata credentials to an attacker.

</details>

<a id="cloud-sec-012"></a>

<details>
<summary><strong>CLOUD-SEC-012. How would you threat-model a Java service that uses several managed cloud services?</strong></summary>

#### Short answer

Map assets, entry points, identities, data flows, trust boundaries, abuse cases and failure impact.

#### Interview answer

I would identify sensitive data, public APIs, IAM roles, secrets, databases, queues, object storage, admin paths and third-party integrations. Then I would ask how data could be read, modified, deleted, leaked or abused.

#### Deep dive

Threat modeling should include cloud-specific risks: public buckets, overbroad IAM, metadata SSRF, event injection, poisoned queues, log leaks and cross-account trust.

#### Production angle

The output should be concrete controls: validation, authorization, encryption, monitoring, rate limits, policy checks and incident playbooks.

#### Traps / caveats

- Do not threat-model only the Java code.
- Include CI/CD and infrastructure changes.
- Revisit the model after new dependencies or architecture changes.

#### Optional Anki

Q: What does cloud threat modeling include?
A: Assets, identities, data flows, trust boundaries, abuse cases and controls.

</details>

<a id="cloud-sec-013"></a>

<details>
<summary><strong>🧠 CLOUD-SEC-013. What does zero-trust mean in practical backend cloud architecture?</strong></summary>

#### Short answer

Zero-trust means no network location is automatically trusted; every access should be authenticated, authorized and observable.

#### Interview answer

In practice, services use strong workload identity, least privilege, mTLS or TLS where needed, short-lived credentials, policy enforcement, segmentation and continuous monitoring. Being inside a VPC is not enough proof of trust.

#### Deep dive

Zero-trust is an architecture direction, not a single product. It changes assumptions about internal traffic and admin access.

#### Production angle

It reduces lateral movement when one service, credential or network segment is compromised.

#### Traps / caveats

- Do not turn zero-trust into unmaintainable ceremony.
- Identity and policy automation are required for developer usability.
- Legacy protocols may need migration plans.

#### Optional Anki

Q: What is the core zero-trust idea?
A: Do not trust by network location; verify identity and authorization for access.

</details>

<a id="cloud-sec-014"></a>

<details>
<summary><strong>🧠 CLOUD-SEC-014. How do data classification, retention and deletion requirements affect cloud services?</strong></summary>

#### Short answer

They determine where data can live, who can access it, how long it is kept and how it is deleted.

#### Interview answer

Data classification labels data by sensitivity and business value. Retention policies define how long it must or may be kept. Deletion requirements define when and how it must be removed from primary stores, backups, logs and derived systems.

#### Deep dive

Backend systems often copy data to caches, events, object storage, search indexes, analytics and logs, so deletion and retention are distributed problems.

#### Production angle

Compliance failures often come from forgotten copies of data, not the primary database.

#### Traps / caveats

- Backups and immutable archives complicate deletion.
- Logs may contain personal data accidentally.
- Retention policies must be enforceable and auditable.

#### Optional Anki

Q: Why is deletion hard in cloud systems?
A: Data may exist in backups, logs, caches, events, indexes and analytics copies.

</details>
