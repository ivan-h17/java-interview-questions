<details>
<summary><strong>CLOUD-NET-001. What are VPCs, subnets and cloud firewall rules at a high level?</strong></summary>

#### Short answer

A VPC is an isolated cloud network, subnets divide its address space, and firewall rules control allowed traffic.

#### Interview answer

A VPC or virtual network gives a workload private networking boundaries. Subnets usually represent address ranges in zones or regions. Firewall rules, security groups or equivalent controls define which sources, destinations, ports and protocols are allowed.

#### Deep dive

Backend engineers do not need to be network specialists, but they should know where their service is reachable from, which dependencies it can reach and what traffic is intentionally blocked.

#### Production angle

Wrong network rules can expose internal APIs publicly or prevent a service from reaching databases, queues or external APIs.

#### Traps / caveats

- Private subnet does not automatically mean no outbound internet.
- Firewall rules should be least privilege, not broad CIDR ranges.
- Network changes need rollout and rollback plans.

#### Optional Anki

Q: What does a VPC provide?
A: An isolated virtual network boundary for cloud resources.

</details>

<details>
<summary><strong>CLOUD-NET-002. What is the difference between public and private subnets?</strong></summary>

#### Short answer

Public subnets can route directly to the internet; private subnets do not expose resources directly to inbound internet traffic.

#### Interview answer

Public subnets are used for resources that must be internet reachable, often load balancers or bastion-style access points. Private subnets are used for application services, databases and internal systems that should be reached through controlled paths.

#### Deep dive

The exact definition depends on route tables and public IP assignment. A private subnet may still make outbound calls through NAT or private connectivity.

#### Production angle

Most Java backend services and databases should not be directly public. They should sit behind load balancers, gateways or private networks.

#### Traps / caveats

- A resource can be exposed by a public IP even if naming suggests it is private.
- NAT enables outbound access but not direct inbound access.
- Private subnet design still needs egress control.

#### Optional Anki

Q: What makes a subnet public?
A: Routing and addressing that allow direct internet reachability.

</details>

<details>
<summary><strong>🧠 CLOUD-NET-003. What are route tables, internet gateways and NAT gateways used for?</strong></summary>

#### Short answer

Route tables decide where traffic goes, internet gateways connect public networks to the internet, and NAT gateways let private resources initiate outbound internet traffic.

#### Interview answer

Route tables map destination ranges to next hops. Internet gateways or equivalent services provide internet connectivity for public resources. NAT gateways allow private instances to call external services without accepting inbound internet connections.

#### Deep dive

For backend services, these components affect access to third-party APIs, package repositories, managed services and update endpoints.

#### Production angle

A failed or misconfigured NAT gateway can break outbound calls from many private services at once.

#### Traps / caveats

- NAT can become a cost and availability dependency.
- Route-table mistakes can blackhole traffic.
- Private connectivity may be better than public internet plus NAT for managed services.

#### Optional Anki

Q: What does NAT provide for private services?
A: Outbound internet access without direct inbound internet exposure.

</details>

<a id="cloud-net-004"></a>

<details>
<summary><strong>🧠 CLOUD-NET-004. What is the difference between stateful and stateless network filtering?</strong></summary>

#### Short answer

Stateful filtering remembers connection state; stateless filtering evaluates each packet independently.

#### Interview answer

With stateful filtering, if outbound traffic is allowed, return traffic is usually allowed automatically. With stateless filtering, both inbound and outbound directions must be explicitly permitted.

#### Deep dive

Provider names differ, but the concept matters when debugging asymmetric network failures or designing defense in depth.

#### Production angle

Stateless rule mistakes often cause confusing connection failures even when one direction looks open.

#### Traps / caveats

- Do not assume every cloud firewall behaves the same way.
- Ephemeral port ranges matter for return traffic in stateless rules.
- Network filtering is not a substitute for application authentication.

#### Optional Anki

Q: Stateful vs stateless network filtering?
A: Stateful remembers connections; stateless evaluates each packet or direction separately.

</details>

<a id="cloud-net-005"></a>

<details>
<summary><strong>CLOUD-NET-005. How do cloud load balancers affect backend service design?</strong></summary>

#### Short answer

They distribute traffic, perform health checks and often terminate TLS, so services must handle stateless requests, forwarding headers and graceful draining.

#### Interview answer

A cloud load balancer sits in front of service instances and routes traffic only to healthy targets. Java services need correct health endpoints, timeout settings, connection handling and awareness of forwarded client information such as original IP and protocol.

#### Deep dive

Load balancers may retry, buffer, impose idle timeouts or remove instances during deployments. These behaviors affect long requests, streaming and graceful shutdown.

#### Production angle

Bad health checks can send users to broken instances or remove healthy instances during dependency outages.

#### Traps / caveats

- Do not make readiness depend on optional dependencies.
- Load balancer timeouts must align with app and gateway timeouts.
- Trust proxy headers only from trusted proxies.

#### Optional Anki

Q: What must Java services handle behind load balancers?
A: Health checks, statelessness, forwarding headers, timeouts and graceful draining.

</details>

<details>
<summary><strong>🧠 CLOUD-NET-006. What is the difference between L4 and L7 load balancing?</strong></summary>

#### Short answer

L4 load balancing routes by transport-level data; L7 load balancing understands application protocols like HTTP.

#### Interview answer

L4 load balancers work with TCP or UDP connections and are usually protocol-agnostic. L7 load balancers can route by HTTP host, path, headers, cookies or methods and can provide features like TLS termination and HTTP redirects.

#### Deep dive

L7 is useful for REST APIs and gateways. L4 can be useful for non-HTTP protocols, lower overhead or preserving protocol behavior.

#### Production angle

Choosing the wrong layer can break WebSockets, gRPC, client IP handling or protocol-specific behavior.

#### Traps / caveats

- L7 proxies may modify headers and connection behavior.
- L4 does not understand HTTP status or paths.
- Timeouts differ by layer and provider.

#### Optional Anki

Q: L4 vs L7 load balancer?
A: L4 routes transport connections; L7 routes application protocol requests.

</details>

<a id="cloud-net-007"></a>

<details>
<summary><strong>CLOUD-NET-007. How should TLS termination be handled at the edge or load balancer?</strong></summary>

#### Short answer

Terminate TLS at a trusted edge when appropriate, then protect internal traffic according to risk and compliance needs.

#### Interview answer

TLS often terminates at a load balancer, gateway or ingress so certificates can be managed centrally. From there, traffic may continue as HTTP in a private network or be re-encrypted to backend services.

#### Deep dive

End-to-end encryption is stronger but adds certificate distribution and operational complexity. The choice depends on network trust, compliance, service mesh, threat model and data sensitivity.

#### Production angle

Certificate expiry, weak TLS policy or incorrect forwarded-proto handling can cause outages or security issues.

#### Traps / caveats

- Do not trust `X-Forwarded-Proto` from arbitrary clients.
- Internal plaintext may violate policy for sensitive data.
- Certificate renewal must be monitored.

#### Optional Anki

Q: Why terminate TLS at a load balancer?
A: To centralize certificate management and edge security controls.

</details>

<a id="cloud-net-008"></a>

<details>
<summary><strong>🧠 CLOUD-NET-008. What is private connectivity to managed services?</strong></summary>

#### Short answer

It lets workloads reach managed services over private network paths instead of public internet endpoints.

#### Interview answer

Private connectivity can expose databases, storage APIs, queues or provider services through private IPs, endpoints or peering. This reduces public exposure and can simplify firewall control.

#### Deep dive

The implementation differs by provider, but the design questions are similar: DNS resolution, route tables, access policies, endpoint scaling, cost and cross-region behavior.

#### Production angle

Private endpoints reduce exposure but can create hidden network dependencies and DNS surprises.

#### Traps / caveats

- Private connectivity does not replace IAM.
- DNS must resolve to the private endpoint from the right networks.
- Endpoint or peering limits can become production constraints.

#### Optional Anki

Q: What does private connectivity to managed services reduce?
A: Public internet exposure for service-to-service or workload-to-managed-service traffic.

</details>

<a id="cloud-net-009"></a>

<details>
<summary><strong>CLOUD-NET-009. How does DNS affect service availability and failover?</strong></summary>

#### Short answer

DNS controls how clients find services, but caching, TTLs and client behavior affect how quickly failover works.

#### Interview answer

Cloud systems often use DNS for load balancers, managed databases, private endpoints and multi-region routing. During failover, DNS records may change, but clients and JVM libraries may cache results.

#### Deep dive

Java DNS caching, connection pools and long-lived connections can delay failover even when provider DNS changes quickly.

#### Production angle

Database failover may require closing stale connections and respecting DNS TTLs, not only waiting for a new DNS record.

#### Traps / caveats

- Low TTL does not guarantee immediate client switch.
- Some clients cache DNS longer than expected.
- DNS health checks need careful design to avoid flapping.

#### Optional Anki

Q: Why can DNS failover be slow?
A: Clients, resolvers and connection pools may cache old addresses or keep old connections.

</details>

<details>
<summary><strong>🧠 CLOUD-NET-010. What is a CDN, and when is it useful for backend systems?</strong></summary>

#### Short answer

A CDN serves cacheable content from edge locations close to users and reduces origin load.

#### Interview answer

CDNs are useful for static assets, downloads, images, public files and sometimes cacheable API responses. They reduce latency and shield backend services from repeated requests.

#### Deep dive

For APIs, CDN use depends on cache keys, headers, authorization, cookies, invalidation and freshness requirements.

#### Production angle

A CDN can reduce database and service load during traffic spikes, but wrong caching can leak or serve stale user data.

#### Traps / caveats

- Do not cache personalized responses unless cache keys are correct.
- Invalidation is not always instant.
- Respect `Cache-Control` and authorization semantics.

#### Optional Anki

Q: When is a CDN useful?
A: For cacheable content that benefits from edge delivery and reduced origin load.

</details>

<details>
<summary><strong>CLOUD-NET-011. Why can outbound traffic and egress rules matter for backend services?</strong></summary>

#### Short answer

Outbound traffic controls security, dependency access and cost.

#### Interview answer

Java services often call payment providers, email APIs, object storage, identity providers and internal services. Egress rules decide what they can reach. Uncontrolled outbound traffic increases data exfiltration risk and can create unexpected network charges.

#### Deep dive

Egress design includes NAT, proxies, private endpoints, allowlists, DNS control and service-to-service policies.

#### Production angle

Blocking required egress can break production; allowing all egress can hide data leaks or malware behavior.

#### Traps / caveats

- Egress through NAT can become expensive.
- Provider APIs may need private endpoints or explicit firewall exceptions.
- DNS-based allowlists can be brittle.

#### Optional Anki

Q: Why control egress?
A: To limit security risk, manage dependency access and avoid unexpected cost.

</details>

<details>
<summary><strong>🧠 CLOUD-NET-012. What are VPN, private interconnect and dedicated connection options used for?</strong></summary>

#### Short answer

They connect cloud networks to on-premise, other clouds or partner networks through private or controlled paths.

#### Interview answer

VPN uses encrypted tunnels over the internet. Dedicated interconnect or direct connection options provide private, often higher-bandwidth and more predictable connectivity. They are used for hybrid systems, migrations, data transfer and private access to existing services.

#### Deep dive

Design needs redundancy, routing, failover, bandwidth, latency and security review.

#### Production angle

A single VPN tunnel can become a critical dependency for migrated Java services that still call on-premise databases or APIs.

#### Traps / caveats

- Private connectivity does not guarantee low latency unless designed and measured.
- Routing changes can affect many systems.
- Hybrid dependencies complicate incident ownership.

#### Optional Anki

Q: What is a private interconnect used for?
A: Private, controlled connectivity between cloud and another network such as on-premise.

</details>

<details>
<summary><strong>CLOUD-NET-013. How do proxy headers such as `X-Forwarded-For` affect security and logging?</strong></summary>

#### Short answer

They carry original client information through proxies, but must be trusted only from known infrastructure.

#### Interview answer

When a load balancer or reverse proxy forwards a request, it may add headers such as original client IP, host or protocol. Java services use them for logging, redirects, rate limiting and security decisions.

#### Deep dive

If the application trusts headers directly from the internet, clients can spoof IPs or protocols. The app should trust forwarded headers only from the configured proxy chain.

#### Production angle

Wrong proxy-header handling breaks audit logs, rate limiting, geo rules, HTTPS redirects and security investigations.

#### Traps / caveats

- Never trust `X-Forwarded-For` from arbitrary clients.
- Multiple proxies append values; parsing order matters.
- Framework proxy settings must match deployment topology.

#### Optional Anki

Q: Why are proxy headers risky?
A: They can be spoofed unless trusted only from known proxies.

</details>

<details>
<summary><strong>CLOUD-NET-014. What are common traps in multi-AZ or multi-region network design?</strong></summary>

#### Short answer

Common traps are hidden single points of failure, cross-zone cost, DNS caching, asymmetric routing and dependency placement.

#### Interview answer

Multi-AZ or multi-region design is not just deploying replicas. The network path, load balancer, NAT, DNS, databases, queues and third-party dependencies must also survive the intended failure.

#### Deep dive

Cross-zone traffic can increase latency and cost. Multi-region traffic can expose data residency and consistency problems.

#### Production angle

A workload can be "multi-AZ" on paper but still fail if all outbound traffic depends on one NAT, all writes depend on one zonal resource or clients cache one failed endpoint.

#### Traps / caveats

- Test zone and region failure scenarios.
- Understand cross-zone data transfer charges.
- Keep routing and health checks simple enough to operate.

#### Optional Anki

Q: What is a multi-AZ trap?
A: Replicas span zones but a shared dependency or network path remains single-zone.

</details>
