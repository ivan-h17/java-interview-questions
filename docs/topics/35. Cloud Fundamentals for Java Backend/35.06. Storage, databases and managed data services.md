# Storage, databases and managed data services

<a id="cloud-data-001"></a>

<details>
<summary><strong>CLOUD-DATA-001. What are the trade-offs of managed databases?</strong></summary>

#### Short answer

Managed databases reduce operational burden but still require schema, capacity, security, backup and client-side failure design.

#### Interview answer

Managed databases can provide provisioning, patching, backups, monitoring, replication and failover. The trade-off is less low-level control, provider-specific limits, maintenance windows, version constraints, cost surprises and reliance on provider behavior.

#### Deep dive

The application team still owns indexes, transactions, query performance, connection pools, data access patterns and restore validation.

#### Production angle

Most managed database incidents are caused by bad queries, connection storms, storage growth, failover surprises or missing restore tests.

#### Traps / caveats

- Managed does not mean self-tuning.
- Read replicas do not solve write bottlenecks.
- Backups are only useful if restore works.

#### Optional Anki

Q: What remains your responsibility with managed databases?
A: Schema, access patterns, security, capacity, client behavior and restore validation.

</details>

<details>
<summary><strong>🧠 CLOUD-DATA-002. When should a Java backend use a managed relational database?</strong></summary>

#### Short answer

Use it when the service needs transactions, relational constraints, SQL querying and operationally supported durability.

#### Interview answer

A managed PostgreSQL or MySQL service is a good default for many Java backends with structured data, transactional updates and reporting needs. It avoids running the database yourself while keeping familiar SQL and JDBC/JPA integration.

#### Deep dive

The decision depends on data volume, write rate, consistency needs, operational maturity, extension support and scaling limits.

#### Production angle

A relational database is often the source of truth, so backup, failover, migration and connection pool design are critical.

#### Traps / caveats

- Do not choose NoSQL just to avoid data modeling.
- Do not assume managed relational databases scale writes automatically.
- ORM behavior can overload even a managed database.

#### Optional Anki

Q: When is a managed relational database a good default?
A: When structured data, SQL, constraints and transactions are needed.

</details>

<details>
<summary><strong>CLOUD-DATA-003. What should you consider before choosing managed PostgreSQL, MySQL or a cloud-native relational database?</strong></summary>

#### Short answer

Consider compatibility, scaling model, consistency, failover behavior, extensions, cost, latency and operational tooling.

#### Interview answer

For Java services, I would check JDBC compatibility, transaction semantics, migration tooling, read/write scaling, backup and restore, failover time, replication lag, supported extensions, monitoring and cost model.

#### Deep dive

Cloud-native relational databases may offer horizontal scaling or global replication, but can differ from standard PostgreSQL/MySQL behavior.

#### Production angle

Small SQL differences or transaction behavior changes can break JPA assumptions, migrations or locking logic.

#### Traps / caveats

- Verify isolation, locking and generated SQL behavior.
- Check connection limits and pooling recommendations.
- Understand failover endpoint and DNS behavior.

#### Optional Anki

Q: What should be checked before choosing a managed relational database?
A: Compatibility, scaling, consistency, failover, extensions, cost and tooling.

</details>

<details>
<summary><strong>CLOUD-DATA-004. What are read replicas, failover replicas and multi-AZ database deployments?</strong></summary>

#### Short answer

Read replicas serve read traffic, failover replicas take over after primary failure, and multi-AZ deployments place database resources across zones for availability.

#### Interview answer

Read replicas can reduce read load but may be eventually consistent. Failover replicas are used for high availability. Multi-AZ means database components are spread across availability zones to survive a zone failure.

#### Deep dive

Some replicas can serve reads; others are only standby. Replication may be synchronous or asynchronous depending on service and configuration.

#### Production angle

Applications must understand read-after-write requirements, replica lag, failover time and connection reconnection behavior.

#### Traps / caveats

- Read replicas can return stale data.
- Failover may drop connections and in-flight transactions.
- Multi-AZ improves availability but does not replace backups.

#### Optional Anki

Q: What is a read replica used for?
A: Serving read traffic, usually with possible replication lag.

</details>

<a id="cloud-data-005"></a>

<details>
<summary><strong>CLOUD-DATA-005. How should Java connection pools be sized for managed databases and autoscaling services?</strong></summary>

#### Short answer

Size pools from database capacity and total replica count, not only from one application instance.

#### Interview answer

If each pod has a pool of 50 connections and autoscaling creates 40 pods, the database may see 2,000 connections. I would set small, measured pools, cap application concurrency, use pool metrics and consider a proxy or pooler if appropriate.

#### Deep dive

The right pool size depends on query latency, transaction duration, CPU cores, database connection limit and the number of service replicas.

#### Production angle

Connection storms during deploys or autoscaling can take down a managed database even when CPU looks fine.

#### Traps / caveats

- Bigger pools often make latency worse under overload.
- Idle connections still consume database resources.
- HikariCP settings should match timeouts and failover behavior.

#### Optional Anki

Q: Why can autoscaling break a database?
A: Each replica opens its own connection pool, multiplying total connections.

</details>

<details>
<summary><strong>🧠 CLOUD-DATA-006. When is object storage a better fit than a database or local filesystem?</strong></summary>

#### Short answer

Object storage fits large immutable or semi-immutable blobs, backups, exports, media and generated files.

#### Interview answer

For files, reports, images, logs, uploads and archives, object storage is usually better than storing blobs in a relational database or local disk. It is durable, scalable and accessible independently from app instances.

#### Deep dive

The database should usually store metadata, ownership, state and object keys, while the object content lives in storage.

#### Production angle

Pre-signed URLs can offload uploads and downloads, reducing application memory and bandwidth pressure.

#### Traps / caveats

- Object storage is not a POSIX filesystem.
- Handle partial uploads, lifecycle policies and access control.
- Do not expose private objects through predictable keys.

#### Optional Anki

Q: What belongs in object storage?
A: Large files, uploads, exports, media, backups and archives.

</details>

<a id="cloud-data-007"></a>

<details>
<summary><strong>🧠 CLOUD-DATA-007. What is the difference between object storage, block storage and file storage?</strong></summary>

#### Short answer

Object storage stores objects by key, block storage provides disk-like volumes, and file storage provides shared filesystem semantics.

#### Interview answer

Object storage is accessed through APIs and is great for blobs. Block storage attaches like a disk to compute and is common for VM volumes or database storage. File storage exposes directories and files to multiple clients.

#### Deep dive

The access pattern matters: random low-latency disk I/O, shared filesystem operations and blob retrieval are different workloads.

#### Production angle

Choosing the wrong storage type can create performance, durability or deployment issues.

#### Traps / caveats

- Object storage does not support normal file locking semantics.
- Block volumes are often zonal and attached to limited instances.
- Shared file storage can become a hidden bottleneck.

#### Optional Anki

Q: Object vs block storage?
A: Object stores blobs by key through APIs; block acts like a disk volume.

</details>

<details>
<summary><strong>🧠 CLOUD-DATA-008. How do storage classes, lifecycle policies and retention policies affect backend design?</strong></summary>

#### Short answer

They control cost, access latency, deletion behavior and compliance for stored data.

#### Interview answer

Frequently accessed files may need standard storage. Old exports, audit archives or backups may move to cheaper classes. Retention policies can prevent deletion for compliance, while lifecycle policies can expire temporary files automatically.

#### Deep dive

Applications should not assume every object is immediately cheap or fast to read forever. Restore time and access cost can change by class.

#### Production angle

Lifecycle mistakes can delete required data or keep sensitive data longer than allowed.

#### Traps / caveats

- Retention and legal hold can block deletion.
- Archive classes may have restore delays.
- Lifecycle rules should be tested in non-production.

#### Optional Anki

Q: What do lifecycle policies do?
A: Move, expire or manage stored data over time.

</details>

<a id="cloud-data-009"></a>

<details>
<summary><strong>CLOUD-DATA-009. What should you consider before using managed Redis or a managed cache?</strong></summary>

#### Short answer

Consider data correctness, eviction, memory limits, failover, latency, client behavior and cache invalidation.

#### Interview answer

Managed Redis can improve latency and reduce database load, but it is not automatically safe. I would define whether it is a cache or source of truth, choose TTLs, handle misses, monitor memory and design for failover.

#### Deep dive

Java clients need timeouts, connection pool settings and serialization choices. Cache keys and invalidation are part of correctness.

#### Production angle

A cache outage should not take down the system unless the business explicitly accepts that dependency.

#### Traps / caveats

- Cache stampedes can overload the database.
- Failover can drop connections and lose volatile data.
- Stale cached authorization or price data can become serious incidents.

#### Optional Anki

Q: What is the main cache correctness problem?
A: Keeping cached data fresh enough and safe under misses, invalidation and failure.

</details>

<a id="cloud-data-010"></a>

<details>
<summary><strong>CLOUD-DATA-010. What should you consider before using managed Kafka or a cloud event-streaming service?</strong></summary>

#### Short answer

Consider ordering, partitions, retention, throughput, schemas, retries, security, observability and consumer behavior.

#### Interview answer

Managed Kafka removes broker operations, but application design still matters. Producers need keys, idempotency and serialization. Consumers need offset handling, retry strategy, DLQ or parking-lot patterns and lag monitoring.

#### Deep dive

Provider-managed event services may not behave exactly like Kafka. Ordering, replay, retention and transaction support vary.

#### Production angle

Wrong partitioning or retry design can create hot partitions, duplicate processing or blocked consumer groups.

#### Traps / caveats

- Managed Kafka does not remove schema governance.
- Consumer lag is a user-impact signal for async workflows.
- Exactly-once business effects still require idempotent application logic.

#### Optional Anki

Q: What remains app-owned with managed Kafka?
A: Keys, schemas, idempotency, retries, offsets, consumer lag and business semantics.

</details>

<details>
<summary><strong>🧠 CLOUD-DATA-011. When might a managed NoSQL database be a better fit than a relational database?</strong></summary>

#### Short answer

NoSQL can fit high-scale key-value, document, wide-column or globally distributed access patterns with known queries.

#### Interview answer

A managed NoSQL database can be a better fit when access patterns are simple and predictable, data volume is high, horizontal scaling is central, or low-latency key-based access matters more than joins and complex transactions.

#### Deep dive

NoSQL design often starts from queries and partition keys, not normalized relational modeling.

#### Production angle

Poor key choice can create hot partitions and throttling even in a managed service.

#### Traps / caveats

- Do not choose NoSQL just because it sounds scalable.
- Query flexibility and transactions may be limited.
- Migration is hard if access patterns change.

#### Optional Anki

Q: What is a common NoSQL design driver?
A: Known high-scale access patterns and partition-key design.

</details>

<a id="cloud-data-012"></a>

<details>
<summary><strong>🧠 CLOUD-DATA-012. How do encryption at rest, backups and retention apply to managed data services?</strong></summary>

#### Short answer

They protect stored data, support recovery and enforce how long data is kept or deleted.

#### Interview answer

Managed services often provide encryption at rest, automated backups and retention controls. The team still chooses keys, access policies, backup windows, retention period, restore testing and compliance behavior.

#### Deep dive

Encryption is only one control. Key access, rotation, audit logs and separation of duties matter as much as the checkbox.

#### Production angle

Ransomware, accidental deletion and bad migrations are only recoverable if backups are recent, restorable and protected from deletion.

#### Traps / caveats

- Encryption does not prevent authorized misuse.
- Backups may copy sensitive data into other regions.
- Retention policies must align with legal deletion requirements.

#### Optional Anki

Q: What must be tested about backups?
A: Actual restore, not just backup creation.

</details>

<a id="cloud-data-013"></a>

<details>
<summary><strong>CLOUD-DATA-013. How can managed database failover affect Java connection pools, DNS and transactions?</strong></summary>

#### Short answer

Failover can drop connections, change endpoints, abort transactions and leave pools holding stale connections.

#### Interview answer

During failover, the database primary changes. Java applications may see connection errors, transaction rollbacks, stale DNS, broken sockets or read-only errors. The pool must detect broken connections and create new ones.

#### Deep dive

Good handling includes reasonable connection timeouts, validation, retry only at safe transaction boundaries and awareness of DNS caching.

#### Production angle

Failover tests should verify how Spring transactions, HikariCP settings and retry logic behave under real connection loss.

#### Traps / caveats

- Retrying inside a transaction can duplicate side effects.
- JVM DNS caching can delay endpoint switch.
- Long transactions increase failover pain.

#### Optional Anki

Q: What should happen after database failover?
A: The app should discard broken connections and retry only safe operations.

</details>

<a id="cloud-data-014"></a>

<details>
<summary><strong>🧠 CLOUD-DATA-014. How do multi-region database designs affect consistency, latency and failure handling?</strong></summary>

#### Short answer

Multi-region databases trade lower regional-failure risk and user latency against consistency complexity, replication lag and higher cost.

#### Interview answer

If writes happen in one region and reads happen elsewhere, replicas may lag. If writes happen in multiple regions, conflict resolution, ordering and transactions become harder. The right design depends on RPO, RTO, latency and business consistency needs.

#### Deep dive

Some systems choose active-passive for simplicity, others use active-active for global availability but accept more complex data semantics.

#### Production angle

Failover can create duplicate processing, stale reads or lost updates if the application is not designed for it.

#### Traps / caveats

- Strong consistency across regions usually costs latency.
- Active-active is not free high availability.
- Test regional failover and recovery of writes.

#### Optional Anki

Q: What is the main multi-region database trade-off?
A: Availability and latency versus consistency complexity and cost.

</details>

<details>
<summary><strong>CLOUD-DATA-015. How can data transfer and cross-zone traffic change the performance and cost of data-heavy services?</strong></summary>

#### Short answer

Moving data across zones, regions or the internet can add latency and significant network cost.

#### Interview answer

Data-heavy services should know where compute, databases, caches and storage are located. Cross-zone reads, cross-region replication, large API responses, analytics exports and object storage transfers can dominate cost and latency.

#### Deep dive

Good design keeps chatty components close, reduces unnecessary payloads and uses caching, compression or async transfer where appropriate.

#### Production angle

A service can look cheap in compute but expensive because it constantly moves data across boundaries.

#### Traps / caveats

- Cross-zone traffic may be charged even inside one region.
- Replication and backups also transfer data.
- Logs and traces can become a data-transfer and storage cost.

#### Optional Anki

Q: Why track data transfer cost?
A: Cross-zone, cross-region and internet traffic can dominate cost and latency.

</details>
