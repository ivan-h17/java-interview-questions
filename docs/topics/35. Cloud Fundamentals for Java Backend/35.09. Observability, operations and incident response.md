# Observability, operations and incident response

---

<a id="cloud-ops-001"></a>

<details>
<summary><strong>CLOUD-OPS-001. What observability is needed for cloud-hosted Java services?</strong></summary>

#### Short answer

Use logs, metrics, traces, health checks, audit events and business signals across the application and its cloud dependencies.

#### Interview answer

A cloud-hosted Java service needs structured logs, RED or USE metrics, distributed traces, dependency metrics, JVM metrics, deployment metadata and alerts tied to user impact. Cloud infrastructure metrics should be connected to application behavior.

#### Deep dive

Observability must include managed services: databases, queues, caches, load balancers, autoscaling and network errors.

#### Production angle

When latency or errors rise, you need to know whether the cause is code, JVM, database, network, provider service, deployment or configuration.

#### Traps / caveats

- Infrastructure green does not mean users are fine.
- Logs without correlation IDs are weak in distributed systems.
- Too many metrics can hide the few that matter.

#### Optional Anki

Q: What signals should cloud Java services expose?
A: Logs, metrics, traces, health, audit events and business signals.

</details>

<a id="cloud-ops-002"></a>

<details>
<summary><strong>CLOUD-OPS-002. How should logs, metrics and traces be connected in a cloud environment?</strong></summary>

#### Short answer

Correlate them with trace IDs, request IDs, service names, versions, regions and dependency names.

#### Interview answer

Logs explain events, metrics show trends and traces show request paths. They should share correlation fields so an engineer can move from an alert to a trace, then to logs and dependency metrics.

#### Deep dive

For Java services, include trace context in logs, propagate it through HTTP and messaging, and tag telemetry with deployment and environment metadata.

#### Production angle

Good correlation reduces time to diagnose incidents across load balancers, gateways, services, queues and databases.

#### Traps / caveats

- Do not log sensitive data just to improve debugging.
- High-cardinality labels can explode metrics cost.
- Async boundaries need explicit context propagation.

#### Optional Anki

Q: How do you connect logs and traces?
A: Include trace or correlation IDs in structured logs and propagate them across calls.

</details>

<a id="cloud-ops-003"></a>

<details>
<summary><strong>🧠 CLOUD-OPS-003. What cloud infrastructure metrics matter for a Java backend?</strong></summary>

#### Short answer

CPU, memory, throttling, restarts, network, load balancer, database, cache, queue, storage, quota and autoscaling metrics matter.

#### Interview answer

For Java, I would watch JVM heap and GC alongside container memory, CPU throttling, pod restarts, request latency, database connections, query latency, queue lag, cache hit rate, load balancer errors and cloud quota usage.

#### Deep dive

Infrastructure metrics are diagnostic inputs. User-facing SLIs still decide whether there is an incident.

#### Production angle

High 5xx may come from load balancer target health, exhausted database connections, OOM kills, throttled cloud APIs or slow downstream calls.

#### Traps / caveats

- CPU low does not mean the service is healthy if threads are blocked.
- Average latency hides p95/p99 problems.
- Queue depth without message age can mislead.

#### Optional Anki

Q: Which database metric is critical for Java services?
A: Connection usage and pool saturation, along with query latency.

</details>

<a id="cloud-ops-004"></a>

<details>
<summary><strong>CLOUD-OPS-004. How should correlation IDs and trace context be propagated across managed services?</strong></summary>

#### Short answer

Pass trace context through HTTP headers and message metadata, and record it in logs and telemetry.

#### Interview answer

For synchronous calls, propagate standard trace headers. For queues or events, include correlation or trace context in message attributes or payload metadata. Each service should continue the trace or at least log the parent correlation ID.

#### Deep dive

Some managed services do not preserve all headers or message attributes, so the application may need explicit mapping.

#### Production angle

Without context propagation, async workflows become hard to investigate because the initial request and later worker processing look unrelated.

#### Traps / caveats

- Do not trust client-provided correlation IDs for authorization.
- Avoid placing personal data in trace IDs or attributes.
- Sampling can hide rare failing traces if configured poorly.

#### Optional Anki

Q: Where should trace context go in async messaging?
A: Message attributes or payload metadata.

</details>

<a id="cloud-ops-005"></a>

<details>
<summary><strong>🧠 CLOUD-OPS-005. What audit logs should be enabled for cloud accounts and resources?</strong></summary>

#### Short answer

Enable control-plane activity, IAM changes, data-access events for sensitive resources, network/security changes and deployment actions.

#### Interview answer

Audit logs should show who changed infrastructure, IAM, secrets, network rules, databases, storage policies and deployment configuration. For sensitive data stores, data access logs may also be required.

#### Deep dive

Audit logs should be centralized, protected from modification and retained long enough for investigations and compliance.

#### Production angle

After a breach or incident, audit logs are often the only way to reconstruct what changed.

#### Traps / caveats

- Data-access logs can be noisy and expensive.
- Logs in the same compromised account may be deleted.
- Audit logging should be enabled before incidents, not after.

#### Optional Anki

Q: What should cloud audit logs capture?
A: Control-plane changes, IAM changes, sensitive data access and security-relevant resource changes.

</details>

<a id="cloud-ops-006"></a>

<details>
<summary><strong>🧠 CLOUD-OPS-006. How should alerts be designed for cloud-hosted services?</strong></summary>

#### Short answer

Alert on user impact, SLO burn and actionable saturation, not every noisy internal metric.

#### Interview answer

Good alerts tell the on-call engineer that users are affected or soon will be. Examples are high error budget burn, elevated 5xx rate, latency SLO breach, queue age above threshold, database pool exhaustion or failed deployments.

#### Deep dive

Cause-based alerts are useful for known urgent causes, but symptom-based alerts prevent missing unexpected failures.

#### Production angle

Alert fatigue causes real incidents to be ignored, so alerts need severity, owner, runbook and clear action.

#### Traps / caveats

- Do not alert on CPU alone unless action is clear.
- Low-traffic services need special alerting strategy.
- Every page should have a runbook or known owner.

#### Optional Anki

Q: What should production alerts focus on?
A: User impact, SLO burn and actionable saturation.

</details>

<a id="cloud-ops-007"></a>

<details>
<summary><strong>🧠 CLOUD-OPS-007. How do SLOs and error budgets help prioritize cloud reliability work?</strong></summary>

#### Short answer

They turn reliability into a measured target and show when to slow risky change or invest in fixes.

#### Interview answer

An error budget is the amount of unreliability allowed by the SLO. If the budget is healthy, teams can ship normally. If it is burning too fast, reliability work, rollback or release restrictions become justified.

#### Deep dive

Cloud reliability work can be endless. Error budgets help choose between more redundancy, better alerts, capacity work, dependency isolation or product delivery.

#### Production angle

Error budget burn alerts can detect incidents faster than raw CPU or memory alerts.

#### Traps / caveats

- Bad SLIs lead to bad priorities.
- Error budgets should reflect user journeys.
- Do not game SLOs to avoid reliability work.

#### Optional Anki

Q: What is an error budget?
A: The unreliability allowed while still meeting an SLO.

</details>

<a id="cloud-ops-008"></a>

<details>
<summary><strong>CLOUD-OPS-008. What should a cloud runbook contain?</strong></summary>

#### Short answer

It should contain symptoms, dashboards, owners, diagnostics, mitigation steps, rollback, escalation and verification.

#### Interview answer

A runbook should explain how to detect the issue, which dashboards and logs to inspect, what safe actions can be taken, how to roll back, how to contact owners or provider support and how to confirm recovery.

#### Deep dive

Runbooks should cover cloud-specific dependencies: database failover, queue backlog, certificate expiry, quota exhaustion, IAM changes and deployment failures.

#### Production angle

The best runbook is tested during drills and improved after incidents.

#### Traps / caveats

- A runbook that only says "check logs" is not enough.
- Dangerous commands need approvals and guardrails.
- Keep runbooks current with architecture changes.

#### Optional Anki

Q: What is the purpose of a runbook?
A: To give on-call engineers safe, tested steps for diagnosis and mitigation.

</details>

<a id="cloud-ops-009"></a>

<details>
<summary><strong>CLOUD-OPS-009. How would you investigate a latency spike in a cloud-hosted Java API?</strong></summary>

#### Short answer

Separate client, edge, application, JVM, dependency, database and infrastructure latency using metrics and traces.

#### Interview answer

I would check when it started, which endpoints and regions are affected, deployment/config changes, load balancer latency, app p95/p99, JVM GC, CPU throttling, thread pools, database queries, connection pools, cache and downstream calls.

#### Deep dive

Traces help identify whether latency is inside the service or waiting on a dependency. Metrics show whether saturation correlates with latency.

#### Production angle

Mitigation may include rollback, scaling, disabling a feature, reducing traffic, increasing timeouts carefully or shedding non-critical work.

#### Traps / caveats

- Averages hide tail latency.
- Scaling app instances can worsen database saturation.
- Retry storms can look like organic traffic growth.

#### Optional Anki

Q: What should you split when debugging latency?
A: Edge, app, JVM, dependency, database and infrastructure time.

</details>

<a id="cloud-ops-010"></a>

<details>
<summary><strong>CLOUD-OPS-010. How would you investigate an increase in 5xx responses after a cloud deployment?</strong></summary>

#### Short answer

Correlate errors with version, region, config, target health, logs, traces and dependency failures.

#### Interview answer

I would first identify whether all instances or only the new version fail. Then I would check deployment events, health checks, startup logs, config/secrets, database migrations, dependency errors, load balancer target status and recent infrastructure changes.

#### Deep dive

If the new version is bad, rollback may be safest. If mixed versions fail due to a database migration or config change, rollback may require a different plan.

#### Production angle

Canary deployments and deployment metadata make this investigation much faster.

#### Traps / caveats

- 5xx at the load balancer may mean no healthy targets, not application exceptions.
- Missing secrets often appear as startup or connection failures.
- Rollback can fail if schema changes are not backward compatible.

#### Optional Anki

Q: What is the first deployment question after 5xx increase?
A: Is it tied to a specific version, region, config or target group?

</details>

<a id="cloud-ops-011"></a>

<details>
<summary><strong>🧠 CLOUD-OPS-011. How should cloud provider incidents be communicated and handled?</strong></summary>

#### Short answer

Treat them as dependencies: assess user impact, verify with your telemetry, communicate status and execute prepared mitigations.

#### Interview answer

I would not rely only on the provider status page. I would check our SLOs, affected regions, error rates, dependency metrics and customer impact. Then communicate known impact, mitigations, next update time and recovery status.

#### Deep dive

Prepared mitigations may include regional failover, disabling optional features, queueing work, using fallback providers or rate limiting.

#### Production angle

Clear communication matters because customers care about service impact, not whether the root cause is provider-owned.

#### Traps / caveats

- Provider status pages can lag reality.
- Do not blame the provider before confirming your own config.
- Regional failover can create data consistency risk.

#### Optional Anki

Q: How should provider incidents be handled?
A: Measure your user impact, communicate clearly and run prepared mitigations.

</details>

<a id="cloud-ops-012"></a>

<details>
<summary><strong>🧠 CLOUD-OPS-012. How can distributed tracing include managed services that do not run your code?</strong></summary>

#### Short answer

Represent managed-service calls as spans from the client side and propagate context through supported metadata.

#### Interview answer

For databases, queues and storage APIs, the Java client or instrumentation can create spans for calls. For async services, trace context can be stored in message attributes so consumers continue the trace.

#### Deep dive

Some managed services add their own telemetry or service maps, but you may need to correlate by request ID, resource name, message ID or log fields.

#### Production angle

Even without code inside the managed service, traces can show that latency is spent in a database, queue publish, object storage call or downstream provider.

#### Traps / caveats

- Instrumentation can add overhead.
- Sampling may drop rare failures.
- Do not put secrets or personal data into span attributes.

#### Optional Anki

Q: How do traces include managed services?
A: Client-side spans and propagated context through headers or message metadata.

</details>
