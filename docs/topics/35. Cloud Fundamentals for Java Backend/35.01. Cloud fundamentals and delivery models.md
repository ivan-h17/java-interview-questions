# Cloud fundamentals and delivery models

<a id="cloud-fund-001"></a>

<details>
<summary><strong>🧠 CLOUD-FUND-001. What cloud concepts should a Java backend engineer understand?</strong></summary>

#### Short answer

A Java backend engineer should understand compute, networking, IAM, managed data services, reliability, observability, security, cost and deployment trade-offs.

#### Interview answer

For backend work, cloud knowledge is not only "where the server runs." I need to understand how services are deployed, how traffic reaches them, how identities and secrets are managed, how databases and queues fail, how autoscaling affects dependencies, and how logs, metrics and traces prove what is happening in production.

#### Deep dive

The useful mental model is a workload: application code, runtime, configuration, data stores, queues, network paths, IAM permissions, CI/CD, monitoring and recovery procedures. A senior engineer does not need to memorize every provider service, but should reason about the shared patterns and risks.

#### Production angle

Most cloud incidents are caused by interaction points: wrong IAM, bad network rules, missing timeouts, exhausted database connections, broken failover, hidden quota limits, or poor observability.

#### Traps / caveats

- Knowing service names is less important than understanding failure modes.
- Managed does not mean risk-free.
- Cloud cost and security are engineering concerns, not only platform-team concerns.

#### Optional Anki

Q: What cloud concepts matter most for Java backend engineers?
A: Compute, networking, IAM, managed data services, reliability, observability, security, cost and deployment trade-offs.

</details>

<details>
<summary><strong>CLOUD-FUND-002. What is cloud computing, and what problems does it solve for backend teams?</strong></summary>

#### Short answer

Cloud computing provides on-demand infrastructure and managed services without owning the physical data center.

#### Interview answer

Cloud lets teams provision compute, storage, networking, databases, queues and security services through APIs. For backend teams, it reduces lead time for infrastructure, improves elasticity, offers managed operational capabilities and makes automation easier.

#### Deep dive

The value is not only renting VMs. The major shift is programmable infrastructure: environments can be created, changed, versioned and observed through platform APIs. That enables autoscaling, repeatable deployments, managed backups, global routing and centralized security controls.

#### Production angle

Cloud helps teams move faster, but also exposes new failure modes: misconfiguration, quota limits, provider outages, unexpected cost and accidental public exposure.

#### Traps / caveats

- Cloud does not remove architecture work.
- Lift-and-shift without operational changes often keeps old problems and adds new cost.
- Provider defaults are not automatically production-safe.

#### Optional Anki

Q: What is cloud computing in backend terms?
A: On-demand infrastructure and managed services controlled through APIs instead of owned data-center hardware.

</details>

<details>
<summary><strong>🧠 CLOUD-FUND-003. What is the difference between public cloud, private cloud, hybrid cloud and multi-cloud?</strong></summary>

#### Short answer

Public cloud is provider-owned shared infrastructure, private cloud is dedicated to one organization, hybrid combines private and public environments, and multi-cloud uses more than one public provider.

#### Interview answer

Public cloud is the common model: AWS, Azure, Google Cloud and similar providers run the infrastructure. Private cloud is operated for one organization, often for regulatory or legacy reasons. Hybrid cloud connects on-premise or private environments with public cloud. Multi-cloud means using multiple public providers, usually for business, resilience, data residency or vendor-risk reasons.

#### Deep dive

The harder part is operational consistency. Identity, networking, observability, deployment pipelines, secrets, data replication and incident response become more complex when workloads span environments.

#### Production angle

Hybrid and multi-cloud can be justified, but they often add latency, security boundaries and team skill requirements.

#### Traps / caveats

- Multi-cloud is not automatic high availability.
- Avoid multi-cloud only because of vague lock-in fear.
- Data movement and identity integration are usually the hard parts.

#### Optional Anki

Q: What is multi-cloud?
A: Running workloads or services across more than one public cloud provider.

</details>

<a id="cloud-fund-004"></a>

<details>
<summary><strong>CLOUD-FUND-004. What are the main trade-offs of cloud compared with on-premise infrastructure?</strong></summary>

#### Short answer

Cloud improves elasticity, speed and managed operations, but adds provider dependency, cost visibility challenges and configuration risk.

#### Interview answer

Compared with on-premise, cloud gives faster provisioning, global services, managed databases, API-driven automation and pay-as-you-go capacity. The trade-offs are less direct control, provider-specific behavior, network and egress cost, quota limits, IAM complexity and the possibility of expensive overuse.

#### Deep dive

On-premise often has slower capacity changes but more stable unit economics for predictable workloads. Cloud is strong for variable demand and managed capabilities, but only if teams design for automation, observability and cost control.

#### Production angle

A system can become less reliable after cloud migration if it keeps local-state assumptions, manual operations and no cost guardrails.

#### Traps / caveats

- Cloud is not always cheaper.
- Provider-managed services still require capacity, security and backup decisions.
- On-premise habits like SSH fixes and manual changes create drift in cloud.

#### Optional Anki

Q: Name one cloud benefit and one cloud trade-off.
A: Benefit: elastic, API-driven managed infrastructure. Trade-off: provider dependency, configuration risk and cost surprises.

</details>

<details>
<summary><strong>🧠 CLOUD-FUND-005. What is the difference between scalability and elasticity?</strong></summary>

#### Short answer

Scalability is the ability to handle more load; elasticity is the ability to add and remove capacity automatically as load changes.

#### Interview answer

A scalable Java service can handle growth by adding instances, increasing resources, partitioning work or improving bottlenecks. An elastic service adjusts capacity dynamically, for example scaling pods or instances up during peak traffic and down later.

#### Deep dive

Scalability can be manual or architectural. Elasticity is operational behavior. A service can be scalable but not elastic if it needs manual provisioning, and elastic but still not scalable if the database, queue or external API becomes the real bottleneck.

#### Production angle

Autoscaling application instances without scaling or protecting downstream dependencies can increase failures and cost.

#### Traps / caveats

- Autoscaling is not instant.
- CPU is not always the right scaling metric for Java services.
- Elastic compute does not make a single primary database infinitely scalable.

#### Optional Anki

Q: Scalability vs elasticity?
A: Scalability handles more load; elasticity changes capacity automatically as load changes.

</details>

<a id="cloud-fund-006"></a>

<details>
<summary><strong>CLOUD-FUND-006. What is the difference between IaaS, PaaS, SaaS, FaaS and managed services?</strong></summary>

#### Short answer

They differ by how much of the stack the provider manages versus the customer manages.

#### Interview answer

IaaS gives infrastructure primitives like VMs, disks and networks. PaaS runs application platforms where the provider manages much of the runtime. SaaS is a complete application consumed by users. FaaS runs functions in response to events. Managed services are provider-operated databases, caches, queues or similar building blocks.

#### Deep dive

The more managed the service, the less low-level operational work the team owns, but the more it must accept platform constraints: quotas, configuration model, supported versions, network behavior and provider-specific APIs.

#### Production angle

Choosing the service model affects patching, scaling, backups, observability, portability and incident response.

#### Traps / caveats

- PaaS and managed service boundaries vary by provider.
- FaaS is not always simpler for long-running or latency-sensitive Java work.
- SaaS still leaves customer data, identity and configuration responsibilities.

#### Optional Anki

Q: What changes between IaaS and PaaS?
A: In PaaS the provider manages more of the OS/runtime platform; in IaaS the customer manages more of the stack.

</details>

<details>
<summary><strong>CLOUD-FUND-007. What are regions, availability zones and edge locations?</strong></summary>

#### Short answer

Regions are geographic cloud areas, availability zones are isolated data-center zones inside a region, and edge locations are closer-to-user sites for caching or traffic entry.

#### Interview answer

A region is a geographic deployment area. Availability zones are separated facilities within a region designed to reduce correlated failure. Edge locations are used by CDNs, DNS, WAFs or edge routing to reduce latency and absorb traffic before it reaches the origin.

#### Deep dive

Multi-AZ improves resilience inside one region. Multi-region handles regional failures or geographic latency, but introduces data consistency, routing, deployment and cost complexity.

#### Production angle

If all service replicas, database primaries and dependencies are in one zone, a zone failure can take down the workload.

#### Traps / caveats

- Multi-AZ is not the same as multi-region.
- Cross-zone and cross-region traffic can add latency and cost.
- Some managed services are regional while others are zonal or global.

#### Optional Anki

Q: What is an availability zone?
A: An isolated data-center zone inside a cloud region.

</details>

<a id="cloud-fund-008"></a>

<details>
<summary><strong>CLOUD-FUND-008. What does cloud-native mean for a backend application?</strong></summary>

#### Short answer

Cloud-native means the application is designed for automated deployment, elasticity, managed infrastructure and failure-aware operation.

#### Interview answer

A cloud-native Java service is usually stateless at the app layer, externally configured, observable, horizontally scalable and resilient to dependency failures. It treats infrastructure as dynamic and expects restarts, rescheduling, network failures and autoscaling.

#### Deep dive

Cloud-native does not require every service to be serverless or microservices. It means the service works well with platform primitives: health checks, immutable artifacts, externalized config, managed identity, logs/metrics/traces and automated rollouts.

#### Production angle

Cloud-native practices reduce manual recovery work and make deployments safer, but they require discipline around state, configuration and dependency contracts.

#### Traps / caveats

- "Runs in cloud" is not the same as cloud-native.
- Cloud-native is not a license to over-split services.
- Stateful workloads can be cloud-native, but need explicit data and recovery design.

#### Optional Anki

Q: What is a cloud-native backend?
A: A backend designed for automated, elastic, observable and failure-aware cloud operation.

</details>

<details>
<summary><strong>CLOUD-FUND-009. Why are stateless services easier to run in cloud environments?</strong></summary>

#### Short answer

Stateless services can be replaced, scaled and load-balanced without preserving local instance state.

#### Interview answer

If a Java service stores session state, files or workflow progress only in local memory or disk, scaling and failover become harder. Stateless services keep durable state in databases, caches, queues or object storage, so any healthy instance can handle the next request.

#### Deep dive

Stateless does not mean no state exists. It means state is externalized to systems designed for durability, sharing and recovery.

#### Production angle

Stateless services make rolling deployments, autoscaling, blue-green releases and zone failover much safer.

#### Traps / caveats

- Local caches are acceptable only when they are disposable and rebuildable.
- Sticky sessions reduce flexibility and can hide scaling problems.
- Externalizing state moves consistency and latency questions elsewhere.

#### Optional Anki

Q: Why are stateless services cloud-friendly?
A: Any replica can serve traffic, so scaling, replacement and failover are simpler.

</details>

<details>
<summary><strong>CLOUD-FUND-010. What operational burden do managed services remove, and what new risks do they introduce?</strong></summary>

#### Short answer

Managed services remove much of the patching, provisioning and routine operations, but introduce quotas, provider-specific behavior and configuration dependency.

#### Interview answer

A managed database or queue can handle backups, patching, replication, failover and monitoring integrations. The team still owns data model, capacity choices, access control, client behavior, backup validation and failure handling.

#### Deep dive

Managed services shift responsibility rather than eliminate it. The provider manages the service infrastructure; the application team manages correct use of the service.

#### Production angle

Incidents often come from wrong parameters, exhausted limits, untested failover, missing alerts or client-side retry storms.

#### Traps / caveats

- Managed does not mean unlimited.
- Read the SLA, quotas and maintenance behavior.
- Provider support does not replace application-level recovery design.

#### Optional Anki

Q: What remains your responsibility with managed services?
A: Correct configuration, access control, capacity, client behavior, backup validation and failure handling.

</details>

<a id="cloud-fund-011"></a>

<details>
<summary><strong>CLOUD-FUND-011. What is vendor lock-in, and when is it an acceptable trade-off?</strong></summary>

#### Short answer

Vendor lock-in is dependency on provider-specific services or APIs; it is acceptable when the value outweighs portability cost.

#### Interview answer

Lock-in happens when an application relies on a provider-specific database, queue, IAM model, deployment platform or API. It is not automatically bad. If the service reduces operational burden, improves reliability or speeds delivery, lock-in may be worth it.

#### Deep dive

The practical question is reversibility. Some decisions can be abstracted or migrated later; others shape data models and workflows deeply. A senior answer names the exit cost and the business reason for accepting it.

#### Production angle

Blind portability can lead to lowest-common-denominator architecture, while blind lock-in can make future migration expensive.

#### Traps / caveats

- Do not build weak abstractions that hide important provider behavior.
- Data gravity is often a stronger lock-in than API syntax.
- Lock-in decisions should be documented.

#### Optional Anki

Q: When is vendor lock-in acceptable?
A: When provider-specific value clearly outweighs migration and portability cost.

</details>

<details>
<summary><strong>CLOUD-FUND-012. What is the difference between a cloud control plane and a data plane?</strong></summary>

#### Short answer

The control plane manages resources and configuration; the data plane handles application traffic or data operations.

#### Interview answer

The control plane is used to create, update and configure cloud resources, such as deploying a database or changing a load balancer. The data plane is the actual runtime path, such as API requests through the load balancer or database queries from the application.

#### Deep dive

This distinction matters because control-plane outages and data-plane outages have different impact. A provider might be unable to create new resources while existing traffic still works, or the data path might fail while the management API remains available.

#### Production angle

Incident response should distinguish "cannot deploy or scale" from "users cannot use the service." Both matter, but they require different actions.

#### Traps / caveats

- Autoscaling may depend on both planes: existing instances serve traffic, but adding capacity needs control-plane operations.
- Do not assume the cloud console being down means your workload is down.
- Control-plane rate limits can break automation.

#### Optional Anki

Q: Control plane vs data plane?
A: Control plane manages resources; data plane serves runtime traffic or data operations.

</details>
