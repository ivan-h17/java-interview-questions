# Scaling, resilience and disaster recovery

---

<a id="cloud-rel-001"></a>

<details>
<summary><strong>CLOUD-REL-001. How do autoscaling and load balancing interact?</strong></summary>

#### Short answer

Autoscaling changes the number of service instances; load balancing routes traffic across healthy instances.

#### Interview answer

When load grows, autoscaling can add replicas or instances. The load balancer must discover them, health-check them and start routing traffic only when they are ready. During scale-down, it should stop routing and allow in-flight requests to drain.

#### Deep dive

Autoscaling has delay: metrics must change, new instances must start, Java must warm up and health checks must pass.

#### Production angle

If startup is slow or readiness is wrong, autoscaling can add capacity too late or send traffic to unready services.

#### Traps / caveats

- Autoscaling application instances can overload databases.
- Health checks should reflect readiness to serve traffic.
- Scale-down needs graceful shutdown.

#### Optional Anki

Q: Autoscaling vs load balancing?
A: Autoscaling changes capacity; load balancing distributes traffic to healthy capacity.

</details>

<a id="cloud-rel-002"></a>

<details>
<summary><strong>🧠 CLOUD-REL-002. What is the difference between horizontal and vertical scaling?</strong></summary>

#### Short answer

Horizontal scaling adds more instances; vertical scaling gives an instance more CPU, memory or I/O.

#### Interview answer

Horizontal scaling is common for stateless Java services because adding replicas improves capacity and availability. Vertical scaling can help databases, legacy apps or workloads that cannot easily split work.

#### Deep dive

Horizontal scaling requires statelessness, shared data stores and load balancing. Vertical scaling has upper limits and may require restarts.

#### Production angle

The right answer often combines both: right-size each instance, then scale out safely.

#### Traps / caveats

- Horizontal scaling does not fix a single database bottleneck.
- Vertical scaling can hide inefficient code temporarily.
- More instances mean more connections and background work.

#### Optional Anki

Q: Horizontal vs vertical scaling?
A: Horizontal adds instances; vertical increases resources per instance.

</details>

<a id="cloud-rel-003"></a>

<details>
<summary><strong>CLOUD-REL-003. What application properties make a Java service easy to scale horizontally?</strong></summary>

#### Short answer

Statelessness, fast startup, bounded resource use, externalized state, idempotency and good health checks.

#### Interview answer

A horizontally scalable Java service should not keep critical session or workflow state in memory. It should start predictably, expose readiness, handle duplicate requests, limit connection pools and tolerate instance replacement.

#### Deep dive

Scale-out also requires dependency protection: database pools, HTTP clients, thread pools and queues must not expand without limits.

#### Production angle

Without bounded concurrency, scaling out can amplify load on downstream systems and make incidents worse.

#### Traps / caveats

- Local caches must be disposable.
- Scheduled jobs must not run once per replica unless intended.
- Warmup and JIT behavior can affect new-instance latency.

#### Optional Anki

Q: What makes a Java service horizontally scalable?
A: Statelessness, externalized state, bounded resources, readiness and idempotency.

</details>

<a id="cloud-rel-004"></a>

<details>
<summary><strong>CLOUD-REL-004. How do health checks, readiness checks and load balancer target health affect availability?</strong></summary>

#### Short answer

They decide whether instances receive traffic, so bad checks can either route to broken instances or remove healthy ones.

#### Interview answer

Liveness checks answer whether the process should be restarted. Readiness checks answer whether the instance can serve traffic. Load balancer target health decides where user requests go.

#### Deep dive

Readiness should include critical local initialization but not every optional dependency. If readiness fails because one optional downstream is down, the whole fleet may be removed from service.

#### Production angle

Bad probes cause cascading outages during slow startups, database maintenance or partial dependency failures.

#### Traps / caveats

- Liveness checks should not be expensive.
- Readiness should fail during graceful shutdown.
- Health endpoints must not expose sensitive details.

#### Optional Anki

Q: Readiness vs liveness?
A: Readiness controls traffic; liveness controls restart.

</details>

<a id="cloud-rel-005"></a>

<details>
<summary><strong>CLOUD-REL-005. Why does graceful shutdown matter during autoscaling and deployments?</strong></summary>

#### Short answer

It lets an instance stop receiving new work and finish or safely abort in-flight work before termination.

#### Interview answer

During rolling deployments or scale-down, the platform may terminate instances. A Java service should fail readiness, drain HTTP requests, stop consuming messages, close resources and respect termination deadlines.

#### Deep dive

For message consumers, graceful shutdown often means stop polling, finish current messages or release leases so another worker can retry.

#### Production angle

Without graceful shutdown, deployments cause 5xx spikes, duplicate message processing or partial transactions.

#### Traps / caveats

- Shutdown timeout must be longer than normal request or task completion.
- Long-running jobs need checkpoints.
- Load balancers may continue routing briefly after deregistration starts.

#### Optional Anki

Q: What should happen during graceful shutdown?
A: Stop new work, drain or checkpoint current work and close resources safely.

</details>

<a id="cloud-rel-006"></a>

<details>
<summary><strong>CLOUD-REL-006. How should Java services handle cloud service outages?</strong></summary>

#### Short answer

Use timeouts, bounded retries, fallback or degradation, circuit breakers, queues and clear user-facing failure behavior.

#### Interview answer

The service should assume cloud dependencies can fail or throttle. It should avoid indefinite waits, retry only safe operations, isolate failures with bulkheads and degrade when possible.

#### Deep dive

Handling depends on dependency criticality. A payment provider outage is different from analytics storage being unavailable.

#### Production angle

If every request waits on a failing managed service, thread pools fill, latency rises and the outage spreads to the caller.

#### Traps / caveats

- Retrying all errors can create a storm.
- Fallbacks must be correct, not just convenient.
- User-visible errors should be honest and actionable.

#### Optional Anki

Q: What protects Java services during dependency outages?
A: Timeouts, bounded retries, circuit breakers, bulkheads and graceful degradation.

</details>

<a id="cloud-rel-007"></a>

<details>
<summary><strong>CLOUD-REL-007. How should timeouts, retries, circuit breakers and bulkheads be used with cloud dependencies?</strong></summary>

#### Short answer

Use timeouts for every call, retries for transient safe failures, circuit breakers for persistent failures and bulkheads to isolate resources.

#### Interview answer

A Java service should set connection, request and total deadlines for cloud APIs. Retries need exponential backoff and jitter. Circuit breakers stop repeated calls to unhealthy dependencies. Bulkheads isolate thread pools, connection pools or concurrency limits per dependency.

#### Deep dive

All of these controls must fit the caller's latency budget. A retry that succeeds after the user timeout is still a failure.

#### Production angle

Good resilience settings prevent one slow cloud dependency from exhausting the whole service.

#### Traps / caveats

- Do not retry non-idempotent operations blindly.
- Circuit breakers need metrics and tuning.
- Bulkheads can reject work; callers must handle it.

#### Optional Anki

Q: What should every cloud dependency call have?
A: A timeout or deadline.

</details>

<a id="cloud-rel-008"></a>

<details>
<summary><strong>CLOUD-REL-008. What is graceful degradation in a cloud-hosted backend?</strong></summary>

#### Short answer

Graceful degradation means keeping critical functionality working while reducing or disabling non-critical features during failure.

#### Interview answer

If recommendations, analytics or email are down, checkout might still work. The service may return partial data, use cached values, queue work for later or disable optional features with a kill switch.

#### Deep dive

Degradation must be designed in the domain. Returning stale inventory or accepting payment without recording state may be unacceptable.

#### Production angle

Graceful degradation can turn a full outage into a partial impairment.

#### Traps / caveats

- Fallback data can be stale or unsafe.
- Degraded success should still be observable.
- Some features should fail closed for security or money movement.

#### Optional Anki

Q: What is graceful degradation?
A: Preserving critical behavior while reducing non-critical functionality during failure.

</details>

<a id="cloud-rel-009"></a>

<details>
<summary><strong>CLOUD-REL-009. How do multi-AZ deployments improve availability?</strong></summary>

#### Short answer

They place resources across isolated zones so one zone failure does not take down the whole workload.

#### Interview answer

A multi-AZ Java service runs replicas in more than one availability zone, with load balancing and dependencies designed to survive a zone failure. Databases, caches, queues and NAT paths also need zone-aware design.

#### Deep dive

Multi-AZ is usually the default level of resilience for important regional services.

#### Production angle

If the app is multi-AZ but the database, NAT or cache is single-zone, the service may still fail.

#### Traps / caveats

- Cross-zone traffic can add cost.
- Some failures are regional, not zonal.
- Test zone evacuation or dependency loss.

#### Optional Anki

Q: What does multi-AZ protect against?
A: Failure of one availability zone, if dependencies are also designed for it.

</details>

<a id="cloud-rel-010"></a>

<details>
<summary><strong>🧠 CLOUD-REL-010. What are backup, restore and disaster recovery basics?</strong></summary>

#### Short answer

Backups create recoverable copies, restore proves they work, and DR defines how the system recovers from major failure.

#### Interview answer

A backend system needs backups for databases, object storage, configuration, secrets and sometimes infrastructure definitions. DR defines recovery targets, runbooks, ownership and dependencies for serious outages.

#### Deep dive

Backup strategy should specify frequency, retention, encryption, location, access control and restore testing.

#### Production angle

Untested backups often fail during the only moment they matter.

#### Traps / caveats

- A backup in the same compromised account may be deletable by an attacker.
- Restore time may exceed RTO.
- Backups can contain sensitive data and need protection.

#### Optional Anki

Q: What proves a backup is useful?
A: A successful restore test.

</details>

<a id="cloud-rel-011"></a>

<details>
<summary><strong>CLOUD-REL-011. How do you test backups and failover instead of assuming they work?</strong></summary>

#### Short answer

Run scheduled restore and failover drills with clear success criteria and measured recovery times.

#### Interview answer

I would restore backups into an isolated environment, verify data integrity, run application checks and measure restore duration. For failover, I would test database failover, service routing, DNS behavior, connection pool recovery and operational communication.

#### Deep dive

Tests should be automated where possible and include both technical recovery and business validation.

#### Production angle

The result should update RTO/RPO estimates, runbooks and monitoring.

#### Traps / caveats

- Do not test only metadata like "backup completed."
- Test permissions needed during emergency restore.
- Include application compatibility with restored data.

#### Optional Anki

Q: What should a restore test verify?
A: Data integrity, application usability and recovery time.

</details>

<details>
<summary><strong>🧠 CLOUD-REL-012. How do active-active and active-passive multi-region designs differ?</strong></summary>

#### Short answer

Active-active serves traffic from multiple regions at once; active-passive keeps a standby region for failover.

#### Interview answer

Active-passive is simpler because one region is primary and another is standby. Active-active can improve latency and availability, but requires multi-region data consistency, conflict handling, global routing and strong operational maturity.

#### Deep dive

There are variants such as warm standby, pilot light and read-only secondary regions.

#### Production angle

Active-active is rarely justified without clear latency, availability or regulatory requirements.

#### Traps / caveats

- Active-active can create split-brain writes.
- Passive regions can drift if not exercised.
- Failback is often harder than failover.

#### Optional Anki

Q: Active-active vs active-passive?
A: Active-active serves traffic in multiple regions; active-passive fails over to a standby.

</details>

<a id="cloud-rel-013"></a>

<details>
<summary><strong>🧠 CLOUD-REL-013. How do multi-region designs change consistency and cost?</strong></summary>

#### Short answer

They increase infrastructure, data-transfer and operational cost while making consistency and conflict handling harder.

#### Interview answer

Multi-region adds duplicate compute, databases, caches, queues, observability and deployment pipelines. Data replication across regions costs money and introduces latency. If both regions can write, conflict resolution becomes a business problem.

#### Deep dive

The design should start from user geography, RTO, RPO, data residency and acceptable stale reads.

#### Production angle

Multi-region systems need drills for regional failure, partial recovery and failback.

#### Traps / caveats

- Multi-region does not automatically mean no downtime.
- Cross-region consistency can slow writes.
- Observability must work during regional partition.

#### Optional Anki

Q: What does multi-region add besides availability?
A: Cost, latency, replication, consistency and operational complexity.

</details>

<details>
<summary><strong>CLOUD-REL-014. What split-brain or duplicate-processing risks appear during failover?</strong></summary>

#### Short answer

Both old and new regions or workers may believe they are active, causing duplicate writes, double processing or conflicting state.

#### Interview answer

During failover, traffic routing, leader election, database promotion and consumer groups can become inconsistent. If two primaries accept writes or two workers process the same work, the system may create conflicts or duplicate side effects.

#### Deep dive

Protection includes fencing tokens, single-writer rules, idempotency, leases, careful promotion procedures and clear failback plans.

#### Production angle

Payment, inventory and notification systems are especially sensitive to duplicate processing.

#### Traps / caveats

- Manual failover can leave old writers running.
- DNS propagation delay can send traffic to both regions.
- Idempotency must cover external side effects too.

#### Optional Anki

Q: What is split-brain in failover?
A: Two sides act as active owners at the same time.

</details>
