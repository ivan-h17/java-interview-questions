# Migration, infrastructure as code and production scenarios

<a id="cloud-mig-001"></a>

<details>
<summary><strong>CLOUD-MIG-001. What should be reviewed before moving a service to managed cloud infrastructure?</strong></summary>

#### Short answer

Review architecture, state, dependencies, security, configuration, data, networking, observability, cost and recovery.

#### Interview answer

Before migration, I would inspect runtime requirements, database dependencies, local disk use, sessions, scheduled jobs, secrets, IAM, network paths, third-party calls, deployment process, monitoring, backups, compliance and rollback options.

#### Deep dive

The goal is to find assumptions that were safe on-premise but unsafe in cloud: static hosts, local files, manual credentials, fixed IPs or hidden batch jobs.

#### Production angle

A migration without readiness review often fails through networking, data transfer, authentication or missing observability.

#### Traps / caveats

- Do not move stateful services without data migration and recovery planning.
- Check latency to remaining on-premise dependencies.
- Define success metrics before migration.

#### Optional Anki

Q: What should cloud migration review cover?
A: State, dependencies, security, network, config, observability, cost and recovery.

</details>

<details>
<summary><strong>CLOUD-MIG-002. What is infrastructure as code, and why is it important in cloud systems?</strong></summary>

#### Short answer

Infrastructure as code manages cloud resources through versioned, reviewable definitions instead of manual changes.

#### Interview answer

IaC lets teams define networks, databases, IAM, queues, alarms and deployment resources in code. It improves repeatability, review, rollback, drift detection and environment consistency.

#### Deep dive

IaC should be integrated with CI/CD, policy checks and change approval for risky resources.

#### Production angle

Manual console changes create drift and make incident recovery hard to reproduce.

#### Traps / caveats

- IaC can still deploy dangerous changes quickly.
- State files or deployment credentials must be protected.
- Some changes are destructive and need explicit review.

#### Optional Anki

Q: Why use IaC?
A: To make infrastructure versioned, repeatable, reviewable and auditable.

</details>

<details>
<summary><strong>🧠 CLOUD-MIG-003. How do Terraform, CloudFormation, CDK or similar tools fit into backend delivery?</strong></summary>

#### Short answer

They provision and update cloud resources that the backend depends on, often through the same delivery governance as application code.

#### Interview answer

Backend services need infrastructure: databases, queues, IAM roles, DNS, alarms and secrets. IaC tools define those resources and can be reviewed, tested and deployed through pipelines.

#### Deep dive

Some teams separate application and infrastructure pipelines; others coordinate them. Either way, compatibility between code and infrastructure changes must be managed.

#### Production angle

A new application version may require a new queue, permission or database setting before deployment.

#### Traps / caveats

- Do not hide large infrastructure changes inside routine app releases.
- IaC plans need human-readable review.
- Rollback is not always automatic for infrastructure.

#### Optional Anki

Q: What does IaC provide to backend delivery?
A: Versioned provisioning and updates for cloud resources the service needs.

</details>

<a id="cloud-mig-004"></a>

<details>
<summary><strong>CLOUD-MIG-004. What is infrastructure drift, and how can it create incidents?</strong></summary>

#### Short answer

Drift is when live infrastructure differs from its declared configuration.

#### Interview answer

Drift happens when someone changes resources manually, automation fails halfway, or provider defaults change. It can cause production to behave differently from staging or make the next IaC deployment unexpectedly destructive.

#### Deep dive

Examples include manually opened firewall rules, changed database parameters, missing alarms or IAM policies that no longer match code.

#### Production angle

Drift makes incidents harder because engineers debug what they think exists, not what actually exists.

#### Traps / caveats

- Emergency fixes should be reconciled back into IaC.
- Drift detection must include security-sensitive resources.
- Importing existing resources into IaC needs care.

#### Optional Anki

Q: What is infrastructure drift?
A: Live infrastructure differs from the declared IaC or expected configuration.

</details>

<details>
<summary><strong>CLOUD-MIG-005. How should cloud environments, accounts, projects or subscriptions be separated?</strong></summary>

#### Short answer

Separate them by environment, ownership, sensitivity and blast-radius requirements.

#### Interview answer

Production should be isolated from development and staging. Sensitive workloads may need separate accounts or projects. Shared services should have clear access boundaries. Billing, audit logs and IAM should reflect ownership.

#### Deep dive

Separation supports least privilege, cost attribution, policy enforcement and safer experimentation.

#### Production angle

A developer experiment should not be able to delete production storage or exhaust production quota.

#### Traps / caveats

- Too many accounts can increase operational overhead.
- Shared networking must be carefully governed.
- Cross-environment credentials are a common risk.

#### Optional Anki

Q: Why separate cloud accounts or projects?
A: To limit blast radius, enforce access boundaries and attribute cost.

</details>

<a id="cloud-mig-006"></a>

<details>
<summary><strong>CLOUD-MIG-006. How would you migrate a stateful Java application from on-premise to the cloud?</strong></summary>

#### Short answer

Analyze state and dependencies, choose a migration strategy, replicate data, test cutover and keep rollback or recovery options.

#### Interview answer

I would identify databases, files, sessions, scheduled jobs, integrations and latency-sensitive dependencies. Then I would decide between lift-and-shift, replatforming or gradual migration. Data migration needs replication, validation, cutover planning and consistency checks.

#### Deep dive

For Java apps, also review configuration, secrets, connection pools, file paths, timeouts, DNS, logging and deployment model.

#### Production angle

The hardest part is usually data and dependency cutover, not starting the application in cloud.

#### Traps / caveats

- Do not ignore on-premise services still on the critical path.
- Test rollback before cutover.
- Freeze windows or dual-write periods need clear rules.

#### Optional Anki

Q: What is hardest in stateful cloud migration?
A: Data migration, consistency and dependency cutover.

</details>

<a id="cloud-mig-007"></a>

<details>
<summary><strong>🧠 CLOUD-MIG-007. What is the strangler pattern in a cloud migration?</strong></summary>

#### Short answer

It gradually replaces parts of a legacy system by routing selected functionality to new services.

#### Interview answer

Instead of rewriting everything, the team places a routing layer around the legacy system and moves features one by one to cloud-hosted services. Over time, the new system grows and the old system shrinks.

#### Deep dive

The pattern needs clear boundaries, routing rules, data synchronization and observability across old and new paths.

#### Production angle

It reduces big-bang migration risk but can create temporary complexity while both systems run.

#### Traps / caveats

- Shared databases can undermine service boundaries.
- Routing mistakes can send users to inconsistent behavior.
- Long transition periods need ownership and cleanup.

#### Optional Anki

Q: What does the strangler pattern reduce?
A: Big-bang migration risk by replacing functionality incrementally.

</details>

<details>
<summary><strong>🧠 CLOUD-MIG-008. How should configuration, feature flags and secrets be handled across cloud environments?</strong></summary>

#### Short answer

Keep them externalized, environment-scoped, validated, audited and separated from code artifacts.

#### Interview answer

Each environment should provide its own non-sensitive config and secrets through controlled systems. Feature flags should have owners, defaults and rollout rules. Secrets should come from managed stores or workload identity, not copied files.

#### Deep dive

Configuration should be compatible with rolling deployments, and risky changes should have validation and rollback.

#### Production angle

Many migration incidents come from wrong endpoints, missing secrets, stale flags or environment drift.

#### Traps / caveats

- Do not reuse production secrets in staging.
- Feature flags are not authorization.
- Runtime configuration changes need audit and observability.

#### Optional Anki

Q: How should cloud config and secrets be managed?
A: Externalized, environment-scoped, validated, audited and separated from artifacts.

</details>

<a id="cloud-mig-009"></a>

<details>
<summary><strong>CLOUD-MIG-009. How should CI/CD pipelines deploy both application code and infrastructure changes?</strong></summary>

#### Short answer

Coordinate infrastructure and application changes with review, ordering, compatibility checks and rollback plans.

#### Interview answer

Pipelines should build immutable artifacts, run tests, review IaC plans, apply safe infrastructure changes, deploy gradually and verify health. Changes that affect databases, queues, IAM or networking must be ordered carefully relative to application versions.

#### Deep dive

Backward-compatible infrastructure changes should usually go first, then app deployment, then cleanup after old versions are gone.

#### Production angle

Deployment should expose version, config, infrastructure and migration state so incidents can be traced.

#### Traps / caveats

- Rollback of code may not roll back infrastructure or data.
- IAM changes can break runtime after deploy.
- Destructive IaC changes need explicit gates.

#### Optional Anki

Q: What must be coordinated in cloud CI/CD?
A: Application code, infrastructure, data changes, IAM, config and rollback.

</details>

<details>
<summary><strong>CLOUD-MIG-010. How do cloud service quotas and rate limits affect production readiness?</strong></summary>

#### Short answer

They cap resource creation, API calls, throughput or concurrency and can block scaling or normal operation.

#### Interview answer

Cloud services have quotas for instances, IPs, load balancers, storage, messages, API calls, database connections and more. Production readiness means checking expected peak usage and requesting increases before launch.

#### Deep dive

Rate limits also apply to control-plane APIs. A deployment or autoscaler can fail even if the application itself is healthy.

#### Production angle

Quota exhaustion often appears during traffic spikes, regional failover, batch jobs or incident recovery.

#### Traps / caveats

- Quota increases can take time.
- Retries can worsen throttling.
- Separate environments and regions may have separate quotas.

#### Optional Anki

Q: Why check quotas before launch?
A: Quotas can block scaling, deployment or runtime throughput under real load.

</details>

<details>
<summary><strong>🧠 CLOUD-MIG-011. When is a multi-cloud or hybrid-cloud design justified, and when is it accidental complexity?</strong></summary>

#### Short answer

It is justified by clear business, regulatory, latency or resilience needs; otherwise it often adds avoidable complexity.

#### Interview answer

Hybrid cloud may be needed during migration, for data residency or because some systems remain on-premise. Multi-cloud may be justified by provider risk, customer requirements or specialized services. It is accidental complexity when used without clear requirements and operating model.

#### Deep dive

The design must handle identity, networking, data movement, observability, deployment and incident ownership across environments.

#### Production angle

Multi-cloud can reduce one risk while increasing many operational risks.

#### Traps / caveats

- Do not assume multi-cloud automatically improves uptime.
- Data gravity and egress cost can dominate.
- Teams need skills and tooling for every platform used.

#### Optional Anki

Q: When is multi-cloud justified?
A: When clear business, regulatory, latency or resilience requirements outweigh added complexity.

</details>

<details>
<summary><strong>CLOUD-MIG-012. How would you run a game day to validate cloud failure scenarios?</strong></summary>

#### Short answer

Choose a realistic failure, define success criteria, execute safely, observe behavior and turn findings into fixes.

#### Interview answer

I would pick scenarios like database failover, queue backlog, region dependency outage, expired certificate, quota exhaustion or bad deployment. I would notify stakeholders, limit blast radius, monitor SLOs, run the scenario and document gaps.

#### Deep dive

Game days should test people, tooling and runbooks, not only technical redundancy.

#### Production angle

They reveal hidden assumptions before real incidents do.

#### Traps / caveats

- Do not run destructive tests without rollback and approval.
- Start in staging, then progress carefully.
- Follow up on findings or the exercise has little value.

#### Optional Anki

Q: What is the goal of a game day?
A: Validate failure behavior, runbooks and team response under controlled conditions.

</details>

<a id="cloud-mig-013"></a>

<details>
<summary><strong>🧠 CLOUD-MIG-013. What should be in a cloud readiness checklist for a Java service?</strong></summary>

#### Short answer

Include runtime sizing, config, secrets, IAM, network, health checks, observability, resilience, data, deployment, cost and recovery.

#### Interview answer

For a Java service, I would check container or runtime settings, JVM memory, connection pools, graceful shutdown, externalized config, workload identity, secrets, database failover, timeouts, logs, metrics, traces, alerts, CI/CD, IaC, quotas and rollback.

#### Deep dive

The checklist should be specific enough to catch production risks but not so bureaucratic that teams bypass it.

#### Production angle

A readiness checklist prevents repeated migration mistakes across services.

#### Traps / caveats

- Checklists must evolve after incidents.
- They should include owners and evidence.
- Passing a checklist is not a substitute for load and failover tests.

#### Optional Anki

Q: Name Java-specific cloud readiness checks.
A: JVM sizing, connection pools, graceful shutdown, timeouts, health checks and telemetry.

</details>

<details>
<summary><strong>CLOUD-MIG-014. How do rollback and roll-forward differ when application, infrastructure and data changes are deployed together?</strong></summary>

#### Short answer

Rollback restores the previous state; roll-forward fixes by applying a new compatible change, which is often safer for data and infrastructure changes.

#### Interview answer

Code rollback is usually simple if the artifact is immutable. Infrastructure and database changes may be hard or unsafe to undo. For schema changes, IAM changes or resource replacement, a roll-forward fix may be safer than trying to reverse everything.

#### Deep dive

Safe deployment uses expand-contract migrations, backward-compatible infrastructure changes and feature flags to reduce rollback risk.

#### Production angle

Incident plans should state which changes are reversible, which are not and what validation is required.

#### Traps / caveats

- Dropped columns or deleted resources may not be rollback-safe.
- IaC rollback can destroy newly created state.
- Always separate deploy from cleanup when possible.

#### Optional Anki

Q: Why is roll-forward often safer for data changes?
A: Some data and infrastructure changes are not safely reversible.

</details>
