# Compute, deployment and runtime choices

---

<a id="cloud-comp-001"></a>

<details>
<summary><strong>CLOUD-COMP-001. What compute options can host a Java backend service in the cloud?</strong></summary>

#### Short answer

Common options are virtual machines, containers, managed container platforms, PaaS runtimes and serverless functions or containers.

#### Interview answer

A Spring Boot service can run on VMs, Kubernetes, managed container services, app platforms, serverless functions or serverless containers. The right choice depends on operational control, deployment speed, scaling behavior, cold starts, networking needs, team skills and cost model.

#### Deep dive

VMs give control but more operations. Containers standardize packaging. Managed platforms reduce infrastructure work. Serverless can reduce idle cost and operations but adds constraints.

#### Production angle

The compute choice affects JVM sizing, startup time, deployment strategy, logs, health checks, networking and how incidents are debugged.

#### Traps / caveats

- Do not choose Kubernetes just because it is popular.
- Do not choose serverless without checking latency, runtime limits and connection behavior.
- The database and network often limit scaling more than compute.

#### Optional Anki

Q: Name common cloud compute choices for Java services.
A: VMs, containers, managed container platforms, PaaS runtimes and serverless.

</details>

<a id="cloud-comp-002"></a>

<details>
<summary><strong>CLOUD-COMP-002. When would you use virtual machines instead of containers or serverless?</strong></summary>

#### Short answer

Use VMs when you need OS-level control, legacy compatibility, specialized agents or predictable long-running workloads.

#### Interview answer

VMs make sense for legacy Java applications, custom OS dependencies, licensed software, unusual networking, stateful workloads, or teams not ready for container orchestration. They offer control but require more patching, hardening and operational work.

#### Deep dive

VMs are often a migration step. A service can move from on-premise VMs to cloud VMs first, then later to containers or managed platforms after configuration, observability and deployment practices improve.

#### Production angle

VM fleets need automated images, patch strategy, instance replacement, monitoring, backup and security baselines.

#### Traps / caveats

- Manually maintained VMs drift quickly.
- VM autoscaling still needs statelessness and startup automation.
- SSH-based fixes are hard to reproduce and audit.

#### Optional Anki

Q: When are VMs a reasonable cloud compute choice?
A: When OS control, legacy compatibility or predictable long-running workloads matter more than platform abstraction.

</details>

<a id="cloud-comp-003"></a>

<details>
<summary><strong>CLOUD-COMP-003. When would you use a managed container platform for Java services?</strong></summary>

#### Short answer

Use it when you want container packaging, orchestration, autoscaling and rollout control without managing all infrastructure yourself.

#### Interview answer

Managed Kubernetes or container platforms fit teams running multiple services that need standardized deployments, service discovery, health checks, autoscaling, secrets integration and controlled rollouts. They are especially useful when the organization already has platform expertise.

#### Deep dive

Containers are good for Java because they package the JAR, runtime, OS libraries and startup command consistently. The platform still needs correct resource limits, probes, logging and network policies.

#### Production angle

A managed platform reduces control-plane operations, but application teams still own image quality, JVM sizing, graceful shutdown and dependency behavior.

#### Traps / caveats

- Containers do not automatically make the app stateless.
- Bad probes or limits can cause outages.
- Kubernetes adds complexity for very small systems.

#### Optional Anki

Q: Why use a managed container platform?
A: To standardize container deployment, scaling and rollout behavior while reducing infrastructure management.

</details>

<a id="cloud-comp-004"></a>

<details>
<summary><strong>🧠 CLOUD-COMP-004. When is a PaaS runtime a good fit for a Spring Boot application?</strong></summary>

#### Short answer

PaaS fits when the team wants simple deployment and managed runtime operations more than low-level infrastructure control.

#### Interview answer

A Spring Boot API with standard HTTP traffic, externalized configuration, logs to stdout and managed database dependencies can fit PaaS well. The platform handles much of the runtime, routing, scaling and patching.

#### Deep dive

PaaS can reduce operational load, but may constrain networking, startup behavior, sidecars, custom agents, file system use, runtime versions and deployment topology.

#### Production angle

PaaS is attractive when delivery speed matters and workload requirements match platform assumptions.

#### Traps / caveats

- Check memory, startup and request-duration limits.
- Avoid relying on local disk or instance affinity.
- Understand how health checks and scaling are configured.

#### Optional Anki

Q: When is PaaS good for Spring Boot?
A: When the app follows standard platform assumptions and the team values managed runtime operations.

</details>

<a id="cloud-comp-005"></a>

<details>
<summary><strong>CLOUD-COMP-005. When is serverless compute a good fit, and when is it a bad fit?</strong></summary>

#### Short answer

Serverless fits event-driven, bursty and operationally simple workloads; it is weaker for long-running, latency-sensitive or highly stateful workloads.

#### Interview answer

Serverless can work well for file processing, scheduled tasks, async event handlers and APIs with variable traffic. It is less attractive when a Java service needs very low cold-start latency, long execution, stable local caches, many persistent connections or deep runtime customization.

#### Deep dive

Serverless changes the unit of scaling and billing. You pay for execution, but you must handle concurrency, idempotency, startup time, retries, limits and observability.

#### Production angle

Serverless can reduce idle cost, but unexpected event storms can create high cost or overload downstream services.

#### Traps / caveats

- Cold starts matter for Java.
- Serverless retries can duplicate side effects.
- Connection pooling behaves differently with short-lived or frozen execution contexts.

#### Optional Anki

Q: What workloads fit serverless well?
A: Bursty, event-driven, short-running workloads with clear idempotency and modest runtime customization.

</details>

<a id="cloud-comp-006"></a>

<details>
<summary><strong>CLOUD-COMP-006. How do serverless cold starts affect Java applications?</strong></summary>

#### Short answer

Cold starts add latency when the platform initializes a new runtime, and Java startup can be heavier than some alternatives.

#### Interview answer

A cold start may include provisioning the execution environment, starting the JVM, loading classes, initializing Spring, creating clients and reading configuration. For Java, this can affect p95 or p99 latency if new instances are created during traffic spikes.

#### Deep dive

Mitigations include reducing startup work, lazy initialization, smaller frameworks, provisioned/minimum concurrency, native images where appropriate, and moving latency-sensitive work away from functions.

#### Production angle

Cold starts can break user-facing APIs but be acceptable for async processing or scheduled jobs.

#### Traps / caveats

- Warmup tricks do not remove all scaling cold starts.
- Native images improve startup but add build and runtime trade-offs.
- Initialization failures can look like intermittent request failures.

#### Optional Anki

Q: Why can Java serverless cold starts be noticeable?
A: JVM and framework initialization can add latency when new execution environments start.

</details>

<details>
<summary><strong>CLOUD-COMP-007. How should JVM memory and CPU settings be handled in cloud runtimes?</strong></summary>

#### Short answer

Size the JVM from container or instance limits, workload measurements and non-heap memory needs, not just from heap assumptions.

#### Interview answer

A Java service needs memory for heap, metaspace, thread stacks, direct buffers, code cache, agents and native libraries. CPU settings affect GC threads, request concurrency and latency. I would validate settings with load tests and production telemetry.

#### Deep dive

Modern JVMs are container-aware, but defaults are not always ideal. `-Xmx` or percentage-based sizing must leave room for non-heap memory.

#### Production angle

Wrong sizing causes OOM kills, GC pressure, CPU throttling, slow startup or noisy-neighbor problems.

#### Traps / caveats

- Do not set heap equal to container memory limit.
- CPU throttling can show up as latency, not errors.
- Autoscaling can multiply database connections.

#### Optional Anki

Q: Why should heap be below container memory limit?
A: The process also needs non-heap and native memory.

</details>

<a id="cloud-comp-008"></a>

<details>
<summary><strong>CLOUD-COMP-008. Why should cloud services avoid relying on local disk?</strong></summary>

#### Short answer

Local disk is usually ephemeral, instance-bound and unsafe for durable shared state.

#### Interview answer

In cloud runtimes, instances can be replaced, rescheduled or scaled down. Data written only to local disk may disappear or be invisible to other replicas. Durable data should go to databases, object storage, managed file storage or queues.

#### Deep dive

Local disk can still be useful for temporary files, caches or buffers if the application can recreate them and handles cleanup.

#### Production angle

Local file assumptions break rolling deployments, autoscaling, failover and disaster recovery.

#### Traps / caveats

- Temporary files can still exhaust disk and crash a service.
- Uploaded files should not stay only on one app instance.
- Local cache must tolerate eviction and stale data.

#### Optional Anki

Q: Why avoid local disk for durable state?
A: It is instance-bound and can disappear when the instance is replaced.

</details>

<a id="cloud-comp-009"></a>

<details>
<summary><strong>CLOUD-COMP-009. How should background jobs and scheduled tasks be run in cloud environments?</strong></summary>

#### Short answer

Run them through managed schedulers, worker services or queues with idempotency and concurrency control.

#### Interview answer

In a scaled cloud service, putting `@Scheduled` in every replica can accidentally run the same job many times. Better patterns are a dedicated worker, managed scheduler, queue-triggered job, leader election or distributed lock, depending on criticality.

#### Deep dive

Long-running jobs should report progress, handle retries, use leases or checkpoints and avoid holding local state that disappears on restart.

#### Production angle

Duplicate invoice generation, double emails and repeated data migrations often come from naive scheduled jobs in horizontally scaled services.

#### Traps / caveats

- Distributed locks need expiration and failure handling.
- Idempotency is safer than assuming a job runs exactly once.
- Scheduled work needs observability and alerting.

#### Optional Anki

Q: What is risky about `@Scheduled` in a scaled service?
A: Every replica may run the same job unless coordination exists.

</details>

<details>
<summary><strong>🧠 CLOUD-COMP-010. How do blue-green, rolling and canary deployments differ in cloud platforms?</strong></summary>

#### Short answer

Rolling replaces instances gradually, blue-green switches between two environments, and canary sends limited traffic to a new version first.

#### Interview answer

Rolling deployment is common and resource-efficient, but old and new versions run together. Blue-green keeps two complete environments and switches traffic, making rollback fast but more expensive. Canary deployment exposes a small percentage of traffic first and expands if metrics are healthy.

#### Deep dive

The best choice depends on compatibility, database migrations, traffic routing, observability and rollback needs.

#### Production angle

Canaries are only useful when metrics are good enough to detect user impact before full rollout.

#### Traps / caveats

- Database changes must be backward compatible during mixed versions.
- Blue-green does not solve bad shared database migrations.
- Canary traffic must be representative.

#### Optional Anki

Q: What is a canary deployment?
A: A rollout where a small slice of traffic reaches the new version before wider release.

</details>

<details>
<summary><strong>🧠 CLOUD-COMP-011. What deployment metadata should be visible for a running Java service?</strong></summary>

#### Short answer

At minimum: version, build commit, image, deployment time, environment, region, configuration version and feature-flag context.

#### Interview answer

A service should expose non-sensitive metadata through logs, health endpoints, metrics or admin diagnostics. This helps connect incidents to deployments and configuration changes.

#### Deep dive

Useful metadata includes application version, Git SHA, container image digest, JVM version, active profile, region/zone, instance ID, config version and migration state.

#### Production angle

When only some replicas fail, metadata quickly shows whether they run a different image, config or region.

#### Traps / caveats

- Do not expose secrets through diagnostic endpoints.
- Version strings should be immutable and traceable.
- Feature flag state can be sensitive if it reveals tenant behavior.

#### Optional Anki

Q: Why expose deployment metadata?
A: To correlate incidents with code, configuration, region and rollout state.

</details>

<details>
<summary><strong>🧠 CLOUD-COMP-012. What are spot, preemptible or interruptible compute instances, and when can backend workloads use them safely?</strong></summary>

#### Short answer

They are discounted compute instances that the provider can reclaim, so they fit fault-tolerant and retryable work.

#### Interview answer

Interruptible capacity can reduce cost for batch jobs, async workers, CI tasks or stateless services with enough redundancy. It is risky for single-instance critical services, stateful work without checkpoints or workloads that cannot tolerate sudden termination.

#### Deep dive

Safe use requires graceful shutdown, work checkpointing, retries, queue-based processing, mixed capacity pools and monitoring of interruption rates.

#### Production angle

For Java workers, interruptible nodes are reasonable when message processing is idempotent and visibility timeouts or leases are configured correctly.

#### Traps / caveats

- Discounted capacity can disappear during high demand.
- Stateful local work may be lost.
- Do not put all replicas of a critical path on interruptible capacity.

#### Optional Anki

Q: What workloads fit interruptible compute?
A: Fault-tolerant, retryable, stateless or checkpointed workloads.

</details>
