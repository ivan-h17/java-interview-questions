# Messaging, events and asynchronous cloud services

<a id="cloud-msg-001"></a>

<details>
<summary><strong>🧠 CLOUD-MSG-001. What managed messaging options are common in cloud platforms?</strong></summary>

#### Short answer

Common options include queues, pub/sub topics, event buses, managed Kafka-style streams, schedulers and workflow services.

#### Interview answer

Cloud platforms usually offer simple queues for work distribution, pub/sub topics for fan-out, event buses for routing, streaming platforms for ordered logs and workflow services for orchestration. Java services use these for async work, integration and decoupling.

#### Deep dive

The important choice is delivery model: command queue, event notification, durable stream or workflow state machine.

#### Production angle

The wrong messaging type can cause ordering bugs, lost retries, high cost or hard-to-debug workflows.

#### Traps / caveats

- A queue and an event stream are not interchangeable.
- Managed messaging still needs idempotent consumers.
- Provider trigger defaults may retry more than expected.

#### Optional Anki

Q: Name common cloud messaging types.
A: Queues, pub/sub topics, event buses, streams, schedulers and workflows.

</details>

<a id="cloud-msg-002"></a>

<details>
<summary><strong>CLOUD-MSG-002. When would you use a queue instead of synchronous HTTP between services?</strong></summary>

#### Short answer

Use a queue when work can be asynchronous and you need buffering, retries or decoupling.

#### Interview answer

A queue is useful for email sending, report generation, image processing, webhook delivery or any task where the caller does not need an immediate result. It protects the caller from slow consumers and lets workers process at their own pace.

#### Deep dive

Queues introduce eventual consistency and duplicate delivery, so consumers must be idempotent and observable.

#### Production angle

A queue can absorb spikes, but an unbounded backlog can still violate business SLOs.

#### Traps / caveats

- Queueing is not a fix for broken capacity planning.
- Users may still need status and timeout semantics.
- Dead letters need owners and replay procedures.

#### Optional Anki

Q: Why use a queue instead of HTTP?
A: To buffer asynchronous work, decouple services and support retries.

</details>

<a id="cloud-msg-003"></a>

<details>
<summary><strong>🧠 CLOUD-MSG-003. When would you use pub/sub or an event bus?</strong></summary>

#### Short answer

Use pub/sub or an event bus when multiple consumers need to react independently to events.

#### Interview answer

If an order is placed and several services need to update search, send email, adjust analytics or trigger fulfillment, an event can be published once and consumed by multiple subscribers. This avoids direct calls from the producer to every downstream service.

#### Deep dive

Events should describe business facts, not remote procedure calls. Consumers should tolerate missing fields, duplicate events and schema evolution.

#### Production angle

Event fan-out improves decoupling but can make end-to-end behavior harder to trace.

#### Traps / caveats

- Do not use events to hide unclear ownership.
- Event contracts need versioning.
- Fan-out can multiply downstream failures.

#### Optional Anki

Q: When is pub/sub useful?
A: When multiple independent consumers need to react to the same event.

</details>

<a id="cloud-msg-004"></a>

<details>
<summary><strong>CLOUD-MSG-004. How do managed queues differ from Kafka-style event streaming?</strong></summary>

#### Short answer

Queues distribute work to consumers; streams keep an ordered log that consumers can read and replay.

#### Interview answer

In a queue, a message is usually processed by one consumer and then removed or acknowledged. In Kafka-style streams, records remain for a retention period, and multiple consumer groups can read independently from offsets.

#### Deep dive

Queues are simple for task processing. Streams are stronger for event logs, replay, audit, projections and multiple independent consumers.

#### Production angle

A queue is often easier to operate for background jobs, while a stream is better when replay and ordering by key matter.

#### Traps / caveats

- Streams require partition and key design.
- Queues may not support replay after acknowledgment.
- Both can deliver duplicates.

#### Optional Anki

Q: Queue vs stream?
A: A queue distributes work; a stream preserves a replayable log.

</details>

<a id="cloud-msg-005"></a>

<details>
<summary><strong>CLOUD-MSG-005. How should Java consumers handle retries and duplicate messages?</strong></summary>

#### Short answer

Consumers should be idempotent, retry transient failures with backoff and route poison messages to a dead-letter path.

#### Interview answer

Cloud messaging is usually at-least-once. A Java consumer should deduplicate by business key, make side effects idempotent, retry only safe failures, avoid tight retry loops and record processing outcomes.

#### Deep dive

Idempotency can use unique database constraints, processed-message tables, idempotency keys or state-machine transitions.

#### Production angle

Without idempotency, retries can double-charge users, send duplicate emails or corrupt projections.

#### Traps / caveats

- Acknowledging before durable side effects can lose work.
- Retrying validation errors just burns capacity.
- Deduplication storage needs retention and cleanup.

#### Optional Anki

Q: What delivery assumption should cloud consumers make?
A: At-least-once delivery, so duplicate messages are possible.

</details>

<a id="cloud-msg-006"></a>

<details>
<summary><strong>CLOUD-MSG-006. What is a dead-letter queue, and when should it be used?</strong></summary>

#### Short answer

A dead-letter queue stores messages that failed processing after configured attempts.

#### Interview answer

DLQs prevent poison messages from blocking the main queue forever. They are useful when transient retries are exhausted or a message cannot currently be processed due to bad data, missing dependency or code defect.

#### Deep dive

A DLQ is not a trash can. It needs alerts, ownership, inspection tooling and safe replay procedures.

#### Production angle

If DLQ depth grows unnoticed, business work may silently stop completing.

#### Traps / caveats

- Do not automatically replay without fixing the cause.
- Include failure reason and correlation IDs.
- Some messages need manual compensation, not replay.

#### Optional Anki

Q: What is a DLQ for?
A: Holding messages that failed after retry attempts for investigation or safe replay.

</details>

<a id="cloud-msg-007"></a>

<details>
<summary><strong>🧠 CLOUD-MSG-007. How do ordering guarantees differ across queues, topics and streams?</strong></summary>

#### Short answer

Ordering is usually limited by partition, message group, key or single queue semantics, not global across all messages.

#### Interview answer

Some queues provide best-effort ordering, FIFO ordering per group or no strict ordering. Streams usually preserve order within a partition. Pub/sub systems may not guarantee global order unless configured around keys.

#### Deep dive

Strict ordering limits parallelism because later messages may wait behind earlier ones for the same key or group.

#### Production angle

For order updates, account balances or workflow state, choose the key that represents the real ordering boundary.

#### Traps / caveats

- Global ordering is expensive and rarely needed.
- Retries can disturb perceived ordering.
- Hot keys can bottleneck ordered processing.

#### Optional Anki

Q: Where does Kafka-style ordering usually hold?
A: Within a partition.

</details>

<a id="cloud-msg-008"></a>

<details>
<summary><strong>🧠 CLOUD-MSG-008. How can event triggers from object storage, databases or schedulers affect service design?</strong></summary>

#### Short answer

They make services reactive, but require idempotency, filtering, retries and clear event contracts.

#### Interview answer

Cloud services can trigger functions or consumers when files arrive, rows change, schedules fire or resources emit events. This is useful for automation, but the service must handle duplicates, out-of-order events and partial failures.

#### Deep dive

An object-created event may arrive before downstream metadata is ready, or a scheduled trigger may overlap with a previous run.

#### Production angle

Event-triggered processing needs correlation IDs, DLQ handling and replay tools.

#### Traps / caveats

- Triggers may deliver duplicate events.
- File upload completion semantics matter.
- Scheduling every replica independently can duplicate jobs.

#### Optional Anki

Q: What must event-triggered services handle?
A: Duplicates, retries, ordering gaps and partial failures.

</details>

<a id="cloud-msg-009"></a>

<details>
<summary><strong>CLOUD-MSG-009. How do throughput limits and backpressure appear in managed messaging services?</strong></summary>

#### Short answer

They appear as throttling, growing lag, delayed delivery, in-flight limits, hot partitions or rejected sends.

#### Interview answer

Managed services have quotas and capacity models. Producers can be throttled, consumers can fall behind, partitions can become hot, or queues can hit in-flight message limits. Backpressure must propagate instead of causing unbounded retries.

#### Deep dive

Useful signals include publish errors, consumer lag, queue age, processing rate, retry count, DLQ depth and downstream saturation.

#### Production angle

Queue depth alone is not enough; message age often shows user impact better.

#### Traps / caveats

- Adding more consumers does not fix hot partitions.
- Retries can amplify overload.
- Provider quotas may need pre-approval before launch.

#### Optional Anki

Q: What async metric often shows user impact better than queue size?
A: Oldest message age or processing lag.

</details>

<a id="cloud-msg-010"></a>

<details>
<summary><strong>CLOUD-MSG-010. What are visibility timeouts, ack deadlines or consumer leases, and why do they matter?</strong></summary>

#### Short answer

They are time windows during which a delivered message is reserved for one consumer before it can be delivered again.

#### Interview answer

When a consumer receives a message, the broker usually hides or leases it until the consumer acknowledges completion. If processing takes longer than the timeout or the consumer crashes, the message can become visible again for another attempt.

#### Deep dive

The timeout should exceed normal processing time but not be so long that failed messages are delayed too much. Long tasks may need heartbeat or lease extension.

#### Production angle

Wrong lease settings cause duplicate concurrent work, slow retries or stuck in-flight messages.

#### Traps / caveats

- A lease is not exactly-once processing.
- Extend leases only while real progress is happening.
- Processing time must include downstream latency and retries.

#### Optional Anki

Q: What happens when a queue visibility timeout expires?
A: The message can be delivered again if it was not acknowledged or deleted.

</details>

<details>
<summary><strong>CLOUD-MSG-011. Why is exactly-once processing difficult even with managed cloud messaging?</strong></summary>

#### Short answer

Because message delivery, consumer execution and external side effects cannot usually be made atomic across all systems.

#### Interview answer

Even if a broker supports strong producer or offset guarantees, the consumer still writes to databases, calls APIs or sends emails. If the consumer crashes after the side effect but before acknowledgment, the message may be retried.

#### Deep dive

The practical solution is idempotent processing, transactional outbox/inbox patterns, deduplication keys and careful transaction boundaries.

#### Production angle

Exactly-once claims should be translated into concrete business guarantees: no double charge, no duplicate shipment, no lost state transition.

#### Traps / caveats

- Broker exactly-once does not mean end-to-end exactly-once side effects.
- Idempotency keys must be stable and scoped correctly.
- Deduplication windows can expire.

#### Optional Anki

Q: Why is exactly-once hard?
A: Message acknowledgment and external side effects are usually not one atomic transaction.

</details>
