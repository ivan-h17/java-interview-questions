# Well-architected thinking and ownership

---

<a id="cloud-arch-001"></a>

<details>
<summary><strong>CLOUD-ARCH-001. What are the main pillars of a well-architected cloud system?</strong></summary>

#### Short answer

The common pillars are operational excellence, security, reliability, performance efficiency, cost optimization and sustainability.

#### Interview answer

Well-architected thinking means evaluating a workload from several angles, not only whether it works. A senior backend engineer should ask whether the system can be operated safely, protected from abuse, recovered from failure, scaled efficiently, kept affordable and improved over time.

#### Deep dive

Different providers name the pillars slightly differently, but the engineering themes are stable: operations, security, reliability, performance, cost and environmental impact.

#### Production angle

These pillars turn architecture review into concrete questions: who owns the runbook, what are the SLOs, how are secrets handled, what fails over, what costs the most and what is the recovery plan?

#### Traps / caveats

- The pillars trade off against each other.
- A system can be secure but too expensive, or cheap but unreliable.
- Architecture review should happen repeatedly, not only before launch.

#### Optional Anki

Q: What are common well-architected pillars?
A: Operations, security, reliability, performance, cost and sustainability.

</details>

<details>
<summary><strong>CLOUD-ARCH-002. How does the shared responsibility model affect a Java backend team?</strong></summary>

#### Short answer

The provider manages parts of the platform, but the application team still owns code, data, identity, configuration and correct use of cloud services.

#### Interview answer

In cloud, responsibility is shared. The provider may manage data centers, hardware and parts of the managed service. The backend team still owns secure code, dependency updates, IAM use, application configuration, data protection, network exposure, logging, backups and incident response for its workload.

#### Deep dive

The split changes by service model. With VMs the team owns more OS and runtime work. With PaaS or managed databases, the provider owns more infrastructure, but the team still owns access, schema design, capacity, client behavior and data correctness.

#### Production angle

Many incidents happen when teams assume "the provider handles that" without checking the actual responsibility boundary.

#### Traps / caveats

- Managed patching does not fix vulnerable application dependencies.
- Encryption features still require key, access and data-classification decisions.
- Backups are useless unless restore is tested.

#### Optional Anki

Q: What does a backend team always retain in cloud?
A: Responsibility for application code, data, identity, configuration and correct use of services.

</details>

<details>
<summary><strong>🧠 CLOUD-ARCH-003. What is a cloud workload, and why is ownership important?</strong></summary>

#### Short answer

A workload is an application capability plus the infrastructure, data, operations and security controls needed to run it.

#### Interview answer

A workload is not just a service JAR. It includes compute, databases, queues, network paths, IAM roles, secrets, dashboards, alerts, deployment pipelines, runbooks and recovery plans. Ownership matters because someone must understand how all those pieces behave together.

#### Deep dive

Cloud platforms make it easy to create resources, so unclear ownership quickly leads to orphaned databases, broad IAM, missing alerts and unpatched infrastructure.

#### Production angle

During incidents, ownership answers who can change scaling, rotate credentials, restore data, contact provider support and communicate status.

#### Traps / caveats

- Resource ownership tags are not enough without operational ownership.
- Shared platform teams do not remove application-team accountability.
- Every critical dependency should have an owner and escalation path.

#### Optional Anki

Q: What is a cloud workload?
A: An application capability plus the cloud resources, data and operations needed to run it.

</details>

<a id="cloud-arch-004"></a>

<details>
<summary><strong>CLOUD-ARCH-004. How do SLOs and SLAs influence cloud architecture decisions?</strong></summary>

#### Short answer

SLOs and SLAs define reliability targets that drive redundancy, dependency choices, monitoring, deployment safety and cost.

#### Interview answer

An SLO is an internal target, like 99.9% successful requests under a latency threshold. An SLA is an external promise. These targets affect whether one region is enough, whether dependencies can be on the critical path, how aggressive deployments can be and how much operational investment is justified.

#### Deep dive

High SLOs require more than replicas. They require tested failover, dependency isolation, good alerts, capacity headroom and recovery procedures.

#### Production angle

If a critical dependency cannot meet the required reliability, the service must cache, degrade, queue, use redundancy or lower the promise.

#### Traps / caveats

- Do not promise higher availability than your dependencies can support.
- SLOs should include user-visible latency and correctness, not only uptime.
- More nines usually cost more.

#### Optional Anki

Q: How do SLOs affect architecture?
A: They drive redundancy, dependency choices, monitoring, deployment safety and cost.

</details>

<a id="cloud-arch-005"></a>

<details>
<summary><strong>CLOUD-ARCH-005. What are RTO and RPO, and why do they matter?</strong></summary>

#### Short answer

RTO is the acceptable recovery time; RPO is the acceptable data loss window.

#### Interview answer

RTO answers "how long can the service be unavailable?" RPO answers "how much data can we lose?" They matter because backup frequency, replication, failover automation and disaster recovery cost depend on these targets.

#### Deep dive

A low RTO may require warm standby, automation or active-active designs. A low RPO may require synchronous replication or carefully designed durable event logs.

#### Production angle

Different business capabilities can have different RTO/RPO. Checkout may need stricter targets than a back-office report.

#### Traps / caveats

- Backups alone do not guarantee low RTO.
- Async replication usually cannot promise zero RPO.
- RTO/RPO should be tested, not only documented.

#### Optional Anki

Q: RTO vs RPO?
A: RTO is recovery time; RPO is acceptable data loss.

</details>

<a id="cloud-arch-006"></a>

<details>
<summary><strong>CLOUD-ARCH-006. What is blast radius, and how can architecture limit it?</strong></summary>

#### Short answer

Blast radius is the scope of damage from a failure, misconfiguration or compromise.

#### Interview answer

Architecture limits blast radius by separating accounts, environments, regions, tenants, networks, IAM roles, databases and deployment units. The goal is that one bad deploy, leaked credential, overloaded tenant or broken dependency does not take down everything.

#### Deep dive

Blast-radius control is a combination of isolation and graceful failure. Rate limits, bulkheads, per-tenant quotas and separate failure domains all help.

#### Production angle

A bad feature flag or IAM change should affect a bounded set of services or tenants, not the whole company.

#### Traps / caveats

- Shared databases and shared admin roles often create huge blast radius.
- Too much isolation increases cost and operational complexity.
- Blast-radius limits need tests and permissions review.

#### Optional Anki

Q: What is blast radius?
A: The scope of damage caused by a failure, mistake or security compromise.

</details>

<details>
<summary><strong>🧠 CLOUD-ARCH-007. What is a fault domain?</strong></summary>

#### Short answer

A fault domain is a set of resources likely to fail together.

#### Interview answer

In cloud, a fault domain can be a VM host, rack, availability zone, region, network dependency, database cluster or provider service. Good architecture spreads critical components across independent fault domains when the business needs higher availability.

#### Deep dive

Fault domains are not only physical. A shared IAM role, shared queue, shared database connection pool or shared deployment pipeline can also create correlated failure.

#### Production angle

If all replicas depend on one NAT gateway, one database primary or one provider service endpoint, that dependency is a fault domain.

#### Traps / caveats

- Multi-instance is not resilient if all instances share the same failing dependency.
- Some managed services hide fault-domain details.
- Cross-domain redundancy has cost and consistency trade-offs.

#### Optional Anki

Q: What is a fault domain?
A: A group of resources that can fail together.

</details>

<a id="cloud-arch-008"></a>

<details>
<summary><strong>CLOUD-ARCH-008. How do reliability, latency, cost, security and complexity trade off against each other?</strong></summary>

#### Short answer

Improving one quality often increases cost or complexity, so architecture must match business risk rather than maximize every dimension.

#### Interview answer

For example, active-active multi-region may improve availability and latency for global users, but it increases data consistency complexity, operational burden and cost. Strong security controls reduce risk, but can slow development if not automated. Caching improves latency and cost, but adds invalidation and stale-data risk.

#### Deep dive

Senior design means naming the trade-off explicitly and selecting the simplest design that meets requirements.

#### Production angle

Overengineering can be as harmful as underengineering because complex systems fail in harder-to-debug ways.

#### Traps / caveats

- Do not choose multi-region without RTO/RPO and user-latency requirements.
- Do not optimize cost by removing critical observability or backups.
- Security controls need developer ergonomics or they get bypassed.

#### Optional Anki

Q: What is a senior way to handle cloud trade-offs?
A: Tie reliability, latency, cost, security and complexity choices to explicit business requirements.

</details>

<details>
<summary><strong>🧠 CLOUD-ARCH-009. Why should cloud architecture be documented and reviewed regularly?</strong></summary>

#### Short answer

Cloud systems change frequently, so documentation and review prevent hidden drift, stale assumptions and unmanaged risk.

#### Interview answer

Architecture docs should capture key decisions: regions, dependencies, IAM boundaries, data stores, failover approach, SLOs, cost assumptions and known trade-offs. Regular review checks whether reality still matches those assumptions.

#### Deep dive

Reviews are especially important after scaling, incidents, new regulations, provider feature changes or migration from one service to another.

#### Production angle

When an incident happens, outdated diagrams and missing runbooks slow diagnosis and recovery.

#### Traps / caveats

- Documentation should be close to code and deployment definitions where possible.
- Diagrams without ownership and failure modes are weak.
- Review should produce concrete actions, not ceremony.

#### Optional Anki

Q: Why review cloud architecture regularly?
A: To catch drift, stale assumptions and unmanaged operational risk.

</details>

<details>
<summary><strong>🧠 CLOUD-ARCH-010. How does sustainability relate to cost, performance and architecture choices?</strong></summary>

#### Short answer

Sustainability often aligns with efficient resource use: less waste usually means lower cost and better capacity discipline.

#### Interview answer

A backend team can improve sustainability by right-sizing services, reducing idle resources, deleting unused data, caching responsibly, avoiding wasteful retries and choosing efficient deployment patterns. These choices often reduce cloud spend too.

#### Deep dive

There can be trade-offs. More replicas can improve availability but consume more resources. Low-carbon regions can help, but latency, compliance and data residency may constrain placement.

#### Production angle

Sustainability becomes practical when measured through resource efficiency, utilization, retention and workload placement.

#### Traps / caveats

- Do not use sustainability as a reason to remove needed redundancy.
- Idle development and staging resources often waste more than teams expect.
- Data retention policies affect both cost and environmental impact.

#### Optional Anki

Q: Why does sustainability matter to backend engineers?
A: Efficient resource use reduces waste, cost and often operational complexity.

</details>

<details>
<summary><strong>CLOUD-ARCH-011. What are landing zones, account or project structures, and guardrails?</strong></summary>

#### Short answer

They are the foundational cloud setup that defines resource hierarchy, identity, network, logging, security controls and allowed patterns.

#### Interview answer

A landing zone is the prepared environment where workloads can run safely. It usually includes accounts or projects, network layout, IAM integration, audit logging, security policies, billing setup, naming standards and baseline monitoring.

#### Deep dive

Guardrails can be preventive, such as blocking public storage buckets, or detective, such as alerting when an unencrypted resource appears.

#### Production angle

Without a solid foundation, every team invents its own insecure IAM, logging, network and cost model.

#### Traps / caveats

- Guardrails should block risky behavior without preventing normal delivery.
- Account/project separation should match ownership and blast-radius needs.
- Foundation changes must be tested like application changes.

#### Optional Anki

Q: What is a cloud landing zone?
A: A prepared cloud foundation with identity, network, logging, security, billing and guardrails.

</details>

<details>
<summary><strong>🧠 CLOUD-ARCH-012. How do policy-as-code and organizational guardrails reduce cloud risk?</strong></summary>

#### Short answer

They make security, compliance and operational rules automatic, reviewable and consistently enforced.

#### Interview answer

Policy-as-code expresses rules such as "storage must be encrypted," "public access is forbidden," or "production resources need tags" in code. Guardrails enforce or detect violations across accounts and projects.

#### Deep dive

Policies can run in CI before deployment, in IaC review, or continuously against live resources. Preventive controls stop bad changes; detective controls alert or open remediation work.

#### Production angle

Policy automation catches risky changes before they become incidents and reduces reliance on manual review.

#### Traps / caveats

- Overly strict policies can block urgent fixes.
- Policies need exceptions with ownership and expiration.
- Runtime drift still needs detection even with IaC checks.

#### Optional Anki

Q: What does policy-as-code improve?
A: It makes cloud rules automatic, reviewable and consistently enforced.

</details>
