# Cost optimization and capacity planning

<a id="cloud-cost-001"></a>

<details>
<summary><strong>CLOUD-COST-001. How can poor backend design increase cloud cost?</strong></summary>

#### Short answer

Poor design wastes compute, storage, network, database capacity and managed-service requests.

#### Interview answer

Inefficient queries, chatty service calls, huge payloads, unbounded retries, bad cache keys, overprovisioned instances, forgotten resources and excessive logging all increase cloud cost. Backend design directly controls many cost drivers.

#### Deep dive

Cost is often a symptom of architecture: data movement, request fan-out, retention, concurrency and inefficient access patterns.

#### Production angle

A sudden bill increase can indicate a production bug, retry storm, traffic spike, abuse or resource leak.

#### Traps / caveats

- Cost optimization should not remove needed reliability controls.
- Optimize the largest cost drivers first.
- Cheap per-request services can become expensive at scale.

#### Optional Anki

Q: How can backend code increase cloud cost?
A: Inefficient queries, payloads, retries, fan-out, logging and resource use.

</details>

<a id="cloud-cost-002"></a>

<details>
<summary><strong>CLOUD-COST-002. What are the biggest cloud cost drivers for backend services?</strong></summary>

#### Short answer

Common drivers are compute, databases, storage, network egress, managed-service requests, observability and idle environments.

#### Interview answer

For Java backends, databases and compute are often large costs, but egress, logs, traces, object storage growth, queue operations, cache memory and staging environments can also be significant.

#### Deep dive

Costs vary by workload. A media service may be bandwidth-heavy, while a transactional API may be database-heavy.

#### Production angle

Cost dashboards should be grouped by service, environment, team, region and major resource type.

#### Traps / caveats

- Untagged resources hide ownership.
- Observability can become a major cost at high volume.
- Cross-zone and cross-region traffic is easy to overlook.

#### Optional Anki

Q: Name common backend cloud cost drivers.
A: Compute, databases, storage, network egress, managed-service calls, observability and idle resources.

</details>

<a id="cloud-cost-003"></a>

<details>
<summary><strong>🧠 CLOUD-COST-003. How do compute, storage, database and network egress costs differ?</strong></summary>

#### Short answer

Compute is usually time and size based, storage is capacity and operation based, databases add managed capacity costs, and egress charges data transfer out or across boundaries.

#### Interview answer

Compute cost depends on instance size, duration and scaling. Storage cost depends on GB stored, class, operations and retrieval. Managed databases charge for compute, storage, I/O, replicas and backups. Network egress charges data leaving regions, zones or the provider.

#### Deep dive

The cost model affects architecture. A design with small compute but heavy cross-region traffic can still be expensive.

#### Production angle

Cost reviews should include traffic paths and data lifecycle, not only instance sizes.

#### Traps / caveats

- Backups and replicas add storage and transfer cost.
- Egress can be hidden inside architecture diagrams.
- Request-based pricing punishes chatty designs.

#### Optional Anki

Q: What is network egress cost?
A: Cost for data transferred out of a boundary such as a region, zone or provider network.

</details>

<a id="cloud-cost-004"></a>

<details>
<summary><strong>CLOUD-COST-004. How can autoscaling reduce cost, and how can it increase cost?</strong></summary>

#### Short answer

Autoscaling reduces idle capacity, but bad signals or runaway load can scale wastefully and overload dependencies.

#### Interview answer

Autoscaling helps match capacity to demand. It can increase cost if retries, bot traffic, slow dependencies or bad metrics cause unnecessary scale-out. It can also multiply database connections and downstream calls.

#### Deep dive

Good autoscaling uses meaningful metrics, min/max limits, cooldowns and dependency-aware capacity planning.

#### Production angle

Autoscaling should be paired with rate limits, backpressure and cost alerts.

#### Traps / caveats

- Scaling on CPU alone may miss blocked-thread overload.
- No max limit can create cost runaway.
- Scaling app replicas does not scale every dependency.

#### Optional Anki

Q: How can autoscaling increase cost?
A: Bad metrics or runaway load can add capacity without fixing the bottleneck.

</details>

<a id="cloud-cost-005"></a>

<details>
<summary><strong>CLOUD-COST-005. What is right-sizing, and how would you right-size a Java service?</strong></summary>

#### Short answer

Right-sizing matches CPU, memory and instance count to measured workload needs with safe headroom.

#### Interview answer

For Java, I would review request rate, latency, CPU, memory, heap, GC, thread pools, connection pools and p95/p99 behavior under real or load-test traffic. Then I would adjust instance size, JVM memory, replica count and autoscaling rules.

#### Deep dive

Right-sizing is continuous. Traffic shape, code, dependencies and JVM settings change over time.

#### Production angle

Over-sized services waste money; under-sized services cause throttling, OOM kills or latency.

#### Traps / caveats

- Do not size from average traffic only.
- Leave memory for non-heap JVM usage.
- Validate after deployment.

#### Optional Anki

Q: What inputs help right-size Java services?
A: CPU, memory, heap, GC, latency, concurrency, pools and traffic peaks.

</details>

<a id="cloud-cost-006"></a>

<details>
<summary><strong>🧠 CLOUD-COST-006. When would you use on-demand, committed-use, reserved or interruptible capacity?</strong></summary>

#### Short answer

Use on-demand for flexibility, commitments for predictable baseline load and interruptible capacity for fault-tolerant work.

#### Interview answer

On-demand is simple and flexible. Reserved or committed-use discounts fit stable workloads with predictable capacity. Interruptible or spot capacity fits batch, workers or stateless services that can tolerate termination.

#### Deep dive

Capacity strategy should separate baseline from burst. Commit too much and you waste money; commit too little and stable workloads cost more.

#### Production angle

Critical user-facing services usually need reliable baseline capacity, while async workers can often use cheaper interruptible capacity.

#### Traps / caveats

- Discount plans are financial commitments.
- Spot capacity can disappear during high demand.
- Interruptible workers need idempotency and checkpointing.

#### Optional Anki

Q: What workload fits interruptible capacity?
A: Fault-tolerant, retryable or checkpointed work.

</details>

<a id="cloud-cost-007"></a>

<details>
<summary><strong>CLOUD-COST-007. How should budgets, alerts and resource tags be used?</strong></summary>

#### Short answer

Use them to make cost visible, owned and actionable before bills become surprises.

#### Interview answer

Budgets define expected spend. Alerts notify teams when spend or usage deviates. Tags or labels attribute resources to service, team, environment, owner and cost center.

#### Deep dive

Tags should be enforced by policy where possible, because untagged resources hide accountability.

#### Production angle

Cost alerts can catch retry storms, leaked resources, abuse or incorrect autoscaling faster than monthly bill review.

#### Traps / caveats

- Budgets without owners do not change behavior.
- Tags need naming standards.
- Alerts should distinguish forecasted and actual spend.

#### Optional Anki

Q: Why tag cloud resources?
A: To attribute cost, ownership, environment and operational responsibility.

</details>

<a id="cloud-cost-008"></a>

<details>
<summary><strong>CLOUD-COST-008. How would you estimate monthly cost for a new backend service?</strong></summary>

#### Short answer

Estimate traffic, compute, database, storage, network, managed-service calls, observability and environments.

#### Interview answer

I would start with expected QPS, peak load, payload size, data volume, retention, database size and external calls. Then estimate replicas, database tier, cache, queues, object storage, egress, logs/traces and non-production environments.

#### Deep dive

Use ranges and assumptions rather than false precision. Validate with load tests and early production data.

#### Production angle

Cost estimates should include growth, burst traffic, backups, replicas and incident headroom.

#### Traps / caveats

- Do not forget staging, dev and test environments.
- Observability and data transfer can be large.
- Managed services often have request-based charges.

#### Optional Anki

Q: What inputs go into backend cost estimation?
A: Traffic, compute, database, storage, network, managed calls, logs and environments.

</details>

<a id="cloud-cost-009"></a>

<details>
<summary><strong>CLOUD-COST-009. How would you investigate a sudden cloud bill increase?</strong></summary>

#### Short answer

Break down cost by service, resource, environment, region, time and owner, then correlate with deployments and traffic.

#### Interview answer

I would identify which cost category changed: compute, database, egress, logs, storage, queues or API calls. Then correlate with traffic, releases, retries, new resources, data exports, autoscaling and possible abuse.

#### Deep dive

Usage metrics often explain cost faster than billing alone: bytes transferred, log volume, query count, object operations, replica count and queue retries.

#### Production angle

Immediate mitigation may be rate limits, disabling a feature, reducing logging, fixing a retry loop or deleting leaked resources.

#### Traps / caveats

- Billing data can lag.
- Deleting resources without understanding ownership can cause outages.
- Cost spikes can indicate a security incident.

#### Optional Anki

Q: What do you correlate with a bill spike?
A: Resource usage, deployments, traffic, retries, regions and owners.

</details>

<details>
<summary><strong>CLOUD-COST-010. What is FinOps, and why should backend engineers care?</strong></summary>

#### Short answer

FinOps is cloud financial management that connects engineering decisions to business value and cost accountability.

#### Interview answer

Backend engineers influence cost through architecture, queries, retries, payloads, retention, logging and resource sizing. FinOps gives teams visibility, budgets, ownership and optimization practices without treating cost as only a finance problem.

#### Deep dive

Good FinOps is not just cutting spend. It is spending intentionally where reliability, performance or delivery speed justify it.

#### Production angle

Cost-aware engineers can prevent runaway spend and explain why some expensive choices are worth it.

#### Traps / caveats

- Do not optimize cost by weakening reliability or security.
- Cost data must be attributed to teams and services.
- Unit economics are better than total bill alone.

#### Optional Anki

Q: Why should backend engineers care about FinOps?
A: Their code and architecture directly drive cloud cost and business value.

</details>
