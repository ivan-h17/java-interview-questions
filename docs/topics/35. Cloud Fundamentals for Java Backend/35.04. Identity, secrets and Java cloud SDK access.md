# Identity, secrets and Java cloud SDK access

---

<a id="cloud-iam-001"></a>

<details>
<summary><strong>CLOUD-IAM-001. What is IAM, and why does least privilege matter in cloud systems?</strong></summary>

#### Short answer

IAM controls who or what can access cloud resources; least privilege limits access to only what is needed.

#### Interview answer

Identity and Access Management defines users, roles, service identities, permissions and policies. Least privilege matters because cloud APIs can create, delete, read or expose critical resources. A compromised service should not automatically become a compromised cloud account.

#### Deep dive

IAM applies to humans, applications, CI/CD pipelines and managed services. Permissions should be scoped by action, resource, environment and sometimes condition.

#### Production angle

Overbroad IAM turns application bugs, SSRF, leaked tokens or CI compromise into large-scale incidents.

#### Traps / caveats

- `admin` permissions are not acceptable for normal service runtime.
- Least privilege needs review as services evolve.
- Deny and boundary policies can override apparent allows.

#### Optional Anki

Q: Why does least privilege matter in cloud?
A: It limits blast radius when a user, service or credential is compromised.

</details>

<a id="cloud-iam-002"></a>

<details>
<summary><strong>🧠 CLOUD-IAM-002. What is the difference between a user, group, role and service account?</strong></summary>

#### Short answer

Users represent people, groups collect users, roles are assumable permission sets, and service accounts represent workloads or automation.

#### Interview answer

Human users should usually authenticate through centralized identity. Groups simplify assigning permissions to people. Roles are temporary identities that users, services or pipelines can assume. Service accounts or workload identities represent applications rather than people.

#### Deep dive

Provider terminology differs, but the principle is stable: separate human identity from workload identity and avoid sharing credentials.

#### Production angle

Audit logs are much clearer when a failing or dangerous action is tied to a specific service identity or human role.

#### Traps / caveats

- Shared human accounts break auditability.
- Service accounts should not be reused across unrelated services.
- Group membership changes can grant broad access unexpectedly.

#### Optional Anki

Q: What is a service account?
A: An identity used by an application or automation, not a human.

</details>

<a id="cloud-iam-003"></a>

<details>
<summary><strong>CLOUD-IAM-003. Why should applications prefer temporary credentials over long-lived access keys?</strong></summary>

#### Short answer

Temporary credentials expire automatically and reduce the damage from leaks.

#### Interview answer

Long-lived access keys can be copied, committed, logged or stolen and remain valid until rotated. Temporary credentials from workload identity, managed identity or role assumption are short-lived and can be scoped to a service.

#### Deep dive

Temporary credentials do not remove the need for least privilege, but they reduce secret distribution and rotation burden.

#### Production angle

If a container image, CI log or heap dump leaks a static key, incident response requires immediate revocation and rotation. Short-lived credentials reduce that window.

#### Traps / caveats

- Temporary credentials can still be abused before they expire.
- The trust policy or workload binding must be correct.
- Local development should not encourage copying production keys.

#### Optional Anki

Q: Why prefer temporary cloud credentials?
A: They expire and reduce the impact of credential leakage.

</details>

<a id="cloud-iam-004"></a>

<details>
<summary><strong>CLOUD-IAM-004. How should a Java service authenticate to cloud APIs in production?</strong></summary>

#### Short answer

Use workload identity, managed identity or role-based temporary credentials rather than embedded access keys.

#### Interview answer

A Java service should run under a dedicated workload identity with least-privilege permissions. The cloud SDK should obtain credentials from the runtime environment, such as instance metadata, pod identity, role assumption or managed identity.

#### Deep dive

This keeps credentials out of source code, images and configuration. The application gets short-lived credentials from the platform and uses normal SDK clients.

#### Production angle

Each service should have its own identity so access can be audited, revoked and scoped independently.

#### Traps / caveats

- Do not bake keys into `application.yml` or images.
- Check that the service identity cannot access unrelated resources.
- Metadata endpoints must be protected from SSRF.

#### Optional Anki

Q: How should production Java services authenticate to cloud APIs?
A: With dedicated workload identity or managed identity that provides temporary credentials.

</details>

<a id="cloud-iam-005"></a>

<details>
<summary><strong>CLOUD-IAM-005. How should local development and CI authenticate to cloud resources safely?</strong></summary>

#### Short answer

Use separate non-production identities, short-lived tokens and scoped permissions; avoid sharing production keys.

#### Interview answer

Local developers should authenticate through SSO or developer roles with limited access. CI should use federated identity or short-lived role assumption from the CI platform. Both should be separated from production runtime identities.

#### Deep dive

CI credentials are high-risk because pipelines can deploy, read secrets or mutate infrastructure. They need least privilege, branch/environment restrictions and audit logging.

#### Production angle

Many breaches start from leaked developer or CI credentials rather than the production service itself.

#### Traps / caveats

- Never copy production service credentials to laptops.
- CI logs can leak environment variables.
- Test environments should not have broad production access.

#### Optional Anki

Q: What is safer than static CI cloud keys?
A: Federated identity or short-lived role assumption scoped to the pipeline.

</details>

<a id="cloud-iam-006"></a>

<details>
<summary><strong>CLOUD-IAM-006. What is workload identity or managed identity?</strong></summary>

#### Short answer

It is a platform-provided identity for a running workload that can obtain short-lived credentials.

#### Interview answer

Workload identity lets a pod, VM, function or app service authenticate as itself to cloud APIs. Instead of storing static keys, the runtime proves its identity to the platform and receives temporary credentials for allowed resources.

#### Deep dive

The important parts are binding the workload to the right identity, limiting permissions and auditing token use.

#### Production angle

Workload identity is one of the best ways to reduce secret sprawl in Java services.

#### Traps / caveats

- Misbinding a workload can grant the wrong service access.
- Temporary credentials still need least privilege.
- Local development needs a separate authentication path.

#### Optional Anki

Q: What problem does workload identity solve?
A: It lets workloads access cloud APIs without distributing long-lived static keys.

</details>

<a id="cloud-iam-007"></a>

<details>
<summary><strong>CLOUD-IAM-007. How should secrets be stored, injected and rotated in cloud-hosted services?</strong></summary>

#### Short answer

Store secrets in a managed secret store, inject only what each service needs and design rotation with overlap.

#### Interview answer

Secrets should not live in Git, images or plain deployment files. A service should retrieve or receive secrets through a secret manager, external secrets operator, mounted files or secure runtime integration. Rotation should support old and new values during a transition.

#### Deep dive

Database passwords, TLS keys, API tokens and signing keys all rotate differently. The application must handle reload or restart, connection-pool refresh and validation.

#### Production angle

Bad rotation often causes outages because old connections keep using invalid credentials or new pods cannot start.

#### Traps / caveats

- Environment variables are easy but can leak through dumps and diagnostics.
- Secret rotation is not complete until old credentials are revoked.
- Secret access should be audited.

#### Optional Anki

Q: Where should cloud-hosted services store secrets?
A: In a managed secret store or equivalent controlled secret system, not in code or images.

</details>

<a id="cloud-iam-008"></a>

<details>
<summary><strong>CLOUD-IAM-008. Why should secrets not be stored in container images, environment dumps or logs?</strong></summary>

#### Short answer

Because those artifacts are widely copied, retained and inspected, making leaked secrets hard to contain.

#### Interview answer

Container images are pushed to registries and reused across environments. Logs and diagnostic dumps go to central systems. If secrets appear there, many people and systems may gain access, and deleting every copy is difficult.

#### Deep dive

Even if a secret is later removed from code, it may still exist in image layers, CI caches, log archives or crash reports.

#### Production angle

When a secret leaks, the safe response is rotation and revocation, not only deleting the visible copy.

#### Traps / caveats

- Masking in logs is helpful but not a complete security control.
- Heap dumps can contain credentials loaded into memory.
- Build arguments can leak into image history.

#### Optional Anki

Q: Why is a secret in a container image dangerous?
A: Images are copied and retained, and old layers may preserve the secret.

</details>

<a id="cloud-iam-009"></a>

<details>
<summary><strong>🧠 CLOUD-IAM-009. How do permission boundaries affect incident blast radius?</strong></summary>

#### Short answer

Permission boundaries cap what an identity can do even if a policy grants broader access.

#### Interview answer

Boundaries, organization policies and resource constraints limit the maximum permissions available to users, roles or projects. They help prevent one bad policy or compromised identity from escaping its intended scope.

#### Deep dive

Boundaries are useful for delegated administration: teams can manage their resources but cannot grant themselves global admin, disable logging or access production secrets.

#### Production angle

If a CI role is compromised, boundaries can prevent it from creating privileged identities or changing unrelated environments.

#### Traps / caveats

- Boundaries are not a substitute for least-privilege policies.
- Misunderstood deny rules can block deployments.
- Boundaries need testing before rollout.

#### Optional Anki

Q: What is the purpose of permission boundaries?
A: To cap the maximum permissions an identity can effectively use.

</details>

<a id="cloud-iam-010"></a>

<details>
<summary><strong>🧠 CLOUD-IAM-010. What audit information should exist for cloud access changes?</strong></summary>

#### Short answer

You need who changed what, when, from where, why, and what effective access resulted.

#### Interview answer

IAM changes should be traceable to a human or pipeline, reviewed in code where possible and logged by the provider. Useful audit data includes identity, action, target resource, old and new permissions, approval, ticket, environment and source IP.

#### Deep dive

Effective access can differ from a single policy file because groups, roles, inherited policies, boundaries and explicit denies interact.

#### Production angle

After a data exposure or failed deployment, audit logs help determine whether permission changes contributed.

#### Traps / caveats

- Audit logs must be protected from modification.
- Console changes can bypass review if not controlled.
- Retention must match investigation and compliance needs.

#### Optional Anki

Q: What should IAM audit logs answer?
A: Who changed access, what changed, when, why and what access resulted.

</details>

<a id="cloud-iam-011"></a>

<details>
<summary><strong>🧠 CLOUD-IAM-011. How do IAM policy evaluation and explicit deny rules work conceptually?</strong></summary>

#### Short answer

Access is allowed only when an applicable allow exists and no applicable explicit deny blocks it.

#### Interview answer

IAM systems evaluate identity policies, resource policies, boundaries and organization rules. The exact model differs by provider, but conceptually an explicit deny usually wins over an allow, and absence of an allow means no access.

#### Deep dive

Conditions such as source network, requested resource, tags, time or MFA can affect the decision. This is why "the role has permission" is not enough; you need effective access.

#### Production angle

Unexpected denies often break deployments, while unexpected allows create security exposure.

#### Traps / caveats

- Multiple policies can combine in non-obvious ways.
- Wildcards can grant more than intended.
- Resource policies can expose data even if identity policies look restricted.

#### Optional Anki

Q: What usually wins in IAM evaluation?
A: An applicable explicit deny.

</details>

<a id="cloud-iam-012"></a>

<details>
<summary><strong>🧠 CLOUD-IAM-012. How would you design cross-account or cross-project access for a backend service?</strong></summary>

#### Short answer

Use explicit trust relationships, dedicated roles, narrow permissions and strong auditing.

#### Interview answer

I would avoid shared static credentials. The calling service should assume or federate into a dedicated role in the target account or project, with permission only for required actions and resources. The trust policy should restrict who can assume it.

#### Deep dive

Cross-boundary access needs clear ownership, environment separation, naming, audit trails and revocation procedures.

#### Production angle

Cross-account access is common for central logging, shared data platforms, deployment pipelines and multi-account service integration.

#### Traps / caveats

- Do not grant broad access to an entire account unless necessary.
- Confused-deputy risks need conditions or external IDs where applicable.
- Audit both the caller and target side.

#### Optional Anki

Q: What is the safe pattern for cross-account service access?
A: Dedicated assumable roles with explicit trust, least privilege and audit.

</details>

<a id="cloud-iam-013"></a>

<details>
<summary><strong>CLOUD-IAM-013. How should Java cloud SDK clients be configured for credentials, region, retries, timeouts and pagination?</strong></summary>

#### Short answer

Use the platform credential chain intentionally, set region explicitly, configure bounded retries and timeouts, and handle paginated responses.

#### Interview answer

A Java cloud SDK client should not rely on accidental local credentials. In production, it should use workload identity or role credentials. Region should be explicit or validated. Retries should use exponential backoff with limits. Timeouts should fit request deadlines. List APIs should handle pagination.

#### Deep dive

SDK defaults are useful but not enough for every service. A backend should classify retryable errors, avoid retrying non-idempotent operations blindly and expose SDK metrics.

#### Production angle

Bad SDK configuration can create hangs, retry storms, wrong-region calls, partial list results or use of a developer credential in the wrong environment.

#### Traps / caveats

- Default timeouts may be too long for user-facing APIs.
- Pagination bugs often miss resources silently.
- SDK retries must fit the service-level latency budget.

#### Optional Anki

Q: What should be configured intentionally in Java cloud SDK clients?
A: Credentials, region, retries, timeouts and pagination.

</details>

<details>
<summary><strong>🧠 CLOUD-IAM-014. What can go wrong with default credential provider chains in Java cloud SDKs?</strong></summary>

#### Short answer

They can pick unexpected credentials from environment variables, local profiles, metadata endpoints or CI context.

#### Interview answer

Credential chains are convenient because the same code can run locally and in production. The risk is ambiguity: a service may accidentally use a developer profile, stale environment variable, overly broad CI role or metadata credential from the wrong runtime.

#### Deep dive

Teams should document expected credential sources per environment and fail fast when the active identity is not the expected one.

#### Production angle

Wrong credentials can cause access denied errors, writes to the wrong account, data exposure or difficult audit trails.

#### Traps / caveats

- Local tests may pass with a developer's broad credentials.
- Environment variables often override later credential sources.
- Metadata endpoints should not be reachable by untrusted request paths.

#### Optional Anki

Q: What is the risk of default credential chains?
A: The SDK may use unexpected credentials from the environment, profiles, CI or metadata.

</details>
