<a id="prod-k8s-001"></a>

<details>
<summary><strong>PROD-K8S-001. How do you investigate `CrashLoopBackOff`?</strong></summary>

#### Short answer

Inspect pod events, previous logs, exit code, startup config, probes, resources, secrets and recent image changes.

#### Interview answer

I start with `kubectl describe pod` style evidence: restart count, last state, exit code, reason and events. Then I inspect previous container logs, image tag/digest, command/args, environment, ConfigMaps, Secrets, missing files, database connectivity, permissions and startup probes. If the app starts then crashes, I check stack traces and JVM/container memory.

#### Deep dive

`CrashLoopBackOff` is the kubelet delaying restarts after repeated container exits. It does not say why the process exits.

#### Production angle

Mitigation may be rollback, fixing config/secrets, disabling broken startup work or routing traffic away from the bad rollout.

#### Traps / caveats

- Do not inspect only current logs; use previous logs after restarts.
- Do not confuse probe restarts with application process crashes.

#### Optional Anki

Q: What does `CrashLoopBackOff` mean?
A: Kubernetes is backing off repeated container restarts.

</details>

<a id="prod-k8s-002"></a>

<details>
<summary><strong>PROD-K8S-002. How do you investigate `OOMKilled` in Kubernetes?</strong></summary>

#### Short answer

Check container memory limit, restart events, heap settings, RSS, non-heap memory and traffic/deploy correlation.

#### Interview answer

I confirm the pod was killed for exceeding memory limits and inspect memory usage before restart, JVM `-Xmx`, direct memory, Metaspace, thread count, heap dump policy and recent deploys. I compare heap metrics to container RSS because Java heap may be stable while native memory causes the kill.

#### Deep dive

The kernel kills the container; Java may not log `OutOfMemoryError` or produce a heap dump.

#### Production angle

Fixes include leaving non-heap headroom, reducing memory growth, adjusting limits or rolling back a memory-heavy release.

#### Traps / caveats

- Do not set heap equal to container limit.
- Do not assume every `OOMKilled` is a Java heap leak.

#### Optional Anki

Q: Why can a Java pod be `OOMKilled` with stable heap?
A: Native/off-heap memory still counts against the container limit.

</details>

<a id="prod-k8s-003"></a>

<details>
<summary><strong>PROD-K8S-003. A pod is not ready, but the container is running. What do you check?</strong></summary>

#### Short answer

Check readiness probe result, application health endpoint, dependencies, startup time, config and network reachability.

#### Interview answer

I inspect readiness probe type, path, port, timeout, failure reason and application logs. Then I check whether the service can initialize required dependencies, load config/secrets, connect to database/cache, expose the correct management port and complete warmup. I also verify the probe is not too strict or too expensive.

#### Deep dive

Running means the process exists; ready means Kubernetes should route traffic to it.

#### Production angle

Bad readiness prevents traffic, causes stuck rollouts and can reduce capacity during incidents.

#### Traps / caveats

- Do not put unstable optional dependencies in readiness unless they are required for serving.
- Do not expose the wrong port/path for the probe.

#### Optional Anki

Q: What does readiness control?
A: Whether the pod receives traffic.

</details>

<a id="prod-k8s-004"></a>

<details>
<summary><strong>PROD-K8S-004. A liveness probe keeps restarting a slow-starting application. What do you change?</strong></summary>

#### Short answer

Add or tune a startup probe, increase initial delay/failure threshold, and make liveness check only process health.

#### Interview answer

If startup is slow, liveness should not kill the app before it can initialize. I would add a startup probe or tune initial delay, timeout, period and failure threshold. I also check JVM warmup, migrations, dependency startup checks and whether readiness rather than liveness should represent dependency availability.

#### Deep dive

Liveness answers "should this process be restarted?" not "is this service ready for production traffic?"

#### Production angle

Misconfigured liveness probes can create a self-inflicted outage by restarting every pod under load or during cold start.

#### Traps / caveats

- Do not make liveness depend on a flaky database.
- Do not hide genuine deadlocks by making liveness too loose.

#### Optional Anki

Q: What Kubernetes probe protects slow startup?
A: Startup probe.

</details>

<a id="prod-k8s-005"></a>

<details>
<summary><strong>PROD-K8S-005. A readiness probe fails only under load. What does that suggest?</strong></summary>

#### Short answer

The health endpoint or required dependency may be starved, slow or competing with user traffic.

#### Interview answer

I check whether readiness uses the same thread pool, connection pool or dependency path as normal requests. Under load, the probe can fail because servlet threads are exhausted, the management endpoint waits for database/cache, CPU is throttled, GC pauses occur or the probe timeout is too low. I compare readiness failures with p99 latency and saturation metrics.

#### Deep dive

Readiness failing under load may be valid if the pod cannot serve traffic, but it can also cause capacity oscillation if it removes pods too aggressively.

#### Production angle

Probe behavior affects load balancing, rolling updates and incident capacity.

#### Traps / caveats

- Do not let readiness checks create extra database load during overload.
- Do not ignore readiness flapping; it can amplify traffic on remaining pods.

#### Optional Anki

Q: What can readiness flapping cause?
A: Capacity loss and traffic concentration on remaining pods.

</details>

<a id="prod-k8s-006"></a>

<details>
<summary><strong>PROD-K8S-006. A new deployment receives no traffic. What Kubernetes resources do you inspect?</strong></summary>

#### Short answer

Inspect Deployment, ReplicaSet, pods, readiness, labels/selectors, Service, Endpoints/EndpointSlices and Ingress/Gateway routing.

#### Interview answer

I verify pods are running and ready, then check Service selectors match pod labels and endpoints exist. I inspect namespace, port names/numbers, targetPort, readiness gates, Ingress/Gateway rules, service mesh routing, network policy and rollout strategy. I also check whether traffic is pinned to old pods by canary or sticky routing rules.

#### Deep dive

Kubernetes traffic depends heavily on labels and selectors. A small label mismatch can produce healthy pods with zero traffic.

#### Production angle

Post-deploy verification should confirm real traffic reaches the new version, not only that pods exist.

#### Traps / caveats

- Do not assume Deployment success means Service routing works.
- Do not forget namespace mismatches.

#### Optional Anki

Q: What Kubernetes object lists actual Service backends?
A: EndpointSlice or Endpoints.

</details>

<a id="prod-k8s-007"></a>

<details>
<summary><strong>PROD-K8S-007. A rollout causes intermittent errors. How do you compare old and new pods?</strong></summary>

#### Short answer

Compare version, image digest, config, env, labels, resources, logs, metrics, traces and dependency behavior by pod.

#### Interview answer

I split telemetry by pod, version and image digest. Then I compare effective config, feature flags, secrets, resource limits, readiness, JVM flags, dependency errors, request paths and error classes between old and new pods. If only new pods fail, rollback or pause rollout is likely. If both fail, the rollout may have triggered shared state pressure.

#### Deep dive

Intermittent errors during rollout often come from mixed versions, schema incompatibility, cache state, sticky sessions or only some pods having bad config.

#### Production angle

Canary and blue/green strategies only work when observability can compare versions cleanly.

#### Traps / caveats

- Do not aggregate old and new pods into one metric.
- Do not use mutable image tags that make version comparison ambiguous.

#### Optional Anki

Q: What dimension should post-deploy metrics include?
A: Application version or image digest.

</details>

<a id="prod-k8s-008"></a>

<details>
<summary><strong>PROD-K8S-008. A config or secret change breaks startup. How do you diagnose it?</strong></summary>

#### Short answer

Compare effective config, secret versions, mount/env behavior, validation errors, pod events and application startup logs.

#### Interview answer

I check the failing pod logs and events, then compare the config/secret version against the previous working deployment. I verify key names, environment-variable mapping, mounted paths, file permissions, secret rotation timing, base64 content mistakes, profile selection and Spring Boot config binding/validation errors. I also check whether pods need restart to pick up changes.

#### Deep dive

Config and secret changes can break production without code deployment, so audit and effective config visibility matter.

#### Production angle

Mitigation may be reverting the config/secret, rolling back pods, restoring old credentials or enabling fail-fast validation in future.

#### Traps / caveats

- Do not print secret values into incident channels.
- Do not assume mounted and environment-based config update the same way.

#### Optional Anki

Q: Why validate config at startup?
A: To fail clearly before serving broken behavior.

</details>

<a id="prod-k8s-009"></a>

<details>
<summary><strong>PROD-K8S-009. A pod cannot pull an image. What do you check?</strong></summary>

#### Short answer

Check image name/tag/digest, registry access, imagePullSecrets, credentials, network, policy and architecture.

#### Interview answer

I inspect pod events for `ImagePullBackOff` or pull errors. Then I verify the image reference exists, tag is correct, digest is available, registry credentials are valid, `imagePullSecrets` are attached, network/proxy access works, admission policy allows the image, and node architecture matches the image.

#### Deep dive

Mutable tags and deleted images can break rollback or rollout even if the application code is fine.

#### Production angle

Release artifacts should be immutable, retained and pullable by the cluster before deployment.

#### Traps / caveats

- Do not rely on `latest` in production.
- Do not forget private registry credentials in the target namespace.

#### Optional Anki

Q: What Kubernetes secret often fixes private image pulls?
A: `imagePullSecrets`.

</details>

<a id="prod-k8s-010"></a>

<details>
<summary><strong>PROD-K8S-010. Requests fail only between pods inside the cluster. What do you inspect?</strong></summary>

#### Short answer

Check Service DNS, endpoints, NetworkPolicy, ports, mTLS/service mesh, sidecars, kube-proxy/CNI and pod readiness.

#### Interview answer

I compare failing source and destination pods, then test DNS resolution, Service name, port and endpoints. I inspect NetworkPolicies, service mesh authorization/mTLS, sidecar health, readiness, namespace, labels, CNI issues, kube-proxy behavior and whether destination pods listen on the expected interface and port.

#### Deep dive

Internal failures can be caused by policy or routing even when both applications are individually healthy.

#### Production angle

Platform and app teams need shared evidence: source, destination, service, port, namespace and error class.

#### Traps / caveats

- Do not debug only from your laptop; test from inside the cluster.
- Do not forget that readiness changes Service endpoints.

#### Optional Anki

Q: What controls which pods a Service routes to?
A: Selector labels and EndpointSlices.

</details>

<a id="prod-k8s-011"></a>

<details>
<summary><strong>PROD-K8S-011. How do resource requests and limits affect throttling, scheduling and OOM behavior?</strong></summary>

#### Short answer

Requests affect scheduling; memory limits can kill containers; CPU limits can throttle them.

#### Interview answer

CPU and memory requests tell the scheduler how much capacity to reserve. Memory limits are enforced by killing containers that exceed them. CPU limits usually throttle CPU rather than killing the container. For Java services, bad settings can cause slow pods, GC pressure, `OOMKilled` restarts, HPA surprises and noisy-neighbor issues.

#### Deep dive

CPU throttling can increase latency even when the JVM is otherwise healthy. Memory limits must include heap and non-heap memory.

#### Production angle

Resource settings are production behavior, not just infrastructure metadata.

#### Traps / caveats

- Do not set Java heap equal to the pod memory limit.
- Do not ignore CPU throttling when debugging p99 latency.

#### Optional Anki

Q: What happens when a container exceeds memory limit?
A: It can be killed by the kernel/container runtime.

</details>

<a id="prod-k8s-012"></a>

<details>
<summary><strong>🧠 PROD-K8S-012. How can misconfigured probes create cascading failures?</strong></summary>

#### Short answer

Bad probes can remove or restart healthy-enough pods, reducing capacity and overloading the remaining pods.

#### Interview answer

If readiness checks depend on overloaded dependencies, pods may flap out of service during peak load. Remaining pods receive more traffic and fail too. If liveness checks restart slow or overloaded pods, the system loses warm capacity and creates more startup load. I check probe failure timing against traffic, dependency load and rollout events.

#### Deep dive

Probe configuration should match semantics: liveness for unrecoverable process failure, readiness for traffic eligibility, startup for slow initialization.

#### Production angle

Probe incidents are often self-inflicted reliability failures and should be tested under realistic load.

#### Traps / caveats

- Do not put expensive dependency checks in liveness.
- Do not let probe timeouts be much tighter than normal service behavior without reason.

#### Optional Anki

Q: Why can readiness flapping cascade?
A: It removes capacity and overloads remaining pods.

</details>

<a id="prod-k8s-013"></a>

<details>
<summary><strong>PROD-K8S-013. A rollout runs mixed application versions and contract errors appear. What do you check?</strong></summary>

#### Short answer

Check backward compatibility across API payloads, database schema, Kafka events, caches and feature flags.

#### Interview answer

I verify whether old and new versions can run at the same time. I check API request/response compatibility, database expand-and-contract state, new required columns, enum values, JSON fields, Kafka schema compatibility, cache key/value versions and feature flags. I also inspect whether clients, consumers and background jobs were upgraded in a safe order.

#### Deep dive

Rolling deployments create a period where both versions are live. Any incompatible assumption can fail only during rollout.

#### Production angle

Mitigation may be pausing rollout, disabling the new behavior, restoring compatibility or rolling forward with a compatibility fix.

#### Traps / caveats

- Do not require a new field before all producers or clients send it.
- Do not drop old columns or event fields while old code still runs.

#### Optional Anki

Q: What must be true for safe rolling deployments?
A: Old and new versions must be compatible while both run.

</details>
