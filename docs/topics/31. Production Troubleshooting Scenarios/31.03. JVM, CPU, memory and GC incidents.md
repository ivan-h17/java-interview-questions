# JVM, CPU, memory and GC incidents

---

<a id="prod-jvm-001"></a>

<details>
<summary><strong>PROD-JVM-001. A service has 100% CPU usage. How do you investigate?</strong></summary>

#### Short answer

Check whether CPU is useful work, retries, GC, JIT, spinning, profiling hotspots or container throttling.

#### Interview answer

I first correlate CPU with traffic, throughput, latency and errors. Then I identify hot threads, map OS thread IDs to Java stacks or capture a short CPU profile/JFR. I also check GC activity, allocation rate, compiler activity, logging storms, serialization, compression, regex, retry loops and recent deployments.

#### Deep dive

High CPU is not automatically bad if throughput increased proportionally. It is bad when latency/errors rise, throughput drops or CPU is wasted on retries, spinning or GC.

#### Production angle

If impact is high, mitigation may be rollback, scaling, throttling traffic or disabling the hot feature while preserving profile evidence.

#### Traps / caveats

- Do not profile only one idle instance.
- Do not assume CPU saturation if Kubernetes CPU throttling is the actual problem.

#### Optional Anki

Q: What evidence helps explain 100% CPU in Java?
A: Hot thread stacks, CPU profile or JFR.

</details>

<a id="prod-jvm-002"></a>

<details>
<summary><strong>PROD-JVM-002. CPU is high, but request throughput is low. What could be happening?</strong></summary>

#### Short answer

The service may be burning CPU on retries, GC, lock contention, spinning, serialization, logging, JIT or failed work.

#### Interview answer

I compare accepted traffic, completed throughput, errors and retry attempts. High CPU with low useful throughput often means the app is repeatedly failing, retrying, polling, logging exceptions, allocating heavily, compressing large payloads or stuck in a hot loop. Profiles and logs show whether CPU belongs to business logic or overhead.

#### Deep dive

Throughput can also be low because all CPU is spent handling timeouts, authentication failures or failed downstream calls that never complete useful business work.

#### Production angle

The right mitigation may be reducing load, disabling retries, opening a circuit breaker or rolling back, not just adding CPUs.

#### Traps / caveats

- Do not optimize a hot stack before checking whether it is caused by an incident pattern.
- Do not ignore retry-attempt volume.

#### Optional Anki

Q: High CPU plus low throughput often means what?
A: CPU is being spent on non-useful or failed work.

</details>

<a id="prod-jvm-003"></a>

<details>
<summary><strong>PROD-JVM-003. CPU increased after deployment without a traffic increase. What evidence do you collect?</strong></summary>

#### Short answer

Compare old and new versions using CPU profiles, allocation rate, GC, request mix, logs, feature flags and dependency behavior.

#### Interview answer

I compare CPU per request, latency, error rate and throughput between old and new pods under similar traffic. Then I collect a short CPU profile or JFR from both versions, inspect allocation and GC metrics, check exception/log volume, payload sizes, serialization, new validation, caching changes, feature flags and dependency retries.

#### Deep dive

CPU per request is often more useful than total CPU because total CPU changes with traffic, scaling and throttling.

#### Production angle

If canary data shows only the new version is expensive, rollback or disabling the feature is usually faster than tuning during the incident.

#### Traps / caveats

- Do not compare profiles from different traffic mixes.
- Do not ignore configuration changes shipped with the deployment.

#### Optional Anki

Q: What metric normalizes post-deploy CPU changes?
A: CPU per request or per unit of work.

</details>

<a id="prod-jvm-004"></a>

<details>
<summary><strong>PROD-JVM-004. A service is running out of heap memory. What evidence do you collect?</strong></summary>

#### Short answer

Collect heap usage trend, GC logs, allocation rate, live set, histograms or dumps, traffic and recent changes.

#### Interview answer

I check whether heap grows between GCs, whether old generation remains high after GC, and whether allocation rate changed. I inspect GC logs, memory metrics, object histograms, JFR allocation events and, if safe, a heap dump. I correlate with traffic, payload size, cache size, batch jobs, recent deploys and data changes.

#### Deep dive

Heap pressure may be a leak, normal cache growth, too-small heap, high allocation churn, large payload buffering or a workload change.

#### Production angle

A heap dump can contain sensitive data and can pause or destabilize a service, so collection needs a safe path.

#### Traps / caveats

- Do not call every memory increase a leak.
- Do not rely only on a heap dump for short-lived allocation churn.

#### Optional Anki

Q: What shows retained heap growth?
A: Heap used after full/major GC increasing over time.

</details>

<a id="prod-jvm-005"></a>

<details>
<summary><strong>PROD-JVM-005. A service has growing native memory usage. What would you check?</strong></summary>

#### Short answer

Check RSS, cgroup memory, direct buffers, Netty, thread count, Metaspace, Code Cache, mmap and Native Memory Tracking.

#### Interview answer

I confirm that process RSS or container memory is growing while Java heap is stable. Then I inspect direct buffer usage, Netty allocator metrics, thread count and stack size, Metaspace/class loading, Code Cache, JNI/native libraries, memory-mapped files and NMT if enabled. I also check container memory limits and OOM events.

#### Deep dive

Native memory is outside the Java heap but still counts against the process and container limit.

#### Production angle

Container OOM kills may happen without a Java `OutOfMemoryError`, so platform events matter.

#### Traps / caveats

- Heap dump alone cannot explain most native memory growth.
- NMT must often be enabled before the incident to be useful.

#### Optional Anki

Q: Stable heap but growing RSS suggests what?
A: Native or off-heap memory growth.

</details>

<a id="prod-jvm-006"></a>

<details>
<summary><strong>PROD-JVM-006. GC pauses increased after deployment. What would you inspect?</strong></summary>

#### Short answer

Inspect allocation rate, live set, object churn, heap sizing, GC logs, traffic mix and code changes.

#### Interview answer

I compare old and new versions for allocation rate, old-gen occupancy, pause causes, Full GC frequency, heap usage after GC, object lifetime and request payload mix. Then I inspect code changes around DTO mapping, JSON processing, logging, caching, batch processing, large collections and buffering. JFR allocation events can identify new allocation hotspots.

#### Deep dive

GC pauses can increase because the app allocates more, retains more, has less effective heap headroom or runs in a tighter container limit.

#### Production angle

Rollback may be the safest mitigation if a release clearly increased GC and user latency.

#### Traps / caveats

- Do not tune GC flags before understanding allocation and retention.
- Do not compare GC behavior without similar traffic and heap settings.

#### Optional Anki

Q: First code-level suspect when GC increases after deploy?
A: Increased allocation or retention.

</details>

<a id="prod-jvm-007"></a>

<details>
<summary><strong>PROD-JVM-007. Full GC is happening frequently. What are likely causes?</strong></summary>

#### Short answer

Likely causes are high live set, memory leak, undersized heap, humongous allocations, metadata pressure or explicit GC.

#### Interview answer

I check GC logs for trigger causes, heap occupancy before and after GC, old-gen growth, allocation rate, humongous object allocation, Metaspace usage and whether `System.gc()` is called. Frequent Full GC usually means the collector cannot reclaim enough memory or is forced into expensive collection.

#### Deep dive

If heap after Full GC remains high and rising, suspect retained-memory growth. If it drops but quickly fills again, suspect high allocation rate or insufficient heap for workload.

#### Production angle

Frequent Full GC can create request timeouts, health-check failures and cascading retries.

#### Traps / caveats

- Do not just increase heap without checking container memory headroom.
- Do not assume Full GC is always a leak.

#### Optional Anki

Q: What does high heap after Full GC suggest?
A: High live set or retained-memory leak.

</details>

<a id="prod-jvm-008"></a>

<details>
<summary><strong>PROD-JVM-008. A Java process is killed by the container OOM killer. How do you investigate?</strong></summary>

#### Short answer

Check Kubernetes/container events, memory limit, RSS, heap settings, native memory, recent growth and whether Java saw an OOME.

#### Interview answer

I inspect pod events, restart reason, exit code, cgroup memory usage, container limit, JVM heap settings, direct memory, thread count, Metaspace, Code Cache and recent memory trend. I check whether the process produced heap dumps or `OutOfMemoryError` logs; often it does not because the kernel kills the process externally.

#### Deep dive

`-Xmx` must leave room for non-heap memory, thread stacks, direct buffers, JVM internals, native libraries and the OS/container overhead.

#### Production angle

Mitigation may be reducing heap, increasing memory limit, fixing native memory growth, reducing thread count or rolling back a memory-heavy release.

#### Traps / caveats

- Do not set `-Xmx` equal to the container memory limit.
- Do not look only at Java heap metrics.

#### Optional Anki

Q: Can `OOMKilled` happen without Java `OutOfMemoryError`?
A: Yes. The container runtime/kernel can kill the process.

</details>

<a id="prod-jvm-009"></a>

<details>
<summary><strong>PROD-JVM-009. How do you use thread dumps during a production incident?</strong></summary>

#### Short answer

Take several dumps over time and inspect thread states, repeated stacks, locks, pool workers and blocked dependencies.

#### Interview answer

I collect multiple thread dumps a few seconds apart from the affected instance. Then I look at request threads, executor workers, scheduler threads, blocked or waiting states, lock owners, database or HTTP waits, deadlock reports and repeated stack traces. If CPU is high, I map hot OS threads to Java thread IDs.

#### Deep dive

One dump is a snapshot; several dumps show whether threads are progressing or stuck.

#### Production angle

Thread dumps are low-cost compared with heap dumps and often explain hangs, pool exhaustion and deadlocks quickly.

#### Traps / caveats

- Do not assume `WAITING` always means a bug; many worker threads wait normally.
- Do not collect dumps from only healthy pods.

#### Optional Anki

Q: Why take multiple thread dumps?
A: To see whether threads are moving or stuck.

</details>

<a id="prod-jvm-010"></a>

<details>
<summary><strong>PROD-JVM-010. When is it reasonable to collect a heap dump or JFR recording in production?</strong></summary>

#### Short answer

Use JFR for low-overhead runtime evidence and heap dumps only when memory diagnosis justifies the risk.

#### Interview answer

I would collect JFR for CPU, allocation, lock, GC, file I/O, socket I/O and latency investigations, usually as a short recording or preconfigured ring buffer. I collect a heap dump when retained memory or object graph analysis is needed and the service can tolerate pause, disk use and sensitive data handling.

#### Deep dive

Heap dumps can be huge, contain secrets or PII, and may pause the JVM. JFR is usually safer but still needs retention and access controls.

#### Production angle

Runbooks should define where dumps go, who may access them and how to avoid filling container disk.

#### Traps / caveats

- Do not heap-dump a critically overloaded pod without impact review.
- Do not leave diagnostic recordings unbounded.

#### Optional Anki

Q: Which is usually safer for production runtime diagnosis, JFR or heap dump?
A: JFR.

</details>

<a id="prod-jvm-011"></a>

<details>
<summary><strong>PROD-JVM-011. How can container CPU throttling look like application latency or CPU saturation?</strong></summary>

#### Short answer

CPU limits can throttle runnable Java threads, increasing latency even when application code did not change.

#### Interview answer

I check container CPU limits, throttling metrics, CPU usage relative to limit, run queue, p99 latency and GC/JIT timing. A Java service can appear slow because it is ready to run but not scheduled enough CPU. This can also stretch GC pauses, JIT warmup and request handling, especially after autoscaling or deployment.

#### Deep dive

Throttling can make CPU graphs misleading: usage may be at the limit while demand is higher than allowed.

#### Production angle

Mitigation may be raising/removing CPU limits, improving requests, scaling out, reducing concurrency or reducing work per request.

#### Traps / caveats

- Do not tune JVM code before checking throttling.
- Do not set CPU limits mechanically without observing latency impact.

#### Optional Anki

Q: What Kubernetes metric explains latency with CPU at limit?
A: CPU throttling.

</details>

<a id="prod-jvm-012"></a>

<details>
<summary><strong>🧠 PROD-JVM-012. How do you distinguish memory leak, memory pressure and normal cache growth?</strong></summary>

#### Short answer

Compare post-GC live set, object ownership, cache bounds, workload changes and whether memory stabilizes.

#### Interview answer

A leak keeps retaining objects that should be released, so post-GC memory grows over time. Memory pressure may come from higher traffic, larger payloads or too-small heap and may stabilize when load drops. Normal cache growth should be bounded, intentional, observable and evictable. I use GC trends, histograms, heap dumps, cache metrics and traffic correlation.

#### Deep dive

Caches are common false positives. The question is whether growth is expected, bounded and useful.

#### Production angle

The mitigation differs: fix references for a leak, resize resources for pressure, or tune eviction for cache growth.

#### Traps / caveats

- Do not disable a critical cache blindly under load.
- Do not call unbounded cache growth "normal."

#### Optional Anki

Q: What trend suggests a retained-memory leak?
A: Increasing heap used after GC.

</details>

<details>
<summary><strong>🧠 PROD-JVM-013. How can JVM warmup, JIT or class loading affect a recent deployment?</strong></summary>

#### Short answer

New pods can be slower while classes load, caches fill, JIT compiles hot paths and connections warm up.

#### Interview answer

I check whether latency is worst during the first minutes after startup or autoscaling. Causes include class loading, Spring initialization, lazy beans, JIT compilation, cold caches, TLS/DB connection setup and first-request code paths. JFR startup data, readiness timing and version-by-age metrics help confirm it.

#### Deep dive

Warmup is often a rollout problem: new pods receive full traffic before they can handle steady-state load.

#### Production angle

Use readiness gates, startup probes, warmup traffic, canaries, gradual rollout and capacity buffer.

#### Traps / caveats

- Do not mark pods ready before the service can serve realistic traffic.
- Do not make warmup perform irreversible business side effects.

#### Optional Anki

Q: What JVM behavior can make new pods slow?
A: JIT warmup and class loading.

</details>
