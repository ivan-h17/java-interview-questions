# Database and transaction incidents

---

<a id="prod-db-001"></a>

<details>
<summary><strong>PROD-DB-001. A SQL query suddenly becomes slow. How do you diagnose it?</strong></summary>

#### Short answer

Compare query plan, actual runtime, data volume, locks, statistics, indexes, parameters and application call pattern.

#### Interview answer

I identify the exact normalized query, parameters, affected endpoint and time of regression. Then I inspect database metrics, `pg_stat_activity`, locks, slow query logs and `EXPLAIN (ANALYZE, BUFFERS)` when safe. I compare plans before/after, check row estimates, stale statistics, data skew, missing or unused indexes, changed bind values and recent deployments or migrations.

#### Deep dive

The same SQL text can behave differently with different parameters, data distribution, cache state, plan choice or concurrent load.

#### Production angle

Mitigation may be disabling an endpoint, adding an index safely, changing query shape, rolling back code or reducing load while a permanent fix is prepared.

#### Traps / caveats

- Do not run expensive `EXPLAIN ANALYZE` on mutating queries without safety controls.
- Do not assume an existing index is usable for the current predicate.

#### Optional Anki

Q: What explains many sudden slow-query incidents?
A: Plan changes, stale stats, data skew, locks or changed parameters.

</details>

<a id="prod-db-002"></a>

<details>
<summary><strong>PROD-DB-002. A database transaction is blocked. What do you check?</strong></summary>

#### Short answer

Find the blocked query, blocking session, held locks, transaction age, application owner and rollback risk.

#### Interview answer

I use database activity and lock views to identify which session is waiting and which session blocks it. Then I inspect transaction age, current query, idle-in-transaction state, lock type, affected tables/rows, application name, pod/version and whether the blocker is safe to cancel or terminate. I also check recent migrations or batch jobs.

#### Deep dive

A transaction can block others even when its current query is idle because locks are held until commit or rollback.

#### Production angle

Killing a blocker can trigger rollback and release locks, but it can also undo important work or cause application errors.

#### Traps / caveats

- Do not terminate a session without understanding business impact.
- Do not ignore idle-in-transaction sessions.

#### Optional Anki

Q: What releases most PostgreSQL transaction locks?
A: Commit or rollback.

</details>

<a id="prod-db-003"></a>

<details>
<summary><strong>PROD-DB-003. Database connection pool usage is maxed out. What are likely causes?</strong></summary>

#### Short answer

Slow queries, long transactions, blocked transactions, leaks, too much concurrency or remote calls inside transactions.

#### Interview answer

I check active and pending pool metrics, acquisition timeout, transaction duration and database session state. Common causes are slow SQL, locks, idle-in-transaction sessions, connection leaks, oversized request concurrency, long `@Transactional` methods, batch jobs or calls to external services while holding a connection.

#### Deep dive

Pool exhaustion is often an application-level symptom of database or transaction behavior.

#### Production angle

Mitigation may be reducing concurrency, isolating expensive endpoints, cancelling safe blockers, rolling back code or adding timeouts.

#### Traps / caveats

- Do not increase pool size without database capacity review.
- Do not assume the database is slow; the app may hold connections too long.

#### Optional Anki

Q: What application mistake exhausts DB pools?
A: Holding transactions/connections while waiting on slow work.

</details>

<a id="prod-db-004"></a>

<details>
<summary><strong>PROD-DB-004. A deployment causes a sudden increase in database load. What do you inspect?</strong></summary>

#### Short answer

Inspect query count, query shape, N+1 behavior, cache hit rate, transactions, batch work and connection concurrency.

#### Interview answer

I compare old and new versions for DB QPS, slow queries, rows read/written, connection pool usage, transaction duration and cache hit rate. I look for N+1 queries, removed caching, changed fetch strategy, new indexes missing, extra validation queries, wider result sets, batch jobs starting on every pod or increased retries after failures.

#### Deep dive

Small code changes can multiply DB load: one extra query per item, one missing cache eviction or one new eager association.

#### Production angle

Rollback, feature flag disablement or temporarily reducing traffic may be needed before query optimization.

#### Traps / caveats

- Do not scale app replicas if each replica adds fixed DB load.
- Do not ignore background jobs started by deployment.

#### Optional Anki

Q: What Java ORM issue can suddenly increase DB load?
A: N+1 queries or changed fetching.

</details>

<a id="prod-db-005"></a>

<details>
<summary><strong>PROD-DB-005. An index exists, but the query is still slow. What could explain it?</strong></summary>

#### Short answer

The index may not match the predicate/order, selectivity may be low, stats may be stale, or the planner may choose another path.

#### Interview answer

I check whether the query can use the index with its predicates, operators, casts, functions and column order. Then I inspect selectivity, data skew, stale statistics, row estimate mismatch, `ORDER BY`, `LIMIT`, join order and whether the query fetches too many rows anyway. For PostgreSQL, the planner may prefer a sequential scan when it estimates that cheaper.

#### Deep dive

An index helps only when it reduces work enough and matches the access pattern.

#### Production angle

Fixes may include rewriting the query, adding a composite/partial/expression index, updating stats or changing pagination.

#### Traps / caveats

- Do not create duplicate indexes blindly.
- Do not assume a boolean or low-cardinality index is useful.

#### Optional Anki

Q: Why can PostgreSQL ignore an index?
A: It estimates another plan is cheaper for the query and data.

</details>

<a id="prod-db-006"></a>

<details>
<summary><strong>PROD-DB-006. A migration is taking too long or blocking production traffic. What do you do?</strong></summary>

#### Short answer

Assess lock impact, migration state, safety of cancellation, rollback/roll-forward path and application compatibility.

#### Interview answer

I identify the migration statement, held locks, blockers, blocked sessions and whether it has committed partial changes. If it is blocking production, I consider cancellation only after understanding rollback cost. Then I decide whether to pause deployment, roll forward with a safer migration, restore compatibility or isolate traffic. Future prevention includes timeouts, online/concurrent operations and rehearsal.

#### Deep dive

Killing a large transaction can start a long rollback. Some schema changes are not safely reversible once application versions or data changes moved forward.

#### Production angle

Migration incidents require coordination between app, database and release owners.

#### Traps / caveats

- Do not assume rollback SQL is enough after data changed.
- Do not run risky DDL without lock and statement timeouts.

#### Optional Anki

Q: What should you check before cancelling a migration?
A: Lock impact, transaction state and rollback cost.

</details>

<a id="prod-db-007"></a>

<details>
<summary><strong>PROD-DB-007. Deadlocks appear after a release. How do you investigate?</strong></summary>

#### Short answer

Inspect deadlock logs, transaction code paths, lock order, new queries, indexes and concurrency changes.

#### Interview answer

I collect database deadlock reports showing the statements and transactions involved. Then I map them to application code, endpoint/version, transaction boundaries and lock acquisition order. I check recent changes to update order, batching, `SELECT FOR UPDATE`, indexes, isolation level, retry behavior and concurrency.

#### Deep dive

Deadlocks are usually prevented by consistent lock ordering, short transactions and good indexes that avoid locking more rows than intended.

#### Production angle

Applications must handle deadlock errors with safe retries when operations are idempotent or transactionally safe.

#### Traps / caveats

- Do not retry forever without backoff.
- Do not ignore missing indexes; they can widen lock scope.

#### Optional Anki

Q: What application pattern reduces deadlocks?
A: Acquire locks in a consistent order.

</details>

<a id="prod-db-008"></a>

<details>
<summary><strong>PROD-DB-008. Read replicas return stale data. What symptoms would users see?</strong></summary>

#### Short answer

Users may not see their own writes, see old status, missing records, stale balances or inconsistent pages.

#### Interview answer

Replica lag can cause a user to create an order and then not see it, update a profile and read the old value, or observe status moving backwards. I check replica lag, read routing, session stickiness, read-after-write requirements, cache interaction and whether the affected flow should read from primary.

#### Deep dive

Asynchronous replicas trade read scale for possible staleness. The application must define where stale reads are acceptable.

#### Production angle

Critical flows like payments, permissions and order confirmation often need primary reads or explicit consistency handling.

#### Traps / caveats

- Do not hide replica lag as a cache bug without checking routing.
- Do not route all reads to replicas if read-after-write is required.

#### Optional Anki

Q: What is the classic replica-lag symptom?
A: User writes data but cannot immediately read it back.

</details>

<a id="prod-db-009"></a>

<details>
<summary><strong>PROD-DB-009. A batch job or report slows down the online application. How do you isolate it?</strong></summary>

#### Short answer

Identify shared resources, reduce batch concurrency, use replicas or separate pools, and protect OLTP traffic.

#### Interview answer

I check whether the batch job shares the same database, connection pool, tables, indexes, locks, CPU, IO or cache with online traffic. Short-term, I pause or throttle the job, reduce batch size, move it off peak or route it to a read replica if safe. Long-term, I isolate pools, schedules, tables, replicas or workloads.

#### Deep dive

Reports can cause sequential scans, large sorts, temp files, lock contention, cache pollution and high IO.

#### Production angle

Online request paths usually need priority over analytical or repair work during business hours.

#### Traps / caveats

- Do not run heavy reporting queries on the primary without capacity review.
- Do not make a batch transaction so large that rollback becomes painful.

#### Optional Anki

Q: How can batch work harm OLTP traffic?
A: It competes for DB connections, locks, CPU, IO and cache.

</details>

<a id="prod-db-010"></a>

<details>
<summary><strong>🧠 PROD-DB-010. How do you use query plans without over-trusting one `EXPLAIN` result?</strong></summary>

#### Short answer

Use plans with real parameters, actual runtime when safe, buffers, statistics and production-like data.

#### Interview answer

I treat `EXPLAIN` as evidence, not truth. I compare estimated rows with actual rows, use `EXPLAIN (ANALYZE, BUFFERS)` when safe, test representative bind values, check generic versus custom plans, and compare production data distribution. I also correlate with database metrics, locks, IO and application timing.

#### Deep dive

Planner estimates depend on statistics, parameters and cost assumptions. A plan from dev or one parameter value may not represent production.

#### Production angle

Wrong plan interpretation can lead to useless indexes or risky query rewrites during an incident.

#### Traps / caveats

- Do not run `ANALYZE` variants on mutating statements without a rollback-safe setup.
- Do not ignore row-estimate mismatches.

#### Optional Anki

Q: What is a key sign a query plan estimate is wrong?
A: Estimated rows differ greatly from actual rows.

</details>

<a id="prod-db-011"></a>

<details>
<summary><strong>🧠 PROD-DB-011. How do transaction isolation and lock scope affect incident diagnosis?</strong></summary>

#### Short answer

Isolation level and query shape determine what a transaction can see, block and retry.

#### Interview answer

I check isolation level, transaction boundaries, statements used, lock modes and whether code uses `SELECT FOR UPDATE`, unique constraints or serializable transactions. Higher isolation or wider scans can increase retries, blocking or serialization failures. Lower isolation can expose stale reads, lost-update risks or inconsistent read behavior depending on design.

#### Deep dive

The same symptom can mean different things: a blocked request, deadlock, serialization failure or stale read all involve concurrency but require different fixes.

#### Production angle

Correct diagnosis prevents dangerous fixes like lowering isolation without understanding correctness requirements.

#### Traps / caveats

- Do not treat all concurrency errors as retryable without idempotency.
- Do not widen transactions to "fix consistency" without measuring lock impact.

#### Optional Anki

Q: Why does isolation level matter in incidents?
A: It changes visibility, locking, retries and anomalies.

</details>
