# Threads, pools and resource exhaustion

---

<a id="prod-res-001"></a>

<details>
<summary><strong>PROD-RES-001. How do you investigate thread pool exhaustion?</strong></summary>

#### Short answer

Check active threads, queue depth, rejection count, task duration, thread dumps and what workers are waiting on.

#### Interview answer

I inspect pool metrics: active count, max size, queue size, completed tasks, rejected tasks and task duration. Then I take thread dumps to see whether workers are doing CPU work, waiting on database or HTTP calls, blocked on locks or stuck in the same code path. I also check recent traffic, deployments and timeout changes.

#### Deep dive

Thread pool exhaustion is usually a symptom of slow work, unbounded queues, missing timeouts, bad pool sizing or dependency saturation.

#### Production angle

Mitigation may be failing fast, reducing concurrency, disabling slow paths or adding bulkheads, not simply increasing pool size.

#### Traps / caveats

- Increasing pool size can overload the dependency workers are waiting on.
- An unbounded queue can hide exhaustion until latency becomes severe.

#### Optional Anki

Q: What two artifacts diagnose thread pool exhaustion?
A: Pool metrics and thread dumps.

</details>

<a id="prod-res-002"></a>

<details>
<summary><strong>PROD-RES-002. How do you investigate database connection pool exhaustion?</strong></summary>

#### Short answer

Check active/idle/pending connections, acquisition time, slow queries, long transactions and connection leaks.

#### Interview answer

I inspect HikariCP or pool metrics: active connections, idle connections, pending threads, acquisition latency, timeouts and leak detection logs. Then I check database activity for slow queries, blocked queries, idle-in-transaction sessions, long transactions and locks. In Java, I look for transactions around remote calls or code paths that forget to close resources.

#### Deep dive

The pool can be exhausted even when the database is healthy if application threads hold connections too long.

#### Production angle

Mitigation may be killing safe blockers, rolling back code, reducing traffic, lowering timeouts or isolating expensive endpoints.

#### Traps / caveats

- Do not just increase pool size; it can overload the database.
- Do not hold `@Transactional` boundaries around slow external calls.

#### Optional Anki

Q: What does high pending threads in a DB pool mean?
A: Requests are waiting to acquire database connections.

</details>

<a id="prod-res-003"></a>

<details>
<summary><strong>PROD-RES-003. HTTP client connection pool is exhausted. What do you check?</strong></summary>

#### Short answer

Check per-route limits, acquisition timeout, response closing, downstream latency, retries and connection leaks.

#### Interview answer

I inspect pool metrics for leased, idle and pending connections by destination. Then I check whether response bodies are consumed and closed, whether downstream latency increased, whether retries multiplied requests, and whether connection limits are too low or shared across unrelated dependencies. I also check DNS, TLS, proxy and service mesh behavior.

#### Deep dive

A full HTTP pool can be caused by slow downstream responses, leaked responses, long streaming calls, missing timeouts or too many concurrent attempts.

#### Production angle

Fixes include timeout budgets, separate pools per critical dependency, bulkheads and backpressure.

#### Traps / caveats

- Do not share one tiny pool across unrelated downstreams.
- Do not retry when the pool is already saturated.

#### Optional Anki

Q: What happens when HTTP pool acquisition has no timeout?
A: Request threads can wait indefinitely.

</details>

<a id="prod-res-004"></a>

<details>
<summary><strong>PROD-RES-004. Executor queue size is growing. What does it usually mean?</strong></summary>

#### Short answer

Work is arriving faster than workers can complete it, or workers are blocked.

#### Interview answer

I compare arrival rate, completion rate, active workers, task duration and queue age. A growing queue can mean traffic spike, slow dependency, too few workers, blocked tasks, long-running tasks, retry amplification or a downstream bottleneck. I also check whether callers time out before queued work starts.

#### Deep dive

Queue size alone is less useful than queue wait time. A short queue of old tasks may be worse than a larger queue draining quickly.

#### Production angle

Bounded queues and rejection policies make overload visible and controllable.

#### Traps / caveats

- Do not make queues unbounded to avoid rejections.
- Do not increase workers without checking the downstream bottleneck.

#### Optional Anki

Q: What does a growing executor queue indicate?
A: Arrival rate exceeds processing capacity.

</details>

<a id="prod-res-005"></a>

<details>
<summary><strong>PROD-RES-005. Requests hang but CPU is low. What resources might be exhausted?</strong></summary>

#### Short answer

Suspect threads, database connections, HTTP connections, locks, sockets, file descriptors, queues or slow downstreams.

#### Interview answer

Low CPU with hanging requests usually means waiting. I check thread dumps, servlet threads, executor pools, DB and HTTP pools, lock contention, socket/file descriptor limits, queue depth, DNS/TLS handshakes, remote service latency and missing timeouts. I also check whether upstreams have already timed out.

#### Deep dive

Resource waits often look like "nothing is happening" from CPU metrics, but thread stacks and pool metrics show where work is stuck.

#### Production angle

Mitigation requires freeing or protecting the scarce resource: timeouts, cancellation, pool isolation, load shedding or rollback.

#### Traps / caveats

- Do not treat low CPU as healthy.
- Do not restart before collecting thread and pool evidence if the issue is recurring.

#### Optional Anki

Q: Low CPU plus hung requests usually means what?
A: Waiting on scarce resources or dependencies.

</details>

<a id="prod-res-006"></a>

<details>
<summary><strong>PROD-RES-006. How do you investigate a suspected deadlock?</strong></summary>

#### Short answer

Collect thread dumps, identify blocked threads and lock owners, and distinguish JVM monitor deadlock from database deadlock.

#### Interview answer

I take multiple thread dumps and look for Java-level deadlock reports, `BLOCKED` threads, lock owner stacks and repeated waiting patterns. If the hang involves database work, I inspect `pg_locks`, blocking sessions and deadlock logs. I also check recent code changes around lock ordering, transactions and nested calls.

#### Deep dive

Not every hang is a JVM deadlock. It can be database locks, distributed waits, executor starvation or a task waiting for work submitted to the same exhausted pool.

#### Production angle

Mitigation may require terminating a safe blocker, rolling back a release, disabling a path or restarting only affected instances after evidence is captured.

#### Traps / caveats

- Do not kill blockers without understanding transaction rollback impact.
- Do not ignore lock ordering in application code.

#### Optional Anki

Q: What artifact identifies Java monitor deadlocks?
A: A Java thread dump.

</details>

<a id="prod-res-007"></a>

<details>
<summary><strong>PROD-RES-007. How do blocked threads differ from waiting or sleeping threads?</strong></summary>

#### Short answer

Blocked threads wait to enter a monitor; waiting threads wait for a signal or condition; sleeping threads pause by time.

#### Interview answer

`BLOCKED` means a thread is trying to enter a synchronized block or method and another thread owns the monitor. `WAITING` or `TIMED_WAITING` can be normal for queues, locks, joins, sleeps, park operations or I/O waits depending on stack. I interpret thread state with the stack trace and application context, not the state name alone.

#### Deep dive

Many healthy worker pools have waiting threads. The red flag is all useful workers waiting on the same scarce resource or lock.

#### Production angle

Understanding states prevents false alarms and helps find the actual owner or dependency causing the stall.

#### Traps / caveats

- Do not assume every `WAITING` thread is stuck.
- Do not ignore repeated identical blocked stacks across dumps.

#### Optional Anki

Q: What does `BLOCKED` mean in a Java thread dump?
A: Waiting to acquire a monitor lock.

</details>

<a id="prod-res-008"></a>

<details>
<summary><strong>PROD-RES-008. File descriptors or sockets are exhausted. What evidence do you collect?</strong></summary>

#### Short answer

Collect open descriptor counts, socket states, limits, connection pools, error logs and ownership by process or endpoint.

#### Interview answer

I check OS limits, process open file descriptors, socket states, per-destination connection counts, accept/connect errors and application logs like "too many open files." Then I inspect HTTP/DB client pools, leaked response bodies, long-lived connections, missing closes, high retry behavior and whether descriptors grow over time.

#### Deep dive

Sockets are file descriptors on Unix-like systems, so network leaks and file leaks can share the same limit.

#### Production angle

Mitigation can include restarting affected instances, raising limits temporarily, reducing connection churn and fixing leaks.

#### Traps / caveats

- Do not raise limits as the only fix for a leak.
- Do not create a new HTTP client per request.

#### Optional Anki

Q: What error often appears with descriptor exhaustion?
A: `Too many open files`.

</details>

<a id="prod-res-009"></a>

<details>
<summary><strong>PROD-RES-009. Scheduled jobs stop running or overlap unexpectedly. What do you inspect?</strong></summary>

#### Short answer

Check scheduler threads, locks, previous run duration, pod count, leader election, time settings and failures.

#### Interview answer

I inspect scheduler pool metrics, job start and completion logs, last successful run, run duration, exceptions, clock/timezone changes, pod restarts, deployment events and whether multiple replicas execute the same job. If jobs require singleton behavior, I check distributed locks, leader election or database advisory lock behavior.

#### Deep dive

A job can stop because the scheduler pool is exhausted, the previous run never completed, the pod restarted or a lock was left stale.

#### Production angle

Critical scheduled work needs freshness metrics and missed-run alerts, not just logs.

#### Traps / caveats

- Do not rely on in-memory locks across multiple replicas.
- Do not let fixed-rate jobs overlap if the work is not idempotent.

#### Optional Anki

Q: What should critical scheduled jobs expose?
A: Last success time, duration and result.

</details>

<a id="prod-res-010"></a>

<details>
<summary><strong>PROD-RES-010. Disk or ephemeral storage is exhausted. What evidence do you collect and how do you mitigate?</strong></summary>

#### Short answer

Check filesystem usage, logs, temp files, heap/JFR dumps, cache directories, PVCs, inode usage and container events.

#### Interview answer

I identify which filesystem is full: container writable layer, mounted volume, log directory, temp directory or node ephemeral storage. Then I check large logs, dumps, uploaded files, batch outputs, cache files, rotated log policy, inodes and recent diagnostic commands. Mitigation may be deleting safe temporary files, moving traffic, increasing storage, disabling dump generation or rolling out a fix.

#### Deep dive

Disk exhaustion can break logging, uploads, database clients, temp-file-backed sorting, TLS material loading or even pod scheduling.

#### Production angle

Diagnostic files like heap dumps can cause a second outage if written to small ephemeral storage.

#### Traps / caveats

- Do not delete unknown files during an incident without owner review.
- Do not ignore inode exhaustion; disk bytes can look available.

#### Optional Anki

Q: What diagnostic artifact can fill pod storage quickly?
A: Heap dumps or large JFR/log files.

</details>

<a id="prod-res-011"></a>

<details>
<summary><strong>PROD-RES-011. How do you decide whether to shed load, throttle or scale during resource exhaustion?</strong></summary>

#### Short answer

Scale only when the bottleneck scales; throttle producers or shed lower-priority work when shared dependencies are saturated.

#### Interview answer

I identify the scarce resource and whether adding instances increases real capacity. If CPU is the bottleneck and dependencies have headroom, scaling may help. If the database, cache, Kafka, file descriptors or downstream API is saturated, scaling the app can worsen the incident. Then I choose load shedding, rate limiting, consumer pause, feature disablement or capacity increase based on priority and safety.

#### Deep dive

The correct action depends on the constraint, not the symptom. High queue depth can mean "need more workers" or "need fewer accepted requests."

#### Production angle

A service should have a documented priority model so responders know what work can be rejected first.

#### Traps / caveats

- Do not scale Kafka consumers into an overloaded database.
- Do not throttle all traffic equally if some paths are critical.

#### Optional Anki

Q: When can scaling make an incident worse?
A: When the bottleneck is a shared downstream dependency.

</details>

<a id="prod-res-012"></a>

<details>
<summary><strong>🧠 PROD-RES-012. How do virtual threads change, but not remove, resource-exhaustion risks?</strong></summary>

#### Short answer

Virtual threads reduce platform-thread pressure, but external resources still need limits, timeouts and backpressure.

#### Interview answer

Virtual threads make blocking code cheaper in terms of Java threads, but they do not create more database connections, HTTP connections, CPU, memory or downstream capacity. A service can still overload dependencies if it starts far more concurrent calls. I would still use connection pools, semaphores, deadlines, rate limits and bulkheads.

#### Deep dive

Virtual threads shift the bottleneck from thread count to real resources like sockets, heap, database sessions and CPU.

#### Production angle

After adopting virtual threads, monitor concurrency, pool waits and downstream load carefully; old thread saturation alerts may no longer show the same risk.

#### Traps / caveats

- Do not remove connection pool limits because virtual threads are cheap.
- Do not allow unlimited per-request fan-out.

#### Optional Anki

Q: What resource risk remains with virtual threads?
A: External resource and downstream capacity exhaustion.

</details>
