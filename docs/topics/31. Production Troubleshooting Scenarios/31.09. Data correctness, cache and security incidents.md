# Data correctness, cache and security incidents

---

<a id="prod-data-001"></a>

<details>
<summary><strong>PROD-DATA-001. Users report seeing stale data. How do you investigate cache, replica and client-side causes?</strong></summary>

#### Short answer

Compare source of truth, cache value, replica lag, client cache and invalidation path for the affected record.

#### Interview answer

I identify an exact user, record and timestamp, then compare database primary, read replica, Redis/local cache, CDN/browser cache and API response. I inspect cache keys, TTLs, tenant/user dimensions, invalidation events, transaction commit timing, replica lag and whether the client is reusing stale responses.

#### Deep dive

Stale data can come from cache invalidation bugs, read replicas, event lag, frontend state, HTTP caching or inconsistent routing.

#### Production angle

Mitigation may be bypassing a cache, routing reads to primary, invalidating affected keys, pausing consumers or disabling a stale feature.

#### Traps / caveats

- Do not assume every stale-data report is a cache bug.
- Do not invalidate all cache keys if a narrow targeted invalidation is safer.

#### Optional Anki

Q: What should stale-data debugging compare first?
A: Source of truth versus served value.

</details>

<a id="prod-data-002"></a>

<details>
<summary><strong>PROD-DATA-002. Users report seeing another user's data. What do you check immediately?</strong></summary>

#### Short answer

Treat it as a serious security incident: stop exposure, check auth, tenant scoping, cache keys, sessions and logs.

#### Interview answer

I first contain the issue: disable the feature, bypass cache, roll back or block affected traffic if needed. Then I inspect authorization checks, tenant filters, cache keys, session handling, CDN/browser caching, object reuse, DTO mapping, query predicates and recent changes. I also preserve evidence and involve security/privacy owners.

#### Deep dive

Cross-user data exposure can be caused by missing tenant predicates, shared cache keys, incorrect session reuse, static mutable state or wrong CDN cache headers.

#### Production angle

This is not only a bug; it may require incident notification, audit, access review and data exposure assessment.

#### Traps / caveats

- Do not keep the feature running while looking for root cause if exposure continues.
- Do not paste sensitive user data into public incident channels.

#### Optional Anki

Q: What is the priority when users see other users' data?
A: Stop further exposure immediately.

</details>

<a id="prod-data-003"></a>

<details>
<summary><strong>PROD-DATA-003. Duplicate orders or payments are created. What do you inspect?</strong></summary>

#### Short answer

Check idempotency, retries, client behavior, transaction boundaries, unique constraints and message reprocessing.

#### Interview answer

I identify duplicate records and correlate them with request IDs, idempotency keys, payment provider IDs, Kafka event IDs and database transactions. I inspect client retries, gateway retries, timeouts after side effects, double-clicks, consumer reprocessing, missing unique constraints and whether idempotency records are written atomically with the business operation.

#### Deep dive

Duplicate side effects often happen when a request times out after the server or provider already completed the operation.

#### Production angle

Mitigation may include disabling the endpoint, enforcing idempotency, adding temporary duplicate detection and starting refund/reconciliation workflow.

#### Traps / caveats

- Do not rely only on frontend button disabling.
- Do not retry payment creation without idempotency keys.

#### Optional Anki

Q: What protects against duplicate payment creation?
A: Idempotency key plus atomic server-side enforcement.

</details>

<a id="prod-data-004"></a>

<details>
<summary><strong>PROD-DATA-004. A background job processed the wrong records. How do you assess impact?</strong></summary>

#### Short answer

Find exact job version, selection criteria, affected records, side effects, downstream propagation and repair options.

#### Interview answer

I stop or pause the job first if damage may continue. Then I inspect job logs, parameters, code version, query criteria, processed IDs, timestamps, tenant scope and output side effects. I determine whether emails, payments, events, cache updates, search indexes or downstream projections were affected and build an affected-record list.

#### Deep dive

Impact assessment needs both data-level scope and business-level consequences.

#### Production angle

Repair work should be idempotent, auditable and validated with queries before and after.

#### Traps / caveats

- Do not rerun the job before understanding why selection was wrong.
- Do not forget downstream systems that consumed bad events.

#### Optional Anki

Q: First action when a damaging job is still running?
A: Pause or stop it safely.

</details>

<a id="prod-data-005"></a>

<details>
<summary><strong>PROD-DATA-005. A cache returns data with the wrong tenant or permissions. How do you mitigate?</strong></summary>

#### Short answer

Bypass or invalidate the unsafe cache, stop exposure, fix key dimensions and verify authorization at source.

#### Interview answer

I treat wrong-tenant or wrong-permission cache data as a security/correctness incident. I disable cache reads for the affected path, invalidate affected keys or flush the cache if needed, and verify server-side authorization against the source of truth. Then I fix cache keys to include tenant, user, role, locale or permission-relevant dimensions as required.

#### Deep dive

Cache keys must represent all data dimensions that affect the value. Permissions often make shared caching unsafe.

#### Production angle

Add tests and metrics for cache key collisions, fallback paths and authorization checks after cache reads.

#### Traps / caveats

- Do not cache permission-sensitive data with only object ID as key.
- Do not rely on frontend filtering for authorization.

#### Optional Anki

Q: What causes wrong-tenant cache data?
A: Missing tenant or permission dimensions in the cache key.

</details>

<a id="prod-data-006"></a>

<details>
<summary><strong>PROD-DATA-006. Sensitive data appears in logs after an exception. How do you fix and prevent it?</strong></summary>

#### Short answer

Stop further leakage, restrict access, redact/remove stored logs if possible, rotate secrets and fix logging/serialization.

#### Interview answer

I first stop the leak by rolling back, changing log level, disabling unsafe logging or deploying redaction. Then I identify what data leaked, who could access it, retention scope and whether credentials must be rotated. Prevention includes structured logging, safe exception mappers, redaction filters, DTO `toString()` hygiene and tests for sensitive fields.

#### Deep dive

Sensitive data can leak through request bodies, exception messages, SQL parameters, stack traces, headers, tokens and generated `toString()` methods.

#### Production angle

This may require security/privacy incident handling, audit and notification depending on data and jurisdiction.

#### Traps / caveats

- Do not paste leaked data into tickets or chat.
- Do not assume deleting application logs removes copies from log pipelines and backups.

#### Optional Anki

Q: What is the first step when secrets appear in logs?
A: Stop further leakage and rotate affected secrets if needed.

</details>

<a id="prod-data-007"></a>

<details>
<summary><strong>PROD-DATA-007. A data backfill is corrupting production data. What is the response?</strong></summary>

#### Short answer

Stop the backfill, preserve evidence, identify affected rows, block further propagation and choose repair or restore.

#### Interview answer

I pause the backfill immediately and prevent additional writes if needed. Then I capture job version, parameters, affected range, audit tables, before/after values, downstream events and replicas/projections touched. The recovery plan may be targeted repair, rollback from audit data, restore to separate environment and copy back, or compensating migration.

#### Deep dive

Repair must be safer than the original backfill: idempotent, bounded, reviewed and validated.

#### Production angle

Large data repairs need owner approval, progress metrics, dry runs and post-repair reconciliation.

#### Traps / caveats

- Do not rerun the same backfill with changed parameters without a reviewed plan.
- Do not assume database rollback is possible after committed batches.

#### Optional Anki

Q: What is the first action when a backfill corrupts data?
A: Stop or pause the backfill.

</details>

<a id="prod-data-008"></a>

<details>
<summary><strong>PROD-DATA-008. A feature behaves differently for different users after rollout. What do you inspect?</strong></summary>

#### Short answer

Check feature flags, targeting, cached state, client version, tenant config, region, permissions and data differences.

#### Interview answer

I compare affected and unaffected users by feature flag state, rollout percentage, tenant, region, client version, account type, permissions, experiments, cached values and data shape. I check whether targeting is deterministic and whether backend and frontend evaluate the same conditions. I also inspect whether mixed versions or stale config created inconsistent behavior.

#### Deep dive

Different behavior can be intentional rollout or accidental split-brain behavior.

#### Production angle

Feature rollouts need dashboards by flag state and safe rollback controls.

#### Traps / caveats

- Do not treat user ID or tenant ID as safe high-cardinality metric labels without controls.
- Do not use feature flags as authorization.

#### Optional Anki

Q: What should rollout telemetry include?
A: Effective feature flag state.

</details>

<a id="prod-data-009"></a>

<details>
<summary><strong>PROD-DATA-009. A schema, API or event contract change breaks only some clients or consumers. What do you check?</strong></summary>

#### Short answer

Check backward compatibility, version skew, required fields, enum changes, serializers, generated clients and rollout order.

#### Interview answer

I identify which clients or consumers fail and compare their versions and contract expectations. Then I check whether a field became required, an enum gained an unknown value, a JSON shape changed, an API status code changed, a Kafka schema is incompatible or generated clients are strict. I also verify rollout order across producers, consumers and gateways.

#### Deep dive

Partial contract failure often appears only with old clients, lagging consumers, cached schemas or traffic pinned to older app versions.

#### Production angle

Mitigation may be restoring backward compatibility, disabling the new producer behavior, accepting both formats or rolling forward consumers.

#### Traps / caveats

- Do not remove fields before all consumers stop requiring them.
- Do not assume "optional" in one language is optional in generated clients.

#### Optional Anki

Q: What contract rule protects mixed-version systems?
A: Backward-compatible changes first.

</details>

<a id="prod-data-010"></a>

<details>
<summary><strong>🧠 PROD-DATA-010. How do you design a repair plan when bad data has already propagated downstream?</strong></summary>

#### Short answer

Define affected scope, source of truth, repair order, idempotent steps, validation, replay/rebuild needs and rollback plan.

#### Interview answer

I first determine the authoritative source and affected records. Then I map downstream systems: caches, search indexes, Kafka consumers, projections, reports, emails and external providers. The repair plan should be idempotent, batched, observable, approved and validated. It may require correcting source data, publishing compensating events, rebuilding projections or reconciling with external systems.

#### Deep dive

When bad data propagates, fixing only the primary database may leave downstream views wrong.

#### Production angle

Repair plans need business validation, audit trail and communication because they change real user-visible state.

#### Traps / caveats

- Do not replay events before knowing current handlers are safe.
- Do not overwrite newer correct data with old repaired data.

#### Optional Anki

Q: What is the first question in a data repair plan?
A: What is the source of truth and affected scope?

</details>
