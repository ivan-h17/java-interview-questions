# 41.07. Observer, events and asynchronous notification

---

<a id="dp-obs-001"></a>

<details>
<summary><strong>DP-OBS-001. What is the Observer pattern?</strong></summary>

#### Short answer

Observer lets one object notify interested observers when its state or an event changes.

#### Interview answer

The subject keeps a list of observers and notifies them when something happens. Observers react without the subject knowing their concrete classes.

In backend code, the idea appears in domain events, Spring application events, listener callbacks and some reactive APIs.

#### Deep dive

Observer decouples the publisher from specific handlers, but it does not automatically solve reliability, ordering, retries or transaction boundaries.

#### Production angle

Use Observer carefully for in-process side effects such as cache invalidation, metrics or local workflow hooks. For cross-service communication, messaging patterns are usually needed.

#### Traps / caveats

- Synchronous observers can make the publisher slow or fragile.
- Asynchronous observers can hide failures.
- Listener registration can cause memory leaks if not cleaned up.

#### Optional Anki

Q: Observer pattern intent?
A: Notify interested observers when a subject changes or emits an event.

</details>

<a id="dp-obs-002"></a>

<details>
<summary><strong>DP-OBS-002. Why are `java.util.Observer` and `Observable` deprecated, and what replaces them?</strong></summary>

#### Short answer

They are deprecated because their design is limited and inflexible; modern code uses listeners, callbacks, reactive streams, property change support, or framework event systems.

#### Interview answer

`Observable` is a class rather than an interface, which limits composition. Its API is old, not strongly typed, and does not model modern concurrency, backpressure or error handling well.

Modern Java code usually uses explicit listener interfaces, `Flow`, reactive libraries, Spring events, message brokers or domain-specific callback contracts.

#### Deep dive

The replacement depends on the scope. In-process UI-style notifications differ from backend integration events or reactive stream processing.

#### Production angle

For backend services, choose a mechanism that makes failure, retries and transactions explicit.

#### Traps / caveats

- Do not use deprecated APIs in new designs.
- Do not replace them blindly with async messaging for local events.
- Reactive APIs are not just Observer with different names; they add stream semantics.

#### Optional Anki

Q: Main design issue with `Observable`?
A: It is a concrete class with an old, limited API.

</details>

<a id="dp-obs-003"></a>

<details>
<summary><strong>DP-OBS-003. What is the difference between Observer, publish-subscribe and event-driven architecture?</strong></summary>

#### Short answer

Observer is usually direct subject-to-observer notification, pub-sub introduces an intermediary channel, and event-driven architecture uses events as an architectural communication style.

#### Interview answer

In Observer, the subject often knows and calls its observers in-process. In publish-subscribe, publishers send messages to a topic or broker and subscribers receive them without direct registration with the publisher.

Event-driven architecture is broader: services communicate by events, with concerns like contracts, ordering, retries, idempotency and observability.

#### Deep dive

The same business idea, "something happened", can be represented as an in-process event, domain event, integration event or broker message. The reliability requirements differ.

#### Production angle

Do not use in-process Observer when you need durable cross-service delivery. Use messaging, outbox and idempotent consumers.

#### Traps / caveats

- Observer is not automatically asynchronous.
- Pub-sub is not automatically reliable.
- Events should represent facts, not hidden RPC commands.

#### Optional Anki

Q: Observer vs pub-sub?
A: Observer is often direct notification; pub-sub uses an intermediary channel.

</details>

<a id="dp-obs-004"></a>

<details>
<summary><strong>DP-OBS-004. How does Observer relate to Spring application events?</strong></summary>

#### Short answer

Spring application events are an in-process event/listener mechanism based on the Observer idea.

#### Interview answer

A Spring bean can publish an event, and methods annotated with `@EventListener` or listener beans can handle it. The publisher does not need to call each handler directly.

This is useful for local decoupling inside one application context.

#### Deep dive

By default, Spring application events are synchronous unless configured with async execution. Transactional event listeners can defer handling to transaction phases.

#### Production angle

Spring events are not durable messaging. If the process crashes after publishing an in-memory event, a handler may not run.

#### Traps / caveats

- Do not use Spring events as a replacement for Kafka or an outbox when durability matters.
- Synchronous listeners participate in the caller's latency and failure path.
- Async listeners need error handling and context propagation.

#### Optional Anki

Q: Are Spring application events durable messages?
A: No. They are in-process events unless combined with durable mechanisms.

</details>

<a id="dp-obs-005"></a>

<details>
<summary><strong>DP-OBS-005. How does Observer relate to messaging systems like Kafka?</strong></summary>

#### Short answer

Kafka implements durable asynchronous publish-subscribe/log-based messaging, not just in-process Observer.

#### Interview answer

Observer and Kafka both decouple producers from consumers, but Kafka adds a brokered log with partitions, offsets, retention, replay and consumer groups. Producers do not call observers directly; consumers read records from topics.

The design must handle serialization, ordering, idempotency, retries and schema evolution.

#### Deep dive

Kafka is an architectural infrastructure choice. Observer is an object-level pattern. They can express related ideas but operate at different levels.

#### Production angle

Use Kafka when consumers are separate services, delivery must survive process failure, or events must be replayable.

#### Traps / caveats

- Kafka does not make handlers idempotent automatically.
- Ordering is per partition, not global.
- Do not publish events before database commit without a reliability pattern.

#### Optional Anki

Q: Main difference between Observer and Kafka?
A: Kafka is durable brokered messaging; Observer is usually direct in-process notification.

</details>

<a id="dp-obs-006"></a>

<details>
<summary><strong>DP-OBS-006. What are the risks of synchronous observer notification?</strong></summary>

#### Short answer

Synchronous observers add latency and make observer failures affect the publisher.

#### Interview answer

If the subject calls every observer inline, one slow handler slows the main operation. One failing handler may break the whole request or transaction unless errors are isolated deliberately.

This is acceptable for some validation or local hooks, but dangerous for optional side effects.

#### Deep dive

Synchronous notification also creates hidden coupling because the publisher's response time and failure behavior depend on all listeners.

#### Production angle

Metrics, emails, cache updates or audit writes should have explicit failure policy. Do they block the user request or not?

#### Traps / caveats

- Do not add slow I/O to synchronous listeners casually.
- Listener order can become a hidden dependency.
- Exceptions should be handled according to business criticality.

#### Optional Anki

Q: Main risk of synchronous observers?
A: Listener latency and failures affect the publisher.

</details>

<a id="dp-obs-007"></a>

<details>
<summary><strong>DP-OBS-007. What are the risks of asynchronous observer notification?</strong></summary>

#### Short answer

Asynchronous observers decouple latency but introduce failure visibility, ordering, context propagation and consistency problems.

#### Interview answer

When observers run later or on another thread, the publisher may succeed while a handler fails. That can be correct, but only if retries, dead letters, logging and idempotency are designed.

Thread-local context such as security, trace IDs and transactions may not be available automatically.

#### Deep dive

Async notification changes semantics. The caller can no longer assume the side effect completed before the response.

#### Production angle

Use explicit queues, outbox tables or executor policies when the side effect matters. Monitor handler failures separately.

#### Traps / caveats

- Do not lose exceptions in background threads.
- Do not rely on original transaction context after commit.
- Make handlers idempotent if retries are possible.

#### Optional Anki

Q: Async observer trade-off?
A: Lower caller latency, but harder failure handling and consistency.

</details>

<a id="dp-obs-008"></a>

<details>
<summary><strong>DP-OBS-008. How would you design event notification with retries and failure isolation?</strong></summary>

#### Short answer

Use explicit event records, durable publication when needed, idempotent handlers, retry policy, dead-letter handling and observability.

#### Interview answer

First decide whether the event is local or integration-level. For durable integration, write the business change and event to the database in one transaction using an outbox. A publisher sends events to the broker. Consumers process idempotently, retry transient failures and send poison messages to a dead-letter path.

Each handler should fail independently unless the side effect is required for the original operation.

#### Deep dive

Retries need classification: validation errors should not be retried forever; network errors may be retried with backoff.

#### Production angle

Track event lag, retry counts, handler errors, dead-letter volume and correlation IDs.

#### Traps / caveats

- Do not retry non-idempotent handlers without protection.
- Do not publish integration events before commit.
- Do not let one optional handler block all handlers.

#### Optional Anki

Q: Key reliability pieces for event notification?
A: Durable publication, idempotent handlers, retries, dead letters and monitoring.

</details>
