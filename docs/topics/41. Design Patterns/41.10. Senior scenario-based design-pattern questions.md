# 41.10. Senior scenario-based design-pattern questions

---

<a id="dp-scen-001"></a>

<details>
<summary><strong>DP-SCEN-001. You have a large `switch` choosing payment providers. Which pattern would you consider and why?</strong></summary>

#### Short answer

Consider Strategy, possibly with Adapter per provider, if providers have independent behavior and change often.

#### Interview answer

I would first check whether the switch is large, repeated or changing frequently. If yes, define a `PaymentStrategy` or `PaymentProvider` interface and move provider-specific logic into implementations. Each implementation may also act as an Adapter around a vendor SDK.

The orchestrator selects a strategy by payment method, country, tenant or feature flag.

#### Deep dive

If the switch is small and stable, keeping it may be clearer. Pattern use is justified when it reduces future change risk.

#### Production angle

Payment routing must fail clearly when no provider matches, log selection decisions, and protect idempotency.

#### Traps / caveats

- Do not silently fall back to the wrong provider.
- Keep common transaction and audit behavior outside provider-specific code where appropriate.
- Test each provider contract.

#### Optional Anki

Q: Pattern for many interchangeable payment providers?
A: Strategy, often with Adapter around each external provider.

</details>

<a id="dp-scen-002"></a>

<details>
<summary><strong>DP-SCEN-002. You need to support multiple notification channels: email, SMS and push. Which patterns might fit?</strong></summary>

#### Short answer

Strategy fits channel-specific sending, Adapter fits external providers, and Command or events can fit asynchronous delivery.

#### Interview answer

Each channel can implement `NotificationSender`. Provider-specific clients are hidden behind adapters. If notifications are sent asynchronously, represent send requests as commands or events and process them through a queue.

The design should separate channel selection, message rendering and delivery.

#### Deep dive

If one business event fans out to several channels, Observer or pub-sub can coordinate handlers, but delivery reliability needs explicit retry and idempotency.

#### Production angle

Notifications need templates, rate limits, provider failures, retries, deduplication and user preferences.

#### Traps / caveats

- Do not make one generic sender full of channel-specific conditionals.
- Avoid retrying non-idempotent sends without deduplication.
- Keep provider DTOs out of the domain model.

#### Optional Anki

Q: Patterns for notification channels?
A: Strategy for channel behavior, Adapter for providers, Command/events for async delivery.

</details>

<a id="dp-scen-003"></a>

<details>
<summary><strong>DP-SCEN-003. You need to build immutable request objects with many optional fields. Which pattern would you use?</strong></summary>

#### Short answer

Use Builder when many optional fields make constructors unreadable; use records or static factories for simpler cases.

#### Interview answer

For a complex immutable request, Builder gives named setters, validation and a final immutable object. Required fields should be clear, and `build()` should reject invalid combinations.

If the request has only a few fields, a record or constructor may be simpler.

#### Deep dive

Builders work well in tests and integration clients, but they can hide missing required fields if not designed carefully.

#### Production angle

Immutable request objects are safer for async processing, caching and logging because they do not change after creation.

#### Traps / caveats

- Defensively copy mutable collections.
- Do not perform slow external validation in `build()`.
- Avoid giant request objects that mix unrelated concerns.

#### Optional Anki

Q: Pattern for many optional constructor fields?
A: Builder.

</details>

<a id="dp-scen-004"></a>

<details>
<summary><strong>DP-SCEN-004. You need to add logging, metrics and retries around service calls. Which patterns might help?</strong></summary>

#### Short answer

Decorator, Proxy/AOP and Chain can help, depending on whether behavior should be explicit, framework-driven or ordered.

#### Interview answer

For explicit wrapping around a client, Decorator is often clear: `MetricsClient` wraps `RetryingClient` wraps the real client. For uniform cross-cutting behavior, Spring AOP proxies can apply metrics or transactions. A Chain fits ordered processing steps such as request filters.

Retries must be designed around idempotency.

#### Deep dive

Decorator order matters. Metrics outside retries measure total retry time; metrics inside retries measure individual attempts.

#### Production angle

Cross-cutting behavior should emit useful logs and metrics without hiding business failures.

#### Traps / caveats

- Do not retry non-idempotent operations blindly.
- Do not swallow exceptions in wrappers.
- Avoid broad AOP pointcuts that change unrelated code.

#### Optional Anki

Q: Explicit wrapper pattern for metrics/retry?
A: Decorator.

</details>

<a id="dp-scen-005"></a>

<details>
<summary><strong>DP-SCEN-005. You need to adapt a third-party API to your domain interface. Which pattern would you use?</strong></summary>

#### Short answer

Use Adapter, often as part of an anti-corruption boundary.

#### Interview answer

Define a domain-facing interface such as `TaxCalculator` or `PaymentGateway`. Implement it with an adapter that calls the third-party API, maps requests/responses, translates errors and hides vendor-specific types.

The domain code should not depend on the provider's DTOs or exceptions.

#### Deep dive

For a large external model mismatch, the adapter may be part of a broader anti-corruption layer with mapping, validation and translation.

#### Production angle

Adapters make provider replacement and failure handling safer, and they reduce blast radius when a vendor API changes.

#### Traps / caveats

- Do not leak vendor status codes across the whole codebase.
- Preserve enough diagnostic information for support.
- Test provider contracts with sandbox or contract tests.

#### Optional Anki

Q: Pattern for wrapping incompatible third-party API?
A: Adapter.

</details>

<a id="dp-scen-006"></a>

<details>
<summary><strong>DP-SCEN-006. You need to execute a sequence of validators where each validator may stop the flow. Which pattern fits?</strong></summary>

#### Short answer

Chain of Responsibility fits ordered validators that can continue or stop processing.

#### Interview answer

Each validator handles one concern and either passes control to the next validator or returns a failure. This works for request validation, fraud checks, security filters and eligibility checks.

The chain order and failure response should be explicit.

#### Deep dive

For independent validations where all errors should be collected, a chain that stops at first failure may be the wrong model. A list of validators with aggregation may be better.

#### Production angle

Validation chains should produce stable error codes, metrics and logs so failures are diagnosable.

#### Traps / caveats

- Order can create hidden coupling.
- Stop-first vs collect-all must match user experience.
- Validators should avoid shared mutable state.

#### Optional Anki

Q: Pattern for ordered validators that may stop flow?
A: Chain of Responsibility.

</details>

<a id="dp-scen-007"></a>

<details>
<summary><strong>DP-SCEN-007. You need to implement order status transitions with different behavior per status. Which pattern fits?</strong></summary>

#### Short answer

State fits if behavior and allowed transitions vary by status; a simple enum or switch may be enough for small stable workflows.

#### Interview answer

If each status has meaningful rules, model states that define allowed actions such as pay, ship, cancel or refund. Invalid transitions should fail explicitly.

If the workflow is small and stable, an enum with transition rules or a transition table may be simpler than state classes.

#### Deep dive

State is most valuable when behavior belongs to lifecycle states, not when status is only a label.

#### Production angle

Correct transition modeling prevents invalid operations and supports auditability.

#### Traps / caveats

- Keep persisted status consistent with code transitions.
- Consider concurrency and optimistic locking.
- Do not spread transition rules across several layers.

#### Optional Anki

Q: Pattern for behavior changing by lifecycle state?
A: State.

</details>

<a id="dp-scen-008"></a>

<details>
<summary><strong>DP-SCEN-008. You need to send events to multiple independent handlers. Which pattern fits and what are the risks?</strong></summary>

#### Short answer

Observer or pub-sub fits fan-out, but reliability, failure isolation and transaction timing must be designed.

#### Interview answer

If handlers are in the same process and non-durable behavior is acceptable, in-process events or Observer may fit. If handlers are separate services or delivery must survive failure, use brokered messaging with outbox and idempotent consumers.

Each handler should fail independently unless it is required for the main operation.

#### Deep dive

The design should define sync vs async, ordering, retry policy, dead-letter behavior and event schema ownership.

#### Production angle

Event fan-out without observability creates hidden workflows that are hard to debug.

#### Traps / caveats

- Do not publish integration events before commit.
- Do not assume all handlers finish before the user response.
- Avoid event chains that become hidden RPC.

#### Optional Anki

Q: Main risk of event fan-out?
A: Hidden failure and consistency behavior unless retries and observability are designed.

</details>

<a id="dp-scen-009"></a>

<details>
<summary><strong>DP-SCEN-009. You need to choose between Decorator and Proxy. How would you decide?</strong></summary>

#### Short answer

Choose Decorator to explicitly add behavior; choose Proxy to control access or apply infrastructure interception.

#### Interview answer

If I am wrapping a client with logging, retry or compression and want the composition visible, Decorator fits. If access must be controlled lazily, remotely, securely or through framework advice, Proxy fits.

Both may have similar code shape, so I explain the intent.

#### Deep dive

Spring AOP proxy is great for uniform concerns. Decorator is often better for domain-specific wrappers and provider-specific behavior.

#### Production angle

Explicit decorators are easier to trace. Proxies are powerful but can surprise developers if call paths bypass them.

#### Traps / caveats

- Do not use AOP for business decisions that should be visible.
- Decorator order matters.
- Proxy limitations include self-invocation and final methods.

#### Optional Anki

Q: Decorator vs Proxy decision?
A: Decorator adds behavior explicitly; Proxy controls access or intercepts infrastructure behavior.

</details>

<a id="dp-scen-010"></a>

<details>
<summary><strong>DP-SCEN-010. How would you design a plugin-like extension mechanism in a Java backend service?</strong></summary>

#### Short answer

Define a stable extension interface, discover or inject implementations, validate registrations and isolate failures.

#### Interview answer

I would start with the extension point: what behavior can plugins provide, what input they receive, what output they return and what errors mean. In Spring, plugins can be beans implementing an interface and registered through a list or map. For external plugins, Java `ServiceLoader` or a module/plugin framework may fit.

The host should control lifecycle, compatibility and security.

#### Deep dive

A plugin mechanism often combines Strategy, Factory, Adapter and sometimes Chain of Responsibility.

#### Production angle

Plugins need versioning, observability, timeout/failure isolation and startup validation.

#### Traps / caveats

- Do not expose internal domain objects if plugin compatibility matters.
- Avoid unbounded plugin execution inside critical paths.
- Treat third-party plugins as untrusted unless proven otherwise.

#### Optional Anki

Q: Core of plugin design?
A: A stable extension contract plus controlled discovery and lifecycle.

</details>

<a id="dp-scen-011"></a>

<details>
<summary><strong>🧠 DP-SCEN-011. You need to introduce a pattern into legacy code. What steps would you take?</strong></summary>

#### Short answer

Protect behavior with tests, identify the real variation point, refactor incrementally and keep compatibility during migration.

#### Interview answer

I would first add characterization tests around current behavior and failure cases. Then I would isolate the change pressure: duplicated switch, vendor leak, construction mess, or large service. Next, introduce the smallest useful abstraction, move one path at a time, and keep old callers working until migration is complete.

I would avoid a big-bang rewrite.

#### Deep dive

Use feature flags or compatibility adapters if behavior must change gradually. Keep each step deployable.

#### Production angle

Legacy refactoring is risky because unknown behavior may be relied on by clients or operations.

#### Traps / caveats

- Do not introduce patterns without tests around current behavior.
- Do not rename and restructure everything at once.
- Monitor production after each migration step.

#### Optional Anki

Q: First step before pattern refactoring in legacy code?
A: Add characterization tests around existing behavior.

</details>

<a id="dp-scen-012"></a>

<details>
<summary><strong>🧠 DP-SCEN-012. How would you explain a design-pattern choice during code review?</strong></summary>

#### Short answer

Explain the concrete problem, why the pattern fits, what trade-offs it adds and what simpler alternatives were considered.

#### Interview answer

I would not just say "I used Strategy." I would say: "Payment provider behavior changes independently and the switch is duplicated in three places. Strategy localizes each provider, keeps selection explicit, and lets us add providers with focused tests. The cost is more classes and registry validation."

That makes the decision reviewable.

#### Deep dive

A good review explanation includes failure modes: how missing implementations fail, how behavior is tested, and how the next expected change looks.

#### Production angle

Clear design explanations help future maintainers avoid both under-design and pattern cargo culting.

#### Traps / caveats

- Do not defend a pattern only by naming it.
- Do not ignore the complexity cost.
- Mention when you would remove or simplify the pattern later.

#### Optional Anki

Q: What should a pattern choice explanation include?
A: Problem, fit, trade-offs, alternatives and tests.

</details>
