# 41.02. Creational patterns and construction trade-offs

---

<a id="dp-cre-001"></a>

<details>
<summary><strong>DP-CRE-001. What problem do creational patterns solve in Java backend code?</strong></summary>

#### Short answer

Creational patterns separate object creation decisions from the code that uses the objects.

#### Interview answer

In backend systems, object creation can involve choosing an implementation, validating input, building immutable objects, hiding vendor classes, or assembling a family of related objects. Creational patterns keep that logic from spreading across services.

They are useful when `new` would couple business code to concrete classes, construction rules or runtime selection logic.

#### Deep dive

Not all construction needs a pattern. A normal constructor is fine for simple objects. A pattern becomes useful when creation has policy: provider selection, environment differences, complex validation, or multiple representations.

#### Production angle

Centralized construction reduces inconsistent configuration and makes tests easier because callers depend on stable contracts.

#### Traps / caveats

- Do not hide simple construction behind unnecessary factories.
- Do not mix object creation with dependency lookup.
- Creation logic should still be observable and testable.

#### Optional Anki

Q: What do creational patterns mainly separate?
A: Object creation decisions from object usage.

</details>

<a id="dp-cre-002"></a>

<details>
<summary><strong>DP-CRE-002. What is the difference between a constructor, static factory, simple factory and Factory Method?</strong></summary>

#### Short answer

A constructor directly creates one class, a static factory names construction, a simple factory centralizes selection, and Factory Method lets subclasses or implementations decide what to create.

#### Interview answer

A constructor is direct: `new Order(...)`. A static factory like `Money.of(amount, currency)` gives construction a name and can validate or choose a representation. A simple factory is usually an object or method with conditionals that returns an interface implementation. Factory Method is a GoF pattern where a creator defines a creation method that subclasses or implementations override.

#### Deep dive

Many interview answers confuse static factory methods with Factory Method. Static factories are common Java idioms; Factory Method is about polymorphic creation.

#### Production angle

Use the lightest mechanism that solves the problem. Static factories are often enough for value objects; Spring bean selection or a map of strategies is often enough for backend services.

#### Traps / caveats

- Static factory is not automatically the GoF Factory Method pattern.
- A simple factory can become a large conditional if variants grow.
- Factories should not become hidden service locators.

#### Optional Anki

Q: Static factory vs Factory Method?
A: A static factory is a named construction method; Factory Method is polymorphic creation through an overridable method.

</details>

<a id="dp-cre-003"></a>

<details>
<summary><strong>DP-CRE-003. When is constructor injection enough, and when do you need a factory?</strong></summary>

#### Short answer

Constructor injection is enough for fixed dependencies; use a factory when the object or implementation must be chosen or created dynamically.

#### Interview answer

If a service always needs the same collaborators, constructor injection is clear and testable. A factory is useful when each request needs a different implementation, object creation requires runtime data, or construction rules should be centralized.

For example, inject `PaymentGateway` directly if there is one gateway. Use a factory or strategy registry if the gateway depends on country, tenant or payment method.

#### Deep dive

Constructor injection wires dependencies at object creation time. Factories often create domain objects or select runtime collaborators during a use case.

#### Production angle

Avoid injecting `ApplicationContext` just to choose beans manually. That hides dependencies and couples business logic to Spring.

#### Traps / caveats

- Do not use a factory only to avoid constructor parameters.
- Do not create objects manually when they need container-managed lifecycle.
- Runtime selection should be explicit and tested.

#### Optional Anki

Q: Constructor injection or factory?
A: Constructor injection for fixed collaborators; factory for dynamic creation or runtime selection.

</details>

<a id="dp-cre-004"></a>

<details>
<summary><strong>DP-CRE-004. How can dependency injection replace or simplify factories?</strong></summary>

#### Short answer

DI can create and wire objects for you, so application code often needs only a small selector or registry instead of a full factory.

#### Interview answer

Spring already knows how to instantiate beans and inject their dependencies. Instead of writing a factory that calls constructors, you can inject `List<PaymentStrategy>` or `Map<String, PaymentStrategy>` and select the correct implementation.

This keeps lifecycle, configuration and proxy behavior under the container.

#### Deep dive

DI is about wiring object graphs. Factories are about creation or selection policy. They overlap but are not identical.

#### Production angle

Using DI correctly avoids duplicate configuration and ensures proxies, metrics, transactions and lifecycle callbacks are applied where expected.

#### Traps / caveats

- DI does not remove the need to model runtime selection.
- Pulling beans from the container manually is Service Locator-like.
- A `Map<String, Bean>` registry still needs clear keys and failure behavior.

#### Optional Anki

Q: How can Spring simplify factories?
A: It can instantiate and wire implementations, leaving application code to select among injected beans.

</details>

<a id="dp-cre-005"></a>

<details>
<summary><strong>DP-CRE-005. What is the Factory Method pattern?</strong></summary>

#### Short answer

Factory Method defines a creation method that lets subclasses or implementations decide which concrete object to create.

#### Interview answer

The pattern separates the creator's workflow from the concrete product it creates. The base creator calls a factory method, and subclasses provide the specific product.

In Java backend code, the exact GoF form is less common than simple factories or DI, but the idea appears when framework extension points create objects through overridable methods.

#### Deep dive

Factory Method is useful when the creation decision belongs to a subtype or plugin. It is less useful when a single class just has a private helper that calls `new`.

#### Production angle

It can keep a stable workflow while allowing product-specific implementations, but it can also make control flow harder to follow.

#### Traps / caveats

- Do not confuse it with every method that returns a new object.
- Prefer simpler construction if there is no polymorphic creation need.
- Test both the base workflow and concrete creation behavior.

#### Optional Anki

Q: Core idea of Factory Method?
A: Defer concrete object creation to an overridable creation method.

</details>

<a id="dp-cre-006"></a>

<details>
<summary><strong>DP-CRE-006. What is Abstract Factory, and when is it useful?</strong></summary>

#### Short answer

Abstract Factory creates families of related objects without coupling clients to their concrete classes.

#### Interview answer

Use Abstract Factory when objects must be compatible as a set. For example, a payment integration might need a validator, request signer, mapper and client that all belong to the same provider family.

The client depends on an abstract factory and receives matching components.

#### Deep dive

Abstract Factory is more heavyweight than a simple factory. It fits multiple related products, not just one object.

#### Production angle

It can prevent mixing incompatible provider components, but it can also create too much ceremony if there are only one or two simple variants.

#### Traps / caveats

- Do not use Abstract Factory for a single object type.
- Adding a new product kind can require changing every factory.
- Families must be real, not invented for pattern completeness.

#### Optional Anki

Q: When does Abstract Factory fit?
A: When clients need a compatible family of related objects.

</details>

<a id="dp-cre-007"></a>

<details>
<summary><strong>DP-CRE-007. How do factories affect testability and the Open/Closed Principle?</strong></summary>

#### Short answer

Factories can improve testability and OCP by centralizing creation and allowing new implementations, but they can hurt both if they hide dependencies or become large conditionals.

#### Interview answer

A good factory lets tests supply fake products or verify selection rules in one place. It also supports OCP when a new implementation can be registered without editing many callers.

A bad factory becomes a giant `switch` that knows about every concrete class and every business rule.

#### Deep dive

Factories are most testable when they depend on explicit inputs and return interfaces. They are least testable when they reach into global state, environment variables or containers directly.

#### Production angle

Centralizing provider selection helps avoid inconsistent behavior between endpoints, batch jobs and message handlers.

#### Traps / caveats

- Do not hide dependencies behind static global factories.
- Do not put too much business logic into creation code.
- Startup validation should catch missing registrations.

#### Optional Anki

Q: Factory testability trap?
A: A factory that hides global lookup or business decisions is harder to test than explicit injection.

</details>

<a id="dp-cre-008"></a>

<details>
<summary><strong>DP-CRE-008. When should you use the Builder pattern?</strong></summary>

#### Short answer

Use Builder when constructing an object needs many optional fields, readable setup, validation or immutable final state.

#### Interview answer

Builder is useful when constructors would become long and ambiguous: `new Request(a, b, null, true, 30, false)`. A builder names each field and can collect validation before creating the final object.

It is common for configuration objects, API requests, test fixtures and immutable domain/data objects.

#### Deep dive

Builder is less useful for small objects with two or three required fields. Java records and named factory methods can be simpler.

#### Production angle

Builder improves readability at call sites and reduces invalid construction, especially for objects passed across layers or integration boundaries.

#### Traps / caveats

- Do not use Builder for every DTO by default.
- Make required fields clear.
- Avoid builders that allow partially invalid objects to leak.

#### Optional Anki

Q: Builder solves what problem?
A: Readable, safe construction of complex objects with many fields or options.

</details>

<a id="dp-cre-009"></a>

<details>
<summary><strong>DP-CRE-009. What validation belongs inside a Builder?</strong></summary>

#### Short answer

A builder should validate construction invariants that are required for the object to be valid.

#### Interview answer

Validation such as required fields, mutually exclusive options, value ranges and internal consistency belongs near construction. The final `build()` method should not return an object that is invalid by design.

External validation that needs a database, remote service or authorization context usually belongs outside the builder.

#### Deep dive

Builders can validate gradually in setter methods or centrally in `build()`. Central validation often gives a clearer view of cross-field rules.

#### Production angle

Construction-time validation prevents invalid state from moving through queues, caches, persistence and logs.

#### Traps / caveats

- Do not duplicate all domain validation in every builder.
- Do not perform slow I/O inside `build()`.
- Bean Validation annotations alone may not express cross-field invariants.

#### Optional Anki

Q: What should `build()` guarantee?
A: It should not return an object that violates construction invariants.

</details>

<a id="dp-cre-010"></a>

<details>
<summary><strong>DP-CRE-010. How do records and builders work together in modern Java?</strong></summary>

#### Short answer

Records are good for compact immutable data carriers; builders can help when record construction has many optional fields or needs readable setup.

#### Interview answer

A record gives a concise constructor, accessors, equality and `toString()`. For small DTOs, that is enough. If a record has many components or optional settings, a builder can make call sites clearer.

The record constructor should still enforce invariants because callers can use the canonical constructor directly unless access is controlled.

#### Deep dive

Records are shallowly immutable. If a record contains a mutable list, the record reference is final but the list can still change unless defensively copied.

#### Production angle

Records are useful for DTOs, commands, events and simple value objects. Builders are useful for readability in tests and integration clients.

#### Traps / caveats

- Do not assume records make nested data immutable.
- Avoid Lombok or generated builders that bypass important validation.
- Very large records may signal missing grouping or modeling.

#### Optional Anki

Q: Are records deeply immutable?
A: No. They are shallowly immutable unless their components are immutable or defensively copied.

</details>

<a id="dp-cre-011"></a>

<details>
<summary><strong>🧠 DP-CRE-011. What is Prototype, and why is `Cloneable` often problematic in Java?</strong></summary>

#### Short answer

Prototype creates objects by copying an existing instance; Java `Cloneable` is problematic because `clone()` has awkward contracts and shallow-copy traps.

#### Interview answer

Prototype is useful when creating a new object from an existing configured object is cheaper or clearer than rebuilding it. In Java, `Cloneable` is rarely pleasant: `clone()` comes from `Object`, often performs shallow copy, interacts badly with final fields and inheritance, and can surprise callers.

Copy constructors or explicit copy methods are usually clearer.

#### Deep dive

The biggest design question is ownership of mutable nested state. A shallow copy shares references; a deep copy duplicates the object graph where appropriate.

#### Production angle

Incorrect copying can leak mutable state between requests, tenants or tests. That becomes a correctness and security issue.

#### Traps / caveats

- Do not expose `clone()` without documenting shallow vs deep behavior.
- Deep copying large graphs can be expensive.
- Copying entities with database identity can create persistence bugs.

#### Optional Anki

Q: Why is `Cloneable` often avoided?
A: It has an awkward contract and often creates shallow-copy surprises.

</details>

<a id="dp-cre-012"></a>

<details>
<summary><strong>🧠 DP-CRE-012. When can `Supplier<T>`, copy constructors or static factory methods replace heavier creational patterns?</strong></summary>

#### Short answer

They fit when creation is simple enough that a full factory hierarchy would add more ceremony than value.

#### Interview answer

`Supplier<T>` can represent lightweight deferred creation, especially in tests or configuration. A copy constructor is clear when creating a modified version of an object. A static factory method is good when construction needs a name, validation or representation choice.

These tools often solve the practical problem without a full GoF pattern implementation.

#### Deep dive

The trade-off is expressiveness. A `Supplier<T>` is concise but has no domain name beyond the variable. A named factory interface communicates intent better when creation is central to the design.

#### Production angle

Prefer the simplest abstraction that still gives good names, testability and lifecycle control.

#### Traps / caveats

- Do not pass anonymous suppliers everywhere if a named concept would clarify the model.
- Static factories can hide dependencies if they reach into global state.
- Copying must preserve invariants and identity rules.

#### Optional Anki

Q: When is `Supplier<T>` enough?
A: When creation is lightweight and deferred, and a named factory hierarchy would be unnecessary.

</details>
