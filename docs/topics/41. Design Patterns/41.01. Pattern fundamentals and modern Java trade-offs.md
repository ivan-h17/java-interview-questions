# 41.01. Pattern fundamentals and modern Java trade-offs

---

<a id="dp-fund-001"></a>

<details>
<summary><strong>DP-FUND-001. What is a design pattern, and what problem does it solve?</strong></summary>

#### Short answer

A design pattern is a named, reusable solution shape for a recurring design problem.

#### Interview answer

In Java backend work, a design pattern is not copied code. It is a vocabulary for a recurring situation: creating objects, adapting interfaces, wrapping behavior, selecting algorithms, coordinating workflows, or separating responsibilities.

The value is that the team can discuss the shape quickly: "this looks like Strategy", "this is a Facade over a subsystem", or "this Proxy is hiding transaction behavior".

#### Deep dive

A pattern describes intent, participants and trade-offs. The same pattern can be implemented with classes, interfaces, lambdas, Spring beans, configuration or framework infrastructure.

#### Production angle

Patterns help when a system changes over time. They can isolate provider-specific logic, protect boundaries around external APIs, and make cross-cutting behavior testable. They are harmful when they add indirection without a real change pressure.

#### Traps / caveats

- Do not treat patterns as mandatory recipes.
- Do not introduce a pattern only because the name sounds professional.
- The pattern should reduce change cost or clarify responsibility.

#### Optional Anki

Q: What is a design pattern?
A: A named, reusable solution shape for a recurring design problem.

</details>

<details>
<summary><strong>DP-FUND-002. Why are design patterns not the same as libraries, frameworks or language features?</strong></summary>

#### Short answer

A pattern is a design idea; a library, framework or language feature is a concrete tool that may implement or replace part of that idea.

#### Interview answer

For example, Strategy is a way to make algorithms interchangeable. In Java it can be implemented with classes, lambdas, enums, a `Map<String, Strategy>`, or Spring beans. Spring is a framework that uses many patterns internally, but the pattern is not the framework.

This distinction matters because a candidate should explain the design force, not only name a tool.

#### Deep dive

Language features can make some patterns lighter. Lambdas can replace small Strategy classes. Records can reduce boilerplate in DTOs. Sealed classes can make some State-like hierarchies safer.

#### Production angle

Choosing a framework feature without understanding the pattern can create hidden coupling. For example, using `ApplicationContext.getBean()` as a factory may actually introduce Service Locator behavior.

#### Traps / caveats

- Do not say "Spring is Singleton"; Spring has singleton-scoped beans, which are different from GoF Singleton.
- A lambda can implement a strategy, but not every lambda is a Strategy pattern.
- Framework convenience can hide lifecycle and proxy behavior.

#### Optional Anki

Q: Pattern vs framework?
A: A pattern is a design idea; a framework is a concrete tool that may use that idea.

</details>

<details>
<summary><strong>DP-FUND-003. How do design patterns relate to SOLID principles?</strong></summary>

#### Short answer

Design patterns are concrete ways to apply design principles such as SRP, OCP, DIP and composition over inheritance.

#### Interview answer

Patterns and SOLID are related but not the same. SOLID gives design heuristics: keep responsibilities cohesive, depend on useful abstractions, and make common change safer. Patterns are common solution shapes that often help achieve those goals.

For example, Strategy can support Open/Closed Principle, Adapter can support Dependency Inversion, and Decorator can preserve Single Responsibility by adding behavior without changing the wrapped object.

#### Deep dive

Patterns can also violate SOLID when used mechanically. A bad Abstract Factory can create unstable abstractions. A Singleton can hide dependencies. A Facade can become a God Object.

#### Production angle

In code review, the useful question is not "which pattern did you use?" but "does this design make the likely next change cheaper and safer?"

#### Traps / caveats

- SOLID does not require adding patterns everywhere.
- A pattern name is not proof of good design.
- A simple branch can be more maintainable than a premature strategy hierarchy.

#### Optional Anki

Q: How do patterns relate to SOLID?
A: Patterns are common implementation shapes that can help apply SOLID principles, but they can also be misused.

</details>

<details>
<summary><strong>DP-FUND-004. When should you avoid introducing a design pattern?</strong></summary>

#### Short answer

Avoid a pattern when the problem is small, stable, local, clearer with direct code, or when the abstraction is based on speculation.

#### Interview answer

I avoid patterns when there is no real variation point, no repeated change pressure, and no boundary to protect. A two-case `switch` in one method may be better than a hierarchy of strategies, factories and registries.

The cost of a pattern is extra concepts, files, wiring, tests and debugging effort.

#### Deep dive

A good signal for a pattern is recurring pain: duplicate branching, hard-to-test construction, external API leakage, repeated cross-cutting code, or many changes touching one central method.

#### Production angle

Over-abstracted production code slows incident response because developers must follow indirection before seeing the actual business rule.

#### Traps / caveats

- Do not confuse simple code with bad design.
- Do not create an interface for every class without a real client boundary.
- Do not hide business decisions behind framework magic.

#### Optional Anki

Q: When should you avoid a pattern?
A: When direct code is clearer and there is no real change pressure or boundary problem.

</details>

<details>
<summary><strong>DP-FUND-005. What does it mean to refactor toward a pattern rather than introduce it upfront?</strong></summary>

#### Short answer

It means starting simple and introducing the pattern only when the code shows a recurring problem the pattern can solve.

#### Interview answer

Instead of guessing that a feature will need Strategy, I may begin with a clear method or switch. If the variants grow, tests become hard, or each new provider requires risky edits, I refactor toward Strategy with a common interface and implementations.

This keeps early code simple while still allowing evolution.

#### Deep dive

Refactoring toward a pattern usually means identifying the stable part and the variation point. Then you extract the variation behind a contract and move callers gradually.

#### Production angle

This is safer in legacy systems because tests can protect the current behavior before structural changes.

#### Traps / caveats

- Do not wait until the code is unmaintainable before refactoring.
- Do not introduce the full pattern if a smaller extraction solves the issue.
- Keep behavior stable during structural refactoring.

#### Optional Anki

Q: What is refactoring toward a pattern?
A: Introducing a pattern after the code reveals a real recurring design problem.

</details>

<a id="dp-fund-006"></a>

<details>
<summary><strong>DP-FUND-006. How do you decide whether a pattern improves or worsens a design?</strong></summary>

#### Short answer

A pattern improves design when it makes likely changes easier, responsibilities clearer and tests simpler without adding excessive indirection.

#### Interview answer

I check the change scenario. If adding a new payment provider becomes adding one class and one test, Strategy or Adapter probably helps. If the same change now requires understanding factories, registries and reflection, the pattern may have made the design worse.

The decision should be based on readability, ownership, testability, risk and expected change frequency.

#### Deep dive

Good patterns create useful seams around variation. Bad patterns create ceremony around code that was already simple.

#### Production angle

Look at operational symptoms: long onboarding, slow debugging, fragile tests, duplicated wiring, unclear logs, or repeated incidents around hidden behavior.

#### Traps / caveats

- Do not measure design quality by number of patterns.
- Do not optimize for future changes nobody expects.
- A pattern can improve extensibility while hurting debuggability.

#### Optional Anki

Q: Main test for a useful pattern?
A: It should make likely changes easier and responsibilities clearer at an acceptable complexity cost.

</details>

<details>
<summary><strong>🧠 DP-FUND-007. How do modern Java features such as lambdas, records, sealed classes and pattern matching reduce the need for some classic patterns?</strong></summary>

#### Short answer

Modern Java can make some pattern implementations smaller or unnecessary by providing concise functions, value carriers and safer type hierarchies.

#### Interview answer

Lambdas can replace small Strategy or Command classes. Records reduce DTO and value-object boilerplate. Sealed classes plus exhaustive `switch` can sometimes be clearer than a full State or Visitor setup when the hierarchy is closed.

The pattern idea may still apply, but the implementation does not need old-school boilerplate.

#### Deep dive

Classic GoF patterns were described before modern Java features, DI containers and common framework conventions. A senior answer should separate the intent from the historical implementation style.

#### Production angle

Using modern Java can reduce code size and make behavior easier to review, but the same design questions remain: ownership, extension, testing, compatibility and runtime behavior.

#### Traps / caveats

- Do not replace polymorphism with a giant switch when new variants are added by different teams.
- Records are shallowly immutable only if their components are immutable or defensively copied.
- Pattern matching does not remove the need for good boundaries.

#### Optional Anki

Q: How can lambdas affect design patterns?
A: They can implement lightweight Strategy or Command behavior without creating many small classes.

</details>
