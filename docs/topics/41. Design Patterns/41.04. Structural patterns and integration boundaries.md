# 41.04. Structural patterns and integration boundaries

---

<a id="dp-struct-001"></a>

<details>
<summary><strong>DP-STRUCT-001. What problem do structural patterns solve?</strong></summary>

#### Short answer

Structural patterns organize how classes and objects are composed to form larger, flexible structures.

#### Interview answer

They help connect objects without forcing everything into inheritance. In backend code, they often appear around external systems, layered APIs, wrappers, old code, object trees and framework infrastructure.

The goal is usually to reduce coupling between a client and a concrete structure.

#### Deep dive

Structural patterns include Adapter, Facade, Decorator, Proxy, Composite, Bridge and Flyweight. The important part is the design force: compatibility, simplification, extension, access control, tree modeling or memory sharing.

#### Production angle

They are especially useful at integration boundaries: REST clients, SDK wrappers, persistence adapters, caching layers and legacy subsystems.

#### Traps / caveats

- Do not add wrappers that only rename methods without protecting a boundary.
- Extra object layers can hide failures and cost.
- Structural patterns should make navigation easier, not harder.

#### Optional Anki

Q: What do structural patterns focus on?
A: Object and class composition.

</details>

<a id="dp-struct-002"></a>

<details>
<summary><strong>DP-STRUCT-002. How are structural patterns related to composition over inheritance?</strong></summary>

#### Short answer

Many structural patterns use composition to add, adapt or combine behavior without creating fragile inheritance hierarchies.

#### Interview answer

Composition means one object delegates to another. Adapter wraps an incompatible API. Decorator wraps an object to add behavior. Facade composes several subsystem calls. Proxy stands in front of a target.

This is often safer than inheritance because behavior can be assembled and replaced at runtime.

#### Deep dive

Inheritance is still useful for true subtype relationships, but it tightly couples behavior to a class hierarchy. Composition makes roles more explicit.

#### Production angle

Composition works well with Spring DI because collaborators are declared and can be replaced in tests or configuration.

#### Traps / caveats

- Composition can still be overused.
- Delegation chains should not obscure where behavior lives.
- Inheritance is not always wrong; use it when substitutability is real.

#### Optional Anki

Q: Why do many patterns prefer composition?
A: It allows behavior to be wrapped, delegated and replaced without rigid inheritance.

</details>

<a id="dp-struct-003"></a>

<details>
<summary><strong>DP-STRUCT-003. What is the Adapter pattern, and when would you use it in a Java backend service?</strong></summary>

#### Short answer

Adapter converts one interface into another interface expected by the client.

#### Interview answer

In a backend service, I use Adapter around external APIs, vendor SDKs, legacy modules or generated clients. The domain or application code depends on a clean port like `PaymentGateway`, while the adapter translates to Stripe, PayPal, REST, SOAP or a legacy database.

The adapter protects the core from vendor models, exceptions and protocol details.

#### Deep dive

Adapter can be class-based or object-based. In Java backend code, object adapters are more common: they wrap a client and map calls.

#### Production angle

Adapters make provider replacement, testing and failure handling clearer. They also help prevent vendor DTOs from leaking into domain code.

#### Traps / caveats

- Do not put all business rules into the adapter.
- Map external errors into meaningful application errors.
- Keep adapter contracts stable and provider-neutral.

#### Optional Anki

Q: What does Adapter protect?
A: The client from an incompatible external or legacy interface.

</details>

<a id="dp-struct-004"></a>

<details>
<summary><strong>DP-STRUCT-004. What is the Facade pattern, and when can it become a God Object?</strong></summary>

#### Short answer

Facade provides a simpler interface over a complex subsystem, but it becomes a God Object when it owns too many unrelated responsibilities.

#### Interview answer

A Facade is useful when clients should not know the detailed sequence of calls into a subsystem. For example, an `InvoiceFacade` might coordinate rendering, tax lookup and PDF storage behind one method.

It becomes problematic when every feature is added to the facade until it contains validation, business rules, persistence, retries, formatting and authorization.

#### Deep dive

A good facade simplifies access while preserving clear subsystem boundaries. It should not become the real domain model.

#### Production angle

Facades can stabilize integration points, but a huge facade becomes a high-change, high-conflict file.

#### Traps / caveats

- Do not hide important transaction or failure semantics.
- Do not let the facade become the only service everyone modifies.
- Keep public methods cohesive around one subsystem or use case area.

#### Optional Anki

Q: Facade risk?
A: It can grow into a God Object if it accumulates unrelated responsibilities.

</details>

<a id="dp-struct-005"></a>

<details>
<summary><strong>DP-STRUCT-005. What is the Decorator pattern, and why can it be better than inheritance?</strong></summary>

#### Short answer

Decorator wraps an object with the same interface to add behavior dynamically.

#### Interview answer

Instead of subclassing for every combination like `LoggingRetryingCachingClient`, Decorator lets you wrap a base client with `LoggingClient`, `RetryingClient` and `CachingClient`. Each wrapper adds one concern and delegates to the next object.

This avoids class explosion and keeps responsibilities smaller.

#### Deep dive

Decorator is transparent to clients when it preserves the same interface. The wrapped object and decorator should obey the same contract.

#### Production angle

Decorators are useful for metrics, tracing, logging, retries, validation and caching around clients or services when explicit wrapping is clearer than AOP.

#### Traps / caveats

- Decorator order can change behavior.
- Do not swallow exceptions unless the contract says so.
- Too many wrappers can make debugging harder.

#### Optional Anki

Q: Decorator vs inheritance?
A: Decorator adds behavior by wrapping objects instead of multiplying subclasses.

</details>

<a id="dp-struct-006"></a>

<details>
<summary><strong>DP-STRUCT-006. How is Decorator used in Java I/O streams?</strong></summary>

#### Short answer

Java I/O streams use wrappers that add behavior such as buffering, filtering or data conversion around another stream.

#### Interview answer

For example, a `BufferedInputStream` wraps an `InputStream` and adds buffering. A `DataInputStream` wraps an input stream and adds methods to read primitive values. The client still works with stream-like abstractions while behavior is composed by wrapping.

This is a classic Decorator example.

#### Deep dive

The benefit is flexible composition: file input, buffering and data parsing can be combined without a subclass for every combination.

#### Production angle

Correct stream wrapping affects performance and resource handling. Buffered wrappers reduce system calls; incorrect closing or layering can leak resources.

#### Traps / caveats

- Wrapper order matters.
- Always manage resource ownership clearly.
- Do not confuse Decorator with inheritance just because classes share a base type.

#### Optional Anki

Q: Java I/O pattern example?
A: `BufferedInputStream` decorating another `InputStream`.

</details>

<a id="dp-struct-007"></a>

<details>
<summary><strong>DP-STRUCT-007. What is the difference between Decorator and Proxy?</strong></summary>

#### Short answer

Decorator adds responsibilities to an object; Proxy controls access to an object.

#### Interview answer

Both wrap another object and may expose the same interface. The intent differs. Decorator enhances behavior, such as adding metrics or retries. Proxy controls access, such as lazy loading, security checks, remote calls or transactional interception.

In practice, code can look similar, so explain intent and failure behavior.

#### Deep dive

Decorator is usually composed explicitly by application code. Proxy is often created by frameworks or infrastructure and may hide the target object.

#### Production angle

If behavior must be obvious and business-specific, Decorator may be better. If behavior is uniform infrastructure, Proxy or AOP may fit.

#### Traps / caveats

- Do not decide only by class shape; decide by intent.
- A proxy can also add behavior, which blurs the boundary.
- Hidden proxies complicate type checks and debugging.

#### Optional Anki

Q: Decorator intent vs Proxy intent?
A: Decorator adds behavior; Proxy controls access.

</details>

<a id="dp-struct-008"></a>

<details>
<summary><strong>DP-STRUCT-008. What is Composite, and when would you model an object tree with it?</strong></summary>

#### Short answer

Composite lets clients treat individual objects and groups of objects through a common interface.

#### Interview answer

Use Composite when the domain naturally forms a tree: menu items, organizational units, permission rules, filters, expressions, document sections or product categories. A leaf performs work directly; a composite delegates to child nodes.

The client can call the same operation on a single node or a whole tree.

#### Deep dive

Composite is useful when tree traversal and uniform operations matter. It is less useful if parent and child concepts are too different.

#### Production angle

Composite can model authorization rules, search filters or workflow trees, but large trees need careful performance and cycle protection.

#### Traps / caveats

- Do not force unrelated objects into one interface.
- Watch recursion depth and cycles.
- Define ownership and mutation rules for children.

#### Optional Anki

Q: Composite solves what?
A: Uniform handling of leaves and groups in a tree structure.

</details>

<a id="dp-struct-009"></a>

<details>
<summary><strong>🧠 DP-STRUCT-009. What is Bridge, and when can it avoid a class hierarchy explosion?</strong></summary>

#### Short answer

Bridge separates an abstraction from its implementation so both can vary independently.

#### Interview answer

Bridge helps when two dimensions vary. For example, reports vary by type and output format. Without Bridge, you might create `PdfSalesReport`, `CsvSalesReport`, `PdfInventoryReport`, and so on. With Bridge, report logic and renderer implementation are separate.

The abstraction delegates implementation-specific work to a separate interface.

#### Deep dive

Bridge is designed upfront for independent variation, while Adapter usually wraps an existing incompatible interface.

#### Production angle

Bridge can be useful in libraries, SDK abstractions or multi-provider systems, but it is often overkill for ordinary application code.

#### Traps / caveats

- Do not introduce Bridge when there is only one real variation axis.
- Names matter; otherwise the design becomes abstract noise.
- Ensure both dimensions truly change independently.

#### Optional Anki

Q: Bridge separates what?
A: An abstraction from its implementation so both can vary independently.

</details>

<details>
<summary><strong>🧠 DP-STRUCT-010. What is Flyweight, and what are its concurrency risks?</strong></summary>

#### Short answer

Flyweight shares immutable intrinsic state across many objects to reduce memory, but shared mutable state can create concurrency bugs.

#### Interview answer

Flyweight is useful when many similar objects duplicate the same data. The shared part is stored once, and request-specific state is kept outside or passed in. Examples include cached metadata, parsed templates, symbols or shared configuration descriptors.

The shared flyweight must usually be immutable or safely synchronized.

#### Deep dive

The key split is intrinsic state, which is shareable, and extrinsic state, which belongs to the current use.

#### Production angle

Flyweight can reduce memory pressure in high-volume systems, but a bad cache or mutable shared object can cause cross-request data leaks.

#### Traps / caveats

- Do not share request-specific data.
- Control cache size and eviction.
- Immutable shared state is much safer than synchronized mutable state.

#### Optional Anki

Q: Flyweight's main safety rule?
A: Share immutable intrinsic state, keep request-specific state outside.

</details>
