# 41.06. Behavioral patterns and workflow modeling

---

<a id="dp-beh-001"></a>

<details>
<summary><strong>DP-BEH-001. What problem do behavioral patterns solve?</strong></summary>

#### Short answer

Behavioral patterns organize how objects communicate, delegate work and vary behavior.

#### Interview answer

They help replace scattered conditionals, unclear workflows and tightly coupled collaborators with explicit roles. In backend code, they often appear in payment selection, validation chains, retries, command processing, workflow states and event handling.

The main value is making behavior easier to extend, test and reason about.

#### Deep dive

Behavioral patterns include Strategy, State, Template Method, Command, Chain of Responsibility, Observer and Visitor. Each solves a different communication or responsibility problem.

#### Production angle

They are useful when business behavior changes often or when failure handling must be isolated.

#### Traps / caveats

- Do not replace every conditional with a class hierarchy.
- Patterns do not fix unclear domain rules.
- Behavior should remain observable and testable.

#### Optional Anki

Q: Behavioral patterns focus on what?
A: Object communication, delegation and varying behavior.

</details>

<a id="dp-beh-002"></a>

<details>
<summary><strong>DP-BEH-002. When is a simple `switch` better than a behavioral pattern?</strong></summary>

#### Short answer

A `switch` is better when cases are small, stable, local and intentionally exhaustive.

#### Interview answer

If there are three fixed enum values and one small mapping, a switch is clearer than creating strategies. A switch is also useful with sealed hierarchies when the compiler can help enforce exhaustive handling.

Patterns become more attractive when variants grow, change independently, need separate tests, or the same switch is duplicated across the codebase.

#### Deep dive

The decision depends on the axis of change. If adding new variants is frequent, polymorphism helps. If adding new operations over stable variants is frequent, a switch or Visitor-like design may be better.

#### Production angle

Simple local code is easier to debug during incidents. Abstraction should pay for itself with real change or risk reduction.

#### Traps / caveats

- Do not duplicate the same switch in many layers.
- Do not hide a complex domain workflow inside one huge switch.
- Do not call every switch an OCP violation.

#### Optional Anki

Q: When is a switch acceptable?
A: When cases are small, stable, local and clear.

</details>

<a id="dp-beh-003"></a>

<details>
<summary><strong>DP-BEH-003. What is the Strategy pattern, and when should you use it?</strong></summary>

#### Short answer

Strategy encapsulates interchangeable algorithms or policies behind a common interface.

#### Interview answer

Use Strategy when a context performs the same kind of work but the implementation varies: payment provider, pricing rule, notification channel, fraud rule, retry policy or export format.

The context depends on a strategy contract and delegates variable behavior to the selected implementation.

#### Deep dive

Strategy is a good replacement for repeated conditionals when variants change independently. It works well with DI because each strategy can be a Spring bean.

#### Production angle

It localizes provider-specific code, makes tests focused and reduces the risk that adding a new variant breaks existing variants.

#### Traps / caveats

- Do not use Strategy for two stable one-line branches.
- Keep the strategy interface small and meaningful.
- Decide how unknown or missing strategies fail.

#### Optional Anki

Q: Strategy pattern intent?
A: Encapsulate interchangeable behavior behind a common contract.

</details>

<a id="dp-beh-004"></a>

<details>
<summary><strong>DP-BEH-004. How would you implement Strategy with Spring beans?</strong></summary>

#### Short answer

Define a strategy interface, implement each variant as a bean, inject a list or map of strategies, and select one by a clear key.

#### Interview answer

For payments, define `PaymentStrategy` with methods like `supports(method)` and `pay(command)`. Each provider implementation is a Spring bean. The orchestrator injects `List<PaymentStrategy>` or `Map<String, PaymentStrategy>` and selects based on request data, tenant, feature flag or configuration.

The orchestrator owns selection; each strategy owns provider-specific behavior.

#### Deep dive

Using a map by bean name is simple, but explicit strategy keys are often safer than relying on bean names.

#### Production angle

Validate at startup that required strategies exist and that keys are unique. Missing strategies should fail clearly.

#### Traps / caveats

- Do not inject `ApplicationContext` for normal selection.
- Avoid putting all selection rules inside each strategy if the orchestrator needs global policy.
- Ensure strategy beans are stateless or thread-safe.

#### Optional Anki

Q: Spring-friendly Strategy implementation?
A: Inject strategy beans as a list or map and select by an explicit key.

</details>

<a id="dp-beh-005"></a>

<details>
<summary><strong>DP-BEH-005. How would you select a Strategy at runtime?</strong></summary>

#### Short answer

Select by explicit request data, configuration, feature flags or domain state using a registry or selector.

#### Interview answer

I prefer a small selector that maps a stable key to a strategy. For example, `paymentMethod=CARD` maps to `CardPaymentStrategy`. If selection is more complex, the selector can evaluate country, tenant, amount or feature flags.

The important point is that selection rules are visible and tested.

#### Deep dive

Some designs let strategies declare `supports(command)`. That can work, but overlapping support rules need deterministic ordering and startup validation.

#### Production angle

Runtime selection should produce clear logs and errors because misrouting payment or notification behavior is high impact.

#### Traps / caveats

- Avoid ambiguous matching.
- Avoid falling back silently to the wrong strategy.
- Keep selection separate from execution when it improves clarity.

#### Optional Anki

Q: What should a runtime strategy selector avoid?
A: Ambiguous or silent fallback behavior.

</details>

<a id="dp-beh-006"></a>

<details>
<summary><strong>DP-BEH-006. What is the difference between Strategy and Dependency Injection?</strong></summary>

#### Short answer

Strategy is a behavioral design pattern; DI is a wiring technique that can provide strategies to a class.

#### Interview answer

Strategy models interchangeable behavior. Dependency Injection supplies dependencies from the outside instead of constructing them internally. Spring can inject strategies, but DI itself is not the Strategy pattern.

A service with one injected repository uses DI, not Strategy. A service choosing among several pricing policies uses Strategy.

#### Deep dive

DI helps implement many patterns: Strategy, Adapter, Decorator, Factory and Chain. The pattern describes the design intent; DI describes how objects are wired.

#### Production angle

Confusing the two can lead to weak abstractions. Injecting an interface is useful only when the contract represents a real dependency or variation point.

#### Traps / caveats

- Not every injected interface is a Strategy.
- Strategy can be implemented without a DI container.
- DI can also wire bad designs.

#### Optional Anki

Q: Strategy vs DI?
A: Strategy is interchangeable behavior; DI is external dependency wiring.

</details>

<a id="dp-beh-007"></a>

<details>
<summary><strong>DP-BEH-007. What is the State pattern, and how is it different from Strategy?</strong></summary>

#### Short answer

State changes an object's behavior based on its internal state; Strategy selects an interchangeable algorithm from outside or context policy.

#### Interview answer

State fits lifecycle behavior: an order behaves differently when `NEW`, `PAID`, `SHIPPED` or `CANCELLED`. Each state can define allowed transitions and actions.

Strategy fits interchangeable policies such as pricing, payment provider or retry algorithm. The selected strategy does not usually represent the object's lifecycle.

#### Deep dive

State often transitions to another state. Strategy normally does not own lifecycle transitions; it performs a selected behavior.

#### Production angle

State can make workflows safer by centralizing allowed transitions and rejecting invalid ones clearly.

#### Traps / caveats

- Do not use State for simple enum labels with no behavior.
- Avoid spreading transition rules across controllers, services and database triggers.
- Persisted state must match the model's allowed transitions.

#### Optional Anki

Q: State vs Strategy?
A: State models lifecycle-dependent behavior; Strategy models interchangeable algorithms or policies.

</details>

<a id="dp-beh-008"></a>

<details>
<summary><strong>DP-BEH-008. How would you model an order lifecycle with the State pattern?</strong></summary>

#### Short answer

Represent each meaningful order state with behavior that controls allowed actions and transitions.

#### Interview answer

For example, `NewOrderState` may allow payment or cancellation. `PaidOrderState` may allow shipment or refund. `ShippedOrderState` may reject cancellation and allow delivery confirmation. The `Order` delegates state-specific actions to the current state.

Invalid transitions should fail with domain-specific errors.

#### Deep dive

In Java, this can be implemented with state classes, enum methods, or a transition table. The right choice depends on complexity.

#### Production angle

Lifecycle modeling prevents incorrect operations such as shipping an unpaid order or refunding twice.

#### Traps / caveats

- Do not over-model if simple enum checks are enough.
- Keep persistence and state model synchronized.
- Make transitions transactional when state changes must be durable.

#### Optional Anki

Q: What should order State enforce?
A: Allowed actions and transitions for each lifecycle state.

</details>

<a id="dp-beh-009"></a>

<details>
<summary><strong>DP-BEH-009. What is Template Method, and when would you use it instead of Strategy?</strong></summary>

#### Short answer

Template Method defines a fixed algorithm skeleton in a base class and lets subclasses override selected steps.

#### Interview answer

Use Template Method when the overall workflow is stable and only specific steps vary. For example, a base importer may define `read`, `validate`, `transform`, `persist`, while subclasses customize formats.

Use Strategy when you want composition and interchangeable behavior without inheritance.

#### Deep dive

Spring's `JdbcTemplate` and `TransactionTemplate` are related in spirit: they own a stable workflow and let user code provide variable work through callbacks, which is often more flexible than subclassing.

#### Production angle

Template Method can centralize error handling and resource cleanup, but inheritance-based designs can become rigid.

#### Traps / caveats

- Avoid deep inheritance chains.
- Make overridable steps clear and protected.
- Do not force subclasses to override irrelevant hooks.

#### Optional Anki

Q: Template Method core idea?
A: Fixed algorithm skeleton with customizable steps.

</details>

<a id="dp-beh-010"></a>

<details>
<summary><strong>DP-BEH-010. What is the Command pattern, and how can it support queues, retries or undo?</strong></summary>

#### Short answer

Command encapsulates a request as an object, making it possible to queue, log, retry, schedule or undo it.

#### Interview answer

A command object represents an action such as `CreateOrderCommand` or `SendEmailCommand`. A handler executes it. Because the request is data, it can be stored, validated, serialized, retried, audited or sent through a queue.

Undo is possible when commands also know or record how to compensate their effect.

#### Deep dive

In backend systems, "command" often means an application input model, not always the exact GoF object with `execute()`. The important idea is separating request description from execution.

#### Production angle

Commands work well with idempotency keys, outbox tables, job queues and audit logs.

#### Traps / caveats

- Retrying non-idempotent commands can duplicate side effects.
- Undo is often compensation, not perfect reversal.
- Do not put huge domain objects into queue commands.

#### Optional Anki

Q: Command pattern benefit?
A: Requests can be queued, logged, retried or compensated as explicit objects.

</details>

<details>
<summary><strong>DP-BEH-011. What is Chain of Responsibility, and how is it used in servlet filters or Spring Security filters?</strong></summary>

#### Short answer

Chain of Responsibility passes a request through ordered handlers, each of which can process, modify or stop the flow.

#### Interview answer

In servlet filters, each filter can inspect the request and decide whether to continue with `chain.doFilter()`. Spring Security uses a filter chain for authentication, authorization, CSRF, session handling and more.

The pattern fits ordered validation, middleware and request processing pipelines.

#### Deep dive

Handlers should have clear responsibilities and predictable ordering. A handler that stops the chain must do so intentionally and return a correct response.

#### Production angle

Filter-chain bugs can cause skipped security, double logging, missing correlation IDs or wrong error responses.

#### Traps / caveats

- Order matters.
- A handler that forgets to call the next step can stop processing.
- Shared mutable state in chain handlers is dangerous.

#### Optional Anki

Q: Chain of Responsibility in web apps?
A: Servlet and Spring Security filters are common examples.

</details>

<a id="dp-beh-012"></a>

<details>
<summary><strong>🧠 DP-BEH-012. What is Visitor, and how does it relate to the expression problem?</strong></summary>

#### Short answer

Visitor lets you add new operations over a stable object structure, but adding new element types becomes harder.

#### Interview answer

Visitor separates operations from the classes being operated on. Each element accepts a visitor, and the visitor has methods for each concrete element type.

It helps when the object hierarchy is stable but you frequently add new operations, such as validation, rendering or exporting.

#### Deep dive

The expression problem is the tension between adding new data variants and adding new operations. Object-oriented polymorphism makes new variants easy but new operations harder. Visitor flips the trade-off.

#### Production angle

Visitor is useful in parsers, ASTs, rule trees and document models. It is usually overkill for ordinary CRUD services.

#### Traps / caveats

- Adding a new element type requires updating all visitors.
- Visitor can expose too much internal structure.
- Pattern matching and sealed classes may be simpler for closed hierarchies.

#### Optional Anki

Q: Visitor is best when what is stable?
A: The object hierarchy is stable and new operations are added often.

</details>
