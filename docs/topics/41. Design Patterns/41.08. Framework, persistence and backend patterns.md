# 41.08. Framework, persistence and backend patterns

---

<a id="dp-fw-001"></a>

<details>
<summary><strong>DP-FW-001. Which design patterns are commonly used in Spring Framework?</strong></summary>

#### Short answer

Spring commonly uses Dependency Injection, Singleton scope, Factory, Proxy, Template Method, Observer, Front Controller and Adapter-like patterns.

#### Interview answer

Spring is pattern-heavy, but the important part is behavior. DI wires dependencies. Singleton scope reuses bean instances. Factories create and expose beans. Proxies support AOP, transactions, caching and security. Templates such as `JdbcTemplate` centralize resource handling. Spring MVC uses a Front Controller through `DispatcherServlet`.

#### Deep dive

Frameworks often use patterns internally so application code can stay simpler. You usually use the framework feature rather than implementing the pattern manually.

#### Production angle

Understanding the patterns helps debug lifecycle, proxying, transaction and event behavior.

#### Traps / caveats

- Do not call every Spring bean a GoF Singleton.
- Do not use `ApplicationContext` lookup as normal business logic.
- Framework patterns still have runtime limits.

#### Optional Anki

Q: Name three Spring-related patterns.
A: Dependency Injection, Proxy and Front Controller.

</details>

<details>
<summary><strong>DP-FW-002. How is Front Controller used in Spring MVC?</strong></summary>

#### Short answer

Spring MVC uses `DispatcherServlet` as a central entry point that dispatches HTTP requests to handlers.

#### Interview answer

The Front Controller pattern puts common request handling in one central component. In Spring MVC, `DispatcherServlet` receives requests, selects a controller method through mappings, invokes argument resolution and message conversion, and coordinates response handling.

Controllers focus on endpoint-specific behavior.

#### Deep dive

The Front Controller enables shared infrastructure: exception handling, interceptors, locale resolution, conversion, validation and content negotiation.

#### Production angle

Understanding the request pipeline helps debug missing mappings, wrong serialization, validation failures and exception handling.

#### Traps / caveats

- `DispatcherServlet` is not your business controller.
- Handler interceptors and servlet filters run at different levels.
- Centralized request handling does not remove endpoint-specific design responsibility.

#### Optional Anki

Q: Spring MVC Front Controller?
A: `DispatcherServlet`.

</details>

<a id="dp-fw-003"></a>

<details>
<summary><strong>DP-FW-003. How is Dependency Injection related to design patterns?</strong></summary>

#### Short answer

Dependency Injection is a design technique where dependencies are provided from outside, and it helps implement many patterns cleanly.

#### Interview answer

DI supports Dependency Inversion by letting high-level code depend on contracts while concrete implementations are supplied externally. It also makes patterns such as Strategy, Adapter, Decorator and Chain easier to wire.

In Spring, constructor injection is the usual form for application services.

#### Deep dive

DI is not the same as Service Locator. With DI, dependencies are visible in the constructor. With Service Locator, code asks a registry for dependencies at runtime.

#### Production angle

Explicit dependencies improve tests, configuration, lifecycle management and observability.

#### Traps / caveats

- Do not inject everything through fields with hidden magic if constructor injection is practical.
- DI can still wire poor abstractions.
- Too many dependencies may indicate a responsibility problem.

#### Optional Anki

Q: DI vs Service Locator?
A: DI provides dependencies from outside; Service Locator makes code look them up.

</details>

<a id="dp-fw-004"></a>

<details>
<summary><strong>DP-FW-004. What is Service Locator, and why is it often considered an anti-pattern?</strong></summary>

#### Short answer

Service Locator is a registry that code queries for dependencies; it is often an anti-pattern because it hides dependencies.

#### Interview answer

Instead of declaring `PaymentGateway` in the constructor, a class calls something like `context.getBean(PaymentGateway.class)` or `registry.get("payment")`. The class now depends on the locator and hides what it needs.

This makes tests, reasoning and refactoring harder.

#### Deep dive

Service Locator can be acceptable in infrastructure or plugin systems, but using it inside business services usually defeats the point of DI.

#### Production angle

Hidden dependencies lead to runtime failures, missing configuration, circular dependency workarounds and surprising behavior in tests.

#### Traps / caveats

- Do not use `ApplicationContext` as a normal dependency resolver in business code.
- A factory that only wraps a service locator has the same problem.
- Explicit constructor dependencies are usually better.

#### Optional Anki

Q: Why is Service Locator problematic?
A: It hides dependencies behind runtime lookup.

</details>

<details>
<summary><strong>DP-FW-005. How does Repository differ from DAO?</strong></summary>

#### Short answer

Repository represents a collection-like boundary for domain aggregates; DAO is a lower-level data access abstraction.

#### Interview answer

A DAO usually maps database operations for tables or records. A Repository is a domain-facing abstraction that loads and saves aggregate roots and hides persistence details from domain/application code.

In Spring Data, repository interfaces often combine both ideas, so the design intent matters.

#### Deep dive

A DDD repository should not become a dumping ground for every query. Complex read models may fit query services or projections better.

#### Production angle

Clear persistence boundaries keep domain logic from depending on SQL, JPA specifics or schema details.

#### Traps / caveats

- Do not expose `JpaRepository` everywhere without considering coupling.
- Do not return arbitrary internal entities from aggregate repositories.
- Read-heavy queries may need separate query models.

#### Optional Anki

Q: Repository vs DAO?
A: Repository is domain-facing; DAO is data-access-focused.

</details>

<a id="dp-fw-006"></a>

<details>
<summary><strong>DP-FW-006. What is the DTO pattern, and when should you use it?</strong></summary>

#### Short answer

A DTO is a data carrier used to transfer data across boundaries without exposing internal domain or persistence objects.

#### Interview answer

Use DTOs at API, messaging and external integration boundaries. They let you shape data for a specific contract, hide internal fields, avoid lazy-loading surprises and maintain backward compatibility.

DTOs should not contain core business behavior.

#### Deep dive

DTOs can be records, classes or generated models. The important part is that they are boundary contracts, not the domain model.

#### Production angle

DTOs prevent leaking JPA entities through REST APIs, which can expose sensitive data, trigger lazy loading or bind API compatibility to schema changes.

#### Traps / caveats

- Do not create unnecessary DTOs inside every private method.
- Do not put business invariants only in DTO validation.
- Keep external DTOs versioned and stable.

#### Optional Anki

Q: Why use DTOs at API boundaries?
A: To protect internal models and define stable external contracts.

</details>

<a id="dp-fw-007"></a>

<details>
<summary><strong>DP-FW-007. What is the Mapper pattern, and why is it useful?</strong></summary>

#### Short answer

A mapper converts data between models, such as entity to DTO or external request to command.

#### Interview answer

Mappers keep conversion logic out of controllers, entities and business services. They are useful when API models, persistence models and domain models differ.

For simple cases, manual mapping is often clearer. For repetitive cases, tools like MapStruct can help.

#### Deep dive

Mapping is a boundary operation. It should not hide major business decisions, load half the database accidentally, or mutate domain state in surprising ways.

#### Production angle

Clear mapping prevents leaking internal fields, reduces serialization bugs and makes API compatibility easier.

#### Traps / caveats

- Do not create "mapping hell" with too many nearly identical models.
- Do not trigger lazy loading unexpectedly during mapping.
- Generated mappers still need tests for important contracts.

#### Optional Anki

Q: Mapper's role?
A: Convert between boundary, domain and persistence models.

</details>

<a id="dp-fw-008"></a>

<details>
<summary><strong>DP-FW-008. What patterns are commonly seen in Hibernate/JPA usage?</strong></summary>

#### Short answer

Hibernate/JPA commonly expose Unit of Work, Identity Map, Proxy, Lazy Loading, Repository-like access and Data Mapper concepts.

#### Interview answer

The persistence context tracks loaded entities and changes, which is Unit of Work-like. It returns the same managed entity instance for the same identity, which is Identity Map-like. Lazy associations often use proxies. Spring Data repositories provide repository-style APIs.

These patterns explain much of JPA behavior.

#### Deep dive

JPA entities are not just POJOs once managed. Their lifecycle, identity, lazy loading and dirty checking depend on the persistence context.

#### Production angle

Understanding these patterns helps debug N+1 queries, lazy initialization exceptions, stale data and unexpected flushes.

#### Traps / caveats

- Do not ignore transaction and persistence context boundaries.
- Do not return lazy entities directly from controllers.
- Entity equality must account for persistence identity and proxies.

#### Optional Anki

Q: What JPA concept acts like Unit of Work?
A: The persistence context plus flush/dirty checking behavior.

</details>

<a id="dp-fw-009"></a>

<details>
<summary><strong>🧠 DP-FW-009. How do Unit of Work, Identity Map, Lazy Loading and Proxy appear in persistence frameworks?</strong></summary>

#### Short answer

The persistence context tracks changes, reuses entity instances by identity, and uses proxies or enhanced classes to load data lazily.

#### Interview answer

Unit of Work means changes are collected and flushed as a unit, often at transaction boundaries. Identity Map means the same database row maps to one managed object instance in a persistence context. Lazy Loading delays fetching associations until needed. Proxy enables lazy access by standing in for the real association.

Together, these patterns make ORM convenient but context-sensitive.

#### Deep dive

The same code can behave differently inside and outside a transaction because lazy loading and dirty checking require an active persistence context.

#### Production angle

These patterns are behind common incidents: N+1 query spikes, `LazyInitializationException`, unexpected updates, and memory growth from large persistence contexts.

#### Traps / caveats

- Lazy loading hides database access behind getters.
- Identity Map scope is the persistence context, not the whole application.
- Unit of Work can flush earlier than expected before queries.

#### Optional Anki

Q: Identity Map in JPA means what?
A: One managed object instance per database identity inside a persistence context.

</details>

<details>
<summary><strong>🧠 DP-FW-010. What is `FactoryBean`, and how is it different from a normal `@Bean` factory method?</strong></summary>

#### Short answer

`FactoryBean<T>` is a Spring bean that produces another object as the exposed bean; an `@Bean` method directly returns the bean instance.

#### Interview answer

With a normal `@Bean` method, Spring registers the returned object. With `FactoryBean`, the factory itself is a bean, but asking for its bean name usually returns the product of `getObject()`. To get the factory itself, Spring uses the `&beanName` convention.

It is mostly used by infrastructure, proxy factories and advanced integrations.

#### Deep dive

`FactoryBean` is useful when object creation needs special logic integrated with the Spring container. Most application code should prefer simple `@Bean` methods or component scanning.

#### Production angle

Understanding `FactoryBean` helps explain why a bean's runtime type may differ from the class that registered it.

#### Traps / caveats

- Business apps rarely need custom `FactoryBean`s.
- Do not confuse the factory bean with the object it produces.
- Type prediction can be tricky for tooling and diagnostics.

#### Optional Anki

Q: How do you retrieve a `FactoryBean` itself?
A: Prefix the bean name with `&`.

</details>
