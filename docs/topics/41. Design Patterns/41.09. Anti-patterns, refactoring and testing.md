# 41.09. Anti-patterns, refactoring and testing

---

<a id="dp-anti-001"></a>

<details>
<summary><strong>DP-ANTI-001. What is an anti-pattern, and how is it different from a trade-off?</strong></summary>

#### Short answer

An anti-pattern is a recurring solution that usually causes more harm than benefit; a trade-off is a conscious choice with known costs.

#### Interview answer

For example, Service Locator in business code often hides dependencies and hurts tests, so it is commonly called an anti-pattern. A trade-off might be using a simple switch instead of Strategy because the cases are fixed and local.

The difference is awareness, context and outcome.

#### Deep dive

Some designs are harmful only in certain contexts. Singleton can be acceptable for immutable infrastructure but bad for mutable business state.

#### Production angle

Senior engineers should explain the failure mode, not just label code as an anti-pattern.

#### Traps / caveats

- Do not use "anti-pattern" as a code-review insult.
- A design can start as a trade-off and become an anti-pattern when context changes.
- Always connect the smell to cost or risk.

#### Optional Anki

Q: Anti-pattern vs trade-off?
A: Anti-pattern is a recurring harmful solution; trade-off is a conscious contextual choice.

</details>

<a id="dp-anti-002"></a>

<details>
<summary><strong>DP-ANTI-002. What are Singleton abuse, global mutable state and Service Locator?</strong></summary>

#### Short answer

They are related ways to hide shared dependencies or state, often making code harder to test and reason about.

#### Interview answer

Singleton abuse uses globally reachable instances as convenient dependency containers or state holders. Global mutable state is data that many parts of the system can change without clear ownership. Service Locator hides dependencies behind runtime lookup.

All three reduce explicitness.

#### Deep dive

The core problem is not "one instance" by itself. The problem is hidden access, mutable shared state and unclear lifecycle.

#### Production angle

These designs cause test pollution, request data leaks, tenant leaks, hard-to-reproduce bugs and fragile startup ordering.

#### Traps / caveats

- A Spring singleton bean is fine when stateless and explicitly injected.
- Do not replace Service Locator with a factory that just delegates to a registry.
- Static mutable caches need strict ownership and concurrency policy.

#### Optional Anki

Q: Common problem with Singleton abuse and Service Locator?
A: Hidden dependencies and shared state.

</details>

<a id="dp-anti-003"></a>

<details>
<summary><strong>DP-ANTI-003. What is over-engineering with patterns?</strong></summary>

#### Short answer

It is using patterns and abstractions beyond the complexity the problem actually needs.

#### Interview answer

Over-engineering appears as factories for simple constructors, strategy hierarchies for two stable branches, interfaces with one implementation forever, or decorators and proxies hiding straightforward code.

The code may look flexible but becomes harder to read, test and debug.

#### Deep dive

The smell is speculative abstraction: designing for imagined future requirements while making current work harder.

#### Production angle

Over-engineering slows incident response and onboarding because developers must navigate layers before finding the actual behavior.

#### Traps / caveats

- Simplicity is not the same as poor design.
- Do not optimize only for theoretical extension.
- Remove abstractions when they no longer protect a real variation point.

#### Optional Anki

Q: Pattern over-engineering means what?
A: Adding pattern machinery without enough real design pressure to justify it.

</details>

<a id="dp-anti-004"></a>

<details>
<summary><strong>DP-ANTI-004. What is Golden Hammer?</strong></summary>

#### Short answer

Golden Hammer is applying a familiar solution everywhere, even when it does not fit.

#### Interview answer

In design patterns, Golden Hammer looks like "everything needs Strategy", "every class needs an interface", "all side effects should be events", or "AOP should handle every cross-cutting concern".

The engineer uses a preferred tool instead of analyzing the problem.

#### Deep dive

Golden Hammer often follows a successful previous use. The pattern worked once, so the team starts seeing every problem through that pattern.

#### Production angle

It creates inconsistent architecture, unnecessary complexity and solutions that fail under real operational constraints.

#### Traps / caveats

- Ask what problem the pattern solves here.
- Compare against the simplest viable design.
- Be willing to use different patterns in different bounded contexts.

#### Optional Anki

Q: Golden Hammer?
A: Overusing a familiar solution whether or not it fits.

</details>

<a id="dp-anti-005"></a>

<details>
<summary><strong>DP-ANTI-005. What is interface bloat?</strong></summary>

#### Short answer

Interface bloat is creating broad or unnecessary interfaces that clients do not need or implementations cannot support cleanly.

#### Interview answer

It appears as `UserService` with dozens of unrelated methods, or an interface created for every implementation with no real abstraction. Clients depend on operations they never use, tests mock too much, and implementations throw unsupported exceptions.

Good interfaces represent cohesive capabilities.

#### Deep dive

Interface bloat can come from mechanical DIP or premature pattern use. The interface keyword does not guarantee abstraction.

#### Production angle

Bloated interfaces cause ripple changes: adding one method forces many clients, mocks and implementations to change.

#### Traps / caveats

- Do not split into one-method interfaces without real clients.
- A concrete class can be acceptable when there is no meaningful abstraction.
- Interface ownership should belong to the client or policy that needs it.

#### Optional Anki

Q: Interface bloat symptom?
A: Clients must depend on, mock or implement methods they do not use.

</details>

<a id="dp-anti-006"></a>

<details>
<summary><strong>DP-ANTI-006. How do you detect that a pattern has become unnecessary complexity?</strong></summary>

#### Short answer

Look for indirection that no longer protects variation, repeated boilerplate, hard navigation, weak names and tests that mostly verify wiring.

#### Interview answer

A pattern may be unnecessary when there is only one implementation, no expected variants, no boundary being protected, and every change requires editing the abstraction and implementation together.

Another signal is that developers bypass the pattern because direct code is easier.

#### Deep dive

Use evidence: commit history, number of implementations, test value, debugging cost and onboarding feedback.

#### Production angle

Unnecessary complexity increases mean time to repair because the structure hides the code that actually runs.

#### Traps / caveats

- One implementation can still be valid if it protects an external boundary.
- Do not remove an abstraction used by other teams without compatibility planning.
- Check tests before simplifying.

#### Optional Anki

Q: Pattern complexity smell?
A: The abstraction changes together with its only implementation and protects no real variation.

</details>

<a id="dp-anti-007"></a>

<details>
<summary><strong>DP-ANTI-007. How do you decide whether to refactor code toward or away from a pattern?</strong></summary>

#### Short answer

Refactor toward a pattern when repeated change pain is clear; refactor away when the pattern adds indirection without benefit.

#### Interview answer

I look at change frequency, duplication, risk, testability and clarity. Repeated provider-specific conditionals may move toward Strategy or Adapter. A factory hierarchy with one implementation and no expected variants may move toward direct construction or simple DI.

The target design should reduce the next likely change.

#### Deep dive

Refactoring should preserve behavior. Characterization tests are useful before changing legacy design.

#### Production angle

Small, reversible steps are safer than replacing the whole design in one release.

#### Traps / caveats

- Do not refactor because a diagram looks cleaner.
- Do not remove an abstraction that protects a vendor or team boundary.
- Keep public APIs stable where possible.

#### Optional Anki

Q: Refactor toward pattern when?
A: When repeated change pain shows a real variation point or boundary problem.

</details>

<a id="dp-anti-008"></a>

<details>
<summary><strong>DP-ANTI-008. How can tests protect pattern refactoring?</strong></summary>

#### Short answer

Tests protect refactoring by locking observable behavior while internal structure changes.

#### Interview answer

Before refactoring, add characterization tests around current behavior, including edge cases and failure modes. Then move structure gradually: extract interfaces, introduce strategies, add adapters or remove unused factories. Tests should verify behavior, not the exact pattern shape.

For risky integrations, add contract tests around boundaries.

#### Deep dive

Good tests let you refactor from switch to Strategy or from static Singleton to DI without changing business outcomes.

#### Production angle

Tests reduce deployment risk when changing code organization in payment, orders, security, persistence or messaging paths.

#### Traps / caveats

- Do not write tests that freeze bad internal structure.
- Include failure and rollback behavior, not only happy path.
- Keep integration tests where framework behavior matters.

#### Optional Anki

Q: What should tests protect during pattern refactoring?
A: Observable behavior and contracts, not the old internal structure.

</details>
