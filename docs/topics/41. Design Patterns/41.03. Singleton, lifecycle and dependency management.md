# 41.03. Singleton, lifecycle and dependency management

---

<a id="dp-sng-001"></a>

<details>
<summary><strong>DP-SNG-001. What is the Singleton pattern, and what are its main risks?</strong></summary>

#### Short answer

Singleton ensures one globally accessible instance of a class, but it can hide dependencies, global state and testing problems.

#### Interview answer

The classic Singleton controls its own instance and exposes it through a static access point. It is often used for shared infrastructure or configuration, but in application code it easily becomes a global dependency.

The main risks are hidden coupling, mutable global state, hard unit tests, lifecycle problems and concurrency bugs.

#### Deep dive

Singleton solves "only one instance" and "global access" together. Often only one of those is really needed. In DI-based applications, the container can manage a single shared instance without making the class a global singleton.

#### Production angle

Singleton abuse causes surprising behavior between tests, tenants, requests and deployments because state can survive longer than intended.

#### Traps / caveats

- Singleton is not the same as a Spring singleton bean.
- Singleton does not make mutable state thread-safe.
- Static access makes replacement and mocking harder.

#### Optional Anki

Q: Main risk of Singleton?
A: It can turn dependencies and mutable state into hidden globals.

</details>

<details>
<summary><strong>DP-SNG-002. How can you implement a thread-safe Singleton in Java?</strong></summary>

#### Short answer

Common safe options are eager initialization, enum Singleton, initialization-on-demand holder, or double-checked locking with `volatile`.

#### Interview answer

For most interviews, I would mention enum Singleton and the holder idiom. Eager initialization is simple if construction is cheap. The holder idiom gives lazy initialization using class loading. Double-checked locking works in modern Java only when the instance field is `volatile`.

The best option depends on lifecycle, dependencies and whether you should use Singleton at all.

#### Deep dive

Thread-safety has two parts: safe publication of the instance and safe access to its internal state. A safe Singleton constructor does not make later mutations safe.

#### Production angle

In Spring applications, prefer container-managed singleton beans for services and infrastructure unless there is a strong reason for static Singleton.

#### Traps / caveats

- A synchronized accessor is simple but can be unnecessary overhead.
- Double-checked locking without `volatile` is broken.
- A thread-safe instance reference does not make the object behavior thread-safe.

#### Optional Anki

Q: Name two safe Singleton implementations.
A: Enum Singleton and initialization-on-demand holder.

</details>

<a id="dp-sng-003"></a>

<details>
<summary><strong>DP-SNG-003. What is the initialization-on-demand holder idiom?</strong></summary>

#### Short answer

It is a lazy Singleton implementation that relies on Java class initialization for thread-safe instance creation.

#### Interview answer

The outer class has a private constructor and a static method like `getInstance()`. Inside it, a private static nested holder class contains the singleton instance. The holder class is loaded only when referenced, and Java class initialization is thread-safe.

It gives lazy initialization without synchronizing every access.

#### Deep dive

This idiom works because the JVM initializes a class once, with proper synchronization. The instance is safely published after class initialization completes.

#### Production angle

It is useful for small standalone utilities, but less useful when the object needs injected dependencies, configuration or managed lifecycle.

#### Traps / caveats

- It does not solve mutable state concurrency.
- It does not fit objects that require Spring-managed dependencies.
- Constructor failures can make later access fail in surprising ways.

#### Optional Anki

Q: What makes the holder idiom thread-safe?
A: Java's class initialization guarantees.

</details>

<a id="dp-sng-004"></a>

<details>
<summary><strong>DP-SNG-004. What is double-checked locking, and why does it require `volatile`?</strong></summary>

#### Short answer

Double-checked locking avoids synchronization after initialization, but the instance field must be `volatile` for safe publication.

#### Interview answer

The pattern first checks if the instance is null, enters a synchronized block only if needed, checks again, and creates the instance. The second check prevents multiple creations when several threads reach the lock.

`volatile` is required so threads do not see a reference to an incompletely constructed object and so writes are visible in the correct order.

#### Deep dive

Without `volatile`, instruction reordering and visibility can let one thread observe a non-null reference before constructor effects are safely visible.

#### Production angle

Even when correct, double-checked locking is more complex than eager initialization, enum Singleton or the holder idiom. Prefer simpler options.

#### Traps / caveats

- The field must be `volatile`.
- The object itself must still be thread-safe.
- In Spring code, this pattern is usually a smell.

#### Optional Anki

Q: Why does double-checked locking need `volatile`?
A: For safe publication and visibility of the constructed instance.

</details>

<a id="dp-sng-005"></a>

<details>
<summary><strong>DP-SNG-005. How can an enum be used to implement Singleton in Java?</strong></summary>

#### Short answer

An enum with one constant gives a simple, serialization-safe Singleton instance.

#### Interview answer

You can write `enum AppSingleton { INSTANCE }` and add methods or fields to it. The JVM ensures one enum constant per classloader, and Java serialization preserves enum identity.

This is often the simplest pure-Java Singleton implementation.

#### Deep dive

Enum Singleton handles some classic Singleton problems, especially serialization. It is less flexible if you need lazy initialization with checked failures, inheritance, or dependency injection.

#### Production angle

Use enum Singleton mostly for small stateless utilities or fixed process-wide services, not for business services that need configuration, tests and lifecycle management.

#### Traps / caveats

- It is per classloader, not universally global across all JVM contexts.
- It does not automatically make mutable fields safe.
- It is awkward for dependencies supplied by a DI container.

#### Optional Anki

Q: Why is enum Singleton popular?
A: It is concise and preserves Singleton identity during serialization.

</details>

<a id="dp-sng-006"></a>

<details>
<summary><strong>🧠 DP-SNG-006. How can reflection or serialization break a Singleton?</strong></summary>

#### Short answer

Reflection can call private constructors, and deserialization can create a new object unless the Singleton defends against it.

#### Interview answer

Classic Singletons rely on private constructors and a static instance. Reflection can make the constructor accessible and create another instance. Serialization can deserialize a separate instance unless `readResolve()` returns the canonical instance.

Enum Singletons are more resistant to these problems.

#### Deep dive

Modern Java module boundaries and security policies can reduce reflective access, but application code should not rely on that as its main Singleton guarantee.

#### Production angle

This matters mostly for libraries, frameworks, serialization-heavy systems and defensive interview knowledge. In typical Spring services, the bigger issue is hidden global state.

#### Traps / caveats

- `readResolve()` must return the existing instance.
- Defensive constructors can still be bypassed in some low-level scenarios.
- Serialization identity is not the same as thread-safety.

#### Optional Anki

Q: How do you preserve Singleton identity during deserialization?
A: Use `readResolve()` or prefer enum Singleton where appropriate.

</details>

<a id="dp-sng-007"></a>

<details>
<summary><strong>DP-SNG-007. How is a Spring singleton bean different from a classic GoF Singleton?</strong></summary>

#### Short answer

A Spring singleton bean is one bean instance per Spring application context, not a class-enforced global instance.

#### Interview answer

Spring singleton is a scope. The container creates and reuses one bean instance for that context. The class itself can still have a public constructor, and another instance can be created manually with `new`.

A GoF Singleton controls its own instance through static access and private construction.

#### Deep dive

Multiple application contexts can have multiple singleton bean instances. Tests, parent-child contexts and web applications can all affect scope.

#### Production angle

Spring singleton beans are the normal default for stateless services. They work well with constructor injection, proxies, configuration and lifecycle callbacks.

#### Traps / caveats

- Spring singleton is not JVM-global.
- Manually created objects are outside Spring lifecycle and proxies.
- Singleton scope does not imply thread-safe mutable state.

#### Optional Anki

Q: Spring singleton scope means what?
A: One bean instance per Spring application context.

</details>

<a id="dp-sng-008"></a>

<details>
<summary><strong>DP-SNG-008. Is a Spring singleton bean automatically thread-safe?</strong></summary>

#### Short answer

No. A singleton bean is shared, so it must be stateless or manage mutable state safely.

#### Interview answer

Spring creates one instance by default, and many request threads can call it concurrently. If the bean only uses local variables and thread-safe collaborators, it is usually fine. If it stores mutable request data in fields, it is unsafe.

Thread-safety depends on the bean's state and collaborators, not on the scope name.

#### Deep dive

Common safe designs use immutable fields, constructor injection, local variables, database transactions and thread-safe clients. Unsafe designs store current user, current request, temporary buffers or mutable collections in fields.

#### Production angle

This is a frequent backend bug: data from one request appears in another request because a singleton service kept request state in a field.

#### Traps / caveats

- `@Service` does not make code thread-safe.
- `volatile` does not make compound state safe.
- Prototype scope is not usually the right fix for bad state ownership.

#### Optional Anki

Q: Are Spring singleton services automatically thread-safe?
A: No. They are shared instances and must be stateless or synchronized by design.

</details>

<a id="dp-sng-009"></a>

<details>
<summary><strong>DP-SNG-009. When is Singleton acceptable in production code?</strong></summary>

#### Short answer

Singleton can be acceptable for truly process-wide, stateless or immutable infrastructure with clear lifecycle and no hidden business dependencies.

#### Interview answer

Examples might include enum constants, stateless utility-like services, immutable configuration snapshots, or low-level infrastructure where a single process-wide instance is intentional.

Even then, I prefer dependency injection for application services because it keeps dependencies explicit and testable.

#### Deep dive

The key question is whether global access is needed. Often "one instance" can be handled by DI scope while avoiding static access.

#### Production angle

Acceptable Singletons should be easy to initialize, observe, shut down and replace in tests. If not, container-managed lifecycle is usually better.

#### Traps / caveats

- Do not put tenant, user or request state in a Singleton.
- Do not use Singleton to avoid passing dependencies.
- Do not hide I/O clients behind static access without lifecycle control.

#### Optional Anki

Q: Safe Singleton shape?
A: Stateless or immutable, process-wide by intent, with clear lifecycle.

</details>

<details>
<summary><strong>DP-SNG-010. When should Singleton be replaced with dependency injection?</strong></summary>

#### Short answer

Replace Singleton with DI when the object is a service dependency, needs configuration, has collaborators, should be mocked, or needs managed lifecycle.

#### Interview answer

In most Spring backend code, business services, clients, repositories, policies and handlers should be injected. That makes dependencies visible in constructors, allows tests to provide fakes, and lets Spring manage proxies, configuration and lifecycle.

Static singleton access hides all of that.

#### Deep dive

Migrating usually means introducing an interface or class dependency, injecting it through constructors, and replacing `Singleton.getInstance()` calls gradually.

#### Production angle

DI improves observability and operability because dependencies are managed consistently by the container and can participate in metrics, tracing, transactions and shutdown.

#### Traps / caveats

- Do not replace static Singleton with `ApplicationContext.getBean()` in business code.
- Avoid global mutable state disguised as an injected bean.
- Ensure tests use the same lifecycle assumptions as production where needed.

#### Optional Anki

Q: Why prefer DI over Singleton for services?
A: DI keeps dependencies explicit, testable and lifecycle-managed.

</details>
