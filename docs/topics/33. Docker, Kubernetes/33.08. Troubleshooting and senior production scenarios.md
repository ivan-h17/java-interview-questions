# Troubleshooting and senior production scenarios

---

<a id="k8s-trbl-001"></a>

<details>
<summary><strong>K8S-TRBL-001. How do you debug a Pod that is not starting?</strong></summary>

#### Short answer

Check Pod events, container status, image pull state, logs, resource scheduling, config mounts and recent changes.

#### Interview answer

I start with `kubectl describe pod` because events often show scheduling failures, image pull errors, mount errors or probe failures. Then I check `kubectl logs`, including previous container logs if it restarted. I compare the manifest with the expected image, command, environment, volumes and resources.

#### Deep dive

The failure can happen before the app starts: insufficient resources, bad image reference, missing Secret, failed volume mount or wrong command. If the app starts and exits, logs and exit code become more important.

#### Production angle

Tie the investigation to the rollout: what changed in image, config, secret, resources, node pool or deployment template?

#### Traps / caveats

- `kubectl logs` may be empty if the container never started.
- Events can expire, so collect evidence quickly during incidents.

#### Optional Anki

Q: First command for a Pod not starting?
A: `kubectl describe pod`.

</details>

<a id="k8s-trbl-002"></a>

<details>
<summary><strong>K8S-TRBL-002. How do you debug `ImagePullBackOff`?</strong></summary>

#### Short answer

Verify the image reference, registry access, imagePullSecrets, tag or digest existence, platform architecture and registry health.

#### Interview answer

`ImagePullBackOff` means Kubernetes failed to pull the image and is backing off retries. I inspect Pod events for the exact error: unauthorized, not found, timeout, TLS issue or rate limit. Then I check registry credentials, repository path, tag or digest, and node network access.

#### Deep dive

Private registries require correct imagePullSecrets or node-level credentials. Multi-architecture images can also fail if the image does not support the node architecture.

#### Production angle

Use immutable image references and CI checks that verify the image exists before updating manifests.

#### Traps / caveats

- A tag may exist in one registry environment but not another.
- Reusing mutable tags can make one node pull different content than another.

#### Optional Anki

Q: What does `ImagePullBackOff` indicate?
A: Kubernetes cannot pull the container image and is delaying retries.

</details>

<a id="k8s-trbl-003"></a>

<details>
<summary><strong>K8S-TRBL-003. How do you debug `CrashLoopBackOff`?</strong></summary>

#### Short answer

Check why the container exits repeatedly: logs, previous logs, exit code, command, config, probes and dependencies.

#### Interview answer

I run `kubectl logs --previous` when the container restarts quickly. Then I inspect the exit code and events. Common causes are missing config, failed startup validation, wrong command, database migration failure, port conflicts, permission errors or liveness killing the container.

#### Deep dive

CrashLoopBackOff is a symptom, not a root cause. The container may be exiting by itself, or Kubernetes may be restarting it because a probe fails.

#### Production angle

Compare the failing Pod with the last known good release: image, environment variables, Secrets, ConfigMaps, resource limits and startup timing.

#### Traps / caveats

- Current logs may only show the latest failed attempt; previous logs often contain the root cause.
- Do not assume every CrashLoop is an application bug; probes and platform config can cause it.

#### Optional Anki

Q: Which logs are useful for fast-restarting containers?
A: Previous container logs.

</details>

<a id="k8s-trbl-004"></a>

<details>
<summary><strong>K8S-TRBL-004. How do you investigate and fix a Java Pod that is repeatedly `OOMKilled`?</strong></summary>

#### Short answer

Confirm container memory usage and limits, then inspect heap, non-heap memory, thread count, direct buffers, traffic and recent changes.

#### Interview answer

I check events and metrics to confirm `OOMKilled` and see memory growth. Then I compare `-Xmx` or `MaxRAMPercentage` with the container limit. I look for heap leaks, off-heap usage, direct buffers, metaspace growth, too many threads, memory-backed volumes or agent overhead.

#### Deep dive

If the kernel kills the container, Java may not produce a heap dump. If Java throws `OutOfMemoryError`, heap dump and GC logs may help. These are different failure modes.

#### Production angle

Fixes can include memory leak repair, lower heap, higher container memory, fewer threads, smaller buffers, better limits, or load reduction. Validate with metrics after rollout.

#### Traps / caveats

- Do not just increase memory without checking for a leak.
- Do not set heap equal to container limit.

#### Optional Anki

Q: What memory besides heap can cause `OOMKilled`?
A: Thread stacks, direct buffers, metaspace, native memory, agents and memory-backed volumes.

</details>

<a id="k8s-trbl-005"></a>

<details>
<summary><strong>K8S-TRBL-005. How do you debug a Pod stuck in `Pending`?</strong></summary>

#### Short answer

Check scheduling events for insufficient resources, node selectors, taints, affinity, quotas, PVC binding or image pull constraints.

#### Interview answer

`Pending` usually means the Pod has not been scheduled or cannot complete setup. `kubectl describe pod` will often show messages such as insufficient CPU, unsatisfied affinity, missing toleration, unbound PVC, quota exceeded or no matching nodes.

#### Deep dive

Pending is different from crashing. The application may not have started at all. The root cause is often cluster capacity or manifest constraints.

#### Production angle

Options include lowering requests, adding capacity, fixing affinity/tolerations, resolving PVC issues or changing rollout strategy.

#### Traps / caveats

- A Pod can be Pending because storage cannot be provisioned, not only because CPU is missing.
- Strict anti-affinity can block scheduling in small clusters.

#### Optional Anki

Q: What does Pending usually point to?
A: Scheduling or setup failure before the app runs.

</details>

<a id="k8s-trbl-006"></a>

<details>
<summary><strong>K8S-TRBL-006. How do you debug a Service that returns no traffic?</strong></summary>

#### Short answer

Check Service selector, Pod labels, endpoints, readiness, ports and network policies.

#### Interview answer

I inspect the Service and EndpointSlices to see whether there are ready backends. Then I verify the selector matches Pod labels, the target port maps to the container port, and Pods are ready. If endpoints exist, I test from inside the cluster and check NetworkPolicy or application-level failures.

#### Deep dive

Traffic path matters: client DNS, Service, endpoints, kube-proxy or data plane, Pod networking and app port all need to align.

#### Production angle

This is common after label changes, port renames, readiness failures or accidental selector mismatch during deployment.

#### Traps / caveats

- A running Pod is not necessarily a ready endpoint.
- A Service can resolve in DNS even when it has no backends.

#### Optional Anki

Q: What object shows the Service's actual backends?
A: EndpointSlices or Endpoints.

</details>

<a id="k8s-trbl-007"></a>

<details>
<summary><strong>K8S-TRBL-007. How do you debug DNS or service-to-service connectivity issues in Kubernetes?</strong></summary>

#### Short answer

Test DNS resolution and network reachability from a Pod, then check Services, endpoints, ports, NetworkPolicy, client config and dependency health.

#### Interview answer

I start from the calling Pod's namespace because search paths and policies matter. I test the Service DNS name, full DNS name, port connectivity and HTTP response. Then I inspect the target Service, EndpointSlices, ready Pods, NetworkPolicies and application logs.

#### Deep dive

Java clients may also have DNS caching, connection pool reuse or stale connections that make service changes appear as network issues.

#### Production angle

Good diagnostics include request metrics, dependency latency, connection pool metrics and clear error classification for DNS, connect timeout, read timeout and HTTP status errors.

#### Traps / caveats

- `curl` from a debug Pod proves network path, not Java client behavior.
- NetworkPolicy can allow ingress but block egress, or the reverse.

#### Optional Anki

Q: Why test from the caller namespace?
A: DNS search paths and NetworkPolicy can be namespace-dependent.

</details>

<a id="k8s-trbl-008"></a>

<details>
<summary><strong>K8S-TRBL-008. How do you take a thread dump or heap dump from a Java application running in Kubernetes?</strong></summary>

#### Short answer

Use JVM tools inside the container or an appropriate debug approach, while considering image tooling, permissions, disk space and sensitive data.

#### Interview answer

If tools are available, `jcmd`, `jstack` or `jmap` can collect diagnostics from the Java process. In minimal images, you may need an ephemeral debug container, sidecar tooling, a debug build image, or preconfigured JVM diagnostic endpoints. Dumps must be stored somewhere with enough space and copied securely.

#### Deep dive

Thread dumps are usually smaller and safer to collect during latency or deadlock issues. Heap dumps can be huge and contain secrets or personal data.

#### Production angle

Plan diagnostics before incidents: permissions, commands, storage, redaction and access controls should be documented in a runbook.

#### Traps / caveats

- A distroless image may not include shell or JDK tools.
- Heap dumps can trigger disk pressure or expose sensitive data.

#### Optional Anki

Q: Why are heap dumps sensitive?
A: They may contain secrets, tokens and user data from memory.

</details>

<a id="k8s-trbl-009"></a>

<details>
<summary><strong>K8S-TRBL-009. How would you investigate high latency that appears only in Kubernetes?</strong></summary>

#### Short answer

Compare app, container, node and network signals: CPU throttling, GC, pool saturation, DNS, service mesh, Ingress, resource limits and downstream latency.

#### Interview answer

I first confirm scope: one endpoint, one version, one node, one zone or all Pods. Then I inspect RED metrics, traces, Java GC and thread metrics, CPU throttling, memory pressure, connection pool wait time, DNS failures, Ingress latency and downstream dependency metrics.

#### Deep dive

Kubernetes-specific causes include CPU limits, noisy nodes, service mesh sidecar overhead, wrong requests, load balancing imbalance, NetworkPolicy or DNS issues, and cold Pods during rollout.

#### Production angle

Look for differences between local, Docker Compose and Kubernetes: resource constraints, network hops, TLS, proxies, secrets/config and startup warm-up.

#### Traps / caveats

- Low CPU usage does not rule out pool saturation or downstream waits.
- Average latency can hide p99 issues caused by a subset of Pods.

#### Optional Anki

Q: What Kubernetes setting commonly causes latency without errors?
A: CPU throttling from CPU limits.

</details>

<a id="k8s-trbl-010"></a>

<details>
<summary><strong>K8S-TRBL-010. How would you investigate a sudden spike in 5xx errors after deployment?</strong></summary>

#### Short answer

Correlate errors with the rollout, compare old and new versions, inspect readiness, logs, traces, dependencies, config and database compatibility.

#### Interview answer

I check deployment timeline, affected routes, status codes, version labels and whether errors come from app, Ingress or upstream proxies. Then I inspect new Pod logs, readiness failures, traces, dependency errors, config changes and database migrations. If impact is high, pause rollout or roll back when safe.

#### Deep dive

A 5xx spike may be caused by incompatible schema, missing config, bad secret, changed endpoint behavior, failing warm-up, connection pool exhaustion or no ready endpoints.

#### Production angle

A good release process exposes version labels in logs, metrics and traces so you can compare old and new versions quickly.

#### Traps / caveats

- Rolling back code may be unsafe if the database migration was not backward compatible.
- Ingress 5xx and application 5xx have different root causes.

#### Optional Anki

Q: What should you do first during a bad rollout?
A: Assess impact, pause or roll back when safe, and correlate errors with changed version/config.

</details>

<a id="dk-scen-001"></a>

<details>
<summary><strong>DK-SCEN-001. A service works in Docker Compose but fails in Kubernetes. What differences would you check?</strong></summary>

#### Short answer

Check networking, DNS names, config, secrets, resource limits, probes, startup order, filesystem permissions, service discovery and external dependencies.

#### Interview answer

Docker Compose and Kubernetes differ in service discovery, readiness, volume behavior, restart semantics, resource constraints and security context. In Compose, a service may start after `depends_on`, but readiness is still not guaranteed. In Kubernetes, probes, ConfigMaps, Secrets, Services and DNS names must be configured explicitly.

#### Deep dive

Local Compose often runs with fewer constraints: no CPU limits, different user IDs, different network paths, local bind mounts and simpler secrets. Kubernetes may expose missing assumptions.

#### Production angle

Use environment parity checks, integration tests and clear startup validation to catch differences before production.

#### Traps / caveats

- `localhost` means different things depending on where the code runs.
- A startup-order fix is not a substitute for retry and readiness logic.

#### Optional Anki

Q: Why can Compose success hide Kubernetes failure?
A: Compose often has different networking, config, resource and security behavior.

</details>

<a id="dk-scen-002"></a>

<details>
<summary><strong>DK-SCEN-002. How would you decide whether a small Java service should run on Kubernetes at all?</strong></summary>

#### Short answer

Compare the operational benefits against complexity, team skill, scale, reliability needs and existing platform investment.

#### Interview answer

Kubernetes helps when you need standardized deployments, autoscaling, self-healing, service discovery, rollout control and many services sharing a platform. For one small service, a managed PaaS, VM, container service or serverless platform may be simpler and cheaper.

#### Deep dive

The decision should include who will own cluster operations, security updates, observability, CI/CD, incident response, cost and developer experience.

#### Production angle

A Senior engineer should avoid accidental platform complexity. Kubernetes is powerful, but it is not automatically the best runtime for every Java service.

#### Traps / caveats

- Do not adopt Kubernetes only because it is popular.
- Do not reject it if the organization already has a mature shared platform that lowers the operational cost.

#### Optional Anki

Q: What is the key Kubernetes adoption trade-off?
A: Operational power and standardization versus platform complexity and ownership cost.

</details>
