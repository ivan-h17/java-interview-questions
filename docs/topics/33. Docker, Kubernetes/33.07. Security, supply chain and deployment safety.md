# Security, supply chain and deployment safety

---

<a id="dk-sec-001"></a>

<details>
<summary><strong>DK-SEC-001. Are containers a security boundary?</strong></summary>

#### Short answer

Containers provide useful isolation, but they should not be treated as a complete security boundary like a separate machine or strong sandbox.

#### Interview answer

Containers isolate processes using kernel features, but they share the host kernel. Misconfigurations such as privileged mode, broad capabilities, host mounts or Docker socket access can break assumptions. A container escape or host kernel issue can affect other workloads.

#### Deep dive

Security comes from layers: minimal images, non-root users, least privilege, patched hosts, runtime policies, network controls, RBAC and admission policies.

#### Production angle

For multi-tenant or sensitive workloads, isolation requirements may require stronger boundaries, separate nodes, separate clusters or VMs.

#### Traps / caveats

- Do not run untrusted code in a normal privileged production container.
- Do not assume namespace isolation protects against every host-level risk.

#### Optional Anki

Q: Why are containers not a perfect security boundary?
A: They share the host kernel and can be weakened by privileges and mounts.

</details>

<a id="dk-sec-002"></a>

<details>
<summary><strong>DK-SEC-002. Why should containers usually run as a non-root user?</strong></summary>

#### Short answer

Running as non-root reduces the impact of application compromise and avoids unnecessary privileges inside the container.

#### Interview answer

If an attacker gains code execution in a root container, they have more options to modify files, bind privileged ports or abuse misconfigurations. A non-root user limits what the process can do and aligns with least privilege.

#### Deep dive

Non-root should be combined with proper file ownership, read-only root filesystems where practical, dropped capabilities and a restricted SecurityContext.

#### Production angle

For Spring Boot services, non-root usually works well because the app does not need root privileges to serve traffic on high ports such as 8080.

#### Traps / caveats

- Simply setting `USER` can break file permissions if directories are owned by root.
- Non-root is not enough if the container is privileged or mounts sensitive host paths.

#### Optional Anki

Q: Why run containers as non-root?
A: To reduce the impact of compromise and enforce least privilege.

</details>

<a id="dk-sec-003"></a>

<details>
<summary><strong>DK-SEC-003. How do Linux capabilities, read-only filesystems and SecurityContext reduce risk?</strong></summary>

#### Short answer

They remove unnecessary privileges and filesystem write access from the containerized process.

#### Interview answer

Linux capabilities split root privileges into smaller permissions. Dropping unnecessary capabilities limits what a process can do. A read-only root filesystem prevents many runtime modifications. Kubernetes SecurityContext lets you configure users, privilege escalation, capabilities and filesystem behavior.

#### Deep dive

For many Java services, the app only needs write access to temporary directories and no special Linux capabilities. If it needs temporary storage, mount a specific writable volume instead of leaving the whole filesystem writable.

#### Production angle

These controls reduce post-compromise options and help pass cluster security policies.

#### Traps / caveats

- Some agents or native tools may require specific write paths; test before enforcing read-only root.
- Dropping capabilities should be explicit and reviewed, not guessed blindly.

#### Optional Anki

Q: What does `allowPrivilegeEscalation: false` help prevent?
A: Processes gaining more privileges than intended.

</details>

<a id="dk-sec-004"></a>

<details>
<summary><strong>DK-SEC-004. How can secrets leak through image layers, environment variables, logs or diagnostics?</strong></summary>

#### Short answer

Secrets can persist in build history, image layers, process environments, application logs, Actuator endpoints, heap dumps, thread dumps and CI output.

#### Interview answer

If a secret is copied into an image or passed during build, it may remain in a lower layer. If passed as an environment variable, it can appear in diagnostics or process metadata. Applications can also accidentally log secrets from configuration, exceptions or debug dumps.

#### Deep dive

Secret safety needs controls across build, deploy and runtime: secret scanning, restricted logs, masked CI output, RBAC, encryption at rest and careful diagnostic handling.

#### Production angle

After a secret leak, rotate the credential and review where it may have been copied. Deleting a log line or image is not enough.

#### Traps / caveats

- Base64-encoded Kubernetes Secret manifests are still plaintext-equivalent for anyone who can read them.
- Heap dumps can contain passwords, tokens and personal data.

#### Optional Anki

Q: What must happen after a secret is exposed?
A: Rotate or revoke it, then remove and audit exposure paths.

</details>

<a id="dk-sec-005"></a>

<details>
<summary><strong>DK-SEC-005. What are image vulnerability scanning, SBOMs, signing and provenance?</strong></summary>

#### Short answer

They are supply-chain controls: scanning finds known vulnerabilities, SBOMs list components, signing verifies origin, and provenance describes how an artifact was built.

#### Interview answer

Container scanning checks OS packages and sometimes language dependencies for known CVEs. An SBOM records what is inside the image. Signing helps verify that an image came from a trusted build process. Provenance or attestations record build inputs and steps.

#### Deep dive

These controls work best together. A signed image can still contain a vulnerability; a scan result needs triage; an SBOM helps incident response when a library CVE appears.

#### Production angle

CI/CD should scan images, attach metadata, enforce policy, and keep enough artifact history to support rollback and audits.

#### Traps / caveats

- Scanner results can include false positives and unexploitable CVEs, but ignoring all findings is unsafe.
- Signing does not prove the code is bug-free; it proves integrity and origin.

#### Optional Anki

Q: What does an SBOM provide?
A: A list of components included in the artifact or image.

</details>

<a id="dk-sec-006"></a>

<details>
<summary><strong>DK-SEC-006. What is the risk of mounting the Docker socket into a container?</strong></summary>

#### Short answer

Access to the Docker socket can effectively give the container control over the host Docker daemon.

#### Interview answer

If a container can talk to `/var/run/docker.sock`, it may create privileged containers, mount host paths or inspect other containers. That can become host-level compromise, not just application compromise.

#### Deep dive

This pattern is sometimes used for build tools or local development convenience, but it is highly sensitive in shared or production environments.

#### Production angle

Avoid mounting the Docker socket into application containers. Use purpose-built build systems, restricted runners or rootless/buildkit-based approaches with least privilege.

#### Traps / caveats

- Read-only mounting the socket does not necessarily make Docker API access safe.
- CI runners with Docker socket access should be treated as highly privileged.

#### Optional Anki

Q: Why is Docker socket access dangerous?
A: It can allow host-level control through the Docker daemon.

</details>

<a id="k8s-sec-001"></a>

<details>
<summary><strong>K8S-SEC-001. What are RBAC and ServiceAccounts in Kubernetes?</strong></summary>

#### Short answer

RBAC controls who can perform actions on Kubernetes resources; ServiceAccounts give Pods an identity for API access.

#### Interview answer

RBAC uses Roles or ClusterRoles and binds them to users, groups or ServiceAccounts. A Pod can run with a ServiceAccount, and that account's permissions determine what Kubernetes API operations the workload can perform.

#### Deep dive

Most application Pods do not need broad Kubernetes API access. If a service only serves HTTP and never calls the Kubernetes API, it should have minimal or no API permissions.

#### Production angle

Least-privilege ServiceAccounts reduce blast radius if a Pod is compromised.

#### Traps / caveats

- Do not run app Pods with default or overly broad ServiceAccounts.
- ClusterRoleBinding grants cluster-wide permissions and should be reviewed carefully.

#### Optional Anki

Q: What identity does a Pod use for Kubernetes API access?
A: A ServiceAccount.

</details>

<a id="k8s-sec-002"></a>

<details>
<summary><strong>K8S-SEC-002. What are the security limitations of Kubernetes Secrets?</strong></summary>

#### Short answer

Kubernetes Secrets are convenient delivery objects, but access control, encryption, audit and external secret management still matter.

#### Interview answer

Secrets are base64-encoded in manifests and can be read by anyone with API permission to get them. They may be mounted into Pods, exposed through environment variables, included in backups or leaked through logs and dumps. Encryption at rest may need explicit cluster configuration.

#### Deep dive

Many teams use external secret managers with operators or CSI drivers to avoid storing plaintext secrets in Git and to support rotation.

#### Production angle

Restrict Secret access with RBAC, avoid broad namespace permissions, encrypt at rest, audit access and rotate credentials after exposure.

#### Traps / caveats

- Base64 is not encryption.
- A user who can create Pods in a namespace may be able to mount Secrets from that namespace, depending on policy.

#### Optional Anki

Q: What is a key limitation of Kubernetes Secrets?
A: They are only as safe as RBAC, encryption, audit and delivery controls around them.

</details>

<a id="k8s-deploy-001"></a>

<details>
<summary><strong>K8S-DEPLOY-001. Why should production deployments use immutable image references and release metadata?</strong></summary>

#### Short answer

They make deployments reproducible, auditable and debuggable.

#### Interview answer

Immutable image references, preferably digests or protected unique tags, identify exactly what is running. Release metadata such as commit SHA, build time, version, owner and config version helps connect incidents to changes.

#### Deep dive

Kubernetes manifests, image labels, annotations and monitoring labels can all carry release identity. The goal is to answer "what code and config is this Pod running?" quickly.

#### Production angle

During rollback, CVE response or a 5xx spike, exact image identity is critical.

#### Traps / caveats

- Mutable tags can make a restart run different code without a manifest change.
- Metadata should not include secrets or high-cardinality user data.

#### Optional Anki

Q: What does immutable image reference support?
A: Reproducible deploys, audit, rollback and incident investigation.

</details>

<a id="k8s-deploy-002"></a>

<details>
<summary><strong>K8S-DEPLOY-002. How do rolling deployments constrain database migrations?</strong></summary>

#### Short answer

During a rolling deployment, old and new application versions may run at the same time, so schema changes must be backward and forward compatible.

#### Interview answer

You cannot safely deploy code that requires a new schema while old Pods still expect the old schema, unless the change is compatible. The usual pattern is expand-and-contract: add compatible schema first, deploy code that can use both, backfill, then remove old columns or behavior later.

#### Deep dive

Irreversible migrations, column renames, type changes and constraint changes are risky during rolling updates. Migration Jobs should be idempotent and observable.

#### Production angle

Many "Kubernetes deployment" failures are actually database compatibility failures.

#### Traps / caveats

- Rollback of code may not rollback data or schema safely.
- Running migrations automatically on every app startup can cause race conditions.

#### Optional Anki

Q: What schema pattern fits rolling deployments?
A: Expand-and-contract migration.

</details>

<a id="k8s-deploy-003"></a>

<details>
<summary><strong>K8S-DEPLOY-003. When would you use Helm, Kustomize or GitOps?</strong></summary>

#### Short answer

Use Helm for packaged parameterized charts, Kustomize for overlay-based manifest customization, and GitOps for reconciling cluster state from versioned Git changes.

#### Interview answer

Helm is useful when packaging reusable applications or managing many values. Kustomize works well when starting from base YAML and applying environment overlays. GitOps tools such as Argo CD or Flux continuously apply and reconcile approved manifests from Git.

#### Deep dive

These tools solve different problems and can be combined. The key is keeping generated manifests reviewable and avoiding hidden environment-specific behavior.

#### Production angle

For Java services, deployment tooling should support review, rollback, config separation, secret handling and traceability.

#### Traps / caveats

- Helm values can become an untyped configuration dumping ground.
- GitOps auto-sync plus unsafe database migrations can make rollback dangerous.

#### Optional Anki

Q: What is the core idea of GitOps?
A: Git is the reviewed source of desired deployment state, reconciled into the cluster.

</details>

<a id="k8s-deploy-004"></a>

<details>
<summary><strong>K8S-DEPLOY-004. What Kubernetes settings matter most for zero or near-zero downtime deployment?</strong></summary>

#### Short answer

Use multiple replicas, correct readiness probes, graceful shutdown, conservative rollout settings, capacity headroom and compatible app/database changes.

#### Interview answer

A zero-downtime deployment needs at least enough replicas to serve traffic while some are updating. Readiness must only pass when Pods are truly ready. Termination must drain in-flight requests. `maxUnavailable` and `maxSurge` should preserve capacity. Old and new versions must be compatible with APIs, messages and database schema.

#### Deep dive

Kubernetes can orchestrate replacement, but application design still matters: idempotency, connection draining, migrations, cache compatibility and client retries are part of the release.

#### Production angle

Watch rollout metrics, error rate, latency, saturation and dependency metrics during deployment, not just Pod status.

#### Traps / caveats

- One replica cannot provide zero downtime during normal replacement.
- Passing liveness does not mean the Pod is ready for traffic.

#### Optional Anki

Q: What must be true besides Kubernetes rollout settings?
A: Old and new application versions must be compatible.

</details>
