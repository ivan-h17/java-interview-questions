# Resources, autoscaling and Java runtime sizing

---

<a id="k8s-res-001"></a>

<details>
<summary><strong>K8S-RES-001. What are CPU and memory requests and limits in Kubernetes?</strong></summary>

#### Short answer

Requests are the resources Kubernetes reserves for scheduling; limits are the maximum resources the container is allowed to use.

#### Interview answer

The scheduler uses requests to decide where a Pod can fit. Limits are enforced by the node runtime and kernel. A container can often use more CPU than requested if available, but if it hits its CPU limit it may be throttled. If it exceeds its memory cgroup limit, it can be killed.

#### Deep dive

Requests affect capacity planning and placement. Limits affect runtime behavior. Setting neither can cause noisy-neighbor issues; setting bad limits can cause throttling or OOM kills.

#### Production angle

For Java services, resource settings must account for heap, non-heap memory, thread count, traffic shape and scaling behavior.

#### Traps / caveats

- Memory request is not a maximum; memory limit is.
- A Pod can be unschedulable if requests are too high for available nodes.

#### Optional Anki

Q: What does the scheduler use for placement?
A: Resource requests.

</details>

<a id="k8s-res-002"></a>

<details>
<summary><strong>K8S-RES-002. How are CPU limits and memory limits enforced differently?</strong></summary>

#### Short answer

CPU limits throttle execution; memory limits can cause the process to be killed.

#### Interview answer

When a container reaches its CPU limit, the kernel restricts how much CPU time it can use. The process usually continues but may become slower. When memory allocation cannot be satisfied within the container memory limit, the container can be terminated with an OOM kill.

#### Deep dive

CPU throttling can increase latency without obvious application errors. Memory limits are more abrupt because the JVM may not get a chance to throw a normal Java exception before the process dies.

#### Production angle

High p99 latency with low application errors can be caused by CPU throttling. Repeated `OOMKilled` events usually require memory sizing or leak investigation.

#### Traps / caveats

- CPU throttling is not always visible from inside normal application logs.
- Memory limit enforcement is reactive and can look like a sudden process death.

#### Optional Anki

Q: CPU limit vs memory limit failure mode?
A: CPU throttles; memory can OOM kill.

</details>

<a id="k8s-res-003"></a>

<details>
<summary><strong>K8S-RES-003. How should you set resource requests and limits for a Java service?</strong></summary>

#### Short answer

Start from load tests and production telemetry, then set requests for normal needed capacity and limits with enough headroom for JVM overhead and bursts.

#### Interview answer

I would measure CPU, memory, GC, latency, thread pools and connection pools under expected traffic. Memory limits must include heap, metaspace, direct buffers, thread stacks, code cache, native libraries and the OS/runtime overhead. CPU requests should reflect capacity needed to meet latency targets.

#### Deep dive

Many teams avoid strict CPU limits for latency-sensitive Java services or set them carefully because throttling can hurt p99 latency. Memory limits are usually necessary to protect nodes, but they must be sized realistically.

#### Production angle

Resource settings should be reviewed after real traffic, not guessed once and forgotten.

#### Traps / caveats

- Do not set `-Xmx` equal to the container memory limit.
- Do not size only from average CPU and memory; check peaks and p95/p99 behavior.

#### Optional Anki

Q: What memory must fit besides Java heap?
A: Metaspace, stacks, direct buffers, code cache, native memory and overhead.

</details>

<a id="k8s-res-004"></a>

<details>
<summary><strong>K8S-RES-004. How do JVM heap settings relate to container memory limits?</strong></summary>

#### Short answer

The heap must be smaller than the container memory limit because the JVM and process use non-heap and native memory too.

#### Interview answer

In modern Java versions, the JVM is container-aware and can size heap based on cgroup limits when configured with percentage-based options. Still, the container limit covers total process memory, not only heap. The JVM needs memory for metaspace, thread stacks, direct buffers, JIT code cache, GC structures and native libraries.

#### Deep dive

You can use explicit `-Xmx` or percentage options such as `MaxRAMPercentage`, but the correct value depends on workload, thread count and off-heap usage.

#### Production angle

Memory sizing should be validated with metrics, Native Memory Tracking when needed, heap dumps and container memory telemetry.

#### Traps / caveats

- A safe-looking heap can still OOM the container because of off-heap growth.
- Too small a heap can increase GC pressure and latency.

#### Optional Anki

Q: Does container memory limit equal Java heap?
A: No, it covers total process memory.

</details>

<a id="k8s-res-005"></a>

<details>
<summary><strong>K8S-RES-005. Why can a Java container be OOMKilled even when `-Xmx` looks safe?</strong></summary>

#### Short answer

Because the container limit includes all process memory, not just heap, and the kernel can kill the process when total usage is too high.

#### Interview answer

Non-heap memory can grow through thread stacks, metaspace, direct buffers, memory-mapped files, native libraries, TLS buffers, compression, monitoring agents or large temporary files in memory-backed volumes. If total memory crosses the cgroup limit, Kubernetes may report `OOMKilled`.

#### Deep dive

The JVM may not throw `OutOfMemoryError` if the kernel kills the process externally. Container metrics and node events are often more informative than Java logs.

#### Production angle

Investigate heap usage, native memory, thread count, direct buffer usage, off-heap caches and recent traffic or deployment changes.

#### Traps / caveats

- Heap dump on Java OOME may not exist for cgroup OOM kill.
- Memory-backed `emptyDir` can count against memory usage.

#### Optional Anki

Q: Why can `OOMKilled` happen without Java `OutOfMemoryError`?
A: The kernel killed the process for exceeding container memory, outside normal JVM exception handling.

</details>

<a id="k8s-res-006"></a>

<details>
<summary><strong>K8S-RES-006. How does the JVM detect container CPU and memory limits?</strong></summary>

#### Short answer

Modern JVMs read cgroup information to detect container CPU and memory constraints.

#### Interview answer

Recent Java versions are container-aware by default. They use cgroup data to influence available processors and memory-based ergonomics such as default heap sizing. This is why Java version and cgroup support matter when running in Kubernetes.

#### Deep dive

Detection is not the same as perfect tuning. CPU quotas can affect `availableProcessors`, ForkJoinPool size, GC threads and application thread choices. Memory ergonomics still need validation for the workload.

#### Production angle

Check JVM flags, Java version and actual runtime values when debugging unexpected heap size, GC threads or parallelism in containers.

#### Traps / caveats

- Old JVM versions may not respect container limits correctly.
- Explicit `-Xmx` or CPU options can override ergonomics.

#### Optional Anki

Q: What OS mechanism tells the JVM about container limits?
A: cgroups.

</details>

<a id="k8s-res-007"></a>

<details>
<summary><strong>K8S-RES-007. How do thread pools and JDBC connection pools interact with Pod CPU, memory and scaling?</strong></summary>

#### Short answer

Every replica adds threads and connections, so pool sizes must be coordinated with per-Pod resources and shared downstream capacity.

#### Interview answer

A Java service with 50 database connections and 20 replicas can open up to 1000 database connections. Large thread pools also consume stack memory and can create context switching. Pool sizing should reflect CPU, latency targets, downstream limits and total replica count.

#### Deep dive

Scaling Pods increases concurrency against downstream systems unless the application or infrastructure applies limits. Backpressure and bounded pools are important.

#### Production angle

Many Kubernetes incidents happen when HPA scales an application and overloads the database, Redis, Kafka or an HTTP dependency.

#### Traps / caveats

- More replicas do not always mean more throughput if the bottleneck is downstream.
- Unlimited executor queues can hide overload until latency and memory explode.

#### Optional Anki

Q: Why can Pod scaling overload a database?
A: Each Pod may add its own connection pool and concurrency.

</details>

<a id="k8s-res-008"></a>

<details>
<summary><strong>K8S-RES-008. What is HorizontalPodAutoscaler, and what metrics can it use?</strong></summary>

#### Short answer

HPA automatically changes replica count based on metrics such as CPU, memory or custom application metrics.

#### Interview answer

HorizontalPodAutoscaler watches metrics and adjusts replicas for scalable workloads like Deployments or StatefulSets. The common basic metric is CPU utilization relative to requests, but HPA can also use memory, custom metrics or external metrics depending on cluster setup.

#### Deep dive

Autoscaling works best when the metric correlates with capacity need and the application can scale horizontally. It also needs realistic requests because CPU utilization is computed against CPU requests.

#### Production angle

For Java services, useful custom metrics may include request rate, queue depth, Kafka lag, pool saturation or latency indicators.

#### Traps / caveats

- If CPU requests are wrong, CPU-based HPA behavior can be misleading.
- HPA cannot fix a non-horizontal bottleneck like a saturated database.

#### Optional Anki

Q: What common HPA metric depends on CPU requests?
A: CPU utilization.

</details>

<a id="k8s-res-009"></a>

<details>
<summary><strong>K8S-RES-009. Why can CPU-based autoscaling be insufficient for Java backend services?</strong></summary>

#### Short answer

CPU may not reflect the real bottleneck, such as database waits, queue lag, connection pool saturation or downstream latency.

#### Interview answer

A Java API can be slow because all request threads are waiting on a database while CPU is low. In that case CPU-based HPA will not scale out, or scaling out may worsen the database bottleneck. The scaling metric should match the saturation signal.

#### Deep dive

For asynchronous workers, Kafka lag or queue depth may be better than CPU. For HTTP APIs, request concurrency, pool wait time or latency can be more meaningful, but they must be used carefully to avoid unstable scaling.

#### Production angle

Autoscaling should be tested under realistic bottlenecks and include cooldowns, max replicas and downstream protection.

#### Traps / caveats

- Scaling on latency alone can amplify overload if the dependency is already saturated.
- Custom metrics with high cardinality or poor freshness can make scaling unstable.

#### Optional Anki

Q: Why can low CPU still mean a service is overloaded?
A: It may be waiting on pools, locks or downstream dependencies.

</details>

<a id="k8s-res-010"></a>

<details>
<summary><strong>K8S-RES-010. What can go wrong if HPA scales a service with a fixed database connection pool size?</strong></summary>

#### Short answer

Total database connections and query load can multiply until the database or pool limits fail.

#### Interview answer

If each Pod has a pool of 30 connections and HPA scales from 4 to 40 Pods, the service can attempt 1200 connections. The database may reject connections, slow down, increase lock contention or degrade other services.

#### Deep dive

Pool size should be considered as a cluster-wide budget, not just a per-Pod default. Sometimes the right fix is smaller per-Pod pools, better query performance, backpressure or database scaling.

#### Production angle

A mature scaling design protects downstream systems with limits, circuit breakers, bulkheads and alerting on pool wait time.

#### Traps / caveats

- Default HikariCP settings may be wrong for high replica counts.
- More connections can reduce throughput if the database is already saturated.

#### Optional Anki

Q: What formula matters for DB connection risk?
A: replicas multiplied by max pool size.

</details>

<a id="k8s-res-011"></a>

<details>
<summary><strong>K8S-RES-011. What are Kubernetes QoS classes, and how do they affect eviction?</strong></summary>

#### Short answer

QoS classes classify Pods by resource requests and limits; they influence which Pods are evicted first under node pressure.

#### Interview answer

Guaranteed Pods have equal CPU and memory requests and limits for all containers. BestEffort Pods have no requests or limits. Burstable is in between. Under resource pressure, Kubernetes uses QoS and actual usage to help decide eviction order.

#### Deep dive

QoS is not a performance guarantee by itself. It is part of node pressure behavior and resource management.

#### Production angle

Critical Java services should not accidentally run as BestEffort. Requests and limits should be explicit and reviewed.

#### Traps / caveats

- Guaranteed QoS may increase reservation cost if limits equal high requests.
- QoS does not protect an app from its own memory limit.

#### Optional Anki

Q: Which QoS class has no requests or limits?
A: BestEffort.

</details>

<a id="k8s-res-012"></a>

<details>
<summary><strong>K8S-RES-012. How do PodDisruptionBudgets, affinity and anti-affinity improve availability?</strong></summary>

#### Short answer

PDBs limit voluntary disruptions, while affinity and anti-affinity influence where replicas are scheduled.

#### Interview answer

A PodDisruptionBudget can require a minimum number of available replicas during voluntary operations such as node drain. Anti-affinity or topology spread constraints can prevent all replicas from landing on one node or zone. Affinity can place Pods near required resources.

#### Deep dive

These tools help preserve capacity during maintenance and failures, but they can also make scheduling harder if constraints are too strict.

#### Production angle

For a Java API with multiple replicas, use spread rules and PDBs so one node drain or zone issue does not remove the whole service.

#### Traps / caveats

- PDBs do not protect against all involuntary failures, such as node crashes.
- Strict anti-affinity can leave Pods Pending in small clusters.

#### Optional Anki

Q: What does a PDB protect against?
A: Too many voluntary disruptions at once.

</details>
