# Kubernetes fundamentals, Pods and workloads

---

<a id="k8s-work-001"></a>

<details>
<summary><strong>K8S-WORK-001. What is Kubernetes, and what does desired state mean?</strong></summary>

#### Short answer

Kubernetes is a container orchestration platform that continuously tries to make the actual cluster state match the desired state declared in resource manifests.

#### Interview answer

Instead of manually starting containers on machines, you declare resources such as Deployments, Services and ConfigMaps. Kubernetes controllers observe the cluster and reconcile differences: if a Pod dies, a controller can create another one; if a Deployment version changes, it rolls out new Pods.

#### Deep dive

Desired state is stored as Kubernetes API objects. Controllers are the automation that watches those objects and performs actions to move actual state closer to the declared spec.

#### Production angle

This model supports repeatable deployments, self-healing, scaling and rollback, but only if manifests describe the service correctly.

#### Traps / caveats

- Kubernetes reconciles infrastructure state, not business correctness.
- A bad desired state can be applied very reliably and break production.

#### Optional Anki

Q: What does Kubernetes reconciliation do?
A: It moves actual cluster state toward declared desired state.

</details>

<details>
<summary><strong>K8S-WORK-002. What is the difference between the Kubernetes control plane and worker nodes?</strong></summary>

#### Short answer

The control plane manages cluster state and decisions; worker nodes run application Pods.

#### Interview answer

The control plane includes components such as the API server, scheduler, controllers and etcd. Worker nodes run kubelet, a container runtime and networking components so Pods can be started and monitored.

#### Deep dive

The API server is the entry point for Kubernetes operations. The scheduler chooses nodes for unscheduled Pods. Controllers reconcile resources. etcd stores cluster state.

#### Production angle

Backend engineers usually do not administer control planes daily, but knowing the split helps during incidents: a scheduling issue is different from a container crash, and an API outage is different from an app outage.

#### Traps / caveats

- If the control plane is unhealthy, existing Pods may still run, but management actions can fail.
- A worker node problem usually affects only workloads placed on that node.

#### Optional Anki

Q: What stores Kubernetes cluster state?
A: etcd.

</details>

<a id="k8s-work-003"></a>

<details>
<summary><strong>K8S-WORK-003. What are `apiVersion`, `kind`, `metadata`, `spec` and `status` in a manifest?</strong></summary>

#### Short answer

They are the main parts of a Kubernetes object: API group/version, object type, identity, desired configuration and observed state.

#### Interview answer

`apiVersion` tells Kubernetes which API version to use. `kind` says what resource type it is, such as Deployment or Service. `metadata` contains name, namespace, labels and annotations. `spec` is what you want. `status` is what Kubernetes observes and updates.

#### Deep dive

Users normally write `spec`; controllers update `status`. This split is central to declarative APIs.

#### Production angle

Reading `spec` and `status` side by side helps debug rollouts: the manifest may request three replicas, while status shows only one ready.

#### Traps / caveats

- Do not hand-edit `status`; it is controller-owned.
- API versions can change, so manifests need maintenance during cluster upgrades.

#### Optional Anki

Q: What is the difference between `spec` and `status`?
A: `spec` is desired state; `status` is observed state.

</details>

<details>
<summary><strong>K8S-WORK-004. What is a namespace in Kubernetes, and what does it not isolate?</strong></summary>

#### Short answer

A namespace groups namespaced resources and access policies, but it is not a hard security or network boundary by itself.

#### Interview answer

Namespaces help organize resources by team, environment or application area. They also scope names, RBAC, quotas and some policies. However, Pods in different namespaces can often talk to each other unless NetworkPolicy or platform rules restrict them.

#### Deep dive

Namespaces are useful for multi-team clusters, but they do not automatically isolate node resources, secrets access across RBAC mistakes, or network traffic.

#### Production angle

Use namespaces with RBAC, quotas, NetworkPolicy and admission policies to create meaningful boundaries.

#### Traps / caveats

- Do not assume `dev` and `prod` namespaces are enough isolation for real production separation.
- Cluster-scoped resources are not contained by a namespace.

#### Optional Anki

Q: Do namespaces block network traffic by default?
A: No, not without NetworkPolicy or platform-specific controls.

</details>

<details>
<summary><strong>K8S-WORK-005. What is a Pod, and why is it the smallest deployable unit?</strong></summary>

#### Short answer

A Pod is one or more containers that share network and storage context; Kubernetes schedules and manages Pods, not individual containers.

#### Interview answer

For a typical Spring Boot service, one Pod contains one application container. The Pod gets an IP, labels, volumes and lifecycle. If the Pod is replaced, the new Pod usually gets a different identity and IP.

#### Deep dive

Containers in the same Pod share `localhost` networking and can share volumes. They should be tightly coupled parts of one runtime unit, not unrelated services.

#### Production angle

Pods are ephemeral, so stable access should go through Services and durable state should live outside the Pod.

#### Traps / caveats

- Do not put independent microservices in one Pod just to simplify deployment.
- Do not rely on Pod IPs as stable service addresses.

#### Optional Anki

Q: What is the smallest deployable unit in Kubernetes?
A: A Pod.

</details>

<a id="k8s-work-006"></a>

<details>
<summary><strong>K8S-WORK-006. When would you run multiple containers in one Pod?</strong></summary>

#### Short answer

When containers are tightly coupled and must share lifecycle, network or volumes, such as a sidecar helper.

#### Interview answer

Common examples are sidecars for logging agents, service mesh proxies, local adapters or file synchronization helpers. The containers should support one application instance together and scale as a unit.

#### Deep dive

Because Pod containers share `localhost`, a sidecar can expose a local proxy or helper endpoint to the main Java process. Shared volumes can also support coordination.

#### Production angle

Sidecars add resource usage and failure modes. They should be included in CPU and memory sizing, health checks and rollout planning.

#### Traps / caveats

- Do not use one Pod as a replacement for proper service boundaries.
- A broken sidecar can make the whole Pod unhealthy.

#### Optional Anki

Q: When is a sidecar appropriate?
A: When a helper must share lifecycle and local context with the main container.

</details>

<a id="k8s-work-007"></a>

<details>
<summary><strong>K8S-WORK-007. What are labels, selectors and annotations used for?</strong></summary>

#### Short answer

Labels identify and group resources for selection; annotations attach non-identifying metadata.

#### Interview answer

Labels are key-value pairs used by Services, Deployments, NetworkPolicies, monitoring tools and queries. Selectors match labels. Annotations store extra metadata such as build info, checksums or tool configuration that should not be used for core selection.

#### Deep dive

Stable labels are critical. If a Deployment selector or Service selector does not match the intended Pods, traffic or rollout behavior breaks.

#### Production angle

Good label conventions support dashboards, ownership, cost allocation, incident filtering and deployment automation.

#### Traps / caveats

- Do not put high-cardinality or sensitive data in labels.
- Do not change immutable Deployment selectors casually.

#### Optional Anki

Q: Labels vs annotations?
A: Labels are for selection/grouping; annotations are metadata.

</details>

<a id="k8s-work-008"></a>

<details>
<summary><strong>K8S-WORK-008. What is the relationship between a Deployment, ReplicaSet and Pods?</strong></summary>

#### Short answer

A Deployment manages ReplicaSets, and ReplicaSets keep the desired number of matching Pods running.

#### Interview answer

You usually create a Deployment for stateless services. It creates and updates ReplicaSets. Each ReplicaSet owns Pods for a specific template version. During a rollout, the Deployment scales the new ReplicaSet up and the old one down.

#### Deep dive

This layering supports rollout history and rollback. A ReplicaSet is lower-level; most teams should not create it directly for application services.

#### Production angle

When a rollout is stuck, inspect the Deployment status, ReplicaSets and Pods to understand which generation is failing.

#### Traps / caveats

- Deleting Pods manually is not a deployment strategy; the ReplicaSet will recreate them.
- Changing labels incorrectly can orphan or misroute Pods.

#### Optional Anki

Q: What manages ReplicaSets during application releases?
A: A Deployment.

</details>

<a id="k8s-work-009"></a>

<details>
<summary><strong>K8S-WORK-009. How do rolling updates work, and what are `maxSurge` and `maxUnavailable`?</strong></summary>

#### Short answer

A rolling update gradually replaces old Pods with new Pods; `maxSurge` allows extra Pods and `maxUnavailable` limits unavailable Pods during the rollout.

#### Interview answer

During a Deployment rollout, Kubernetes creates Pods from the new template and removes old Pods while respecting readiness and rollout strategy. `maxSurge` controls how many replicas above desired count can exist temporarily. `maxUnavailable` controls how many desired replicas may be unavailable.

#### Deep dive

Readiness probes are central: a new Pod should not count as available until it can serve traffic safely.

#### Production angle

For zero or near-zero downtime, set sensible readiness probes, enough replicas, compatible application versions and rollout limits that preserve capacity.

#### Traps / caveats

- Rolling updates do not solve incompatible database schema changes by themselves.
- Too low `maxSurge` or too strict readiness can make rollouts slow or stuck.

#### Optional Anki

Q: What does `maxUnavailable` limit?
A: How many desired replicas may be unavailable during rollout.

</details>

<details>
<summary><strong>K8S-WORK-010. When would you use a Kubernetes Job or CronJob?</strong></summary>

#### Short answer

Use a Job for finite work that should complete, and a CronJob for recurring scheduled Jobs.

#### Interview answer

Jobs fit tasks like database migrations, one-time backfills, report generation or batch processing. CronJobs fit scheduled cleanup or periodic synchronization. They differ from Deployments because success is completion, not continuous serving.

#### Deep dive

Important settings include restart policy, backoff limit, concurrency policy, deadlines and cleanup history. For database or message-processing work, idempotency matters.

#### Production angle

A failed migration Job or duplicated CronJob execution can corrupt data if the task is not designed to resume or retry safely.

#### Traps / caveats

- CronJob schedules are not a substitute for idempotent job logic.
- Do not run long-lived HTTP services as Jobs.

#### Optional Anki

Q: Job vs Deployment?
A: A Job runs finite work to completion; a Deployment keeps services running.

</details>

<a id="k8s-work-011"></a>

<details>
<summary><strong>K8S-WORK-011. When should you use a StatefulSet instead of a Deployment?</strong></summary>

#### Short answer

Use StatefulSet when each replica needs stable identity, ordered lifecycle or stable per-replica storage.

#### Interview answer

Deployments are usually best for stateless services. StatefulSets are for workloads where `app-0`, `app-1` style identity, stable network names and persistent volume claims matter. Examples include some databases, queues or clustered systems.

#### Deep dive

StatefulSet does not magically make state safe. You still need backup, restore, replication, upgrade and failure handling.

#### Production angle

For Java backend teams, the common senior answer is to prefer managed databases unless there is a strong reason and operational capability to run stateful systems in Kubernetes.

#### Traps / caveats

- Do not use StatefulSet just because the app writes temporary files.
- Stable Pod identity is not the same as data durability.

#### Optional Anki

Q: Main StatefulSet feature?
A: Stable identity and stable per-replica storage.

</details>

<details>
<summary><strong>K8S-WORK-012. What are Operators and CRDs at a high level?</strong></summary>

#### Short answer

A CRD adds a custom Kubernetes resource type; an Operator is a controller that automates lifecycle logic for such resources.

#### Interview answer

Kubernetes lets teams extend the API. A Custom Resource Definition might define a `PostgresCluster` resource. An Operator watches that resource and creates or updates lower-level resources to run backups, failover, upgrades or scaling.

#### Deep dive

Operators encode operational knowledge, often for stateful or complex platforms. They can reduce manual work but also add another controller and failure mode.

#### Production angle

Use Operators when the lifecycle is complex enough to justify automation and the team trusts the Operator's behavior, upgrade path and observability.

#### Traps / caveats

- A CRD is just an API extension; useful behavior requires a controller.
- Installing many Operators can increase cluster complexity and blast radius.

#### Optional Anki

Q: What does an Operator do?
A: It reconciles custom resources by automating domain-specific operational tasks.

</details>
