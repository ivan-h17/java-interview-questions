# Dockerfile builds and container runtime configuration

---

<a id="dk-df-001"></a>

<details>
<summary><strong>DK-DF-001. What should a production Dockerfile for a Spring Boot service include?</strong></summary>

#### Short answer

It should use a maintained Java runtime, copy the application artifact, run as non-root, expose a clear startup command, and avoid secrets or unnecessary tools.

#### Interview answer

A production Dockerfile should separate build and runtime concerns, usually with a multi-stage build or a prebuilt jar copied into a runtime image. It should choose a supported Java base image, set a working directory, copy only required files, run as a non-root user, use exec-form `ENTRYPOINT`, and rely on runtime configuration for environment-specific values.

#### Deep dive

For Spring Boot, layered jars or Jib can improve layer reuse by separating dependencies, Spring Boot loader code and application classes. The Dockerfile should also support predictable JVM options through environment variables or platform configuration.

#### Production angle

The Dockerfile becomes part of the release artifact and supply chain, so it affects vulnerability response, rollout speed, resource behavior and incident debugging.

#### Traps / caveats

- Do not install build tools in the final runtime image unless required.
- Do not bake credentials, profiles or production URLs into the image.

#### Optional Anki

Q: What should a Spring Boot production image avoid?
A: Secrets, unnecessary build tools, mutable state and environment-specific config.

</details>

<details>
<summary><strong>DK-DF-002. What is the difference between `RUN`, `CMD` and `ENTRYPOINT`?</strong></summary>

#### Short answer

`RUN` executes while building the image; `CMD` and `ENTRYPOINT` define what runs when a container starts.

#### Interview answer

`RUN` creates image layers, for example installing packages or preparing files. `ENTRYPOINT` is the main executable for the container. `CMD` provides default arguments or a default command that can be overridden more easily at runtime.

#### Deep dive

For an application container, `ENTRYPOINT ["java", "..."]` often expresses the main process. `CMD` can hold default arguments, but teams vary in style.

#### Production angle

Clear startup configuration helps Kubernetes send signals correctly, collect logs and restart the process consistently.

#### Traps / caveats

- `RUN` does not execute when the container starts.
- Shell-form commands can change signal handling and argument parsing.

#### Optional Anki

Q: When does `RUN` execute?
A: During image build, not container startup.

</details>

<details>
<summary><strong>DK-DF-003. Why is exec form usually preferred over shell form for Java containers?</strong></summary>

#### Short answer

Exec form runs the Java process directly, which improves signal handling and avoids shell parsing surprises.

#### Interview answer

With exec form, for example `ENTRYPOINT ["java", "-jar", "app.jar"]`, the JVM is the main process and receives signals such as `SIGTERM` directly. With shell form, a shell process may become PID 1 and fail to forward signals correctly.

#### Deep dive

PID 1 has special behavior on Linux. If the container entrypoint does not handle signals and child reaping properly, graceful shutdown can fail or zombies can accumulate.

#### Production angle

Kubernetes terminates Pods by sending `SIGTERM` and waiting for the grace period. If the JVM does not receive it, in-flight requests and cleanup may be cut off by `SIGKILL`.

#### Traps / caveats

- Shell form can be useful when shell expansion is intentionally needed, but application containers rarely need it.
- If using a wrapper script, make sure it uses `exec` to replace itself with the Java process.

#### Optional Anki

Q: Why prefer exec-form `ENTRYPOINT`?
A: The app process receives signals directly and avoids shell parsing issues.

</details>

<details>
<summary><strong>DK-DF-004. What is the difference between `COPY` and `ADD`?</strong></summary>

#### Short answer

`COPY` copies local files into the image; `ADD` can also fetch URLs and automatically extract local tar archives.

#### Interview answer

For most application Dockerfiles, `COPY` is preferred because it is explicit and predictable. `ADD` has extra behavior that can surprise reviewers, especially automatic archive extraction or remote URL handling.

#### Deep dive

The Docker build context still controls what local files are available. `.dockerignore` should exclude files that should not be sent to the daemon or included in layers.

#### Production angle

Predictable file copying reduces accidental inclusion of secrets, build cache churn and unexpected image contents.

#### Traps / caveats

- Do not use `ADD` for remote downloads when a controlled package manager or checksum verification is more appropriate.
- Do not copy the entire repository when only the jar and config defaults are needed.

#### Optional Anki

Q: Which instruction is usually preferred for simple file copying?
A: `COPY`.

</details>

<details>
<summary><strong>DK-DF-005. Why are multi-stage builds useful for Java applications?</strong></summary>

#### Short answer

They let you build with a full toolchain and ship only the minimal runtime artifacts.

#### Interview answer

A builder stage can use Maven or Gradle and a full JDK. The final stage can contain only the runtime JDK or JRE, the application jar and required files. This reduces image size, attack surface and accidental leakage of build caches.

#### Deep dive

Multi-stage builds also make it easier to separate dependency download layers from application source layers. In some teams, CI builds the jar first and the Dockerfile only packages it; both approaches can work.

#### Production angle

Smaller runtime images usually pull faster, scan cleaner and contain fewer tools attackers can use after compromise.

#### Traps / caveats

- Do not copy the whole build workspace from the builder stage into the final stage.
- Make sure the runtime Java version is compatible with the compiled bytecode.

#### Optional Anki

Q: Main benefit of multi-stage builds?
A: Build with full tools, ship a smaller runtime image.

</details>

<a id="dk-df-006"></a>

<details>
<summary><strong>DK-DF-006. What is `.dockerignore`, and why is it important?</strong></summary>

#### Short answer

`.dockerignore` excludes files from the build context so they are not sent to the builder or copied accidentally.

#### Interview answer

It works like a filter for the Docker build context. It should usually exclude `.git`, IDE files, local build outputs, logs, secrets, temporary files and anything not needed to build the image.

#### Deep dive

Even if the Dockerfile does not copy a file explicitly, sending a huge or sensitive build context is still wasteful and risky. It can slow builds and make accidental `COPY . .` much more dangerous.

#### Production angle

A good `.dockerignore` improves CI performance and reduces the chance of leaking credentials or local-only files into images.

#### Traps / caveats

- `.dockerignore` is not a substitute for secret scanning.
- Be careful not to exclude files required by the build, such as Maven wrapper files.

#### Optional Anki

Q: What does `.dockerignore` protect?
A: Build context size and accidental inclusion of unwanted files.

</details>

<details>
<summary><strong>DK-DF-007. How can Dockerfile instruction order affect build cache efficiency?</strong></summary>

#### Short answer

Instructions that change often should appear later, so stable dependency and setup layers stay cacheable.

#### Interview answer

Docker reuses cached layers only while the current instruction and previous layers are unchanged. If you copy all source code before resolving dependencies, every small code change may invalidate dependency downloads. Copying build descriptors first can keep expensive dependency layers stable.

#### Deep dive

For Java, a common pattern is to copy `pom.xml` or Gradle files, download dependencies, then copy source and build. Layered jars and Jib apply the same idea at application-layer level.

#### Production angle

Good instruction order speeds CI, reduces registry pushes and makes emergency rebuilds faster.

#### Traps / caveats

- Cache use must not hide dependency updates; lock or refresh dependencies intentionally.
- Over-optimizing Dockerfile order can make simple builds harder to read.

#### Optional Anki

Q: Where should frequently changing source usually appear?
A: Later in the Dockerfile, after stable dependency layers.

</details>

<a id="dk-df-008"></a>

<details>
<summary><strong>DK-DF-008. How can you reduce the size and attack surface of a Java container image?</strong></summary>

#### Short answer

Use a minimal maintained runtime image, multi-stage builds, `.dockerignore`, fewer packages, non-root execution and regular base image updates.

#### Interview answer

The final image should contain only what is needed to run the service. Remove build tools, package manager caches and unused files. Prefer a small supported base image, scan dependencies, and run with least privilege.

#### Deep dive

Image size and attack surface are related but not identical. A small image with old vulnerable libraries is still risky, while a slightly larger maintained image can be safer.

#### Production angle

Lean images improve pull time and reduce CVE volume, but production operability still needs logs, metrics and a debugging strategy.

#### Traps / caveats

- Do not remove CA certificates, timezone data or native libraries the app actually needs.
- Do not choose distroless without planning how to debug failures.

#### Optional Anki

Q: Does smallest image always mean safest image?
A: No. Maintenance, patching and compatibility matter too.

</details>

<details>
<summary><strong>DK-DF-009. What is the difference between build-time `ARG` and runtime `ENV`?</strong></summary>

#### Short answer

`ARG` is available during image build; `ENV` becomes part of the image runtime environment unless overridden.

#### Interview answer

`ARG` is useful for build parameters such as version numbers or optional build flags. `ENV` sets environment variables visible to processes running in the container. Runtime platform configuration can override environment variables when the container starts.

#### Deep dive

Both can leak information if used carelessly. `ARG` values can appear in build metadata or history depending on usage, and `ENV` values are visible to the runtime environment and diagnostic output.

#### Production angle

Use build arguments for non-sensitive build metadata and runtime configuration mechanisms for environment-specific settings.

#### Traps / caveats

- Do not pass secrets through `ARG`.
- Do not use `ENV` to bake production-only behavior into a supposedly reusable image.

#### Optional Anki

Q: `ARG` vs `ENV`?
A: `ARG` is build-time; `ENV` is runtime environment.

</details>

<details>
<summary><strong>DK-DF-010. Why should secrets not be passed as Docker build arguments or baked into images?</strong></summary>

#### Short answer

Because build inputs and image layers can be persisted, cached, inspected and pushed to registries.

#### Interview answer

If a secret is used in a Dockerfile through `ARG`, `ENV` or copied files, it may end up in image history, build cache, logs or a layer. Even deleting it in a later step may not remove it from previous layers.

#### Deep dive

Build-time secrets should be provided through mechanisms designed not to persist them, such as BuildKit secret mounts, and runtime secrets should come from the deployment platform.

#### Production angle

Leaked build secrets can compromise package repositories, source systems, deployment credentials or production data.

#### Traps / caveats

- A private registry does not make secret-bearing images acceptable.
- Secret rotation is still required after a leak, even if the image is deleted.

#### Optional Anki

Q: Why is deleting a secret later in a Dockerfile not enough?
A: It may remain in an earlier image layer.

</details>

<a id="dk-df-011"></a>

<details>
<summary><strong>DK-DF-011. How can BuildKit help with cache mounts and secret mounts?</strong></summary>

#### Short answer

BuildKit can mount caches and secrets during specific build steps without baking them into final image layers.

#### Interview answer

Cache mounts can speed dependency downloads, for example Maven or Gradle caches, without copying the cache into the image. Secret mounts can provide credentials to one build step, such as accessing a private repository, without storing the secret in the resulting layer.

#### Deep dive

This is useful for Java builds because dependency resolution is expensive and private repositories are common. The Dockerfile still needs to be written carefully so secret content is not echoed or copied.

#### Production angle

BuildKit helps make builds faster and safer, especially in CI, but it does not replace secret scanning or least-privilege repository credentials.

#### Traps / caveats

- Secret mounts reduce persistence risk but do not protect against commands that print the secret.
- Cache mounts can hide stale or corrupted dependency cache issues if not managed.

#### Optional Anki

Q: BuildKit secret mount benefit?
A: Use a secret during a build step without storing it in the image layer.

</details>

<a id="dk-df-012"></a>

<details>
<summary><strong>DK-DF-012. What are Jib and Spring Boot layered jars, and how can they help Java image builds?</strong></summary>

#### Short answer

They are Java-focused ways to structure container image layers so dependencies and application code can be cached separately.

#### Interview answer

Jib builds container images directly from Maven or Gradle without requiring a handwritten Dockerfile for common Java cases. Spring Boot layered jars split the executable jar into logical layers, such as dependencies and application classes, which helps Docker cache stable parts.

#### Deep dive

These tools reduce boilerplate and often produce better layer reuse than a naive Dockerfile. A custom Dockerfile may still be needed for OS packages, native tools or unusual runtime setup.

#### Production angle

Better layering speeds CI and deployments because dependency layers change less often than application code.

#### Traps / caveats

- Tool-generated images still need base image, JVM option and security review.
- Do not assume Jib or layered jars remove the need for runtime configuration discipline.

#### Optional Anki

Q: Why do layered jars help Docker builds?
A: They separate stable dependencies from frequently changing application code.

</details>
