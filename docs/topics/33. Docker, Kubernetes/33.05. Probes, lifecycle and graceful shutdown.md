# Probes, lifecycle and graceful shutdown

---

<a id="k8s-health-001"></a>

<details>
<summary><strong>K8S-HEALTH-001. What is the difference between liveness, readiness and startup probes?</strong></summary>

#### Short answer

Liveness decides whether to restart a container, readiness decides whether it receives traffic, and startup protects slow-starting containers before liveness takes over.

#### Interview answer

A liveness probe answers "is this process stuck beyond recovery?" A readiness probe answers "can this instance safely serve traffic now?" A startup probe gives an application extra time to initialize without being killed by liveness checks.

#### Deep dive

Readiness can change during normal operation, for example during dependency loss or graceful shutdown. Liveness should be much more conservative because failure causes restarts.

#### Production angle

Correct probes are central to zero-downtime rollout and incident recovery. Bad probes can remove all capacity or restart healthy-but-slow Pods.

#### Traps / caveats

- Do not make liveness depend on every downstream service.
- Do not use startup delay as a substitute for a startup probe when startup time varies.

#### Optional Anki

Q: Which probe removes a Pod from Service endpoints?
A: Readiness.

</details>

<a id="k8s-health-002"></a>

<details>
<summary><strong>K8S-HEALTH-002. Why can a bad liveness probe cause a production outage?</strong></summary>

#### Short answer

Because liveness failure restarts containers, so a fragile check can turn temporary slowness into restart loops.

#### Interview answer

If liveness checks a slow dependency, performs heavy work, has a tiny timeout or shares an overloaded thread pool, it can fail under load even though the service would recover. Kubernetes then restarts Pods, reducing capacity and causing more load on remaining Pods.

#### Deep dive

This creates a feedback loop: load causes probe failure, failure causes restarts, restarts reduce capacity, and reduced capacity increases load.

#### Production angle

Liveness should usually check process-level health and deadlock-style failure, not full dependency readiness.

#### Traps / caveats

- A health endpoint can fail because the health check implementation is overloaded, not because the service is dead.
- Aggressive liveness settings can hide the root cause by constantly restarting the process.

#### Optional Anki

Q: What happens when liveness fails repeatedly?
A: Kubernetes restarts the container.

</details>

<a id="k8s-health-003"></a>

<details>
<summary><strong>K8S-HEALTH-003. What should a liveness endpoint check in a Spring Boot service?</strong></summary>

#### Short answer

It should check that the application process is alive and not irrecoverably broken, while avoiding fragile downstream dependency checks.

#### Interview answer

For Spring Boot, liveness often maps to the application availability state exposed by Actuator. It should be cheap, fast and local. It should not fail just because PostgreSQL, Redis or another service has a temporary issue.

#### Deep dive

If the JVM is deadlocked or the embedded server cannot respond at all, liveness can fail. If the database is down, readiness may fail while liveness stays up so the process can recover without restart.

#### Production angle

Conservative liveness prevents restart storms and lets the service recover from transient dependency failures.

#### Traps / caveats

- Do not run expensive SQL queries in liveness.
- Do not expose health endpoints publicly without security review.

#### Optional Anki

Q: Should liveness usually check the database?
A: No, dependency checks usually belong in readiness.

</details>

<a id="k8s-health-004"></a>

<details>
<summary><strong>K8S-HEALTH-004. What should a readiness endpoint check, and when should dependencies be included?</strong></summary>

#### Short answer

Readiness should report whether this instance can safely handle traffic right now, including critical dependencies when failure means requests cannot succeed.

#### Interview answer

Readiness can include checks for startup completion, required configuration, database connectivity, migration state, cache warm-up or message consumer readiness. But it should be designed carefully: if every Pod marks unready because a shared dependency is down, the system may produce no endpoints.

#### Deep dive

For dependencies, the question is whether routing traffic to the instance is useful. If the service can degrade gracefully, readiness may stay true while specific operations fail or degrade.

#### Production angle

Readiness controls load balancer routing, so it protects users during startup, shutdown, rollouts and partial failures.

#### Traps / caveats

- Over-strict readiness can remove all replicas during a downstream outage.
- Under-strict readiness can send traffic to instances that are not initialized.

#### Optional Anki

Q: What question does readiness answer?
A: Can this instance safely receive traffic now?

</details>

<a id="k8s-health-005"></a>

<details>
<summary><strong>K8S-HEALTH-005. How do Kubernetes probes relate to Spring Boot Actuator liveness and readiness health groups?</strong></summary>

#### Short answer

Spring Boot Actuator can expose dedicated liveness and readiness health information that Kubernetes probes can call.

#### Interview answer

Spring Boot manages application availability states and exposes liveness/readiness indicators when probe support is enabled or when running in Kubernetes. Kubernetes can configure HTTP probes against those Actuator endpoints instead of using one generic health check for everything.

#### Deep dive

The value is separation. Liveness should indicate whether the app should be restarted; readiness should indicate whether it should receive traffic. Spring health groups let you include different checks in each.

#### Production angle

Actuator health endpoints should be exposed only as needed and secured appropriately. Internal probe paths should not leak sensitive details.

#### Traps / caveats

- Do not point both liveness and readiness at the same broad dependency-heavy endpoint.
- Actuator configuration differs by Spring Boot version, so verify the exact endpoint paths in the project.

#### Optional Anki

Q: Why use separate Actuator health groups?
A: Liveness and readiness answer different operational questions.

</details>

<a id="k8s-health-006"></a>

<details>
<summary><strong>K8S-HEALTH-006. What are `initialDelaySeconds`, `periodSeconds`, `timeoutSeconds` and `failureThreshold`?</strong></summary>

#### Short answer

They tune when probes start, how often they run, how long each check may take and how many failures are tolerated.

#### Interview answer

`initialDelaySeconds` waits before the first probe. `periodSeconds` controls probe frequency. `timeoutSeconds` is the per-probe timeout. `failureThreshold` is how many consecutive failures are needed before Kubernetes acts.

#### Deep dive

Startup probes are usually better than very large liveness initial delays for slow applications, because they separate startup tolerance from normal liveness behavior.

#### Production angle

Probe timing must reflect real startup, warm-up, GC pauses, dependency behavior and load. Too aggressive settings create false failures; too loose settings slow incident detection.

#### Traps / caveats

- Very short timeouts can fail during normal JVM pauses or CPU throttling.
- Long failure thresholds on readiness can delay traffic removal during shutdown.

#### Optional Anki

Q: What does `failureThreshold` control?
A: The number of consecutive probe failures before action is taken.

</details>

<a id="k8s-health-007"></a>

<details>
<summary><strong>K8S-HEALTH-007. How do `SIGTERM` and `terminationGracePeriodSeconds` affect Java application shutdown?</strong></summary>

#### Short answer

Kubernetes sends `SIGTERM` to request shutdown, waits the grace period, then sends `SIGKILL` if the process is still running.

#### Interview answer

The Java process should receive `SIGTERM`, stop accepting new work, finish in-flight requests if possible, close resources and exit before `terminationGracePeriodSeconds` expires. If it does not, Kubernetes forcefully kills it.

#### Deep dive

This depends on correct container entrypoint signal handling. Spring Boot supports graceful shutdown when configured, but thread pools, consumers and custom background tasks also need proper shutdown behavior.

#### Production angle

Graceful shutdown prevents dropped requests, duplicate message processing and corrupted partial work during rollouts and scaling events.

#### Traps / caveats

- Shell-form entrypoints can prevent the JVM from receiving `SIGTERM`.
- The grace period must be long enough for realistic request and cleanup time.

#### Optional Anki

Q: What happens after termination grace expires?
A: Kubernetes sends `SIGKILL`.

</details>

<a id="k8s-health-008"></a>

<details>
<summary><strong>K8S-HEALTH-008. What is a `preStop` hook, and how can a service stop accepting traffic before shutdown?</strong></summary>

#### Short answer

A `preStop` hook runs before container termination and can give the Pod time to become unready or drain traffic.

#### Interview answer

During termination, a service should be removed from endpoints and stop accepting new traffic before the process exits. This can be done with readiness state changes, graceful shutdown settings and sometimes a `preStop` delay or hook that lets endpoint updates propagate.

#### Deep dive

The hook is not a replacement for application-level graceful shutdown. It is one part of a termination sequence that also includes readiness, load balancer behavior and request timeouts.

#### Production angle

For Java APIs behind Ingress or cloud load balancers, drain timing matters because external systems may keep routing briefly after termination starts.

#### Traps / caveats

- A blind sleep in `preStop` can hide timing issues but may slow rollouts.
- `preStop` execution counts within the termination grace period.

#### Optional Anki

Q: What should happen before a Pod exits?
A: It should stop receiving new traffic and drain in-flight work.

</details>

<a id="k8s-health-009"></a>

<details>
<summary><strong>K8S-HEALTH-009. What happens to in-flight requests during Pod termination?</strong></summary>

#### Short answer

They may complete if the application and platform allow graceful draining before the grace period ends.

#### Interview answer

When termination starts, Kubernetes removes the Pod from endpoints and sends `SIGTERM`. Existing connections or requests may still be active. The application should stop accepting new requests, finish current ones within a bounded time and close resources cleanly.

#### Deep dive

Behavior also depends on Ingress, load balancers, HTTP keep-alive, client retries and application server graceful shutdown settings.

#### Production angle

Without proper draining, rolling deployments can create user-visible errors even when readiness probes look correct.

#### Traps / caveats

- Endpoint removal is not instantaneous across every proxy and load balancer.
- Long-running requests need explicit timeout and cancellation design.

#### Optional Anki

Q: Why can requests fail during an otherwise healthy rollout?
A: In-flight work may be cut off if termination and draining are not configured correctly.

</details>

<a id="k8s-health-010"></a>

<details>
<summary><strong>K8S-HEALTH-010. How should slow Java startup, warm-up and JIT behavior be handled during rollouts?</strong></summary>

#### Short answer

Use startup probes, realistic readiness checks, enough rollout capacity and warm-up-aware monitoring.

#### Interview answer

Java services can start slowly because of class loading, dependency initialization, migrations, cache warm-up or JIT compilation. A startup probe prevents liveness from killing the app too early. Readiness should become true only when the service can handle traffic at an acceptable level.

#### Deep dive

Warm-up is not always equal to process start. The first requests may be slower due to JIT, lazy initialization or cold caches. Some teams use controlled warm-up traffic before full exposure.

#### Production angle

Rollouts should preserve capacity while new Pods warm up, otherwise a deployment can cause latency spikes.

#### Traps / caveats

- Do not set liveness delays based only on average startup time.
- Do not mark ready before required caches, migrations or clients are usable.

#### Optional Anki

Q: Which probe protects slow-starting containers?
A: Startup probe.

</details>

<a id="k8s-health-011"></a>

<details>
<summary><strong>K8S-HEALTH-011. How would you debug repeated probe failures?</strong></summary>

#### Short answer

Inspect events, probe configuration, endpoint behavior, app logs, resource throttling and dependency health.

#### Interview answer

I start with `kubectl describe pod` to see probe failure messages and timing. Then I compare the probe path, port and scheme with the application config. I check logs, Actuator health details, CPU throttling, GC pauses, startup duration and dependency failures.

#### Deep dive

Probe failures can be caused by routing to the wrong port, missing management endpoint exposure, TLS mismatch, path errors, overloaded thread pools or slow dependencies.

#### Production angle

During an incident, distinguish "probe detects a real failure" from "probe design is causing the failure."

#### Traps / caveats

- Do not just increase thresholds without understanding the cause.
- The probe may hit a different port or management context than normal traffic.

#### Optional Anki

Q: First command for probe failure context?
A: `kubectl describe pod`.

</details>

<a id="k8s-health-012"></a>

<details>
<summary><strong>K8S-HEALTH-012. What is the difference between application health and process health?</strong></summary>

#### Short answer

Process health means the program is running; application health means it can perform its intended work correctly.

#### Interview answer

A Java process can be alive while the application is unusable because its database pool is exhausted, config is wrong or a required dependency is down. Conversely, a dependency outage may make one feature unhealthy while the process should keep running and recover.

#### Deep dive

This distinction maps to liveness and readiness. Liveness is closer to process survivability; readiness is closer to service capability.

#### Production angle

Good health design avoids both false confidence and destructive restarts. It also communicates degraded mode clearly through metrics and alerts.

#### Traps / caveats

- A green `/health` endpoint can be misleading if it checks only the process.
- A red dependency check should not always trigger process restart.

#### Optional Anki

Q: Which health concept decides traffic routing?
A: Application readiness.

</details>
