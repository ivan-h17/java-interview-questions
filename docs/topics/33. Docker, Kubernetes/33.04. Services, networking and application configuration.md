# Services, networking, storage and application configuration

---

<a id="k8s-net-001"></a>

<details>
<summary><strong>K8S-NET-001. What is a Kubernetes Service, and why do Pods need it?</strong></summary>

#### Short answer

A Service gives stable access to a dynamic set of Pods selected by labels.

#### Interview answer

Pods are ephemeral and their IPs can change when they are recreated. A Service provides a stable virtual address and DNS name, then routes traffic to ready matching Pods through endpoints or EndpointSlices.

#### Deep dive

Services decouple clients from individual Pod IPs. For a Spring Boot app, other services should call the Service DNS name, not a Pod directly.

#### Production angle

When traffic disappears, check the Service selector, matching Pod labels, endpoints and readiness state.

#### Traps / caveats

- A Service with no matching ready endpoints will not magically route traffic.
- Service discovery does not guarantee application compatibility or health.

#### Optional Anki

Q: Why do Pods need Services?
A: Pods are ephemeral; Services provide stable discovery and routing.

</details>

<a id="k8s-net-002"></a>

<details>
<summary><strong>K8S-NET-002. What is the difference between ClusterIP, NodePort and LoadBalancer Services?</strong></summary>

#### Short answer

ClusterIP exposes a Service inside the cluster, NodePort exposes it on node ports, and LoadBalancer asks the platform for an external load balancer.

#### Interview answer

ClusterIP is the default and is used for internal service-to-service traffic. NodePort opens a port on each node and is often a building block rather than a direct production interface. LoadBalancer integrates with cloud or platform infrastructure to expose the service externally.

#### Deep dive

Ingress often sits in front of Services to provide HTTP routing, TLS termination and host/path rules. Not every environment supports `LoadBalancer` automatically.

#### Production angle

Choose the simplest exposure that matches the use case: internal APIs usually need ClusterIP; public HTTP traffic usually goes through Ingress or Gateway infrastructure.

#### Traps / caveats

- NodePort can expand network exposure if firewalls are not managed.
- LoadBalancer behavior is platform-dependent and may create cloud resources and cost.

#### Optional Anki

Q: What is the default Service type?
A: ClusterIP.

</details>

<a id="k8s-net-003"></a>

<details>
<summary><strong>K8S-NET-003. What happens if a Service selector matches no ready Pods?</strong></summary>

#### Short answer

The Service has no usable endpoints, so traffic cannot be routed to application Pods.

#### Interview answer

This can happen when labels do not match, Pods are not ready, the Deployment failed, or the selector points to the wrong version. DNS may still resolve the Service name, but requests fail or time out because there are no backend endpoints.

#### Deep dive

Kubernetes tracks backends through EndpointSlices. Inspecting the Service and EndpointSlices often shows whether the problem is discovery, readiness or the application itself.

#### Production angle

Many 503 incidents behind Ingress are caused by Services with zero ready endpoints.

#### Traps / caveats

- Successful DNS lookup does not prove there are healthy backends.
- A Pod can be running but excluded from endpoints because readiness is failing.

#### Optional Anki

Q: What should you check when a Service has no traffic?
A: Selector, Pod labels, readiness and endpoints.

</details>

<a id="k8s-net-004"></a>

<details>
<summary><strong>K8S-NET-004. How does Kubernetes DNS help service discovery?</strong></summary>

#### Short answer

Kubernetes DNS creates names for Services so Pods can call stable service names instead of Pod IPs.

#### Interview answer

A Service named `orders` in namespace `prod` can be reached with names such as `orders`, `orders.prod` or the full cluster DNS name depending on the client namespace and resolver search path. This lets applications use stable logical names.

#### Deep dive

DNS returns Service addresses or, for headless Services, Pod addresses. Clients still need sane connection pooling, timeouts and DNS caching behavior.

#### Production angle

Java HTTP clients and JDBC drivers may cache DNS or keep long-lived connections, so service changes can require connection refresh behavior.

#### Traps / caveats

- DNS discovery does not replace timeouts, retries or connection pool management.
- `localhost` inside a Pod means the Pod itself, not another Service.

#### Optional Anki

Q: What should services call in Kubernetes instead of Pod IPs?
A: Service DNS names.

</details>

<a id="k8s-net-005"></a>

<details>
<summary><strong>K8S-NET-005. What is the difference between Ingress, an Ingress controller and a Service of type LoadBalancer?</strong></summary>

#### Short answer

Ingress is HTTP routing configuration; an Ingress controller implements it; a LoadBalancer Service exposes a Service through platform load-balancing infrastructure.

#### Interview answer

Ingress defines host/path routing, TLS and related HTTP behavior. It does nothing without an Ingress controller such as NGINX, Traefik or a cloud controller. A LoadBalancer Service usually creates an external load balancer for one Service.

#### Deep dive

Ingress is commonly used to route many HTTP applications through shared edge infrastructure. LoadBalancer Services are simpler but can be less flexible for many routes and domains.

#### Production angle

For a Java REST API, traffic often flows: external load balancer to Ingress controller to Service to ready Pods.

#### Traps / caveats

- Creating an Ingress resource does not expose traffic if no controller handles it.
- Ingress behavior differs across controllers, especially annotations and timeouts.

#### Optional Anki

Q: Does an Ingress work without a controller?
A: No, an Ingress controller must implement it.

</details>

<a id="k8s-net-006"></a>

<details>
<summary><strong>K8S-NET-006. What are common causes of 502 or 503 errors behind Ingress?</strong></summary>

#### Short answer

Common causes include no ready endpoints, wrong Service port, app crashes, probe failures, upstream timeouts, TLS mismatch or bad routing rules.

#### Interview answer

I check the Ingress rule, controller logs, Service, endpoints, Pod readiness, app logs and recent rollout events. A 503 often means no healthy backend; a 502 often means the controller reached something but got a bad upstream response or connection failure.

#### Deep dive

Exact status meanings vary by Ingress controller. The debugging path should follow the request chain from edge to controller to Service to Pod.

#### Production angle

Deployment-time 502/503 spikes often indicate readiness, rollout sequencing, port naming or application startup issues.

#### Traps / caveats

- Do not debug only the application logs; the Ingress controller may show the real failure.
- A Service port and container port mismatch is easy to miss.

#### Optional Anki

Q: What is a common Kubernetes cause of Ingress 503?
A: The Service has no ready endpoints.

</details>

<a id="k8s-net-007"></a>

<details>
<summary><strong>K8S-NET-007. What is a NetworkPolicy, and how can it restrict service-to-service traffic?</strong></summary>

#### Short answer

NetworkPolicy defines allowed ingress or egress traffic for selected Pods, if the cluster network plugin enforces it.

#### Interview answer

By default, many clusters allow broad Pod-to-Pod communication. A NetworkPolicy can select Pods by labels and allow traffic only from certain namespaces, Pods or IP blocks, and only to specific ports. Egress policies can restrict outbound calls.

#### Deep dive

NetworkPolicy is additive: allowed traffic is the union of matching policies. It depends on a CNI plugin that supports enforcement.

#### Production angle

NetworkPolicy reduces blast radius when a service is compromised and helps enforce intended service boundaries.

#### Traps / caveats

- If the CNI does not enforce NetworkPolicy, policies may have no effect.
- NetworkPolicy is not application authorization; it is network-level control.

#### Optional Anki

Q: What must support NetworkPolicy enforcement?
A: The cluster network plugin/CNI.

</details>

<a id="k8s-net-008"></a>

<details>
<summary><strong>K8S-NET-008. What are CNI, Gateway API and service mesh at a high level?</strong></summary>

#### Short answer

CNI provides Pod networking, Gateway API models advanced traffic routing, and service mesh adds service-to-service traffic control and telemetry through proxies or similar infrastructure.

#### Interview answer

CNI plugins give Pods network connectivity and may enforce NetworkPolicy. Gateway API is a newer, more expressive Kubernetes API family for traffic routing than traditional Ingress. A service mesh can provide mTLS, retries, traffic splitting and observability between services.

#### Deep dive

These are platform-level tools. A Java backend engineer should understand the concepts and trade-offs, but does not usually need to implement them from scratch.

#### Production angle

They affect latency, debugging, security and ownership. Introducing a mesh or Gateway layer should solve a real operational problem, not just follow fashion.

#### Traps / caveats

- Service mesh retries can amplify traffic if application retries also exist.
- Gateway and mesh behavior is implementation-specific.

#### Optional Anki

Q: What does CNI provide?
A: Container/Pod networking integration for Kubernetes.

</details>

<a id="k8s-stor-001"></a>

<details>
<summary><strong>K8S-STOR-001. How should a Java service handle local files, uploads and persistent storage in Kubernetes?</strong></summary>

#### Short answer

Treat the container filesystem as temporary; store durable files in object storage, a database or explicit persistent storage designed for the workload.

#### Interview answer

A Pod can be restarted, rescheduled or replaced, so files written to the container writable layer are not durable. For uploads, a Java backend usually streams the file to object storage or another durable service and stores metadata in a database. Kubernetes volumes are useful for specific cases, but they need clear ownership, backup, access mode and lifecycle design.

#### Deep dive

Ephemeral volumes are useful for temporary scratch space. PersistentVolumeClaims can attach durable storage, but they introduce scheduling, access mode and operational concerns. For horizontally scaled stateless APIs, shared object storage is often simpler than sharing a filesystem between Pods.

#### Production angle

File handling affects data loss, scaling, backups, cleanup, cost and incident recovery. Make storage behavior explicit before running multiple replicas.

#### Traps / caveats

- Do not store user uploads only in the container filesystem.
- Do not assume all persistent volumes support multi-writer access or fast failover.

#### Optional Anki

Q: Where should durable uploaded files usually live for a stateless Kubernetes API?
A: In durable external storage such as object storage, with metadata in a database.

</details>

<a id="k8s-cfg-001"></a>

<details>
<summary><strong>K8S-CFG-001. What is the difference between a ConfigMap and a Secret?</strong></summary>

#### Short answer

A ConfigMap stores non-sensitive configuration; a Secret stores sensitive values but still needs careful access control and encryption.

#### Interview answer

Both can be consumed by Pods as environment variables or mounted files. ConfigMaps are for normal config such as feature toggles or URLs. Secrets are for passwords, tokens and certificates, but Kubernetes Secrets are not automatically a complete secret-management solution.

#### Deep dive

Secrets are base64-encoded in manifests, not inherently encrypted by that encoding. Cluster encryption at rest, RBAC, audit and external secret managers may be needed.

#### Production angle

A Java service should fail fast on missing required config and avoid logging secret values from env, config endpoints or exceptions.

#### Traps / caveats

- Base64 is encoding, not encryption.
- Do not store plaintext Secrets in Git.

#### Optional Anki

Q: ConfigMap vs Secret?
A: ConfigMap is non-sensitive config; Secret is sensitive data with extra handling needs.

</details>

<a id="k8s-cfg-002"></a>

<details>
<summary><strong>K8S-CFG-002. What are the trade-offs between passing configuration as environment variables and mounted files?</strong></summary>

#### Short answer

Environment variables are simple and startup-oriented; mounted files can update on disk and are better for larger or file-shaped config.

#### Interview answer

Environment variables map well to Spring Boot relaxed binding and simple values. Mounted files work better for certificates, config trees or values that libraries expect as files. Env vars normally require a process restart to change, while mounted ConfigMap or Secret volumes can update on disk with caveats.

#### Deep dive

Even when mounted files update, the application must reload them or be restarted. Many teams intentionally restart Pods after config changes for predictability.

#### Production angle

Choose a pattern that supports validation, audit and safe rollout. For Spring Boot, typed `@ConfigurationProperties` plus startup validation helps catch bad config early.

#### Traps / caveats

- Environment variables can leak through diagnostics, process inspection or crash reports.
- File updates are eventually reflected, not an instant distributed config system.

#### Optional Anki

Q: Do env var config changes update inside a running process?
A: No, the process usually needs restart.

</details>

<a id="k8s-cfg-003"></a>

<details>
<summary><strong>K8S-CFG-003. What happens to running Pods when a ConfigMap or Secret changes?</strong></summary>

#### Short answer

Environment variables do not update in a running process; mounted volumes may update on disk, but the application may still need a restart or reload.

#### Interview answer

If a ConfigMap or Secret is injected as environment variables, existing Pods keep the old values. If mounted as a normal projected volume, Kubernetes can update the files eventually. However, many applications read config only at startup, so they will continue using old values until restart or explicit reload.

#### Deep dive

Common rollout patterns include changing a Pod template annotation with a config checksum, using a reloader controller, or intentionally creating a new Deployment revision.

#### Production angle

Configuration changes should be deployed and observed like code changes when they can affect production behavior.

#### Traps / caveats

- Do not assume a ConfigMap edit automatically changes Spring Boot runtime behavior.
- ConfigMap or Secret mounts using `subPath` do not receive live updates.
- Secret rotation needs overlap and application compatibility, not just replacing a value.

#### Optional Anki

Q: Do ConfigMap env vars update in running Pods?
A: No.

</details>

<details>
<summary><strong>K8S-CFG-004. How would you manage Spring Boot configuration and profiles in Kubernetes?</strong></summary>

#### Short answer

Use the same image across environments, inject externalized configuration at runtime, validate typed properties, and avoid profile explosion.

#### Interview answer

I would keep the container image environment-neutral. Kubernetes provides environment-specific values through ConfigMaps, Secrets, mounted files or an external secret/config system. Spring Boot profiles can select broad environment behavior, but most operational values should be explicit properties.

#### Deep dive

Typed `@ConfigurationProperties` with validation is safer than scattering many `@Value` fields. The service should fail fast when required configuration is missing or invalid.

#### Production angle

Version config changes, review them, expose safe effective config metadata, and avoid storing secrets in manifests or Helm values files.

#### Traps / caveats

- Do not build one image per environment just to change config.
- Do not put sensitive values in ConfigMaps or logs.

#### Optional Anki

Q: Should a Spring Boot image be rebuilt for each environment?
A: Usually no; promote the same image and inject runtime config.

</details>
