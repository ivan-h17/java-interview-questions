# Containerization fundamentals and Docker images

---

<a id="dk-con-001"></a>

<details>
<summary><strong>DK-CON-001. What problem do containers solve for Java backend services?</strong></summary>

#### Short answer

Containers package an application with its runtime environment so it can run more consistently across local, CI and production systems.

#### Interview answer

For a Java backend service, a container gives a repeatable unit of deployment: the JDK or JRE, application artifact, startup command, OS libraries and default runtime settings. It reduces "works on my machine" problems and makes the service easier to schedule, restart, scale and roll back.

#### Deep dive

Containers do not remove the need for configuration management. Network, CPU, memory, filesystem, secrets and platform differences still matter, but the application runtime becomes much more explicit.

#### Production angle

A good image lets the deployment platform promote the same artifact through environments and reason about version, health, logs and resource usage.

#### Traps / caveats

- Do not bake environment-specific config or secrets into the image.
- Containers improve parity, but they do not guarantee identical production behavior.

#### Optional Anki

Q: What is the main deployment benefit of containers?
A: They package the application and runtime into a repeatable deployment unit.

</details>

<a id="dk-con-002"></a>

<details>
<summary><strong>DK-CON-002. How is a container different from a virtual machine?</strong></summary>

#### Short answer

A VM virtualizes a whole machine with its own guest OS kernel; a container isolates processes while sharing the host kernel.

#### Interview answer

VMs are heavier because each VM runs a guest operating system. Containers are lighter because they run as isolated processes on the host OS. This makes containers faster to start and denser to run, but also means kernel compatibility and host security matter more.

#### Deep dive

Container isolation is built from OS features such as namespaces, cgroups and capabilities. A VM gives a stronger boundary because the guest kernel is separated by a hypervisor.

#### Production angle

Containers are a good fit for stateless Java services, CI jobs and horizontally scaled workloads. VMs may still be preferred for stronger isolation, legacy software or special kernel requirements.

#### Traps / caveats

- A container is not a tiny VM.
- A Linux container cannot run with a Windows kernel, and the reverse is also not generally true.

#### Optional Anki

Q: What does a container share with the host?
A: The host OS kernel.

</details>

<a id="dk-con-003"></a>

<details>
<summary><strong>DK-CON-003. What does it mean that containers share the host kernel?</strong></summary>

#### Short answer

The containerized process uses the same kernel as the host, while user-space files, process view, networking and resources are isolated.

#### Interview answer

The image may contain its own Linux user-space libraries and tools, but system calls go to the host kernel. That is why container isolation depends on kernel features and why host kernel vulnerabilities can affect containers.

#### Deep dive

This also explains some practical differences: container CPU and memory limits are enforced by cgroups, process visibility is controlled by namespaces, and kernel-level features depend on the node, not the image.

#### Production angle

For Java services, kernel sharing usually works well, but teams must still patch nodes, restrict privileges and avoid assuming the container is a complete security boundary.

#### Traps / caveats

- Updating an image does not update the host kernel.
- Running a privileged container can weaken isolation dramatically.

#### Optional Anki

Q: Why can a host kernel vulnerability matter to containers?
A: Containers share the host kernel.

</details>

<a id="dk-con-004"></a>

<details>
<summary><strong>DK-CON-004. What are namespaces and cgroups at a high level?</strong></summary>

#### Short answer

Namespaces isolate what a process can see; cgroups control and account for the resources it can use.

#### Interview answer

Namespaces provide separate views of things like process IDs, network interfaces, mounts and hostnames. Cgroups limit and measure CPU, memory and other resources. Together they make a process feel like it runs in its own environment.

#### Deep dive

Containers usually combine several namespaces with cgroup limits, Linux capabilities, seccomp, AppArmor or SELinux policies. The exact behavior depends on the runtime and host configuration.

#### Production angle

Understanding cgroups matters for Java memory limits, CPU throttling and `OOMKilled` incidents. Understanding namespaces helps explain port binding, `localhost`, process lists and filesystem mounts.

#### Traps / caveats

- Namespaces are isolation, not resource control.
- Cgroups can kill or throttle the process without the JVM fully understanding why.

#### Optional Anki

Q: Namespaces vs cgroups?
A: Namespaces isolate views; cgroups limit and account for resources.

</details>

<a id="dk-con-005"></a>

<details>
<summary><strong>DK-CON-005. What is the difference between a container image and a running container?</strong></summary>

#### Short answer

An image is a read-only template; a container is a running process created from that image with runtime configuration.

#### Interview answer

The image contains layers, files, metadata and default commands. When it runs, the runtime adds a writable layer, environment variables, mounts, network settings, resource limits and the main process.

#### Deep dive

Many containers can be started from the same image. If a container writes to its own filesystem, those writes belong to that container instance and should normally be treated as temporary.

#### Production angle

Build once, run many times is the useful model. The same immutable image can be promoted across environments while configuration and secrets are injected at runtime.

#### Traps / caveats

- Do not store important state only in a container writable layer.
- Do not confuse image rebuilds with container restarts.

#### Optional Anki

Q: Image vs container?
A: An image is the template; a container is a running instance.

</details>

<a id="dk-con-006"></a>

<details>
<summary><strong>DK-CON-006. Why should containers usually be treated as immutable and disposable?</strong></summary>

#### Short answer

Because containers can be stopped, replaced, rescheduled or recreated at any time, so state and fixes should live outside the running instance.

#### Interview answer

The container should be a reproducible runtime for a known image. If you patch files manually inside a running container, the change disappears on restart and cannot be audited or promoted safely. Persistent state belongs in databases, object storage or volumes designed for it.

#### Deep dive

Immutability simplifies rollbacks and scaling. Disposable runtime instances also fit orchestrators such as Kubernetes, where Pods are expected to be ephemeral.

#### Production angle

When an incident happens, the fix should usually be a new image, config change or infrastructure change, not SSH-style manual mutation inside a container.

#### Traps / caveats

- Debugging inside a container is fine; treating that change as a fix is not.
- Local development containers may be more mutable, but production should not depend on that.

#### Optional Anki

Q: Why are production containers disposable?
A: They can be replaced at any time, so durable state and fixes must live outside the instance.

</details>

<a id="dk-con-007"></a>

<details>
<summary><strong>DK-CON-007. What should not be stored inside a container image?</strong></summary>

#### Short answer

Do not store secrets, environment-specific configuration, mutable data, logs, dumps or private credentials inside the image.

#### Interview answer

An image should contain application code and required runtime files. Secrets and environment-specific values should be injected at runtime through the platform. Logs should go to stdout/stderr, and persistent data should go to an external service or mounted storage.

#### Deep dive

Image layers are durable and often pushed to registries, copied to CI caches and scanned by tools. Deleting a secret in a later layer does not reliably remove it from image history.

#### Production angle

Keeping images environment-neutral allows the same artifact to be promoted from staging to production and reduces credential leakage risk.

#### Traps / caveats

- Build arguments can still appear in image metadata or build history.
- A private registry is not a safe place to hide secrets in images.

#### Optional Anki

Q: Why should secrets not be stored in images?
A: Image layers and registries can preserve and expose them.

</details>

<a id="dk-con-008"></a>

<details>
<summary><strong>DK-CON-008. How do Docker image layers affect build cache, pull time and image size?</strong></summary>

#### Short answer

Each Dockerfile step can create a layer; stable layers can be reused, while large or frequently changing layers slow builds and pulls.

#### Interview answer

Docker caches layers when the instruction and its inputs have not changed. If you copy application source before dependencies, every code change can invalidate dependency download layers. Layer size also matters because images are transferred and stored layer by layer.

#### Deep dive

Layering is why Java builds often copy Maven or Gradle descriptors first, resolve dependencies, and only then copy source. Spring Boot layered jars and Jib use a similar idea by separating dependencies from application classes.

#### Production angle

Good layering speeds CI, reduces registry traffic, improves node pull time and makes rollouts less painful.

#### Traps / caveats

- Deleting files in a later layer may not reduce the size of earlier layers.
- Cache efficiency must not come at the cost of stale dependencies or unreproducible builds.

#### Optional Anki

Q: Why copy dependency descriptors before source code in many Dockerfiles?
A: To keep dependency layers cacheable when only application code changes.

</details>

<a id="dk-con-009"></a>

<details>
<summary><strong>DK-CON-009. How would you choose a base image for a Java service?</strong></summary>

#### Short answer

Choose a maintained, minimal, compatible JDK or JRE image with clear patching, architecture support and operational tooling needs.

#### Interview answer

I check the Java version, vendor support, OS family, vulnerability profile, image size, libc compatibility, time zone and certificate behavior, and whether I need shell/debug tools. For production, I prefer a small maintained runtime image and a separate build stage.

#### Deep dive

The smallest image is not always best. A distroless image reduces attack surface but can make debugging harder; a Debian-based image is often more predictable for native libraries.

#### Production angle

The base image affects CVE response, startup diagnostics, native DNS or TLS behavior, and how quickly the team can patch runtime vulnerabilities.

#### Traps / caveats

- Do not pick Alpine blindly for Java services that depend on native libraries.
- Do not use an unmaintained image just because it is small.

#### Optional Anki

Q: What matters when choosing a Java base image?
A: Compatibility, maintenance, patching, size, security and operability.

</details>

<a id="dk-con-010"></a>

<details>
<summary><strong>DK-CON-010. What are the trade-offs between Alpine, Debian/Ubuntu and distroless Java images?</strong></summary>

#### Short answer

Alpine is small but can have libc compatibility surprises; Debian/Ubuntu is larger but familiar; distroless is minimal but harder to inspect interactively.

#### Interview answer

Alpine uses musl libc, so Java itself usually works, but native dependencies, DNS behavior or tooling assumptions can surprise you. Debian and Ubuntu images are larger but have glibc and familiar packages. Distroless images remove shells and package managers, reducing attack surface but changing debugging workflows.

#### Deep dive

The right choice depends on whether the service needs native libraries, shell-based diagnostics, strict security posture, or very small pull sizes.

#### Production angle

For a Senior backend role, the important answer is not "always use the smallest image"; it is to choose deliberately and test runtime behavior.

#### Traps / caveats

- Smaller image size does not automatically mean lower risk.
- Distroless requires readiness for external debugging tools and good telemetry.

#### Optional Anki

Q: Main distroless trade-off?
A: Lower attack surface, but less interactive debugging capability.

</details>

<a id="dk-con-011"></a>

<details>
<summary><strong>DK-CON-011. Why should production deployments avoid mutable image tags such as `latest`?</strong></summary>

#### Short answer

Mutable tags make deployments non-reproducible because the same tag can point to different image contents over time.

#### Interview answer

If production uses `latest`, a restart can pull a different image than the one that was tested. Rollback and incident analysis become unreliable because the deployment record does not identify exact bytes. Immutable tags and digests make the release traceable.

#### Deep dive

Tags are names; digests identify image content. Many teams use semantic or commit-based tags for readability and pin by digest for exactness.

#### Production angle

Immutable image references support audit, rollback, vulnerability response and promotion of the same artifact through environments.

#### Traps / caveats

- A commit SHA tag is only safe if the registry policy prevents overwriting it.
- `imagePullPolicy: Always` does not fix mutable-tag ambiguity.

#### Optional Anki

Q: Why prefer image digests in production?
A: A digest identifies exact image content.

</details>

<a id="dk-con-012"></a>

<details>
<summary><strong>DK-CON-012. What are OCI, container runtimes, containerd and CRI-O at a high level?</strong></summary>

#### Short answer

OCI defines container image/runtime standards; containerd and CRI-O are runtimes that Kubernetes can use to run containers through the Container Runtime Interface.

#### Interview answer

Docker is not the only way to run containers. Kubernetes talks to a container runtime through CRI. containerd and CRI-O pull images, manage containers and delegate low-level execution to runtime components that implement OCI behavior.

#### Deep dive

A Java backend engineer usually does not operate runtimes daily, but should understand that Kubernetes does not require Docker Engine on nodes. This matters when debugging image pulls, runtime errors or node behavior.

#### Production angle

Runtime choice affects node operations, logging, image pulling, security features and troubleshooting commands.

#### Traps / caveats

- "Docker image" is often used casually, but OCI images can be run by many runtimes.
- Installing Docker locally does not mean production Kubernetes nodes use Docker Engine.

#### Optional Anki

Q: How does Kubernetes talk to container runtimes?
A: Through the Container Runtime Interface, usually to runtimes like containerd or CRI-O.

</details>

<a id="dk-con-013"></a>

<details>
<summary><strong>DK-CON-013. Why should containerized applications write logs to stdout and stderr?</strong></summary>

#### Short answer

Because container platforms collect process output from stdout and stderr and route it to logging systems outside the container.

#### Interview answer

A container should not manage its own log files as durable state. The application writes structured logs to stdout or stderr, and the runtime or Kubernetes node logging pipeline collects them. This keeps containers disposable and lets logs be centralized, searched, retained and correlated.

#### Deep dive

For Spring Boot services, this usually means console logging with a consistent format, safe fields and correlation IDs. File appenders can still be used in special cases, but they require explicit volume, rotation and collection design.

#### Production angle

Centralized log collection is what makes `kubectl logs`, node agents and observability platforms useful during incidents.

#### Traps / caveats

- Do not store important logs only inside the container filesystem.
- Do not log secrets, tokens, raw credentials or excessive high-cardinality payloads.

#### Optional Anki

Q: Why log to stdout/stderr in containers?
A: The platform collects process output and ships it to centralized logging.

</details>
