# Logging, structured events and correlation

---

<a id="obs-log-001"></a>

<details>
<summary><strong>OBS-LOG-001. What is structured logging, and why is it useful?</strong></summary>

#### Short answer

Structured logging records events as fields, usually JSON, so logs can be searched, filtered and aggregated reliably.

#### Interview answer

Instead of writing only free-text messages, structured logs include fields like timestamp, level, service, trace ID, operation, result and error category. This makes logs machine-queryable and allows incident responders to filter by tenant, endpoint, dependency, version or failure type.

#### Deep dive

The message is still useful for humans, but stable field names are what make logs useful at scale. Teams should standardize key names across services.

#### Production angle

Structured logs help answer questions like "which requests for tenant X failed after version Y was deployed?"

#### Traps / caveats

- Do not put unbounded or sensitive values into structured fields casually.
- Do not rely on inconsistent field names such as `requestId`, `req_id` and `correlation` across services.

#### Optional Anki

Q: Why prefer structured logs over plain text?
A: They can be queried and aggregated by stable fields.

</details>

<a id="obs-log-002"></a>

<details>
<summary><strong>OBS-LOG-002. What fields should a backend service include in important log events?</strong></summary>

#### Short answer

Include time, level, service, environment, version, operation, result, trace/request IDs, error category and safe business context.

#### Interview answer

Useful logs usually include `timestamp`, `level`, `service`, `env`, `version`, `trace_id`, `span_id`, request or correlation ID, route or operation name, outcome, status, latency and exception class. For business flows, include safe IDs such as order ID or job ID when policy allows.

#### Deep dive

Field choice should match incident questions. For example, payment processing needs payment attempt ID and outcome category; a batch job needs job ID, partition and processed counts.

#### Production angle

Good fields let engineers isolate one affected user journey without enabling DEBUG logs globally.

#### Traps / caveats

- Do not log raw request/response bodies by default.
- Safe identifiers still need privacy and retention review.

#### Optional Anki

Q: Name two correlation fields common in logs.
A: `trace_id` and request or correlation ID.

</details>

<a id="obs-log-003"></a>

<details>
<summary><strong>OBS-LOG-003. What is a correlation ID or request ID?</strong></summary>

#### Short answer

It is an identifier carried through related work so logs and events can be connected.

#### Interview answer

A request ID usually identifies one inbound request to a service. A correlation ID often identifies a broader business workflow across services, messages or jobs. The exact meaning must be consistent inside the system.

#### Deep dive

Correlation IDs are useful even without full tracing. They can be generated at the edge, accepted from trusted upstreams, and propagated through HTTP headers and message metadata.

#### Production angle

When a customer reports one failed checkout, a correlation ID helps find all related logs and events quickly.

#### Traps / caveats

- Do not trust arbitrary external correlation IDs without validation and length limits.
- Do not use correlation IDs as metric labels.

#### Optional Anki

Q: What is the main purpose of a correlation ID?
A: To connect related logs and events across components.

</details>

<a id="obs-log-004"></a>

<details>
<summary><strong>OBS-LOG-004. What is a trace ID, and how does it differ from a correlation ID?</strong></summary>

#### Short answer

A trace ID identifies one distributed trace; a correlation ID is a broader application identifier whose meaning is defined by the system.

#### Interview answer

A trace ID is part of tracing context and links spans in one trace. A correlation ID may represent a request, business workflow, command or external client request. Sometimes they are the same value, but they do not have to be.

#### Deep dive

Trace IDs are managed by tracing instrumentation and sampling. Correlation IDs are often application-level and may be useful even when the trace was not sampled.

#### Production angle

Log both when both are available: trace ID for telemetry navigation and correlation/business ID for user workflow investigation.

#### Traps / caveats

- Do not assume every correlation ID has a trace in the tracing backend.
- Do not expose internal trace identifiers as a stable public contract unless intended.

#### Optional Anki

Q: Does a correlation ID always equal a trace ID?
A: No, a trace ID identifies telemetry spans; a correlation ID is application-defined.

</details>

<a id="obs-log-005"></a>

<details>
<summary><strong>OBS-LOG-005. How should trace IDs and span IDs appear in logs?</strong></summary>

#### Short answer

They should be emitted as stable structured fields on logs produced inside the active trace context.

#### Interview answer

Application logs should include fields such as `trace_id` and `span_id` so a log line can link to the relevant trace and span. In Java, this is usually done by logging framework integration with MDC or the observability library.

#### Deep dive

For async code, the logging context must be propagated to worker threads or reactive operators. Otherwise logs from downstream work appear disconnected from the request that caused them.

#### Production angle

Trace-log correlation lets engineers jump from a slow span to the exact error or branch that occurred inside it.

#### Traps / caveats

- Do not manually invent trace IDs separate from the tracing system.
- MDC values can leak between reused threads if not cleared correctly.

#### Optional Anki

Q: Why put `trace_id` in logs?
A: To correlate log events with distributed traces.

</details>

<a id="obs-log-006"></a>

<details>
<summary><strong>OBS-LOG-006. What should not be logged, and how should sensitive data be masked or redacted?</strong></summary>

#### Short answer

Do not log secrets, credentials, tokens, private keys, raw PII, payment data or sensitive payloads; remove or mask them before logs leave the service.

#### Interview answer

Logs are copied, indexed and viewed by many systems and people. Passwords, authorization headers, JWTs, API keys, session IDs, private keys, full card numbers and unnecessary personal data should be omitted or redacted. Redaction should be centralized where possible.

#### Deep dive

Masking keeps part of a value, such as the last four digits; redaction removes it. Hashing is not automatically safe if the value has a small search space or can still identify a person.

#### Production angle

Unsafe logging can turn an ordinary bug into a security incident and a data deletion problem.

#### Traps / caveats

- Do not rely only on reviewers catching sensitive log statements.
- Exception messages and serialized objects can accidentally contain secrets.

#### Optional Anki

Q: Should raw JWTs be logged for debugging?
A: No, tokens are credentials and should be omitted or redacted.

</details>

<a id="obs-log-007"></a>

<details>
<summary><strong>OBS-LOG-007. How do you make logs useful without creating too much noise?</strong></summary>

#### Short answer

Log important state transitions and failures with context, use levels consistently, and avoid repetitive per-record or full-payload logs.

#### Interview answer

INFO should describe meaningful business or operational events, WARN should describe unexpected but handled conditions, and ERROR should indicate failed operations that need attention. High-volume debug details should be sampled, guarded or enabled temporarily.

#### Deep dive

A useful logging strategy defines which events matter, which fields are required, which values are forbidden, and how long logs are retained. Logs should complement metrics, not replace them.

#### Production angle

Excessive logs raise cost and can hide the signal during incidents.

#### Traps / caveats

- Do not log every retry attempt as ERROR if retries are normal and bounded.
- Do not suppress all exception details; keep enough cause and classification to act.

#### Optional Anki

Q: What should ERROR logs usually represent?
A: Failed operations that require investigation or indicate user/business impact.

</details>

<a id="obs-log-008"></a>

<details>
<summary><strong>OBS-LOG-008. What makes an error log actionable?</strong></summary>

#### Short answer

It identifies what failed, where, why if known, impact, correlation context and what category of action may be needed.

#### Interview answer

An actionable error log includes operation name, safe identifiers, error type, result category, dependency if relevant, trace ID and enough exception information. It avoids vague messages like "failed" without context.

#### Deep dive

Not every exception deserves ERROR. Expected validation failures may be INFO or WARN with metrics. Unexpected failures should preserve stack traces and cause chains where useful.

#### Production angle

Actionable logs reduce time spent searching for which tenant, request, dependency or release caused the issue.

#### Traps / caveats

- Do not log and rethrow the same exception at every layer.
- Do not omit the original cause when wrapping exceptions.

#### Optional Anki

Q: What is a common bad error log?
A: A generic "failed" message without operation, IDs, cause or impact.

</details>

<a id="obs-log-009"></a>

<details>
<summary><strong>OBS-LOG-009. How should runtime log-level changes be used safely in production?</strong></summary>

#### Short answer

Use them temporarily, narrowly and with access control, because verbose logging can expose data and overload systems.

#### Interview answer

Runtime log-level changes, such as through Spring Boot Actuator, are useful during incidents when one package or class needs DEBUG logs without a redeploy. They should be restricted, audited, time-limited and rolled back after diagnosis.

#### Deep dive

In a replicated service, changing one instance may be enough for diagnosis, while changing all replicas can create huge log volume. Changes may also disappear after restart unless persisted intentionally.

#### Production angle

Dynamic logging is powerful for production debugging but should be treated as an administrative operation.

#### Traps / caveats

- TRACE logs can include sensitive payloads or very high volume.
- Do not expose log-level management endpoints publicly.

#### Optional Anki

Q: Why should runtime DEBUG logging be time-limited?
A: It can create cost, noise and sensitive-data exposure.

</details>

<a id="obs-log-010"></a>

<details>
<summary><strong>🧠 OBS-LOG-010. How do asynchronous processing and thread pools break log context propagation?</strong></summary>

#### Short answer

Thread-local logging context does not automatically move to another thread or async continuation.

#### Interview answer

Java logging correlation often uses MDC, which is typically thread-local. When work moves to an executor, `CompletableFuture`, scheduler, message listener or reactive pipeline, the new thread may not have the original request context unless the framework captures and restores it.

#### Deep dive

Context propagation must also clear old context to avoid leaking one request's IDs into another request on reused threads. Instrumentation libraries, task decorators or explicit context wrappers can help.

#### Production angle

Broken propagation produces orphan logs that are hard to connect to the request or job that caused them.

#### Traps / caveats

- Copying MDC manually everywhere is error-prone.
- Propagating too much context can leak sensitive or stale data.

#### Optional Anki

Q: Why can MDC fail in async code?
A: MDC is usually thread-local and async work may run on a different reused thread.

</details>

<details>
<summary><strong>🧠 OBS-LOG-011. How do log sampling and retention policies affect incident investigation?</strong></summary>

#### Short answer

Sampling and retention control cost, but they can remove evidence needed to debug rare or delayed incidents.

#### Interview answer

Sampling reduces log volume by keeping only some events or suppressing repetitive logs. Retention defines how long logs remain searchable. Both should reflect incident needs: security events, payment failures and audit-like records may need different treatment from noisy debug logs.

#### Deep dive

Sampling should preserve rare errors and representative context, not randomly drop the only useful event. Retention should match how long incidents are usually discovered after they happen.

#### Production angle

If logs expire after three days but customers report monthly billing issues after two weeks, investigation will be weak.

#### Traps / caveats

- Do not sample away all failed requests while keeping successful ones.
- Do not confuse debug logs with audit trails; they have different retention and integrity needs.

#### Optional Anki

Q: What is a risk of aggressive log sampling?
A: It can drop the evidence needed for rare failure investigation.

</details>
