# Investigation scenarios, quality and governance

---

<a id="obs-scen-001"></a>

<details>
<summary><strong>OBS-SCEN-001. A service has high p99 latency but normal average latency. What do you check?</strong></summary>

#### Short answer

Check tail-specific causes: slow dependencies, pool waits, queueing, GC pauses, locks, retries, large payloads and affected dimensions.

#### Interview answer

I would break latency down by endpoint, version, tenant, region and dependency. Then inspect traces for slow requests, pool wait metrics, database query latency, retries, queue depth, GC pauses and thread contention. Normal average latency means most requests are fine, so the issue is likely partial or tail-heavy.

#### Deep dive

Tail latency is often caused by saturation, fan-out calls, one bad partition, cold caches, slow queries or retry behavior.

#### Production angle

Users experience the slow request they hit, not the average request.

#### Traps / caveats

- Do not optimize based only on one trace without checking scope.
- Do not ignore pool and queue wait time.

#### Optional Anki

Q: What does high p99 with normal average usually suggest?
A: Tail latency affecting a minority of requests.

</details>

<a id="obs-scen-002"></a>

<details>
<summary><strong>OBS-SCEN-002. Error rate increased after deployment. Which telemetry do you inspect first?</strong></summary>

#### Short answer

Compare old versus new versions for errors, affected endpoints, logs, traces, dependencies and business outcomes.

#### Interview answer

I would check deployment markers, error rate by version and endpoint, exception categories, logs with trace IDs, traces for failing requests, dependency metrics and feature-flag/config changes. If only new pods fail, rollback or disable the change may be the fastest mitigation.

#### Deep dive

Also check whether the error is server-side, validation-related, serialization-related, database-related or caused by a downstream contract mismatch.

#### Production angle

Version-aware telemetry turns "errors are up" into "version 2.3 fails on POST /orders due to database constraint errors."

#### Traps / caveats

- Do not assume every post-deploy error is caused by code; config and traffic shifts matter.
- Do not wait for root cause if rollback is safe and user impact is high.

#### Optional Anki

Q: Why filter errors by version after deployment?
A: To see whether the new release is responsible.

</details>

<a id="obs-scen-003"></a>

<details>
<summary><strong>OBS-SCEN-003. How do you correlate one API request with logs, traces and database calls?</strong></summary>

#### Short answer

Use the trace ID or correlation ID to find the request trace, related logs and dependency spans or metrics.

#### Interview answer

Start from a request ID, trace ID, error response ID or safe business ID. Find the trace, inspect spans for controller, service, database and downstream calls, then query logs by `trace_id` or correlation ID. Database spans or query logs should show the relevant operation category and timing.

#### Deep dive

If tracing is missing, use gateway logs, application logs, access logs and database timing metrics to reconstruct the path.

#### Production angle

Correlation turns a customer report into concrete evidence instead of searching by timestamp alone.

#### Traps / caveats

- Do not put raw sensitive customer data into correlation fields.
- Sampled traces may be missing, so logs still matter.

#### Optional Anki

Q: What identifier usually connects logs and traces?
A: The trace ID.

</details>

<a id="obs-scen-004"></a>

<details>
<summary><strong>OBS-SCEN-004. A dashboard shows normal CPU but users report timeouts. What else do you inspect?</strong></summary>

#### Short answer

Inspect dependency latency, pool waits, locks, queues, thread states, network errors, retries, load balancers and client timeouts.

#### Interview answer

Low CPU often means the service is waiting. I would check database and HTTP dependency latency, connection pool acquisition time, executor queues, thread dumps, lock contention, Kafka or job backlog, retry volume, GC pauses, ingress/load balancer metrics and whether timeouts happen upstream.

#### Deep dive

Timeouts can occur outside the application process, such as at a proxy, gateway, service mesh or client.

#### Production angle

Normal CPU should not reassure you when latency and availability indicators show user impact.

#### Traps / caveats

- Do not scale CPU when the bottleneck is a database pool or downstream timeout.
- Do not rely only on application dashboards; check edge and network telemetry.

#### Optional Anki

Q: What does low CPU with hanging requests often imply?
A: Waiting on dependencies, locks, queues or pools.

</details>

<a id="obs-scen-005"></a>

<details>
<summary><strong>OBS-SCEN-005. A health check is green but the service is unusable. What could be wrong?</strong></summary>

#### Short answer

The health check may be too shallow, checking process liveness while real serving paths are broken.

#### Interview answer

A green health check can miss broken dependencies, exhausted pools, bad configuration, authorization failures, message backlog, failed business rules, partial endpoint failure or upstream routing problems. Liveness and readiness are not substitutes for user-impact metrics.

#### Deep dive

Health checks often test "can the process answer this endpoint?" not "can checkout complete?" Service health needs API SLOs and business metrics too.

#### Production angle

Green health with user failure is a signal that observability and readiness semantics need improvement.

#### Traps / caveats

- Do not add every dependency to liveness as a reaction.
- Do not let health endpoints become expensive full-system tests.

#### Optional Anki

Q: What does a green liveness check prove?
A: Mostly that the process can respond to the liveness endpoint.

</details>

<a id="obs-scen-006"></a>

<details>
<summary><strong>OBS-SCEN-006. Traces are incomplete across service boundaries. What do you check?</strong></summary>

#### Short answer

Check trace header propagation, client/server instrumentation, async boundaries, sampling, proxies and messaging headers.

#### Interview answer

I would verify that inbound and outbound frameworks are instrumented, W3C trace headers are preserved, service gateways do not strip them, message producers and consumers copy headers, and executors/reactive pipelines propagate context. I would also check sampling and exporter failures.

#### Deep dive

Incomplete traces can be caused by missing instrumentation in one service, incompatible propagators, lost context in async code, or a failing telemetry pipeline.

#### Production angle

Trace gaps make it hard to find the service or dependency causing cross-service latency.

#### Traps / caveats

- Do not assume missing spans mean the service was not called.
- Do not mix propagation formats accidentally across services.

#### Optional Anki

Q: What HTTP header commonly carries trace context?
A: `traceparent`.

</details>

<a id="obs-scen-007"></a>

<details>
<summary><strong>OBS-SCEN-007. What observability checklist should be completed before launching a new service?</strong></summary>

#### Short answer

Confirm metrics, logs, traces, health checks, dashboards, alerts, ownership, runbooks, retention and sensitive-data controls.

#### Interview answer

Before launch, I want RED metrics, dependency metrics, JVM/resource metrics, structured logs with trace IDs, trace propagation, liveness/readiness, business outcome metrics, dashboards, SLO or launch alerts, runbooks, on-call ownership and redaction/cardinality review.

#### Deep dive

Async services also need lag, event age, processing duration, retry and DLQ telemetry. Batch jobs need completion, duration and failure visibility.

#### Production angle

Launch readiness should prove the team can detect, triage and mitigate failures.

#### Traps / caveats

- Do not wait for the first outage to add alert ownership.
- Do not launch with telemetry that leaks secrets or creates unbounded labels.

#### Optional Anki

Q: Name one non-metric launch observability requirement.
A: Runbook and alert ownership.

</details>

<a id="obs-scen-008"></a>

<details>
<summary><strong>OBS-SCEN-008. A scheduled job or batch pipeline fails silently. What observability should have caught it?</strong></summary>

#### Short answer

Job completion, duration, failure count, freshness, processed records and missed-run alerts should have caught it.

#### Interview answer

Scheduled jobs need telemetry for last successful run, last attempted run, duration, result, processed count, failed count, skipped count and output freshness. Alerts should fire when a critical job does not run, runs too long, processes zero records unexpectedly or produces stale downstream data.

#### Deep dive

Batch jobs should emit business-level completion metrics, not only logs. For partitioned jobs, metrics should show per-partition or per-tenant gaps when bounded.

#### Production angle

Silent job failures often appear as stale reports, missing notifications or delayed billing long after the cause happened.

#### Traps / caveats

- Do not rely only on "job started" logs.
- Do not alert only on exceptions; a job can complete successfully but process no required data.

#### Optional Anki

Q: What metric detects a missed scheduled job?
A: Last successful run age or output freshness.

</details>

<a id="obs-scen-009"></a>

<details>
<summary><strong>OBS-SCEN-009. How do you keep telemetry names, owners and retention useful across services?</strong></summary>

#### Short answer

Use shared conventions, review, ownership metadata, documentation, dashboards as code and retention policies by signal value.

#### Interview answer

Telemetry should have naming conventions for common operations, standard labels, owners, service metadata and documented meaning. Critical dashboards and alert rules should be versioned and reviewed. Retention should match investigation needs, compliance and cost.

#### Deep dive

Governance does not mean blocking every team. It means giving teams reusable libraries, safe defaults and review for high-cardinality or sensitive telemetry.

#### Production angle

Consistent telemetry lets responders move between services without relearning every metric vocabulary.

#### Traps / caveats

- Do not let unused metrics live forever without owners.
- Do not standardize so rigidly that teams cannot expose domain-specific signals.

#### Optional Anki

Q: Why document metric meaning?
A: So dashboards and alerts remain understandable across teams and time.

</details>

<a id="obs-scen-010"></a>

<details>
<summary><strong>🧠 OBS-SCEN-010. How do you improve observability after a postmortem without adding noise?</strong></summary>

#### Short answer

Add telemetry that answers a missed incident question, remove or tune noisy signals, and verify the new signal would have helped.

#### Interview answer

Start from the postmortem: what did we not know quickly enough? Add the smallest metric, log field, span, dashboard or alert that would answer that question next time. Prefer user-impact or decision-supporting telemetry over broad debug output.

#### Deep dive

Every new alert should have owner, severity, threshold reasoning and runbook updates. Every new metric should have bounded labels and a dashboard or query use case.

#### Production angle

Postmortem-driven observability improves detection and diagnosis without turning the system into a noisy telemetry dump.

#### Traps / caveats

- Do not add an alert for every symptom seen during the incident.
- Do not keep noisy follow-up telemetry forever if it stops being useful.

#### Optional Anki

Q: What question should postmortem observability work answer?
A: What did we need to know sooner during the incident?

</details>
