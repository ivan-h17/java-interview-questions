# Distributed tracing, OpenTelemetry and telemetry pipelines

---

<a id="obs-trace-001"></a>

<details>
<summary><strong>OBS-TRACE-001. What is distributed tracing?</strong></summary>

#### Short answer

Distributed tracing records the path of one request or workflow across services and operations.

#### Interview answer

A trace is made of spans. Each span represents a unit of work, such as handling an HTTP request, calling a database or publishing a message. The trace connects these spans so engineers can see where time was spent and where failures occurred.

#### Deep dive

Tracing is especially useful for microservices, async workflows and fan-out calls. It complements metrics and logs; it does not replace them.

#### Production angle

During a latency incident, a trace can show whether the slow part is the service itself, a database query, an HTTP dependency or queue wait.

#### Traps / caveats

- A sampled trace may not exist for every request.
- Missing instrumentation can hide the actual slow operation.

#### Optional Anki

Q: What is a span?
A: A timed unit of work inside a trace.

</details>

<a id="obs-trace-002"></a>

<details>
<summary><strong>OBS-TRACE-002. How do OpenTelemetry traces help debug microservices?</strong></summary>

#### Short answer

They provide a vendor-neutral way to collect and connect spans across services, libraries and infrastructure.

#### Interview answer

OpenTelemetry instrumentation can trace inbound HTTP, outbound HTTP, JDBC, messaging, executors and custom spans. This helps show the full path of a request across services and dependencies, including timing, status and selected attributes.

#### Deep dive

OpenTelemetry separates APIs, SDKs, instrumentation and export pipeline. A Java service can use an agent, framework integration or manual instrumentation.

#### Production angle

OpenTelemetry helps standardize tracing across services instead of each team using incompatible vendor-specific instrumentation.

#### Traps / caveats

- Auto-instrumentation may miss custom business steps.
- Too many span attributes or high trace volume can become expensive.

#### Optional Anki

Q: Why is OpenTelemetry useful across many services?
A: It standardizes telemetry APIs and data export.

</details>

<a id="obs-trace-003"></a>

<details>
<summary><strong>OBS-TRACE-003. What is context propagation?</strong></summary>

#### Short answer

Context propagation passes trace and correlation context across threads, services and asynchronous boundaries.

#### Interview answer

When service A calls service B, publishes a message or submits async work, it should pass the current trace context so child or linked spans can be connected to the original operation. Without propagation, traces become fragmented.

#### Deep dive

Propagation commonly uses HTTP headers, message headers and framework-specific async context mechanisms. It often depends on instrumentation in clients, servers and executors.

#### Production angle

Broken propagation turns a distributed trace into isolated pieces, making incident investigation much slower.

#### Traps / caveats

- Do not propagate sensitive data as tracing baggage casually.
- Thread-local context needs special handling across async execution.

#### Optional Anki

Q: What happens when trace context is not propagated?
A: Spans appear as separate traces instead of one connected workflow.

</details>

<a id="obs-trace-004"></a>

<details>
<summary><strong>OBS-TRACE-004. How should trace context propagate through HTTP calls?</strong></summary>

#### Short answer

HTTP clients should inject trace headers, and servers should extract them and create child spans.

#### Interview answer

In practice, tracing instrumentation adds headers such as W3C `traceparent` and sometimes `tracestate` to outbound requests. The receiving service extracts the context and continues the trace by creating a server span related to the client span.

#### Deep dive

Most modern Java frameworks and HTTP clients can do this automatically when properly instrumented. Gateways, proxies and service meshes should preserve tracing headers.

#### Production angle

HTTP propagation lets engineers follow a request from gateway to backend services and dependencies.

#### Traps / caveats

- Do not strip trace headers at gateways unless intentional.
- Be careful accepting untrusted external trace context without limits and policy.

#### Optional Anki

Q: Which common HTTP header carries W3C trace context?
A: `traceparent`.

</details>

<a id="obs-trace-005"></a>

<details>
<summary><strong>OBS-TRACE-005. How should trace context propagate through messaging systems?</strong></summary>

#### Short answer

Put trace or correlation context in message headers and extract it when consuming the message.

#### Interview answer

For Kafka or similar brokers, the producer injects trace context into record headers. The consumer extracts it and creates a processing span, often linked to the produce span. This preserves causality between the request that published an event and the asynchronous work that consumed it.

#### Deep dive

Messaging traces are not always a simple parent-child call stack. Retries, DLQs and batch consumption may require links, separate spans and clear messaging attributes.

#### Production angle

Trace context through messages helps answer "which request created this event?" and "where did this workflow stall?"

#### Traps / caveats

- Retry and DLQ publication should preserve useful context.
- Do not put large or sensitive business payloads into tracing headers.

#### Optional Anki

Q: Where is trace context usually stored in Kafka records?
A: Record headers.

</details>

<a id="obs-trace-006"></a>

<details>
<summary><strong>OBS-TRACE-006. When should you create a custom span?</strong></summary>

#### Short answer

Create a custom span for meaningful work not already covered by automatic instrumentation.

#### Interview answer

Good custom spans represent important business operations, expensive computations, external calls hidden behind libraries, queue waits or workflow steps. They should help explain latency or failure. Do not create spans for every small helper method.

#### Deep dive

Span names should be stable and operation-oriented, such as `payment.authorize` or `order.reserve_inventory`. Attributes should classify outcomes without leaking sensitive data.

#### Production angle

Custom spans make traces explain domain behavior, not just framework internals.

#### Traps / caveats

- Too many tiny spans make traces noisy and expensive.
- Missing custom spans can hide the actual business bottleneck.

#### Optional Anki

Q: What is a good custom span boundary?
A: A meaningful operation that helps explain latency or failure.

</details>

<a id="obs-trace-007"></a>

<details>
<summary><strong>OBS-TRACE-007. What should and should not be added as span attributes?</strong></summary>

#### Short answer

Add stable, useful, non-sensitive context; avoid secrets, raw payloads and high-cardinality values unless policy allows.

#### Interview answer

Good span attributes include service version, operation name, dependency name, result category, HTTP route template, messaging topic or database system. Dangerous attributes include tokens, passwords, full request bodies, emails, raw SQL with values, request IDs as indexed dimensions, and personal data.

#### Deep dive

Traces can often tolerate more request-level detail than metrics, but trace attributes are still stored, indexed and accessed by people and tools.

#### Production angle

Safe attributes make traces useful without turning observability into a privacy incident.

#### Traps / caveats

- Do not put full SQL parameter values into spans.
- Do not assume traces have weaker compliance requirements than logs.

#### Optional Anki

Q: What is a safe span attribute for HTTP?
A: Route template, such as `/orders/{id}`, not the raw URL.

</details>

<a id="obs-trace-008"></a>

<details>
<summary><strong>OBS-TRACE-008. What is trace sampling, and why is it needed?</strong></summary>

#### Short answer

Trace sampling keeps only some traces to control cost, storage and pipeline load.

#### Interview answer

High-traffic services cannot always store every trace. Sampling selects which traces are recorded or exported. The goal is to preserve enough evidence for debugging while keeping overhead and cost acceptable.

#### Deep dive

Sampling strategy should consider traffic volume, error traces, latency outliers, important tenants and compliance. Metrics should still track all requests because sampled traces are not complete traffic counts.

#### Production angle

Good sampling keeps traces affordable while preserving enough failed and slow examples to investigate incidents.

#### Traps / caveats

- Sampling can hide rare failures if configured poorly.
- Do not use sampled trace counts as exact request counts.

#### Optional Anki

Q: Why sample traces?
A: To control telemetry volume and cost.

</details>

<a id="obs-trace-009"></a>

<details>
<summary><strong>OBS-TRACE-009. What is the difference between head sampling and tail sampling?</strong></summary>

#### Short answer

Head sampling decides at the start of a trace; tail sampling decides after seeing more or all of the trace.

#### Interview answer

Head sampling is cheap and simple but cannot know whether a request will become slow or fail. Tail sampling can keep traces based on outcome, latency or attributes after the trace completes, but it needs buffering and more collector-side resources.

#### Deep dive

Head sampling often happens in the SDK or agent. Tail sampling is commonly implemented in a collector or backend that can observe the completed trace.

#### Production angle

Tail sampling is useful when you want to keep errors and outliers without storing every successful fast request.

#### Traps / caveats

- Tail sampling can lose traces if collectors are overloaded or buffering is undersized.
- Head sampling can drop the one failed trace you needed.

#### Optional Anki

Q: Which sampling style can keep traces based on final latency?
A: Tail sampling.

</details>

<a id="obs-trace-010"></a>

<details>
<summary><strong>OBS-TRACE-010. What role does the OpenTelemetry Collector play?</strong></summary>

#### Short answer

The Collector receives, processes and exports telemetry between applications and observability backends.

#### Interview answer

Applications can send traces, metrics and logs to an OpenTelemetry Collector instead of directly to a vendor backend. The Collector can batch, filter, enrich, transform, sample and route telemetry to one or more destinations.

#### Deep dive

Collectors can run as agents near workloads, as gateways, or both. They separate application instrumentation from backend-specific export details.

#### Production angle

A Collector layer gives teams centralized control over sampling, redaction, routing and exporter configuration.

#### Traps / caveats

- A Collector is another production component that must be monitored and scaled.
- Bad Collector configuration can drop or distort telemetry.

#### Optional Anki

Q: Why use an OpenTelemetry Collector?
A: To process and export telemetry independently of application code.

</details>

<a id="obs-trace-011"></a>

<details>
<summary><strong>🧠 OBS-TRACE-011. What can go wrong when telemetry exporters or collectors are overloaded?</strong></summary>

#### Short answer

Telemetry can be dropped, delayed, consume application resources or hide incidents exactly when load is highest.

#### Interview answer

Exporters buffer and send telemetry. If the backend or Collector is slow, buffers may grow, exports may fail, CPU and memory may rise, and telemetry may be dropped. The application must not block critical request processing indefinitely while trying to export observability data.

#### Deep dive

Collectors also need their own metrics: receive rate, export failures, queue size, dropped items, memory usage and retry behavior. Backpressure behavior should be chosen deliberately.

#### Production angle

During outages, telemetry volume often increases. The telemetry pipeline must degrade safely rather than making the application outage worse.

#### Traps / caveats

- Do not ignore exporter error logs as harmless background noise.
- Do not assume "no traces" means "no traffic" when the pipeline may be failing.

#### Optional Anki

Q: What should happen if telemetry export is slow?
A: It should degrade safely, usually by buffering within limits or dropping telemetry, not blocking critical work.

</details>

<a id="obs-trace-012"></a>

<details>
<summary><strong>🧠 OBS-TRACE-012. What can go wrong when traces cross async boundaries, executors or reactive pipelines?</strong></summary>

#### Short answer

Trace context can be lost, spans can be parented incorrectly, or work can be measured without queue/wait time.

#### Interview answer

Async Java code often moves work across threads, callbacks or reactive operators. If context is not captured and restored, child spans become disconnected. If instrumentation starts spans only after a worker begins, traces may miss time spent waiting in a queue.

#### Deep dive

Executors, schedulers, `CompletableFuture`, Reactor and message listeners all need compatible instrumentation. Context must also be cleared to avoid leaking one request's context into another.

#### Production angle

Async trace gaps make slow requests look like they spent less time than users actually experienced.

#### Traps / caveats

- Do not assume ThreadLocal context works across async boundaries.
- Do not ignore queue time when diagnosing tail latency.

#### Optional Anki

Q: What async delay can traces miss?
A: Queue or pool wait time before the worker starts.

</details>

<a id="obs-trace-013"></a>

<details>
<summary><strong>🧠 OBS-TRACE-013. How do you avoid leaking sensitive data through trace attributes?</strong></summary>

#### Short answer

Use semantic conventions and allowlists, avoid raw payloads, redact at instrumentation boundaries, and review attributes like logs.

#### Interview answer

Trace attributes should be intentionally designed. Use route templates, result categories and dependency names. Avoid tokens, passwords, emails, full addresses, raw SQL parameters, payment data and request bodies. Central instrumentation should sanitize data before export.

#### Deep dive

Tail sampling and indexing can make sensitive attributes searchable and widely visible. Baggage is especially risky because it propagates across process boundaries.

#### Production angle

Trace leakage creates the same compliance and incident-response problems as unsafe logging.

#### Traps / caveats

- Do not put PII into baggage.
- Do not assume vendor-side redaction catches everything after export.

#### Optional Anki

Q: Why is baggage sensitive?
A: It propagates across services and can leak data widely.

</details>
