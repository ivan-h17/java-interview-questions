# Alerting, on-call and incident response

---

<a id="obs-alert-001"></a>

<details>
<summary><strong>OBS-ALERT-001. What makes an alert actionable?</strong></summary>

#### Short answer

An actionable alert indicates real impact or imminent risk, has an owner, and suggests a concrete investigation or mitigation path.

#### Interview answer

A good alert tells the on-call engineer what is affected, how severe it is, when it started, which service owns it, and where to look next. It should represent something worth waking or interrupting a person for.

#### Deep dive

Actionability depends on severity. Some issues should page immediately, some should create tickets, and some should only appear on dashboards.

#### Production angle

Actionable alerts reduce alert fatigue and improve response time for real incidents.

#### Traps / caveats

- Do not page on metrics nobody knows how to fix.
- Do not create alerts without owners and runbooks.

#### Optional Anki

Q: What are two properties of an actionable alert?
A: It has an owner and a clear response path.

</details>

<a id="obs-alert-002"></a>

<details>
<summary><strong>OBS-ALERT-002. How do you design alerts that avoid noise and alert fatigue?</strong></summary>

#### Short answer

Alert on user impact and sustained risk, use severity levels, group related alerts and regularly review noisy rules.

#### Interview answer

I prefer alerts based on SLO burn, availability, latency, critical dependency failures and saturation that requires action. Thresholds should include duration or burn-rate logic. Related alerts should be grouped so one outage does not create hundreds of pages.

#### Deep dive

Noise control includes deduplication, inhibition, maintenance windows, route ownership and distinguishing page-level alerts from ticket-level alerts.

#### Production angle

If on-call engineers learn that alerts are usually false or unactionable, they will respond slower to real incidents.

#### Traps / caveats

- Do not tune alerts only by raising thresholds until they never fire.
- Do not suppress diagnostic alerts that are useful as context; route them differently.

#### Optional Anki

Q: What is alert fatigue?
A: Reduced responsiveness caused by frequent noisy or unactionable alerts.

</details>

<a id="obs-alert-003"></a>

<details>
<summary><strong>OBS-ALERT-003. Why should alerts focus on user impact when possible?</strong></summary>

#### Short answer

User-impact alerts catch what matters even when the internal root cause is unknown.

#### Interview answer

An alert like "checkout availability is below SLO" is more important than "CPU is high" because it reflects user harm. Infrastructure and cause-based alerts are still useful for diagnosis, but user-impact alerts should drive paging priority.

#### Deep dive

User impact can be measured by failed requests, slow requests, stale data, unprocessed events or failed business outcomes depending on the service.

#### Production angle

This keeps incident response focused on restoring service, not chasing every internal anomaly.

#### Traps / caveats

- Do not ignore saturation metrics; they can predict upcoming user impact.
- Some cause alerts are page-worthy, such as disk almost full or certificate expiry.

#### Optional Anki

Q: Why is "checkout failing" a better page than "CPU high"?
A: It directly reflects user impact.

</details>

<a id="obs-alert-004"></a>

<details>
<summary><strong>OBS-ALERT-004. What should an alert description include?</strong></summary>

#### Short answer

It should include the symptom, severity, affected service, time window, likely impact, owner, links and first response steps.

#### Interview answer

An alert should state what condition fired, which service or workflow is affected, current value versus threshold, when it started, possible user impact, and where to investigate. It should link to dashboards, traces/log queries, runbooks and recent deployments.

#### Deep dive

Descriptions should be written for a tired engineer who may not know the service deeply. They should avoid vague text like "metric too high."

#### Production angle

Clear alert text reduces handoff time and prevents repeated tribal-knowledge lookups.

#### Traps / caveats

- Do not include secrets or sensitive query values in alert messages.
- Do not link only to a generic dashboard if a focused panel exists.

#### Optional Anki

Q: What should an alert compare?
A: Current value versus the threshold or SLO condition.

</details>

<a id="obs-alert-005"></a>

<details>
<summary><strong>OBS-ALERT-005. Why should alerts link to dashboards and runbooks?</strong></summary>

#### Short answer

They shorten the path from notification to diagnosis and mitigation.

#### Interview answer

A dashboard shows current scope, trend and related signals. A runbook explains first checks, likely causes, mitigation options, escalation contacts and rollback instructions. Without links, every incident starts with manual searching.

#### Deep dive

Runbooks should be tested and updated after incidents. A stale runbook can be worse than no runbook if it tells engineers to take unsafe actions.

#### Production angle

Good links reduce mean time to acknowledge, diagnose and mitigate.

#### Traps / caveats

- Do not link to dashboards that require unavailable permissions for on-call.
- Do not let runbooks become long documents with no concrete first action.

#### Optional Anki

Q: What is the purpose of a runbook link in an alert?
A: To provide immediate investigation and mitigation steps.

</details>

<a id="obs-alert-006"></a>

<details>
<summary><strong>OBS-ALERT-006. How do alert thresholds, durations and grouping affect on-call quality?</strong></summary>

#### Short answer

They control sensitivity, noise, detection speed and how many pages one incident creates.

#### Interview answer

Low thresholds and short durations detect issues quickly but can be noisy. Long durations reduce noise but may detect severe incidents too late. Grouping prevents one root issue from paging separately for every instance, endpoint or dependency.

#### Deep dive

Thresholds should reflect SLOs, historical baseline, traffic volume and business criticality. Alert grouping should preserve useful dimensions without creating duplicate pages.

#### Production angle

Good tuning helps on-call engineers trust alerts and respond with the right urgency.

#### Traps / caveats

- Do not add a long `for` duration to all alerts; severe outages need fast detection.
- Over-grouping can hide which service or region is affected.

#### Optional Anki

Q: What is a risk of too-long alert duration?
A: Slow detection of serious incidents.

</details>

<a id="obs-alert-007"></a>

<details>
<summary><strong>OBS-ALERT-007. How do you handle alert storms during a large outage?</strong></summary>

#### Short answer

Identify the primary incident, suppress duplicates where safe, communicate status and focus on mitigation.

#### Interview answer

During an alert storm, I would declare or join the incident, identify the highest-level user-impact alert, silence known duplicate alerts temporarily with clear scope and expiry, assign roles, and focus on restoring service. Diagnostic alerts should remain available in dashboards.

#### Deep dive

Alert routing should support grouping, inhibition and dependency-aware suppression before incidents happen. Manual silences need audit and expiration.

#### Production angle

Without alert-storm handling, responders waste time acknowledging symptoms instead of fixing the outage.

#### Traps / caveats

- Do not silence broad alert classes indefinitely.
- Do not suppress alerts that indicate a separate customer-impacting incident.

#### Optional Anki

Q: What should silences have during incidents?
A: Clear scope, owner and expiration.

</details>

<a id="obs-alert-008"></a>

<details>
<summary><strong>OBS-ALERT-008. How should alerts be reviewed after incidents?</strong></summary>

#### Short answer

Review whether alerts fired, fired at the right time, had useful context and mapped to the right severity.

#### Interview answer

After an incident, check detection time, false positives, missed symptoms, alert text, dashboard links, runbook usefulness, ownership and escalation path. Fix noisy alerts, add missing user-impact signals and remove alerts that no one acts on.

#### Deep dive

Alert review should be part of the postmortem action list. The goal is not more alerts by default; it is better detection and response.

#### Production angle

Alert quality improves when teams treat alerts as production code with feedback loops.

#### Traps / caveats

- Do not add a new alert for every observed metric after every incident.
- Do not ignore alerts that fired too late because "they eventually worked."

#### Optional Anki

Q: What is one post-incident alert review question?
A: Did the first page identify real user impact quickly enough?

</details>

<a id="obs-alert-009"></a>

<details>
<summary><strong>🧠 OBS-ALERT-009. How do symptom-based alerts differ from cause-based alerts?</strong></summary>

#### Short answer

Symptom-based alerts detect user-visible failure; cause-based alerts detect known internal conditions.

#### Interview answer

Symptom alerts include high checkout failure rate, API SLO burn or old unprocessed events. Cause alerts include high CPU, database disk nearly full or circuit breaker open. Symptom alerts are usually better for paging because they catch unknown causes, while cause alerts guide diagnosis or prevent known failures.

#### Deep dive

The best setup often uses symptom alerts for primary paging and cause alerts as supporting pages, tickets or dashboard context depending on severity.

#### Production angle

Symptom-based alerting reduces blind spots from root causes the team did not anticipate.

#### Traps / caveats

- Some causes are urgent even before user impact, such as disk full risk.
- A symptom alert still needs labels and dashboards to locate likely causes.

#### Optional Anki

Q: Which alert type is usually better for paging?
A: Symptom-based user-impact alerts.

</details>

<details>
<summary><strong>🧠 OBS-ALERT-010. How do you test that alerting actually works end to end?</strong></summary>

#### Short answer

Test metric emission, rule evaluation, routing, notification delivery, escalation and runbook usability.

#### Interview answer

End-to-end alert testing means proving that a real or simulated bad condition emits the right telemetry, the alert rule fires, the correct on-call receives it, links work, and the runbook leads to a safe response. This can be done with synthetic checks, staging drills or controlled production tests.

#### Deep dive

Testing should cover low traffic, maintenance windows, silences, routing changes and escalation paths. Alert rules that only exist on paper often fail during real incidents.

#### Production angle

Alerting is part of the production system; it needs verification like any other critical workflow.

#### Traps / caveats

- Do not test only the PromQL expression and ignore notification routing.
- Do not run destructive tests without clear guardrails.

#### Optional Anki

Q: What does end-to-end alert testing include besides the rule?
A: Routing, notification, escalation and runbook validation.

</details>
