# Observability fundamentals and signals

---

<a id="obs-fund-001"></a>

<details>
<summary><strong>OBS-FUND-001. What is observability, and how is it different from monitoring?</strong></summary>

#### Short answer

Monitoring tells you whether known signals are healthy; observability helps you understand unknown failure modes from the telemetry a system emits.

#### Interview answer

Monitoring is usually based on predefined dashboards and alerts: error rate, latency, CPU, memory, queue lag. Observability is broader: the system exposes enough logs, metrics, traces and context to answer new questions during incidents without redeploying just to add debug output.

#### Deep dive

A mature system needs both. Monitoring catches expected symptoms quickly, while observability supports investigation when the symptom is new, cross-service, tenant-specific or caused by an interaction nobody predicted.

#### Production angle

Good observability reduces mean time to detect and recover because engineers can move from "something is broken" to "this dependency, version, tenant or path is broken."

#### Traps / caveats

- Do not treat a dashboard as proof that the system is observable.
- Observability without ownership, retention and alerting discipline becomes expensive noise.

#### Optional Anki

Q: Monitoring vs observability?
A: Monitoring checks known signals; observability helps investigate unknown behavior from emitted telemetry.

</details>

<details>
<summary><strong>OBS-FUND-002. What are logs, metrics, traces and profiles?</strong></summary>

#### Short answer

Logs are event records, metrics are numeric time series, traces follow operations across boundaries, and profiles show where runtime resources are spent.

#### Interview answer

Logs answer "what happened?" Metrics answer "how often, how much and how bad?" Traces answer "where did this request or workflow spend time?" Profiles answer "which code paths used CPU, allocation, locks or wall time?"

#### Deep dive

These signals have different costs and strengths. Metrics are cheap to aggregate, logs carry rich context, traces connect distributed work, and profiles explain runtime hotspots that ordinary application telemetry may miss.

#### Production angle

During a latency incident, metrics identify scope, traces locate the slow operation, logs explain unusual decisions, and profiles can reveal CPU, allocation or lock contention.

#### Traps / caveats

- Logs alone rarely show distribution or blast radius.
- Traces and profiles can be sampled, so absence of evidence is not always evidence of absence.

#### Optional Anki

Q: What question does a trace answer?
A: Where time and failures occurred along one request or workflow path.

</details>

<a id="obs-fund-003"></a>

<details>
<summary><strong>OBS-FUND-003. How do logs, metrics and traces complement each other during an incident?</strong></summary>

#### Short answer

Metrics show scope and trend, traces show the execution path, and logs provide detailed context for specific events.

#### Interview answer

I usually start with metrics to see whether the issue affects one endpoint, region, tenant, version or dependency. Then I use traces to find where affected requests spend time or fail. Finally, I inspect correlated logs to understand decisions, exceptions and business identifiers.

#### Deep dive

The signals should be connected by service name, environment, version, trace ID and safe business identifiers. Without correlation, engineers waste time manually stitching evidence together.

#### Production angle

Cross-signal correlation is what turns telemetry from separate dashboards into an incident workflow.

#### Traps / caveats

- Do not jump from one error log to a global conclusion without metrics.
- Do not trust a single trace as representative without checking aggregate data.

#### Optional Anki

Q: Which signal tells you how widespread an incident is?
A: Metrics.

</details>

<details>
<summary><strong>OBS-FUND-004. What are RED metrics?</strong></summary>

#### Short answer

RED means Rate, Errors and Duration, usually used to monitor request-oriented services.

#### Interview answer

Rate is how many requests or operations are handled. Errors are failed requests or bad outcomes. Duration is latency, usually measured with percentiles like p95 and p99, not only averages.

#### Deep dive

RED works well for HTTP APIs, RPC calls, message processing and business operations that have a clear count, outcome and duration. It should be broken down by bounded labels such as route template, method, status class, dependency and service version.

#### Production angle

RED metrics are often the first service dashboard row and the basis for API SLOs.

#### Traps / caveats

- Do not use raw URLs as labels; use route templates.
- An operation can be technically successful but still fail the business outcome.

#### Optional Anki

Q: What does RED stand for?
A: Rate, Errors and Duration.

</details>

<a id="obs-fund-005"></a>

<details>
<summary><strong>OBS-FUND-005. What are USE metrics?</strong></summary>

#### Short answer

USE means Utilization, Saturation and Errors, usually used for resources.

#### Interview answer

Utilization measures how busy a resource is, such as CPU usage or active database connections. Saturation measures queued or waiting work, such as pending threads or connection acquisition wait. Errors measure failed operations on that resource.

#### Deep dive

USE is valuable for CPU, memory, disks, network, thread pools, executors, connection pools and queues. Saturation is especially important because latency can explode when a resource is near capacity.

#### Production angle

USE metrics help explain why a service is slow even when request error rate has not increased yet.

#### Traps / caveats

- High utilization is not always bad if there is no saturation or user impact.
- Low CPU does not mean the service is healthy; it may be waiting on locks, pools or dependencies.

#### Optional Anki

Q: What does saturation measure?
A: Queued or waiting work for a constrained resource.

</details>

<details>
<summary><strong>OBS-FUND-006. Why is observability a design concern, not only an operations concern?</strong></summary>

#### Short answer

Because useful telemetry depends on code-level choices: boundaries, identifiers, error classification, labels, span placement and business events.

#### Interview answer

Operations teams can run monitoring tools, but application developers decide what the service emits. If code does not expose safe business IDs, operation names, result categories, dependency timings and context propagation, production investigation becomes guesswork.

#### Deep dive

Observability should be part of API, database, messaging and resilience design. For example, retries need attempt metrics, outbox flows need lag and failure metrics, and authorization decisions may need audit events.

#### Production angle

The best time to add core telemetry is before launch, not during the first incident.

#### Traps / caveats

- Do not add telemetry only around infrastructure and ignore business outcomes.
- Do not let every team invent incompatible metric and log names.

#### Optional Anki

Q: Why is observability partly an application design problem?
A: The application owns the domain context and operation boundaries needed for useful telemetry.

</details>

<a id="obs-fund-007"></a>

<details>
<summary><strong>OBS-FUND-007. What telemetry should a new backend service expose before production?</strong></summary>

#### Short answer

Expose request metrics, dependency metrics, structured logs, distributed traces, health checks, JVM/resource metrics, deployment metadata and business outcome metrics.

#### Interview answer

Before production, a service should have RED metrics for APIs, USE metrics for pools and queues, outbound dependency latency and errors, structured logs with trace IDs, traces across HTTP and messaging, liveness/readiness checks, JVM metrics, and dashboards tied to alerts.

#### Deep dive

For async services, include queue lag, event age, processing duration, retry/DLQ counts and business completion metrics. For APIs, include route-level latency, status class, error category and request volume.

#### Production angle

Launch readiness should include "can we detect and debug failure?" not only "does the happy path work?"

#### Traps / caveats

- Do not expose only host metrics; they rarely explain business impact.
- Do not launch without clear alert ownership and runbooks for critical flows.

#### Optional Anki

Q: Name three telemetry requirements before production.
A: Request metrics, structured logs with trace IDs, and dependency metrics.

</details>

<a id="obs-fund-008"></a>

<details>
<summary><strong>🧠 OBS-FUND-008. How can observability create cost, privacy or reliability risks?</strong></summary>

#### Short answer

Telemetry can become expensive, leak sensitive data, overload pipelines or change application behavior if it is unbounded.

#### Interview answer

High-cardinality metrics, verbose logs, unsampled traces and large span attributes can create major storage and query cost. Logs and traces can leak tokens, PII or payment data. Exporters and collectors can also consume CPU, memory or network if configured without backpressure and sampling.

#### Deep dive

Telemetry is production traffic. It needs budgets, sampling, retention, redaction, access controls and failure behavior that does not take down the application.

#### Production angle

A logging spike during an outage can overload log ingestion exactly when engineers need it most.

#### Traps / caveats

- Do not put request IDs, user IDs or raw URLs into metric labels.
- Do not let telemetry export block critical request processing.

#### Optional Anki

Q: Why can high-cardinality metrics be dangerous?
A: They create too many time series, increasing cost and potentially overloading the metrics backend.

</details>
