# Backend dependencies and resource observability

---

<a id="obs-dep-001"></a>

<details>
<summary><strong>OBS-DEP-001. What metrics should be collected for outbound HTTP clients?</strong></summary>

#### Short answer

Collect request rate, latency, status, errors, timeouts, retries, connection-pool usage and circuit-breaker or fallback events.

#### Interview answer

For each downstream dependency, measure calls by operation, result, status class, exception category and duration. Track connect/read/request timeouts, retry attempts, retry success, fallback usage, open circuit breakers and connection pool wait or exhaustion.

#### Deep dive

Client-side metrics can differ from server-side metrics because the client sees DNS, TLS, pool waits, network errors and caller-side timeouts.

#### Production angle

These metrics show whether an API slowdown is local or caused by a downstream service.

#### Traps / caveats

- Do not hide retry attempts inside one successful final call.
- Do not label metrics by raw URL or full query string.

#### Optional Anki

Q: Why distinguish original calls from retry attempts?
A: Retries can hide failures and amplify downstream load.

</details>

<a id="obs-dep-002"></a>

<details>
<summary><strong>OBS-DEP-002. What metrics should be collected for database calls?</strong></summary>

#### Short answer

Measure query duration, error rate, rows affected or returned where useful, transaction duration, lock waits and pool behavior.

#### Interview answer

Application metrics should show database operation count, latency percentiles, timeouts, exceptions, transaction duration and result categories. Database-side metrics should add slow queries, locks, deadlocks, CPU, I/O, connection count and replication lag if relevant.

#### Deep dive

Use bounded operation names like repository method or query category rather than raw SQL with parameters. Traces can show representative SQL carefully, but metrics should stay low-cardinality.

#### Production angle

Database telemetry helps distinguish slow SQL, blocked transactions, connection starvation and database overload.

#### Traps / caveats

- Do not record full SQL values in metric labels.
- Query latency without pool wait time can understate user-visible latency.

#### Optional Anki

Q: Which database metric helps find blocked transactions?
A: Lock wait or blocking session metrics.

</details>

<a id="obs-dep-003"></a>

<details>
<summary><strong>OBS-DEP-003. What metrics should be collected for connection pools?</strong></summary>

#### Short answer

Collect active, idle, max, pending waiters, acquisition time, timeouts and connection creation or validation failures.

#### Interview answer

For database or HTTP pools, watch whether active connections approach max, idle connections disappear, threads wait for acquisition, acquisition latency rises, or timeouts occur. These metrics should be correlated with dependency latency and request traffic.

#### Deep dive

Pool exhaustion may mean the pool is too small, but it can also mean calls are slow, transactions are too long, responses are not closed, or concurrency is unbounded.

#### Production angle

Connection pool pressure is a common cause of high p99 latency with low CPU.

#### Traps / caveats

- Do not blindly increase pool size; the downstream may not handle it.
- Do not ignore connection leaks or long transactions.

#### Optional Anki

Q: What does connection acquisition time show?
A: Time spent waiting for a connection from the pool.

</details>

<a id="obs-dep-004"></a>

<details>
<summary><strong>OBS-DEP-004. What metrics should be collected for thread pools and executors?</strong></summary>

#### Short answer

Collect active threads, pool size, queue size, task rate, task duration, rejection count and wait time.

#### Interview answer

Executor metrics should show how much work is arriving, how many tasks are running, how many are queued, how long tasks wait before execution, how long they run and whether tasks are rejected. Separate metrics by executor name and purpose.

#### Deep dive

Queue size without enqueue wait time is incomplete. A small queue may still cause high latency if tasks are slow and users wait synchronously.

#### Production angle

Executor metrics reveal async bottlenecks, scheduler starvation and overloaded downstream isolation pools.

#### Traps / caveats

- Do not use one shared unbounded executor for unrelated work.
- Thread pool health cannot be inferred from CPU alone.

#### Optional Anki

Q: What executor metric shows backlog?
A: Queue size or queued task count.

</details>

<a id="obs-dep-005"></a>

<details>
<summary><strong>OBS-DEP-005. What metrics should be collected for Kafka producers and consumers?</strong></summary>

#### Short answer

Collect producer send latency/errors/retries and consumer lag, processing time, failures, commits, rebalances, retries and DLQ metrics.

#### Interview answer

For producers, monitor send rate, error rate, retry rate, request latency, batch behavior and buffer pressure. For consumers, monitor lag by partition, event age, processing duration, poll behavior, commit failures, rebalance count, retry backlog and DLQ growth.

#### Deep dive

Application-level success matters. A consumer can poll messages successfully while failing to update the database or publish follow-up events.

#### Production angle

Kafka telemetry should show both broker/client health and business pipeline progress.

#### Traps / caveats

- Aggregate lag can hide one stuck partition.
- Lag of zero does not prove processing side effects succeeded.

#### Optional Anki

Q: Why monitor oldest event age?
A: It reflects business delay better than raw offset lag.

</details>

<a id="obs-dep-006"></a>

<details>
<summary><strong>OBS-DEP-006. What metrics should be collected for Redis or cache usage?</strong></summary>

#### Short answer

Collect hit/miss rate, latency, errors, timeouts, evictions, memory usage, keyspace pressure and fallback behavior.

#### Interview answer

At application level, monitor cache hits, misses, load duration, load failures, stale/fallback usage and Redis command latency/errors. At Redis level, watch memory, evictions, connected clients, blocked clients, slow commands, keyspace size and replication or failover status if used.

#### Deep dive

Hit rate is not enough. A high hit rate can still hide stale data, hot keys, slow commands or incorrect authorization-sensitive caching.

#### Production angle

Cache metrics show whether caching reduces database load or introduces correctness and outage risks.

#### Traps / caveats

- Do not treat hit rate as the only cache success metric.
- Do not ignore cache-miss load on the database during cold starts.

#### Optional Anki

Q: What cache metric can be misleading by itself?
A: Hit rate.

</details>

<a id="obs-dep-007"></a>

<details>
<summary><strong>OBS-DEP-007. What metrics help detect retry storms?</strong></summary>

#### Short answer

Track retry attempts, retry rate, original request rate, downstream errors, timeouts, concurrency, queue depth and saturation.

#### Interview answer

A retry storm appears when failed or slow dependency calls cause clients to send many extra attempts. Metrics should distinguish initial attempts from retries, show retry budget consumption, backoff behavior, downstream latency, circuit breaker state and request amplification.

#### Deep dive

Retries can make an incident worse even when each client behaves according to its local policy. Coordinated clients can overload a recovering dependency.

#### Production angle

Retry metrics help decide whether to reduce retries, open a circuit breaker, shed load or degrade gracefully.

#### Traps / caveats

- Do not count only final failures; retry attempts may be the harmful load.
- Do not retry at every layer without a global budget.

#### Optional Anki

Q: What is request amplification?
A: Extra downstream load caused by retries or duplicated attempts.

</details>

<a id="obs-dep-008"></a>

<details>
<summary><strong>OBS-DEP-008. What metrics help detect queue buildup or consumer lag?</strong></summary>

#### Short answer

Use queue depth, oldest item age, enqueue/dequeue rate, processing time, error rate, retry backlog and worker saturation.

#### Interview answer

For queues and consumers, depth alone is not enough. Track how fast work arrives, how fast it completes, how old the oldest unprocessed item is, how long processing takes, how many items fail or retry, and whether workers or downstream dependencies are saturated.

#### Deep dive

Oldest item age often maps better to user impact than raw count. One old critical job may be worse than many fresh low-priority jobs.

#### Production angle

Queue buildup is an early signal of slow consumers, failing dependencies or insufficient capacity.

#### Traps / caveats

- Do not ignore DLQ or retry queues when the main queue looks healthy.
- Do not aggregate all priorities or tenants if one critical group is stuck.

#### Optional Anki

Q: Which queue metric maps well to business delay?
A: Oldest unprocessed item age.

</details>

<a id="obs-dep-009"></a>

<details>
<summary><strong>OBS-DEP-009. How do dependency metrics help distinguish internal latency from downstream latency?</strong></summary>

#### Short answer

They split total request time into local work, dependency calls, pool waits, retries and queueing.

#### Interview answer

If API latency rises, dependency metrics show whether time is spent in outbound HTTP, database queries, Redis, Kafka, connection acquisition or internal code. Comparing request latency with dependency latency and traces helps identify the critical path.

#### Deep dive

A service can appear slow because it is waiting for a downstream, or because its own pools are saturated before the downstream call starts. Both need different fixes.

#### Production angle

This distinction prevents premature scaling or code optimization when the real issue is a dependency or pool bottleneck.

#### Traps / caveats

- Do not trust downstream server metrics alone; clients see network and timeout behavior.
- Do not ignore parallel calls; total latency is often the slowest required branch, not sum of all calls.

#### Optional Anki

Q: What does dependency latency help separate?
A: Local processing time from downstream wait time.

</details>

<a id="obs-dep-010"></a>

<details>
<summary><strong>🧠 OBS-DEP-010. How can missing queue time or pool wait time make traces misleading?</strong></summary>

#### Short answer

The trace may show only execution time after work starts, hiding time spent waiting for a thread, connection or queue slot.

#### Interview answer

If a request waits 800 ms for a database connection and then runs a 20 ms query, a trace that starts the database span only after connection acquisition makes the database look fast. The user still experienced 820 ms of latency.

#### Deep dive

Instrument enqueue time, dequeue time, pool acquisition time and queue length where resource waiting matters. Otherwise tail latency investigations can point to the wrong layer.

#### Production angle

Hidden wait time is common in p99 incidents with saturated pools and low CPU.

#### Traps / caveats

- Do not assume a short dependency span means the dependency path is healthy.
- Pool wait time may need separate metrics because auto-tracing may not capture it.

#### Optional Anki

Q: What can hide before a database query span starts?
A: Connection pool acquisition wait.

</details>

<a id="obs-dep-011"></a>

<details>
<summary><strong>🧠 OBS-DEP-011. How do you instrument a dependency without creating too much metric cardinality?</strong></summary>

#### Short answer

Use bounded dependency names, operation categories and result classes instead of raw endpoints, IDs or payload-derived labels.

#### Interview answer

For an HTTP dependency, use labels like `dependency=payment-service`, `operation=authorize`, `method=POST`, `status_class=5xx`, not raw URL or customer ID. For SQL, use query category or repository operation, not full SQL text with values.

#### Deep dive

Detailed per-request context belongs in logs and traces. Metrics should support aggregation across many requests and stable dashboards.

#### Production angle

Bounded dependency labels let teams compare dependencies safely without overwhelming the metrics backend.

#### Traps / caveats

- Do not derive labels directly from user input.
- Do not remove operation labels completely; otherwise dependency metrics become too vague.

#### Optional Anki

Q: What is a safe HTTP dependency metric label?
A: A bounded operation name such as `authorize`, not the raw URL.

</details>
