# Spring Boot Actuator, Micrometer and Java service telemetry

---

<a id="obs-spring-001"></a>

<details>
<summary><strong>OBS-SPRING-001. How does Micrometer fit into Spring Boot observability?</strong></summary>

#### Short answer

Micrometer is Spring Boot's main application metrics and observation facade.

#### Interview answer

Spring Boot uses Micrometer to collect and publish metrics for HTTP requests, JVM, system resources, data sources, caches and custom application behavior. Micrometer can export to monitoring systems such as Prometheus through registries, and its observation model can connect metrics with tracing context.

#### Deep dive

Micrometer lets application code instrument behavior without hard-coding one vendor backend. The same service can expose metrics to different registries by configuration.

#### Production angle

Micrometer is usually the Java service layer between application behavior and dashboards or alerts.

#### Traps / caveats

- Micrometer does not automatically make bad labels safe.
- Custom metrics still need clear names, units and ownership.

#### Optional Anki

Q: What is Micrometer in Spring Boot?
A: A metrics and observation facade used to instrument and export telemetry.

</details>

<details>
<summary><strong>OBS-SPRING-002. What does Spring Boot Actuator provide for production services?</strong></summary>

#### Short answer

Actuator provides production management endpoints for health, metrics, info, environment, logging and diagnostics.

#### Interview answer

Actuator exposes endpoints such as health, metrics, prometheus, info, loggers, mappings, beans and conditions depending on configuration. It is commonly used for Kubernetes probes, Prometheus scraping, runtime log-level changes and operational diagnostics.

#### Deep dive

Endpoint availability, HTTP/JMX exposure and authorization are separate concerns. A feature can be available in the application but not exposed over HTTP.

#### Production angle

Actuator is powerful enough to support operations, but also sensitive enough to require deliberate exposure.

#### Traps / caveats

- Do not expose diagnostic endpoints publicly.
- Health details, env and heap dumps can leak sensitive internals.

#### Optional Anki

Q: Which Actuator endpoint commonly exposes Prometheus metrics?
A: `/actuator/prometheus`.

</details>

<details>
<summary><strong>OBS-SPRING-003. Why should Actuator endpoints be secured?</strong></summary>

#### Short answer

They can reveal internals, configuration, topology, logs or memory contents, and some can change runtime behavior.

#### Interview answer

Actuator endpoints are administrative surfaces. Public exposure of endpoints like `env`, `beans`, `mappings`, `heapdump`, `logfile` or `loggers` can leak secrets, dependency names, routes, stack details or allow runtime log changes. They should be protected with authentication, authorization and network controls.

#### Deep dive

Even read-only operational data helps attackers map the system. A separate management port is useful but not sufficient without access control.

#### Production angle

Operational endpoint exposure should be part of security review and deployment configuration.

#### Traps / caveats

- Do not assume "internal network" means safe.
- Health details can disclose service dependencies and database names.

#### Optional Anki

Q: Why is exposing `heapdump` dangerous?
A: It can contain secrets, tokens and personal data.

</details>

<a id="obs-spring-004"></a>

<details>
<summary><strong>OBS-SPRING-004. How do liveness and readiness health indicators differ?</strong></summary>

#### Short answer

Liveness says whether the process should be restarted; readiness says whether the instance should receive traffic.

#### Interview answer

In Kubernetes-style deployments, failed liveness usually causes a restart. Failed readiness removes the instance from serving traffic. A dependency outage may justify failing readiness, but often should not fail liveness because restarting the service will not fix the dependency.

#### Deep dive

Startup probes or startup states can avoid killing applications that need time to initialize. Readiness should also fail during graceful shutdown before the process exits.

#### Production angle

Correct probe design prevents traffic from hitting unready instances and avoids restart storms.

#### Traps / caveats

- Do not put every downstream dependency into liveness.
- Do not make probes slower than their timeout budget.

#### Optional Anki

Q: Which probe controls whether an instance receives traffic?
A: Readiness.

</details>

<a id="obs-spring-005"></a>

<details>
<summary><strong>OBS-SPRING-005. What should and should not be included in a readiness check?</strong></summary>

#### Short answer

Readiness should include conditions required to serve traffic, but avoid expensive, slow or broad dependency checks.

#### Interview answer

A readiness check may include initialization complete, required local state loaded, database connectivity if all requests depend on it, and graceful shutdown state. It should not run heavy SQL queries, call many downstream services, or depend on optional components that only affect some endpoints.

#### Deep dive

Readiness can be split by health groups when different traffic types need different dependencies. Checks should be bounded by timeouts and safe under frequent polling.

#### Production angle

A bad readiness check can remove all pods from service during a temporary dependency blip.

#### Traps / caveats

- Do not use readiness as a complete integration test.
- Do not let readiness checks overload the database.

#### Optional Anki

Q: What property must health checks have?
A: They should be fast, bounded and safe to call repeatedly.

</details>

<a id="obs-spring-006"></a>

<details>
<summary><strong>OBS-SPRING-006. What metrics does Spring Boot expose automatically for HTTP requests?</strong></summary>

#### Short answer

Spring Boot commonly exposes HTTP server request count, duration and tags such as method, URI pattern, status and exception.

#### Interview answer

With Actuator and Micrometer, Spring Boot can instrument server HTTP requests and publish metrics for latency and request count. Useful dimensions include route template, method, status, outcome and exception category, depending on framework and configuration.

#### Deep dive

The URI tag should represent a low-cardinality route pattern, not the raw requested path. Custom conventions or filters may be needed for unusual routing.

#### Production angle

These metrics are the basis for API dashboards, latency alerts and endpoint-level SLOs.

#### Traps / caveats

- Raw path labels can create high-cardinality time series.
- Automatic metrics do not replace business outcome metrics.

#### Optional Anki

Q: Why should HTTP metrics use URI templates?
A: To avoid high cardinality from IDs in raw paths.

</details>

<a id="obs-spring-007"></a>

<details>
<summary><strong>OBS-SPRING-007. What JVM metrics are useful for Java backend services?</strong></summary>

#### Short answer

Useful JVM metrics include heap and non-heap memory, GC, threads, classes, CPU, allocation pressure and sometimes buffer pools.

#### Interview answer

For a Java service, I watch heap used/committed/max, GC pause time and frequency, live threads, blocked threads if available, CPU usage, class loading, direct buffer memory and process memory. These should be correlated with request latency and deployment events.

#### Deep dive

JVM metrics show symptoms but not always causes. GC pressure may come from allocation-heavy code, caches, large payloads or changed traffic mix.

#### Production angle

JVM metrics help decide whether an incident is application code, memory pressure, GC, CPU, container limits or dependency waiting.

#### Traps / caveats

- Heap usage alone does not show native memory or container RSS.
- GC pause metrics need latency correlation to prove user impact.

#### Optional Anki

Q: Name two JVM metrics useful during latency incidents.
A: GC pause time and thread count/state.

</details>

<a id="obs-spring-008"></a>

<details>
<summary><strong>OBS-SPRING-008. How do you add a custom Micrometer metric?</strong></summary>

#### Short answer

Inject `MeterRegistry` and register a counter, gauge, timer or distribution metric with controlled tags.

#### Interview answer

For example, use a `Counter` for completed business events, a `Timer` for operation duration, or a `Gauge` for queue size. The metric should have a stable name, clear unit and low-cardinality tags such as operation, result or provider.

#### Deep dive

Timers should wrap the real operation boundary. Gauges need a stable object or callback source; otherwise they can disappear or report misleading values.

#### Production angle

Custom metrics are valuable when automatic HTTP/JVM metrics cannot show whether domain work is succeeding.

#### Traps / caveats

- Do not create meters dynamically per user, request or object ID.
- Do not add custom metrics without dashboards or known use cases.

#### Optional Anki

Q: Which Micrometer type measures duration?
A: `Timer`.

</details>

<a id="obs-spring-009"></a>

<details>
<summary><strong>🧠 OBS-SPRING-009. How can Actuator health checks accidentally cause outages?</strong></summary>

#### Short answer

Health checks can overload dependencies, trigger restart storms or remove all instances from traffic if they are too broad or expensive.

#### Interview answer

If every pod runs frequent database queries in health checks, the checks themselves can add load during an incident. If liveness depends on a temporary downstream outage, Kubernetes may restart all pods. If readiness fails globally on an optional dependency, traffic can be removed from healthy instances.

#### Deep dive

Health checks should be cheap, bounded, dependency-aware and separated by liveness/readiness semantics. Optional dependencies should often be exposed as details or separate indicators, not global failure.

#### Production angle

Probe misconfiguration can turn a dependency issue into a full service outage.

#### Traps / caveats

- Do not use liveness to test all dependencies.
- Do not let health-check timeouts exceed probe timeouts.

#### Optional Anki

Q: Why is dependency-based liveness risky?
A: It can restart healthy application processes for an external dependency outage.

</details>

<details>
<summary><strong>🧠 OBS-SPRING-010. How do Micrometer observations connect metrics, traces and contextual data?</strong></summary>

#### Short answer

An observation represents an operation and can produce metrics, spans and context tags from the same instrumentation point.

#### Interview answer

Micrometer Observation provides a common model around an operation such as an HTTP request or repository call. Handlers can turn the observation into metrics, tracing spans or contextual data. This helps keep operation names and tags consistent across signals.

#### Deep dive

Observation context can carry low-cardinality tags for metrics and richer contextual data for traces. Teams still need to decide what is safe and useful for each signal.

#### Production angle

Shared instrumentation reduces drift between metrics, traces and logs when debugging one operation.

#### Traps / caveats

- Do not assume every observation tag is safe for metrics.
- Auto-instrumentation may still miss custom business boundaries.

#### Optional Anki

Q: What is the value of Micrometer Observation?
A: It can instrument one operation consistently for metrics, traces and context.

</details>
