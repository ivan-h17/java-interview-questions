# Metrics and instrumentation design

<a id="obs-met-001"></a>

<details>
<summary><strong>OBS-MET-001. What is the difference between a counter, gauge, timer and histogram?</strong></summary>

#### Short answer

A counter only increases, a gauge shows a current value, a timer measures duration, and a histogram records value distributions in buckets.

#### Interview answer

Use counters for events like requests or failures. Use gauges for current state like queue size or active connections. Use timers for operation duration, usually with count and latency distribution. Use histograms when you need bucketed distributions, percentiles or SLO-style threshold analysis.

#### Deep dive

The right instrument matters because backend systems aggregate and query each type differently. A request total should not be a gauge, and a queue depth should not be a counter.

#### Production angle

Incorrect metric types create misleading dashboards and broken alerts.

#### Traps / caveats

- Gauges can go up and down; counters should not reset except on process restart.
- Percentiles require distribution data, not only total time and count.

#### Optional Anki

Q: Which metric type is appropriate for active database connections?
A: A gauge.

</details>

<details>
<summary><strong>OBS-MET-002. What is a percentile, and why do p95 and p99 matter?</strong></summary>

#### Short answer

A percentile shows the value below which a percentage of observations fall; p95 and p99 expose tail latency.

#### Interview answer

If p95 latency is 300 ms, 95% of requests completed in 300 ms or less and 5% were slower. p99 shows the slowest 1% except extreme outliers. These matter because users often experience tail latency, especially when one page or workflow makes several backend calls.

#### Deep dive

Percentiles are better than averages for latency, but they still need enough traffic and correct aggregation. Aggregating percentiles across instances incorrectly can mislead.

#### Production angle

SLOs often use percentile or threshold-based latency because averages can look fine while many users time out.

#### Traps / caveats

- Do not average p99 values from different instances.
- Low traffic can make high percentiles noisy.

#### Optional Anki

Q: What does p99 latency represent?
A: 99% of observed requests were at or below that latency.

</details>

<a id="obs-met-003"></a>

<details>
<summary><strong>OBS-MET-003. Why can averages hide production problems?</strong></summary>

#### Short answer

Averages smooth out outliers and minority failures, so severe tail latency can disappear in the mean.

#### Interview answer

If most requests take 30 ms but 1% take 10 seconds, the average may still look acceptable while real users see timeouts. Averages also hide tenant-specific, endpoint-specific and dependency-specific problems if data is aggregated too broadly.

#### Deep dive

Use percentiles, histograms, error rates and breakdown labels to see distribution and affected groups. Average latency is useful for trend context, not as the main reliability signal.

#### Production angle

Many incidents start as tail latency or partial failure before average latency looks bad.

#### Traps / caveats

- Do not alert only on average latency.
- Do not aggregate all routes together when only one critical endpoint is failing.

#### Optional Anki

Q: Which metric reveals tail latency better than average?
A: Percentiles such as p95 or p99.

</details>

<a id="obs-met-004"></a>

<details>
<summary><strong>OBS-MET-004. What tags or labels should a service metric usually include?</strong></summary>

#### Short answer

Use bounded labels that support useful aggregation, such as service, environment, version, operation, outcome and dependency.

#### Interview answer

For HTTP metrics, common labels are route template, method, status class, exception category and service version. For dependency metrics, use dependency name, operation and result. Labels should be low-cardinality and stable.

#### Deep dive

Metric labels define how engineers slice data during incidents. They should answer likely questions without exploding the number of time series.

#### Production angle

Good labels let you quickly compare old versus new versions, successful versus failed calls, and one dependency versus another.

#### Traps / caveats

- Do not use raw URL, user ID, request ID, email or UUID as labels.
- Too few labels can make metrics impossible to debug.

#### Optional Anki

Q: Why use route templates instead of raw URLs in HTTP metrics?
A: Templates keep cardinality bounded.

</details>

<a id="obs-met-005"></a>

<details>
<summary><strong>OBS-MET-005. Why can high-cardinality metrics become expensive or harmful?</strong></summary>

#### Short answer

High-cardinality labels create many time series, increasing storage, memory, query cost and backend load.

#### Interview answer

Every unique combination of metric name and label values creates a separate series. If a service labels latency by user ID or request ID, it can create millions of series. This can slow dashboards, break alerts and overload the metrics backend.

#### Deep dive

Cardinality is multiplicative. A few labels with many values can be worse than many labels with small controlled value sets.

#### Production angle

A single bad label in a high-volume service can become a monitoring incident.

#### Traps / caveats

- Low traffic does not make unbounded label design safe long term.
- Traces and logs are better places for request-level identifiers.

#### Optional Anki

Q: What creates a time series in labeled metrics?
A: A metric name plus one unique combination of label values.

</details>

<a id="obs-met-006"></a>

<details>
<summary><strong>OBS-MET-006. What is the difference between business metrics and technical metrics?</strong></summary>

#### Short answer

Technical metrics describe system behavior; business metrics describe domain outcomes.

#### Interview answer

Technical metrics include latency, error rate, CPU, heap, pool usage and queue depth. Business metrics include orders created, payments authorized, invoices sent, failed validations or duplicate events skipped. Senior engineers connect both because a technically healthy service can still fail the business process.

#### Deep dive

Business metrics should be carefully named, owned and reviewed with product or domain owners. They are not just dashboard decoration; they often define correctness and user impact.

#### Production angle

An event consumer can have zero errors but still process zero successful payments due to a business rule regression.

#### Traps / caveats

- Do not label business metrics with unbounded object IDs.
- Do not use technical availability as the only proxy for business success.

#### Optional Anki

Q: Give one example of a business metric.
A: Successful payment authorizations per minute.

</details>

<a id="obs-met-007"></a>

<details>
<summary><strong>OBS-MET-007. How do you instrument a custom business operation safely?</strong></summary>

#### Short answer

Measure count, duration and outcome with stable names, bounded labels and clear ownership.

#### Interview answer

For a business operation like payment capture, I would record attempts, successes, failures by category, duration and maybe amount bucket if useful. Labels should be bounded, such as provider, operation and result, not payment ID or user ID.

#### Deep dive

Instrumentation should sit near the operation boundary, not scattered across low-level helper methods. Define what counts as success, failure, retry and ignored duplicate.

#### Production angle

Good custom metrics show whether the system is doing the business work it exists to do.

#### Traps / caveats

- Do not increment success before the transaction or side effect really committed.
- Do not add a metric without documenting what it means.

#### Optional Anki

Q: What labels are safe for a payment metric?
A: Bounded labels like provider and result category, not payment ID.

</details>

<a id="obs-met-008"></a>

<details>
<summary><strong>OBS-MET-008. Why do metric naming, units and label consistency matter?</strong></summary>

#### Short answer

Consistent naming and units make metrics understandable, comparable and safe to query across services.

#### Interview answer

A metric name should say what is measured, and its unit should be obvious or encoded by convention. Labels should have consistent meanings across services, for example `result=success|error` or `exception=TimeoutException`. Inconsistent metrics make dashboards and alerts fragile.

#### Deep dive

Teams should standardize names for common operations such as HTTP server requests, outbound dependencies, job processing and queues. Changing a metric name is a production contract change for dashboards and alerts.

#### Production angle

During incidents, inconsistent labels force engineers to relearn each service instead of comparing them quickly.

#### Traps / caveats

- Do not mix seconds and milliseconds under the same metric name.
- Do not reuse one label key with different meanings in different services.

#### Optional Anki

Q: Why are metric units important?
A: Wrong or unclear units make dashboards and alerts misleading.

</details>

<a id="obs-met-009"></a>

<details>
<summary><strong>🧠 OBS-MET-009. What are histogram buckets, and how do they affect latency analysis?</strong></summary>

#### Short answer

Histogram buckets count observations below configured thresholds, and bucket choice controls what latency questions you can answer accurately.

#### Interview answer

A latency histogram might have buckets such as 50 ms, 100 ms, 250 ms, 500 ms and 1 second. If buckets are too coarse or do not match SLO thresholds, percentile estimates and "requests under target" queries can be inaccurate or useless.

#### Deep dive

Buckets should reflect expected latency ranges and important SLO boundaries. More buckets improve detail but increase time series count, especially with labels.

#### Production angle

If the SLO is "95% under 300 ms" but no useful bucket exists near 300 ms, alerting and diagnosis become weaker.

#### Traps / caveats

- Do not enable many buckets with many labels without estimating cardinality.
- Histogram percentiles are estimates, not exact raw measurements.

#### Optional Anki

Q: Why should histogram buckets align with SLOs?
A: They make threshold and percentile analysis meaningful around the target.

</details>

<details>
<summary><strong>🧠 OBS-MET-010. How do you prevent user IDs, request IDs or raw URLs from becoming metric labels?</strong></summary>

#### Short answer

Enforce metric review, use route templates and bounded classifications, and deny or normalize unsafe labels at instrumentation boundaries.

#### Interview answer

For HTTP metrics, label `/orders/{id}` rather than `/orders/123`. For user-specific or request-specific values, put them in logs or traces, not metrics. Libraries should expose safe APIs and common interceptors should normalize paths and outcome labels.

#### Deep dive

Some teams add metric filters or registry customizers that reject labels matching UUIDs, emails or high-cardinality patterns. Code review and dashboards should also watch series growth.

#### Production angle

Cardinality guardrails prevent one accidental deployment from overwhelming the metrics system.

#### Traps / caveats

- Do not rely only on developer discipline for high-volume shared instrumentation.
- Do not remove all labels; preserve bounded dimensions needed for diagnosis.

#### Optional Anki

Q: Where should request IDs go?
A: Logs and traces, not metric labels.

</details>
