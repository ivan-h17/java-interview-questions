<a id="obs-dash-001"></a>

<details>
<summary><strong>OBS-DASH-001. What should a useful service dashboard show?</strong></summary>

#### Short answer

It should show user impact, request health, dependency health, resource saturation, recent changes and ownership context.

#### Interview answer

A good service dashboard starts with traffic, latency, errors and availability. It also shows dependency latency/errors, JVM and resource saturation, queue or pool pressure, deployment version, active incidents or recent releases, and links to logs, traces and runbooks.

#### Deep dive

Dashboards should be organized by investigation flow, not by every metric that exists. The first screen should answer whether users are affected and where to look next.

#### Production angle

During incidents, dashboards reduce time spent guessing which system or version changed.

#### Traps / caveats

- Do not build dashboards full of metrics no one can interpret.
- Do not hide critical user-impact signals below infrastructure details.

#### Optional Anki

Q: What should a service dashboard show first?
A: User-impact signals such as traffic, errors and latency.

</details>

<details>
<summary><strong>OBS-DASH-002. What should an API latency and error-rate dashboard include?</strong></summary>

#### Short answer

Include request rate, latency percentiles, error rates, status classes, endpoints, versions and dependency correlation.

#### Interview answer

For latency, show p50, p95, p99 and timeout rates by route template and version. For errors, show 5xx, important 4xx, exception categories and failed business outcomes. Correlate the API view with downstream calls and recent deployments.

#### Deep dive

Use route templates rather than raw URLs. Separate client-caused errors from server failures where possible, but do not ignore 4xx spikes after API or frontend changes.

#### Production angle

This dashboard should show whether a regression affects one endpoint, one version, or the whole service.

#### Traps / caveats

- Do not rely on averages for latency.
- Do not aggregate all endpoints if only checkout or payment matters.

#### Optional Anki

Q: Which latency series should usually appear besides average?
A: p95 and p99.

</details>

<details>
<summary><strong>OBS-DASH-003. What should a dependency dashboard include?</strong></summary>

#### Short answer

Show call rate, latency, errors, timeouts, retries, circuit-breaker state and saturation per dependency.

#### Interview answer

For each downstream HTTP service, database, Redis, Kafka or third-party API, a dependency dashboard should show volume, success/failure rate, latency percentiles, timeout count, retry attempts, fallback usage, queue or pool wait, and recent version changes.

#### Deep dive

Client-side and server-side views may disagree. The caller sees timeouts, network errors and pool waits that the downstream may never record.

#### Production angle

Dependency dashboards reveal whether your service is slow internally or mostly waiting on something else.

#### Traps / caveats

- Do not hide retries inside a single "success" metric.
- Do not label dependencies with raw URLs or hostnames that change frequently unless bounded.

#### Optional Anki

Q: Why show retries on dependency dashboards?
A: Retries can hide failures and amplify load.

</details>

<a id="obs-dash-004"></a>

<details>
<summary><strong>OBS-DASH-004. What should a database or connection-pool dashboard include?</strong></summary>

#### Short answer

Include query latency, errors, pool active/idle/max/pending, acquisition time, transactions and database-side saturation.

#### Interview answer

For Java services, Hikari-style pool metrics are critical: active connections, idle connections, max size, pending threads and acquisition timeouts. Add query duration, transaction duration, database error categories, slow query count, lock waits and database CPU/I/O where available.

#### Deep dive

Connection pool saturation can be caused by slow queries, long transactions, leaked connections, too much concurrency or database overload. Pool metrics alone do not identify which one.

#### Production angle

Pool wait time often explains high API latency when database query time looks normal.

#### Traps / caveats

- Do not increase pool size before understanding database capacity.
- Do not ignore transaction duration and lock waits.

#### Optional Anki

Q: What pool metric reveals callers waiting for a connection?
A: Pending threads or connection acquisition time.

</details>

<a id="obs-dash-005"></a>

<details>
<summary><strong>OBS-DASH-005. How should dashboards show deployment versions or recent releases?</strong></summary>

#### Short answer

Dashboards should annotate deployments and allow metrics to be filtered or grouped by service version.

#### Interview answer

A useful dashboard shows deployment markers, current version per instance, rollout progress and comparisons between old and new versions. Metrics should include a bounded version label or equivalent metadata where it helps identify regressions.

#### Deep dive

Deployment context is often the fastest path to root cause. It should cover application version, config changes, feature flags and infrastructure changes where possible.

#### Production angle

When error rate rises after rollout, version-aware dashboards show whether only new pods are failing.

#### Traps / caveats

- Do not let build SHA labels create unnecessary long-term cardinality if retention is high.
- Do not forget config and feature-flag changes; not all regressions are code deploys.

#### Optional Anki

Q: Why annotate deployments on dashboards?
A: To correlate telemetry changes with releases.

</details>

<details>
<summary><strong>OBS-DASH-006. What is Prometheus commonly used for?</strong></summary>

#### Short answer

Prometheus is commonly used to scrape, store, query and alert on time-series metrics.

#### Interview answer

Prometheus pulls metrics from targets, stores them as labeled time series, and provides PromQL for querying. In Java services, it often scrapes Micrometer metrics exposed through Spring Boot Actuator.

#### Deep dive

Prometheus works well for numeric operational metrics and alerting. It is not a log store or a distributed tracing backend.

#### Production angle

Prometheus is frequently the source for service dashboards and alert rules around latency, errors and saturation.

#### Traps / caveats

- Do not expose Prometheus scrape endpoints publicly without controls.
- Bad labels can overload Prometheus with too many time series.

#### Optional Anki

Q: Is Prometheus primarily for logs?
A: No, it is primarily for time-series metrics.

</details>

<a id="obs-dash-007"></a>

<details>
<summary><strong>OBS-DASH-007. What is Grafana commonly used for?</strong></summary>

#### Short answer

Grafana is commonly used to build dashboards and visualizations from metrics and other data sources.

#### Interview answer

Grafana connects to systems such as Prometheus, Loki, Tempo, Elasticsearch or databases and visualizes data as panels, dashboards and alerts depending on setup. It is often the operator-facing view for service health.

#### Deep dive

Grafana is a visualization and alerting layer; data quality still depends on the underlying metrics, logs or traces.

#### Production angle

Grafana dashboards can encode incident workflows, with links from high-level symptoms to detailed service and dependency views.

#### Traps / caveats

- A beautiful dashboard can still be misleading if queries are wrong.
- Do not make dashboards editable by everyone without review in critical environments.

#### Optional Anki

Q: What is Grafana's common role?
A: Visualizing and exploring telemetry from data sources.

</details>

<details>
<summary><strong>OBS-DASH-008. What PromQL mistakes commonly lead to misleading graphs?</strong></summary>

#### Short answer

Common mistakes include wrong rate windows, averaging percentiles, missing label grouping, using counters as gauges and ignoring resets.

#### Interview answer

For counters, use `rate()` or `increase()` over an appropriate window instead of plotting raw values. Group by the right labels, such as route or status, and avoid aggregating away the dimension that identifies the problem. Be careful with `histogram_quantile()` and bucket aggregation.

#### Deep dive

PromQL queries should match the metric type. Counter resets, scrape gaps, low traffic and inconsistent labels can all distort results.

#### Production angle

Bad queries can make an outage look healthy or make a normal deployment look broken.

#### Traps / caveats

- Do not average already-computed p95 or p99 series across instances.
- Do not use too short a rate window for low-volume services.

#### Optional Anki

Q: What function is commonly used to graph counter rates?
A: `rate()`.

</details>

<details>
<summary><strong>🧠 OBS-DASH-009. When are Prometheus recording rules useful?</strong></summary>

#### Short answer

Recording rules precompute frequently used or expensive PromQL expressions into new time series.

#### Interview answer

Use recording rules for common SLO calculations, expensive aggregations, normalized service-level metrics and alert expressions that should be fast and consistent. They turn complex queries into named series that dashboards and alerts can reuse.

#### Deep dive

Recording rules also encode definitions. For example, "good requests" and "bad requests" for an SLO should be computed consistently rather than rewritten differently in every dashboard.

#### Production angle

Precomputed rules make alerts more reliable and dashboards faster during incidents.

#### Traps / caveats

- Wrong recording rules centralize wrong math.
- Recording too many high-cardinality derived series increases storage cost.

#### Optional Anki

Q: Why use recording rules for SLOs?
A: To make common SLO calculations fast and consistent.

</details>
