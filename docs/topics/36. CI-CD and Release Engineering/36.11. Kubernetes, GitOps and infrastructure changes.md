# Kubernetes, GitOps and infrastructure changes

---

<a id="cicd-k8s-001"></a>

<details>
<summary><strong>CICD-K8S-001. How does CI/CD change when deploying to Kubernetes?</strong></summary>

#### Short answer

The pipeline deploys container images and Kubernetes manifests, and release safety depends on probes, rollout status, resources and cluster policies.

#### Interview answer

For Kubernetes, CI builds and scans an image, publishes it, updates manifests or Helm values, applies or syncs them, and watches rollout status. The app must expose correct readiness and liveness checks, use sensible resource requests, handle termination and externalize config.

#### Deep dive

Kubernetes makes rolling deployment common, but the application still needs mixed-version compatibility and graceful shutdown.

#### Production angle

Kubernetes deployment failures often come from image pull errors, bad probes, insufficient resources, missing secrets or runtime misconfiguration.

#### Traps / caveats

- A created Deployment object does not mean rollout succeeded.
- Bad resource limits can create `OOMKilled` loops after release.

#### Optional Anki

Q: What must CI/CD watch in Kubernetes deployments?
A: Image identity, manifests, rollout status, probes, resources and runtime config.

</details>

<a id="cicd-k8s-002"></a>

<details>
<summary><strong>CICD-K8S-002. What is GitOps, and how is it different from a pipeline directly applying changes to a cluster?</strong></summary>

#### Short answer

GitOps uses Git as the desired state and a controller reconciles the cluster; direct apply pushes changes from the pipeline.

#### Interview answer

In GitOps, deployment configuration is committed to a repository, reviewed, and synchronized by a cluster-side controller such as Argo CD or Flux. In direct deployment, the CI pipeline runs commands like `kubectl apply` or Helm against the cluster.

#### Deep dive

GitOps improves auditability and drift detection, but adds reconciliation behavior that teams must understand during rollback and emergency changes.

#### Production angle

If someone manually changes the cluster, GitOps may revert it unless the desired state in Git changes.

#### Traps / caveats

- GitOps does not remove the need for safe migrations and rollout checks.
- Auto-sync can amplify a bad committed manifest quickly.

#### Optional Anki

Q: What is the core idea of GitOps?
A: Git stores desired state, and a controller reconciles the environment to it.

</details>

<details>
<summary><strong>🧠 CICD-K8S-003. What belongs in application source repositories versus deployment configuration repositories?</strong></summary>

#### Short answer

Application code and build logic belong with the app; environment manifests and deployment state often belong in deployment repos.

#### Interview answer

The app repo should contain source code, tests, Dockerfile, build configuration and maybe base manifests. Deployment repos often contain environment-specific Kubernetes manifests, Helm values, Kustomize overlays, image versions and promotion history.

#### Deep dive

There is no universal rule. A small team may keep everything together, while a platform organization may separate app and environment ownership.

#### Production angle

The split should preserve traceability from code commit to deployed image and manifest.

#### Traps / caveats

- Do not hide environment-specific behavior in undocumented pipeline variables.
- Do not store plaintext secrets in deployment repos.

#### Optional Anki

Q: What should deployment repositories contain?
A: Reviewed environment deployment state such as manifests, overlays, values and image versions.

</details>

<a id="cicd-k8s-004"></a>

<details>
<summary><strong>CICD-K8S-004. How do liveness, readiness and startup probes affect release safety?</strong></summary>

#### Short answer

Startup probes protect slow startup, readiness controls traffic, and liveness restarts truly stuck containers.

#### Interview answer

Startup probes give slow Java apps time to initialize. Readiness probes decide whether a pod should receive traffic. Liveness probes restart containers that are stuck and cannot recover themselves.

#### Deep dive

Probe design should reflect service behavior. A liveness probe that depends on a flaky database can restart all pods during a dependency incident.

#### Production angle

Correct probes are central to rolling updates and zero-downtime deployment.

#### Traps / caveats

- Do not use the same deep dependency check for liveness and readiness blindly.
- Too aggressive probes can cause restart loops.

#### Optional Anki

Q: Which probe controls traffic routing?
A: Readiness probe.

</details>

<a id="cicd-k8s-005"></a>

<details>
<summary><strong>CICD-K8S-005. How should Kubernetes resource requests and limits be validated before deployment?</strong></summary>

#### Short answer

Validate them against JVM sizing, load tests, historical metrics and cluster policy.

#### Interview answer

For Java services, memory requests and limits must match heap, metaspace, direct memory, thread stacks and native overhead. CPU settings affect latency and GC behavior. CI can run policy checks, while staging and production metrics confirm real usage.

#### Deep dive

Container memory limit below actual JVM needs causes `OOMKilled`; too low CPU can increase GC pauses and response latency.

#### Production angle

Bad resource settings can make a release fail even when code is correct.

#### Traps / caveats

- `-Xmx` is not the only memory Java uses.
- Removing limits entirely may violate platform fairness and cost controls.

#### Optional Anki

Q: What Java memory uses count besides heap?
A: Metaspace, direct buffers, thread stacks, code cache and native overhead.

</details>

<a id="cicd-k8s-006"></a>

<details>
<summary><strong>🧠 CICD-K8S-006. How should infrastructure-as-code changes be reviewed and deployed together with application changes?</strong></summary>

#### Short answer

Review them as part of one release plan, with ordering, rollback and compatibility made explicit.

#### Interview answer

IaC changes that affect networking, IAM, databases, queues, secrets or resource limits can break an application release. They should have plans, diffs, policy checks, approval, staged rollout and clear dependency order relative to app deployment.

#### Deep dive

Some infrastructure changes are backward-compatible and can be applied first. Others require app changes, feature flags or migration windows.

#### Production angle

Many release incidents are caused by infrastructure or permission changes deployed near application changes.

#### Traps / caveats

- Terraform or Helm plans can hide risky runtime effects if reviewers lack context.
- Rolling back infrastructure can be harder than rolling back code.

#### Optional Anki

Q: What must be explicit when app and IaC changes ship together?
A: Ordering, compatibility, rollback and ownership.

</details>

<details>
<summary><strong>🧠 CICD-K8S-007. What can go wrong when GitOps auto-sync, database migrations and rollback interact?</strong></summary>

#### Short answer

Auto-sync may revert manifests while database state remains migrated, creating version and schema mismatch.

#### Interview answer

If GitOps rolls the app back automatically after a failed sync, the old app may run against a new or partial schema. If migrations run as app startup, repeated reconciliation can retry migrations unexpectedly.

#### Deep dive

Safe design separates migration steps, records migration state, disables unsafe auto-rollback for stateful changes or uses expand-and-contract compatibility.

#### Production angle

The cluster can look reconciled while the database is in a state no running app version expects.

#### Traps / caveats

- Git revert is not database rollback.
- Auto-sync should be understood before enabling it for stateful releases.

#### Optional Anki

Q: Why can GitOps rollback be unsafe with migrations?
A: Git reverts manifests, but database state may remain changed.

</details>
