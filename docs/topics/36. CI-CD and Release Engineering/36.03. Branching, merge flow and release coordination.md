# Branching, merge flow and release coordination

---

<a id="cicd-flow-001"></a>

<details>
<summary><strong>CICD-FLOW-001. How do trunk-based development, GitFlow and release branches affect CI/CD?</strong></summary>

#### Short answer

Trunk-based development favors frequent integration and fast CI/CD; GitFlow and release branches add coordination but can slow integration.

#### Interview answer

Trunk-based development keeps changes small and merged to main frequently, which fits continuous integration. GitFlow uses long-lived feature, develop and release branches, which can work for scheduled releases but increases merge and integration risk. Release branches are useful for stabilization or patch streams but should not become a dumping ground for unmerged work.

#### Deep dive

Branching strategy shapes pipeline design. More branches mean more rules about which branch can publish artifacts, deploy to environments and receive hotfixes.

#### Production angle

For backend services, branch strategy affects how quickly security fixes, hotfixes, migrations and contract changes can move to production.

#### Traps / caveats

- Long-lived branches often hide integration problems until late.
- Trunk-based development still needs feature flags or small slicing for unfinished work.

#### Optional Anki

Q: Which branching style best supports CI?
A: Trunk-based development, because it encourages frequent integration.

</details>

<details>
<summary><strong>CICD-FLOW-002. Why is long-lived branching risky for continuous integration?</strong></summary>

#### Short answer

Long-lived branches delay integration, so conflicts and behavior mismatches appear late.

#### Interview answer

CI assumes changes are integrated frequently. When branches live for weeks, tests pass in isolation but fail when combined with other work. Dependency upgrades, database migrations, API changes and generated code can diverge.

#### Deep dive

The risk is not only Git conflicts. The bigger issue is semantic conflict: two changes are individually correct but incompatible together.

#### Production angle

Late integration creates release crunches, emergency fixes and larger deployment batches.

#### Traps / caveats

- Rebasing frequently reduces but does not eliminate hidden behavior conflicts.
- Feature flags are usually better than hiding large unfinished work on a branch.

#### Optional Anki

Q: Why are long-lived branches bad for CI?
A: They delay integration and make conflicts appear late.

</details>

<details>
<summary><strong>CICD-FLOW-003. How should pull request checks, code review and CI work together?</strong></summary>

#### Short answer

CI validates repeatable checks, while code review focuses on design, correctness and maintainability that automation cannot fully judge.

#### Interview answer

Pull requests should run automated checks before merge, and reviewers should look at behavior, risk, API compatibility, tests, observability and operational impact. CI should remove routine questions from review, such as formatting, compilation and test status.

#### Deep dive

For risky changes, review should include deployment plan, migration safety, feature flags, rollback and monitoring. The reviewer should know whether CI has verified the relevant boundaries.

#### Production angle

Good review plus CI catches both mechanical failures and production design risks.

#### Traps / caveats

- Review approval should not override failing required checks without explicit policy.
- Green CI does not prove the design is safe.

#### Optional Anki

Q: How do CI and code review complement each other?
A: CI automates repeatable validation; review evaluates design and risk.

</details>

<details>
<summary><strong>CICD-FLOW-004. How do you handle a hotfix when the main branch has unreleased changes?</strong></summary>

#### Short answer

Patch from the currently released version, deploy the fix, then merge or cherry-pick it back to main.

#### Interview answer

If main contains unreleased work, create the hotfix from the production tag or release branch. Build and deploy a new patch artifact through the same pipeline, then bring the fix back to main so it is not lost in future releases.

#### Deep dive

The important part is preserving traceability. The hotfix should have its own commit, artifact, tests, approval and deployment record.

#### Production angle

This avoids accidentally releasing unrelated unfinished changes while fixing a production incident.

#### Traps / caveats

- Do not patch production manually outside version control.
- Do not forget to merge the hotfix back to main.

#### Optional Anki

Q: Where should a hotfix branch start if main is unreleased?
A: From the production tag or release branch.

</details>

<details>
<summary><strong>CICD-FLOW-005. What is a release branch, and when is it useful?</strong></summary>

#### Short answer

A release branch is a branch used to stabilize or patch a specific release line.

#### Interview answer

Release branches are useful when production needs patches while main continues moving, or when a product has scheduled release windows. They allow controlled fixes without pulling in unrelated main-branch changes.

#### Deep dive

They should be short-lived or clearly owned. Long-lived release branches require regular merging, security patch strategy and support policy.

#### Production angle

Release branches help with hotfixes, customer-specific supported versions and regulated release windows.

#### Traps / caveats

- Release branches can hide drift from main.
- Too many active release branches increase maintenance and security burden.

#### Optional Anki

Q: What is a release branch for?
A: Stabilizing or patching a specific release line.

</details>

<details>
<summary><strong>🧠 CICD-FLOW-006. How do you coordinate releases across multiple services without creating a distributed big-bang release?</strong></summary>

#### Short answer

Use backward-compatible contracts, independent deployments, feature flags and staged rollout order.

#### Interview answer

I would avoid requiring all services to deploy at the same minute. Instead, make APIs and events backward compatible, deploy providers before consumers when adding fields or endpoints, use feature flags for behavior changes, and monitor each step.

#### Deep dive

For event-driven systems, schema evolution, consumer lag and old message formats matter. For REST, versioning, optional fields and tolerant readers matter.

#### Production angle

This lets teams release services independently while reducing cross-service outage risk.

#### Traps / caveats

- Shared database changes can reintroduce big-bang coupling.
- A flag in one service may not protect consumers from contract breaks.

#### Optional Anki

Q: How do you avoid big-bang microservice releases?
A: Design backward-compatible contracts and roll out services independently with flags and monitoring.

</details>

<details>
<summary><strong>🧠 CICD-FLOW-007. What are the trade-offs between independent service releases and synchronized platform releases?</strong></summary>

#### Short answer

Independent releases reduce coordination and batch size; synchronized releases can simplify compatibility but increase waiting and blast radius.

#### Interview answer

Independent service releases fit microservices because teams can ship fixes and features without waiting for everyone else. Synchronized releases may be useful for tightly coupled platform changes, shared protocol upgrades or regulated release windows, but they create large batches and complex coordination.

#### Deep dive

The best answer is often mixed: services deploy independently by default, with explicit coordination only for cross-cutting changes that truly require it.

#### Production angle

Independent release maturity requires contract testing, observability, ownership and rollback discipline.

#### Traps / caveats

- Independent deployment is unsafe if services are actually tightly coupled.
- Synchronized releases can mask architectural coupling instead of fixing it.

#### Optional Anki

Q: What is the main benefit of independent service releases?
A: Smaller batches and less cross-team coordination.

</details>
