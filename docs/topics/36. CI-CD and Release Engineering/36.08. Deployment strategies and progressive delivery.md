# Deployment strategies and progressive delivery

---

<a id="cicd-dep-001"></a>

<details>
<summary><strong>CICD-DEP-001. What is the difference between rolling, blue-green and canary deployment?</strong></summary>

#### Short answer

Rolling gradually replaces instances, blue-green switches traffic between two environments, and canary exposes a new version to a small subset first.

#### Interview answer

Rolling deployment updates replicas in batches. Blue-green keeps old and new environments side by side and switches traffic when the new one is ready. Canary deployment sends a small percentage of traffic to the new version, observes it, then increases exposure.

#### Deep dive

Each strategy has different requirements for capacity, routing, state compatibility, observability and rollback.

#### Production angle

For Java services, the strategy must account for startup time, readiness, caches, sessions, database schema and downstream calls.

#### Traps / caveats

- Deployment strategy does not fix incompatible database changes.
- Canary without good metrics is mostly symbolic.

#### Optional Anki

Q: What is a canary deployment?
A: Gradual exposure of a new version to a small subset of traffic before wider rollout.

</details>

<a id="cicd-dep-002"></a>

<details>
<summary><strong>CICD-DEP-002. When would you choose rolling deployment for a Java backend service?</strong></summary>

#### Short answer

Use rolling deployment for stateless or backward-compatible services where old and new versions can run together.

#### Interview answer

Rolling deployment is a good default for many Spring Boot APIs because it avoids full downtime and does not require duplicate full environments. It works when readiness checks are correct, startup is predictable and shared state remains compatible.

#### Deep dive

The application must tolerate mixed versions during the rollout. This affects API contracts, database schema, caches and message formats.

#### Production angle

Rolling deployments are common in Kubernetes, but bad probes or slow startup can cause partial outages.

#### Traps / caveats

- Do not use rolling deployment for incompatible schema changes.
- Graceful shutdown and request draining matter.

#### Optional Anki

Q: What must be true for rolling deployment?
A: Old and new versions must run safely at the same time.

</details>

<a id="cicd-dep-003"></a>

<details>
<summary><strong>CICD-DEP-003. When is blue-green deployment a good fit, and what does it cost?</strong></summary>

#### Short answer

Blue-green fits when you need fast traffic switch and rollback, but it costs extra capacity and coordination.

#### Interview answer

Blue-green is useful for high-risk releases, platform upgrades or services where you want to verify a full new environment before switching traffic. It requires duplicate infrastructure, routing control and careful handling of shared state.

#### Deep dive

The hard part is not only running two app versions. Databases, queues, caches, sessions and background jobs may still be shared.

#### Production angle

Blue-green can reduce downtime, but it does not make irreversible data changes safe by itself.

#### Traps / caveats

- Duplicate workers can process jobs twice if not controlled.
- Switching traffic back may not undo database or external side effects.

#### Optional Anki

Q: Main cost of blue-green deployment?
A: Extra capacity and careful shared-state coordination.

</details>

<a id="cicd-dep-004"></a>

<details>
<summary><strong>CICD-DEP-004. When is canary deployment better than blue-green deployment?</strong></summary>

#### Short answer

Canary is better when risk should be measured gradually under real traffic before full rollout.

#### Interview answer

Canary deployment helps when failures may appear only under production traffic, tenant mix, data shape or downstream behavior. Instead of switching all users at once, the team exposes a small percentage and watches error rate, latency, saturation and business signals.

#### Deep dive

Canary needs routing, version labels, metrics by version and clear rollback criteria. Without those, it is just a slow rollout.

#### Production angle

Canary is useful for Java APIs with performance-sensitive changes, dependency upgrades or behavior changes that could affect only some users.

#### Traps / caveats

- A small canary may not catch rare code paths.
- Sticky sessions or uneven traffic can bias results.

#### Optional Anki

Q: Why use canary deployment?
A: To limit exposure while measuring real production behavior.

</details>

<a id="cicd-dep-005"></a>

<details>
<summary><strong>CICD-DEP-005. How do feature flags reduce release risk?</strong></summary>

#### Short answer

They decouple deploying code from exposing behavior.

#### Interview answer

Feature flags let teams deploy code disabled, enable it for selected users or tenants, and turn it off quickly if problems appear. They are useful for gradual rollout, kill switches and separating technical deployment from business release.

#### Deep dive

Flags should be evaluated consistently and wrapped behind a local abstraction, not scattered as vendor calls through business code.

#### Production angle

A flag can stop a bad feature faster than rebuilding and rolling back the whole service.

#### Traps / caveats

- Flags create extra code paths that must be tested.
- Flags around irreversible side effects require idempotency and stable decisions.

#### Optional Anki

Q: What do feature flags decouple?
A: Code deployment from behavior release.

</details>

<a id="cicd-dep-006"></a>

<details>
<summary><strong>CICD-DEP-006. What is progressive delivery?</strong></summary>

#### Short answer

Progressive delivery gradually exposes changes using automation, metrics and controls such as canaries and feature flags.

#### Interview answer

Progressive delivery extends CI/CD with controlled exposure. A change may move from internal users to 1%, 5%, 25% and then 100%, with automated checks deciding whether to continue or stop.

#### Deep dive

It combines deployment strategy, release flags, observability, SLOs and rollback automation.

#### Production angle

Progressive delivery reduces blast radius for risky backend changes while preserving delivery speed.

#### Traps / caveats

- It requires trustworthy metrics and version attribution.
- It does not replace compatibility design for data and contracts.

#### Optional Anki

Q: What is progressive delivery?
A: Gradual, monitored exposure of changes using automated release controls.

</details>

<a id="cicd-dep-007"></a>

<details>
<summary><strong>CICD-DEP-007. How do readiness checks affect a zero-downtime deployment?</strong></summary>

#### Short answer

Readiness checks tell the platform when a replica can safely receive traffic.

#### Interview answer

During deployment, new pods should not receive traffic until the app has started, loaded required config, connected to critical dependencies and is ready to serve. Old pods should fail readiness before shutdown so traffic drains.

#### Deep dive

Readiness is different from liveness. Liveness restarts a broken process; readiness controls traffic routing.

#### Production angle

Bad readiness checks can send traffic to half-started Java apps or remove healthy pods during temporary dependency issues.

#### Traps / caveats

- Do not make readiness depend on every optional downstream service.
- A shallow health endpoint can be green while core workflows are broken.

#### Optional Anki

Q: What does readiness control?
A: Whether a replica should receive traffic.

</details>

<a id="cicd-dep-008"></a>

<details>
<summary><strong>CICD-DEP-008. What must be true for two application versions to run at the same time safely?</strong></summary>

#### Short answer

They must be compatible in APIs, data schema, messages, config, caches and side effects.

#### Interview answer

Mixed-version safety means old and new versions can both read and write expected data, process messages, handle requests and use shared infrastructure. This usually requires backward-compatible schema changes, tolerant readers and careful feature-flag rollout.

#### Deep dive

The most dangerous areas are database columns, enum values, serialized payloads, cache keys, scheduled jobs and idempotency.

#### Production angle

Rolling, canary and blue-green deployments all rely on some form of mixed-version compatibility.

#### Traps / caveats

- Adding a non-null database column without a default can break old writers.
- New event fields should not break old consumers.

#### Optional Anki

Q: What is mixed-version compatibility?
A: The ability for old and new app versions to run together safely.

</details>

<a id="cicd-dep-009"></a>

<details>
<summary><strong>🧠 CICD-DEP-009. What is automated canary analysis?</strong></summary>

#### Short answer

Automated canary analysis compares canary behavior against baseline metrics and decides whether to continue, pause or roll back.

#### Interview answer

Instead of relying only on a human watching dashboards, automated analysis checks error rate, latency, saturation, traffic, logs and business metrics for the canary version. If metrics exceed thresholds, rollout stops automatically.

#### Deep dive

Good analysis needs version labels, stable baseline, enough traffic, meaningful metrics and well-chosen thresholds.

#### Production angle

It reduces reaction time for bad releases, especially outside normal working hours.

#### Traps / caveats

- Bad thresholds create false positives or false confidence.
- Low-traffic services may not produce enough signal for automation.

#### Optional Anki

Q: What does automated canary analysis compare?
A: Canary metrics against baseline or control metrics.

</details>

<details>
<summary><strong>🧠 CICD-DEP-010. How do sticky sessions, caches and long-running requests complicate deployment strategy?</strong></summary>

#### Short answer

They keep users or state tied to old instances, making traffic shifting and rollback less clean.

#### Interview answer

Sticky sessions can prevent even traffic distribution during canaries. Caches can hold old data formats or stale values across versions. Long-running requests may be killed during shutdown unless the service drains traffic and respects termination deadlines.

#### Deep dive

The safer design is stateless services, external session storage where needed, versioned cache keys, graceful shutdown and idempotent retries.

#### Production angle

These issues can create user-visible errors even when deployment status says the rollout succeeded.

#### Traps / caveats

- Cache invalidation may be needed during rollback.
- Background workers need graceful stop logic too, not just HTTP servers.

#### Optional Anki

Q: Why do sticky sessions hurt canary deployments?
A: They can skew traffic and keep users tied to a version.

</details>
