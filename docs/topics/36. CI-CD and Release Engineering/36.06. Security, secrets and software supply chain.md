# Security, secrets and software supply chain

---

<a id="cicd-sec-001"></a>

<details>
<summary><strong>CICD-SEC-001. What security checks should a Java backend CI pipeline include?</strong></summary>

#### Short answer

Include dependency scanning, secret scanning, static analysis, container scanning, license checks and deployment policy checks.

#### Interview answer

For Java backends, CI should scan Maven or Gradle dependencies for known vulnerabilities, detect committed secrets, run SAST for common code risks, scan container images, check IaC or Kubernetes manifests where relevant, and enforce rules for artifact signing, provenance and permissions.

#### Deep dive

Security checks should be tuned by severity, exploitability and exposure. A vulnerable library used only in tests is different from a vulnerable runtime dependency on an internet-facing service.

#### Production angle

Security gates help prevent known vulnerable dependencies, leaked credentials and unsafe deployment manifests from reaching production.

#### Traps / caveats

- Scanners produce false positives and require triage.
- Build plugins and CI actions are also supply-chain dependencies.

#### Optional Anki

Q: Name common security checks in Java CI.
A: Dependency, secret, SAST, container, license and deployment policy checks.

</details>

<details>
<summary><strong>CICD-SEC-002. How do SAST, dependency scanning, container scanning and secret scanning differ?</strong></summary>

#### Short answer

They inspect different risk surfaces: source code, libraries, images and exposed credentials.

#### Interview answer

SAST analyzes source code for risky patterns. Dependency scanning checks third-party packages for known vulnerabilities. Container scanning checks OS packages, runtime files and image layers. Secret scanning looks for tokens, keys and credentials in source, logs or artifacts.

#### Deep dive

These tools complement each other. A clean SAST result does not mean dependencies are safe, and a clean dependency scan does not mean secrets were not leaked.

#### Production angle

Different incidents require different evidence: vulnerable JARs, unsafe code paths, compromised base images or exposed secrets.

#### Traps / caveats

- A CVE finding still needs exploitability assessment.
- Secret redaction is not guaranteed once a secret has leaked.

#### Optional Anki

Q: What does dependency scanning inspect?
A: Third-party package versions and known vulnerabilities.

</details>

<details>
<summary><strong>CICD-SEC-003. How should CI/CD handle secrets without exposing them in logs or artifacts?</strong></summary>

#### Short answer

Use scoped secret stores, short-lived credentials, masking, least privilege and strict separation between trusted and untrusted jobs.

#### Interview answer

Secrets should be injected only into jobs that need them, never committed or baked into images. CI should avoid printing commands or environment dumps containing secrets, mask derived values where possible, and rotate credentials immediately if exposed.

#### Deep dive

Deployment credentials should usually come from OIDC or workload identity rather than long-lived shared tokens. PR jobs from forks should not receive production secrets.

#### Production angle

CI logs and artifacts often have wider access than production systems, so a leaked secret can become a production incident.

#### Traps / caveats

- Masking can fail when secrets are transformed or embedded in structured data.
- Secrets passed as command-line arguments may appear in process listings.

#### Optional Anki

Q: Should untrusted PR jobs receive deployment secrets?
A: No, they should run without privileged secrets.

</details>

<a id="cicd-sec-004"></a>

<details>
<summary><strong>CICD-SEC-004. Why are short-lived credentials safer than long-lived deployment secrets?</strong></summary>

#### Short answer

Short-lived credentials reduce the useful lifetime and blast radius of a leak.

#### Interview answer

Long-lived deployment tokens can be copied, logged and reused long after a pipeline run. Short-lived credentials are issued for a specific job, identity, audience and time window, so compromise is harder to exploit later.

#### Deep dive

Modern CI often uses OIDC federation to exchange the workflow identity for cloud credentials. This avoids storing static cloud keys in the CI system.

#### Production angle

If a short-lived token leaks, the response may still include investigation, but the attacker has a smaller window.

#### Traps / caveats

- Short-lived credentials still need least privilege.
- Misconfigured trust policies can allow the wrong workflow to mint credentials.

#### Optional Anki

Q: Why prefer short-lived deployment credentials?
A: They reduce leak lifetime and limit reuse.

</details>

<a id="cicd-sec-005"></a>

<details>
<summary><strong>CICD-SEC-005. What is the risk of running untrusted pull request code in privileged CI jobs?</strong></summary>

#### Short answer

Untrusted code can steal secrets, modify artifacts, poison caches or access internal networks.

#### Interview answer

Pull request code can change build scripts, tests or dependency definitions. If that code runs in a job with deployment credentials, repository write tokens or access to private services, an attacker can exfiltrate secrets or tamper with the release path.

#### Deep dive

This is especially dangerous for public repositories and self-hosted runners, but private repositories are not automatically safe if many users can open PRs.

#### Production angle

A compromised CI job can become a production compromise if it can publish artifacts or deploy.

#### Traps / caveats

- Do not assume tests are harmless; tests are executable code.
- Cache restore/save from untrusted branches can become a poisoning vector.

#### Optional Anki

Q: Why are privileged CI jobs dangerous for untrusted PRs?
A: PR code can run arbitrary commands and steal or misuse privileges.

</details>

<a id="cicd-sec-006"></a>

<details>
<summary><strong>CICD-SEC-006. How should permissions differ between build jobs, test jobs and deploy jobs?</strong></summary>

#### Short answer

Each job should receive only the permissions and secrets required for its purpose.

#### Interview answer

Build and test jobs usually need read access to source and dependencies. Publishing jobs need write access to artifact registries. Deploy jobs need narrowly scoped environment permissions. Production deployment credentials should not be available to unit tests or untrusted PR checks.

#### Deep dive

Separate identities make audit clearer and reduce blast radius. A test failure should not have the same credentials as a production deploy.

#### Production angle

Least privilege limits damage from compromised dependencies, malicious PRs or mistaken scripts.

#### Traps / caveats

- Default CI tokens may be broader than expected.
- Shared secrets across environments make staging compromise more dangerous.

#### Optional Anki

Q: What permission principle applies to CI jobs?
A: Least privilege per job and environment.

</details>

<a id="cicd-sec-007"></a>

<details>
<summary><strong>CICD-SEC-007. What is an SBOM, and how can it help during vulnerability response?</strong></summary>

#### Short answer

An SBOM is a software bill of materials: an inventory of components included in an artifact.

#### Interview answer

For a Java service, an SBOM lists application dependencies, transitive libraries and sometimes container OS packages. During vulnerability response, it helps answer which services contain a vulnerable component and which artifact versions need patching.

#### Deep dive

SBOMs are most useful when tied to exact artifact versions or image digests and stored with release metadata.

#### Production angle

When a major library CVE appears, SBOMs speed up impact analysis across services.

#### Traps / caveats

- An SBOM does not prove a vulnerability is exploitable.
- An SBOM can be incomplete if build plugins, generated artifacts or base images are not included.

#### Optional Anki

Q: What is an SBOM?
A: An inventory of software components in an artifact.

</details>

<a id="cicd-sec-008"></a>

<details>
<summary><strong>CICD-SEC-008. Why should release artifacts or container images be signed?</strong></summary>

#### Short answer

Signing lets consumers verify that an artifact came from a trusted identity and was not modified.

#### Interview answer

Artifact signing adds integrity and authenticity to the release process. A deployment platform can reject unsigned or wrongly signed images, reducing the chance of running tampered or unofficial artifacts.

#### Deep dive

Signing should be paired with policy enforcement. A signature that nobody verifies is mostly audit decoration.

#### Production angle

Signed artifacts are valuable when multiple teams, registries or clusters consume the same release outputs.

#### Traps / caveats

- Signing does not make vulnerable code safe.
- Signing keys or signing identities must be protected carefully.

#### Optional Anki

Q: What does artifact signing provide?
A: Integrity and authenticity for release artifacts.

</details>

<a id="cicd-sec-009"></a>

<details>
<summary><strong>🧠 CICD-SEC-009. How do artifact attestations and provenance reduce software supply chain risk?</strong></summary>

#### Short answer

They provide verifiable evidence about how an artifact was built and by which trusted process.

#### Interview answer

An attestation can state that a specific workflow built a specific artifact from a specific commit with specific inputs. Provenance helps deployment systems and auditors verify that the artifact followed the approved build path.

#### Deep dive

This reduces risks such as tampered artifacts, manual registry pushes, unreviewed source, compromised build parameters and unknown builders.

#### Production angle

For critical services, deployment policy can require valid provenance before production rollout.

#### Traps / caveats

- Attestations must be verified against policy.
- If the CI platform itself is compromised, trust assumptions need review.

#### Optional Anki

Q: What do attestations add beyond an SBOM?
A: Evidence about the build process, source and builder identity.

</details>

<a id="cicd-sec-010"></a>

<details>
<summary><strong>🧠 CICD-SEC-010. How can a compromised CI runner become a production security incident?</strong></summary>

#### Short answer

A compromised runner can steal secrets, tamper with artifacts or deploy malicious code.

#### Interview answer

CI runners execute build scripts, tests and third-party actions. If compromised, they may access tokens, cloud credentials, source code, private dependencies, signing keys, caches and registries. If they can publish or deploy, the attacker can reach production.

#### Deep dive

Self-hosted runners are especially sensitive because they may persist state, share machines, or have private network access. Ephemeral isolated runners reduce but do not eliminate risk.

#### Production angle

Runner compromise should trigger credential rotation, artifact trust review, cache invalidation and audit of releases produced during the exposure window.

#### Traps / caveats

- A green pipeline can still produce a malicious artifact if the runner is compromised.
- Shared runners can spread compromise across repositories.

#### Optional Anki

Q: Why is CI runner compromise serious?
A: The runner may access secrets, artifacts, registries and deployment credentials.

</details>

<details>
<summary><strong>CICD-SEC-011. How should third-party CI actions, reusable workflows and build plugins be pinned and reviewed?</strong></summary>

#### Short answer

Treat them as code dependencies: pin versions, review maintainers, restrict allowed sources and monitor vulnerabilities.

#### Interview answer

Third-party GitHub Actions, reusable workflows, Maven plugins and Gradle plugins run code in the build path. Pin them to immutable references where practical, avoid untrusted sources, review permissions, update deliberately and track advisories.

#### Deep dive

For high-risk pipelines, use organization-approved workflows, internal mirrors, dependency verification, checksums or SHA pinning. Reusable workflows should have clear inputs, secrets boundaries and change review.

#### Production angle

A compromised action or plugin can steal secrets or alter release artifacts even if application code is clean.

#### Traps / caveats

- Pinning to a tag is weaker than pinning to an immutable commit or verified release.
- Build plugins are part of the supply chain, not just tooling.

#### Optional Anki

Q: Why review third-party CI actions and build plugins?
A: They execute code inside the build and can affect secrets or artifacts.

</details>
