# Pipeline performance, scalability and runner operations

---

<a id="cicd-run-001"></a>

<details>
<summary><strong>CICD-RUN-001. What makes a CI pipeline too slow, and how do you improve it?</strong></summary>

#### Short answer

Pipelines become slow from too much serial work, inefficient tests, cold dependency downloads, poor caching and unnecessary full builds.

#### Interview answer

I would measure where time is spent, then split fast and slow checks, run independent jobs in parallel, cache dependencies carefully, build only affected modules where safe, optimize slow tests and avoid rebuilding artifacts unnecessarily.

#### Deep dive

For Java, common bottlenecks include full Spring context tests, integration tests with shared environments, code generation, container builds, dependency resolution and static analysis.

#### Production angle

Slow CI increases batch size and encourages bypassing checks, which makes releases riskier.

#### Traps / caveats

- Do not optimize by deleting important risk checks.
- Bad caching can make builds fast but incorrect.

#### Optional Anki

Q: First step in speeding up CI?
A: Measure stage and job duration to find the real bottleneck.

</details>

<details>
<summary><strong>🧠 CICD-RUN-002. How can test parallelization reduce feedback time?</strong></summary>

#### Short answer

It splits independent tests across workers so total wall-clock time decreases.

#### Interview answer

Unit tests, module tests and some integration tests can run in parallel if they do not share mutable state. CI can split tests by module, package, historical duration or test type.

#### Deep dive

Parallelization exposes hidden test coupling: shared databases, static state, fixed ports, time assumptions and order dependence.

#### Production angle

Faster test feedback helps developers keep changes small and integrated.

#### Traps / caveats

- Parallel tests must isolate data and external resources.
- More workers can increase infrastructure cost and dependency load.

#### Optional Anki

Q: What risk does test parallelization expose?
A: Hidden shared state and order-dependent tests.

</details>

<details>
<summary><strong>CICD-RUN-003. What are the risks of build caching in CI?</strong></summary>

#### Short answer

Caching can return stale, poisoned or incorrect outputs if inputs and trust boundaries are not controlled.

#### Interview answer

Dependency caches and build caches speed up Java builds, but they can hide broken dependency resolution, reuse outputs with undeclared inputs, or allow untrusted branches to poison cache content. Cache keys and permissions matter.

#### Deep dive

Gradle build cache correctness depends on tasks declaring inputs and outputs properly. Maven dependency caches should not hide missing or mutable artifacts.

#### Production angle

A wrong cached artifact can make CI green while the actual clean build would fail or produce different code.

#### Traps / caveats

- Do not share writeable caches between trusted and untrusted jobs.
- Periodic clean builds catch cache-dependent assumptions.

#### Optional Anki

Q: Main CI cache risk?
A: Reusing stale, poisoned or incorrectly keyed outputs.

</details>

<details>
<summary><strong>CICD-RUN-004. When should a team use self-hosted runners instead of managed runners?</strong></summary>

#### Short answer

Use self-hosted runners when managed runners cannot meet network, performance, cost, hardware or compliance needs.

#### Interview answer

Self-hosted runners are useful for private network access, specialized hardware, large builds, custom tooling or regulatory constraints. They require serious security hardening, isolation, patching, cleanup and access control.

#### Deep dive

For untrusted code, ephemeral clean runners are much safer than reused machines. Public repositories should be especially careful with self-hosted runners.

#### Production angle

A compromised self-hosted runner may expose internal networks, secrets and deployment credentials.

#### Traps / caveats

- Do not run untrusted PR code on privileged self-hosted runners.
- Reused runners can leak state between jobs.

#### Optional Anki

Q: Why are self-hosted runners risky?
A: They may persist compromise and expose internal resources or secrets.

</details>

<details>
<summary><strong>🧠 CICD-RUN-005. How do you isolate CI jobs to avoid cross-build contamination?</strong></summary>

#### Short answer

Use clean ephemeral environments, scoped workspaces, controlled caches and per-job credentials.

#### Interview answer

Each job should start from a clean state or a trusted image, receive only required credentials, write to an isolated workspace and use cache keys that cannot be poisoned by unrelated jobs. Temporary files and containers should be cleaned up.

#### Deep dive

Contamination can come from leftover files, local Maven repositories, Gradle caches, Docker layers, environment variables, ports, databases or background processes.

#### Production angle

Isolation prevents one build from affecting another and reduces the impact of malicious or broken scripts.

#### Traps / caveats

- Shared runners require strict cleanup.
- Secret values can leak through logs, process lists or leftover files.

#### Optional Anki

Q: How do you prevent cross-build contamination?
A: Ephemeral jobs, isolated workspaces, scoped caches and per-job credentials.

</details>

<details>
<summary><strong>🧠 CICD-RUN-006. How would you scale CI/CD for a monorepo with many Java services?</strong></summary>

#### Short answer

Use affected-change detection, shared build conventions, parallelism, caching, ownership and selective release pipelines.

#### Interview answer

In a Java monorepo, I would map changes to affected modules and services, run common validation once, run service-specific tests only where needed, parallelize independent jobs and publish only changed artifacts. Shared pipeline templates and dependency policies keep behavior consistent.

#### Deep dive

Affected-build logic must be conservative around shared libraries, parent POMs, Gradle convention plugins, generated code and deployment manifests.

#### Production angle

The goal is fast feedback without missing integration breakages from shared code.

#### Traps / caveats

- Incorrect affected-change detection can skip required tests.
- A monorepo needs strong ownership boundaries, not just tooling.

#### Optional Anki

Q: Main risk of selective monorepo CI?
A: Skipping tests for code that was actually affected.

</details>
