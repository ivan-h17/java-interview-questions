# Observability, verification and automated release analysis

---

<a id="cicd-obs-001"></a>

<details>
<summary><strong>CICD-OBS-001. What are smoke tests and post-deploy checks?</strong></summary>

#### Short answer

Smoke tests are small checks that verify a deployed service is basically working; post-deploy checks verify health after rollout.

#### Interview answer

For a backend service, smoke tests may call health endpoints, check critical API paths, verify database connectivity, confirm message consumer startup and validate key configuration. Post-deploy checks also inspect metrics, logs, traces and deployment status.

#### Deep dive

Smoke tests should be fast and safe. They are not full regression suites.

#### Production angle

They catch issues such as wrong config, failed startup, broken routing or missing secrets immediately after deployment.

#### Traps / caveats

- A health endpoint alone is not enough for critical workflows.
- Smoke tests must avoid destructive production actions.

#### Optional Anki

Q: What is a smoke test?
A: A small check that verifies a deployed service is basically usable.

</details>

<details>
<summary><strong>CICD-OBS-002. What metrics should be watched during and after a deployment?</strong></summary>

#### Short answer

Watch errors, latency, traffic, saturation, restarts, dependency failures and business signals by version.

#### Interview answer

Key metrics include request rate, 4xx and 5xx rates, latency percentiles, CPU, memory, GC, thread pools, database pool usage, queue lag, Kafka consumer lag, pod restarts, failed jobs and important domain metrics.

#### Deep dive

Metrics should be broken down by service version, route, dependency, tenant or region where useful.

#### Production angle

Deployment automation can use these metrics to pause or roll back a canary.

#### Traps / caveats

- Average latency hides tail latency.
- Aggregate metrics can hide version-specific failures.

#### Optional Anki

Q: What should deployment metrics be labeled with?
A: At least service, version, environment and sometimes route or tenant.

</details>

<details>
<summary><strong>CICD-OBS-003. How should logs, metrics and traces identify the deployed version?</strong></summary>

#### Short answer

They should include stable deployment metadata such as service name, version, commit SHA, image digest and environment.

#### Interview answer

Every log, metric and trace should be attributable to a service instance and version. This can be done through structured log fields, Micrometer tags, OpenTelemetry resource attributes, Kubernetes labels and Actuator info endpoints.

#### Deep dive

Version attribution lets the team compare old and new versions during canary or rolling deployment.

#### Production angle

Without version labels, diagnosing a bad release becomes guesswork.

#### Traps / caveats

- Avoid high-cardinality labels such as raw user IDs.
- Do not put secrets or sensitive config in telemetry.

#### Optional Anki

Q: Why tag telemetry with deployed version?
A: To correlate behavior and incidents with specific releases.

</details>

<details>
<summary><strong>CICD-OBS-004. How should a failed deployment be detected automatically?</strong></summary>

#### Short answer

Combine deployment controller status, health checks, smoke tests and release metrics with explicit failure thresholds.

#### Interview answer

Automation should watch rollout status, readiness, pod restarts, image pull errors, startup failures, smoke test results, error rate, latency and dependency failures. If thresholds are crossed, the pipeline should stop rollout and alert owners.

#### Deep dive

Kubernetes can report progress deadline failures, but higher-level release tooling usually decides what action to take.

#### Production angle

Fast automatic detection reduces exposure time for bad releases.

#### Traps / caveats

- Green rollout status does not prove business correctness.
- Thresholds must account for traffic volume and normal variance.

#### Optional Anki

Q: What should automatic deployment detection combine?
A: Rollout status, health, smoke tests and production metrics.

</details>

<details>
<summary><strong>🧠 CICD-OBS-005. What should a release dashboard show for a backend service?</strong></summary>

#### Short answer

It should show what is deployed, rollout progress, health, user impact and recent changes.

#### Interview answer

A useful dashboard includes current version, previous version, commit range, image digest, rollout status, pod health, error rate, latency, traffic, saturation, dependency health, queue lag, canary comparison, config or flag changes and links to logs and traces.

#### Deep dive

The dashboard should answer whether the release is healthy and what changed without requiring several manual searches.

#### Production angle

During an incident, the release dashboard becomes the starting point for triage.

#### Traps / caveats

- Do not expose secrets or sensitive config values.
- Dashboard success should not be based only on infrastructure health.

#### Optional Anki

Q: What should a release dashboard answer?
A: What changed, what is deployed and whether users are affected.

</details>

<details>
<summary><strong>CICD-OBS-006. How do SLOs and error budgets influence release decisions?</strong></summary>

#### Short answer

They define how much reliability risk the service can afford before slowing or stopping releases.

#### Interview answer

If a service is burning its error budget, the team may pause risky releases and focus on reliability. If the service is healthy, the team can accept normal release risk. SLOs also define which metrics matter during canary analysis.

#### Deep dive

Error budgets turn release debates from opinion into risk management: how much failure can users tolerate over the measurement window?

#### Production angle

Release automation can use SLO burn rate to stop rollout when user impact becomes unacceptable.

#### Traps / caveats

- SLOs must reflect user experience, not only server uptime.
- Error budgets should not be used to ignore preventable failures.

#### Optional Anki

Q: How do error budgets affect releases?
A: They show how much reliability risk remains before slowing or stopping change.

</details>

<a id="cicd-obs-007"></a>

<details>
<summary><strong>CICD-OBS-007. How do you verify a background worker or Kafka consumer deployment when there is no user-facing HTTP endpoint?</strong></summary>

#### Short answer

Verify startup, subscription, lag, processing success, error rates and side effects.

#### Interview answer

For a worker or Kafka consumer, I would check that the new version starts, joins the consumer group, receives partitions, keeps lag stable or decreasing, processes messages successfully, handles retries and emits expected metrics. A synthetic test message can help if it is safe.

#### Deep dive

Workers need versioned telemetry just like APIs. For scheduled jobs, verify scheduling ownership so duplicate instances do not run unexpectedly.

#### Production angle

HTTP health can be green while a consumer is stuck, paused, not subscribed or failing every message.

#### Traps / caveats

- A consumer can be alive but not making progress.
- Test messages must not create unsafe business side effects.

#### Optional Anki

Q: What proves a Kafka consumer release is healthy?
A: It joins correctly, processes messages, keeps lag under control and has low failure rate.

</details>

<details>
<summary><strong>🧠 CICD-OBS-008. How do you avoid false confidence from green health checks during a broken release?</strong></summary>

#### Short answer

Use health checks as one signal, and also verify critical workflows, metrics, dependencies and business outcomes.

#### Interview answer

A health endpoint may only prove the process is running. To avoid false confidence, combine readiness, smoke tests, versioned error and latency metrics, logs, traces, queue progress, dependency checks and domain metrics.

#### Deep dive

Health checks should be designed carefully: readiness can include critical dependencies, but liveness should avoid restarting healthy processes because a dependency is temporarily unavailable.

#### Production angle

Many broken releases return green health while failing authorization, serialization, database writes or downstream calls.

#### Traps / caveats

- Do not make health checks so deep that they cause cascading restarts.
- Do not treat "pod ready" as "release successful".

#### Optional Anki

Q: Why are green health checks not enough?
A: They may prove the process is alive, not that critical workflows work.

</details>
