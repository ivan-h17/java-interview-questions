<a id="cicd-test-001"></a>

<details>
<summary><strong>CICD-TEST-001. Which tests should run in CI for a Spring Boot backend service?</strong></summary>

#### Short answer

Run unit tests, focused Spring tests, integration tests for external boundaries, contract tests and smoke checks around deployment.

#### Interview answer

For Spring Boot, CI should usually run fast unit tests, controller or repository slice tests where useful, integration tests with Testcontainers or test doubles, API or messaging contract tests, migration checks and smoke tests after deployment. The exact mix depends on service risk and pipeline cost.

#### Deep dive

The goal is to cover business logic, serialization, persistence, transactions, HTTP or Kafka contracts, configuration and startup behavior without making every PR painfully slow.

#### Production angle

Many backend incidents come from boundaries: database schema, serialization, security config, missing properties, dependency behavior and downstream contracts.

#### Traps / caveats

- A Spring context test alone is not a complete test strategy.
- Too many slow full-context tests can make developers avoid running CI.

#### Optional Anki

Q: What test types belong in Spring Boot CI?
A: Unit, focused Spring, integration, contract, migration and smoke tests.

</details>

<details>
<summary><strong>CICD-TEST-002. How do unit, integration, contract, end-to-end and smoke tests fit into a pipeline?</strong></summary>

#### Short answer

They form layers of confidence, from fast local logic checks to slower production-readiness checks.

#### Interview answer

Unit tests run early and validate isolated logic. Integration tests validate real boundaries like databases, queues or framework wiring. Contract tests validate compatibility between services. End-to-end tests cover critical workflows but should be limited. Smoke tests verify a deployed artifact is alive and usable.

#### Deep dive

The pipeline should place faster, more deterministic tests earlier and slower, broader tests later. Not every workflow needs full end-to-end coverage.

#### Production angle

Layered tests catch different failure modes: code bugs, wiring bugs, contract breaks and deployment failures.

#### Traps / caveats

- End-to-end tests are expensive and often flaky if overused.
- Contract tests do not prove full business correctness.

#### Optional Anki

Q: What are smoke tests for?
A: Verifying that a deployed service is basically alive and usable.

</details>

<details>
<summary><strong>CICD-TEST-003. Why should slow tests be separated from fast feedback checks?</strong></summary>

#### Short answer

Slow tests delay developer feedback and make CI less useful if they block every small change.

#### Interview answer

Fast tests should run on every PR so developers learn quickly whether they broke basic behavior. Slow integration, end-to-end, load or security checks may run after merge, nightly, or only for affected areas, while still blocking release when they reveal real risk.

#### Deep dive

Separation does not mean deletion. It means choosing the right stage and trigger for each test type.

#### Production angle

If CI takes too long, teams batch changes, skip checks or merge blindly, which increases release risk.

#### Traps / caveats

- A slow test that catches critical production failures still needs a reliable place in the pipeline.
- Slow tests should be optimized, not permanently ignored.

#### Optional Anki

Q: Why separate slow tests?
A: To keep PR feedback fast while preserving deeper release validation later.

</details>

<details>
<summary><strong>CICD-TEST-004. How should flaky tests be handled in CI?</strong></summary>

#### Short answer

Treat flaky tests as defects: quarantine carefully, investigate root cause and fix or remove them.

#### Interview answer

A flaky test should not be accepted as normal. The team should record the failure, identify whether it is test code, timing, data, environment or product behavior, and fix it. Temporary quarantine is acceptable only with owner, deadline and tracking.

#### Deep dive

Common causes are sleeps, shared state, order dependence, real external services, time zones, random ports, async timing and non-isolated databases.

#### Production angle

Flaky tests destroy trust in CI. Teams start rerunning jobs until green, which hides real failures.

#### Traps / caveats

- Automatic retries can reduce noise but also hide real nondeterminism.
- Deleting flaky tests without replacing coverage can create blind spots.

#### Optional Anki

Q: What is the right attitude toward flaky tests?
A: Treat them as defects with ownership and a fix plan.

</details>

<details>
<summary><strong>🧠 CICD-TEST-005. When should test coverage block a merge, and when can it mislead?</strong></summary>

#### Short answer

Coverage can block when it prevents obvious regression in important code, but it can mislead when treated as proof of quality.

#### Interview answer

Coverage thresholds are useful as guardrails, especially to prevent large untested changes. But high line coverage does not prove correct assertions, realistic inputs, concurrency safety, transaction behavior or contract compatibility.

#### Deep dive

A good policy focuses on meaningful tests for changed code and critical paths, not only global percentage targets.

#### Production angle

Production bugs often happen in integration boundaries, configuration, data shape and timing, not just uncovered lines.

#### Traps / caveats

- Teams can game coverage with weak assertions.
- Strict global thresholds can block refactoring without improving risk.

#### Optional Anki

Q: Why can coverage mislead?
A: It measures executed lines, not necessarily useful assertions or production risk.

</details>

<details>
<summary><strong>CICD-TEST-006. How do consumer-driven contract tests reduce deployment risk between services?</strong></summary>

#### Short answer

They verify that a provider still satisfies the contracts its consumers rely on.

#### Interview answer

In consumer-driven contract testing, consumers define expected requests, responses or messages. The provider verifies those contracts in CI before release, so incompatible API or event changes are caught before deployment.

#### Deep dive

This is useful for REST, JSON payloads, Kafka events and generated clients. It supports independent deployment because compatibility is tested explicitly.

#### Production angle

Contract tests reduce incidents where one service deploys safely by itself but breaks another service at runtime.

#### Traps / caveats

- Contracts must be kept current and owned.
- They do not replace provider-side business tests.

#### Optional Anki

Q: What problem do consumer-driven contract tests solve?
A: They catch provider changes that would break existing consumers.

</details>

<details>
<summary><strong>CICD-TEST-007. What should a pre-production environment verify before production deployment?</strong></summary>

#### Short answer

It should verify artifact startup, runtime config, dependencies, migrations, core workflows and observability.

#### Interview answer

Pre-production should run the same artifact with production-like configuration shape, secrets injection mechanism, database migration path, network routes, health checks and critical integrations. It should also verify logs, metrics, traces and dashboards.

#### Deep dive

Perfect parity is unrealistic, but the environment should validate the assumptions most likely to break production.

#### Production angle

A release that works locally but fails in production often missed environment validation: missing secret, wrong profile, blocked egress, bad certificate or incompatible schema.

#### Traps / caveats

- Staging that uses fake infrastructure may miss real deployment failures.
- Staging must not reuse production secrets or sensitive data carelessly.

#### Optional Anki

Q: What should pre-production verify?
A: Startup, config, dependencies, migrations, critical workflows and telemetry.

</details>

<details>
<summary><strong>🧠 CICD-TEST-008. How should test data be managed in CI and staging?</strong></summary>

#### Short answer

Use isolated, repeatable, minimal data with clear reset, masking and ownership rules.

#### Interview answer

CI should create deterministic test data per run, often through migrations, fixtures, builders or containers. Staging data should be representative enough for release confidence, but sensitive production data must be masked, minimized and controlled.

#### Deep dive

Tests should not depend on shared mutable rows unless the environment is explicitly managed. For integration tests, each run should clean up or use isolated schemas, containers or transactions.

#### Production angle

Bad test data practices create flaky tests, false confidence, privacy leaks and staging failures that do not reproduce.

#### Traps / caveats

- Copying production data into staging can violate privacy and compliance rules.
- Overly synthetic data can miss real cardinality, nullability and encoding problems.

#### Optional Anki

Q: What are good CI test data properties?
A: Isolated, deterministic, minimal and easy to reset.

</details>

<details>
<summary><strong>🧠 CICD-TEST-009. How do you design quality gates that reduce risk without making delivery painfully slow?</strong></summary>

#### Short answer

Make gates risk-based, automated, fast where possible and clear about ownership and remediation.

#### Interview answer

I would require fast correctness and security gates on PRs, run heavier integration and deployment gates after merge, and use progressive delivery metrics for production exposure. Gates should block only when the risk justifies it and should tell developers how to fix failures.

#### Deep dive

Use different policies for changed code, critical services, dependency upgrades, database migrations and low-risk documentation changes.

#### Production angle

Good gates increase confidence without encouraging teams to bypass the pipeline.

#### Traps / caveats

- Noisy gates become ignored gates.
- Manual approval without evidence is weak risk control.

#### Optional Anki

Q: What makes a quality gate effective?
A: Clear risk basis, automation, low noise, ownership and useful remediation.

</details>
