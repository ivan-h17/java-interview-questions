# Java backend release scenarios

---

<a id="cicd-scen-001"></a>

<details>
<summary><strong>CICD-SCEN-001. A Spring Boot service passes CI but fails on startup in production. What do you check first?</strong></summary>

#### Short answer

Check logs, configuration, secrets, active profile, dependencies, migrations and resource limits.

#### Interview answer

I would start with startup logs and events, then compare the deployed artifact, active profiles, required properties, secrets, database connectivity, migrations, certificates, environment variables and Kubernetes events. If it is containerized, also check image pull, command, ports, memory and CPU.

#### Deep dive

CI often validates code but not exact production config or network paths. Spring Boot startup failures frequently come from missing properties, invalid secrets or failed bean creation.

#### Production angle

Fail-fast configuration validation and pre-prod startup checks prevent many of these issues.

#### Traps / caveats

- Do not assume CI used the same profile or config source.
- Do not print secrets while debugging config.

#### Optional Anki

Q: First production startup failure checks?
A: Logs, config, secrets, profiles, migrations, dependencies and resources.

</details>

<a id="cicd-scen-002"></a>

<details>
<summary><strong>CICD-SCEN-002. A deployment succeeds but traffic still goes to old pods. What could be wrong?</strong></summary>

#### Short answer

Check service selectors, readiness, rollout status, ingress or load balancer routing, canary rules and DNS or service mesh config.

#### Interview answer

The new pods may not be ready, labels may not match the Service selector, the rollout may be paused, traffic rules may still point to the old version, or sticky sessions may keep users on old pods. In GitOps, the desired state may also not have synced.

#### Deep dive

Kubernetes object update success is not the same as traffic shifting. Routing layers must be checked separately.

#### Production angle

This can create false confidence because the pipeline says "deployed" while users still run old code.

#### Traps / caveats

- Readiness failures keep new pods out of service.
- Multiple routing layers can override each other.

#### Optional Anki

Q: What can keep traffic on old pods after deployment?
A: Readiness, selectors, rollout state, ingress rules, service mesh or sticky sessions.

</details>

<a id="cicd-scen-003"></a>

<details>
<summary><strong>CICD-SCEN-003. A new version causes a spike in HTTP 500 responses after 5% canary traffic. What should the pipeline do?</strong></summary>

#### Short answer

Stop the rollout, alert owners, preserve evidence and roll back or disable the change if safe.

#### Interview answer

The pipeline should automatically fail canary analysis, prevent further traffic increase, capture metrics and logs for the canary version, notify the team and execute the predefined recovery path. That may be rollback, traffic shift back, or feature-flag disable.

#### Deep dive

The team should compare canary and baseline by route, dependency, tenant and error type before deciding whether to patch forward.

#### Production angle

Canary value comes from limiting blast radius and reacting before 100% exposure.

#### Traps / caveats

- Do not retry rollout blindly.
- Confirm whether errors are from code, config, schema or downstream dependency.

#### Optional Anki

Q: What should a failed canary do?
A: Stop rollout and trigger evidence capture, alerting and safe recovery.

</details>

<a id="cicd-scen-004"></a>

<details>
<summary><strong>CICD-SCEN-004. A release works in staging but fails in production because of missing configuration. How do you prevent this class of issue?</strong></summary>

#### Short answer

Use typed required configuration, startup validation, environment parity checks and deployment-time config verification.

#### Interview answer

I would model config with `@ConfigurationProperties`, validate required values at startup, fail fast on invalid config, check environment manifests in CI, and make non-sensitive effective config version visible. Staging should use the same config injection mechanism as production.

#### Deep dive

Config contracts should be part of release validation: required keys, allowed values, profile behavior and secret references.

#### Production angle

Missing config should be caught before traffic reaches the new version.

#### Traps / caveats

- Default values can hide missing production config.
- Do not log actual secret values while validating presence.

#### Optional Anki

Q: How do you prevent missing production config?
A: Typed config, startup validation, CI manifest checks and environment parity.

</details>

<a id="cicd-scen-005"></a>

<details>
<summary><strong>CICD-SCEN-005. A pipeline suddenly starts failing because a dependency version disappeared or changed. What should you inspect?</strong></summary>

#### Short answer

Inspect dependency versions, repositories, mirrors, caches, lockfiles, snapshots, dynamic versions and artifact retention.

#### Interview answer

I would check whether the build uses `SNAPSHOT`, version ranges, dynamic Gradle versions, unpinned plugins, repository order, private proxy behavior or deleted artifacts. Then compare dependency trees and build logs from the last successful run.

#### Deep dive

Builds should not depend on mutable dependency coordinates for production releases. Dependency locking and private artifact repositories reduce this risk.

#### Production angle

Dependency instability can block urgent hotfixes or produce different artifacts from the same source.

#### Traps / caveats

- CI cache may hide dependency problems until a clean runner appears.
- Public repository outages can break builds without code changes.

#### Optional Anki

Q: What dependency practices cause non-reproducible builds?
A: Snapshots, dynamic versions, unpinned plugins and mutable repositories.

</details>

<a id="cicd-scen-006"></a>

<details>
<summary><strong>CICD-SCEN-006. A vulnerability scan fails right before release. How do you decide whether to block, patch, waive or rollback?</strong></summary>

#### Short answer

Evaluate severity, exploitability, exposure, affected artifact, available fix and business risk.

#### Interview answer

I would identify the vulnerable component, whether it is runtime or test-only, whether the code path is reachable, whether the service is exposed, and whether a fixed version exists. Critical exploitable runtime vulnerabilities should usually block. Lower-risk findings may get a time-bound waiver with owner.

#### Deep dive

For already deployed vulnerable artifacts, the decision may be patch forward, rollback, disable exposure, add compensating controls or rotate secrets if compromise is suspected.

#### Production angle

Security gates need policy so teams do not debate from scratch during a release window.

#### Traps / caveats

- CVSS alone does not prove exploitability in your service.
- Waivers need expiry and accountability.

#### Optional Anki

Q: What matters when triaging a vulnerability gate?
A: Severity, exploitability, exposure, affected artifact and fix availability.

</details>

<a id="cicd-scen-007"></a>

<details>
<summary><strong>CICD-SCEN-007. A rollback restores the old app version, but errors continue. What stateful components do you inspect?</strong></summary>

#### Short answer

Inspect database schema and data, caches, queues, messages, feature flags, config, sessions and external side effects.

#### Interview answer

The old app may be running against new schema, migrated data, stale cache entries, incompatible messages, changed config, rotated secrets or altered downstream state. I would check each stateful dependency touched by the release.

#### Deep dive

Rollback restores code, not necessarily state. Data repair or roll-forward may be required.

#### Production angle

This is why stateful release changes need explicit compatibility and recovery plans.

#### Traps / caveats

- Clearing caches can help or harm depending on load and correctness.
- Message queues may contain events produced by the new version.

#### Optional Anki

Q: What does app rollback not automatically restore?
A: Database, cache, messages, config, sessions and external side effects.

</details>

<a id="cicd-scen-008"></a>

<details>
<summary><strong>CICD-SCEN-008. A background job is deployed twice and processes the same data twice. How could the release process have contributed?</strong></summary>

#### Short answer

The rollout may have allowed duplicate workers without locking, idempotency or leader election.

#### Interview answer

Blue-green, rolling deployment or failed rollback can temporarily run old and new workers together. If the job has no idempotency key, distributed lock, partition ownership, lease or scheduler coordination, both versions can process the same work.

#### Deep dive

Background jobs need release-specific controls: single active scheduler, graceful shutdown, checkpointing and duplicate-safe processing.

#### Production angle

Duplicate processing can charge users twice, send duplicate emails or corrupt aggregates.

#### Traps / caveats

- HTTP readiness does not prove worker ownership is correct.
- Locking alone is not enough if side effects are not idempotent.

#### Optional Anki

Q: How can deployment duplicate background work?
A: Old and new workers can run concurrently without coordination.

</details>

<a id="cicd-scen-009"></a>

<details>
<summary><strong>CICD-SCEN-009. A CI job leaked a production secret into logs. What immediate and long-term actions are needed?</strong></summary>

#### Short answer

Revoke and rotate the secret, restrict log access, assess exposure, then fix the pipeline and secret handling.

#### Interview answer

Immediately stop the leak, remove or restrict logs, rotate the exposed credential, audit access and look for suspicious use. Longer term, identify why masking failed, reduce secret scope, use short-lived credentials, avoid printing commands, and add tests or policy to prevent recurrence.

#### Deep dive

If the secret grants production access, treat it as a security incident until impact is understood.

#### Production angle

CI logs often have broader access than production infrastructure, so leaked secrets must be handled seriously.

#### Traps / caveats

- Deleting logs is not enough; rotate the secret.
- Transformed secrets may not be masked automatically.

#### Optional Anki

Q: First action after secret leak?
A: Revoke or rotate the secret and restrict exposure.

</details>

<a id="cicd-scen-010"></a>

<details>
<summary><strong>🧠 CICD-SCEN-010. How would you design a safe release plan for a high-traffic Java service with database changes and multiple downstream consumers?</strong></summary>

#### Short answer

Use backward-compatible migrations, contract checks, staged rollout, feature flags, observability and explicit recovery plans.

#### Interview answer

I would start with requirements and risk: schema changes, API or event contracts, downstream consumers, traffic patterns and rollback constraints. Then use expand-and-contract migrations, verify contracts, deploy code with behavior disabled if possible, canary by version or tenant, monitor SLOs and downstream errors, and only clean up old schema after all consumers are safe.

#### Deep dive

The plan should include database lock analysis, migration batching, old/new version compatibility, consumer lag, idempotency, feature-flag defaults and communication with downstream owners.

#### Production angle

High traffic magnifies small mistakes, so blast radius and observability matter more than raw deployment speed.

#### Traps / caveats

- Do not combine schema removal and consumer behavior change in one irreversible release.
- Downstream consumers may process old messages long after the producer changes.

#### Optional Anki

Q: What pattern helps release DB changes safely?
A: Expand-and-contract migration with mixed-version compatibility.

</details>

<details>
<summary><strong>CICD-SCEN-011. Two services deploy independently and a consumer breaks after an API or event schema change. What release compatibility checks were missing?</strong></summary>

#### Short answer

Missing checks likely include contract tests, schema compatibility validation, tolerant-reader behavior and consumer rollout planning.

#### Interview answer

For REST, the provider may have removed or renamed a field, changed status codes, tightened validation or changed error shape. For events, the producer may have changed schema, enum values or required fields. CI should verify backward and forward compatibility before release.

#### Deep dive

Consumer-driven contracts, OpenAPI diff checks, schema registry compatibility, generated client tests and replay tests can catch these breaks.

#### Production angle

Independent deployment works only when contracts evolve safely and old consumers remain supported during rollout.

#### Traps / caveats

- Adding enum values can break consumers that assume a closed set.
- Optional JSON fields can become effectively required if consumers depend on them.

#### Optional Anki

Q: What protects independent service releases?
A: Backward-compatible contracts, contract tests and schema compatibility checks.

</details>
