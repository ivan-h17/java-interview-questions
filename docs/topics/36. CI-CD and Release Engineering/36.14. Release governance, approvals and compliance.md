# Release governance, approvals and compliance

---

<a id="cicd-gov-001"></a>

<details>
<summary><strong>CICD-GOV-001. When should production deployments require manual approval?</strong></summary>

#### Short answer

Use manual approval for high-risk changes, regulated environments, weak automation or known production instability.

#### Interview answer

Manual approval is reasonable for database-breaking changes, sensitive infrastructure changes, high-impact customer releases, compliance-controlled systems or emergency overrides. It should be based on release evidence, not just habit.

#### Deep dive

As automation matures, some approvals can become policy-as-code gates. The goal is controlled risk, not manual ceremony.

#### Production angle

Approvals can prevent unsafe changes, but excessive approvals increase batch size and delay fixes.

#### Traps / caveats

- "Someone clicked approve" is not meaningful without evidence.
- Manual gates should not compensate for missing tests forever.

#### Optional Anki

Q: When is manual production approval justified?
A: High-risk, regulated, unstable or insufficiently automated releases.

</details>

<a id="cicd-gov-002"></a>

<details>
<summary><strong>CICD-GOV-002. What should an approval gate check besides "someone clicked approve"?</strong></summary>

#### Short answer

It should check release evidence: tests, scans, artifact identity, change scope, risk and rollback plan.

#### Interview answer

An approval should verify that required tests passed, vulnerabilities are acceptable, artifact and image digest are known, migrations are reviewed, config and flag changes are understood, monitoring is ready and rollback or roll-forward is planned.

#### Deep dive

Approval quality improves when the pipeline presents a checklist and links to evidence automatically.

#### Production angle

Evidence-based approvals reduce rubber-stamping and improve incident accountability.

#### Traps / caveats

- Approvers need enough context and authority to say no.
- Approval records should be auditable.

#### Optional Anki

Q: What should an approval gate evaluate?
A: Evidence, risk, artifact identity, migrations, monitoring and recovery plan.

</details>

<details>
<summary><strong>🧠 CICD-GOV-003. How should release notes or change summaries be generated for backend services?</strong></summary>

#### Short answer

Generate them from commits, pull requests, issue links and deployment metadata, then allow human cleanup for important releases.

#### Interview answer

Backend release summaries should show changed services, commit range, PRs, issue links, database migrations, config or flag changes, dependency upgrades, operational impact and rollback notes. Automation can draft this from repository and pipeline metadata.

#### Deep dive

For internal services, release notes are less about marketing and more about operational awareness.

#### Production angle

Good summaries help on-call engineers correlate incidents with recent changes.

#### Traps / caveats

- Raw commit lists are often too noisy.
- Sensitive implementation or security details may need restricted visibility.

#### Optional Anki

Q: What should backend release notes highlight?
A: Changed services, PRs, migrations, config, dependencies, impact and rollback notes.

</details>

<a id="cicd-gov-004"></a>

<details>
<summary><strong>CICD-GOV-004. What audit trail should a release process keep?</strong></summary>

#### Short answer

It should record who changed what, what was built, what passed, who approved and what was deployed.

#### Interview answer

An audit trail should include source commit, artifact digest, build workflow, test and scan results, SBOM, provenance, approval, deployment time, target environment, config or flag changes and rollback actions.

#### Deep dive

Audit records should be tamper-resistant enough for the organization risk level and retained according to policy.

#### Production angle

Audit trails support incident investigation, compliance reviews and vulnerability response.

#### Traps / caveats

- Logs may contain secrets and need controlled retention.
- Audit data is useful only if it links code, artifact and deployment.

#### Optional Anki

Q: What are key release audit facts?
A: Source, artifact, checks, approvals, deployment target and timing.

</details>

<a id="cicd-gov-005"></a>

<details>
<summary><strong>CICD-GOV-005. How do compliance requirements affect deployment automation?</strong></summary>

#### Short answer

They add evidence, access control, approvals, retention and separation requirements, but should still be automated where possible.

#### Interview answer

Compliance may require change records, approval history, segregation of duties, audit logs, vulnerability handling, artifact retention, data residency and controlled access to production. Automation can enforce and record these controls more reliably than manual checklists.

#### Deep dive

Good compliance design makes the safe path easy and visible. It should not force teams into untracked manual work.

#### Production angle

Automated compliance controls reduce both regulatory risk and operational mistakes.

#### Traps / caveats

- Compliance does not automatically mean slow releases.
- Manual screenshots and ad hoc approvals are fragile evidence.

#### Optional Anki

Q: How should CI/CD handle compliance?
A: Automate controls, evidence, approvals, access rules and retention.

</details>

<details>
<summary><strong>🧠 CICD-GOV-006. How do you balance separation of duties with fast, automated delivery?</strong></summary>

#### Short answer

Separate authority and controls without requiring every release to be manually performed by another team.

#### Interview answer

Developers can own delivery while production permissions, approvals, policy-as-code and audit trails enforce separation. For example, developers merge code, CI builds artifacts, a protected environment requires approval, and deployment uses a service identity with limited permissions.

#### Deep dive

The separation should be around control and evidence, not necessarily around who clicks a deploy button.

#### Production angle

This keeps releases fast while reducing unilateral production risk.

#### Traps / caveats

- Shared admin credentials break separation of duties.
- Too much central gatekeeping creates bottlenecks and shadow processes.

#### Optional Anki

Q: What is a good modern separation-of-duties pattern?
A: Protected workflows, limited identities, approvals and audit trails instead of manual handoffs.

</details>
