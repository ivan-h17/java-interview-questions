# CI/CD fundamentals and release mindset

---

<a id="cicd-fund-001"></a>

<details>
<summary><strong>CICD-FUND-001. What is the difference between continuous integration, continuous delivery and continuous deployment?</strong></summary>

#### Short answer

Continuous integration keeps code integrated and tested often; continuous delivery keeps software always releasable; continuous deployment automatically releases every passing change to production.

#### Interview answer

CI is about merging frequently and validating changes with automated builds and tests. Continuous delivery adds a reliable path from commit to a production-ready artifact, usually with a manual approval before production. Continuous deployment removes that manual production gate and deploys automatically when all checks pass.

#### Deep dive

The distinction is important because a team can have CI without safe releases, and can have delivery automation without automatically deploying to users. The maturity requirement grows from CI to delivery to deployment.

#### Production angle

For Java backend teams, the difference shows up in how safely they can ship database changes, configuration changes, dependency upgrades and service contract changes.

#### Traps / caveats

- Running a build server is not the same as practicing CI.
- Continuous deployment is risky without strong tests, observability, rollback and small changes.

#### Optional Anki

Q: What is the key difference between continuous delivery and continuous deployment?
A: Continuous delivery keeps every change releasable; continuous deployment automatically releases passing changes to production.

</details>

<details>
<summary><strong>CICD-FUND-002. What problem does CI/CD solve for a Java backend team?</strong></summary>

#### Short answer

CI/CD reduces integration risk, manual release mistakes and slow feedback between code changes and production behavior.

#### Interview answer

In a Java backend team, CI/CD makes builds repeatable, catches broken tests or dependency problems early, packages artifacts consistently and deploys them through controlled stages. It also makes release history, approvals, artifacts and failures visible instead of relying on local developer machines or manual runbooks.

#### Deep dive

The real value is not only speed. It is reducing batch size, making deployment boring, and creating a clear path for rollback, roll-forward and incident analysis.

#### Production angle

Good CI/CD prevents common incidents: wrong JAR deployed, wrong config used, missing migration, untested contract change, leaked secret or undocumented hotfix.

#### Traps / caveats

- CI/CD does not replace engineering discipline around tests and compatibility.
- A fast pipeline that ships unsafe changes is just a faster incident path.

#### Optional Anki

Q: What is the main backend value of CI/CD?
A: Repeatable validation, packaging and deployment with faster feedback and fewer manual release errors.

</details>

<details>
<summary><strong>CICD-FUND-003. What is a deployment pipeline?</strong></summary>

#### Short answer

A deployment pipeline is an automated sequence that takes a source change through build, validation, packaging, promotion and deployment.

#### Interview answer

A typical pipeline compiles the code, runs tests, performs static and security checks, builds a release artifact or image, publishes it, deploys it to environments, and verifies the result. Each stage should increase confidence and stop the change if a blocking quality gate fails.

#### Deep dive

Pipelines should produce traceable artifacts, not just execute scripts. A good pipeline shows what commit, dependencies, image, config version and approval produced a running service.

#### Production angle

During an incident, the pipeline is often the fastest way to answer what changed, when it changed, who approved it and whether rollback is possible.

#### Traps / caveats

- A pipeline with many manual hidden steps is not truly repeatable.
- A green deploy step does not prove the release is healthy for users.

#### Optional Anki

Q: What does a deployment pipeline do?
A: It automates build, validation, artifact creation, promotion, deployment and verification.

</details>

<details>
<summary><strong>CICD-FUND-004. How is deployment different from release?</strong></summary>

#### Short answer

Deployment puts code into an environment; release exposes functionality or behavior to users.

#### Interview answer

A service can be deployed without being fully released if the new behavior is behind a feature flag, disabled route, dark launch or internal-only path. Release is the business or user-facing activation of behavior.

#### Deep dive

Separating deployment from release lets teams deploy safely during normal hours, test in production with limited exposure, and turn features on gradually. It is especially useful for risky Java backend changes with downstream dependencies or database compatibility constraints.

#### Production angle

This separation allows faster rollback of behavior through a flag even when rolling back the binary would be slower or unsafe.

#### Traps / caveats

- Feature flags need owners and cleanup dates.
- A deployed but disabled path still needs security, validation and observability.

#### Optional Anki

Q: What is the difference between deployment and release?
A: Deployment installs code; release exposes behavior to users.

</details>

<details>
<summary><strong>CICD-FUND-005. Why should releases be small, frequent and reversible?</strong></summary>

#### Short answer

Small releases are easier to review, test, deploy, debug and roll back.

#### Interview answer

Large releases combine many unrelated changes, so failures are harder to isolate and rollback may undo useful work. Small, frequent releases reduce blast radius and make production feedback more precise.

#### Deep dive

Reversibility does not always mean a simple binary rollback. It may require compatible database migrations, feature flags, previous artifacts, restored config and a clear roll-forward path.

#### Production angle

When an incident starts after a small release, the team can correlate symptoms with a narrow change set and decide quickly whether to disable, roll back or patch forward.

#### Traps / caveats

- Small releases still need compatibility checks.
- Reversibility must be designed before deployment, especially for data changes.

#### Optional Anki

Q: Why are small releases safer?
A: They reduce blast radius and make testing, debugging and rollback easier.

</details>

<details>
<summary><strong>CICD-FUND-006. What does "production-ready" mean before a backend service is deployed?</strong></summary>

#### Short answer

Production-ready means the service is deployable, observable, configurable, secure and recoverable under expected production conditions.

#### Interview answer

For a Java backend, production readiness includes passing tests, a versioned artifact, externalized config, validated secrets, migrations, health checks, logs, metrics, traces, dashboards, alerts, resource sizing and rollback or roll-forward plans.

#### Deep dive

It also means operational ownership: someone knows the SLOs, dependencies, runbooks, failure modes and escalation path. Production readiness is not just code correctness.

#### Production angle

Most deployment failures are not compilation failures; they are missing config, bad credentials, wrong resource limits, incompatible schemas or invisible runtime behavior.

#### Traps / caveats

- A service can pass CI and still be unready for production.
- Readiness should be checked continuously, not only before the first launch.

#### Optional Anki

Q: What does production-ready include beyond passing tests?
A: Config, secrets, observability, health checks, resource sizing, ownership and recovery plans.

</details>

<details>
<summary><strong>🧠 CICD-FUND-007. How can CI/CD improve both delivery speed and reliability instead of trading one for the other?</strong></summary>

#### Short answer

CI/CD improves both when it reduces batch size, automates feedback and makes recovery faster.

#### Interview answer

Speed and reliability improve together when changes are small, tests run automatically, artifacts are reproducible, deployments are gradual, and failures are detected early. The team spends less time coordinating large releases and more time learning from safe production feedback.

#### Deep dive

The key is system design: trunk-based flow, fast pipelines, contract tests, deploy/release separation, observability, rollback and clear ownership. These practices reduce both waiting time and failure impact.

#### Production angle

A reliable release process lets teams ship dependency patches, security fixes and production bug fixes quickly without heroic manual coordination.

#### Traps / caveats

- Optimizing only pipeline speed can remove important risk controls.
- Optimizing only approvals can create large, risky batches.

#### Optional Anki

Q: How can CI/CD improve speed and reliability at the same time?
A: By making changes smaller, feedback faster, deployment repeatable and recovery cheaper.

</details>

<details>
<summary><strong>🧠 CICD-FUND-008. When is full continuous deployment too risky or immature for a team?</strong></summary>

#### Short answer

It is too risky when tests, observability, rollback, ownership or compatibility practices are not strong enough.

#### Interview answer

Full continuous deployment is immature if the team has flaky tests, weak production monitoring, manual database changes, unclear ownership, frequent hotfixes, unsafe secrets handling or no reliable rollback. In that case, continuous delivery with explicit production approval is usually safer.

#### Deep dive

Risk also depends on domain. Payments, healthcare, regulated data and shared platform services may require extra controls even with high automation.

#### Production angle

The goal is not to remove humans blindly; it is to make the release decision evidence-based and low-risk.

#### Traps / caveats

- Manual approval does not make a bad pipeline safe.
- Continuous deployment can still include automated policy gates and progressive rollout.

#### Optional Anki

Q: What must be mature before continuous deployment?
A: Tests, observability, rollback, ownership, compatibility and security controls.

</details>
