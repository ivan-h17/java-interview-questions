# Database migrations and stateful release constraints

---

<a id="cicd-db-001"></a>

<details>
<summary><strong>CICD-DB-001. Why are database migrations often the hardest part of rollback?</strong></summary>

#### Short answer

Because data and schema changes can be irreversible or incompatible with the old application version.

#### Interview answer

Rolling back code is relatively easy if the old artifact exists. Rolling back a database is harder because columns may be dropped, values transformed, constraints changed, data rewritten or external effects already produced.

#### Deep dive

Safe database release design usually uses backward-compatible changes first, then application rollout, then cleanup later after old versions are gone.

#### Production angle

A failed migration can leave both old and new app versions broken if compatibility was not planned.

#### Traps / caveats

- Down migrations are often unsafe for production data.
- Backups help disaster recovery but are not a quick rollback for a busy database.

#### Optional Anki

Q: Why are DB migrations hard to roll back?
A: They can change persistent state in ways old code cannot handle.

</details>

<a id="cicd-db-002"></a>

<details>
<summary><strong>CICD-DB-002. When should migrations run as part of application startup versus a separate pipeline step?</strong></summary>

#### Short answer

Startup migrations fit simple safe changes; separate steps fit risky, long-running or coordinated production migrations.

#### Interview answer

Running Flyway or Liquibase at startup is convenient for small services and simple schema changes. For production-critical systems, long locks, backfills, large table changes or multi-service coordination are safer as explicit pipeline or DBA-reviewed steps.

#### Deep dive

Startup migrations can be dangerous during horizontal rollout if many replicas try to migrate simultaneously or if migration failure prevents all pods from starting.

#### Production angle

Separate migration steps allow lock timeout settings, monitoring, approvals and a clear stop point before app rollout.

#### Traps / caveats

- Do not run heavy data migrations during every app startup.
- Startup migrations still need idempotency and locking.

#### Optional Anki

Q: When prefer separate migration steps?
A: For risky, long-running, lock-heavy or coordinated database changes.

</details>

<a id="cicd-db-003"></a>

<details>
<summary><strong>CICD-DB-003. How do rolling deployments constrain schema changes?</strong></summary>

#### Short answer

Schema changes must be compatible with both old and new application versions during the rollout.

#### Interview answer

In rolling deployment, old and new pods run at the same time. Therefore the database schema must support both versions. Adding nullable columns is usually safer than renaming or dropping columns used by old code.

#### Deep dive

Breaking changes should be split: expand schema, deploy compatible code, migrate data, switch reads or writes, then contract old schema later.

#### Production angle

Ignoring mixed-version compatibility causes partial outages where some pods work and others fail.

#### Traps / caveats

- Adding a required non-null column without default can break old insert logic.
- Renaming columns is usually drop-and-add from the application perspective.

#### Optional Anki

Q: What does rolling deployment require from schema changes?
A: Compatibility with old and new application versions.

</details>

<a id="cicd-db-004"></a>

<details>
<summary><strong>CICD-DB-004. What is the expand-and-contract migration pattern from a release perspective?</strong></summary>

#### Short answer

First add compatible schema, then move application behavior, then remove old schema later.

#### Interview answer

Expand means adding new columns, tables or indexes in a backward-compatible way. The app is then changed to write or read both old and new forms as needed. Contract removes old schema only after all running versions and data have moved.

#### Deep dive

This pattern is essential for zero-downtime deployments because it avoids requiring code and schema to switch at the exact same moment.

#### Production angle

It reduces rollback risk because old code can continue running during early phases.

#### Traps / caveats

- Cleanup must not be forgotten.
- Dual writes need verification and idempotency.

#### Optional Anki

Q: What are the phases of expand-and-contract?
A: Add compatible schema, migrate behavior/data, then remove old schema.

</details>

<a id="cicd-db-005"></a>

<details>
<summary><strong>CICD-DB-005. How should CI verify that application code and database migrations are compatible?</strong></summary>

#### Short answer

Run migrations from a realistic baseline and test the application against the migrated schema.

#### Interview answer

CI should apply migrations to a clean database and, when possible, to a copy of the previous schema state. Then it should run repository, integration and startup tests against the result. It can also check migration ordering, checksum drift and generated schema expectations.

#### Deep dive

For services with rolling deploys, compatibility tests should check old app against expanded schema and new app against old-compatible data shapes.

#### Production angle

This catches missing columns, invalid constraints, broken indexes and startup failures before production.

#### Traps / caveats

- Testing only an empty schema misses real data issues.
- ORM auto-DDL should not silently replace reviewed migrations in production.

#### Optional Anki

Q: How can CI test migrations?
A: Apply migrations to a database and run application integration tests against it.

</details>

<a id="cicd-db-006"></a>

<details>
<summary><strong>CICD-DB-006. What deployment checks are needed before a risky production data migration?</strong></summary>

#### Short answer

Check backup, lock risk, runtime estimate, batching, monitoring, rollback or repair plan and application compatibility.

#### Interview answer

Before a risky migration, I would verify backups and restore strategy, run the migration on production-like data, estimate locks and duration, set timeouts, batch large updates, monitor database load, define pause/resume behavior and communicate ownership.

#### Deep dive

For PostgreSQL, table rewrites, long transactions, index creation mode, foreign keys and constraint validation can change lock behavior significantly.

#### Production angle

Data migrations can degrade the whole service even when application pods are healthy.

#### Traps / caveats

- A successful staging run on small data does not prove production safety.
- Rollback may mean repair scripts, not a simple down migration.

#### Optional Anki

Q: What must be checked before risky data migration?
A: Backup, lock impact, duration, batching, monitoring and recovery plan.

</details>

<a id="cicd-db-007"></a>

<details>
<summary><strong>🧠 CICD-DB-007. How would you recover from a release where the app deployed successfully but a migration partially failed?</strong></summary>

#### Short answer

Stop further rollout, identify migration state, protect data, then choose roll-forward, repair or rollback based on compatibility.

#### Interview answer

First I would freeze deployment, inspect migration logs and schema state, check whether the app version can safely run with the partial state, and look for data corruption or locks. Then I would decide whether to complete the migration, apply a repair script, disable affected behavior or roll back the app.

#### Deep dive

Good migration tools track applied changes, but partial data migrations may need custom progress markers and idempotent repair.

#### Production angle

The priority is preventing more writes into an inconsistent state while keeping unaffected paths available if possible.

#### Traps / caveats

- Do not blindly rerun a non-idempotent migration.
- Do not roll back the app if the old version cannot handle the partial schema.

#### Optional Anki

Q: First step after partial migration failure?
A: Stop rollout and determine the exact schema/data state.

</details>
