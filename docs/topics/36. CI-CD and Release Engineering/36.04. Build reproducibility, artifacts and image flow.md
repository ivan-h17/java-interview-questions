# Build reproducibility, artifacts and image flow

---

<a id="cicd-art-001"></a>

<details>
<summary><strong>CICD-ART-001. What should be included in a production release artifact?</strong></summary>

#### Short answer

It should include the runnable application and metadata needed to identify, verify and operate it.

#### Interview answer

For Java, the artifact may be an executable JAR or container image containing the application code, runtime dependencies and startup command. It should also have metadata such as version, commit SHA, build time, build number, image digest, dependency information and links to test or scan results.

#### Deep dive

Configuration and secrets should usually not be baked into the artifact. The same artifact should be deployable to multiple environments with different runtime configuration.

#### Production angle

A complete artifact makes rollback, audit, vulnerability response and incident debugging possible.

#### Traps / caveats

- Do not include production secrets in JARs, images or layers.
- Do not rely only on mutable tags such as `latest`.

#### Optional Anki

Q: What belongs in a production artifact?
A: Runnable application code, dependencies and identifying metadata, but not environment secrets.

</details>

<a id="cicd-art-002"></a>

<details>
<summary><strong>CICD-ART-002. Why should the same artifact be promoted across environments?</strong></summary>

#### Short answer

Promoting the same artifact proves that the binary tested in lower environments is the one deployed to production.

#### Interview answer

If every environment uses the same JAR or image digest, differences come from configuration and infrastructure, not from rebuilding code. This makes test evidence meaningful and reduces the chance that production runs an untested artifact.

#### Deep dive

Promotion also supports audit and rollback because the artifact has one identity throughout its lifecycle.

#### Production angle

During a release incident, the team can compare environment config and runtime state instead of wondering whether the production binary is different.

#### Traps / caveats

- Environment-specific config should be injected at runtime.
- If migrations are tied to artifact startup, promotion still needs schema compatibility checks.

#### Optional Anki

Q: Why promote the same artifact?
A: To ensure production runs the exact artifact that was tested and approved.

</details>

<a id="cicd-art-003"></a>

<details>
<summary><strong>CICD-ART-003. What can go wrong if each environment rebuilds its own artifact?</strong></summary>

#### Short answer

Each environment can produce a different binary, dependency graph or image layer set.

#### Interview answer

Rebuilding per environment can pull different dependency versions, plugins, base images, generated sources or build metadata. A staging build can pass while a production rebuild fails or behaves differently.

#### Deep dive

Even small differences matter in Java: a transitive dependency change can create `NoSuchMethodError`, a different JDK can change behavior, and a different base image can change certificates or timezone data.

#### Production angle

Per-environment rebuilds weaken test evidence and make rollback less reliable.

#### Traps / caveats

- Rebuilding is especially risky with dynamic versions, snapshots or mutable image tags.
- Build caches can hide the issue until a cache miss.

#### Optional Anki

Q: Why are per-environment rebuilds risky?
A: They can produce different artifacts than the ones tested earlier.

</details>

<a id="cicd-art-004"></a>

<details>
<summary><strong>CICD-ART-004. How should Docker images be tagged in CI/CD?</strong></summary>

#### Short answer

Use immutable, traceable tags such as commit SHA, semantic version or build number, and deploy by digest when possible.

#### Interview answer

A good image tagging strategy includes human-readable release tags and machine-stable identifiers. For example, use `service:1.8.3`, `service:git-abc1234`, and record the image digest. Production manifests should avoid ambiguous mutable tags.

#### Deep dive

Tags are names; digests identify content. The registry can move a tag, but a digest points to a specific image manifest.

#### Production angle

Traceable tags and digests make rollout history, rollback and vulnerability response much easier.

#### Traps / caveats

- `latest` is not a production deployment strategy.
- Retagging an image can confuse audit and rollback.

#### Optional Anki

Q: What image identifiers are safest for production?
A: Immutable tags plus the image digest.

</details>

<a id="cicd-art-005"></a>

<details>
<summary><strong>CICD-ART-005. Why are image digests safer than mutable tags for production deployment?</strong></summary>

#### Short answer

A digest identifies exact image content; a tag can be moved to different content.

#### Interview answer

Deploying by digest guarantees the runtime pulls the exact image that was scanned, tested and approved. Mutable tags like `latest` or even reused version tags can change behind the same name.

#### Deep dive

Digest pinning is part of artifact integrity. It reduces ambiguity when investigating whether production is running the intended container image.

#### Production angle

If a bad image is pushed under a reused tag, digest-based deployment prevents unexpected production changes.

#### Traps / caveats

- Digest pinning does not prove the image is secure; it proves identity.
- Retention policies must keep the referenced digest available for rollback.

#### Optional Anki

Q: Why deploy by image digest?
A: Because a digest identifies exact immutable image content.

</details>

<a id="cicd-art-006"></a>

<details>
<summary><strong>🧠 CICD-ART-006. What metadata should be attached to a build artifact or container image?</strong></summary>

#### Short answer

Attach metadata that proves origin, content, build process, dependencies and deployment context.

#### Interview answer

Useful metadata includes service name, version, commit SHA, branch or tag, build ID, build timestamp, builder identity, JDK version, Maven or Gradle version, dependency list, SBOM, image digest, base image, test results, scan results and provenance or attestation links.

#### Deep dive

Metadata should be machine-readable where possible, for example OCI labels, manifest annotations, artifact repository properties or deployment labels.

#### Production angle

Good metadata lets incident response answer whether a vulnerable dependency is deployed, which commit introduced behavior, and which artifacts can be rolled back.

#### Traps / caveats

- Avoid embedding secrets or sensitive internal URLs.
- Metadata should not make builds non-reproducible unless the trade-off is intentional.

#### Optional Anki

Q: Why attach metadata to artifacts?
A: To trace origin, content, build process and deployment state.

</details>

<a id="cicd-art-007"></a>

<details>
<summary><strong>🧠 CICD-ART-007. How do Maven or Gradle wrappers, pinned plugins, dependency locking and image digests make a Java build reproducible enough for release engineering?</strong></summary>

#### Short answer

They remove moving parts from the build: tool versions, plugin versions, dependency versions and base image identity.

#### Interview answer

The Maven or Gradle wrapper fixes the build tool version. Pinned plugins and Java toolchains reduce differences between machines. Dependency locking or strict version management prevents unexpected transitive changes. Image digests prevent base images from changing under a tag.

#### Deep dive

Java builds can also vary because of generated timestamps, manifest entries, file ordering, locale, timezone or generated sources. Reproducibility means the team can rebuild or at least explain exactly what inputs produced the artifact.

#### Production angle

Reproducible builds support rollback, audit, incident response and supply-chain trust.

#### Traps / caveats

- `SNAPSHOT`, dynamic versions and mutable plugin versions break release confidence.
- A build cache is not a substitute for declared inputs and locked dependencies.

#### Optional Anki

Q: What makes a Java build more reproducible?
A: Wrapper versions, pinned plugins, fixed Java toolchains, dependency locking and immutable base images.

</details>

<details>
<summary><strong>🧠 CICD-ART-008. What is build provenance, and why does it matter for a production artifact?</strong></summary>

#### Short answer

Build provenance is verifiable information about where, when, how and from what inputs an artifact was built.

#### Interview answer

Provenance ties an artifact to source commit, builder, workflow, parameters, dependencies and outputs. It matters because production teams need confidence that the artifact came from the expected source and trusted build process.

#### Deep dive

Provenance is usually represented as an attestation. It complements SBOMs: an SBOM describes contents, while provenance describes the build path.

#### Production angle

During a compromise or vulnerability response, provenance helps identify whether an artifact was built by a trusted pipeline or tampered with outside it.

#### Traps / caveats

- Provenance is useful only if consumers verify it.
- A trusted builder can still build vulnerable or incorrect code.

#### Optional Anki

Q: What does build provenance describe?
A: The source, builder, process, inputs and outputs of an artifact build.

</details>

<details>
<summary><strong>🧠 CICD-ART-009. How can artifact retention policy affect rollback, audit and incident response?</strong></summary>

#### Short answer

If artifacts disappear too soon, rollback and investigation may become impossible or unreliable.

#### Interview answer

A retention policy controls how long builds, images, logs, test reports, SBOMs and scan results remain available. Production artifacts and their evidence should live at least as long as the release support, audit and incident response requirements.

#### Deep dive

Retention should distinguish temporary PR artifacts from released production artifacts. The latter often need stronger immutability and longer retention.

#### Production angle

If a previous image digest was garbage-collected, rollback may fail exactly when the team needs it.

#### Traps / caveats

- Keeping everything forever can create cost and data-retention risks.
- Logs may contain sensitive data, so retention must also respect security policy.

#### Optional Anki

Q: Why does artifact retention matter?
A: It preserves rollback targets and release evidence for audit and incident response.

</details>
