# Pipeline architecture and stages

---

<a id="cicd-pipe-001"></a>

<details>
<summary><strong>CICD-PIPE-001. What stages should a typical Java backend CI pipeline contain?</strong></summary>

#### Short answer

It should compile, test, analyze, package, publish and optionally deploy and verify the service.

#### Interview answer

For a Spring Boot backend, I expect stages for checkout, dependency resolution, compile, unit tests, integration tests, static analysis, security scanning, packaging a JAR or image, publishing artifacts, deploying to an environment, and running smoke or post-deploy checks.

#### Deep dive

Not every check needs to run on every event. Fast checks belong on pull requests; heavier integration, security and environment checks may run after merge or before production.

#### Production angle

Pipeline stages should produce enough evidence to explain what was shipped: commit, build logs, test reports, image digest, SBOM, config version and deployment result.

#### Traps / caveats

- Do not rely on local developer builds as release evidence.
- Do not let packaging succeed if tests or dependency resolution are inconsistent.

#### Optional Anki

Q: Name core stages of a Java backend pipeline.
A: Compile, test, analyze, package, publish, deploy and verify.

</details>

<details>
<summary><strong>CICD-PIPE-002. What should run on every pull request versus only after merge?</strong></summary>

#### Short answer

Pull requests need fast confidence checks; after merge can run heavier publishing, deployment and broader verification.

#### Interview answer

On every PR, run compile, unit tests, targeted integration tests, formatting or lint checks, static analysis and relevant security checks. After merge, build the release artifact, run full integration or contract suites if needed, publish images, deploy to shared environments and run smoke tests.

#### Deep dive

The boundary depends on cost and risk. A small service may run almost everything on PRs, while a large monorepo may use affected-module detection and scheduled deeper checks.

#### Production angle

PR checks protect the main branch. Post-merge checks prove the actual merge commit, artifact and environment path are safe.

#### Traps / caveats

- Testing only the PR branch can miss merge-result failures.
- Publishing artifacts from untrusted PR code can expose secrets or credentials.

#### Optional Anki

Q: What is the usual split between PR and post-merge pipeline work?
A: PRs run fast validation; post-merge builds and promotes real release artifacts.

</details>

<details>
<summary><strong>CICD-PIPE-003. How do you design a pipeline that gives fast feedback without skipping important checks?</strong></summary>

#### Short answer

Use layered checks: fast required gates early, slower and broader checks later or only for affected areas.

#### Interview answer

I would separate the pipeline into quick PR feedback and deeper release confidence. Fast stages include compile, unit tests and static checks. Slower stages include full integration tests, contract tests, container scans, environment deploys and smoke tests.

#### Deep dive

Techniques include test splitting, parallel execution, affected-module selection, caching with validation, scheduled full suites and risk-based gates for high-impact changes.

#### Production angle

Fast feedback keeps developers from bypassing CI, while deeper gates protect production from integration and environment failures.

#### Traps / caveats

- Skipping slow tests permanently creates blind spots.
- Over-aggressive caching can hide dependency or generated-code problems.

#### Optional Anki

Q: How do you balance fast feedback and coverage?
A: Layer checks by speed and risk, and run deeper verification later in the pipeline.

</details>

<details>
<summary><strong>CICD-PIPE-004. Why should build, test, package and deploy stages be separated?</strong></summary>

#### Short answer

Separation makes failures clearer, artifacts reusable and deployments more controlled.

#### Interview answer

Build, test, package and deploy answer different questions. Build checks whether code compiles, tests check behavior, packaging creates a release artifact, and deployment changes an environment. Keeping them separate improves traceability and avoids rebuilding different artifacts for different environments.

#### Deep dive

A clean pipeline promotes the same artifact forward. Environment-specific differences should come from runtime configuration, not rebuilding code.

#### Production angle

During rollback or audit, separation helps prove which artifact was tested, signed, deployed and verified.

#### Traps / caveats

- Combining packaging and deployment can hide what was actually released.
- Rebuilding during deploy breaks reproducibility.

#### Optional Anki

Q: Why separate pipeline stages?
A: To improve traceability, failure isolation, artifact reuse and deployment control.

</details>

<details>
<summary><strong>CICD-PIPE-005. What is a quality gate in a deployment pipeline?</strong></summary>

#### Short answer

A quality gate is a required condition that must pass before a change can move to the next stage.

#### Interview answer

Quality gates can include tests, coverage thresholds, static analysis, dependency vulnerability policy, contract compatibility, image scanning, approval, smoke tests and SLO-based canary checks. A good gate is objective, visible and tied to production risk.

#### Deep dive

Gates should be risk-based. A formatting issue may block a PR, while a low-severity vulnerability might warn unless policy says otherwise.

#### Production angle

Quality gates prevent known bad releases from reaching production and create evidence for audit and incident review.

#### Traps / caveats

- Too many noisy gates train teams to ignore failures.
- A gate should have clear ownership and remediation guidance.

#### Optional Anki

Q: What is a pipeline quality gate?
A: A required check that controls whether a change can advance.

</details>

<details>
<summary><strong>🧠 CICD-PIPE-006. Which pipeline failures should block a merge, and which should only warn?</strong></summary>

#### Short answer

Block failures that indicate correctness, security, compatibility or release integrity risk; warn on low-risk, informational or non-actionable findings.

#### Interview answer

Compile failures, failing tests, broken contracts, critical vulnerabilities, secret leaks and packaging errors should block. Warnings may be appropriate for low-severity vulnerabilities, coverage drift, style issues during migration or non-critical quality trends, but only if there is an owner and policy.

#### Deep dive

The decision should depend on severity, exploitability, blast radius, false-positive rate and whether the finding is new or existing technical debt.

#### Production angle

Blocking everything can freeze delivery; blocking too little sends bad releases to production. Teams need explicit release policy, not ad hoc decisions.

#### Traps / caveats

- "Warning only" checks often become ignored checks.
- Critical security or compatibility failures should not depend on individual preference.

#### Optional Anki

Q: What pipeline failures should block?
A: Failures that threaten correctness, security, compatibility or artifact integrity.

</details>

<details>
<summary><strong>CICD-PIPE-007. How should pipeline logs and artifacts help developers debug failures?</strong></summary>

#### Short answer

They should make failures reproducible, searchable and tied to the exact commit, environment and artifact.

#### Interview answer

Useful pipeline output includes clear stage names, failing command, test reports, stack traces, dependency trees, generated reports, image digest, environment target and links to deployed versions. Logs should be structured enough to find the root cause without exposing secrets.

#### Deep dive

Artifacts such as JUnit reports, coverage reports, static analysis output, SBOMs and container scan results should be retained with the build.

#### Production angle

Good pipeline evidence reduces time to fix failed releases and helps incident review reconstruct what happened.

#### Traps / caveats

- Verbose logs that hide the first failure slow debugging.
- Logs must redact secrets, tokens, URLs with credentials and sensitive payloads.

#### Optional Anki

Q: What should CI logs and artifacts provide?
A: Clear failure context, reports, exact versions and safe debugging evidence.

</details>

<details>
<summary><strong>🧠 CICD-PIPE-008. How would you design a reusable CI/CD pipeline template for many Java microservices?</strong></summary>

#### Short answer

Create a shared template with sensible defaults, versioning, extension points and service-level configuration.

#### Interview answer

I would standardize wrapper-based Maven or Gradle builds, Java version setup, tests, reports, image build, scanning, artifact publishing, deployment and verification. Services should configure only what differs: module path, runtime image, deployment target, test profile and risk gates.

#### Deep dive

The template should be versioned and rolled out gradually. It should expose clear extension points instead of letting each service copy and mutate pipeline logic.

#### Production angle

Reusable templates improve governance and speed, but broken shared logic can affect many services, so changes need compatibility tests and staged rollout.

#### Traps / caveats

- Avoid a rigid template that cannot handle real service differences.
- Avoid copy-paste pipelines that drift silently across teams.

#### Optional Anki

Q: What makes a reusable pipeline template safe?
A: Versioning, defaults, extension points, staged rollout and clear service overrides.

</details>
