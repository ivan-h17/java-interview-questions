# Rollback, roll-forward, hotfixes and failed releases

---

<a id="cicd-fail-001"></a>

<details>
<summary><strong>CICD-FAIL-001. What should a rollback strategy include?</strong></summary>

#### Short answer

It should define what can be reverted, how to trigger it, how to verify it and what state cannot be undone automatically.

#### Interview answer

A rollback strategy should include previous artifact availability, deployment commands, config rollback, feature flag rollback, database migration constraints, smoke checks, monitoring and owner escalation. It should be tested before an incident.

#### Deep dive

Rollback is easy for stateless code and hard for state changes. Data migrations, external side effects and message processing often require roll-forward or repair.

#### Production angle

During an incident, a clear rollback plan reduces decision time and avoids improvising under pressure.

#### Traps / caveats

- Rolling back the app may not roll back database or cache state.
- If old artifacts are deleted, rollback may fail.

#### Optional Anki

Q: What should rollback planning cover beyond the old binary?
A: Config, flags, data, verification, owners and stateful side effects.

</details>

<a id="cicd-fail-002"></a>

<details>
<summary><strong>CICD-FAIL-002. When is roll-forward safer than rollback?</strong></summary>

#### Short answer

Roll-forward is safer when the system state has changed in a way the old version cannot handle.

#### Interview answer

If a release includes irreversible migrations, writes new data formats, publishes new events or triggers external side effects, going back to the old code may make things worse. A small forward patch can be safer if it restores compatibility or fixes the defect directly.

#### Deep dive

Roll-forward requires fast build and deploy capability, good tests and confidence that the patch addresses the actual problem.

#### Production angle

Payment, order and messaging systems often need repair or compensation instead of simple rollback.

#### Traps / caveats

- Roll-forward is risky if root cause is unknown.
- Rollback should still be available for purely stateless failures.

#### Optional Anki

Q: When is rollback unsafe?
A: When new state or side effects are incompatible with the old version.

</details>

<a id="cicd-fail-003"></a>

<details>
<summary><strong>CICD-FAIL-003. What should happen automatically when a deployment fails?</strong></summary>

#### Short answer

The pipeline should stop rollout, surface evidence, alert owners and optionally roll back if policy says it is safe.

#### Interview answer

On failure, the deployment system should mark the release failed, stop further promotion, preserve logs and events, notify the responsible team, and run diagnostic or rollback steps. Automatic rollback is useful only when the failure mode is understood and rollback is safe.

#### Deep dive

Kubernetes may report a rollout failure, but higher-level tooling usually decides whether to undo, retry or page someone.

#### Production angle

Automatic handling prevents partial unknown deployments and speeds recovery.

#### Traps / caveats

- Blind retry can worsen overload or repeat destructive side effects.
- Automatic rollback cannot fix broken database migrations.

#### Optional Anki

Q: What should a failed deployment trigger?
A: Stop, evidence capture, notification and safe rollback or investigation.

</details>

<a id="cicd-fail-004"></a>

<details>
<summary><strong>CICD-FAIL-004. How do you detect that a release is bad after it reaches production?</strong></summary>

#### Short answer

Watch version-attributed technical and business signals during and after rollout.

#### Interview answer

I would monitor error rate, latency, saturation, pod restarts, failed jobs, queue lag, database errors, dependency failures and key business metrics. These metrics should be labeled by version, environment and deployment.

#### Deep dive

Some bad releases do not fail health checks. They may corrupt data, drop messages, return wrong results or affect only one tenant.

#### Production angle

Detection should be tied to release automation so canaries and rollouts stop before broad exposure.

#### Traps / caveats

- Green health checks are not enough.
- Aggregate metrics can hide canary or tenant-specific failures.

#### Optional Anki

Q: What signals reveal a bad release?
A: Version-attributed errors, latency, saturation, restarts, queue lag and business metrics.

</details>

<a id="cicd-fail-005"></a>

<details>
<summary><strong>🧠 CICD-FAIL-005. What information should be available during a deployment incident?</strong></summary>

#### Short answer

The team needs release identity, change context, runtime evidence, ownership and recovery options.

#### Interview answer

Useful information includes deployed version, commit range, artifact digest, config and flag changes, migration status, deployment events, logs, metrics, traces, recent dependency changes, owners, approval history, rollback command and runbook.

#### Deep dive

This information should be linked from the release record or dashboard, not assembled manually from several tools during the incident.

#### Production angle

Fast access to release context reduces recovery time and prevents wrong rollback decisions.

#### Traps / caveats

- Do not expose secrets while collecting diagnostic context.
- Missing deployment labels make version-specific debugging much harder.

#### Optional Anki

Q: What release context matters during incidents?
A: Version, artifact, config, flags, migrations, telemetry, owners and recovery steps.

</details>

<a id="cicd-fail-006"></a>

<details>
<summary><strong>CICD-FAIL-006. How should a hotfix move from code change to production?</strong></summary>

#### Short answer

Through the same controlled pipeline, with scoped tests and expedited but visible approval.

#### Interview answer

A hotfix should be committed, reviewed if possible, built by CI, tested against the failing scenario, packaged as a traceable artifact and deployed with clear monitoring. The process can be faster, but it should not bypass version control, artifact tracking or basic safety checks.

#### Deep dive

After production recovery, the fix should be merged back into main and followed by a post-incident review if the issue was significant.

#### Production angle

Emergency changes are high risk because pressure encourages shortcuts.

#### Traps / caveats

- Manual server edits create untraceable drift.
- A hotfix that is not merged back can disappear in the next release.

#### Optional Anki

Q: Should hotfixes bypass CI?
A: No, they should use an expedited but controlled pipeline.

</details>

<a id="cicd-fail-007"></a>

<details>
<summary><strong>CICD-FAIL-007. Why should previous artifacts remain available after a release?</strong></summary>

#### Short answer

They are needed for rollback, audit, debugging and vulnerability comparison.

#### Interview answer

Keeping previous JARs, images, SBOMs, scan results and logs lets the team redeploy a known version, compare changes and prove what ran in production. Without retained artifacts, rollback may require rebuilding, which is unsafe during an incident.

#### Deep dive

Production artifacts should have stronger retention than temporary branch builds.

#### Production angle

If an image digest has been garbage-collected, the platform may not be able to roll back.

#### Traps / caveats

- Retention needs cost and compliance limits.
- Old artifacts may contain vulnerable dependencies, so access must be controlled.

#### Optional Anki

Q: Why keep previous release artifacts?
A: To support rollback, audit and incident investigation.

</details>

<a id="cicd-fail-008"></a>

<details>
<summary><strong>🧠 CICD-FAIL-008. How do you design a release process so failed deployments do not leave the system in an unknown state?</strong></summary>

#### Short answer

Make releases atomic where possible, observable, idempotent and explicit about state transitions.

#### Interview answer

I would use a deployment controller with clear rollout status, immutable artifacts, versioned config, migration tracking, health and smoke checks, automatic stop conditions and a defined recovery path. Each step should record success or failure and be safe to retry or resume.

#### Deep dive

Unknown state often appears when scripts partially apply changes without recording progress, or when app, database and infrastructure changes are interleaved without ownership.

#### Production angle

A known failed state is manageable; an unknown state causes long investigations and risky manual fixes.

#### Traps / caveats

- Idempotency matters for deploy scripts and migrations.
- Manual console changes during incident response must be recorded.

#### Optional Anki

Q: How do you avoid unknown release state?
A: Use traceable, idempotent, observable steps with explicit recovery paths.

</details>
