# Environment promotion, configuration and secrets

---

<a id="cicd-env-001"></a>

<details>
<summary><strong>CICD-ENV-001. How do environment-specific config and secrets fit into deployments?</strong></summary>

#### Short answer

The artifact should stay the same, while environment-specific config and secrets are supplied at runtime by controlled systems.

#### Interview answer

A Java service should not be rebuilt for dev, staging and production. The pipeline promotes one artifact and injects runtime configuration through environment variables, mounted files, config services, Kubernetes objects or cloud secret managers.

#### Deep dive

Non-sensitive config and secrets should have different storage, access and audit policies. Required configuration should be validated at startup.

#### Production angle

Many deployment failures come from missing or wrong environment values, not from code changes.

#### Traps / caveats

- Do not put secrets into images, Helm values or build logs.
- Runtime config must be compatible with the deployed app version.

#### Optional Anki

Q: What should vary between environments?
A: Runtime configuration and secrets, not the built artifact.

</details>

<a id="cicd-env-002"></a>

<details>
<summary><strong>CICD-ENV-002. What is the difference between build-time configuration and runtime configuration?</strong></summary>

#### Short answer

Build-time configuration affects artifact creation; runtime configuration affects behavior when the artifact runs.

#### Interview answer

Build-time values include compiler target, plugin versions, generated code options and image base. Runtime values include database URL, feature flags, credentials, timeouts and external endpoints. Production environment differences should usually be runtime configuration.

#### Deep dive

Mixing runtime concerns into build time creates environment-specific artifacts and weakens promotion.

#### Production angle

If production behavior depends on build-time profiles, staging may not test the same code path that production runs.

#### Traps / caveats

- Maven or Gradle profiles can accidentally change production behavior.
- Some optimizations or generated clients are legitimately build-time, so the boundary must be explicit.

#### Optional Anki

Q: What is runtime configuration?
A: Values supplied when the artifact runs, such as endpoints, credentials and feature flags.

</details>

<a id="cicd-env-003"></a>

<details>
<summary><strong>CICD-ENV-003. Why should production and staging be similar, and where is perfect parity unrealistic?</strong></summary>

#### Short answer

Similarity catches deployment assumptions early, but scale, data, traffic and access controls often differ.

#### Interview answer

Staging should mimic production deployment shape: same artifact type, config mechanism, secrets injection, database migration process, networking model and observability. Perfect parity is unrealistic because production has real data volume, traffic patterns, compliance constraints and cost limits.

#### Deep dive

The goal is risk-based parity, not expensive duplication. Match the parts most likely to break releases.

#### Production angle

If staging differs too much, a green staging deployment can still fail from missing config, blocked network paths or different database behavior.

#### Traps / caveats

- Staging with toy data can miss performance and query-plan issues.
- Production data should not be copied to staging without masking and governance.

#### Optional Anki

Q: What kind of parity matters most?
A: Parity in artifact, deployment mechanism, config, dependencies and observability.

</details>

<a id="cicd-env-004"></a>

<details>
<summary><strong>CICD-ENV-004. What is environment drift, and how can CI/CD detect it?</strong></summary>

#### Short answer

Environment drift is unintended difference between environments or declared infrastructure and actual state.

#### Interview answer

Drift can appear in Kubernetes manifests, config maps, secrets, database schema, feature flags, cloud resources, IAM roles or manually changed servers. CI/CD can detect it through IaC plans, config validation, schema checks, policy-as-code, deployment diffs and runtime metadata.

#### Deep dive

Drift often comes from emergency manual fixes, console edits, inconsistent pipelines or environment-specific workarounds.

#### Production angle

Drift makes releases unpredictable because staging no longer proves production behavior.

#### Traps / caveats

- Drift detection must avoid printing secrets.
- Some differences are intentional and should be documented, not treated as drift.

#### Optional Anki

Q: What is environment drift?
A: Unintended difference between expected and actual environment state.

</details>

<a id="cicd-env-005"></a>

<details>
<summary><strong>🧠 CICD-ENV-005. How should feature flags be promoted and cleaned up across environments?</strong></summary>

#### Short answer

Flags should be versioned or auditable, promoted deliberately, have safe defaults, and be removed after use.

#### Interview answer

Feature flags should have owners, purpose, default value, rollout plan, cleanup date and audit trail. Promotion should be controlled so staging and production flag states are intentional rather than accidental copies.

#### Deep dive

Release flags, ops flags and permission flags have different lifecycles. Temporary release flags should be removed once the rollout is complete.

#### Production angle

Stale flags create hidden behavior paths and make deployment incidents harder to reason about.

#### Traps / caveats

- Do not assume a flag state in staging matches production.
- Feature flags are not a replacement for authorization.

#### Optional Anki

Q: What is feature flag debt?
A: Old flags that remain in code and config after their purpose is gone.

</details>

<a id="cicd-env-006"></a>

<details>
<summary><strong>🧠 CICD-ENV-006. How should deployment pipelines handle secrets rotation?</strong></summary>

#### Short answer

Pipelines should support overlapping old and new secrets, validation, deployment order and rollback-safe cleanup.

#### Interview answer

Secret rotation often needs a dual-secret period: create new credential, update consumers, verify both old and new work, then revoke the old one. Pipelines should avoid logging secrets and should coordinate app restarts or reloads when clients cache credentials.

#### Deep dive

Database pools, Kafka clients, HTTP clients and SDK credential providers may not pick up new secrets until refresh or restart.

#### Production angle

Bad rotation can cause widespread connection failures even when the application code did not change.

#### Traps / caveats

- Revoking the old secret before all replicas update can cause downtime.
- Rollback must account for which secret each version can use.

#### Optional Anki

Q: What is the dual-secret rotation pattern?
A: Temporarily support old and new credentials until all clients move safely.

</details>

<details>
<summary><strong>🧠 CICD-ENV-007. How do you prevent environment-specific hacks from becoming hidden release dependencies?</strong></summary>

#### Short answer

Make differences explicit, reviewed, validated and owned instead of hidden in scripts or manual changes.

#### Interview answer

I would keep environment differences in versioned configuration or infrastructure definitions, document why they exist, validate them in CI, and expose non-sensitive effective config metadata. Temporary workarounds should have owners and removal dates.

#### Deep dive

Hidden dependencies include manual database grants, special DNS entries, one-off secrets, local files, patched containers or manually edited Kubernetes resources.

#### Production angle

Hidden environment hacks cause releases to pass in one environment and fail in another with no obvious code change.

#### Traps / caveats

- "Just for production" exceptions should be rare and visible.
- Do not reveal sensitive values while making config observable.

#### Optional Anki

Q: How do you control environment-specific differences?
A: Version them, review them, validate them and assign ownership.

</details>
