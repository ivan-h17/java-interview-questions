# Dates, numbers, enums and generic types

---

<a id="json-type-001"></a>

<details>
<summary><strong>JSON-TYPE-001. How should `LocalDate`, `Instant` and `OffsetDateTime` be serialized?</strong></summary>

#### Short answer

Use explicit, documented ISO-8601-style strings and choose the Java type that matches the meaning.

#### Interview answer

`LocalDate` is a calendar date without time or zone, such as a birth date. `Instant` is an absolute moment in UTC. `OffsetDateTime` carries date, time and an offset. JSON should represent them with clear string formats, not ambiguous local strings or framework defaults.

Register Java Time support and test the actual output.

#### Deep dive

Do not serialize time values as arbitrary timestamps unless the contract explicitly uses them. Human and business dates are often not instants.

#### Production angle

Bad date semantics cause timezone bugs, billing errors and confusing audit logs.

#### Traps / caveats

- `LocalDateTime` has no zone or offset.
- Server default timezone should not leak into API behavior.
- Timestamps as numbers need unit clarity: seconds, millis or nanos.

#### Optional Anki

Q: What does `Instant` represent?
A: An absolute moment on the timeline, typically serialized in UTC.

</details>

<a id="json-type-002"></a>

<details>
<summary><strong>JSON-TYPE-002. Why should API date/time formats be explicit?</strong></summary>

#### Short answer

Because clients and servers otherwise guess formats, time zones and precision differently.

#### Interview answer

Date/time values are contract-sensitive. The API should define the format, timezone/offset policy and precision. ISO-8601 strings are usually a good default because they are readable and widely supported.

Without explicit formats, framework upgrades or default timezone changes can change behavior.

#### Deep dive

Precision matters too. Some systems support nanoseconds, others truncate to milliseconds or seconds.

#### Production angle

Audit, ordering, retries, cache expiration and financial workflows can break from date/time ambiguity.

#### Traps / caveats

- Avoid locale-specific date strings.
- Do not mix UTC instants and local business dates.
- Test serialization and deserialization around DST boundaries.

#### Optional Anki

Q: Why document timestamp precision?
A: Different systems may truncate or compare timestamps differently.

</details>

<a id="json-type-003"></a>

<details>
<summary><strong>JSON-TYPE-003. How should time zones and offsets be handled in JSON APIs?</strong></summary>

#### Short answer

Use UTC instants for events and explicit zones or local dates for business rules that depend on location.

#### Interview answer

For audit timestamps and event times, serialize an `Instant` or offset timestamp consistently, often UTC. For business concepts like store opening date, payroll date or local appointment time, preserve the intended local date/time and zone information.

The type should match the domain meaning.

#### Deep dive

An offset is not the same as a time zone. A zone like `Europe/Berlin` has DST rules; an offset like `+02:00` only tells the offset at one moment.

#### Production angle

Misusing local time for global events creates ordering bugs and failed reconciliation.

#### Traps / caveats

- Do not use server local time implicitly.
- Offset and zone are different.
- DST transitions can create missing or duplicated local times.

#### Optional Anki

Q: What is safer for audit event timestamps?
A: An absolute instant, usually represented in UTC.

</details>

<a id="json-type-004"></a>

<details>
<summary><strong>JSON-TYPE-004. Why do Java Time types need appropriate Jackson module/configuration support?</strong></summary>

#### Short answer

Jackson needs Java Time support and configuration to serialize/deserialize `java.time` types correctly and consistently.

#### Interview answer

Java Time types are not old `Date` values. The mapper should register the Java Time module and configure whether dates are written as ISO strings or timestamps. Spring Boot usually handles this when dependencies and auto-configuration are correct.

Manual mappers can miss this setup.

#### Deep dive

Different mapper configuration can produce different shapes for the same type, such as strings versus arrays/numeric timestamps.

#### Production angle

Date format drift between MVC, HTTP clients and message producers causes integration failures.

#### Traps / caveats

- `new ObjectMapper()` may not have Java Time support.
- Do not rely on defaults without tests.
- Upgrades can change defaults or module behavior.

#### Optional Anki

Q: What module is commonly needed for `java.time`?
A: The Jackson Java Time module.

</details>

<a id="json-type-005"></a>

<details>
<summary><strong>JSON-TYPE-005. Why is `BigDecimal` usually preferred for money in JSON payloads?</strong></summary>

#### Short answer

Money needs decimal precision, and binary floating-point types like `double` can introduce rounding errors.

#### Interview answer

Financial values should not be represented in Java with `double` or `float` because many decimal values cannot be represented exactly. `BigDecimal` keeps decimal precision and scale under application control.

The API should also define currency and rounding rules.

#### Deep dive

Some APIs serialize money as decimal strings to avoid client-side JavaScript number precision issues. Others use integer minor units such as cents, if that fits all currencies.

#### Production angle

Rounding and precision bugs become reconciliation, billing and compliance problems.

#### Traps / caveats

- `BigDecimal.equals()` is scale-sensitive.
- Currency is part of the value.
- JavaScript clients may lose precision with large or precise numbers.

#### Optional Anki

Q: Why avoid `double` for money?
A: Binary floating-point cannot exactly represent many decimal amounts.

</details>

<a id="json-type-006"></a>

<details>
<summary><strong>JSON-TYPE-006. What precision problems can appear with JSON floating-point numbers?</strong></summary>

#### Short answer

JSON numbers do not define fixed precision, and clients may parse them into binary floating-point values that lose decimal or integer precision.

#### Interview answer

A server may send a decimal value, but a JavaScript client may parse it as a `Number`, which is floating-point. Decimal fractions and very large integers can lose precision. Java code can also accidentally bind to `double` instead of `BigDecimal`.

For money and exact values, use `BigDecimal`, strings or integer minor units by contract.

#### Deep dive

Precision problems are not only display issues. They affect comparisons, signatures, idempotency keys and calculations.

#### Production angle

APIs carrying money, IDs or measurements should explicitly define numeric representation.

#### Traps / caveats

- JSON number syntax does not guarantee Java `long` safety for all clients.
- Scientific notation may surprise clients.
- Decimal scale may matter in business rules.

#### Optional Anki

Q: Why can JSON decimals be risky for clients?
A: Clients may parse them into imprecise floating-point numbers.

</details>

<a id="json-type-007"></a>

<details>
<summary><strong>JSON-TYPE-007. Why can large numeric IDs be dangerous for JavaScript clients?</strong></summary>

#### Short answer

JavaScript numbers cannot safely represent all 64-bit integer IDs exactly.

#### Interview answer

If a Java service returns a `long` ID as a JSON number, JavaScript clients may parse it as a floating-point `Number` and lose precision for large values. The client can then send back a different ID.

For public APIs, large IDs are often serialized as strings.

#### Deep dive

The issue also affects caches, URLs, logs and signatures if values are normalized differently across clients.

#### Production angle

ID precision bugs can cause wrong-resource access or failed lookups.

#### Traps / caveats

- Database `BIGINT` does not mean every client can handle it as a number.
- Do not mix numeric and string ID formats casually.
- Document ID type consistently.

#### Optional Anki

Q: Common JSON representation for large public IDs?
A: String.

</details>

<a id="json-type-008"></a>

<details>
<summary><strong>JSON-TYPE-008. How do `@JsonValue`, `@JsonCreator` and custom mapping affect enum serialization?</strong></summary>

#### Short answer

They let an enum use explicit external values instead of default Java enum names.

#### Interview answer

`@JsonValue` can serialize an enum as a code or label. `@JsonCreator` can map that external value back to an enum. Custom serializers/deserializers can implement more complex mapping.

This is useful when API values must stay stable even if Java enum names change.

#### Deep dive

Enum mapping should handle unknown values deliberately. A code map should reject invalid values or map them to a known fallback only if the contract allows it.

#### Production angle

Stable enum codes reduce breaking changes when refactoring Java code.

#### Traps / caveats

- Do not serialize ordinal values.
- Ensure serialization and deserialization are symmetric.
- Fallback enum values can hide producer bugs.

#### Optional Anki

Q: What does `@JsonValue` do on an enum?
A: Defines the value used when serializing the enum.

</details>

<a id="json-type-009"></a>

<details>
<summary><strong>JSON-TYPE-009. How should APIs handle unknown enum values from clients or external systems?</strong></summary>

#### Short answer

For requests, usually reject unknown values clearly; for consuming external systems, tolerate or quarantine them according to contract.

#### Interview answer

If a client sends an unknown enum to your public API, that is usually a validation error. But when your service consumes another service's events or responses, unknown enum values can appear after producer upgrades. In that case, tolerant handling, `UNKNOWN` values or dead-letter processing may be appropriate.

The decision depends on whether you are producer, consumer or public API boundary.

#### Deep dive

Adding enum values can be backward-compatible for tolerant consumers but breaking for strict consumers.

#### Production angle

Unknown enum handling should be covered by contract tests and alerts, not discovered by consumer crashes.

#### Traps / caveats

- `UNKNOWN` fallback may hide important new states.
- Rejecting unknown values can block forward compatibility.
- Clients should not assume enum lists never grow.

#### Optional Anki

Q: Is adding an enum value always safe?
A: No, strict consumers may break.

</details>

<a id="json-type-010"></a>

<details>
<summary><strong>JSON-TYPE-010. How should `Optional`, `null`, empty collections and default values be handled in JSON?</strong></summary>

#### Short answer

Define separate semantics for absence, null, empty and default values; do not let framework defaults decide accidentally.

#### Interview answer

In JSON, absent fields, explicit nulls, empty arrays and default values are different. For responses, empty collections are often easier than null. For requests, null may be invalid, clear a value or mean something else depending on the operation.

Java `Optional` is usually not ideal as a DTO field; validation and explicit nullable fields are often clearer.

#### Deep dive

Defaults should be visible and tested. `@JsonInclude` affects output but does not define input semantics.

#### Production angle

Clear null/absence policy prevents data loss and client confusion.

#### Traps / caveats

- `Optional` fields can complicate binding.
- Primitive defaults hide missing input.
- Empty string is not the same as null.

#### Optional Anki

Q: Is empty array the same as null?
A: No, empty usually means known empty collection; null means no value.

</details>

<a id="json-type-011"></a>

<details>
<summary><strong>JSON-TYPE-011. How do generic types lose type information during deserialization?</strong></summary>

#### Short answer

Java type erasure removes generic type parameters at runtime unless the framework receives explicit type metadata.

#### Interview answer

If you deserialize into raw `List.class`, Jackson knows it needs a list but not the element type, so objects may become `LinkedHashMap`. To deserialize `List<UserDto>`, Jackson needs a full generic type token.

This is caused by Java generics erasure, not JSON itself.

#### Deep dive

The same issue appears in HTTP clients, wrappers like `ApiResponse<T>`, records with generic payloads and collections of maps.

#### Production angle

Wrong generic binding causes runtime `ClassCastException`, missing validation and broken client code.

#### Traps / caveats

- `Class<List<UserDto>>` is not available directly.
- Raw types hide type-safety problems.
- Nested generics need full type metadata.

#### Optional Anki

Q: Why does JSON sometimes deserialize to `List<LinkedHashMap>`?
A: The target element type was erased or not provided.

</details>

<a id="json-type-012"></a>

<details>
<summary><strong>JSON-TYPE-012. How do `TypeReference` and `JavaType` help with generic deserialization?</strong></summary>

#### Short answer

They provide Jackson with full generic target type information at runtime.

#### Interview answer

`TypeReference<List<UserDto>>` captures generic type information through an anonymous subclass. `JavaType` is Jackson's programmatic representation of a type, useful for dynamic generic construction.

Both tell Jackson the nested element types it cannot infer from `Class` alone.

#### Deep dive

`JavaType` is useful when types are known dynamically, such as `List<T>` where `T` is passed as a `Class`.

#### Production angle

Use these in reusable HTTP clients, event consumers and test utilities to avoid raw maps and unchecked casts.

#### Traps / caveats

- `TypeReference` must include the full generic type.
- Type tokens do not validate business semantics.
- Framework clients may have their own equivalent type token APIs.

#### Optional Anki

Q: What does `TypeReference<List<UserDto>>` preserve?
A: The list element type for runtime deserialization.

</details>

<details>
<summary><strong>JSON-TYPE-013. How can default locale, default charset or default time zone leak into JSON behavior?</strong></summary>

#### Short answer

Code that relies on JVM or OS defaults can format, parse or encode JSON differently across environments.

#### Interview answer

If date formatting uses the default timezone, a container setting can change timestamps. If number or date formatting uses the default locale, output may differ by region. If byte/string conversion uses a default charset, non-ASCII text can be corrupted.

JSON APIs should use explicit locale-neutral formats, UTF-8 and deliberate timezone handling.

#### Deep dive

The risk often enters through custom serializers, manual formatting or tests running under different environments.

#### Production angle

Set explicit serialization policies and include non-ASCII, timezone and locale-sensitive cases in tests.

#### Traps / caveats

- Server local timezone should not define API timestamps.
- Locale-specific formatting is bad for machine APIs.
- Default charset assumptions break cross-platform behavior.

#### Optional Anki

Q: What charset should JSON APIs normally use?
A: UTF-8.

</details>
