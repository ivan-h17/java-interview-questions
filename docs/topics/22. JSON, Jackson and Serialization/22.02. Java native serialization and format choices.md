# Java native serialization and format choices

---

<a id="json-ser-001"></a>

<details>
<summary><strong>JSON-SER-001. What is Java native serialization with `Serializable`?</strong></summary>

#### Short answer

Java native serialization is the built-in mechanism for converting `Serializable` object graphs to a JVM-specific byte stream and back.

#### Interview answer

A class implements `Serializable` to opt into Java's native object serialization. The runtime can write the object graph, including referenced serializable objects, to a byte stream and later reconstruct it.

It preserves Java object-oriented details better than JSON, but that also makes it tightly coupled to Java classes and risky across boundaries.

#### Deep dive

Java serialization can bypass constructors during deserialization and uses class metadata. It was historically used for RMI, sessions and caching, but modern backend systems usually prefer explicit formats such as JSON, Protobuf or Avro.

#### Production angle

Avoid it for public APIs, untrusted input and long-lived storage unless there is a strong legacy reason.

#### Traps / caveats

- `Serializable` is a marker interface, not a schema.
- Deserialization of untrusted data is dangerous.
- Class evolution is fragile.

#### Optional Anki

Q: What does `Serializable` enable?
A: Java native object serialization to and from a byte stream.

</details>

<a id="json-ser-002"></a>

<details>
<summary><strong>JSON-SER-002. How is Java native serialization different from JSON serialization with Jackson?</strong></summary>

#### Short answer

Java native serialization is JVM-specific object serialization; Jackson JSON serialization maps Java values to a language-neutral JSON data contract.

#### Interview answer

Java serialization writes class-based object graphs. Jackson writes JSON properties and values according to DTO shape, annotations and mapper configuration. JSON is readable and usable by many languages, while Java serialization is mostly useful only to compatible Java runtimes.

Jackson encourages explicit API contracts; Java serialization couples consumers to Java implementation details.

#### Deep dive

Jackson normally calls constructors, setters, getters or record constructors depending on configuration. Java deserialization can recreate objects without normal construction.

#### Production angle

Use JSON for REST APIs and external integrations; do not expose native Java serialization to clients.

#### Traps / caveats

- JSON does not preserve object identity unless explicitly modeled.
- Java serialization can serialize fields you did not intend to expose.
- Both require compatibility planning.

#### Optional Anki

Q: Which is language-neutral: Java native serialization or JSON?
A: JSON.

</details>

<a id="json-ser-003"></a>

<details>
<summary><strong>JSON-SER-003. Why is Java native serialization usually avoided for public APIs and long-lived storage?</strong></summary>

#### Short answer

It is Java-specific, fragile under class changes and unsafe for untrusted input.

#### Interview answer

Public APIs need stable, language-neutral contracts. Java serialization exposes implementation details like class names, fields and serial form. Refactoring packages, changing fields or changing class hierarchy can break compatibility.

Security is the bigger issue: deserializing untrusted byte streams can trigger gadget chains or unexpected code paths.

#### Deep dive

Long-lived storage also suffers because old data must remain readable after code changes. Schema-based or explicit formats are easier to migrate and inspect.

#### Production angle

Prefer JSON for external APIs, Avro/Protobuf for governed messages and explicit database schemas for storage.

#### Traps / caveats

- `serialVersionUID` does not make arbitrary class changes safe.
- Internal-only use still needs trust and version boundaries.
- Stored serialized blobs are hard to query and migrate.

#### Optional Anki

Q: Main reasons to avoid Java serialization for public APIs?
A: JVM coupling, brittle evolution and deserialization security risk.

</details>

<a id="json-ser-004"></a>

<details>
<summary><strong>JSON-SER-004. What is `serialVersionUID`, and what problem does it solve?</strong></summary>

#### Short answer

`serialVersionUID` is a version identifier used to check whether a serialized stream is compatible with the current class.

#### Interview answer

When Java deserializes an object, it compares the stream's `serialVersionUID` with the class's current value. If they differ, deserialization fails with `InvalidClassException`.

Defining it explicitly prevents the compiler from generating a value that changes unexpectedly after small code changes.

#### Deep dive

It only controls the compatibility check. It does not solve semantic compatibility, missing fields, renamed fields or broken invariants.

#### Production angle

If a system still uses Java serialization, explicit `serialVersionUID` and compatibility tests are important during deployments.

#### Traps / caveats

- Matching IDs do not guarantee correct behavior.
- Changing the ID forces old serialized data to fail.
- Prefer explicit schemas for long-lived contracts.

#### Optional Anki

Q: What exception appears when `serialVersionUID` is incompatible?
A: `InvalidClassException`.

</details>

<a id="json-ser-005"></a>

<details>
<summary><strong>JSON-SER-005. How do `transient`, `static` and `final` fields affect Java serialization?</strong></summary>

#### Short answer

`transient` fields are skipped, `static` fields are not part of instance state, and `final` fields can be serialized but may complicate evolution and invariants.

#### Interview answer

Java serialization stores object instance state. A `transient` field is excluded and will have its default value unless restored manually. `static` fields belong to the class, not the instance, so they are not serialized as object state. `final` fields can be part of serialized state, but deserialization does not follow normal constructor-based initialization.

#### Deep dive

If a skipped field is derived, sensitive or environment-specific, it may need recalculation in `readObject`. Otherwise the object may be restored in an invalid state.

#### Production angle

This matters for secrets, cached derived values and invariants in legacy serialized data.

#### Traps / caveats

- `transient` is not encryption; it only skips serialization.
- Missing transient fields may cause nulls after deserialization.
- Static configuration should not be expected in serialized blobs.

#### Optional Anki

Q: Does Java serialization store `static` fields?
A: No, they are class state, not instance state.

</details>

<a id="json-ser-006"></a>

<details>
<summary><strong>JSON-SER-006. How can Java serialization expose sensitive fields or break encapsulation?</strong></summary>

#### Short answer

It can serialize private object state directly, including fields not intended for external exposure.

#### Interview answer

Encapsulation controls normal access through methods, but serialization is a separate mechanism. A private token, password-like value, internal flag or derived field may be written unless marked `transient` or customized.

Deserialization can also create objects in states that normal constructors or setters would reject.

#### Deep dive

The serialized form becomes another public surface. If it crosses trust boundaries, attackers may inspect, tamper with or replay object state.

#### Production angle

Do not serialize security-sensitive domain objects blindly. Use explicit DTOs and avoid Java native serialization for untrusted data.

#### Traps / caveats

- Private does not mean not serialized.
- `transient` fields still need safe reinitialization.
- Serialized internal state can become a compatibility burden.

#### Optional Anki

Q: Can Java serialization include private fields?
A: Yes, unless excluded or customized.

</details>

<a id="json-ser-007"></a>

<details>
<summary><strong>JSON-SER-007. How can `writeObject`, `readObject`, `writeReplace` and `readResolve` customize Java serialization?</strong></summary>

#### Short answer

They are special hooks that customize what is written, how objects are restored, or which replacement object is serialized/deserialized.

#### Interview answer

`writeObject` and `readObject` let a serializable class control its serialized fields and restore transient or derived state. `writeReplace` can substitute another object before serialization. `readResolve` can replace the deserialized object, commonly used for singleton or canonical instances.

These hooks are powerful but easy to misuse.

#### Deep dive

They are invoked reflectively by the serialization mechanism with expected signatures. Bugs can break invariants or compatibility.

#### Production angle

In modern backend code, seeing many serialization hooks is often a sign of legacy complexity that needs careful tests.

#### Traps / caveats

- Wrong method signatures silently fail to act as hooks.
- Hooks do not make untrusted deserialization safe.
- `readResolve` is relevant for singletons and canonicalization.

#### Optional Anki

Q: Which hook can preserve singleton identity after deserialization?
A: `readResolve`.

</details>

<a id="json-ser-008"></a>

<details>
<summary><strong>JSON-SER-008. How can deserialization bypass constructors, break invariants or break a Singleton?</strong></summary>

#### Short answer

Java deserialization can recreate objects without running normal constructors, so constructor-enforced invariants and singleton identity can be bypassed.

#### Interview answer

If a class relies on its constructor to validate fields or register state, native deserialization may restore field values directly. That can create objects that normal code could never construct.

For singletons, deserialization can create a new instance unless `readResolve` or enum singletons are used.

#### Deep dive

This is one reason deserialization is treated as a security-sensitive boundary. Similar risks exist in other frameworks when binding bypasses domain factories or validation layers.

#### Production angle

Do not deserialize untrusted data into domain objects with important invariants. Use DTOs, validate them and then call domain logic intentionally.

#### Traps / caveats

- Constructor validation alone may not protect deserialization paths.
- Singleton classes need serialization-aware design.
- Reflection and framework binding can create similar invariant gaps.

#### Optional Anki

Q: Why can Java deserialization break a singleton?
A: It can create a new instance unless resolution logic prevents it.

</details>
