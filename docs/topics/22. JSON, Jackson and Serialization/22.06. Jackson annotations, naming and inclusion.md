# Jackson annotations, naming and inclusion

---

<a id="json-ann-001"></a>

<details>
<summary><strong>JSON-ANN-001. What do `@JsonProperty` and `@JsonAlias` do?</strong></summary>

#### Short answer

`@JsonProperty` defines the main JSON property name or access rules; `@JsonAlias` defines alternative input names accepted during deserialization.

#### Interview answer

Use `@JsonProperty` when the Java name and JSON name differ, or when a constructor parameter needs an explicit property name. `@JsonAlias` helps accept old or partner-specific field names while keeping one canonical output name.

This is useful for compatibility migrations.

#### Deep dive

`@JsonAlias` is typically for reading, not writing. The serialized field name remains the main property name.

#### Production angle

Aliases allow zero-downtime field renames, but they should be documented and eventually cleaned up if temporary.

#### Traps / caveats

- Too many aliases make contracts hard to reason about.
- `@JsonProperty` names become public API.
- Aliases do not solve semantic differences.

#### Optional Anki

Q: What is `@JsonAlias` mainly for?
A: Accepting alternative input property names.

</details>

<a id="json-ann-002"></a>

<details>
<summary><strong>JSON-ANN-002. What do `@JsonIgnore` and `@JsonIgnoreProperties` do?</strong></summary>

#### Short answer

They tell Jackson to ignore specific properties or groups of properties during serialization/deserialization.

#### Interview answer

`@JsonIgnore` usually applies to one property. `@JsonIgnoreProperties` can ignore several names and can also be used to ignore unknown input fields on a type.

They are useful for hiding internal fields or tolerating external payloads, but they are not a replacement for proper DTO design.

#### Deep dive

Ignoring a property can affect read, write or both depending on configuration and annotations. For read-only/write-only semantics, use explicit access settings when possible.

#### Production angle

Ignoring fields on entities can hide symptoms while the API remains coupled to persistence.

#### Traps / caveats

- Ignoring sensitive fields is not the only security control.
- Ignored input may make clients think a change was accepted.
- Global ignore policies can hide bugs.

#### Optional Anki

Q: What does `@JsonIgnoreProperties(ignoreUnknown = true)` do?
A: It ignores unknown JSON fields for that type during deserialization.

</details>

<a id="json-ann-003"></a>

<details>
<summary><strong>JSON-ANN-003. What does `@JsonInclude` control?</strong></summary>

#### Short answer

`@JsonInclude` controls which values are included in serialized JSON, such as nulls, empty values or defaults.

#### Interview answer

It is commonly used to omit null fields from responses or to skip empty collections. This changes response shape, so it should match the API contract.

For example, omitting null can reduce noise, but clients must handle absent fields correctly.

#### Deep dive

Inclusion can be configured globally, per class or per property. It mainly affects serialization, not validation or request semantics.

#### Production angle

Changing inclusion policy can break clients and snapshot tests.

#### Traps / caveats

- Omitted and explicit null are different.
- Empty collections may be easier for clients than absent collections.
- Do not use inclusion to hide security-sensitive data.

#### Optional Anki

Q: Does `@JsonInclude` primarily affect input or output?
A: Output serialization.

</details>

<a id="json-ann-004"></a>

<details>
<summary><strong>JSON-ANN-004. What does `@JsonFormat` control?</strong></summary>

#### Short answer

`@JsonFormat` customizes how a value is serialized or deserialized, often for dates, times, enums or numeric/text shapes.

#### Interview answer

Common uses are setting a date/time pattern, timezone, shape or enum representation. It can make one field use a specific API format without changing the global mapper.

Use it carefully because formats become part of the API contract.

#### Deep dive

For dates and times, prefer standard ISO-8601 formats where possible. Custom patterns increase parsing and compatibility risk.

#### Production angle

Field-level format changes can surprise clients if not documented and tested.

#### Traps / caveats

- Pattern timezones can be misunderstood.
- Custom date patterns are often less interoperable.
- Global and field-level format policies can conflict.

#### Optional Anki

Q: Common use of `@JsonFormat`?
A: Customizing date/time serialization format.

</details>

<a id="json-ann-005"></a>

<details>
<summary><strong>JSON-ANN-005. What are Jackson naming strategies, and when would you use `@JsonNaming`?</strong></summary>

#### Short answer

Naming strategies convert Java property names to JSON names, such as camelCase to snake_case.

#### Interview answer

A naming strategy lets Java code use normal Java naming while the API uses a different JSON convention. `@JsonNaming` applies a strategy to a class; global mapper configuration applies it broadly.

Use it when a contract consistently requires snake_case, kebab-case or another style.

#### Deep dive

Explicit `@JsonProperty` can override naming strategy for individual fields.

#### Production angle

Changing naming strategy after clients exist is a large breaking change.

#### Traps / caveats

- Do not mix conventions casually.
- Be careful with acronyms like `URL`, `ID` and `UUID`.
- Generated clients depend on stable field names.

#### Optional Anki

Q: What does a naming strategy change?
A: The mapping between Java property names and JSON field names.

</details>

<a id="json-ann-006"></a>

<details>
<summary><strong>JSON-ANN-006. How can Jackson control null handling with setters or configuration?</strong></summary>

#### Short answer

Jackson can decide whether null input is accepted, skipped, converted to empty values or rejected through annotations and mapper configuration.

#### Interview answer

For a property, null handling can be controlled with annotations such as `@JsonSetter(nulls = Nulls.SKIP)`, `Nulls.FAIL` or `Nulls.AS_EMPTY`, or through global mapper configuration. This is useful when null should not overwrite a default, when null collections should become empty, or when null should fail.

The policy should match the API's semantics.

#### Deep dive

Null input handling is separate from output inclusion. A field omitted from output does not define what input null means.

#### Production angle

Wrong null handling creates data loss in updates and inconsistent validation behavior.

#### Traps / caveats

- Skipping nulls can hide invalid client input.
- Converting null to empty may change domain meaning.
- Bean Validation should still enforce required values.

#### Optional Anki

Q: Is null input handling the same as `@JsonInclude`?
A: No, null input and output inclusion are separate concerns.

</details>

<a id="json-ann-007"></a>

<details>
<summary><strong>JSON-ANN-007. When would you use `@JsonAnyGetter` or `@JsonAnySetter`?</strong></summary>

#### Short answer

Use them for controlled dynamic properties that are stored in a map but appear as normal JSON fields.

#### Interview answer

`@JsonAnyGetter` exposes map entries as JSON properties. `@JsonAnySetter` captures unknown JSON properties into a map. They are useful for metadata, extension fields or partner-specific attributes.

They should be used carefully because they make the schema flexible.

#### Deep dive

Dynamic fields can conflict with real fields, bypass validation or make authorization harder.

#### Production angle

If dynamic attributes are exposed publicly, validate allowed names, value types and maximum size.

#### Traps / caveats

- Do not accept arbitrary dynamic fields without limits.
- Field name conflicts can be confusing.
- Generated API docs may not capture dynamic fields well.

#### Optional Anki

Q: What does `@JsonAnySetter` commonly capture?
A: Unknown JSON fields into a map.

</details>

<a id="json-ann-008"></a>

<details>
<summary><strong>JSON-ANN-008. When would you use `@JsonUnwrapped`, and what compatibility risks does it create?</strong></summary>

#### Short answer

`@JsonUnwrapped` flattens nested object properties into the parent JSON object, but it can create name collisions and brittle contracts.

#### Interview answer

It is useful when Java composition is internal but the JSON contract is flat. For example, an `Address` value object might be serialized as `street`, `city` and `zip` on the parent object.

The risk is that adding fields to the nested object can unexpectedly add top-level API fields or conflict with existing names.

#### Deep dive

Unwrapped properties also complicate partial updates, validation paths and schema documentation.

#### Production angle

Use explicit DTOs if the public shape is important or likely to evolve.

#### Traps / caveats

- Watch for property name collisions.
- Nested refactors can become public API changes.
- It can make errors and docs less clear.

#### Optional Anki

Q: Main risk of `@JsonUnwrapped`?
A: Flattened fields can collide and make internal changes affect public JSON.

</details>

<a id="json-ann-009"></a>

<details>
<summary><strong>JSON-ANN-009. What is `@JsonView`, and why should it be used carefully?</strong></summary>

#### Short answer

`@JsonView` selects different property sets for different serialization or deserialization views.

#### Interview answer

It can let one DTO serialize different fields for public, internal or admin views. The problem is that security and contract behavior become annotation-driven and easy to misconfigure.

For many APIs, separate DTOs are clearer.

#### Deep dive

Views can affect both read and write behavior. That makes validation and documentation more complex.

#### Production angle

Using views for authorization is risky unless thoroughly tested and centrally controlled.

#### Traps / caveats

- Do not rely on views as the only authorization mechanism.
- Views make OpenAPI documentation harder.
- Missing a view annotation can leak or hide fields.

#### Optional Anki

Q: Safer alternative to many `@JsonView` combinations?
A: Separate purpose-built DTOs.

</details>

<a id="json-ann-010"></a>

<details>
<summary><strong>JSON-ANN-010. How do custom serializers and deserializers work?</strong></summary>

#### Short answer

They are custom Jackson handlers that control how a type or property is written to JSON or read from JSON.

#### Interview answer

A custom serializer writes JSON tokens for a value. A custom deserializer reads JSON and constructs a Java value. They can be registered globally in a module or applied to a property/type with annotations.

They are useful for value objects, legacy formats or special external contracts.

#### Deep dive

Custom handlers should be small and well tested because they bypass many default assumptions. For complex domain construction, deserialization into a DTO plus service mapping may be cleaner.

#### Production angle

Custom serializers/deserializers become part of the API contract and can affect many endpoints if registered globally.

#### Traps / caveats

- Avoid embedding business logic in serializers.
- Handle nulls and invalid tokens explicitly.
- Global registration may have broad side effects.

#### Optional Anki

Q: When use a custom deserializer?
A: When default binding cannot read the required external format cleanly.

</details>

<a id="json-ann-011"></a>

<details>
<summary><strong>JSON-ANN-011. When would you use Jackson mix-ins instead of annotations on the target class?</strong></summary>

#### Short answer

Use mix-ins when you need Jackson annotations for a type you cannot or should not modify.

#### Interview answer

A mix-in lets you attach Jackson annotation behavior externally. This is useful for third-party classes, generated classes, shared domain types or cases where you do not want transport annotations inside the model.

It keeps the target class clean but makes serialization behavior less visible.

#### Deep dive

Mix-ins are registered on the mapper and can affect all serialization/deserialization of that type through that mapper.

#### Production angle

They are useful for integration layers, but tests must verify the mapper configuration that registers them.

#### Traps / caveats

- Behavior can be hard to discover.
- Different mappers may or may not have the mix-in.
- Overusing mix-ins can hide API design problems.

#### Optional Anki

Q: Why use a Jackson mix-in?
A: To add serialization annotations externally without editing the class.

</details>

<a id="json-ann-012"></a>

<details>
<summary><strong>JSON-ANN-012. How can annotation-heavy DTOs create maintenance problems or leak transport concerns into the domain model?</strong></summary>

#### Short answer

Too many annotations can make one class serve too many contracts and mix transport details into models that should stay independent.

#### Interview answer

A DTO with many naming, view, ignore, format, custom serializer and validation annotations becomes hard to reason about. If those annotations are on entities or domain objects, the domain model becomes coupled to JSON transport concerns.

Often the cleaner fix is separate DTOs per boundary or version.

#### Deep dive

Annotation-heavy classes often hide incompatible requirements: create vs update, public vs internal, admin vs user, v1 vs v2.

#### Production angle

The result is fragile API evolution, surprising field leaks and tests that only cover one view.

#### Traps / caveats

- Annotations are useful, but not a substitute for boundary design.
- One DTO for every use case becomes a maintenance trap.
- Keep domain invariants out of serialization glue.

#### Optional Anki

Q: What is a smell in DTO design?
A: One heavily annotated class trying to satisfy many different API contracts.

</details>
