<a id="json-spring-001"></a>

<details>
<summary><strong>JSON-SPRING-001. How does Spring MVC use Jackson for `@RequestBody` and `@ResponseBody`?</strong></summary>

#### Short answer

Spring MVC uses HTTP message converters, usually Jackson's JSON converter, to read `@RequestBody` values and write `@ResponseBody` responses.

#### Interview answer

When a controller parameter is annotated with `@RequestBody`, Spring chooses a message converter based on `Content-Type` and target type. For JSON, the Jackson converter deserializes the request body into the DTO.

For `@ResponseBody` or `@RestController`, Spring uses converters again, this time based on return value and `Accept` negotiation, to serialize the response.

#### Deep dive

This happens before controller method execution for request binding and after method return for response writing. Exceptions from parsing and binding should be mapped to client-friendly errors.

#### Production angle

The exact mapper configuration used by Spring MVC should match the rest of the service's JSON behavior.

#### Traps / caveats

- `@RequestBody` parsing errors are different from Bean Validation errors.
- Missing or wrong `Content-Type` can select the wrong converter or fail.
- Returning entities directly can trigger lazy loading during response writing.

#### Optional Anki

Q: What maps JSON request bodies in Spring MVC?
A: An HTTP message converter backed by Jackson.

</details>

<details>
<summary><strong>JSON-SPRING-002. What is a Jackson HTTP message converter responsible for?</strong></summary>

#### Short answer

It converts between HTTP message bodies and Java objects using Jackson.

#### Interview answer

The Jackson message converter reads JSON bytes from the request body and deserializes them into a Java target type. It also serializes controller return values into JSON response bodies.

It is selected based on media type, supported Java type and Spring's converter ordering.

#### Deep dive

Converters also interact with content negotiation, character encoding, error handling and streaming. In Spring Boot, the converter usually uses the application-configured `ObjectMapper`.

#### Production angle

Custom converters or custom mappers can accidentally change API behavior across endpoints.

#### Traps / caveats

- Converter selection depends on headers.
- Converter configuration is part of your API contract.
- Multiple converters can produce surprising behavior if ordered badly.

#### Optional Anki

Q: What does `MappingJackson2HttpMessageConverter` do?
A: Reads and writes JSON HTTP bodies using Jackson.

</details>

<details>
<summary><strong>JSON-SPRING-003. How does content negotiation affect JSON request and response handling?</strong></summary>

#### Short answer

`Content-Type` tells the server what the request body is; `Accept` tells the server what response formats the client can handle.

#### Interview answer

For JSON requests, clients should send `Content-Type: application/json`. Spring uses that to choose a reader. For responses, Spring considers the `Accept` header, return type and available converters to choose a media type.

Wrong headers can lead to 415 Unsupported Media Type, 406 Not Acceptable or unexpected response formats.

#### Deep dive

Content negotiation is not only syntax. Versioned media types and vendor media types can also influence serialization policy in mature APIs.

#### Production angle

Clients, tests and documentation should send realistic headers; otherwise behavior in production can differ from tests.

#### Traps / caveats

- `Accept: */*` can hide negotiation issues.
- Missing `Content-Type` can break request binding.
- Do not rely on file extensions for API negotiation.

#### Optional Anki

Q: Which header describes the request body format?
A: `Content-Type`.

</details>

<details>
<summary><strong>JSON-SPRING-004. How should Jackson be configured centrally in a Spring Boot application?</strong></summary>

#### Short answer

Use Spring Boot's Jackson auto-configuration, properties and customizers so MVC, clients and tests share consistent behavior.

#### Interview answer

In Spring Boot, prefer `application.yml` Jackson properties and `Jackson2ObjectMapperBuilderCustomizer` for application-wide settings. Register modules as beans or dependencies where Boot can discover them.

Avoid creating unrelated ad hoc mappers unless you have a separate contract with clear reasons.

#### Deep dive

Central settings usually include Java Time handling, naming strategy, inclusion, unknown properties, enum handling and serialization features.

#### Production angle

Central configuration prevents one endpoint or client from using different date, null or enum behavior.

#### Traps / caveats

- A custom `ObjectMapper` bean can disable or bypass Boot defaults if done carelessly.
- Tests should verify the real mapper.
- Library code should not silently create its own mapper.

#### Optional Anki

Q: Preferred Spring Boot hook for Jackson customization?
A: `Jackson2ObjectMapperBuilderCustomizer` or Boot Jackson properties.

</details>

<a id="json-spring-005"></a>

<details>
<summary><strong>JSON-SPRING-005. What risks appear when defining a custom mapper bean in Spring Boot?</strong></summary>

#### Short answer

A custom mapper can accidentally lose Boot's modules, features and consistency with MVC, clients and tests.

#### Interview answer

Spring Boot normally auto-configures a mapper with discovered modules and settings. If a team replaces it manually, they can lose Java Time support, naming policy, property inclusion, Kotlin or JDK8 modules and custom features.

The safer approach is usually to customize Boot's mapper instead of replacing it completely.

#### Deep dive

Multiple mapper beans also create ambiguity. Some libraries may use one mapper while MVC uses another.

#### Production angle

This often shows up as only some endpoints producing timestamps as arrays, rejecting unknown fields differently or failing on `Optional`.

#### Traps / caveats

- Avoid `new ObjectMapper()` in production code paths.
- Check which mapper Feign, Kafka, Redis or tests use.
- Keep custom mappers named and scoped if unavoidable.

#### Optional Anki

Q: Main risk of a hand-made Spring Boot `ObjectMapper`?
A: Losing auto-configured modules and consistent API behavior.

</details>

<a id="json-spring-006"></a>

<details>
<summary><strong>JSON-SPRING-006. How can different HTTP clients, Feign clients or message producers accidentally use different JSON configuration?</strong></summary>

#### Short answer

They may instantiate their own mappers or use library defaults instead of the application's configured mapper.

#### Interview answer

Spring MVC may use one mapper, while a Feign client, WebClient codec, Kafka serializer, Redis serializer or test helper uses another. If configuration differs, the same DTO can serialize dates, enums, nulls or unknown fields differently depending on the path.

Centralize mapper configuration or explicitly wire the same JSON policy into each boundary.

#### Deep dive

Sometimes the correct answer is not one global mapper, but one clearly named mapper per contract: public REST, internal events, legacy partner API and so on.

#### Production angle

Inconsistent serialization breaks integrations and makes replay/debugging confusing.

#### Traps / caveats

- Tests using a standalone mapper may not match MVC.
- Message serializers may not use Spring MVC's mapper.
- Contract-specific differences should be intentional and documented.

#### Optional Anki

Q: Why can the same DTO serialize differently in one app?
A: Different components may use different mapper configurations.

</details>

<a id="json-spring-007"></a>

<details>
<summary><strong>JSON-SPRING-007. How should JSON parse errors differ from validation errors in HTTP responses?</strong></summary>

#### Short answer

Parse errors mean the body could not be read as the expected JSON/type; validation errors mean it parsed but violated constraints.

#### Interview answer

A malformed JSON body, wrong token type or invalid date format should produce a parse/binding error, usually a 400 with a clear message. Bean Validation errors should identify invalid fields and constraints, also often 400 or 422 depending on API policy.

Keep the distinction because clients need different fixes.

#### Deep dive

In Spring, parse errors often appear as `HttpMessageNotReadableException`; validation errors may appear as method argument validation exceptions or binding exceptions.

#### Production angle

Error responses should include safe field paths and stable application error codes, not stack traces or raw sensitive payloads.

#### Traps / caveats

- Do not return 500 for bad client JSON.
- Do not expose internal class names.
- Avoid echoing secrets from rejected payloads.

#### Optional Anki

Q: What is the difference between parse and validation errors?
A: Parse fails to construct input; validation rejects constructed input.

</details>

<a id="json-spring-008"></a>

<details>
<summary><strong>JSON-SPRING-008. How do Jackson deserialization and Bean Validation interact in Spring MVC?</strong></summary>

#### Short answer

Spring first deserializes the JSON into the target object, then Bean Validation runs if the parameter is annotated with `@Valid` or `@Validated`.

#### Interview answer

Jackson handles syntax, JSON shape and Java binding. After binding succeeds, Bean Validation checks constraints such as `@NotNull`, `@Size`, `@Email` and cascaded `@Valid` nested objects.

If deserialization fails, validation usually does not run because there is no valid object to validate.

#### Deep dive

Constructor-thrown exceptions, invalid enum values and date parsing failures are binding problems. Missing fields that become `null` may be caught by `@NotNull` if validation runs.

#### Production angle

API error handling should make both cases client-friendly and consistent while preserving the distinction.

#### Traps / caveats

- `@Valid` is required on controller parameters for validation.
- `@Valid` is also needed for nested objects/collections.
- Primitive fields can hide missing values by defaulting to `0` or `false`.

#### Optional Anki

Q: Which happens first in Spring MVC: Jackson binding or Bean Validation?
A: Jackson binding happens first; validation runs after successful binding.

</details>

<details>
<summary><strong>JSON-SPRING-009. How can reactive JSON encoding or decoding affect memory use and backpressure?</strong></summary>

#### Short answer

Reactive stacks can stream data with backpressure, but collecting large JSON into objects, arrays or buffers can still cause memory pressure.

#### Interview answer

In WebFlux or reactive clients, codecs decode and encode JSON over reactive streams. If the API processes items incrementally, backpressure can help. But if the code aggregates a large body into a list, string or tree, it still buffers data in memory.

The JSON shape matters: one huge JSON array is harder to process incrementally than line-delimited JSON or paged responses.

#### Deep dive

Reactive does not make serialization free. CPU-heavy parsing still uses CPU, and blocking mapping code can harm event-loop threads.

#### Production angle

Set body-size limits, use streaming-friendly formats for large flows and monitor memory, allocation and event-loop blocking.

#### Traps / caveats

- Reactive is not automatic backpressure if you collect everything.
- Avoid blocking serialization work on event-loop threads.
- Test large payload behavior, not only happy-path small JSON.

#### Optional Anki

Q: Does reactive JSON automatically prevent memory issues?
A: No, buffering or collecting large payloads can still exhaust memory.

</details>
