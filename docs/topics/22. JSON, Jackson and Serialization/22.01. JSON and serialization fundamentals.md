# JSON and serialization fundamentals

---

<a id="json-fund-001"></a>

<details>
<summary><strong>JSON-FUND-001. What is the difference between serialization and deserialization?</strong></summary>

#### Short answer

Serialization converts an in-memory object to a transferable format; deserialization converts that format back into objects or data structures.

#### Interview answer

In Java backend work, serialization often means converting DTOs, events or responses into JSON, bytes or another wire format. Deserialization is the reverse: parsing a request body, message or file into Java objects.

The important point is that serialization crosses a boundary. The format becomes a contract, so field names, types, null handling and compatibility matter.

#### Deep dive

Serialization is not only a technical conversion. It can lose type information, object identity, methods, private invariants and Java-specific semantics. Deserialization should be treated as untrusted input handling.

#### Production angle

Many production bugs are boundary bugs: incompatible payloads, wrong dates, missing fields, unexpected nulls, enum changes or unsafe deserialization.

#### Traps / caveats

- Deserialized data is not automatically valid business data.
- Java objects and wire payloads do not have identical type systems.
- Never treat untrusted deserialization as harmless object construction.

#### Optional Anki

Q: What is serialization?
A: Converting an in-memory value into a transferable or storable format.

</details>

<details>
<summary><strong>JSON-FUND-002. What is JSON, and why is it common in backend APIs?</strong></summary>

#### Short answer

JSON is a simple text data format based on objects, arrays, strings, numbers, booleans and null; it is common because it is readable, language-neutral and well supported by web clients.

#### Interview answer

JSON is popular for REST APIs and service communication because browsers, JavaScript, mobile clients and backend frameworks all support it well. It is easy to inspect in logs, curl, tests and API documentation.

For Java services, Jackson commonly maps between JSON and DTOs.

#### Deep dive

JSON is not a full object model. It has no classes, methods, comments, date type, binary type, integer type distinction or object identity. Those semantics must be defined by the API contract.

#### Production angle

Its readability helps debugging, but JSON can be verbose and expensive for very large payloads or high-throughput messaging.

#### Traps / caveats

- JSON does not define domain validation.
- Date, money and enum formats are API decisions.
- Text readability does not make it safe to log raw payloads.

#### Optional Anki

Q: Why is JSON common in APIs?
A: It is language-neutral, readable and broadly supported by web tooling.

</details>

<details>
<summary><strong>JSON-FUND-003. What JSON value types exist?</strong></summary>

#### Short answer

JSON has objects, arrays, strings, numbers, booleans and null.

#### Interview answer

A JSON document is built from six value types: object, array, string, number, boolean and null. Objects contain string property names mapped to values. Arrays contain ordered values. Values can be nested.

Everything else, such as dates, UUIDs, enums, money and binary data, is represented using those basic types by convention.

#### Deep dive

JSON numbers do not distinguish Java types like `int`, `long`, `double` or `BigDecimal`. JSON strings are Unicode text, so special characters and escaping rules matter.

#### Production angle

APIs must document how business types are represented: timestamps as ISO-8601 strings, money as decimal strings or numbers, IDs as strings when JavaScript precision matters.

#### Traps / caveats

- JSON has no native date type.
- JSON has no native binary type.
- JSON object property names are strings.

#### Optional Anki

Q: What are the JSON value types?
A: Object, array, string, number, boolean and null.

</details>

<a id="json-fund-004"></a>

<details>
<summary><strong>JSON-FUND-004. How does the JSON data model differ from Java's type system?</strong></summary>

#### Short answer

JSON is a small data model, while Java has classes, interfaces, generics, methods, identity, visibility, primitive types and rich libraries.

#### Interview answer

JSON can represent nested values, but it does not know Java classes, constructors, method behavior, private fields, generics, object identity or inheritance. Jackson bridges this gap using declared Java types, annotations, modules and configuration.

That mapping is powerful but not automatic contract design.

#### Deep dive

Java can distinguish `int`, `long`, `BigDecimal`, `Instant`, `LocalDate`, enum constants and value objects. JSON usually represents those through numbers or strings. Some Java information, especially generic type parameters, may be erased unless explicit type metadata is supplied.

#### Production angle

Most compatibility issues happen when Java refactoring accidentally changes the external JSON shape.

#### Traps / caveats

- Renaming a Java field can rename JSON unless mapped explicitly.
- Java default values can hide missing JSON fields.
- Generic collections need full type information during deserialization.

#### Optional Anki

Q: Why is JSON-to-Java mapping not trivial?
A: JSON lacks many Java type-system concepts, so the mapping needs a contract and configuration.

</details>

<details>
<summary><strong>JSON-FUND-005. What is the difference between syntactically valid JSON and a semantically valid payload?</strong></summary>

#### Short answer

Syntactically valid JSON follows JSON grammar; semantically valid payloads also satisfy the API's expected fields, types, ranges and business rules.

#### Interview answer

`{"age": -5}` can be valid JSON syntax, but invalid for a user creation API. Similarly, a field may parse as a string but violate a UUID format, enum contract or domain rule.

Parsing only proves the payload is JSON. Validation proves it is acceptable input for this operation.

#### Deep dive

Validation often has layers: JSON parsing, DTO binding, Bean Validation, authorization checks and domain invariants. Each layer catches different problems.

#### Production angle

Good APIs return clear client errors for invalid input instead of allowing invalid state to reach services or the database.

#### Traps / caveats

- A successfully deserialized DTO can still be invalid.
- Bean Validation does not replace business validation.
- Do not expose raw parser internals in error responses.

#### Optional Anki

Q: Can valid JSON be invalid input?
A: Yes, syntax can be valid while API semantics are wrong.

</details>

<a id="json-fund-006"></a>

<details>
<summary><strong>JSON-FUND-006. What is JSON Schema, and when would you use it?</strong></summary>

#### Short answer

JSON Schema describes and validates JSON document structure: required fields, types, formats, ranges and allowed shapes.

#### Interview answer

I would use JSON Schema when a JSON contract needs machine-readable validation or documentation outside a single Java codebase: public APIs, partner integrations, config files, event payloads or contract tests.

It helps catch malformed payloads before business logic, but it does not replace domain rules.

#### Deep dive

JSON Schema can describe object properties, arrays, required fields, allowed values, numeric bounds and combinations of schemas. Some constraints, such as cross-resource authorization or database uniqueness, still belong in application logic.

#### Production angle

Schemas help align producers and consumers, especially when services are deployed independently.

#### Traps / caveats

- Keep schema and implementation from drifting.
- Format validation may vary by validator.
- Schema validation does not prove authorization or business correctness.

#### Optional Anki

Q: What does JSON Schema validate?
A: The structural and basic value constraints of JSON documents.

</details>

<a id="json-fund-007"></a>

<details>
<summary><strong>JSON-FUND-007. What are the trade-offs of schema-less JSON in microservice communication?</strong></summary>

#### Short answer

Schema-less JSON is flexible and easy to evolve informally, but it can hide incompatible changes until runtime.

#### Interview answer

The upside is low ceremony: producers can add fields and consumers can ignore what they do not need. The downside is weak guarantees. Renames, changed meanings, new required fields, type changes or enum changes can break consumers without compile-time feedback.

For important service contracts, use OpenAPI, JSON Schema, contract tests or schema-registry-like governance.

#### Deep dive

Tolerant readers are useful, but they must still validate the fields they rely on. Schema-less does not mean contract-less.

#### Production angle

Independent deployments need compatibility rules: additive changes are usually safer, removals and type changes need migration plans.

#### Traps / caveats

- Ignoring unknown fields helps forward compatibility but can hide client mistakes.
- Adding a required request field is a breaking change.
- Loose contracts can create inconsistent interpretation across services.

#### Optional Anki

Q: Main risk of schema-less JSON between services?
A: Runtime contract breakage that tests or compilers may not catch.

</details>

<a id="json-fund-008"></a>

<details>
<summary><strong>JSON-FUND-008. How does JSON differ from XML, Java native serialization, Protobuf and Avro?</strong></summary>

#### Short answer

JSON is readable and flexible; XML is more verbose and document-oriented; Java serialization is JVM-specific; Protobuf and Avro are compact schema-oriented formats.

#### Interview answer

JSON is a good default for public HTTP APIs because it is readable and widely supported. XML has namespaces, attributes and document features but is more verbose. Java native serialization is tightly coupled to Java classes and is risky for public boundaries. Protobuf and Avro are better for high-throughput messaging or strongly governed contracts because they are compact and schema-driven.

#### Deep dive

Format choice affects compatibility, tooling, performance, debuggability and governance. JSON is easy to inspect but less strict by default. Protobuf and Avro require schema discipline but give better binary efficiency and evolution rules.

#### Production angle

For REST APIs, JSON is often best. For Kafka topics with long-lived contracts and high volume, Avro or Protobuf may be better.

#### Traps / caveats

- Do not choose JSON only because it is familiar.
- Do not expose Java serialization across trust boundaries.
- Binary formats are not automatically easier to evolve; schemas still need discipline.

#### Optional Anki

Q: Why use Protobuf or Avro instead of JSON?
A: Compact payloads, explicit schemas and stronger compatibility governance.

</details>

<details>
<summary><strong>JSON-FUND-009. What is JSON canonicalization, and why can field order or formatting matter for signatures and caching?</strong></summary>

#### Short answer

Canonicalization produces a stable JSON representation so logically equal data has the same bytes for signing, hashing or cache keys.

#### Interview answer

JSON objects are conceptually unordered, and insignificant whitespace can vary. But signatures, hashes and byte-level cache keys depend on exact bytes. Canonicalization defines stable ordering, escaping, number formatting and whitespace so the same logical payload produces the same representation.

#### Deep dive

Without canonicalization, two services can serialize the same data differently: field order, pretty printing, numeric scale or escaping may differ. That breaks signatures and can reduce cache hits.

#### Production angle

Use a clear canonical format for signed webhooks, idempotency hashes, request fingerprints and cache keys.

#### Traps / caveats

- Do not rely on incidental `HashMap` iteration order.
- Pretty printing changes bytes.
- Signing parsed-and-reserialized JSON can invalidate signatures.

#### Optional Anki

Q: Why canonicalize JSON before signing?
A: So equivalent data produces stable bytes for the signature.

</details>

<details>
<summary><strong>JSON-FUND-010. How do character encoding and escaping affect JSON payloads?</strong></summary>

#### Short answer

JSON is text, usually UTF-8 in APIs, and escaping is needed so quotes, backslashes and control characters are represented safely.

#### Interview answer

A JSON parser needs bytes decoded with the right character encoding. For HTTP APIs, UTF-8 should be the expected standard. Inside JSON strings, characters such as quotes, backslashes and control characters must be escaped according to JSON rules.

A JSON serializer should handle this; manual string concatenation is dangerous.

#### Deep dive

Escaping for JSON is not the same as escaping for HTML, SQL, shell or JavaScript. A JSON string safely embedded in a JSON response may still be unsafe if later inserted into HTML without HTML escaping.

#### Production angle

Encoding mismatches cause corrupted text, failed parsing and signature mismatches. Logs and tests should include non-ASCII examples.

#### Traps / caveats

- Do not build JSON with string concatenation.
- JSON escaping does not prevent XSS in HTML contexts.
- Always set consistent request and response encodings.

#### Optional Anki

Q: What should build JSON strings with escaping?
A: A JSON serializer, not manual concatenation.

</details>
