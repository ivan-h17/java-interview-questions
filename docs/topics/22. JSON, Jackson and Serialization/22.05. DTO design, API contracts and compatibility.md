# DTO design, API contracts and compatibility

---

<a id="json-dto-001"></a>

<details>
<summary><strong>JSON-DTO-001. How should DTOs be designed for REST APIs?</strong></summary>

#### Short answer

DTOs should model the external API contract explicitly, not mirror entities or internal domain objects by default.

#### Interview answer

Good REST DTOs expose only the fields the operation needs, use stable field names, define null and optional semantics, and carry validation annotations appropriate for the boundary. Request DTOs should represent what the client may send. Response DTOs should represent what the service deliberately returns.

The DTO is part of the API contract, so it should evolve carefully.

#### Deep dive

DTOs can be records or classes. The important part is explicit shape, validation, compatibility and mapping at the boundary.

#### Production angle

Clear DTOs reduce accidental data exposure, mass assignment, lazy loading, N+1 queries and breaking API changes.

#### Traps / caveats

- Do not blindly mirror database tables.
- Avoid leaking internal IDs or flags unless required.
- Keep transport validation separate from core business invariants.

#### Optional Anki

Q: What should a DTO primarily model?
A: The API boundary contract.

</details>

<a id="json-dto-002"></a>

<details>
<summary><strong>JSON-DTO-002. Why should request DTOs often differ from response DTOs?</strong></summary>

#### Short answer

Requests describe what clients may send; responses describe what clients may see. Those are different permissions and contracts.

#### Interview answer

A create request might allow `name` and `email`, while the response includes `id`, `createdAt` and status. The client should not be able to set server-managed fields like owner, role, balance, audit fields or version.

Separate DTOs make allowed input and returned output explicit.

#### Deep dive

Trying to reuse one DTO often creates confusing annotations like read-only fields, write-only fields, nullable fields and validation groups. Sometimes that is acceptable, but separate DTOs are usually clearer.

#### Production angle

Separate request DTOs are a strong defense against over-posting and accidental privilege changes.

#### Traps / caveats

- Do not rely only on clients to omit protected fields.
- Response DTOs may contain derived or masked values.
- Validation rules often differ between create, update and response.

#### Optional Anki

Q: Why separate request and response DTOs?
A: They represent different contracts and permissions.

</details>

<a id="json-dto-003"></a>

<details>
<summary><strong>JSON-DTO-003. Why should APIs usually avoid exposing domain objects or persistence entities directly?</strong></summary>

#### Short answer

It couples the API to internal models and can leak data, trigger lazy loading, create recursion and break compatibility.

#### Interview answer

Domain objects and JPA entities exist for business logic and persistence. They may contain internal fields, bidirectional relationships, lazy associations and invariants that are not part of the public API. Returning them directly makes refactoring dangerous because internal changes become API changes.

Use DTOs or projections to define the boundary deliberately.

#### Deep dive

Annotations like `@JsonIgnore` can reduce symptoms, but they do not solve the architectural coupling.

#### Production angle

Entity serialization commonly causes N+1 queries, huge responses, `LazyInitializationException` and data leaks.

#### Traps / caveats

- Getters on entities can trigger database queries.
- Entity relationships rarely match API response shape.
- Security should not depend on serializer annotations alone.

#### Optional Anki

Q: Main reason not to expose entities directly?
A: It couples public JSON to persistence internals.

</details>

<a id="json-dto-004"></a>

<details>
<summary><strong>JSON-DTO-004. How should APIs handle unknown JSON fields?</strong></summary>

#### Short answer

Choose deliberately: ignore unknown fields for tolerant compatibility, or reject them for strict public input validation.

#### Interview answer

Ignoring unknown fields helps forward compatibility because newer clients can send fields older servers do not understand. Rejecting unknown fields catches typos, wrong clients and accidental contract drift.

For public write APIs, I often prefer strictness unless there is a clear versioning reason for tolerance. For consumers of external APIs, tolerant reading is usually useful.

#### Deep dive

The policy can differ by boundary: public REST request, internal event consumer, partner integration or admin import.

#### Production angle

Document the policy and test it. Silent unknown fields can make clients believe the server accepted a value that it ignored.

#### Traps / caveats

- Ignored fields can hide mass-assignment attempts.
- Strict rejection can hurt rolling upgrades.
- Unknown response fields should usually be tolerated by clients.

#### Optional Anki

Q: Why ignore unknown fields as a client?
A: To remain compatible with newer producers that add fields.

</details>

<a id="json-dto-005"></a>

<details>
<summary><strong>JSON-DTO-005. What compatibility risks exist when adding new JSON fields?</strong></summary>

#### Short answer

Adding optional response fields is usually safe, but adding required request fields or fields with new semantics can break clients.

#### Interview answer

For responses, clients following tolerant-reader behavior should ignore new fields. But fragile clients, strict snapshot tests or generated models can still break. For requests, adding a new required field is breaking because old clients will not send it.

Safe additions need defaults, optional semantics or versioning.

#### Deep dive

New fields can also affect authorization, caching, signatures, pagination payload size and mobile clients with older models.

#### Production angle

Roll out new fields with contract tests and observability. For required behavior, support old and new clients during migration.

#### Traps / caveats

- Adding a response field can leak sensitive data.
- Adding a field to a signed payload can break signatures.
- Adding a required request field is not backward-compatible.

#### Optional Anki

Q: Is adding a required request field backward-compatible?
A: No.

</details>

<a id="json-dto-006"></a>

<details>
<summary><strong>JSON-DTO-006. What compatibility risks exist when renaming or removing JSON fields?</strong></summary>

#### Short answer

Renaming or removing fields is usually breaking because existing clients may still read or send the old field.

#### Interview answer

Field names are part of the API contract. If a response field is removed, clients may fail or display missing data. If a request field is renamed, old clients keep sending the old name and the server may ignore or reject it.

Use aliases, dual-write/dual-read periods, deprecation and versioning when needed.

#### Deep dive

Jackson `@JsonAlias` can help read old names, but it does not automatically write both names or solve semantic migration.

#### Production angle

Renames need a migration plan, metrics for old-field usage and a removal date.

#### Traps / caveats

- Java refactoring can accidentally rename JSON.
- Removing a "unused" field may break unknown consumers.
- Aliases are usually input-only.

#### Optional Anki

Q: Are JSON field names part of the contract?
A: Yes.

</details>

<a id="json-dto-007"></a>

<details>
<summary><strong>JSON-DTO-007. What is the difference between an omitted field and a field explicitly set to `null`?</strong></summary>

#### Short answer

Omitted means the client did not send the field; explicit `null` means the client sent the field with no value.

#### Interview answer

For create requests, both may mean missing required data. For partial updates, the difference is critical: omitted may mean "leave unchanged", while `null` may mean "clear the value" or may be invalid.

The API must define this behavior.

#### Deep dive

Plain Java fields often cannot distinguish absent from null after binding. You may need patch models, `JsonNode`, wrappers, `Optional` carefully, or field masks.

#### Production angle

Ambiguous null handling causes accidental data loss during PATCH-like updates.

#### Traps / caveats

- `@JsonInclude` affects output, not necessarily input semantics.
- Primitive fields cannot represent null or missing.
- Do not infer patch semantics accidentally.

#### Optional Anki

Q: Why does absent vs null matter for PATCH?
A: Omitted can mean unchanged, while null may mean clear.

</details>

<a id="json-dto-008"></a>

<details>
<summary><strong>JSON-DTO-008. How should optional fields be represented in request and response payloads?</strong></summary>

#### Short answer

Use clear contract semantics: document whether optional fields may be absent, null, empty, or defaulted.

#### Interview answer

For responses, optional fields can be omitted or included as null, but the policy should be consistent. For requests, optional means the server can process the request without that field, not that any value is acceptable.

In Java DTOs, nullable reference types plus validation are common. `Optional` is usually better as a return type than as a DTO field, unless the team intentionally supports it.

#### Deep dive

Empty string, empty array, null and missing are different values. Treat them according to domain semantics.

#### Production angle

Clients need predictable payload shape. Inconsistent null/absence behavior creates fragile client code.

#### Traps / caveats

- Optional does not mean unvalidated.
- `Optional` fields in DTOs can complicate Jackson and Bean Validation.
- Empty collections are often easier for clients than null collections.

#### Optional Anki

Q: Does optional mean "any value is valid"?
A: No, it means the field is not required.

</details>

<a id="json-dto-009"></a>

<details>
<summary><strong>JSON-DTO-009. Why are partial updates tricky when JSON fields can be absent or `null`?</strong></summary>

#### Short answer

Because the server must distinguish "do not change", "set to null", "set to default" and "invalid value".

#### Interview answer

In a PATCH-like request, absent fields usually mean no change. Explicit null may mean clear the value, but only if the field is nullable and the operation allows clearing it. Primitive defaults like `0` and `false` can hide whether the client sent a value.

Use explicit patch DTOs, field masks, JSON Merge Patch or JSON Patch when appropriate.

#### Deep dive

Blindly mapping partial JSON onto an entity can overwrite existing values with nulls or defaults.

#### Production angle

Patch bugs are common sources of data loss and security issues.

#### Traps / caveats

- Do not deserialize PATCH directly into an entity.
- Do not use one DTO for create, replace and patch without clear semantics.
- Validate allowed fields and permissions per field.

#### Optional Anki

Q: Main risk of naive partial update binding?
A: Accidentally overwriting existing data.

</details>

<a id="json-dto-010"></a>

<details>
<summary><strong>JSON-DTO-010. How do request DTOs and read-only/write-only fields help prevent over-posting, mass assignment and data leaks?</strong></summary>

#### Short answer

They restrict what clients can set and what responses can expose.

#### Interview answer

Mass assignment happens when a client sends fields the server should control, such as `role`, `ownerId`, `status` or `balance`, and the application blindly binds them. Request DTOs should contain only writable fields. Jackson access settings such as `@JsonProperty(access = READ_ONLY)` and `WRITE_ONLY` can help, for example accepting a password but never serializing it back.

The strongest design is explicit command DTOs plus service-level authorization.

#### Deep dive

Jackson access controls are useful for DTO boundaries, but should not be the only security boundary.

#### Production angle

This prevents privilege escalation, excessive data exposure and accidental leaking of secrets.

#### Traps / caveats

- Do not bind request JSON directly to entities.
- Do not trust hidden UI fields.
- Serializer annotations do not replace authorization checks.

#### Optional Anki

Q: What is mass assignment?
A: Binding client-supplied fields to properties the client should not control.

</details>

<a id="json-dto-011"></a>

<details>
<summary><strong>JSON-DTO-011. How should enum values be modeled for long-term JSON API compatibility?</strong></summary>

#### Short answer

Use stable external values and define how clients should handle unknown or future values.

#### Interview answer

Serializing enum names is simple, but Java enum names become part of the API contract. If those names are likely to change, use stable codes or explicit external values. For public APIs, document allowed values and plan for unknown values.

Never rely on ordinal values in JSON APIs.

#### Deep dive

Sometimes representing an enum as an object is better when clients need labels, descriptions or deprecation metadata, but it increases payload size and complexity.

#### Production angle

Enum changes break clients surprisingly often, especially mobile apps and generated clients.

#### Traps / caveats

- Do not serialize enum ordinal values.
- Renaming a Java enum constant can be a breaking API change.
- Unknown enum values need a strategy.

#### Optional Anki

Q: Why avoid enum ordinals in JSON?
A: Reordering enum constants changes the wire value.

</details>

<a id="json-dto-012"></a>

<details>
<summary><strong>JSON-DTO-012. How should API teams deprecate or version JSON fields?</strong></summary>

#### Short answer

Deprecate with documentation, telemetry, compatibility windows and migration support before removal.

#### Interview answer

For a field migration, add the new field while still supporting the old one, update documentation and clients, monitor usage of the old field, then remove it only after the compatibility window. If behavior changes are large, create a new API version or media type.

Jackson aliases can help read old request names during migration.

#### Deep dive

Deprecation should include semantics, not only field name changes. A field with the same name but changed meaning is also a breaking change.

#### Production angle

Use contract tests and logs/metrics to verify old clients have moved before removal.

#### Traps / caveats

- Do not remove fields only because current frontend does not use them.
- Generated clients may fail on missing fields.
- Public API removals require stronger governance than internal APIs.

#### Optional Anki

Q: Safe rename strategy?
A: Support old and new names during migration, monitor usage, then remove later.

</details>

<a id="json-dto-013"></a>

<details>
<summary><strong>JSON-DTO-013. How can projections, field selection or flexible JSON shapes complicate authorization and compatibility?</strong></summary>

#### Short answer

They make response shape dynamic, so every selectable field must be checked for permissions, cost and compatibility.

#### Interview answer

Field selection can reduce payload size, but it can also expose fields that the endpoint normally hides. Authorization must be enforced per field or per projection, not only per resource. Dynamic shapes also complicate caching, documentation, generated clients and contract tests.

#### Deep dive

Graph-like field selection can trigger expensive joins, lazy loading or N+1 behavior if it is not tied to query planning.

#### Production angle

Limit allowed projections, validate requested fields and monitor expensive combinations.

#### Traps / caveats

- Do not let clients request arbitrary entity paths.
- Field selection affects cache keys.
- Hidden fields must remain hidden even if requested explicitly.

#### Optional Anki

Q: Main security risk of field selection?
A: Clients may request fields they are not authorized to see.

</details>

<a id="json-dto-014"></a>

<details>
<summary><strong>JSON-DTO-014. Which Jackson strictness and coercion settings matter for public API contracts?</strong></summary>

#### Short answer

Settings for unknown fields, nulls, trailing tokens, duplicate keys, scalar coercion, enum handling and creator properties can change what inputs the API accepts.

#### Interview answer

Jackson can be permissive: it may coerce strings to numbers, accept case-insensitive enums, ignore unknown fields or allow missing creator values depending on configuration. Public APIs should define these policies intentionally instead of inheriting accidental defaults.

Strict input handling catches client bugs early; tolerant reading helps compatibility where needed.

#### Deep dive

Important choices include `FAIL_ON_UNKNOWN_PROPERTIES`, `FAIL_ON_TRAILING_TOKENS`, `FAIL_ON_NULL_FOR_PRIMITIVES`, missing or null creator-property handling, scalar coercions such as accepting float-as-int, duplicate-key detection and unknown enum handling.

#### Production angle

Make strictness part of contract tests, especially before dependency upgrades.

#### Traps / caveats

- Changing strictness can be a breaking API change.
- Lenient parsing can hide bad clients.
- Strict parsing can break rolling upgrades if not planned.

#### Optional Anki

Q: Why do Jackson coercion settings matter?
A: They define which invalid-looking JSON values the API accepts.

</details>
