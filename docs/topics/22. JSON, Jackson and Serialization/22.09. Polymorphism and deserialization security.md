# Polymorphism and deserialization security

---

<a id="json-sec-001"></a>

<details>
<summary><strong>JSON-SEC-001. When would an API need polymorphic JSON?</strong></summary>

#### Short answer

When one field can contain several known shapes and the receiver needs to know which subtype to construct.

#### Interview answer

Polymorphic JSON appears in event payloads, payment methods, notification channels, rules, search filters or workflow actions. For example, a `paymentMethod` may be a card, bank account or wallet, each with different fields.

The API needs a discriminator field or another clear contract to identify the shape.

#### Deep dive

Polymorphism is useful when the variants are part of the public model. It is dangerous when it exposes Java class names or arbitrary implementation types.

#### Production angle

Polymorphic APIs need compatibility rules for adding new subtypes and client behavior for unknown types.

#### Traps / caveats

- Do not expose internal Java class names.
- Do not deserialize untrusted payloads into arbitrary subtypes.
- Adding a subtype can break strict clients.

#### Optional Anki

Q: What is a discriminator in polymorphic JSON?
A: A field that identifies which payload subtype/shape is present.

</details>

<a id="json-sec-002"></a>

<details>
<summary><strong>JSON-SEC-002. How do `@JsonTypeInfo` and `@JsonSubTypes` support polymorphic deserialization?</strong></summary>

#### Short answer

They tell Jackson how type metadata appears in JSON and which concrete subtypes are allowed.

#### Interview answer

`@JsonTypeInfo` defines how Jackson includes or reads type information, such as a discriminator property. `@JsonSubTypes` lists known subtype mappings. Together they allow an abstract base type or interface to deserialize into a concrete implementation.

For APIs, use stable logical names, not Java class names.

#### Deep dive

Polymorphism can also be configured with custom type resolvers or modules. The key is to keep the set of allowed types controlled.

#### Production angle

Subtype mappings are part of the API contract and should be tested with old/new clients.

#### Traps / caveats

- Type metadata shape is a contract.
- Avoid `Id.CLASS` for public or untrusted JSON.
- Unknown subtype behavior must be defined.

#### Optional Anki

Q: What does `@JsonSubTypes` define?
A: The concrete subtype mappings Jackson may use.

</details>

<a id="json-sec-003"></a>

<details>
<summary><strong>JSON-SEC-003. Why is exposing Java class names in JSON type metadata dangerous?</strong></summary>

#### Short answer

It leaks implementation details, couples clients to Java packages and can enable unsafe deserialization paths.

#### Interview answer

If JSON contains full class names, refactoring packages or classes becomes a breaking API change. It also reveals internal structure and may let attackers attempt to instantiate unexpected classes if validation is weak.

Use stable logical type names such as `"card"` or `"bank_account"` instead.

#### Deep dive

Class-name metadata turns a data contract into an implementation contract. That is the opposite of a stable public API.

#### Production angle

External payloads should be designed around domain concepts, not runtime implementation names.

#### Traps / caveats

- Class-name metadata makes migrations harder.
- It can expose internal libraries.
- It is especially risky with default typing.

#### Optional Anki

Q: Preferred polymorphic type id for APIs?
A: Stable logical discriminator values, not Java class names.

</details>

<a id="json-sec-004"></a>

<details>
<summary><strong>JSON-SEC-004. How does Jackson default typing become a security risk?</strong></summary>

#### Short answer

Default typing can allow type metadata to select many classes, which is dangerous when deserializing untrusted JSON.

#### Interview answer

Jackson default typing adds type information automatically for broad categories of values. If enabled too broadly, incoming JSON may influence which Java classes are instantiated. With vulnerable gadget classes on the classpath, that can become a deserialization attack.

Modern configurations should use allow-listed polymorphic type validation and narrow target types.

#### Deep dive

The risk is not "JSON is dangerous" by itself. The risk is combining untrusted input, broad type selection and gadget-capable classes.

#### Production angle

Avoid default typing for public request bodies. Prefer explicit DTOs and explicit subtype lists.

#### Traps / caveats

- Do not deserialize untrusted JSON into `Object`.
- Do not enable broad default typing casually.
- Dependency changes can add new gadget classes.

#### Optional Anki

Q: Why is broad default typing risky?
A: It may let input influence which Java classes are instantiated.

</details>

<a id="json-sec-005"></a>

<details>
<summary><strong>JSON-SEC-005. What is an allow-list approach for polymorphic subtype validation?</strong></summary>

#### Short answer

It accepts only known, intended subtypes instead of allowing arbitrary classes or packages.

#### Interview answer

For polymorphic deserialization, an allow-list defines exactly which logical subtypes are valid. The input discriminator maps to those subtypes only. Everything else is rejected.

This is safer than broad package-based or class-name based acceptance.

#### Deep dive

Allow-lists should be tied to API concepts: `"email"`, `"sms"`, `"push"`, not implementation class names.

#### Production angle

Adding a new subtype should be treated as a contract change with tests, docs and client readiness.

#### Traps / caveats

- Package-prefix checks can still be too broad.
- Unknown subtypes should fail safely or be quarantined.
- Keep subtype registration close to contract ownership.

#### Optional Anki

Q: What is safer than arbitrary polymorphic class loading?
A: An explicit allow-list of valid subtypes.

</details>

<a id="json-sec-006"></a>

<details>
<summary><strong>JSON-SEC-006. Why should untrusted JSON usually not be deserialized into arbitrary `Object` graphs?</strong></summary>

#### Short answer

Because arbitrary object graphs give attackers too much influence over types, memory shape and behavior.

#### Interview answer

A public API should bind JSON to known DTO types, not arbitrary `Object`, raw maps or polymorphic graphs. Known DTOs constrain fields, types and validation. Arbitrary graphs increase the risk of unsafe type selection, resource exhaustion and business logic bypass.

Even if there is no code execution issue, untyped data is hard to validate correctly.

#### Deep dive

`Map<String, Object>` may be acceptable for controlled metadata, but it needs limits and validation.

#### Production angle

Use explicit schemas and DTOs for trust boundaries. Quarantine unknown or dynamic payloads before processing.

#### Traps / caveats

- `Object` target types interact badly with default typing.
- Untyped data tends to spread casts and assumptions.
- Dynamic fields still need authorization and size limits.

#### Optional Anki

Q: Best target type for public request JSON?
A: A known request DTO, not arbitrary `Object`.

</details>

<a id="json-sec-007"></a>

<details>
<summary><strong>JSON-SEC-007. What is a deserialization gadget at a high level?</strong></summary>

#### Short answer

A gadget is a class or method chain that performs dangerous behavior when constructed or invoked during deserialization.

#### Interview answer

Some classes have methods that run during deserialization, property setting, finalization or other framework hooks. An attacker may craft input that causes a chain of such classes to execute unwanted behavior if the deserializer is allowed to instantiate them.

This is why untrusted deserialization must restrict types.

#### Deep dive

Gadget risk depends on the libraries on the classpath, deserializer features and reachable methods. It is not limited to one framework.

#### Production angle

Keep dependencies updated, avoid broad polymorphic typing and use allow-listed DTOs at boundaries.

#### Traps / caveats

- Adding dependencies can change gadget exposure.
- "Internal" endpoints can become externally reachable.
- Blocking one class is weaker than allow-listing valid types.

#### Optional Anki

Q: What makes gadget attacks possible?
A: Untrusted input controlling dangerous object construction or method chains.

</details>

<a id="json-sec-008"></a>

<details>
<summary><strong>JSON-SEC-008. How can large, deeply nested or malformed JSON become a resource-exhaustion risk, and how can limits be enforced?</strong></summary>

#### Short answer

Attackers can send payloads that consume too much CPU, memory or stack; enforce body size, nesting depth, token, string and processing limits.

#### Interview answer

JSON parsing is work. Huge arrays, deeply nested objects, long strings, duplicate fields or malformed payloads can tie up request threads, allocate memory and create GC pressure. The service should enforce HTTP body limits, parser constraints, request timeouts and validation limits.

For large legitimate payloads, use streaming or asynchronous import patterns.

#### Deep dive

Modern Jackson versions provide parser-level constraints such as `StreamReadConstraints`, and frameworks can also limit request body size. Infrastructure such as gateways should enforce limits too.

#### Production angle

Resource limits are security controls and reliability controls.

#### Traps / caveats

- Do not rely only on application validation after full parsing.
- Compression can hide very large decompressed payloads.
- Logging rejected payloads can create another resource leak.

#### Optional Anki

Q: Why are JSON size limits security features?
A: They prevent CPU and memory exhaustion from hostile or broken clients.

</details>

<a id="json-sec-009"></a>

<details>
<summary><strong>JSON-SEC-009. How can duplicate keys, trailing tokens or implicit coercions create security or correctness bugs?</strong></summary>

#### Short answer

They let clients send ambiguous or misleading payloads that different parsers or layers may interpret differently.

#### Interview answer

Duplicate keys can cause one layer to read the first value and another to use the last. Trailing tokens can hide extra data after a valid object. Implicit coercions can make `"false"`, `0`, empty strings or strings-as-numbers bind in surprising ways.

Strict parsing reduces ambiguity for public APIs. Relevant Jackson settings include trailing-token failure, duplicate detection and explicit coercion rules.

#### Deep dive

These issues matter when payloads are signed, validated by a gateway, logged, or processed by multiple services with different parser settings.

#### Production angle

Configure and test parser strictness for security-sensitive endpoints.

#### Traps / caveats

- Ambiguous JSON can bypass validation assumptions.
- Different languages may parse edge cases differently.
- Changing coercion policy can be a breaking change.

#### Optional Anki

Q: Why reject trailing tokens?
A: To ensure the whole request body is exactly the expected payload.

</details>

<a id="json-sec-010"></a>

<details>
<summary><strong>JSON-SEC-010. How can polymorphic JSON APIs hurt backward compatibility and client portability?</strong></summary>

#### Short answer

They require every client to understand type metadata, subtype shapes and future subtype behavior.

#### Interview answer

Polymorphic JSON is harder for clients than a flat stable shape. Generated clients need discriminator support. Mobile or third-party clients may fail when a new subtype appears. If the API uses Java-specific metadata, non-Java clients become tightly coupled to Java implementation details.

Keep discriminators stable and document unknown subtype behavior.

#### Deep dive

Sometimes separate endpoints or explicit command types are clearer than one highly polymorphic field.

#### Production angle

Subtype additions should go through compatibility review just like adding enum values.

#### Traps / caveats

- New subtype can be breaking for strict clients.
- Class-name metadata is not portable.
- Versioning polymorphic contracts is harder than versioning simple DTOs.

#### Optional Anki

Q: What should polymorphic APIs use for type metadata?
A: Stable logical discriminators.

</details>
