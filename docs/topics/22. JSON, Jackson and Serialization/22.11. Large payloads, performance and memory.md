# Large payloads, performance and memory

---

<a id="json-perf-001"></a>

<details>
<summary><strong>JSON-PERF-001. How should large JSON request payloads be handled?</strong></summary>

#### Short answer

Set size limits, validate early, stream when appropriate and consider asynchronous import workflows for very large data.

#### Interview answer

Large JSON payloads should not be accepted without limits. Configure HTTP body limits, timeouts and parser constraints. If the payload is a large array or file-like import, streaming parsing or upload-to-object-storage plus async processing may be better than binding everything into memory.

Also define partial failure and validation reporting.

#### Deep dive

A large JSON body often expands in memory because bytes become strings, nodes, DTOs and collections.

#### Production angle

Large payloads can exhaust request threads, heap and database resources. They need observability and backpressure.

#### Traps / caveats

- Do not log full large payloads.
- Do not process unbounded arrays synchronously by default.
- Compression can hide large decompressed bodies.

#### Optional Anki

Q: First control for large JSON requests?
A: Enforce request size and parser limits.

</details>

<a id="json-perf-002"></a>

<details>
<summary><strong>JSON-PERF-002. When should you use streaming JSON parsing instead of full data binding?</strong></summary>

#### Short answer

Use streaming when the payload is too large to hold comfortably in memory or can be processed item by item.

#### Interview answer

Full data binding is convenient for normal request DTOs. Streaming is better for large arrays, imports, exports, log processing or transformations where each item can be processed independently.

It reduces peak memory but increases code complexity.

#### Deep dive

A common pattern is streaming through an array and binding each item to a DTO separately, then validating and processing one item or batch at a time.

#### Production angle

Streaming helps avoid allocation spikes and GC pressure during large jobs.

#### Traps / caveats

- Streaming code must still validate structure and handle errors.
- Partial processing needs retry and idempotency design.
- Do not use streaming prematurely for small payloads.

#### Optional Anki

Q: Main trade-off of streaming JSON?
A: Lower memory use but more complex code.

</details>

<a id="json-perf-003"></a>

<details>
<summary><strong>JSON-PERF-003. What memory costs come from reading a whole payload into `JsonNode` or `String`?</strong></summary>

#### Short answer

It duplicates data in memory and creates additional objects beyond the raw request bytes.

#### Interview answer

If the server reads a request body into a `String`, it holds decoded text in memory. If it then parses into `JsonNode`, it creates a full tree of objects. If it later maps to DTOs, that is another object graph.

Peak memory can be several times larger than the payload size.

#### Deep dive

Large strings, arrays, node trees and DTO collections also increase GC work and can fragment memory.

#### Production angle

This matters for concurrent large requests, batch imports and endpoints returning huge responses.

#### Traps / caveats

- Payload size in bytes is not heap size.
- Pretty printing and logging add more copies.
- `JsonNode` flexibility has a memory cost.

#### Optional Anki

Q: Why can a 20 MB JSON request use much more than 20 MB heap?
A: Decoding, parsing and object graphs duplicate and expand the data.

</details>

<a id="json-perf-004"></a>

<details>
<summary><strong>JSON-PERF-004. Why can `writeValueAsString()` be worse than streaming directly to an output stream?</strong></summary>

#### Short answer

It builds the entire JSON response as a `String` before sending it, increasing memory and latency.

#### Interview answer

`writeValueAsString()` is fine for small values and tests, but for large responses it creates a complete string in memory. Streaming directly to the HTTP output stream or a file lets Jackson write incrementally and avoids one large intermediate string.

#### Deep dive

Large strings can create allocation spikes and require contiguous memory. They also delay first byte until the whole response is generated.

#### Production angle

For exports and large responses, stream output and use pagination when possible.

#### Traps / caveats

- Streaming response error handling is different once bytes are sent.
- Do not stream unbounded result sets from a transaction casually.
- Compression and buffering layers may still buffer data.

#### Optional Anki

Q: Why avoid `writeValueAsString()` for huge responses?
A: It materializes the entire JSON as one string in memory.

</details>

<a id="json-perf-005"></a>

<details>
<summary><strong>JSON-PERF-005. How does reusing a configured mapper affect performance?</strong></summary>

#### Short answer

Reusing a mapper preserves configuration and lets Jackson reuse serializer/deserializer caches.

#### Interview answer

Creating a new `ObjectMapper` repeatedly forces Jackson to rebuild configuration and introspect types again. A shared configured mapper avoids this overhead and keeps behavior consistent.

For per-type or per-use settings, use `ObjectReader` and `ObjectWriter`.

#### Deep dive

Mapper reuse is both a performance and correctness practice. It prevents accidental differences in date formats, modules and feature flags.

#### Production angle

Repeated mapper creation in hot paths can show up as CPU and allocation overhead.

#### Traps / caveats

- Configure the mapper before concurrent use.
- Do not mutate a shared mapper per request.
- Measure before optimizing less obvious Jackson internals.

#### Optional Anki

Q: Why reuse `ObjectMapper`?
A: It reuses configuration and caches.

</details>

<a id="json-perf-006"></a>

<details>
<summary><strong>JSON-PERF-006. When is base64-encoded binary data in JSON acceptable, and when should you use multipart uploads or object storage instead?</strong></summary>

#### Short answer

Base64 in JSON is acceptable for small binary values; large files should usually use multipart upload or object storage references.

#### Interview answer

Base64 makes binary data text-safe but increases size and requires the server to decode it, often after parsing the JSON. For small icons, tokens or compact blobs it can be acceptable. For large documents, images or videos, use multipart/form-data, direct object storage upload or a separate file endpoint.

#### Deep dive

Embedding large binary data in JSON makes validation, retry, logging and memory use worse.

#### Production angle

Large base64 JSON payloads can exceed request limits and create heap pressure.

#### Traps / caveats

- Do not log base64 payloads.
- Validate decoded size, not only encoded size.
- Use checksums and content-type validation for files.

#### Optional Anki

Q: Why is base64 not ideal for large files?
A: It increases payload size and usually forces buffering/decoding work.

</details>

<a id="json-perf-007"></a>

<details>
<summary><strong>JSON-PERF-007. How can JSON serialization/deserialization create allocation spikes and GC pressure?</strong></summary>

#### Short answer

Parsing and writing JSON create many temporary strings, arrays, DTOs, collections and buffers.

#### Interview answer

JSON processing allocates decoded text, token buffers, property names, object graphs, collections and output buffers. Large or complex payloads amplify this. If many requests do it concurrently, allocation rate rises and GC pressure increases.

The fix may be pagination, streaming, DTO simplification, mapper reuse or reducing unnecessary transformations.

#### Deep dive

Serialization hot spots often appear together with mapping layers, logging and validation allocations.

#### Production angle

Use JFR or allocation profiling to identify whether JSON is really the allocation source.

#### Traps / caveats

- CPU symptoms may actually be GC from allocation.
- Logging serialized payloads doubles work.
- Pretty printing costs extra bytes and CPU.

#### Optional Anki

Q: How to confirm JSON allocation pressure?
A: Use allocation profiling or JFR, not guesses.

</details>

<a id="json-perf-008"></a>

<details>
<summary><strong>JSON-PERF-008. How do payload shape, pagination and field selection affect JSON performance?</strong></summary>

#### Short answer

Large nested payloads, unbounded arrays and expensive fields increase serialization time, memory use and database work.

#### Interview answer

A flat, paginated response is easier to serialize than a huge nested graph. Field selection can reduce payload size, but it can also complicate caching, authorization and database fetch planning. Pagination prevents one request from forcing the service to serialize too much data.

#### Deep dive

Payload shape should align with query shape. Adding nested fields may require additional joins or batch loading.

#### Production angle

Response size metrics and query count tests help catch slow growth before incidents.

#### Traps / caveats

- Do not let clients request unlimited page sizes.
- Dynamic fields must affect cache keys.
- Nested response shape can create hidden N+1 queries.

#### Optional Anki

Q: Why paginate JSON responses?
A: To bound serialization, memory, network and database work.

</details>

<a id="json-perf-009"></a>

<details>
<summary><strong>JSON-PERF-009. How would you measure whether JSON processing is actually the bottleneck?</strong></summary>

#### Short answer

Profile CPU and allocation, measure payload size and compare time spent in database, mapping, serialization and network.

#### Interview answer

I would start with endpoint latency breakdown, request/response sizes and database timings. Then capture a JFR or profiler sample under representative load. If Jackson serialization/deserialization dominates CPU or allocation stacks, it is a real bottleneck.

I would also test with realistic payloads, not tiny samples.

#### Deep dive

Serialization may be blamed when the real issue is lazy loading, DTO mapping, compression, logging or client network speed.

#### Production angle

Add metrics for payload size, serialization time where appropriate, GC allocation rate and slow endpoint traces.

#### Traps / caveats

- Do not optimize Jackson before measuring.
- Include database queries triggered by serialization.
- Benchmark with production-like payload shapes.

#### Optional Anki

Q: What tools help identify JSON bottlenecks?
A: JFR, profilers, traces, payload-size metrics and query timing.

</details>

<a id="json-perf-010"></a>

<details>
<summary><strong>JSON-PERF-010. What role can Jackson performance modules or generated accessors play, and why should they be benchmarked?</strong></summary>

#### Short answer

They can reduce reflection/introspection overhead for some workloads, but benefits depend on payloads, JVM and configuration.

#### Interview answer

Jackson has optional modules and techniques that can speed up property access or serialization for certain classes. They may help high-throughput services, but they also add dependencies and can have compatibility constraints.

Benchmark with your DTOs and traffic before relying on them.

#### Deep dive

Often bigger gains come from reducing payload size, removing N+1 queries, avoiding repeated mapper creation or streaming large data.

#### Production angle

Performance modules should be validated during upgrades because behavior and compatibility can change.

#### Traps / caveats

- Microbenchmarks can mislead.
- Some modules may not support every Java language feature equally.
- Measure end-to-end latency and allocation, not only serialization time.

#### Optional Anki

Q: Should Jackson performance modules be added blindly?
A: No, benchmark with real payloads and constraints.

</details>
