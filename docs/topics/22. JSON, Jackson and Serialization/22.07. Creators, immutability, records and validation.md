# Creators, immutability, records and validation

---

<a id="json-create-001"></a>

<details>
<summary><strong>JSON-CREATE-001. How does Jackson deserialize a mutable POJO with a default constructor and setters?</strong></summary>

#### Short answer

It creates the object with the no-arg constructor, then sets properties through setters or fields.

#### Interview answer

For a typical mutable DTO, Jackson instantiates the class using a default constructor and then binds JSON properties to Java properties. It may call setters, assign visible fields, or use configured visibility rules.

This is simple and framework-friendly, but it allows temporarily incomplete objects during construction.

#### Deep dive

Validation usually runs after deserialization. Constructor invariants are not enforced unless the constructor or setters contain checks, and setter-based binding can leave invalid intermediate state.

#### Production angle

Mutable DTOs are fine for boundary models, but validate them before applying changes to domain objects.

#### Traps / caveats

- No-arg constructor DTOs can hide required fields.
- Setters can be called in framework-controlled order.
- Default primitive values can mask missing input.

#### Optional Anki

Q: How does Jackson bind a normal mutable DTO?
A: No-arg constructor first, then properties through setters or fields.

</details>

<details>
<summary><strong>JSON-CREATE-002. When would you use `@JsonCreator`?</strong></summary>

#### Short answer

Use `@JsonCreator` when Jackson needs an explicit constructor or factory method for deserialization.

#### Interview answer

`@JsonCreator` is useful for immutable classes, value objects, static factories or constructors where parameters should map directly to JSON properties. Combined with `@JsonProperty`, it tells Jackson how to create the object.

Records often need less annotation because their canonical constructor maps naturally.

#### Deep dive

Creator mode can be property-based or delegating. Property-based maps object fields to parameters. Delegating passes one JSON value into the creator.

#### Production angle

Use creators to keep DTOs immutable while still supporting JSON binding.

#### Traps / caveats

- Missing or null creator parameters must be handled deliberately.
- Constructor exceptions need clean API error mapping.
- Too much logic in creators can blur validation and domain boundaries.

#### Optional Anki

Q: What does `@JsonCreator` define?
A: How Jackson should construct an object during deserialization.

</details>

<a id="json-create-003"></a>

<details>
<summary><strong>JSON-CREATE-003. What is the difference between constructor-based and static-factory deserialization?</strong></summary>

#### Short answer

Constructor-based deserialization calls a constructor; static-factory deserialization calls a named static method that returns the object.

#### Interview answer

Constructor-based creation is direct and common for immutable DTOs. Static factories are useful when construction needs a meaningful name, normalization, subtype selection or a value-object style API.

Both can be annotated with `@JsonCreator`.

#### Deep dive

A factory can return cached or specialized instances, but that power can hide side effects. For request DTOs, keep construction simple and predictable.

#### Production angle

Prefer simple creator logic and push business decisions into services or domain factories after validation.

#### Traps / caveats

- Factories can hide complex behavior from API binding.
- Jackson needs clear parameter names or annotations.
- Creator exceptions should map to 400-style errors, not 500s.

#### Optional Anki

Q: Why use a static factory with Jackson?
A: To control or name object creation when a constructor is not ideal.

</details>

<a id="json-create-004"></a>

<details>
<summary><strong>JSON-CREATE-004. How do records work with Jackson serialization and deserialization?</strong></summary>

#### Short answer

Modern Jackson treats record components as properties and uses the canonical constructor for deserialization.

#### Interview answer

For serialization, Jackson calls record accessors like `id()` and `name()`. For deserialization, it maps JSON properties to record components and invokes the canonical constructor.

Records are good for DTOs when the API shape is explicit and stable.

#### Deep dive

Record component names become JSON property names unless changed by annotations or naming strategy. Missing, null or renamed fields should be tested.

#### Production angle

Records reduce boilerplate and accidental mutation, but they make constructor-based binding behavior important.

#### Traps / caveats

- Renaming a record component can break JSON.
- Primitive components hide missing values.
- Nested validation still needs `@Valid`.

#### Optional Anki

Q: How does Jackson deserialize a record?
A: By calling the canonical constructor with component values.

</details>

<a id="json-create-005"></a>

<details>
<summary><strong>JSON-CREATE-005. How can immutable DTOs with final fields be deserialized safely?</strong></summary>

#### Short answer

Use constructor/creator binding, records or builder-based binding, then validate the constructed object.

#### Interview answer

Immutable DTOs should receive all required values through a constructor, record canonical constructor or builder. Jackson can map JSON properties to those inputs. This avoids setter-based mutation and makes required shape more visible.

Validation should still run after binding, and constructor checks should produce client-friendly errors.

#### Deep dive

Immutable DTOs are not automatically valid. They can still contain nulls, defaults or inconsistent field combinations if validation is missing.

#### Production angle

Immutable request models are easier to reason about in async code, tests and service mapping.

#### Traps / caveats

- Final fields do not define API requiredness by themselves.
- Defaults must be explicit.
- Constructor binding needs stable property names.

#### Optional Anki

Q: Safe way to bind immutable DTOs?
A: Constructor, record or builder-based binding with validation.

</details>

<a id="json-create-006"></a>

<details>
<summary><strong>JSON-CREATE-006. How can Jackson work with builder-based DTOs, including Lombok builders?</strong></summary>

#### Short answer

Jackson can deserialize through a builder when the class is annotated/configured to identify the builder and its methods.

#### Interview answer

Builder-based DTOs are useful for immutable objects with many optional fields. Jackson can use a builder if it knows the builder class, method prefixes and build method. Lombok can generate builders, but Jackson integration usually needs the right Lombok/Jackson annotations, commonly `@Jacksonized` with Lombok builders.

#### Deep dive

Builder method names may not match Jackson defaults. For Lombok, generated code should be inspected or tested because annotation placement, builder defaults and prefix configuration matter.

#### Production angle

Builder DTOs should have serialization tests for missing fields, nulls and defaults.

#### Traps / caveats

- Generated builders can hide requiredness.
- Defaults in Lombok builders need care.
- Do not put business workflows in DTO builders.

#### Optional Anki

Q: Why test builder-based Jackson DTOs?
A: Generated builder methods and defaults can bind differently than expected.

</details>

<a id="json-create-007"></a>

<details>
<summary><strong>JSON-CREATE-007. How should default values be handled during deserialization?</strong></summary>

#### Short answer

Defaults should be explicit, documented and tested for missing fields, null fields and old clients.

#### Interview answer

Default values can live in field initializers, constructors, builders, service logic or database defaults. For API DTOs, prefer defaults that are visible and match the contract. Be clear whether a missing field uses a default, while explicit null is rejected or handled differently.

#### Deep dive

Jackson may bypass some default mechanisms depending on constructor, builder or setter binding. Lombok builder defaults are a common source of surprises.

#### Production angle

Defaults are often used for backward compatibility when adding optional request fields.

#### Traps / caveats

- Primitive defaults can hide missing data.
- Null may override a default unless configured otherwise.
- Database defaults do not help validation before persistence.

#### Optional Anki

Q: What should be tested with defaults?
A: Missing field, explicit null and explicit value.

</details>

<a id="json-create-008"></a>

<details>
<summary><strong>JSON-CREATE-008. How should required fields be validated after deserialization?</strong></summary>

#### Short answer

Use Bean Validation for boundary constraints and service/domain validation for business invariants.

#### Interview answer

After Jackson creates the DTO, Spring can run Bean Validation with `@Valid` or `@Validated`. Use annotations like `@NotNull`, `@NotBlank`, `@Size` and `@Valid` for nested objects. Then the service layer should enforce rules that depend on state, permissions or database data.

#### Deep dive

Requiredness can mean syntactically required for the API, required for a specific operation, or required for a domain transition. Keep those levels clear.

#### Production angle

Good validation produces stable field-level errors and prevents invalid data from reaching the database.

#### Traps / caveats

- `@NotNull` does not reject blank strings.
- Nested validation requires `@Valid`.
- Constructor exceptions may bypass standard validation formatting.

#### Optional Anki

Q: What enables validation of nested DTOs?
A: `@Valid` on the nested field/component.

</details>

<a id="json-create-009"></a>

<details>
<summary><strong>JSON-CREATE-009. How can missing fields, `null` values and primitive defaults break constructor-based DTOs?</strong></summary>

#### Short answer

Missing or null inputs can become nulls, default primitive values, creator failures or invalid objects depending on type and configuration.

#### Interview answer

Constructor-based DTOs make required fields visible, but Jackson still needs values for parameters. A missing `String` may become null unless rejected. A missing `int` may become `0`, which can look like a real value. Explicit null for a primitive may fail or become a default depending on settings.

Use wrapper types for nullable values and validation for requiredness.

#### Deep dive

Creator-property strictness settings can turn some missing/null creator values into binding errors. The team should configure and test the desired behavior.

#### Production angle

This is a common source of bad requests being accepted as valid business commands.

#### Traps / caveats

- Primitive DTO fields are dangerous for required input.
- Null and missing are not the same.
- Constructor binding still needs validation.

#### Optional Anki

Q: Why avoid primitive request DTO fields for required values?
A: Missing input can become a misleading default like `0` or `false`.

</details>

<details>
<summary><strong>JSON-CREATE-010. How can deserialization break business invariants when validation is placed in the wrong layer?</strong></summary>

#### Short answer

If JSON binding creates domain objects directly, it may bypass factories, permissions, workflows or invariants that services should enforce.

#### Interview answer

Business invariants often depend on current state, user permissions, database data or workflow transitions. If a request is deserialized directly into a domain object or entity, the client may set fields that should only be changed through domain behavior.

The safer path is request DTO -> validation -> service authorization -> domain method/factory.

#### Deep dive

Constructor validation catches local invariants, but not cross-aggregate rules, ownership or state transitions.

#### Production angle

Misplaced validation leads to privilege bugs, invalid state and inconsistent behavior across endpoints.

#### Traps / caveats

- Domain objects are not request DTOs.
- Bean Validation is not authorization.
- Deserialization should not perform business workflows.

#### Optional Anki

Q: Safer input flow?
A: DTO binding, validation, authorization, then domain logic.

</details>
