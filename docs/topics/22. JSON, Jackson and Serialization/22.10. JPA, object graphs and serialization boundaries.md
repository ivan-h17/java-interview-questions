# JPA, object graphs and serialization boundaries

---

<a id="json-jpa-001"></a>

<details>
<summary><strong>JSON-JPA-001. Why should REST controllers map JPA entities to DTOs before JSON serialization?</strong></summary>

#### Short answer

DTO mapping creates a deliberate API shape and avoids exposing persistence internals, lazy associations and internal fields.

#### Interview answer

JPA entities are designed for persistence, not JSON APIs. They may include lazy relationships, bidirectional graphs, audit fields, version fields, internal IDs and fields clients should never see. Mapping to DTOs lets the service choose exactly what leaves the boundary.

It also decouples API evolution from database mapping.

#### Deep dive

Mapping should happen while required data is available, usually within a service transaction or through query projections.

#### Production angle

DTO mapping prevents common incidents: data leaks, huge payloads, N+1 queries and `LazyInitializationException`.

#### Traps / caveats

- `@JsonIgnore` on entities is a patch, not a boundary.
- Mapping can still cause N+1 if fetch plans are bad.
- Do not deserialize request JSON directly into entities.

#### Optional Anki

Q: Why map entities to DTOs?
A: To define an explicit API contract and avoid persistence leaks.

</details>

<a id="json-jpa-002"></a>

<details>
<summary><strong>JSON-JPA-002. How can JSON serialization accidentally trigger lazy loading?</strong></summary>

#### Short answer

Jackson calls getters, and entity getters may initialize lazy associations.

#### Interview answer

When Jackson serializes an entity, it introspects properties and calls accessors. If a getter returns a lazy collection or proxy, Hibernate may load it from the database. If the session is closed, serialization may fail. If Open Session in View is enabled, it may execute SQL during response serialization.

#### Deep dive

This makes database access depend on the JSON shape and serializer traversal, not explicit service logic.

#### Production angle

Serialization-triggered lazy loading can create latency spikes and unexpected database load.

#### Traps / caveats

- Getters are not harmless on entities.
- OSIV can hide the problem until traffic grows.
- Logging or debugging entity `toString()` can trigger similar issues.

#### Optional Anki

Q: Why can Jackson trigger lazy loading?
A: It calls entity accessors that initialize lazy proxies/collections.

</details>

<a id="json-jpa-003"></a>

<details>
<summary><strong>JSON-JPA-003. How can JSON serialization create N+1 query problems?</strong></summary>

#### Short answer

Serializing a list of entities can touch lazy associations one row at a time, causing one query per entity.

#### Interview answer

If an endpoint returns 100 orders and JSON serialization accesses `order.customer` or `order.items`, Hibernate may load those associations lazily for each order. That turns one query into many queries.

The fix is explicit DTO projections, fetch joins, entity graphs or batch fetching based on the response shape.

#### Deep dive

N+1 can be hidden in mapping code too. The important principle is that query shape and response shape must align.

#### Production angle

N+1 during serialization commonly appears as slow endpoints and database saturation after adding a response field.

#### Traps / caveats

- Adding a JSON field can add database queries.
- OSIV can hide query origin.
- Caching may mask N+1 in tests.

#### Optional Anki

Q: How can adding a response field cause N+1?
A: It may access a lazy association per row during serialization or mapping.

</details>

<a id="json-jpa-004"></a>

<details>
<summary><strong>JSON-JPA-004. How do cyclic references happen in JSON serialization?</strong></summary>

#### Short answer

Bidirectional object graphs can reference each other, causing serializers to walk in circles.

#### Interview answer

For example, `Order` has `customer`, and `Customer` has `orders`. If Jackson serializes both directions naively, it can recurse indefinitely or produce huge nested JSON.

The better design is usually a DTO that cuts the graph at intentional boundaries.

#### Deep dive

Object graphs and JSON trees are different. JSON is a tree-like representation, while Java entity graphs can have cycles and shared references.

#### Production angle

Cyclic serialization can cause stack overflows, large responses and accidental exposure of unrelated data.

#### Traps / caveats

- Bidirectional JPA relationships are common.
- `toString()`, logging and debugging can have similar recursion.
- Identity annotations solve serialization shape, not API design.

#### Optional Anki

Q: Why do entity cycles break JSON serialization?
A: JSON serialization may recursively traverse bidirectional references.

</details>

<a id="json-jpa-005"></a>

<details>
<summary><strong>JSON-JPA-005. How do `@JsonManagedReference`, `@JsonBackReference` and `@JsonIdentityInfo` address cyclic references?</strong></summary>

#### Short answer

Managed/back references serialize one direction and suppress the back direction; identity info serializes object references by identity.

#### Interview answer

`@JsonManagedReference` and `@JsonBackReference` are paired annotations for parent-child relationships. They prevent walking back from child to parent. `@JsonIdentityInfo` writes identity metadata so repeated objects can be referenced instead of fully nested.

These tools solve recursion symptoms, but DTOs are often cleaner for APIs.

#### Deep dive

Identity-based JSON can be harder for clients to consume because it introduces reference semantics into the payload.

#### Production angle

Use these annotations carefully for internal serialization or simple cases, not as a substitute for API boundary design.

#### Traps / caveats

- They can make JSON shape surprising.
- They do not fix lazy loading or N+1.
- They mix persistence graph concerns into serialization.

#### Optional Anki

Q: What is the cleaner API alternative to cycle annotations on entities?
A: DTOs that avoid exposing the cyclic graph.

</details>

<a id="json-jpa-006"></a>

<details>
<summary><strong>JSON-JPA-006. How can Hibernate proxies affect JSON field names, types and error messages?</strong></summary>

#### Short answer

Hibernate proxies are runtime-generated objects that can confuse type discovery, serialization and error handling if exposed directly.

#### Interview answer

Lazy associations may be represented by proxy objects rather than the actual entity class. Jackson may see proxy-specific types, trigger initialization, or fail on proxy internals depending on configuration. Error messages may mention proxy classes instead of domain classes.

DTO mapping avoids exposing proxies to JSON.

#### Deep dive

Some modules can help Jackson understand Hibernate types, but they do not remove the boundary problem.

#### Production angle

Proxy-related serialization failures often appear only on lazy fields or detached entities.

#### Traps / caveats

- `getClass()` on a proxy may not equal the entity class.
- Proxy serialization can leak internals.
- Hibernate modules are not a replacement for DTOs.

#### Optional Anki

Q: What is the safest way to keep Hibernate proxies out of JSON?
A: Map entities to DTOs before serialization.

</details>

<a id="json-jpa-007"></a>

<details>
<summary><strong>JSON-JPA-007. Why can Open Session in View hide serialization and fetching problems?</strong></summary>

#### Short answer

OSIV keeps the persistence session open through view/response rendering, so lazy loading during JSON serialization succeeds instead of failing.

#### Interview answer

With OSIV enabled, Jackson can trigger SQL while serializing the response. That may make endpoints "work" even though the service layer did not fetch required data intentionally. The cost appears later as N+1 queries, long transactions or unpredictable latency.

Without OSIV, the same code may fail with lazy initialization errors, revealing the missing boundary.

#### Deep dive

The problem is not just configuration preference. It is about keeping database access inside explicit service/query logic.

#### Production angle

OSIV can make database load depend on response serialization and client-selected fields.

#### Traps / caveats

- Disabling OSIV can reveal hidden bugs.
- OSIV does not fix fetch planning.
- Lazy loading during serialization is hard to observe without SQL tracing.

#### Optional Anki

Q: What does OSIV hide?
A: Missing fetch plans and lazy SQL triggered during serialization.

</details>

<a id="json-jpa-008"></a>

<details>
<summary><strong>JSON-JPA-008. How would you debug database queries triggered during JSON serialization?</strong></summary>

#### Short answer

Trace SQL with request correlation, inspect stack traces or profiler data, and identify entity getters or mappers touched during serialization.

#### Interview answer

I would reproduce the endpoint with SQL logging or datasource proxy tracing and correlate queries with the request. Then I would check whether queries happen after the service method returns or inside DTO mapping/serialization. A profiler, debugger or stack trace sampling can show Jackson calling entity getters.

The fix is usually explicit fetch planning and DTO mapping.

#### Deep dive

Compare behavior with OSIV on/off and use integration tests that count queries for key endpoints.

#### Production angle

This investigation helps explain slow endpoints after a response field change.

#### Traps / caveats

- Do not leave verbose SQL logging enabled in production broadly.
- Query count tests must use realistic data.
- Caches can hide the issue during reproduction.

#### Optional Anki

Q: What is the typical fix for SQL during serialization?
A: Fetch required data explicitly and serialize DTOs.

</details>
