# Testing, debugging and production scenarios

---

<a id="json-test-001"></a>

<details>
<summary><strong>JSON-TEST-001. How should JSON serialization and deserialization behavior be tested?</strong></summary>

#### Short answer

Test real examples for both directions using the same mapper configuration the application uses.

#### Interview answer

For DTOs and API boundaries, test that expected Java objects serialize to the documented JSON and representative JSON deserializes correctly. Include edge cases: missing fields, nulls, unknown fields, invalid enums, dates, numbers and nested validation.

For Spring endpoints, prefer tests that exercise MVC converters, not only standalone mappers.

#### Deep dive

Serialization tests should protect contracts, not freeze every incidental formatting detail unless the format is part of the contract.

#### Production angle

Good JSON tests catch breaking changes during refactors and dependency upgrades.

#### Traps / caveats

- Tests using `new ObjectMapper()` may not match production.
- Snapshot tests can be too brittle.
- Include negative tests, not only happy paths.

#### Optional Anki

Q: What mapper should JSON tests use?
A: The real application-configured mapper.

</details>

<a id="json-test-002"></a>

<details>
<summary><strong>JSON-TEST-002. How can Spring Boot tests verify the real application JSON mapper configuration?</strong></summary>

#### Short answer

Use Spring test slices or integration tests that inject the configured mapper or exercise MVC message converters.

#### Interview answer

`@JsonTest` can test Jackson components and the configured `ObjectMapper`. MVC tests with `MockMvc` or full integration tests can verify actual request/response conversion, validation and exception handling.

The goal is to avoid a test-only mapper that differs from production.

#### Deep dive

Also test HTTP clients or message serializers if they have separate mapper configuration.

#### Production angle

This catches missing modules, wrong date formats and inconsistent unknown-field policies.

#### Traps / caveats

- Standalone unit tests may bypass Spring Boot auto-configuration.
- Feign/WebClient/Kafka serializers may need separate tests.
- Assert both success and error responses.

#### Optional Anki

Q: What does `@JsonTest` help test?
A: JSON serialization/deserialization with Spring Boot's Jackson configuration.

</details>

<a id="json-test-003"></a>

<details>
<summary><strong>JSON-TEST-003. What are the strengths and weaknesses of snapshot or golden-file JSON tests?</strong></summary>

#### Short answer

They catch contract changes clearly, but can become brittle if they freeze irrelevant formatting or ordering.

#### Interview answer

Golden-file tests are useful for public payload examples, partner contracts and complex JSON shapes. They make diffs easy to review. But if they assert every field order, whitespace or incidental default, they produce noisy failures.

Use them for important examples and combine them with semantic assertions.

#### Deep dive

For compatibility, keep old payload examples as read tests and new expected payloads as write tests.

#### Production angle

Golden files are strong regression protection during mapper or framework upgrades.

#### Traps / caveats

- Do not blindly accept snapshot updates.
- Avoid including volatile fields unless normalized.
- Keep examples realistic and reviewed.

#### Optional Anki

Q: Main risk of snapshot JSON tests?
A: They can become brittle and hide whether a change is meaningful.

</details>

<a id="json-test-004"></a>

<details>
<summary><strong>JSON-TEST-004. How do contract tests help catch JSON compatibility breaks between services?</strong></summary>

#### Short answer

They verify that producers and consumers still agree on payload shape, required fields and compatible changes.

#### Interview answer

Consumer-driven or shared contract tests capture the JSON examples and expectations that consumers rely on. They catch removals, renames, type changes, enum changes and new required fields before deployment.

They are especially useful when services deploy independently.

#### Deep dive

Contract tests should cover tolerant-reader behavior too: extra fields, missing optional fields and unknown enum strategy where relevant.

#### Production angle

They reduce integration incidents after one team deploys a "small" DTO refactor.

#### Traps / caveats

- Contracts must be versioned and owned.
- Tests should run in CI for producers and consumers.
- Contract tests do not replace end-to-end observability.

#### Optional Anki

Q: What kind of JSON changes do contract tests catch?
A: Renames, removals, type changes, enum changes and required-field changes.

</details>

<a id="json-test-005"></a>

<details>
<summary><strong>JSON-TEST-005. What invalid payload cases should be tested for JSON endpoints?</strong></summary>

#### Short answer

Malformed JSON, wrong types, missing required fields, nulls, unknown fields, invalid formats, unknown enums, duplicates and oversized payloads.

#### Interview answer

Good negative tests include malformed syntax, a string where an object is expected, missing required fields, explicit nulls, invalid dates, invalid enum values, extra fields according to policy, duplicate keys and payloads exceeding limits.

Also test nested validation and arrays with invalid elements.

#### Deep dive

Security-sensitive endpoints should test coercion behavior and trailing tokens if strict parsing is expected.

#### Production angle

Invalid payload tests make error responses predictable and prevent accidental 500s.

#### Traps / caveats

- Do not only test happy-path JSON.
- Field paths in errors should be safe and useful.
- Avoid echoing sensitive rejected values.

#### Optional Anki

Q: Why test explicit null separately from missing?
A: They can have different API semantics.

</details>

<a id="json-test-006"></a>

<details>
<summary><strong>JSON-TEST-006. How would you debug `UnrecognizedPropertyException`?</strong></summary>

#### Short answer

Check whether the JSON contains a field the target DTO does not recognize, then decide whether to fix the client, DTO name, alias or unknown-field policy.

#### Interview answer

I would inspect the exception path and field name, compare the payload with the DTO and API contract, and check naming strategy and `@JsonProperty` annotations. If the field is a typo, reject it. If it is a new compatible field from a producer, consider tolerant reading or an alias.

#### Deep dive

In Spring, confirm which mapper configuration is used. A standalone client mapper may fail while MVC succeeds, or the reverse.

#### Production angle

For external integrations, log safe metadata and sample sanitized payloads to identify producer changes.

#### Traps / caveats

- Do not blindly ignore all unknown fields without understanding the contract.
- Naming strategy mismatch can look like unknown fields.
- Generated clients may send old or new names.

#### Optional Anki

Q: What does `UnrecognizedPropertyException` usually mean?
A: JSON has a property not known to the target type under current mapper config.

</details>

<a id="json-test-007"></a>

<details>
<summary><strong>JSON-TEST-007. How would you debug `MismatchedInputException` or `InvalidDefinitionException`?</strong></summary>

#### Short answer

Check whether the JSON shape matches the target type and whether Jackson knows how to construct that type.

#### Interview answer

`MismatchedInputException` often means the JSON token does not match the expected Java type: array vs object, string vs number, null for primitive, or missing creator value. `InvalidDefinitionException` often points to mapper/type configuration problems: no suitable creator, unsupported type, conflicting annotations or missing module.

Use the exception path and target type to narrow it down.

#### Deep dive

For records, immutable classes and builders, check constructors, parameter names, `@JsonCreator`, modules and visibility.

#### Production angle

Map these failures to clear 400 responses for client input, not generic 500s.

#### Traps / caveats

- Missing Java Time module can appear as a definition/config issue.
- Generic raw types can cause later cast failures.
- Constructor exceptions may be wrapped by Jackson.

#### Optional Anki

Q: What is a common cause of `InvalidDefinitionException`?
A: Jackson cannot construct or serialize the target type with current configuration.

</details>

<a id="json-test-008"></a>

<details>
<summary><strong>JSON-TEST-008. How would you debug a wrong date/time or time zone in a JSON response?</strong></summary>

#### Short answer

Trace the value from domain type to mapper configuration to output, checking timezone, offset, precision and modules.

#### Interview answer

I would first identify the Java type: `Instant`, `LocalDate`, `LocalDateTime`, `OffsetDateTime` or `ZonedDateTime`. Then check mapper configuration, Java Time module, field annotations, server default timezone, database value and client interpretation.

Also verify whether the expected value is an absolute moment or local business time.

#### Deep dive

Problems often come from using `LocalDateTime` for an instant, converting through the default timezone, or truncating precision.

#### Production angle

Add tests around UTC, non-UTC offsets and DST-sensitive examples.

#### Traps / caveats

- Client display timezone may differ from API value.
- Offset is not the same as time zone.
- Database column type can affect interpretation.

#### Optional Anki

Q: First question for date/time bugs?
A: What domain meaning and Java type is this value supposed to have?

</details>

<a id="json-test-009"></a>

<details>
<summary><strong>JSON-TEST-009. What should a service do if an external API adds, removes or changes a JSON field?</strong></summary>

#### Short answer

Treat it as a contract event: assess compatibility, update parsing/mapping, add tests and coordinate migration if breaking.

#### Interview answer

If a provider adds a field, tolerant consumers should usually ignore it. If a field is removed, renamed or changes type/meaning, the consumer may need fallback logic, aliases, version handling or a coordinated rollout.

Do not patch blindly; understand whether business semantics changed.

#### Deep dive

For critical integrations, keep example payloads from providers as fixtures and run contract tests in CI.

#### Production angle

Use alerting around deserialization failures and dead-letter queues for message consumers.

#### Traps / caveats

- Ignoring unknown fields does not help when a required field disappears.
- Type changes can partially work but corrupt meaning.
- External docs may lag actual behavior.

#### Optional Anki

Q: What is usually safe for consumers?
A: Ignoring newly added fields, if required fields and semantics stay stable.

</details>

<a id="json-test-010"></a>

<details>
<summary><strong>JSON-TEST-010. How should parse errors and raw payloads be logged without leaking sensitive data?</strong></summary>

#### Short answer

Log safe metadata, error type, field path and correlation ID; avoid raw payloads or sanitize and truncate them heavily.

#### Interview answer

Raw JSON can contain passwords, tokens, personal data and large blobs. For parse errors, log request ID, endpoint, client, content length, parser error category and safe field path. If payload samples are needed, use redaction, truncation and access controls.

Clients should receive safe error messages, not stack traces.

#### Deep dive

Malformed JSON may not be easy to redact reliably because parsing failed. That is another reason to avoid raw logging.

#### Production angle

Logs are often copied to centralized systems with broad access and retention requirements.

#### Traps / caveats

- Do not echo secrets from rejected payloads.
- Do not log huge payloads.
- Redaction must handle nested and unknown fields.

#### Optional Anki

Q: Why avoid logging raw JSON payloads?
A: They can contain secrets, personal data and huge content.

</details>

<a id="json-test-011"></a>

<details>
<summary><strong>JSON-TEST-011. What should be checked before upgrading Jackson, Spring Boot or a JSON-related dependency?</strong></summary>

#### Short answer

Check release notes, mapper configuration, module compatibility, serialization snapshots, negative tests and API contract tests.

#### Interview answer

Before upgrading, run tests that cover date formats, enum handling, unknown fields, null/coercion behavior, polymorphism, records/builders, validation errors and custom serializers. Review release notes for behavior and security changes.

Also verify Spring Boot auto-configuration and clients/message serializers still use the intended mapper.

#### Deep dive

Dependency upgrades can tighten security defaults, change module behavior or reveal ambiguous DTO definitions.

#### Production angle

Use canary deployment and monitor deserialization failures, 4xx/5xx changes and payload compatibility metrics.

#### Traps / caveats

- Passing unit tests with a test mapper is not enough.
- Custom serializers/deserializers need explicit coverage.
- Security fixes may require code/config changes.

#### Optional Anki

Q: What tests are critical before a Jackson upgrade?
A: Contract, serialization/deserialization, negative input and real mapper configuration tests.

</details>

<a id="json-test-012"></a>

<details>
<summary><strong>JSON-TEST-012. How would you investigate slow JSON serialization in production?</strong></summary>

#### Short answer

Measure payload size, query activity, CPU and allocation profiles, then determine whether Jackson, mapping, lazy loading, logging or network is the real bottleneck.

#### Interview answer

I would start from traces and metrics: endpoint latency, response size, database time and GC. Then capture JFR or a profiler during the slow period. If stacks show Jackson and DTO mapping, inspect payload shape, mapper reuse, custom serializers and large collections. If SQL appears during serialization, fix fetch plans and DTO mapping.

#### Deep dive

Slow serialization is often a symptom of too much data: unbounded pages, nested graphs, field selection or accidental entity serialization.

#### Production angle

Fixes may include pagination, DTO projections, streaming, removing raw payload logging, mapper reuse and query planning.

#### Traps / caveats

- Do not assume Jackson is the bottleneck without profiling.
- Database lazy loading can look like serialization latency.
- Large responses may be slow because of client/network backpressure.

#### Optional Anki

Q: What should you check before tuning Jackson?
A: Payload size, database queries, mapping cost, GC and profiler data.

</details>
