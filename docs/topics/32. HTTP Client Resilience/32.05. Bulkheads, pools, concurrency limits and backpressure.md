# Bulkheads, pools, concurrency limits and backpressure

---

<a id="hcr-bulk-001"></a>

<details>
<summary><strong>HCR-BULK-001. What is a bulkhead?</strong></summary>

#### Short answer

A bulkhead isolates resources so failure in one dependency or workload does not consume everything.

#### Interview answer

The idea comes from compartments: if one area floods, the whole system should not sink. In backend services, a bulkhead can be a separate thread pool, semaphore, queue, connection pool or concurrency limit for a dependency.

If recommendations are slow, a bulkhead prevents recommendation calls from exhausting threads needed for checkout, health checks or other dependencies.

#### Deep dive

Bulkheads are about isolation, not only limiting. They make failure domains explicit and metrics easier to understand.

#### Production angle

Bulkheads reduce blast radius during dependency outages and traffic spikes.

#### Traps / caveats

- A global executor is not a bulkhead.
- A huge queue can hide overload.
- Bulkhead limits must match downstream capacity.

#### Optional Anki

Q: What problem does a bulkhead solve?
A: One failing workload consuming shared resources.

</details>

<a id="hcr-bulk-002"></a>

<details>
<summary><strong>HCR-BULK-002. How does a bulkhead prevent one downstream from exhausting all service resources?</strong></summary>

#### Short answer

It gives the downstream a bounded resource slice and rejects or degrades when that slice is full.

#### Interview answer

Suppose a service has one shared executor for all outbound calls. If one dependency becomes slow, its calls can occupy every worker. A bulkhead limits that dependency to a bounded number of concurrent calls or threads, leaving capacity for unrelated work.

When the limit is reached, the service can fail fast, shed optional work or return fallback instead of queueing forever.

#### Deep dive

Bulkheads should be combined with timeout budgets and metrics. A bulkhead without timeouts can still hold its own capacity too long.

#### Production angle

Resource isolation is one of the strongest protections against cascading failures.

#### Traps / caveats

- Increasing the bulkhead limit may overload the downstream.
- Queued work still consumes latency budget.
- Optional traffic should not starve critical traffic.

#### Optional Anki

Q: What should happen when a dependency bulkhead is full?
A: Fail fast, degrade or shed according to policy.

</details>

<a id="hcr-bulk-003"></a>

<details>
<summary><strong>HCR-BULK-003. What is the difference between a semaphore bulkhead and a thread-pool bulkhead?</strong></summary>

#### Short answer

A semaphore bulkhead limits concurrency; a thread-pool bulkhead also isolates execution threads and queues.

#### Interview answer

A semaphore bulkhead allows only N concurrent calls. It is lightweight and useful when the caller's execution model is already appropriate, such as blocking servlet threads or reactive pipelines that should not switch pools unnecessarily.

A thread-pool bulkhead runs work on a dedicated executor. It isolates blocking work from caller threads but adds scheduling overhead, queueing and context propagation concerns.

#### Deep dive

For blocking HTTP clients, thread-pool isolation can protect request threads. For reactive clients, semaphore-style limits are often cleaner than blocking or offloading incorrectly.

#### Production angle

Choosing the wrong bulkhead can either fail to isolate blocking work or add unnecessary complexity.

#### Traps / caveats

- Thread pools need bounded queues.
- Semaphore bulkheads do not isolate CPU or blocking threads.
- Context propagation can break across executor boundaries.

#### Optional Anki

Q: What does a semaphore bulkhead mainly limit?
A: Concurrent calls.

</details>

<a id="hcr-bulk-004"></a>

<details>
<summary><strong>HCR-BULK-004. When should each downstream dependency have a separate HTTP connection pool?</strong></summary>

#### Short answer

Use separate pools when dependencies have different hosts, criticality, latency, capacity or failure behavior.

#### Interview answer

Separate pools prevent a slow or high-volume dependency from consuming all outbound connections. They also allow dependency-specific limits, idle eviction, TLS settings, proxy settings and metrics.

For example, a third-party fraud API and an internal catalog API should not necessarily share one global pool with the same limits.

#### Deep dive

Some clients pool per route internally, but total pool limits still matter. A busy route can consume the global limit and starve others if not configured carefully.

#### Production angle

Per-dependency pools make saturation visible and give operators safer controls during incidents.

#### Traps / caveats

- Too many pools can waste connections and memory.
- Pool limits should align with downstream capacity.
- Separate pools do not replace timeouts.

#### Optional Anki

Q: Why avoid one global HTTP pool for all dependencies?
A: One dependency can starve others.

</details>

<a id="hcr-bulk-005"></a>

<details>
<summary><strong>HCR-BULK-005. Why can an unbounded queue before an HTTP client be dangerous?</strong></summary>

#### Short answer

It hides overload until latency, memory or stale work becomes a production incident.

#### Interview answer

An unbounded queue accepts more work even when workers or downstream capacity are saturated. Requests sit in the queue, consuming memory and exceeding their deadlines before they even start. When the dependency recovers, the backlog can flood it again.

Bounded queues force the service to make an explicit overload decision: reject, shed, degrade or apply backpressure.

#### Deep dive

Queue age is often more important than queue size. A small queue with very old requests can already violate SLOs.

#### Production angle

Unbounded queues are common in retry storms, async wrappers and background workers calling HTTP dependencies.

#### Traps / caveats

- A queue is not capacity.
- Queued retries can prolong outages.
- Rejecting early may be better than timing out late.

#### Optional Anki

Q: Why bound queues before HTTP clients?
A: To make overload visible and protect latency/memory.

</details>

<a id="hcr-bulk-006"></a>

<details>
<summary><strong>HCR-BULK-006. What is connection pool acquisition timeout, and why does it matter?</strong></summary>

#### Short answer

It is the maximum time a request waits locally for an available connection from the pool.

#### Interview answer

If all connections to a dependency are busy, a new request may wait in the client pool before any network call starts. Pool acquisition timeout limits that wait. Without it, requests can spend most of their latency budget waiting locally and then still attempt the downstream call.

This timeout should be part of the overall operation deadline.

#### Deep dive

Pool exhaustion can mean the downstream is slow, responses are not closed, concurrency is too high, or pool limits are too low.

#### Production angle

Pool acquisition metrics often reveal local saturation even when downstream server latency looks normal.

#### Traps / caveats

- Connect timeout does not cover pool wait.
- Increasing pool size may worsen downstream overload.
- Always close or consume response bodies.

#### Optional Anki

Q: What does pool acquisition timeout limit?
A: Waiting for a free HTTP connection.

</details>

<a id="hcr-bulk-007"></a>

<details>
<summary><strong>HCR-BULK-007. How do backpressure, load shedding and client-side concurrency limits differ for outgoing HTTP calls?</strong></summary>

#### Short answer

Concurrency limits cap in-flight calls, backpressure slows producers, and load shedding rejects work to protect the system.

#### Interview answer

A client-side concurrency limit says "only N calls to this dependency may be in flight." Backpressure tells upstream producers to slow down when capacity is low. Load shedding rejects or drops lower-priority work when accepting it would harm the system.

For synchronous HTTP APIs, true backpressure is limited. Fast rejection with `429`, `503` or degraded response is often clearer than queueing unbounded work.

#### Deep dive

These controls should be priority-aware. Critical traffic may get reserved capacity while optional traffic is shed first.

#### Production angle

They keep overload from turning into total service collapse.

#### Traps / caveats

- Queues without deadlines are not backpressure.
- Shedding must be observable.
- Clients need retry guidance if they may retry.

#### Optional Anki

Q: What does load shedding mean?
A: Intentionally rejecting work to protect the system.

</details>

<details>
<summary><strong>🧠 HCR-BULK-008. How do virtual threads change, but not remove, the need for dependency isolation?</strong></summary>

#### Short answer

Virtual threads make blocking cheaper for the JVM, but downstream services, connection pools and databases still have finite capacity.

#### Interview answer

Virtual threads can reduce the cost of blocking waits compared with platform threads. That helps servlet-style code handle many concurrent waits. But they do not make a downstream API accept unlimited traffic, do not increase HTTP connection pool capacity and do not remove latency budgets.

You still need timeouts, connection limits, concurrency limits, rate limits and fallback policy.

#### Deep dive

Virtual threads can make it easier to accidentally create very high concurrency because thread count is no longer the obvious bottleneck.

#### Production angle

After migrating to virtual threads, monitor downstream QPS, pool waits, database connections, rate limits and tail latency.

#### Traps / caveats

- Virtual threads are not backpressure.
- They do not fix missing timeouts.
- They can expose hidden downstream capacity limits faster.

#### Optional Anki

Q: What limit remains important with virtual threads?
A: Downstream and connection-pool capacity.

</details>
