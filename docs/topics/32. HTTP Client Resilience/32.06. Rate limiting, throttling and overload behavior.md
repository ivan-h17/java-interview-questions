# Rate limiting, throttling and overload behavior

---

<a id="hcr-rate-001"></a>

<details>
<summary><strong>HCR-RATE-001. What is the difference between server-side rate limiting and client-side throttling?</strong></summary>

#### Short answer

Server-side rate limiting rejects excess incoming traffic; client-side throttling limits outgoing traffic before sending it.

#### Interview answer

An API provider uses server-side rate limiting to protect itself and enforce quotas, often returning `429`. A Java service uses client-side throttling to respect downstream limits and avoid creating overload.

Both can exist at the same time. A well-behaved client should not rely on the server to reject it after it already sent too much traffic.

#### Deep dive

Client-side throttling can be per instance, per tenant, per dependency or fleet-wide. Distributed quotas may require shared state or conservative local limits.

#### Production angle

For third-party APIs, client-side throttling prevents quota incidents and reduces support escalations.

#### Traps / caveats

- Rate limiting is not authorization.
- Per-instance limits can exceed a global quota when scaled out.
- Throttling needs metrics.

#### Optional Anki

Q: Who enforces server-side rate limiting?
A: The receiving service/API provider.

</details>

<a id="hcr-rate-002"></a>

<details>
<summary><strong>HCR-RATE-002. How should a Java client handle `429 Too Many Requests` and `Retry-After` values?</strong></summary>

#### Short answer

It should slow down, respect retry guidance, avoid immediate retries and surface throttling metrics.

#### Interview answer

`429` means the client exceeded a rate limit or quota. The client should parse `Retry-After` if present, apply backoff and jitter, and retry only if the operation is safe and the caller deadline allows it.

For sustained `429`s, the service should reduce request rate, disable optional traffic, queue asynchronously if acceptable or fail fast with clear messaging.

#### Deep dive

`Retry-After` can be seconds or an HTTP-date. Clients should cap wait time and handle invalid values defensively.

#### Production angle

Repeated `429`s should trigger dashboards and alerts because the service is either over quota or misconfigured.

#### Traps / caveats

- Do not retry `429` immediately.
- Do not ignore tenant-specific quotas.
- Do not block request threads for long retry delays.

#### Optional Anki

Q: What does `429` tell a client?
A: Slow down or wait according to rate-limit policy.

</details>

<a id="hcr-rate-003"></a>

<details>
<summary><strong>HCR-RATE-003. How can rate limiting and retry policies work against each other?</strong></summary>

#### Short answer

Retries can consume rate-limit quota faster and cause more throttling.

#### Interview answer

If a dependency returns `429` and the client retries aggressively, every retry may count against the same quota. The client then makes the throttling worse and may prevent normal traffic from succeeding.

Retry and rate-limit policy should be coordinated: respect `Retry-After`, use retry budgets, limit concurrency and avoid retrying when quota is exhausted.

#### Deep dive

For shared third-party quotas, one noisy tenant or batch job can consume quota and cause unrelated user requests to fail.

#### Production angle

Dashboards should show original calls, retry attempts and throttled calls separately.

#### Traps / caveats

- Retrying `429` without delay is self-harm.
- Per-service retries can hide tenant-level quota problems.
- Backoff should not exceed request deadlines.

#### Optional Anki

Q: Why can retries worsen rate limiting?
A: They add more quota-consuming requests.

</details>

<a id="hcr-rate-004"></a>

<details>
<summary><strong>HCR-RATE-004. When should a service fail fast instead of queueing more outbound calls?</strong></summary>

#### Short answer

Fail fast when queued work is unlikely to complete within deadline or would overload a dependency.

#### Interview answer

If the dependency is saturated, the local pool is full, or the caller's deadline is short, queueing more work often only creates late failures. Failing fast gives callers a quick, honest response and preserves resources for traffic that can still succeed.

For optional features, fail fast may mean returning a degraded response. For critical operations, it may mean `503` or a domain unavailable result.

#### Deep dive

Queueing is useful only for short bursts when the service has enough capacity to drain before deadlines expire.

#### Production angle

Fast failure is a resilience feature because it prevents overload from turning into total collapse.

#### Traps / caveats

- Do not queue without a maximum age.
- Do not fail fast critical traffic before shedding optional traffic.
- Return retry guidance when clients can retry safely.

#### Optional Anki

Q: Why fail fast under overload?
A: To protect capacity and avoid late, useless work.

</details>

<a id="hcr-rate-005"></a>

<details>
<summary><strong>HCR-RATE-005. How should clients behave when a third-party API has a documented quota?</strong></summary>

#### Short answer

They should enforce client-side throttling, prioritize traffic and monitor quota usage before the provider rejects calls.

#### Interview answer

For a third-party quota, I would configure per-dependency rate limits, account for all service instances, reserve capacity for critical traffic and reduce optional/batch traffic first. The client should handle `429` gracefully and expose remaining quota if the provider returns it.

If quota is business-critical, the system may need caching, batching, async processing or a commercial quota increase.

#### Deep dive

Fleet-wide quotas are tricky because horizontal scaling multiplies request rate. Local per-instance limits must account for replica count.

#### Production angle

Quota exhaustion should be visible before customers experience failures.

#### Traps / caveats

- Do not let background jobs consume user quota.
- Do not hardcode quotas without configuration.
- Do not assume all tenants have the same quota.

#### Optional Anki

Q: What should be shed first when quota is scarce?
A: Optional or low-priority traffic.

</details>

<a id="hcr-rate-006"></a>

<details>
<summary><strong>🧠 HCR-RATE-006. What is adaptive concurrency limiting, and when is it useful?</strong></summary>

#### Short answer

Adaptive concurrency limiting adjusts allowed in-flight requests based on observed latency or failure signals.

#### Interview answer

Instead of a fixed concurrency limit, an adaptive limiter increases or decreases concurrency as the dependency's behavior changes. If latency rises or failures increase, the limiter reduces in-flight calls. If the dependency is healthy, it can allow more.

It is useful when dependency capacity changes over time and fixed limits are either too conservative or too risky.

#### Deep dive

Adaptive limiters need careful tuning and observability. They should not fight with autoscaling, server-side rate limits or circuit breakers.

#### Production angle

They can help protect dependencies during gradual overload before hard failures appear.

#### Traps / caveats

- Adaptive does not mean unlimited.
- Bad feedback signals can cause oscillation.
- It still needs deadlines and retry budgets.

#### Optional Anki

Q: What signal commonly drives adaptive concurrency?
A: Latency and failure/saturation signals.

</details>
