<details>
<summary><strong>HCR-JAVA-001. How do `RestClient`, `WebClient`, `RestTemplate` and Feign differ at a high level?</strong></summary>

#### Short answer

`RestClient` is Spring's modern blocking client, `WebClient` is reactive, `RestTemplate` is older blocking API, and Feign is declarative interface-based HTTP.

#### Interview answer

For typical Spring MVC services, `RestClient` is a good modern blocking choice. `RestTemplate` is still common in legacy code but is not the preferred API for new Spring clients. `WebClient` fits reactive WebFlux applications or services intentionally built around non-blocking I/O. Feign lets teams define HTTP clients as annotated interfaces, commonly in Spring Cloud setups.

Client choice does not remove the need for explicit timeouts, error mapping, connection pools, retries and metrics.

#### Deep dive

The execution model matters. Using `WebClient` and immediately calling `block()` everywhere often adds complexity without gaining non-blocking benefits.

#### Production angle

Mismatched client choice can cause thread starvation, event-loop blocking or hard-to-debug context propagation issues.

#### Traps / caveats

- Do not choose reactive clients only because they sound faster.
- Do not rely on default timeout behavior.
- Generated/declarative clients still need resilience configuration.

#### Optional Anki

Q: Modern Spring blocking HTTP client?
A: `RestClient`.

</details>

<details>
<summary><strong>HCR-JAVA-002. How should HTTP client connection pools be configured?</strong></summary>

#### Short answer

Configure pools per dependency with bounded total and per-route connections, acquisition timeout, idle eviction and metrics.

#### Interview answer

An HTTP client pool should match expected concurrency, downstream capacity and timeout budget. Important settings include maximum total connections, maximum per route/host, connection acquisition timeout, connect/read/request timeouts, idle connection eviction and keep-alive behavior.

For different dependencies, use separate clients or clearly separated pool settings so one dependency cannot starve another.

#### Deep dive

Pool sizing should be derived from request rate and latency, not guesswork. Roughly, in-flight calls equal throughput multiplied by latency, with margin for bursts.

#### Production angle

Pool metrics are essential: active connections, idle connections, pending acquisition, timeouts and errors by dependency.

#### Traps / caveats

- Bigger pools can overload downstream services.
- Missing acquisition timeout causes local waiting.
- Unclosed response bodies can leak pool connections.

#### Optional Anki

Q: Which pool timeout is often forgotten?
A: Connection acquisition timeout.

</details>

<details>
<summary><strong>HCR-JAVA-003. How do you propagate correlation IDs and tracing context in outgoing calls?</strong></summary>

#### Short answer

Use client interceptors, filters or instrumentation to add safe correlation and trace headers consistently.

#### Interview answer

Outgoing clients should propagate trace context such as W3C `traceparent` and application correlation IDs. In Spring, this usually belongs in `RestClient` interceptors, `WebClient` filters, Feign interceptors or observability instrumentation rather than every call site.

Authorization context is separate: sometimes you forward a user token, sometimes use service credentials, and sometimes exchange tokens.

#### Deep dive

Async boundaries can lose thread-local context. Reactive context and executor context propagation need explicit support or framework instrumentation.

#### Production angle

Without propagation, traces break at service boundaries and incident diagnosis becomes guesswork.

#### Traps / caveats

- Do not blindly trust inbound correlation headers from public clients.
- Do not forward user tokens to services that should not receive them.
- Do not log tokens or secrets while debugging headers.

#### Optional Anki

Q: Common W3C trace propagation header?
A: `traceparent`.

</details>

<details>
<summary><strong>HCR-JAVA-004. What resilience settings should be configured explicitly for every generated or declarative HTTP client?</strong></summary>

#### Short answer

Base URL, timeouts, pool limits, error mapping, retry policy, authentication, observability and fallback behavior should be explicit.

#### Interview answer

Generated or declarative clients reduce boilerplate but can hide defaults. Each client should have a named dependency configuration: base URL, connect/read/request timeouts, pool settings, status-to-error mapping, retry and circuit breaker policy, rate limits, auth handling, tracing, metrics and logging redaction.

The configuration should be validated at startup so missing URLs or unsafe defaults fail early.

#### Deep dive

Generated clients often share HTTP transports. That sharing must be intentional, especially for pools and interceptors.

#### Production angle

Explicit client configuration makes dependency behavior reviewable and safer to change.

#### Traps / caveats

- Do not let generated clients use infinite defaults.
- Do not apply one retry policy globally.
- Do not log generated request bodies without redaction.

#### Optional Anki

Q: Why configure generated clients explicitly?
A: To avoid hidden unsafe defaults.

</details>

<details>
<summary><strong>HCR-JAVA-005. Where should timeout, retry and circuit breaker configuration live in a Spring Boot service?</strong></summary>

#### Short answer

Keep it in typed, validated, per-dependency configuration near client construction, with business fallback policy outside the low-level transport.

#### Interview answer

In Spring Boot, I would model client settings as configuration properties, validate them at startup and apply them in a dedicated client configuration class. Each downstream gets named settings for timeout, retry, circuit breaker, pool and rate limit behavior.

Business fallback decisions should usually live in the application/service layer, not hidden in a generic HTTP wrapper.

#### Deep dive

Centralizing helpers is useful, but avoid a universal "resilient client" that erases dependency-specific semantics.

#### Production angle

Per-dependency config makes safe runtime changes, canaries and incident rollback easier.

#### Traps / caveats

- Do not scatter timeout values across call sites.
- Do not hide money/security fallback in infrastructure code.
- Validate that required client properties are present.

#### Optional Anki

Q: Should every dependency share one timeout?
A: No, configure per dependency and operation.

</details>

<a id="hcr-java-006"></a>

<details>
<summary><strong>HCR-JAVA-006. How do WebClient filters or RestClient interceptors help implement cross-cutting client behavior?</strong></summary>

#### Short answer

They centralize repeated behavior such as headers, tracing, logging, error mapping and metrics.

#### Interview answer

Interceptors and filters let you add behavior around every outgoing request without duplicating code: correlation IDs, trace headers, auth headers, redaction, metrics, request IDs and consistent status handling.

They should stay generic. Business-specific retry or fallback decisions should still respect the dependency contract.

#### Deep dive

Ordering matters. For example, tracing, retries and logging can produce different spans and logs depending on where they are applied.

#### Production angle

Cross-cutting client behavior improves consistency across many downstream integrations.

#### Traps / caveats

- Do not log sensitive headers.
- Do not consume response bodies in interceptors accidentally.
- Be careful with blocking work in reactive filters.

#### Optional Anki

Q: What are client interceptors useful for?
A: Shared outbound behavior like headers, tracing and metrics.

</details>

<a id="hcr-java-007"></a>

<details>
<summary><strong>HCR-JAVA-007. What can go wrong when blocking inside a WebFlux or Reactor pipeline?</strong></summary>

#### Short answer

Blocking can starve event-loop threads and destroy the scalability model of reactive code.

#### Interview answer

WebFlux relies on a small number of event-loop threads for non-blocking work. If code calls blocking APIs, sleeps, waits on futures or uses a blocking HTTP client on those threads, it can prevent other requests from making progress.

If blocking is unavoidable, it should be isolated on a bounded scheduler or executor with clear limits.

#### Deep dive

Blocking also complicates context propagation, cancellation and timeout behavior. A reactive timeout may not stop a blocking call running elsewhere unless wired correctly.

#### Production angle

Event-loop starvation appears as high latency with low CPU utilization and confusing thread dumps.

#### Traps / caveats

- Calling `.block()` in reactive request flow is a red flag.
- Offloading to an unbounded scheduler creates another overload risk.
- Database or SDK clients may still be blocking.

#### Optional Anki

Q: Main rule for Reactor event-loop threads?
A: Do not block them.

</details>

<a id="hcr-java-008"></a>

<details>
<summary><strong>🧠 HCR-JAVA-008. How should Resilience4j Retry, CircuitBreaker, RateLimiter, Bulkhead and TimeLimiter be combined?</strong></summary>

#### Short answer

Combine them deliberately per dependency because ordering changes load, metrics and failure behavior.

#### Interview answer

A common model is: limit concurrency with a bulkhead, apply an attempt timeout, retry safe transient failures within a deadline, use a circuit breaker to stop calls to unhealthy dependencies and rate-limit outbound traffic when capacity or quota requires it.

But the exact decorator order matters. For example, if the circuit breaker wraps retries, it may see final operation results; if retries wrap the breaker, attempts may be rejected quickly when the circuit is open.

#### Deep dive

The chosen order should be documented and verified with tests and metrics. Different dependencies may need different composition.

#### Production angle

Bad composition can create hidden retry storms, misleading breaker metrics or user-visible latency spikes.

#### Traps / caveats

- TimeLimiter around blocking work still needs an executor and cancellation story.
- RateLimiter plus Retry can fight each other.
- Fallback should not hide critical failures.

#### Optional Anki

Q: Why does resilience decorator order matter?
A: It changes which failures are counted, retried or rejected.

</details>

<details>
<summary><strong>🧠 HCR-JAVA-009. What can go wrong when wrapping blocking HTTP clients in `CompletableFuture`?</strong></summary>

#### Short answer

It makes the call asynchronous to the caller but still consumes blocking threads and can hide pool saturation.

#### Interview answer

Putting a blocking HTTP call inside `CompletableFuture.supplyAsync()` does not make the I/O non-blocking. It moves the wait to another executor. If that executor is shared, unbounded or undersized, it can become saturated and cause unrelated async work to fail.

You also need deadlines, cancellation handling, context propagation and error mapping.

#### Deep dive

Using the common ForkJoinPool for blocking I/O is usually a bad default. Use a dedicated bounded executor or a real non-blocking client when appropriate.

#### Production angle

Async wrappers often fail under load because queues grow while metrics only show "async" code.

#### Traps / caveats

- `CompletableFuture` timeout does not necessarily stop the underlying HTTP call.
- ThreadLocal context may be lost.
- Blocking calls still need HTTP client timeouts.

#### Optional Anki

Q: Does `CompletableFuture` make blocking HTTP non-blocking?
A: No, it only moves blocking work to another thread.

</details>

<details>
<summary><strong>HCR-JAVA-010. How would you migrate a legacy `RestTemplate` client to `RestClient` without changing resilience behavior?</strong></summary>

#### Short answer

Preserve the underlying timeouts, pool, error mapping, interceptors, metrics and tests before changing call syntax.

#### Interview answer

I would first inventory existing `RestTemplate` behavior: request factory, timeouts, message converters, interceptors, error handler, auth, tracing, metrics and retry wrappers. Then I would build an equivalent `RestClient` configuration and migrate one dependency at a time behind the same adapter interface.

Contract tests with a fake server should verify status mapping, headers, serialization, timeouts and retry behavior.

#### Deep dive

The migration risk is not the fluent API; it is accidental behavior changes in transport and error handling.

#### Production angle

Roll out with dependency-specific metrics and compare old versus new latency, errors and pool behavior.

#### Traps / caveats

- Do not lose interceptors or redaction.
- Do not change timeout defaults silently.
- Do not migrate critical clients without integration tests.

#### Optional Anki

Q: Biggest risk in `RestTemplate` to `RestClient` migration?
A: Accidentally changing transport, timeout or error behavior.

</details>
