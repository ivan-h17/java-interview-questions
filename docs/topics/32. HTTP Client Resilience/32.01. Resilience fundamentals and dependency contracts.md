# Resilience fundamentals and dependency contracts

---

<a id="hcr-fund-001"></a>

<details>
<summary><strong>HCR-FUND-001. What does HTTP client resilience mean in a Java backend service?</strong></summary>

#### Short answer

HTTP client resilience means designing outgoing calls so slow, failing or overloaded dependencies do not break the whole service.

#### Interview answer

In a Java backend, every remote HTTP dependency can fail, stall, return bad responses or behave differently under load. Resilience is the set of client-side decisions that bound the damage: timeouts, deadlines, retries, idempotency, circuit breakers, bulkheads, rate limits, fallbacks and observability.

The goal is not to make remote calls magically reliable. The goal is to fail predictably, protect local resources and keep critical user flows working when a dependency is degraded.

#### Deep dive

Resilience policy should be per dependency and per operation. A payment call, recommendation call and feature flag call should not share the same timeout, retry and fallback behavior.

#### Production angle

Bad client defaults often turn one dependency incident into thread exhaustion, retry storms, high p99 latency or incorrect fallback data.

#### Traps / caveats

- Resilience is not only retries.
- More retries can reduce availability during overload.
- Fallbacks must be correct for the domain, not just convenient.

#### Optional Anki

Q: Main goal of HTTP client resilience?
A: Bound dependency failure impact and protect service resources.

</details>

<details>
<summary><strong>HCR-FUND-002. Why are remote HTTP calls different from local method calls?</strong></summary>

#### Short answer

Remote calls cross process and network boundaries, so latency, partial failure, ambiguity and independent deployment become part of the contract.

#### Interview answer

A local method call is usually fast and either returns or throws in the same process. A remote HTTP call can be slow, time out, fail after the server committed work, return a malformed body, hit a stale DNS entry or traverse proxies and load balancers.

This means callers need explicit timeouts, error classification, retry rules and idempotency. They also need observability because a failure may be in the caller, network, mesh, gateway or downstream service.

#### Deep dive

The hardest case is an ambiguous outcome: the request was sent, the response was lost, and the client does not know whether the server executed the operation.

#### Production angle

Treating remote calls as local methods creates hidden distributed-system bugs, especially duplicate writes and thread starvation.

#### Traps / caveats

- A timeout does not prove the downstream did nothing.
- HTTP status alone may not describe business outcome.
- Network success does not imply domain correctness.

#### Optional Anki

Q: Why is a timed-out remote write ambiguous?
A: The server may have committed before the client stopped waiting.

</details>

<details>
<summary><strong>HCR-FUND-003. What is a transient failure, and how is it different from a persistent failure?</strong></summary>

#### Short answer

A transient failure may disappear soon; a persistent failure is expected to keep failing until something changes.

#### Interview answer

Transient failures include brief overload, connection reset, temporary DNS failure, a rolling restart or a small packet loss. A retry may help if the operation is safe and the caller still has time.

Persistent failures include bad credentials, invalid request payload, unsupported API version, missing resource or a down dependency with no capacity. Retrying these usually wastes resources and can amplify incidents.

#### Deep dive

Failure classification should combine exception type, HTTP status, operation semantics and dependency contract. For example, `503` may be transient, while `400` is usually a caller bug.

#### Production angle

Correct classification determines retry, alerting and circuit breaker behavior.

#### Traps / caveats

- Not every `5xx` is safe to retry.
- Some `409` or `429` responses may be retryable only under documented rules.
- Permanent failures should fail fast and surface useful diagnostics.

#### Optional Anki

Q: Should validation errors be retried?
A: Usually no; they are persistent until the request changes.

</details>

<a id="hcr-fund-004"></a>

<details>
<summary><strong>HCR-FUND-004. What is a partial failure in a distributed system?</strong></summary>

#### Short answer

A partial failure means one part of the system fails while other parts keep running.

#### Interview answer

In distributed systems, dependencies fail independently. Your service may be healthy while the pricing service is slow, one availability zone has DNS issues, a third-party API rejects requests, or only one endpoint fails because it depends on a degraded service.

Client resilience exists because these partial failures are normal. The caller must decide whether to wait, retry, degrade, fail fast or route around the problem.

#### Deep dive

Partial failure is harder than total failure because the system can still accept traffic while some paths are unreliable. That can create inconsistent user experience or hidden data damage.

#### Production angle

Good services classify dependencies by criticality and expose degraded states through metrics, logs, traces and sometimes API responses.

#### Traps / caveats

- Do not assume "service is up" means every dependency is usable.
- Optional dependency failure should not take down unrelated endpoints.
- Silent partial failure can be worse than explicit failure.

#### Optional Anki

Q: What is partial failure?
A: Some components fail while the rest of the system continues operating.

</details>

<a id="hcr-fund-005"></a>

<details>
<summary><strong>HCR-FUND-005. How can one slow downstream service cause a cascading failure?</strong></summary>

#### Short answer

Slow downstream calls can occupy threads, connections and queues until the caller also becomes unavailable.

#### Interview answer

If a Java service waits too long for a slow dependency, servlet threads, executor workers or HTTP client connections can pile up. Then unrelated requests may wait behind stuck work. If retries start, the caller sends even more traffic to the struggling dependency.

This is a cascading failure: one dependency problem consumes shared resources and spreads to services that were otherwise healthy.

#### Deep dive

Common amplifiers are missing timeouts, unbounded queues, shared thread pools, global HTTP client pools, aggressive retries and fallbacks that overload another dependency.

#### Production angle

Prevent cascades with deadlines, bounded pools, bulkheads, circuit breakers, load shedding and per-dependency dashboards.

#### Traps / caveats

- Increasing timeouts can make exhaustion worse.
- Increasing pool size can overload the downstream.
- Retries must be measured separately from original demand.

#### Optional Anki

Q: Main cause of cascading failure from slow HTTP calls?
A: Shared resource exhaustion in the caller.

</details>

<a id="hcr-fund-006"></a>

<details>
<summary><strong>HCR-FUND-006. What should a service know about each downstream dependency before calling it?</strong></summary>

#### Short answer

It should know the dependency's purpose, criticality, latency, error contract, capacity, retry rules, idempotency support and fallback policy.

#### Interview answer

For each downstream, I want to know whether it is critical or optional, what operations are read versus write, expected p95/p99 latency, documented timeouts, retryable statuses, rate limits, authentication behavior and data freshness requirements.

I also want operational details: owner, dashboard, runbook, support channel, quotas, environment endpoints and whether the API supports idempotency keys or operation status lookup.

#### Deep dive

This information should shape client configuration instead of relying on global defaults.

#### Production angle

During incidents, dependency ownership, quotas and fallback rules matter as much as code.

#### Traps / caveats

- Do not apply one retry policy to every dependency.
- Do not hide dependency-specific behavior behind a generic HTTP utility.
- Unknown quotas often become production throttling incidents.

#### Optional Anki

Q: Why classify dependencies before configuring clients?
A: Criticality and contract determine timeout, retry and fallback behavior.

</details>

<a id="hcr-fund-007"></a>

<details>
<summary><strong>HCR-FUND-007. How do critical and optional downstream dependencies differ in resilience design?</strong></summary>

#### Short answer

Critical dependencies often fail the request if unavailable; optional dependencies can often degrade, skip or use stale data.

#### Interview answer

A critical dependency is required to produce a correct response, such as payment authorization for checkout or permission checks for access control. If it fails, the safest behavior may be to fail closed.

An optional dependency improves the response but is not required, such as recommendations or enrichment data. It can use a short timeout, fallback, stale cache or feature flag disablement.

#### Deep dive

Criticality is operation-specific. A cache may be optional for product descriptions but critical if it stores idempotency keys or rate-limit state.

#### Production angle

Dependency classification prevents non-critical features from consuming resources needed for revenue, safety or correctness-critical paths.

#### Traps / caveats

- Do not fail open for authorization without explicit design.
- Do not silently degrade critical data like balances or prices.
- Optional fallback usage still needs alerts.

#### Optional Anki

Q: What is the default safe behavior for failed permission checks?
A: Usually fail closed.

</details>
