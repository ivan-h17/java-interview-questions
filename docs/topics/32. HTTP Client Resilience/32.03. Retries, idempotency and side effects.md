# Retries, idempotency and side effects

---

<a id="hcr-retry-001"></a>

<details>
<summary><strong>HCR-RETRY-001. When is an HTTP request safe to retry?</strong></summary>

#### Short answer

Retry only when the failure may be transient and the operation is safe, idempotent or protected against duplicate side effects.

#### Interview answer

A retry is safe when repeating the request cannot incorrectly change state. Reads are usually safer. Writes need explicit protection such as idempotency keys, unique constraints or an operation status resource.

The failure must also be retryable. A timeout, connection reset or temporary `503` may be worth retrying. A validation error, bad credentials or business rejection usually should fail fast.

#### Deep dive

Retry safety is about operation semantics, not only HTTP method. A `POST` can be retry-safe with an idempotency key; a poorly designed `GET` that triggers side effects is not truly safe.

#### Production angle

Blind retries are a common cause of duplicate orders, double charges and retry storms.

#### Traps / caveats

- Timeout after sending a request is an ambiguous outcome.
- Do not retry writes without deduplication.
- Stop retrying when the caller's deadline is nearly exhausted.

#### Optional Anki

Q: Key condition for retrying side-effecting operations?
A: Durable idempotency or deduplication.

</details>

<a id="hcr-retry-002"></a>

<details>
<summary><strong>HCR-RETRY-002. Why should retries use exponential backoff and jitter?</strong></summary>

#### Short answer

Backoff reduces pressure on a failing dependency; jitter prevents clients from retrying in synchronized waves.

#### Interview answer

Immediate retries can multiply traffic exactly when the downstream is unhealthy. Exponential backoff spaces attempts farther apart, giving the dependency time to recover. Jitter randomizes delays so many service instances do not all retry at the same moments.

This makes retries more polite and reduces repeated traffic spikes.

#### Deep dive

Retries still need limits: maximum attempts, maximum delay, total deadline and retryable error classification.

#### Production angle

Backoff and jitter are basic defenses against retry storms during outages, deployments and failovers.

#### Traps / caveats

- Backoff does not make unsafe operations safe.
- Too much backoff can exceed user latency budgets.
- Multiple retry layers can multiply attempts.

#### Optional Anki

Q: Why add jitter to retry backoff?
A: To avoid synchronized retry bursts.

</details>

<a id="hcr-retry-003"></a>

<details>
<summary><strong>HCR-RETRY-003. How should retry policies respect `Retry-After` and server-provided retry guidance?</strong></summary>

#### Short answer

Clients should treat retry guidance as an upper-level contract and retry only if it fits local deadlines, safety rules and quotas.

#### Interview answer

`Retry-After` on `429` or `503` tells clients when the server believes retry may be acceptable. A Java client should parse both seconds and HTTP-date forms, cap the delay to local policy and avoid retrying if the caller's deadline will expire first.

It should also preserve idempotency rules. A server saying "retry later" does not make a non-idempotent write safe.

#### Deep dive

For third-party APIs, the documented quota and retry guidance should drive client-side throttling. If a fleet ignores guidance, it can keep itself throttled for longer.

#### Production angle

Respecting server guidance reduces quota violations and helps downstream systems recover.

#### Traps / caveats

- Do not sleep past the caller's deadline.
- Do not retry immediately after `429`.
- Be careful with clock skew for HTTP-date values.

#### Optional Anki

Q: Common status that often includes `Retry-After`?
A: `429 Too Many Requests` or `503 Service Unavailable`.

</details>

<a id="hcr-retry-004"></a>

<details>
<summary><strong>HCR-RETRY-004. How do idempotency keys make retries safer?</strong></summary>

#### Short answer

They let the server recognize repeated attempts for the same command and avoid executing side effects twice.

#### Interview answer

For operations like payment creation or order placement, the client may time out after the server has committed. If the client retries with the same idempotency key, the server can return the original result instead of creating a duplicate.

The key must be stored durably and checked atomically with the business operation.

#### Deep dive

Good idempotency designs also store a request fingerprint, operation state, response status and retention window. Reusing the same key with a different payload should be rejected.

#### Production angle

Idempotency keys are essential for safe retries over unreliable networks.

#### Traps / caveats

- In-memory idempotency state fails after restart.
- Keys need expiration but not too soon.
- Idempotency does not replace reconciliation.

#### Optional Anki

Q: What does an idempotency key prevent?
A: Duplicate side effects from retried commands.

</details>

<a id="hcr-retry-005"></a>

<details>
<summary><strong>HCR-RETRY-005. Which HTTP methods are usually safe or idempotent enough to retry?</strong></summary>

#### Short answer

`GET`, `HEAD` and `OPTIONS` are defined as safe; `PUT` and `DELETE` are idempotent by intent; `POST` needs extra care.

#### Interview answer

Safe methods should not change server state from the client's point of view, so they are usually retry candidates. Idempotent methods can be repeated with the same intended final effect, so `PUT` and `DELETE` are often retryable.

`POST` is commonly used for commands that create side effects, so it should be retried only with idempotency keys or a clear operation contract.

#### Deep dive

Real APIs can violate method semantics. The retry decision should be based on the API contract, not only the method name.

#### Production angle

Correct method semantics make client retries, caching and incident recovery much safer.

#### Traps / caveats

- A retried `DELETE` may return `404` after the first attempt succeeded.
- `GET` should not perform business writes.
- `TRACE` is defined as safe by HTTP semantics but is rarely relevant for backend application APIs and is often disabled for security reasons.
- `PUT` can still trigger side effects such as notifications if poorly designed.

#### Optional Anki

Q: Is `POST` automatically unsafe to retry?
A: Not if protected by durable idempotency, but it is unsafe by default.

</details>

<a id="hcr-retry-006"></a>

<details>
<summary><strong>HCR-RETRY-006. Why can retrying a timed-out `POST` create duplicate side effects?</strong></summary>

#### Short answer

The timeout may happen after the server completed the operation but before the client received the response.

#### Interview answer

When a client sends a `POST` to create an order or payment, the server may commit the transaction and then the response may be delayed or lost. From the client perspective, the call timed out. If it sends a new `POST` without the same idempotency key, the server may execute the command again.

This creates duplicate orders, double charges or repeated notifications.

#### Deep dive

The safe pattern is durable idempotency, operation status lookup and reconciliation for ambiguous outcomes.

#### Production angle

Payment and order creation APIs should be designed around ambiguous outcomes, not only success or failure.

#### Traps / caveats

- Client timeout does not mean rollback.
- Server logs may show success while client logs show timeout.
- Retrying with a new idempotency key defeats deduplication.

#### Optional Anki

Q: What does a timed-out write mean?
A: Unknown outcome.

</details>

<a id="hcr-retry-007"></a>

<details>
<summary><strong>HCR-RETRY-007. Which HTTP statuses and transport errors are usually retryable, and which are not?</strong></summary>

#### Short answer

Retry temporary transport failures and overload statuses cautiously; do not retry validation, authentication or business errors by default.

#### Interview answer

Connection reset, temporary DNS failure, timeout before response, `503`, `504` and sometimes `429` may be retryable if the operation is safe and the deadline allows it. `500` depends on the API contract.

`400`, `401`, `403`, most `404`, validation errors and business conflicts usually are not retryable without changing the request or credentials.

#### Deep dive

The exact policy should be dependency-specific. Some APIs use `409` for optimistic locking where retry after reload makes sense; others use it for a real business conflict.

#### Production angle

Retry classification affects downstream load, user latency and correctness.

#### Traps / caveats

- Do not retry all `5xx` blindly.
- Respect `Retry-After` for `429` and `503`.
- Transport errors after request write may still be ambiguous.

#### Optional Anki

Q: Are most `4xx` responses retryable?
A: Usually no.

</details>

<a id="hcr-retry-008"></a>

<details>
<summary><strong>HCR-RETRY-008. How should a client distinguish retryable transport errors from business errors?</strong></summary>

#### Short answer

Keep transport failure handling separate from domain result handling and classify errors explicitly.

#### Interview answer

Transport errors include connection failures, timeouts, TLS errors and malformed responses. Business errors are valid responses that say the operation cannot proceed, such as insufficient funds, invalid state or permission denied.

The client adapter should map raw HTTP details into clear exception or result types: retryable dependency failure, non-retryable dependency failure, business rejection and ambiguous write outcome.

#### Deep dive

Avoid exposing raw HTTP exceptions deep into business code. The application layer should make decisions using domain-relevant outcomes.

#### Production angle

Good error classification makes retry policy, logging and alerts predictable.

#### Traps / caveats

- A `200` response can still contain a business failure in some APIs.
- A `404` may be domain "not found", not infrastructure failure.
- Do not log sensitive error bodies.

#### Optional Anki

Q: Why separate transport errors from business errors?
A: They require different retry, alerting and user behavior.

</details>

<a id="hcr-retry-009"></a>

<details>
<summary><strong>HCR-RETRY-009. What is a retry budget?</strong></summary>

#### Short answer

A retry budget limits how much extra traffic retries may add.

#### Interview answer

Retries are useful only if they improve final success without overwhelming the dependency. A retry budget caps retry attempts as a fraction of original requests, per dependency, per time window or per caller deadline.

For example, a service might allow retries only while retry traffic stays below a small percentage of normal traffic and disable or throttle retries during outages.

#### Deep dive

Retry budgets are stronger than fixed max attempts alone because they react to fleet-wide behavior. They help avoid thousands of instances multiplying load at once.

#### Production angle

Retry budgets let operators see and control whether retries are helping or worsening an incident.

#### Traps / caveats

- Per-request max attempts do not protect a whole fleet.
- Retry attempts should be measured separately.
- Budgets should be dependency-specific.

#### Optional Anki

Q: What does a retry budget protect?
A: Downstream capacity and caller resources during failures.

</details>

<a id="hcr-retry-010"></a>

<details>
<summary><strong>HCR-RETRY-010. Why is retrying at every layer of a call chain dangerous?</strong></summary>

#### Short answer

Retries multiply across layers and can turn a small failure rate into a traffic explosion.

#### Interview answer

If a gateway retries three times, service A retries three times and service B's SDK retries three times, one user request can become dozens of downstream attempts. This increases latency, hides the original failure and overloads the service that is already struggling.

Retries should be coordinated. Often one layer should own retry policy for a given operation.

#### Deep dive

Multiple retry layers also make observability confusing because a single user request may produce many spans, logs and errors.

#### Production angle

During outages, layered retries are a common amplifier of cascading failures.

#### Traps / caveats

- SDKs may retry by default.
- Gateways and service meshes may also retry.
- More attempts can reduce final success if they consume scarce capacity.

#### Optional Anki

Q: What happens when three layers each retry three times?
A: Attempts multiply across the call chain.

</details>

<a id="hcr-retry-011"></a>

<details>
<summary><strong>HCR-RETRY-011. How should retries stop when the overall deadline is almost exhausted?</strong></summary>

#### Short answer

Before each retry, the client should check remaining time and skip attempts that cannot finish within the deadline.

#### Interview answer

A retry policy should not blindly run `maxAttempts`. It should consider the remaining deadline, expected attempt timeout, backoff delay and caller cancellation. If there is not enough time for a meaningful attempt, fail fast with a clear timeout result.

This prevents retries from causing the caller to exceed its SLO or upstream gateway timeout.

#### Deep dive

Deadline-aware retries are especially important in fan-out endpoints, where one dependency may consume time needed for the rest of the response.

#### Production angle

Deadline-aware retrying improves tail latency and avoids wasting work after the user has already timed out.

#### Traps / caveats

- Backoff sleep counts against the deadline.
- A final retry with too little time often only adds latency.
- Cancellation should stop queued retry attempts.

#### Optional Anki

Q: Should retry max attempts always be used?
A: No, stop when the remaining deadline is insufficient.

</details>

<a id="hcr-retry-012"></a>

<details>
<summary><strong>🧠 HCR-RETRY-012. What are hedged requests, and how are they different from retries?</strong></summary>

#### Short answer

Hedged requests send a duplicate request before the first one fails, usually to reduce tail latency.

#### Interview answer

A retry happens after an attempt fails or times out. A hedged request starts a second attempt after a short delay while the first is still running. The client uses whichever succeeds first and cancels or ignores the other.

Hedging can reduce p99 latency when slow outliers are independent, but it increases load and is dangerous for side-effecting operations unless they are idempotent.

#### Deep dive

Hedging works best for read-only calls to replicated services with spare capacity. It should be controlled by budgets and disabled during overload.

#### Production angle

Hedging can improve latency but can also double traffic exactly when a dependency is degraded.

#### Traps / caveats

- Do not hedge non-idempotent writes.
- Hedging needs load and cancellation controls.
- It can hide the real tail-latency source.

#### Optional Anki

Q: Retry versus hedge?
A: Retry after failure; hedge before failure to race a slow attempt.

</details>
