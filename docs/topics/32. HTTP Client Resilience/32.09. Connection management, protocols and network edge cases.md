# Connection management, protocols and network edge cases

<a id="hcr-net-001"></a>

<details>
<summary><strong>HCR-NET-001. Why is connection reuse important for HTTP client latency and throughput?</strong></summary>

#### Short answer

Reusing connections avoids repeated TCP and TLS setup and improves throughput.

#### Interview answer

Opening a new connection for every request adds DNS, TCP handshake, TLS handshake and kernel resource cost. Reuse lets the client send requests over existing connections, reducing latency and CPU overhead.

In Java services, connection reuse is usually handled by the HTTP client pool. Correct pool configuration is part of resilience because it controls concurrency and resource usage.

#### Deep dive

Connection reuse is especially important for TLS-heavy traffic and high-throughput internal service calls.

#### Production angle

Poor reuse can cause latency spikes, high CPU, ephemeral port pressure and downstream connection churn.

#### Traps / caveats

- Reuse requires response bodies to be consumed or closed.
- Idle connections can become stale.
- Reuse does not remove the need for timeouts.

#### Optional Anki

Q: What setup cost does connection reuse avoid?
A: Repeated TCP/TLS handshakes.

</details>

<details>
<summary><strong>HCR-NET-002. How can stale keep-alive connections, idle eviction and unclosed response bodies cause intermittent failures?</strong></summary>

#### Short answer

They can make the pool hand out dead connections or prevent connections from returning to the pool.

#### Interview answer

A keep-alive connection can be closed by the server, proxy or load balancer while the client still thinks it is reusable. The next request may fail with connection reset. Idle eviction and stale-connection validation reduce this risk.

Separately, if response bodies are not fully consumed or closed, the client may not release the connection back to the pool, causing pool exhaustion.

#### Deep dive

These problems are often intermittent because they depend on idle time, traffic patterns and proxy behavior.

#### Production angle

Symptoms include sporadic connection resets, pool acquisition timeouts and failures after quiet periods.

#### Traps / caveats

- Do not ignore response body cleanup on error paths.
- Idle timeout should be lower than upstream/load balancer idle close where possible.
- Pool exhaustion may be a leak, not a small pool.

#### Optional Anki

Q: What happens if response bodies are not closed?
A: Connections may not return to the pool.

</details>

<details>
<summary><strong>HCR-NET-003. How can DNS caching affect failover to a new IP address?</strong></summary>

#### Short answer

Stale DNS cache can keep clients sending traffic to old or unhealthy addresses after failover.

#### Interview answer

Java processes, OS resolvers, service meshes and HTTP clients may cache DNS results. If a dependency fails over to new IPs, clients with long cache TTLs may continue using old addresses until cache expiration or connection reset.

This matters for blue-green deployments, regional failover and third-party endpoint changes.

#### Deep dive

DNS behavior also interacts with connection pools. Even after DNS changes, existing pooled connections may keep using old endpoints.

#### Production angle

During failover incidents, check DNS answers from inside pods, JVM DNS TTL settings, mesh behavior and connection pool reuse.

#### Traps / caveats

- Low DNS TTL does not force existing connections to close.
- Different environments may use different resolvers.
- Infinite JVM DNS cache can break failover.

#### Optional Anki

Q: Why can DNS failover be slow for Java clients?
A: Cached DNS and existing pooled connections may keep old targets.

</details>

<a id="hcr-net-004"></a>

<details>
<summary><strong>HCR-NET-004. What should you check when HTTP calls fail only after deployment or pod restart?</strong></summary>

#### Short answer

Check DNS, TLS, warmup, connection pools, credentials, proxy/mesh config and changed base image or environment variables.

#### Interview answer

Deployment-only failures often come from configuration or environment changes rather than business code. I would compare old and new pods for endpoint URLs, secrets, truststores, certificates, DNS resolution, proxy variables, service mesh sidecars, egress policies and JVM options.

I would also check whether cold connections and TLS handshakes exceed very short timeouts right after restart.

#### Deep dive

Latency spikes after deploy can be caused by empty connection pools, DNS refresh, class loading, JIT warmup or downstream connection limits.

#### Production angle

Canary deploys should monitor outbound dependency errors and latency, not only inbound HTTP status.

#### Traps / caveats

- Do not assume all pods got the same secret/config.
- Do not disable TLS validation as a quick fix.
- Warmup behavior can hide until traffic shifts.

#### Optional Anki

Q: Common client-side cause of post-deploy latency spikes?
A: Cold connection pools and TLS handshakes.

</details>

<details>
<summary><strong>HCR-NET-005. What certificate, hostname verification or truststore issues can break outbound calls?</strong></summary>

#### Short answer

Expired certificates, missing CAs, hostname mismatch, wrong SNI, clock skew or changed truststores can break TLS.

#### Interview answer

TLS failures often show up as handshake exceptions, trust path errors or hostname verification failures. Causes include expired server certificates, missing intermediate CA, private CA not in the JVM truststore, wrong endpoint host, missing SNI, clock skew or base image changes.

The fix should preserve validation: update certificates or truststores, correct hostnames and rotate secrets safely.

#### Deep dive

Different environments may use different CAs or proxies, so a call can work in staging and fail in production or one region.

#### Production angle

Certificate expiry and truststore changes should be monitored and tested before deployment.

#### Traps / caveats

- Do not use "trust all" in production.
- Hostname verification protects against wrong endpoints.
- Do not log private keys or secret material.

#### Optional Anki

Q: Unsafe TLS production fix?
A: Disabling certificate or hostname validation broadly.

</details>

<a id="hcr-net-006"></a>

<details>
<summary><strong>HCR-NET-006. How do proxies, service meshes and load balancers change HTTP client failure modes?</strong></summary>

#### Short answer

They add hops that can inject timeouts, retries, connection resets, TLS behavior and routing decisions.

#### Interview answer

An outbound call may pass through a proxy, sidecar, gateway or load balancer. These components can have their own connection pools, idle timeouts, retries, circuit breakers, TLS certificates and error responses.

When diagnosing failures, the client must consider whether the error came from the application, sidecar, gateway, network policy or downstream service.

#### Deep dive

Retries in both the application and mesh can multiply attempts. Timeout budgets must be coordinated across layers.

#### Production angle

Mesh/gateway configuration changes can cause application incidents without code changes.

#### Traps / caveats

- Do not retry blindly at both mesh and app layers.
- Proxy idle timeouts can create stale client connections.
- Error status may be generated before the request reaches downstream.

#### Optional Anki

Q: Why inspect mesh config during HTTP client incidents?
A: It may own retries, timeouts, TLS and routing.

</details>

<details>
<summary><strong>🧠 HCR-NET-007. How do HTTP/2 multiplexing and HTTP/1.1 connection pools differ for resilience?</strong></summary>

#### Short answer

HTTP/1.1 usually uses multiple connections for concurrency; HTTP/2 can multiplex many streams over fewer connections.

#### Interview answer

With HTTP/1.1, each connection typically handles one in-flight request at a time unless pipelining is used. Concurrency often means more pooled connections. With HTTP/2, many streams can share one connection, reducing connection count and handshake overhead.

Resilience tuning changes: HTTP/2 stream limits, connection-level failures and head-of-line behavior at lower layers must be considered differently from HTTP/1.1 pool sizing.

#### Deep dive

If one HTTP/2 connection fails, many streams may fail together. Also, downstream or proxy stream limits can become the real bottleneck.

#### Production angle

Protocol changes should be load tested because old pool assumptions may no longer apply.

#### Traps / caveats

- Fewer connections does not mean unlimited concurrency.
- One connection can become a larger failure domain.
- Mesh and load balancers may terminate or translate protocols.

#### Optional Anki

Q: Main HTTP/2 concurrency feature?
A: Multiplexed streams over a connection.

</details>

<a id="hcr-net-008"></a>

<details>
<summary><strong>HCR-NET-008. Why should large response bodies, streaming and decompression be included in resilience design?</strong></summary>

#### Short answer

They can consume time, memory, CPU and connections beyond the initial response status.

#### Interview answer

An HTTP call is not finished when headers arrive. Large bodies can exhaust memory, slow down response processing or hold a pooled connection for a long time. Streaming responses can last indefinitely. Decompression can amplify payload size and CPU cost.

Clients should define max body size, streaming time limits, idle limits and parsing behavior.

#### Deep dive

For reactive clients, backpressure must be preserved. For blocking clients, streams must be consumed and closed safely.

#### Production angle

Large or malicious responses can become latency, memory or availability incidents.

#### Traps / caveats

- Do not read unbounded bodies into memory.
- Decompression bombs are possible.
- Streaming needs cancellation and cleanup.

#### Optional Anki

Q: Why limit response body size?
A: To protect memory, CPU and connection usage.

</details>

<details>
<summary><strong>HCR-NET-009. How should client-side load balancing and service discovery interact with retries?</strong></summary>

#### Short answer

Retries should avoid repeatedly hitting the same unhealthy instance when safe, while respecting idempotency and deadlines.

#### Interview answer

If service discovery returns multiple instances, retry policy may choose another instance after connection failure, timeout or selected `5xx`. This can help during rolling restarts or instance-level failures.

But retries should still be bounded, deadline-aware and safe for the operation. They should also respect load balancer health signals and not send traffic to instances marked unhealthy.

#### Deep dive

Retrying a different instance can be wrong if the operation depends on session affinity or non-replicated local state.

#### Production angle

Instance-level metrics help distinguish one bad pod from a dependency-wide outage.

#### Traps / caveats

- Do not retry writes to another instance without idempotency.
- Do not ignore stale service discovery data.
- Retry storms can spread load to healthy instances.

#### Optional Anki

Q: Why retry a different instance?
A: To recover from instance-specific failure when safe.

</details>

<details>
<summary><strong>HCR-NET-010. What can go wrong when an HTTP client follows redirects automatically, especially with authorization headers?</strong></summary>

#### Short answer

Redirects can send requests, methods or sensitive headers to unintended locations.

#### Interview answer

Automatic redirects are convenient for browsers but risky for service-to-service clients. A dependency may redirect to another host, scheme or path. If the client forwards `Authorization`, cookies or signed headers, credentials could leak to the wrong destination.

Redirects can also change method semantics, add latency, break tracing or bypass allowlists.

#### Deep dive

Backend clients should usually restrict redirects: same host only, safe methods only, no sensitive header forwarding unless explicitly allowed.

#### Production angle

Redirect behavior should be tested for auth flows, third-party APIs and proxy changes.

#### Traps / caveats

- Do not follow cross-host redirects blindly.
- Do not downgrade from HTTPS to HTTP.
- Count redirects in timeout and tracing.

#### Optional Anki

Q: Main redirect security risk?
A: Leaking sensitive headers to an unintended host.

</details>

<details>
<summary><strong>HCR-NET-011. How do you prevent SSRF or unsafe outbound calls when URLs are dynamic?</strong></summary>

#### Short answer

Use allowlists, strict URL parsing, DNS/IP validation and block internal metadata or private network targets.

#### Interview answer

If users or external data can influence outbound URLs, the service can become a server-side request forgery path. The client should allow only approved schemes, hosts and ports; resolve and validate DNS results; block private, loopback, link-local and metadata IP ranges; and avoid following redirects to disallowed targets.

Prefer identifiers mapped to known endpoints over accepting raw URLs.

#### Deep dive

Validation must happen after redirects and DNS resolution, not only on the original string. DNS rebinding is a risk.

#### Production angle

SSRF can expose cloud metadata, internal admin panels or private services.

#### Traps / caveats

- Do not validate URLs with string prefix checks only.
- Do not allow redirects to bypass checks.
- Do not log sensitive fetched content.

#### Optional Anki

Q: Safer design than accepting arbitrary callback URLs?
A: Map trusted identifiers to allowlisted endpoints.

</details>
