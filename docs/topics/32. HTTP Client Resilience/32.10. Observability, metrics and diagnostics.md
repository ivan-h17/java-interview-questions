# Observability, metrics and diagnostics

---

<a id="hcr-obs-001"></a>

<details>
<summary><strong>HCR-OBS-001. What metrics should be collected for every outbound HTTP client?</strong></summary>

#### Short answer

Collect request rate, latency, errors, timeouts, retries, pool state, circuit breaker state and fallback usage by dependency.

#### Interview answer

At minimum, expose outbound call count, success/failure count, status class, latency percentiles, timeout count, retry attempts, final failures, connection pool active/idle/pending, circuit breaker state, rate-limit rejections and fallback count.

Metrics should be tagged by dependency and operation, not by raw URL or user-controlled values.

#### Deep dive

Client-side metrics and server-side metrics will differ. The client may time out while the server later succeeds.

#### Production angle

Dependency-level metrics make it possible to detect whether an incident is local, network-related or downstream.

#### Traps / caveats

- Do not use high-cardinality tags like full URL with IDs.
- Separate original calls from retries.
- Include pool waits, not only response latency.

#### Optional Anki

Q: Key outbound metric tag?
A: Dependency or client name.

</details>

<a id="hcr-obs-002"></a>

<details>
<summary><strong>HCR-OBS-002. Why should metrics distinguish original calls from retry attempts?</strong></summary>

#### Short answer

Because retry traffic can hide real demand and show whether retries are helping or amplifying failure.

#### Interview answer

If metrics only show total outbound calls, a retry storm may look like normal increased traffic. Separating original attempts, retry attempts and final outcomes shows whether retries improve success rate or simply add load and latency.

It also helps capacity planning because downstream systems see attempts, not user requests.

#### Deep dive

Useful metrics include first-attempt success rate, retry success rate, attempts per operation and final user-visible success.

#### Production angle

During incidents, operators need to know whether turning down retries will improve recovery.

#### Traps / caveats

- "Eventually succeeded" can still violate latency SLO.
- Retry attempts may be counted as errors by downstream.
- Multiple retry layers confuse metrics.

#### Optional Anki

Q: Why split retry metrics?
A: To see retry amplification and final success impact.

</details>

<a id="hcr-obs-003"></a>

<details>
<summary><strong>HCR-OBS-003. How should timeout, retry, fallback and circuit breaker events be logged?</strong></summary>

#### Short answer

Log structured, low-cardinality events with dependency, operation, policy outcome and correlation IDs.

#### Interview answer

Logs should identify the dependency, operation, attempt number, final outcome, timeout type, breaker state, fallback used and correlation/trace ID. They should avoid huge bodies and sensitive headers.

Retries should not create noisy error logs for every expected attempt. Usually the final failure is error-level; intermediate retry attempts are debug or structured events/metrics.

#### Deep dive

Logging policy should align with alerting. If every retry is an error, logs become useless during incidents.

#### Production angle

Structured logs help reconstruct what happened for one request without leaking secrets.

#### Traps / caveats

- Do not log `Authorization`, cookies or API keys.
- Avoid high-cardinality exception messages as metric labels.
- Do not swallow fallback events.

#### Optional Anki

Q: What should fallback logs include?
A: Dependency, reason, fallback type and correlation ID.

</details>

<a id="hcr-obs-004"></a>

<details>
<summary><strong>HCR-OBS-004. What tags or labels are useful for HTTP client metrics, and which are dangerous for cardinality?</strong></summary>

#### Short answer

Use stable tags like dependency, operation and status class; avoid raw URLs, IDs, tenant names and exception messages.

#### Interview answer

Useful labels include client name, dependency, logical operation, method, status class, exception type, retry attempt flag and outcome. Dangerous labels include full URL, query string, user ID, order ID, tenant ID, raw error text and dynamic hostnames.

High-cardinality labels can overload metrics storage and make dashboards slow or expensive.

#### Deep dive

For URLs, use route templates or logical operation names instead of concrete paths with identifiers.

#### Production angle

Good labels let teams group by dependency and failure mode without breaking the observability platform.

#### Traps / caveats

- Cardinality incidents are production incidents.
- Exception class is safer than exception message.
- Tenant-level metrics need controlled aggregation.

#### Optional Anki

Q: Why not tag metrics with full URL?
A: IDs and query parameters create high cardinality.

</details>

<a id="hcr-obs-005"></a>

<details>
<summary><strong>HCR-OBS-005. How should distributed tracing represent outbound HTTP calls?</strong></summary>

#### Short answer

Each outbound call should appear as a client span with method, target, status/error and timing, linked to the inbound request trace.

#### Interview answer

Tracing should show which downstream calls were made, how long they took and whether they failed. The client should propagate trace context, record method, dependency/host, route template where available, status code or error type and timing.

For retries and redirects, traces should make repeated attempts visible without exploding into unreadable noise.

#### Deep dive

Use semantic conventions and avoid recording sensitive URL query values or bodies.

#### Production angle

Traces help identify whether user latency is local processing, database work or a specific outbound dependency.

#### Traps / caveats

- Do not sample away all traces during incidents if possible.
- Do not expose secrets in span attributes.
- Async/reactive boundaries need context propagation.

#### Optional Anki

Q: What span kind represents outbound HTTP calls?
A: Client span.

</details>

<a id="hcr-obs-006"></a>

<details>
<summary><strong>HCR-OBS-006. What dashboards and alerts are useful for dependency health?</strong></summary>

#### Short answer

Dashboards should show latency, errors, timeouts, retries, saturation, breaker state and fallback use per dependency.

#### Interview answer

A useful dependency dashboard includes request rate, success rate, status codes, p95/p99 latency, timeout rate, retry attempts, retry success, circuit breaker state, pool pending/active counts, rate-limit events and fallback usage.

Alerts should focus on user impact and early warning: rising timeouts, high pool wait, sustained fallback ratio, open circuit for critical dependency or retries increasing without success.

#### Deep dive

Dashboards should separate critical and optional dependencies because their impact differs.

#### Production angle

Good dashboards let incident responders quickly decide whether to reduce retries, disable optional features or escalate to the dependency owner.

#### Traps / caveats

- Alerting on every single dependency error creates noise.
- Do not ignore fallback usage just because HTTP status is 200.
- Pool saturation is often earlier than total failure.

#### Optional Anki

Q: What metric exposes hidden degraded success?
A: Fallback usage rate.

</details>

<a id="hcr-obs-007"></a>

<details>
<summary><strong>HCR-OBS-007. How do you tell whether retries are helping or making an incident worse?</strong></summary>

#### Short answer

Compare retry success, final user success, added latency, downstream load and saturation.

#### Interview answer

Retries help when retry attempts succeed often enough within the latency budget and do not overload the dependency. They hurt when they increase QPS, p99 latency, pool saturation and timeout rate without improving final success.

I would inspect first-attempt success, attempts per operation, retry success rate, final failure rate, downstream QPS, breaker state and pool metrics.

#### Deep dive

Retries can look good if measured only by "retry eventually succeeded", but bad if they push user latency past the SLO.

#### Production angle

If retries are not improving final success, reduce or disable them before they amplify the outage.

#### Traps / caveats

- Do not ignore idempotency risk.
- Do not measure retries without latency.
- Downstream may see retry attempts as extra load.

#### Optional Anki

Q: Key retry health question?
A: Do retries improve final success within budget without adding harmful load?

</details>

<a id="hcr-obs-008"></a>

<details>
<summary><strong>🧠 HCR-OBS-008. How should retry attempts and redirects be represented in OpenTelemetry spans?</strong></summary>

#### Short answer

They should be visible as repeated client attempts, with attributes that preserve correlation and attempt context.

#### Interview answer

OpenTelemetry semantic conventions model outbound HTTP as client spans. Retries and redirects should not disappear inside one opaque span if they materially affect latency or behavior. Implementations commonly represent attempts as separate client spans under the same trace and include resend/attempt information where supported.

The goal is to let operators see that one logical dependency call involved multiple HTTP exchanges.

#### Deep dive

Span design should balance detail and noise. High-volume clients may need sampling or aggregation while preserving failed and slow traces.

#### Production angle

Clear retry/redirect spans explain why one user request caused multiple downstream calls.

#### Traps / caveats

- Do not leak full URLs with secrets.
- Keep retry attempts correlated to the original operation.
- Metrics should still count attempts separately.

#### Optional Anki

Q: Why expose retry attempts in traces?
A: To explain added latency and duplicated downstream calls.

</details>
