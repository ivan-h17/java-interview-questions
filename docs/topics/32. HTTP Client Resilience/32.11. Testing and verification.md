<a id="hcr-test-001"></a>

<details>
<summary><strong>HCR-TEST-001. How would you unit test retry logic without sleeping in tests?</strong></summary>

#### Short answer

Inject a fake clock, scheduler or retry abstraction and assert attempts, delays and stop conditions deterministically.

#### Interview answer

Tests should not wait real seconds for retry backoff. I would isolate the retry policy, inject a controllable scheduler or clock, and use a fake dependency that fails and then succeeds. The test should assert which errors are retried, how many attempts happen, whether backoff is requested and whether deadlines stop retries.

For library-based retries, use test hooks or configure very small deterministic delays only in integration tests.

#### Deep dive

Retry tests should cover both success-after-retry and no-retry cases, such as validation errors or exhausted deadlines.

#### Production angle

Deterministic retry tests prevent accidental infinite retries or unsafe retrying of writes.

#### Traps / caveats

- Avoid `Thread.sleep()` in unit tests.
- Test non-retryable errors.
- Assert final outcome and attempt count.

#### Optional Anki

Q: How to test backoff without sleeping?
A: Use a fake clock/scheduler or policy abstraction.

</details>

<details>
<summary><strong>HCR-TEST-002. How would you integration test HTTP client timeouts?</strong></summary>

#### Short answer

Use a fake server that delays connection, headers or body and assert the client fails within the expected budget.

#### Interview answer

I would run a local fake server such as WireMock or MockWebServer and configure endpoints that delay responses, stream slowly, close connections or never send a body. Then I would point the real client configuration at that server and assert timeout type, elapsed time and resource cleanup.

The test should cover connection/pool acquisition when possible, response delay and slow body behavior.

#### Deep dive

For precise timing, use generous assertions and avoid relying on tiny millisecond thresholds. The goal is behavior, not benchmarking.

#### Production angle

Timeout tests catch unsafe client defaults before production incidents.

#### Traps / caveats

- Do not test only happy-path serialization.
- Ensure failed calls release connections.
- Account for CI timing variability.

#### Optional Anki

Q: Best tool style for HTTP timeout integration tests?
A: A controllable fake HTTP server.

</details>

<a id="hcr-test-003"></a>

<details>
<summary><strong>HCR-TEST-003. How can WireMock, MockWebServer or similar tools help test HTTP clients?</strong></summary>

#### Short answer

They let tests exercise real HTTP serialization, headers, status mapping and resilience behavior against a controlled server.

#### Interview answer

Mocking the Java client object often misses the important behavior: actual URL, headers, JSON shape, status mapping, timeouts and retries. A fake HTTP server lets the real client send real requests and receive configured responses.

I would use it to test success, `4xx`, `5xx`, malformed body, slow response, headers, auth and idempotency keys.

#### Deep dive

These tests are especially useful for adapter classes that translate remote API details into application-level results.

#### Production angle

Fake-server tests reduce risk when dependency contracts or client configuration change.

#### Traps / caveats

- Keep fake responses aligned with the real API.
- Verify the request shape, not only the response.
- Do not overfit tests to implementation internals.

#### Optional Anki

Q: Why prefer fake server over mocking client internals?
A: It tests real HTTP behavior and configuration.

</details>

<a id="hcr-test-004"></a>

<details>
<summary><strong>HCR-TEST-004. How would you test fallback behavior without hiding real errors?</strong></summary>

#### Short answer

Test both fallback output and explicit telemetry/error signals that prove degradation was visible.

#### Interview answer

Fallback tests should assert that fallback is used only for allowed failures and that critical failures still fail. They should verify response shape, freshness indicators, logs/metrics/events and that the primary exception is not silently swallowed.

For optional data, assert the degraded response is explicit. For critical data, assert no unsafe fallback happens.

#### Deep dive

Fallback tests should include stale-data age limits and behavior when fallback data is unavailable too.

#### Production angle

Good fallback tests prevent "successful" responses that hide outages or return unsafe data.

#### Traps / caveats

- Do not assert only HTTP 200.
- Test forbidden fallback paths.
- Verify fallback metrics.

#### Optional Anki

Q: What must fallback tests verify besides response data?
A: Degradation telemetry.

</details>

<a id="hcr-test-005"></a>

<details>
<summary><strong>HCR-TEST-005. What should be verified in a load test before enabling retries in production?</strong></summary>

#### Short answer

Verify final success, p99 latency, downstream QPS, retry volume, pool saturation and behavior under partial failure.

#### Interview answer

Retries can look safe in unit tests and fail under load. Before enabling them, I would test normal traffic, dependency slowdowns, intermittent `5xx`, `429`, connection resets and timeouts. I would measure original calls versus retry attempts, final user success, p95/p99 latency, pool waits, breaker state and downstream load.

The policy is only useful if it improves final success within the latency budget.

#### Deep dive

Load tests should include multiple service instances because retry amplification is a fleet behavior.

#### Production angle

This prevents deploying a retry policy that makes incidents worse.

#### Traps / caveats

- Do not test only a single instance.
- Do not ignore quota or rate-limit behavior.
- Watch tail latency, not only average success.

#### Optional Anki

Q: Key retry load-test metric?
A: Final success rate versus added latency and retry load.

</details>

<a id="hcr-test-006"></a>

<details>
<summary><strong>HCR-TEST-006. How would you verify that client metrics and traces are emitted correctly?</strong></summary>

#### Short answer

Run client calls through success, failure, retry and fallback paths and assert metrics, labels and spans.

#### Interview answer

I would test that outbound calls emit dependency-level metrics with stable labels, latency, status/error, retry count and fallback/circuit breaker events. For tracing, I would verify that client spans exist, trace context is propagated and failed calls include useful error attributes.

This can be done with in-memory metric registries, test exporters or integration tests against an observability collector.

#### Deep dive

Also verify cardinality: tags should use operation names or route templates, not raw IDs or query strings.

#### Production angle

Telemetry tests prevent silent observability regressions after client refactoring.

#### Traps / caveats

- Do not tag with full URL.
- Verify retry attempts separately from final result.
- Redact secrets in spans and logs.

#### Optional Anki

Q: What should observability tests catch?
A: Missing metrics/traces and dangerous high-cardinality labels.

</details>

<details>
<summary><strong>🧠 HCR-TEST-007. When are Toxiproxy, network fault injection or controlled chaos experiments useful?</strong></summary>

#### Short answer

They are useful when you need to validate behavior under realistic network failures that fake responses do not cover.

#### Interview answer

Fake servers are good for status codes and delays, but real networks fail in messier ways: latency spikes, packet loss, connection resets, half-open connections and DNS/TLS issues. Tools like Toxiproxy or controlled chaos experiments can simulate these failures against staging or carefully scoped production traffic.

Use them for critical dependencies after basic tests and observability are already in place.

#### Deep dive

Chaos experiments need a hypothesis, blast-radius limit, rollback plan and monitoring. They are not random breakage.

#### Production angle

They prove whether timeouts, circuit breakers, fallback and alerts work before a real incident.

#### Traps / caveats

- Do not run broad fault injection without approval and rollback.
- Start in lower environments.
- Measure user impact and recovery, not only failure.

#### Optional Anki

Q: What makes a chaos experiment controlled?
A: Clear hypothesis, limited blast radius, monitoring and rollback.

</details>
