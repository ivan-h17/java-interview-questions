# Timeout, deadline and latency budget design

---

<a id="hcr-time-001"></a>

<details>
<summary><strong>HCR-TIME-001. What is the difference between connect timeout, read timeout, request timeout and overall deadline?</strong></summary>

#### Short answer

They limit different phases: connection establishment, waiting for data, one HTTP attempt and the whole user operation.

#### Interview answer

Connect timeout limits how long the client waits to establish a connection. Read or response timeout limits waiting for response data after the request is sent. Request timeout often means a per-attempt limit for one HTTP exchange, depending on the library.

An overall deadline is broader: it caps the full operation, including connection pool wait, DNS, TLS, retries, redirects and response processing. In production, the overall deadline is usually the most important boundary because users and upstream services care about end-to-end time.

#### Deep dive

Timeout names vary across `RestClient`, `WebClient`, Apache HttpClient, Reactor Netty and Java `HttpClient`, so you must verify what each setting actually covers.

#### Production angle

Layered timeouts prevent stuck calls and keep retry policies inside the caller's latency budget.

#### Traps / caveats

- Socket read timeout is not the same as total deadline.
- Pool acquisition wait can consume the whole request budget.
- Retries multiply per-attempt timeout cost.

#### Optional Anki

Q: What is an overall deadline?
A: The maximum time allowed for the whole operation, including attempts and overhead.

</details>

<a id="hcr-time-002"></a>

<details>
<summary><strong>HCR-TIME-002. Why are missing HTTP client timeouts dangerous?</strong></summary>

#### Short answer

Missing timeouts let slow or stuck calls hold threads, connections and memory for too long.

#### Interview answer

If a downstream service stops responding and the client has no timeout, callers can wait indefinitely. In a servlet service, request threads block. In async workers, executor queues grow. In HTTP clients, connection pools fill. Eventually unrelated endpoints may fail because shared resources are exhausted.

Timeouts turn uncontrolled waiting into predictable failure that can be handled, measured and isolated.

#### Deep dive

Timeouts should be paired with cancellation, pool limits, circuit breakers and metrics. A timeout that does not release resources or stop queued work is only partly useful.

#### Production angle

Many cascading failures start with one dependency slowdown and clients that wait far longer than the user-facing SLO allows.

#### Traps / caveats

- Default timeouts may be infinite or too high.
- Retrying without timeouts can still hang.
- Increasing timeouts during incidents can worsen saturation.

#### Optional Anki

Q: Main production risk of missing HTTP timeouts?
A: Resource exhaustion while waiting on slow dependencies.

</details>

<a id="hcr-time-003"></a>

<details>
<summary><strong>HCR-TIME-003. What is a timeout budget?</strong></summary>

#### Short answer

A timeout budget is the portion of the caller's latency limit allocated to a downstream operation.

#### Interview answer

If an endpoint must respond in 500 ms, it cannot spend 500 ms on one dependency and still do database work, serialization and other calls. A timeout budget divides the available time across local processing, downstream calls, retries and safety margin.

The budget should reflect business SLOs, dependency latency distribution and whether calls are sequential or parallel.

#### Deep dive

Budgets are more useful than arbitrary timeouts because they make trade-offs explicit. For example, two sequential downstream calls need separate limits that fit within the caller's remaining deadline.

#### Production angle

Budgeting keeps p99 latency, retry behavior and upstream gateway timeouts aligned.

#### Traps / caveats

- Do not set downstream timeouts longer than the upstream timeout.
- Do not forget time spent waiting for a connection from the pool.
- Retries need their own budget.

#### Optional Anki

Q: What should drive timeout values?
A: Caller deadline, dependency latency and operation criticality.

</details>

<a id="hcr-time-004"></a>

<details>
<summary><strong>HCR-TIME-004. How should timeouts propagate across nested service calls?</strong></summary>

#### Short answer

Each service should pass or derive a remaining deadline so downstream calls cannot outlive the caller's request.

#### Interview answer

In nested calls, the upstream's deadline should constrain every downstream operation. If service A has 300 ms left and calls service B, B should not spend 2 seconds calling service C. It should use the remaining budget or fail fast.

This can be implemented through explicit request context, deadline headers, framework context or service-level policy. The exact mechanism matters less than preserving the invariant: work should stop when the caller no longer needs the result.

#### Deep dive

Deadline propagation is especially important for fan-out calls because a single slow branch can hold the whole response hostage.

#### Production angle

Without propagated deadlines, downstream services keep doing useless work after clients have timed out, increasing load during incidents.

#### Traps / caveats

- Header deadlines must be validated; do not blindly trust external clients.
- Time clocks and units must be handled consistently.
- Cancellation should release local resources where possible.

#### Optional Anki

Q: Why propagate deadlines?
A: To stop nested work from exceeding the caller's remaining time.

</details>

<a id="hcr-time-005"></a>

<details>
<summary><strong>HCR-TIME-005. How do you choose timeout values from downstream latency percentiles?</strong></summary>

#### Short answer

Start from the caller's budget, then use downstream p95/p99 latency, variance and criticality to choose a value with a small false-timeout rate.

#### Interview answer

I would not pick timeouts from guesses. I would inspect dependency latency percentiles under normal and peak load, decide how much user latency can be spent there, and choose a timeout that fits the caller's budget while avoiding excessive false failures.

For a stable internal service, timeout may be near p99 plus margin. For a variable third-party API, the service may need shorter timeouts, fallback, async workflow or a different user experience.

#### Deep dive

Timeouts should include connection pool wait, connect, TLS, request and response body handling if those phases affect user latency.

#### Production angle

Timeout values should be revisited after traffic growth, dependency changes or SLO changes.

#### Traps / caveats

- Average latency is not enough.
- Too many false timeouts can create retries and overload.
- Very high timeouts hide incidents and consume resources.

#### Optional Anki

Q: Which latency percentiles matter most for timeout design?
A: Tail percentiles such as p95, p99 and sometimes p99.9.

</details>

<a id="hcr-time-006"></a>

<details>
<summary><strong>HCR-TIME-006. What can go wrong when timeouts are too low or too high?</strong></summary>

#### Short answer

Too-low timeouts create false failures; too-high timeouts waste resources and delay recovery.

#### Interview answer

If a timeout is too low, normal latency variance can be mistaken for failure. That causes unnecessary retries, user errors, noisy alerts and pressure on the dependency.

If a timeout is too high, calls wait long after the user has given up. Threads, connections and memory remain occupied, queues grow and p99 latency worsens. During incidents, high timeouts make the caller slow instead of failing quickly.

#### Deep dive

Timeouts should be tuned with retry policy. Three attempts with a 1 second timeout can already exceed many API latency budgets.

#### Production angle

The right timeout is a trade-off between user experience, dependency behavior and resource protection.

#### Traps / caveats

- Do not "fix" timeouts by only raising them.
- Do not set every dependency to the same timeout.
- Watch timeout rate after changing values.

#### Optional Anki

Q: Symptom of too-low timeouts?
A: False failures and unnecessary retries during normal latency spikes.

</details>

<a id="hcr-time-007"></a>

<details>
<summary><strong>HCR-TIME-007. Should DNS lookup, TLS handshake and connection pool acquisition be covered by the timeout budget?</strong></summary>

#### Short answer

Yes. They consume real user-visible time and can be failure points.

#### Interview answer

A user does not care whether 300 ms was spent on DNS, TLS, waiting for a pooled connection or reading the body. All of it contributes to latency. A robust client budget should include connection acquisition, connect, TLS handshake, request transmission, response headers and body consumption.

Different client libraries expose these phases differently, so configuration needs to be verified rather than assumed.

#### Deep dive

Pool acquisition timeout is easy to miss. If all connections are busy, a call may wait locally before it even attempts the network.

#### Production angle

DNS, TLS and pool waits often explain deployment-only or high-concurrency failures.

#### Traps / caveats

- A connect timeout does not cover waiting for a pooled connection.
- TLS handshake can dominate very short timeouts.
- DNS caching can hide failover behavior.

#### Optional Anki

Q: Why include pool acquisition in timeout budgets?
A: Waiting locally still consumes user latency and request resources.

</details>

<a id="hcr-time-008"></a>

<details>
<summary><strong>🧠 HCR-TIME-008. How should a client behave when the caller has already cancelled the request?</strong></summary>

#### Short answer

It should stop unnecessary work, cancel pending calls when possible and release resources promptly.

#### Interview answer

If the upstream caller disconnects or its deadline expires, continuing expensive downstream calls usually wastes capacity. The service should propagate cancellation to async tasks, reactive chains or HTTP calls where the library supports it. It should also avoid starting new retries after cancellation.

For side-effecting operations, cancellation must be handled carefully. If the request was already sent, the client may not know whether the server committed the operation.

#### Deep dive

Cancellation is easier with structured concurrency or reactive pipelines than with ad hoc background tasks. Blocking clients may need interruptible execution and bounded executors.

#### Production angle

Ignoring cancellation creates load during traffic spikes and can keep downstream systems busy with results nobody will use.

#### Traps / caveats

- Cancellation is not rollback.
- Do not abandon reconciliation for side-effecting calls.
- Some HTTP clients cannot cancel already-sent work completely.

#### Optional Anki

Q: Does client cancellation prove server-side work stopped?
A: No.

</details>

<details>
<summary><strong>🧠 HCR-TIME-009. Why can socket-level read timeouts be misleading as end-to-end HTTP timeouts?</strong></summary>

#### Short answer

A read timeout may only limit inactivity between reads, not the total request duration.

#### Interview answer

Socket read timeout commonly means "how long to wait for data on the socket" or "how long between packets", depending on the client. A slow streaming response can keep sending small chunks and never hit the read timeout while the overall operation lasts too long.

End-to-end HTTP timeout should cover the whole operation: pool wait, connect, TLS, request, response headers, body and retries.

#### Deep dive

This distinction matters for large downloads, streaming APIs and decompression. The response can be active but still violate the caller's latency budget.

#### Production angle

Relying only on read timeout can let requests run past gateway deadlines, leaving local resources occupied after the user has gone.

#### Traps / caveats

- Read timeout is not a complete deadline.
- Streaming APIs need separate idle and total-duration policies.
- Large bodies need size and time limits.

#### Optional Anki

Q: Why is read timeout not enough?
A: It may measure socket inactivity rather than total operation time.

</details>
