# Circuit breakers and failure classification

---

<a id="hcr-cb-001"></a>

<details>
<summary><strong>HCR-CB-001. What is a circuit breaker?</strong></summary>

#### Short answer

A circuit breaker temporarily stops calls to an unhealthy dependency so failures happen fast and recovery has room.

#### Interview answer

A circuit breaker observes calls to a dependency. If failures, timeouts or slow calls exceed configured thresholds, it opens and rejects new calls immediately. After a wait period, it allows limited trial calls to check whether the dependency recovered.

It protects the caller from wasting resources on calls likely to fail and protects the downstream from continued pressure during an incident.

#### Deep dive

A circuit breaker is not a timeout, retry policy or concurrency limiter. It should be combined with those patterns, not used as a replacement.

#### Production angle

Open circuit state should be visible in metrics and alerts because it directly changes user-facing behavior.

#### Traps / caveats

- A circuit breaker does not fix the dependency.
- It needs sensible failure classification.
- It should not hide critical outages behind silent fallback.

#### Optional Anki

Q: What does a circuit breaker do when open?
A: Rejects calls quickly or routes to explicit fallback.

</details>

<a id="hcr-cb-002"></a>

<details>
<summary><strong>HCR-CB-002. What are the Closed, Open and Half-Open circuit breaker states?</strong></summary>

#### Short answer

Closed allows calls, Open rejects calls, and Half-Open allows limited probes to test recovery.

#### Interview answer

In Closed state, calls go through and the breaker records outcomes. If the failure or slow-call threshold is exceeded, it moves to Open. In Open state, calls fail fast instead of hitting the dependency.

After a wait period, the breaker enters Half-Open and lets a limited number of trial calls through. If they succeed, it closes; if they fail, it opens again.

#### Deep dive

Some libraries add special states such as forced open, disabled or metrics-only, but Closed/Open/Half-Open are the core interview model.

#### Production angle

Half-Open protects recovering dependencies from full traffic while giving clients a controlled recovery path.

#### Traps / caveats

- Half-Open probe count should be limited.
- Open state should not be treated as success.
- Low-traffic dependencies may recover slowly if no calls trigger probes.

#### Optional Anki

Q: Purpose of Half-Open state?
A: Test recovery with limited traffic.

</details>

<a id="hcr-cb-003"></a>

<details>
<summary><strong>HCR-CB-003. When should a circuit breaker open?</strong></summary>

#### Short answer

It should open when enough recent calls show the dependency is failing or too slow beyond configured thresholds.

#### Interview answer

A breaker should open on dependency failures that are likely to make future calls fail: timeouts, connection failures, selected `5xx` statuses, or slow calls above a threshold. It should use a minimum call count so a tiny sample does not trip the breaker accidentally.

The exact threshold depends on dependency criticality, traffic volume and acceptable false positives.

#### Deep dive

For low-volume dependencies, failure-rate thresholds can be unstable. A small number of failures may look like 100 percent failure but not be statistically meaningful.

#### Production angle

Breaker thresholds should be tuned with production traffic patterns and reviewed after incidents.

#### Traps / caveats

- Do not open on client validation errors.
- Do not open based on one failure unless the operation is extremely critical.
- Slow-call thresholds need realistic latency baselines.

#### Optional Anki

Q: Why use a minimum call count?
A: To avoid opening based on too little data.

</details>

<a id="hcr-cb-004"></a>

<details>
<summary><strong>HCR-CB-004. What failures should be recorded by a circuit breaker, and which should be ignored?</strong></summary>

#### Short answer

Record dependency health failures; ignore caller mistakes and expected business outcomes.

#### Interview answer

A breaker should usually record timeouts, connection failures, selected server errors and slow calls. It should usually ignore validation errors, authentication failures caused by caller configuration, `404` for normal not-found cases and business rejections.

The rule is: count failures that indicate the downstream is unhealthy or unavailable, not failures caused by a bad request or valid domain decision.

#### Deep dive

Some statuses depend on contract. A `409` may be a business conflict, while a `429` may indicate overload and should trigger throttling or breaker logic.

#### Production angle

Bad classification can either open the breaker unnecessarily or keep sending traffic to a broken dependency.

#### Traps / caveats

- Do not count every exception automatically.
- Parsing errors may indicate contract drift and may deserve recording.
- Authentication failures can be local misconfiguration, not downstream outage.

#### Optional Anki

Q: Should `400 Bad Request` usually trip a circuit breaker?
A: No, it usually indicates a caller/request problem.

</details>

<a id="hcr-cb-005"></a>

<details>
<summary><strong>🧠 HCR-CB-005. How do failure-rate, slow-call-rate and sliding-window settings affect circuit breaker behavior?</strong></summary>

#### Short answer

They define what the breaker measures, over what sample, and when it decides the dependency is unhealthy.

#### Interview answer

Failure-rate threshold opens the breaker when too many calls fail. Slow-call-rate threshold opens when too many calls exceed a duration limit even if they eventually succeed. Sliding windows define the sample: count-based windows use recent N calls; time-based windows use calls within a recent time period.

The minimum number of calls matters because a percentage is meaningless with too few samples.

#### Deep dive

Slow-call detection can protect a dependency before it becomes fully unavailable. But aggressive slow-call thresholds can open during harmless latency spikes.

#### Production angle

These settings should match traffic volume. High-throughput and low-throughput dependencies need different windows and thresholds.

#### Traps / caveats

- A sliding window is not a concurrency limit.
- Too-small windows cause flapping.
- Too-large windows delay recovery.

#### Optional Anki

Q: Does a circuit breaker sliding window limit concurrent calls?
A: No; use a bulkhead for concurrency limits.

</details>

<a id="hcr-cb-006"></a>

<details>
<summary><strong>HCR-CB-006. How should retry and circuit breaker policies be ordered?</strong></summary>

#### Short answer

Usually, timeout each attempt, retry only safe failures, and let the circuit breaker observe the final or configured attempt outcomes deliberately.

#### Interview answer

Ordering changes behavior. If retry is outside the breaker, the breaker may see only the final result and hide individual failures. If retry is inside the breaker, every failed attempt may count and open the circuit faster.

The right choice depends on what you want the breaker to measure: user-visible operation failures or individual downstream attempts. The important part is to choose deliberately and verify metrics.

#### Deep dive

Retries should not continue when the breaker is open. Timeouts should be applied so calls do not hang before breaker decisions are made.

#### Production angle

Poor composition can create surprising metrics, excessive retries or delayed circuit opening.

#### Traps / caveats

- Retrying through an open circuit is pointless.
- Counting each retry as a breaker failure may open too aggressively.
- Counting only final result may hide downstream instability.

#### Optional Anki

Q: Why does retry/breaker order matter?
A: It changes load, metrics and when the breaker opens.

</details>

<a id="hcr-cb-007"></a>

<details>
<summary><strong>HCR-CB-007. What should a client return when the circuit is open?</strong></summary>

#### Short answer

Return an explicit failure or safe fallback that matches the operation's correctness requirements.

#### Interview answer

When a circuit is open, the client should not pretend the dependency succeeded. For optional features, it may return degraded data, stale cache or omit that part of the response. For critical operations, it should return a clear dependency-unavailable error, often mapped to `503`, `502` or a domain-specific unavailable state.

The response should be observable and, when appropriate, visible to callers as degraded.

#### Deep dive

Fallback policy belongs to business semantics. The HTTP client layer should not silently decide that stale prices, permissions or payment state are acceptable.

#### Production angle

Open-circuit responses must support incident triage: logs, metrics and traces should identify the dependency and breaker state.

#### Traps / caveats

- Do not return stale data for correctness-critical decisions.
- Do not hide open circuits from dashboards.
- Do not leak internal dependency details to public clients.

#### Optional Anki

Q: Should open circuit be treated as success?
A: No, unless an explicit safe fallback is used.

</details>
