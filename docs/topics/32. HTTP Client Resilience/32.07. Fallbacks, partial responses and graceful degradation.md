# Fallbacks, partial responses and graceful degradation

---

<a id="hcr-fall-001"></a>

<details>
<summary><strong>HCR-FALL-001. When is a fallback safe, and when is it dangerous?</strong></summary>

#### Short answer

A fallback is safe when degraded data is acceptable; it is dangerous when it can break correctness, security or money-related decisions.

#### Interview answer

Fallbacks are good for optional features: recommendations, avatars, secondary enrichment or non-critical analytics. Returning stale or default data may preserve the main user flow.

Fallbacks are dangerous for payments, permissions, pricing, balances, inventory reservations and compliance decisions. In those cases, stale or guessed data can be worse than an explicit failure.

#### Deep dive

Fallback policy should be a business decision, not an accidental catch block inside the HTTP client.

#### Production angle

Fallback usage should be counted and alerted on because it often indicates a dependency outage.

#### Traps / caveats

- Do not fallback to "allow" for authorization.
- Do not return stale prices without business approval.
- Do not hide degraded responses as fully successful.

#### Optional Anki

Q: Where are fallbacks most risky?
A: Security, financial and correctness-critical decisions.

</details>

<a id="hcr-fall-002"></a>

<details>
<summary><strong>HCR-FALL-002. What is the difference between fallback, retry and graceful degradation?</strong></summary>

#### Short answer

Retry repeats the primary action; fallback uses an alternative; graceful degradation preserves core behavior with reduced functionality.

#### Interview answer

Retry is for transient failures when repeating the operation is safe. Fallback is alternative behavior after the primary path fails, such as cached data or omitting optional content. Graceful degradation is the broader product/system behavior where important flows keep working even though some features are reduced.

They can be combined, but each has different correctness and latency trade-offs.

#### Deep dive

Retry increases load; fallback may reduce correctness; degradation changes user experience. A senior design names these trade-offs explicitly.

#### Production angle

Clear distinctions make incident response faster: teams know whether to retry less, open a breaker, disable a feature or serve degraded data.

#### Traps / caveats

- Do not retry before checking idempotency.
- Do not fallback silently for critical data.
- Graceful degradation still needs telemetry.

#### Optional Anki

Q: Retry versus fallback?
A: Retry repeats primary work; fallback uses alternative behavior.

</details>

<a id="hcr-fall-003"></a>

<details>
<summary><strong>HCR-FALL-003. How would you design partial results when optional downstream calls fail?</strong></summary>

#### Short answer

Return the core response, mark missing/degraded parts explicitly and emit telemetry for the failed dependency.

#### Interview answer

If a dashboard depends on required data plus optional enrichment, I would define which fields are mandatory and which can be omitted or stale. The API response should make degraded sections explicit where callers need to know, for example `recommendationsUnavailable` or a freshness timestamp.

The service should use short timeouts for optional calls and not let them block the entire response.

#### Deep dive

Partial response design is an API contract. Callers should not have to infer degradation from missing fields unless that is documented.

#### Production angle

Operators need metrics for fallback count, missing sections, dependency latency and user impact.

#### Traps / caveats

- Do not mark degraded responses as identical to complete responses.
- Do not expose internal stack traces.
- Keep required fields stable for compatibility.

#### Optional Anki

Q: What should partial responses expose?
A: Which optional data is missing or degraded when callers need to know.

</details>

<a id="hcr-fall-004"></a>

<details>
<summary><strong>HCR-FALL-004. When is returning stale cached data an acceptable fallback?</strong></summary>

#### Short answer

It is acceptable when the domain tolerates bounded staleness and the response clearly respects freshness limits.

#### Interview answer

Stale cache can be fine for product descriptions, recommendations, feature metadata or non-critical display data. It is risky for permissions, balances, inventory, prices and payment state.

The fallback should define maximum age, source, invalidation behavior and whether users or callers need a freshness indicator.

#### Deep dive

Stale fallback is safer when the cache is read-through for optional data and not the system of record for correctness-critical decisions.

#### Production angle

Sustained stale-cache usage should alert teams because it may hide a dependency outage.

#### Traps / caveats

- Stale data can violate legal or business rules.
- Cache fallback can overload the cache during dependency outages.
- Missing freshness metadata causes false confidence.

#### Optional Anki

Q: Key condition for stale fallback?
A: Bounded staleness accepted by the domain.

</details>

<a id="hcr-fall-005"></a>

<details>
<summary><strong>HCR-FALL-005. How can fallback logic hide a serious production issue?</strong></summary>

#### Short answer

If fallback returns successful-looking responses, users and dashboards may not reveal that the primary dependency is broken.

#### Interview answer

A fallback that always returns default data can make error rates look good while business quality collapses. For example, recommendations may be empty for all users, prices may be stale or permission checks may use old data.

Fallbacks must emit metrics, logs and traces that identify when they were used and why.

#### Deep dive

Fallbacks should have their own SLO or quality signal, not only count as HTTP success.

#### Production angle

Silent fallback can delay incident detection and create data correctness problems.

#### Traps / caveats

- Success rate can be misleading during fallback.
- Default values may corrupt downstream decisions.
- Alert on fallback ratio, not only errors.

#### Optional Anki

Q: Why track fallback usage?
A: It is often a hidden dependency failure signal.

</details>

<a id="hcr-fall-006"></a>

<details>
<summary><strong>HCR-FALL-006. When should a service fail the whole request instead of returning a degraded response?</strong></summary>

#### Short answer

Fail the request when degraded output would be incorrect, unsafe or misleading for the caller.

#### Interview answer

If the missing dependency is required for authorization, payment, pricing, balance, inventory reservation or compliance, returning guessed or stale data can violate correctness. The service should fail clearly, often with a retryable unavailable response if the caller can retry later.

For optional data, degraded response may be fine. The decision should be documented per use case.

#### Deep dive

Failing fast can be more reliable than returning a response that looks successful but causes bad business actions.

#### Production angle

Critical failures should have strong alerts, runbooks and clear error contracts.

#### Traps / caveats

- Do not optimize availability at the cost of correctness.
- Do not fail the whole request for optional cosmetic data.
- Avoid leaking internal dependency names externally.

#### Optional Anki

Q: What matters more for critical operations, availability or correctness?
A: Correctness.

</details>

<a id="hcr-fall-007"></a>

<details>
<summary><strong>🧠 HCR-FALL-007. What correctness risks appear when fallback data is used for payments, permissions or pricing?</strong></summary>

#### Short answer

Fallback data can authorize the wrong user, charge the wrong amount or make irreversible decisions from stale state.

#### Interview answer

Payments, permissions and pricing are correctness-critical. A stale permission cache may allow access after revocation. A stale price may undercharge or overcharge. A stale payment status may trigger duplicate capture or incorrect order state.

For these domains, fallback should usually be fail closed, manual review, asynchronous retry or reconciliation, not guessed success.

#### Deep dive

If fallback is allowed, it needs explicit business approval, freshness bounds, audit logs and repair procedures.

#### Production angle

Incorrect fallback can become a security incident, financial loss or compliance issue.

#### Traps / caveats

- "Better than failing" is false for many critical decisions.
- Auditability matters when fallback affects money or access.
- Reconciliation must cover ambiguous outcomes.

#### Optional Anki

Q: Safe default for failed authorization dependency?
A: Fail closed.

</details>
