# 13.04. Collector choice and trade-offs

---

<a id="mem-collect-001"></a>

<details>
<summary><strong>MEM-COLLECT-001. What garbage collectors are commonly relevant in modern HotSpot JVMs?</strong></summary>

#### Short answer

Commonly relevant collectors include G1, Parallel GC, ZGC, Shenandoah and sometimes Serial GC for very small workloads.

#### Interview answer

For backend services, G1 is a common general-purpose collector. Parallel GC is useful when throughput matters more than pause time. ZGC and Shenandoah target very low pause times, especially with larger heaps. Serial GC can be acceptable for tiny tools or constrained single-threaded workloads.

The right choice depends on workload, heap size, latency target, CPU budget and JDK version.

#### Deep dive

Collector capabilities and defaults change across Java versions, so a senior answer should avoid hard-coded assumptions and verify the runtime.

#### Production angle

Collector changes should be tested with production-like traffic, realistic heap sizes and latency SLOs.

#### Traps / caveats

- "Modern" depends on the JDK version and distribution.
- The default collector is not always optimal.
- Collector choice cannot fix bad allocation or retention by itself.

#### Optional Anki

Q: Which HotSpot collector is often a general-purpose backend default?
A: G1, depending on Java version and runtime settings.

</details>

<a id="mem-collect-002"></a>

<details>
<summary><strong>MEM-COLLECT-002. What is Parallel GC, and when would you use it?</strong></summary>

#### Short answer

Parallel GC is a throughput-oriented collector that uses multiple threads and can tolerate longer pauses.

#### Interview answer

Parallel GC focuses on maximizing application throughput rather than minimizing pause latency. It performs GC work with multiple threads, but collections are generally stop-the-world.

It can be a good fit for batch jobs, offline processing or services where throughput matters more than p99 latency.

#### Deep dive

Parallel GC may outperform low-pause collectors for CPU-heavy batch workloads because it spends less CPU on concurrent bookkeeping.

#### Production angle

Use it when latency SLOs allow pauses and throughput is the primary goal. Validate with real data sizes and job concurrency.

#### Traps / caveats

- It is usually a poor fit for latency-sensitive APIs.
- More GC threads can compete with application threads.
- Batch workloads still need memory bounds.

#### Optional Anki

Q: What is Parallel GC optimized for?
A: Throughput more than low pause latency.

</details>

<a id="mem-collect-003"></a>

<details>
<summary><strong>MEM-COLLECT-003. What is G1 GC, and why is it a common default choice?</strong></summary>

#### Short answer

G1 is a region-based generational collector designed to balance throughput and predictable pauses.

#### Interview answer

G1 divides the heap into regions and collects selected regions instead of always treating the heap as one contiguous young/old layout. It aims to meet a pause-time goal while maintaining reasonable throughput.

It is a common default because it works well for many server workloads without extreme tuning.

#### Deep dive

G1 performs young collections, concurrent marking and mixed collections that reclaim old regions with high garbage content.

#### Production angle

G1 is often the first collector to understand for Java backend services. Watch pause times, old-gen occupancy, humongous allocations, evacuation failures and allocation rate.

#### Traps / caveats

- `MaxGCPauseMillis` is a target, not a guarantee.
- G1 can still have Full GC fallback.
- Large live sets or humongous objects can hurt it.

#### Optional Anki

Q: What is the core idea of G1 regions?
A: Split the heap into regions and collect useful regions based on predicted value and pause goals.

</details>

<a id="mem-collect-004"></a>

<details>
<summary><strong>MEM-COLLECT-004. What is ZGC, and what problem does it try to solve?</strong></summary>

#### Short answer

ZGC is a low-latency collector designed to keep pause times very short, even with large heaps.

#### Interview answer

ZGC does most GC work concurrently while the application runs. It uses barriers and object relocation techniques to avoid long stop-the-world compaction pauses.

It is attractive for latency-sensitive services where long GC pauses are unacceptable.

#### Deep dive

ZGC trades some throughput and CPU overhead for low pauses. Newer JDK versions include generational improvements, but details depend on the runtime.

#### Production angle

Before switching to ZGC, test CPU headroom, latency distribution, allocation stalls, memory footprint and behavior under peak traffic.

#### Traps / caveats

- Low pause does not mean lower CPU.
- Low pause does not fix memory leaks.
- Version-specific ZGC behavior must be verified.

#### Optional Anki

Q: What is the main reason to consider ZGC?
A: Very short GC pause times.

</details>

<a id="mem-collect-005"></a>

<details>
<summary><strong>MEM-COLLECT-005. What is Shenandoah GC, and what problem does it try to solve?</strong></summary>

#### Short answer

Shenandoah is a low-pause collector that performs much of marking and evacuation concurrently.

#### Interview answer

Like ZGC, Shenandoah aims to reduce stop-the-world pause time by doing object graph tracing and relocation concurrently with application execution. It is designed for workloads where long pauses are more harmful than extra CPU overhead.

Availability and behavior depend on JDK version and distribution.

#### Deep dive

Shenandoah uses barriers to keep application reads/writes correct while objects may move concurrently.

#### Production angle

It should be evaluated with realistic traffic, CPU limits, heap sizes and tail-latency objectives.

#### Traps / caveats

- Do not assume every JDK distribution supports the same collectors.
- Concurrent work can cost CPU.
- Degenerated or Full GC cycles indicate the collector is failing to keep up.

#### Optional Anki

Q: What is Shenandoah optimized for?
A: Low pause times through concurrent GC work.

</details>

<a id="mem-collect-006"></a>

<details>
<summary><strong>MEM-COLLECT-006. How would you choose between G1, ZGC, Shenandoah and Parallel GC?</strong></summary>

#### Short answer

Choose based on latency target, throughput target, heap size, allocation behavior, CPU budget and JDK support.

#### Interview answer

Start with the workload. If it is a normal backend service, G1 is often a good baseline. If p99 latency is sensitive and heap is large, test ZGC or Shenandoah. If it is a batch job where throughput matters more than pause time, Parallel GC may be better.

Then validate with realistic load instead of relying on generic advice.

#### Deep dive

The collector is only one part of the system. Allocation rate, live set size, request concurrency, caches and container limits can dominate the outcome.

#### Production angle

Compare before/after using latency percentiles, GC pause distribution, CPU, RSS, allocation stalls, throughput and error rate.

#### Traps / caveats

- Do not switch collectors to hide a leak.
- Do not optimize for average latency only.
- Do not ignore CPU throttling in containers.

#### Optional Anki

Q: What should decide GC choice?
A: Measured workload trade-offs: latency, throughput, heap size, CPU and runtime support.

</details>

<a id="mem-collect-007"></a>

<details>
<summary><strong>MEM-COLLECT-007. What is the trade-off between throughput, latency, footprint and startup time?</strong></summary>

#### Short answer

Optimizing one JVM goal often costs another: lower pauses may use more CPU or memory; higher throughput may allow longer pauses.

#### Interview answer

Throughput is how much useful work the application completes. Latency is how long individual operations take, especially tail latency. Footprint is memory usage. Startup time is how quickly the process becomes ready.

JVM flags and collectors balance these goals differently.

#### Deep dive

Low-latency collectors often perform more concurrent bookkeeping. Throughput-oriented collectors may pause longer but spend less total overhead. Large heaps can reduce GC frequency but increase footprint and dump size.

#### Production angle

A senior answer should tie tuning to SLOs. An internal batch job and public API should not have the same GC goals.

#### Traps / caveats

- "Faster" is not a single dimension.
- More memory may reduce pauses but increase cost and recovery time.
- Startup optimizations can conflict with peak performance.

#### Optional Anki

Q: What is the common cost of low-pause GC?
A: More CPU and/or memory overhead.

</details>

<a id="mem-collect-008"></a>

<details>
<summary><strong>MEM-COLLECT-008. Why can a low-latency collector use more CPU than a throughput-oriented collector?</strong></summary>

#### Short answer

Low-latency collectors do more work concurrently and use barriers to avoid long pauses.

#### Interview answer

Collectors such as ZGC or Shenandoah keep pauses short by moving work out of stop-the-world phases. That work still has to happen: concurrent marking, relocation, barriers and metadata maintenance consume CPU while the application runs.

The result can be better p99 latency but lower raw throughput.

#### Deep dive

In CPU-limited containers, concurrent GC threads may compete with application threads and make latency worse if there is not enough headroom.

#### Production angle

When switching to a low-pause collector, watch CPU saturation, throttling, request latency, allocation stalls and throughput.

#### Traps / caveats

- Low-pause is not automatically lower-cost.
- CPU throttling can make concurrent GC fall behind.
- Batch jobs may prefer Parallel GC.

#### Optional Anki

Q: Why can ZGC increase CPU usage?
A: It performs more GC work concurrently and uses runtime barriers to keep pauses short.

</details>

<a id="mem-collect-009"></a>

<details>
<summary><strong>MEM-COLLECT-009. Why should GC choice be validated with production-like load tests?</strong></summary>

#### Short answer

GC behavior depends heavily on real allocation rate, live set, traffic shape and resource limits.

#### Interview answer

Synthetic tests often miss request concurrency, payload sizes, caches, warmup, downstream latency and container CPU/memory limits. A collector that looks good in a small benchmark may behave differently under peak traffic.

Production-like load reveals tail latency, promotion, native memory, allocation stalls and CPU trade-offs.

#### Deep dive

GC tuning is empirical. You need a baseline, one change at a time and enough runtime to include warmup and steady state.

#### Production angle

Validate against SLOs: p95/p99 latency, throughput, CPU, RSS, GC pause distribution, OOM risk and cost.

#### Traps / caveats

- Microbenchmarks rarely represent service memory behavior.
- Testing only average latency hides tail regressions.
- Short tests may miss leaks or cache growth.

#### Optional Anki

Q: Why is GC tuning empirical?
A: Collector behavior depends on real workload allocation and retention patterns.

</details>

<a id="mem-collect-010"></a>

<details>
<summary><strong>🧠 MEM-COLLECT-010. How do you check the default garbage collector for the Java version you run?</strong></summary>

#### Short answer

Check the actual JVM version, flags and startup logs instead of relying on memory.

#### Interview answer

The default collector can vary by Java version, VM distribution, heap size, platform and flags. To check it, inspect startup logs, `-Xlog:gc`, `java -XX:+PrintFlagsFinal -version`, `jcmd VM.flags` or runtime observability.

In an interview, say what is common, then say you would verify in the actual runtime.

#### Deep dive

Old advice may mention CMS or older defaults. Modern deployments also vary because container settings and vendor builds matter.

#### Production angle

During incidents, collect JVM command line, flags, version, container limits and GC log header before making tuning changes.

#### Traps / caveats

- Do not assume "modern Java" means one exact default forever.
- Old CMS tuning flags may be ignored or fail startup.
- Managed platforms may inject JVM flags.

#### Optional Anki

Q: What is the safest way to know the active collector?
A: Inspect the actual running JVM flags/logs.

</details>

<a id="mem-collect-011"></a>

<details>
<summary><strong>🧠 MEM-COLLECT-011. How did HotSpot collectors evolve from Serial GC and CMS to G1, ZGC and Shenandoah?</strong></summary>

#### Short answer

The evolution moved from simple stop-the-world collectors toward collectors that balance throughput, pause predictability and concurrent work.

#### Interview answer

Serial GC is simple and uses one GC thread, so it is suitable mainly for small heaps, tiny tools or constrained environments. Parallel GC improves throughput by using multiple GC threads, but it still accepts longer stop-the-world pauses.

CMS tried to reduce old-generation pauses by marking and sweeping concurrently, but it had fragmentation and tuning issues and is no longer the modern default direction. G1 replaced many CMS use cases with a region-based design, concurrent marking and more predictable pause targeting. ZGC and Shenandoah go further toward low pauses by doing more marking and relocation concurrently.

#### Deep dive

The key trade-off did not disappear. Serial and Parallel are simpler and can have good throughput, but pauses can be long. G1 adds region selection and pause goals. ZGC and Shenandoah use barriers and concurrent relocation to reduce pause time, usually at the cost of extra CPU, memory overhead and version-specific behavior.

In interviews, it is better to explain the direction of the trade-offs than to memorize every historical flag.

#### Production angle

Do not copy old CMS-era tuning into a modern service. Check the actual JDK, active collector and workload. For a normal backend service, G1 is often the baseline; low-pause collectors need validation against CPU budget, latency SLOs and heap size.

#### Traps / caveats

- CMS advice is often outdated for current JDKs.
- "Newer collector" does not automatically mean better for every workload.
- Collector availability and defaults depend on JDK version and distribution.
- Low pause often moves cost into concurrent CPU work and barriers.

#### Optional Anki

Q: What problem did G1 address compared with many CMS-era deployments?
A: More predictable region-based collection with pause goals and less fragmentation risk.

</details>
