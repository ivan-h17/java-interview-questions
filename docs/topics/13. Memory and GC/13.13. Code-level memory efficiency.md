# 13.13. Code-level memory efficiency

---

<a id="mem-code-001"></a>

<details>
<summary><strong>MEM-CODE-001. How can you reduce memory allocation in Java code?</strong></summary>

#### Short answer

Reduce unnecessary temporary objects, bound data structures, stream data incrementally and avoid retaining large graphs.

#### Interview answer

I would first measure allocation hotspots. Common fixes include avoiding repeated conversions, pre-sizing collections, streaming large payloads, reducing DTO copies, using primitive-friendly structures where justified and avoiding unbounded queues/caches.

The goal is not "zero allocation"; it is reducing allocation that affects latency, CPU or memory.

#### Deep dive

Modern JVM allocation is cheap, so blind micro-optimization can make code worse. Focus on hot paths and large object graphs.

#### Production angle

Use JFR or allocation profiling to find real hotspots before changing code.

#### Traps / caveats

- Do not optimize cold code.
- Object pooling often hurts more than it helps.
- Readability matters unless memory impact is proven.

#### Optional Anki

Q: What should guide memory allocation optimization?
A: Measurement of real allocation hotspots.

</details>

<a id="mem-code-002"></a>

<details>
<summary><strong>MEM-CODE-002. How can pre-sizing collections reduce allocation and rehashing?</strong></summary>

#### Short answer

Pre-sizing avoids repeated internal array growth, copying and hash table resizing.

#### Interview answer

Collections such as `ArrayList` and `HashMap` grow their internal storage as elements are added. If the expected size is known, setting initial capacity can reduce intermediate allocations and copying. For maps, it can also reduce rehashing.

This matters in hot paths and large batch processing.

#### Deep dive

For `HashMap`, capacity and load factor interact. Pre-sizing too large wastes memory; too small causes resizing.

#### Production angle

Pre-size when building large collections per request, per batch or during deserialization/mapping.

#### Traps / caveats

- Do not pre-size huge collections from untrusted input.
- Over-allocation wastes memory.
- For small collections, the gain may be irrelevant.

#### Optional Anki

Q: What does pre-sizing an `ArrayList` avoid?
A: Repeated internal array resizing and copying.

</details>

<a id="mem-code-003"></a>

<details>
<summary><strong>MEM-CODE-003. How can object pooling be harmful in modern Java, and when can it still make sense?</strong></summary>

#### Short answer

Pooling ordinary objects can increase complexity and retention; it is useful mainly for expensive native or reusable resources.

#### Interview answer

Modern JVMs allocate short-lived objects efficiently. Pooling normal Java objects can keep them alive longer, increase old-gen pressure, create synchronization overhead and introduce stale-state bugs. It often fights the garbage collector.

Pooling still makes sense for expensive resources such as database connections, threads, buffers in some I/O frameworks or objects with costly native allocation.

#### Deep dive

The key distinction is object allocation cost versus resource acquisition cost.

#### Production angle

Use proven pools with bounds, metrics and leak detection. Do not invent a pool for ordinary DTOs without profiling.

#### Traps / caveats

- Pools can become memory leaks.
- Pooled objects must be reset safely.
- Unbounded pools are dangerous under load.

#### Optional Anki

Q: Why is pooling ordinary Java objects often bad?
A: It can increase retention and complexity while GC already handles short-lived objects well.

</details>

<a id="mem-code-004"></a>

<details>
<summary><strong>MEM-CODE-004. How do unbounded collections cause production memory problems?</strong></summary>

#### Short answer

They grow with traffic, input cardinality or downstream slowness until memory is exhausted.

#### Interview answer

An unbounded `List`, `Map`, queue or cache has no hard memory limit. It may work in tests but fail in production when tenant count, request rate or key cardinality grows. If producers are faster than consumers, unbounded queues convert latency into memory growth.

Every long-lived collection needs an ownership and eviction story.

#### Deep dive

Thread-safe collections do not solve this; they only make concurrent access safer.

#### Production angle

Bound queues, caches and buffers. Monitor size, cardinality, age, eviction and rejection.

#### Traps / caveats

- `ConcurrentHashMap` can leak just as well as `HashMap`.
- TTL alone may not cap peak memory.
- "Temporary" collections become leaks if stored globally.

#### Optional Anki

Q: What is the main risk of an unbounded queue?
A: It turns overload into memory growth.

</details>

<a id="mem-code-005"></a>

<details>
<summary><strong>MEM-CODE-005. How can streams, lambdas and boxing create extra allocations?</strong></summary>

#### Short answer

They can create wrapper objects, intermediate containers, captured closures and boxed primitives.

#### Interview answer

Streams and lambdas are usually fine, but in hot paths they can allocate through boxing, collectors, grouping maps, temporary lists or captured objects. Boxing converts primitives into objects, which increases memory and GC pressure when repeated at scale.

Use primitive streams or loops when profiling shows a real problem.

#### Deep dive

The JIT can optimize some allocations away, but not all. Complex stream pipelines with collectors often allocate real data structures.

#### Production angle

Look for hot serialization, mapping and aggregation paths that allocate heavily per request.

#### Traps / caveats

- Do not ban streams globally.
- `Optional` fields and boxed counters can add footprint in large object graphs.
- Capturing `this` can retain more than intended.

#### Optional Anki

Q: What is boxing?
A: Wrapping a primitive value in an object such as `Integer`.

</details>

<a id="mem-code-006"></a>

<details>
<summary><strong>🧠 MEM-CODE-006. When can primitive collections reduce memory footprint?</strong></summary>

#### Short answer

They help when storing many primitive values where boxing overhead dominates memory.

#### Interview answer

Standard Java collections store objects, so `List<Integer>` stores references to boxed `Integer` objects. For millions of primitive values, boxing overhead can be much larger than the raw data. Primitive collections from specialized libraries store primitive values more compactly.

They are useful in memory-sensitive hot paths, not as a default style.

#### Deep dive

Primitive collections can improve memory locality and reduce GC pressure, but add dependencies and API differences.

#### Production angle

Consider them for large in-memory indexes, analytics, caches or high-cardinality counters after measuring footprint.

#### Traps / caveats

- They reduce readability and portability.
- They may not integrate with all frameworks.
- Gains are small for small collections.

#### Optional Anki

Q: Why does `List<Integer>` use more memory than an `int[]`?
A: It stores boxed objects and references, not raw primitive ints.

</details>

<a id="mem-code-007"></a>

<details>
<summary><strong>MEM-CODE-007. How can large DTO graphs increase memory pressure?</strong></summary>

#### Short answer

Large DTO graphs create many objects and references, often retained for the duration of request processing.

#### Interview answer

Mapping database rows, JSON payloads or remote responses into deep DTO graphs can allocate many objects per request. If the endpoint processes many requests concurrently, those graphs multiply. If they are cached, queued or logged, they may survive longer than expected.

Flattening, projections and streaming can reduce pressure.

#### Deep dive

ORM entity graphs can be even worse if lazy loading or broad fetch joins load more data than needed.

#### Production angle

Watch allocation rate and request payload size. Use DTO projections, pagination and bounded response shapes.

#### Traps / caveats

- A single request may be fine; concurrency makes it expensive.
- Mapping layers can duplicate the same data several times.
- Logging DTOs can retain or allocate large strings.

#### Optional Anki

Q: Why do DTO graphs hurt under concurrency?
A: Each in-flight request may hold its own large object graph.

</details>

<a id="mem-code-008"></a>

<details>
<summary><strong>MEM-CODE-008. How can JSON serialization and deserialization create allocation spikes?</strong></summary>

#### Short answer

JSON processing can allocate large strings, byte arrays, parser buffers, maps, lists and DTO graphs.

#### Interview answer

Deserializing a large JSON payload often builds buffers and object graphs. Serializing can create intermediate strings or byte arrays. Under high concurrency, those temporary allocations create young-gen pressure and sometimes large-object pressure.

Streaming parsers and bounded payloads reduce the risk.

#### Deep dive

Jackson and similar libraries are efficient when used well, but careless tree-model parsing or full buffering can be expensive.

#### Production angle

Limit payload sizes, use streaming for large data and monitor allocation hotspots around controllers and clients.

#### Traps / caveats

- `JsonNode` trees can be much heavier than typed streaming.
- Logging full payloads doubles memory pressure.
- Compression changes CPU/memory trade-offs.

#### Optional Anki

Q: What JSON style can reduce memory for large payloads?
A: Streaming parsing/serialization.

</details>

<a id="mem-code-009"></a>

<details>
<summary><strong>MEM-CODE-009. How would you process large files without loading them entirely into memory?</strong></summary>

#### Short answer

Process them as streams or chunks, with bounded buffers and backpressure.

#### Interview answer

Instead of `readAllBytes()` or building a giant list, read the file incrementally using streams, readers, channels or framework streaming APIs. Process records one batch at a time and write results incrementally.

This keeps memory bounded by buffer or batch size.

#### Deep dive

For structured files, choose parsers that support streaming. For database writes, batch in controlled sizes instead of accumulating all rows.

#### Production angle

Combine streaming with file size limits, timeout handling, error recovery and observability of throughput/backpressure.

#### Traps / caveats

- Some APIs look streaming but buffer internally.
- Do not keep all parsed records for final aggregation unless bounded.
- Always close streams with try-with-resources.

#### Optional Anki

Q: What is the main memory benefit of streaming a file?
A: Memory stays bounded by buffer/batch size.

</details>

<a id="mem-code-010"></a>

<details>
<summary><strong>MEM-CODE-010. How can pagination, streaming, backpressure and bounded queues reduce memory pressure?</strong></summary>

#### Short answer

They limit how much data or work is in memory at one time.

#### Interview answer

Pagination limits result size. Streaming avoids loading full data sets. Backpressure slows producers when consumers cannot keep up. Bounded queues cap in-flight work and force rejection, waiting or shedding instead of unlimited memory growth.

These are core backend memory-control patterns.

#### Deep dive

Memory pressure often comes from uncontrolled concurrency and buffering, not only individual object size.

#### Production angle

Apply bounds at API, database, queue, HTTP client and executor boundaries.

#### Traps / caveats

- Offset pagination can have database performance issues.
- Backpressure must propagate to the real producer.
- Bounded queues need a deliberate rejection policy.

#### Optional Anki

Q: What does backpressure protect?
A: Consumers and memory by slowing or limiting producers.

</details>

<a id="mem-code-011"></a>

<details>
<summary><strong>MEM-CODE-011. How can `CompletableFuture` chains or logging large payloads retain too much memory?</strong></summary>

#### Short answer

Async closures and log messages can capture or duplicate large objects beyond their useful lifetime.

#### Interview answer

`CompletableFuture` stages may capture variables in lambdas. If those variables include request DTOs, payloads or service objects, they stay reachable until the chain completes. Logging large payloads can allocate large strings and keep sensitive or bulky data in memory longer.

Both problems get worse with high concurrency.

#### Deep dive

Async failures and timeouts can retain chains longer than expected if futures are not completed or cancelled correctly.

#### Production angle

Capture only needed fields, apply timeouts, avoid logging full payloads and ensure async work has bounded concurrency.

#### Traps / caveats

- A small lambda can capture a large enclosing object.
- MDC propagation can retain request context.
- Logging can create both memory and security issues.

#### Optional Anki

Q: Why can a `CompletableFuture` lambda retain memory?
A: It can capture references that remain alive until the stage completes.

</details>
