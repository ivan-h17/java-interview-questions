# 13.05. G1, ZGC and Shenandoah practical overview

---

<a id="mem-g1-001"></a>

<details>
<summary><strong>MEM-G1-001. How does G1 GC work at a high level?</strong></summary>

#### Short answer

G1 splits the heap into regions and tries to collect regions with the most reclaimable garbage while meeting pause goals.

#### Interview answer

G1 is a generational, region-based collector. Instead of using one fixed contiguous young and old layout, it divides the heap into many regions. It performs young collections, concurrent marking and mixed collections that include old regions with a lot of garbage.

Its goal is to balance throughput with more predictable pause times.

#### Deep dive

G1 estimates how expensive each collection set will be and tries to stay near the pause-time target. This is a target, not a hard real-time guarantee.

#### Production angle

Watch pause time distribution, old-gen occupancy, allocation rate, humongous allocations, mixed collections and Full GC fallback.

#### Traps / caveats

- G1 is not pause-free.
- `MaxGCPauseMillis` is not a guarantee.
- Large live sets and humongous objects can still cause problems.

#### Optional Anki

Q: Why is G1 called region-based?
A: It divides the heap into regions and selects regions to collect.

</details>

<a id="mem-g1-002"></a>

<details>
<summary><strong>🧠 MEM-G1-002. What G1 concepts should a backend developer know: regions, mixed collections and `MaxGCPauseMillis`?</strong></summary>

#### Short answer

A backend developer should know that G1 collects heap regions, mixes young and old-region work, and treats `MaxGCPauseMillis` as a soft target.

#### Interview answer

G1 regions are equal-sized heap chunks used as young, survivor, old or humongous regions. After concurrent marking, G1 can run mixed collections that collect young regions plus selected old regions with high garbage.

`MaxGCPauseMillis` tells G1 the desired pause target, but G1 may miss it under pressure.

#### Deep dive

G1 chooses collection sets based on predicted cost and reclaimable bytes. This prediction can fail if allocation rate, live set or remembered-set cost is too high.

#### Production angle

If pauses exceed the target, inspect whether G1 is collecting too much live data, dealing with humongous objects or falling behind on marking.

#### Traps / caveats

- Lowering `MaxGCPauseMillis` can reduce throughput.
- Mixed collections are normal; Full GC fallback is not.
- Region mechanics matter only when they explain symptoms.

#### Optional Anki

Q: Is `MaxGCPauseMillis` a hard SLA?
A: No, it is a collector target.

</details>

<a id="mem-g1-003"></a>

<details>
<summary><strong>🧠 MEM-G1-003. Why can humongous objects be problematic in G1?</strong></summary>

#### Short answer

Humongous objects consume whole G1 regions and can increase fragmentation and old-generation pressure.

#### Interview answer

In G1, objects above a certain size are treated as humongous and allocated directly into one or more contiguous regions. Large arrays, byte buffers or payloads can therefore consume regions inefficiently and become harder to reclaim.

This can lead to allocation failures, extra marking pressure or Full GC fallback.

#### Deep dive

The humongous threshold depends on G1 region size. A workload with many large byte arrays may behave very differently after payload size or region sizing changes.

#### Production angle

Look for GC log entries about humongous allocations and heap dumps dominated by large arrays. Fixes often involve streaming, chunking, bounding payloads or changing data representation.

#### Traps / caveats

- Increasing heap may only delay the issue.
- Large objects are often caused by request or batch design.
- The same payload can affect heap and direct memory differently.

#### Optional Anki

Q: What kind of objects often become G1 humongous objects?
A: Very large arrays or buffers.

</details>

<a id="mem-zgc-001"></a>

<details>
<summary><strong>MEM-ZGC-001. How does ZGC work at a high level?</strong></summary>

#### Short answer

ZGC does most marking, relocation and reference processing concurrently to keep stop-the-world pauses very short.

#### Interview answer

ZGC is a low-latency collector. It uses barriers and metadata encoded in references to let application threads continue while the collector marks and relocates objects.

The main goal is very short pauses, even for large heaps.

#### Deep dive

Because much work is concurrent, ZGC needs CPU headroom. If allocation outruns concurrent collection, allocation stalls can occur.

#### Production angle

ZGC is worth testing for latency-sensitive services, but monitor CPU, RSS, allocation stalls and throughput, not only pause time.

#### Traps / caveats

- Low pause does not mean no pause.
- Low pause does not mean lower CPU.
- Behavior depends on JDK version and whether generational ZGC is used.

#### Optional Anki

Q: What is ZGC mainly optimized for?
A: Very short GC pauses.

</details>

<a id="mem-zgc-002"></a>

<details>
<summary><strong>MEM-ZGC-002. Why does ZGC usually have very short pause times?</strong></summary>

#### Short answer

ZGC moves most expensive GC work out of stop-the-world phases and runs it concurrently.

#### Interview answer

Traditional collectors may pause application threads for significant marking or compaction work. ZGC uses concurrent algorithms and barriers so the application can keep running while objects are marked and relocated.

Only short coordination phases require stop-the-world pauses.

#### Deep dive

The cost does not disappear; it shifts into concurrent CPU work and runtime barriers.

#### Production angle

For APIs with strict p99 latency, this can be a good trade-off. For CPU-constrained services or batch jobs, the overhead may be unattractive.

#### Traps / caveats

- Pause time is not the same as total GC overhead.
- ZGC still needs enough memory and CPU to keep up.
- Allocation stalls can show that low-pause GC is underprovisioned.

#### Optional Anki

Q: How does ZGC keep pauses short?
A: By performing most GC work concurrently and using barriers for correctness.

</details>

<a id="mem-zgc-003"></a>

<details>
<summary><strong>MEM-ZGC-003. How would you compare G1, ZGC and Shenandoah for a backend service?</strong></summary>

#### Short answer

G1 is a balanced default; ZGC and Shenandoah target lower pauses at the cost of more concurrent overhead.

#### Interview answer

For a typical backend service, I would start with G1 unless there is a latency reason to do otherwise. If p99 latency is hurt by GC pauses, I would test ZGC or Shenandoah. If the service has little CPU headroom, the extra concurrent overhead may be a problem.

The decision should be based on measured workload behavior.

#### Deep dive

G1 often works well with moderate heaps and normal latency goals. ZGC and Shenandoah become more attractive with larger heaps or stricter latency objectives.

#### Production angle

Compare p99 latency, GC pause distribution, CPU usage, RSS, throughput, allocation stalls and OOM risk before and after.

#### Traps / caveats

- Do not switch collectors before understanding allocation and retention.
- Do not rely on average latency.
- Do not ignore JDK distribution and version support.

#### Optional Anki

Q: When should you consider ZGC or Shenandoah?
A: When GC pauses hurt latency and the service has enough CPU/memory headroom.

</details>

<a id="mem-zgc-004"></a>

<details>
<summary><strong>MEM-ZGC-004. What should you test before switching a service from G1 to ZGC or Shenandoah?</strong></summary>

#### Short answer

Test latency, throughput, CPU, memory footprint, allocation stalls, warmup and behavior under peak load.

#### Interview answer

I would compare current G1 metrics with the candidate collector under production-like traffic. Key signals are p95/p99 latency, GC pause distribution, CPU usage, container throttling, RSS, allocation rate, live set, throughput and error rate.

I would also test deployment startup, warmup and failure modes.

#### Deep dive

Low-pause collectors can change the resource profile. A service may trade pause time for higher CPU or different memory behavior.

#### Production angle

Roll out gradually with dashboards, rollback criteria and identical application code where possible.

#### Traps / caveats

- A local benchmark is not enough.
- CPU-limited pods can hide the benefit.
- A collector switch should not be used to ignore a leak.

#### Optional Anki

Q: What is the minimum safe approach to switching GC collectors?
A: Compare with production-like load and clear rollout/rollback metrics.

</details>

<a id="mem-zgc-005"></a>

<details>
<summary><strong>🧠 MEM-ZGC-005. What are colored pointers and load barriers in ZGC?</strong></summary>

#### Short answer

Colored pointers store GC state in references, and load barriers let ZGC fix or validate references as the application reads them.

#### Interview answer

ZGC uses metadata associated with object references to track marking and relocation state. Load barriers execute when application code reads references, allowing the JVM to handle relocated objects while the application continues running.

This is part of how ZGC performs concurrent relocation with short pauses.

#### Deep dive

The exact representation is JVM-specific and has changed over time. The interview value is understanding that barriers shift some GC correctness work into normal application execution.

#### Production angle

Barriers are one source of CPU overhead in low-pause collectors. They help latency but are not free.

#### Traps / caveats

- Do not over-explain bit layouts unless asked.
- Colored pointers are not a Java-language feature.
- Version-specific details should be verified.

#### Optional Anki

Q: What do ZGC load barriers help with?
A: Correctness while objects are marked or relocated concurrently.

</details>

<a id="mem-zgc-006"></a>

<details>
<summary><strong>🧠 MEM-ZGC-006. What are ZGC allocation stalls or Shenandoah degenerated cycles?</strong></summary>

#### Short answer

They are signs that a low-pause collector could not keep up with allocation or concurrent collection work.

#### Interview answer

ZGC allocation stalls happen when application threads need memory faster than the collector can make it available. Shenandoah degenerated cycles occur when concurrent collection cannot complete as planned and the collector falls back to a more stop-the-world path.

Both indicate pressure from allocation rate, live set size, CPU limits or heap sizing.

#### Deep dive

Low-pause collectors rely on concurrent progress. If they do not get enough CPU or memory headroom, they may still stall or fall back.

#### Production angle

Investigate CPU throttling, allocation spikes, live set growth, heap headroom and collector logs before assuming the collector is broken.

#### Traps / caveats

- Low-pause collectors can still have failure modes.
- Allocation stalls are often workload or sizing signals.
- Switching collectors without fixing pressure may move the symptom.

#### Optional Anki

Q: What do allocation stalls suggest?
A: Allocation is outrunning the collector's ability to provide free memory.

</details>
