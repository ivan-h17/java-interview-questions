# 13.03. Garbage collection fundamentals

---

<a id="mem-gc-001"></a>

<details>
<summary><strong>MEM-GC-001. What is garbage collection in Java?</strong></summary>

#### Short answer

Garbage collection automatically finds unreachable heap objects and reclaims their memory.

#### Interview answer

In Java, the programmer does not explicitly free ordinary heap objects. The garbage collector tracks which objects are still reachable from GC roots and reclaims memory for objects that can no longer be reached.

GC improves safety, but it does not remove the need to control object lifetime, caches, queues and resource cleanup.

#### Deep dive

Collectors use algorithms such as marking, copying, compacting and concurrent tracing. Different collectors optimize for different trade-offs: latency, throughput, footprint and CPU overhead.

#### Production angle

GC affects tail latency, CPU usage and memory sizing. A healthy service still needs GC observability and allocation discipline.

#### Traps / caveats

- GC does not close files, sockets or database connections deterministically.
- GC does not prevent memory leaks caused by unwanted reachability.
- "No manual free" does not mean "no memory design".

#### Optional Anki

Q: What does GC reclaim?
A: Memory used by heap objects that are no longer reachable.

</details>

<a id="mem-gc-002"></a>

<details>
<summary><strong>MEM-GC-002. When does an object become eligible for garbage collection?</strong></summary>

#### Short answer

An object becomes eligible for GC when it is no longer reachable from any GC root.

#### Interview answer

GC eligibility is based on reachability, not on scope alone. If no live thread, static field, JNI handle, classloader, monitor or other root can reach an object, the collector may reclaim it.

An object can leave a method scope but still be reachable through a collection, cache, thread-local or callback.

#### Deep dive

Reachability is transitive. If a root references object A and A references object B, then B is live too.

#### Production angle

Most Java memory leaks are caused by objects accidentally remaining reachable through long-lived structures.

#### Traps / caveats

- Setting one local reference to `null` does not help if another reference exists.
- Being unused by business logic is not the same as unreachable.
- Finalization or cleaners can delay reclamation-related cleanup.

#### Optional Anki

Q: What makes a Java object eligible for GC?
A: It is no longer reachable from GC roots.

</details>

<a id="mem-gc-003"></a>

<details>
<summary><strong>MEM-GC-003. What are GC roots?</strong></summary>

#### Short answer

GC roots are starting points the collector treats as definitely reachable.

#### Interview answer

Common GC roots include active thread stacks, static fields through loaded classes, JNI references, JVM internals and some synchronization/runtime structures. The collector starts from roots and follows references to find the live object graph.

Anything reachable from a root is considered live.

#### Deep dive

Root sets vary by JVM implementation and collector, but the core idea is stable: roots anchor reachability.

#### Production angle

Heap dump analysis often starts by asking why an object is reachable from a root. "Shortest path to GC roots" helps explain retention.

#### Traps / caveats

- Static fields are a common source of accidental long-lived reachability.
- Thread stacks and `ThreadLocal` values can retain request data.
- JNI/native references can keep Java objects alive.

#### Optional Anki

Q: Why do GC roots matter?
A: They are the starting points for determining which objects are live.

</details>

<a id="mem-gc-004"></a>

<details>
<summary><strong>MEM-GC-004. What is reachability in the context of GC?</strong></summary>

#### Short answer

Reachability means an object can be reached by following references from GC roots.

#### Interview answer

An object is strongly reachable if a chain of strong references connects it to a GC root. Such objects are live and cannot be reclaimed. If no such chain exists, the object may be collected depending on reference type and collector timing.

Reachability is about the object graph, not whether code "intends" to use the object.

#### Deep dive

Java also has soft, weak and phantom reachability through reference objects, but strong reachability is the default that keeps objects alive.

#### Production angle

Understanding reachability is key to heap dump analysis: the problem is usually not object count alone, but the retaining path that keeps objects alive.

#### Traps / caveats

- A small root can retain a huge object graph.
- Collections often hide retention because each element is reachable from the collection.
- Lambdas and inner classes can retain enclosing objects.

#### Optional Anki

Q: What keeps a heap object alive?
A: A reachable path from a GC root, usually through strong references.

</details>

<a id="mem-gc-005"></a>

<details>
<summary><strong>MEM-GC-005. How can a memory leak happen in Java if memory is garbage-collected?</strong></summary>

#### Short answer

A Java leak happens when objects are no longer needed but remain reachable.

#### Interview answer

GC only collects unreachable objects. If an object is still referenced by a static collection, cache, thread-local, listener registry, queue or classloader, the collector must treat it as live even if the application no longer needs it.

That is why garbage-collected languages can still leak memory.

#### Deep dive

Java leaks are usually retention leaks, not forgotten `free()` calls. The retained object graph may be much larger than the object that accidentally holds it.

#### Production angle

Leak symptoms include increasing post-GC heap, old-generation growth, OOME after hours/days and heap dump dominators showing unexpected owners.

#### Traps / caveats

- "GC runs often" does not mean the leak is gone.
- A cache without bounds is often a leak under another name.
- Leaks can be outside heap too, for example native buffers.

#### Optional Anki

Q: What is the usual Java memory leak pattern?
A: Unneeded objects remain reachable from long-lived references.

</details>

<a id="mem-gc-006"></a>

<details>
<summary><strong>MEM-GC-006. What is the difference between high memory usage and a memory leak?</strong></summary>

#### Short answer

High memory usage may be expected workload state; a leak is unwanted memory retention that keeps growing or never releases.

#### Interview answer

A service can use a lot of memory legitimately: warm caches, active sessions, large batches or normal traffic bursts. A leak means memory is retained beyond its useful lifetime.

The key question is whether memory stabilizes under steady load and whether post-GC usage returns to a reasonable baseline.

#### Deep dive

A growing heap before GC is normal. A growing post-GC baseline is more suspicious.

#### Production angle

Compare memory after full/old collections, cache metrics, request volume and deployment timeline. Heap dumps over time are more useful than a single snapshot.

#### Traps / caveats

- A warm cache can look like a leak until it reaches its bound.
- A leak can be slow and only appear after days.
- Native memory leaks may not show in heap graphs.

#### Optional Anki

Q: What memory trend is suspicious for a heap leak?
A: Post-GC heap usage steadily increases under steady workload.

</details>

<a id="mem-gc-007"></a>

<details>
<summary><strong>MEM-GC-007. What is the generational hypothesis?</strong></summary>

#### Short answer

Most objects die young, and objects that survive longer are more likely to keep surviving.

#### Interview answer

Generational collectors exploit the observation that many objects are short-lived: temporary DTOs, iterators, strings and intermediate results. They collect young objects frequently and cheaply, while collecting older objects less often.

This is why allocation of short-lived objects can be efficient in Java.

#### Deep dive

When the hypothesis matches the application, young collections reclaim most memory. When many objects survive, promotion pressure and old-generation work increase.

#### Production angle

High promotion rate or old-gen growth suggests objects are surviving longer than expected: caches, queues, request fan-out, long transactions or large batches.

#### Traps / caveats

- "Most objects die young" is not true for every workload.
- Long-lived caches change the live set shape.
- Low-pause collectors may implement generations differently.

#### Optional Anki

Q: What does the generational hypothesis say?
A: Most objects die young; older objects tend to survive longer.

</details>

<a id="mem-gc-008"></a>

<details>
<summary><strong>MEM-GC-008. What are Eden, Survivor spaces, Young Generation and Old Generation?</strong></summary>

#### Short answer

They are generational heap areas used to separate new, surviving and long-lived objects.

#### Interview answer

In a typical generational model, new objects are allocated in Eden. After a young GC, surviving objects may move through Survivor spaces. Objects that survive enough collections or cannot fit may be promoted to Old Generation.

The goal is to collect short-lived objects frequently without scanning the entire heap every time.

#### Deep dive

Exact layouts differ by collector. G1 uses regions rather than fixed contiguous young/old spaces, but it still has young and old roles.

#### Production angle

Young-gen pressure usually means high allocation rate. Old-gen pressure usually means retention, promotion or an oversized live set.

#### Traps / caveats

- Do not assume every collector exposes the same spaces.
- Old-gen growth is more serious than temporary Eden growth.
- Promotion is normal; excessive promotion is the concern.

#### Optional Anki

Q: Where do most new objects start in a generational heap?
A: In the young generation, commonly Eden.

</details>

<a id="mem-gc-009"></a>

<details>
<summary><strong>MEM-GC-009. What is object promotion?</strong></summary>

#### Short answer

Promotion is moving an object from young generation to old generation after it survives young collections or cannot remain in young space.

#### Interview answer

Objects that survive young GC are copied or retained for another chance. After surviving enough times, or when young space cannot hold them, they are promoted to old generation.

Promotion is normal, but excessive promotion increases old-gen occupancy and can lead to more expensive collections.

#### Deep dive

Promotion behavior depends on collector, object age, survivor sizing and allocation pressure.

#### Production angle

High promotion rate after a release can point to longer object lifetimes, larger request graphs, new caches or queues retaining objects.

#### Traps / caveats

- Promotion is not itself a leak.
- Promotion rate must be interpreted with traffic and allocation rate.
- Large objects may bypass normal young-generation behavior.

#### Optional Anki

Q: What does high promotion rate suggest?
A: Many objects are surviving young collections and moving to old generation.

</details>

<a id="mem-gc-010"></a>

<details>
<summary><strong>MEM-GC-010. What is the difference between minor GC and Full GC?</strong></summary>

#### Short answer

Minor GC usually collects young generation; Full GC usually involves the whole heap and is more disruptive.

#### Interview answer

A minor or young GC focuses on young-generation memory and is usually frequent and relatively cheap. A Full GC typically processes the entire heap and often includes old generation and class metadata work, depending on collector.

Full GC is usually a stronger warning signal for backend latency.

#### Deep dive

Terminology can be collector-specific. "Major GC" is especially ambiguous, so in interviews it is better to describe what memory areas are collected and whether the pause is stop-the-world.

#### Production angle

Frequent Full GCs can indicate old-gen pressure, metadata pressure, explicit `System.gc()`, evacuation failure or wrong heap/collector sizing.

#### Traps / caveats

- Do not treat "major" and "full" as universally identical.
- A young GC can still hurt latency if very frequent.
- Low-pause collectors still have some stop-the-world phases.

#### Optional Anki

Q: Why are frequent Full GCs concerning?
A: They usually mean expensive whole-heap or old-generation pressure.

</details>

<a id="mem-gc-011"></a>

<details>
<summary><strong>🧠 MEM-GC-011. What is the difference between marking, copying, sweeping and compacting?</strong></summary>

#### Short answer

Marking finds live objects, copying moves live objects, sweeping reclaims dead space and compacting reduces fragmentation.

#### Interview answer

Marking traces reachable objects. Sweeping frees memory occupied by unmarked objects. Copying moves live objects to another area, often making allocation simple afterward. Compacting moves live objects together to create larger contiguous free space.

Collectors combine these techniques differently.

#### Deep dive

Copying is efficient when most objects are dead. Mark-sweep can leave fragmentation. Compaction improves locality and free-space quality but moving objects has cost.

#### Production angle

Fragmentation, evacuation failure and compaction pauses are common reasons GC behavior changes under large live sets or large objects.

#### Traps / caveats

- No single algorithm is best for every workload.
- Moving collectors must update references.
- Compaction can reduce fragmentation but may add pause or concurrent work.

#### Optional Anki

Q: What does compaction solve?
A: Fragmentation by moving live objects together.

</details>

<a id="mem-gc-012"></a>

<details>
<summary><strong>MEM-GC-012. What is stop-the-world, and why do collectors still need some pauses?</strong></summary>

#### Short answer

Stop-the-world means application threads are paused so the JVM can perform work that requires a stable view.

#### Interview answer

Collectors pause application threads for phases that are hard or unsafe to run while the object graph is changing. Examples include initial root scanning, remark phases, some evacuation work or final synchronization.

Modern collectors try to make pauses short, but "low pause" does not mean "zero pause".

#### Deep dive

Concurrent collectors do much work while the application runs, but they use barriers and brief synchronization phases to preserve correctness.

#### Production angle

STW pauses can directly affect p99 latency. Monitor pause distribution, not only average pause time.

#### Traps / caveats

- A collector can be concurrent and still have STW phases.
- Short pauses can still be frequent enough to matter.
- Time to safepoint can add to perceived pause time.

#### Optional Anki

Q: What does stop-the-world pause?
A: Application threads.

</details>

<a id="mem-gc-013"></a>

<details>
<summary><strong>MEM-GC-013. Why is calling `System.gc()` usually a bad idea?</strong></summary>

#### Short answer

It asks the JVM to run GC at an application-chosen time, which can cause unnecessary pauses and poor throughput.

#### Interview answer

`System.gc()` is only a request, but many JVM configurations treat it seriously and may trigger an expensive collection. Application code usually lacks enough global information to decide when GC should run.

GC scheduling should normally be left to the collector.

#### Deep dive

Some deployments disable or alter explicit GC behavior with JVM flags. Libraries that call it can create surprising latency spikes.

#### Production angle

If latency spikes look like explicit Full GC, inspect GC logs for explicit causes and search code/dependencies for `System.gc()`.

#### Traps / caveats

- `System.gc()` does not guarantee all garbage is collected.
- It is not a reliable cleanup mechanism.
- Disabling explicit GC can affect code that relied on it accidentally.

#### Optional Anki

Q: What is `System.gc()`?
A: A request to the JVM to perform garbage collection, not a safe cleanup guarantee.

</details>

<a id="mem-gc-014"></a>

<details>
<summary><strong>🧠 MEM-GC-014. What is a safepoint, and why can time to safepoint matter?</strong></summary>

#### Short answer

A safepoint is a place where Java threads can be paused safely for JVM operations; reaching it late can extend pauses.

#### Interview answer

For some JVM operations, all Java threads must reach a known safe state. The pause experienced by the application includes not only the VM operation but also time spent waiting for threads to reach safepoints.

Long time to safepoint can make pauses appear worse than the GC work itself.

#### Deep dive

Safepoints are used for GC, deoptimization, biased-locking era operations, class unloading and other VM tasks. Modern JVM logs and JFR can show safepoint timing.

#### Production angle

If GC logs show small GC work but large pauses, investigate safepoint time, long-running native calls, tight loops or blocked VM operations.

#### Traps / caveats

- "GC pause" may include more than collector work.
- Safepoint behavior is JVM-specific.
- Profilers and diagnostics can also trigger safepoint-sensitive work.

#### Optional Anki

Q: Why can time to safepoint matter?
A: Application threads may be paused later than expected, extending observed latency.

</details>
