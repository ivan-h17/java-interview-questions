# 13.09. GC logs, metrics and observability

---

<a id="mem-obs-001"></a>

<details>
<summary><strong>MEM-OBS-001. How do you enable GC logging in modern Java?</strong></summary>

#### Short answer

Use unified JVM logging, commonly with `-Xlog:gc*` and appropriate file/rotation options.

#### Interview answer

Modern Java uses unified logging through `-Xlog`. A typical starting point is enabling GC-related tags and writing them to a file with rotation, for example `-Xlog:gc*:file=/var/log/app/gc.log:time,uptime,level,tags:filecount=5,filesize=20m`.

The exact command should be tailored to the JDK version and operational environment.

GC logs should be enabled before incidents when possible.

#### Deep dive

Useful log details include pause reasons, durations, heap before/after, metaspace, concurrent cycles and collector-specific events.

#### Production angle

Keep logs rotated and shipped. In containers, make sure logs are not lost on restart or too noisy for the platform.

#### Traps / caveats

- Old `-XX:+PrintGCDetails` advice may not apply to modern Java.
- Too much logging can create noise or I/O overhead.
- Logs without timestamps and deployment context are harder to use.

#### Optional Anki

Q: What modern JVM option family controls GC logging?
A: Unified logging through `-Xlog`.

</details>

<a id="mem-obs-002"></a>

<details>
<summary><strong>MEM-OBS-002. What metrics should you monitor for JVM memory and GC?</strong></summary>

#### Short answer

Monitor heap/non-heap usage, allocation rate, GC pause distribution, GC count/time, old-gen usage, promotion, RSS and OOM events.

#### Interview answer

Important JVM metrics include used/committed/max heap, memory pools, allocation rate, promoted memory, GC pause count and duration, old-generation occupancy, Metaspace, direct buffer usage and thread count. Pair them with OS/container RSS and Kubernetes restart/OOMKilled events.

Use percentiles and trends, not only current values.

#### Deep dive

JVM metrics explain managed memory; container metrics reveal total process pressure.

#### Production angle

Dashboards should show memory and latency together so GC impact on user-facing behavior is visible.

#### Traps / caveats

- Used heap alone is insufficient.
- Average pause time hides tail latency.
- Missing RSS can hide native memory growth.

#### Optional Anki

Q: Why monitor both JVM heap and RSS?
A: Heap is only part of total process memory.

</details>

<a id="mem-obs-003"></a>

<details>
<summary><strong>MEM-OBS-003. What are allocation rate, live set size and promotion rate?</strong></summary>

#### Short answer

Allocation rate is new memory per time, live set is retained memory after GC, and promotion rate is memory moving to old generation.

#### Interview answer

Allocation rate shows how much garbage the application creates. Live set size shows how much memory remains reachable after GC. Promotion rate shows how much data survives young collections and moves toward old generation.

Together they distinguish churn, retention and old-gen pressure.

#### Deep dive

High allocation with stable live set suggests churn. Growing live set suggests retention. High promotion suggests objects are living longer than expected.

#### Production angle

These metrics help decide whether to optimize allocation, bound caches, resize heap or tune GC.

#### Traps / caveats

- Allocation rate can be high without a leak.
- Promotion can be normal under some workloads.
- Live set must be interpreted after GC, not at random peaks.

#### Optional Anki

Q: What does high allocation with stable live set suggest?
A: Object churn rather than retained-memory leak.

</details>

<a id="mem-obs-004"></a>

<details>
<summary><strong>MEM-OBS-004. What is GC pause time distribution?</strong></summary>

#### Short answer

It is the distribution of GC pause durations, especially percentiles such as p95 and p99.

#### Interview answer

Average pause time is not enough. A service may have low average pauses but occasional long pauses that break user-facing latency SLOs. Pause distribution shows how often pauses happen and how bad the tail is.

This should be correlated with request latency.

#### Deep dive

Different pause causes matter: young GC, mixed GC, Full GC, remark, cleanup or safepoint delays.

#### Production angle

Alert on meaningful tail behavior and SLO impact, not every small GC pause.

#### Traps / caveats

- A few long pauses can dominate p99.
- Frequent short pauses can also hurt throughput.
- GC pause metrics may not include all safepoint time depending on source.

#### Optional Anki

Q: Why is average GC pause misleading?
A: It hides rare long pauses that affect tail latency.

</details>

<a id="mem-obs-005"></a>

<details>
<summary><strong>MEM-OBS-005. What is GC throughput overhead?</strong></summary>

#### Short answer

It is the share of time or CPU spent on GC instead of application work.

#### Interview answer

GC overhead measures how much runtime cost garbage collection adds. A service can have short pauses but still high GC overhead if collections are very frequent or concurrent GC consumes a lot of CPU.

Throughput-oriented and low-latency collectors trade this overhead differently.

#### Deep dive

GC overhead can be visible as increased CPU, reduced request throughput or less CPU available to application threads.

#### Production angle

Monitor GC time, CPU usage, allocation rate and request throughput together.

#### Traps / caveats

- Low pause does not imply low overhead.
- High GC CPU may come from allocation churn.
- CPU throttling can amplify GC overhead.

#### Optional Anki

Q: Can GC overhead be high even with short pauses?
A: Yes, if GC runs frequently or concurrently consumes CPU.

</details>

<a id="mem-obs-006"></a>

<details>
<summary><strong>MEM-OBS-006. What does high GC frequency indicate?</strong></summary>

#### Short answer

It often indicates high allocation rate, too small heap/young generation or memory pressure.

#### Interview answer

Frequent young GCs usually point to high allocation rate or insufficient young-generation space. Frequent old or Full GCs are more concerning and may indicate old-gen pressure, retention, leaks or collector fallback.

Frequency must be interpreted with pause duration and workload.

#### Deep dive

High frequency with low pause cost may be acceptable; high frequency plus latency or CPU impact is a problem.

#### Production angle

Correlate GC count with traffic, allocation metrics, deployment changes and endpoint mix.

#### Traps / caveats

- Low GC frequency is not always good if heap grows too large.
- Frequency alone does not identify leak vs churn.
- Full GC frequency is a stronger warning than young GC frequency.

#### Optional Anki

Q: What does frequent young GC commonly suggest?
A: High allocation rate or insufficient young space.

</details>

<a id="mem-obs-007"></a>

<details>
<summary><strong>MEM-OBS-007. What does old generation increasing after every GC suggest?</strong></summary>

#### Short answer

It suggests objects are being retained or promoted faster than old generation is reclaimed.

#### Interview answer

If old generation steadily rises after collections, the service is keeping more long-lived objects. This may be a leak, cache growth, queue buildup, session accumulation or long-running workload.

The important signal is the post-GC trend, not one spike.

#### Deep dive

Old-gen growth can be normal during warmup if it plateaus. It is suspicious if it grows without bound under steady load.

#### Production angle

Check cache size, queue depth, active sessions, tenant cardinality, heap dumps and recent deployments.

#### Traps / caveats

- Warmup growth is not automatically a leak.
- Old-gen metrics differ by collector.
- High promotion rate can make old-gen grow even without a classic leak.

#### Optional Anki

Q: What old-gen trend is leak-like?
A: Post-GC old-gen usage rises continuously under steady load.

</details>

<a id="mem-obs-008"></a>

<details>
<summary><strong>MEM-OBS-008. How would you detect a memory leak from monitoring graphs?</strong></summary>

#### Short answer

Look for a rising post-GC baseline, old-gen growth and memory that does not stabilize under steady workload.

#### Interview answer

Heap usage normally rises and falls in a sawtooth pattern. A leak is suggested when the low points after GC keep moving upward. Supporting signals include increasing old generation, longer GC pauses, more frequent Full GC and eventual OOME.

Correlate this with traffic and deployment changes.

#### Deep dive

Native leaks show up differently: RSS rises while heap may stay flat.

#### Production angle

A good dashboard shows heap pools, GC events, RSS, cache sizes, queue depth and deployment markers.

#### Traps / caveats

- Traffic growth can look like memory growth.
- Cache warmup can look leak-like until bounded.
- Some leaks only happen on specific endpoints or tenants.

#### Optional Anki

Q: What is a key graph signal of heap leak?
A: Rising post-GC heap baseline.

</details>

<a id="mem-obs-009"></a>

<details>
<summary><strong>MEM-OBS-009. Why can RSS be much larger than used Java heap?</strong></summary>

#### Short answer

RSS includes total resident process memory, while used heap is only Java heap objects.

#### Interview answer

RSS includes committed heap pages plus Metaspace, Code Cache, thread stacks, direct buffers, memory-mapped files, native libraries, JVM internals and allocator behavior. Used heap is just memory currently used by heap objects.

That difference explains many container OOM surprises.

#### Deep dive

Committed heap can also be larger than used heap. OS memory accounting and container cgroups see the process, not just JVM heap.

#### Production angle

If RSS grows while heap is stable, investigate native memory, direct buffers, threads, mmap and NMT output.

#### Traps / caveats

- Heap dump cannot explain all RSS growth.
- `-Xmx` does not cap RSS.
- Native allocator behavior can keep RSS high after frees.

#### Optional Anki

Q: What does RSS measure?
A: Resident physical memory used by the process.

</details>

<a id="mem-obs-010"></a>

<details>
<summary><strong>MEM-OBS-010. How would you correlate GC pauses with request latency?</strong></summary>

#### Short answer

Align timestamps from GC logs/metrics with latency metrics, traces and request volume.

#### Interview answer

I would compare GC pause events with p95/p99 latency spikes on the same timeline. Then I would check whether pauses happen before or during slow requests, whether all endpoints are affected and whether CPU or downstream latency also changed.

Correlation is not automatically causation, but it guides the next check.

#### Deep dive

Distributed traces can show whether slow time is inside the service, downstream calls or queueing. JFR can add thread/GC detail.

#### Production angle

Use consistent clocks, deployment markers and dashboards that overlay GC events with service latency.

#### Traps / caveats

- A latency spike can cause allocation pressure, not only result from it.
- Downstream slowness can increase in-flight objects and GC pressure.
- Clock skew can mislead correlation.

#### Optional Anki

Q: What do you compare to correlate GC with latency?
A: GC event timestamps with request latency percentiles and traces.

</details>

<a id="mem-obs-011"></a>

<details>
<summary><strong>MEM-OBS-011. What JVM memory metrics would you expose through Micrometer or Actuator?</strong></summary>

#### Short answer

Expose heap/non-heap pools, GC pauses, allocation/promotion where available, buffer pools, thread count and process memory.

#### Interview answer

For Spring Boot services, useful metrics include JVM memory used/committed/max by area and pool, GC pause count/duration, allocation and promotion metrics where supported, buffer pool/direct memory, thread count, loaded classes and process RSS.

Pair them with application metrics such as cache size, queue depth and request latency.

#### Deep dive

Metric names vary by Micrometer/JVM version, so the important part is the signal, not memorizing one exact name.

#### Production angle

Dashboards should connect JVM memory to user impact and capacity: latency, traffic, CPU, pod restarts and OOMKilled events.

#### Traps / caveats

- Metrics without labels by pool are less useful.
- Actuator endpoints must be secured.
- High-cardinality tags can create their own memory/observability problems.

#### Optional Anki

Q: What non-JVM app metrics help explain memory?
A: Cache size, queue depth, traffic and request latency.

</details>
