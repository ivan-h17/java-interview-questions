# 13.01. JVM memory mental model

---

<a id="mem-fund-001"></a>

<details>
<summary><strong>MEM-FUND-001. What is the difference between heap and stack memory in Java?</strong></summary>

#### Short answer

The heap stores objects; each thread stack stores method call frames, local variables and execution state.

#### Interview answer

In Java, objects normally live on the heap and are managed by the garbage collector. Each Java thread has its own stack, which contains frames for active method calls: parameters, local variables, operand stack data and return information.

Local variables can hold primitive values or references to heap objects. The reference may be on the stack, but the object it points to is usually on the heap.

#### Deep dive

Heap memory is shared across threads, so objects stored there require normal concurrency rules. Stack memory is thread-local and grows/shrinks with method calls.

The JVM and JIT may optimize aggressively, but the interview-level model remains: object lifetime is mostly heap/GC driven, while call execution is stack driven.

#### Production angle

Heap pressure usually shows up as GC activity or heap OOME. Stack pressure usually appears as `StackOverflowError` or native memory pressure when too many platform threads exist.

#### Traps / caveats

- "Reference on stack" does not mean "object on stack".
- Stack memory is not garbage-collected like the heap.
- Too many threads can exhaust native memory through stacks.

#### Optional Anki

Q: What is the simple heap vs stack distinction in Java?
A: Heap stores objects; each thread stack stores active method call frames and local execution state.

</details>

<a id="mem-fund-002"></a>

<details>
<summary><strong>MEM-FUND-002. Which JVM memory areas are shared between threads and which are thread-local?</strong></summary>

#### Short answer

The heap, Metaspace and Code Cache are shared; Java stacks, native method stacks and program counters are thread-local.

#### Interview answer

All threads can access heap objects, so heap data must be protected by synchronization, immutability, confinement or other concurrency mechanisms. Class metadata in Metaspace and compiled code in the Code Cache are also process-wide JVM resources.

Each Java thread has its own call stack and program counter. Native method execution may use native stack memory as well.

#### Deep dive

The exact implementation details are JVM-specific, but the practical distinction matters: shared areas create coordination and memory pressure across the process; thread-local areas scale with the number of threads.

#### Production angle

In services with many platform threads, native memory may grow because every thread needs stack memory. In services with heavy dynamic class generation, Metaspace can grow independently from the heap.

#### Traps / caveats

- Thread-local JVM areas do not make referenced heap objects thread-local.
- `ThreadLocal` values are stored in thread-owned maps, but the values themselves are heap objects.
- Container memory must include both shared and per-thread memory.

#### Optional Anki

Q: Which JVM memory areas grow with the number of platform threads?
A: Mainly Java/native thread stacks and per-thread execution state.

</details>

<a id="mem-fund-003"></a>

<details>
<summary><strong>MEM-FUND-003. What is the difference between JVM runtime data areas and the Java Memory Model?</strong></summary>

#### Short answer

Runtime data areas describe where the JVM stores data; the Java Memory Model describes visibility, ordering and safe communication between threads.

#### Interview answer

JVM runtime data areas are a memory layout concept: heap, stacks, Metaspace, program counters and related areas. The Java Memory Model is a concurrency contract: it defines happens-before relationships, visibility of writes, `volatile`, `synchronized`, final-field guarantees and allowed reorderings.

They are related to memory, but they answer different questions.

#### Deep dive

Knowing that an object is on the heap does not tell you whether another thread sees the latest value. Visibility depends on synchronization and happens-before, not only on where bytes are stored.

#### Production angle

Many production bugs are not "heap vs stack" bugs but visibility bugs: stale reads, unsafe publication and data races.

#### Traps / caveats

- The JMM is not the same as heap layout.
- Heap objects can still be safely immutable or dangerously racy.
- `volatile` affects visibility and ordering, not object allocation location.

#### Optional Anki

Q: What does the Java Memory Model define?
A: Thread visibility, ordering and happens-before rules.

</details>

<a id="mem-fund-004"></a>

<details>
<summary><strong>MEM-FUND-004. What is stored in the Java heap?</strong></summary>

#### Short answer

The heap stores Java objects, arrays and object state managed by the garbage collector.

#### Interview answer

Most objects created with `new`, arrays, collection contents, DTO graphs and cached data live on the heap. The heap is shared by all threads and is the main area managed by GC.

References to heap objects may be stored in local variables, object fields, static fields, native handles or internal JVM structures.

#### Deep dive

The heap is usually divided logically by the collector, for example young and old generations in generational collectors. The exact layout depends on the GC implementation.

#### Production angle

Heap size, allocation rate and live set size drive GC behavior. A service can have a large heap but still perform badly if allocation rate is high or the live set is too large.

#### Traps / caveats

- Static fields are references from class metadata/class mirrors to heap objects; they can keep large graphs alive.
- Heap dump analysis shows heap objects, not all process memory.
- Large heaps can make dumps, restarts and incident handling harder.

#### Optional Anki

Q: What are the most common things stored in the Java heap?
A: Objects, arrays and their state.

</details>

<a id="mem-fund-005"></a>

<details>
<summary><strong>MEM-FUND-005. What is stored in a Java thread stack?</strong></summary>

#### Short answer

A Java thread stack stores frames for active method calls, including local variables and execution state.

#### Interview answer

Every platform thread has a stack. Each method call adds a frame; returning from the method removes it. Frames contain local variables, operand stack information and metadata needed to resume execution.

Local variables may contain primitive values or references to heap objects.

#### Deep dive

Stack size is controlled by `-Xss` for platform threads. Recursion, deep call chains and many platform threads increase stack-related risk.

#### Production angle

Small stacks can cause `StackOverflowError` in deep call paths. Large stacks combined with many threads can waste native memory and contribute to pod OOM kills.

#### Traps / caveats

- A stack variable holding a reference does not own the heap object.
- Stack memory is usually outside the Java heap budget.
- Virtual threads change the scaling model, but memory still exists somewhere.

#### Optional Anki

Q: What does each Java platform thread have?
A: Its own stack containing active method call frames.

</details>

<a id="mem-fund-006"></a>

<details>
<summary><strong>MEM-FUND-006. What is Metaspace, and how is it related to class metadata?</strong></summary>

#### Short answer

Metaspace is native memory used by HotSpot to store class metadata.

#### Interview answer

In modern HotSpot JVMs, class metadata is stored in Metaspace, outside the Java heap. This includes information the JVM needs about loaded classes, methods, fields, constant pools and runtime class structures.

The `Class` objects visible to Java code are heap objects, but the underlying class metadata is in Metaspace.

#### Deep dive

Metaspace replaced PermGen in HotSpot. It can grow until limited by native memory or by `-XX:MaxMetaspaceSize`.

#### Production angle

Metaspace growth is often related to classloading, proxies, reflection, dynamic bytecode generation or classloader leaks.

#### Traps / caveats

- Increasing `-Xmx` does not directly increase Metaspace.
- A heap dump alone may not explain Metaspace growth.
- Setting `MaxMetaspaceSize` too low can cause premature OOME.

#### Optional Anki

Q: Is Metaspace inside the Java heap?
A: No, HotSpot Metaspace uses native memory.

</details>

<a id="mem-fund-007"></a>

<details>
<summary><strong>MEM-FUND-007. Why is `-Xmx` not the full memory usage of a Java process?</strong></summary>

#### Short answer

`-Xmx` limits Java heap, but a JVM process also uses native memory, stacks, Metaspace, Code Cache, direct buffers and JVM internals.

#### Interview answer

A Java process has more memory than the heap. Besides heap, it uses thread stacks, Metaspace, Code Cache, direct/off-heap buffers, native libraries, JIT/compiler structures and memory mapped files.

That is why process RSS or container memory usage can be much larger than "used heap".

#### Deep dive

Some memory is reserved but not committed. Some is committed but not part of Java heap. Tools such as heap dumps see heap objects, while OS metrics see process memory.

#### Production angle

In Kubernetes, setting `-Xmx` equal to the pod memory limit is dangerous. You need headroom for non-heap and native memory.

#### Traps / caveats

- Heap usage stable does not mean process memory is stable.
- Native leaks do not show up as retained heap objects.
- Direct buffers can OOM independently from heap.

#### Optional Anki

Q: Why can RSS exceed Java heap usage?
A: The process also uses non-heap/native memory such as stacks, Metaspace, Code Cache and direct buffers.

</details>

<details>
<summary><strong>MEM-FUND-008. Where is the String Pool stored in modern Java, and can it cause OOME?</strong></summary>

#### Short answer

In modern HotSpot JVMs, interned strings live on the heap, and excessive interning can contribute to heap OOME.

#### Interview answer

The String Pool stores canonical interned string instances. Since modern Java moved interned strings out of PermGen-era storage, they are heap objects and are garbage-collectable when no longer reachable.

If code interns unbounded user input or high-cardinality values, it can retain many strings and increase heap pressure.

#### Deep dive

String literals are interned by class loading. Calling `intern()` manually can be useful in narrow cases but is dangerous for arbitrary runtime data.

#### Production angle

Symptoms can look like many retained `String`, `byte[]` or compact-string backing arrays in heap dumps.

#### Traps / caveats

- Do not intern request IDs, tokens or arbitrary names blindly.
- The pool does not make strings immortal in modern HotSpot.
- String memory issues often come from maps, caches and logs, not only the pool.

#### Optional Anki

Q: Can interned strings contribute to Java heap OOME?
A: Yes, if many interned strings remain reachable.

</details>

<details>
<summary><strong>🧠 MEM-FUND-009. How is a Java object represented in memory at a high level?</strong></summary>

#### Short answer

A Java object contains a header plus its fields, with alignment and padding determined by the JVM.

#### Interview answer

In HotSpot, an object has an object header used for runtime metadata such as identity, locking state and class information, followed by instance fields. Arrays also store length.

The exact layout is JVM-specific and affected by compressed references, field types and alignment.

#### Deep dive

This explains why small objects are not just the sum of their fields. Header overhead, references, padding and object graph shape can dominate memory footprint.

#### Production angle

Millions of small objects can consume much more memory than expected. This matters for caches, DTO graphs, maps and high-cardinality in-memory state.

#### Traps / caveats

- Object layout is implementation-specific.
- A reference field stores a reference, not the target object inline.
- Measuring with assumptions is risky; use tools such as JOL when exact layout matters.

#### Optional Anki

Q: Why can a small Java object take more memory than its fields suggest?
A: Object header, references, alignment and padding add overhead.

</details>

<a id="mem-fund-010"></a>

<details>
<summary><strong>🧠 MEM-FUND-010. What are compressed ordinary object pointers and compressed class space?</strong></summary>

#### Short answer

Compressed ordinary object pointers reduce reference size; compressed class space stores compressed class pointer metadata.

#### Interview answer

HotSpot can represent object references as compressed pointers instead of full 64-bit addresses, reducing heap footprint and improving cache locality. Compressed class pointers similarly refer to class metadata through a compressed representation, backed by compressed class space.

This is mostly a JVM footprint optimization.

#### Deep dive

Whether compression is enabled depends on heap size, alignment and JVM flags. Very large heaps may lose compressed references and see a noticeable footprint increase.

#### Production angle

Crossing a heap-size threshold can unexpectedly increase memory usage because references become wider. This is one reason bigger heaps are not always better.

#### Traps / caveats

- Do not memorize one universal heap cutoff; verify on the JVM you run.
- Compressed OOPs affects references, not primitive field sizes.
- It is usually a tuning detail, not an application design tool.

#### Optional Anki

Q: What is the main benefit of compressed OOPs?
A: Lower memory footprint by using compressed object references.

</details>
