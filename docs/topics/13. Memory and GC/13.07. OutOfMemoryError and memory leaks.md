# 13.07. OutOfMemoryError and memory leaks

---

<a id="mem-oom-001"></a>

<details>
<summary><strong>MEM-OOM-001. What happens when `OutOfMemoryError` occurs?</strong></summary>

#### Short answer

The JVM failed to allocate required memory in a specific area and throws an `OutOfMemoryError`.

#### Interview answer

`OutOfMemoryError` means the JVM could not satisfy an allocation request: heap object, Metaspace, direct buffer, native thread or another memory area. It is an `Error`, not a normal business exception, and the process may be in an unhealthy state.

The safest production response is usually to capture evidence and restart the instance under orchestration.

#### Deep dive

The exact message matters. `Java heap space`, `Metaspace`, `Direct buffer memory` and `Unable to create new native thread` point to different root causes.

#### Production angle

Enable useful diagnostics ahead of time: logs, metrics, heap dumps when safe, restart policy, alerts and enough disk/storage to preserve evidence.

#### Traps / caveats

- Do not assume every OOME is a heap leak.
- Do not keep serving traffic after repeated OOME without understanding state.
- OOMKilled may happen without Java throwing OOME.

#### Optional Anki

Q: What does `OutOfMemoryError` mean?
A: The JVM could not allocate required memory in some managed or native-backed area.

</details>

---

<a id="mem-oom-002"></a>

<details>
<summary><strong>MEM-OOM-002. What common types of `OutOfMemoryError` should a backend developer know?</strong></summary>

#### Short answer

Know heap space, GC overhead limit, Metaspace, direct buffer memory and unable to create new native thread.

#### Interview answer

`Java heap space` means heap allocation failed. `GC overhead limit exceeded` means the JVM spends too much time in GC while reclaiming little. `Metaspace` points to class metadata pressure. `Direct buffer memory` points to off-heap direct memory. `Unable to create new native thread` points to thread or native resource exhaustion.

Each message changes the investigation path.

#### Deep dive

Some errors are caused by leaks, others by bad sizing, traffic spikes, native limits or container configuration.

#### Production angle

Alert messages should include the exact OOME text. A runbook should branch by type instead of treating all memory failures as heap leaks.

#### Traps / caveats

- Heap dumps help heap OOME more than native OOME.
- Thread OOME may be a thread leak or OS/PID limit problem.
- Direct memory OOME may involve Netty pools or NIO buffers.

#### Optional Anki

Q: Why does the exact OOME message matter?
A: It points to the memory area that failed.

</details>

<a id="mem-oom-003"></a>

<details>
<summary><strong>MEM-OOM-003. What does `java.lang.OutOfMemoryError: Java heap space` mean?</strong></summary>

#### Short answer

The JVM could not allocate an object because the Java heap did not have enough reclaimable space.

#### Interview answer

`Java heap space` means a heap allocation failed after the JVM tried to make space through GC. Causes include a real heap leak, an oversized live set, too small heap, large request payloads, unbounded queues or normal traffic exceeding capacity.

The next step is to determine whether memory is retained or merely allocated heavily.

#### Deep dive

Look at post-GC heap, old-generation occupancy, heap dumps, allocation profiles and recent deployment changes.

#### Production angle

Collect evidence before restart if safe: GC logs, heap dump, class histogram, metrics and the failing endpoint or workload pattern.

#### Traps / caveats

- Increasing heap may only delay a leak.
- A single heap dump can be misleading without timeline.
- Large arrays often dominate heap OOME incidents.

#### Optional Anki

Q: What failed in `Java heap space` OOME?
A: A Java heap object allocation.

</details>

---

<a id="mem-oom-004"></a>

<details>
<summary><strong>MEM-OOM-004. What does `GC overhead limit exceeded` mean?</strong></summary>

#### Short answer

The JVM is spending excessive time in GC while reclaiming very little heap.

#### Interview answer

This error is a protection mechanism: the JVM detects that it is almost constantly collecting but not freeing enough memory. It usually means the heap is near exhaustion and the live set is too large for the configured heap.

Common causes are leaks, unbounded caches/queues or severe undersizing.

#### Deep dive

It is different from a single allocation failure. It means the JVM is stuck in a bad GC efficiency state.

#### Production angle

Investigate old-gen occupancy, post-GC heap baseline, GC throughput overhead and recent changes that increased retained memory.

#### Traps / caveats

- Disabling the overhead limit does not fix the root cause.
- It can happen without one huge allocation.
- It often precedes or accompanies heap OOME.

#### Optional Anki

Q: What does `GC overhead limit exceeded` indicate?
A: Too much GC time with too little memory reclaimed.

</details>

---

<a id="mem-oom-005"></a>

<details>
<summary><strong>MEM-OOM-005. What does `OutOfMemoryError: Metaspace` mean?</strong></summary>

#### Short answer

The JVM could not allocate more class metadata in Metaspace.

#### Interview answer

Metaspace stores class metadata outside the Java heap. Metaspace OOME can be caused by too many loaded classes, dynamic proxies, bytecode generation, repeated classloader creation or classloader leaks.

Increasing heap does not fix it.

#### Deep dive

A common pattern is redeployment or plugin loading where old classloaders remain reachable, preventing class unloading.

#### Production angle

Check loaded class count, Metaspace metrics, NMT, classloader stats and framework behavior around dynamic class generation.

#### Traps / caveats

- `MaxMetaspaceSize` too low can cause false pressure.
- Raising the limit can hide a leak.
- Heap dump analysis may need classloader-focused inspection.

#### Optional Anki

Q: Is Metaspace OOME fixed by increasing `-Xmx`?
A: No, Metaspace is outside Java heap.

</details>

---

<a id="mem-oom-006"></a>

<details>
<summary><strong>MEM-OOM-006. What does `OutOfMemoryError: Direct buffer memory` mean?</strong></summary>

#### Short answer

The JVM could not allocate more direct buffer memory outside the Java heap.

#### Interview answer

Direct buffers use native memory and are common in NIO, Netty and high-throughput I/O. This OOME means the direct memory limit or available native memory was exhausted.

Heap usage may look normal because the failing memory is off-heap.

#### Deep dive

Direct memory is associated with Java wrapper objects, but native memory cleanup depends on those wrappers becoming unreachable and cleaners running.

#### Production angle

Inspect direct buffer metrics, Netty allocator metrics, RSS, NMT, request payload sizes and whether buffers are released correctly.

#### Traps / caveats

- A heap dump may not show the full native allocation.
- Netty reference-counted buffers must be released correctly.
- Increasing heap can make direct memory headroom worse in containers.

#### Optional Anki

Q: Why can direct buffer OOME occur when heap looks fine?
A: Direct buffers allocate native memory outside heap.

</details>

<a id="mem-oom-007"></a>

<details>
<summary><strong>MEM-OOM-007. What does `OutOfMemoryError: Unable to create new native thread` mean?</strong></summary>

#### Short answer

The JVM could not create another OS thread because native memory or thread limits were exhausted.

#### Interview answer

Java platform threads map to native threads. Creating one requires OS resources and stack memory. This error can happen because of too many threads, a thread leak, huge stack size, OS user limits, container PID limits or memory exhaustion.

It is not primarily a Java heap problem.

#### Deep dive

Thread pools, schedulers, unbounded executors and per-request thread creation are common causes.

#### Production angle

Check thread count, thread dumps, executor metrics, `ulimit`, PID limits, container settings, stack size and RSS.

#### Traps / caveats

- Increasing `-Xmx` does not help and may hurt.
- The process can become unstable if it cannot create critical JVM threads.
- Virtual threads reduce native thread pressure but do not remove all limits.

#### Optional Anki

Q: What should you inspect for native thread OOME?
A: Thread count, OS/container limits, stack size and thread leaks.

</details>

<a id="mem-oom-008"></a>

<details>
<summary><strong>MEM-OOM-008. Can `OutOfMemoryError` be caught and handled safely?</strong></summary>

#### Short answer

Usually not safely; you can catch it for emergency logging or cleanup, but the process may be unhealthy.

#### Interview answer

`OutOfMemoryError` is an `Error`, not a normal recoverable exception. After OOME, important allocations may fail, application state may be inconsistent and recovery code may itself need memory.

In production, the safer pattern is fail fast, capture evidence if possible and let orchestration restart the instance.

#### Deep dive

There are narrow cases where a component catches OOME around a known large allocation and degrades gracefully, but this must be designed carefully.

#### Production angle

Use `ExitOnOutOfMemoryError`, restart policies and alerting. Avoid swallowing OOME and continuing silently.

#### Traps / caveats

- Catching `Throwable` can accidentally catch OOME.
- Logging after OOME can allocate and fail.
- Continuing after repeated OOME can corrupt service behavior.

#### Optional Anki

Q: Should normal business code catch OOME?
A: No, usually the process should capture evidence and restart.

</details>

<a id="mem-oom-009"></a>

<details>
<summary><strong>MEM-OOM-009. How would you detect a Java heap memory leak?</strong></summary>

#### Short answer

Watch post-GC heap growth and confirm with heap dumps, histograms or allocation/retention analysis.

#### Interview answer

I would look for a steadily rising post-GC baseline, increasing old generation, frequent Full GC and eventual heap OOME. Then I would compare heap dumps or class histograms over time and inspect dominators and paths to GC roots.

The goal is to find what retains the growing object graph.

#### Deep dive

A leak may be slow, traffic-dependent or triggered by a specific endpoint, tenant or deployment.

#### Production angle

Correlate memory growth with releases, traffic, cache metrics, queue lengths and request patterns.

#### Traps / caveats

- One heap dump rarely proves growth.
- High allocation rate is not necessarily a leak.
- Native memory leaks need different tools.

#### Optional Anki

Q: What graph trend suggests a heap leak?
A: Post-GC heap usage steadily rises over time.

</details>

<a id="mem-oom-010"></a>

<details>
<summary><strong>MEM-OOM-010. How would you distinguish a memory leak from normal cache growth?</strong></summary>

#### Short answer

A healthy cache reaches a bound; a leak or bad cache grows without an effective limit.

#### Interview answer

I would check whether the cache has maximum size/weight, TTL, eviction metrics and stable cardinality under steady load. Normal cache warmup should plateau. A leak-like cache keeps growing or retains entries long after they are useful.

Heap dumps can show cache dominance and key/value types.

#### Deep dive

Some caches grow with business data or tenant count. That may be intended but still requires capacity limits.

#### Production angle

Monitor cache size, hit rate, eviction count, entry weight, load failures and memory usage after warmup.

#### Traps / caveats

- TTL alone is not a memory bound.
- High hit rate does not prove safe memory behavior.
- Weak/soft references are not a substitute for explicit cache policy.

#### Optional Anki

Q: What should normal cache warmup do?
A: Grow until it reaches a stable bound.

</details>

<a id="mem-oom-011"></a>

<details>
<summary><strong>MEM-OOM-011. How can static collections cause memory leaks?</strong></summary>

#### Short answer

A static collection can live for the lifetime of the classloader and retain everything added to it.

#### Interview answer

Static fields are reachable through loaded classes. If a static `Map`, `List` or registry accumulates data and never removes it, all entries remain reachable and cannot be collected.

This is common with global caches, registries, test helpers or accidental singleton state.

#### Deep dive

The static field may be small, but it can retain a large graph through collection elements.

#### Production angle

Heap dumps often show static maps or singleton beans as dominators. The fix is bounded storage, lifecycle cleanup or removing global mutable state.

#### Traps / caveats

- `static final` does not mean memory-safe.
- Static state can also cause classloader leaks.
- A concurrent collection can still leak if unbounded.

#### Optional Anki

Q: Why are static collections risky?
A: They can retain entries for the lifetime of the classloader.

</details>

<a id="mem-oom-012"></a>

<details>
<summary><strong>MEM-OOM-012. How can `ThreadLocal` cause memory leaks?</strong></summary>

#### Short answer

`ThreadLocal` values can remain attached to long-lived pool threads after request work finishes.

#### Interview answer

In backend services, threads are reused by pools. If code sets a `ThreadLocal` and does not remove it, the value can stay reachable for as long as the thread lives. This can retain request data, security context, tenant data or large buffers.

The risk is worse with application redeployments and classloader references.

#### Deep dive

`ThreadLocalMap` entries can also behave surprisingly when keys are weakly referenced but values remain until cleanup occurs.

#### Production angle

Always clean up in `finally`, use framework-supported context propagation and monitor thread pool reuse boundaries.

#### Traps / caveats

- MDC is often backed by thread-local state.
- Async execution can lose or leak thread-local context.
- Virtual threads reduce some pool reuse risks but do not make context design irrelevant.

#### Optional Anki

Q: What is the standard `ThreadLocal` cleanup pattern?
A: Remove the value in a `finally` block.

</details>

<a id="mem-oom-013"></a>

<details>
<summary><strong>MEM-OOM-013. How can classloader leaks happen in Java applications?</strong></summary>

#### Short answer

A classloader leaks when something outside it still references classes, instances or static state loaded by it.

#### Interview answer

In app servers, plugin systems or redeployable applications, old classloaders should become unreachable after undeploy. They cannot be collected if threads, statics, registries, JDBC drivers, caches, listeners or `ThreadLocal` values still reference their classes or objects.

That keeps both heap objects and Metaspace alive.

#### Deep dive

The leak root is often a parent classloader, running thread or global registry that outlives the application classloader.

#### Production angle

Symptoms include Metaspace growth after redeployments and heap dumps showing old classloaders retained.

#### Traps / caveats

- Restarting hides the leak until the next redeploy cycle.
- Static cleanup hooks are easy to forget.
- Dynamically generated classes amplify the issue.

#### Optional Anki

Q: What must happen for a classloader to be unloaded?
A: The classloader and its loaded classes/instances must become unreachable.

</details>

<a id="mem-oom-014"></a>

<details>
<summary><strong>MEM-OOM-014. How can listeners, executors, scheduled tasks or MDC retain objects?</strong></summary>

#### Short answer

They can keep callbacks, task closures or context maps reachable long after the request or component should be gone.

#### Interview answer

Listener registries retain subscribers until explicitly removed. Executors retain queued tasks, running task closures and scheduled tasks. MDC stores logging context, often in thread-local state. If these hold request objects, service beans or classloader-owned classes, they can leak.

Lifecycle cleanup is essential.

#### Deep dive

Leaks often come from "small" objects such as lambdas that capture a large enclosing object graph.

#### Production angle

Check queue size, scheduled task registries, listener counts, MDC cleanup and shutdown hooks during memory investigations.

#### Traps / caveats

- Lambdas can retain `this`.
- Cancelling a scheduled task may not remove all references immediately.
- Logging context must be cleared on pooled threads.

#### Optional Anki

Q: Why can a listener registry leak?
A: It keeps subscriber references until they are removed.

</details>

<a id="mem-oom-015"></a>

<details>
<summary><strong>MEM-OOM-015. How can unbounded queues and caches cause memory leaks?</strong></summary>

#### Short answer

They retain data without a hard limit, so memory grows with traffic or key cardinality.

#### Interview answer

An unbounded queue retains tasks or messages when producers outrun consumers. An unbounded cache retains entries as more keys appear. Both can look fine in tests but fail under production traffic spikes, slow downstreams or high-cardinality tenants.

Bounded capacity and backpressure are required.

#### Deep dive

Unbounded structures often turn latency or downstream failure into memory growth.

#### Production angle

Monitor queue depth, cache size, eviction, rejected tasks, downstream latency and producer/consumer rates.

#### Traps / caveats

- `ConcurrentHashMap` is thread-safe, not memory-safe.
- TTL without max size can still allow huge growth.
- Unbounded executor queues can hide overload until OOME.

#### Optional Anki

Q: What should replace unbounded queues under load?
A: Bounded queues with backpressure, rejection or shedding policy.

</details>

<a id="mem-oom-016"></a>

<details>
<summary><strong>MEM-OOM-016. What would you do after receiving a production `OutOfMemoryError`?</strong></summary>

#### Short answer

Stabilize the service, preserve evidence and identify the failed memory area before changing settings.

#### Interview answer

First, check the exact OOME message, logs, metrics, pod events and recent deployments. If safe, collect a heap dump, class histogram, GC logs or NMT data depending on the error type. Then restart or replace the unhealthy instance.

After mitigation, analyze whether the cause was leak, sizing, traffic spike, native memory, thread growth or configuration.

#### Deep dive

Evidence must be collected quickly because restarts remove process state. But diagnostics must not make the outage worse.

#### Production angle

A mature team has preconfigured dump paths, alert context, dashboards and runbooks per OOME type.

#### Traps / caveats

- Do not blindly increase heap.
- Do not ignore OOMKilled events.
- Do not leave sensitive dumps unmanaged.

#### Optional Anki

Q: What is the first thing to identify after OOME?
A: The exact memory area/message that failed.

</details>

<a id="mem-oom-017"></a>

<details>
<summary><strong>🧠 MEM-OOM-017. What are retention path, retained size, shallow size and dominator tree?</strong></summary>

#### Short answer

They are heap analysis concepts used to explain what keeps objects alive and how much memory they retain.

#### Interview answer

Shallow size is the memory of one object itself. Retained size is the memory that would become collectible if that object were removed. A retention path shows references from GC roots to an object. A dominator tree groups objects by which objects dominate retention.

These concepts help find leak owners, not just large object types.

#### Deep dive

An object with small shallow size can have huge retained size if it owns a large collection or graph.

#### Production angle

In MAT or similar tools, inspect dominators and paths to GC roots to find the field, cache or thread retaining memory.

#### Traps / caveats

- Largest shallow object is not always the leak.
- Paths to roots can be expensive to compute.
- Retained size can be tool- and snapshot-dependent.

#### Optional Anki

Q: What does retained size estimate?
A: Memory that would be freed if an object and objects only reachable through it were collected.

</details>
