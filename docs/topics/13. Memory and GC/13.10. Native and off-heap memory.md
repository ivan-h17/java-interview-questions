# 13.10. Native and off-heap memory

---

<a id="mem-native-001"></a>

<details>
<summary><strong>MEM-NATIVE-001. What is native or off-heap memory in a Java process?</strong></summary>

#### Short answer

It is memory used by the JVM process outside the managed Java heap.

#### Interview answer

A Java process uses native memory for Metaspace, thread stacks, Code Cache, direct buffers, GC/JIT structures, native libraries, memory-mapped files and JVM internals. Off-heap usually refers to memory intentionally used outside heap, such as direct buffers or native caches.

This memory counts toward process RSS and container limits.

#### Deep dive

Some native memory is controlled by JVM flags, some by libraries and some by OS allocator behavior.

#### Production angle

When heap is stable but RSS grows, native/off-heap memory is a primary suspect.

#### Traps / caveats

- Heap dumps do not show all native memory.
- `-Xmx` does not cap native memory.
- Container OOMKilled can happen with healthy heap usage.

#### Optional Anki

Q: What is native memory in Java?
A: Process memory outside the managed Java heap.

</details>

<a id="mem-native-002"></a>

<details>
<summary><strong>MEM-NATIVE-002. What are DirectByteBuffers?</strong></summary>

#### Short answer

`DirectByteBuffer`s are byte buffers whose storage is allocated outside the Java heap.

#### Interview answer

Direct buffers are used for efficient I/O because native code and operating system calls can work with their memory more directly. The Java object is on the heap, but the buffer storage is native memory.

They are common in NIO frameworks and libraries such as Netty.

#### Deep dive

Direct memory cleanup depends on the Java wrapper becoming unreachable and cleaner mechanisms eventually releasing native memory.

#### Production angle

Direct buffer-heavy services must monitor direct memory and process RSS, not only heap.

#### Traps / caveats

- Direct buffers can cause native pressure while heap looks fine.
- Cleaner timing is not deterministic.
- Pooling reduces allocation cost but can retain memory.

#### Optional Anki

Q: Where is the storage of a direct buffer allocated?
A: Outside the Java heap, in native memory.

</details>

<a id="mem-native-003"></a>

<details>
<summary><strong>MEM-NATIVE-003. Why can direct memory cause OOME even if heap looks fine?</strong></summary>

#### Short answer

Direct memory is outside the heap, so it can be exhausted independently from heap usage.

#### Interview answer

The heap may have plenty of free space while direct buffer memory reaches its limit or the process runs out of native memory. The JVM then throws `OutOfMemoryError: Direct buffer memory` or the container may kill the process if RSS exceeds the limit.

This is common in network-heavy services.

#### Deep dive

The heap contains wrapper objects, but the large payload memory may be native. A heap dump may show wrappers without making native pressure obvious.

#### Production angle

Inspect direct buffer pool metrics, Netty allocator metrics, NMT, RSS and request payload behavior.

#### Traps / caveats

- Increasing heap does not increase direct memory headroom in containers.
- Direct memory leaks often come from missed buffer release.
- Native OOM may not produce a useful heap dump.

#### Optional Anki

Q: What metric can reveal direct memory pressure better than heap used?
A: Direct buffer/native memory or process RSS metrics.

</details>

<a id="mem-native-004"></a>

<details>
<summary><strong>MEM-NATIVE-004. How does Netty use pooled direct memory?</strong></summary>

#### Short answer

Netty often pools direct buffers to reduce allocation cost and improve I/O performance.

#### Interview answer

Netty uses `ByteBuf` abstractions and can allocate pooled direct memory. Pooling avoids frequent native allocations and helps high-throughput networking, but memory remains reserved by the pool and must be released correctly when reference-counted buffers are used.

Mismanagement can look like direct memory growth.

#### Deep dive

Reference-counted buffers require ownership discipline. Forgetting `release()` or retaining too long can leak native memory.

#### Production angle

Monitor Netty allocator metrics, leak detector logs, direct memory usage and request/response buffering.

#### Traps / caveats

- Pooled memory staying high is not always a leak.
- Reference-counted APIs are easy to misuse.
- Heap metrics alone are insufficient for Netty services.

#### Optional Anki

Q: Why does Netty pool direct buffers?
A: To reduce native allocation overhead and improve I/O performance.

</details>

<a id="mem-native-005"></a>

<details>
<summary><strong>MEM-NATIVE-005. What is memory-mapped I/O, and how can it affect process memory?</strong></summary>

#### Short answer

Memory-mapped I/O maps file contents into virtual memory, which can affect RSS and native memory interpretation.

#### Interview answer

With memory-mapped I/O, a file is mapped into the process address space and accessed like memory. The OS loads pages as needed. Java can use this through APIs such as `MappedByteBuffer`.

It can be efficient, but memory accounting can be confusing because mapped pages may appear in process memory.

#### Deep dive

Mapped memory is outside ordinary Java heap. Releasing mappings depends on buffer lifecycle and JVM/OS behavior.

#### Production angle

When RSS is high and heap is stable, check mmap usage, file-backed mappings and libraries that use memory-mapped files.

#### Traps / caveats

- Virtual memory reservation is not the same as resident memory.
- Mapped files can hold file descriptors/resources.
- Heap dump will not show mapped page contents as heap objects.

#### Optional Anki

Q: Is memory-mapped file data ordinary Java heap?
A: No, it is mapped native/OS-managed memory.

</details>

<a id="mem-native-006"></a>

<details>
<summary><strong>MEM-NATIVE-006. Why is native memory not visible in a normal heap dump?</strong></summary>

#### Short answer

A heap dump contains Java heap objects, not all native allocations owned by the process.

#### Interview answer

Heap dumps show Java objects and references. Native allocations from direct buffers, thread stacks, Metaspace internals, native libraries, malloc arenas or memory mappings are outside the heap. The dump may show Java wrapper objects, but not necessarily the native bytes they represent.

Use NMT or OS/native tools for native memory.

#### Deep dive

This distinction is why heap dump analysis can look normal while RSS keeps growing.

#### Production angle

For RSS growth with flat heap, collect NMT, `/proc` maps/smaps where available, container metrics and library-specific native metrics.

#### Traps / caveats

- Heap dump cannot prove native memory is healthy.
- Wrapper objects can underestimate native payload size.
- Some native allocations are invisible to NMT categories.

#### Optional Anki

Q: What does a normal heap dump exclude?
A: Most process native memory allocations.

</details>

<a id="mem-native-007"></a>

<details>
<summary><strong>MEM-NATIVE-007. How would you investigate native memory growth?</strong></summary>

#### Short answer

Compare RSS with heap metrics, then inspect NMT, direct buffers, thread count, mmap and native library behavior.

#### Interview answer

First confirm heap is stable while RSS grows. Then check direct buffer metrics, Netty pools, thread count and stack sizing, Metaspace/class count, Code Cache and NMT summaries/diffs. OS-level evidence such as memory maps can help identify mmap or native allocator growth.

Tie the growth to traffic, deployment and workload changes.

#### Deep dive

NMT baseline/diff is useful if enabled. If not, you may need platform tools or library-specific metrics.

#### Production angle

Native growth can lead to OOMKilled without Java OOME, so container events and RSS alerts are critical.

#### Traps / caveats

- Do not take only a heap dump and stop.
- Native allocator behavior may keep RSS high after frees.
- Missing JDK tools in containers can block diagnosis.

#### Optional Anki

Q: What is the first check for native memory growth?
A: Heap stable while process RSS grows.

</details>

<a id="mem-native-008"></a>

<details>
<summary><strong>🧠 MEM-NATIVE-008. How can virtual threads affect memory compared to platform threads?</strong></summary>

#### Short answer

Virtual threads avoid one OS stack per task, but their continuations and captured state still consume memory.

#### Interview answer

Platform threads are expensive because each maps to an OS thread with a native stack. Virtual threads are much lighter and allow many concurrent blocking-style tasks. Their stack state is stored in JVM-managed chunks when parked, rather than requiring a dedicated native thread per virtual thread.

This reduces native thread pressure, but millions of virtual threads can still consume heap and scheduler resources.

#### Deep dive

Pinned virtual threads, large captured request graphs and unbounded task creation can still cause memory or throughput problems.

#### Production angle

Monitor virtual thread count, request concurrency, heap pressure and blocking behavior. Use bounded admission even with virtual threads.

#### Traps / caveats

- Virtual threads are not free.
- They do not eliminate backpressure requirements.
- Thread-local usage can become expensive at huge scale.

#### Optional Anki

Q: What memory benefit do virtual threads provide?
A: They avoid requiring one native OS stack per concurrent task.

</details>

<a id="mem-native-009"></a>

<details>
<summary><strong>🧠 MEM-NATIVE-009. How can JNI libraries, native allocators or glibc arenas affect RSS?</strong></summary>

#### Short answer

Native code and allocators can reserve or retain memory outside JVM heap accounting, causing RSS growth or poor memory return to the OS.

#### Interview answer

JNI libraries can allocate memory with native allocators that the JVM does not manage like heap. General-purpose allocators may keep arenas and caches for reuse, so RSS may remain high even after memory is freed. glibc arenas can also multiply with threads and affect memory footprint.

This can make process memory look like a leak even when heap is stable.

#### Deep dive

NMT may not fully attribute all third-party native allocations. OS tools, allocator configuration and library metrics may be needed.

#### Production angle

For native-heavy services, compare RSS, NMT, thread count, memory maps and library-specific stats. Consider allocator tuning only with careful testing.

#### Traps / caveats

- Native memory problems may survive heap tuning.
- Freeing memory does not always reduce RSS immediately.
- Allocator changes can affect performance and fragmentation.

#### Optional Anki

Q: Why can RSS stay high after native memory is freed?
A: The native allocator may retain arenas/pages for reuse instead of returning them immediately.

</details>
