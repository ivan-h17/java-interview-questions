# 13.11. Class loading, Metaspace and class unloading

---

<a id="mem-class-001"></a>

<details>
<summary><strong>MEM-CLASS-001. What is stored in Metaspace?</strong></summary>

#### Short answer

Metaspace stores JVM class metadata outside the Java heap.

#### Interview answer

HotSpot uses Metaspace for metadata about loaded classes: structure, methods, fields, constant pools and runtime data needed by the JVM. The Java `Class` object is on the heap, but the underlying metadata is native memory.

Metaspace grows as classes are loaded.

#### Deep dive

Frameworks that create proxies or generated classes can increase Metaspace usage even if application code does not define many classes manually.

#### Production angle

Monitor Metaspace and loaded class count. Growth after redeployments or runtime generation can indicate classloader leaks.

#### Traps / caveats

- Metaspace is not controlled by `-Xmx`.
- Heap dumps do not fully represent Metaspace.
- Class metadata can remain if classloaders are retained.

#### Optional Anki

Q: Is Metaspace heap memory?
A: No, it is native memory used for class metadata.

</details>

<a id="mem-class-002"></a>

<details>
<summary><strong>MEM-CLASS-002. When can classes be unloaded?</strong></summary>

#### Short answer

Classes can be unloaded when their defining classloader and loaded classes are no longer reachable.

#### Interview answer

The JVM cannot unload an individual class while its classloader remains live. In practice, class unloading requires the classloader, its classes, instances, static fields and related metadata to become unreachable.

Class unloading usually happens during GC cycles that include class metadata processing.

#### Deep dive

Application classloaders in redeployable environments should become unreachable after undeploy. If not, Metaspace grows over redeployments.

#### Production angle

Class unloading matters in app servers, plugin systems, scripting engines and applications with heavy dynamic class generation.

#### Traps / caveats

- Static fields can keep classloader-owned graphs alive.
- Running threads can retain context classloaders.
- Parent classloader references can prevent unloading.

#### Optional Anki

Q: What must become unreachable for class unloading?
A: The defining classloader and objects/classes it owns.

</details>

<a id="mem-class-003"></a>

<details>
<summary><strong>MEM-CLASS-003. What can prevent class unloading?</strong></summary>

#### Short answer

Reachable classloaders, static fields, running threads, `ThreadLocal`s, registries and native references can prevent unloading.

#### Interview answer

A classloader cannot be unloaded if anything still references it or objects loaded by it. Common causes include static collections, thread context classloaders, `ThreadLocal` values, scheduler threads, JDBC drivers, logging frameworks, listeners and global registries.

The retention root often lives outside the application classloader.

#### Deep dive

Classloader leaks are transitive: one retained class or instance can keep the whole classloader and its metadata alive.

#### Production angle

In redeployable systems, verify shutdown hooks, deregistration and thread cleanup.

#### Traps / caveats

- A small forgotten listener can retain a large classloader.
- Metaspace leaks may also retain heap.
- Restarting hides but does not fix classloader leaks.

#### Optional Anki

Q: Why can one leaked object prevent many classes from unloading?
A: It can keep the defining classloader reachable.

</details>

<a id="mem-class-004"></a>

<details>
<summary><strong>MEM-CLASS-004. What is a classloader leak?</strong></summary>

#### Short answer

A classloader leak is unwanted retention of a classloader that should have been garbage-collected.

#### Interview answer

Classloader leaks often occur after redeployment or plugin unload. The old classloader remains reachable through a long-lived thread, static field, registry, native handle or `ThreadLocal`, so classes, class metadata and related heap objects cannot be freed.

Over time, this can cause Metaspace OOME.

#### Deep dive

The leak may not show up as one huge object; it may appear as many old classloaders with similar retained graphs.

#### Production angle

Look for increasing loaded class count, Metaspace growth and old application classloaders in heap dump or classloader stats.

#### Traps / caveats

- Increasing Metaspace only delays the failure.
- The retaining root may be in a framework or container.
- Classloader leaks are less visible in simple one-shot apps.

#### Optional Anki

Q: What memory area is commonly affected by classloader leaks?
A: Metaspace.

</details>

<a id="mem-class-005"></a>

<details>
<summary><strong>MEM-CLASS-005. How can static fields or `ThreadLocal` prevent classloader unloading?</strong></summary>

#### Short answer

They can keep classloader-owned objects reachable from long-lived roots.

#### Interview answer

Static fields belong to classes loaded by a classloader and can retain object graphs. `ThreadLocal` values on long-lived threads can retain objects loaded by an old application classloader. If those roots remain after redeployment, the classloader cannot be collected.

This ties heap retention to Metaspace retention.

#### Deep dive

Thread pools are especially risky because threads may outlive application lifecycle boundaries.

#### Production angle

Clean static registries, shut down executors and remove `ThreadLocal` values during application shutdown.

#### Traps / caveats

- `ThreadLocal` keys may be weak, but values can still linger.
- Static caches in shared libraries can retain application classes.
- MDC cleanup matters on pooled threads.

#### Optional Anki

Q: Why are long-lived thread pools risky for class unloading?
A: Their `ThreadLocal` values or context classloaders can retain old application classes.

</details>

<a id="mem-class-006"></a>

<details>
<summary><strong>🧠 MEM-CLASS-006. How can dynamically generated classes increase Metaspace usage?</strong></summary>

#### Short answer

Generated proxies, bytecode and lambda-related classes add class metadata that lives in Metaspace.

#### Interview answer

Frameworks may generate classes for proxies, reflection optimization, serialization, ORM, mocking, scripting or expression evaluation. If generation is bounded, this is normal. If classes are generated per tenant, request or unique input, Metaspace can grow unexpectedly.

Classloaders also determine whether generated classes can be unloaded.

#### Deep dive

Modern JVMs handle lambdas differently from older anonymous-class patterns, but dynamic runtime generation can still create metadata pressure.

#### Production angle

Watch loaded class count, Metaspace growth and framework caches when introducing dynamic proxies or scripting.

#### Traps / caveats

- Dynamic class generation is not automatically a leak.
- Unbounded generation is the risk.
- Mocking/proxy-heavy tests may not reflect production.

#### Optional Anki

Q: Why can generated classes affect Metaspace?
A: Every loaded class needs class metadata.

</details>

<a id="mem-class-007"></a>

<details>
<summary><strong>MEM-CLASS-007. How would you investigate Metaspace growth?</strong></summary>

#### Short answer

Monitor Metaspace and loaded classes, then inspect classloaders, generated classes and class unloading behavior.

#### Interview answer

I would first confirm Metaspace growth with JVM metrics and GC logs. Then I would check loaded class count, recent deployments, proxy/generation-heavy code, NMT Class category and classloader stats if available. Heap dumps can help find old classloaders retained by threads, statics or registries.

The goal is to distinguish normal class loading from a leak.

#### Deep dive

If growth happens only after redeployments, suspect classloader leaks. If it happens with traffic, suspect dynamic class generation.

#### Production angle

Collect evidence before simply raising `MaxMetaspaceSize`, otherwise the leak may reappear later.

#### Traps / caveats

- Heap usage can be stable while Metaspace grows.
- Class unloading depends on GC and classloader reachability.
- NMT may need startup configuration.

#### Optional Anki

Q: What two signals help investigate Metaspace growth?
A: Metaspace usage and loaded class/classloader counts.

</details>

<a id="mem-class-008"></a>

<details>
<summary><strong>🧠 MEM-CLASS-008. Why can increasing `MaxMetaspaceSize` hide a classloader leak?</strong></summary>

#### Short answer

It gives the leak more room to grow without removing the retained classloaders.

#### Interview answer

If Metaspace grows because old classloaders are retained, increasing `MaxMetaspaceSize` only delays OOME. The same leak still accumulates metadata and often heap objects too.

The real fix is to break the retaining references and allow unloading.

#### Deep dive

This is similar to increasing heap for a heap leak: it changes time-to-failure, not the failure mode.

#### Production angle

Raising the limit can be a temporary mitigation, but it should be paired with leak analysis and a follow-up fix.

#### Traps / caveats

- Bigger limits can increase RSS and pod OOM risk.
- The leak may become slower and harder to notice.
- Classloader leaks often require lifecycle fixes.

#### Optional Anki

Q: What does increasing `MaxMetaspaceSize` do for a classloader leak?
A: It delays failure but does not fix retention.

</details>
