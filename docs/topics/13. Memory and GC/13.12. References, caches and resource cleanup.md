# 13.12. References, caches and resource cleanup

---

<a id="mem-ref-001"></a>

<details>
<summary><strong>MEM-REF-001. How do strong, soft, weak and phantom references affect cache and cleanup design?</strong></summary>

#### Short answer

They define different reachability strengths, but production caches should usually use explicit bounds instead of relying on GC reference behavior.

#### Interview answer

Strong references keep objects alive. Soft references may be cleared under memory pressure. Weak references do not keep objects alive once only weakly reachable. Phantom references are used for post-mortem cleanup patterns after final reachability is gone.

For backend caches, explicit eviction, TTL and size/weight limits are usually safer than soft/weak-reference tricks.

#### Deep dive

Reference types are useful for specialized structures and cleanup, but they make cache behavior less predictable because GC timing becomes part of application semantics.

#### Production angle

Use Caffeine or another cache with clear policy, metrics and bounds. Treat reference-based behavior as advanced and carefully justified.

#### Traps / caveats

- Weak references can disappear sooner than business logic expects.
- Soft references can be cleared unpredictably.
- Phantom references are not deterministic cleanup for normal resources.

#### Optional Anki

Q: What should production caches rely on instead of GC pressure?
A: Explicit eviction, TTL and size/weight bounds.

</details>

<a id="mem-ref-002"></a>

<details>
<summary><strong>MEM-REF-002. Why is `WeakHashMap` not a general-purpose cache?</strong></summary>

#### Short answer

`WeakHashMap` weakens keys, so entries can disappear based on key reachability, not cache policy.

#### Interview answer

`WeakHashMap` removes entries when keys are no longer strongly reachable elsewhere. That is useful for certain metadata associations, but it is not a normal cache policy: it has no capacity planning, no TTL, no weight limit and no predictable eviction based on value.

For production caches, use an explicit cache library.

#### Deep dive

Values can also accidentally refer back to keys, preventing cleanup. Behavior depends on GC timing.

#### Production angle

Use `WeakHashMap` only when the lifecycle of the key should control the lifecycle of the entry.

#### Traps / caveats

- Weak keys can vanish unexpectedly.
- It does not protect against large value graphs.
- It is not a replacement for Caffeine or Redis.

#### Optional Anki

Q: What controls `WeakHashMap` entry removal?
A: Weak key reachability and GC processing.

</details>

<a id="mem-ref-003"></a>

<details>
<summary><strong>MEM-REF-003. Why are `SoftReference` caches usually a poor production strategy?</strong></summary>

#### Short answer

They make cache eviction depend on GC pressure, which is hard to predict and observe.

#### Interview answer

Soft references can be cleared when the JVM needs memory, but the exact timing depends on GC behavior and memory pressure. This gives unpredictable hit rates and can cause cache stampedes when many entries are cleared together.

Explicit cache sizing is more reliable.

#### Deep dive

Soft-reference caches were historically popular, but modern backend systems need predictable latency, capacity and metrics.

#### Production angle

Use bounded caches with maximum size/weight, TTL, refresh policy and observability.

#### Traps / caveats

- Soft references do not encode business freshness.
- GC pressure can clear too much at once.
- Hit-rate instability can increase downstream load.

#### Optional Anki

Q: What is the main problem with soft-reference caches?
A: Eviction is driven by GC pressure rather than explicit policy.

</details>

<a id="mem-ref-004"></a>

<details>
<summary><strong>MEM-REF-004. How should production caches be bounded to avoid memory leaks?</strong></summary>

#### Short answer

Use explicit maximum size or weight, eviction policy, TTL/expiry and metrics.

#### Interview answer

A production cache should have a clear memory bound: maximum entries or maximum weight when values differ in size. It should also define expiration or refresh behavior, eviction policy and what happens under load.

Without bounds, a cache can become an unbounded memory leak.

#### Deep dive

Size-based bounds and TTL solve different problems. Size controls memory; TTL controls staleness and eventual removal.

#### Production angle

Monitor cache size, weight, hit rate, eviction count, load latency and downstream impact.

#### Traps / caveats

- TTL alone is not a hard memory bound.
- Maximum entry count can be unsafe if entries vary greatly in size.
- Cache keys with unbounded cardinality are dangerous.

#### Optional Anki

Q: What is the minimum production cache memory control?
A: A maximum size or maximum weight.

</details>

<a id="mem-ref-005"></a>

<details>
<summary><strong>MEM-REF-005. How do eviction policy, TTL, maximum size and maximum weight differ?</strong></summary>

#### Short answer

Eviction chooses what to remove; TTL removes by age; max size limits count; max weight limits estimated memory or cost.

#### Interview answer

An eviction policy decides which entries leave when space is needed. TTL expires entries after a time. Maximum size caps entry count. Maximum weight caps total estimated cost, useful when entries have different memory sizes.

They are complementary controls.

#### Deep dive

For backend services, maximum weight is often better than size when values can be tiny or huge.

#### Production angle

Choose policies based on business correctness, memory risk and downstream load if entries are evicted or refreshed.

#### Traps / caveats

- TTL does not prevent too many entries before expiry.
- Size count does not account for value size.
- Eviction can increase downstream traffic.

#### Optional Anki

Q: Which cache bound handles differently sized values better?
A: Maximum weight.

</details>

<a id="mem-ref-006"></a>

<details>
<summary><strong>MEM-REF-006. How can Caffeine help manage cache memory, and which metrics matter?</strong></summary>

#### Short answer

Caffeine provides bounded in-process caching with eviction, expiry, refresh and useful statistics.

#### Interview answer

Caffeine supports maximum size/weight, time-based expiry, refresh, weak/soft options when justified and efficient eviction algorithms. For memory safety, the important part is explicit bounds and visibility into cache behavior.

Useful metrics include size/weight, hit rate, eviction count, load count, load failures and load duration.

#### Deep dive

Caffeine is in-process, so its memory is part of the service heap. Each replica has its own cache.

#### Production angle

Tune cache policy with downstream capacity in mind. Evicting too aggressively can overload databases or remote services.

#### Traps / caveats

- In-process caches multiply memory by replica count.
- Hit rate alone does not prove memory safety.
- Weight functions must approximate real cost well enough.

#### Optional Anki

Q: What Caffeine feature is most important for memory safety?
A: Explicit maximum size or weight.

</details>

<a id="mem-ref-007"></a>

<details>
<summary><strong>MEM-REF-007. When should you use Redis or another external cache instead of an in-process cache?</strong></summary>

#### Short answer

Use an external cache when data must be shared, large, centrally bounded or survive individual service instances.

#### Interview answer

In-process caches are fast and simple but consume each replica's heap and are not shared. Redis or another external cache is useful when cache data is large, needs shared state, central eviction, cross-instance consistency or independent scaling.

The trade-off is network latency, serialization and another dependency.

#### Deep dive

External caches still need eviction, TTL and capacity planning. They move memory pressure, not eliminate it.

#### Production angle

Choose based on latency, consistency, cost, failure mode and memory budget across replicas.

#### Traps / caveats

- Redis is not infinite memory.
- External cache failure must be handled.
- In-process caches can create per-replica inconsistency.

#### Optional Anki

Q: What is a key memory downside of in-process caches?
A: Memory is duplicated in every service replica.

</details>

<a id="mem-ref-008"></a>

<details>
<summary><strong>MEM-REF-008. Why should resource cleanup not rely on GC timing?</strong></summary>

#### Short answer

GC reclaims memory eventually; it does not deterministically release external resources.

#### Interview answer

Files, sockets, database connections and native handles should be closed explicitly. GC timing is nondeterministic, and memory pressure may not align with resource pressure. Waiting for GC can exhaust file descriptors, connection pools or native memory.

Use `try-with-resources` and explicit lifecycle management.

#### Deep dive

Cleaners and phantom references are safety nets for special cases, not normal resource management.

#### Production angle

Resource leaks can break services before heap usage looks dangerous.

#### Traps / caveats

- Finalizers are unreliable and deprecated for this purpose.
- Cleaner execution is not prompt.
- Closing wrappers may not close underlying resources if ownership is unclear.

#### Optional Anki

Q: Why is GC timing bad for file/socket cleanup?
A: It is nondeterministic and may run too late.

</details>

<a id="mem-ref-009"></a>

<details>
<summary><strong>MEM-REF-009. Why is try-with-resources preferred for files, sockets and streams?</strong></summary>

#### Short answer

It guarantees `close()` is called at scope exit, including exceptional paths.

#### Interview answer

`try-with-resources` works with `AutoCloseable` and closes resources automatically in reverse order. This makes cleanup explicit, local and exception-safe.

It is the standard pattern for files, sockets, streams, JDBC resources and similar lifecycle-bound objects.

#### Deep dive

Suppressed exceptions preserve information if both the body and close operation throw.

#### Production angle

Correct resource cleanup prevents file descriptor leaks, connection pool exhaustion and native memory/resource pressure.

#### Traps / caveats

- Do not return a stream backed by a closed resource.
- Know who owns and closes the resource.
- Closing a wrapper may close the underlying stream depending on API.

#### Optional Anki

Q: What interface enables try-with-resources?
A: `AutoCloseable`.

</details>

<a id="mem-ref-010"></a>

<details>
<summary><strong>🧠 MEM-REF-010. What is the relationship between `Cleaner`, `PhantomReference` and cleanup?</strong></summary>

#### Short answer

They support cleanup after an object becomes unreachable, but they are nondeterministic safety mechanisms.

#### Interview answer

`PhantomReference` lets code be notified after an object is no longer reachable and before/around reclamation-related cleanup. `Cleaner` is a higher-level API that can run cleanup actions when an object becomes phantom reachable.

They are useful for native resource safety nets, not for timely business resource management.

#### Deep dive

Cleanup actions must not capture the object being cleaned, or they can keep it alive. They also run asynchronously and may be delayed.

#### Production angle

Use explicit close for normal resources; use Cleaner/phantom patterns only as backup for native or library internals.

#### Traps / caveats

- Cleaner is not deterministic.
- Cleanup code can accidentally retain the target object.
- It does not replace `try-with-resources`.

#### Optional Anki

Q: What should Cleaner be treated as?
A: A safety net, not primary resource cleanup.

</details>
