# 13.15. Myths and interview traps

---

<a id="mem-myth-001"></a>

<details>
<summary><strong>MEM-MYTH-001. Is GC a complete protection against memory leaks?</strong></summary>

#### Short answer

No. GC only collects unreachable objects; it cannot collect objects that are still accidentally reachable.

#### Interview answer

Java removes the need for manual `free()`, but it does not remove memory leaks. If unused objects are still referenced by caches, static fields, queues, thread locals or listeners, the collector must keep them.

So Java leaks are usually retention leaks.

#### Deep dive

The leak is not "lost memory"; it is memory that the application still points to even though business logic no longer needs it.

#### Production angle

Heap dump analysis focuses on retaining paths from GC roots to leaked objects.

#### Traps / caveats

- GC cannot know business intent.
- Unbounded caches are common leaks.
- Native memory can leak outside heap too.

#### Optional Anki

Q: Why can Java still leak memory?
A: Unneeded objects can remain reachable.

</details>

<a id="mem-myth-002"></a>

<details>
<summary><strong>MEM-MYTH-002. Does setting a reference to `null` always help GC?</strong></summary>

#### Short answer

No. It helps only if that reference was part of the last reachable path and the object is no longer needed.

#### Interview answer

Setting a local variable to `null` usually does not matter because the variable goes out of scope soon anyway. It can help for long-lived fields, arrays or large temporary objects kept alive longer than necessary.

The real question is whether any other reachable reference still exists.

#### Deep dive

The JIT can also optimize local variable liveness, so manual nulling is rarely needed in ordinary code.

#### Production angle

Prefer narrowing scopes, clearing large collections and designing ownership/lifecycle correctly.

#### Traps / caveats

- Nulling one reference does not break other retaining paths.
- Manual nulling can make code harder to read.
- Clearing a collection may be more relevant than nulling the collection variable.

#### Optional Anki

Q: When does setting a reference to null help?
A: When it removes the last meaningful reachable path earlier than normal scope/lifecycle would.

</details>

<a id="mem-myth-003"></a>

<details>
<summary><strong>MEM-MYTH-003. Does `System.gc()` force garbage collection?</strong></summary>

#### Short answer

No. It requests GC, and the JVM may ignore, delay or handle it according to configuration.

#### Interview answer

`System.gc()` is not a deterministic cleanup command. Depending on JVM and flags, it may trigger a costly collection, do little or be disabled. Application code should not rely on it for correctness or resource cleanup.

The collector is better positioned to decide when to run.

#### Deep dive

Explicit GC can create latency spikes if it triggers Full GC.

#### Production angle

If GC logs show explicit collections, search application and dependency code for `System.gc()`.

#### Traps / caveats

- It does not guarantee all garbage is reclaimed.
- It does not close resources.
- Disabling explicit GC can change behavior of code that relied on it.

#### Optional Anki

Q: What is `System.gc()` best described as?
A: A request to the JVM, not a guarantee.

</details>

<a id="mem-myth-004"></a>

<details>
<summary><strong>🧠 MEM-MYTH-004. Does a local variable always live on the stack?</strong></summary>

#### Short answer

The variable slot may be in a stack frame conceptually, but JIT optimizations can place values in registers or optimize objects away.

#### Interview answer

At the JVM model level, local variables are part of a stack frame. At runtime, the JIT can optimize aggressively: values may be in registers, object allocations may be eliminated, and liveness may be shorter than source-code scope.

For interviews, avoid using this as proof that an object is stack-allocated.

#### Deep dive

Escape analysis and scalar replacement can make some object allocations disappear, but this is not a language guarantee.

#### Production angle

This matters mostly for performance analysis and benchmark interpretation, not ordinary application design.

#### Traps / caveats

- A reference local variable is not the object itself.
- Source scope is not always runtime liveness.
- Microbenchmarks can be invalid if the JIT eliminates work.

#### Optional Anki

Q: Does a local reference mean the object is on the stack?
A: No, it usually references a heap object.

</details>

<a id="mem-myth-005"></a>

<details>
<summary><strong>MEM-MYTH-005. Does a larger heap always improve performance?</strong></summary>

#### Short answer

No. A larger heap can reduce GC frequency but increase footprint, pause impact and incident cost.

#### Interview answer

More heap can help if the service is undersized and collecting too frequently. But it can also make collections process a larger live set, increase memory cost, enlarge heap dumps and delay detection of leaks.

Heap size should match live set and latency goals.

#### Deep dive

The best heap size is workload-specific. Bigger is not automatically faster.

#### Production angle

Measure GC pause distribution, allocation rate, live set and RSS before and after changing heap.

#### Traps / caveats

- Larger heap can hide leaks.
- Larger heap can worsen recovery and dump handling.
- Container memory limits still apply.

#### Optional Anki

Q: Why can a larger heap be bad?
A: It can increase footprint, hide leaks and make incidents heavier.

</details>

<a id="mem-myth-006"></a>

<details>
<summary><strong>MEM-MYTH-006. Is high memory usage always a leak?</strong></summary>

#### Short answer

No. High memory usage can be normal warmup, cache occupancy, batching or traffic-driven state.

#### Interview answer

A leak is unwanted retention that keeps growing or never releases. High memory usage is only suspicious when it does not stabilize, grows after GC or contradicts expected workload behavior.

You need trend and context.

#### Deep dive

Modern services often use memory intentionally for caches, buffers and throughput.

#### Production angle

Correlate memory with traffic, cache metrics, GC, deployment markers and post-GC baselines.

#### Traps / caveats

- Cache warmup can look like a leak.
- Native leaks can occur with stable heap.
- Low memory usage is not automatically efficient.

#### Optional Anki

Q: What distinguishes a leak from high but healthy memory usage?
A: Unbounded or unintended retention over time.

</details>

<a id="mem-myth-007"></a>

<details>
<summary><strong>MEM-MYTH-007. Is G1 or ZGC always the best collector?</strong></summary>

#### Short answer

No. Collector choice depends on workload goals and constraints.

#### Interview answer

G1 is a strong default for many services, but it is not always best. ZGC can improve pause times but may use more CPU. Parallel GC can be better for throughput-focused batch jobs. Shenandoah may be attractive for low-pause workloads where supported.

The correct answer is measured trade-off, not collector branding.

#### Deep dive

Collector defaults and capabilities change with Java version and distribution.

#### Production angle

Choose and validate collectors using production-like load, latency SLOs, CPU limits and memory budgets.

#### Traps / caveats

- Do not switch collectors to hide application memory problems.
- Do not optimize only average latency.
- Old tuning advice may be obsolete.

#### Optional Anki

Q: What decides the best GC collector?
A: Workload measurements and trade-offs.

</details>

<a id="mem-myth-008"></a>

<details>
<summary><strong>MEM-MYTH-008. Can finalizers be used for reliable cleanup?</strong></summary>

#### Short answer

No. Finalizers are unreliable, delayed and should not be used for normal resource cleanup.

#### Interview answer

Finalization depends on GC timing and finalizer execution, so it is not prompt or reliable. It can delay reclamation, create performance problems and introduce security/lifecycle bugs.

Use `try-with-resources`, explicit `close()` and well-defined ownership instead.

#### Deep dive

Cleaner/phantom-reference mechanisms are safer for special fallback cleanup, but they are still not deterministic.

#### Production angle

Resource cleanup bugs can exhaust file descriptors, sockets or native memory long before heap is full.

#### Traps / caveats

- Finalizers are not guaranteed to run promptly.
- Cleanup code can resurrect or retain objects in old patterns.
- GC is not resource lifecycle management.

#### Optional Anki

Q: What should replace finalizers for normal resources?
A: Explicit close, usually with try-with-resources.

</details>

<a id="mem-myth-009"></a>

<details>
<summary><strong>🧠 MEM-MYTH-009. Can a heap dump explain native memory leaks?</strong></summary>

#### Short answer

Usually not fully. A heap dump shows heap objects, not all native allocations.

#### Interview answer

A heap dump may show Java wrappers for direct buffers or objects that own native resources, but it does not show all native memory itself. Native leaks require process metrics, NMT, direct buffer metrics, library-specific metrics or OS/native tools.

If RSS grows while heap is stable, heap dump is not enough.

#### Deep dive

Native allocations can come from direct buffers, JNI libraries, thread stacks, mmap or allocator arenas.

#### Production angle

Use NMT and OS/container evidence before concluding heap is healthy or unhealthy.

#### Traps / caveats

- A normal heap dump does not rule out native leak.
- Direct buffer wrappers may understate native memory.
- OOMKilled can happen without heap OOME.

#### Optional Anki

Q: What should you inspect when RSS grows but heap is stable?
A: Native/off-heap memory with NMT, OS metrics and library metrics.

</details>

<a id="mem-myth-010"></a>

<details>
<summary><strong>MEM-MYTH-010. Should every memory issue be solved by adding more RAM?</strong></summary>

#### Short answer

No. More RAM can be a mitigation, but root cause may be leaks, unbounded data, bad allocation patterns or wrong limits.

#### Interview answer

Adding memory can buy time or handle legitimate growth, but it does not fix unbounded caches, leaks, excessive allocation, direct memory misuse or thread leaks. It can also increase cost and make incidents larger.

A senior engineer separates mitigation from root-cause fix.

#### Deep dive

Sometimes adding memory is correct: the service may simply be underprovisioned for its live set and traffic. But that conclusion should come from evidence.

#### Production angle

Use metrics to decide: live set, allocation rate, RSS, OOM events, cache bounds, queue depth and latency.

#### Traps / caveats

- More memory can delay alerts.
- Bigger heaps make dumps and restarts heavier.
- Cost and density matter in Kubernetes.

#### Optional Anki

Q: When is adding RAM acceptable?
A: As evidence-based capacity increase or temporary mitigation, not as a blind fix.

</details>
