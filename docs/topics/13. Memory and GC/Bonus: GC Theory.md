# Bonus: GC Theory

This note summarizes the Shortcut GC theory article in the repository's interview-prep style. It is meant as a compact theory pass before answering the Memory and GC questions.

## 1. JVM memory areas

The JVM process uses several memory areas. For GC interviews, the most important distinction is between memory that stores objects and memory that stores execution state or JVM metadata.

### Heap

The heap stores Java objects and arrays. It is shared by application threads and is the main area managed by garbage collection.

Modern collectors may divide the heap differently internally, but the mental model is:

- most new objects are allocated in young memory;
- objects that survive long enough may be promoted or treated as old;
- large or long-lived objects can put pressure on old memory;
- heap size is controlled mainly by `-Xms` and `-Xmx`.

### Stack

Each Java thread has its own stack. Stack frames contain method call state, local variables and references to heap objects.

The object itself is usually on the heap. A local variable on the stack may only hold a reference to it. When the method returns, that local reference disappears, but the object is collected only if no other reachable reference still exists.

### Metaspace

Metaspace stores class metadata, such as loaded class information and runtime structures related to classes. It is native memory, not normal Java heap.

Metaspace can grow because of many loaded classes, dynamic proxies, generated bytecode or classloader leaks. A heap dump can show classloader retention paths, but native memory tools and JVM class-loading metrics are often needed too.

## 2. What GC does

Garbage collection automatically reclaims memory for objects that are no longer reachable. It does not collect objects just because the application no longer "logically" needs them.

The collector answers one core question: can this object still be reached from a GC root?

If yes, the object is live. If no, the object is eligible for collection.

Common GC roots include:

- local variables and active stack frames;
- static fields;
- live threads;
- JNI references;
- JVM internal references;
- synchronization and class-loading structures.

GC does not run line by line with the code. Setting a variable to `null` may help only when it removes the last relevant strong reference earlier than it would otherwise disappear.

## 3. Reachability example

```java
class UserService {
    private static final List<User> USERS = new ArrayList<>();

    void register(User user) {
        USERS.add(user);
    }
}
```

Even if a request finishes, a `User` added to the static list remains reachable through a static field, which is a GC root path. The collector must keep it.

That is why Java can have memory leaks without manual `malloc()` and `free()`: reachable-but-unneeded objects are still live from GC's point of view.

## 4. Why not rely on `finalize()`

Finalization is not reliable cleanup. It is delayed, not guaranteed to run promptly, can create performance issues and can even make object lifetime harder to reason about.

Use explicit cleanup:

- `try-with-resources` for files, sockets and streams;
- lifecycle methods for services;
- explicit unregister or cancel operations for listeners and tasks;
- `Cleaner` or phantom-reference patterns only for specialized cases.

## 5. Generational model

The generational hypothesis says most objects die young, while a smaller set lives much longer. Generational collectors exploit this by collecting young memory frequently and old memory less frequently.

Typical terms:

- Eden: where many new objects are allocated.
- Survivor spaces: areas for objects that survive young collections.
- Old generation: where longer-lived objects eventually move.
- Minor GC: usually a young-generation collection.
- Full GC: usually a more expensive collection involving old memory or the whole heap.

Promotion happens when an object survives enough young collections or cannot fit in survivor space. Too much promotion can increase old-generation pressure.

## 6. Basic GC algorithms

Collectors combine several basic techniques.

### Mark

Trace all reachable objects from GC roots and mark them as live.

### Sweep

Reclaim memory occupied by unmarked objects. This can leave fragmented free space.

### Compact

Move live objects together to create larger contiguous free regions. This reduces fragmentation but moving objects requires reference updates and synchronization.

### Copy

Copy live objects from one area to another and then reclaim the old area at once. This works well when most objects are dead, which is common in young memory.

### Concurrent marking

Do part of the marking work while application threads continue running. This reduces pause time but requires barriers and coordination.

## 7. Stop-the-world pauses

Stop-the-world means application threads are paused so the JVM can perform a phase that needs a stable view of the heap or thread state.

Modern collectors try to reduce pause length, but they still have some stop-the-world phases. A low-pause collector is not a zero-pause collector.

In production, watch:

- pause duration distribution, especially p95 and p99;
- GC frequency;
- allocation rate;
- promotion rate;
- old-generation occupancy after GC;
- time to safepoint.

## 8. Collector evolution

### Serial GC

Simple collector using one GC thread. It can be fine for tiny heaps, command-line tools or constrained single-threaded environments.

### Parallel GC

Throughput-oriented collector that uses multiple GC threads. It can be good for batch work but may allow longer pauses.

### CMS

Concurrent Mark Sweep tried to reduce old-generation pauses by doing marking and sweeping concurrently. Its weaknesses included fragmentation, tuning complexity and fallback pauses. Modern JVMs generally moved away from CMS-era advice.

### G1 GC

G1 divides the heap into regions and chooses collection sets based on predicted cost and reclaimable memory. It is a common general-purpose backend baseline because it balances throughput and pause predictability.

### ZGC and Shenandoah

ZGC and Shenandoah target very short pauses by doing more work concurrently and using barriers. They can be useful for latency-sensitive services and large heaps, but they need CPU headroom and production-like validation.

## 9. TLAB

TLAB means Thread-Local Allocation Buffer. It is a small heap allocation area reserved for one thread.

Without TLABs, many threads allocating objects would constantly coordinate on shared heap allocation state. With TLABs, most small allocations are fast pointer bumps inside a thread-local buffer.

TLABs improve allocation throughput, but they do not make allocation free. High allocation rate still creates GC pressure.

## 10. Card Table and Remembered Sets

Generational GC must handle old objects pointing to young objects. During a young collection, the collector cannot simply ignore old memory, because an old object may be the only thing keeping a young object alive.

A Card Table divides part of the heap into coarse cards. When code writes a reference, a write barrier can mark the corresponding card as dirty. During young GC, the collector scans dirty cards instead of the whole old generation.

Remembered Sets are metadata that track references into a region. G1 uses this idea heavily because it collects selected regions, so it needs to know which outside references point into each region.

The benefit is faster targeted collection. The cost is extra memory and CPU for maintaining metadata.

## 11. Java reference types

### Strong reference

Normal Java reference. As long as an object is strongly reachable, it is not collectible.

### SoftReference

May be cleared under memory pressure. It is usually a poor foundation for predictable production caches.

### WeakReference

Does not keep the object alive. Useful for specialized metadata associations, but weakly referenced objects can disappear earlier than business logic expects.

### PhantomReference

Used for post-mortem cleanup patterns after an object is no longer reachable in the normal sense. It is advanced and not a replacement for explicit resource cleanup.

## 12. Typical Java memory leaks

GC prevents leaks only when unused objects become unreachable. Common leak patterns keep objects reachable accidentally.

### Static collections

A static map, list or cache can retain objects forever unless entries are removed or bounded.

### Listener registries

Listeners must be unregistered when their owner is no longer active. Otherwise a long-lived registry can retain subscribers, services, request objects or classloaders.

Weak listeners avoid strong retention but can create another bug: the listener may be collected while the application still expects it to receive events.

### Inner classes and lambdas

Non-static inner classes hold an implicit reference to the outer instance. Lambdas and anonymous classes can capture `this` or large variables. If the callback is stored in a long-lived place, the captured graph stays reachable.

### ThreadLocal

Thread pools reuse threads. If a `ThreadLocal` value is not removed, request-scoped data can remain attached to a worker thread long after the request finishes.

### Unbounded queues and caches

Unbounded data structures turn traffic, slow consumers or high-cardinality keys into memory growth. Use maximum size, maximum weight, TTL, backpressure and metrics.

## 13. Practical diagnostics

Useful first signals:

- exact `OutOfMemoryError` message;
- GC logs, for example `-Xlog:gc*` on modern Java;
- heap dump on OOME, configured with care;
- class histogram;
- Java Flight Recorder;
- Eclipse MAT dominator tree and paths to GC roots;
- Native Memory Tracking for off-heap or native growth.

Heap dumps can contain customer data and are expensive to capture. In production, dump paths, retention, access control and disk capacity must be planned before an incident.

## 14. Interview summary

A strong GC answer usually connects these ideas:

- GC collects unreachable objects, not useless objects.
- Reachability starts from GC roots.
- Generational GC exists because most objects die young.
- Stop-the-world pauses still exist, even in modern collectors.
- Collector choice is a trade-off between latency, throughput, footprint, CPU and JDK support.
- Memory leaks in Java are usually accidental strong references from long-lived structures.
- Production diagnosis needs metrics, logs and retention paths, not guesses.
