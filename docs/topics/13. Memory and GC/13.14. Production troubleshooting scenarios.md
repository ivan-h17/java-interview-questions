# 13.14. Production troubleshooting scenarios

---

<a id="mem-prod-001"></a>

<details>
<summary><strong>MEM-PROD-001. How would you investigate high p99 latency with GC pauses in logs?</strong></summary>

#### Short answer

Correlate GC pauses with latency, then inspect allocation rate, live set, collector behavior and recent workload changes.

#### Interview answer

I would first align timestamps between p99 latency spikes and GC events. Then I would check pause type, duration, heap before/after, allocation rate, old-gen trend and whether traffic or deployment changed. If GC is correlated, I would look for allocation hotspots or retained-memory growth.

I would avoid changing GC flags before understanding the cause.

#### Deep dive

GC may be the cause, a symptom or only correlated. Downstream slowness can increase in-flight objects and trigger more GC.

#### Production angle

Use GC logs, metrics, traces, JFR and deployment markers. Mitigate by scaling, reducing load or rolling back if needed.

#### Traps / caveats

- Average latency can hide p99 impact.
- GC logs alone do not explain allocation source.
- Time to safepoint can inflate pause impact.

#### Optional Anki

Q: What is the first step when GC pauses and latency spikes appear together?
A: Correlate their timestamps and then validate causality with supporting metrics.

</details>

<a id="mem-prod-002"></a>

<details>
<summary><strong>MEM-PROD-002. A service uses 2 GB heap but container RSS reaches 5 GB. What would you check?</strong></summary>

#### Short answer

Check native/off-heap memory: direct buffers, threads, Metaspace, Code Cache, mmap, native libraries and allocator behavior.

#### Interview answer

I would compare heap used/committed with RSS and container limit. If heap is stable, I would inspect direct buffer usage, Netty pools, thread count and stack size, Metaspace, Code Cache, NMT output and memory-mapped files.

I would also check whether the heap is committed larger than used.

#### Deep dive

RSS is process memory, not heap memory. It includes many JVM and native areas.

#### Production angle

If the pod is close to its limit, mitigation may require lowering heap, reducing threads/direct memory, increasing limit or rolling out a fix.

#### Traps / caveats

- Heap dump may look normal.
- `-Xmx` does not cap RSS.
- OOMKilled can happen before Java logs OOME.

#### Optional Anki

Q: What does heap 2 GB and RSS 5 GB suggest?
A: Significant non-heap/native memory usage or committed memory outside used heap.

</details>

<a id="mem-prod-003"></a>

<details>
<summary><strong>MEM-PROD-003. A service crashes with Java heap space after several hours. What data do you collect first?</strong></summary>

#### Short answer

Collect exact error, GC logs, heap metrics timeline, heap dump or histogram if safe, and recent deployment/traffic context.

#### Interview answer

I would capture the exact OOME message, GC logs, heap usage before/after GC, old-gen trend, request traffic, cache/queue metrics and deployment timeline. If safe and configured, collect a heap dump or at least a class histogram before restart.

The goal is to distinguish leak, cache growth, traffic spike or bad sizing.

#### Deep dive

Several hours to failure often suggests slow retention, cache cardinality growth or workload accumulation.

#### Production angle

After mitigation, compare dumps or histograms over time and identify dominant retaining paths.

#### Traps / caveats

- Restarting loses evidence.
- Heap dump may contain sensitive data.
- Increasing heap without analysis may only delay recurrence.

#### Optional Anki

Q: What evidence is most useful for heap OOME?
A: Heap trend, GC logs and retained-object evidence such as heap dump or histogram.

</details>

<a id="mem-prod-004"></a>

<details>
<summary><strong>MEM-PROD-004. A service crashes with Direct buffer memory. What are likely causes?</strong></summary>

#### Short answer

Likely causes are direct buffer leak, Netty buffer misuse, oversized payloads, too low direct memory limit or insufficient container headroom.

#### Interview answer

I would check whether the service uses Netty, NIO, WebClient, gRPC or large file/network buffers. Then I would inspect direct memory metrics, Netty allocator stats, leak detector output, RSS, `MaxDirectMemorySize` and request payload sizes.

The heap may look healthy because direct memory is off-heap.

#### Deep dive

Reference-counted buffer leaks are common when ownership rules are unclear.

#### Production angle

Mitigate by reducing traffic, limiting payloads, fixing buffer release, tuning direct memory or increasing container memory with proper headroom.

#### Traps / caveats

- Heap OOME and direct memory OOME need different evidence.
- Increasing heap can reduce native headroom.
- Pool memory staying high is not automatically a leak.

#### Optional Anki

Q: Which libraries often use direct memory heavily?
A: NIO/Netty-based networking libraries.

</details>

<a id="mem-prod-005"></a>

<details>
<summary><strong>MEM-PROD-005. A service crashes with unable to create new native thread. What are likely causes?</strong></summary>

#### Short answer

Likely causes are too many platform threads, thread leaks, OS/PID limits, large stack size or native memory exhaustion.

#### Interview answer

I would check thread count over time, thread dumps, executor configuration, scheduler behavior, per-request thread creation, `-Xss`, process limits and Kubernetes PID/memory constraints. The issue is usually outside Java heap.

The fix is often bounding or reducing threads, not increasing heap.

#### Deep dive

Thread pools can leak if tasks block forever or code creates new executors repeatedly.

#### Production angle

Monitor thread count and executor queues. Alert before hitting OS thread limits.

#### Traps / caveats

- More heap can make native thread creation worse in a fixed container.
- Thread dumps may fail if the process cannot create helper threads.
- Virtual threads solve different problems and still need bounds.

#### Optional Anki

Q: What is the first metric to check for native thread OOME?
A: Java/native thread count over time.

</details>

<a id="mem-prod-006"></a>

<details>
<summary><strong>MEM-PROD-006. A service was migrated to Kubernetes and started being OOMKilled. What changed?</strong></summary>

#### Short answer

The process now runs under cgroup memory limits, and total RSS matters, not just heap.

#### Interview answer

I would compare old host memory assumptions with pod memory requests/limits and JVM flags. In Kubernetes, if RSS exceeds the memory limit, the process is killed externally. Heap, Metaspace, stacks, direct buffers and native memory all count.

Container CPU limits can also change GC behavior through throttling.

#### Deep dive

Older Java versions or inherited flags may not size heap safely for containers.

#### Production angle

Check pod events, exit code, RSS, heap max, direct memory, thread count, memory limits and heap dump path/storage.

#### Traps / caveats

- `OOMKilled` may leave no Java stack trace.
- Memory request is not a hard limit; memory limit is.
- `-Xmx` equal to pod limit is unsafe.

#### Optional Anki

Q: What memory does Kubernetes enforce?
A: Total container memory, not only Java heap.

</details>

<a id="mem-prod-007"></a>

<details>
<summary><strong>MEM-PROD-007. After enabling a large cache, GC pauses increased. What would you check?</strong></summary>

#### Short answer

Check cache size/weight, entry lifetime, hit rate, eviction, old-gen growth and live set increase.

#### Interview answer

A large cache increases the live set. I would inspect whether it is bounded, whether entries are too large, whether TTL/eviction works and whether old generation grows after GC. I would also check if the cache increases downstream load due to churn or stampede.

The cache may improve latency while hurting GC.

#### Deep dive

Long-lived cache entries make GC more expensive because they must be traced and retained.

#### Production angle

Tune maximum weight/size, TTL, refresh and replica memory budget. Consider external cache if in-process memory is too costly.

#### Traps / caveats

- High hit rate does not prove safe memory behavior.
- TTL alone is not a memory bound.
- Every replica has its own in-process cache.

#### Optional Anki

Q: Why can a cache increase GC pause time?
A: It increases the live set that GC must process.

</details>

<a id="mem-prod-008"></a>

<details>
<summary><strong>🧠 MEM-PROD-008. After switching to ZGC, CPU usage increased or a batch job slowed down. How would you reason about it?</strong></summary>

#### Short answer

Low-pause collectors trade pause time for concurrent CPU overhead, which may hurt throughput-heavy workloads.

#### Interview answer

I would compare before/after CPU, throughput, p99 latency, GC overhead and allocation behavior. ZGC may reduce pauses but use more CPU due to barriers and concurrent work. For a batch job, Parallel GC may be faster if long pauses are acceptable.

This is not automatically a bug.

#### Deep dive

CPU-constrained containers can make concurrent GC compete with application work or fall behind.

#### Production angle

Choose the collector based on workload goals: API tail latency versus batch throughput.

#### Traps / caveats

- Lower pause time is not the same as better throughput.
- Collector changes need production-like benchmarking.
- CPU throttling can distort results.

#### Optional Anki

Q: Why might ZGC slow a batch job?
A: Its low-pause concurrent overhead may reduce raw throughput compared with Parallel GC.

</details>

<a id="mem-prod-009"></a>

<details>
<summary><strong>MEM-PROD-009. A service creates many short-lived DTOs. What GC behavior do you expect?</strong></summary>

#### Short answer

Mostly young-generation allocation and young GCs; it is fine until allocation rate becomes too high.

#### Interview answer

Short-lived DTOs usually die young and are collected efficiently. I would expect young-gen usage to rise and fall, with most objects not promoted. If allocation rate is very high, the service may still spend too much CPU in young GC.

The issue is churn, not retention, unless objects start surviving.

#### Deep dive

JFR or allocation profiling is better than heap dump for short-lived allocation.

#### Production angle

Optimize DTO churn only when metrics show GC CPU or latency impact.

#### Traps / caveats

- A stable heap can still have high allocation cost.
- Logging or async capture can make DTOs live longer.
- Large DTO graphs can become old-gen pressure under concurrency.

#### Optional Anki

Q: What tool is useful for short-lived DTO churn?
A: Allocation profiling or JFR allocation events.

</details>

<a id="mem-prod-010"></a>

<details>
<summary><strong>MEM-PROD-010. A service has old generation steadily increasing after each GC. What does it suggest?</strong></summary>

#### Short answer

It suggests retained objects, cache growth, queue buildup or promotion pressure.

#### Interview answer

A steadily rising old-gen baseline means objects are surviving and accumulating. I would check cache sizes, queues, sessions, static collections, thread locals, active requests and recent changes that increase object lifetime.

If it does not plateau, a leak is likely.

#### Deep dive

Warmup can grow old gen normally. The key is whether it stabilizes under steady workload.

#### Production angle

Use heap dumps/histograms over time to identify growing retained types and owners.

#### Traps / caveats

- One old-gen rise after traffic spike is not proof.
- Promotion pressure can mimic leak symptoms.
- Native memory issues may occur with stable old gen.

#### Optional Anki

Q: What old-gen pattern suggests retention?
A: The post-GC old-gen baseline keeps rising.

</details>

<a id="mem-prod-011"></a>

<details>
<summary><strong>MEM-PROD-011. A heap dump is huge, slow to capture and contains customer data. How do you handle it safely?</strong></summary>

#### Short answer

Protect the service first, then handle the dump as sensitive data with controlled capture, storage and access.

#### Interview answer

If possible, remove one replica from traffic before capture. Ensure enough disk, choose an approved encrypted location and restrict access. If capture is too disruptive, consider class histograms, JFR or sampling first.

Treat the dump as production-sensitive data.

#### Deep dive

Huge dumps can pause the JVM and take a long time to transfer or open. They may contain raw request bodies, tokens and PII.

#### Production angle

Have a predefined runbook, retention policy and secure transfer path.

#### Traps / caveats

- Do not upload dumps to random file shares.
- Do not assume redaction in logs means dump data is safe.
- A failed dump can still consume disk.

#### Optional Anki

Q: How should heap dumps be classified?
A: As sensitive production data.

</details>

<a id="mem-prod-012"></a>

<details>
<summary><strong>MEM-PROD-012. How would you decide whether to increase heap size, reduce allocation rate or switch collector?</strong></summary>

#### Short answer

Use evidence: live set growth points to retention, high churn points to allocation optimization, and pause/SLO issues may justify collector testing.

#### Interview answer

If post-GC live set is near heap limit but legitimate, increasing heap may help. If allocation rate is high but live set is stable, reduce churn or tune young-gen behavior. If pauses violate SLOs after code and sizing are reasonable, test another collector.

Do not treat GC tuning as the first fix for bad memory behavior.

#### Deep dive

Each option has cost: bigger heap increases footprint, code changes take engineering time, low-pause collectors may use more CPU.

#### Production angle

Compare changes through load tests and rollout metrics: latency, CPU, RSS, GC overhead, throughput and OOM risk.

#### Traps / caveats

- Increasing heap hides leaks.
- Switching collector does not reduce live set.
- Optimizing allocation without measuring can waste effort.

#### Optional Anki

Q: What does stable live set plus high GC CPU suggest?
A: Allocation churn may be the problem.

</details>

<a id="mem-prod-013"></a>

<details>
<summary><strong>🧠 MEM-PROD-013. A classloader leak appears after multiple redeployments. How do you find it?</strong></summary>

#### Short answer

Look for old classloaders retained by threads, statics, registries, `ThreadLocal`s or generated classes.

#### Interview answer

I would compare Metaspace and loaded class count across redeployments. Then I would take a heap dump or classloader stats and look for multiple old application classloaders. Paths to GC roots usually reveal retaining threads, statics, listener registries, JDBC drivers or `ThreadLocal` values.

The fix is lifecycle cleanup.

#### Deep dive

Classloader leaks often retain both metadata and heap graphs.

#### Production angle

Validate the fix by redeploying repeatedly in a test environment and watching classloader/Metaspace stabilization.

#### Traps / caveats

- Restarting the whole JVM masks the problem.
- The root can be in a shared library or container.
- Increasing Metaspace delays but does not fix it.

#### Optional Anki

Q: What evidence points to classloader leak?
A: Old application classloaders remain reachable after redeploy.

</details>

<a id="mem-prod-014"></a>

<details>
<summary><strong>🧠 MEM-PROD-014. A `ThreadLocal` leak appears in a thread pool. How do you prevent it?</strong></summary>

#### Short answer

Always remove thread-local values at the end of work and use framework-managed context propagation carefully.

#### Interview answer

Thread pool threads outlive individual requests. If request context is stored in `ThreadLocal` and not removed, it can be seen by later work and retain memory. The standard pattern is set context before work and remove it in `finally`.

For async flows, use explicit context propagation libraries or framework hooks.

#### Deep dive

MDC, security context and tenant context are common leak sources.

#### Production angle

Use filters/interceptors/executor wrappers that guarantee cleanup and tests that verify no context leaks between requests.

#### Traps / caveats

- `InheritableThreadLocal` can make leaks worse.
- Async boundaries can lose cleanup assumptions.
- Values can retain large request graphs.

#### Optional Anki

Q: What is the safest cleanup pattern for `ThreadLocal`?
A: Remove it in `finally` after the work finishes.

</details>
