# 09.06. Generic arrays, varargs, raw types and heap pollution

---

<a id="rg-arr-001"></a>

<details>
<summary><strong>🧠 RG-ARR-001. Why can you not safely create <code>new T[]</code> or <code>List&lt;String&gt;[]</code>?</strong></summary>

#### Short answer

Generic element types are not fully known at runtime, while arrays require a reified runtime component type.

#### Interview answer

Arrays know their component type at runtime, so `String[]` can reject storing an `Integer`. Generic type arguments such as `T` or `List<String>` are erased, so the runtime cannot enforce the real element type for `new T[]` or `new List<String>[]`.

Java disallows these creations because they would be unsound.

#### Deep dive

You can create arrays of raw or unbounded wildcard types in some cases, but assigning them to parameterized array types creates unchecked warnings and heap pollution risk.

#### Production angle

Prefer `List<T>` over generic arrays in application code. If an API requires arrays, pass an array factory or `IntFunction<T[]>`, as many stream APIs do.

#### Traps / caveats

- `new Object[]` cast to `T[]` is usually unsafe.
- Arrays of generic collections are especially error-prone.
- Suppressing warnings does not make the operation safe.

#### Optional Anki

Q: Why is `new T[]` disallowed?
A: `T` is erased, but arrays need a runtime component type.

</details>

<a id="rg-arr-002"></a>

<details>
<summary><strong>RG-ARR-002. How is array covariance different from generic invariance?</strong></summary>

#### Short answer

Arrays are covariant and checked at runtime; generic collections are invariant and checked mostly at compile time.

#### Interview answer

`String[]` is assignable to `Object[]`, so arrays are covariant. But storing a non-string into that array through the `Object[]` reference throws `ArrayStoreException`.

`List<String>` is not assignable to `List<Object>`. Java prevents the unsafe write at compile time instead of allowing it and failing later.

#### Deep dive

This difference exists because arrays are reified: they know their element type at runtime. Generics are erased, so Java relies on compile-time invariance and wildcards.

#### Production angle

Use collections for most generic code. Arrays are fine for low-level APIs and fixed-size data, but mixing arrays and generics often produces warnings and traps.

#### Traps / caveats

- `String` subtype of `Object` does not imply `List<String>` subtype of `List<Object>`.
- Array covariance can fail at runtime.
- Generic invariance can be relaxed safely with wildcards.

#### Optional Anki

Q: Why can arrays throw `ArrayStoreException`?
A: They know their component type at runtime and reject invalid stores.

</details>

<a id="rg-arr-003"></a>

<details>
<summary><strong>RG-ARR-003. What is `ArrayStoreException`, and what does it reveal about arrays?</strong></summary>

#### Short answer

`ArrayStoreException` is thrown when code stores an incompatible value into an array at runtime.

#### Interview answer

For example:

```java
Object[] values = new String[1];
values[0] = 42; // ArrayStoreException
```

The assignment compiles because arrays are covariant, but the runtime array is still a `String[]`, so it rejects the integer.

#### Deep dive

This shows that arrays carry reified component type information at runtime. Generic collections do not enforce element type the same way because type arguments are erased.

#### Production angle

Array covariance is rarely the right abstraction for backend domain collections. Prefer typed collections unless an array is required by an API or performance-sensitive path.

#### Traps / caveats

- The exception may appear far from the assignment that created the covariant reference.
- Generic collections can fail later with `ClassCastException` instead.
- Do not use arrays to bypass generic type design.

#### Optional Anki

Q: What does `ArrayStoreException` demonstrate?
A: Arrays have runtime component type checks.

</details>

<a id="rg-arr-004"></a>

<details>
<summary><strong>🧠 RG-ARR-004. How can generic varargs cause heap pollution?</strong></summary>

#### Short answer

Generic varargs are implemented as arrays, and arrays of non-reifiable generic types can be polluted with values of the wrong type.

#### Interview answer

A varargs parameter like `List<String>... lists` is really an array at runtime. Because generic element types are erased, the array can be treated unsafely as `Object[]` and assigned a `List<Integer>`. Later, code expects strings and may fail with `ClassCastException`.

That is heap pollution: a variable of a parameterized type refers to an object that is not actually safe for that type.

#### Deep dive

The compiler warns because it cannot fully verify safety. The method may still be safe if it only reads from the varargs array and does not expose or modify it unsafely.

#### Production angle

Varargs generic helpers should be small, reviewed and tested. Prefer collections as parameters when that avoids warnings and caller confusion.

#### Traps / caveats

- The warning is not cosmetic.
- Storing into the varargs array is dangerous.
- Returning or exposing the varargs array is dangerous.

#### Optional Anki

Q: Why are generic varargs risky?
A: Varargs use arrays, but generic element types are erased.

</details>

<a id="rg-arr-005"></a>

<details>
<summary><strong>🧠 RG-ARR-005. What is `@SafeVarargs`, and when is it safe to use?</strong></summary>

#### Short answer

`@SafeVarargs` suppresses generic varargs warnings when the method body is known not to perform unsafe operations.

#### Interview answer

Use `@SafeVarargs` only when a generic varargs method does not write unsafe values into the varargs array and does not expose the array where others can corrupt it. Typical safe methods only iterate over the arguments or copy them into a safe collection.

On modern Java, it is allowed on final, static or private methods and constructors because overriding cannot change the safety assumptions. The private-method case was added after the original Java 7 rules.

#### Deep dive

The annotation is a promise by the author. The compiler trusts it more than it proves every operation safe.

#### Production angle

This is common in utility methods and builders. If the safety argument is not obvious, avoid generic varargs and accept a `Collection` instead.

#### Traps / caveats

- Do not annotate just to silence warnings.
- Do not mutate the varargs array with incompatible values.
- Do not return the varargs array.

#### Optional Anki

Q: What does `@SafeVarargs` mean?
A: The author promises the generic varargs body is type-safe.

</details>

<a id="rg-arr-006"></a>

<details>
<summary><strong>RG-ARR-006. Can primitive types be used as generic type arguments, and what boxing traps follow?</strong></summary>

#### Short answer

No. Generic type arguments must be reference types, so primitives use wrappers such as `Integer`.

#### Interview answer

You write `List<Integer>`, not `List<int>`. Java boxes primitive `int` values into `Integer` objects and unboxes them when needed.

This is convenient but can add allocation, null-safety issues and CPU overhead in hot paths.

#### Deep dive

Autoboxing can also change behavior. Unboxing a `null` `Integer` throws `NullPointerException`, and comparing boxed values with `==` checks references except for some cached values.

#### Production angle

In ordinary backend code this is fine. In high-throughput aggregation, parsing or metrics code, boxing overhead can become visible in profiles.

#### Traps / caveats

- `List<Integer>` can contain `null`.
- `Integer` comparison with `==` is a common bug.
- Boxing can create large numbers of short-lived objects.

#### Optional Anki

Q: Why can you write `List<Integer>` but not `List<int>`?
A: Java generics require reference type arguments.

</details>

<a id="rg-arr-007"></a>

<details>
<summary><strong>RG-ARR-007. When should you prefer primitive-specialized APIs such as `IntStream`?</strong></summary>

#### Short answer

Use primitive-specialized APIs when profiling or code shape shows boxing overhead matters.

#### Interview answer

`IntStream`, `LongStream` and `DoubleStream` avoid boxing for common numeric pipelines. They are useful for sums, averages, ranges and tight numeric loops.

For normal business lists, readability may matter more than avoiding every boxed value. Use primitive APIs when they make code both clearer and cheaper.

#### Deep dive

Primitive streams have specialized operations such as `sum()`, `average()` and `summaryStatistics()`. They are not a universal replacement for object streams because they support only primitive values.

#### Production angle

Use profiling data. If allocation flame graphs show millions of boxed numbers, primitive streams or specialized collections may be justified.

#### Traps / caveats

- Primitive streams do not support arbitrary object payloads.
- Streams are not always faster than loops.
- Avoid premature optimization in database-bound request paths.

#### Optional Anki

Q: Main benefit of `IntStream` over `Stream<Integer>`?
A: Avoiding boxing for integer values.

</details>

<a id="rg-arr-008"></a>

<details>
<summary><strong>RG-ARR-008. What are raw types, and why should they be avoided?</strong></summary>

#### Short answer

Raw types are generic types used without type arguments, such as `List` instead of `List<String>`.

#### Interview answer

Raw types bypass generic type checking. A raw `List` can accept strings, integers and any other object, so errors may appear much later as `ClassCastException`.

They exist mostly for backward compatibility with pre-generics Java and legacy libraries.

#### Deep dive

Using raw types also spreads unchecked warnings. Once a raw collection crosses an API boundary, the compiler cannot prove what it contains.

#### Production angle

Avoid raw types in new code. They weaken contracts and make bugs appear far from the source of pollution.

#### Traps / caveats

- `List<?>` is safer than raw `List` for unknown element type.
- Suppressing raw warnings globally hides real bugs.
- Some framework APIs may still expose raw types; isolate them.

#### Optional Anki

Q: What is a raw type?
A: A generic type used without type arguments.

</details>

<a id="rg-arr-009"></a>

<details>
<summary><strong>RG-ARR-009. When do raw types still appear in legacy code, and how should you migrate them?</strong></summary>

#### Short answer

They appear around old APIs, reflection, legacy collections and unchecked framework boundaries; migrate by adding precise types at the boundary.

#### Interview answer

Raw types often appear in old Java code, old libraries, reflection-heavy code, generic registries and framework callbacks. Do not blindly cast them everywhere. Find the boundary, validate or narrow the data once, then expose a typed API internally.

For example, convert a raw `List` to `List<UserDto>` after checking or deserializing elements.

#### Deep dive

The migration goal is to localize unsafety. Keep unchecked casts in small methods with comments explaining the invariant.

#### Production angle

This reduces late `ClassCastException` failures and lets modern code regain compiler protection.

#### Traps / caveats

- Do not add `@SuppressWarnings` over whole classes.
- Do not assume old data is clean.
- Add tests around migration boundaries.

#### Optional Anki

Q: How should raw-type migration be handled?
A: Add precise types at boundaries and localize unchecked casts.

</details>

<details>
<summary><strong>RG-ARR-010. What is heap pollution, and how can you localize unsafe generic casts?</strong></summary>

#### Short answer

Heap pollution occurs when a parameterized variable refers to an object that violates its declared type.

#### Interview answer

For example, a `List<String>` reference polluted with an integer will compile in some raw/unchecked path but fail later when code reads a string. The fix is to prevent raw writes, validate uncertain data and keep unchecked casts in one small boundary method.

If a cast is unavoidable, document why it is safe and test the boundary.

#### Deep dive

Heap pollution often comes from raw types, generic arrays, generic varargs, unchecked casts and reflection.

#### Production angle

Localizing unsafe casts makes production failures easier to diagnose. Instead of random `ClassCastException` in business code, invalid data fails near the integration boundary.

#### Traps / caveats

- `@SuppressWarnings("unchecked")` suppresses compiler feedback only.
- Runtime validation may be necessary for untrusted input.
- A generic wrapper does not guarantee nested data is valid after deserialization.

#### Optional Anki

Q: What is heap pollution?
A: A parameterized variable refers to data that violates its declared type.

</details>

<a id="rg-arr-011"></a>

<details>
<summary><strong>RG-ARR-011. Why are unchecked generic warnings important?</strong></summary>

#### Short answer

They mark places where the compiler cannot prove generic type safety.

#### Interview answer

An unchecked warning means Java accepted code that may be unsafe because of erasure, raw types or casts. It is not automatically a bug, but it is a place where a `ClassCastException` or heap pollution can originate.

Senior code should either remove the warning or isolate and justify it.

#### Deep dive

Unchecked warnings often appear with deserialization, reflection and legacy APIs. They are acceptable only when the boundary is controlled and the invariant is clear.

#### Production angle

Warnings ignored during development become runtime incidents later. Treat them as design feedback, especially in shared libraries and framework glue.

#### Traps / caveats

- Suppressing a warning does not validate data.
- A broad suppression can hide future unrelated warnings.
- Prefer local suppression on the smallest possible statement or method.

#### Optional Anki

Q: What does an unchecked warning mean?
A: The compiler cannot prove generic type safety.

</details>

<a id="rg-arr-012"></a>

<details>
<summary><strong>🧠 RG-ARR-012. Why is `new T()` not allowed, and what alternatives exist?</strong></summary>

#### Short answer

`T` is erased at runtime, and Java does not know which constructor to call.

#### Interview answer

A generic method or class cannot write `new T()` because the actual type argument is not available as a constructible runtime class. Even if it were, Java would not know whether the type has an accessible no-arg constructor.

Common alternatives are passing `Supplier<T>`, `Class<T>` for reflective construction, or a factory interface.

#### Deep dive

`Supplier<T>` is usually cleaner because it leaves construction policy with the caller. `Class<T>` reflection can work but introduces checked exceptions, access issues and weaker compile-time guarantees.

#### Production angle

Prefer explicit factories in backend code. They are easier to test, work with dependency injection and avoid reflection surprises.

#### Traps / caveats

- Reflection may fail because of access, modules or missing constructors.
- `Class<T>` is insufficient for nested generic types such as `List<UserDto>`.
- Do not hide dependency creation inside generic utilities.

#### Optional Anki

Q: Preferred alternative to `new T()`?
A: Pass a `Supplier<T>` or factory.

</details>
