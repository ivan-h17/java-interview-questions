# 09.03. Records in backend APIs and frameworks

---

<a id="rg-be-001"></a>

<details>
<summary><strong>RG-BE-001. Where are records useful in Java backend applications?</strong></summary>

#### Short answer

Records are useful for DTOs, commands, events, projections, response models, value objects and compound keys.

#### Interview answer

In backend services, records fit places where the data shape is explicit and mostly immutable: REST request and response DTOs, internal command objects, Kafka payloads, query projections, jOOQ rows, cache keys and small value objects.

They are less suitable for ORM entities, long-lived mutable workflows and models that need hidden representation.

#### Deep dive

Records work best when their components are the contract. If the team would be comfortable documenting the fields in the type declaration, a record is often a good fit.

#### Production angle

Records reduce boilerplate and accidental setter-based mutation. They also make DTO construction easier to reason about in tests and mapping code.

#### Traps / caveats

- Framework compatibility still matters.
- Component names become part of serialization/deserialization behavior.
- Generated `toString()` can leak sensitive fields.

#### Optional Anki

Q: Common backend use for records?
A: DTOs, projections, events, commands, value objects and compound keys.

</details>

<a id="rg-be-002"></a>

<details>
<summary><strong>RG-BE-002. Are records good candidates for request and response DTOs?</strong></summary>

#### Short answer

Yes, often. Records are good DTOs when the API shape is stable and constructor-based binding is supported.

#### Interview answer

Records are concise and immutable-ish, so they work well for request and response DTOs in modern Spring/Jackson applications. They make required fields visible and remove setter-heavy mutable DTOs.

But DTOs are API contracts. Adding, removing or renaming a record component can break clients, tests, serialization and deserialization.

#### Deep dive

For request DTOs, think about validation, missing fields, defaults, null handling and backward compatibility. For response DTOs, think about field names, generated `toString()` and whether the record exposes internal domain structure.

#### Production angle

Records are especially useful for internal APIs and stable public API versions. For rapidly evolving external contracts, explicit versioned DTOs may be safer.

#### Traps / caveats

- Records do not have setters by default.
- Adding a component changes the canonical constructor.
- Optional fields require an intentional null/default policy.

#### Optional Anki

Q: Why are records attractive for DTOs?
A: They make the DTO shape explicit and reduce mutable boilerplate.

</details>

<a id="rg-be-003"></a>

<details>
<summary><strong>RG-BE-003. How do records work with Jackson serialization and deserialization?</strong></summary>

#### Short answer

Modern Jackson can serialize record accessors and deserialize records through their canonical constructor using component names.

#### Interview answer

Jackson treats record components as properties. For serialization, it calls accessors such as `name()`. For deserialization, it maps JSON properties to the record canonical constructor parameters.

This works well when JSON field names match component names and the application uses a Jackson version with record support.

#### Deep dive

Annotations such as `@JsonProperty`, `@JsonFormat` and validation annotations may be placed on components depending on the intended target. Constructor-based creation means missing, unknown or `null` values should be tested explicitly.

#### Production angle

Records can simplify API DTOs, but compatibility depends on Jackson version, naming strategy, modules such as Java Time support and configuration for unknown fields or coercions.

#### Traps / caveats

- Missing JSON fields may become `null` or default primitive values depending on type/configuration.
- Component renames break JSON binding.
- Generic records may need extra type information during deserialization.

#### Optional Anki

Q: How does Jackson deserialize a record?
A: By mapping JSON properties to the canonical constructor parameters.

</details>

<a id="rg-be-004"></a>

<details>
<summary><strong>RG-BE-004. What can break when deserializing JSON into records?</strong></summary>

#### Short answer

Breakage usually comes from missing fields, renamed components, `null`s, unknown properties, type coercion, generic type erasure or unsupported modules.

#### Interview answer

Records use constructor-based deserialization, so every component value must be resolved somehow. If JSON omits a required field, sends `null`, uses a different name or changes shape, construction may fail or create an invalid object.

Generic records add another issue: runtime type information can be lost unless the caller provides a full generic type token.

#### Deep dive

The exact behavior depends on Jackson configuration. Unknown properties, coercions from strings to numbers, enum handling and Java Time support should be deliberately configured and tested.

#### Production angle

API compatibility tests should include missing fields, extra fields, `null` values, unknown enums and older/newer payload examples.

#### Traps / caveats

- Constructor validation may produce a server error unless mapped to a client-friendly response.
- Primitive components cannot represent missing values well.
- Generic payloads often deserialize to `LinkedHashMap` without type metadata.

#### Optional Anki

Q: Why can generic JSON records deserialize incorrectly?
A: Type erasure can hide the nested target type unless a full type token is provided.

</details>

<a id="rg-be-005"></a>

<details>
<summary><strong>RG-BE-005. How do validation annotations work on record components?</strong></summary>

#### Short answer

Bean Validation annotations can be placed on record components and are used by frameworks that inspect constructor parameters, accessors or fields.

#### Interview answer

In Spring MVC, a record request DTO can use annotations such as `@NotNull`, `@Email`, `@Size` or `@Valid` on components. When the controller parameter is annotated with `@Valid`, validation runs after binding.

For nested components, `@Valid` is still needed to cascade validation into nested objects or collections.

#### Deep dive

Annotation target matters. Some annotations can apply to fields, methods, parameters or record components. Most common Bean Validation annotations work well, but custom annotations should declare appropriate targets.

#### Production angle

Validation should produce clear 400 responses for invalid client input. Constructor validation and Bean Validation can coexist, but exception mapping must be consistent.

#### Traps / caveats

- `@NotNull` does not validate blank strings.
- `@Valid` is needed for nested validation.
- Constructor-thrown exceptions may bypass normal validation error formatting.

#### Optional Anki

Q: What enables nested validation in record DTOs?
A: `@Valid` on the nested component.

</details>

<a id="rg-be-006"></a>

<details>
<summary><strong>RG-BE-006. Why are records usually not a good fit for Hibernate entities?</strong></summary>

#### Short answer

Hibernate entities usually need identity, lifecycle, mutation, no-arg construction and proxying, while records are final value-like classes.

#### Interview answer

Records are final and their state is defined by constructor components. Hibernate entities often need a no-arg constructor, mutable fields for dirty checking, lazy-loading proxies and identity rules based on database or business identity.

That makes records a poor match for normal entity modeling.

#### Deep dive

Records can still be useful around Hibernate: DTO projections, query result objects, immutable snapshots or external API models. The entity itself should usually remain a class designed for persistence lifecycle.

#### Production angle

Forcing records into entity roles can break lazy loading, dirty checking, equality, generated IDs and framework tooling.

#### Traps / caveats

- A JPA entity is not just a DTO for a table row.
- Generated record equality often conflicts with entity equality.
- Lazy proxies generally do not work with final record classes.

#### Optional Anki

Q: Where do records fit with JPA?
A: Projections and DTOs, not usually entities.

</details>

<a id="rg-be-007"></a>

<details>
<summary><strong>RG-BE-007. How can records be used for JPA projections and query results?</strong></summary>

#### Short answer

Records can represent immutable query result DTOs populated from selected columns or constructor expressions.

#### Interview answer

Instead of loading full entities, a query can select only the fields needed for a view and map them into a record such as `record OrderSummary(long id, BigDecimal total)`.

This is useful for read endpoints, reports and list views where the result is not meant to be managed by the persistence context.

#### Deep dive

Spring Data JPA and JPQL constructor expressions can use DTO-style projections. Native queries may require explicit mapping depending on the framework and result shape.

#### Production angle

Projection records reduce over-fetching, avoid lazy-loading surprises and make read models explicit. They also separate API/read concerns from entity internals.

#### Traps / caveats

- Projection field order and names must match the mapping strategy.
- Projections are not managed entities.
- Complex projections can hide inefficient queries if not checked with SQL logs or plans.

#### Optional Anki

Q: Why use records for JPA projections?
A: To return immutable selected query results without loading full entities.

</details>

<a id="rg-be-008"></a>

<details>
<summary><strong>RG-BE-008. How do records interact with MapStruct and other mappers?</strong></summary>

#### Short answer

Mappers can create records through their canonical constructor when source properties match record components.

#### Interview answer

Records are constructor-based targets. A mapper such as MapStruct can map source properties to the record constructor instead of calling setters.

This works well for DTOs because the target is complete after construction. It also exposes missing mappings early when a new component is added.

#### Deep dive

Mapping libraries need to understand component names and constructor parameters. Custom mappings are needed when names differ, values are computed, nested objects need conversion or defaults are required.

#### Production angle

Record mapping reduces partially initialized DTOs and setter mistakes. Compile-time mapper errors are useful during API evolution.

#### Traps / caveats

- Adding a component may break generated mappers until mapping is updated.
- Avoid hiding domain decisions inside generic mappers.
- Be explicit about null mapping and default values.

#### Optional Anki

Q: How are records usually mapped as targets?
A: Through their canonical constructor.

</details>

<a id="rg-be-009"></a>

<details>
<summary><strong>RG-BE-009. How do records affect REST API backward compatibility?</strong></summary>

#### Short answer

Record components often map directly to JSON fields, so changing components can change the external contract.

#### Interview answer

If a record is used as a REST DTO, adding, removing or renaming a component may change JSON shape and constructor expectations. Clients may fail if a required response field disappears or the server rejects older requests that do not send a new required field.

Records make these changes visible in code, but they do not make them automatically compatible.

#### Deep dive

Backward-compatible evolution usually means additive optional response fields, tolerant request parsing, default values, versioned DTOs or endpoint versioning when the contract changes materially.

#### Production angle

Use contract tests and sample payloads from old clients. Do not rely only on Java compilation to prove API compatibility.

#### Traps / caveats

- Adding a primitive component can be awkward because missing values cannot be `null`.
- Renaming a component can rename JSON unless annotated.
- Internal record changes should not leak into public API changes accidentally.

#### Optional Anki

Q: Why can changing a record DTO break clients?
A: Components often become serialized fields and constructor parameters.

</details>

<a id="rg-be-010"></a>

<details>
<summary><strong>RG-BE-010. Can records be used as Kafka or message payloads, and what are the schema-evolution concerns?</strong></summary>

#### Short answer

Yes, records can be message payloads, but schema evolution, defaults, nullability and versioning must be designed explicitly.

#### Interview answer

Records are good immutable message shapes: `OrderCreated`, `PaymentFailed`, `UserRegistered`. They make event data explicit and reduce accidental mutation after creation.

The risk is that message contracts live longer than code deployments. Consumers may receive old or new payload versions, so adding/removing/renaming components must be compatible with the serialization format and consumer expectations.

#### Deep dive

With JSON messages, test unknown fields, missing fields and `null`s. With Avro/Protobuf-like schemas, follow schema registry compatibility rules and provide defaults where needed.

#### Production angle

Events should be versioned as public contracts. Records help model them, but they do not replace compatibility testing, consumer-driven contracts or replay testing.

#### Traps / caveats

- Do not expose internal entity records directly as events.
- Generated `toString()` may log sensitive payload fields.
- Generic event wrappers can lose type information during deserialization.

#### Optional Anki

Q: Main concern for record message payloads?
A: Schema evolution across independently deployed producers and consumers.

</details>

<a id="rg-be-011"></a>

<details>
<summary><strong>RG-BE-011. How should records model optional or nullable fields in API contracts?</strong></summary>

#### Short answer

Use a clear null/default/optional-field policy; do not add `Optional` components blindly.

#### Interview answer

For API DTOs, a missing field, explicit `null` and a real value may have different meanings. Records force you to model that choice in the constructor and component types.

For responses, nullable fields may be acceptable if documented. For requests, validation groups, separate DTOs or explicit patch models are often clearer than many nullable components.

#### Deep dive

Using `Optional` as a record component is controversial because many serializers, validators and JavaBean-style tools handle plain nullable fields more naturally. `Optional` is strongest as a return type, not as stored state.

#### Production angle

This matters for partial updates, backward compatibility and client SDKs. Ambiguous null handling causes data loss and hard-to-debug API behavior.

#### Traps / caveats

- Primitive components cannot represent absent values.
- `Optional` fields may serialize awkwardly.
- Do not conflate missing and explicitly null in PATCH-like APIs.

#### Optional Anki

Q: Why are nullable record API fields tricky?
A: Missing, null and present values may mean different things.

</details>

<a id="rg-be-012"></a>

<details>
<summary><strong>RG-BE-012. What should you consider before exposing records in a public library or external API?</strong></summary>

#### Short answer

Expose records only when you are willing to make their component names, types and value semantics part of the public contract.

#### Interview answer

A public record is concise but commits you to its component shape. Clients may construct it, deconstruct it, serialize it or rely on generated equality and accessors.

If you need freedom to change internals, hide representation, add derived state or preserve binary/source compatibility more carefully, a regular class may be safer.

#### Deep dive

Record component changes can affect constructors, accessors, serialization, pattern matching and documentation. For libraries supporting older Java baselines, records may not be available.

#### Production angle

For external APIs and shared libraries, compatibility matters more than local boilerplate reduction. Use records where stable value semantics are exactly the intended API.

#### Traps / caveats

- Java baseline requirements can exclude records.
- Component names are not private implementation details.
- Generated `toString()` and equality are public behavior.

#### Optional Anki

Q: What do you commit to when publishing a record API?
A: Component names, types and value-based behavior.

</details>
