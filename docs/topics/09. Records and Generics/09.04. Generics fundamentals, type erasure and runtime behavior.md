# 09.04. Generics fundamentals, type erasure and runtime behavior

---

<a id="rg-gen-001"></a>

<details>
<summary><strong>RG-GEN-001. What are generics in Java, and why were they added?</strong></summary>

#### Short answer

Generics let classes, interfaces and methods work with types as parameters while preserving compile-time type safety.

#### Interview answer

Generics were added so APIs such as collections can express what type they contain. Instead of a raw `List` that accepts anything and requires casts, `List<String>` says the list should contain strings and lets the compiler catch many mistakes.

This improves safety, readability and API contracts without requiring separate collection classes for every element type.

#### Deep dive

Java generics are mostly a compile-time feature implemented with type erasure. The compiler checks type constraints and inserts casts where needed, but most generic type parameters are not reified at runtime.

#### Production angle

Generics make repository APIs, mappers, DTO wrappers, collections and service abstractions safer. They prevent many `ClassCastException` bugs from escaping into production.

#### Traps / caveats

- Generics do not guarantee runtime element type checks.
- Raw types bypass compile-time safety.
- Overly complex generic signatures can harm maintainability.

#### Optional Anki

Q: What is the main benefit of Java generics?
A: Compile-time type safety for reusable typed APIs.

</details>

<a id="rg-gen-002"></a>

<details>
<summary><strong>RG-GEN-002. What is the difference between a type parameter and a type argument?</strong></summary>

#### Short answer

A type parameter is the variable declared by a generic type or method; a type argument is the actual type supplied by the caller.

#### Interview answer

In `class Box<T>`, `T` is a type parameter. In `Box<String>`, `String` is a type argument. The parameter is part of the generic declaration; the argument is used when the generic type is instantiated or referenced.

This distinction helps explain generic APIs clearly.

#### Deep dive

Type parameters can have bounds, such as `<T extends Number>`. Type arguments must satisfy those bounds, so `Box<Integer>` might be valid while `Box<String>` is not for a numeric box.

#### Production angle

Clear type parameters make APIs easier to read. Use conventional names such as `T`, `E`, `K`, `V` and `R` for simple cases, and meaningful names when the role is domain-specific.

#### Traps / caveats

- Do not use generic letters when a domain type would be clearer.
- Type arguments are checked at compile time but usually erased at runtime.
- A wildcard such as `? extends Number` is a type argument too.

#### Optional Anki

Q: In `Map<K,V>`, what are `K` and `V`?
A: Type parameters.

</details>

<a id="rg-gen-003"></a>

<details>
<summary><strong>RG-GEN-003. What are generic classes, interfaces, methods and constructors?</strong></summary>

#### Short answer

They are declarations that introduce type parameters at the class, interface, method or constructor level.

#### Interview answer

A generic class or interface declares type parameters on the type, such as `class Repository<T>` or `interface Mapper<S, T>`. A generic method declares its own type parameters before the return type, such as `<T> T require(T value)`.

Constructors can also declare their own type parameters, though this is less common.

#### Deep dive

Method-level type parameters are independent from class-level type parameters. Static methods cannot use a class-level type parameter because there is no instance type, but static methods can declare their own generic parameters.

#### Production angle

Generic methods are useful for helper APIs, mapping utilities, type-safe factories and repository abstractions. Keep signatures simple enough that callers can understand errors from the compiler.

#### Traps / caveats

- Class-level `T` is not available from static fields.
- Method-level type parameters can shadow class-level names.
- Generic constructors are rare and can confuse readers.

#### Optional Anki

Q: Where is a generic method type parameter declared?
A: Before the method return type.

</details>

<a id="rg-gen-004"></a>

<details>
<summary><strong>RG-GEN-004. How do generics improve API contracts?</strong></summary>

#### Short answer

Generics make accepted and returned types explicit, so callers and implementers get compile-time checks.

#### Interview answer

Without generics, an API often accepts or returns `Object`, forcing callers to cast and discover mistakes at runtime. With generics, `Repository<User>` communicates that `findById()` returns a `User`, not just any object.

This makes APIs self-documenting and lets the compiler enforce consistency across layers.

#### Deep dive

Generics can encode relationships between inputs and outputs, such as `Mapper<S, T>` or `<T> T read(String json, Class<T> type)`. This is stronger than documentation because incorrect uses may fail compilation.

#### Production angle

Good generic contracts reduce runtime casting failures and clarify shared abstractions such as repositories, HTTP clients, event handlers and serializers.

#### Traps / caveats

- Generic contracts can be too abstract and hide domain intent.
- `Map<String, Object>` often weakens the contract.
- Runtime deserialization may still need explicit type metadata.

#### Optional Anki

Q: How do generics help API design?
A: They express type relationships that the compiler can check.

</details>

<a id="rg-gen-005"></a>

<details>
<summary><strong>RG-GEN-005. What are type inference and the diamond operator?</strong></summary>

#### Short answer

Type inference lets the compiler infer generic types, and the diamond operator `<>` avoids repeating type arguments in constructors.

#### Interview answer

Java can infer many generic types from assignment targets, method arguments and return contexts. For example, `List<String> names = new ArrayList<>();` uses the diamond operator to infer `String`.

Generic method calls can also infer type arguments, so you usually write `List.of("a")` instead of explicitly specifying the type.

#### Deep dive

Type inference improves readability but is limited by context. If the compiler cannot infer a type, adding an explicit type witness or intermediate variable can clarify the code.

#### Production angle

Inference keeps code less noisy, especially in collection and mapper-heavy code. But ambiguous inference errors can make overly generic APIs painful to use.

#### Traps / caveats

- Inference can choose a broader type than expected.
- Overloaded generic methods can create confusing compiler errors.
- Do not rely on inference when explicit types improve readability.

#### Optional Anki

Q: What does `new ArrayList<>()` use?
A: The diamond operator with compiler type inference.

</details>

<a id="rg-gen-006"></a>

<details>
<summary><strong>RG-GEN-006. What is type erasure?</strong></summary>

#### Short answer

Type erasure is the compilation strategy where generic type parameters are mostly removed and replaced with bounds or `Object`.

#### Interview answer

Java generics are checked by the compiler, then most generic type information is erased in bytecode. `List<String>` and `List<Integer>` are both ordinary `List` objects at runtime.

The compiler inserts casts where needed and may generate bridge methods to preserve polymorphism.

#### Deep dive

An unbounded `T` erases to `Object`. A bounded `T extends Number` erases to `Number`. This is why some generic operations, such as `new T()` or `instanceof List<String>`, are not possible.

#### Production angle

Erasure explains many framework issues: JSON clients need `TypeReference`, generic bean resolution needs metadata, and unchecked casts must be isolated.

#### Traps / caveats

- Compile-time generic safety is not the same as runtime reification.
- Reflection can see some signature metadata, but object instances do not carry full generic arguments.
- Raw types defeat compiler checks.

#### Optional Anki

Q: What does unbounded `T` erase to?
A: `Object`.

</details>

<a id="rg-gen-007"></a>

<details>
<summary><strong>RG-GEN-007. Why does Java use type erasure?</strong></summary>

#### Short answer

Java uses erasure mainly to preserve compatibility with pre-generics Java libraries and bytecode.

#### Interview answer

Generics were added after Java already had a large ecosystem of raw collections and libraries. Erasure allowed generic code to interoperate with old bytecode and APIs without creating a separate runtime class for each type argument.

This compatibility came with trade-offs: less runtime type information and some unchecked warnings.

#### Deep dive

Erasure keeps one compiled representation of `List`, not separate runtime types for `List<String>` and `List<Integer>`. The compiler enforces type rules before runtime where possible.

#### Production angle

The legacy compatibility is useful, but backend developers must understand where runtime type information is still needed: serializers, dependency injection, reflection-heavy frameworks and generic HTTP clients.

#### Traps / caveats

- Erasure is not a bug; it is a design trade-off.
- It does not mean generics are useless.
- Runtime type loss must be handled explicitly in some framework code.

#### Optional Anki

Q: Main reason Java generics use erasure?
A: Backward compatibility with pre-generics Java.

</details>

<a id="rg-gen-008"></a>

<details>
<summary><strong>RG-GEN-008. What happens to unbounded and bounded type parameters during erasure?</strong></summary>

#### Short answer

Unbounded parameters erase to `Object`; bounded parameters erase to their leftmost bound.

#### Interview answer

For `<T>`, the compiler generally treats `T` as `Object` after erasure. For `<T extends Number>`, `T` erases to `Number`. For multiple bounds such as `<T extends Base & Closeable>`, the erasure is the first bound.

The compiler inserts casts at use sites where the source code expects a more specific type.

#### Deep dive

The leftmost-bound rule is why multiple bound ordering matters: if there is a class bound, it must appear before interface bounds.

#### Production angle

This matters when reading bytecode, debugging bridge methods, designing bounded APIs or interpreting reflection output.

#### Traps / caveats

- Bounds still matter at compile time even though erased code is less specific.
- Multiple bounds affect erased signatures.
- Changing bounds can affect binary compatibility.

#### Optional Anki

Q: What does `<T extends Number>` erase to?
A: `Number`.

</details>

<a id="rg-gen-009"></a>

<details>
<summary><strong>RG-GEN-009. Why do <code>List&lt;String&gt;</code> and <code>List&lt;Integer&gt;</code> have the same runtime class?</strong></summary>

#### Short answer

Because Java generics are erased, both are represented by the same runtime `List` type.

#### Interview answer

At compile time, the compiler checks that `List<String>` is used with strings and `List<Integer>` with integers. At runtime, both are just instances of the same collection implementation, such as `ArrayList`.

The type argument exists mainly in compile-time checks and some class-file signature metadata, not as a per-object runtime type.

#### Deep dive

This is why `new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()` is true.

#### Production angle

This explains why deserializing `List<UserDto>` requires extra type information. The runtime cannot infer the element type from the raw list object.

#### Traps / caveats

- The collection object does not enforce element types at runtime.
- Raw writes can pollute a generic collection.
- Reflection may inspect declared generic signatures, not arbitrary object contents.

#### Optional Anki

Q: Why do different `List<T>` arguments share one runtime class?
A: Type erasure.

</details>

<a id="rg-gen-010"></a>

<details>
<summary><strong>RG-GEN-010. Why are <code>List&lt;String&gt;.class</code> and <code>instanceof List&lt;String&gt;</code> not valid?</strong></summary>

#### Short answer

Because `List<String>` is not reified as a distinct runtime class.

#### Interview answer

Java can test `obj instanceof List<?>` because `List` is a runtime type. It cannot test `obj instanceof List<String>` because the element type `String` is erased and not available as part of the object type.

For the same reason, there is no class literal for `List<String>`; only `List.class` exists.

#### Deep dive

Some generic types are called non-reifiable because their full type information is not available at runtime. Parameterized types such as `List<String>` fall into this category.

#### Production angle

When runtime type checks are needed, pass explicit metadata such as `Class<T>`, Jackson `TypeReference<T>` or Spring `ParameterizedTypeReference<T>`.

#### Traps / caveats

- `instanceof List<?>` only checks that it is a list, not its element type.
- Checking every element manually is sometimes necessary for untrusted raw data.
- Type tokens solve metadata capture, not arbitrary data validation.

#### Optional Anki

Q: Why is `instanceof List<String>` invalid?
A: `String` is not reified in the runtime list type.

</details>

<a id="rg-gen-011"></a>

<details>
<summary><strong>RG-GEN-011. What generic type information is still available through reflection?</strong></summary>

#### Short answer

Reflection can often read generic signatures declared on fields, methods, parameters, superclasses and interfaces.

#### Interview answer

Although object instances do not carry full generic arguments, class files can store generic signature metadata. Reflection can inspect a field declared as `List<UserDto>`, a method return type, a generic superclass or implemented interface.

This is how many frameworks recover useful generic information from declarations.

#### Deep dive

Reflection APIs may return `ParameterizedType`, `TypeVariable`, `WildcardType` or `GenericArrayType`. This metadata describes declarations, not necessarily the runtime contents of an object.

#### Production angle

Frameworks such as Jackson and Spring use declared generic signatures for binding, dependency injection and HTTP client response types.

#### Traps / caveats

- Local variable generic information is generally not available in the same way.
- Runtime objects still do not prove their element contents.
- Raw declarations lose useful metadata.

#### Optional Anki

Q: Where can reflection see generic metadata?
A: In declared signatures such as fields, methods, superclasses and interfaces.

</details>

<a id="rg-gen-012"></a>

<details>
<summary><strong>RG-GEN-012. How do frameworks preserve generic type information with type tokens?</strong></summary>

#### Short answer

They capture a generic type in a subclass or object that retains the declared generic signature.

#### Interview answer

Libraries use type tokens such as Jackson `TypeReference<List<UserDto>>` or Spring `ParameterizedTypeReference<List<UserDto>>`. You create an anonymous subclass, and the framework reads its generic superclass signature through reflection.

This gives the framework the full nested type that erasure would otherwise hide.

#### Deep dive

`Class<T>` is enough for simple non-generic types like `UserDto.class`. For `List<UserDto>` or `ApiResponse<OrderDto>`, a richer `Type` representation is needed.

#### Production angle

This prevents bugs where JSON deserializes into `List<LinkedHashMap>` instead of typed DTOs, or HTTP clients return raw maps.

#### Traps / caveats

- A raw `Class<List>` does not contain the element type.
- Generic wrappers require preserving both wrapper and payload types.
- Type tokens help deserialization but do not validate business semantics.

#### Optional Anki

Q: What problem does `TypeReference<List<UserDto>>` solve?
A: It preserves the list element type for runtime deserialization.

</details>

<a id="rg-gen-013"></a>

<details>
<summary><strong>🧠 RG-GEN-013. How can type erasure cause method-signature conflicts?</strong></summary>

#### Short answer

Two generic method signatures can erase to the same bytecode signature, so Java cannot overload them.

#### Interview answer

Methods such as `void handle(List<String> values)` and `void handle(List<Integer> values)` look different in source code, but both erase to `void handle(List values)`. The JVM signature would be the same, so the compiler rejects the overload.

This is one of the visible consequences of erasure.

#### Deep dive

Erasure also affects inherited generic methods and may require bridge methods when overriding with more specific types.

#### Production angle

Design APIs with distinct method names, parameter counts or non-erased parameter types instead of relying on generic arguments for overload resolution.

#### Traps / caveats

- Return type alone is not enough for overloading.
- Generic type arguments do not create distinct runtime parameter types.
- Adding overloads later can break source compatibility.

#### Optional Anki

Q: Why cannot Java overload `m(List<String>)` and `m(List<Integer>)`?
A: Both erase to `m(List)`.

</details>

<a id="rg-gen-014"></a>

<details>
<summary><strong>RG-GEN-014. Do generics add runtime overhead in Java?</strong></summary>

#### Short answer

Generics themselves usually add little direct runtime overhead because they are erased, but boxing and inserted casts can matter.

#### Interview answer

The generic type parameter is mostly a compile-time concept, so `List<String>` does not create a different runtime container than `List<Object>`. The main performance costs around generics usually come from boxing primitives, extra allocations in generic abstractions or casts inserted by the compiler.

In normal backend code, generics are chosen for safety and clarity, not avoided for performance.

#### Deep dive

Primitive types cannot be generic type arguments, so `List<Integer>` stores boxed `Integer` objects. In hot loops or high-throughput paths, this can increase allocation and CPU cost.

#### Production angle

Measure before optimizing. If profiling shows boxing or generic abstraction overhead, consider primitive streams, specialized collections or simpler code in hot paths.

#### Traps / caveats

- Do not blame generics for database or network latency.
- Boxing overhead is different from erasure overhead.
- Overly generic abstractions can hurt readability even when runtime cost is small.

#### Optional Anki

Q: What is a common performance cost near generics?
A: Boxing primitives into wrapper objects.

</details>
