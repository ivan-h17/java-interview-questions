# 09.05. Wildcards, bounds, PECS and API design

---

<a id="rg-wild-001"></a>

<details>
<summary><strong>RG-WILD-001. What is a bounded type parameter, and what is an upper bound?</strong></summary>

#### Short answer

A bounded type parameter restricts allowed type arguments; an upper bound says the type must be that type or a subtype.

#### Interview answer

`<T extends Number>` means `T` can be `Number` or a subclass such as `Integer` or `BigDecimal`. The bound lets code safely use operations available on `Number`.

Bounds make generic APIs more precise than accepting any `Object`.

#### Deep dive

Java uses `extends` for upper bounds on both classes and interfaces. A type parameter can also have multiple bounds, such as `<T extends Base & Serializable>`.

#### Production angle

Bounds are useful in reusable algorithms, validators, mappers and type-safe registries. They should express a real capability the method needs.

#### Traps / caveats

- Overly broad bounds are almost as weak as no bounds.
- Overly specific bounds reduce API reuse.
- `T extends Serializable` is often a weak design constraint unless serialization is truly required.

#### Optional Anki

Q: What does `<T extends Number>` mean?
A: `T` must be `Number` or a subtype of `Number`.

</details>

<a id="rg-wild-002"></a>

<details>
<summary><strong>RG-WILD-002. What is a lower-bounded wildcard?</strong></summary>

#### Short answer

A lower-bounded wildcard, such as `? super T`, accepts `T` or any supertype of `T`.

#### Interview answer

`List<? super Integer>` means a list whose element type is `Integer`, `Number`, `Object` or another supertype. It is useful when the method wants to put `Integer` values into the list.

The compiler guarantees that adding an `Integer` is safe because every possible target type can hold an `Integer`.

#### Deep dive

Lower bounds are common in consumer APIs: callbacks, comparators, destinations and output collections.

#### Production angle

They make APIs more flexible. A method that writes `User` objects can accept `Collection<? super User>`, so callers can pass `Collection<User>` or `Collection<Object>`.

#### Traps / caveats

- Reading from `? super T` gives only `Object` safely.
- Lower bounds are often harder to read than upper bounds.
- Use them only when they improve caller flexibility.

#### Optional Anki

Q: What is `? super T` best for?
A: Consumers or destinations that accept `T` values.

</details>

<a id="rg-wild-003"></a>

<details>
<summary><strong>RG-WILD-003. What is the difference between <code>&lt;? extends T&gt;</code> and <code>&lt;? super T&gt;</code>?</strong></summary>

#### Short answer

`? extends T` is good for reading `T` values; `? super T` is good for writing `T` values.

#### Interview answer

`List<? extends Number>` is some list of `Number` or a subtype. You can safely read values as `Number`, but you cannot safely add an `Integer` because the actual list might be `List<Double>`.

`List<? super Integer>` is some list of `Integer` or a supertype. You can safely add `Integer`, but reads are only safe as `Object`.

#### Deep dive

This is variance at use sites. Java generic types are invariant by default, so wildcards describe controlled flexibility at the point of use.

#### Production angle

This distinction appears in collection copy methods, event handlers, comparators and generic API design.

#### Traps / caveats

- `extends` does not mean immutable; it means producer-like access.
- `super` does not mean you can read as `T`.
- The actual type behind a wildcard is unknown to the caller.

#### Optional Anki

Q: Which wildcard is for producers?
A: `? extends T`.

</details>

<a id="rg-wild-004"></a>

<details>
<summary><strong>RG-WILD-004. What is PECS: Producer Extends, Consumer Super?</strong></summary>

#### Short answer

PECS is a rule of thumb: use `extends` when a parameter produces values, and `super` when it consumes values.

#### Interview answer

If a method only reads `T` values from a collection, use `? extends T`. If it writes `T` values into a collection, use `? super T`. If it both reads and writes meaningful `T` values, a plain `Collection<T>` may be clearer.

This makes APIs flexible without losing type safety.

#### Deep dive

PECS is about the parameter's role from the method's perspective. A source collection is a producer; a destination collection is a consumer.

#### Production angle

PECS helps design reusable utilities and framework APIs without forcing callers to copy collections just to satisfy exact generic types.

#### Traps / caveats

- Do not apply PECS mechanically to return types.
- If a parameter is both source and destination, wildcards may be wrong.
- Too many wildcards can make APIs hard to use.

#### Optional Anki

Q: What does PECS stand for?
A: Producer Extends, Consumer Super.

</details>

<a id="rg-wild-005"></a>

<details>
<summary><strong>RG-WILD-005. Why can you read from <code>List&lt;? extends T&gt;</code> but not safely add <code>T</code>?</strong></summary>

#### Short answer

The list's exact element type is unknown, but every possible element is at least a `T`.

#### Interview answer

If you have `List<? extends Number>`, the actual list might be `List<Integer>`, `List<Double>` or `List<BigDecimal>`. Reading is safe as `Number`.

Adding is unsafe because adding an `Integer` into a `List<Double>` would break type safety. The compiler prevents that.

#### Deep dive

You can usually add `null`, because `null` is assignable to any reference type, but that is rarely useful and often a bad idea.

#### Production angle

Use upper-bounded wildcards for input collections that are read-only from the method's point of view, such as bulk validation or aggregation.

#### Traps / caveats

- `? extends T` does not make the collection unmodifiable.
- You can still call methods that do not depend on adding a concrete element.
- Do not use it for a destination collection.

#### Optional Anki

Q: Why can `List<? extends Number>` not accept an `Integer` safely?
A: The actual list might be `List<Double>`.

</details>

<a id="rg-wild-006"></a>

<details>
<summary><strong>RG-WILD-006. Why can you add <code>T</code> to <code>List&lt;? super T&gt;</code> but only read <code>Object</code> safely?</strong></summary>

#### Short answer

The list can hold `T`, but its exact supertype is unknown, so reads can only be guaranteed as `Object`.

#### Interview answer

For `List<? super Integer>`, the actual list might be `List<Integer>`, `List<Number>` or `List<Object>`. Adding an `Integer` is safe for all of them.

But when reading, the compiler does not know whether the list contains only integers or mixed objects. The only always safe type is `Object`.

#### Deep dive

This is the consumer side of PECS. The collection consumes `T` values, but it does not promise to produce `T` values.

#### Production angle

Lower bounds are useful for fill methods, copy destinations, event sinks and callback registries.

#### Traps / caveats

- Do not expect to read `T` back without a cast.
- Lower-bounded APIs can be confusing if overused.
- Use clear parameter names like `destination` or `sink`.

#### Optional Anki

Q: What can you safely read from `List<? super T>`?
A: `Object`.

</details>

<a id="rg-wild-007"></a>

<details>
<summary><strong>RG-WILD-007. What is the difference between <code>List&lt;?&gt;</code> and <code>List&lt;Object&gt;</code>?</strong></summary>

#### Short answer

`List<?>` means a list of some unknown type; `List<Object>` means a list that can contain any `Object`.

#### Interview answer

You can pass `List<String>` to a method accepting `List<?>`, because the method promises not to add arbitrary objects. You cannot pass `List<String>` to `List<Object>` because then the method could add an `Integer`, breaking the original list's type safety.

`List<?>` is useful when you only need operations independent of the element type, such as size, iteration as `Object`, or logging.

#### Deep dive

`List<?>` is not the same as a raw `List`. It preserves type safety by preventing unsafe writes.

#### Production angle

Use `List<?>` for generic read-only-ish inspection APIs. Use `List<Object>` only when the list is truly meant to contain mixed object types.

#### Traps / caveats

- You cannot add normal values to `List<?>`.
- `List<?>` still lets you read elements as `Object`.
- `List<Object>` is often a smell in typed domain code.

#### Optional Anki

Q: Can `List<String>` be passed to `List<?>`?
A: Yes.

</details>

<a id="rg-wild-008"></a>

<details>
<summary><strong>RG-WILD-008. Why is <code>List&lt;String&gt;</code> not a subtype of <code>List&lt;Object&gt;</code>?</strong></summary>

#### Short answer

Because generic collections are invariant to prevent unsafe writes.

#### Interview answer

If `List<String>` were a subtype of `List<Object>`, code accepting `List<Object>` could add any object, such as an `Integer`, into a string list. Later, string-list code would fail when reading.

Java prevents this by making `List<String>` and `List<Object>` unrelated except through wildcard forms like `List<? extends Object>`.

#### Deep dive

Arrays are covariant, so `String[]` can be assigned to `Object[]`, but arrays perform runtime store checks. Generics are invariant and catch this category of issue at compile time.

#### Production angle

This is a frequent API-design bug. If callers have `List<String>` and you only read values, accept `List<? extends CharSequence>` or `Collection<String>` depending on the need.

#### Traps / caveats

- `String` is a subtype of `Object`; `List<String>` is not a subtype of `List<Object>`.
- Use wildcards for flexible input.
- Do not fix this by using raw types.

#### Optional Anki

Q: Why are generic collections invariant?
A: To prevent unsafe writes at compile time.

</details>

<details>
<summary><strong>RG-WILD-009. How do <code>Collections.copy()</code> and <code>Comparator&lt;? super T&gt;</code> demonstrate PECS?</strong></summary>

#### Short answer

`Collections.copy()` reads from an `extends` source and writes to a `super` destination; `Comparator<? super T>` consumes `T` values for comparison.

#### Interview answer

`Collections.copy(dest, src)` conceptually uses a source like `List<? extends T>` because it reads `T` values, and a destination like `List<? super T>` because it writes `T` values.

`Comparator<? super T>` means a comparator of `T` or a supertype can compare `T` values. For example, a `Comparator<Object>` can compare strings, though a more specific comparator is usually clearer.

#### Deep dive

These APIs show that wildcards are not academic. They make standard library methods usable with more caller types while preserving type safety.

#### Production angle

This pattern appears when building utility methods, sort APIs, batch copy operations and event dispatchers.

#### Traps / caveats

- Source and destination roles must be clear.
- Do not use `extends` for a destination.
- Do not use exact `T` when a wildcard would improve useful flexibility.

#### Optional Anki

Q: In PECS, what is a copy source?
A: A producer, so it uses `extends`.

</details>

<a id="rg-wild-010"></a>

<details>
<summary><strong>🧠 RG-WILD-010. What is wildcard capture, and how can helper methods solve it?</strong></summary>

#### Short answer

Wildcard capture is when the compiler treats an unknown wildcard as a specific hidden type inside a generic helper method.

#### Interview answer

With `List<?>`, the element type is unknown, so some operations are rejected. A helper method like `<T> void swap(List<T> list, int i, int j)` can capture the unknown type as `T` and perform operations that are safe for one consistent list element type.

This is why compiler messages sometimes mention "capture of ?".

#### Deep dive

Capture does not discover the runtime type. It gives the compiler a name for the unknown compile-time type so it can reason consistently within the helper method.

#### Production angle

Wildcard capture is useful when implementing generic libraries and utilities. Most application code should avoid exposing APIs that require callers to understand capture.

#### Traps / caveats

- Capture is compile-time reasoning, not runtime inspection.
- It cannot make unsafe mixed-type operations safe.
- A simpler exact type parameter may be clearer than wildcard-heavy code.

#### Optional Anki

Q: What does a helper method do for wildcard capture?
A: It gives the unknown wildcard type a named type parameter.

</details>

<a id="rg-wild-011"></a>

<details>
<summary><strong>RG-WILD-011. When should API designers prefer type parameters over wildcards?</strong></summary>

#### Short answer

Use a type parameter when the same type must relate multiple parameters, a parameter and return type, or repeated uses.

#### Interview answer

If a method needs to say "these two things have the same type" or "the return type matches the input type", use a named type parameter. For example, `<T> T first(List<T> values)` needs `T` because the output type depends on the input.

Wildcards are better when you only need flexible input without naming the relationship.

#### Deep dive

Named type parameters are also clearer when the method needs to call other generic methods that require a consistent type.

#### Production angle

Good type parameter design makes fluent APIs, mappers and registries type-safe without casts.

#### Traps / caveats

- Do not introduce `<T>` if it appears only once; a wildcard may be better.
- Do not use a type parameter to hide a lack of domain modeling.
- Too many type parameters reduce readability.

#### Optional Anki

Q: When is `<T>` better than `?`?
A: When multiple parts of the method signature must share the same type.

</details>

<a id="rg-wild-012"></a>

<details>
<summary><strong>RG-WILD-012. When should API designers prefer wildcards over type parameters?</strong></summary>

#### Short answer

Use wildcards when a parameter is only a producer or only a consumer and no named type relationship is needed.

#### Interview answer

If a method only reads from a collection, `Collection<? extends User>` can be more flexible than `Collection<User>`. If it only writes users into a collection, `Collection<? super User>` can be more flexible.

The wildcard communicates the role without inventing unnecessary type parameters.

#### Deep dive

Wildcards are especially common in public library APIs because they accept a broader set of caller types safely.

#### Production angle

Using wildcards in input parameters can avoid forcing callers to copy or cast collections just to call your method.

#### Traps / caveats

- Avoid wildcard return types unless there is a strong reason.
- Do not stack wildcards so deeply that the signature becomes unreadable.
- If callers must name the type, use a type parameter.

#### Optional Anki

Q: When is a wildcard better than `<T>`?
A: When only one parameter has a producer or consumer role and no type relationship needs naming.

</details>

<a id="rg-wild-013"></a>

<details>
<summary><strong>RG-WILD-013. Should public APIs return wildcard types?</strong></summary>

#### Short answer

Usually no. Wildcard return types often push complexity onto callers.

#### Interview answer

Wildcards are most useful in input parameters. Returning `List<? extends User>` can make callers unable to add values, assign the result conveniently or pass it to other APIs.

If the method owns the return type, prefer a concrete generic return such as `List<User>` or a named type parameter when needed.

#### Deep dive

Wildcard returns can be appropriate for advanced library internals or when returning a view with intentionally restricted operations, but they should be rare and justified.

#### Production angle

Simple return types make controller code, service code and tests easier to use. Public APIs should optimize caller ergonomics.

#### Traps / caveats

- Do not expose implementation uncertainty in return types.
- Avoid forcing callers into capture helpers.
- Use interfaces like `List<T>` or `Collection<T>` deliberately, not wildcard returns by default.

#### Optional Anki

Q: Where are wildcards usually most useful?
A: Method input parameters.

</details>

<a id="rg-wild-014"></a>

<details>
<summary><strong>🧠 RG-WILD-014. What is the difference between declaration-site and use-site variance?</strong></summary>

#### Short answer

Declaration-site variance is declared on the generic type itself; use-site variance is declared where the type is used.

#### Interview answer

Java mainly uses use-site variance with wildcards: `List<? extends Number>` or `Comparator<? super String>`. The generic class `List<E>` itself does not declare that it is covariant or contravariant.

Languages such as Kotlin and Scala support declaration-site variance, where a type can declare variance in its definition, such as an `out T` producer.

#### Deep dive

Use-site variance is flexible but can make Java signatures verbose. Declaration-site variance can make APIs cleaner when a type has a consistent producer or consumer role.

#### Production angle

This matters when translating APIs between Java and Kotlin or reading Kotlin declarations from Java.

#### Traps / caveats

- Java arrays are covariant, but Java generic types are invariant by default.
- Java wildcards are not the same as Kotlin `out` and `in` declarations.
- Variance should express real read/write behavior.

#### Optional Anki

Q: What variance style does Java generics mainly use?
A: Use-site variance with wildcards.

</details>
