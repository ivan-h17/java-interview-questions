# 09.09. Senior scenario-based records and generics questions

---

<a id="rg-scenario-001"></a>

<details>
<summary><strong>RG-SCENARIO-001. You receive a mutable `List` inside a record constructor. How do you make the record safe?</strong></summary>

#### Short answer

Copy the list in the constructor, and ensure the accessor does not expose mutable internal state.

#### Interview answer

I would use a compact constructor and store an immutable snapshot:

```java
record OrderSnapshot(List<OrderLine> lines) {
    OrderSnapshot {
        lines = List.copyOf(lines);
    }
}
```

If `OrderLine` is mutable, I also need immutable line objects or element-level copies. Otherwise the list structure is safe but the elements can still change.

#### Deep dive

For arrays, I would clone on input and override the accessor to clone on output. For collections, `List.copyOf()` gives a shallow unmodifiable copy.

#### Production angle

This protects async commands, events, cache keys and audit snapshots from caller-side mutation after construction.

#### Traps / caveats

- `Collections.unmodifiableList(input)` can still reflect mutations to `input`.
- Shallow copies do not protect mutable elements.
- Copying very large lists may require a performance trade-off.

#### Optional Anki

Q: What is the usual safe copy for a record list component?
A: `List.copyOf(input)`.

</details>

<a id="rg-scenario-002"></a>

<details>
<summary><strong>RG-SCENARIO-002. A record is used as a `HashMap` key, and lookups sometimes fail. What would you check?</strong></summary>

#### Short answer

Check whether any equality-relevant component mutates after insertion or has surprising equality semantics.

#### Interview answer

I would inspect all record components used by generated `equals()` and `hashCode()`: collections, arrays, mutable dates, entities, generated IDs or mutable nested objects. If any of them changes after insertion, the map lookup can fail.

I would also check whether arrays are used, because generated equality compares array references, not contents.

#### Deep dive

The debugging path is to log or breakpoint the key at insertion and lookup, compare `hashCode()`, inspect nested mutable state and search for shared references.

#### Production angle

This bug appears in caches, deduplication maps and grouping logic. The fix is usually an immutable key record with copied components or a simpler key type.

#### Traps / caveats

- The map is usually not broken; the key contract is.
- `toString()` may hide reference-equality issues.
- Entity components can change identity after persistence.

#### Optional Anki

Q: Main cause of failed `HashMap` lookup with record keys?
A: A component changed after insertion.

</details>

<a id="rg-scenario-003"></a>

<details>
<summary><strong>RG-SCENARIO-003. A team wants to convert all JPA entities to records. What would you say?</strong></summary>

#### Short answer

I would push back. Records are useful around JPA, but usually not as entities.

#### Interview answer

JPA entities normally need lifecycle identity, lazy loading, dirty checking, generated IDs, no-arg construction and framework-managed mutation. Records are final transparent values with component-based equality.

I would suggest using records for DTO projections, commands, events and API models while keeping entities as classes designed for persistence behavior.

#### Deep dive

The team may be trying to reduce boilerplate. Better options are disciplined entity design, Lombok with care, embeddable value objects, projections or mapper-generated DTOs.

#### Production angle

Forcing records into entity roles can break lazy associations, equality, persistence lifecycle and transaction behavior.

#### Traps / caveats

- A table row shape is not the same as a domain entity.
- Generated record equality is usually wrong for mutable entities.
- Records are good for immutable snapshots of entities.

#### Optional Anki

Q: Best JPA use for records?
A: DTO projections and immutable snapshots.

</details>

<a id="rg-scenario-004"></a>

<details>
<summary><strong>RG-SCENARIO-004. A REST response record changed by adding a new component. What compatibility risks exist?</strong></summary>

#### Short answer

The JSON response shape, generated constructor, mappers, tests and clients may all be affected.

#### Interview answer

Adding a response component may be backward-compatible for tolerant JSON clients, but not always. Strict clients, generated SDKs, snapshot tests or consumers expecting an exact schema may fail.

If the same record is also used for requests, older clients may not send the new field, causing deserialization or validation failures.

#### Deep dive

Compatibility depends on whether the field is required, nullable, has a default, and whether clients ignore unknown fields. Public APIs need contract tests and versioning policies.

#### Production angle

Before deployment, test representative old clients and stored payloads. Avoid reusing one internal record as both persistence projection and public API contract.

#### Traps / caveats

- Adding a primitive component gives no natural absent value.
- Component renames are more dangerous than additive fields.
- Mapper code may fail to compile, which is useful feedback.

#### Optional Anki

Q: Why can adding a record component break REST compatibility?
A: It can change JSON shape and constructor requirements.

</details>

<a id="rg-scenario-005"></a>

<details>
<summary><strong>RG-SCENARIO-005. A generic JSON client returns <code>List&lt;LinkedHashMap&gt;</code> instead of <code>List&lt;UserDto&gt;</code>. Why?</strong></summary>

#### Short answer

The client lost the generic element type at runtime and deserialized objects as maps.

#### Interview answer

Because of type erasure, passing only `List.class` tells the JSON library it should create a list, but not what element type the list contains. Without `UserDto` metadata, objects become generic maps such as `LinkedHashMap`.

The fix is to pass a full type token like `TypeReference<List<UserDto>>` or Spring `ParameterizedTypeReference<List<UserDto>>`.

#### Deep dive

This also applies to wrappers like `ApiResponse<List<UserDto>>`. The full nested type must be preserved.

#### Production angle

This bug often escapes when generic HTTP clients return raw `Object` or map structures. Add typed client methods and tests for nested DTO deserialization.

#### Traps / caveats

- `List.class` is not enough.
- Casting `List<LinkedHashMap>` to `List<UserDto>` only moves the failure later.
- Generic records have the same issue.

#### Optional Anki

Q: How do you deserialize `List<UserDto>` safely?
A: Provide a full generic type token.

</details>

<a id="rg-scenario-006"></a>

<details>
<summary><strong>RG-SCENARIO-006. How would you design a type-safe API response wrapper with records and generics?</strong></summary>

#### Short answer

Use a simple generic record for valid shared metadata, and avoid ambiguous success/error states.

#### Interview answer

For a normal success response, I might use:

```java
record ApiResponse<T>(T data, String requestId) {}
```

But I would not mix success and error in one nullable shape like `data` plus `error`. For errors, use a separate `ErrorResponse` or a sealed result model internally.

#### Deep dive

If the wrapper is public, define nullability, JSON field names, examples and compatibility rules. Generic wrappers need type tokens in clients.

#### Production angle

Consistent response wrappers simplify client code and observability, but over-wrapping every endpoint can make APIs noisy.

#### Traps / caveats

- Avoid states where both `data` and `error` are set.
- Generic wrappers can complicate OpenAPI/client generation.
- Do not wrap just because a framework template does.

#### Optional Anki

Q: What is the main design risk in generic response wrappers?
A: Ambiguous states and lost generic type information.

</details>

<a id="rg-scenario-007"></a>

<details>
<summary><strong>RG-SCENARIO-007. How would you design a generic pagination response DTO?</strong></summary>

#### Short answer

Use a typed item list plus explicit pagination metadata.

#### Interview answer

A simple offset-based DTO could be:

```java
record PageResponse<T>(
    List<T> items,
    int page,
    int size,
    long totalElements
) {
    PageResponse {
        items = List.copyOf(items);
    }
}
```

For cursor pagination, use cursor fields instead of total counts if totals are expensive or unstable.

#### Deep dive

The wrapper should match the pagination strategy. Offset pagination, cursor pagination and keyset pagination have different metadata.

#### Production angle

Pagination DTOs are public contracts. Define empty pages, max size, sorting, next cursor and total-count semantics clearly.

#### Traps / caveats

- Do not promise `totalElements` if counting is too expensive or inconsistent.
- Copy items if the response should be immutable.
- Generic clients need type metadata for `PageResponse<UserDto>`.

#### Optional Anki

Q: What should pagination DTOs separate?
A: Items and pagination metadata.

</details>

<a id="rg-scenario-008"></a>

<details>
<summary><strong>RG-SCENARIO-008. A method accepts <code>List&lt;Object&gt;</code> but callers have <code>List&lt;String&gt;</code>. How would you fix the API?</strong></summary>

#### Short answer

If the method only reads, accept `List<?>` or `List<? extends SomeBaseType>` instead of `List<Object>`.

#### Interview answer

`List<String>` is not a subtype of `List<Object>`, so the original signature is too restrictive. If the method only logs or counts values, `List<?>` is enough. If it reads values as `CharSequence`, use `List<? extends CharSequence>`.

If the method needs to add arbitrary objects, then callers should not pass a `List<String>`.

#### Deep dive

The right signature depends on whether the parameter is a producer, consumer or both. PECS guides the choice.

#### Production angle

Fixing the signature avoids unsafe casts and preserves caller type safety.

#### Traps / caveats

- Do not solve this with raw `List`.
- `List<Object>` means the method may add any object.
- Wildcards should match actual read/write behavior.

#### Optional Anki

Q: Why cannot `List<String>` be passed to `List<Object>`?
A: It would allow unsafe writes into the string list.

</details>

<a id="rg-scenario-009"></a>

<details>
<summary><strong>RG-SCENARIO-009. You need a method that copies elements from one collection to another. How would you use PECS?</strong></summary>

#### Short answer

Use `? extends T` for the source and `? super T` for the destination.

#### Interview answer

The source produces values, so it should be `Collection<? extends T>`. The destination consumes values, so it should be `Collection<? super T>`.

```java
static <T> void copy(Collection<? super T> dest, Collection<? extends T> src) {
    dest.addAll(src);
}
```

This allows copying `List<Integer>` into `List<Number>` safely.

#### Deep dive

The method does not need to know the exact source subtype, only that source elements can be viewed as `T`.

#### Production angle

This pattern is useful in utility methods, batch assembly and event dispatch code.

#### Traps / caveats

- Source is `extends`; destination is `super`.
- If source and destination are the same mutable collection, behavior may need special handling.
- Avoid over-generalizing if a concrete type is clearer.

#### Optional Anki

Q: In a copy method, which side uses `super`?
A: The destination.

</details>

<a id="rg-scenario-010"></a>

<details>
<summary><strong>RG-SCENARIO-010. A raw list causes a `ClassCastException` far from the source of the bug. How would you investigate?</strong></summary>

#### Short answer

Trace where the raw list is created or crossed an unchecked boundary, then add type checks or typed wrappers there.

#### Interview answer

I would search for raw `List`, unchecked casts and suppressed warnings around the failing data path. The failure point is often only where the bad element is read; the real bug is where it was inserted.

Then I would localize the unsafe boundary: convert raw data into a typed collection once, validate element types, and expose `List<UserDto>` internally.

#### Deep dive

If the source is JSON/reflection/legacy code, add tests for invalid element types and fail fast with a clear error.

#### Production angle

This turns late random `ClassCastException` into early boundary validation, which is easier to monitor and debug.

#### Traps / caveats

- Do not cast the whole raw list and assume contents are valid.
- Broad warning suppressions hide the source.
- Logs should include enough context without dumping sensitive data.

#### Optional Anki

Q: Where is the real bug in raw-list `ClassCastException`?
A: Usually where the wrong element entered the list.

</details>

<a id="rg-scenario-011"></a>

<details>
<summary><strong>🧠 RG-SCENARIO-011. A generic varargs method produces heap pollution warnings. How would you make it safe?</strong></summary>

#### Short answer

Avoid generic varargs if possible; otherwise ensure the method only safely reads arguments and annotate narrowly with `@SafeVarargs`.

#### Interview answer

First I would ask whether the method should accept `List<T>` or `Collection<T>` instead of varargs. If varargs are the right API, the method must not write incompatible values into the varargs array or expose that array.

If it is final, static or private and the body is safe, add `@SafeVarargs`.

#### Deep dive

Safe implementations usually iterate over the varargs values or copy them into a new collection. Unsafe ones store into `args`, return `args`, or pass it to code that may corrupt it.

#### Production angle

This is common in small utility APIs. Keeping the method tiny makes the safety promise reviewable.

#### Traps / caveats

- Do not annotate just to silence the compiler.
- Do not suppress warnings at class level.
- Add tests for mixed or malicious inputs when data is untrusted.

#### Optional Anki

Q: When is `@SafeVarargs` justified?
A: When the generic varargs body is actually type-safe and cannot be overridden unsafely.

</details>

<details>
<summary><strong>RG-SCENARIO-012. A generic method has an unreadable signature with many bounds. How would you refactor it?</strong></summary>

#### Short answer

Look for a named domain type, smaller interfaces or simpler method responsibilities.

#### Interview answer

I would first ask what business concept the generic signature is trying to express. If the method is really about an `OrderSearchCriteria`, `ExportJob` or `ValidationResult`, I would introduce that type.

If multiple capabilities are needed, a small named interface may be clearer than a long bound list.

#### Deep dive

Some complexity belongs in reusable libraries, but application services should optimize for domain clarity. Splitting one generic method into two focused methods can also remove awkward bounds.

#### Production angle

Readable signatures reduce misuse, review time and onboarding cost.

#### Traps / caveats

- Do not remove type safety by falling back to `Object`.
- Do not preserve a generic abstraction after its use cases diverge.
- Keep useful compile-time constraints where they protect real bugs.

#### Optional Anki

Q: First refactoring question for unreadable generics?
A: What domain concept is this signature hiding?

</details>

<details>
<summary><strong>RG-SCENARIO-013. You need runtime type information for <code>List&lt;OrderDto&gt;</code>. How would you preserve it?</strong></summary>

#### Short answer

Use a full generic type token, not just `List.class`.

#### Interview answer

For Jackson, use something like `new TypeReference<List<OrderDto>>() {}`. For Spring WebClient or RestTemplate-style APIs, use `new ParameterizedTypeReference<List<OrderDto>>() {}`.

This captures the nested generic type in a reflective signature so the framework knows the list element type.

#### Deep dive

`Class<OrderDto>` is enough for one DTO object, but `List<OrderDto>` needs a richer `Type` representation.

#### Production angle

Typed client methods should hide this detail from business code. Tests should verify the returned elements are real DTOs, not maps.

#### Traps / caveats

- `List.class` loses `OrderDto`.
- Casting after deserialization does not convert map elements.
- Nested wrappers require preserving the whole type tree.

#### Optional Anki

Q: What preserves `List<OrderDto>` for Jackson?
A: `TypeReference<List<OrderDto>>`.

</details>

<a id="rg-scenario-014"></a>

<details>
<summary><strong>🧠 RG-SCENARIO-014. A bridge method appears in a stack trace. What does it mean?</strong></summary>

#### Short answer

It is a compiler-generated method used to preserve generic polymorphism after erasure.

#### Interview answer

I would not treat it as a source method I forgot about. Bridge methods are synthetic bytecode methods. They often delegate from an erased signature, such as `compareTo(Object)`, to a specific method, such as `compareTo(MyType)`.

If the bridge method appears near a `ClassCastException`, it may mean a generic contract was violated.

#### Deep dive

Reflection can identify bridge methods with `Method.isBridge()`. Frameworks often need to resolve the bridged method to find annotations or generic metadata.

#### Production angle

This matters when debugging AOP, metrics, code coverage, bytecode instrumentation or generic interface implementations.

#### Traps / caveats

- Bridge methods are expected with some generic overrides.
- They can appear in stack traces even though not in source.
- Do not double-count bridge and real methods in reflection code.

#### Optional Anki

Q: What commonly creates bridge methods?
A: Generic overriding after type erasure.

</details>

<a id="rg-scenario-015"></a>

<details>
<summary><strong>RG-SCENARIO-015. How would you decide between a record, a class, an enum and a sealed hierarchy?</strong></summary>

#### Short answer

Choose based on identity, state shape, number of variants and need for extension.

#### Interview answer

Use a record for a transparent value-like state carrier. Use a regular class for hidden state, lifecycle, mutation, inheritance or framework requirements. Use an enum for a fixed set of stable named constants. Use a sealed hierarchy when a concept has a closed set of variants, especially if each variant carries different data.

The model should express the domain, not just use the newest feature.

#### Deep dive

Records and sealed interfaces combine well for result types: each record variant carries data, and the sealed interface controls the set of cases.

#### Production angle

The right shape improves validation, API evolution, persistence mapping and exhaustiveness in business logic.

#### Traps / caveats

- Enums are hard to evolve when persisted or exposed externally.
- Sealed hierarchies are bad for open plugin models.
- Records are bad for identity-based lifecycle entities.

#### Optional Anki

Q: What is a sealed hierarchy good for?
A: A closed set of known variants.

</details>

<a id="rg-scenario-016"></a>

<details>
<summary><strong>RG-SCENARIO-016. How would you migrate a Lombok DTO to a record safely?</strong></summary>

#### Short answer

Check API shape, constructor binding, null/default behavior, generated methods and framework compatibility before replacing it.

#### Interview answer

I would compare the Lombok DTO's public contract with the record: field names, getters, setters, constructors, JSON names, validation annotations, equality and `toString()`. Records use component accessors, so any JavaBean getter expectations need checking.

Then I would update mappers, tests and serialization samples.

#### Deep dive

If the DTO was mutable because frameworks or code set fields gradually, migration may require constructor-based mapping or a builder before creating the record.

#### Production angle

Use contract tests for JSON request/response compatibility and compile-time mapper checks. Watch for sensitive fields in generated `toString()`.

#### Traps / caveats

- Lombok `@Data` equality may differ from record equality.
- Removing setters can break reflection or mapper code.
- Component names become constructor and serialization names.

#### Optional Anki

Q: Main migration check from Lombok DTO to record?
A: Preserve the external contract and framework binding behavior.

</details>

<details>
<summary><strong>RG-SCENARIO-017. How would you design domain value objects using records without leaking persistence concerns?</strong></summary>

#### Short answer

Make records express domain concepts and invariants, not database columns or entity lifecycle details.

#### Interview answer

I would create small named records such as `EmailAddress`, `Money` or `OrderNumber` with validation in constructors and behavior where useful. They should not know about JPA IDs, lazy associations or table shapes.

Persistence mapping can convert between entities and value records at the boundary.

#### Deep dive

If a value object contains mutable components, copy them. If it needs rich lifecycle behavior or hidden state, it may need a regular class.

#### Production angle

This improves type safety and prevents primitive obsession while keeping persistence concerns isolated.

#### Traps / caveats

- Do not mirror every table column as a public record component.
- Avoid generic `Pair` for domain values.
- Keep validation errors mapped cleanly at API boundaries.

#### Optional Anki

Q: What should a domain record represent?
A: A named domain value with clear invariants.

</details>

<a id="rg-scenario-018"></a>

<details>
<summary><strong>RG-SCENARIO-018. How would you use sealed interfaces and records to model business results?</strong></summary>

#### Short answer

Define a sealed result interface and use records for each concrete success or failure variant.

#### Interview answer

For example:

```java
sealed interface PaymentResult permits Approved, Declined, Failed {}
record Approved(String authCode) implements PaymentResult {}
record Declined(String reason) implements PaymentResult {}
record Failed(String message) implements PaymentResult {}
```

This avoids ambiguous nullable result wrappers and makes each case explicit.

#### Deep dive

With pattern matching, callers can handle each known variant. This is useful when the set of outcomes is intentionally closed.

#### Production angle

Business results become easier to test and log. API mapping can convert each variant into the correct HTTP status or response body.

#### Traps / caveats

- Keep sealed hierarchies internal if public evolution is uncertain.
- Do not create too many variants for incidental details.
- Persisted variant names need compatibility planning.

#### Optional Anki

Q: Why use sealed records for results?
A: To model explicit closed success/failure variants.

</details>

<a id="rg-scenario-019"></a>

<details>
<summary><strong>RG-SCENARIO-019. How would you avoid generic type information loss in a Spring REST client?</strong></summary>

#### Short answer

Use `ParameterizedTypeReference<T>` for generic response types.

#### Interview answer

If the endpoint returns `PageResponse<UserDto>`, passing only `PageResponse.class` loses `UserDto`. With Spring clients, I would use:

```java
new ParameterizedTypeReference<PageResponse<UserDto>>() {}
```

That preserves the nested generic type for message conversion.

#### Deep dive

For non-generic responses, `UserDto.class` is enough. For generic wrappers, lists and maps, a parameterized type reference is the safer contract.

#### Production angle

Typed client methods should centralize this so callers do not repeat anonymous type tokens everywhere.

#### Traps / caveats

- Raw classes lose nested type arguments.
- Generic records have the same issue as generic classes.
- Tests should assert element types, not only HTTP status.

#### Optional Anki

Q: Spring type token for generic HTTP responses?
A: `ParameterizedTypeReference<T>`.

</details>

<a id="rg-scenario-020"></a>

<details>
<summary><strong>RG-SCENARIO-020. How would you test that a record with collection components is truly immutable?</strong></summary>

#### Short answer

Test mutation of the original input, mutation through the accessor and mutation of nested elements if relevant.

#### Interview answer

I would construct the record from a mutable list, mutate the original list and assert the record did not change. Then I would call the accessor and verify structural mutation fails or does not affect the record.

If elements are mutable, I would test whether mutating an element changes the record's observable state. If it does, the record is only shallowly immutable.

#### Deep dive

For arrays, test both input-array mutation and accessor-array mutation. For nested collections, test each ownership boundary you claim to protect.

#### Production angle

These tests are valuable for cache keys, events, snapshots and request objects shared across threads or async tasks.

#### Traps / caveats

- `UnsupportedOperationException` from a list accessor is not enough if elements mutate.
- Do not call a record deeply immutable unless the whole reachable graph is protected.
- Large defensive-copy tests should also consider performance.

#### Optional Anki

Q: What three mutations should immutability tests check?
A: Original input, accessor result and nested mutable elements.

</details>
