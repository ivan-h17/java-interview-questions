<a id="rg-adv-001"></a>

<details>
<summary><strong>🧠 RG-ADV-001. What are recursive type bounds and F-bounded polymorphism?</strong></summary>

#### Short answer

They are generic bounds where a type parameter is bounded by a type expression involving itself.

#### Interview answer

A recursive bound looks like `<T extends Comparable<T>>`. It says `T` is comparable to values of its own type. F-bounded polymorphism is this broader pattern of using the subtype itself in the bound.

It is useful when an API wants operations to return or compare the concrete subtype rather than a base type.

#### Deep dive

Fluent builders sometimes use recursive bounds so base builder methods can return the concrete builder type. This avoids casts in fluent chains but makes signatures harder to read.

#### Production angle

Use recursive bounds in shared infrastructure only when they remove real type-safety problems. In application code, simpler composition or explicit return types are often clearer.

#### Traps / caveats

- Error messages become harder for teammates.
- It can create an illusion of type safety if the hierarchy is poorly designed.
- Fluent APIs can often be simpler with concrete builders.

#### Optional Anki

Q: What is a common recursive bound example?
A: `<T extends Comparable<T>>`.

</details>

<a id="rg-adv-002"></a>

<details>
<summary><strong>🧠 RG-ADV-002. How does <code>Comparable&lt;T&gt;</code> relate to recursive bounds?</strong></summary>

#### Short answer

APIs often use `<T extends Comparable<? super T>>` to require values that can be compared with themselves or supertypes.

#### Interview answer

`Comparable<T>` expresses that a type can compare itself to another `T`. A sorting or max function can require a type that is comparable:

```java
static <T extends Comparable<? super T>> T max(List<T> values)
```

The `? super T` part allows comparisons defined on a supertype.

#### Deep dive

This is more flexible than `<T extends Comparable<T>>`, especially when subclasses inherit comparison behavior from a base class.

#### Production angle

This appears in reusable sorting, range and validation utilities. Most backend code should prefer existing library methods unless custom comparison is domain-specific.

#### Traps / caveats

- `Comparable` should be consistent with equality when used in sorted sets/maps.
- Natural ordering is not always the domain ordering you need.
- Complex bounds may be overkill for one local method.

#### Optional Anki

Q: Why use `Comparable<? super T>`?
A: To allow comparison behavior declared on a supertype of `T`.

</details>

<a id="rg-adv-003"></a>

<details>
<summary><strong>🧠 RG-ADV-003. What are multiple bounds, and what syntax restrictions apply?</strong></summary>

#### Short answer

Multiple bounds require a type to satisfy more than one type, with at most one class bound listed first.

#### Interview answer

Java allows declarations such as `<T extends BaseEntity & Auditable & Serializable>`. If there is a class bound, it must be first. Interface bounds follow it.

This lets a method rely on multiple capabilities without accepting unrelated objects.

#### Deep dive

The single-class-first rule follows Java's single inheritance model and erasure rules. The erased type is the leftmost bound.

#### Production angle

Multiple bounds can be useful in framework utilities, but in domain code they may reveal that a named interface or adapter would be clearer.

#### Traps / caveats

- Only one class bound is allowed.
- Class bound must come before interface bounds.
- Too many bounds make APIs hard to use.

#### Optional Anki

Q: In `<T extends A & B>`, what must `A` be if it is a class?
A: The first bound.

</details>

<a id="rg-adv-004"></a>

<details>
<summary><strong>🧠 RG-ADV-004. How does erasure work with multiple bounds?</strong></summary>

#### Short answer

The type parameter erases to its leftmost bound.

#### Interview answer

For `<T extends Number & Comparable<T>>`, `T` erases to `Number`. For `<T extends Closeable & Flushable>`, it erases to `Closeable` because that is the first bound.

The compiler may insert casts to access members from other bounds.

#### Deep dive

This is why bound order can affect generated signatures and binary compatibility. Java requires a class bound to be first, then interface bounds.

#### Production angle

Most developers see this only when reading bytecode, reflection results, generated bridge methods or binary compatibility issues in libraries.

#### Traps / caveats

- Reordering bounds can affect erased signatures.
- The compiler still checks all bounds at compile time.
- Runtime reflection may show different levels of detail depending on API used.

#### Optional Anki

Q: Multiple-bound erasure uses which bound?
A: The leftmost bound.

</details>

<details>
<summary><strong>🧠 RG-ADV-005. What are bridge methods, and why does the compiler generate them?</strong></summary>

#### Short answer

Bridge methods are synthetic methods generated to preserve polymorphism after type erasure.

#### Interview answer

When a subclass overrides a generic method with a more specific type, erasure can make the bytecode signatures differ from the source-level override. The compiler adds a bridge method with the erased signature that delegates to the specific method.

This keeps old-style JVM dispatch working correctly.

#### Deep dive

For example, a class implementing `Comparable<MyType>` may have a real `compareTo(MyType)` method and a synthetic bridge `compareTo(Object)` that casts and delegates.

#### Production angle

Bridge methods usually do not matter, but they can appear in stack traces, reflection, code coverage, AOP, bytecode instrumentation and profiling.

#### Traps / caveats

- Bridge methods are normal implementation artifacts, not duplicate source methods.
- Reflection code may need to ignore synthetic/bridge methods.
- They are a consequence of erasure, not a runtime bug.

#### Optional Anki

Q: Why are bridge methods generated?
A: To preserve polymorphic overriding after erasure.

</details>

<a id="rg-adv-006"></a>

<details>
<summary><strong>🧠 RG-ADV-006. Why might bridge methods appear in stack traces or reflection?</strong></summary>

#### Short answer

They are real bytecode methods generated by the compiler, so runtime tools can observe them.

#### Interview answer

Even though you did not write a bridge method in source code, the JVM executes bytecode. If a bridge method performs a cast and delegates, exceptions or instrumentation may show that synthetic method.

Reflection can also list bridge methods unless filtered.

#### Deep dive

`Method.isBridge()` and `Method.isSynthetic()` can help reflection-heavy code identify compiler-generated methods.

#### Production angle

This matters for frameworks that scan methods for annotations, generate proxies, collect metrics or weave aspects. Naive scanning may double-count methods or pick the wrong one.

#### Traps / caveats

- Do not treat bridge methods as source-level API.
- Be careful with AOP pointcuts matching both real and bridge methods.
- Stack traces involving bridges often still point to a real generic override problem.

#### Optional Anki

Q: Which reflection method identifies bridge methods?
A: `Method.isBridge()`.

</details>

<a id="rg-adv-007"></a>

<details>
<summary><strong>RG-ADV-007. How can generics improve repository, mapper and service abstractions?</strong></summary>

#### Short answer

Generics can express reusable type relationships without losing compile-time safety.

#### Interview answer

A `Repository<T, ID>` can say that a repository returns `T` and accepts an `ID` of a specific type. A `Mapper<S, T>` can say it maps from source `S` to target `T`. This avoids repeated casts and clarifies contracts.

Generics are useful when the abstraction is genuinely the same across types.

#### Deep dive

The key is preserving useful constraints. A generic API should expose the type relationships callers care about, not hide every domain concept behind `T`.

#### Production angle

Good generic abstractions reduce duplication in persistence, mapping and client code. They also make refactoring safer because type errors appear at compile time.

#### Traps / caveats

- Do not use generics to erase domain vocabulary.
- Generic CRUD services often become too weak for real business behavior.
- Avoid casts inside generic abstractions when the type contract can express the relation.

#### Optional Anki

Q: When are generic abstractions useful?
A: When the same behavior truly applies across types and type relations matter.

</details>

<a id="rg-adv-008"></a>

<details>
<summary><strong>RG-ADV-008. When do generic base repositories or services become an anti-pattern?</strong></summary>

#### Short answer

They become an anti-pattern when they hide domain behavior behind generic CRUD and force awkward extension points.

#### Interview answer

A generic base repository can reduce duplication for simple persistence operations. But a generic base service like `BaseCrudService<T>` often grows hooks, flags, reflection and conditional logic for every entity's special case.

At that point it hides business intent and makes the code harder to change.

#### Deep dive

Domain services often differ in validation, authorization, transactions, events and invariants. Those differences are usually more important than the shared CRUD skeleton.

#### Production angle

Over-generic services create bugs when a new use case accidentally inherits behavior that is not valid for its domain.

#### Traps / caveats

- Duplication is sometimes cheaper than a bad abstraction.
- Generic repositories are less risky than generic business services.
- Watch for `if entityType == ...` inside generic code.

#### Optional Anki

Q: What is the smell in a generic base service?
A: It hides domain-specific behavior behind weak CRUD abstraction.

</details>

<details>
<summary><strong>🧠 RG-ADV-009. How can type erasure affect dependency injection with generic beans?</strong></summary>

#### Short answer

Erasure removes runtime type parameters from ordinary objects, so DI frameworks must rely on declared generic metadata and qualifiers.

#### Interview answer

If you have beans like `Handler<UserEvent>` and `Handler<OrderEvent>`, the raw runtime type is just `Handler`. Spring can often resolve generic arguments from class signatures or injection points, but ambiguity can still happen.

Qualifiers, explicit bean names or more specific interfaces may be needed.

#### Deep dive

Frameworks inspect generic superclasses, implemented interfaces and injection-point declarations. But proxies, raw types and factory methods can obscure metadata.

#### Production angle

This matters in event dispatchers, strategy registries, generic clients and mappers. Ambiguous or wrong bean selection can cause startup failures or subtle runtime routing bugs.

#### Traps / caveats

- Do not rely on erased runtime class alone.
- Raw bean declarations lose metadata.
- Proxies can complicate generic metadata lookup.

#### Optional Anki

Q: Why can two `Handler<T>` beans be ambiguous?
A: Their raw runtime type is the same after erasure.

</details>

<details>
<summary><strong>🧠 RG-ADV-010. How do generics interact with proxies and AOP?</strong></summary>

#### Short answer

Proxies operate at runtime on classes or interfaces, while generic type information may be erased or only available in declarations.

#### Interview answer

Spring AOP or other proxy frameworks wrap beans using interfaces or subclasses. Generic signatures may not be directly visible on the proxy class, and bridge methods can appear around generic overrides.

This can affect pointcuts, reflection-based method lookup and return-type handling.

#### Deep dive

JDK dynamic proxies expose interface methods. CGLIB-style proxies subclass concrete classes. Each approach has different behavior for final classes, bridge methods and generic metadata.

#### Production angle

Problems appear in transaction aspects, metrics aspects, generic handlers and serialization around proxied return types. Inspect the target class, not only the proxy class, when debugging.

#### Traps / caveats

- Records are final, so subclass-based proxies cannot extend them.
- Bridge methods may match pointcuts unexpectedly.
- Generic return types may need target-method metadata, not proxy-class metadata.

#### Optional Anki

Q: Why can generic AOP reflection be tricky?
A: Proxies and erasure can hide or duplicate method metadata.

</details>

<a id="rg-adv-011"></a>

<details>
<summary><strong>RG-ADV-011. How should generic pagination and error wrappers be designed?</strong></summary>

#### Short answer

Keep wrappers explicit, simple and stable, with clear metadata and typed payloads.

#### Interview answer

A pagination wrapper might be `record PageResponse<T>(List<T> items, int page, int size, long total)`. It should separate payload from metadata and avoid ambiguous fields.

For errors, avoid designs like `Response<T>(T data, String error)` where both success and failure can be half-filled. A sealed success/failure model or separate error response is often clearer.

#### Deep dive

Generic wrappers become public contracts quickly. Think about JSON shape, nullability, empty pages, cursor vs offset pagination, and how clients generate types.

#### Production angle

Good wrappers make API responses predictable and easier to deserialize. Bad wrappers create null checks, ambiguous states and client-side bugs.

#### Traps / caveats

- Avoid `data` plus `error` where both can be set or both missing.
- Do not expose internal pagination implementation accidentally.
- Generic wrappers need type tokens for deserialization.

#### Optional Anki

Q: What is a trap in `Response<T>(T data, String error)`?
A: It can represent ambiguous invalid states.

</details>

<details>
<summary><strong>RG-ADV-012. How do generic records work with serializers?</strong></summary>

#### Short answer

They serialize like other records, but deserialization often needs full generic type information.

#### Interview answer

`record ApiResponse<T>(T data)` can serialize easily because the runtime object has a concrete `data` value. Deserialization is harder: the framework must know whether `T` is `UserDto`, `OrderDto` or something else.

For JSON, callers often need `TypeReference<ApiResponse<UserDto>>` or `ParameterizedTypeReference<ApiResponse<UserDto>>`.

#### Deep dive

Nested generics multiply this issue: `PageResponse<List<UserDto>>` requires preserving the whole type tree.

#### Production angle

Without type metadata, payloads may deserialize into maps instead of DTOs. This is common in generic REST clients and message consumers.

#### Traps / caveats

- `ApiResponse.class` loses `T`.
- Runtime payload inspection is not a substitute for a contract.
- Public generic records can make client SDKs more complex.

#### Optional Anki

Q: What does a generic record need for JSON deserialization?
A: Full generic type metadata, usually through a type token.

</details>
