# 09.01. Records fundamentals, constructors and modeling

---

<a id="rg-rec-001"></a>

<details>
<summary><strong>RG-REC-001. What is a record in Java, and what problem does it solve?</strong></summary>

#### Short answer

A record is a special kind of Java class for transparent, value-like data carriers with a fixed set of components.

#### Interview answer

Records solve the boilerplate problem for classes that mainly carry data. Instead of manually writing fields, constructor, accessors, `equals()`, `hashCode()` and `toString()`, you declare the state once in the record header.

For example, `record UserDto(long id, String email) {}` clearly says that the type is defined by `id` and `email`. It is still a nominal Java type, not a tuple: `UserDto` and `CustomerDto` are different types even if their components match.

#### Deep dive

Records became a final language feature in Java 16. A record is implicitly final and extends `java.lang.Record`. Its component list is part of the class API, so records are best when exposing the state is intentional.

#### Production angle

Records are useful for DTOs, commands, events, projections, simple value objects and composite keys. They reduce repetitive code but do not remove the need for validation, compatibility thinking or defensive copying.

#### Traps / caveats

- A record is not automatically deeply immutable.
- A record is not a good default for entities with lifecycle identity.
- Component names and order become part of the public contract.

#### Optional Anki

Q: What problem do Java records solve?
A: They reduce boilerplate for transparent value-like data carriers.

</details>

<a id="rg-rec-002"></a>

<details>
<summary><strong>RG-REC-002. What makes records transparent data carriers?</strong></summary>

#### Short answer

The record header publicly declares the complete state used by the generated constructor, accessors and value-based methods.

#### Interview answer

A record is transparent because its representation is visible in the type declaration. If you write `record Money(BigDecimal amount, Currency currency)`, callers can see that `amount` and `currency` define the value.

This is different from a class that hides representation behind getters and behavior. A record can still have methods, validation and static factories, but the declared components are supposed to explain the state that matters.

#### Deep dive

Transparency is a design promise. The generated `equals()`, `hashCode()` and `toString()` are based on the components. Accessors use component names, such as `amount()`, not JavaBean-style `getAmount()` by default.

#### Production angle

This makes records good at boundaries: responses, query results, message payloads and immutable command objects. It is weaker for models where you want to hide persistence details, lazy state or derived internal representation.

#### Traps / caveats

- Do not use a record if exposing components would lock in internals you expect to change.
- Do not hide surprising mutation behind a record-looking API.
- Generated `toString()` can expose sensitive component values.

#### Optional Anki

Q: What does record transparency mean?
A: The record header declares the visible state that defines the value.

</details>

<a id="rg-rec-003"></a>

<details>
<summary><strong>RG-REC-003. What are the main differences between a record and a regular class?</strong></summary>

#### Short answer

A record has declared components, generated value-based methods, final component fields and strict inheritance limits. A regular class is more flexible.

#### Interview answer

A record is still a class, but with special rules. Java generates private final fields for components, accessors, a canonical constructor, `equals()`, `hashCode()` and `toString()`. Records are implicitly final and cannot extend arbitrary classes.

A regular class is better when you need hidden representation, mutable state, inheritance, non-component instance fields, complex lifecycle or identity separate from field values.

#### Deep dive

Records can declare methods, static members, nested types and constructors, but they cannot declare extra instance fields. A record constructor must preserve the component model: every instance is defined by the component values.

#### Production angle

Records are attractive for DTO-heavy backend code, but a regular class is usually clearer for JPA entities, aggregates, builders, state machines and framework models that require proxying or mutation.

#### Traps / caveats

- Records are final; they cannot be subclassed.
- Records use component accessors, not JavaBean getters by default.
- Record equality is component-based unless deliberately overridden.

#### Optional Anki

Q: When is a regular class better than a record?
A: When identity, lifecycle, hidden state, mutation or inheritance matters.

</details>

<a id="rg-rec-004"></a>

<details>
<summary><strong>RG-REC-004. What does Java generate from record components?</strong></summary>

#### Short answer

Java generates private final fields, public accessors, a canonical constructor and implementations of `equals()`, `hashCode()` and `toString()`.

#### Interview answer

For `record User(String name, int age)`, Java creates component fields, `name()` and `age()` accessors, a constructor accepting both values, and value-style implementations of `equals()`, `hashCode()` and `toString()`.

The generated methods use all record components. That makes records concise and predictable for simple data carriers.

#### Deep dive

The component declaration also drives reflection metadata and annotation propagation rules. Component annotations can be relevant to constructor parameters, fields, accessors or record components depending on the annotation target.

#### Production angle

The generated code reduces mistakes in DTOs and value objects, especially around equality and logging. But generated `toString()` may leak PII, tokens or other sensitive data if such values are components.

#### Traps / caveats

- Accessors are named `component()`, not `getComponent()`.
- Generated equality includes all components.
- Component order matters for constructors and some reflective code.

#### Optional Anki

Q: Which methods does a record commonly generate?
A: Accessors, canonical constructor, `equals()`, `hashCode()` and `toString()`.

</details>

<a id="rg-rec-005"></a>

<details>
<summary><strong>RG-REC-005. What is a compact constructor, and when should you use it?</strong></summary>

#### Short answer

A compact constructor is a record constructor without an explicit parameter list, used mainly for validation and normalization.

#### Interview answer

In a compact constructor, Java provides the record components as constructor parameters and assigns them to fields after the body runs. For example:

```java
record Email(String value) {
    Email {
        value = value.trim().toLowerCase(Locale.ROOT);
        if (value.isBlank()) throw new IllegalArgumentException("blank email");
    }
}
```

Use it when the constructor logic directly protects component invariants.

#### Deep dive

A compact constructor cannot assign component fields directly, such as `this.value = ...`. It should update the parameter variable or validate it. After the constructor body, Java performs the component field assignment.

#### Production angle

Compact constructors are useful for small value objects, request models and command objects. They keep invalid values from spreading deeper into services.

#### Traps / caveats

- Keep constructor logic small and deterministic.
- Avoid database calls, remote calls or heavy business workflows in constructors.
- Do not throw checked exceptions from compact constructors for ordinary validation.

#### Optional Anki

Q: What is the main use of a compact record constructor?
A: Validation and normalization of component values.

</details>

<a id="rg-rec-006"></a>

<details>
<summary><strong>RG-REC-006. Can a record constructor validate or normalize component values?</strong></summary>

#### Short answer

Yes. A record constructor can reject invalid values or normalize parameters before the component fields are assigned.

#### Interview answer

Record constructors are a good place for invariant checks. You can reject `null`, trim strings, normalize case, copy collections or check a range before the record instance is created.

For example, `record PageRequest(int page, int size)` can reject negative pages and cap size to a service limit. That keeps the record valid everywhere it is used.

#### Deep dive

Normalization should not surprise callers. A record remains transparent: the component values after construction define the object. If normalization hides a lot of business meaning, a named factory or regular class may be clearer.

#### Production angle

Validation in records catches bad input close to API boundaries and makes command/event objects safer. For external request validation, coordinate constructor validation with Bean Validation so error handling remains user-friendly.

#### Traps / caveats

- `Objects.requireNonNull()` is useful but does not replace domain validation.
- Avoid expensive side effects in constructors.
- Normalize before defensive copying when the copy depends on normalized values.

#### Optional Anki

Q: Can a record normalize constructor parameters?
A: Yes, by assigning normalized values to the constructor parameters before field assignment.

</details>

<a id="rg-rec-007"></a>

<details>
<summary><strong>RG-REC-007. What restrictions apply to record constructors and instance fields?</strong></summary>

#### Short answer

Records cannot declare extra instance fields, and every noncanonical constructor must begin by delegating to another constructor with `this(...)`.

#### Interview answer

A record's instance state is exactly its components. You cannot add extra non-static fields to store hidden mutable state or caches. The canonical constructor initializes all components, and any noncanonical overloaded constructor must call `this(...)` as its first statement.

The canonical constructor cannot be less accessible than the record itself. A public record cannot hide its canonical constructor as private.

#### Deep dive

These restrictions preserve the record model: the visible component list describes the complete instance state. Static fields and methods are allowed because they are not per-instance state.

#### Production angle

This is why records are poor for models that need lazy fields, ORM-managed state, lifecycle flags or hidden caches. A regular class gives more control over representation.

#### Traps / caveats

- A record field for a mutable component is final only as a reference.
- A compact constructor cannot assign `this.component` directly.
- Overloaded constructors must delegate to the canonical constructor.

#### Optional Anki

Q: Can a record declare extra instance fields?
A: No. Its instance state is limited to record components.

</details>

<a id="rg-rec-008"></a>

<details>
<summary><strong>RG-REC-008. Can records declare extra methods, static members and nested types?</strong></summary>

#### Short answer

Yes. Records can declare instance methods, static fields, static methods and nested classes, records or enums.

#### Interview answer

Records are not just empty data bags. They can include behavior derived from their components, validation helpers, static factories and nested helper types.

For example, `record Money(BigDecimal amount, Currency currency)` can have `plus(Money other)` or `isZero()` methods. That often makes records useful for small domain value objects.

#### Deep dive

The main limitation is instance state. Extra methods must work from components or local values. Static members are allowed because they do not change the per-instance record shape.

#### Production angle

Adding small behavior to records can avoid anemic DTO-style code. But if behavior needs collaborators, persistence access or complex state transitions, move it to a service, aggregate or regular class.

#### Traps / caveats

- Do not put service orchestration into records.
- Avoid expensive work in accessors.
- Static mutable fields can still create thread-safety problems.

#### Optional Anki

Q: Can records have methods?
A: Yes, as long as extra instance state is not added.

</details>

<a id="rg-rec-009"></a>

<details>
<summary><strong>RG-REC-009. Can records extend classes or be extended by other classes?</strong></summary>

#### Short answer

No. Records implicitly extend `java.lang.Record` and are implicitly final.

#### Interview answer

A record cannot extend an arbitrary class, because it already extends `java.lang.Record`. It also cannot be extended by another class because records are final.

This supports the value-carrier model: record equality and state are fixed by the component list, and subclassing would make those semantics much harder to reason about.

#### Deep dive

Records can implement interfaces, including sealed interfaces. That is the normal way to combine records with polymorphism.

#### Production angle

Use interfaces or sealed hierarchies when you need variants. Use regular classes if your model genuinely depends on inheritance or framework subclass proxies.

#### Traps / caveats

- Hibernate-style lazy proxies are one reason records do not fit normal entity usage.
- A record cannot be abstract.
- Do not model record variation with inheritance; use composition or interfaces.

#### Optional Anki

Q: What class does every record extend?
A: `java.lang.Record`.

</details>

<a id="rg-rec-010"></a>

<details>
<summary><strong>RG-REC-010. Can records implement interfaces and participate in sealed hierarchies?</strong></summary>

#### Short answer

Yes. Records can implement interfaces and are often useful as concrete variants of sealed interfaces.

#### Interview answer

A record can implement ordinary interfaces such as `Comparable`, marker interfaces such as `Serializable`, or a sealed interface representing a closed set of alternatives.

For example:

```java
sealed interface PaymentResult permits Approved, Declined {}
record Approved(String authorizationId) implements PaymentResult {}
record Declined(String reason) implements PaymentResult {}
```

This models variants with different data cleanly.

#### Deep dive

Records are final, so they are natural leaves in sealed hierarchies. Combined with pattern matching, this can make business-result handling more exhaustive and explicit.

#### Production angle

This is useful for command results, domain events, validation outcomes and error models where the set of cases is intentionally limited.

#### Traps / caveats

- Sealed hierarchies are too restrictive for plugin-style extension points.
- Persisted or serialized variants need compatibility planning.
- Do not use sealed records only because they are modern; use them when closed alternatives are real.

#### Optional Anki

Q: Why do records fit sealed hierarchies well?
A: They are final concrete data-carrying variants.

</details>

<a id="rg-rec-011"></a>

<details>
<summary><strong>🧠 RG-REC-011. How do record patterns and pattern matching interact with records?</strong></summary>

#### Short answer

Record patterns let code match a record and deconstruct its components directly in pattern-matching contexts.

#### Interview answer

Record patterns extend pattern matching from just testing a type to also extracting record components. Instead of checking a record type and then calling accessors manually, a pattern can bind component values in one expression.

This works especially well with sealed interfaces where each variant is a record. The code can switch over a closed result type and handle each record shape explicitly.

#### Deep dive

Record patterns were finalized in Java 21. They are useful when the record shape is part of the domain model and deconstruction makes the code clearer. They are less useful if the code becomes a large procedural type switch that should be polymorphic.

#### Production angle

Pattern matching can make error/result handling concise in modern Java services, but teams need a consistent Java baseline and style rules before relying heavily on it.

#### Traps / caveats

- This is Java-version-sensitive.
- Pattern matching does not replace domain behavior.
- Large nested patterns can become harder to read than named methods.

#### Optional Anki

Q: What do record patterns add?
A: They allow matching a record and binding its components directly.

</details>

<a id="rg-rec-012"></a>

<details>
<summary><strong>RG-REC-012. When should you use or avoid a record instead of a regular class?</strong></summary>

#### Short answer

Use a record for transparent value-like data. Avoid it when identity, hidden state, mutation, inheritance or complex lifecycle matters.

#### Interview answer

I use records when the type is mainly defined by a fixed set of values: DTOs, projections, commands, events, small value objects or compound keys. The record header should be enough to understand the state.

I avoid records for JPA entities, mutable workflows, lazy-loaded models, large behavior-rich aggregates, framework-proxied classes and public APIs where component evolution would be painful.

#### Deep dive

Records reduce boilerplate but also constrain design. Those constraints are valuable when they match the model and harmful when they fight it.

#### Production angle

In backend services, records are often best at boundaries and in immutable internal messages. Domain entities and persistence models should be evaluated separately instead of converted mechanically.

#### Traps / caveats

- Do not use records only because they are shorter.
- Do not expose persistence details through record components.
- Check serialization, validation and Java version compatibility.

#### Optional Anki

Q: Main design test for records?
A: Whether the visible components intentionally define the whole value.

</details>
