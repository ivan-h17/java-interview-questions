# 09.02. Records equality, immutability and value semantics

---

<a id="rg-eq-001"></a>

<details>
<summary><strong>RG-EQ-001. How do record-generated `equals()`, `hashCode()` and `toString()` work?</strong></summary>

#### Short answer

They are generated from all record components and treat the record as a component-based value.

#### Interview answer

For a record, Java generates `equals()`, `hashCode()` and `toString()` based on the component list. Two records of the same record type are equal when their corresponding component values are equal.

This is convenient for DTOs, value objects and map keys because the equality logic matches the visible state in the record header.

#### Deep dive

The generated `equals()` is type-specific. Two different record classes with identical component values are not equal. Component equality follows normal Java equality rules, so arrays use reference equality unless you override the generated methods.

#### Production angle

Generated equality reduces boilerplate bugs, but you must choose components carefully. A component that changes over time, contains mutable state or includes sensitive data can affect equality, hashing and logs.

#### Traps / caveats

- Arrays are compared by reference by default.
- Generated `toString()` can expose secrets or PII.
- Overriding only one of `equals()` or `hashCode()` breaks the contract.

#### Optional Anki

Q: What fields do record-generated equality methods use?
A: All record components.

</details>

<a id="rg-eq-002"></a>

<details>
<summary><strong>RG-EQ-002. Are Java records deeply immutable?</strong></summary>

#### Short answer

No. Records are shallowly immutable by default because component fields are final, but referenced objects may still be mutable.

#### Interview answer

A record prevents reassignment of component fields after construction, but it does not freeze the object graph. `record Order(List<Item> items)` has a final `items` reference, yet the list contents can change if the same mutable list is shared.

Deep immutability requires immutable component types or defensive copies of mutable components.

#### Deep dive

This distinction matters because records look immutable at first glance. If a component is a mutable collection, array, `Date`, entity or custom mutable object, the record can still change observably through that component.

#### Production angle

For request DTOs and internal messages, shallow immutability may be enough only when components are themselves safe. For cache keys, events and domain values, mutable components are a serious correctness risk.

#### Traps / caveats

- `final` protects the reference, not the referenced object.
- `Collections.unmodifiableList()` may still be a live view.
- Mutable elements inside an immutable list can still mutate.

#### Optional Anki

Q: Are records deeply immutable by default?
A: No. They are only shallowly immutable by default.

</details>

<a id="rg-eq-003"></a>

<details>
<summary><strong>RG-EQ-003. How should records handle mutable components such as collections, dates or arrays?</strong></summary>

#### Short answer

Copy mutable inputs in the constructor and avoid exposing mutable internals through accessors.

#### Interview answer

For mutable components, a record should take ownership of its state. For collections, use `List.copyOf()`, `Set.copyOf()` or `Map.copyOf()` when a shallow immutable copy is enough. For arrays and old date types, copy on input and copy again on output.

For example, `record Team(List<String> members)` should usually store `List.copyOf(members)`.

#### Deep dive

Copying protects the collection structure but not necessarily mutable elements. If elements are mutable, you need immutable element types, element copies or a clear ownership rule.

#### Production angle

This prevents subtle bugs in cache keys, deduplication, audit events and async pipelines where another layer mutates the input after record construction.

#### Traps / caveats

- `Date` is mutable; prefer `Instant` or `LocalDate` where possible.
- Arrays need special care because accessors expose the actual array unless overridden.
- Defensive copying large graphs can be expensive.

#### Optional Anki

Q: How do you protect a record collection component?
A: Copy it in the constructor, often with `List.copyOf()`.

</details>

<a id="rg-eq-004"></a>

<details>
<summary><strong>RG-EQ-004. Why are arrays dangerous as record components?</strong></summary>

#### Short answer

Arrays are mutable and use reference-based `equals()` and `hashCode()` by default.

#### Interview answer

An array component creates two problems. First, callers can mutate the array contents unless the record copies it and hides the stored array. Second, generated record equality compares the array reference, not the array contents.

So two records containing equal array contents may not be equal, while one record's observable contents may change after construction.

#### Deep dive

To support array content equality, you would need custom `equals()`, `hashCode()` and likely `toString()` using `Arrays.equals()`, `Arrays.hashCode()` and `Arrays.toString()` or deep variants.

#### Production angle

Array components are risky for map keys, cache keys, signatures, serialized payloads and tests that expect value equality. Prefer lists or dedicated immutable value types.

#### Traps / caveats

- Cloning only in the constructor is not enough if the accessor returns the stored array.
- Overriding equality for arrays must keep `hashCode()` consistent.
- Arrays of mutable elements still have mutable element state.

#### Optional Anki

Q: Why do arrays break intuitive record equality?
A: Array `equals()` compares references, not contents.

</details>

<a id="rg-eq-005"></a>

<details>
<summary><strong>RG-EQ-005. How can defensive copying make a record safer?</strong></summary>

#### Short answer

Defensive copying prevents callers from mutating the record's internal state through shared mutable objects.

#### Interview answer

When a record receives a mutable object, it can store a safe copy instead of the caller's original reference. For mutable outputs, the accessor can return a copy so callers cannot mutate stored state.

For collections, `List.copyOf()` is often enough for a shallow immutable snapshot. For arrays, clone on input and output.

#### Deep dive

Defensive copying should be deliberate. It protects ownership boundaries but can add allocation cost and may not protect mutable elements inside a collection.

#### Production angle

This is important for records used as cache keys, event payloads, async command objects and request models passed between layers.

#### Traps / caveats

- A shallow copy does not make mutable elements immutable.
- Copying huge lists on every call can hurt latency.
- Returning an unmodifiable view of a mutable backing list can still leak live changes.

#### Optional Anki

Q: What does defensive copying protect against?
A: Caller-side mutation of objects stored inside the record.

</details>

<a id="rg-eq-006"></a>

<details>
<summary><strong>RG-EQ-006. Can you use a record as a `HashMap` key?</strong></summary>

#### Short answer

Yes, records can be good `HashMap` keys when all components used for equality are stable and safely immutable.

#### Interview answer

Records often work well as compound keys because they generate `equals()` and `hashCode()` from components. For example, `record UserRegionKey(long userId, String region)` is much clearer than concatenating strings.

The key requirement is stability. Once inserted into a hash-based collection, the values that affect equality and hash code must not change.

#### Deep dive

If all components are immutable values such as strings, primitives, enums and `java.time` types, the record is usually safe. Mutable components require copying or a different key design.

#### Production angle

Records are useful for cache keys, deduplication keys, grouping keys and lookup maps. Stable key design prevents hard-to-debug missing entries.

#### Traps / caveats

- Avoid arrays as record key components unless equality is customized carefully.
- Avoid entity objects as key components if their identity changes.
- Generated `hashCode()` includes every component.

#### Optional Anki

Q: When is a record safe as a `HashMap` key?
A: When its equality-relevant components are stable and immutable enough.

</details>

<a id="rg-eq-007"></a>

<details>
<summary><strong>RG-EQ-007. What can go wrong if a record key contains mutable components?</strong></summary>

#### Short answer

If a component changes after insertion, the key's hash code or equality can change, so map lookups may fail.

#### Interview answer

Hash-based maps choose a bucket from the key's hash code. If a record key contains a mutable list and that list changes, the record's `hashCode()` can change. The map still stores the entry in the old bucket, but lookup uses the new hash and may not find it.

This creates bugs where the key appears equal in logs but the map cannot retrieve the value.

#### Deep dive

Even if the hash code does not change, equality changes can break deduplication and set membership semantics. Arrays add another trap because their default equality is reference-based.

#### Production angle

This can break caches, idempotency keys, aggregation maps and in-memory indexes. It is often diagnosed only after inspecting mutations around insertion time.

#### Traps / caveats

- Unmodifiable wrappers are not always immutable snapshots.
- Mutating nested elements can be enough to break equality.
- Logging `toString()` may not reveal reference-equality traps.

#### Optional Anki

Q: Why do mutable map keys break hash maps?
A: Their hash code or equality can change after insertion.

</details>

<a id="rg-eq-008"></a>

<details>
<summary><strong>RG-EQ-008. When should you override record accessors or generated methods?</strong></summary>

#### Short answer

Override them only when the generated behavior is wrong for the record contract, and keep the contract consistent.

#### Interview answer

Common reasons are defensive copying in an accessor, hiding sensitive values from `toString()`, or handling array equality with content-based logic.

Be careful with `equals()` and `hashCode()`. If you override them, they must remain consistent with each other and with the record's intended value semantics.

#### Deep dive

Overriding accessors to perform heavy calculations or side effects violates expectations. Accessors should be cheap and unsurprising because callers treat them like simple component reads.

#### Production angle

Custom `toString()` is often needed when records contain passwords, tokens, personal data or large payloads. Custom equality should be rare and reviewed carefully.

#### Traps / caveats

- Do not make accessors perform remote calls.
- Do not hide mutable internal state through only constructor copies; accessors may need copies too.
- Do not override equality to ignore components unless the record still has a clear value identity.

#### Optional Anki

Q: What is a common safe reason to override a record accessor?
A: Returning a defensive copy of a mutable component.

</details>

<a id="rg-eq-009"></a>

<details>
<summary><strong>RG-EQ-009. What is the relationship between records and value objects?</strong></summary>

#### Short answer

Records are often a good implementation tool for value objects, but not every record is a domain value object.

#### Interview answer

A value object is defined by its value rather than identity. Records support this naturally with component-based equality and final fields. `record EmailAddress(String value)` can be a good value object if it validates the email and protects invariants.

But a record used as a DTO is just a data contract. It becomes a value object only when it expresses a meaningful domain concept with valid operations and invariants.

#### Deep dive

Records can have behavior, so they do not have to be anemic. A `Money` record can validate currency and implement arithmetic. Still, if the domain concept needs hidden state or lifecycle transitions, a regular class may fit better.

#### Production angle

Records can reduce duplicated validation and make APIs more type-safe, for example replacing raw strings with `EmailAddress`, `UserId` or `CurrencyCode` records.

#### Traps / caveats

- A record with no validation may only be a typed tuple.
- Do not expose persistence identifiers or ORM details through value object records blindly.
- Avoid generic `Pair` records in domain code when names matter.

#### Optional Anki

Q: Are all records value objects?
A: No. Records can implement value objects, but many records are only DTOs.

</details>

<a id="rg-eq-010"></a>

<details>
<summary><strong>RG-EQ-010. Why are records usually a poor fit for lifecycle-based entities?</strong></summary>

#### Short answer

Entities have stable identity and lifecycle changes, while records are final transparent values defined by their components.

#### Interview answer

A JPA or domain entity often changes state over time: status, version, associations and audit fields. Its identity may be a database ID or business key, not all current fields. Records, by default, make equality depend on all components and cannot be proxied or mutated like typical ORM entities.

That mismatch makes records risky as entities.

#### Deep dive

Records can represent snapshots or projections of entities, but the entity itself usually needs controlled mutation, persistence lifecycle hooks, lazy loading support and identity rules that do not map cleanly to record components.

#### Production angle

Using records as entities can break dirty checking, lazy loading, generated IDs, framework requirements and equality semantics. Use records for entity projections, commands and events instead.

#### Traps / caveats

- Do not confuse an immutable snapshot with an entity.
- A generated database ID can make equality unstable before persistence.
- ORM proxies typically require non-final classes and no-arg constructors.

#### Optional Anki

Q: Why do records usually not fit entities?
A: Entities need identity and lifecycle semantics beyond component values.

</details>

<a id="rg-eq-011"></a>

<details>
<summary><strong>RG-EQ-011. How should records be designed for stable equality over time?</strong></summary>

#### Short answer

Choose only stable, immutable-enough components that truly define the value.

#### Interview answer

A record's equality should remain valid for the lifetime of the object. That means avoiding mutable collections, arrays, generated IDs that change later, timestamps that are adjusted after creation, or references to entities with unstable equality.

If a component is mutable, copy it. If a concept has identity independent of current fields, consider a regular class instead.

#### Deep dive

Stable equality is also about domain meaning. If changing a field should not make it a different value, that field probably should not be a record component or the type is not a good record candidate.

#### Production angle

Stable equality protects hash maps, sets, caches, deduplication stores and idempotency logic.

#### Traps / caveats

- Including volatile metadata in a key record can break cache reuse.
- Including mutable lists can break lookups after mutation.
- Ignoring fields in custom equality can make the record misleading.

#### Optional Anki

Q: What should record equality be based on?
A: Stable components that truly define the value.

</details>

<a id="rg-eq-012"></a>

<details>
<summary><strong>RG-EQ-012. How can records reduce boilerplate but still lead to an anemic model?</strong></summary>

#### Short answer

Records remove data-class boilerplate, but domain behavior can still be misplaced into services if records only carry data.

#### Interview answer

A record can be a good domain value object when it contains validation and meaningful behavior. But if every domain concept becomes a record with only fields, and all rules live in procedural service methods, the model can become anemic.

The question is not "record or class"; it is whether the design keeps invariants and behavior near the domain concept.

#### Deep dive

For simple CRUD and boundary DTOs, data carriers are fine. For rich business rules, records should either contain appropriate value behavior or be limited to commands, events and snapshots around a richer model.

#### Production angle

Anemic models often create duplicated validation, inconsistent transitions and fragile services that manipulate raw state directly.

#### Traps / caveats

- Records are not automatically bad domain models.
- Boilerplate reduction is not the same as good modeling.
- Avoid generic tuple records when named domain types would clarify intent.

#### Optional Anki

Q: Can records cause anemic modeling?
A: Yes, if they are used only as passive data while domain rules live elsewhere.

</details>
