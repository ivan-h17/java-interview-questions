# 09.08. Performance, readability and anti-patterns

---

<a id="rg-smell-001"></a>

<details>
<summary><strong>RG-SMELL-001. Can records improve performance compared with regular classes?</strong></summary>

#### Short answer

Not automatically. Records mainly improve clarity and boilerplate; performance is usually similar to equivalent final classes.

#### Interview answer

A record is still an object. If a record and a regular class have the same fields and behavior, they usually have similar allocation and memory characteristics.

Records may indirectly help performance by encouraging small immutable DTOs and simpler code, but they are not a magic optimization.

#### Deep dive

The JVM can optimize ordinary classes and records. Future JVM features may change value-object performance, but today's records should be chosen for modeling, not assumed memory savings.

#### Production angle

Measure allocation rate, GC pressure and CPU with profiling tools before claiming records made code faster.

#### Traps / caveats

- Do not use records as a performance hack.
- Generated methods can still be expensive if components are large.
- Better modeling can improve maintainability even without speed gains.

#### Optional Anki

Q: Do records automatically make objects faster?
A: No.

</details>

<a id="rg-smell-002"></a>

<details>
<summary><strong>RG-SMELL-002. Do records automatically reduce memory usage?</strong></summary>

#### Short answer

No. A record is a normal object with fields for its components.

#### Interview answer

Records remove source-code boilerplate, not object headers, references or component storage. A record with the same fields as a final class normally has similar memory usage.

Memory use depends more on number of objects, field types, object graph shape, boxing and collection choices.

#### Deep dive

A record containing a large list does not copy or compress that list unless you explicitly do so. If you create many short-lived records, allocation rate can still be high.

#### Production angle

Use memory profilers or allocation tracking. Optimizing DTO memory often means reducing graph size, avoiding unnecessary boxing or streaming results instead of changing classes to records.

#### Traps / caveats

- Boilerplate reduction is not memory reduction.
- Defensive copies can increase memory use.
- Generated `toString()` on large graphs can be costly.

#### Optional Anki

Q: What do records reduce by default?
A: Source-code boilerplate, not object memory.

</details>

<a id="rg-smell-003"></a>

<details>
<summary><strong>🧠 RG-SMELL-003. Can escape analysis optimize short-lived record allocations?</strong></summary>

#### Short answer

Sometimes. The JIT may eliminate or scalar-replace short-lived allocations that do not escape.

#### Interview answer

Escape analysis lets the JVM determine whether an object is visible outside a local scope. If a short-lived record is only used inside a method, the JIT may avoid allocating it as a real heap object.

This is not guaranteed source-level behavior; it depends on JVM, code shape and runtime optimization.

#### Deep dive

Records can be convenient temporary carriers, but the same optimization can apply to regular objects. Do not rely on it for correctness or blindly assume it always happens.

#### Production angle

If allocation rate matters, verify with JFR, allocation profiling or benchmarking. Microbenchmarks must be written carefully to avoid misleading dead-code elimination.

#### Traps / caveats

- Escape analysis is an optimization, not a language guarantee.
- Logging, storing or returning an object usually makes it escape.
- Records are not value types.

#### Optional Anki

Q: What can escape analysis do?
A: Eliminate or scalar-replace some non-escaping allocations.

</details>

<a id="rg-smell-004"></a>

<details>
<summary><strong>RG-SMELL-004. How can boxing in generic collections hurt performance?</strong></summary>

#### Short answer

Boxing stores primitives as wrapper objects, adding allocation, memory and sometimes null-related overhead.

#### Interview answer

Generic collections cannot store primitives directly, so `List<Integer>` stores `Integer` objects. In hot numeric paths, this can create many objects and extra indirection compared with `int[]`, `IntStream` or primitive-specialized collections.

It can also introduce unboxing `NullPointerException` if a wrapper is unexpectedly null.

#### Deep dive

Boxing overhead is often irrelevant next to database or network latency. It becomes important in CPU-heavy loops, parsing, aggregation, metrics and high-volume data processing.

#### Production angle

Use profilers to find allocation sources. If boxed numbers dominate, consider primitive arrays, primitive streams or specialized libraries.

#### Traps / caveats

- Do not optimize boxed collections without evidence.
- `Integer` identity comparison with `==` is a bug source.
- Primitive streams are not always more readable.

#### Optional Anki

Q: Why can `List<Integer>` allocate more than `int[]`?
A: It stores boxed `Integer` objects.

</details>

<a id="rg-smell-005"></a>

<details>
<summary><strong>RG-SMELL-005. How can large immutable record graphs create memory pressure?</strong></summary>

#### Short answer

Immutable updates and defensive copies can create many short-lived objects or duplicate large structures.

#### Interview answer

A record graph is still an object graph. If every small change creates copied records and copied collections, allocation rate can rise. Defensive copying of large lists or nested structures can also duplicate data.

Immutability improves reasoning, but it has memory trade-offs.

#### Deep dive

Structural sharing, pagination, streaming, builders or controlled local mutation can reduce copying in hot paths.

#### Production angle

This matters for large API responses, batch jobs, ETL pipelines and cache snapshots. Watch allocation rate, GC pauses and retained heap.

#### Traps / caveats

- Do not deep-copy large graphs blindly.
- Immutable wrappers do not shrink data.
- Caching large immutable graphs can retain more memory than expected.

#### Optional Anki

Q: Main memory risk of immutable record graphs?
A: Extra allocation and copying.

</details>

<a id="rg-smell-006"></a>

<details>
<summary><strong>RG-SMELL-006. How can overly generic APIs hide business intent?</strong></summary>

#### Short answer

They replace domain vocabulary with abstract type parameters, making behavior harder to understand and validate.

#### Interview answer

An API like `process(T input, Context<C> context)` may be reusable but says little about the business rule. A method such as `approveOrder(ApproveOrderCommand command)` communicates intent, invariants and ownership much better.

Generics are good for reusable infrastructure, but domain code needs names.

#### Deep dive

Over-generic APIs often grow flags, callbacks and special-case hooks. This is a sign the abstraction is trying to cover unrelated use cases.

#### Production angle

Hidden business intent leads to accidental reuse, weaker tests and bugs when a domain-specific rule is skipped.

#### Traps / caveats

- Do not confuse fewer lines with clearer design.
- Shared generic services can become dumping grounds.
- Use domain records/classes when names carry meaning.

#### Optional Anki

Q: What can generic APIs hide?
A: Domain intent and invariants.

</details>

<a id="rg-smell-007"></a>

<details>
<summary><strong>RG-SMELL-007. When should you replace complex generics with a simpler domain type?</strong></summary>

#### Short answer

When the generic signature is harder to understand than the business concept it represents.

#### Interview answer

If a method has several bounds, nested wildcards and a signature only one developer understands, step back. A named domain type such as `OrderSearchCriteria`, `PriceRange` or `ValidationResult` may communicate the model better.

Types are documentation and constraints. A domain type can hold validation and behavior that generic containers cannot express.

#### Deep dive

Complex generics are justified in libraries where many callers benefit. In application code, the cost is often not worth it.

#### Production angle

Simpler domain types improve logging, metrics, validation, API docs and onboarding.

#### Traps / caveats

- Do not create generic tuple wrappers for meaningful concepts.
- Do not preserve a bad abstraction just because it is reusable.
- Keep advanced generics near infrastructure boundaries.

#### Optional Anki

Q: When is a domain type better than a generic signature?
A: When it expresses business meaning more clearly.

</details>

<a id="rg-smell-008"></a>

<details>
<summary><strong>RG-SMELL-008. Why are <code>Map&lt;String, Object&gt;</code>, <code>Pair</code> and generic tuple records often code smells?</strong></summary>

#### Short answer

They hide meaning, weaken type safety and make contracts implicit.

#### Interview answer

`Map<String, Object>` forces callers to know magic keys and cast values. `Pair` or `Tuple` forces callers to remember what `left` and `right` mean. A named record such as `PriceRange(min, max)` or `UserRole(userId, role)` is clearer and safer.

These generic containers are acceptable for local glue code, but risky as domain or API contracts.

#### Deep dive

The problem is not the data shape; it is unnamed meaning. Named types make validation, serialization and documentation stronger.

#### Production angle

Typed records reduce runtime casts, client confusion, broken JSON contracts and accidental key mismatches.

#### Traps / caveats

- `Map<String, Object>` may be acceptable for truly dynamic metadata.
- `Pair` can be fine inside a small local transformation.
- Do not expose tuple-like structures in public APIs without strong reason.

#### Optional Anki

Q: Why is `Pair` often weaker than a named record?
A: It hides the meaning of its fields.

</details>

<a id="rg-smell-009"></a>

<details>
<summary><strong>RG-SMELL-009. Why is suppressing unchecked warnings globally dangerous?</strong></summary>

#### Short answer

It hides all unsafe generic operations in a broad scope, including future real bugs.

#### Interview answer

`@SuppressWarnings("unchecked")` should be used at the smallest possible scope after you understand why the cast is safe. Putting it on a class or package can hide unrelated unchecked operations added later.

Unchecked warnings are often the only compiler signal that type safety has been weakened.

#### Deep dive

Good practice is to isolate unsafe casts in boundary methods and add a short explanation of the invariant, especially around legacy APIs, reflection or deserialization.

#### Production angle

Broad suppression makes `ClassCastException` bugs harder to trace because the unsafe source is no longer visible during review.

#### Traps / caveats

- A suppression is not validation.
- Suppressions should not replace better generic signatures.
- Treat new unchecked warnings as review items.

#### Optional Anki

Q: Where should unchecked warning suppression live?
A: At the smallest justified scope.

</details>

<details>
<summary><strong>🧠 RG-SMELL-010. Why is reflection-based mutation of records dangerous?</strong></summary>

#### Short answer

It violates record and final-field assumptions, making code fragile, non-portable and hard to reason about.

#### Interview answer

Records are designed as transparent final-state carriers. Trying to mutate their component fields through reflection, `Unsafe` or similar mechanisms breaks the mental model and may violate JVM optimization assumptions.

It can also fail under newer Java access rules, modules, security settings or framework changes.

#### Deep dive

Even if a hack works on one runtime, it may not be reliable across JDK versions, JVM flags or deployment environments. It can also break hash-based collections if the record is used as a key.

#### Production angle

Use constructors, factories, mappers or copy methods instead. Reflection mutation of records is a sign the type is wrong for the framework or workflow.

#### Traps / caveats

- Final-field mutation can create visibility and correctness surprises.
- Mutating a record key can break maps and sets.
- Framework hacks may fail after Java upgrades.

#### Optional Anki

Q: What should replace reflection mutation of records?
A: Constructors, factories, mappers or regular mutable classes.

</details>
