# Performance, reliability and operational trade-offs

---

<a id="ms-perf-001"></a>

<details>
<summary><strong>MS-PERF-001. How do you investigate high latency in a microservice system?</strong></summary>

#### Short answer

Start from user-impact metrics, then use traces, dependency metrics, logs, and recent changes to isolate the bottleneck.

#### Interview answer

Check whether latency is global or limited to one endpoint, tenant, region, or version. Use traces to find slow spans, then inspect CPU, GC, database queries, connection pools, queues, and downstream services. Compare with recent deployments or traffic spikes.

#### Deep dive

High latency is often saturation: a pool, queue, lock, CPU, database, or dependency is over capacity.

#### Production angle

Mitigate while investigating: reduce traffic, roll back, disable a feature, shed load, or increase capacity if the bottleneck is known.

#### Traps / caveats

- Do not optimize code before finding the slow resource.
- Average latency hides p99 user pain.

</details>

<a id="ms-perf-002"></a>

<details>
<summary><strong>MS-PERF-002. How do you identify whether latency is caused by CPU, database, network or downstream services?</strong></summary>

#### Short answer

Correlate traces with host metrics, JVM metrics, database metrics, and per-dependency timings.

#### Interview answer

CPU-bound latency shows high CPU and hot methods. Database latency shows slow queries, locks, pool wait, or high DB load. Network/downstream latency appears in client spans and timeout metrics. Thread dumps and pool metrics help identify blocking.

#### Deep dive

Latency can be layered: a service may look slow because it is waiting for the database, which is slow because of locks or IO.

#### Production angle

Use dependency-level dashboards so the service owner does not guess from aggregate API latency.

#### Traps / caveats

- Low CPU with high latency often means blocking or waiting.
- Database connection wait is a service-side symptom of database or pool pressure.

</details>

<a id="ms-perf-003"></a>

<details>
<summary><strong>MS-PERF-003. What is tail latency, and why does it matter in microservices?</strong></summary>

#### Short answer

Tail latency is high-percentile latency, such as p95 or p99, and it matters because users experience slow outliers.

#### Interview answer

In microservices, one request may call many dependencies. Even if each dependency is usually fast, the chance of at least one slow call increases with fan-out. Tail latency becomes the user-visible latency.

#### Deep dive

Averages hide outliers. p99 latency often reveals saturation, GC pauses, lock contention, slow queries, or noisy neighbors.

#### Production angle

SLOs should use percentiles and error rates, not only average response time.

#### Traps / caveats

- Optimizing median latency may not improve user complaints.
- High p99 can come from retries and queueing, not only slow code.

</details>

<a id="ms-perf-004"></a>

<details>
<summary><strong>MS-PERF-004. How does fan-out amplify latency and failure probability?</strong></summary>

#### Short answer

The more dependencies a request needs, the more likely one will be slow or fail.

#### Interview answer

If a request calls ten services, the total response depends on all required calls. Parallel fan-out is limited by the slowest required call. Sequential fan-out adds latencies. Availability also multiplies: many dependencies reduce the chance that all are healthy.

#### Deep dive

Fan-out also increases load on downstream systems and can create correlated failures during retries.

#### Production angle

Track fan-out per endpoint and dependency contribution to p95/p99 latency.

#### Traps / caveats

- Parallelizing calls does not remove dependency failure probability.
- Optional dependencies should have separate timeouts and fallback behavior.

</details>

<a id="ms-perf-005"></a>

<details>
<summary><strong>MS-PERF-005. How do you reduce fan-out in a request path?</strong></summary>

#### Short answer

Use better boundaries, coarser APIs, batching, caching, read models, and asynchronous processing.

#### Interview answer

If one endpoint calls many services, ask whether the data should be precomputed or owned differently. Read-heavy composed views can use projections. Repeated remote lookups can be batched or cached. Non-critical work can move out of the request path.

#### Deep dive

Fan-out reduction often starts with domain design, not only code optimization.

#### Production angle

Reducing fan-out improves latency, availability, and incident blast radius.

#### Traps / caveats

- Do not cache sensitive or rapidly changing data without invalidation policy.
- Do not build a read model without monitoring projection lag.

</details>

<a id="ms-perf-006"></a>

<details>
<summary><strong>MS-PERF-006. What is resource isolation?</strong></summary>

#### Short answer

Resource isolation separates capacity so one workload, tenant, or dependency cannot consume everything.

#### Interview answer

Examples include separate thread pools per dependency, queue limits per work type, database pools, tenant quotas, CPU/memory limits, and priority queues. Isolation turns one failure into a contained degradation instead of total service failure.

#### Deep dive

Isolation is the practical goal behind bulkheads, quotas, and workload separation.

#### Production angle

Resource isolation makes overload behavior predictable and easier to operate.

#### Traps / caveats

- Over-isolation can waste capacity.
- Noisy background jobs need isolation from user-facing traffic.

</details>

<a id="ms-perf-007"></a>

<details>
<summary><strong>MS-PERF-007. How do CPU, memory, thread pools and connection pools affect reliability?</strong></summary>

#### Short answer

They are finite resources; saturation turns normal latency into timeouts and cascading failures.

#### Interview answer

High CPU delays work. Memory pressure causes GC pauses or OOMs. Thread pool exhaustion prevents requests from running. Connection pool exhaustion blocks database or HTTP calls. Reliability depends on keeping these resources bounded and observable.

#### Deep dive

Saturation can be more dangerous than errors because requests keep waiting and consuming resources.

#### Production angle

Alert on saturation metrics before user-facing failures explode.

#### Traps / caveats

- Bigger pools can move the bottleneck downstream.
- Unbounded queues hide overload until recovery is harder.

</details>

<a id="ms-perf-008"></a>

<details>
<summary><strong>MS-PERF-008. How can one slow downstream service exhaust all threads in an upstream service?</strong></summary>

#### Short answer

Threads block waiting for the slow dependency until the upstream has no threads left to serve other requests.

#### Interview answer

In a blocking servlet service, each request uses a worker thread. If many requests call a slow downstream and wait too long, the worker pool fills. Then even endpoints unrelated to that downstream can stop responding.

#### Deep dive

Virtual threads reduce platform-thread exhaustion but do not remove downstream capacity, timeout, or connection pool limits.

#### Production angle

Use timeouts, dependency bulkheads, separate pools, circuit breakers, and load shedding.

#### Traps / caveats

- Increasing servlet threads can overload the downstream further.
- Async clients still need concurrency limits.

</details>

<a id="ms-perf-009"></a>

<details>
<summary><strong>MS-PERF-009. How do you set per-dependency concurrency limits?</strong></summary>

#### Short answer

Limit concurrent calls based on downstream capacity, latency, error rate, and caller resource budget.

#### Interview answer

Set separate limits for each dependency using semaphores, bulkheads, connection pools, or rate limiters. Critical dependencies may get larger budgets than optional ones. Limits should be adjusted with load testing and production telemetry.

#### Deep dive

The limit should protect both the caller and downstream. It is not just a performance tuning knob.

#### Production angle

Monitor rejections, queueing, latency, and downstream health to tune limits.

#### Traps / caveats

- Unlimited concurrency can collapse a dependency during spikes.
- Too low a limit can throttle healthy traffic unnecessarily.

</details>

<a id="ms-perf-019"></a>

<details>
<summary><strong>🧠 MS-PERF-019. How do error budgets influence release decisions?</strong></summary>

#### Short answer

Error budgets balance reliability and delivery speed by limiting risky changes when reliability has already degraded.

#### Interview answer

If a service has an SLO of 99.9%, the error budget is the allowed unreliability. When the budget is healthy, teams can release normally. When it is burned down, releases may be frozen or limited to reliability fixes.

#### Deep dive

Error budgets make reliability trade-offs explicit instead of relying on vague opinions.

#### Production angle

They help decide whether to continue a canary, pause feature rollout, or prioritize incident remediation.

#### Traps / caveats

- Error budgets require meaningful user-centered SLIs.
- They should guide decisions, not become a bureaucratic checkbox.

</details>
