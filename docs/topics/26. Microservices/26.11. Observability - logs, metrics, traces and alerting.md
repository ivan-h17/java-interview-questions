# Observability - logs, metrics, traces and alerting

---

<a id="ms-obs-001"></a>

<details>
<summary><strong>MS-OBS-001. How do you monitor a distributed system of microservices?</strong></summary>

#### Short answer

Use metrics, logs, traces, health checks, SLOs, and business-level signals across every critical service and dependency.

#### Interview answer

I would monitor request rate, latency, errors, saturation, dependency calls, queue lag, consumer failures, database pools, and business outcomes. Logs should be structured and correlated. Traces should show cross-service paths. Alerts should focus on user impact and SLO burn, not every internal warning.

#### Deep dive

Microservice monitoring must connect components into a system view. Per-service dashboards alone are not enough.

#### Production angle

During incidents, teams need to answer what changed, which path is affected, which dependency is slow, and which users are impacted.

#### Traps / caveats

- Do not rely only on logs; they are expensive and hard to aggregate under load.
- Do not alert on every low-level symptom without user impact.

</details>

<a id="ms-obs-003"></a>

<details>
<summary><strong>MS-OBS-003. Why is distributed tracing important in microservices?</strong></summary>

#### Short answer

Tracing connects a request's path across services so latency and failure causes can be located.

#### Interview answer

In a microservice system, one user request can pass through gateways, services, databases, and queues. Distributed tracing records spans across those boundaries, showing where time was spent and which dependency failed.

#### Deep dive

Traces are especially useful for fan-out, tail latency, partial failures, and version-specific regressions. They complement metrics and logs; they do not replace them.

#### Production angle

A good trace can reduce incident diagnosis from guesswork to a concrete slow span or failing dependency.

#### Traps / caveats

- Tracing without context propagation breaks at service boundaries.
- High-cardinality or over-sampled tracing can become expensive.

</details>

<a id="ms-obs-007"></a>

<details>
<summary><strong>MS-OBS-007. What is trace context propagation?</strong></summary>

#### Short answer

It is passing trace identifiers across service boundaries so spans can be linked into one trace.

#### Interview answer

When service A calls service B over HTTP or publishes a message, it should propagate trace context through headers or message metadata. The receiver creates child spans or linked spans so the whole workflow is observable.

#### Deep dive

Context propagation must cross HTTP clients, message producers, consumers, async executors, and sometimes scheduled jobs.

#### Production angle

Broken propagation creates isolated traces that make multi-service debugging much harder.

#### Traps / caveats

- Do not put sensitive user data into trace context.
- ThreadLocal-based context can be lost in async execution without instrumentation.

</details>

<a id="ms-obs-017"></a>

<details>
<summary><strong>MS-OBS-017. How do you design alerts for microservices?</strong></summary>

#### Short answer

Alert on user impact, SLO burn, critical dependency failures, and actionable saturation.

#### Interview answer

Good alerts tell an on-call engineer that something important is broken and where to start. For APIs, alert on elevated error rate, latency, or availability. For consumers, alert on processing delay, DLQ growth, and stuck workflows. Avoid noisy alerts for transient internal events.

#### Deep dive

Alerts should have severity, ownership, runbooks, and enough context to act.

#### Production angle

Symptom alerts catch unknown causes; cause alerts are useful when the cause is well understood and actionable.

#### Traps / caveats

- Do not alert on every exception if it does not affect users.
- Do not create alerts without an owner or runbook.

</details>

<a id="ms-obs-018"></a>

<details>
<summary><strong>MS-OBS-018. Why are symptom-based alerts better than cause-based alerts?</strong></summary>

#### Short answer

Symptoms capture user impact even when the root cause is unknown.

#### Interview answer

An alert like "checkout availability below SLO" is more important than "CPU high" because it reflects user harm. Cause alerts can support diagnosis, but symptom alerts prevent missing incidents caused by unexpected failure modes.

#### Deep dive

Cause-based alerts are useful for known, actionable problems such as disk almost full or certificate expiring. They should not replace SLO-based alerts.

#### Production angle

Symptom-based alerting reduces noise and focuses incident response on protecting users.

#### Traps / caveats

- Do not ignore saturation metrics; use them as diagnostic or predictive alerts.
- A symptom alert still needs labels or dashboards to identify likely causes.

</details>

<a id="ms-obs-020"></a>

<details>
<summary><strong>MS-OBS-020. How should structured logs be designed for multi-service debugging?</strong></summary>

#### Short answer

Use consistent fields such as timestamp, service, version, trace ID, correlation ID, user/tenant ID policy, operation, error category, and business ID.

#### Interview answer

Structured logs should be machine-queryable and consistent across services. They should include enough context to connect logs with traces and business operations, while avoiding sensitive data. Error logs should preserve cause and classification.

#### Deep dive

Use stable field names and avoid logging huge payloads. Logs should answer "what happened to order X?" without exposing private data.

#### Production angle

Good log fields speed incident triage and support audit investigations.

#### Traps / caveats

- Do not log tokens, passwords, raw PII, or full payment data.
- Do not use inconsistent correlation ID names across services.

</details>

---

<a id="ms-obs-021"></a>

<details>
<summary><strong>MS-OBS-021. What should not be logged?</strong></summary>

#### Short answer

Do not log secrets, credentials, tokens, private keys, raw PII, payment data, or sensitive payloads.

#### Interview answer

Logs often leave the service boundary and are stored in shared systems. Sensitive fields should be masked, hashed only when appropriate, or omitted. Authorization decisions and business IDs can be logged, but with a clear data classification policy.

#### Deep dive

Traces and metrics can also leak data through attributes and labels, not only logs.

#### Production angle

Unsafe logging creates security incidents, compliance risk, and costly data deletion work.

#### Traps / caveats

- Do not put user emails or tenant IDs into high-cardinality metrics without policy.
- Redaction should happen before data leaves the service when possible.

</details>

<a id="ms-obs-022"></a>

<details>
<summary><strong>MS-OBS-022. How do you debug a slow request across multiple services?</strong></summary>

#### Short answer

Start from the trace, identify the slow span, then correlate metrics, logs, deployment changes, and dependency health.

#### Interview answer

I would find an affected request by trace ID or business ID, inspect the critical path, and compare span timings. Then I would check whether the slowness is local CPU, database, lock, queue wait, network, or downstream service. Finally, I would look for recent deployments or traffic changes.

#### Deep dive

If tracing is missing, use gateway logs, correlation IDs, per-dependency metrics, and sampling from affected services.

#### Production angle

Mitigation may be rollback, disabling a feature, reducing traffic, increasing capacity, or shedding optional work.

#### Traps / caveats

- Do not jump to scaling before identifying the bottleneck.
- A slow upstream may only be waiting on an even slower downstream.

</details>

<a id="ms-obs-023"></a>

<details>
<summary><strong>MS-OBS-023. How do you identify the service causing latency in a distributed trace?</strong></summary>

#### Short answer

Look for spans with high duration, queue/wait time, repeated retries, or slow dependency calls.

#### Interview answer

A trace shows parent-child spans. I compare total request time with span durations and dependency calls. The culprit may be a service's own processing, its database query, an outbound call, or waiting for a resource like a thread or connection pool.

#### Deep dive

Be careful with parallel spans: the longest required parallel branch often controls response time, not the sum of all spans.

#### Production angle

Use trace data with service metrics to verify whether the issue is widespread or a single request anomaly.

#### Traps / caveats

- The service with the longest span may be waiting on another dependency.
- Missing instrumentation can hide the real slow operation.

</details>

<a id="ms-obs-024"></a>

<details>
<summary><strong>🧠 MS-OBS-024. How do you detect cascading failures from telemetry?</strong></summary>

#### Short answer

Look for latency, retry, saturation, and error signals spreading from one dependency to upstream services.

#### Interview answer

Signs include rising downstream latency, increasing in-flight calls, thread or connection pool saturation, retry volume spikes, circuit breakers opening, queue growth, and then upstream API errors. Traces show more time spent waiting on the failing dependency.

#### Deep dive

Cascades often start as slowness before hard errors appear, so saturation metrics are critical.

#### Production angle

Dashboards should show dependency graphs and propagation of impact across services.

#### Traps / caveats

- Error rate may stay low while latency and saturation are already dangerous.
- Retrying can make the original failure look like a traffic spike.

</details>

<a id="ms-obs-026"></a>

<details>
<summary><strong>🧠 MS-OBS-026. How do you instrument Java microservices with OpenTelemetry?</strong></summary>

#### Short answer

Use OpenTelemetry auto-instrumentation or SDKs to emit traces, metrics, and logs with consistent resource and context metadata.

#### Interview answer

For Spring Boot services, a Java agent or starter can instrument HTTP servers, clients, JDBC, messaging, and executors. Add manual spans for important business operations and propagate context through HTTP headers and message metadata.

#### Deep dive

Instrumentation should include service name, version, environment, endpoint, dependency, and safe business identifiers where appropriate.

#### Production angle

Sampling, attribute cardinality, exporter reliability, and collector capacity need operational tuning.

#### Traps / caveats

- Do not add high-cardinality labels casually.
- Auto-instrumentation may miss custom async boundaries or business context.

</details>

<a id="ms-obs-028"></a>

<details>
<summary><strong>🧠 MS-OBS-028. How do you design audit trails across multiple services?</strong></summary>

#### Short answer

Record who did what, when, through which service, against which business object, and with what result.

#### Interview answer

Each service should audit decisions for the data it owns. Cross-service workflows need correlation IDs and business IDs so events can be reconstructed. Audit events should be immutable, access-controlled, and protected from accidental deletion.

#### Deep dive

Audit is not the same as debug logging. It has stricter integrity, retention, privacy, and access requirements.

#### Production angle

Audit trails support incident review, fraud investigation, compliance, and customer support.

#### Traps / caveats

- Do not rely on ordinary application logs as the only audit trail.
- Do not include unnecessary PII in audit records.

</details>
