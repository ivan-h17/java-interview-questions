# API Gateway, BFF and edge patterns

---

<a id="ms-api-001"></a>

<details>
<summary><strong>MS-API-001. What is the API Gateway pattern?</strong></summary>

#### Short answer

An API Gateway is an edge entry point that routes client requests to backend services and applies cross-cutting API policies.

#### Interview answer

It commonly handles routing, TLS termination, authentication integration, rate limiting, request size limits, observability, and sometimes simple aggregation. It hides internal service topology from clients, but it should not own core domain logic.

#### Deep dive

The gateway is useful because clients should not need to know every internal service. It can also centralize edge controls while services remain responsible for their own business rules.

#### Production angle

The gateway is often a high-traffic component and must be monitored, scaled, and deployed carefully.

#### Traps / caveats

- Do not turn the gateway into a business workflow engine.
- Gateway authentication does not remove the need for service-side authorization.

</details>

---

<a id="ms-api-004"></a>

<details>
<summary><strong>MS-API-004. What should not be placed in an API Gateway?</strong></summary>

#### Short answer

Core business logic, persistence rules, long-running workflows, and service-owned invariants should not live in the gateway.

#### Interview answer

The gateway should apply edge concerns and light composition, not become the central domain layer. If order validation, payment rules, or inventory decisions live in the gateway, backend services can become thin data stores and the architecture loses ownership.

#### Deep dive

A gateway with too much logic becomes hard to test, risky to deploy, and a bottleneck for every team.

#### Production angle

Gateway bugs can affect every client and many services, so its blast radius should be kept small.

#### Traps / caveats

- Response shaping is acceptable; business authority is not.
- Do not put secrets, tenant policy, or auth decisions only in client-facing code.

</details>

<a id="ms-api-005"></a>

<details>
<summary><strong>MS-API-005. How can an API Gateway become a bottleneck or a mini-monolith?</strong></summary>

#### Short answer

It becomes a bottleneck when too many teams, workflows, and business rules depend on one gateway release.

#### Interview answer

If every client feature requires gateway code changes, the gateway becomes a coordination point. Heavy aggregation can also create latency fan-out, large payloads, and shared failure modes.

#### Deep dive

The gateway should be stable infrastructure with clear ownership. Complex client-specific behavior may belong in BFFs or in backend services.

#### Production angle

Gateway saturation can make the whole system look down even if backend services are healthy.

#### Traps / caveats

- Scaling the gateway does not fix bad downstream fan-out.
- One generic gateway for every client can force awkward compromise APIs.

</details>

<a id="ms-api-008"></a>

<details>
<summary><strong>MS-API-008. What is a Backend for Frontend (BFF)?</strong></summary>

#### Short answer

A BFF is a backend tailored to one frontend or client type, such as web, mobile, or partner API.

#### Interview answer

A BFF adapts backend services to a specific client experience. It can aggregate data, shape responses, hide backend topology, and optimize payloads for mobile or web needs. It should remain a presentation/composition layer, not the owner of core business rules.

#### Deep dive

BFFs are useful when different clients have different workflows, latency constraints, or release cadences.

#### Production angle

A BFF needs the same operational treatment as any service: monitoring, versioning, security, and ownership.

#### Traps / caveats

- Do not create a BFF per screen without a reason.
- Do not duplicate domain rules across multiple BFFs.

</details>

---

<a id="ms-api-009"></a>

<details>
<summary><strong>MS-API-009. When would you use a BFF instead of one generic API Gateway?</strong></summary>

#### Short answer

Use a BFF when clients need materially different API shapes, latency behavior, or release cadence.

#### Interview answer

Mobile may need smaller payloads and fewer round trips, while web may need richer data and partner APIs need stricter contracts. A single generic gateway can become bloated. Separate BFFs let teams optimize client experience without forcing one API to serve all use cases.

#### Deep dive

BFFs trade extra deployables for clearer ownership and better client ergonomics.

#### Production angle

They can reduce client complexity and request fan-out, but increase service count and monitoring surface.

#### Traps / caveats

- BFFs should not bypass service ownership or security checks.
- Avoid copying the same aggregation logic into many BFFs without a reason.

</details>

<a id="ms-api-015"></a>

<details>
<summary><strong>MS-API-015. What are the risks of response aggregation in an API Gateway?</strong></summary>

#### Short answer

Aggregation creates downstream fan-out, latency amplification, partial failure handling, and unclear ownership of response semantics.

#### Interview answer

If the gateway calls five services to build one response, the slowest dependency can dominate latency. The design must define what data is required, what can be omitted, how timeouts work, and how errors are represented to clients.

#### Deep dive

Aggregation is safest for simple read composition. Complex business decisions should stay in domain services or dedicated application services.

#### Production angle

Monitor per-downstream latency, timeout rates, and fallback use so the aggregate API does not hide unhealthy services.

#### Traps / caveats

- Do not let aggregation create a hidden distributed transaction.
- Do not return inconsistent partial data unless the API contract allows it.

</details>

<a id="ms-api-021"></a>

<details>
<summary><strong>🧠 MS-API-021. How do OpenAPI, API catalogs and ownership metadata help govern microservice APIs?</strong></summary>

#### Short answer

They make service contracts discoverable, reviewable, testable, and clearly owned.

#### Interview answer

OpenAPI documents endpoints, schemas, errors, and authentication expectations. API catalogs add ownership, lifecycle, dependency, and deprecation metadata. Together they help teams understand who owns an API, which clients depend on it, and whether a change is compatible.

#### Deep dive

Governance is not only documentation. It can drive contract tests, breaking-change checks, security review, and client generation.

#### Production angle

Good API metadata reduces incident confusion and makes safe deprecation possible.

#### Traps / caveats

- A stale OpenAPI spec is worse than no spec in some cases.
- Catalogs need ownership discipline, not just tooling.

</details>

<a id="ms-api-022"></a>

<details>
<summary><strong>MS-API-022. How do you deprecate and retire public or internal APIs safely?</strong></summary>

#### Short answer

Measure usage, announce the plan, provide a compatible replacement, migrate consumers, and remove only after evidence shows it is safe.

#### Interview answer

I would first identify consumers through logs, auth clients, API catalog, or tracing. Then publish a deprecation timeline, add warnings or headers where appropriate, support both old and new versions during migration, and monitor remaining traffic before retirement.

#### Deep dive

Internal APIs still need discipline because services may be deployed independently and old versions can exist during rollouts.

#### Production angle

Unsafe removal causes client outages that look like provider incidents.

#### Traps / caveats

- Do not rely only on verbal announcements.
- Do not remove fields or change semantics just because Java compilation passes.

</details>
