# Java and Spring backend integration

<a id="ms-java-003"></a>

<details>
<summary><strong>MS-JAVA-003. How do you configure HTTP clients in Spring microservices?</strong></summary>

#### Short answer

Configure typed clients with explicit timeouts, connection pools, retries where safe, observability, and error mapping.

#### Interview answer

Whether using `RestClient`, `WebClient`, Feign, or another client, I would avoid ad hoc calls scattered through business logic. Each downstream should have a small adapter with configured connect/read/response timeouts, base URL, authentication, tracing, metrics, and failure classification.

#### Deep dive

HTTP clients are integration boundaries. They should translate remote failures into domain-relevant categories without leaking library exceptions everywhere.

#### Production angle

Monitor per-client latency, errors, pool saturation, and timeout rates.

#### Traps / caveats

- Do not rely on default timeouts.
- Do not put retries around non-idempotent operations without idempotency.

</details>

<a id="ms-java-004"></a>

<details>
<summary><strong>MS-JAVA-004. What timeout settings should every service-to-service HTTP client have?</strong></summary>

#### Short answer

At minimum: connection timeout, response/read timeout, and preferably an overall request deadline.

#### Interview answer

Connection timeout limits establishing a connection. Read or response timeout limits waiting for data. An overall deadline ensures retries and multiple attempts do not exceed the caller's budget. Pool acquisition timeout is also important when using connection pools.

#### Deep dive

Timeout values should be per dependency and based on latency goals and production percentiles.

#### Production angle

Timeout metrics tell whether failures are connection-level, downstream slowness, or caller pool exhaustion.

#### Traps / caveats

- Infinite defaults can exhaust servlet threads.
- Very short timeouts can create false failures and retries.

</details>

<a id="ms-java-005"></a>

<details>
<summary><strong>MS-JAVA-005. How do you implement retries and circuit breakers in Spring Boot?</strong></summary>

#### Short answer

Use a resilience library such as Resilience4j around specific downstream calls with explicit policies and metrics.

#### Interview answer

I would apply retry, circuit breaker, timeout, and bulkhead policies at the client adapter boundary, not deep inside domain logic. Configure which exceptions are retryable, max attempts, backoff, jitter, failure thresholds, and fallback behavior.

#### Deep dive

Policies should be per dependency because payment, inventory, search, and recommendation calls have different correctness and latency requirements.

#### Production angle

Expose metrics for retries, breaker states, timeouts, and rejected calls.

#### Traps / caveats

- Do not retry all exceptions by default.
- Do not stack application and service-mesh retries without calculating total attempts.

</details>

<a id="ms-java-007"></a>

<details>
<summary><strong>MS-JAVA-007. How do you propagate correlation IDs in Spring Boot?</strong></summary>

#### Short answer

Read or create a correlation ID at the boundary, put it in logging/tracing context, and forward it to downstream calls and messages.

#### Interview answer

Use a filter or interceptor for incoming HTTP requests. Store the ID in MDC or tracing context, add it to response headers, and configure HTTP clients and message producers to propagate it. Clear context after request completion.

#### Deep dive

For async code, MDC may not propagate automatically; executors or instrumentation must carry context explicitly.

#### Production angle

Correlation IDs allow logs from many services to be queried for one request or business operation.

#### Traps / caveats

- Do not trust externally supplied IDs blindly if they can cause log injection or cardinality problems.
- Do not forget message consumers and scheduled jobs.

</details>

<a id="ms-java-008"></a>

<details>
<summary><strong>MS-JAVA-008. How do you propagate security context between Spring services?</strong></summary>

#### Short answer

Forward or exchange verified tokens with proper audience and scopes, and avoid relying on raw thread-local security context across boundaries.

#### Interview answer

At the HTTP boundary, Spring Security validates the token. For downstream calls, the service may forward the user's token if appropriate or use token exchange to get a service-specific token. The downstream still validates it.

#### Deep dive

Async execution and messaging require explicit context handling because `SecurityContextHolder` is thread-local by default.

#### Production angle

Security context propagation should preserve auditability without leaking broad credentials.

#### Traps / caveats

- Do not pass user tokens to services that do not need them.
- Do not trust headers unless added by trusted infrastructure.

</details>

<a id="ms-java-009"></a>

<details>
<summary><strong>MS-JAVA-009. How do Spring transactions interact with message publishing?</strong></summary>

#### Short answer

A Spring database transaction does not automatically make broker publishing atomic with database commits.

#### Interview answer

If code saves an entity in a `@Transactional` method and then publishes a message, a crash or rollback can leave the database and broker inconsistent. Even publishing after commit can fail. Use Transactional Outbox when reliable publication matters.

#### Deep dive

Transaction synchronization callbacks can order actions around commit, but they still do not solve atomicity with an external broker.

#### Production angle

The failure appears as missing events or events for data that never committed.

#### Traps / caveats

- Do not assume `@Transactional` covers Kafka or RabbitMQ by default.
- Publishing inside a transaction can expose events before commit depending on implementation.

</details>

<a id="ms-java-010"></a>

<details>
<summary><strong>MS-JAVA-010. Why can publishing an event inside a transaction be unsafe without Outbox?</strong></summary>

#### Short answer

Because database commit and broker publish are two separate operations that can succeed or fail independently.

#### Interview answer

If the event is published and then the database transaction rolls back, consumers see a false event. If the database commits and the process crashes before publish, consumers never see the change. Outbox records the event intent in the same database transaction.

#### Deep dive

The unsafe part is not the Java syntax; it is the lack of atomicity across resources.

#### Production angle

Missing or false events can corrupt projections, trigger wrong emails, or break downstream workflows.

#### Traps / caveats

- `@TransactionalEventListener(AFTER_COMMIT)` helps timing but not reliable broker publication.
- Consumers still need idempotency even with Outbox.

</details>

<a id="ms-java-011"></a>

<details>
<summary><strong>MS-JAVA-011. How do you implement Transactional Outbox in a Java service?</strong></summary>

#### Short answer

Write business data and an outbox row in one local transaction, then publish outbox rows with a relay.

#### Interview answer

In the `@Transactional` service method, persist the aggregate change and an outbox record containing event type, aggregate ID, payload, headers, and status. A scheduled poller or CDC relay claims records, publishes them, and marks them sent or leaves them for retry.

#### Deep dive

The relay needs locking/claiming, retry policy, ordering decisions, serialization versioning, and cleanup.

#### Production angle

Monitor unsent count, oldest unsent age, publish failures, and relay health.

#### Traps / caveats

- Do not publish and mark sent in a way that loses messages after crashes.
- Do not forget schema evolution for stored payloads.

</details>

<a id="ms-java-012"></a>

<details>
<summary><strong>MS-JAVA-012. How do you implement idempotent consumers in Java?</strong></summary>

#### Short answer

Use a processed-message table or business unique constraint in the same transaction as the side effect.

#### Interview answer

When a message arrives, the consumer tries to insert its message ID or business idempotency key. If it already exists, skip or return the existing result. If inserted, process the business update and commit both together.

#### Deep dive

For Kafka, commit offsets only after the business transaction succeeds if you want at-least-once processing.

#### Production angle

Dedup tables need indexes, retention, and cleanup to avoid unbounded growth.

#### Traps / caveats

- Do not commit the offset before the database update unless message loss is acceptable.
- Do not use a cache as the only deduplication store for critical effects.

</details>

<a id="ms-java-014"></a>

<details>
<summary><strong>MS-JAVA-014. How can database connection pools become a bottleneck in a Java microservice?</strong></summary>

#### Short answer

Requests block waiting for connections when the pool is exhausted, and too many connections can overload the database.

#### Interview answer

Each request that opens a transaction holds a connection. Slow queries, long transactions, N+1 queries, or downstream calls inside transactions can exhaust the pool. Scaling replicas multiplies total connections.

#### Deep dive

Connection pool size should match database capacity and service concurrency, not simply be made large.

#### Production angle

Monitor active connections, pending acquisition, acquisition timeout, transaction duration, and database waits.

#### Traps / caveats

- Increasing pool size can degrade database performance.
- Holding transactions while making remote calls is a common scalability bug.

</details>
