# Data ownership, Database per Service and shared database risks

---

<a id="ms-data-001"></a>

<details>
<summary><strong>MS-DATA-001. What is the Database per Service pattern?</strong></summary>

#### Short answer

Each service owns its persistence and other services access its data only through its public contracts.

#### Interview answer

Database per Service does not always mean a physically separate database server. It means exclusive ownership: one service controls the schema, writes, migrations, invariants, and access policy for its data. Other services use APIs, events, or read models.

#### Deep dive

The pattern preserves loose coupling, but it removes easy joins and global transactions. It pushes the system toward API composition, events, Saga, CQRS, and eventual consistency where appropriate.

#### Production angle

Ownership makes schema changes safer because one team can evolve its database without unknown external queries breaking.

#### Traps / caveats

- A separate schema is not enough if other services query it directly.
- Database per Service increases reporting and consistency design work.

</details>

---

<a id="ms-data-002"></a>

<details>
<summary><strong>MS-DATA-002. Why should each microservice own its data?</strong></summary>

#### Short answer

Data ownership lets a service protect its invariants and evolve independently.

#### Interview answer

If multiple services write the same tables, no service truly owns the business rules. Direct database access also couples consumers to schema details, blocks migrations, and bypasses validation and authorization.

#### Deep dive

Ownership means the service is responsible for correctness, access control, migrations, retention, and publishing changes needed by others.

#### Production angle

Clear ownership speeds incident triage because teams know who can repair corrupted data and explain behavior.

#### Traps / caveats

- Shared read access can still break migrations.
- Data ownership does not mean hiding all useful data; it means exposing it intentionally.

</details>

<a id="ms-data-003"></a>

<details>
<summary><strong>MS-DATA-003. What problems arise when microservices share one database?</strong></summary>

#### Short answer

Shared databases create tight coupling, unsafe schema changes, unclear ownership, and cross-service transaction temptation.

#### Interview answer

When services share tables, one team's migration can break another service. Services may bypass APIs, duplicate rules, and depend on internal columns. The database becomes the integration layer, which weakens independent deployability.

#### Deep dive

Shared databases also make it harder to enforce least privilege, auditing, data retention, and tenant boundaries.

#### Production angle

Incidents often involve unknown consumers, hidden SQL queries, and fear of changing columns or indexes.

#### Traps / caveats

- A shared database can be acceptable during migration, but it should be treated as technical debt.
- Read-only access can still create strong coupling.

</details>

---

<a id="ms-data-004"></a>

<details>
<summary><strong>MS-DATA-004. When can a shared database be acceptable temporarily?</strong></summary>

#### Short answer

During migration or early decomposition, if ownership, access rules, and an exit plan are explicit.

#### Interview answer

A shared database may be a pragmatic bridge while extracting a service from a monolith. The team should restrict writes, document consumers, avoid new direct dependencies, and gradually replace access with APIs, events, or read models.

#### Deep dive

Temporary shared access becomes dangerous when it has no owner or deadline. Treat it like a migration state, not a target architecture.

#### Production angle

Use database permissions, monitoring, query logs, and migration plans to prevent accidental permanent coupling.

#### Traps / caveats

- "Temporary" shared databases often become permanent without governance.
- Do not let new features deepen shared-table dependencies.

</details>

<a id="ms-data-005"></a>

<details>
<summary><strong>MS-DATA-005. How do you enforce service data ownership?</strong></summary>

#### Short answer

Use permissions, schema boundaries, reviews, contracts, and operational ownership to prevent direct access by other services.

#### Interview answer

Only the owning service should have write permissions to its tables. Other services should use APIs, events, or replicated read models. Schema changes should go through the owning team's pipeline, and database credentials should be scoped.

#### Deep dive

Enforcement is both technical and organizational. Architecture rules need CI checks, database permissions, code review, and incident accountability.

#### Production angle

Restricted credentials reduce the blast radius of bugs and make access auditing easier.

#### Traps / caveats

- Conventions without permissions are weak.
- Reporting jobs and admin scripts also need ownership review.

</details>

<a id="ms-data-007"></a>

<details>
<summary><strong>MS-DATA-007. How should services expose data to other services?</strong></summary>

#### Short answer

Through explicit APIs, events, snapshots, or read models, depending on freshness and coupling needs.

#### Interview answer

For current queries, expose an API with a stable contract. For changes other services need to react to, publish integration events. For high-read or cross-domain views, build read models or projections owned by the consuming side or a reporting service.

#### Deep dive

The right pattern depends on latency, consistency, query shape, and ownership. Avoid exposing internal tables or entity models.

#### Production angle

Explicit contracts make authorization, rate limiting, schema evolution, and observability manageable.

#### Traps / caveats

- Events are not a good fit for every query.
- API responses should not leak persistence internals.

</details>

<a id="ms-data-009"></a>

<details>
<summary><strong>MS-DATA-009. Why is data duplication sometimes acceptable in microservices?</strong></summary>

#### Short answer

Duplication can reduce coupling and improve read performance when ownership and freshness rules are clear.

#### Interview answer

A service may keep a local copy of data from another service to avoid synchronous calls or build a read model. The original owner remains authoritative, while the copy is derived and eventually consistent.

#### Deep dive

Duplication is acceptable when it is deliberate, traceable, and recoverable from source data or events.

#### Production angle

Derived data needs lag monitoring, replay/backfill support, and reconciliation when events are missed or schemas change.

#### Traps / caveats

- Duplicated data should not become a second source of truth.
- Stale copies must be acceptable for the user flow.

</details>

<a id="ms-data-010"></a>

<details>
<summary><strong>MS-DATA-010. How do you maintain consistency when each service owns its database?</strong></summary>

#### Short answer

Use local transactions plus patterns such as Saga, Outbox, idempotency, read models, and reconciliation.

#### Interview answer

Each service updates its own database atomically. Cross-service workflows are coordinated through messages or commands, with retries and compensations when needed. For reads, use API composition or projections depending on freshness and performance.

#### Deep dive

Microservice consistency is often business-specific. Some invariants need to stay inside one service; others can be eventually consistent with clear user experience.

#### Production angle

You need observability for stuck workflows, failed events, duplicate processing, and reconciliation drift.

#### Traps / caveats

- Saga is not ACID isolation across services.
- Avoid designing workflows that require many services to update atomically.

</details>

<a id="ms-data-012"></a>

<details>
<summary><strong>MS-DATA-012. When is eventual consistency acceptable or unacceptable?</strong></summary>

#### Short answer

It is acceptable when temporary staleness is safe and visible enough; unacceptable when it violates critical business or user guarantees.

#### Interview answer

Eventual consistency works for search indexes, recommendations, analytics, notifications, and many read models. It is dangerous for double-spending, duplicate payment capture, overselling limited inventory, or authorization decisions that must be current.

#### Deep dive

The question is not "eventual consistency yes or no"; it is "how stale, for whom, and with what compensation?"

#### Production angle

Expose pending states, reconciliation, and user messaging when workflows are not immediately final.

#### Traps / caveats

- Do not hide eventual consistency behind a UI that promises immediate completion.
- Strong consistency may require keeping data inside one service boundary.

</details>

<a id="ms-data-015"></a>

<details>
<summary><strong>🧠 MS-DATA-015. How do you use API Composition to query data owned by multiple services?</strong></summary>

#### Short answer

An API composer calls multiple owning services and combines their responses into one result.

#### Interview answer

API Composition works for low-to-moderate fan-out reads where freshness matters and latency is acceptable. The composer must handle timeouts, partial failures, authorization, and response semantics.

#### Deep dive

It is simpler than maintaining a projection but can become slow and fragile if every request fans out to many services.

#### Production angle

Use per-dependency metrics and clear fallback policy. Consider a read model when composition becomes hot or complex.

#### Traps / caveats

- Do not compose data by querying other services' databases.
- Do not use composition for large distributed joins.

</details>

<a id="ms-data-020"></a>

<details>
<summary><strong>MS-DATA-020. How do you handle schema changes across service-owned databases?</strong></summary>

#### Short answer

Use backward-compatible migrations, expand-and-contract, and service-local ownership of schema changes.

#### Interview answer

The owning service should migrate its database in steps: add new nullable columns or tables, deploy code that writes both old and new shapes if needed, backfill safely, switch readers, then remove old fields later. Other services should not depend on internal schema.

#### Deep dive

Schema changes become cross-service problems only when ownership is violated or external contracts expose database details.

#### Production angle

Migrations need lock awareness, rollback strategy, monitoring, and compatibility with rolling deployments.

#### Traps / caveats

- Do not make a breaking database migration and code deployment inseparable.
- Direct SQL consumers make safe schema evolution much harder.

</details>

<a id="ms-data-021"></a>

<details>
<summary><strong>MS-DATA-021. How do you join data from multiple services?</strong></summary>

#### Short answer

Use API composition, read models/projections, search indexes, or reporting pipelines; avoid runtime distributed database-style joins.

#### Interview answer

For simple fresh reads, call the owning services and compose the response. For high-traffic or complex views, build a read model from events. For analytics, use a separate data warehouse or reporting pipeline.

#### Deep dive

The owner of a cross-service view should be explicit. Often the consuming service owns its projection, while source services publish stable events.

#### Production angle

Monitor projection lag, rebuild capability, and data quality. Users should know when data can be stale.

#### Traps / caveats

- Do not let a reporting query become hidden production coupling.
- Avoid synchronous joins across many services in a hot path.

</details>

<a id="ms-data-023"></a>

<details>
<summary><strong>🧠 MS-DATA-023. What are the risks of distributed joins?</strong></summary>

#### Short answer

Distributed joins are slow, fragile, hard to optimize, and couple services at runtime.

#### Interview answer

A distributed join requires multiple remote calls, pagination coordination, inconsistent snapshots, partial failure handling, and complex authorization. It can also overload source services with query patterns they did not design for.

#### Deep dive

Relational databases optimize joins inside one engine with statistics and transaction semantics. Across services, you lose those guarantees.

#### Production angle

Distributed joins often show up as p99 latency spikes and cascading failures during traffic bursts.

#### Traps / caveats

- Do not replace a database join with N remote calls without measuring.
- Use read models or analytics stores for repeated cross-domain queries.

</details>
