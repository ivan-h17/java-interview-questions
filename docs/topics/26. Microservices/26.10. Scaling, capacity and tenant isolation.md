# Scaling, capacity and tenant isolation

---

<a id="ms-scale-012"></a>

<details>
<summary><strong>MS-SCALE-012. How do you scale read-heavy services?</strong></summary>

#### Short answer

Use caching, replicas, read models, pagination, denormalization, and horizontal scaling when the bottleneck supports it.

#### Interview answer

First find the bottleneck: CPU, database, network, cache, or downstream calls. Then use appropriate techniques such as HTTP caching, Redis/cache-aside, database read replicas, query optimization, precomputed projections, and service replicas behind a load balancer.

#### Deep dive

Scaling application instances helps only if shared dependencies can handle the additional load.

#### Production angle

Monitor cache hit rate, database CPU/IO, query latency, connection pools, and stale data risk.

#### Traps / caveats

- Caching can introduce stale data and invalidation complexity.
- Read replicas can have replication lag.

</details>

<a id="ms-scale-014"></a>

<details>
<summary><strong>MS-SCALE-014. What is autoscaling, and which metrics can drive it?</strong></summary>

#### Short answer

Autoscaling adjusts the number of service instances based on demand or saturation signals.

#### Interview answer

Common metrics include CPU, memory, request rate, latency, queue length, consumer lag, active connections, thread pool saturation, and custom business workload indicators. The right metric depends on what actually limits the service.

#### Deep dive

Autoscaling has lag. It should be combined with capacity planning, load shedding, and backpressure for sudden spikes.

#### Production angle

Bad autoscaling metrics can oscillate or scale the wrong component while the real bottleneck remains downstream.

#### Traps / caveats

- CPU-only scaling is weak for I/O-bound services.
- Scaling consumers can overload the database or external API.

</details>

<a id="ms-scale-015"></a>

<details>
<summary><strong>MS-SCALE-015. Why is CPU alone often insufficient for autoscaling?</strong></summary>

#### Short answer

Many Java microservices are limited by I/O, database pools, queues, or downstream latency before CPU is high.

#### Interview answer

A service can be overloaded while CPU is low if threads are blocked waiting for a slow database or HTTP dependency. CPU-based autoscaling would not react correctly. Latency, in-flight requests, queue depth, pool saturation, and error rates may be better signals.

#### Deep dive

For asynchronous consumers, lag or processing delay often matters more than CPU.

#### Production angle

Choose scaling metrics from load tests and production bottleneck analysis.

#### Traps / caveats

- Low CPU does not mean healthy.
- High CPU can be useful, but it must be interpreted with latency and saturation.

</details>

<a id="ms-scale-016"></a>

<details>
<summary><strong>MS-SCALE-016. How do queue length and lag help autoscale consumers?</strong></summary>

#### Short answer

They show whether consumers are keeping up with incoming work.

#### Interview answer

Queue length and consumer lag measure backlog. If lag grows and downstream capacity is available, adding consumers can reduce processing delay. If lag grows because the database or external service is slow, scaling consumers may worsen the bottleneck.

#### Deep dive

Use lag age/time as well as item count because one large message or bursty topic can distort simple counts.

#### Production angle

Autoscaling should respect max concurrency, partition count, downstream rate limits, and rebalance behavior.

#### Traps / caveats

- More consumers than partitions may not increase Kafka throughput.
- Scaling on lag without backpressure can overload dependencies.

</details>

<a id="ms-scale-017"></a>

<details>
<summary><strong>MS-SCALE-017. How do you estimate capacity for a microservice?</strong></summary>

#### Short answer

Estimate request rate, latency target, resource cost per request, dependency limits, and peak traffic.

#### Interview answer

Start with expected QPS, peak factor, payload size, critical paths, and p95/p99 latency goals. Measure CPU, memory, thread usage, database connections, downstream calls, and queue work per request. Then load test and add headroom.

#### Deep dive

Capacity is often constrained by shared dependencies, not only service instances.

#### Production angle

Capacity planning should include failure scenarios, deploy surges, retries, and regional loss if relevant.

#### Traps / caveats

- Average QPS hides bursts.
- Ignoring dependency limits leads to false confidence from app-only load tests.

</details>

<a id="ms-scale-019"></a>

<details>
<summary><strong>MS-SCALE-019. How does database connection pool size limit service scalability?</strong></summary>

#### Short answer

Each service instance has a finite database connection pool, and the database can handle only a finite total number of active connections.

#### Interview answer

If every replica has a pool of 50 and you scale to 40 replicas, the database may face 2,000 possible connections. Too many connections increase memory use, contention, and latency. Too few can make requests wait in the service.

#### Deep dive

Pool size should reflect database capacity, query latency, transaction duration, and concurrency needs.

#### Production angle

Monitor pool acquisition time, active connections, database CPU/IO, lock waits, and slow queries.

#### Traps / caveats

- Increasing pool size can make the database slower.
- Long transactions hold connections and reduce effective capacity.

</details>

<a id="ms-scale-020"></a>

<details>
<summary><strong>MS-SCALE-020. How can a downstream dependency limit horizontal scaling?</strong></summary>

#### Short answer

Adding more service replicas increases calls to shared dependencies, which may already be the bottleneck.

#### Interview answer

If every request calls payment, database, or inventory, scaling the caller increases pressure on those systems. The caller may look scalable while the dependency becomes slower, causing retries and cascading failures.

#### Deep dive

Horizontal scaling works best for stateless CPU-bound services. It is limited by databases, caches, queues, external APIs, and rate limits.

#### Production angle

Use dependency-level capacity, bulkheads, backpressure, and rate limits before autoscaling aggressively.

#### Traps / caveats

- Scaling consumers can drain a queue faster than the database can process writes.
- Autoscaling one tier can shift the bottleneck to another tier.

</details>

<a id="ms-scale-023"></a>

<details>
<summary><strong>MS-SCALE-023. How would you design a microservice to handle a traffic spike?</strong></summary>

#### Short answer

Use headroom, autoscaling, caching, queues, backpressure, load shedding, and dependency protection.

#### Interview answer

I would identify whether the spike is reads, writes, or background work. For reads, use caching and replicas. For writes, use queues when the workflow can be asynchronous. Protect dependencies with rate limits, concurrency limits, and fast failure for optional work.

#### Deep dive

Spike handling should preserve critical flows first. Not all endpoints need the same priority.

#### Production angle

Prepare dashboards and runbooks before spikes: saturation, queue age, error rate, fallback rate, and downstream health.

#### Traps / caveats

- Queues help only if delayed processing is acceptable.
- Autoscaling may be too slow for sudden bursts.

</details>

<a id="ms-scale-024"></a>

<details>
<summary><strong>🧠 MS-SCALE-024. What is tenant isolation, and why does it matter in multi-tenant microservices?</strong></summary>

#### Short answer

Tenant isolation prevents one customer or tenant from affecting another's data, performance, or security.

#### Interview answer

Isolation can be logical, such as tenant IDs and authorization checks, or physical, such as separate databases, queues, caches, or deployments for high-value tenants. The right level depends on compliance, noisy-neighbor risk, cost, and operational needs.

#### Deep dive

Isolation applies to data access, resource quotas, background jobs, rate limits, logs, metrics, and support tooling.

#### Production angle

Tenant-aware dashboards help identify whether one tenant is causing load, errors, or queue growth.

#### Traps / caveats

- Tenant ID in a column is not enough without consistent authorization and indexing.
- Shared caches can leak data if keys are not tenant-scoped.

</details>

<a id="ms-scale-025"></a>

<details>
<summary><strong>🧠 MS-SCALE-025. How do you prevent noisy-neighbor problems between tenants or services?</strong></summary>

#### Short answer

Use quotas, rate limits, resource isolation, priority queues, per-tenant metrics, and sometimes physical separation.

#### Interview answer

A noisy neighbor consumes shared CPU, database connections, queue capacity, cache memory, or external API quota. Prevent it by setting per-tenant or per-client limits, isolating expensive jobs, limiting concurrency, and prioritizing critical traffic.

#### Deep dive

The strongest isolation is separate infrastructure, but it costs more. Many systems use mixed isolation: shared by default, dedicated for large or regulated tenants.

#### Production angle

Alert on per-tenant usage and saturation, not just global averages.

#### Traps / caveats

- Global limits can let one tenant consume the whole budget.
- Isolation needs to include background workers and batch jobs, not only HTTP APIs.

</details>
