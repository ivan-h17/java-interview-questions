# Deployment, orchestration and release strategies

---

<a id="ms-deploy-007"></a>

<details>
<summary><strong>MS-DEPLOY-007. How do you roll back a microservice safely?</strong></summary>

#### Short answer

Rollback is safe only if APIs, events, data schema, and side effects remain compatible with the previous version.

#### Interview answer

The service should support backward-compatible deployments. If the code writes data the old version cannot read, rollback may fail. Prefer roll-forward for data migrations when rollback is risky, and use feature flags or canaries to reduce blast radius.

#### Deep dive

Rollback planning must include database migrations, message schemas, caches, and external provider side effects.

#### Production angle

A rollback runbook should define when to roll back, how to verify, and which metrics confirm recovery.

#### Traps / caveats

- Do not assume container rollback fixes incompatible schema changes.
- Do not roll back a producer if consumers now depend on new event semantics.

</details>

<a id="ms-deploy-008"></a>

<details>
<summary><strong>MS-DEPLOY-008. How do you deploy database changes safely with microservices?</strong></summary>

#### Short answer

Use expand-and-contract migrations compatible with rolling deployments and service-owned schema changes.

#### Interview answer

Add new schema in a backward-compatible way, deploy code that can handle both old and new shapes, backfill safely, switch readers/writers, then remove old schema later. Avoid long locks and test migration behavior on realistic data.

#### Deep dive

Database changes are dangerous because rollback is not always possible and old service versions may still run.

#### Production angle

Monitor migration duration, lock waits, error rates, and data consistency during rollout.

#### Traps / caveats

- Do not make a column non-null before all rows are backfilled.
- Do not let other services query owned schema directly.

</details>

<a id="ms-deploy-009"></a>

<details>
<summary><strong>MS-DEPLOY-009. What is backward-compatible deployment?</strong></summary>

#### Short answer

It means new and old versions of services, APIs, events, and schemas can coexist during rollout.

#### Interview answer

Rolling deployments create version skew. A backward-compatible deployment ensures old consumers can talk to new providers and new consumers can tolerate old providers where required. Changes are usually additive first and destructive later.

#### Deep dive

Compatibility applies to HTTP contracts, event schemas, database schema, caches, and background jobs.

#### Production angle

Backward compatibility enables canary, rolling deployment, rollback, and independent releases.

#### Traps / caveats

- Adding a required field is often breaking.
- Changing field meaning can be breaking even if the schema is unchanged.

</details>

<a id="ms-deploy-010"></a>

<details>
<summary><strong>MS-DEPLOY-010. What is expand-and-contract migration?</strong></summary>

#### Short answer

It is a multi-step migration: add new structure, move traffic/data, then remove old structure after compatibility is proven.

#### Interview answer

First expand the schema or API with backward-compatible additions. Then deploy code that writes or reads both forms, backfill if needed, switch consumers, and finally contract by removing old fields or paths.

#### Deep dive

This pattern avoids breaking rolling deployments and gives time to verify data correctness.

#### Production angle

It is essential for zero-downtime database and contract changes.

#### Traps / caveats

- Contract too early and old versions fail.
- Dual-write phases need monitoring and cleanup plans.

</details>

<a id="ms-deploy-011"></a>

<details>
<summary><strong>MS-DEPLOY-011. How do you coordinate API changes across multiple services?</strong></summary>

#### Short answer

Use compatible changes, contracts, versioning where needed, staged rollout, and consumer migration tracking.

#### Interview answer

The provider should add fields or endpoints first, keep old behavior, and notify consumers. Consumers migrate independently. Only after usage metrics show old behavior is gone should the provider remove it.

#### Deep dive

Coordination should be driven by contracts and telemetry, not chat messages alone.

#### Production angle

API gateways, logs, and catalogs can show which clients still use old endpoints or fields.

#### Traps / caveats

- Do not remove or rename fields without a migration period.
- Do not assume all internal consumers deploy quickly.

</details>

<a id="ms-deploy-012"></a>

<details>
<summary><strong>MS-DEPLOY-012. How do you coordinate event schema changes across multiple services?</strong></summary>

#### Short answer

Use backward-compatible event evolution, schema checks, consumer migration, and replay-aware versioning.

#### Interview answer

Producers should add optional fields with defaults and avoid changing meaning. Consumers should tolerate unknown fields and missing optional fields. Schema registry or contract tests can block incompatible changes. Old event versions may need support for historical replay.

#### Deep dive

Events are harder than APIs because producers may not know every consumer and old messages can live in retention.

#### Production angle

Monitor consumer failures after schema rollout and keep rollback/parallel publishing options if needed.

#### Traps / caveats

- Do not assume changing only the producer is enough.
- Required fields without defaults often break old events.

</details>

<a id="ms-deploy-014"></a>

<details>
<summary><strong>🧠 MS-DEPLOY-014. What is a service mesh, and when would you introduce it?</strong></summary>

#### Short answer

A service mesh is infrastructure for service-to-service traffic management, mTLS, policy, and telemetry, usually through sidecars or node-level proxies.

#### Interview answer

Introduce a mesh when many services need consistent mTLS, traffic splitting, retries, timeouts, authorization policy, and observability that are hard to manage in each application. It is more justified at platform scale than for a small system.

#### Deep dive

Service mesh moves some network concerns out of application code but adds operational complexity and another control plane.

#### Production angle

Mesh outages or misconfigurations can affect a large part of the platform, so rollout and ownership matter.

#### Traps / caveats

- Do not introduce a mesh before you understand the problem it solves.
- Mesh retries can conflict with application retries if not coordinated.

</details>

<a id="ms-deploy-017"></a>

<details>
<summary><strong>MS-DEPLOY-017. How do you handle graceful shutdown of a service?</strong></summary>

#### Short answer

Stop receiving new work, finish or hand off in-flight work, close resources, and exit before the platform kills the process.

#### Interview answer

On shutdown, the service should fail readiness, let load balancers stop routing new requests, stop accepting new messages, complete or safely abort current work, flush telemetry, and close connections. The termination grace period must be long enough for normal cleanup.

#### Deep dive

HTTP services, consumers, and schedulers need different shutdown handling.

#### Production angle

Bad shutdown causes failed requests, duplicate message processing, and partial writes during deployment.

#### Traps / caveats

- Do not keep readiness true while shutting down.
- Do not start new background work after shutdown begins.

</details>

<a id="ms-deploy-018"></a>

<details>
<summary><strong>MS-DEPLOY-018. How do you prevent traffic from reaching a service during shutdown?</strong></summary>

#### Short answer

Fail readiness first, wait for endpoint removal and connection draining, then stop the process.

#### Interview answer

In Kubernetes, the service should become not ready during pre-stop or shutdown. The platform removes it from endpoints, but propagation and load balancer delay can exist, so the service may need a short drain period before closing.

#### Deep dive

Long-lived connections and client-side caches can still send traffic briefly after readiness changes.

#### Production angle

Graceful shutdown should be tested during rolling deployments, not only assumed.

#### Traps / caveats

- Do not terminate immediately after readiness flips.
- Do not forget consumers and scheduled jobs; they receive "traffic" differently.

</details>

<a id="ms-deploy-019"></a>

<details>
<summary><strong>MS-DEPLOY-019. How do readiness and liveness probes affect deployment safety?</strong></summary>

#### Short answer

Readiness controls rollout traffic; liveness restarts stuck processes. Incorrect probes can cause outages.

#### Interview answer

Readiness should become true only when the service can serve and false during shutdown or severe local inability to serve. Liveness should detect unrecoverable hangs, not temporary downstream outages. Used correctly, they make rolling updates safer.

#### Deep dive

A bad liveness probe can restart every instance during a dependency outage, making recovery worse.

#### Production angle

Probe failures should be observable and tested under startup, shutdown, and downstream failure scenarios.

#### Traps / caveats

- Do not use the same strict dependency check for liveness and readiness.
- Do not mark ready before migrations, warmup, or listener startup is complete.

</details>

<a id="ms-deploy-020"></a>

<details>
<summary><strong>🧠 MS-DEPLOY-020. How do you design startup and shutdown behavior for consumers?</strong></summary>

#### Short answer

Consumers should start only when dependencies are ready and shut down by stopping new polling before finishing or safely committing in-flight work.

#### Interview answer

At startup, the consumer should load config, connect to dependencies, and only then join the consumer group. At shutdown, it should stop polling, finish current records when possible, commit offsets only after successful processing, and avoid duplicate side effects through idempotency.

#### Deep dive

Consumer group rebalancing, offset commits, and long processing times make shutdown more complex than HTTP request draining.

#### Production angle

Bad consumer shutdown causes duplicate processing, message loss, or rebalance storms during deployments.

#### Traps / caveats

- Do not commit offsets before processing completes unless at-most-once loss is acceptable.
- Do not let long-running records exceed broker poll intervals.

</details>
