# Synchronous and asynchronous communication

---

<a id="ms-comm-002"></a>

<details>
<summary><strong>MS-COMM-002. What is the difference between synchronous and asynchronous communication?</strong></summary>

#### Short answer

Synchronous communication waits for an immediate response; asynchronous communication sends work or facts to be handled later.

#### Interview answer

HTTP or gRPC calls are usually synchronous: the caller is blocked until the callee responds or times out. Messaging is usually asynchronous: the producer publishes a command or event, and consumers process it later. Synchronous calls are simpler for queries; asynchronous flows reduce temporal coupling.

#### Deep dive

The trade-off is clarity versus resilience. Sync calls give immediate answers but couple availability and latency. Async messaging improves decoupling but introduces eventual consistency, ordering, retries, and duplicate handling.

#### Production angle

Choosing the wrong style can create cascading failures or confusing user experiences with stale state.

#### Traps / caveats

- Async does not mean simple; it shifts complexity to consumers and operations.
- Sync calls always need timeouts and failure handling.

</details>

<a id="ms-comm-003"></a>

<details>
<summary><strong>MS-COMM-003. When would you use synchronous communication between services?</strong></summary>

#### Short answer

Use it when the caller needs an immediate answer to continue the user flow and the dependency is acceptable in the critical path.

#### Interview answer

Synchronous calls fit reads, validation, and operations where the user needs a result now, such as price calculation or eligibility checks. I would keep the chain short, set deadlines, and ensure the downstream is reliable enough for the path.

#### Deep dive

Synchronous communication is not wrong; uncontrolled synchronous dependency graphs are the problem. Strong candidates discuss latency budget, ownership, fallback, and partial failure.

#### Production angle

Every sync dependency reduces the availability of the caller's request path unless guarded by timeouts, bulkheads, and degradation policy.

#### Traps / caveats

- Do not make a synchronous call for every field in a response.
- Do not leave HTTP clients with infinite or very high default timeouts.

</details>

<a id="ms-comm-004"></a>

<details>
<summary><strong>MS-COMM-004. When would you use asynchronous communication between services?</strong></summary>

#### Short answer

Use it for work that can happen later, fan-out notifications, integration events, long-running workflows, and traffic smoothing.

#### Interview answer

Asynchronous messaging is useful when the producer should not wait for every consumer or when work can be processed after the request returns. Examples are sending emails, updating search indexes, building projections, and continuing a Saga.

#### Deep dive

Async communication reduces temporal coupling, but consumers must handle duplicates, retries, ordering, poison messages, and schema evolution.

#### Production angle

Queues and logs can absorb spikes, but backlog, lag, DLQs, and replay safety become operational concerns.

#### Traps / caveats

- Do not use events when the caller needs a strong immediate answer.
- Do not publish events from a database transaction without addressing the dual-write problem.

</details>

<a id="ms-comm-005"></a>

<details>
<summary><strong>MS-COMM-005. What are the risks of synchronous service-to-service calls?</strong></summary>

#### Short answer

They couple latency and availability and can create cascading failures when dependencies slow down.

#### Interview answer

A synchronous caller waits for the callee, so a slow downstream can consume threads, connections, and request budget upstream. Long chains amplify p99 latency and make partial failures user-visible.

#### Deep dive

The risk grows with fan-out. If one request calls five services, the probability that at least one dependency is slow or unavailable is much higher than for one local operation.

#### Production angle

Controls include timeouts, retries with budgets, circuit breakers, bulkheads, load shedding, caching, and reducing request-path fan-out.

#### Traps / caveats

- Retrying every failed sync call can make outages worse.
- A fallback is only safe if stale or partial data is acceptable.

</details>

<a id="ms-comm-006"></a>

<details>
<summary><strong>MS-COMM-006. What are the risks of asynchronous messaging?</strong></summary>

#### Short answer

Async messaging adds eventual consistency, duplicate messages, ordering issues, retry storms, DLQ handling, and harder debugging.

#### Interview answer

Producers and consumers are decoupled in time, but the business process is still connected. Consumers may process events late, more than once, or out of order. Schema changes can break old consumers, and failed messages need a replay strategy.

#### Deep dive

Async systems require explicit thinking about delivery semantics, idempotency, offset/ack strategy, poison messages, and consumer lag.

#### Production angle

Operational dashboards need lag, retry count, DLQ size, processing latency, and downstream failure metrics.

#### Traps / caveats

- "Eventual consistency" is not acceptable for every user expectation.
- DLQ is not a fix by itself; it is a quarantine that needs ownership.

</details>

<a id="ms-comm-016"></a>

<details>
<summary><strong>🧠 MS-COMM-016. How does API composition affect latency, availability and failure handling?</strong></summary>

#### Short answer

API composition combines data from multiple services, so latency and availability depend on all required downstream calls.

#### Interview answer

An API composer or gateway can simplify clients, but it creates fan-out. If one downstream is slow, the composed response may be slow or incomplete. The design must define required versus optional data, per-call timeouts, fallback behavior, and caching.

#### Deep dive

Parallel calls can reduce total latency, but they increase concurrent load and can still suffer from tail latency. For frequently needed views, a read model may be better.

#### Production angle

Monitor dependency-level latency and error rates, not just the API gateway's aggregate response time.

#### Traps / caveats

- Do not put complex domain workflow into a gateway just because it composes APIs.
- Do not make every frontend request trigger a large service fan-out.

</details>

<a id="ms-comm-017"></a>

<details>
<summary><strong>MS-COMM-017. How do you avoid cascading latency with service-to-service calls?</strong></summary>

#### Short answer

Keep call chains short, set deadlines, isolate dependencies, and avoid uncontrolled fan-out.

#### Interview answer

I would start with a latency budget for the whole request and allocate budgets to each downstream call. Calls should have timeouts, bounded concurrency, circuit breakers where useful, and clear fallback or failure behavior. Expensive fan-out should be replaced with caching, batching, read models, or asynchronous processing.

#### Deep dive

Cascading latency happens when slow dependencies hold upstream resources long enough to make those upstream services slow too.

#### Production angle

Track p95/p99 latency per dependency, in-flight requests, thread pool saturation, connection pool usage, and timeout rates.

#### Traps / caveats

- Adding retries without a deadline can worsen latency.
- Increasing thread pools hides symptoms until the dependency or database collapses.

</details>

<a id="ms-comm-018"></a>

<details>
<summary><strong>MS-COMM-018. How do you set timeouts for inter-service calls?</strong></summary>

#### Short answer

Set timeouts from the caller's end-to-end deadline, downstream latency distribution, and business tolerance for waiting.

#### Interview answer

Every remote call should have connection, request/read, and sometimes overall operation timeouts. The timeout must fit inside the remaining request budget. For example, if the API target is 500 ms, a downstream call cannot wait 5 seconds.

#### Deep dive

Use production percentiles, not guesses. Timeouts should be lower for optional dependencies and carefully tuned for critical operations with known slow behavior.

#### Production angle

Timeouts need metrics and logs so teams can distinguish downstream slowness, network failures, and caller-side saturation.

#### Traps / caveats

- Default HTTP client timeouts may be infinite or unsuitable.
- Very aggressive timeouts can cause false failures and retry storms.

</details>

<a id="ms-comm-022"></a>

<details>
<summary><strong>🧠 MS-COMM-022. What is message ordering, and why is it hard in distributed systems?</strong></summary>

#### Short answer

Message ordering means consumers observe events in a required sequence, but distributed producers, partitions, retries, and clocks make global ordering hard.

#### Interview answer

Most systems can preserve ordering only within a partition or key, such as all events for one order. Global ordering across all entities reduces scalability and is rarely needed. Consumers should often handle out-of-order messages using versions, timestamps, sequence numbers, or idempotent state transitions.

#### Deep dive

Retries and redelivery can reorder events. Multiple producers may not share a reliable clock or global sequence.

#### Production angle

Ordering requirements should be explicit because they influence partition keys, throughput, replay, and consumer logic.

#### Traps / caveats

- Do not assume Kafka or any broker gives global order across partitions.
- Event timestamps are not enough for correctness if producer clocks differ.

</details>

<a id="ms-comm-023"></a>

<details>
<summary><strong>MS-COMM-023. How do you design idempotent message consumers?</strong></summary>

#### Short answer

Make repeated processing of the same message produce the same final result without duplicate side effects.

#### Interview answer

Use a stable message ID or business idempotency key and record processed messages or state transitions transactionally with the business update. For external side effects, pass idempotency keys downstream or isolate side effects behind a reliable workflow.

#### Deep dive

Idempotency can be implemented with unique constraints, processed-message tables, version checks, upserts, or naturally idempotent state transitions.

#### Production angle

Idempotent consumers are required for at-least-once delivery, retries, redelivery after crashes, and DLQ reprocessing.

#### Traps / caveats

- Checking "processed" outside the business transaction can race.
- Deduplication records need retention and cleanup policy.

</details>

<a id="ms-comm-024"></a>

<details>
<summary><strong>MS-COMM-024. How do you handle duplicate messages?</strong></summary>

#### Short answer

Assume duplicates can happen and handle them with idempotent processing, deduplication keys, and transactional state updates.

#### Interview answer

Duplicates can come from producer retries, broker redelivery, consumer crashes, offset commit timing, or manual replay. The consumer should detect duplicates using message IDs or business keys and make the operation safe to repeat.

#### Deep dive

For state changes, unique constraints and compare-and-set logic are often more reliable than in-memory caches. For side effects, use downstream idempotency or an outbox-style command log.

#### Production angle

Duplicate handling should be tested with redelivery and replay, not only happy-path consumption.

#### Traps / caveats

- Exactly-once broker features do not make external database or HTTP side effects exactly once.
- Deduplicating by payload hash can fail when equivalent messages differ in metadata.

</details>

<a id="ms-comm-027"></a>

<details>
<summary><strong>MS-COMM-027. How should services handle partial failure during communication?</strong></summary>

#### Short answer

Treat partial failure as normal: time out, retry only safe operations, degrade when possible, and preserve enough state for recovery.

#### Interview answer

A caller may not know whether a downstream operation failed before or after doing the work. The design needs idempotency keys, clear error classification, retries with budget and backoff, compensation when needed, and observability.

#### Deep dive

Distributed communication has ambiguous outcomes. A timeout does not mean the callee did nothing; it means the caller did not receive a result in time.

#### Production angle

Payment, inventory, and order workflows need reconciliation jobs and manual repair paths for ambiguous outcomes.

#### Traps / caveats

- Do not blindly retry non-idempotent operations.
- Do not map all downstream failures to generic 500 without preserving context.

</details>

<a id="ms-comm-029"></a>

<details>
<summary><strong>MS-COMM-029. What are the trade-offs between REST, gRPC and messaging?</strong></summary>

#### Short answer

REST is simple and web-friendly, gRPC is efficient and contract-first, and messaging is asynchronous and decoupled but operationally more complex.

#### Interview answer

REST fits public APIs, CRUD-like resources, and broad interoperability. gRPC fits internal low-latency service calls with strict schemas and code generation. Messaging fits events, commands, fan-out, and delayed processing where eventual consistency is acceptable.

#### Deep dive

The choice should follow communication semantics, not fashion. Ask whether the caller needs an immediate response, whether ordering matters, how contracts evolve, and how failures are handled.

#### Production angle

REST/gRPC need timeouts and dependency isolation; messaging needs lag, DLQ, replay, and consumer idempotency operations.

#### Traps / caveats

- gRPC does not remove distributed failure modes.
- Messaging is not a replacement for query APIs when clients need current state.

</details>

<a id="ms-comm-030"></a>

<details>
<summary><strong>MS-COMM-030. How do you apply backpressure across synchronous and asynchronous service boundaries?</strong></summary>

#### Short answer

Limit intake when downstream capacity is constrained, instead of letting queues, threads, or memory grow without bound.

#### Interview answer

For synchronous calls, use bounded concurrency, connection pool limits, rate limits, timeouts, and fast rejection. For asynchronous consumers, control poll rate, batch size, worker pool size, queue depth, and pause/resume behavior. Producers should observe rejection or lag signals instead of pushing endlessly.

#### Deep dive

Backpressure is a feedback mechanism. It turns overload into controlled slowing or rejection rather than hidden resource exhaustion.

#### Production angle

Good backpressure prevents retry storms, OOMs, thread starvation, and database pool exhaustion during dependency degradation.

#### Traps / caveats

- An unbounded queue is not resilience; it delays failure and consumes memory.
- Scaling consumers may worsen an outage if the downstream is already saturated.

</details>
