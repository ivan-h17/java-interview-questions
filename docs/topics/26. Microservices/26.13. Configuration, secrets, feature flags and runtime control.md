# Configuration, secrets, feature flags and runtime control

---

<a id="ms-conf-007"></a>

<details>
<summary><strong>🧠 MS-CONF-007. How do services reload configuration safely?</strong></summary>

#### Short answer

Reload only validated runtime-safe configuration, apply changes atomically, and keep rollback or previous-value behavior.

#### Interview answer

Some config can change at runtime, like limits or feature flags. Other config, such as database URL or core security settings, may require restart. Runtime reload should validate values, apply them consistently across threads, emit audit logs, and expose current config version.

#### Deep dive

Dynamic config needs ownership and change control because a bad value can cause an outage faster than a code release.

#### Production angle

Use staged rollout, canary, monitoring, and kill switches for high-risk changes.

#### Traps / caveats

- Do not reload secrets or connection settings casually without lifecycle handling.
- Do not let invalid config partially apply.

</details>

<a id="ms-conf-009"></a>

<details>
<summary><strong>MS-CONF-009. How do feature flags help with microservice releases?</strong></summary>

#### Short answer

They decouple deployment from feature activation and support gradual rollout, rollback, and experimentation.

#### Interview answer

A service can deploy code with a feature disabled, then enable it for internal users, a canary group, one tenant, or a percentage of traffic. Flags also allow quick disablement if behavior causes errors.

#### Deep dive

Feature flags are especially useful for backward-compatible migrations, API changes, and gradual consumer rollout.

#### Production angle

Flags need ownership, audit, cleanup, and monitoring because stale flags become hidden complexity.

#### Traps / caveats

- Do not use flags to hide incompatible contracts.
- Long-lived flags create many untested code paths.

</details>

<a id="ms-conf-010"></a>

<details>
<summary><strong>MS-CONF-010. What are the risks of feature flags?</strong></summary>

#### Short answer

They can create hidden complexity, inconsistent behavior, stale code paths, and risky runtime changes.

#### Interview answer

Each flag adds a branch that should be tested, monitored, documented, and eventually removed. Bad flag configuration can enable features for the wrong users, break assumptions between services, or cause a sudden traffic spike.

#### Deep dive

Flags need types: release flags, ops flags, experiment flags, and permission flags have different lifetimes and controls.

#### Production angle

Feature flag changes should be auditable and sometimes require approvals, just like deployments.

#### Traps / caveats

- Do not leave release flags forever.
- Do not use a flag system as an ungoverned production control plane.

</details>

<a id="ms-conf-013"></a>

<details>
<summary><strong>MS-CONF-013. How should secrets rotation work without downtime?</strong></summary>

#### Short answer

Support overlap between old and new credentials, roll services gradually, verify, then revoke the old secret.

#### Interview answer

For database passwords, API keys, or certificates, the provider should accept both old and new credentials during rotation. Services reload or restart with the new secret, health checks verify success, and only then is the old secret disabled.

#### Deep dive

Some clients cannot reload credentials safely, so planned rolling restart may be better than dynamic reload.

#### Production angle

Rotation needs audit logs, alerts for authentication failures, and a rollback path if the new secret fails.

#### Traps / caveats

- Do not revoke the old secret before all instances use the new one.
- Do not rotate only the application side if the provider is not ready.

</details>

<a id="ms-conf-014"></a>

<details>
<summary><strong>🧠 MS-CONF-014. What happens if a configuration change breaks one service instance?</strong></summary>

#### Short answer

The platform should detect failed readiness or errors, stop routing to the bad instance, and allow rollback of the config.

#### Interview answer

If config is rolled out gradually, only a subset of instances should be affected. Readiness checks, error metrics, and canary analysis should catch it. The config system should support versioning, audit, and rollback.

#### Deep dive

Dynamic configuration can fail faster than deployments because it may change many instances at once without a build pipeline.

#### Production angle

Treat risky config changes like releases: staged rollout, owner approval, monitoring, and rollback.

#### Traps / caveats

- Do not push global config changes without blast-radius control.
- Do not make readiness depend on optional config that can temporarily fail.

</details>
