# Testing microservices

---

<a id="ms-test-001"></a>

<details>
<summary><strong>MS-TEST-001. How do you test microservices?</strong></summary>

#### Short answer

Use a layered strategy: unit, component, integration, contract, migration, messaging, and limited end-to-end tests.

#### Interview answer

Most tests should verify service behavior in isolation with real boundaries where useful. Contract tests protect API and event compatibility. Integration tests cover databases, brokers, and HTTP clients. End-to-end tests should be few and focused on critical flows.

#### Deep dive

Microservice testing is about confidence without requiring the whole system for every change.

#### Production angle

The test strategy should catch breaking contracts, unsafe migrations, idempotency bugs, and retry/DLQ behavior before release.

#### Traps / caveats

- Too many E2E tests become slow and flaky.
- Unit tests alone do not prove service integration safety.

</details>

<a id="ms-test-003"></a>

<details>
<summary><strong>MS-TEST-003. What is consumer-driven contract testing?</strong></summary>

#### Short answer

Consumers define expectations for a provider API or event, and the provider verifies it still satisfies them.

#### Interview answer

In consumer-driven contracts, each consumer records the requests, responses, fields, and behavior it depends on. The provider runs those contracts in CI to detect breaking changes before deployment.

#### Deep dive

It helps independent deployment because providers can evolve safely while knowing which consumer expectations matter.

#### Production angle

Contract tests reduce surprise runtime failures after a provider release.

#### Traps / caveats

- Contracts should capture behavior, not implementation internals.
- Consumer contracts can become stale if consumers do not maintain them.

</details>

<a id="ms-test-004"></a>

<details>
<summary><strong>MS-TEST-004. When would you use contract tests?</strong></summary>

#### Short answer

Use them for service APIs and events that have independent producers and consumers.

#### Interview answer

Contract tests are valuable when teams deploy independently and a provider change can break consumers. They are especially useful for REST APIs, message schemas, error formats, required fields, and backward compatibility.

#### Deep dive

They do not replace integration or end-to-end tests; they specifically protect contracts.

#### Production angle

Run contract checks in CI and before deployment of provider changes.

#### Traps / caveats

- Do not use contract tests to assert provider database details.
- They cannot prove all business workflows across many services.

</details>

<a id="ms-test-006"></a>

<details>
<summary><strong>MS-TEST-006. Why are too many end-to-end tests risky in microservice systems?</strong></summary>

#### Short answer

They are slow, flaky, hard to debug, and couple many services' release cycles.

#### Interview answer

An E2E test fails if any service, environment, network, database, broker, or test data setup is unstable. That makes failures expensive to diagnose. E2E tests should cover a small number of critical user journeys, not every edge case.

#### Deep dive

Prefer testing most behavior closer to the owning service and using contracts for boundaries.

#### Production angle

Flaky E2E suites cause teams to ignore failures or delay releases unnecessarily.

#### Traps / caveats

- Do not remove all E2E tests; keep critical smoke flows.
- Do not use E2E tests as a substitute for service-level tests.

</details>

<a id="ms-test-008"></a>

<details>
<summary><strong>MS-TEST-008. How do you test asynchronous messaging?</strong></summary>

#### Short answer

Test producer contracts, consumer behavior, idempotency, retry paths, ordering assumptions, and DLQ handling.

#### Interview answer

Producer tests should verify message schema and metadata. Consumer tests should run with realistic broker or test container setup and cover duplicate messages, out-of-order events, poison messages, and offset/ack behavior.

#### Deep dive

Async tests must avoid sleeps where possible. Use polling with timeouts, deterministic test data, and observable state.

#### Production angle

Messaging bugs often appear only under redelivery, replay, or downstream outage, so test those explicitly.

#### Traps / caveats

- Do not test only the happy path consume event.
- Do not rely on fixed sleeps that make tests flaky.

</details>

<a id="ms-test-009"></a>

<details>
<summary><strong>🧠 MS-TEST-009. How do you test Saga workflows?</strong></summary>

#### Short answer

Test the state machine, participant contracts, retries, compensation, timeouts, and stuck workflow recovery.

#### Interview answer

I would test the orchestrator or choreography flow with fake or real participant boundaries. Cases should include all-success, business rejection, technical retry, compensation success, compensation failure, duplicate messages, and timeout.

#### Deep dive

The Saga should expose state that tests can assert deterministically, rather than depending only on logs.

#### Production angle

Saga tests should mirror support scenarios: "what happens to order X if payment times out?"

#### Traps / caveats

- Do not test only the successful path.
- Do not ignore idempotency and duplicate command handling.

</details>

<a id="ms-test-011"></a>

<details>
<summary><strong>MS-TEST-011. How do you test idempotent consumers?</strong></summary>

#### Short answer

Deliver the same message multiple times and verify the business effect happens once.

#### Interview answer

Tests should send duplicate events or commands with the same idempotency key, including after simulated crash or transaction rollback. Verify database state, external call count, processed-message records, and returned result.

#### Deep dive

Use real unique constraints or transaction behavior in tests where possible because races are easy to miss with mocks.

#### Production angle

Idempotency tests protect DLQ replay, broker redelivery, and consumer restarts.

#### Traps / caveats

- Do not test only in-memory deduplication.
- Do not forget duplicate side effects to external systems.

</details>

---

<a id="ms-test-012"></a>

<details>
<summary><strong>🧠 MS-TEST-012. How do you test retry and DLQ behavior?</strong></summary>

#### Short answer

Inject transient and permanent failures and verify retry count, backoff behavior, DLQ metadata, and safe reprocessing.

#### Interview answer

Transient dependency failure should retry and eventually succeed. Permanent poison data should stop after configured attempts and move to DLQ with original payload and error context. Reprocessing should not duplicate side effects.

#### Deep dive

Tests should cover failure classification because retrying permanent failures creates noise and delaying transient failures too early can lose work.

#### Production angle

DLQ tests validate operational recovery, not just code correctness.

#### Traps / caveats

- Do not make retry tests sleep for real backoff durations.
- Do not drop original failure metadata.

</details>

<a id="ms-test-017"></a>

<details>
<summary><strong>MS-TEST-017. How do you test backward compatibility of APIs and events?</strong></summary>

#### Short answer

Run old consumer expectations against new provider behavior and test old data/messages against new consumers.

#### Interview answer

For APIs, use contract tests and sample payloads from existing clients. For events, validate schema compatibility and replay representative old messages into new consumers. Also test unknown fields, missing optional fields, and default values.

#### Deep dive

Compatibility is semantic as well as syntactic. A field can keep the same type but change meaning and still break consumers.

#### Production angle

Compatibility testing supports rolling deployments and independent releases.

#### Traps / caveats

- Do not test only generated schemas.
- Do not remove fields before all consumers stop depending on them.

</details>

<a id="ms-test-018"></a>

<details>
<summary><strong>MS-TEST-018. How do you test database migrations in a microservice?</strong></summary>

#### Short answer

Test migrations from production-like old schemas and data, with rolling deployment compatibility.

#### Interview answer

Run migration tests against snapshots or representative data, verify locks and runtime, and test old code with new schema and new code with transitional schema when using expand-and-contract. Include rollback or roll-forward behavior.

#### Deep dive

Migrations are part of deployment, not just database administration. They must be compatible with service version skew.

#### Production angle

Test for long locks, slow backfills, failed constraints, and data repair scripts.

#### Traps / caveats

- Do not rely only on an empty database migration test.
- Do not combine a breaking schema change with a single irreversible code deploy.

</details>

<a id="ms-test-019"></a>

<details>
<summary><strong>🧠 MS-TEST-019. How do you keep test environments reliable for many services?</strong></summary>

#### Short answer

Prefer isolated service tests, ephemeral dependencies, contract testing, deterministic data, and a small number of shared E2E environments.

#### Interview answer

Shared environments become unstable when many teams deploy and mutate data. Use local or CI test containers for service-level tests, mocks for owned contracts, and carefully managed staging for critical integration flows.

#### Deep dive

Environment reliability is an architecture problem: contracts and component tests reduce dependence on full-system environments.

#### Production angle

Unreliable test environments slow releases and train teams to ignore failures.

#### Traps / caveats

- Do not let shared staging become the only quality gate.
- Do not use uncontrolled shared test data.

</details>

<a id="ms-test-021"></a>

<details>
<summary><strong>MS-TEST-021. How do you avoid flaky distributed tests?</strong></summary>

#### Short answer

Make tests deterministic, isolate dependencies, control time, avoid fixed sleeps, and assert observable outcomes.

#### Interview answer

Use unique test data, polling with timeouts instead of sleeps, stable contracts, controlled clocks, and resettable dependencies. Keep E2E tests few and make failures diagnosable with logs, traces, and artifacts.

#### Deep dive

Flakiness often comes from race conditions, shared state, timing assumptions, and unstable environments.

#### Production angle

A flaky suite reduces trust and can block urgent releases or allow broken releases through.

#### Traps / caveats

- Do not solve flakiness by only increasing sleeps.
- Do not ignore flaky tests; they often reveal real concurrency or integration assumptions.

</details>
