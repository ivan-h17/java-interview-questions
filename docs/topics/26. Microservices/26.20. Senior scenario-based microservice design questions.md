# Senior scenario-based microservice design questions

---

<a id="ms-scen-001"></a>

<details>
<summary><strong>MS-SCEN-001. Design an order checkout flow with payment, inventory reservation and shipping as microservices.</strong></summary>

#### Short answer

Use an order service as workflow owner, reserve inventory, authorize payment, then confirm order and trigger fulfillment.

#### Interview answer

Create an order in `PENDING` state with an idempotency key. Reserve inventory and authorize payment through idempotent commands. If both succeed, mark the order confirmed and publish events for shipping and notification. If a step fails, compensate completed steps.

#### Deep dive

Prefer payment authorization before capture so failures can be handled without refunding captured money.

#### Production angle

Track Saga state, correlation IDs, payment provider references, inventory reservations, and manual repair actions.

#### Traps / caveats

- Do not pretend the whole flow is one ACID transaction.
- Do not ignore duplicate checkout requests.

</details>

<a id="ms-scen-002"></a>

<details>
<summary><strong>MS-SCEN-002. How would you redesign a synchronous checkout flow that frequently fails because one downstream service is slow?</strong></summary>

#### Short answer

Remove non-critical work from the request path, add timeouts and isolation, and consider asynchronous workflow for slow steps.

#### Interview answer

First identify the slow dependency with traces and metrics. If it is optional, degrade or move it async. If it is required, add strict timeouts, bulkheads, circuit breakers, and idempotency. For long-running work, accept checkout as pending and complete through a Saga.

#### Deep dive

The user experience may need to shift from "completed immediately" to "accepted and processing" if the business can tolerate it.

#### Production angle

Monitor pending age, failure rate, fallback rate, and downstream saturation.

#### Traps / caveats

- Do not just increase timeouts.
- Do not retry slow required calls without budget and idempotency.

</details>

<a id="ms-scen-003"></a>

<details>
<summary><strong>MS-SCEN-003. How would you handle payment succeeded but inventory reservation failed?</strong></summary>

#### Short answer

Compensate the payment, mark the order failed or pending repair, and make the operation auditable and idempotent.

#### Interview answer

If payment was only authorized, void the authorization. If money was captured, issue a refund according to business policy. Release or avoid inventory reservation, update order state, notify the user, and record the provider reference for reconciliation.

#### Deep dive

The exact compensation depends on whether payment was authorized or captured and what the provider guarantees.

#### Production angle

This scenario needs manual repair tooling because provider outcomes can be ambiguous.

#### Traps / caveats

- Do not retry inventory forever while holding customer money silently.
- Do not issue duplicate refunds; compensation must be idempotent.

</details>

<a id="ms-scen-005"></a>

<details>
<summary><strong>MS-SCEN-005. How would you design idempotent order creation with client retries?</strong></summary>

#### Short answer

Require a client idempotency key and store it with the created order and response.

#### Interview answer

When the client submits checkout, it sends a stable key. The order service stores the key with a unique constraint and the resulting order. If the same key arrives again, return the original result instead of creating another order.

#### Deep dive

The key should be scoped to user or tenant and operation type so two different requests are not collapsed accidentally.

#### Production angle

Store status as well as result so retries during an in-progress workflow return a meaningful pending state.

#### Traps / caveats

- Do not generate a new key on every retry.
- Do not rely only on client-side retry behavior for deduplication.

</details>

<a id="ms-scen-006"></a>

<details>
<summary><strong>MS-SCEN-006. How would you prevent duplicate payment charges in a microservice system?</strong></summary>

#### Short answer

Use payment idempotency keys, unique business references, state machines, and provider reconciliation.

#### Interview answer

Each payment attempt should have a stable idempotency key and provider reference. The service should store attempts with unique constraints, call the provider idempotently, and never capture twice for the same order unless there is a new explicit business operation.

#### Deep dive

Timeouts are ambiguous, so after an unknown outcome the service should query or reconcile with the provider rather than blindly retry capture.

#### Production angle

Payment flows need audit logs, manual repair, and alerts for duplicate or inconsistent provider states.

#### Traps / caveats

- Do not use only order ID if multiple legitimate payment attempts can exist.
- Do not retry non-idempotent provider calls after timeout.

</details>

<a id="ms-scen-007"></a>

<details>
<summary><strong>MS-SCEN-007. How would you debug a request that is slow only in production and passes through five services?</strong></summary>

#### Short answer

Use traces to find the slow span, then correlate with dependency metrics, saturation, data shape, and recent changes.

#### Interview answer

I would start with affected trace IDs, compare normal and slow requests, and locate where time is spent. Then check database queries, connection pools, downstream calls, retries, GC, queueing, and version rollout. Production-only issues often involve data volume, traffic, or dependency behavior absent in tests.

#### Deep dive

Look at p99 and outliers, not only average latency.

#### Production angle

Mitigate first if users are impacted: rollback, disable feature, shed optional work, or reduce traffic.

#### Traps / caveats

- Do not assume the first service in the path is the cause.
- Do not debug only from logs if traces and metrics exist.

</details>

<a id="ms-scen-008"></a>

<details>
<summary><strong>MS-SCEN-008. How would you handle a sudden spike in consumer lag?</strong></summary>

#### Short answer

Identify whether production increased, consumption slowed, or downstream processing is failing, then scale or throttle accordingly.

#### Interview answer

Check input rate, consumer error rate, processing latency, downstream dependency health, rebalances, deployment changes, and partition distribution. If downstreams are healthy, add consumers within partition limits. If downstreams are failing, pause, throttle, or shed work rather than amplifying load.

#### Deep dive

Lag count and lag age both matter. A small number of old messages can be more urgent than a large burst of fresh ones.

#### Production angle

Watch DLQ growth, retry rate, oldest message age, and business SLA for processing delay.

#### Traps / caveats

- More consumers do not help if partitions or downstream capacity are limiting.
- Do not replay DLQ while the root cause remains.

</details>

<a id="ms-scen-009"></a>

<details>
<summary><strong>MS-SCEN-009. How would you handle a downstream service outage without taking down the whole system?</strong></summary>

#### Short answer

Contain the failure with timeouts, circuit breakers, bulkheads, fallback or degradation, and backpressure.

#### Interview answer

First classify whether the downstream is critical or optional. Optional features can degrade or use cached data. Critical workflows may return pending state or fail fast. Protect the caller with bounded concurrency and avoid retries that overload the failing service.

#### Deep dive

The right behavior depends on business semantics. Some operations should stop rather than proceed incorrectly.

#### Production angle

Alert on dependency outage and fallback use, then coordinate recovery and replay if work was queued.

#### Traps / caveats

- Do not hide critical failures as success.
- Do not let retry storms prevent downstream recovery.

</details>

<a id="ms-scen-012"></a>

<details>
<summary><strong>MS-SCEN-012. How would you split a shared database without downtime?</strong></summary>

#### Short answer

Use phased ownership, compatible schemas, data sync, dual-read/write only when controlled, validation, and gradual cutover.

#### Interview answer

First identify the owning service and block new external writes. Create the new store, backfill data, keep it in sync with events or CDC, validate parity, switch reads and writes gradually, then remove old access after monitoring.

#### Deep dive

The hardest part is hidden consumers and transactional assumptions around shared tables.

#### Production angle

Track sync lag, mismatch count, write errors, and old database access logs.

#### Traps / caveats

- Do not do one-time copy for data that still changes.
- Do not cut over without rollback or repair plan.

</details>

<a id="ms-scen-015"></a>

<details>
<summary><strong>MS-SCEN-015. How would you detect and stop a retry storm?</strong></summary>

#### Short answer

Detect spikes in retries, traffic, latency, and dependency saturation; stop it with backoff, jitter, circuit breakers, rate limits, and load shedding.

#### Interview answer

I would identify which clients or services are retrying, whether retries are layered, and which dependency is failing. Immediate mitigations are disabling retries, opening breakers, reducing traffic, applying rate limits, or pausing consumers.

#### Deep dive

Retry storms often start from a small failure that gets amplified by many callers retrying simultaneously.

#### Production angle

Dashboards should show retry attempts separately from original request rate.

#### Traps / caveats

- Do not scale callers during a downstream retry storm.
- Do not forget SDK or service-mesh retries.

</details>

<a id="ms-scen-016"></a>

<details>
<summary><strong>MS-SCEN-016. How would you decide whether to use Saga, Outbox or 2PC for a business flow?</strong></summary>

#### Short answer

Use Outbox for reliable publication, Saga for multi-service workflows, and 2PC only in narrow cases where atomic coordination is acceptable and supported.

#### Interview answer

If one service updates data and must publish an event, use Outbox. If multiple services must complete a business process with local transactions, use Saga. If strict atomicity across resources is required and the environment supports it with acceptable availability trade-offs, consider 2PC.

#### Deep dive

These patterns solve different problems and are often combined. Saga steps frequently use Outbox.

#### Production angle

The decision depends on consistency requirements, failure handling, operations maturity, and business tolerance for pending states.

#### Traps / caveats

- Do not use Saga when the invariant really belongs inside one service.
- Do not dismiss 2PC dogmatically, but know its operational cost.

</details>

<a id="ms-scen-017"></a>

<details>
<summary><strong>MS-SCEN-017. How would you design a microservice to satisfy a 99.9% availability SLO?</strong></summary>

#### Short answer

Define the user-facing SLI, remove single points of failure, isolate dependencies, and design graceful degradation.

#### Interview answer

I would define what counts as available, then design redundant instances, safe deployments, health checks, timeouts, dependency bulkheads, database HA, rollback, monitoring, and incident response. Dependencies must have compatible reliability or the service must degrade around them.

#### Deep dive

99.9% allows about 43 minutes of downtime per 30 days, so deployment and dependency failures matter.

#### Production angle

Use error budget burn alerts and release gates tied to SLO health.

#### Traps / caveats

- Do not promise an SLO higher than critical dependencies can support.
- Do not count only server uptime; count successful user operations.

</details>

<a id="ms-scen-019"></a>

<details>
<summary><strong>MS-SCEN-019. How would you roll out a breaking API change safely?</strong></summary>

#### Short answer

Avoid breaking in place: add a compatible version, migrate consumers, monitor usage, then retire the old contract.

#### Interview answer

Introduce a new endpoint, version, or field while keeping old behavior. Publish migration guidance and contract tests. Track consumers through logs or API catalog. Once traffic to the old contract is gone and old deployments are retired, remove it.

#### Deep dive

Sometimes the best "breaking change" is an additive change plus new semantics under a new resource or media type.

#### Production angle

Use canaries and rollback for the provider, but also coordinate consumer readiness.

#### Traps / caveats

- Do not change response meaning silently.
- Do not trust that all internal clients update immediately.

</details>

<a id="ms-scen-020"></a>

<details>
<summary><strong>MS-SCEN-020. How would you roll out a breaking event schema change safely?</strong></summary>

#### Short answer

Publish a compatible new version, migrate consumers, handle historical replay, and retire the old version only after usage is gone.

#### Interview answer

For events, I would avoid breaking existing schemas. Add optional fields or create a new event version/type. Consumers migrate independently. The producer may publish both versions for a period. Historical events need upcasting or old-schema support.

#### Deep dive

Events are harder than APIs because consumers can be unknown and old messages can be replayed.

#### Production angle

Monitor consumer errors, schema registry compatibility, and usage of old versions.

#### Traps / caveats

- Do not remove fields required by historical replay.
- Do not reuse the same event name with incompatible semantics.

</details>

<a id="ms-scen-021"></a>

<details>
<summary><strong>🧠 MS-SCEN-021. How would you build a read model that combines data from multiple services?</strong></summary>

#### Short answer

Subscribe to source service events and maintain a projection optimized for the query.

#### Interview answer

Each owning service publishes integration events for relevant changes. A projection service consumes them, stores a read model, and serves queries. It must handle duplicates, out-of-order events, schema evolution, rebuilds, and projection lag.

#### Deep dive

The read model is derived data, not the source of truth. Rebuild and reconciliation capability are important.

#### Production angle

Expose lag, freshness, rebuild status, and skipped/failed events.

#### Traps / caveats

- Do not let the projection become the write authority accidentally.
- Do not hide stale data if users expect current state.

</details>

<a id="ms-scen-024"></a>

<details>
<summary><strong>MS-SCEN-024. How would you set timeouts for a request path that calls three downstream services?</strong></summary>

#### Short answer

Start with the end-to-end deadline and allocate per-call budgets based on criticality and latency percentiles.

#### Interview answer

If the API budget is 800 ms, reserve time for gateway, app logic, serialization, and retries. Then assign budgets to each downstream. Required calls get enough time for normal p95 behavior; optional calls get shorter timeouts and fallback. Retries must fit inside the same deadline.

#### Deep dive

For parallel calls, the slowest required dependency controls response time. For sequential calls, the budgets add.

#### Production angle

Instrument timeout rate and dependency latency to tune values after deployment.

#### Traps / caveats

- Do not give each downstream a separate 2-second timeout.
- Do not retry after the user-facing deadline has already expired.

</details>

<a id="ms-scen-025"></a>

<details>
<summary><strong>MS-SCEN-025. How would you decide whether a new feature should be a new service or part of an existing service?</strong></summary>

#### Short answer

Choose a new service only if it has a clear business boundary, ownership, data responsibility, and independent lifecycle.

#### Interview answer

I would ask whether the feature belongs to an existing bounded context, shares invariants or transactions, changes with the same team, and needs the same data. A new service is justified by independent scaling, release cadence, availability/security needs, or team ownership.

#### Deep dive

Starting inside a modular boundary can be a good option when the domain is still uncertain.

#### Production angle

Every new service adds deployment, monitoring, security, testing, and on-call cost.

#### Traps / caveats

- Do not create a new service because the feature is "big".
- Do not bury a genuinely separate capability in a service nobody owns.

</details>
