# Migration, decomposition and Strangler Fig

---

<a id="ms-mig-002"></a>

<details>
<summary><strong>MS-MIG-002. When would you use the Strangler Fig pattern?</strong></summary>

#### Short answer

Use it when replacing or decomposing a legacy system incrementally instead of doing a risky big-bang rewrite.

#### Interview answer

The idea is to route selected functionality to new services while the old system continues serving the rest. Over time, more routes, data flows, or capabilities move to the new implementation until the old part can be retired.

#### Deep dive

It works best when there is a clear boundary to extract and a routing layer that can direct traffic safely.

#### Production angle

Strangler migrations need observability, rollback, data synchronization, and parity validation.

#### Traps / caveats

- Do not run two implementations indefinitely without ownership.
- Do not start with the hardest core domain flow unless risk is justified.

</details>

<a id="ms-mig-003"></a>

<details>
<summary><strong>MS-MIG-003. How do you migrate from a monolith to microservices incrementally?</strong></summary>

#### Short answer

First create modular boundaries, then extract one capability at a time with routing, contracts, and data ownership plans.

#### Interview answer

I would identify a bounded capability with manageable risk, build a service around it, route some traffic to it, validate behavior against the monolith, and gradually move ownership. Database separation usually happens in phases, not as a first blind cut.

#### Deep dive

Before extraction, clean module boundaries inside the monolith often reveal whether the split is viable.

#### Production angle

Use feature flags, canaries, parallel run, metrics, and rollback during extraction.

#### Traps / caveats

- Do not rewrite the whole monolith in parallel.
- Do not extract code while leaving all data and rules shared without a plan.

</details>

<a id="ms-mig-005"></a>

<details>
<summary><strong>MS-MIG-005. How do you avoid a big-bang rewrite?</strong></summary>

#### Short answer

Deliver small slices, keep the old system running, and migrate traffic and data gradually.

#### Interview answer

A big-bang rewrite is risky because value arrives late and parity is hard to prove. Instead, choose one capability, create an adapter or routing layer, run old and new implementations side by side where useful, and move consumers incrementally.

#### Deep dive

The migration should produce production value after each step, not only after the whole rewrite.

#### Production angle

Incremental migration allows real traffic validation and quick rollback for small pieces.

#### Traps / caveats

- Do not underestimate hidden behavior in legacy systems.
- Do not let the migration create permanent duplicate systems.

</details>

<a id="ms-mig-006"></a>

<details>
<summary><strong>MS-MIG-006. How do you route traffic during monolith decomposition?</strong></summary>

#### Short answer

Use a gateway, reverse proxy, feature flag, or routing adapter to send selected requests to the new service.

#### Interview answer

Routing can be by endpoint, tenant, user cohort, percentage, or feature flag. Start with low-risk traffic, observe behavior, and keep rollback to the monolith available until the new service is proven.

#### Deep dive

Routing must handle sessions, auth, idempotency, and different response shapes if old and new implementations are not identical.

#### Production angle

Monitor old versus new success rate, latency, business outcomes, and error categories.

#### Traps / caveats

- Do not split traffic if both systems write conflicting data.
- Do not forget cache and client behavior during routing changes.

</details>

<a id="ms-mig-007"></a>

<details>
<summary><strong>MS-MIG-007. How do you split a database when extracting a service?</strong></summary>

#### Short answer

Move ownership gradually: isolate access, create new schema, synchronize data, switch writes, migrate reads, then remove old access.

#### Interview answer

First identify tables and invariants owned by the new service. Stop other modules from writing them directly. Use events, CDC, or backfills to populate the new store. Switch writes through the service, then migrate reads to APIs or projections.

#### Deep dive

Database splitting is usually the hardest part because hidden joins and transactions reveal real coupling.

#### Production angle

Validate counts, checksums, business invariants, lag, and error rates during migration.

#### Traps / caveats

- Do not copy tables once and assume synchronization is solved.
- Do not break reporting and admin jobs without replacements.

</details>

<a id="ms-mig-010"></a>

<details>
<summary><strong>MS-MIG-010. How do you validate that a new service behaves like the old module?</strong></summary>

#### Short answer

Use contract tests, golden test cases, shadow traffic, parallel run, and business outcome comparison.

#### Interview answer

Capture expected behavior from the monolith, including edge cases. Run the new service against the same inputs and compare responses, state changes, events, and side effects. For low-risk cases, shadow production traffic without affecting users.

#### Deep dive

Behavioral parity includes error handling, validation, permissions, timing assumptions, and data rounding or default rules.

#### Production angle

Track mismatch rate and investigate before moving more traffic.

#### Traps / caveats

- Do not compare only HTTP status codes.
- Do not let shadow traffic trigger real external side effects.

</details>

<a id="ms-mig-011"></a>

<details>
<summary><strong>🧠 MS-MIG-011. How do you handle data synchronization during migration?</strong></summary>

#### Short answer

Use controlled dual writes, events, CDC, or scheduled backfills with reconciliation and a clear cutover plan.

#### Interview answer

The safest approach depends on ownership and write paths. CDC can replicate changes from the old database, events can publish domain changes, and backfills can initialize historical data. Reconciliation verifies the new service matches the source before cutover.

#### Deep dive

Dual writes are risky unless made reliable through Outbox or transactional mechanisms.

#### Production angle

Monitor lag, failed sync records, mismatch counts, and cutover readiness.

#### Traps / caveats

- Do not ignore deletes and corrections.
- Do not assume source and target schemas have identical semantics.

</details>

<a id="ms-mig-012"></a>

<details>
<summary><strong>MS-MIG-012. How do you retire old monolith functionality safely?</strong></summary>

#### Short answer

Verify no traffic or dependencies remain, freeze old writes, archive data if needed, and remove code in controlled steps.

#### Interview answer

Before removal, check routing metrics, logs, database access, batch jobs, reports, admin tools, and customer support flows. Then disable with a flag or route change, monitor, and remove code and schema only after a safe period.

#### Deep dive

Retirement is part of migration. Leaving old paths alive creates duplicate behavior and future incidents.

#### Production angle

Keep rollback or restoration options until confidence is high.

#### Traps / caveats

- Do not remove code while hidden batch jobs still depend on tables.
- Do not forget documentation, runbooks, and alerts.

</details>

<a id="ms-mig-014"></a>

<details>
<summary><strong>MS-MIG-014. What are common failure modes of monolith-to-microservice migration?</strong></summary>

#### Short answer

Wrong boundaries, shared databases forever, big-bang rewrites, missing observability, and underestimated operational cost.

#### Interview answer

Teams often extract services by tables or technical layers, creating chatty distributed systems. They may keep shared data and still expect independent deployment. Another failure mode is rebuilding everything before users see value, then discovering hidden legacy behavior late.

#### Deep dive

Migration fails when the architecture changes faster than domain understanding, platform maturity, and team ownership.

#### Production angle

Failure appears as slower delivery, more incidents, and services nobody wants to own.

#### Traps / caveats

- Do not migrate only to follow a trend.
- Do not ignore the cost of operating more deployables.

</details>

<a id="ms-mig-015"></a>

<details>
<summary><strong>MS-MIG-015. When should you stop splitting the monolith?</strong></summary>

#### Short answer

Stop when additional splits no longer improve ownership, delivery, scaling, or reliability enough to justify the complexity.

#### Interview answer

If a module changes with the same team, shares invariants, needs local transactions, and has no independent scaling or release need, it may be better inside the existing service or modular monolith. Splitting should solve a real constraint.

#### Deep dive

Microservices are not a target count. The right architecture is the smallest one that supports business and operational needs.

#### Production angle

Too many services increase platform cost, incident surface, and cognitive load.

#### Traps / caveats

- Do not split just because code is large.
- Do not keep splitting when the team cannot operate the existing services well.

</details>
