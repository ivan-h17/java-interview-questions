# Authentication, authorization and security

---

<a id="ms-sec-001"></a>

<details>
<summary><strong>MS-SEC-001. How do you implement authentication and authorization in microservices?</strong></summary>

#### Short answer

Authenticate at the edge, propagate trusted identity, and enforce authorization both at the edge and inside services that own resources.

#### Interview answer

The API Gateway or identity layer usually validates user login and tokens. Services should validate tokens or trusted identity context, enforce resource-level authorization, and never rely only on client claims. Service-to-service calls need their own authentication, often through mTLS, signed tokens, or platform identity.

#### Deep dive

Authorization belongs near the data and business action because only the owning service fully understands resource rules.

#### Production angle

Security decisions need audit logs, token validation metrics, secret rotation, and fail-closed behavior.

#### Traps / caveats

- Gateway-only authorization is usually insufficient.
- Do not trust arbitrary headers from clients as identity.

</details>

---

<a id="ms-sec-007"></a>

<details>
<summary><strong>MS-SEC-007. Should each service validate access tokens?</strong></summary>

#### Short answer

Usually yes, or it should receive identity through a trusted internal mechanism with equivalent validation guarantees.

#### Interview answer

Each service should not blindly trust that a request passed through the gateway. It should validate token signature, issuer, audience, expiration, and scopes, or rely on verified identity from a service mesh or trusted proxy. The exact approach depends on architecture.

#### Deep dive

Defense in depth matters because internal routes, misconfigured gateways, and compromised services can bypass assumptions.

#### Production angle

Token validation must handle key rotation, clock skew, and identity provider outages.

#### Traps / caveats

- Do not skip audience checks.
- Do not accept unsigned or weakly validated JWTs.

</details>

<a id="ms-sec-008"></a>

<details>
<summary><strong>MS-SEC-008. How do you propagate user identity between services?</strong></summary>

#### Short answer

Propagate only the necessary verified identity and authorization context, using signed tokens or trusted infrastructure metadata.

#### Interview answer

A service can forward the user's token when downstream needs user-level authorization, or exchange it for a token with a narrower audience. It can also pass correlation and tenant context separately. Downstream services should verify the source and token claims.

#### Deep dive

Avoid spreading raw user context everywhere. Use least privilege and explicit audiences.

#### Production angle

Identity propagation needs traceability: which user triggered which service action.

#### Traps / caveats

- Do not pass identity in unsigned headers from external clients.
- Do not give every downstream the same broad token if it needs only narrow permissions.

</details>

<a id="ms-sec-009"></a>

<details>
<summary><strong>MS-SEC-009. What is service-to-service authentication?</strong></summary>

#### Short answer

It proves the identity of the calling service to the receiving service.

#### Interview answer

Service-to-service authentication can use mTLS certificates, signed service tokens, workload identity, or platform-level identity. It answers "which service is calling?" before authorization answers "is that service allowed to do this?"

#### Deep dive

This is separate from end-user identity. A request may carry both user identity and caller service identity.

#### Production angle

Strong service identity supports least privilege, audit, and blast-radius reduction after compromise.

#### Traps / caveats

- Internal network location is not strong identity.
- Do not let all services share the same credential.

</details>

---

<a id="ms-sec-010"></a>

<details>
<summary><strong>🧠 MS-SEC-010. What is mTLS, and when is it useful between services?</strong></summary>

#### Short answer

mTLS is mutual TLS: both client and server authenticate each other with certificates while encrypting traffic.

#### Interview answer

It is useful when services need strong workload identity and encrypted internal communication. In Kubernetes, a service mesh can manage certificates and enforce mTLS policies without each application hand-rolling TLS.

#### Deep dive

mTLS proves service identity, but it does not replace application-level authorization or user-level permissions.

#### Production angle

Certificate rotation, trust roots, mesh policy, and observability are operational concerns.

#### Traps / caveats

- mTLS says who is calling, not whether the business action is allowed.
- Certificate misconfiguration can create broad outages.

</details>

<a id="ms-sec-012"></a>

<details>
<summary><strong>🧠 MS-SEC-012. What does zero trust mean in microservice environments?</strong></summary>

#### Short answer

Zero trust means services verify identity, authorization, and policy even inside the internal network.

#### Interview answer

The old model trusted anything inside the network. Zero trust treats internal calls as potentially risky: authenticate workloads, authorize actions, encrypt traffic, enforce least privilege, validate input, and audit access.

#### Deep dive

Zero trust is a set of controls, not one product. Service mesh, identity provider, network policy, secrets management, and application authorization all contribute.

#### Production angle

It reduces lateral movement if one service or credential is compromised.

#### Traps / caveats

- Do not confuse zero trust with blocking all communication.
- Network policy cannot replace resource-level authorization.

</details>

<a id="ms-sec-013"></a>

<details>
<summary><strong>MS-SEC-013. How should authorization be split between API Gateway and services?</strong></summary>

#### Short answer

The gateway enforces coarse edge policy; services enforce resource and business authorization.

#### Interview answer

The gateway can validate tokens, reject unauthenticated requests, check broad scopes, rate-limit, and block invalid clients. Services should still check whether the caller can access the specific order, account, tenant, or action.

#### Deep dive

The owning service has the domain data needed for object-level checks, such as whether user A can approve invoice B.

#### Production angle

Defense in depth protects against misrouting, internal misuse, and gateway configuration mistakes.

#### Traps / caveats

- Do not put all authorization only in the gateway.
- Do not duplicate complex rules inconsistently across services.

</details>

---

<a id="ms-sec-014"></a>

<details>
<summary><strong>MS-SEC-014. Why is gateway-only authorization usually insufficient?</strong></summary>

#### Short answer

The gateway lacks full resource context and can be bypassed or misconfigured.

#### Interview answer

Gateway checks are usually coarse: token validity, route access, or broad scope. They cannot reliably know every domain invariant or object-level permission. Internal calls, async messages, admin paths, and misconfigured routing also need protection.

#### Deep dive

Authorization should be enforced where the protected action and data are owned.

#### Production angle

Gateway-only models often lead to IDOR/BOLA vulnerabilities when services trust path IDs without checking ownership.

#### Traps / caveats

- Do not assume internal APIs are unreachable.
- Do not treat possession of a valid token as permission for every resource.

</details>

<a id="ms-sec-017"></a>

<details>
<summary><strong>MS-SEC-017. How do you handle secrets in microservices?</strong></summary>

#### Short answer

Store secrets in a secrets manager, inject them securely at runtime, rotate them, and never commit them to Git or images.

#### Interview answer

Secrets include passwords, API keys, private keys, certificates, and tokens. Services should receive them through platform mechanisms with least privilege. Rotation should be planned so old and new credentials can overlap during rollout.

#### Deep dive

Secrets need ownership, access audit, encryption at rest, and incident response for leakage.

#### Production angle

Rotation without downtime requires clients and providers to accept both old and new credentials temporarily or support reload.

#### Traps / caveats

- Environment variables can still leak through dumps, logs, or process inspection.
- Do not bake secrets into Docker images.

</details>

<a id="ms-sec-019"></a>

<details>
<summary><strong>MS-SEC-019. How do you secure internal APIs?</strong></summary>

#### Short answer

Use authentication, authorization, network controls, input validation, rate limits, audit logs, and secure defaults even for internal endpoints.

#### Interview answer

Internal APIs should not rely only on private networking. They need service identity, least privilege, tenant/resource checks, validation, and observability. Admin and actuator endpoints need stricter exposure and access controls.

#### Deep dive

Internal APIs are often reachable by compromised workloads, misconfigured ingress, or debugging tools.

#### Production angle

Restrict access with mTLS, service tokens, Kubernetes NetworkPolicies, firewall rules, and API-level checks.

#### Traps / caveats

- "Only internal" is not a security policy.
- Do not expose management endpoints broadly.

</details>

<a id="ms-sec-020"></a>

<details>
<summary><strong>MS-SEC-020. How do you protect against IDOR/BOLA across services?</strong></summary>

#### Short answer

Every service that owns a resource must verify the caller is allowed to access that specific object.

#### Interview answer

IDOR/BOLA occurs when a caller changes an ID and accesses another user's or tenant's resource. Services should check ownership, tenant, role, and business policy using trusted identity context, not just route-level scopes.

#### Deep dive

Cross-service calls can propagate user identity, but the resource-owning service must still enforce object-level authorization.

#### Production angle

Audit denied and high-risk access attempts, and test APIs with cross-tenant and cross-user cases.

#### Traps / caveats

- Do not trust frontend-hidden IDs.
- Do not let gateway route authorization replace object authorization.

</details>

<a id="ms-sec-021"></a>

<details>
<summary><strong>MS-SEC-021. How do you avoid leaking PII in logs and traces?</strong></summary>

#### Short answer

Classify sensitive fields, redact before export, restrict attributes, and review logging and tracing policy.

#### Interview answer

Use structured logging with safe fields, mask or omit PII, and avoid raw payload logging. Trace attributes should use stable technical IDs or approved business IDs, not names, emails, tokens, or addresses unless policy allows.

#### Deep dive

PII leakage can happen through error messages, exception objects, metric labels, trace baggage, and debug logs.

#### Production angle

Central log systems need access controls, retention limits, and deletion policies.

#### Traps / caveats

- Hashing PII is not always anonymization.
- Do not put PII in high-cardinality metric labels.

</details>

<a id="ms-sec-023"></a>

<details>
<summary><strong>🧠 MS-SEC-023. How do you handle authorization for asynchronous message consumers?</strong></summary>

#### Short answer

Authorize based on trusted event origin, service permissions, tenant/resource context, and the consumer's own business rules.

#### Interview answer

Async consumers cannot rely on an active HTTP session. Events should carry enough safe context, such as tenant, actor, source service, and business IDs. The consumer must verify the event source and decide whether the action is allowed for its owned resource.

#### Deep dive

Sometimes the authorization decision should be made at command time and stored as part of the workflow, but consumers still need trust and validity checks.

#### Production angle

Audit asynchronous actions because they can mutate data long after the original request.

#### Traps / caveats

- Do not trust arbitrary events from unowned topics.
- Do not include broad user tokens in long-lived messages unless lifecycle and leakage risks are controlled.

</details>

<a id="ms-sec-025"></a>

<details>
<summary><strong>🧠 MS-SEC-025. What is unsafe consumption of downstream or third-party APIs?</strong></summary>

#### Short answer

It is trusting external responses too much or integrating without validation, timeouts, limits, and failure policy.

#### Interview answer

Services should validate downstream data shape, size, status semantics, and trust level. They should use timeouts, retries with limits, circuit breakers, input/output validation, and safe parsing. Third-party responses should not directly drive privileged actions without checks.

#### Deep dive

Downstream APIs can return malformed data, unexpected states, excessive payloads, stale information, or malicious content if compromised.

#### Production angle

Monitor dependency errors, schema drift, latency, rate limiting, and security incidents from providers.

#### Traps / caveats

- Do not deserialize untrusted polymorphic payloads unsafely.
- Do not assume a successful HTTP status means business success.

</details>
