# Event-driven design, Outbox, Inbox and reliability patterns

---

<a id="ms-event-002"></a>

<details>
<summary><strong>MS-EVENT-002. What is the Transactional Outbox pattern?</strong></summary>

#### Short answer

Transactional Outbox stores messages in the same database transaction as the business change, then publishes them asynchronously.

#### Interview answer

Instead of updating the database and publishing to a broker as two separate operations, the service writes an outbox row with the event or command in the same local transaction. A relay later reads the outbox and publishes messages.

#### Deep dive

Outbox gives reliable publication but not exactly-once end-to-end behavior. The relay can publish duplicates, so consumers must be idempotent.

#### Production angle

Monitor outbox backlog, relay errors, publish latency, and stuck records.

#### Traps / caveats

- Outbox does not remove the need for idempotent consumers.
- Outbox records need cleanup or archival.

</details>

---

<a id="ms-event-004"></a>

<details>
<summary><strong>MS-EVENT-004. How does Transactional Outbox solve the dual-write problem?</strong></summary>

#### Short answer

It makes the database update and message intent one atomic local transaction.

#### Interview answer

The dual-write problem happens when a service updates its database and publishes a message separately. If it crashes between those operations, the database and broker disagree. Outbox avoids this by storing the message to publish inside the same transaction as the business update.

#### Deep dive

The relay may still fail after publishing and before marking sent, so duplicate publication is possible and expected.

#### Production angle

Outbox turns a dangerous atomicity problem into an operational retry problem.

#### Traps / caveats

- Publishing directly from inside a transaction is not enough if the broker publish is not part of the database commit.
- Do not treat "sent" flags as reliable without concurrency and retry design.

</details>

<a id="ms-event-007"></a>

<details>
<summary><strong>MS-EVENT-007. How do Outbox and Inbox work together?</strong></summary>

#### Short answer

Outbox reliably publishes messages; Inbox records consumed messages so processing is idempotent.

#### Interview answer

The producer writes an outbox record with its business change. A relay publishes it. The consumer stores the message ID in an inbox or processed-message table in the same transaction as its business update. If the message is redelivered, the consumer can skip or return the existing result.

#### Deep dive

Together they support at-least-once messaging with effectively-once business effects.

#### Production angle

Inbox tables need retention, indexing, and monitoring for duplicates and processing failures.

#### Traps / caveats

- Inbox storage must be transactional with the consumer's side effect.
- Outbox plus Inbox still requires schema compatibility and replay discipline.

</details>

<a id="ms-event-008"></a>

<details>
<summary><strong>MS-EVENT-008. What is an idempotent consumer?</strong></summary>

#### Short answer

An idempotent consumer can process the same message multiple times without changing the final result more than once.

#### Interview answer

Because message delivery is usually at least once, consumers must tolerate duplicates. They can use message IDs, business keys, unique constraints, version checks, and state-machine transitions to avoid duplicate side effects.

#### Deep dive

Idempotency can be natural, such as setting status to `PAID`, or enforced, such as inserting a processed message ID with a unique constraint.

#### Production angle

Idempotent consumers make retries, DLQ reprocessing, failover, and replay safer.

#### Traps / caveats

- A read-before-write duplicate check can race without a unique constraint or transaction.
- External HTTP side effects need their own idempotency strategy.

</details>

<a id="ms-event-009"></a>

<details>
<summary><strong>🧠 MS-EVENT-009. How do you design idempotency keys for consumers?</strong></summary>

#### Short answer

Use a stable identifier that represents the business operation, not an accidental delivery attempt.

#### Interview answer

Good keys are event ID, command ID, order ID plus action, or provider idempotency key depending on the operation. The key must be stable across retries and redeliveries and unique for different business effects.

#### Deep dive

For commands, a business operation key is often better than a random message ID because the same request may be retried through different infrastructure paths.

#### Production angle

Key choice affects duplicate prevention, retention duration, and manual replay behavior.

#### Traps / caveats

- Do not use timestamp or payload hash as the only idempotency key.
- One key per customer can incorrectly suppress distinct operations.

</details>

<a id="ms-event-010"></a>

<details>
<summary><strong>MS-EVENT-010. How do you handle duplicate events?</strong></summary>

#### Short answer

Assume duplicates and make consumers idempotent using keys, constraints, and transactional processing.

#### Interview answer

Duplicates can come from retries, relay crashes, broker redelivery, consumer restarts, or replay. Consumers should record processed IDs or make state transitions naturally idempotent. External side effects should use idempotency keys.

#### Deep dive

Deduplication windows should match broker retention, replay policy, and business risk. Some events can be safely reprocessed indefinitely; others need careful retention.

#### Production angle

Test duplicate handling explicitly by redelivering messages in integration tests.

#### Traps / caveats

- Do not assume broker "exactly once" covers external databases.
- In-memory deduplication is not enough after restart.

</details>

<a id="ms-event-014"></a>

<details>
<summary><strong>MS-EVENT-014. How do you evolve event schemas safely?</strong></summary>

#### Short answer

Make compatible changes, support old and new consumers, and test schema evolution before deployment.

#### Interview answer

Prefer additive optional fields, defaults, tolerant readers, and clear versioning. Avoid renaming or removing fields until consumers have migrated. For Avro or Protobuf, use schema compatibility rules and registry checks where available.

#### Deep dive

Event schemas are long-lived because old events may be replayed after new code is deployed.

#### Production angle

Validate changes with contract tests and replay tests, not only producer unit tests.

#### Traps / caveats

- Changing field meaning can break consumers even if the schema is syntactically compatible.
- Historical events may not contain newly required fields.

</details>

<a id="ms-event-021"></a>

<details>
<summary><strong>MS-EVENT-021. How do you handle out-of-order events?</strong></summary>

#### Short answer

Use per-entity ordering where possible and make consumers robust with versions, sequence numbers, buffering, or monotonic state transitions.

#### Interview answer

For many business flows, ordering is needed only per aggregate, such as per order. Choose partition keys accordingly. Consumers can ignore older versions, store pending events briefly, or design state changes that are safe when events arrive late.

#### Deep dive

Out-of-order handling should be domain-specific. Sometimes the correct answer is to fetch current state from the owner instead of trusting event order.

#### Production angle

Monitor skipped, late, or stale events because they can reveal producer or partitioning issues.

#### Traps / caveats

- Do not rely on wall-clock timestamps for strict ordering.
- Global ordering is expensive and often unnecessary.

</details>

<a id="ms-event-026"></a>

<details>
<summary><strong>MS-EVENT-026. How do you reprocess DLQ messages safely?</strong></summary>

#### Short answer

Fix the root cause, inspect the message, reprocess through idempotent logic, and control rate and side effects.

#### Interview answer

Before replaying, understand whether the failure was poison data, schema mismatch, downstream outage, or code bug. Reprocessing should preserve metadata, use idempotent consumers, avoid duplicate external side effects, and be rate-limited.

#### Deep dive

DLQ messages often need quarantine, manual correction, replay to a staging consumer, or skip with business approval.

#### Production angle

Reprocessing should be an auditable operation with metrics for success, failure, and skipped messages.

#### Traps / caveats

- Do not bulk replay into a still-broken consumer.
- Do not edit messages without preserving original evidence.

</details>

<a id="ms-event-029"></a>

<details>
<summary><strong>🧠 MS-EVENT-029. How do AsyncAPI or schema registries help govern event contracts?</strong></summary>

#### Short answer

They document and validate event contracts so producers and consumers can evolve independently.

#### Interview answer

AsyncAPI describes channels, messages, payloads, and protocols. Schema registries validate compatibility and provide a source of truth for schemas. Both help teams understand ownership, versions, and consumers.

#### Deep dive

Governance should include semantic review, not only syntactic schema checks.

#### Production angle

Contract governance reduces surprise consumer breakage during independent deployments.

#### Traps / caveats

- A schema registry cannot know every business meaning change.
- Documentation must be kept in the delivery workflow or it becomes stale.

</details>

<a id="ms-event-030"></a>

<details>
<summary><strong>🧠 MS-EVENT-030. How do you deprecate or retire event versions safely?</strong></summary>

#### Short answer

Identify consumers, publish a migration path, support parallel versions, monitor usage, and retire only after consumers and replay needs are handled.

#### Interview answer

Events live longer than one deployment because old messages may remain in retention or archives. I would track consumers, announce deprecation, add replacement events, migrate consumers, and verify no active or replay consumer depends on the old version.

#### Deep dive

For historical replay, consumers may need upcasters or compatibility code even after live producers stop sending old versions.

#### Production angle

Unsafe event removal can break background consumers silently before anyone sees user impact.

#### Traps / caveats

- Do not assume "no current traffic" means no replay dependency.
- Do not reuse event names with incompatible meaning.

</details>
