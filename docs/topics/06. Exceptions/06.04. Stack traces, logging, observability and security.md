# 06.04. Stack traces, logging, observability and security

---

<a id="exc-log-001"></a>

<details>
<summary><strong>EXC-LOG-001. How do you read a Java stack trace and identify the real root cause?</strong></summary>

#### Short answer

Start from the exception type and message, inspect the top application frames, then follow `Caused by` chains to the deepest meaningful cause.

#### Interview answer

I read a stack trace in layers. First, identify the top exception and whether it is a wrapper. Then look at the first frames from our code, not only framework frames. Next, follow `Caused by` sections until the original technical or domain failure appears.

For wrapped async or framework failures, the visible exception may be `CompletionException`, `InvocationTargetException` or a Spring wrapper. The useful cause is often inside.

#### Deep dive

The deepest cause is not always the most important one. A socket timeout may be the technical cause, but the higher-level exception may tell you which provider call or order operation failed.

#### Production angle

Good root-cause analysis combines stack trace, request ID, deployment version, input class, dependency health and recent changes.

#### Traps / caveats

- Do not stop at `RuntimeException: failed`.
- Do not ignore application frames in the middle of framework noise.
- Check suppressed exceptions for cleanup failures.

#### Optional Anki

Q: What stack trace sections often reveal wrapping?
A: `Caused by` sections.

</details>

<a id="exc-log-002"></a>

<details>
<summary><strong>EXC-LOG-002. Why should production code usually avoid `printStackTrace()`?</strong></summary>

#### Short answer

`printStackTrace()` writes directly to standard error, bypassing structured logging, log levels, correlation IDs and centralized log policy.

#### Interview answer

Production services need logs with timestamps, levels, service names, request IDs, trace IDs and routing to log aggregation. `printStackTrace()` bypasses that. It also makes tests noisy and gives little control over sampling, formatting or redaction.

Use the project's logger and pass the exception object so the logging framework records the stack trace correctly.

#### Deep dive

In containers, stdout and stderr may be collected, but raw stack traces still lose structured fields and consistent formatting.

#### Production angle

Unstructured stack traces make searching and alerting harder. They can also leak sensitive data if no log filtering policy applies.

#### Traps / caveats

- Do not replace `printStackTrace()` with `log.error(e.getMessage())`.
- Do not log and swallow unless the operation can safely continue.
- Tests may use stack traces for debugging, but application code should use logging.

#### Optional Anki

Q: What should production code use instead of `printStackTrace()`?
A: A structured logger with the exception object passed.

</details>

<a id="exc-log-003"></a>

<details>
<summary><strong>EXC-LOG-003. How should exceptions be logged correctly, including logger argument order?</strong></summary>

#### Short answer

Log a clear message with relevant safe context and pass the exception as the last argument to the logger.

#### Interview answer

With SLF4J-style logging, use:

```java
log.error("Failed to process order {}", orderId, e);
```

The exception must be the last argument so the logging framework treats it as a throwable and prints the stack trace. Include context that helps identify the operation, but do not log secrets or huge payloads.

#### Deep dive

Use log levels deliberately. Expected validation failures are often not `ERROR`; infrastructure failures may be `WARN` or `ERROR` depending on retry and impact.

#### Production angle

Good exception logs allow operators to answer: what operation failed, for which safe identifier, on which version, and what was the root cause?

#### Traps / caveats

- `log.error("failed: {}", e)` may log only `toString()` instead of the stack trace.
- Avoid high-cardinality or sensitive context in metrics labels.
- Do not duplicate logs at every layer.

#### Optional Anki

Q: In SLF4J-style logging, where should the exception object go?
A: As the last logger argument.

</details>

<a id="exc-log-004"></a>

<details>
<summary><strong>EXC-LOG-004. Why is logging the same exception multiple times harmful, and what does "log once, handle once" mean?</strong></summary>

#### Short answer

Duplicate logging creates noise and false incident volume. "Log once, handle once" means one layer should own logging and the boundary should own recovery or mapping.

#### Interview answer

If every layer catches, logs and rethrows, one failure produces many stack traces. That makes alerts noisy and hides the actual rate of failures. It also wastes CPU and storage.

The usual policy is: intermediate layers add context by wrapping when useful; the boundary logs and handles. Boundaries include controllers, message listeners, scheduled jobs and top-level task runners.

#### Deep dive

Sometimes a lower layer logs at debug or attaches context, but production error logging should be centralized enough to avoid duplicates.

#### Production angle

Duplicate logs inflate error dashboards and can trigger paging for one failing request as if many failures occurred.

#### Traps / caveats

- Do not log and rethrow by default.
- Do not swallow just because you logged.
- Make sure the boundary actually logs unexpected failures.

#### Optional Anki

Q: What is the problem with logging and rethrowing at every layer?
A: One failure becomes many noisy log entries.

</details>

<a id="exc-log-005"></a>

<details>
<summary><strong>EXC-LOG-005. What context should be included when logging an exception?</strong></summary>

#### Short answer

Include safe identifiers and operation context: request ID, trace ID, entity ID, dependency name, action, retry attempt and relevant state.

#### Interview answer

A useful exception log says what failed and where to investigate. For example: "failed to reserve inventory", order ID, product ID, dependency name, attempt number and trace ID. Avoid raw payloads, credentials, tokens, personal data and large objects.

Context should be structured when possible so logs can be searched and grouped reliably.

#### Deep dive

Some context belongs in MDC or structured fields rather than repeated in every message. Correlation ID and trace ID should be propagated across service boundaries.

#### Production angle

During incidents, context reduces the need to reproduce. It links logs to traces, metrics, database records and external provider calls.

#### Traps / caveats

- Do not log full request bodies by default.
- Do not log secrets or authorization headers.
- Avoid unbounded strings and high-cardinality metric labels.

#### Optional Anki

Q: What kind of ID is useful in every exception log?
A: A correlation, request or trace ID.

</details>

<a id="exc-log-006"></a>

<details>
<summary><strong>EXC-LOG-006. How do correlation IDs, trace IDs and MDC / thread context help exception debugging?</strong></summary>

#### Short answer

They connect logs from the same request or workflow across classes, threads and services.

#### Interview answer

A correlation ID or trace ID lets you find all log entries related to one request or business operation. MDC stores contextual fields in thread-local logging context so every log line can include them automatically.

In distributed systems, trace context also links logs to spans and dependency calls.

#### Deep dive

MDC is thread-local, so async execution requires explicit propagation or framework support. Without propagation, logs from worker threads may lose request context.

#### Production angle

Good correlation turns "one exception in a service" into a full timeline: inbound request, database query, downstream call, retry and response.

#### Traps / caveats

- Clear MDC after request handling to avoid leaking context between requests.
- Propagate context across executor boundaries deliberately.
- Do not trust client-supplied IDs without validation policy.

#### Optional Anki

Q: Why can MDC fail in async code?
A: It is usually thread-local and may not propagate to worker threads automatically.

</details>

<a id="exc-log-007"></a>

<details>
<summary><strong>EXC-LOG-007. How should stack traces be handled in user-facing API responses?</strong></summary>

#### Short answer

Do not return stack traces to external clients. Return a safe, stable error format and keep stack traces in internal logs.

#### Interview answer

External error responses should include a status, stable application error code, safe message, request ID or trace ID, and field errors when relevant. Stack traces reveal implementation details and confuse clients.

Internal logs should contain the stack trace and enough context for debugging. The response and log can be linked by request ID.

#### Deep dive

For Spring, a global exception handler can map exceptions to `ProblemDetail` or another standard response shape. Internal exception details should be hidden behind safe user-facing messages.

#### Production angle

Leaking stack traces can expose package names, library versions, SQL, file paths, hostnames or business internals.

#### Traps / caveats

- Do not return `exception.getMessage()` blindly.
- Validation errors can expose field-level details, but they still need safe messages.
- Include a support/debug ID so operators can find the internal log.

#### Optional Anki

Q: Where should stack traces go?
A: Internal logs, not external API responses.

</details>

<a id="exc-log-008"></a>

<details>
<summary><strong>EXC-LOG-008. Which exception metrics are useful in production, and why can high-cardinality labels hurt metrics systems?</strong></summary>

#### Short answer

Useful metrics include error rate by stable type/category, endpoint, dependency and retry outcome. High-cardinality labels like user ID or full message can overload metrics storage.

#### Interview answer

Metrics should answer operational questions: Are errors increasing? Which endpoint or dependency is affected? Are retries succeeding? Are failures client-side, server-side or upstream?

Labels must be bounded and stable. Exception class, status family, endpoint template and dependency name are useful. Raw messages, IDs, emails and payload fragments create too many time series.

#### Deep dive

Logs are for high-cardinality detail. Metrics are for aggregation. Traces connect one request path.

#### Production angle

High-cardinality metrics can increase cost, slow dashboards and even drop data when limits are exceeded.

#### Traps / caveats

- Do not label metrics with `exception.getMessage()`.
- Use route templates, not raw URLs with IDs.
- Separate expected validation failures from server defects.

#### Optional Anki

Q: Why should exception messages not be metric labels?
A: They create high cardinality and unstable time series.

</details>

<a id="exc-log-009"></a>

<details>
<summary><strong>EXC-LOG-009. When would you sample exception logs?</strong></summary>

#### Short answer

Sample logs when failures are high-volume, expected or repetitive enough to overwhelm storage, while keeping metrics and representative examples.

#### Interview answer

Sampling is useful for exception storms, invalid user input floods, noisy downstream failures or known retryable errors. You still need counters and alerts so sampling does not hide the rate. For rare or severe failures, log every event.

Sampling should be deliberate and ideally category-based, not random suppression of all errors.

#### Deep dive

An effective policy might log the first occurrence, then sample repeated identical errors per time window while counting all occurrences in metrics.

#### Production angle

Sampling protects log systems and on-call engineers during bursts. It should not hide security events, data loss or unknown server errors.

#### Traps / caveats

- Do not sample without metrics.
- Do not sample away the first example of a new failure.
- Keep request IDs for sampled examples.

#### Optional Anki

Q: What must accompany sampled exception logs?
A: Metrics that count the full failure rate.

</details>

<a id="exc-sec-001"></a>

<details>
<summary><strong>EXC-SEC-001. What internal data can exception messages or logs accidentally leak?</strong></summary>

#### Short answer

They can leak credentials, tokens, personal data, SQL, file paths, hostnames, internal IDs, payloads and implementation details.

#### Interview answer

Exception messages often include values that were being processed. In backend systems, that might be authorization headers, passwords, payment data, personal identifiers, SQL text, table names, internal service URLs or filesystem paths.

Logs are internal, but they are still widely accessible in many organizations and may be retained for a long time. External API responses need even stricter filtering.

#### Deep dive

Some libraries include request URLs, headers or SQL fragments in exceptions. Review defaults for HTTP clients, ORM, validation and serialization libraries.

#### Production angle

Leaked secrets in logs can require credential rotation and incident response. Leaked personal data can create compliance issues.

#### Traps / caveats

- Do not log full request bodies by default.
- Redact tokens and secrets before logging.
- Do not assume logs are visible only to developers.

#### Optional Anki

Q: Name one thing exception logs should never include.
A: Secrets such as tokens, passwords or API keys.

</details>

<a id="exc-sec-002"></a>

<details>
<summary><strong>EXC-SEC-002. How do you convert internal exceptions into safe external errors?</strong></summary>

#### Short answer

Map internal exceptions to stable external error codes, HTTP statuses and safe messages, while logging the internal details with a correlation ID.

#### Interview answer

At the API boundary, use a global error handler. It should classify exceptions, choose the correct status code, return a stable application error code, include safe details such as field errors, and attach a request ID. The stack trace and root cause stay in logs.

This separates client contract from internal implementation.

#### Deep dive

For example, a database unique constraint may become `409 Conflict` with `USER_EMAIL_ALREADY_EXISTS`. A database outage may become `503 Service Unavailable` without table names or SQL.

#### Production angle

Safe external errors improve client behavior and reduce data leakage. Internal logs still support incident debugging.

#### Traps / caveats

- Do not return raw exception messages.
- Do not turn all errors into 500.
- Keep error codes backward-compatible.

#### Optional Anki

Q: What should link a safe client error to internal logs?
A: A request ID, trace ID or support ID.

</details>

<a id="exc-sec-003"></a>

<details>
<summary><strong>EXC-SEC-003. How can swallowed exceptions create security or correctness bugs?</strong></summary>

#### Short answer

Swallowed exceptions can make code continue after a failed validation, authorization, audit, write or cleanup step.

#### Interview answer

An empty catch block says "failure does not matter", often accidentally. If authorization lookup fails and code defaults to allow, that is a security bug. If audit logging fails and the system silently proceeds despite a strict audit requirement, that may violate compliance. If persistence fails and code returns success, data becomes inconsistent.

Failures must be classified: fail closed, fail open only when explicitly safe, retry, degrade or abort.

#### Deep dive

Swallowing `InterruptedException` is especially dangerous because it can prevent shutdown and cancellation.

#### Production angle

Swallowed exceptions create incidents with missing evidence. The first visible symptom may be inconsistent data or a stuck service rather than an obvious error.

#### Traps / caveats

- Do not catch and ignore broadly.
- Logging alone is not handling.
- Define fail-open vs fail-closed behavior for security-sensitive paths.

#### Optional Anki

Q: What is a fail-closed behavior?
A: Denying or aborting when the system cannot verify safety.

</details>

<a id="exc-log-010"></a>

<details>
<summary><strong>🧠 EXC-LOG-010. How do you read `... N more` in Java stack traces?</strong></summary>

#### Short answer

`... N more` means the current stack trace shares the last N frames with the enclosing stack trace, so Java omits repeated frames.

#### Interview answer

When exceptions are chained, many frames are identical between the wrapper and cause. Java compresses the repeated tail as `... N more`. It is not missing data; it points to frames already shown above.

To read it, follow each `Caused by` block and mentally expand the omitted frames from the previous trace if needed.

#### Deep dive

This compression keeps chained stack traces shorter. It commonly appears in framework and async wrappers.

#### Production angle

Understanding `... N more` prevents misreading a stack trace as truncated. Real truncation is usually caused by log limits, not this notation.

#### Traps / caveats

- Do not assume `... N more` hides the root cause.
- Check log aggregation limits if the stack trace ends abruptly.
- The important frame may be above the compressed tail.

#### Optional Anki

Q: What does `... 20 more` mean?
A: Twenty stack frames are shared with the enclosing trace and omitted.

</details>

<a id="exc-log-011"></a>

<details>
<summary><strong>🧠 EXC-LOG-011. Why can asynchronous code make stack traces and logging context harder to read?</strong></summary>

#### Short answer

Async execution separates the caller stack from the worker stack, and thread-local logging context may not propagate automatically.

#### Interview answer

In synchronous code, the stack usually shows the full call path. In async code, work runs later on another thread. The stack trace may show only executor, `CompletableFuture` or framework frames plus the failing lambda. The original caller may not be on the stack anymore.

MDC and other thread-local context can also be lost when work moves to another thread unless the framework propagates it.

#### Deep dive

Async frameworks often wrap failures in `CompletionException`, `ExecutionException` or framework-specific task exceptions. You need to unwrap and preserve context explicitly.

#### Production angle

Use trace propagation, named tasks, structured logs and clear wrapping around async boundaries. Otherwise failures become hard to connect to the request or message that started them.

#### Traps / caveats

- Do not assume MDC automatically follows executor tasks.
- Do not log only `CompletionException`; inspect the cause.
- Name threads and executors meaningfully.

#### Optional Anki

Q: Why is async stack trace context often incomplete?
A: The failing work runs later on a different thread from the original caller.

</details>
