# 06.02. try, catch, finally and resource cleanup

---

<a id="exc-flow-001"></a>

<details>
<summary><strong>EXC-FLOW-001. How should `catch` blocks be ordered, and what does multi-catch change?</strong></summary>

#### Short answer

Catch more specific exception types before broader ones. Multi-catch lets one handler handle several unrelated exception types with the same logic.

#### Interview answer

Java checks catch blocks top to bottom. If a broad type like `Exception` appears before `IOException`, the narrower block is unreachable and the code will not compile. The usual order is from most specific to most general.

Multi-catch, such as `catch (IOException | TimeoutException e)`, is useful when different exception types should be handled identically. The caught variable is effectively final because assigning a new value would make type analysis ambiguous.

#### Deep dive

Use multi-catch when the recovery action is truly the same: add context, return a specific response, or trigger a retry. If the behavior differs, separate catch blocks are clearer.

#### Production angle

Good catch ordering prevents broad handlers from swallowing important distinctions such as validation errors, conflicts, timeouts and unexpected bugs.

#### Traps / caveats

- Do not put `catch (Exception e)` before specific handlers.
- Do not use multi-catch just to compress code if the cases deserve different metrics or responses.
- Avoid catching exceptions only to log and rethrow at every layer.

#### Optional Anki

Q: Why must narrower catch blocks come before broader ones?
A: Otherwise the narrower handlers are unreachable.

</details>

<a id="exc-flow-002"></a>

<details>
<summary><strong>EXC-FLOW-002. What does `finally` guarantee, and when can it fail to run?</strong></summary>

#### Short answer

`finally` normally runs when control leaves a `try` block, whether by success, return or exception. It may not run if the JVM process terminates or the thread is forcibly stopped.

#### Interview answer

`finally` is for cleanup that should happen on both normal and exceptional paths. If the `try` block returns, throws, or completes normally, Java runs the `finally` block before leaving the method or continuing.

It is not an absolute guarantee against process death. `System.exit`, JVM crash, machine failure, kill signals, severe native failures or deprecated unsafe thread-stopping behavior can prevent it.

#### Deep dive

`finally` is often replaced by try-with-resources for closeable resources because try-with-resources handles ordering and suppressed exceptions more safely.

#### Production angle

Use `finally` for releasing locks, restoring thread-local state and cleaning up non-`AutoCloseable` resources. For files, sockets and database resources, prefer try-with-resources or framework lifecycle management.

#### Traps / caveats

- `finally` does not protect against process termination.
- Code inside `finally` can itself fail.
- Long or blocking cleanup inside `finally` can cause latency or shutdown issues.

#### Optional Anki

Q: Does `finally` run before a method returns?
A: Yes, under normal JVM execution.

</details>

<a id="exc-flow-003"></a>

<details>
<summary><strong>EXC-FLOW-003. How do `return`, `throw` and `finally` interact?</strong></summary>

#### Short answer

`finally` runs after a `return` or `throw` is chosen but before control actually leaves. A `return` or exception from `finally` can override the original outcome.

#### Interview answer

If a `try` block returns a value, Java computes that return path, then executes `finally`, then returns. If the `try` block throws, Java starts unwinding, executes `finally`, then continues throwing unless `finally` changes the outcome.

The dangerous part is that `finally` can replace the original result. A `return` in `finally` can swallow an exception. A new exception thrown from `finally` can mask the original exception.

#### Deep dive

For object references, the return value reference is selected before `finally`, but the object itself can still be mutated by `finally`. That kind of code is hard to reason about and should be avoided.

#### Production angle

Masking the original exception makes incidents harder to diagnose. A service may log only the cleanup failure while hiding the database or business failure that caused the path.

#### Traps / caveats

- Avoid `return` from `finally`.
- Avoid throwing from `finally` unless you deliberately preserve the original failure.
- Keep cleanup small and defensive.

#### Optional Anki

Q: What can a `return` in `finally` do to an exception from `try`?
A: It can swallow and replace it.

</details>

<a id="exc-flow-004"></a>

<details>
<summary><strong>EXC-FLOW-004. Why should `finally` not return or throw without a deliberate reason?</strong></summary>

#### Short answer

Because it can hide the original return value or exception, making behavior surprising and diagnostics misleading.

#### Interview answer

`finally` should usually clean up and then let the original control flow continue. If it returns, it overrides any previous return or exception. If it throws, it can mask the original exception. That is almost always a bug because the first failure is usually the one you need to investigate.

Try-with-resources handles close failures better by preserving the primary exception and attaching close failures as suppressed exceptions.

#### Deep dive

If cleanup can fail, handle that failure explicitly: log it with context, attach it as suppressed where appropriate, or let try-with-resources do the work.

#### Production angle

Masking exceptions causes false alerts and slower incident response. For example, a cleanup exception may hide a payment or database failure.

#### Traps / caveats

- Static analysis tools often flag `return` in `finally`.
- Do not put business decisions inside cleanup blocks.
- If cleanup failure matters, design a clear reporting strategy.

#### Optional Anki

Q: Why is throwing from `finally` risky?
A: It can mask the original exception.

</details>

<a id="exc-flow-005"></a>

<details>
<summary><strong>EXC-FLOW-005. Why should exceptions not be used for normal control flow?</strong></summary>

#### Short answer

Exceptions are for exceptional or failure paths. Using them for expected branches makes code slower, noisier and harder to understand.

#### Interview answer

Normal control flow should be expressed with conditions, return values, polymorphism, `Optional`, validation results or domain result types. Exceptions carry stack traces and signal failure. If code throws thousands of exceptions per second for ordinary checks, it wastes CPU, creates GC pressure and pollutes logs or metrics.

An exception can still represent an expected business failure at a boundary, such as "duplicate email", but it should not replace simple branching in a hot loop.

#### Deep dive

Examples of bad control flow include parsing repeatedly by catching `NumberFormatException` when pre-validation is cheap, or using `NoSuchElementException` from `Optional.get()` as a normal absence path.

#### Production angle

Exception-driven hot paths can create latency spikes and obscure real incidents with expected noise.

#### Traps / caveats

- Do not optimize prematurely; occasional exceptions are fine.
- Boundary validation failures can be modeled as exceptions if the framework handles them cleanly.
- Bulk validation usually needs error lists, not one exception per invalid field.

#### Optional Anki

Q: What is the main performance cost of frequent exceptions?
A: Allocation and stack trace creation, plus logging and GC pressure.

</details>

<a id="exc-twr-001"></a>

<details>
<summary><strong>EXC-TWR-001. How does try-with-resources work?</strong></summary>

#### Short answer

Try-with-resources automatically closes declared `AutoCloseable` resources when the block exits, in reverse declaration order.

#### Interview answer

Try-with-resources is Java's structured resource cleanup syntax. Resources are declared in the `try (...)` header. When the block exits normally or exceptionally, Java calls `close()` on each resource.

If both the body and a `close()` call throw, the body exception remains primary and the close exception is attached as a suppressed exception. This is safer than manual `finally`, where cleanup can easily mask the original failure.

#### Deep dive

Example:

```java
try (InputStream in = Files.newInputStream(path)) {
    return in.readAllBytes();
}
```

The stream is closed even if `readAllBytes()` fails.

#### Production angle

Backend code uses scarce external resources: database connections, statements, result sets, HTTP responses, files and sockets. Deterministic close prevents file descriptor leaks and connection pool exhaustion.

#### Traps / caveats

- Do not return a resource that will be closed by the block.
- Know whether closing a wrapper closes the underlying resource.
- Inspect suppressed exceptions when cleanup also failed.

#### Optional Anki

Q: In what order does try-with-resources close resources?
A: Reverse declaration order.

</details>

<a id="exc-twr-002"></a>

<details>
<summary><strong>EXC-TWR-002. What requirements must a resource satisfy to be used in try-with-resources?</strong></summary>

#### Short answer

The resource must implement `AutoCloseable` or a subtype such as `Closeable`.

#### Interview answer

Any object used in a try-with-resources header must be assignable to `AutoCloseable`. Java will call its `close()` method when leaving the block. Many standard resource types implement it, including streams, readers, writers, JDBC `Connection`, `Statement`, `ResultSet` and many HTTP client response objects.

Since Java 9, an effectively final variable can also be used in the resource header.

#### Deep dive

`Closeable` extends `AutoCloseable` and narrows `close()` to throw `IOException`. `AutoCloseable.close()` can throw `Exception`, which is broader and can be inconvenient for custom APIs.

#### Production angle

If your type owns an external resource, implementing `AutoCloseable` makes ownership visible and lets callers use safe cleanup syntax.

#### Traps / caveats

- `AutoCloseable` does not require `close()` to be idempotent.
- Do not implement `AutoCloseable` for ordinary objects that do not need explicit lifecycle.
- Document whether closing also closes nested or delegated resources.

#### Optional Anki

Q: What interface enables try-with-resources?
A: `AutoCloseable`.

</details>

<a id="exc-twr-003"></a>

<details>
<summary><strong>EXC-TWR-003. In what order are resources closed in try-with-resources?</strong></summary>

#### Short answer

Resources are closed in reverse order of declaration.

#### Interview answer

If a try-with-resources statement declares `A`, then `B`, then `C`, Java closes `C` first, then `B`, then `A`. This matches typical wrapper ownership: the outermost wrapper is closed before the underlying resource.

For example, if a `BufferedReader` wraps an `InputStreamReader` that wraps an `InputStream`, the reader should close before the underlying stream.

#### Deep dive

Reverse close order also applies when the body throws. If multiple `close()` calls throw, the first failure in the primary path remains primary and later close failures are attached as suppressed exceptions.

#### Production angle

Correct close order matters for flushing buffers, returning connections to pools and releasing layered resources without leaks.

#### Traps / caveats

- Do not manually close resources inside the block unless there is a clear reason.
- Be careful when one resource depends on another declared later.
- Suppressed exceptions may contain useful cleanup failure details.

#### Optional Anki

Q: If resources are declared `r1; r2`, which closes first?
A: `r2`.

</details>

<details>
<summary><strong>EXC-TWR-004. What are suppressed exceptions, how do they differ from the cause, and what happens if both the body and `close()` throw?</strong></summary>

#### Short answer

Suppressed exceptions are secondary failures attached to a primary exception. The cause explains why an exception was created; suppressed exceptions record additional failures, often from cleanup.

#### Interview answer

In try-with-resources, if the try body throws and then `close()` also throws, Java keeps the body exception as the primary exception. The close exception is stored in `primary.getSuppressed()`.

The cause is different. A cause is usually the lower-level exception that was wrapped to create a higher-level exception. Suppressed exceptions are peer failures that happened while handling the same operation.

#### Deep dive

One exception can have one cause but multiple suppressed exceptions. This is useful when several resources fail during cleanup or when structured/concurrent operations need to report multiple related failures.

#### Production angle

When logs show a failure but cleanup also failed, suppressed exceptions can explain leaked connections, failed flushes or incomplete file writes.

#### Traps / caveats

- Do not ignore suppressed exceptions during diagnostics.
- Do not confuse `getCause()` with `getSuppressed()`.
- Suppression can be disabled for some `Throwable` instances, but that is uncommon.

#### Optional Anki

Q: Where does try-with-resources store close failures when the body already failed?
A: In `Throwable.getSuppressed()`.

</details>

<a id="exc-twr-005"></a>

<details>
<summary><strong>EXC-TWR-005. How should JDBC resources, HTTP responses and file streams be closed?</strong></summary>

#### Short answer

Close resources deterministically with try-with-resources or framework-managed lifecycle, and make ownership clear.

#### Interview answer

For direct JDBC code, use try-with-resources for `Connection`, `PreparedStatement` and `ResultSet` unless a framework manages them. For HTTP clients, close response bodies when the API requires it. For file streams, readers and writers, close them with try-with-resources so file descriptors are released.

The key design point is ownership. The code that opens or receives ownership of a resource must close it. If ownership is transferred, document it clearly.

#### Deep dive

Frameworks such as Spring may bind JDBC connections to transactions and close or release them through transaction synchronization. In that case, manually closing a framework-managed resource can be wrong.

#### Production angle

Failure to close resources causes connection pool exhaustion, "too many open files", blocked deployments and slow degradation under load.

#### Traps / caveats

- Do not close a resource you do not own.
- Do not return a stream from inside a try-with-resources block that closes it.
- Closing a wrapper may close the underlying resource.

#### Optional Anki

Q: What is the main rule for resource cleanup?
A: The owner of the resource is responsible for closing it.

</details>

<a id="exc-twr-006"></a>

<details>
<summary><strong>EXC-TWR-006. Why is relying on GC, finalizers or `Cleaner` unsafe for external resource cleanup?</strong></summary>

#### Short answer

Garbage collection is not deterministic. External resources must be released promptly, not whenever the GC happens to collect an object.

#### Interview answer

GC manages Java heap memory. It does not guarantee timely release of file descriptors, sockets, database connections or native handles. Finalizers are unreliable and have serious performance and security issues. `Cleaner` is safer than finalization for last-resort cleanup, but it is still not deterministic.

The normal solution is explicit ownership with try-with-resources, lifecycle callbacks or framework-managed resource scopes.

#### Deep dive

A Java object can become unreachable long after the external resource should have been returned. Under low allocation pressure, GC may not run soon enough to avoid exhausting a small pool of external resources.

#### Production angle

This shows up as open file leaks, exhausted HTTP pools or database pools while heap memory looks healthy.

#### Traps / caveats

- `Cleaner` can be a safety net, not the primary lifecycle mechanism.
- Finalization is not a destructor model.
- Heap metrics alone do not reveal external resource leaks.

#### Optional Anki

Q: Why is GC not enough for sockets or database connections?
A: It does not release external resources deterministically.

</details>

<details>
<summary><strong>🧠 EXC-TWR-007. Should `AutoCloseable.close()` be idempotent or throw `InterruptedException`?</strong></summary>

#### Short answer

`AutoCloseable` does not require idempotent `close()`, but idempotence is usually friendlier. `close()` should usually not throw `InterruptedException`; if interruption happens, restore the interrupt flag and expose an appropriate exception.

#### Interview answer

The interface contract allows `close()` to throw `Exception` and does not require repeated calls to be safe. In practical backend APIs, idempotent close often reduces double-close bugs and makes cleanup paths easier.

Throwing `InterruptedException` from `close()` is awkward because try-with-resources cleanup can happen while another exception is already propagating. Many APIs avoid it. If cleanup detects interruption, it should usually restore the interrupt flag with `Thread.currentThread().interrupt()` and throw or record a domain-appropriate failure.

#### Deep dive

`Closeable` has a stronger tradition of idempotence than `AutoCloseable`. For custom resources, document the behavior explicitly.

#### Production angle

Predictable close behavior is important in pools, clients and framework integrations. Surprise interruption handling in cleanup can mask primary failures or break shutdown.

#### Traps / caveats

- Do not swallow interruption silently.
- Do not make `close()` perform expensive business work.
- Avoid broad `throws Exception` in custom close methods when a narrower type is possible.

#### Optional Anki

Q: Is `AutoCloseable.close()` required to be idempotent?
A: No, but idempotence is usually a good practical design.

</details>
