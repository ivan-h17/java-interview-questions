# 06.03. Custom exception design, propagation and chaining

---

<a id="exc-custom-001"></a>

<details>
<summary><strong>EXC-CUSTOM-001. When should you create a custom exception, and when should you avoid creating one?</strong></summary>

#### Short answer

Create a custom exception when it adds stable meaning that callers, handlers or operators can use. Avoid it when a standard exception already communicates the failure clearly.

#### Interview answer

A custom exception is useful when the failure is part of your domain or application contract: duplicate registration, insufficient balance, unsupported state transition, external provider unavailable. It gives global handlers, retry logic and metrics a stable category.

Avoid creating a new class for every tiny variation. If no code will handle it differently and the message is enough, a standard exception may be clearer.

#### Deep dive

Useful custom exceptions usually preserve the cause, have a meaningful name, and optionally include structured fields such as an application error code or entity ID. They should not become mutable DTOs.

#### Production angle

Good custom exceptions make HTTP mapping, alert routing and dashboards cleaner. Exception explosion makes code harder to search and maintain.

#### Traps / caveats

- Do not create custom exceptions just to rename `IllegalArgumentException`.
- Do not lose the original cause.
- Do not put sensitive data into fields or messages.

#### Optional Anki

Q: When is a custom exception justified?
A: When it adds stable meaning used by callers, handlers or operators.

</details>

<a id="exc-custom-002"></a>

<details>
<summary><strong>EXC-CUSTOM-002. Should a custom exception extend `Exception` or `RuntimeException`?</strong></summary>

#### Short answer

Extend `Exception` only when callers are expected to handle the failure explicitly. Extend `RuntimeException` when handling is centralized or the failure is a programming/domain contract violation.

#### Interview answer

For most Spring backend services, custom application exceptions often extend `RuntimeException`. They are handled by global exception handlers, transaction rules, retry policies or message listener infrastructure.

Checked custom exceptions can be useful in library APIs where the caller truly has a local recovery choice. If every caller will only wrap or rethrow, checked exceptions create noise.

#### Deep dive

The choice affects Spring transaction rollback defaults. Runtime exceptions trigger rollback by default; checked exceptions do not unless configured with `rollbackFor` or equivalent.

#### Production angle

Be consistent across the codebase. Mixed exception policies cause unexpected commits, broad catch blocks and confusing handler logic.

#### Traps / caveats

- Do not make an exception checked just because it is "important".
- Do not make everything unchecked without documenting boundary behavior.
- Remember transaction rollback rules.

#### Optional Anki

Q: What custom exception base type is common in Spring service code?
A: `RuntimeException`, with centralized handling and rollback policy.

</details>

<a id="exc-custom-003"></a>

<details>
<summary><strong>EXC-CUSTOM-003. How should custom exceptions preserve the cause and expose useful structured details?</strong></summary>

#### Short answer

Provide constructors that accept a message and cause, and include stable structured details only when handlers need them.

#### Interview answer

A good custom exception should not destroy diagnostic information. If it wraps a lower-level failure, pass the original exception as the cause. That keeps the full stack trace chain available.

Structured fields can be useful for application error code, entity ID, provider name or retry category. Keep them stable and non-sensitive. Do not rely on parsing the message.

#### Deep dive

Common constructors are:

```java
MyException(String message)
MyException(String message, Throwable cause)
```

For domain failures, you might also add `errorCode()` or `resourceId()`.

#### Production angle

Structured details improve global error responses, logs and metrics. Preserved causes reduce time to root cause during incidents.

#### Traps / caveats

- Do not include passwords, tokens or full request bodies.
- Do not expose internal IDs to external clients without policy.
- Keep exception objects immutable after construction.

#### Optional Anki

Q: Why should wrapping exceptions preserve the cause?
A: To keep the original failure and stack trace available.

</details>

<a id="exc-custom-004"></a>

<details>
<summary><strong>EXC-CUSTOM-004. What is the difference between domain exceptions and technical exceptions?</strong></summary>

#### Short answer

Domain exceptions represent business rule failures. Technical exceptions represent infrastructure, integration or system failures.

#### Interview answer

A domain exception says the business operation cannot proceed according to business rules: insufficient funds, duplicate username, invalid state transition. A technical exception says something outside the domain rule failed: database timeout, broken HTTP call, serialization failure, disk error.

The distinction matters because clients and retry logic treat them differently. A domain conflict usually should not be retried blindly. A transient technical failure might be retryable.

#### Deep dive

Domain exceptions often map to 400, 404, 409 or 422. Technical exceptions often map to 500, 502, 503 or 504 depending on where the failure occurred.

#### Production angle

Clear separation helps alerting. Domain validation failures may be normal traffic; technical failures may page the team.

#### Traps / caveats

- Not every business failure needs an exception; validation may need an error list.
- Do not expose technical exception details to clients.
- Some failures cross categories, such as optimistic locking conflict.

#### Optional Anki

Q: Is a database timeout a domain or technical exception?
A: Technical.

</details>

<a id="exc-custom-005"></a>

<details>
<summary><strong>EXC-CUSTOM-005. How would you design an exception hierarchy for business rules or a Java SDK?</strong></summary>

#### Short answer

Define a small, meaningful hierarchy around caller actions: validation, conflict, not found, authorization, transient infrastructure and permanent provider failure. Use error codes for finer subcategories when subclasses would not change handling.

#### Interview answer

I would start from use cases, not class names. For a business module, define a base application exception and a few categories that handlers need to distinguish. For an SDK, expose exceptions that client code can handle reliably, such as authentication failure, rate limit, timeout, conflict and invalid request.

For example, a registration module might use `RegistrationException` as a base, with `DuplicateEmailException`, `WeakPasswordException` and `RegistrationProviderUnavailableException`. If the only difference is a display message or field name, a stable error code on one validation exception may be better than a new class.

The hierarchy should be stable, documented and not tied to internal implementation details.

#### Deep dive

Avoid both extremes: one generic `BusinessException` with message parsing, and dozens of unique classes that no caller handles differently. A useful rule is: create a subclass when code needs different catch/mapping/retry behavior; use structured error codes when the category is the same but the client needs a precise reason.

#### Production angle

Good hierarchy supports HTTP mapping, retry decisions, client SDK docs and metrics. It also makes migrations safer because clients depend on stable categories.

#### Traps / caveats

- Do not leak vendor exceptions directly from a public SDK.
- Do not model every database constraint as a separate exception class.
- Keep backward compatibility when changing public exception types.
- Do not create subclasses only to vary the English message.

#### Optional Anki

Q: What should drive an exception hierarchy?
A: The distinctions callers and handlers actually need.

</details>

<a id="exc-custom-006"></a>

<details>
<summary><strong>EXC-CUSTOM-006. How should validation failures be represented: exceptions, result objects or error lists?</strong></summary>

#### Short answer

Use exceptions for single operation-level failures, and result objects or error lists when callers need all validation errors at once.

#### Interview answer

For request validation in a web API, framework validation often collects field errors and maps them to a 400 or 422 response. Throwing one exception per field is not useful. For domain operations, a single rule failure may be a domain exception if it aborts the command.

The model depends on workflow. Interactive forms and batch imports usually need error lists. Command methods often fail fast with a clear exception.

#### Deep dive

Validation errors should have stable field names, error codes and safe user-facing messages. Technical details belong in logs, not the external response.

#### Production angle

Bulk validation with exceptions per row can create exception storms. Prefer accumulated error reports for imports and batch jobs.

#### Traps / caveats

- Do not use exceptions to carry huge lists of unstructured text.
- Do not expose raw regex, SQL or parser details as user messages.
- Keep validation policy consistent across API and async consumers.

#### Optional Anki

Q: What is better for batch validation: many thrown exceptions or an error list?
A: Usually an error list.

</details>

<a id="exc-custom-007"></a>

<details>
<summary><strong>EXC-CUSTOM-007. At which boundaries should technical exceptions be translated into application or domain exceptions?</strong></summary>

#### Short answer

Translate at architectural boundaries where low-level details cross into higher-level code: repository, gateway/client, message adapter and controller boundaries.

#### Interview answer

Lower layers know technical details; higher layers need business meaning. A repository can translate `SQLException` or vendor constraint errors into persistence/application exceptions. An HTTP client gateway can translate client library exceptions into provider unavailable, timeout or bad upstream response.

Do not translate at every method. Translate where it improves abstraction and handling.

#### Deep dive

Good translation preserves the cause and adds context. Bad translation wraps repeatedly and hides the root cause.

#### Production angle

Boundary translation gives global handlers stable categories for rollback, retry, HTTP mapping and alerting while preserving technical details in logs.

#### Traps / caveats

- Do not drop the cause.
- Do not translate so early that useful technical classification is lost.
- Do not expose raw database or provider exceptions from domain services.

#### Optional Anki

Q: Where should `SQLException` usually be translated?
A: At the repository or persistence boundary.

</details>

<a id="exc-prop-001"></a>

<details>
<summary><strong>EXC-PROP-001. What is exception chaining, and how is it different from exception wrapping?</strong></summary>

#### Short answer

Exception chaining links an exception to its cause. Wrapping creates a new higher-level exception and sets the lower-level exception as its cause.

#### Interview answer

Chaining is the general mechanism: an exception can have a cause accessible with `getCause()`. Wrapping is a common use of chaining where code catches a low-level exception and throws a new exception with more appropriate abstraction or context.

For example, an HTTP client exception can be wrapped in `PaymentProviderUnavailableException`, preserving the original as the cause.

#### Deep dive

Wrapping should add value: a better type, better context or a boundary translation. If it adds nothing, rethrowing the same exception is clearer.

#### Production angle

Good chaining lets logs show both the domain operation that failed and the technical root cause.

#### Traps / caveats

- Do not wrap and forget the cause.
- Do not over-wrap at every layer.
- Do not use message parsing instead of cause traversal.

#### Optional Anki

Q: What method returns an exception's cause?
A: `getCause()`.

</details>

<a id="exc-prop-002"></a>

<details>
<summary><strong>EXC-PROP-002. When should you rethrow the same exception instead of throwing a new one?</strong></summary>

#### Short answer

Rethrow the same exception when you cannot add useful type, context or recovery meaning.

#### Interview answer

If a catch block only logs or converts `e` into `new Exception(e)` without adding meaning, it is usually worse than letting the original exception propagate. The original stack trace and type are clearer.

Throw a new exception only when crossing an abstraction boundary, adding operation context, or converting to a stable application contract.

#### Deep dive

`throw e` preserves the original exception object. In modern Java, precise rethrow can also preserve narrower checked exception types in some catch-and-rethrow cases.

#### Production angle

Unnecessary wrapping creates noisy stack traces and makes root-cause search slower.

#### Traps / caveats

- Do not catch just to log and rethrow unless that layer owns logging.
- Do not use `new Exception(e)` as a generic wrapper.
- If you wrap, use a meaningful message and cause.

#### Optional Anki

Q: What is the rule for wrapping?
A: Wrap only when it adds useful abstraction or context.

</details>

<a id="exc-prop-003"></a>

<details>
<summary><strong>EXC-PROP-003. How can wrapping add useful context without hiding the root cause?</strong></summary>

#### Short answer

Use a meaningful higher-level exception type and message, and pass the original exception as the cause.

#### Interview answer

Good wrapping says what operation failed at the current layer while preserving why it failed underneath. For example:

```java
throw new InvoiceExportException("Failed to export invoice " + invoiceId, e);
```

The new type is useful to handlers, the message adds business context, and the cause keeps the original stack trace.

#### Deep dive

Context should be safe and relevant: IDs, operation names, provider names and retry category. Avoid secrets and huge payloads.

#### Production angle

Good context shortens incident debugging. Logs can show "failed to call payment provider for order 123" and still include the socket timeout cause.

#### Traps / caveats

- Do not hide root cause behind a generic message.
- Do not add sensitive context.
- Do not wrap repeatedly with nearly identical messages.

#### Optional Anki

Q: What constructor argument preserves the root cause during wrapping?
A: The `Throwable cause`.

</details>

<a id="exc-prop-004"></a>

<details>
<summary><strong>EXC-PROP-004. How can stack trace information or the original cause be lost?</strong></summary>

#### Short answer

By throwing a new exception without the cause, overwriting stack traces, throwing from `finally`, or logging only the message.

#### Interview answer

The common bug is:

```java
catch (IOException e) {
    throw new RuntimeException("Failed");
}
```

The original `IOException` is gone. You also lose useful diagnostics if `finally` throws over the original exception, if code catches and returns `null`, or if logs use `e.getMessage()` instead of passing the exception object.

#### Deep dive

Some frameworks wrap exceptions several times. That is fine if the cause chain is preserved. It becomes a problem when a layer replaces the exception with a generic one.

#### Production angle

Lost causes turn incidents into guesswork. Operators see "Failed" but not timeout, constraint violation or parse error.

#### Traps / caveats

- Always pass the cause when wrapping.
- Pass exceptions to the logger, not just their messages.
- Inspect suppressed exceptions when cleanup failed.

#### Optional Anki

Q: What is the common bad wrapping pattern?
A: Throwing a new exception without passing the original as cause.

</details>

<a id="exc-prop-005"></a>

<details>
<summary><strong>EXC-PROP-005. When would you prefer `Optional`, `Result`, `Either` or error objects instead of exceptions?</strong></summary>

#### Short answer

Use value-based results for expected, frequent, non-exceptional outcomes that callers should branch on explicitly.

#### Interview answer

`Optional` is good for an absent single value, such as "user not found" in an internal lookup. `Result` or `Either` is useful when success and failure are both normal outcomes and the caller must handle both. Error objects are useful for validation and batch processing where multiple errors need to be returned.

Exceptions are better for aborting a command, enforcing contracts, or reporting unexpected infrastructure failures.

#### Deep dive

The design should make the common caller behavior obvious. If every caller catches `NotFoundException` to continue, `Optional` may be clearer. If absence is exceptional for a command, an exception may be fine.

#### Production angle

Using exceptions for expected high-volume results can create performance and observability noise. Using result objects for truly exceptional failures can hide incidents if callers ignore them.

#### Traps / caveats

- Do not return `Optional` for every nullable field or DTO property.
- Do not make callers inspect strings inside `Result`.
- Keep error contracts consistent between sync APIs, REST and messaging.

#### Optional Anki

Q: What is `Optional` best for?
A: Expected absence of a single value.

</details>

<a id="exc-custom-008"></a>

<details>
<summary><strong>🧠 EXC-CUSTOM-008. When would you disable stack trace generation in a custom exception?</strong></summary>

#### Short answer

Only in carefully measured hot paths where the exception is expected, frequent, and diagnostics do not need per-throw stack traces.

#### Interview answer

Java `Throwable` has a protected constructor that can disable suppression and stack trace writing. Some systems use stackless exceptions for very high-volume control signals, parsers or frameworks.

In normal backend code, stack traces are too valuable to remove. Disabling them should be a deliberate performance trade-off with metrics and alternative context.

#### Deep dive

A stackless exception can reduce allocation and CPU cost, but it makes root-cause analysis harder. It also surprises developers who expect stack traces in logs.

#### Production angle

Use stackless exceptions only with clear naming, limited scope and observability that identifies the operation and caller context another way.

#### Traps / caveats

- Do not remove stack traces to hide noisy bugs.
- Benchmark before changing exception behavior.
- Avoid stackless exceptions in public APIs unless documented.

#### Optional Anki

Q: What is the main trade-off of stackless exceptions?
A: Better performance but weaker diagnostics.

</details>
