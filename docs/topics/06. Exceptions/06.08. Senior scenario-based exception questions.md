# 06.08. Senior scenario-based exception questions

---

<a id="exc-scenario-001"></a>

<details>
<summary><strong>EXC-SCENARIO-001. An external payment API times out. What should the service return, log and retry?</strong></summary>

#### Short answer

Treat the outcome as ambiguous, log with correlation and provider context, return a safe error or pending status, and retry only with idempotency protection.

#### Interview answer

A timeout does not prove the payment failed; the provider may have processed it after our client stopped waiting. I would log the payment operation ID, provider, timeout, attempt and trace ID. The API response depends on product requirements: often 202 pending, 503/504, or a domain status like "payment processing".

Retries need idempotency keys or provider request IDs. Without them, retrying can charge twice.

#### Deep dive

The service should reconcile later by querying provider status or consuming webhook events. Payment state should model pending, authorized, failed and unknown states explicitly.

#### Production angle

Payment timeouts are correctness problems, not just technical exceptions. Observability and reconciliation are as important as the immediate HTTP response.

#### Traps / caveats

- Do not assume timeout means rollback.
- Do not retry non-idempotently.
- Do not expose provider internals to the client.

#### Optional Anki

Q: Why is retrying payment after timeout dangerous?
A: The original request may have succeeded, causing duplicate charge.

</details>

<a id="exc-scenario-002"></a>

<details>
<summary><strong>EXC-SCENARIO-002. A database unique constraint violation happens during user registration. How should it be handled?</strong></summary>

#### Short answer

Translate it to a domain conflict such as duplicate email, return a safe 409 response, and keep the database constraint as the final correctness guard.

#### Interview answer

First, do not rely only on a pre-check like "find by email" because concurrent requests can race. The unique constraint is the authoritative guard. Catch or translate the persistence exception at the repository/service boundary, identify the relevant constraint when possible, and map it to a domain exception such as `EmailAlreadyRegisteredException`.

The API can return `409 Conflict` with a stable error code.

#### Deep dive

Pre-checks are still useful for user experience, but they are not sufficient for correctness. The insert/update must handle the constraint violation.

#### Production angle

Metrics should treat expected duplicates differently from database outages or schema bugs.

#### Traps / caveats

- Do not expose raw constraint names if they reveal internals.
- Do not return 500 for expected duplicate registration.
- Do not parse vendor messages unless there is no better stable signal.

#### Optional Anki

Q: Why is a pre-check before insert not enough for uniqueness?
A: Concurrent requests can pass the check and race at insert time.

</details>

<a id="exc-scenario-003"></a>

<details>
<summary><strong>EXC-SCENARIO-003. A request partially succeeds before an exception is thrown. How do you keep the system consistent?</strong></summary>

#### Short answer

Use transaction boundaries for local changes and compensating actions, outbox, idempotency or saga patterns for cross-resource work.

#### Interview answer

First identify what partially succeeded: database writes, message publication, external HTTP calls, cache updates or file writes. For one database, a transaction can roll back local changes. Across systems, rollback is not automatic. You need design patterns: outbox for messages, idempotency for retries, compensating actions for external side effects, and explicit state transitions.

Do not hide the exception and return success unless the operation is truly complete or safely queued.

#### Deep dive

A common design is to commit local state and an outbox event atomically, then process side effects asynchronously with retries.

#### Production angle

Partial success is where exception handling meets system design. The answer should discuss consistency model, not only `try-catch`.

#### Traps / caveats

- Local transactions do not roll back external service calls.
- Retrying after partial success can duplicate side effects.
- Cache updates should not be the source of truth.

#### Optional Anki

Q: What pattern helps atomically persist state and publish later?
A: The outbox pattern.

</details>

<a id="exc-scenario-004"></a>

<details>
<summary><strong>EXC-SCENARIO-004. A scheduled job fails repeatedly. How should failures be logged, retried and alerted?</strong></summary>

#### Short answer

Log once per attempt with job context, use bounded retries/backoff where useful, record metrics, and alert on sustained failure or business impact.

#### Interview answer

A scheduled job has no user request to return to, so the job boundary must own exception handling. Include job name, run ID, input range, attempt and trace ID. If the failure is transient, retry with backoff and a limit. If it is deterministic bad data, skip/quarantine the item and continue if safe.

Alert on repeated failure, missed schedules, stale output or queue growth.

#### Deep dive

The job should be idempotent or checkpointed so retries do not duplicate work. Long jobs need progress markers and clear restart behavior.

#### Production angle

Repeated job failures often become data freshness incidents. Observability should show last successful run and lag.

#### Traps / caveats

- Do not retry forever in a tight loop.
- Do not log a full stack trace for every item in a bad batch.
- Do not mark the job successful after silently skipping critical work.

#### Optional Anki

Q: What should every scheduled job failure log include?
A: Job name/run context and correlation information.

</details>

<a id="exc-scenario-005"></a>

<details>
<summary><strong>EXC-SCENARIO-005. A Kafka consumer fails to process a message. How should retries and DLQ behavior be designed?</strong></summary>

#### Short answer

Classify the failure, retry transient errors with backoff, send poison messages to a DLQ after limits, and commit offsets only according to the chosen delivery semantics.

#### Interview answer

A consumer failure can be transient, such as a database timeout, or permanent, such as invalid message schema. Transient errors can be retried with backoff. Permanent poison messages should not block the partition forever; after a policy limit, send them to a DLQ with enough metadata to investigate.

Offset commit timing matters. Commit after successful processing for at-least-once semantics, and make processing idempotent because duplicates can happen.

#### Deep dive

DLQ records should include original topic, partition, offset, key, failure category, exception summary and timestamp, while avoiding sensitive payload leakage.

#### Production angle

Bad retry policy can cause consumer lag, rebalance storms and duplicate writes.

#### Traps / caveats

- Do not retry invalid messages forever.
- Do not commit before processing unless message loss is acceptable.
- Do not assume exactly-once business behavior without idempotent side effects.

#### Optional Anki

Q: Why are poison messages dangerous?
A: They can block processing forever if retried without a DLQ policy.

</details>

<a id="exc-scenario-006"></a>

<details>
<summary><strong>EXC-SCENARIO-006. A REST endpoint returns a stack trace to the client. What is wrong and how would you fix it?</strong></summary>

#### Short answer

It leaks internals and creates an unsafe error contract. Add global exception handling that returns safe structured errors and logs the stack trace internally.

#### Interview answer

The client should not see Java class names, file paths, SQL, framework internals or stack frames. I would implement or fix a `@ControllerAdvice`, map known exceptions to statuses and error codes, add a fallback 500 handler, and include a request or trace ID in the response.

The stack trace should be logged internally with context.

#### Deep dive

Also check environment configuration. Some frameworks expose detailed error pages or messages in development mode; production should disable them.

#### Production angle

This is both a security and API-quality issue. It can leak implementation details and confuse client retry behavior.

#### Traps / caveats

- Do not simply hide all details and lose field validation errors.
- Do not return raw `exception.getMessage()`.
- Test error responses with contract tests.

#### Optional Anki

Q: What should replace stack traces in external API errors?
A: Safe structured errors with stable codes and a trace/request ID.

</details>

<a id="exc-scenario-007"></a>

<details>
<summary><strong>EXC-SCENARIO-007. A service slowly exhausts its database connection pool. How can exception handling cause this?</strong></summary>

#### Short answer

Exceptions can bypass cleanup if connections, statements or result sets are not closed on all paths.

#### Interview answer

If code opens a JDBC connection and an exception happens before `close()`, the connection may never return to the pool. Similar leaks can happen with result sets, statements, streams or HTTP responses. Manual cleanup in normal paths is not enough; use try-with-resources or framework-managed transactions.

Exception handling can also swallow failures and keep transactions open too long.

#### Deep dive

In Spring, verify transaction boundaries and connection acquisition. Long transactions, blocked calls inside transactions and missing response body close can look like pool exhaustion too.

#### Production angle

Investigate pool metrics, active/idle counts, leak detection logs, thread dumps and recent error spikes.

#### Traps / caveats

- Do not close framework-managed connections manually.
- Do not hold database transactions while calling slow external services.
- Do not ignore suppressed close failures.

#### Optional Anki

Q: What Java construct helps prevent JDBC resource leaks?
A: Try-with-resources.

</details>

<a id="exc-scenario-008"></a>

<details>
<summary><strong>EXC-SCENARIO-008. The application throws `OutOfMemoryError` in production. Should you catch it?</strong></summary>

#### Short answer

Usually no. Treat it as a serious process health problem; capture diagnostics if possible and let the process restart.

#### Interview answer

`OutOfMemoryError` means the JVM could not allocate memory. The application may be in an unreliable state, and even logging or recovery code may allocate more memory. Normal business code should not catch it and continue.

At top-level boundaries, infrastructure may catch `Throwable` to log minimally, trigger diagnostics or initiate shutdown. The real fix is to inspect heap dump, GC logs, allocation profile and recent changes.

#### Deep dive

Some specialized systems reserve memory for emergency logging, but that is platform-level design, not ordinary service logic.

#### Production angle

Use memory limits, heap dumps on OOM, restart policy, alerts and postmortem analysis. Check leaks, unbounded caches, large payloads and log storms.

#### Traps / caveats

- Do not return success after OOM.
- Do not catch `Error` broadly in business code.
- Stack traces may be incomplete during severe memory pressure.

#### Optional Anki

Q: Is `OutOfMemoryError` normally recoverable in application code?
A: No.

</details>

<a id="exc-scenario-009"></a>

<details>
<summary><strong>EXC-SCENARIO-009. Logs show only `CompletionException`. How do you find the real root cause?</strong></summary>

#### Short answer

Unwrap the `CompletionException` cause chain and inspect the original exception from the failed async stage.

#### Interview answer

`CompletionException` is usually a wrapper from `CompletableFuture`. I would inspect `getCause()` recursively, including any `ExecutionException` or framework wrapper below it. The real cause may be an HTTP timeout, validation failure, database exception or bug in a lambda.

Then improve logging so async boundaries log the meaningful cause and context, not just the wrapper.

#### Deep dive

If multiple futures are combined, one failure may hide others. Check suppressed or aggregated failures depending on the API used.

#### Production angle

Add trace propagation, task names and operation IDs to async logs so a failed stage can be linked back to the request or message.

#### Traps / caveats

- Do not handle all `CompletionException` the same way.
- Do not lose the original cause when rewrapping.
- Watch for swallowed failures in `exceptionally`.

#### Optional Anki

Q: Where is the real cause of `CompletionException` usually found?
A: In `getCause()`.

</details>

<a id="exc-scenario-010"></a>

<details>
<summary><strong>EXC-SCENARIO-010. A service ignores `InterruptedException` and shutdown hangs. What is the bug?</strong></summary>

#### Short answer

The code swallowed a cooperative cancellation signal, so the thread kept running instead of stopping or preserving interrupt status.

#### Interview answer

`InterruptedException` tells blocking code that the thread was asked to stop waiting. Catching it with an empty block, or logging and continuing forever, breaks shutdown and timeout behavior. If the method can throw it, propagate it. If not, restore the flag with `Thread.currentThread().interrupt()` and exit or throw an appropriate exception.

#### Deep dive

Common bad code appears in loops around `sleep`, `take`, `join` or blocking queues. The loop catches interruption and continues.

#### Production angle

This causes slow deployments, stuck worker pools and processes that refuse graceful shutdown.

#### Traps / caveats

- Do not convert interruption to normal success.
- Do not retry immediately after interruption unless policy says so.
- Test shutdown paths, not only normal processing.

#### Optional Anki

Q: What should code usually do after catching interruption and not rethrowing?
A: Restore the interrupt flag and stop the operation.

</details>

<a id="exc-scenario-011"></a>

<details>
<summary><strong>EXC-SCENARIO-011. A Spring `@Transactional` method throws a checked exception and data is committed. Why?</strong></summary>

#### Short answer

Spring does not roll back on checked exceptions by default, so the transaction can commit unless rollback is configured.

#### Interview answer

By default, Spring rolls back for `RuntimeException` and `Error`, not checked exceptions. If a transactional method throws a checked business exception and no `rollbackFor` rule exists, Spring may commit the transaction.

The fix is to decide the desired business behavior: configure `rollbackFor`, use an unchecked application exception, or separate validation from transactional writes.

#### Deep dive

Also verify that the method is actually transactional. Self-invocation, private methods, final methods or wrong bean boundaries can bypass proxy-based transactions.

#### Production angle

This bug creates surprising partial data because developers assume "any exception means rollback".

#### Traps / caveats

- Do not add `rollbackFor = Exception.class` blindly without understanding business exceptions.
- Catching the exception inside the method can still lead to commit.
- Test rollback with integration tests.

#### Optional Anki

Q: What Spring rollback rule causes this scenario?
A: Checked exceptions do not trigger rollback by default.

</details>

<a id="exc-scenario-012"></a>

<details>
<summary><strong>EXC-SCENARIO-012. A client retries after a timeout and creates duplicate data. How should exceptions and idempotency be handled?</strong></summary>

#### Short answer

Treat timeout as ambiguous and use idempotency keys, unique constraints or deduplication so repeated requests return the original result instead of repeating side effects.

#### Interview answer

The client timed out, but the server may have completed the write. Retrying the same command without idempotency can create duplicates. The API should accept an idempotency key or use a natural unique business key. The server stores request status/result and returns the same outcome for repeated attempts.

Exception handling should classify timeout separately from known failure and document retry behavior.

#### Deep dive

For async workflows, return an operation ID and let clients poll status. For synchronous writes, combine idempotency with database constraints and transactional storage.

#### Production angle

Duplicate orders, payments and registrations are common symptoms of retry without idempotency.

#### Traps / caveats

- Do not tell clients to retry all 5xx blindly.
- Idempotency keys need expiration and conflict handling.
- Database uniqueness is a guard, not a complete client contract.

#### Optional Anki

Q: What is the safe retry primitive for non-idempotent POST commands?
A: An idempotency key or equivalent deduplication key.

</details>
