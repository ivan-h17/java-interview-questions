# 06.06. Concurrency, async execution and interruption

---

<a id="exc-async-001"></a>

<details>
<summary><strong>EXC-ASYNC-001. What happens if an exception is thrown from `Thread.run()`, and what is `Thread.UncaughtExceptionHandler`?</strong></summary>

#### Short answer

An uncaught exception from `Thread.run()` terminates that thread and is reported to its `UncaughtExceptionHandler`.

#### Interview answer

If a thread's `run()` method throws an exception that is not caught inside the thread, the thread dies. Java then calls the thread's `UncaughtExceptionHandler`, or the default handler if configured.

This handler is a last-resort boundary for logging, metrics or shutdown decisions. It cannot magically resume the failed operation safely.

#### Deep dive

Executor frameworks often catch task exceptions before they reach the thread's uncaught handler, especially for submitted tasks. So behavior differs between raw threads and executors.

#### Production angle

Unhandled thread death can silently stop background work if the application does not monitor it. Thread names and handlers improve diagnosis.

#### Traps / caveats

- Do not rely only on uncaught handlers inside executors.
- A handler should not perform complex recovery in an unsafe state.
- Always include thread name and task context in logs.

#### Optional Anki

Q: What happens to a thread when `run()` throws uncaught?
A: The thread terminates.

</details>

<a id="exc-async-002"></a>

<details>
<summary><strong>EXC-ASYNC-002. What is the difference between `ExecutorService.execute()` and `submit()` for exceptions?</strong></summary>

#### Short answer

`execute()` lets unchecked task exceptions reach the worker's uncaught handling path; `submit()` captures task failures inside the returned `Future`.

#### Interview answer

With `execute(Runnable)`, an unchecked exception escapes the task and is handled by the executor/thread machinery, often logged through the uncaught exception handler and followed by worker replacement.

With `submit(...)`, the executor catches the exception and stores it in the returned `Future`. The caller sees it only when calling `get()`, wrapped in `ExecutionException`. If no one checks the future, the failure may be missed.

#### Deep dive

This distinction is a common source of silent failures in background code. `submit()` is useful when the caller will observe the result; `execute()` is useful for fire-and-forget tasks only with proper boundary logging.

#### Production angle

Always observe futures or attach completion handlers. Otherwise failed tasks can vanish from operational visibility.

#### Traps / caveats

- Do not ignore a `Future` returned from `submit()`.
- Do not assume `UncaughtExceptionHandler` catches submitted task failures.
- Wrap task bodies with explicit logging when needed.

#### Optional Anki

Q: How does `submit()` expose a task exception?
A: Through `Future.get()` as an `ExecutionException`.

</details>

<a id="exc-async-003"></a>

<details>
<summary><strong>EXC-ASYNC-003. How does `Future.get()` report task failures?</strong></summary>

#### Short answer

`Future.get()` throws `ExecutionException` when the task failed, and the original task exception is available as the cause.

#### Interview answer

`Future.get()` has several outcomes. It returns the result if the task succeeded. It throws `ExecutionException` if the task threw an exception. It throws `InterruptedException` if the waiting thread is interrupted. It can throw `CancellationException` if the future was canceled.

The real task failure is inside `executionException.getCause()`.

#### Deep dive

`ExecutionException` is checked because `get()` is a blocking API that forces the caller to handle failure and interruption.

#### Production angle

Code that logs only `ExecutionException` without inspecting the cause loses the real failure type and message.

#### Traps / caveats

- Handle `InterruptedException` correctly by restoring the interrupt flag when you cannot propagate it.
- Distinguish cancellation from failure.
- Do not block indefinitely without timeout in request threads.

#### Optional Anki

Q: Where is the original task exception stored after `Future.get()` fails?
A: In `ExecutionException.getCause()`.

</details>

<a id="exc-async-004"></a>

<details>
<summary><strong>EXC-ASYNC-004. How does `CompletableFuture` wrap failures, and how do `get()` and `join()` differ?</strong></summary>

#### Short answer

`CompletableFuture.get()` reports failures with checked `ExecutionException`; `join()` reports failures with unchecked `CompletionException`.

#### Interview answer

If a `CompletableFuture` stage throws, the future completes exceptionally. Calling `get()` wraps that failure in `ExecutionException`. Calling `join()` wraps it in `CompletionException`. Both wrappers usually have the real cause inside `getCause()`.

`get()` also declares `InterruptedException`; `join()` does not, which makes `join()` convenient but easier to misuse in code that should respect interruption.

#### Deep dive

If code manually completes a future exceptionally with a `CompletionException`, wrapping may be slightly different, but the practical rule is to unwrap to the meaningful cause.

#### Production angle

Global logs that show only `CompletionException` are weak. Handlers should unwrap and classify the root cause before mapping or alerting.

#### Traps / caveats

- Do not call `join()` in event-loop or request paths without understanding blocking.
- Do not swallow failures in `exceptionally`.
- Distinguish timeout, cancellation and real failure.

#### Optional Anki

Q: Which method throws unchecked `CompletionException`: `get()` or `join()`?
A: `join()`.

</details>

<a id="exc-async-005"></a>

<details>
<summary><strong>EXC-ASYNC-005. How should exceptions be handled in a `CompletableFuture` chain?</strong></summary>

#### Short answer

Handle them with `handle`, `exceptionally`, `whenComplete` or async recovery stages, and make sure failures are observed at the boundary.

#### Interview answer

`handle` can transform both success and failure into a new result. `exceptionally` recovers from failure. `whenComplete` observes success or failure but usually should not be used for recovery. `exceptionallyCompose` or composition with another future can recover asynchronously.

The chain should end at a boundary that observes failure: HTTP response mapping, job logging, message retry, or caller result.

#### Deep dive

Recovery changes the future back to successful completion. That is useful for fallbacks but dangerous if it hides a real failure.

#### Production angle

Async failure policy should include logging context, timeout, cancellation, retries and metrics. Otherwise failures may sit inside futures unnoticed.

#### Traps / caveats

- `whenComplete` is for side effects, not normal recovery.
- `exceptionally` can accidentally turn a failed operation into success.
- Always preserve or reconstruct useful context across async boundaries.

#### Optional Anki

Q: Which `CompletableFuture` method observes both success and failure without normally recovering?
A: `whenComplete`.

</details>

<a id="exc-async-006"></a>

<details>
<summary><strong>EXC-ASYNC-006. How do checked exceptions fit into `CompletableFuture` pipelines?</strong></summary>

#### Short answer

Standard `CompletableFuture` functional stages do not allow arbitrary checked exceptions, so checked failures must be caught and wrapped or handled before entering the pipeline.

#### Interview answer

Methods such as `thenApply` take functional interfaces that do not declare checked exceptions. If a lambda calls code that throws `IOException`, the lambda must catch it, convert it to an unchecked exception, return a failed future, or use a helper that adapts checked exceptions.

The wrapping should preserve the cause and match the service's exception policy.

#### Deep dive

For async operations, `CompletableFuture.failedFuture(e)` can represent a failure explicitly. For synchronous code inside a stage, throwing a `CompletionException` or domain runtime exception is common.

#### Production angle

Random `RuntimeException(e)` wrappers make async failures hard to classify. Use meaningful application exceptions where possible.

#### Traps / caveats

- Do not use sneaky throws casually in async pipelines.
- Do not lose interruption semantics when wrapping.
- Do not turn checked infrastructure failures into successful fallback values unless intended.

#### Optional Anki

Q: Can a `thenApply` lambda directly throw `IOException`?
A: Not unless it catches or adapts it, because `Function` does not declare it.

</details>

<a id="exc-async-007"></a>

<details>
<summary><strong>EXC-ASYNC-007. What makes `InterruptedException` special, and why should the interrupt flag often be restored?</strong></summary>

#### Short answer

`InterruptedException` is a cooperative cancellation signal. Catching it clears the interrupt status, so code that cannot propagate it should usually restore the flag.

#### Interview answer

Interruption is how Java asks a thread to stop waiting, sleeping or blocking cooperatively. Many blocking methods throw `InterruptedException` and clear the thread's interrupted status. If you catch it and cannot rethrow, call `Thread.currentThread().interrupt()` so outer code can still observe cancellation.

Swallowing interruption can make shutdown, timeouts and cancellation hang.

#### Deep dive

Good handling depends on context: propagate `InterruptedException` if your method can declare it; otherwise restore the flag and abort or throw an appropriate unchecked exception.

#### Production angle

Ignoring interruption is a common cause of slow shutdowns, stuck job workers and broken thread pool lifecycle.

#### Traps / caveats

- Do not catch `InterruptedException` and continue as if nothing happened.
- Do not wrap it without restoring the interrupt status if the method cannot throw it.
- Interruption does not forcibly kill a thread.

#### Optional Anki

Q: What should you often do after catching `InterruptedException` if you cannot rethrow it?
A: Restore the interrupt flag with `Thread.currentThread().interrupt()`.

</details>

<a id="exc-async-008"></a>

<details>
<summary><strong>EXC-ASYNC-008. What is the difference between cancellation and failure?</strong></summary>

#### Short answer

Failure means work tried and errored; cancellation means work was requested to stop or not complete, often intentionally.

#### Interview answer

An exception such as `IOException` or `IllegalStateException` means the task failed. Cancellation means the result is no longer needed, a timeout occurred, a parent task stopped, or a caller canceled the operation. Java often represents cancellation with `CancellationException`.

Handling differs. Failures may need retry or alerting. Cancellations may be normal and should often avoid noisy error logs.

#### Deep dive

Cancellation may or may not interrupt the underlying running work depending on API and implementation. For example, some futures only mark the future canceled.

#### Production angle

Treating cancellation as an error creates noisy logs during shutdowns and timeouts. Treating real failures as cancellation hides incidents.

#### Traps / caveats

- Do not assume `cancel(true)` always stops the underlying task.
- Do not retry cancellations blindly.
- Preserve cancellation state across composed async operations.

#### Optional Anki

Q: What exception commonly represents cancellation?
A: `CancellationException`.

</details>

<a id="exc-async-009"></a>

<details>
<summary><strong>EXC-ASYNC-009. How can unhandled async exceptions silently disappear?</strong></summary>

#### Short answer

They can be captured in futures, swallowed by callbacks, logged only by framework internals, or occur on threads without visible supervision.

#### Interview answer

In async code, an exception often does not throw on the original caller thread. It may complete a `Future` exceptionally. If no one calls `get()`, `join()` or attaches a handler, the failure may never be observed. In scheduled or message frameworks, behavior depends on the container's error handler.

Fire-and-forget code needs explicit boundary logging and metrics.

#### Deep dive

`exceptionally` can also hide failures by returning fallback values without logging or marking degraded behavior.

#### Production angle

Silent async failures cause missing notifications, stuck jobs, unprocessed messages and data drift.

#### Traps / caveats

- Do not ignore returned futures.
- Do not use `void @Async` methods without an exception strategy.
- Do not let callbacks swallow exceptions without metrics.

#### Optional Anki

Q: Why can a failed `submit()` task be missed?
A: The exception is stored in the `Future` and no one may observe it.

</details>

<a id="exc-async-010"></a>

<details>
<summary><strong>EXC-ASYNC-010. Why should locks, semaphores, permits and other concurrency resources be released after exceptions?</strong></summary>

#### Short answer

Because an exception can exit the critical section early, leaving locks or permits held forever unless release is guaranteed.

#### Interview answer

When code acquires a lock, semaphore permit or similar resource, release must happen in `finally` or an equivalent structured construct. Otherwise an exception between acquire and release can deadlock other threads or exhaust permits.

The same idea applies to thread-local state and MDC: restore or clear it even when work fails.

#### Deep dive

For `Lock`, the pattern is:

```java
lock.lock();
try {
    work();
} finally {
    lock.unlock();
}
```

#### Production angle

Leaked locks or permits are production outages: hung workers, blocked request threads, saturated pools and timeout storms.

#### Traps / caveats

- Only unlock if the lock was actually acquired.
- Be careful with interruption during acquisition.
- Keep critical sections small.

#### Optional Anki

Q: Where should `unlock()` usually be called?
A: In a `finally` block after successful acquisition.

</details>

<a id="exc-async-011"></a>

<details>
<summary><strong>🧠 EXC-ASYNC-011. How do exceptions behave in virtual threads?</strong></summary>

#### Short answer

Exceptions in virtual threads behave like exceptions in platform threads: uncaught exceptions terminate that virtual thread. The difference is the execution model and scale, not exception semantics.

#### Interview answer

A virtual thread is still a Java `Thread`. If code inside it throws and does not catch, the virtual thread ends and the exception is handled by the thread's uncaught exception mechanism or by the framework supervising it.

The important backend difference is scale: many virtual threads may fail concurrently, so structured supervision, logging context and clear boundaries matter even more.

#### Deep dive

Blocking calls in virtual threads are intended to be cheap, but exception handling still needs the same rules: preserve causes, handle interruption, release resources and observe task failures.

#### Production angle

Virtual threads make thread-per-request designs more practical, but they do not remove the need for timeouts, cancellation policy and exception observability.

#### Traps / caveats

- Do not assume virtual threads make failures automatically visible.
- Avoid noisy logs when many short-lived virtual threads fail from the same dependency outage.
- Keep thread naming and tracing useful.

#### Optional Anki

Q: Does an uncaught exception terminate a virtual thread?
A: Yes.

</details>

<a id="exc-async-012"></a>

<details>
<summary><strong>🧠 EXC-ASYNC-012. How do structured concurrency APIs aggregate or propagate task failures?</strong></summary>

#### Short answer

Structured concurrency scopes supervise related tasks, propagate failure to the parent, and cancel or collect sibling tasks according to the scope's completion policy.

#### Interview answer

The idea is to treat concurrent subtasks as a structured block: fork tasks, wait for them, and decide what happens if one fails. The parent sees the outcome instead of losing failures in detached tasks.

As of JDK 26, structured concurrency is still a preview API. In the JDK 25 preview, `StructuredTaskScope.open()` creates a scope whose default policy fails if any subtask fails; other policies can be supplied with a `Joiner`. In JDK 26, the API is previewed again with small changes such as `Joiner` timeout handling and naming/result-shape changes. For interviews, explain the concept and mention that exact API names are version-sensitive.

#### Deep dive

The key interview concept is supervision. Related async work should have an owner responsible for cancellation, joining, failure propagation and cleanup. If a subtask fails, the scope can propagate the failure to the parent and prevent sibling tasks from leaking beyond the request or operation that created them.

#### Production angle

Structured concurrency reduces leaked tasks and invisible async failures. It helps implement request-scoped deadlines and cancellation, especially with virtual threads where many concurrent subtasks are cheap but still need ownership.

#### Traps / caveats

- Do not detach subtasks without ownership.
- Know whether sibling tasks are canceled on first failure.
- Preserve the most useful cause and inspect suppressed/aggregated failures.
- Check the target JDK before using concrete `StructuredTaskScope` APIs in production code.

#### Optional Anki

Q: What problem does structured concurrency solve for exceptions?
A: It gives related tasks a parent that observes failures and handles cancellation.

</details>
