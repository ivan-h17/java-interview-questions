# 06.07. Performance and testing

---

<a id="exc-perf-001"></a>

<details>
<summary><strong>EXC-PERF-001. Are exceptions expensive in Java, and what part is usually expensive?</strong></summary>

#### Short answer

Creating and throwing exceptions can be expensive mainly because of stack trace capture, allocation and later logging.

#### Interview answer

A `try-catch` block itself is usually not the expensive part. The expensive part is actually throwing: creating the exception, filling in the stack trace, unwinding control flow, and often logging the full stack. If exceptions are rare, this cost is acceptable. If they happen on a hot path, it becomes a performance problem.

The right rule is not "never use exceptions"; it is "do not use them for expected high-volume control flow".

#### Deep dive

Stack trace creation walks stack frames to record where the exception was created. Logging then formats and emits that information, which can be much more expensive than the throw itself.

#### Production angle

Exception storms can raise CPU, allocate memory, increase GC pressure and overload logging systems.

#### Traps / caveats

- Do not micro-optimize rare failure paths.
- Do not remove stack traces from normal exceptions without strong evidence.
- Logging volume is often the real production cost.

#### Optional Anki

Q: What is usually the expensive part of exceptions?
A: Throwing and stack trace creation, especially when logged.

</details>

<a id="exc-perf-002"></a>

<details>
<summary><strong>EXC-PERF-002. Why should exceptions not be used in hot-path control flow?</strong></summary>

#### Short answer

Frequent exceptions allocate, capture stack traces, disrupt optimized code paths and create noisy observability.

#### Interview answer

In a hot path, expected outcomes should be represented by branches, return values, `Optional`, result objects or validation results. Throwing exceptions for routine cases like "not found in cache" or "field invalid in a large import" can create thousands of stack traces per second.

That cost affects latency, throughput and log systems.

#### Deep dive

The JIT can optimize normal predictable branches well. Exception paths are optimized differently and are meant to be uncommon.

#### Production angle

Hot-path exceptions show up as CPU spikes, GC pressure, large log bills and alerts that hide real defects.

#### Traps / caveats

- Occasional business exceptions are fine.
- Do not convert every failure to error codes; exceptions remain useful for aborting operations.
- Measure before making stackless exceptions or complex alternatives.

#### Optional Anki

Q: What should replace exceptions for frequent expected validation results?
A: Result objects or error lists.

</details>

<a id="exc-perf-003"></a>

<details>
<summary><strong>EXC-PERF-003. How do exception allocation and full stack trace logging affect CPU, memory and GC pressure?</strong></summary>

#### Short answer

Each thrown exception can allocate objects and stack trace data; full logging formats and writes that data, increasing CPU, memory churn and I/O.

#### Interview answer

An exception is an object, and its stack trace contains frame information. Throwing many exceptions creates allocation pressure. If each one is logged with a full stack, the logging framework formats large strings and writes them to appenders or remote systems.

Under load, this can become a feedback loop: failures create logs, logs slow the service, timeouts create more failures.

#### Deep dive

Async appenders help but do not remove total cost. They can also build queues and start dropping logs if overwhelmed.

#### Production angle

Monitor exception rate, log throughput, GC pauses and logging queue health. During incidents, reduce repeated noisy logs while keeping metrics.

#### Traps / caveats

- Do not log full stack traces for every expected 4xx validation error.
- Do not sample without counting.
- Do not ignore logging backpressure.

#### Optional Anki

Q: Why can logging stack traces cause incidents during failure storms?
A: Formatting and emitting many large logs consumes CPU, memory and I/O.

</details>

<a id="exc-perf-004"></a>

<details>
<summary><strong>EXC-PERF-004. What is an exception storm in production, and how would you reduce exception volume?</strong></summary>

#### Short answer

An exception storm is a sudden high rate of repeated exceptions. Reduce it by fixing the cause, classifying expected failures, adding backoff, sampling logs and avoiding exceptions for normal high-volume cases.

#### Interview answer

Exception storms often happen after a dependency outage, bad deploy, invalid data batch or retry loop. The response is to identify the repeated category, stop unsafe retries, add backoff/jitter, sample duplicate logs, and keep metrics counting all events.

For expected high-volume validation or parsing failures, change the design to result objects or aggregate errors.

#### Deep dive

The best fix is usually not "catch and ignore". It is to reduce repeated failure creation while preserving observability and correctness.

#### Production angle

An exception storm can overload the service and observability stack at the same time, making recovery harder.

#### Traps / caveats

- Do not hide all errors to make dashboards green.
- Do not retry faster than the dependency can recover.
- Keep a representative stack trace for debugging.

#### Optional Anki

Q: What should remain even if exception logs are sampled?
A: Metrics counting the full failure rate.

</details>

<a id="exc-perf-005"></a>

<details>
<summary><strong>🧠 EXC-PERF-005. What do `Throwable.fillInStackTrace()` and HotSpot fast-throw optimization do?</strong></summary>

#### Short answer

`fillInStackTrace()` records stack frames for a throwable. HotSpot fast-throw can optimize some repeatedly thrown implicit exceptions by omitting stack traces; the related diagnostic flag is `OmitStackTraceInFastThrow`.

#### Interview answer

When a throwable is created, `fillInStackTrace()` captures where it was created. That is useful for diagnostics but can be expensive.

HotSpot has an optimization for some common implicit exceptions, such as repeated `NullPointerException` at the same bytecode location, where after enough occurrences it may throw a preallocated exception without a full stack trace. The behavior is controlled by the HotSpot flag `-XX:-OmitStackTraceInFastThrow` if you need to disable it for diagnostics. This is an implementation optimization, not portable Java semantics and not something application logic should depend on.

#### Deep dive

The JVM flag behavior and exact cases are implementation-specific. The important point is that stack traces are diagnostic data with cost. If a repeated exception suddenly appears without a stack trace, check whether fast-throw is involved before assuming the logging system truncated it.

#### Production angle

If logs suddenly show stackless repeated exceptions, JVM optimization may be involved. The real fix is still to fix the repeated failure.

#### Traps / caveats

- Do not rely on fast-throw for performance design.
- Do not disable useful diagnostics without measurement.
- Stackless repeated exceptions can make debugging harder.
- `OmitStackTraceInFastThrow` is HotSpot-specific diagnostic knowledge, not a Java language guarantee.

#### Optional Anki

Q: What HotSpot flag is related to stackless repeated implicit exceptions?
A: `OmitStackTraceInFastThrow`.

</details>

<a id="exc-perf-006"></a>

<details>
<summary><strong>🧠 EXC-PERF-006. Is a `try-catch` block expensive when no exception is thrown, and how can exceptions affect JIT optimization?</strong></summary>

#### Short answer

A non-throwing `try-catch` is usually cheap. Frequent actual exceptions can affect optimization assumptions and move execution onto slower uncommon paths.

#### Interview answer

Modern JVMs are designed so simply having a `try-catch` block is not normally a performance problem. The cost appears when exceptions are thrown frequently. Exceptions represent uncommon control flow, and the JIT may optimize assuming they are rare.

If the "rare" path becomes common, the code can suffer from deoptimization, poor branch predictability and stack trace overhead.

#### Deep dive

Exact JIT behavior is JVM-specific. In interviews, avoid overclaiming low-level details; focus on the practical rule: measure and keep exceptions exceptional.

#### Production angle

Do not remove useful try-catch blocks for performance without profiling. Look for high exception rates, not just handler presence.

#### Traps / caveats

- Empty catch blocks are not a performance optimization.
- Microbenchmarks can mislead if they do not warm up correctly.
- Logging often dominates the cost.

#### Optional Anki

Q: Is merely entering a `try` block usually expensive?
A: No, not compared with actually throwing an exception.

</details>

<a id="exc-perf-007"></a>

<details>
<summary><strong>🧠 EXC-PERF-007. How would you benchmark exception-heavy code correctly?</strong></summary>

#### Short answer

Use JMH, realistic exception rates, proper warmup, separate logging cost, and measure allocation as well as latency.

#### Interview answer

Exception benchmarks are easy to get wrong. I would use JMH rather than ad-hoc loops, include warmup, avoid dead-code elimination, and test realistic ratios of success to failure. I would measure throughput, latency, allocations and GC.

If production logs stack traces, benchmark logging separately because it can dominate the cost.

#### Deep dive

Compare alternatives fairly: branch/result object, exception without logging, exception with logging, stackless exception if relevant. Use representative stack depth and payload context.

#### Production angle

Benchmark results should be validated against production telemetry: exception rate, CPU profile, allocation profile and log volume.

#### Traps / caveats

- Do not benchmark with `System.currentTimeMillis()` in a simple loop.
- Do not ignore JIT warmup.
- Do not benchmark exceptions without the logging behavior used in production.

#### Optional Anki

Q: What Java tool is commonly used for reliable microbenchmarks?
A: JMH.

</details>

<a id="exc-test-001"></a>

<details>
<summary><strong>EXC-TEST-001. How do you test that code throws an exception and verify its message, error code or cause?</strong></summary>

#### Short answer

Use assertion APIs such as JUnit `assertThrows`, then inspect the returned exception object.

#### Interview answer

In JUnit, `assertThrows` verifies the type and returns the exception:

```java
var ex = assertThrows(DuplicateUserException.class,
        () -> service.register(command));
assertEquals("USER_DUPLICATE", ex.errorCode());
assertInstanceOf(DataIntegrityViolationException.class, ex.getCause());
```

Test stable fields and causes, not fragile full stack traces.

#### Deep dive

For custom exceptions, tests should cover the exception type, meaningful message or code, structured fields and preserved cause.

#### Production angle

Exception tests protect API contracts and prevent accidental changes that break clients, rollback behavior or error mapping.

#### Traps / caveats

- Do not assert the entire stack trace.
- Do not overfit tests to exact wording unless the message is a contract.
- Test both expected and unexpected error paths.

#### Optional Anki

Q: What does JUnit `assertThrows` return?
A: The thrown exception object.

</details>

<a id="exc-test-002"></a>

<details>
<summary><strong>EXC-TEST-002. How do you test cleanup, transaction rollback or retry behavior after an exception?</strong></summary>

#### Short answer

Inject controlled failures and verify observable effects: resources closed, data rolled back, retries attempted and final outcome correct.

#### Interview answer

For cleanup, use a fake or mock `AutoCloseable` and verify `close()` runs when work throws. For transactions, use integration tests with a real database or test container and assert committed state, not just method calls. For retries, use a fake dependency that fails a known number of times and verify attempts, backoff policy where practical, and idempotent outcome.

#### Deep dive

Unit tests can verify local behavior. Transaction rollback and message retry behavior often need integration tests because proxies, database transactions and listener containers are involved.

#### Production angle

These tests catch the failures that cause real incidents: leaked connections, committed partial data and retry duplication.

#### Traps / caveats

- Do not mock away the transactional proxy when testing rollback rules.
- Avoid slow sleeps for retry timing; use configurable clocks or policies.
- Verify final state, not only that an exception was thrown.

#### Optional Anki

Q: What should a transaction rollback test assert?
A: The database state after the failure.

</details>

<a id="exc-test-003"></a>

<details>
<summary><strong>EXC-TEST-003. How do you test interruption handling and exceptions in asynchronous code?</strong></summary>

#### Short answer

Use controlled executors, futures, latches or test utilities, and assert both failure propagation and interrupt status when relevant.

#### Interview answer

For async exceptions, test that the returned `Future` or `CompletableFuture` completes exceptionally with the expected cause. For interruption, run code on a test thread, interrupt it at a controlled point, and verify it exits, restores interrupt status when appropriate, or propagates `InterruptedException`.

Use timeouts in tests so failures do not hang the suite.

#### Deep dive

Avoid relying on arbitrary sleeps. Use `CountDownLatch`, barriers, fake dependencies or deterministic executors to control timing.

#### Production angle

Async and interruption bugs often appear only during shutdown, timeouts or load. Focused tests prevent stuck workers and silent failures.

#### Traps / caveats

- Do not ignore exceptions from futures in tests.
- Do not write flaky timing-based tests.
- Always clean up executors created by tests.

#### Optional Anki

Q: What should async exception tests inspect?
A: The future's exceptional completion and root cause.

</details>

<a id="exc-test-004"></a>

<details>
<summary><strong>EXC-TEST-004. Why are tests that assert full stack traces usually brittle?</strong></summary>

#### Short answer

Stack traces change with refactoring, compiler output, framework versions and line numbers, even when behavior is correct.

#### Interview answer

The stack trace is diagnostic detail, not usually a stable contract. Refactoring a method, changing a lambda, upgrading a framework or moving code can change stack frames. Tests that assert the whole trace will fail for irrelevant reasons.

Assert the exception type, error code, message contract, cause type and observable behavior instead.

#### Deep dive

It can be reasonable to assert that a cause is preserved or that a stack trace is present. Asserting every frame is rarely useful.

#### Production angle

Stable tests let teams refactor error-handling internals without breaking unrelated behavior.

#### Traps / caveats

- Do not assert full stack traces in snapshots.
- Do not make internal exception messages public contracts accidentally.
- Use contract tests for external error responses.

#### Optional Anki

Q: What should exception tests prefer over full stack traces?
A: Type, code, cause and observable behavior.

</details>

<a id="exc-test-005"></a>

<details>
<summary><strong>🧠 EXC-TEST-005. How do you test suppressed exceptions or use failure injection testing?</strong></summary>

#### Short answer

For suppressed exceptions, make both the body and `close()` fail and assert `getSuppressed()`. For failure injection, deliberately make dependencies fail to verify resilience behavior.

#### Interview answer

A suppressed exception test can use a custom `AutoCloseable` whose `close()` throws while the try body also throws. Then assert the primary exception and suppressed close failure.

Failure injection means testing how the system behaves when dependencies fail: database timeout, HTTP 503, broken network, full queue, bad message or partial write. The goal is to verify retries, rollback, DLQ, cleanup and observability.

#### Deep dive

Failure injection can be done with fakes, mocks, proxy tools, test containers, chaos testing or controlled feature flags. Scope should match risk.

#### Production angle

These tests reveal whether exception handling is reliable under realistic failure, not only on the happy path.

#### Traps / caveats

- Do not run destructive chaos tests against shared environments without controls.
- Assert recovery and final state, not only logs.
- Keep injected failures deterministic in CI.

#### Optional Anki

Q: Which method returns suppressed exceptions?
A: `getSuppressed()`.

</details>
