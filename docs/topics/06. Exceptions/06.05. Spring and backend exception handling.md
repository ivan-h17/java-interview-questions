# 06.05. Spring and backend exception handling

---

<a id="exc-spring-001"></a>

<details>
<summary><strong>EXC-SPRING-001. How does Spring MVC handle exceptions from controllers and global handlers?</strong></summary>

#### Short answer

Spring MVC resolves controller exceptions through its exception resolver chain, including local `@ExceptionHandler` methods, `@ControllerAdvice`, response-status mappings and default framework handlers.

#### Interview answer

When a controller throws an exception, Spring MVC does not usually let it escape directly to the servlet container. It asks configured `HandlerExceptionResolver`s to handle it. A method-level `@ExceptionHandler` can handle exceptions for one controller. A `@ControllerAdvice` can handle them globally. Spring can also use exceptions annotated with response status or framework-specific handlers for validation, binding and media-type failures.

The selected handler should translate internal exceptions into a safe response body and status code.

#### Deep dive

Resolver ordering matters. More specific handlers should catch known application exceptions, while a fallback handler can map unexpected exceptions to a generic 500 response. In Spring MVC, common pieces in this area include `ExceptionHandlerExceptionResolver`, `ResponseStatusExceptionResolver`, `DefaultHandlerExceptionResolver`, and, in many applications, a `@ControllerAdvice` extending or mirroring `ResponseEntityExceptionHandler`.

#### Production angle

Centralized exception handling makes API errors consistent, prevents stack trace leaks and gives one place for logging and metrics policy.

#### Traps / caveats

- Do not handle every exception as 500.
- Do not expose raw exception messages to clients.
- Make sure the global handler itself is simple and tested.
- Do not let a catch-all handler shadow more specific validation or domain handlers.

#### Optional Anki

Q: What annotation is commonly used for global Spring MVC exception handling?
A: `@ControllerAdvice`.

</details>

<a id="exc-spring-002"></a>

<details>
<summary><strong>EXC-SPRING-002. How would you choose between `@ControllerAdvice`, `@ExceptionHandler`, `ResponseStatusException` and `ProblemDetail`?</strong></summary>

#### Short answer

Use `@ControllerAdvice` for global policy, `@ExceptionHandler` for mapping exception types, `ResponseStatusException` for simple local status failures, and `ProblemDetail` / `ErrorResponse` for a standard Spring 6+ error shape.

#### Interview answer

For a production API, I prefer a global `@ControllerAdvice` with `@ExceptionHandler` methods for known exception categories. That keeps error mapping consistent. `ResponseStatusException` is convenient for simple controller-level cases, but overusing it spreads policy across controllers.

`ProblemDetail` is a response representation for machine-readable error details. It can carry status, title, detail, type, instance and extension fields such as application error code or trace ID. Spring's `ErrorResponse` abstraction can also expose a `ProblemDetail` body from framework and application exceptions.

#### Deep dive

Domain exceptions should usually not know about HTTP directly. The web boundary maps domain failures to HTTP statuses and response bodies. For shared APIs, document which error codes are stable and which fields clients may rely on.

#### Production angle

Consistent error shape improves client SDKs, documentation, monitoring and support workflows.

#### Traps / caveats

- Do not mix many unrelated error response formats.
- Do not put business mapping logic in every controller.
- Keep `detail` safe for external clients.
- Do not put Java exception class names into public error codes.
- Remember that `type` and custom properties become part of the API contract if clients use them.

#### Optional Anki

Q: What is `@ControllerAdvice` good for?
A: Centralizing controller exception handling policy.

</details>

<a id="exc-spring-003"></a>

<details>
<summary><strong>EXC-SPRING-003. How should backend exceptions be mapped to HTTP status codes and stable application error codes?</strong></summary>

#### Short answer

Map by failure category: malformed input to 400, semantic validation failures often to 400 or 422 by API policy, auth failures to 401/403, missing resources to 404, conflicts to 409, rate limits to 429, dependency failures to 502/503/504, and bugs to 500.

#### Interview answer

HTTP status should describe the protocol-level result. An application error code should describe the business or platform reason more specifically. For example, `409 Conflict` with `USER_EMAIL_ALREADY_EXISTS` is more useful than a generic 500 or a free-text message.

For senior-level design, be explicit about gray areas. `401` means authentication is missing or invalid; `403` means the caller is authenticated but not allowed. `404` can be used for true absence, and sometimes to avoid revealing whether a protected resource exists. `409` is good for state conflicts such as duplicate unique keys or optimistic locking. `502` usually means a bad upstream response, `503` means temporary unavailability, and `504` means gateway/upstream timeout.

The mapping should be stable and documented. Clients should not depend on Java exception class names.

#### Deep dive

Not every exception maps one-to-one to a status. A `DataIntegrityViolationException` could mean a duplicate resource, invalid reference, or internal schema bug. Translate it near the boundary with enough context. Choose either 400 or 422 for validation consistently; the exact choice is less important than a stable documented policy.

#### Production angle

Stable error codes drive client behavior, retries, user messages, analytics and support troubleshooting.

#### Traps / caveats

- Do not return 200 with an error body for failed operations.
- Do not use 500 for expected domain conflicts.
- Do not expose Java class names as external error codes.
- Do not return 401 when the real issue is authorization after authentication.
- Do not make clients parse human-readable messages.

#### Optional Anki

Q: What HTTP status commonly represents a unique constraint conflict in a create API?
A: `409 Conflict`.

</details>

<a id="exc-spring-004"></a>

<details>
<summary><strong>EXC-SPRING-004. How are validation exceptions usually handled in Spring Boot?</strong></summary>

#### Short answer

Spring validation failures are usually handled by a global exception handler that returns a 400 or 422 response with field-level errors.

#### Interview answer

Spring MVC can trigger validation through Bean Validation annotations such as `@Valid` or `@Validated`. Invalid request bodies, parameters or binding failures produce framework exceptions. Common examples include `MethodArgumentNotValidException` for request-body validation, `BindException` for binding/form-style failures, `ConstraintViolationException` for validated parameters, and `MethodArgumentTypeMismatchException` for conversion failures. A `@ControllerAdvice` can map those to a consistent response containing field name, rejected value policy, error code and safe message.

The client should receive actionable validation details, not a stack trace.

#### Deep dive

Validation at the HTTP boundary catches malformed or invalid input. Domain validation may still be needed deeper in the service because not all callers are HTTP controllers. The external response should distinguish field errors from object-level errors, for example invalid date range or inconsistent command state.

#### Production angle

Consistent validation responses reduce client bugs and support tickets. Metrics should separate validation failures from server failures.

#### Traps / caveats

- Do not expose raw rejected values when they may contain secrets.
- Do not rely only on controller validation for messages, jobs or internal callers.
- Keep field names stable in public APIs.
- Do not assume every validation exception has the same structure.

#### Optional Anki

Q: Should validation failures normally expose stack traces to clients?
A: No, they should expose safe field-level error details.

</details>

<a id="exc-spring-005"></a>

<details>
<summary><strong>EXC-SPRING-005. Why should internal exception details not be exposed to API clients?</strong></summary>

#### Short answer

They can leak implementation details, sensitive data and security-relevant information, and they create unstable client contracts.

#### Interview answer

Internal exceptions often mention class names, SQL, table names, file paths, provider URLs, headers or payload fragments. External clients do not need that. They need a stable status, error code, safe message and request ID.

The internal stack trace should be logged with correlation context so support can investigate.

#### Deep dive

Even messages that look harmless can reveal whether a user exists, which field is indexed, or which dependency failed. Public errors should be intentionally designed.

#### Production angle

Leaking internals can aid attackers and complicate compliance. It also couples clients to implementation details that may change.

#### Traps / caveats

- Do not return `ex.getMessage()` blindly.
- Do not include SQL errors in client responses.
- Distinguish safe user-facing messages from technical log messages.

#### Optional Anki

Q: What should clients receive instead of internal exception details?
A: A safe status, stable error code, message and request/trace ID.

</details>

<a id="exc-spring-006"></a>

<details>
<summary><strong>EXC-SPRING-006. How does `@Transactional` decide whether to roll back for checked exceptions, unchecked exceptions and `Error`?</strong></summary>

#### Short answer

By default, Spring rolls back on unchecked exceptions and `Error`, but not on checked exceptions unless rollback rules are configured.

#### Interview answer

Spring's default transaction interceptor marks a transaction rollback-only when a transactional method exits with a `RuntimeException` or `Error`. Checked exceptions do not trigger rollback by default because Spring treats them as declared business outcomes unless told otherwise.

You can configure `rollbackFor`, `noRollbackFor` or programmatic rollback rules when the default does not match the domain.

#### Deep dive

The exception must escape the transactional proxy for the default rule to apply. If the method catches it and returns normally, Spring may commit unless rollback-only was set.

#### Production angle

This is a common interview and production trap. A checked exception from a transactional method can commit partial work if rollback rules are not configured.

#### Traps / caveats

- Self-invocation can bypass transactional proxies.
- Catching and swallowing can prevent rollback.
- Rollback rules should match business semantics, not just exception class names.

#### Optional Anki

Q: Do checked exceptions trigger Spring rollback by default?
A: No, not unless configured.

</details>

<a id="exc-spring-007"></a>

<details>
<summary><strong>EXC-SPRING-007. How can swallowing an exception break transaction rollback?</strong></summary>

#### Short answer

If a transactional method catches an exception and returns normally, Spring may see success and commit the transaction.

#### Interview answer

Spring transaction rollback is usually decided when the proxied method exits. If an exception escapes, Spring can mark rollback according to its rules. If code catches the exception, logs it and returns success, the transaction interceptor may commit.

If the operation must fail, rethrow an appropriate exception or mark the transaction rollback-only deliberately.

#### Deep dive

An inner transactional operation may mark the transaction rollback-only. Then an outer method that catches the exception can still later get `UnexpectedRollbackException` when commit is attempted.

#### Production angle

Swallowed exceptions create data correctness bugs: partial writes, false success responses and missing retries.

#### Traps / caveats

- Logging is not handling.
- Returning a fallback inside a transaction may still commit previous writes.
- Understand propagation when inner methods fail.

#### Optional Anki

Q: What does Spring see if a transactional method catches an exception and returns normally?
A: Usually a successful method exit.

</details>

<a id="exc-spring-008"></a>

<details>
<summary><strong>EXC-SPRING-008. What is Spring persistence exception translation, and why is `DataAccessException` unchecked?</strong></summary>

#### Short answer

Spring translates low-level persistence exceptions into a consistent unchecked `DataAccessException` hierarchy.

#### Interview answer

Different persistence technologies throw different exceptions: JDBC has `SQLException`, JPA has `PersistenceException`, vendors have their own types. Spring's exception translation maps these to a common `DataAccessException` hierarchy so service code is not tied to one provider.

`DataAccessException` is unchecked because most callers cannot locally recover from every database failure, and Spring expects centralized transaction and boundary handling.

#### Deep dive

Translation can classify failures such as duplicate key, deadlock, optimistic locking, connection failure or bad SQL grammar. The original exception is preserved as the cause.

#### Production angle

Stable exception categories help retry deadlocks, map duplicate keys to 409, and alert on connectivity failures without leaking vendor details.

#### Traps / caveats

- Do not catch only `SQLException` in Spring repository code and miss translated exceptions.
- Not every `DataAccessException` is retryable.
- Inspect the cause for vendor-specific diagnostics when debugging.

#### Optional Anki

Q: Why does Spring use `DataAccessException`?
A: To provide a consistent unchecked persistence exception hierarchy.

</details>

<a id="exc-spring-009"></a>

<details>
<summary><strong>EXC-SPRING-009. How should retryable and non-retryable backend exceptions be distinguished?</strong></summary>

#### Short answer

Distinguish by failure semantics: transient infrastructure failures may be retryable; validation errors, authorization failures and many business conflicts are not.

#### Interview answer

Retryable failures include timeouts, temporary network errors, rate limits with backoff, deadlocks and serialization conflicts when the operation is idempotent or safely repeatable. Non-retryable failures include invalid input, unauthorized access, malformed requests and permanent business rule violations.

The exception or error classification should make that decision explicit.

#### Deep dive

Retry policy also depends on operation safety. A timeout after sending a request is ambiguous: the downstream may have completed the operation. Idempotency keys or deduplication may be required before retrying.

#### Production angle

Bad retries amplify outages and create duplicate writes. Good retry classification reduces transient failure impact without hiding real bugs.

#### Traps / caveats

- Do not retry all exceptions.
- Do not retry non-idempotent writes without safeguards.
- Add backoff, jitter and retry budgets.

#### Optional Anki

Q: Are validation exceptions retryable?
A: Usually no.

</details>

<a id="exc-spring-010"></a>

<details>
<summary><strong>EXC-SPRING-010. How do idempotency, timeouts and exception handling interact in REST APIs?</strong></summary>

#### Short answer

Timeouts make outcomes uncertain, and idempotency lets clients or services safely retry without creating duplicate effects.

#### Interview answer

If a client times out, it may not know whether the server processed the request. Retrying a non-idempotent operation like payment or order creation can duplicate work. Exception handling should classify timeout as ambiguous and use idempotency keys, natural unique constraints or request deduplication to make retries safe.

HTTP method semantics help, but application-level idempotency is often needed for POST commands.

#### Deep dive

The server should store idempotency keys with operation status and result when appropriate. A repeated request can return the original result instead of executing again.

#### Production angle

Most duplicate payment/order incidents are not caused by exceptions alone; they are caused by exceptions plus unsafe retry behavior.

#### Traps / caveats

- A timeout does not prove failure.
- Retrying after a 5xx can still duplicate side effects.
- Idempotency needs storage and expiration policy.

#### Optional Anki

Q: Why is timeout handling hard?
A: The caller may not know whether the operation completed.

</details>

<a id="exc-spring-011"></a>

<details>
<summary><strong>EXC-SPRING-011. How should HTTP client exceptions from `RestClient`, `WebClient`, Feign or `RestTemplate` be handled?</strong></summary>

#### Short answer

Translate client-library exceptions into stable gateway/application exceptions that classify timeout, connection failure, 4xx, 5xx and bad response cases.

#### Interview answer

HTTP client libraries expose different exception types. Application code should not spread those across services. A gateway adapter should catch library-specific failures and translate them to meaningful categories: upstream timeout, upstream unavailable, upstream rejected request, rate limited, invalid response, or non-retryable client error.

Preserve the cause and include safe context such as provider name and operation.

#### Deep dive

For `WebClient`, error handling may happen in reactive pipelines; for blocking clients it may happen around the call. The policy should still be the same: classify, preserve, map and observe.

#### Production angle

Consistent translation makes retries, circuit breakers and dashboards work across different HTTP client implementations.

#### Traps / caveats

- Do not treat all 4xx and 5xx the same.
- Do not log full response bodies if they may contain sensitive data.
- Configure timeouts; do not rely on defaults blindly.

#### Optional Anki

Q: Where should HTTP client library exceptions usually be translated?
A: In the gateway/client adapter boundary.

</details>

<a id="exc-spring-012"></a>

<details>
<summary><strong>EXC-SPRING-012. How should exceptions in scheduled jobs, `@Async` methods and message listeners be handled?</strong></summary>

#### Short answer

They need explicit boundary handling because failures may not have an HTTP request to report to and can otherwise disappear, repeat endlessly or stop processing.

#### Interview answer

Scheduled jobs should catch at the job boundary, log with job context, update metrics and decide whether to retry, skip or alert. `@Async` methods need care because `void` async failures go to an async exception handler, while `Future` or `CompletableFuture` failures must be observed by the caller. Message listeners need retry, backoff, offset/ack strategy and DLQ policy.

The handler should distinguish poison messages, transient dependency failures and bugs.

#### Deep dive

For message systems, committing an offset before successful processing can lose messages; committing after processing can create duplicates. Exception handling must match delivery guarantees.

#### Production angle

Unobserved async failures cause silent data loss. Unbounded retries cause retry storms and consumer lag.

#### Traps / caveats

- Do not let scheduled jobs fail silently forever.
- Do not ignore returned futures.
- Do not retry poison messages indefinitely without DLQ or quarantine.

#### Optional Anki

Q: Why are async exceptions easy to miss?
A: They may be stored in a future or handled on another thread instead of thrown to the caller.

</details>

<a id="exc-spring-013"></a>

<details>
<summary><strong>EXC-SPRING-013. What observability should exist around backend exceptions?</strong></summary>

#### Short answer

Use structured logs, metrics, traces and alerts that classify failures by stable category, endpoint, dependency and impact.

#### Interview answer

Good exception observability includes error rate metrics, exception category, endpoint or job name, dependency name, retry outcome, trace IDs and enough structured logs to debug examples. Distributed tracing should show failing spans and downstream errors.

Alerts should focus on user impact and SLOs, not every individual stack trace.

#### Deep dive

Separate expected client/domain failures from server defects and dependency outages. A spike in validation errors means something different from a spike in database connection failures.

#### Production angle

Observability turns exception handling from "log and hope" into measurable reliability behavior.

#### Traps / caveats

- Do not use high-cardinality labels like user ID or exception message.
- Do not page on expected 4xx validation traffic.
- Make sure sampled logs still have complete metrics.

#### Optional Anki

Q: What should exception metrics be labeled with?
A: Stable categories such as endpoint template, dependency and exception class/category.

</details>
