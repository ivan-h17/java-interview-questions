# 06.01. Exception hierarchy, contracts and checked vs unchecked

---

<a id="exc-core-001"></a>

<details>
<summary><strong>EXC-CORE-001. Explain the Java exception hierarchy and the practical difference between `Throwable`, `Exception`, `RuntimeException` and `Error`.</strong></summary>

#### Short answer

`Throwable` is the root type for everything that can be thrown. `Exception` is for conditions application code may handle, `RuntimeException` is an unchecked exception usually caused by bugs or invalid state, and `Error` represents serious JVM or environment problems.

#### Interview answer

The Java hierarchy starts with `Throwable`. Its two main branches are `Exception` and `Error`. Most application failures are modeled as `Exception`. Checked exceptions are `Exception` subclasses except `RuntimeException`; they must be caught or declared. `RuntimeException` and `Error` are unchecked.

In backend code, the practical question is not only the hierarchy but the contract: is this a recoverable business or infrastructure condition, a caller bug, or a system failure that should normally stop the current operation?

#### Deep dive

`RuntimeException` includes common failures such as `NullPointerException`, `IllegalArgumentException` and `IllegalStateException`. They usually mean the code violated an API contract or reached an invalid state.

`Error` includes failures such as `OutOfMemoryError`, `StackOverflowError` and linkage errors. Catching them broadly can leave the process in an unreliable state.

#### Production angle

The hierarchy affects rollback rules, API contracts, retry policies and global exception handlers. For example, Spring transactions roll back by default on unchecked exceptions and `Error`, but not on checked exceptions.

#### Traps / caveats

- Do not treat all unchecked exceptions as unrecoverable; some represent expected conflicts at a boundary.
- Do not catch `Error` casually.
- The exception class should communicate meaning, not just satisfy the compiler.

#### Optional Anki

Q: What is the root class of Java's throwable hierarchy?
A: `Throwable`.

</details>

<a id="exc-core-002"></a>

<details>
<summary><strong>EXC-CORE-002. What makes an exception checked or unchecked, and which exceptions must be handled or declared?</strong></summary>

#### Short answer

A checked exception is a `Throwable` that is not a `RuntimeException` or `Error`. Checked exceptions must be caught or declared with `throws`.

#### Interview answer

Java checks exceptions at compile time by type. If a method can throw a checked exception, the caller must handle it in a `catch` block or declare it in its own `throws` clause. `RuntimeException` and `Error` are unchecked, so the compiler does not force callers to handle them.

The intent is to make recoverable or expected failure modes visible in the API. In practice, many backend frameworks translate low-level checked exceptions into unchecked exceptions to avoid leaking implementation details through every layer.

#### Deep dive

Examples of checked exceptions include `IOException` and `SQLException`. Examples of unchecked exceptions include `IllegalArgumentException`, `IllegalStateException`, `NullPointerException` and `DataAccessException`.

Checked-ness is not about severity. An unchecked exception can be recoverable at a boundary, and a checked exception can still be fatal for the current request.

#### Production angle

Checked exceptions can be useful in libraries where callers truly have different recovery options. In service code, too many checked exceptions often produce catch-and-wrap boilerplate or broad `throws Exception`.

#### Traps / caveats

- `Error` is unchecked, but that does not mean application code should handle it normally.
- Do not decide checked vs unchecked only by "recoverable" in the abstract; consider the caller's actual ability to recover.
- Framework boundaries often change exception types.

#### Optional Anki

Q: Which Java exceptions are unchecked?
A: `RuntimeException`, `Error` and their subclasses.

</details>

<a id="exc-core-003"></a>

<details>
<summary><strong>EXC-CORE-003. How are exceptions propagated through the call stack?</strong></summary>

#### Short answer

When an exception is thrown, Java searches the current call stack for the nearest matching `catch` block. If none is found, the exception continues upward and can terminate the thread.

#### Interview answer

Throwing an exception exits the current normal control flow. Java unwinds stack frames until it finds a compatible `catch` block. During unwinding, `finally` blocks and try-with-resources cleanup run for frames being exited.

If no handler is found, the exception becomes uncaught. In a plain thread, it is reported to the thread's uncaught exception handler. In frameworks, executors or containers, the framework often catches it and maps it to a task failure, HTTP response, rollback or log entry.

#### Deep dive

The selected `catch` block is based on runtime exception type and source-order reachability. A catch for `IOException` can catch `FileNotFoundException`; a catch for `Exception` catches many unrelated failures and can hide bugs.

#### Production angle

Understanding propagation is essential for transaction rollback, resource cleanup and global error handling. Catching too low can prevent the right boundary from seeing the failure.

#### Traps / caveats

- Catching and returning success changes propagation and may break rollback or retries.
- Async code often stores exceptions instead of throwing them on the caller thread.
- `finally` can mask the original exception if it throws.

#### Optional Anki

Q: What does Java do when no matching `catch` exists in the current method?
A: It unwinds the stack and searches callers.

</details>

<a id="exc-core-004"></a>

<details>
<summary><strong>EXC-CORE-004. Why are exceptions part of a method or API contract?</strong></summary>

#### Short answer

Exceptions describe how an API reports failure, invalid input and boundary conditions. Callers depend on that behavior just like they depend on return types.

#### Interview answer

A method contract is not only "what it returns when everything works". It also includes what inputs are valid, what happens when dependencies fail, which exceptions can be expected, and whether failures are retryable or should be shown to users.

For public APIs, exceptions should be meaningful and stable enough for callers to handle. Throwing random low-level exceptions from deep inside the implementation leaks details and couples callers to internals.

#### Deep dive

Checked exceptions make some failure contracts visible in the method signature. Unchecked exceptions need documentation, tests or framework conventions. For example, a repository might translate vendor SQL errors into a stable `DuplicateEmailException` or Spring `DataIntegrityViolationException`.

#### Production angle

Stable exception contracts make retries, HTTP mapping, metrics, alerts and client SDK behavior predictable. Unstable contracts cause clients to catch too broadly or fail on implementation changes.

#### Traps / caveats

- Do not expose vendor-specific exceptions from domain services unless that is intentional.
- Avoid `throws Exception`; it gives callers no useful contract.
- A message is not a contract; the type or structured code should carry meaning.

#### Optional Anki

Q: Why are exceptions part of an API contract?
A: They define how failure is reported and what callers may handle.

</details>

<a id="exc-core-005"></a>

<details>
<summary><strong>EXC-CORE-005. When is catching `Throwable` or `Error` acceptable, and why is it usually risky?</strong></summary>

#### Short answer

It is acceptable only at very high-level boundaries for logging, cleanup or controlled shutdown. It is risky because `Error` may mean the JVM or process is already unstable.

#### Interview answer

Application code should usually catch specific exceptions, not `Throwable`. Catching `Throwable` also catches serious `Error`s such as `OutOfMemoryError`, `StackOverflowError` and linkage failures. Continuing normal business logic after those can corrupt state or hide a fatal problem.

There are narrow cases: a container, executor, test runner or top-level service boundary may catch `Throwable` to log, release resources, mark a task failed, or trigger process shutdown.

#### Deep dive

Even when catching `Throwable`, the handler should be simple and defensive. It should avoid allocating much memory, making complex calls or pretending the operation succeeded.

#### Production angle

Top-level handlers are useful to prevent silent thread death and to capture diagnostics. They are not a substitute for health checks, restart policy and crash-only recovery.

#### Traps / caveats

- `catch (Throwable)` can swallow interruption-related errors or framework lifecycle failures.
- Catching `Error` in a loop can create a noisy, unhealthy process.
- Logging an `OutOfMemoryError` may itself fail if logging allocates memory.

#### Optional Anki

Q: Why is `catch (Throwable)` dangerous?
A: It catches serious `Error`s that application code usually cannot safely recover from.

</details>

<a id="exc-core-006"></a>

<details>
<summary><strong>EXC-CORE-006. How do exception type, message, cause and stack trace serve different purposes?</strong></summary>

#### Short answer

The type tells code how to classify the failure, the message explains this occurrence, the cause preserves the underlying failure, and the stack trace shows where it happened.

#### Interview answer

A good exception gives both machines and humans useful information. The class or error code should be stable enough for code to map or handle. The message should help developers understand the specific case. The cause should preserve the lower-level failure when wrapping. The stack trace should point to the path that produced the exception.

These parts are complementary. A clear message cannot replace the cause, and a cause cannot replace a meaningful domain type.

#### Deep dive

For example, `new OrderCreationException("payment authorization failed for orderId=...", cause)` gives a service-level classification while preserving the HTTP client or payment SDK failure below it.

#### Production angle

Good exception structure improves logs, alerts, metrics, HTTP error mapping and incident response. Poor structure produces noisy logs and slow root-cause analysis.

#### Traps / caveats

- Do not include secrets, tokens or full payloads in messages.
- Do not parse exception messages for business logic.
- Do not wrap without preserving the cause.

#### Optional Anki

Q: What part of an exception should code usually branch on?
A: The exception type or structured error code, not the free-text message.

</details>

<a id="exc-core-007"></a>

<details>
<summary><strong>EXC-CORE-007. How do common runtime exceptions like `NullPointerException`, `IllegalArgumentException`, `IllegalStateException`, `UnsupportedOperationException` and `ClassCastException` signal different bugs?</strong></summary>

#### Short answer

They point to different contract violations: missing object, bad argument, invalid object state, unsupported operation or wrong runtime type.

#### Interview answer

`NullPointerException` usually means code used absence as if it were an object. `IllegalArgumentException` means the caller passed an invalid value. `IllegalStateException` means the receiver is not in a valid state for the operation. `UnsupportedOperationException` means the method is intentionally not supported. `ClassCastException` means code assumed the wrong runtime type.

In interviews, the important point is to choose the exception that tells the caller what they did wrong or what state prevented the operation.

#### Deep dive

These exceptions are unchecked because they usually represent programming or contract errors. They can still appear at boundaries from invalid input, deserialization, raw generics, proxy types or incorrect feature assumptions.

#### Production angle

Frequent runtime exceptions should be treated as quality signals. A spike in `ClassCastException` after deployment may indicate a DTO/schema mismatch; a spike in `IllegalStateException` may indicate a broken state transition.

#### Traps / caveats

- Do not use `NullPointerException` intentionally for validation; fail fast with a clearer message or `Objects.requireNonNull`.
- `UnsupportedOperationException` can indicate a bad abstraction if clients reasonably expect support.
- `ClassCastException` is often caused earlier by raw types or untyped payloads.

#### Optional Anki

Q: When should `IllegalStateException` be used?
A: When the object or system state does not allow the requested operation.

</details>

<a id="exc-check-001"></a>

<details>
<summary><strong>EXC-CHECK-001. When should you use checked exceptions, and when should you use unchecked exceptions?</strong></summary>

#### Short answer

Use checked exceptions when callers are expected and able to handle a declared failure. Use unchecked exceptions for programming errors, invalid state, and failures best handled at a boundary.

#### Interview answer

Checked exceptions make sense when the API is a library-style contract and different callers may handle the failure differently. For example, an API that reads from an external resource may declare `IOException`.

Unchecked exceptions make sense when recovery is not local, when the failure indicates a bug, or when forcing every intermediate layer to declare the exception would leak implementation details. Backend services often translate low-level checked exceptions into unchecked application exceptions at boundaries.

#### Deep dive

The decision should consider the caller, not the exception in isolation. If the immediate caller cannot do anything useful except wrap or rethrow, a checked exception may add noise.

#### Production angle

Good exception choice keeps service code readable and makes boundary handling consistent. Bad choice leads to broad `catch`, swallowed failures or APIs that expose database, HTTP client or filesystem details everywhere.

#### Traps / caveats

- Checked does not automatically mean recoverable.
- Unchecked does not automatically mean fatal.
- Do not convert everything to unchecked without a clear boundary policy.

#### Optional Anki

Q: What is the main question when choosing checked vs unchecked?
A: Can the caller reasonably handle this failure as part of the API contract?

</details>

<a id="exc-check-002"></a>

<details>
<summary><strong>EXC-CHECK-002. Why are checked exceptions controversial in backend Java applications?</strong></summary>

#### Short answer

They make failures explicit, but they can also create boilerplate, leak low-level details and interact poorly with lambdas and frameworks.

#### Interview answer

Checked exceptions were designed to force callers to acknowledge expected failures. That is useful for some APIs. The controversy is that backend applications often have many layers where intermediate code cannot recover. The result can be `throws Exception`, repetitive wrapping, or catch blocks that only log and continue incorrectly.

Modern frameworks often prefer unchecked exception hierarchies and centralized boundary handling: translate low-level failures once, then map them to rollback, retries, HTTP errors or messages.

#### Deep dive

Checked exceptions also do not fit Java functional interfaces cleanly. A lambda passed to `Function<T, R>` cannot throw arbitrary checked exceptions without wrapping or custom interfaces.

#### Production angle

A codebase should have a consistent policy. Otherwise one layer exposes `SQLException`, another wraps in `RuntimeException`, and a controller catches `Exception` to return a generic 500.

#### Traps / caveats

- The problem is not checked exceptions themselves; it is poor boundary design.
- Avoid broad conversion that loses context.
- Do not use checked exceptions for ordinary validation lists in bulk workflows.

#### Optional Anki

Q: What is a common backend problem with checked exceptions?
A: Intermediate layers often cannot recover and only add boilerplate or leaking abstractions.

</details>

<a id="exc-check-003"></a>

<details>
<summary><strong>EXC-CHECK-003. Why should public APIs usually avoid `throws Exception` and generic `Exception`?</strong></summary>

#### Short answer

Generic exceptions hide the real failure contract and force callers to catch too broadly.

#### Interview answer

`throws Exception` tells the caller almost nothing. It does not distinguish validation failure, missing resource, timeout, duplicate data, programming error or infrastructure outage. Callers either catch everything, which can hide bugs, or propagate everything, which spreads an unclear contract.

Public APIs should expose meaningful exception types, structured error codes or result types that match the domain.

#### Deep dive

Throwing `new Exception(...)` is also weak because code cannot handle it specifically. If wrapping is needed, use a domain-specific type and preserve the cause.

#### Production angle

Generic failures make error mapping, retries and alerting imprecise. A global handler cannot reliably decide whether to return 400, 409, 503 or 500 from `Exception` alone.

#### Traps / caveats

- A top-level framework method may catch `Exception`, but business APIs should not use it as their contract.
- Do not replace `Exception` with dozens of tiny classes without need.
- Prefer stable categories over message parsing.

#### Optional Anki

Q: Why is `throws Exception` a poor public API contract?
A: It hides failure meaning and forces broad handling.

</details>

<a id="exc-check-004"></a>

<details>
<summary><strong>🧠 EXC-CHECK-004. What is "sneaky throws", and why should it be used carefully?</strong></summary>

#### Short answer

"Sneaky throws" is a generics trick or library feature that throws a checked exception without declaring it. It bypasses compiler checking and can surprise callers.

#### Interview answer

Java bytecode does not enforce checked exceptions the same way the compiler does. A "sneaky throws" helper uses type erasure to throw a checked exception as if it were unchecked. Libraries such as Lombok can generate this pattern.

It can reduce boilerplate in narrow cases, but it weakens the method contract. Callers may not know a checked exception can escape, and normal `catch` expectations become unclear.

#### Deep dive

Sneaky throws does not change the actual runtime object. If a thrown object is an `IOException`, it is still an `IOException`; the compiler was just bypassed at the throw site.

#### Production angle

Use it sparingly in infrastructure adapters where the boundary already has a clear unchecked error policy. Avoid it in public APIs and business logic.

#### Traps / caveats

- It can make code harder to reason about and test.
- It may break caller expectations around declared exceptions.
- It should not be used to avoid thinking about failure contracts.

#### Optional Anki

Q: What does sneaky throws bypass?
A: Compile-time checked-exception enforcement.

</details>

<a id="exc-core-008"></a>

<details>
<summary><strong>🧠 EXC-CORE-008. How are exceptions represented in bytecode and the JVM execution model?</strong></summary>

#### Short answer

Bytecode methods have exception handler tables that describe protected instruction ranges and handler targets. When an exception is thrown, the JVM searches these handlers and unwinds stack frames.

#### Interview answer

At the bytecode level, `try-catch` is not a special block instruction around every operation. A method contains normal instructions plus an exception table. Each table entry says: for this range of bytecode positions, if a throwable of this type appears, jump to this handler.

When an exception is thrown, the JVM searches for a matching handler in the current frame. If none matches, it unwinds to the caller. `finally` is compiled into cleanup paths that run during normal and exceptional exits.

#### Deep dive

The compiler enforces checked exceptions, but the JVM mostly deals with thrown objects and handler tables. This distinction explains techniques such as sneaky throws and why unchecked vs checked is primarily a Java language rule.

#### Production angle

You rarely need bytecode details day to day, but they help explain why entering a `try` block is cheap compared with actually throwing and filling a stack trace.

#### Traps / caveats

- Do not rely on bytecode tricks in ordinary application code.
- Decompilers may make generated `finally` code look confusing.
- Exact implementation details can vary by compiler and JVM.

#### Optional Anki

Q: What structure tells the JVM where catch handlers are?
A: The method's exception table.

</details>
