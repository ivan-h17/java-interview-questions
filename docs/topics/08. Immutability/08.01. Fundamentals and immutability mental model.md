# 08.01. Fundamentals and immutability mental model

---

<a id="imm-fund-001"></a>

<details>
<summary><strong>IMM-FUND-001. What is an immutable object?</strong></summary>

#### Short answer

An immutable object is an object whose observable state cannot change after construction.

#### Interview answer

In Java, immutability means callers cannot observe the object moving from one state to another after it has been created. Instead of changing itself, an immutable object returns a new object when a different value is needed.

Typical examples are `String`, `BigInteger`, `LocalDate`, `Instant` and well-designed value objects such as `Money` or `EmailAddress`.

#### Deep dive

Immutability is about the whole observable state, not only field reassignment. A `final List<Item>` field is still a mutable list unless the list structure and the elements are protected.

An immutable class usually has private final fields, no setters, constructor validation, defensive copies for mutable inputs and safe exposure of internal data.

#### Production angle

Immutable objects are useful for DTOs, commands, events, cache keys, configuration snapshots and domain value objects because they can be passed around without worrying that another layer silently changes them.

#### Traps / caveats

- `final` references do not make referenced objects immutable.
- No setters is not enough if internal mutable state leaks.
- Immutability can be shallow or deep.

#### Optional Anki

Q: What is an immutable object?
A: An object whose observable state cannot change after construction.

</details>

<details>
<summary><strong>IMM-FUND-002. What is the difference between immutable, read-only and unmodifiable?</strong></summary>

#### Short answer

Immutable means the state cannot change. Read-only usually means the current API does not expose mutation. Unmodifiable means mutation through that wrapper or collection reference is rejected.

#### Interview answer

These terms are related but not identical. An immutable object owns state that cannot change after construction. A read-only interface may expose only getters, but the underlying object can still change elsewhere. An unmodifiable collection rejects calls such as `add` or `remove`, but it may be a view over a mutable backing collection.

#### Deep dive

`Collections.unmodifiableList(list)` returns a read-only view of `list`. If someone mutates `list`, the view changes. `List.copyOf(list)` creates an unmodifiable shallow snapshot, so structural changes to the source list do not affect the copy.

Both approaches are shallow: mutable elements can still be changed.

#### Production angle

This matters at API boundaries. Returning an unmodifiable view of internal state is safe only if the owner controls all mutation and live-view semantics are intentional.

#### Traps / caveats

- Read-only does not imply immutable.
- Unmodifiable does not imply detached from backing state.
- Collection immutability does not imply element immutability.

#### Optional Anki

Q: Is `Collections.unmodifiableList()` an immutable copy?
A: No. It is a read-only view of an existing list.

</details>

<a id="imm-fund-003"></a>

<details>
<summary><strong>IMM-FUND-003. What is the difference between shallow, deep and transitive immutability?</strong></summary>

#### Short answer

Shallow immutability protects direct fields from reassignment. Deep or transitive immutability protects the whole reachable object graph from mutation.

#### Interview answer

A shallowly immutable object has stable direct references after construction, but referenced objects may still be mutable. A deeply immutable object cannot be changed through any object reachable from it. Transitive immutability is the stronger property that every reachable part is also immutable.

Records are a common shallow example: component fields are final, but `record User(List<String> roles)` is not deeply immutable unless `roles` is copied and its elements are safe.

#### Deep dive

Deep immutability is hard in Java because the language has no universal immutable type system. You usually enforce it by choosing immutable component types, copying mutable inputs, avoiding mutable static state and not exposing internals.

#### Production angle

Shallow immutability may be enough for DTOs with `String`, numbers and `java.time` values. Aggregates containing collections, arrays or entity references need a stronger policy.

#### Traps / caveats

- A final reference is only shallow protection.
- Deep copying large graphs can be expensive.
- Some mutable objects are hidden behind interfaces.

#### Optional Anki

Q: Are Java records deeply immutable by default?
A: No. They are shallowly immutable by default.

</details>

<a id="imm-fund-004"></a>

<details>
<summary><strong>IMM-FUND-004. What benefits and trade-offs do immutable objects provide?</strong></summary>

#### Short answer

They improve reasoning, sharing, thread-safety and cache-key correctness, but can increase allocation, copying cost and update complexity.

#### Interview answer

Immutable objects are easier to reason about because their state does not change behind your back. They are naturally safer to share between threads, good for value objects and cache keys, and they reduce defensive coordination around ownership.

The trade-off is that updates require new objects or copied structures. For large object graphs or hot write paths, this can increase memory pressure and make code awkward unless you use builders, structural sharing or a mutable internal model.

#### Deep dive

Immutability often moves complexity from synchronization to construction. You must validate up front, copy inputs safely and design update operations carefully.

#### Production angle

It works well for request models, events, configuration snapshots and read-mostly state. It is less attractive for ORM entities, large mutable workflows or tight loops where mutation is local and controlled.

#### Traps / caveats

- Do not assume immutable is always faster.
- Avoid copying huge graphs blindly.
- Immutable data does not make side-effecting services thread-safe.

#### Optional Anki

Q: What is the main runtime trade-off of immutable updates?
A: More allocation or copying unless sharing is used.

</details>

<a id="imm-fund-005"></a>

<details>
<summary><strong>IMM-FUND-005. When is a mutable design better than an immutable one?</strong></summary>

#### Short answer

Mutable design is better when controlled state transitions, ORM lifecycle, large in-place updates or performance-sensitive local mutation matter more than sharing immutable values.

#### Interview answer

Mutability is not automatically bad. A JPA entity, an aggregate with a lifecycle, a builder, a parser buffer or a batch-processing accumulator may be clearer as mutable state with a controlled owner.

The key is scope. Local mutation inside one method or one aggregate boundary is often fine. Shared uncontrolled mutation across threads or layers is where bugs appear.

#### Deep dive

Mutable entities can express business transitions like `confirm()`, `cancel()` or `changeAddress()`. Those transitions enforce invariants better than replacing the whole entity with a copied object after every small change.

#### Production angle

Use immutability at boundaries and for values. Use controlled mutability for persistence models, long-running workflows and performance-sensitive state machines.

#### Traps / caveats

- Avoid public setters that bypass invariants.
- Do not share mutable objects casually between threads.
- Do not force immutable copies where a transaction-owned entity is the real model.

#### Optional Anki

Q: Where is mutability often appropriate?
A: Inside controlled ownership boundaries such as builders, JPA entities and local accumulators.

</details>

<a id="imm-fund-006"></a>

<details>
<summary><strong>IMM-FUND-006. Why are immutable value objects easier to reason about than mutable entities?</strong></summary>

#### Short answer

Immutable value objects are defined by their value and do not have lifecycle state changes. Mutable entities have identity and can change over time.

#### Interview answer

A value object such as `Money`, `EmailAddress` or `DateRange` is usually equal to another instance with the same value. If it is immutable, callers can pass it around safely and use value-based equality without worrying that the value changes later.

An entity has identity and lifecycle. Two `Order` objects may represent the same order even if their fields differ over time. That makes equality, mutation and persistence behavior more subtle.

#### Deep dive

Immutability fits value objects because it preserves invariants after construction. Entities often need behavior that changes state, such as status transitions or optimistic locking fields.

#### Production angle

Immutable value objects reduce duplicate validation and accidental corruption in APIs, caches, messages and database projections.

#### Traps / caveats

- Do not model every domain object as a value object.
- Entity equality should not blindly include mutable fields.
- Value objects containing collections still need defensive copying.

#### Optional Anki

Q: Why are value objects usually immutable?
A: Their meaning is their value, so changing that value would effectively create a different value.

</details>

<a id="imm-fund-007"></a>

<details>
<summary><strong>IMM-FUND-007. Can an object be logically immutable but physically mutable?</strong></summary>

#### Short answer

Yes. An object can keep the same logical value while mutating hidden internal caches or derived data.

#### Interview answer

Logical immutability means externally visible state does not change. Physical mutability means implementation details can change internally. For example, an immutable object may lazily cache a computed hash code or parsed representation without changing its logical value.

This is acceptable when the cache does not affect equality, validation or visible behavior except performance.

#### Deep dive

The dangerous part is thread-safety. Lazy caches inside otherwise immutable objects must be safely published or tolerate benign races. If the cached value is derived only from immutable state, computing it more than once may be acceptable.

#### Production angle

Logical immutability is common in expensive value objects such as normalized keys, parsed expressions or large strings. It avoids recomputing while keeping the public contract immutable.

#### Traps / caveats

- Hidden mutable caches can create data races.
- Cached values must not depend on mutable external state.
- Do not expose cached mutable objects directly.

#### Optional Anki

Q: What is logical immutability?
A: Publicly observable state is immutable even if private implementation caches change.

</details>

<details>
<summary><strong>IMM-FUND-008. What is representation exposure, and how can it break immutability?</strong></summary>

#### Short answer

Representation exposure happens when internal mutable state is exposed so callers can mutate it outside the owning object's control.

#### Interview answer

If an immutable-looking class stores a caller-provided `List` directly or returns its internal array from a getter, outside code can change the object's state. The class may have no setters, but its representation is still exposed.

The usual fixes are defensive copies, immutable component types, unmodifiable snapshots or behavior methods that avoid exposing raw storage.

#### Deep dive

Representation exposure can happen on input and output. Input exposure happens when a constructor stores a mutable argument. Output exposure happens when a getter returns internal mutable state.

It also applies to `Date`, arrays, buffers, collections, builders and mutable entity references.

#### Production angle

These bugs often appear far from the owning class: a controller, mapper or test helper mutates a returned collection and later the cache, domain object or response becomes inconsistent.

#### Traps / caveats

- Private fields do not help if getters return mutable internals.
- Wrapping without copying can still expose backing changes.
- Mutable elements can expose state even when the collection structure is protected.

#### Optional Anki

Q: What prevents representation exposure for mutable constructor arguments?
A: Defensive copying on input.

</details>
