# 08.09. Senior scenario-based immutability questions

---

<a id="imm-scenario-001"></a>

<details>
<summary><strong>IMM-SCENARIO-001. Design an immutable `Money` class for a payment service.</strong></summary>

#### Short answer

Use final validated amount and currency fields, explicit rounding rules and operations that return new `Money` objects.

#### Interview answer

I would store `BigDecimal amount` and `Currency currency`, validate both in a factory or constructor, and normalize scale according to the business rule. The class would be final, expose no setters and return new instances for `add`, `subtract` or `multiply`.

Operations must reject currency mismatches unless an explicit exchange conversion is provided.

#### Deep dive

Equality should be deliberate about `BigDecimal` scale. Either normalize amount scale or define equality so `1.0` and `1.00` behave according to the domain expectation.

#### Production angle

Centralizing money rules prevents scattered rounding, currency mixing and invalid negative or over-precision amounts.

#### Traps / caveats

- Do not use `double` for money.
- Do not hide rounding rules.
- Do not let JSON/deserialization bypass validation.

#### Optional Anki

Q: What should `Money.add` validate?
A: Matching currency and valid resulting amount rules.

</details>

<a id="imm-scenario-002"></a>

<details>
<summary><strong>IMM-SCENARIO-002. Design an immutable `OrderSnapshot` that contains order items.</strong></summary>

#### Short answer

Create immutable snapshot types for the order and each item, copy the item list, and avoid references to live entities.

#### Interview answer

`OrderSnapshot` should contain stable values such as order ID, status, totals, timestamps and a `List<OrderItemSnapshot>`. The constructor should validate fields and store `List.copyOf(items)`. `OrderItemSnapshot` should also be immutable and contain copied values, not references to mutable `OrderItem` entities.

#### Deep dive

If item fields include mutable types such as options maps, those must be copied too. The snapshot should represent the state at one point in time.

#### Production angle

This is useful for audit logs, invoices, outbox events and customer-visible order history.

#### Traps / caveats

- Do not store live entity references.
- Copying the list is not enough if items are mutable.
- Include enough data so history does not depend on later joins to changed tables.

#### Optional Anki

Q: Why use `OrderItemSnapshot` instead of `OrderItem` in a snapshot?
A: To avoid later entity mutation changing historical state.

</details>

<a id="imm-scenario-003"></a>

<details>
<summary><strong>IMM-SCENARIO-003. How would you refactor a mutable DTO used across multiple threads?</strong></summary>

#### Short answer

Identify ownership and mutation points, then replace shared mutable state with immutable snapshots or thread-confined builders.

#### Interview answer

First I would find who writes the DTO and who reads it. If it is built once and then shared, I would introduce an immutable DTO with constructor validation and copied collections. If it is assembled gradually, I would use a mutable builder confined to one thread, then publish the immutable result.

If updates are required, I would publish new immutable versions through a safe mechanism.

#### Deep dive

The migration should be incremental: add an immutable type, map from the old DTO, update shared paths, then remove or confine the mutable DTO.

#### Production angle

This reduces races in async pipelines, executor tasks and message processing.

#### Traps / caveats

- Do not just add `volatile` to fields of a mutable DTO.
- Do not share builders.
- Validate collection and nested object mutability.

#### Optional Anki

Q: What is a safe pattern for gradually building immutable data?
A: Use a thread-confined builder and publish an immutable result.

</details>

<a id="imm-scenario-004"></a>

<details>
<summary><strong>IMM-SCENARIO-004. How would you design a cache key for a complex search request?</strong></summary>

#### Short answer

Create a small immutable normalized key containing exactly the request fields that affect the result.

#### Interview answer

I would define a record or final class with stable fields: query text after normalization, tenant, user-visible filters, pagination, sort, locale and any permission context that changes results. Collections should be copied and normalized, for example sorting unordered filters.

The key should have stable `equals()` and `hashCode()` and avoid storing mutable request DTOs directly.

#### Deep dive

The key should not contain irrelevant fields such as tracing IDs if they do not affect the result. It also should not omit fields such as tenant or authorization scope.

#### Production angle

Good cache keys prevent data leaks between users and avoid low hit rates from accidental key variation.

#### Traps / caveats

- Include tenant and authorization context when results depend on them.
- Normalize unordered filters.
- Keep the key reasonably small.

#### Optional Anki

Q: What should a cache key include?
A: All fields that affect the cached result, normalized and immutable.

</details>

<a id="imm-scenario-005"></a>

<details>
<summary><strong>IMM-SCENARIO-005. How would you protect a public API from caller-side mutation of request data?</strong></summary>

#### Short answer

Copy mutable inputs at the boundary, validate them, and convert them into immutable internal command objects.

#### Interview answer

At the controller or adapter boundary, I would deserialize into a DTO, validate it, normalize it and map it to an immutable command. Collection fields should be copied. Mutable nested data should be converted into immutable value objects.

Downstream services should receive the immutable command, not a mutable request object owned by the framework or caller.

#### Deep dive

For external APIs, also document mutability and schema guarantees. For message consumers, treat payloads as immutable facts once accepted.

#### Production angle

This prevents accidental changes between validation, authorization, persistence and event publishing.

#### Traps / caveats

- Do not trust unmodifiable wrappers around caller-owned collections.
- Validate after normalization.
- Be careful with partial update semantics.

#### Optional Anki

Q: Why map request DTOs to immutable commands?
A: To give service logic a stable validated input.

</details>

<a id="imm-scenario-006"></a>

<details>
<summary><strong>IMM-SCENARIO-006. How would you safely reload application configuration using immutable objects?</strong></summary>

#### Short answer

Build and validate a complete new immutable configuration snapshot, then atomically publish it.

#### Interview answer

I would represent runtime configuration as an immutable `ConfigSnapshot`. Reloading reads new raw config, validates it, resolves defaults and builds a complete snapshot. Only after successful validation would I replace the current snapshot using `volatile`, `AtomicReference` or a framework-supported refresh mechanism.

Readers use the snapshot they read for the whole operation.

#### Deep dive

Never mutate nested maps or lists in place during reload. That can expose half-updated configuration to request threads.

#### Production angle

This pattern keeps feature flags, limits and endpoint maps consistent during reload.

#### Traps / caveats

- Failed reload should leave the old snapshot active.
- Long operations may use an older snapshot.
- Secret values need redaction in logs and `toString()`.

#### Optional Anki

Q: What should happen if config validation fails during reload?
A: Keep the previous snapshot active.

</details>

<a id="imm-scenario-007"></a>

<details>
<summary><strong>IMM-SCENARIO-007. How would you design immutable events for a Kafka-based system?</strong></summary>

#### Short answer

Use immutable payloads with stable schema fields, copied collections, event metadata and no live entity references.

#### Interview answer

An event should describe a fact that happened. I would use a record or immutable class with event ID, aggregate ID, timestamp, version, tenant and immutable payload fields. Collections should be copied, nested values should be immutable, and sensitive data should be excluded or redacted.

The event schema should be versioned and backward compatible for consumers.

#### Deep dive

Immutability helps retries because every retry publishes or processes the same fact. It does not solve ordering, idempotency or exactly-once guarantees by itself.

#### Production angle

Immutable events improve auditability, replay safety and debugging in event-driven systems.

#### Traps / caveats

- Do not serialize JPA entities directly.
- Include idempotency/event IDs.
- Keep generated `toString()` from leaking secrets.

#### Optional Anki

Q: What should event payloads avoid referencing?
A: Live mutable entities.

</details>

<a id="imm-scenario-008"></a>

<details>
<summary><strong>IMM-SCENARIO-008. How would you handle a nested collection of mutable objects in an immutable aggregate?</strong></summary>

#### Short answer

Convert each mutable nested object into an immutable value or snapshot, then store an unmodifiable copied collection.

#### Interview answer

I would not store `List<MutableChild>` directly. I would map each child into an immutable `ChildSnapshot` or value object, then store `List.copyOf(mappedChildren)`. If the nested object contains more mutable collections, repeat the same policy recursively where needed.

#### Deep dive

This avoids relying on arbitrary deep-copy behavior. The immutable aggregate defines exactly which data is captured.

#### Production angle

This is common for orders with items, users with addresses, invoices with lines and reports with grouped rows.

#### Traps / caveats

- A shallow collection copy is not enough.
- Do not keep entity references for convenience.
- Large deep snapshots may require pagination or explicit projection design.

#### Optional Anki

Q: What is safer than deep-copying mutable entities into an aggregate?
A: Mapping them to immutable snapshot/value types.

</details>

<a id="imm-scenario-009"></a>

<details>
<summary><strong>IMM-SCENARIO-009. A code review shows `Collections.unmodifiableList(input)` in a constructor. What questions would you ask?</strong></summary>

#### Short answer

Ask who owns `input`, whether it can change later, whether elements are mutable and whether snapshot semantics are required.

#### Interview answer

`Collections.unmodifiableList(input)` in a constructor is suspicious because it wraps the caller's list instead of copying it. I would ask whether the caller can mutate `input` after construction. If yes, the object is not immutable. I would also check whether list elements are mutable and whether nulls are allowed.

The likely fix is `List.copyOf(input)` plus immutable element types or element copies.

#### Deep dive

An unmodifiable wrapper can be fine for a private backing collection controlled by the owner, but constructor input is usually not controlled by the new object.

#### Production angle

This bug causes snapshots, cache values and DTOs to change after validation.

#### Traps / caveats

- Wrapping is not copying.
- Element mutability may still remain after `List.copyOf`.
- Changing behavior to reject nulls may need migration care.

#### Optional Anki

Q: Why is `Collections.unmodifiableList(input)` risky in a constructor?
A: The caller may still mutate the backing list.

</details>

<a id="imm-scenario-010"></a>

<details>
<summary><strong>IMM-SCENARIO-010. How would you use immutable objects to reduce locking in a read-heavy service?</strong></summary>

#### Short answer

Keep read-mostly state as immutable snapshots and publish replacements atomically.

#### Interview answer

If reads dominate, I would store the state in an immutable object graph referenced by a volatile field or `AtomicReference`. Readers take a local reference and use it without locking. Writers build a new snapshot off to the side, validate it and swap the reference.

This avoids locking every read while keeping each read internally consistent.

#### Deep dive

This works when updates can replace the whole state and stale reads are acceptable for a short time. If every update must coordinate with external side effects, locks or transactions may still be needed.

#### Production angle

Examples include feature flags, route maps, compiled validation rules and pricing tables.

#### Traps / caveats

- Snapshot rebuild cost can be high.
- Readers may see older state.
- Avoid mutating shared nested collections during rebuild.

#### Optional Anki

Q: How do readers access immutable snapshot state?
A: Read the current reference and use that stable snapshot without locking.

</details>

<a id="imm-scenario-011"></a>

<details>
<summary><strong>IMM-SCENARIO-011. How would you balance immutability and performance for large response objects?</strong></summary>

#### Short answer

Use immutable boundaries where correctness matters, but avoid unnecessary full-graph copies by projecting, paginating and sharing safe values.

#### Interview answer

I would first identify the ownership boundary. If the response is built from mutable entities, map it to immutable DTOs so callers cannot change internal state. For very large responses, I would avoid copying more than needed: paginate, stream, project only required fields and use immutable element types.

If repeated snapshots are needed, consider caching or structural sharing.

#### Deep dive

The goal is not "copy everything always." It is stable API output with measured allocation cost.

#### Production angle

Large immutable response graphs can create allocation spikes and GC pressure. Profiling should guide optimizations.

#### Traps / caveats

- Do not expose entities to avoid mapping cost.
- Do not return live mutable collections from caches.
- Measure realistic payload sizes.

#### Optional Anki

Q: What is the first alternative to huge immutable response copies?
A: Return less data through projection or pagination.

</details>

<a id="imm-scenario-012"></a>

<details>
<summary><strong>IMM-SCENARIO-012. A framework requires a no-arg constructor and setters. How would you keep your domain model immutable?</strong></summary>

#### Short answer

Separate framework models from domain models, or restrict framework-required mutability behind protected/package-private access.

#### Interview answer

If a framework requires mutable JavaBean-style objects, I would avoid making that object the core domain model. Use a persistence or transport model that satisfies the framework, then map it to immutable domain values, commands or DTOs.

If the same class must be used, keep constructors and setters as restricted as possible, validate after loading and expose a controlled public API.

#### Deep dive

For JPA, controlled mutable entities are often acceptable while value objects and external messages remain immutable. For JSON, constructor binding or records may avoid setters entirely.

#### Production angle

Separating models prevents framework constraints from leaking into domain invariants and public API contracts.

#### Traps / caveats

- Do not expose framework setters as business operations.
- Validate objects created through reflection or deserialization.
- Mapping adds cost but often reduces long-term coupling.

#### Optional Anki

Q: What is the cleanest way to handle framework-required mutability?
A: Use separate framework and domain models, with mapping at the boundary.

</details>
