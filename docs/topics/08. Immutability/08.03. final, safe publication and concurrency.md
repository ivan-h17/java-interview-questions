# 08.03. `final`, safe publication and concurrency

---

<a id="imm-jmm-001"></a>

<details>
<summary><strong>IMM-JMM-001. What does the `final` keyword mean for variables, fields, methods and classes?</strong></summary>

#### Short answer

`final` prevents reassignment of variables and fields, prevents method overriding, and prevents class inheritance.

#### Interview answer

For a local variable or field, `final` means the variable can be assigned only once. For a method, it means subclasses cannot override it. For a class, it means the class cannot be subclassed.

For immutability, final fields are important because they make object state fixed after construction. But final fields only freeze the reference or primitive value, not the object behind a reference.

#### Deep dive

`final` is also relevant to the Java Memory Model. Properly initialized final fields have stronger visibility guarantees after construction than ordinary fields.

#### Production angle

Final fields make value types easier to review and safer to publish. Final classes can protect API contracts, but may conflict with ORM or proxy-based frameworks.

#### Traps / caveats

- `final List<T>` does not make the list immutable.
- Final methods do not make superclass state immutable.
- Final classes can still contain mutable fields.

#### Optional Anki

Q: What does `final` do to a reference field?
A: It prevents reassignment of the reference.

</details>

<a id="imm-jmm-002"></a>

<details>
<summary><strong>IMM-JMM-002. How do final-field semantics help safe publication?</strong></summary>

#### Short answer

Final-field semantics help other threads see final fields correctly initialized after the constructor finishes.

#### Interview answer

The Java Memory Model gives special treatment to final fields. If an object is constructed correctly and `this` does not escape during construction, other threads that obtain the reference are guaranteed to see the initialized values of its final fields.

This is one reason immutable objects with final fields are safer to share than mutable objects with ordinary fields.

#### Deep dive

The guarantee is not a license to publish references carelessly in all designs. It gives initialization safety for final fields and the state they reference as initialized before constructor completion, but later mutation, ordinary mutable fields and broader object-graph changes still need normal concurrency rules.

#### Production angle

Final-field semantics reduce visibility bugs in shared DTOs, configuration values and cache keys, especially when objects cross thread boundaries.

#### Traps / caveats

- Do not let `this` escape from the constructor.
- Mutable objects reachable from final fields can still be mutated.
- Non-final lazy caches need their own thread-safety policy.

#### Optional Anki

Q: What must not happen during construction for final-field guarantees to hold?
A: `this` must not escape.

</details>

<a id="imm-jmm-003"></a>

<details>
<summary><strong>IMM-JMM-003. Can immutable objects be shared between threads without synchronization?</strong></summary>

#### Short answer

Usually yes, if they are correctly constructed and safely reachable, because their state does not change.

#### Interview answer

Immutable objects are naturally thread-safe for reading because there are no writes after construction. Multiple threads can read the same `String`, `LocalDate` or immutable DTO without locking.

The object must still be constructed correctly. If it contains mutable internals or unsafe lazy caches, it may not be truly thread-safe.

#### Deep dive

Immutability eliminates races over the object's state, but it does not eliminate synchronization around replacing references to different immutable objects. If a shared configuration reference is swapped at runtime, the reference update needs `volatile`, `AtomicReference` or locking.

#### Production angle

Immutable messages, request snapshots and cache keys are safe to pass to executors, queues and virtual-thread tasks without defensive locking.

#### Traps / caveats

- Immutable object state is safe; changing which object is referenced is a separate concurrency problem.
- Referenced non-thread-safe resources break the assumption.
- Lazy fields need care.

#### Optional Anki

Q: Why are immutable objects thread-safe for reads?
A: No thread can change their state after construction.

</details>

<a id="imm-jmm-004"></a>

<details>
<summary><strong>IMM-JMM-004. What is safe publication, and when is it still needed with immutable objects?</strong></summary>

#### Short answer

Safe publication means making an object reference visible to other threads in a way that guarantees they see a correctly initialized object.

#### Interview answer

Safe publication can happen through final fields, volatile fields, locks, class initialization, thread-safe collections or concurrency utilities. Immutable objects reduce what needs protection after publication, but the reference still has to become visible correctly.

For a static final constant initialized during class loading, publication is handled by class initialization. For hot-reloaded state, use `volatile` or `AtomicReference`.

#### Deep dive

Final-field semantics provide initialization safety for final fields, but they do not safely publish later assignments to ordinary shared fields. A mutable holder pointing to immutable values still needs visibility rules for the holder.

#### Production angle

Configuration reloads and feature-flag snapshots are classic cases: each snapshot is immutable, but the current snapshot reference must be safely replaced.

#### Traps / caveats

- Immutable state does not make non-volatile reference replacement visible.
- Publishing from constructors is dangerous.
- Collections used for publication must be thread-safe for the access pattern.

#### Optional Anki

Q: Name one way to safely publish a changing immutable snapshot.
A: Store it in a `volatile` field or `AtomicReference`.

</details>

<a id="imm-jmm-005"></a>

<details>
<summary><strong>IMM-JMM-005. When are `volatile` or `AtomicReference` useful with immutable state?</strong></summary>

#### Short answer

They are useful when the immutable object does not change, but the shared reference to the current immutable object changes.

#### Interview answer

If you keep application settings in an immutable `ConfigSnapshot`, each snapshot is thread-safe. But when you reload configuration, threads need to see the new snapshot. A `volatile ConfigSnapshot current` gives visibility for simple replacement. An `AtomicReference<ConfigSnapshot>` also supports atomic compare-and-set updates.

#### Deep dive

This pattern separates data consistency from reference coordination. Readers get a stable snapshot without locking. Writers build a new immutable object and then publish it in one atomic reference update.

#### Production angle

It is useful for feature flags, route tables, rate-limit rules, pricing tables and read-mostly indexes.

#### Traps / caveats

- Updates that depend on the old value may need CAS or a lock.
- A snapshot can be stale immediately after reading it.
- Building the new snapshot must not mutate the old one.

#### Optional Anki

Q: Why combine `AtomicReference` with immutable state?
A: To atomically publish or replace whole consistent snapshots.

</details>

<a id="imm-jmm-006"></a>

<details>
<summary><strong>IMM-JMM-006. How can compare-and-set update immutable state safely?</strong></summary>

#### Short answer

CAS reads the current immutable state, builds a new state, and swaps it only if the current reference has not changed.

#### Interview answer

With `AtomicReference<State>`, an update loop reads the old state, derives a new immutable state, and calls `compareAndSet(old, updated)`. If another thread updated first, CAS fails and the loop retries with the latest state.

This avoids mutating shared state in place while preserving atomicity for the reference update.

#### Deep dive

CAS works best when state is small enough to copy and update logic is cheap. If the state is large or updates are frequent, retries and allocation can become expensive.

#### Production angle

This pattern is useful for counters with extra metadata, read-mostly routing tables and in-memory state machines where the whole invariant fits in one state object.

#### Traps / caveats

- Retry loops must be bounded by practical cost.
- Mapping functions should be pure and side-effect free.
- Multiple independent references cannot be made atomic by CAS on only one of them.

#### Optional Anki

Q: What does CAS protect when using immutable state?
A: The atomic replacement of the shared state reference.

</details>

<a id="imm-jmm-007"></a>

<details>
<summary><strong>IMM-JMM-007. How can lazy cached values be implemented safely in immutable objects?</strong></summary>

#### Short answer

Use a thread-safe lazy pattern, or allow benign repeated computation when the cached value is derived from immutable state.

#### Interview answer

An immutable object can cache derived data such as `hashCode`, parsed fields or formatted text. If the cache is computed lazily, the field is physically mutable, so it needs a concurrency policy.

Common options are eager computation, a volatile cached field, synchronized initialization, holder objects, or benign race where multiple threads may compute the same deterministic value.

#### Deep dive

The cached value must not affect logical equality except as a derived optimization. It should be derived only from immutable state. If a cached object is mutable, do not expose it directly.

#### Production angle

Lazy caches can reduce repeated CPU cost for large value objects and cache keys, but bad implementations can create rare visibility bugs.

#### Traps / caveats

- Non-volatile lazy fields can be unsafe if object construction is not enough.
- `0` as a sentinel is tricky for cached hash codes because a real hash can be zero.
- Cached mutable results can leak state.

#### Optional Anki

Q: Can an immutable object have a mutable cached field?
A: Yes, if it does not change logical state and is made thread-safe.

</details>

<a id="imm-jmm-008"></a>

<details>
<summary><strong>IMM-JMM-008. Are `static final` fields always immutable?</strong></summary>

#### Short answer

No. `static final` makes the field reference fixed, but the referenced object can still be mutable.

#### Interview answer

`static final int MAX = 10` is an immutable constant. But `static final List<String> ROLES = new ArrayList<>()` is dangerous because the list contents can still change. The field cannot point to another list, but the same list can be mutated.

For constants, use immutable values or unmodifiable snapshots.

#### Deep dive

Public static final mutable objects are global mutable state. They are hard to test, hard to reason about and unsafe under concurrency unless carefully controlled.

#### Production angle

Global mutable state can cause cross-request data leaks, flaky tests and unexpected production behavior after one component modifies shared data.

#### Traps / caveats

- `static final Map` can still be mutable.
- Arrays in constants are mutable.
- Constant inlining applies only to compile-time constants, not arbitrary objects.

#### Optional Anki

Q: Is `public static final List<T>` automatically immutable?
A: No.

</details>

<a id="imm-jmm-009"></a>

<details>
<summary><strong>🧠 IMM-JMM-009. Can reflection, `Unsafe` or deserialization break immutability guarantees?</strong></summary>

#### Short answer

Yes. Advanced mechanisms can bypass constructors, access controls or normal final-field expectations.

#### Interview answer

Normal Java code cannot assign to a final field after construction, but reflection, unsafe APIs, instrumentation or some serialization paths can bypass normal construction and mutation rules. This can break invariants and confuse JVM optimizations or other threads.

For ordinary backend code this is usually a framework and security concern, not a daily design tool.

#### Deep dive

Deserialization can create objects without executing the normal constructor path. Reflection can access private members when permitted. `Unsafe` and instrumentation can operate outside normal language guarantees.

#### Production angle

Be careful when immutable objects cross serialization, ORM, JSON or reflection-heavy framework boundaries. Validate after deserialization where appropriate and avoid relying on reflection hacks to mutate final state.

#### Traps / caveats

- Do not use reflection mutation as an application update strategy.
- Security modules and newer JDK access rules may block reflective access.
- Generated code can bypass assumptions you made in hand-written constructors.

#### Optional Anki

Q: Why is reflective mutation of final fields dangerous?
A: It bypasses normal construction and visibility assumptions.

</details>

<a id="imm-jmm-010"></a>

<details>
<summary><strong>IMM-JMM-010. What is the difference between immutable data and a thread-safe service?</strong></summary>

#### Short answer

Immutable data cannot change after construction. A thread-safe service coordinates concurrent behavior and side effects correctly.

#### Interview answer

An immutable DTO or value object is safe to share because it has no state changes. A service can still be unsafe if it mutates shared fields, uses non-thread-safe collaborators, performs check-then-act sequences or coordinates external side effects incorrectly.

Immutability helps service design, but it does not replace transaction boundaries, locking, idempotency or safe use of dependencies.

#### Deep dive

A service that holds an immutable configuration snapshot may be thread-safe for reading that config, but its database writes, cache updates and message publishing still need proper coordination.

#### Production angle

This distinction matters in Spring singletons. Constructor-injected immutable dependencies are good, but request-specific mutable state must not be stored in singleton fields.

#### Traps / caveats

- Stateless-looking services can still mutate collaborators.
- Immutable messages do not make message processing idempotent.
- Thread-safe data does not make a whole workflow thread-safe.

#### Optional Anki

Q: Does immutable data make a side-effecting service thread-safe?
A: No. The service's operations still need concurrency control.

</details>
