# 08.04. Defensive copying and immutable collections

---

<a id="imm-copy-001"></a>

<details>
<summary><strong>IMM-COPY-001. What is defensive copying, and when do you need it?</strong></summary>

#### Short answer

Defensive copying means creating your own copy of mutable data so outside code cannot change your internal state.

#### Interview answer

You need defensive copying when accepting or exposing mutable objects such as arrays, collections, `Date`, buffers or mutable DTOs. If an immutable class stores a caller-owned mutable object directly, the caller can mutate it after construction. If a getter returns internal mutable state, the caller can mutate it from outside.

#### Deep dive

Defensive copying can happen on input, output or both. Input copies protect construction. Output copies protect internal state from getters. The copy must match the guarantee: a shallow copy is not enough when elements are mutable and part of the invariant.

#### Production angle

Defensive copying protects cache values, public API models, configuration snapshots and domain value objects from accidental mutation in another layer.

#### Traps / caveats

- Copying only on output does not protect against constructor argument mutation.
- Copying only the collection structure does not protect mutable elements.
- Blind deep copies can be expensive.

#### Optional Anki

Q: What does defensive copying prevent?
A: External mutation of internal object state.

</details>

<a id="imm-copy-002"></a>

<details>
<summary><strong>IMM-COPY-002. What is the difference between shallow copy and deep copy?</strong></summary>

#### Short answer

A shallow copy copies the container or object shell. A deep copy also copies nested mutable objects.

#### Interview answer

For a list, a shallow copy creates a new list containing the same element references. That protects the list structure but not the elements. A deep copy creates new copies of the elements or the whole reachable object graph.

Shallow copying is enough when elements are immutable or intentionally shared. Deep copying is needed when nested mutation would break invariants.

#### Deep dive

Deep copying arbitrary graphs is hard because of cycles, shared references, polymorphism and identity. In Java backend code, converting to immutable value types is often cleaner than deep-copying arbitrary mutable entities.

#### Production angle

Order snapshots, audit records and event payloads often need deep immutability or at least immutable projections of mutable entities.

#### Traps / caveats

- `new ArrayList<>(old)` is shallow.
- Serialization-based deep copy is usually slow and brittle.
- Deep copy can accidentally lose identity relationships.

#### Optional Anki

Q: Does `new ArrayList<>(list)` copy the elements?
A: No. It copies element references.

</details>

<a id="imm-copy-003"></a>

<details>
<summary><strong>IMM-COPY-003. How do you defensively copy arrays?</strong></summary>

#### Short answer

Use `clone()`, `Arrays.copyOf()` or conversion to an immutable collection, and avoid returning the internal array.

#### Interview answer

Arrays are mutable, even if the field is final. In a constructor, copy an input array with `input.clone()` or `Arrays.copyOf(input, input.length)`. In an accessor, return a copy rather than the internal array.

For object arrays, this only copies the array structure. If elements are mutable, those elements must be copied or replaced with immutable values.

#### Deep dive

Primitive arrays avoid element-level mutability, but the array slots are still mutable. For API design, prefer `List.copyOf` or a domain-specific immutable type when possible.

#### Production angle

Array leaks appear in security-sensitive code, binary payload wrappers, IDs, hashes and cryptographic material.

#### Traps / caveats

- `final byte[]` is mutable.
- Object array copying is shallow.
- Returning a read-only interface is not possible for raw arrays.

#### Optional Anki

Q: How do you safely expose an internal array?
A: Return a copy, not the internal array.

</details>

<a id="imm-copy-004"></a>

<details>
<summary><strong>IMM-COPY-004. How do you defensively copy lists, sets and maps?</strong></summary>

#### Short answer

Use unmodifiable snapshots such as `List.copyOf`, `Set.copyOf` and `Map.copyOf`, or create a new collection and wrap it when needed.

#### Interview answer

For many immutable classes, `List.copyOf(input)`, `Set.copyOf(input)` and `Map.copyOf(input)` are good defaults. They create unmodifiable shallow snapshots and reject nulls. If you need a specific implementation or null behavior, create a new collection explicitly and then expose it safely.

#### Deep dive

Map copying protects keys and values only by reference. If map values are mutable, a caller can still mutate a value object already stored in the map unless you copy or convert values too.

#### Production angle

Collection copies are common in DTO constructors, configuration binding and event creation.

#### Traps / caveats

- `copyOf` is shallow.
- `Set.copyOf` may collapse duplicates based on set equality.
- Null rejection can change behavior when migrating legacy code.

#### Optional Anki

Q: Which standard method creates an unmodifiable list snapshot?
A: `List.copyOf`.

</details>

<a id="imm-copy-005"></a>

<details>
<summary><strong>IMM-COPY-005. How do you protect a collection that contains mutable elements?</strong></summary>

#### Short answer

Use immutable element types, copy each mutable element, or transform elements into immutable DTOs or value objects.

#### Interview answer

An unmodifiable `List<Address>` prevents adding or removing addresses, but if `Address` has setters, callers can still mutate an address in the list. To make the aggregate immutable, the elements must be immutable too or copied into immutable representations.

#### Deep dive

Element copying should be explicit. For domain entities, it is usually better to create snapshot types such as `AddressSnapshot` or `OrderItemSnapshot` instead of deep-copying entities directly.

#### Production angle

This is critical for audit records, Kafka events and cached response DTOs. The snapshot should not change when the live entity changes later.

#### Traps / caveats

- Unmodifiable collection structure is not deep immutability.
- Entity references inside snapshots can leak lifecycle changes.
- Copy constructors must copy all mutable fields, not only top-level fields.

#### Optional Anki

Q: What breaks an immutable collection design with mutable elements?
A: The elements can still be mutated.

</details>

<a id="imm-copy-006"></a>

<details>
<summary><strong>IMM-COPY-006. What is the difference between an unmodifiable view and an immutable copy?</strong></summary>

#### Short answer

An unmodifiable view blocks mutation through the view. An immutable copy is a detached snapshot of the structure.

#### Interview answer

`Collections.unmodifiableList(list)` wraps the original list. If the original list changes, the view reflects that change. `List.copyOf(list)` creates an unmodifiable snapshot, so later structural changes to the original do not affect the copy.

Both are shallow with respect to element objects.

#### Deep dive

Views are useful when the owner wants callers to observe live state without mutating it. Copies are better for immutable value objects and stable API results.

#### Production angle

Using a view in a constructor is usually wrong because the caller often still owns the backing list. Use a copy for API boundaries unless live semantics are intentional.

#### Traps / caveats

- Unmodifiable views are not security boundaries.
- A copy can still contain mutable elements.
- Copies cost allocation and time.

#### Optional Anki

Q: Which can reflect changes to a backing collection?
A: An unmodifiable view.

</details>

<a id="imm-copy-007"></a>

<details>
<summary><strong>IMM-COPY-007. What are `List.of()`, `Set.of()`, `Map.of()` and `copyOf()` used for?</strong></summary>

#### Short answer

`of()` creates small unmodifiable collections from provided elements. `copyOf()` creates unmodifiable snapshots from existing collections or maps.

#### Interview answer

Use `List.of("A", "B")`, `Set.of(...)` and `Map.of(...)` for literals or small fixed data. Use `List.copyOf(existing)` when you receive an existing collection and need a stable unmodifiable snapshot.

These factory collections are unmodifiable and reject null keys or values.

#### Deep dive

`copyOf` may reuse the input if it is already an appropriate unmodifiable collection. That is fine because the input cannot be structurally modified through normal APIs.

#### Production angle

They are good defaults for immutable DTOs, value objects and configuration snapshots in modern Java.

#### Traps / caveats

- They are shallow.
- They reject nulls.
- `Map.of` is awkward for many entries; use `Map.ofEntries` or a builder-style approach.

#### Optional Anki

Q: Should you use `List.of` or `List.copyOf` for an existing collection?
A: `List.copyOf`.

</details>

<a id="imm-copy-008"></a>

<details>
<summary><strong>IMM-COPY-008. What does `UnsupportedOperationException` mean for unmodifiable collections?</strong></summary>

#### Short answer

It means the collection implementation does not support the requested mutating operation.

#### Interview answer

Collection interfaces include mutating methods such as `add`, `remove` and `clear`, but not every implementation supports them. Unmodifiable collections throw `UnsupportedOperationException` when those methods are called.

This is a runtime contract, not a compile-time type distinction.

#### Deep dive

The Java collection interfaces historically mix read and write operations. That means a method returning `List<T>` cannot express "read-only" in the type alone. Documentation and implementation choice carry the mutability contract.

#### Production angle

Unexpected `UnsupportedOperationException` often appears after switching from mutable lists to `List.of`, `List.copyOf` or `Stream.toList`.

#### Traps / caveats

- Catching the exception is not a design strategy.
- Some fixed-size lists allow `set` but not `add`.
- API contracts should document mutability expectations.

#### Optional Anki

Q: Is unmodifiable collection mutation rejected at compile time?
A: No. It fails at runtime.

</details>

<a id="imm-copy-009"></a>

<details>
<summary><strong>IMM-COPY-009. When should you prefer copying over wrapping, and when is a live view acceptable?</strong></summary>

#### Short answer

Prefer copying at ownership boundaries. Use live views only when the owner controls mutation and callers intentionally observe live state.

#### Interview answer

Constructors, public APIs, cache values and events usually need copies because they should not depend on later caller-side mutation. Wrapping is acceptable when the backing collection is private and controlled by the owner, and the API clearly intends to expose a read-only live view.

#### Deep dive

Copying gives snapshot semantics. Wrapping gives read-only access to the same backing state. They answer different design questions.

#### Production angle

For immutable DTOs and messages, prefer snapshots. For domain objects exposing current children inside a transaction, a read-only live view may be acceptable if mutation methods remain controlled.

#### Traps / caveats

- Wrapping caller-owned input is a common bug.
- Copying very large collections repeatedly can be expensive.
- Live views can surprise callers when data changes between reads.

#### Optional Anki

Q: Which is safer for constructor input: wrapping or copying?
A: Copying.

</details>

<a id="imm-copy-010"></a>

<details>
<summary><strong>IMM-COPY-010. What performance costs can defensive copying and snapshots introduce?</strong></summary>

#### Short answer

They can increase allocation, CPU work, memory footprint and GC pressure, especially for large or frequently copied structures.

#### Interview answer

Defensive copying is a correctness tool, but it is not free. Copying a small list in a DTO constructor is usually fine. Copying a large response graph on every request, or copying a huge configuration tree on every getter, can hurt latency and memory.

The right design depends on ownership, update frequency, size and whether callers need snapshots or live views.

#### Deep dive

Optimization options include immutable element types, copy-on-write, builders, structural sharing, pagination, streaming, caching derived immutable snapshots and avoiding repeated getter copies by storing an unmodifiable snapshot.

#### Production angle

High-throughput services can show defensive copies as allocation hotspots in profilers and GC logs.

#### Traps / caveats

- Do not remove defensive copies without proving ownership is safe.
- Do not return internal mutable state just for speed.
- Benchmark realistic object sizes and access patterns.

#### Optional Anki

Q: What is the main cost of defensive copying?
A: Extra allocation and copying work.

</details>
