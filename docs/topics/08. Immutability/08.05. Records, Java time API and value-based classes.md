# 08.05. Records, Java time API and value-based classes

---

<a id="imm-rec-001"></a>

<details>
<summary><strong>IMM-REC-001. What is a record, and how does it help create immutable models?</strong></summary>

#### Short answer

A record is a compact Java class for transparent data carriers with final component fields and generated accessors, `equals()`, `hashCode()` and `toString()`.

#### Interview answer

Records reduce boilerplate for value-like data. A record declares its state in the header, and Java generates private final fields, a canonical constructor, accessors and component-based `equals()`, `hashCode()` and `toString()`.

This helps create immutable-looking DTOs, commands, events and small value objects, especially when components are themselves immutable.

#### Deep dive

Records are transparent: their API is tied to their components. That is useful for simple data carriers but less suitable when you need representation hiding, complex lifecycle or flexible binary/API evolution.

#### Production angle

Records are practical for request/response DTOs, query projections, Kafka payloads and small internal values in modern Spring and Java applications.

#### Traps / caveats

- Records are shallowly immutable by default.
- Mutable components still need defensive copying.
- Adding a record component is an API compatibility change.

#### Optional Anki

Q: What methods does a record generate?
A: Accessors, `equals()`, `hashCode()` and `toString()`.

</details>

<a id="imm-rec-002"></a>

<details>
<summary><strong>IMM-REC-002. Are Java records deeply immutable?</strong></summary>

#### Short answer

No. Records are shallowly immutable by default because component fields are final, but component objects can still be mutable.

#### Interview answer

A record prevents reassignment of its component fields. It does not make a mutable component immutable. For example, `record User(List<String> roles)` stores a final reference to a list. If that list is mutable and shared, the roles can still change.

To make the record safer, copy mutable components in the constructor and protect accessors when needed.

#### Deep dive

Records are best with immutable component types such as `String`, primitive wrappers, enums, `BigDecimal` used carefully, `UUID` and `java.time` types.

#### Production angle

This trap often appears when records are used as DTOs or cache keys with collection components.

#### Traps / caveats

- Final component fields do not protect mutable objects.
- Array components are especially dangerous.
- Generated equality uses component values according to their own equality semantics.

#### Optional Anki

Q: What kind of immutability do records provide by default?
A: Shallow immutability.

</details>

<a id="imm-rec-003"></a>

<details>
<summary><strong>IMM-REC-003. How do you make defensive copies in a record constructor and accessor?</strong></summary>

#### Short answer

Copy mutable components in the compact or canonical constructor, and override accessors if returning the stored value would leak mutable state.

#### Interview answer

For a collection component, a compact constructor can replace the parameter with an unmodifiable snapshot:

```java
record User(String name, List<String> roles) {
    User {
        roles = List.copyOf(roles);
    }
}
```

For arrays, copy in the constructor and override the accessor to return a copy.

#### Deep dive

Record fields are assigned after the compact constructor body. Reassigning the constructor parameter in a compact constructor changes what gets stored.

#### Production angle

This is important for records used as API contracts, cache keys, messages and configuration snapshots.

#### Traps / caveats

- `List.copyOf` is shallow.
- Array accessors must return copies.
- Null handling and validation should be explicit.

#### Optional Anki

Q: How can a record protect a `List` component?
A: Assign `roles = List.copyOf(roles)` in the compact constructor.

</details>

<a id="imm-rec-004"></a>

<details>
<summary><strong>IMM-REC-004. What traps appear when record components are arrays or collections?</strong></summary>

#### Short answer

Arrays are mutable and use identity equality. Collections may be mutable and their elements may be mutable too.

#### Interview answer

A record with an array component has two problems: the array contents can change, and generated `equals()` compares arrays by reference rather than by contents. A record with a collection component gets collection equality, but mutation of the collection or its elements can still change the record's logical value.

#### Deep dive

If arrays are required, copy them on input and output, and consider overriding `equals()`, `hashCode()` and `toString()` if content-based behavior is needed. Often a list or dedicated immutable value type is better.

#### Production angle

These traps break map keys, deduplication, logging and API snapshots.

#### Traps / caveats

- Array components can make two visually identical records unequal.
- Mutable collection components can change hash codes over time.
- Defensive copying must cover accessors too.

#### Optional Anki

Q: Why are arrays risky in records?
A: They are mutable and generated equality compares array references.

</details>

<a id="imm-rec-005"></a>

<details>
<summary><strong>IMM-REC-005. Can records have behavior and validation logic?</strong></summary>

#### Short answer

Yes. Records can have constructors, methods, static members and validation logic.

#### Interview answer

Records are not just dumb tuples. A record can validate and normalize components in a compact constructor, add derived methods and implement interfaces. That makes records useful for small value objects and DTOs with simple invariants.

For example, a `DateRange` record can reject an end date before the start date and provide `contains(date)`.

#### Deep dive

Records cannot declare extra instance fields beyond components. If the behavior requires hidden state, lazy mutable internals or representation hiding, a regular class may be a better fit.

#### Production angle

Validation in records can prevent invalid request models or command objects from reaching service logic.

#### Traps / caveats

- Do not put heavy business workflows in record constructors.
- Avoid I/O or database access in record validation.
- Keep record behavior consistent with transparent component state.

#### Optional Anki

Q: Can a record validate constructor arguments?
A: Yes, commonly in a compact constructor.

</details>

<a id="imm-rec-006"></a>

<details>
<summary><strong>IMM-REC-006. When should you use a record instead of a classic immutable class?</strong></summary>

#### Short answer

Use a record for simple transparent data where the state description is the API.

#### Interview answer

A record is a good fit for DTOs, query results, commands, events and small value objects where component-based equality and generated methods are exactly what you want.

Use a classic class when you need representation hiding, custom construction patterns, inheritance control beyond record restrictions, complex invariants, binary compatibility flexibility or framework behavior that records do not support well.

#### Deep dive

Records make API evolution more explicit but also more rigid. Adding, removing or reordering components changes construction and generated methods.

#### Production angle

For backend APIs, records are excellent internal DTOs and projections. For public library APIs or long-lived message schemas, think carefully about evolution.

#### Traps / caveats

- Records expose their data model intentionally.
- Records are final.
- A record with components has no implicit no-arg constructor; an explicit no-arg constructor is possible only if it delegates to the canonical constructor with default values.

#### Optional Anki

Q: What is the main design signal of a record?
A: The declared state is the public data contract.

</details>

<a id="imm-rec-007"></a>

<details>
<summary><strong>IMM-REC-007. Why are records usually poor JPA entities but useful DTOs and projections?</strong></summary>

#### Short answer

JPA entities need identity, lifecycle, proxies and mutable persistence state, while records are final value-like data carriers.

#### Interview answer

Hibernate entities normally need a no-arg constructor, non-final classes for proxies, mutable fields for dirty checking and identity/lifecycle semantics. Records are final, component-based and value-like, which conflicts with normal entity modeling.

Records are useful for DTO projections, read models, API responses and command/event payloads because those are value-like snapshots.

#### Deep dive

Some frameworks support records for projections or constructor binding. That is different from making records managed entities.

#### Production angle

Keep persistence entities separate from immutable API or event records. Map from entity state to immutable snapshots at boundaries.

#### Traps / caveats

- Do not expose managed entities as immutable DTOs.
- Record equality is component-based, not database identity-based.
- Lazy proxies and final records do not mix well.

#### Optional Anki

Q: Where are records useful with JPA?
A: DTO projections and read models, not usually managed entities.

</details>

<a id="imm-rec-008"></a>

<details>
<summary><strong>IMM-REC-008. How do records interact with JSON serialization and API compatibility?</strong></summary>

#### Short answer

Modern JSON libraries can serialize and deserialize records through their components, but component changes affect the API contract.

#### Interview answer

Jackson and similar libraries can bind JSON properties to record components. This works well for immutable DTOs when constructor names and JSON property names match or are annotated.

The risk is evolution. Adding a required component, renaming a component or changing a type can break clients or deserialization unless defaults, optional fields or compatibility handling are designed.

#### Deep dive

Records do not follow JavaBean getter names by default; accessors are named after components. Framework versions and configuration matter.

#### Production angle

For public APIs and Kafka schemas, treat record components as schema fields. Version them deliberately.

#### Traps / caveats

- Adding a component changes constructors and equality.
- Missing JSON fields may become null unless validation rejects them.
- Generated `toString()` may expose sensitive fields.

#### Optional Anki

Q: What is a compatibility risk of public records?
A: Changing components changes the public data contract.

</details>

<a id="imm-rec-009"></a>

<details>
<summary><strong>IMM-REC-009. Why are `LocalDate`, `Instant` and other `java.time` types immutable?</strong></summary>

#### Short answer

`java.time` types return new instances for changes, which makes them safe value objects.

#### Interview answer

The modern date/time API was designed around immutable, thread-safe value types. Calling `plusDays`, `withMonth` or similar methods does not mutate the original object; it returns a new value.

This is very different from legacy `Date` and `Calendar`, which are mutable and can leak state if stored or returned directly.

#### Deep dive

Immutable time types make date calculations safer in shared DTOs, cache keys and domain objects. They also have clearer types: `Instant` for a timeline point, `LocalDate` for a date without timezone and `ZonedDateTime` for timezone-aware values.

#### Production angle

Prefer `java.time` in APIs, entities and DTOs unless legacy integration forces old types.

#### Traps / caveats

- `LocalDateTime` has no timezone.
- `Date` is mutable.
- Immutability does not solve timezone or clock-source mistakes.

#### Optional Anki

Q: Does `LocalDate.plusDays(1)` mutate the original date?
A: No. It returns a new `LocalDate`.

</details>

<details>
<summary><strong>🧠 IMM-REC-010. What are value-based classes, and why should they not be used for identity-sensitive operations?</strong></summary>

#### Short answer

Value-based classes are classes where equality should be based on value, not object identity, so identity-sensitive operations are discouraged.

#### Interview answer

Value-based classes represent values rather than identity-bearing objects. Examples in the JDK include many immutable types such as `Optional` and several date/time classes. The guidance is to avoid depending on identity operations like `==`, identity hash codes or synchronization on instances.

The implementation may reuse instances or change representation in future JVMs.

#### Deep dive

This direction aligns with Java's broader move toward value-oriented programming. A value-based object should be treated like "the value 10" rather than "this particular box containing 10".

#### Production angle

Use `equals()` for value comparison and avoid locking on value-based objects. Lock on private dedicated lock objects if synchronization is needed.

#### Traps / caveats

- Do not use `==` for value comparison.
- Do not use instances as monitor locks.
- Do not rely on stable identity hash codes.

#### Optional Anki

Q: How should value-based classes be compared?
A: By value, usually with `equals()`, not identity.

</details>
