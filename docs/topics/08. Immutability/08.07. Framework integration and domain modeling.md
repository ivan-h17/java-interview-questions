# 08.07. Framework integration and domain modeling

<a id="imm-fw-001"></a>

<details>
<summary><strong>IMM-FW-001. How do immutable classes work with Jackson JSON deserialization?</strong></summary>

#### Short answer

Jackson can deserialize immutable classes through constructors, records, builders or annotated creators.

#### Interview answer

For immutable objects, Jackson cannot set fields through setters after creating an empty object unless such a model exists. Instead, it can call a constructor, record canonical constructor, static factory or builder. You may need `@JsonCreator`, `@JsonProperty`, parameter-name metadata or builder annotations depending on the class and Jackson version.

#### Deep dive

Records are usually straightforward with modern Jackson. Classic immutable classes need constructors or builders that match JSON properties. Validation should still happen in the constructor or factory.

#### Production angle

Immutable request DTOs keep controller inputs stable after deserialization and make validation clearer.

#### Traps / caveats

- Missing fields may become null unless validated.
- Renaming constructor parameters can break binding.
- Generated `toString()` may expose sensitive JSON fields.

#### Optional Anki

Q: How can Jackson create immutable objects?
A: Through a constructor, record canonical constructor, factory or builder.

</details>

<a id="imm-fw-002"></a>

<details>
<summary><strong>IMM-FW-002. What should you consider when using immutable DTOs in Spring MVC?</strong></summary>

#### Short answer

Consider JSON binding, validation, null handling, API evolution and whether collection fields are defensively copied.

#### Interview answer

Immutable DTOs work well in Spring MVC because request data should usually be a stable snapshot. Records or constructor-bound classes can represent requests and responses clearly. Bean Validation can be applied to fields, constructor parameters or record components depending on setup.

You still need explicit validation for cross-field invariants and defensive copying for mutable components.

#### Deep dive

For partial updates, immutable DTOs can be awkward because absence, null and unchanged values have different meanings. Use dedicated patch DTOs or command types instead of overloading one model.

#### Production angle

Immutable DTOs reduce accidental mutation between controller, service and mapper layers.

#### Traps / caveats

- Do not expose JPA entities as DTOs.
- Avoid using one DTO for create, update, patch and response if the contracts differ.
- Document nullability and defaults.

#### Optional Anki

Q: Why are immutable request DTOs useful?
A: They represent a stable validated request snapshot.

</details>

<a id="imm-fw-003"></a>

<details>
<summary><strong>IMM-FW-003. How do mapping libraries such as MapStruct work with immutable targets?</strong></summary>

#### Short answer

They use constructors, builders, records or factory methods instead of setters.

#### Interview answer

For mutable targets, mappers often create an object and call setters. For immutable targets, the mapper must call a constructor, record constructor, builder or factory method with all required values.

This means the target's construction API must be clear and complete.

#### Deep dive

Mapping mutable entities into immutable DTOs is a common backend pattern. Mapping immutable DTOs back into managed entities should usually happen through domain methods or application services, not blind field replacement.

#### Production angle

Immutable targets make mapper output safer for APIs and events, but mapping errors can appear as constructor argument order, missing values or nullability bugs.

#### Traps / caveats

- Generated mappers can bypass manual validation if they call the wrong constructor.
- Builder defaults may differ from constructor defaults.
- Mutable nested objects still need conversion.

#### Optional Anki

Q: What does a mapper need for immutable targets?
A: A constructor, builder, factory or record constructor.

</details>

<a id="imm-fw-004"></a>

<details>
<summary><strong>IMM-FW-004. Should JPA entities be immutable?</strong></summary>

#### Short answer

Usually not fully. JPA entities commonly need controlled mutability for persistence lifecycle and business state transitions.

#### Interview answer

JPA entities represent identity and lifecycle. Hibernate often expects a no-arg constructor, field access, proxies and dirty checking. Full immutability can fight those mechanisms. A better design is controlled mutability: private fields, protected constructors, behavior methods and no public setter flood.

Immutable value objects and embeddables can still be very useful inside the entity model.

#### Deep dive

Some read-only entities or projections can be immutable, but normal write models usually need state changes inside a transaction.

#### Production angle

Separate mutable persistence entities from immutable API DTOs, events and value objects. Map between them at boundaries.

#### Traps / caveats

- Public setters can bypass invariants.
- Final classes and methods can break proxies.
- Entity equality should not use mutable state casually.

#### Optional Anki

Q: What is often better than fully immutable JPA entities?
A: Controlled mutability with behavior methods.

</details>

<a id="imm-fw-005"></a>

<details>
<summary><strong>IMM-FW-005. When are immutable JPA embeddables useful?</strong></summary>

#### Short answer

They are useful for value objects such as `Money`, `Address`, `DateRange` or `EmailAddress` that belong to an entity.

#### Interview answer

Embeddables often model values without independent identity. That makes them a good fit for immutability. Instead of mutating part of an embedded value, create a new value and assign it through a controlled entity method.

This keeps invariants close to the value object and avoids scattered validation.

#### Deep dive

JPA provider support and access strategy matter. Some frameworks need a no-arg constructor or field access. You can still keep the public API immutable while satisfying framework requirements with restricted constructors.

#### Production angle

Immutable embeddables reduce bugs around money, addresses, date ranges and normalized identifiers.

#### Traps / caveats

- Do not share mutable embeddables between entities.
- Replacing an embeddable must still be tracked by persistence.
- Framework requirements may weaken pure immutability.

#### Optional Anki

Q: Why do embeddables often fit immutability?
A: They usually represent values without independent identity.

</details>

<a id="imm-fw-006"></a>

<details>
<summary><strong>IMM-FW-006. How does Hibernate dirty checking interact with immutable objects?</strong></summary>

#### Short answer

Hibernate detects changes to managed entity state; immutable values are usually replaced rather than mutated in place.

#### Interview answer

Hibernate dirty checking compares managed state during flush. With mutable entity fields, changing a field can be detected. With immutable value objects, you typically assign a new value object to the entity field through a domain method.

This can be clearer because the replacement represents a real business change.

#### Deep dive

If an object is mutable but Hibernate cannot detect its internal mutation, changes may not persist correctly. Conversely, immutable values reduce hidden in-place changes.

#### Production angle

Use immutable value objects for small owned concepts and mutable entities for aggregate lifecycle. Test persistence updates so replacements are detected as expected.

#### Traps / caveats

- Mutating a value object hidden inside an entity can bypass dirty checking.
- Final fields may not fit provider expectations.
- Lazy-loaded associations are not immutable snapshots.

#### Optional Anki

Q: How do you update an immutable embeddable?
A: Replace it with a new value object through the owning entity.

</details>

<a id="imm-fw-007"></a>

<details>
<summary><strong>IMM-FW-007. How can Spring Boot immutable `@ConfigurationProperties` be modeled and reloaded?</strong></summary>

#### Short answer

Model configuration as constructor-bound immutable objects, and publish refreshed snapshots safely if runtime reload is needed.

#### Interview answer

Immutable configuration properties can be represented with records or constructor-bound classes. The object should validate required values and copy collection fields. For normal startup configuration, Spring creates the object once.

If configuration can reload at runtime, publish a new immutable snapshot through a safe mechanism such as a volatile reference, `AtomicReference` or framework-supported refresh scope.

#### Deep dive

Do not mutate nested configuration maps in place. Build a complete new snapshot so readers never see half-updated settings.

#### Production angle

Immutable config avoids request threads observing partially changed limits, endpoints or feature flags.

#### Traps / caveats

- Reloading is a concurrency problem even if each snapshot is immutable.
- Validate new config before publishing it.
- Keep secrets out of generated `toString()`.

#### Optional Anki

Q: How should runtime config reload publish immutable state?
A: Build and validate a new snapshot, then safely replace the shared reference.

</details>

<a id="imm-domain-001"></a>

<details>
<summary><strong>IMM-DOMAIN-001. Why are value objects usually immutable in DDD?</strong></summary>

#### Short answer

Value objects are defined by their values, so changing the value means creating a different value.

#### Interview answer

In DDD, a value object has no independent identity. `Money(10, USD)` or `EmailAddress("a@b.com")` is identified by its value. Immutability fits because it preserves the meaning and invariants of the value after construction.

If a value needs to change, the model usually replaces it with a new value object.

#### Deep dive

Immutable value objects can enforce validation once and then be reused safely across entities, messages and APIs.

#### Production angle

They reduce duplicate validation and accidental corruption for concepts such as money, date ranges, IDs and normalized text.

#### Traps / caveats

- Value objects can still contain collections that need copying.
- Do not put entity lifecycle inside value objects.
- Equality should match domain meaning.

#### Optional Anki

Q: What identifies a DDD value object?
A: Its value, not object identity.

</details>

<a id="imm-domain-002"></a>

<details>
<summary><strong>IMM-DOMAIN-002. How would you model `Money` as an immutable value object?</strong></summary>

#### Short answer

Store amount and currency as final validated fields, normalize scale deliberately, and return new `Money` instances for operations.

#### Interview answer

I would model `Money` with `BigDecimal amount` and `Currency currency`, both required. The constructor or factory validates nulls, scale, precision and allowed currencies. Operations like `add` check matching currency and return a new `Money`.

Equality should be deliberate about `BigDecimal` scale because `1.0` and `1.00` are not equal by `BigDecimal.equals()`.

#### Deep dive

Many teams normalize amount scale by currency or use minor units such as cents to avoid scale surprises. The right choice depends on domain rules.

#### Production angle

Money bugs are expensive. A small immutable value object centralizes validation and prevents accidental currency mixing.

#### Traps / caveats

- Do not use `double` for money.
- Define rounding rules explicitly.
- Be careful with `BigDecimal.equals()` vs `compareTo()`.

#### Optional Anki

Q: Why should `Money.add` check currency?
A: Adding different currencies without conversion is invalid.

</details>

<a id="imm-domain-003"></a>

<details>
<summary><strong>IMM-DOMAIN-003. How do immutable command and event objects help backend systems?</strong></summary>

#### Short answer

They provide stable snapshots of intent or facts that cannot be accidentally changed during processing.

#### Interview answer

A command represents a request to do something. An event represents something that happened. Both benefit from immutability because handlers, validators, loggers and message publishers can all observe the same stable data.

This is especially important when commands or events cross thread, transaction or service boundaries.

#### Deep dive

Immutable commands still need validation and authorization. Immutable events should contain enough data for consumers without relying on mutable entity references.

#### Production angle

Stable message payloads improve auditability, retry behavior, idempotency and debugging.

#### Traps / caveats

- Immutable events do not guarantee exactly-once processing.
- Avoid putting live entity references in events.
- Version event schemas explicitly.

#### Optional Anki

Q: Why should event payloads be immutable?
A: They represent a fact that should not change after publication.

</details>

<a id="imm-domain-004"></a>

<details>
<summary><strong>IMM-DOMAIN-004. How can immutable snapshots support audit, history and event sourcing?</strong></summary>

#### Short answer

They capture state at a point in time, so later mutations do not rewrite history.

#### Interview answer

An immutable snapshot records what was true when an action happened: order items, prices, customer details, limits or authorization context. If the live entity changes later, the snapshot remains the same.

Event sourcing relies on events being historical facts. Audit logs similarly need records that cannot be mutated casually after the fact.

#### Deep dive

The snapshot should contain immutable values or deep immutable projections. Storing references to live mutable entities defeats the point.

#### Production angle

Snapshots help debug incidents, rebuild read models and prove what data was used for a decision.

#### Traps / caveats

- Snapshots can contain sensitive data and need retention rules.
- Schema evolution still matters.
- Immutability in memory is not the same as tamper-proof storage.

#### Optional Anki

Q: Why not store entity references in audit snapshots?
A: They can change later and corrupt historical meaning.

</details>

<a id="imm-domain-005"></a>

<details>
<summary><strong>IMM-DOMAIN-005. How can overusing immutable DTOs lead to an anemic domain model?</strong></summary>

#### Short answer

If everything becomes passive data copied between services, domain behavior and invariants may move into procedural service code.

#### Interview answer

Immutable DTOs are good at boundaries, but domain models need behavior. If every change is implemented by taking a DTO, modifying fields elsewhere and saving it, the domain object may stop protecting its invariants.

For entities and aggregates, controlled behavior methods can be clearer than endless immutable data transformations.

#### Deep dive

The issue is not immutability itself. Immutable value objects are strong domain models. The problem is using DTOs as the whole domain and putting all rules in large services.

#### Production angle

Anemic models often create duplicated validation, inconsistent transitions and fragile transaction scripts.

#### Traps / caveats

- Do not confuse DTO immutability with domain modeling.
- Entities may need controlled mutability.
- Value objects should still contain behavior relevant to their value.

#### Optional Anki

Q: Is immutability bad for DDD?
A: No. Immutable value objects are good; passive DTO-only domain models are the risk.

</details>
