# 08.06. Equality, `HashMap` keys and caching

---

<a id="imm-key-001"></a>

<details>
<summary><strong>IMM-KEY-001. Why are immutable objects good candidates for map keys and cache keys?</strong></summary>

#### Short answer

Their equality-relevant state is stable, so their `hashCode()` and `equals()` behavior does not change after insertion.

#### Interview answer

Hash-based maps rely on a key's hash and equality to find entries. If a key is immutable, the fields used in `equals()` and `hashCode()` cannot change after insertion. That makes lookups, removals and deduplication reliable.

Immutable keys are also easier to reuse in caches because callers cannot accidentally alter what the key means.

#### Deep dive

A good cache key should include all inputs that affect the result and normalize values where needed. For example, sort unordered filters or normalize case if the backend treats values case-insensitively.

#### Production angle

Bad mutable cache keys cause missed cache hits, wrong hits, memory leaks and very hard-to-debug behavior under load.

#### Traps / caveats

- Immutability alone is not enough; equality must include the right fields.
- Mutable fields inside records can still break keys.
- Overly large keys can make hashing expensive.

#### Optional Anki

Q: Why are immutable keys reliable in hash maps?
A: Their hash and equality do not change after insertion.

</details>

<a id="imm-key-002"></a>

<details>
<summary><strong>IMM-KEY-002. What happens if a key is mutated after insertion into a `HashMap`?</strong></summary>

#### Short answer

The entry can become unreachable because the key may no longer hash to or compare equal in the bucket where it was stored.

#### Interview answer

When a key is inserted, `HashMap` chooses a bucket based on the key's hash at that time. If equality-relevant state changes later, `get(key)` may compute a different hash or fail equality checks. The entry is still physically in the map, but normal lookup can return `null`.

#### Deep dive

The map does not re-index entries when key objects change. Mutation can also allow duplicate logical keys or make removal fail.

#### Production angle

This appears in caches, deduplication maps, request grouping and sets when DTOs or entities with setters are used as keys.

#### Traps / caveats

- Mutating a field not used in equality may be harmless for lookup, but still confusing.
- Lists and arrays inside keys are common hidden sources.
- Recomputing the same key object does not fix a corrupted map entry.

#### Optional Anki

Q: Does `HashMap` rehash a key when the key changes?
A: No.

</details>

<a id="imm-key-003"></a>

<details>
<summary><strong>IMM-KEY-003. What are the requirements for a reliable `HashMap` key?</strong></summary>

#### Short answer

It needs stable equality, stable hash code, correct `equals()` and `hashCode()` contracts, and reasonable hashing performance.

#### Interview answer

A reliable key should use fields that do not change while the key is in the map. If two keys are equal, they must have the same hash code. Equality should be symmetric, transitive and consistent. Hashing should spread values well enough and not be too expensive.

Immutability is the simplest way to make the key stable.

#### Deep dive

For composite keys, use a record or final class with normalized components. Avoid arrays unless you explicitly implement content-based equality and copy the array.

#### Production angle

Reliable keys matter in caches, authorization maps, idempotency tracking and in-memory indexes.

#### Traps / caveats

- Database-generated IDs can be unstable before persistence.
- Entity equality can change across lifecycle states.
- `BigDecimal` equality includes scale, which may surprise key design.

#### Optional Anki

Q: What must be true if `a.equals(b)`?
A: `a.hashCode()` must equal `b.hashCode()`.

</details>

<a id="imm-key-004"></a>

<details>
<summary><strong>IMM-KEY-004. How do immutable value objects simplify `equals()` and `hashCode()` correctness?</strong></summary>

#### Short answer

Their equality fields are fixed, so generated or hand-written equality remains consistent over time.

#### Interview answer

A value object is usually compared by its values. If those values are immutable, `equals()` and `hashCode()` are stable. This makes records and final value classes good fits for keys, set elements and DTO comparison.

For mutable entities, equality often has to consider identity, lifecycle and persistence state, which is harder.

#### Deep dive

Immutable value objects can also cache hash codes safely when hashing is expensive, as long as the cached value is derived from immutable state.

#### Production angle

Stable equality avoids subtle bugs in collections, caches, Hibernate sets and deduplication logic.

#### Traps / caveats

- Generated record equality can be wrong for arrays.
- Mutable components still break stability.
- Equality should match the business meaning, not just all fields mechanically.

#### Optional Anki

Q: Why is value-object equality easier when the object is immutable?
A: Equality-relevant state cannot change.

</details>

<a id="imm-key-005"></a>

<details>
<summary><strong>IMM-KEY-005. Why is `String` a common `HashMap` key?</strong></summary>

#### Short answer

`String` is immutable, has well-defined value equality and caches its hash code.

#### Interview answer

Strings are stable values. Once a `String` is created, its contents cannot be changed through normal Java APIs. Its `equals()` compares text content, and its `hashCode()` is based on that content and can be cached.

This makes `String` convenient for map keys such as IDs, names, headers and configuration keys.

#### Deep dive

String immutability also supports interning and safe sharing. But key design still matters: normalization, case sensitivity, locale and whitespace can all affect whether two strings should be considered the same business key.

#### Production angle

String keys are everywhere in request metadata, JSON fields, Redis keys and in-memory maps. Normalize consistently at boundaries.

#### Traps / caveats

- Do not compare strings with `==`.
- Beware locale-sensitive case conversion.
- Very large strings can make keys memory-heavy.

#### Optional Anki

Q: Why is `String` safe as a hash key?
A: Its content and hash-relevant state are immutable.

</details>

<a id="imm-key-006"></a>

<details>
<summary><strong>IMM-KEY-006. Can arrays or lists be reliable map keys?</strong></summary>

#### Short answer

Lists can be reliable if they and their elements are stable. Arrays are usually poor keys unless wrapped or handled with content-based equality.

#### Interview answer

`List.equals()` and `List.hashCode()` are content-based, so a list can be a key if it never changes and its elements are stable. In practice, mutable lists are risky.

Arrays do not use content-based `equals()` and `hashCode()` by default; they use object identity. Two arrays with the same contents are not equal unless they are the same array instance.

#### Deep dive

For array-like keys, create an immutable wrapper that copies the array and implements `equals()` and `hashCode()` using `Arrays.equals` and `Arrays.hashCode`.

#### Production angle

Composite request filters, byte keys and multi-column indexes often tempt developers to use lists or arrays. A dedicated immutable key type is clearer.

#### Traps / caveats

- Mutating a list key breaks lookup.
- Array keys usually compare by identity.
- Element mutability can break list key stability.

#### Optional Anki

Q: Do Java arrays have content-based `equals()` by default?
A: No.

</details>

<a id="imm-key-007"></a>

<details>
<summary><strong>IMM-KEY-007. Should JPA entities be used as `HashMap` keys?</strong></summary>

#### Short answer

Usually avoid it unless equality is carefully designed around stable identity.

#### Interview answer

JPA entities are mutable and have lifecycle states. If equality uses a generated database ID, the ID may be null before persistence and assigned later. If equality uses mutable business fields, the hash can change when the entity changes.

Prefer immutable key objects built from stable identifiers or normalized business keys.

#### Deep dive

Hibernate proxies can also complicate `equals()` if it uses exact class comparison. Collections managed by Hibernate have their own equality and lifecycle concerns.

#### Production angle

Using entities as map keys can break caches, deduplication and sets during persistence transitions or flushes.

#### Traps / caveats

- Generated IDs are not stable before insert.
- Mutable natural keys can change.
- Proxy classes can surprise class-based equality.

#### Optional Anki

Q: What is a safer alternative to using a JPA entity as a map key?
A: An immutable key built from stable identity fields.

</details>

<a id="imm-key-008"></a>

<details>
<summary><strong>IMM-KEY-008. How would you debug a failed lookup caused by a mutated key?</strong></summary>

#### Short answer

Inspect the key fields used in equality and hashing before and after insertion, and check whether any referenced mutable state changed.

#### Interview answer

I would find the key class, review `equals()` and `hashCode()`, and identify every field involved. Then I would check where the key is created, inserted and mutated. If the key contains collections, arrays or entities, I would inspect whether their state changes after insertion.

In a debugger or test, log the hash code at insertion and at lookup.

#### Deep dive

Sometimes the lookup key is not the inserted object but a newly created equal object. Then the bug may be normalization, equality implementation, missing fields or inconsistent types.

#### Production angle

Symptoms include cache misses, duplicate set entries, failed removals and map size growth despite expected key reuse.

#### Traps / caveats

- Do not rely only on `toString()`.
- Hash collisions are possible but less likely than bad key design.
- Rebuilding the map may hide the issue temporarily.

#### Optional Anki

Q: What should you compare first in a suspected mutated-key bug?
A: The key's equality-relevant fields and hash code before insertion and lookup.

</details>
