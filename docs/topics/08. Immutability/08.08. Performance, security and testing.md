# 08.08. Performance, security and testing

---

<a id="imm-perf-001"></a>

<details>
<summary><strong>IMM-PERF-001. How does immutability affect performance?</strong></summary>

#### Short answer

It can improve performance by reducing locks and enabling sharing, but it can hurt performance through extra allocation and copying.

#### Interview answer

Immutable objects can be shared safely, cached, reused and read without locks. That can improve throughput and simplify concurrency. They can also make cache keys reliable and reduce defensive synchronization.

The cost is that updates require new objects or copied structures. In write-heavy paths or large object graphs, this can increase allocation rate, memory footprint and GC pressure.

#### Deep dive

The performance result depends on object size, update frequency, escape analysis, allocation patterns and whether structural sharing is available.

#### Production angle

Use profiling before changing design. If immutable copies show up as allocation hotspots, optimize the copy boundary rather than abandoning immutability everywhere.

#### Traps / caveats

- Immutable is not automatically faster.
- Mutable local variables can be perfectly fine.
- Removing copies can reintroduce correctness bugs.

#### Optional Anki

Q: What are two performance benefits of immutability?
A: Safe sharing and less locking.

</details>

<a id="imm-perf-002"></a>

<details>
<summary><strong>IMM-PERF-002. How can immutable objects increase allocation rate and GC pressure?</strong></summary>

#### Short answer

Every logical update may create new objects, and large defensive copies can allocate many short-lived objects.

#### Interview answer

With mutable objects, an update can change fields in place. With immutable objects, an update usually creates a new object and sometimes copies nested collections. In high-throughput services, many short-lived immutable objects can increase allocation rate and GC work.

This is not always a problem because modern JVM allocation is fast, but it becomes visible under large graphs or hot loops.

#### Deep dive

Escape analysis can eliminate some short-lived allocations, but you should not assume it removes all object creation. Measure with realistic workloads.

#### Production angle

Symptoms include high young-generation GC, allocation hotspots in profilers and latency spikes during batch transformations.

#### Traps / caveats

- Do not optimize based on object count alone.
- Avoid huge copied response graphs when pagination would solve the real problem.
- Builder use can reduce intermediate copies during construction.

#### Optional Anki

Q: Why can immutable updates create GC pressure?
A: They often allocate new objects instead of mutating in place.

</details>

<a id="imm-perf-003"></a>

<details>
<summary><strong>IMM-PERF-003. How can immutable snapshots reduce lock contention?</strong></summary>

#### Short answer

Readers can access a stable snapshot without locking while writers publish a new snapshot atomically.

#### Interview answer

For read-mostly state, keep an immutable snapshot in a volatile field or `AtomicReference`. Readers read the current reference and do not need locks. Writers build a new snapshot and replace the reference.

This avoids holding locks around many read operations while preserving consistency within each snapshot.

#### Deep dive

This pattern works when readers can tolerate seeing a slightly old snapshot and updates can replace the whole state.

#### Production angle

It is useful for feature flags, routing tables, pricing rules, permission maps and configuration.

#### Traps / caveats

- Large snapshots can be expensive to rebuild.
- Readers may see old data briefly.
- Multi-step external side effects still need coordination.

#### Optional Anki

Q: What state pattern helps read-mostly concurrency?
A: Immutable snapshots published through a volatile or atomic reference.

</details>

<a id="imm-perf-004"></a>

<details>
<summary><strong>🧠 IMM-PERF-004. When are persistent data structures and structural sharing useful?</strong></summary>

#### Short answer

They are useful when you need immutable updates without copying an entire large structure each time.

#### Interview answer

Persistent data structures return a new version after an update while sharing unchanged parts with the old version. Structural sharing reduces the cost of immutable updates compared with full copying.

They are useful for snapshots, versioned state, functional-style transformations and read-mostly data with occasional updates.

#### Deep dive

Java's standard collections are not persistent collections in this sense. Libraries can provide persistent vectors, maps or sets, often using tree-like structures.

#### Production angle

They can help with in-memory indexes, configuration versions, rule sets and systems that need old and new versions alive at the same time.

#### Traps / caveats

- They are not automatically faster than mutable collections.
- They add library and mental-model cost.
- Random access and memory overhead depend on the implementation.

#### Optional Anki

Q: What is structural sharing?
A: Reusing unchanged parts between old and new immutable versions.

</details>

<a id="imm-perf-005"></a>

<details>
<summary><strong>IMM-PERF-005. When is object pooling useful or harmful for immutable objects?</strong></summary>

#### Short answer

Pooling is rarely useful for ordinary immutable objects and can hurt performance, but canonicalization may help for repeated expensive values.

#### Interview answer

Modern JVM allocation is fast, so pooling small immutable objects often adds complexity, contention and memory retention. For immutable objects, caching or canonicalization can be useful when values repeat often and are expensive to create or compare, such as interned strings or predefined constants.

#### Deep dive

Pooling mutable objects is a different topic and can introduce reset bugs. For immutable objects, the main risk is unbounded caches retaining values forever.

#### Production angle

Use measured cache policies, not ad hoc global pools. Watch memory growth and eviction behavior.

#### Traps / caveats

- Do not pool just to avoid `new`.
- Unbounded interning can leak memory.
- Pool lookups can cost more than allocation.

#### Optional Anki

Q: Is object pooling usually needed for small immutable objects?
A: No.

</details>

<a id="imm-sec-001"></a>

<details>
<summary><strong>IMM-SEC-001. How can immutability improve security and prevent time-of-check to time-of-use bugs?</strong></summary>

#### Short answer

Immutable data cannot be changed between validation and use, which reduces accidental or malicious state changes.

#### Interview answer

A time-of-check to time-of-use bug happens when data is validated, then changed before it is used. If a request, permission set or file descriptor metadata is immutable after validation, later code uses the same state that was checked.

Immutability also reduces accidental mutation of authorization tokens, audit records and signed payloads.

#### Deep dive

Immutability is not a complete security boundary. Reflection, deserialization, storage tampering or mutable nested state can still break assumptions.

#### Production angle

Immutable request fingerprints, idempotency keys and authorization contexts make security decisions easier to audit.

#### Traps / caveats

- Unmodifiable views are not security boundaries.
- Immutable objects can still contain sensitive data.
- Validate nested mutable inputs before copying or signing.

#### Optional Anki

Q: What class of bug can immutability reduce between validation and use?
A: Time-of-check to time-of-use bugs.

</details>

<a id="imm-sec-002"></a>

<details>
<summary><strong>IMM-SEC-002. Why are `String` objects problematic for passwords and secrets?</strong></summary>

#### Short answer

Strings are immutable, so their contents cannot be reliably cleared from memory after use.

#### Interview answer

Because `String` is immutable, a password stored as a string may remain in memory until garbage collection, and copies can be created by logging, concatenation, interning mistakes or framework handling. You cannot overwrite a `String`'s contents through normal APIs.

For secrets that must be cleared, `char[]` or `byte[]` gives more control, though it is not perfect.

#### Deep dive

In many backend APIs, secrets still arrive as strings due to HTTP, JSON or framework contracts. The goal is to minimize retention, logging and unnecessary copies.

#### Production angle

Do not log secrets, include them in exceptions or expose them through generated `toString()`.

#### Traps / caveats

- Mutable arrays can be cleared but can also be leaked.
- Clearing memory does not remove copies already made elsewhere.
- Hash passwords with appropriate password-hashing algorithms, not plain hashes.

#### Optional Anki

Q: Why can a `char[]` be preferable to `String` for secrets?
A: Its contents can be overwritten after use.

</details>

<a id="imm-sec-003"></a>

<details>
<summary><strong>IMM-SEC-003. What sensitive data should not appear in generated `toString()` methods?</strong></summary>

#### Short answer

Passwords, tokens, API keys, secrets, personal data and security decisions should not be printed blindly.

#### Interview answer

Immutable classes and records often have generated `toString()` methods. That is convenient for debugging but dangerous if the object contains access tokens, refresh tokens, passwords, private keys, session IDs, personal identifiers or payment data.

The class should override `toString()` or use annotations/configuration to redact sensitive fields.

#### Deep dive

The risk is higher for immutable objects because they are often used as request DTOs, commands and events that may be logged at boundaries.

#### Production angle

Sensitive `toString()` output leaks into logs, traces, exception messages, test reports and monitoring tools.

#### Traps / caveats

- Records include all components in generated `toString()`.
- Redaction must be consistent across logs and mappers.
- Do not rely on "internal only" logs for secrets.

#### Optional Anki

Q: What record feature can leak secrets?
A: Generated `toString()` includes component values.

</details>

<a id="imm-test-001"></a>

<details>
<summary><strong>IMM-TEST-001. How would you test that a class is immutable?</strong></summary>

#### Short answer

Test that external mutation of constructor inputs and getter results cannot change the object, and that equality-relevant state stays stable.

#### Interview answer

I would write tests that pass mutable inputs, mutate them after construction and assert the object did not change. Then I would get collections or arrays from accessors, try to mutate them or mutate returned copies, and assert internal state is still unchanged.

For key types, I would test `equals()` and `hashCode()` stability.

#### Deep dive

Reflection-based tests can inspect fields and setters, but behavior tests are more important. They verify the public immutability contract, not just implementation style.

#### Production angle

Regression tests are useful after mapper, Lombok, record or framework changes that can silently reintroduce mutable leaks.

#### Traps / caveats

- Do not only check that fields are final.
- Test mutable elements, not only collection structure.
- Serialization/deserialization paths need separate tests.

#### Optional Anki

Q: What is a key immutability test for constructor input?
A: Mutate the original input after construction and assert the object is unchanged.

</details>

<a id="imm-test-002"></a>

<details>
<summary><strong>IMM-TEST-002. How can code review and static analysis catch mutability leaks?</strong></summary>

#### Short answer

Look for mutable fields, direct storage of mutable inputs, mutable getters, public setters, array exposure and mutable components in records.

#### Interview answer

A review checklist should flag `Date`, arrays, collections, builders, entity references, non-final fields, setters and public mutable static state. For records, check collection and array components. Static analysis can detect exposed internal representation, field mutability and unsafe assignments.

The reviewer should ask what the immutability guarantee actually is: shallow, deep, snapshot or read-only view.

#### Deep dive

Tools help, but they cannot fully understand domain ownership. A mutable object may be safe if it is confined and never exposed, or unsafe if shared through an interface.

#### Production angle

Review catches many bugs before they become cache corruption, data races or API mutation surprises.

#### Traps / caveats

- Lombok-generated methods can hide mutability problems.
- A clean-looking record can still contain mutable components.
- Static analysis findings need domain judgment.

#### Optional Anki

Q: What should a review check in records used as immutable DTOs?
A: Mutable components such as arrays, collections and mutable element types.

</details>
