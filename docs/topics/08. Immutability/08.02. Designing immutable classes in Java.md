# 08.02. Designing immutable classes in Java

---

<a id="imm-design-001"></a>

<details>
<summary><strong>IMM-DESIGN-001. How do you create an immutable class in Java?</strong></summary>

#### Short answer

Make state private and final, do not expose mutators, validate construction, copy mutable inputs and avoid leaking mutable internals.

#### Interview answer

A typical immutable Java class is final, has private final fields, initializes all state in the constructor, exposes no setters and validates arguments before the object becomes visible. If a field refers to mutable data, the constructor copies it and accessors return safe copies or immutable views.

For example, a `Money` class would store a normalized `BigDecimal` and `Currency`, validate scale and currency, and return a new `Money` for operations like `add`.

#### Deep dive

Immutability is a contract. The implementation must cover inheritance, constructor leaks, arrays, collections, mutable elements, serialization and framework-generated code.

#### Production angle

Immutable classes are useful for request objects, value objects, events and cache keys because callers can share them without ownership confusion.

#### Traps / caveats

- No setters is not enough.
- `final` fields are not enough for mutable referenced objects.
- Frameworks can require constructors, setters or proxies that conflict with immutability.

#### Optional Anki

Q: Name three rules for immutable Java classes.
A: Private final fields, no mutators, and defensive copies for mutable state.

</details>

<a id="imm-design-002"></a>

<details>
<summary><strong>IMM-DESIGN-002. Why should immutable classes usually use private final fields and no setters?</strong></summary>

#### Short answer

Private fields preserve encapsulation, final fields prevent reassignment after construction, and no setters prevents ordinary state changes.

#### Interview answer

`private` keeps callers from changing fields directly. `final` makes the reference or primitive value assigned once, which supports both readability and Java Memory Model guarantees for final fields. Avoiding setters keeps the object from exposing a mutation API.

Together they create a strong baseline, but they do not complete immutability if the fields refer to mutable objects.

#### Deep dive

A final field of type `List<Item>` only means the field cannot point to another list. The list can still be modified unless it is copied or is itself immutable.

#### Production angle

Private final fields make value classes easier to review. They show that the important state is fixed at construction and help tools detect accidental mutation.

#### Traps / caveats

- `final` is reference immutability, not object immutability.
- Setters are not the only way to mutate state.
- Public mutable fields break the contract immediately.

#### Optional Anki

Q: Does `final List<Item>` make the list immutable?
A: No. It only prevents field reassignment.

</details>

<a id="imm-design-003"></a>

<details>
<summary><strong>IMM-DESIGN-003. Is it enough to make all fields final to make a class immutable?</strong></summary>

#### Short answer

No. Final fields prevent reassignment, but referenced objects may still be mutable and exposed.

#### Interview answer

All fields being final is useful, but not sufficient. If a final field points to an array, `Date`, `List`, `Map`, entity or mutable DTO, that object can still change. If the constructor stores external references or getters return internals, callers can mutate the supposedly immutable object.

#### Deep dive

Final fields also do not prevent mutation through reflection, unsafe mechanisms or deserialization tricks. Those are not normal application paths, but they matter for security-sensitive code and framework integration.

#### Production angle

This trap commonly breaks cache keys and DTO snapshots. A key object looks final, but a list inside it changes and `hashCode()` changes with it.

#### Traps / caveats

- Final fields are necessary for many immutable classes, but not sufficient.
- Arrays are always mutable.
- Mutable elements can break otherwise protected collections.

#### Optional Anki

Q: What does final guarantee for a reference field?
A: The reference cannot be reassigned after construction.

</details>

<a id="imm-design-004"></a>

<details>
<summary><strong>IMM-DESIGN-004. How should an immutable class handle mutable constructor arguments?</strong></summary>

#### Short answer

It should validate and copy mutable arguments instead of storing caller-owned references directly.

#### Interview answer

If a constructor receives a mutable object such as `List`, `Map`, array or `Date`, storing it directly lets the caller mutate the object's state after construction. An immutable class should take a defensive copy, normalize it if needed, and store only safe state.

For collections, `List.copyOf`, `Set.copyOf` and `Map.copyOf` are often good for shallow unmodifiable snapshots.

#### Deep dive

For mutable elements, a shallow collection copy is not enough. You may need immutable element types, element-level copies or conversion to a safe DTO/value type.

#### Production angle

Constructor copying protects API requests, cache values and configuration snapshots from later caller-side mutation.

#### Traps / caveats

- Copy before storing the reference.
- Do not validate one object and then store a different mutable reference.
- `List.copyOf` rejects null elements.

#### Optional Anki

Q: Why copy mutable constructor arguments?
A: To prevent the caller from changing the object's state after construction.

</details>

<a id="imm-design-005"></a>

<details>
<summary><strong>IMM-DESIGN-005. How should getters expose mutable fields safely?</strong></summary>

#### Short answer

Return immutable values, defensive copies or controlled read-only snapshots instead of internal mutable references.

#### Interview answer

If a getter returns an internal array or mutable collection, callers can mutate it and break invariants. For arrays, return `array.clone()` or a copied collection. For collections, return a stored immutable copy or a fresh copy when needed. For old mutable date types, return a copied instance or use `java.time`.

#### Deep dive

Returning a fresh copy every time is safe but may be expensive. A stored unmodifiable snapshot is often enough if elements are immutable. For live views, document that the view is live and ensure the owner controls mutation.

#### Production angle

Getter leaks often cause flaky behavior in tests and production because mutation happens in utility code far from the model class.

#### Traps / caveats

- Returning an unmodifiable view is not a detached copy.
- Returning mutable elements can still leak state.
- Expensive copying in hot getters can become a latency issue.

#### Optional Anki

Q: What is dangerous about returning an internal array?
A: The caller can modify the object's internal state.

</details>

<a id="imm-design-006"></a>

<details>
<summary><strong>IMM-DESIGN-006. How do you handle arrays, collections and nested mutable objects inside immutable classes?</strong></summary>

#### Short answer

Copy arrays and collections, prefer immutable element types, and convert nested mutable objects into immutable representations.

#### Interview answer

Arrays are always mutable, so copy them on input and output. Collections should usually be stored as unmodifiable snapshots such as `List.copyOf`. If elements are mutable, copy or transform each element too.

Nested mutable objects are the hard part. A shallow copy of `List<Address>` is not deeply immutable if `Address` has setters.

#### Deep dive

The best design is often to use immutable nested value objects from the start. Deep copying arbitrary graphs is expensive and can require cycle handling, identity preservation and clear ownership rules.

#### Production angle

This comes up in order snapshots, API responses and event payloads. A snapshot must not change when the live entity changes later.

#### Traps / caveats

- `List.copyOf` protects structure, not element state.
- Deep copies can accidentally share mutable children.
- Entity references inside immutable DTOs are usually a smell.

#### Optional Anki

Q: Is `List.copyOf(addresses)` deeply immutable?
A: No. It does not copy mutable `Address` objects.

</details>

<a id="imm-design-007"></a>

<details>
<summary><strong>IMM-DESIGN-007. How do you preserve invariants and validation in an immutable class?</strong></summary>

#### Short answer

Validate and normalize all constructor inputs before the object becomes visible, then store only valid state.

#### Interview answer

An immutable object cannot rely on later setters to fix state, so construction must establish all invariants. The constructor or factory should check required fields, normalize values and reject invalid combinations.

For example, `DateRange(start, end)` should reject `end` before `start`. `Money` should reject missing currency and may normalize amount scale.

#### Deep dive

Validation should happen before assigning or publishing state. If validation uses mutable inputs, validate the copied or normalized version that will actually be stored.

#### Production angle

Immutable value objects push validation to boundaries and reduce invalid intermediate states in services, messages and caches.

#### Traps / caveats

- Do not allow partially initialized objects to escape.
- Avoid complex I/O or database calls in value-object constructors.
- Keep validation rules close to the invariant they protect.

#### Optional Anki

Q: When should immutable object invariants be established?
A: During construction, before the object is visible.

</details>

<a id="imm-design-008"></a>

<details>
<summary><strong>IMM-DESIGN-008. What are withers and modified-copy methods in immutable models?</strong></summary>

#### Short answer

They are methods that return a new object with one or more changed values while leaving the original unchanged.

#### Interview answer

Because immutable objects do not mutate in place, an update operation returns a modified copy. A method like `withEmail(newEmail)` or `changeQuantity(qty)` creates a new instance with the requested change and the old values for everything else.

Good modified-copy methods should still validate invariants and avoid leaking mutable state.

#### Deep dive

Generic withers can be convenient for DTOs. Domain objects often benefit from intention-revealing methods such as `rescheduleTo(date)` instead of mechanical `withStartDate(date)`.

#### Production angle

Withers help keep request transformations and configuration changes explicit. For large aggregates, copying the whole graph can be expensive, so a builder or structural sharing may be better.

#### Traps / caveats

- Do not bypass constructor validation.
- Do not create ambiguous updates that break invariants.
- For records, adding many withers can signal the model is too large.

#### Optional Anki

Q: What does a wither return?
A: A new object with a modified value.

</details>

<a id="imm-design-009"></a>

<details>
<summary><strong>IMM-DESIGN-009. Why should immutable classes avoid leaking `this` from constructors?</strong></summary>

#### Short answer

Leaking `this` can expose a partially constructed object and weaken initialization safety.

#### Interview answer

During construction, the object is not fully initialized. If `this` is registered in a listener, stored in a static field, passed to another thread or used through an overridable method, another part of the program may observe incomplete state.

This is especially bad for immutable classes because their safety depends on construction completing correctly.

#### Deep dive

Final-field semantics rely on fields being set in the constructor and the constructed object not escaping prematurely. Constructor leaks can also call subclass code before subclass fields are initialized.

#### Production angle

This issue appears in dependency registration, event listeners, background tasks and framework callbacks started from constructors.

#### Traps / caveats

- Do not start threads from constructors.
- Do not call overridable methods from constructors.
- Prefer factories when registration is needed after construction.

#### Optional Anki

Q: What is a constructor leak?
A: Publishing `this` before construction has finished.

</details>

<a id="imm-design-010"></a>

<details>
<summary><strong>IMM-DESIGN-010. Why are final classes and composition often safer than inheritance for immutable models?</strong></summary>

#### Short answer

Subclasses can add mutable state or override behavior, so final classes and composition make immutability guarantees easier to enforce.

#### Interview answer

If an immutable class is extensible, a subclass can add setters, mutable fields or override getters to return changing values. That breaks callers' expectations. Making the class final prevents untrusted subclassing.

Composition is often safer because the immutable object owns its parts explicitly instead of depending on fragile superclass behavior.

#### Deep dive

If a class cannot be final, use private fields, final methods for critical accessors and clear subclassing contracts. Sealed classes can limit who may extend a type, but they do not automatically make subclasses immutable.

#### Production angle

Final value types reduce surprises in APIs, cache keys and security-sensitive objects. Framework proxies may conflict with final classes, so keep persistence entities separate when needed.

#### Traps / caveats

- A non-final immutable class must document subclass responsibilities.
- Protected mutable fields break encapsulation.
- Dynamic proxies and ORMs may require non-final types.

#### Optional Anki

Q: Why make immutable classes final?
A: To prevent subclasses from adding or exposing mutable state.

</details>
