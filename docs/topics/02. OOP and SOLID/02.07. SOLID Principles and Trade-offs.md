# 02.07. SOLID Principles and Trade-offs

---

<a id="solid-001"></a>

<details>
<summary><strong>SOLID-001. What does SOLID stand for?</strong></summary>

#### Short answer

SOLID is an acronym for five object-oriented design principles: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, and Dependency Inversion.

#### Interview answer

In an interview I would say that SOLID is not a framework and not a checklist for creating more interfaces. It is a vocabulary for discussing change, substitutability, boundaries, and dependencies.

The principles help us ask better design questions: who owns this behavior, how will it change, can this implementation replace another one, and what dependencies should point inward?

#### Deep dive

The five principles are related. SRP tries to keep responsibilities cohesive. OCP tries to let common changes happen by adding or replacing behavior instead of editing risky code. LSP protects polymorphic substitution. ISP keeps clients from depending on irrelevant operations. DIP makes high-level policy less dependent on low-level details.

#### Production angle

In production, SOLID is useful when code changes often, has multiple teams, external integrations, tests, and long-lived behavior. For a small script or stable CRUD endpoint, the simplest design may be better than a highly abstract one.

#### Traps / caveats

- Do not recite only the acronym; explain the design forces behind it.
- Do not assume more layers automatically means more SOLID.
- SOLID can reduce change cost, but it can also add abstraction cost.

#### Optional Anki

Q: What does SOLID stand for?
A: SOLID is an acronym for five object-oriented design principles: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, and Dependency Inversion.

</details>

<a id="solid-002"></a>

<details>
<summary><strong>SOLID-002. Why do we need SOLID principles at all?</strong></summary>

#### Short answer

We need SOLID as heuristics for making code easier to change, test, reason about, and extend without breaking existing behavior.

#### Interview answer

The main reason is not beauty; it is change. Backend systems keep getting new rules, integrations, persistence details, and operational constraints.

SOLID gives us names for recurring problems: classes that do too much, abstractions that are not substitutable, interfaces that force unused methods, and high-level code tied directly to low-level details.

#### Deep dive

Without design heuristics, code often grows by local patches. Each local patch can be reasonable, but together they create hidden coupling. SOLID helps move from accidental structure to intentional boundaries.

#### Production angle

A production symptom is expensive small changes: adding a new payment method touches controller, service, validation, persistence, tests, and unrelated flows. SOLID does not remove all edits, but it helps keep edits localized.

#### Traps / caveats

- SOLID is not a substitute for domain knowledge.
- For very small code, ceremony can cost more than future flexibility.
- Bad tests and unclear requirements can still break a SOLID-looking design.

#### Optional Anki

Q: Why do we need SOLID principles at all?
A: We need SOLID as heuristics for making code easier to change, test, reason about, and extend without breaking existing behavior.

</details>

<a id="solid-003"></a>

<details>
<summary><strong>SOLID-003. Are SOLID principles strict rules or design heuristics?</strong></summary>

#### Short answer

SOLID principles are design heuristics, not strict laws. They guide trade-offs and should be applied based on context, change frequency, risk, and team needs.

#### Interview answer

I would not treat a SOLID principle like a compiler rule. A design can intentionally violate one principle to gain simplicity, performance, transactional clarity, or lower operational risk.

The important part is to recognize the trade-off. A senior answer should explain why the current shape is acceptable and what signal would make us refactor later.

#### Deep dive

Heuristics are useful because design happens under uncertainty. We usually do not know every future extension point. Applying principles too early can create speculative abstractions; applying them too late can make change expensive.

#### Production angle

In code review, frame SOLID comments as risk statements: “this switch changes every release”, “this interface forces fake methods”, or “this service depends on an SDK and is hard to test,” rather than “this violates SOLID.”

#### Traps / caveats

- Do not use SOLID as a style weapon in code review.
- A simple direct dependency can be better than an unnecessary interface.
- A heuristic still needs evidence: change history, tests, complexity, and risk.

#### Optional Anki

Q: Are SOLID principles strict rules or design heuristics?
A: SOLID principles are design heuristics, not strict laws. They guide trade-offs and should be applied based on context, change frequency, risk, and team needs.

</details>

<a id="solid-004"></a>

<details>
<summary><strong>SOLID-004. What are the risks of applying SOLID mechanically?</strong></summary>

#### Short answer

Mechanical SOLID often creates too many abstractions, tiny interfaces, indirection, unnecessary patterns, and code that is harder to read than the original problem.

#### Interview answer

A common mistake is to create an interface for every class, split every method into a strategy, or wrap every dependency before there is a real variation point. The result looks flexible but becomes harder to navigate.

Another mistake is optimizing for theoretical extension while ignoring current correctness, transaction boundaries, debugging, and observability.

#### Deep dive

Mechanical SRP can fragment cohesive logic. Mechanical OCP can hide simple control flow behind polymorphism. Mechanical DIP can introduce unstable abstractions owned by the wrong layer. Mechanical ISP can produce many interfaces with no meaningful client boundary.

#### Production angle

In production, over-abstracted code slows incident response: the developer jumps through `FooService`, `FooServiceImpl`, `FooStrategyFactory`, and several adapters before finding the actual business rule.

#### Traps / caveats

- Do not split code only to satisfy a slogan.
- Do not make a domain model depend on abstractions that only mirror infrastructure classes.
- Measure readability and change cost, not just pattern count.

#### Optional Anki

Q: What are the risks of applying SOLID mechanically?
A: Mechanical SOLID often creates too many abstractions, tiny interfaces, indirection, unnecessary patterns, and code that is harder to read than the original problem.

</details>

<a id="solid-005"></a>

<details>
<summary><strong>SOLID-005. How do you decide when a SOLID violation is acceptable?</strong></summary>

#### Short answer

A SOLID violation is acceptable when the trade-off is explicit, the code is small or stable, the risk is contained, and there is a clear trigger for refactoring.

#### Interview answer

I look at change frequency, blast radius, team ownership, test coverage, and business risk. A large `switch` in one internal report generator may be fine; the same `switch` in payment routing that changes weekly is a smell.

The decision is not “is there a violation?” but “is the current cost lower than the cost of abstraction?”

#### Deep dive

Acceptable violations usually have constraints: they are local, visible, tested, and easy to replace. Dangerous violations hide inside public APIs, shared base classes, framework entry points, or code used by many teams.

#### Production angle

In a real codebase, I might leave a duplicate branch until the third variant appears, but I would add characterization tests and avoid spreading the same branch across many services.

#### Traps / caveats

- Do not justify every shortcut as pragmatism.
- Temporary violations should not become undocumented architecture.
- A violation in private code is usually less risky than a violation in a public contract.

#### Optional Anki

Q: How do you decide when a SOLID violation is acceptable?
A: A SOLID violation is acceptable when the trade-off is explicit, the code is small or stable, the risk is contained, and there is a clear trigger for refactoring.

</details>

<a id="solid-srp-001"></a>

<details>
<summary><strong>SOLID-SRP-001. What is the Single Responsibility Principle?</strong></summary>

#### Short answer

The Single Responsibility Principle says that a module or class should have one responsibility axis, often phrased as one reason to change.

#### Interview answer

SRP is about cohesion. A class should group behavior that changes for the same reason and should not mix unrelated concerns such as validation, persistence, formatting, authorization, and external calls unless it is explicitly orchestrating them.

It does not mean “one method per class.” It means the class has a clear job.

#### Deep dive

The word “responsibility” should be interpreted from the viewpoint of stakeholders and changes. Tax calculation may change because finance changes rules; JSON formatting changes because API contract changes; persistence changes because schema or storage changes.

#### Production angle

A production SRP smell is a service that must be edited for unrelated tickets. For example, `OrderService` changes for discounts, inventory, e-mail templates, metrics labels, and database migrations.

#### Traps / caveats

- Do not split responsibilities so much that simple use cases become unreadable.
- SRP applies to modules and services too, not only classes.
- A coordinator can have one responsibility: orchestration of a use case.

#### Optional Anki

Q: What is the Single Responsibility Principle?
A: The Single Responsibility Principle says that a module or class should have one responsibility axis, often phrased as one reason to change.

</details>

<a id="solid-srp-002"></a>

<details>
<summary><strong>SOLID-SRP-002. What does "one reason to change" mean?</strong></summary>

#### Short answer

“One reason to change” means that a class should be affected mainly by one kind of business, technical, or stakeholder-driven change.

#### Interview answer

It is not literally one possible edit. Any useful class can change for bugs, refactoring, or naming. The idea is that the class should not combine independent policies.

For example, a price calculator should change when pricing rules change, not when an e-mail template changes or when the persistence schema changes.

#### Deep dive

A practical test is to ask: which stakeholder asks for this change? Finance, legal, operations, API consumers, and database administrators often represent different change axes. If one class answers to too many of them, it is probably not cohesive.

#### Production angle

During refactoring, group changes by commit history. If unrelated tickets repeatedly touch the same file in different regions, that file probably contains multiple reasons to change.

#### Traps / caveats

- Do not use “one reason” as a mathematical rule.
- A reason to change is not the same as a public method.
- Sometimes a transaction boundary intentionally keeps several steps together.

#### Optional Anki

Q: What does "one reason to change" mean?
A: “One reason to change” means that a class should be affected mainly by one kind of business, technical, or stakeholder-driven change.

</details>

<a id="solid-srp-003"></a>

<details>
<summary><strong>SOLID-SRP-003. What are common SRP violations in services, controllers and entities?</strong></summary>

#### Short answer

Common SRP violations are controllers with business logic, services that validate, calculate, persist, notify, and format responses, and entities that mix domain state with infrastructure concerns.

#### Interview answer

In controllers, the usual smell is business decisions inside HTTP-specific code. In services, the smell is a large `doEverything()` method that coordinates too much and owns rules that belong in domain objects or policies.

In entities, the smell can go both ways: either entities are anemic bags of fields, or they know about repositories, JSON, Kafka, Spring beans, and database details.

#### Deep dive

A cleaner split is often: controller maps protocol concerns, application service orchestrates the use case, domain objects enforce business rules, repository persists aggregates, and adapters call external systems.

#### Production angle

In production, SRP violations increase merge conflicts, flaky tests, and risky deployments because unrelated changes concentrate in one hot class.

#### Traps / caveats

- Do not move all logic from entities into services just to keep entities “simple.”
- Do not put transport annotations and persistence behavior into pure domain objects without a conscious boundary decision.
- A service can orchestrate several collaborators and still follow SRP if orchestration is its responsibility.

#### Optional Anki

Q: What are common SRP violations in services, controllers and entities?
A: Common SRP violations are controllers with business logic, services that validate, calculate, persist, notify, and format responses, and entities that mix domain state with infrastructure concerns.

</details>

<a id="solid-ocp-001"></a>

<details>
<summary><strong>SOLID-OCP-001. What is the Open/Closed Principle?</strong></summary>

#### Short answer

The Open/Closed Principle says that software entities should be open for extension but closed for modification: new behavior should often be added without repeatedly editing stable, tested code.

#### Interview answer

OCP does not mean code is never modified. It means we identify variation points and design them so common additions happen by adding a new implementation, rule, handler, or configuration rather than changing the central algorithm every time.

For example, adding a new discount rule can mean adding a new `DiscountPolicy`, not editing a giant pricing method.

#### Deep dive

OCP relies on stable abstractions. A bad abstraction makes extension harder because every new case needs changes both in the implementation and in the abstraction. Good OCP starts from observed variation, not from guessing every future feature.

#### Production angle

In backend code, OCP is common in payment providers, notification channels, authorization policies, validators, mappers, and message handlers.

#### Traps / caveats

- Do not abstract before the variation point is real enough.
- OCP can move complexity from `if` statements into class discovery and wiring.
- Closed for modification is more important for stable shared code than for private local code.

#### Optional Anki

Q: What is the Open/Closed Principle?
A: The Open/Closed Principle says that software entities should be open for extension but closed for modification: new behavior should often be added without repeatedly editing stable, tested code.

</details>

<a id="solid-ocp-002"></a>

<details>
<summary><strong>SOLID-OCP-002. Why can large switch or if-else blocks violate OCP, and when is a switch still acceptable?</strong></summary>

#### Short answer

Large type- or mode-based branches can violate OCP because every new case requires editing the same central code. A switch is acceptable when the set of cases is small, stable, local, or intentionally exhaustive.

#### Interview answer

A branch becomes an OCP smell when it appears in many places or changes frequently. Adding one new type then requires edits in validation, calculation, mapping, persistence, and tests.

A switch is fine for simple mapping, parsing a fixed enum, handling a sealed hierarchy exhaustively, or choosing between two stable cases where polymorphism would add noise.

#### Deep dive

The decision depends on the axis of change. If the cases are domain variants with their own behavior, polymorphism or a strategy registry may fit. If the cases are just data labels with tiny differences, a switch may be clearer.

#### Production angle

In production, repeated switches are risky because teams forget one location. A central registry or strategy map can make missing support fail fast during startup or tests.

#### Traps / caveats

- Do not replace a clear switch with ten classes for two stable cases.
- Do not duplicate the same switch across layers.
- With sealed types, an exhaustive switch can be a deliberate safety mechanism, not a smell.

#### Optional Anki

Q: Why can large switch or if-else blocks violate OCP, and when is a switch still acceptable?
A: Large type- or mode-based branches can violate OCP because every new case requires editing the same central code. A switch is acceptable when the set of cases is small, stable, local, or intentionally exhaustive.

</details>

<a id="solid-ocp-003"></a>

<details>
<summary><strong>SOLID-OCP-003. How does the Strategy pattern support OCP?</strong></summary>

#### Short answer

Strategy supports OCP by encapsulating interchangeable algorithms behind a common contract, so new algorithms can be added as new implementations.

#### Interview answer

A strategy is useful when a use case has a stable context but variable behavior. The context depends on a `PricingStrategy`, `RetryPolicy`, or `FraudRule` contract and delegates the variable part.

Adding a new provider or algorithm normally means adding a class and wiring it, not rewriting the main flow.

#### Deep dive

The strategy contract must be narrow and semantic. It should say what inputs it needs, what output means, whether it may throw, whether it is idempotent, and how it handles unsupported cases.

#### Production angle

In Spring, strategies are often injected as `List<PaymentHandler>` or `Map<String, PaymentHandler>`. This can work well, but selection rules should be explicit and tested.

#### Traps / caveats

- Do not use Strategy when a simple parameter or function is enough.
- Avoid strategies that need many unrelated dependencies; that may reveal a wrong boundary.
- Make unknown or duplicate strategy keys fail fast.

#### Optional Anki

Q: How does the Strategy pattern support OCP?
A: Strategy supports OCP by encapsulating interchangeable algorithms behind a common contract, so new algorithms can be added as new implementations.

</details>

<a id="solid-lsp-001"></a>

<details>
<summary><strong>SOLID-LSP-001. What is the Liskov Substitution Principle?</strong></summary>

#### Short answer

The Liskov Substitution Principle says that objects of a subtype must be usable wherever the base type is expected without breaking the client’s correctness.

#### Interview answer

LSP is not only about inheritance syntax. It is about preserving the contract of the base type: accepted inputs, promised outputs, exceptions, side effects, state transitions, and semantic meaning.

If client code is correct with `PaymentMethod`, replacing it with `CardPaymentMethod` or `WalletPaymentMethod` should not require hidden special cases.

#### Deep dive

A subtype may add behavior, but it should not strengthen preconditions, weaken postconditions, introduce unexpected failures, or change the meaning of an inherited method. This is why “is-a” in natural language is not enough.

#### Production angle

LSP failures often appear as `instanceof` checks, `UnsupportedOperationException`, feature flags per subtype, or tests that only pass for one implementation.

#### Traps / caveats

- Do not confuse subclassing with safe subtyping.
- A subtype that compiles can still violate the behavioral contract.
- LSP applies to interfaces and abstract classes, not only class inheritance.

#### Optional Anki

Q: What is the Liskov Substitution Principle?
A: The Liskov Substitution Principle says that objects of a subtype must be usable wherever the base type is expected without breaking the client’s correctness.

</details>

<a id="solid-lsp-002"></a>

<details>
<summary><strong>SOLID-LSP-002. Give a practical example of an LSP violation.</strong></summary>

#### Short answer

A practical LSP violation is a `ReadOnlyAccount` subclass of `Account` where `withdraw()` throws `UnsupportedOperationException` even though clients of `Account` expect withdrawal to work.

#### Interview answer

Suppose `Account.withdraw(amount)` promises to either withdraw valid funds or fail only for documented business reasons such as insufficient balance. A subtype that always rejects withdrawal is not a valid substitute.

The fix may be to split the contract into `ReadableAccount` and `WithdrawableAccount`, or model read-only access as a separate view instead of a subtype.

#### Deep dive

Classic rectangle-square examples are memorable, but backend examples are usually better: mutable versus read-only repositories, sync versus async senders, idempotent versus non-idempotent clients, or collections that claim to be mutable but are not.

#### Production angle

In production, LSP violations cause runtime surprises. The type says “you can call this,” but a particular implementation fails in a path that was not obvious to the caller.

#### Traps / caveats

- Do not fix an LSP violation by adding `if (x instanceof ReadOnlyAccount)` everywhere.
- Separate capability interfaces when operations are optional.
- Document unsupported operations clearly if the interface intentionally allows them.

#### Optional Anki

Q: Give a practical example of an LSP violation.
A: A practical LSP violation is a `ReadOnlyAccount` subclass of `Account` where `withdraw()` throws `UnsupportedOperationException` even though clients of `Account` expect withdrawal to work.

</details>

<a id="solid-lsp-003"></a>

<details>
<summary><strong>SOLID-LSP-003. How can strengthening preconditions, weakening postconditions, unexpected exceptions or UnsupportedOperationException break LSP?</strong></summary>

#### Short answer

They break LSP because clients written for the base contract can no longer rely on the same inputs, outputs, guarantees, or failure modes for every subtype.

#### Interview answer

Strengthening a precondition means the subtype accepts fewer valid calls than the base type. Weakening a postcondition means it guarantees less after success. Unexpected exceptions add new failure paths the client did not agree to handle.

`UnsupportedOperationException` is especially dangerous when the base contract implies the operation is supported.

#### Deep dive

A valid subtype may relax preconditions and strengthen postconditions. For example, it may accept more input formats or return a more specific non-null result if the base contract allows it. The direction matters.

#### Production angle

In backend APIs, LSP breaks show up as special-case retries, different transaction semantics, unexpected blocking, partial writes, or an implementation that throws for a method the service assumed was safe.

#### Traps / caveats

- Do not widen checked or runtime failure semantics silently.
- Do not make a subtype require extra setup not required by the base type unless the contract says so.
- Optional operations should be modeled explicitly when clients need to know capabilities.

#### Optional Anki

Q: How can strengthening preconditions, weakening postconditions, unexpected exceptions or UnsupportedOperationException break LSP?
A: They break LSP because clients written for the base contract can no longer rely on the same inputs, outputs, guarantees, or failure modes for every subtype.

</details>

<a id="solid-lsp-004"></a>

<details>
<summary><strong>🧠 SOLID-LSP-004. How can tests or contract tests detect LSP violations?</strong></summary>

#### Short answer

Contract tests detect LSP violations by running the same behavioral test suite against every implementation of an interface or base type.

#### Interview answer

The test should express the public contract, not implementation details. If every `PaymentGateway` must reject negative amounts, be idempotent for the same request id, and map provider failures consistently, those rules become shared tests.

Each implementation supplies a factory or fixture, and the same tests run against real adapters, fakes, and in-memory versions where practical.

#### Deep dive

Contract tests are not a proof, but they catch common violations: unsupported methods, different null handling, unexpected exceptions, weaker guarantees, and inconsistent ordering or equality.

#### Production angle

For external adapters, contract tests can be combined with provider sandbox tests and consumer-driven contracts. For pure interfaces, JUnit parameterized tests often work well.

#### Traps / caveats

- Do not test only the mock; a mock may encode the caller’s assumptions rather than the real contract.
- Do not make the contract so vague that any implementation passes.
- Keep slow provider tests separate from fast in-memory contract tests when needed.

#### Optional Anki

Q: How can tests or contract tests detect LSP violations?
A: Contract tests detect LSP violations by running the same behavioral test suite against every implementation of an interface or base type.

</details>

<a id="solid-isp-001"></a>

<details>
<summary><strong>SOLID-ISP-001. What is the Interface Segregation Principle?</strong></summary>

#### Short answer

The Interface Segregation Principle says that clients should not be forced to depend on methods they do not use.

#### Interview answer

ISP is about client-specific contracts. Instead of one broad `UserService` interface with read, write, export, password, notification, and admin operations, clients may depend on narrower capabilities such as `UserReader` or `PasswordResetter`.

This reduces accidental coupling and makes implementations simpler.

#### Deep dive

ISP does not require every method to have its own interface. The interface should represent a cohesive capability used together by real clients.

For example, a read-only controller can depend on:

```java
interface UserReader {
    Optional<UserView> findById(UserId id);
}
```

while a password reset use case depends on:

```java
interface PasswordResetter {
    void resetPassword(UserId id, ResetToken token);
}
```

Neither client needs to know about exports, admin operations, or notification settings.

#### Production angle

In production, ISP helps avoid ripple effects: adding an admin method should not force read-only clients, mocks, or external adapters to change.

#### Traps / caveats

- Do not create dozens of one-method interfaces without a client boundary.
- A broad API may be fine for internal cohesive modules.
- Splitting interfaces can expose naming problems and responsibility problems.

#### Optional Anki

Q: What is a practical sign that an interface violates ISP?
A: Clients must implement, mock, or depend on methods they never use, often leading to empty methods or `UnsupportedOperationException`.

</details>

<a id="solid-isp-002"></a>

<details>
<summary><strong>SOLID-ISP-002. What is a fat interface, and how do you refactor it?</strong></summary>

#### Short answer

A fat interface is an interface with too many unrelated methods, forcing clients and implementations to know about capabilities they do not need.

#### Interview answer

A fat interface often appears as `Manager`, `Service`, or `Client` with dozens of operations. Refactoring starts by grouping methods by real clients and responsibilities.

For example, split `DocumentService` into `DocumentReader`, `DocumentWriter`, `DocumentExporter`, and `DocumentPermissionChecker` only if those are real separate capabilities in the system.

#### Deep dive

A safe migration keeps the old interface temporarily as a facade or composed interface while new code depends on narrower interfaces. Tests should confirm that behavior did not change.

For a public API, one migration path is to introduce smaller interfaces first, make the old interface extend them for compatibility, then gradually move clients to the narrower contracts:

```java
interface DocumentService extends DocumentReader, DocumentWriter, DocumentExporter {
}
```

That preserves existing callers while allowing new code to depend only on the capability it needs.

#### Production angle

This refactoring reduces mock setup, prevents empty `UnsupportedOperationException` implementations, and clarifies ownership between teams.

#### Traps / caveats

- Do not split by technical layer only; split by client need and responsibility.
- Keep backward compatibility when the interface is public.
- Too many tiny interfaces can be as confusing as one fat interface.

#### Optional Anki

Q: How can you migrate away from a fat public interface safely?
A: Introduce narrower capability interfaces, keep the old interface temporarily as a composed facade, move clients gradually, and preserve behavior with tests.

</details>

<a id="solid-dip-001"></a>

<details>
<summary><strong>SOLID-DIP-001. What is the Dependency Inversion Principle?</strong></summary>

#### Short answer

The Dependency Inversion Principle says that high-level policy should not depend directly on low-level details; both should depend on stable abstractions.

#### Interview answer

In practical Java terms, a use-case service should not be tightly coupled to an SDK, database client, HTTP library, or message broker API when those are replaceable details. The application defines a port such as `PaymentGateway`, and infrastructure implements it.

The dependency direction points toward the business policy, not toward the implementation detail.

#### Deep dive

DIP is about ownership of the abstraction. An interface placed in the low-level package and mirroring a concrete SDK may not invert anything. A useful abstraction is shaped by the high-level code’s needs.

#### Production angle

In production, DIP makes external systems replaceable, test doubles easier, and business logic less vulnerable to library churn. It is especially useful around payments, messaging, storage, identity providers, clocks, and id generators.

#### Traps / caveats

- Do not create an interface only because “DIP says so.”
- A dependency on a stable JDK type can be perfectly fine.
- The abstraction should speak the domain/application language, not the vendor API language.

#### Optional Anki

Q: What is the Dependency Inversion Principle?
A: The Dependency Inversion Principle says that high-level policy should not depend directly on low-level details; both should depend on stable abstractions.

</details>

<a id="solid-dip-002"></a>

<details>
<summary><strong>SOLID-DIP-002. What does it mean to depend on abstractions, not concretions?</strong></summary>

#### Short answer

It means client code should depend on contracts that express the behavior it needs, rather than on specific implementation classes that contain replaceable details.

#### Interview answer

A good abstraction is not just an interface keyword. It is a stable boundary: `ExchangeRateProvider.getRate()` is better for a pricing service than depending directly on `AwsSecretsManagerClient`, `HttpClient`, or a vendor SDK.

The implementation may still be concrete at runtime. The source dependency of high-level code is what we are controlling.

#### Deep dive

Abstractions can be interfaces, abstract classes, functions, records as data contracts, modules, or protocols. The right abstraction depends on what must vary and what clients actually need.

#### Production angle

In Spring, this often means constructor-injecting a port into an application service and binding the port to an adapter in configuration. The service does not know whether the adapter uses REST, gRPC, JDBC, or a fake.

#### Traps / caveats

- Do not make the abstraction more volatile than the concrete class.
- Do not expose vendor exceptions and DTOs through the abstraction unless they are part of your chosen contract.
- Depending on an interface owned by the wrong layer may still be coupling to a detail.

#### Optional Anki

Q: What does it mean to depend on abstractions, not concretions?
A: It means client code should depend on contracts that express the behavior it needs, rather than on specific implementation classes that contain replaceable details.

</details>

<details>
<summary><strong>🧠 SOLID-006. Which SOLID principle do developers most often misunderstand?</strong></summary>

#### Short answer

Developers often misunderstand DIP and SRP: DIP is not “put an interface in front of every class,” and SRP is not “one tiny class per method.”

#### Interview answer

For DIP, the misunderstanding is syntactic: people depend on an interface but the interface mirrors one implementation and is owned by the low-level layer. That gives ceremony without real inversion.

For SRP, the misunderstanding is mechanical splitting. A class can have several methods and still one responsibility if those methods support the same cohesive concept.

#### Deep dive

LSP is also often underestimated because code compiles even when behavior is not substitutable. Its failures appear later as production edge cases and special handling.

#### Production angle

A useful interview answer explains the misunderstanding and gives a code-review heuristic: ask what changes independently, who owns the abstraction, and whether all implementations preserve the same contract.

#### Traps / caveats

- Do not answer with only one principle name; explain the misunderstanding.
- An interface can increase coupling if it is unstable or poorly owned.
- A small class is not automatically cohesive.

#### Optional Anki

Q: Which SOLID principle do developers most often misunderstand?
A: Developers often misunderstand DIP and SRP: DIP is not “put an interface in front of every class,” and SRP is not “one tiny class per method.”

</details>

<a id="solid-lsp-005"></a>

<details>
<summary><strong>🧠 SOLID-LSP-005. How do Java collection wrappers expose LSP trade-offs?</strong></summary>

#### Short answer

Java collection wrappers expose LSP trade-offs because some collections share a broad interface but intentionally reject mutation operations with `UnsupportedOperationException`.

#### Interview answer

For example, a method accepting `List` may assume it can call `add()`. If the list is an unmodifiable view or fixed-size list, that call fails at runtime. The type alone did not express the mutability capability.

This is a known trade-off in the Java Collections Framework: broad interfaces are convenient, but optional operations weaken substitutability for clients that need mutation.

#### Deep dive

A safer API can accept `Collection` or `Iterable` for read-only consumption, return immutable snapshots for defensive boundaries, or document mutability requirements explicitly.

#### Production angle

In production, this causes bugs when a service mutates a collection received from another layer. Defensive copying or capability-specific APIs avoid surprises.

#### Traps / caveats

- Do not assume `List` always means mutable list.
- Returning an unmodifiable view is not the same as returning an immutable copy.
- Optional operations are acceptable only when clients understand the contract.
