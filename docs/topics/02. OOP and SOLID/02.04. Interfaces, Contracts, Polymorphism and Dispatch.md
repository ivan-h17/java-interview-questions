# 02.04. Interfaces, Contracts, Polymorphism and Dispatch

---

<a id="oop-iface-001"></a>

<details>
<summary><strong>OOP-IFACE-001. What is an interface in Java?</strong></summary>

#### Short answer

An interface in Java is a reference type that defines a contract: method signatures, constants, nested types, and, since Java 8, optional `default` and `static` methods. A class implements an interface to promise that it supports that API.

#### Interview answer

I would describe an interface as a public capability boundary. It says what clients may call and what implementors must provide, but normally does not own instance state.

For example, `PaymentGateway` can hide whether payment is handled by Stripe, an internal adapter, or a test fake. The service depends on the contract, not the concrete class.

#### Deep dive

Technically, Java interfaces can contain abstract methods, private helper methods, `default` methods, `static` methods, constants, and nested types. Interface fields are implicitly `public static final`, so they should not be used as mutable shared state.

Design-wise, the important part is the semantic contract: null handling, exceptions, idempotency, ordering, thread-safety, and side effects. A method signature alone is not enough to make a useful abstraction.

#### Production angle

In production, interfaces are useful at real variation points: external systems, algorithms, policies, persistence ports, clocks, id generators, and test seams. They are less useful when they merely mirror one class and add no stable boundary.

#### Traps / caveats

- Do not create an interface for every class by default.
- Do not treat an interface as only syntax; document the behavioral contract.
- Avoid putting mutable global state or implementation-specific constants in interfaces.

#### Optional Anki

Q: What is an interface in Java?
A: An interface defines a contract that clients can use and classes can implement; the useful part is the behavioral boundary, not just the method signatures.

</details>

<details>
<summary><strong>OOP-IFACE-002. What is an abstract class in Java?</strong></summary>

#### Short answer

An abstract class is a class that cannot be instantiated directly and may contain abstract methods, implemented methods, fields, constructors, and shared state.

#### Interview answer

An abstract class is useful when several related subclasses share code, state, construction rules, or a template algorithm. It can define common behavior and leave specific steps abstract.

For example, a base `AbstractFileImporter` might own resource handling and validation flow while subclasses parse different formats.

#### Deep dive

Unlike an interface, an abstract class participates in the single class inheritance chain. This means it can reuse implementation directly, but also couples subclasses to the base class internals and lifecycle.

A good abstract class has a small protected surface. It should define stable extension points and avoid forcing subclasses to know fragile ordering or hidden internal state.

#### Production angle

In production, abstract classes are common in framework extension points and template methods. They are risky in domain code when they become large base classes with too many hooks, because later base-class changes can break subclasses.

#### Traps / caveats

- Do not use an abstract class just to prevent instantiation; a private constructor or utility class may be clearer.
- Avoid calling overridable methods from constructors.
- Too much `protected` state often breaks encapsulation.

#### Optional Anki

Q: What is an abstract class in Java?
A: An abstract class is a partially implemented class meant to be subclassed; it can hold state and shared behavior but increases inheritance coupling.

</details>

<details>
<summary><strong>OOP-IFACE-003. When would you use an interface instead of an abstract class?</strong></summary>

#### Short answer

Use an interface when you need a capability contract independent of a class hierarchy, especially when multiple unrelated classes can provide the behavior.

#### Interview answer

I choose an interface when clients should depend on “what this object can do” rather than “what family this object belongs to”. Java classes can implement many interfaces but extend only one class, so interfaces are the natural tool for roles such as `Runnable`, `Comparator`, `Repository`, or `PaymentGateway`.

I choose an abstract class when I need shared state, construction logic, or a template algorithm that subclasses intentionally reuse.

#### Deep dive

The decision is also about evolution. Interfaces are better public API boundaries because they avoid committing clients to an inheritance hierarchy. However, adding abstract methods to a widely implemented interface is a breaking change unless a compatible `default` method is possible.

Abstract classes can evolve by adding concrete methods or fields, but they consume the subclass single-inheritance slot and can expose fragile protected internals.

#### Production angle

In backend systems, prefer interfaces for ports, adapters, policies, and use-case dependencies. Use abstract classes sparingly for framework-style reuse where subclass authors understand the lifecycle.

#### Traps / caveats

- An interface with one implementation is not automatically wrong, but it should have a reason such as a boundary or future variation.
- An abstract class is not a substitute for composition.
- A “marker” interface without behavior needs strong justification.

#### Optional Anki

Q: When would you use an interface instead of an abstract class?
A: Prefer an interface for independent capabilities and multiple implementations; prefer an abstract class for intentional shared implementation and state.

</details>

<details>
<summary><strong>🧠 OOP-IFACE-004. What is an interface or object contract?</strong></summary>

#### Short answer

An interface or object contract is the full set of promises clients can rely on: methods, valid inputs, outputs, state changes, exceptions, side effects, ordering, and semantic meaning.

#### Interview answer

In interviews I separate syntax from contract. Syntax says `charge(Money)`; the contract says whether zero money is allowed, whether the call is idempotent, what happens on timeout, whether it reserves or captures funds, and what exceptions mean.

A class contract can also include invariants: for example, an `Order` never has a negative total and cannot be paid twice.

#### Deep dive

Contracts exist even when they are not written down. The problem is that undocumented contracts become tribal knowledge and are easy to break during refactoring.

Contracts may be expressed through names, types, validation, checked or unchecked exceptions, Javadoc, tests, API docs, package boundaries, and monitoring assumptions. The stronger the boundary, the more explicit the contract should be.

#### Production angle

In production, contract clarity reduces integration bugs. Public interfaces, domain objects, REST APIs, message schemas, and persistence ports should be explicit about nullability, errors, retries, transactional behavior, and compatibility.

#### Traps / caveats

- Method names alone rarely describe the whole contract.
- Tests document examples but do not replace a clear semantic contract.
- Changing behavior without changing signatures can still be a breaking change.

#### Optional Anki

Q: What is an interface or object contract?
A: A contract is everything a caller may safely rely on, not just the Java signature.

</details>

<details>
<summary><strong>🧠 OOP-IFACE-005. Why can a badly designed interface be worse than no interface?</strong></summary>

#### Short answer

A bad interface creates a false abstraction: it adds indirection while exposing the wrong operations, leaking implementation details, or forcing clients and implementors into unstable assumptions.

#### Interview answer

An interface is a promise. If the promise is wrong, every implementation and every caller pays for it. For example, a generic `StorageService` with `save(Object)` and `find(String)` may hide important differences: transactions, consistency, identity, serialization, and error behavior.

No interface can be better than a premature interface because concrete code is easier to refactor before many consumers depend on an accidental contract.

#### Deep dive

Bad interfaces often come from abstracting nouns instead of behaviors. They are too broad, too generic, too coupled to one implementation, or too low-level for clients. A strong interface is cohesive, named in the language of the caller, and hides a real design decision.

Interface Segregation matters here: clients should not depend on methods they do not use. But over-segmentation can also create a maze of tiny roles with no meaningful boundary.

#### Production angle

In production, bad interfaces slow changes because every fix becomes a compatibility discussion. They also make tests misleading: mocks may verify calls to a bad abstraction instead of proving useful behavior.

#### Traps / caveats

- “Interface for testability” can produce mock-friendly but domain-poor design.
- Too generic interfaces often lose type safety and semantic meaning.
- A leaky interface can be harder to remove than a concrete dependency.

#### Optional Anki

Q: Why can a badly designed interface be worse than no interface?
A: A bad interface freezes the wrong contract; no interface is often easier to refactor until a real boundary appears.

</details>

<details>
<summary><strong>🧠 OOP-IFACE-006. What are default methods in interfaces, and what are their trade-offs?</strong></summary>

#### Short answer

A default method is an interface method with a body. It lets an interface provide reusable behavior and evolve without forcing every existing implementor to add the new method immediately.

#### Interview answer

Default methods are useful for backward-compatible API evolution and small convenience behavior. For example, an interface can add `isEmpty()` implemented through `size()`.

The trade-off is that interfaces start to contain implementation decisions. Too many default methods can turn an interface into a hidden base class and make conflicts or surprising inheritance behavior more likely.

#### Deep dive

Default methods cannot hold instance fields, so nontrivial stateful behavior still belongs in classes or composed collaborators. They also interact with multiple interface inheritance: if two interfaces provide incompatible defaults for the same method, the implementing class usually must resolve the conflict explicitly.

A default method should depend only on the interface’s own stable abstract operations and should not assume hidden implementation details.

#### Production angle

In library and platform APIs, default methods are valuable for compatible evolution. In application code, use them sparingly: prefer them for simple derived operations, not for business workflows with dependencies, state, or transactions.

#### Traps / caveats

- A default method is not a replacement for an abstract class.
- Adding a default method can still change behavior if implementors already had similarly named inherited methods.
- Default methods should not hide expensive or side-effecting behavior behind harmless-looking helpers.

#### Optional Anki

Q: What are default methods in interfaces, and what are their trade-offs?
A: Default methods add interface behavior for compatibility and convenience, but too many of them turn a contract into a fragile implementation mixin.

</details>

<details>
<summary><strong>OOP-IFACE-008. What is polymorphism?</strong></summary>

#### Short answer

Polymorphism is the ability to use different concrete objects through the same contract, so the same call can execute different behavior depending on the actual object.

#### Interview answer

In Java, the most common form is subtype polymorphism: a variable of type `PaymentMethod` may reference `CardPayment`, `WalletPayment`, or `BankTransferPayment`. Calling `pay()` dispatches to the implementation of the actual object.

This is useful because clients can depend on a stable abstraction and new behavior can be added by adding new implementations instead of editing every caller’s `if`/`switch` logic.

#### Deep dive

Polymorphism is not only “inheritance”. Java supports it through interfaces, abstract classes, concrete class inheritance, generics, lambdas for functional interfaces, and method overloading in a different compile-time sense.

Good polymorphism requires substitutability: each implementation must honor the base contract. Otherwise polymorphism just hides broken special cases behind a common type.

#### Production angle

In production, polymorphism is valuable for strategies, pricing rules, validators, parsers, integrations, and authorization policies. It is less helpful when there is no real variation or when all implementations need many type checks.

#### Traps / caveats

- Do not replace every conditional with polymorphism; simple branching may be clearer.
- Polymorphism without a strong contract leads to surprising implementations.
- Downcasting after introducing polymorphism usually means the abstraction is wrong or incomplete.

#### Optional Anki

Q: What is polymorphism?
A: Polymorphism lets clients call one contract while runtime implementations provide the specific behavior.

</details>

<details>
<summary><strong>OOP-IFACE-009. What is dynamic dispatch, and how is it different from static binding?</strong></summary>

#### Short answer

Dynamic dispatch chooses the overridden instance method at runtime based on the actual object type. Static binding is resolved at compile time, for example overloaded methods, static methods, private methods, and field access.

#### Interview answer

If `PaymentMethod pm = new CardPayment()` and code calls `pm.pay()`, Java uses the runtime class `CardPayment` to choose the overridden `pay()`. That is dynamic dispatch.

By contrast, overloaded methods are selected from the compile-time types of arguments. A call to `print(Object)` versus `print(String)` is chosen before runtime overriding lookup.

#### Deep dive

Dynamic dispatch enables runtime polymorphism and substitutability. Static binding makes calls simpler and sometimes more predictable, but it does not provide runtime variation.

Java has specific lookup rules: first the compiler determines which method signature is invoked, then runtime dispatch chooses the implementation for overridable instance methods. This distinction explains many interview puzzles around overloads, overrides, `null`, and casts.

#### Production angle

In production, understanding dispatch helps debug plugin systems, framework callbacks, proxies, AOP, and mocking. It also helps avoid misleading APIs where overloads look polymorphic but behave according to compile-time types.

#### Traps / caveats

- Fields are not overridden polymorphically like methods.
- `static` methods are hidden, not overridden.
- A cast changes the compile-time type used for overload selection, but not the runtime object used for overriding.

#### Optional Anki

Q: What is dynamic dispatch, and how is it different from static binding?
A: Overriding is runtime dispatch; overloading and static members are chosen by compile-time rules.

</details>

<details>
<summary><strong>OOP-IFACE-010. What is the difference between method overriding and method overloading?</strong></summary>

#### Short answer

Overriding replaces inherited instance behavior in a subtype with the same method signature. Overloading defines multiple methods with the same name but different parameter lists, selected at compile time.

#### Interview answer

Overriding supports runtime polymorphism: a `List` reference can call an overridden method on an `ArrayList` object. Overloading is API convenience: `send(Message)`, `send(Message, Timeout)`, and `send(String)` are different methods with a shared name.

The key interview point: overriding depends on the runtime receiver; overloading depends on compile-time argument types and most-specific method selection.

#### Deep dive

An overriding method must follow Java compatibility rules: same signature, compatible return type, no broader checked exceptions, and at least as visible as the base method. `@Override` should be used to let the compiler catch mistakes.

Overloading can become confusing with `null`, boxing, varargs, generics, and inheritance. A clear API often prefers differently named methods when overloads would encode different semantics.

#### Production angle

In production code, overriding is useful for extension points and polymorphic models. Overloading is useful for ergonomic constructors/factories, but excessive overloading makes call sites ambiguous and refactoring risky.

#### Traps / caveats

- Do not confuse overriding with hiding `static` methods.
- Changing a parameter type creates an overload, not an override.
- Overloads with `null` can be ambiguous or select a surprising method.

#### Optional Anki

Q: What is the difference between method overriding and method overloading?
A: Overriding is same signature plus runtime receiver; overloading is same name plus different parameters selected at compile time.

</details>

<details>
<summary><strong>🧠 OOP-IFACE-011. How do preconditions, postconditions and semantic contracts relate to interface design?</strong></summary>

#### Short answer

Preconditions say what callers must satisfy before a call; postconditions say what the implementation guarantees after success; semantic contracts describe the business meaning of those promises.

#### Interview answer

For an interface, signatures are only the shape. Preconditions and postconditions are the behavior. For example, `reserve(sku, quantity)` might require positive quantity and existing SKU, and guarantee either a reservation id or a specific failure with no partial reservation.

These rules determine whether implementations are substitutable. A subtype should not require stronger preconditions or provide weaker postconditions than the interface promises.

#### Deep dive

Semantic contracts include idempotency, transactional boundaries, timeouts, retries, consistency, ordering, authorization assumptions, and error classification. These are especially important for distributed systems because method signatures do not express network or storage failure modes.

A good contract moves ambiguity out of caller code. Callers should not need to read every implementation to know whether they can retry, whether a result is cached, or whether a method mutates state.

#### Production angle

In production, unclear pre/postconditions cause inconsistent validation, retry storms, partial writes, and incompatible implementations. For important interfaces, express contracts with types, validation, Javadoc, tests, and operational runbooks.

#### Traps / caveats

- Do not put all validation responsibility on callers if the implementation can protect itself cheaply.
- Do not make postconditions depend on undocumented timing or environment assumptions.
- A method returning `boolean` often hides too many failure reasons.

#### Optional Anki

Q: How do preconditions, postconditions and semantic contracts relate to interface design?
A: Preconditions and postconditions make an interface contract precise enough for callers and implementors to be substitutable.

</details>

<details>
<summary><strong>🧠 OOP-IFACE-012. How can default interface methods create conflicts?</strong></summary>

#### Short answer

Default methods can conflict when a class inherits two incompatible defaults with the same signature, or when interface defaults interact with class methods and inheritance rules.

#### Interview answer

The classic example is `interface A { default void log() {} }` and `interface B { default void log() {} }`. A class implementing both `A` and `B` must usually override `log()` and decide which behavior, if any, to call.

Java also gives class methods priority over interface defaults. This avoids some ambiguity but can surprise developers who expect an interface default to override inherited class behavior.

#### Deep dive

Conflicts become more subtle in larger hierarchies where one interface refines another, or where a library adds a new default method with a name already used by implementations. Even source-compatible changes can alter behavior or create compilation failures for downstream classes.

The safest default methods are small, derived, and based only on existing abstract methods of the same interface. They should not act as broad mixins with independent behavior.

#### Production angle

In production libraries, adding default methods requires compatibility analysis and tests against representative implementations. In application code, resolve conflicts explicitly and prefer clear class methods when business semantics differ.

#### Traps / caveats

- A conflict is not only a compiler error; it can also be a surprising inherited behavior.
- Calling `A.super.method()` ties the class to a specific interface default.
- Default-method conflicts often reveal interfaces with overlapping responsibilities.

#### Optional Anki

Q: How can default interface methods create conflicts?
A: If two inherited defaults define the same method, the class must often resolve the ambiguity explicitly; class methods generally win over interface defaults.

</details>
