# 02.05. Inheritance, Composition and Delegation

---

<a id="oop-inher-001"></a>

<details>
<summary><strong>OOP-INHER-001. What is inheritance?</strong></summary>

#### Short answer

Inheritance is a mechanism where one type is defined in terms of another type, so a subclass can reuse, specialize, or extend behavior from a superclass and can be treated as that superclass type.

#### Interview answer

In Java, a class can extend one superclass and implement multiple interfaces. Inheritance gives two things that are often mixed together: implementation reuse and subtype polymorphism.

For example, `ArrayList` is a subtype of `List`, but implementation reuse through a base class is a different design decision from exposing a substitutable public type.

#### Deep dive

Inheritance is powerful because it can model “is-a” relationships and enable dynamic dispatch. It is dangerous because the subclass depends on base-class behavior, initialization order, protected state, and undocumented extension points.

A good inheritance design has a stable base contract, clear hooks, and real substitutability. Without those, composition and delegation are usually safer.

#### Production angle

In production, use inheritance carefully for framework extension points, closed domain taxonomies, and stable polymorphic models. Avoid using it just to share a few helper methods.

#### Traps / caveats

- “Is-a” in natural language is not enough; the subtype must honor the base contract.
- Inheritance exposes subclasses to base-class changes.
- Deep inheritance hierarchies are hard to reason about and test.

#### Optional Anki

Q: What is inheritance?
A: Inheritance combines subtype polymorphism with possible implementation reuse; good inheritance requires substitutability and a stable base contract.

</details>

<a id="oop-inher-002"></a>

<details>
<summary><strong>🧠 OOP-INHER-002. What is the difference between subclassing and subtyping?</strong></summary>

#### Short answer

Subclassing is a language mechanism for extending a class. Subtyping is a type relationship where one type can be safely used wherever another type is expected.

#### Interview answer

In Java, `class B extends A` creates both a subclass relationship and usually a subtype relationship. But conceptually they are not the same: subclassing is about implementation structure, while subtyping is about the public contract and substitutability.

Interfaces make this distinction clearer. A class can be a subtype of `Comparable` without sharing implementation with other comparable classes.

#### Deep dive

The important design point is that subtype promises should be behavioral, not only syntactic. If `Square` extends `Rectangle` but cannot support independent width and height changes, the subclass may violate the expected rectangle contract.

Some languages support subtyping without subclassing more directly; in Java, interfaces are the main tool for separating role subtyping from class inheritance.

#### Production angle

In production, confusing subclassing with subtyping leads to APIs that accept a base class but then need type checks, downcasts, and special cases. That is a sign the type hierarchy does not match behavior.

#### Traps / caveats

- Do not subclass just to reuse code if the object is not behaviorally substitutable.
- Do not assume every subtype should inherit implementation.
- A subtype can weaken the design if it narrows what callers may safely do.

#### Optional Anki

Q: What is the difference between subclassing and subtyping?
A: Subclassing is implementation inheritance; subtyping is substitutable use through a contract.

</details>

<a id="oop-inher-003"></a>

<details>
<summary><strong>OOP-INHER-003. How does Java support multiple inheritance of type, and how does it avoid multiple inheritance of implementation?</strong></summary>

#### Short answer

Java supports multiple inheritance of type because a class can implement multiple interfaces. It avoids general multiple inheritance of implementation because a class can extend only one class.

#### Interview answer

A class can be both `Runnable`, `Closeable`, and `Comparable` because these are roles or contracts. But it cannot extend two concrete classes such as `FileInputStream` and `Thread`.

Default interface methods add limited implementation inheritance, but they do not add instance fields and Java has conflict-resolution rules when defaults collide.

#### Deep dive

The main avoided problem is ambiguity: if two base classes provide state, constructors, and methods with the same signature, it is hard to define which state and behavior the child owns. Java chooses single class inheritance plus interfaces and composition.

This design pushes reusable behavior toward composition, helper classes, and default methods for simple derived operations.

#### Production angle

In production, model multiple roles with interfaces and share substantial implementation through delegation. This keeps object state ownership explicit and avoids base-class entanglement.

#### Traps / caveats

- Default methods mean interfaces are not purely abstract anymore, but they are still not full multiple implementation inheritance.
- Interfaces with conflicting defaults may force explicit override.
- Composition is often the right answer when you want behavior from multiple sources.

#### Optional Anki

Q: How does Java support multiple inheritance of type, and how does it avoid multiple inheritance of implementation?
A: Java allows many implemented interfaces but only one extended class; shared stateful implementation should usually come through composition.

</details>

<a id="oop-inher-004"></a>

<details>
<summary><strong>OOP-INHER-004. Why can inheritance break encapsulation?</strong></summary>

#### Short answer

Inheritance can break encapsulation because subclasses depend on and can be affected by superclass implementation details, especially protected state, overridable hooks, and internal method call order.

#### Interview answer

A normal client sees only the public contract. A subclass often sees more: protected methods, protected fields, lifecycle hooks, and sometimes assumptions about when base methods are called.

If the base class changes its internal algorithm, a subclass override may now be called in a different order or with different intermediate state. The public API did not change, but the subclass broke.

#### Deep dive

This is sometimes called inheritance exposing a second, less explicit API: the subclassing API. If that API is not designed and documented, subclass authors reverse-engineer it from current implementation.

Final methods, private state, small protected APIs, composition, and clear template methods can reduce the risk.

#### Production angle

In production, this matters when framework base classes or shared domain base classes evolve. A harmless optimization in a superclass can break subclasses in other teams or services.

#### Traps / caveats

- `protected` is not “almost private”; it is part of the subclass contract.
- Overridable methods called from base methods can expose internal timing.
- Adding a new overridable method can create unexpected subclass interactions.

#### Optional Anki

Q: Why can inheritance break encapsulation?
A: Inheritance breaks encapsulation when subclasses depend on superclass internals rather than only on a stable contract.

</details>

<a id="oop-inher-005"></a>

<details>
<summary><strong>🧠 OOP-INHER-005. What is the fragile base class problem?</strong></summary>

#### Short answer

The fragile base class problem is when changes to a superclass accidentally break subclasses, even though the superclass public API still looks compatible.

#### Interview answer

It happens because subclasses are coupled to implementation details: which methods call which hooks, how state is initialized, and what side effects happen internally. A base class can add a call, reorder operations, or cache a result and unintentionally violate subclass assumptions.

The classic symptom is that a base class evolves reasonably for its own tests, but unknown subclasses in applications or downstream libraries start failing.

#### Deep dive

This is a deeper problem than binary compatibility. The code may still compile and link, but behavior changes. That makes the problem hard to detect without tests covering real subclasses.

Good base classes are designed for inheritance: they define a clear subclass contract, restrict extension points, document call order, and often make non-extension methods `final`. If a class is not designed for inheritance, it should often be final or have no accessible constructors.

#### Production angle

In production, fragile base classes are common in shared internal libraries. Teams can reduce risk with composition, sealed hierarchies, narrow protected APIs, contract tests, and release notes for subclassing behavior changes.

#### Traps / caveats

- Passing unit tests for the base class is not enough.
- A protected hook is a compatibility commitment.
- Framework-style inheritance should be treated like public API design.

#### Optional Anki

Q: What is the fragile base class problem?
A: Fragile base class means superclass implementation changes can break subclass behavior without obvious signature changes.

</details>

<a id="oop-inher-006"></a>

<details>
<summary><strong>OOP-INHER-006. Why should constructors not call overridable methods?</strong></summary>

#### Short answer

Constructors should not call overridable methods because the subclass part of the object is not initialized yet, but dynamic dispatch can call the subclass override.

#### Interview answer

When a superclass constructor runs, Java can dispatch an overridable method call to the subclass implementation. That implementation may read subclass fields that still have default values, use dependencies not assigned yet, or publish `this` too early.

This creates bugs that are hard to see because the call happens before the subclass constructor body starts.

#### Deep dive

Safe construction should establish invariants before overridable behavior runs. If customization is needed, prefer constructor parameters, factories, composition, non-overridable private/final helper methods, or a separate initialization method controlled by a framework after construction.

Even a method that seems harmless today may become unsafe after a subclass override is added later.

#### Production angle

In production, this bug appears in framework entities, UI components, test base classes, and dependency-heavy services. It can cause null pointer exceptions, broken metrics registration, or partially initialized objects escaping to other threads.

#### Traps / caveats

- Calling a `final`, `private`, or `static` helper from a constructor is different because it is not overridden.
- Do not start threads or register callbacks from constructors unless construction is fully safe.
- Avoid relying on subclass fields during superclass construction.

#### Optional Anki

Q: Why should constructors not call overridable methods?
A: Overridable calls from constructors can dispatch to subclass code before the subclass state is initialized.

</details>

<a id="oop-inher-007"></a>

<details>
<summary><strong>OOP-INHER-007. What does the final keyword mean for classes and methods?</strong></summary>

#### Short answer

For a class, `final` means it cannot be subclassed. For a method, `final` means subclasses cannot override it.

#### Interview answer

A `final` class communicates that inheritance is not part of its contract. This can protect invariants, simplify reasoning, and avoid fragile subclasses. Many value objects and security-sensitive types are good candidates.

A `final` method allows a class to expose stable behavior while still permitting subclassing elsewhere. It is common in template-method designs where the outer algorithm is fixed and only specific hooks are overridable.

#### Deep dive

`final` is a design boundary. It says: clients may use this class, but they may not specialize it through inheritance. This is often preferable unless the class was explicitly designed and documented for extension.

Do not confuse final classes/methods with final variables. A final variable cannot be reassigned, but the referenced object may still be mutable unless the object itself is immutable.

#### Production angle

In production, `final` helps maintain invariants in domain objects, value objects, and library APIs. The trade-off is reduced mocking/subclassing flexibility, usually solved through interfaces or composition rather than making everything open.

#### Traps / caveats

- Do not remove `final` casually from shared APIs; it changes the extension contract.
- A final class can still implement interfaces.
- Final does not make object state immutable.

#### Optional Anki

Q: What does the final keyword mean for classes and methods?
A: Final on a class forbids subclassing; final on a method forbids overriding and helps preserve a stable algorithm or invariant.

</details>

<a id="oop-inher-008"></a>

<details>
<summary><strong>OOP-INHER-008. When is inheritance a good or bad design choice?</strong></summary>

#### Short answer

Inheritance is good when there is a stable “is-a” relationship, real substitutability, and intentionally shared behavior. It is bad when used only for convenience, code reuse, or accidental similarity.

#### Interview answer

Good inheritance has a base type that defines a contract all subclasses can honor. Examples include closed taxonomies, framework base classes with documented hooks, or domain hierarchies where all variants share lifecycle and behavior.

Bad inheritance appears when a subclass must disable base behavior, override methods to throw `UnsupportedOperationException`, depend on call order, or require callers to check concrete type.

#### Deep dive

The question is not “is it an is-a relationship in English?” but “can every subclass be used safely under the base contract?” If the answer is no, prefer composition, delegation, strategy, or separate interfaces.

Modern Java also offers records, enums, and sealed classes that can model many cases more explicitly than open inheritance.

#### Production angle

In production, choose inheritance when the hierarchy is stable and owned by the same team or has a clear public extension contract. Avoid it across volatile business concepts where rules and combinations change frequently.

#### Traps / caveats

- Inheritance locks design decisions into the type hierarchy.
- Deep hierarchies make debugging behavior difficult.
- Composition can model multiple independent dimensions better than inheritance.

#### Optional Anki

Q: When is inheritance a good or bad design choice?
A: Use inheritance for stable substitutable hierarchies; avoid it for incidental reuse or changing combinations of behavior.

</details>

<a id="oop-inher-010"></a>

<details>
<summary><strong>OOP-INHER-010. When is composition better than inheritance?</strong></summary>

#### Short answer

Composition is better when behavior should be assembled from independent parts, varied at runtime, tested separately, or changed without exposing superclass internals.

#### Interview answer

With composition, an object holds collaborators and delegates work to them. For example, `OrderService` can use a `DiscountPolicy`, `TaxCalculator`, and `PaymentGateway` instead of inheriting from a giant base service.

This avoids the single-inheritance limitation and makes each behavior replaceable. It also keeps state ownership clearer because each collaborator owns its own rules.

#### Deep dive

Composition is especially useful when there are multiple axes of variation. A product can vary by pricing, delivery, promotion, and tax rules. Modeling all combinations as subclasses creates a combinatorial explosion.

Inheritance may still be appropriate for a stable family. Composition is not automatically better; it can add indirection. The senior-level decision is about which boundary changes independently.

#### Production angle

In production, composition works well with dependency injection, testing, feature flags, strategy selection, adapters, and clean architecture ports. It is usually safer for evolving business logic than a shared base class.

#### Traps / caveats

- Too many tiny composed objects can make control flow hard to follow.
- Composition still needs clear contracts; otherwise it becomes dependency soup.
- Do not compose infrastructure dependencies directly into rich domain objects if it pollutes the domain model.

#### Optional Anki

Q: When is composition better than inheritance?
A: Composition is better when parts vary independently; inheritance is better only when the base relationship is stable and substitutable.

</details>

<details>
<summary><strong>🧠 OOP-INHER-011. What is delegation, and how is it different from inheritance?</strong></summary>

#### Short answer

Delegation means an object handles a request by forwarding part of the work to another object. Inheritance gets behavior from a superclass; delegation uses a collaborator.

#### Interview answer

For example, a `CachingUserRepository` can implement `UserRepository` and delegate cache misses to a real `JdbcUserRepository`. The caching class adds behavior without becoming a subclass of the JDBC implementation.

Delegation is often used in decorators, adapters, proxies, strategies, and facades.

#### Deep dive

The main difference is coupling direction. With inheritance, the subclass is coupled to base-class implementation and lifecycle. With delegation, the delegating object depends on a collaborator contract and can often swap it at construction time or runtime.

Delegation can preserve encapsulation better because the collaborator’s internals remain private. The delegating object chooses what to expose.

#### Production angle

In production, delegation is the default way to add cross-cutting or optional behavior: caching, retries, metrics, authorization checks, validation, and external API adapters.

#### Traps / caveats

- Delegation can become boilerplate when many methods are simply forwarded.
- A delegating wrapper must preserve the delegate contract.
- Hidden delegation chains can make debugging difficult if naming and tracing are poor.

#### Optional Anki

Q: What is delegation, and how is it different from inheritance?
A: Delegation forwards work to a collaborator; inheritance acquires behavior from a superclass.

</details>

<a id="oop-inher-013"></a>

<details>
<summary><strong>🧠 OOP-INHER-013. What is the difference between association, aggregation and composition?</strong></summary>

#### Short answer

Association is a general relationship between objects. Aggregation is a weak whole-part relationship where parts can outlive the whole. Composition is a strong ownership relationship where parts conceptually belong to the whole.

#### Interview answer

A `Customer` associated with an `Order` means they are related. A `Team` aggregating `Employee` objects means employees can exist without the team. An `Order` composed of `OrderLine` objects means lines normally do not have a meaningful independent lifecycle outside the order.

In code, these are design meanings, not just field declarations. A field can represent any of them depending on lifecycle, ownership, and invariants.

#### Deep dive

Composition is often aligned with aggregate boundaries in DDD: the root controls child objects and protects consistency. Aggregation is weaker and more ambiguous; many teams avoid using the term unless UML precision is needed.

The practical questions are: who creates the child, who can modify it, who deletes it, can it be shared, and where are invariants enforced?

#### Production angle

In production, the distinction affects persistence cascading, REST resource design, event ownership, concurrency, and transaction boundaries. Mistaking a shared entity for a composed child can cause accidental deletes or duplicated state.

#### Traps / caveats

- Do not infer composition only from a Java field.
- Aggregation is often too vague; clarify lifecycle and ownership instead.
- Database foreign keys do not automatically define object ownership.

#### Optional Anki

Q: What is the difference between association, aggregation and composition?
A: Association is any link; aggregation is weak whole-part; composition is strong ownership with a dependent lifecycle.

</details>

<details>
<summary><strong>🧠 OOP-INHER-014. How can composition lead to too many small objects?</strong></summary>

#### Short answer

Composition can lead to too many small objects when every tiny rule or step becomes its own class without a clear responsibility, stable contract, or reuse point.

#### Interview answer

Composition is a tool, not a goal. If a use case has ten collaborators named `Helper`, `Resolver`, `Processor`, and `Manager`, the design may be split by implementation steps rather than responsibilities.

The result is excessive indirection: to understand one business operation, a developer must jump through many files that each contain one trivial method.

#### Deep dive

This is sometimes the opposite smell of a god object. Instead of one large class, logic is scattered across many tiny abstractions. Both problems come from unclear boundaries.

A good split has a name from the domain or architecture, a reason to change independently, and a contract that helps callers. If a class cannot be named without generic words, it may not deserve to exist yet.

#### Production angle

In production, too many micro-objects increase onboarding cost, tracing complexity, DI configuration, test setup, and mock count. Start with clear cohesive classes, then extract collaborators when there is real independent change or duplication.

#### Traps / caveats

- Small is not automatically cohesive.
- A class extracted only to make a method shorter may not improve design.
- Too many mocks in a unit test often reveal over-composition or wrong boundaries.

#### Optional Anki

Q: How can composition lead to too many small objects?
A: Composition becomes harmful when it creates indirection without independent responsibility or a useful contract.

</details>
