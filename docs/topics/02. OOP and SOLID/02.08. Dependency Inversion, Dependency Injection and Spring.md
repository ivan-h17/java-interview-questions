# 02.08. Dependency Inversion, Dependency Injection and Spring

---

<a id="oop-di-001"></a>

<details>
<summary><strong>OOP-DI-001. What is the difference between DIP, dependency injection and IoC?</strong></summary>

#### Short answer

DIP is a design principle, dependency injection is a technique for providing dependencies from outside, and IoC is a broader idea where control of creation or flow is delegated to a container or framework.

#### Interview answer

DIP answers the design question: which direction should source dependencies point? DI answers the construction question: how does an object receive its collaborators? IoC answers the control question: who creates and wires objects or calls application code?

Spring provides an IoC container and supports DI, but using Spring annotations does not automatically mean your design follows DIP.

#### Deep dive

You can have DI without DIP: a service can receive a concrete vendor client through its constructor and still be tightly coupled to the vendor. You can also follow DIP without a container by manually wiring ports and adapters in `main()` or tests.

#### Production angle

In production, confusing these concepts leads to false confidence: the code is injectable, but business logic still imports SDK classes, framework exceptions, or persistence APIs.

#### Traps / caveats

- Do not say “DIP means dependency injection.”
- Do not assume IoC containers are required for clean architecture.
- Constructor injection improves explicitness, but the abstraction still has to be well designed.

#### Optional Anki

Q: What is the difference between DIP, dependency injection and IoC?
A: DIP is a design principle, dependency injection is a technique for providing dependencies from outside, and IoC is a broader idea where control of creation or flow is delegated to a container or framework.

</details>

<details>
<summary><strong>OOP-DI-002. How does constructor injection support DIP?</strong></summary>

#### Short answer

Constructor injection supports DIP by making required collaborators explicit and allowing high-level code to receive abstractions instead of constructing low-level details itself.

#### Interview answer

A class with constructor-injected dependencies states its needs in one place. This makes the dependency graph visible, enables immutable required dependencies, and simplifies tests.

For example, `CheckoutService(PaymentGateway gateway, Clock clock)` depends on capabilities. It does not call `new StripeClient()` or `Instant.now()` deep inside business logic.

#### Deep dive

Constructor injection also reveals design smells. If a constructor has fifteen unrelated dependencies, the class probably has too many responsibilities or is doing too much orchestration.

#### Production angle

In Spring, constructor injection is usually preferred for mandatory dependencies because beans are created fully initialized and required dependencies can be `final`.

#### Traps / caveats

- Constructor injection does not fix a bad abstraction.
- Too many constructor parameters are a signal, not a reason to switch to field injection.
- Optional dependencies may still be modeled with configuration objects or explicit optional collaborators.

#### Optional Anki

Q: How does constructor injection support DIP?
A: Constructor injection supports DIP by making required collaborators explicit and allowing high-level code to receive abstractions instead of constructing low-level details itself.

</details>

<a id="oop-di-003"></a>

<details>
<summary><strong>OOP-DI-003. How does field injection make dependencies less explicit?</strong></summary>

#### Short answer

Field injection hides dependencies inside private fields set by a framework, so the constructor no longer shows what the object needs to be valid.

#### Interview answer

With field injection, the class can be constructed in an invalid state outside the container. Tests often need reflection or Spring context just to create the object. Required dependencies cannot naturally be `final`.

This weakens the object’s invariant: after construction, the object is not necessarily ready to use.

#### Deep dive

Field injection also hides dependency count. A class with many injected fields looks less alarming than a constructor with the same dependencies, so responsibility problems remain hidden longer.

#### Production angle

In production, field injection makes plain unit tests harder and encourages tests that start a full Spring context for logic that could be tested as a normal object.

#### Traps / caveats

- Do not use field injection to hide constructor bloat.
- Field injection can be acceptable in rare framework glue, but it is a poor default for application and domain services.
- Do not confuse private fields with encapsulated dependencies.

#### Optional Anki

Q: How does field injection make dependencies less explicit?
A: Field injection hides dependencies inside private fields set by a framework, so the constructor no longer shows what the object needs to be valid.

</details>

<details>
<summary><strong>OOP-DI-004. Why is depending on an interface not automatically DIP?</strong></summary>

#### Short answer

Depending on an interface is not automatically DIP because the interface may be unstable, owned by the wrong layer, or merely mirror one concrete implementation.

#### Interview answer

DIP is about dependency direction and abstraction ownership. If `OrderService` depends on `StripePaymentClientInterface` from the infrastructure package, the business service still speaks the vendor language.

A better port might be `PaymentGateway` in the application boundary with methods and errors shaped by the checkout use case.

#### Deep dive

An interface can be worse than a concrete class when it adds a fake abstraction that changes together with the implementation. Then callers depend on two names instead of one design boundary.

#### Production angle

In code reviews, check package direction: can the domain or application module compile without infrastructure? If not, the interface may not be providing real inversion.

#### Traps / caveats

- Do not name interfaces after implementation details.
- A single stable concrete class can be cleaner than a one-to-one unstable interface.
- The abstraction should be defined by client needs, not by vendor API shape.

#### Optional Anki

Q: Why is depending on an interface not automatically DIP?
A: Depending on an interface is not automatically DIP because the interface may be unstable, owned by the wrong layer, or merely mirror one concrete implementation.

</details>

<details>
<summary><strong>OOP-DI-005. When is it okay to depend on a concrete class?</strong></summary>

#### Short answer

It is okay to depend on a concrete class when it is stable, local, simple, not a replaceable policy, and does not drag in volatile infrastructure concerns.

#### Interview answer

Examples include value objects, records, domain entities, small pure helpers, JDK classes, and internal classes that are not expected to vary independently.

Creating an interface for every one of them only adds indirection and mock-heavy tests.

#### Deep dive

The key question is whether the dependency represents a volatile detail or a stable concept. `Money`, `EmailAddress`, and `Clock` are acceptable concrete or standard dependencies; an external payment SDK in domain logic is usually not.

#### Production angle

In production, concrete dependencies are fine when replacing them would not be a real requirement and tests can use them directly without slow I/O or global state.

#### Traps / caveats

- Do not abstract stable domain values.
- Do not depend directly on concrete classes that open sockets, start transactions, or call external systems from business logic.
- Avoid interfaces created only for mocking when a real object is cheap and deterministic.

#### Optional Anki

Q: When is it okay to depend on a concrete class?
A: It is okay to depend on a concrete class when it is stable, local, simple, not a replaceable policy, and does not drag in volatile infrastructure concerns.

</details>

<details>
<summary><strong>OOP-DI-006. Should repositories always have interfaces?</strong></summary>

#### Short answer

Repositories do not always need interfaces. They need interfaces when they are real ports, have multiple implementations, isolate domain/application code from persistence, or improve meaningful tests.

#### Interview answer

In a hexagonal style, an application service may depend on an `OrderRepository` port and a JPA adapter implements it. That can keep JPA and Spring Data out of the domain/application core.

In a simple Spring CRUD service, adding `UserRepositoryInterface` over a single Spring Data repository may be pure ceremony.

#### Deep dive

A repository interface should express aggregate-oriented operations in application language, not just mirror `JpaRepository` method by method.

For example, an application port may be:

```java
interface OrderRepository {
    Optional<Order> findById(OrderId id);
    void save(Order order);
    List<Order> findOrdersReadyForBilling(Instant cutoff);
}
```

The JPA adapter can use `JpaRepository`, `EntityManager`, projections, or SQL internally, but those details do not leak into the use case.

#### Production angle

In production, repository interfaces are valuable at module boundaries and when tests need an in-memory implementation of business persistence semantics. They are less valuable when all code already lives in one persistence-heavy module.

#### Traps / caveats

- Do not create an interface only because the class name ends with `Repository`.
- Do not expose JPA-specific query details through a domain port.
- Do not mock repositories so heavily that persistence behavior is never tested.

#### Optional Anki

Q: What makes a repository interface a real port rather than ceremony?
A: It expresses application or aggregate operations and hides persistence details such as `JpaRepository`, `EntityManager`, SQL exceptions, lazy proxies, and paging types.

</details>

<details>
<summary><strong>OOP-DI-007. When is an interface with a single implementation useful or unnecessary?</strong></summary>

#### Short answer

A single-implementation interface is useful when it defines a stable boundary; it is unnecessary when it only duplicates one class without independent meaning.

#### Interview answer

Useful cases include external system ports, test seams for slow or nondeterministic resources, public module APIs, plugin points, and boundaries where implementation details must not leak inward.

Unnecessary cases are `UserService` plus `UserServiceImpl` when there is no separate client contract and no expected variation.

#### Deep dive

The number of implementations today is not the only criterion. A boundary may be important even with one adapter. But the interface should still be named and shaped by the client’s need.

#### Production angle

In Spring codebases, one-to-one interfaces often accumulate because of old conventions. Removing them can improve navigation, but do it carefully if other modules compile against them.

#### Traps / caveats

- Do not judge only by implementation count.
- Do judge by stability, ownership, clients, and test value.
- Avoid `Impl` naming when a concrete class name can describe the implementation.

#### Optional Anki

Q: When is an interface with a single implementation useful or unnecessary?
A: A single-implementation interface is useful when it defines a stable boundary; it is unnecessary when it only duplicates one class without independent meaning.

</details>

<details>
<summary><strong>OOP-DI-008. What is the Service Locator anti-pattern?</strong></summary>

#### Short answer

Service Locator is an anti-pattern when business code hides dependencies by looking them up from a global registry or container instead of declaring them explicitly.

#### Interview answer

With Service Locator, a class calls something like `ApplicationContext.getBean()` or `ServiceRegistry.get(PaymentGateway.class)` inside its methods. The constructor does not reveal what the class needs.

This makes tests harder, hides coupling, and can fail at runtime when a dependency is missing or misconfigured.

#### Deep dive

A locator can be acceptable in infrastructure code, plugin frameworks, or composition roots where dynamic lookup is the actual responsibility. It becomes a problem when ordinary domain/application objects use it to avoid declaring dependencies.

#### Production angle

In Spring, injecting `ApplicationContext` into a service is often a smell. Prefer constructor injection of the needed collaborators or a small factory/strategy registry with a clear contract.

#### Traps / caveats

- Do not hide dependencies behind static accessors.
- Do not use Service Locator to work around circular dependencies.
- A factory is not automatically a locator if its dependency and creation role are explicit.

#### Optional Anki

Q: What is the Service Locator anti-pattern?
A: Service Locator is an anti-pattern when business code hides dependencies by looking them up from a global registry or container instead of declaring them explicitly.

</details>

<details>
<summary><strong>OOP-DI-010. How can Spring make DIP easier or worse if misused?</strong></summary>

#### Short answer

Spring makes DIP easier by wiring abstractions and managing object graphs, but worse if business code becomes coupled to Spring annotations, containers, proxies, or bean lookup.

#### Interview answer

Good Spring usage keeps domain/application logic as plain Java objects with constructor-injected ports. Configuration binds ports to adapters.

Misuse happens when services call `ApplicationContext`, depend on `@Transactional` semantics in domain code, use static context holders, or let every class become a container-managed anemic service.

#### Deep dive

Spring proxies can also affect OOP assumptions: self-invocation may bypass proxy behavior, final methods/classes can limit proxying strategies, and annotations may move important behavior outside visible method calls.

#### Production angle

In production, Spring helps compose large systems, but clean boundaries still require package/module discipline, explicit ports, and tests that can run without the full container where possible.

#### Traps / caveats

- Do not assume `@Autowired` means DIP.
- Avoid leaking Spring types into pure domain code.
- Be aware of proxy boundaries for transactions, security, caching, and events.

#### Optional Anki

Q: How can Spring make DIP easier or worse if misused?
A: Spring makes DIP easier by wiring abstractions and managing object graphs, but worse if business code becomes coupled to Spring annotations, containers, proxies, or bean lookup.

</details>

<details>
<summary><strong>OOP-DI-011. How do you avoid framework dependencies in domain code?</strong></summary>

#### Short answer

Avoid framework dependencies in domain code by keeping domain types as plain Java, defining ports at the application boundary, and moving Spring/JPA/HTTP concerns to adapters.

#### Interview answer

Domain code should express business rules and invariants. It should not need `ApplicationContext`, `@Autowired`, web DTOs, HTTP clients, or messaging templates.

Application services can orchestrate use cases and depend on ports. Infrastructure adapters implement those ports with Spring, JPA, Kafka, REST clients, or other details.

#### Deep dive

Some annotations such as validation or persistence annotations may be pragmatic in certain projects, but they should be a deliberate trade-off. The more central the domain model, the more careful the boundary should be.

#### Production angle

The payoff is testability and portability: core business logic can be tested quickly without a database, web server, broker, or Spring context.

#### Traps / caveats

- Do not confuse domain purity with ignoring persistence constraints.
- Do not place ports so deep that domain objects become service locators.
- Mapping between persistence entities and domain objects has a cost; use it where the boundary value justifies it.

#### Optional Anki

Q: How do you avoid framework dependencies in domain code?
A: Avoid framework dependencies in domain code by keeping domain types as plain Java, defining ports at the application boundary, and moving Spring/JPA/HTTP concerns to adapters.

</details>

<details>
<summary><strong>🧠 OOP-DI-012. What is a port and adapter?</strong></summary>

#### Short answer

A port is an application-defined contract for communication across a boundary; an adapter implements that contract for a specific technology, protocol, or external system.

#### Interview answer

In hexagonal architecture, the core exposes or consumes ports. Incoming adapters call the application through input ports, such as REST controllers or message listeners. Outgoing adapters implement output ports, such as repositories, payment gateways, or notification senders.

The core owns the port language; adapters translate between that language and external APIs.

#### Deep dive

Ports and adapters are a practical way to apply DIP. They keep business rules from depending on details such as SQL, HTTP, Kafka, cloud SDKs, or file formats.

#### Production angle

In production, this makes replacement and testing easier: a failing external provider can be isolated behind an adapter, and the same port can have fake, in-memory, sandbox, and real implementations.

#### Traps / caveats

- Do not create ports for every private helper.
- Do not let vendor DTOs leak through a port unless the vendor is part of your public contract.
- Input and output ports solve different dependency directions.

#### Optional Anki

Q: What is a port and adapter?
A: A port is an application-defined contract for communication across a boundary; an adapter implements that contract for a specific technology, protocol, or external system.

</details>

<details>
<summary><strong>🧠 OOP-DI-013. What is the difference between compile-time dependency and runtime dependency?</strong></summary>

#### Short answer

A compile-time dependency is what code must know to compile; a runtime dependency is the actual object or module used when the application runs.

#### Interview answer

`CheckoutService` may compile against the `PaymentGateway` interface, while at runtime Spring injects `StripePaymentAdapter`. DIP mainly controls compile-time source dependencies; DI chooses runtime collaborators.

This distinction explains why depending on an interface can decouple source code even though a concrete object is always present at runtime.

#### Deep dive

In Java modules, build tools, and layered architectures, compile-time dependencies strongly influence what code can import. Runtime dependencies are controlled by configuration, classpath/module path, dependency injection, service loading, or factories.

#### Production angle

In production, separating the two helps with replaceable adapters, test fixtures, blue/green migrations, and avoiding accidental imports from infrastructure into domain code.

#### Traps / caveats

- Do not assume runtime polymorphism removes compile-time coupling if imports still point to infrastructure.
- Do not hide compile-time coupling behind reflection unless there is a strong reason.
- Build modules can enforce architecture better than conventions alone.

#### Optional Anki

Q: What is the difference between compile-time dependency and runtime dependency?
A: A compile-time dependency is what code must know to compile; a runtime dependency is the actual object or module used when the application runs.

</details>
