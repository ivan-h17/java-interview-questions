# 02.12. Code Smells and Anti-patterns Worth Knowing

---

<a id="oop-anti-002"></a>

<details>
<summary><strong>OOP-ANTI-002. What are God Object and Big Ball of Mud?</strong></summary>

#### Short answer

A God Object is one class that knows too much and does too much. A Big Ball of Mud is a system with weak boundaries, tangled dependencies, and no clear architecture.

#### Interview answer

A God Object usually combines validation, business rules, persistence, external calls, formatting, configuration, and orchestration in one place. It becomes a magnet for changes because many unrelated features must touch it.

A Big Ball of Mud is the system-level version: layers are blurred, modules depend on each other in many directions, and every change requires understanding accidental coupling rather than a clear model.

#### Deep dive

The smell is not just size. A large class can be acceptable when it has one cohesive responsibility. The stronger signal is unrelated reasons to change, too many dependencies, low testability, and code that manipulates many concepts directly.

Typical refactoring starts with characterization tests, then extracts clear responsibilities: domain behavior into domain objects, persistence into repositories, integration code into adapters, and use-case coordination into application services.

#### Production angle

In production, these smells increase blast radius. A small change in pricing may accidentally break persistence or notifications because everything shares the same class or dependency chain.

The practical goal is not a perfect architecture rewrite. It is to reduce risk by creating seams, moving one responsibility at a time, and protecting behavior with tests and metrics.

#### Traps / caveats

- Do not split a God Object randomly by line count; split by responsibility and change reason.
- Do not create many tiny services that still share the same unclear model.
- Do not call every large legacy class a God Object without checking cohesion.

#### Optional Anki

Q: What are God Object and Big Ball of Mud?
A: A God Object is one class that knows too much and does too much. A Big Ball of Mud is a system with weak boundaries, tangled dependencies, and no clear architecture.

<details>
<summary><strong>OOP-ANTI-003. What are Service Locator, Singleton abuse and global mutable state?</strong></summary>

#### Short answer

They are related ways of hiding or centralizing dependencies. They often make code harder to test, reason about, isolate, and evolve.

#### Interview answer

Service Locator means code asks a registry for dependencies instead of declaring them. Singleton abuse means using a globally reachable single instance as a convenient dependency container or mutable store. Global mutable state means data can be read or changed from many places without a clear owner.

The problem is not the word `static` itself. The problem is hidden collaboration and shared mutation: callers cannot see what the object needs, tests cannot replace it cleanly, and behavior may depend on previous requests or tests.

#### Deep dive

A singleton can be acceptable for truly stateless services, constants, or JVM-wide infrastructure managed at the composition root. It becomes harmful when domain code directly reaches into global state or when the singleton has lifecycle, configuration, cache, or request-specific behavior.

Prefer constructor injection for required collaborators. If legacy code already uses a locator or singleton, introduce an adapter or seam and gradually move callers to explicit dependencies.

#### Production angle

These smells commonly create flaky tests, order-dependent behavior, hard-to-debug configuration issues, memory leaks, and unsafe shared state in multi-threaded applications.

They also hide operational dependencies: a class may talk to a payment provider, clock, cache, or message broker even though its constructor does not reveal that fact.

#### Traps / caveats

- Do not replace a Service Locator with an interface that still hides the same lookup inside.
- Do not confuse immutable global constants with global mutable state.
- Do not introduce static mocks as the main solution; they often treat the symptom, not the design issue.

#### Optional Anki

Q: What are Service Locator, Singleton abuse and global mutable state?
A: They are related ways of hiding or centralizing dependencies. They often make code harder to test, reason about, isolate, and evolve.

<details>
<summary><strong>OOP-ANTI-004. What is a circular dependency smell?</strong></summary>

#### Short answer

A circular dependency smell appears when classes, packages, or modules depend on each other in a loop, making boundaries unclear and changes harder to isolate.

#### Interview answer

A direct cycle is `A -> B -> A`; an indirect cycle is `A -> B -> C -> A`. It often means that responsibilities are mixed or that high-level policy depends on low-level detail while the detail also depends back on policy.

Circular dependencies hurt compile-time structure, tests, deployment boundaries, and mental model. In Spring they may also cause bean creation problems or force workarounds such as lazy injection.

#### Deep dive

Typical fixes are: extract a shared abstraction into a lower-level module, move misplaced behavior to the owner, introduce a domain event, invert the dependency through a port, or split a module along responsibility boundaries.

The right fix depends on the direction of knowledge. Domain rules should not depend on REST, database, or messaging adapters; infrastructure can depend inward on application-defined ports.

#### Production angle

Cycles slow down builds, make refactoring risky, and can turn a small module change into a wide regression. They also make it hard to deploy or extract modules independently.

A useful production-oriented practice is to monitor package or module dependency graphs and fail builds for newly introduced cycles in important boundaries.

#### Traps / caveats

- Do not hide a cycle with lazy initialization and call it solved.
- Do not fix every cycle by creating a generic utilities module; it can become a dumping ground.
- Do not invert dependencies toward unstable abstractions owned by the wrong layer.

#### Optional Anki

Q: What is a circular dependency smell?
A: A circular dependency smell appears when classes, packages, or modules depend on each other in a loop, making boundaries unclear and changes harder to isolate.

</details>

<details>
<summary><strong>OOP-ANTI-005. What are inheritance abuse and Fat Interface?</strong></summary>

#### Short answer

Inheritance abuse is using inheritance where composition or a smaller contract would be safer. A Fat Interface forces clients to depend on methods they do not need or cannot implement meaningfully.

#### Interview answer

Inheritance abuse often appears when a subclass reuses code but is not a true subtype, overrides many methods awkwardly, or inherits state and lifecycle it cannot control. It couples the subclass to base-class internals.

A Fat Interface violates the Interface Segregation Principle. For example, one `DocumentStore` interface with `save`, `search`, `archive`, `exportPdf`, and `sendEmail` may force implementations to throw `UnsupportedOperationException` or provide fake behavior.

#### Deep dive

Good inheritance models an `is-a` relationship plus substitutable behavior. If the main goal is to reuse implementation, composition and delegation are usually safer.

A Fat Interface is usually refactored into role interfaces such as `DocumentReader`, `DocumentWriter`, `DocumentSearcher`, or capability-specific ports. Clients then depend only on the role they use.

#### Production angle

Inheritance abuse often creates fragile release behavior: a harmless base-class change breaks subclasses. Fat interfaces increase blast radius because every new method affects many implementations.

Both smells are especially painful in public APIs and shared libraries where clients cannot be updated atomically.

#### Traps / caveats

- Do not assume `extends` means a valid domain `is-a` relationship.
- Do not split interfaces so aggressively that clients must inject many tiny objects for one coherent task.
- Default methods can reduce migration pain but can also hide a fat contract.

#### Optional Anki

Q: What are inheritance abuse and Fat Interface?
A: Inheritance abuse is using inheritance where composition or a smaller contract would be safer. A Fat Interface forces clients to depend on methods they do not need or cannot implement meaningfully.

</details>

<details>
<summary><strong>🧠 OOP-ANTI-006. What are Primitive Obsession, Data Class and Feature Envy?</strong></summary>

#### Short answer

Primitive Obsession overuses raw primitives for domain concepts. Data Class is mostly passive data. Feature Envy is behavior that belongs more naturally to another object.

#### Interview answer

Primitive Obsession is using `String`, `int`, or `BigDecimal` everywhere for concepts like email, money, percentage, order status, or customer id. The result is duplicated validation and unclear meaning.

Data Class is a class with fields and accessors but little meaningful behavior. Feature Envy is a method that constantly asks another object for data and makes decisions that probably belong there.

#### Deep dive

A common fix for Primitive Obsession is a value object: `EmailAddress`, `Money`, `Percentage`, `OrderId`. It gives the concept a name, validation, formatting, and operations.

Data classes are not always bad: DTOs, records used for API shapes, projections, and persistence snapshots can be intentionally data-oriented. The smell appears when domain rules live outside while domain objects only carry data.

#### Production angle

In production, primitive obsession causes inconsistent validation: one endpoint accepts an invalid email, another rejects it, a third trims it differently. Feature Envy spreads business rules across services and makes fixes incomplete.

Value objects and behavior-oriented methods reduce duplication and make invariants easier to test.

#### Traps / caveats

- Do not wrap every primitive blindly; focus on concepts with rules, units, or repeated meaning.
- Do not move behavior into DTOs that are deliberately boundary data shapes.
- Feature Envy is a clue, not proof; sometimes a service legitimately coordinates several objects.

#### Optional Anki

Q: What are Primitive Obsession, Data Class and Feature Envy?
A: Primitive Obsession overuses raw primitives for domain concepts. Data Class is mostly passive data. Feature Envy is behavior that belongs more naturally to another object.

</details>

<details>
<summary><strong>🧠 OOP-ANTI-007. What are boolean-flag parameter and speculative generality smells?</strong></summary>

#### Short answer

A boolean-flag parameter changes behavior through a vague `true` or `false`. Speculative generality creates abstractions for imagined future needs instead of real variation.

#### Interview answer

A boolean flag like `sendInvoice(order, true)` makes the call site unclear and often means one method has two responsibilities. Multiple flags create a combinatorial set of modes.

Speculative generality appears as unused base classes, strategy interfaces with one implementation, generic extension points, or configuration options created because “we might need it later”.

#### Deep dive

For boolean flags, consider separate intention-revealing methods such as `sendInvoiceNow` and `scheduleInvoice`, or an explicit command/options object when there are several named choices.

For speculative generality, prefer simple code until real variation appears. When variation appears twice or starts changing independently, then extract a stable abstraction based on actual use cases.

#### Production angle

Boolean flags make tests harder because each mode and combination needs coverage. Speculative abstractions slow delivery because developers must understand extension points that do not solve current production problems.

The pragmatic approach is to remove unused flexibility and keep the code easy to change when the real requirement arrives.

#### Traps / caveats

- A boolean is not always a smell; it is fine for a simple value, not for hidden control flow.
- An enum can be clearer than a boolean, but a large mode enum can become the same smell.
- Do not delete extension points blindly if they support real plugins, tenants, or compatibility promises.

#### Optional Anki

Q: What are boolean-flag parameter and speculative generality smells?
A: A boolean-flag parameter changes behavior through a vague `true` or `false`. Speculative generality creates abstractions for imagined future needs instead of real variation.

<details>
<summary><strong>OOP-ANTI-008. How do you distinguish a design smell from an intentional trade-off?</strong></summary>

#### Short answer

A smell is a signal to investigate, not an automatic defect. It becomes an intentional trade-off when the team understands the cost, accepts it for a reason, and controls the risk.

#### Interview answer

I would ask: what problem does this design solve, how often does this code change, what breaks when it changes, how hard is it to test, and is the complexity paying for itself?

For example, a switch over a small stable enum can be clearer than a strategy hierarchy. A transaction script can be fine for a simple use case. A DTO can be intentionally passive at an API boundary.

#### Deep dive

A useful distinction is accidental vs deliberate. Accidental smells are not documented, surprise maintainers, and keep causing bugs. Deliberate trade-offs are local, visible, tested, and revisited when requirements change.

Good trade-offs usually have a small blast radius. If the choice leaks everywhere, blocks tests, or creates cycles, it may no longer be a reasonable shortcut.

#### Production angle

In production code, perfect design is less important than safe change. I would accept a known smell when it keeps a hot fix small, avoids unnecessary migration risk, or improves performance with measured evidence.

But I would also leave a clear name, tests, and maybe a technical-debt note so the shortcut does not silently become architecture.

#### Traps / caveats

- Do not use “trade-off” as a polite name for code nobody wants to understand.
- Do not refactor a smell without knowing the behavior and business risk.
- Do not optimize for theoretical purity over current team and product constraints.

#### Optional Anki

Q: How do you distinguish a design smell from an intentional trade-off?
A: A smell is a signal to investigate, not an automatic defect. It becomes an intentional trade-off when the team understands the cost, accepts it for a reason, and controls the risk.

</details>

<details>
<summary><strong>🧠 OOP-ANTI-009. What are Golden Hammer and Lava Flow?</strong></summary>

#### Short answer

Golden Hammer is forcing a familiar tool or pattern onto every problem. Lava Flow is old, poorly understood code that remains in the system because nobody is sure whether it is still needed.

#### Interview answer

Golden Hammer often looks like “everything must be microservices”, “everything needs Strategy”, or “every class needs an interface”. It replaces design thinking with a favorite solution.

Lava Flow appears after abandoned features, incomplete rewrites, emergency patches, or copied legacy paths. The code is risky to remove because behavior, owners, and callers are unclear.

#### Deep dive

The fix for Golden Hammer is to compare alternatives against forces: change frequency, complexity, performance, team knowledge, operational cost, and reversibility.

The fix for Lava Flow is evidence-driven cleanup: find usage, add logging or metrics if necessary, cover behavior with tests, deprecate, remove in small steps, and monitor.

#### Production angle

Golden Hammer increases cost by applying heavy solutions where simple code would work. Lava Flow increases risk because obsolete paths may still run for a rare tenant, batch job, or migration case.

A senior answer should show caution: remove dead code, but only after proving it is dead or making rollback safe.

#### Traps / caveats

- Do not assume a pattern is good because it worked in a previous project.
- Do not delete suspicious legacy code without usage analysis.
- Do not keep Lava Flow forever because “maybe someone needs it”; make the uncertainty visible and measurable.

#### Optional Anki

Q: What are Golden Hammer and Lava Flow?
A: Golden Hammer is forcing a familiar tool or pattern onto every problem. Lava Flow is old, poorly understood code that remains in the system because nobody is sure whether it is still needed.

</details>
