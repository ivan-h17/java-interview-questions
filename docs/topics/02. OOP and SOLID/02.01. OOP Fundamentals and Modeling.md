# 02.01. OOP Fundamentals and Modeling

---

<a id="oop-fund-001"></a>

<details>
<summary><strong>OOP-FUND-001. What is Object-Oriented Programming?</strong></summary>

#### Short answer

Object-Oriented Programming is a way to design software around objects that combine state, behavior, identity, and contracts. The goal is not just to use classes, but to model responsibilities and interactions clearly.

#### Interview answer

In Java, OOP usually means that important concepts are represented as classes and objects, and clients interact with them through methods. A good object owns part of the system state and exposes meaningful operations such as `order.cancel(reason)` or `account.withdraw(amount)`.

The benefits are encapsulation, local reasoning, polymorphism, and a vocabulary close to the domain. OOP is still only a tool: some code is better expressed as simple functions, records, data transformations, or SQL queries.

#### Deep dive

Classic OOP is often explained through encapsulation, abstraction, inheritance, and polymorphism. In backend design, the more important questions are: who owns state, where do rules live, and what contract do callers depend on?

A class with private fields and public setters may use OOP syntax while still being procedural. A stronger model keeps behavior near the data it protects and exposes business operations instead of raw field manipulation.

#### Production angle

In production, OOP helps when the domain has state, lifecycle, rules, and behavior variation that evolve over time. It hurts when teams create artificial hierarchies, interfaces for everything, or objects with no real responsibility.

#### Traps / caveats

- OOP is not “classes everywhere”; it is about responsibility boundaries and behavior.
- Getters and setters do not automatically create encapsulation.
- Inheritance is only one OOP mechanism and is often less flexible than composition.
- For simple data movement, procedural or functional style may be clearer.

#### Optional Anki

Q: What is OOP in one practical sentence?
A: OOP models software as interacting objects that own state, expose behavior, and protect contracts.

</details>

<details>
<summary><strong>OOP-FUND-003. What are the four pillars of OOP?</strong></summary>

#### Short answer

The four classic pillars are encapsulation, abstraction, inheritance, and polymorphism. A senior answer should explain how they control change and protect correctness, not just list them.

#### Interview answer

Encapsulation keeps state and behavior behind a controlled boundary. Abstraction exposes the useful concept or contract while hiding irrelevant details. Inheritance lets one type reuse or specialize another type. Polymorphism lets code work with different implementations through a common contract.

In modern Java backend code, composition, interfaces, records, sealed classes, and simple functions are often as important as inheritance.

#### Deep dive

The pillars support each other, but they do not guarantee good design. An interface can be a poor abstraction, private fields can still expose invalid states through setters, and inheritance can create tight coupling.

Polymorphism also does not require a concrete base class. Java interfaces and composition often provide a safer extension point than a deep inheritance hierarchy.

#### Production angle

In production, encapsulation limits the blast radius of changes, abstraction hides volatile details, and polymorphism allows new behavior without editing every caller. Misused inheritance often causes fragile base classes and surprising side effects.

#### Traps / caveats

- Do not present inheritance as the most important pillar in modern design.
- Polymorphism is not the same as “using an interface for every class”.
- Abstraction should hide accidental complexity, not important business rules.
- Encapsulation is broken if callers can still create invalid states.

#### Optional Anki

Q: Name the four OOP pillars.
A: Encapsulation, abstraction, inheritance, and polymorphism.

</details>

<details>
<summary><strong>OOP-FUND-004. What is the difference between a class and an object?</strong></summary>

#### Short answer

A class is a type or blueprint that defines fields, methods, constructors, and contracts. An object is a runtime instance of a class with identity and usually state.

#### Interview answer

In Java, a class describes what instances can do and what data they contain. For example, `Order` defines methods such as `addItem()` and fields such as status or items. An object is a particular order, for example order `#123`, with its current state.

Static members belong to the class level, while instance fields belong to individual objects.

#### Deep dive

The distinction matters for debugging. A bug in method implementation affects all objects of that class. A bug in one object's state may affect only that instance, unless state is shared through static fields or shared mutable collaborators.

Class design defines possible shape and lifecycle. Object design asks whether a specific instance is valid, immutable, identifiable, and able to collaborate safely.

#### Production angle

In production, confusing class-level and object-level state leads to bugs. Static mutable fields can accidentally share data between requests or tenants. Instance state in singleton Spring beans can also become accidental global state.

#### Traps / caveats

- A class is not an object instance; it defines how instances behave.
- Static fields are shared at class level, not copied per object.
- Spring singleton beans are objects too, but usually only one instance is reused by many requests.
- A class can be syntactically correct and still model the wrong concept.

#### Optional Anki

Q: Class vs object?
A: A class defines type and behavior; an object is a runtime instance with identity and state.

</details>

<details>
<summary><strong>OOP-FUND-005. What is the difference between state and behavior?</strong></summary>

#### Short answer

State is what an object knows at a point in time. Behavior is what the object can do: operations that read, validate, change, or expose that state through a contract.

#### Interview answer

An `Order` state may include items, status, customer ID, and total. Its behavior may include `addItem()`, `confirm()`, `cancel()`, and `calculateTotal()`. In a good model, behavior expresses allowed operations over the state.

The design question is where behavior should live. If all behavior is outside the object, the object becomes a data holder. If too much behavior is in one object, it becomes a God Object.

#### Deep dive

State may be mutable or immutable, stored or derived, persistent or temporary. Behavior may be command-like, query-like, or both when the domain requires it.

State and behavior are connected by invariants. If an account balance cannot go below zero, `withdraw()` should enforce that rule; a raw `setBalance()` often does not express the invariant.

#### Production angle

In backend systems, separating state from behavior too aggressively often creates transaction scripts with duplicated validation. Storing request-specific mutable state inside shared services creates concurrency bugs. The right boundary depends on lifecycle and ownership.

#### Traps / caveats

- Behavior is not any method; useful behavior protects or uses state through a clear rule.
- Derived values can be part of observable state even if not stored in fields.
- Mutable state in shared objects requires special care.
- A data-only object is not always wrong, but it should be intentional.

#### Optional Anki

Q: State vs behavior?
A: State is what an object knows; behavior is what it can do with or around that state.

</details>

<details>
<summary><strong>OOP-FUND-006. What is the difference between object identity and object equality?</strong></summary>

#### Short answer

Object identity means two references point to the same runtime instance. Object equality means two objects are logically equal according to `equals()`, even if they are different instances.

#### Interview answer

In Java, `==` on object references checks identity. `equals()` checks logical equality according to the class contract. Value objects such as `Money` usually compare by fields. Entities such as `Customer` usually compare by stable identity.

Collections such as `HashSet` and `HashMap` rely on `equals()` and `hashCode()`. If equality changes while an object is used as a key, lookups can fail.

#### Deep dive

The default `Object.equals()` behaves like identity equality. A correct override should be reflexive, symmetric, transitive, consistent, and compatible with `hashCode()`: equal objects must have equal hash codes.

JPA entities are tricky because generated IDs may be `null` before persistence. Records generate component-based equality, which is good for values but usually wrong for identity-based entities.

#### Production angle

Production bugs often come from mutable objects in hash-based collections, Lombok-generated equality over wrong fields, or distributed code comparing local object references instead of stable identifiers.

#### Traps / caveats

- `==` compares object references, not logical equality.
- Equal objects must have equal `hashCode()` values.
- Do not base equality on mutable fields if the object can be used in hash collections.
- Entity equality and value object equality are usually designed differently.

#### Optional Anki

Q: Identity vs equality in Java?
A: Identity is same reference (`==`); equality is logical equivalence defined by `equals()`.

</details>

<details>
<summary><strong>OOP-FUND-007. What does it mean to model a domain concept as an object?</strong></summary>

#### Short answer

It means representing a business concept as an object with a clear name, state, behavior, lifecycle, invariants, and collaboration boundaries instead of treating it as a bag of fields.

#### Interview answer

First ask what the concept means in business language and what decisions it owns. An `Order` is not just a database row: it may know when items can be added, when it can be paid, and which status transitions are valid.

The object should expose operations from the domain language and protect rules that belong to it. It should not contain every related operation; some behavior may belong to another object, domain service, application service, or aggregate boundary.

#### Deep dive

A useful domain object answers: what makes it valid, how it changes, what identity or value semantics it has, who may create it, and what external details it should not know.

Modeling is not mirroring database tables or API payloads. A table stores persistence details; a domain object expresses behavior and invariants. Sometimes a DTO or record is enough; sometimes a richer aggregate is needed.

#### Production angle

Good modeling localizes change. If cancellation rules change, a well-modeled order or policy gives one obvious place to change and test. Poor modeling spreads the same rule across controllers, services, jobs, and consumers.

#### Traps / caveats

- Do not model every noun as a class; model responsibilities, rules, and lifecycle.
- A domain object should not know HTTP, SQL, or Kafka details unless that is explicitly its boundary.
- Mirroring database tables often creates persistence-shaped objects, not domain objects.
- Too much behavior in one object can become a God Object.

#### Optional Anki

Q: What does domain modeling as objects focus on?
A: Business meaning, invariants, lifecycle, behavior, identity/value semantics, and boundaries.

</details>

<details>
<summary><strong>OOP-FUND-008. What is the difference between an entity and a value object?</strong></summary>

#### Short answer

An entity is defined by stable identity and lifecycle. A value object is defined by its values, usually immutable, and interchangeable with another value object with the same values.

#### Interview answer

A `Customer`, `Order`, or `Account` is often an entity because it remains the same conceptual thing while attributes change. A `Money`, `EmailAddress`, or `DateRange` is usually a value object.

Value objects should usually be immutable, validated at construction, and compared by value. Entities should usually have equality based on stable identity rather than all mutable attributes.

#### Deep dive

The distinction drives equality, persistence, and API design. Treating an entity as a value can break identity and updates. Treating a value object as an entity creates unnecessary IDs, joins, and lifecycle complexity.

Java records can fit many value objects because they provide component-based equality and compact constructors for validation. They still require defensive copies for mutable components.

#### Production angle

In production, this distinction prevents subtle ORM and collection bugs. Entity identity should stay stable; value objects should be safe to copy, compare, serialize, and use inside other objects.

#### Traps / caveats

- A database ID alone does not make a good domain entity.
- Value objects should validate their own values.
- Records are convenient for value objects but do not automatically protect mutable components.
- Entities may contain value objects as attributes.

#### Optional Anki

Q: Entity vs value object?
A: Entity is defined by identity and lifecycle; value object is defined by its values.

</details>

<details>
<summary><strong>🧠 OOP-FUND-009. What is an anemic domain model, and when is it a problem?</strong></summary>

#### Short answer

An anemic domain model is a model where domain objects mostly contain data and almost no behavior, while business rules live in services. It is a problem when rules become duplicated, scattered, and easy to bypass.

#### Interview answer

A typical anemic model has entities with getters and setters, while services perform all validation and state transitions. For simple CRUD this can be acceptable. The problem appears when the domain has non-trivial invariants: cancellation rules, credit limits, pricing, reservation, or account balance.

If rules live only in application services, every caller must remember to apply them. A batch job, Kafka consumer, or admin endpoint may update state directly and skip a rule.

#### Deep dive

Anemic models often arise from database-first design, generated entities, excessive layering, or fear of putting behavior into JPA entities. The result is procedural code with objects as data records.

The alternative is not to put all logic into entities. Some rules need repositories, time, external services, or cross-aggregate coordination. The key is to avoid a model where domain objects cannot protect even their own basic invariants.

#### Production angle

Production symptoms include duplicated validation, inconsistent states from different entry points, and service classes with hundreds of lines of conditional logic around passive data objects.

#### Traps / caveats

- Anemic model is not automatically bad for simple CRUD or reporting.
- Rich domain model does not mean entities should call databases or external services.
- JPA constraints may influence where behavior lives, but they do not require a completely passive model.
- Moving logic into objects without clear responsibility can create a God Object.

#### Optional Anki

Q: When is an anemic domain model a problem?
A: When important business rules are scattered in services and domain objects cannot protect their own invariants.

</details>

<details>
<summary><strong>🧠 OOP-FUND-011. When can procedural or data-transformation code be simpler than OOP?</strong></summary>

#### Short answer

Procedural or data-transformation style can be simpler when the task is a clear sequence of steps over data, with little domain state, lifecycle, polymorphism, or rich invariants.

#### Interview answer

Examples are CSV import, ETL pipelines, report generation, DTO mapping, simple validation, batch transformations, and algorithms where the value is a transparent data flow. Forcing everything into stateful objects can add ceremony without improving correctness.

A pragmatic answer is: OOP is good when behavior belongs with state and the model changes over time. A procedural pipeline is good when the work is naturally a sequence of transformations.

#### Deep dive

Modern Java supports both styles. Records can represent immutable data shapes, streams can express transformations, and services can orchestrate use cases. A small mapper function can be clearer than a hierarchy of mapper objects.

The risk of procedural style is scattered business logic. The risk of OOP is over-modeling: many tiny classes and strategies before variation actually exists.

#### Production angle

Simple procedural code is often easier to debug for one-off jobs and linear workflows. When the same rules are copied into multiple pipelines, extract shared domain concepts or policies.

#### Traps / caveats

- Do not use OOP patterns just to avoid a simple function.
- Do not keep complex domain rules as duplicated procedural checks forever.
- Data transformation is not the same as domain modeling.
- A stream pipeline can become unreadable if it hides too much logic in lambdas.

#### Optional Anki

Q: When is procedural code better than OOP?
A: When the task is mostly a linear data transformation with little stateful domain behavior.

</details>

<details>
<summary><strong>🧠 OOP-FUND-012. How does OOP compare with functional programming?</strong></summary>

#### Short answer

OOP organizes code around objects that own state and expose behavior. Functional programming organizes code around functions, immutable data, composition, and explicit control of side effects.

#### Interview answer

OOP is strong for stateful domain concepts with identity, lifecycle, and behavior variation: orders, accounts, policies, gateways. Functional style is strong for transformations, calculations, immutability, and reducing side effects.

In Java backend development, they are usually mixed. Domain objects may be object-oriented, value objects immutable, mapping logic functional, and streams used for data processing.

#### Deep dive

OOP hides state behind methods and often uses dynamic dispatch for behavior variation. FP makes data flow explicit and passes behavior as functions. OOP can become hard when many mutable objects interact. FP can become awkward when a domain has rich identity and coordinated state transitions.

Java features such as lambdas, method references, streams, records, and sealed types make mixed design natural.

#### Production angle

Functional techniques reduce concurrency bugs and simplify tests because pure functions are deterministic. OOP boundaries reduce coupling around mutable business state. Maintainable Java systems often use both.

#### Traps / caveats

- FP is not just “using streams”; it is mostly about immutability, composition, and controlled side effects.
- OOP is not necessarily mutable; objects and value objects can be immutable.
- A long stream chain with side effects can be worse than a simple loop.
- Pure functions are easy to test, but real backend systems still need controlled side effects.

#### Optional Anki

Q: OOP vs FP in Java?
A: OOP models behavior around objects and state; FP favors immutable data, pure functions, and composition.

</details>

<details>
<summary><strong>🧠 OOP-FUND-013. How does DDD relate to OOP?</strong></summary>

#### Short answer

DDD is a design approach for aligning software with a complex business domain. OOP is one common way to implement DDD concepts such as entities, value objects, aggregates, repositories, domain services, and domain events.

#### Interview answer

DDD is not “objects everywhere”. It starts with understanding the domain, building a ubiquitous language, and defining bounded contexts. OOP helps express tactical DDD patterns: an entity owns identity and lifecycle, a value object captures a validated concept, and an aggregate protects consistency rules.

For example, an `Order` aggregate can expose `confirm()` or `cancel()` and prevent invalid transitions. A `Money` value object can enforce currency and amount rules.

#### Deep dive

Strategic DDD is about bounded contexts, context maps, language, and team boundaries. Tactical DDD is about modeling building blocks. OOP is useful for tactical modeling, but DDD can also use functional or data-oriented approaches if they better express the model.

In Java backend architecture, domain concepts should stay independent from controllers, ORM details, messaging frameworks, and Spring annotations when possible.

#### Production angle

DDD helps when business rules are complex, language is ambiguous, and teams need clear ownership. It can be overkill for small CRUD modules. A senior engineer models the core domain deeply and keeps supporting areas simpler.

#### Traps / caveats

- DDD is not the same as layered architecture or “entities plus repositories”.
- OOP syntax does not guarantee a domain model aligned with the business.
- Do not force rich aggregates into simple CRUD where transaction scripts are enough.
- A domain model polluted by framework and transport details becomes harder to evolve.

#### Optional Anki

Q: How does DDD relate to OOP?
A: DDD defines domain-centered modeling ideas; OOP is a common way to implement entities, value objects, aggregates, and domain behavior.

</details>
