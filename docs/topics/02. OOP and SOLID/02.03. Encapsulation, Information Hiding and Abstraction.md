# 02.03. Encapsulation, Information Hiding and Abstraction

---

<a id="oop-encap-001"></a>

<details>
<summary><strong>OOP-ENCAP-001. What is encapsulation?</strong></summary>

#### Short answer

Encapsulation is the object-oriented practice of keeping state and behavior together and controlling how state can be observed or changed so that the object remains valid.

#### Interview answer

In an interview I would avoid defining encapsulation as “private fields plus getters”. Private fields are only one technique. The goal is that an object owns its state and exposes meaningful operations, for example `order.cancel(reason)` or `account.withdraw(amount)`, instead of forcing callers to manipulate its internals. Good encapsulation protects invariants, hides representation choices, and lets the implementation change without changing callers.

#### Deep dive

Encapsulation works at several levels: class, package, module, aggregate, service API. At class level it means hiding representation details such as “list or set”, “cents or `BigDecimal`”, “cached or computed”. At domain level it means exposing operations in the ubiquitous language and keeping invalid transitions impossible or at least localized. Encapsulation is not about hiding everything blindly: DTOs, records, and simple projections may intentionally be mostly data.

#### Production angle

In production code, encapsulation reduces the blast radius of changes and defects. If validation and state transitions are centralized inside the object or aggregate, fewer services can accidentally persist invalid state, publish inconsistent events, or bypass business rules. It also makes refactoring safer: callers depend on a stable contract, not on internal fields.

#### Traps / caveats

- Private fields with public setters for everything are often just procedural code with extra syntax.
- Over-encapsulation can make simple DTOs or projections unnecessarily hard to use.
- An object can still leak internals through mutable getters, callbacks, inheritance hooks, reflection, or serialization.

#### Optional Anki

Q: What is encapsulation beyond private fields?
A: It is controlling access to state through meaningful operations so invariants and representation details stay inside the object boundary.

</details>

<a id="oop-encap-002"></a>

<details>
<summary><strong>OOP-ENCAP-002. What is the difference between encapsulation, abstraction and data hiding?</strong></summary>

#### Short answer

Abstraction is about the useful model or contract, encapsulation is about keeping state and behavior behind that contract, and data hiding is about preventing clients from depending on internal representation.

#### Interview answer

These terms overlap but are not identical. Abstraction says “what is the essential concept?”: for example, `PaymentMethod` can authorize a payment without exposing provider-specific details. Encapsulation says “who owns the state and rules?”: the object or module controls changes to its state. Data hiding, or information hiding, says “what implementation details must clients not know?”: fields, collection types, cache structure, database IDs, or protocol details.

#### Deep dive

You can have one without the others. A public interface may be a good abstraction but a poor encapsulation boundary if it exposes mutable objects. A class may hide all fields but expose a weak abstraction such as `getStatus()` plus `setStatus()`. Data hiding is usually an implementation technique that supports encapsulation; abstraction is the design of the public surface.

#### Production angle

Confusing these concepts leads to brittle APIs. For example, an API may look abstract because it has an interface, but still leak SQL pagination, provider error codes, or JPA lazy-loading behavior. A stable abstraction should hide details that are likely to change and expose the business operation the caller actually needs.

#### Traps / caveats

- An interface is not automatically a good abstraction.
- Data hiding is not enough if the exposed operations still allow invalid states.
- Abstraction should hide accidental complexity, not important domain rules.

#### Optional Anki

Q: Difference between abstraction and encapsulation?
A: Abstraction defines the useful public model; encapsulation protects state and rules behind that model.

</details>

<a id="oop-encap-003"></a>

<details>
<summary><strong>OOP-ENCAP-003. Is making fields private enough for good encapsulation?</strong></summary>

#### Short answer

No. Private fields help, but good encapsulation also requires meaningful methods, protected invariants, controlled mutability, and no accidental exposure of internal mutable objects.

#### Interview answer

Making fields private prevents direct field access, but it does not automatically create a good object model. If every field has a setter, callers can still put the object into invalid states. If getters expose mutable collections, callers can bypass validation. The better question is: can the object enforce its invariants and can I change its internal representation without breaking clients?

#### Deep dive

Good encapsulation usually means constructor validation, behavior-oriented methods, minimal mutators, defensive copies for mutable inputs and outputs, and a clear distinction between domain objects and DTOs. Sometimes a field should not have a setter at all; instead the object should expose a domain operation. For example, `order.markPaid(paymentId)` can validate status, amount, timestamps, and events in one place.

#### Production angle

In backend systems, “private fields plus setters” often spreads validation across services, controllers, mappers, and tests. Later, one path forgets a check and bad state reaches the database or an event. Encapsulated operations make it easier to audit all legal state transitions and to add logging or events around them.

#### Traps / caveats

- Framework requirements, such as JPA access rules, can influence visibility, but they do not remove the need for invariants.
- A getter can break encapsulation even if the field itself is private.
- Not every object needs rich behavior; simple DTOs can intentionally be data carriers.

#### Optional Anki

Q: Why are private fields not enough?
A: Because callers may still mutate state through setters or exposed mutable objects and bypass invariants.

</details>

<a id="oop-encap-004"></a>

<details>
<summary><strong>OOP-ENCAP-004. Why can exposing getters and setters for every field be harmful?</strong></summary>

#### Short answer

It turns an object into a data bag, moves business decisions outside the object, makes invalid states easier, and makes future representation changes harder.

#### Interview answer

Getters and setters are not evil, but generating them for every field is a smell in domain code. It encourages clients to ask for data, make decisions elsewhere, and then push raw values back. That scatters business rules across the codebase. A domain object should often expose operations such as `reserve()`, `cancel()`, `changeEmail()`, or `addItem()`, where validation and side effects can be controlled.

#### Deep dive

Setters are especially risky when several fields must change together. For example, changing an order status may require a reason, timestamp, domain event, and allowed transition check. A set of independent setters cannot express that atomic rule. Getters can also couple clients to representation: a caller that iterates over `List<LineItem>` may break if the object later stores items in a map for lookup.

#### Production angle

In production, excessive getters and setters often create inconsistent validation between REST controllers, batch jobs, listeners, and tests. A future change then requires finding every place that mutates the object. Behavior-oriented methods reduce duplication and make invariants easier to protect with unit tests.

#### Traps / caveats

- DTOs, request/response models, projections, and configuration classes may reasonably have simple accessors.
- Removing all getters can hurt readability; query methods are useful when they expose stable facts, not internals.
- JavaBeans conventions may be required by frameworks, so the design boundary may be a mapper rather than the entity itself.

#### Optional Anki

Q: Main risk of getters/setters for every field?
A: They expose raw state manipulation and move business rules outside the object.

</details>

<a id="oop-encap-006"></a>

<details>
<summary><strong>OOP-ENCAP-006. What is representation exposure, and how can a getter accidentally cause it?</strong></summary>

#### Short answer

Representation exposure happens when internal implementation objects become accessible to callers, usually through a getter that returns a mutable collection or mutable reference.

#### Interview answer

A classic example is a class with a private `List<Item> items` and a public `getItems()` that returns the same list. The field is private, but callers can still run `order.getItems().clear()` and bypass checks in `addItem()` or `removeItem()`. The object has exposed its representation, so its invariants are no longer fully under its control.

#### Deep dive

Representation exposure is not limited to collections. It can happen with arrays, old mutable date/time classes, buffers, builders, maps, entity references, or any mutable object. It can also happen on input: if the constructor stores a caller-provided mutable list directly, the caller can mutate it later. Common fixes are defensive copying, immutable copies, narrow query methods, domain operations, or returning a read-only view when a live view is intentional.

#### Production angle

This bug often appears as “impossible” state changes: a list becomes empty, order totals no longer match items, or a supposedly immutable response changes between logs. It is also a common concurrency problem because callers may modify shared mutable state without the owner’s lock or transaction boundary.

#### Traps / caveats

- An unmodifiable wrapper prevents mutation through that wrapper, but the original collection may still change elsewhere.
- A copy of a collection is usually shallow; mutable elements inside it may still be changed.
- Returning entities from aggregates can expose more behavior and state than intended.

#### Optional Anki

Q: How can a getter break encapsulation?
A: By returning an internal mutable object, so callers can mutate representation directly and bypass invariants.

</details>

<details>
<summary><strong>OOP-ENCAP-007. What is defensive copying, and when should you return an immutable copy instead of an unmodifiable view?</strong></summary>

#### Short answer

Defensive copying means copying mutable inputs or outputs so callers cannot mutate your internal state. Return an immutable copy when the caller needs a stable snapshot; return an unmodifiable view only when a live read-only view is intentional and safe.

#### Interview answer

A defensive copy breaks aliasing between the object and the caller. On input, the object copies a provided collection instead of storing the caller’s reference. On output, it returns a copy instead of the internal collection. An immutable copy, for example `List.copyOf(items)`, is a snapshot that cannot be structurally changed. An unmodifiable view, for example `Collections.unmodifiableList(items)`, blocks mutation through the view but still reflects changes made to the backing list.

#### Deep dive

Use immutable copies for public APIs, snapshots, value objects, events, DTOs crossing threads, and data that must not change after validation. Use an unmodifiable view when you explicitly want callers to observe current state without modifying it and the owner controls all mutations. Be aware that both approaches are usually shallow: if `Item` is mutable, copying `List<Item>` does not make each item immutable.

#### Production angle

Immutable snapshots make logs, audit events, retry payloads, cache values, and async tasks more predictable. Unmodifiable views can be faster and avoid allocation, but they are dangerous if clients assume a stable snapshot. In concurrent code, a live view over a mutable collection can still fail with stale reads or concurrent modification issues.

#### Traps / caveats

- `List.copyOf(...)` rejects null elements; this can be useful validation or a surprise.
- Defensive copying can be expensive for large graphs; sometimes a narrower query method is better.
- Unmodifiable is not the same as immutable if someone else still owns the backing collection.

#### Optional Anki

Q: Immutable copy vs unmodifiable view?
A: An immutable copy is an independent snapshot; an unmodifiable view is a read-only wrapper over a backing object that may still change.

</details>

<details>
<summary><strong>🧠 OOP-ENCAP-008. What is a leaky abstraction?</strong></summary>

#### Short answer

A leaky abstraction is an abstraction that fails to hide important implementation details, so callers must understand those details to use it correctly.

#### Interview answer

A good abstraction lets callers think in terms of the problem, not the implementation. It becomes leaky when implementation details show through the API. For example, a domain service that exposes SQL error codes, a repository method that forces callers to handle JPA lazy-loading behavior, or a storage abstraction that still requires callers to know S3 object key rules. The abstraction exists, but callers still pay the cognitive cost of the hidden layer.

#### Deep dive

All non-trivial abstractions leak a little, but the design question is whether the leak is acceptable. Some details are essential and should be part of the contract: latency, ordering guarantees, idempotency, consistency model, or error semantics. Accidental details should usually be hidden: exact collection type, database vendor quirks, provider DTOs, internal retry mechanism, or cache layout.

#### Production angle

Leaky abstractions are common around persistence, messaging, HTTP clients, transactions, and frameworks. They cause duplicated workarounds: every caller catches the same provider exception or knows the same transaction rule. A practical fix is to move those rules behind an adapter, define domain-level errors, and document the guarantees the abstraction actually provides.

#### Traps / caveats

- Hiding essential operational facts, such as latency or eventual consistency, creates a worse abstraction.
- A wrapper with the same methods as the underlying library usually does not create a meaningful abstraction.
- Too much abstraction can hide useful debugging information.

#### Optional Anki

Q: What makes an abstraction leaky?
A: Callers must know implementation details that the abstraction was supposed to hide.

</details>

<details>
<summary><strong>OOP-ENCAP-009. What is the difference between a DTO and a domain object?</strong></summary>

#### Short answer

A DTO carries data across boundaries; a domain object represents a business concept and should protect business rules, behavior, and invariants.

#### Interview answer

A DTO is optimized for communication: REST requests, REST responses, messages, external provider payloads, or projections. It is usually simple, serializable, and shaped for a specific boundary. A domain object is optimized for business meaning: it owns rules like “an order cannot be cancelled after shipment” or “a withdrawal cannot make the balance negative”. Mixing the two often leaks API or persistence concerns into domain code.

#### Deep dive

DTOs may contain validation related to the boundary, such as required JSON fields or format checks, but they should not become the central place for domain decisions. Domain objects should not be shaped by frontend convenience or database schema alone. A JPA entity can be a domain object in simpler systems, but in more complex domains it may be better treated as a persistence model mapped to a separate domain model.

#### Production angle

Keeping DTOs separate helps with API evolution, backward compatibility, security, and lazy-loading problems. For example, returning a JPA entity directly from a REST endpoint can expose internal fields, trigger unexpected SQL queries, create circular JSON graphs, or make API changes depend on database refactoring.

#### Traps / caveats

- A DTO with many validation annotations is still not necessarily a domain model.
- Mapping layers add code; for small CRUD services a pragmatic model may be acceptable.
- A domain object with only getters and setters can degrade into an anemic data structure.

#### Optional Anki

Q: DTO vs domain object?
A: A DTO is a boundary data shape; a domain object models business behavior and invariants.

</details>

<details>
<summary><strong>🧠 OOP-ENCAP-010. What does "tell, don't ask" mean?</strong></summary>

#### Short answer

“Tell, don’t ask” means you should usually ask an object to perform a meaningful operation instead of extracting its state and making decisions elsewhere.

#### Interview answer

The idea is to keep behavior close to the data it depends on. Instead of `if (order.getStatus() == NEW) order.setStatus(CANCELLED)`, a caller can say `order.cancel(reason)`. The order then decides whether cancellation is allowed and updates all related state consistently. This supports encapsulation because clients depend on behavior, not on internal state transitions.

#### Deep dive

The principle is a heuristic, not a law. Querying state is fine when the caller genuinely needs information, especially for rendering, reporting, authorization, or orchestration. The smell appears when many callers repeatedly inspect the same fields and duplicate the same decision logic. That usually means the decision belongs in the object, aggregate, policy, strategy, or domain service.

#### Production angle

This principle helps find duplication in services. If several services contain the same `if` chain over an object’s state, moving that behavior behind a method can reduce bugs and make changes testable. It is also useful in refactoring anemic domain models where services perform all domain decisions over passive data.

#### Traps / caveats

- Do not move every decision into one huge entity; cross-aggregate workflows may belong in an application service.
- For DTOs and read models, asking for data is normal.
- Overusing the rule can create methods that mix unrelated responsibilities.

#### Optional Anki

Q: What is “tell, don’t ask”?
A: Prefer telling an object to perform a domain operation over asking for raw state and deciding outside.

</details>

<details>
<summary><strong>🧠 OOP-ENCAP-012. What is the Command-Query Separation principle?</strong></summary>

#### Short answer

Command-Query Separation says a method should either change state or return information, but ideally not both.

#### Interview answer

A command performs an action and may change state, such as `cancelOrder()` or `save()`. A query returns information and should not have observable side effects, such as `total()` or `findById()`. The benefit is predictability: callers can invoke queries without worrying that they changed the system, and commands are easier to reason about as state transitions.

#### Deep dive

CQS is a local design principle, not the same thing as CQRS architecture. In Java code it often means avoiding methods like `getOrCreate()` when the creation side effect is surprising, or `isValid()` when it also mutates validation state. Some methods pragmatically return results from commands, such as generated IDs, version numbers, or domain events. That is acceptable when the side effect is obvious from the name and contract.

#### Production angle

CQS makes production behavior easier to debug. If a “read” endpoint unexpectedly writes audit rows, initializes missing records, or changes cache state in a visible way, retries and monitoring become confusing. Clear command/query boundaries also help with transaction settings, caching, metrics, and read-only database routing.

#### Traps / caveats

- CQS is not CQRS; CQRS separates read and write models at an architectural level.
- Logging, metrics, tracing, and caching are side effects, but usually not the domain state changes CQS is warning about.
- A command returning a result is not automatically bad if the command nature is explicit.

#### Optional Anki

Q: What does CQS require?
A: A method should be either a command that changes state or a query that returns data without observable state changes.

</details>

<details>
<summary><strong>🧠 OOP-ENCAP-013. How can encapsulation improve thread-safety?</strong></summary>

#### Short answer

Encapsulation improves thread-safety by keeping mutable state behind a controlled boundary where synchronization, immutability, atomic operations, and safe publication can be enforced consistently.

#### Interview answer

Thread-safety is much harder when any caller can access and mutate internal state. Encapsulation lets the owner decide how state is protected: make it immutable, guard it with a lock, use atomic classes, return snapshots, or expose higher-level atomic operations. For example, `account.withdraw(amount)` can check and update balance under one lock; `getBalance()` plus `setBalance()` cannot protect that invariant across callers.

#### Deep dive

Encapsulation is not enough by itself: the implementation still needs correct concurrency design. But it is a prerequisite for many designs because it prevents reference escape. Returning an internal mutable list lets callers modify it without the object’s lock. Publishing a partially constructed object lets other threads see invalid state. Immutable objects, final fields, defensive copies, and clear ownership rules are common ways to combine encapsulation with thread-safety.

#### Production angle

In backend services this matters for caches, singleton Spring beans, shared clients, in-memory registries, rate limiters, and async processing. A class can document that all mutations go through a few synchronized or atomic methods. If it exposes its internal map or list, that guarantee disappears and race conditions become intermittent production bugs.

#### Traps / caveats

- Encapsulation does not automatically make a class thread-safe; locks, immutability, or atomicity still must be correct.
- Individually thread-safe methods can still be unsafe when a caller needs a multi-step atomic operation.
- JPA entities and request-scoped DTOs should usually not be treated as shared thread-safe objects.

#### Optional Anki

Q: Why does encapsulation help thread-safety?
A: It prevents uncontrolled access to mutable state, so synchronization or immutability can be enforced in one place.

</details>
