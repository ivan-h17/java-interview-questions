<details>
<summary><strong>OOP-JAVA-001. How do records, enums and sealed classes change object modeling in modern Java?</strong></summary>

#### Short answer

Records, enums, and sealed classes give Java more precise modeling tools: records for transparent value carriers, enums for fixed named instances, and sealed types for controlled hierarchies.

#### Interview answer

A record is a good fit for immutable-ish data shapes where component-based equality is desired, such as commands, query results, IDs, or value-like DTOs. An enum is good for a closed set of stable constants with behavior. A sealed interface or class is good when a domain concept has a known set of variants.

Together they reduce the need for defensive class hierarchies, marker subclasses, and stringly typed models.

#### Deep dive

These tools also constrain design. Records are final and expose their components through accessors, so they are not good for behavior-rich entities with hidden representation. Enums are hard to evolve if values are persisted or exposed in APIs. Sealed types make extension explicit, but can be too closed for plugin-style systems.

#### Production angle

In production, records are useful at boundaries and for value-like models, enums are useful for stable state machines or codes, and sealed hierarchies are useful for command/result/error models where exhaustive handling matters.

#### Traps / caveats

- Do not use records for JPA entities with lifecycle and lazy-loading expectations.
- Do not persist enum ordinals; prefer stable explicit codes when values cross boundaries.
- Do not seal a hierarchy that other modules must extend dynamically.

#### Optional Anki

Q: How do records, enums and sealed classes change object modeling in modern Java?
A: Records, enums, and sealed classes give Java more precise modeling tools: records for transparent value carriers, enums for fixed named instances, and sealed types for controlled hierarchies.

<details>
<summary><strong>OOP-JAVA-004. How do equals() and hashCode() relate to object identity and value equality?</strong></summary>

#### Short answer

`==` checks reference identity for objects, while `equals()` defines logical equality; `hashCode()` must be consistent with `equals()` for hash-based collections.

#### Interview answer

For entities, equality is often based on stable identity, such as a database id or business id, but this is tricky before persistence assigns the id. For value objects and records, equality is usually based on components.

If two objects are equal according to `equals()`, they must have the same `hashCode()`. Otherwise `HashMap` and `HashSet` behave incorrectly.

#### Deep dive

Mutable fields used in equality are dangerous. If an object is placed in a `HashSet` and then a field used by `hashCode()` changes, the object may become unreachable inside the set.

#### Production angle

In production, equality bugs appear as duplicate entries, missing cache hits, failed deletes from sets, and persistence bugs with proxies or generated ids.

#### Traps / caveats

- Do not use mutable business fields in `hashCode()` unless objects never live in hash collections while mutable.
- Do not mix `getClass()` and `instanceof` equality casually in inheritance hierarchies.
- Be careful with ORM proxies and generated identifiers.

#### Optional Anki

A: `==` checks reference identity for objects, while `equals()` defines logical equality; `hashCode()` must be consistent with `equals()` for hash-based collections.

<details>
<summary><strong>🧠 OOP-JAVA-007. Why is Cloneable considered problematic?</strong></summary>

#### Short answer

`Cloneable` is problematic because it is a marker interface tied to `Object.clone()`, creates shallow copies by default, bypasses constructors, and has weakly expressed copy semantics.

#### Interview answer

The `Cloneable` interface does not declare a public `clone()` method. It only changes the behavior of `Object.clone()`. That makes the API surprising.

The default clone operation copies fields as if by assignment, so referenced mutable objects are shared unless the class manually fixes them.

#### Deep dive

Because constructors are not called, invariants, validation, and final-field expectations can be subtle. Inheritance makes it even harder because every superclass and subclass must cooperate correctly.

#### Production angle

In modern Java code, prefer copy constructors, static factories, explicit `copyWith...` methods, serialization-specific copying only when needed, or immutable objects that do not need defensive cloning.

#### Traps / caveats

- Do not assume `clone()` means deep copy.
- Do not expose `Cloneable` as a domain-level copy contract without documenting semantics.
- Copying complex mutable object graphs requires explicit ownership decisions.

#### Optional Anki

Q: Why is Cloneable considered problematic?
A: `Cloneable` is problematic because it is a marker interface tied to `Object.clone()`, creates shallow copies by default, bypasses constructors, and has weakly expressed copy semantics.

<details>
<summary><strong>🧠 OOP-JAVA-008. How does Lombok affect OOP design readability?</strong></summary>

#### Short answer

Lombok can reduce boilerplate, but it can also hide constructors, mutability, equality, and generated behavior that are important for understanding an object model.

#### Interview answer

Annotations like `@Getter`, `@Setter`, `@Builder`, `@Data`, and `@EqualsAndHashCode` change the public API of a class. A reader must know Lombok rules to know what methods exist and what they mean.

This is convenient for DTOs, but risky for domain objects where API shape, invariants, and equality are design decisions.

#### Deep dive

`@Data` is especially broad because it creates getters, setters, `toString()`, `equals()`, `hashCode()`, and required-args constructor behavior. That can accidentally turn a domain object into a mutable data bag.

#### Production angle

In production, Lombok can speed development, but teams should define rules: which annotations are allowed on DTOs, entities, value objects, and domain objects; what must be written manually; and how delomboked code is inspected when behavior matters.

#### Traps / caveats

- Do not use `@Setter` everywhere by default.
- Do not hide business invariants behind generated constructors/builders.
- Generated code is still part of the public contract.

#### Optional Anki

Q: How does Lombok affect OOP design readability?
A: Lombok can reduce boilerplate, but it can also hide constructors, mutability, equality, and generated behavior that are important for understanding an object model.

</details>

<details>
<summary><strong>🧠 OOP-JAVA-009. What are the risks of Lombok-generated equals() and hashCode() in entities?</strong></summary>

#### Short answer

Lombok-generated `equals()` and `hashCode()` can be risky in entities because default field-based equality may include mutable fields, generated ids, lazy associations, or bidirectional relationships.

#### Interview answer

An entity usually has identity and lifecycle. If Lombok includes all fields, changing a name, status, or collection can change the hash code after the object is placed in a set.

Including associations can trigger lazy loading, recursion, performance problems, or stack overflows in bidirectional graphs.

#### Deep dive

Generated ids are also tricky: before persistence, id may be `null`; after flush, it changes. Equality that changes during the lifecycle can corrupt hash-based collections.

#### Production angle

For JPA entities, many teams write equality manually or use a stable business key when available. If Lombok is used, include/exclude fields deliberately and test entity equality across lifecycle states.

#### Traps / caveats

- Do not put `@Data` on JPA entities by default.
- Do not include mutable collections or lazy associations in equality.
- Do not cache `hashCode()` for mutable entities.

#### Optional Anki

Q: What are the risks of Lombok-generated equals() and hashCode() in entities?
A: Lombok-generated `equals()` and `hashCode()` can be risky in entities because default field-based equality may include mutable fields, generated ids, lazy associations, or bidirectional relationships.

<details>
<summary><strong>🧠 OOP-JAVA-010. How can serialization or reflection break encapsulation?</strong></summary>

#### Short answer

Serialization and reflection can break encapsulation by creating objects, reading or writing fields, or invoking members in ways normal constructors and access rules would not allow.

#### Interview answer

Java serialization can reconstruct objects from bytes, sometimes bypassing normal construction logic unless special methods and validation are used. Reflection can access members dynamically and, with sufficient access, suppress normal language access checks.

Frameworks use this power for ORM, JSON binding, dependency injection, testing, and migration tools.

#### Deep dive

The design risk is that private fields and constructors no longer fully protect invariants. An object may be instantiated with invalid state, mutated after construction, or exposed through data-binding rules.

For example, a domain object may require `total >= 0` and a non-null currency in its factory method, but a JSON mapper or ORM can populate fields separately through reflection or a no-arg constructor. If validation is only in the factory, deserialization can create a state normal application code could never create.

#### Production angle

In production, protect boundaries with validation after deserialization, immutable DTOs where possible, explicit constructors/factories, module `opens` discipline, and careful framework configuration.

#### Traps / caveats

- Do not assume `private` is an absolute runtime security boundary.
- Do not deserialize untrusted data with unsafe mechanisms.
- Do not let frameworks populate domain objects into invalid states without validation.

#### Optional Anki

Q: Why is validation needed even when domain constructors protect invariants?
A: Reflection, ORM, or JSON binding may instantiate objects and set fields outside normal constructors, so boundary validation must still reject invalid state.

</details>

<details>
<summary><strong>🧠 OOP-JAVA-011. How does the Java module system affect encapsulation?</strong></summary>

#### Short answer

The Java module system strengthens encapsulation by making module dependencies explicit and allowing modules to export or open only selected packages.

#### Interview answer

Before modules, `public` mainly meant public on the classpath. With JPMS, a public type in a package is accessible to other modules only when the package is exported and the consuming module reads the module.

`exports` is for compile-time and normal runtime access to public API. `opens` is for reflective access, commonly used by frameworks.

#### Deep dive

This helps separate API packages from internal packages. It also makes accidental reflection harder unless a package is opened. However, many Spring/JPA applications still run on the classpath or use broad opens, so the benefit depends on actual module discipline.

#### Production angle

In production libraries, JPMS can make boundaries explicit and reduce accidental coupling. In applications, it can reveal hidden dependencies but may add build and framework integration complexity.

#### Traps / caveats

- Do not export internal packages just to make compilation easy.
- Use `opens` narrowly for frameworks that need reflection.
- JPMS complements package design; it does not replace good API boundaries.

#### Optional Anki

Q: How does the Java module system affect encapsulation?
A: The Java module system strengthens encapsulation by making module dependencies explicit and allowing modules to export or open only selected packages.
