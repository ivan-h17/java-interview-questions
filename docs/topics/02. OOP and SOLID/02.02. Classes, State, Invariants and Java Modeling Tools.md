<a id="oop-class-001"></a>

<details>
<summary><strong>OOP-CLASS-001. What should a constructor do?</strong></summary>

#### Short answer

A constructor should create a valid object by initializing required state, validating inputs, and establishing invariants. It should avoid heavy work, hidden side effects, and calling overridable methods.

#### Interview answer

The main responsibility of a constructor is to make the object usable immediately after creation. Required dependencies and mandatory values should be provided, invalid combinations rejected, and mutable inputs copied when needed.

A constructor should usually not open network connections, start threads, perform database writes, publish events, or call methods that subclasses can override. If creation is complex, a static factory, builder, or factory object can express intent better.

#### Deep dive

Constructor validation protects invariants. A `DateRange` constructor should reject an end date before a start date. A `Money` constructor should reject missing currency or invalid scale if those are domain rules.

Constructors also define ownership. If the object stores a mutable collection from the caller, it should usually copy it; otherwise the caller can mutate the collection later and break invariants without invoking the object.

#### Production angle

Bad constructors create partially initialized objects, hidden latency, and hard-to-test side effects. Good constructors fail early and explicitly, which is important for configuration objects, domain values, and required dependencies.

#### Traps / caveats

- Do not create an invalid object and plan to “fix it later”.
- Do not call overridable methods from constructors.
- Do not store caller-owned mutable collections without copying or an explicit ownership contract.
- Use factories or builders when constructor parameters become ambiguous.

#### Optional Anki

Q: Main job of a constructor?
A: Create a fully initialized valid object and establish invariants.

</details>

<details>
<summary><strong>OOP-CLASS-002. What is an object invariant?</strong></summary>

#### Short answer

An object invariant is a condition that must remain true for an object to be valid whenever it is observable by other code.

#### Interview answer

Examples: an order total equals the sum of order lines; a date range has `start <= end`; an account balance cannot be negative; a paid order cannot be edited. Constructors establish invariants, and every mutating method must preserve them.

Invariants are a practical reason for encapsulation. If callers freely set fields, they can create combinations the object should never allow.

#### Deep dive

Invariants may be structural, such as non-null fields and consistent collections, or business-level, such as status transitions and limits. Some invariants belong to one object; others belong to an aggregate or transaction boundary.

In concurrent code, an invariant also needs atomicity and visibility. A method can be correct in single-threaded code but broken if another thread observes intermediate state.

#### Production angle

Production incidents often come from missing invariants: negative balances, impossible statuses, duplicate active subscriptions, or mismatched totals. Clear invariants guide tests, validation, database constraints, and transaction boundaries.

#### Traps / caveats

- Field validation is not enough when validity depends on relationships between fields.
- Some invariants need database constraints or transactions, not only Java code.
- Mutable internals must not let callers bypass invariant checks.
- Temporary invariant violations inside a method should not be observable.

#### Optional Anki

Q: What is an invariant?
A: A condition that must remain true for an object or aggregate to be valid.

</details>

<details>
<summary><strong>OOP-CLASS-004. What is the difference between a mutable and immutable object?</strong></summary>

#### Short answer

A mutable object can change its observable state after construction. An immutable object cannot change its observable state after construction.

#### Interview answer

A mutable `Order` may move from `DRAFT` to `CONFIRMED`. An immutable `Money` or `DateRange` returns a new object when a change is needed. Immutability makes objects easier to reason about because there are no hidden state changes.

In Java, immutability usually requires final fields, no setters, constructor validation, no leaking mutable internals, and defensive copies of mutable inputs and outputs.

#### Deep dive

Mutable objects are useful for entities with lifecycle and controlled transitions. Immutable objects are useful for values, configuration, messages, commands, events, and keys in collections. Immutability often improves thread-safety when objects are safely published.

The cost of immutability is object creation and sometimes awkward updates for large graphs. The cost of mutability is defensive design: ownership, synchronization, copying, and careful APIs.

#### Production angle

Immutability helps avoid accidental cross-request changes and concurrency defects. Mutable state is still necessary for many domain entities and persistence models, but it should be owned and modified through explicit operations.

#### Traps / caveats

- `final` prevents field reassignment, not mutation of the referenced object.
- A record is not deeply immutable if its components are mutable.
- Mutable objects should not be hash keys if equality depends on mutable fields.
- Immutability does not remove the need for validation.

#### Optional Anki

Q: Mutable vs immutable object?
A: Mutable state can change after construction; immutable observable state cannot.

</details>

<a id="oop-class-005"></a>

<details>
<summary><strong>OOP-CLASS-005. How should mutable state be controlled inside an object?</strong></summary>

#### Short answer

Mutable state should have a clear owner, be private, be changed through meaningful methods, preserve invariants, and not leak through mutable getters or shared references.

#### Interview answer

Avoid arbitrary setters and expose domain operations instead. `order.addItem(product, quantity)` can validate quantity, update totals, and reject changes after confirmation. A raw `setItems()` makes every caller responsible for correctness.

For mutable collections, copy inputs, return immutable snapshots or unmodifiable views when appropriate, and keep mutation methods inside the owner object. For concurrent access, use synchronization, locks, immutable snapshots, or thread confinement.

#### Deep dive

Controlling mutable state narrows the mutation surface. The fewer places can change state, the easier it is to reason about invariants. Prefer private fields, constructor validation, use-case methods, and small state transitions.

Ownership is critical. If an object owns a list, callers should not mutate it directly. If ownership is intentionally shared, document and protect the contract.

#### Production angle

Uncontrolled mutable state causes data to change between validation and persistence, cached objects to be accidentally modified, and concurrent requests to see inconsistent intermediate state.

#### Traps / caveats

- Public setters for every field are a common sign of weak encapsulation.
- Returning a mutable collection from a getter exposes internal representation.
- An unmodifiable view is not the same as an immutable snapshot.
- Thread-safety is part of state control when objects are shared.

#### Optional Anki

Q: Main rule for mutable state?
A: Give it one clear owner and mutate it only through operations that preserve invariants.

</details>

<a id="oop-class-006"></a>

<details>
<summary><strong>OOP-CLASS-006. When would you use a static factory method instead of a constructor?</strong></summary>

#### Short answer

Use a static factory method when creation needs a meaningful name, validation alternatives, caching, subtype selection, conversion, or hidden construction details. Use a constructor when creation is simple and obvious.

#### Interview answer

A constructor can only have the class name, so it cannot explain intent well. Static factories can be named: `Money.of("USD", amount)`, `UserId.fromString(raw)`, `Order.draft(customerId)`. They can return cached instances, a subtype, or a normalized value.

Factories help when there are multiple ways to create an object with the same parameter types, when parameters are ambiguous, or when construction should be centralized.

#### Deep dive

Common names communicate semantics: `of()` for already valid values, `from()` for conversion, `parse()` for parsing that may fail, `valueOf()` for value-based conversion possibly using caching.

A static factory is not the Factory Method pattern. Static factories are class-level methods. A factory object is better when creation needs dependencies, polymorphism, or test replacement.

#### Production angle

Static factories improve readability and backward compatibility. Behind the same method you can add validation, caching, normalization, or implementation selection. But they should not hide slow I/O or surprising side effects.

#### Traps / caveats

- Do not hide slow I/O or database calls behind a factory that looks cheap.
- Private constructors plus static factories can make subclassing impossible.
- Static factories are harder to mock than injected factory objects.
- Do not replace every constructor with a factory by default.

#### Optional Anki

Q: Why use a static factory?
A: It can have a meaningful name and hide validation, caching, conversion, or implementation selection.

</details>

<a id="oop-class-007"></a>

<details>
<summary><strong>OOP-CLASS-007. What are instance methods vs static methods, and what are the risks of static-heavy design?</strong></summary>

#### Short answer

Instance methods are invoked on an object and can use its state and polymorphism. Static methods belong to the class and are useful for stateless utilities or factories, but static-heavy design often hides dependencies and hurts testability.

#### Interview answer

An instance method has a receiver object: `order.cancel()` works on a particular order. A static method has no receiver instance: `Money.of()` or `Math.max()` belongs to the class level.

Static methods are fine for pure functions, constants, simple factories, and utility operations. Problems appear when static methods hold mutable global state, call external systems, read configuration, or replace dependency injection.

#### Deep dive

Static-heavy code looks convenient at first because calls are short and no object graph is needed. Over time it can create tight coupling: application code calls `EmailSender.send()` or `Config.get()` from anywhere, making boundaries unclear.

Instance methods are not automatically better. A stateless helper object injected everywhere is also noise. The question is whether the operation needs state, polymorphism, dependencies, lifecycle, or replacement.

#### Production angle

Production issues include hidden global caches, test pollution, hard-to-control time and randomness, and configuration read from unexpected places. Injecting clocks, clients, repositories, and policies usually gives better control.

#### Traps / caveats

- Static methods are not evil; static mutable state and hidden side effects are the usual problem.
- Static dispatch does not support normal runtime polymorphism.
- A utility class can become a dumping ground for unrelated behavior.
- Instance methods can also be poorly designed if they do not belong to the object responsibility.

#### Optional Anki

Q: Main risk of static-heavy design?
A: Hidden dependencies, global mutable state, poor testability, and loss of polymorphic replacement.

</details>

<details>
<summary><strong>🧠 OOP-CLASS-008. When is an enum a better model than a class hierarchy?</strong></summary>

#### Short answer

An enum is better when the set of variants is small, fixed, known at compile time, and each variant is primarily a named singleton value with optional simple behavior.

#### Interview answer

Use an enum for concepts such as `OrderStatus`, `PaymentType`, or `RiskLevel`, where callers should not create new values dynamically. Enums are type-safe, self-documenting, and can contain fields and methods when behavior is simple.

A class hierarchy is better when each variant has substantial state, independent lifecycle, different dependencies, or external extensibility. Sealed classes are a middle ground for closed variants with different data.

#### Deep dive

Enums are instances, not integer constants. They can implement interfaces and define per-constant behavior. This is useful for small policies, but awkward when behavior needs repositories, remote clients, or complex configuration.

Avoid enum for frequently changing business data. If admins must add values without redeploying, the concept may belong in configuration or a database.

#### Production angle

Enums are excellent for stable protocol values and internal state machines, but they create deployment coupling when the value set changes frequently. Persisting enum names is readable but renames are breaking; persisting ordinals is usually dangerous.

#### Traps / caveats

- Do not persist enum ordinals unless migration risk is fully controlled.
- An enum is poor for user-extensible or frequently changing reference data.
- Do not inject infrastructure dependencies into enum constants.
- A giant enum with many unrelated methods may be a hidden God Object.

#### Optional Anki

Q: When is enum better than hierarchy?
A: When variants are fixed, known, named singleton values with simple optional behavior.

</details>

<details>
<summary><strong>OOP-CLASS-009. When is a record a good or bad fit for object modeling?</strong></summary>

#### Short answer

A record is good for transparent, value-like, mostly immutable data carriers such as DTOs, commands, events, and small value objects. It is bad for identity-based entities, complex lifecycle, hidden mutable state, or representation hiding.

#### Interview answer

A Java record declares its state in the header and gets a canonical constructor, accessors, `equals()`, `hashCode()`, and `toString()` based on components. That makes it excellent for shapes such as `record EmailAddress(String value)` or `record OrderCreated(UUID orderId, Instant createdAt)`.

A record is transparent by design: its components are the public API. If you need to hide representation, control identity, support lazy loading, or expose behavior without committing to fields, a normal class is usually better.

#### Deep dive

Records can have compact constructors for validation and methods, so they are not limited to dumb data. However, they cannot declare extra instance fields beyond components and are implicitly final. Their equality is component-based.

Records are shallowly immutable. If a component is `List<Item>`, the reference is final, but the list contents may still change. For stronger immutability, copy mutable inputs, often with `List.copyOf()`.

#### Production angle

Records reduce boilerplate for request/response DTOs, messages, projections, and value objects. Be careful with frameworks that require no-arg constructors, proxies, field mutation, or identity semantics.

#### Traps / caveats

- A record is not automatically deeply immutable.
- Record component names and types become part of the public contract.
- Component-based equality is usually wrong for mutable or identity-based entities.
- Do not use records only to reduce boilerplate if the model needs hidden representation.

#### Optional Anki

Q: Best use for records?
A: Transparent value-like data carriers with component-based equality and little hidden state.

</details>

<details>
<summary><strong>OOP-CLASS-010. How do access modifiers and package boundaries support encapsulation?</strong></summary>

#### Short answer

Access modifiers and package boundaries restrict what code can see and call. They help expose a small stable API while keeping implementation details private to a class, package, module, or layer.

#### Interview answer

In Java, `private` keeps members inside the class, package-private keeps them inside the package, `protected` exposes them to subclasses and same-package code, and `public` exposes them broadly. A good design makes only the intended API public.

Package boundaries are useful: put an aggregate and helper classes in one package, expose only the aggregate root publicly, and keep internal policies package-private so unrelated code cannot bypass rules.

#### Deep dive

Visibility is a design tool. Every public type or method becomes something callers may depend on, so changing it later is harder. Package-private classes are valuable for implementation details that need collaboration but should not become external API.

`protected` is often overused. It exposes internals to subclasses and same-package code, and subclass coupling can be fragile.

#### Production angle

Accidental public APIs become long-term maintenance costs. Good package boundaries let teams refactor internals and keep controllers, persistence models, and domain internals from depending on each other accidentally.

#### Traps / caveats

- Public should mean “supported contract”, not “I needed access from a test”.
- `protected` can leak implementation details and create fragile inheritance coupling.
- Package-private works best when packages represent cohesive modules, not random folders.
- Reflection and frameworks can bypass visibility, but that does not make visibility irrelevant.

#### Optional Anki

Q: Why use package-private?
A: To let collaborating classes work together while keeping implementation details outside the public API.

</details>

<details>
<summary><strong>🧠 OOP-CLASS-011. What are nested classes and when are they useful?</strong></summary>

#### Short answer

A nested class is a class declared inside another class or interface. It is useful for helper types, builders, adapters, iterators, private implementation details, and tightly scoped concepts.

#### Interview answer

Java has static nested classes, inner classes, local classes, and anonymous classes. A static nested class does not need an instance of the outer class. A non-static inner class has a reference to an enclosing instance, which can be useful but can also keep the outer object alive longer than expected.

Use nested classes when the type is strongly tied to the outer type and not useful on its own, for example `Order.Builder`, a private `Node`, or an adapter implementation.

#### Deep dive

A static nested class is usually safer as a default because it does not capture the outer instance. Inner classes are useful when they intentionally need access to outer instance state, for example an iterator over a custom collection.

Nested classes help encapsulation by keeping implementation types private and organized. Too much nesting makes code harder to navigate, especially if the nested type grows into an independent concept.

#### Production angle

Nested helpers reduce public API noise. The main production risk is accidental retention of outer instances by non-static inner classes, which can cause memory leaks in listeners, callbacks, caches, or long-lived tasks.

#### Traps / caveats

- Prefer static nested classes unless access to the outer instance is required.
- A non-static inner class holds an enclosing instance reference.
- Do not hide a large independent domain concept as a private nested class.
- Anonymous classes can capture variables; be careful with lifecycle and readability.

#### Optional Anki

Q: Static nested vs inner class?
A: Static nested class has no outer instance; inner class is tied to an enclosing object instance.

</details>

<details>
<summary><strong>🧠 OOP-CLASS-012. When can sealed classes or sealed interfaces make a model safer?</strong></summary>

#### Short answer

Sealed classes or interfaces make a model safer when the set of allowed subtypes should be closed and known, so the compiler and maintainers can reason about all valid variants.

#### Interview answer

A sealed hierarchy is useful for domain alternatives such as `PaymentResult`, `OrderCommand`, `DiscountRule`, or `DeliveryOption`, when only a controlled set of implementations is valid. It prevents unrelated code from adding unsupported subtypes.

For example, `sealed interface PaymentResult permits Authorized, Declined, Failed` says that these are the only direct results. Each subtype can be a record carrying different data.

#### Deep dive

Sealed types work well with records and pattern matching. They model a closed sum type: a value is one of a known set of alternatives. The compiler can help with exhaustive handling depending on the Java version and language features used.

Use sealed types when you own the hierarchy and want controlled extension. Do not use them for plugin APIs or public extension points where third-party implementations are intended.

#### Production angle

Sealed models reduce invalid implementations and make changes explicit. Adding a new subtype forces review of places that handle the hierarchy, which is valuable for workflows, error models, commands, and state transitions.

#### Traps / caveats

- Sealed types are for closed hierarchies, not open plugin systems.
- Direct permitted subclasses must choose `final`, `sealed`, or `non-sealed`.
- A sealed hierarchy can still have poor contracts; sealing only controls who can implement it.
- Do not use sealed classes where a simple enum is enough.

#### Optional Anki

Q: Why use sealed classes/interfaces?
A: To restrict a hierarchy to a known set of valid subtypes and make handling safer.

</details>
