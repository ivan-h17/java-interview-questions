# 02.10. Spring Backend Architecture and Persistence Boundaries

---

<a id="oop-be-001"></a>

<details>
<summary><strong>OOP-BE-001. How should responsibilities be split between Controller, Service and Repository?</strong></summary>

#### Short answer

A controller should handle HTTP concerns, a service should coordinate an application use case, and a repository should abstract persistence access.

#### Interview answer

In a typical Spring backend, the controller maps requests, validates input shape, handles status codes, and delegates. The service owns the use-case workflow: authorization checks, transaction boundary, domain calls, persistence calls, and integration coordination. The repository loads and saves aggregates or entities without exposing SQL, JPA, or storage details to the service more than necessary.

A useful rule is: the controller speaks HTTP, the service speaks application language, and the repository speaks persistence language.

#### Deep dive

This split is about responsibility, not about forcing every request through three classes. Very simple CRUD endpoints may have thin services, but business rules should not be scattered across controllers and repositories.

The service should usually not become a dumping ground either. If it contains complex business decisions, push rules into domain objects, domain services, policies, validators, or workflow components with clear names.

#### Production angle

In production, this separation helps with observability and failure isolation: HTTP mapping bugs are debugged in controllers, transaction and orchestration bugs in services, and query/fetching bugs in repositories.

It also makes refactoring safer because API contracts, use-case contracts, and persistence contracts can evolve separately.

#### Traps / caveats

- Do not put business decisions in controllers just because the code is short.
- Do not put authorization, transactions, and external calls into repositories.
- Do not assume a class annotated `@Service` is automatically a well-designed service.

#### Optional Anki

Q: How should responsibilities be split between Controller, Service and Repository?
A: A controller should handle HTTP concerns, a service should coordinate an application use case, and a repository should abstract persistence access.

</details>

<details>
<summary><strong>OOP-BE-002. What is the difference between an application service and a domain service?</strong></summary>

#### Short answer

An application service orchestrates a use case; a domain service contains domain logic that does not naturally belong to one entity or value object.

#### Interview answer

An application service is part of the application layer. It answers: “What should happen when this use case is executed?” It starts transactions, loads objects, calls domain behavior, saves results, publishes events, and maps results to the outside world.

A domain service is part of the domain model. It answers: “What is the business rule?” For example, pricing across several products, eligibility rules, or allocation logic may need a domain service when no single entity should own the whole rule.

#### Deep dive

Application services are allowed to depend on repositories, clocks, gateways, and transactions. Domain services should ideally be independent of Spring, HTTP, JPA, messaging, and database transactions. They should be easy to unit-test without a container.

If a “domain service” mainly calls repositories and external APIs, it is probably an application service or an infrastructure adapter with a domain-sounding name.

#### Production angle

This distinction prevents business logic from being tied to framework lifecycle and makes rules reusable from REST, messaging, batch jobs, and tests.

It also helps reviewers see whether a change affects business policy or only use-case orchestration.

#### Traps / caveats

- Do not call every Spring `@Service` a domain service.
- Do not move logic to a domain service if it clearly belongs inside an entity that owns the data and invariant.
- Do not inject repositories into pure domain services unless you intentionally accept that coupling.

#### Optional Anki

Q: What is the difference between an application service and a domain service?
A: An application service orchestrates a use case; a domain service contains domain logic that does not naturally belong to one entity or value object.

</details>

<details>
<summary><strong>OOP-BE-003. What is the difference between DTO, entity and domain model?</strong></summary>

#### Short answer

A DTO is a boundary data shape, an entity is an object with identity and lifecycle, and a domain model is the set of domain concepts, rules, and behaviors used to solve business problems.

#### Interview answer

A DTO is optimized for transfer: REST request, REST response, messaging payload, or external API contract. It usually has little or no behavior.

An entity is defined by identity and lifecycle. In JPA, `@Entity` also means a persistence-mapped class, but in domain modeling “entity” means a domain object whose identity matters over time.

A domain model is broader: entities, value objects, domain services, policies, events, and invariants that represent the business.

#### Deep dive

The same Java class can sometimes serve as both JPA entity and domain entity, but that is a trade-off. It couples persistence constraints, lazy loading, proxies, and annotations to domain design.

DTOs should not become the internal domain model by accident. When services pass request DTOs everywhere, validation and business rules often become procedural and duplicated.

#### Production angle

Separating DTOs from domain objects protects API compatibility. You can change database mappings or domain internals without breaking clients, and you can version API payloads independently.

It also reduces security bugs where internal fields, flags, or relationships are serialized unintentionally.

#### Traps / caveats

- Do not expose persistence entities as API DTOs by default.
- Do not confuse a JPA entity with a rich domain model; it may be only a persistence record.
- Do not create DTOs for every internal method call when a domain object would be clearer.

#### Optional Anki

Q: What is the difference between DTO, entity and domain model?
A: A DTO is a boundary data shape, an entity is an object with identity and lifecycle, and a domain model is the set of domain concepts, rules, and behaviors used to solve business problems.

</details>

<details>
<summary><strong>OOP-BE-004. Why should REST controllers usually not contain business logic?</strong></summary>

#### Short answer

REST controllers should stay thin because their responsibility is transport: mapping HTTP to application use cases, not owning business rules.

#### Interview answer

Controllers know about paths, headers, status codes, validation errors, request and response DTOs, and security context extraction. Business logic should live in services and domain objects where it can be reused from other entry points.

When a controller contains pricing, state transitions, limits, or persistence decisions, the same rules are hard to reuse for Kafka consumers, scheduled jobs, CLI tools, batch processing, or integration tests.

#### Deep dive

Thin does not mean empty. A controller may perform syntactic validation, choose response codes, translate exceptions, and call one or more application services. It should not decide business policy.

If a controller method grows because of mapping code, extracting a mapper may be useful. If it grows because of business decisions, the design boundary is probably wrong.

#### Production angle

Keeping controllers thin makes API tests smaller and domain tests faster. It also makes production incidents easier to trace: transport failures and business failures are separated.

In distributed systems, this matters because the same use case is often triggered by HTTP, messages, retries, or admin tools.

#### Traps / caveats

- Do not hide all logic behind a generic `execute()` service just to keep the controller tiny.
- Do not duplicate validation: syntactic input validation belongs near the boundary; domain invariants belong in the domain.
- Do not let controllers open transactions manually unless there is a very specific reason.

#### Optional Anki

Q: Why should REST controllers usually not contain business logic?
A: REST controllers should stay thin because their responsibility is transport: mapping HTTP to application use cases, not owning business rules.

</details>

<details>
<summary><strong>OOP-BE-006. Should services always have interfaces in Spring?</strong></summary>

#### Short answer

No. A service interface is useful when it represents a real contract or variation point; otherwise a single implementation interface can add noise.

#### Interview answer

In Spring, a service does not need an interface just to be injectable. Constructor injection works with concrete classes. Interfaces are valuable when there are multiple implementations, module boundaries, contract tests, adapters, public extension points, or a need to hide infrastructure details from a higher layer.

A forced `UserService` plus `UserServiceImpl` pair often creates ceremony without reducing coupling, because the interface mirrors the implementation exactly.

#### Deep dive

The key question is not “interface or class?” but “who owns the abstraction?” If the application core defines `PaymentGateway`, that is a meaningful port. If a class defines `UserService` only because Spring examples used interfaces, the abstraction may be speculative.

Testing is not always enough justification. Modern mocking tools can mock classes, and many tests should use real collaborators when they are cheap and deterministic.

#### Production angle

Unnecessary service interfaces slow navigation, duplicate Javadoc, and make refactoring more expensive. Useful interfaces, however, protect architecture boundaries and make integration replacement explicit.

A good code review asks whether the interface has a stable semantic contract or only copies today’s methods.

#### Traps / caveats

- Do not create interfaces mechanically for every `@Service`.
- Do not name every implementation `*Impl` when a domain-specific name would be clearer.
- Do not remove interfaces that define module contracts, ports, or multiple implementations just because there is currently one adapter.

#### Optional Anki

Q: Should services always have interfaces in Spring?
A: No. A service interface is useful when it represents a real contract or variation point; otherwise a single implementation interface can add noise.

</details>

<details>
<summary><strong>🧠 OOP-BE-007. How can Spring annotations leak infrastructure concerns into domain code?</strong></summary>

#### Short answer

Spring annotations leak infrastructure when domain objects depend on framework lifecycle, transactions, persistence, scheduling, security, or messaging instead of expressing pure business concepts.

#### Interview answer

Annotations such as `@Entity`, `@Transactional`, `@Autowired`, `@Component`, `@Async`, or messaging annotations are not bad by themselves. The problem appears when they make the domain model require Spring or JPA to be valid, testable, or understandable.

For example, a domain object that publishes through `ApplicationEventPublisher`, reads `SecurityContextHolder`, or relies on lazy-loaded relationships is no longer just a domain object. It knows how the application is wired.

#### Deep dive

There are several levels of compromise. A pragmatic project may use JPA annotations directly on domain entities. A stricter hexagonal design keeps domain classes free of Spring annotations and maps them to persistence models or adapters.

The decision depends on complexity. For CRUD systems, direct JPA entities may be fine. For complex business rules, avoiding framework dependencies can keep the model simpler and more durable.

#### Production angle

Framework leakage often becomes visible during tests, migration, or performance work: domain tests require a Spring context, persistence proxies appear in business logic, or transaction behavior changes method semantics.

A good boundary lets you test rules with plain objects and test framework integration separately.

#### Traps / caveats

- Do not treat every annotation as leakage; annotations on adapters and configuration are normal.
- Do not over-isolate simple CRUD code if mapping cost is higher than the benefit.
- Do not let domain methods depend on an active transaction unless that is an explicit design choice.

#### Optional Anki

Q: How can Spring annotations leak infrastructure concerns into domain code?
A: Spring annotations leak infrastructure when domain objects depend on framework lifecycle, transactions, persistence, scheduling, security, or messaging instead of expressing pure business concepts.

</details>

<details>
<summary><strong>🧠 OOP-BE-008. How does OOP design change when using JPA entities?</strong></summary>

#### Short answer

JPA adds persistence constraints to object design: identity, no-arg constructors, non-final classes, lazy loading, proxies, managed/detached states, and ORM relationship rules.

#### Interview answer

A plain domain object can be designed only around business invariants. A JPA entity must also satisfy provider requirements and mapping behavior. It needs a primary key, a public or protected no-arg constructor, persistent fields/properties, and it usually cannot rely on final classes or final persistent members.

The object also has persistence lifecycle states. A method that works on a managed entity inside a transaction may fail or trigger unexpected queries when called on a detached entity outside a transaction.

#### Deep dive

JPA can encourage bidirectional associations, mutable collections, protected setters, and technical constructors. Those choices may conflict with strong encapsulation. You can still keep invariants by using behavior methods such as `order.addItem(...)`, limiting setters, and maintaining both sides of associations in one place.

For complex models, teams sometimes separate persistence entities from domain objects. That avoids ORM constraints in the domain but adds mapping and synchronization cost.

#### Production angle

Most production JPA bugs are boundary bugs: lazy initialization outside a transaction, accidental N+1 queries, unexpected dirty checking, cascades deleting too much, or equality based on mutable fields.

Designing entities with small aggregate boundaries and explicit methods reduces these risks.

#### Traps / caveats

- Do not design JPA entities as if they were immutable records.
- Do not expose persistent collections directly as mutable lists.
- Do not base `equals()` and `hashCode()` on mutable state or lazy associations.

#### Optional Anki

Q: How does OOP design change when using JPA entities?
A: JPA adds persistence constraints to object design: identity, no-arg constructors, non-final classes, lazy loading, proxies, managed/detached states, and ORM relationship rules.

</details>

<a id="oop-be-009"></a>

<details>
<summary><strong>🧠 OOP-BE-009. Should JPA entities contain business behavior?</strong></summary>

#### Short answer

They can contain business behavior, especially invariant-preserving behavior, but they should not contain infrastructure orchestration or framework-dependent workflows.

#### Interview answer

A JPA entity does not have to be an anemic data holder. Methods like `order.confirm()`, `account.withdraw(amount)`, or `subscription.cancel(reason)` can be a good place for rules that protect the entity’s state.

However, a JPA entity should usually not send emails, call remote APIs, open transactions, publish directly through Spring, or query repositories. Those are application or infrastructure responsibilities.

#### Deep dive

A rich JPA entity works best when behavior depends on its own state and owned child objects. When behavior needs several aggregates, repositories, external services, or policies, use an application service plus domain service/policy object.

Be careful with lazy relationships. A domain method that walks a large graph can hide database access and make object behavior surprisingly expensive.

#### Production angle

Behavior inside entities reduces duplicated rules and invalid states, but only if transaction and fetching boundaries are understood.

In code reviews, look for entities with only setters and services that manually enforce every state transition; that is often a sign that behavior belongs closer to the data.

#### Traps / caveats

- Do not inject Spring beans into JPA entities.
- Do not make entity methods depend on hidden lazy loading unless it is deliberate and tested.
- Do not put cross-aggregate workflow into one entity just to make the model “rich”.

#### Optional Anki

Q: Should JPA entities contain business behavior?
A: They can contain business behavior, especially invariant-preserving behavior, but they should not contain infrastructure orchestration or framework-dependent workflows.

</details>

<details>
<summary><strong>OOP-BE-010. What are the risks of exposing JPA entities through REST APIs?</strong></summary>

#### Short answer

Exposing JPA entities through REST couples the public API to persistence internals and can cause security leaks, lazy loading bugs, recursion, over-posting, and compatibility problems.

#### Interview answer

A REST API is a public contract. A JPA entity is an internal persistence model. If the same class is serialized directly, database fields, relationships, technical IDs, flags, and internal state can leak to clients.

Deserializing requests into entities is also risky: clients may set fields they should not control, such as status, owner, version, audit fields, or associations.

#### Deep dive

Serialization can trigger lazy loading and N+1 queries, fail with lazy initialization errors, or recurse through bidirectional relationships. Adding Jackson annotations to entities can hide symptoms but usually increases coupling between API and persistence.

DTOs let you design the API intentionally: flatten data, hide internals, validate input, version payloads, and choose fetch plans explicitly.

#### Production angle

In production, direct entity exposure often becomes painful when API compatibility conflicts with schema refactoring. A column rename, relation split, or entity redesign suddenly becomes a breaking API change.

It can also create data breach incidents when a newly added internal field is automatically serialized.

#### Traps / caveats

- Do not rely on `@JsonIgnore` as the main API design tool.
- Do not accept entity objects as request bodies for commands that should allow only specific fields.
- For internal admin-only tools the trade-off may be acceptable, but make it explicit.

#### Optional Anki

Q: What are the risks of exposing JPA entities through REST APIs?
A: Exposing JPA entities through REST couples the public API to persistence internals and can cause security leaks, lazy loading bugs, recursion, over-posting, and compatibility problems.

</details>

<details>
<summary><strong>🧠 OOP-BE-012. How do transactional boundaries influence class design?</strong></summary>

#### Short answer

Transactional boundaries define which operations must be atomic and consistent, so they often belong around application use cases rather than arbitrary helper methods.

#### Interview answer

A transaction boundary is a design boundary. It answers which reads, writes, validations, and domain events belong to one unit of work. In Spring, this boundary is commonly placed on application service methods such as `placeOrder()` or `transferMoney()`.

That placement keeps controllers outside persistence details and keeps repositories focused on data access.

#### Deep dive

Transactions influence method size and object collaboration. If one service method must update five aggregates, publish messages, and call remote APIs, it may be mixing transaction work with distributed workflow. You may need smaller aggregate boundaries, domain events, outbox, saga/process manager, or after-commit hooks.

Propagation and proxy behavior also matter. A method annotated with `@Transactional` may not apply if it is called through `this` inside the same object in proxy mode.

#### Production angle

Bad transaction boundaries cause long locks, stale reads, partial updates, duplicate side effects, and lazy loading failures. Good boundaries make consistency rules explicit and keep external I/O outside database transactions when possible.

For message publishing, prefer patterns that coordinate with commit, such as transactional outbox, rather than sending to Kafka in the middle of a database transaction.

#### Traps / caveats

- Do not put `@Transactional` everywhere “just in case”.
- Do not perform slow remote calls while holding database locks unless you understand the consequences.
- Do not assume nested private or self-invoked methods get Spring transactional advice.

#### Optional Anki

Q: How do transactional boundaries influence class design?
A: Transactional boundaries define which operations must be atomic and consistent, so they often belong around application use cases rather than arbitrary helper methods.

</details>

<details>
<summary><strong>🧠 OOP-BE-013. How can domain events reduce coupling?</strong></summary>

#### Short answer

Domain events reduce coupling by representing important business facts and letting other components react without the producer knowing every consumer.

#### Interview answer

Instead of `OrderService` directly calling invoicing, email, analytics, loyalty, and shipping code, it can record that `OrderPlaced` happened. Handlers decide what to do with that fact.

The producer then depends on a stable domain event concept, not on every downstream workflow. This is especially useful when side effects are optional, asynchronous, or owned by different modules.

#### Deep dive

A domain event should describe something that already happened in business language, not an instruction like `SendEmailCommand`. It should contain enough information for subscribers, but not expose the entire mutable aggregate unless that is intentional.

Inside one process, events may be synchronous. Across services, you need delivery, ordering, idempotency, retries, and usually an outbox to avoid losing events after database commit.

#### Production angle

Domain events are useful for audit trails, notifications, integration, cache invalidation, and eventual consistency. They make new reactions easier to add without modifying the core use case repeatedly.

They also improve incident analysis because business facts become explicit and observable.

#### Traps / caveats

- Do not use events to hide required synchronous validation.
- Do not publish before commit if consumers assume committed state.
- Do not make events so generic that subscribers must query many services to understand them.

#### Optional Anki

Q: How can domain events reduce coupling?
A: Domain events reduce coupling by representing important business facts and letting other components react without the producer knowing every consumer.

</details>

<details>
<summary><strong>🧠 OOP-BE-015. What is the difference between layered architecture and hexagonal architecture?</strong></summary>

#### Short answer

Layered architecture organizes code by technical layers; hexagonal architecture centers the application/domain core and connects external systems through ports and adapters.

#### Interview answer

A typical layered architecture has Controller, Service, Repository, and Database layers. Dependencies usually flow downward: web depends on service, service depends on repository, repository depends on persistence.

Hexagonal architecture asks the core to define ports for what it needs and what it exposes. Adapters implement those ports for REST, persistence, messaging, external APIs, CLI, or tests. The core should not depend on adapter details.

#### Deep dive

Layering is simple and familiar, but it can still allow business code to depend directly on infrastructure types. Hexagonal design makes the dependency direction more explicit: domain/application code owns the abstractions, infrastructure plugs in.

They are not mutually exclusive. A hexagonal application may still have internal layers, and a layered Spring app can use ports for important boundaries.

#### Production angle

Hexagonal architecture pays off when the domain is valuable, integrations change, tests should run without infrastructure, or the same use case has multiple entry points.

Layered architecture is often enough for straightforward CRUD or small services where mapping overhead would dominate.

#### Traps / caveats

- Do not call a project hexagonal just because packages are named `ports` and `adapters`.
- Do not add mapping layers mechanically when the model has little behavior.
- Do not let persistence annotations or vendor SDK types leak into ports that belong to the core.

#### Optional Anki

Q: What is the difference between layered architecture and hexagonal architecture?
A: Layered architecture organizes code by technical layers; hexagonal architecture centers the application/domain core and connects external systems through ports and adapters.

</details>

<details>
<summary><strong>🧠 OOP-BE-016. How can AOP and proxies affect object-oriented assumptions?</strong></summary>

#### Short answer

AOP proxies can make method behavior depend on how an object is called, because transactions, security, caching, retries, or async behavior may run only through the proxy.

#### Interview answer

In plain OOP, calling `this.method()` and calling the same method from another object usually execute the same method body. With Spring proxy-based AOP, external calls go through a proxy that can add advice; self-invocation through `this` bypasses the proxy.

This affects `@Transactional`, `@Cacheable`, `@Async`, security annotations, retry annotations, and custom aspects.

#### Deep dive

Proxies also affect type assumptions. With interface-based proxies, the runtime object may implement only the interface. With class-based proxies, final classes or final methods are difficult or impossible to advise. Private methods are not advised through normal proxy interception.

AOP is powerful for cross-cutting concerns, but the class source code no longer tells the whole runtime story. The object’s behavior includes container configuration.

#### Production angle

Production symptoms include missing transactions, cache not being used, async code running synchronously, retries not applying, and security checks being skipped on internal calls.

The fix is often to move the advised method to another bean, call through a proper boundary, or redesign the method so the cross-cutting concern is applied at the use-case entry point.

#### Traps / caveats

- Do not assume annotations work on self-invoked methods.
- Do not hide important business behavior in aspects without tests and documentation.
- Do not use `AopContext.currentProxy()` as a normal design tool; it couples business code to Spring AOP.

#### Optional Anki

Q: How can AOP and proxies affect object-oriented assumptions?
A: AOP proxies can make method behavior depend on how an object is called, because transactions, security, caching, retries, or async behavior may run only through the proxy.

</details>
