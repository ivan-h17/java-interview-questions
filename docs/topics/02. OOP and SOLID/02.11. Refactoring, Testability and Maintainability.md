# 02.11. Refactoring, Testability and Maintainability

---

<a id="oop-ref-003"></a>

<details>
<summary><strong>OOP-REF-003. How can hidden dependencies or static-heavy code make tests harder?</strong></summary>

#### Short answer

Hidden dependencies and static-heavy code make tests harder because collaborators cannot be seen, replaced, isolated, or controlled easily.

#### Interview answer

A hidden dependency is something a class uses without declaring it clearly: static singletons, global registries, system time, environment variables, filesystem access, network clients, random generators, or service locators.

Tests need control. If a method calls `Instant.now()`, `UUID.randomUUID()`, `System.getenv()`, or `PaymentClientHolder.get()` deep inside logic, tests become slow, flaky, order-dependent, or require heavy tooling.

#### Deep dive

Static methods are not automatically bad. Pure functions, constants, and small deterministic helpers are fine. The problem is static access to mutable state, I/O, time, configuration, or external services.

A common refactoring is to inject small abstractions: `Clock`, `IdGenerator`, `PaymentGateway`, or configuration objects. This makes dependencies visible and test seams explicit.

#### Production angle

In production, hidden dependencies also hurt debugging. A behavior may change because of global state, time zone, feature flag, or environment setting that is not visible in the constructor or method signature.

Making dependencies explicit improves both unit tests and operational reasoning.

#### Traps / caveats

- Do not replace every static helper with an interface.
- Do not use a mocking framework to hide a design problem caused by global mutable state.
- Do not pass the whole application context as a workaround for explicit dependencies.

#### Optional Anki

Q: How can hidden dependencies or static-heavy code make tests harder?
A: Hidden dependencies and static-heavy code make tests harder because collaborators cannot be seen, replaced, isolated, or controlled easily.

<details>
<summary><strong>🧠 OOP-REF-004. When can excessive mocking indicate poor design?</strong></summary>

#### Short answer

Excessive mocking can indicate poor design when a test must simulate many internal collaborators to verify one behavior.

#### Interview answer

Mocks are useful at expensive or non-deterministic boundaries: payment gateways, message brokers, email senders, clocks, or remote services. They become suspicious when every small class interaction is mocked and the test mostly verifies call order rather than business outcome.

A test with ten mocks often reveals that the class has too many responsibilities, too much orchestration, or dependencies that are too fine-grained.

#### Deep dive

Excessive mocking also makes tests brittle. A harmless refactoring that preserves behavior can break many tests because they asserted implementation details.

The design alternative is to group cohesive behavior, use real value objects and pure collaborators, test through public use-case boundaries, and mock only external seams.

#### Production angle

In production-oriented testing, excessive mocking can create false confidence: all mocks behave as expected, but real persistence, serialization, transactions, retries, or mapping fail.

Balance unit tests with integration or contract tests around risky boundaries.

#### Traps / caveats

- Do not conclude “mocks are bad”; they are valuable at true boundaries.
- Do not verify every private collaboration through mocks.
- Do not keep a poor object boundary only because tests already mock it.

#### Optional Anki

Q: When can excessive mocking indicate poor design?
A: Excessive mocking can indicate poor design when a test must simulate many internal collaborators to verify one behavior.

<details>
<summary><strong>OOP-REF-006. How do you test behavior instead of implementation details?</strong></summary>

#### Short answer

Test observable outcomes and contracts: returned values, state changes, published events, saved records, or external calls at boundaries, not internal steps.

#### Interview answer

A behavior-focused test asks: “Given this input and state, what should the system guarantee?” It does not ask whether helper method A called helper method B unless that interaction is itself the contract.

For example, test that placing an order reduces stock, stores the order, and emits `OrderPlaced`. Do not test that `validate()` was called before `calculate()` unless the order of those calls is externally meaningful.

#### Deep dive

Good behavior tests usually use public methods, domain language, stable inputs, and meaningful assertions. They allow internal refactoring: extracting methods, changing algorithms, or replacing collaborators should not break the test if the contract remains the same.

Some implementation-detail tests are still useful for complex algorithms, but they should be limited and recognized as more brittle.

#### Production angle

Behavior tests are more maintainable during refactoring and better at catching real regressions. They also document business rules for future developers.

For backend systems, combine them with contract tests for APIs and integration tests for persistence or messaging boundaries.

#### Traps / caveats

- Do not assert private method calls.
- Do not overuse mocks to verify every internal interaction.
- Do not make assertions so broad that the test cannot explain what broke.

#### Optional Anki

Q: How do you test behavior instead of implementation details?
A: Test observable outcomes and contracts: returned values, state changes, published events, saved records, or external calls at boundaries, not internal steps.

</details>

<details>
<summary><strong>OOP-REF-007. How do you refactor a God Object?</strong></summary>

#### Short answer

Refactor a God Object gradually: protect current behavior with tests, identify responsibility clusters, extract cohesive components, and route clients through stable boundaries.

#### Interview answer

A God Object knows too much and does too much. It often combines validation, persistence, calculations, orchestration, formatting, external calls, caching, and configuration.

Start by making behavior safe to change: add characterization tests around important use cases, logging if needed, and small assertions for invariants. Then look for clusters of methods and fields that change together.

#### Deep dive

Useful extraction targets are value objects, policies, validators, domain services, repositories, mappers, clients, or workflow steps. Prefer extracting a vertical slice that has clear inputs and outputs, not randomly moving methods to a `Helper`.

Keep the original class as a facade temporarily if many clients depend on it. Move behavior behind the facade in small steps, then shrink the facade.

#### Production angle

In production systems, big-bang rewrites of God Objects are risky. Incremental extraction lets you ship safely and observe behavior after each step.

Track metrics such as class size, dependency count, and change frequency to confirm the object is actually shrinking.

#### Traps / caveats

- Do not split by technical layer only if the real problem is mixed business responsibilities.
- Do not create ten anemic services that still share the same mutable state.
- Do not refactor without tests or at least strong characterization around critical behavior.

#### Optional Anki

Q: How do you refactor a God Object?
A: Refactor a God Object gradually: protect current behavior with tests, identify responsibility clusters, extract cohesive components, and route clients through stable boundaries.

<a id="oop-ref-008"></a>

<details>
<summary><strong>OOP-REF-008. What is a safe first step when refactoring a large legacy class?</strong></summary>

#### Short answer

A safe first step is to add characterization tests and identify seams before changing structure.

#### Interview answer

Before improving design, understand and protect current behavior. Legacy code often contains undocumented edge cases and production workarounds. Characterization tests capture what the code does today, even if the behavior is not ideal.

Then create small seams: wrap static calls, inject time, isolate external I/O, or extract a pure calculation. These seams give you control without rewriting everything.

#### Deep dive

A safe first refactoring is usually mechanical and low-risk: rename for clarity, extract method, introduce parameter object, wrap dependency, or move code with no behavior change. Avoid changing logic and structure at the same time.

If the class is too hard to instantiate, use a higher-level test first, then work inward.

#### Production angle

Production legacy code should be refactored in reversible steps. Small commits, feature flags when needed, and monitoring reduce the blast radius.

The goal of the first step is not perfect design; it is making the next step safer.

#### Traps / caveats

- Do not start by rewriting the whole class from scratch.
- Do not “clean up” suspicious edge cases before you know why they exist.
- Do not mix formatting-only changes with behavioral refactoring in the same commit.

#### Optional Anki

Q: What is a safe first step when refactoring a large legacy class?
A: A safe first step is to add characterization tests and identify seams before changing structure.

</details>

<a id="oop-ref-009"></a>

<details>
<summary><strong>🧠 OOP-REF-009. How do characterization tests help with refactoring?</strong></summary>

#### Short answer

Characterization tests capture the current behavior of legacy code so you can refactor with regression protection.

#### Interview answer

A characterization test does not start by proving the behavior is correct according to an ideal specification. It observes what the system currently does for important inputs and locks that behavior down.

This is valuable when requirements are missing, code is old, or behavior includes subtle compatibility rules. Once the behavior is documented by tests, you can change structure and see whether you accidentally changed outcomes.

#### Deep dive

Good characterization tests focus on important scenarios, boundary values, bug-prone cases, and integration behavior. They should avoid copying every line of implementation into assertions.

After refactoring, some characterization tests may become true specification tests, and some may be deleted if they only protected a temporary step.

#### Production angle

In production, characterization tests are especially useful before changing billing, permissions, migrations, retry behavior, or data transformations where unknown edge cases are dangerous.

They turn tribal knowledge into executable documentation.

#### Traps / caveats

- Do not confuse characterization with approval of bad behavior; it may capture bugs intentionally before fixing them.
- Do not overfit tests to logs, timing, or random internal details.
- Do not keep obsolete characterization tests forever if they block intended behavior changes.

#### Optional Anki

Q: How do characterization tests help with refactoring?
A: Characterization tests capture the current behavior of legacy code so you can refactor with regression protection.

</details>

<details>
<summary><strong>OOP-REF-010. How do you split a class with multiple responsibilities?</strong></summary>

#### Short answer

Split it by cohesive reasons to change: identify behavior clusters, data ownership, dependencies, and clients, then extract one responsibility at a time.

#### Interview answer

Start by mapping what the class does: validation, calculation, persistence, formatting, authorization, integration, caching, workflow, and state management. Then group methods and fields that belong together and change for the same reason.

A good extracted class has a clear name, small public API, explicit inputs, and owned data. Examples: `PriceCalculator`, `OrderValidator`, `InvoiceRenderer`, `CustomerEligibilityPolicy`, or `PaymentAdapter`.

#### Deep dive

Prefer moving behavior with the data it uses most. If extracted classes constantly ask the old class for data, you may have created Feature Envy or an anemic split.

Use tests to keep behavior stable. Extract one cluster, delegate from the old class, update clients gradually, and only then remove the old delegation.

#### Production angle

This refactoring reduces merge conflicts, improves ownership, and makes tests more focused. It also reduces incident risk because changes become localized.

Measure progress by fewer unrelated dependencies per class and less frequent modification of the same file for unrelated features.

#### Traps / caveats

- Do not split by method count alone.
- Do not create vague classes named `Processor`, `Manager`, or `Helper` unless the responsibility is truly clear.
- Do not move state without moving the invariants that protect it.

#### Optional Anki

Q: How do you split a class with multiple responsibilities?
A: Split it by cohesive reasons to change: identify behavior clusters, data ownership, dependencies, and clients, then extract one responsibility at a time.

</details>

<details>
<summary><strong>OOP-REF-011. How do you refactor a large if-else or switch by type?</strong></summary>

#### Short answer

Refactor it by moving type-specific behavior behind polymorphism, Strategy, handlers, or a registry when the branching represents varying behavior.

#### Interview answer

A switch by type is a smell when every new type requires editing the same conditional in many places. For example, payment type, document type, shipment carrier, or discount type often fits a strategy or handler model.

The usual path is: identify the variation, define a small behavior contract, create one implementation per case, and replace the conditional with lookup or dispatch.

#### Deep dive

Not every switch is bad. A switch is acceptable when the set of cases is small, stable, local, and clearer than indirection. Modern Java switch expressions over enums or sealed hierarchies can be very readable.

The refactoring is most valuable when behavior changes independently, cases are owned by different modules, or adding a new case currently requires risky edits.

#### Production angle

In production, replacing a central switch with handlers can improve deploy safety and test isolation. Each case can be tested independently, and new cases can be added with less risk to existing ones.

However, dynamic registries can hide control flow, so keep discovery and ordering explicit.

#### Traps / caveats

- Do not replace a simple two-case switch with a complex hierarchy.
- Do not create one-method classes if they make navigation worse without real variation.
- Do not forget a default or unknown-type strategy for externally supplied values.

#### Optional Anki

Q: How do you refactor a large if-else or switch by type?
A: Refactor it by moving type-specific behavior behind polymorphism, Strategy, handlers, or a registry when the branching represents varying behavior.

</details>

<details>
<summary><strong>OOP-REF-012. How do you extract an interface without overengineering?</strong></summary>

#### Short answer

Extract an interface only around a stable contract or real boundary, and keep it small, consumer-oriented, and behavior-focused.

#### Interview answer

A good interface is owned by the client that needs the abstraction. It describes capability, not the current class. For example, `PaymentGateway` or `ExchangeRateProvider` is clearer than `StripeClientInterface`.

Before extracting, ask: will there be another implementation, a test fake, a module boundary, a port, or a stable public contract? If not, a concrete class may be simpler.

#### Deep dive

Extract from usage, not from implementation. Start with the methods the client actually needs. Avoid leaking DTOs, exceptions, transactions, or vendor SDK types from the implementation if the interface is supposed to protect a boundary.

If there is only one implementation but the boundary is important, a single-implementation interface can still be justified. If the interface merely duplicates every public method of the class, it is probably overengineering.

#### Production angle

A focused interface improves testability, replacement, and architecture enforcement. An unnecessary one adds files, indirection, duplicated documentation, and harder refactoring.

Review interfaces periodically; abstractions that never gained a second reason to exist can often be removed.

#### Traps / caveats

- Do not name interfaces after implementation details.
- Do not expose every method “just in case”.
- Do not extract an interface only because a mocking framework was inconvenient.

#### Optional Anki

Q: How do you extract an interface without overengineering?
A: Extract an interface only around a stable contract or real boundary, and keep it small, consumer-oriented, and behavior-focused.

</details>

<details>
<summary><strong>OOP-REF-013. How do you keep behavior unchanged while improving design?</strong></summary>

#### Short answer

Keep behavior unchanged by working in small mechanical steps, using tests as a safety net, and separating refactoring from feature changes.

#### Interview answer

Refactoring means changing structure without changing observable behavior. Start with tests or characterization, then make small transformations: rename, extract method, move method, introduce parameter object, replace conditional, or extract class.

After each step, run tests. If something fails, the last change is small enough to understand or revert.

#### Deep dive

Separate commits help: one commit for safety tests, one for mechanical refactoring, one for intended behavior change. This makes review and rollback much easier.

Use IDE refactorings when possible, but still review semantic effects: moving code can change visibility, transaction proxying, serialization, equality, or lazy-loading behavior.

#### Production angle

In production, safe refactoring also uses canary releases, feature flags, metrics, logs, and database migration discipline when the change crosses runtime boundaries.

The strongest signal is that external contracts and important business outcomes remain stable.

#### Traps / caveats

- Do not mix cleanup with new business behavior in the same diff.
- Do not rely only on compiler success; behavior can change without type errors.
- Do not reformat entire files while reviewing subtle logic movement.

#### Optional Anki

Q: How do you keep behavior unchanged while improving design?
A: Keep behavior unchanged by working in small mechanical steps, using tests as a safety net, and separating refactoring from feature changes.

</details>

<details>
<summary><strong>🧠 OOP-REF-014. What is a seam in code?</strong></summary>

#### Short answer

A seam is a place where you can change or replace behavior without editing the code that uses it directly.

#### Interview answer

A seam gives tests or production configuration a way to control a dependency. Common seams are interfaces, constructor parameters, method parameters, factories, adapters, configuration objects, subclass hooks, and module boundaries.

For example, replacing `Instant.now()` with an injected `Clock` creates a seam. Tests can use a fixed clock, while production uses the system clock.

#### Deep dive

Seams are especially useful in legacy code where direct tests are hard. You introduce the smallest seam around an expensive, non-deterministic, or dangerous dependency, then test the business logic behind it.

Not every seam needs an interface. Sometimes a parameter, package-private method, or small wrapper is enough.

#### Production angle

Good seams reduce the need for heavy integration environments in unit tests. They also make production replacement safer: changing payment provider, clock source, storage, or message publisher becomes localized.

Too many seams, however, create abstraction noise.

#### Traps / caveats

- Do not add seams around pure deterministic calculations unless there is real variation.
- Do not expose test-only seams as confusing public API.
- Do not use subclassing hooks when constructor injection or a small adapter would be clearer.

#### Optional Anki

Q: What is a seam in code?
A: A seam is a place where you can change or replace behavior without editing the code that uses it directly.

</details>

<details>
<summary><strong>🧠 OOP-REF-015. How can over-abstracted code make tests worse?</strong></summary>

#### Short answer

Over-abstracted code makes tests worse by forcing tests to navigate unnecessary indirection, mock too many layers, and assert plumbing instead of behavior.

#### Interview answer

Abstraction is useful when it hides real volatility or protects a boundary. It hurts when every small operation has an interface, factory, strategy, provider, resolver, and manager without meaningful variation.

Tests then become setup-heavy: create many mocks, wire many objects, and verify that delegation happened. The business assertion becomes tiny compared with the test plumbing.

#### Deep dive

Over-abstraction also makes tests brittle. A refactor that merges two unnecessary layers can break many tests even though behavior improves. It may also hide simple logic behind dynamic discovery, reflection, annotations, or configuration.

Prefer simple objects, direct calls, and real collaborators until you see a stable reason for abstraction.

#### Production angle

In production, over-abstracted code slows debugging. Stack traces are longer, logs mention generic components, and ownership is unclear.

Simplifying abstractions can improve both test readability and incident response.

#### Traps / caveats

- Do not remove abstractions that protect real external boundaries.
- Do not confuse “few layers” with “no design”.
- Do not keep an abstraction only because deleting it would require updating mocks.

#### Optional Anki

Q: How can over-abstracted code make tests worse?
A: Over-abstracted code makes tests worse by forcing tests to navigate unnecessary indirection, mock too many layers, and assert plumbing instead of behavior.

</details>
