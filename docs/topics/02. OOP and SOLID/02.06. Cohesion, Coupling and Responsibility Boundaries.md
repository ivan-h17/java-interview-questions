# 02.06. Cohesion, Coupling and Responsibility Boundaries

---

<a id="oop-resp-001"></a>

<details>
<summary><strong>OOP-RESP-001. What are cohesion and coupling?</strong></summary>

#### Short answer

Cohesion describes how closely the responsibilities inside a module or class belong together. Coupling describes how strongly one module or class depends on others.

#### Interview answer

High cohesion means the class has a focused reason to exist: its methods and data serve the same concept or use case boundary. Low coupling means it knows as little as possible about other classes and depends on stable contracts instead of volatile details.

For example, a `Money` value object with amount/currency validation is cohesive. A service that directly knows controllers, repositories, HTTP clients, email templates, metrics, and domain internals is highly coupled.

#### Deep dive

Cohesion and coupling are not binary. Some coupling is necessary: useful software connects things. The goal is appropriate coupling at explicit boundaries, and high cohesion inside those boundaries.

A class can be small but not cohesive if it mixes unrelated reasons to change. A class can be large but cohesive if it owns a complex but unified concept.

#### Production angle

In production, good cohesion and controlled coupling make changes safer, tests smaller, reviews easier, and incidents easier to localize. Poor boundaries turn small changes into multi-module regressions.

#### Traps / caveats

- Low coupling does not mean no dependencies; it means depending on the right abstractions.
- High cohesion is about responsibility, not just file size.
- Framework annotations can hide coupling but do not remove it.

#### Optional Anki

Q: What are cohesion and coupling?
A: Cohesion is “how well the inside fits together”; coupling is “how much the outside is depended on”.

</details>

<a id="oop-resp-002"></a>

<details>
<summary><strong>OOP-RESP-002. What do high cohesion and low coupling mean in practice?</strong></summary>

#### Short answer

In practice, high cohesion means a class has a clear focused purpose, and low coupling means it communicates through small stable contracts rather than knowing many implementation details.

#### Interview answer

A cohesive class is easy to describe in one sentence without “and then also”. Its methods use the same data and support the same responsibility. A loosely coupled class can be changed or replaced without rewriting many neighbors.

For example, `InvoiceCalculator` should calculate invoices, not send emails and update CRM records. It may depend on a `TaxPolicy` contract instead of hardcoding one tax implementation.

#### Deep dive

Practices that support this include dependency injection, package-private implementation classes, narrow interfaces, domain objects that own invariants, and separating orchestration from business decisions.

But “low coupling” should not create artificial layers for every method. Extra abstractions are only valuable when they protect a real boundary or variation point.

#### Production angle

In production, high cohesion/low coupling shows up in fast feature changes, small PRs, few unrelated test failures, clear ownership, and classes that can be understood without loading the whole system into memory.

#### Traps / caveats

- Too many layers can reduce cohesion by scattering one responsibility.
- Dependency injection can create low construction coupling but still leave high semantic coupling.
- A class with many tiny interfaces can still be coupled if it orchestrates too much.

#### Optional Anki

Q: What do high cohesion and low coupling mean in practice?
A: High cohesion means focused purpose; low coupling means depending on small stable contracts and hiding volatile details.

</details>

<details>
<summary><strong>OOP-RESP-004. How do you determine whether a class has one responsibility?</strong></summary>

#### Short answer

A class has one responsibility when it has one coherent reason to change, a name that matches its behavior, and methods/data that support the same concept or use case boundary.

#### Interview answer

I do not count methods mechanically. I ask: can I explain this class without using a list of unrelated duties? Do its methods operate on the same state? Would changes from different business stakeholders touch it for different reasons?

For example, `OrderPricingService` may have several methods but one responsibility if all are about pricing. A `UserManager` that validates passwords, sends emails, writes audit logs, provisions accounts, and generates reports likely has several responsibilities.

#### Deep dive

Responsibility is about axis of change. A class can coordinate multiple collaborators and still have one responsibility if its role is orchestration of one use case. Conversely, a small utility can violate SRP if it mixes formatting, parsing, validation, and persistence helpers.

Look for clusters: methods that change together, data used together, tests that belong together, and vocabulary from the same domain concept.

#### Production angle

In production, responsibility analysis is best done during code review and refactoring. Split when unrelated changes collide, tests require unrelated setup, or bug fixes repeatedly touch the same large class for different reasons.

#### Traps / caveats

- Do not split only because a class is longer than a threshold.
- Do not keep unrelated behavior together only because it shares a database table.
- A vague name often hides multiple responsibilities.

#### Optional Anki

Q: How do you determine whether a class has one responsibility?
A: Check one responsibility by reason to change, cohesive state/methods, clear name, and focused tests.

</details>

<details>
<summary><strong>OOP-RESP-005. How can too many dependencies indicate poor responsibility boundaries?</strong></summary>

#### Short answer

Too many dependencies can indicate that a class coordinates too many concerns, knows too much about the system, or sits on the wrong boundary between responsibilities.

#### Interview answer

A constructor with many dependencies is a useful smell. It may mean the class handles validation, persistence, notifications, payments, metrics, configuration, mapping, and authorization all at once.

The important word is “may”: some orchestration classes legitimately depend on several ports for one use case. The question is whether the dependencies form a coherent group or unrelated clusters.

#### Deep dive

Analyze dependency clusters. If half the methods use dependencies A/B/C and another half use X/Y/Z, the class may contain two responsibilities. If dependencies are only used to pass data between each other, the class may be a procedural coordinator with weak domain boundaries.

Another signal is test setup: if every unit test needs many mocks and most are irrelevant to the behavior under test, the class likely has too broad a boundary.

#### Production angle

In production, too many dependencies increase blast radius: a change in one integration forces retesting unrelated use cases. Splitting by use case, policy, adapter, or domain operation usually reduces risk.

#### Traps / caveats

- Do not blindly introduce a facade just to hide a long constructor; it may only move the problem.
- A dependency count metric is a smell, not a verdict.
- Framework-injected dependencies still count as design dependencies.

#### Optional Anki

Q: How can too many dependencies indicate poor responsibility boundaries?
A: Many dependencies are a signal to look for unrelated clusters of responsibilities and excessive orchestration.

</details>

<a id="oop-resp-006"></a>

<details>
<summary><strong>OOP-RESP-006. How can a class become a "manager" or "service" with too many responsibilities?</strong></summary>

#### Short answer

A class becomes an overgrown manager/service when new behavior is repeatedly added to one convenient coordination point instead of creating clearer domain, policy, adapter, or use-case boundaries.

#### Interview answer

Names like `UserManager`, `OrderService`, or `CommonProcessor` are not automatically bad, but they can become dumping grounds. The class starts with one use case, then accumulates validation, mapping, transaction control, notifications, reporting, permissions, and integration retries.

Because the class is already injected everywhere, adding one more method feels cheap. Over time it becomes expensive to test and risky to change.

#### Deep dive

The smell is a mismatch between name and behavior. A service named after a broad noun often attracts all actions around that noun. Better boundaries are often verbs or policies: `RegisterUserUseCase`, `PasswordPolicy`, `UserNotificationPort`, `OrderCancellationPolicy`.

Moving behavior into rich domain objects can also help when the service is manipulating entity internals and duplicating rules.

#### Production angle

In production, manager classes become merge-conflict hotspots and incident hotspots. Refactor by extracting one behavior at a time, adding characterization tests, and routing callers through clearer APIs gradually.

#### Traps / caveats

- A service layer is not a license to put all business logic in one class.
- “Manager” often means the domain concept is not understood well enough.
- Do not create a new tiny service for every method without improving names and contracts.

#### Optional Anki

Q: How can a class become a "manager" or "service" with too many responsibilities?
A: Manager/service bloat happens when convenience beats responsibility boundaries; split by use case, policy, port, or domain behavior.

</details>

<details>
<summary><strong>🧠 OOP-RESP-007. What is a transaction script, and when is it acceptable?</strong></summary>

#### Short answer

A transaction script is a procedural use-case method that coordinates steps such as validation, database access, external calls, and state updates in one workflow.

#### Interview answer

It is acceptable when the business logic is simple, mostly linear, and has few domain invariants. For example, an admin operation that reads a record, changes one status, writes an audit row, and returns a DTO may be clearer as a transaction script.

It becomes a problem when many scripts duplicate rules or manipulate domain state in inconsistent ways. Then richer domain objects, policies, or aggregates may be needed.

#### Deep dive

Transaction script is not an anti-pattern by itself. It is a pattern for simple domains and integration-heavy applications. The mistake is applying it blindly to complex domains with lifecycle rules, cross-field invariants, and many behavior variants.

A pragmatic architecture can use transaction scripts at application boundaries while still keeping critical business invariants inside domain objects.

#### Production angle

In production, transaction scripts are common in CRUD services, batch jobs, migration utilities, and simple integration workflows. Monitor for duplication and inconsistent validation as the domain grows.

#### Traps / caveats

- Do not call every service method a transaction script; some are orchestration around rich domain behavior.
- A transaction script can still be well-tested and cleanly structured.
- Too many scripts with copy-pasted rules indicate a missing domain model.

#### Optional Anki

Q: What is a transaction script, and when is it acceptable?
A: Transaction script is acceptable for simple linear use cases; it smells when domain rules are duplicated across many scripts.

</details>

<details>
<summary><strong>OOP-RESP-009. How do you break a cyclic dependency?</strong></summary>

#### Short answer

Break a cyclic dependency by identifying the direction of ownership, extracting a stable abstraction, moving shared concepts to a lower layer, or introducing events/callbacks so dependencies point one way.

#### Interview answer

First, understand why the cycle exists. If `billing` depends on `orders` and `orders` depends on `billing`, one module may be using the other for a policy, data shape, notification, or persistence detail.

Common fixes are: extract an interface owned by the caller, move DTO/value objects into a shared kernel, invert dependency with dependency injection, publish a domain event, or merge modules if the separation is artificial.

#### Deep dive

A cycle is often a sign that responsibilities or layers are unclear. Breaking it mechanically by creating a “common” package can make things worse if that package becomes a dumping ground.

The desired result is an acyclic dependency graph aligned with stability: higher-level policies depend on lower-level abstractions or stable domain concepts, while volatile infrastructure depends inward.

#### Production angle

In production, cycles hurt builds, deployments, modularization, tests, and ownership. Break them incrementally with characterization tests and module-level checks so the cycle does not reappear.

#### Traps / caveats

- A shared `common` module can become a hidden cycle of concepts.
- Do not introduce an interface in the wrong module; the abstraction should belong to the policy that needs it.
- Sometimes the correct fix is merging two modules that were split too early.

#### Optional Anki

Q: How do you break a cyclic dependency?
A: Break cycles by clarifying ownership and making dependencies point toward stable contracts or events.

</details>

<details>
<summary><strong>OOP-RESP-010. How do you split a large service class safely?</strong></summary>

#### Short answer

Split a large service safely by first protecting behavior with tests, then extracting cohesive slices one at a time behind clear names and contracts.

#### Interview answer

Start with characterization tests around the current behavior, especially edge cases and transaction boundaries. Then look for method/dependency clusters: pricing, validation, notification, persistence orchestration, mapping, authorization, or one specific use case.

Extract the smallest coherent collaborator, route the old service through it, and keep public API compatibility until callers can migrate. Avoid a big-bang rewrite.

#### Deep dive

Good extraction targets have names and reasons to change: `CancellationPolicy`, `RefundCalculator`, `OrderNotificationPort`, `CreateOrderUseCase`. Bad extraction targets are vague helpers that merely move private lines elsewhere.

After extraction, reduce dependencies and tests in the original service. If the original service remains a giant coordinator, continue slicing or reconsider the application boundary.

#### Production angle

In production, prefer incremental refactoring under feature flags or behind the old facade. Track behavior with tests, metrics, logs, and rollout plans when the service handles critical workflows.

#### Traps / caveats

- Do not split by arbitrary method count; split by responsibility and dependency clusters.
- Do not change behavior and structure in the same risky PR if avoidable.
- Preserve transactional semantics when moving code across methods/classes.

#### Optional Anki

Q: How do you split a large service class safely?
A: Protect with tests, identify cohesive clusters, extract one collaborator at a time, and keep behavior stable.

</details>

<details>
<summary><strong>🧠 OOP-RESP-011. How can naming reveal unclear responsibilities?</strong></summary>

#### Short answer

Naming reveals unclear responsibilities when class or method names are vague, generic, too broad, or require words like “and”, “manager”, “helper”, “util”, or “processor” without domain meaning.

#### Interview answer

A good name summarizes a responsibility. If a class is named `OrderHelper`, ask what it helps with: pricing, cancellation, fulfillment, persistence, validation, or notifications? The answer may reveal several classes.

Similarly, a method named `process()` hides what actually happens. `cancelOrder()`, `calculateRefund()`, or `reserveInventory()` exposes intent and makes misplaced behavior visible.

#### Deep dive

Naming is design feedback. When a class needs a long name with multiple concepts, it may cross boundaries. When a short name is too vague, the concept may be poorly understood.

Names should come from the domain or architecture. `FraudPolicy`, `InvoiceNumberGenerator`, and `PaymentGateway` communicate more than `CommonService`.

#### Production angle

In production, naming improves ownership, code search, onboarding, and incident response. A clear name helps a developer find the right place to change behavior and avoid adding code to the wrong class.

#### Traps / caveats

- Do not rename without improving boundaries if the old name accurately reflects a messy design.
- Generic suffixes are not always bad, but they should not replace domain meaning.
- A name that only describes a technical step may miss the business responsibility.

#### Optional Anki

Q: How can naming reveal unclear responsibilities?
A: Vague names are design smells; precise domain names expose whether responsibilities are cohesive.

</details>

<details>
<summary><strong>🧠 OOP-RESP-012. How can metrics like class size, method count or dependency count help detect responsibility problems?</strong></summary>

#### Short answer

Metrics can highlight responsibility smells by showing unusually large classes, many methods, high dependency count, high fan-in/fan-out, or complex methods, but they are signals, not proof.

#### Interview answer

A large class may be cohesive and necessary; a small class may be meaningless. Metrics are useful for prioritizing review attention. For example, a service with 40 methods and 18 dependencies deserves inspection for unrelated clusters.

Method count, constructor dependency count, cyclomatic complexity, afferent/efferent coupling, change frequency, and test setup size can all point to boundary problems.

#### Deep dive

The best use of metrics is trend and comparison within the same codebase. A class that grows every sprint and is modified by unrelated stories is more concerning than a large stable parser with clear responsibility.

Combine metrics with qualitative questions: what are the reasons to change, which dependencies are used together, which tests fail together, and what name would describe the extracted concept?

#### Production angle

In production, metrics help create objective refactoring candidates and prevent debates based only on taste. Use them in dashboards or static analysis, but let engineers validate the design diagnosis.

#### Traps / caveats

- Do not create hard universal thresholds without context.
- Reducing a metric can make design worse if it adds fake abstractions.
- Track change frequency and defect history, not only static size.

#### Optional Anki

Q: How can metrics like class size, method count or dependency count help detect responsibility problems?
A: Metrics are smoke detectors: they tell you where to inspect, not what exact refactoring to apply.

</details>
