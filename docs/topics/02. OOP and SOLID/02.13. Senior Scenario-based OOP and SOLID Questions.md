<a id="oop-scen-001"></a>

<details>
<summary><strong>OOP-SCEN-001. A service class has validation, database writes, Kafka publishing and email sending. How would you refactor it?</strong></summary>

#### Short answer

I would keep the service as a use-case orchestrator, move rules to domain objects or validators, persistence to repositories, and side effects to ports or event handlers, usually with an outbox for reliable publishing.

#### Interview answer

First I would protect current behavior with tests. Then I would identify responsibilities: input validation, business invariants, transaction, persistence, Kafka event, and email notification.

A good target is an application service that coordinates the use case: validate command, load aggregate, call domain behavior, save through repository, record a domain event or outbox message, and trigger email through a notification port or asynchronous handler.

#### Deep dive

The transaction should normally cover database state and the outbox record, not a direct Kafka publish plus email send. External side effects can be processed after commit to avoid sending messages for rolled-back data.

Validation may be split: syntactic request validation at the boundary, business validation inside the domain model, and cross-aggregate orchestration in the application service.

#### Production angle

The production risks are duplicate events, lost events, email sent before rollback, slow transactions, and mixed retry policies. Outbox, idempotent consumers, and clear boundaries reduce those risks.

Refactoring should be incremental: extract one collaborator, compare behavior, deploy safely, then continue.

#### Traps / caveats

- Do not put all extracted logic into another giant manager.
- Do not send Kafka messages inside a transaction and assume rollback will undo them.
- Do not move business rules only to validators if the domain object can still become invalid later.

#### Optional Anki

Q: Why is direct Kafka publishing inside a database transaction risky?
A: The broker send is not rolled back with the database commit, so use an outbox or after-commit flow plus idempotent consumers.

</details>

<a id="oop-scen-002"></a>

<details>
<summary><strong>OOP-SCEN-002. A new payment provider must be added every month. How would you design the code?</strong></summary>

#### Short answer

I would define a stable payment port, implement each provider as an adapter, select providers through configuration or a registry, and protect the contract with tests.

#### Interview answer

The core application should speak in business terms: authorize payment, capture, refund, void, get status. Provider-specific SDKs, request formats, credentials, and error codes belong in adapters.

Each new provider becomes a new adapter implementing the same port. Selection can be based on merchant, country, currency, feature flag, or routing policy, but the domain should not know provider classes.

#### Deep dive

The contract should include semantic details: idempotency keys, timeout behavior, retryable vs non-retryable errors, currency support, partial refunds, and state transitions.

Contract tests can run against fake providers and, where possible, sandbox accounts. Shared tests ensure every adapter handles common scenarios consistently.

#### Production angle

Payments need strong operational design: idempotency, audit logs, reconciliation, observability, safe retries, secrets handling, and graceful provider failover when business allows it.

Adding a provider should not require changing core payment rules unless the business capability itself changes.

#### Traps / caveats

- Do not make the port a lowest-common-denominator API that hides important provider differences.
- Do not leak vendor exceptions and DTOs into the domain or application core.
- Do not assume all payment operations are synchronous or equally idempotent.

#### Optional Anki

Q: What details should a payment provider port define explicitly?
A: Idempotency, timeouts, retryable failures, currency support, partial refunds, operation state transitions, and provider-unavailable behavior.

</details>

<a id="oop-scen-003"></a>

<details>
<summary><strong>OOP-SCEN-003. A discount engine is implemented as a huge if-else chain. How would you refactor it?</strong></summary>

#### Short answer

I would first cover existing behavior with tests, then extract discount rules into named strategies or specifications, with explicit ordering and conflict rules.

#### Interview answer

A huge if-else chain usually mixes rule selection, rule condition, calculation, priority, and error handling. I would identify each rule, name it in domain language, and extract it behind a small `DiscountRule` contract.

Then an engine can evaluate applicable rules, combine results, and explain decisions. The design should make rule order, exclusivity, stacking, and maximum discount visible.

#### Deep dive

Strategy works well when rules are implemented by developers. Specification helps express predicates and combinations. A rules engine may be useful only if non-developers need to modify rules frequently and the operational cost is justified.

The refactoring should preserve behavior: golden-master tests for existing inputs, focused unit tests per rule, and integration tests for rule combinations.

#### Production angle

Discount logic needs explainability. Support teams should be able to answer why a discount was or was not applied, especially during promotions.

Avoid changing all rules for every new campaign; make campaign-specific changes local and observable.

#### Traps / caveats

- Do not replace a simple stable switch with a complex rules framework without a real need.
- Do not ignore rule ordering; moving code out of an if-else can accidentally change priority.
- Do not hide business language behind generic names like `Rule1` or `ProcessorImpl`.

#### Optional Anki

Q: What must be preserved when refactoring a discount if-else chain?
A: Existing rule priority, exclusivity, stacking behavior, maximum discount limits, and explanations for why a rule applied.

</details>

<details>
<summary><strong>OOP-SCEN-004. A class has 15 dependencies in the constructor. What does it tell you, and what would you do?</strong></summary>

#### Short answer

It usually suggests poor responsibility boundaries or orchestration doing too much. I would group dependencies by use case, remove unused ones, and extract cohesive collaborators instead of hiding them in a facade.

#### Interview answer

Many constructor dependencies are a signal, not automatic proof. A top-level application orchestrator can legitimately need several ports. But 15 dependencies often means the class handles too many use cases or mixes policies, persistence, notifications, mapping, and integrations.

I would inspect which methods use which dependencies. If groups do not overlap, split the class by use case or responsibility. If several dependencies always work together, extract a cohesive collaborator with a meaningful name.

#### Deep dive

Useful refactorings include split service, extract policy, extract adapter, move mapping to boundary, introduce domain object behavior, and separate command use cases from query use cases.

A dependency object or facade is acceptable only if it represents a real concept. A `ServiceDependencies` bag usually hides the smell and makes tests worse.

#### Production angle

Too many dependencies increase startup wiring complexity, test setup, and blast radius. Changes to one collaborator can affect many unrelated use cases.

A safe approach is to split along existing tests or public methods and deploy small refactorings with no behavior change.

#### Traps / caveats

- Do not hide dependencies by injecting `ApplicationContext` or a Service Locator.
- Do not split by technical layer only if the real issue is mixed business responsibilities.
- Do not create an abstraction for every dependency just to reduce constructor length.

#### Optional Anki

Q: Why is a `ServiceDependencies` bag a weak fix for too many constructor dependencies?
A: It hides the dependency smell instead of reducing responsibility, and tests still need to understand the same unrelated collaborators.

</details>

<a id="oop-scen-005"></a>

<details>
<summary><strong>OOP-SCEN-005. Two modules depend on each other. How would you break the cycle?</strong></summary>

#### Short answer

I would map the dependency cycle, find the direction that violates ownership, and break it by moving shared concepts, extracting a port, or using events.

#### Interview answer

First I would make the cycle visible: which classes, packages, or build modules reference each other and for what reason. Then I would decide which module should own the concept.

Common fixes are extracting a shared value object to a lower module, moving behavior to the module that owns the data, inverting the dependency through an interface owned by the higher-level policy, or replacing synchronous calls with events.

#### Deep dive

For example, if `orders` calls `billing` and `billing` calls back into `orders`, maybe both need a shared `CustomerId` value object, or `billing` should publish `InvoicePaid` and `orders` should react.

The goal is acyclic dependencies that match architectural direction: domain inward, infrastructure outward, and clear ownership of contracts.

#### Production angle

Cycles make deployments and refactoring harder. They also complicate incident analysis because responsibility for a failure is spread across modules.

After breaking the cycle, add architecture tests or build rules so the dependency direction stays clean.

#### Traps / caveats

- Do not create a `common` module full of unrelated things.
- Do not use events when the caller actually needs an immediate consistent result.
- Do not put the interface in the wrong module; ownership of the abstraction matters.

#### Optional Anki

Q: What is a common bad fix for circular dependencies?
A: Moving unrelated types into a generic `common` module; it often becomes a dumping ground and hides ownership problems.

</details>

<a id="oop-scen-006"></a>

<details>
<summary><strong>OOP-SCEN-006. A subclass throws UnsupportedOperationException for several inherited methods. What principle might be violated?</strong></summary>

#### Short answer

It likely violates LSP because the subclass cannot be used safely where the base type is expected. It may also indicate inheritance abuse or a fat interface.

#### Interview answer

If the base contract says clients can call a method, a subtype should support that behavior or the contract must clearly mark it as optional. Throwing `UnsupportedOperationException` from several inherited methods often means the type hierarchy is wrong.

A classic example is a read-only implementation inheriting mutating operations from a mutable abstraction. Clients now need type checks or defensive handling, which defeats polymorphism.

#### Deep dive

Possible fixes are split interfaces into read and write roles, use composition instead of inheritance, introduce a separate abstraction for read-only behavior, or make unsupported operations explicit in the contract.

LSP is about behavior, not only method signatures. The subtype must respect expected preconditions, postconditions, invariants, and exceptions.

#### Production angle

In production, this often appears as rare runtime failures when a new implementation is passed into old code that assumes the full base contract.

Contract tests are a good safety net: every implementation must pass the same behavioral suite.

#### Traps / caveats

- Some Java APIs document optional operations; that is a trade-off, not a free pass for any subtype.
- Do not “fix” the issue by catching `UnsupportedOperationException` everywhere.
- Do not ignore other LSP violations such as stricter inputs or weaker outputs.

#### Optional Anki

Q: Why can `UnsupportedOperationException` indicate an LSP violation?
A: The base contract tells clients the operation exists, but the subtype cannot safely honor that behavior without special-case handling.

</details>

<a id="oop-scen-007"></a>

<details>
<summary><strong>OOP-SCEN-007. A controller contains all business logic. How would you restructure it?</strong></summary>

#### Short answer

I would keep the controller focused on HTTP concerns, move use-case orchestration to an application service, and put business rules into domain objects or domain services.

#### Interview answer

A REST controller should map routes, parse input, validate request shape, handle authentication context if needed, call an application service, and map the result to a response.

Business decisions such as pricing, eligibility, order transitions, and cancellation rules should not live in controller methods. They belong to the domain model or to application/domain services depending on the rule.

#### Deep dive

A safe refactoring is to extract a command object, move the logic to a service method, keep response mapping in the controller, and add tests at both levels: controller tests for HTTP behavior and service/domain tests for business behavior.

DTOs help keep REST representation separate from domain state. The controller can translate validation errors and domain errors into HTTP status codes.

#### Production angle

Controllers full of business logic are hard to reuse from messaging, batch jobs, or internal APIs. They also make business behavior depend on web framework details.

Clear separation improves test speed, error handling consistency, and observability around use cases.

#### Traps / caveats

- Do not move logic from controller to an anemic service that still does everything procedurally if a domain model is needed.
- Do not put HTTP status codes or request objects into domain classes.
- Do not duplicate validation rules between controller and domain; split syntactic and business validation.

#### Optional Anki

Q: Which responsibilities should usually remain in a REST controller?
A: HTTP routing, request parsing, boundary validation, authentication context handling, calling the use case, and response mapping.

</details>

<a id="oop-scen-008"></a>

<details>
<summary><strong>OOP-SCEN-008. A JPA entity is returned directly from a REST endpoint. What problems can happen?</strong></summary>

#### Short answer

It can leak persistence details into the API, expose sensitive fields, trigger lazy-loading problems, create JSON cycles, and make API evolution depend on database mapping.

#### Interview answer

A JPA entity is designed for persistence, not necessarily for public JSON. It may contain lazy associations, bidirectional relationships, internal ids, audit fields, version fields, or fields that should never be writable by clients.

Returning it directly couples REST representation to database schema and ORM mapping. A harmless entity change can become a breaking API change.

#### Deep dive

Common issues include `LazyInitializationException`, N+1 queries during serialization, infinite recursion in bidirectional relationships, over-posting on input, and accidental exposure of internal state.

Use DTOs or response models at the API boundary. Map explicitly or with a controlled mapper, and design fetch plans for the use case.

#### Production angle

In production this can become a security issue and a performance issue. One new association can suddenly expand payloads or trigger many database queries.

DTOs also help version APIs without forcing database migrations or changing persistence mapping just for representation needs.

#### Traps / caveats

- Do not assume `@JsonIgnore` annotations fully solve boundary leakage.
- Do not expose entity setters to clients through request binding.
- Do not map everything eagerly just to avoid lazy-loading errors.

#### Optional Anki

Q: Why is `@JsonIgnore` not enough to justify exposing JPA entities?
A: It treats serialization symptoms while the API remains coupled to persistence mapping, lazy loading, entity lifecycle, and schema evolution.

</details>

<a id="oop-scen-009"></a>

<details>
<summary><strong>OOP-SCEN-009. A domain class exposes a mutable List through a getter. What can go wrong?</strong></summary>

#### Short answer

Callers can mutate internal state without the domain object enforcing invariants, causing representation exposure, invalid state, concurrency issues, and persistence surprises.

#### Interview answer

If `Order.getItems()` returns the internal mutable list, external code can call `clear`, `add`, or modify elements directly. The `Order` cannot enforce rules like “order must have at least one item” or “cancelled orders cannot change items”.

This breaks encapsulation because the object no longer controls state transitions.

#### Deep dive

Better options are behavior methods like `addItem`, `removeItem`, `changeQuantity`, and read-only views or snapshots for queries. For mutable elements, consider defensive copying or immutable value objects.

With JPA, collection handling needs care because replacing collections can affect dirty checking or orphan removal. Encapsulation can still be preserved with protected constructors, field access, and controlled methods.

#### Production angle

In production, representation exposure creates bugs far away from the class that owns the invariant. A helper method can accidentally corrupt an aggregate and the failure appears later during checkout or persistence flush.

Encapsulated state transitions make audit, validation, and domain events more reliable.

#### Traps / caveats

- An unmodifiable view is not the same as a defensive copy if the backing list can still change.
- Do not expose mutable elements inside an otherwise unmodifiable collection.
- Do not add setters for collections just because a framework needs construction; use framework-friendly but controlled mapping.

#### Optional Anki

Q: Why is an unmodifiable view not always enough for collection encapsulation?
A: The backing collection or mutable elements can still change, so callers may observe or indirectly cause invalid state.

</details>

<a id="oop-scen-010"></a>

<details>
<summary><strong>OOP-SCEN-010. A team created interfaces for every class with one implementation. Is this good design?</strong></summary>

#### Short answer

Not automatically. Interfaces are useful for stable contracts and boundaries, but creating one for every class often adds noise without reducing coupling.

#### Interview answer

An interface with one implementation is useful when it represents a real boundary: payment gateway, message publisher, clock, external API, storage port, plugin point, or separately owned module.

It is often unnecessary for simple internal services where there is no real variation and no boundary. In that case, the interface duplicates the class name and makes navigation and refactoring harder.

#### Deep dive

Depending on an interface is not automatically DIP. The abstraction must be owned by the high-level policy and express the need of the client, not just mirror the concrete implementation.

A good test double can sometimes justify an interface, but many tests can also instantiate a concrete class with explicit dependencies.

#### Production angle

Too many meaningless interfaces increase maintenance cost. Every rename, method change, and navigation step touches two files with no architectural benefit.

Use interfaces deliberately at boundaries where replacement, independent deployment, external integration, or contract testing matters.

#### Traps / caveats

- Do not remove a single-implementation interface if it is a public contract for another module.
- Do not create interfaces only because a mocking framework prefers them.
- Do not name interfaces as `IUserService` or duplicate implementation names without adding semantic value.

#### Optional Anki

Q: When is a single-implementation interface justified?
A: When it protects a real boundary, such as an external system port, public module contract, plugin point, or slow/non-deterministic test seam.

</details>

<a id="oop-scen-011"></a>

<details>
<summary><strong>OOP-SCEN-011. How would you design a notification system supporting email, SMS and push notifications?</strong></summary>

#### Short answer

I would model notification sending through a channel port, implement email/SMS/push as adapters, and separate orchestration, templates, preferences, delivery tracking, and retry policy.

#### Interview answer

At the application level, a `NotificationService` can decide what notification must be sent for a use case. Channel-specific implementations such as `EmailSender`, `SmsSender`, and `PushSender` implement a common port or separate role-specific ports.

The domain may emit events like `OrderShipped`; handlers translate them into notification commands. Templates, localization, user preferences, and provider delivery details should be separate concerns.

#### Deep dive

The abstraction should not pretend all channels are identical. SMS length, email attachments, push tokens, unsubscribe rules, and delivery receipts differ. Either expose a common minimal command or define channel-specific capabilities.

For reliability, store notification requests, process them asynchronously, use retries with backoff, and make sends idempotent where providers allow it.

#### Production angle

Production concerns include provider outages, rate limits, duplicate sends, user opt-out compliance, observability, dead-letter queues, and audit trails.

A clear design lets you add a new channel without changing order, billing, or user-account domain logic.

#### Traps / caveats

- Do not put email template rendering inside domain entities.
- Do not force all channels into one fat interface if their capabilities differ strongly.
- Do not send notifications inside the same transaction that changes business state unless the side effect is safely coordinated.

#### Optional Anki

Q: What should not be hidden inside a notification channel adapter?
A: User preference policy, required business decisions, delivery tracking semantics, and retry rules that belong to the use case.

</details>

<a id="oop-scen-012"></a>

<details>
<summary><strong>OOP-SCEN-012. How would you design order cancellation or pricing rules that change frequently?</strong></summary>

#### Short answer

I would isolate changing rules behind named policies or strategies, keep invariants in the domain model, and make rule behavior easy to test and explain.

#### Interview answer

For cancellation, the order aggregate should protect core state transitions: pending can be cancelled, shipped may require return flow, delivered may require refund rules. Frequently changing policy can be delegated to `CancellationPolicy`.

For pricing, separate base price calculation, discounts, taxes, promotions, and rounding. Use strategies/specifications when rules vary independently; use simple code when variation is small and stable.

#### Deep dive

The model should express domain language: `cancel`, `refund`, `applyPromotion`, `calculateTax`, not generic `process`. Rule order, precedence, effective dates, and auditability matter.

When business users change rules often, a configuration-driven or rules-engine approach may be justified, but only with validation, versioning, tests, and operational ownership.

#### Production angle

Frequent rule changes need safe rollout: feature flags, effective dates, canary checks, audit logs, and quick rollback.

Tests should cover boundary cases: time zones, rounding, currency, partial cancellations, retries, and historical orders using old rules.

#### Traps / caveats

- Do not put every rule into a separate class if business does not actually vary it.
- Do not let configuration bypass domain invariants.
- Do not forget that old orders may need old rule versions for audit or legal reasons.

#### Optional Anki

Q: What production concerns matter for frequently changing pricing rules?
A: Effective dates, rule versions, auditability, rounding, currency behavior, feature flags, rollback, and historical orders.

</details>

<a id="oop-scen-013"></a>

<details>
<summary><strong>OOP-SCEN-013. How would you refactor static utility-heavy code to become testable?</strong></summary>

#### Short answer

I would keep pure deterministic utilities static, but introduce explicit seams for time, randomness, I/O, configuration, and external services, then inject those dependencies.

#### Interview answer

The first step is classification. Static methods that format strings or calculate pure values are usually fine. Static methods that read files, call APIs, use current time, mutate caches, or access singletons are testing problems.

For stateful or side-effecting static calls, wrap the behavior behind a small interface or object such as `Clock`, `IdGenerator`, `FileStorage`, or `PaymentGateway`, and pass it through constructors.

#### Deep dive

In legacy code, a seam can be introduced gradually: create an instance-based wrapper that delegates to existing static code, inject the wrapper into new code, then move logic out of the static utility over time.

Characterization tests help ensure behavior stays unchanged while seams are added.

#### Production angle

This reduces flaky tests and makes operational dependencies visible. It also supports better observability and configuration because collaborators are explicit.

The refactoring should avoid big rewrites: replace one static dependency at a time and keep the old API while migrating callers.

#### Traps / caveats

- Do not turn pure helpers into interfaces just for “OOP purity”.
- Do not rely only on static mocking; it can keep the design hidden.
- Do not introduce a huge utility service with the same mixed responsibilities.

#### Optional Anki

Q: Which static helpers are usually fine to keep static?
A: Pure deterministic helpers, constants, and simple calculations without time, randomness, I/O, configuration, mutable state, or external services.

</details>

<a id="oop-scen-014"></a>

<details>
<summary><strong>OOP-SCEN-014. How would you replace a Singleton dependency in legacy code?</strong></summary>

#### Short answer

I would introduce an interface or adapter around the singleton, inject it into new or refactored code, and migrate direct singleton calls incrementally.

#### Interview answer

First, identify what the singleton actually provides: configuration, cache, external client, factory, or business service. Then define a small contract based on caller needs, not the whole singleton API.

Create an adapter that delegates to the existing singleton. New code depends on the contract. Existing code can be migrated method by method, protected by characterization tests.

#### Deep dive

At the composition root, bind the adapter as the current implementation. Later you can replace it with a real instance-based implementation without changing domain code.

If the singleton stores mutable global state, also plan lifecycle and state ownership: who initializes it, clears it, reloads it, and makes it thread-safe?

#### Production angle

Incremental replacement reduces risk. You can compare old and new paths, add metrics, and roll back by changing wiring instead of editing every caller at once.

The main production benefit is explicit dependencies and more reliable tests around code that used to depend on global state.

#### Traps / caveats

- Do not make the adapter expose the whole singleton API if callers need only two methods.
- Do not introduce a new singleton wrapper around the old singleton.
- Do not ignore concurrency and lifecycle behavior when removing global state.

#### Optional Anki

Q: What is the safe first abstraction around a legacy singleton?
A: A small caller-oriented adapter or interface that exposes only needed behavior while delegating to the existing singleton during migration.

</details>

<a id="oop-scen-015"></a>

<details>
<summary><strong>OOP-SCEN-015. How would you decide between Strategy, inheritance and switch for varying behavior?</strong></summary>

#### Short answer

Use Strategy for independently changing algorithms, inheritance for true substitutable subtypes, and switch for small, stable, local choices where abstraction would add noise.

#### Interview answer

I would look at the variation axis. If behavior changes by provider, policy, algorithm, or tenant and new variants are added often, Strategy is usually good. It localizes new behavior behind a contract.

Inheritance is appropriate when objects are real subtypes with compatible behavior and shared invariants. A switch is fine when the set is closed and stable, especially with enums or sealed types and simple local behavior.

#### Deep dive

Ask what is more likely to change: adding new variants or adding new operations. Strategy helps when variants change independently. A switch can be clearer when all variants are known and the operation is small.

Inheritance is the riskiest if used only for code reuse because it couples subclass behavior to base-class internals.

#### Production angle

In production, the best choice is the one that keeps the common change small and safe. For a monthly new payment provider, Strategy/adapters make sense. For three stable order statuses, a switch may be clearer.

The decision should consider readability, testability, performance, team familiarity, and rollout risk.

#### Traps / caveats

- Do not replace every switch with polymorphism mechanically.
- Do not use inheritance just because several classes share code.
- Do not create strategies with leaky contracts that require callers to know concrete types anyway.

#### Optional Anki

Q: When is a switch better than Strategy?
A: When the case set is small, stable, local, and clearer than an indirection layer, especially with enums or sealed types.

</details>

<a id="oop-scen-017"></a>

<details>
<summary><strong>OOP-SCEN-017. How would you keep domain code independent from Spring?</strong></summary>

#### Short answer

Keep domain classes as plain Java objects, define ports in the application/domain side, and put Spring annotations, configuration, persistence, and messaging in outer layers.

#### Interview answer

Domain code should express business concepts and rules, not framework lifecycle. Avoid `@Service`, `@Autowired`, `@Transactional`, `ApplicationEventPublisher`, JPA queries, and web annotations inside core domain objects.

Use constructors and methods normally. Application services can be Spring beans and can call domain objects. Infrastructure adapters implement ports and are wired by Spring configuration.

#### Deep dive

Domain events can be plain objects returned from aggregates or collected during state changes. An application service or adapter can publish them using Spring after persistence concerns are handled.

Module boundaries help: `domain` has no Spring dependency; `application` depends on domain and ports; `infrastructure` depends on application ports and Spring/JPA/Kafka.

#### Production angle

This makes business rules faster to test, easier to reuse, and less fragile during framework upgrades or infrastructure migrations.

It also makes it clearer which failures are domain failures and which are transaction, messaging, or persistence failures.

#### Traps / caveats

- Do not confuse “no Spring in domain” with “no Spring in the application at all”.
- Do not let JPA annotations drive the entire domain model if they damage invariants.
- Do not make ports too technical; they should express application needs.

#### Optional Anki

Q: Which Spring concerns should stay outside core domain objects?
A: Bean lifecycle, `@Transactional`, repositories, event publishers, web annotations, messaging clients, configuration, and framework exceptions.

</details>

<a id="oop-scen-018"></a>

<details>
<summary><strong>OOP-SCEN-018. How would you design integration with a third-party fraud provider?</strong></summary>

#### Short answer

I would define a fraud-check port in application terms, implement the provider as an adapter with an anti-corruption layer, and add resilience, observability, contract tests, and fallback policy.

#### Interview answer

The application should ask a business question such as `assessOrderRisk` or `screenPayment`, not manipulate vendor request DTOs directly. The adapter translates domain/application data to the provider API and translates provider responses back.

The port should model outcomes: approved, declined, manual review, provider unavailable, retry later. That is better than leaking raw vendor codes throughout the system.

#### Deep dive

The adapter owns authentication, request signing, timeouts, retries, rate limits, schema differences, and vendor SDK quirks. Use contract tests for mapping and sandbox integration tests where possible.

Decide failure policy with the business: fail closed, fail open, queue for manual review, or retry asynchronously. That policy belongs near the use case, not hidden in the HTTP client.

#### Production angle

Production concerns include latency budgets, circuit breakers, audit logs, PII handling, idempotency, provider outages, and dashboards for decision distribution.

A clean adapter boundary lets you replace the provider or run two providers in shadow mode without rewriting domain logic.

#### Traps / caveats

- Do not leak vendor DTOs, exceptions, or status codes into domain code.
- Do not retry non-idempotent operations blindly.
- Do not treat fraud decision policy as a purely technical HTTP-client concern.

#### Optional Anki

Q: Why should fraud provider status codes not leak into domain code?
A: They couple business rules to one vendor and make provider replacement, fallback policy, and testing harder.

</details>

<a id="oop-scen-019"></a>

<details>
<summary><strong>OOP-SCEN-019. How would you design a replaceable storage layer without leaking database-specific details?</strong></summary>

#### Short answer

Define repository or storage ports in application/domain terms, keep database APIs in adapters, and avoid leaking JPA, SQL, `Pageable`, entities, or vendor exceptions through the core contract.

#### Interview answer

The core should request operations it actually needs: `findOrderById`, `saveOrder`, `findPendingPayments`, or `appendEvent`. The implementation can use JPA, JDBC, MongoDB, S3, or another store behind that port.

The contract should return domain objects, aggregates, query models, or application-defined results, not persistence-provider types.

#### Deep dive

Full storage replaceability is expensive and rarely perfect. The goal is usually to isolate persistence decisions so most business code does not depend on them.

For complex search, reporting, pagination, and sorting, define application-specific query objects or separate read models instead of pretending all databases support the same semantics.

#### Production angle

This design helps with migrations, testing, and vendor changes. You can add a new adapter, dual-write or shadow-read carefully, and compare results during migration.

Still, database behavior such as transactions, locking, consistency, and query capabilities can influence the application design and should not be ignored.

#### Traps / caveats

- Do not promise database independence if your business logic depends on specific transaction or query semantics.
- Do not leak `EntityManager`, `JpaRepository`, SQL exceptions, or ORM lazy proxies through the domain boundary.
- Do not create generic CRUD repositories when the domain needs specific operations.

#### Optional Anki

Q: What persistence details should not leak through a domain repository port?
A: `EntityManager`, `JpaRepository`, lazy proxies, SQL exceptions, vendor query APIs, persistence entities, and technical pagination types.

</details>

<a id="oop-scen-020"></a>

<details>
<summary><strong>OOP-SCEN-020. How would you prevent domain objects from becoming simple DTOs with no behavior?</strong></summary>

#### Short answer

Give domain objects business-named methods that protect invariants and perform valid state transitions, while keeping DTOs at boundaries.

#### Interview answer

I would look for rules currently living in services: validation, state transitions, calculations, eligibility checks, and consistency rules. Many of those can move into entities, aggregates, or value objects.

Instead of setters like `setStatus(CANCELLED)`, use behavior such as `cancel(reason)`, `pay(paymentId)`, `ship(trackingNumber)`, or `changeAddress(newAddress)`.

#### Deep dive

Rich domain objects should not know about every technical concern. They should own business consistency for their boundary. Application services still coordinate repositories, transactions, external systems, and cross-aggregate workflows.

Value objects are especially useful: they turn repeated primitive validation into reusable, named, immutable concepts.

#### Production angle

Putting invariants in the domain reduces duplicated checks and prevents invalid states from entering persistence. It also makes business tests faster because they do not require web or database infrastructure.

The result is code that is easier to explain in business terms during incidents and feature discussions.

#### Traps / caveats

- Do not put orchestration, HTTP, transactions, or email sending inside entities.
- Do not make domain objects rich by adding random helper methods; behavior must belong to the concept.
- Do not confuse a DTO boundary object with an anemic domain model.

#### Optional Anki

Q: What is a sign that a domain object is becoming an anemic DTO?
A: Services repeatedly read its fields, make business decisions externally, and then push new state back through setters.

</details>

<details>
<summary><strong>🧠 OOP-SCEN-021. How would you balance readability and abstraction in a small feature?</strong></summary>

#### Short answer

Start with the simplest readable design, name concepts clearly, and introduce abstraction only for real variation, tested boundaries, or meaningful domain language.

#### Interview answer

For a small feature, I would avoid pattern-first design. Clear straightforward code with good names, small methods, and tests is often better than factories, strategies, and interfaces created just in case.

At the same time, I would not ignore boundaries. If the feature calls an external service, mutates important domain state, or has rules likely to change, a small abstraction may be justified.

#### Deep dive

A practical heuristic: keep code local until duplication or variation becomes real; extract when a name improves understanding; hide details when they are unstable or external; avoid hiding simple business flow behind generic indirection.

Readable abstraction has a domain name and reduces decisions for the reader. Bad abstraction adds files but not meaning.

#### Production angle

Small features still need safe change. Tests, clear error handling, and explicit dependencies matter more than showcasing design patterns.

The design should be easy for the next developer to modify during an incident or urgent product change.

#### Traps / caveats

- Do not equate fewer classes with better readability when one class mixes unrelated ideas.
- Do not equate more abstractions with senior design.
- Do not postpone naming important domain concepts just because the feature is small.

#### Optional Anki

Q: When is abstraction justified even in a small feature?
A: When it protects an external boundary, names an important domain concept, isolates unstable behavior, or makes meaningful tests simpler.

<details>
<summary><strong>🧠 OOP-SCEN-022. How would you explain an OOP/SOLID refactoring to a product-focused team?</strong></summary>

#### Short answer

I would translate the refactoring into product outcomes: lower change risk, faster delivery, fewer regressions, safer releases, and clearer ownership, while proposing incremental steps.

#### Interview answer

I would avoid saying “we need SOLID because the code is ugly”. Instead I would explain the current pain: a small pricing change touches five unrelated areas, tests are slow, releases are risky, or incidents take too long to diagnose.

Then I would propose a small plan connected to delivery: add characterization tests, extract payment provider boundary, move email sending behind a port, or split the controller logic before the next feature.

#### Deep dive

A product-focused explanation should include trade-offs: what we will change, what we will not change, how behavior stays the same, how long the code is protected by tests, and how we can stop if value does not appear.

Use concrete examples: “After this, adding one notification channel changes one adapter instead of touching checkout, billing, and user settings.”

#### Production angle

Tie refactoring to risk and flow metrics: regression rate, cycle time, lead time for similar changes, incident recovery time, test reliability, and number of touched files.

Prefer refactoring as part of feature work or risk reduction, not an open-ended rewrite.

#### Traps / caveats

- Do not sell refactoring as purely aesthetic cleanup.
- Do not ask for a big rewrite without evidence and milestones.
- Do not hide risks; explain how behavior will be protected and how rollback works.

#### Optional Anki

Q: How should refactoring be framed for a product-focused team?
A: Tie it to concrete outcomes such as lower regression risk, faster similar changes, safer releases, clearer ownership, and shorter incident recovery.

</details>
