# Data modeling and schema design

---

<a id="db-model-001"></a>

<details>
<summary><strong>DB-MODEL-001. What is database normalization?</strong></summary>

#### Short answer

Database normalization is a way to design relational schemas so data is stored with less duplication and fewer update anomalies.

#### Interview answer

Normalization means organizing tables and relationships so each fact is stored in one logical place. Instead of duplicating customer data in every order row, we store customers separately and reference them from orders.

The goal is correctness and maintainability: fewer duplicated values, fewer inconsistent updates, and clearer relationships between entities.

In practice, I usually aim for a reasonably normalized OLTP schema first, and denormalize only when there is a clear read-performance or reporting reason.

#### Deep dive

Without normalization, one business fact may appear in many rows. If it changes, every copy must be updated correctly.

Typical anomalies:

- Update anomaly: one copy changes, another copy stays stale.
- Insert anomaly: cannot add a fact without unrelated data.
- Delete anomaly: deleting one row accidentally removes the only copy of another fact.

Normalization is based on functional dependencies: which attributes determine other attributes. At senior level, the important part is not memorizing forms mechanically, but understanding which table owns each business fact.

#### Production angle

Normalized schemas are usually easier to keep correct under concurrent writes. They also make constraints and foreign keys more meaningful. The trade-off is that reads may require more joins.

#### Traps / caveats

- Normalization is not a goal by itself; it supports correctness.
- Over-normalization can make reads and application code unnecessarily complex.
- Analytics schemas are often intentionally denormalized.
- Do not denormalize before measuring or having a clear access pattern.

#### Optional Anki

Q: What is normalization mainly for?
A: Reducing duplication and update anomalies.

</details>

<a id="db-model-002"></a>

<details>
<summary><strong>DB-MODEL-002. What are 1NF, 2NF and 3NF?</strong></summary>

#### Short answer

1NF means atomic column values, 2NF removes partial dependency on a composite key, and 3NF removes transitive dependency between non-key attributes.

#### Interview answer

First normal form says that columns should contain atomic values, not repeating groups or arrays of independent facts.

Second normal form matters when the table has a composite key: every non-key column should depend on the whole key, not just part of it.

Third normal form means non-key columns should depend on the key, not on other non-key columns. For example, if `customer_id` determines `customer_email`, order rows should usually store `customer_id`, not duplicate the email as an authoritative fact.

#### Deep dive

Example 2NF issue: table key is `(order_id, product_id)`, but `order_date` depends only on `order_id`. It belongs in `orders`, not in `order_items`.

Example 3NF issue: `zip_code` determines `city`. If every customer row stores both and city changes/corrects, updates can become inconsistent.

3NF is not the final possible normal form. BCNF is stricter and removes more dependency anomalies, but real OLTP schemas are usually designed by balancing correctness, simplicity, and access patterns.

#### Production angle

In interviews, the exact academic definitions matter less than recognizing duplication and dependency problems in real schemas.

#### Traps / caveats

- 2NF is mainly relevant for composite keys.
- 3NF does not mean there is no duplication anywhere; it means dependencies are modeled correctly.
- Real production schemas may intentionally violate normal forms for performance.

#### Optional Anki

Q: What is 1NF?
A: Atomic values and no repeating groups.

Q: What does 3NF remove?
A: Transitive dependencies between non-key attributes.

</details>

<a id="db-model-003"></a>

<details>
<summary><strong>DB-MODEL-003. When would you intentionally denormalize a schema?</strong></summary>

#### Short answer

I would denormalize when a normalized model is correct but too slow or inconvenient for a proven read pattern, and the team can safely maintain the duplicated data.

#### Interview answer

Denormalization means storing derived or duplicated data intentionally. Typical reasons are faster reads, fewer joins, reporting needs, cached counters, search views, or preserving historical snapshots.

I would not denormalize only because “joins are bad”. I would first understand the access pattern, check the execution plan, add proper indexes, and measure. If reads are still too expensive, denormalization can be a valid trade-off.

#### Deep dive

Examples:

- Store `orders.total_amount` instead of summing items every time.
- Store customer name in an invoice snapshot because invoices must preserve historical data.
- Create a read model for a dashboard or search page.

#### Production angle

The hard part is keeping denormalized data consistent. You need a clear owner, update strategy, backfill plan, reconciliation checks, and monitoring for drift.

Common maintenance strategies are transactional updates in the same write path, database triggers, background jobs, CDC/event-driven updates, batch rebuilds, and periodic reconciliation against the source-of-truth tables.

#### Traps / caveats

- Denormalization improves some reads but makes writes and consistency harder.
- It can create stale data and race conditions.
- It should be documented as an intentional decision, not accidental duplication.
- Sometimes a materialized view, cache, or index is a better first step.

#### Optional Anki

Q: Main risk of denormalization?
A: Duplicated data can become inconsistent.

</details>

<a id="db-model-004"></a>

<details>
<summary><strong>DB-MODEL-004. What are one-to-one, one-to-many and many-to-many relationships?</strong></summary>

#### Short answer

They describe cardinality between entities: one row relates to one row, one row relates to many rows, or many rows relate to many rows.

#### Interview answer

One-to-one means one row in table A corresponds to at most one row in table B, for example user and user profile.

One-to-many means one parent row has many child rows, for example customer and orders.

Many-to-many means rows on both sides can have many related rows, for example students and courses. In a relational database this is modeled with a junction table.

#### Deep dive

```sql
-- one-to-many
orders.customer_id REFERENCES customers(id)

-- one-to-one
user_profiles.user_id UNIQUE REFERENCES users(id)

-- many-to-many
student_courses(student_id, course_id)
```

#### Production angle

Cardinality should be enforced by constraints, not only by ORM mappings. For example, one-to-one needs a unique constraint on the foreign key.

Delete behavior should be chosen deliberately with options such as `ON DELETE RESTRICT`, `CASCADE`, `SET NULL`, or `NO ACTION`. Foreign key columns often need indexes when they are used for joins, parent-child lookups, or delete checks.

#### Traps / caveats

- A foreign key alone usually models many-to-one from child to parent.
- One-to-one requires uniqueness on the foreign key.
- Many-to-many should not be modeled as comma-separated ids or arrays for core relational data.
- Relationships can be optional or mandatory depending on nullability.
- A many-to-many relationship can become a real domain entity if it has status, lifecycle, audit fields, permissions, or other attributes.

#### Optional Anki

Q: How do you enforce one-to-one with a foreign key?
A: Add a unique constraint on the foreign key.

</details>

<a id="db-model-005"></a>

<details>
<summary><strong>DB-MODEL-005. How do you model a many-to-many relationship in a relational database?</strong></summary>

#### Short answer

Use a junction table with foreign keys to both tables. Usually the pair of foreign keys is unique or is the primary key.

#### Interview answer

For example, users can have many roles and roles can belong to many users. I would create `user_roles` with `user_id` and `role_id`, both referencing parent tables.

If the relationship has attributes, such as assignment time or status, those attributes belong in the junction table.

#### Deep dive

```sql
CREATE TABLE user_roles (
    user_id BIGINT NOT NULL REFERENCES users(id),
    role_id BIGINT NOT NULL REFERENCES roles(id),
    assigned_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, role_id)
);
```

#### Production angle

Add indexes for both access directions if the application queries both “roles by user” and “users by role”. The primary key on `(user_id, role_id)` helps the first direction, but not always the second.

#### Traps / caveats

- Do not store many-to-many ids as comma-separated strings.
- Think about cascade delete rules carefully.
- If the relationship needs its own lifecycle, treat the junction table as a real entity.
- If the relationship has status, audit fields, permissions, or business rules, it is probably a domain entity rather than just a technical mapping table.
- Index order matters for query patterns.

#### Optional Anki

Q: How is many-to-many modeled relationally?
A: With a junction table containing foreign keys to both sides.

</details>

<a id="db-model-006"></a>

<details>
<summary><strong>DB-MODEL-006. What is a surrogate key?</strong></summary>

#### Short answer

A surrogate key is an artificial identifier with no business meaning, such as a generated numeric id or UUID.

#### Interview answer

A surrogate key exists only to identify a row. It is not derived from real-world data and should not change when business attributes change.

Common examples are `BIGSERIAL`, identity columns, sequences, or UUIDs. They are popular because they are stable, small enough for foreign keys if numeric, and simple to use from application code.

#### Deep dive

```sql
CREATE TABLE customers (
    id BIGSERIAL PRIMARY KEY,
    email TEXT NOT NULL UNIQUE
);
```

Here `id` is a surrogate key, while `email` is a business attribute with a unique constraint.

#### Production angle

Surrogate keys are usually a safe default for OLTP systems. Business uniqueness should still be enforced separately with unique constraints.

#### Traps / caveats

- A surrogate key does not enforce business uniqueness.
- Do not expose sequential ids publicly if enumeration is a security concern.
- Changing key type later can be expensive.
- UUID surrogate keys have different index and storage trade-offs than numeric keys.

#### Optional Anki

Q: What is a surrogate key?
A: An artificial row identifier without business meaning.

</details>

<a id="db-model-007"></a>

<details>
<summary><strong>DB-MODEL-007. What is a natural key?</strong></summary>

#### Short answer

A natural key is a real business attribute or combination of attributes that uniquely identifies a row, such as country code or external system id.

#### Interview answer

Unlike a surrogate key, a natural key has business meaning. Examples are ISO country code, tax id, or an id from an external provider.

Natural keys can be good when they are stable, compact, and truly unique. But many business values that look unique later change, get reused, or have exceptions.

#### Deep dive

```sql
CREATE TABLE countries (
    code CHAR(2) PRIMARY KEY,
    name TEXT NOT NULL
);
```

Here `code` can be a natural primary key if ISO codes are acceptable for the domain.

#### Production angle

I usually prefer surrogate primary keys for internal identity and unique constraints for natural business identifiers. That gives stable references and still protects business rules.

#### Traps / caveats

- Email is often a bad primary key because it can change.
- External ids may change semantics when providers migrate systems.
- Natural keys can be wide, which makes foreign keys and indexes larger.
- If a natural key is used, validate its stability with the business domain.

#### Optional Anki

Q: What is a natural key?
A: A business-meaningful unique identifier.

</details>

<a id="db-model-008"></a>

<details>
<summary><strong>DB-MODEL-008. What are the pros and cons of UUID primary keys?</strong></summary>

#### Short answer

UUIDs are globally unique and easy to generate outside the database, but they are larger than integers and random UUIDs can hurt B-tree index locality.

#### Interview answer

UUID primary keys are useful in distributed systems because services can generate ids without a central sequence. They are also harder to enumerate than sequential ids, which can be useful for public identifiers.

The downsides are storage and performance. UUID is 16 bytes, larger than `BIGINT`. Random UUIDs insert into random places in a B-tree index, causing more page splits, cache misses, and index bloat.

Modern options like UUIDv7 or ULID-style time-ordered identifiers reduce the locality problem while preserving distributed generation.

#### Deep dive

```sql
CREATE TABLE events (
    id UUID PRIMARY KEY,
    payload JSONB NOT NULL
);
```

Good fit: offline id generation, event ingestion, external ids. Risky fit: huge high-write table with random UUIDv4 as the primary B-tree index key.

#### Production angle

If UUIDs are needed, consider time-ordered UUIDs, proper fillfactor, monitoring index bloat, and keeping separate internal numeric keys if the schema has many large child tables.

#### Traps / caveats

- UUIDs are not automatically faster or safer than integers.
- The main index locality problem is usually random UUIDv4, not UUIDs as a concept.
- A public UUID can be separate from an internal numeric primary key.
- Time-ordered UUIDs reduce locality problems but do not remove the larger storage and foreign-key cost.
- Random UUIDs can hurt index locality.
- UUIDs make foreign keys and indexes larger.
- Do not store UUIDs as text unless there is a strong reason; PostgreSQL has a native `uuid` type.

#### Optional Anki

Q: Main advantage of UUID keys?
A: Distributed generation and global uniqueness.

Q: Main index problem with random UUIDs?
A: Poor B-tree locality.

</details>

<a id="db-model-009"></a>

<details>
<summary><strong>DB-MODEL-009. What are the pros and cons of sequential primary keys?</strong></summary>

#### Short answer

Sequential keys are small, fast, and index-friendly, but they are predictable and usually require database-side generation or coordination.

#### Interview answer

A sequential primary key, usually `BIGINT` generated by sequence or identity, is a strong default for many OLTP tables. It is compact, joins efficiently, and inserts tend to go to the end of the B-tree index.

The downsides are predictability and central generation. If ids are exposed in APIs, users may enumerate resources unless authorization is correct. In distributed systems, sequence generation may also become a coordination point.

#### Deep dive

```sql
CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

#### Production angle

Sequential keys are excellent for internal relational identity. If sequential ids are exposed externally, authorization must not rely on id unpredictability. For public APIs, it is common to use a separate public UUID or slug while keeping an internal numeric primary key.

#### Traps / caveats

- Sequential ids are predictable; never rely on obscurity for authorization.
- Use `BIGINT` rather than `INT` for tables that can grow large.
- Sequence gaps are normal and should not be treated as data loss.
- Hot insert patterns can still create contention in some workloads.

#### Optional Anki

Q: Main index advantage of sequential ids?
A: Inserts are mostly append-like in the B-tree.

</details>

<a id="db-model-010"></a>

<details>
<summary><strong>🧠 DB-MODEL-010. Why can random UUIDs be bad for B-tree indexes?</strong></summary>

#### Short answer

Random UUIDs insert into random positions in a B-tree, causing poor locality, more page splits, more cache misses, and larger indexes.

#### Interview answer

A B-tree index is ordered. With sequential ids, new entries usually go near the end of the index. With random UUIDv4, each insert may target a different page.

That random write pattern is harder for memory cache and storage. It can fragment the index, increase page splits, and make the primary key and all referencing foreign-key indexes larger.

#### Deep dive

The issue is not uniqueness itself. The issue is randomness combined with an ordered index structure. Time-ordered identifiers such as UUIDv7 reduce this problem because nearby inserts have similar prefixes.

#### Production angle

For high-write large tables, random UUID primary keys should be a conscious decision. Benchmark with production-like data, monitor index bloat, and consider UUIDv7, ULID-like ids, or internal numeric keys.

#### Traps / caveats

- Small tables may not notice the difference.
- The problem is worse on high-write and large indexed tables.
- UUID as public id can be separate from internal primary key.
- The problem is mostly about random UUIDv4 locality; UUIDv7/ULID-style ids reduce locality issues but still use wider keys than `BIGINT`.
- Use PostgreSQL native `uuid`, not text, when using UUIDs.

#### Optional Anki

Q: Why do random UUIDs hurt B-tree locality?
A: They insert into random index pages instead of mostly appending.

</details>

<a id="db-model-011"></a>

<details>
<summary><strong>DB-MODEL-011. When would you use a composite primary key?</strong></summary>

#### Short answer

I would use a composite primary key when row identity is naturally defined by a combination of columns, especially in junction tables or scoped entities.

#### Interview answer

A composite primary key contains more than one column. It is common for many-to-many tables, for example `(user_id, role_id)`, where the pair is the identity.

It can also be useful when uniqueness is scoped, for example `(tenant_id, external_id)`.

I avoid composite keys when they make foreign keys, ORM mapping, or API references too cumbersome; then I may use a surrogate key plus a unique constraint on the natural column pair.

#### Deep dive

```sql
CREATE TABLE user_roles (
    user_id BIGINT NOT NULL REFERENCES users(id),
    role_id BIGINT NOT NULL REFERENCES roles(id),
    PRIMARY KEY (user_id, role_id)
);
```

#### Production angle

Composite keys affect index order. A primary key on `(tenant_id, id)` helps queries by tenant first, but not necessarily by `id` alone.

#### Traps / caveats

- Composite primary keys make child foreign keys wider.
- Tenant-scoped composite foreign keys such as `(tenant_id, entity_id)` can prevent accidental cross-tenant references.
- ORMs can handle them, but mapping is often more verbose.
- Column order matters for indexes.
- Sometimes surrogate primary key plus unique composite constraint is more practical.

#### Optional Anki

Q: Common use case for composite primary key?
A: Junction table, such as `(user_id, role_id)`.

</details>

<a id="db-model-012"></a>

<details>
<summary><strong>DB-MODEL-012. How would you model soft deletes?</strong></summary>

#### Short answer

Usually with a nullable `deleted_at` timestamp, sometimes also `deleted_by` and `delete_reason`. Active rows are those where `deleted_at IS NULL`.

#### Interview answer

Soft delete means we do not physically remove the row. Instead, we mark it as deleted. I prefer `deleted_at` over a boolean `is_deleted`, because it also tells when deletion happened.

Queries must consistently filter out deleted rows. If uniqueness should apply only to active rows, PostgreSQL partial unique indexes are useful.

#### Deep dive

```sql
ALTER TABLE users
ADD COLUMN deleted_at TIMESTAMPTZ;

CREATE UNIQUE INDEX users_email_active_uq
ON users (email)
WHERE deleted_at IS NULL;
```

#### Production angle

Soft delete is useful for recovery, audit, legal hold, and preserving references. But it requires consistent query filters, index strategy, and a retention or purge process.

If all reads must exclude deleted rows, enforce that convention through repositories, views, Row Level Security, or carefully designed query filters instead of relying only on developer memory.

#### Traps / caveats

- Forgetting `deleted_at IS NULL` leaks deleted data.
- Soft-deleted rows still occupy storage and indexes.
- Foreign keys still reference soft-deleted rows unless modeled otherwise.
- Unique constraints may need partial indexes.
- Soft delete is not the same as audit history.

#### Optional Anki

Q: Common soft delete column?
A: `deleted_at`.

Q: How to enforce unique email only for active users in PostgreSQL?
A: Partial unique index with `WHERE deleted_at IS NULL`.

</details>

<a id="db-model-013"></a>

<details>
<summary><strong>DB-MODEL-013. What are the risks of soft deletes?</strong></summary>

#### Short answer

Soft deletes can leak deleted data, complicate queries and constraints, increase table bloat, and make business semantics unclear.

#### Interview answer

The main risk is that deleted rows are still in the table. Every read path must know whether to include or exclude them. If one query forgets the filter, users may see deleted data.

Soft deletes also complicate uniqueness, foreign keys, counts, reports, and cleanup. Over time, tables and indexes may grow with data that is not normally used.

#### Deep dive

Example issue: user email is unique. If a user is soft-deleted, should another user be allowed to reuse the same email? The answer depends on business rules and affects indexes.

#### Production angle

Before choosing soft delete, define who can see deleted data, how long it is retained, how it is purged, how it affects uniqueness, and how foreign-key relationships behave.

#### Traps / caveats

- Soft delete can violate privacy expectations if data should be truly erased.
- It can make analytics wrong if deleted rows are counted accidentally.
- It can hide data quality problems instead of solving lifecycle design.
- It requires retention and purge jobs in many systems.
- For high-volume tables, soft deletes without physical purge can create long-term table and index bloat.

#### Optional Anki

Q: Main soft delete risk?
A: Deleted rows remain visible unless every query filters them correctly.

</details>

<a id="db-model-014"></a>

<details>
<summary><strong>DB-MODEL-014. How would you model audit fields like created_at and updated_at?</strong></summary>

#### Short answer

Common audit fields are `created_at`, `updated_at`, sometimes `created_by`, `updated_by`, and `deleted_at`. Use timezone-aware timestamps and clear ownership for setting them.

#### Interview answer

I usually model timestamps as `TIMESTAMPTZ NOT NULL`. `created_at` can default to `now()`. `updated_at` can be maintained by application code, ORM auditing, or a database trigger.

For user attribution, `created_by` and `updated_by` can reference users or store an actor id, depending on whether actors always exist in the same database.

#### Deep dive

```sql
CREATE TABLE invoices (
    id BIGSERIAL PRIMARY KEY,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_by BIGINT,
    updated_by BIGINT
);
```

#### Production angle

Audit fields are useful for debugging, support, ordering, synchronization, and incident analysis. For full compliance audit, simple fields are not enough; you need an audit log or event history.

#### Traps / caveats

- Use `TIMESTAMPTZ` in PostgreSQL for absolute points in time.
- Define whether database time or application time is authoritative.
- In PostgreSQL, `now()` / `CURRENT_TIMESTAMP` returns the transaction start time; use `clock_timestamp()` if you need the actual wall-clock time at the moment of execution.
- `updated_at` can be forgotten if maintained manually.
- Audit fields do not show what changed; they only show metadata about the row.

#### Optional Anki

Q: PostgreSQL type for audit timestamps?
A: Usually `TIMESTAMPTZ`.

Q: Are `created_at` and `updated_at` a full audit log?
A: No.

</details>

<a id="db-model-015"></a>

<details>
<summary><strong>DB-MODEL-015. How would you design a schema for multi-tenant data?</strong></summary>

#### Short answer

Common options are shared tables with `tenant_id`, separate schemas per tenant, or separate databases per tenant. The right choice depends on isolation, scale, operations, and cost.

#### Interview answer

For many SaaS systems, the practical default is shared tables with a `tenant_id` column on tenant-owned tables. Queries always filter by tenant, and uniqueness is usually scoped by tenant, for example `UNIQUE (tenant_id, email)`.

If tenants require strong isolation, custom backup/restore, different versions, or very different sizes, separate schemas or databases may be better.

The most important rule is that tenant isolation must be enforced consistently, not left to ad-hoc filters scattered through application code.

#### Deep dive

```sql
CREATE TABLE users (
    tenant_id BIGINT NOT NULL REFERENCES tenants(id),
    id BIGINT GENERATED ALWAYS AS IDENTITY,
    email TEXT NOT NULL,
    PRIMARY KEY (tenant_id, id),
    UNIQUE (tenant_id, email)
);
```

This makes identity and uniqueness tenant-scoped. Another common option is `id` as global primary key plus indexes and unique constraints that include `tenant_id`.

#### Production angle

Multi-tenancy affects indexing, authorization, migrations, backups, analytics, noisy-neighbor isolation, and incident response. For shared tables, indexes often need to include `tenant_id` when queries are tenant-scoped, but column order should still follow actual query patterns: equality filters, range filters, ordering, and selectivity.

Tenant isolation should be enforced at multiple levels: application authorization, tenant-scoped queries, tenant-scoped unique constraints, tenant-scoped foreign keys, optional PostgreSQL Row Level Security, and tests that specifically check cross-tenant access.

#### Traps / caveats

- Forgetting tenant filters is a serious data leak.
- Unique constraints often need `tenant_id`.
- Foreign keys may need composite tenant-scoped references to prevent cross-tenant links.
- Large tenants can dominate shared tables and indexes.
- Row Level Security can help, but it must be carefully designed and tested.
- Do not blindly put `tenant_id` first in every index; index column order still depends on the real filtering and sorting pattern.

#### Optional Anki

Q: Common shared-table multi-tenant column?
A: `tenant_id`.

Q: How to scope unique email per tenant?
A: `UNIQUE (tenant_id, email)`.

</details>
