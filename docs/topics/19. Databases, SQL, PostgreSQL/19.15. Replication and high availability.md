# Replication and high availability

---

<a id="db-repl-001"></a>

<details>
<summary><strong>🧠 DB-REPL-001. What is physical replication?</strong></summary>

#### Short answer

Physical replication copies PostgreSQL data at the storage/WAL level, producing a byte-for-byte compatible standby.

#### Interview answer

In PostgreSQL, physical replication streams WAL records from primary to standby. The standby replays the same low-level changes and becomes a copy of the primary cluster.

It is commonly used for high availability, failover, backups, and read-only replicas.

#### Deep dive

Physical replication is usually database-cluster oriented, not selective per table. The standby has the same database structure and cannot independently change replicated data.

Because changes are WAL-level, this replication is efficient and faithful but less flexible than logical replication.

#### Production angle

In production, physical replication is the standard building block for hot standby and failover. You must monitor lag, WAL retention, replication slots, disk usage, and failover procedures.

Read-only traffic can be sent to standbys, but the application must tolerate lag.

#### Traps / caveats

- Physical replication is not table-level filtering.
- Standby queries are read-only.
- Replica lag can break read-after-write expectations.
- A failed replication slot can retain WAL and fill disk.

#### Optional Anki

Q: What does physical replication copy?
A: WAL/storage-level changes, producing a standby copy of the primary.

</details>

<a id="db-repl-002"></a>

<details>
<summary><strong>🧠 DB-REPL-002. What is logical replication?</strong></summary>

#### Short answer

Logical replication replicates data changes in logical form, usually per table/publication, rather than copying the whole storage layout.

#### Interview answer

PostgreSQL logical replication uses publications and subscriptions. A publisher defines which tables to publish, and a subscriber receives row-level changes.

It is useful for selective replication, migrations, data distribution, integration pipelines, and some zero-downtime upgrade scenarios.

#### Deep dive

Logical replication is based on logical decoding of WAL. It can replicate INSERT/UPDATE/DELETE/TRUNCATE operations, but schema changes require separate handling.

It can work across different major versions more flexibly than physical replication, but it has its own limitations.

#### Production angle

In production, logical replication needs careful monitoring: replication lag, slot retention, conflicts, missing primary keys, schema drift, and initial data copy.

It is not a magic distributed database.

#### Traps / caveats

- DDL is not automatically handled like DML.
- Tables usually need replica identity for updates/deletes.
- Large transactions can create lag.
- Conflicts and schema drift must be managed.

#### Optional Anki

Q: What is logical replication useful for?
A: Selective table-level replication, migrations, integrations, and data distribution.

</details>

<a id="db-repl-003"></a>

<details>
<summary><strong>🧠 DB-REPL-003. What is streaming replication?</strong></summary>

#### Short answer

Streaming replication continuously sends WAL records from a primary server to standby servers.

#### Interview answer

Instead of waiting for WAL archive files, standby servers receive WAL over a replication connection and replay it quickly.

This is the common mechanism behind hot standby replicas in PostgreSQL.

#### Deep dive

Streaming replication can be asynchronous or synchronous. In asynchronous mode, primary commits do not wait for standby. In synchronous mode, commits can wait for acknowledgements from configured synchronous standbys.

The trade-off is latency vs durability/consistency.

#### Production angle

Monitor replication lag, WAL sender/receiver status, network, disk IO, and standby replay delay.

Do not send latency-sensitive read-after-write traffic to a lagging replica.

#### Traps / caveats

- Network issues can cause lag.
- Synchronous replication can add commit latency.
- A standby can be available but stale.
- Replication does not replace backups.

#### Optional Anki

Q: What does streaming replication stream?
A: WAL records from primary to standby.

</details>

<a id="db-repl-004"></a>

<details>
<summary><strong>🧠 DB-REPL-004. What is a replication slot?</strong></summary>

#### Short answer

A replication slot tells PostgreSQL to retain WAL needed by a replica or logical consumer until that consumer confirms it has received it.

#### Interview answer

Slots prevent a replica or logical subscriber from falling behind and losing required WAL. Without a slot, old WAL might be removed before the consumer reads it.

Slots can be physical or logical.

#### Deep dive

A slot has a restart position. PostgreSQL keeps WAL from that point so the consumer can resume.

This reliability comes with a risk: if a slot is inactive or consumer is broken, WAL can accumulate and fill disk.

#### Production angle

In production, monitor inactive slots, retained WAL size, lag, and disk usage. Drop unused slots intentionally.

Useful checks include `pg_replication_slots` columns such as `active`, `restart_lsn`, `confirmed_flush_lsn`, and retained WAL estimated with `pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)`.

Slots are powerful but dangerous when ignored.

#### Traps / caveats

- Slots protect consumers but can fill disk.
- Dropping a slot can break a lagging consumer.
- Logical slots are common for CDC tools.
- `max_slot_wal_keep_size` can limit damage, but the consumer can still break if required WAL is removed.
- Slots are not backups.

#### Optional Anki

Q: Main risk of replication slots?
A: An inactive slot can retain WAL until disk fills up.

</details>

<a id="db-repl-005"></a>

<details>
<summary><strong>DB-REPL-005. What is replication lag?</strong></summary>

#### Short answer

Replication lag is how far a replica is behind the primary in receiving, writing, flushing, or replaying changes.

#### Interview answer

A replica may have received WAL but not replayed it yet. From the application point of view, the important question is usually: can a read from replica see the write that just committed on primary?

Lag can be measured in bytes, time, or LSN difference, depending on the view and metric.

#### Deep dive

Lag sources include network, standby IO, long-running queries on standby, high write volume, checkpoints, replication slot retention, and CPU pressure.

In physical streaming replication, monitor write_lag, flush_lag, replay_lag and LSN positions.

On the primary, `pg_stat_replication` exposes `sent_lsn`, `write_lsn`, `flush_lsn`, `replay_lsn`, `write_lag`, `flush_lag`, and `replay_lag`. `pg_wal_lsn_diff` helps estimate byte lag.

#### Production angle

In production, lag affects correctness. After a user writes data, routing the next read to a lagging replica can show stale data.

Solutions include read-your-writes routing to primary, sticky sessions, lag-aware routing, waiting for replay, or accepting eventual consistency.

#### Traps / caveats

- A replica can be healthy but stale.
- Time lag and byte lag tell different things.
- Long standby queries can delay replay.
- Read replicas do not scale writes.

#### Optional Anki

Q: What is replication lag?
A: How far a replica is behind the primary in applying changes.

</details>

<a id="db-repl-006"></a>

<details>
<summary><strong>DB-REPL-006. Why can reading from replicas be dangerous after writes?</strong></summary>

#### Short answer

Because replicas may be stale due to replication lag, so a read immediately after a write may not see the committed data.

#### Interview answer

The primary commits the transaction first, and the replica applies WAL later. In asynchronous replication this delay is expected.

This can break user flows like create order → redirect to order page if the order page reads from replica.

#### Deep dive

The problem is read-after-write consistency. The system may be eventually consistent, but users often expect their own writes to be visible immediately.

Different consistency requirements can apply to different reads.

#### Production angle

Production patterns: route reads after writes to primary for a period, use sticky sessions, check replica lag, include causal tokens/LSNs, or block until replica catches up.

Do not blindly load-balance all reads to replicas.

#### Traps / caveats

- Stale reads are correctness bugs for some flows.
- Synchronous replication reduces but does not remove all design issues.
- Different endpoints may need different consistency.
- Cache plus replica lag can make staleness worse.

#### Optional Anki

Q: Why can read replicas show stale data?
A: Because asynchronous replicas apply committed primary changes later.

</details>

<a id="db-repl-007"></a>

<details>
<summary><strong>DB-REPL-007. What is read-after-write consistency?</strong></summary>

#### Short answer

Read-after-write consistency means a client can read its own committed write immediately after writing.

#### Interview answer

For example, after creating a profile, the user refreshes the page and expects to see the new profile. If the read goes to a lagging replica, the profile may appear missing.

This consistency is often required for user-facing flows.

#### Deep dive

Read-after-write can be local to one user or global. Local read-your-writes is easier: route this user's reads to primary temporarily or use a session marker.

Global immediate consistency across replicas is more expensive.

#### Production angle

In production, classify endpoints: some need fresh data, some tolerate lag. This lets you safely use replicas without breaking correctness.

Document consistency expectations in service contracts.

#### Traps / caveats

- Do not assume eventual consistency is acceptable everywhere.
- A successful write response changes user expectations.
- Sticky routing can help but must expire.
- Background jobs may tolerate more staleness than user flows.

#### Optional Anki

Q: What is read-after-write consistency?
A: A client can read its own committed write immediately after writing.

</details>

<a id="db-repl-008"></a>

<details>
<summary><strong>DB-REPL-008. What is synchronous replication?</strong></summary>

#### Short answer

Synchronous replication makes a primary commit wait until configured standby server(s) confirm receiving or applying WAL to a required level.

#### Interview answer

It improves durability and can reduce data loss on primary failure, because commit acknowledgement depends on standby acknowledgement.

The exact wait point depends on configuration: remote write, flush, apply, or quorum behavior.

#### Deep dive

Synchronous replication trades commit latency and availability for stronger guarantees. If synchronous standby is unavailable and no alternative is configured, writes may block.

It does not automatically solve application-level consistency design.

#### Production angle

Use it for critical data where losing committed transactions is unacceptable. Configure quorum/standby names carefully and test failover behavior.

Monitor synchronous standby health and commit latency.

#### Traps / caveats

- Synchronous replication can block writes.
- It adds network latency to commits.
- It does not replace backups.
- Improper failover can still cause operational issues.

#### Optional Anki

Q: Main trade-off of synchronous replication?
A: Stronger durability/consistency at the cost of commit latency and possible write blocking.

</details>

<a id="db-repl-009"></a>

<details>
<summary><strong>DB-REPL-009. What is asynchronous replication?</strong></summary>

#### Short answer

Asynchronous replication lets primary commits return without waiting for replicas to confirm the change.

#### Interview answer

This is the common default for read replicas. It keeps write latency low and replicas eventually catch up.

The downside is possible data loss if primary fails before WAL reaches a standby, and possible stale reads from replicas.

#### Deep dive

The primary and standby are loosely coupled. The replica replays WAL when it can. Lag depends on write rate, network, standby load and IO.

Asynchronous replication is often good enough for read scaling and many HA setups, but consistency expectations must be explicit.

#### Production angle

Use asynchronous replicas for traffic that tolerates staleness: reports, feeds, search pages, background jobs.

Keep fresh reads on primary when correctness requires it.

#### Traps / caveats

- Low write latency does not mean no lag.
- A replica can be seconds or minutes behind during incidents.
- Failover may lose latest commits.
- Read routing must be lag-aware.

#### Optional Anki

Q: What does asynchronous replication optimize for?
A: Low primary commit latency and read scaling, at the cost of lag/data-loss risk.

</details>

<a id="db-repl-010"></a>

<details>
<summary><strong>DB-REPL-010. What are the trade-offs between synchronous and asynchronous replication?</strong></summary>

#### Short answer

Synchronous replication gives stronger durability but higher latency and lower availability; asynchronous replication gives lower latency but allows lag and possible data loss.

#### Interview answer

Synchronous commits wait for standby acknowledgement. This reduces the chance of acknowledged data being lost but makes writes depend on replica/network health.

Asynchronous commits do not wait, so writes are fast and available, but replicas can be stale and failover can lose recent commits.

#### Deep dive

The choice is not always global. Some systems use asynchronous replication generally but stronger durability for specific critical flows, or tune synchronous_commit.

Quorum synchronous replication can balance guarantees and availability.

#### Production angle

Ask product/business what is worse: slower writes, blocked writes, stale reads, or losing the last few committed transactions.

Then encode the decision in database config and application routing.

#### Traps / caveats

- There is no universally best mode.
- Synchronous replication can reduce availability during standby failures.
- Asynchronous replication requires lag-aware reads.
- Failover semantics must be tested.

#### Optional Anki

Q: Synchronous vs asynchronous replication?
A: Synchronous waits for standby; asynchronous does not, trading durability for latency/availability.

</details>

<a id="db-repl-011"></a>

<details>
<summary><strong>DB-REPL-011. What happens during failover?</strong></summary>

#### Short answer

Failover promotes a standby to become the new primary when the old primary is unavailable.

#### Interview answer

A failover process usually detects primary failure, chooses a standby, promotes it, redirects clients, and prevents the old primary from accepting writes if it comes back.

After failover, other replicas must follow the new primary or be rebuilt.

#### Deep dive

The hard parts are fencing, split-brain prevention, replication lag, client reconnects, DNS/load balancer updates, and data loss risk.

Failover can be manual or automated through orchestration tools.

#### Production angle

Production failover must be rehearsed. Run drills, measure RTO/RPO, and verify applications handle reconnects and read/write routing changes.

Do not discover failover behavior during the first real incident.

#### Traps / caveats

- Automated failover without fencing can create split brain.
- Asynchronous replication can lose recent commits.
- Clients need retry/reconnect logic.
- Old primary must not rejoin as primary accidentally.

#### Optional Anki

Q: What is failover?
A: Promoting a standby to primary and redirecting traffic after primary failure.

</details>

<a id="db-repl-012"></a>

<details>
<summary><strong>🧠 DB-REPL-012. What problems can appear after failover?</strong></summary>

#### Short answer

Problems include data loss, split brain, stale routing, broken connections, replicas following the wrong primary, and application retry storms.

#### Interview answer

If the old primary accepted writes that were not replicated, those writes may be lost after standby promotion. If both old and new primary accept writes, split brain occurs.

Applications may still connect to old endpoints or have cached DNS.

#### Deep dive

Other problems: sequence gaps, replication topology repair, broken logical replication, read replicas that need rebuild, long recovery time, and inconsistent caches.

Failover changes are both database and application events.

#### Production angle

In production, have runbooks: validate new primary, block old primary, update routing, check replication, verify application health, inspect data loss window, and reconcile if needed.

Use circuit breakers/retries carefully to avoid thundering herds.

#### Traps / caveats

- Failover can succeed technically but fail at application level.
- Split brain is catastrophic.
- DNS TTLs can delay traffic switch.
- Caches/search indexes may become inconsistent.

#### Optional Anki

Q: Name one serious failover risk.
A: Split brain or loss of recent writes.

</details>

<a id="db-repl-013"></a>

<details>
<summary><strong>🧠 DB-REPL-013. What is split brain?</strong></summary>

#### Short answer

Split brain is when two nodes both believe they are primary and accept writes at the same time.

#### Interview answer

This can happen after network partitions or bad failover if the old primary is not fenced before a standby is promoted.

Once two primaries accept divergent writes, reconciliation can be extremely difficult.

#### Deep dive

Split brain is a distributed systems failure. Prevention needs fencing, consensus/orchestration, clear ownership, and safe failover rules.

Database replication alone does not automatically solve split brain.

#### Production angle

In production, ensure there is exactly one writable primary. Automation should prevent the old primary from accepting writes before promoting another node.

Test network-partition scenarios, not only clean shutdown.

#### Traps / caveats

- Split brain can corrupt business data.
- Manual emergency actions can cause it.
- Load balancers can route writes to the wrong node.
- Fencing is not optional in serious HA setups.

#### Optional Anki

Q: What is split brain?
A: Two nodes accepting writes as primary at the same time.

</details>

<a id="db-repl-014"></a>

<details>
<summary><strong>🧠 DB-REPL-014. How would you design application behavior when a read replica is lagging?</strong></summary>

#### Short answer

Use lag-aware routing: send consistency-sensitive reads to primary, avoid lagging replicas, or degrade gracefully.

#### Interview answer

The application should know which reads require freshness. For example, after a write, read the user's own data from primary for a short time.

For less critical pages, stale data may be acceptable with clear semantics.

#### Deep dive

Implementation options: track replica lag metrics, set a maximum lag threshold, remove lagging replicas from read pool, use sticky primary reads after writes, or wait until a replica reaches a known LSN.

A common senior-level design is a causal token: after a write, remember an LSN/timestamp and route reads only to replicas that have replayed at least that point; otherwise use primary.

Some systems use causal tokens to route reads safely.

#### Production angle

In production, make lag behavior visible: metrics, alerts, feature flags, fallback to primary, and load protection so a fallback does not overload primary.

Test how the app behaves when replica lag spikes.

#### Traps / caveats

- Fallback to primary can overload primary.
- Strict freshness for every read may remove replica benefits.
- Do not hide stale data bugs as cache issues.
- Define acceptable staleness per use case.

#### Optional Anki

Q: How to handle lagging read replicas?
A: Use lag-aware routing and send fresh reads to primary when needed.

</details>

<a id="db-repl-015"></a>

<details>
<summary><strong>🧠 DB-REPL-015. When would you route reads to replicas, and when would you avoid it?</strong></summary>

#### Short answer

Use replicas for stale-tolerant read-heavy workloads; avoid them for read-after-write, locking, transactional, or consistency-critical reads.

#### Interview answer

Good replica reads: reports, feeds, search pages, exports, dashboards, background jobs, and public content that tolerates lag.

Avoid replicas when a user must immediately see their own write, when using `SELECT FOR UPDATE`, when correctness requires latest state, or when lag is high.

#### Deep dive

Routing can be per endpoint or per query. A simple rule is: writes and strong reads go to primary; weak reads can go to replicas.

Some queries are expensive enough that they should go to analytics infrastructure instead of OLTP replicas.

#### Production angle

In production, use health checks, lag thresholds, connection pools per target, and clear ownership of routing rules.

Observe replica impact: a heavy report on replica can still affect replication replay and lag.

#### Traps / caveats

- Read-only does not mean safe for all reads.
- A replica cannot handle writes or row locks that must affect primary.
- Stale reads can violate business expectations.
- Replicas can become overloaded too.

#### Optional Anki

Q: When avoid read replicas?
A: For read-after-write, locking, or consistency-critical reads.

</details>
