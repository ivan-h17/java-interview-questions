# Partitioning, sharding and scaling

---

<a id="db-scale-001"></a>

<details>
<summary><strong>DB-SCALE-001. What is table partitioning in PostgreSQL?</strong></summary>

#### Short answer

Table partitioning is splitting one logical table into multiple physical child tables called partitions, while querying through the parent table.

#### Interview answer

In PostgreSQL, a partitioned table is a logical parent. Actual rows live in partitions. A row is routed to a partition based on the partition key, for example date, region, tenant, or hash value.

Partitioning is usually used for very large tables, time-series data, audit logs, and workloads where queries naturally target a subset of data.

#### Deep dive

The key mechanism is partition pruning: the planner or executor can skip partitions that cannot contain matching rows. For example, a query for one month can avoid scanning partitions for other months.

Partitioning is not the same as an index. It reduces the number of physical relations to scan; indexes inside relevant partitions still matter.

#### Production angle

In production, partitioning is useful for lifecycle management: dropping or detaching an old partition is often safer and faster than deleting millions of rows.

Before partitioning, check query patterns, partition count, maintenance overhead, indexes, constraints, and operational tooling.

#### Traps / caveats

- Partitioning does not automatically make every query faster.
- Bad partition key selection can make performance worse.
- Too many partitions can slow planning and operations.
- Unique constraints on partitioned tables have limitations.

#### Optional Anki

Q: What is PostgreSQL table partitioning?
A: One logical parent table split into multiple physical partitions, with rows routed by a partition key.

</details>

<a id="db-scale-002"></a>

<details>
<summary><strong>DB-SCALE-002. What is the difference between partitioning and sharding?</strong></summary>

#### Short answer

Partitioning usually splits data inside one database cluster; sharding splits data across multiple independent database nodes or clusters.

#### Interview answer

Partitioning is a database-internal scaling and maintenance technique. The application may still see one logical table.

Sharding is a distributed architecture technique. Data is divided across separate database instances, and the application or infrastructure must route requests to the correct shard.

#### Deep dive

Partitioning helps when one table is too large to manage efficiently or queries naturally filter by partition key. Sharding helps when one database instance is not enough for storage, write throughput, or tenant isolation.

Partitioning does not remove the limits of one primary database server. Sharding introduces cross-shard query, transaction, rebalancing, and operational complexity.

#### Production angle

For a senior backend answer, explain the trade-off: partitioning is easier operationally but has limited scale-out; sharding scales further but makes consistency and queries harder.

Many systems should exhaust indexing, query optimization, read replicas, partitioning, and vertical scaling before introducing sharding.

#### Traps / caveats

- Do not call every partitioning scheme sharding.
- Sharding usually changes application architecture.
- Cross-shard joins and transactions are expensive or avoided.
- Bad shard key selection is hard to fix later.

#### Optional Anki

Q: Partitioning vs sharding?
A: Partitioning splits data inside one DB cluster; sharding splits data across independent DB nodes/clusters.

</details>

<a id="db-scale-003"></a>

<details>
<summary><strong>DB-SCALE-003. What are range, list and hash partitioning?</strong></summary>

#### Short answer

Range partitions by value intervals, list partitions by explicit value lists, and hash partitions by hash remainder.

#### Interview answer

Range partitioning is common for dates: one partition per month or day. List partitioning is common for categories like country or region. Hash partitioning spreads data more evenly when no natural range exists.

Choosing the type depends on query predicates, data distribution, retention, and operational tasks.

#### Deep dive

Range works best when queries contain conditions like `created_at >= ... AND created_at < ...`. List works when partitions map to known values. Hash can distribute writes but gives less natural pruning for range queries.

Composite partitioning is also possible through subpartitioning, but it increases complexity.

#### Production angle

Use range partitioning for time-based retention. Use list partitioning when operations are naturally grouped by category. Use hash partitioning when you need distribution but not time-window lifecycle management.

Always test with production-like queries.

#### Traps / caveats

- Hash partitioning is not the same as sharding.
- Range partitions can become unbalanced if recent data is much hotter.
- List partitions need a strategy for new values.
- Default partitions can hide routing mistakes.

#### Optional Anki

Q: Name three PostgreSQL partitioning strategies.
A: Range, list, and hash partitioning.

</details>

<a id="db-scale-004"></a>

<details>
<summary><strong>DB-SCALE-004. What is partition pruning?</strong></summary>

#### Short answer

Partition pruning is PostgreSQL skipping partitions that cannot contain rows matching the query conditions.

#### Interview answer

If a table is partitioned by `created_at` and the query asks for January only, PostgreSQL can avoid scanning February, March, and other partitions.

Pruning can happen during planning or execution, depending on whether partition key values are known early enough.

#### Deep dive

Partition pruning requires predicates that the planner can relate to the partition key. Functions or expressions around the partition key can prevent effective pruning.

Prepared statements and parameters can also affect whether pruning happens at planning time or execution time.

#### Production angle

In production, inspect plans to verify that only relevant partitions are scanned. If all partitions are scanned, the partitioning may not match the query pattern.

Poor pruning is a common reason partitioned tables disappoint.

#### Traps / caveats

- Partitioning helps only when pruning actually works.
- Wrapping partition keys in functions can block pruning.
- Queries without partition-key filters may scan many partitions.
- Too many partitions can increase planning overhead.

#### Optional Anki

Q: What is partition pruning?
A: Skipping partitions that cannot match the query predicates.

</details>

<a id="db-scale-005"></a>

<details>
<summary><strong>DB-SCALE-005. When does partitioning improve query performance?</strong></summary>

#### Short answer

Partitioning improves performance when queries can prune most partitions or when maintenance operations become cheaper.

#### Interview answer

The best case is a large table with clear partition-key filters. For example, querying one month in a table partitioned by month can scan one partition instead of many years of data.

Partitioning can also help with bulk deletion, archiving, index maintenance, and vacuum pressure by isolating data into smaller physical units.

#### Deep dive

Performance benefit depends on pruning, partition-local indexes, partition count, and data distribution. Partitioning often improves predictable range queries but does not help arbitrary filters.

Partitioning can also reduce index height and index bloat per partition.

#### Production angle

Good use cases: time-series events, audit logs, large append-only tables, tenant or region separation with natural filters.

Measure with `EXPLAIN (ANALYZE, BUFFERS)`; do not assume partitioning is a free optimization.

#### Traps / caveats

- Partitioning helps fewer queries than people expect.
- If queries do not filter by partition key, benefit may be small.
- Local indexes still need to be designed.
- Partitioning can increase operational complexity.

#### Optional Anki

Q: When does partitioning improve query performance?
A: When predicates allow pruning most partitions or maintenance benefits dominate.

</details>

<a id="db-scale-006"></a>

<details>
<summary><strong>DB-SCALE-006. When can partitioning make performance worse?</strong></summary>

#### Short answer

Partitioning can hurt when pruning does not work, there are too many partitions, or queries need to touch most partitions.

#### Interview answer

Each partition is a separate relation with its own metadata and often its own indexes. Queries touching many partitions can have more planning and execution overhead.

If partitions are too small or too numerous, the overhead may exceed the benefit.

#### Deep dive

Bad partition keys cause poor pruning. Generic queries, global reports, and cross-partition aggregations can become more expensive.

Also, schema changes, constraint management, index creation, and permissions may become more complex.

#### Production angle

Use benchmarks with representative data. Watch planning time, number of scanned partitions, and operational cost.

Partitioning should solve a specific problem: retention, pruning, maintenance, or scale boundary.

#### Traps / caveats

- Do not partition small tables just because the feature exists.
- Too many partitions can be a problem.
- Wrong partition key is expensive to change.
- Global uniqueness and foreign keys may have limitations.

#### Optional Anki

Q: When can partitioning hurt?
A: When queries touch many partitions or pruning does not match query patterns.

</details>

<a id="db-scale-009"></a>

<details>
<summary><strong>DB-SCALE-009. Why is partitioning useful for time-series or audit tables?</strong></summary>

#### Short answer

Time-series and audit data naturally grows by time, is often queried by time range, and often has retention rules.

#### Interview answer

Range partitioning by day, week, or month lets PostgreSQL prune irrelevant time periods and lets operations teams drop or archive old partitions efficiently.

This matches event tables, logs, audit trails, metrics, and immutable history.

#### Deep dive

Without partitioning, deleting old data creates many dead tuples that require VACUUM. With partitioning, old data can often be removed by detaching or dropping a partition.

Indexes per partition are smaller, and maintenance can be targeted.

#### Production angle

Choose partition size based on query patterns and operations, not just calendar convenience. For example, daily partitions may be too many for moderate data, while yearly partitions may be too large.

Automate future partition creation and old partition cleanup.

#### Traps / caveats

- Time partitioning only helps if queries filter by time.
- Late-arriving data needs a plan.
- Retention by partition drop is fast but irreversible unless archived.
- Too many small partitions create overhead.

#### Optional Anki

Q: Why is partitioning useful for time-series data?
A: Because queries and retention usually follow time ranges, enabling pruning and fast old-data removal.

</details>

<a id="db-scale-010"></a>

<details>
<summary><strong>DB-SCALE-010. How would you delete old data from a huge table efficiently?</strong></summary>

#### Short answer

Prefer partition drop/detach for partitioned tables; otherwise delete in small batches and monitor vacuum, locks and replication lag.

#### Interview answer

A huge single `DELETE` can create massive dead tuples, generate lots of WAL, hold locks for a long time, and stress autovacuum.

If the table is time-partitioned, dropping or detaching an old partition is usually much cheaper because it removes a whole physical table.

#### Deep dive

For non-partitioned tables, use batched deletes with a stable key, commit between batches, rate-limit the job, and run during low traffic. Then monitor bloat and vacuum progress.

Sometimes creating a new table with only retained data and swapping can be better, but it is operationally more complex.

#### Production angle

In production, consider foreign keys, cascading deletes, triggers, replication, backups, and application expectations.

Always test the deletion plan on staging with realistic data volume.

#### Traps / caveats

- Huge DELETE is not free in MVCC systems.
- DELETE does not immediately shrink table files.
- Partition drop is fast but requires partitioning design in advance.
- Cascading deletes can explode unexpectedly.

#### Optional Anki

Q: Efficient way to remove old time-based data?
A: Drop or detach old partitions; otherwise batch deletes and monitor vacuum/locks.

</details>

<a id="db-scale-011"></a>

<details>
<summary><strong>DB-SCALE-011. What is sharding?</strong></summary>

#### Short answer

Sharding is splitting data across multiple database nodes, usually by a shard key, so each node stores only part of the data.

#### Interview answer

The goal is to scale beyond one database instance for storage, write throughput, tenant isolation, or geographic distribution.

The application or a routing layer determines which shard holds a given row.

#### Deep dive

Common shard keys are tenant id, user id, account id, or region. The shard key should distribute load and align with common queries.

Sharding is a distributed systems decision, not just a database feature.

#### Production angle

In production, sharding affects every layer: data access, migrations, monitoring, backups, rebalancing, analytics, and incident response.

Introduce it only when the benefits justify the complexity.

#### Traps / caveats

- Cross-shard joins are hard.
- Cross-shard transactions are expensive or avoided.
- Resharding can be painful.
- Hot shards can still happen with a bad key.

#### Optional Anki

Q: What is sharding?
A: Splitting data across multiple database nodes by a shard key.

</details>

<a id="db-scale-012"></a>

<details>
<summary><strong>DB-SCALE-012. What are common sharding keys?</strong></summary>

#### Short answer

Common sharding keys are tenant_id, user_id, account_id, customer_id, organization_id, region, or another high-level ownership key.

#### Interview answer

A good shard key distributes data and traffic evenly, appears in most queries, and keeps related data together.

For SaaS systems, tenant_id is common. For consumer systems, user_id or account_id may be common. For geo systems, region may be used.

#### Deep dive

The key is not only about cardinality. It is about access patterns, hot keys, growth, rebalancing, and transactional boundaries.

Sometimes compound keys or directory-based routing are used.

#### Production angle

Choose a key early but validate it with expected scale and query behavior. Changing the shard key later can require large data movement and application changes.

Make sure operational tools can locate data by shard key.

#### Traps / caveats

- High cardinality alone is not enough.
- A celebrity user or huge tenant can create a hot shard.
- Region-based sharding can cause uneven load.
- Queries without shard key may fan out to all shards.

#### Optional Anki

Q: What makes a good shard key?
A: It distributes load, appears in common queries, and keeps related data together.

</details>

<a id="db-scale-013"></a>

<details>
<summary><strong>DB-SCALE-013. What are the risks of bad shard key selection?</strong></summary>

#### Short answer

Bad shard keys cause hot shards, fan-out queries, difficult transactions, expensive resharding and uneven growth.

#### Interview answer

If the key is not present in common queries, the system must query many shards. If one key receives too much traffic, one shard becomes overloaded while others are idle.

If data related to one workflow is spread across shards, transactions and joins become difficult.

#### Deep dive

Bad keys also hurt operations: backups, restores, tenant moves, analytics, and incident debugging.

Resharding often means dual writes, data copy, consistency validation, and routing changes.

#### Production angle

In production, simulate load distribution and growth. Think about the largest tenants/users, not only average behavior.

Plan escape hatches such as tenant split, directory routing, or moving hot tenants to dedicated shards.

#### Traps / caveats

- Average distribution can hide hot keys.
- Changing shard key later is expensive.
- Fan-out queries can destroy latency.
- Cross-shard consistency is harder than local consistency.

#### Optional Anki

Q: Main risk of a bad shard key?
A: Hot shards and queries that must fan out across many shards.

</details>

<a id="db-scale-015"></a>

<details>
<summary><strong>🧠 DB-SCALE-015. What are the trade-offs between vertical scaling, read replicas, partitioning and sharding?</strong></summary>

#### Short answer

Vertical scaling is simplest but finite; read replicas scale reads; partitioning helps large-table pruning/maintenance; sharding scales writes/storage but is most complex.

#### Interview answer

Vertical scaling means bigger hardware. It is operationally simple but eventually hits cost or physical limits.

Read replicas offload reads but introduce replication lag and do not scale writes.

Partitioning improves large-table management and pruning inside one cluster.

Sharding distributes data across nodes but introduces distributed-systems complexity.

#### Deep dive

A senior answer should choose the least complex option that solves the actual bottleneck. If the bottleneck is CPU for reads, replicas may help. If it is old-data cleanup, partitioning may help. If writes and storage exceed one primary, sharding may be needed.

Each option affects consistency, operations, failure modes and cost differently.

#### Production angle

Use metrics before picking a scaling strategy: CPU, IO, locks, buffer hit ratio, query plans, connection pool, and write throughput.

Do not jump to sharding before optimizing schema, queries, indexes, and operational practices.

#### Traps / caveats

- Read replicas can return stale data.
- Partitioning is not horizontal write scaling.
- Vertical scaling can hide inefficient queries temporarily.
- Sharding has the highest long-term complexity.

#### Optional Anki

Q: Order scaling options by complexity.
A: Vertical scaling/read replicas/partitioning are usually simpler; sharding is usually the most complex.

</details>
