# Indexes: basics, B-tree, cardinality and selectivity

---

<a id="db-idx-001"></a>

<details>
<summary><strong>DB-IDX-001. What are indexes used for?</strong></summary>

#### Short answer

Indexes are auxiliary data structures that help PostgreSQL find rows faster than reading the whole table. They are mainly used to speed up selective filters, joins, ordering, uniqueness checks, and some access patterns like pagination.

#### Interview answer

An index is similar to an ordered lookup structure. Instead of scanning every row, PostgreSQL can search the index, find matching index entries, and then fetch the corresponding table rows.

For a backend developer, the important point is that an index is not “just performance magic”. It must match real queries: `WHERE` predicates, join columns, `ORDER BY`, uniqueness constraints, and data distribution.

#### Deep dive

PostgreSQL stores table data in the heap and stores indexes separately. A typical B-tree index contains sorted keys and references to heap tuples. For a query like:

```sql
SELECT *
FROM users
WHERE email = 'alice@example.com';
```

an index on `email` can let PostgreSQL locate the matching key quickly instead of scanning all users.

#### Production angle

In production, indexes should be added based on measured query patterns, not by guessing. Use `EXPLAIN` / `EXPLAIN ANALYZE`, check selectivity, table size, write rate, and existing indexes.

Indexes also cost disk space and slow down writes, because PostgreSQL must maintain them on `INSERT`, `UPDATE`, and `DELETE`.

#### Traps / caveats

- An index does not guarantee that PostgreSQL will use it.
- Predicates that match a large fraction of the table may still be faster with a sequential scan.
- Too many indexes can hurt write performance and increase maintenance cost.
- Indexes should be designed for concrete queries, not for every column.
- A missing index and a wrong index are both common production problems.

#### Optional Anki

Q: What is the main purpose of an index?
A: To find matching rows faster by using an auxiliary data structure instead of scanning the whole table.

Q: Are indexes free?
A: No. They cost disk space and add write/maintenance overhead.

</details>

<a id="db-idx-002"></a>

<details>
<summary><strong>DB-IDX-002. How does an index lookup differ from a sequential table scan?</strong></summary>

#### Short answer

A sequential scan reads table pages one by one and checks rows. An index lookup first searches an index and then reads only the table rows that match the index entries.

#### Interview answer

A sequential scan is simple: PostgreSQL walks through the table and evaluates the filter for each row. It is often good when the table is small or the query returns a large part of it.

An index lookup is more targeted: PostgreSQL uses the index to find candidate row locations. It is usually good when the predicate is selective and returns a small fraction of rows.

#### Deep dive

In PostgreSQL, a normal index scan usually needs two structures:

- the index, where matching keys are found;
- the heap, where the actual table rows are checked and returned.

This means an index scan can involve random heap reads. For many matching rows, that can be more expensive than reading the table sequentially.

#### Production angle

When debugging performance, do not assume “index scan is always better”. Compare plans with `EXPLAIN ANALYZE`, look at actual rows, buffers, and whether the query reads a large percentage of the table.

#### Traps / caveats

- Sequential scan is not automatically bad.
- Index scan is not automatically good.
- Index lookup may cause many random heap reads.
- Index-only scan is a special case and requires all needed columns plus visibility information.

#### Optional Anki

Q: When can a sequential scan be better than an index scan?
A: When the query reads a large fraction of the table or the table is small.

</details>

<a id="db-idx-003"></a>

<details>
<summary><strong>DB-IDX-003. How does a B-tree index work?</strong></summary>

#### Short answer

A B-tree index keeps keys sorted in a balanced tree. PostgreSQL can navigate from the root page through internal pages to leaf pages and find matching keys efficiently.

#### Interview answer

B-tree is the default PostgreSQL index type and fits the most common cases: equality, range queries, sorting, uniqueness, and prefix-like access patterns.

Conceptually, PostgreSQL searches the tree by comparing the query value with separator keys until it reaches the leaf page containing matching index entries.

#### Deep dive

A B-tree is balanced, so all leaf pages are at the same depth. This keeps lookup cost predictable even as the table grows.

For an equality predicate:

```sql
WHERE email = 'alice@example.com'
```

PostgreSQL descends to the leaf page for that key and reads matching entries. For a range predicate:

```sql
WHERE created_at >= now() - interval '1 day'
```

it finds the lower bound and scans forward through leaf entries until the range ends.

#### Production angle

In production, B-tree indexes are the first choice for common OLTP filters and joins. But they are not ideal for every use case: full-text search, JSONB containment, arrays, geospatial search, or huge naturally ordered time-series data may need other index types.

#### Traps / caveats

- B-tree is great for equality, ranges, ordering, and uniqueness, but not for every predicate.
- It stores sorted keys, not full table rows.
- PostgreSQL indexes are secondary structures separate from the heap.
- A B-tree index can still be ignored if the predicate is not selective enough.

#### Optional Anki

Q: What is the default index type in PostgreSQL?
A: B-tree.

Q: What query patterns are B-tree indexes good for?
A: Equality, ranges, ordering, uniqueness, and common join/filter predicates.

</details>

<a id="db-idx-008"></a>

<details>
<summary><strong>DB-IDX-008. How can a B-tree index help with ORDER BY?</strong></summary>

#### Short answer

A B-tree index can return rows in index order, so PostgreSQL may avoid a separate sort step for compatible `ORDER BY` clauses, especially with `LIMIT`.

#### Interview answer

Because B-tree stores keys in sorted order, it can satisfy ordering requirements. For example:

```sql
CREATE INDEX idx_orders_created_at ON orders (created_at DESC);

SELECT *
FROM orders
ORDER BY created_at DESC
LIMIT 50;
```

The planner may scan the index in order and stop after 50 rows.

A single-column B-tree can usually be scanned forward or backward. For composite indexes, mixed ordering matters: an index on `(tenant_id, created_at DESC)` is not the same ordering as `(tenant_id, created_at ASC)` for every query shape.

#### Deep dive

Ordering is most powerful when combined with filtering and `LIMIT`. A composite index can support both filtering and ordering if column order matches the query pattern:

```sql
CREATE INDEX idx_orders_tenant_status_created
ON orders (tenant_id, status, created_at DESC);
```

This can help:

```sql
WHERE tenant_id = ?
  AND status = ?
ORDER BY created_at DESC
LIMIT 50;
```

For exact ordering compatibility, pay attention to column order, direction, and `NULLS FIRST` / `NULLS LAST`.

#### Production angle

For API pagination, a matching index can prevent expensive sorts and make keyset pagination efficient. This is often more important than only optimizing a single equality lookup.

#### Traps / caveats

- The index order must be compatible with `ORDER BY`.
- Composite index order matters.
- Mixed `ASC`/`DESC` order in composite indexes may require an index defined with that exact direction.
- `NULLS FIRST` / `NULLS LAST` can affect whether the index order matches the query.
- If the query filters too broadly, an ordered index scan may still read many rows.
- Sorting small result sets in memory may be cheaper than using an index.

#### Optional Anki

Q: How can an index help `ORDER BY ... LIMIT`?
A: PostgreSQL can scan the B-tree in order and stop after enough rows.

</details>

<a id="db-idx-009"></a>

<details>
<summary><strong>DB-IDX-009. What is a composite index?</strong></summary>

#### Short answer

A composite index is an index built on multiple columns, for example `(tenant_id, status, created_at)`.

#### Interview answer

Composite indexes are useful when queries usually filter or order by the same combination of columns. They are not the same as several separate single-column indexes.

```sql
CREATE INDEX idx_orders_tenant_status_created
ON orders (tenant_id, status, created_at DESC);
```

#### Deep dive

In a B-tree composite index, keys are ordered lexicographically: first by the first column, then by the second column inside equal first-column values, and so on.

This makes column order very important. An index on `(tenant_id, created_at)` and an index on `(created_at, tenant_id)` serve different query patterns.

#### Production angle

Composite indexes are common for multi-tenant applications, status dashboards, search screens, and pagination. They should be designed from real queries, not by simply grouping columns that “seem related”.

#### Traps / caveats

- A composite index is not always a replacement for all single-column indexes.
- Column order matters for filtering and ordering.
- Too-wide composite indexes increase write and storage overhead.
- Do not create every possible column combination.

#### Optional Anki

Q: Is `(a, b)` the same as two indexes on `a` and `b`?
A: No. A composite index stores combined ordered keys and supports combined access patterns.

</details>

<a id="db-idx-011"></a>

<details>
<summary><strong>DB-IDX-011. Why does column order matter in a composite index?</strong></summary>

#### Short answer

Column order defines how the composite key is sorted, which affects filtering, range scans, ordering, and how much of the index PostgreSQL must scan.

#### Interview answer

For `(tenant_id, created_at)`, all rows of one tenant are grouped together and ordered by time inside that tenant. For `(created_at, tenant_id)`, rows are primarily grouped by time, not tenant.

These indexes answer different questions efficiently.

#### Deep dive

Column order matters for:

- leading equality predicates;
- first range predicate;
- `ORDER BY` compatibility;
- index reuse across multiple queries;
- join conditions and pagination.

#### Production angle

If a Java endpoint always queries orders by tenant and then by time, `(tenant_id, created_at)` is often a better index than `(created_at, tenant_id)`, even if `created_at` has high cardinality.

#### Traps / caveats

- Do not choose column order only by cardinality.
- Do not blindly put `tenant_id` first in every index; check query patterns.
- Changing column order creates a different index.

#### Optional Anki

Q: Why does column order matter?
A: It defines how keys are sorted and which predicates can efficiently narrow the index scan.

</details>

<a id="db-idx-012"></a>

<details>
<summary><strong>DB-IDX-012. What is the leftmost prefix rule?</strong></summary>

#### Short answer

The leftmost prefix rule is the idea that a composite B-tree index is most effective when query conditions use the leading columns of the index.

#### Interview answer

For an index on `(a, b, c)`, queries filtering by `a`, or by `a` and `b`, are usually a good fit. A query filtering only by `c` is usually much weaker.

```sql
-- good
WHERE a = ?

-- good
WHERE a = ? AND b = ?

-- usually weak
WHERE c = ?
```

#### Deep dive

In PostgreSQL, this is not an absolute “cannot use later columns” rule. PostgreSQL can sometimes use a multicolumn index even if leading columns are missing, especially with skip scan or filtering. But the index is most efficient when leading columns are constrained.

#### Production angle

This nuance matters in production reviews. A developer may say “we have index `(a,b,c)`, so query by `c` is covered”. A senior answer should be: technically possible in some cases, but likely not efficient; check `EXPLAIN ANALYZE`.

#### Traps / caveats

- It is a rule of thumb, not a complete PostgreSQL planner specification.
- Skip scan can make some non-leftmost cases usable.
- Efficiency still depends on selectivity, statistics, table size, and cost estimates.

#### Optional Anki

Q: What is the leftmost prefix rule?
A: A composite B-tree index is usually most efficient when predicates constrain its leading columns.

</details>

<a id="db-idx-013"></a>

<details>
<summary><strong>DB-IDX-013. Should the most selective column always go first in a composite index?</strong></summary>

#### Short answer

No. Selectivity matters, but column order should primarily follow query patterns: equality predicates, range predicates, ordering, joins, and pagination.

#### Interview answer

A common oversimplification is “put the most selective column first”. That can be wrong for composite B-tree indexes.

For example, if every query is tenant-scoped:

```sql
WHERE tenant_id = ?
  AND created_at >= ?
ORDER BY created_at DESC
```

`(tenant_id, created_at DESC)` may be better than `(created_at, tenant_id)`, even if `created_at` has more distinct values.

#### Deep dive

A better rule of thumb:

- put columns used by mandatory equality predicates first;
- then the first range predicate;
- then columns needed for ordering or covering;
- validate with real queries and `EXPLAIN ANALYZE`.

If all leading columns are equality predicates, their internal order can be less important for narrowing the scan, but it still affects index reuse, ordering, and compression/locality.

#### Production angle

During index design, ask: which endpoint uses this index, which filters are always present, which filters are optional, what is the sort order, and how many rows are returned?

#### Traps / caveats

- “Most selective first” is incomplete advice.
- Query pattern matters more than isolated column statistics.
- Range predicates change how later columns can be used.
- Optional filters make one perfect composite index harder.

#### Optional Anki

Q: Should the most selective column always be first?
A: No. Use equality/range/order/query-pattern rules and validate with plans.

</details>

<a id="db-idx-015"></a>

<details>
<summary><strong>DB-IDX-015. How do equality predicates and range predicates affect composite index design?</strong></summary>

#### Short answer

Equality predicates on leading columns narrow the index scan strongly. The first range predicate usually defines the scanned range, and later columns often become less useful for narrowing.

#### Interview answer

For an index on `(tenant_id, status, created_at, id)`:

```sql
WHERE tenant_id = ?
  AND status = ?
  AND created_at >= ?
```

`tenant_id` and `status` are equality predicates. They define a narrow prefix. `created_at` is the range predicate. It defines the interval inside that prefix.

#### Deep dive

Columns after the first range predicate can still help with ordering, index-only scans, or additional filtering, but they often cannot reduce the scanned range as efficiently as earlier equality columns.

This is why an index like `(tenant_id, status, created_at)` is often better than `(created_at, tenant_id, status)` for tenant-scoped time queries.

#### Production angle

This distinction matters for API filters like “orders for tenant by status in a date range”. A wrong column order can cause PostgreSQL to scan a much larger part of the index than expected.

#### Traps / caveats

- Equality predicates are usually best before range predicates.
- Multiple range predicates are harder to optimize with one B-tree index.
- Additional columns after a range can still be useful, but understand why.

#### Optional Anki

Q: Which usually comes first in a composite B-tree index: equality or range columns?
A: Equality columns usually come first, then the first range column.

</details>

<a id="db-idx-016"></a>

<details>
<summary><strong>DB-IDX-016. When should you create an index?</strong></summary>

#### Short answer

Create an index when it supports an important query pattern, constraint, join, ordering, or pagination flow and the expected read benefit is higher than the write and storage cost.

#### Interview answer

Good candidates include:

- frequent selective `WHERE` predicates;
- foreign keys used in joins and parent-child lookups;
- columns used for `ORDER BY ... LIMIT`;
- unique business identifiers;
- partial subsets frequently queried by the application.

#### Deep dive

Index design should start from the query, not from the table schema. A column being “important” does not automatically mean it needs an index.

Use `EXPLAIN ANALYZE` on representative data and check whether the index reduces actual work: scanned rows, buffers, sort cost, and execution time.

#### Production angle

In production, consider write rate, table size, index build strategy, and operational risk. On large tables, creating an index may require `CREATE INDEX CONCURRENTLY` and a rollback plan.

#### Traps / caveats

- Do not add indexes just because a column appears in a query.
- Do not add duplicate indexes that serve the same pattern.
- Do not forget write overhead.
- Check whether an existing composite index already covers the query.

#### Optional Anki

Q: What should index creation start from?
A: A real query pattern and its execution plan.

</details>

<a id="db-idx-017"></a>

<details>
<summary><strong>DB-IDX-017. What are the downsides of indexes?</strong></summary>

#### Short answer

Indexes speed up some reads but cost disk space, slow down writes, increase WAL/maintenance work, and can become bloated or redundant.

#### Interview answer

Every index is another structure PostgreSQL must maintain. On insert, PostgreSQL usually adds entries to every relevant index. On update, indexes may need changes if indexed columns change. On delete, index entries become obsolete and later need cleanup.

#### Deep dive

Downsides include:

- disk usage;
- write amplification;
- more WAL generation;
- slower bulk loads;
- index bloat;
- longer vacuum/reindex/backup time;
- more complex planning choices.

#### Production angle

For high-write services, indexes should be treated as part of the write path. Removing unused or redundant indexes can noticeably improve write performance and storage usage.

#### Traps / caveats

- “More indexes” is not automatically better.
- Unused indexes still cost writes.
- Wide indexes may hurt cache efficiency.
- Indexes can hide bad query design temporarily.

#### Optional Anki

Q: What is the biggest trade-off of indexes?
A: Faster reads for some queries in exchange for more storage and write overhead.

</details>

<a id="db-idx-018"></a>

<details>
<summary><strong>DB-IDX-018. How do indexes affect INSERT, UPDATE and DELETE performance?</strong></summary>

#### Short answer

Indexes make writes more expensive because PostgreSQL must keep index entries consistent with table rows.

#### Interview answer

On `INSERT`, PostgreSQL adds a new heap tuple and creates entries in relevant indexes. On `UPDATE`, PostgreSQL creates a new row version; if indexed values change, related index entries must be updated. On `DELETE`, row versions become dead and index cleanup happens later through vacuum-related maintenance.

#### Deep dive

PostgreSQL has HOT updates: if no indexed column changes and there is enough room on the heap page, PostgreSQL may avoid creating new index entries for the update. This is one reason unnecessary indexes can reduce the chance of efficient updates.

#### Production angle

In production, write-heavy tables with many indexes can show high CPU, WAL volume, replication lag, and storage growth. Index count should be reviewed when optimizing write throughput.

#### Traps / caveats

- Index overhead is paid even if the index is rarely used for reads.
- Updating indexed columns is usually more expensive than updating non-indexed columns.
- Deletes do not immediately remove all physical index/table garbage.
- Bulk imports may be faster when indexes are created after loading, depending on constraints and operational needs.

#### Optional Anki

Q: Why can extra indexes slow down writes?
A: Each write must maintain additional index structures.

</details>

<a id="db-idx-021"></a>

<details>
<summary><strong>DB-IDX-021. What is the difference between cardinality and selectivity?</strong></summary>

#### Short answer

Cardinality is the number of distinct values. Selectivity is the fraction of rows returned by a specific predicate.

#### Interview answer

Cardinality describes data shape. Selectivity describes query filtering power.

For example, `status` may have low cardinality because it has only 5 possible values. But `WHERE status = 'FAILED'` can still be very selective, meaning a low selectivity value, if failed orders are rare.

#### Deep dive

High cardinality often helps index usefulness, but it is not enough. Data skew matters. A column can have many distinct values, while one value still dominates a large part of the table.

The planner estimates selectivity from statistics and uses that estimate to choose between scan methods.

#### Production angle

When discussing indexes in production, use selectivity language: “How many rows does this predicate return?” rather than only “How many distinct values does this column have?”

#### Traps / caveats

- Do not use cardinality and selectivity as synonyms.
- High cardinality does not guarantee index usage.
- Low cardinality does not automatically mean an index is useless.
- Planner estimates can be wrong if statistics are stale or data is skewed.

#### Optional Anki

Q: Cardinality vs selectivity?
A: Cardinality = distinct values; selectivity = fraction of rows matched by a predicate.

</details>

<a id="db-idx-022"></a>

<details>
<summary><strong>DB-IDX-022. How does selectivity affect index usage?</strong></summary>

#### Short answer

A predicate that matches a small fraction of rows usually makes indexes more useful. A predicate that matches a large fraction of the table often makes sequential scan cheaper.

#### Interview answer

PostgreSQL compares estimated costs. If an index predicate returns 10 rows out of 10 million, an index is likely useful. If it returns 8 million rows, reading through the index plus heap visits may cost more than a sequential scan.

#### Deep dive

The cost depends on:

- estimated rows;
- heap page access pattern;
- table/index size;
- cache effects;
- correlation between index order and heap order;
- random vs sequential I/O cost settings;
- whether index-only scan is possible.

#### Production angle

For slow-query debugging, ask: “How many rows did PostgreSQL expect, how many did it actually read, and why?” This connects selectivity with `EXPLAIN ANALYZE` and planner statistics.

#### Traps / caveats

- A small matching fraction helps but does not guarantee an index scan.
- Broad predicates can still work with partial or composite indexes when the indexed subset or access path is small.
- Bad selectivity estimates often cause bad plans.

#### Optional Anki

Q: Why can PostgreSQL skip an index on a broad predicate?
A: Because reading much of the table through the index and heap can be more expensive than a sequential scan.

</details>

<a id="db-idx-023"></a>

<details>
<summary><strong>DB-IDX-023. Why can PostgreSQL ignore an existing index?</strong></summary>

#### Short answer

PostgreSQL can ignore an index when the planner estimates that another plan is cheaper, such as a sequential scan, bitmap scan, different index, or join strategy.

#### Interview answer

Common reasons:

- predicate is not selective enough;
- table is small;
- statistics are stale or inaccurate;
- query uses a function/cast not matching the index;
- composite index leading columns are not constrained;
- collation/operator class does not match;
- index scan would require too many random heap fetches;
- prepared statement generic plan is not good for this parameter value.

#### Deep dive

Example:

```sql
CREATE INDEX idx_users_email ON users (email);

-- may not use idx_users_email
SELECT *
FROM users
WHERE lower(email) = 'alice@example.com';
```

This query needs an expression index on `lower(email)` or a different design such as normalized email storage.

#### Production angle

In production, do not force index usage blindly. First inspect `EXPLAIN ANALYZE`, compare estimated vs actual rows, check statistics, check query predicates, and validate that the index actually matches the query.

#### Traps / caveats

- An unused index may be the correct planner choice.
- Bad statistics can make the planner choose poorly.
- Expression mismatch is a common reason indexes are ignored.
- Different parameter values can need different plans.

#### Optional Anki

Q: Name one reason PostgreSQL ignores an index.
A: The predicate is estimated to return too many rows, so a sequential scan is cheaper.

</details>

<a id="db-idx-024"></a>

<details>
<summary><strong>DB-IDX-024. When can a sequential scan be faster than an index scan?</strong></summary>

#### Short answer

A sequential scan can be faster when the query reads a large part of the table, the table is small, or index access would cause many random heap reads.

#### Interview answer

Index scans are targeted, but they can be expensive if they repeatedly jump from index entries to scattered heap pages. Sequential scans read table pages in order and can be very efficient for broad scans.

Example:

```sql
WHERE status = 'ACTIVE'
```

If almost every row is active, the index may not help.

#### Deep dive

The planner considers row estimates, I/O costs, page counts, correlation, and possible parallelism. A sequential scan is not a “failure”; it is often the optimal plan for queries that return a large fraction of the table.

#### Production angle

During slow-query analysis, a sequential scan is suspicious only if the query should be selective and the planner estimate is wrong, or if there is no suitable index for an important predicate.

#### Traps / caveats

- Do not treat every sequential scan as a bug.
- Small tables often do not need indexes for every query.
- Low correlation can make index scans expensive.
- Parallel sequential scan can be very effective for analytical-style queries.

#### Optional Anki

Q: Is a sequential scan always bad?
A: No. It can be optimal for small tables or queries returning a large fraction of rows.

</details>

<a id="db-idx-026"></a>

<details>
<summary><strong>🧠 DB-IDX-026. Why can an index on a boolean column be useless?</strong></summary>

#### Short answer

A boolean column has only two values, so a plain index may be useless if each value matches a large part of the table.

#### Interview answer

For example, if 95% of rows have `is_active = true`, this query may not benefit from a simple B-tree index on `is_active`:

```sql
WHERE is_active = true
```

PostgreSQL may prefer a sequential scan because the query returns most rows.

#### Deep dive

But a boolean column can still be useful in:

- a partial index for the rare value;
- a composite index with tenant/date/status;
- a query that also needs ordering and `LIMIT`.

#### Production angle

A common soft-delete pattern is better served by a partial index on active rows than by a simple boolean index:

```sql
CREATE INDEX idx_users_active_email
ON users (email)
WHERE deleted_at IS NULL;
```

#### Traps / caveats

- Boolean column does not automatically mean “never index it”.
- Index usefulness depends on predicate selectivity.
- Partial and composite indexes are often better than a plain boolean index.

#### Optional Anki

Q: Why can an index on boolean be bad?
A: Because each value may match too many rows, making sequential scan cheaper.

</details>

<a id="db-idx-027"></a>

<details>
<summary><strong>🧠 DB-IDX-027. How can a partial index help with low-selectivity predicates?</strong></summary>

#### Short answer

A partial index indexes only rows that satisfy a predicate, so it can make a rare or important subset small and efficient to search.

#### Interview answer

If most rows are `ACTIVE`, a full index on `status` may not help. But if failed rows are rare and frequently queried, a partial index can focus only on them:

```sql
CREATE INDEX idx_orders_failed_created
ON orders (created_at)
WHERE status = 'FAILED';
```

#### Deep dive

For PostgreSQL to use a partial index, the query condition must imply the partial index predicate. PostgreSQL does not do arbitrary theorem proving, so the predicate should be written in a way the planner can recognize.

#### Production angle

Partial indexes are excellent for soft deletes, rare states, unprocessed jobs, unpaid invoices, and queue-like tables:

```sql
CREATE INDEX idx_jobs_pending_created
ON jobs (created_at)
WHERE status = 'PENDING';
```

#### Traps / caveats

- The query must match or imply the partial predicate.
- Parameterized queries can make predicate implication harder for the planner.
- Partial indexes are bad if the predicate subset grows too large.
- Do not create many partial indexes for every possible status.

#### Optional Anki

Q: What is the key requirement for using a partial index?
A: The query condition must imply the index predicate.

</details>

<a id="db-idx-028"></a>

<details>
<summary><strong>🧠 DB-IDX-028. What is data skew, and how can it affect index usage?</strong></summary>

#### Short answer

Data skew means values are distributed unevenly. It can make some predicates return very few rows and others return many rows on the same column.

#### Interview answer

Example: a `user_id` column has millions of distinct users, but one “system user” owns 40% of all rows. The column has high cardinality, but `WHERE user_id = system_user` matches too many rows for a simple index lookup to be attractive.

#### Deep dive

PostgreSQL planner statistics include most common values and frequencies. These help the planner distinguish common values from rare values. But if statistics are stale or the query uses a generic prepared plan, estimates may be wrong.

#### Production angle

In production, data skew often explains why a query is fast for one customer and slow for another. Senior debugging should include checking parameter values, actual rows, and whether the plan changes between values.

#### Traps / caveats

- Average selectivity can be misleading.
- High cardinality does not remove skew risk.
- Generic plans can be bad when different parameter values need different plans.
- Extended statistics may help for correlated columns.

#### Optional Anki

Q: What is data skew?
A: Uneven distribution of values, where some values are much more common than others.

</details>

<a id="db-idx-029"></a>

<details>
<summary><strong>🧠 DB-IDX-029. What is an index-only scan?</strong></summary>

#### Short answer

An index-only scan is a scan where PostgreSQL can return the required columns using the index without fetching every matching row from the heap.

#### Interview answer

A normal index scan finds matching index entries and then visits the heap to get row data and check visibility. An index-only scan can avoid heap visits when:

- the index contains all columns needed by the query;
- the index type supports index-only scans;
- the visibility map says the heap page is all-visible.

#### Deep dive

Example:

```sql
CREATE INDEX idx_users_email_id
ON users (email) INCLUDE (id);

SELECT id
FROM users
WHERE email = 'alice@example.com';
```

The index has `email` for searching and `id` as payload. If visibility conditions are satisfied, PostgreSQL can answer mostly from the index.

#### Production angle

Index-only scans are very useful for read-heavy tables with stable data, reporting queries, and pagination endpoints. They are less likely on heavily updated tables because visibility map bits may be cleared by recent writes.

#### Traps / caveats

- “All columns are in the index” is necessary but not sufficient.
- MVCC visibility is the reason heap access may still be needed.
- Vacuum helps maintain visibility map information.
- Index-only scans can be worse if the index becomes too large.

#### Optional Anki

Q: What two things are needed for an index-only scan?
A: The index must contain all needed columns, and heap pages must be known all-visible through the visibility map.

</details>

<a id="db-idx-035"></a>

<details>
<summary><strong>DB-IDX-035. What is a partial index?</strong></summary>

#### Short answer

A partial index is an index built only for rows that satisfy a `WHERE` predicate.

#### Interview answer

Example:

```sql
CREATE INDEX idx_orders_unpaid
ON orders (created_at)
WHERE paid_at IS NULL;
```

The index contains only unpaid orders. Queries for unpaid orders can use a smaller, more focused index.

#### Deep dive

Partial indexes are useful when only a subset of rows is commonly queried, especially if that subset is much smaller than the whole table.

The query predicate must imply the index predicate. If PostgreSQL cannot prove that the query matches the partial index condition, it may not use the index.

#### Production angle

Common production patterns:

- active rows: `WHERE deleted_at IS NULL`;
- pending jobs: `WHERE status = 'PENDING'`;
- rare error states;
- tenant-specific or type-specific subsets when justified.

#### Traps / caveats

- Partial index must match the query predicate.
- It is not useful for queries outside its subset.
- If the subset grows large, the benefit decreases.
- Do not overuse partial indexes for every possible state.

#### Optional Anki

Q: What is a partial index?
A: An index over only the rows that satisfy a specific predicate.

</details>

<a id="db-idx-036"></a>

<details>
<summary><strong>DB-IDX-036. When would you create a partial index?</strong></summary>

#### Short answer

Create a partial index when important queries repeatedly target a small, stable subset of a table.

#### Interview answer

Good cases:

- soft-deleted tables where most queries read active rows;
- job queues where workers read pending jobs;
- rare statuses like failed, unpaid, unprocessed;
- conditional uniqueness for active records.

#### Deep dive

Example conditional unique index:

```sql
CREATE UNIQUE INDEX ux_users_active_email
ON users (email)
WHERE deleted_at IS NULL;
```

This allows reusing an email after soft delete while keeping active emails unique.

#### Production angle

In production, partial indexes should be documented because application queries must include the predicate. If one team forgets `deleted_at IS NULL`, the index may not be used and the query may also return wrong data.

#### Traps / caveats

- The predicate should be stable and meaningful.
- Predicate implication must be recognizable by the planner.
- Partial indexes can surprise developers who do not know the table design.
- They can complicate migrations and uniqueness rules.

#### Optional Anki

Q: Give a common partial index use case.
A: Index only active rows with `WHERE deleted_at IS NULL`.

</details>

<a id="db-idx-038"></a>

<details>
<summary><strong>🧠 DB-IDX-038. When would you create an index on lower(email)?</strong></summary>

#### Short answer

Create an index on `lower(email)` when the application performs case-insensitive email lookup using `lower(email)` in queries.

#### Interview answer

Without an expression index, this query may not use a plain index on `email`:

```sql
SELECT *
FROM users
WHERE lower(email) = lower(?);
```

A matching index:

```sql
CREATE INDEX idx_users_lower_email
ON users (lower(email));
```

#### Deep dive

If email must be unique case-insensitively, use a unique expression index:

```sql
CREATE UNIQUE INDEX ux_users_lower_email
ON users (lower(email));
```

Another option is to store normalized email in a separate column or use a PostgreSQL type/extension appropriate for case-insensitive text, depending on project standards.

#### Production angle

In production, choose one consistent email normalization strategy. Mixing raw email, lowercased comparisons, and application-side normalization can cause duplicates or missed lookups.

#### Traps / caveats

- A plain index on `email` usually does not help `lower(email)` predicates.
- Locale/collation rules can affect text comparison.
- Case-insensitive uniqueness should be enforced in the database if it is a business invariant.
- Consider storing normalized values explicitly for clarity.

#### Optional Anki

Q: Why create `lower(email)` index?
A: To support case-insensitive lookup/uniqueness that uses `lower(email)` in predicates.

</details>

<a id="db-idx-039"></a>

<details>
<summary><strong>DB-IDX-039. What is a unique index?</strong></summary>

#### Short answer

A unique index enforces that indexed key values are unique across the table, according to PostgreSQL uniqueness rules.

#### Interview answer

Example:

```sql
CREATE UNIQUE INDEX ux_users_email
ON users (email);
```

This prevents two rows from having the same non-null `email` value.

#### Deep dive

PostgreSQL automatically creates unique indexes for primary key and unique constraints. A manually created unique index can also be partial or expression-based:

```sql
CREATE UNIQUE INDEX ux_users_active_email
ON users (email)
WHERE deleted_at IS NULL;
```

#### Production angle

Use unique indexes/constraints to protect business invariants against all writers, not only your Java application. This is essential under concurrency.

#### Traps / caveats

- Unique index behavior with `NULL` needs attention.
- PostgreSQL can support `NULLS NOT DISTINCT` for cases where nulls should be treated as equal.
- A unique index is not always the same as declaring a unique constraint semantically.
- Partial unique indexes are powerful for soft-delete scenarios.

#### Optional Anki

Q: What does a unique index do?
A: It enforces uniqueness of indexed key values.

</details>

<a id="db-idx-040"></a>

<details>
<summary><strong>DB-IDX-040. What is the difference between a unique index and a unique constraint?</strong></summary>

#### Short answer

A unique constraint is a schema-level integrity rule; PostgreSQL enforces it using a unique index. A unique index is the physical/index mechanism and can be more flexible, for example partial or expression-based.

#### Interview answer

When you write:

```sql
ALTER TABLE users
ADD CONSTRAINT users_email_key UNIQUE (email);
```

PostgreSQL creates a unique index to enforce the constraint. The constraint communicates a data model invariant.

When you write:

```sql
CREATE UNIQUE INDEX ux_users_lower_email
ON users (lower(email));
```

you create an index directly, which can enforce uniqueness on an expression.

#### Deep dive

Use a unique constraint for normal relational model invariants. Use a unique index directly when you need features not expressible as a standard constraint, such as partial uniqueness or expression-based uniqueness.

Foreign keys generally reference primary keys, unique constraints, or suitable non-partial unique indexes on referenced columns; partial/expression uniqueness is not a general replacement for relational keys.

#### Production angle

In production, constraints are easier to understand as business rules and are visible in schema modeling. Direct unique indexes are very useful for advanced patterns, but should be named and documented clearly.

#### Traps / caveats

- A unique constraint creates/uses a unique index.
- A unique index can be partial or expression-based; a standard unique constraint cannot express every such case.
- Use constraints for clear data model invariants when possible.
- Be careful with `NULL` semantics.

#### Optional Anki

Q: How does PostgreSQL enforce a unique constraint?
A: With a unique index.

Q: Why use a direct unique index?
A: For advanced cases such as partial or expression-based uniqueness.

</details>
