# Slow query and production troubleshooting

---

<a id="db-prod-001"></a>

<details>
<summary><strong>DB-PROD-001. How would you investigate a slow PostgreSQL query in production?</strong></summary>

#### Short answer

Start with the exact query and context, then inspect EXPLAIN ANALYZE, buffers, row estimates, locks, resource metrics, and application behavior.

#### Interview answer

First identify whether it is one slow query, many slow queries, or general database saturation. Capture the normalized SQL, parameters, frequency, latency percentiles, and affected endpoint.

Then run `EXPLAIN (ANALYZE, BUFFERS)` safely on representative data if possible.

#### Deep dive

Look for scan type, join algorithm, estimated vs actual rows, sort/hash spills, buffer reads, loops, rows removed by filter, and index usage.

Also check locks, connection pool wait, CPU, IO, replication lag, autovacuum, and recent schema/data/statistics changes.

#### Production angle

In production, avoid guessing. Use metrics and traces. If the immediate impact is high, mitigate first: timeout, reduce traffic, disable feature, add index concurrently, or route heavy workload away.

Then fix root cause.

#### Traps / caveats

- Slow query may be blocked, not CPU-heavy.
- Dev data often hides bad plans.
- EXPLAIN without ANALYZE can be misleading.
- Adding an index blindly can hurt writes and not fix the root cause.

#### Optional Anki

Q: First tool for slow query plan?
A: EXPLAIN (ANALYZE, BUFFERS) on representative query/data.

</details>

<a id="db-prod-002"></a>

<details>
<summary><strong>DB-PROD-002. What would you check first: query plan, locks, CPU, IO, connection pool or application code?</strong></summary>

#### Short answer

Check symptoms first to classify the bottleneck; there is no single universal first item.

#### Interview answer

If only one endpoint is slow, start with its traces and query plan. If many DB operations are slow, check DB CPU/IO/locks and connection pool. If threads wait for connections, check pool exhaustion.

Use a hypothesis-driven approach.

#### Deep dive

A slow request can be caused by a bad plan, blocked lock, saturated IO, connection wait, GC pause, remote service call inside transaction, or too many retries.

Correlate application metrics with database metrics by time.

#### Production angle

Production triage should answer: is the database overloaded, is the query blocked, is the app waiting for a connection, or is one query plan bad?

Then take targeted action.

#### Traps / caveats

- Do not tunnel vision on indexes.
- Pool wait can look like DB slowness.
- Lock waits can hide behind query latency.
- Recent deployments/data changes are clues.

#### Optional Anki

Q: Why not always start with indexes?
A: The issue may be locks, IO, pool wait, or application behavior.

</details>

<a id="db-prod-003"></a>

<details>
<summary><strong>DB-PROD-003. How do you find currently running queries?</strong></summary>

#### Short answer

Use pg_stat_activity to see active sessions, their queries, state, wait events, and timings.

#### Interview answer

A typical query selects pid, usename, application_name, state, wait_event_type, wait_event, query_start, xact_start and query.

Filter for `state = 'active'` and long-running durations.

#### Deep dive

`pg_stat_activity` shows current backend activity. It helps distinguish active CPU/IO work from waiting on locks or client activity.

Application name in JDBC URL helps identify the service.

```
SELECT pid, usename, application_name, state,
       wait_event_type, wait_event,
       now() - query_start AS query_age,
       now() - xact_start AS xact_age,
       query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY query_age DESC;
```

#### Production angle

In production, build safe dashboards and read-only diagnostic queries. Do not expose sensitive query parameters broadly.

Use `pg_cancel_backend` or `pg_terminate_backend` carefully and with runbook approval.

#### Traps / caveats

- Query text can contain sensitive data.
- A session can be idle but still in transaction.
- Killing a backend can roll back work.
- Current query may not show full application context.

#### Optional Anki

Q: Which view shows active queries?
A: pg_stat_activity.

</details>

<a id="db-prod-004"></a>

<details>
<summary><strong>DB-PROD-004. How do you find blocked queries?</strong></summary>

#### Short answer

Look for sessions waiting on locks in pg_stat_activity and join with pg_locks or use pg_blocking_pids(pid).

#### Interview answer

Blocked queries often have wait_event_type = 'Lock'. PostgreSQL provides `pg_blocking_pids(pid)` to identify blockers.

You want both the blocked query and the blocking session.

#### Deep dive

Lock wait diagnosis includes transaction start time, query start time, state, relation, lock mode, and whether the blocker is idle in transaction.

A short query can be blocked by an old forgotten transaction.

```
SELECT a.pid AS blocked_pid,
       pg_blocking_pids(a.pid) AS blocker_pids,
       now() - a.query_start AS blocked_for,
       a.wait_event_type,
       a.wait_event,
       a.query
FROM pg_stat_activity a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0;
```

#### Production angle

In production, killing blockers is risky. First understand what work will be rolled back and whether the blocker is part of critical flow.

Set lock_timeout for migrations to avoid blocking traffic.

#### Traps / caveats

- Blocked query time is not execution time.
- The blocker may be idle-in-transaction.
- Terminating wrong backend can cause user-visible errors.
- Lock queues can create cascading incidents.

#### Optional Anki

Q: How identify blockers?
A: Use pg_blocking_pids(pid) and pg_stat_activity/pg_locks.

</details>

<a id="db-prod-005"></a>

<details>
<summary><strong>DB-PROD-005. How do you find blocking transactions?</strong></summary>

#### Short answer

Use pg_blocking_pids() to map blocked sessions to blocker pids, then inspect blocker transaction state in pg_stat_activity.

#### Interview answer

Important fields are pid, state, xact_start, query_start, wait_event, application_name, client_addr and query.

Blockers are often long transactions or idle-in-transaction sessions.

#### Deep dive

A transaction can block others even if its current query is idle. Locks are held until commit/rollback.

Check how long the transaction has been open, not only how long the current statement is running.

#### Production angle

In production, contact service owner if possible, inspect app logs/traces for that connection, then decide cancel/terminate or wait.

After incident, fix transaction boundaries or add timeouts.

#### Traps / caveats

- Idle blockers are easy to miss.
- Locks persist until transaction end.
- Canceling query may not end transaction; terminating backend does.
- Root cause is often app transaction scope.

#### Optional Anki

Q: What field reveals long transaction age?
A: xact_start in pg_stat_activity.

</details>

<a id="db-prod-006"></a>

<details>
<summary><strong>DB-PROD-006. How do you detect missing indexes?</strong></summary>

#### Short answer

Look for slow queries doing large scans or expensive joins where selective predicates or join keys are not indexed.

#### Interview answer

Use `EXPLAIN (ANALYZE, BUFFERS)`, slow query logs, pg_stat_statements, and workload analysis.

A missing index is suggested when many rows are scanned/filtered to return few rows, or joins repeatedly scan a large table.

With `pg_stat_statements`, start from the workload cost, then inspect the plans of the top statements.

```
SELECT query, calls, total_exec_time, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

#### Deep dive

Index design depends on predicates, selectivity, ordering, joins and write cost. A composite index may be better than separate indexes.

Always check existing indexes for redundancy.

#### Production angle

In production, test the candidate index on realistic data and add it concurrently if needed. Validate that the planner uses it and latency improves.

Do not add indexes for one-off queries without considering write overhead.

#### Traps / caveats

- Not every seq scan means missing index.
- Low-selectivity predicates may not benefit.
- Indexes slow writes.
- Planner statistics must be fresh.

#### Optional Anki

Q: Main symptom of missing selective index?
A: Large scan with many rows removed to return few rows.

</details>

<a id="db-prod-007"></a>

<details>
<summary><strong>DB-PROD-007. How do you detect unused indexes?</strong></summary>

#### Short answer

Use index usage statistics such as pg_stat_user_indexes and compare scans against index size and write overhead.

#### Interview answer

PostgreSQL tracks how often indexes are scanned. An index with zero or very low scans over a meaningful period may be unused.

But stats reset after restart and rare critical queries may still need an index.

#### Deep dive

Check `idx_scan`, index size, relation size, constraints, uniqueness, and whether the index supports foreign keys or rare maintenance queries.

Duplicate/redundant indexes may be easier to remove.

```
SELECT schemaname, relname, indexrelname, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC, pg_relation_size(indexrelid) DESC;
```

#### Production angle

In production, remove indexes conservatively: verify across full business cycles, check dashboards/reports/batch jobs, and drop concurrently if supported.

Observe write performance and query regressions after removal.

#### Traps / caveats

- Stats resets can mislead.
- Unique/constraint indexes may be required even with low scans.
- Rare emergency/reporting queries may need an index.
- Dropping an index is a production change.

#### Optional Anki

Q: Which view helps detect unused indexes?
A: pg_stat_user_indexes.

</details>

<a id="db-prod-008"></a>

<details>
<summary><strong>DB-PROD-008. How do you detect table or index bloat?</strong></summary>

#### Short answer

Bloat is detected with statistics/extensions/estimation queries comparing relation size to expected live data and by observing vacuum/index behavior.

#### Interview answer

PostgreSQL MVCC leaves dead tuples after updates/deletes. If vacuum cannot keep up, table and indexes can grow larger than needed.

Use extensions or queries that estimate bloat, plus relation sizes and dead tuple stats.

#### Deep dive

Signals: high dead tuple count, table/index size growing faster than data, slow index scans, autovacuum constantly running or not running enough.

Exact bloat measurement is approximate unless using specialized tools.

```
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

#### Production angle

In production, fix the cause before cleanup: long transactions, insufficient autovacuum, high update churn, bad fillfactor, or missing partitioning.

Cleanup options include VACUUM, REINDEX CONCURRENTLY, pg_repack-like approaches, or partition rotation.

#### Traps / caveats

- VACUUM does not always shrink files.
- VACUUM FULL rewrites and locks heavily.
- Index bloat can remain after table vacuum.
- Long transactions can prevent cleanup.

#### Optional Anki

Q: What causes PostgreSQL bloat?
A: Dead tuples from MVCC updates/deletes that are not reclaimed effectively.

</details>

<a id="db-prod-009"></a>

<details>
<summary><strong>DB-PROD-009. How would you investigate high database CPU usage?</strong></summary>

#### Short answer

Find top queries by CPU/time/frequency, inspect plans, check active sessions, and correlate with deployments or traffic changes.

#### Interview answer

Use pg_stat_statements if available to find expensive queries. Use pg_stat_activity to see what is running now.

High CPU often comes from bad plans, missing indexes, excessive query frequency, too many connections, or expensive sorts/joins.

`pg_stat_statements` does not directly report pure CPU per query; correlate query time, plans, wait events, and host/cloud CPU metrics.

#### Deep dive

Look at query plans for sequential scans over large tables, nested loops with high loop counts, misestimated rows, expensive functions, and JIT overhead.

Check whether CPU is actually DB CPU or application connection waiting.

#### Production angle

In production, mitigate by limiting traffic, disabling heavy feature, killing runaway queries if safe, increasing resources temporarily, or adding safe indexes.

Long-term fix: query optimization, schema/index changes, caching/read models.

#### Traps / caveats

- CPU can be high because of too many connections.
- A single bad query can dominate CPU.
- Autovacuum also consumes CPU but is necessary.
- Do not disable safety features blindly.

#### Optional Anki

Q: What helps find top expensive queries?
A: pg_stat_statements if enabled.

</details>

<a id="db-prod-010"></a>

<details>
<summary><strong>DB-PROD-010. How would you investigate high database IO usage?</strong></summary>

#### Short answer

Check query plans and buffers, disk metrics, checkpoint/WAL activity, autovacuum, large scans, sorts spilling to disk, and cache hit ratio.

#### Interview answer

High IO can be reads from large scans or writes from heavy updates/inserts, WAL, checkpoints, vacuum and index builds.

`EXPLAIN (ANALYZE, BUFFERS)` shows shared hit/read/dirtied/written blocks for a query.

#### Deep dive

Look for poor cache locality, missing indexes, table/index bloat, insufficient memory, sort/hash spilling, and concurrent maintenance jobs.

High WAL generation can also affect replicas and disk bandwidth.

Use `BUFFERS`, `temp_blks_read`/`temp_blks_written` from `pg_stat_statements`, `track_io_timing` if enabled, and `pg_stat_io` on PostgreSQL 16+.

#### Production angle

In production, identify whether IO is read or write, random or sequential, query-driven or maintenance-driven.

Mitigate by reducing workload, stopping bad jobs, adding indexes carefully, increasing memory, or scaling storage.

#### Traps / caveats

- Low cache hit ratio is a symptom, not full diagnosis.
- Index-only scans depend on visibility map.
- Checkpoints can create IO spikes.
- Adding indexes also increases write IO.

#### Optional Anki

Q: Which EXPLAIN option helps inspect IO?
A: BUFFERS.

</details>

<a id="db-prod-011"></a>

<details>
<summary><strong>DB-PROD-011. How would you investigate connection pool exhaustion?</strong></summary>

#### Short answer

Check pool metrics, active/pending counts, acquisition timeouts, long transactions, slow queries, locks and connection leaks.

#### Interview answer

Pool exhaustion means all connections are in use and requests wait. The cause may be not enough pool capacity, but more often slow queries, locks, long transactions or leaks.

Start from pool metrics and correlate with DB sessions.

#### Deep dive

Inspect Hikari metrics: active, idle, pending, max, connection acquisition time. On PostgreSQL, inspect pg_stat_activity: state, query_start, xact_start, wait events, application_name.

Also check acquisition timeout count, leak detection logs, request concurrency, retry rate, and whether one endpoint monopolizes the shared pool. Thread dumps can show where application threads are waiting.

#### Production angle

Immediate mitigation: fail fast with timeouts, reduce traffic, disable heavy feature, fix blockers, cancel runaway queries. Long-term: shorten transactions, fix leaks, optimize queries, tune pool size.

Do not blindly increase pool size without DB capacity check.

#### Traps / caveats

- Increasing pool size can overload DB.
- Long @Transactional methods are common culprits.
- Connection leaks often appear after error paths.
- Retries amplify exhaustion.

#### Optional Anki

Q: What should you check for pool exhaustion?
A: Pool metrics plus pg_stat_activity for long queries/transactions/waits.

</details>

<a id="db-prod-012"></a>

<details>
<summary><strong>DB-PROD-012. How would you investigate sudden query plan regression?</strong></summary>

#### Short answer

Compare old and new plans, statistics, data distribution, parameters, indexes, PostgreSQL version/config, and recent ANALYZE or deployments.

#### Interview answer

A plan regression means PostgreSQL starts using a worse plan for the same logical query. Causes include stale stats, changed data distribution, dropped/invalid index, parameter skew, generic prepared plans, or config changes.

Start with `EXPLAIN (ANALYZE, BUFFERS)` and estimated vs actual rows.

#### Deep dive

Check if ANALYZE ran recently or not, if table grew, if most common values changed, if an index became bloated/invalid, and if prepared statements switched to a generic plan.

Compare with staging only if data is representative.

#### Production angle

In production, mitigation might be running ANALYZE, adding extended stats, changing query shape, adding/removing index, or forcing custom plans at application/session level if justified.

Permanent fix should address misestimation/root cause.

#### Traps / caveats

- Stats can be technically fresh but insufficient.
- Data skew is common.
- Generic prepared plans can hurt specific values.
- Do not fix by disabling planner features globally unless emergency.

#### Optional Anki

Q: Main symptom of bad plan estimates?
A: Large difference between estimated and actual rows.

</details>

<a id="db-prod-013"></a>

<details>
<summary><strong>DB-PROD-013. How can stale statistics cause bad plans?</strong></summary>

#### Short answer

PostgreSQL uses statistics to estimate row counts; stale stats can make it choose wrong scans, joins or indexes.

#### Interview answer

ANALYZE collects stats about row counts, distinct values, most common values and histograms. If data changes a lot, old stats no longer represent reality.

The planner may think a predicate is selective when it is not, or vice versa.

#### Deep dive

Bad estimates lead to bad choices: nested loop over huge rows, seq scan instead of index scan, hash join with spill, or wrong join order.

Autovacuum normally runs ANALYZE, but thresholds may not fit all tables.

#### Production angle

In production, run ANALYZE on affected tables, adjust autovacuum/analyze thresholds, increase statistics target, or add extended stats for correlated columns.

Validate with estimated vs actual rows.

#### Traps / caveats

- ANALYZE is cheap compared to bad plans, but not free.
- Stats are samples and can miss rare distributions.
- Temporary tables need stats too.
- Partition stats can need attention.

#### Optional Anki

Q: What do stale stats break?
A: Planner row estimates, leading to bad access/join choices.

</details>

<a id="db-prod-014"></a>

<details>
<summary><strong>DB-PROD-014. How can data skew cause bad plans?</strong></summary>

#### Short answer

Data skew means values are unevenly distributed, so average estimates do not match specific parameter values.

#### Interview answer

Example: most users have few orders, but one enterprise tenant has millions. A plan good for normal tenants may be terrible for the huge tenant.

Similarly, status='ACTIVE' may match 90% of rows while status='FAILED' matches 1%.

#### Deep dive

PostgreSQL statistics track most common values, but skew across multiple columns may require extended statistics or different query/index design.

Generic prepared plans are vulnerable when parameter values have very different selectivity.

#### Production angle

In production, check slow query parameters. Do not only test with average users.

Use extended stats, partial indexes, query specialization, or custom plans where appropriate.

#### Traps / caveats

- Average cardinality can hide hot values.
- One big tenant can break assumptions.
- Partial indexes may help rare values.
- Caching can mask but not fix skew.

#### Optional Anki

Q: What is data skew?
A: Uneven value distribution that makes estimates differ per parameter value.

</details>

<a id="db-prod-015"></a>

<details>
<summary><strong>🧠 DB-PROD-015. How can a generic prepared statement plan cause bad performance?</strong></summary>

#### Short answer

A generic plan is reused for many parameter values, but one average plan can be bad when parameter selectivity varies a lot.

#### Interview answer

Prepared statements can use custom plans based on actual parameters or generic plans reused across executions.

If some parameter values return 1 row and others return millions, a generic plan may be wrong for one side.

#### Deep dive

Example: `WHERE tenant_id = ?` where one tenant is huge. A generic plan may choose nested loop or index scan that is fine for small tenants but terrible for large tenant.

Parameter-sensitive workloads require care.

#### Production angle

In production, compare plans for literal values vs prepared execution, inspect plan_cache_mode if needed, and consider query specialization for hot/skewed values.

Do not disable prepared statements globally without understanding impact.

#### Traps / caveats

- Prepared statements are good for safety but can affect plans.
- Generic plan issues appear with skew.
- Literal EXPLAIN may not match prepared execution.
- Fix can be query-specific.

#### Optional Anki

Q: When generic plan hurts?
A: When different parameter values have very different selectivity.

</details>

<a id="db-prod-016"></a>

<details>
<summary><strong>DB-PROD-016. What would you do if autovacuum is not keeping up?</strong></summary>

#### Short answer

Identify why, tune autovacuum for affected tables, reduce long transactions, and consider manual VACUUM/REINDEX/partitioning where needed.

#### Interview answer

Autovacuum may not keep up because update/delete rate is high, thresholds are too high, workers are limited, long transactions prevent cleanup, or IO throttling is too conservative.

Symptoms include dead tuple growth, bloat, wraparound risk, and poor plans.

#### Deep dive

Check pg_stat_user_tables, last_autovacuum, n_dead_tup, vacuum progress, long transactions, and table-specific autovacuum settings.

Hot tables often need custom autovacuum scale factor/threshold.

```
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum,
       vacuum_count, autovacuum_count,
       age(relfrozenxid) AS xid_age
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

#### Production angle

In production, first protect wraparound and disk space. Kill or fix long idle transactions if safe. Tune autovacuum per table. Use partitioning for high-churn time-series tables.

Manual VACUUM can help, but fix the root cause.

#### Traps / caveats

- Disabling autovacuum is dangerous.
- Long transactions can make vacuum ineffective.
- VACUUM FULL is intrusive.
- Autovacuum tuning is workload-specific.

#### Optional Anki

Q: Common cause of ineffective vacuum?
A: Long-running transactions holding old snapshots.

</details>

<a id="db-prod-017"></a>

<details>
<summary><strong>DB-PROD-017. What would you do if replication lag grows?</strong></summary>

#### Short answer

Find whether lag is caused by primary write rate, network, standby IO/CPU, long standby queries, slots, or maintenance jobs, then mitigate based on cause.

#### Interview answer

Check WAL generation rate, standby replay status, network, disk IO, long-running queries on standby, replication slots, and recent heavy writes/backfills/index builds.

Lag can be receiving lag, flush lag, or replay lag.

#### Deep dive

If standby received WAL but cannot replay, IO/CPU or long queries may be the issue. If it is not receiving, network or primary sender may be the issue.

Large transactions can cause lag spikes. Use `pg_stat_replication` on primary, `pg_last_wal_receive_lsn()`/`pg_last_wal_replay_lsn()` on standby, and `pg_replication_slots` for WAL retention.

#### Production angle

Production response: remove lagging replica from read pool, route fresh reads to primary, throttle heavy writes/backfills, cancel long standby queries if safe, and alert on WAL retention.

Protect disk if slots retain WAL.

#### Traps / caveats

- Replica lag can cause stale reads.
- Replication slots can fill disk.
- Heavy migrations/backfills create WAL spikes.
- Fallback to primary can overload primary.

#### Optional Anki

Q: First app action for high replica lag?
A: Stop routing consistency-sensitive reads to the lagging replica.

</details>

<a id="db-prod-018"></a>

<details>
<summary><strong>DB-PROD-018. What would you do if a migration locks a hot table?</strong></summary>

#### Short answer

Identify blocker/blocked sessions, stop or cancel the migration if safe, restore traffic, then redesign the migration with safer locking behavior.

#### Interview answer

A migration waiting for a strong lock can create a lock queue and block normal application queries behind it.

First triage: is production traffic blocked? Which session is migration? Which sessions are blockers?

#### Deep dive

Use pg_stat_activity, pg_locks and pg_blocking_pids. If migration is causing outage, cancel it if rollback is safe. If a blocker is an idle transaction, decide whether to terminate it based on runbook.

After mitigation, add lock_timeout and split migration into safer steps.

#### Production angle

Production learning: never run risky DDL without lock_timeout, statement_timeout, monitoring and rollback plan. Use concurrent/online variants, batching, expand-and-contract and maintenance windows.

Communicate incident impact.

#### Traps / caveats

- Canceling migration may leave partial/invalid objects.
- Killing blockers can roll back user work.
- Lock queues can outlast the original query if not handled.
- Runbooks matter.

#### Optional Anki

Q: What is first goal when migration locks hot table?
A: Restore availability by understanding/canceling blockers or migration safely.

</details>

<a id="db-prod-019"></a>

<details>
<summary><strong>DB-PROD-019. How would you design database timeouts for a Java service?</strong></summary>

#### Short answer

Use layered timeouts: connection acquisition timeout, JDBC/socket timeout, statement/query timeout, lock timeout, transaction timeout and API timeout.

#### Interview answer

Timeouts should form a budget. The database query timeout should fit inside the service request timeout, and retries should not exceed the total deadline.

PostgreSQL has statement_timeout and lock_timeout; pools have connectionTimeout; frameworks have transaction timeouts.

#### Deep dive

Timeouts protect resources and prevent indefinite waits. Lock timeout is especially useful for migrations and operations that should fail fast if blocked.

Set them per workload; reporting queries may need different limits than OLTP requests.

#### Production angle

In production, expose timeout errors clearly and correlate them with query/lock/pool metrics. Retry only idempotent operations and use backoff/jitter.

Timeouts are part of resilience, not just configuration.

#### Traps / caveats

- Missing timeouts cause thread exhaustion.
- Too aggressive timeouts cause false failures.
- Retries can multiply DB load.
- Timeouts must align across layers.

#### Optional Anki

Q: Name DB-related timeout layers.
A: Pool acquisition, statement/query, lock, transaction and API deadline.

</details>

<a id="db-prod-020"></a>

<details>
<summary><strong>DB-PROD-020. How would you prevent one slow query from exhausting the whole service?</strong></summary>

#### Short answer

Use timeouts, pool isolation, concurrency limits, circuit breakers, query optimization, pagination limits, and workload separation.

#### Interview answer

One slow query can hold many connections, causing pool exhaustion and making unrelated endpoints fail.

Protect the service with statement timeouts, connection acquisition timeouts, bounded pools, and endpoint-level concurrency limits.

#### Deep dive

Separate critical OLTP traffic from heavy reporting jobs with different pools, replicas, queues or read models.

Apply max page sizes, forbid unbounded exports, and use async jobs for heavy operations.

#### Production angle

In production, add observability and automatic safeguards: slow-query alerts, pool pending alerts, feature flags, rate limits and fail-fast behavior.

Then fix the query/index/schema root cause.

#### Traps / caveats

- Retries can make slow-query incidents worse.
- A shared pool lets one endpoint starve others.
- Timeouts without cancellation may still leave DB work running.
- Heavy queries may belong in analytics path.

#### Optional Anki

Q: How isolate slow heavy DB work?
A: Use separate pools/replicas/queues and enforce timeouts/concurrency limits.

</details>
