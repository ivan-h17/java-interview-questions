# JOINs, subqueries and set operations

---

<a id="db-join-001"></a>

<details>
<summary><strong>DB-JOIN-001. What types of JOIN exist?</strong></summary>

#### Short answer

The main SQL join types are INNER JOIN, LEFT OUTER JOIN, RIGHT OUTER JOIN, FULL OUTER JOIN and CROSS JOIN. There are also self joins and logical semi/anti joins expressed with `EXISTS`, `IN`, `NOT EXISTS` or `LEFT JOIN ... IS NULL`.

#### Interview answer

A join combines rows from two relations based on a condition. `INNER JOIN` returns matched rows only. Outer joins preserve unmatched rows from one or both sides. `CROSS JOIN` creates a Cartesian product.

#### Deep dive

Examples:

```sql
SELECT * FROM orders o INNER JOIN customers c ON c.id = o.customer_id;
SELECT * FROM customers c LEFT JOIN orders o ON o.customer_id = c.id;
SELECT * FROM a CROSS JOIN b;
```

#### Production angle

In production, join correctness is as important as performance. A wrong outer join condition can silently drop or duplicate data. For performance, join cardinality, indexes, statistics and join algorithm matter.

#### Traps / caveats

- Outer join conditions are easy to break by moving filters from `ON` to `WHERE`.
- Joins can multiply rows if the relationship is not one-to-one.
- A join can be logically correct but slow due to missing indexes or bad estimates.
- SQL join type is not the same as physical join algorithm.

#### Optional Anki

Q: Main SQL join types?
A: INNER, LEFT OUTER, RIGHT OUTER, FULL OUTER and CROSS JOIN.

</details>

<a id="db-join-002"></a>

<details>
<summary><strong>DB-JOIN-002. What is the difference between INNER JOIN and LEFT JOIN?</strong></summary>

#### Short answer

`INNER JOIN` returns only rows that have a match on both sides. `LEFT JOIN` returns all rows from the left table and fills right-side columns with `NULL` when there is no match.

#### Interview answer

Use `INNER JOIN` when the relationship must exist and unmatched rows should be excluded. Use `LEFT JOIN` when you want to keep the left-side rows even if related data is missing.

#### Deep dive

Example:

```sql
-- only customers with orders
SELECT c.id, o.id
FROM customers c
INNER JOIN orders o ON o.customer_id = c.id;

-- all customers, even without orders
SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;
```

#### Production angle

A common production bug is accidentally turning a `LEFT JOIN` into an `INNER JOIN` by filtering the right table in `WHERE`. This can remove rows that should have been preserved.

#### Traps / caveats

- Right-side columns in unmatched `LEFT JOIN` rows are `NULL`.
- Filters on right-side columns must be placed carefully.
- A `LEFT JOIN` can still multiply rows if the right side has multiple matches.
- Do not use `LEFT JOIN` when an `INNER JOIN` expresses the business rule better.

#### Optional Anki

Q: Difference between INNER and LEFT JOIN?
A: `INNER JOIN` returns matched rows only; `LEFT JOIN` keeps all left rows and uses NULLs for missing right rows.

</details>

<a id="db-join-003"></a>

<details>
<summary><strong>DB-JOIN-003. What is the difference between LEFT JOIN, RIGHT JOIN and FULL OUTER JOIN?</strong></summary>

#### Short answer

`LEFT JOIN` preserves all rows from the left side, `RIGHT JOIN` preserves all rows from the right side, and `FULL OUTER JOIN` preserves unmatched rows from both sides.

#### Interview answer

`RIGHT JOIN` is usually avoidable by swapping table order and using `LEFT JOIN`. `FULL OUTER JOIN` is useful when comparing two datasets and you need matched and unmatched rows from both sides.

#### Deep dive

Example full join for reconciliation:

```sql
SELECT a.id AS source_id, b.id AS target_id
FROM source_data a
FULL OUTER JOIN target_data b ON b.id = a.id
WHERE a.id IS NULL OR b.id IS NULL;
```

#### Production angle

In production code, prefer the join form that makes the preserved side obvious. Many teams avoid `RIGHT JOIN` for readability and use `LEFT JOIN` consistently.

#### Traps / caveats

- Outer joins introduce `NULL`s for missing sides.
- `FULL OUTER JOIN` can be expensive on large datasets.
- Filters after a full join can accidentally remove the unmatched rows you wanted.
- `RIGHT JOIN` often reduces readability.

#### Optional Anki

Q: What does FULL OUTER JOIN preserve?
A: Matched rows plus unmatched rows from both sides.

</details>

<a id="db-join-004"></a>

<details>
<summary><strong>DB-JOIN-004. What is CROSS JOIN?</strong></summary>

#### Short answer

`CROSS JOIN` returns the Cartesian product of two tables: every row from the first table combined with every row from the second table.

#### Interview answer

If table A has 100 rows and table B has 50 rows, a cross join returns 5,000 rows. It has no join condition by itself.

#### Deep dive

Example:

```sql
SELECT d.day, r.room_id
FROM days d
CROSS JOIN rooms r;
```

#### Production angle

Cross joins are valid for generating combinations, calendars, grids or test data. They are dangerous when they happen accidentally because row counts can explode.

#### Traps / caveats

- Missing join conditions can create accidental cross joins.
- Cross joins can produce huge intermediate results.
- Always estimate cardinality.
- Use it intentionally and usually with small inputs or later filters.

#### Optional Anki

Q: What is CROSS JOIN?
A: A Cartesian product of two inputs.

</details>

<a id="db-join-005"></a>

<details>
<summary><strong>DB-JOIN-005. What is a self join?</strong></summary>

#### Short answer

A self join is a join where a table is joined with itself using different aliases.

#### Interview answer

It is useful when rows in the same table are related to each other, for example employees and managers, categories and parent categories, or comparing rows within the same group.

#### Deep dive

Example:

```sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;
```

#### Production angle

For hierarchies of unknown depth, self join works only for fixed levels. Recursive CTEs or specialized models may be better for arbitrary-depth trees.

#### Traps / caveats

- Always use clear aliases.
- Self joins can multiply rows if relationship cardinality is not clear.
- Recursive structures may need recursive CTEs.
- Index the self-referencing foreign key if it is queried often.

#### Optional Anki

Q: What is a self join?
A: A table joined with itself using aliases.

</details>

<a id="db-join-006"></a>

<details>
<summary><strong>DB-JOIN-006. What is the difference between putting a condition in ON vs WHERE for a LEFT JOIN?</strong></summary>

#### Short answer

For a `LEFT JOIN`, a condition in `ON` controls which right-side rows match. A condition in `WHERE` is applied after the join and can remove rows with no match, effectively turning the outer join into an inner join.

#### Interview answer

This is one of the most important join traps. If you want all customers and only their paid orders, put `o.status = 'PAID'` in `ON`. If you put it in `WHERE`, customers without paid orders disappear.

#### Deep dive

Correct for preserving all customers:

```sql
SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id
 AND o.status = 'PAID';
```

Different semantics:

```sql
SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'PAID';
```

#### Production angle

This bug often appears in reporting endpoints, exports and dashboards: numbers are lower than expected because rows with missing right-side data were filtered out.

#### Traps / caveats

- For inner joins, optimizer can often move predicates around more freely.
- For outer joins, predicate placement can change semantics.
- Use `WHERE o.id IS NULL` intentionally for anti-join patterns.
- Always test outer joins with rows that have no match.

#### Optional Anki

Q: Why is `WHERE` dangerous after `LEFT JOIN`?
A: It can filter out NULL-extended rows and turn the query into inner-join semantics.

</details>

<a id="db-join-007"></a>

<details>
<summary><strong>DB-JOIN-007. What is better: JOIN or subquery?</strong></summary>

#### Short answer

There is no universal answer. It depends on semantics, readability, data size, indexes and the execution plan. PostgreSQL can often rewrite subqueries and joins into similar plans.

#### Interview answer

Use the form that expresses intent clearly. If you need columns from both tables, a join is natural. If you only need to check existence, `EXISTS` may express the intent better. If you need pre-aggregation, a subquery or CTE can be clearer.

#### Deep dive

Compare:

```sql
-- join for data from both sides
SELECT o.id, c.email
FROM orders o
JOIN customers c ON c.id = o.customer_id;

-- existence check
SELECT c.*
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
```

#### Production angle

In production, do not decide by folklore like “joins are faster” or “subqueries are slower”. Use `EXPLAIN ANALYZE`, check actual rows and compare with realistic data.

#### Traps / caveats

- A join can duplicate rows; `EXISTS` usually does not.
- A subquery can be optimized into a semi-join or anti-join.
- Correlated subqueries can be slow if not decorrelated or indexed.
- Readability and correctness come before micro-optimizing syntax.

#### Optional Anki

Q: What is better, JOIN or subquery?
A: It depends on semantics and plan; compare with `EXPLAIN ANALYZE`.

</details>

<a id="db-join-008"></a>

<details>
<summary><strong>DB-JOIN-008. When can a subquery be better than a JOIN?</strong></summary>

#### Short answer

A subquery can be better when it expresses existence, anti-existence, pre-aggregation, top-N per parent with `LATERAL`, or isolation of a logical step more clearly than a join.

#### Interview answer

For example, `EXISTS` avoids row multiplication when you only care whether related rows exist. A subquery can also aggregate child rows before joining to the parent, reducing intermediate result size.

#### Deep dive

Example pre-aggregation:

```sql
SELECT c.id, o.total_amount
FROM customers c
JOIN (
  SELECT customer_id, sum(amount) AS total_amount
  FROM orders
  GROUP BY customer_id
) o ON o.customer_id = c.id;
```

Example top-N per parent with `LATERAL`:

```sql
SELECT c.id, o.id AS last_order_id
FROM customers c
LEFT JOIN LATERAL (
  SELECT id
  FROM orders o
  WHERE o.customer_id = c.id
  ORDER BY created_at DESC
  LIMIT 1
) o ON true;
```

#### Production angle

In production reports, pre-aggregating before joining can be much cheaper than joining raw high-cardinality tables and aggregating afterward.

#### Traps / caveats

- A subquery is not automatically faster.
- CTEs/subqueries can make plans clearer or worse depending on materialization and optimization.
- Watch for correlated subqueries that execute many times.
- `LATERAL` is powerful for per-parent lookups, but it can become a repeated lookup without the right index.
- Measure with realistic cardinalities.

#### Optional Anki

Q: When is `EXISTS` better than a join?
A: When you only need to know whether related rows exist and do not need columns from them.

</details>

<a id="db-join-009"></a>

<details>
<summary><strong>DB-JOIN-009. What is a correlated subquery?</strong></summary>

#### Short answer

A correlated subquery is a subquery that references columns from the outer query. Its result depends on the current outer row.

#### Interview answer

Logically, PostgreSQL evaluates the correlated subquery for each relevant outer row. The planner may optimize or transform it, but the dependency on the outer row is the defining feature.

#### Deep dive

Example:

```sql
SELECT c.*
FROM customers c
WHERE EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.id
);
```

#### Production angle

Correlated subqueries are common in existence checks and per-row calculations. They are not automatically bad, but they require correct indexes and plan inspection when data is large.

#### Traps / caveats

- A correlated subquery can become a nested-loop-like repeated lookup.
- Without an index on the inner table correlation column, it can be very slow.
- The planner may decorrelate some subqueries but not all.
- `EXISTS` correlated subqueries are often fine with the right index.

#### Optional Anki

Q: What makes a subquery correlated?
A: It references a column from the outer query.

</details>

<a id="db-join-010"></a>

<details>
<summary><strong>DB-JOIN-010. Why can correlated subqueries be slow?</strong></summary>

#### Short answer

They can be slow because the inner query may need to run or be probed for many outer rows, especially if the inner side has no suitable index or returns many rows.

#### Interview answer

A correlated subquery often behaves like repeated lookups: for each customer, check orders; for each order, check payments; and so on. With a good index, this may be fine. Without it, it can become extremely expensive.

#### Deep dive

Potential rewrite:

```sql
-- correlated
SELECT c.*
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- possible equivalent join/semi-join style
SELECT DISTINCT c.*
FROM customers c
JOIN orders o ON o.customer_id = c.id;
```

#### Production angle

Do not rewrite blindly: `EXISTS` can be more correct than `JOIN DISTINCT`. The production approach is to inspect the plan and add the right index, such as `orders(customer_id)`, if the access pattern is valid.

#### Traps / caveats

- Repeated execution is a logical model; planner may optimize some cases.
- Missing inner indexes are the common problem.
- Aggregated correlated subqueries can be especially expensive.
- Rewriting can change duplicates and semantics.

#### Optional Anki

Q: Common fix for slow correlated `EXISTS`?
A: Index the inner table column used to correlate with the outer row.

</details>

<a id="db-join-011"></a>

<details>
<summary><strong>DB-JOIN-011. What is the difference between IN and EXISTS?</strong></summary>

#### Short answer

`IN` compares a value against a set of values. `EXISTS` checks whether a subquery returns at least one row. `EXISTS` is usually better when you only care about existence.

#### Interview answer

`IN` reads naturally when the subquery returns a simple value list. `EXISTS` reads naturally when the inner query is correlated and expresses “there is at least one matching row”. PostgreSQL may optimize both into similar semi-join plans.

#### Deep dive

Examples:

```sql
SELECT * FROM orders WHERE status IN ('NEW', 'PAID');

SELECT c.*
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.id
);
```

#### Production angle

For production, prefer the expression that communicates intent. For anti-conditions, be especially careful: `NOT IN` and `NOT EXISTS` can differ because of `NULL`.

#### Traps / caveats

- `IN` has tricky `NULL` semantics.
- `EXISTS` can stop after finding a matching row logically.
- The optimizer may rewrite both.
- Do not assume one is always faster; check the plan.

#### Optional Anki

Q: Difference between `IN` and `EXISTS`?
A: `IN` compares to a value set; `EXISTS` checks whether a subquery returns any row.

</details>

<a id="db-join-012"></a>

<details>
<summary><strong>DB-JOIN-012. What is the difference between NOT IN and NOT EXISTS?</strong></summary>

#### Short answer

`NOT EXISTS` checks that no matching row exists. `NOT IN` checks that a value is not equal to any value in a set, but it behaves dangerously if the set contains `NULL`.

#### Interview answer

Because SQL uses three-valued logic, if the `NOT IN` subquery returns a `NULL`, the comparison can become `UNKNOWN` for all rows, and the query may return no rows.

#### Deep dive

Safer anti-join pattern:

```sql
SELECT c.*
FROM customers c
WHERE NOT EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.id
);
```

#### Production angle

In production, I usually prefer `NOT EXISTS` for anti-joins unless the `NOT IN` column is guaranteed `NOT NULL` and the semantics are obvious.

#### Traps / caveats

- `NOT IN` plus nullable subquery result is a classic bug.
- `NOT EXISTS` is usually safer for anti-joins.
- Adding `WHERE inner_col IS NOT NULL` can make `NOT IN` safer, but `NOT EXISTS` is often clearer.
- Always consider duplicate semantics and nullability.

#### Optional Anki

Q: Why prefer `NOT EXISTS` over `NOT IN`?
A: Because `NOT IN` can behave unexpectedly when the subquery returns `NULL`.

</details>

<a id="db-join-013"></a>

<details>
<summary><strong>DB-JOIN-013. Why can NOT IN behave unexpectedly with NULL values?</strong></summary>

#### Short answer

Because `x NOT IN (subquery)` is equivalent to saying that `x` is not equal to every value in the set. If one of those values is `NULL`, SQL cannot prove the comparison, so the result can become `UNKNOWN`.

#### Interview answer

In a `WHERE` clause, only `TRUE` rows are returned. `UNKNOWN` is filtered out. That is why a single `NULL` in the subquery can cause `NOT IN` to return no rows.

#### Deep dive

Example:

```sql
SELECT 1
WHERE 42 NOT IN (1, 2, NULL);
-- returns no row because result is UNKNOWN
```

#### Production angle

This is a real source of production bugs in cleanup jobs, exclusion filters and reporting queries. Use `NOT EXISTS` or explicitly remove `NULL`s if that matches the business rule.

#### Traps / caveats

- This is not a performance issue first; it is a correctness issue.
- `NOT IN` is okay if the compared values are guaranteed non-null.
- `NOT EXISTS` usually expresses anti-join semantics more safely.
- Tests should include NULL cases.

#### Optional Anki

Q: What happens with `42 NOT IN (1, 2, NULL)`?
A: It returns UNKNOWN, so a WHERE clause filters it out.

</details>

<a id="db-join-014"></a>

<details>
<summary><strong>DB-JOIN-014. What is the difference between EXISTS and JOIN?</strong></summary>

#### Short answer

`EXISTS` checks whether at least one related row exists. A `JOIN` combines rows and can return columns from both sides, but it can also duplicate outer rows if multiple matches exist.

#### Interview answer

Use `EXISTS` for semi-join semantics: “return customers that have orders”. Use `JOIN` when you need order data too.

#### Deep dive

Compare:

```sql
-- one row per customer if condition matches
SELECT c.*
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- one row per matching order
SELECT c.*, o.id
FROM customers c
JOIN orders o ON o.customer_id = c.id;
```

#### Production angle

A common bug is using `JOIN` when the business question is existence. Developers then add `DISTINCT` to remove duplicates, which can hide the issue and add cost.

#### Traps / caveats

- `EXISTS` does not return columns from the inner query.
- `JOIN` can multiply rows.
- `DISTINCT` after a join may be a smell.
- The planner may implement `EXISTS` as a semi-join internally.

#### Optional Anki

Q: When use `EXISTS` instead of `JOIN`?
A: When you only need to check that related rows exist.

</details>

<a id="db-join-015"></a>

<details>
<summary><strong>DB-JOIN-015. How can indexes help JOIN performance?</strong></summary>

#### Short answer

Indexes help joins by making lookups on join keys cheaper, especially for nested loop joins, foreign-key lookups and selective joins. They can also help with merge joins and ordering.

#### Interview answer

The most common case is an index on the child table foreign key. If we load one customer and then fetch their orders, `orders(customer_id)` is essential.

#### Deep dive

Example:

```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);

SELECT *
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.id = 123;
```

#### Production angle

In production, index both the lookup pattern and filter pattern. For example, `orders(customer_id, created_at DESC)` may be better than only `orders(customer_id)` for “latest orders by customer”.

#### Traps / caveats

- PostgreSQL does not automatically index foreign key columns.
- Parent primary keys are indexed, but child foreign keys often need manual indexes.
- Hash joins may not need an index on the join key but still depend on memory and row counts.
- Composite indexes should match real filters and ordering.

#### Optional Anki

Q: Which FK side often needs a manual index?
A: The child table foreign key column.

</details>

<a id="db-join-016"></a>

<details>
<summary><strong>🧠 DB-JOIN-016. What is join selectivity?</strong></summary>

#### Short answer

Join selectivity is the estimated fraction or number of row combinations that will match a join condition. It helps the planner estimate join result size.

#### Interview answer

If the planner thinks a join returns few rows, it may choose a nested loop. If it expects many rows, it may prefer a hash join or merge join. Bad estimates can lead to bad join order and algorithm.

#### Deep dive

Join selectivity depends on constraints, distinct counts, most common values, histograms, null fractions, data skew and correlations between columns.

#### Production angle

When a production join suddenly becomes slow, compare estimated rows vs actual rows in `EXPLAIN ANALYZE`. Large mismatch often points to stale statistics, data skew or missing extended statistics.

#### Traps / caveats

- Join selectivity is an estimate, not a guarantee.
- Bad estimates can be worse than missing indexes.
- Data skew can break average-based assumptions.
- Constraints and fresh statistics help the planner.

#### Optional Anki

Q: Why does join selectivity matter?
A: It affects estimated result size, join order and join algorithm choice.

</details>

<a id="db-join-017"></a>

<details>
<summary><strong>🧠 DB-JOIN-017. How can PostgreSQL choose between different join orders?</strong></summary>

#### Short answer

PostgreSQL uses a cost-based planner. It estimates row counts and costs for possible join orders and algorithms, then chooses the cheapest plan according to its cost model.

#### Interview answer

The planner uses table statistics, indexes, constraints, predicates and join conditions. For many joined tables, the search space becomes huge, so PostgreSQL may use genetic query optimization for very complex joins.

#### Deep dive

Inner joins can often be reordered freely. Outer joins restrict reordering because changing order can change semantics. This is another reason why join type matters.

#### Production angle

If a join plan is bad in production, inspect estimated vs actual rows, check statistics freshness, check whether predicates are selective, and consider whether extended statistics or query rewrite is needed.

#### Traps / caveats

- The planner does not know your business semantics beyond constraints and statistics.
- Outer joins limit reordering.
- Stale statistics can produce bad join order.
- For many joins, query shape and schema design matter a lot.

#### Optional Anki

Q: How does PostgreSQL choose join order?
A: Using cost estimates based on statistics, constraints, predicates, indexes and join conditions.

</details>

<a id="db-join-018"></a>

<details>
<summary><strong>🧠 DB-JOIN-018. How can PostgreSQL rewrite subqueries internally?</strong></summary>

#### Short answer

PostgreSQL can often transform subqueries into joins, semi-joins, anti-joins, pull-up subqueries, or otherwise flatten parts of the query when it is semantically safe.

#### Interview answer

For example, `EXISTS` may become a semi-join and `NOT EXISTS` may become an anti-join. Some `IN` queries can be rewritten similarly. But not every subquery can be decorrelated or flattened.

#### Deep dive

Reasons a subquery may not be freely rewritten include aggregation, volatile functions, limits, ordering requirements, outer joins, lateral dependencies, and semantic differences around duplicates or `NULL`.

#### Production angle

For production tuning, do not guess whether PostgreSQL rewrote a query. Check the actual plan with `EXPLAIN`. If the plan is poor, try alternative equivalent forms and compare with `EXPLAIN ANALYZE`.

#### Traps / caveats

- Rewrites must preserve semantics, including duplicates and `NULL` behavior.
- A prettier SQL query may not produce a better plan.
- A CTE or subquery can help readability but may affect optimization depending on structure.
- Use plans, not assumptions.

#### Optional Anki

Q: What can `EXISTS` become internally?
A: Often a semi-join, if rewriting is semantically safe.

</details>

<a id="db-join-019"></a>

<details>
<summary><strong>DB-JOIN-019. What is the difference between JOIN and UNION?</strong></summary>

#### Short answer

A `JOIN` combines columns from related rows side by side. A `UNION` combines rows from compatible result sets one after another.

#### Interview answer

Use a join when the business question needs data from related tables in the same result row, for example order plus customer email. Use a union when two queries produce the same shape and you want one combined list.

#### Deep dive

Examples:

```sql
-- add columns from customers
SELECT o.id, c.email
FROM orders o
JOIN customers c ON c.id = o.customer_id;

-- append rows from two sources
SELECT email FROM customers
UNION
SELECT email FROM newsletter_subscribers;
```

#### Production angle

Confusing these operations is a design smell. A join can multiply rows because of relationship cardinality. A union can hide duplicates or force expensive duplicate elimination depending on whether you use `UNION` or `UNION ALL`.

#### Traps / caveats

- Set operation inputs must have compatible column counts and types.
- Output column names come from the first query.
- `UNION` removes duplicates; `UNION ALL` does not.
- Final `ORDER BY` applies to the combined result.

#### Optional Anki

Q: JOIN vs UNION?
A: JOIN combines columns horizontally; UNION combines compatible rows vertically.

</details>
