# Locks and concurrency control

---

<a id="db-lock-001"></a>

<details>
<summary><strong>DB-LOCK-001. What types of locks exist in PostgreSQL?</strong></summary>

#### Short answer

PostgreSQL has table-level locks, row-level locks, page-level locks, advisory locks, and predicate locks for Serializable isolation.

#### Interview answer

For backend developers, the most important are row locks from `UPDATE`/`DELETE`/`SELECT FOR UPDATE`, table locks from DDL, advisory locks for application coordination, and lock waits/deadlocks.

#### Deep dive

Locks coexist with MVCC. Normal reads usually do not block writes, but writes, explicit locks, DDL, foreign keys, unique checks, and serializable predicate locks can still create waits.

#### Production angle

Investigate lock problems through `pg_stat_activity`, `pg_locks`, `pg_blocking_pids(pid)`, wait events, transaction age, and application request traces.

#### Traps / caveats

- Do not just say “the table is locked”; lock mode matters.
- Row locks do not block ordinary SELECTs.
- DDL often needs stronger locks than expected.

#### Optional Anki

Q: What are the main PostgreSQL lock categories?
A: Table, row, page, advisory, and predicate locks.

</details>

---

<a id="db-lock-002"></a>

<details>
<summary><strong>DB-LOCK-002. What are table-level locks?</strong></summary>

#### Short answer

Table-level locks are relation-level locks acquired by statements with different lock strengths.

#### Interview answer

A normal `SELECT` takes a weak `ACCESS SHARE` lock. Many schema-changing statements need stronger locks, and `ACCESS EXCLUSIVE` conflicts with normal reads and writes.

#### Deep dive

Table-level locks use a conflict matrix. This matters for migrations, `ALTER TABLE`, `CREATE INDEX`, `VACUUM FULL`, and other maintenance operations.

#### Production angle

A fast DDL can still be dangerous if it waits for a strong lock and blocks new queries behind it. Use lock timeouts and migration windows.

#### Traps / caveats

- Blocked DDL can create a queue of blocked app queries.
- `VACUUM FULL` is highly disruptive.
- `CREATE INDEX CONCURRENTLY` reduces but does not eliminate locks.

#### Optional Anki

Q: Why care about table locks in migrations?
A: Strong table locks can block application reads/writes.

</details>

---

<a id="db-lock-003"></a>

<details>
<summary><strong>DB-LOCK-003. What are row-level locks?</strong></summary>

#### Short answer

Row-level locks protect individual rows from conflicting concurrent modifications.

#### Interview answer

`UPDATE`, `DELETE`, and `SELECT ... FOR UPDATE` acquire row locks. Other transactions trying to update/delete/lock the same rows can wait.

#### Deep dive

PostgreSQL has several row lock strengths: `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, and `FOR KEY SHARE`. They block different sets of concurrent operations.

#### Production angle

Row locks are normal in OLTP, but long transactions can keep them too long and create latency spikes, blocked requests, and deadlocks.

#### Traps / caveats

- Row locks do not block ordinary SELECTs.
- Locking many rows still has cost.
- Foreign keys can cause unexpected row-lock waits.

#### Optional Anki

Q: What acquires row-level locks?
A: UPDATE, DELETE, and row-locking SELECTs such as SELECT FOR UPDATE.

</details>

---

<a id="db-lock-004"></a>

<details>
<summary><strong>DB-LOCK-004. What is SELECT FOR UPDATE?</strong></summary>

#### Short answer

`SELECT FOR UPDATE` reads rows and locks them as if they are going to be updated.

#### Interview answer

It is a pessimistic locking tool. Other transactions trying to update, delete, or lock the same rows will wait until the current transaction ends.

#### Deep dive

Typical use: lock an order before changing its state.

```sql
BEGIN;
SELECT * FROM orders WHERE id = 42 FOR UPDATE;
UPDATE orders SET status = 'PAID' WHERE id = 42;
COMMIT;
```

#### Production angle

Use it when concurrent modifications of the same business entity must be serialized. Keep the transaction short and consider `NOWAIT` or `lock_timeout` when waiting is unacceptable.

#### Traps / caveats

- Do not hold it across remote calls.
- It only locks selected rows.
- At higher isolation levels, locking a row changed after transaction start can fail.

#### Optional Anki

Q: What does SELECT FOR UPDATE do?
A: Locks selected rows against conflicting modifications until transaction end.

</details>

---

<a id="db-lock-005"></a>

<details>
<summary><strong>🧠 DB-LOCK-005. What is SELECT FOR SHARE?</strong></summary>

#### Short answer

`SELECT FOR SHARE` reads rows and takes a shared row lock.

#### Interview answer

It blocks conflicting updates/deletes but allows compatible shared locks. It is weaker than `FOR UPDATE`.

#### Deep dive

PostgreSQL also has `FOR KEY SHARE` and `FOR NO KEY UPDATE` for more precise row locking. The exact lock mode matters for foreign-key-heavy workloads.

#### Production angle

Use explicit shared locks carefully. Many correctness problems are better solved with constraints, unique indexes, or Serializable isolation.

#### Traps / caveats

- Developers often overuse explicit locks.
- `FOR SHARE` can still block writers.
- Locking reads can reduce concurrency.

#### Optional Anki

Q: Is FOR SHARE weaker than FOR UPDATE?
A: Yes. It takes a shared row lock, not an update lock.

</details>

<a id="db-lock-006"></a>

<details>
<summary><strong>DB-LOCK-006. What is SKIP LOCKED?</strong></summary>

#### Short answer

`SKIP LOCKED` skips locked rows instead of waiting for them.

#### Interview answer

It is commonly used when many workers pull jobs from the same table. Each worker locks available rows and skips rows already locked by other workers.

#### Deep dive

Queue-like pattern:

```sql
WITH picked AS (
  SELECT id
  FROM jobs
  WHERE status = 'READY'
  ORDER BY created_at
  LIMIT 10
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs j
SET status = 'PROCESSING'
FROM picked
WHERE j.id = picked.id
RETURNING j.*;
```

#### Production angle

It improves throughput but gives an intentionally inconsistent view: locked rows disappear from the current worker’s result. You need retries, stuck-job recovery, and good indexes.

#### Traps / caveats

- Not a general correctness tool.
- Can cause starvation.
- Must be paired with job state and recovery logic.

#### Optional Anki

Q: Typical use of SKIP LOCKED?
A: Concurrent workers claiming different rows without blocking.

</details>

---

<a id="db-lock-007"></a>

<details>
<summary><strong>DB-LOCK-007. When would you use SKIP LOCKED?</strong></summary>

#### Short answer

Use it for concurrent task picking when workers should not wait for rows locked by other workers.

#### Interview answer

Good cases include DB-backed job queues, small outbox pollers, task claiming, and batch processors where every row should be processed by one worker.

#### Deep dive

The usual design includes status columns, retry counters, timestamps, limited batch size, and indexes on the picking predicate and order columns.

#### Production angle

If you need high-throughput event streaming, replay, fan-out, and retention, use a broker like Kafka rather than turning PostgreSQL into a universal queue.

#### Traps / caveats

- Useful, but not Kafka/RabbitMQ replacement for every case.
- Requires stuck-job cleanup.
- Ordering is best-effort under concurrency.

#### Optional Anki

Q: What must accompany SKIP LOCKED queues?
A: State transitions, retry/recovery logic, and indexes.

</details>

<a id="db-lock-008"></a>

<details>
<summary><strong>DB-LOCK-008. What is NOWAIT?</strong></summary>

#### Short answer

`NOWAIT` makes a lock attempt fail immediately instead of waiting.

#### Interview answer

With `SELECT ... FOR UPDATE NOWAIT`, PostgreSQL returns an error if the row is already locked by another transaction.

#### Deep dive

Example:

```sql
SELECT *
FROM orders
WHERE id = 42
FOR UPDATE NOWAIT;
```

#### Production angle

Use it when fast failure is better than tying up request threads. Translate the error into retry, conflict response, or business-specific fallback.

#### Traps / caveats

- Not the same as SKIP LOCKED.
- Requires error handling.
- Can create retry storms if clients retry aggressively.

#### Optional Anki

Q: What does NOWAIT do?
A: Fails immediately if the lock cannot be acquired.

</details>

<a id="db-lock-009"></a>

<details>
<summary><strong>🧠 DB-LOCK-009. What are advisory locks?</strong></summary>

#### Short answer

Advisory locks are application-defined locks identified by numeric keys rather than rows or tables.

#### Interview answer

They are useful when the protected resource is logical, for example one import per tenant or one scheduled job instance.

#### Deep dive

PostgreSQL supports session-level and transaction-level advisory locks. Transaction-scoped locks are usually safer with connection pools because they release automatically at commit/rollback.

#### Production angle

Use advisory locks as cooperative coordination, not as a replacement for constraints. Key design and release semantics are part of correctness.

#### Traps / caveats

- PostgreSQL does not know your business invariant.
- Session-level locks can leak with pooled connections.
- Wrong key design can serialize unrelated work.

#### Optional Anki

Q: Are advisory locks tied to table rows?
A: No. They are application-defined locks by key.

</details>

---

<a id="db-lock-010"></a>

<details>
<summary><strong>🧠 DB-LOCK-010. When would you use advisory locks?</strong></summary>

#### Short answer

Use advisory locks for coarse-grained application mutual exclusion when a row lock does not naturally represent the resource.

#### Interview answer

Examples: only one cache rebuild per key, only one tenant-level import, only one billing cycle run, or preventing overlapping background tasks.

#### Deep dive

Transaction-scoped example:

```sql
SELECT pg_try_advisory_xact_lock(12345);
```

#### Production angle

Prefer `pg_try_advisory_xact_lock` when you want fast failure. Log the semantic meaning of lock keys so incidents are debuggable.

#### Traps / caveats

- Do not replace unique constraints with advisory locks.
- Avoid session locks unless release is guaranteed.
- Use stable key hashing.

#### Optional Anki

Q: Good advisory-lock use case?
A: One logical operation per business key.

</details>

<a id="db-lock-011"></a>

<details>
<summary><strong>DB-LOCK-011. What is a deadlock?</strong></summary>

#### Short answer

A deadlock is a cycle where transactions wait for locks held by each other, so none can proceed.

#### Interview answer

Example: transaction A locks row 1 and waits for row 2, while transaction B locks row 2 and waits for row 1.

#### Deep dive

PostgreSQL detects deadlocks and aborts one transaction. The application should retry the whole transaction if the operation is safe to retry.

#### Production angle

Prevent deadlocks with consistent lock ordering, short transactions, proper indexes, and avoiding external calls inside transactions.

#### Traps / caveats

- Increasing timeout does not solve deadlocks.
- The victim transaction is not predictable.
- Retry at transaction boundary.

#### Optional Anki

Q: How does PostgreSQL resolve a deadlock?
A: It aborts one transaction.

</details>

---

<a id="db-lock-012"></a>

<details>
<summary><strong>🧠 DB-LOCK-012. How does PostgreSQL detect and handle deadlocks?</strong></summary>

#### Short answer

PostgreSQL detects cycles in the lock wait graph and breaks the deadlock by aborting one transaction.

#### Interview answer

The aborted transaction releases its locks, allowing the other transactions to continue. Application code receives an error.

#### Deep dive

Detection is not immediate for every short wait; PostgreSQL checks after `deadlock_timeout` to avoid excessive detection overhead.

#### Production angle

Handle SQLSTATE `40P01` as a retryable failure only when the whole transaction can safely be retried from the beginning.

#### Traps / caveats

- Retrying only part of the transaction can break invariants.
- Frequent deadlocks indicate design issues.
- Log deadlock details.

#### Optional Anki

Q: What should app code do after a deadlock error?
A: Roll back and retry the whole transaction if safe.

</details>

<a id="db-lock-013"></a>

<details>
<summary><strong>DB-LOCK-013. How can you prevent deadlocks in application code?</strong></summary>

#### Short answer

Use consistent lock ordering, short transactions, proper indexes, and transaction-level retries.

#### Interview answer

If two code paths update the same resources in different orders, deadlocks become likely. Choose deterministic ordering, such as locking accounts by id.

#### Deep dive

Example transfer pattern:

```sql
SELECT *
FROM accounts
WHERE id IN (:from_id, :to_id)
ORDER BY id
FOR UPDATE;
```

#### Production angle

Also avoid holding locks while doing HTTP calls, file I/O, user interaction, or long computations.

#### Traps / caveats

- Lock order must be consistent across services.
- Indexes on foreign keys can reduce lock duration.
- Retries still need backoff and idempotency.

#### Optional Anki

Q: Main deadlock prevention idea?
A: Acquire locks in a consistent order.

</details>

<a id="db-lock-014"></a>

<details>
<summary><strong>DB-LOCK-014. What is lock_timeout?</strong></summary>

#### Short answer

`lock_timeout` aborts a statement if it waits too long to acquire a lock.

#### Interview answer

It applies to lock acquisition, not total query execution. If the lock is acquired quickly, a slow query will not be stopped by `lock_timeout`.

#### Deep dive

Useful for safer migrations:

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';
ALTER TABLE users ADD COLUMN risk_score integer;
COMMIT;
```

#### Production angle

Use it to avoid waiting silently behind locks and building a queue of blocked application queries.

#### Traps / caveats

- Different from `statement_timeout`.
- Global settings can hurt unrelated sessions.
- Timeout errors must be handled.

#### Optional Anki

Q: What does lock_timeout limit?
A: Time spent waiting to acquire a lock.

</details>

<a id="db-lock-015"></a>

<details>
<summary><strong>DB-LOCK-015. What is statement_timeout?</strong></summary>

#### Short answer

`statement_timeout` aborts a SQL statement that runs longer than the configured time.

#### Interview answer

It is a broad safety timeout for runaway queries. It is different from `lock_timeout`, which only covers waiting for locks.

#### Deep dive

In a Java service, DB statement timeout should be consistent with HTTP request timeout, connection-pool timeout, and retry policy.

#### Production angle

Use different settings for OLTP, reporting, migrations, and maintenance; one global value is often too blunt.

#### Traps / caveats

- Timeout cancels a statement, not necessarily the whole business operation cleanly.
- Timeouts do not replace optimization.
- Aggressive global timeouts can break legitimate jobs.

#### Optional Anki

Q: What does statement_timeout protect from?
A: Queries running longer than allowed.

</details>

<a id="db-lock-016"></a>

<details>
<summary><strong>DB-LOCK-016. What is idle_in_transaction_session_timeout?</strong></summary>

#### Short answer

`idle_in_transaction_session_timeout` terminates sessions that stay idle inside an open transaction too long.

#### Interview answer

It prevents forgotten transactions from holding snapshots, locks, and connections indefinitely.

#### Deep dive

Even if no significant lock is held, an open idle transaction can prevent VACUUM from removing dead tuples visible to that transaction.

#### Production angle

Use as a safety net, but also fix application transaction boundaries. Ensure the connection pool handles terminated connections.

#### Traps / caveats

- Can roll back open work.
- Not the same as ordinary idle session timeout.
- Can reduce bloat from forgotten transactions.

#### Optional Anki

Q: What does this timeout kill?
A: Sessions idle while inside an open transaction.

</details>

<a id="db-lock-017"></a>

<details>
<summary><strong>DB-LOCK-017. How would you investigate blocked queries?</strong></summary>

#### Short answer

Use `pg_stat_activity`, `pg_blocking_pids(pid)`, and `pg_locks` to find blocked sessions and blockers.

#### Interview answer

A useful first query:

```sql
SELECT pid, usename, application_name, client_addr,
       state, wait_event_type, wait_event,
       now() - xact_start AS xact_age,
       now() - query_start AS query_age,
       pg_blocking_pids(pid) AS blocking_pids,
       query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

#### Deep dive

After finding blockers, inspect their query, transaction age, state, app name, client address, and whether they are idle in transaction.

#### Production angle

Do not kill sessions blindly. Understand whether the blocker is a migration, business-critical transaction, app bug, or maintenance job.

#### Traps / caveats

- Blocked query is a symptom; the blocker is often root cause.
- The blocker can look harmless if it is idle.
- Prefer `pg_cancel_backend` when possible; `pg_terminate_backend` rolls back the session transaction.

#### Optional Anki

Q: PostgreSQL function for blockers?
A: `pg_blocking_pids(pid)`.

</details>

<a id="db-lock-018"></a>

<details>
<summary><strong>DB-LOCK-018. How would you find the transaction that blocks other transactions?</strong></summary>

#### Short answer

Map blocked PIDs to blocker PIDs with `pg_blocking_pids`, then join back to `pg_stat_activity`.

#### Interview answer

Example:

```sql
SELECT blocked.pid AS blocked_pid,
       blocked.application_name AS blocked_app,
       blocker.pid AS blocker_pid,
       blocker.usename AS blocker_user,
       blocker.application_name AS blocker_app,
       blocker.client_addr AS blocker_client,
       now() - blocker.xact_start AS blocker_xact_age,
       now() - blocker.query_start AS blocker_query_age,
       blocker.state AS blocker_state,
       blocker.wait_event_type AS blocker_wait_type,
       blocker.wait_event AS blocker_wait_event,
       blocker.query AS blocker_query
FROM pg_stat_activity blocked
JOIN LATERAL unnest(pg_blocking_pids(blocked.pid)) b(pid) ON true
JOIN pg_stat_activity blocker ON blocker.pid = b.pid;
```

#### Deep dive

Then correlate with application logs, request IDs, migration jobs, and deploy history to find which code path opened or held the transaction.

#### Production angle

In incident response, collect evidence before termination: PID, app name, user, client, query, state, wait event, and transaction age.

#### Traps / caveats

- Blocking chains can be multi-level.
- Terminating the wrong session can lose work.
- Prevent recurring issues with timeouts and shorter transactions.

#### Optional Anki

Q: How to find blocker details?
A: Join `pg_blocking_pids(pid)` with `pg_stat_activity`.

</details>
