# Aggregation, GROUP BY and window functions

---

<a id="db-agg-001"></a>

<details>
<summary><strong>DB-AGG-001. What is the difference between WHERE and HAVING?</strong></summary>

#### Short answer

`WHERE` filters rows before grouping; `HAVING` filters groups after aggregation.

#### Interview answer

Use `WHERE` for row-level filters and `HAVING` for conditions on aggregate results like `COUNT(*)` or `SUM(amount)`.

#### Deep dive

Logical order matters: `FROM/JOIN` produce rows, `WHERE` filters rows, `GROUP BY` creates groups, aggregates are computed, and `HAVING` filters groups.

```sql
SELECT customer_id, COUNT(*)
FROM orders
WHERE status = 'PAID'
GROUP BY customer_id
HAVING COUNT(*) > 10;
```

#### Production angle

Move non-aggregate filters from `HAVING` to `WHERE` when it preserves semantics; it reduces rows before grouping.

#### Traps / caveats

- `WHERE COUNT(*) > 10` is invalid.
- Using `HAVING` for simple filters can force unnecessary aggregation.
- Do not move conditions between WHERE and HAVING if it changes semantics.

#### Optional Anki

Q: What is the difference between WHERE and HAVING?
A: WHERE filters rows before grouping; HAVING filters groups after aggregation.

</details>

<details>
<summary><strong>DB-AGG-002. What does GROUP BY do?</strong></summary>

#### Short answer

`GROUP BY` groups rows by key so aggregates can be calculated per group.

#### Interview answer

Use it when you need one result row per customer, status, day, tenant, or another grouping key.

#### Deep dive

Selected columns must be either grouped or aggregated, unless PostgreSQL can prove functional dependency in specific cases.

```sql
SELECT status, COUNT(*)
FROM orders
GROUP BY status;
```

#### Production angle

Large grouping can require sort/hash aggregate and may spill to disk; check plan, rows, memory, and indexes.

#### Traps / caveats

- GROUP BY changes result cardinality.
- GROUP BY is not the same as DISTINCT intent.
- For detailed rows plus totals, window functions may be better.

#### Optional Anki

Q: What does GROUP BY do?
A: GROUP BY groups rows by key so aggregates can be calculated per group.

</details>

<a id="db-agg-003"></a>

<details>
<summary><strong>DB-AGG-003. When should you use HAVING?</strong></summary>

#### Short answer

Use `HAVING` when a filter depends on an aggregate or group-level value.

#### Interview answer

Typical examples are customers with more than 10 orders or days where revenue exceeds a threshold.

#### Deep dive

A `HAVING` predicate is evaluated after grouping, so it can reference aggregate expressions.

```sql
SELECT customer_id, SUM(amount)
FROM payments
GROUP BY customer_id
HAVING SUM(amount) > 10000;
```

#### Production angle

Prefer `WHERE` for row filters to reduce data before aggregation.

#### Traps / caveats

- Do not use HAVING as a replacement for WHERE.
- HAVING can be expensive if it forces grouping many unnecessary rows.
- Aliases and HAVING behavior can differ between DBMS dialects.

#### Optional Anki

Q: When should you use HAVING?
A: Use HAVING when a filter depends on an aggregate or group-level value.

</details>

<details>
<summary><strong>DB-AGG-004. What is the difference between GROUP BY and DISTINCT?</strong></summary>

#### Short answer

`DISTINCT` removes duplicate result rows; `GROUP BY` creates groups, usually for aggregation.

#### Interview answer

They can sometimes produce similar output, but communicate different intent.

#### Deep dive

PostgreSQL may implement both via sorting or hashing. `GROUP BY` also allows aggregate expressions per group.

```sql
SELECT DISTINCT status FROM orders;
SELECT status, COUNT(*) FROM orders GROUP BY status;
```

#### Production angle

If `DISTINCT` is used to hide duplicates from a join, first check whether the join condition is wrong.

#### Traps / caveats

- DISTINCT is not a universal performance fix.
- GROUP BY without aggregates can resemble DISTINCT but intent differs.
- Both can be expensive on large data.

#### Optional Anki

Q: What is the difference between GROUP BY and DISTINCT?
A: DISTINCT removes duplicate result rows; GROUP BY creates groups, usually for aggregation.

</details>

<details>
<summary><strong>DB-AGG-005. How does GROUP BY handle NULL?</strong></summary>

#### Short answer

For grouping, all `NULL` values in a grouping column belong to one group.

#### Interview answer

This differs from normal equality comparison where `NULL = NULL` is unknown.

#### Deep dive

Grouping treats nulls as not distinct for grouping purposes, so reports can contain one null bucket.

```sql
SELECT region, COUNT(*)
FROM customers
GROUP BY region;
```

#### Production angle

Decide whether NULL means unknown, not applicable, or unassigned; sometimes use `COALESCE` for clearer reports.

#### Traps / caveats

- Do not confuse GROUP BY behavior with equality comparison.
- A NULL bucket can hide data quality issues.
- COALESCE can make business meaning explicit.

#### Optional Anki

Q: How does GROUP BY handle NULL?
A: For grouping, all NULL values in a grouping column belong to one group.

</details>

<a id="db-agg-006"></a>

<details>
<summary><strong>DB-AGG-006. What are window functions?</strong></summary>

#### Short answer

Window functions calculate values across rows related to the current row while keeping individual rows in the result.

#### Interview answer

They use an `OVER` clause with optional `PARTITION BY`, `ORDER BY`, and frame definition.

#### Deep dive

Unlike `GROUP BY`, window functions do not collapse rows. PostgreSQL computes them over the virtual table produced after `FROM`, `WHERE`, grouping, and `HAVING`.

```sql
SELECT order_id, customer_id, amount,
       SUM(amount) OVER (PARTITION BY customer_id) AS customer_total
FROM orders;
```

#### Production angle

Useful for rankings, running totals, latest row per group, top-N per group, deduplication, and reports; they may require large sorts.

#### Traps / caveats

- Window functions cannot be used directly in WHERE.
- Default frames can surprise with last_value and running aggregates.
- ORDER BY inside OVER is separate from final ORDER BY.

#### Optional Anki

Q: What are window functions?
A: Window functions calculate values across rows related to the current row while keeping individual rows in the result.

</details>

<a id="db-agg-007"></a>

<details>
<summary><strong>DB-AGG-007. What is the difference between GROUP BY and window functions?</strong></summary>

#### Short answer

`GROUP BY` returns one row per group; window functions return row-level results plus calculations over related rows.

#### Interview answer

Use `GROUP BY` for summaries and window functions for contextual values on each row.

#### Deep dive

A window aggregate such as `SUM(x) OVER (...)` is calculated over a window but does not remove individual rows.

```sql
SELECT customer_id, SUM(amount) FROM orders GROUP BY customer_id;

SELECT order_id, customer_id, amount,
       SUM(amount) OVER (PARTITION BY customer_id)
FROM orders;
```

#### Production angle

Window functions can replace correlated subqueries/self-joins, but they may sort large data; verify with `EXPLAIN ANALYZE`.

#### Traps / caveats

- Do not expect GROUP BY to keep detail rows.
- Do not expect window functions to reduce rows.
- Filter window results in an outer query.

#### Optional Anki

Q: What is the difference between GROUP BY and window functions?
A: GROUP BY returns one row per group; window functions return row-level results plus calculations over related rows.

</details>

<a id="db-agg-008"></a>

<details>
<summary><strong>DB-AGG-008. What does ROW_NUMBER() do?</strong></summary>

#### Short answer

`ROW_NUMBER()` assigns a unique sequential number to rows inside a window partition.

#### Interview answer

It is commonly used for latest-row-per-group, top-N-per-group, pagination-like ranking, and deduplication.

#### Deep dive

The numbering depends entirely on `OVER (... ORDER BY ...)`. Add tie-breakers for deterministic results.

```sql
SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC, id DESC) AS rn
FROM orders;
```

#### Production angle

For APIs and batch jobs, unstable ordering can produce flaky results; include a unique key in ORDER BY when needed.

#### Traps / caveats

- ROW_NUMBER never gives same number to ties.
- Without unique order, ties are unstable.
- Use subquery/CTE to filter rn.

#### Optional Anki

Q: What does ROW_NUMBER() do?
A: ROW_NUMBER() assigns a unique sequential number to rows inside a window partition.

</details>

<a id="db-agg-009"></a>

<details>
<summary><strong>DB-AGG-009. What do RANK() and DENSE_RANK() do?</strong></summary>

#### Short answer

`RANK()` and `DENSE_RANK()` rank rows and give the same rank to ties.

#### Interview answer

`RANK()` leaves gaps after ties; `DENSE_RANK()` does not.

#### Deep dive

For values 100, 100, 90: `RANK()` gives 1,1,3; `DENSE_RANK()` gives 1,1,2.

```sql
SELECT score,
       RANK() OVER (ORDER BY score DESC),
       DENSE_RANK() OVER (ORDER BY score DESC)
FROM results;
```

#### Production angle

Choose based on business semantics: competition ranking vs dense category ranking.

#### Traps / caveats

- Ties are defined by ORDER BY values.
- Adding a tie-breaker may remove ties.
- Rank semantics must be clear for top-N.

#### Optional Anki

Q: What do RANK() and DENSE_RANK() do?
A: RANK() and DENSE_RANK() rank rows and give the same rank to ties.

</details>

<details>
<summary><strong>DB-AGG-010. What is the difference between RANK(), DENSE_RANK() and ROW_NUMBER()?</strong></summary>

#### Short answer

`ROW_NUMBER()` always creates unique positions. `RANK()` and `DENSE_RANK()` share ranks for ties; only `RANK()` leaves gaps.

#### Interview answer

Use `ROW_NUMBER()` when you need exactly N rows or deduplication. Use rank functions when ties should be preserved.

#### Deep dive

For scores 100,100,90: row_number may be 1,2,3; rank is 1,1,3; dense_rank is 1,1,2.

```sql
SELECT score,
       ROW_NUMBER() OVER (ORDER BY score DESC),
       RANK() OVER (ORDER BY score DESC),
       DENSE_RANK() OVER (ORDER BY score DESC)
FROM results;
```

#### Production angle

Product requirements for “top 3” must specify whether ties are included.

#### Traps / caveats

- ROW_NUMBER is not tie-aware.
- RANK leaves gaps.
- DENSE_RANK has no gaps.
- Tie-breaker changes semantics.

#### Optional Anki

Q: What is the difference between RANK(), DENSE_RANK() and ROW_NUMBER()?
A: ROW_NUMBER() always creates unique positions. RANK() and DENSE_RANK() share ranks for ties; only RANK() leaves gaps.

</details>

<a id="db-agg-011"></a>

<details>
<summary><strong>DB-AGG-011. What is PARTITION BY in a window function?</strong></summary>

#### Short answer

`PARTITION BY` splits rows into independent groups for window calculation.

#### Interview answer

For example, `PARTITION BY customer_id` ranks or aggregates separately for each customer.

#### Deep dive

If omitted, the whole result set is one partition.

```sql
ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC)
```

#### Production angle

Large partitions can require large sorts; suitable indexes on partition/order columns may help.

#### Traps / caveats

- It is not physical table partitioning.
- It does not reduce row count.
- No PARTITION BY means one global partition.

#### Optional Anki

Q: What is PARTITION BY in a window function?
A: PARTITION BY splits rows into independent groups for window calculation.

</details>

<a id="db-agg-012"></a>

<details>
<summary><strong>DB-AGG-012. What is ORDER BY inside OVER()?</strong></summary>

#### Short answer

It defines the order used by the window function, independently of the final query order.

#### Interview answer

Ranking, lag/lead, running totals, and frame-sensitive functions depend on this order.

#### Deep dive

Window `ORDER BY` is part of the window definition; final `ORDER BY` controls output order.

```sql
ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC, id DESC)
```

#### Production angle

Use deterministic tie-breakers for stable API responses.

#### Traps / caveats

- Window ORDER BY and final ORDER BY are different.
- Non-unique ordering can be unstable.
- Tie-breakers may change rank semantics.

#### Optional Anki

Q: What is ORDER BY inside OVER()?
A: It defines the order used by the window function, independently of the final query order.

</details>

<details>
<summary><strong>DB-AGG-015. How would you find the latest row per group?</strong></summary>

#### Short answer

Use `ROW_NUMBER()` partitioned by group and ordered by timestamp descending, then filter to `rn = 1`. In PostgreSQL, `DISTINCT ON` is also common.

#### Interview answer

`ROW_NUMBER()` is portable and flexible; `DISTINCT ON` is concise in PostgreSQL; `LATERAL ... LIMIT 1` can be efficient when you fetch the latest child row for a limited parent set.

#### Deep dive

Add a tie-breaker like `id DESC` so “latest” is deterministic. `DISTINCT ON` must be paired with an `ORDER BY` that starts with the distinct key.

```sql
SELECT * FROM (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC, id DESC) rn
  FROM orders o
) x WHERE rn = 1;

SELECT DISTINCT ON (customer_id) *
FROM orders
ORDER BY customer_id, created_at DESC, id DESC;
```

#### Production angle

For high-volume APIs, index by group and ordering columns, for example `(customer_id, created_at DESC, id DESC)`. If the parent set is already small, a `LATERAL` subquery with `LIMIT 1` can avoid ranking the whole child table.

#### Traps / caveats

- `MAX(created_at)` alone does not return the full row.
- Timestamps can tie; use a deterministic tie-breaker.
- `DISTINCT ON` is PostgreSQL-specific and depends on correct `ORDER BY`.

#### Optional Anki

Q: How would you find the latest row per group?
A: Use ROW_NUMBER(), PostgreSQL DISTINCT ON, or LATERAL LIMIT 1 depending on portability and data shape; always use deterministic ordering.

</details>

<details>
<summary><strong>DB-AGG-016. How would you find duplicates in a table?</strong></summary>

#### Short answer

Group by the business key and use `HAVING COUNT(*) > 1`.

#### Interview answer

First define what counts as duplicate: email, tenant+external_id, full row, or normalized key.

#### Deep dive

After finding duplicates, clean data and enforce the invariant with a unique constraint/index.

```sql
SELECT tenant_id, email, COUNT(*)
FROM users
GROUP BY tenant_id, email
HAVING COUNT(*) > 1;
```

#### Production angle

For soft deletes, use partial unique indexes to enforce uniqueness only for active rows.

#### Traps / caveats

- Duplicate definition is business-specific.
- NULL and case sensitivity matter.
- Finding duplicates is easier than safely removing them.

#### Optional Anki

Q: How would you find duplicates in a table?
A: Group by the business key and use HAVING COUNT(*) > 1.

</details>

<a id="db-agg-018"></a>

<details>
<summary><strong>DB-AGG-018. How would you calculate top-N records per group?</strong></summary>

#### Short answer

Use a ranking window function per group and filter in an outer query. For selected parent rows, a `LATERAL` subquery with `ORDER BY ... LIMIT N` can be better.

#### Interview answer

Use `ROW_NUMBER()` for exactly N rows; use `RANK()`/`DENSE_RANK()` if ties should be included. For API endpoints scoped to a small set of groups, use an index-backed lateral lookup.

#### Deep dive

The query needs a clear `PARTITION BY` and deterministic `ORDER BY`. Ranking the whole table is simple; lateral lookup is often faster when the outer query already restricts groups.

```sql
SELECT * FROM (
  SELECT p.*, ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY rating DESC, id) rn
  FROM products p
) x WHERE rn <= 3;

SELECT c.id, p.*
FROM categories c
JOIN LATERAL (
  SELECT *
  FROM products p
  WHERE p.category_id = c.id
  ORDER BY rating DESC, id
  LIMIT 3
) p ON true;
```

#### Production angle

For heavy dashboards, consider indexes such as `(category_id, rating DESC, id)`, precomputed rankings, or materialized views. Watch whether the plan sorts all rows or performs small index scans per group.

#### Traps / caveats

- Clarify tie behavior.
- Filter window results in an outer query.
- Global ranking can sort a lot of data; lateral lookup depends on a suitable index.

#### Optional Anki

Q: How would you calculate top-N records per group?
A: Use a ranking window function per group and filter in an outer query.

</details>
