# VACUUM, ANALYZE and maintenance

---

<a id="db-maint-001"></a>

<details>
<summary><strong>DB-MAINT-001. What is VACUUM in PostgreSQL?</strong></summary>

#### Short answer

`VACUUM` is PostgreSQL maintenance that cleans dead tuples, marks space reusable, updates visibility information, and helps prevent transaction ID wraparound.

#### Interview answer

Because MVCC keeps old tuple versions after `UPDATE` and `DELETE`, PostgreSQL needs VACUUM to remove versions that no transaction can see anymore.

#### Deep dive

Standard VACUUM usually does not shrink the physical file. It makes space reusable inside the relation and updates the visibility map.

#### Production angle

On busy OLTP tables, watch dead tuples, autovacuum activity, table bloat, transaction age, and tables where vacuum repeatedly fails to make progress.

#### Traps / caveats

- Routine VACUUM is normal, not emergency cleanup.
- VACUUM can be blocked by old snapshots.
- VACUUM FULL is a different, disruptive operation.

#### Optional Anki

Q: What does VACUUM clean?
A: Dead tuple versions no transaction can see.

</details>

<a id="db-maint-002"></a>

<details>
<summary><strong>DB-MAINT-002. Why does PostgreSQL need VACUUM?</strong></summary>

#### Short answer

PostgreSQL needs VACUUM because MVCC leaves old tuple versions behind after updates and deletes.

#### Interview answer

VACUUM recovers or reuses space, updates visibility map information, supports index-only scans, and protects against transaction ID wraparound through freezing.

#### Deep dive

VACUUM can also run together with ANALYZE or be accompanied by autovacuum ANALYZE to keep planner statistics fresh.

#### Production angle

If VACUUM cannot keep up, performance slowly degrades: more pages are read, indexes bloat, cache efficiency drops, and wraparound risk grows.

#### Traps / caveats

- VACUUM is essential in PostgreSQL.
- Autovacuum should almost never be disabled globally.
- Manual VACUUM does not fix bad transaction design.

#### Optional Anki

Q: Name two reasons for VACUUM.
A: Clean dead tuples and prevent transaction ID wraparound.

</details>

<a id="db-maint-003"></a>

<details>
<summary><strong>DB-MAINT-003. What is the difference between VACUUM and VACUUM FULL?</strong></summary>

#### Short answer

Regular VACUUM marks dead-tuple space reusable; VACUUM FULL rewrites the table to physically reclaim disk space.

#### Interview answer

`VACUUM` can normally run with reads and writes. `VACUUM FULL` requires a strong exclusive lock and is much more disruptive.

#### Deep dive

VACUUM FULL creates a compact rewritten relation. This needs time, I/O, extra disk space during the operation, and usually a maintenance window.

#### Production angle

In production, prefer autovacuum tuning, partitioning, batched deletes, or online rebuild strategies before choosing VACUUM FULL.

#### Traps / caveats

- VACUUM FULL can cause downtime.
- Regular VACUUM usually does not return disk to OS.
- Frequent VACUUM FULL suggests root-cause problems.

#### Optional Anki

Q: Which one physically shrinks table files?
A: VACUUM FULL.

</details>

<a id="db-maint-004"></a>

<details>
<summary><strong>DB-MAINT-004. What is autovacuum?</strong></summary>

#### Short answer

Autovacuum is PostgreSQL’s background system that automatically runs VACUUM and ANALYZE when tables need maintenance.

#### Interview answer

It monitors table changes and starts workers based on thresholds for inserts, updates, deletes, and transaction ID age. It also runs anti-wraparound maintenance even if normal cleanup thresholds are not met.

#### Deep dive

Important settings include `autovacuum_vacuum_threshold`, `autovacuum_vacuum_scale_factor`, `autovacuum_analyze_threshold`, `autovacuum_analyze_scale_factor`, cost delay/limit, max workers, and per-table storage parameters.

#### Production angle

Large or hot tables often need table-specific tuning because default scale factors may trigger too late. Example:

```sql
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_threshold = 5000,
  autovacuum_analyze_scale_factor = 0.01
);
```

#### Traps / caveats

- Autovacuum can be running but still insufficient.
- Long transactions can prevent useful cleanup.
- Per-table settings should be based on write rate and table size, not copied blindly.
- Too aggressive autovacuum can create I/O pressure.

#### Optional Anki

Q: What does autovacuum automate?
A: VACUUM and ANALYZE, including anti-wraparound maintenance.

</details>

<a id="db-maint-005"></a>

<details>
<summary><strong>DB-MAINT-005. What can happen if autovacuum does not keep up?</strong></summary>

#### Short answer

Dead tuples accumulate, table and index bloat grow, queries read more pages, and transaction ID wraparound pressure increases.

#### Interview answer

Symptoms often appear gradually: higher I/O, bigger indexes, lower cache efficiency, slower scans, unstable latency, and more heap fetches for index-only scans.

#### Deep dive

Autovacuum can fail to keep up because of long transactions, too-conservative thresholds, too few workers, heavy update/delete workload, or replication slots holding old horizons.

#### Production angle

Investigate per-table dead tuples, last autovacuum time, autovacuum logs, table age, long-running transactions, and write rate.

#### Traps / caveats

- One manual VACUUM may not fix the root cause.
- A single hot table can need custom settings.
- Ignoring wraparound pressure can become an outage.

#### Optional Anki

Q: What is a sign autovacuum is not keeping up?
A: Growing dead tuples/bloat and slow scans.

</details>

<a id="db-maint-006"></a>

<details>
<summary><strong>DB-MAINT-006. What is table bloat?</strong></summary>

#### Short answer

Table bloat is wasted space inside a table caused by dead/reusable tuples and page fragmentation.

#### Interview answer

After many updates/deletes, a table file can contain many pages with little live data. Regular VACUUM can reuse space but usually does not shrink the file.

#### Deep dive

Bloat hurts cache efficiency and makes scans read more pages for the same useful data.

#### Production angle

Reduce it with autovacuum tuning, shorter transactions, batching, partition lifecycle management, fillfactor, and avoiding unnecessary updates.

#### Traps / caveats

- A large table is not necessarily bloated.
- VACUUM FULL reclaims disk but locks heavily.
- Partition drop/detach is often better for old-data cleanup.

#### Optional Anki

Q: Why does table bloat hurt performance?
A: More pages must be read for the same live data.

</details>

<a id="db-maint-008"></a>

<details>
<summary><strong>DB-MAINT-008. How can you detect table or index bloat?</strong></summary>

#### Short answer

Use size metrics, dead tuple estimates, autovacuum history, index statistics, and extensions like `pgstattuple` where available.

#### Interview answer

Start with simple signals, then confirm with size and inspection tools:

```sql
SELECT relname, n_live_tup, n_dead_tup,
       last_autovacuum, last_vacuum,
       pg_total_relation_size(relid) AS total_bytes
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;
```

#### Deep dive

Compare `pg_relation_size`, `pg_total_relation_size`, index sizes, row counts, and workload patterns. Extensions such as `pgstattuple` or `pgstattuple_approx` can inspect bloat more directly, but they add cost and may not be available in every managed database.

#### Production angle

Confirm bloat before running disruptive cleanup. In managed databases, use vendor metrics and supported extensions/tools.

#### Traps / caveats

- `n_dead_tup` is an estimate.
- Big size alone is not proof of bloat.
- Exact inspection can be expensive on large relations.
- Cleanup can require locks, time, and disk space.

#### Optional Anki

Q: Is `n_dead_tup` exact?
A: No, it is an estimate.

</details>

<a id="db-maint-009"></a>

<details>
<summary><strong>DB-MAINT-009. What is ANALYZE?</strong></summary>

#### Short answer

`ANALYZE` collects table statistics used by the PostgreSQL planner.

#### Interview answer

It samples data and records information such as null fraction, distinct values, most common values, frequencies, and histograms.

#### Deep dive

The planner uses these statistics for selectivity estimates, row count estimates, scan choice, join order, and join algorithm selection.

#### Production angle

Run ANALYZE after large data loads, mass updates/deletes, migrations that change distribution, or when EXPLAIN shows bad estimated-vs-actual rows.

#### Traps / caveats

- ANALYZE does not clean dead tuples.
- Statistics are estimates based on sampling.
- Stale stats can make useful indexes look bad.

#### Optional Anki

Q: What does ANALYZE update?
A: Planner statistics.

</details>

---

<a id="db-maint-010"></a>

<details>
<summary><strong>DB-MAINT-010. Why does PostgreSQL need ANALYZE?</strong></summary>

#### Short answer

PostgreSQL needs ANALYZE so the cost-based planner can estimate how much data a query will process.

#### Interview answer

Without statistics, the planner can choose bad indexes, bad join order, wrong join algorithms, or underestimate memory-heavy operations.

#### Deep dive

A query’s cost depends heavily on value distribution and selectivity, not only table size.

#### Production angle

Run or wait for ANALYZE after bulk changes. For critical query regressions, compare `EXPLAIN (ANALYZE, BUFFERS)` before and after.

#### Traps / caveats

- Not a replacement for indexes.
- Autovacuum ANALYZE may not run immediately.
- Bad estimates can be caused by correlations, not just stale stats.

#### Optional Anki

Q: Why does planner need stats?
A: To estimate selectivity and row counts.

</details>

<a id="db-maint-011"></a>

<details>
<summary><strong>DB-MAINT-011. How does ANALYZE affect query plans?</strong></summary>

#### Short answer

ANALYZE changes planner estimates, which can change scan type, join order, join algorithm, sorting, and memory choices.

#### Interview answer

If statistics show that a predicate is highly selective, PostgreSQL may use an index. If it returns most rows, a sequential scan may be cheaper.

#### Deep dive

Better statistics can fix a bad plan, but they can also reveal that an old index is no longer useful for current data distribution.

#### Production angle

If a plan changes after ANALYZE, inspect estimated vs actual rows, chosen indexes, join types, and parameter values.

#### Traps / caveats

- A plan change is not always a regression.
- Bad plans often start with bad row estimates.
- Data skew may require higher stats or extended stats.

#### Optional Anki

Q: What plan symptom suggests stale stats?
A: Estimated rows differ greatly from actual rows.

</details>

---

<a id="db-maint-012"></a>

<details>
<summary><strong>DB-MAINT-012. Why can stale statistics cause bad query plans?</strong></summary>

#### Short answer

Stale statistics give the planner wrong row count and selectivity estimates, so it can choose the wrong plan.

#### Interview answer

If PostgreSQL expects 100 rows but gets 10 million, a nested loop or repeated index lookup can become catastrophic.

#### Deep dive

Staleness often appears after bulk loads, mass updates/deletes, tenant growth, seasonal data changes, or too-high autovacuum analyze thresholds.

#### Production angle

In production slow-query debugging, check estimated vs actual rows first. If the mismatch is huge, run ANALYZE and inspect data distribution.

#### Traps / caveats

- Adding an index may not help if estimates are wrong.
- Prepared statement generic plans can amplify selectivity issues.
- Stale stats affect joins too.

#### Optional Anki

Q: Classic sign of stale stats?
A: Huge mismatch between estimated and actual rows.

</details>

<a id="db-maint-013"></a>

<details>
<summary><strong>🧠 DB-MAINT-013. What is default_statistics_target?</strong></summary>

#### Short answer

`default_statistics_target` controls the default detail level for column statistics collected by ANALYZE.

#### Interview answer

Higher values allow larger samples and more detailed most-common-value lists and histograms.

#### Deep dive

You can override it per column using `ALTER TABLE ... ALTER COLUMN ... SET STATISTICS`.

#### Production angle

Increase it selectively for important skewed columns, not blindly for the whole database.

#### Traps / caveats

- Higher is not always better.
- Increases ANALYZE cost and metadata.
- Extended statistics may be more appropriate for correlated columns.

#### Optional Anki

Q: What does statistics target affect?
A: The amount/detail of planner statistics.

</details>

<a id="db-maint-014"></a>

<details>
<summary><strong>🧠 DB-MAINT-014. When would you increase statistics target?</strong></summary>

#### Short answer

Increase statistics target when important queries have bad estimates because a column’s data distribution is skewed or complex.

#### Interview answer

Typical cases include skewed status values, heavy tenants, timestamps with uneven distribution, or rare values that are important for query plans.

#### Deep dive

Example:

```sql
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;
```

#### Production angle

Measure before and after with `EXPLAIN (ANALYZE, BUFFERS)`. The goal is better estimates and plan stability.

#### Traps / caveats

- Not the first fix for every slow query.
- Missing indexes and bad query shape can still be root causes.
- Use extended stats for correlations.

#### Optional Anki

Q: When increase statistics target?
A: When bad estimates come from skewed data on important columns.

</details>

<a id="db-maint-015"></a>

<details>
<summary><strong>🧠 DB-MAINT-015. What are extended statistics?</strong></summary>

#### Short answer

Extended statistics are planner statistics over combinations of columns.

#### Interview answer

They help when predicates use correlated columns, when multi-column distinct counts matter, or when most-common-value combinations are important.

#### Deep dive

PostgreSQL supports extended statistic kinds such as `dependencies`, `ndistinct`, and `mcv`. Example:

```sql
CREATE STATISTICS orders_tenant_status_stats
  (dependencies, ndistinct, mcv)
ON tenant_id, status
FROM orders;
ANALYZE orders;
```

#### Production angle

Use them when the planner assumes independent predicates but the columns are actually dependent.

#### Traps / caveats

- They improve estimates, not physical access.
- They do not replace indexes.
- Choose statistic kinds based on the estimation problem.
- Run ANALYZE after creating them.

#### Optional Anki

Q: What problem do extended stats solve?
A: Bad estimates for correlated columns.

</details>

---

<a id="db-maint-016"></a>

<details>
<summary><strong>🧠 DB-MAINT-016. When would you create extended statistics?</strong></summary>

#### Short answer

Create extended statistics when important queries filter/group by multiple correlated columns and estimates are bad.

#### Interview answer

Example: `tenant_id` and `status` may not be independent. Multiplying single-column selectivities can produce a wrong estimate.

#### Deep dive

Extended statistics are most useful when `EXPLAIN (ANALYZE, BUFFERS)` shows estimated rows far from actual rows for multi-column predicates.

#### Production angle

After creation, run ANALYZE and verify that row estimates and plan choices improve.

#### Traps / caveats

- Not automatically created for composite indexes.
- Do not use them instead of a needed composite index.
- They add statistics complexity.

#### Optional Anki

Q: Extended stats help when columns are what?
A: Correlated or jointly distributed.

</details>

<a id="db-maint-017"></a>

<details>
<summary><strong>🧠 DB-MAINT-017. What is REINDEX?</strong></summary>

#### Short answer

`REINDEX` rebuilds an index from table data.

#### Interview answer

It is used for bloated, corrupted, or otherwise problematic indexes. A fresh index structure can reduce bloat.

#### Deep dive

Plain REINDEX can block operations. PostgreSQL also supports concurrent rebuilds to reduce production impact.

#### Production angle

Use after measuring bloat or when corruption is suspected, and fix the workload that caused repeated bloat.

#### Traps / caveats

- REINDEX is not query optimization by itself.
- Needs disk and time.
- Concurrent variants can leave invalid indexes after failure.

#### Optional Anki

Q: What does REINDEX do?
A: Rebuilds an index.

</details>

---

<a id="db-maint-018"></a>

<details>
<summary><strong>🧠 DB-MAINT-018. When would you use REINDEX CONCURRENTLY?</strong></summary>

#### Short answer

Use `REINDEX CONCURRENTLY` when you need to rebuild an index in production while minimizing blocking.

#### Interview answer

It builds a replacement index with less disruption than plain REINDEX, but it usually takes longer and needs extra disk space.

#### Deep dive

Concurrent rebuilds have more phases and can fail due to interfering transactions, so monitoring and cleanup are important.

#### Production angle

Run during lower traffic if possible, check disk space, monitor replication lag, and have a rollback/cleanup plan.

#### Traps / caveats

- Concurrent does not mean zero-impact.
- Can be slower than plain REINDEX.
- Failure can require invalid-index cleanup.

#### Optional Anki

Q: Why use REINDEX CONCURRENTLY?
A: To rebuild indexes with less blocking.

</details>

<a id="db-maint-019"></a>

<details>
<summary><strong>🧠 DB-MAINT-019. What is CLUSTER in PostgreSQL?</strong></summary>

#### Short answer

`CLUSTER` physically rewrites a table in the order of an index.

#### Interview answer

It can improve locality for queries that read ranges in index order because related heap rows are stored closer together.

#### Deep dive

Example:

```sql
CLUSTER orders USING idx_orders_created_at;
```

#### Production angle

CLUSTER is not automatically maintained. New inserts and updates gradually destroy the physical ordering.

#### Traps / caveats

- Not the same as creating an index.
- Rewrites and locks the table.
- Ordering decays over time.

#### Optional Anki

Q: What does CLUSTER do?
A: Rewrites a table physically ordered by an index.

</details>

---

<a id="db-maint-020"></a>

<details>
<summary><strong>🧠 DB-MAINT-020. When can CLUSTER help, and what are its downsides?</strong></summary>

#### Short answer

CLUSTER can help when queries frequently scan ranges in the same order as an index and benefit from heap locality.

#### Interview answer

Example: large time-ordered data that is usually read by time range can sometimes benefit from physical ordering.

#### Deep dive

Downsides: table rewrite, strong locks, extra I/O/disk, no automatic maintenance of order, and limited benefit for highly changing data.

#### Production angle

Consider indexes, BRIN, partitioning, caching, or query redesign before choosing CLUSTER in production.

#### Traps / caveats

- Do not CLUSTER just because a table is slow.
- Requires planning/maintenance window for many systems.
- Partitioning is often cleaner for time-series lifecycle.

#### Optional Anki

Q: Main CLUSTER downside?
A: It rewrites/locks the table and order is not maintained automatically.

</details>
