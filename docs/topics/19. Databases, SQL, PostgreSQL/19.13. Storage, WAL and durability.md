# Storage, WAL and durability

---

<a id="db-wal-001"></a>

<details>
<summary><strong>DB-WAL-001. What is WAL in PostgreSQL?</strong></summary>

#### Short answer

WAL, or Write-Ahead Log, is PostgreSQL’s append-only log of changes written before data pages are considered durable.

#### Interview answer

The main idea is write the change to WAL first; data pages can be flushed later. After a crash, PostgreSQL replays WAL to restore a consistent state.

#### Deep dive

WAL is central to crash recovery, durability, physical replication, point-in-time recovery, and write performance. WAL position is tracked with LSNs, and WAL files live under `pg_wal`.

#### Production angle

For Java backend systems, WAL explains why heavy writes, many indexes, large rows, bulk updates, and full-page writes can affect disk I/O, WAL storage, backups/PITR, and replication lag.

#### Traps / caveats

- WAL is not an application log.
- More indexes often mean more WAL on writes.
- Replication slots and archiving problems can retain WAL files.
- Commit durability depends on WAL-related settings.

#### Optional Anki

Q: What is WAL used for?
A: Crash recovery, durability, replication, and PITR.

</details>

<a id="db-wal-002"></a>

<details>
<summary><strong>DB-WAL-002. Why does PostgreSQL use Write-Ahead Logging?</strong></summary>

#### Short answer

PostgreSQL uses WAL to make commits durable without flushing every changed data page immediately.

#### Interview answer

Sequentially writing WAL is usually cheaper than random writes to many table and index pages. Data pages can be written later by background writers and checkpoints.

#### Deep dive

During recovery, PostgreSQL starts from a checkpoint and replays WAL records to redo committed changes that were not fully flushed to data files.

#### Production angle

WAL is a performance and durability trade-off surface. Monitor WAL generation rate, checkpoint frequency, disk throughput, replication lag, and retained WAL size. Useful starting points are `pg_stat_wal`, replication slot state, archive status, and LSN lag such as `pg_wal_lsn_diff`.

#### Traps / caveats

- WAL reduces random data-page fsync pressure, but writes are not free.
- Unlogged tables have different durability and replication trade-offs.
- Bulk operations can generate huge WAL and affect PITR/replicas.

#### Optional Anki

Q: Why write ahead?
A: WAL must be durable before related data-page changes are considered safe.

</details>

<a id="db-wal-003"></a>

<details>
<summary><strong>DB-WAL-003. How does WAL help with crash recovery?</strong></summary>

#### Short answer

After a crash, PostgreSQL replays WAL records from the last checkpoint to restore committed changes.

#### Interview answer

At commit, required WAL is made durable according to settings. The actual heap/index pages may still be dirty in memory and flushed later.

#### Deep dive

Recovery uses WAL as redo information. It does not rerun application code; it re-applies low-level database changes.

#### Production angle

Checkpoint tuning affects recovery time. Longer intervals can smooth write load but increase WAL replay time after crash; shorter intervals can increase full-page writes and latency spikes.

#### Traps / caveats

- WAL replay is redo, not business replay.
- Durability depends on `fsync` and `synchronous_commit`.
- Replication also consumes WAL.

#### Optional Anki

Q: What does PostgreSQL replay after crash?
A: WAL records since the recovery checkpoint.

</details>

<a id="db-wal-007"></a>

<details>
<summary><strong>🧠 DB-WAL-007. What is synchronous_commit?</strong></summary>

#### Short answer

`synchronous_commit` controls how much WAL durability work must complete before PostgreSQL reports commit success.

#### Interview answer

With default local durable behavior, commit waits for local WAL flush. With `off`, commit can return before WAL is safely flushed.

#### Deep dive

With synchronous replication, settings like `remote_write`, `on`, and `remote_apply` also control waiting for standby WAL write, flush, or apply progress.

#### Production angle

For non-critical events, `synchronous_commit=off` can reduce latency with a small acknowledged-data-loss window. Do not use it for critical state unless the risk is accepted.

#### Traps / caveats

- `off` does not mean database inconsistency, but recent acknowledged commits can be lost.
- Replication configuration changes remote meanings.
- Can be set per transaction for non-critical work.

#### Optional Anki

Q: Risk of synchronous_commit=off?
A: Recent commits reported as successful can be lost after crash.

</details>

<a id="db-wal-008"></a>

<details>
<summary><strong>🧠 DB-WAL-008. What can be lost if synchronous_commit is disabled?</strong></summary>

#### Short answer

Recently acknowledged committed transactions can be lost if the server crashes before their WAL is flushed.

#### Interview answer

The database should recover to a consistent state, but those transactions may look as if they never committed.

#### Deep dive

This is a durability trade-off, not a logical consistency feature. It reduces commit latency but allows a small window of data loss.

#### Production angle

Use only for regeneratable telemetry, caches, or non-critical events where possible loss is explicitly accepted.

#### Traps / caveats

- Not appropriate for payments/orders unless business accepts risk.
- Retries can create duplicates if commit outcome is ambiguous.
- Different from replica lag.

#### Optional Anki

Q: What can be lost?
A: Recently acknowledged commits not yet flushed to WAL durably.

</details>

<details>
<summary><strong>DB-WAL-014. How can very large rows affect performance?</strong></summary>

#### Short answer

Very large rows increase I/O, memory pressure, WAL volume, vacuum cost, replication lag, and network transfer.

#### Interview answer

Even if values are TOASTed, reading a large column can require detoasting and extra page reads. Updating it writes more WAL and creates more maintenance work.

#### Deep dive

Large rows also make ORM `SELECT *` patterns expensive and can turn simple API endpoints into storage-heavy operations.

#### Production angle

Return only needed columns, split large blobs/documents if necessary, use object storage for large binary files, and benchmark JSONB-heavy designs.

#### Traps / caveats

- Large rows can make simple queries unexpectedly slow.
- Large values increase backup and replication cost.
- Indexing huge expressions/documents needs careful design.

#### Optional Anki

Q: Why avoid SELECT * with large columns?
A: It may force reading/detoasting values the request does not need.

</details>
