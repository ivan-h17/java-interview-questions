# Storage, WAL and durability

---

<a id="db-wal-001"></a>

<details>
<summary><strong>DB-WAL-001. What is WAL in PostgreSQL?</strong></summary>

#### Short answer

WAL, or Write-Ahead Log, is PostgreSQL’s append-only log of changes written before data pages are considered durable.

#### Interview answer

The main idea is write the change to WAL first; data pages can be flushed later. After a crash, PostgreSQL replays WAL to restore a consistent state.

#### Deep dive

WAL is central to crash recovery, durability, physical replication, point-in-time recovery, and write performance. WAL position is tracked with LSNs, and WAL files live under `pg_wal`.

#### Production angle

For Java backend systems, WAL explains why heavy writes, many indexes, large rows, bulk updates, and full-page writes can affect disk I/O, WAL storage, backups/PITR, and replication lag.

#### Traps / caveats

- WAL is not an application log.
- More indexes often mean more WAL on writes.
- Replication slots and archiving problems can retain WAL files.
- Commit durability depends on WAL-related settings.

#### Optional Anki

Q: What is WAL used for?
A: Crash recovery, durability, replication, and PITR.

</details>

<a id="db-wal-002"></a>

<details>
<summary><strong>DB-WAL-002. Why does PostgreSQL use Write-Ahead Logging?</strong></summary>

#### Short answer

PostgreSQL uses WAL to make commits durable without flushing every changed data page immediately.

#### Interview answer

Sequentially writing WAL is usually cheaper than random writes to many table and index pages. Data pages can be written later by background writers and checkpoints.

#### Deep dive

During recovery, PostgreSQL starts from a checkpoint and replays WAL records to redo committed changes that were not fully flushed to data files.

#### Production angle

WAL is a performance and durability trade-off surface. Monitor WAL generation rate, checkpoint frequency, disk throughput, replication lag, and retained WAL size. Useful starting points are `pg_stat_wal`, replication slot state, archive status, and LSN lag such as `pg_wal_lsn_diff`.

#### Traps / caveats

- WAL reduces random data-page fsync pressure, but writes are not free.
- Unlogged tables have different durability and replication trade-offs.
- Bulk operations can generate huge WAL and affect PITR/replicas.

#### Optional Anki

Q: Why write ahead?
A: WAL must be durable before related data-page changes are considered safe.

</details>

<a id="db-wal-003"></a>

<details>
<summary><strong>DB-WAL-003. How does WAL help with crash recovery?</strong></summary>

#### Short answer

After a crash, PostgreSQL replays WAL records from the last checkpoint to restore committed changes.

#### Interview answer

At commit, required WAL is made durable according to settings. The actual heap/index pages may still be dirty in memory and flushed later.

#### Deep dive

Recovery uses WAL as redo information. It does not rerun application code; it re-applies low-level database changes.

#### Production angle

Checkpoint tuning affects recovery time. Longer intervals can smooth write load but increase WAL replay time after crash; shorter intervals can increase full-page writes and latency spikes.

#### Traps / caveats

- WAL replay is redo, not business replay.
- Durability depends on `fsync` and `synchronous_commit`.
- Replication also consumes WAL.

#### Optional Anki

Q: What does PostgreSQL replay after crash?
A: WAL records since the recovery checkpoint.

</details>

<a id="db-wal-004"></a>

<details>
<summary><strong>🧠 DB-WAL-004. What is a checkpoint?</strong></summary>

#### Short answer

A checkpoint is a point where PostgreSQL ensures dirty data pages up to a WAL position are written to disk.

#### Interview answer

Checkpoints limit crash recovery work: after a checkpoint, PostgreSQL normally does not need to replay older WAL for crash recovery.

#### Deep dive

During a checkpoint, many dirty pages may be written. PostgreSQL spreads this work according to checkpoint settings, but it can still create I/O pressure and interact with full-page writes.

#### Production angle

Frequent checkpoint warnings, write latency spikes, or high WAL churn mean you should review `checkpoint_timeout`, `max_wal_size`, `checkpoint_completion_target`, storage latency, and WAL generation rate.

#### Traps / caveats

- Checkpoint is not transaction commit.
- Too-frequent checkpoints can hurt latency.
- Too-infrequent checkpoints can increase recovery time.

#### Optional Anki

Q: What does a checkpoint reduce?
A: WAL replay needed during crash recovery.

</details>

<a id="db-wal-005"></a>

<details>
<summary><strong>🧠 DB-WAL-005. How do checkpoints affect performance?</strong></summary>

#### Short answer

Checkpoints affect performance by flushing dirty pages and influencing WAL volume and recovery time.

#### Interview answer

Too frequent checkpoints cause repeated write pressure and more full-page writes after each checkpoint. Too rare checkpoints can require more WAL storage and longer crash recovery.

#### Deep dive

Settings such as `checkpoint_timeout`, `max_wal_size`, `min_wal_size`, and `checkpoint_completion_target` determine checkpoint frequency and smoothing. `wal_compression` can reduce full-page image volume at CPU cost.

#### Production angle

Monitor checkpoint frequency, buffers written by checkpoints, WAL generation, storage latency, and application latency around checkpoints. Depending on PostgreSQL version, use checkpoint/WAL stats views such as `pg_stat_checkpointer`, `pg_stat_bgwriter`, and `pg_stat_wal`.

#### Traps / caveats

- Tuning is storage-dependent.
- Bulk loads can trigger checkpoint pressure and large WAL bursts.
- Increasing `max_wal_size` can reduce checkpoint frequency but may increase crash recovery time.
- Frequent checkpoints amplify full-page writes.

#### Optional Anki

Q: Why can checkpoints create latency spikes?
A: They flush dirty pages and create write I/O.

</details>

<a id="db-wal-006"></a>

<details>
<summary><strong>🧠 DB-WAL-006. What is fsync, and why does it matter?</strong></summary>

#### Short answer

`fsync` makes PostgreSQL ask the OS/storage to flush data to durable media.

#### Interview answer

With `fsync` enabled, PostgreSQL relies on sync calls to make WAL/data durable. Turning it off may improve speed but risks unrecoverable corruption after a crash.

#### Deep dive

`fsync=off` is generally acceptable only for disposable test data or databases that can be rebuilt.

#### Production angle

In production, fix write latency via storage, batching, WAL/checkpoint tuning, and workload design — not by disabling durability.

#### Traps / caveats

- Do not confuse `fsync=off` with `synchronous_commit=off`.
- `fsync=off` can corrupt the database after crash.
- Storage reliability matters.

#### Optional Anki

Q: Is fsync=off safe for production?
A: No, it risks data corruption after crashes.

</details>

<a id="db-wal-007"></a>

<details>
<summary><strong>🧠 DB-WAL-007. What is synchronous_commit?</strong></summary>

#### Short answer

`synchronous_commit` controls how much WAL durability work must complete before PostgreSQL reports commit success.

#### Interview answer

With default local durable behavior, commit waits for local WAL flush. With `off`, commit can return before WAL is safely flushed.

#### Deep dive

With synchronous replication, settings like `remote_write`, `on`, and `remote_apply` also control waiting for standby WAL write, flush, or apply progress.

#### Production angle

For non-critical events, `synchronous_commit=off` can reduce latency with a small acknowledged-data-loss window. Do not use it for critical state unless the risk is accepted.

#### Traps / caveats

- `off` does not mean database inconsistency, but recent acknowledged commits can be lost.
- Replication configuration changes remote meanings.
- Can be set per transaction for non-critical work.

#### Optional Anki

Q: Risk of synchronous_commit=off?
A: Recent commits reported as successful can be lost after crash.

</details>

<a id="db-wal-008"></a>

<details>
<summary><strong>🧠 DB-WAL-008. What can be lost if synchronous_commit is disabled?</strong></summary>

#### Short answer

Recently acknowledged committed transactions can be lost if the server crashes before their WAL is flushed.

#### Interview answer

The database should recover to a consistent state, but those transactions may look as if they never committed.

#### Deep dive

This is a durability trade-off, not a logical consistency feature. It reduces commit latency but allows a small window of data loss.

#### Production angle

Use only for regeneratable telemetry, caches, or non-critical events where possible loss is explicitly accepted.

#### Traps / caveats

- Not appropriate for payments/orders unless business accepts risk.
- Retries can create duplicates if commit outcome is ambiguous.
- Different from replica lag.

#### Optional Anki

Q: What can be lost?
A: Recently acknowledged commits not yet flushed to WAL durably.

</details>

<a id="db-wal-009"></a>

<details>
<summary><strong>🧠 DB-WAL-009. What is full_page_writes?</strong></summary>

#### Short answer

`full_page_writes` writes a full image of a page to WAL the first time that page is modified after a checkpoint.

#### Interview answer

It protects against torn pages: if a crash happens during a partial page write, WAL contains a full page image that can restore the page.

#### Deep dive

The cost is more WAL volume after checkpoints, especially with write-heavy workloads and frequent checkpoints.

#### Production angle

Normally keep it enabled. If WAL volume is too high, investigate checkpoint frequency, WAL compression, workload, and storage before disabling safety features.

#### Traps / caveats

- Disabling it can risk page corruption after crash.
- Frequent checkpoints increase full-page image churn.
- WAL compression can help in some systems.

#### Optional Anki

Q: What does full_page_writes protect against?
A: Torn pages.

</details>

<a id="db-wal-010"></a>

<details>
<summary><strong>DB-WAL-010. What is the difference between WAL and table data files?</strong></summary>

#### Short answer

WAL is the sequential redo log of changes; table data files are the actual heap and index pages.

#### Interview answer

A transaction can commit after required WAL is durable even if the modified table/index pages are still dirty in memory.

#### Deep dive

Data files are flushed later by background writers and checkpoints. WAL lets PostgreSQL recover changes if a crash happens before that flush.

#### Production angle

This separation is why WAL disk, data disk, checkpoint tuning, and replication lag must be analyzed separately.

#### Traps / caveats

- Do not delete WAL files manually.
- Data files alone are not enough for crash recovery.
- WAL volume grows with writes and indexes.

#### Optional Anki

Q: What is WAL relative to data files?
A: WAL is redo log; data files store heap/index pages.

</details>

<a id="db-wal-011"></a>

<details>
<summary><strong>🧠 DB-WAL-011. What is a PostgreSQL page?</strong></summary>

#### Short answer

A PostgreSQL page is a fixed-size storage block, commonly 8 KB, used for heap and index data.

#### Interview answer

Tables and indexes are stored as pages. A heap page contains tuple data and page metadata; index pages contain index-specific structures.

#### Deep dive

A normal tuple cannot span pages; large variable-length values are handled by TOAST.

#### Production angle

Page-level behavior affects cache locality, bloat, fillfactor, heap fetches, WAL full-page images, and random/sequential I/O.

#### Traps / caveats

- Page size is usually fixed at build time.
- Large values can trigger TOAST.
- Bloat means more pages for the same useful data.

#### Optional Anki

Q: Common PostgreSQL page size?
A: 8 KB in typical builds.

</details>

<a id="db-wal-012"></a>

<details>
<summary><strong>🧠 DB-WAL-012. What is TOAST?</strong></summary>

#### Short answer

TOAST is PostgreSQL’s mechanism for storing large variable-length values that do not fit well in a normal heap tuple.

#### Interview answer

TOAST stands for The Oversized-Attribute Storage Technique. PostgreSQL can compress large values and/or store them out of line in a per-table TOAST table, with a pointer left in the main row.

#### Deep dive

It applies to TOAST-able variable-length types such as large `text`, `bytea`, `jsonb`, and arrays. Column storage strategy matters: `PLAIN`, `MAIN`, `EXTERNAL`, and `EXTENDED` have different compression/out-of-line behavior.

#### Production angle

TOAST is transparent, but not free. Reading/updating large toasted columns can add I/O, CPU, WAL, vacuum work, and network cost.

#### Traps / caveats

- Avoid `SELECT *` on tables with large columns.
- Large JSONB/text can dominate storage and WAL.
- TOAST is not a cache.

#### Optional Anki

Q: What does TOAST handle?
A: Large variable-length values.

</details>

<a id="db-wal-013"></a>

<details>
<summary><strong>🧠 DB-WAL-013. When does PostgreSQL use TOAST?</strong></summary>

#### Short answer

PostgreSQL uses TOAST when a variable-length value or row is too large to store normally in a heap page.

#### Interview answer

Large values may be compressed inline or moved out of line into a TOAST table, leaving a pointer in the main row.

#### Deep dive

The decision depends on value size, row size, data type storage strategy, compression, and row layout. The practical threshold is around a few KB by default, but it is not a fixed application-level contract.

#### Production angle

Queries that do not need large columns should avoid selecting them to reduce detoasting, I/O, memory, and network traffic.

#### Traps / caveats

- Not every type is TOAST-able.
- A value may be compressed inline, stored externally, or both.
- Updating toasted values can create extra WAL, dead TOAST rows, and vacuum work.

#### Optional Anki

Q: What remains in the main row for external TOAST?
A: A pointer/reference.

</details>

<a id="db-wal-014"></a>

<details>
<summary><strong>DB-WAL-014. How can very large rows affect performance?</strong></summary>

#### Short answer

Very large rows increase I/O, memory pressure, WAL volume, vacuum cost, replication lag, and network transfer.

#### Interview answer

Even if values are TOASTed, reading a large column can require detoasting and extra page reads. Updating it writes more WAL and creates more maintenance work.

#### Deep dive

Large rows also make ORM `SELECT *` patterns expensive and can turn simple API endpoints into storage-heavy operations.

#### Production angle

Return only needed columns, split large blobs/documents if necessary, use object storage for large binary files, and benchmark JSONB-heavy designs.

#### Traps / caveats

- Large rows can make simple queries unexpectedly slow.
- Large values increase backup and replication cost.
- Indexing huge expressions/documents needs careful design.

#### Optional Anki

Q: Why avoid SELECT * with large columns?
A: It may force reading/detoasting values the request does not need.

</details>
