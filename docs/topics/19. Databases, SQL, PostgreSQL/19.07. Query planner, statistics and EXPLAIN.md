# Query planner, statistics and EXPLAIN

---

<a id="db-plan-001"></a>

<details>
<summary><strong>DB-PLAN-001. What is the PostgreSQL query planner?</strong></summary>

#### Short answer

The query planner chooses a physical execution plan for a SQL query.

#### Interview answer

Because SQL is declarative, PostgreSQL must decide which scans, indexes, join order, join algorithms, sorts, aggregates, and memory strategies to use.

#### Deep dive

The planner is cost-based. It estimates row counts and costs using statistics, table/index metadata, configuration, and query predicates. The cheapest estimated plan wins.

#### Production angle

Bad production plans usually come from bad estimates, stale statistics, skewed data, missing indexes, generic prepared plans, or non-representative parameters.

#### Traps / caveats

- Cost is an estimate, not milliseconds.
- The planner can choose a valid but slow plan.
- Planner behavior depends on data distribution.

#### Optional Anki

Q: What is the PostgreSQL query planner?
A: The query planner chooses a physical execution plan for a SQL query.

</details>

<a id="db-plan-002"></a>

<details>
<summary><strong>DB-PLAN-002. How does PostgreSQL decide whether to use an index?</strong></summary>

#### Short answer

It compares estimated costs of sequential scan, index scan, bitmap scan, and other paths.

#### Interview answer

PostgreSQL estimates predicate selectivity and decides whether using the index plus heap access is cheaper than reading the table sequentially.

#### Deep dive

The decision uses statistics such as `n_distinct`, MCVs, histograms, null fraction, table size, index structure, correlation, and cost parameters like random/sequential page cost.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'ACTIVE';
```

#### Production angle

If PostgreSQL ignores an index, inspect `EXPLAIN (ANALYZE, BUFFERS)`, selectivity, stale stats, expression mismatch, composite index order, heap fetches, and whether a partial/expression index is needed.

#### Traps / caveats

- Index existence does not imply index usage.
- Low selectivity can make Seq Scan cheaper.
- A function on a column may require an expression index.
- Stale statistics can mislead the planner.

#### Optional Anki

Q: How does PostgreSQL decide whether to use an index?
A: It compares estimated costs of sequential scan, index scan, bitmap scan, and other paths.

</details>

<details>
<summary><strong>DB-PLAN-003. What statistics does PostgreSQL use to estimate selectivity?</strong></summary>

#### Short answer

PostgreSQL uses statistics collected by `ANALYZE`: row counts, null fraction, distinct values, most common values, histograms, and correlation.

#### Interview answer

These statistics help estimate how many rows a predicate will return and therefore influence scan type, join order, join algorithm, and memory-heavy nodes.

#### Deep dive

Single-column stats may fail for correlated columns. Extended statistics can help with dependencies, ndistinct combinations, and MCV lists across multiple columns.

```sql
CREATE STATISTICS users_tenant_status_stats
  (dependencies, ndistinct, mcv)
  ON tenant_id, status
  FROM users;

ANALYZE users;
```

#### Production angle

If actual rows differ greatly from estimated rows, inspect `pg_stats`, run `ANALYZE`, and consider extended statistics or a higher per-column statistics target.

```sql
ALTER TABLE users ALTER COLUMN tenant_id SET STATISTICS 1000;
ANALYZE users;
```

#### Traps / caveats

- Statistics are sampled, not exact.
- Multi-column correlation can break estimates unless extended stats exist.
- Large imports/deletes can make stats stale.

#### Optional Anki

Q: What statistics does PostgreSQL use to estimate selectivity?
A: PostgreSQL uses statistics collected by ANALYZE: row counts, null fraction, distinct values, most common values, histograms, and correlation.

</details>

<details>
<summary><strong>🧠 DB-PLAN-004. What is pg_stats?</strong></summary>

#### Short answer

`pg_stats` is a system view exposing planner statistics for table columns.

#### Interview answer

It shows distribution data such as null fraction, distinct count estimate, MCV values/frequencies, histograms, and correlation.

#### Deep dive

Use it to understand how PostgreSQL sees your data, especially when the plan estimates are wrong.

```sql
SELECT attname, null_frac, n_distinct, most_common_vals, most_common_freqs
FROM pg_stats
WHERE schemaname = 'public' AND tablename = 'orders';
```

#### Production angle

In incidents, `pg_stats` helps confirm skew, rare values, common values, and stale statistics.

#### Traps / caveats

- pg_stats is based on samples.
- Stats can be stale.
- Access may be filtered by permissions.

#### Optional Anki

Q: What is pg_stats?
A: pg_stats is a system view exposing planner statistics for table columns.

<summary><strong>🧠 DB-PLAN-005. What are n_distinct, most_common_vals, most_common_freqs and histogram_bounds?</strong></summary>

#### Short answer

They are planner statistics describing data distribution in a column.

#### Interview answer

`n_distinct` estimates distinct values. `most_common_vals` and `most_common_freqs` describe frequent values and their fractions. `histogram_bounds` approximates less common value distribution.

#### Deep dive

They are used to estimate equality and range selectivity. If `ACTIVE` is 80% of rows, an index on status may not be attractive for `status='ACTIVE'`.

#### Production angle

When estimates are bad, compare actual data distribution with `pg_stats`; increase stats target or use extended stats if needed.

#### Traps / caveats

- MCV list size is limited.
- Histograms are approximations.
- Very skewed data needs extra attention.

#### Optional Anki

Q: What are n_distinct, most_common_vals, most_common_freqs and histogram_bounds?
A: They are planner statistics describing data distribution in a column.

<details>
<summary><strong>DB-PLAN-006. What is the difference between cardinality, selectivity and estimated rows?</strong></summary>

#### Short answer

Cardinality is number of distinct values; selectivity is fraction of rows matched by a predicate; estimated rows is the planner’s row-count prediction.

#### Interview answer

High cardinality can make an index useful, but a concrete predicate can still have low selectivity for common values.

#### Deep dive

Example: `user_id` may be high-cardinality, but one huge user/tenant may own most rows. The same predicate can be selective for one value and non-selective for another.

#### Production angle

Compare estimated rows to actual rows. Large mismatch means planner misunderstood selectivity or correlation.

#### Traps / caveats

- High cardinality is not always high selectivity.
- Estimated rows are not actual rows.
- Skewed values break average assumptions.

#### Optional Anki

Q: What is the difference between cardinality, selectivity and estimated rows?
A: Cardinality is number of distinct values; selectivity is fraction of rows matched by a predicate; estimated rows is the planner’s row-count prediction.

</details>

<details>
<summary><strong>DB-PLAN-007. How can stale statistics cause a bad query plan?</strong></summary>

#### Short answer

Stale statistics make PostgreSQL estimate row counts and selectivity incorrectly.

#### Interview answer

After large inserts, deletes, or distribution changes, old stats can make the planner choose an index scan, seq scan, or join algorithm that is no longer appropriate.

#### Deep dive

In `EXPLAIN ANALYZE`, stale stats often appear as a big estimated/actual row mismatch.

#### Production angle

Run `ANALYZE` after large data changes and tune autovacuum/analyze thresholds for volatile tables.

#### Traps / caveats

- ANALYZE fixes statistics, not missing indexes.
- Autovacuum may not run often enough for hot tables.
- Plan change after ANALYZE can be good.

#### Optional Anki

Q: How can stale statistics cause a bad query plan?
A: Stale statistics make PostgreSQL estimate row counts and selectivity incorrectly.

<summary><strong>DB-PLAN-008. How can data skew cause a bad query plan?</strong></summary>

#### Short answer

Data skew means values are distributed unevenly, so average selectivity is misleading.

#### Interview answer

One tenant may have 90% of rows while others have 100 rows. A generic plan or average estimate may be bad for the large tenant.

#### Deep dive

Skew interacts with prepared statements, generic plans, MCV stats, partial indexes, and query splitting.

#### Production angle

Debug by checking MCV frequencies, actual parameters, estimated/actual rows, and whether special-case plans are justified.

#### Traps / caveats

- Average value can hide extremes.
- Multi-tenant systems often have skew.
- Generic plans can be bad with skew.

<details>
<summary><strong>DB-PLAN-009. What is EXPLAIN?</strong></summary>

#### Short answer

`EXPLAIN` shows the estimated execution plan PostgreSQL expects to use.

#### Interview answer

It shows plan nodes, scan types, join methods, estimated cost, rows, and width.

#### Deep dive

Plain `EXPLAIN` does not execute the query, so it gives estimates only.

```sql
EXPLAIN
SELECT * FROM orders WHERE customer_id = 42;
```

#### Production angle

Use it when execution would be unsafe or expensive. Use `EXPLAIN ANALYZE` for actual runtime data.

#### Traps / caveats

- Plain EXPLAIN is estimates only.
- Plans can differ with parameters.
- For writes, EXPLAIN ANALYZE actually executes changes.

#### Optional Anki

Q: What is EXPLAIN?
A: EXPLAIN shows the estimated execution plan PostgreSQL expects to use.

</details>

<details>
<summary><strong>DB-PLAN-010. What is the difference between EXPLAIN and EXPLAIN ANALYZE?</strong></summary>

#### Short answer

`EXPLAIN` shows an estimated plan; `EXPLAIN ANALYZE` executes the query and shows actual runtime statistics.

#### Interview answer

Use `EXPLAIN ANALYZE` to see actual rows, actual time, loops, and where time is spent.

#### Deep dive

The ability to compare estimated rows to actual rows is one of the most important parts of senior PostgreSQL debugging.

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42;
```

#### Production angle

Run `EXPLAIN ANALYZE` carefully for mutating queries; use a transaction and rollback if appropriate and safe.

#### Traps / caveats

- EXPLAIN ANALYZE executes the query.
- One run can be affected by cache state.
- Do not benchmark with unrealistic parameters.

#### Optional Anki

Q: What is the difference between EXPLAIN and EXPLAIN ANALYZE?
A: EXPLAIN shows an estimated plan; EXPLAIN ANALYZE executes the query and shows actual runtime statistics.

</details>

<details>
<summary><strong>DB-PLAN-011. Why should you use EXPLAIN (ANALYZE, BUFFERS)?</strong></summary>

#### Short answer

It shows actual execution plus buffer usage, which helps understand IO/cache behavior.

#### Interview answer

`ANALYZE` gives actual rows and timing; `BUFFERS` shows shared buffer hits/reads/dirtied/written.

#### Deep dive

Buffers help distinguish CPU-heavy cached work from disk-read-heavy work.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 42;
```

#### Production angle

For production incidents, `BUFFERS` often explains why the same query behaves differently under cache/IO pressure.

#### Traps / caveats

- Buffer hits still cost CPU.
- Reads usually indicate IO pressure.
- Use representative parameters and data.

#### Optional Anki

Q: Why should you use EXPLAIN (ANALYZE, BUFFERS)?
A: It shows actual execution plus buffer usage, which helps understand IO/cache behavior.

</details>

`cost` is estimated work, `rows` is estimated output row count, and `width` is estimated average row size.

#### Interview answer

#### Production angle

#### Traps / caveats

- Cost is not wall-clock time.
- Rows can be misestimated.
- Wide rows can be expensive.

<details>
<summary><strong>🧠 DB-PLAN-014. Why is a large estimated/actual row mismatch dangerous?</strong></summary>

#### Short answer

Because the planner uses row estimates to choose almost everything in the plan.

#### Interview answer

If PostgreSQL expects 10 rows but gets 1,000,000, it may choose nested loops or memory settings that become disastrous.

#### Deep dive

Mismatches can come from stale stats, skew, correlated columns, missing extended stats, generic plans, or expressions that hide selectivity.

#### Production angle

Fixing row estimates often fixes the whole query plan more effectively than forcing planner behavior.

#### Traps / caveats

- Do not optimize only the final slow node.
- Large mismatch is a root-cause clue.
- Planner toggles are diagnostic, not final fixes.

#### Optional Anki

Q: Why is a large estimated/actual row mismatch dangerous?
A: Because the planner uses row estimates to choose almost everything in the plan.

<summary><strong>DB-PLAN-015. What is a Seq Scan?</strong></summary>

#### Short answer

Seq Scan means PostgreSQL reads table pages sequentially and checks rows against the filter.

#### Interview answer

It is often correct for small tables or predicates that return a large percentage of rows.

#### Deep dive

Sequential IO can be cheaper than random index lookups when many rows/pages are needed.

#### Production angle

Seq Scan is a problem when it scans a huge table unexpectedly for a query that should be selective.

#### Traps / caveats

- Seq Scan is not always bad.
- Small tables often use Seq Scan.
- Check rows removed by filter and buffers.

#### Optional Anki

Q: What is a Seq Scan?
A: Seq Scan means PostgreSQL reads table pages sequentially and checks rows against the filter.

</details>

<details>
<summary><strong>DB-PLAN-016. What is an Index Scan?</strong></summary>

#### Short answer

Index Scan uses an index to locate matching row pointers and then reads corresponding heap rows.

#### Interview answer

It is useful for selective predicates, ordered access, and LIMIT queries.

#### Deep dive

A normal index scan usually still visits the heap for MVCC visibility and columns not stored in the index.

#### Production angle

If many matching rows are scattered across the table, random heap reads can make Index Scan slower than Bitmap/Seq Scan.

#### Traps / caveats

- Index Scan is not always faster.
- Low selectivity can make it bad.
- Index Scan differs from Index Only Scan.

#### Optional Anki

Q: What is an Index Scan?
A: Index Scan uses an index to locate matching row pointers and then reads corresponding heap rows.

</details>

<details>
<summary><strong>🧠 DB-PLAN-018. What is a Bitmap Index Scan?</strong></summary>

#### Short answer

Bitmap Index Scan reads an index and builds a bitmap of matching heap locations.

#### Interview answer

It usually works with Bitmap Heap Scan, which later visits table pages.

#### Deep dive

PostgreSQL can combine multiple bitmap index scans using AND/OR before reading the heap.

#### Production angle

Useful when many rows match but not enough to justify a full sequential scan.

#### Traps / caveats

- Bitmap Index Scan alone does not fetch heap rows.
- Often paired with Bitmap Heap Scan.
- Lossy bitmaps require rechecks.

#### Optional Anki

Q: What is a Bitmap Index Scan?
A: Bitmap Index Scan reads an index and builds a bitmap of matching heap locations.

<details>
<summary><strong>🧠 DB-PLAN-019. What is a Bitmap Heap Scan?</strong></summary>

#### Short answer

Bitmap Heap Scan visits heap pages based on a bitmap produced by one or more bitmap index scans.

#### Interview answer

It groups heap access by page, reducing random IO compared with row-by-row index lookups.

#### Deep dive

It can show exact/lossy heap blocks and recheck conditions in `EXPLAIN`.

#### Production angle

If it is slow, inspect heap blocks, lossy pages, rechecks, memory, and selectivity.

#### Traps / caveats

- Bitmap Heap Scan can still read many pages.
- Lossy bitmap means rechecking rows.
- It can be a good middle-ground plan.

#### Optional Anki

Q: What is a Bitmap Heap Scan?
A: Bitmap Heap Scan visits heap pages based on a bitmap produced by one or more bitmap index scans.

<details>
<summary><strong>🧠 DB-PLAN-020. When does PostgreSQL choose Bitmap Heap Scan instead of Index Scan?</strong></summary>

#### Short answer

When batching heap page reads is estimated cheaper than many individual index-driven heap fetches.

#### Interview answer

This often happens for medium-selectivity predicates: too many rows for simple Index Scan, too few for Seq Scan.

#### Deep dive

Bitmap scans can also combine several indexes when no single composite index matches the query.

#### Production angle

If this plan is slow, consider a better composite index, more selective filter, more memory, or reducing input earlier.

#### Traps / caveats

- Bitmap scan is not an error.
- Composite index may beat bitmap combination.
- Low work_mem can worsen lossy bitmap behavior.

#### Optional Anki

Q: When does PostgreSQL choose Bitmap Heap Scan instead of Index Scan?
A: When batching heap page reads is estimated cheaper than many individual index-driven heap fetches.

<details>
<summary><strong>DB-PLAN-024. What is work_mem?</strong></summary>

#### Short answer

`work_mem` is the per-operation memory target for sorts, hash tables, and similar nodes before spilling to temp files.

#### Interview answer

It is per operation, not a global cap. One query can use multiple `work_mem` allocations.

#### Deep dive

Sorts, hash joins, hash aggregates, and some bitmap operations can be affected. Hash operations can use more than `work_mem` according to `hash_mem_multiplier`.

#### Production angle

Tune carefully: high global `work_mem` can exhaust memory under concurrency. Prefer workload/session-level tuning when possible.

```sql
BEGIN;
SET LOCAL work_mem = '256MB';
-- run one heavy report query
COMMIT;
```

#### Traps / caveats

- Not a global memory cap.
- Concurrency and parallel workers multiply memory use.
- For hash nodes, also consider `hash_mem_multiplier`.
- Raising it may hide bad query shape.

#### Optional Anki

Q: What is work_mem?
A: work_mem is the memory limit for certain operations like sorts and hash tables before spilling to temp files.

</details>

<details>
<summary><strong>DB-PLAN-025. How can work_mem affect sort and hash operations?</strong></summary>

#### Short answer

If `work_mem` is too small, sorts and hash operations may spill to disk.

#### Interview answer

In-memory sorts/hashes are usually faster than external sorts or batched hash operations using temp files, but memory settings are multiplied per node, worker, and concurrent query.

#### Deep dive

Look for external sort, temp reads/writes, hash batches, and memory usage in `EXPLAIN (ANALYZE, BUFFERS)`. For hashes, compare estimated rows with actual rows because bad estimates often cause spill.

#### Production angle

Before raising memory, try reducing input rows, adding useful indexes, or rewriting the query. Use `SET LOCAL work_mem` for a known heavy statement instead of raising the global default.

#### Traps / caveats

- High global `work_mem` is dangerous.
- Parallel/concurrent queries multiply memory.
- `hash_mem_multiplier` changes hash-node memory behavior.
- Fixing indexes can avoid sort.

#### Optional Anki

Q: How can work_mem affect sort and hash operations?
A: If work_mem is too small, sorts and hash operations may spill to disk.

</details>

<details>
<summary><strong>🧠 DB-PLAN-029. What is a generic plan vs a custom plan for prepared statements?</strong></summary>

#### Short answer

A custom plan is optimized for concrete parameter values; a generic plan is reused without parameter-specific optimization.

#### Interview answer

PostgreSQL can choose generic plans for prepared statements after repeated executions if it estimates reuse is cheaper than planning for each parameter set.

#### Deep dive

Generic plans are risky when parameter selectivity varies: one value returns 10 rows, another returns 10 million. Reproduce with `PREPARE`/`EXPLAIN EXECUTE` and compare forced custom vs forced generic plans.

```sql
SET plan_cache_mode = force_custom_plan;
EXPLAIN EXECUTE find_orders(42);

SET plan_cache_mode = force_generic_plan;
EXPLAIN EXECUTE find_orders(42);
```

#### Production angle

In Java apps, server-side prepared statements, ORM behavior, and connection pools can expose this issue. Check JDBC driver prepare thresholds and ORM query reuse before blaming only the database.

#### Traps / caveats

- Generic plan hides parameter selectivity.
- Custom planning has overhead.
- Skewed data makes this important.
- Use `plan_cache_mode` for diagnosis, not as a first permanent fix.

#### Optional Anki

Q: What is a generic plan vs a custom plan for prepared statements?
A: A custom plan is optimized for concrete parameter values; a generic plan is reused without parameter-specific optimization.

</details>

Q: How can prepared statements cause unexpected query plans?
A: They may lead to a generic plan that is bad for specific parameter values.

<summary><strong>DB-PLAN-031. How would you debug a bad query plan?</strong></summary>

#### Short answer

Use the real query and parameters, run `EXPLAIN (ANALYZE, BUFFERS)`, compare estimates to actuals, and find the first wrong estimate or expensive node.

#### Interview answer

Then inspect stats, indexes, predicates, joins, memory spills, prepared plans, locks, `pg_stat_statements`, and connection pool metrics.

#### Deep dive

Work from the first major estimate mismatch upward, not only from the slowest-looking node. Typical fixes: run `ANALYZE`, add/change indexes, rewrite query, add extended statistics, reduce input rows, tune memory locally, or split skewed cases.

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT ...;

SELECT query, calls, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 20;
```

#### Production angle

Validate changes with repeated measurements on production-like data. For risky experiments, test planner hypotheses with session-local settings, but make durable fixes through stats, indexes, query shape, or data model.

#### Traps / caveats

- Do not blindly add indexes.
- Do not optimize on toy data.
- One plan run can be cache-dependent.
- Find root cause, not only the slowest node.
- Planner GUCs are diagnostic tools, not normal application tuning.
