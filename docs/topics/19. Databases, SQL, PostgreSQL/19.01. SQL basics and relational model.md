# SQL basics and relational model

---

<a id="db-sql-001"></a>

<details>
<summary><strong>DB-SQL-001. What is SQL?</strong></summary>

#### Short answer

SQL is a declarative language for working with relational databases. We use it to define schemas, query data, change data, manage permissions, and control transactions.

#### Interview answer

SQL stands for Structured Query Language. In backend development, I mostly use it to query and modify data in relational databases like PostgreSQL.

The important point is that SQL is declarative: I describe what result I want, not exactly how to iterate over rows. The database optimizer decides the execution plan: which indexes to use, which join algorithm to choose, and whether a sequential scan is cheaper.

SQL is also broader than `SELECT`. It includes schema changes like `CREATE TABLE`, data changes like `INSERT` and `UPDATE`, access control like `GRANT`, and transaction control like `COMMIT` and `ROLLBACK`.

#### Deep dive

SQL works with tables, rows, columns, constraints, relations, and result sets. A query is usually written as a logical expression over sets of rows, while the database engine converts it into a physical execution plan.

For example:

```sql
SELECT id, email
FROM users
WHERE status = 'ACTIVE'
ORDER BY created_at DESC
LIMIT 50;
```

This query describes the required result. PostgreSQL may execute it using an index scan, a sequential scan plus sort, or another plan depending on indexes, table size, statistics, and selectivity.

Different databases support the SQL standard with dialect-specific extensions. PostgreSQL SQL is not identical to MySQL, Oracle, or SQL Server SQL.

#### Production angle

For a Java backend developer, SQL matters even when using JPA or another ORM. Production issues often require reading generated SQL, checking execution plans with `EXPLAIN`, understanding indexes, avoiding N+1 queries, and making safe schema changes.

Good SQL usage also includes parameterized queries to avoid SQL injection, clear transaction boundaries, migrations through tools like Flyway or Liquibase, and awareness of database-specific behavior.

#### Traps / caveats

- SQL is declarative, but performance depends heavily on physical details: indexes, statistics, row counts, data distribution, and locks.
- SQL is not the same in every database. Dialects and transaction behavior differ.
- ORM knowledge does not replace SQL knowledge for serious backend work.
- `NULL` has special three-valued logic and often surprises developers.
- A query can be logically correct and still be dangerous in production if it scans too much data or locks too many rows.

#### Optional Anki

Q: What is SQL?
A: SQL is a declarative language for defining, querying, modifying, securing, and transactionally managing data in relational databases.

Q: Why is SQL called declarative?
A: Because the query describes the desired result, while the database optimizer decides how to execute it.

<details>
<summary><strong>DB-SQL-002. What are DDL, DML, DCL and TCL?</strong></summary>

#### Short answer

DDL changes database structure, DML works with data, DCL manages permissions, and TCL controls transactions.

#### Interview answer

These are common categories of SQL commands.

DDL means Data Definition Language. It is used for schema objects: `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `CREATE INDEX`.

DML means Data Manipulation Language. It is used to work with rows: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, and `MERGE`. Some classifications separate `SELECT` into DQL, but in interviews it is often discussed together with DML.

DCL means Data Control Language. It manages access: `GRANT` and `REVOKE`.

TCL means Transaction Control Language. It manages transaction boundaries and savepoints: `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`.

#### Deep dive

Example DDL:

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    email TEXT NOT NULL UNIQUE
);
```

Example DML:

```sql
INSERT INTO users (email) VALUES ('alice@example.com');

UPDATE users
SET email = 'alice.new@example.com'
WHERE id = 1;
```

Example DCL:

```sql
GRANT SELECT ON users TO reporting_user;
REVOKE SELECT ON users FROM reporting_user;
```

Example TCL:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

The categories are useful for communication, but exact behavior depends on the DBMS. For example, PostgreSQL supports transactional DDL for many operations, while some databases auto-commit DDL statements.

#### Production angle

In production, DDL is usually handled through migrations and requires extra care because schema changes can lock tables, rewrite data, or break application compatibility.

DML is the everyday workload of the application, so it must be written with indexes, transaction boundaries, batching, and locking behavior in mind.

DCL should follow least privilege: application users should not usually have owner-level permissions.

TCL matters for correctness. A money transfer, order creation, or outbox write usually must be atomic, and rollback behavior must be understood together with the Java transaction manager.

#### Traps / caveats

- The categories are not always perfectly consistent across books and databases. `SELECT` may be called DML or DQL.
- DDL behavior differs between DBMSs. PostgreSQL supports transactional DDL for many commands, but not every database does.
- `TRUNCATE` is often grouped with DDL, but its transactional and locking behavior is database-specific.
- DCL changes are security-sensitive and should be reviewed like application permission changes.
- TCL commands may be hidden by frameworks like Spring `@Transactional`, but the database transaction still exists.

#### Optional Anki

Q: What is DDL?
A: Data Definition Language: SQL commands that define or change database structure, such as `CREATE`, `ALTER`, and `DROP`.

Q: What is DML?
A: Data Manipulation Language: SQL commands that read or modify data rows, such as `SELECT`, `INSERT`, `UPDATE`, and `DELETE`.

Q: What is DCL?
A: Data Control Language: SQL commands that manage permissions, mainly `GRANT` and `REVOKE`.

Q: What is TCL?
A: Transaction Control Language: SQL commands that control transactions, such as `BEGIN`, `COMMIT`, `ROLLBACK`, and `SAVEPOINT`.

</details>

<details>
<summary><strong>DB-SQL-003. What is NULL in SQL?</strong></summary>

#### Short answer

`NULL` means that a value is absent, unknown, or not applicable. It is not the same as zero, an empty string, or `false`.

#### Interview answer

In SQL, `NULL` is a special marker for missing information. For example, a user may not have a middle name, or an order may not yet have a delivery date.

The important part is that comparisons with `NULL` do not behave like normal comparisons. `column = NULL` does not return true; it returns `UNKNOWN`. To check for nulls, we use `IS NULL` and `IS NOT NULL`.

Aggregates also have special behavior: most aggregate functions ignore `NULL`, while `COUNT(*)` counts rows regardless of null values.

#### Deep dive

Example:

```sql
SELECT *
FROM users
WHERE deleted_at IS NULL;
```

This means “users that are not deleted yet” if `deleted_at` is used for soft deletes.

`NULL` is part of SQL three-valued logic: predicates may evaluate to `TRUE`, `FALSE`, or `UNKNOWN`. In a `WHERE` clause, only `TRUE` rows are returned.

#### Production angle

In schema design, nullable columns should be intentional. If a field is mandatory for business logic, use `NOT NULL` and ideally enforce it at the database level.

In application code, nullable database columns must map clearly to Java types: plain nullable reference, `Optional` at boundaries, or a domain-specific state.

#### Traps / caveats

- `NULL = NULL` is not true; it is `UNKNOWN`.
- Use `IS NULL`, not `= NULL`.
- `NOT IN` can behave unexpectedly if the subquery contains `NULL`.
- Most aggregates ignore `NULL`, but `COUNT(*)` does not.
- `NULL` may mean different business states, so avoid using it when a clearer domain value exists.

#### Optional Anki

Q: What is `NULL` in SQL?
A: A marker for an absent, unknown, or not applicable value.

Q: How do you check for `NULL`?
A: With `IS NULL` or `IS NOT NULL`.

</details>

<a id="db-sql-004"></a>

<details>
<summary><strong>DB-SQL-004. Why is NULL not equal to NULL?</strong></summary>

#### Short answer

Because `NULL` means unknown, and SQL cannot say that two unknown values are equal. The comparison returns `UNKNOWN`, not `TRUE`.

#### Interview answer

`NULL` is not a value; it is a marker for missing or unknown information. If we compare one unknown value with another unknown value, the result is still unknown.

That is why `NULL = NULL` is not true in SQL. To check whether both values are null-safe equal in PostgreSQL, we can use `IS NOT DISTINCT FROM`.

#### Deep dive

```sql
SELECT NULL = NULL;              -- UNKNOWN
SELECT NULL IS NULL;             -- TRUE
SELECT NULL IS NOT DISTINCT FROM NULL; -- TRUE
```

In `WHERE`, rows are returned only when the predicate is `TRUE`. `FALSE` and `UNKNOWN` are both filtered out.

#### Production angle

This matters when comparing nullable columns, syncing data, implementing upserts, or detecting changes. A naive comparison may miss cases where both sides are `NULL`.

#### Traps / caveats

- `WHERE column = NULL` is almost always a bug.
- Use `IS NOT DISTINCT FROM` in PostgreSQL for null-safe equality.
- Default PostgreSQL unique constraints treat nulls as distinct; PostgreSQL also supports `NULLS NOT DISTINCT` for unique constraints/indexes.
- Different databases may have different null-safe equality operators.

#### Optional Anki

Q: Why is `NULL = NULL` not true?
A: Because both sides are unknown, so the result is `UNKNOWN`.

Q: What is PostgreSQL null-safe equality?
A: `IS NOT DISTINCT FROM`.

</details>

<a id="db-sql-005"></a>

<details>
<summary><strong>DB-SQL-005. What is SQL three-valued logic?</strong></summary>

#### Short answer

SQL predicates can return three results: `TRUE`, `FALSE`, and `UNKNOWN`. `UNKNOWN` usually appears when `NULL` is involved.

#### Interview answer

In many programming languages, boolean logic has only true and false. SQL adds a third state: `UNKNOWN`.

If a predicate compares something with `NULL`, SQL often cannot decide whether it is true or false. For example, `age > 18` is unknown if `age` is `NULL`.

In `WHERE` and `HAVING`, only rows where the predicate is `TRUE` pass. Rows with `FALSE` or `UNKNOWN` are filtered out.

#### Deep dive

Useful examples:

```sql
TRUE AND UNKNOWN   -- UNKNOWN
FALSE AND UNKNOWN  -- FALSE
TRUE OR UNKNOWN    -- TRUE
FALSE OR UNKNOWN   -- UNKNOWN
NOT UNKNOWN        -- UNKNOWN
```

This explains why `NOT IN` with nulls can be dangerous.

#### Production angle

Three-valued logic affects filters, joins, constraints, and analytics. When nullable columns are used in predicates, tests should include null cases explicitly.

#### Traps / caveats

- `UNKNOWN` is not the same as `FALSE`, but `WHERE` filters both out.
- `NOT UNKNOWN` is still `UNKNOWN`.
- `NOT IN` can return no rows if the right side contains `NULL`.
- Use `IS NULL`, `IS NOT NULL`, `EXISTS`, or null-safe comparison when appropriate.

#### Optional Anki

Q: What are the three SQL logical values?
A: `TRUE`, `FALSE`, and `UNKNOWN`.

Q: Which rows pass a `WHERE` filter?
A: Only rows where the predicate is `TRUE`.

</details>

<details>
<summary><strong>DB-SQL-006. What is the difference between PRIMARY KEY and UNIQUE?</strong></summary>

#### Short answer

A primary key uniquely identifies a row and cannot contain `NULL`. A unique constraint also enforces uniqueness, but a table can have many unique constraints and nullable behavior depends on the database.

#### Interview answer

`PRIMARY KEY` is the main identifier of a table row. It implies uniqueness and `NOT NULL`. Usually it is used as the target for foreign keys and as the stable identity in application code.

`UNIQUE` means that values in one or more columns must be unique. It is useful for natural identifiers like email, external id, or a business code.

In PostgreSQL, both primary keys and unique constraints are enforced with indexes, but their meaning in the data model is different.

#### Deep dive

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    email TEXT UNIQUE
);
```

Here `id` is the row identity, while `email` is an additional unique business attribute.

#### Production angle

Choose primary keys that are stable and never reused. Use unique constraints for business rules that must be protected from race conditions, such as unique email or unique external payment id.

#### Traps / caveats

- A table has only one primary key, but it may contain multiple columns.
- A table can have many unique constraints.
- In PostgreSQL, unique constraints allow multiple `NULL` values by default.
- A unique constraint is not automatically the best primary key for application references.

#### Optional Anki

Q: What does primary key imply?
A: Uniqueness and `NOT NULL`.

Q: Can a table have multiple unique constraints?
A: Yes.

</details>

<a id="db-sql-007"></a>

<details>
<summary><strong>DB-SQL-007. Can a UNIQUE column contain NULL values in PostgreSQL?</strong></summary>

#### Short answer

Yes. By default, PostgreSQL allows multiple `NULL` values in a unique column because nulls are treated as distinct. If needed, PostgreSQL can enforce `NULLS NOT DISTINCT`.

#### Interview answer

In PostgreSQL, a unique constraint prevents duplicate non-null values. But several rows may contain `NULL`, because `NULL` means unknown, and unknown values are not considered equal by default.

If the business rule says “only one null is allowed” or “nulls should compare as equal”, PostgreSQL supports `UNIQUE NULLS NOT DISTINCT`.

#### Deep dive

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    phone TEXT UNIQUE
);
```

This table allows many users with `phone = NULL`, but it does not allow two users with the same non-null phone.

#### Production angle

When uniqueness is part of a business rule, clarify whether missing values are allowed and how many missing values are valid. This affects schema design, validation, and race-condition protection.

#### Traps / caveats

- Unique does not imply `NOT NULL`.
- Multiple `NULL` values are allowed by default in PostgreSQL unique constraints.
- If the column must always be present and unique, use `NOT NULL UNIQUE`.
- PostgreSQL-specific features may not exist in the same form in other databases.

#### Optional Anki

Q: Can PostgreSQL unique columns contain multiple nulls?
A: Yes, by default.

Q: How do you make nulls equal for uniqueness in PostgreSQL?
A: Use `UNIQUE NULLS NOT DISTINCT`.

</details>

<a id="db-sql-008"></a>

<details>
<summary><strong>DB-SQL-008. Can a FOREIGN KEY column contain NULL?</strong></summary>

#### Short answer

Yes, if the foreign key column is nullable. A `NULL` foreign key usually means that the relationship is optional or not yet known.

#### Interview answer

A foreign key enforces that a non-null value must reference an existing row in the parent table. But if the column itself allows `NULL`, then `NULL` is allowed and the database does not require a referenced parent row for that value.

If the relationship is mandatory, the foreign key column should also be declared `NOT NULL`.

#### Deep dive

```sql
CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    assigned_manager_id BIGINT REFERENCES managers(id)
);
```

This allows orders without an assigned manager. To make assignment mandatory, add `NOT NULL`.

#### Production angle

Nullable foreign keys are useful for optional relationships, drafts, delayed assignment, and soft workflow states. But they should be modeled deliberately, because they affect joins, API responses, and business invariants.

#### Traps / caveats

- Foreign key does not automatically mean `NOT NULL`.
- For mandatory relationships, use both `REFERENCES` and `NOT NULL`.
- With composite foreign keys, null handling depends on match rules such as `MATCH SIMPLE` and `MATCH FULL`.
- With PostgreSQL default `MATCH SIMPLE`, the foreign key check can pass if at least one referencing column is `NULL`.
- Use `MATCH FULL` when a composite relationship should be all-or-none: either all referencing columns are `NULL`, or all of them must match a parent row.
- Nullable foreign keys can turn inner joins into missing rows if the query is not written carefully.

#### Optional Anki

Q: Can a foreign key be null?
A: Yes, if the foreign key column is nullable.

Q: How do you make a foreign key relationship mandatory?
A: Add `NOT NULL` to the foreign key column.

</details>

<a id="db-sql-009"></a>

<details>
<summary><strong>DB-SQL-009. What are NOT NULL, CHECK, UNIQUE, PRIMARY KEY and FOREIGN KEY constraints?</strong></summary>

#### Short answer

They are database rules that protect data integrity: required values, valid values, uniqueness, row identity, and relationships between tables.

#### Interview answer

`NOT NULL` means the column must have a value.

`CHECK` validates a condition, for example positive price.

`UNIQUE` prevents duplicate values.

`PRIMARY KEY` uniquely identifies a row and implies `NOT NULL`.

`FOREIGN KEY` ensures that a value references an existing row in another table, or another column set in the same table.

#### Deep dive

```sql
CREATE TABLE order_items (
    id BIGSERIAL PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES orders(id),
    sku TEXT NOT NULL,
    quantity INT NOT NULL CHECK (quantity > 0),
    UNIQUE (order_id, sku)
);
```

This schema says that every item belongs to an order, quantity must be positive, and the same SKU cannot be duplicated inside one order.

#### Production angle

Constraints protect data even when multiple services, scripts, batch jobs, or manual SQL touch the database. They also prevent race conditions that application-level checks alone cannot reliably handle.

For production migrations on large tables, constraints should be added carefully. PostgreSQL supports patterns such as `NOT VALID` constraints followed by `VALIDATE CONSTRAINT`, and some constraints can be `DEFERRABLE` so they are checked at transaction commit.

#### Traps / caveats

- Application validation and database constraints solve different problems; often both are needed.
- Adding constraints to large existing tables may require careful migration and validation.
- `CHECK` constraints interact with `NULL`: if the check evaluates to `UNKNOWN`, the row may pass unless `NOT NULL` is also used.
- Foreign keys improve correctness but can affect writes and deletes due to checks and locks.
- PostgreSQL also supports exclusion constraints, which are useful for rules like preventing overlapping time ranges.
- `DEFERRABLE` constraints can be checked at transaction commit, which is useful for some bulk changes or circular references.
- On large existing tables, adding a constraint with `NOT VALID` and validating it later can reduce migration risk.

#### Optional Anki

Q: What does `NOT NULL` enforce?
A: The column must contain a value.

Q: What does a foreign key enforce?
A: Referential integrity between tables.

</details>

<a id="db-sql-010"></a>

<details>
<summary><strong>DB-SQL-010. Why should important business rules sometimes be enforced at the database level?</strong></summary>

#### Short answer

Because the database is the final shared boundary for data. Database constraints protect data from bugs, race conditions, manual changes, and multiple applications writing to the same tables.

#### Interview answer

Application validation is useful for good errors and user experience, but it is not enough for critical invariants. If two requests run concurrently, both can pass an application check and still create invalid data.

For example, if email must be unique, the reliable protection is a unique constraint. If order amount must be positive, a `CHECK` constraint can protect the invariant even outside the application path.

#### Deep dive

A common race condition:

```sql
-- Request A and B both check:
SELECT 1 FROM users WHERE email = 'a@example.com';

-- Both see no row, both try to insert.
```

A unique constraint makes one insert succeed and the other fail safely.

#### Production angle

In production, data can be modified by migrations, admin scripts, support tools, batch jobs, and future services. Important invariants should live close to the data.

#### Traps / caveats

- Do not push all business logic into the database; keep complex workflows in application code.
- Database constraints are best for stable invariants, not for volatile product rules.
- Adding constraints late can fail because existing data is already invalid.
- Applications must handle constraint violation errors cleanly.

#### Optional Anki

Q: Why enforce uniqueness in the database?
A: To prevent duplicates even under concurrency and outside normal application flow.

</details>

<details>
<summary><strong>DB-SQL-011. What is the difference between DELETE, TRUNCATE and DROP?</strong></summary>

#### Short answer

`DELETE` removes selected rows, `TRUNCATE` quickly removes all rows from a table, and `DROP` removes the database object itself.

#### Interview answer

`DELETE` is DML. It can use `WHERE`, deletes rows one by one logically, fires delete triggers, and can be rolled back inside a transaction.

`TRUNCATE` removes all rows from a table and is usually much faster for full cleanup. In PostgreSQL it is transactional, but it takes stronger locks and has different trigger behavior.

`DROP` removes the table, index, view, or another object definition, not just its data.

#### Deep dive

```sql
DELETE FROM sessions WHERE expires_at < now();
TRUNCATE TABLE staging_events;
DROP TABLE old_import_buffer;
```

`DELETE` is for selective removal. `TRUNCATE` is for full table cleanup. `DROP` is a schema operation.

#### Production angle

On hot production tables, all three commands require care. Large `DELETE` can create many dead tuples that later need to be cleaned by `VACUUM`, and it can create bloat and long transactions. `TRUNCATE` takes strong locks. `DROP` can break dependent code or objects.

For large historical cleanup, batching deletes or dropping/detaching old partitions is often safer than one huge `DELETE`.

#### Traps / caveats

- `DELETE` without `WHERE` removes all rows.
- `TRUNCATE` is not a filtered operation.
- `TRUNCATE` may restart identity sequences if requested with `RESTART IDENTITY`.
- `DROP ... CASCADE` can remove dependent objects.
- Behavior differs across DBMSs, especially transaction behavior around DDL.

#### Optional Anki

Q: Which command removes selected rows?
A: `DELETE`.

Q: Which command removes the table itself?
A: `DROP TABLE`.

</details>

<details>
<summary><strong>DB-SQL-012. What is the difference between UNION and UNION ALL?</strong></summary>

#### Short answer

`UNION` combines result sets and removes duplicates. `UNION ALL` combines result sets and keeps duplicates.

#### Interview answer

Both operators append rows from compatible queries. The difference is duplicate handling.

`UNION` behaves like `UNION DISTINCT`: it removes duplicate rows, which usually requires sorting or hashing. `UNION ALL` does not remove duplicates, so it is usually faster.

#### Deep dive

```sql
SELECT email FROM customers
UNION
SELECT email FROM newsletter_subscribers;
```

This returns unique emails. With `UNION ALL`, duplicate emails would remain.

#### Production angle

Prefer `UNION ALL` when duplicates are impossible or acceptable. Use `UNION` only when deduplication is required by the business logic.

#### Traps / caveats

- `UNION` may be significantly slower because it removes duplicates.
- The queries must have the same number of columns and compatible types.
- `ORDER BY` for the final result belongs at the end of the whole union query.
- Deduplication compares full rows, not just one column unless only one column is selected.
- Set operations compare selected rows, not business entities; choose the projected columns deliberately.
- When combining several set operations, use parentheses to make precedence explicit.

#### Optional Anki

Q: Which is faster: `UNION` or `UNION ALL`?
A: Usually `UNION ALL`, because it does not remove duplicates.

</details>

<details>
<summary><strong>DB-SQL-013. What are INTERSECT and EXCEPT used for?</strong></summary>

#### Short answer

`INTERSECT` returns rows that appear in both result sets. `EXCEPT` returns rows from the first result set that are absent from the second.

#### Interview answer

These are SQL set operations.

`INTERSECT` is useful when we need common rows between two queries, for example users who bought product A and product B.

`EXCEPT` is useful for difference checks, for example active users who have not accepted new terms.

#### Deep dive

```sql
SELECT user_id FROM purchases WHERE product_id = 1
INTERSECT
SELECT user_id FROM purchases WHERE product_id = 2;
```

```sql
SELECT id FROM users WHERE active = true
EXCEPT
SELECT user_id FROM accepted_terms;
```

By default these operations remove duplicates. PostgreSQL also supports `INTERSECT ALL` and `EXCEPT ALL`.

#### Production angle

Set operations are useful for reconciliation queries, data quality checks, migration verification, and analytics. For application queries, `EXISTS` or joins may be more flexible depending on indexes and query shape.

For anti-join style logic, compare `EXCEPT`, `NOT EXISTS`, and `LEFT JOIN ... IS NULL` with `EXPLAIN ANALYZE` instead of assuming one form is always faster.

#### Traps / caveats

- Input queries must have the same number of columns and compatible types.
- Default `INTERSECT` and `EXCEPT` remove duplicates.
- For anti-join logic, compare `EXCEPT`, `NOT EXISTS`, and left join depending on readability and performance.
- Set operations may require sorting or hashing, especially when duplicates must be removed.
- Column names in the final result come from the first query.

#### Optional Anki

Q: What does `INTERSECT` return?
A: Rows common to both result sets.

Q: What does `EXCEPT` return?
A: Rows from the first result set that are not in the second.

</details>

<details>
<summary><strong>DB-SQL-014. What is the difference between COUNT(*) and COUNT(column)?</strong></summary>

#### Short answer

`COUNT(*)` counts rows. `COUNT(column)` counts only rows where that column is not `NULL`.

#### Interview answer

`COUNT(*)` means “how many rows are in the group or result set”. It does not care whether any particular column is null.

`COUNT(column)` counts non-null values in that column. This is useful when we want to know how many rows actually have a value.

#### Deep dive

```sql
SELECT
    COUNT(*) AS total_rows,
    COUNT(delivered_at) AS delivered_rows
FROM orders;
```

If `delivered_at` is null for pending orders, `COUNT(delivered_at)` counts only delivered orders.

#### Production angle

This difference is common in reports and metrics. Using the wrong count can silently produce wrong dashboards, conversion rates, or SLA numbers.

#### Traps / caveats

- `COUNT(1)` is not meaningfully faster than `COUNT(*)` in PostgreSQL.
- `COUNT(*)` on a large table is not an O(1) metadata lookup; PostgreSQL usually has to count rows visible to the current MVCC snapshot.
- `COUNT(column)` ignores nulls.
- `COUNT(DISTINCT column)` counts distinct non-null values.
- On very large tables, exact counts can be expensive in PostgreSQL.

#### Optional Anki

Q: What does `COUNT(*)` count?
A: Rows.

Q: What does `COUNT(column)` ignore?
A: `NULL` values.

</details>

<a id="db-sql-016"></a>

<details>
<summary><strong>DB-SQL-016. What are aggregate functions?</strong></summary>

#### Short answer

Aggregate functions calculate one value from many rows, usually for the whole result set or per `GROUP BY` group.

#### Interview answer

Common aggregate functions are `COUNT`, `SUM`, `AVG`, `MIN`, and `MAX`. PostgreSQL also has aggregates like `array_agg`, `json_agg`, and `string_agg`.

They are often used with `GROUP BY`. Without `GROUP BY`, the aggregate is calculated over the whole result set.

#### Deep dive

```sql
SELECT customer_id, SUM(total_amount) AS revenue
FROM orders
GROUP BY customer_id;
```

Most aggregates ignore `NULL`. For example, `AVG(score)` averages only non-null scores.

#### Production angle

Aggregates are common in reporting and APIs. On large tables, they can be expensive, so indexes, pre-aggregation, materialized views, or streaming pipelines may be needed.

#### Traps / caveats

- Most aggregates ignore `NULL`; `COUNT(*)` counts rows.
- `WHERE` filters rows before aggregation; `HAVING` filters groups after aggregation.
- Aggregating after an accidental one-to-many join can inflate numbers.
- Large aggregations may spill to disk if memory is insufficient.

#### Optional Anki

Q: Name common aggregate functions.
A: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`.

</details>

<a id="db-sql-017"></a>

<details>
<summary><strong>DB-SQL-017. What is a CTE / WITH query?</strong></summary>

#### Short answer

A CTE is a named temporary result inside one SQL statement, defined with `WITH`. It makes complex queries easier to structure and can be recursive.

#### Interview answer

CTE stands for Common Table Expression. It lets us define a named subquery at the beginning of a statement and then use it in the main query.

CTEs are useful for readability, step-by-step transformations, sharing a subquery inside one statement, and recursive queries.

In PostgreSQL, CTEs can be inlined by the optimizer in many cases, and we can also use `MATERIALIZED` or `NOT MATERIALIZED` when needed.

#### Deep dive

```sql
WITH paid_orders AS (
    SELECT *
    FROM orders
    WHERE status = 'PAID'
)
SELECT customer_id, COUNT(*)
FROM paid_orders
GROUP BY customer_id;
```

The CTE names the intermediate result and makes the final query easier to read.

#### Production angle

CTEs improve maintainability of complex SQL, especially reports and data migrations. But always check the execution plan for heavy queries, because materialization or repeated work can affect performance.

#### Traps / caveats

- CTE is scoped to one statement only.
- CTE is not the same as a temporary table.
- Performance behavior differs between PostgreSQL versions and between databases.
- Before PostgreSQL 12, CTEs commonly acted as optimization fences, so old advice about CTE performance may be version-dependent.
- Data-modifying CTEs exist, but they can make statements harder to reason about and should be used carefully.
- A CTE can improve readability but does not automatically improve performance.

#### Optional Anki

Q: What keyword defines a CTE?
A: `WITH`.

Q: Is a CTE visible outside the statement?
A: No.

</details>

<a id="db-sql-018"></a>

<details>
<summary><strong>🧠 DB-SQL-018. What is a recursive CTE?</strong></summary>

#### Short answer

A recursive CTE is a `WITH RECURSIVE` query that refers to itself. It is used for hierarchies, trees, graphs, and repeated expansion.

#### Interview answer

A recursive CTE has two parts: a non-recursive base query and a recursive query that references the CTE name. The database repeatedly runs the recursive part until no new rows are produced.

Typical examples are category trees, organization charts, comments with replies, and graph traversal.

#### Deep dive

```sql
WITH RECURSIVE category_tree AS (
    SELECT id, parent_id, name
    FROM categories
    WHERE id = 10

    UNION ALL

    SELECT c.id, c.parent_id, c.name
    FROM categories c
    JOIN category_tree t ON c.parent_id = t.id
)
SELECT *
FROM category_tree;
```

#### Production angle

Recursive CTEs are convenient, but for deep or frequently queried hierarchies, consider indexing parent columns, limiting depth, caching, closure tables, materialized paths, or denormalized read models.

#### Traps / caveats

- Cycles can cause repeated traversal unless handled.
- Use `UNION ALL` when deduplication is not required; `UNION` adds deduplication cost.
- For graph-like data, add explicit cycle protection; PostgreSQL also supports `SEARCH` and `CYCLE` syntax in modern versions.
- Recursive queries can become expensive on large graphs.
- Use indexes on parent/reference columns.
- Consider adding depth limits for safety.

#### Optional Anki

Q: What keyword starts a recursive CTE?
A: `WITH RECURSIVE`.

Q: What are recursive CTEs often used for?
A: Trees, hierarchies, and graph traversal.

</details>

<a id="db-sql-019"></a>

<details>
<summary><strong>DB-SQL-019. What is a view?</strong></summary>

#### Short answer

A view is a named saved SQL query that can be used like a virtual table. It usually stores the query definition, not the data.

#### Interview answer

A view hides query complexity behind a database object. Instead of repeating a complex join or filter in many places, we can define it once and query the view.

Views are also useful for access control: we can expose only certain columns or rows to some users.

#### Deep dive

```sql
CREATE VIEW active_users AS
SELECT id, email
FROM users
WHERE deleted_at IS NULL;
```

Then:

```sql
SELECT *
FROM active_users;
```

#### Production angle

Views can stabilize read contracts for reporting or integrations. But they do not automatically improve performance; the underlying query still has to be executed.

#### Traps / caveats

- A regular view is not a cached result.
- Complex views can hide expensive queries.
- Changing a view can break consumers.
- Some views are updatable, but not all; it depends on query complexity and database rules.

#### Optional Anki

Q: Does a regular view store data?
A: Usually no; it stores a query definition.

</details>

<a id="db-sql-020"></a>

<details>
<summary><strong>🧠 DB-SQL-020. What is a materialized view in PostgreSQL?</strong></summary>

#### Short answer

A materialized view stores the result of a query physically. It can make expensive reads faster, but the data becomes stale until the materialized view is refreshed.

#### Interview answer

In PostgreSQL, a materialized view is similar to a cached table created from a query. Unlike a regular view, it stores data on disk.

We use it when the query is expensive and the application can tolerate stale data, for example reports, dashboards, or precomputed search data.

To update the data, we run `REFRESH MATERIALIZED VIEW`. PostgreSQL also supports `REFRESH MATERIALIZED VIEW CONCURRENTLY`, but it requires a suitable `UNIQUE` index on the materialized view that covers all rows and uses only column names, not an expression or partial index.

#### Deep dive

```sql
CREATE MATERIALIZED VIEW daily_sales AS
SELECT date_trunc('day', created_at) AS day,
       SUM(total_amount) AS revenue
FROM orders
GROUP BY date_trunc('day', created_at);
```

```sql
REFRESH MATERIALIZED VIEW daily_sales;
```

#### Production angle

Materialized views are useful for read-heavy reporting workloads. The key production questions are refresh frequency, refresh duration, locking behavior, staleness tolerance, and whether indexes are needed on the materialized view.

#### Traps / caveats

- Materialized views are not updated automatically when base tables change.
- Data can be stale between refreshes.
- Refresh can be expensive and may need scheduling.
- `REFRESH ... CONCURRENTLY` requires at least one suitable `UNIQUE` index on the materialized view that includes all rows and is not an expression or partial index.
- `REFRESH ... CONCURRENTLY` can reduce read blocking, but it is usually slower and still consumes resources.
- Indexes on base tables do not replace indexes on the materialized view itself.

#### Optional Anki

Q: Does a materialized view store data?
A: Yes, it stores the query result physically.

Q: How is a PostgreSQL materialized view updated?
A: With `REFRESH MATERIALIZED VIEW`.

</details>
