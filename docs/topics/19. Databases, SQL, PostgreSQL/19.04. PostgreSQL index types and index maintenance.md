# PostgreSQL index types and index maintenance

---

<a id="db-idxtype-001"></a>

<details>
<summary><strong>DB-IDXTYPE-001. What index types does PostgreSQL support?</strong></summary>

#### Short answer

PostgreSQL has several built-in index access methods: B-tree, Hash, GiST, SP-GiST, GIN and BRIN. B-tree is the default and covers most common equality, range and sorting use cases. Extensions can add more specialized access methods.

#### Interview answer

For a backend interview, I would start with B-tree as the default index type. Then I would mention that other index types exist for special data and operators: GIN for composite values like arrays, `jsonb` and full-text search, GiST/SP-GiST for specialized structures, and BRIN for very large physically ordered tables.

#### Deep dive

The index type is selected with `USING`:

```sql
CREATE INDEX idx_users_email ON users USING btree (email);
CREATE INDEX idx_events_payload ON events USING gin (payload);
```

The important idea is that an index is not only a data structure; it is also tied to supported operators through operator classes.

#### Production angle

In production, most indexes are B-tree. Use other types only when the query operators and data types require them, and confirm the choice with `EXPLAIN ANALYZE`.

#### Traps / caveats

- Do not choose GIN, GiST or BRIN just because they sound more advanced.
- The same column may need different index types for different query patterns.
- Operator class matters as much as index type.
- Extra index types often have different write costs and maintenance behavior.
- Extension-provided access methods, for example `bloom`, are extra tools, not defaults for normal OLTP schemas.

#### Optional Anki

Q: What is the default PostgreSQL index type?
A: B-tree.

</details>

<a id="db-idxtype-002"></a>

<details>
<summary><strong>DB-IDXTYPE-002. When would you use a B-tree index?</strong></summary>

#### Short answer

Use a B-tree index for the common ordered comparison patterns: equality, range filters, sorting, uniqueness and many foreign-key or join lookups.

#### Interview answer

B-tree is the default because it works well for scalar values that can be ordered: numbers, timestamps, text, UUIDs and many other types. It supports predicates like `=`, `<`, `>`, `BETWEEN`, `IS NULL`, and can also help with `ORDER BY`.

#### Deep dive

Typical examples:

```sql
CREATE INDEX idx_orders_user_id ON orders (user_id);
CREATE INDEX idx_orders_created_at ON orders (created_at DESC);
CREATE UNIQUE INDEX idx_users_email ON users (email);
```

#### Production angle

For Java backend systems, B-tree indexes are usually the first tool for slow endpoints with selective filters, joins by IDs, pagination by timestamp/id, and uniqueness checks. Start with query shape and selectivity, not with “index every column”.

#### Traps / caveats

- B-tree is not good for arbitrary substring search like `LIKE '%abc%'` without special extensions/operator classes.
- A B-tree on a low-selectivity column may be ignored.
- Composite B-tree indexes depend heavily on column order.
- An index that helps reads can hurt writes.

#### Optional Anki

Q: Common B-tree use cases?
A: Equality, ranges, sorting, uniqueness and joins on ordered scalar columns.

</details>

<a id="db-idxtype-003"></a>

<details>
<summary><strong>🧠 DB-IDXTYPE-003. When would you use a Hash index?</strong></summary>

#### Short answer

A Hash index is used for equality lookups only. In practice, B-tree is usually preferred unless measurement shows that Hash is better for a very specific equality-only workload.

#### Interview answer

Hash indexes store hash values and support equality comparisons. They do not preserve ordering, so they cannot help with range predicates or `ORDER BY`.

#### Deep dive

Example:

```sql
CREATE INDEX idx_sessions_token_hash
ON sessions USING hash (token);
```

This can theoretically help for `WHERE token = ?`, but a B-tree on `token` often works well too.

#### Production angle

Use Hash indexes carefully. They are a niche option; the cost of surprising future maintainers may be higher than the small performance gain. If you use one, document why and keep the benchmark or `EXPLAIN ANALYZE` evidence.

#### Traps / caveats

- Hash indexes do not support range scans.
- They do not support sorting.
- They are not a general replacement for B-tree.
- They are usually not the first choice for normal backend schemas.

#### Optional Anki

Q: What can a Hash index support?
A: Equality lookups only.

</details>

<a id="db-idxtype-004"></a>

<details>
<summary><strong>DB-IDXTYPE-004. What is a GIN index?</strong></summary>

#### Short answer

GIN means Generalized Inverted Index. It is useful when one table row contains multiple searchable elements, such as array elements, `jsonb` keys/values, full-text lexemes or trigram tokens.

#### Interview answer

I explain GIN as an inverted index: instead of mapping one row to one key, it maps each contained key or token to the rows that contain it. This is why it works well for “contains” style queries.

#### Deep dive

Examples:

```sql
CREATE INDEX idx_posts_tags ON posts USING gin (tags);
CREATE INDEX idx_events_payload ON events USING gin (payload jsonb_path_ops);
CREATE INDEX idx_documents_search ON documents USING gin (to_tsvector('english', body));
```

Common operators include array containment, `jsonb` containment and full-text search operators. For substring search, GIN is often used together with the `pg_trgm` extension.

#### Production angle

GIN is powerful but not free. It can be larger and more expensive to update than B-tree. For high-write tables, check write overhead, pending list behavior, index size and actual query plans.

#### Traps / caveats

- GIN is usually not for simple scalar equality; B-tree is often better there.
- GIN can be large.
- GIN writes can be expensive.
- The operator class matters: `jsonb_ops`, `jsonb_path_ops`, `gin_trgm_ops` behave differently.
- A GIN index helps only if the query uses compatible operators.

#### Optional Anki

Q: What is GIN good for?
A: Searching inside composite values: arrays, `jsonb`, full-text vectors and trigram tokens.

</details>

---

<a id="db-idxtype-005"></a>

<details>
<summary><strong>DB-IDXTYPE-005. When would you use a GIN index?</strong></summary>

#### Short answer

Use a GIN index when queries search inside a composite value: array contains element, `jsonb` contains path/value, full-text search matches lexemes, or trigram search matches text fragments.

#### Interview answer

Typical use cases are tags, permissions arrays, JSONB metadata, document search and flexible filters over semi-structured data. The key is that the query must use operators supported by the GIN operator class.

#### Deep dive

Examples:

```sql
-- array containment
SELECT * FROM posts WHERE tags @> ARRAY['java'];

-- JSONB containment
SELECT * FROM events WHERE payload @> '{"type": "ORDER_CREATED"}';

-- trigram search with pg_trgm
SELECT * FROM users WHERE email ILIKE '%example%';
```

#### Production angle

Before adding a GIN index, check whether the data should really be stored as JSON/array or modeled relationally. A GIN index can make flexible queries fast, but it can also hide a weak schema design.

#### Traps / caveats

- Do not add GIN to every JSONB column by default.
- GIN is often read-optimized and can be costly for writes.
- Choose the right operator class.
- For frequently queried JSON keys, expression indexes or normalized columns may be better.

#### Optional Anki

Q: When should you consider GIN?
A: When searching inside arrays, JSONB, full-text vectors or trigram tokens.

</details>

<a id="db-idxtype-006"></a>

<details>
<summary><strong>🧠 DB-IDXTYPE-006. What is a GiST index?</strong></summary>

#### Short answer

GiST means Generalized Search Tree. It is a flexible index framework used for data types and operators where B-tree ordering is not enough, such as geometric data, ranges, nearest-neighbor search and exclusion constraints.

#### Interview answer

GiST indexes do not have one fixed meaning like B-tree. Their behavior depends on the operator class. They can represent bounding boxes, ranges or other summary predicates and use them to narrow the search.

#### Deep dive

Common examples include range overlap queries and PostGIS spatial indexes:

```sql
CREATE INDEX idx_bookings_period
ON bookings USING gist (period);

CREATE INDEX idx_places_geom
ON places USING gist (geom);
```

#### Production angle

GiST often appears in production for scheduling conflicts, geospatial search and exclusion constraints like “two bookings for the same room must not overlap”.

#### Traps / caveats

- GiST can be lossy, so PostgreSQL may need a recheck condition.
- The operator class defines what the index can do.
- For simple equality/range over scalar columns, B-tree is usually better.
- Spatial use cases often depend on extensions such as PostGIS.

#### Optional Anki

Q: What is GiST used for?
A: Specialized operators such as ranges, geometry, nearest-neighbor search and exclusion constraints.

</details>

---

<a id="db-idxtype-007"></a>

<details>
<summary><strong>🧠 DB-IDXTYPE-007. When would you use a GiST index?</strong></summary>

#### Short answer

Use GiST when the query is based on specialized operators such as range overlap, spatial relationships, nearest-neighbor search or exclusion constraints.

#### Interview answer

For example, a booking system can use a range column and an exclusion constraint to prevent overlapping reservations. A maps/search system can use GiST with PostGIS geometry.

#### Deep dive

Example of preventing overlapping bookings:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE room_bookings
ADD CONSTRAINT no_overlapping_bookings
EXCLUDE USING gist (
  room_id WITH =,
  period WITH &&
);
```

#### Production angle

In production, GiST is valuable when it enforces correctness, not only performance. Exclusion constraints can move complex concurrency-sensitive checks from application code into the database.

#### Traps / caveats

- GiST is not a default replacement for B-tree.
- Range and spatial indexes require query operators that match the operator class.
- Exclusion constraints may need extensions like `btree_gist` for scalar equality columns.
- Always test under concurrent writes if the constraint protects business correctness.

#### Optional Anki

Q: Give a practical GiST use case.
A: Preventing overlapping ranges with an exclusion constraint, or spatial search with PostGIS.

</details>

<a id="db-idxtype-008"></a>

<details>
<summary><strong>🧠 DB-IDXTYPE-008. What is an SP-GiST index?</strong></summary>

#### Short answer

SP-GiST means Space-Partitioned GiST. It supports partitioned search structures for data that can be naturally split into non-overlapping regions or prefixes.

#### Interview answer

SP-GiST is useful for specialized structures such as quadtrees, k-d trees, radix trees and tries. Typical examples include certain geometric data, IP/network-like data, text prefixes and nearest-neighbor-style searches depending on operator class.

#### Deep dive

Unlike B-tree, SP-GiST is not a general-purpose index type. It is selected when the data distribution and operators match a space-partitioning strategy.

#### Production angle

A senior answer should not pretend SP-GiST is used daily in normal CRUD services. It is enough to know what class of problems it solves and when to look it up.

#### Traps / caveats

- It is specialized and operator-class dependent.
- Most backend projects never need it directly.
- Do not use it unless query operators and data type clearly match.
- Benchmark against GiST/B-tree/GIN when unsure.

#### Optional Anki

Q: What is SP-GiST for?
A: Specialized space-partitioned data structures such as tries, quadtrees or k-d trees.

</details>

<a id="db-idxtype-009"></a>

<details>
<summary><strong>DB-IDXTYPE-009. What is a BRIN index?</strong></summary>

#### Short answer

BRIN means Block Range Index. It stores compact summaries for ranges of table pages instead of storing every indexed value. It is tiny and useful for very large tables where values are physically correlated with table order.

#### Interview answer

I would describe BRIN as a “page-range summary index”. For example, if rows are inserted by time, then rows with close `created_at` values are often located near each other physically. BRIN can store min/max timestamps per block range and skip ranges that cannot match.

#### Deep dive

Example:

```sql
CREATE INDEX idx_events_created_at_brin
ON events USING brin (created_at);
```

#### Production angle

BRIN is a strong option for huge append-only or time-series tables when a B-tree would be very large. It will not find individual rows as precisely as B-tree, but it can skip large irrelevant parts of the table with very little index storage.

#### Traps / caveats

- BRIN works best when indexed values are correlated with physical order.
- If data is randomly distributed, BRIN may be ineffective.
- BRIN usually produces lossy matches and requires heap rechecks.
- It is not a replacement for B-tree on highly selective random lookups.

#### Optional Anki

Q: What is BRIN good for?
A: Very large tables where values are physically ordered or correlated, such as time-series by `created_at`.

</details>

---

<a id="db-idxtype-010"></a>

<details>
<summary><strong>DB-IDXTYPE-010. Why is BRIN useful for large append-only or time-series tables?</strong></summary>

#### Short answer

Because append-only/time-series data is often physically ordered by time, and BRIN can summarize page ranges instead of indexing every row. This makes the index very small while still allowing PostgreSQL to skip irrelevant ranges.

#### Interview answer

For example, an `events` table may receive rows in increasing `created_at` order. A query for last week only needs recent page ranges. BRIN can quickly identify which ranges may contain that time interval.

#### Deep dive

Example query:

```sql
SELECT *
FROM events
WHERE created_at >= now() - interval '7 days';
```

#### Production angle

BRIN is often used when B-tree index size and maintenance cost become painful. It trades precision for small size and cheap maintenance. That is a good trade-off for very large historical tables with range scans.

#### Traps / caveats

- BRIN does not magically make all time-series queries fast.
- Out-of-order inserts reduce physical correlation.
- You still need to check `EXPLAIN ANALYZE` and buffers.
- Partitioning and BRIN are often complementary for time-series data.

#### Optional Anki

Q: Why is BRIN small?
A: It stores summaries for block ranges, not every indexed value.

</details>

<a id="db-idxtype-011"></a>

<details>
<summary><strong>🧠 DB-IDXTYPE-011. What is an operator class?</strong></summary>

#### Short answer

An operator class defines how a data type can be indexed by a specific index method: which operators are supported and how values are compared or searched.

#### Interview answer

The same data type can have different operator classes for different query semantics. For example, text can use the default B-tree operator class for normal ordering, or pattern operator classes for prefix pattern matching in some collations. JSONB can use different GIN operator classes with different trade-offs.

#### Deep dive

Examples:

```sql
CREATE INDEX idx_users_email_pattern
ON users (email text_pattern_ops);

CREATE INDEX idx_events_payload_path
ON events USING gin (payload jsonb_path_ops);
```

#### Production angle

Operator classes are a common reason why “I created an index but it is not used”. The index must match the operator used in the query.

#### Traps / caveats

- Index type and operator class are different concepts.
- The default operator class is not always right for pattern matching or JSONB containment.
- A query must use operators supported by the index operator class.
- Changing operator class can change index size and behavior.

#### Optional Anki

Q: What does an operator class define?
A: Which operators and comparison/search semantics an index supports for a data type.

</details>

<a id="db-idxtype-012"></a>

<details>
<summary><strong>DB-IDXTYPE-012. Why can LIKE 'abc%' use an index, but LIKE '%abc' usually cannot?</strong></summary>

#### Short answer

`LIKE 'abc%'` has a fixed prefix, so a B-tree can use it as a range search when the collation and operator class support that pattern. `LIKE '%abc'` has a leading wildcard, so there is no fixed starting point in the B-tree.

#### Interview answer

A B-tree is ordered from left to right. Prefix search can map to a contiguous range: from `abc` to values before the next prefix. In PostgreSQL, non-`C` collations may require pattern operator classes such as `text_pattern_ops`. Contains/suffix search does not map to a normal B-tree range because the beginning of the string is unknown.

#### Deep dive

For contains search, PostgreSQL commonly uses `pg_trgm` with GIN or GiST:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_users_email_trgm
ON users USING gin (email gin_trgm_ops);

SELECT *
FROM users
WHERE email ILIKE '%example%';
```

#### Production angle

For API search endpoints, choose the search type deliberately: exact lookup, prefix autocomplete, substring search, full-text search and fuzzy search need different indexes and sometimes different systems.

#### Traps / caveats

- Collation can affect whether a normal B-tree helps prefix `LIKE`; pattern operator classes may be needed.
- `ILIKE` and case-insensitive search may require expression indexes or trigram indexes.
- Trigram indexes can be large and write-expensive.
- For real full-text search, use full-text search features rather than many `ILIKE` filters.

#### Optional Anki

Q: Why can `LIKE 'abc%'` use B-tree?
A: Because it has a fixed prefix that maps to a B-tree range.

Q: What index helps `LIKE '%abc%'`?
A: Usually a trigram index with `pg_trgm`, often GIN.

</details>

<a id="db-idxtype-013"></a>

<details>
<summary><strong>DB-IDXTYPE-013. What is index bloat?</strong></summary>

#### Short answer

Index bloat is wasted space inside an index, often caused by updates, deletes, page splits and dead index entries that are not fully reclaimed or compacted.

#### Interview answer

In PostgreSQL, MVCC creates new tuple versions on update. Indexes can accumulate entries pointing to old tuple versions. VACUUM can clean dead entries, but it does not always shrink the index file back to an ideal compact size.

#### Deep dive

Bloat means more pages to read, worse cache efficiency, more disk usage and sometimes slower index scans. Heavy update/delete workloads are typical candidates.

#### Production angle

In production, index bloat is investigated with index sizes, table statistics, extension-based tools such as `pgstattuple`, and query symptoms. Fixes may include `REINDEX CONCURRENTLY`, dropping unused indexes, better fillfactor or reducing unnecessary updates.

#### Traps / caveats

- Bloat is not the same as “large index”; a large index may be necessary.
- VACUUM helps but may not fully compact the index.
- Reindexing a hot production table must be planned carefully.
- Bloat symptoms may look like general IO or cache problems.

#### Optional Anki

Q: What is index bloat?
A: Wasted space inside an index that increases size and can hurt performance.

</details>

<a id="db-idxtype-014"></a>

<details>
<summary><strong>DB-IDXTYPE-014. How can you detect unused indexes?</strong></summary>

#### Short answer

Start with PostgreSQL statistics views such as `pg_stat_user_indexes`, especially `idx_scan`, and combine that with index size, uptime/stat reset time, query logs and domain knowledge.

#### Interview answer

An index with `idx_scan = 0` for a long representative period may be unused. But this is only a signal, not proof. It may be used rarely for critical maintenance/reporting queries or constraints.

#### Deep dive

Example query:

```sql
SELECT
  schemaname, relname AS table_name, indexrelname AS index_name,
  idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC, pg_relation_size(indexrelid) DESC;
```

#### Production angle

Before dropping an index, check whether it backs a primary key, unique constraint or exclusion constraint, whether statistics were recently reset, and whether the observation window included batch jobs and monthly reports.

#### Traps / caveats

- `idx_scan = 0` does not always mean safe to drop.
- Stats reset after restart or manual reset.
- Rare but critical queries may need the index.
- Dropping an index can break constraints if it is constraint-backed.
- Always use a review process before dropping production indexes.

#### Optional Anki

Q: Which view helps find unused indexes?
A: `pg_stat_user_indexes`.

</details>

<a id="db-idxtype-015"></a>

<details>
<summary><strong>DB-IDXTYPE-015. How can you detect duplicate or redundant indexes?</strong></summary>

#### Short answer

Compare index definitions: indexed columns, column order, uniqueness, predicates, expressions, included columns, operator classes and sort order. Redundant indexes often have the same or overlapping definitions.

#### Interview answer

A simple duplicate is two indexes on exactly the same columns with the same options. A redundant index can be more subtle, for example an index on `(user_id)` may be covered by `(user_id, created_at)` for some query patterns, but not always.

#### Deep dive

Useful catalog sources include `pg_indexes`, `pg_index`, `pg_class`, `pg_attribute` and extension/tooling queries from `pg_stat_statements` or DBA scripts.

#### Production angle

In production, avoid mechanical cleanup. Validate with real query patterns, constraints and `EXPLAIN`. Sometimes two similar indexes exist because one supports uniqueness or ordering and the other supports a different predicate or operator class.

#### Traps / caveats

- Column order matters.
- Predicates matter for partial indexes.
- Included columns matter for index-only scans.
- A unique index is not equivalent to a non-unique index.
- Dropping a redundant-looking index can regress a specific query.

#### Optional Anki

Q: What should you compare to find duplicate indexes?
A: Columns, order, predicates, expressions, included columns, operator classes and uniqueness.

</details>

<a id="db-idxtype-016"></a>

<details>
<summary><strong>DB-IDXTYPE-016. What are the risks of having too many indexes?</strong></summary>

#### Short answer

Too many indexes increase disk usage, slow down writes, generate more WAL, increase vacuum/autovacuum work, worsen cache efficiency and make schema maintenance harder.

#### Interview answer

Every `INSERT` must add entries to all relevant indexes. Every `UPDATE` may need to update indexes if indexed columns change, and even updates of non-indexed columns can interact with MVCC/HOT behavior. Every `DELETE` leaves cleanup work.

#### Deep dive

Too many indexes can also confuse humans. Developers may add a new index instead of understanding existing composite indexes, which leads to duplication and long-term performance debt.

#### Production angle

In production, index design is a lifecycle process: add indexes for measured needs, monitor usage, remove redundant indexes carefully, and consider write-heavy workload impact.

#### Traps / caveats

- Indexing every foreign key and every column blindly is not always correct.
- Indexes increase backup/restore and replication workload indirectly through data size and WAL.
- Unused indexes can still slow writes.
- More indexes mean more objects to review during migrations.

#### Optional Anki

Q: Main risk of too many indexes?
A: Higher write and maintenance cost.

</details>

<a id="db-idxtype-017"></a>

<details>
<summary><strong>DB-IDXTYPE-017. What is CREATE INDEX CONCURRENTLY?</strong></summary>

#### Short answer

`CREATE INDEX CONCURRENTLY` builds an index without blocking normal writes to the table. It is the safer PostgreSQL option for adding indexes to large production tables.

#### Interview answer

A normal `CREATE INDEX` can block writes while the index is being built. `CONCURRENTLY` avoids locking out writes, but it is slower and more expensive because PostgreSQL needs more work and coordination with concurrent transactions.

#### Deep dive

Example:

```sql
CREATE INDEX CONCURRENTLY idx_orders_user_created
ON orders (user_id, created_at DESC);
```

#### Production angle

For Java backend deployments, `CONCURRENTLY` is important because a blocking index migration can freeze writes and cause API errors, timeouts, queue buildup or incident-level impact.

#### Traps / caveats

- It cannot run inside a normal transaction block.
- It takes longer than a normal index build.
- It still needs some locks and waits for transactions.
- Only one concurrent index build can run on the same table at a time.
- If it fails, an invalid index may remain and must be cleaned up.
- It can create IO pressure and replication lag.

#### Optional Anki

Q: Why use `CREATE INDEX CONCURRENTLY`?
A: To build an index without blocking normal writes to the table.

</details>

---

<a id="db-idxtype-018"></a>

<details>
<summary><strong>DB-IDXTYPE-018. Why is CREATE INDEX CONCURRENTLY useful in production?</strong></summary>

#### Short answer

It allows adding an index to a live table while reads and writes continue, reducing the risk of downtime caused by blocking DDL.

#### Interview answer

Production services often cannot stop writes for a long index build. Without `CONCURRENTLY`, an index creation on a large hot table can block inserts, updates and deletes, which can cascade into application errors.

#### Deep dive

A good deployment plan uses `CREATE INDEX CONCURRENTLY` as a separate migration step, monitors locks and IO, and verifies the new plan after the index is ready.

#### Production angle

This is especially important for SaaS/online systems where migrations run while traffic is active. It does not mean “no risk”; it means lower locking risk with higher duration and resource cost.

#### Traps / caveats

- It reduces write blocking but does not remove all operational risk.
- It can increase load for a long time.
- It should be scheduled and monitored.
- It is often incompatible with migration frameworks that wrap every migration in one transaction unless configured.

#### Optional Anki

Q: What production problem does `CREATE INDEX CONCURRENTLY` solve?
A: It avoids blocking normal writes during index creation.

</details>

<a id="db-idxtype-019"></a>

<details>
<summary><strong>🧠 DB-IDXTYPE-019. What are the downsides of CREATE INDEX CONCURRENTLY?</strong></summary>

#### Short answer

It is slower, uses more resources, cannot run inside a regular transaction block, still waits for transactions, allows only one concurrent build per table, and can leave an invalid index if it fails.

#### Interview answer

`CONCURRENTLY` trades locking safety for operational complexity. PostgreSQL must scan the table more than once and coordinate with concurrent changes to make sure the final index is valid.

#### Deep dive

If the statement fails, for example due to timeout or cancellation, you may see an invalid index in the catalog. It consumes space, can still add update overhead, and may need `DROP INDEX CONCURRENTLY` before retrying. A failed concurrent unique index build can be especially surprising because uniqueness may start being enforced before the command fully succeeds.

#### Production angle

In migration tools, concurrent index creation often must be executed outside the normal transactional migration. This requires explicit tool configuration and review.

#### Traps / caveats

- It is not free downtime prevention.
- It can cause IO pressure and replication lag.
- It cannot run inside a normal transaction block.
- Only one concurrent index build is allowed on the same table at a time.
- Failed concurrent builds need cleanup.
- Invalid indexes are ignored for reads, but they can still consume storage and update work.
- Failed concurrent unique indexes can still affect uniqueness checks.
- Do not run many heavy concurrent index builds without capacity planning.

#### Optional Anki

Q: Main downside of `CREATE INDEX CONCURRENTLY`?
A: It avoids blocking writes but takes longer and uses more resources.

</details>

<a id="db-idxtype-020"></a>

<details>
<summary><strong>DB-IDXTYPE-020. How would you safely add an index to a large production table?</strong></summary>

#### Short answer

First prove the index is needed, design it for a concrete query, test it on production-like data, then add it with `CREATE INDEX CONCURRENTLY`, monitor impact, and verify the resulting plan.

#### Interview answer

My process would be: collect the slow query, inspect `EXPLAIN ANALYZE`, check selectivity and existing indexes, choose index columns/operator class/predicate, estimate size, test on staging or a restored production snapshot, then deploy separately from risky application changes.

#### Deep dive

Example production-safe index:

```sql
CREATE INDEX CONCURRENTLY idx_orders_tenant_created
ON orders (tenant_id, created_at DESC)
WHERE deleted_at IS NULL;
```

#### Production angle

During rollout, monitor locks, CPU, IO, replication lag, table activity and migration timeout behavior. After build, run `ANALYZE` if needed, verify the query plan, and later remove redundant indexes carefully.

#### Traps / caveats

- Do not add indexes blindly during an incident without understanding write impact.
- Avoid normal `CREATE INDEX` on a large hot table.
- Check migration tool transaction settings.
- Have a cleanup plan for invalid indexes.
- Verify improvement with actual production-like queries, not only theory.

#### Optional Anki

Q: Safe way to add an index to a large hot table?
A: Use a measured design and `CREATE INDEX CONCURRENTLY`, monitor impact, then verify the plan.

</details>

<a id="db-idxtype-021"></a>

<details>
<summary><strong>DB-IDXTYPE-021. What are REINDEX and REINDEX CONCURRENTLY?</strong></summary>

#### Short answer

`REINDEX` rebuilds an existing index. `REINDEX CONCURRENTLY` does it with much less blocking for normal reads and writes, but it is slower, more resource-heavy and has operational caveats similar to `CREATE INDEX CONCURRENTLY`.

#### Interview answer

I would use reindexing when an index is bloated, suspected to be corrupted, or needs to be rebuilt after certain maintenance operations. On a hot production table, the concurrent form is usually the safer option because normal `REINDEX` can block writes.

#### Deep dive

Examples:

```sql
REINDEX INDEX CONCURRENTLY idx_orders_user_created;

REINDEX TABLE CONCURRENTLY orders;
```

#### Production angle

In production, do not reindex just because an index is large. First prove bloat or a real symptom. Plan IO, WAL, replication lag, lock waits and migration timeout behavior. For very large indexes, run during a low-traffic window and monitor progress.

#### Traps / caveats

- Large index does not automatically mean bloated index.
- Non-concurrent reindexing can block writes.
- Concurrent reindexing cannot run inside a normal transaction block.
- Reindexing creates IO and WAL pressure.
- System catalog reindexing has extra restrictions.

#### Optional Anki

Q: What does `REINDEX` do?
A: It rebuilds an existing index.

</details>

<details>
<summary><strong>🧠 DB-IDXTYPE-022. How can you monitor index creation progress in PostgreSQL?</strong></summary>

#### Short answer

Use `pg_stat_progress_create_index` for build phase and progress counters, and combine it with lock, IO, CPU, WAL and replication-lag monitoring.

#### Interview answer

For a production index build I want to know what phase it is in, whether it is waiting on lockers, how much of the table scan is done, and whether it is causing system-level pressure. Progress view data is useful, but it is not a full health check by itself.

#### Deep dive

Example:

```sql
SELECT
  pid,
  command,
  phase,
  lockers_total,
  lockers_done,
  blocks_total,
  blocks_done,
  tuples_total,
  tuples_done
FROM pg_stat_progress_create_index;
```

#### Production angle

During online migrations, also watch `pg_locks`, database CPU/IO, slow query latency, dead tuples, WAL volume and replica lag. A concurrent index build can be non-blocking for writes but still harmful if it saturates IO.

#### Traps / caveats

- Progress counters are not always linear.
- A build can spend a long time waiting for old transactions.
- Application-side migration timeouts may cancel the build and leave cleanup work.
- Monitoring only locks is not enough; IO and replicas matter too.

#### Optional Anki

Q: Which view shows index build progress?
A: `pg_stat_progress_create_index`.

<details>
<summary><strong>🧠 DB-IDXTYPE-023. What GIN and BRIN maintenance details matter in production?</strong></summary>

#### Short answer

GIN can have write and pending-list behavior that affects latency. BRIN depends on summarization, physical correlation and settings such as `pages_per_range`. Both need validation with real workload and maintenance monitoring.

#### Interview answer

GIN is often used for JSONB, arrays, full-text search and trigram search, but high write rates can make it expensive. BRIN is tiny and cheap, but only effective when table order correlates with the indexed value and ranges are summarized well.

#### Deep dive

Examples:

```sql
CREATE INDEX idx_events_payload_gin
ON events USING gin (payload)
WITH (fastupdate = on);

CREATE INDEX idx_events_created_at_brin
ON events USING brin (created_at)
WITH (pages_per_range = 128, autosummarize = on);
```

#### Production angle

For GIN, watch index size, write latency, VACUUM behavior and pending-list cleanup. For BRIN, check whether out-of-order writes reduce correlation and whether chosen block ranges are too coarse or too fine. A bad BRIN can look cheap but still fail to filter enough pages.

#### Traps / caveats

- GIN can be very large and write-expensive.
- GIN pending-list cleanup can cause latency spikes.
- BRIN needs summarized ranges; unsummarized ranges reduce usefulness.
- BRIN is not a precise point-lookup index.
- Changing storage parameters requires testing, not guessing.

#### Optional Anki

Q: What does BRIN depend on most?
A: Physical correlation between indexed values and table order.

</details>

<a id="db-idxtype-024"></a>

<details>
<summary><strong>🧠 DB-IDXTYPE-024. How do indexes work with partitioned tables in PostgreSQL?</strong></summary>

#### Short answer

Indexes on partitioned tables are physically maintained per partition. A parent partitioned index represents matching indexes on partitions. For large live partitioned tables, index rollout often has to be planned partition by partition.

#### Interview answer

The planner can use partition pruning to touch fewer partitions, and then use local indexes inside those partitions. PostgreSQL currently does not support `CREATE INDEX CONCURRENTLY` directly on a partitioned table, so a common production approach is to build indexes concurrently on partitions and then attach or create the parent metadata index.

#### Deep dive

Typical staged idea:

```sql
CREATE INDEX CONCURRENTLY idx_events_2026_01_tenant_created
ON events_2026_01 (tenant_id, created_at);

CREATE INDEX CONCURRENTLY idx_events_2026_02_tenant_created
ON events_2026_02 (tenant_id, created_at);
```

After partition indexes exist, the parent partitioned index step can be much cheaper because it is mostly metadata.

#### Production angle

For time-series systems, partitioning and indexing should be designed together. Old cold partitions may need fewer or different indexes than the hot partition. New partitions must get the right indexes automatically through migrations or partition-management tooling.

#### Traps / caveats

- Do not assume one global physical index exists across all partitions.
- Missing indexes on new partitions can cause sudden regressions.
- Concurrent parent index builds are not supported; plan per-partition rollout.
- Unique indexes on partitioned tables have restrictions around partition keys.
- Partition pruning and index usage are different optimizations; you often need both.

#### Optional Anki

Q: Are partitioned-table indexes one global physical index in PostgreSQL?
A: No. They are represented at the parent level but physically maintained per partition.

</details>
