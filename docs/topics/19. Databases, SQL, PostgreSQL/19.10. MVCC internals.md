# MVCC internals

---

<a id="db-mvcc-001"></a>

<details>
<summary><strong>DB-MVCC-001. What is MVCC in PostgreSQL?</strong></summary>

#### Short answer

MVCC means Multi-Version Concurrency Control. PostgreSQL keeps multiple row versions and lets each transaction read a consistent snapshot.

#### Interview answer

MVCC is PostgreSQL’s main concurrency model. Instead of making readers wait for writers, PostgreSQL usually lets readers see the row version that is visible to their snapshot while writers create newer row versions.

#### Deep dive

Each heap tuple has MVCC metadata. Visibility is not just “latest row wins”; PostgreSQL checks transaction IDs, snapshots, commit status, and tuple metadata to decide whether a tuple version is visible.

#### Production angle

MVCC explains dead tuples, table bloat, autovacuum pressure, old snapshots, index-only scan heap fetches, and why long transactions can hurt the whole database.

#### Traps / caveats

- MVCC reduces read/write blocking, but does not remove all locks.
- Write-write conflicts can still block.
- Dead tuples must be cleaned by VACUUM.
- Long-running snapshots can prevent cleanup.

#### Optional Anki

Q: What is MVCC?
A: PostgreSQL’s snapshot-based concurrency model that stores multiple row versions.

</details>

<a id="db-mvcc-006"></a>

<details>
<summary><strong>DB-MVCC-006. Why does UPDATE create a new row version instead of modifying the row in place?</strong></summary>

#### Short answer

Because old transactions may still need the old version while newer transactions should see the updated version.

#### Interview answer

In-place modification would break snapshot consistency. PostgreSQL creates a new tuple version and keeps the old one until it is no longer visible to any active snapshot.

#### Deep dive

This improves concurrency but creates dead tuples, WAL, and potentially new index entries. If indexed columns are unchanged and there is free space on the same page, a HOT update can keep the update chain on the heap page and avoid new index entries.

#### Production angle

Update-heavy tables need autovacuum tuning, careful indexing, short transactions, and sometimes lower `fillfactor` so HOT updates have room on the page.

#### Traps / caveats

- Updating indexed columns is more expensive because indexes usually need new entries.
- Frequent updates can cause table and index bloat.
- HOT updates depend on unchanged indexed columns, page free space, and later pruning/VACUUM.

#### Optional Anki

Q: Why not update in place?
A: It would break snapshot visibility for concurrent transactions.

</details>

<a id="db-mvcc-007"></a>

<details>
<summary><strong>DB-MVCC-007. What is a dead tuple?</strong></summary>

#### Short answer

A dead tuple is an old row version that no active or future transaction needs to see and that VACUUM can remove or mark reusable.

#### Interview answer

Dead tuples are created by `UPDATE` and `DELETE`. They are normal in PostgreSQL MVCC, but they should be cleaned regularly.

#### Deep dive

PostgreSQL cannot remove a tuple immediately if some old snapshot may still see it. VACUUM waits until it is safe.

#### Production angle

High dead tuple counts often point to heavy updates/deletes, long transactions, or autovacuum not keeping up.

#### Traps / caveats

- Updates create dead tuples too, not only deletes.
- Standard VACUUM usually reuses space, not shrinks files.
- Dead tuples increase I/O and bloat.

#### Optional Anki

Q: What creates dead tuples?
A: UPDATE and DELETE.

</details>

<a id="db-mvcc-008"></a>

<details>
<summary><strong>DB-MVCC-008. How does MVCC affect readers and writers?</strong></summary>

#### Short answer

MVCC allows readers and writers to work concurrently in most normal cases.

#### Interview answer

Normal reads do not block writes, and writes do not invalidate already-running reads. A reader sees the version visible to its snapshot.

#### Deep dive

MVCC reduces read/write contention, but write/write conflicts, explicit locks, DDL locks, and Serializable predicate locks still exist.

#### Production angle

This is why analytical reads can run during writes, but very long reads can still harm vacuum and bloat.

#### Traps / caveats

- MVCC does not make PostgreSQL lock-free.
- Two writers updating the same row can wait.
- DDL can still block reads/writes.

#### Optional Anki

Q: Do normal reads block writes in PostgreSQL MVCC?
A: Usually no.

</details>

<a id="db-mvcc-009"></a>

<details>
<summary><strong>DB-MVCC-009. Why are long-running transactions dangerous in PostgreSQL?</strong></summary>

#### Short answer

Long transactions can keep old snapshots alive, prevent VACUUM cleanup, hold locks, and exhaust connections.

#### Interview answer

VACUUM cannot remove tuple versions that might still be visible to a long-running transaction. Even a read-only transaction can therefore contribute to bloat.

#### Deep dive

In Java, this often happens when `@Transactional` wraps external HTTP calls, file processing, large loops, or slow business workflows.

#### Production angle

Keep transactions short, avoid remote calls inside transactions, and monitor old snapshots with:

```sql
SELECT pid, state, backend_xmin,
       now() - xact_start AS xact_age,
       wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

#### Traps / caveats

- A read-only transaction can still be harmful.
- Long transactions can cause connection pool exhaustion.
- The session can be dangerous even if it is idle.

#### Optional Anki

Q: Why can a long read-only transaction cause bloat?
A: It can keep an old snapshot alive and block VACUUM cleanup.

</details>

<a id="db-mvcc-010"></a>

<details>
<summary><strong>DB-MVCC-010. What is idle in transaction, and why is it bad?</strong></summary>

#### Short answer

`idle in transaction` means a session has an open transaction but is not currently executing a query.

#### Interview answer

It can happen when code opens a transaction, runs a query, and then waits for remote I/O, user input, or forgets to commit/rollback.

#### Deep dive

Such a session can hold locks, a snapshot, and a connection. It can also prevent cleanup of dead tuples that are visible to its old snapshot.

#### Production angle

Use correct transaction boundaries and consider `idle_in_transaction_session_timeout` as a safety net.

#### Traps / caveats

- It can roll back work if killed.
- Connection pool idle is not the same as DB idle in transaction.
- It is often an application bug.

#### Optional Anki

Q: Why is idle in transaction bad?
A: It can hold snapshots, locks, and connections while doing nothing.

</details>

<a id="db-mvcc-011"></a>

<details>
<summary><strong>🧠 DB-MVCC-011. How is MVCC related to VACUUM?</strong></summary>

#### Short answer

MVCC creates old row versions; VACUUM removes or marks reusable the versions that no transaction can see.

#### Interview answer

PostgreSQL cannot immediately delete old versions because older snapshots may still need them. VACUUM performs the safe cleanup later.

#### Deep dive

VACUUM also updates the visibility map and participates in anti-wraparound freezing.

#### Production angle

If VACUUM is blocked by old snapshots, dead tuples and bloat grow even if autovacuum is running.

#### Traps / caveats

- VACUUM must respect snapshots.
- VACUUM is not optional.
- Standard VACUUM usually does not shrink files.

#### Optional Anki

Q: Why does MVCC require VACUUM?
A: MVCC leaves old tuple versions behind.

</details>

<a id="db-mvcc-013"></a>

<details>
<summary><strong>🧠 DB-MVCC-013. What is transaction ID wraparound?</strong></summary>

#### Short answer

Transaction ID wraparound is the risk caused by finite PostgreSQL transaction IDs being reused over time.

#### Interview answer

PostgreSQL uses transaction IDs for visibility. Very old tuple transaction IDs must be frozen before ID reuse can make visibility ambiguous.

#### Deep dive

Autovacuum runs anti-wraparound vacuuming to freeze old tuples and protect the database.

#### Production angle

Monitor XID age, long transactions, replication slots, and autovacuum health. Wraparound pressure can become an availability incident.

#### Traps / caveats

- This is not only a DBA theory topic.
- Disabling autovacuum is dangerous.
- Long transactions can delay freezing.

#### Optional Anki

Q: What protects against XID wraparound?
A: VACUUM/freezing, usually through autovacuum.

</details>
