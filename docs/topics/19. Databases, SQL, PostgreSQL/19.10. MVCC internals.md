# MVCC internals

---

<a id="db-mvcc-001"></a>

<details>
<summary><strong>DB-MVCC-001. What is MVCC in PostgreSQL?</strong></summary>

#### Short answer

MVCC means Multi-Version Concurrency Control. PostgreSQL keeps multiple row versions and lets each transaction read a consistent snapshot.

#### Interview answer

MVCC is PostgreSQL’s main concurrency model. Instead of making readers wait for writers, PostgreSQL usually lets readers see the row version that is visible to their snapshot while writers create newer row versions.

#### Deep dive

Each heap tuple has MVCC metadata. Visibility is not just “latest row wins”; PostgreSQL checks transaction IDs, snapshots, commit status, and tuple metadata to decide whether a tuple version is visible.

#### Production angle

MVCC explains dead tuples, table bloat, autovacuum pressure, old snapshots, index-only scan heap fetches, and why long transactions can hurt the whole database.

#### Traps / caveats

- MVCC reduces read/write blocking, but does not remove all locks.
- Write-write conflicts can still block.
- Dead tuples must be cleaned by VACUUM.
- Long-running snapshots can prevent cleanup.

#### Optional Anki

Q: What is MVCC?
A: PostgreSQL’s snapshot-based concurrency model that stores multiple row versions.

</details>

<a id="db-mvcc-002"></a>

<details>
<summary><strong>🧠 DB-MVCC-002. How does MVCC work under the hood?</strong></summary>

#### Short answer

PostgreSQL stores row versions in heap pages. INSERT creates a tuple, UPDATE creates a new tuple version, and DELETE marks an old tuple version as deleted.

#### Interview answer

A statement reads through a snapshot. During a scan, PostgreSQL checks tuple metadata such as `xmin` and `xmax` together with transaction status to decide whether a tuple version is visible.

#### Deep dive

Conceptually, an update is closer to creating a new row version than modifying a row in place. Old snapshots can still see the old version, while new snapshots can see the committed new version.

```sql
-- conceptual example
UPDATE accounts SET balance = balance + 100 WHERE id = 1;
-- old tuple version remains for old snapshots
-- new tuple version becomes visible after commit
```

#### Production angle

Under the hood MVCC means update-heavy tables create dead tuples, generate WAL, may update indexes, and require enough autovacuum capacity. HOT updates can reduce index churn only under specific conditions.

#### Traps / caveats

- UPDATE is not a cheap in-place overwrite.
- `xmax` can also be involved in locking metadata, so do not oversimplify it.
- HOT updates are an optimization, not a guarantee.

#### Optional Anki

Q: Why does UPDATE create old versions?
A: To preserve visibility for transactions that still need the old snapshot.

</details>

<a id="db-mvcc-003"></a>

<details>
<summary><strong>🧠 DB-MVCC-003. What is a transaction snapshot?</strong></summary>

#### Short answer

A transaction snapshot defines which transaction effects are visible to a statement or transaction.

#### Interview answer

At `READ COMMITTED`, PostgreSQL generally takes a fresh snapshot for each statement. At `REPEATABLE READ` and `SERIALIZABLE`, the transaction sees a stable transaction-level snapshot.

#### Deep dive

A snapshot is not a physical copy of rows. It is visibility information that lets PostgreSQL decide whether a tuple version was created by a visible transaction and not removed by a visible transaction.

#### Production angle

Long-lived snapshots are a production problem because they can prevent VACUUM from removing dead tuples and can increase table/index bloat.

#### Traps / caveats

- Snapshot behavior depends on isolation level.
- A snapshot is not a copy of the database.
- Old snapshots can make cleanup impossible for some tuples.

#### Optional Anki

Q: Is a snapshot a physical copy?
A: No. It is metadata/rules for tuple visibility.

</details>

<a id="db-mvcc-004"></a>

<details>
<summary><strong>🧠 DB-MVCC-004. What are tuple versions?</strong></summary>

#### Short answer

Tuple versions are physical versions of a logical row stored in PostgreSQL heap storage.

#### Interview answer

When a logical row is updated, PostgreSQL can keep the old tuple version and create a new one. Different transactions can see different tuple versions depending on their snapshots.

#### Deep dive

Tuple versions are the reason updates can coexist with old readers. They are also why PostgreSQL needs VACUUM to remove versions that are no longer visible to any transaction.

#### Production angle

Many tuple versions are normal, but uncontrolled growth means more heap pages, worse cache efficiency, and slower scans.

#### Traps / caveats

- A logical row can have multiple physical versions.
- Indexes may need entries for new tuple versions.
- Dead versions are cleaned later, not immediately.

#### Optional Anki

Q: What is a tuple version?
A: A physical row version used by PostgreSQL MVCC.

</details>

<a id="db-mvcc-005"></a>

<details>
<summary><strong>🧠 DB-MVCC-005. What are xmin and xmax?</strong></summary>

#### Short answer

`xmin` and `xmax` are PostgreSQL system columns used by MVCC. Conceptually, `xmin` identifies the creating transaction and `xmax` identifies the deleting/updating/locking transaction.

#### Interview answer

A tuple is visible if its `xmin` is visible to the snapshot and its `xmax` does not make the tuple invisible for that snapshot.

#### Deep dive

You can inspect these columns for learning/debugging, but application logic must not depend on them.

```sql
SELECT xmin, xmax, ctid, *
FROM orders
WHERE id = 42;
```

#### Production angle

They are useful for understanding MVCC, but real visibility also depends on transaction status, snapshots, hint bits, and MultiXact/lock cases.

#### Traps / caveats

- Do not treat `xmax = 0` as the full definition of a live row in every context.
- These are implementation details.
- Transaction IDs wrap around, so freezing matters.

#### Optional Anki

Q: What is `xmin`?
A: The transaction ID that created the tuple version.

</details>

<a id="db-mvcc-006"></a>

<details>
<summary><strong>DB-MVCC-006. Why does UPDATE create a new row version instead of modifying the row in place?</strong></summary>

#### Short answer

Because old transactions may still need the old version while newer transactions should see the updated version.

#### Interview answer

In-place modification would break snapshot consistency. PostgreSQL creates a new tuple version and keeps the old one until it is no longer visible to any active snapshot.

#### Deep dive

This improves concurrency but creates dead tuples, WAL, and potentially new index entries. If indexed columns are unchanged and there is free space on the same page, a HOT update can keep the update chain on the heap page and avoid new index entries.

#### Production angle

Update-heavy tables need autovacuum tuning, careful indexing, short transactions, and sometimes lower `fillfactor` so HOT updates have room on the page.

#### Traps / caveats

- Updating indexed columns is more expensive because indexes usually need new entries.
- Frequent updates can cause table and index bloat.
- HOT updates depend on unchanged indexed columns, page free space, and later pruning/VACUUM.

#### Optional Anki

Q: Why not update in place?
A: It would break snapshot visibility for concurrent transactions.

</details>

<a id="db-mvcc-007"></a>

<details>
<summary><strong>DB-MVCC-007. What is a dead tuple?</strong></summary>

#### Short answer

A dead tuple is an old row version that no active or future transaction needs to see and that VACUUM can remove or mark reusable.

#### Interview answer

Dead tuples are created by `UPDATE` and `DELETE`. They are normal in PostgreSQL MVCC, but they should be cleaned regularly.

#### Deep dive

PostgreSQL cannot remove a tuple immediately if some old snapshot may still see it. VACUUM waits until it is safe.

#### Production angle

High dead tuple counts often point to heavy updates/deletes, long transactions, or autovacuum not keeping up.

#### Traps / caveats

- Updates create dead tuples too, not only deletes.
- Standard VACUUM usually reuses space, not shrinks files.
- Dead tuples increase I/O and bloat.

#### Optional Anki

Q: What creates dead tuples?
A: UPDATE and DELETE.

</details>

<a id="db-mvcc-008"></a>

<details>
<summary><strong>DB-MVCC-008. How does MVCC affect readers and writers?</strong></summary>

#### Short answer

MVCC allows readers and writers to work concurrently in most normal cases.

#### Interview answer

Normal reads do not block writes, and writes do not invalidate already-running reads. A reader sees the version visible to its snapshot.

#### Deep dive

MVCC reduces read/write contention, but write/write conflicts, explicit locks, DDL locks, and Serializable predicate locks still exist.

#### Production angle

This is why analytical reads can run during writes, but very long reads can still harm vacuum and bloat.

#### Traps / caveats

- MVCC does not make PostgreSQL lock-free.
- Two writers updating the same row can wait.
- DDL can still block reads/writes.

#### Optional Anki

Q: Do normal reads block writes in PostgreSQL MVCC?
A: Usually no.

</details>

<a id="db-mvcc-009"></a>

<details>
<summary><strong>DB-MVCC-009. Why are long-running transactions dangerous in PostgreSQL?</strong></summary>

#### Short answer

Long transactions can keep old snapshots alive, prevent VACUUM cleanup, hold locks, and exhaust connections.

#### Interview answer

VACUUM cannot remove tuple versions that might still be visible to a long-running transaction. Even a read-only transaction can therefore contribute to bloat.

#### Deep dive

In Java, this often happens when `@Transactional` wraps external HTTP calls, file processing, large loops, or slow business workflows.

#### Production angle

Keep transactions short, avoid remote calls inside transactions, and monitor old snapshots with:

```sql
SELECT pid, state, backend_xmin,
       now() - xact_start AS xact_age,
       wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

#### Traps / caveats

- A read-only transaction can still be harmful.
- Long transactions can cause connection pool exhaustion.
- The session can be dangerous even if it is idle.

#### Optional Anki

Q: Why can a long read-only transaction cause bloat?
A: It can keep an old snapshot alive and block VACUUM cleanup.

</details>

<a id="db-mvcc-010"></a>

<details>
<summary><strong>DB-MVCC-010. What is idle in transaction, and why is it bad?</strong></summary>

#### Short answer

`idle in transaction` means a session has an open transaction but is not currently executing a query.

#### Interview answer

It can happen when code opens a transaction, runs a query, and then waits for remote I/O, user input, or forgets to commit/rollback.

#### Deep dive

Such a session can hold locks, a snapshot, and a connection. It can also prevent cleanup of dead tuples that are visible to its old snapshot.

#### Production angle

Use correct transaction boundaries and consider `idle_in_transaction_session_timeout` as a safety net.

#### Traps / caveats

- It can roll back work if killed.
- Connection pool idle is not the same as DB idle in transaction.
- It is often an application bug.

#### Optional Anki

Q: Why is idle in transaction bad?
A: It can hold snapshots, locks, and connections while doing nothing.

</details>

<a id="db-mvcc-011"></a>

<details>
<summary><strong>🧠 DB-MVCC-011. How is MVCC related to VACUUM?</strong></summary>

#### Short answer

MVCC creates old row versions; VACUUM removes or marks reusable the versions that no transaction can see.

#### Interview answer

PostgreSQL cannot immediately delete old versions because older snapshots may still need them. VACUUM performs the safe cleanup later.

#### Deep dive

VACUUM also updates the visibility map and participates in anti-wraparound freezing.

#### Production angle

If VACUUM is blocked by old snapshots, dead tuples and bloat grow even if autovacuum is running.

#### Traps / caveats

- VACUUM must respect snapshots.
- VACUUM is not optional.
- Standard VACUUM usually does not shrink files.

#### Optional Anki

Q: Why does MVCC require VACUUM?
A: MVCC leaves old tuple versions behind.

</details>

<a id="db-mvcc-012"></a>

<details>
<summary><strong>🧠 DB-MVCC-012. How is MVCC related to index-only scans?</strong></summary>

#### Short answer

Index-only scans still need MVCC visibility. PostgreSQL can skip heap reads only when the visibility map says the heap page is all-visible.

#### Interview answer

Indexes do not contain enough visibility information for every tuple. The visibility map tells whether all tuples on a heap page are visible to all transactions.

#### Deep dive

VACUUM updates the visibility map. Frequently updated tables often have fewer all-visible pages and therefore more heap fetches.

#### Production angle

If an index-only scan unexpectedly reads the heap, check `Heap Fetches`, recent updates, autovacuum, and visibility map coverage.

#### Traps / caveats

- A covering index does not guarantee a pure index-only scan.
- Frequent updates reduce all-visible coverage.
- Heap fetches matter in EXPLAIN.

#### Optional Anki

Q: Why can index-only scans still read the heap?
A: To check MVCC visibility when the page is not marked all-visible.

</details>

<a id="db-mvcc-013"></a>

<details>
<summary><strong>🧠 DB-MVCC-013. What is transaction ID wraparound?</strong></summary>

#### Short answer

Transaction ID wraparound is the risk caused by finite PostgreSQL transaction IDs being reused over time.

#### Interview answer

PostgreSQL uses transaction IDs for visibility. Very old tuple transaction IDs must be frozen before ID reuse can make visibility ambiguous.

#### Deep dive

Autovacuum runs anti-wraparound vacuuming to freeze old tuples and protect the database.

#### Production angle

Monitor XID age, long transactions, replication slots, and autovacuum health. Wraparound pressure can become an availability incident.

#### Traps / caveats

- This is not only a DBA theory topic.
- Disabling autovacuum is dangerous.
- Long transactions can delay freezing.

#### Optional Anki

Q: What protects against XID wraparound?
A: VACUUM/freezing, usually through autovacuum.

</details>

<a id="db-mvcc-014"></a>

<details>
<summary><strong>🧠 DB-MVCC-014. What is freezing in PostgreSQL?</strong></summary>

#### Short answer

Freezing marks very old tuple transaction IDs as safely visible so they are no longer affected by transaction ID wraparound.

#### Interview answer

During VACUUM, PostgreSQL can freeze old tuples. Conceptually, the old `xmin` no longer needs to be compared in the normal way for future visibility.

#### Deep dive

Freezing is normal maintenance. Emergency anti-wraparound freezing is what you want to avoid.

#### Production angle

Track database and table age, plus autovacuum progress. Useful starting points are `age(datfrozenxid)`, `age(relfrozenxid)`, `pg_stat_all_tables`, and `pg_stat_progress_vacuum`.

#### Traps / caveats

- Freezing is not archiving or deleting data.
- It is about XID visibility safety.
- Emergency freezing can create I/O pressure.

#### Optional Anki

Q: What does freezing protect against?
A: Transaction ID wraparound.

</details>

<a id="db-mvcc-015"></a>

<details>
<summary><strong>🧠 DB-MVCC-015. What can happen if transaction ID wraparound is not prevented?</strong></summary>

#### Short answer

PostgreSQL can be forced into aggressive anti-wraparound vacuuming and, near the safety limit, can stop accepting transactions that would assign new XIDs.

#### Interview answer

If old transaction IDs wrap around unsafely, visibility rules could become ambiguous. PostgreSQL has safeguards, but those safeguards can cause severe operational incidents.

#### Deep dive

The practical risk is usually urgent vacuum pressure, transaction interruption, and emergency maintenance rather than silent corruption.

#### Production angle

Have alerts for XID age, autovacuum failures, old transactions, prepared transactions, and replication slots that hold old horizons. Start with:

```sql
SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;
```

#### Traps / caveats

- Do not ignore wraparound warnings.
- Fix root causes, not only run one manual VACUUM.
- Old transactions, prepared transactions, and replication slots can hold horizons.

#### Optional Anki

Q: Operational risk of wraparound pressure?
A: Forced vacuuming and possible rejection of transactions that need new XIDs.

</details>
