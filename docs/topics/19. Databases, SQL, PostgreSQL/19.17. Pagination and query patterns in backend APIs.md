# Pagination and query patterns in backend APIs

---

<a id="db-api-001"></a>

<details>
<summary><strong>DB-API-001. What is OFFSET/LIMIT pagination?</strong></summary>

#### Short answer

OFFSET/LIMIT pagination returns a page by skipping N rows and then taking a limited number of rows.

#### Interview answer

Example: `LIMIT 20 OFFSET 100` means skip the first 100 rows and return the next 20.

It is simple and supports page numbers, which makes it common in admin tables and small datasets.

#### Deep dive

The database still has to identify and discard skipped rows. With large offsets, work grows with the offset.

Results also require stable ordering, otherwise pages can be inconsistent.

#### Production angle

Use OFFSET/LIMIT for small datasets, internal tools, or shallow pages. For infinite scroll or large tables, prefer keyset/cursor pagination.

Always include deterministic ORDER BY.

#### Traps / caveats

- Without ORDER BY, page order is not guaranteed.
- Large offsets are slow.
- Concurrent inserts/deletes can shift rows between pages.
- COUNT(*) for total pages may be expensive.

#### Optional Anki

Q: What does OFFSET do?
A: Skips a number of rows before returning the limit.

</details>

<a id="db-api-002"></a>

<details>
<summary><strong>DB-API-002. Why can OFFSET pagination become slow on large tables?</strong></summary>

#### Short answer

Because PostgreSQL must still walk through the skipped rows before returning the requested page.

#### Interview answer

With `OFFSET 100000 LIMIT 20`, the database cannot simply jump to row 100001 unless the access path supports it perfectly. It often reads many index/table entries and discards them.

The deeper the page, the more work.

#### Deep dive

Even with an index, PostgreSQL may scan through index entries to reach the offset. If heap visits are needed, it can be even more expensive.

Large OFFSET also creates unstable UX under concurrent changes.

#### Production angle

In production APIs, large offsets can become a hidden denial-of-service vector. Add maximum page depth, use keyset pagination, or use search/index systems for deep browsing.

Monitor queries with high offsets.

#### Traps / caveats

- Index does not eliminate offset cost completely.
- Page number UX conflicts with performance on large data.
- Deletes/inserts can duplicate or skip rows across pages.
- Deep pagination should be restricted.

#### Optional Anki

Q: Why is OFFSET slow for deep pages?
A: Rows before the requested page still need to be scanned/skipped.

</details>

<a id="db-api-003"></a>

<details>
<summary><strong>DB-API-003. What is keyset pagination?</strong></summary>

#### Short answer

Keyset pagination uses the last seen sort key instead of OFFSET to fetch the next page.

#### Interview answer

Instead of saying “skip 100000 rows”, the query says “give me rows after this last value”.

Example: `WHERE (created_at, id) < (:last_created_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20`.

#### Deep dive

Keyset pagination works best with a stable, indexed order. It can use an index range scan and does not pay the cost of skipping previous pages.

It is ideal for feeds, event streams, audit logs, and infinite scroll.

#### Production angle

In production, return an opaque cursor containing the last key values and sort direction. Keep cursor validation and versioning in mind.

Keyset pagination is usually not good for jumping to arbitrary page number.

#### Traps / caveats

- Ordering must be unique or have a tie-breaker.
- Cursor values must match ORDER BY exactly.
- Changing filters invalidates cursors.
- Backward pagination needs separate design.

#### Optional Anki

Q: What is keyset pagination?
A: Fetching the next page using the last seen sort key instead of OFFSET.

</details>

<a id="db-api-004"></a>

<details>
<summary><strong>DB-API-004. How would you implement cursor/keyset pagination?</strong></summary>

#### Short answer

Choose a deterministic ORDER BY, add a tie-breaker, index it, and use the last returned key values as the next cursor.

#### Interview answer

For ordering by newest first, use `ORDER BY created_at DESC, id DESC`. The next page condition is `(created_at, id) < (:lastCreatedAt, :lastId)`.

Encode cursor values into an opaque token so clients do not depend on internal details.

#### Deep dive

The index should match filtering and ordering, for example `(tenant_id, created_at DESC, id DESC)` for tenant-scoped feeds.

Use a unique tie-breaker like id because timestamps can have duplicates.

#### Production angle

In production, include filters in cursor or reject cursor/filter mismatches. Sign or encrypt cursors if tampering matters.

Define cursor expiration and backward navigation separately.

#### Traps / caveats

- Do not use non-deterministic ordering.
- Do not expose raw sensitive fields in cursor.
- Null sort values require explicit handling.
- Use consistent ASC/DESC semantics.

#### Optional Anki

Q: Keyset pagination needs what tie-breaker?
A: A unique stable column like id after the main sort key.

</details>

<a id="db-api-005"></a>

<details>
<summary><strong>DB-API-005. What are the trade-offs between OFFSET pagination and keyset pagination?</strong></summary>

#### Short answer

OFFSET is simpler and supports page numbers; keyset is faster and more stable for large/deep pagination but does not support arbitrary page jumps easily.

#### Interview answer

OFFSET is good for admin lists, small tables, and shallow pages. Keyset is good for user feeds, infinite scroll, large tables, and high-traffic endpoints.

OFFSET works with arbitrary sorting more easily; keyset requires a careful indexed ordering.

#### Deep dive

OFFSET page N can be requested directly. Keyset uses cursor chain: next page depends on previous page's last key.

Under concurrent writes, keyset is usually less prone to duplicates/skips when ordered by immutable keys.

#### Production angle

For public APIs, choose based on UX: page numbers vs endless scrolling. For performance-critical endpoints, keyset is usually safer.

Document cursor semantics in API contracts.

#### Traps / caveats

- Keyset is not always trivial with complex sorting.
- OFFSET can be acceptable with small limits and max page depth.
- Keyset requires stable order.
- Total count can be expensive for both.

#### Optional Anki

Q: OFFSET vs keyset?
A: OFFSET is simple/page-number based; keyset is faster for deep pages but cursor-based.

</details>

<a id="db-api-006"></a>

<details>
<summary><strong>DB-API-006. How can indexes support pagination?</strong></summary>

#### Short answer

Indexes can provide rows in the required filter and sort order, reducing scanning and sorting work.

#### Interview answer

For pagination, the index should often start with equality filters, then sorting keys. Example: `(tenant_id, created_at DESC, id DESC)`.

This lets PostgreSQL quickly find the next rows for a tenant in the correct order.

#### Deep dive

For OFFSET, an index may avoid a sort but still has to skip rows. For keyset, the index can do a range scan starting after the cursor.

Index-only scans can help if selected columns are covered and visibility map allows it.

#### Production angle

In production, always inspect the query plan. If the database sorts large result sets or scans many rows, index design may not match pagination pattern.

Use realistic filters and data distribution when testing.

#### Traps / caveats

- Index column order matters.
- ORDER BY direction can matter.
- Covering too many columns increases index size.
- Dynamic filters make one perfect index impossible.

#### Optional Anki

Q: What index supports tenant feed pagination?
A: Often (tenant_id, created_at DESC, id DESC).

</details>

<a id="db-api-007"></a>

<details>
<summary><strong>DB-API-007. Why is stable ordering important for pagination?</strong></summary>

#### Short answer

Stable ordering prevents rows from appearing in random order, being duplicated, or being skipped between pages.

#### Interview answer

If multiple rows have the same sort value, ordering only by that value is not deterministic. Add a unique tie-breaker like `id`.

Without ORDER BY, PostgreSQL does not guarantee row order at all.

#### Deep dive

For keyset pagination, cursor condition must match ORDER BY exactly. For example, if ORDER BY is `created_at DESC, id DESC`, cursor comparison should use both fields.

Stable ordering is also important for caching and reproducible API behavior.

#### Production angle

In production APIs, always specify deterministic ordering. Avoid relying on physical table order or implicit primary-key order.

Document ordering so clients understand page behavior.

#### Traps / caveats

- ORDER BY created_at alone is not stable if timestamps duplicate.
- Concurrent writes still affect pagination, but stable order reduces surprises.
- NULL ordering should be explicit.
- Changing default order is a breaking API change.

#### Optional Anki

Q: How make pagination order stable?
A: Add a deterministic ORDER BY with a unique tie-breaker.

</details>

<a id="db-api-008"></a>

<details>
<summary><strong>DB-API-008. How would you paginate by created_at and id?</strong></summary>

#### Short answer

Order by created_at plus id as a tie-breaker, and use both values in the cursor condition.

#### Interview answer

For newest first: `ORDER BY created_at DESC, id DESC`. Next page: rows where `(created_at, id) < (:lastCreatedAt, :lastId)`.

Use a matching index, often `(created_at DESC, id DESC)` or with tenant/filter columns before it.

#### Deep dive

The tuple comparison must match direction. For ascending order, use `>` instead of `<`.

If created_at can be NULL, either disallow NULL or define explicit NULL ordering and cursor logic.

#### Production angle

In production, include the cursor in API response as an opaque token. Validate that client uses it with the same filters.

Use id as stable tie-breaker because created_at is not guaranteed unique.

#### Traps / caveats

- Use both keys, not only created_at.
- ORDER direction matters.
- Clock precision can create duplicate timestamps.
- Do not let clients edit cursor internals.

#### Optional Anki

Q: Why include id when paginating by created_at?
A: It is a unique tie-breaker for rows with the same timestamp.

</details>

<details>
<summary><strong>DB-API-009. How would you implement search by optional filters?</strong></summary>

#### Short answer

Build the WHERE clause from allowed filters, bind values safely, and design indexes for the most common filter combinations.

#### Interview answer

Optional filters create many possible query shapes. A clean implementation maps user-provided filters to known predicates and parameters.

Do not concatenate raw client SQL.

#### Deep dive

Patterns include dynamic SQL builders, Specifications/Criteria API, jOOQ, or explicit repository methods for common cases.

Indexing every combination is impossible; choose indexes based on frequency, selectivity, and ordering.

#### Production angle

In production, log normalized query patterns, track slow combinations, and avoid unbounded filters. Use limits, timeouts, and pagination.

Consider search engines for full-text/fuzzy search.

#### Traps / caveats

- Dynamic filters can create bad plans.
- OR-heavy queries may be hard to optimize.
- Prepared statements with very different selectivity can behave unexpectedly.
- Always constrain maximum result size.

#### Optional Anki

Q: How to index optional filters?
A: Index common/selective combinations, not every possible combination.

</details>

<a id="db-api-010"></a>

<details>
<summary><strong>🧠 DB-API-010. How can dynamic filters lead to bad query plans?</strong></summary>

#### Short answer

Dynamic filters create many predicate combinations, and PostgreSQL may misestimate selectivity or choose a plan that is bad for some parameter values.

#### Interview answer

A query with optional filters often has skewed parameter values: one status returns 1% of rows, another returns 80%. A generic plan may be bad for one of them.

OR conditions and nullable parameter tricks can also make indexes harder to use.

#### Deep dive

Examples of risky patterns: `WHERE (:status IS NULL OR status = :status)`, huge IN lists, non-sargable expressions, and arbitrary sorting.

Sometimes separate query shapes perform better than one universal query.

#### Production angle

In production, use `EXPLAIN (ANALYZE, BUFFERS)` for slow combinations, inspect estimated vs actual rows, and track parameter distributions.

Consider custom SQL for hot paths.

#### Traps / caveats

- One query to handle all filters is often not optimal.
- Generic prepared plans can hurt skewed workloads.
- Functions on columns can block indexes.
- Filter selectivity changes as data grows.

#### Optional Anki

Q: Why can optional filters hurt plans?
A: They create many query shapes and selectivity patterns that are hard to estimate.

</details>
