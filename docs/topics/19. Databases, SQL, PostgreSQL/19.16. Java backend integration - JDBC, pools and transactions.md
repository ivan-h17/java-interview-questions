# Java backend integration: JDBC, pools and transactions

---

<a id="db-java-001"></a>

<details>
<summary><strong>DB-JAVA-001. What is JDBC?</strong></summary>

#### Short answer

JDBC is the standard Java API for connecting to relational databases and executing SQL.

#### Interview answer

JDBC provides interfaces like `Connection`, `Statement`, `PreparedStatement`, `CallableStatement`, and `ResultSet`.

Most higher-level tools such as Spring JDBC, JPA providers, and migration tools ultimately use JDBC drivers underneath.

#### Deep dive

JDBC is driver-based. The PostgreSQL JDBC driver implements the JDBC interfaces and speaks PostgreSQL protocol.

JDBC itself is low-level: it does not manage ORM mappings, transactions at service level, or connection pooling by magic.

#### Production angle

For senior backend work, JDBC knowledge helps debug connection leaks, transaction boundaries, parameter binding, batch operations, and generated SQL behavior.

Even if using JPA, production incidents often require JDBC-level understanding.

#### Traps / caveats

- JDBC is not an ORM.
- Always close resources or use try-with-resources / framework management.
- Connections are expensive and should usually come from a pool.
- Driver behavior can affect performance.

#### Optional Anki

Q: What is JDBC?
A: The standard Java API for database connectivity and SQL execution.

</details>

<a id="db-java-002"></a>

<details>
<summary><strong>🧠 DB-JAVA-002. What is a JDBC URL?</strong></summary>

#### Short answer

A JDBC URL is a connection string that tells the JDBC driver which database to connect to and with what parameters.

#### Interview answer

For PostgreSQL it often looks like `jdbc:postgresql://host:5432/dbname`. It may include SSL, timeouts, application name, and other driver options.

The URL format is driver-specific.

#### Deep dive

A JDBC URL is usually used together with username/password or other authentication methods. In production, secrets should come from secure configuration, not hardcoded strings.

Some options can also be configured through DataSource properties.

#### Production angle

Use connection names/application names to identify services in `pg_stat_activity`. Configure SSL and timeouts deliberately.

Bad URL/configuration can cause hidden production issues, such as missing timeouts or wrong target database.

#### Traps / caveats

- Do not log credentials.
- Different environments must not accidentally point to production.
- Driver parameters differ by database.
- Timeout defaults may be unsafe.

#### Optional Anki

Q: What is a JDBC URL for?
A: To identify the database endpoint and connection options for the driver.

</details>

<a id="db-java-003"></a>

<details>
<summary><strong>DB-JAVA-003. What is DataSource?</strong></summary>

#### Short answer

A DataSource is a factory for database connections, commonly backed by a connection pool in server applications.

#### Interview answer

In modern Java apps, code usually obtains connections from `DataSource` instead of `DriverManager`. Frameworks like Spring manage the DataSource and inject it where needed.

A DataSource can provide pooling, configuration, monitoring, and integration with transactions.

#### Deep dive

DataSource is an interface; implementations include HikariCP, Tomcat JDBC Pool, application server pools, and vendor-specific sources.

The application code should not usually create a new physical database connection per request.

#### Production angle

In production, tune the DataSource/pool: maximum pool size, connection timeout, idle timeout, max lifetime, leak detection, validation query/keepalive.

Expose pool metrics.

#### Traps / caveats

- DataSource does not automatically make bad queries fast.
- Pool sizing must match DB capacity.
- A misconfigured pool can overload PostgreSQL.
- Do not bypass the framework's transaction-aware DataSource.

#### Optional Anki

Q: What is DataSource?
A: A configurable source/factory of database connections, often with pooling.

</details>

<a id="db-java-004"></a>

<details>
<summary><strong>DB-JAVA-004. What is the difference between DriverManager and DataSource?</strong></summary>

#### Short answer

DriverManager is a simple static API for creating connections; DataSource is configurable, injectable, and usually supports pooling.

#### Interview answer

`DriverManager.getConnection()` is fine for small examples and tools. Server applications should use DataSource because it integrates better with frameworks, pools, JNDI, metrics, and transaction managers.

DataSource separates connection configuration from application logic.

#### Deep dive

DriverManager usually creates a physical connection when called. A pooled DataSource returns a logical handle to an existing pooled connection.

Spring's transaction management also expects to work with a managed DataSource.

#### Production angle

In production, use DataSource. Direct DriverManager calls inside business code can bypass pooling and transaction management.

That can cause slow requests, too many DB connections, or inconsistent transactions.

#### Traps / caveats

- DriverManager is not appropriate for high-throughput services.
- DataSource still needs correct pooling config.
- Mixing connection sources can break transactions.
- Direct connections are easy to leak.

#### Optional Anki

Q: DriverManager vs DataSource?
A: DriverManager creates direct connections; DataSource is managed/configurable and commonly pooled.

</details>

<a id="db-java-005"></a>

<details>
<summary><strong>DB-JAVA-005. What is Statement?</strong></summary>

#### Short answer

Statement is a JDBC object used to execute static SQL text without parameter binding.

#### Interview answer

`Statement` can execute SQL strings, but values are usually concatenated into SQL manually. That makes it dangerous for user input.

For dynamic values, use `PreparedStatement`.

#### Deep dive

Statement has methods like `executeQuery`, `executeUpdate`, and `execute`. It is useful for fixed admin queries or DDL scripts generated safely.

It does not separate SQL structure from parameters.

#### Production angle

In production application code, raw Statement should be rare. It is easy to introduce SQL injection or quoting bugs.

If identifiers must be dynamic, use allowlists and safe query builders.

#### Traps / caveats

- Never concatenate user input into Statement SQL.
- PreparedStatement is the default choice for values.
- Statement can still be useful for fixed SQL.
- Dynamic identifiers need allowlists, not bind parameters.

#### Optional Anki

Q: When should Statement be avoided?
A: When SQL contains user-controlled values; use PreparedStatement instead.

</details>

<a id="db-java-006"></a>

<details>
<summary><strong>DB-JAVA-006. What is PreparedStatement?</strong></summary>

#### Short answer

PreparedStatement is a JDBC statement with parameter placeholders that lets values be bound separately from SQL text.

#### Interview answer

Instead of concatenating values into SQL, we write placeholders and bind values through methods like `setString`, `setLong`, and `setTimestamp`.

This improves safety and can help performance for repeated statements.

#### Deep dive

A prepared statement separates SQL code from data values. The database/driver treats bound parameters as values, not executable SQL.

Depending on driver and DB, it may be server-side prepared or emulated client-side until a threshold.

#### Production angle

Use PreparedStatement by default for application SQL. It is central for SQL injection prevention and correct type handling.

Still design query shape carefully; parameters cannot safely replace identifiers like table or column names.

#### Traps / caveats

- PreparedStatement prevents value injection, not bad authorization.
- It does not parameterize column/table names.
- Generic prepared plans can sometimes hurt performance.
- Always bind values with correct types.

#### Optional Anki

Q: What is PreparedStatement?
A: A parameterized JDBC statement that binds values separately from SQL text.

</details>

<a id="db-java-007"></a>

<details>
<summary><strong>DB-JAVA-007. How does PreparedStatement help prevent SQL injection?</strong></summary>

#### Short answer

It sends SQL structure and parameter values separately, so user input is treated as data rather than SQL code.

#### Interview answer

If a user enters `' OR 1=1 --`, a prepared statement binds it as a string value, not as SQL syntax.

This prevents the classic attack where input breaks out of quotes and changes the query.

#### Deep dive

PreparedStatement is effective for values in predicates, inserts and updates. It does not automatically secure dynamic identifiers, dynamically assembled SQL fragments, or unsafe ORDER BY clauses.

Safe dynamic SQL still needs allowlists.

#### Production angle

In production, combine prepared statements with least-privilege DB users, validation, safe query builders, and security review.

PreparedStatement is necessary, but not the entire security model.

#### Traps / caveats

- PreparedStatement does not validate business permissions.
- Dynamic ORDER BY cannot be parameterized as a value.
- String concatenation around prepared SQL can reintroduce injection.
- Stored procedures can still be unsafe if they build SQL badly.

#### Optional Anki

Q: How does PreparedStatement prevent injection?
A: By treating bound user input as data values, not SQL code.

</details>

<a id="db-java-008"></a>

<details>
<summary><strong>🧠 DB-JAVA-008. What is CallableStatement?</strong></summary>

#### Short answer

CallableStatement is a JDBC interface for calling stored procedures or database functions.

#### Interview answer

It supports input, output and input/output parameters depending on database support.

In PostgreSQL, application code more often uses regular SQL or functions; procedures are used when logic belongs in the database.

#### Deep dive

CallableStatement uses call syntax and can handle return values. It is useful for legacy systems, complex DB-side operations, or vendor APIs.

But DB-side procedural logic can make application behavior harder to test and version.

#### Production angle

Use it when there is a clear reason: performance-critical DB-local processing, existing stored procedures, or administrative operations.

Keep migrations and procedure versioning disciplined.

#### Traps / caveats

- Stored procedures can hide business logic from application tests.
- They can still be vulnerable to SQL injection if dynamic SQL is built unsafely.
- Portability across DBs decreases.
- Error handling semantics may differ.

#### Optional Anki

Q: What is CallableStatement for?
A: Calling stored procedures or database functions from JDBC.

</details>

<a id="db-java-009"></a>

<details>
<summary><strong>DB-JAVA-009. What is ResultSet?</strong></summary>

#### Short answer

ResultSet is a JDBC cursor-like object that represents rows returned by a query.

#### Interview answer

You iterate through it with `next()` and read column values with getters like `getString`, `getLong`, and `getTimestamp`.

ResultSet is usually tied to the Statement and Connection lifecycle.

#### Deep dive

ResultSet can be forward-only or scrollable depending on configuration and driver support. Fetch size can affect memory and streaming behavior.

Mapping ResultSet rows to domain objects is what JDBC template libraries help with.

#### Production angle

For large result sets, avoid loading everything into memory. Use pagination, streaming/fetch size where appropriate, and close resources reliably.

Long-lived ResultSets can hold connections and transactions open.

#### Traps / caveats

- Column names/types must match expectations.
- ResultSet can keep DB resources open.
- Large reads can exhaust memory.
- Do not return live ResultSet outside repository layer.

#### Optional Anki

Q: What is ResultSet?
A: A JDBC object for iterating rows returned by a query.

</details>

<a id="db-java-010"></a>

<details>
<summary><strong>DB-JAVA-010. What is a database connection pool?</strong></summary>

#### Short answer

A connection pool keeps a limited set of reusable database connections so requests do not create a new physical connection every time.

#### Interview answer

Opening a database connection is expensive. A pool creates and maintains connections, lends them to application threads, and returns them after use.

In Java services, HikariCP is a very common pool implementation.

#### Deep dive

A pooled connection is usually a logical wrapper. When code calls `close()`, the connection returns to the pool instead of closing the physical socket.

Pool settings include maximumPoolSize, connectionTimeout, idleTimeout, maxLifetime, validation, and leak detection.

#### Production angle

In production, pool metrics are critical: active, idle, pending, acquisition time, timeouts, and usage duration.

A pool protects the database from unlimited concurrency, but a wrongly sized pool can either throttle the app or overload PostgreSQL.

#### Traps / caveats

- A bigger pool is not always better.
- Leaked connections exhaust the pool.
- Long transactions hold connections too long.
- Each app instance has its own pool, so total connections multiply.

#### Optional Anki

Q: What is a connection pool?
A: A limited reusable set of DB connections shared by application requests.

</details>

<a id="db-java-011"></a>

<details>
<summary><strong>DB-JAVA-011. Why do Java applications need a connection pool?</strong></summary>

#### Short answer

Because physical database connections are expensive, and unbounded connection creation would hurt latency and overload the database.

#### Interview answer

A pool reuses connections, controls concurrency, provides timeouts, and exposes metrics.

It is especially important in web services where many requests may need database access concurrently.

#### Deep dive

Without pooling, each request could pay TCP/authentication/session setup cost. With pooling, requests wait for an existing connection or fail fast when the pool is saturated.

The pool is also a backpressure mechanism.

#### Production angle

In production, connection pool behavior often explains latency spikes. Pending threads waiting for DB connections can look like slow SQL even when the database is just saturated.

Monitor both application pool metrics and PostgreSQL sessions.

#### Traps / caveats

- Too small pool causes waiting.
- Too large pool causes DB contention.
- A pool does not fix slow queries.
- Connection leaks are often application bugs.

#### Optional Anki

Q: Why use a connection pool?
A: To reuse expensive DB connections and limit concurrent DB access.

</details>

<a id="db-java-012"></a>

<details>
<summary><strong>DB-JAVA-012. What is HikariCP?</strong></summary>

#### Short answer

HikariCP is a popular high-performance JDBC connection pool used by many Java and Spring Boot applications.

#### Interview answer

HikariCP manages database connections and exposes settings like `maximumPoolSize`, `minimumIdle`, `connectionTimeout`, `idleTimeout`, `maxLifetime`, `keepaliveTime`, and `leakDetectionThreshold`.

Spring Boot commonly uses HikariCP as the default connection pool when available.

#### Deep dive

HikariCP focuses on simplicity and low overhead. But its performance depends on correct sizing and database/query behavior.

The pool should be monitored like any other critical resource.

#### Production angle

In production, tune max pool size per service instance and count total connections across all replicas.

Configure timeouts so request threads do not hang indefinitely waiting for a connection. Keep `maxLifetime` shorter than database/proxy/network connection lifetime, and use leak detection as an incident signal, not as normal control flow.

#### Traps / caveats

- HikariCP is not a cache of query results.
- Defaults may not fit your workload.
- Max pool size per pod times pod count can exceed DB max_connections.
- `maxLifetime`, `keepaliveTime` and proxy/network timeouts must be aligned to avoid stale or mass-retired connections.

#### Optional Anki

Q: What is HikariCP?
A: A widely used JDBC connection pool for Java applications.

</details>

<a id="db-java-013"></a>

<details>
<summary><strong>DB-JAVA-013. How would you size a connection pool?</strong></summary>

#### Short answer

Size it from database capacity, service replica count, workload concurrency, query latency, and acceptable queueing — not by guessing a large number.

#### Interview answer

Start with the total database connection budget. Divide it among all application instances and background jobs. Then validate with load testing.

The goal is enough connections to keep the database busy, but not so many that PostgreSQL spends most time context-switching, waiting on locks, or thrashing IO.

#### Deep dive

Use metrics: active connections, idle connections, pending threads, pool wait time, query time, CPU, IO, locks, and transaction duration.

If most time is spent waiting for the DB, increasing pool size may make things worse.

#### Production angle

In Kubernetes, remember multiplication: `pool_size * pod_count`. A deployment scale-up can suddenly exceed PostgreSQL `max_connections`.

Budget all connections: `pool_size * pod_count + background_jobs + migrations + admin_margin` must fit below safe PostgreSQL capacity, not merely below `max_connections`.

Use PgBouncer or reduce pools if many services connect to the same DB, but understand transaction-pooling caveats.

#### Traps / caveats

- Bigger pool is not automatically faster.
- Pool exhaustion can be a symptom of slow queries.
- Long transactions reduce available connections.
- PgBouncer transaction pooling is not transparent for session state, temp tables, LISTEN/NOTIFY, advisory locks, and some prepared statement usage.
- Use load tests, not only rules of thumb.

#### Optional Anki

Q: What is the biggest pool sizing trap?
A: Thinking bigger is always better; total connections can overload PostgreSQL.

</details>

<a id="db-java-014"></a>

<details>
<summary><strong>DB-JAVA-014. What happens when the connection pool is exhausted?</strong></summary>

#### Short answer

New requests wait for a connection until the pool timeout; if no connection is returned, they fail with a timeout/error.

#### Interview answer

Pool exhaustion means all connections are active or leaked, and additional threads are waiting. This increases latency and can cascade through the service.

Causes include slow queries, long transactions, connection leaks, too much concurrency, or a pool that is too small for the workload.

#### Deep dive

From the DB side, you may see many active or idle-in-transaction sessions. From the app side, you see pool pending count and acquisition timeout.

Pool exhaustion is often a symptom, not root cause.

#### Production angle

In production, check active connection count, longest connection usage, slow queries, locks, thread dumps, and leak detection logs.

Fail fast with sensible timeouts rather than letting request threads pile up forever.

#### Traps / caveats

- Increasing pool size may overload DB.
- Leaked connections look like permanent activity.
- Idle-in-transaction connections can hold locks/snapshots.
- Retries can amplify exhaustion.

#### Optional Anki

Q: What happens when a pool is exhausted?
A: Threads wait for connections and eventually time out.

</details>

<a id="db-java-015"></a>

<details>
<summary><strong>DB-JAVA-015. How can @Transactional accidentally hold a database connection for too long?</strong></summary>

#### Short answer

A transactional method can keep a connection open while doing slow non-database work, remote calls, or long processing inside the transaction boundary.

#### Interview answer

In Spring, a connection is often acquired when the transaction first needs database access and held until transaction completion.

If the method then calls another service, waits for HTTP, sends messages, processes files, or loops over many items, the DB connection and transaction can remain open unnecessarily.

#### Deep dive

Long transactions keep snapshots, can hold locks, prevent vacuum cleanup, increase connection pool usage, and cause contention.

This is especially dangerous with `@Transactional` on broad service methods that mix business orchestration with database writes.

#### Production angle

In production, keep transaction boundaries small: read/validate, write DB changes, commit, then call external systems or send async events using outbox if needed.

Monitor transaction duration and idle-in-transaction sessions.

#### Traps / caveats

- Do not wrap HTTP calls in DB transactions.
- Self-invocation can bypass @Transactional, but broad transactions are another problem.
- Read-only transactions can still hold connections/snapshots.
- Lazy loading can unexpectedly extend DB access.

#### Optional Anki

Q: How can @Transactional hurt the pool?
A: Long transactions hold DB connections until commit/rollback.

</details>

<a id="db-java-016"></a>

<details>
<summary><strong>DB-JAVA-016. Why are long transactions dangerous for a Java service?</strong></summary>

#### Short answer

Long transactions keep database resources open, reduce pool availability, hold locks/snapshots, and make failures more expensive.

#### Interview answer

A Java service under load has a limited pool of connections. If each request holds a transaction for a long time, throughput collapses because connections are occupied.

Long transactions also interact badly with MVCC and vacuum.

#### Deep dive

They can block other transactions, accumulate row versions, make deadlock windows larger, and cause stale snapshots. If the service crashes, rollback may undo a large amount of work.

Long transactions are often caused by broad service methods and external calls inside transaction boundaries.

#### Production angle

Production rule: make transactions as short as correctness allows. Split orchestration from persistence, use outbox for external side effects, and batch large work carefully.

Monitor transaction duration and connection usage.

#### Traps / caveats

- Long read-only transactions can still be harmful.
- Locks are held until commit.
- Rollback cost can be large.
- Timeouts should protect both app and DB.

#### Optional Anki

Q: Why avoid long transactions?
A: They hold connections, locks and snapshots, reducing throughput and harming MVCC cleanup.

</details>

<a id="db-java-017"></a>

<details>
<summary><strong>DB-JAVA-017. What is the N+1 problem from the database perspective?</strong></summary>

#### Short answer

N+1 is one query for parent rows plus N additional queries for related rows, causing many round trips and repeated index/table access.

#### Interview answer

From the database side, N+1 looks like many similar small queries. Each may be fast alone, but together they create latency, CPU, connection usage, and query overhead.

It is common with ORM lazy loading in loops.

#### Deep dive

Example: load 100 orders, then load customer for each order separately. That is 101 queries instead of one join/fetch or two batched queries.

Solutions include JOIN FETCH, EntityGraph, batch fetching, DTO projections, or explicit queries.

#### Production angle

In production, detect N+1 through SQL logs, APM traces, query frequency, and request-level DB call counts.

Database optimization alone will not fix a bad access pattern.

#### Traps / caveats

- N+1 can overload the DB with many cheap queries.
- Adding indexes may hide but not fix it.
- EAGER everywhere can create worse queries.
- Measure query count per request.

#### Optional Anki

Q: N+1 from DB perspective?
A: Many repeated round trips/queries instead of a set-based query.

</details>

<a id="db-java-018"></a>

<details>
<summary><strong>DB-JAVA-018. How do batch inserts and batch updates work?</strong></summary>

#### Short answer

Batch operations group many similar SQL statements and send/execute them more efficiently than one round trip per row.

#### Interview answer

JDBC supports batching through `addBatch()` and `executeBatch()`. PostgreSQL driver and server can optimize repeated statements and reduce network overhead.

In ORM, batching often needs configuration and correct flush/clear behavior.

#### Deep dive

Batching improves throughput but increases transaction size. Very large batches can hold locks longer, generate large WAL bursts, consume memory, and cause bigger rollbacks.

Sometimes COPY is better for bulk loads.

#### Production angle

In production, tune batch size. Common starting points are tens or hundreds, not unbounded thousands.

Commit in chunks for huge imports and monitor WAL, locks, replication lag, and pool usage.

#### Traps / caveats

- Batching is not the same as one giant transaction.
- ORM identity generation strategy can disable batching.
- Large batches can hurt replicas via WAL spikes.
- Handle partial failures carefully.

#### Optional Anki

Q: What is the point of JDBC batching?
A: Reduce round trips and improve throughput for repeated similar statements.

</details>

<a id="db-java-019"></a>

<details>
<summary><strong>DB-JAVA-019. How would you safely build dynamic SQL?</strong></summary>

#### Short answer

Use bind parameters for values and allowlists for dynamic identifiers or SQL fragments.

#### Interview answer

Values like email, status, ids, timestamps should be passed through PreparedStatement parameters.

But column names, table names, sort directions, and SQL keywords cannot be bound as values. For them, map user choices to allowed constants.

#### Deep dive

Example: if API supports sort by name or created_at, convert input to an enum and produce only known SQL fragments.

Query builders can help, but unsafe string concatenation can still introduce injection.

#### Production angle

In production, review dynamic query builders carefully. Add tests with malicious inputs and monitor slow dynamic query patterns.

Prefer clear repository methods for common queries.

#### Traps / caveats

- Bind parameters do not work for identifiers.
- Escaping is harder than allowlisting.
- Dynamic optional filters can create plan instability.
- Never trust client-provided SQL fragments.

#### Optional Anki

Q: How to safely handle dynamic ORDER BY?
A: Map allowed client values to hardcoded column/direction fragments.

</details>

<a id="db-java-020"></a>

<details>
<summary><strong>DB-JAVA-020. What is the difference between application-level validation and database constraints?</strong></summary>

#### Short answer

Application validation gives user-friendly checks before writing; database constraints enforce invariants for all writers under concurrency.

#### Interview answer

Application code can validate format, business workflow, and user-facing messages. But only database constraints protect data if another service, script, migration, or race condition writes invalid data.

Important invariants should often exist in both layers.

#### Deep dive

Examples: `NOT NULL`, `UNIQUE`, `CHECK`, foreign keys, exclusion constraints. Application validation complements them with better UX.

Race conditions make database constraints especially important for uniqueness and relationships.

#### Production angle

In production, constraint violations should be handled gracefully and mapped to proper API errors.

During migrations, add constraints safely using techniques like backfill, NOT VALID/VALIDATE where appropriate.

#### Traps / caveats

- Application validation can be bypassed.
- Database constraints can be less user-friendly without error mapping.
- Constraints can lock or scan large tables when added carelessly.
- Do not duplicate complex business workflows blindly in DB constraints.

#### Optional Anki

Q: Why keep DB constraints if app validates?
A: They protect invariants for all writers and under concurrency.

</details>
