# Join algorithms

---

<a id="db-joinalg-001"></a>

<details>
<summary><strong>🧠 DB-JOINALG-001. What join algorithms does PostgreSQL use?</strong></summary>

#### Short answer

The main PostgreSQL join algorithms are Nested Loop Join, Hash Join, and Merge Join.

#### Interview answer

SQL join type describes semantics; join algorithm describes physical execution.

#### Deep dive

The planner chooses an algorithm based on row estimates, indexes, join condition, ordering, memory, and cost settings. In `EXPLAIN`, read the node name together with join conditions and child nodes.

```text
Nested Loop
  -> ...
  -> Index Scan ...

Hash Join
  Hash Cond: (o.customer_id = c.id)
  -> Hash

Merge Join
  Merge Cond: (a.id = b.a_id)
```

#### Production angle

When debugging joins, inspect algorithm, join order, estimated/actual rows, loops, hash batches, sort spills, indexes, buffers, and whether `Memoize` appears on repeated parameterized lookups.

#### Traps / caveats

- Join type and join algorithm are different.
- The same SQL join can use different algorithms.
- Bad estimates often cause bad join choices.

#### Optional Anki

Q: What join algorithms does PostgreSQL use?
A: The main PostgreSQL join algorithms are Nested Loop Join, Hash Join, and Merge Join.

</details>

<a id="db-joinalg-002"></a>

<details>
<summary><strong>🧠 DB-JOINALG-002. What is a Nested Loop Join?</strong></summary>

#### Short answer

Nested Loop Join iterates rows from the outer input and searches matching rows in the inner input for each outer row.

#### Interview answer

Conceptually it is like a loop inside a loop, but the inner side can be an efficient index lookup. Modern PostgreSQL may add `Memoize` to cache repeated inner lookups.

#### Deep dive

It is excellent when the outer side is small and the inner access path is cheap; it is terrible when the outer side is huge and inner lookup repeats many times. In plans, the total cost is often hidden in `loops`, not in one execution of the inner node.

#### Production angle

In `EXPLAIN ANALYZE`, pay attention to `loops`, actual rows on the outer side, and `Memoize` hit/miss counters when present. A node that is fast once can be expensive when executed hundreds of thousands of times.

#### Traps / caveats

- Nested Loop is not always bad.
- Large unexpected outer rows make it dangerous.
- Inner side usually needs a good index.
- `Memoize` can help repeated lookups, but it does not fix a fundamentally huge outer input.

#### Optional Anki

Q: What is a Nested Loop Join?
A: Nested Loop Join iterates rows from the outer input and searches matching rows in the inner input for each outer row.

</details>

<a id="db-joinalg-003"></a>

<details>
<summary><strong>🧠 DB-JOINALG-003. When is Nested Loop Join a good strategy?</strong></summary>

#### Short answer

It is good when the outer input is small and each inner lookup is cheap, usually indexed.

#### Interview answer

Examples: join a few orders to their items, fetch children for one aggregate root, or run a selective query with `LIMIT`.

#### Deep dive

Nested loops can also be good when ordered index access lets the query stop early.

#### Production angle

For Java services fetching by primary key or tenant-scoped ID, nested loops with correct indexes are often ideal.

#### Traps / caveats

- Good for small outer side.
- Good inner index matters.
- LIMIT/order can make it attractive.

#### Optional Anki

Q: When is Nested Loop Join a good strategy?
A: It is good when the outer input is small and each inner lookup is cheap, usually indexed.

</details>

<a id="db-joinalg-004"></a>

<details>
<summary><strong>🧠 DB-JOINALG-004. When can Nested Loop Join become very slow?</strong></summary>

#### Short answer

When the outer side is much larger than expected or the inner side has no efficient access path.

#### Interview answer

A common bad plan is estimated 100 outer rows but actual 1,000,000 rows; the inner lookup then repeats too many times.

#### Deep dive

The root cause is often wrong estimates from stale stats, data skew, correlated predicates, or missing indexes.

#### Production angle

Fix estimates, reduce the outer input earlier, add the right index, or let the planner switch to Hash/Merge Join.

#### Traps / caveats

- Nested Loop may be symptom, not root cause.
- Check loops and actual rows.
- Do not force join methods as a long-term fix.

#### Optional Anki

Q: When can Nested Loop Join become very slow?
A: When the outer side is much larger than expected or the inner side has no efficient access path.

</details>

<a id="db-joinalg-005"></a>

<details>
<summary><strong>🧠 DB-JOINALG-005. What is a Hash Join?</strong></summary>

#### Short answer

Hash Join builds a hash table from one input and probes it with rows from the other input.

#### Interview answer

It is usually used for equality joins over medium/large inputs when nested loops would be too expensive and useful ordering is not available.

#### Deep dive

PostgreSQL usually builds the hash table on the smaller side. If the hash table does not fit memory, it may use batches and temporary files. In a plan, look for `Hash Cond`, `Buckets`, `Batches`, and memory usage.

```text
Hash Join
  Hash Cond: (line_items.order_id = orders.id)
  -> Seq Scan on line_items
  -> Hash
       Buckets: 262144  Batches: 1  Memory Usage: 12000kB
```

#### Production angle

When debugging, check hash memory usage, buckets, batches, temp reads/writes, `work_mem`, `hash_mem_multiplier`, and whether inputs can be filtered earlier.

#### Traps / caveats

- Mostly for equality joins.
- Can spill to disk.
- Indexes are not required for Hash Join, but can reduce inputs.

#### Optional Anki

Q: What is a Hash Join?
A: Hash Join builds a hash table from one input and probes it with rows from the other input.

</details>

<a id="db-joinalg-006"></a>

<details>
<summary><strong>🧠 DB-JOINALG-006. When is Hash Join a good strategy?</strong></summary>

#### Short answer

It is good for equality joins with large enough inputs when hashing is cheaper than repeated index lookups or sorting.

#### Interview answer

It is common in reporting, analytics, and joins where both sides are scanned and joined by an equality key.

#### Deep dive

If it fits in memory, it can be very fast. If it spills, performance can degrade sharply.

#### Production angle

For heavy reports, consider filtering earlier, proper statistics, session-level `work_mem`, or separating reporting workloads.

#### Traps / caveats

- Only equality joins are natural for Hash Join.
- Input size matters.
- Spill behavior matters.

#### Optional Anki

Q: When is Hash Join a good strategy?
A: It is good for equality joins with large enough inputs when hashing is cheaper than repeated index lookups or sorting.

</details>

<a id="db-joinalg-007"></a>

<details>
<summary><strong>🧠 DB-JOINALG-007. How does work_mem affect Hash Join?</strong></summary>

#### Short answer

`work_mem` and `hash_mem_multiplier` influence how much memory a Hash Join can use before PostgreSQL uses batches/temp files.

#### Interview answer

If the hash table is too large, PostgreSQL partitions it into batches and reads/writes temporary data, which can be slow. A jump from `Batches: 1` to many batches is a strong spill signal.

#### Deep dive

A single query can use multiple memory allocations, and concurrency multiplies memory demand. Hash joins may use `work_mem * hash_mem_multiplier`, so changing memory globally can have a large blast radius.

#### Production angle

Tune carefully: raising global `work_mem` can hurt stability; prefer reducing inputs or session-level tuning when appropriate.

```sql
BEGIN;
SET LOCAL work_mem = '256MB';
-- one heavy analytical query
COMMIT;
```

#### Traps / caveats

- `work_mem` is per operation.
- Hash nodes also depend on `hash_mem_multiplier`.
- Parallel/concurrent queries multiply usage.
- Spill may indicate too much input, not only too little memory.

#### Optional Anki

Q: How does work_mem affect Hash Join?
A: work_mem limits memory available for hash tables before PostgreSQL uses batches/temp files.

</details>

<details>
<summary><strong>🧠 DB-JOINALG-008. What is a Merge Join?</strong></summary>

#### Short answer

Merge Join joins two sorted inputs by walking through them in order and matching equal join keys.

#### Interview answer

It works well when both inputs are already sorted by the join key or can be sorted cheaply.

#### Deep dive

PostgreSQL may use indexes to produce sorted input or add explicit Sort nodes before the Merge Join.

#### Production angle

If a Merge Join is slow, inspect Sort nodes, sort spills, indexes that could provide order, and row estimates.

#### Traps / caveats

- Merge Join is not SQL MERGE.
- Requires sorted inputs.
- Sort cost can dominate.

#### Optional Anki

Q: What is a Merge Join?
A: Merge Join joins two sorted inputs by walking through them in order and matching equal join keys.

</details>

<a id="db-joinalg-009"></a>

<details>
<summary><strong>🧠 DB-JOINALG-009. When is Merge Join a good strategy?</strong></summary>

#### Short answer

It is good when both inputs are already sorted or sorting is cheap, especially for large equality joins.

#### Interview answer

Indexes on join keys can allow PostgreSQL to stream both sides in order without explicit sorting.

#### Deep dive

Merge Join can be attractive when output ordering is also needed.

#### Production angle

If sorts spill to disk, consider indexes, reducing input, or local `work_mem` tuning.

#### Traps / caveats

- Useful order can come from indexes.
- Hash Join may beat Merge Join if sorting is expensive.
- Needs correct row estimates.

#### Optional Anki

Q: When is Merge Join a good strategy?
A: It is good when both inputs are already sorted or sorting is cheap, especially for large equality joins.

</details>

<details>
<summary><strong>🧠 DB-JOINALG-010. How can indexes affect join strategy?</strong></summary>

#### Short answer

Indexes can make nested-loop lookups cheap, provide sorted input for merge joins, or reduce inputs before any join.

#### Interview answer

An index on the inner join key often supports Nested Loop. B-tree indexes on both join keys may support Merge Join. Filtering indexes reduce row counts.

#### Deep dive

A composite index matching filters plus join/order columns can be much more useful than separate indexes.

#### Production angle

Before adding an index, check read benefit, write overhead, migration safety, and whether the query plan actually changes.

#### Traps / caveats

- Indexing FK columns is often useful but not enough.
- Composite index order matters.
- Too many indexes hurt writes.

#### Optional Anki

Q: How can indexes affect join strategy?
A: Indexes can make nested-loop lookups cheap, provide sorted input for merge joins, or reduce inputs before any join.

</details>

<details>
<summary><strong>🧠 DB-JOINALG-011. Why can PostgreSQL choose a bad join strategy?</strong></summary>

#### Short answer

Usually because estimates are wrong or available paths make the wrong strategy look cheap.

#### Interview answer

Root causes include stale stats, data skew, correlated columns, generic plans, missing indexes, wrong predicates, or non-representative data.

#### Deep dive

Bad strategies often appear as huge-loop Nested Loops, spilling Hash Joins, or Merge Joins with expensive Sorts.

#### Production angle

Fix estimates and access paths rather than forcing join methods permanently.

#### Traps / caveats

- Planner toggles are diagnostic.
- Bad join order may start from an earlier misestimate.
- Real parameter values matter.

#### Optional Anki

Q: Why can PostgreSQL choose a bad join strategy?
A: Usually because estimates are wrong or available paths make the wrong strategy look cheap.

</details>

<a id="db-joinalg-012"></a>

<details>
<summary><strong>🧠 DB-JOINALG-012. How would you optimize a slow join?</strong></summary>

#### Short answer

Use real query/parameters, run `EXPLAIN (ANALYZE, BUFFERS)`, and inspect join order, algorithm, estimates, loops, buffers, indexes, and memory spills.

#### Interview answer

Find whether the bottleneck is too many input rows, bad estimates, missing indexes, wrong join predicates, sort/hash spill, locks, or application-level N+1.

#### Deep dive

Then reduce inputs earlier, add/change indexes, rewrite query, update stats, add extended stats, tune memory locally, or split skewed cases. Temporarily toggling join methods can test a hypothesis, but it should not be the durable fix.

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT ... FROM a JOIN b ON ...;

SET LOCAL enable_nestloop = off;
-- diagnostic only: compare alternative plan shape
```

#### Production angle

Validate on production-like data and consider write overhead/migration safety for any index. In application incidents, also check whether the “slow join” is actually an ORM N+1 query pattern or a missing tenant predicate.

#### Traps / caveats

- Do not blindly add indexes.
- Check actual rows and loops.
- A missing tenant filter can look like a join problem.
- Do not ship disabled join methods as normal application configuration.

#### Optional Anki

Q: How would you optimize a slow join?
A: Use real query/parameters, run EXPLAIN (ANALYZE, BUFFERS), and inspect join order, algorithm, estimates, loops, buffers, indexes, and memory spills.
