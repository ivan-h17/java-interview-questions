<details>
<summary><strong>DB-TX-001. What does ACID mean?</strong></summary>

#### Short answer

ACID means Atomicity, Consistency, Isolation, and Durability.

#### Interview answer

These are transaction guarantees: all-or-nothing, valid state transitions, concurrency isolation, and persistence after commit.

#### Deep dive

PostgreSQL implements these properties using WAL, MVCC, locks, constraints, snapshots, and crash recovery. Different isolation levels provide different trade-offs.

#### Production angle

For Java backend systems, ACID matters in order creation, payments, inventory, idempotency, outbox writes, and any operation where partial writes break invariants.

#### Traps / caveats

- ACID does not mean every anomaly is impossible at every isolation level.
- Consistency is partly enforced by DB constraints and partly by application design.
- Durability can be affected by database configuration.

#### Optional Anki

Q: What does ACID mean?
A: ACID means Atomicity, Consistency, Isolation, and Durability.

</details>

<details>
<summary><strong>DB-TX-006. What isolation levels exist in SQL?</strong></summary>

#### Short answer

SQL isolation levels are Read Uncommitted, Read Committed, Repeatable Read, and Serializable.

#### Interview answer

They define which concurrency anomalies may be allowed.

#### Deep dive

PostgreSQL has specific behavior: Read Uncommitted behaves like Read Committed, and Repeatable Read prevents phantoms in PostgreSQL.

#### Production angle

Do not assume behavior is identical across DBMSs. Always know the actual database implementation.

#### Traps / caveats

- PostgreSQL default is Read Committed.
- Read Uncommitted is not dirty-read mode in PostgreSQL.
- Serializable requires retry handling.

#### Optional Anki

Q: What isolation levels exist in SQL?
A: SQL isolation levels are Read Uncommitted, Read Committed, Repeatable Read, and Serializable.

</details>

<details>
<summary><strong>DB-TX-008. What is Read Committed?</strong></summary>

#### Short answer

Read Committed means each statement sees data committed before that statement starts.

#### Interview answer

It is PostgreSQL’s default isolation level.

#### Deep dive

Two SELECT statements in one transaction can see different results if another transaction commits between them.

#### Production angle

For read-modify-write logic, use atomic updates, explicit locks, unique constraints, or optimistic locking when needed.

#### Traps / caveats

- Statement-level snapshot, not transaction-level snapshot.
- Non-repeatable reads are possible.
- Naive read-modify-write can be unsafe.

#### Optional Anki

Q: What is Read Committed?
A: Read Committed means each statement sees data committed before that statement starts.

</details>

<a id="db-tx-009"></a>

<details>
<summary><strong>DB-TX-009. What is Repeatable Read?</strong></summary>

#### Short answer

Repeatable Read gives a transaction a stable snapshot for its lifetime.

#### Interview answer

In PostgreSQL, Repeatable Read is snapshot isolation: it gives a stable transaction snapshot and prevents phantom reads, but it is still not Serializable.

#### Deep dive

The transaction does not see changes committed after its snapshot was taken. However, snapshot isolation can still allow write-skew-style business invariant bugs when two transactions update different rows after reading the same predicate.

#### Production angle

Useful for consistent reports or multi-step reads, but long transactions can delay cleanup and increase bloat risk. For business invariants, prefer constraints, explicit locks, or Serializable with retry.

#### Traps / caveats

- Long Repeatable Read transactions can harm VACUUM.
- Not identical across all DBMSs.
- Still not the same as Serializable.
- Can allow write-skew-style invariant violations unless guarded by constraints, locks, or Serializable retry.

#### Optional Anki

Q: What is Repeatable Read?
A: In PostgreSQL, it gives a stable transaction snapshot and prevents phantoms, but it is still snapshot isolation, not full Serializable.

</details>

<details>
<summary><strong>DB-TX-010. What is Serializable?</strong></summary>

#### Short answer

Serializable is the strongest isolation level: transactions behave as if executed one at a time in some serial order.

#### Interview answer

PostgreSQL implements it using Serializable Snapshot Isolation and can abort transactions to prevent anomalies.

#### Deep dive

Serialization failure is expected behavior, not a database bug.

#### Production angle

Applications must retry the whole transaction with bounded retry and proper idempotency/side-effect design.

#### Traps / caveats

- Serializable requires retry logic.
- Not “no concurrency”.
- Conflict-heavy workloads can see more aborts.

#### Optional Anki

Q: What is Serializable?
A: Serializable is the strongest isolation level: transactions behave as if executed one at a time in some serial order.

</details>

<summary><strong>DB-TX-011. What is the default isolation level in PostgreSQL?</strong></summary>

#### Short answer

The default PostgreSQL isolation level is Read Committed.

#### Interview answer

Each statement gets its own snapshot of committed data.

#### Deep dive

This means repeated reads inside one transaction can observe different committed states.

#### Production angle

In Spring, `@Transactional` usually uses the database default unless isolation is configured.

#### Traps / caveats

- Default is not Serializable.
- Two SELECTs can see different data.
- Spring may inherit DB default.

#### Optional Anki

Q: What is the default isolation level in PostgreSQL?
A: The default PostgreSQL isolation level is Read Committed.

<details>
<summary><strong>DB-TX-012. Why does PostgreSQL Read Uncommitted behave like Read Committed?</strong></summary>

#### Short answer

Because PostgreSQL MVCC does not allow dirty reads.

#### Interview answer

Transactions read committed row versions according to snapshot visibility rules.

#### Deep dive

Uncommitted changes from other transactions are not visible as ordinary data.

#### Production angle

Do not use Read Uncommitted expecting dirty reads or special performance in PostgreSQL.

#### Traps / caveats

- SQL level exists, but implementation maps behavior.
- Dirty reads are unavailable.
- Other databases can differ.

#### Optional Anki

Q: Why does PostgreSQL Read Uncommitted behave like Read Committed?
A: Because PostgreSQL MVCC does not allow dirty reads.

</details>

<details>
<summary><strong>DB-TX-013. What is Dirty Read?</strong></summary>

#### Short answer

Dirty Read is reading another transaction’s uncommitted data.

#### Interview answer

If the other transaction rolls back, the reader saw data that never committed.

#### Deep dive

PostgreSQL prevents dirty reads even under Read Uncommitted behavior.

#### Production angle

In PostgreSQL interviews, mention that dirty read is a standard anomaly but not possible with normal PostgreSQL isolation.

#### Traps / caveats

- Do not confuse with non-repeatable read.
- PostgreSQL does not expose uncommitted data.
- Dirty read is about uncommitted writes.

#### Optional Anki

Q: What is Dirty Read?
A: Dirty Read is reading another transaction’s uncommitted data.

</details>

<a id="db-tx-014"></a>

<details>
<summary><strong>DB-TX-014. What is Non-Repeatable Read?</strong></summary>

#### Short answer

Non-repeatable read occurs when the same row read twice in one transaction has different committed values.

#### Interview answer

At Read Committed, each statement has a new snapshot, so another committed update can become visible.

#### Deep dive

Repeatable Read prevents this by using a stable transaction snapshot.

#### Production angle

If stable reads are required, use Repeatable Read, explicit locks, or atomic update patterns.

#### Traps / caveats

- Possible at Read Committed.
- Different from phantom read.
- May matter in multi-step validation.

#### Optional Anki

Q: What is Non-Repeatable Read?
A: Non-repeatable read occurs when the same row read twice in one transaction has different committed values.

</details>

<a id="db-tx-015"></a>

<details>
<summary><strong>DB-TX-015. What is Phantom Read?</strong></summary>

#### Short answer

Phantom Read happens when repeating a predicate query returns a different set of rows due to concurrent inserts/deletes.

#### Interview answer

It is about sets/ranges, not a single row changing value.

#### Deep dive

PostgreSQL Read Committed can see phantoms. PostgreSQL Repeatable Read prevents them under its implementation.

#### Production angle

For range invariants, use the right isolation, constraints, locks, or serializable retry design.

#### Traps / caveats

- Phantoms are range/set anomalies.
- PostgreSQL Repeatable Read is stronger than SQL minimum.
- Serializable may be needed for complex invariants.

#### Optional Anki

Q: What is Phantom Read?
A: Phantom Read happens when repeating a predicate query returns a different set of rows due to concurrent inserts/deletes.

</details>

<a id="db-tx-016"></a>

<details>
<summary><strong>DB-TX-016. What is Lost Update?</strong></summary>

#### Short answer

Lost Update occurs when concurrent transactions overwrite each other’s updates based on stale reads.

#### Interview answer

Example: two requests read stock=10, both calculate 9, and both write 9, though correct result should be 8.

#### Deep dive

Prevent with atomic SQL updates, row locks, optimistic locking/version columns, constraints, or Serializable plus retry. If you must read before deciding, lock the row explicitly; if you can express the change as one statement, prefer an atomic update and check affected rows.

```sql
UPDATE products
SET stock = stock - 1
WHERE id = ? AND stock > 0;

SELECT *
FROM products
WHERE id = ?
FOR UPDATE;
```

#### Production angle

In JPA/Hibernate, use `@Version` for optimistic locking when entity-level lost updates matter. For hot counters or inventory, atomic SQL is usually simpler and safer than loading an entity, modifying it, and relying on dirty checking.

#### Traps / caveats

- Naive read-modify-write is unsafe.
- ORM dirty checking can hide risk.
- Atomic SQL often helps.
- `SELECT FOR UPDATE` belongs to locking behavior; use it deliberately and keep transactions short.

#### Optional Anki

Q: What is Lost Update?
A: Lost Update occurs when concurrent transactions overwrite each other’s updates based on stale reads.

</details>

<details>
<summary><strong>DB-TX-017. Which anomalies are possible at PostgreSQL Read Committed?</strong></summary>

#### Short answer

Dirty reads are prevented, but non-repeatable reads, phantoms, and read-modify-write anomalies can happen.

#### Interview answer

Each statement sees a fresh committed snapshot, so the world can change between statements in the same transaction. That is fine for many CRUD flows, but unsafe for multi-step business decisions unless guarded.

#### Deep dive

Lost updates, non-repeatable reads, phantoms, and inconsistent decisions are possible with naive application logic. PostgreSQL still prevents dirty reads.

#### Production angle

Use atomic updates, constraints, explicit locks, optimistic locking, idempotency keys, or stricter isolation for critical invariants. In Spring, `@Transactional` gives a boundary, not automatic correctness for every invariant.

#### Traps / caveats

- No dirty reads in PostgreSQL.
- Read Committed is not enough for every invariant.
- `@Transactional` alone does not solve all anomalies.
- External side effects still need idempotency/outbox design.

#### Optional Anki

Q: Which anomalies are possible at PostgreSQL Read Committed?
A: Dirty reads are prevented, but non-repeatable reads, phantoms, and read-modify-write anomalies can happen.

</details>

<a id="db-tx-018"></a>

<details>
<summary><strong>🧠 DB-TX-018. How does PostgreSQL Repeatable Read differ from standard Repeatable Read?</strong></summary>

#### Short answer

PostgreSQL Repeatable Read is stronger than the SQL standard minimum because it prevents phantom reads.

#### Interview answer

It gives a stable snapshot for the whole transaction and prevents phantoms in PostgreSQL, which is stronger than the SQL standard minimum for Repeatable Read.

#### Deep dive

Changes committed after the snapshot are not visible to the transaction. This prevents many read anomalies, but it does not make all concurrent histories serializable.

#### Production angle

Good for consistent reports, but long snapshots can prevent cleanup and increase bloat. For cross-row invariants such as “at least one doctor on call”, use Serializable retries, constraints, or explicit locking patterns.

#### Traps / caveats

- Not the same across DBMSs.
- Long transactions are dangerous.
- Still not full Serializable.
- Write skew is the classic snapshot-isolation caveat.

#### Optional Anki

Q: How does PostgreSQL Repeatable Read differ from standard Repeatable Read?
A: PostgreSQL Repeatable Read is stronger than the SQL standard minimum because it prevents phantom reads.

</details>

<a id="db-tx-019"></a>

<details>
<summary><strong>🧠 DB-TX-019. What is Snapshot Isolation?</strong></summary>

#### Short answer

Snapshot Isolation means a transaction reads from a consistent committed snapshot as of a point in time.

#### Interview answer

Readers can see old row versions while writers create new versions, so readers and writers often do not block each other.

#### Deep dive

It improves concurrency but requires cleanup of old row versions and can allow anomalies such as write skew when it is not Serializable.

#### Production angle

Long-running snapshots can hold back VACUUM and cause bloat.

#### Traps / caveats

- Snapshot isolation is not always Serializable.
- Long snapshots hurt cleanup.
- Write conflicts still matter.
- Cross-row invariants need additional protection.

#### Optional Anki

Q: What is Snapshot Isolation?
A: Snapshot Isolation means a transaction reads from a consistent committed snapshot as of a point in time.

</details>

<a id="db-tx-020"></a>

<details>
<summary><strong>🧠 DB-TX-020. How does PostgreSQL Serializable isolation work conceptually?</strong></summary>

#### Short answer

It makes concurrent transactions behave as if they ran in some serial order.

#### Interview answer

PostgreSQL uses Serializable Snapshot Isolation and may abort transactions with serialization failures to avoid anomalies.

#### Deep dive

The database detects dangerous read/write dependency patterns and refuses to commit one transaction. Serializable protects invariants by aborting unsafe histories, so the application must be prepared to retry.

#### Production angle

Application code must retry the whole transaction, not just the last statement. Keep external side effects outside the retried unit or protect them with outbox/idempotency.

#### Traps / caveats

- Serialization failure is expected.
- Retries must be bounded.
- External side effects need outbox/idempotency.

#### Optional Anki

Q: How does PostgreSQL Serializable isolation work conceptually?
A: It makes concurrent transactions behave as if they ran in some serial order.

</details>

<a id="db-tx-021"></a>

<details>
<summary><strong>DB-TX-021. Why should applications retry transactions at Serializable isolation?</strong></summary>

#### Short answer

Because PostgreSQL can abort a Serializable transaction to preserve correctness.

#### Interview answer

A serialization failure means the DB prevented an anomaly. The proper response is to retry the entire transaction if the operation is safe.

#### Deep dive

Retries must be designed with idempotency, external side effects, limits, backoff, and observability.

#### Production angle

Never do irreversible external calls inside a retried transaction without outbox/idempotency protection.

#### Traps / caveats

- Retry whole transaction.
- Use bounded retries.
- Design side effects carefully.

#### Optional Anki

Q: Why should applications retry transactions at Serializable isolation?
A: Because PostgreSQL can abort a Serializable transaction to preserve correctness.

</details>
