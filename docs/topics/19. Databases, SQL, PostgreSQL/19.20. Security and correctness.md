# Security and correctness

<a id="db-sec-001"></a>

<details>
<summary><strong>DB-SEC-001. What is SQL injection?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>SQL injection is a vulnerability where attacker-controlled input is interpreted as SQL code instead of data.</p>
</td>
<td valign="top" width="50%">
<p>SQL-инъекция (SQL injection) — это уязвимость, при которой пользовательский ввод интерпретируется как SQL-код, а не как данные.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>It usually happens when application code concatenates user input into a SQL string.</p>
<p>Example: if input changes <code>WHERE email = '...'</code> into <code>WHERE email = '' OR 1=1 --'</code>, the attacker changes query logic.</p>
</td>
<td valign="top" width="50%">
<p>Обычно это происходит, когда код приложения склеивает пользовательский ввод со строкой SQL.</p>
<p>Например, ввод может превратить <code>WHERE email = '...'</code> в <code>WHERE email = '' OR 1=1 --'</code>. В результате атакующий меняет логику запроса.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>SQL injection can read data, bypass authentication, modify data, delete data, or execute database-specific operations depending on permissions and DB features.</p>
<p>The root problem is mixing code and data in one SQL string.</p>
</td>
<td valign="top" width="50%">
<p>SQL-инъекция может читать данные, обходить аутентификацию, изменять или удалять данные и выполнять специфичные для БД операции, если это позволяют права и возможности базы.</p>
<p>Корневая проблема — смешивание кода и данных в одной SQL-строке.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, prevent SQL injection with prepared statements, safe query builders, allowlists for dynamic identifiers, least privilege, review, and tests.</p>
<p>Treat SQL injection as high severity because it can become data breach.</p>
</td>
<td valign="top" width="50%">
<p>В production SQL-инъекции предотвращают подготовленными запросами (prepared statements), безопасными query builder-ами, allowlist-ами для динамических идентификаторов, минимально необходимыми правами (least privilege), ревью и тестами.</p>
<p>SQL-инъекция — критичная проблема, потому что она может привести к утечке данных.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Escaping manually is fragile.</li>
<li>Prepared statements protect values, not arbitrary SQL fragments.</li>
<li>ORM does not automatically make all queries safe.</li>
<li>Least privilege limits blast radius but does not fix injection.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Ручное экранирование хрупкое.</li>
<li>Подготовленные запросы защищают значения, но не произвольные SQL-фрагменты.</li>
<li>ORM не делает все запросы безопасными автоматически.</li>
<li>Минимальные права ограничивают ущерб, но не исправляют саму инъекцию.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is SQL injection?<br>A: User input being executed as SQL code instead of treated as data.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое SQL-инъекция (SQL injection)?<br>A: Пользовательский ввод выполняется как SQL-код вместо того, чтобы обрабатываться как данные.</p>
</td>
</tr>
</tbody>
</table>

</details>

<a id="db-sec-002"></a>

<details>
<summary><strong>DB-SEC-002. How do prepared statements prevent SQL injection?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>They separate SQL text from parameter values, so user input is bound as data and cannot change query structure.</p>
</td>
<td valign="top" width="50%">
<p>Они отделяют текст SQL от значений параметров, поэтому пользовательский ввод привязывается как данные и не может изменить структуру запроса.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>With PreparedStatement, SQL contains placeholders. Values are sent separately using bind parameters.</p>
<p>The database/driver treats those values as literals, even if they contain quotes, comments, or SQL keywords.</p>
</td>
<td valign="top" width="50%">
<p>В <code>PreparedStatement</code> SQL содержит плейсхолдеры, а значения передаются отдельно через bind-параметры.</p>
<p>База или драйвер воспринимают эти значения как литералы, даже если внутри есть кавычки, комментарии или SQL-ключевые слова.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Prepared statements are safe for values in predicates, INSERTs, UPDATEs and similar places. They are not a solution for dynamic column names, table names or ORDER BY direction.</p>
<p>For dynamic structure, use allowlists.</p>
</td>
<td valign="top" width="50%">
<p>Подготовленные запросы безопасны для значений в предикатах, <code>INSERT</code>, <code>UPDATE</code> и похожих местах. Но они не решают проблему динамических имён колонок, таблиц или направления <code>ORDER BY</code>.</p>
<p>Для динамической структуры запроса используй allowlist допустимых вариантов.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, use parameter binding by default in repositories. If raw SQL is needed, review it carefully and test malicious inputs.</p>
<p>Use logging that does not leak sensitive bound values.</p>
</td>
<td valign="top" width="50%">
<p>В production используй привязку параметров по умолчанию во всех repository-слоях. Если нужен raw SQL, внимательно ревьюй его и тестируй вредоносные входные данные.</p>
<p>Логирование не должно раскрывать чувствительные значения параметров.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>PreparedStatement does not authorize access.</li>
<li>It cannot bind identifiers.</li>
<li>Unsafe string concatenation around prepared SQL can still be vulnerable.</li>
<li>Stored procedures can also build unsafe dynamic SQL.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li><code>PreparedStatement</code> не авторизует доступ.</li>
<li>Он не может привязывать идентификаторы как значения.</li>
<li>Небезопасная конкатенация вокруг prepared SQL всё равно может быть уязвимой.</li>
<li>Хранимые процедуры тоже могут собирать небезопасный динамический SQL.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What do prepared statements separate?<br>A: SQL code and parameter values.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что разделяют подготовленные запросы (prepared statements)?<br>A: SQL-код и значения параметров.</p>
</td>
</tr>
</tbody>
</table>

</details>

<a id="db-sec-003"></a>

<details>
<summary><strong>DB-SEC-003. Can SQL injection still happen when using PreparedStatement?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Yes, if only some values are parameterized but other SQL fragments are still built unsafely.</p>
</td>
<td valign="top" width="50%">
<p>Да, если параметризована только часть значений, а другие SQL-фрагменты всё ещё собираются небезопасно.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>PreparedStatement protects bound values. It does not protect string-concatenated table names, column names, ORDER BY clauses, raw WHERE fragments, or stored procedures that build SQL unsafely.</p>
<p>Injection can also happen if developers concatenate input before preparing the statement.</p>
</td>
<td valign="top" width="50%">
<p><code>PreparedStatement</code> защищает привязанные значения. Он не защищает имена таблиц и колонок, <code>ORDER BY</code>, raw <code>WHERE</code>-фрагменты или хранимые процедуры, если они собираются строковой конкатенацией.</p>
<p>Инъекция возможна, если разработчик склеил ввод со строкой SQL до создания prepared statement.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example risky pattern: <code>ORDER BY " + request.getSort()</code>. The sort value must be mapped to an allowlisted column.</p>
<p>Another risky pattern: dynamic <code>IN</code> or WHERE clauses generated from raw strings.</p>
</td>
<td valign="top" width="50%">
<p>Опасный паттерн: <code>ORDER BY " + request.getSort()</code>. Значение сортировки нужно маппить на колонку из allowlist-а.</p>
<p>Другой опасный паттерн — динамические <code>IN</code> или <code>WHERE</code>, собранные из сырых строк.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production code reviews, search for SQL string concatenation, native queries, Criteria string fragments, stored procedure dynamic SQL, and reporting/admin tools.</p>
<p>PreparedStatement is necessary but not enough.</p>
</td>
<td valign="top" width="50%">
<p>На production-ревью ищи конкатенацию SQL-строк, native queries, строковые фрагменты Criteria API, динамический SQL в хранимых процедурах и reporting/admin-инструменты.</p>
<p><code>PreparedStatement</code> необходим, но сам по себе недостаточен.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Identifiers cannot be bound as normal parameters.</li>
<li>Unsafe ORDER BY is common.</li>
<li>Using PreparedStatement after concatenation is not safe.</li>
<li>Authorization bugs can look like injection impact.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Идентификаторы нельзя привязать как обычные параметры.</li>
<li>Небезопасный <code>ORDER BY</code> встречается часто.</li>
<li>Использование <code>PreparedStatement</code> после конкатенации не делает запрос безопасным.</li>
<li>Ошибки авторизации могут выглядеть как последствия SQL-инъекции.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Can injection happen with PreparedStatement?<br>A: Yes, if SQL structure is still concatenated unsafely.</p>
</td>
<td valign="top" width="50%">
<p>Q: Может ли SQL-инъекция случиться с <code>PreparedStatement</code>?<br>A: Да, если структура SQL всё ещё собирается небезопасной конкатенацией.</p>
</td>
</tr>
</tbody>
</table>

</details>

<a id="db-sec-004"></a>

<details>
<summary><strong>DB-SEC-004. How would you safely build queries with dynamic ORDER BY?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Map allowed client sort options to hardcoded SQL fragments; never concatenate raw client input.</p>
</td>
<td valign="top" width="50%">
<p>Сопоставь разрешённые варианты сортировки с заранее заданными SQL-фрагментами; никогда не конкатенируй сырой ввод клиента.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>You cannot bind a column name or direction as a normal value parameter. Instead, parse the request into an enum like CREATED_AT_DESC or NAME_ASC.</p>
<p>Then generate SQL from a fixed allowlist.</p>
</td>
<td valign="top" width="50%">
<p>Имя колонки или направление сортировки нельзя привязать как обычный параметр-значение. Вместо этого разбери запрос в enum вроде <code>CREATED_AT_DESC</code> или <code>NAME_ASC</code>.</p>
<p>Затем генерируй SQL только из фиксированного allowlist-а.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example mapping: <code>createdAtDesc -&gt; ORDER BY created_at DESC, id DESC</code>. Unknown values should be rejected.</p>
<p>Use stable tie-breakers for pagination.</p>
</td>
<td valign="top" width="50%">
<p>Пример маппинга: <code>createdAtDesc -&gt; ORDER BY created_at DESC, id DESC</code>. Неизвестные значения нужно отклонять.</p>
<p>Для пагинации используй стабильные дополнительные ключи сортировки.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, document allowed sort fields and directions in API contract. Add tests for malicious sort parameters.</p>
<p>Ensure each allowed sort has an index strategy if used on large data.</p>
</td>
<td valign="top" width="50%">
<p>В production документируй разрешённые поля и направления сортировки в API-контракте. Добавь тесты на вредоносные параметры сортировки.</p>
<p>Если сортировка используется на больших данных, у каждого разрешённого варианта должна быть индексная стратегия.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Bind parameters are for values, not identifiers.</li>
<li>Do not expose DB column names directly as public API contract unless intentional.</li>
<li>Dynamic sorting can break index usage.</li>
<li>Always include deterministic ordering.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Bind-параметры предназначены для значений, а не для идентификаторов.</li>
<li>Не раскрывай имена колонок БД напрямую в публичном API без явной причины.</li>
<li>Динамическая сортировка может сломать использование индексов.</li>
<li>Всегда добавляй детерминированный порядок сортировки.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Safe dynamic ORDER BY approach?<br>A: Allowlist enum values mapped to hardcoded SQL fragments.</p>
</td>
<td valign="top" width="50%">
<p>Q: Как безопасно сделать динамический ORDER BY?<br>A: Через enum/allowlist, где значения маппятся на заранее заданные SQL-фрагменты.</p>
</td>
</tr>
</tbody>
</table>

<a id="db-sec-005"></a>

<details>
<summary><strong>DB-SEC-005. What database permissions should an application user have?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>An application user should have the minimum permissions needed for its workload, usually not owner or superuser permissions.</p>
</td>
<td valign="top" width="50%">
<p>Пользователь приложения должен иметь минимальные права, необходимые для его нагрузки, и обычно не должен быть владельцем объектов или суперпользователем.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For a typical service, grant access only to required schemas, tables, sequences, functions, and operations. Separate migration/admin users from runtime users.</p>
<p>Read-only jobs should use read-only roles. Runtime roles usually should not own application tables.</p>
</td>
<td valign="top" width="50%">
<p>Обычному сервису дают доступ только к нужным схемам, таблицам, последовательностям, функциям и операциям. Пользователей для миграций и администрирования отделяют от runtime-пользователей приложения.</p>
<p>Read-only задачи должны использовать read-only роли. Runtime-роли обычно не должны владеть таблицами приложения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Least privilege reduces blast radius if SQL injection, credential leak, or application bug happens.</p>
<p>It also makes accidental destructive operations less likely. Review <code>search_path</code>, <code>SECURITY DEFINER</code> functions, default privileges, and schema ownership, because they can accidentally widen runtime power.</p>
</td>
<td valign="top" width="50%">
<p>Минимальные права (least privilege) уменьшают ущерб при SQL-инъекции, утечке credentials или ошибке приложения.</p>
<p>Также снижается риск случайных разрушительных операций. Отдельно проверяют <code>search_path</code>, функции <code>SECURITY DEFINER</code>, права по умолчанию и владение схемами, потому что они могут незаметно расширить возможности runtime-роли.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, use separate credentials per service/environment, rotate secrets, audit grants, and avoid sharing one powerful user across services.</p>
<p>Migration tools may need higher privileges, but runtime app should not. Use explicit GRANTs and review default privileges for newly created tables/sequences.</p>
</td>
<td valign="top" width="50%">
<p>В production используют отдельные credentials для каждого сервиса и окружения, ротируют секреты, аудитят <code>GRANT</code>-ы и не разделяют одного мощного пользователя между сервисами.</p>
<p>Инструментам миграций могут требоваться более широкие права, но runtime-приложению — нет. Для новых таблиц и последовательностей нужны явные <code>GRANT</code>-ы и ревью прав по умолчанию.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Runtime app user should not be superuser.</li>
<li>Do not reuse migration credentials in app runtime.</li>
<li>GRANTs should be reviewed.</li>
<li><code>search_path</code> and <code>SECURITY DEFINER</code> functions are common privilege-escalation footguns.</li>
<li>Least privilege cannot replace input validation.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Runtime-пользователь приложения не должен быть суперпользователем.</li>
<li>Не используй credentials для миграций в runtime-приложении.</li>
<li><code>GRANT</code>-ы нужно ревьюить.</li>
<li><code>search_path</code> и функции <code>SECURITY DEFINER</code> часто становятся источником повышения привилегий.</li>
<li>Минимальные права не заменяют валидацию входных данных.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What principle governs DB permissions?<br>A: Least privilege.</p>
</td>
<td valign="top" width="50%">
<p>Q: Какой принцип для прав в БД?<br>A: Минимально необходимые права (least privilege).</p>
</td>
</tr>
</tbody>
</table>

<a id="db-sec-006"></a>

<details>
<summary><strong>DB-SEC-006. Why should an application usually not connect as a database superuser?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Because any application bug, injection, or credential leak would have unrestricted database power.</p>
</td>
<td valign="top" width="50%">
<p>Потому что любая ошибка приложения, инъекция или утечка credentials получит почти неограниченную власть над базой.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A superuser can bypass protections, read/modify everything, create dangerous functions, change settings, and damage the cluster.</p>
<p>Runtime application logic rarely needs that power.</p>
</td>
<td valign="top" width="50%">
<p>Суперпользователь может обходить защиты, читать и менять всё, создавать опасные функции, менять настройки и повредить кластер.</p>
<p>Runtime-логике приложения почти никогда не нужны такие права.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Separate roles are safer: runtime role for normal app operations, migration role for schema changes, admin role for operations, read-only role for reports.</p>
<p>This also improves auditing.</p>
</td>
<td valign="top" width="50%">
<p>Безопаснее разделять роли: runtime-роль для обычной работы приложения, migration-роль для изменений схемы, admin-роль для администрирования, read-only роль для отчётов.</p>
<p>Такой подход также упрощает аудит.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, verify actual grants. Many incidents happen because an app used a powerful owner account for convenience.</p>
<p>Use secrets management and rotation.</p>
</td>
<td valign="top" width="50%">
<p>В production проверяй фактические права. Многие инциденты происходят из-за того, что приложение для удобства использовало мощную owner-учётку.</p>
<p>Используй управление секретами и ротацию.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Superuser bypasses many safeguards.</li>
<li>Compromised app becomes compromised database.</li>
<li>Migrations and runtime should use different roles.</li>
<li>Cloud-managed DBs may restrict superuser but owner roles can still be too powerful.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Суперпользователь обходит многие защитные механизмы.</li>
<li>Скомпрометированное приложение превращается в скомпрометированную базу.</li>
<li>Миграции и runtime должны использовать разные роли.</li>
<li>В managed cloud-БД суперпользователь может быть ограничен, но owner-роли всё равно часто слишком сильные.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why not connect as superuser?<br>A: It massively increases blast radius of bugs or compromise.</p>
</td>
<td valign="top" width="50%">
<p>Q: Почему не подключаться суперпользователем?<br>A: Это резко увеличивает ущерб от ошибок и компрометации приложения.</p>
</td>
</tr>

<a id="db-sec-007"></a>

<details>
<summary><strong>🧠 DB-SEC-007. What is row-level security in PostgreSQL?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Row-level security lets PostgreSQL restrict which rows a user can read or modify using policies on a table.</p>
</td>
<td valign="top" width="50%">
<p>Защита на уровне строк (Row-Level Security, RLS) позволяет PostgreSQL ограничивать, какие строки пользователь может читать или изменять, через политики на таблице.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>RLS is enabled per table and policies define allowed rows for SELECT, INSERT, UPDATE and DELETE. Policies use <code>USING</code> for visible/target rows and <code>WITH CHECK</code> for rows being inserted or updated.</p>
<p>It can act like an automatic security filter applied inside the database.</p>
</td>
<td valign="top" width="50%">
<p>RLS включается на таблице, а политики определяют разрешённые строки для <code>SELECT</code>, <code>INSERT</code>, <code>UPDATE</code> и <code>DELETE</code>. <code>USING</code> задаёт видимые или целевые строки, а <code>WITH CHECK</code> проверяет строки при <code>INSERT</code> или <code>UPDATE</code>.</p>
<p>Это работает как автоматический security-фильтр внутри базы данных.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>RLS is useful for multi-tenant systems, self-service analytics, and defense-in-depth. Policies can use current database role, session variables, or security context functions.</p>
<p>By default, table owners, superusers, and roles with <code>BYPASSRLS</code> can bypass policies. <code>ALTER TABLE ... FORCE ROW LEVEL SECURITY</code> can force the owner through policies, but superuser/BYPASSRLS still matter.</p>
</td>
<td valign="top" width="50%">
<p>RLS полезен для multi-tenant систем, self-service аналитики и защиты в глубину (defense-in-depth). Политики могут использовать текущую роль БД, session variables или функции security context.</p>
<p>По умолчанию владельцы таблиц, суперпользователи и роли с <code>BYPASSRLS</code> могут обходить политики. <code>ALTER TABLE ... FORCE ROW LEVEL SECURITY</code> заставляет владельца проходить через политики, но superuser и <code>BYPASSRLS</code> всё равно имеют значение.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, RLS must be tested thoroughly. Application must reliably set tenant/user context per transaction/request.</p>
<p>With connection pools, prefer transaction-scoped context such as <code>SET LOCAL app.tenant_id = ...</code> inside the transaction, and make sure context cannot leak to the next request.</p>
<p>RLS should complement application authorization, not replace all of it blindly.</p>
</td>
<td valign="top" width="50%">
<p>В production RLS нужно тщательно тестировать. Приложение должно надёжно выставлять tenant/user context на каждую транзакцию или запрос.</p>
<p>С пулами соединений лучше использовать контекст, ограниченный транзакцией, например <code>SET LOCAL app.tenant_id = ...</code> внутри транзакции, и гарантировать, что контекст не утечёт в следующий запрос.</p>
<p>RLS дополняет авторизацию в приложении, а не слепо заменяет её.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Wrong session context can expose or hide data.</li>
<li>Superuser/owner/<code>BYPASSRLS</code> bypass matters.</li>
<li>Policies can affect query performance.</li>
<li>Connection pool context leaks can become cross-tenant data leaks.</li>
<li>RLS complexity can surprise developers.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Неправильный session context может открыть чужие данные или скрыть свои.</li>
<li>Обход через superuser, owner или <code>BYPASSRLS</code> имеет значение.</li>
<li>Политики могут влиять на производительность запросов.</li>
<li>Утечка контекста через пул соединений может стать cross-tenant утечкой данных.</li>
<li>Сложность RLS часто неожиданна для разработчиков.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does RLS restrict?<br>A: Which rows can be selected/inserted/updated/deleted based on policies.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что ограничивает RLS?<br>A: Какие строки можно читать, вставлять, обновлять или удалять согласно политикам.</p>
</td>
</tr>
</tbody>
</table>

</details>

<details>
<summary><strong>🧠 DB-SEC-008. When would you use row-level security?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use RLS when the database itself should enforce tenant/user row isolation as defense-in-depth or for direct data access.</p>
</td>
<td valign="top" width="50%">
<p>RLS используют, когда сама база должна обеспечивать изоляцию строк по tenant/user: для защиты в глубину или прямого доступа к данным.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Good use cases: multi-tenant SaaS tables, internal analytics tools, user-scoped data, and environments where multiple roles query shared tables.</p>
<p>RLS is especially valuable when not all access goes through one application code path.</p>
</td>
<td valign="top" width="50%">
<p>Хорошие сценарии: multi-tenant SaaS-таблицы, внутренние аналитические инструменты, данные в области конкретного пользователя и окружения, где общие таблицы читают разные роли.</p>
<p>RLS особенно полезен, когда не весь доступ идёт через один путь в коде приложения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>RLS is not free. It adds policy complexity and can affect query planning/performance.</p>
<p>If all access is already strongly controlled by a simple service and operational complexity matters more, application-only enforcement may be chosen.</p>
</td>
<td valign="top" width="50%">
<p>RLS не бесплатен. Он добавляет сложность политик и может влиять на планирование и производительность запросов.</p>
<p>Если весь доступ уже строго контролируется простым сервисом, а операционная сложность важнее, можно выбрать контроль только на уровне приложения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, use RLS with clear policies, tests for cross-tenant access, session context discipline, and monitoring for slow plans.</p>
<p>Make sure the runtime role is not table owner and does not have <code>BYPASSRLS</code>. Add indexes that support policy predicates, for example <code>tenant_id</code>.</p>
<p>Use RLS to reduce blast radius, not as an excuse to skip application authorization.</p>
</td>
<td valign="top" width="50%">
<p>В production RLS используют с понятными политиками, тестами на cross-tenant доступ, строгой дисциплиной session context и мониторингом медленных планов.</p>
<p>Runtime-роль не должна быть владельцем таблицы и не должна иметь <code>BYPASSRLS</code>. Для предикатов политик, например <code>tenant_id</code>, обычно нужны поддерживающие индексы.</p>
<p>RLS уменьшает возможный ущерб, но не является оправданием для пропуска авторизации в приложении.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>RLS can be bypassed by privileged roles.</li>
<li>Testing is mandatory.</li>
<li>Policies can make debugging harder.</li>
<li>Policies without supporting indexes can make tenant-scoped queries slow.</li>
<li>Context propagation bugs are serious.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Привилегированные роли могут обходить RLS.</li>
<li>Тестирование обязательно.</li>
<li>Политики усложняют отладку.</li>
<li>Политики без поддерживающих индексов могут замедлить tenant-scoped запросы.</li>
<li>Ошибки передачи контекста очень опасны.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: When is RLS useful?<br>A: Multi-tenant/user-scoped data where DB-level row isolation is valuable.</p>
</td>
<td valign="top" width="50%">
<p>Q: Когда полезен RLS?<br>A: Когда для multi-tenant или user-scoped данных важна изоляция строк на уровне БД.</p>
</td>
</tr>

<summary><strong>🧠 DB-SEC-009. How would you store sensitive data in PostgreSQL?</strong></summary>

<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Minimize sensitive data, classify it, encrypt where needed, restrict access, avoid logging it, and define retention/deletion rules.</p>
</td>
<td valign="top" width="50%">
<p>Минимизируй чувствительные данные, классифицируй их, шифруй при необходимости, ограничивай доступ, не логируй лишнее и задавай правила хранения/удаления.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Sensitive data includes passwords, tokens, personal data, financial data, secrets and regulated fields.</p>
<p>Passwords should not be encrypted reversibly; store strong salted hashes using application-level password hashing.</p>
</td>
<td valign="top" width="50%">

</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">

<p>Use column access control, RLS where appropriate, auditing, and masking in lower environments.</p>
</td>
<td valign="top" width="50%">

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<li>Encryption without key management is weak.</li>
<li>Backups also contain sensitive data.</li>
<li>Logs often leak parameters accidentally.</li>
</ul>
</td>

<ul>

<li>Шифрование без управления ключами слабое.</li>
