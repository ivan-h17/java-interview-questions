# Security and correctness

<a id="db-sec-001"></a>

<details>
<summary><strong>DB-SEC-001. What is SQL injection?</strong></summary>

#### Short answer

SQL injection is a vulnerability where attacker-controlled input is interpreted as SQL code instead of data.

#### Interview answer

It usually happens when application code concatenates user input into a SQL string.

Example: if input changes `WHERE email = '...'` into `WHERE email = '' OR 1=1 --'`, the attacker changes query logic.

#### Deep dive

SQL injection can read data, bypass authentication, modify data, delete data, or execute database-specific operations depending on permissions and DB features.

The root problem is mixing code and data in one SQL string.

#### Production angle

In production, prevent SQL injection with prepared statements, safe query builders, allowlists for dynamic identifiers, least privilege, review, and tests.

Treat SQL injection as high severity because it can become data breach.

#### Traps / caveats

- Escaping manually is fragile.
- Prepared statements protect values, not arbitrary SQL fragments.
- ORM does not automatically make all queries safe.
- Least privilege limits blast radius but does not fix injection.

#### Optional Anki

Q: What is SQL injection?
A: User input being executed as SQL code instead of treated as data.

</details>

<a id="db-sec-002"></a>

<details>
<summary><strong>DB-SEC-002. How do prepared statements prevent SQL injection?</strong></summary>

#### Short answer

They separate SQL text from parameter values, so user input is bound as data and cannot change query structure.

#### Interview answer

With PreparedStatement, SQL contains placeholders. Values are sent separately using bind parameters.

The database/driver treats those values as literals, even if they contain quotes, comments, or SQL keywords.

#### Deep dive

Prepared statements are safe for values in predicates, INSERTs, UPDATEs and similar places. They are not a solution for dynamic column names, table names or ORDER BY direction.

For dynamic structure, use allowlists.

#### Production angle

In production, use parameter binding by default in repositories. If raw SQL is needed, review it carefully and test malicious inputs.

Use logging that does not leak sensitive bound values.

#### Traps / caveats

- PreparedStatement does not authorize access.
- It cannot bind identifiers.
- Unsafe string concatenation around prepared SQL can still be vulnerable.
- Stored procedures can also build unsafe dynamic SQL.

#### Optional Anki

Q: What do prepared statements separate?
A: SQL code and parameter values.

</details>

<a id="db-sec-003"></a>

<details>
<summary><strong>DB-SEC-003. Can SQL injection still happen when using PreparedStatement?</strong></summary>

#### Short answer

Yes, if only some values are parameterized but other SQL fragments are still built unsafely.

#### Interview answer

PreparedStatement protects bound values. It does not protect string-concatenated table names, column names, ORDER BY clauses, raw WHERE fragments, or stored procedures that build SQL unsafely.

Injection can also happen if developers concatenate input before preparing the statement.

#### Deep dive

Example risky pattern: `ORDER BY " + request.getSort()`. The sort value must be mapped to an allowlisted column.

Another risky pattern: dynamic `IN` or WHERE clauses generated from raw strings.

#### Production angle

In production code reviews, search for SQL string concatenation, native queries, Criteria string fragments, stored procedure dynamic SQL, and reporting/admin tools.

PreparedStatement is necessary but not enough.

#### Traps / caveats

- Identifiers cannot be bound as normal parameters.
- Unsafe ORDER BY is common.
- Using PreparedStatement after concatenation is not safe.
- Authorization bugs can look like injection impact.

#### Optional Anki

Q: Can injection happen with PreparedStatement?
A: Yes, if SQL structure is still concatenated unsafely.

</details>

<a id="db-sec-004"></a>

<details>
<summary><strong>DB-SEC-004. How would you safely build queries with dynamic ORDER BY?</strong></summary>

#### Short answer

Map allowed client sort options to hardcoded SQL fragments; never concatenate raw client input.

#### Interview answer

You cannot bind a column name or direction as a normal value parameter. Instead, parse the request into an enum like CREATED_AT_DESC or NAME_ASC.

Then generate SQL from a fixed allowlist.

#### Deep dive

Example mapping: `createdAtDesc -> ORDER BY created_at DESC, id DESC`. Unknown values should be rejected.

Use stable tie-breakers for pagination.

#### Production angle

In production, document allowed sort fields and directions in API contract. Add tests for malicious sort parameters.

Ensure each allowed sort has an index strategy if used on large data.

#### Traps / caveats

- Bind parameters are for values, not identifiers.
- Do not expose DB column names directly as public API contract unless intentional.
- Dynamic sorting can break index usage.
- Always include deterministic ordering.

#### Optional Anki

Q: Safe dynamic ORDER BY approach?
A: Allowlist enum values mapped to hardcoded SQL fragments.

</details>

<a id="db-sec-005"></a>

<details>
<summary><strong>DB-SEC-005. What database permissions should an application user have?</strong></summary>

#### Short answer

An application user should have the minimum permissions needed for its workload, usually not owner or superuser permissions.

#### Interview answer

For a typical service, grant access only to required schemas, tables, sequences, functions, and operations. Separate migration/admin users from runtime users.

Read-only jobs should use read-only roles. Runtime roles usually should not own application tables.

#### Deep dive

Least privilege reduces blast radius if SQL injection, credential leak, or application bug happens.

It also makes accidental destructive operations less likely. Review `search_path`, `SECURITY DEFINER` functions, default privileges, and schema ownership, because they can accidentally widen runtime power.

#### Production angle

In production, use separate credentials per service/environment, rotate secrets, audit grants, and avoid sharing one powerful user across services.

Migration tools may need higher privileges, but runtime app should not. Use explicit GRANTs and review default privileges for newly created tables/sequences.

#### Traps / caveats

- Runtime app user should not be superuser.
- Do not reuse migration credentials in app runtime.
- GRANTs should be reviewed.
- `search_path` and `SECURITY DEFINER` functions are common privilege-escalation footguns.
- Least privilege cannot replace input validation.

#### Optional Anki

Q: What principle governs DB permissions?
A: Least privilege.

</details>

<a id="db-sec-006"></a>

<details>
<summary><strong>DB-SEC-006. Why should an application usually not connect as a database superuser?</strong></summary>

#### Short answer

Because any application bug, injection, or credential leak would have unrestricted database power.

#### Interview answer

A superuser can bypass protections, read/modify everything, create dangerous functions, change settings, and damage the cluster.

Runtime application logic rarely needs that power.

#### Deep dive

Separate roles are safer: runtime role for normal app operations, migration role for schema changes, admin role for operations, read-only role for reports.

This also improves auditing.

#### Production angle

In production, verify actual grants. Many incidents happen because an app used a powerful owner account for convenience.

Use secrets management and rotation.

#### Traps / caveats

- Superuser bypasses many safeguards.
- Compromised app becomes compromised database.
- Migrations and runtime should use different roles.
- Cloud-managed DBs may restrict superuser but owner roles can still be too powerful.

#### Optional Anki

Q: Why not connect as superuser?
A: It massively increases blast radius of bugs or compromise.

</details>

<a id="db-sec-007"></a>

<details>
<summary><strong>🧠 DB-SEC-007. What is row-level security in PostgreSQL?</strong></summary>

#### Short answer

Row-level security lets PostgreSQL restrict which rows a user can read or modify using policies on a table.

#### Interview answer

RLS is enabled per table and policies define allowed rows for SELECT, INSERT, UPDATE and DELETE. Policies use `USING` for visible/target rows and `WITH CHECK` for rows being inserted or updated.

It can act like an automatic security filter applied inside the database.

#### Deep dive

RLS is useful for multi-tenant systems, self-service analytics, and defense-in-depth. Policies can use current database role, session variables, or security context functions.

By default, table owners, superusers, and roles with `BYPASSRLS` can bypass policies. `ALTER TABLE ... FORCE ROW LEVEL SECURITY` can force the owner through policies, but superuser/BYPASSRLS still matter.

#### Production angle

In production, RLS must be tested thoroughly. Application must reliably set tenant/user context per transaction/request.

With connection pools, prefer transaction-scoped context such as `SET LOCAL app.tenant_id = ...` inside the transaction, and make sure context cannot leak to the next request.

RLS should complement application authorization, not replace all of it blindly.

#### Traps / caveats

- Wrong session context can expose or hide data.
- Superuser/owner/`BYPASSRLS` bypass matters.
- Policies can affect query performance.
- Connection pool context leaks can become cross-tenant data leaks.
- RLS complexity can surprise developers.

#### Optional Anki

Q: What does RLS restrict?
A: Which rows can be selected/inserted/updated/deleted based on policies.

</details>

<a id="db-sec-008"></a>

<details>
<summary><strong>🧠 DB-SEC-008. When would you use row-level security?</strong></summary>

#### Short answer

Use RLS when the database itself should enforce tenant/user row isolation as defense-in-depth or for direct data access.

#### Interview answer

Good use cases: multi-tenant SaaS tables, internal analytics tools, user-scoped data, and environments where multiple roles query shared tables.

RLS is especially valuable when not all access goes through one application code path.

#### Deep dive

RLS is not free. It adds policy complexity and can affect query planning/performance.

If all access is already strongly controlled by a simple service and operational complexity matters more, application-only enforcement may be chosen.

#### Production angle

In production, use RLS with clear policies, tests for cross-tenant access, session context discipline, and monitoring for slow plans.

Make sure the runtime role is not table owner and does not have `BYPASSRLS`. Add indexes that support policy predicates, for example `tenant_id`.

Use RLS to reduce blast radius, not as an excuse to skip application authorization.

#### Traps / caveats

- RLS can be bypassed by privileged roles.
- Testing is mandatory.
- Policies can make debugging harder.
- Policies without supporting indexes can make tenant-scoped queries slow.
- Context propagation bugs are serious.

#### Optional Anki

Q: When is RLS useful?
A: Multi-tenant/user-scoped data where DB-level row isolation is valuable.

</details>

<a id="db-sec-009"></a>

<details>
<summary><strong>🧠 DB-SEC-009. How would you store sensitive data in PostgreSQL?</strong></summary>

#### Short answer

Minimize sensitive data, classify it, encrypt where needed, restrict access, avoid logging it, and define retention/deletion rules.

#### Interview answer

Sensitive data includes passwords, tokens, personal data, financial data, secrets and regulated fields.

Passwords should not be encrypted reversibly; store strong salted hashes using application-level password hashing.

#### Deep dive

For fields that must be recoverable, consider encryption at application level or database/extension/cloud KMS approaches. Manage keys separately from the database.

Use column access control, RLS where appropriate, auditing, and masking in lower environments.

#### Production angle

In production, do data minimization first: do not store what you do not need. Define retention, deletion, backups, restore procedures and incident response.

Prevent secrets from appearing in logs, traces and query dashboards.

#### Traps / caveats

- Hash passwords, do not encrypt them for later decryption.
- Encryption without key management is weak.
- Backups also contain sensitive data.
- Logs often leak parameters accidentally.

#### Optional Anki

Q: How store passwords?
A: As strong salted hashes, not reversible encrypted values.

</details>

<a id="db-sec-010"></a>

<details>
<summary><strong>DB-SEC-010. What are the risks of logging SQL queries with parameters?</strong></summary>

#### Short answer

SQL logs with parameters can expose passwords, tokens, personal data, financial data, tenant data and business secrets.

#### Interview answer

Detailed SQL logging is useful for debugging, but bound values may include sensitive data. Logs are often copied to centralized systems with broad access and long retention.

An innocent debug log can become a data leak.

#### Deep dive

Risk is higher for authentication, payments, PII, secrets, tokens and multi-tenant data. Even query shape can reveal business behavior.

Use redaction, sampling, normalized query fingerprints, and strict access controls.

#### Production angle

In production, avoid logging raw parameter values by default. Enable detailed logging only temporarily, with approval and retention controls.

Review APM/tracing tools too; they can capture SQL parameters.

#### Traps / caveats

- Logs are part of the security boundary.
- Redaction must happen before data leaves service.
- Debug logging can violate compliance.
- Slow query logs may include sensitive statements.

#### Optional Anki

Q: Main risk of SQL parameter logging?
A: Leaking sensitive data through logs/traces/APM.

</details>
