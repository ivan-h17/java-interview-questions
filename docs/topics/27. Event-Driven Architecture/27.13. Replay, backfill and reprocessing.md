# Replay, backfill and reprocessing

---

<a id="eda-replay-001"></a>

<details>
<summary><strong>EDA-REPLAY-001. What is event replay, and when is it useful?</strong></summary>

#### Short answer

Event replay means processing past events again to rebuild, repair, audit, or onboard consumers.

#### Interview answer

Replay is useful for rebuilding projections, backfilling a new consumer, recovering after a bug, migrating storage, or recalculating derived state. It depends on event retention, schema compatibility, and replay-safe handlers.

#### Deep dive

Replay is easy only if events are retained, ordered enough for the use case, and interpretable by current code. Consumers must distinguish state updates from external side effects.

#### Production angle

Plan replay before incidents. Define retention windows, tooling, throttling, checkpoints, validation, and rollback strategy.

#### Traps / caveats

- Replaying can duplicate external side effects.
- Old events may use old schemas.
- Replay can overload databases and downstream systems.

#### Optional Anki

Q: What is event replay?
A: Reprocessing historical events.

</details>

<details>
<summary><strong>EDA-REPLAY-002. What are the risks of replaying historical events?</strong></summary>

#### Short answer

Replay can corrupt current state, repeat side effects, overload systems, or fail on old schema versions.

#### Interview answer

If a handler sends emails or charges payments, replaying old events can repeat those effects. If current code interprets old events differently, it can build incorrect state. If replay is too fast, it can overload databases and brokers.

#### Deep dive

Historical events may include facts that were valid under older business rules. Reprocessing them with current rules may not reproduce original decisions unless the event model and code handle versioning.

#### Production angle

Run replay in controlled batches with idempotency, side-effect suppression, metrics, and validation against expected counts or checksums.

#### Traps / caveats

- "Just reset offset" is not a safe replay plan.
- Current code may not be compatible with old events.
- Replaying into live tables needs careful cutover or checkpoints.

#### Optional Anki

Q: Biggest replay risk?
A: Repeating side effects or corrupting derived state.

</details>

<details>
<summary><strong>EDA-REPLAY-003. How do you backfill a new consumer from an existing event stream?</strong></summary>

#### Short answer

Start from a known offset or snapshot, process historical events safely, then catch up to live traffic.

#### Interview answer

I would confirm event retention and schema compatibility, create the consumer with a separate group or subscription, process history into its own state store, monitor lag, validate output, then enable live reads or actions after catch-up.

#### Deep dive

If retention does not cover all required history, backfill may need a database export, snapshot, object storage archive, or special migration stream.

#### Production angle

Throttle backfill so it does not starve live consumers or overload shared databases. Keep clear checkpoints so the job can resume.

#### Traps / caveats

- Historical data may include deleted or anonymized records.
- Backfill should not trigger production notifications.
- Catch-up logic must handle events arriving during the backfill.

#### Optional Anki

Q: How do you onboard a new projection consumer?
A: Backfill from retained events or source snapshot, validate, then catch up to live.

</details>

<a id="eda-replay-004"></a>

<details>
<summary><strong>🧠 EDA-REPLAY-004. How do you reprocess events with fixed consumer code without corrupting current state or repeating side effects?</strong></summary>

#### Short answer

Use replay mode, idempotent writes, side-effect suppression, checkpoints, and validation before switching traffic.

#### Interview answer

After fixing the consumer, I would decide whether to repair affected records or rebuild the whole projection. I would replay into a new table or isolated namespace when possible, disable external effects, compare results, then cut over safely.

#### Deep dive

For live state, use event versions, sequence checks, and deterministic rebuild logic. For external side effects, rely on stored operation records or explicitly skip them during replay.

#### Production angle

Critical repairs should produce an audit trail: what was replayed, which code version, which offsets, which rows changed, and what validation passed.

#### Traps / caveats

- Reprocessing into the same table can mix old and new logic.
- Replayed events can arrive out of order relative to live updates.
- Skipping side effects must be explicit and tested.

#### Optional Anki

Q: Safe replay strategy after consumer bug?
A: Replay idempotently into isolated state, suppress side effects, validate, then cut over or repair.

</details>
