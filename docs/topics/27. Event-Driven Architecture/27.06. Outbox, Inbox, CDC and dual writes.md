# Outbox, Inbox, CDC and dual writes

---

<a id="eda-outbox-001"></a>

<details>
<summary><strong>EDA-OUTBOX-001. What is the dual-write problem?</strong></summary>

#### Short answer

The dual-write problem happens when one operation must update two systems, such as a database and a broker, without one atomic commit.

#### Interview answer

If a service saves an order and publishes `OrderCreated`, there are two writes: database and broker. If the database commits but publishing fails, the event is lost. If the event is published but the transaction rolls back, consumers see a false event.

#### Deep dive

The problem is not fixed by changing the order of operations. Publishing before commit and publishing after commit both have crash windows. Without a distributed transaction or reliability pattern, the systems can diverge.

#### Production angle

Dual-write bugs show up as missing events, ghost events, inconsistent projections, stuck Sagas, and manual data repair.

#### Traps / caveats

- "Publish after commit" still fails if the process crashes before publish.
- Retrying publish can create duplicates.
- Broker durability does not prove database commit.

#### Optional Anki

Q: What is the dual-write problem?
A: Updating two systems without one atomic commit can leave them inconsistent.

</details>

<a id="eda-outbox-002"></a>

<details>
<summary><strong>EDA-OUTBOX-002. What problem does the Transactional Outbox pattern solve?</strong></summary>

#### Short answer

It reliably ties event publication to a local database transaction.

#### Interview answer

The service writes business data and an outbox row in the same database transaction. A separate relay later reads the outbox and publishes events to the broker. If the transaction rolls back, no outbox row exists. If it commits, the event is durably available for publishing.

#### Deep dive

Outbox avoids distributed transactions between database and broker. It does not prevent duplicate publication, so consumers must remain idempotent.

#### Production angle

Use Outbox for events derived from committed state changes, such as order created, account debited, payment captured, or shipment requested.

#### Traps / caveats

- The outbox row must be written in the same transaction as business data.
- Relay failures create lag and need monitoring.
- Outbox does not remove schema evolution or replay concerns.

#### Optional Anki

Q: What does Transactional Outbox guarantee?
A: If the local database transaction commits, the event record is durably stored for publishing.

</details>

<a id="eda-outbox-003"></a>

<details>
<summary><strong>EDA-OUTBOX-003. What fields are commonly stored in an outbox table, and where should the transaction boundary be?</strong></summary>

#### Short answer

Common fields include event ID, aggregate ID, event type, payload, headers, status, timestamps, retry count, and error details. The outbox insert belongs in the same transaction as the business change.

#### Interview answer

For order creation, the transaction writes the `orders` row and an outbox row with `OrderCreated`. The relay later publishes that row and marks it published or records retry state.

#### Deep dive

A useful outbox schema supports ordering, retry, deduplication, observability, and cleanup. The event ID should be stable so duplicate publishing can be safely deduplicated downstream.

#### Production angle

Indexes usually target unpublished status plus creation time. Cleanup or archiving must avoid deleting records before audit, replay, or troubleshooting windows are satisfied.

#### Traps / caveats

- Do not generate a new event ID on every relay retry.
- Do not publish directly inside the transaction and treat outbox as backup.
- Large payloads can make the table expensive to scan and retain.

#### Optional Anki

Q: Where should the outbox write occur?
A: In the same local transaction as the business data change.

</details>

<a id="eda-outbox-004"></a>

<details>
<summary><strong>EDA-OUTBOX-004. How do polling-based and CDC-based outbox relays differ?</strong></summary>

#### Short answer

Polling queries the outbox table directly; CDC reads committed changes from the database log.

#### Interview answer

A polling relay periodically selects unpublished rows, claims them, publishes, and marks them sent. A CDC relay uses database change data capture, often through a connector, to stream inserted outbox rows to the broker.

#### Deep dive

Polling is simpler and easier to operate at small to medium scale, but it adds query load and polling latency. CDC can be lower-latency and scalable, but adds connector offsets, database-log behavior, schema-change handling, and operational complexity.

#### Production angle

Start with polling unless throughput, latency, or database load justify CDC. Either way, monitor relay lag and failures.

#### Traps / caveats

- Polling needs safe row claiming to avoid duplicate workers.
- CDC can still duplicate on connector restart.
- Schema changes can break CDC pipelines if not tested.

#### Optional Anki

Q: Polling vs CDC outbox?
A: Polling reads the table; CDC streams committed changes from the database log.

</details>

<a id="eda-outbox-005"></a>

<details>
<summary><strong>EDA-OUTBOX-005. What happens if an outbox relay publishes an event and crashes before marking it as sent?</strong></summary>

#### Short answer

The event may be published again after restart, so consumers must be idempotent.

#### Interview answer

The relay cannot atomically publish to the broker and mark the database row as sent unless another distributed transaction is used. If it crashes between those actions, the row still looks unpublished and will be retried.

#### Deep dive

This is normal and expected. Outbox improves reliability by preventing lost events, but it commonly gives at-least-once publication. Event IDs, consumer deduplication, and safe handlers close the loop.

#### Production angle

A duplicate `OrderCreated` should not create two orders in a projection, send two payment charges, or reserve inventory twice.

#### Traps / caveats

- Marking sent before publishing can lose events.
- Marking sent after publishing can duplicate events.
- Idempotency is required even if the relay is well implemented.

#### Optional Anki

Q: Why can Outbox publish duplicates?
A: The relay can crash after broker publish but before recording success.

</details>

<a id="eda-outbox-006"></a>

<details>
<summary><strong>EDA-OUTBOX-006. What is the Inbox pattern, and how do Outbox and Inbox work together?</strong></summary>

#### Short answer

Inbox records consumed message IDs or incoming commands so a consumer can process each one safely once.

#### Interview answer

Outbox protects reliable publishing from the producer. Inbox protects reliable consumption on the receiver. A consumer inserts an inbox or processed-message record in the same transaction as its business update. If the same message arrives again, the unique key detects it.

#### Deep dive

Together they form an at-least-once workflow with effectively-once outcomes: producer stores events durably, broker may redeliver, and consumer deduplicates transactionally.

#### Production angle

Use Inbox for payment handling, inventory reservation, ledger updates, and any handler where duplicates would corrupt state.

#### Traps / caveats

- Inbox must be in the same transaction as the side effect it protects.
- Deduplication retention must cover redelivery and replay windows.
- One event may need separate idempotency for separate side effects.

#### Optional Anki

Q: Outbox vs Inbox?
A: Outbox protects publishing; Inbox protects consuming.

</details>

<a id="eda-outbox-007"></a>

<details>
<summary><strong>🧠 EDA-OUTBOX-007. How is the Outbox pattern different from Event Sourcing, and what CDC gotchas matter?</strong></summary>

#### Short answer

Outbox stores integration messages alongside current-state persistence. Event Sourcing stores domain state itself as an event history.

#### Interview answer

With Outbox, the main state may still be normal relational tables, and events are a publication mechanism. With Event Sourcing, the event stream is the source of truth, and current state is reconstructed from events.

#### Deep dive

CDC-based outbox reads committed outbox inserts from the database log. Gotchas include connector restarts, duplicates, schema changes, transaction boundaries, large transactions, log retention, ordering assumptions, and whether metadata includes commit order and timestamps.

#### Production angle

Choose Outbox for reliable integration from conventional services. Choose Event Sourcing only when historical state transitions, audit, temporal queries, or event-first modeling justify the complexity.

#### Traps / caveats

- Outbox events are not automatically a complete domain history.
- CDC is operational infrastructure, not just a library.
- Raw CDC table changes are not the same as stable integration events.

#### Optional Anki

Q: Main difference between Outbox and Event Sourcing?
A: Outbox publishes events from current-state persistence; Event Sourcing persists state as events.

</details>
