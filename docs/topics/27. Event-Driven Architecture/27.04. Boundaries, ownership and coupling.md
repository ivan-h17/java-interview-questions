# Boundaries, ownership and coupling

---

<a id="eda-bound-001"></a>

<details>
<summary><strong>EDA-BOUND-001. Who should own an event type and its schema?</strong></summary>

#### Short answer

The service or team that owns the business fact should own the event type and schema.

#### Interview answer

If the order service owns order lifecycle, it should own `OrderCreated`, `OrderApproved`, or `OrderCancelled` integration events. Ownership means defining semantics, schema, versioning, compatibility policy, documentation, and deprecation.

#### Deep dive

Consumers can request changes, but they should not directly control the producer's event model. Otherwise the producer becomes a shared integration database in message form.

#### Production angle

Event ownership should appear in catalogs, runbooks, schema registry metadata, and on-call escalation paths.

#### Traps / caveats

- No owner means no safe evolution.
- Shared ownership often causes ambiguous semantics.
- Consumer-specific fields can pollute a general event contract.

#### Optional Anki

Q: Who owns `OrderCreated`?
A: The team that owns the order lifecycle fact.

</details>

<a id="eda-bound-002"></a>

<details>
<summary><strong>EDA-BOUND-002. How do bounded contexts influence event design?</strong></summary>

#### Short answer

Bounded contexts define which language, rules, and facts an event should expose.

#### Interview answer

An event from the order context should use order-domain concepts, not inventory table names or payment internals. When another bounded context consumes it, it may translate the event into its own model instead of adopting the producer's language everywhere.

#### Deep dive

This prevents semantic coupling. For example, "reserved" may mean different things in inventory, payment, and fulfillment. Events need clear definitions at the context boundary.

#### Production angle

Good boundaries reduce accidental dependencies and make schema evolution safer across teams.

#### Traps / caveats

- Same word can have different meanings in different contexts.
- Do not publish persistence objects as integration events.
- Translation code is often necessary and healthy.

#### Optional Anki

Q: Why do bounded contexts matter for events?
A: They keep event meaning aligned with the owning domain language.

</details>

<details>
<summary><strong>EDA-BOUND-003. Why should consumers not depend on a producer's database schema?</strong></summary>

#### Short answer

Because database schema is an internal implementation detail, while events are external contracts.

#### Interview answer

If consumers depend on column names, join structure, or raw change-data records, the producer cannot refactor storage safely. Integration events should expose stable business facts, not internal tables.

#### Deep dive

CDC can be useful for publishing events, but raw database changes are often technical events. They may expose temporary states, normalized structure, internal IDs, or fields that have no stable business meaning.

#### Production angle

Database-coupled consumers cause migration risk. A simple table split can become a cross-team incident.

#### Traps / caveats

- CDC-based outbox is different from exposing all table changes.
- Raw data-change events can be valid inside a data platform, but they need clear scope.
- Stable integration events may intentionally duplicate or reshape data.

#### Optional Anki

Q: Why avoid exposing database schema as an event contract?
A: It couples consumers to producer storage internals.

</details>

<details>
<summary><strong>EDA-BOUND-004. How can an anti-corruption layer be used for consumed events?</strong></summary>

#### Short answer

It translates external event contracts into the consumer's internal model.

#### Interview answer

A consumer should not spread producer DTOs across its domain logic. An anti-corruption layer validates the event, maps fields, handles versions, and converts external language into local commands or domain objects.

#### Deep dive

This is especially useful when consuming events from another bounded context, vendor, or legacy system. It contains schema ugliness and semantic differences at the boundary.

#### Production angle

An anti-corruption layer makes contract changes easier to test and reduces impact when a producer adds fields or publishes a new version.

#### Traps / caveats

- Mapping code should include validation and defaults.
- Do not silently accept semantically invalid events.
- Avoid leaking external event classes into core domain code.

#### Optional Anki

Q: What does an event anti-corruption layer do?
A: It maps external event contracts into the consumer's internal model.

</details>

<details>
<summary><strong>🧠 EDA-BOUND-005. What are the risks of a shared enterprise event model?</strong></summary>

#### Short answer

A shared enterprise model can create global coupling, slow evolution, and ambiguous ownership.

#### Interview answer

A single canonical model sounds attractive, but many domains use similar words differently. If every service must conform to one model, small changes require broad coordination and teams lose autonomy. It can become a distributed shared database in schema form.

#### Deep dive

Some shared vocabulary is useful for truly common identifiers or metadata. The risk is forcing domain-specific behavior into one generic object with unclear semantics.

#### Production angle

Prefer owned, domain-specific integration events with documented translations. Use common envelopes and shared primitives carefully, not a universal business object.

#### Traps / caveats

- "Canonical" often becomes lowest-common-denominator.
- Global schemas can block independent deployability.
- Governance should enable evolution, not centralize every design decision.

#### Optional Anki

Q: Main risk of a shared enterprise event model?
A: It creates global schema and semantic coupling.

</details>
