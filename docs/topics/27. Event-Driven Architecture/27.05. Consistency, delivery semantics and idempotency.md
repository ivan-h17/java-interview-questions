# Consistency, delivery semantics and idempotency

---

<a id="eda-rel-001"></a>

<details>
<summary><strong>EDA-REL-001. What is eventual consistency in event-driven systems?</strong></summary>

#### Short answer

Eventual consistency means different parts of the system may be temporarily out of sync but should converge if processing succeeds.

#### Interview answer

After an order is created, the order database may be updated immediately, while search, analytics, notification, and inventory projections update later. During that delay, reads from those systems may not reflect the latest state.

#### Deep dive

Eventual consistency is a product and architecture decision. It requires explicit workflow states, retry handling, monitoring, and reconciliation. It is acceptable for many background views, but not for all invariants.

#### Production angle

Expose statuses like `PENDING`, `PROCESSING`, or `CONFIRMED` instead of pretending every downstream system updates instantly.

#### Traps / caveats

- Eventual consistency is not an excuse for lost events.
- Users may need clear UI feedback.
- Some domains require immediate consistency for critical decisions.

#### Optional Anki

Q: What does eventual consistency require?
A: A design for convergence, failure handling, and user-visible intermediate states.

</details>

<a id="eda-rel-002"></a>

<details>
<summary><strong>EDA-REL-002. How can read-your-own-writes expectations be handled in an eventually consistent flow?</strong></summary>

#### Short answer

Return authoritative state from the write service, expose workflow status, or route reads to a source that has observed the write.

#### Interview answer

If a user creates an order and immediately refreshes, they expect to see it. The API can return the created representation directly, read from the command-side database, show a pending status, or wait only for a specific projection checkpoint when the latency budget allows.

#### Deep dive

Read-your-own-writes is a UX guarantee, not just a database property. In event-driven systems, read models and replicas lag. The design should decide which views are immediate and which are eventually updated.

#### Production angle

For important flows, include operation IDs, status endpoints, or projection version checks so clients do not misinterpret lag as failure.

#### Traps / caveats

- Blindly reading from replicas or projections can show stale state.
- Blocking until all consumers finish can destroy the benefit of async design.
- Polling status needs timeouts and clear terminal states.

#### Optional Anki

Q: How can an API handle read-your-own-writes with async projections?
A: Return authoritative state or expose a pending workflow/status model.

</details>

<a id="eda-rel-003"></a>

<details>
<summary><strong>EDA-REL-003. What is the difference between at-most-once, at-least-once and exactly-once delivery?</strong></summary>

#### Short answer

At-most-once may lose messages, at-least-once may duplicate them, and exactly-once means a specific system avoids duplicates within defined boundaries.

#### Interview answer

At-most-once typically acknowledges before processing, so failures can lose messages. At-least-once acknowledges after processing or durable receipt, so retries can duplicate messages. Exactly-once claims must be read carefully because they often apply only inside a broker or stream-processing transaction, not to external databases or APIs.

#### Deep dive

Most backend systems design for at-least-once plus idempotent consumers. It is practical because duplicate handling is usually easier than proving no loss or no duplicates across multiple systems.

#### Production angle

Payment, inventory, email, and database writes must be safe under retry. This is an application-level requirement, not just a broker setting.

#### Traps / caveats

- "Exactly-once" rarely means exactly-once business effect.
- At-most-once is dangerous for important state changes.
- At-least-once without idempotency causes duplicate side effects.

#### Optional Anki

Q: Common backend default for reliable messaging?
A: At-least-once delivery plus idempotent processing.

</details>

<a id="eda-rel-004"></a>

<details>
<summary><strong>EDA-REL-004. Why do backend systems often assume at-least-once delivery?</strong></summary>

#### Short answer

Because retrying after uncertain failures is safer than silently losing important messages.

#### Interview answer

If a consumer crashes after updating the database but before acknowledging the message, the broker may redeliver. That duplicate is usually preferable to losing the event entirely. The system then needs idempotency to make repeated processing safe.

#### Deep dive

Distributed systems often cannot distinguish "operation failed" from "operation succeeded but acknowledgement failed". At-least-once accepts this ambiguity and pushes correctness into deduplication and idempotent writes.

#### Production angle

Use processed-message tables, unique constraints, idempotency keys, upserts, and transactional boundaries to protect state.

#### Traps / caveats

- Do not rely on "it probably only happens once".
- Retries can duplicate external calls.
- Deduplication retention must match redelivery and replay requirements.

#### Optional Anki

Q: Why assume duplicate delivery?
A: Because crashes and acknowledgement failures make redelivery normal in reliable systems.

</details>

<a id="eda-rel-005"></a>

<details>
<summary><strong>EDA-REL-005. What is an idempotent consumer, and how do you choose an idempotency key?</strong></summary>

#### Short answer

An idempotent consumer produces the same final result when processing the same event more than once. The key should uniquely identify the business operation or event.

#### Interview answer

For event deduplication, the idempotency key is often `eventId` plus consumer name. For commands, it may be a client-provided command ID. For business operations, it may be a natural unique key such as payment transaction ID.

#### Deep dive

The key must match the side effect being protected. If one event triggers several independent effects, each may need its own idempotency record. Store deduplication in the same transaction as the state update when possible.

#### Production angle

Database unique constraints are a strong tool: insert a processed-message row and update business state in one transaction.

#### Traps / caveats

- Aggregate ID alone is usually not enough; one aggregate has many events.
- Generated random keys at the consumer do not deduplicate retries.
- Dedup records need cleanup only after safe retention windows.

#### Optional Anki

Q: What is a common consumer deduplication key?
A: Consumer identity plus event ID.

</details>

<a id="eda-rel-006"></a>

<details>
<summary><strong>EDA-REL-006. How do you make external side effects safe when events can be redelivered?</strong></summary>

#### Short answer

Use idempotency keys, transactional state, provider-side deduplication, and avoid repeating irreversible effects during retries.

#### Interview answer

If a handler charges a payment, sends an email, or calls another API, duplicate delivery can repeat the side effect. The handler should record intent and result, use stable idempotency keys with external providers, and retry only operations that are safe or guarded.

#### Deep dive

External side effects are harder than database updates because they are outside the local transaction. A common design is to store a local operation record, call the provider with an idempotency key, then record the result and handle ambiguous timeouts by querying provider status.

#### Production angle

Payments, shipping labels, webhooks, and emails need explicit duplicate-suppression and reconciliation workflows.

#### Traps / caveats

- Retrying after timeout may duplicate work if the provider lacks idempotency.
- Email is often acceptable to duplicate less than payment, but still affects users.
- Do not replay historical events into live external effects by accident.

#### Optional Anki

Q: How do you make payment processing safe under duplicate events?
A: Use stable idempotency keys and persist operation state.

</details>

<a id="eda-rel-007"></a>

<details>
<summary><strong>🧠 EDA-REL-007. Why is end-to-end exactly-once processing hard across a broker and an external database?</strong></summary>

#### Short answer

Because the broker, database, and external services have separate commit and failure boundaries.

#### Interview answer

A consumer may write to a database and then fail before acknowledging the broker. The broker redelivers, and the database write may happen again unless guarded. Broker transactions can help inside the broker, but they usually do not include arbitrary relational database writes or external APIs.

#### Deep dive

True atomicity across systems requires distributed transactions or carefully designed application protocols. Most teams avoid distributed transactions and instead use local transactions, Outbox/Inbox, idempotency, reconciliation, and replay-safe design.

#### Production angle

The realistic goal is effectively-once business outcome: duplicates may occur technically, but state and side effects converge correctly.

#### Traps / caveats

- Kafka exactly-once does not automatically make database writes exactly once.
- Database uniqueness can protect state but not all external calls.
- Reconciliation is still needed for ambiguous failures.

#### Optional Anki

Q: Practical alternative to end-to-end exactly-once?
A: At-least-once delivery with idempotent, transactional, and reconcilable processing.

</details>
