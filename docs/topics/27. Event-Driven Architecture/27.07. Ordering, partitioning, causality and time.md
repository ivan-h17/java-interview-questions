# Ordering, partitioning, causality and time

---

<a id="eda-order-001"></a>

<details>
<summary><strong>EDA-ORDER-001. Why is event ordering hard in distributed systems?</strong></summary>

#### Short answer

Different producers, partitions, networks, retries, and clocks can observe and deliver events in different orders.

#### Interview answer

There is rarely one global sequence of everything that happened. Two services can publish concurrently, retries can delay older events, consumers can process at different speeds, and broker partitions usually preserve order only inside a partition or message group.

#### Deep dive

Ordering needs a scope. Per-order ordering is realistic. Global ordering across all orders, payments, and inventory is usually expensive and unnecessary.

#### Production angle

Define ordering requirements explicitly: per aggregate, per account, per tenant, per partition, or none. Then choose keys, consumer concurrency, and storage accordingly.

#### Traps / caveats

- Timestamp order is not reliable global order.
- Consumer parallelism can break processing order.
- Retries and DLQ redrive can reintroduce old events.

#### Optional Anki

Q: What ordering scope is usually practical?
A: Per entity or aggregate, not global system-wide ordering.

</details>

<a id="eda-order-002"></a>

<details>
<summary><strong>EDA-ORDER-002. When do you really need global ordering?</strong></summary>

#### Short answer

Rarely. You need it only when all events must be interpreted through one total sequence.

#### Interview answer

Global ordering may be useful for a single ledger, matching engine, or serialized command stream. Most business systems need ordering only within a specific entity, such as one order, account, customer, or inventory item.

#### Deep dive

Global ordering limits throughput and availability because all writes contend for one sequence. It can also make multi-region designs slower and more fragile.

#### Production angle

Ask what invariant actually requires ordering. If only one account balance needs sequential updates, partition by account rather than forcing all accounts through one global lane.

#### Traps / caveats

- "Nice for debugging" is not enough reason for global ordering.
- Global order does not automatically solve all consistency problems.
- Strict ordering can turn one hot key into a bottleneck.

#### Optional Anki

Q: Why avoid global ordering by default?
A: It reduces parallelism and increases coordination cost.

</details>

<a id="eda-order-003"></a>

<details>
<summary><strong>EDA-ORDER-003. How do you preserve ordering per entity, such as per order or per account?</strong></summary>

#### Short answer

Use the entity ID as the partition or message-group key and process that key serially.

#### Interview answer

If all events for `order-123` use `orderId` as the key, a log broker can place them in the same partition. The consumer must also avoid processing multiple events for the same key concurrently unless the operations are safe.

#### Deep dive

Ordering is a combination of producer key choice, broker behavior, consumer concurrency, retries, and state storage. A good key must have enough cardinality to avoid hot partitions while grouping events that require sequencing.

#### Production angle

For account balance changes, use account ID. For order lifecycle, use order ID. Monitor hot keys and lag per partition or group.

#### Traps / caveats

- Changing the key changes ordering semantics.
- Increasing partitions can affect ordering assumptions in some systems.
- DLQ redrive may process older events after newer ones.

#### Optional Anki

Q: How do you preserve per-order event order?
A: Key events by order ID and process each key serially.

</details>

<a id="eda-order-004"></a>

<details>
<summary><strong>EDA-ORDER-004. How should you choose a partition key for an event stream?</strong></summary>

#### Short answer

Choose a key that matches required ordering and has enough cardinality for balanced load.

#### Interview answer

The partition key should group events that must be processed in order, such as `orderId` for order lifecycle events. It should also distribute traffic well. A low-cardinality key like `country` or `status` can create hot partitions.

#### Deep dive

Sometimes ordering and load conflict. If one customer generates huge traffic, customer ID may be a hot key. You may need subkeys, sharding, command serialization, or a different business design.

#### Production angle

Key choice is hard to change later because consumers may depend on ordering. Review it as part of event design.

#### Traps / caveats

- Random keys improve load but lose per-entity ordering.
- Low-cardinality keys create bottlenecks.
- Key semantics should be documented in the event contract.

#### Optional Anki

Q: Good partition key criteria?
A: Groups required ordering and spreads load.

</details>

<a id="eda-order-005"></a>

<details>
<summary><strong>EDA-ORDER-005. What are out-of-order, late, event-time and processing-time issues?</strong></summary>

#### Short answer

Out-of-order means events are processed in a different sequence than expected. Late events arrive after the consumer has already processed newer data. Event time is when the business fact occurred; processing time is when the consumer handles it.

#### Interview answer

A consumer may process `OrderShipped` before `OrderPaid` because of retries or routing delays. The event time may say payment happened earlier, but processing time is later. Consumers need rules for whether to ignore, buffer, compensate, or apply late events.

#### Deep dive

Event time is important for analytics and business correctness. Processing time is important for operations and latency. They are both useful, but neither creates a perfect global order.

#### Production angle

For projections, store version, sequence, status transition rules, or last processed event metadata to handle late arrivals safely.

#### Traps / caveats

- Producer clocks can be wrong.
- Ignoring late events may hide real corrections.
- Buffering for order increases latency and memory use.

#### Optional Anki

Q: Event time vs processing time?
A: Event time is when the fact occurred; processing time is when it is handled.

</details>

<a id="eda-order-006"></a>

<details>
<summary><strong>🧠 EDA-ORDER-006. How can causal ordering or commutative operations reduce strict ordering requirements?</strong></summary>

#### Short answer

Causality tracks what caused what, and commutative operations produce the same result regardless of order.

#### Interview answer

Causation IDs help reconstruct chains such as command -> event -> downstream event. Commutative operations, like adding independent IDs to a set, are less sensitive to ordering than operations like "set balance to current balance minus amount".

#### Deep dive

If handlers can be designed around idempotent and commutative updates, strict ordering becomes less important. For example, storing ledger entries is often safer than mutating a balance directly from unordered deltas.

#### Production angle

Reducing strict ordering improves throughput and recovery because consumers can process in parallel and tolerate redelivery more easily.

#### Traps / caveats

- Not all business operations are commutative.
- Causation IDs help analysis; they do not enforce correctness alone.
- Rebuilding derived state still needs deterministic rules.

#### Optional Anki

Q: Why are commutative handlers useful?
A: They reduce dependence on strict event order.

</details>
