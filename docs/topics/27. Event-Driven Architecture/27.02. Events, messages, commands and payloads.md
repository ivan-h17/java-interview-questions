# Events, messages, commands and payloads

---

<a id="eda-event-001"></a>

<details>
<summary><strong>EDA-EVENT-001. What is the difference between an event and a message?</strong></summary>

#### Short answer

An event is the business fact. A message is the transport package carrying that fact.

#### Interview answer

`OrderCreated` is an event: it says something happened. The Kafka record, RabbitMQ message, or HTTP webhook delivery is the message. The message includes payload and metadata needed to transport, route, trace, and process the event.

#### Deep dive

The distinction matters because transport details should not define the business meaning. The same event could be carried through Kafka, AMQP, SQS, or a webhook with different headers and delivery guarantees.

#### Production angle

Keep event meaning stable while allowing transport-level metadata such as message ID, correlation ID, content type, partition key, and retry count.

#### Traps / caveats

- Do not mix business fields with broker-specific metadata without reason.
- A message may carry a command, event, or request.
- Broker delivery guarantees apply to messages, not automatically to business correctness.

#### Optional Anki

Q: Event vs message?
A: Event is the fact; message is the transport envelope.

</details>

<a id="eda-event-002"></a>

<details>
<summary><strong>EDA-EVENT-002. What is the difference between an event, a command and a request?</strong></summary>

#### Short answer

An event says something happened, a command asks a specific receiver to do something, and a request expects a response.

#### Interview answer

`OrderCreated` is an event. `ReserveInventory` is a command. `GET /orders/123` or `AuthorizePayment` as a call is a request. Events are usually broadcast facts; commands have intent and ownership; requests are usually synchronous interactions with success/failure response.

#### Deep dive

Confusing these leads to weak contracts. If an "event" is named `CreateInvoice`, consumers may treat it as an instruction, making the producer responsible for downstream behavior. A real event should let consumers decide what to do.

#### Production angle

Clear naming helps incident analysis. A payment event should not secretly mean "please ship the order" unless that workflow is explicitly modeled.

#### Traps / caveats

- Past tense usually fits events.
- Commands need a clear target and authorization model.
- Request-response over a broker is possible, but it is still a request pattern.

#### Optional Anki

Q: Why are event names often past tense?
A: Because they describe facts that already happened.

</details>

<a id="eda-event-003"></a>

<details>
<summary><strong>EDA-EVENT-003. What is the difference between a domain event and an integration event?</strong></summary>

#### Short answer

A domain event is internal to a bounded context; an integration event is a public contract for other systems.

#### Interview answer

A domain event captures something meaningful inside the domain model, such as `OrderApproved`. It may contain internal concepts and evolve with the domain. An integration event is deliberately shaped for external consumers and should be stable, documented, versioned, and free of private implementation details.

#### Deep dive

Many systems map domain events to integration events at the boundary. This avoids leaking internal aggregate structure, persistence names, or temporary workflow states to consumers that should not depend on them.

#### Production angle

When teams consume each other's events, integration events should have owners, compatibility rules, deprecation paths, and monitoring.

#### Traps / caveats

- Publishing internal domain events directly can create tight coupling.
- Integration events may be less detailed than domain events.
- Not every internal state change deserves a public event.

#### Optional Anki

Q: Domain event vs integration event?
A: Domain event is internal domain fact; integration event is an external contract.

</details>

<a id="eda-event-004"></a>

<details>
<summary><strong>EDA-EVENT-004. Why should an event usually describe a past fact instead of an intention?</strong></summary>

#### Short answer

Because consumers should react to what happened, not be commanded by a producer's intention.

#### Interview answer

`OrderCreated` tells consumers a fact. `CreateShipment` tells someone what to do. If an event describes intention, it becomes a command disguised as an event and couples the producer to downstream behavior.

#### Deep dive

Fact-based events give consumers autonomy. One consumer may reserve inventory, another may update analytics, and another may ignore the event. The producer should not know or control all future reactions.

#### Production angle

Fact-based naming makes audit, replay, and debugging clearer because the stream records actual system history.

#### Traps / caveats

- Some workflows use command messages; that is fine if named and owned as commands.
- A fact should only be published after the producing state change is committed.
- Avoid vague facts like `DataChanged`.

#### Optional Anki

Q: Why prefer `OrderCreated` over `CreateOrderNotification`?
A: It records a fact rather than prescribing downstream action.

</details>

<a id="eda-event-005"></a>

<details>
<summary><strong>EDA-EVENT-005. What is the difference between event notification and event-carried state transfer?</strong></summary>

#### Short answer

Event notification says something changed, often with an ID. Event-carried state transfer includes enough data for consumers to act without calling back.

#### Interview answer

With notification, an event might contain only `orderId` and event metadata. Consumers call the producer if they need details. With event-carried state transfer, the event includes fields such as customer ID, status, total, and timestamps so consumers can update their own state directly.

#### Deep dive

Notification keeps payloads small but can create callback storms and runtime coupling. State transfer reduces callbacks and improves replay, but larger payloads increase schema governance and privacy concerns.

#### Production angle

For read models, analytics, and search indexing, state transfer is often useful. For sensitive or large data, notification may be safer.

#### Traps / caveats

- Too little data creates chatty consumers.
- Too much data leaks internals or PII.
- Payload design should consider replay and schema evolution.

#### Optional Anki

Q: Main trade-off of event-carried state transfer?
A: Fewer callbacks but larger, more governed payload contracts.

</details>

<a id="eda-event-006"></a>

<details>
<summary><strong>EDA-EVENT-006. What metadata should most integration events include?</strong></summary>

#### Short answer

Common metadata includes event ID, type, version, source, timestamp, correlation ID, causation ID, content type, and trace context.

#### Interview answer

The payload describes the business fact. Metadata helps route, deduplicate, trace, audit, and evolve the event. At minimum, I expect a stable event ID, event type, schema version, producer/source, occurrence time, and correlation information.

#### Deep dive

Correlation ID groups work belonging to the same user request or workflow. Causation ID points to the message or command that caused this event. Together they make asynchronous chains debuggable.

#### Production angle

Good metadata allows DLQ triage, replay, deduplication, contract checks, distributed tracing, and incident reconstruction.

#### Traps / caveats

- Producer timestamp is not a reliable global ordering source.
- Event ID should be stable across retries.
- Sensitive values should not be placed in headers just because they are metadata.

#### Optional Anki

Q: What IDs help debug event chains?
A: Correlation ID and causation ID.

</details>

<details>
<summary><strong>🧠 EDA-EVENT-007. How can CloudEvents-like envelope conventions help interoperability?</strong></summary>

#### Short answer

They standardize event metadata so tools, platforms, and teams can understand events consistently.

#### Interview answer

A CloudEvents-like envelope defines common attributes such as ID, source, type, time, subject, content type, and extension attributes. Even if a team does not adopt the exact specification, a common envelope reduces one-off formats and makes routing, tracing, cataloging, and validation easier.

#### Deep dive

The benefit is strongest across many teams or platforms. Consumers can parse metadata without knowing every producer's custom header names. Infrastructure can route or inspect events without deserializing domain payloads.

#### Production angle

Use conventions for event catalogs, audit pipelines, schema registries, observability tooling, and cross-platform integration.

#### Traps / caveats

- A standard envelope does not make a bad payload contract good.
- Teams still need semantic versioning and ownership.
- Avoid blindly exposing internal IDs or sensitive metadata.

#### Optional Anki

Q: What does a CloudEvents-like envelope standardize?
A: Common event metadata used for routing, tracing, validation, and interoperability.

</details>
