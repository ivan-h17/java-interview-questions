# Observability, lineage and operations

---

<a id="eda-obs-001"></a>

<details>
<summary><strong>EDA-OBS-001. What metrics should every event-driven flow expose?</strong></summary>

#### Short answer

Expose publish rate, consume rate, lag, processing latency, failure rate, retry count, DLQ depth, and oldest unprocessed message age.

#### Interview answer

For each critical flow, I want to know whether events are being produced, delivered, consumed, and processed successfully. Count and age metrics are both important: a small queue with very old messages can still indicate a stuck partition.

#### Deep dive

Metrics should be labeled by stable dimensions such as event type, consumer group, topic/queue, environment, and result. Avoid high-cardinality labels such as event ID or user ID.

#### Production angle

Dashboards should show end-to-end health: producer success, broker backlog, consumer lag, handler errors, DLQ growth, and downstream latency.

#### Traps / caveats

- Average lag can hide one stuck key or partition.
- Success publish metrics do not prove consumer effects happened.
- High-cardinality metrics can damage observability systems.

#### Optional Anki

Q: Key event-driven operational metrics?
A: Rate, lag, latency, errors, retries, DLQ depth, and oldest message age.

</details>

<details>
<summary><strong>EDA-OBS-002. How do queue depth, broker lag and consumer lag differ?</strong></summary>

#### Short answer

Queue depth is messages waiting, broker lag is stored delivery backlog, and consumer lag is how far a consumer is behind the latest produced event.

#### Interview answer

In a queue, depth often means ready or unacknowledged messages. In a log broker, consumer lag is commonly the difference between latest offset and committed consumer offset. Time lag measures how old unprocessed events are.

#### Deep dive

The exact terms depend on broker, but the operational question is the same: are consumers keeping up, and how old is the work they have not processed?

#### Production angle

Alert on oldest age and sustained lag growth, not only raw message count. A high-throughput topic may always have some lag.

#### Traps / caveats

- Offset lag does not always equal business delay.
- One hot partition may be hidden by aggregate lag.
- Acked messages may still have failed business side effects if handling is wrong.

#### Optional Anki

Q: Why is oldest message age useful?
A: It shows business delay even when counts are misleading.

</details>

<details>
<summary><strong>EDA-OBS-003. How should DLQ depth, retry counts and processing latency be monitored?</strong></summary>

#### Short answer

Monitor rate, total depth, oldest age, error causes, and changes after deploys.

#### Interview answer

DLQ depth should usually alert quickly for critical flows. Retry counts should be broken down by exception type and dependency. Processing latency should include handler execution time and end-to-end event age.

#### Deep dive

A sudden DLQ spike after deployment often means a code or schema bug. A slow retry increase may point to dependency degradation. Latency percentiles are more useful than averages.

#### Production angle

Dashboards should link failed event samples, consumer version, deployment timeline, and runbooks for redrive or rollback.

#### Traps / caveats

- DLQ with no owner becomes silent data loss.
- Retrying can hide user-visible delay.
- Alert fatigue appears if thresholds ignore traffic patterns.

#### Optional Anki

Q: What DLQ metric matters besides count?
A: Oldest message age and failure reason.

</details>

<a id="eda-obs-004"></a>

<details>
<summary><strong>EDA-OBS-004. How do you propagate trace context across asynchronous event boundaries?</strong></summary>

#### Short answer

Put trace context and correlation IDs into message metadata and restore them when the consumer handles the event.

#### Interview answer

The producer extracts the current trace context and writes it to headers. The consumer reads those headers and starts a linked or child span for handler execution. Correlation and causation IDs should also be logged for business-level debugging.

#### Deep dive

Async tracing is not always a simple parent-child call because processing may happen much later. Some tracing systems model this with links rather than direct child spans.

#### Production angle

Propagated context lets you follow a user action from HTTP request to event publish to downstream consumers, retries, and side effects.

#### Traps / caveats

- Thread-local MDC does not automatically cross broker boundaries.
- Missing context makes incidents much harder to reconstruct.
- Do not put sensitive data into trace headers.

#### Optional Anki

Q: How does trace context cross async boundaries?
A: Via message headers/metadata, then restored by the consumer.

</details>

<a id="eda-obs-005"></a>

<details>
<summary><strong>EDA-OBS-005. How would you debug a missing event or a missing side effect?</strong></summary>

#### Short answer

Trace the flow from producer transaction to broker delivery to consumer processing and downstream side effect.

#### Interview answer

I would check whether the business transaction committed, whether an outbox row exists, whether the relay published, whether the broker has the message, whether the consumer group received it, whether the handler failed or retried, and whether the downstream side effect was idempotently skipped or failed.

#### Deep dive

Use event ID, aggregate ID, correlation ID, outbox status, broker offset, consumer logs, DLQ entries, and target system records to reconstruct the chain.

#### Production angle

Good systems make this a standard runbook with dashboards and search queries. Bad systems require guessing across logs.

#### Traps / caveats

- Missing side effect does not always mean missing event.
- A consumer may have skipped a duplicate because of a bad idempotency key.
- A projection may lag even though event processing is healthy.

#### Optional Anki

Q: First debug split for missing side effect?
A: Determine whether publish, delivery, processing, or downstream effect failed.

</details>

<a id="eda-obs-006"></a>

<details>
<summary><strong>🧠 EDA-OBS-006. What are event lineage and high-cardinality metric traps in event-driven systems?</strong></summary>

#### Short answer

Event lineage tracks causal chains between events. High-cardinality metrics use labels with too many values and can overload monitoring systems.

#### Interview answer

Lineage answers "what caused this event and what did it cause?" using event ID, causation ID, correlation ID, and workflow state. High-cardinality traps happen when metrics label by event ID, user ID, order ID, or raw error message.

#### Deep dive

Lineage is better captured in logs, traces, or audit stores than as metric labels. Metrics should aggregate on bounded dimensions like event type, consumer, result, and error class.

#### Production angle

Lineage helps debug missing or duplicate effects. Controlled cardinality keeps observability cost and reliability under control.

#### Traps / caveats

- Metrics are not a substitute for searchable event logs.
- Raw exception labels can explode cardinality.
- Lineage data may contain sensitive identifiers and needs retention policy.

#### Optional Anki

Q: Why not label metrics by event ID?
A: It creates unbounded cardinality.

</details>
