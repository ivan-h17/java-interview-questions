<details>
<summary><strong>EDA-JAVA-001. How can a Spring service publish an event transactionally?</strong></summary>

#### Short answer

For integration events, usually write an outbox row in the same `@Transactional` method as the business change.

#### Interview answer

A Spring service can save business state and an outbox record in one database transaction. After commit, a relay publishes the outbox event. For in-process domain notifications, Spring application events or `@TransactionalEventListener` can be useful, but they are not a durable broker integration by themselves.

#### Deep dive

Publishing directly to Kafka inside a transaction does not make the database and broker one atomic unit. If reliability matters, use Outbox or another explicit consistency pattern.

#### Production angle

For order creation, persist order and outbox row together; let a monitored relay publish and retry.

#### Traps / caveats

- `@Transactional` does not cover broker publishing automatically.
- Publishing before commit can expose rolled-back state.
- Publishing after commit without Outbox has a crash window.

#### Optional Anki

Q: Reliable transactional event publishing in Spring?
A: Write an outbox row in the same database transaction, then publish asynchronously.

</details>

<details>
<summary><strong>EDA-JAVA-002. How does `@TransactionalEventListener` differ from publishing an integration event to a broker?</strong></summary>

#### Short answer

`@TransactionalEventListener` is an in-process Spring mechanism tied to transaction phases; broker publishing is inter-process durable messaging.

#### Interview answer

`@TransactionalEventListener` can run code after commit, before commit, after rollback, or after completion depending on phase. It is useful for local application behavior. Publishing to Kafka, RabbitMQ, or another broker is a separate distributed integration concern.

#### Deep dive

An after-commit listener still runs in the same application process. If the process crashes after commit but before the listener publishes externally, the event may be lost unless backed by Outbox.

#### Production angle

Use `@TransactionalEventListener` for local cleanup or internal handlers. Use Outbox for reliable integration events.

#### Traps / caveats

- It does not persist events by itself.
- Async listeners need explicit executor and context propagation.
- Exceptions after commit cannot roll back the original transaction.

#### Optional Anki

Q: Is `@TransactionalEventListener` a replacement for Outbox?
A: No, not for durable external integration.

</details>

<details>
<summary><strong>EDA-JAVA-003. What is the difference between a Spring `ApplicationEvent` and an integration event?</strong></summary>

#### Short answer

A Spring `ApplicationEvent` is usually in-process; an integration event is a cross-service contract.

#### Interview answer

`ApplicationEvent` can decouple components inside one Spring application. An integration event is serialized, versioned, published to a broker, and consumed by other services. It needs stronger contract governance and failure handling.

#### Deep dive

In-process events share memory, deployment, codebase, transaction context, and failure domain. Integration events cross process boundaries and must handle schema evolution, delivery semantics, retries, and observability.

#### Production angle

Do not expose internal Spring events directly as public event contracts without mapping and review.

#### Traps / caveats

- In-process event handlers can still create hidden coupling.
- Integration events need stable IDs and metadata.
- Application events are not automatically durable.

#### Optional Anki

Q: Spring event vs integration event?
A: In-process decoupling vs cross-service durable contract.

</details>

<details>
<summary><strong>EDA-JAVA-004. Why do acknowledgment, offset commit and deserialization strategy matter in Java consumers?</strong></summary>

#### Short answer

They determine whether failures cause message loss, duplicates, retries, or DLQ routing.

#### Interview answer

A consumer should acknowledge or commit only after the message has been safely processed or moved to a terminal path. Deserialization failures must be handled separately because the handler may never receive a valid object.

#### Deep dive

Auto-commit or auto-ack can mark work done before business processing succeeds. Manual commit gives control but requires careful transaction and error handling. Deserialization errors need error handlers, dead-letter routing, or raw-message capture depending on framework.

#### Production angle

For important events, coordinate database transaction commit and message acknowledgement so duplicates are possible but loss is avoided.

#### Traps / caveats

- Committing before processing can lose messages.
- Committing after processing can duplicate messages after crash.
- Bad deserializers can poison a consumer loop.

#### Optional Anki

Q: Safe consumer commit rule?
A: Commit after durable processing or safe terminal handling.

</details>

<details>
<summary><strong>EDA-JAVA-005. How can database constraints help implement consumer deduplication and ack/transaction consistency?</strong></summary>

#### Short answer

Unique constraints can enforce one processed record per message or business operation inside the same transaction as the state update.

#### Interview answer

The consumer inserts `(consumer_name, event_id)` into a `processed_messages` table with a unique constraint. If insert succeeds, it applies business changes and commits. If insert fails, the event was already processed and can be acknowledged safely.

#### Deep dive

This is stronger than in-memory deduplication because it survives restarts and works across instances. It also lets the database enforce correctness under concurrency.

#### Production angle

Use this for ledger entries, inventory reservations, payment events, and any handler where duplicate processing would corrupt state.

#### Traps / caveats

- The dedup insert and business update must share a transaction.
- Dedup records need retention and cleanup policy.
- Event ID must be stable and trustworthy.

#### Optional Anki

Q: Why use a unique constraint for deduplication?
A: It atomically prevents duplicate processing across restarts and instances.

</details>

<details>
<summary><strong>🧠 EDA-JAVA-006. What pitfalls appear with virtual threads, MDC propagation, blocking I/O, reactive pipelines and message listeners?</strong></summary>

#### Short answer

Concurrency tools change execution mechanics, but they do not solve ordering, idempotency, backpressure, or context propagation automatically.

#### Interview answer

Virtual threads can make blocking consumers cheaper, but database pools, broker partitions, and downstream rate limits still bound throughput. MDC and trace context are usually thread-local and must be propagated. Reactive listeners need careful error handling, backpressure, and transaction boundaries.

#### Deep dive

Mixing blocking calls into reactive pipelines can starve event loops. Spawning too much concurrency with virtual threads can overload databases. Message listener containers also have their own threading, ack, and retry semantics.

#### Production angle

Tune concurrency around downstream capacity and measure lag, handler latency, pool usage, and error rate.

#### Traps / caveats

- Virtual threads do not increase database connection pool capacity.
- MDC does not magically cross async boundaries.
- Reactive completion must align with acknowledgement.

#### Optional Anki

Q: What do virtual threads not solve for consumers?
A: Ordering, idempotency, backpressure, and downstream bottlenecks.

</details>
