# CQRS, projections and read models

---

<a id="eda-cqrs-001"></a>

<details>
<summary><strong>EDA-CQRS-001. What is CQRS?</strong></summary>

#### Short answer

CQRS separates the write model from the read model.

#### Interview answer

Command Query Responsibility Segregation means commands change state through a write model, while queries read from a model optimized for reading. The read model can be a database view, search index, cache, projection table, or denormalized document store.

#### Deep dive

CQRS does not require Event Sourcing. It can be useful whenever write-side invariants and read-side query needs differ significantly.

#### Production angle

Use CQRS for complex reads, search, dashboards, or high-read workloads where normal transactional tables are not a good API-facing shape.

#### Traps / caveats

- CQRS adds synchronization and consistency complexity.
- Not every CRUD service needs CQRS.
- Read models can lag and fail.

#### Optional Anki

Q: What does CQRS separate?
A: State-changing commands from read queries.

</details>

<a id="eda-cqrs-002"></a>

<details>
<summary><strong>EDA-CQRS-002. What is a projection or read model?</strong></summary>

#### Short answer

A projection is a derived view of data built for a specific query or use case.

#### Interview answer

A consumer can listen to order and payment events and build a `customer_order_summary` table. That table is not the source of truth; it is optimized for fast reads.

#### Deep dive

Projections often denormalize data, combine fields from multiple events, and store exactly what the UI or API needs. They should be rebuildable or repairable from source data or event history when possible.

#### Production angle

Read models need lag metrics, rebuild tooling, schema migrations, and correctness checks against source systems.

#### Traps / caveats

- Do not update projections as if they are authoritative business state.
- Rebuilds can be expensive and must avoid external side effects.
- A projection bug can affect user-visible data.

#### Optional Anki

Q: Is a projection usually the source of truth?
A: No, it is derived read state.

</details>

<a id="eda-cqrs-003"></a>

<details>
<summary><strong>EDA-CQRS-003. How does projection lag affect user experience?</strong></summary>

#### Short answer

Users may not immediately see changes in views backed by asynchronous projections.

#### Interview answer

After placing an order, the command may succeed, but the order history view may update seconds later. If the UI does not account for this, users may retry, call support, or think the operation failed.

#### Deep dive

Projection lag can come from broker backlog, consumer failure, slow downstream storage, bad deployment, or replay. The system needs a UX and operational answer for lag.

#### Production angle

Show pending states, return the created resource from the command, expose operation status, or read from the write model for immediate confirmation.

#### Traps / caveats

- Stale views can trigger duplicate user actions.
- Lag can violate business expectations if not documented.
- Monitoring average lag can hide one stuck partition.

#### Optional Anki

Q: What is projection lag?
A: Delay between source state change and read-model update.

</details>

<a id="eda-cqrs-004"></a>

<details>
<summary><strong>EDA-CQRS-004. How do you rebuild a projection and handle projection failures?</strong></summary>

#### Short answer

Rebuild from a trusted source or event history, make processing idempotent, and isolate replay from live side effects.

#### Interview answer

To rebuild, create a new projection table or index, replay historical events or reload source data, validate counts and samples, then switch reads over. Failures should be retried or quarantined with enough metadata to fix and resume.

#### Deep dive

Rebuilds need versioned projection code. Old events may require schema upcasting or default handling. Live events may be buffered, dual-written to old and new projections, or applied after a checkpoint.

#### Production angle

For critical projections, maintain runbooks for backfill, cutover, verification, rollback, and throttling so rebuilds do not overload databases or brokers.

#### Traps / caveats

- Rebuild should not resend emails or call payment APIs.
- Replaying into the current table can corrupt live state if not planned.
- Poison events should not stop the whole rebuild indefinitely.

#### Optional Anki

Q: Safe projection rebuild principle?
A: Rebuild idempotently from trusted history and avoid live side effects.

</details>

<a id="eda-cqrs-005"></a>

<details>
<summary><strong>🧠 EDA-CQRS-005. When is CQRS without Event Sourcing enough?</strong></summary>

#### Short answer

When you need separate read models but do not need event history as the source of truth.

#### Interview answer

Many systems keep normal relational write tables and publish events or run jobs to update read models. That gives query optimization and decoupling without adopting full Event Sourcing.

#### Deep dive

Event Sourcing changes how domain state is persisted. CQRS alone changes read/write model shape. If current-state persistence is enough and historical reconstruction is not a core requirement, CQRS without Event Sourcing is simpler.

#### Production angle

Use normal database tables plus projections for search pages, dashboards, reporting views, and API response optimization.

#### Traps / caveats

- CQRS still needs synchronization and lag handling.
- Without retained events, rebuild must use another trusted source.
- Avoid adopting Event Sourcing only to get denormalized reads.

#### Optional Anki

Q: Does CQRS require Event Sourcing?
A: No.

</details>
