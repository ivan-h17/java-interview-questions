# Testing and verification

---

<a id="eda-test-001"></a>

<details>
<summary><strong>EDA-TEST-001. How do you unit test an event handler?</strong></summary>

#### Short answer

Call the handler with representative events and verify state changes, emitted commands/events, and error behavior.

#### Interview answer

A unit test should isolate business logic from the broker. It should cover valid events, missing optional fields, duplicate handling decisions, invalid state transitions, and mapping from event payload to domain operation.

#### Deep dive

Keep broker-specific code thin. Put handler logic in a service that can be tested with normal inputs and fake dependencies.

#### Production angle

Unit tests should include realistic event examples from contract fixtures so schema drift is caught early.

#### Traps / caveats

- Mocking the broker does not test serialization or acknowledgements.
- Unit tests alone do not prove transactional behavior.
- Do not ignore negative cases and malformed events.

#### Optional Anki

Q: What should event-handler unit tests focus on?
A: Business behavior, mapping, idempotency, and error handling.

</details>

<a id="eda-test-002"></a>

<details>
<summary><strong>EDA-TEST-002. How do you integration test a producer-consumer flow with a broker?</strong></summary>

#### Short answer

Run the broker and real serialization locally or in CI, publish a real message, and verify durable consumer effects.

#### Interview answer

For Java services, Testcontainers is often useful for Kafka, RabbitMQ, or databases. The test should verify serialization, topic/queue configuration, listener wiring, acknowledgements, transaction boundaries, and resulting database state.

#### Deep dive

Integration tests should not try to model an entire distributed system. Pick critical paths and failure modes: publish success, consume success, duplicate delivery, deserialization failure, and retry/DLQ.

#### Production angle

Use real database constraints and broker behavior where correctness depends on them.

#### Traps / caveats

- In-memory mocks can hide broker-specific behavior.
- Tests must avoid sleeps where polling with timeouts is clearer.
- CI tests need stable ports, cleanup, and isolated topics.

#### Optional Anki

Q: Why use Testcontainers for messaging tests?
A: To test real broker and database behavior in CI.

</details>

<details>
<summary><strong>EDA-TEST-003. How do schema contract tests protect event consumers?</strong></summary>

#### Short answer

They verify that producers do not publish events consumers cannot parse or interpret.

#### Interview answer

Contract tests can check schema compatibility, required metadata, example payloads, enum values, and consumer expectations. They should run in CI before a producer schema change is deployed.

#### Deep dive

Consumer-driven contracts are useful when consumers rely on specific fields or semantics. Schema registry checks catch structural issues, while contract fixtures catch application expectations.

#### Production angle

Contract tests reduce breaking changes during independent deployments and rolling upgrades.

#### Traps / caveats

- Contracts must be owned and maintained.
- Schema compatibility does not guarantee semantic compatibility.
- Hidden consumers cannot be protected unless they are discoverable.

#### Optional Anki

Q: What do event contract tests prevent?
A: Producer changes that break consumer expectations.

</details>

<a id="eda-test-004"></a>

<details>
<summary><strong>EDA-TEST-004. How do you test idempotency, duplicates, out-of-order events, retries and DLQ behavior?</strong></summary>

#### Short answer

Inject duplicate, reordered, failing, and invalid events and verify final state, acknowledgements, retries, and DLQ records.

#### Interview answer

For idempotency, process the same event twice and assert one business effect. For out-of-order events, send later states before earlier ones and verify rules. For retries and DLQ, simulate transient and permanent failures and assert retry count, backoff path, and DLQ metadata.

#### Deep dive

These tests often need a real database because uniqueness, transactions, and locks are part of correctness.

#### Production angle

Test the exact cases that cause incidents: duplicate payment events, stale status events, poison payloads, and downstream timeouts.

#### Traps / caveats

- Testing only happy-path consumption gives false confidence.
- Time-based retry tests should be controllable.
- Verify no duplicate external side effects occurred.

#### Optional Anki

Q: How do you test idempotent handling?
A: Process the same event twice and assert one final business effect.

</details>

<a id="eda-test-005"></a>

<details>
<summary><strong>🧠 EDA-TEST-005. What would you verify in a chaos test for a critical event-driven flow?</strong></summary>

#### Short answer

Verify the system survives crashes, broker issues, dependency failures, duplicates, lag, and recovery without data loss or corrupt side effects.

#### Interview answer

I would kill consumers during processing, restart brokers or block dependencies, inject duplicate and delayed messages, slow the database, and verify that events are retried, deduplicated, monitored, and eventually processed or safely quarantined.

#### Deep dive

Chaos tests need clear invariants. For example: no payment charged twice, every committed order eventually reaches a terminal state, DLQ is alerted, and replay does not repeat side effects.

#### Production angle

Run controlled experiments in staging or production-like environments with rollback and observability ready.

#### Traps / caveats

- Chaos without invariants is just random failure.
- Do not run destructive experiments without blast-radius controls.
- Verify recovery, not only failure detection.

#### Optional Anki

Q: What makes chaos testing useful?
A: Clear invariants and verification of recovery under realistic failures.

</details>
