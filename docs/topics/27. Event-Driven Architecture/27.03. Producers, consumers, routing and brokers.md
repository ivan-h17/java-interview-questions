# Producers, consumers, routing and brokers

---

<a id="eda-route-001"></a>

<details>
<summary><strong>EDA-ROUTE-001. What are event producers, event consumers and event routers?</strong></summary>

#### Short answer

Producers create events, consumers react to them, and routers deliver events to interested consumers.

#### Interview answer

An order service may produce `OrderCreated`. Payment, inventory, analytics, and notification services may consume it. A router can be a broker, event bus, topic exchange, or managed event service that decides which consumers receive which events.

#### Deep dive

The producer should own the event contract and publish after durable state changes. Consumers own their own processing, retries, and state updates. The router provides delivery mechanics but not business correctness.

#### Production angle

Clear producer and consumer ownership helps on-call teams diagnose whether a missing side effect is a publish, routing, broker, or consumer problem.

#### Traps / caveats

- A broker is not the owner of the business contract.
- Producers should not rely on hidden consumer behavior.
- Consumers must tolerate duplicates and compatible schema changes.

#### Optional Anki

Q: What does an event consumer own?
A: Its own reaction, state updates, idempotency, and failure handling.

</details>

<a id="eda-route-002"></a>

<details>
<summary><strong>EDA-ROUTE-002. What role does a broker play in an event-driven architecture?</strong></summary>

#### Short answer

A broker durably accepts, stores, routes, and delivers messages between producers and consumers.

#### Interview answer

The broker decouples producers and consumers in time. It can buffer load, support fan-out, retain events, track offsets or acknowledgements, and provide delivery guarantees. Examples include Kafka, RabbitMQ, SQS/SNS, Pub/Sub, Pulsar, and NATS depending on model and requirements.

#### Deep dive

Different brokers optimize for different models: queues, topic exchanges, durable logs, cloud-managed events, or streaming. Choosing one depends on ordering, replay, throughput, latency, retention, and operational maturity.

#### Production angle

Broker health becomes part of application reliability. Monitor publish latency, delivery lag, storage, partitions/queues, failed deliveries, and consumer progress.

#### Traps / caveats

- A broker does not provide end-to-end exactly-once business effects.
- Managed services reduce operations but impose quotas and semantics.
- A broker outage must be designed for explicitly.

#### Optional Anki

Q: What does a broker mainly provide?
A: Durable routing and delivery between producers and consumers.

</details>

<a id="eda-route-003"></a>

<details>
<summary><strong>EDA-ROUTE-003. How do queue, publish-subscribe and append-only log messaging models differ?</strong></summary>

#### Short answer

A queue distributes work among consumers, publish-subscribe broadcasts to subscribers, and a log stores ordered records for independent consumer positions.

#### Interview answer

In a work queue, one message is usually handled by one worker in a competing group. In pub-sub, each subscriber group receives its own copy. In an append-only log like Kafka, records stay in partitions for retention, and consumers track offsets independently.

#### Deep dive

Queues are good for task distribution. Pub-sub is good for fan-out. Logs are good for replay, event streams, multiple independent consumers, and rebuilding projections. Each has different ordering and retention behavior.

#### Production angle

Choose the model from requirements: work distribution, fan-out, replay, retention, ordering, and operational cost.

#### Traps / caveats

- Using a queue as a long-term event store can fail retention needs.
- Using a log for simple work queues may be unnecessary complexity.
- Pub-sub does not remove consumer idempotency needs.

#### Optional Anki

Q: Which model is best for replaying historical events?
A: An append-only log with retention.

</details>

<a id="eda-route-004"></a>

<details>
<summary><strong>EDA-ROUTE-004. How does fan-out to multiple consumers work?</strong></summary>

#### Short answer

One published event is delivered to multiple independent consumer groups or subscriptions.

#### Interview answer

For `OrderCreated`, payment, inventory, notification, and analytics can each receive the event. Each consumer group tracks its own progress and failure handling, so one slow consumer should not block unrelated consumers.

#### Deep dive

Fan-out can happen through separate queues, topic subscriptions, Kafka consumer groups, or managed event routing rules. The key idea is that each logical consumer gets an independent delivery stream.

#### Production angle

Fan-out makes adding consumers easy, but every new consumer adds infrastructure cost, schema dependency, and operational failure modes.

#### Traps / caveats

- A slow consumer can still create broker storage pressure.
- Fan-out can amplify one event into many downstream calls.
- Producers should not need redeploys for every new consumer.

#### Optional Anki

Q: What is fan-out?
A: Delivering one event to multiple independent consumers.

</details>

<details>
<summary><strong>🧠 EDA-ROUTE-005. How do broker delivery and ordering guarantees shape application design?</strong></summary>

#### Short answer

Applications must be designed around the broker's real guarantees for duplicates, loss, ordering, replay, and acknowledgement.

#### Interview answer

If the broker provides at-least-once delivery, consumers must be idempotent. If ordering is only per partition or message group, the event key must match the entity that needs ordering. If retention is limited, replay and recovery plans must fit that window.

#### Deep dive

Broker guarantees are usually local to the broker. They do not automatically cover database writes, external API calls, emails, payments, or search-index updates. End-to-end correctness requires application-level patterns.

#### Production angle

Document assumptions such as "events for one order use orderId as key" and test them during scaling, partition changes, and deployment.

#### Traps / caveats

- Exactly-once product claims rarely mean exactly-once external side effects.
- Increasing partition count can change ordering assumptions in some systems.
- Acking before processing risks loss; acking after processing risks duplicates.

#### Optional Anki

Q: What should at-least-once delivery trigger in consumer design?
A: Idempotent processing.

</details>
