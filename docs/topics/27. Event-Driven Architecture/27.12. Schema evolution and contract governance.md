# Schema evolution and contract governance

---

<a id="eda-schema-001"></a>

<details>
<summary><strong>EDA-SCHEMA-001. How do you version event schemas safely?</strong></summary>

#### Short answer

Use backward-compatible changes first, version contracts deliberately, and test producers against known consumers.

#### Interview answer

Safe evolution usually means adding optional fields with defaults, keeping old fields during migration, and avoiding semantic changes under the same name. Breaking changes need a new version, parallel publication, or a coordinated migration.

#### Deep dive

Schema compatibility includes syntax and meaning. A field can remain the same type but change meaning, which is still a breaking change for consumers.

#### Production angle

Use schema registry rules, contract tests, event catalogs, deprecation windows, and consumer readiness checks before removing fields.

#### Traps / caveats

- Renaming a field is remove plus add.
- Required fields break older producers or consumers.
- Versioning every tiny change can create unnecessary fragmentation.

#### Optional Anki

Q: Safest common event schema change?
A: Add an optional field with a sensible default.

</details>

<details>
<summary><strong>EDA-SCHEMA-002. What are backward and forward compatibility for events?</strong></summary>

#### Short answer

Backward compatibility means new consumers can read old events. Forward compatibility means old consumers can tolerate new events.

#### Interview answer

Backward compatibility matters for replay because historical events may use older schemas. Forward compatibility matters during rolling deployments because an old consumer may receive messages from a newer producer.

#### Deep dive

Compatibility depends on serialization format and consumer behavior. JSON consumers may ignore unknown fields, but generated clients or strict validators may fail. Avro and Protobuf have their own rules around defaults and field IDs.

#### Production angle

Test compatibility against historical samples and deployed consumer versions, not only against the current schema.

#### Traps / caveats

- Unknown fields are safe only if consumers actually ignore them.
- Removing a field can break replay and old consumers.
- Compatibility does not guarantee semantic correctness.

#### Optional Anki

Q: Why does backward compatibility matter for events?
A: Consumers may replay old events.

</details>

<a id="eda-schema-003"></a>

<details>
<summary><strong>EDA-SCHEMA-003. Why is adding an optional field usually safer than adding a required field?</strong></summary>

#### Short answer

Older producers and historical events will not contain the new field.

#### Interview answer

If a new required field is added, old events become invalid and old producers cannot publish without changes. Optional fields with defaults let old and new versions coexist during deployment and replay.

#### Deep dive

In asynchronous systems, producers and consumers are rarely upgraded at exactly the same time. The schema must support mixed versions.

#### Production angle

For important fields, add them optional first, deploy consumers that can handle both states, backfill if needed, then enforce requirements later at a domain boundary.

#### Traps / caveats

- Optional does not mean meaningless; document when it may be absent.
- Null and missing can have different semantics.
- Required business invariants may belong in producer validation, not only schema.

#### Optional Anki

Q: Why avoid new required event fields?
A: Old events and old producers do not have them.

</details>

<a id="eda-schema-004"></a>

<details>
<summary><strong>EDA-SCHEMA-004. What can go wrong when renaming or removing event fields?</strong></summary>

#### Short answer

Consumers may fail, silently lose data, or misinterpret events during replay and rolling deployments.

#### Interview answer

A rename looks simple in code but appears as removing one field and adding another to consumers. Old consumers may still read the old field. Historical events still contain it. Removing it too early breaks replay and deployed consumers.

#### Deep dive

The safest path is expand-and-contract: add the new field, publish both for a while, migrate consumers, verify usage, then remove the old field after a deprecation window.

#### Production angle

Track consumer versions and schema usage before removal. Breaking one analytics or billing consumer can still be a production incident.

#### Traps / caveats

- Type-compatible changes can still be semantically breaking.
- Consumers may depend on undocumented fields.
- Schema registry checks may not catch application-level meaning changes.

#### Optional Anki

Q: What is renaming a field from compatibility view?
A: Removing the old field and adding a new one.

</details>

<a id="eda-schema-005"></a>

<details>
<summary><strong>EDA-SCHEMA-005. What is semantic compatibility, and why is it harder than syntactic compatibility?</strong></summary>

#### Short answer

Syntactic compatibility checks structure; semantic compatibility checks whether meaning stayed safe for consumers.

#### Interview answer

Changing `status` from `PAID` to `SETTLED` may be syntactically fine if it is still a string, but consumers may have business logic tied to `PAID`. Semantic compatibility requires understanding how consumers interpret values.

#### Deep dive

Schema tools can verify field names, types, defaults, and compatibility mode. They cannot fully know domain meaning, allowed transitions, currency units, timezone interpretation, or changed business rules.

#### Production angle

Use contract tests, sample events, review by consuming teams, and explicit documentation for meaning and lifecycle.

#### Traps / caveats

- Enum value changes are often semantic breaks.
- Unit changes like cents to dollars are dangerous.
- "Same JSON shape" does not mean compatible behavior.

#### Optional Anki

Q: Semantic compatibility example?
A: Same field type but changed business meaning.

</details>

<a id="eda-schema-006"></a>

<details>
<summary><strong>EDA-SCHEMA-006. What problem does a schema registry solve?</strong></summary>

#### Short answer

It stores schemas and enforces compatibility rules between producers and consumers.

#### Interview answer

A schema registry lets teams register event schemas, validate messages, and prevent incompatible producer changes from being deployed. It is common with Avro, Protobuf, JSON Schema, and Kafka ecosystems.

#### Deep dive

Registry compatibility modes can catch many structural breaks. They are most useful when integrated into CI/CD and producer startup or serialization paths.

#### Production angle

Use schema registry to prevent bad deployments, document contracts, discover event versions, and support replay of old events.

#### Traps / caveats

- It does not understand all business semantics.
- Bypassing registry validation defeats the purpose.
- Registry availability and migration need operational planning.

#### Optional Anki

Q: What does a schema registry enforce?
A: Registered schema compatibility rules.

</details>

<a id="eda-schema-007"></a>

<details>
<summary><strong>🧠 EDA-SCHEMA-007. How can an event catalog or AsyncAPI-style documentation help teams govern event contracts?</strong></summary>

#### Short answer

It makes event ownership, schema, meaning, consumers, and lifecycle visible across teams.

#### Interview answer

An event catalog documents event types, payloads, versions, owners, topics, producers, consumers, examples, compatibility rules, deprecation status, and support contacts. AsyncAPI-style specs can describe asynchronous channels and message contracts similarly to how OpenAPI documents HTTP APIs.

#### Deep dive

Governance is not only validation. Teams need discoverability and context: what event means, when it is emitted, ordering key, retention, privacy classification, and whether it is stable for external consumption.

#### Production angle

Good catalogs reduce accidental duplicate events, hidden consumers, unsafe changes, and slow incident escalation.

#### Traps / caveats

- Documentation must be generated or checked in CI where possible.
- A catalog without ownership becomes stale.
- AsyncAPI describes contracts; it does not guarantee runtime delivery.

#### Optional Anki

Q: Why use an event catalog?
A: To make event contracts discoverable, owned, and governable.

</details>
