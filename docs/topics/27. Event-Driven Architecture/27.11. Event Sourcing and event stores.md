# Event Sourcing and event stores

---

<a id="eda-es-001"></a>

<details>
<summary><strong>EDA-ES-001. What is Event Sourcing?</strong></summary>

#### Short answer

Event Sourcing stores the state of an entity as a sequence of events instead of only storing its current state.

#### Interview answer

Instead of an `orders` row with the latest status only, an event-sourced order stores events such as `OrderCreated`, `PaymentAuthorized`, `OrderApproved`, and `OrderCancelled`. Current state is reconstructed by replaying those events.

#### Deep dive

The event log is the source of truth. Projections or snapshots may exist for fast reads, but the authoritative history is the sequence of domain events.

#### Production angle

It is useful for auditability, temporal queries, debugging state transitions, and domains where history matters as much as current state.

#### Traps / caveats

- It is a different persistence model, not just "publish events".
- Queries usually need projections.
- Event design mistakes are harder to fix once history exists.

#### Optional Anki

Q: What is source of truth in Event Sourcing?
A: The append-only domain event history.

</details>

<a id="eda-es-002"></a>

<details>
<summary><strong>EDA-ES-002. How is Event Sourcing different from event-driven architecture?</strong></summary>

#### Short answer

EDA is a communication style; Event Sourcing is a persistence style.

#### Interview answer

A service can publish integration events while still storing current state in relational tables. That is event-driven but not event-sourced. In Event Sourcing, the service stores domain events as the primary record and derives current state from them.

#### Deep dive

Event Sourcing often produces events that can feed EDA, but the concepts are separate. An outbox event may be a public integration contract, while an event-sourced event may be an internal domain history record.

#### Production angle

Do not introduce Event Sourcing just because a system uses Kafka. Use it only when the persistence benefits justify operational and modeling complexity.

#### Traps / caveats

- Integration events are not always suitable as domain event history.
- Event Sourcing often requires CQRS.
- Historical events need long-term schema evolution.

#### Optional Anki

Q: EDA vs Event Sourcing?
A: EDA is communication; Event Sourcing is persistence.

</details>

<a id="eda-es-003"></a>

<details>
<summary><strong>EDA-ES-003. How is aggregate state reconstructed from events, and why are snapshots useful?</strong></summary>

#### Short answer

State is rebuilt by applying events in order. Snapshots reduce replay cost.

#### Interview answer

To load an aggregate, the system reads its events from the event store and applies each event to an empty state object. If the aggregate has thousands of events, a snapshot can store state at a known version, then replay only later events.

#### Deep dive

Events must be applied deterministically. The same event sequence should produce the same state. Snapshotting is an optimization, not a replacement for the event history.

#### Production angle

Snapshots matter for aggregates with long histories, startup performance, and command latency. They need versioning and compatibility with event changes.

#### Traps / caveats

- Applying events should not call external systems.
- Snapshots can become stale or incompatible.
- Event order per aggregate is critical.

#### Optional Anki

Q: Why use snapshots in Event Sourcing?
A: To avoid replaying the full event history every time.

</details>

<a id="eda-es-004"></a>

<details>
<summary><strong>EDA-ES-004. When should Event Sourcing be avoided?</strong></summary>

#### Short answer

Avoid it when current-state persistence is enough and the team does not need full event history as the source of truth.

#### Interview answer

For simple CRUD, ordinary relational tables plus audit logs or outbox events are usually simpler. Event Sourcing adds event modeling, versioning, projections, upcasting, replay, and operational complexity.

#### Deep dive

It is a strong fit for domains with important state transitions, audit requirements, temporal queries, or complex workflows. It is a poor default for every entity in a system.

#### Production angle

Before choosing Event Sourcing, confirm how you will query, migrate, delete or anonymize data, rebuild projections, and train developers.

#### Traps / caveats

- "We want Kafka" is not a reason for Event Sourcing.
- Debugging can become harder if events are poorly modeled.
- GDPR/privacy requirements can conflict with immutable histories.

#### Optional Anki

Q: When is Event Sourcing overkill?
A: Simple CRUD with no need for event history as source of truth.

</details>

<details>
<summary><strong>🧠 EDA-ES-005. How should event upcasting and corrections be handled without rewriting immutable history?</strong></summary>

#### Short answer

Use upcasters to read old event versions into the current model, and publish corrective events for business corrections.

#### Interview answer

When an old event schema changes, an upcaster can transform the old representation at read time. If a past business fact was wrong, do not silently edit history. Add a correction event, reversal, or adjustment that records what changed and why.

#### Deep dive

Technical migration and business correction are different. Upcasting handles schema evolution. Corrective events preserve auditability and explain how state moved from wrong to right.

#### Production angle

Version event schemas, test historical replay, and keep correction workflows visible to support and audit teams.

#### Traps / caveats

- Rewriting history can break audit and projections.
- Upcasters must be tested on real old events.
- Correction events need clear semantics, not vague "data fixed" payloads.

#### Optional Anki

Q: How do you correct event-sourced history?
A: Add corrective events rather than silently rewriting old facts.

</details>
