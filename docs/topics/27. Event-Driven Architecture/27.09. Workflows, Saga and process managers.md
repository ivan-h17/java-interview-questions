# Workflows, Saga and process managers

---

<a id="eda-saga-001"></a>

<details>
<summary><strong>EDA-SAGA-001. What is the Saga pattern?</strong></summary>

#### Short answer

A Saga coordinates a business workflow across multiple local transactions.

#### Interview answer

Instead of one distributed ACID transaction across services, each service performs its own local transaction and publishes a result. If a later step fails, compensating actions are used to semantically undo or adjust earlier steps.

#### Deep dive

A Saga is useful when one business operation spans services with separate databases, such as order creation, payment authorization, inventory reservation, and shipping request.

#### Production angle

Saga state, timeouts, retries, idempotency, compensation, and monitoring are critical. Without them, workflows get stuck or silently inconsistent.

#### Traps / caveats

- Saga is not a database rollback.
- Compensation can fail and needs handling.
- Users may see intermediate states.

#### Optional Anki

Q: What does a Saga replace?
A: A distributed transaction across multiple service-owned databases.

</details>

<a id="eda-saga-002"></a>

<details>
<summary><strong>EDA-SAGA-002. How do choreography and orchestration differ in Saga workflows?</strong></summary>

#### Short answer

Choreography uses events between participants; orchestration uses a central coordinator that commands each step.

#### Interview answer

In choreography, the order service publishes `OrderCreated`, payment reacts and publishes `PaymentAuthorized`, inventory reacts, and so on. In orchestration, a Saga orchestrator explicitly tells payment and inventory what to do and records the workflow state.

#### Deep dive

Choreography is decentralized and can be simple for small flows. Orchestration is clearer for complex workflows because state, timeouts, and decisions are explicit in one place.

#### Production angle

For a two-step flow, choreography may be enough. For multi-step payment, inventory, fraud, shipment, and compensation logic, orchestration is usually easier to debug.

#### Traps / caveats

- Choreography can create cyclic event dependencies.
- Orchestrators can become too central if they own domain logic.
- Both require idempotent participants.

#### Optional Anki

Q: Choreography vs orchestration?
A: Choreography reacts through events; orchestration uses an explicit coordinator.

</details>

<a id="eda-saga-003"></a>

<details>
<summary><strong>EDA-SAGA-003. What is a compensating action, and how is it different from rollback?</strong></summary>

#### Short answer

A compensating action is a new business operation that counteracts a previous completed step; rollback undoes uncommitted work inside one transaction.

#### Interview answer

If payment was authorized but inventory reservation fails, the compensation may release or void the authorization. The original payment transaction already committed, so this is not a database rollback.

#### Deep dive

Compensation must follow business rules. Some actions cannot be fully undone, such as sending an email or shipping a package. The system may need refunds, adjustment records, or manual review instead.

#### Production angle

Compensations need idempotency, auditability, retries, and alerting just like forward steps.

#### Traps / caveats

- Compensation is not always symmetrical.
- Compensation can fail.
- Legal and financial systems often require reversal records, not deletion.

#### Optional Anki

Q: Why is compensation not rollback?
A: It is a separate committed business action after earlier work already committed.

</details>

<a id="eda-saga-004"></a>

<details>
<summary><strong>EDA-SAGA-004. What is a Process Manager pattern?</strong></summary>

#### Short answer

A Process Manager tracks a long-running workflow and decides what step should happen next.

#### Interview answer

It listens to events, stores workflow state, sends commands, handles timeouts, and triggers compensation. It is useful when the workflow logic is more complex than simple event chaining.

#### Deep dive

Unlike a simple event handler, a process manager has memory. It knows that payment succeeded, inventory is pending, fraud check timed out, and shipment must wait.

#### Production angle

Process managers make stuck workflow debugging easier because each instance has explicit state and history.

#### Traps / caveats

- Do not put all domain rules into a generic workflow layer.
- Process manager state must be durable.
- Commands sent by the process manager must be idempotent.

#### Optional Anki

Q: Why use a Process Manager?
A: To make long-running workflow state and decisions explicit.

</details>

<a id="eda-saga-005"></a>

<details>
<summary><strong>EDA-SAGA-005. How do Saga timeouts, duplicate execution and explicit Saga state affect correctness?</strong></summary>

#### Short answer

Timeouts handle missing responses, idempotency handles duplicate messages, and explicit state prevents ambiguous workflow progress.

#### Interview answer

A Saga cannot assume every participant responds. It needs timeout rules such as cancel, retry, compensate, or manual review. Duplicate events or commands should not execute a step twice. Explicit Saga state records which steps have completed and what can happen next.

#### Deep dive

Without durable state, a workflow can lose track after restart. Without idempotent steps, retries can double-charge or double-reserve. Without timeouts, workflows remain stuck forever.

#### Production angle

Monitor counts and age of Sagas by state. Alert on stuck states, repeated compensation failures, and high timeout rates.

#### Traps / caveats

- Timeout does not prove failure; the remote action may still complete later.
- Duplicate Saga starts need command-level idempotency.
- Manual intervention paths should be designed before incidents.

#### Optional Anki

Q: Why store Saga state?
A: To make progress, retries, timeouts, and compensation durable and debuggable.

</details>

<a id="eda-saga-006"></a>

<details>
<summary><strong>🧠 EDA-SAGA-006. When would you use a workflow engine instead of broker choreography?</strong></summary>

#### Short answer

Use a workflow engine when workflows are long-running, complex, stateful, timeout-heavy, or need strong operational tooling.

#### Interview answer

Plain broker choreography works for simple flows. A workflow engine is useful when there are many steps, human tasks, timers, retries, compensation, visibility requirements, or frequent business-process changes.

#### Deep dive

Engines such as Temporal or BPMN-style platforms can persist workflow state, manage timers, retry activities, and provide operational views. The trade-off is adopting another platform and programming model.

#### Production angle

Consider a workflow engine for onboarding, payment settlement, fulfillment, or approval flows where stuck instances must be visible and recoverable.

#### Traps / caveats

- A workflow engine does not remove idempotency requirements.
- Engine outages and versioning need operational planning.
- Avoid using workflow orchestration for trivial asynchronous side effects.

#### Optional Anki

Q: When is broker choreography not enough?
A: When workflow state, timers, compensation, and operations become complex.

</details>
