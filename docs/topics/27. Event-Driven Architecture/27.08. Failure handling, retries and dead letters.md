# Failure handling, retries and dead letters

---

<a id="eda-fail-001"></a>

<details>
<summary><strong>EDA-FAIL-001. What is a poison message?</strong></summary>

#### Short answer

A poison message is a message that repeatedly fails processing and blocks or degrades the consumer.

#### Interview answer

It may contain invalid data, an unsupported schema version, a business state the consumer cannot handle, or data that triggers a bug. If retried forever, it can block ordered processing and waste resources.

#### Deep dive

Poison messages should be distinguished from transient failures. A database timeout may succeed later. A malformed payload will probably fail every time until code, data, or the message is fixed.

#### Production angle

Consumers need retry limits, classification, DLQ/quarantine, alerts, and safe reprocessing tools.

#### Traps / caveats

- Infinite retries can stop progress.
- Skipping without audit can lose business facts.
- One poison event can block a whole ordered partition.

#### Optional Anki

Q: What is a poison message?
A: A message that repeatedly fails and cannot be processed normally.

</details>

<a id="eda-fail-002"></a>

<details>
<summary><strong>EDA-FAIL-002. How should retry policies be designed for event consumers?</strong></summary>

#### Short answer

Retries should be bounded, classified by error type, delayed with backoff, observable, and safe for idempotent processing.

#### Interview answer

Transient failures like timeouts may be retried. Permanent failures like invalid schema should go to DLQ or quarantine. The policy should define max attempts, delay, jitter, error metadata, alerting, and what happens after retries are exhausted.

#### Deep dive

Retrying inside the listener can block partitions. Delayed retry topics, scheduled queues, or external retry state may be better depending on broker and ordering requirements.

#### Production angle

Retry metrics should include attempts, age, error type, consumer version, and final destination.

#### Traps / caveats

- Retrying non-idempotent handlers can duplicate side effects.
- Retrying permanent failures wastes capacity.
- Long blocking retries can cause consumer rebalances or lease expirations.

#### Optional Anki

Q: What should a retry policy include?
A: Classification, max attempts, backoff, jitter, observability, and a terminal path.

</details>

<a id="eda-fail-003"></a>

<details>
<summary><strong>EDA-FAIL-003. Why should retries usually use exponential backoff and jitter?</strong></summary>

#### Short answer

Backoff reduces pressure on failing dependencies, and jitter prevents many consumers from retrying at the same time.

#### Interview answer

If a database or API is down, immediate retries can amplify the outage. Exponential backoff spaces retries increasingly. Jitter randomizes retry timing so thousands of consumers do not synchronize and create retry storms.

#### Deep dive

Retries are useful only when the failure may recover. They should respect timeout budgets, downstream rate limits, and consumer lag. Sometimes circuit breaking or pausing consumption is better.

#### Production angle

Retry storms can turn a small dependency incident into broker lag, thread pool exhaustion, and database overload.

#### Traps / caveats

- Backoff without a max delay can hide stuck messages for too long.
- Jitter does not make unsafe operations safe to retry.
- Retry settings need monitoring and tuning.

#### Optional Anki

Q: Why add jitter to retries?
A: To avoid synchronized retry spikes.

</details>

<a id="eda-fail-004"></a>

<details>
<summary><strong>EDA-FAIL-004. What is a Dead Letter Queue, and what metadata should be kept with a DLQ message?</strong></summary>

#### Short answer

A DLQ stores messages that could not be processed after normal retry handling.

#### Interview answer

The DLQ preserves failed messages for inspection, repair, and reprocessing. It should include original payload, headers, event ID, source topic/queue, partition/offset if relevant, failure reason, stack or error code, attempt count, timestamps, and consumer version.

#### Deep dive

A DLQ is not a trash can. It is an operational workflow. Teams need ownership, alerts, dashboards, retention, and tooling to redrive safely.

#### Production angle

DLQ growth after deployment often points to schema incompatibility, code bugs, downstream outage, bad data, or changed assumptions.

#### Traps / caveats

- Moving to DLQ can violate strict ordering.
- Redriving without a fix repeats the failure.
- DLQ retention should match audit and recovery needs.

#### Optional Anki

Q: What is DLQ for?
A: Preserving failed messages for diagnosis and safe reprocessing.

</details>

<a id="eda-fail-005"></a>

<details>
<summary><strong>EDA-FAIL-005. How do you reprocess failed events safely?</strong></summary>

#### Short answer

Fix the root cause, reprocess with idempotency, preserve audit trail, and control rate and ordering impact.

#### Interview answer

I would inspect why the event failed, deploy a fix or repair data, then redrive a small batch first. The handler must be idempotent, external side effects must be guarded, and metrics should confirm success before bulk reprocessing.

#### Deep dive

Reprocessing can corrupt current state if old events are applied blindly. Consumers may need version checks, replay mode, side-effect suppression, or a separate rebuild pipeline.

#### Production angle

Use runbooks and tooling rather than manual ad hoc scripts for critical flows like payment, inventory, and customer data.

#### Traps / caveats

- Do not redrive into live side effects without safeguards.
- Respect ordering if the stream depends on it.
- Keep the original failure metadata for audit.

#### Optional Anki

Q: First step before DLQ redrive?
A: Understand and fix the failure cause.

</details>

<a id="eda-fail-006"></a>

<details>
<summary><strong>EDA-FAIL-006. How should a consumer behave when its downstream dependency is down?</strong></summary>

#### Short answer

It should fail safely, retry with backoff, avoid overload, and expose lag or failure state.

#### Interview answer

If the consumer cannot complete its work because a database or API is down, it should not acknowledge successful processing. It can pause consumption, retry later, send messages to delayed retry, or move permanent failures to DLQ depending on the failure.

#### Deep dive

Continuing to consume without processing can lose work if acknowledgements are wrong. Aggressive retries can overload the dependency. The right behavior depends on idempotency, ordering, and business urgency.

#### Production angle

During outages, operators need controls to pause consumers, scale down, adjust retry rate, and drain backlog after recovery.

#### Traps / caveats

- Acking before durable processing can lose messages.
- Holding messages forever can block partitions.
- Circuit breakers should not silently drop business events.

#### Optional Anki

Q: Should a consumer ack when downstream processing failed?
A: Usually no, unless the message is deliberately moved to a safe terminal path.

</details>

<a id="eda-fail-007"></a>

<details>
<summary><strong>🧠 EDA-FAIL-007. When should you skip, quarantine, pause or stop an event stream?</strong></summary>

#### Short answer

Skip only when safe and audited, quarantine bad messages, pause for recoverable dependency failures, and stop when continued processing risks corruption.

#### Interview answer

For malformed or unsupported messages, quarantine or DLQ is better than infinite retry. For downstream outages, pause or delayed retry may be better. If a bug is corrupting money, inventory, or customer data, stop processing until the fix and repair plan are clear.

#### Deep dive

The decision depends on ordering, business criticality, replayability, side effects, and whether later events depend on the failed one. A strict ordered stream may require pausing rather than skipping.

#### Production angle

Runbooks should define who can pause, redrive, skip, or quarantine, and what audit record is required.

#### Traps / caveats

- Skipping can create hidden data gaps.
- Pausing can create large backlogs and missed SLAs.
- Stopping is safer than corrupting critical state.

#### Optional Anki

Q: When should you stop a stream?
A: When continued processing risks corrupting critical state.

</details>
