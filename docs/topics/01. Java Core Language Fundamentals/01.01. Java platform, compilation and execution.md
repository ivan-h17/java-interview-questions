<details>
<summary><strong>JCORE-PLAT-001. What is the difference between JVM, JRE and JDK?</strong></summary>

#### Short answer

The **JVM** executes Java bytecode. The **JRE** is a runtime environment: JVM plus standard libraries and runtime files needed to run Java applications. The **JDK** is the developer kit: runtime plus tools such as `javac`, `jar`, `jlink` and diagnostic utilities.

#### Interview answer

A good way to explain it is: JVM is the engine, JRE is what a machine needs to run a Java app, and JDK is what a developer or build system needs to build and inspect one.

The JVM is both a specification and an implementation family, for example HotSpot. It loads classes, verifies bytecode, manages memory, runs the interpreter and JIT compiler, and must preserve Java Memory Model semantics during execution and optimization. The JRE historically packaged the JVM and class library for running apps. The JDK adds development tools: compiler, archiver, documentation tools, module tools and troubleshooting tools. In modern Java deployments teams often install a full JDK or build a trimmed runtime image, so the conceptual distinction matters more than assuming a separate “JRE installer”.

#### Deep dive

The JVM runs `.class` files, not `.java` source files. It performs class loading, bytecode verification, linking, initialization, interpretation, JIT compilation, garbage collection and native interop through mechanisms such as JNI.

The JRE includes the runtime libraries and launcher needed to execute applications. The JDK includes the JRE-like runtime plus tools: `javac` for compilation, `jar` for archives, `javadoc`, `jdeps`, `jlink`, `jcmd`, `jstack`, `jmap` and others depending on the distribution.

Different vendors can provide compatible JDK builds. Compatibility still depends on the Java version, class-file version, available APIs and vendor-specific packaging choices.

#### Production angle

For backend services, compile and test with an explicit JDK version, then run on a compatible runtime. A common production issue is compiling with a newer JDK and running on an older runtime, which can fail with `UnsupportedClassVersionError`.

Small container images are useful, but removing the full JDK also removes diagnostic tools. Many teams use a slim runtime for normal execution and keep a debug image or sidecar workflow with JDK tools for incidents.

#### Traps / caveats

- JRE is not the same thing as JVM; it contains a JVM plus runtime libraries.
- JDK is not only `javac`; it also contains launchers, packaging, module and diagnostic tools.
- Do not assume a separate JRE installation exists in modern deployments; custom runtime images and full JDK images are common.
- Vendor and version differences can matter for GC defaults, container behavior, crypto providers and diagnostics.

#### Optional Anki

Q: JVM vs JRE vs JDK?
A: JVM executes bytecode; JRE is JVM plus runtime libraries for running apps; JDK is runtime plus development and diagnostic tools.

Q: Why might a production image include a JDK?
A: For tools such as jcmd, jstack, jmap, jdeps or emergency diagnostics, even if the app only needs a runtime to execute.

<details>
<summary><strong>JCORE-PLAT-002. How does Java source code become a running program?</strong></summary>

#### Short answer

Java source code is compiled by `javac` from `.java` files into `.class` bytecode. The classes are often packaged into a JAR. The `java` launcher starts a JVM, class loaders load classes, the JVM verifies and links them, initializes the main class, and executes bytecode using interpretation and JIT compilation.

#### Interview answer

The lifecycle is: source code → compilation → class files → packaging → JVM startup → class loading/linking/initialization → execution.

In practice a build tool such as Maven or Gradle calls `javac`, annotation processors may generate additional source or metadata, and dependencies are resolved on the compile classpath or module path. The output is bytecode in `.class` files, commonly packaged into a JAR. At launch, the JVM locates the main class or executable JAR manifest, loads classes lazily as they are referenced, verifies bytecode safety, resolves symbolic references, runs static initialization, and calls `public static void main(String[] args)` or a framework bootstrap.

#### Deep dive

`javac` parses source code, performs semantic checks, type checks, constant folding and desugaring, then emits class files. Desugaring means some high-level constructs are represented through lower-level bytecode patterns; for example enhanced loops, lambdas and switch features have bytecode-level translations.

At runtime the JVM does not load every class immediately. Class loading is demand-driven. The lifecycle of a class includes loading, verification, preparation, optional resolution and initialization. Resolution can be lazy, so linkage problems may appear only when a code path is executed.

Execution usually starts with interpreted bytecode. Hot code can later be compiled to native machine code by the JIT compiler. If the JVM made an optimization assumption that becomes invalid, it can deoptimize back to safer code.

#### Production angle

Most production failures in this area are not syntax errors; they are packaging, classpath, module path or version problems. Examples: wrong main class in the manifest, missing dependency, incompatible transitive dependency, different runtime classpath from test classpath, or class files compiled for a newer Java version.

A practical backend answer should mention reproducible builds, locked dependency versions, CI tests using the same packaged artifact, explicit `--release` target when needed, and smoke tests for the exact container image that will be deployed.

#### Traps / caveats

- Java is both compiled and executed by a runtime; `javac` compilation and JIT compilation are different stages.
- Compilation does not automatically bundle all dependencies into your application JAR.
- Class loading is lazy, so a missing class can stay hidden until a specific endpoint or job runs.
- With `java -jar`, the launcher ignores a separate `-cp`; dependencies must come from the JAR layout, manifest `Class-Path` or framework launcher.
- Static initialization can fail before application code appears to start.

#### Optional Anki

Q: What are the major stages from Java source to execution?
A: Compile .java to .class, package, launch JVM, load/link/initialize classes, execute via interpreter and JIT.

Q: Why can a Java app compile but fail only in production?
A: Runtime classpath, Java version, packaging, config or dependency versions can differ from compile/test time.

</details>

<details>
<summary><strong>JCORE-PLAT-003. What is Java bytecode, and why does it matter?</strong></summary>

#### Short answer

Java bytecode is the platform-neutral instruction format stored in `.class` files. It matters because it is the contract between compilers and the JVM: the JVM can verify it, load it dynamically, interpret it, JIT-compile it to native code, and run bytecode produced by Java and other JVM languages.

#### Interview answer

Bytecode is not source code and not CPU machine code. It is an intermediate representation defined by the JVM specification. A `.class` file contains bytecode for methods plus metadata such as the constant pool, fields, methods, descriptors, attributes and class-file version.

It matters for portability and tooling. Java, Kotlin, Scala and other JVM languages can compile to bytecode. The JVM can verify bytecode before execution, which supports type safety and memory-safety rules at the bytecode level. Tools can inspect or transform bytecode for coverage, profiling, proxies and instrumentation.

#### Deep dive

The JVM bytecode model is stack-based: instructions operate on an operand stack and local variables. For example, bytecode can load a value, call a method, branch, create an object, access a field or throw an exception.

Bytecode keeps symbolic references that are resolved by the JVM at runtime. It also contains metadata used by reflection, debuggers and frameworks. Some source-level information is not preserved in the same form; for example generic type parameters are mostly erased and represented through signatures and compiler-inserted casts.

Modern JVM features such as lambdas rely heavily on bytecode mechanisms like `invokedynamic`, which lets the runtime link call sites dynamically.

#### Production angle

Bytecode matters in production when debugging class version errors, dependency conflicts, framework proxies or Java agents. Tools such as `javap`, `jdeps`, profilers and coverage agents work at this level.

Bytecode instrumentation can change startup time, stack traces, method shapes and sometimes performance. This is normal for agents like coverage, tracing or APM, but it should be considered when comparing test and production behavior.

#### Traps / caveats

- Bytecode is portable, but not every bytecode version runs on every Java runtime.
- The JVM may execute bytecode by interpreting it or by compiling hot parts to native code.
- Do not expect all source-level constructs to exist directly in bytecode; many are desugared or erased.
- Framework-generated bytecode can make stack traces and equality/proxy behavior less obvious.

#### Optional Anki

Q: What is bytecode?
A: A JVM instruction format stored in .class files; intermediate between source code and native machine code.

Q: Why does bytecode matter?
A: It enables portability, verification, dynamic loading, JIT compilation and tooling/instrumentation.

</details>

<details>
<summary><strong>JCORE-PLAT-004. Why is Java called platform-independent?</strong></summary>

#### Short answer

Java is called platform-independent because compiled Java bytecode can run on any compatible JVM, regardless of the underlying operating system or CPU architecture. The JVM and standard library provide the platform-specific implementation details.

#### Interview answer

The phrase usually means “compile once, run on any compatible JVM”. Source code is compiled to bytecode, and each platform has its own JVM implementation that translates that bytecode into actual execution on the local OS and CPU.

This is different from languages that normally compile directly into a platform-specific executable. In Java the binary artifact is usually a JAR with class files, and the target platform provides the JVM.

#### Deep dive

The JVM abstracts many low-level details: instruction set, memory management, object layout, threads, file and socket APIs, and exception handling. The class-file format defines a stable intermediate representation, so a class compiled on macOS can run on Linux or Windows if the runtime is compatible.

However, platform independence is not absolute. Java programs can depend on native libraries, OS commands, filesystem case sensitivity, path conventions, configured or older-runtime default charset behavior, default locale, default time zone, available fonts, crypto providers, container limits and environment variables.

Java version compatibility also matters. Bytecode compiled for a newer class-file version will not run on an older JVM.

#### Production angle

For backend services, portability works best when the app avoids platform defaults and native assumptions. Use `Path` APIs instead of string-concatenated paths, set encoding/time zone/locale intentionally when they affect behavior, package native dependencies per OS and architecture, and test the exact container base image.

Containers make the runtime environment more repeatable, but they do not remove Java version, CPU architecture, libc, file system or kernel-level differences.

#### Traps / caveats

- Platform-independent does not mean environment-independent.
- A compatible JVM is required; bytecode is not executed directly by the operating system.
- Native libraries via JNI/JNA must match OS and CPU architecture.
- Locale, time zone and configured or older-runtime charset defaults can change behavior across machines.
- Java version mismatch can break startup even if the OS is supported.

#### Optional Anki

Q: Why is Java platform-independent?
A: Because .class bytecode runs on any compatible JVM, and the JVM maps it to the local OS/CPU.

Q: What breaks Java portability?
A: Java version mismatch, native libraries, OS-specific commands, filesystem assumptions, locale/time zone and configured runtime defaults.

</details>

<details>
<summary><strong>JCORE-PLAT-005. What is the difference between compile time and runtime in Java?</strong></summary>

#### Short answer

**Compile time** is when source code is translated and checked by the compiler. **Runtime** is when the JVM executes the program. Compile-time problems include syntax, type and missing-symbol errors; runtime problems include nulls, bad casts, class loading, configuration, dependency and external-system failures.

#### Interview answer

Compile time answers the question “can this source code be compiled against the declared APIs?” Runtime answers “what actually happens when this packaged application runs with real classes, data, config and environment?”

Java has strong static typing, so many mistakes are caught at compile time: invalid syntax, incompatible types, inaccessible members, missing imports, unhandled checked exceptions and missing symbols on the compile classpath. But Java also has dynamic class loading, reflection, proxies, dependency resolution and external configuration, so many failures appear only at runtime.

#### Deep dive

`javac` compiles against a compile classpath or module path. The running application uses a runtime classpath or module path, which may differ. That gap explains classic linkage errors: code compiled against one library version can run with another and fail with `NoSuchMethodError`, `NoClassDefFoundError` or similar errors.

Generics are another good example. The compiler checks generic types, but most generic information is erased in bytecode. Some casts are inserted by the compiler and can still fail at runtime if raw types or unchecked operations polluted the data.

Annotation processing is mostly compile-time; reflection, dependency injection and proxy generation are runtime mechanisms unless a framework explicitly moves work to build time.

#### Production angle

“It compiles” is not a production guarantee. CI should test the packaged artifact with the same dependency graph and Java runtime that production will use. Dependency locking, build scans, dependency convergence checks and container-level smoke tests reduce runtime surprises.

Runtime failures are often caused by environment: missing secrets, invalid config, wrong database schema, different classpath, insufficient permissions, missing native library, memory limits or incompatible Java version.

#### Traps / caveats

- A compile-time type check does not prove runtime data is valid.
- Warnings, unchecked casts and raw types can become runtime `ClassCastException`s.
- Reflection and framework wiring can hide errors until startup or first request.
- Compile classpath and runtime classpath can differ.
- Checked exceptions are compile-time rules for declared calls; failures can still cross async, framework or reflection boundaries differently.

#### Optional Anki

Q: Compile time vs runtime?
A: Compile time checks and generates bytecode; runtime executes the packaged app with real classes, config, data and environment.

Q: Why can NoSuchMethodError happen at runtime?
A: The code compiled against an API version where the method existed, but runtime loaded a different incompatible version.

</details>

<details>
<summary><strong>JCORE-PLAT-006. What is the difference between javac, java and jar?</strong></summary>

#### Short answer

`javac` compiles Java source files into `.class` bytecode. `java` launches a JVM and runs a class, JAR or module. `jar` creates, reads and updates JAR archives; it packages class files and resources but does not compile or execute the application by itself.

#### Interview answer

The three commands map to three different concerns: compile, run and package.

`javac` is used during the build. It needs source files and compile dependencies and produces class files. `java` is used during execution. It starts the JVM, accepts JVM options, loads the main class or executable JAR, and passes application arguments to `main`. `jar` is an archive tool based on ZIP format with Java-specific conventions such as `META-INF/MANIFEST.MF`.

#### Deep dive

Typical minimal flow:

```
javac -d out src/com/acme/App.java
java -cp out com.acme.App
jar --create --file app.jar -C out .
```

`javac` options control output directory, classpath/module path, annotation processing, debug information and target release. `java` options control classpath/module path, main class or `-jar`, heap size, system properties, GC, agents and diagnostic flags. `jar` can create executable JARs by adding a manifest with `Main-Class`, can package resources, service provider files and multi-release classes.

Build tools usually hide these commands, but understanding them helps debug broken builds and deployments.

#### Production angle

In production the important details are packaging and launch command correctness. A thin JAR requires dependencies to be present on the runtime classpath. A fat/uber JAR bundles dependencies but can create resource merging, duplicate class or shading issues. An executable JAR needs a correct manifest or framework-specific launcher layout.

Command-line order matters. JVM options such as `-Xmx`, `-D...` or `-javaagent` must be passed to the `java` launcher before the main class or `-jar`; arguments after the main class are application arguments.

#### Traps / caveats

- `jar` does not compile Java source code.
- `javac` does not automatically include third-party dependencies inside your output JAR.
- A JAR can be valid but not executable if it has no `Main-Class` or launcher metadata.
- With `java -jar`, the launcher ignores a separate `-cp`; dependencies must come from the JAR layout, manifest `Class-Path` or framework launcher.
- JVM options placed after the main class are not JVM options anymore; they are passed to the application.

#### Optional Anki

Q: What do javac, java and jar do?
A: javac compiles, java launches/runs, jar packages archives.

Q: Why can a JAR fail to run?
A: It may miss Main-Class metadata, dependencies, a compatible runtime, or the launch command may use the wrong classpath/options.

</details>

<details>
<summary><strong>JCORE-PLAT-007. What is JIT compilation at a high level?</strong></summary>

#### Short answer

JIT, or just-in-time compilation, is runtime compilation performed by the JVM. The JVM starts by interpreting bytecode, observes which methods and loops are hot, then compiles those hot parts into optimized native machine code for the current CPU.

#### Interview answer

JIT is why Java can be portable and still fast. `javac` produces portable bytecode ahead of time, and the JVM compiles frequently executed bytecode to native code at runtime.

The key idea is profiling. The JVM knows actual runtime types, branch frequencies and call patterns, so it can inline methods, remove unnecessary checks, optimize virtual calls, eliminate some allocations and specialize code for what really happens. If an assumption becomes invalid, the JVM can deoptimize and recompile differently.

#### Deep dive

HotSpot commonly uses tiered compilation: simple compilation and profiling first, then more expensive optimization for very hot code. Important concepts include method counters, loop counters, inlining, escape analysis, on-stack replacement, safepoints, deoptimization and the code cache.

JIT compilation is not the same as source compilation. It works from bytecode to native instructions while the program is running. This has a warm-up cost but gives the runtime information that an ahead-of-time compiler might not have.

JIT also interacts with GC and the memory model. For example, optimizations must preserve Java semantics, including visibility rules and exception behavior.

#### Production angle

JIT affects production behavior through warm-up, latency and benchmarking. The first requests after startup can be slower while classes load, profiles collect and hot code is compiled. Microbenchmarks without warm-up are often misleading; JMH exists largely to handle JVM benchmarking correctly.

Usually you should not tune JIT first. Start with algorithmic improvements, allocation reduction, database and network latency, GC logs and profiler data. JIT flags are powerful but can make behavior harder to reason about. For short-lived workloads or very fast startup requirements, teams may compare normal JIT-based JVM execution with AOT/native-image approaches.

#### Traps / caveats

- JIT compiles bytecode to native code at runtime; it does not compile `.java` source to `.class` files.
- Warm-up matters: the first run and steady-state performance can differ significantly.
- Microbenchmarks are easy to get wrong because the JIT may eliminate dead code or optimize unrealistic patterns.
- More JIT tuning is not automatically better; wrong flags can hurt startup, memory or latency.
- Optimized native code can be deoptimized if runtime assumptions change.

#### Optional Anki

Q: What is JIT compilation?
A: Runtime compilation of hot bytecode into optimized native machine code by the JVM.

Q: Why does Java warm-up matter?
A: The JVM needs time to load classes, collect profiles and JIT-compile hot methods before steady-state performance.

</details>

<details>
<summary><strong>JCORE-PLAT-008. What is the difference between `javac --source`, `--target` and `--release`?</strong></summary>

#### Short answer

`-source` controls accepted Java language syntax. `-target` controls the emitted class-file version. `--release` controls both and also restricts the visible standard-library APIs to the selected Java release.

#### Interview answer

The important production distinction is API compatibility. Compiling with `-source 17 -target 17` on a newer JDK may still accidentally use JDK APIs that did not exist in Java 17, unless the build also uses a matching boot classpath. `--release 17` prevents that by compiling against the public APIs for that release.

For modern builds, prefer `--release` when you need to produce bytecode for an older Java runtime. Use toolchains in Maven or Gradle so the compiler version is explicit and reproducible.

#### Deep dive

Class-file version controls whether an older JVM can load the class. API availability controls whether the code can actually run. `--release` handles both for platform APIs. It does not make third-party dependencies compatible; those dependencies must also support the target runtime.

This matters for libraries that support multiple Java versions. They may compile main code for an older release while using newer JDKs in tests or build plugins. Multi-release JARs are another mechanism, but they add packaging and test complexity.

#### Production angle

A common failure is shipping class files compiled for a newer runtime and getting `UnsupportedClassVersionError`. A subtler failure is compiling to an older class-file version but calling a newer JDK method, then failing with linkage errors on the older runtime. CI should test on the oldest supported runtime.

#### Traps / caveats

- `-target` alone does not guarantee API compatibility with the target Java version.
- `--release` covers JDK platform APIs, not third-party library compatibility.
- Build plugins and test code may run on a different JDK from the application runtime.
- Multi-release JARs can help libraries but require careful testing for every supported runtime.
- Use CI to run the packaged artifact on the intended Java runtime, not only to compile it.

#### Optional Anki

Q: Why prefer `--release` over only `-source`/`-target`?
A: It also restricts visible JDK APIs to the selected release, preventing accidental use of newer platform APIs.

Q: What causes `UnsupportedClassVersionError`?
A: Running class files compiled for a newer Java class-file version on an older JVM.

</details>

<details>
<summary><strong>JCORE-PLAT-009. What changes when compiling and running Java preview features with `--enable-preview`?</strong></summary>

#### Short answer

Preview features must be enabled both at compile time and at runtime. Compile with `--enable-preview` plus the selected release or source level, and run tests and the application with `--enable-preview` on the matching Java feature release.

#### Interview answer

Preview features are not final Java features yet. They are included so developers can try them and give feedback, but their syntax or semantics may change before finalization.

The practical rule is that every Java tool in the path must agree: compiler, tests, IDE, build plugins and runtime. A typical command is `javac --enable-preview --release 21 ...`, followed by `java --enable-preview ...`. If you compile preview bytecode and run without the flag, the JVM rejects it.

#### Deep dive

Preview class files are marked so the JVM knows they depend on preview semantics for that Java release. They are tied to a specific feature release, so preview code compiled for one Java version is not a portable promise for later versions.

Build tools need explicit configuration. Maven and Gradle may require compiler arguments and test JVM arguments. IDE language level and run configurations must also enable preview, otherwise the code may compile in CI but fail locally, or the reverse.

#### Production angle

Preview features are usually a poor default for production services because upgrades can require source changes and operational flags must be carried everywhere. They are more reasonable for experiments, internal tools, learning or code that can move quickly with JDK releases.

#### Traps / caveats

- Enabling preview only for compilation is not enough; runtime and tests need it too.
- Preview features can change or disappear before becoming final.
- Preview bytecode is tied to the Java feature release it was compiled for.
- CI, IDE and local command-line builds can drift if preview flags are configured in only one place.
- Libraries should be very cautious about exposing preview features in public APIs.

#### Optional Anki

Q: What flags are needed for preview features?
A: Compile with `--enable-preview` plus a release/source level, and run with `--enable-preview` on the matching JDK release.

Q: Why are preview features risky in production?
A: They can change before finalization and require consistent compiler/test/runtime flags.

</details>

<details>
<summary><strong>🧠 JCORE-PLAT-010. What is a multi-release JAR, and when is it useful?</strong></summary>

#### Short answer

A multi-release JAR contains base classes plus version-specific classes under `META-INF/versions/N/`. A newer JVM can load the highest matching versioned class, while older JVMs use the base version.

#### Interview answer

Multi-release JARs are mainly a library packaging tool. They let a library support an older baseline Java version while using newer JDK APIs or implementations on newer runtimes.

For example, the base class may work on Java 11, while `META-INF/versions/17/` contains an optimized implementation for Java 17+. The manifest must declare the JAR as multi-release. At runtime, the JVM chooses the highest versioned entry that is less than or equal to the current Java version.

#### Deep dive

The base version defines the compatibility floor. Versioned entries override classes or resources for newer runtimes. The public API should stay compatible across versions, otherwise consumers see different behavior depending on the JDK they run.

Builds usually compile each versioned slice with the correct `--release`. Tests must run on every supported runtime, because a class that works in the base path may fail in a versioned path.

#### Production angle

Multi-release JARs can reduce the need for separate artifacts, but they complicate debugging. When a bug happens, you must know which runtime version was used and which physical class entry was loaded. Tools and dependency scanners also need to understand multi-release layout.

#### Traps / caveats

- The manifest must mark the archive as multi-release.
- The base classes still need to run on the lowest supported Java version.
- Each versioned slice should be compiled with the correct target release.
- Behavior can differ by runtime version, so test every supported JDK.
- For normal applications, a single target runtime is often simpler than a multi-release JAR.

#### Optional Anki

Q: What is a multi-release JAR?
A: A JAR with base entries plus version-specific entries under `META-INF/versions/N/` selected by runtime Java version.

Q: When is it useful?
A: Mostly for libraries that support an older baseline while using newer JDK APIs on newer runtimes.

</details>

<details>
<summary><strong>JCORE-PLAT-011. How do class loading, linking and initialization work?</strong></summary>

#### Short answer

The JVM does not load every class at startup. It loads classes on demand, verifies them, prepares static storage, resolves symbolic references when needed, and initializes a class before its first active use.

#### Interview answer

The class lifecycle is usually described as loading, linking and initialization. Loading finds the class bytes and creates a `Class` object. Linking includes verification, preparation and resolution. Initialization runs static field initializers and static blocks.

Class loaders define class identity together with the class name: the same binary name loaded by two different class loaders is not the same runtime class. Standard loading is parent-first for core classes, but application servers, plugins and frameworks may use more complex loaders, including the thread context class loader.

#### Deep dive

Verification checks that bytecode is structurally valid and respects JVM safety rules. Preparation allocates and initializes static fields to default values. Resolution turns symbolic references from the constant pool into direct references, but it may be lazy, so some linkage failures appear only when a path is executed.

Initialization is triggered by active use, for example creating an instance, calling a static method, writing or reading a non-constant static field, or reflective access that requires initialization. Initialization order matters: superclass initialization happens before subclass initialization.

#### Production angle

Class loading problems often appear as startup failures, first-request failures, plugin isolation bugs or memory leaks after redeploy. A common senior-level debugging path is to check which class loader loaded a class, which JAR provided it, whether there are duplicate classes, and whether a framework relies on the context class loader.

#### Traps / caveats

- Class loading is lazy; a bad dependency can stay hidden until a specific code path runs.
- Class identity is class name plus defining class loader, not just the package and class name.
- Static initialization can throw and leave the class unusable for the rest of the process.
- Resolution is not always eager, so linkage errors may appear after startup.
- Custom class loaders can break assumptions about casting, singletons, resources and service loading.

#### Optional Anki

Q: What are the class lifecycle stages?
A: Loading, linking and initialization; linking includes verification, preparation and resolution.

Q: Why can two classes with the same name be incompatible?
A: Runtime class identity includes both binary name and defining class loader.

</details>

<details>
<summary><strong>JCORE-PLAT-012. What is the difference between classpath and module path?</strong></summary>

#### Short answer

The classpath is the traditional unordered search path for classes and resources. The module path is used by JPMS modules: modules declare dependencies, exported packages and readability rules through `module-info.java`.

#### Interview answer

On the classpath, classes are found by scanning entries such as directories and JARs. There is no strong module boundary: if a public class is present, code can usually access it, and duplicate classes are resolved by search order.

On the module path, the JVM resolves a module graph. A named module must require other modules and export packages that consumers may use. This gives stronger encapsulation and reliable configuration, but it also means reflective access and deep framework integration may need `opens`, `--add-opens` or `--add-exports`.

#### Deep dive

Classpath applications live mostly in the unnamed module. Module-path applications can use explicit named modules, automatic modules from ordinary JARs, and the platform modules from the JDK. JPMS checks split packages and module readability, so some dependency problems fail earlier than they would on the classpath.

Many backend applications still run on the classpath because frameworks, reflection-heavy libraries and build tooling are simpler there. Senior-level understanding is not "modules are always better"; it is knowing what boundary and operational behavior you are choosing.

#### Production angle

Classpath issues usually look like wrong JAR order, duplicate classes, missing classes or dependency convergence failures. Module-path issues often look like unresolved modules, inaccessible packages, illegal reflective access or missing `opens` for serialization, DI, proxies or ORM.

#### Traps / caveats

- Classpath has weak boundaries and can hide duplicate-class problems until runtime.
- Module path has stronger checks but can expose reflection and package-visibility problems.
- Automatic modules are useful for migration but their names can be unstable if not declared intentionally.
- A package cannot be split across modules in the same layer.
- Most Spring Boot services do not need to be modularized just to be modern Java applications.

#### Optional Anki

Q: Classpath vs module path?
A: Classpath is a loose class/resource search path; module path resolves named modules with dependencies, exports and readability rules.

Q: Why can JPMS break reflection-heavy frameworks?
A: Strong encapsulation can block reflective access unless packages are opened or exports are adjusted.

</details>

<a id="jcore-plat-013"></a>

<details>
<summary><strong>JCORE-PLAT-013. What are common Java startup and linkage errors?</strong></summary>

#### Short answer

Common errors include `ClassNotFoundException`, `NoClassDefFoundError`, `NoSuchMethodError`, `NoSuchFieldError`, `UnsupportedClassVersionError`, `ExceptionInInitializerError` and `ClassCastException` caused by class loader mismatch.

#### Interview answer

These errors usually mean the code that runs is not the same code shape the compiler saw. A class may be missing from the runtime classpath, a dependency version may be different, a class may have been compiled for a newer Java version, or a static initializer may have failed.

A senior answer should distinguish missing class from incompatible class. Missing class points to packaging or runtime classpath. `NoSuchMethodError` and `NoSuchFieldError` point to binary incompatibility: the class exists, but not with the member the caller was compiled against.

#### Deep dive

`ClassNotFoundException` is a checked exception from explicit loading, such as `Class.forName`. `NoClassDefFoundError` is an error when a class that was needed by the JVM cannot be found or cannot be defined at runtime; it can also appear after initialization failed earlier.

`UnsupportedClassVersionError` means class-file version mismatch. `ExceptionInInitializerError` wraps failure from static initialization. A surprising `ClassCastException` between classes with the same name often means different class loaders loaded separate copies.

#### Production angle

Debug by checking the Java runtime version, the exact packaged artifact, dependency tree, duplicate classes, manifest, container image and startup command. Tools such as `jdeps`, `jar tf`, Maven/Gradle dependency reports, `-verbose:class` or unified logging for class loading can show what is actually loaded.

#### Traps / caveats

- A successful compile does not prove the runtime dependency graph is the same.
- `NoSuchMethodError` usually points to dependency version conflict, not a source-level typo.
- `NoClassDefFoundError` can be caused by earlier initialization failure, not only by a missing JAR.
- Fat JARs can hide duplicate classes and resource merge problems.
- Container images can run a different Java version from the build machine.

#### Optional Anki

Q: What does `NoSuchMethodError` usually mean?
A: Binary incompatibility: runtime loaded a class version without the method the caller was compiled against.

Q: What should you inspect for startup linkage errors?
A: Runtime JDK, packaged artifact, dependency tree, duplicate classes, manifest, image and launch command.

<summary><strong>🧠 JCORE-PLAT-014. What are `jlink`, CDS and AOT/native-image trade-offs?</strong></summary>

#### Short answer

`jlink` builds a custom runtime image from selected modules. CDS shares preprocessed class metadata to improve startup and memory use. AOT/native-image approaches compile ahead of time for faster startup and smaller deployment in some cases, but trade away some JVM dynamism and may require extra configuration.

#### Interview answer

These tools are deployment and startup tools, not replacements for understanding normal JVM execution. `jlink` is useful when you want to ship a minimized runtime instead of a full JDK or generic JRE-like image. CDS can reduce startup and footprint by reusing class metadata across JVM processes or starts.

AOT and native images are attractive for short-lived services, CLIs, serverless and scale-to-zero workloads. For typical long-running backend services, the normal JVM can be better because JIT optimization, mature GC, observability tooling and dynamic framework behavior are valuable.

#### Deep dive

`jlink` works with modules and can remove unused JDK modules from the runtime image. This can reduce image size and attack surface, but it also removes tools and APIs that are not included.

CDS is less invasive because the application still runs on the JVM. Native-image style AOT is more invasive: reflection, dynamic proxies, resources, JNI, serialization and framework discovery may need explicit metadata or build-time analysis. The resulting binary is platform-specific.

#### Production angle

The trade-off is not only image size. Ask what you need during incidents: shell access, `jcmd`, heap dumps, JFR, profilers, agents and consistent diagnostics. A minimal image can be good for production, but teams often keep a debug image or operational path with full JDK tools.

#### Traps / caveats

- `jlink` can remove modules or tools you later need for diagnostics or optional behavior.
- CDS helps startup and footprint, but it does not turn Java into native code.
- Native images are platform-specific and may need explicit reflection/resource/proxy configuration.
- AOT can improve startup but may reduce peak performance compared with warmed-up JIT code.
- For long-running services, measure startup, memory, latency, throughput and operability before choosing.

#### Optional Anki

Q: What does `jlink` do?
A: Builds a custom runtime image from selected Java modules.

Q: Native image main trade-off?
A: Faster startup and sometimes smaller footprint, but less JVM dynamism and more build-time configuration.
