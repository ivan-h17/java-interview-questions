# 1. Java platform, compilation and execution


<a id="jcore-plat-001"></a>

<details>
<summary><strong>JCORE-PLAT-001. What is the difference between JVM, JRE and JDK?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The <strong>JVM</strong> executes Java bytecode. The <strong>JRE</strong> is a runtime environment: JVM plus standard libraries and runtime files needed to run Java applications. The <strong>JDK</strong> is the developer kit: runtime plus tools such as <code>javac</code>, <code>jar</code>, <code>jlink</code> and diagnostic utilities.</p>
</td>
<td valign="top" width="50%">
<p><strong>JVM</strong> выполняет байткод Java. <strong>JRE</strong> — среда выполнения: JVM плюс стандартные библиотеки и файлы, нужные для запуска приложения. <strong>JDK</strong> — комплект разработчика: время выполнения плюс инструменты вроде <code>javac</code>, <code>jar</code>, <code>jlink</code> и диагностические утилиты.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A good way to explain it is: JVM is the engine, JRE is what a machine needs to run a Java app, and JDK is what a developer or build system needs to build and inspect one.</p>
<p>The JVM is both a specification and an implementation family, for example HotSpot. It loads classes, verifies bytecode, manages memory, runs the interpreter and JIT compiler, and must preserve Java Memory Model semantics during execution and optimization. The JRE historically packaged the JVM and class library for running apps. The JDK adds development tools: compiler, archiver, documentation tools, module tools and troubleshooting tools. In modern Java deployments teams often install a full JDK or build a trimmed runtime image, so the conceptual distinction matters more than assuming a separate “JRE installer”.</p>
</td>
<td valign="top" width="50%">
<p>Удобная формулировка для интервью: JVM — это движок, JRE — то, что нужно машине для запуска Java-приложения, а JDK — то, что нужно разработчику или системе сборки для сборки и диагностики.</p>
<p>JVM — это и спецификация, и семейство реализаций, например HotSpot. Она загружает классы, проверяет байткод, управляет памятью, запускает интерпретатор и JIT-компилятор, а при выполнении и оптимизации обязана сохранять семантику Java Memory Model. JRE исторически упаковывала JVM и стандартную библиотеку для запуска приложений. JDK добавляет инструменты разработки: компилятор, архиватор, документацию, модульные инструменты и утилиты диагностики. В современных деплоях часто ставят полный JDK или собирают урезанный образ среды выполнения, поэтому важнее понимать концепции, а не ожидать отдельный “JRE installer”.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The JVM runs <code>.class</code> files, not <code>.java</code> source files. It performs class loading, bytecode verification, linking, initialization, interpretation, JIT compilation, garbage collection and native interop through mechanisms such as JNI.</p>
<p>The JRE includes the runtime libraries and launcher needed to execute applications. The JDK includes the JRE-like runtime plus tools: <code>javac</code> for compilation, <code>jar</code> for archives, <code>javadoc</code>, <code>jdeps</code>, <code>jlink</code>, <code>jcmd</code>, <code>jstack</code>, <code>jmap</code> and others depending on the distribution.</p>
<p>Different vendors can provide compatible JDK builds. Compatibility still depends on the Java version, class-file version, available APIs and vendor-specific packaging choices.</p>
</td>
<td valign="top" width="50%">
<p>JVM выполняет файлы <code>.class</code>, а не исходники <code>.java</code>. Она загружает классы, проверяет байткод, выполняет линковку и инициализацию, интерпретирует код, запускает JIT-компиляцию, управляет сборкой мусора и взаимодействует с нативным кодом через механизмы вроде JNI.</p>
<p>JRE содержит библиотеки времени выполнения и запускатель, нужные для выполнения приложений. JDK включает JRE-подобную среду выполнения и инструменты: <code>javac</code> для компиляции, <code>jar</code> для архивов, <code>javadoc</code>, <code>jdeps</code>, <code>jlink</code>, <code>jcmd</code>, <code>jstack</code>, <code>jmap</code> и другие утилиты в зависимости от дистрибутива.</p>
<p>Разные поставщики могут поставлять совместимые JDK-сборки. Совместимость всё равно зависит от версии Java, версии class-файлов, доступных API и особенностей упаковки конкретного поставщика.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For backend services, compile and test with an explicit JDK version, then run on a compatible runtime. A common production issue is compiling with a newer JDK and running on an older runtime, which can fail with <code>UnsupportedClassVersionError</code>.</p>
<p>Small container images are useful, but removing the full JDK also removes diagnostic tools. Many teams use a slim runtime for normal execution and keep a debug image or sidecar workflow with JDK tools for incidents.</p>
</td>
<td valign="top" width="50%">
<p>Для бэкенд-сервисов важно явно фиксировать версию JDK для сборки и тестов, а запускать в совместимой среде выполнения. Типичная проблема в продакшене — собрать код новым JDK и запустить на старой среде выполнения, что может закончиться <code>UnsupportedClassVersionError</code>.</p>
<p>Маленькие контейнерные образы полезны, но вместе с полным JDK часто исчезают диагностические инструменты. Поэтому команды нередко используют облегчённый runtime-образ для обычного запуска и отдельный отладочный образ или процесс с JDK-утилитами для инцидентов.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>JRE is not the same thing as JVM; it contains a JVM plus runtime libraries.</li>
<li>JDK is not only <code>javac</code>; it also contains launchers, packaging, module and diagnostic tools.</li>
<li>Do not assume a separate JRE installation exists in modern deployments; custom runtime images and full JDK images are common.</li>
<li>Vendor and version differences can matter for GC defaults, container behavior, crypto providers and diagnostics.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>JRE — не то же самое, что JVM; внутри JRE есть JVM и библиотеки времени выполнения.</li>
<li>JDK — это не только <code>javac</code>; там есть запускатели, инструменты упаковки, модульные и диагностические инструменты.</li>
<li>Не стоит ожидать отдельную установку JRE в современных деплоях; часто используют custom-образ среды выполнения или полный JDK image.</li>
<li>Отличия поставщиков и версий могут влиять на настройки GC по умолчанию, поведение в контейнерах, криптопровайдеры и диагностику.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: JVM vs JRE vs JDK?<br>A: JVM executes bytecode; JRE is JVM plus runtime libraries for running apps; JDK is runtime plus development and diagnostic tools.</p>
<p>Q: Why might a production image include a JDK?<br>A: For tools such as jcmd, jstack, jmap, jdeps or emergency diagnostics, even if the app only needs a runtime to execute.</p>
</td>
<td valign="top" width="50%">
<p>Q: JVM vs JRE vs JDK?<br>A: JVM выполняет байткод; JRE = JVM плюс библиотеки времени выполнения; JDK = время выполнения плюс инструменты разработки и диагностики.</p>
<p>Q: Зачем в продакшен image может быть JDK?<br>A: Чтобы иметь утилиты вроде jcmd, jstack, jmap, jdeps для диагностики, хотя для запуска приложению достаточно время выполнения.</p>
</td>

<details>
<summary><strong>JCORE-PLAT-002. How does Java source code become a running program?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Java source code is compiled by <code>javac</code> from <code>.java</code> files into <code>.class</code> bytecode. The classes are often packaged into a JAR. The <code>java</code> launcher starts a JVM, class loaders load classes, the JVM verifies and links them, initializes the main class, and executes bytecode using interpretation and JIT compilation.</p>
</td>
<td valign="top" width="50%">
<p>Исходный код Java компилируется <code>javac</code> из <code>.java</code> в байткод <code>.class</code>. Часто классы упаковывают в JAR. Команда <code>java</code> запускает JVM, загрузчики классов загружают классы, JVM проверяет и линкует их, инициализирует главный класс и выполняет байткод через интерпретацию и JIT-компиляцию.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The lifecycle is: source code → compilation → class files → packaging → JVM startup → class loading/linking/initialization → execution.</p>
<p>In practice a build tool such as Maven or Gradle calls <code>javac</code>, annotation processors may generate additional source or metadata, and dependencies are resolved on the compile classpath or module path. The output is bytecode in <code>.class</code> files, commonly packaged into a JAR. At launch, the JVM locates the main class or executable JAR manifest, loads classes lazily as they are referenced, verifies bytecode safety, resolves symbolic references, runs static initialization, and calls <code>public static void main(String[] args)</code> or a framework bootstrap.</p>
</td>
<td valign="top" width="50%">
<p>Жизненный цикл: исходники → компиляция → class-файлы → упаковка → старт JVM → загрузка/линковка/инициализация классов → выполнение.</p>
<p>На практике инструмент сборки вроде Maven или Gradle вызывает <code>javac</code>, процессоры аннотаций могут генерировать дополнительные исходники или метаданные, а зависимости берутся из classpath компиляции или module path. Результат — байткод в <code>.class</code>, обычно упакованный в JAR. При запуске JVM находит главный класс или манифест исполняемого JAR, лениво загружает классы при обращении к ним, проверяет безопасность байткода, разрешает символьные ссылки, выполняет статическую инициализацию и вызывает <code>public static void main(String[] args)</code> либо стартовый код фреймворка.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>javac</code> parses source code, performs semantic checks, type checks, constant folding and desugaring, then emits class files. Desugaring means some high-level constructs are represented through lower-level bytecode patterns; for example enhanced loops, lambdas and switch features have bytecode-level translations.</p>
<p>At runtime the JVM does not load every class immediately. Class loading is demand-driven. The lifecycle of a class includes loading, verification, preparation, optional resolution and initialization. Resolution can be lazy, so linkage problems may appear only when a code path is executed.</p>
<p>Execution usually starts with interpreted bytecode. Hot code can later be compiled to native machine code by the JIT compiler. If the JVM made an optimization assumption that becomes invalid, it can deoptimize back to safer code.</p>
</td>
<td valign="top" width="50%">
<p><code>javac</code> парсит исходники, делает семантические проверки, проверки типов, свёртку констант и десахаризацию, затем генерирует class-файлы. Десахаризация означает, что часть высокоуровневых конструкций представляется более низкоуровневыми шаблонами байткода; например расширенные циклы for, лямбды и новые конструкции switch имеют трансляцию на уровне байткода.</p>
<p>Во время выполнения JVM не загружает все классы сразу. Загрузка классов обычно происходит по требованию. Жизненный цикл класса включает загрузку, проверку, подготовку, необязательное разрешение ссылок и инициализацию. Разрешение ссылок может быть ленивым, поэтому проблемы линковки иногда появляются только при выполнении конкретной ветки кода.</p>
<p>Выполнение часто начинается с интерпретации байткода. Горячий код позже может быть скомпилирован JIT-компилятором в машинный код. Если JVM сделала оптимизационное предположение, которое перестало быть верным, она может выполнить деоптимизацию обратно к более безопасному коду.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Most production failures in this area are not syntax errors; they are packaging, classpath, module path or version problems. Examples: wrong main class in the manifest, missing dependency, incompatible transitive dependency, different runtime classpath from test classpath, or class files compiled for a newer Java version.</p>
<p>A practical backend answer should mention reproducible builds, locked dependency versions, CI tests using the same packaged artifact, explicit <code>--release</code> target when needed, and smoke tests for the exact container image that will be deployed.</p>
</td>
<td valign="top" width="50%">
<p>Большинство проблем в продакшене здесь — не синтаксические ошибки, а упаковка, classpath, module path или проблемы версий. Примеры: неправильный главный класс в манифесте, отсутствующая зависимость, несовместимая транзитивная зависимость, отличие runtime classpath от test classpath или class-файлы, собранные под более новую Java.</p>
<p>Практичный ответ для бэкенд-интервью должен упомянуть воспроизводимые сборки, зафиксированные версии зависимостей, CI-тесты именно упакованного артефакта, явную цель <code>--release</code> при необходимости и smoke-тесты для того контейнерного образа, который будет деплоиться.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Java is both compiled and executed by a runtime; <code>javac</code> compilation and JIT compilation are different stages.</li>
<li>Compilation does not automatically bundle all dependencies into your application JAR.</li>
<li>Class loading is lazy, so a missing class can stay hidden until a specific endpoint or job runs.</li>
<li>With <code>java -jar</code>, the launcher ignores a separate <code>-cp</code>; dependencies must come from the JAR layout, manifest <code>Class-Path</code> or framework launcher.</li>
<li>Static initialization can fail before application code appears to start.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Java одновременно компилируется и выполняется время выполнения’ом; компиляция <code>javac</code> и JIT-компиляция — разные этапы.</li>
<li>Компиляция не упаковывает все зависимости в приложение JAR автоматически.</li>
<li>Загрузка классов ленивый, поэтому отсутствующий класс может не проявиться до запуска конкретного endpoint’а или job’ы.</li>
<li>С <code>java -jar</code> запускатель игнорирует отдельный <code>-cp</code>; зависимости должны приходить из layout JAR, манифест <code>Class-Path</code> или фреймворк запускатель.</li>
<li>Статическая инициализация может упасть ещё до того, как приложение “нормально” стартовало.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What are the major stages from Java source to execution?<br>A: Compile .java to .class, package, launch JVM, load/link/initialize classes, execute via interpreter and JIT.</p>
<p>Q: Why can a Java app compile but fail only in production?<br>A: Runtime classpath, Java version, packaging, config or dependency versions can differ from compile/test time.</p>
</td>
<td valign="top" width="50%">
<p>Q: Основные этапы от Java исходный код до выполнения?<br>A: Скомпилировать .java в .класс, упаковать, запустить JVM, загрузить/слинковать/инициализировать классы, выполнить через interpreter и JIT.</p>
<p>Q: Почему Java app может компилироваться, но падать только в продакшен?<br>A: Runtime classpath, версия Java, упаковка, config или версии зависимостей могут отличаться от этапа компиляции/тестов.</p>
</td>
</tr>

<details>
<summary><strong>JCORE-PLAT-003. What is Java bytecode, and why does it matter?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Java bytecode is the platform-neutral instruction format stored in <code>.class</code> files. It matters because it is the contract between compilers and the JVM: the JVM can verify it, load it dynamically, interpret it, JIT-compile it to native code, and run bytecode produced by Java and other JVM languages.</p>
</td>
<td valign="top" width="50%">
<p>Байткод Java — платформенно-нейтральный набор инструкций в файлах <code>.class</code>. Он важен, потому что это контракт между компиляторами и JVM: JVM может его проверять, динамически загружать, интерпретировать, JIT-компилировать в нативный код и запускать байткод, созданный Java и другими JVM-языками.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Bytecode is not source code and not CPU machine code. It is an intermediate representation defined by the JVM specification. A <code>.class</code> file contains bytecode for methods plus metadata such as the constant pool, fields, methods, descriptors, attributes and class-file version.</p>
<p>It matters for portability and tooling. Java, Kotlin, Scala and other JVM languages can compile to bytecode. The JVM can verify bytecode before execution, which supports type safety and memory-safety rules at the bytecode level. Tools can inspect or transform bytecode for coverage, profiling, proxies and instrumentation.</p>
</td>
<td valign="top" width="50%">
<p>Байткод — это не исходный код и не машинный код конкретного CPU. Это промежуточное представление, определённое спецификацией JVM. Файл <code>.class</code> содержит байткод методов и метаданные: constant pool, поля, методы, дескрипторы, attributes и версию class-файла.</p>
<p>Он важен для переносимости и инструментов. Java, Kotlin, Scala и другие JVM-языки могут компилироваться в байткод. JVM проверяет байткод перед выполнением, что поддерживает правила type safety и memory-safety на уровне байткода. Инструменты могут анализировать или трансформировать байткод для coverage, профилирования, прокси и instrumentation.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The JVM bytecode model is stack-based: instructions operate on an operand stack and local variables. For example, bytecode can load a value, call a method, branch, create an object, access a field or throw an exception.</p>
<p>Bytecode keeps symbolic references that are resolved by the JVM at runtime. It also contains metadata used by reflection, debuggers and frameworks. Some source-level information is not preserved in the same form; for example generic type parameters are mostly erased and represented through signatures and compiler-inserted casts.</p>
<p>Modern JVM features such as lambdas rely heavily on bytecode mechanisms like <code>invokedynamic</code>, which lets the runtime link call sites dynamically.</p>
</td>
<td valign="top" width="50%">
<p>Модель байткода JVM стековая: инструкции работают со стеком операндов и локальными переменными. Например, байткод может загрузить значение, вызвать метод, сделать переход, создать объект, обратиться к полю или выбросить исключение.</p>
<p>Байткод хранит символьные ссылки, которые JVM разрешает во время выполнения. Также он содержит метаданные для reflection, отладчиков и фреймворков. Часть информации исходного уровня не сохраняется в прежнем виде; например параметры generic-типов в основном стираются (type erasure) и представлены через сигнатуры и вставленные компилятором приведения типов.</p>
<p>Современные возможности JVM вроде лямбд активно используют байткод-механизмы типа <code>invokedynamic</code>, который позволяет runtime динамически связывать call sites.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Bytecode matters in production when debugging class version errors, dependency conflicts, framework proxies or Java agents. Tools such as <code>javap</code>, <code>jdeps</code>, profilers and coverage agents work at this level.</p>
<p>Bytecode instrumentation can change startup time, stack traces, method shapes and sometimes performance. This is normal for agents like coverage, tracing or APM, but it should be considered when comparing test and production behavior.</p>
</td>
<td valign="top" width="50%">
<p>Байткод важен в продакшен при разборе класс версия ошибки, зависимость conflicts, фреймворк прокси или Java agents. Утилиты вроде <code>javap</code>, <code>jdeps</code>, profilers и coverage agents работают именно на этом уровне.</p>
<p>Байткод instrumentation может менять запуск time, stack traces, форму методов и иногда производительность. Это нормально для coverage, tracing или APM agents, но это нужно учитывать при сравнении поведения в тестах и продакшен.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">

<li>Bytecode is portable, but not every bytecode version runs on every Java runtime.</li>
<li>The JVM may execute bytecode by interpreting it or by compiling hot parts to native code.</li>
<li>Do not expect all source-level constructs to exist directly in bytecode; many are desugared or erased.</li>
<li>Framework-generated bytecode can make stack traces and equality/proxy behavior less obvious.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Байткод переносим, но не каждая версия байткода запускается на любой версии Java время выполнения.</li>
<li>JVM может выполнять байткод через интерпретацию или компилировать горячие участки в нативный код.</li>
<li>Не стоит ожидать, что все source-level конструкции существуют в байткоде напрямую; многие desugared или erased.</li>
<li>Сгенерированный фреймворк’ами байткод может усложнять stack traces и поведение равенство/прокси.</li>
</ul>
</td>

<p>Q: Why does bytecode matter?<br>A: It enables portability, verification, dynamic loading, JIT compilation and tooling/instrumentation.</p>

<p>Q: Почему байткод важен?<br>A: Он даёт переносимость, проверку, динамическая загрузка, JIT-компиляция и инструменты и инструментирование.</p>

<details>
<summary><strong>JCORE-PLAT-004. Why is Java called platform-independent?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Java is called platform-independent because compiled Java bytecode can run on any compatible JVM, regardless of the underlying operating system or CPU architecture. The JVM and standard library provide the platform-specific implementation details.</p>
</td>
<td valign="top" width="50%">
<p>Java называют platform-independent, потому что скомпилированный байткод может выполняться на любой совместимой JVM независимо от операционной системы и архитектуры CPU. JVM и стандартная библиотека берут на себя platform-specific детали.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The phrase usually means “compile once, run on any compatible JVM”. Source code is compiled to bytecode, and each platform has its own JVM implementation that translates that bytecode into actual execution on the local OS and CPU.</p>
<p>This is different from languages that normally compile directly into a platform-specific executable. In Java the binary artifact is usually a JAR with class files, and the target platform provides the JVM.</p>
</td>
<td valign="top" width="50%">
<p>Обычно это означает “compile once, run on any compatible JVM”. Исходный код компилируется в байткод, а для каждой платформы есть своя реализация JVM, которая выполняет этот байткод поверх локальной OS и CPU.</p>
<p>Это отличается от языков, где код обычно компилируется сразу в platform-specific исполняемый файл. В Java бинарный артефакт часто является JAR с class-файлами, а целевая платформа предоставляет JVM.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The JVM abstracts many low-level details: instruction set, memory management, object layout, threads, file and socket APIs, and exception handling. The class-file format defines a stable intermediate representation, so a class compiled on macOS can run on Linux or Windows if the runtime is compatible.</p>
<p>However, platform independence is not absolute. Java programs can depend on native libraries, OS commands, filesystem case sensitivity, path conventions, configured or older-runtime default charset behavior, default locale, default time zone, available fonts, crypto providers, container limits and environment variables.</p>
<p>Java version compatibility also matters. Bytecode compiled for a newer class-file version will not run on an older JVM.</p>
</td>
<td valign="top" width="50%">
<p>JVM абстрагирует многие низкоуровневые детали: instruction set, управление памятью, layout объектов, потоки, API файлов и сокетов, обработку исключений. Формат class-файла задаёт стабильное промежуточное представление, поэтому класс, собранный на macOS, может работать на Linux или Windows при совместимой среде выполнения.</p>
<p>Но platform independence не абсолютна. Java-программы могут зависеть от нативных библиотек, OS-команд, чувствительности файловой системы к регистру, соглашений о путях, настроенного charset по умолчанию или поведения старой среды выполнения, locale по умолчанию, time zone по умолчанию, шрифтов, криптопровайдеров, container limits и environment variables.</p>
<p>Также важна совместимость версий Java. Байткод, скомпилированный под более новую версию class-file, не запустится на более старой JVM.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For backend services, portability works best when the app avoids platform defaults and native assumptions. Use <code>Path</code> APIs instead of string-concatenated paths, set encoding/time zone/locale intentionally when they affect behavior, package native dependencies per OS and architecture, and test the exact container base image.</p>
<p>Containers make the runtime environment more repeatable, but they do not remove Java version, CPU architecture, libc, file system or kernel-level differences.</p>
</td>
<td valign="top" width="50%">
<p>Для бэкенд-сервисов переносимость лучше работает, когда приложение не полагается на platform defaults и нативные предположения. Используйте API <code>Path</code> вместо склейки путей строками, явно задавайте encoding/time zone/locale там, где они влияют на поведение, пакуйте нативные зависимости под конкретные OS и architecture, тестируйте точный container base image.</p>
<p>Контейнеры делают среду выполнения более повторяемой, но не устраняют различия версии Java, CPU architecture, libc, файловой системы или kernel-level поведения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Platform-independent does not mean environment-independent.</li>
<li>A compatible JVM is required; bytecode is not executed directly by the operating system.</li>
<li>Native libraries via JNI/JNA must match OS and CPU architecture.</li>
<li>Locale, time zone and configured or older-runtime charset defaults can change behavior across machines.</li>
<li>Java version mismatch can break startup even if the OS is supported.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Platform-independent не означает environment-independent.</li>
<li>Нужна совместимая JVM; операционная система не выполняет байткод напрямую.</li>
<li>Нативные библиотеки через JNI/JNA должны соответствовать OS и CPU architecture.</li>
<li>Locale, time zone и charset по умолчанию, заданный конфигурацией или старой средой выполнения, могут менять поведение на разных машинах.</li>
<li>Несовпадение версии Java может сломать старт, даже если OS поддерживается.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>

<details>
<summary><strong>JCORE-PLAT-005. What is the difference between compile time and runtime in Java?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><strong>Compile time</strong> is when source code is translated and checked by the compiler. <strong>Runtime</strong> is when the JVM executes the program. Compile-time problems include syntax, type and missing-symbol errors; runtime problems include nulls, bad casts, class loading, configuration, dependency and external-system failures.</p>
</td>
<td valign="top" width="50%">
<p><strong>Compile time</strong> — этап, когда исходный код переводится и проверяется компилятором. <strong>Runtime</strong> — этап, когда JVM выполняет программу. Проблемы на этапе компиляции: syntax, тип и ошибки отсутствующих символов; время выполнения проблемы: nulls, неверные приведения типов, загрузка классов, конфигурация, зависимость и сбои внешних систем.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Compile time answers the question “can this source code be compiled against the declared APIs?” Runtime answers “what actually happens when this packaged application runs with real classes, data, config and environment?”</p>
<p>Java has strong static typing, so many mistakes are caught at compile time: invalid syntax, incompatible types, inaccessible members, missing imports, unhandled checked exceptions and missing symbols on the compile classpath. But Java also has dynamic class loading, reflection, proxies, dependency resolution and external configuration, so many failures appear only at runtime.</p>
</td>
<td valign="top" width="50%">
<p>Compile time отвечает на вопрос: “можно ли скомпилировать этот исходный код против объявленных API?” Runtime отвечает: “что реально произойдёт, когда упакованное приложение запустится с настоящими классами, данными, config и environment?”</p>
<p>У Java сильная статический typing, поэтому многие ошибки ловятся на этап компиляции: invalid syntax, несовместимые типы, недоступные члены класса, отсутствующие импорты, необработанные checked-исключения и отсутствующие символы в classpath компиляции. Но в Java есть динамический загрузка классов, reflection, прокси, разрешение зависимостей и внешняя конфигурация, поэтому многие сбои проявляются только в время выполнения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>javac</code> compiles against a compile classpath or module path. The running application uses a runtime classpath or module path, which may differ. That gap explains classic linkage errors: code compiled against one library version can run with another and fail with <code>NoSuchMethodError</code>, <code>NoClassDefFoundError</code> or similar errors.</p>
<p>Generics are another good example. The compiler checks generic types, but most generic information is erased in bytecode. Some casts are inserted by the compiler and can still fail at runtime if raw types or unchecked operations polluted the data.</p>
<p>Annotation processing is mostly compile-time; reflection, dependency injection and proxy generation are runtime mechanisms unless a framework explicitly moves work to build time.</p>
</td>
<td valign="top" width="50%">
<p><code>javac</code> компилирует код против classpath компиляции или module path. Запущенное приложение использует classpath во время выполнения или module path, которые могут отличаться. Этот разрыв объясняет классические linkage ошибки: код был собран против одной версии библиотеки, а запустился с другой и получил <code>NoSuchMethodError</code>, <code>NoClassDefFoundError</code> или похожие ошибки.</p>
<p>Generics — хороший пример. Компилятор проверяет generic типы, но большая часть generic-информации стирается в байткоде. Некоторые приведения типов вставляются компилятором и всё равно могут упасть в время выполнения, если сырые типы или unchecked эксплуатации “загрязнили” данные.</p>
<p>Annotation processing обычно compile-time; reflection, зависимость injection и proxy generation — время выполнения mechanisms, если фреймворк явно не переносит работу на build time.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>“It compiles” is not a production guarantee. CI should test the packaged artifact with the same dependency graph and Java runtime that production will use. Dependency locking, build scans, dependency convergence checks and container-level smoke tests reduce runtime surprises.</p>
<p>Runtime failures are often caused by environment: missing secrets, invalid config, wrong database schema, different classpath, insufficient permissions, missing native library, memory limits or incompatible Java version.</p>
</td>
<td valign="top" width="50%">
<p>“It compiles” не является гарантией для продакшена. CI должен тестировать упакованный артефакт с тем же граф зависимостей и Java время выполнения, которые будут в продакшен. Dependency locking, отчёты сборки, проверки согласованности зависимостей и smoke-тесты на уровне контейнера уменьшают сюрпризы во время выполнения.</p>
<p>Runtime сбои часто вызваны environment: отсутствующие секреты, invalid config, неправильная база данных schema, другой classpath, недостаточные permissions, отсутствующий нативный библиотека, memory limits или incompatible Java версия.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>A compile-time type check does not prove runtime data is valid.</li>
<li>Warnings, unchecked casts and raw types can become runtime <code>ClassCastException</code>s.</li>
<li>Reflection and framework wiring can hide errors until startup or first request.</li>
<li>Compile classpath and runtime classpath can differ.</li>
<li>Checked exceptions are compile-time rules for declared calls; failures can still cross async, framework or reflection boundaries differently.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Compile-time тип check не доказывает, что время выполнения data корректна.</li>
<li>Warnings, unchecked приведения типов и сырые типы могут стать время выполнения <code>ClassCastException</code>.</li>
<li>Reflection и фреймворк wiring могут скрывать ошибки до запуск или первого запросе.</li>
<li>Compile classpath и classpath во время выполнения могут отличаться.</li>
<li>Checked exceptions — compile-time правила для объявленных вызовов; сбои через async, фреймворк или reflection границах могут проходить иначе.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Compile time vs runtime?<br>A: Compile time checks and generates bytecode; runtime executes the packaged app with real classes, config, data and environment.</p>
<p>Q: Why can NoSuchMethodError happen at runtime?<br>A: The code compiled against an API version where the method existed, but runtime loaded a different incompatible version.</p>
</td>
<td valign="top" width="50%">
<p>Q: Compile time vs время выполнения?<br>A: Compile time проверяет код и генерирует байткод; время выполнения выполняет packaged app с реальными классы, config, data и environment.</p>
<p>Q: Почему NoSuchMethodError появляется в время выполнения?<br>A: Код компилировался против версии API, где метод был, но время выполнения загрузил другую несовместимую версию.</p>
</td>
</tr>

<details>
<summary><strong>JCORE-PLAT-006. What is the difference between javac, java and jar?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>javac</code> compiles Java source files into <code>.class</code> bytecode. <code>java</code> launches a JVM and runs a class, JAR or module. <code>jar</code> creates, reads and updates JAR archives; it packages class files and resources but does not compile or execute the application by itself.</p>
</td>
<td valign="top" width="50%">
<p><code>javac</code> компилирует исходные Java-файлы в байткод <code>.class</code>. <code>java</code> запускает JVM и выполняет класс, JAR или модуль. <code>jar</code> создаёт, читает и обновляет JAR-архивы; он упаковывает class-файлы и ресурсы, но сам не компилирует и не выполняет приложение.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The three commands map to three different concerns: compile, run and package.</p>
<p><code>javac</code> is used during the build. It needs source files and compile dependencies and produces class files. <code>java</code> is used during execution. It starts the JVM, accepts JVM options, loads the main class or executable JAR, and passes application arguments to <code>main</code>. <code>jar</code> is an archive tool based on ZIP format with Java-specific conventions such as <code>META-INF/MANIFEST.MF</code>.</p>
</td>
<td valign="top" width="50%">
<p>Эти три команды отвечают за разные задачи: компиляцию, запуск и упаковку.</p>
<p><code>javac</code> используется во время сборки. Ему нужны исходные файлы и зависимости для компиляции, а результатом являются class-файлы. <code>java</code> используется во время выполнения. Она стартует JVM, принимает опции JVM, загружает главный класс или исполняемый JAR и передаёт аргументы приложения в <code>main</code>. <code>jar</code> — инструмент архивации на базе ZIP-формата с Java-специфичными соглашениями вроде <code>META-INF/MANIFEST.MF</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Typical minimal flow:</p>
<pre><code>javac -d out src/com/acme/App.java
java -cp out com.acme.App
jar --create --file app.jar -C out .</code></pre>
<p><code>javac</code> options control output directory, classpath/module path, annotation processing, debug information and target release. <code>java</code> options control classpath/module path, main class or <code>-jar</code>, heap size, system properties, GC, agents and diagnostic flags. <code>jar</code> can create executable JARs by adding a manifest with <code>Main-Class</code>, can package resources, service provider files and multi-release classes.</p>
<p>Build tools usually hide these commands, but understanding them helps debug broken builds and deployments.</p>
</td>
<td valign="top" width="50%">
<p>Типичная минимальная последовательность:</p>
<pre><code>javac -d out src/com/acme/App.java
java -cp out com.acme.App
jar --create --file app.jar -C out .</code></pre>
<p>Опции <code>javac</code> задают каталог вывода, classpath или module path, обработку аннотаций, отладочную информацию и целевой релиз. Опции <code>java</code> задают classpath или module path, главный класс или <code>-jar</code>, размер heap, системные свойства, GC, агенты и диагностические флаги. <code>jar</code> может создавать исполняемый JAR через манифест с <code>Main-Class</code>, упаковывать ресурсы, файлы service provider и multi-release классы.</p>
<p>Инструменты сборки обычно скрывают эти команды, но их понимание помогает разбирать сломанные сборки и деплои.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production the important details are packaging and launch command correctness. A thin JAR requires dependencies to be present on the runtime classpath. A fat/uber JAR bundles dependencies but can create resource merging, duplicate class or shading issues. An executable JAR needs a correct manifest or framework-specific launcher layout.</p>
<p>Command-line order matters. JVM options such as <code>-Xmx</code>, <code>-D...</code> or <code>-javaagent</code> must be passed to the <code>java</code> launcher before the main class or <code>-jar</code>; arguments after the main class are application arguments.</p>
</td>
<td valign="top" width="50%">
<p>В продакшене важны корректная упаковка и правильная команда запуска. Тонкий JAR требует, чтобы зависимости присутствовали в classpath во время выполнения. Толстый или uber JAR пакует зависимости внутрь, но может создать проблемы со слиянием ресурсов, дублирующимися классами или shading. Исполняемому JAR нужен корректный манифест или layout запускателя конкретного фреймворка.</p>
<p>Порядок аргументов командной строки важен. Опции JVM вроде <code>-Xmx</code>, <code>-D...</code> или <code>-javaagent</code> передаются запускателю <code>java</code> до главного класса или <code>-jar</code>; аргументы после главного класса становятся аргументами приложения.</p>
</td>
</tr>

<a id="jcore-plat-007"></a>

<details>
<summary><strong>JCORE-PLAT-007. What is JIT compilation at a high level?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>JIT, or just-in-time compilation, is runtime compilation performed by the JVM. The JVM starts by interpreting bytecode, observes which methods and loops are hot, then compiles those hot parts into optimized native machine code for the current CPU.</p>
</td>
<td valign="top" width="50%">
<p>JIT, или just-in-time compilation, — это компиляция во время выполнения внутри JVM. JVM начинает с интерпретации байткода, наблюдает, какие методы и циклы стали “горячими”, а затем компилирует эти участки в оптимизированный машинный код для текущего CPU.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>JIT is why Java can be portable and still fast. <code>javac</code> produces portable bytecode ahead of time, and the JVM compiles frequently executed bytecode to native code at runtime.</p>
<p>The key idea is profiling. The JVM knows actual runtime types, branch frequencies and call patterns, so it can inline methods, remove unnecessary checks, optimize virtual calls, eliminate some allocations and specialize code for what really happens. If an assumption becomes invalid, the JVM can deoptimize and recompile differently.</p>
</td>
<td valign="top" width="50%">
<p>JIT объясняет, почему Java может быть переносимой и при этом быстрой. <code>javac</code> заранее создаёт переносимый байткод, а JVM во время выполнения компилирует часто исполняемый байткод в нативный код.</p>
<p>Ключевая идея — профилирование. JVM знает реальные фактические типы, частоты ветвлений и паттерны вызовов, поэтому может делать инлайнинг методов, убирать лишние проверки, оптимизировать виртуальные вызовы, устранять некоторые выделения памяти и специализировать код под фактическое поведение. Если предположение стало неверным, JVM может сделать деоптимизацию и перекомпилировать иначе.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>HotSpot commonly uses tiered compilation: simple compilation and profiling first, then more expensive optimization for very hot code. Important concepts include method counters, loop counters, inlining, escape analysis, on-stack replacement, safepoints, deoptimization and the code cache.</p>
<p>JIT compilation is not the same as source compilation. It works from bytecode to native instructions while the program is running. This has a warm-up cost but gives the runtime information that an ahead-of-time compiler might not have.</p>
<p>JIT also interacts with GC and the memory model. For example, optimizations must preserve Java semantics, including visibility rules and exception behavior.</p>
</td>
<td valign="top" width="50%">
<p>HotSpot обычно использует многоуровневую компиляцию: сначала простая компиляция и профилирование, затем более дорогая оптимизация для очень горячего кода. Важные понятия: счётчики методов, счётчики циклов, инлайнинг, escape analysis, on-stack replacement, safepoints, деоптимизация и кеш кода.</p>
<p>JIT-компиляция — это не то же самое, что компиляция исходного кода. Она переводит байткод в нативные инструкции уже во время работы программы. Это даёт стоимость прогрева, но предоставляет информацию времени выполнения, которой может не быть у ahead-of-time компилятора.</p>
<p>JIT также взаимодействует с GC и моделью памяти. Например, оптимизации обязаны сохранять семантику Java, включая правила видимости и поведение исключений.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>JIT affects production behavior through warm-up, latency and benchmarking. The first requests after startup can be slower while classes load, profiles collect and hot code is compiled. Microbenchmarks without warm-up are often misleading; JMH exists largely to handle JVM benchmarking correctly.</p>
<p>Usually you should not tune JIT first. Start with algorithmic improvements, allocation reduction, database and network latency, GC logs and profiler data. JIT flags are powerful but can make behavior harder to reason about. For short-lived workloads or very fast startup requirements, teams may compare normal JIT-based JVM execution with AOT/native-image approaches.</p>
</td>
<td valign="top" width="50%">
<p>JIT влияет на продакшен через прогрев, задержки и бенчмарки. Первые запросы после запуска могут быть медленнее, пока загружаются классы, собирается профиль и компилируется горячий код. Микробенчмарки без прогрева часто вводят в заблуждение; JMH во многом существует именно для корректного бенчмаркинга JVM.</p>
<p>Обычно не стоит начинать настройку производительности с JIT. Сначала смотрят алгоритмы, снижение выделений памяти, задержки базы данных и сети, логи GC и данные профилировщика. Флаги JIT мощные, но усложняют рассуждение о поведении. Для короткоживущих нагрузок или требований к очень быстрому запуску команды могут сравнивать обычное выполнение на JVM с JIT и подходы AOT/native-image.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>JIT compiles bytecode to native code at runtime; it does not compile <code>.java</code> source to <code>.class</code> files.</li>
<li>Warm-up matters: the first run and steady-state performance can differ significantly.</li>
<li>Microbenchmarks are easy to get wrong because the JIT may eliminate dead code or optimize unrealistic patterns.</li>
<li>More JIT tuning is not automatically better; wrong flags can hurt startup, memory or latency.</li>
<li>Optimized native code can be deoptimized if runtime assumptions change.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>JIT компилирует байткод в нативный код во время выполнения; она не компилирует <code>.java</code> исходный код в <code>.class</code> files.</li>
<li>Warm-up важен: first run и стабильной производительности могут сильно отличаться.</li>
<li>Microbenchmarks легко сделать неправильно, потому что JIT может удалить dead code или оптимизировать нереалистичные patterns.</li>
<li>Больше JIT tuning не значит лучше; неправильные flags могут ухудшить запуск, memory или latency.</li>
<li>Оптимизированный нативный код может быть deoptimized, если время выполнения предположения изменились.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

</td>

<details>
<summary><strong>JCORE-PLAT-008. What is the difference between <code>javac --source</code>, <code>--target</code> and <code>--release</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>-source</code> controls accepted Java language syntax. <code>-target</code> controls the emitted class-file version. <code>--release</code> controls both and also restricts the visible standard-library APIs to the selected Java release.</p>
</td>
<td valign="top" width="50%">
<p><code>-source</code> управляет допустимым Java syntax. <code>-target</code> управляет версией сгенерированный класс files. <code>--release</code> управляет обоими и дополнительно ограничивает видимые standard-библиотека APIs выбранной Java release.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The important production distinction is API compatibility. Compiling with <code>-source 17 -target 17</code> on a newer JDK may still accidentally use JDK APIs that did not exist in Java 17, unless the build also uses a matching boot classpath. <code>--release 17</code> prevents that by compiling against the public APIs for that release.</p>
<p>For modern builds, prefer <code>--release</code> when you need to produce bytecode for an older Java runtime. Use toolchains in Maven or Gradle so the compiler version is explicit and reproducible.</p>
</td>
<td valign="top" width="50%">
<p>Главное продакшен-отличие - API совместимость. Если собрать с <code>-source 17 -target 17</code> на более новом JDK, можно случайно использовать JDK APIs, которых не было в Java 17, если build не использует подходящий boot classpath. <code>--release 17</code> предотвращает это, потому что компилирует против публичных API выбранной release.</p>
<p>В modern builds лучше использовать <code>--release</code>, когда нужно выпускать байткод для более старого Java время выполнения. Toolchains в Maven или Gradle помогают сделать компилятор версия явной и reproducible.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Class-file version controls whether an older JVM can load the class. API availability controls whether the code can actually run. <code>--release</code> handles both for platform APIs. It does not make third-party dependencies compatible; those dependencies must also support the target runtime.</p>
<p>This matters for libraries that support multiple Java versions. They may compile main code for an older release while using newer JDKs in tests or build plugins. Multi-release JARs are another mechanism, but they add packaging and test complexity.</p>
</td>
<td valign="top" width="50%">
<p>Class-file версия определяет, сможет ли старая JVM загрузить класс. API availability определяет, сможет ли код реально выполниться. <code>--release</code> закрывает оба вопроса для platform APIs. Он не делает third-party зависимости совместимыми; сами зависимости тоже должны поддерживать цель время выполнения.</p>
<p>Это важно для библиотеки, которые поддерживают несколько Java versions. Они могут компилировать main code под старую release, но использовать новые JDKs в tests или build плагинов. Multi-release JARs - ещё один механизм, но он усложняет упаковка и testing.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">

A subtler failure is compiling to an older class-file version but calling a newer JDK method, then failing with linkage errors on the older runtime. CI should test on the oldest supported runtime.</p>
</td>
<td valign="top" width="50%">
<p>Типичная ошибка - отгрузить класс files, собранные под более новый время выполнения, и получить <code>UnsupportedClassVersionError</code>. Более тонкая ошибка - собрать older class-file версия, но вызвать новый JDK метод и получить linkage ошибки на старой среде выполнения. CI должен тестировать на oldest supported время выполнения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>

<li><code>--release</code> covers JDK platform APIs, not third-party library compatibility.</li>
<li>Build plugins and test code may run on a different JDK from the application runtime.</li>
<li>Multi-release JARs can help libraries but require careful testing for every supported runtime.</li>

</ul>
</td>

<li><code>--release</code> покрывает JDK platform APIs, но не совместимость third-party библиотеки.</li>
<li>Build плагинов и test code могут запускаться на другом JDK, чем приложение время выполнения.</li>
<li>Multi-release JARs могут помочь библиотеки, но требуют аккуратного testing для каждого supported время выполнения.</li>

</ul>

<details>
<summary><strong>JCORE-PLAT-011. How do class loading, linking and initialization work?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The JVM does not load every class at startup. It loads classes on demand, verifies them, prepares static storage, resolves symbolic references when needed, and initializes a class before its first active use.</p>
</td>
<td valign="top" width="50%">
<p>JVM не загружает все классы при старте. Она загружает классы по требованию, проверяет их, подготавливает статический storage, разрешает символьные ссылки при необходимости и инициализирует класс перед первым active use.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The class lifecycle is usually described as loading, linking and initialization. Loading finds the class bytes and creates a <code>Class</code> object. Linking includes verification, preparation and resolution. Initialization runs static field initializers and static blocks.</p>
<p>Class loaders define class identity together with the class name: the same binary name loaded by two different class loaders is not the same runtime class. Standard loading is parent-first for core classes, but application servers, plugins and frameworks may use more complex loaders, including the thread context class loader.</p>
</td>
<td valign="top" width="50%">
<p>Жизненный цикл класса обычно описывают как loading, linking и инициализацию. Loading находит байты класса и создаёт объект <code>Class</code>. Linking включает проверку, подготовку и разрешение ссылок. Initialization выполняет статический поле initializers и статический blocks.</p>
<p>Class loader участвует в идентичности класса вместе с именем класса: один и тот же binary name, загруженный разными загрузчиками классов, даёт разные фактические классы. Стандартная модель часто parent-first для core-классов, но серверы приложений, плагины и фреймворки могут использовать более сложные loaders, включая thread context class loader.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Verification checks that bytecode is structurally valid and respects JVM safety rules. Preparation allocates and initializes static fields to default values. Resolution turns symbolic references from the constant pool into direct references, but it may be lazy, so some linkage failures appear only when a path is executed.</p>
<p>Initialization is triggered by active use, for example creating an instance, calling a static method, writing or reading a non-constant static field, or reflective access that requires initialization. Initialization order matters: superclass initialization happens before subclass initialization.</p>
</td>
<td valign="top" width="50%">
<p>Verification проверяет, что байткод структурно корректен и соблюдает JVM safety правила. Preparation выделяет статический поля и задаёт им значения по умолчанию. Resolution превращает символьные ссылки из constant pool в direct ссылки, но может быть ленивой, поэтому часть linkage сбои проявляется только при выполнении конкретного пути.</p>
<p>Initialization запускается при active use: например, при создании объекта, вызове статический метод, чтении или записи non-constant статический поле, либо reflection access, которому нужна инициализацию. Порядок важен: суперкласс инициализацию выполняется до подкласс инициализацию.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Class loading problems often appear as startup failures, first-request failures, plugin isolation bugs or memory leaks after redeploy. A common senior-level debugging path is to check which class loader loaded a class, which JAR provided it, whether there are duplicate classes, and whether a framework relies on the context class loader.</p>
</td>
<td valign="top" width="50%">
<p>Проблемы загрузки классов часто выглядят как сбои при запуске, падение на первом запросе, ошибки изоляции плагинов или утечки памяти после redeploy. Практичный практичный путь диагностики для senior-уровня: проверить, какой загрузчик классов загрузил класс, из какого JAR он пришёл, есть ли дублирующимися классами и не полагается ли фреймворк на контекстный загрузчик классов.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Class loading is lazy; a bad dependency can stay hidden until a specific code path runs.</li>
<li>Class identity is class name plus defining class loader, not just the package and class name.</li>
<li>Static initialization can throw and leave the class unusable for the rest of the process.</li>
<li>Resolution is not always eager, so linkage errors may appear after startup.</li>
<li>Custom class loaders can break assumptions about casting, singletons, resources and service loading.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Загрузка классов ленивый; плохая зависимость может не проявиться до конкретного ветка кода.</li>
<li>Class идентичность - это класс name плюс defining загрузчик классов, а не только package и класс name.</li>
<li>Статическая инициализация может упасть и сделать класс непригодным для остального времени жизни процесса.</li>
<li>Resolution не всегда eager, поэтому linkage ошибки могут появиться после запуск.</li>
<li>Custom загрузчики классов могут ломать предположения про приведение типов, singletons, ресурсы и загрузку сервисов.</li>

<summary><strong>JCORE-PLAT-012. What is the difference between classpath and module path?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The classpath is the traditional unordered search path for classes and resources. The module path is used by JPMS modules: modules declare dependencies, exported packages and readability rules through <code>module-info.java</code>.</p>
</td>
<td valign="top" width="50%">
<p>Classpath — традиционный путь поиска классов и ресурсов. Module path используется модулями JPMS: модули объявляют зависимости, экспортируемые пакеты и правила readability через <code>module-info.java</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>On the classpath, classes are found by scanning entries such as directories and JARs. There is no strong module boundary: if a public class is present, code can usually access it, and duplicate classes are resolved by search order.</p>
<p>On the module path, the JVM resolves a module graph. A named module must require other modules and export packages that consumers may use. </td>
<td valign="top" width="50%">
<p>На classpath классы ищутся по элементам вроде каталогов и JAR. Строгой модульной границы нет: если public-класс присутствует, код обычно может к нему обратиться, а дублирующиеся классы разрешаются порядком поиска.</p>
<p>На module path JVM строит граф модулей. Named module должен требовать другие модули и экспортировать пакеты, доступные потребителям. Это даёт более сильную инкапсуляцию и надёжную конфигурацию, но reflection и глубокая интеграция с фреймворками могут требовать <code>opens</code>, <code>--add-opens</code> или <code>--add-exports</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Classpath applications live mostly in the unnamed module. Module-path applications can use explicit named modules, automatic modules from ordinary JARs, and the platform modules from the JDK. JPMS checks split packages and module readability, so some dependency problems fail earlier than they would on the classpath.</p>
<p>Many backend applications still run on the classpath because frameworks, reflection-heavy libraries and build tooling are simpler there. Senior-level understanding is not "modules are always better"; it is knowing what boundary and operational behavior you are choosing.</p>
</td>
<td valign="top" width="50%">
<p>Classpath-приложения в основном живут в unnamed module. Приложения на module path могут использовать явные named modules, automatic modules из обычных JAR и platform modules из JDK. <p>Многие бэкенд-приложения всё ещё запускаются на classpath, потому что фреймворки, reflection-heavy библиотеки и инструменты сборки там проще. Senior-level понимание — это не “modules always better”, а осознанный выбор границ и эксплуатационного поведения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>

<td valign="top" width="50%">
<p>Проблемы classpath обычно выглядят как неверный порядок JAR, дублирующиеся классы, отсутствующие классы или ошибки согласования зависимостей. <details>
<summary><strong>🧠 JCORE-PLAT-014. What are <code>jlink</code>, CDS and AOT/native-image trade-offs?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>jlink</code> builds a custom runtime image from selected modules. CDS shares preprocessed class metadata to improve startup and memory use. AOT/native-image approaches compile ahead of time for faster startup and smaller deployment in some cases, but trade away some JVM dynamism and may require extra configuration.</p>
</td>
<td valign="top" width="50%">
<p><code>jlink</code> собирает custom образ среды выполнения из выбранных modules. CDS переиспользует preprocessed класс метаданные для лучшего запуск и memory use. AOT/native-image approaches компилируют заранее ради faster запуск и иногда smaller deployment, но уменьшают JVM dynamism и могут требовать extra конфигурация.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>These tools are deployment and startup tools, not replacements for understanding normal JVM execution. <code>jlink</code> is useful when you want to ship a minimized runtime instead of a full JDK or generic JRE-like image. CDS can reduce startup and footprint by reusing class metadata across JVM processes or starts.</p>
<p>AOT and native images are attractive for short-lived services, CLIs, serverless and scale-to-zero workloads. For typical long-running backend services, the normal JVM can be better because JIT optimization, mature GC, observability tooling and dynamic framework behavior are valuable.</p>
</td>
<td valign="top" width="50%">
<p>Эти инструменты относятся к deployment и запуск, а не заменяют понимание обычного JVM execution. <code>jlink</code> полезен, когда нужно ship minimized время выполнения вместо full JDK или generic JRE-like image. CDS может уменьшить запуск и footprint за счёт reuse класс метаданные между JVM processes или starts.</p>
<p>AOT и нативный images привлекательны для short-lived сервисы, CLIs, serverless и scale-to-zero workloads. Для обычных long-running backend сервисы normal JVM часто лучше, потому что JIT optimization, mature GC, observability инструменты и динамический фреймворк поведение имеют большую ценность.</p>

</tr>

<p>CDS is less invasive because the application still runs on the JVM. Native-image style AOT is more invasive: reflection, dynamic proxies, resources, JNI, serialization and framework discovery may need explicit metadata or build-time analysis. The resulting binary is platform-specific.</p>
</td>
<td valign="top" width="50%">
<p><code>jlink</code> работает с modules и может убрать unused JDK modules из образ среды выполнения. Это уменьшает image size и attack surface, но также убирает инструменты и APIs, которые не включены.</p>
<p>CDS менее invasive, потому что приложение всё ещё работает на JVM. Native-image style AOT более invasive: reflection, динамические прокси, ресурсы, JNI, сериализация и framework discovery могут требовать явных метаданных или build-time analysis. Получившийся бинарный файл platform-specific.</p>

<td valign="top" width="50%">
