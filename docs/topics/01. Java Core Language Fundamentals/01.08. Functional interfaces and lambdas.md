# 8. Functional interfaces and lambdas

<a id="jcore-func-001"></a>

<details>
<summary><strong>JCORE-FUNC-001. What is a functional interface?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A functional interface is an interface with exactly one abstract method. It can be used as the target type for a lambda expression or method reference. <code>@FunctionalInterface</code> is optional but useful because the compiler checks the intent.</p>
</td>
<td valign="top" width="50%">

<p>Функциональный интерфейс (functional interface) — это интерфейс ровно с одним абстрактным методом. Он может быть целевым типом для лямбда-выражения или ссылки на метод. Аннотация <code>@FunctionalInterface</code> не обязательна, но полезна: компилятор проверяет намерение.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The single abstract method is often called the SAM. Default methods, static methods, and methods from <code>Object</code> do not count as additional abstract methods for this purpose. Examples include <code>Runnable</code>, <code>Callable</code>, <code>Comparator</code>, <code>Predicate</code>, <code>Function</code>, <code>Consumer</code>, and <code>Supplier</code>.</p>
<p>A lambda does not have a standalone type by itself; it is typed by the target functional interface. That is why the same lambda body can match different interfaces if their method signatures are compatible.</p>
</td>
<td valign="top" width="50%">

<p>Единственный абстрактный метод часто называют SAM. Методы по умолчанию, статические методы и методы из <code>Object</code> не считаются дополнительными абстрактными методами. Примеры: <code>Runnable</code>, <code>Callable</code>, <code>Comparator</code>, <code>Predicate</code>, <code>Function</code>, <code>Consumer</code>, <code>Supplier</code>.</p>
<p>У лямбда-выражения нет самостоятельного типа: тип задаётся целевым функциональным интерфейсом. Поэтому одно и то же тело лямбды может подходить разным интерфейсам, если их сигнатуры совместимы.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The compiler uses the target type to infer parameter types, return type, and checked exceptions. This is also why overloads that accept different functional interfaces can become ambiguous when passed a lambda.</p>
</td>
<td valign="top" width="50%">

<p>Компилятор использует целевой тип, чтобы вывести типы параметров, возвращаемый тип и проверяемые исключения. Поэтому перегрузки, принимающие разные функциональные интерфейсы, могут стать неоднозначными, если передать им лямбду.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In backend code, functional interfaces are common in stream pipelines, callbacks, retry policies, validators, mappers, and small extension points. Prefer standard interfaces from <code>java.util.function</code> when their names fit; define a custom interface when the domain meaning or checked exceptions matter.</p>
</td>
<td valign="top" width="50%">

<p>В серверном коде функциональные интерфейсы часто встречаются в потоковых цепочках, обратных вызовах (callbacks), политиках повторов, валидаторах, мапперах и небольших точках расширения. Если смысл подходит, лучше использовать стандартные интерфейсы из <code>java.util.function</code>; если важна доменная семантика или проверяемые исключения, уместен собственный интерфейс.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>@FunctionalInterface</code> is a compile-time check, not a runtime feature.</li>
<li>Adding a second abstract method breaks lambda compatibility.</li>
<li>A lambda can throw only exceptions allowed by the target method signature.</li>
<li>Overloaded methods with similar functional interfaces can make lambdas ambiguous.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>@FunctionalInterface</code> — проверка компилятора, а не механизм времени выполнения.</li>
<li>Добавление второго абстрактного метода ломает совместимость с лямбдами.</li>
<li>Лямбда может выбрасывать только исключения, разрешённые целевой сигнатурой.</li>
<li>Перегрузки с похожими функциональными интерфейсами могут сделать лямбду неоднозначной.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What makes an interface functional?<br>A: Exactly one abstract method, regardless of default or static methods.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что делает интерфейс функциональным?<br>A: Ровно один абстрактный метод, независимо от методов по умолчанию и статических методов.</p>

</td>
</tr>
</tbody>
</table>
</details>


<a id="jcore-func-002"></a>

<details>
<summary><strong>JCORE-FUNC-002. What is the difference between a lambda and an anonymous class?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A lambda is an expression that implements a functional interface more directly and has lexical <code>this</code>. An anonymous class creates a real anonymous class instance with its own <code>this</code>, can have fields and multiple methods, and can implement or extend types in a more class-like way.</p>
</td>
<td valign="top" width="50%">

<p>Лямбда — это выражение для реализации функционального интерфейса, причём <code>this</code> внутри неё относится к внешнему объекту. Анонимный класс создаёт отдельный объект анонимного класса со своим <code>this</code>, может иметь поля и несколько методов и ведёт себя ближе к обычному классу.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A lambda is not just shorter syntax for every anonymous class. It can only target a functional interface. It does not introduce a new scope for <code>this</code> in the same way, and local variables captured by a lambda must be final or effectively final.</p>
<p>An anonymous class is useful when you need object identity, additional helper methods or fields, a distinct <code>this</code>, or to extend a class rather than implement a functional interface.</p>
</td>
<td valign="top" width="50%">

<p>Лямбда — не просто короткая запись любого анонимного класса. Она может соответствовать только функциональному интерфейсу. Она иначе трактует <code>this</code>, а захваченные локальные переменные должны быть <code>final</code> или фактически финальными.</p>
<p>Анонимный класс полезен, если нужна собственная идентичность объекта, дополнительные поля или вспомогательные методы, отдельный <code>this</code> либо расширение класса, а не только реализация функционального интерфейса.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>At runtime, lambdas are typically implemented through <code>invokedynamic</code> and JVM-managed machinery, while anonymous classes produce class-like artifacts. Code should not depend on lambda identity, generated class names, or serialization details.</p>
</td>
<td valign="top" width="50%">

<p>Во время выполнения лямбды обычно реализуются через <code>invokedynamic</code> и механизм JVM, а анонимные классы выглядят как отдельные классы. Код не должен зависеть от идентичности лямбды, имени сгенерированного класса или деталей сериализации.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For business code, lambdas are excellent for short behavior passed to APIs. If the logic grows, needs state, or deserves a name for observability and testing, extract a named class or method instead of hiding it in a large lambda.</p>
</td>
<td valign="top" width="50%">

<p>В прикладном коде лямбды хороши для короткого поведения, передаваемого в API. Если логика растёт, требует состояния или заслуживает отдельного имени для наблюдаемости и тестов, лучше вынести её в именованный метод или класс.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Inside a lambda, <code>this</code> is the enclosing instance; inside an anonymous class, <code>this</code> is the anonymous object.</li>
<li>Anonymous classes can declare fields; lambdas cannot.</li>
<li>A lambda can target only a functional interface.</li>
<li>Do not rely on lambda object identity or generated implementation details.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>В лямбде <code>this</code> — внешний объект; в анонимном классе <code>this</code> — сам анонимный объект.</li>
<li>Анонимный класс может объявлять поля, лямбда — нет.</li>
<li>Лямбда подходит только функциональному интерфейсу.</li>
<li>Не опирайтесь на идентичность объекта лямбды или детали её реализации.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Is a lambda the same as an anonymous class?<br>A: No; it has different <code>this</code>, scoping, target-type, and implementation semantics.</p>
</td>
<td valign="top" width="50%">

<p>Q: Лямбда — то же самое, что анонимный класс?<br>A: Нет; у неё другие правила для <code>this</code>, области видимости, целевого типа и реализации.</p>

</td>
</tr>
</tbody>
</table>
</details>


<a id="jcore-func-003"></a>

<details>
<summary><strong>JCORE-FUNC-003. What does effectively final mean for variables captured by lambdas?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A local variable captured by a lambda must be final or effectively final: after initialization, the variable itself is not reassigned. The referenced object may still be mutable, but the local variable reference cannot change.</p>
</td>
<td valign="top" width="50%">

<p>Локальная переменная, захваченная лямбдой, должна быть <code>final</code> или фактически финальной: после инициализации сама переменная не переназначается. Объект, на который она ссылается, может оставаться изменяемым, но ссылка в локальной переменной не меняется.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The rule exists because lambdas can outlive the stack frame where a local variable was declared. Java captures the value of the local variable, not a live mutable local slot. Reassignment would create confusing semantics and visibility issues.</p>
<p>For example, <code>int count = 0; list.forEach(x -> count++);</code> does not compile because <code>count</code> would need reassignment. Using a mutable holder can compile, but it may be a design smell and can be unsafe in parallel code.</p>
</td>
<td valign="top" width="50%">

<p>Правило нужно потому, что лямбда может пережить стековый кадр, где объявлена локальная переменная. Java захватывает значение локальной переменной, а не живую изменяемую ячейку стека. Переназначение создало бы неясную семантику и проблемы видимости.</p>
<p>Например, <code>int count = 0; list.forEach(x -> count++);</code> не компилируется, потому что <code>count</code> пришлось бы переназначать. Изменяемый контейнер может обойти запрет, но часто это признак неудачного дизайна и риск в параллельном коде.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Effectively final is about the variable, not object immutability. Capturing <code>List&lt;String&gt; names</code> and mutating the list is allowed if the variable <code>names</code> is not reassigned. That can still make code harder to reason about.</p>
</td>
<td valign="top" width="50%">

<p>Фактическая финальность относится к переменной, а не к неизменяемости объекта. Можно захватить <code>List&lt;String&gt; names</code> и менять сам список, если переменная <code>names</code> не переназначается. Но такой код всё равно труднее понимать.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production code, prefer returning values through stream reductions or collectors instead of mutating captured holders. If shared mutable state is unavoidable, use proper synchronization or thread-safe structures and document why.</p>
</td>
<td valign="top" width="50%">

<p>В промышленном коде лучше возвращать результат через свёртки или коллекторы, а не менять захваченные контейнеры. Если общее изменяемое состояние неизбежно, нужны синхронизация или потокобезопасные структуры и явное объяснение причины.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Effectively final does not mean deeply immutable.</li>
<li>A captured mutable object can still be modified.</li>
<li>Mutable holders used to bypass the rule often break parallel streams.</li>
<li>Fields are different from local variables; lambdas can access mutable instance fields, which has its own risks.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Фактически финальная переменная не означает глубоко неизменяемый объект.</li>
<li>Захваченный изменяемый объект всё ещё можно менять.</li>
<li>Изменяемые контейнеры для обхода правила часто ломают параллельные потоки.</li>
<li>Поля отличаются от локальных переменных: лямбда может обращаться к изменяемым полям объекта, но это отдельный риск.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does effectively final mean?<br>A: The local variable is not declared final but is never reassigned after initialization.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что значит «фактически финальная» переменная?<br>A: Она не объявлена как <code>final</code>, но после инициализации ни разу не переназначается.</p>

</td>
</tr>
</tbody>
</table>

<a id="jcore-func-004"></a>

<details>
<summary><strong>JCORE-FUNC-004. Why are checked exceptions awkward in lambdas?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A lambda may throw only the checked exceptions declared by the abstract method of its target functional interface. Many standard interfaces in <code>java.util.function</code> do not declare checked exceptions, so lambdas used with them cannot throw checked exceptions directly.</p>
</td>
<td valign="top" width="50%">

<p>Лямбда может выбрасывать только те проверяемые исключения, которые объявлены в абстрактном методе её целевого функционального интерфейса. Многие стандартные интерфейсы из <code>java.util.function</code> не объявляют проверяемые исключения, поэтому такая лямбда не может выбросить их напрямую.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For example, <code>Function&lt;Path, String&gt;</code> cannot directly call an API that throws <code>IOException</code> unless the lambda catches it or wraps it. This becomes visible in stream pipelines, where operations like <code>map</code> use standard functional interfaces.</p>
<p>Common solutions are to catch and wrap the exception, move the throwing logic into a named method that handles it, use a custom throwing functional interface, or avoid a stream pipeline when ordinary control flow is clearer.</p>
</td>
<td valign="top" width="50%">

<p>Например, <code>Function&lt;Path, String&gt;</code> не может напрямую вызвать API, выбрасывающее <code>IOException</code>, если лямбда не перехватит или не завернёт исключение. Это часто проявляется в потоковых цепочках, где <code>map</code> принимает стандартный функциональный интерфейс.</p>
<p>Обычные решения: перехватить и завернуть исключение, вынести логику в именованный метод, использовать собственный функциональный интерфейс с проверяемым исключением или отказаться от потока там, где обычный цикл понятнее.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The awkwardness comes from combining Java's checked exception model with generic higher-order APIs. A stream pipeline does not have a built-in way to say “each element mapping may throw <code>IOException</code>” unless the target interface declares it.</p>
</td>
<td valign="top" width="50%">

<p>Сложность возникает из сочетания проверяемых исключений Java с обобщёнными API высшего порядка. Потоковая цепочка не умеет сама выразить «преобразование каждого элемента может выбросить <code>IOException</code>», если целевой интерфейс этого не объявляет.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In backend code, wrapping checked exceptions into domain-specific unchecked exceptions can be reasonable at boundaries, but do not hide important failure context. For batch processing, decide whether one failed element should stop the pipeline, be collected as an error, or be retried.</p>
</td>
<td valign="top" width="50%">

<p>В серверном коде на границах слоя иногда разумно заворачивать проверяемые исключения в доменные непроверяемые. Но нельзя терять важный контекст ошибки. В пакетной обработке нужно явно решить, должен ли один неудачный элемент остановить цепочку, попасть в список ошибок или уйти на повтор.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not use generic <code>RuntimeException</code> wrappers that hide the cause.</li>
<li>Avoid “sneaky throws” tricks in ordinary application code.</li>
<li>A stream is not always clearer than a loop when exception handling is central.</li>
<li>Custom throwing interfaces help locally but do not integrate magically with standard stream methods.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не заворачивайте всё в безликий <code>RuntimeException</code> без причины и контекста.</li>
<li>Не используйте трюки со «скрытым выбрасыванием» в обычном прикладном коде.</li>
<li>Если обработка ошибок — центральная часть логики, цикл может быть понятнее потока.</li>
<li>Собственный интерфейс с проверяемым исключением помогает локально, но не меняет стандартные методы Stream API.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why can <code>map(path -> Files.readString(path))</code> fail to compile?<br>A: <code>Files.readString</code> throws <code>IOException</code>, but <code>Function.apply</code> does not declare it.</p>
</td>
<td valign="top" width="50%">

<p>Q: Почему <code>map(path -> Files.readString(path))</code> может не компилироваться?<br>A: <code>Files.readString</code> выбрасывает <code>IOException</code>, а <code>Function.apply</code> его не объявляет.</p>

</td>
</tr>
</tbody>

<a id="jcore-func-005"></a>

<details>
<summary><strong>JCORE-FUNC-005. Why can side effects inside lambdas make code harder to reason about?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Side effects make lambdas depend on more than their input and output. Mutating external state, doing I/O, logging too much, or updating shared counters can make evaluation order, retries, laziness, and concurrency behavior surprising.</p>
</td>
<td valign="top" width="50%">

<p>Побочные эффекты (side effects) заставляют лямбду зависеть не только от входа и выхода. Изменение внешнего состояния, ввод-вывод, чрезмерное логирование или обновление общих счётчиков делают порядок вычислений, повторы, ленивость и многопоточность менее очевидными.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Many APIs that accept lambdas, especially streams, are designed around transformations. A pure mapping like <code>x -> normalize(x)</code> is easy to reason about. A mapping that also writes to a list, increments a shared counter, or calls a remote service is much harder.</p>
<p>In sequential code this can already be confusing. In parallel streams or asynchronous callbacks, side effects can become race conditions, duplicate operations, inconsistent metrics, or tests that pass only by accident.</p>
</td>
<td valign="top" width="50%">

<p>Многие API, принимающие лямбды, особенно Stream API, рассчитаны на преобразования. Чистое преобразование вроде <code>x -> normalize(x)</code> легко понимать. А преобразование, которое заодно пишет в список, увеличивает общий счётчик или вызывает внешний сервис, уже существенно сложнее.</p>
<p>Даже в последовательном коде это запутывает. В параллельных потоках или асинхронных обратных вызовах (callbacks) побочные эффекты могут превратиться в гонки данных, дублирующиеся операции, неконсистентные метрики или случайно проходящие тесты.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The issue is not that side effects are always wrong; backend code must perform I/O. The issue is hiding side effects inside expressions that look like simple transformations. Side effects should be explicit and placed where ordering, error handling, and retries are clear.</p>
</td>
<td valign="top" width="50%">

<p>Проблема не в том, что побочные эффекты всегда запрещены: серверный код обязан выполнять ввод-вывод. Проблема в том, что они прячутся внутри выражений, похожих на простые преобразования. Побочные эффекты должны быть видны там, где понятны порядок, обработка ошибок и повторы.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For production streams, prefer collectors over mutating external collections, explicit loops for complex workflows, and idempotent operations when retries are possible. Keep remote calls out of parallel streams unless concurrency, backpressure, and failure behavior are designed.</p>
</td>
<td valign="top" width="50%">

<p>В боевых потоковых цепочках лучше использовать коллекторы вместо изменения внешних коллекций, обычные циклы для сложных сценариев и идемпотентные операции там, где возможны повторы. Удалённые вызовы не стоит прятать в параллельные потоки без продуманной конкуренции, обратного давления (backpressure) и обработки сбоев.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>forEach</code> that mutates external state is often a smell.</li>
<li>Parallel streams require thread-safe and non-interfering operations.</li>
<li>Lazy evaluation means side effects may run later than expected or not at all without a terminal operation.</li>
<li>Retries can duplicate non-idempotent side effects.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>forEach</code>, который меняет внешнее состояние, часто является тревожным признаком.</li>
<li>Параллельные потоки требуют потокобезопасных операций без вмешательства во внешний источник.</li>
<li>Из-за ленивых вычислений побочный эффект может выполниться позже ожидаемого или не выполниться без терминальной операции.</li>
<li>Повторы могут продублировать неидемпотентный побочный эффект.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why prefer pure lambdas in transformations?<br>A: They make behavior depend only on input and output, which is easier to test and parallelize.</p>
</td>
<td valign="top" width="50%">

<p>Q: Почему в преобразованиях лучше чистые лямбды?<br>A: Их поведение зависит только от входа и выхода, поэтому их проще тестировать и распараллеливать.</p>

</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>JCORE-FUNC-006. What are method references, and when do they improve readability?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A method reference is compact syntax for a lambda that only calls an existing method or constructor. It improves readability when the referenced method name clearly expresses the operation, for example <code>User::getId</code> or <code>String::trim</code>.</p>
</td>
<td valign="top" width="50%">

<p>Ссылка на метод (method reference) — компактная запись лямбды, которая только вызывает существующий метод или конструктор. Она улучшает читаемость, когда имя метода ясно выражает действие, например <code>User::getId</code> или <code>String::trim</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Common forms are <code>Type::staticMethod</code>, <code>object::instanceMethod</code>, <code>Type::instanceMethod</code>, and <code>Type::new</code>. The compiler adapts the method reference to the target functional interface just as it does for lambdas.</p>
<p>A method reference is best when it removes noise. <code>users.stream().map(User::email)</code> can be clearer than <code>u -> u.email()</code>. But if the lambda contains meaningful parameter names or extra logic, an explicit lambda can be more readable.</p>
</td>
<td valign="top" width="50%">

<p>Основные формы: <code>Type::staticMethod</code>, <code>object::instanceMethod</code>, <code>Type::instanceMethod</code> и <code>Type::new</code>. Компилятор подгоняет ссылку на метод под целевой функциональный интерфейс так же, как лямбду.</p>
<p>Ссылка на метод хороша, когда убирает шум. <code>users.stream().map(User::email)</code> может быть понятнее, чем <code>u -> u.email()</code>. Но если имена параметров важны или внутри есть дополнительная логика, явная лямбда часто читается лучше.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Method references participate in overload resolution through the target type. This means they can become ambiguous when multiple overloads or generic methods match. In that case, use an explicit lambda, cast the target type, or split the expression.</p>
</td>
<td valign="top" width="50%">

<p>Ссылки на методы участвуют в разрешении перегрузки через целевой тип. Поэтому они могут стать неоднозначными, если подходят несколько перегрузок или обобщённых методов. В таком случае используют явную лямбду, приведение к целевому типу или разбивают выражение.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production code, use method references for straightforward mapping, filtering, sorting, and construction. Avoid clever chains where the reader has to mentally reconstruct argument binding; clarity is more important than saving a few characters.</p>
</td>
<td valign="top" width="50%">

<p>В промышленном коде ссылки на методы хорошо подходят для простого отображения, фильтрации, сортировки и создания объектов. Не стоит строить слишком хитрые цепочки, где читателю приходится восстанавливать привязку аргументов в голове: ясность важнее нескольких сэкономленных символов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>A method reference is not automatically clearer than a lambda.</li>
<li>Overloaded method names can make references ambiguous.</li>
<li>Constructor references can hide which constructor overload is selected.</li>
<li>If parameter names explain intent, keep the lambda.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Ссылка на метод не всегда понятнее лямбды.</li>
<li>Перегруженные методы могут сделать ссылку неоднозначной.</li>
<li>Ссылка на конструктор может скрыть выбранную перегрузку.</li>
<li>Если имена параметров объясняют смысл, лучше оставить лямбду.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: When does a method reference help?<br>A: When an existing method name clearly states exactly what the lambda would do.</p>
</td>
<td valign="top" width="50%">

<p>Q: Когда ссылка на метод помогает?<br>A: Когда имя существующего метода ясно говорит, что сделала бы лямбда.</p>

</td>
</tr>

<a id="jcore-func-007"></a>

<details>
<summary><strong>🧠 JCORE-FUNC-007. What does <code>this</code> refer to inside a lambda versus inside an anonymous class?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Inside a lambda, <code>this</code> refers to the enclosing instance. Inside an anonymous class, <code>this</code> refers to the anonymous class instance itself.</p>
</td>
<td valign="top" width="50%">

<p>Внутри лямбды <code>this</code> относится к внешнему объекту. Внутри анонимного класса <code>this</code> относится к самому объекту анонимного класса.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>This is one of the most important semantic differences. A lambda has lexical scoping for <code>this</code>, so calling <code>this.someMethod()</code> calls a method on the surrounding object. An anonymous class introduces a new inner object; <code>this.someMethod()</code> refers to that object.</p>
<p>If an anonymous class needs the outer object explicitly, Java uses <code>OuterClass.this</code>. In a lambda, that qualification is usually unnecessary because plain <code>this</code> already means the outer instance.</p>
</td>
<td valign="top" width="50%">

<p>Это одно из главных семантических отличий. У лямбды лексическая область видимости для <code>this</code>: вызов <code>this.someMethod()</code> обращается к окружающему объекту. Анонимный класс создаёт новый внутренний объект, и <code>this.someMethod()</code> относится к нему.</p>
<p>Если анонимному классу нужен внешний объект, используется запись <code>OuterClass.this</code>. В лямбде обычно она не нужна, потому что обычный <code>this</code> уже указывает на внешний экземпляр.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The difference affects equality, logging, callbacks, and lifecycle code. Passing <code>this</code> from a lambda passes the enclosing object; passing <code>this</code> from an anonymous class passes the callback object.</p>
</td>
<td valign="top" width="50%">

<p>Это различие влияет на равенство, логирование, обратные вызовы (callbacks) и код жизненного цикла. Если передать <code>this</code> из лямбды, уйдёт внешний объект; если из анонимного класса — объект обратного вызова.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In backend code, avoid large inline callbacks where <code>this</code> is easy to misread. A named method reference or a separate class can make ownership and lifecycle much clearer.</p>
</td>
<td valign="top" width="50%">

<p>В серверном коде лучше избегать больших встроенных обратных вызовов, где легко неверно прочитать <code>this</code>. Ссылка на именованный метод или отдельный класс часто яснее показывает владельца и жизненный цикл.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not assume a lambda creates a new <code>this</code> scope.</li>
<li>Anonymous classes can accidentally capture the outer instance and extend its lifetime.</li>
<li>In nested code, use explicit names or extraction if <code>this</code> becomes unclear.</li>
<li>This difference is visible in stack traces and logging context.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не считайте, что лямбда создаёт новую область <code>this</code>.</li>
<li>Анонимные классы могут случайно удерживать внешний объект дольше нужного.</li>
<li>Во вложенном коде лучше дать явные имена или вынести код, если <code>this</code> становится неясным.</li>
<li>Различие видно в трассировках стека и контексте логирования.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is <code>this</code> in a lambda?<br>A: The enclosing instance, not a new lambda object.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что означает <code>this</code> в лямбде?<br>A: Внешний экземпляр, а не новый объект лямбды.</p>

</td>
</tr>
