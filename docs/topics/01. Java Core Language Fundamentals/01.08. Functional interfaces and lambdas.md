# 01.08. Functional interfaces and lambdas

---

<a id="jcore-func-001"></a>

<details>
<summary><strong>JCORE-FUNC-001. What is a functional interface?</strong></summary>

#### Short answer

A functional interface is an interface with exactly one abstract method. It can be used as the target type for a lambda expression or method reference. `@FunctionalInterface` is optional but useful because the compiler checks the intent.

#### Interview answer

The single abstract method is often called the SAM. Default methods, static methods, and methods from `Object` do not count as additional abstract methods for this purpose. Examples include `Runnable`, `Callable`, `Comparator`, `Predicate`, `Function`, `Consumer`, and `Supplier`.

A lambda does not have a standalone type by itself; it is typed by the target functional interface. That is why the same lambda body can match different interfaces if their method signatures are compatible.

#### Deep dive

The compiler uses the target type to infer parameter types, return type, and checked exceptions. This is also why overloads that accept different functional interfaces can become ambiguous when passed a lambda.

#### Production angle

In backend code, functional interfaces are common in stream pipelines, callbacks, retry policies, validators, mappers, and small extension points. Prefer standard interfaces from `java.util.function` when their names fit; define a custom interface when the domain meaning or checked exceptions matter.

#### Traps / caveats

- `@FunctionalInterface` is a compile-time check, not a runtime feature.
- Adding a second abstract method breaks lambda compatibility.
- A lambda can throw only exceptions allowed by the target method signature.
- Overloaded methods with similar functional interfaces can make lambdas ambiguous.

#### Optional Anki

Q: What makes an interface functional?
A: Exactly one abstract method, regardless of default or static methods.

</details>

<details>
<summary><strong>JCORE-FUNC-002. What is the difference between a lambda and an anonymous class?</strong></summary>

#### Short answer

A lambda is an expression that implements a functional interface more directly and has lexical `this`. An anonymous class creates a real anonymous class instance with its own `this`, can have fields and multiple methods, and can implement or extend types in a more class-like way.

#### Interview answer

A lambda is not just shorter syntax for every anonymous class. It can only target a functional interface. It does not introduce a new scope for `this` in the same way, and local variables captured by a lambda must be final or effectively final.

An anonymous class is useful when you need object identity, additional helper methods or fields, a distinct `this`, or to extend a class rather than implement a functional interface.

#### Deep dive

At runtime, lambdas are typically implemented through `invokedynamic` and JVM-managed machinery, while anonymous classes produce class-like artifacts. Code should not depend on lambda identity, generated class names, or serialization details.

#### Production angle

For business code, lambdas are excellent for short behavior passed to APIs. If the logic grows, needs state, or deserves a name for observability and testing, extract a named class or method instead of hiding it in a large lambda.

#### Traps / caveats

- Inside a lambda, `this` is the enclosing instance; inside an anonymous class, `this` is the anonymous object.
- Anonymous classes can declare fields; lambdas cannot.
- A lambda can target only a functional interface.
- Do not rely on lambda object identity or generated implementation details.

#### Optional Anki

Q: Is a lambda the same as an anonymous class?
A: No; it has different `this`, scoping, target-type, and implementation semantics.

</details>

<details>
<summary><strong>JCORE-FUNC-003. What does effectively final mean for variables captured by lambdas?</strong></summary>

#### Short answer

A local variable captured by a lambda must be final or effectively final: after initialization, the variable itself is not reassigned. The referenced object may still be mutable, but the local variable reference cannot change.

#### Interview answer

The rule exists because lambdas can outlive the stack frame where a local variable was declared. Java captures the value of the local variable, not a live mutable local slot. Reassignment would create confusing semantics and visibility issues.

For example, `int count = 0; list.forEach(x -> count++);` does not compile because `count` would need reassignment. Using a mutable holder can compile, but it may be a design smell and can be unsafe in parallel code.

#### Deep dive

Effectively final is about the variable, not object immutability. Capturing `List<String> names` and mutating the list is allowed if the variable `names` is not reassigned. That can still make code harder to reason about.

#### Production angle

In production code, prefer returning values through stream reductions or collectors instead of mutating captured holders. If shared mutable state is unavoidable, use proper synchronization or thread-safe structures and document why.

#### Traps / caveats

- Effectively final does not mean deeply immutable.
- A captured mutable object can still be modified.
- Mutable holders used to bypass the rule often break parallel streams.
- Fields are different from local variables; lambdas can access mutable instance fields, which has its own risks.

#### Optional Anki

Q: What does effectively final mean?
A: The local variable is not declared final but is never reassigned after initialization.

</details>

<details>
<summary><strong>JCORE-FUNC-004. Why are checked exceptions awkward in lambdas?</strong></summary>

#### Short answer

A lambda may throw only the checked exceptions declared by the abstract method of its target functional interface. Many standard interfaces in `java.util.function` do not declare checked exceptions, so lambdas used with them cannot throw checked exceptions directly.

#### Interview answer

For example, `Function<Path, String>` cannot directly call an API that throws `IOException` unless the lambda catches it or wraps it. This becomes visible in stream pipelines, where operations like `map` use standard functional interfaces.

Common solutions are to catch and wrap the exception, move the throwing logic into a named method that handles it, use a custom throwing functional interface, or avoid a stream pipeline when ordinary control flow is clearer.

#### Deep dive

The awkwardness comes from combining Java's checked exception model with generic higher-order APIs. A stream pipeline does not have a built-in way to say “each element mapping may throw `IOException`” unless the target interface declares it.

#### Production angle

In backend code, wrapping checked exceptions into domain-specific unchecked exceptions can be reasonable at boundaries, but do not hide important failure context. For batch processing, decide whether one failed element should stop the pipeline, be collected as an error, or be retried.

#### Traps / caveats

- Do not use generic `RuntimeException` wrappers that hide the cause.
- Avoid “sneaky throws” tricks in ordinary application code.
- A stream is not always clearer than a loop when exception handling is central.
- Custom throwing interfaces help locally but do not integrate magically with standard stream methods.

#### Optional Anki

Q: Why can `map(path -> Files.readString(path))` fail to compile?
A: `Files.readString` throws `IOException`, but `Function.apply` does not declare it.

</details>

<details>
<summary><strong>JCORE-FUNC-005. Why can side effects inside lambdas make code harder to reason about?</strong></summary>

#### Short answer

Side effects make lambdas depend on more than their input and output. Mutating external state, doing I/O, logging too much, or updating shared counters can make evaluation order, retries, laziness, and concurrency behavior surprising.

#### Interview answer

Many APIs that accept lambdas, especially streams, are designed around transformations. A pure mapping like `x -> normalize(x)` is easy to reason about. A mapping that also writes to a list, increments a shared counter, or calls a remote service is much harder.

In sequential code this can already be confusing. In parallel streams or asynchronous callbacks, side effects can become race conditions, duplicate operations, inconsistent metrics, or tests that pass only by accident.

#### Deep dive

The issue is not that side effects are always wrong; backend code must perform I/O. The issue is hiding side effects inside expressions that look like simple transformations. Side effects should be explicit and placed where ordering, error handling, and retries are clear.

#### Production angle

For production streams, prefer collectors over mutating external collections, explicit loops for complex workflows, and idempotent operations when retries are possible. Keep remote calls out of parallel streams unless concurrency, backpressure, and failure behavior are designed.

#### Traps / caveats

- `forEach` that mutates external state is often a smell.
- Parallel streams require thread-safe and non-interfering operations.
- Lazy evaluation means side effects may run later than expected or not at all without a terminal operation.
- Retries can duplicate non-idempotent side effects.

#### Optional Anki

Q: Why prefer pure lambdas in transformations?
A: They make behavior depend only on input and output, which is easier to test and parallelize.

</details>

<details>
<summary><strong>JCORE-FUNC-006. What are method references, and when do they improve readability?</strong></summary>

#### Short answer

A method reference is compact syntax for a lambda that only calls an existing method or constructor. It improves readability when the referenced method name clearly expresses the operation, for example `User::getId` or `String::trim`.

#### Interview answer

Common forms are `Type::staticMethod`, `object::instanceMethod`, `Type::instanceMethod`, and `Type::new`. The compiler adapts the method reference to the target functional interface just as it does for lambdas.

A method reference is best when it removes noise. `users.stream().map(User::email)` can be clearer than `u -> u.email()`. But if the lambda contains meaningful parameter names or extra logic, an explicit lambda can be more readable.

#### Deep dive

Method references participate in overload resolution through the target type. This means they can become ambiguous when multiple overloads or generic methods match. In that case, use an explicit lambda, cast the target type, or split the expression.

#### Production angle

In production code, use method references for straightforward mapping, filtering, sorting, and construction. Avoid clever chains where the reader has to mentally reconstruct argument binding; clarity is more important than saving a few characters.

#### Traps / caveats

- A method reference is not automatically clearer than a lambda.
- Overloaded method names can make references ambiguous.
- Constructor references can hide which constructor overload is selected.
- If parameter names explain intent, keep the lambda.

#### Optional Anki

Q: When does a method reference help?
A: When an existing method name clearly states exactly what the lambda would do.

</details>

<details>
<summary><strong>🧠 JCORE-FUNC-007. What does `this` refer to inside a lambda versus inside an anonymous class?</strong></summary>

#### Short answer

Inside a lambda, `this` refers to the enclosing instance. Inside an anonymous class, `this` refers to the anonymous class instance itself.

#### Interview answer

This is one of the most important semantic differences. A lambda has lexical scoping for `this`, so calling `this.someMethod()` calls a method on the surrounding object. An anonymous class introduces a new inner object; `this.someMethod()` refers to that object.

If an anonymous class needs the outer object explicitly, Java uses `OuterClass.this`. In a lambda, that qualification is usually unnecessary because plain `this` already means the outer instance.

#### Deep dive

The difference affects equality, logging, callbacks, and lifecycle code. Passing `this` from a lambda passes the enclosing object; passing `this` from an anonymous class passes the callback object.

#### Production angle

In backend code, avoid large inline callbacks where `this` is easy to misread. A named method reference or a separate class can make ownership and lifecycle much clearer.

#### Traps / caveats

- Do not assume a lambda creates a new `this` scope.
- Anonymous classes can accidentally capture the outer instance and extend its lifetime.
- In nested code, use explicit names or extraction if `this` becomes unclear.
- This difference is visible in stack traces and logging context.

#### Optional Anki

Q: What is `this` in a lambda?
A: The enclosing instance, not a new lambda object.

</details>
