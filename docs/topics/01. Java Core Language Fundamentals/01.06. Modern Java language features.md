# 6. Modern Java language features


<a id="jcore-modern-001"></a>

<details>
<summary><strong>JCORE-MODERN-001. What problem does <code>Optional</code> solve, and how should it be used?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>Optional&lt;T&gt;</code> represents an expected possible absence of a single return value. It makes absence explicit in the method signature and encourages callers to handle both cases instead of accidentally dereferencing <code>null</code>. It is best used as a return type, not as a universal null replacement.</p>
</td>
<td valign="top" width="50%">

<p><code>Optional</code> явно показывает ожидаемое отсутствие значения, в первую очередь как возвращаемый тип метода. Его стоит использовать для результата, который может отсутствовать, а не как универсальную замену <code>null</code> во всех местах программы.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A good use is <code>findUser(id): Optional&lt;User&gt;</code>, where “not found” is a normal outcome. The caller can use <code>map</code>, <code>flatMap</code>, <code>orElseThrow</code>, <code>orElseGet</code>, or <code>ifPresent</code> to handle absence explicitly.</p>
<p>Optional is not primarily about avoiding all nulls internally. It is an API signal. It tells the reader: this method may return no value, and that case is part of the contract, not an exceptional failure.</p>
</td>
<td valign="top" width="50%">

<p><code>Optional&lt;T&gt;</code> помогает отличить «метод может ничего не найти» от ошибки или обычного объекта. Клиент видит это в сигнатуре и вынужден явно обработать случай отсутствия: <code>map</code>, <code>flatMap</code>, <code>orElseGet</code>, <code>orElseThrow</code> или <code>ifPresent</code>.</p>
<p>Хороший стиль — возвращать <code>Optional</code> из методов поиска, где отсутствие является нормальным исходом. Плохой стиль — сразу вызывать <code>get()</code> без проверки: это возвращает нас к той же проблеме, только с другим исключением.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use <code>Optional.empty()</code> for absence and <code>Optional.ofNullable(value)</code> when adapting possibly-null values. Use <code>Optional.of(value)</code> only when value must be non-null and a null should fail fast.</p>
<p>Avoid calling <code>get()</code> without checking. It turns Optional back into a nullable-like trap, except with <code>NoSuchElementException</code>. Prefer terminal operations that express the fallback or failure behavior.</p>
</td>
<td valign="top" width="50%">

<p><code>Optional</code> — это контейнер для одного возможного значения, а не коллекция и не механизм обработки ошибок. Если нужно вернуть причину отказа, лучше использовать исключение, результат с кодом ошибки или отдельный доменный тип.</p>
<p>В цепочках преобразований <code>map</code> применяет функцию к значению, если оно есть, а <code>flatMap</code> нужен, когда функция сама возвращает <code>Optional</code>. Для дорогого запасного значения обычно выбирают <code>orElseGet</code>, чтобы вычислять его лениво.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In backend APIs, Optional is useful for repository lookups and computations where absence is normal. For REST/JSON DTOs, entities and fields, check framework support and team conventions; explicit nullable annotations may be clearer.</p>
</td>
<td valign="top" width="50%">

<p>В серверном API <code>Optional</code> хорошо работает на границах поиска: <code>findById</code>, поиск конфигурации, необязательная связанная сущность. Он делает контракт заметным и уменьшает случайные <code>NullPointerException</code>, если команда использует его дисциплинированно.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Optional should not be used just to avoid thinking about nullability.</li>
<li>Do not return <code>null</code> from a method declared to return Optional.</li>
<li>Avoid <code>optional.get()</code> without a presence check.</li>
<li>For collections, returning an empty collection is usually better than <code>Optional&lt;List&lt;T&gt;&gt;</code>.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не вызывайте <code>Optional.get()</code> без предварительной проверки.</li>
<li><code>Optional</code> не должен сам быть <code>null</code>.</li>
<li>Не используйте <code>Optional</code> для ошибок, где нужна причина отказа.</li>
<li>Возвращайте пустой <code>Optional</code>, а не <code>null</code>, если сигнатура уже говорит <code>Optional</code>.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the best common use of <code>Optional</code>?<br>A: As a return type for an expected absent-or-present single value.</p>
</td>
<td valign="top" width="50%">

<p>Q: Где <code>Optional</code> обычно наиболее уместен?<br>A: В возвращаемом типе метода, когда отсутствие значения является ожидаемым результатом.</p>

</td>
</tr>
</tbody>
</table>

<a id="jcore-modern-002"></a>

<details>
<summary><strong>JCORE-MODERN-002. When should <code>Optional</code> not be used?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Avoid Optional for fields, DTO properties, entity attributes, method parameters, collections that can simply be empty, and performance-critical hot paths unless there is a clear benefit. It is mainly intended to communicate optional return values.</p>
</td>
<td valign="top" width="50%">

<p><code>Optional</code> обычно не стоит использовать для полей, параметров методов, элементов коллекций и DTO, предназначенных для сериализации или ORM. Он лучше всего работает как возвращаемый тип, а не как способ заменить все возможные <code>null</code> в объектной модели.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Optional parameters often make APIs awkward: callers must wrap values, and the method still needs to define what absence means. Overloading, separate methods, nullable annotations, or a parameter object can be clearer.</p>
<p>Optional fields can also cause friction with serializers, ORMs and validation frameworks. Some support it, some need configuration, and some produce awkward JSON or persistence models. For DTOs, explicit nullability rules may be more interoperable.</p>
</td>
<td valign="top" width="50%">

<p>Параметр типа <code>Optional</code> часто ухудшает API: вызывающему коду приходится оборачивать значение, хотя проще иметь два метода, перегрузку или явно разрешить <code>null</code> с документацией. Поля типа <code>Optional</code> могут плохо сочетаться с сериализацией, JPA и JavaBean-инструментами.</p>
<p>Коллекция из <code>Optional</code> почти всегда хуже, чем коллекция только присутствующих значений или отдельная структура результата. Если в списке много «пустых» элементов, это часто признак, что модель данных выбрана неудачно.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Do not use <code>Optional&lt;List&lt;T&gt;&gt;</code> when an empty list means “no results”. Use Optional only when there is a real distinction between “no value” and “a present empty value”.</p>
<p>Do not store Optional in collections as a routine practice. A collection of optionals often means the model is unclear; filter absent values or use a richer domain type.</p>
</td>
<td valign="top" width="50%">

<p><code>Optional</code> не делает объект автоматически безопасным от <code>null</code>. Можно всё равно присвоить <code>null</code> самой переменной типа <code>Optional</code>. Поэтому нужны соглашения команды, аннотации допустимости <code>null</code> (nullability) и понятные контракты API.</p>
<p>Для обязательных полей используйте обычные типы и проверку в конструкторе. Для необязательных полей в сериализуемых DTO часто лучше обычное поле с явным контрактом nullability или отдельная модель запроса/ответа.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Team consistency matters. Pick conventions for API boundaries, persistence models and JSON contracts. Use Optional where it improves the contract; otherwise use explicit validation, annotations and clear defaults.</p>
</td>
<td valign="top" width="50%">

<p>В сервисах особенно важно не смешивать стили. Если репозиторий возвращает <code>Optional&lt;Entity&gt;</code>, это понятно. Если вся доменная модель заполнена полями <code>Optional</code>, код становится шумным и плохо работает с фреймворками.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Optional is not serializable-friendly in every framework/use case.</li>
<li>Optional parameters often reduce readability.</li>
<li>Optional fields can confuse ORM and JSON mapping.</li>
<li>Empty collections are usually better than optional collections.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>Optional</code> как параметр часто делает вызовы громоздкими.</li>
<li><code>Optional</code> в JPA-сущностях и DTO может ломать инструменты сериализации или маппинга.</li>
<li>Не кладите <code>Optional</code> внутрь коллекции без очень веской причины.</li>
<li><code>Optional</code> не заменяет документацию и аннотации допустимости <code>null</code> (nullability).</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Should Optional usually be used for method parameters?<br>A: Usually no. Prefer overloads, nullable annotations, a parameter object, or clearer API design.</p>
</td>
<td valign="top" width="50%">

<p>Q: Где <code>Optional</code> обычно не стоит использовать?<br>A: В полях, параметрах, элементах коллекций и моделях, которые должны удобно сериализоваться или маппиться ORM.</p>

</td>
</tr>

<a id="jcore-modern-003"></a>

<details>
<summary><strong>JCORE-MODERN-003. What is the difference between <code>orElse()</code> and <code>orElseGet()</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>orElse(value)</code> evaluates its argument eagerly, even when the Optional has a value. <code>orElseGet(supplier)</code> evaluates the supplier lazily only when the Optional is empty. Use <code>orElseGet</code> for expensive or side-effecting fallback creation.</p>
</td>
<td valign="top" width="50%">

<p><code>orElse()</code> вычисляет запасное значение заранее, даже если <code>Optional</code> не пустой. <code>orElseGet()</code> принимает <code>Supplier</code> и вычисляет запасное значение лениво — только когда значения внутри <code>Optional</code> нет.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The common trap is <code>userOpt.orElse(loadDefaultUser())</code>. <code>loadDefaultUser()</code> runs before <code>orElse</code> is called, regardless of whether <code>userOpt</code> is present. With <code>orElseGet(() -&gt; loadDefaultUser())</code>, the method runs only if needed.</p>
<p>For cheap constants, <code>orElse</code> is perfectly fine: <code>name.orElse("anonymous")</code>. For database calls, object allocation, logging, metrics, timestamps or exceptions with expensive messages, prefer lazy forms.</p>
</td>
<td valign="top" width="50%">

<p>Разница важна, если запасное значение дорогое, имеет побочные эффекты или создаёт новый объект. <code>optional.orElse(loadFromDb())</code> вызовет <code>loadFromDb()</code> сразу. <code>optional.orElseGet(() -&gt; loadFromDb())</code> вызовет его только для пустого <code>Optional</code>.</p>
<p>Если запасное значение — простая константа вроде <code>"unknown"</code>, <code>orElse()</code> вполне нормально. Если это вычисление, запрос, логирование, генерация UUID или создание дорогого объекта, обычно нужен <code>orElseGet()</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Related methods follow the same idea. <code>orElseThrow()</code> throws when empty. <code>or(Supplier&lt;Optional&lt;T&gt;&gt;)</code> can lazily provide another Optional. <code>map</code> and <code>flatMap</code> apply transformations only when present.</p>
<p>Do not use <code>orElseGet</code> for readability theater when the fallback is a literal. The goal is to avoid unnecessary work or side effects, not to make every Optional chain longer.</p>
</td>
<td valign="top" width="50%">

<p><code>orElse()</code> получает уже готовый аргумент, поэтому Java должна вычислить его до вызова метода. <code>orElseGet()</code> получает функцию, и сам <code>Optional</code> решает, вызывать её или нет.</p>
<p>Похожее различие есть с <code>orElseThrow()</code>: современная форма без аргументов бросает <code>NoSuchElementException</code>, а форма с поставщиком исключения позволяет лениво создать доменное исключение.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In backend code, the difference can cause unexpected database calls, remote calls, cache misses or audit events. Review Optional fallbacks that call methods, allocate heavy objects or mutate state.</p>
</td>
<td valign="top" width="50%">

<p>В рабочем коде эта разница часто проявляется как лишние запросы к базе, неожиданное логирование или создание ненужных объектов. Правило простое: дешёвая константа — <code>orElse</code>, вычисление или побочный эффект — <code>orElseGet</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>orElse(expensive())</code> runs <code>expensive()</code> even when value is present.</li>
<li><code>orElseGet</code> supplier should be side-effect safe because it runs on absence.</li>
<li>Use <code>orElse</code> for cheap constants.</li>
<li>Do not confuse <code>orElseGet</code> with asynchronous execution; it is just lazy.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>orElse(expensive())</code> вызывает <code>expensive()</code> даже при наличии значения.</li>
<li><code>orElseGet</code> требует функцию без аргументов.</li>
<li>Не прячьте побочные эффекты в запасном значении без необходимости.</li>
<li>Для исключений используйте <code>orElseThrow</code>, а не <code>orElse</code> с фиктивным объектом.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Which Optional fallback is lazy?<br>A: <code>orElseGet()</code>; <code>orElse()</code> evaluates its argument eagerly.</p>
</td>
<td valign="top" width="50%">

<p>Q: Чем <code>orElse()</code> отличается от <code>orElseGet()</code>?<br>A: <code>orElse()</code> вычисляет запасное значение сразу, <code>orElseGet()</code> — лениво только при пустом <code>Optional</code>.</p>

</td>
</tr>
</tbody>

<a id="jcore-modern-004"></a>

<details>
<summary><strong>JCORE-MODERN-004. What is local variable type inference with <code>var</code>, and when can it hurt readability?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>var</code> lets the compiler infer the type of a local variable from its initializer. It is still statically typed; the inferred type is fixed at compile time. It hurts readability when the initializer does not make the type or intent obvious.</p>
</td>
<td valign="top" width="50%">

<p><code>var</code> — это локальный вывод типа переменной: компилятор выводит статический тип из инициализатора. Это не динамическая типизация. Читаемость страдает, когда из правой части неочевидно, какой тип получился или почему этот тип важен.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>var</code> is allowed for local variables with initializers, enhanced-for variables, and lambda parameters when all explicitly declared lambda parameters use <code>var</code>. It is not allowed for fields, method return types, ordinary method parameters, or variables without initializers.</p>
<p>Good uses include obvious constructors, long generic types, and try-with-resources: <code>var users = new ArrayList&lt;User&gt;();</code>. Bad uses include vague factory calls: <code>var data = service.get();</code> when the type matters to understand the code.</p>
</td>
<td valign="top" width="50%">

<p><code>var</code> можно использовать только для локальных переменных с инициализатором, например <code>var users = repository.findAll();</code>. После компиляции у переменной есть обычный конкретный статический тип, и он не меняется.</p>
<p>Он полезен, когда тип очевиден или слишком шумный: обобщения (generics), try-with-resources, локальные временные переменные. Но если тип несёт смысл для читателя, лучше написать его явно, особенно на границах бизнес-логики.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The inferred type may be more specific or less general than the type you would write explicitly. For example, <code>var users = new ArrayList&lt;User&gt;();</code> infers <code>ArrayList&lt;User&gt;</code>, not <code>List&lt;User&gt;</code>, which can expose implementation-specific methods or make later refactoring harder.</p>
<p><code>var</code> does not mean dynamic typing. You cannot assign a different incompatible type later. It also does not infer from future assignments; the initializer is required.</p>
</td>
<td valign="top" width="50%">

<p><code>var</code> не работает для полей, параметров методов и возвращаемых типов. Нельзя объявить <code>var x;</code> без инициализатора, потому что компилятору не из чего вывести тип.</p>
<p>Иногда <code>var</code> выводит более общий или неожиданный тип, чем хотел разработчик, например при фабричных методах, литералах, анонимных классах или сложных цепочках Stream API. Поэтому важно смотреть не только на краткость, но и на ясность.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use <code>var</code> when it removes noise without hiding meaning. In code reviews, ask whether a reader can understand the type and business role from the initializer and variable name without jumping to the declaration target.</p>
</td>
<td valign="top" width="50%">

<p>Командное правило обычно такое: используйте <code>var</code>, когда имя переменной и инициализатор делают тип очевидным; не используйте, когда явный тип помогает понять доменную модель, API или результат сложного выражения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>var</code> is not dynamic typing.</li>
<li><code>var</code> requires an initializer.</li>
<li><code>var</code> can hide important API types behind vague names.</li>
<li>The variable name becomes more important when the type is omitted.</li>
<li>In lambda parameters, either all explicitly declared parameter types use <code>var</code>, or none do.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>var</code> не означает динамическую типизацию.</li>
<li><code>var</code> требует инициализатор.</li>
<li><code>var</code> нельзя использовать для полей и сигнатур методов.</li>
<li>Слишком много <code>var</code> в сложном коде ухудшает навигацию и ревью.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Is <code>var</code> dynamically typed?<br>A: No. The compiler infers a static type at compile time.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что такое <code>var</code> в Java?<br>A: Локальный вывод статического типа из инициализатора, а не динамическая типизация.</p>

</td>
</tr>

<details>
<summary><strong>JCORE-MODERN-005. What are switch expressions, and how do they differ from old <code>switch</code> statements?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A switch expression produces a value. It supports arrow labels, requires exhaustive handling, and uses <code>yield</code> for block arms that return a value. Old switch statements are primarily control-flow statements and historically allowed fall-through unless <code>break</code> was used.</p>
</td>
<td valign="top" width="50%">

<p>Switch-выражение возвращает значение и должно быть исчерпывающим. В нём часто используют стрелочные ветки <code>case X -&gt;</code>, которые не проваливаются в следующую ветку. Старый <code>switch</code>-оператор в первую очередь управляет потоком выполнения и исторически требовал <code>break</code>, чтобы избежать проваливания (fall-through).</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example: <code>int len = switch (day) { case MONDAY, FRIDAY -&gt; 6; default -&gt; 0; };</code>. This directly assigns the result and avoids a mutable temporary variable plus repeated <code>break</code> statements.</p>
<p>Arrow labels <code>case X -&gt;</code> do not fall through. If an arm needs multiple statements, use a block and <code>yield value;</code>. Switch expressions must cover all possible inputs, often with <code>default</code> unless the compiler can prove exhaustive handling.</p>
</td>
<td valign="top" width="50%">

<p>Switch-выражение можно присвоить переменной или вернуть из метода: <code>var label = switch (status) { ... };</code>. Каждая ветка должна дать значение: через выражение справа от <code>-&gt;</code> или через <code>yield</code> в блочной ветке.</p>
<p>Это уменьшает типичные ошибки старого <code>switch</code>: забытый <code>break</code>, неинициализированная переменная результата и неочевидная логика присваивания внутри веток.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Switch expressions became final in Java 14. They can use both arrow and traditional colon labels, but arrow labels are usually clearer because they avoid accidental fall-through.</p>
<p>Classic switch statements still exist and are useful for side effects. Modern Java also allows arrow-label switch statements, so “expression vs statement” and “arrow vs colon” are related but separate choices.</p>
</td>
<td valign="top" width="50%">

<p>Старый <code>switch</code>-оператор всё ещё доступен и полезен, когда нужен именно побочный эффект или управление потоком. Switch-выражение лучше подходит, когда нужно вычислить значение.</p>
<p>Исчерпываемость особенно важна для enum и запечатанных типов: компилятор может проверить, что все варианты покрыты. Это делает код устойчивее к изменениям модели.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use switch expressions for mapping enum/domain states to values, HTTP statuses, messages or strategies. They reduce accidental fall-through and make missing cases more visible during compilation.</p>
</td>
<td valign="top" width="50%">

<p>В серверном коде switch-выражения хорошо подходят для маппинга статусов, enum, команд и небольших закрытых наборов вариантов. Они делают намерение явным: мы не просто выполняем ветку, а вычисляем результат.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Switch expressions must be exhaustive.</li>
<li>Arrow cases do not fall through.</li>
<li><code>yield</code> is for returning a value from a block arm.</li>
<li><code>break</code> is not used to return values from switch expressions.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Switch-выражение должно вернуть значение на всех путях.</li>
<li>Стрелочные ветки не имеют неявного проваливания (fall-through).</li>
<li>Для многострочной ветки switch-выражения используется <code>yield</code>.</li>
<li>Не превращайте большой switch в замену полиморфизму, если поведение принадлежит самим типам.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What must a switch expression do that a switch statement need not always do?<br>A: Be exhaustive and produce a value or throw on every path.</p>
</td>
<td valign="top" width="50%">

<p>Q: Главное отличие switch-выражения от старого <code>switch</code>?<br>A: Switch-выражение вычисляет значение и должно быть исчерпывающим; старый <code>switch</code> в первую очередь управляет выполнением.</p>

</td>
</tr>

<a id="jcore-modern-006"></a>

<details>
<summary><strong>JCORE-MODERN-006. What is pattern matching for <code>instanceof</code> useful for?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Pattern matching for <code>instanceof</code> combines a type test and cast in one construct. If the test succeeds, Java introduces a pattern variable with the tested type, reducing boilerplate and making type-safe conditional extraction clearer.</p>
</td>
<td valign="top" width="50%">

<p>Сопоставление с образцом (pattern matching) для <code>instanceof</code> объединяет проверку типа, приведение и объявление переменной. Вместо «проверил тип — сделал приведение типа — присвоил переменной» можно написать <code>if (obj instanceof User u)</code> и сразу использовать <code>u</code> в безопасной области видимости.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Instead of <code>if (obj instanceof String) { String s = (String) obj; ... }</code>, write <code>if (obj instanceof String s) { ... }</code>. The variable <code>s</code> is available only where the compiler knows the pattern matched.</p>
<p>This improves readability in validation, mapping, exception handling and code that deals with heterogeneous values. It also avoids accidental mismatch between the type checked and the type cast.</p>
</td>
<td valign="top" width="50%">

<p>Раньше код выглядел так: <code>if (obj instanceof User) { User u = (User) obj; ... }</code>. Теперь типовой образец делает это короче и безопаснее: <code>if (obj instanceof User u) { ... }</code>. Переменная <code>u</code> доступна только там, где компилятор знает, что проверка прошла.</p>
<p>Это снижает шум и риск ошибочного приведения к не тому типу. Особенно полезно в коде, который разбирает разные реализации интерфейса, события, команды или результаты.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Pattern variable scope is flow-sensitive. In <code>if (!(obj instanceof User u)) return;</code>, <code>u</code> is available after the guard because the only remaining path is the successful match path.</p>
<p>Pattern matching does not change object type or perform deep destructuring by itself. It is still an <code>instanceof</code> test plus a typed binding. More advanced pattern matching appears in switch and record patterns.</p>
</td>
<td valign="top" width="50%">

<p>Область видимости переменной образца зависит от потока управления. Например, после условия с ранним выходом переменная может быть доступна дальше, если компилятор доказал, что иначе выполнение не продолжится.</p>
<p>Сопоставление с образцом не отменяет необходимость хорошей модели типов. Если код состоит из длинной цепочки <code>instanceof</code>, возможно, поведение лучше перенести в полиморфные методы или запечатанную иерархию.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use it to simplify safe type checks, especially in adapters, deserializers, domain event handling and exception mapping. Avoid long chains of <code>instanceof</code> when polymorphism or a visitor-like design would express the model better.</p>
</td>
<td valign="top" width="50%">

<p>В сервисном коде это хорошо работает на границах, где приходит общий тип: сообщения, ошибки, результаты парсинга, события. Код становится короче, но всё ещё типобезопасным.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Pattern variables exist only where the match is definitely true.</li>
<li>It is not dynamic typing; the pattern variable has a static type.</li>
<li>Do not replace good polymorphism with huge <code>instanceof</code> chains.</li>
<li>A null reference does not match a type pattern.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Переменная образца (pattern variable) доступна только в области, где проверка точно успешна.</li>
<li><code>instanceof</code> с <code>null</code> возвращает <code>false</code>.</li>
<li>Не заменяйте хорошую доменную модель длинными цепочками проверок типа.</li>
<li>Имя переменной образца не должно конфликтовать с уже доступной переменной в той же области.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What boilerplate does pattern matching for <code>instanceof</code> remove?<br>A: The separate cast after a successful type check.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что даёт сопоставление с образцом для <code>instanceof</code>?<br>A: Проверку типа, безопасное приведение и объявление переменной в одном выражении.</p>

</td>
</tr>

<a id="jcore-modern-007"></a>

<details>
<summary><strong>JCORE-MODERN-007. What are sealed classes and sealed interfaces?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Sealed classes and interfaces restrict which classes or interfaces may directly extend or implement them. A sealed type declares or implies its permitted subclasses, and each permitted subclass must choose whether it is <code>final</code>, <code>sealed</code>, or <code>non-sealed</code>.</p>
</td>
<td valign="top" width="50%">

<p>Запечатанный класс (sealed class) или запечатанный интерфейс (sealed interface) ограничивает список прямых наследников. Разрешённые подтипы указываются через <code>permits</code> или выводятся компилятором, а каждый прямой наследник должен быть <code>final</code>, <code>sealed</code> или <code>non-sealed</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>They model a closed set of alternatives. For example, <code>sealed interface PaymentResult permits Approved, Declined, Error</code> says that these are the known direct variants. This is stronger than documentation and more flexible than making the root type package-private.</p>
<p>Permitted subclasses must be close enough to the sealed type according to module/package rules. This lets the compiler and readers know who is allowed to participate in the hierarchy.</p>
</td>
<td valign="top" width="50%">

<p>Запечатанные типы позволяют сказать: «у этого базового типа есть только такие варианты». Это полезно, когда модель должна быть расширяема внутри контролируемого набора, но закрыта для произвольных внешних реализаций.</p>
<p>Например, <code>sealed interface PaymentResult permits Approved, Declined, Error</code> явно задаёт возможные результаты. Код, который обрабатывает <code>PaymentResult</code>, может опираться на этот закрытый список.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A permitted subclass marked <code>final</code> stops extension. A permitted subclass marked <code>sealed</code> continues the controlled hierarchy. A permitted subclass marked <code>non-sealed</code> reopens that branch to arbitrary subclasses.</p>
<p>Sealed types work especially well with records and pattern matching for switch because the compiler can reason about the known alternatives.</p>
</td>
<td valign="top" width="50%">

<p>Прямые наследники запечатанного типа должны находиться в том же модуле, а если модулей нет — в том же пакете. Каждый наследник обязан явно выбрать дальнейшую стратегию: закрыть ветку через <code>final</code>, продолжить ограничение через <code>sealed</code> или открыть её через <code>non-sealed</code>.</p>
<p>Запечатанные типы хорошо сочетаются с сопоставлением с образцом для <code>switch</code>, потому что компилятор знает все разрешённые варианты и может проверять исчерпываемость.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use sealed types for domain alternatives that should be closed by design: result types, commands, events, state machines and error hierarchies. Avoid sealing extension points intended for external plugins or unknown future implementors.</p>
</td>
<td valign="top" width="50%">

<p>В серверных доменных моделях запечатанные типы полезны для закрытых наборов состояний, команд, событий и результатов операций. Они делают ограничения модели частью типа, а не только документацией или соглашением команды.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Sealed restricts direct subclasses, not object creation by itself.</li>
<li>Every permitted subclass must declare <code>final</code>, <code>sealed</code>, or <code>non-sealed</code>.</li>
<li><code>non-sealed</code> deliberately reopens a branch.</li>
<li>Sealed hierarchies are a modeling tool, not an access-control replacement for secrets.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>sealed</code> ограничивает только прямых наследников.</li>
<li>Каждый прямой наследник должен быть <code>final</code>, <code>sealed</code> или <code>non-sealed</code>.</li>
<li><code>non-sealed</code> снова открывает ветку для произвольного наследования.</li>
<li>Не используйте <code>sealed</code>, если сторонние расширения являются частью публичного контракта.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does a sealed type control?<br>A: Which classes or interfaces may directly extend or implement it.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что делает запечатанный класс?<br>A: Ограничивает список прямых наследников и заставляет каждую ветку явно выбрать <code>final</code>, <code>sealed</code> или <code>non-sealed</code>.</p>

</td>
</tr>

<details>
<summary><strong>JCORE-MODERN-008. When are sealed types useful in backend domain models?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Sealed types are useful when the domain has a known finite set of alternatives: payment outcomes, order states, commands, events, validation results, workflow steps or error categories. They make the model explicit and help the compiler check exhaustive handling.</p>
</td>
<td valign="top" width="50%">

<p>Запечатанные типы полезны в доменных моделях, когда есть закрытый набор вариантов: результат платежа, состояние заказа, команда, событие или ошибка. Они делают модель явной и помогают компилятору проверять, что обработаны все случаи.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Without sealed types, code often uses a base interface plus documentation saying “only these implementations exist”. Sealed types make that rule part of the type system. This is especially helpful when business logic switches over all variants.</p>
<p>They pair well with records: each variant can be a small immutable data carrier, while the sealed root expresses the closed family. Pattern matching switch can then handle each subtype directly.</p>
</td>
<td valign="top" width="50%">

<p>Во многих серверных задачах бизнес говорит не «любой наследник когда-нибудь», а «есть ровно такие варианты». Запечатанная иерархия выражает это в коде лучше, чем открытый интерфейс с комментариями.</p>
<p>Например, результат операции может быть <code>Success</code>, <code>ValidationError</code> или <code>ExternalServiceUnavailable</code>. Если это запечатанный интерфейс, обработчик через <code>switch</code> может быть исчерпывающим, а добавление нового варианта заставит обновить места обработки.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Sealed types are less suitable when the hierarchy is intended for external extension, plugins, integrations, or unknown third-party implementors. In those cases, an open interface is more honest.</p>
<p>They also require versioning care. Adding a new permitted subtype is a source-level compatibility event for exhaustive switches: code may need to handle the new case. That is often a feature, not a bug, for domain models.</p>
</td>
<td valign="top" width="50%">

<p>Запечатанные типы особенно хорошо работают вместе с <code>record</code>: каждый вариант — небольшой неизменяемый носитель данных, а базовый запечатанный интерфейс задаёт общий тип. Это похоже на алгебраические типы данных, но в синтаксисе Java.</p>
<p>Они не подходят для плагинных API, где новые реализации должны добавляться извне без изменения базового модуля. В таких случаях обычный интерфейс остаётся более гибким.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use sealed hierarchies inside bounded contexts where the team owns all variants. They improve readability, refactoring safety and test coverage for exhaustive business rules. For public extension APIs, prefer open interfaces unless closure is part of the contract.</p>
</td>
<td valign="top" width="50%">

<p>Для доменной модели это снижает количество «невозможных» состояний. Вместо набора полей, допускающих <code>null</code> и флагов можно описать реальные варианты отдельными типами и дать компилятору помогать при изменениях.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Adding a variant forces exhaustive handlers to be revisited.</li>
<li>Sealed roots are not ideal for plugin ecosystems.</li>
<li>Serialization frameworks may need subtype metadata/configuration.</li>
<li>Closed alternatives should reflect real domain stability, not just current implementation convenience.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не закрывайте иерархию, если её должны расширять внешние клиенты.</li>
<li>Следите, чтобы запечатанная иерархия не стала огромной заменой нормальной декомпозиции.</li>
<li>При добавлении нового варианта нужно обновить обработчики.</li>
<li>Для ORM-сущностей запечатанное наследование может потребовать отдельной проверки совместимости с фреймворком.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why do sealed types fit domain alternatives?<br>A: They encode the finite set of allowed variants in the type system.</p>
</td>
<td valign="top" width="50%">

<p>Q: Где запечатанные типы особенно полезны в серверном коде?<br>A: В закрытых наборах доменных вариантов: состояниях, результатах, командах, событиях и ошибках.</p>

<details>
<summary><strong>🧠 JCORE-MODERN-009. How should teams think about preview Java features in production code?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Preview features are high-quality but not final Java features. They require explicit preview enablement and may change, be finalized differently, or be removed in later releases. Production teams should use them only with deliberate governance, version pinning and migration plans.</p>
</td>
<td valign="top" width="50%">

<p>Предварительные возможности (preview features) Java в рабочем коде нужно использовать очень осторожно. Они требуют явного включения при компиляции и запуске, ещё не являются окончательным контрактом языка и могут измениться или исчезнуть в следующей версии.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The key risk is lifecycle. Code compiled with preview features is tied to the Java release whose preview it used; later JDKs are not required to run or compile it unchanged. Build tools, IDEs, CI, containers and runtime flags all need to agree.</p>
<p>Preview does not mean “toy” or “unstable experiment”; it means the feature is intended for feedback before becoming permanent. But using it in distributed production artifacts still increases maintenance and upgrade risk.</p>
</td>
<td valign="top" width="50%">

<p>Предварительная возможность (preview feature) — это не экспериментальная игрушка, но и не финальная возможность. Она уже достаточно качественная, чтобы разработчики могли дать обратную связь, однако синтаксис, семантика или API могут поменяться. Поэтому команда должна заранее решить, допустимы ли такие возможности в основной ветке.</p>
<p>Если preview всё же используется, его нужно включать одинаково в javac, тестах, IDE, CI, среде выполнения и сборке контейнера. Иначе код может компилироваться локально, но падать в CI или при запуске.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A reasonable policy is: allow preview features in experiments, prototypes, benchmarks and isolated internal tools; be cautious in core services and shared libraries; avoid them in public APIs unless the organization accepts the compatibility cost.</p>
<p>When using preview features, document the JDK version, enable flags explicitly, add upgrade tickets, and run CI on the exact JDK. Revisit the code when the feature is re-previewed or finalized.</p>
</td>
<td valign="top" width="50%">

<p>Главный риск — миграция. Код на предварительные возможности может потребовать правок при переходе на следующий JDK. Кроме того, библиотеки, статический анализ, форматтеры и инструменты покрытия тестами могут поддерживать новые конструкции не сразу.</p>
<p>Разумная политика: не использовать preview в критичных рабочих сервисах без сильной причины; разрешать в прототипах, внутренних инструментах или изолированных модулях; фиксировать версию JDK и план миграции.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For senior backend work, the answer is not “never” or “always”. It is risk management: consider support windows, deployment platform, framework compatibility, operational ownership and the cost of rewriting code on the next JDK.</p>
</td>
<td valign="top" width="50%">

<p>На интервью хороший ответ — не «никогда» и не «всегда можно», а управляемый риск. Для коммерческого сервиса preview должен проходить через архитектурное решение: зачем он нужен, как включается в сборке, кто отвечает за обновление JDK и как быстро можно откатиться.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Preview features are disabled by default and require opt-in.</li>
<li>Preview class files are tied to a specific Java release.</li>
<li>A preview feature can change before finalization.</li>
<li>Shared libraries should be more conservative than local experiments.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Предварительные возможности нужно включать и при компиляции, и при запуске.</li>
<li>Поведение или синтаксис предварительных возможностей могут измениться.</li>
<li>Инструменты разработки и анализа могут отставать.</li>
<li>Нельзя незаметно использовать preview в библиотеке, если потребители не готовы к тем же требованиям JDK.</li>

<details>
<summary><strong>JCORE-MODERN-010. What are records in Java, and what problem do they solve?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Records are special classes for transparent immutable data carriers. A record declares components and the compiler provides a canonical constructor, accessors, <code>equals()</code>, <code>hashCode()</code> and <code>toString()</code> based on those components.</p>
</td>
<td valign="top" width="50%">

<p><code>record</code> — это специальный класс для прозрачного неизменяемого носителя данных. Java автоматически создаёт поля, методы доступа, канонический конструктор, <code>equals()</code>, <code>hashCode()</code> и <code>toString()</code> на основе компонентов <code>record</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>They solve the boilerplate problem for simple value-like aggregates: DTO-like results, keys, coordinates, domain values and messages. Instead of writing fields, constructor, accessors and equality manually, you declare <code>record Money(BigDecimal amount, Currency currency) {}</code>.</p>
<p>Records are nominal classes, not anonymous tuples. A <code>Money</code> record and a <code>Price</code> record with the same components are different types. Records can implement interfaces and have methods, but they are final and cannot extend arbitrary classes.</p>
</td>
<td valign="top" width="50%">

<p><code>record</code> решает проблему шаблонного кода в простых классах-носителях данных: больше не нужно вручную писать конструктор, методы доступа, равенство и строковое представление для объекта, чья идентичность определяется набором компонентов.</p>
<p>Например, <code>record UserId(UUID value) {}</code> ясно говорит: это значение с одним компонентом. Компоненты <code>record</code> являются <code>final</code>-полями, а сам <code>record</code>-класс неявно <code>final</code>, поэтому он хорошо подходит для неизменяемых DTO и объекта-значения (value object).</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Record fields are final, but record immutability is shallow. If a component is a mutable list, the reference cannot be reassigned but the list contents can still mutate unless you make defensive copies.</p>
<p>A compact constructor can validate and normalize components. It should preserve the record’s transparent data-carrier promise: do not hide surprising mutable behavior behind a record shape.</p>
</td>
<td valign="top" width="50%">

<p>У <code>record</code> есть метод доступа (accessor) с именем компонента, например <code>name()</code>, а не JavaBean-метод <code>getName()</code>. Можно добавить валидацию или нормализацию в компактном конструкторе, а также объявить дополнительные методы.</p>
<p><code>record</code> не означает глубокую неизменяемость. Если компонент — изменяемый объект, например массив или изменяемый список, нужно делать защитные копии, иначе состояние <code>record</code> фактически можно менять снаружи.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use records for small immutable-ish carriers at service boundaries, query results, events and value objects when their identity is exactly their components. Use regular classes when behavior, lifecycle, inheritance, encapsulation or mutability is central.</p>
</td>
<td valign="top" width="50%">

<p><code>record</code>-классы удобны для DTO, результатов запросов, ключей, сообщений и небольших доменных значений. Но для JPA-сущностей, сложного жизненного цикла, ленивых прокси и изменяемых агрегатов обычный класс часто подходит лучше.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Records are final.</li>
<li>Record immutability is shallow.</li>
<li>Accessors are named <code>amount()</code>, not JavaBean <code>getAmount()</code> by default.</li>
<li>Do not use records for entities with complex lifecycle identity unless the fit is deliberate.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>record</code>-класс неявно <code>final</code>.</li>
<li>Компоненты <code>record</code> задают <code>equals()</code> и <code>hashCode()</code>.</li>
<li><code>record</code> не гарантирует глубокую неизменяемость компонентов.</li>
<li>Метод доступа называется как компонент: <code>name()</code>, а не обязательно <code>getName()</code>.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What methods does a record generate from its components?<br>A: Accessors, canonical constructor, <code>equals()</code>, <code>hashCode()</code> and <code>toString()</code>.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что автоматически даёт <code>record</code>?<br>A: Компоненты, конструктор, методы доступа, <code>equals()</code>, <code>hashCode()</code> и <code>toString()</code> на основе состояния.</p>

</td>
</tr>

<details>
<summary><strong>JCORE-MODERN-011. When should you use a record instead of a regular class?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use a record when the type is mainly a transparent carrier for a fixed set of values and equality should be based on those values. Use a regular class when you need mutable state, hidden representation, complex invariants, inheritance, lazy behavior, or identity separate from the fields.</p>
</td>
<td valign="top" width="50%">

<p><code>record</code> стоит использовать, когда класс — это небольшой неизменяемый носитель данных, а его равенство определяется всеми компонентами. Обычный класс лучше выбрать, если нужны изменяемое состояние, сложный жизненный цикл, наследование, нестандартная идентичность или тесная интеграция с фреймворком.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Good record candidates: request/response projections, query results, compound map keys, small domain values, events and command payloads. The reader should be comfortable seeing all components in the type declaration.</p>
<p>Poor candidates: JPA entities with generated IDs and lazy associations, classes that must follow JavaBean conventions, objects with significant mutable lifecycle, and types whose equality must ignore some fields.</p>
</td>
<td valign="top" width="50%">

<p>Хороший кандидат на <code>record</code> — DTO ответа, команда, событие, ключ, значение конфигурации, результат вычисления. В таких случаях компоненты полностью описывают объект, а автоматически сгенерированные методы именно такие, как нужны.</p>
<p>Обычный класс лучше, если объект имеет идентичность, отличную от полей, например JPA-сущность с id и жизненным циклом. Также обычный класс удобнее, когда нужно скрыть часть состояния, управлять инвариантами через методы или поддерживать наследование.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Records can still have validation, normalization, derived methods and static factories. They are not limited to an empty body. But they should remain transparent: the declared components should explain the state that defines the value.</p>
<p>If a component is mutable, consider copying it in the constructor and accessor. Otherwise a record may look immutable while exposing mutable internals.</p>
</td>
<td valign="top" width="50%">

<p><code>record</code> может иметь компактный конструктор для проверки и нормализации компонентов, но он не должен превращаться в большой сервисный объект. Если внутри много поведения, изменяемых полей и сложных зависимостей, <code>record</code>, скорее всего, выбран не по назначению.</p>
<p>Для публичного API важно помнить: компоненты <code>record</code> становятся частью контракта. Переименование или изменение компонента влияет на конструктор, методы доступа, сериализацию и равенство.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In backend teams, records are great for internal DTOs and value objects on modern Java versions. Check framework compatibility for serialization, validation and reflection, especially if APIs expect JavaBean getters or no-arg constructors.</p>
</td>
<td valign="top" width="50%">

<p>В серверном коде <code>record</code>-классы хорошо сокращают шаблонный код в слоях API и сообщений. Но перед использованием с Jackson, JPA, MapStruct или другими инструментами стоит проверить версии и соглашения команды.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Records are not a replacement for all DTO/entity classes.</li>
<li>Frameworks may require extra configuration for record constructors/accessors.</li>
<li>Component order and names are part of the record API.</li>
<li>Mutable components require defensive-copy decisions.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не используйте <code>record</code> для сущности с изменяемым жизненным циклом только ради краткости.</li>
<li>Компоненты <code>record</code> определяют равенство и хеш-код.</li>
<li>Изменяемые компоненты требуют защитных копий.</li>
<li>Изменение списка компонентов — изменение публичного контракта <code>record</code>.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the main design test for using a record?<br>A: Whether the type is a transparent value carrier whose equality is its declared components.</p>
</td>
<td valign="top" width="50%">

<p>Q: Когда <code>record</code> лучше обычного класса?<br>A: Когда это небольшой неизменяемый носитель данных, и все компоненты участвуют в равенстве.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A text block starts with <code>"""</code> followed by a line terminator, then content, then closing <code>"""</code>. The compiler normalizes line terminators, removes incidental indentation and interprets escape sequences.</p>

<p>Например, SQL-запрос или JSON для теста становится заметно читабельнее. Это не шаблонизатор и не интерполяция строк: подстановка значений всё равно делается обычными средствами, например форматированием или параметрами prepared statement.</p>

<th colspan="2" align="left">Deep dive</th>

</td>
<td valign="top" width="50%">

<a id="jcore-modern-013"></a>

<details>
<summary><strong>JCORE-MODERN-013. What is pattern matching for <code>switch</code>, and how does it differ from classic <code>switch</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Pattern matching for <code>switch</code> lets <code>case</code> labels contain type patterns and guarded patterns, so a switch can dispatch by type and conditions, not only by constants. It differs from classic switch by supporting richer matching, null handling when declared, and exhaustiveness checking for pattern switches.</p>
</td>
<td valign="top" width="50%">

<p>Сопоставление с образцом (pattern matching) для <code>switch</code> позволяет использовать в <code>case</code> не только константы, но и образцы типов, <code>null</code> и условия <code>when</code>. В отличие от классического <code>switch</code>, он хорошо работает с объектными иерархиями и может проверять исчерпываемость вариантов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Classic switch historically matched constants of limited types such as ints, enums and strings. Pattern switch can say <code>case String s -&gt;</code>, <code>case Integer i when i &gt; 0 -&gt;</code>, or <code>case null -&gt;</code>. This replaces many <code>if/else instanceof</code> chains.</p>
<p>Pattern switch became final in Java 21. It works with both switch expressions and switch statements, and it pairs especially well with sealed hierarchies because the compiler can know all permitted variants.</p>
</td>
<td valign="top" width="50%">

<p>Классический <code>switch</code> исторически был про выбор по значениям вроде чисел, строк и enum. Switch с сопоставлением образцов позволяет писать ветки вида <code>case Success s -&gt;</code> или <code>case Error e when e.retryable() -&gt;</code>, одновременно проверяя тип и создавая переменную.</p>
<p>Это особенно полезно вместе с запечатанными типами: компилятор знает разрешённые подтипы и может потребовать обработать их все. Код становится похож на явный разбор вариантов доменной модели.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Pattern order matters because earlier cases can dominate later cases. A broad <code>case Object o</code> before <code>case String s</code> would make the string case unreachable. Guards make matching more precise but can also affect exhaustiveness reasoning.</p>
<p>Null handling is explicit. A pattern such as <code>case String s</code> does not match null. Use <code>case null</code> or <code>case null, default</code> when null is part of the accepted input.</p>
</td>
<td valign="top" width="50%">

<p>Switch с сопоставлением образцов учитывает порядок веток, потому что более общий образец может перекрыть более конкретный. Например, ветка для <code>Object</code> раньше ветки для <code>String</code> сделала бы вторую недостижимой.</p>
<p><code>null</code> можно обработать явно через <code>case null</code>. Если этого не сделать, поведение зависит от формы switch и правил языка; на практике лучше быть явным, когда <code>null</code> возможен.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use pattern switch for closed domain alternatives, event handling, result mapping and adapter code. Avoid using it to centralize behavior that belongs polymorphically on domain objects, unless exhaustive external handling is the clearer design.</p>
</td>
<td valign="top" width="50%">

<p>В серверном коде switch с сопоставлением образцов удобен для результатов операций, событий, команд, ошибок и закрытых доменных вариантов. Он помогает заменить длинные цепочки <code>if instanceof</code> на более структурированный и проверяемый код.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Case order can make later patterns unreachable.</li>
<li>Null must be handled explicitly if accepted.</li>
<li>Dominance and exhaustiveness errors are compile-time feedback.</li>
<li>Pattern switch can be clearer than visitors for simple closed hierarchies, but not always.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Порядок <code>case</code> важен: общий образец может сделать частный недостижимым.</li>
<li>Для возможного <code>null</code> лучше явно писать <code>case null</code>.</li>
<li>Для switch-выражения нужна исчерпываемость.</li>
<li>Не используйте switch с сопоставлением образцов как замену полиморфизму там, где поведение естественно принадлежит объектам.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does pattern switch add to classic switch?<br>A: Cases can match patterns such as types and guarded conditions, not just constants.</p>
</td>
<td valign="top" width="50%">

<p>Q: Чем switch с сопоставлением образцов отличается от классического <code>switch</code>?<br>A: Он может выбирать по образцам типов, связывать переменные, использовать условия <code>when</code> и проверять исчерпываемость.</p>

</td>

<a id="jcore-modern-014"></a>

<details>
<summary><strong>🧠 JCORE-MODERN-014. How do sealed classes help make <code>switch</code> exhaustive?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Sealed classes tell the compiler the complete set of permitted direct subtypes. When a switch handles all permitted alternatives, the compiler can treat it as exhaustive without requiring a catch-all default in many cases.</p>
</td>
<td valign="top" width="50%">

<p>Запечатанные классы помогают сделать <code>switch</code> исчерпывающим, потому что компилятор знает полный список разрешённых прямых наследников. Если <code>switch</code> обработал все варианты запечатанной иерархии, ему часто не нужен <code>default</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For a sealed root like <code>sealed interface Result permits Success, Failure</code>, a switch expression with <code>case Success s</code> and <code>case Failure f</code> covers the known family. If a new permitted subtype is later added, recompilation can reveal switches that need updating.</p>
<p>This is powerful because missing domain cases become compile-time problems rather than runtime surprises. It is similar to exhaustive enum switches, but for class hierarchies.</p>
</td>
<td valign="top" width="50%">

<p>У открытого интерфейса компилятор не знает, какие реализации могут появиться завтра, поэтому не может доказать, что все варианты обработаны. У запечатанного интерфейса список вариантов ограничен, например <code>Success</code>, <code>Failure</code>, <code>Pending</code>.</p>
<p>Когда <code>switch</code> покрывает все разрешённые варианты, компилятор может считать его исчерпывающим. Если позже добавить новый подтип, места с таким <code>switch</code> начнут требовать обновления, что полезно для сопровождения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Exhaustiveness depends on the static type of the switch selector and the sealed hierarchy known to the compiler. If a branch is <code>non-sealed</code>, the compiler must account for unknown subtypes under that branch, often requiring a broader case.</p>
<p>A default case can be useful for defensive compatibility, but it can also hide the fact that a new domain variant deserves explicit handling. For internal domain models, explicit cases are often better.</p>
</td>
<td valign="top" width="50%">

<p>Если разрешённый наследник сам является <code>sealed</code>, исчерпываемость может учитывать его подварианты. Если ветка помечена <code>non-sealed</code>, она снова открывает наследование, и компилятору может понадобиться более общий <code>case</code> или <code>default</code>.</p>
<p>Отсутствие <code>default</code> иногда полезно намеренно: при добавлении нового варианта компилятор покажет все места, где нужно принять решение, а не спрячёт новый вариант в старой ветке по умолчанию.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use sealed plus switch for workflows, command/result models and error mapping where every variant must be handled. Treat new subtype compiler errors as helpful prompts to update business logic and tests.</p>
</td>
<td valign="top" width="50%">

<p>Это сильный инструмент для доменных моделей: добавление нового состояния заказа, результата платежа или типа ошибки заставляет обновить обработчики на этапе компиляции, а не ждать редкого сценария во время выполнения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>A <code>default</code> branch can hide newly added variants.</li>
<li><code>non-sealed</code> branches reduce exhaustiveness precision.</li>
<li>Exhaustiveness is checked at compile time, so recompilation matters.</li>
<li>The selector’s static type affects what the compiler can prove.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>default</code> может скрыть то, что новый вариант не обработан явно.</li>
<li><code>non-sealed</code> ветка снижает пользу проверки исчерпываемости.</li>
<li>Исчерпываемость зависит от доступной компилятору запечатанной иерархии.</li>
<li>При изменении запечатанной модели нужно перекомпилировать код, который её обрабатывает.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why do sealed types help switch exhaustiveness?<br>A: The compiler knows the permitted subtype set and can verify all alternatives are handled.</p>
</td>
<td valign="top" width="50%">

<p>Q: Как <code>sealed</code> помогает <code>switch</code>?<br>A: Компилятор знает разрешённые подтипы и может проверить, что <code>switch</code> обработал все варианты.</p>

</td>

<details>
<summary><strong>JCORE-MODERN-015. What are unnamed variables and patterns?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Unnamed variables and patterns use the underscore character <code>_</code> to declare that a value or binding is intentionally unused. They improve readability and let the compiler enforce that the unused binding is not accidentally referenced.</p>
</td>
<td valign="top" width="50%">

<p>Безымянные переменные и образцы используют символ <code>_</code> для значения, которое нужно принять синтаксически, но не нужно использовать. Это уменьшает шум в коде и явно показывает, что переменная намеренно игнорируется.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Unnamed variables are useful in enhanced for loops, catch blocks, lambda parameters, try-with-resources and local declarations where the side effect matters but the value does not. Example: <code>for (var _ : orders) count++;</code>.</p>
<p>Unnamed patterns are useful inside pattern matching when a nested component must be matched structurally but does not need a name. They make pattern code shorter and communicate intent.</p>
</td>
<td valign="top" width="50%">

<p>Вместо имени вроде <code>ignored</code> можно использовать <code>_</code> там, где язык разрешает безымянную переменную или безымянный образец. Такой элемент нельзя прочитать по имени: он именно показывает «это значение мне не нужно».</p>
<p>Это полезно в сопоставлении с образцом, record-образцах, обработчиках исключений, параметрах lambda и локальных местах, где значение важно только фактом присутствия или соответствия структуре.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Each <code>_</code> is not a variable name you can read later. It is a placeholder for an unnamed binding. Multiple underscores can appear in the same scope because they do not introduce ordinary names.</p>
<p>Unnamed variables and patterns were finalized in Java 22. They are not for fields or ordinary method parameters; their scope is limited to specific local variable and pattern contexts.</p>
</td>
<td valign="top" width="50%">

<p>Безымянный образец помогает разобрать структуру, не придумывая имена для частей, которые не используются. Например, при разборе <code>record</code> можно сохранить только нужные компоненты, а остальные обозначить <code>_</code>.</p>
<p>Это также снижает количество предупреждений о неиспользуемых переменных и делает намерение явным для ревьюера: переменная не забыта, она действительно не нужна.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use <code>_</code> when ignoring a value is intentional and important for maintainability, not as a way to avoid naming things you should understand. It can reduce warnings and make catch/lambda/loop intent explicit.</p>
</td>
<td valign="top" width="50%">

<p>В командном коде <code>_</code> полезен, когда без него появляются искусственные имена вроде <code>unused</code>, <code>ignored</code> или <code>dummy</code>. Но если значение помогает понять бизнес-смысл, лучше дать ему нормальное имя.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>You cannot read from an unnamed variable.</li>
<li>Unnamed variables are not ordinary variables named underscore.</li>
<li>They are not allowed in every declaration context.</li>
<li>Do not use <code>_</code> to hide unclear code; use it to express intentional non-use.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>_</code> нельзя использовать как обычное имя переменной для чтения значения.</li>
<li>Не заменяйте осмысленные имена на <code>_</code>, если они помогают понимать код.</li>
<li>Возможность зависит от версии Java и включённых возможностей языка.</li>
<li>Несколько <code>_</code> не создают несколько читаемых переменных с одним именем; это намеренно неиспользуемые значения.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>Q: Зачем нужен <code>_</code> в безымянных переменных и образцах?<br>A: Чтобы явно показать, что значение принято синтаксически, но намеренно не используется.</p>

<details>
<summary><strong>🧠 JCORE-MODERN-016. Why is <code>_</code> special in modern Java?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>_</code> is special because it is reserved and cannot be used as an ordinary identifier. Modern Java uses it for unnamed variables and unnamed patterns, meaning “this value is intentionally unused”.</p>
</td>
<td valign="top" width="50%">

<p>Символ <code>_</code> особый: начиная с Java 9 его нельзя использовать как обычный идентификатор, а в современной Java он применяется для безымянных переменных и образцов. Такое значение нельзя прочитать; оно обозначает намеренно проигнорированную часть кода.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Historically, some code used underscore as a variable name. Java 8 warned about this, and Java 9 made <code>_</code> unusable as an ordinary identifier. Later, Java used that reserved syntax for unnamed variables and patterns.</p>
<p>The important semantic point is that <code>_</code> does not create a normal binding. You cannot later write <code>System.out.println(_)</code>. Multiple underscores in one scope are allowed because they are not names that collide.</p>
</td>
<td valign="top" width="50%">

<p>Раньше одиночное подчёркивание иногда использовали как имя временной переменной. Теперь это запрещено, чтобы освободить <code>_</code> для языковой роли: «значение есть, но оно мне не нужно». Поэтому <code>int _ = 1;</code> как обычная переменная не является корректным современным стилем и в новых версиях не компилируется как обычный идентификатор.</p>
<p>В сопоставлении с образцом и других разрешённых местах <code>_</code> улучшает читаемость: не нужно придумывать имя для значения, которое не будет использоваться.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>This feature is useful for declaring unused lambda parameters, exception parameters, loop variables and pattern components. It documents intent more strongly than names like <code>ignored</code> because accidental use is impossible.</p>
<p>Do not confuse Java’s <code>_</code> with wildcard or discard syntax in other languages. The exact allowed contexts are defined by Java, and ordinary method parameters or fields are not unnamed just because you want to ignore them.</p>
</td>
<td valign="top" width="50%">

<p><code>_</code> отличается от переменной с именем <code>ignored</code>. <code>ignored</code> можно случайно прочитать или использовать, а <code>_</code> не вводит читаемое имя. Это помогает компилятору и читателю одинаково понять намерение.</p>
<p>Команде важно учитывать версию Java. Код с современными возможностями вокруг <code>_</code> должен собираться тем JDK, который их поддерживает, а не просто выглядеть похожим на код из другой версии.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>When modernizing code, rename legacy underscore identifiers before upgrading. Use <code>_</code> deliberately in new code to reduce unused-variable noise and communicate that ignoring the value is part of the design.</p>
</td>
<td valign="top" width="50%">

<p>В рабочем коде <code>_</code> стоит использовать там, где он явно уменьшает шум: в образцах, lambda-параметрах, параметрах <code>catch</code> или локальных переменных, которые нужны только для побочного эффекта создания ресурса. Но он не должен скрывать полезную информацию от читателя.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>A single underscore is not a legal ordinary identifier.</li>
<li>You cannot read an unnamed variable later.</li>
<li>Multiple <code>_</code> placeholders can appear in one scope.</li>
<li>Do not assume every language’s underscore rules apply to Java.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Одиночный <code>_</code> нельзя использовать как обычный идентификатор.</li>
<li><code>_</code> нельзя прочитать как переменную.</li>
<li>Нужна версия Java, которая поддерживает конкретное использование <code>_</code>.</li>
<li>Не путайте <code>_</code> с соглашением именования; это синтаксическая возможность языка.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>Q: Почему <code>_</code> особый в современной Java?<br>A: Он зарезервирован не как обычное имя, а как обозначение намеренно неиспользуемой переменной или части образца.</p>
