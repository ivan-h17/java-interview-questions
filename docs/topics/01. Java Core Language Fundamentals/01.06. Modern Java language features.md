<details>
<summary><strong>JCORE-MODERN-001. What problem does `Optional` solve, and how should it be used?</strong></summary>

#### Short answer

`Optional<T>` represents an expected possible absence of a single return value. It makes absence explicit in the method signature and encourages callers to handle both cases instead of accidentally dereferencing `null`. It is best used as a return type, not as a universal null replacement.

#### Interview answer

A good use is `findUser(id): Optional<User>`, where “not found” is a normal outcome. The caller can use `map`, `flatMap`, `orElseThrow`, `orElseGet`, or `ifPresent` to handle absence explicitly.

Optional is not primarily about avoiding all nulls internally. It is an API signal. It tells the reader: this method may return no value, and that case is part of the contract, not an exceptional failure.

#### Deep dive

Use `Optional.empty()` for absence and `Optional.ofNullable(value)` when adapting possibly-null values. Use `Optional.of(value)` only when value must be non-null and a null should fail fast.

Avoid calling `get()` without checking. It turns Optional back into a nullable-like trap, except with `NoSuchElementException`. Prefer terminal operations that express the fallback or failure behavior.

#### Production angle

In backend APIs, Optional is useful for repository lookups and computations where absence is normal. For REST/JSON DTOs, entities and fields, check framework support and team conventions; explicit nullable annotations may be clearer.

#### Traps / caveats

- Optional should not be used just to avoid thinking about nullability.
- Do not return `null` from a method declared to return Optional.
- Avoid `optional.get()` without a presence check.
- For collections, returning an empty collection is usually better than `Optional<List<T>>`.

#### Optional Anki

Q: What is the best common use of `Optional`?
A: As a return type for an expected absent-or-present single value.

</details>

<a id="jcore-modern-002"></a>

<details>
<summary><strong>JCORE-MODERN-002. When should `Optional` not be used?</strong></summary>

#### Short answer

Avoid Optional for fields, DTO properties, entity attributes, method parameters, collections that can simply be empty, and performance-critical hot paths unless there is a clear benefit. It is mainly intended to communicate optional return values.

#### Interview answer

Optional parameters often make APIs awkward: callers must wrap values, and the method still needs to define what absence means. Overloading, separate methods, nullable annotations, or a parameter object can be clearer.

Optional fields can also cause friction with serializers, ORMs and validation frameworks. Some support it, some need configuration, and some produce awkward JSON or persistence models. For DTOs, explicit nullability rules may be more interoperable.

#### Deep dive

Do not use `Optional<List<T>>` when an empty list means “no results”. Use Optional only when there is a real distinction between “no value” and “a present empty value”.

Do not store Optional in collections as a routine practice. A collection of optionals often means the model is unclear; filter absent values or use a richer domain type.

#### Production angle

Team consistency matters. Pick conventions for API boundaries, persistence models and JSON contracts. Use Optional where it improves the contract; otherwise use explicit validation, annotations and clear defaults.

#### Traps / caveats

- Optional is not serializable-friendly in every framework/use case.
- Optional parameters often reduce readability.
- Optional fields can confuse ORM and JSON mapping.
- Empty collections are usually better than optional collections.

#### Optional Anki

Q: Should Optional usually be used for method parameters?
A: Usually no. Prefer overloads, nullable annotations, a parameter object, or clearer API design.

</details>

<details>
<summary><strong>JCORE-MODERN-003. What is the difference between `orElse()` and `orElseGet()`?</strong></summary>

#### Short answer

`orElse(value)` evaluates its argument eagerly, even when the Optional has a value. `orElseGet(supplier)` evaluates the supplier lazily only when the Optional is empty. Use `orElseGet` for expensive or side-effecting fallback creation.

#### Interview answer

The common trap is `userOpt.orElse(loadDefaultUser())`. `loadDefaultUser()` runs before `orElse` is called, regardless of whether `userOpt` is present. With `orElseGet(() -> loadDefaultUser())`, the method runs only if needed.

For cheap constants, `orElse` is perfectly fine: `name.orElse("anonymous")`. For database calls, object allocation, logging, metrics, timestamps or exceptions with expensive messages, prefer lazy forms.

#### Deep dive

Related methods follow the same idea. `orElseThrow()` throws when empty. `or(Supplier<Optional<T>>)` can lazily provide another Optional. `map` and `flatMap` apply transformations only when present.

Do not use `orElseGet` for readability theater when the fallback is a literal. The goal is to avoid unnecessary work or side effects, not to make every Optional chain longer.

#### Production angle

In backend code, the difference can cause unexpected database calls, remote calls, cache misses or audit events. Review Optional fallbacks that call methods, allocate heavy objects or mutate state.

#### Traps / caveats

- `orElse(expensive())` runs `expensive()` even when value is present.
- `orElseGet` supplier should be side-effect safe because it runs on absence.
- Use `orElse` for cheap constants.
- Do not confuse `orElseGet` with asynchronous execution; it is just lazy.

#### Optional Anki

Q: Which Optional fallback is lazy?
A: `orElseGet()`; `orElse()` evaluates its argument eagerly.

</details>

<details>
<summary><strong>JCORE-MODERN-004. What is local variable type inference with `var`, and when can it hurt readability?</strong></summary>

#### Short answer

`var` lets the compiler infer the type of a local variable from its initializer. It is still statically typed; the inferred type is fixed at compile time. It hurts readability when the initializer does not make the type or intent obvious.

#### Interview answer

`var` is allowed for local variables with initializers, enhanced-for variables, and lambda parameters when all explicitly declared lambda parameters use `var`. It is not allowed for fields, method return types, ordinary method parameters, or variables without initializers.

Good uses include obvious constructors, long generic types, and try-with-resources: `var users = new ArrayList<User>();`. Bad uses include vague factory calls: `var data = service.get();` when the type matters to understand the code.

#### Deep dive

The inferred type may be more specific or less general than the type you would write explicitly. For example, `var users = new ArrayList<User>();` infers `ArrayList<User>`, not `List<User>`, which can expose implementation-specific methods or make later refactoring harder.

`var` does not mean dynamic typing. You cannot assign a different incompatible type later. It also does not infer from future assignments; the initializer is required.

#### Production angle

Use `var` when it removes noise without hiding meaning. In code reviews, ask whether a reader can understand the type and business role from the initializer and variable name without jumping to the declaration target.

#### Traps / caveats

- `var` is not dynamic typing.
- `var` requires an initializer.
- `var` can hide important API types behind vague names.
- The variable name becomes more important when the type is omitted.
- In lambda parameters, either all explicitly declared parameter types use `var`, or none do.

#### Optional Anki

Q: Is `var` dynamically typed?
A: No. The compiler infers a static type at compile time.

</details>

<details>
<summary><strong>JCORE-MODERN-005. What are switch expressions, and how do they differ from old `switch` statements?</strong></summary>

#### Short answer

A switch expression produces a value. It supports arrow labels, requires exhaustive handling, and uses `yield` for block arms that return a value. Old switch statements are primarily control-flow statements and historically allowed fall-through unless `break` was used.

#### Interview answer

Example: `int len = switch (day) { case MONDAY, FRIDAY -> 6; default -> 0; };`. This directly assigns the result and avoids a mutable temporary variable plus repeated `break` statements.

Arrow labels `case X ->` do not fall through. If an arm needs multiple statements, use a block and `yield value;`. Switch expressions must cover all possible inputs, often with `default` unless the compiler can prove exhaustive handling.

#### Deep dive

Switch expressions became final in Java 14. They can use both arrow and traditional colon labels, but arrow labels are usually clearer because they avoid accidental fall-through.

Classic switch statements still exist and are useful for side effects. Modern Java also allows arrow-label switch statements, so “expression vs statement” and “arrow vs colon” are related but separate choices.

#### Production angle

Use switch expressions for mapping enum/domain states to values, HTTP statuses, messages or strategies. They reduce accidental fall-through and make missing cases more visible during compilation.

#### Traps / caveats

- Switch expressions must be exhaustive.
- Arrow cases do not fall through.
- `yield` is for returning a value from a block arm.
- `break` is not used to return values from switch expressions.

#### Optional Anki

Q: What must a switch expression do that a switch statement need not always do?
A: Be exhaustive and produce a value or throw on every path.

</details>

<details>
<summary><strong>JCORE-MODERN-006. What is pattern matching for `instanceof` useful for?</strong></summary>

#### Short answer

Pattern matching for `instanceof` combines a type test and cast in one construct. If the test succeeds, Java introduces a pattern variable with the tested type, reducing boilerplate and making type-safe conditional extraction clearer.

#### Interview answer

Instead of `if (obj instanceof String) { String s = (String) obj; ... }`, write `if (obj instanceof String s) { ... }`. The variable `s` is available only where the compiler knows the pattern matched.

This improves readability in validation, mapping, exception handling and code that deals with heterogeneous values. It also avoids accidental mismatch between the type checked and the type cast.

#### Deep dive

Pattern variable scope is flow-sensitive. In `if (!(obj instanceof User u)) return;`, `u` is available after the guard because the only remaining path is the successful match path.

Pattern matching does not change object type or perform deep destructuring by itself. It is still an `instanceof` test plus a typed binding. More advanced pattern matching appears in switch and record patterns.

#### Production angle

Use it to simplify safe type checks, especially in adapters, deserializers, domain event handling and exception mapping. Avoid long chains of `instanceof` when polymorphism or a visitor-like design would express the model better.

#### Traps / caveats

- Pattern variables exist only where the match is definitely true.
- It is not dynamic typing; the pattern variable has a static type.
- Do not replace good polymorphism with huge `instanceof` chains.
- A null reference does not match a type pattern.

#### Optional Anki

Q: What boilerplate does pattern matching for `instanceof` remove?
A: The separate cast after a successful type check.

</details>

<details>
<summary><strong>JCORE-MODERN-007. What are sealed classes and sealed interfaces?</strong></summary>

#### Short answer

Sealed classes and interfaces restrict which classes or interfaces may directly extend or implement them. A sealed type declares or implies its permitted subclasses, and each permitted subclass must choose whether it is `final`, `sealed`, or `non-sealed`.

#### Interview answer

They model a closed set of alternatives. For example, `sealed interface PaymentResult permits Approved, Declined, Error` says that these are the known direct variants. This is stronger than documentation and more flexible than making the root type package-private.

Permitted subclasses must be close enough to the sealed type according to module/package rules. This lets the compiler and readers know who is allowed to participate in the hierarchy.

#### Deep dive

A permitted subclass marked `final` stops extension. A permitted subclass marked `sealed` continues the controlled hierarchy. A permitted subclass marked `non-sealed` reopens that branch to arbitrary subclasses.

Sealed types work especially well with records and pattern matching for switch because the compiler can reason about the known alternatives.

#### Production angle

Use sealed types for domain alternatives that should be closed by design: result types, commands, events, state machines and error hierarchies. Avoid sealing extension points intended for external plugins or unknown future implementors.

#### Traps / caveats

- Sealed restricts direct subclasses, not object creation by itself.
- Every permitted subclass must declare `final`, `sealed`, or `non-sealed`.
- `non-sealed` deliberately reopens a branch.
- Sealed hierarchies are a modeling tool, not an access-control replacement for secrets.

#### Optional Anki

Q: What does a sealed type control?
A: Which classes or interfaces may directly extend or implement it.

</details>

<a id="jcore-modern-008"></a>

<details>
<summary><strong>JCORE-MODERN-008. When are sealed types useful in backend domain models?</strong></summary>

#### Short answer

Sealed types are useful when the domain has a known finite set of alternatives: payment outcomes, order states, commands, events, validation results, workflow steps or error categories. They make the model explicit and help the compiler check exhaustive handling.

#### Interview answer

Without sealed types, code often uses a base interface plus documentation saying “only these implementations exist”. Sealed types make that rule part of the type system. This is especially helpful when business logic switches over all variants.

They pair well with records: each variant can be a small immutable data carrier, while the sealed root expresses the closed family. Pattern matching switch can then handle each subtype directly.

#### Deep dive

Sealed types are less suitable when the hierarchy is intended for external extension, plugins, integrations, or unknown third-party implementors. In those cases, an open interface is more honest.

They also require versioning care. Adding a new permitted subtype is a source-level compatibility event for exhaustive switches: code may need to handle the new case. That is often a feature, not a bug, for domain models.

#### Production angle

Use sealed hierarchies inside bounded contexts where the team owns all variants. They improve readability, refactoring safety and test coverage for exhaustive business rules. For public extension APIs, prefer open interfaces unless closure is part of the contract.

#### Traps / caveats

- Adding a variant forces exhaustive handlers to be revisited.
- Sealed roots are not ideal for plugin ecosystems.
- Serialization frameworks may need subtype metadata/configuration.
- Closed alternatives should reflect real domain stability, not just current implementation convenience.

#### Optional Anki

Q: Why do sealed types fit domain alternatives?
A: They encode the finite set of allowed variants in the type system.

</details>

<details>
<summary><strong>🧠 JCORE-MODERN-009. How should teams think about preview Java features in production code?</strong></summary>

#### Short answer

Preview features are high-quality but not final Java features. They require explicit preview enablement and may change, be finalized differently, or be removed in later releases. Production teams should use them only with deliberate governance, version pinning and migration plans.

#### Interview answer

The key risk is lifecycle. Code compiled with preview features is tied to the Java release whose preview it used; later JDKs are not required to run or compile it unchanged. Build tools, IDEs, CI, containers and runtime flags all need to agree.

Preview does not mean “toy” or “unstable experiment”; it means the feature is intended for feedback before becoming permanent. But using it in distributed production artifacts still increases maintenance and upgrade risk.

#### Deep dive

A reasonable policy is: allow preview features in experiments, prototypes, benchmarks and isolated internal tools; be cautious in core services and shared libraries; avoid them in public APIs unless the organization accepts the compatibility cost.

When using preview features, document the JDK version, enable flags explicitly, add upgrade tickets, and run CI on the exact JDK. Revisit the code when the feature is re-previewed or finalized.

#### Production angle

For senior backend work, the answer is not “never” or “always”. It is risk management: consider support windows, deployment platform, framework compatibility, operational ownership and the cost of rewriting code on the next JDK.

#### Traps / caveats

- Preview features are disabled by default and require opt-in.
- Preview class files are tied to a specific Java release.
- A preview feature can change before finalization.
- Shared libraries should be more conservative than local experiments.

#### Optional Anki

Q: What is the main production risk of preview features?
A: Compatibility and upgrade risk because preview code is tied to a specific Java release and feature design may change.

</details>

<details>
<summary><strong>JCORE-MODERN-010. What are records in Java, and what problem do they solve?</strong></summary>

#### Short answer

Records are special classes for transparent immutable data carriers. A record declares components and the compiler provides a canonical constructor, accessors, `equals()`, `hashCode()` and `toString()` based on those components.

#### Interview answer

They solve the boilerplate problem for simple value-like aggregates: DTO-like results, keys, coordinates, domain values and messages. Instead of writing fields, constructor, accessors and equality manually, you declare `record Money(BigDecimal amount, Currency currency) {}`.

Records are nominal classes, not anonymous tuples. A `Money` record and a `Price` record with the same components are different types. Records can implement interfaces and have methods, but they are final and cannot extend arbitrary classes.

#### Deep dive

Record fields are final, but record immutability is shallow. If a component is a mutable list, the reference cannot be reassigned but the list contents can still mutate unless you make defensive copies.

A compact constructor can validate and normalize components. It should preserve the record’s transparent data-carrier promise: do not hide surprising mutable behavior behind a record shape.

#### Production angle

Use records for small immutable-ish carriers at service boundaries, query results, events and value objects when their identity is exactly their components. Use regular classes when behavior, lifecycle, inheritance, encapsulation or mutability is central.

#### Traps / caveats

- Records are final.
- Record immutability is shallow.
- Accessors are named `amount()`, not JavaBean `getAmount()` by default.
- Do not use records for entities with complex lifecycle identity unless the fit is deliberate.

#### Optional Anki

Q: What methods does a record generate from its components?
A: Accessors, canonical constructor, `equals()`, `hashCode()` and `toString()`.

</details>

<a id="jcore-modern-011"></a>

<details>
<summary><strong>JCORE-MODERN-011. When should you use a record instead of a regular class?</strong></summary>

#### Short answer

Use a record when the type is mainly a transparent carrier for a fixed set of values and equality should be based on those values. Use a regular class when you need mutable state, hidden representation, complex invariants, inheritance, lazy behavior, or identity separate from the fields.

#### Interview answer

Good record candidates: request/response projections, query results, compound map keys, small domain values, events and command payloads. The reader should be comfortable seeing all components in the type declaration.

Poor candidates: JPA entities with generated IDs and lazy associations, classes that must follow JavaBean conventions, objects with significant mutable lifecycle, and types whose equality must ignore some fields.

#### Deep dive

Records can still have validation, normalization, derived methods and static factories. They are not limited to an empty body. But they should remain transparent: the declared components should explain the state that defines the value.

If a component is mutable, consider copying it in the constructor and accessor. Otherwise a record may look immutable while exposing mutable internals.

#### Production angle

In backend teams, records are great for internal DTOs and value objects on modern Java versions. Check framework compatibility for serialization, validation and reflection, especially if APIs expect JavaBean getters or no-arg constructors.

#### Traps / caveats

- Records are not a replacement for all DTO/entity classes.
- Frameworks may require extra configuration for record constructors/accessors.
- Component order and names are part of the record API.
- Mutable components require defensive-copy decisions.

#### Optional Anki

Q: What is the main design test for using a record?
A: Whether the type is a transparent value carrier whose equality is its declared components.

</details>

<details>
<summary><strong>JCORE-MODERN-012. What are text blocks, and when are they useful?</strong></summary>

#### Short answer

Text blocks are multi-line string literals delimited by triple quotes. They are useful for embedded SQL, JSON, XML, HTML, test fixtures and messages where ordinary string literals would require noisy escaping and concatenation.

#### Interview answer

A text block starts with `"""` followed by a line terminator, then content, then closing `"""`. The compiler normalizes line terminators, removes incidental indentation and interprets escape sequences.

They improve readability of structured text: SQL queries in tests, JSON payload examples, expected files, templates and documentation snippets. They are still ordinary `String` values at runtime, not a new string type.

#### Deep dive

Text blocks do not provide interpolation by themselves. Use `formatted`, `String.format`, template engines or prepared statements depending on the use case.

Indentation and trailing newline behavior matter. The position of the closing delimiter influences incidental indentation stripping; putting it on the same line as content can avoid a final newline.

#### Production angle

Text blocks are excellent for test fixtures and readable SQL, but do not build unsafe SQL by concatenating user input. For production SQL with parameters, still use prepared statements, jOOQ, JPA parameters or another safe binding mechanism.

#### Traps / caveats

- Text blocks are not raw strings; escapes are still processed.
- They do not do interpolation automatically.
- Trailing newline may surprise tests.
- Readable SQL string is not automatically safe SQL.

#### Optional Anki

Q: Are text blocks a new runtime string type?
A: No. They compile to ordinary `String` values.

</details>

<details>
<summary><strong>JCORE-MODERN-013. What is pattern matching for `switch`, and how does it differ from classic `switch`?</strong></summary>

#### Short answer

Pattern matching for `switch` lets `case` labels contain type patterns and guarded patterns, so a switch can dispatch by type and conditions, not only by constants. It differs from classic switch by supporting richer matching, null handling when declared, and exhaustiveness checking for pattern switches.

#### Interview answer

Classic switch historically matched constants of limited types such as ints, enums and strings. Pattern switch can say `case String s ->`, `case Integer i when i > 0 ->`, or `case null ->`. This replaces many `if/else instanceof` chains.

Pattern switch became final in Java 21. It works with both switch expressions and switch statements, and it pairs especially well with sealed hierarchies because the compiler can know all permitted variants.

#### Deep dive

Pattern order matters because earlier cases can dominate later cases. A broad `case Object o` before `case String s` would make the string case unreachable. Guards make matching more precise but can also affect exhaustiveness reasoning.

Null handling is explicit. A pattern such as `case String s` does not match null. Use `case null` or `case null, default` when null is part of the accepted input.

#### Production angle

Use pattern switch for closed domain alternatives, event handling, result mapping and adapter code. Avoid using it to centralize behavior that belongs polymorphically on domain objects, unless exhaustive external handling is the clearer design.

#### Traps / caveats

- Case order can make later patterns unreachable.
- Null must be handled explicitly if accepted.
- Dominance and exhaustiveness errors are compile-time feedback.
- Pattern switch can be clearer than visitors for simple closed hierarchies, but not always.

#### Optional Anki

Q: What does pattern switch add to classic switch?
A: Cases can match patterns such as types and guarded conditions, not just constants.

</details>

<details>
<summary><strong>🧠 JCORE-MODERN-014. How do sealed classes help make `switch` exhaustive?</strong></summary>

#### Short answer

Sealed classes tell the compiler the complete set of permitted direct subtypes. When a switch handles all permitted alternatives, the compiler can treat it as exhaustive without requiring a catch-all default in many cases.

#### Interview answer

For a sealed root like `sealed interface Result permits Success, Failure`, a switch expression with `case Success s` and `case Failure f` covers the known family. If a new permitted subtype is later added, recompilation can reveal switches that need updating.

This is powerful because missing domain cases become compile-time problems rather than runtime surprises. It is similar to exhaustive enum switches, but for class hierarchies.

#### Deep dive

Exhaustiveness depends on the static type of the switch selector and the sealed hierarchy known to the compiler. If a branch is `non-sealed`, the compiler must account for unknown subtypes under that branch, often requiring a broader case.

A default case can be useful for defensive compatibility, but it can also hide the fact that a new domain variant deserves explicit handling. For internal domain models, explicit cases are often better.

#### Production angle

Use sealed plus switch for workflows, command/result models and error mapping where every variant must be handled. Treat new subtype compiler errors as helpful prompts to update business logic and tests.

#### Traps / caveats

- A `default` branch can hide newly added variants.
- `non-sealed` branches reduce exhaustiveness precision.
- Exhaustiveness is checked at compile time, so recompilation matters.
- The selector’s static type affects what the compiler can prove.

#### Optional Anki

Q: Why do sealed types help switch exhaustiveness?
A: The compiler knows the permitted subtype set and can verify all alternatives are handled.

</details>

<details>
<summary><strong>JCORE-MODERN-015. What are unnamed variables and patterns?</strong></summary>

#### Short answer

Unnamed variables and patterns use the underscore character `_` to declare that a value or binding is intentionally unused. They improve readability and let the compiler enforce that the unused binding is not accidentally referenced.

#### Interview answer

Unnamed variables are useful in enhanced for loops, catch blocks, lambda parameters, try-with-resources and local declarations where the side effect matters but the value does not. Example: `for (var _ : orders) count++;`.

Unnamed patterns are useful inside pattern matching when a nested component must be matched structurally but does not need a name. They make pattern code shorter and communicate intent.

#### Deep dive

Each `_` is not a variable name you can read later. It is a placeholder for an unnamed binding. Multiple underscores can appear in the same scope because they do not introduce ordinary names.

Unnamed variables and patterns were finalized in Java 22. They are not for fields or ordinary method parameters; their scope is limited to specific local variable and pattern contexts.

#### Production angle

Use `_` when ignoring a value is intentional and important for maintainability, not as a way to avoid naming things you should understand. It can reduce warnings and make catch/lambda/loop intent explicit.

#### Traps / caveats

- You cannot read from an unnamed variable.
- Unnamed variables are not ordinary variables named underscore.
- They are not allowed in every declaration context.
- Do not use `_` to hide unclear code; use it to express intentional non-use.

#### Optional Anki

Q: What does `_` mean as an unnamed variable?
A: A value is intentionally ignored and no ordinary variable name is introduced.

</details>

<a id="jcore-modern-016"></a>

<details>
<summary><strong>🧠 JCORE-MODERN-016. Why is `_` special in modern Java?</strong></summary>

#### Short answer

`_` is special because it is reserved and cannot be used as an ordinary identifier. Modern Java uses it for unnamed variables and unnamed patterns, meaning “this value is intentionally unused”.

#### Interview answer

Historically, some code used underscore as a variable name. Java 8 warned about this, and Java 9 made `_` unusable as an ordinary identifier. Later, Java used that reserved syntax for unnamed variables and patterns.

The important semantic point is that `_` does not create a normal binding. You cannot later write `System.out.println(_)`. Multiple underscores in one scope are allowed because they are not names that collide.

#### Deep dive

This feature is useful for declaring unused lambda parameters, exception parameters, loop variables and pattern components. It documents intent more strongly than names like `ignored` because accidental use is impossible.

Do not confuse Java’s `_` with wildcard or discard syntax in other languages. The exact allowed contexts are defined by Java, and ordinary method parameters or fields are not unnamed just because you want to ignore them.

#### Production angle

When modernizing code, rename legacy underscore identifiers before upgrading. Use `_` deliberately in new code to reduce unused-variable noise and communicate that ignoring the value is part of the design.

#### Traps / caveats

- A single underscore is not a legal ordinary identifier.
- You cannot read an unnamed variable later.
- Multiple `_` placeholders can appear in one scope.
- Do not assume every language’s underscore rules apply to Java.

#### Optional Anki

Q: Can Java code use `_` as a normal variable name?
A: No. It is reserved/special and is used for unnamed variables and patterns in modern Java.

</details>
