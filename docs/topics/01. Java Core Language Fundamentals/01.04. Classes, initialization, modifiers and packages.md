# 4. Classes, initialization, modifiers and packages


<a id="jcore-class-001"></a>

<details>
<summary><strong>JCORE-CLASS-001. How does object initialization work: fields, instance initializers and constructors?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Object initialization first allocates the object and gives fields default values. In the common order, superclass construction runs before this class’s instance field initializers and instance initializer blocks, and then the constructor epilogue finishes. Modern Java also allows a restricted constructor prologue before an explicit <code>super(...)</code> or <code>this(...)</code>, so the “constructor body runs last” shortcut needs that caveat.</p>
</td>
<td valign="top" width="50%">

<p>Инициализация объекта начинается с выделения памяти и значений по умолчанию для полей. В обычной схеме сначала выполняется конструирование суперкласса, затем инициализаторы полей и блоки инициализации экземпляра текущего класса, а после этого — оставшаяся часть конструктора. Начиная с Java 25 у конструктора может быть ограниченный пролог перед явным <code>super(...)</code> или <code>this(...)</code>, поэтому правило «тело конструктора всегда выполняется последним» требует оговорки.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>When Java executes <code>new Child()</code>, it normally initializes the object from the top of the hierarchy down. The memory for the whole object exists first, and superclass construction precedes subclass initialization code that depends on a fully initialized receiver. Since Java 25, a constructor may have a restricted prologue before explicit delegation, but ordinary instance initializers still run as part of the current class’s construction path.</p>
<p>This means field initializers are not “magical defaults”; they are executable initialization code inserted into constructors. If there are multiple constructors, the initializer code is effectively run for each construction path after the superclass constructor has completed.</p>
</td>
<td valign="top" width="50%">

<p>Когда Java выполняет <code>new Child()</code>, объект обычно строится сверху вниз по иерархии наследования. Память под весь объект уже выделена, но код инициализации подкласса, которому нужен полностью подготовленный получатель, выполняется после конструктора суперкласса. Java 25 добавляет ограниченный пролог конструктора, но обычные инициализаторы экземпляра всё равно остаются частью пути конструирования текущего класса.</p>
<p>Инициализаторы полей — это не «магические значения», а исполняемый код инициализации, который компилятор фактически добавляет в конструкторы. Если у класса несколько конструкторов, этот код выполняется на каждом корректном пути создания объекта после завершения конструктора суперкласса.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Useful baseline order: default values first; explicit superclass constructor; instance variable initializers and instance initializer blocks of the current class in textual order; then the constructor epilogue. The Java 25 flexible-constructor-body feature adds a restricted prologue before explicit delegation, but that prologue is not a license to use a half-built object freely. Static initialization is separate and happens at class initialization time, not once per object.</p>
<p>A dangerous edge case is calling overridable methods from constructors. Dynamic dispatch already works while the subclass part may not be initialized yet, so a superclass constructor can call a subclass method that observes default values in subclass fields.</p>
</td>
<td valign="top" width="50%">

<p>Базовый порядок удобно помнить так: сначала значения по умолчанию, затем явный или неявный конструктор суперкласса, затем инициализаторы полей экземпляра и блоки инициализации экземпляра текущего класса в порядке объявления, затем эпилог конструктора. Статическая инициализация — отдельный процесс: она происходит при инициализации класса, а не при каждом создании объекта.</p>
<p>Опасный случай — вызов переопределяемых методов из конструктора. Динамическая диспетчеризация уже работает, хотя часть подкласса может быть ещё не инициализирована, поэтому конструктор суперкласса способен вызвать метод подкласса, который увидит значения полей по умолчанию.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production code, keep constructors simple, validate required arguments early, avoid starting threads or publishing <code>this</code> during construction, and prefer factory methods/builders when initialization has many branches. For dependency-injected services, avoid heavy work in constructors; use lifecycle hooks deliberately.</p>
</td>
<td valign="top" width="50%">

<p>В рабочем коде конструкторы лучше держать простыми: рано проверять обязательные аргументы, не запускать потоки и не публиковать <code>this</code> во время конструирования. Если инициализация разветвлённая или тяжёлая, обычно удобнее фабричный метод, строитель (builder) или явный жизненный цикл. В сервисах с внедрением зависимостей (dependency injection) тяжёлую работу лучше не прятать в конструкторе.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Fields have default values before explicit initializers run.</li>
<li>Instance initializer blocks run before the constructor body, not after it.</li>
<li>Superclass construction normally happens before subclass initialization that depends on the constructed receiver; Java 25 constructor prologues are restricted.</li>
<li>Calling overridable methods from constructors can expose partially initialized state.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Поля получают значения по умолчанию до выполнения явных инициализаторов.</li>
<li>Блоки инициализации экземпляра выполняются до основной части конструктора текущего класса.</li>
<li>Конструирование суперкласса обычно предшествует инициализации подкласса; прологи конструкторов в Java 25 имеют строгие ограничения.</li>
<li>Вызов переопределяемых методов из конструктора может открыть частично инициализированное состояние.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the usual order before a constructor epilogue in the same class?<br>A: Superclass construction, then instance field initializers and instance initializer blocks in source order; Java 25 adds a restricted prologue caveat.</p>
</td>
<td valign="top" width="50%">

<p>Q: Каков обычный порядок перед эпилогом конструктора текущего класса?<br>A: Конструктор суперкласса, затем инициализаторы полей и блоки инициализации экземпляра в порядке объявления; для Java 25 нужно помнить об ограниченном прологе конструктора.</p>

</td>
</tr>

<a id="jcore-class-002"></a>

<details>
<summary><strong>JCORE-CLASS-002. When is a Java class initialized?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A class is initialized when it is first actively used: for example when creating an instance, invoking a static method, reading or writing a non-constant static field, or using reflection in ways that trigger initialization. Initialization runs static field initializers and static initializer blocks once per class loader.</p>
</td>
<td valign="top" width="50%">

<p>Класс инициализируется при первом активном использовании (active use): например при создании экземпляра, вызове статического метода или чтении/записи статического поля, которое не является константной переменной. Перед этим JVM загружает и связывает класс; сама инициализация выполняет статические инициализаторы и присваивания статическим полям.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Loading a class and initializing a class are not the same. Loading makes the class available to the JVM; linking verifies and prepares it; initialization executes the class’s static initialization code. Before a class is initialized, its superclass is initialized first, except for special interface rules.</p>
<p>Accessing a compile-time constant such as <code>public static final int PORT = 8080;</code> usually does not initialize the declaring class because the value can be inlined into the client class. Accessing <code>static final</code> values computed at runtime does initialize the class.</p>
</td>
<td valign="top" width="50%">

<p>Инициализация класса — это момент, когда выполняются <code>static</code>-инициализаторы и выражения инициализации статических полей. Она происходит один раз для конкретного класса в рамках конкретного загрузчика классов. Типичные триггеры: <code>new</code>, вызов статического метода, обращение к неконстантному статическому полю, некоторые операции рефлексии и инициализация подкласса, если сначала нужно инициализировать суперкласс.</p>
<p>Важно отличать загрузку класса от его инициализации. Класс может быть найден, проверен и подготовлен раньше, но статический код не обязан выполниться до первого активного использования.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The JVM synchronizes class initialization so that only one thread runs the initialization code. Other threads needing the same class wait until initialization completes or fails. If initialization fails, later uses can see <code>NoClassDefFoundError</code> because the class is considered erroneous.</p>
<p>Class initialization is lazy. Merely importing a class, declaring a variable of that type, or referring to its class literal in some cases is not the same as executing its static initialization code. Active use is the key concept.</p>
</td>
<td valign="top" width="50%">

<p>Сначала JVM загружает байткод, затем выполняет связывание: проверку, подготовку и разрешение ссылок по мере необходимости. На этапе подготовки статические поля получают значения по умолчанию, а реальные выражения вроде <code>static int x = compute();</code> выполняются уже при инициализации.</p>
<p>Доступ к константной переменной — например к <code>static final int PORT = 8080</code>, если значение является константным выражением, — обычно не запускает инициализацию класса у клиента, потому что значение может быть встроено компилятором.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In services, class initialization bugs often appear only on first request or first access to a rarely used code path. Avoid doing network calls, file IO, secret loading or complex dependency wiring in static initializers; make startup behavior explicit and observable instead.</p>
</td>
<td valign="top" width="50%">

<p>На практике это влияет на время старта, ленивую загрузку и диагностику ошибок. Тяжёлая статическая инициализация может неожиданно замедлить первый запрос, а ошибка в ней может сделать класс непригодным для дальнейшего использования в этом загрузчике классов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>import</code> never initializes a class.</li>
<li>Reading a compile-time constant may not initialize the declaring class.</li>
<li>Initialization is once per class loader, not once per JVM globally.</li>
<li>Failed initialization can poison later class use.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Загрузка класса и инициализация класса — разные этапы.</li>
<li>Инициализация выполняется один раз на пару «класс + загрузчик классов».</li>
<li>Чтение константной переменной обычно не запускает инициализацию класса.</li>
<li>Инициализация подкласса требует предварительной инициализации его суперклассов.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Does reading every <code>static final</code> field initialize its class?<br>A: No. Reading a compile-time constant can be compiled as an inlined constant and not trigger initialization.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что обычно запускает инициализацию класса?<br>A: Первое активное использование: <code>new</code>, статический метод, неконстантное статическое поле или некоторые операции рефлексии.</p>

</td>
</tr>
</tbody>
</table>

<a id="jcore-class-003"></a>

<details>
<summary><strong>🧠 JCORE-CLASS-003. What can go wrong with static initialization?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Static initialization can fail, run too early, run in an unexpected order, deadlock, hide slow IO, or expose partially initialized state through circular references. Because it happens once and is tied to class loading, failures can make the class unusable for the rest of the JVM lifetime for that class loader.</p>
</td>
<td valign="top" width="50%">

<p>Со статической инициализацией могут возникать задержки старта, скрытые обращения к сети или диску, взаимные блокировки, циклы между классами и ошибки, после которых класс становится непригодным для использования. Поэтому статический код должен быть простым, быстрым и предсказуемым.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Static initializers look convenient for constants and simple caches, but they are dangerous when they perform real work. Exceptions are wrapped in <code>ExceptionInInitializerError</code>, and other threads may block waiting for the class initialization lock. If initialization depends on another class that depends back on the first one, one side may observe default values.</p>
<p>Another common issue is order inside one class: static fields and static blocks execute in source order. A field initializer that reads another static field declared later may see its default value, not the value assigned later.</p>
</td>
<td valign="top" width="50%">

<p>Статическая инициализация выполняется под управлением JVM и защищается блокировкой инициализации класса. Если в ней делать тяжёлую работу, брать чужие блокировки, обращаться к внешним сервисам или запускать потоки, можно получить очень неприятные проблемы: зависание при старте, порядок-зависимые ошибки или отказ класса при первом обращении.</p>
<p>Если статический инициализатор бросает исключение, JVM оборачивает его в <code>ExceptionInInitializerError</code>. После неудачной инициализации класс в этом загрузчике обычно считается ошибочным, и последующие обращения могут заканчиваться уже другими ошибками, например <code>NoClassDefFoundError</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Static initialization is synchronized per class. If two classes initialize on different threads and each initializer waits for the other class, a deadlock is possible. This is rare, but very hard to debug because stack traces point at class loading rather than ordinary application code.</p>
<p>Static initialization also interacts badly with tests and containers. Mutable static fields can retain state across tests, across requests, or across redeploys depending on class loader behavior.</p>
</td>
<td valign="top" width="50%">

<p>Частая ловушка — циклическая статическая инициализация. Класс <code>A</code> при инициализации обращается к <code>B</code>, а <code>B</code> в ответ читает ещё не присвоенное поле <code>A</code>. Код компилируется, но во время выполнения можно увидеть <code>null</code>, <code>0</code> или частично подготовленное состояние.</p>
<p>Вторая ловушка — неявные зависимости: статический логгер, реестр, кеш, настройка часового пояса или чтение конфигурации. Всё это выглядит безобидно, пока порядок загрузки и окружение не меняются.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Prefer simple static constants and immutable stateless helpers. Use dependency injection, explicit startup components, lazy holders, memoized suppliers, or lifecycle-managed caches for expensive initialization. Log and fail explicitly rather than hiding startup work in class initialization.</p>
</td>
<td valign="top" width="50%">

<p>В сервисах статическую инициализацию лучше ограничивать константами и простыми неизменяемыми объектами. Конфигурацию, подключения, кеши и фоновые задачи безопаснее создавать через внедрение зависимостей (dependency injection) или явный жизненный цикл приложения, где ошибки можно контролируемо обработать и залогировать.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Static initialization order inside a class is textual.</li>
<li>Exceptions become <code>ExceptionInInitializerError</code>.</li>
<li>Circular initialization can expose default values instead of intended values.</li>
<li>Slow or blocking static initialization can make first request latency unpredictable.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не выполняйте сетевые вызовы и тяжёлый ввод-вывод в статических инициализаторах.</li>
<li>Не берите чужие блокировки из статической инициализации: это может привести к дедлоку.</li>
<li>Не полагайтесь на порядок инициализации независимых классов.</li>
<li>Исключение в статической инициализации может «испортить» класс для текущего загрузчика.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why should heavy IO be avoided in static initializers?<br>A: It hides startup work in class loading, can block class initialization, and can poison the class if it fails.</p>
</td>
<td valign="top" width="50%">

<p>Q: Почему статическая инициализация опасна?<br>A: Она выполняется неявно, один раз, под блокировкой JVM; задержки, циклы и исключения могут сломать первый доступ к классу.</p>

</td>
</tr>

<a id="jcore-class-004"></a>

<details>
<summary><strong>JCORE-CLASS-004. What are the rules for constructor chaining with <code>this()</code> and <code>super()</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>this(...)</code> calls another constructor in the same class; <code>super(...)</code> calls a superclass constructor. A constructor still has at most one explicit constructor invocation, and it cannot directly call both. On modern Java, statements may appear before that invocation in a restricted constructor prologue; older Java required <code>this(...)</code> or <code>super(...)</code> to be the first statement. If neither is written, Java inserts an implicit no-argument <code>super()</code>.</p>
</td>
<td valign="top" width="50%">

<p>Конструктор может явно делегировать либо другому конструктору этого же класса через <code>this(...)</code>, либо конструктору суперкласса через <code>super(...)</code>, но не обоим сразу. Если явного вызова нет, компилятор добавляет <code>super()</code>. Исторически такой вызов должен был быть первой инструкцией, а Java 25 допускает ограниченный пролог перед ним.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Constructor chaining exists to guarantee that each construction path eventually initializes superclass state and then current-class state. A <code>this()</code> call delegates to another constructor in the same class; that chain eventually reaches a constructor that invokes <code>super()</code>, explicitly or implicitly.</p>
<p>The traditional interview rule is “constructor delegation must happen first”. Since Java 25, the better answer is more nuanced: Java supports flexible constructor bodies, so a restricted prologue may run before <code>this(...)</code> or <code>super(...)</code>. The prologue can validate parameters or compute arguments, but it is in an early construction context and generally cannot use the object under construction.</p>
</td>
<td valign="top" width="50%">

<p>Цепочка конструкторов должна в итоге дойти до конструктора суперкласса и далее до <code>Object</code>. Вызов <code>this(...)</code> используется для переиспользования логики между конструкторами одного класса; <code>super(...)</code> выбирает конкретный конструктор родителя. Цикл из вызовов <code>this(...)</code> запрещён компилятором.</p>
<p>До завершения делегирования объект ещё находится в раннем контексте конструирования. Поэтому Java ограничивает доступ к <code>this</code> и к членам экземпляра до того, как суперкласс будет корректно сконструирован.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The compiler rejects recursive constructor invocation, such as constructor A calling B and B calling A. It also rejects an implicit <code>super()</code> if the superclass has no accessible no-argument constructor. Arguments to <code>this(...)</code> or <code>super(...)</code> are evaluated before entering the target constructor.</p>
<p>In Java 25 flexible constructor bodies split a constructor body into a prologue before the explicit constructor invocation and an epilogue after it. In the early construction context, code cannot read instance state, call instance methods, use ordinary <code>this</code>, or use <code>super</code> members, because the object is not yet safely initialized. Java does allow certain field assignments before <code>super()</code>, which can help avoid superclass constructor callbacks observing default subclass field values.</p>
<p>Records have specialized constructor rules: record constructors may not call <code>super(...)</code>; noncanonical constructors delegate to the canonical constructor with <code>this(...)</code>. Compact constructors are mainly for validation and normalization of record components.</p>
</td>
<td valign="top" width="50%">

<p>Если у родителя нет доступного конструктора без аргументов, подкласс обязан явно вызвать подходящий <code>super(...)</code>. Аргументы для <code>super(...)</code> вычисляются до входа в конструктор суперкласса, поэтому здесь тоже нужно избегать обращений к ещё не готовому состоянию объекта.</p>
<p>Java 25 с гибким телом конструктора разрешает некоторые инструкции перед явным <code>super(...)</code> или <code>this(...)</code>, например проверку и подготовку аргументов. Но это не отменяет фундаментального правила: объект нельзя свободно использовать до корректного построения родительской части.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use constructor chaining to reduce duplication, but keep chains obvious. A constructor prologue is good for cheap parameter validation and argument preparation; do not turn it into a hidden initialization framework. For complex creation logic, prefer static factories or builders so validation, defaults and invariants remain readable and testable.</p>
</td>
<td valign="top" width="50%">

<p>На интервью и в код-ревью хороший ответ — использовать <code>this(...)</code> для устранения дублирования, но не прятать сложную бизнес-логику в цепочке конструкторов. Проверки аргументов лучше делать явно и близко к месту, где они нужны.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>this()</code> and <code>super()</code> cannot both appear directly in the same constructor.</li>
<li>In Java 25+, statements may appear before them only under early-construction-context restrictions.</li>
<li>Older Java baselines require explicit constructor invocation to be the first statement.</li>
<li>Implicit <code>super()</code> requires an accessible no-argument superclass constructor.</li>
<li>Recursive constructor chains are compile-time errors.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Нельзя вызвать и <code>this(...)</code>, и <code>super(...)</code> из одного конструктора.</li>
<li>Если явного вызова нет, компилятор пытается вставить <code>super()</code>.</li>
<li>Циклическая цепочка <code>this(...)</code> не компилируется.</li>
<li>Java 25 разрешает ограниченный пролог конструктора, но не свободное использование <code>this</code> до делегирования.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the Java 25 update to the old “super must be first” rule?<br>A: A restricted constructor prologue may run before <code>this(...)</code> or <code>super(...)</code>, but it cannot freely access the object under construction.</p>
</td>
<td valign="top" width="50%">

<p>Q: Чем отличаются <code>this(...)</code> и <code>super(...)</code> в конструкторе?<br>A: <code>this(...)</code> делегирует другому конструктору текущего класса, а <code>super(...)</code> вызывает конструктор суперкласса.</p>

</td>
</tr>

<a id="jcore-class-005"></a>

<details>
<summary><strong>JCORE-CLASS-005. What does <code>static</code> mean for fields, methods and nested classes?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>static</code> means “belongs to the class rather than to a particular instance”. A static field is one variable per class loader, a static method is called without an instance and is not dynamically dispatched, and a static nested class has no implicit reference to an outer object.</p>
</td>
<td valign="top" width="50%">

<p><code>static</code> означает принадлежность классу, а не конкретному экземпляру. Статическое поле хранится на уровне класса, статический метод вызывается без динамической диспетчеризации по объекту, а статический вложенный класс не содержит неявной ссылки на внешний объект.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For fields, <code>static</code> is shared class state. All instances see the same field. For methods, <code>static</code> means the method is resolved by the compile-time type and cannot access instance members without an explicit object reference.</p>
<p>For nested classes, <code>static</code> means the nested class is just scoped inside the outer class name. It can access private members of the outer class by normal compiler-supported access, but it does not capture a particular outer instance.</p>
</td>
<td valign="top" width="50%">

<p>Для поля <code>static</code> означает одно значение на класс в рамках загрузчика классов. Для метода — что метод выбирается по статическому типу и не является полиморфным экземплярным методом. Для вложенного класса — что ему не нужен экземпляр внешнего класса.</p>
<p>Важно не путать <code>static</code> с «глобальной переменной без последствий». Изменяемое статическое состояние разделяется между потоками, тестами и иногда арендаторами приложения, поэтому требует особой осторожности.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Static members are inherited in the sense that they can be referenced through subclass names, but static methods are hidden, not overridden. Calling a static method through an instance is legal but misleading because the chosen method still depends on the declared type, not the runtime object.</p>
<p>Static fields are initialized during class initialization. If mutable, they are shared across all threads and requests using that class loader, so thread-safety and lifecycle become global concerns.</p>
</td>
<td valign="top" width="50%">

<p>Статические члены доступны через имя класса, и такой стиль обычно предпочтительнее, чем вызов через объект. Статические методы могут быть скрыты методом с такой же сигнатурой в подклассе, но это не переопределение.</p>
<p>Статический вложенный класс часто используют для builder, вспомогательных типов или группировки тесно связанного кода. В отличие от внутреннего класса, он не удерживает внешний экземпляр и поэтому реже создаёт неожиданные утечки памяти.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use static for true constants, stateless utility methods, factories, and nested helper types that do not need an outer instance. Avoid mutable static state in services unless it is intentionally shared, thread-safe, observable and lifecycle-managed.</p>
</td>
<td valign="top" width="50%">

<p>Хорошие кандидаты для <code>static</code> — константы, чистые утилитные методы и вложенные типы без зависимости от внешнего экземпляра. Плохие кандидаты — изменяемые реестры, глобальная конфигурация, кэши без жизненного цикла и состояние, зависящее от запроса.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Static methods are not polymorphic instance methods.</li>
<li>A static nested class is not an inner class.</li>
<li>Mutable static fields create global shared state.</li>
<li>Calling static methods via object references hurts readability.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Статический метод не переопределяется; он скрывается.</li>
<li>Статическое поле не принадлежит объекту, даже если к нему обратиться через ссылку.</li>
<li>Одно и то же статическое поле существует отдельно для разных загрузчиков классов.</li>
<li>Изменяемое статическое состояние почти всегда требует синхронизации или замены на управляемую зависимость.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Does a static nested class hold an implicit outer instance reference?<br>A: No. Only non-static inner classes do.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что означает <code>static</code> у вложенного класса?<br>A: У такого класса нет неявной ссылки на экземпляр внешнего класса.</p>

<a id="jcore-class-006"></a>

<details>
<summary><strong>JCORE-CLASS-006. What does <code>final</code> mean for variables, fields, methods and classes?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>final</code> means different but related things depending on the target: a final variable can be assigned only once, a final field cannot be reassigned after construction or static initialization, a final method cannot be overridden, and a final class cannot be subclassed.</p>
</td>
<td valign="top" width="50%">

<p><code>final</code> запрещает повторное присваивание переменной или поля, переопределение метода и наследование от класса. Но <code>final</code> у ссылки не делает сам объект неизменяемым: он запрещает только заменить ссылку другой.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For local variables and parameters, <code>final</code> prevents reassignment of the variable. It does not make the object immutable. A <code>final List</code> variable cannot point to another list, but the list contents may still change.</p>
<p>For fields, final helps express invariants and has special memory-model guarantees after safe construction. For methods and classes, final is an inheritance control tool: it protects behavior from overriding or prevents extension entirely.</p>
</td>
<td valign="top" width="50%">

<p>Локальная <code>final</code>-переменная присваивается один раз. Поле <code>final</code> должно быть присвоено в объявлении, инициализаторе или конструкторе. <code>final</code>-метод нельзя переопределить, а <code>final</code>-класс нельзя расширить.</p>
<p>Для многопоточности важны гарантии финальных полей: правильно сконструированный объект с <code>final</code>-полями безопаснее публиковать, потому что Java Memory Model даёт специальные гарантии видимости для этих полей. Но это не заменяет синхронизацию для изменяемого состояния.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A blank final field is a final field without an initializer; it must be definitely assigned exactly once by every constructor path. Static blank finals must be assigned by static initialization. Effectively final local variables are not declared final but are never reassigned; lambdas can capture them.</p>
<p>Final and immutability are not synonyms. To make a class immutable you usually need final fields, no setters, defensive copies for mutable inputs/outputs, no leaking of mutable internals, and careful superclass design.</p>
</td>
<td valign="top" width="50%">

<p>Ссылка <code>final List&lt;String&gt; list</code> не может быть переназначена, но сам список всё ещё может изменяться, если он изменяемый. Поэтому неизменяемость объекта требует неизменяемых полей, защитных копий и отсутствия методов, меняющих состояние.</p>
<p>Для лямбд и локальных классов Java допускает захват локальных переменных, которые являются <code>final</code> или фактически <code>final</code> (effectively final): переменная не помечена <code>final</code>, но после присваивания больше не меняется.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use final to communicate intent and protect invariants. It is especially useful for dependencies, value objects and classes not designed for inheritance. Do not rely on final alone for thread safety or immutability; design the whole object boundary.</p>
</td>
<td valign="top" width="50%">

<p>В рабочем коде <code>final</code> полезен как сигнал намерения: зависимость не переназначается, класс не предназначен для наследования, метод не является точкой расширения. Это упрощает чтение кода и уменьшает случайные изменения состояния.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>final</code> reference does not mean immutable object.</li>
<li>A final method cannot be overridden but can still be overloaded.</li>
<li>A final class can still contain mutable state.</li>
<li>Blank final fields must be definitely assigned on every construction path.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>final</code>-ссылка не делает объект неизменяемым.</li>
<li><code>final</code>-поле должно быть точно присвоено на каждом пути конструирования.</li>
<li><code>final</code>-метод нельзя переопределить, но его можно перегрузить.</li>
<li><code>final</code>-класс всё ещё может содержать изменяемое состояние.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Does <code>final List&lt;String&gt;</code> make the list immutable?<br>A: No. It only prevents reassigning the variable or field to another list.</p>
</td>
<td valign="top" width="50%">

<p>Q: Делает ли <code>final</code> объект неизменяемым?<br>A: Нет. <code>final</code> запрещает переназначить ссылку или поле, но не запрещает менять сам изменяемый объект.</p>

</td>

<a id="jcore-class-007"></a>

<details>
<summary><strong>JCORE-CLASS-007. How do <code>public</code>, <code>protected</code>, package-private and <code>private</code> access differ?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>public</code> is accessible from everywhere. <code>private</code> is accessible only inside the declaring top-level or nested context according to Java access rules. Package-private has no modifier and is accessible only inside the same package. <code>protected</code> is accessible in the same package and also from subclasses, with extra restrictions outside the package.</p>
</td>
<td valign="top" width="50%">

<p><code>public</code> доступен отовсюду, <code>protected</code> — из того же пакета и из подклассов с дополнительными правилами, отсутствие модификатора даёт доступ только внутри пакета, а <code>private</code> ограничивает доступ объявляющим классом. Для верхнеуровневых классов допустимы только <code>public</code> и доступ внутри пакета.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The usual order from most open to most restrictive is <code>public</code>, <code>protected</code>, package-private, <code>private</code>, although <code>protected</code> is not simply “package-private plus children” in all contexts. Outside the package, a subclass can access a protected member through itself or a subtype reference, not through an arbitrary superclass instance.</p>
<p>Top-level classes can be only <code>public</code> or package-private. Members of classes can use all four levels. Interface members have their own defaults: methods are often public, and fields are public static final constants.</p>
</td>
<td valign="top" width="50%">

<p>Модификаторы доступа управляют тем, какой код может обращаться к типу, полю, методу или конструктору. <code>public</code> формирует внешний API. Доступ внутри пакета удобен для внутренней реализации модуля или библиотеки. <code>private</code> скрывает детали внутри класса.</p>
<p><code>protected</code> часто понимают слишком широко. Он доступен из того же пакета, а из другого пакета — только через наследование и с правилами доступа через ссылку подходящего подтипа, а не просто через любой объект родительского класса.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Packages are part of the access model. This is why package-private is a useful encapsulation tool for module-internal implementation details, tests in the same package, and domain classes that should not be public API.</p>
<p>Access modifiers control source-level and runtime access checks, not object ownership. Making a field <code>private</code> does not make the object immutable or thread-safe; it only controls direct access.</p>
</td>
<td valign="top" width="50%">

<p>В современных приложениях на доступ влияет не только модификатор Java, но и модульная система: пакет должен быть экспортирован из модуля, иначе даже <code>public</code>-тип может быть недоступен внешнему модулю.</p>
<p>Для вложенных классов и членов можно использовать все четыре уровня доступа. Для верхнеуровневых типов <code>private</code> и <code>protected</code> невозможны.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For backend APIs, keep public surface small and stable. Prefer package-private implementation classes, public interfaces or facades where needed, and private fields with behavior-focused methods. Avoid exposing mutable internals just because fields are private.</p>
</td>
<td valign="top" width="50%">

<p>Хорошая практика — делать минимально необходимый уровень доступа. Чем меньше публичная поверхность, тем проще менять реализацию, поддерживать совместимость и тестировать поведение через реальные API, а не через случайно открытые детали.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Package names matter for package-private access.</li>
<li><code>protected</code> outside the package has subtype-reference rules.</li>
<li>Top-level classes cannot be <code>private</code> or <code>protected</code>.</li>
<li>Access control is not a substitute for immutability or validation.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Доступ внутри пакета (package-private) означает отсутствие модификатора, а не ключевое слово.</li>
<li><code>protected</code> — это не «public для всех подклассов без ограничений».</li>
<li>Верхнеуровневый класс не может быть <code>private</code> или <code>protected</code>.</li>
<li>Модули могут дополнительно ограничивать доступ к <code>public</code>-типам.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does package-private mean?<br>A: No access modifier; accessible only from code in the same package.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что означает доступ внутри пакета (package-private)?<br>A: Доступ только из кода того же пакета; явного ключевого слова для него нет.</p>

</td>
</tr>

<details>
<summary><strong>JCORE-CLASS-008. What does <code>abstract</code> mean for classes and methods?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>An abstract class cannot be instantiated directly and may contain abstract methods. An abstract method has no body and must be implemented by a concrete subclass, unless the subclass is also abstract. Abstract classes can also contain fields, constructors and concrete methods.</p>
</td>
<td valign="top" width="50%">

<p><code>abstract</code>-класс нельзя создать напрямую, а <code>abstract</code>-метод объявляет обязательное поведение без реализации. Конкретный подкласс должен реализовать все абстрактные методы или сам остаться абстрактным.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Abstract classes define partial implementations or shared contracts. They are useful when subclasses share state or common behavior, while abstract methods represent behavior that subclasses must provide.</p>
<p>A class must be abstract if it declares or inherits abstract methods without implementing them. Constructors in abstract classes still run as part of subclass construction; they are not for direct instantiation but for initializing the abstract superclass part.</p>
</td>
<td valign="top" width="50%">

<p>Абстрактный класс используют, когда нужно задать общий базовый тип и, возможно, часть общей реализации: поля, конструктор, обычные методы, <code>protected</code>-методы расширения. Абстрактный метод — это обещание, что конкретный наследник предоставит реализацию.</p>
<p>Интерфейс чаще подходит для чистого контракта между независимыми типами, а абстрактный класс — когда действительно нужна общая реализация и состояние. Из-за одиночного наследования классов абстрактный базовый класс сильнее связывает дизайн.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Abstract methods can appear in abstract classes and interfaces. A method cannot be both <code>abstract</code> and <code>final</code>, <code>static</code>, or <code>private</code> in the ordinary overriding sense, because abstract requires implementation by overriding.</p>
<p>Abstract classes are still reference types with normal inheritance, initialization and access rules. They are not the same as interfaces: classes can extend only one class, abstract or not, but can implement multiple interfaces.</p>
</td>
<td valign="top" width="50%">

<p>Абстрактный класс может не иметь ни одного абстрактного метода: это способ запретить прямое создание базового класса. И наоборот, наличие абстрактного метода делает класс абстрактным, если только метод не реализован.</p>
<p>Абстрактные методы не имеют тела и не могут быть <code>private</code>, потому что наследники должны иметь возможность их реализовать. Статические методы тоже не бывают абстрактными: они не участвуют в динамической диспетчеризации.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use abstract classes when you need shared implementation, protected hooks or common state. Use interfaces when you mainly need a role/contract. In frameworks, abstract base classes can reduce duplication but may create fragile inheritance hierarchies if hooks and invariants are not well documented.</p>
</td>
<td valign="top" width="50%">

<p>В промышленном коде абстрактные классы стоит использовать осторожно. Они удобны для шаблонного метода и общей инфраструктуры, но легко превращаются в хрупкую иерархию. Для бизнес-вариантов часто лучше интерфейс, композиция или запечатанная иерархия.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Abstract classes can have constructors, but cannot be directly instantiated.</li>
<li>An abstract method has no body.</li>
<li>A concrete subclass must implement inherited abstract methods.</li>
<li>Abstract base classes can become fragile if subclasses depend on undocumented call order.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Абстрактный класс может иметь конструктор, но его вызывает конструктор подкласса.</li>
<li>Абстрактный класс может содержать обычные методы и поля.</li>
<li>Абстрактный метод нельзя объявить <code>private</code> или <code>static</code>.</li>
<li>Конкретный подкласс обязан реализовать все унаследованные абстрактные методы.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Can an abstract class have concrete methods and fields?<br>A: Yes. It can provide shared implementation and state.</p>
</td>
<td valign="top" width="50%">

<p>Q: Можно ли создать объект абстрактного класса?<br>A: Напрямую нельзя; создать можно только конкретный подкласс.</p>

</td>

<a id="jcore-class-009"></a>

<details>
<summary><strong>JCORE-CLASS-009. What do <code>volatile</code> and <code>synchronized</code> mean at a high level?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>volatile</code> gives visibility and ordering guarantees for reads and writes of a variable. <code>synchronized</code> provides mutual exclusion around a monitor and also visibility guarantees when threads enter and exit synchronized blocks or methods. Volatile is not a general replacement for locking.</p>
</td>
<td valign="top" width="50%">

<p><code>volatile</code> даёт видимость и порядок для чтения и записи отдельной переменной, но не делает составные операции атомарными. <code>synchronized</code> даёт взаимное исключение через монитор и также создаёт гарантии видимости: выход из блока виден последующему входу в тот же монитор.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>At a high level, <code>volatile</code> says: when one thread writes this field, other threads reading it should see the latest value according to the Java Memory Model, and certain reordering is constrained. It is good for simple state flags and safely published references, not for compound actions like increment.</p>
<p><code>synchronized</code> says: only one thread at a time can hold the same monitor. It protects critical sections, and releasing a monitor happens-before a later acquisition of the same monitor. This makes changes visible to the next thread entering the synchronized region.</p>
</td>
<td valign="top" width="50%">

<p><code>volatile</code> подходит для простых флагов состояния и безопасной публикации отдельных значений, когда операция действительно сводится к одному чтению или одной записи. Например, поток может читать <code>volatile boolean stopped</code>, который меняет другой поток.</p>
<p><code>synchronized</code> защищает критическую секцию: только один поток одновременно владеет монитором. Кроме блокировки, он задаёт отношение happens-before, поэтому изменения, сделанные внутри синхронизированного блока, становятся видимы потоку, который позже входит в блок с тем же монитором.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>volatile int count</code> does not make <code>count++</code> atomic because increment is read-modify-write. For atomic counters use <code>AtomicInteger</code>, <code>LongAdder</code>, or synchronization depending on semantics.</p>
<p><code>synchronized</code> can be used on instance methods, static methods and blocks. Instance synchronized methods lock <code>this</code>; static synchronized methods lock the <code>Class</code> object. Blocks can lock any chosen object, which should usually be private and final.</p>
</td>
<td valign="top" width="50%">

<p>Операция <code>count++</code> над <code>volatile</code>-переменной всё равно не атомарна: это чтение, вычисление и запись. Для счётчиков обычно нужны <code>AtomicInteger</code>, <code>LongAdder</code> или синхронизация.</p>
<p><code>synchronized</code> проще рассуждать для инвариантов из нескольких полей, потому что он защищает группу действий. <code>volatile</code> лучше подходит для независимого состояния и неблокирующей коммуникации, но требует аккуратного проектирования.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In backend services, use higher-level concurrency tools first: immutable data, thread-safe collections, executors, atomics and locks from <code>java.util.concurrent</code>. Use <code>volatile</code> for simple publication/flags and <code>synchronized</code> for small critical sections with clear lock ownership.</p>
</td>
<td valign="top" width="50%">

<p>На интервью достаточно объяснить это на уровне Java Memory Model: <code>volatile</code> — видимость без взаимного исключения, <code>synchronized</code> — взаимное исключение плюс видимость. В сервисном коде часто лучше использовать готовые конкурентные структуры и явные абстракции, чем писать низкоуровневую синхронизацию вручную.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Volatile gives visibility, not compound atomicity.</li>
<li>Synchronizing on public objects can cause accidental lock interference.</li>
<li>Static synchronized locks the <code>Class</code> object.</li>
<li>Visibility bugs may pass tests and fail under load.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>volatile</code> не делает <code>++</code> атомарным.</li>
<li><code>synchronized</code> должен использовать один и тот же монитор для защищаемого состояния.</li>
<li>Синхронизация на публично доступном объекте повышает риск внешних блокировок и дедлоков.</li>
<li>Нельзя исправить гонку данных одним <code>volatile</code>, если инвариант зависит от нескольких полей.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Does <code>volatile</code> make <code>count++</code> atomic?<br>A: No. It gives visibility/order guarantees, but increment is a compound read-modify-write operation.</p>
</td>
<td valign="top" width="50%">

<p>Q: Главное отличие <code>volatile</code> от <code>synchronized</code>?<br>A: <code>volatile</code> даёт видимость для отдельной переменной, а <code>synchronized</code> даёт взаимное исключение и видимость для критической секции.</p>

</td>
</tr>

<details>
<summary><strong>JCORE-CLASS-010. What is the difference between a static nested class and an inner class?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A static nested class is nested for namespacing but has no implicit outer instance. An inner class is a non-static nested class and has an implicit reference to an enclosing outer object, so it can access that object’s instance members directly.</p>
</td>
<td valign="top" width="50%">

<p>Статический вложенный класс не имеет неявной ссылки на экземпляр внешнего класса. Внутренний класс — это нестатический вложенный класс; каждый его объект связан с конкретным внешним объектом и может обращаться к его членам экземпляра.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use a static nested class when the helper type belongs conceptually inside the outer class but does not need per-object state from it. Use an inner class when each nested instance is tied to a particular outer instance.</p>
<p>Creating an inner class normally requires an outer instance, for example <code>outer.new Inner()</code> from outside. The inner object keeps the outer object reachable, which can be useful but can also cause memory leaks.</p>
</td>
<td valign="top" width="50%">

<p>Если вложенному типу не нужен объект внешнего класса, почти всегда лучше сделать его <code>static</code>. Так он проще, дешевле по памяти и не удерживает внешний объект случайно.</p>
<p>Внутренний класс полезен, когда его смысл действительно зависит от конкретного экземпляра внешнего класса. Тогда компилятор хранит скрытую ссылку на внешний объект, а код внутреннего класса может обращаться к его полям и методам.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A static nested class can have static members normally. Inner classes historically had restrictions on static declarations, though modern Java has relaxed some rules for static members such as local records. The key interview distinction remains the outer-instance reference.</p>
<p>Anonymous classes and local classes are also kinds of inner classes when declared in an instance context. Lambdas are not anonymous inner classes; their runtime representation and capture semantics are different.</p>
</td>
<td valign="top" width="50%">

<p>Нестатический внутренний класс создаётся через внешний экземпляр, например <code>outer.new Inner()</code>. Эта связь влияет на сериализацию, жизненный цикл и утечки памяти: пока жив внутренний объект, он может удерживать внешний.</p>
<p>Статический вложенный класс — обычный класс, просто объявленный внутри другого класса для группировки и ограничения видимости. Пример: <code>Map.Entry</code> как вложенный тип или <code>Builder</code> внутри создаваемого класса.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Prefer static nested classes by default for builders, DTO helpers, map keys and strategy objects that do not need outer state. This avoids accidental retention of large service objects, controllers or caches through hidden outer references.</p>
</td>
<td valign="top" width="50%">

<p>В серверном коде статические вложенные классы часто удобны для builder, DTO-представлений, локальных стратегий и вспомогательных типов. Нестатические внутренние классы лучше использовать только при явной необходимости доступа к состоянию внешнего объекта.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Inner classes can accidentally keep the outer object alive.</li>
<li>A static nested class is not tied to a specific outer instance.</li>
<li>Both can access private members due to nesting rules, but only inner classes have implicit outer state.</li>
<li>Lambdas are not simply anonymous inner classes.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Внутренний класс может неявно продлить жизнь внешнего объекта.</li>
<li>Статический вложенный класс не может напрямую обращаться к нестатическим членам внешнего объекта.</li>
<li>Слово <code>static</code> для вложенного класса не означает «один экземпляр».</li>
<li>Локальные и анонимные классы — отдельные формы вложенных классов со своими правилами захвата переменных.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Which nested class has an implicit reference to the outer instance?<br>A: A non-static inner class.</p>
</td>
<td valign="top" width="50%">

<p>Q: Когда выбирать статический вложенный класс?<br>A: Когда вложенному типу не нужна ссылка на конкретный экземпляр внешнего класса.</p>

</td>

<details>
<summary><strong>🧠 JCORE-CLASS-011. What problems can mutable static state create in production services?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Mutable static state is global shared state per class loader. It can create race conditions, request leakage, tenant leakage, test pollution, memory leaks, configuration drift, class-loader leaks and hard-to-reproduce bugs across redeploys or parallel tests.</p>
</td>
<td valign="top" width="50%">

<p>Изменяемое статическое состояние разделяется всеми потоками и всеми вызовами в рамках одного загрузчика классов. Оно может привести к гонкам данных, утечкам между тестами или арендаторами, устаревшей конфигурации, сложной очистке кешей и непредсказуемому поведению при перезагрузках приложения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The main issue is hidden lifetime. A static mutable field often lives much longer than a request, transaction, test, or dependency-injection scope. If it stores user data, context, caches, clocks or configuration, different parts of the application may accidentally share state that should have been scoped.</p>
<p>Thread safety is another issue. Every request thread sees the same static object. Without synchronization or a thread-safe structure, updates can be lost, stale, or internally inconsistent. Even with thread safety, the lifecycle and eviction policy may be unclear.</p>
</td>
<td valign="top" width="50%">

<p>Статическое изменяемое поле фактически становится глобальным состоянием. В маленьком примере это удобно, но в сервисе оно ухудшает тестируемость, усложняет параллельный запуск тестов и может ломать изоляцию запросов. Если состояние меняется из нескольких потоков, появляются обычные проблемы конкурентности.</p>
<p>Отдельная проблема — жизненный цикл. Объект, положенный в статическое поле, может пережить запрос, пользователя, тестовый сценарий или даже часть перезагрузки контейнера. В окружениях с несколькими загрузчиками классов это также может приводить к утечкам памяти.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In application servers, plugin systems and tests, “global” may actually mean “global for this class loader”. This can lead to state surviving longer than expected, or duplicated statics when the same classes are loaded by different class loaders.</p>
<p>Static state also makes code harder to test because dependencies are hidden. Tests need reset hooks, ordering controls or isolated JVMs, all of which are signals that the design may be too global.</p>
</td>
<td valign="top" width="50%">

<p>Классические примеры: статический <code>Map</code> как кеш без ограничений, статический текущий пользователь, изменяемая глобальная конфигурация, самописный singleton с ленивой инициализацией без синхронизации. Все они выглядят простыми, но создают скрытые зависимости и порядок-зависимые ошибки.</p>
<p>Безопасные альтернативы зависят от задачи: неизменяемые константы, конфигурация через dependency injection, потокобезопасные кеши с политикой вытеснения, <code>ThreadLocal</code> только с обязательной очисткой, явный жизненный цикл компонента.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use dependency injection and explicit scopes for services, caches, configuration, clocks and context. Static final immutable constants are fine; mutable singletons should be rare, thread-safe, observable, resettable only when truly needed, and backed by clear ownership.</p>
</td>
<td valign="top" width="50%">

<p>В рабочем сервисе изменяемое статическое состояние должно быть исключением, а не нормой. Если оно всё же нужно, явно задайте владельца, синхронизацию, политику очистки, метрики и поведение при изменении конфигурации.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Static mutable caches can leak memory without eviction.</li>
<li>Static user/request context can leak data between requests.</li>
<li>Parallel tests can fail because of shared static state.</li>
<li>Class-loader behavior can make “singleton” assumptions wrong.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Статическое поле общее для потоков; обычный <code>HashMap</code> не становится потокобезопасным.</li>
<li>Статические кеши без лимитов часто превращаются в утечки памяти.</li>
<li>Статическое состояние делает тесты зависимыми от порядка запуска.</li>
<li>В контейнерах и плагинных системах статические ссылки могут удерживать загрузчик классов.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why is mutable static state dangerous in a backend service?<br>A: It is shared across threads and scopes, so lifetime, thread safety and data isolation become global concerns.</p>
</td>
<td valign="top" width="50%">

<p>Q: Почему изменяемое статическое состояние опасно в сервисах?<br>A: Это скрытое глобальное состояние: оно разделяется потоками, ухудшает тесты, может протекать между запросами и требует явного жизненного цикла.</p>

</td>
</tr>

<a id="jcore-class-012"></a>

<details>
<summary><strong>JCORE-CLASS-012. What is the difference between <code>import</code>, static import and package-private access?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>import</code> only lets source code use a type name without writing its fully qualified name. Static import lets code use static members without qualifying them by class name. Package-private access is an access-control rule: a declaration with no access modifier is accessible only inside the same package.</p>
</td>
<td valign="top" width="50%">

<p><code>import</code> только сокращает имена типов в исходном коде и не даёт дополнительных прав доступа. Статический импорт сокращает обращение к доступным статическим членам. Доступ внутри пакета (package-private) — это правило видимости: член или тип без модификатора доступен только внутри того же пакета.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Imports do not load classes, initialize classes, change dependencies, or grant access rights. They are compile-time name resolution conveniences. You cannot import your way around <code>private</code> or package-private access.</p>
<p>Static imports are often useful for constants, enum constants, test assertions and factory methods, but overuse can make code unclear because the declaring class is hidden. Package-private access is about encapsulating implementation inside a package.</p>
</td>
<td valign="top" width="50%">

<p>Обычный <code>import</code> позволяет писать <code>List</code> вместо <code>java.util.List</code>. Статический импорт позволяет писать <code>emptyList()</code> вместо <code>Collections.emptyList()</code>, если метод доступен. Но ни один импорт не «открывает» приватный или package-private член из другого пакета.</p>
<p>Пакет в Java — это часть системы доступа, а не просто папка. Код в одном пакете может видеть package-private объявления друг друга; код в подпакете не считается кодом того же пакета.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A normal import can import a single type or all top-level types in a package using wildcard syntax. It does not import subpackages. A static import can import a single static member or all accessible static members of a type.</p>
<p>Package-private is based on the package declaration, not directory layout alone. Build tools usually align directories and packages, but the language rule is the package name.</p>
</td>
<td valign="top" width="50%">

<p>Импорт со звёздочкой, например <code>java.util.*</code>, импортирует типы из указанного пакета, но не из подпакетов. Статический импорт со звёздочкой импортирует доступные статические члены указанного типа. При конфликтах имён лучше использовать явное полное имя.</p>
<p>Доступ определяется модификаторами, пакетами и, в модульных приложениях, экспортами модулей. Импорт участвует только в разрешении имён на этапе компиляции.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use imports for readability, static imports sparingly when they improve fluency, and package-private classes/methods to keep implementation details out of public APIs. In tests, same-package tests can access package-private internals without widening production visibility.</p>
</td>
<td valign="top" width="50%">

<p>В командном коде статический импорт удобен для тестов, матчеров и констант, но чрезмерное использование ухудшает читаемость. Доступ внутри пакета часто полезен для внутренней реализации пакета: меньше публичного API — меньше обязательств по совместимости.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Imports do not affect runtime class initialization.</li>
<li>Wildcard imports do not import subpackages.</li>
<li>Static import can hide where a method or constant comes from.</li>
<li>Package-private access cannot be bypassed with import.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Импорт не влияет на время выполнения и не попадает в байткод как зависимость сам по себе.</li>
<li>Импорт не даёт доступа к <code>private</code> или членам с доступом внутри пакета.</li>
<li>Подпакет не является частью родительского пакета для доступа.</li>
<li>Статический импорт может сделать источник метода или константы неочевидным.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Does <code>import</code> grant access to package-private classes from another package?<br>A: No. Import only helps with names; it does not change access control.</p>
</td>
<td valign="top" width="50%">

<p>Q: Даёт ли <code>import</code> доступ к package-private классу из другого пакета?<br>A: Нет. <code>import</code> только сокращает имя; правила доступа он не меняет.</p>

</td>

<details>
<summary><strong>JCORE-CLASS-013. What is a compile-time constant in Java?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A compile-time constant is a constant expression known to the compiler, usually stored in a <code>final</code> variable of primitive type or <code>String</code>. Such constants can be used in places like <code>case</code> labels and annotations, and references to them may be inlined into client class files.</p>
</td>
<td valign="top" width="50%">

<p>Константная переменная в Java — это <code>final</code>-переменная примитивного типа или <code>String</code>, инициализированная константным выражением времени компиляции. Такие значения компилятор может встроить в код клиента, поэтому обращение к ним обычно не требует инициализации класса-владельца.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A typical constant variable is <code>static final int MAX = 10;</code> or <code>static final String ROLE = "admin";</code>. The initializer must be a constant expression: literals, simple arithmetic on constants, string concatenation of constants, and similar compile-time operations.</p>
<p>A <code>static final</code> field is not automatically a compile-time constant. <code>static final Integer X = 1;</code>, <code>static final int X = compute();</code>, or <code>static final List&lt;String&gt; L = ...</code> are not constant variables in the JLS sense.</p>
</td>
<td valign="top" width="50%">

<p>Пример: <code>public static final int PORT = 8080;</code> — константная переменная, если выражение справа является константным. А <code>public static final Integer PORT = 8080;</code> уже не подходит, потому что это ссылочный тип. <code>public static final int PORT = compute();</code> тоже не константа времени компиляции.</p>
<p>Главное практическое следствие — встраивание. Если библиотека изменила значение публичной константы, а клиентский код не был перекомпилирован, клиент может продолжить использовать старое встроенное значение.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Inlining creates binary compatibility surprises. If library version 1 exposes <code>public static final int TIMEOUT = 100;</code> and a client compiles against it, the client may contain the literal <code>100</code>. Updating the library to <code>200</code> may not affect old clients until they are recompiled.</p>
<p>Compile-time constants also affect initialization: reading a constant variable through another class can avoid triggering initialization of the declaring class. That is why constants should not be used to hide side effects.</p>
</td>
<td valign="top" width="50%">

<p>Константное выражение может использовать литералы, некоторые арифметические операции, строки и другие константные переменные. Оно вычисляется компилятором, а не при запуске приложения.</p>
<p>Не всякое <code>static final</code> поле является константой времени компиляции. Ссылочные объекты, массивы, результаты вызовов методов и значения, вычисляемые в статическом блоке, требуют обычной инициализации класса.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For public APIs, be careful with public compile-time constants whose values may change. Prefer enums, configuration, methods, or non-constant accessors for values that are not truly stable across releases.</p>
</td>
<td valign="top" width="50%">

<p>Для внутренних констант это удобно и безопасно. Для публичных констант в библиотеках нужно помнить о бинарной совместимости: изменение значения может потребовать перекомпиляции потребителей. Для конфигурации, которая должна меняться без перекомпиляции, константы времени компиляции не подходят.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Not every <code>static final</code> field is a compile-time constant.</li>
<li>Changing public constants can require client recompilation.</li>
<li>Wrapper types are not primitive/String constant variables.</li>
<li>Reading a compile-time constant may not initialize the declaring class.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>static final</code> не всегда означает константу времени компиляции.</li>
<li>Константными переменными могут быть только примитивы и <code>String</code>.</li>
<li>Встроенные значения могут устареть у неперекомпилированных клиентов.</li>
<li>Доступ к константной переменной обычно не запускает статическую инициализацию класса.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Is <code>static final int X = compute();</code> a compile-time constant?<br>A: No. The value is computed at runtime, so reading it triggers class initialization.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что такое константная переменная?<br>A: <code>final</code>-переменная примитивного типа или <code>String</code>, инициализированная константным выражением времени компиляции.</p>

<details>
<summary><strong>🧠 JCORE-CLASS-014. Does accessing a <code>static final</code> field always trigger class initialization?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>No. Accessing a <code>static final</code> field that is a compile-time constant usually does not trigger initialization of the declaring class, because the compiler can inline the value. Accessing a <code>static final</code> field computed at runtime does trigger initialization.</p>
</td>
<td valign="top" width="50%">

<p>Нет. Доступ к <code>static final</code> полю запускает инициализацию класса не всегда. Если поле является константной переменной, его значение может быть встроено в вызывающий код, и класс-владелец не инициализируется. Неконстантные <code>static final</code> поля обычно требуют инициализации класса.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The important distinction is not <code>final</code> but “constant variable”. <code>public static final String NAME = "api";</code> is a compile-time constant. <code>public static final String NAME = System.getenv("NAME");</code> is not. Reading the first can be compiled as a literal in the caller; reading the second requires running the declaring class initialization code.</p>
<p>This is often tested in interviews with a static block printing a message. If the caller reads only a constant variable, the message may not print because the declaring class was never initialized.</p>
</td>
<td valign="top" width="50%">

<p>Разница в том, известно ли значение компилятору как константное выражение. <code>static final int X = 10;</code> или <code>static final String S = "ok";</code> — типичные константы времени компиляции. А <code>static final Integer X = 10;</code>, <code>static final int X = compute();</code> или <code>static final List&lt;String&gt; NAMES = ...</code> — нет.</p>
<p>Поэтому утверждение «любой доступ к статическому полю инициализирует класс» слишком грубое. Для интервью важно назвать исключение: константные переменные.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The behavior follows from constant expressions and active-use rules. It also has a maintenance implication: the caller’s class file may contain a copy of the old value. Recompilation is needed to pick up changed constants in many scenarios.</p>
<p>Fields of reference types other than <code>String</code>, even if <code>static final</code>, are not compile-time constants. For example <code>static final Integer X = 1;</code> requires class initialization when accessed normally.</p>
</td>
<td valign="top" width="50%">

<p>Компилятор может заменить обращение к константной переменной непосредственным значением в class-файле клиента. Тогда при выполнении нет обращения к полю класса-владельца, а значит нет и причины запускать его статическую инициализацию.</p>
<p>Если же поле требует выполнения кода при инициализации — вызова метода, создания объекта, заполнения массива, чтения конфигурации, — обращение к нему является активным использованием класса.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Do not put observable side effects in static initializers and expect them to run when constants are read. For public constants that may change, prefer accessor methods or configuration to avoid inlining surprises.</p>
</td>
<td valign="top" width="50%">

<p>Это важно для библиотек и фреймворков. Изменение публичной константы может не подхватиться без перекомпиляции клиента, а попытка «лениво» выполнить статический блок через чтение константы может вообще не сработать.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>static final</code> is not enough; the field must be a constant variable.</li>
<li>Constants can be inlined into client bytecode.</li>
<li>Changing a public compile-time constant may not affect already compiled clients.</li>
<li>A static block may not run when only a constant is read.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>static final String</code> может быть константой времени компиляции.</li>
<li><code>static final Integer</code> не является константной переменной.</li>
<li>Массив или коллекция в <code>static final</code> поле могут оставаться изменяемыми.</li>
<li>Рефлексия и другие механизмы доступа могут иметь свои триггеры инициализации.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What matters for class initialization: <code>static final</code> or compile-time constant?<br>A: Compile-time constant. A non-constant <code>static final</code> field still triggers initialization when accessed.</p>
</td>
<td valign="top" width="50%">

<p>Q: Всегда ли чтение <code>static final</code> поля инициализирует класс?<br>A: Нет. Если это константная переменная, значение может быть встроено компилятором.</p>

<details>
<summary><strong>JCORE-CLASS-015. What is <code>ExceptionInInitializerError</code>, and when can it appear?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>ExceptionInInitializerError</code> is an <code>Error</code> thrown when an exception occurs during static initialization of a class or interface. It can appear from static field initializers or static initializer blocks, often on first active use of the class.</p>
</td>
<td valign="top" width="50%">

<p><code>ExceptionInInitializerError</code> появляется, когда исключение возникает во время статической инициализации класса: в статическом блоке или при инициализации статического поля. Это <code>Error</code>, который оборачивает исходное исключение и показывает, что класс не удалось корректно инициализировать.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If a static initializer throws a runtime exception, the JVM wraps it in <code>ExceptionInInitializerError</code>. The original cause is available through the error’s cause or exception accessors. Because it is an <code>Error</code>, normal application code usually should not catch it to continue as if nothing happened.</p>
<p>After initialization fails, the class is considered erroneous for that class loader. Later attempts to use it can fail with <code>NoClassDefFoundError</code> saying the class could not be initialized, even though the class file exists.</p>
</td>
<td valign="top" width="50%">

<p>Пример: <code>static final Config CONFIG = loadConfig();</code>, где <code>loadConfig()</code> бросает исключение. При первом активном использовании класса JVM запускает статическую инициализацию, получает исключение и выбрасывает <code>ExceptionInInitializerError</code>.</p>
<p>После такой ошибки класс в данном загрузчике обычно считается ошибочным. Повторные попытки обращения могут приводить не к повторному выполнению инициализатора, а к ошибкам вроде <code>NoClassDefFoundError</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Common causes include parsing invalid configuration in a static field, building a static singleton with missing dependencies, loading native libraries, reading files, connecting to external systems, or circular initialization that produces unexpected null/default values.</p>
<p>Checked exceptions cannot be thrown directly from static initializers unless caught or wrapped, so failures are often wrapped in unchecked exceptions first, then wrapped again by the JVM. This can make root-cause stacks noisy.</p>
</td>
<td valign="top" width="50%">

<p>Если статический инициализатор бросает уже <code>Error</code>, JVM может передать его иначе, но обычные исключения из статического кода оборачиваются. Исходную причину нужно смотреть через <code>getCause()</code> и стек вызовов.</p>
<p>Часто корень проблемы — слишком много работы в статической инициализации: чтение файлов, подключение к сервисам, парсинг конфигурации, обращение к другим классам с собственной статической инициализацией.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Treat it as a startup/configuration/class-loading failure. Inspect the root cause, avoid heavy static initialization, move fallible startup work into explicit lifecycle components, and add tests that initialize important classes under realistic configuration.</p>
</td>
<td valign="top" width="50%">

<p>В рабочем сервисе такая ошибка обычно проявляется как падение при старте или при первом запросе к редко используемому коду. Лечится не перехватом <code>Error</code> вокруг каждого вызова, а упрощением статической инициализации и переносом отказоустойчивой логики в управляемый жизненный цикл.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>It is an <code>Error</code>, not a checked exception.</li>
<li>Later failures may be <code>NoClassDefFoundError</code>, hiding the original initializer failure.</li>
<li>The first stack trace usually has the most useful root cause.</li>
<li>Static initialization failure can be caused by configuration or environment differences.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>ExceptionInInitializerError</code> относится к статической инициализации, а не к обычному конструктору объекта.</li>
<li>Исходная причина находится в <code>getCause()</code>.</li>
<li>После неудачной инициализации класс может не инициализироваться повторно.</li>
<li>Не стоит использовать статические инициализаторы для операций, которые нормально могут отказать.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What usually causes <code>ExceptionInInitializerError</code>?<br>A: An exception thrown while running static field initializers or static initializer blocks.</p>
</td>
<td valign="top" width="50%">

<p>Q: Когда появляется <code>ExceptionInInitializerError</code>?<br>A: Когда исключение возникает при выполнении статического блока или инициализации статического поля класса.</p>

<details>
<summary><strong>🧠 JCORE-CLASS-016. How can circular static initialization cause bugs?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Circular static initialization happens when class A’s static initialization uses class B, while class B’s static initialization uses class A. Because each class is initialized only once and fields get default values before initializers run, one class can observe another class’s partially initialized state.</p>
</td>
<td valign="top" width="50%">

<p>Циклическая статическая инициализация возникает, когда классы во время инициализации обращаются друг к другу. Один класс может увидеть другой в частично подготовленном состоянии: со значениями по умолчанию, <code>null</code> или не полностью заполненными объектами. Такие ошибки часто зависят от порядка первого обращения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The bug is not always an exception. Sometimes it is worse: a field that should be <code>42</code> is read as <code>0</code>, or a reference that should be non-null is read as <code>null</code>, because the other class is in the middle of initialization.</p>
<p>The order can depend on which class is first actively used. That means tests may pass when class A is touched first, but production may fail when a different code path touches class B first.</p>
</td>
<td valign="top" width="50%">

<p>Представьте, что <code>A.X</code> инициализируется через <code>B.Y</code>, а <code>B.Y</code> в свою очередь читает <code>A.X</code>. JVM не может «магически» вычислить оба значения одновременно. Она начинает инициализацию одного класса, затем другого, и при обратном обращении может вернуть ещё не присвоенное значение.</p>
<p>Это особенно неприятно, потому что код выглядит детерминированным, но результат зависит от того, какой класс был впервые использован раньше. В тестах порядок может быть одним, а в приложении — другим.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The JVM has rules to prevent recursive initialization from running the same class initializer twice. If the class is already being initialized by the current thread, the recursive request can proceed without re-running it, so default or partly assigned values may be visible.</p>
<p>Circular initialization is especially likely with static singletons, registries, constants that are not compile-time constants, and helper classes that initialize each other for convenience.</p>
</td>
<td valign="top" width="50%">

<p>На этапе подготовки статические поля уже имеют значения по умолчанию. Если во время цикла другой класс читает поле до выполнения его явного инициализатора, он может увидеть именно это значение по умолчанию.</p>
<p>Циклы бывают не только прямыми. Их могут создавать статические фабрики, логгеры, реестры, enum, кеши, конфигурация и вызовы методов из статических инициализаторов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Break cycles by moving initialization into explicit factories, dependency injection, lazy holders, or methods. Keep static initialization limited to true constants and simple immutable objects. Add startup tests that touch classes in realistic order.</p>
</td>
<td valign="top" width="50%">

<p>Лучшее решение — разорвать цикл: вынести вычисление в явный метод, использовать ленивую инициализацию с понятным владельцем, перенести зависимости в DI-контейнер или заменить статические связи на неизменяемую конфигурацию, создаваемую при старте приложения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>A circular static dependency can produce wrong values without throwing an exception.</li>
<li>First active-use order can change behavior.</li>
<li>Compile-time constants may hide cycles because they do not initialize the class.</li>
<li>Static registries are common sources of circular initialization.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Цикл статической инициализации не всегда приводит к исключению; иногда он даёт неверное значение.</li>
<li>Порядок первого обращения к классам может менять результат.</li>
<li>Статические методы, вызванные из инициализаторов, могут скрывать цикл.</li>
<li>Добавление логирования или метрик в статический код тоже может создать новую зависимость.</li>
</ul>
