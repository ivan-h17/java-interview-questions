<a id="jcore-class-001"></a>

<details>
<summary><strong>JCORE-CLASS-001. How does object initialization work: fields, instance initializers and constructors?</strong></summary>

#### Short answer

Object initialization first allocates the object and gives fields default values. In the common order, superclass construction runs before this class’s instance field initializers and instance initializer blocks, and then the constructor epilogue finishes. Modern Java also allows a restricted constructor prologue before an explicit `super(...)` or `this(...)`, so the “constructor body runs last” shortcut needs that caveat.

#### Interview answer

When Java executes `new Child()`, it normally initializes the object from the top of the hierarchy down. The memory for the whole object exists first, and superclass construction precedes subclass initialization code that depends on a fully initialized receiver. Since Java 25, a constructor may have a restricted prologue before explicit delegation, but ordinary instance initializers still run as part of the current class’s construction path.

This means field initializers are not “magical defaults”; they are executable initialization code inserted into constructors. If there are multiple constructors, the initializer code is effectively run for each construction path after the superclass constructor has completed.

#### Deep dive

Useful baseline order: default values first; explicit superclass constructor; instance variable initializers and instance initializer blocks of the current class in textual order; then the constructor epilogue. The Java 25 flexible-constructor-body feature adds a restricted prologue before explicit delegation, but that prologue is not a license to use a half-built object freely. Static initialization is separate and happens at class initialization time, not once per object.

A dangerous edge case is calling overridable methods from constructors. Dynamic dispatch already works while the subclass part may not be initialized yet, so a superclass constructor can call a subclass method that observes default values in subclass fields.

#### Production angle

In production code, keep constructors simple, validate required arguments early, avoid starting threads or publishing `this` during construction, and prefer factory methods/builders when initialization has many branches. For dependency-injected services, avoid heavy work in constructors; use lifecycle hooks deliberately.

#### Traps / caveats

- Fields have default values before explicit initializers run.
- Instance initializer blocks run before the constructor body, not after it.
- Superclass construction normally happens before subclass initialization that depends on the constructed receiver; Java 25 constructor prologues are restricted.
- Calling overridable methods from constructors can expose partially initialized state.

#### Optional Anki

Q: What is the usual order before a constructor epilogue in the same class?
A: Superclass construction, then instance field initializers and instance initializer blocks in source order; Java 25 adds a restricted prologue caveat.

</details>

<a id="jcore-class-002"></a>

<details>
<summary><strong>JCORE-CLASS-002. When is a Java class initialized?</strong></summary>

#### Short answer

A class is initialized when it is first actively used: for example when creating an instance, invoking a static method, reading or writing a non-constant static field, or using reflection in ways that trigger initialization. Initialization runs static field initializers and static initializer blocks once per class loader.

#### Interview answer

Loading a class and initializing a class are not the same. Loading makes the class available to the JVM; linking verifies and prepares it; initialization executes the class’s static initialization code. Before a class is initialized, its superclass is initialized first, except for special interface rules.

Accessing a compile-time constant such as `public static final int PORT = 8080;` usually does not initialize the declaring class because the value can be inlined into the client class. Accessing `static final` values computed at runtime does initialize the class.

#### Deep dive

The JVM synchronizes class initialization so that only one thread runs the initialization code. Other threads needing the same class wait until initialization completes or fails. If initialization fails, later uses can see `NoClassDefFoundError` because the class is considered erroneous.

Class initialization is lazy. Merely importing a class, declaring a variable of that type, or referring to its class literal in some cases is not the same as executing its static initialization code. Active use is the key concept.

#### Production angle

In services, class initialization bugs often appear only on first request or first access to a rarely used code path. Avoid doing network calls, file IO, secret loading or complex dependency wiring in static initializers; make startup behavior explicit and observable instead.

#### Traps / caveats

- `import` never initializes a class.
- Reading a compile-time constant may not initialize the declaring class.
- Initialization is once per class loader, not once per JVM globally.
- Failed initialization can poison later class use.

#### Optional Anki

Q: Does reading every `static final` field initialize its class?
A: No. Reading a compile-time constant can be compiled as an inlined constant and not trigger initialization.

</details>

<details>
<summary><strong>🧠 JCORE-CLASS-003. What can go wrong with static initialization?</strong></summary>

#### Short answer

Static initialization can fail, run too early, run in an unexpected order, deadlock, hide slow IO, or expose partially initialized state through circular references. Because it happens once and is tied to class loading, failures can make the class unusable for the rest of the JVM lifetime for that class loader.

#### Interview answer

Static initializers look convenient for constants and simple caches, but they are dangerous when they perform real work. Exceptions are wrapped in `ExceptionInInitializerError`, and other threads may block waiting for the class initialization lock. If initialization depends on another class that depends back on the first one, one side may observe default values.

Another common issue is order inside one class: static fields and static blocks execute in source order. A field initializer that reads another static field declared later may see its default value, not the value assigned later.

#### Deep dive

Static initialization is synchronized per class. If two classes initialize on different threads and each initializer waits for the other class, a deadlock is possible. This is rare, but very hard to debug because stack traces point at class loading rather than ordinary application code.

Static initialization also interacts badly with tests and containers. Mutable static fields can retain state across tests, across requests, or across redeploys depending on class loader behavior.

#### Production angle

Prefer simple static constants and immutable stateless helpers. Use dependency injection, explicit startup components, lazy holders, memoized suppliers, or lifecycle-managed caches for expensive initialization. Log and fail explicitly rather than hiding startup work in class initialization.

#### Traps / caveats

- Static initialization order inside a class is textual.
- Exceptions become `ExceptionInInitializerError`.
- Circular initialization can expose default values instead of intended values.
- Slow or blocking static initialization can make first request latency unpredictable.

#### Optional Anki

Q: Why should heavy IO be avoided in static initializers?
A: It hides startup work in class loading, can block class initialization, and can poison the class if it fails.

</details>

<details>
<summary><strong>JCORE-CLASS-004. What are the rules for constructor chaining with `this()` and `super()`?</strong></summary>

#### Short answer

`this(...)` calls another constructor in the same class; `super(...)` calls a superclass constructor. A constructor still has at most one explicit constructor invocation, and it cannot directly call both. On modern Java, statements may appear before that invocation in a restricted constructor prologue; older Java required `this(...)` or `super(...)` to be the first statement. If neither is written, Java inserts an implicit no-argument `super()`.

#### Interview answer

Constructor chaining exists to guarantee that each construction path eventually initializes superclass state and then current-class state. A `this()` call delegates to another constructor in the same class; that chain eventually reaches a constructor that invokes `super()`, explicitly or implicitly.

The traditional interview rule is “constructor delegation must happen first”. Since Java 25, the better answer is more nuanced: Java supports flexible constructor bodies, so a restricted prologue may run before `this(...)` or `super(...)`. The prologue can validate parameters or compute arguments, but it is in an early construction context and generally cannot use the object under construction.

#### Deep dive

The compiler rejects recursive constructor invocation, such as constructor A calling B and B calling A. It also rejects an implicit `super()` if the superclass has no accessible no-argument constructor. Arguments to `this(...)` or `super(...)` are evaluated before entering the target constructor.

In Java 25 flexible constructor bodies split a constructor body into a prologue before the explicit constructor invocation and an epilogue after it. In the early construction context, code cannot read instance state, call instance methods, use ordinary `this`, or use `super` members, because the object is not yet safely initialized. Java does allow certain field assignments before `super()`, which can help avoid superclass constructor callbacks observing default subclass field values.

Records have specialized constructor rules: record constructors may not call `super(...)`; noncanonical constructors delegate to the canonical constructor with `this(...)`. Compact constructors are mainly for validation and normalization of record components.

#### Production angle

Use constructor chaining to reduce duplication, but keep chains obvious. A constructor prologue is good for cheap parameter validation and argument preparation; do not turn it into a hidden initialization framework. For complex creation logic, prefer static factories or builders so validation, defaults and invariants remain readable and testable.

#### Traps / caveats

- `this()` and `super()` cannot both appear directly in the same constructor.
- In Java 25+, statements may appear before them only under early-construction-context restrictions.
- Older Java baselines require explicit constructor invocation to be the first statement.
- Implicit `super()` requires an accessible no-argument superclass constructor.
- Recursive constructor chains are compile-time errors.

#### Optional Anki

Q: What is the Java 25 update to the old “super must be first” rule?
A: A restricted constructor prologue may run before `this(...)` or `super(...)`, but it cannot freely access the object under construction.

</details>

<details>
<summary><strong>JCORE-CLASS-005. What does `static` mean for fields, methods and nested classes?</strong></summary>

#### Short answer

`static` means “belongs to the class rather than to a particular instance”. A static field is one variable per class loader, a static method is called without an instance and is not dynamically dispatched, and a static nested class has no implicit reference to an outer object.

#### Interview answer

For fields, `static` is shared class state. All instances see the same field. For methods, `static` means the method is resolved by the compile-time type and cannot access instance members without an explicit object reference.

For nested classes, `static` means the nested class is just scoped inside the outer class name. It can access private members of the outer class by normal compiler-supported access, but it does not capture a particular outer instance.

#### Deep dive

Static members are inherited in the sense that they can be referenced through subclass names, but static methods are hidden, not overridden. Calling a static method through an instance is legal but misleading because the chosen method still depends on the declared type, not the runtime object.

Static fields are initialized during class initialization. If mutable, they are shared across all threads and requests using that class loader, so thread-safety and lifecycle become global concerns.

#### Production angle

Use static for true constants, stateless utility methods, factories, and nested helper types that do not need an outer instance. Avoid mutable static state in services unless it is intentionally shared, thread-safe, observable and lifecycle-managed.

#### Traps / caveats

- Static methods are not polymorphic instance methods.
- A static nested class is not an inner class.
- Mutable static fields create global shared state.
- Calling static methods via object references hurts readability.

#### Optional Anki

Q: Does a static nested class hold an implicit outer instance reference?
A: No. Only non-static inner classes do.

</details>

<details>
<summary><strong>JCORE-CLASS-006. What does `final` mean for variables, fields, methods and classes?</strong></summary>

#### Short answer

`final` means different but related things depending on the target: a final variable can be assigned only once, a final field cannot be reassigned after construction or static initialization, a final method cannot be overridden, and a final class cannot be subclassed.

#### Interview answer

For local variables and parameters, `final` prevents reassignment of the variable. It does not make the object immutable. A `final List` variable cannot point to another list, but the list contents may still change.

For fields, final helps express invariants and has special memory-model guarantees after safe construction. For methods and classes, final is an inheritance control tool: it protects behavior from overriding or prevents extension entirely.

#### Deep dive

A blank final field is a final field without an initializer; it must be definitely assigned exactly once by every constructor path. Static blank finals must be assigned by static initialization. Effectively final local variables are not declared final but are never reassigned; lambdas can capture them.

Final and immutability are not synonyms. To make a class immutable you usually need final fields, no setters, defensive copies for mutable inputs/outputs, no leaking of mutable internals, and careful superclass design.

#### Production angle

Use final to communicate intent and protect invariants. It is especially useful for dependencies, value objects and classes not designed for inheritance. Do not rely on final alone for thread safety or immutability; design the whole object boundary.

#### Traps / caveats

- `final` reference does not mean immutable object.
- A final method cannot be overridden but can still be overloaded.
- A final class can still contain mutable state.
- Blank final fields must be definitely assigned on every construction path.

#### Optional Anki

Q: Does `final List<String>` make the list immutable?
A: No. It only prevents reassigning the variable or field to another list.

</details>

<details>
<summary><strong>JCORE-CLASS-007. How do `public`, `protected`, package-private and `private` access differ?</strong></summary>

#### Short answer

`public` is accessible from everywhere. `private` is accessible only inside the declaring top-level or nested context according to Java access rules. Package-private has no modifier and is accessible only inside the same package. `protected` is accessible in the same package and also from subclasses, with extra restrictions outside the package.

#### Interview answer

The usual order from most open to most restrictive is `public`, `protected`, package-private, `private`, although `protected` is not simply “package-private plus children” in all contexts. Outside the package, a subclass can access a protected member through itself or a subtype reference, not through an arbitrary superclass instance.

Top-level classes can be only `public` or package-private. Members of classes can use all four levels. Interface members have their own defaults: methods are often public, and fields are public static final constants.

#### Deep dive

Packages are part of the access model. This is why package-private is a useful encapsulation tool for module-internal implementation details, tests in the same package, and domain classes that should not be public API.

Access modifiers control source-level and runtime access checks, not object ownership. Making a field `private` does not make the object immutable or thread-safe; it only controls direct access.

#### Production angle

For backend APIs, keep public surface small and stable. Prefer package-private implementation classes, public interfaces or facades where needed, and private fields with behavior-focused methods. Avoid exposing mutable internals just because fields are private.

#### Traps / caveats

- Package names matter for package-private access.
- `protected` outside the package has subtype-reference rules.
- Top-level classes cannot be `private` or `protected`.
- Access control is not a substitute for immutability or validation.

#### Optional Anki

Q: What does package-private mean?
A: No access modifier; accessible only from code in the same package.

</details>

<details>
<summary><strong>JCORE-CLASS-008. What does `abstract` mean for classes and methods?</strong></summary>

#### Short answer

An abstract class cannot be instantiated directly and may contain abstract methods. An abstract method has no body and must be implemented by a concrete subclass, unless the subclass is also abstract. Abstract classes can also contain fields, constructors and concrete methods.

#### Interview answer

Abstract classes define partial implementations or shared contracts. They are useful when subclasses share state or common behavior, while abstract methods represent behavior that subclasses must provide.

A class must be abstract if it declares or inherits abstract methods without implementing them. Constructors in abstract classes still run as part of subclass construction; they are not for direct instantiation but for initializing the abstract superclass part.

#### Deep dive

Abstract methods can appear in abstract classes and interfaces. A method cannot be both `abstract` and `final`, `static`, or `private` in the ordinary overriding sense, because abstract requires implementation by overriding.

Abstract classes are still reference types with normal inheritance, initialization and access rules. They are not the same as interfaces: classes can extend only one class, abstract or not, but can implement multiple interfaces.

#### Production angle

Use abstract classes when you need shared implementation, protected hooks or common state. Use interfaces when you mainly need a role/contract. In frameworks, abstract base classes can reduce duplication but may create fragile inheritance hierarchies if hooks and invariants are not well documented.

#### Traps / caveats

- Abstract classes can have constructors, but cannot be directly instantiated.
- An abstract method has no body.
- A concrete subclass must implement inherited abstract methods.
- Abstract base classes can become fragile if subclasses depend on undocumented call order.

#### Optional Anki

Q: Can an abstract class have concrete methods and fields?
A: Yes. It can provide shared implementation and state.

</details>

<a id="jcore-class-009"></a>

<details>
<summary><strong>JCORE-CLASS-009. What do `volatile` and `synchronized` mean at a high level?</strong></summary>

#### Short answer

`volatile` gives visibility and ordering guarantees for reads and writes of a variable. `synchronized` provides mutual exclusion around a monitor and also visibility guarantees when threads enter and exit synchronized blocks or methods. Volatile is not a general replacement for locking.

#### Interview answer

At a high level, `volatile` says: when one thread writes this field, other threads reading it should see the latest value according to the Java Memory Model, and certain reordering is constrained. It is good for simple state flags and safely published references, not for compound actions like increment.

`synchronized` says: only one thread at a time can hold the same monitor. It protects critical sections, and releasing a monitor happens-before a later acquisition of the same monitor. This makes changes visible to the next thread entering the synchronized region.

#### Deep dive

`volatile int count` does not make `count++` atomic because increment is read-modify-write. For atomic counters use `AtomicInteger`, `LongAdder`, or synchronization depending on semantics.

`synchronized` can be used on instance methods, static methods and blocks. Instance synchronized methods lock `this`; static synchronized methods lock the `Class` object. Blocks can lock any chosen object, which should usually be private and final.

#### Production angle

In backend services, use higher-level concurrency tools first: immutable data, thread-safe collections, executors, atomics and locks from `java.util.concurrent`. Use `volatile` for simple publication/flags and `synchronized` for small critical sections with clear lock ownership.

#### Traps / caveats

- Volatile gives visibility, not compound atomicity.
- Synchronizing on public objects can cause accidental lock interference.
- Static synchronized locks the `Class` object.
- Visibility bugs may pass tests and fail under load.

#### Optional Anki

Q: Does `volatile` make `count++` atomic?
A: No. It gives visibility/order guarantees, but increment is a compound read-modify-write operation.

</details>

<details>
<summary><strong>JCORE-CLASS-010. What is the difference between a static nested class and an inner class?</strong></summary>

#### Short answer

A static nested class is nested for namespacing but has no implicit outer instance. An inner class is a non-static nested class and has an implicit reference to an enclosing outer object, so it can access that object’s instance members directly.

#### Interview answer

Use a static nested class when the helper type belongs conceptually inside the outer class but does not need per-object state from it. Use an inner class when each nested instance is tied to a particular outer instance.

Creating an inner class normally requires an outer instance, for example `outer.new Inner()` from outside. The inner object keeps the outer object reachable, which can be useful but can also cause memory leaks.

#### Deep dive

A static nested class can have static members normally. Inner classes historically had restrictions on static declarations, though modern Java has relaxed some rules for static members such as local records. The key interview distinction remains the outer-instance reference.

Anonymous classes and local classes are also kinds of inner classes when declared in an instance context. Lambdas are not anonymous inner classes; their runtime representation and capture semantics are different.

#### Production angle

Prefer static nested classes by default for builders, DTO helpers, map keys and strategy objects that do not need outer state. This avoids accidental retention of large service objects, controllers or caches through hidden outer references.

#### Traps / caveats

- Inner classes can accidentally keep the outer object alive.
- A static nested class is not tied to a specific outer instance.
- Both can access private members due to nesting rules, but only inner classes have implicit outer state.
- Lambdas are not simply anonymous inner classes.

#### Optional Anki

Q: Which nested class has an implicit reference to the outer instance?
A: A non-static inner class.

</details>

<a id="jcore-class-011"></a>

<details>
<summary><strong>🧠 JCORE-CLASS-011. What problems can mutable static state create in production services?</strong></summary>

#### Short answer

Mutable static state is global shared state per class loader. It can create race conditions, request leakage, tenant leakage, test pollution, memory leaks, configuration drift, class-loader leaks and hard-to-reproduce bugs across redeploys or parallel tests.

#### Interview answer

The main issue is hidden lifetime. A static mutable field often lives much longer than a request, transaction, test, or dependency-injection scope. If it stores user data, context, caches, clocks or configuration, different parts of the application may accidentally share state that should have been scoped.

Thread safety is another issue. Every request thread sees the same static object. Without synchronization or a thread-safe structure, updates can be lost, stale, or internally inconsistent. Even with thread safety, the lifecycle and eviction policy may be unclear.

#### Deep dive

In application servers, plugin systems and tests, “global” may actually mean “global for this class loader”. This can lead to state surviving longer than expected, or duplicated statics when the same classes are loaded by different class loaders.

Static state also makes code harder to test because dependencies are hidden. Tests need reset hooks, ordering controls or isolated JVMs, all of which are signals that the design may be too global.

#### Production angle

Use dependency injection and explicit scopes for services, caches, configuration, clocks and context. Static final immutable constants are fine; mutable singletons should be rare, thread-safe, observable, resettable only when truly needed, and backed by clear ownership.

#### Traps / caveats

- Static mutable caches can leak memory without eviction.
- Static user/request context can leak data between requests.
- Parallel tests can fail because of shared static state.
- Class-loader behavior can make “singleton” assumptions wrong.

#### Optional Anki

Q: Why is mutable static state dangerous in a backend service?
A: It is shared across threads and scopes, so lifetime, thread safety and data isolation become global concerns.

</details>

<details>
<summary><strong>JCORE-CLASS-012. What is the difference between `import`, static import and package-private access?</strong></summary>

#### Short answer

`import` only lets source code use a type name without writing its fully qualified name. Static import lets code use static members without qualifying them by class name. Package-private access is an access-control rule: a declaration with no access modifier is accessible only inside the same package.

#### Interview answer

Imports do not load classes, initialize classes, change dependencies, or grant access rights. They are compile-time name resolution conveniences. You cannot import your way around `private` or package-private access.

Static imports are often useful for constants, enum constants, test assertions and factory methods, but overuse can make code unclear because the declaring class is hidden. Package-private access is about encapsulating implementation inside a package.

#### Deep dive

A normal import can import a single type or all top-level types in a package using wildcard syntax. It does not import subpackages. A static import can import a single static member or all accessible static members of a type.

Package-private is based on the package declaration, not directory layout alone. Build tools usually align directories and packages, but the language rule is the package name.

#### Production angle

Use imports for readability, static imports sparingly when they improve fluency, and package-private classes/methods to keep implementation details out of public APIs. In tests, same-package tests can access package-private internals without widening production visibility.

#### Traps / caveats

- Imports do not affect runtime class initialization.
- Wildcard imports do not import subpackages.
- Static import can hide where a method or constant comes from.
- Package-private access cannot be bypassed with import.

#### Optional Anki

Q: Does `import` grant access to package-private classes from another package?
A: No. Import only helps with names; it does not change access control.

</details>

<details>
<summary><strong>JCORE-CLASS-013. What is a compile-time constant in Java?</strong></summary>

#### Short answer

A compile-time constant is a constant expression known to the compiler, usually stored in a `final` variable of primitive type or `String`. Such constants can be used in places like `case` labels and annotations, and references to them may be inlined into client class files.

#### Interview answer

A typical constant variable is `static final int MAX = 10;` or `static final String ROLE = "admin";`. The initializer must be a constant expression: literals, simple arithmetic on constants, string concatenation of constants, and similar compile-time operations.

A `static final` field is not automatically a compile-time constant. `static final Integer X = 1;`, `static final int X = compute();`, or `static final List<String> L = ...` are not constant variables in the JLS sense.

#### Deep dive

Inlining creates binary compatibility surprises. If library version 1 exposes `public static final int TIMEOUT = 100;` and a client compiles against it, the client may contain the literal `100`. Updating the library to `200` may not affect old clients until they are recompiled.

Compile-time constants also affect initialization: reading a constant variable through another class can avoid triggering initialization of the declaring class. That is why constants should not be used to hide side effects.

#### Production angle

For public APIs, be careful with public compile-time constants whose values may change. Prefer enums, configuration, methods, or non-constant accessors for values that are not truly stable across releases.

#### Traps / caveats

- Not every `static final` field is a compile-time constant.
- Changing public constants can require client recompilation.
- Wrapper types are not primitive/String constant variables.
- Reading a compile-time constant may not initialize the declaring class.

#### Optional Anki

Q: Is `static final int X = compute();` a compile-time constant?
A: No. The value is computed at runtime, so reading it triggers class initialization.

</details>

<a id="jcore-class-014"></a>

<details>
<summary><strong>🧠 JCORE-CLASS-014. Does accessing a `static final` field always trigger class initialization?</strong></summary>

#### Short answer

No. Accessing a `static final` field that is a compile-time constant usually does not trigger initialization of the declaring class, because the compiler can inline the value. Accessing a `static final` field computed at runtime does trigger initialization.

#### Interview answer

The important distinction is not `final` but “constant variable”. `public static final String NAME = "api";` is a compile-time constant. `public static final String NAME = System.getenv("NAME");` is not. Reading the first can be compiled as a literal in the caller; reading the second requires running the declaring class initialization code.

This is often tested in interviews with a static block printing a message. If the caller reads only a constant variable, the message may not print because the declaring class was never initialized.

#### Deep dive

The behavior follows from constant expressions and active-use rules. It also has a maintenance implication: the caller’s class file may contain a copy of the old value. Recompilation is needed to pick up changed constants in many scenarios.

Fields of reference types other than `String`, even if `static final`, are not compile-time constants. For example `static final Integer X = 1;` requires class initialization when accessed normally.

#### Production angle

Do not put observable side effects in static initializers and expect them to run when constants are read. For public constants that may change, prefer accessor methods or configuration to avoid inlining surprises.

#### Traps / caveats

- `static final` is not enough; the field must be a constant variable.
- Constants can be inlined into client bytecode.
- Changing a public compile-time constant may not affect already compiled clients.
- A static block may not run when only a constant is read.

#### Optional Anki

Q: What matters for class initialization: `static final` or compile-time constant?
A: Compile-time constant. A non-constant `static final` field still triggers initialization when accessed.

</details>

<a id="jcore-class-015"></a>

<details>
<summary><strong>JCORE-CLASS-015. What is `ExceptionInInitializerError`, and when can it appear?</strong></summary>

#### Short answer

`ExceptionInInitializerError` is an `Error` thrown when an exception occurs during static initialization of a class or interface. It can appear from static field initializers or static initializer blocks, often on first active use of the class.

#### Interview answer

If a static initializer throws a runtime exception, the JVM wraps it in `ExceptionInInitializerError`. The original cause is available through the error’s cause or exception accessors. Because it is an `Error`, normal application code usually should not catch it to continue as if nothing happened.

After initialization fails, the class is considered erroneous for that class loader. Later attempts to use it can fail with `NoClassDefFoundError` saying the class could not be initialized, even though the class file exists.

#### Deep dive

Common causes include parsing invalid configuration in a static field, building a static singleton with missing dependencies, loading native libraries, reading files, connecting to external systems, or circular initialization that produces unexpected null/default values.

Checked exceptions cannot be thrown directly from static initializers unless caught or wrapped, so failures are often wrapped in unchecked exceptions first, then wrapped again by the JVM. This can make root-cause stacks noisy.

#### Production angle

Treat it as a startup/configuration/class-loading failure. Inspect the root cause, avoid heavy static initialization, move fallible startup work into explicit lifecycle components, and add tests that initialize important classes under realistic configuration.

#### Traps / caveats

- It is an `Error`, not a checked exception.
- Later failures may be `NoClassDefFoundError`, hiding the original initializer failure.
- The first stack trace usually has the most useful root cause.
- Static initialization failure can be caused by configuration or environment differences.

#### Optional Anki

Q: What usually causes `ExceptionInInitializerError`?
A: An exception thrown while running static field initializers or static initializer blocks.

</details>

<a id="jcore-class-016"></a>

<details>
<summary><strong>🧠 JCORE-CLASS-016. How can circular static initialization cause bugs?</strong></summary>

#### Short answer

Circular static initialization happens when class A’s static initialization uses class B, while class B’s static initialization uses class A. Because each class is initialized only once and fields get default values before initializers run, one class can observe another class’s partially initialized state.

#### Interview answer

The bug is not always an exception. Sometimes it is worse: a field that should be `42` is read as `0`, or a reference that should be non-null is read as `null`, because the other class is in the middle of initialization.

The order can depend on which class is first actively used. That means tests may pass when class A is touched first, but production may fail when a different code path touches class B first.

#### Deep dive

The JVM has rules to prevent recursive initialization from running the same class initializer twice. If the class is already being initialized by the current thread, the recursive request can proceed without re-running it, so default or partly assigned values may be visible.

Circular initialization is especially likely with static singletons, registries, constants that are not compile-time constants, and helper classes that initialize each other for convenience.

#### Production angle

Break cycles by moving initialization into explicit factories, dependency injection, lazy holders, or methods. Keep static initialization limited to true constants and simple immutable objects. Add startup tests that touch classes in realistic order.

#### Traps / caveats

- A circular static dependency can produce wrong values without throwing an exception.
- First active-use order can change behavior.
- Compile-time constants may hide cycles because they do not initialize the class.
- Static registries are common sources of circular initialization.

#### Optional Anki

Q: Why can circular static initialization return default values?
A: Static fields are default-initialized before initializers run, and another class may read them while initialization is still in progress.
