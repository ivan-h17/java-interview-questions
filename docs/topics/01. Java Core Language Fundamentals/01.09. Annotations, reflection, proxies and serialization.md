# 9. Annotations, reflection, proxies and serialization


<a id="jcore-meta-001"></a>

<details>
<summary><strong>JCORE-META-001. What are annotations used for in Java frameworks?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Annotations are metadata attached to code elements. Frameworks use them for declarative configuration: dependency injection, HTTP routing, transactions, validation, persistence mapping, serialization, security, tests, and code generation.</p>
</td>
<td valign="top" width="50%">

<p>Аннотации — это метаданные, прикреплённые к элементам кода. Фреймворки используют их для декларативной настройки: внедрения зависимостей, HTTP-маршрутов, транзакций, валидации, ORM-маппинга, сериализации, безопасности, тестов и генерации кода.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>An annotation does not do anything by itself. Some tool must read it: the compiler, an annotation processor, a runtime framework through reflection, or bytecode tooling. For example, <code>@Transactional</code> is meaningful because a framework creates transactional behavior around the method.</p>
<p>The benefit is that configuration stays close to the code it describes. The cost is that behavior may become less visible because it is triggered indirectly by framework conventions.</p>
</td>
<td valign="top" width="50%">

<p>Аннотация сама по себе ничего не выполняет. Её должен прочитать инструмент: компилятор, процессор аннотаций, фреймворк через рефлексию или инструмент работы с байткодом. Например, <code>@Transactional</code> имеет смысл только потому, что фреймворк добавляет вокруг метода транзакционное поведение.</p>
<p>Плюс в том, что настройка находится рядом с кодом, который описывает. Минус — поведение становится менее явным, потому что запускается косвенно через правила фреймворка.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Annotations can target classes, methods, fields, parameters, type uses, and other elements. They can be retained only in source, in the class file, or at runtime. That retention choice determines which tools can see them.</p>
</td>
<td valign="top" width="50%">

<p>Аннотации могут ставиться на классы, методы, поля, параметры, использование типов и другие элементы. Они могут сохраняться только в исходном коде, в <code>.class</code>-файле или во время выполнения. Выбор политики хранения определяет, какие инструменты смогут их увидеть.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production services, annotations are powerful but should not replace clear design. Know which annotations are interpreted at compile time and which at runtime, and understand the proxy or reflection behavior behind important framework annotations.</p>
</td>
<td valign="top" width="50%">

<p>В промышленном сервисе аннотации очень полезны, но не должны заменять понятный дизайн. Важно знать, какие аннотации обрабатываются при компиляции, какие — во время выполнения, и какое прокси- или рефлексивное поведение стоит за ключевыми аннотациями фреймворка.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>An annotation is metadata, not executable behavior by itself.</li>
<li>Framework annotations can hide control flow from readers.</li>
<li>Wrong retention or target can make an annotation invisible where you expect it.</li>
<li>Custom annotations need a processor or runtime code to have an effect.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Аннотация — это метаданные, а не выполняемое поведение само по себе.</li>
<li>Аннотации фреймворка могут скрывать поток управления от читателя.</li>
<li>Неверные <code>@Retention</code> или <code>@Target</code> делают аннотацию невидимой там, где вы ожидаете её увидеть.</li>
<li>Пользовательская аннотация начинает работать только при наличии процессора или кода, который её читает.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why does <code>@Transactional</code> work?<br>A: Because a framework reads the annotation and applies transactional behavior, usually through a proxy/interceptor.</p>
</td>
<td valign="top" width="50%">

<p>Q: Почему работает <code>@Transactional</code>?<br>A: Потому что фреймворк читает аннотацию и добавляет транзакционное поведение, обычно через proxy или перехватчик (interceptor).</p>

</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>JCORE-META-002. What is the difference between source, class and runtime annotation retention?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>SOURCE</code> annotations are discarded by the compiler. <code>CLASS</code> annotations are written to the class file but are not necessarily available through reflection. <code>RUNTIME</code> annotations are kept in the class file and visible to runtime reflection.</p>
</td>
<td valign="top" width="50%">

<p><code>SOURCE</code>-аннотации отбрасываются компилятором. <code>CLASS</code>-аннотации записываются в <code>.class</code>-файл, но обычно не доступны через рефлексию. <code>RUNTIME</code>-аннотации сохраняются в <code>.class</code>-файле и видны рефлексии во время выполнения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Retention defines how long annotation metadata survives. <code>SOURCE</code> is useful for compile-time checks such as <code>@Override</code> or tools that read source. <code>CLASS</code> is useful for bytecode tools and some compile-time or build-time processing. <code>RUNTIME</code> is needed when a framework reads annotations while the application is running.</p>
<p>If no <code>@Retention</code> is specified, the default is <code>RetentionPolicy.CLASS</code>. That is a common surprise for custom annotations expected to work with reflection.</p>
</td>
<td valign="top" width="50%">

<p>Политика хранения определяет, как долго живут метаданные аннотации. <code>SOURCE</code> удобна для проверок компилятора и инструментов, читающих исходники. <code>CLASS</code> полезна для инструментов байткода и обработки на этапе сборки. <code>RUNTIME</code> нужна, когда фреймворк читает аннотацию во время работы приложения.</p>
<p>Если <code>@Retention</code> не указана, используется <code>RetentionPolicy.CLASS</code>. Это частая неожиданность для пользовательских аннотаций, которые ожидали читать через рефлексию.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Choosing runtime retention has a cost: metadata remains available at runtime and frameworks may scan it. Choosing source retention means runtime code cannot see it at all. The retention policy should match the consumer of the annotation.</p>
</td>
<td valign="top" width="50%">

<p>Выбор <code>RUNTIME</code> имеет цену: метаданные остаются доступными во время выполнения, и фреймворки могут их сканировать. Выбор <code>SOURCE</code> означает, что код во время выполнения аннотацию не увидит. Политика хранения должна соответствовать потребителю аннотации.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For framework integration, always check retention. A custom validation or mapping annotation intended for runtime use must have <code>@Retention(RetentionPolicy.RUNTIME)</code>. A Lombok-style or static-analysis annotation may only need source retention.</p>
</td>
<td valign="top" width="50%">

<p>При интеграции с фреймворком всегда проверяйте <code>@Retention</code>. Пользовательская аннотация для валидации во время выполнения или маппинга должна иметь <code>@Retention(RetentionPolicy.RUNTIME)</code>. Аннотации в стиле Lombok или статического анализа могут жить только в исходном коде.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Default retention is <code>CLASS</code>, not <code>RUNTIME</code>.</li>
<li>Reflection cannot read <code>SOURCE</code> annotations.</li>
<li>Runtime frameworks usually require <code>RUNTIME</code> retention.</li>
<li>Bytecode tools may use <code>CLASS</code> retention without reflection.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Политика по умолчанию — <code>CLASS</code>, а не <code>RUNTIME</code>.</li>
<li>Рефлексия не читает <code>SOURCE</code>-аннотации.</li>
<li>Фреймворкам, работающим во время выполнения, обычно нужна <code>RUNTIME</code>-политика.</li>
<li>Инструменты байткода могут использовать <code>CLASS</code>-аннотации без рефлексии.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why is my custom annotation not visible through reflection?<br>A: It probably does not have <code>@Retention(RetentionPolicy.RUNTIME)</code>.</p>
</td>
<td valign="top" width="50%">

<p>Q: Почему моя аннотация не видна через рефлексию?<br>A: Скорее всего, у неё нет <code>@Retention(RetentionPolicy.RUNTIME)</code>.</p>

</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>JCORE-META-003. What does an annotation <code>@Target</code> control?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>@Target</code> controls where an annotation is legal: class, method, field, constructor, parameter, type use, package, module, and other element kinds. The compiler rejects uses outside the declared targets.</p>
</td>
<td valign="top" width="50%">

<p><code>@Target</code> задаёт, где аннотацию разрешено применять: на классе, методе, поле, конструкторе, параметре, использовании типа, пакете, модуле и других видах элементов. Компилятор отклоняет применение вне разрешённых целей.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For example, <code>@Target(ElementType.METHOD)</code> means the annotation can be placed on methods but not on fields or classes. Multiple targets can be listed. <code>ElementType.TYPE_USE</code> is broader and allows annotations in type positions, such as <code>List&lt;@NonNull String&gt;</code>.</p>
<p>If <code>@Target</code> is absent, the annotation can generally be used on declaration contexts where annotations are syntactically allowed, but not on type-use contexts. To support places such as <code>List&lt;@NonNull String&gt;</code>, declare <code>@Target(ElementType.TYPE_USE)</code>. Being explicit is usually better for custom annotations.</p>
</td>
<td valign="top" width="50%">

<p>Например, <code>@Target(ElementType.METHOD)</code> означает, что аннотацию можно ставить на методы, но нельзя на поля или классы. Можно указать несколько целей. <code>ElementType.TYPE_USE</code> шире: он разрешает аннотации в позициях типа, например <code>List&lt;@NonNull String&gt;</code>.</p>
<p>Если <code>@Target</code> отсутствует, аннотацию обычно можно применять к контекстам объявления, где синтаксис разрешает аннотации, но не к контекстам использования типа. Для мест вроде <code>List&lt;@NonNull String&gt;</code> нужен <code>@Target(ElementType.TYPE_USE)</code>. Для пользовательских аннотаций явный список целей чаще понятнее.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>@Target</code> is a compile-time restriction, not a runtime scanner. A framework may still ignore an annotation even if it is legal at that location. Legal placement and framework semantics are separate questions.</p>
</td>
<td valign="top" width="50%">

<p><code>@Target</code> — это ограничение компиляции, а не механизм сканирования во время выполнения. Фреймворк может проигнорировать аннотацию, даже если она легально стоит в этом месте. Допустимость размещения и смысл для фреймворка — разные вопросы.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production code, precise targets make annotations self-documenting and prevent misuse. For example, an annotation intended only for REST handler methods should not be allowed on arbitrary fields.</p>
</td>
<td valign="top" width="50%">

<p>В промышленном коде точный <code>@Target</code> делает аннотацию самодокументируемой и предотвращает ошибочное применение. Например, аннотацию для REST-методов не стоит разрешать на произвольных полях.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>A legal annotation placement does not guarantee framework behavior.</li>
<li><code>TYPE</code> and <code>TYPE_USE</code> are different targets.</li>
<li>Forgetting <code>PARAMETER</code> can break parameter-level annotations.</li>
<li>Being too broad makes custom annotations easier to misuse.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Легальное размещение аннотации не гарантирует, что фреймворк её обработает.</li>
<li><code>TYPE</code> и <code>TYPE_USE</code> — разные цели.</li>
<li>Если забыть <code>PARAMETER</code>, аннотация не сработает на параметрах.</li>
<li>Слишком широкий <code>@Target</code> облегчает неправильное использование аннотации.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does <code>@Target</code> enforce?<br>A: The Java elements on which an annotation may be written.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что проверяет <code>@Target</code>?<br>A: На каких элементах Java разрешено писать аннотацию.</p>

</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>JCORE-META-004. What is reflection, and why do frameworks use it?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Reflection is the ability to inspect and sometimes access classes, methods, fields, constructors, annotations, and generic metadata at runtime. Frameworks use it to wire code by convention and metadata instead of requiring manual registration for every class.</p>
</td>
<td valign="top" width="50%">

<p>Рефлексия — это возможность во время выполнения изучать, а иногда и вызывать классы, методы, поля, конструкторы, аннотации и часть обобщённых метаданных. Фреймворки используют её, чтобы связывать код по соглашениям и метаданным, а не требовать ручной регистрации каждого класса.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Dependency injection containers inspect constructors and annotations to create beans. JSON libraries inspect fields or accessors to serialize objects. ORMs inspect entity classes and mappings. Test frameworks find test methods. Reflection lets framework code work with application classes it did not know at compile time.</p>
<p>Reflection can also invoke methods, create instances, and access members subject to Java access rules and module restrictions. Modern Java's module system and stronger encapsulation can limit reflective access unless packages are opened.</p>
</td>
<td valign="top" width="50%">

<p>Контейнеры внедрения зависимостей смотрят на конструкторы и аннотации, чтобы создавать bean-ы. JSON-библиотеки изучают поля или аксессоры для сериализации. ORM читает классы сущностей и маппинг. Тестовые фреймворки находят тестовые методы. Рефлексия позволяет фреймворку работать с классами приложения, о которых он не знал при компиляции.</p>
<p>Через рефлексию можно также вызывать методы, создавать экземпляры и обращаться к членам класса с учётом правил доступа Java и ограничений модульной системы. В современной Java сильная инкапсуляция может запретить доступ, если пакет не открыт.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Reflection trades static explicitness for runtime flexibility. The compiler cannot check many reflective names and calls, so mistakes move from compile time to application startup or runtime paths.</p>
</td>
<td valign="top" width="50%">

<p>Рефлексия меняет статическую явность на гибкость во время выполнения. Компилятор не может проверить многие имена и вызовы, поэтому ошибки переезжают из этапа компиляции в старт приложения или в конкретный путь выполнения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, reflection is acceptable when it is isolated inside frameworks or infrastructure. For your own code, prefer explicit APIs when possible. If using reflection, cache metadata, test startup paths, and be aware of native-image or modular-runtime constraints.</p>
</td>
<td valign="top" width="50%">

<p>В промышленном коде рефлексия приемлема, когда она изолирована внутри фреймворка или инфраструктуры. В собственном коде по возможности лучше выбирать явные API. Если рефлексия всё же нужна, кэшируйте метаданные, тестируйте старт приложения и учитывайте ограничения native image и модульной среды.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Reflective failures often appear at runtime, not compile time.</li>
<li>Access to private members can be restricted by modules or security policy.</li>
<li>Reflection can be slower if metadata is repeatedly discovered.</li>
<li>It can make code harder for refactoring tools and static analyzers.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Ошибки рефлексии часто проявляются во время выполнения, а не при компиляции.</li>
<li>Доступ к закрытым членам может быть ограничен модулями или политиками безопасности.</li>
<li>Рефлексия может быть медленной при повторном поиске метаданных.</li>
<li>Такой код сложнее для рефакторинга и статического анализа.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why do frameworks use reflection?<br>A: To inspect and operate on application classes dynamically using metadata and conventions.</p>
</td>
<td valign="top" width="50%">

<p>Q: Зачем фреймворкам рефлексия?<br>A: Чтобы динамически изучать и использовать классы приложения по метаданным и соглашениям.</p>

</td>
</tr>
</tbody>

<a id="jcore-meta-005"></a>

<details>
<summary><strong>JCORE-META-005. What are the downsides of reflection?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Reflection reduces compile-time safety, can hurt readability, has performance overhead if used carelessly, may break encapsulation, complicates refactoring, and can be restricted by the module system or native-image environments.</p>
</td>
<td valign="top" width="50%">

<p>Рефлексия снижает безопасность на этапе компиляции, ухудшает читаемость, при неосторожном использовании даёт накладные расходы, может нарушать инкапсуляцию, усложняет рефакторинг и ограничивается модульной системой или средами native image.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A reflective call often refers to members by names or metadata rather than direct type-safe references. If a method is renamed, the compiler may not catch all reflective usages. Exceptions are also wrapped in reflective exceptions such as <code>InvocationTargetException</code>, which adds noise.</p>
<p>Reflection can also bypass normal access boundaries when allowed. That is powerful for frameworks but dangerous in application code because it couples code to private implementation details.</p>
</td>
<td valign="top" width="50%">

<p>Рефлексивный вызов часто обращается к членам класса по имени или метаданным, а не через типобезопасную ссылку. Если метод переименовали, компилятор может не найти все такие места. Исключения также заворачиваются в рефлексивные исключения вроде <code>InvocationTargetException</code>, что добавляет шум.</p>
<p>Рефлексия может обходить обычные границы доступа, если среда это разрешает. Для фреймворков это мощный инструмент, но в прикладном коде он опасен: появляется зависимость от внутренних деталей реализации.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Performance cost is often not about one reflective call but about repeated scanning and metadata lookup. Frameworks usually cache reflective metadata and generate accessors or bytecode where needed. Your own reflection utilities should do the same if they are on hot paths.</p>
</td>
<td valign="top" width="50%">

<p>Затраты производительности часто связаны не с одним рефлексивным вызовом, а с повторным сканированием и поиском метаданных. Фреймворки обычно кэшируют рефлексивные метаданные и при необходимости генерируют аксессоры или байткод. Собственные утилиты должны делать то же самое, если попали в горячий путь.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, reflection may affect startup time, memory use, observability, and compatibility with GraalVM native image. It should be documented and covered by integration tests because failures often appear only with real wiring and packaging.</p>
</td>
<td valign="top" width="50%">

<p>В промышленной эксплуатации рефлексия может влиять на время старта, память, наблюдаемость и совместимость с GraalVM native image. Её стоит документировать и покрывать интеграционными тестами, потому что ошибки часто проявляются только при реальной сборке и настройке приложения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not use reflection when a normal method call or interface would be clearer.</li>
<li>Cache metadata instead of scanning repeatedly.</li>
<li>Expect module-access issues in modern Java.</li>
<li>Avoid depending on private fields of classes you do not own.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не используйте рефлексию там, где обычный вызов метода или интерфейс понятнее.</li>
<li>Кэшируйте метаданные вместо повторного сканирования.</li>
<li>В современной Java учитывайте ограничения доступа модулей.</li>
<li>Не завязывайтесь на закрытые поля классов, которыми вы не владеете.</li>
</ul>

<summary><strong>JCORE-META-006. What are dynamic proxies used for in Java frameworks?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Dynamic proxies are runtime-generated objects that implement interfaces and route method calls through an invocation handler. Frameworks use them for cross-cutting behavior such as transactions, security, caching, metrics, retries, logging, and remote clients.</p>
</td>
<td valign="top" width="50%">

<p>Динамические прокси — это объекты, созданные во время выполнения, которые реализуют интерфейсы и передают вызовы методов обработчику. Фреймворки используют их для сквозного поведения: транзакций, безопасности, кэширования, метрик, повторов, логирования и удалённых клиентов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The JDK proxy mechanism works with interfaces: the proxy implements the same interface as the target and delegates calls to an <code>InvocationHandler</code>. The handler can run code before and after the target call, change arguments, handle exceptions, or decide not to call the target.</p>
<p>Frameworks can also use class-based proxies through bytecode generation libraries. Those can proxy classes, but final classes and final methods create limits because subclass-based interception depends on overriding methods.</p>
</td>
<td valign="top" width="50%">

<p>Механизм JDK proxy работает с интерфейсами: proxy реализует тот же интерфейс, что и целевой объект, и передаёт вызовы в <code>InvocationHandler</code>. Обработчик может выполнить код до и после вызова, изменить аргументы, обработать исключение или вообще не вызывать цель.</p>
<p>Фреймворки также могут использовать прокси на основе классов через генерацию байткода. Они умеют проксировать классы, но <code>final</code>-классы и <code>final</code>-методы ограничивают такой подход, потому что перехват через наследование требует переопределения методов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A proxy changes the object you are calling. The caller sees an object with the same API, but the actual runtime class may be generated. This is why annotations such as <code>@Transactional</code> often work only when a call goes through the proxy.</p>
</td>
<td valign="top" width="50%">

<p>Прокси меняет объект, к которому обращается клиент. Клиент видит тот же API, но фактический класс во время выполнения может быть сгенерированным. Поэтому аннотации вроде <code>@Transactional</code> часто работают только тогда, когда вызов проходит через proxy.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, understand where proxies are inserted. Self-invocation, direct construction with <code>new</code>, final methods, package visibility, and equality checks can all bypass or confuse proxy-based behavior.</p>
</td>
<td valign="top" width="50%">

<p>В промышленном коде важно понимать, где именно вставлен proxy. Самовызов внутри объекта, ручное создание через <code>new</code>, <code>final</code>-методы, видимость пакета и проверки равенства могут обойти или запутать поведение на основе прокси.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>JDK dynamic proxies require interfaces.</li>
<li>Subclass-based proxies cannot override final methods.</li>
<li>A method call must go through the proxy for advice/interception to run.</li>
<li>Proxy classes can make stack traces and debugging less direct.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Динамический proxy JDK (JDK dynamic proxy) требует интерфейс.</li>
<li>Прокси на основе наследования не может переопределить <code>final</code>-метод.</li>
<li>Чтобы перехват сработал, вызов должен пройти через proxy.</li>
<li>Сгенерированные классы proxy усложняют трассировки стека и отладку.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>

<details>
<summary><strong>JCORE-META-007. How can proxies affect method calls, equality checks and stack traces?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A proxy is not the original class. It can intercept only calls that pass through it, can change the runtime class seen by <code>getClass()</code>, may affect <code>equals()</code>/<code>hashCode()</code>, and often adds generated frames to stack traces.</p>
</td>
<td valign="top" width="50%">

<p>Proxy — не исходный класс. Он перехватывает только вызовы, которые проходят через него, меняет фактический класс, видимый через <code>getClass()</code>, может влиять на <code>equals()</code>/<code>hashCode()</code> и часто добавляет сгенерированные кадры в трассировку стека.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The method-call issue is common with Spring-style AOP: an external call to a proxied bean goes through the proxy, but a method inside the target calling another method on <code>this</code> may bypass the proxy. Then transactional, caching, or security advice may not run.</p>
<p>Equality can also be tricky. If <code>equals()</code> uses strict <code>getClass()</code>, a proxy subclass may not compare equal to the target type. If equality uses identity, two wrappers around the same target can still be different objects.</p>
</td>
<td valign="top" width="50%">

<p>Проблема вызовов часто встречается в AOP-подходе Spring: внешний вызов к bean-у, обёрнутому в proxy, проходит через proxy, а метод внутри целевого объекта, вызывающий другой метод через <code>this</code>, может обойти proxy. Тогда транзакции, кэширование или безопасность не сработают.</p>
<p>С равенством тоже есть нюансы. Если <code>equals()</code> строго проверяет <code>getClass()</code>, proxy-подкласс может не считаться равным целевому типу. Если равенство основано на идентичности, две обёртки над одной целью всё равно будут разными объектами.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Stack traces include proxy and interceptor frames, so the first application method may not be at the top. Debugging requires recognizing generated class names and framework invocation layers.</p>
</td>
<td valign="top" width="50%">

<p>В трассировке стека появляются кадры proxy и перехватчиков (interceptors), поэтому первый метод приложения не всегда находится наверху. При отладке нужно узнавать имена сгенерированных классов и слои вызовов фреймворка.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, avoid designs where correctness depends on an internal self-invocation being intercepted. Keep equality implementations proxy-aware when entities or services may be proxied, and use framework utilities if the framework provides them.</p>
</td>
<td valign="top" width="50%">

<p>В промышленном коде лучше не строить корректность на том, что внутренний самовызов будет перехвачен. Реализации равенства должны учитывать proxy, если сущности или сервисы могут проксироваться; если фреймворк даёт специальные утилиты, стоит использовать их.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Self-invocation can bypass proxy advice.</li>
<li>Strict <code>getClass()</code>-based equality may fail with subclass proxies.</li>
<li>Generated proxy frames can obscure the real call path.</li>
<li>Directly injecting or constructing the target instead of the proxy bypasses framework behavior.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Самовызов может обойти поведение proxy.</li>
<li>Равенство через строгий <code>getClass()</code> может ломаться с proxy-подклассами.</li>
<li>Сгенерированные кадры proxy скрывают реальный путь вызова.</li>
<li>Если внедрить или создать целевой объект вместо proxy, поведение фреймворка не выполнится.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>

</td>
<td valign="top" width="50%">

<details>
<summary><strong>JCORE-META-008. What are the risks of Java native serialization?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Java native serialization is risky because deserializing untrusted data can execute dangerous object graphs, expose gadget-chain attacks, bypass constructors, and create fragile version coupling. It is usually avoided for public or untrusted data formats.</p>
</td>
<td valign="top" width="50%">

<p>Нативная сериализация Java рискованна: десериализация недоверенных данных может активировать опасные графы объектов, привести к атакам через цепочки гаджетов (gadget chain), обойти конструкторы и создать хрупкую связь версий. Для публичных или недоверенных форматов её обычно избегают.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>Serializable</code> was designed for Java object graphs, not for stable public protocols. Deserialization can instantiate objects without normal constructors and invoke special hooks such as <code>readObject</code>. Attackers can exploit classes on the classpath whose deserialization has side effects.</p>
<p>It also creates compatibility problems. Renaming fields, changing class hierarchy, or changing <code>serialVersionUID</code> can break old serialized data. The binary format is Java-specific and not friendly to cross-language systems.</p>
</td>
<td valign="top" width="50%">

<p><code>Serializable</code> задуман для графов Java-объектов, а не для стабильных публичных протоколов. Десериализация может создавать объекты без обычных конструкторов и вызывать специальные методы вроде <code>readObject</code>. Злоумышленник может использовать классы из classpath, у которых при десериализации есть побочные эффекты.</p>
<p>Есть и проблемы совместимости. Переименование полей, изменение иерархии или <code>serialVersionUID</code> может сломать старые данные. Бинарный формат специфичен для Java и неудобен для систем на разных языках.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The most serious risk is security. Treat Java deserialization like executing code from the input unless strong filters and strict type allow-lists are in place. Even then, prefer safer data formats for external boundaries.</p>
</td>
<td valign="top" width="50%">

<p>Главный риск — безопасность. Десериализацию Java стоит воспринимать почти как выполнение кода из входных данных, если нет строгих фильтров и белого списка типов. Даже при таких мерах для внешних границ лучше выбирать более безопасные форматы данных.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For production APIs and messaging, prefer JSON, Avro, Protobuf, or another explicit schema/format. If native serialization is unavoidable for legacy systems, use serialization filters, minimize the classpath exposure, version deliberately, and never deserialize untrusted payloads blindly.</p>
</td>
<td valign="top" width="50%">

<p>Для промышленных API и сообщений лучше использовать JSON, Avro, Protobuf или другой явный формат со схемой. Если нативная сериализация неизбежна из-за устаревшей системы (legacy), применяйте фильтры сериализации, ограничивайте доступные типы, версионируйте формат осознанно и никогда не десериализуйте недоверенную полезную нагрузку (payload) вслепую.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Never deserialize untrusted data with unrestricted native serialization.</li>
<li>Constructors are not the normal initialization path during deserialization.</li>
<li>Versioning object graphs is fragile.</li>
<li>Serialization hooks can hide surprising behavior.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Никогда не десериализуйте недоверенные данные через неограниченную нативную сериализацию.</li>
<li>При десериализации конструкторы не являются обычным путём инициализации.</li>
<li>Версионировать графы объектов хрупко.</li>
<li>Специальные методы сериализации могут скрывать неожиданное поведение.</li>
</ul>

<details>
<summary><strong>🧠 JCORE-META-009. What is the difference between runtime reflection and annotation processing?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Runtime reflection inspects metadata while the application is running. Annotation processing runs during compilation and can validate annotations, generate source files, or report compile-time errors before the application starts.</p>
</td>
<td valign="top" width="50%">

<p>Рефлексия во время выполнения читает метаданные уже работающего приложения. Обработка аннотаций (annotation processing) выполняется при компиляции: она может проверять аннотации, генерировать исходный код и выдавать ошибки до запуска приложения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Runtime reflection is flexible because it sees the actual classes loaded in the application, but failures appear at startup or runtime. Annotation processing moves work earlier: tools such as mappers, builders, and dependency metadata generators can produce code that is then compiled normally.</p>
<p>Annotation processors generally operate on source-level or compiler model elements, not live objects. They do not execute application logic in the same way a runtime framework does.</p>
</td>
<td valign="top" width="50%">

<p>Рефлексия во время выполнения гибкая: она видит реальные классы, загруженные приложением. Но ошибки проявляются при старте или в конкретном сценарии выполнения. Обработка аннотаций переносит работу раньше: генераторы мапперов, классов-строителей (builders) и метаданных зависимостей создают код, который затем компилируется обычным образом.</p>
<p>Процессоры аннотаций обычно работают с моделью исходного кода или компилятора, а не с живыми объектами. Они не выполняют бизнес-логику приложения так, как это делает фреймворк времени выполнения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The trade-off is startup/runtime flexibility versus compile-time safety and generated code. Annotation processing can reduce reflection and improve native-image compatibility, but it adds build complexity and generated sources to understand.</p>
</td>
<td valign="top" width="50%">

<p>Компромисс здесь такой: гибкость при запуске и во время выполнения против статической проверки и сгенерированного кода. Обработка аннотаций может уменьшить рефлексию и улучшить совместимость с native image, но добавляет сложность сборки и сгенерированные исходники.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production systems, annotation processing is attractive for stable mappings and repetitive boilerplate. Runtime reflection is useful for plugins, dynamic frameworks, and cases where classes are not fully known at compile time. Many frameworks combine both approaches.</p>
</td>
<td valign="top" width="50%">

<p>В промышленных системах обработка аннотаций удобна для стабильных маппингов и повторяющегося шаблонного кода. Рефлексия полезна для плагинов, динамических фреймворков и случаев, где классы не полностью известны при компиляции. Многие фреймворки сочетают оба подхода.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">

<tr>
<td valign="top" width="50%">

</td>

<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">

<th colspan="2" align="left">Production angle</th>

<td valign="top" width="50%">

<p>В промышленном сервисе правила проксирования нужно проверять тестами. Нельзя считать, что аннотация работает только потому, что код компилируется. Интеграционные тесты должны проходить через реальную сборку bean-ов и настоящий путь вызова.</p>

<details>
<summary><strong>JCORE-META-011. What does <code>Serializable</code> mean in Java?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>Serializable</code> is a marker interface indicating that objects of a class may be serialized by Java's native serialization mechanism. It does not define methods; the serialization runtime interprets the class structure and special serialization hooks.</p>
</td>
<td valign="top" width="50%">

<p><code>Serializable</code> — маркерный интерфейс, показывающий, что объекты класса можно сериализовать встроенным механизмом Java. Он не объявляет методов; механизм сериализации сам интерпретирует структуру класса и специальные методы сериализации.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>By default, native serialization includes non-static, non-transient fields that are serializable. Static fields belong to the class, not the object state. Transient fields are skipped. If a referenced object is not serializable, serialization can fail with <code>NotSerializableException</code>.</p>
<p>Classes can customize serialization through special methods such as <code>writeObject</code>, <code>readObject</code>, <code>writeReplace</code>, and <code>readResolve</code>. That power is also part of why native serialization is hard to reason about and risky for untrusted data.</p>
</td>
<td valign="top" width="50%">

<p>По умолчанию нативная сериализация включает нестатические и не-<code>transient</code> поля, которые сами сериализуемы. Статические поля относятся к классу, а не к состоянию объекта. <code>transient</code>-поля пропускаются. Если связанный объект не сериализуем, возможен <code>NotSerializableException</code>.</p>
<p>Классы могут настраивать сериализацию специальными методами вроде <code>writeObject</code>, <code>readObject</code>, <code>writeReplace</code> и <code>readResolve</code>. Эта гибкость одновременно делает нативную сериализацию сложной и рискованной для недоверенных данных.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Implementing <code>Serializable</code> is not a guarantee of a good external format. It says something about Java's object serialization mechanism, not about JSON, database persistence, or general API compatibility.</p>
</td>
<td valign="top" width="50%">

<p>Реализация <code>Serializable</code> не означает хороший внешний формат. Она относится к механизму сериализации Java-объектов, а не к JSON, хранению в БД или общей совместимости API.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In modern backend systems, implement <code>Serializable</code> only when a framework or legacy protocol truly requires it. For service communication and storage, prefer explicit formats and schemas.</p>
</td>
<td valign="top" width="50%">

<p>В современных серверных системах <code>Serializable</code> стоит реализовывать только тогда, когда этого действительно требует фреймворк или устаревший протокол (legacy). Для обмена между сервисами и хранения лучше выбирать явные форматы и схемы.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>Serializable</code> has no methods; it is a marker.</li>
<li>All non-transient object fields must be serializable unless custom logic handles them.</li>
<li>It is unrelated to JSON serialization unless a library chooses to consider it.</li>
<li>Do not deserialize untrusted native-serialized data.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>Serializable</code> не содержит методов; это маркер.</li>
<li>Все нестатические не-<code>transient</code> объектные поля должны быть сериализуемыми, если нет специальной логики.</li>
<li>Он не связан с JSON-сериализацией, если конкретная библиотека сама так не решила.</li>
<li>Не десериализуйте недоверенные данные встроенным механизмом Java.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>

<details>
<summary><strong>JCORE-META-012. What is <code>serialVersionUID</code>, and why can it matter?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>serialVersionUID</code> is a version identifier for a serializable class. During deserialization, Java checks that the stream's class version matches the local class version; a mismatch can cause <code>InvalidClassException</code>.</p>
</td>
<td valign="top" width="50%">

<p><code>serialVersionUID</code> — идентификатор версии сериализуемого класса. При десериализации Java проверяет, совпадает ли версия класса в потоке с локальной версией; несовпадение может привести к <code>InvalidClassException</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If a class does not declare <code>serialVersionUID</code>, the JVM computes one from class details. That computed value can change after seemingly harmless modifications, compiler differences, or refactoring. Declaring it explicitly makes the compatibility decision intentional.</p>
<p>Keeping the same value means “I believe old serialized data is compatible with this class.” Changing it means “old serialized data should not be accepted.” The value does not magically make incompatible class changes safe; it only controls the version check.</p>
</td>
<td valign="top" width="50%">

<p>Если класс не объявляет <code>serialVersionUID</code>, JVM вычисляет его по деталям класса. Такое вычисленное значение может измениться после внешне безобидных правок, другой версии компилятора или рефакторинга. Явное объявление делает решение о совместимости осознанным.</p>
<p>Оставить то же значение означает: «я считаю старые сериализованные данные совместимыми с этим классом». Изменить значение означает: «старые данные принимать нельзя». Само значение не делает несовместимые изменения безопасными; оно только управляет проверкой версии.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Serialization compatibility depends on field changes, class hierarchy, custom serialization methods, and invariants. <code>serialVersionUID</code> is one part of the protocol, not a migration system.</p>
</td>
<td valign="top" width="50%">

<p>Совместимость сериализации зависит от изменений полей, иерархии классов, специальных методов сериализации и инвариантов. <code>serialVersionUID</code> — часть протокола, но не система миграции данных.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, explicitly declare <code>serialVersionUID</code> for classes that are truly serialized across versions. Add compatibility tests if old serialized payloads must remain readable. For ordinary DTOs not using native serialization, do not treat this field as a general versioning solution.</p>
</td>
<td valign="top" width="50%">

<p>В промышленном коде явно объявляйте <code>serialVersionUID</code> у классов, которые действительно сериализуются между версиями. Если старые полезные нагрузки (payload) должны читаться, нужны тесты совместимости. Для обычных DTO без нативной сериализации это поле не является универсальным механизмом версионирования.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>The computed default can change unexpectedly.</li>
<li>Same <code>serialVersionUID</code> does not guarantee semantic compatibility.</li>
<li>Changing it rejects old streams rather than migrating them.</li>
<li>It matters only for Java native serialization.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Вычисляемое значение по умолчанию может измениться неожиданно.</li>
<li>Одинаковый <code>serialVersionUID</code> не гарантирует смысловую совместимость.</li>
<li>Изменение значения отклоняет старые потоки, а не мигрирует их.</li>
<li>Он важен только для нативной сериализации Java.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>

<td valign="top" width="50%">

<p>Q: Зачем явно объявлять <code>serialVersionUID</code>?<br>A: Чтобы решение о совместимости нативной сериализации было стабильным и осознанным.</p>
