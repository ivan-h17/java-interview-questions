# 01.09. Annotations, reflection, proxies and serialization

---

<a id="jcore-meta-001"></a>

<details>
<summary><strong>JCORE-META-001. What are annotations used for in Java frameworks?</strong></summary>

#### Short answer

Annotations are metadata attached to code elements. Frameworks use them for declarative configuration: dependency injection, HTTP routing, transactions, validation, persistence mapping, serialization, security, tests, and code generation.

#### Interview answer

An annotation does not do anything by itself. Some tool must read it: the compiler, an annotation processor, a runtime framework through reflection, or bytecode tooling. For example, `@Transactional` is meaningful because a framework creates transactional behavior around the method.

The benefit is that configuration stays close to the code it describes. The cost is that behavior may become less visible because it is triggered indirectly by framework conventions.

#### Deep dive

Annotations can target classes, methods, fields, parameters, type uses, and other elements. They can be retained only in source, in the class file, or at runtime. That retention choice determines which tools can see them.

#### Production angle

In production services, annotations are powerful but should not replace clear design. Know which annotations are interpreted at compile time and which at runtime, and understand the proxy or reflection behavior behind important framework annotations.

#### Traps / caveats

- An annotation is metadata, not executable behavior by itself.
- Framework annotations can hide control flow from readers.
- Wrong retention or target can make an annotation invisible where you expect it.
- Custom annotations need a processor or runtime code to have an effect.

#### Optional Anki

Q: Why does `@Transactional` work?
A: Because a framework reads the annotation and applies transactional behavior, usually through a proxy/interceptor.

</details>

<details>
<summary><strong>JCORE-META-002. What is the difference between source, class and runtime annotation retention?</strong></summary>

#### Short answer

`SOURCE` annotations are discarded by the compiler. `CLASS` annotations are written to the class file but are not necessarily available through reflection. `RUNTIME` annotations are kept in the class file and visible to runtime reflection.

#### Interview answer

Retention defines how long annotation metadata survives. `SOURCE` is useful for compile-time checks such as `@Override` or tools that read source. `CLASS` is useful for bytecode tools and some compile-time or build-time processing. `RUNTIME` is needed when a framework reads annotations while the application is running.

If no `@Retention` is specified, the default is `RetentionPolicy.CLASS`. That is a common surprise for custom annotations expected to work with reflection.

#### Deep dive

Choosing runtime retention has a cost: metadata remains available at runtime and frameworks may scan it. Choosing source retention means runtime code cannot see it at all. The retention policy should match the consumer of the annotation.

#### Production angle

For framework integration, always check retention. A custom validation or mapping annotation intended for runtime use must have `@Retention(RetentionPolicy.RUNTIME)`. A Lombok-style or static-analysis annotation may only need source retention.

#### Traps / caveats

- Default retention is `CLASS`, not `RUNTIME`.
- Reflection cannot read `SOURCE` annotations.
- Runtime frameworks usually require `RUNTIME` retention.
- Bytecode tools may use `CLASS` retention without reflection.

#### Optional Anki

Q: Why is my custom annotation not visible through reflection?
A: It probably does not have `@Retention(RetentionPolicy.RUNTIME)`.

</details>

<a id="jcore-meta-003"></a>

<details>
<summary><strong>JCORE-META-003. What does an annotation `@Target` control?</strong></summary>

#### Short answer

`@Target` controls where an annotation is legal: class, method, field, constructor, parameter, type use, package, module, and other element kinds. The compiler rejects uses outside the declared targets.

#### Interview answer

For example, `@Target(ElementType.METHOD)` means the annotation can be placed on methods but not on fields or classes. Multiple targets can be listed. `ElementType.TYPE_USE` is broader and allows annotations in type positions, such as `List<@NonNull String>`.

If `@Target` is absent, the annotation can generally be used on declaration contexts where annotations are syntactically allowed, but not on type-use contexts. To support places such as `List<@NonNull String>`, declare `@Target(ElementType.TYPE_USE)`. Being explicit is usually better for custom annotations.

#### Deep dive

`@Target` is a compile-time restriction, not a runtime scanner. A framework may still ignore an annotation even if it is legal at that location. Legal placement and framework semantics are separate questions.

#### Production angle

In production code, precise targets make annotations self-documenting and prevent misuse. For example, an annotation intended only for REST handler methods should not be allowed on arbitrary fields.

#### Traps / caveats

- A legal annotation placement does not guarantee framework behavior.
- `TYPE` and `TYPE_USE` are different targets.
- Forgetting `PARAMETER` can break parameter-level annotations.
- Being too broad makes custom annotations easier to misuse.

#### Optional Anki

Q: What does `@Target` enforce?
A: The Java elements on which an annotation may be written.

</details>

<details>
<summary><strong>JCORE-META-004. What is reflection, and why do frameworks use it?</strong></summary>

#### Short answer

Reflection is the ability to inspect and sometimes access classes, methods, fields, constructors, annotations, and generic metadata at runtime. Frameworks use it to wire code by convention and metadata instead of requiring manual registration for every class.

#### Interview answer

Dependency injection containers inspect constructors and annotations to create beans. JSON libraries inspect fields or accessors to serialize objects. ORMs inspect entity classes and mappings. Test frameworks find test methods. Reflection lets framework code work with application classes it did not know at compile time.

Reflection can also invoke methods, create instances, and access members subject to Java access rules and module restrictions. Modern Java's module system and stronger encapsulation can limit reflective access unless packages are opened.

#### Deep dive

Reflection trades static explicitness for runtime flexibility. The compiler cannot check many reflective names and calls, so mistakes move from compile time to application startup or runtime paths.

#### Production angle

In production, reflection is acceptable when it is isolated inside frameworks or infrastructure. For your own code, prefer explicit APIs when possible. If using reflection, cache metadata, test startup paths, and be aware of native-image or modular-runtime constraints.

#### Traps / caveats

- Reflective failures often appear at runtime, not compile time.
- Access to private members can be restricted by modules or security policy.
- Reflection can be slower if metadata is repeatedly discovered.
- It can make code harder for refactoring tools and static analyzers.

#### Optional Anki

Q: Why do frameworks use reflection?
A: To inspect and operate on application classes dynamically using metadata and conventions.

</details>

<a id="jcore-meta-005"></a>

<details>
<summary><strong>JCORE-META-005. What are the downsides of reflection?</strong></summary>

#### Short answer

Reflection reduces compile-time safety, can hurt readability, has performance overhead if used carelessly, may break encapsulation, complicates refactoring, and can be restricted by the module system or native-image environments.

#### Interview answer

A reflective call often refers to members by names or metadata rather than direct type-safe references. If a method is renamed, the compiler may not catch all reflective usages. Exceptions are also wrapped in reflective exceptions such as `InvocationTargetException`, which adds noise.

Reflection can also bypass normal access boundaries when allowed. That is powerful for frameworks but dangerous in application code because it couples code to private implementation details.

#### Deep dive

Performance cost is often not about one reflective call but about repeated scanning and metadata lookup. Frameworks usually cache reflective metadata and generate accessors or bytecode where needed. Your own reflection utilities should do the same if they are on hot paths.

#### Production angle

In production, reflection may affect startup time, memory use, observability, and compatibility with GraalVM native image. It should be documented and covered by integration tests because failures often appear only with real wiring and packaging.

#### Traps / caveats

- Do not use reflection when a normal method call or interface would be clearer.
- Cache metadata instead of scanning repeatedly.
- Expect module-access issues in modern Java.
- Avoid depending on private fields of classes you do not own.

#### Optional Anki

Q: What is the main trade-off of reflection?
A: Runtime flexibility at the cost of compile-time safety and explicitness.

</details>

<details>
<summary><strong>JCORE-META-006. What are dynamic proxies used for in Java frameworks?</strong></summary>

#### Short answer

Dynamic proxies are runtime-generated objects that implement interfaces and route method calls through an invocation handler. Frameworks use them for cross-cutting behavior such as transactions, security, caching, metrics, retries, logging, and remote clients.

#### Interview answer

The JDK proxy mechanism works with interfaces: the proxy implements the same interface as the target and delegates calls to an `InvocationHandler`. The handler can run code before and after the target call, change arguments, handle exceptions, or decide not to call the target.

Frameworks can also use class-based proxies through bytecode generation libraries. Those can proxy classes, but final classes and final methods create limits because subclass-based interception depends on overriding methods.

#### Deep dive

A proxy changes the object you are calling. The caller sees an object with the same API, but the actual runtime class may be generated. This is why annotations such as `@Transactional` often work only when a call goes through the proxy.

#### Production angle

In production, understand where proxies are inserted. Self-invocation, direct construction with `new`, final methods, package visibility, and equality checks can all bypass or confuse proxy-based behavior.

#### Traps / caveats

- JDK dynamic proxies require interfaces.
- Subclass-based proxies cannot override final methods.
- A method call must go through the proxy for advice/interception to run.
- Proxy classes can make stack traces and debugging less direct.

#### Optional Anki

Q: What does a JDK dynamic proxy do?
A: It implements interfaces at runtime and dispatches calls to an `InvocationHandler`.

</details>

<details>
<summary><strong>JCORE-META-007. How can proxies affect method calls, equality checks and stack traces?</strong></summary>

#### Short answer

A proxy is not the original class. It can intercept only calls that pass through it, can change the runtime class seen by `getClass()`, may affect `equals()`/`hashCode()`, and often adds generated frames to stack traces.

#### Interview answer

The method-call issue is common with Spring-style AOP: an external call to a proxied bean goes through the proxy, but a method inside the target calling another method on `this` may bypass the proxy. Then transactional, caching, or security advice may not run.

Equality can also be tricky. If `equals()` uses strict `getClass()`, a proxy subclass may not compare equal to the target type. If equality uses identity, two wrappers around the same target can still be different objects.

#### Deep dive

Stack traces include proxy and interceptor frames, so the first application method may not be at the top. Debugging requires recognizing generated class names and framework invocation layers.

#### Production angle

In production, avoid designs where correctness depends on an internal self-invocation being intercepted. Keep equality implementations proxy-aware when entities or services may be proxied, and use framework utilities if the framework provides them.

#### Traps / caveats

- Self-invocation can bypass proxy advice.
- Strict `getClass()`-based equality may fail with subclass proxies.
- Generated proxy frames can obscure the real call path.
- Directly injecting or constructing the target instead of the proxy bypasses framework behavior.

#### Optional Anki

Q: Why might `@Transactional` not run on an internal method call?
A: The call may use `this` and bypass the proxy.

</details>

<details>
<summary><strong>JCORE-META-008. What are the risks of Java native serialization?</strong></summary>

#### Short answer

Java native serialization is risky because deserializing untrusted data can execute dangerous object graphs, expose gadget-chain attacks, bypass constructors, and create fragile version coupling. It is usually avoided for public or untrusted data formats.

#### Interview answer

`Serializable` was designed for Java object graphs, not for stable public protocols. Deserialization can instantiate objects without normal constructors and invoke special hooks such as `readObject`. Attackers can exploit classes on the classpath whose deserialization has side effects.

It also creates compatibility problems. Renaming fields, changing class hierarchy, or changing `serialVersionUID` can break old serialized data. The binary format is Java-specific and not friendly to cross-language systems.

#### Deep dive

The most serious risk is security. Treat Java deserialization like executing code from the input unless strong filters and strict type allow-lists are in place. Even then, prefer safer data formats for external boundaries.

#### Production angle

For production APIs and messaging, prefer JSON, Avro, Protobuf, or another explicit schema/format. If native serialization is unavoidable for legacy systems, use serialization filters, minimize the classpath exposure, version deliberately, and never deserialize untrusted payloads blindly.

#### Traps / caveats

- Never deserialize untrusted data with unrestricted native serialization.
- Constructors are not the normal initialization path during deserialization.
- Versioning object graphs is fragile.
- Serialization hooks can hide surprising behavior.

#### Optional Anki

Q: What is the biggest risk of Java native serialization?
A: Unsafe deserialization of untrusted data, including gadget-chain attacks.

</details>

<details>
<summary><strong>🧠 JCORE-META-009. What is the difference between runtime reflection and annotation processing?</strong></summary>

#### Short answer

Runtime reflection inspects metadata while the application is running. Annotation processing runs during compilation and can validate annotations, generate source files, or report compile-time errors before the application starts.

#### Interview answer

Runtime reflection is flexible because it sees the actual classes loaded in the application, but failures appear at startup or runtime. Annotation processing moves work earlier: tools such as mappers, builders, and dependency metadata generators can produce code that is then compiled normally.

Annotation processors generally operate on source-level or compiler model elements, not live objects. They do not execute application logic in the same way a runtime framework does.

#### Deep dive

The trade-off is startup/runtime flexibility versus compile-time safety and generated code. Annotation processing can reduce reflection and improve native-image compatibility, but it adds build complexity and generated sources to understand.

#### Production angle

In production systems, annotation processing is attractive for stable mappings and repetitive boilerplate. Runtime reflection is useful for plugins, dynamic frameworks, and cases where classes are not fully known at compile time. Many frameworks combine both approaches.

#### Traps / caveats

- Annotation processing cannot inspect runtime-only state.
- Reflection errors are often later than compile-time processor errors.
- Generated code must be included in IDE and build workflows.
- Changing retention alone does not make an annotation processor see or not see an annotation; processors work in the compiler environment.

#### Optional Anki

Q: Runtime reflection or annotation processing: which runs earlier?
A: Annotation processing; it runs during compilation.

</details>

<details>
<summary><strong>🧠 JCORE-META-010. How can final classes and final methods limit proxy-based frameworks?</strong></summary>

#### Short answer

Subclass-based proxies work by generating a subclass and overriding methods to intercept calls. A final class cannot be subclassed, and a final method cannot be overridden, so that style of proxy cannot intercept them.

#### Interview answer

JDK dynamic proxies avoid this by proxying interfaces, but they require callers to use the interface type. Class-based proxies, common in AOP frameworks, are limited by Java inheritance rules. Private methods, static methods, constructors, and some package-private cases can also be problematic for interception.

This matters for annotations such as transactions, caching, retries, and security. The annotation may be present, but if the framework cannot build a suitable proxy or cannot intercept the method, the behavior may not apply.

#### Deep dive

Languages or tools that make classes final by default can make proxy-based frameworks more surprising. The team must decide whether to use interfaces, open classes, build-time weaving, or framework-specific plugins.

#### Production angle

In production services, verify framework proxy rules in tests. Do not assume an annotation works just because it compiles. Integration tests should cover the actual bean wiring and call path.

#### Traps / caveats

- Final classes block subclass-based proxies.
- Final methods cannot be intercepted by overriding.
- JDK proxies need interfaces and interface-typed usage.
- Self-invocation can still bypass interception even when the class is not final.

#### Optional Anki

Q: Why can `final` break AOP interception?
A: Subclass proxies need to override methods, and `final` forbids that.

</details>

<details>
<summary><strong>JCORE-META-011. What does `Serializable` mean in Java?</strong></summary>

#### Short answer

`Serializable` is a marker interface indicating that objects of a class may be serialized by Java's native serialization mechanism. It does not define methods; the serialization runtime interprets the class structure and special serialization hooks.

#### Interview answer

By default, native serialization includes non-static, non-transient fields that are serializable. Static fields belong to the class, not the object state. Transient fields are skipped. If a referenced object is not serializable, serialization can fail with `NotSerializableException`.

Classes can customize serialization through special methods such as `writeObject`, `readObject`, `writeReplace`, and `readResolve`. That power is also part of why native serialization is hard to reason about and risky for untrusted data.

#### Deep dive

Implementing `Serializable` is not a guarantee of a good external format. It says something about Java's object serialization mechanism, not about JSON, database persistence, or general API compatibility.

#### Production angle

In modern backend systems, implement `Serializable` only when a framework or legacy protocol truly requires it. For service communication and storage, prefer explicit formats and schemas.

#### Traps / caveats

- `Serializable` has no methods; it is a marker.
- All non-transient object fields must be serializable unless custom logic handles them.
- It is unrelated to JSON serialization unless a library chooses to consider it.
- Do not deserialize untrusted native-serialized data.

#### Optional Anki

Q: What kind of interface is `Serializable`?
A: A marker interface for Java native serialization.

</details>

<details>
<summary><strong>JCORE-META-012. What is `serialVersionUID`, and why can it matter?</strong></summary>

#### Short answer

`serialVersionUID` is a version identifier for a serializable class. During deserialization, Java checks that the stream's class version matches the local class version; a mismatch can cause `InvalidClassException`.

#### Interview answer

If a class does not declare `serialVersionUID`, the JVM computes one from class details. That computed value can change after seemingly harmless modifications, compiler differences, or refactoring. Declaring it explicitly makes the compatibility decision intentional.

Keeping the same value means “I believe old serialized data is compatible with this class.” Changing it means “old serialized data should not be accepted.” The value does not magically make incompatible class changes safe; it only controls the version check.

#### Deep dive

Serialization compatibility depends on field changes, class hierarchy, custom serialization methods, and invariants. `serialVersionUID` is one part of the protocol, not a migration system.

#### Production angle

In production, explicitly declare `serialVersionUID` for classes that are truly serialized across versions. Add compatibility tests if old serialized payloads must remain readable. For ordinary DTOs not using native serialization, do not treat this field as a general versioning solution.

#### Traps / caveats

- The computed default can change unexpectedly.
- Same `serialVersionUID` does not guarantee semantic compatibility.
- Changing it rejects old streams rather than migrating them.
- It matters only for Java native serialization.

#### Optional Anki

Q: Why declare `serialVersionUID` explicitly?
A: To make native-serialization compatibility decisions stable and intentional.

</details>

<details>
<summary><strong>JCORE-META-013. What does `transient` mean for fields?</strong></summary>

#### Short answer

For Java native serialization, `transient` means a field is skipped by the default serialization mechanism. After deserialization, that field receives its default value unless custom deserialization logic restores it.

#### Interview answer

Use `transient` for derived, cached, sensitive, non-serializable, or environment-specific state that should not be part of the serialized object form. Examples include cached calculations, open sockets, thread pools, loggers in some designs, or secrets that must not be written.

The keyword affects Java native serialization. Other frameworks such as JSON serializers, ORMs, and mappers may or may not honor it; many have their own annotations like `@JsonIgnore` or `@Transient`.

#### Deep dive

After deserialization, transient fields may violate object invariants if code assumes they are initialized. Use `readObject`, lazy initialization, validation, or a safer serialization format to restore required derived state.

#### Production angle

In production, be careful with secrets and credentials: `transient` only affects one serialization mechanism and is not a general data-leak prevention strategy. Check the actual serializers and loggers used by the service.

#### Traps / caveats

- `transient` does not affect static fields; static fields are not object state.
- A transient field is defaulted after deserialization unless restored.
- JSON and ORM frameworks may require separate annotations.
- Do not rely on `transient` alone to protect secrets.

#### Optional Anki

Q: What does `transient` do?
A: It excludes a field from Java's default native serialization.

</details>
