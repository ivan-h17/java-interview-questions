# 01.02. Language, primitives and numeric types

---

<a id="jcore-type-001"></a>

<details>
<summary><strong>JCORE-TYPE-001. What is the difference between primitive types and reference types in Java?</strong></summary>

#### Short answer

Primitive variables hold simple values of one of Java’s eight primitive types: `boolean`, `byte`, `short`, `char`, `int`, `long`, `float` and `double`. Reference variables hold references to objects or arrays. Primitives cannot be `null` and do not have object identity; references can be `null` and point to objects with identity, fields and methods.

#### Interview answer

In an interview I would say that primitives are value types built into the language, while reference types represent objects. With primitives, assignment copies the primitive value. With references, assignment copies the reference value, so two variables may refer to the same object.

This distinction affects nullability, equality, memory layout, generics and performance. For example, `int` can be compared directly with `==`, but `Integer` is an object and `==` compares references unless unboxing happens. Collections and generics work with reference types, so primitives are usually boxed into wrappers such as `Integer` or `Long`.

#### Deep dive

Primitive fields and array elements have default values such as `0`, `false` or `\u0000`. Reference fields and array elements default to `null`. Local variables, both primitive and reference, must be definitely assigned before use.

Reference types include classes, interfaces, arrays, enums, records and annotations. Arrays are objects even when their elements are primitive, for example `int[]` is a reference type whose elements are primitive `int` values.

The JVM representation is implementation-dependent, but the language-level rule is stable: primitive variables contain primitive values, reference variables contain references, and all method arguments are passed by value.

#### Production angle

In backend code the choice often appears in DTOs, entities and hot loops. Primitive fields avoid `null` and boxing overhead but cannot represent “missing value”. Wrapper fields can model absence, but they require explicit null handling and may cause accidental unboxing `NullPointerException`.

#### Traps / caveats

- `int` and `Integer` are not the same type: one is primitive, the other is an object.
- A reference variable is not the object itself; reassigning it does not change another variable that points to the old object.
- Primitive arrays such as `int[]` are objects, but their elements are not boxed.

#### Optional Anki

Q: What is the key difference between primitive and reference variables?
A: Primitive variables hold primitive values; reference variables hold references to objects or arrays.

</details>

<details>
<summary><strong>JCORE-TYPE-002. What are wrapper classes, and when does Java use them automatically?</strong></summary>

#### Short answer

Wrapper classes are object representations of primitive types: `Integer` for `int`, `Long` for `long`, and so on. Java automatically boxes a primitive into a wrapper and unboxes a wrapper into a primitive in many contexts, especially assignments, method calls, arithmetic and generics-related code.

#### Interview answer

Wrappers exist because Java has both primitives and objects. The wrapper classes add object behavior around primitive values: they can be stored in collections, used as generic type arguments, compared with methods, parsed from strings and represented as nullable fields.

Autoboxing is compiler-supported syntactic sugar. For example, `Integer x = 10;` is roughly `Integer x = Integer.valueOf(10);`, and `int y = x;` is roughly `int y = x.intValue();`. This is convenient, but it can hide allocation, identity comparison issues and `NullPointerException` during unboxing.

#### Deep dive

The wrapper types are `Boolean`, `Byte`, `Short`, `Character`, `Integer`, `Long`, `Float` and `Double`. They are immutable value-based classes in everyday usage; code should not rely on their object identity.

Automatic conversion happens in assignment contexts, invocation contexts and numeric expressions. It does not mean primitives become objects everywhere. For example, `List<int>` is invalid because generic type arguments must be reference types, so the code must use `List<Integer>`.

#### Production angle

Wrappers are common in JSON DTOs, database mappings and optional fields. Be deliberate: use wrappers where absence is meaningful, primitives where a value is mandatory and a default like zero is safe. In performance-sensitive code, avoid accidental boxing in streams, maps and tight loops.

#### Traps / caveats

- Unboxing a `null` wrapper throws `NullPointerException`.
- `Integer` identity must not be used for business equality; use `equals()` or compare primitives.
- Generic collections require wrappers, which can add memory and CPU overhead.

#### Optional Anki

Q: Why do wrapper classes exist?
A: They let primitive values participate in object APIs such as collections, generics, nullable fields and utility methods.

</details>

<details>
<summary><strong>JCORE-TYPE-003. What is autoboxing, and what pitfalls does it create?</strong></summary>

#### Short answer

Autoboxing is the compiler’s automatic conversion from a primitive to its wrapper type; unboxing is the reverse conversion. Pitfalls include hidden allocations, surprising `==` behavior, `NullPointerException` when unboxing `null`, overload-resolution surprises and slower hot code.

#### Interview answer

Autoboxing makes code more readable because you can write `List<Integer> ids = List.of(1, 2, 3);` instead of manually calling `Integer.valueOf`. The compiler inserts boxing and unboxing conversions where the language allows them.

The problem is that it looks free but is not always free. A wrapper can be `null`, has object identity, may allocate or use a cache, and requires unboxing for arithmetic. For example, `Integer x = null; int y = x;` compiles but fails at runtime.

#### Deep dive

Boxing normally uses `valueOf`, not `new`. Some wrapper values are cached, for example small integers, but relying on the cache is a bug. Unboxing calls methods such as `intValue()`, so it fails if the wrapper reference is `null`.

In overload resolution, Java prefers widening over boxing, and fixed arity over varargs. This can produce unexpected method choices when overloads mix primitives, wrappers and varargs. In arithmetic, boxed values are unboxed and then numeric promotion rules apply.

#### Production angle

Autoboxing issues often show up in metrics aggregation, stream pipelines, ORM mappings and cache keys. A loop that repeatedly updates boxed counters can create many temporary objects. Prefer primitive-specialized APIs where available, such as `IntStream`, `LongStream` or primitive arrays for hot paths.

#### Traps / caveats

- `Boolean flag = null; if (flag) ...` throws during unboxing.
- `Long sum = 0L; sum += value;` creates a new `Long` each update because wrappers are immutable.
- A method overload may be selected by widening instead of boxing, which can surprise readers.

#### Optional Anki

Q: What is the most dangerous autoboxing pitfall?
A: Accidental unboxing of `null`, which throws `NullPointerException`.

</details>

<details>
<summary><strong>JCORE-TYPE-004. Why can comparing boxed numbers with == produce surprising results?</strong></summary>

#### Short answer

For boxed numbers, `==` usually compares object references, not numeric values. Some boxed values are cached, so `Integer.valueOf(127) == Integer.valueOf(127)` is guaranteed to be true, while the same comparison for larger values is not portable and may be false. Use `equals()`, `compareTo()` or unbox deliberately.

#### Interview answer

The surprising part is that boxed values look like numbers but are objects. If both operands are reference types, `==` checks whether they are the same object. For cached values this can be true, which makes `==` look reliable in small examples. For values outside the cache, two wrappers with the same numeric value may be different objects.

If one side is primitive and the other is boxed, Java unboxes the wrapper and performs primitive numeric comparison. That can also surprise people because it may throw `NullPointerException` if the wrapper is `null`.

#### Deep dive

The language guarantees caching for some wrapper values, such as `Boolean` values and at least the integer range `-128..127` for integral wrappers where applicable. Implementations may cache more, but portable code must not depend on that.

`equals()` compares wrapper values only when the wrapper classes are the same. For ordering or cross-type numeric logic, be explicit: convert to the intended primitive type, use `compare` methods, or use a domain type such as `BigDecimal` with clear scale rules.

#### Production angle

This bug is common in tests and business checks around IDs, status codes and counters. It may pass for small fixture values and fail later with production-sized IDs. Code review rule: never use `==` for boxed numeric equality unless you are deliberately checking identity, which is almost never the business requirement.

#### Traps / caveats

- `Integer a = 1000; Integer b = 1000; a == b` can be false.
- `Integer a = null; a == 0` throws because `a` is unboxed.
- `new Integer(...)` style object creation, where available in legacy code, makes identity comparisons even less predictable.

#### Optional Anki

Q: How should boxed numeric values be compared for equality?
A: Usually with `equals()` after null handling, or by deliberate primitive comparison after safe unboxing.

</details>

<details>
<summary><strong>JCORE-TYPE-005. How do numeric promotion and implicit widening conversions work?</strong></summary>

#### Short answer

Java allows safe implicit widening conversions, such as `int` to `long` or `float` to `double`. In numeric expressions, smaller integral types like `byte`, `short` and `char` are usually promoted to `int`, and binary numeric promotion chooses a common type such as `long`, `float` or `double`.

#### Interview answer

Numeric promotion is the set of rules Java uses to evaluate numeric expressions. A classic example is `byte a = 1; byte b = 2; byte c = a + b;`, which does not compile because `a + b` is promoted to `int`. You need an explicit cast or an `int` result variable.

For binary operations, Java promotes operands to a common type. If either is `double`, the result is `double`; else if either is `float`, result is `float`; else if either is `long`, result is `long`; otherwise it is `int`. Widening is implicit, narrowing usually requires a cast.

#### Deep dive

Widening does not always mean “no information loss” in the human sense. For example, converting a large `int` to `float` is allowed implicitly, but `float` may not represent every `int` exactly. It is considered a widening primitive conversion because the target type has a wider range, not because every value keeps all precision.

Constant expressions have special assignment rules: `byte b = 10;` is valid when the constant fits, but `byte b = someInt;` is not. Compound assignment also hides a cast: `b += 1` is roughly `b = (byte)(b + 1)`.

#### Production angle

Promotion bugs appear in boundaries: serialization formats, database column types, metrics counters and monetary calculations. Be explicit about the expected result type, especially for division: `int / int` performs integer division even if you assign the result to `double`.

#### Traps / caveats

- `char + char`, `byte + byte` and `short + short` produce `int`.
- `long + float` produces `float`, which can lose integer precision.
- `1 / 2` is `0`, while `1.0 / 2` is `0.5`.

#### Optional Anki

Q: What is the result type of `byte + byte` in Java?
A: `int`, because small integral types are promoted before arithmetic.

</details>

<details>
<summary><strong>JCORE-TYPE-006. What can go wrong with integer overflow in Java?</strong></summary>

#### Short answer

For `int` and `long`, Java integer arithmetic silently wraps around on overflow. It usually does not throw an exception. This can produce negative sizes, wrong balances, broken pagination, incorrect timestamps or security bugs unless the code validates ranges or uses checked arithmetic.

#### Interview answer

Integer overflow means the mathematical result does not fit into the type. For example, `Integer.MAX_VALUE + 1` becomes `Integer.MIN_VALUE`. Java defines this wraparound behavior for integral arithmetic, so the program keeps running with a wrong value.

The fix depends on the domain. Use `long` instead of `int` when the range is genuinely larger, use `Math.addExact`, `subtractExact`, `multiplyExact` or `toIntExact` when overflow should fail fast, and use `BigInteger` for unbounded integer arithmetic.

#### Deep dive

Overflow is especially easy to miss in multiplication before widening: `long bytes = count * 1024 * 1024;` can overflow as `int` before assignment if `count` is an `int`. Use `1024L` or convert earlier.

Array sizes, collection capacities and indexes are `int`-based in many APIs, so converting from `long` to `int` must be checked. Also remember that `Math.abs(Integer.MIN_VALUE)` is still negative because its positive counterpart does not fit in `int`.

#### Production angle

Overflow can become an incident when calculating money in minor units, rate-limit counters, pagination offsets or buffer sizes. Add boundary tests around max values, use exact arithmetic for critical calculations, and validate external numeric input before multiplication or casting.

#### Traps / caveats

- Widening after an overflowing `int` expression does not recover the correct value.
- `Math.abs(Integer.MIN_VALUE)` returns `Integer.MIN_VALUE`.
- Overflow in capacity calculations can turn a large positive request into a small or negative number.

#### Optional Anki

Q: Does `int` overflow throw an exception in Java?
A: No. Normal `int`/`long` arithmetic wraps around silently; use checked methods when needed.

</details>

<details>
<summary><strong>JCORE-TYPE-007. Why are float and double unsafe for money calculations?</strong></summary>

#### Short answer

`float` and `double` are binary floating-point types. Many decimal values, such as `0.1`, cannot be represented exactly, so arithmetic accumulates rounding errors. Money usually requires exact decimal rules, fixed scale and explicit rounding, so binary floating point is the wrong default.

#### Interview answer

The classic issue is `0.1 + 0.2` not being exactly `0.3`. That is not a Java bug; it is a property of binary floating-point representation. These types are excellent for scientific or approximate calculations, but money is usually a legal/accounting domain where one cent matters.

For money, prefer `BigDecimal` with clear scale and rounding rules, or store minor units as `long`, for example cents, when the domain allows it. The important part is to make rounding explicit at boundaries such as tax, discount, currency conversion and database persistence.

#### Deep dive

Floating-point arithmetic has finite precision and uses binary fractions. It is also not associative in general: `(a + b) + c` can differ from `a + (b + c)`. Comparisons often need tolerances in approximate domains, but tolerances are usually not a good model for invoices and balances.

`float` has much less precision than `double`, but both have the same conceptual issue for decimal money. Formatting a `double` to two digits only hides the internal approximation; it does not make intermediate business calculations exact.

#### Production angle

Avoid exposing money as JSON floating numbers if clients and services can round differently. Prefer strings, integer minor units or a structured amount/currency representation. Align Java types with database decimal columns and document rounding mode in business rules.

#### Traps / caveats

- Rounding only at display time may be too late if intermediate calculations affected decisions.
- `double` keys in maps or equality checks can be unstable for business logic.
- `float` is not a “smaller money type”; it is usually worse because it has less precision.

#### Optional Anki

Q: Why should `double` not be the default for money?
A: It represents binary fractions, so many decimal amounts are inexact and rounding errors can affect business results.

</details>

<details>
<summary><strong>JCORE-TYPE-008. Why is BigDecimal commonly used for money?</strong></summary>

#### Short answer

`BigDecimal` represents decimal numbers with arbitrary precision and an explicit scale, so it can model values like `0.10` exactly. It also forces explicit rounding for operations that cannot produce a finite decimal result, which is important for financial rules.

#### Interview answer

Money is usually decimal, not binary. `BigDecimal` is popular because it stores an unscaled integer value plus a scale. That allows exact decimal representation and predictable rounding policies such as `HALF_UP` or `HALF_EVEN`.

However, `BigDecimal` is not magic. You still need domain rules: currency, scale, rounding mode, where rounding happens, and whether values are allowed to have more precision than the currency minor unit. In many systems, a dedicated `Money` value object around `BigDecimal` is better than passing raw numbers everywhere.

#### Deep dive

Important operations such as division may throw `ArithmeticException` if the exact result has a non-terminating decimal expansion and no rounding mode is provided. This is a feature: it prevents silent financial rounding.

`BigDecimal` is immutable. Methods like `setScale`, `add` and `multiply` return new values. The caller must use the returned value. Performance is lower than primitive arithmetic, but correctness usually matters more for money.

#### Production angle

Use a consistent construction policy, usually strings, integer minor units or `BigDecimal.valueOf`. Normalize scale at service boundaries if the domain requires it. Keep database column precision and scale aligned with application validation to avoid late persistence failures or unexpected truncation.

#### Traps / caveats

- `BigDecimal` must be constructed carefully; `new BigDecimal(0.1)` imports binary floating-point noise.
- `BigDecimal.equals()` is scale-sensitive, so `1.0` and `1.00` are not equal by `equals()`.
- Forgetting that `BigDecimal` is immutable leads to ignored calculation results.

#### Optional Anki

Q: What two pieces mainly define a `BigDecimal` value?
A: An unscaled integer value and a scale.

</details>

<details>
<summary><strong>JCORE-TYPE-009. Why is new BigDecimal("0.1") usually safer than new BigDecimal(0.1)?</strong></summary>

#### Short answer

`new BigDecimal("0.1")` creates the exact decimal value `0.1`. `new BigDecimal(0.1)` first takes the already-inexact binary `double` value for `0.1` and then converts that exact binary approximation into a decimal, producing a long unexpected value.

#### Interview answer

The constructor from `double` is dangerous because the damage has already happened before `BigDecimal` sees the value. The literal `0.1` is represented as the nearest binary floating-point value, not as an exact decimal tenth.

Using a string preserves the decimal the developer wrote. Another acceptable option in many cases is `BigDecimal.valueOf(0.1)`, which uses the canonical string representation of the double, but for financial input I still prefer strings or integer minor units from the boundary.

#### Deep dive

This issue is about construction, not about `BigDecimal` arithmetic itself. Once a correct decimal value is constructed, operations can be exact subject to precision, scale and rounding rules. If an external API sends JSON numbers, the parser may already parse them as floating point unless configured otherwise.

`new BigDecimal("0.10")` also preserves scale `2`, which can matter for formatting and for `equals()`. `new BigDecimal("0.1")` and `new BigDecimal("0.10")` compare numerically equal with `compareTo`, but not necessarily with `equals`.

#### Production angle

Define how amounts enter the system: string decimal, integer minor units or database decimal mapping. Avoid accepting frontend floating-point artifacts silently. Add tests for exact string representation and rounding behavior around external API boundaries.

#### Traps / caveats

- `new BigDecimal(0.1).toString()` is not `"0.1"`.
- `BigDecimal.valueOf(double)` is safer than the double constructor, but it still starts from a double value.
- A JSON number may lose precision before your domain object is constructed.

#### Optional Anki

Q: Why prefer `new BigDecimal("0.1")` over `new BigDecimal(0.1)`?
A: The string constructor receives exact decimal text; the double constructor receives an inexact binary approximation.

</details>

<details>
<summary><strong>JCORE-TYPE-010. What is the difference between BigDecimal.equals() and BigDecimal.compareTo()?</strong></summary>

#### Short answer

`BigDecimal.equals()` compares both numeric value and scale, so `1.0` and `1.00` are not equal. `BigDecimal.compareTo()` compares numeric value, so those two values compare as equal. This difference matters in collections and business equality.

#### Interview answer

This is one of the most common `BigDecimal` interview traps. `equals()` is strict: value and scale must match. `compareTo()` is numeric: it ignores scale differences that do not change the mathematical value.

For business checks like “is amount zero?” prefer `amount.compareTo(BigDecimal.ZERO) == 0`. For hash-based collections, remember that `HashSet` and `HashMap` use `equals` and `hashCode`, so `1.0` and `1.00` are different keys.

#### Deep dive

This also creates an inconsistency between natural ordering and equality: sorted collections such as `TreeSet` use comparison, while hash collections use equality. A `TreeSet` may treat `1.0` and `1.00` as the same element, while a `HashSet` treats them as different.

The right solution is domain-specific. You can normalize scale at object construction, use a dedicated money type, or consistently use `compareTo` for numeric checks. Do not sprinkle random `stripTrailingZeros()` calls without understanding scale and formatting requirements.

#### Production angle

This bites when amounts are used as cache keys, map keys, deduplication keys or test assertions. Decide whether scale is meaningful in your domain. If not, normalize values before storage and comparison, or wrap `BigDecimal` in a value object with explicit equality semantics.

#### Traps / caveats

- `new BigDecimal("1.0").equals(new BigDecimal("1.00"))` is false.
- `compareTo` returning `0` does not imply `equals` is true for `BigDecimal`.
- Hash-based and sorted collections can behave differently for scale variants.

#### Optional Anki

Q: How to check whether a `BigDecimal` amount is numerically zero?
A: Use `amount.compareTo(BigDecimal.ZERO) == 0`, after null handling.

</details>

<details>
<summary><strong>🧠 JCORE-TYPE-011. How do NaN, infinity and signed zero affect floating-point comparisons?</strong></summary>

#### Short answer

Floating point has special values. `NaN` is unordered: primitive comparisons like `nan == nan` are false. Infinities compare as very large positive or negative values. `0.0 == -0.0` is true for primitive comparison, but some library methods distinguish signed zero.

#### Interview answer

With `double` and `float`, not every result is a normal finite number. Division by zero in floating-point arithmetic can produce `Infinity`, `-Infinity` or `NaN` rather than throwing an arithmetic exception. `NaN` means “not a number” and is not equal to anything, including itself, under primitive `==`.

Signed zero is another edge case: `0.0 == -0.0` is true, but `1.0 / 0.0` gives positive infinity and `1.0 / -0.0` gives negative infinity. Wrapper methods such as `Double.compare` and `Double.equals` have their own defined ordering/equality behavior for these values.

#### Deep dive

Use `Double.isNaN`, `Float.isNaN`, `Double.isInfinite` and `Double.isFinite`-style checks where appropriate. Do not test NaN with `==`. Sorting and collection behavior should be based on `Double.compare` or a domain comparator, not hand-written comparison logic that forgets special values.

For boxed values, `Double.equals` treats NaN values as equal after canonicalization but distinguishes `0.0` and `-0.0`. That differs from primitive `==`, so using floating wrappers as map keys should be done carefully.

#### Production angle

Special floating values can leak into APIs, JSON, databases or metrics and break consumers that expect finite numbers. Validate external numeric input and calculation outputs before persisting or serializing. In telemetry, explicitly decide how to handle NaN and infinity.

#### Traps / caveats

- `x == Double.NaN` is never the right NaN check.
- `0.0 == -0.0` is true, but division can reveal the sign.
- Some JSON/database layers reject or stringify NaN and infinity inconsistently.

#### Optional Anki

Q: How do you check whether a `double` is NaN?
A: Use `Double.isNaN(value)`, not `value == Double.NaN`.

</details>

<details>
<summary><strong>🧠 JCORE-TYPE-012. How do Java char, Unicode code points and surrogate pairs differ?</strong></summary>

#### Short answer

Java `char` is a 16-bit UTF-16 code unit, not necessarily a full user-visible character. A Unicode code point is a numeric value in the Unicode code space; Unicode scalar values are code points except surrogate code points. Code points outside the Basic Multilingual Plane are represented in UTF-16 by a surrogate pair: two `char` values.

#### Interview answer

The trap is thinking that one `char` equals one character. That is only true for some characters. Java strings are UTF-16 sequences, so `String.length()` returns the number of `char` code units, not the number of Unicode code points and not the number of user-perceived characters.

For example, many emoji require two `char` values. To process real Unicode code points, use APIs such as `String.codePoints()`, `codePointAt` and `offsetByCodePoints`. For user-visible grapheme clusters, even code points may not be enough because one visible character can be composed from multiple code points.

#### Deep dive

A high surrogate followed by a low surrogate forms one supplementary code point. A lone surrogate is possible in a Java `String` even though it is not a valid Unicode scalar value by itself. That is why naive substring, reverse, truncation or validation logic can split a surrogate pair.

`String.chars()` returns an `IntStream` of UTF-16 code units, while `String.codePoints()` returns Unicode code points. This distinction is important for validation, normalization, escaping and length limits.

#### Production angle

Unicode bugs show up in login names, search indexing, SMS limits, database length constraints and API validation. Define whether limits are in bytes, UTF-16 units, code points or grapheme clusters. Avoid truncating strings blindly before persistence or display.

#### Traps / caveats

- `String.length()` is not “number of characters” in the user-interface sense.
- `char` cannot represent every Unicode code point alone.
- Naive substring can split an emoji or another supplementary character.

#### Optional Anki

Q: What does Java `char` represent?
A: A 16-bit UTF-16 code unit, not necessarily a complete Unicode character.

</details>

<a id="jcore-type-013"></a>

<details>
<summary><strong>JCORE-TYPE-013. Is Java pass-by-value or pass-by-reference?</strong></summary>

#### Short answer

Java is always pass-by-value. For primitives, the copied value is the primitive value. For objects, the copied value is the reference. A method can mutate the object through that copied reference, but it cannot reassign the caller’s variable.

#### Interview answer

The confusion comes from object references. When you pass an object to a method, Java copies the reference value into the parameter. Both caller and callee may now refer to the same object, so mutations are visible. But the parameter itself is a local variable. If the method assigns it to a new object, the caller’s variable still points to the old object.

A good phrase is: Java passes object references by value, not objects by reference. There is no Java equivalent of C++ reference parameters where assigning the parameter changes the caller’s variable.

#### Deep dive

For `void change(StringBuilder sb)`, calling `sb.append("x")` mutates the shared object. Calling `sb = new StringBuilder()` only changes the local copy of the reference. The same principle applies to arrays, collections and custom objects.

This rule also explains why Java cannot implement a swap method like `swap(a, b)` that swaps two caller variables by assigning parameters. You can modify contents of mutable holder objects, but not the caller variables themselves.

#### Production angle

This matters for API design. Mutating arguments can create hidden side effects and thread-safety bugs. Prefer immutable objects, return new values, or document mutation clearly. When accepting mutable collections or arrays, consider defensive copies if ownership should not be shared.

#### Traps / caveats

- “Objects are passed by reference” is imprecise and misleading for Java.
- Reassigning a parameter does not affect the caller’s variable.
- Mutating a shared object through a copied reference is still visible to other holders of that reference.

#### Optional Anki

Q: Can a Java method reassign a caller’s object variable by assigning its parameter?
A: No. The parameter is a copy of the reference value.

</details>

<a id="jcore-type-014"></a>

<details>
<summary><strong>JCORE-TYPE-014. What happens when a method modifies an object passed as an argument?</strong></summary>

#### Short answer

If a method mutates the object that a copied reference points to, the caller can observe that mutation because both references point to the same object. If the method only reassigns its parameter to another object, the caller does not see that reassignment.

#### Interview answer

Passing an object argument gives the method access to the same object, not a copy of the object. Therefore `list.add(x)` inside the method changes the list that the caller passed. But `list = new ArrayList<>()` changes only the method’s local parameter.

Whether this is good or bad depends on the API contract. Some methods intentionally fill a collection or update an aggregate. Others should avoid side effects and return a new object. The key is that the caller should not be surprised.

#### Deep dive

Object mutability is the real issue. Immutable objects such as `String`, many date/time classes and records with immutable components cannot have their internal state changed through a method call. Mutable objects such as arrays, `ArrayList` or `StringBuilder` can.

The `final` keyword on a parameter only prevents reassignment of that local parameter. It does not make the object immutable. `final List<String> list` can still be mutated with `list.add(...)`.

#### Production angle

Hidden mutations are a common source of flaky tests and concurrency bugs. Be careful with entity objects managed by an ORM, cached DTOs, request-scoped collections and shared configuration objects. Defensive copying and immutable value objects often make service boundaries safer.

#### Traps / caveats

- `final` on a reference does not freeze the referenced object.
- A method name like `validate` should not unexpectedly mutate the object.
- Returning an internal mutable collection exposes the object to external mutation.

#### Optional Anki

Q: What is visible to the caller: parameter reassignment or object mutation?
A: Object mutation is visible if the same object is shared; parameter reassignment is not.

</details>

<a id="jcore-type-015"></a>

<details>
<summary><strong>JCORE-TYPE-015. What are arrays in Java, and how do they differ from collections?</strong></summary>

#### Short answer

Arrays are fixed-size objects with a reified runtime component type and indexed access. Collections are object-based data structures with richer APIs, usually dynamic size and generic compile-time types. Arrays can hold primitives directly; generic collections cannot hold primitive type arguments.

#### Interview answer

An array is a language-level container: `int[]`, `String[]`, etc. Its length is fixed after creation, and you access elements by index. Arrays know their component type at runtime, so storing the wrong type can be detected at runtime.

Collections are framework types such as `List`, `Set` and `Map`. They are more flexible: resizing, searching, iteration, algorithms and implementations with different performance characteristics. Generics give compile-time type safety, but because of type erasure a `List<String>` does not carry `String` as a runtime component type in the same way an array does.

#### Deep dive

Arrays are covariant: a `String[]` can be assigned to `Object[]`. Generic collections are invariant: `List<String>` is not a subtype of `List<Object>`. This makes collections safer at compile time, while arrays require runtime store checks.

Arrays use `length` field, collections use methods like `size()`. Arrays work well for fixed-size, low-level or performance-sensitive data. Collections are usually better for business code because they express intent and provide rich operations.

#### Production angle

Use arrays for binary data, interop, fixed-size tables and hot paths where primitive storage matters. Use collections for domain models, service APIs and most application logic. Avoid exposing mutable arrays from APIs unless the caller is allowed to modify them.

#### Traps / caveats

- Arrays have fixed length; `Arrays.asList(array)` returns a fixed-size list view for object arrays.
- `List<int>` is invalid; use `List<Integer>` or primitive-specialized structures.
- Array covariance can produce `ArrayStoreException`.

#### Optional Anki

Q: Name two key differences between arrays and collections.
A: Arrays are fixed-size and reified at runtime; collections are usually dynamically sized and use erased generic types.

</details>

<a id="jcore-type-016"></a>

<details>
<summary><strong>JCORE-TYPE-016. Why are Java arrays covariant?</strong></summary>

#### Short answer

Java arrays are covariant: if `String` is a subtype of `Object`, then `String[]` is considered a subtype of `Object[]`. This is convenient and historically part of Java’s type system, but it is not fully type-safe at compile time, so arrays perform runtime store checks.

#### Interview answer

Covariance allows code such as `Object[] objects = new String[10];`. Reading is safe because every `String` is an `Object`. Writing is the problem: `objects[0] = new Object()` compiles, but the actual runtime array is a `String[]`, so the JVM throws `ArrayStoreException`.

Generics took a different approach: `List<String>` is not a subtype of `List<Object>`. That prevents the same kind of write problem at compile time. Wildcards such as `? extends Object` are used when covariance is needed safely.

#### Deep dive

Arrays are reified: the JVM knows the component type at runtime. That is why it can enforce the runtime store check. Generic types are erased, so the JVM generally does not know whether a raw `List` was meant to be a `List<String>`.

Array covariance is mainly a legacy/convenience design. Modern Java code usually avoids relying on it for API design because it moves errors from compile time to runtime.

#### Production angle

Do not design APIs around writable covariant arrays unless necessary. Prefer `List<T>` or read-only views for application-level APIs. Arrays are still fine for low-level data, but be careful when passing subtype arrays to APIs that accept supertype arrays and may write into them.

#### Traps / caveats

- Array covariance is type-safe only with runtime checks, not purely at compile time.
- The error appears at the store operation, not at the assignment `Object[] o = new String[1]`.
- Generic invariance often feels stricter, but it prevents this runtime failure.

#### Optional Anki

Q: Why can `Object[] a = new String[1]` later fail?
A: Arrays are covariant, but the JVM checks the real component type on store and may throw `ArrayStoreException`.

</details>

<a id="jcore-type-017"></a>

<details>
<summary><strong>JCORE-TYPE-017. What is ArrayStoreException, and when can it happen?</strong></summary>

#### Short answer

`ArrayStoreException` is a runtime exception thrown when code tries to store a value whose type is incompatible with the actual runtime component type of an array. It commonly happens because arrays are covariant.

#### Interview answer

Example: `Object[] values = new String[1]; values[0] = 42;`. This compiles because the variable type is `Object[]`, but at runtime the actual array is `String[]`. The JVM prevents storing an `Integer` into a `String[]` and throws `ArrayStoreException`.

It is different from `ClassCastException`. `ClassCastException` is about an invalid cast; `ArrayStoreException` is about an invalid array write.

#### Deep dive

The JVM checks array stores because arrays are reified and know their component type. The check applies to reference arrays, not primitive arrays in the same way, because primitive arrays cannot be assigned covariantly to object arrays like `Object[]`.

The exception can also appear indirectly in reflection, serialization frameworks or generic-looking helper methods that internally use arrays.

#### Production angle

This exception usually indicates a poor API boundary or unsafe array reuse. Prefer typed collections for mutable APIs, avoid accepting overly broad array types when writing into them, and add tests when framework code fills arrays reflectively.

#### Traps / caveats

- The assignment to a wider array reference may succeed; the store fails later.
- `Object[]` cannot point to `int[]`; primitive arrays are objects but not object arrays.
- `Arrays.copyOf` and reflective array creation need the intended component type.

#### Optional Anki

Q: What operation throws `ArrayStoreException`?
A: Storing an element incompatible with the array’s actual runtime component type.

</details>

<a id="jcore-type-018"></a>

<details>
<summary><strong>JCORE-TYPE-018. What are varargs, and what pitfalls do they create?</strong></summary>

#### Short answer

Varargs let a method accept zero or more arguments as an array, for example `void log(String... messages)`. Pitfalls include ambiguity with overloads, confusion with passing `null`, accidental mutation of the backing array, and heap pollution with generic varargs.

#### Interview answer

Varargs are mostly syntactic sugar. A parameter `T...` is compiled as `T[]`, and callers can pass individual arguments or an array. Inside the method, it is just an array.

This is convenient for APIs like logging or formatting, but it should not be abused. Overloaded methods with varargs can be hard to reason about. Generic varargs are also tricky because arrays are reified while generics are erased, which can lead to heap pollution warnings.

#### Deep dive

A varargs parameter must be the last parameter. Each method can have only one varargs parameter. Passing no arguments creates an empty array. Passing an existing array uses that array reference, so modifying the array inside the method may affect the caller’s array.

For generic varargs, `@SafeVarargs` can be used on constructors and methods that cannot be overridden, such as `static`, `final` or `private` methods, when they do not perform unsafe operations with the varargs array. It is a promise by the author, not a magic runtime protection.

#### Production angle

Varargs are good for small convenience APIs, but avoid them in high-volume paths if they allocate arrays on every call. Be careful in public APIs because adding overloads later can change method resolution or create source ambiguity for clients.

#### Traps / caveats

- `method(null)` may mean a null array or one null element depending on overloads and target type.
- Generic varargs can produce heap pollution warnings.
- A varargs method receives an array, so mutating it can surprise a caller who passed an existing array.

#### Optional Anki

Q: What is `T...` inside a Java method?
A: It is a `T[]` array parameter, with call-site syntax for zero or more arguments.

</details>

<a id="jcore-type-019"></a>

<details>
<summary><strong>JCORE-TYPE-019. What are casting, upcasting and downcasting in Java?</strong></summary>

#### Short answer

Casting tells the compiler to treat a value as another compatible type. Upcasting converts a subtype reference to a supertype and is implicit and safe. Downcasting converts a supertype reference to a subtype; it requires an explicit cast and is checked at runtime.

#### Interview answer

Example: `String s = "x"; Object o = s;` is upcasting. Every `String` is an `Object`, so no explicit cast is needed. Downcasting is the reverse direction: `String t = (String) o;`. It succeeds only if the actual object is a `String`.

A cast does not change the object. It changes the static type through which the code views the object, and for downcasts it asks the JVM to verify that the object really has the requested type. If not, the JVM throws `ClassCastException`.

#### Deep dive

There are also primitive casts, such as `(int) longValue`, which can narrow or change numeric representation. Reference casts follow the inheritance/interface type relationship and runtime object type. Arrays have their own covariance behavior and runtime checks.

Modern Java often replaces explicit downcast patterns with pattern matching for `instanceof`: `if (obj instanceof String s) { ... }`. This combines the type test and cast, reducing mistakes.

#### Production angle

Frequent downcasts in business code are often a design smell: the API may be too generic, or polymorphism/sealed types/visitor-like dispatch may be clearer. Casts are sometimes necessary at boundaries such as reflection, deserialization and framework integration, but isolate and validate them there.

#### Traps / caveats

- A cast does not convert an arbitrary object into another class; it only checks/views compatible types.
- Downcasting based on assumptions about data shape often fails after API evolution.
- Primitive narrowing casts can silently lose information, unlike reference downcasts that fail with an exception.

#### Optional Anki

Q: What is the difference between upcasting and downcasting?
A: Upcasting goes from subtype to supertype and is implicit; downcasting goes from supertype to subtype and is runtime-checked.

</details>

<a id="jcore-type-020"></a>

<details>
<summary><strong>JCORE-TYPE-020. What is ClassCastException, and how can it be avoided?</strong></summary>

#### Short answer

`ClassCastException` is thrown when code tries to cast an object to a type that the object is not an instance of. Avoid it by using precise generic types, avoiding raw types, checking with `instanceof` or pattern matching when needed, and designing APIs that do not require guessing runtime types.

#### Interview answer

A `ClassCastException` means the compiler allowed the cast syntactically, but the JVM found that the actual object does not match the requested type. For example, `Object x = 123; String s = (String) x;` compiles but fails at runtime.

The best prevention is stronger typing. Use generics correctly, do not use raw collections, avoid `Object`-based APIs where a specific type is known, and prefer polymorphism over manual type switches. When the type is genuinely uncertain, check it first with `instanceof` pattern matching.

#### Deep dive

Generics eliminate many casts at the source level, but type erasure means some casts still exist in compiler-generated bytecode. Raw types can bypass generic checks and move the failure to a later read. For example, adding an `Integer` to a raw list that is later treated as `List<String>` can fail when an element is read.

Classloader issues can also produce confusing cast failures: two classes with the same fully qualified name loaded by different classloaders are different runtime types. This is less common in simple apps but relevant in application servers, plugins and test frameworks.

#### Production angle

In backend systems, `ClassCastException` often appears around JSON deserialization to raw maps, message payloads, cache values, reflection, proxies and framework extension points. Validate payload schemas, keep typed boundaries, and fail early with clear errors instead of letting a deep cast fail later.

#### Traps / caveats

- Raw collections compile with warnings, but can fail much later with `ClassCastException`.
- `instanceof` checks should not replace good polymorphic design everywhere.
- A proxy object may implement an interface but not be the concrete class you tried to cast to.

#### Optional Anki

Q: What is the usual root cause of `ClassCastException`?
A: The actual runtime object is not an instance of the type requested by the cast.

</details>

<a id="jcore-type-021"></a>

<details>
<summary><strong>JCORE-TYPE-021. How does Java choose between overloaded methods?</strong></summary>

#### Short answer

Java resolves overloaded methods at compile time. It first finds methods with the right name and accessible scope, checks which are applicable to the argument expressions, prefers fixed-arity methods before varargs, and then chooses the most specific applicable method. If no single best method exists, the call is a compile-time error.

#### Interview answer

The important interview point is that overloading is based on the compile-time types of the arguments, not on the runtime classes of arbitrary objects. For `print(String)` and `print(Object)`, a variable declared as `String` chooses `print(String)`, while a variable declared as `Object` chooses `print(Object)` even if it currently points to a `String`.

The compiler applies overload resolution in phases. It tries matching-arity methods without boxing/varargs first, then matching-arity methods that may use boxing or unboxing, and only then variable-arity methods. Among applicable candidates it picks the most specific one.

#### Deep dive

Overload resolution is a source-language rule. It considers the receiver type, method name, accessibility, arity, generic inference, conversion contexts and specificity. The selected signature is encoded into bytecode; runtime dispatch may still choose an overriding implementation for that selected signature, but it does not rerun overload resolution.

Specificity is roughly subtype-based: `String` is more specific than `Object`, and `Integer` is more specific than `Number`. With generics, lambdas, method references and varargs, the rules become more complex, so production APIs should avoid overload sets that rely on subtle compiler choices.

#### Production angle

For maintainable APIs, keep overload sets small and obvious. Avoid overloads whose parameter types are unrelated, differ only by wrappers/primitives, or combine fixed arity and varargs in surprising ways. Adding a new overload can change source-level resolution for clients after recompilation even if binary compatibility looks fine.

#### Traps / caveats

- The runtime class of a non-receiver argument does not decide the overload.
- The most specific overload can make `null` calls surprising or ambiguous.
- A new overload may silently change which method client source code calls after recompilation.

#### Optional Anki

Q: When is an overloaded Java method selected?
A: At compile time, using the compile-time types and overload-resolution rules.

</details>

<a id="jcore-type-022"></a>

<details>
<summary><strong>JCORE-TYPE-022. Why can passing null to overloaded methods be ambiguous?</strong></summary>

#### Short answer

The `null` literal is compatible with any reference type, so several reference overloads may be applicable. If one parameter type is more specific, Java chooses it; for example `String` beats `Object`. If candidates are unrelated, such as `String` and `Integer`, the call is ambiguous and fails to compile.

#### Interview answer

Example: with `m(Object)` and `m(String)`, `m(null)` calls `m(String)`, because `String` is more specific. But with `m(String)` and `m(Integer)`, neither type is more specific than the other, so `m(null)` is a compile-time ambiguity.

The fix is to avoid such overloads or make the target type explicit: `m((String) null)`. But explicit null casts are usually a smell in application code; clearer API names or typed optional values are often better.

#### Deep dive

Ambiguity arises because overload resolution must select one method before runtime. The `null` literal has the null type and can convert to any reference type, but it cannot convert to primitives except indirectly through boxing/unboxing situations that still require a reference target. If two applicable reference overloads are incomparable, the compiler cannot guess developer intent.

This is especially problematic with overloads such as `create(Path)` and `create(URI)`, or builders that accept several nullable reference types. The ambiguity may appear only when a caller passes a literal `null` or a conditional expression with a null branch.

#### Production angle

Public APIs should avoid unrelated nullable overloads. Prefer explicit method names, parameter objects, builders with named setters, or non-null contracts. In tests, include calls with `null` when an API intentionally accepts it, because overload additions can change the compile result or selected method.

#### Traps / caveats

- `m(null)` can choose a more specific overload rather than the one that seems more general.
- Unrelated reference overloads make `null` ambiguous.
- A cast like `(String) null` resolves ambiguity but may hide poor API design.

#### Optional Anki

Q: Why is `m(null)` ambiguous for `m(String)` and `m(Integer)`?
A: `null` matches both reference types, and neither overload is more specific.

</details>

<a id="jcore-type-023"></a>

<details>
<summary><strong>🧠 JCORE-TYPE-023. How do widening, boxing, unboxing and varargs interact in overload resolution?</strong></summary>

#### Short answer

Java overload resolution prefers the least invasive applicable phase: first fixed-arity calls using identity and widening conversions, then fixed-arity calls that may use boxing or unboxing, and finally varargs. This is why `m(long)` is preferred over `m(Integer)` for an `int` argument, and fixed-arity methods are preferred over varargs when both apply.

#### Interview answer

The practical rule of thumb is: widening beats boxing; boxing beats varargs; fixed arity beats variable arity. But there is no general “widen then box” conversion for overload resolution, so some calls that look plausible are not applicable.

Example: for `void m(long)` and `void m(Integer)`, calling `m(1)` chooses `m(long)`, because primitive widening from `int` to `long` is found in the first phase. For `void m(Integer)` and `void m(int...)`, `m(1)` chooses `m(Integer)`, because boxing fixed arity is considered before varargs.

#### Deep dive

Strict invocation allows identity and widening primitive/reference conversions but not boxing. Loose invocation adds boxing and unboxing, and may combine unboxing with widening primitive conversion in some invocation contexts. Varargs is considered only after no fixed-arity candidate worked.

A common trap is expecting `int` to become `Long`. Java can widen `int` to `long`, or box `int` to `Integer`, but it does not widen to `long` and then box to `Long` as a single overload conversion.

#### Production angle

Avoid overloads that differ only by primitive/wrapper forms or by fixed versus varargs forms. They are easy to misunderstand and can become unstable when another overload is added. In performance-sensitive code, also remember that a selected boxing overload allocates or reuses wrapper objects and may introduce null-unboxing risks later.

#### Traps / caveats

- Widening primitive conversion is preferred before boxing.
- There is no general `int -> long -> Long` method-invocation conversion.
- Varargs overloads are last-resort candidates and can hide allocation or ambiguity.

#### Optional Anki

Q: In overload resolution, what generally wins: widening, boxing, or varargs?
A: Widening first, then boxing/unboxing, then varargs.

</details>

<a id="jcore-type-024"></a>

<details>
<summary><strong>JCORE-TYPE-024. Why are overloaded methods resolved at compile time while overridden methods are resolved at runtime?</strong></summary>

#### Short answer

Overloading chooses between different method signatures, so the compiler must pick a signature using the compile-time types of the call. Overriding chooses an implementation for the already-selected signature, so the JVM can dispatch dynamically based on the actual receiver object at runtime.

#### Interview answer

Overloaded methods are separate methods with the same name but different parameter lists. The compiler has to decide which descriptor the call refers to before bytecode is generated. That decision is static.

Overridden instance methods share a compatible signature across an inheritance hierarchy. Bytecode can encode a virtual call to that signature, and at runtime the JVM chooses the implementation from the actual class of the receiver. This is dynamic dispatch and is the basis of polymorphism.

#### Deep dive

Consider `void f(Object)` and `void f(String)`. If the argument variable is declared as `Object`, the compiler selects `f(Object)`. If that selected method is overridden in a subclass, runtime dispatch may choose the subclass implementation of `f(Object)`, but it will not switch to `f(String)` just because the argument object is actually a `String`.

Static methods are hidden, not overridden, so they are also selected statically. Private methods and constructors are not overridden either. Instance method overriding is the runtime-polymorphic case.

#### Production angle

This distinction matters for API design and debugging. Overloads can make behavior depend on the static type visible at the call site, while overrides make behavior depend on the runtime receiver. When behavior should vary by object type, prefer polymorphism; when using overloads, keep call sites explicit and avoid overloads that pretend to be dynamic multi-dispatch.

#### Traps / caveats

- Overloading is not dynamic dispatch on argument runtime types.
- Overriding dispatches only on the receiver, not on all arguments.
- Static methods are hidden, not overridden, so they do not participate in virtual dispatch.

#### Optional Anki

Q: What is selected statically and what is selected dynamically?
A: Overload signature is selected statically; overridden instance-method implementation is selected dynamically by receiver type.

</details>
