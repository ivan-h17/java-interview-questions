# 2. Language, primitives and numeric types

<a id="jcore-type-001"></a>

<details>
<summary><strong>JCORE-TYPE-001. What is the difference between primitive types and reference types in Java?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Primitive variables hold simple values of one of Java’s eight primitive types: <code>boolean</code>, <code>byte</code>, <code>short</code>, <code>char</code>, <code>int</code>, <code>long</code>, <code>float</code> and <code>double</code>. Reference variables hold references to objects or arrays. Primitives cannot be <code>null</code> and do not have object identity; references can be <code>null</code> and point to objects with identity, fields and methods.</p>
</td>
<td valign="top" width="50%">
<p>Примитивные переменные хранят простые значения одного из восьми типов Java: <code>boolean</code>, <code>byte</code>, <code>short</code>, <code>char</code>, <code>int</code>, <code>long</code>, <code>float</code> и <code>double</code>. Ссылочные переменные хранят ссылки на объекты или массивы. Примитивы не могут быть <code>null</code> и не имеют идентичность; ссылки могут быть <code>null</code> и указывать на объекты с идентичность, полями и методами.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In an interview I would say that primitives are value types built into the language, while reference types represent objects. With primitives, assignment copies the primitive value. With references, assignment copies the reference value, so two variables may refer to the same object.</p>
<p>This distinction affects nullability, equality, memory layout, generics and performance. For example, <code>int</code> can be compared directly with <code>==</code>, but <code>Integer</code> is an object and <code>==</code> compares references unless unboxing happens. Collections and generics work with reference types, so primitives are usually boxed into wrappers such as <code>Integer</code> or <code>Long</code>.</p>
</td>
<td valign="top" width="50%">
<p>На интервью я бы сказал, что примитивы — это встроенные типы-значения, а ссылочные типы представляют объекты. При присваивании примитива копируется само значение. При присваивании ссылки копируется значение ссылки, поэтому две переменные могут указывать на один и тот же объект.</p>
<p>Это влияет на <code>null</code>, равенство, модель памяти, обобщения и производительность. Например, <code>int</code> можно сравнивать через <code>==</code>, а <code>Integer</code> — объект, и <code>==</code> сравнивает ссылки, если не произошло распаковки. Коллекции и обобщения работают со ссылочными типами, поэтому примитивы обычно упаковываются в классы-обёртки вроде <code>Integer</code> или <code>Long</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Primitive fields and array elements have default values such as <code>0</code>, <code>false</code> or <code>\u0000</code>. Reference fields and array elements default to <code>null</code>. Local variables, both primitive and reference, must be definitely assigned before use.</p>
<p>Reference types include classes, interfaces, arrays, enums, records and annotations. Arrays are objects even when their elements are primitive, for example <code>int[]</code> is a reference type whose elements are primitive <code>int</code> values.</p>
<p>The JVM representation is implementation-dependent, but the language-level rule is stable: primitive variables contain primitive values, reference variables contain references, and all method arguments are passed by value.</p>
</td>
<td valign="top" width="50%">
<p>Поля и элементы массивов примитивных типов имеют значения по умолчанию: например <code>0</code>, <code>false</code> или <code>\u0000</code>. Поля и элементы массивов ссылочных типов по умолчанию равны <code>null</code>. Локальные переменные, и примитивные, и ссылочные, должны быть определённо присвоены перед использованием.</p>
<p>К ссылочным типам относятся классы, интерфейсы, массивы, enum, records и аннотации. Массивы — это объекты даже тогда, когда их элементы примитивные: например, <code>int[]</code> — ссылочный тип, элементы которого являются примитивами <code>int</code>.</p>
<p>Конкретное JVM-представление зависит от реализации, но правило языка стабильно: переменные примитивного типа содержат значения примитивов, переменные ссылочного типа содержат ссылки, а все аргументы методов передаются по значению.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In backend code the choice often appears in DTOs, entities and hot loops. Primitive fields avoid <code>null</code> and boxing overhead but cannot represent “missing value”. Wrapper fields can model absence, but they require explicit null handling and may cause accidental unboxing <code>NullPointerException</code>.</p>
</td>
<td valign="top" width="50%">
<p>В бэкенд-коде выбор часто встречается в DTO, сущностях и горячих циклах. Примитивные поля не бывают <code>null</code> и не требуют накладных расходов упаковки, но не могут выразить “значение отсутствует”. Поля-обёртки могут моделировать отсутствие значения, но требуют явной обработки <code>null</code> и могут привести к случайному <code>NullPointerException</code> при распаковке.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>int</code> and <code>Integer</code> are not the same type: one is primitive, the other is an object.</li>
<li>A reference variable is not the object itself; reassigning it does not change another variable that points to the old object.</li>
<li>Primitive arrays such as <code>int[]</code> are objects, but their elements are not boxed.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li><code>int</code> и <code>Integer</code> — не один и тот же тип: первый примитив, второй объект.</li>
<li>Ссылочная переменная — это не сам объект; её переустановка не меняет другую переменную, указывающую на старый объект.</li>
<li>Примитивные массивы вроде <code>int[]</code> являются объектами, но их элементы не boxed.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the key difference between primitive and reference variables?<br>A: Primitive variables hold primitive values; reference variables hold references to objects or arrays.</p>
</td>
<td valign="top" width="50%">
<p>Q: В чём главное отличие примитив и переменные ссылочного типа?<br>A: Primitive variables хранят примитивные значения; переменные ссылочного типа хранят ссылки на объекты или массивы.</p>
</td>
</tr>
</tbody>
</table>

<a id="jcore-type-002"></a>

<details>
<summary><strong>JCORE-TYPE-002. What are wrapper classes, and when does Java use them automatically?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Wrapper classes are object representations of primitive types: <code>Integer</code> for <code>int</code>, <code>Long</code> for <code>long</code>, and so on. Java automatically boxes a primitive into a wrapper and unboxes a wrapper into a primitive in many contexts, especially assignments, method calls, arithmetic and generics-related code.</p>
</td>
<td valign="top" width="50%">
<p>Wrapper классы — объектные представления примитивных типов: <code>Integer</code> для <code>int</code>, <code>Long</code> для <code>long</code> и так далее. Java автоматически делает упаковка примитива в обёртка и распаковке обёртка в примитив во многих контекстах: присваивания, вызовы методов, арифметика и код с обобщения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Wrappers exist because Java has both primitives and objects. The wrapper classes add object behavior around primitive values: they can be stored in collections, used as generic type arguments, compared with methods, parsed from strings and represented as nullable fields.</p>
<p>Autoboxing is compiler-supported syntactic sugar. For example, <code>Integer x = 10;</code> is roughly <code>Integer x = Integer.valueOf(10);</code>, and <code>int y = x;</code> is roughly <code>int y = x.intValue();</code>. This is convenient, but it can hide allocation, identity comparison issues and <code>NullPointerException</code> during unboxing.</p>
</td>
<td valign="top" width="50%">
<p>Wrappers нужны потому, что в Java есть и примитивы, и объекты. Wrapper классы добавляют объектное поведение вокруг значения примитивов: их можно хранить в коллекциях, использовать как generic тип аргументы, сравнивать методами, парсить из строк и использовать как nullable-поля.</p>
<p>Autoboxing — это syntactic sugar на уровне компилятора. Например, <code>Integer x = 10;</code> примерно превращается в <code>Integer x = Integer.valueOf(10);</code>, а <code>int y = x;</code> — в <code>int y = x.intValue();</code>. Это удобно, но может скрывать выделение памяти, проблемы идентичность сравнение и <code>NullPointerException</code> при распаковке.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The wrapper types are <code>Boolean</code>, <code>Byte</code>, <code>Short</code>, <code>Character</code>, <code>Integer</code>, <code>Long</code>, <code>Float</code> and <code>Double</code>. They are immutable value-based classes in everyday usage; code should not rely on their object identity.</p>
<p>Automatic conversion happens in assignment contexts, invocation contexts and numeric expressions. It does not mean primitives become objects everywhere. For example, <code>List&lt;int&gt;</code> is invalid because generic type arguments must be reference types, so the code must use <code>List&lt;Integer&gt;</code>.</p>
</td>
<td valign="top" width="50%">
<p>Wrapper-типы: <code>Boolean</code>, <code>Byte</code>, <code>Short</code>, <code>Character</code>, <code>Integer</code>, <code>Long</code>, <code>Float</code> и <code>Double</code>. На практике они неизменяемый value-based классы; код не должен опираться на их идентичность объекта.</p>
<p>Автоматическая конвертация происходит в assignment contexts, контекстах вызова и numeric expressions. Это не значит, что примитивы “всегда становятся объектами”. Например, <code>List&lt;int&gt;</code> некорректен, потому что generic тип аргументы должны быть ссылочными типами; нужно использовать <code>List&lt;Integer&gt;</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Wrappers are common in JSON DTOs, database mappings and optional fields. Be deliberate: use wrappers where absence is meaningful, primitives where a value is mandatory and a default like zero is safe. In performance-sensitive code, avoid accidental boxing in streams, maps and tight loops.</p>
</td>
<td valign="top" width="50%">
<p>Wrappers часто встречаются в JSON DTO, база данных mappings и optional поля. Выбор должен быть осознанным: обёртки — когда отсутствие значения имеет смысл, примитивов — когда значение обязательно и стандартный вроде нуля безопасен. В performance-sensitive коде стоит избегать случайного упаковка в streams, maps и tight loops.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Unboxing a <code>null</code> wrapper throws <code>NullPointerException</code>.</li>
<li><code>Integer</code> identity must not be used for business equality; use <code>equals()</code> or compare primitives.</li>
<li>Generic collections require wrappers, which can add memory and CPU overhead.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Unboxing <code>null</code>-обёртка выбрасывает <code>NullPointerException</code>.</li>
<li>Identity у <code>Integer</code> нельзя использовать для бизнес равенство; используйте <code>equals()</code> или сравнивайте примитивов.</li>
<li>Generic коллекции требуют обёртки, что может добавить memory и CPU overhead.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why do wrapper classes exist?<br>A: They let primitive values participate in object APIs such as collections, generics, nullable fields and utility methods.</p>
</td>
<td valign="top" width="50%">
<p>Q: Зачем нужны классы-обёртки?<br>A: Они позволяют значения примитивов участвовать в объект APIs: коллекции, обобщения, nullable-поля и utility методы.</p>
</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>JCORE-TYPE-003. What is autoboxing, and what pitfalls does it create?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Autoboxing is the compiler’s automatic conversion from a primitive to its wrapper type; unboxing is the reverse conversion. Pitfalls include hidden allocations, surprising <code>==</code> behavior, <code>NullPointerException</code> when unboxing <code>null</code>, overload-resolution surprises and slower hot code.</p>
</td>
<td valign="top" width="50%">
<p>Autoboxing — автоматическое преобразование примитива в тип-обёртка компилятором; распаковке — обратное преобразование. Основные ловушки: скрытые выделения памяти, неожиданное поведение <code>==</code>, <code>NullPointerException</code> при распаковке <code>null</code>, сюрпризы разрешение перегрузки и замедление горячий код.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Autoboxing makes code more readable because you can write <code>List&lt;Integer&gt; ids = List.of(1, 2, 3);</code> instead of manually calling <code>Integer.valueOf</code>. The compiler inserts boxing and unboxing conversions where the language allows them.</p>
<p>The problem is that it looks free but is not always free. A wrapper can be <code>null</code>, has object identity, may allocate or use a cache, and requires unboxing for arithmetic. For example, <code>Integer x = null; int y = x;</code> compiles but fails at runtime.</p>
</td>
<td valign="top" width="50%">
<p>Autoboxing делает код читаемее: можно написать <code>List&lt;Integer&gt; ids = List.of(1, 2, 3);</code>, а не вызывать вручную <code>Integer.valueOf</code>. Компилятор вставляет упаковка и распаковке conversions там, где это разрешено языком.</p>
<p>Проблема в том, что это выглядит бесплатным, но не всегда бесплатно. Wrapper может быть <code>null</code>, имеет идентичность объекта, может создавать объект или использовать cache, а для арифметики требует распаковке. Например, <code>Integer x = null; int y = x;</code> компилируется, но падает в время выполнения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Boxing normally uses <code>valueOf</code>, not <code>new</code>. Some wrapper values are cached, for example small integers, but relying on the cache is a bug. Unboxing calls methods such as <code>intValue()</code>, so it fails if the wrapper reference is <code>null</code>.</p>
<p>In overload resolution, Java prefers widening over boxing, and fixed arity over varargs. This can produce unexpected method choices when overloads mix primitives, wrappers and varargs. In arithmetic, boxed values are unboxed and then numeric promotion rules apply.</p>
</td>
<td valign="top" width="50%">
<p>Boxing обычно использует <code>valueOf</code>, а не <code>new</code>. Некоторые обёртка значения кешируются, например маленькие integers, но полагаться на cache — ошибка. Unboxing вызывает методы вроде <code>intValue()</code>, поэтому падает, если обёртка ссылка равна <code>null</code>.</p>
<p>В разрешение перегрузки Java предпочитает расширение перед упаковка, а фиксированное число аргументов перед varargs. Из-за этого при перегрузках с примитивов, обёртки и varargs может быть выбран неожиданный метод. В арифметике упакованные значения распаковываются, затем применяются numeric promotion правила.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Autoboxing issues often show up in metrics aggregation, stream pipelines, ORM mappings and cache keys. A loop that repeatedly updates boxed counters can create many temporary objects. Prefer primitive-specialized APIs where available, such as <code>IntStream</code>, <code>LongStream</code> or primitive arrays for hot paths.</p>
</td>
<td valign="top" width="50%">
<p>Проблемы автоупаковка часто всплывают в metrics aggregation, stream pipelines, ORM mappings и cache ключами. Цикл, который постоянно обновляет boxed counters, может создавать много временных объектов. Для hot paths лучше использовать primitive-specialized APIs, например <code>IntStream</code>, <code>LongStream</code> или примитив массивы.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>Boolean flag = null; if (flag) ...</code> throws during unboxing.</li>
<li><code>Long sum = 0L; sum += value;</code> creates a new <code>Long</code> each update because wrappers are immutable.</li>
<li>A method overload may be selected by widening instead of boxing, which can surprise readers.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li><code>Boolean flag = null; if (flag) ...</code> падает при распаковке.</li>
<li><code>Long sum = 0L; sum += value;</code> создаёт новый <code>Long</code> при каждом обновлении, потому что обёртки неизменяемый.</li>
<li>Перегруженный метод может быть выбран через расширение, а не упаковка, что удивляет при чтении кода.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the most dangerous autoboxing pitfall?<br>A: Accidental unboxing of <code>null</code>, which throws <code>NullPointerException</code>.</p>
</td>
<td valign="top" width="50%">
<p>Q: Самая опасная ловушка автоупаковка?<br>A: Случайный распаковке значения <code>null</code>, который выбрасывает <code>NullPointerException</code>.</p>
</td>
</tr>

<a id="jcore-type-004"></a>

<details>
<summary><strong>JCORE-TYPE-004. Why can comparing boxed numbers with == produce surprising results?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For boxed numbers, <code>==</code> usually compares object references, not numeric values. Some boxed values are cached, so <code>Integer.valueOf(127) == Integer.valueOf(127)</code> is guaranteed to be true, while the same comparison for larger values is not portable and may be false. Use <code>equals()</code>, <code>compareTo()</code> or unbox deliberately.</p>
</td>
<td valign="top" width="50%">
<p>Для упакованных чисел оператор <code>==</code> обычно сравнивает ссылки на объекты, а не числовые значения. Некоторые упакованные значения кешируются, поэтому <code>Integer.valueOf(127) == Integer.valueOf(127)</code> гарантированно true, а такое же сравнение для больших значений не portable и может быть false. Используйте <code>equals()</code>, <code>compareTo()</code> или осознанный распаковке.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The surprising part is that boxed values look like numbers but are objects. If both operands are reference types, <code>==</code> checks whether they are the same object. For cached values this can be true, which makes <code>==</code> look reliable in small examples. For values outside the cache, two wrappers with the same numeric value may be different objects.</p>
<p>If one side is primitive and the other is boxed, Java unboxes the wrapper and performs primitive numeric comparison. That can also surprise people because it may throw <code>NullPointerException</code> if the wrapper is <code>null</code>.</p>
</td>
<td valign="top" width="50%">
<p>Сюрприз в том, что упакованные значения выглядят как числа, но являются объектами. Если оба операнда — ссылочных типов, <code>==</code> проверяет, один ли это объект. Для cached значения это может быть true, из-за чего <code>==</code> выглядит надёжным в маленьких примерах. Для значений вне cache два обёртки с одинаковым числом могут быть разными объектами.</p>
<p>Если одна сторона примитив, а другая boxed, Java распаковывает обёртка и делает примитив numeric сравнение. Это тоже может удивить, потому что при <code>null</code> обёртка будет <code>NullPointerException</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The language guarantees caching for some wrapper values, such as <code>Boolean</code> values and at least the integer range <code>-128..127</code> for integral wrappers where applicable. Implementations may cache more, but portable code must not depend on that.</p>
<p><code>equals()</code> compares wrapper values only when the wrapper classes are the same. For ordering or cross-type numeric logic, be explicit: convert to the intended primitive type, use <code>compare</code> methods, or use a domain type such as <code>BigDecimal</code> with clear scale rules.</p>
</td>
<td valign="top" width="50%">

</td>

Code review rule: never use <code>==</code> for boxed numeric equality unless you are deliberately checking identity, which is almost never the business requirement.</p>
</td>
<td valign="top" width="50%">
<p>Этот баг часто встречается в тестах и бизнес-проверках вокруг IDs, status codes и counters. Он может проходить на маленьких fixture значения и ломаться позже на продакшен-sized IDs. <details>
<summary><strong>JCORE-TYPE-005. How do numeric promotion and implicit widening conversions work?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Java allows safe implicit widening conversions, such as <code>int</code> to <code>long</code> or <code>float</code> to <code>double</code>. In numeric expressions, smaller integral types like <code>byte</code>, <code>short</code> and <code>char</code> are usually promoted to <code>int</code>, and binary numeric promotion chooses a common type such as <code>long</code>, <code>float</code> or <code>double</code>.</p>
</td>
<td valign="top" width="50%">
<p>Java разрешает безопасные неявный расширяющими преобразованиями, например <code>int</code> в <code>long</code> или <code>float</code> в <code>double</code>. В numeric expressions маленькие integral типы вроде <code>byte</code>, <code>short</code> и <code>char</code> обычно promoted to <code>int</code>, а бинарная numeric promotion выбирает общий тип: <code>long</code>, <code>float</code> или <code>double</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Numeric promotion is the set of rules Java uses to evaluate numeric expressions. A classic example is <code>byte a = 1; byte b = 2; byte c = a + b;</code>, which does not compile because <code>a + b</code> is promoted to <code>int</code>. You need an explicit cast or an <code>int</code> result variable.</p>
<p>For binary operations, Java promotes operands to a common type. If either is <code>double</code>, the result is <code>double</code>; else if either is <code>float</code>, result is <code>float</code>; else if either is <code>long</code>, result is <code>long</code>; otherwise it is <code>int</code>. Widening is implicit, narrowing usually requires a cast.</p>
</td>
<td valign="top" width="50%">
<p>Numeric promotion — набор правил, по которым Java вычисляет numeric expressions. Классический пример: <code>byte a = 1; byte b = 2; byte c = a + b;</code> не компилируется, потому что <code>a + b</code> promoted to <code>int</code>. Нужен явный приведение типа или переменная результата типа <code>int</code>.</p>
<p>Для бинарная эксплуатации Java приводит operands к общему типу. Если один из них <code>double</code>, результат <code>double</code>; иначе если есть <code>float</code>, результат <code>float</code>; иначе если есть <code>long</code>, результат <code>long</code>; иначе <code>int</code>. Widening происходит неявный, narrowing обычно требует приведение типа.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Widening does not always mean “no information loss” in the human sense. For example, converting a large <code>int</code> to <code>float</code> is allowed implicitly, but <code>float</code> may not represent every <code>int</code> exactly. It is considered a widening primitive conversion because the target type has a wider range, not because every value keeps all precision.</p>
<p>Constant expressions have special assignment rules: <code>byte b = 10;</code> is valid when the constant fits, but <code>byte b = someInt;</code> is not. Compound assignment also hides a cast: <code>b += 1</code> is roughly <code>b = (byte)(b + 1)</code>.</p>
</td>
<td valign="top" width="50%">
<p>Widening не всегда означает “без потери информации” в человеческом смысле. Например, большой <code>int</code> можно неявный преобразовать в <code>float</code>, но <code>float</code> не обязан точно представлять каждый <code>int</code>. Это расширяющим преобразованием примитива из-за более широкого диапазона, а не потому, что сохраняется вся precision.</p>
<p>Для constant expressions есть специальные правила присваивания: <code>byte b = 10;</code> корректно, если константа помещается, а <code>byte b = someInt;</code> — нет. Compound assignment тоже скрывает приведение типа: <code>b += 1</code> примерно равно <code>b = (byte)(b + 1)</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Promotion bugs appear in boundaries: serialization formats, database column types, metrics counters and monetary calculations. Be explicit about the expected result type, especially for division: <code>int / int</code> performs integer division even if you assign the result to <code>double</code>.</p>
</td>
<td valign="top" width="50%">
<p>Promotion ошибкаs часто появляются на границах: формат сериализацииs, база данных column типы, metrics counters и monetary calculations. Явно выбирайте ожидаемый результат тип, особенно для деления: <code>int / int</code> выполняет integer division, даже если результат присваивается в <code>double</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>char + char</code>, <code>byte + byte</code> and <code>short + short</code> produce <code>int</code>.</li>
<li><code>long + float</code> produces <code>float</code>, which can lose integer precision.</li>
<li><code>1 / 2</code> is <code>0</code>, while <code>1.0 / 2</code> is <code>0.5</code>.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li><code>char + char</code>, <code>byte + byte</code> и <code>short + short</code> дают <code>int</code>.</li>
<li><code>long + float</code> даёт <code>float</code>, что может потерять integer precision.</li>
<li><code>1 / 2</code> равно <code>0</code>, а <code>1.0 / 2</code> равно <code>0.5</code>.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the result type of <code>byte + byte</code> in Java?<br>A: <code>int</code>, because small integral types are promoted before arithmetic.</p>
</td>
<td valign="top" width="50%">
<p>Q: Какой тип результата у <code>byte + byte</code> в Java?<br>A: <code>int</code>, потому что малые целочисленные типы повышаются перед арифметикой.</p>
</td>

<details>
<summary><strong>JCORE-TYPE-006. What can go wrong with integer overflow in Java?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For <code>int</code> and <code>long</code>, Java integer arithmetic silently wraps around on overflow. It usually does not throw an exception. This can produce negative sizes, wrong balances, broken pagination, incorrect timestamps or security bugs unless the code validates ranges or uses checked arithmetic.</p>
</td>
<td valign="top" width="50%">
<p>Для <code>int</code> и <code>long</code> целочисленная арифметика в Java при переполнении молча переходит по кругу. Обычно исключение не выбрасывается. Это может дать отрицательные размеры, неверные балансы, сломанную пагинацию, неправильные временные метки или ошибки безопасности, если код не проверяет диапазоны и не использует проверяемую арифметику.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Integer overflow means the mathematical result does not fit into the type. For example, <code>Integer.MAX_VALUE + 1</code> becomes <code>Integer.MIN_VALUE</code>. Java defines this wraparound behavior for integral arithmetic, so the program keeps running with a wrong value.</p>
<p>The fix depends on the domain. Use <code>long</code> instead of <code>int</code> when the range is genuinely larger, use <code>Math.addExact</code>, <code>subtractExact</code>, <code>multiplyExact</code> or <code>toIntExact</code> when overflow should fail fast, and use <code>BigInteger</code> for unbounded integer arithmetic.</p>
</td>
<td valign="top" width="50%">
<p>Целочисленное переполнение означает, что математический результат не помещается в тип. Например, <code>Integer.MAX_VALUE + 1</code> становится <code>Integer.MIN_VALUE</code>. Java определяет такое поведение перехода по кругу для целочисленной арифметики, поэтому программа продолжает работать с неверным значением.</p>
<p>Исправление зависит от домена. Используйте <code>long</code> вместо <code>int</code>, если нужен больший диапазон; <code>Math.addExact</code>, <code>subtractExact</code>, <code>multiplyExact</code> или <code>toIntExact</code>, если переполнение должно быстро падать; и <code>BigInteger</code> для целочисленной арифметики без фиксированной верхней границы.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Overflow is especially easy to miss in multiplication before widening: <code>long bytes = count * 1024 * 1024;</code> can overflow as <code>int</code> before assignment if <code>count</code> is an <code>int</code>. Use <code>1024L</code> or convert earlier.</p>
<p>Array sizes, collection capacities and indexes are <code>int</code>-based in many APIs, so converting from <code>long</code> to <code>int</code> must be checked. Also remember that <code>Math.abs(Integer.MIN_VALUE)</code> is still negative because its positive counterpart does not fit in <code>int</code>.</p>
</td>
<td valign="top" width="50%">
<p>Переполнение особенно легко пропустить при умножении до расширения типа: <code>long bytes = count * 1024 * 1024;</code> может переполниться как <code>int</code> до присваивания, если <code>count</code> имеет тип <code>int</code>. Используйте <code>1024L</code> или преобразуйте тип раньше.</p>
<p>Размеры массивов, ёмкости коллекций и индексы во многих API основаны на <code>int</code>, поэтому преобразование из <code>long</code> в <code>int</code> нужно проверять. Также помните, что <code>Math.abs(Integer.MIN_VALUE)</code> всё ещё отрицателен, потому что положительный аналог не помещается в <code>int</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Overflow can become an incident when calculating money in minor units, rate-limit counters, pagination offsets or buffer sizes. Add boundary tests around max values, use exact arithmetic for critical calculations, and validate external numeric input before multiplication or casting.</p>
</td>
<td valign="top" width="50%">
<p>Переполнение может стать инцидентом при расчёте денег в минимальных единицах, счётчиков rate limit, смещений пагинации или размеров буферов. Добавляйте граничные тесты около максимальных значений, используйте точную арифметику для критичных расчётов и валидируйте внешний числовой ввод до умножения или приведения типов.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Widening after an overflowing <code>int</code> expression does not recover the correct value.</li>
<li><code>Math.abs(Integer.MIN_VALUE)</code> returns <code>Integer.MIN_VALUE</code>.</li>
<li>Overflow in capacity calculations can turn a large positive request into a small or negative number.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>

<li><code>Math.abs(Integer.MIN_VALUE)</code> возвращает <code>Integer.MIN_VALUE</code>.</li>
<li>Переполнение в расчётах ёмкости может превратить большой положительный запрос в маленькое или отрицательное число.</li>
</ul>

<table>

<tr>
<td valign="top" width="50%">
<p><code>float</code> and <code>double</code> are binary floating-point types. Many decimal values, such as <code>0.1</code>, cannot be represented exactly, so arithmetic accumulates rounding errors. </tr>
<tr>

<td valign="top" width="50%">

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">

<details>
<summary><strong>JCORE-TYPE-013. Is Java pass-by-value or pass-by-reference?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Java is always pass-by-value. For primitives, the copied value is the primitive value. For objects, the copied value is the reference. A method can mutate the object through that copied reference, but it cannot reassign the caller’s variable.</p>
</td>
<td valign="top" width="50%">
<p>Java всегда pass-by-value. Для примитивов копируемое значение — само примитивное значение. Для объектов копируемое значение — ссылка. Метод может изменить объект через эту скопированную ссылку, но не может переназначить переменную вызывающего кода.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The confusion comes from object references. When you pass an object to a method, Java copies the reference value into the parameter. Both caller and callee may now refer to the same object, so mutations are visible. But the parameter itself is a local variable. If the method assigns it to a new object, the caller’s variable still points to the old object.</p>
<p>A good phrase is: Java passes object references by value, not objects by reference. There is no Java equivalent of C++ reference parameters where assigning the parameter changes the caller’s variable.</p>
</td>
<td valign="top" width="50%">
<p>Путаница возникает из-за ссылок на объекты. Когда объект передаётся в метод, Java копирует значение ссылки в параметр. Вызывающий и вызываемый код могут теперь указывать на один и тот же объект, поэтому изменения видимы. Но сам параметр — локальная переменная. Если метод присвоит ему новый объект, переменная вызывающего кода всё равно будет указывать на старый объект.</p>
<p>Хорошая формулировка: Java передаёт ссылки на объекты по значению, а не объекты по ссылке. В Java нет аналога ссылочных параметров C++, где присваивание параметру меняет переменную вызывающего кода.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For <code>void change(StringBuilder sb)</code>, calling <code>sb.append("x")</code> mutates the shared object. Calling <code>sb = new StringBuilder()</code> only changes the local copy of the reference. The same principle applies to arrays, collections and custom objects.</p>
<p>This rule also explains why Java cannot implement a swap method like <code>swap(a, b)</code> that swaps two caller variables by assigning parameters. You can modify contents of mutable holder objects, but not the caller variables themselves.</p>
</td>
<td valign="top" width="50%">
<p>Для <code>void change(StringBuilder sb)</code> вызов <code>sb.append("x")</code> изменяет общий объект. Вызов <code>sb = new StringBuilder()</code> меняет только локальную копию ссылки. Тот же принцип применим к массивам, коллекциям и пользовательским объектам.</p>
<p>Это правило объясняет, почему Java не может реализовать метод <code>swap(a, b)</code>, который поменяет местами две переменные вызывающего кода через присваивание параметрам. Можно менять содержимое изменяемых holder-объектов, но не сами переменные вызывающего кода.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>This matters for API design. Mutating arguments can create hidden side effects and thread-safety bugs. Prefer immutable objects, return new values, or document mutation clearly. When accepting mutable collections or arrays, consider defensive copies if ownership should not be shared.</p>
</td>
<td valign="top" width="50%">
<p>Это важно для дизайна API. Изменение аргументов может создавать скрытые побочные эффекты и ошибки thread-safety. Предпочитайте неизменяемые объекты, возвращайте новые значения или явно документируйте изменение. При приёме изменяемых коллекций или массивов подумайте о defensive copies, если владение не должно быть общим.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>“Objects are passed by reference” is imprecise and misleading for Java.</li>
<li>Reassigning a parameter does not affect the caller’s variable.</li>
<li>Mutating a shared object through a copied reference is still visible to other holders of that reference.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Фраза “объекты передаются по ссылке” для Java неточная и вводит в заблуждение.</li>
<li>Переназначение параметра не влияет на переменную вызывающего кода.</li>
<li>Изменение общего объекта через скопированную ссылку всё равно видно другим владельцам этой ссылки.</li>
</ul>
</td>

<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">

<td valign="top" width="50%">
<p>Q: Может ли Java-метод переназначить объектную переменную вызывающего кода через присваивание параметру?<br>A: Нет. Параметр — это копия значения ссылки.</p>

</td>

<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>

<details>
<summary><strong>JCORE-TYPE-015. What are arrays in Java, and how do they differ from collections?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Arrays are fixed-size objects with a reified runtime component type and indexed access. Collections are object-based data structures with richer APIs, usually dynamic size and generic compile-time types. Arrays can hold primitives directly; generic collections cannot hold primitive type arguments.</p>
</td>
<td valign="top" width="50%">
<p>Массивы — объекты фиксированного размера с reified типом компонента во время выполнения и доступом по индексу. Коллекции — object-based структуры данных с более богатыми API, обычно динамическим размером и обобщёнными типами на этапе компиляции. Массивы могут напрямую хранить примитивы; обобщённые коллекции не могут иметь примитивы как аргументы типов.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>An array is a language-level container: <code>int[]</code>, <code>String[]</code>, etc. Its length is fixed after creation, and you access elements by index. Arrays know their component type at runtime, so storing the wrong type can be detected at runtime.</p>
<p>Collections are framework types such as <code>List</code>, <code>Set</code> and <code>Map</code>. They are more flexible: resizing, searching, iteration, algorithms and implementations with different performance characteristics. Generics give compile-time type safety, but because of type erasure a <code>List&lt;String&gt;</code> does not carry <code>String</code> as a runtime component type in the same way an array does.</p>
</td>
<td valign="top" width="50%">
<p>Массив — контейнер уровня языка: <code>int[]</code>, <code>String[]</code> и т.д. Его длина фиксируется при создании, элементы доступны по индексу. Массивы знают свой тип компонента во время выполнения, поэтому запись неправильного типа можно обнаружить во время выполнения.</p>
<p>Коллекции — типы фреймворка вроде <code>List</code>, <code>Set</code> и <code>Map</code>. Они гибче: resizing, searching, iteration, algorithms и реализации с разными характеристиками производительности. Generics дают статическую type safety, но из-за type erasure <code>List&lt;String&gt;</code> не несёт <code>String</code> как тип компонента во время выполнения так же, как массив.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Arrays are covariant: a <code>String[]</code> can be assigned to <code>Object[]</code>. Generic collections are invariant: <code>List&lt;String&gt;</code> is not a subtype of <code>List&lt;Object&gt;</code>. This makes collections safer at compile time, while arrays require runtime store checks.</p>
<p>Arrays use <code>length</code> field, collections use methods like <code>size()</code>. Arrays work well for fixed-size, low-level or performance-sensitive data. Collections are usually better for business code because they express intent and provide rich operations.</p>
</td>
<td valign="top" width="50%">
<p>Массивы ковариантны: <code>String[]</code> можно присвоить <code>Object[]</code>. Generic-коллекции инвариантны: <code>List&lt;String&gt;</code> не является subtype of <code>List&lt;Object&gt;</code>. Поэтому коллекции безопаснее на этапе компиляции, а массивы требуют store-проверки во время выполнения.</p>
<p>Массивы используют поле <code>length</code>, коллекции — методы вроде <code>size()</code>. Массивы хороши для fixed-size, low-level или performance-sensitive данных. Коллекции обычно лучше для бизнес-кода, потому что выражают intent и дают богатые операции.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use arrays for binary data, interop, fixed-size tables and hot paths where primitive storage matters. Use collections for domain models, service APIs and most application logic. Avoid exposing mutable arrays from APIs unless the caller is allowed to modify them.</p>
</td>
<td valign="top" width="50%">

<details>
<summary><strong>JCORE-TYPE-016. Why are Java arrays covariant?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Java arrays are covariant: if <code>String</code> is a subtype of <code>Object</code>, then <code>String[]</code> is considered a subtype of <code>Object[]</code>. This is convenient and historically part of Java’s type system, but it is not fully type-safe at compile time, so arrays perform runtime store checks.</p>
</td>
<td valign="top" width="50%">
<p>Java массивы covariant: если <code>String</code> subtype of <code>Object</code>, то <code>String[]</code> считается subtype of <code>Object[]</code>. Это удобно и исторически является частью тип system Java, но не полностью type-safe на этап компиляции, поэтому массивы выполняют время выполнения store проверки.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Covariance allows code such as <code>Object[] objects = new String[10];</code>. Reading is safe because every <code>String</code> is an <code>Object</code>. Writing is the problem: <code>objects[0] = new Object()</code> compiles, but the actual runtime array is a <code>String[]</code>, so the JVM throws <code>ArrayStoreException</code>.</p>
<p>Generics took a different approach: <code>List&lt;String&gt;</code> is not a subtype of <code>List&lt;Object&gt;</code>. That prevents the same kind of write problem at compile time. Wildcards such as <code>? extends Object</code> are used when covariance is needed safely.</p>
</td>
<td valign="top" width="50%">
<p>Covariance позволяет код вроде <code>Object[] objects = new String[10];</code>. Reading безопасен, потому что каждый <code>String</code> является <code>Object</code>. Проблема в writing: <code>objects[0] = new Object()</code> компилируется, но actual время выполнения массив — <code>String[]</code>, поэтому JVM выбрасывает <code>ArrayStoreException</code>.</p>
<p>Generics выбрали другой подход: <code>List&lt;String&gt;</code> не subtype of <code>List&lt;Object&gt;</code>. Это предотвращает похожую проблему записи на этап компиляции. Wildcards вроде <code>? extends Object</code> используются, когда covariance нужна безопасно.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Arrays are reified: the JVM knows the component type at runtime. That is why it can enforce the runtime store check. Generic types are erased, so the JVM generally does not know whether a raw <code>List</code> was meant to be a <code>List&lt;String&gt;</code>.</p>
<p>Array covariance is mainly a legacy/convenience design. Modern Java code usually avoids relying on it for API design because it moves errors from compile time to runtime.</p>
</td>
<td valign="top" width="50%">
<p>Arrays reified: JVM знает component тип в время выполнения. Поэтому она может выполнить время выполнения store check. Generic типы erased, поэтому JVM обычно не знает, должен ли raw <code>List</code> быть <code>List&lt;String&gt;</code>.</p>
<p>Array covariance — в основном legacy/convenience design. Современный Java code обычно не опирается на неё в дизайн API, потому что она переносит ошибки из этап компиляции в время выполнения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Do not design APIs around writable covariant arrays unless necessary. Prefer <code>List&lt;T&gt;</code> or read-only views for application-level APIs. Arrays are still fine for low-level data, but be careful when passing subtype arrays to APIs that accept supertype arrays and may write into them.</p>
</td>
<td valign="top" width="50%">
<p>Не проектируйте APIs вокруг writable covariant массивы без необходимости. Для application-level APIs лучше <code>List&lt;T&gt;</code> или read-only views. Arrays всё ещё нормальны для low-level data, но будьте осторожны, передавая subtype массивы в APIs, которые принимают supertype массивы и могут в них писать.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Array covariance is type-safe only with runtime checks, not purely at compile time.</li>
<li>The error appears at the store operation, not at the assignment <code>Object[] o = new String[1]</code>.</li>
<li>Generic invariance often feels stricter, but it prevents this runtime failure.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Array covariance type-safe только с время выполнения проверки, не полностью на этап компиляции.</li>
<li>Ошибка появляется при store operation, а не при assignment <code>Object[] o = new String[1]</code>.</li>
<li>Generic invariance кажется строже, но предотвращает такой время выполнения сбой.</li>
</ul>

<th colspan="2" align="left">Optional Anki</th>

<details>
<summary><strong>JCORE-TYPE-019. What are casting, upcasting and downcasting in Java?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Casting tells the compiler to treat a value as another compatible type. Upcasting converts a subtype reference to a supertype and is implicit and safe. Downcasting converts a supertype reference to a subtype; it requires an explicit cast and is checked at runtime.</p>
</td>
<td valign="top" width="50%">
<p>Приведение типа говорит компилятору рассматривать значение как другой совместимый тип. Восходящее приведение преобразует ссылку подтипа к супертипу, происходит неявно и безопасно. Нисходящее приведение преобразует ссылку супертипа к подтипу; оно требует явного приведения и проверяется во время выполнения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example: <code>String s = "x"; Object o = s;</code> is upcasting. Every <code>String</code> is an <code>Object</code>, so no explicit cast is needed. Downcasting is the reverse direction: <code>String t = (String) o;</code>. It succeeds only if the actual object is a <code>String</code>.</p>
<p>A cast does not change the object. It changes the static type through which the code views the object, and for downcasts it asks the JVM to verify that the object really has the requested type. If not, the JVM throws <code>ClassCastException</code>.</p>
</td>
<td valign="top" width="50%">
<p>Пример: <code>String s = "x"; Object o = s;</code> — восходящее приведение. Каждый <code>String</code> является <code>Object</code>, поэтому явное приведение типа не нужно. Нисходящее приведение — обратное направление: <code>String t = (String) o;</code>. Оно успешно только если фактический объект действительно <code>String</code>.</p>
<p>Приведение типа не меняет объект. Оно меняет статический тип, через который код смотрит на объект, а для нисходящего приведения просит JVM проверить, что объект действительно имеет запрошенный тип. Если нет, JVM выбрасывает <code>ClassCastException</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>There are also primitive casts, such as <code>(int) longValue</code>, which can narrow or change numeric representation. Reference casts follow the inheritance/interface type relationship and runtime object type. Arrays have their own covariance behavior and runtime checks.</p>
<p>Modern Java often replaces explicit downcast patterns with pattern matching for <code>instanceof</code>: <code>if (obj instanceof String s) { ... }</code>. This combines the type test and cast, reducing mistakes.</p>
</td>
<td valign="top" width="50%">
<p>Есть также приведения примитивов, например <code>(int) longValue</code>, которые могут сузить или изменить числовое представление. Ссылочные приведения следуют отношениям наследования и интерфейсов, а также фактическому типу объекта во время выполнения. У массивов есть своё ковариантное поведение и проверки во время выполнения.</p>
<p>Modern Java часто заменяет явные шаблоны нисходящего приведения на pattern matching для <code>instanceof</code>: <code>if (obj instanceof String s) { ... }</code>. Это объединяет проверку типа и приведение, снижая вероятность ошибок.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Frequent downcasts in business code are often a design smell: the API may be too generic, or polymorphism/sealed types/visitor-like dispatch may be clearer. Casts are sometimes necessary at boundaries such as reflection, deserialization and framework integration, but isolate and validate them there.</p>
</td>
<td valign="top" width="50%">
<p>Частые нисходящие приведения типов в бизнес-коде часто являются design smell: API может быть слишком обобщённым, или полиморфизм, sealed-типы либо visitor-like dispatch будут понятнее. Приведения типов иногда нужны на границах вроде reflection, десериализации и интеграции с фреймворками, но там их лучше изолировать и валидировать.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>A cast does not convert an arbitrary object into another class; it only checks/views compatible types.</li>
<li>Downcasting based on assumptions about data shape often fails after API evolution.</li>
<li>Primitive narrowing casts can silently lose information, unlike reference downcasts that fail with an exception.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Приведение типа не превращает произвольный объект в другой класс; оно только проверяет или показывает совместимые типы.</li>
<li>Нисходящее приведение на основе предположений о форме данных часто ломается после эволюции API.</li>
<li>Сужающие приведения примитивов могут молча терять информацию, в отличие от ссылочных нисходящих приведений, которые падают с исключением.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the difference between upcasting and downcasting?<br>A: Upcasting goes from subtype to supertype and is implicit; downcasting goes from supertype to subtype and is runtime-checked.</p>
</td>
<td valign="top" width="50%">
<p>Q: Чем отличаются восходящее приведение и нисходящее приведение?<br>A: Восходящее приведение идёт от подтипа к супертипу и выполняется неявно; нисходящее приведение идёт от супертипа к подтипу и проверяется во время выполнения.</p>
</td>

<details>
<summary><strong>JCORE-TYPE-020. What is ClassCastException, and how can it be avoided?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>ClassCastException</code> is thrown when code tries to cast an object to a type that the object is not an instance of. Avoid it by using precise generic types, avoiding raw types, checking with <code>instanceof</code> or pattern matching when needed, and designing APIs that do not require guessing runtime types.</p>
</td>
<td valign="top" width="50%">
<p><code>ClassCastException</code> выбрасывается, когда код пытается привести объект к типу, экземпляром которого объект не является. Избегайте этого через точные generic-типы, отказ от raw types, проверки <code>instanceof</code> или pattern matching при необходимости и дизайн API без угадывания фактических типов.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A <code>ClassCastException</code> means the compiler allowed the cast syntactically, but the JVM found that the actual object does not match the requested type. For example, <code>Object x = 123; String s = (String) x;</code> compiles but fails at runtime.</p>
<p>The best prevention is stronger typing. Use generics correctly, do not use raw collections, avoid <code>Object</code>-based APIs where a specific type is known, and prefer polymorphism over manual type switches. When the type is genuinely uncertain, check it first with <code>instanceof</code> pattern matching.</p>
</td>
<td valign="top" width="50%">
<p><code>ClassCastException</code> означает, что компилятор синтаксически разрешил приведение типа, но JVM обнаружила, что фактический объект не соответствует запрошенному типу. Например, <code>Object x = 123; String s = (String) x;</code> компилируется, но падает во время выполнения.</p>
<p>Лучшая профилактика — более строгая типизация. Корректно используйте обобщения, не используйте сырые коллекции, избегайте <code>Object</code>-based API, когда известен конкретный тип, и предпочитайте полиморфизм ручным переключателям по типу. Когда тип действительно неизвестен, сначала проверяйте его через pattern matching для <code>instanceof</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Generics eliminate many casts at the source level, but type erasure means some casts still exist in compiler-generated bytecode. Raw types can bypass generic checks and move the failure to a later read. For example, adding an <code>Integer</code> to a raw list that is later treated as <code>List&lt;String&gt;</code> can fail when an element is read.</p>
<p>Classloader issues can also produce confusing cast failures: two classes with the same fully qualified name loaded by different classloaders are different runtime types. This is less common in simple apps but relevant in application servers, plugins and test frameworks.</p>
</td>
<td valign="top" width="50%">
<p>Generics устраняют многие приведения типов на уровне исходного кода, но type erasure означает, что некоторые приведения типов всё равно существуют в сгенерированном компилятором байткоде. Raw types могут обойти generic-проверки и перенести сбой на более позднее чтение. Например, добавление <code>Integer</code> в raw list, который позже рассматривается как <code>List&lt;String&gt;</code>, может упасть при чтении элемента.</p>
<p>Проблемы classloader тоже могут давать непонятные сбои приведения типов: два класса с одним полным именем, загруженные разными загрузчиками классов, являются разными фактическими типами. Это реже в простых приложениях, но важно в серверах приложений, плагинах и тестовых фреймворках.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In backend systems, <code>ClassCastException</code> often appears around JSON deserialization to raw maps, message payloads, cache values, reflection, proxies and framework extension points. Validate payload schemas, keep typed boundaries, and fail early with clear errors instead of letting a deep cast fail later.</p>
</td>
<td valign="top" width="50%">
<p>В бэкенд-системах <code>ClassCastException</code> часто появляется вокруг десериализация JSON в сырые map-структуры, payload сообщений, значения из кеша, reflection, прокси и точки расширения фреймворка. Валидируйте схемы payload, держите типизированные границы и раннее падение с понятными ошибки вместо позднего падения deep приведение типа.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Raw collections compile with warnings, but can fail much later with <code>ClassCastException</code>.</li>
<li><code>instanceof</code> checks should not replace good polymorphic design everywhere.</li>
<li>A proxy object may implement an interface but not be the concrete class you tried to cast to.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Raw коллекции компилируются с warnings, но могут намного позже упасть с <code>ClassCastException</code>.</li>
<li><code>instanceof</code> проверки не должны повсюду заменять хороший полиморфен design.</li>
<li>Прокси-объект может implement interface, но не быть конкретный класс, к которому вы пытаетесь приведение типа.</li>

</td>
<td valign="top" width="50%">

<a id="jcore-type-021"></a>

<details>
<summary><strong>JCORE-TYPE-021. How does Java choose between overloaded methods?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Java resolves overloaded methods at compile time. It first finds methods with the right name and accessible scope, checks which are applicable to the argument expressions, prefers fixed-arity methods before varargs, and then chooses the most specific applicable method. If no single best method exists, the call is a compile-time error.</p>
</td>
<td valign="top" width="50%">
<p>Java выбирает перегруженный метод на этапе компиляции. Сначала ищутся доступные методы с нужным именем, затем проверяется их применимость к выражениям аргументов. Методы с фиксированным числом аргументов рассматриваются раньше varargs, после чего выбирается наиболее специфичный применимый метод. Если единственного лучшего метода нет, вызов даёт ошибку компиляции.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The important interview point is that overloading is based on the compile-time types of the arguments, not on the runtime classes of arbitrary objects. For <code>print(String)</code> and <code>print(Object)</code>, a variable declared as <code>String</code> chooses <code>print(String)</code>, while a variable declared as <code>Object</code> chooses <code>print(Object)</code> even if it currently points to a <code>String</code>.</p>
<p>The compiler applies overload resolution in phases. It tries matching-arity methods without boxing/varargs first, then matching-arity methods that may use boxing or unboxing, and only then variable-arity methods. Among applicable candidates it picks the most specific one.</p>
</td>
<td valign="top" width="50%">
<p>Главная мысль для интервью: перегрузка выбирается по статическим типам аргументов, а не по фактическим классам произвольных объектов. Для <code>print(String)</code> и <code>print(Object)</code> переменная, объявленная как <code>String</code>, выберет <code>print(String)</code>, а переменная, объявленная как <code>Object</code>, выберет <code>print(Object)</code>, даже если сейчас указывает на <code>String</code>.</p>
<p>Компилятор применяет разрешение перегрузки по фазам. Сначала он пробует методы с подходящим числом аргументов без упаковки и varargs, затем методы с подходящим числом аргументов с возможной упаковкой или распаковкой, и только потом методы с переменным числом аргументов. Среди применимых кандидатов выбирается наиболее специфичный.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Overload resolution is a source-language rule. It considers the receiver type, method name, accessibility, arity, generic inference, conversion contexts and specificity. The selected signature is encoded into bytecode; runtime dispatch may still choose an overriding implementation for that selected signature, but it does not rerun overload resolution.</p>
<p>Specificity is roughly subtype-based: <code>String</code> is more specific than <code>Object</code>, and <code>Integer</code> is more specific than <code>Number</code>. With generics, lambdas, method references and varargs, the rules become more complex, so production APIs should avoid overload sets that rely on subtle compiler choices.</p>
</td>
<td valign="top" width="50%">
<p>Разрешение перегрузки — это правило языка Java. Оно учитывает тип получателя, имя метода, доступность, число аргументов, вывод обобщённых типов, контексты преобразования и специфичность. Выбранная сигнатура записывается в байткод; диспетчеризация во время выполнения может выбрать переопределённую реализацию для этой сигнатуры, но разрешение перегрузки заново не запускается.</p>
<p>Специфичность примерно основана на подтипах: <code>String</code> более специфичен, чем <code>Object</code>, а <code>Integer</code> более специфичен, чем <code>Number</code>. С обобщениями, лямбдами, ссылками на методы и varargs правила усложняются, поэтому продакшен-API не должны полагаться на тонкий выбор компилятора.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For maintainable APIs, keep overload sets small and obvious. Avoid overloads whose parameter types are unrelated, differ only by wrappers/primitives, or combine fixed arity and varargs in surprising ways. Adding a new overload can change source-level resolution for clients after recompilation even if binary compatibility looks fine.</p>
</td>
<td valign="top" width="50%">
<p>Для поддерживаемых API держите наборы перегрузок маленькими и очевидными. Избегайте перегрузок, где типы параметров не связаны, отличаются только обёртками и примитивами или неожиданно смешивают фиксированное число аргументов и varargs. Добавление новой перегрузки может изменить разрешение на уровне исходного кода у клиентов после перекомпиляции, даже если бинарная совместимость выглядит нормальной.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>The runtime class of a non-receiver argument does not decide the overload.</li>
<li>The most specific overload can make <code>null</code> calls surprising or ambiguous.</li>
<li>A new overload may silently change which method client source code calls after recompilation.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Фактический класс аргумента, не являющегося получателем вызова, не выбирает перегрузку.</li>
<li>Наиболее специфичная перегрузка может сделать вызовы с <code>null</code> неожиданными или неоднозначными.</li>
<li>Новая перегрузка может незаметно изменить, какой метод вызывает исходный код клиента после перекомпиляции.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: When is an overloaded Java method selected?<br>A: At compile time, using the compile-time types and overload-resolution rules.</p>
</td>
<td valign="top" width="50%">
<p>Q: Когда выбирается перегруженный метод Java?<br>A: В этап компиляции, по статические типы и правилам разрешение перегрузки.</p>
</td>
</tr>

<details>
<summary><strong>JCORE-TYPE-022. Why can passing null to overloaded methods be ambiguous?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The <code>null</code> literal is compatible with any reference type, so several reference overloads may be applicable. If one parameter type is more specific, Java chooses it; for example <code>String</code> beats <code>Object</code>. If candidates are unrelated, such as <code>String</code> and <code>Integer</code>, the call is ambiguous and fails to compile.</p>
</td>
<td valign="top" width="50%">
<p>Литерал <code>null</code> совместим с любым ссылочным типом, поэтому несколько ссылочных перегрузок могут быть применимы. Если один тип параметра более специфичен, Java выбирает его; например, <code>String</code> выигрывает у <code>Object</code>. Если кандидаты несвязаны, например <code>String</code> и <code>Integer</code>, вызов становится неоднозначным и не компилируется.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example: with <code>m(Object)</code> and <code>m(String)</code>, <code>m(null)</code> calls <code>m(String)</code>, because <code>String</code> is more specific. But with <code>m(String)</code> and <code>m(Integer)</code>, neither type is more specific than the other, so <code>m(null)</code> is a compile-time ambiguity.</p>
<p>The fix is to avoid such overloads or make the target type explicit: <code>m((String) null)</code>. But explicit null casts are usually a smell in application code; clearer API names or typed optional values are often better.</p>
</td>
<td valign="top" width="50%">
<p>Пример: при <code>m(Object)</code> и <code>m(String)</code> вызов <code>m(null)</code> попадёт в <code>m(String)</code>, потому что <code>String</code> более специфичен. Но при <code>m(String)</code> и <code>m(Integer)</code> ни один тип не более специфичен, поэтому <code>m(null)</code> — неоднозначность на этапе компиляции.</p>
<p>Исправить можно, избежав таких перегрузки или явно указав целевой тип: <code>m((String) null)</code>. Но явные приведения null обычно являются smell в прикладном коде; часто лучше использовать более ясные имена API или типизированные optional-значения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Ambiguity arises because overload resolution must select one method before runtime. The <code>null</code> literal has the null type and can convert to any reference type, but it cannot convert to primitives except indirectly through boxing/unboxing situations that still require a reference target. If two applicable reference overloads are incomparable, the compiler cannot guess developer intent.</p>
<p>This is especially problematic with overloads such as <code>create(Path)</code> and <code>create(URI)</code>, or builders that accept several nullable reference types. The ambiguity may appear only when a caller passes a literal <code>null</code> or a conditional expression with a null branch.</p>
</td>
<td valign="top" width="50%">
<p>Ambiguity возникает потому, что разрешение перегрузки должна выбрать один метод до время выполнения. Литерал <code>null</code> имеет тип null и может convert к любому ссылочный тип, но не может convert к примитивов, кроме косвенных упаковка/ситуаций с распаковкой, где всё равно нужен ссылочный целевой тип. Если два применимых ссылочных перегрузок несравнимы, компилятор не может угадать намерение разработчика.</p>
<p>Это особенно проблемно с перегрузки вроде <code>create(Path)</code> и <code>create(URI)</code> или builder'ы, принимающими несколько nullable-ссылочных типов. Ambiguity может появиться только когда вызывающий код передаёт литерал <code>null</code> или условное выражение с веткой с null.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Public APIs should avoid unrelated nullable overloads. Prefer explicit method names, parameter objects, builders with named setters, or non-null contracts. In tests, include calls with <code>null</code> when an API intentionally accepts it, because overload additions can change the compile result or selected method.</p>
</td>
<td valign="top" width="50%">
<p>Публичные API не должны иметь несвязанных перегрузок, принимающих null. Предпочитайте явные имена методов, объекты параметров, builder'ы с именованными сеттерами или non-null-контракты. В тестах добавляйте вызовы с <code>null</code>, если API сознательно принимает его, потому что новые перегрузки могут изменить результат компиляции или выбранный метод.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>m(null)</code> can choose a more specific overload rather than the one that seems more general.</li>
<li>Unrelated reference overloads make <code>null</code> ambiguous.</li>
<li>A cast like <code>(String) null</code> resolves ambiguity but may hide poor API design.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li><code>m(null)</code> может выбрать более специфичную перегрузку, а не ту, которая кажется более общей.</li>
<li>Unrelated ссылка перегрузки делают <code>null</code> неоднозначным.</li>
<li>Приведение типа вроде <code>(String) null</code> снимает неоднозначность, но может скрывать слабый дизайн API.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why is <code>m(null)</code> ambiguous for <code>m(String)</code> and <code>m(Integer)</code>?<br>A: <code>null</code> matches both reference types, and neither overload is more specific.</p>
</td>
<td valign="top" width="50%">
<p>Q: Почему <code>m(null)</code> неоднозначен для <code>m(String)</code> и <code>m(Integer)</code>?<br>A: <code>null</code> подходит к обоим ссылочным типам, и ни одна перегрузка не более специфична.</p>

<a id="jcore-type-023"></a>

<details>
<summary><strong>🧠 JCORE-TYPE-023. How do widening, boxing, unboxing and varargs interact in overload resolution?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Java overload resolution prefers the least invasive applicable phase: first fixed-arity calls using identity and widening conversions, then fixed-arity calls that may use boxing or unboxing, and finally varargs. This is why <code>m(long)</code> is preferred over <code>m(Integer)</code> for an <code>int</code> argument, and fixed-arity methods are preferred over varargs when both apply.</p>
</td>
<td valign="top" width="50%">
<p>Java разрешение перегрузки предпочитает наименее инвазивную применимую фазу: сначала вызовы с фиксированным числом аргументов с идентичность и расширяющими преобразованиями, затем вызовы с фиксированным числом аргументов с упаковка или распаковке, и только потом varargs. Поэтому <code>m(long)</code> предпочитается <code>m(Integer)</code> для <code>int</code> argument, а методы с фиксированным числом аргументов предпочитаются varargs, когда подходят оба варианта.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The practical rule of thumb is: widening beats boxing; boxing beats varargs; fixed arity beats variable arity. But there is no general “widen then box” conversion for overload resolution, so some calls that look plausible are not applicable.</p>
<p>Example: for <code>void m(long)</code> and <code>void m(Integer)</code>, calling <code>m(1)</code> chooses <code>m(long)</code>, because primitive widening from <code>int</code> to <code>long</code> is found in the first phase. For <code>void m(Integer)</code> and <code>void m(int...)</code>, <code>m(1)</code> chooses <code>m(Integer)</code>, because boxing fixed arity is considered before varargs.</p>
</td>
<td valign="top" width="50%">
<p>Практическое правило: расширение предпочтительнее упаковки; упаковка предпочтительнее varargs; фиксированное число аргументов beats переменное число аргументов. Но общего “widen then box” преобразование для разрешение перегрузки нет, поэтому некоторые calls, которые кажутся возможными, не применимы.</p>
<p>Пример: для <code>void m(long)</code> и <code>void m(Integer)</code> вызов <code>m(1)</code> выберет <code>m(long)</code>, потому что расширяющее преобразование примитива из <code>int</code> в <code>long</code> находится на первой фазе. Для <code>void m(Integer)</code> и <code>void m(int...)</code> вызов <code>m(1)</code> выберет <code>m(Integer)</code>, потому что упаковка фиксированное число аргументов рассматривается до varargs.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Strict invocation allows identity and widening primitive/reference conversions but not boxing. Loose invocation adds boxing and unboxing, and may combine unboxing with widening primitive conversion in some invocation contexts. Varargs is considered only after no fixed-arity candidate worked.</p>
<p>A common trap is expecting <code>int</code> to become <code>Long</code>. Java can widen <code>int</code> to <code>long</code>, or box <code>int</code> to <code>Integer</code>, but it does not widen to <code>long</code> and then box to <code>Long</code> as a single overload conversion.</p>
</td>
<td valign="top" width="50%">
<p>Строгий вызов разрешает идентичность и расширяющие преобразования примитивов и ссылок, но не упаковка. Нестрогий вызов добавляет упаковка и распаковке, а в некоторых контекстах вызова может сочетать распаковке с расширяющим преобразованием примитива. Varargs рассматривается только после того, как кандидат с фиксированным числом аргументов не найден.</p>
<p>Частая ловушка — ожидать, что <code>int</code> станет <code>Long</code>. Java может widen <code>int</code> к <code>long</code> или box <code>int</code> к <code>Integer</code>, но не делает widen к <code>long</code> и потом box к <code>Long</code> как единое преобразование для перегрузки.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Avoid overloads that differ only by primitive/wrapper forms or by fixed versus varargs forms. They are easy to misunderstand and can become unstable when another overload is added. In performance-sensitive code, also remember that a selected boxing overload allocates or reuses wrapper objects and may introduce null-unboxing risks later.</p>
</td>
<td valign="top" width="50%">
<p>Избегайте перегрузки, которые отличаются только формами примитивов и обёрток или формами с фиксированным числом аргументов и varargs. Их легко неправильно понять, и они становятся нестабильными при добавлении ещё одного перегрузка. В чувствительном к производительности коде также помните, что выбранный перегрузка с упаковкой создаёт или переиспользует объекты-обёртки и может добавить null-риски распаковки null позже.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Widening primitive conversion is preferred before boxing.</li>
<li>There is no general <code>int -> long -> Long</code> method-invocation conversion.</li>
<li>Varargs overloads are last-resort candidates and can hide allocation or ambiguity.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Widening примитив преобразование предпочитается перед упаковка.</li>
<li>Нет общего преобразования при вызове метода <code>int -> long -> Long</code>.</li>
<li>Varargs перегрузки — кандидаты последней очереди и могут скрывать выделение памяти или неоднозначность.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: In overload resolution, what generally wins: widening, boxing, or varargs?<br>A: Widening first, then boxing/unboxing, then varargs.</p>
</td>
<td valign="top" width="50%">
<p>Q: В разрешение перегрузки что обычно выигрывает: расширение, упаковка или varargs?<br>A: Сначала расширение, затем упаковкой/распаковкой, затем varargs.</p>
</td>
</tr>

<a id="jcore-type-024"></a>

<details>
<summary><strong>JCORE-TYPE-024. Why are overloaded methods resolved at compile time while overridden methods are resolved at runtime?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Overloading chooses between different method signatures, so the compiler must pick a signature using the compile-time types of the call. Overriding chooses an implementation for the already-selected signature, so the JVM can dispatch dynamically based on the actual receiver object at runtime.</p>
</td>
<td valign="top" width="50%">
<p>Overloading выбирает между разными сигнатурами методов, поэтому компилятор должен выбрать сигнатура по статические типы вызова. Overriding выбирает реализация для уже выбранной сигнатура, поэтому JVM может динамически выбрать реализацию по фактического объекта-получателя в время выполнения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Overloaded methods are separate methods with the same name but different parameter lists. The compiler has to decide which descriptor the call refers to before bytecode is generated. That decision is static.</p>
<p>Overridden instance methods share a compatible signature across an inheritance hierarchy. Bytecode can encode a virtual call to that signature, and at runtime the JVM chooses the implementation from the actual class of the receiver. This is dynamic dispatch and is the basis of polymorphism.</p>
</td>
<td valign="top" width="50%">
<p>Перегруженные методы — это отдельные методы с одинаковым именем, но разными списками параметров. Компилятор должен решить, к какому дескриптору относится вызов, до генерации байткода. Это статическое решение.</p>
<p>Переопределённые методы экземпляра имеют совместимую сигнатура в иерархии наследования. Байткод может закодировать virtual call к этой сигнатура, а в время выполнения JVM выбирает реализация из фактический класс получателя. Это динамическая диспетчеризация и основа полиморфизм.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Consider <code>void f(Object)</code> and <code>void f(String)</code>. If the argument variable is declared as <code>Object</code>, the compiler selects <code>f(Object)</code>. If that selected method is overridden in a subclass, runtime dispatch may choose the subclass implementation of <code>f(Object)</code>, but it will not switch to <code>f(String)</code> just because the argument object is actually a <code>String</code>.</p>
<p>Static methods are hidden, not overridden, so they are also selected statically. Private methods and constructors are not overridden either. Instance method overriding is the runtime-polymorphic case.</p>
</td>
<td valign="top" width="50%">
<p>Рассмотрим <code>void f(Object)</code> и <code>void f(String)</code>. Если переменная-аргумент объявлена как <code>Object</code>, компилятор выбирает <code>f(Object)</code>. Если этот выбранный метод переопределённые в подкласс, диспетчеризация во время выполнения может выбрать подкласс реализация of <code>f(Object)</code>, но не переключится на <code>f(String)</code> только потому, что объект-аргумент фактически <code>String</code>.</p>
<p>Static методы скрываются, а не переопределённые, поэтому тоже выбираются статически. Private-методы и конструкторы тоже не переопределённые. Instance метод переопределение — это случай полиморфизма времени выполнения.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>This distinction matters for API design and debugging. Overloads can make behavior depend on the static type visible at the call site, while overrides make behavior depend on the runtime receiver. When behavior should vary by object type, prefer polymorphism; when using overloads, keep call sites explicit and avoid overloads that pretend to be dynamic multi-dispatch.</p>
</td>
<td valign="top" width="50%">
<p>Это различие важно для дизайна API и отладки. Перегрузки могут делать поведение зависимым от статического типа, видимого в месте вызова, а переопределения делают поведение зависимым от получателя во время выполнения. Когда поведение должно меняться по типу объекта, предпочитайте полиморфизм; при использовании перегрузки делайте места вызова явными и избегайте перегрузок, которые выглядят как динамический multidispatch.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Overloading is not dynamic dispatch on argument runtime types.</li>
<li>Overriding dispatches only on the receiver, not on all arguments.</li>
<li>Static methods are hidden, not overridden, so they do not participate in virtual dispatch.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Overloading — не динамическая диспетчеризация по фактические типы аргументов.</li>
<li>Overriding dispatches только по receiver, а не по всем аргументы.</li>
<li>Static методы hidden, not переопределённые, поэтому не участвуют в виртуальной диспетчеризации.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is selected statically and what is selected dynamically?<br>A: Overload signature is selected statically; overridden instance-method implementation is selected dynamically by receiver type.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что выбирается статически, а что динамически?<br>A: Overload сигнатура выбирается статически; реализация переопределённого метода экземпляра выбирается динамически по тип получателя.</p>
</td>
</tr>
