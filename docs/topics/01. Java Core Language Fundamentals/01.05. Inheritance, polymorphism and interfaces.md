# 5. Inheritance, polymorphism and interfaces


<a id="jcore-oop-001"></a>

<details>
<summary><strong>JCORE-OOP-001. What is the difference between overloading and overriding?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Overloading means multiple methods have the same name but different parameter lists, and the compiler chooses one at compile time. Overriding means a subclass provides a new implementation of an inherited instance method with a compatible signature, and the JVM chooses the implementation at runtime by receiver type.</p>
</td>
<td valign="top" width="50%">

<p>Перегрузка методов (overloading) — это несколько методов с одним именем, но разными параметрами; нужная сигнатура выбирается компилятором. Переопределение методов (overriding) — это реализация унаследованного экземплярного метода в подклассе; конкретная реализация выбирается во время выполнения по фактическому типу объекта.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Overloading is about API convenience: <code>find(id)</code>, <code>find(email)</code>, <code>find(id, lockMode)</code>. The selected signature depends on the compile-time types of arguments, overload resolution rules, widening, boxing and varargs.</p>
<p>Overriding is about polymorphism. If <code>Animal a = new Dog(); a.speak();</code>, Java invokes <code>Dog.speak()</code> if <code>Dog</code> overrides the instance method. Return types may be covariant, and the overriding method cannot reduce visibility or throw broader checked exceptions.</p>
</td>
<td valign="top" width="50%">

<p>При перегрузке компилятор смотрит на имя метода, количество и типы аргументов, применяет правила расширения, упаковки и varargs и выбирает наиболее подходящую сигнатуру. Возвращаемый тип сам по себе не перегружает метод.</p>
<p>При переопределении подкласс предоставляет метод с совместимой сигнатурой. Если вызов идёт через ссылку базового типа, JVM всё равно вызывает реализацию фактического класса объекта. Именно это даёт полиморфизм для экземплярных методов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Static methods are not overridden; they are hidden. Private methods are not overridden either because they are not inherited in the overriding sense. Final methods cannot be overridden.</p>
<p>Overloading and overriding can combine, which makes APIs confusing. A subclass can override one signature and overload another. The compile-time overload is chosen first, then runtime dispatch applies only to the selected instance-method signature.</p>
</td>
<td valign="top" width="50%">

<p>Статические методы не переопределяются, а скрываются. <code>private</code>-методы тоже не участвуют в переопределении, потому что не наследуются как точка динамической диспетчеризации. <code>final</code>-метод нельзя переопределить.</p>
<p>Переопределённый метод может иметь ковариантный возвращаемый тип, то есть вернуть более конкретный тип. Параметры при этом не становятся «ковариантными»: изменение параметров создаёт перегрузку, а не переопределение.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production APIs, avoid overload sets that differ only by similar reference types, boxed/primitives, or nullable arguments. Use clear method names or parameter objects when overload resolution could surprise readers.</p>
</td>
<td valign="top" width="50%">

<p>В API перегрузки удобны, но их легко сделать неоднозначными, особенно с <code>null</code>, varargs и упаковкой. Переопределение — основа расширяемости, поэтому важно явно использовать <code>@Override</code>, чтобы компилятор ловил ошибки сигнатуры.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Overloading is compile-time; overriding is runtime for instance methods.</li>
<li>Static methods are hidden, not overridden.</li>
<li>Private and final methods are not overridden.</li>
<li>Overload resolution can select a different method than a reader expects.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Метод нельзя перегрузить только возвращаемым типом.</li>
<li>Изменение параметров при «переопределении» на самом деле создаёт перегрузку.</li>
<li>Статические методы скрываются, а не переопределяются.</li>
<li><code>@Override</code> помогает обнаружить ошибочную сигнатуру.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Which is resolved at runtime: overloading or overriding?<br>A: Overriding of instance methods is resolved at runtime; overloading is resolved at compile time.</p>
</td>
<td valign="top" width="50%">

<p>Q: Главное отличие перегрузки от переопределения?<br>A: Перегрузка выбирается на этапе компиляции по параметрам, переопределение — во время выполнения по фактическому типу объекта.</p>

</td>
</tr>
</tbody>
</table>
</details>


<a id="jcore-oop-002"></a>

<details>
<summary><strong>JCORE-OOP-002. How does dynamic dispatch work in Java?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Dynamic dispatch means that an overridden instance method call is selected at runtime based on the actual class of the receiver object, not only the variable’s compile-time type. This is the mechanism behind Java polymorphism.</p>
</td>
<td valign="top" width="50%">

<p>Динамическая диспетчеризация означает, что вызов переопределённого экземплярного метода выбирается во время выполнения по фактическому классу объекта-получателя, а не только по типу переменной. Поэтому ссылка типа <code>Animal</code> может вызвать реализацию <code>Dog</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The compiler checks that the method exists on the compile-time type and emits a call for that method signature. At runtime, for virtual/interface calls, the JVM chooses the most specific overriding implementation available on the receiver’s actual class.</p>
<p>Example: <code>Payment p = new CardPayment(); p.authorize();</code>. The call is legal because <code>Payment</code> declares <code>authorize()</code>, but the implementation invoked is <code>CardPayment.authorize()</code> if it overrides that method.</p>
</td>
<td valign="top" width="50%">

<p>Компилятор сначала проверяет, что метод доступен у статического типа ссылки. Но если метод экземплярный и переопределяемый, окончательная реализация выбирается JVM по реальному объекту. Это и есть обычный полиморфизм во время выполнения (runtime polymorphism) в Java.</p>
<p>Например, <code>Animal a = new Dog(); a.speak();</code> компилируется против типа <code>Animal</code>, но во время выполнения вызывает <code>Dog.speak()</code>, если метод переопределён.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Dynamic dispatch does not apply to fields, constructors, private methods, static methods or overload selection. Fields are resolved by compile-time type; constructors are not inherited; private methods are not overridden; static methods are hidden.</p>
<p>The JVM can optimize dynamic dispatch heavily using inline caches, class hierarchy analysis and JIT inlining, while preserving the language semantics. In normal code, write for clarity and let the JVM optimize.</p>
</td>
<td valign="top" width="50%">

<p>Динамическая диспетчеризация применяется к экземплярным методам, но не к полям, конструкторам, статическим методам и <code>private</code>-методам. Перегрузка выбирает сигнатуру раньше — на этапе компиляции; уже выбранная сигнатура затем может быть переопределена и вызвана динамически.</p>
<p>Во время конструирования динамическая диспетчеризация тоже работает, что делает вызов переопределяемых методов из конструктора опасным: подкласс ещё может быть не готов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Dynamic dispatch enables strategy objects, framework callbacks, proxies and dependency injection. It also means calling overridable methods from constructors or from partially initialized lifecycle code can execute subclass behavior earlier than expected.</p>
</td>
<td valign="top" width="50%">

<p>Динамическая диспетчеризация полезна для интерфейсов, стратегий и расширяемого поведения. Но в больших иерархиях она усложняет понимание потока выполнения, поэтому дизайн должен явно показывать точки расширения и защищать инварианты базового класса.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>The receiver runtime type matters only after the compile-time signature is selected.</li>
<li>Fields are not dynamically dispatched.</li>
<li>Static methods are not dynamically dispatched.</li>
<li>Constructor calls are not polymorphic, but method calls made inside constructors can be.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Поля не являются полиморфными: доступ к полю выбирается по статическому типу.</li>
<li>Статические методы не участвуют в динамической диспетчеризации.</li>
<li>Перегрузка выбирается до runtime, переопределение — во время выполнения.</li>
<li>Вызов переопределяемого метода из конструктора может увидеть неготовый подкласс.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: In <code>Base b = new Sub(); b.m();</code>, which <code>m()</code> runs if <code>m</code> is overridden?<br>A: The implementation in <code>Sub</code>, selected by the receiver’s runtime type.</p>
</td>
<td valign="top" width="50%">

<p>Q: По чему Java выбирает реализацию переопределённого метода?<br>A: По фактическому классу объекта-получателя во время выполнения.</p>

</td>
</tr>
</tbody>
</table>
</details>


<a id="jcore-oop-003"></a>

<details>
<summary><strong>JCORE-OOP-003. Why are static methods not polymorphic?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Static methods belong to the class, not to an object instance, so there is no receiver object whose runtime type could drive dynamic dispatch. If a subclass declares a static method with the same signature, it hides the superclass method; calls are resolved by compile-time type.</p>
</td>
<td valign="top" width="50%">

<p>Статические методы не полиморфны, потому что принадлежат классу, а не экземпляру. Вызов статического метода связывается с типом, известным компилятору; метод с такой же сигнатурой в подклассе скрывает родительский метод, но не переопределяет его.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Polymorphic overriding works for instance methods because the call has a receiver: <code>obj.method()</code>. A static call is conceptually <code>Type.method()</code>. Even when Java allows <code>obj.staticMethod()</code>, that syntax is misleading; the declared type of <code>obj</code> determines the method.</p>
<p>This is why static methods cannot be abstract and cannot be overridden. They can be overloaded, and same-signature static methods in subclasses are method hiding, not overriding.</p>
</td>
<td valign="top" width="50%">

<p>Если написать <code>Base b = new Child(); b.staticMethod();</code>, выбор будет сделан по типу <code>Base</code>, а не по фактическому объекту <code>Child</code>. Поэтому статические методы лучше вызывать через имя класса: <code>Base.staticMethod()</code>.</p>
<p>Такое поведение называется скрытием метода (method hiding). Оно похоже внешне на переопределение, но не использует динамическую диспетчеризацию.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If <code>Base b = new Sub(); b.util();</code> and <code>util</code> is static in both classes, the <code>Base</code> version is chosen because <code>b</code> has compile-time type <code>Base</code>. The runtime object <code>new Sub()</code> does not matter.</p>
<p>Java 8 added static methods in interfaces, but they are still not inherited like instance methods. They are called through the interface name and are mainly utility/factory methods related to the interface.</p>
</td>
<td valign="top" width="50%">

<p>Статический метод может быть объявлен в подклассе с той же сигнатурой, если правила доступа и возвращаемого типа соблюдены. Но аннотация <code>@Override</code> для такого метода не сработает, потому что это не переопределение.</p>
<p>Полиморфизм требует объекта-получателя. У статического метода получателя нет: он вызывается как член класса, поэтому JVM не ищет реализацию по фактическому типу объекта.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Do not design extension points as static methods. Use interfaces, instance methods, dependency injection or strategy objects. Static methods are fine for stateless helpers and factories where polymorphic replacement is not part of the design.</p>
</td>
<td valign="top" width="50%">

<p>В рабочем коде статические методы подходят для чистых утилит или фабрик, но не для поведения, которое должно меняться по реализации. Для полиморфного поведения используйте экземплярные методы, интерфейсы или стратегии.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Calling static methods through instances is legal but misleading.</li>
<li>Subclass static methods hide superclass static methods.</li>
<li>Static interface methods must be called through the interface name.</li>
<li>Mocks/proxies generally intercept instance behavior, not static dispatch, unless special tooling is used.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Вызов статического метода через объект компилируется, но ухудшает читаемость.</li>
<li>Статический метод в подклассе скрывает, а не переопределяет метод родителя.</li>
<li><code>@Override</code> не применяется к скрытию статических методов.</li>
<li>Статические методы не могут быть абстрактными в обычном смысле полиморфного контракта.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What determines which static method is called?<br>A: The compile-time type or explicit class/interface name, not the runtime object type.</p>
</td>
<td valign="top" width="50%">

<p>Q: Почему статический метод не полиморфен?<br>A: У него нет объектного получателя; выбор делается по типу, известному на этапе компиляции.</p>

</td>
</tr>
</tbody>
</table>

<a id="jcore-oop-004"></a>

<details>
<summary><strong>JCORE-OOP-004. When should you use an interface instead of an abstract class?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use an interface when you want to define a capability or contract that many unrelated classes can implement. Use an abstract class when you need shared state, constructor logic, protected hooks, or a partial implementation tightly coupled to a class hierarchy.</p>
</td>
<td valign="top" width="50%">

<p>Интерфейс лучше использовать, когда нужен контракт, который могут реализовать разные иерархии классов. Абстрактный класс лучше подходит, когда кроме контракта нужна общая реализация, состояние, конструкторы или <code>protected</code>-хуки.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Interfaces are better for roles: <code>Repository</code>, <code>Clock</code>, <code>PaymentGateway</code>, <code>Validator</code>. A class can implement multiple interfaces, which keeps designs flexible and testable.</p>
<p>Abstract classes are better for common base implementation: shared fields, template methods, constructor-enforced invariants, or code reuse for a narrow family of related classes. But Java has single class inheritance, so choosing an abstract base class consumes the one superclass slot.</p>
</td>
<td valign="top" width="50%">

<p>Интерфейс задаёт «что объект умеет», не заставляя наследоваться от конкретного базового класса. Класс может реализовать несколько интерфейсов, поэтому интерфейсы удобны для API, стратегий, адаптеров и тестируемых зависимостей.</p>
<p>Абстрактный класс задаёт более сильную связь. Он полезен, когда нужен общий код, поля, инварианты и контролируемый путь конструирования. Но из-за одиночного наследования классов он занимает единственное место базового класса у наследника.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Modern interfaces can have default and static methods, but they still cannot have instance fields or constructors. Default methods should support evolution or small reusable behavior, not turn interfaces into stateful base classes.</p>
<p>A useful rule is “interface for type, abstract class for skeletal implementation”. The JDK uses this pattern, for example collection interfaces plus abstract skeletal classes.</p>
</td>
<td valign="top" width="50%">

<p>После Java 8 интерфейсы могут иметь методы по умолчанию и статические методы, а позже — <code>private</code>-вспомогательные методы. Но интерфейс всё равно не заменяет абстрактный класс, если нужно состояние экземпляра или конструктор.</p>
<p>Если сомневаетесь, чаще начинайте с интерфейса и композиции. Абстрактный класс выбирайте, когда общая реализация действительно существенна и вы готовы поддерживать эту иерархию как часть дизайна.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In backend services, interfaces improve testing, proxying and module boundaries. Abstract classes are useful inside frameworks or domain hierarchies, but overusing them can lead to fragile base-class problems and hard-to-change inheritance.</p>
</td>
<td valign="top" width="50%">

<p>В серверном коде интерфейсы удобны для границ модулей, портов, клиентов внешних сервисов и тестовых заглушек. Абстрактные классы уместны для фреймворкового кода и шаблонного метода, но в доменной модели часто лучше избегать глубоких иерархий.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>A class can implement many interfaces but extend only one class.</li>
<li>Interfaces should not become dumping grounds for unrelated methods.</li>
<li>Abstract base classes can accidentally expose protected mutable state.</li>
<li>Default methods do not make interfaces equivalent to abstract classes.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Методы по умолчанию не означают, что интерфейс стал полноценным базовым классом.</li>
<li>Абстрактный класс может навязать наследникам состояние и порядок инициализации.</li>
<li>Класс может реализовать много интерфейсов, но наследоваться только от одного класса.</li>
<li>Не используйте абстрактный класс только ради группировки методов без общего состояния или инвариантов.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the usual rule of thumb: interface or abstract class?<br>A: Interface for a contract/capability; abstract class for shared state or skeletal implementation.</p>
</td>
<td valign="top" width="50%">

<p>Q: Когда выбрать интерфейс вместо абстрактного класса?<br>A: Когда нужен контракт для разных реализаций без общей базовой реализации и состояния.</p>

</td>
</tr>
</tbody>

<a id="jcore-oop-005"></a>

<details>
<summary><strong>JCORE-OOP-005. What are default methods in interfaces, and why were they added?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Default methods are interface methods with a body, declared with <code>default</code>. They were added mainly to evolve interfaces without breaking existing implementors, such as adding new operations to library interfaces while providing a fallback implementation.</p>
</td>
<td valign="top" width="50%">

<p>Метод по умолчанию — это метод интерфейса с реализацией. Его добавили, чтобы развивать существующие интерфейсы без поломки всех реализаций и чтобы поддержать новые API вроде Collections и Streams в Java 8.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Before default methods, adding an abstract method to an interface broke every implementing class. Java 8 needed a way to add methods such as stream-related helpers to existing collection interfaces while preserving source and binary compatibility as much as possible.</p>
<p>A default method is inherited by implementing classes unless the class overrides it or another rule selects a more specific method. Implementations can call a particular default via <code>InterfaceName.super.method()</code>.</p>
</td>
<td valign="top" width="50%">

<p>До появления методов по умолчанию добавление нового абстрактного метода в публичный интерфейс ломало все классы, которые его реализуют. Метод по умолчанию позволяет добавить поведение с базовой реализацией, а реализации могут переопределить его при необходимости.</p>
<p>Это особенно помогло развить стандартные интерфейсы коллекций: можно было добавить методы вроде <code>forEach</code> или <code>removeIf</code>, не заставляя переписать весь существующий код.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Default methods are instance methods. They cannot hold per-instance state in the interface. They can call other interface methods, including abstract methods, which lets a default method express behavior in terms of the contract.</p>
<p>They also introduce multiple-inheritance-of-behavior issues. Java resolves many cases with “class wins” and “more specific interface wins”, but if unrelated interfaces provide conflicting defaults, the implementing class must override.</p>
</td>
<td valign="top" width="50%">

<p>Методы по умолчанию участвуют в наследовании интерфейсов, но правила конфликтов строго определены. Метод класса имеет приоритет над методом по умолчанию интерфейса. Более специфичный интерфейс имеет приоритет над более общим. Если конфликт остаётся, класс обязан явно переопределить метод.</p>
<p>Метод по умолчанию не должен превращать интерфейс в хранилище состояния. Он лучше подходит для поведения, которое можно выразить через другие методы интерфейса.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use default methods for small, stable behavior that naturally belongs to the interface. Avoid putting heavy logic, IO, state assumptions or framework-specific behavior into default methods, because every implementor inherits it.</p>
</td>
<td valign="top" width="50%">

<p>При проектировании API методы по умолчанию полезны для обратной совместимости и удобных вспомогательных операций. Но не стоит добавлять в них тяжёлую логику, скрытые зависимости или поведение, которое неожиданно меняет семантику старых реализаций.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Default methods are not a substitute for stateful base classes.</li>
<li>Adding a default method can still create conflicts for classes implementing multiple interfaces.</li>
<li>A class method beats an interface default method.</li>
<li>Default behavior should not rely on hidden implementation details.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Метод по умолчанию можно переопределить в классе реализации.</li>
<li>Методы по умолчанию могут конфликтовать при множественном наследовании интерфейсов.</li>
<li>Метод класса выигрывает у метода по умолчанию интерфейса.</li>
<li>Метод по умолчанию не даёт интерфейсу обычных полей экземпляра.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why were default methods added?<br>A: To let interfaces evolve by adding methods with default implementations without forcing every implementor to change immediately.</p>
</td>
<td valign="top" width="50%">

<p>Q: Зачем добавили методы по умолчанию?<br>A: Чтобы добавлять методы в интерфейсы с базовой реализацией без массовой поломки существующих реализаций.</p>

<details>
<summary><strong>JCORE-OOP-006. What happens if two interfaces provide conflicting default methods?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If a class implements two unrelated interfaces that provide the same default method signature, Java requires the class to override the method and resolve the conflict. The override can choose one default explicitly with <code>InterfaceName.super.method()</code> or provide a new implementation.</p>
</td>
<td valign="top" width="50%">

<p>Если два интерфейса дают конфликтующие методы по умолчанию, Java сначала применяет правила приоритета: метод класса выигрывает у интерфейса, более специфичный интерфейс выигрывает у более общего. Если однозначного победителя нет, класс должен явно переопределить метод.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Java has rules to avoid ambiguity. First, class methods win over interface default methods. Second, a more specific subinterface default wins over a less specific superinterface default. If neither rule resolves the conflict, the implementing class must override.</p>
<p>This makes multiple inheritance of behavior explicit at conflict points. The compiler does not guess which business behavior you intended.</p>
</td>
<td valign="top" width="50%">

<p>Класс не может молча унаследовать две равноправные реализации одного метода по умолчанию. Он обязан написать свою реализацию и, если нужно, явно вызвать одну из версий через <code>InterfaceName.super.method()</code>.</p>
<p>Это правило сохраняет предсказуемость. В отличие от некоторых языков с множественным наследованием реализации, Java не пытается угадать, какой метод по умолчанию имелся в виду.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Example: if <code>Auditable</code> and <code>Trackable</code> both define <code>default String label()</code>, then <code>class Order implements Auditable, Trackable</code> must implement <code>label()</code>. Inside it, the class may call <code>Auditable.super.label()</code>.</p>
<p>If a superclass already has an instance method with the same signature, that method wins, including methods inherited from <code>Object</code>. Interfaces cannot use default methods to provide override-equivalent defaults for core <code>Object</code> methods such as <code>equals</code> and <code>hashCode</code>.</p>
</td>
<td valign="top" width="50%">

<p>Если суперкласс уже содержит конкретный метод с такой сигнатурой, он имеет приоритет над методами по умолчанию интерфейсов. Если один интерфейс наследует другой и переопределяет метод по умолчанию, более специфичный вариант выигрывает.</p>
<p>Конфликт может возникнуть и между методом по умолчанию и абстрактным методом из другого интерфейса. В сомнительных случаях лучше явно переопределить метод и сделать выбор видимым в коде.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In API design, avoid default methods with very broad names in widely implemented interfaces. A new default method can accidentally conflict with existing interfaces or class methods in client code.</p>
</td>
<td valign="top" width="50%">

<p>В командном коде явное переопределение при конфликте — хороший сигнал для читателя. Оно показывает, какая семантика выбрана, и защищает от сюрпризов при изменении интерфейсов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Unrelated interface defaults with the same signature require an explicit override.</li>
<li>A class method wins over interface defaults.</li>
<li>A more specific interface wins over a less specific one.</li>
<li><code>InterfaceName.super.method()</code> works only from an implementing class or subinterface context.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Две равноправные реализации по умолчанию требуют явного переопределения.</li>
<li>Вызвать конкретную реализацию по умолчанию можно через <code>SomeInterface.super.method()</code>.</li>
<li>Метод суперкласса имеет приоритет над методом по умолчанию интерфейса.</li>
<li>Более специфичный интерфейс выигрывает у более общего.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: How does Java handle two unrelated conflicting default methods?<br>A: The implementing class must override the method and resolve the conflict explicitly.</p>
</td>
<td valign="top" width="50%">

<p>Q: Что делать при конфликте двух методов по умолчанию?<br>A: Явно переопределить метод в классе и при необходимости вызвать выбранную реализацию через <code>InterfaceName.super.method()</code>.</p>

<details>
<summary><strong>🧠 JCORE-OOP-007. What inheritance-related problems can appear when implementing <code>equals()</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Inheritance makes <code>equals()</code> hard because subclasses can add state and break symmetry or transitivity. A superclass and subclass may disagree about whether they are equal, especially when one uses <code>instanceof</code> and the other uses additional fields or stricter class checks.</p>
</td>
<td valign="top" width="50%">

<p>Главная проблема <code>equals()</code> в иерархиях наследования — сохранить симметричность и транзитивность, когда подкласс добавляет новые поля. Сравнение через <code>instanceof</code> допускает равенство с подклассами, а сравнение через <code>getClass()</code> запрещает его; оба подхода имеют свои компромиссы.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Suppose <code>Point</code> compares <code>x</code> and <code>y</code>, and <code>ColorPoint</code> adds <code>color</code>. If <code>Point.equals()</code> accepts any <code>Point</code>, then a plain point may consider itself equal to a color point. But the color point may require matching color, so symmetry breaks.</p>
<p>Using <code>getClass()</code> avoids equality between superclass and subclass, preserving symmetry, but it makes equality strict by runtime class. That can be awkward with ORM proxies. Using <code>instanceof</code> supports subtype equality but is safe mostly when subclasses cannot add significant equality state or when a pattern like <code>canEqual</code> is used carefully.</p>
</td>
<td valign="top" width="50%">

<p>Если базовый класс сравнивает только свои поля, а подкласс добавляет новое значимое поле, легко получить нарушение контракта. Например, <code>Point</code> может считать равным <code>ColorPoint</code> по координатам, а <code>ColorPoint</code> не считать равным <code>Point</code>, потому что у него есть ещё цвет.</p>
<p>Поэтому для расширяемых классов <code>equals()</code> проектировать сложно. Часто безопаснее сделать класс <code>final</code>, использовать композицию вместо наследования или сравнивать точный класс через <code>getClass()</code>, если равенство между подклассами не нужно.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The safest design is often to make value classes final or use records, so equality cannot be complicated by subclasses. For non-final hierarchies, decide whether equality is identity-based, class-strict, or deliberately extensible, and document it.</p>
<p>Entities add another complication: generated identifiers, lazy proxies and lifecycle states can interact badly with equality. Inheritance amplifies those problems because proxy subclasses may not equal the real entity class under <code>getClass()</code>.</p>
</td>
<td valign="top" width="50%">

<p><code>instanceof</code> поддерживает равенство между базовым типом и подклассом, но может сломать симметричность, когда подкласс сужает смысл равенства. <code>getClass()</code> сохраняет строгую проверку типа, но делает равенство более жёстким: объекты разных подклассов никогда не равны, даже если их состояние совпадает.</p>
<p>Существуют шаблоны вроде <code>canEqual</code>, но они усложняют код. В большинстве прикладных моделей проще избегать наследования для объектов-значений или явно закрывать иерархию.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Prefer final immutable value objects for equality-heavy types. Avoid adding equality-relevant state in subclasses unless the base class was designed for it. For ORM entities, follow the framework/team equality strategy consistently.</p>
</td>
<td valign="top" width="50%">

<p>Для DTO, <code>record</code> и объектов-значений обычно лучше использовать <code>final</code>-классы, <code>record</code> или композицию. Для JPA-сущностей правила равенства нужно проектировать отдельно: прокси, идентификаторы и жизненный цикл сущности добавляют свои ограничения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Subclass equality can violate symmetry.</li>
<li>Subclass equality can violate transitivity.</li>
<li><code>getClass()</code> can conflict with proxy subclasses.</li>
<li><code>instanceof</code> can be wrong if subclasses add significant state.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Подкласс, добавивший поле, может нарушить симметричность <code>equals()</code>.</li>
<li><code>getClass()</code> плохо сочетается с некоторыми прокси ORM.</li>
<li><code>instanceof</code> может быть слишком широким для объектов-значений.</li>
<li>При изменении <code>equals()</code> всегда проверяйте согласованность с <code>hashCode()</code>.</li>
</ul>

</td>

<th colspan="2" align="left">Optional Anki</th>

<details>
<summary><strong>JCORE-OOP-008. What is method hiding, and how is it different from overriding?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Method hiding happens when a subclass declares a static method with the same signature as a static method in a superclass. The selected method is based on the compile-time type. Overriding applies to instance methods, and the selected implementation is based on the runtime receiver type.</p>
</td>
<td valign="top" width="50%">

<p>Скрытие метода (method hiding) относится к статическим методам: метод подкласса с той же сигнатурой скрывает статический метод суперкласса, а выбор делается по статическому типу ссылки. Переопределение относится к экземплярным методам, и реализация выбирается во время выполнения по фактическому типу объекта.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>With overriding, <code>Base b = new Sub(); b.run();</code> calls <code>Sub.run()</code> if <code>run</code> is an overridden instance method. With hiding, <code>Base b = new Sub(); b.util();</code> calls <code>Base.util()</code> if <code>util</code> is static.</p>
<p>Fields can also be hidden by fields with the same name in subclasses. Like static methods, fields are resolved using the compile-time type, not dynamically dispatched.</p>
</td>
<td valign="top" width="50%">

<p>При переопределении <code>Base b = new Child(); b.run();</code> вызывает <code>Child.run()</code>, если <code>run()</code> — экземплярный переопределённый метод. При скрытии <code>b.staticRun()</code> связывается с <code>Base.staticRun()</code>, потому что статический метод выбирается компилятором.</p>
<p>Именно поэтому статические методы следует вызывать через имя класса. Тогда читателю ясно, что полиморфизма здесь нет.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The compiler enforces consistency: an instance method cannot override a static method, and a static method cannot hide an instance method with the same signature. Return types and visibility still have compatibility rules.</p>
<p>Hiding is rarely a good design tool. It can be useful for class-specific factories or utilities, but it often confuses readers because the syntax looks like polymorphism while the semantics are static.</p>
</td>
<td valign="top" width="50%">

<p>Скрывающий статический метод должен соблюдать совместимые правила доступа и возвращаемого типа. Но он не участвует в таблице виртуальных вызовов и не может быть отмечен как <code>@Override</code>.</p>
<p>Поля ведут себя ближе к скрытию, чем к переопределению: поле с тем же именем в подклассе скрывает поле родителя, а доступ к полю определяется статическим типом выражения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Avoid naming static methods in subclasses as if they were polymorphic replacements. Call static methods through class names, not instances, and use instance methods or interfaces for behavior that must vary by runtime type.</p>
</td>
<td valign="top" width="50%">

<p>Скрытие методов редко нужно как осознанный дизайн. В API оно часто запутывает, особенно если статический метод вызывают через объект. Лучше использовать разные имена или явно вызывать статический метод через класс.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Method hiding applies to static methods, overriding to instance methods.</li>
<li>Hidden static method selection uses compile-time type.</li>
<li>Field hiding follows compile-time type too.</li>
<li>Calling hidden static methods through instances is especially confusing.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>@Override</code> не применяется к статическим методам.</li>
<li>Вызов статического метода через ссылку не делает его полиморфным.</li>
<li>Поля не переопределяются полиморфно.</li>
<li>Скрытие может создать впечатление переопределения, но результат будет выбран на этапе компиляции.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is selected by runtime type: hidden static method or overridden instance method?<br>A: Only the overridden instance method.</p>
</td>
<td valign="top" width="50%">

<p>Q: Чем скрытие метода отличается от переопределения?<br>A: Скрытие относится к статическим методам и выбирается по статическому типу, переопределение — к экземплярным методам и выбирается по фактическому типу объекта.</p>

<details>
<summary><strong>JCORE-OOP-009. What are covariant return types in overridden methods?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Covariant return types allow an overriding method to return a subtype of the return type declared by the overridden method. For example, if a superclass method returns <code>Animal</code>, an overriding subclass method may return <code>Dog</code>.</p>
</td>
<td valign="top" width="50%">

<p>Ковариантный возвращаемый тип означает, что переопределённый метод может возвращать более конкретный тип, чем метод суперкласса. Например, базовый метод возвращает <code>Animal</code>, а переопределённый в подклассе — <code>Dog</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>This improves type precision without breaking polymorphism. Code using a superclass reference can still treat the result as the broader type, while code using the subclass API can receive the narrower type without casting.</p>
<p>Covariant returns work only for reference types, because they rely on subtype relationships. They do not mean arbitrary return-type overloading; Java does not overload methods by return type alone.</p>
</td>
<td valign="top" width="50%">

<p>Это удобно, потому что сохраняет совместимость с контрактом родителя и одновременно даёт клиентам подкласса более точный тип без лишнего приведения. Метод всё ещё переопределяет родительский, если параметры и остальные правила сигнатуры совместимы.</p>
<p>Ковариантность применяется к возвращаемому типу, но не к параметрам. Если изменить тип параметра, получится перегрузка, а не переопределение.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The parameter list must still match the overridden method signature. The overriding method must respect access and checked-exception rules: it cannot reduce visibility and cannot declare broader checked exceptions.</p>
<p>A common use is fluent APIs and copy/factory methods. For example, a base builder method may return <code>Builder</code>, while a subclass builder narrows return type to <code>SpecialBuilder</code>.</p>
</td>
<td valign="top" width="50%">

<p>Возвращаемый тип должен быть тем же типом или подтипом исходного возвращаемого типа для ссылочных типов. Для примитивов такой ковариантности нет: нельзя переопределить метод, возвращающий <code>int</code>, методом, возвращающим <code>long</code>.</p>
<p>При обобщениях (generics) и стирании типов компилятор иногда создаёт мостовые методы (bridge methods), чтобы сохранить полиморфизм на уровне байткода. Обычно это деталь реализации, но она может быть видна в рефлексии или стеке вызовов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use covariant returns to improve API ergonomics when the subtype is truly guaranteed. Avoid complex hierarchies where fluent self-types become hard to reason about; generics may be clearer for advanced builder patterns.</p>
</td>
<td valign="top" width="50%">

<p>Ковариантные возвращаемые типы полезны в цепочных API (fluent API), builder, фабриках и методах копирования, где подкласс может вернуть свой более конкретный тип. Главное — не путать это с изменением параметров метода.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Return type alone cannot overload a method.</li>
<li>Covariant return requires a subtype relationship.</li>
<li>Primitive return types are not covariant.</li>
<li>Overriding rules for visibility and checked exceptions still apply.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Ковариантность относится к возвращаемому типу, а не к параметрам.</li>
<li>Для примитивных возвращаемых типов нельзя заменить <code>int</code> на <code>long</code> как ковариантный возврат.</li>
<li>Более конкретный тип должен быть подтипом исходного возвращаемого типа.</li>
<li>Изменение параметров создаёт перегрузку, даже если имя метода совпадает.</li>
</ul>

</td>
</tr>
