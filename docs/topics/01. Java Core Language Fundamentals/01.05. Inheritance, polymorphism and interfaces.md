# 01.05. Inheritance, polymorphism and interfaces

<a id="jcore-oop-001"></a>

<details>
<summary><strong>JCORE-OOP-001. What is the difference between overloading and overriding?</strong></summary>

#### Short answer

Overloading means multiple methods have the same name but different parameter lists, and the compiler chooses one at compile time. Overriding means a subclass provides a new implementation of an inherited instance method with a compatible signature, and the JVM chooses the implementation at runtime by receiver type.

#### Interview answer

Overloading is about API convenience: `find(id)`, `find(email)`, `find(id, lockMode)`. The selected signature depends on the compile-time types of arguments, overload resolution rules, widening, boxing and varargs.

Overriding is about polymorphism. If `Animal a = new Dog(); a.speak();`, Java invokes `Dog.speak()` if `Dog` overrides the instance method. Return types may be covariant, and the overriding method cannot reduce visibility or throw broader checked exceptions.

#### Deep dive

Static methods are not overridden; they are hidden. Private methods are not overridden either because they are not inherited in the overriding sense. Final methods cannot be overridden.

Overloading and overriding can combine, which makes APIs confusing. A subclass can override one signature and overload another. The compile-time overload is chosen first, then runtime dispatch applies only to the selected instance-method signature.

#### Production angle

In production APIs, avoid overload sets that differ only by similar reference types, boxed/primitives, or nullable arguments. Use clear method names or parameter objects when overload resolution could surprise readers.

#### Traps / caveats

- Overloading is compile-time; overriding is runtime for instance methods.
- Static methods are hidden, not overridden.
- Private and final methods are not overridden.
- Overload resolution can select a different method than a reader expects.

#### Optional Anki

Q: Which is resolved at runtime: overloading or overriding?
A: Overriding of instance methods is resolved at runtime; overloading is resolved at compile time.

</details>

<details>
<summary><strong>JCORE-OOP-002. How does dynamic dispatch work in Java?</strong></summary>

#### Short answer

Dynamic dispatch means that an overridden instance method call is selected at runtime based on the actual class of the receiver object, not only the variable’s compile-time type. This is the mechanism behind Java polymorphism.

#### Interview answer

The compiler checks that the method exists on the compile-time type and emits a call for that method signature. At runtime, for virtual/interface calls, the JVM chooses the most specific overriding implementation available on the receiver’s actual class.

Example: `Payment p = new CardPayment(); p.authorize();`. The call is legal because `Payment` declares `authorize()`, but the implementation invoked is `CardPayment.authorize()` if it overrides that method.

#### Deep dive

Dynamic dispatch does not apply to fields, constructors, private methods, static methods or overload selection. Fields are resolved by compile-time type; constructors are not inherited; private methods are not overridden; static methods are hidden.

The JVM can optimize dynamic dispatch heavily using inline caches, class hierarchy analysis and JIT inlining, while preserving the language semantics. In normal code, write for clarity and let the JVM optimize.

#### Production angle

Dynamic dispatch enables strategy objects, framework callbacks, proxies and dependency injection. It also means calling overridable methods from constructors or from partially initialized lifecycle code can execute subclass behavior earlier than expected.

#### Traps / caveats

- The receiver runtime type matters only after the compile-time signature is selected.
- Fields are not dynamically dispatched.
- Static methods are not dynamically dispatched.
- Constructor calls are not polymorphic, but method calls made inside constructors can be.

#### Optional Anki

Q: In `Base b = new Sub(); b.m();`, which `m()` runs if `m` is overridden?
A: The implementation in `Sub`, selected by the receiver’s runtime type.

</details>

<details>
<summary><strong>JCORE-OOP-003. Why are static methods not polymorphic?</strong></summary>

#### Short answer

Static methods belong to the class, not to an object instance, so there is no receiver object whose runtime type could drive dynamic dispatch. If a subclass declares a static method with the same signature, it hides the superclass method; calls are resolved by compile-time type.

#### Interview answer

Polymorphic overriding works for instance methods because the call has a receiver: `obj.method()`. A static call is conceptually `Type.method()`. Even when Java allows `obj.staticMethod()`, that syntax is misleading; the declared type of `obj` determines the method.

This is why static methods cannot be abstract and cannot be overridden. They can be overloaded, and same-signature static methods in subclasses are method hiding, not overriding.

#### Deep dive

If `Base b = new Sub(); b.util();` and `util` is static in both classes, the `Base` version is chosen because `b` has compile-time type `Base`. The runtime object `new Sub()` does not matter.

Java 8 added static methods in interfaces, but they are still not inherited like instance methods. They are called through the interface name and are mainly utility/factory methods related to the interface.

#### Production angle

Do not design extension points as static methods. Use interfaces, instance methods, dependency injection or strategy objects. Static methods are fine for stateless helpers and factories where polymorphic replacement is not part of the design.

#### Traps / caveats

- Calling static methods through instances is legal but misleading.
- Subclass static methods hide superclass static methods.
- Static interface methods must be called through the interface name.
- Mocks/proxies generally intercept instance behavior, not static dispatch, unless special tooling is used.

#### Optional Anki

Q: What determines which static method is called?
A: The compile-time type or explicit class/interface name, not the runtime object type.

</details>

<details>
<summary><strong>JCORE-OOP-004. When should you use an interface instead of an abstract class?</strong></summary>

#### Short answer

Use an interface when you want to define a capability or contract that many unrelated classes can implement. Use an abstract class when you need shared state, constructor logic, protected hooks, or a partial implementation tightly coupled to a class hierarchy.

#### Interview answer

Interfaces are better for roles: `Repository`, `Clock`, `PaymentGateway`, `Validator`. A class can implement multiple interfaces, which keeps designs flexible and testable.

Abstract classes are better for common base implementation: shared fields, template methods, constructor-enforced invariants, or code reuse for a narrow family of related classes. But Java has single class inheritance, so choosing an abstract base class consumes the one superclass slot.

#### Deep dive

Modern interfaces can have default and static methods, but they still cannot have instance fields or constructors. Default methods should support evolution or small reusable behavior, not turn interfaces into stateful base classes.

A useful rule is “interface for type, abstract class for skeletal implementation”. The JDK uses this pattern, for example collection interfaces plus abstract skeletal classes.

#### Production angle

In backend services, interfaces improve testing, proxying and module boundaries. Abstract classes are useful inside frameworks or domain hierarchies, but overusing them can lead to fragile base-class problems and hard-to-change inheritance.

#### Traps / caveats

- A class can implement many interfaces but extend only one class.
- Interfaces should not become dumping grounds for unrelated methods.
- Abstract base classes can accidentally expose protected mutable state.
- Default methods do not make interfaces equivalent to abstract classes.

#### Optional Anki

Q: What is the usual rule of thumb: interface or abstract class?
A: Interface for a contract/capability; abstract class for shared state or skeletal implementation.

</details>

<details>
<summary><strong>JCORE-OOP-005. What are default methods in interfaces, and why were they added?</strong></summary>

#### Short answer

Default methods are interface methods with a body, declared with `default`. They were added mainly to evolve interfaces without breaking existing implementors, such as adding new operations to library interfaces while providing a fallback implementation.

#### Interview answer

Before default methods, adding an abstract method to an interface broke every implementing class. Java 8 needed a way to add methods such as stream-related helpers to existing collection interfaces while preserving source and binary compatibility as much as possible.

A default method is inherited by implementing classes unless the class overrides it or another rule selects a more specific method. Implementations can call a particular default via `InterfaceName.super.method()`.

#### Deep dive

Default methods are instance methods. They cannot hold per-instance state in the interface. They can call other interface methods, including abstract methods, which lets a default method express behavior in terms of the contract.

They also introduce multiple-inheritance-of-behavior issues. Java resolves many cases with “class wins” and “more specific interface wins”, but if unrelated interfaces provide conflicting defaults, the implementing class must override.

#### Production angle

Use default methods for small, stable behavior that naturally belongs to the interface. Avoid putting heavy logic, IO, state assumptions or framework-specific behavior into default methods, because every implementor inherits it.

#### Traps / caveats

- Default methods are not a substitute for stateful base classes.
- Adding a default method can still create conflicts for classes implementing multiple interfaces.
- A class method beats an interface default method.
- Default behavior should not rely on hidden implementation details.

#### Optional Anki

Q: Why were default methods added?
A: To let interfaces evolve by adding methods with default implementations without forcing every implementor to change immediately.

</details>

<details>
<summary><strong>JCORE-OOP-006. What happens if two interfaces provide conflicting default methods?</strong></summary>

#### Short answer

If a class implements two unrelated interfaces that provide the same default method signature, Java requires the class to override the method and resolve the conflict. The override can choose one default explicitly with `InterfaceName.super.method()` or provide a new implementation.

#### Interview answer

Java has rules to avoid ambiguity. First, class methods win over interface default methods. Second, a more specific subinterface default wins over a less specific superinterface default. If neither rule resolves the conflict, the implementing class must override.

This makes multiple inheritance of behavior explicit at conflict points. The compiler does not guess which business behavior you intended.

#### Deep dive

Example: if `Auditable` and `Trackable` both define `default String label()`, then `class Order implements Auditable, Trackable` must implement `label()`. Inside it, the class may call `Auditable.super.label()`.

If a superclass already has an instance method with the same signature, that method wins, including methods inherited from `Object`. Interfaces cannot use default methods to provide override-equivalent defaults for core `Object` methods such as `equals` and `hashCode`.

#### Production angle

In API design, avoid default methods with very broad names in widely implemented interfaces. A new default method can accidentally conflict with existing interfaces or class methods in client code.

#### Traps / caveats

- Unrelated interface defaults with the same signature require an explicit override.
- A class method wins over interface defaults.
- A more specific interface wins over a less specific one.
- `InterfaceName.super.method()` works only from an implementing class or subinterface context.

#### Optional Anki

Q: How does Java handle two unrelated conflicting default methods?
A: The implementing class must override the method and resolve the conflict explicitly.

</details>

<details>
<summary><strong>🧠 JCORE-OOP-007. What inheritance-related problems can appear when implementing `equals()`?</strong></summary>

#### Short answer

Inheritance makes `equals()` hard because subclasses can add state and break symmetry or transitivity. A superclass and subclass may disagree about whether they are equal, especially when one uses `instanceof` and the other uses additional fields or stricter class checks.

#### Interview answer

Suppose `Point` compares `x` and `y`, and `ColorPoint` adds `color`. If `Point.equals()` accepts any `Point`, then a plain point may consider itself equal to a color point. But the color point may require matching color, so symmetry breaks.

Using `getClass()` avoids equality between superclass and subclass, preserving symmetry, but it makes equality strict by runtime class. That can be awkward with ORM proxies. Using `instanceof` supports subtype equality but is safe mostly when subclasses cannot add significant equality state or when a pattern like `canEqual` is used carefully.

#### Deep dive

The safest design is often to make value classes final or use records, so equality cannot be complicated by subclasses. For non-final hierarchies, decide whether equality is identity-based, class-strict, or deliberately extensible, and document it.

Entities add another complication: generated identifiers, lazy proxies and lifecycle states can interact badly with equality. Inheritance amplifies those problems because proxy subclasses may not equal the real entity class under `getClass()`.

#### Production angle

Prefer final immutable value objects for equality-heavy types. Avoid adding equality-relevant state in subclasses unless the base class was designed for it. For ORM entities, follow the framework/team equality strategy consistently.

#### Traps / caveats

- Subclass equality can violate symmetry.
- Subclass equality can violate transitivity.
- `getClass()` can conflict with proxy subclasses.
- `instanceof` can be wrong if subclasses add significant state.

#### Optional Anki

Q: Why is `equals()` easier in final classes?
A: No subclass can add equality-relevant state and break the equality contract.

</details>

<details>
<summary><strong>JCORE-OOP-008. What is method hiding, and how is it different from overriding?</strong></summary>

#### Short answer

Method hiding happens when a subclass declares a static method with the same signature as a static method in a superclass. The selected method is based on the compile-time type. Overriding applies to instance methods, and the selected implementation is based on the runtime receiver type.

#### Interview answer

With overriding, `Base b = new Sub(); b.run();` calls `Sub.run()` if `run` is an overridden instance method. With hiding, `Base b = new Sub(); b.util();` calls `Base.util()` if `util` is static.

Fields can also be hidden by fields with the same name in subclasses. Like static methods, fields are resolved using the compile-time type, not dynamically dispatched.

#### Deep dive

The compiler enforces consistency: an instance method cannot override a static method, and a static method cannot hide an instance method with the same signature. Return types and visibility still have compatibility rules.

Hiding is rarely a good design tool. It can be useful for class-specific factories or utilities, but it often confuses readers because the syntax looks like polymorphism while the semantics are static.

#### Production angle

Avoid naming static methods in subclasses as if they were polymorphic replacements. Call static methods through class names, not instances, and use instance methods or interfaces for behavior that must vary by runtime type.

#### Traps / caveats

- Method hiding applies to static methods, overriding to instance methods.
- Hidden static method selection uses compile-time type.
- Field hiding follows compile-time type too.
- Calling hidden static methods through instances is especially confusing.

#### Optional Anki

Q: What is selected by runtime type: hidden static method or overridden instance method?
A: Only the overridden instance method.

</details>

<details>
<summary><strong>JCORE-OOP-009. What are covariant return types in overridden methods?</strong></summary>

#### Short answer

Covariant return types allow an overriding method to return a subtype of the return type declared by the overridden method. For example, if a superclass method returns `Animal`, an overriding subclass method may return `Dog`.

#### Interview answer

This improves type precision without breaking polymorphism. Code using a superclass reference can still treat the result as the broader type, while code using the subclass API can receive the narrower type without casting.

Covariant returns work only for reference types, because they rely on subtype relationships. They do not mean arbitrary return-type overloading; Java does not overload methods by return type alone.

#### Deep dive

The parameter list must still match the overridden method signature. The overriding method must respect access and checked-exception rules: it cannot reduce visibility and cannot declare broader checked exceptions.

A common use is fluent APIs and copy/factory methods. For example, a base builder method may return `Builder`, while a subclass builder narrows return type to `SpecialBuilder`.

#### Production angle

Use covariant returns to improve API ergonomics when the subtype is truly guaranteed. Avoid complex hierarchies where fluent self-types become hard to reason about; generics may be clearer for advanced builder patterns.

#### Traps / caveats

- Return type alone cannot overload a method.
- Covariant return requires a subtype relationship.
- Primitive return types are not covariant.
- Overriding rules for visibility and checked exceptions still apply.

#### Optional Anki

Q: Can an overridden method return a subtype of the original return type?
A: Yes, for reference types; this is called a covariant return type.

</details>
