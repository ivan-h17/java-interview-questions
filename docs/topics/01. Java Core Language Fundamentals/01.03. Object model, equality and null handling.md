# 01.03. Object model, equality and null handling

<a id="jcore-obj-001"></a>

<details>
<summary><strong>JCORE-OBJ-001. What is the difference between object identity and logical equality?</strong></summary>

#### Short answer

Object identity means that two references denote the exact same object instance. Logical equality means that two objects are considered equal by domain rules, usually by an overridden `equals()` method. By default, `Object.equals()` is identity-based, but value-like classes often override it.

#### Interview answer

In an interview I would separate two questions: “Is it the same object?” and “Do these objects represent the same value or domain concept?” The first question is answered by reference identity, for example `a == b` for references. The second is answered by `a.equals(b)`, provided the class has a meaningful equality implementation.

For example, two different `Money` instances may both represent 10 USD and therefore be logically equal. Two different entity objects may represent the same database row if they have the same stable identifier. Identity still matters for synchronization, identity maps, object graphs and object lifecycle.

#### Deep dive

Every Java object has identity independent of its current field values. This is why an object can be mutated and still remain the same object. Tools such as `System.identityHashCode(obj)` and `IdentityHashMap` work with identity semantics rather than ordinary logical equality.

Logical equality is a contract chosen by the class. A value object usually compares all significant immutable components. An entity often compares a stable identity such as a business key or database identifier, but this must be designed carefully when identifiers are assigned after persistence.

The two notions should not be mixed casually. Identity is about object instance sameness; equality is about substitutability according to the class contract. A class can intentionally use identity equality by not overriding `equals()`.

#### Production angle

In production, decide equality semantics as part of the domain model. Make value objects immutable and compare stable fields. For entities, avoid equality based on mutable state, generated identifiers before assignment, or framework proxy classes unless the ORM strategy is explicitly accounted for.

#### Traps / caveats

- Equal objects do not have to be the same object.
- The same hash code does not prove equality.
- Default `equals()` from `Object` is identity equality.
- Mutable equality fields can make logical equality unstable.

#### Optional Anki

Q: What is object identity?
A: Two references have object identity equality when they point to the same object instance.

<details>
<summary><strong>JCORE-OBJ-002. What is the difference between `==` and `equals()`?</strong></summary>

#### Short answer

For primitives, `==` compares primitive values. For references, `==` compares object identity: whether both references point to the same object. `equals()` is a method call that may compare logical equality, depending on how the class implements it.

#### Interview answer

The key rule is that `==` is an operator and cannot be overridden. With references it answers “same object?”. `equals()` is polymorphic: `String`, wrappers, records and many domain classes implement it to compare meaningful state. Enums are the exception: each enum constant is a singleton, and `Enum.equals()` is final and identity-based.

For example, two different `String` objects can have `a == b` as `false` but `a.equals(b)` as `true`. If a class does not override `equals()`, then its inherited `Object.equals()` behaves like reference identity.

#### Deep dive

`equals()` is an instance method, so `a.equals(b)` throws `NullPointerException` if `a` is `null`. Use `Objects.equals(a, b)` for null-safe comparison of two possibly-null references.

Arrays are a frequent exception to expectations: arrays inherit `Object.equals()`, so `someArray.equals(otherArray)` compares identity. Use `Arrays.equals()` for one-dimensional contents and `Arrays.deepEquals()` for nested object arrays.

For enums, `==` is idiomatic and safe because each enum constant is a singleton. For boxed numbers and strings, prefer logical comparison unless you intentionally need reference identity.

#### Production angle

Use `equals()` or `Objects.equals()` for domain values, identifiers and DTO fields. Use `==` for primitives, enum constants and deliberate identity checks. Code reviews should flag accidental `==` comparisons on strings, wrappers and domain value objects.

#### Traps / caveats

- `a.equals(b)` is not null-safe when `a` is `null`.
- Arrays need `Arrays.equals()`, not plain `equals()`, for content comparison.
- String interning can make some `==` tests appear to work accidentally.
- For classes that do not override `equals()`, `==` and `equals()` are effectively the same.

#### Optional Anki

Q: What does `==` compare for references?
A: Object identity: whether both references point to the same object.

</details>

<summary><strong>JCORE-OBJ-003. What is the contract between `equals()` and `hashCode()`?</strong></summary>

#### Short answer

If two objects are equal according to `equals()`, they must return the same `hashCode()` value. The reverse is not required: unequal objects may have the same hash code. If you override `equals()`, you almost always must override `hashCode()` using the same significant state.

#### Interview answer

The `equals()` contract requires an equivalence relation: reflexive, symmetric, transitive, consistent, and `x.equals(null)` must be `false`. The `hashCode()` contract adds the hash rule: equal objects must have equal hash codes, and the hash code must remain consistent while the fields used by equality are unchanged.

This matters because `HashMap`, `HashSet` and similar structures use `hashCode()` to choose a bucket and then `equals()` to find the exact key. Breaking the contract can make present elements appear missing or allow duplicate logical keys.

#### Deep dive

A good implementation normally derives `hashCode()` from the same equality-relevant fields used by `equals()`. If `equals()` compares `currency` and `amount`, then `hashCode()` should usually be derived from `currency` and `amount` too. The contract permits less precise hashes, even a constant, but poor distribution hurts performance. Utilities such as `Objects.hash(...)`, IDE generation, Lombok and records can help, but the chosen fields still need design review.

Hash codes are not unique identifiers. Collisions are legal and expected; they mainly affect performance. Also, Java does not require a hash code to be stable across different JVM executions, only within one execution as long as equality-relevant data is unchanged.

Inheritance makes equality contracts harder. A subclass that adds significant fields can easily violate symmetry or transitivity if the superclass equality was not designed for extension.

#### Production angle

Prefer immutable value objects as hash keys. Generate and test `equals()`/`hashCode()` together, include contract tests for important domain types, and be cautious with generated database identifiers, timestamps, collections and lazy-loaded associations in equality methods.

#### Traps / caveats

- Overriding `equals()` without `hashCode()` breaks hash-based collections.
- Unequal objects may legally share a hash code.
- Using mutable fields in either method can break lookups after mutation.
- Subclass equality can violate symmetry or transitivity.

#### Optional Anki

Q: What must be true when `a.equals(b)` is `true`?
A: `a.hashCode() == b.hashCode()` must also be true.

</details>

<details>
<summary><strong>JCORE-OBJ-004. Why are mutable objects dangerous as keys in hash-based collections?</strong></summary>

#### Short answer

Hash-based collections place a key according to its hash code at insertion time. If fields used by `equals()` or `hashCode()` change later, the key may live in the wrong bucket. Then `contains`, `get` or `remove` may fail even though the object is physically still inside the collection.

#### Interview answer

Imagine a `UserKey` whose hash code uses `email`. You put it into a `HashSet`, then change the email. The set does not re-index the object automatically. A lookup with the mutated object computes a different hash and searches a different bucket.

The same problem appears in `HashMap` keys. The map may no longer find the value by the mutated key, and it may accept another logically equal key later, creating confusing duplicate logical entries.

#### Deep dive

A hash table normally uses the hash code to narrow the search to one bucket, then uses `equals()` inside that bucket. Mutation of equality-relevant state breaks the assumption that the key’s hash and equality relation are stable while the key is stored.

The dangerous mutation may be indirect. A key may contain a mutable `List`, `Date`, array or nested object that participates in equality. Mutating the nested object can break the outer key even if the key object itself has no setters.

ORM entities are another common trap: equality based on a generated `id` can change when the entity is persisted. Equality based on mutable business fields can also change during normal updates.

#### Production angle

Use immutable key classes, records with immutable components, or stable identifiers. If a key must change, remove the old key from the collection, mutate or create a new key, and insert it again. Avoid using full mutable entities as map keys unless equality is carefully constrained to stable identity.

#### Traps / caveats

- A key object can be present but unreachable by lookup.
- Nested mutable fields can break an otherwise “immutable-looking” key.
- Generated ORM identifiers can change equality after persistence.
- Lombok-generated equality may accidentally include mutable collections.

#### Optional Anki

Q: Why can a mutated `HashMap` key become unreachable?
A: Its current hash code may point to a different bucket than the one used when it was inserted.

</details>

<details>
<summary><strong>JCORE-OBJ-005. What is a good strategy for handling `null` in Java APIs?</strong></summary>

#### Short answer

A good strategy is to make nullability explicit, minimize accepted and returned `null`, and fail fast for invalid required values. Return empty collections instead of `null`, use `Optional<T>` for normal absence of a single value when appropriate, and document or annotate nullable contracts.

#### Interview answer

At API boundaries, decide whether `null` is a valid value. If it is not valid, reject it immediately with `Objects.requireNonNull`, validation annotations or explicit checks. This gives a clear failure close to the caller instead of a later mysterious `NullPointerException`.

For return values, avoid ambiguous `null`. A collection-returning method should normally return an empty list, set or map. A lookup method may return `Optional<T>`, throw a domain exception for required data, or use a result type that expresses absence and errors separately.

#### Deep dive

Java has no built-in non-null type system, so null contracts are partly convention and tooling. Common approaches include Javadoc, `@Nullable`/`@NonNull` annotations, Bean Validation, static analyzers, IDE inspections and Kotlin interop annotations.

Good null handling starts at boundaries: controllers, JSON deserialization, database rows, external clients and configuration. Convert loosely typed or nullable external data into validated internal objects. Inside the domain layer, prefer invariants that make illegal null states unrepresentable.

Sometimes a Null Object pattern is useful when a default behavior is meaningful. But do not hide a missing required dependency or invalid state behind a fake object that causes wrong business behavior.

#### Production angle

Define a project-wide convention: which annotations to use, whether service methods may return `null`, how repositories express missing rows, and whether DTO fields are nullable. Enforce the convention with code review, tests, static analysis and API schemas.

#### Traps / caveats

- Do not return `null` for collections when an empty collection has the intended meaning.
- `Optional` is usually better as a return type than as a field or parameter.
- Annotations help tools but do not automatically enforce runtime checks.
- Distinguish “unknown”, “not applicable”, “not found” and “empty” instead of using one vague `null`.

#### Optional Anki

Q: What should collection-returning methods usually return when there are no elements?
A: An empty collection, not `null`.

</details>

<details>
<summary><strong>JCORE-OBJ-006. What are common causes of `NullPointerException` in backend code?</strong></summary>

#### Short answer

Common backend causes are missing input validation, nullable database or JSON fields, absent map entries, repository methods returning `null`, uninitialized dependencies, autounboxing a null wrapper, chained dereferences and collection elements that unexpectedly contain `null`.

#### Interview answer

A `NullPointerException` happens when code tries to use `null` as if it were an object: call a method, read or write a field, access array length, enter a synchronized block, throw it as an exception, or unbox it to a primitive.

In backend systems the root cause is often at a boundary. Data may be missing from a request body, an external service, a database row, a cache, a message payload or configuration. The failure appears later because the value was accepted without validation.

#### Deep dive

Typical examples include `map.get(key).doWork()` when the key is absent, `Boolean enabled` being unboxed in `if (enabled)`, mapper code that assumes nested DTO fields exist, and tests that use mocks returning `null` by default.

Frameworks can shift where nulls appear. Dependency injection may fail because a bean is optional or not constructed as expected. ORM lazy relationships or optional columns may produce null fields. Deserialization can bypass constructors or leave fields unset if validation is missing.

Modern JVMs can produce more helpful NPE messages, but the design goal remains the same: make null contracts explicit and fail close to the boundary where invalid data entered the system.

#### Production angle

Use request validation, database constraints, constructor invariants, `Objects.requireNonNull`, static analysis and tests for boundary cases. Avoid long chains of dereferences in business code; split them into named validated steps so failures identify the missing data clearly.

#### Traps / caveats

- Autounboxing a null `Integer`, `Long` or `Boolean` throws NPE.
- `Map.get()` returning `null` can mean “no mapping” or “mapped to null” for maps that allow null values.
- Mocks often return `null` unless explicitly configured.
- A non-null collection may still contain null elements.

#### Optional Anki

Q: Why can `if (flag)` throw NPE when `flag` is `Boolean`?
A: Java unboxes `Boolean` to `boolean`; unboxing `null` throws NPE.

</details>

<details>
<summary><strong>JCORE-OBJ-007. How should a method communicate whether it can return `null`?</strong></summary>

#### Short answer

A method should communicate nullable returns through its API contract: use `Optional<T>` for ordinary absence of one value, return empty collections for no elements, throw exceptions for abnormal missing required data, and add clear Javadoc and nullability annotations when `null` is part of the contract.

#### Interview answer

The Java type `T` alone does not say whether `null` is allowed. Therefore the API needs a convention. A method named `findById` can return `Optional<User>` if “not found” is expected. A method named `getRequiredUser` can throw if the user must exist.

If `null` must be returned for compatibility or framework reasons, document it explicitly and use annotations such as `@Nullable`. Callers should not have to guess from implementation details or examples.

#### Deep dive

Different absence semantics deserve different types. “No rows” usually maps to an empty list. “Maybe one row” can map to `Optional<T>`. “Remote service failed” should not be encoded as `null`; it should usually be an exception, error result or retryable failure type.

`Optional` should never itself be `null`. Returning `null` from a method declared as `Optional<T>` combines the worst of both approaches. Also avoid using `Optional` where serialization frameworks, entity mapping or hot allocation paths make it awkward.

Nullability annotations are not all identical. Teams should standardize on one annotation set and configure IDEs/build tools to treat violations consistently.

#### Production angle

Make nullability visible in public APIs, OpenAPI schemas, generated clients and Kotlin interop. In repositories and services, keep naming consistent: for example, `find...` for optional results and `get...` or `require...` for required results.

#### Traps / caveats

- Javadoc-only contracts are easy to miss unless enforced by review and tooling.
- `@Nullable` does not perform a runtime check by itself.
- Returning `null` from `Optional<T>` methods is a serious API bug.
- Do not use exceptions for normal absence in high-volume lookup paths unless the domain really treats absence as exceptional.

#### Optional Anki

Q: What is a common return type for expected absence of one value?
A: `Optional<T>`, if it fits the API style and performance constraints.

</details>

<details>
<summary><strong>🧠 JCORE-OBJ-008. What are the trade-offs between `getClass()` and `instanceof` in `equals()`?</strong></summary>

#### Short answer

`getClass()` makes equality strict: objects are equal only if they have the exact same runtime class. `instanceof` allows equality across a superclass/subclass boundary. `getClass()` is safer for many value classes; `instanceof` is more flexible but can break symmetry or transitivity when subclasses add significant state.

#### Interview answer

With `getClass()`, a `Point` is never equal to a `ColoredPoint`, even if their common fields match. This avoids many inheritance problems because equality is defined only inside one concrete class.

With `instanceof`, a superclass can say “anything that is a Point-like object may be equal”. That can be useful for interfaces or carefully designed hierarchies, but it becomes dangerous when subclasses add fields that should affect equality.

#### Deep dive

The core issue is the `equals()` contract. If `Point.equals()` uses `instanceof Point` and ignores color, but `ColoredPoint.equals()` compares color, then `point.equals(coloredPoint)` and `coloredPoint.equals(point)` may disagree. That violates symmetry.

For final classes and records, this problem is much smaller because subclasses cannot add equality-relevant state. For non-final classes, prefer designing equality either as final and class-local, or as a documented extensible scheme such as the `canEqual` pattern.

Framework proxies complicate the choice. Some ORM frameworks create proxy subclasses, so strict `getClass()` equality may say a proxy and the real entity class are different. Entity equality should be designed together with the persistence framework.

#### Production angle

For value objects, prefer final classes/records and simple generated equality. For entities, document the equality policy and test it with proxies, transient objects and persisted objects. Avoid subclassable value classes unless there is a strong reason and a carefully designed equality contract.

#### Traps / caveats

- `instanceof` returns `false` for `null`; `obj.getClass()` throws NPE if `obj` is `null`.
- `getClass()` may not work as expected with ORM proxy subclasses.
- `instanceof` can break symmetry when subclasses add fields.
- For final classes, the practical difference is often small.

#### Optional Anki

Q: Which equality check is stricter: `getClass()` or `instanceof`?
A: `getClass()`; it requires the exact same runtime class.

</details>

<details>
<summary><strong>JCORE-OBJ-009. What methods does every Java object inherit from `Object`?</strong></summary>

#### Short answer

Every Java object has methods from `java.lang.Object`: `getClass()`, `equals(Object)`, `hashCode()`, `toString()`, `clone()`, `finalize()`, `wait()`, `wait(long)`, `wait(long,int)`, `notify()` and `notifyAll()`. Some are `final`, some are `protected`, and `finalize()` is deprecated for removal.

#### Interview answer

`Object` is the root of the class hierarchy, so all ordinary objects and arrays have these methods. The commonly overridden methods are `equals()`, `hashCode()` and `toString()`. `clone()` and `finalize()` are legacy mechanisms that are usually avoided.

`wait()`, `notify()` and `notifyAll()` are monitor methods used with intrinsic locks. They are low-level concurrency primitives; most backend code should prefer `java.util.concurrent` abstractions instead.

#### Deep dive

`getClass()`, `wait()`, `notify()` and `notifyAll()` are `final`, so they cannot be overridden. `Object.clone()` is `protected` and only works conventionally for classes that implement `Cloneable`; arrays are a special case with a public clone operation. `finalize()` is `protected`, deprecated for removal, and should not be used for resource management.

The inherited methods are not the same as language features. Arrays have a `length` field-like member, not a `length()` method. Constructors are not inherited methods, although `Object` has a no-argument constructor.

Calling any instance method requires a non-null receiver. A variable of any reference type can be `null`, but `null` is not an object and does not inherit methods.

#### Production angle

In everyday backend work, focus on correct `equals()`/`hashCode()`, safe `toString()`, and avoiding legacy `clone()`/`finalize()`. Use higher-level concurrency utilities rather than raw monitor waiting unless you are implementing low-level synchronization code.

#### Traps / caveats

- `null` does not inherit anything; method calls on `null` throw NPE.
- `clone()` is not a public copying API by default.
- `finalize()` is deprecated for removal and unreliable.
- `wait()` and `notify()` must be used while owning the object monitor.

#### Optional Anki

Q: Which `Object` methods are most commonly overridden?
A: `equals()`, `hashCode()` and `toString()`.

</details>

<details>
<summary><strong>JCORE-OBJ-010. When should `toString()` be overridden, and what should it avoid?</strong></summary>

#### Short answer

Override `toString()` when a readable representation helps debugging, logging, tests or operations. It should include useful stable fields, but avoid secrets, personal data, huge object graphs, lazy loading, network calls, expensive computation and side effects.

#### Interview answer

The default `Object.toString()` is usually not helpful for domain objects because it looks like class name plus a hash-based suffix. A good override gives concise diagnostic information such as an id, status, code, amount or important configuration values.

But `toString()` is not a serialization format and should not be part of business logic. It is mainly for humans and diagnostics. Machine-readable output should use JSON/XML/protobuf serializers or explicit formatting methods.

#### Deep dive

Logging frameworks, exception messages and debuggers may call `toString()` implicitly. That makes side effects dangerous: a string conversion should not change state, hit a database, perform remote calls or trigger lazy loading that changes transaction behavior.

Security is equally important. Do not print passwords, tokens, session ids, private keys, full card numbers or sensitive PII. For large object graphs, include identifiers or counts rather than recursively printing everything.

Records generate a component-based `toString()`, which is convenient but can leak sensitive components if a record stores secrets. Generated methods still need review.

#### Production angle

Define safe logging conventions. For entities, include class name and stable id rather than entire relationships. For DTOs, mask sensitive fields. For high-volume objects, keep `toString()` cheap and avoid allocating large temporary strings unnecessarily.

#### Traps / caveats

- Do not expose secrets or PII in logs through `toString()`.
- Do not trigger lazy database loading from `toString()`.
- Do not rely on `toString()` as a stable parseable API.
- Beware recursive object graphs that can cause very large output or stack overflow.

#### Optional Anki

Q: What should `toString()` primarily be used for?
A: Human-readable diagnostics, not serialization or business logic.

</details>

<details>
<summary><strong>🧠 JCORE-OBJ-011. Why are `clone()` and `finalize()` usually avoided in modern Java?</strong></summary>

#### Short answer

`clone()` is avoided because the `Cloneable` protocol is awkward, shallow by default, inheritance-hostile and easy to implement incorrectly. `finalize()` is avoided because finalization is deprecated for removal, unreliable, slow, security-sensitive and not guaranteed to run promptly or at all. Use copy constructors/factories and explicit resource management instead.

#### Interview answer

`Object.clone()` performs a field-by-field copy. That is usually a shallow copy, so references to mutable nested objects are shared unless the class fixes them manually. `Cloneable` is only a marker interface; it does not declare a public `clone()` method, and without it `Object.clone()` throws `CloneNotSupportedException`.

`finalize()` is not a destructor. The garbage collector may call it after an indefinite delay, or not before program exit. Finalizers can resurrect objects, run on unspecified threads, hide exceptions and create performance/security problems. Modern Java prefers `try-with-resources`, `AutoCloseable`, and occasionally `Cleaner` for advanced cleanup safety nets.

#### Deep dive

Copying is usually clearer when expressed explicitly: a copy constructor, static factory, builder, record “with” style method, or domain-specific copy method can state whether the copy is shallow, deep or partially transformed. These approaches can validate invariants and do not depend on `Cloneable` conventions.

Resource cleanup should also be explicit. Files, sockets, database connections and native handles should be closed deterministically with `try-with-resources` or lifecycle management from the owning framework. A GC-triggered cleanup mechanism cannot guarantee timely release of scarce external resources.

`Cleaner` and phantom references are safer than finalizers for some advanced cases, but they are still not a substitute for explicit close when timely release is required.

#### Production angle

Expose intentional copy APIs and document their depth. For resources, implement `AutoCloseable`, use `try-with-resources`, and let dependency injection containers manage lifecycle where appropriate. Treat finalizer warnings as migration work, not as harmless noise.

#### Traps / caveats

- A cloned object may share mutable internal state with the original.
- `Cloneable` does not declare `clone()`, which makes the API misleading.
- `finalize()` is not guaranteed to run promptly, and may never run before shutdown.
- Calling `System.gc()` is not a correct resource-management strategy.

#### Optional Anki

Q: What should replace `finalize()` for ordinary resource cleanup?
A: Explicit cleanup with `AutoCloseable` and `try-with-resources`.

</details>
