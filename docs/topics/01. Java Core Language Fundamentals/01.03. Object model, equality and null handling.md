# 3. Object model, equality and null handling

<a id="jcore-obj-001"></a>

<details>
<summary><strong>JCORE-OBJ-001. What is the difference between object identity and logical equality?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Object identity means that two references denote the exact same object instance. Logical equality means that two objects are considered equal by domain rules, usually by an overridden <code>equals()</code> method. By default, <code>Object.equals()</code> is identity-based, but value-like classes often override it.</p>
</td>
<td valign="top" width="50%">
<p>Идентичность объекта означает, что две ссылки указывают на один и тот же экземпляр. Логическое равенство означает, что два объекта считаются равными по доменным правилам, обычно через переопределённый <code>equals()</code>. По умолчанию <code>Object.equals()</code> основан на идентичности, но классы со значимой value-семантикой часто его переопределяют.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In an interview I would separate two questions: “Is it the same object?” and “Do these objects represent the same value or domain concept?” The first question is answered by reference identity, for example <code>a == b</code> for references. The second is answered by <code>a.equals(b)</code>, provided the class has a meaningful equality implementation.</p>
<p>For example, two different <code>Money</code> instances may both represent 10 USD and therefore be logically equal. Two different entity objects may represent the same database row if they have the same stable identifier. Identity still matters for synchronization, identity maps, object graphs and object lifecycle.</p>
</td>
<td valign="top" width="50%">
<p>На интервью я бы разделил два вопроса: «это тот же самый объект?» и «представляют ли эти объекты одно и то же значение или доменную сущность?» На первый вопрос отвечает идентичность ссылок, например <code>a == b</code> для ссылок. На второй отвечает <code>a.equals(b)</code>, если у класса есть осмысленная реализация равенства.</p>
<p>Например, два разных экземпляра <code>Money</code> могут оба представлять 10 USD и поэтому быть логически равными. Два разных объекта-сущности могут представлять одну строку в базе, если имеют одинаковый стабильный идентификатор. Идентичность всё равно важна для синхронизации, identity map, графов объектов и жизненного цикла объекта.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Every Java object has identity independent of its current field values. This is why an object can be mutated and still remain the same object. Tools such as <code>System.identityHashCode(obj)</code> and <code>IdentityHashMap</code> work with identity semantics rather than ordinary logical equality.</p>
<p>Logical equality is a contract chosen by the class. A value object usually compares all significant immutable components. An entity often compares a stable identity such as a business key or database identifier, but this must be designed carefully when identifiers are assigned after persistence.</p>
<p>The two notions should not be mixed casually. Identity is about object instance sameness; equality is about substitutability according to the class contract. A class can intentionally use identity equality by not overriding <code>equals()</code>.</p>
</td>
<td valign="top" width="50%">
<p>У каждого Java-объекта есть идентичность независимо от текущих значений полей. Поэтому объект можно изменить, но он всё равно останется тем же объектом. Инструменты вроде <code>System.identityHashCode(obj)</code> и <code>IdentityHashMap</code> работают с семантикой идентичности, а не с обычным логическим равенством.</p>
<p>Логическое равенство — это контракт, выбранный классом. Объект-значение обычно сравнивает все значимые неизменяемые компоненты. Сущность часто сравнивает стабильную идентичность, например бизнес-ключ или идентификатор базы данных, но это надо проектировать аккуратно, если идентификатор присваивается только после сохранения.</p>
<p>Эти два понятия нельзя смешивать неосознанно. Идентичность говорит о совпадении экземпляра объекта; равенство говорит о взаимозаменяемости согласно контракту класса. Класс может намеренно использовать равенство по идентичности, если не переопределяет <code>equals()</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, decide equality semantics as part of the domain model. Make value objects immutable and compare stable fields. For entities, avoid equality based on mutable state, generated identifiers before assignment, or framework proxy classes unless the ORM strategy is explicitly accounted for.</p>
</td>
<td valign="top" width="50%">
<p>В продакшене семантику равенства нужно выбирать как часть доменной модели. Объекты-значения лучше делать неизменяемыми и сравнивать стабильные поля. Для сущностей избегайте равенства по изменяемому состоянию, сгенерированным идентификаторам до их присваивания или прокси-классам фреймворка, если стратегия ORM не учтена явно.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Equal objects do not have to be the same object.</li>
<li>The same hash code does not prove equality.</li>
<li>Default <code>equals()</code> from <code>Object</code> is identity equality.</li>
<li>Mutable equality fields can make logical equality unstable.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Равные объекты не обязаны быть одним и тем же объектом.</li>
<li>Одинаковый хеш-код не доказывает равенство.</li>
<li>Default <code>equals()</code> из <code>Object</code> — это равенство по идентичности.</li>
<li>Изменяемые поля, участвующие в равенстве, могут сделать логическое равенство нестабильным.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is object identity?<br>A: Two references have object identity equality when they point to the same object instance.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что такое идентичность объекта?<br>A: Это ситуация, когда две ссылки указывают на один и тот же экземпляр объекта.</p>
</td>
</tr>

<a id="jcore-obj-002"></a>

<details>
<summary><strong>JCORE-OBJ-002. What is the difference between <code>==</code> and <code>equals()</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For primitives, <code>==</code> compares primitive values. For references, <code>==</code> compares object identity: whether both references point to the same object. <code>equals()</code> is a method call that may compare logical equality, depending on how the class implements it.</p>
</td>
<td valign="top" width="50%">
<p>Для примитивов <code>==</code> сравнивает значения примитивов. Для ссылок <code>==</code> сравнивает идентичность объекта: указывают ли обе ссылки на один объект. <code>equals()</code> — это вызов метода, который может сравнивать логическое равенство в зависимости от реализации класса.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The key rule is that <code>==</code> is an operator and cannot be overridden. With references it answers “same object?”. <code>equals()</code> is polymorphic: <code>String</code>, wrappers, records and many domain classes implement it to compare meaningful state. Enums are the exception: each enum constant is a singleton, and <code>Enum.equals()</code> is final and identity-based.</p>
<p>For example, two different <code>String</code> objects can have <code>a == b</code> as <code>false</code> but <code>a.equals(b)</code> as <code>true</code>. If a class does not override <code>equals()</code>, then its inherited <code>Object.equals()</code> behaves like reference identity.</p>
</td>
<td valign="top" width="50%">
<p>Главное правило: <code>==</code> — оператор, его нельзя переопределить. Для ссылок он отвечает на вопрос «тот же самый объект?». <code>equals()</code> полиморфен: <code>String</code>, классы-обёртки, records и многие доменные классы реализуют его для сравнения значимого состояния. Перечисления — исключение: каждая константа перечисления является singleton, а <code>Enum.equals()</code> final и основан на идентичности.</p>
<p>Например, два разных объекта <code>String</code> могут иметь <code>a == b</code> как <code>false</code>, но <code>a.equals(b)</code> как <code>true</code>. Если класс не переопределяет <code>equals()</code>, то унаследованный <code>Object.equals()</code> ведёт себя как идентичность ссылок.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>equals()</code> is an instance method, so <code>a.equals(b)</code> throws <code>NullPointerException</code> if <code>a</code> is <code>null</code>. Use <code>Objects.equals(a, b)</code> for null-safe comparison of two possibly-null references.</p>
<p>Arrays are a frequent exception to expectations: arrays inherit <code>Object.equals()</code>, so <code>someArray.equals(otherArray)</code> compares identity. Use <code>Arrays.equals()</code> for one-dimensional contents and <code>Arrays.deepEquals()</code> for nested object arrays.</p>
<p>For enums, <code>==</code> is idiomatic and safe because each enum constant is a singleton. For boxed numbers and strings, prefer logical comparison unless you intentionally need reference identity.</p>
</td>
<td valign="top" width="50%">
<p><code>equals()</code> — метод экземпляра, поэтому <code>a.equals(b)</code> бросит <code>NullPointerException</code>, если <code>a</code> равен <code>null</code>. Для безопасного сравнения двух ссылок, каждая из которых может быть <code>null</code>, используйте <code>Objects.equals(a, b)</code>.</p>
<p>Массивы часто ломают ожидания: они наследуют <code>Object.equals()</code>, поэтому <code>someArray.equals(otherArray)</code> сравнивает идентичность. Для содержимого одномерных массивов используйте <code>Arrays.equals()</code>, для вложенных массивов объектов — <code>Arrays.deepEquals()</code>.</p>
<p>Для перечислений <code>==</code> идиоматичен и безопасен, потому что каждая константа перечисления — singleton. Для упакованных чисел и строк предпочитайте логическое сравнение, если намеренно не нужна идентичность ссылок.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use <code>equals()</code> or <code>Objects.equals()</code> for domain values, identifiers and DTO fields. Use <code>==</code> for primitives, enum constants and deliberate identity checks. Code reviews should flag accidental <code>==</code> comparisons on strings, wrappers and domain value objects.</p>
</td>
<td valign="top" width="50%">
<p>Используйте <code>equals()</code> или <code>Objects.equals()</code> для доменных значений, идентификаторов и полей DTO. Используйте <code>==</code> для примитивов, констант перечисления и осознанных проверок идентичности. На ревью кода стоит ловить случайные сравнения <code>==</code> для строк, классов-обёрток и доменных объектов-значений.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>a.equals(b)</code> is not null-safe when <code>a</code> is <code>null</code>.</li>
<li>Arrays need <code>Arrays.equals()</code>, not plain <code>equals()</code>, for content comparison.</li>
<li>String interning can make some <code>==</code> tests appear to work accidentally.</li>
<li>For classes that do not override <code>equals()</code>, <code>==</code> and <code>equals()</code> are effectively the same.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li><code>a.equals(b)</code> не null-safe, если <code>a</code> равен <code>null</code>.</li>
<li>Для сравнения содержимого массивов нужен <code>Arrays.equals()</code>, а не обычный <code>equals()</code>.</li>
<li>Интернирование строк может случайно сделать некоторые проверки через <code>==</code> «работающими».</li>
<li>Для классов без переопределения <code>equals()</code> операторы <code>==</code> и <code>equals()</code> фактически совпадают.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does <code>==</code> compare for references?<br>A: Object identity: whether both references point to the same object.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что сравнивает <code>==</code> для ссылок?<br>A: Идентичность объекта: указывают ли обе ссылки на один объект.</p>
</td>
</tr>

<details>
<summary><strong>JCORE-OBJ-003. What is the contract between <code>equals()</code> and <code>hashCode()</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If two objects are equal according to <code>equals()</code>, they must return the same <code>hashCode()</code> value. The reverse is not required: unequal objects may have the same hash code. If you override <code>equals()</code>, you almost always must override <code>hashCode()</code> using the same significant state.</p>
</td>
<td valign="top" width="50%">
<p>Если два объекта равны по <code>equals()</code>, они обязаны возвращать одинаковое значение <code>hashCode()</code>. Обратное не требуется: неравные объекты могут иметь одинаковый хеш-код. Если вы переопределяете <code>equals()</code>, почти всегда нужно переопределить <code>hashCode()</code> по тем же значимые поля.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The <code>equals()</code> contract requires an equivalence relation: reflexive, symmetric, transitive, consistent, and <code>x.equals(null)</code> must be <code>false</code>. The <code>hashCode()</code> contract adds the hash rule: equal objects must have equal hash codes, and the hash code must remain consistent while the fields used by equality are unchanged.</p>
<p>This matters because <code>HashMap</code>, <code>HashSet</code> and similar structures use <code>hashCode()</code> to choose a bucket and then <code>equals()</code> to find the exact key. Breaking the contract can make present elements appear missing or allow duplicate logical keys.</p>
</td>
<td valign="top" width="50%">
<p>Контракт <code>equals()</code> требует отношения эквивалентности: рефлексивность, симметричность, транзитивность, согласованность, и <code>x.equals(null)</code> должен быть <code>false</code>. Контракт <code>hashCode()</code> добавляет правило хеша: равные объекты обязаны иметь одинаковые хеш-коды, а хеш-код должен оставаться согласованным, пока поля, участвующие в равенстве не изменились.</p>
<p>Это важно, потому что <code>HashMap</code>, <code>HashSet</code> и похожие структуры используют <code>hashCode()</code> для выбора bucket, а затем <code>equals()</code> для поиска точного ключа. Нарушение контракта может сделать существующие элементы «невидимыми» или разрешить дублирующиеся логические ключи.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A good implementation normally derives <code>hashCode()</code> from the same equality-relevant fields used by <code>equals()</code>. If <code>equals()</code> compares <code>currency</code> and <code>amount</code>, then <code>hashCode()</code> should usually be derived from <code>currency</code> and <code>amount</code> too. The contract permits less precise hashes, even a constant, but poor distribution hurts performance. Utilities such as <code>Objects.hash(...)</code>, IDE generation, Lombok and records can help, but the chosen fields still need design review.</p>
<p>Hash codes are not unique identifiers. Collisions are legal and expected; they mainly affect performance. Also, Java does not require a hash code to be stable across different JVM executions, only within one execution as long as equality-relevant data is unchanged.</p>
<p>Inheritance makes equality contracts harder. A subclass that adds significant fields can easily violate symmetry or transitivity if the superclass equality was not designed for extension.</p>
</td>
<td valign="top" width="50%">
<p>Хорошая реализация обычно строит <code>hashCode()</code> из тех же полей, участвующих в равенстве, что и <code>equals()</code>. Если <code>equals()</code> сравнивает <code>currency</code> и <code>amount</code>, то <code>hashCode()</code> обычно тоже стоит строить из <code>currency</code> и <code>amount</code>. Контракт разрешает менее точные hashes, даже постоянный хеш-код, но плохая distribution ухудшает производительность. Утилиты вроде <code>Objects.hash(...)</code>, IDE generation, Lombok и records помогают, но выбранные поля всё равно требуют проектной проверки.</p>
<p>Хеш-коды не являются уникальными идентификаторами. Коллизии легальны и ожидаемы; в основном они влияют на производительность. Также Java не требует, чтобы хеш-код был стабильным между разными JVM executions, только внутри одного execution, пока данные, участвующие в равенстве не меняется.</p>
<p>Наследование усложняет контракты равенства. Подкласс, который добавляет значимые поля, легко может нарушить симметричность или транзитивность, если суперкласс равенство не был designed for extension.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Prefer immutable value objects as hash keys. Generate and test <code>equals()</code>/<code>hashCode()</code> together, include contract tests for important domain types, and be cautious with generated database identifiers, timestamps, collections and lazy-loaded associations in equality methods.</p>
</td>
<td valign="top" width="50%">
<p>Для хеш-ключей предпочитайте неизменяемые объекты-значения. Генерируйте и тестируйте <code>equals()</code>/<code>hashCode()</code> вместе, добавляйте контрактные тесты для важных доменных типов и будьте осторожны с сгенерированными идентификаторами базы данных, timestamps, коллекции и лениво загружаемыми связями в методах равенства.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Overriding <code>equals()</code> without <code>hashCode()</code> breaks hash-based collections.</li>
<li>Unequal objects may legally share a hash code.</li>
<li>Using mutable fields in either method can break lookups after mutation.</li>
<li>Subclass equality can violate symmetry or transitivity.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Override <code>equals()</code> без <code>hashCode()</code> ломает хеш-коллекции.</li>
<li>Unравные объекты могут легально иметь одинаковый хеш-код.</li>
<li>Mutable поля в этих методах могут сломать поиск после изменение.</li>
<li>Подкласс равенство может нарушить симметричность или транзитивность.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What must be true when <code>a.equals(b)</code> is <code>true</code>?<br>A: <code>a.hashCode() == b.hashCode()</code> must also be true.</p>
</td>
<td valign="top" width="50%">
<p>Q: Что должно быть верно, если <code>a.equals(b)</code> равно <code>true</code>?<br>A: <code>a.hashCode() == b.hashCode()</code> тоже должно быть true.</p>
</td>
</tr>

<a id="jcore-obj-004"></a>

<details>
<summary><strong>JCORE-OBJ-004. Why are mutable objects dangerous as keys in hash-based collections?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Hash-based collections place a key according to its hash code at insertion time. If fields used by <code>equals()</code> or <code>hashCode()</code> change later, the key may live in the wrong bucket. Then <code>contains</code>, <code>get</code> or <code>remove</code> may fail even though the object is physically still inside the collection.</p>
</td>
<td valign="top" width="50%">
<p>Хеш-коллекции размещают ключ по его хеш-код на момент вставки. Если поля, используемые в <code>equals()</code> или <code>hashCode()</code>, позже изменятся, ключ может оказаться в неправильном bucket. Тогда <code>contains</code>, <code>get</code> или <code>remove</code> могут не найти объект, хотя физически он всё ещё внутри коллекции.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Imagine a <code>UserKey</code> whose hash code uses <code>email</code>. You put it into a <code>HashSet</code>, then change the email. The set does not re-index the object automatically. A lookup with the mutated object computes a different hash and searches a different bucket.</p>
<p>The same problem appears in <code>HashMap</code> keys. The map may no longer find the value by the mutated key, and it may accept another logically equal key later, creating confusing duplicate logical entries.</p>
</td>
<td valign="top" width="50%">
<p>Представьте <code>UserKey</code>, чей хеш-код использует <code>email</code>. Вы кладёте его в <code>HashSet</code>, а потом меняете email. Set не re-index объект автоматически. Lookup с изменённый объект вычисляет другой hash и ищет в другом bucket.</p>
<p>Та же проблема возникает с ключами в <code>HashMap</code>. <code>Map</code> может перестать находить значение по изменённый ключ и позже может принять другой логически равными ключ, создавая запутанные дублирующиеся логические записи.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A hash table normally uses the hash code to narrow the search to one bucket, then uses <code>equals()</code> inside that bucket. Mutation of equality-relevant state breaks the assumption that the key’s hash and equality relation are stable while the key is stored.</p>
<p>The dangerous mutation may be indirect. A key may contain a mutable <code>List</code>, <code>Date</code>, array or nested object that participates in equality. Mutating the nested object can break the outer key even if the key object itself has no setters.</p>
<p>ORM entities are another common trap: equality based on a generated <code>id</code> can change when the entity is persisted. Equality based on mutable business fields can also change during normal updates.</p>
</td>
<td valign="top" width="50%">
<p>Hash table обычно использует хеш-код, чтобы сузить поиск до одного bucket, а затем применяет <code>equals()</code> внутри bucket. Изменение состояние, участвующее в равенстве нарушает предположение, что hash и равенство relation ключа стабильны, пока ключ хранится в коллекции.</p>
<p>Опасная изменение может быть indirect. Ключ может содержать изменяемый <code>List</code>, <code>Date</code>, массив или nested объект, участвующий в равенство. Изменение nested объект может сломать внешний ключ, даже если у самого объект-ключ нет setters.</p>
<p>ORM entities — ещё одна частая ловушка: равенства по сгенерированный <code>id</code> может измениться при persistence. Equality по изменяемый бизнес поля тоже может измениться во время обычных updates.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use immutable key classes, records with immutable components, or stable identifiers. If a key must change, remove the old key from the collection, mutate or create a new key, and insert it again. Avoid using full mutable entities as map keys unless equality is carefully constrained to stable identity.</p>
</td>
<td valign="top" width="50%">
<p>Используйте неизменяемые классы ключей, records с неизменяемыми компонентами или стабильные идентификаторы. Если ключ должен измениться, удалите старый ключ из коллекции, измените его или создайте новый, затем вставьте снова. Не используйте полные изменяемые сущности как ключи map, если равенство не ограничено аккуратно выбранной стабильной идентичностью.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>A key object can be present but unreachable by lookup.</li>
<li>Nested mutable fields can break an otherwise “immutable-looking” key.</li>
<li>Generated ORM identifiers can change equality after persistence.</li>
<li>Lombok-generated equality may accidentally include mutable collections.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Объект-ключ может присутствовать, но быть unreachable для поиска.</li>
<li>Nested изменяемые поля могут сломать ключ, который выглядит неизменяемый.</li>
<li>Generated ORM идентификаторов могут изменить равенства после сохранения.</li>
<li>Сгенерированное Lombok равенство может случайно включить изменяемые коллекции.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why can a mutated <code>HashMap</code> key become unreachable?<br>A: Its current hash code may point to a different bucket than the one used when it was inserted.</p>
</td>
<td valign="top" width="50%">
<p>Q: Почему mutated <code>HashMap</code> ключ может стать unreachable?<br>A: Его текущий хеш-код может указывать на другой bucket, не тот, который использовался при вставке.</p>
</td>
</tr>

<details>
<summary><strong>JCORE-OBJ-005. What is a good strategy for handling <code>null</code> in Java APIs?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A good strategy is to make nullability explicit, minimize accepted and returned <code>null</code>, and fail fast for invalid required values. Return empty collections instead of <code>null</code>, use <code>Optional&lt;T&gt;</code> for normal absence of a single value when appropriate, and document or annotate nullable contracts.</p>
</td>
<td valign="top" width="50%">
<p>Хорошая стратегия — явно описывать допустимость null, минимизировать принимаемые и возвращаемые <code>null</code> и fail fast для недопустимых обязательных значений. Возвращайте пустые коллекции вместо <code>null</code>, используйте <code>Optional&lt;T&gt;</code> для нормального отсутствия одного значения, когда это уместно, и документируйте или аннотируйте контракты nullable.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>At API boundaries, decide whether <code>null</code> is a valid value. If it is not valid, reject it immediately with <code>Objects.requireNonNull</code>, validation annotations or explicit checks. This gives a clear failure close to the caller instead of a later mysterious <code>NullPointerException</code>.</p>
<p>For return values, avoid ambiguous <code>null</code>. A collection-returning method should normally return an empty list, set or map. A lookup method may return <code>Optional&lt;T&gt;</code>, throw a domain exception for required data, or use a result type that expresses absence and errors separately.</p>
</td>
<td valign="top" width="50%">
<p>На границах API нужно решить, является ли <code>null</code> допустимым значением. Если нет, отклоняйте его сразу через <code>Objects.requireNonNull</code>, валидационные аннотации или явные проверки. Это даёт понятный сбой рядом с вызывающим кодом вместо позднего загадочного <code>NullPointerException</code>.</p>
<p>Для возвращаемых значений избегайте неоднозначного <code>null</code>. Метод, возвращающий коллекцию, обычно должен возвращать пустой list, set или map. Lookup-метод может вернуть <code>Optional&lt;T&gt;</code>, бросить доменное исключение для обязательных данных или использовать тип результата, который отдельно выражает отсутствие значения и ошибки.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Java has no built-in non-null type system, so null contracts are partly convention and tooling. Common approaches include Javadoc, <code>@Nullable</code>/<code>@NonNull</code> annotations, Bean Validation, static analyzers, IDE inspections and Kotlin interop annotations.</p>
<p>Good null handling starts at boundaries: controllers, JSON deserialization, database rows, external clients and configuration. Convert loosely typed or nullable external data into validated internal objects. Inside the domain layer, prefer invariants that make illegal null states unrepresentable.</p>
<p>Sometimes a Null Object pattern is useful when a default behavior is meaningful. But do not hide a missing required dependency or invalid state behind a fake object that causes wrong business behavior.</p>
</td>
<td valign="top" width="50%">
<p>В Java нет встроенной системы non-null типов, поэтому null-контракты частично остаются соглашением и задачей инструментов. Частые подходы: Javadoc, аннотации <code>@Nullable</code>/<code>@NonNull</code>, Bean Validation, статические анализаторы, инспекции IDE и аннотации для совместимости с Kotlin.</p>
<p>Хорошая работа с null начинается на границах: контроллеры, десериализация JSON, строки базы данных, внешние клиенты и конфигурация. Преобразуйте loosely typed или nullable внешние данные в проверенные внутренние объекты. В доменном слое предпочитайте инварианты, где недопустимые состояния с null непредставимы.</p>
<p>Иногда паттерн Null Object полезен, если поведение по умолчанию действительно имеет смысл. Но не скрывайте отсутствующую обязательную зависимость или invalid state за поддельным объектом, который приводит к неправильному бизнес-поведению.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Define a project-wide convention: which annotations to use, whether service methods may return <code>null</code>, how repositories express missing rows, and whether DTO fields are nullable. Enforce the convention with code review, tests, static analysis and API schemas.</p>
</td>
<td valign="top" width="50%">
<p>Определите единое соглашение проекта: какие annotations использовать, могут ли сервисные методы возвращать <code>null</code>, как repositories выражают отсутствующие строки и какие полей DTO nullable. Enforce convention через ревью кода, tests, статический analysis и схемы API.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not return <code>null</code> for collections when an empty collection has the intended meaning.</li>
<li><code>Optional</code> is usually better as a return type than as a field or parameter.</li>
<li>Annotations help tools but do not automatically enforce runtime checks.</li>
<li>Distinguish “unknown”, “not applicable”, “not found” and “empty” instead of using one vague <code>null</code>.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li>Не возвращайте <code>null</code> для коллекции, если ожидаемый смысл — пустые коллекции.</li>
<li><code>Optional</code> обычно лучше как тип возвращаемого значения, чем как поле или параметр.</li>
<li>Annotations помогают инструменты, но сами по себе не enforce время выполнения проверки.</li>
<li>Различайте “неизвестно”, “not применимы”, “не найдено” и “пусто” вместо одного vague <code>null</code>.</li>
</ul>
</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>

</td>
<td valign="top" width="50%">
<p>Q: Что обычно должны возвращать коллекции-returning методы, если элементов нет?<br>A: Empty коллекции, а не <code>null</code>.</p>
</td>

<summary><strong>JCORE-OBJ-006. What are common causes of <code>NullPointerException</code> in backend code?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Common backend causes are missing input validation, nullable database or JSON fields, absent map entries, repository methods returning <code>null</code>, uninitialized dependencies, autounboxing a null wrapper, chained dereferences and collection elements that unexpectedly contain <code>null</code>.</p>
</td>
<td valign="top" width="50%">
<p>Частые бэкенд-причины: отсутствие валидации входных данных, nullable-поля базы данных или JSON, отсутствующие записи в map, методы репозитория, возвращающие <code>null</code>, неинициализированные зависимости, автораспаковка null-обёртки, цепочки разыменований и элементы коллекций, которые неожиданно содержат <code>null</code>.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A <code>NullPointerException</code> happens when code tries to use <code>null</code> as if it were an object: call a method, read or write a field, access array length, enter a synchronized block, throw it as an exception, or unbox it to a primitive.</p>

</td>
<td valign="top" width="50%">
<p><code>NullPointerException</code> возникает, когда код пытается использовать <code>null</code> как объект: вызвать метод, прочитать или записать поле, получить длину массива, войти в synchronized-блок, бросить его как исключение или распаковать в примитив.</p>
<p>В бэкенд-системах первопричина часто находится на границе. Данные могут отсутствовать в теле запроса, внешнем сервисе, строке базы данных, кеше, payload сообщения или конфигурации. Ошибка появляется позже, потому что значение приняли без валидации.</p>

</tr>

<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Typical examples include <code>map.get(key).doWork()</code> when the key is absent, <code>Boolean enabled</code> being unboxed in <code>if (enabled)</code>, mapper code that assumes nested DTO fields exist, and tests that use mocks returning <code>null</code> by default.</p>
<p>Frameworks can shift where nulls appear. Dependency injection may fail because a bean is optional or not constructed as expected. ORM lazy relationships or optional columns may produce null fields. Deserialization can bypass constructors or leave fields unset if validation is missing.</p>

</td>
<td valign="top" width="50%">
<p>Типичные примеры: <code>map.get(key).doWork()</code>, когда ключ отсутствует; <code>Boolean enabled</code>, который распаковывается в <code>if (enabled)</code>; код маппера, предполагающий наличие вложенных полей DTO; и тесты, где mocks по умолчанию возвращают <code>null</code>.</p>

<th colspan="2" align="left">Production angle</th>

<tr>
<td valign="top" width="50%">
<p>Use request validation, database constraints, constructor invariants, <code>Objects.requireNonNull</code>, static analysis and tests for boundary cases. Avoid long chains of dereferences in business code; split them into named validated steps so failures identify the missing data clearly.</p>
</td>
<td valign="top" width="50%">
<p>Используйте валидацию запросов, ограничения базы данных, инварианты конструкторов, <code>Objects.requireNonNull</code>, статический анализ и тесты для граничных случаев. Избегайте длинных цепочек разыменований в бизнес-коде; разбивайте их на именованные проверенные шаги, чтобы сбой ясно показывал отсутствующие данные.</p>

<li>Mocks often return <code>null</code> unless explicitly configured.</li>

</td>
<td valign="top" width="50%">

<details>
<summary><strong>JCORE-OBJ-007. How should a method communicate whether it can return <code>null</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A method should communicate nullable returns through its API contract: use <code>Optional&lt;T&gt;</code> for ordinary absence of one value, return empty collections for no elements, throw exceptions for abnormal missing required data, and add clear Javadoc and nullability annotations when <code>null</code> is part of the contract.</p>
</td>
<td valign="top" width="50%">
<p>Метод должен сообщать о возвращаемых nullable значениях через контракт API: использовать <code>Optional&lt;T&gt;</code> для нормального отсутствия одного значения, возвращать пустые коллекции при отсутствии элементов, бросать исключения, если обязательные данные отсутствуют неожиданно и добавлять ясный Javadoc и аннотации допустимости null, если <code>null</code> является частью контракта.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The Java type <code>T</code> alone does not say whether <code>null</code> is allowed. Therefore the API needs a convention. A method named <code>findById</code> can return <code>Optional&lt;User&gt;</code> if “not found” is expected. A method named <code>getRequiredUser</code> can throw if the user must exist.</p>
<p>If <code>null</code> must be returned for compatibility or framework reasons, document it explicitly and use annotations such as <code>@Nullable</code>. Callers should not have to guess from implementation details or examples.</p>
</td>
<td valign="top" width="50%">
<p>Сам тип Java <code>T</code> не говорит, разрешён ли <code>null</code>. Поэтому API нужен явный контракт. Метод <code>findById</code> может возвращать <code>Optional&lt;User&gt;</code>, если “не найдено” ожидаемо. Метод <code>getRequiredUser</code> может бросать исключение, если пользователь обязан существовать.</p>
<p>Если <code>null</code> приходится возвращать из-за совместимости или требований фреймворка, документируйте это явно и используйте аннотации вроде <code>@Nullable</code>. Вызывающий код не должен угадывать контракт по деталям реализации или примерам.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Different absence semantics deserve different types. “No rows” usually maps to an empty list. “Maybe one row” can map to <code>Optional&lt;T&gt;</code>. “Remote service failed” should not be encoded as <code>null</code>; it should usually be an exception, error result or retryable failure type.</p>
<p><code>Optional</code> should never itself be <code>null</code>. Returning <code>null</code> from a method declared as <code>Optional&lt;T&gt;</code> combines the worst of both approaches. Also avoid using <code>Optional</code> where serialization frameworks, entity mapping or hot allocation paths make it awkward.</p>
<p>Nullability annotations are not all identical. Teams should standardize on one annotation set and configure IDEs/build tools to treat violations consistently.</p>
</td>
<td valign="top" width="50%">
<p>Разной семантике отсутствия значения нужны разные типы. “No rows” обычно соответствует пустому list. “Maybe one row” может соответствовать <code>Optional&lt;T&gt;</code>. “Remote service failed” не должен кодироваться как <code>null</code>; обычно это исключение, результат с ошибкой или тип retryable-сбоя.</p>
<p><code>Optional</code> сам никогда не должен быть <code>null</code>. Возврат <code>null</code> из метода, объявленного как <code>Optional&lt;T&gt;</code>, объединяет худшее из двух подходов. Также избегайте <code>Optional</code> там, где фреймворки сериализации, маппинг сущностей или горячие пути выделения памяти делают его неудобным.</p>

</td>
<td valign="top" width="50%">

<details>
<summary><strong>🧠 JCORE-OBJ-008. What are the trade-offs between <code>getClass()</code> and <code>instanceof</code> in <code>equals()</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>getClass()</code> makes equality strict: objects are equal only if they have the exact same runtime class. <code>instanceof</code> allows equality across a superclass/subclass boundary. <code>getClass()</code> is safer for many value classes; <code>instanceof</code> is more flexible but can break symmetry or transitivity when subclasses add significant state.</p>
</td>
<td valign="top" width="50%">
<p><code>getClass()</code> делает равенство строгим: объекты равны только при точно одинаковом фактическом классе. <code>instanceof</code> допускает равенство между суперклассом и подклассом. <code>getClass()</code> безопаснее для многих классов-значений; <code>instanceof</code> гибче, но может нарушить симметричность или транзитивность, если подклассы добавляют значимое состояние.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>With <code>getClass()</code>, a <code>Point</code> is never equal to a <code>ColoredPoint</code>, even if their common fields match. This avoids many inheritance problems because equality is defined only inside one concrete class.</p>
<p>With <code>instanceof</code>, a superclass can say “anything that is a Point-like object may be equal”. That can be useful for interfaces or carefully designed hierarchies, but it becomes dangerous when subclasses add fields that should affect equality.</p>
</td>
<td valign="top" width="50%">
<p>С <code>getClass()</code> объект <code>Point</code> никогда не равен <code>ColoredPoint</code>, даже если общие поля совпадают. Это избегает многих проблем наследования, потому что равенство определено только внутри одного конкретного класса.</p>
<p>С <code>instanceof</code> суперкласс может сказать: «любой Point-like объект может быть равен». Это бывает полезно для интерфейсов или аккуратно спроектированных иерархий, но опасно, когда подклассы добавляют поля, которые должны влиять на равенство.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The core issue is the <code>equals()</code> contract. If <code>Point.equals()</code> uses <code>instanceof Point</code> and ignores color, but <code>ColoredPoint.equals()</code> compares color, then <code>point.equals(coloredPoint)</code> and <code>coloredPoint.equals(point)</code> may disagree. That violates symmetry.</p>
<p>For final classes and records, this problem is much smaller because subclasses cannot add equality-relevant state. For non-final classes, prefer designing equality either as final and class-local, or as a documented extensible scheme such as the <code>canEqual</code> pattern.</p>
<p>Framework proxies complicate the choice. Some ORM frameworks create proxy subclasses, so strict <code>getClass()</code> equality may say a proxy and the real entity class are different. Entity equality should be designed together with the persistence framework.</p>
</td>
<td valign="top" width="50%">
<p>Основная проблема — контракт <code>equals()</code>. Если <code>Point.equals()</code> использует <code>instanceof Point</code> и игнорирует color, а <code>ColoredPoint.equals()</code> сравнивает color, то <code>point.equals(coloredPoint)</code> и <code>coloredPoint.equals(point)</code> могут дать разные ответы. Это нарушает симметричность.</p>
<p>Для final-классов и records эта проблема намного меньше, потому что подклассы не могут добавить состояние, участвующее в равенстве. Для non-final классов лучше проектировать равенство либо как final и class-local, либо как документированную расширяемую схему, например паттерн <code>canEqual</code>.</p>
<p>Прокси фреймворков усложняют выбор. Некоторые ORM-фреймворки создают proxy-подклассы, поэтому strict <code>getClass()</code>-равенство может считать proxy и реальный класс сущности разными. Равенство сущностей нужно проектировать вместе с persistence-фреймворком.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For value objects, prefer final classes/records and simple generated equality. For entities, document the equality policy and test it with proxies, transient objects and persisted objects. Avoid subclassable value classes unless there is a strong reason and a carefully designed equality contract.</p>
</td>
<td valign="top" width="50%">
<p>Для объектов-значений предпочитайте final-классы, records и простое сгенерированное равенство. Для сущностей документируйте политику равенства и тестируйте её с прокси, transient-объектами и сохранёнными объектами. Избегайте наследуемых классов-значений, если нет сильной причины и аккуратно спроектированного контракта равенства.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>instanceof</code> returns <code>false</code> for <code>null</code>; <code>obj.getClass()</code> throws NPE if <code>obj</code> is <code>null</code>.</li>
<li><code>getClass()</code> may not work as expected with ORM proxy subclasses.</li>
<li><code>instanceof</code> can break symmetry when subclasses add fields.</li>
<li>For final classes, the practical difference is often small.</li>
</ul>
</td>
<td valign="top" width="50%">
<ul>
<li><code>instanceof</code> возвращает <code>false</code> для <code>null</code>; <code>obj.getClass()</code> бросает NPE, если <code>obj</code> равен <code>null</code>.</li>
<li><code>getClass()</code> может работать неожиданно с ORM proxy-подклассами.</li>
<li><code>instanceof</code> может нарушить симметричность, когда подклассы добавляют поля.</li>
<li>Для final классы практическая разница часто мала.</li>
</ul>
</td>
</tr>

<p>Every Java object has methods from <code>java.lang.Object</code>: <code>getClass()</code>, <code>equals(Object)</code>, <code>hashCode()</code>, <code>toString()</code>, <code>clone()</code>, <code>finalize()</code>, <code>wait()</code>, <code>wait(long)</code>, <code>wait(long,int)</code>, <code>notify()</code> and <code>notifyAll()</code>. <details>
<summary><strong>🧠 JCORE-OBJ-011. Why are <code>clone()</code> and <code>finalize()</code> usually avoided in modern Java?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>clone()</code> is avoided because the <code>Cloneable</code> protocol is awkward, shallow by default, inheritance-hostile and easy to implement incorrectly. <code>finalize()</code> is avoided because finalization is deprecated for removal, unreliable, slow, security-sensitive and not guaranteed to run promptly or at all. Use copy constructors/factories and explicit resource management instead.</p>
</td>
<td valign="top" width="50%">
<p><code>clone()</code> обычно избегают, потому что протокол <code>Cloneable</code> неудобен, по умолчанию делает поверхностную копию, плохо сочетается с наследованием и легко реализуется неправильно. <code>finalize()</code> избегают, потому что финализация помечена как устаревшая for removal, ненадёжна, медленна, security-sensitive и не гарантирует своевременное выполнение или выполнение вообще. Вместо этого используйте копирующие конструкторы или фабрики и явное управление ресурсами.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>Object.clone()</code> performs a field-by-field copy. That is usually a shallow copy, so references to mutable nested objects are shared unless the class fixes them manually. <code>Cloneable</code> is only a marker interface; it does not declare a public <code>clone()</code> method, and without it <code>Object.clone()</code> throws <code>CloneNotSupportedException</code>.</p>
<p><code>finalize()</code> is not a destructor. The garbage collector may call it after an indefinite delay, or not before program exit. Finalizers can resurrect objects, run on unspecified threads, hide exceptions and create performance/security problems. Modern Java prefers <code>try-with-resources</code>, <code>AutoCloseable</code>, and occasionally <code>Cleaner</code> for advanced cleanup safety nets.</p>
</td>
<td valign="top" width="50%">
<p><code>Object.clone()</code> делает копирование поле за полем. Обычно это поверхностная копия, поэтому ссылки на изменяемые вложенные объекты будут общими, если класс вручную это не исправит. <code>Cloneable</code> — только маркерный интерфейс; он не объявляет public-метод <code>clone()</code>, а без него <code>Object.clone()</code> бросает <code>CloneNotSupportedException</code>.</p>
<p><code>finalize()</code> — не деструктор. Сборщик мусора может вызвать его после неопределённой задержки или не вызвать до завершения программы. Финализаторы могут воскрешать объекты, выполняться на неопределённых потоках, скрывать исключения и создавать проблемы производительности и безопасности. Modern Java предпочитает <code>try-with-resources</code>, <code>AutoCloseable</code> и иногда <code>Cleaner</code> как дополнительную страховку для очистки ресурсов.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Copying is usually clearer when expressed explicitly: a copy constructor, static factory, builder, record “with” style method, or domain-specific copy method can state whether the copy is shallow, deep or partially transformed. These approaches can validate invariants and do not depend on <code>Cloneable</code> conventions.</p>
<p>Resource cleanup should also be explicit. Files, sockets, database connections and native handles should be closed deterministically with <code>try-with-resources</code> or lifecycle management from the owning framework. A GC-triggered cleanup mechanism cannot guarantee timely release of scarce external resources.</p>
<p><code>Cleaner</code> and phantom references are safer than finalizers for some advanced cases, but they are still not a substitute for explicit close when timely release is required.</p>
</td>
<td valign="top" width="50%">
<p>Копирование обычно яснее выражается явно: копирующий конструктор, статическая фабрика, builder, record-метод в стиле “with” или доменный метод копирования может указать, является ли копия поверхностной, глубокой или частично преобразованной. Эти подходы могут проверять инварианты и не зависят от соглашений <code>Cloneable</code>.</p>
<p>Очистка ресурсов тоже должна быть явной. Файлы, сокеты, соединения с базой данных и нативные handles должны закрываться детерминированно через <code>try-with-resources</code> или управление жизненным циклом во владеющем фреймворке. Механизм очистки, запускаемый GC, не может гарантировать своевременное освобождение дефицитных внешних ресурсов.</p>
<p><code>Cleaner</code> и phantom references безопаснее финализаторов для некоторых продвинутых случаев, но они всё равно не заменяют явный close, когда нужно своевременное освобождение.</p>
</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Expose intentional copy APIs and document their depth. For resources, implement <code>AutoCloseable</code>, use <code>try-with-resources</code>, and let dependency injection containers manage lifecycle where appropriate. Treat finalizer warnings as migration work, not as harmless noise.</p>
</td>
<td valign="top" width="50%">
<p>Предоставляйте intentional copy APIs и документируйте их depth. Для ресурсы реализуйте <code>AutoCloseable</code>, используйте <code>try-with-resources</code> и позволяйте зависимость injection containers управлять жизненный цикл там, где это уместно. Рассматривайте предупреждения о финализаторах как работу по миграции, а не безобидный шум.</p>
</td>
</tr>
