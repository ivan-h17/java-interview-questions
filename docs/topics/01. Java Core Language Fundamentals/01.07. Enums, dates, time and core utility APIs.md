# 01.07. Enums, dates, time and core utility APIs

---

<a id="jcore-api-001"></a>

<details>
<summary><strong>JCORE-API-001. What are enums good for in backend code?</strong></summary>

#### Short answer

Enums are good for small, closed sets of named values: statuses, modes, directions, roles inside code, feature states, and strategy choices. They give type safety, readable names, and a single place for behavior related to those values.

#### Interview answer

In an interview I would say: use an enum when the set is controlled by the application and changes through code releases. Compared with strings or integers, enums make invalid values harder to pass around and make switch logic, validation, and serialization rules more explicit.

Enums can also carry behavior. For example, a payment status can expose whether it is terminal, or a pricing policy enum can implement different calculation logic per constant. That said, enums are not a replacement for database reference tables when business users need to add values without redeploying code.

#### Deep dive

Every enum constant is a singleton instance of the enum type. This means enums can have fields, methods, interfaces, and constant-specific class bodies. The closed nature of enums also makes them useful with exhaustive switch logic, because the compiler knows the finite set of constants.

#### Production angle

In backend services, enums are useful for internal domain states and protocol-level values, but the external representation must be stable. Persist or expose a stable code or name deliberately; do not let an internal refactoring silently change API or database meaning.

#### Traps / caveats

- Do not use an enum for data that is open-ended or tenant-configurable.
- Be careful when exposing enum names in public APIs: renaming a constant can become a breaking change.
- Do not put heavy mutable state into enum constants.
- Do not persist `ordinal()` as a business value.

#### Optional Anki

Q: When is an enum a good model?
A: When the value set is small, closed, type-safe, and owned by the codebase.

</details>

<details>
<summary><strong>JCORE-API-002. How can enums have fields, methods and constructors?</strong></summary>

#### Short answer

A Java enum is a special class. Its constants are instances created by private enum constructors during class initialization, so the enum type can define fields, methods, constructors, and constant-specific behavior.

#### Interview answer

An enum constructor is implicitly private; you cannot create enum instances with `new`. The constants at the top of the enum declaration call that constructor. For example, `ACTIVE("A")` can initialize a stable external code stored in a final field.

Methods can expose metadata, implement business decisions, or satisfy an interface. For more advanced cases, each constant can override an abstract method in a constant-specific class body.

#### Deep dive

A common pattern is to keep immutable fields in enum constants: a database code, display key, retry policy, or severity. Another pattern is enum-as-strategy, where constants implement a small variation of behavior. This can be clean for a closed set but becomes awkward if the set grows often.

#### Production angle

In production code, enum fields should usually be immutable and initialized eagerly. If an enum needs dependencies from Spring or another container, prefer mapping from the enum to a service elsewhere instead of trying to inject mutable framework state into enum constants.

#### Traps / caveats

- Enum constructors cannot be public or protected.
- Constants must appear before fields and methods.
- Avoid mutable fields in enum constants unless the state is carefully synchronized.
- Constant-specific behavior is powerful, but overuse can hide complex business logic in a type that looks simple.

#### Optional Anki

Q: Why can an enum have a constructor?
A: Because enum constants are instances initialized by that constructor, but no new instances can be created by user code.

</details>

<details>
<summary><strong>JCORE-API-003. Why is persisting enum `ordinal()` usually dangerous?</strong></summary>

#### Short answer

`ordinal()` is the declaration position of an enum constant. Persisting it is dangerous because inserting, removing, or reordering constants changes the stored meaning without any database schema change.

#### Interview answer

If `PENDING` has ordinal 0 and `PAID` has ordinal 1, then adding a new constant before them shifts the numbers. Old rows may suddenly be interpreted as different statuses. That is a silent data corruption risk.

Persist a stable representation instead: a string name if names are part of the contract, or better a dedicated stable code such as `"P"`, `"PAID"`, or a database lookup key.

#### Deep dive

`ordinal()` exists mainly for low-level enum infrastructure such as `EnumSet` and `EnumMap`. It is not a business identifier. A business identifier should remain stable across source-code reordering and refactoring.

#### Production angle

With JPA, prefer `EnumType.STRING` over `EnumType.ORDINAL` for simple cases, or use an explicit converter for stable external codes. For public APIs, document unknown-value handling and backward compatibility expectations.

#### Traps / caveats

- Reordering enum constants becomes a data migration if ordinal values are persisted.
- `name()` is safer than ordinal, but renaming constants can still break persisted data.
- A stable code field is often the best persistence boundary.
- Do not use `ordinal()` in JSON contracts or database columns unless the numbers are explicitly versioned protocol values.

#### Optional Anki

Q: Why not store enum ordinal?
A: It depends on source declaration order, so code refactoring can change persisted meaning.

</details>

<details>
<summary><strong>JCORE-API-004. What should an API do with unknown enum values from clients or external systems?</strong></summary>

#### Short answer

It should handle them deliberately. For client input, often reject unknown values with a clear validation error. For external systems, a tolerant reader may map unknown values to `UNKNOWN`, preserve the raw value, log/measure it, and avoid silently treating it as a valid known state.

#### Interview answer

The right policy depends on direction. Inbound commands from your clients usually need strict validation because an unknown enum means the client sent unsupported input. Inbound events from partner systems may need forward compatibility: their system can deploy a new enum before yours.

The important rule is not to default unknown values to a business meaning like `ACTIVE` or `STANDARD`. That hides incompatibility and can cause incorrect decisions.

#### Deep dive

A robust design separates parsing from decision-making. Parsing can produce a value object containing `knownEnum` and `rawValue`, or an enum with `UNKNOWN` plus metadata. Decision code should then explicitly decide whether unknown is allowed in that context.

#### Production angle

In public REST APIs, return a stable error shape for unsupported values and document enum evolution. In event-driven systems, monitor unknown values and route them to dead-letter queues or compatibility paths if processing safely is impossible.

#### Traps / caveats

- Do not silently coerce unknown values to a default business value.
- Do not lose the raw external value if it is needed for diagnostics or replay.
- A single `UNKNOWN` constant may not be enough if different unknown values must be preserved.
- Strict validation and tolerant reading are both valid; choose by boundary and compatibility needs.

#### Optional Anki

Q: What is the worst way to handle an unknown enum?
A: Silently map it to a valid business default.

</details>

<a id="jcore-api-005"></a>

<details>
<summary><strong>JCORE-API-005. How does the Java Date/Time API improve over `Date` and `Calendar`?</strong></summary>

#### Short answer

The `java.time` API is clearer, mostly immutable, thread-safe by design, and separates concepts such as instant, local date, local date-time, offset, time zone, duration, and period. `Date` and `Calendar` are mutable and historically confusing.

#### Interview answer

With the old API, a `Date` represents an instant but its name suggests a calendar date; formatting and time zones are handled elsewhere; `Calendar` is mutable and verbose. `java.time` gives types that say what they mean: `Instant` for machine time, `LocalDate` for a date without a zone, `ZonedDateTime` for a local date-time in a region zone.

The new API also has fluent operations, explicit formatters, better parsing, and a clear separation between human calendar arithmetic and machine-time arithmetic.

#### Deep dive

The key conceptual improvement is explicitness. If code stores `LocalDateTime`, it is saying “no offset or zone is attached.” If it stores `Instant`, it is saying “a point on the UTC time-line.” This prevents many accidental conversions through the default time zone.

#### Production angle

For backend services, prefer `Instant` for audit timestamps and event time, `LocalDate` for business dates such as birth date or invoice date, and explicit `ZoneId` when presenting or scheduling local times. Keep old API types mostly at integration boundaries.

#### Traps / caveats

- Do not use `LocalDateTime` as if it were an absolute timestamp.
- Do not rely on the JVM default time zone for business logic.
- Be explicit when converting between old and new date/time APIs.
- Remember that immutability does not remove time-zone complexity.

#### Optional Anki

Q: What is the main advantage of `java.time`?
A: It uses explicit, mostly immutable types for different date/time concepts.

</details>

<details>
<summary><strong>JCORE-API-006. What is the difference between `Instant`, `LocalDateTime`, `OffsetDateTime` and `ZonedDateTime`?</strong></summary>

#### Short answer

`Instant` is an absolute point on the UTC time-line. `LocalDateTime` is calendar date and wall-clock time without offset or zone. `OffsetDateTime` adds a fixed UTC offset. `ZonedDateTime` adds a region time zone with daylight-saving rules.

#### Interview answer

Use `Instant` for storage and event timestamps when you need a precise moment. Use `LocalDateTime` only when the local date and time are meaningful without choosing a zone yet, for example a draft schedule form. Use `OffsetDateTime` for wire formats that include an offset. Use `ZonedDateTime` for business rules tied to a region such as `Europe/Berlin`.

A fixed offset like `+02:00` is not the same as a time zone like `Europe/Berlin`. The zone contains historical and future rules; the offset is just one numeric shift at one moment.

#### Deep dive

The conversion direction matters. `LocalDateTime` plus a `ZoneId` can map to zero, one, or two valid instants around daylight-saving transitions. `Instant` plus a zone maps to a single local representation.

#### Production angle

A common backend rule is: store `Instant` for facts that already happened, store the user's `ZoneId` for presentation or scheduling, and avoid dropping offset/zone information accidentally when parsing request payloads.

#### Traps / caveats

- `LocalDateTime` has no time zone and is not a timestamp.
- `OffsetDateTime` has an offset but not full regional rules.
- `ZonedDateTime` can change offset depending on date because of zone rules.
- `Instant` is great for machines but not enough to express a local recurring schedule.

#### Optional Anki

Q: Which type is a true absolute timestamp?
A: `Instant`.

</details>

<details>
<summary><strong>JCORE-API-007. Why are time zones and daylight saving time common backend bug sources?</strong></summary>

#### Short answer

Because local time is not a simple continuous line. Daylight-saving transitions can skip local times, repeat local times, and create days that are not 24 hours long. Time-zone rules also change by country and over time.

#### Interview answer

Bugs appear when code assumes that adding 24 hours means “same local time tomorrow,” that every local time exists, or that an offset uniquely identifies a time zone. They also appear when servers, databases, containers, and clients use different default zones.

For example, scheduling a job at 02:30 local time can fail on a spring-forward day because 02:30 may not exist. In autumn, the same local time may occur twice.

#### Deep dive

Calendar arithmetic and duration arithmetic are different. `plusDays(1)` in a zone means “next calendar day,” while `plus(Duration.ofHours(24))` means exactly 24 hours later. Around DST, these can differ.

#### Production angle

In production, store facts as instants, store user or business zones explicitly, test DST boundaries, and avoid hidden defaults. For recurring schedules, persist the local rule and zone, not only the next computed instant.

#### Traps / caveats

- Do not assume every day has 24 hours.
- Do not assume every local time exists exactly once.
- Do not treat offset and time zone as equivalent.
- Do not rely on the system default zone in distributed services.

#### Optional Anki

Q: Why can 02:30 be a dangerous scheduled time?
A: Around daylight-saving transitions it may not exist or may occur twice.

</details>

<details>
<summary><strong>JCORE-API-008. Why is `Clock` useful for testing date/time logic?</strong></summary>

#### Short answer

`Clock` lets code receive the current time as a dependency instead of calling `Instant.now()` or `LocalDate.now()` directly. Tests can inject a fixed or offset clock and become deterministic.

#### Interview answer

Time-dependent code is otherwise hard to test: the result changes every time the test runs, midnight can break assertions, and time-zone differences between machines can cause flaky failures. Injecting `Clock` moves “what time is it?” to the edge of the code.

Production code can use `Clock.systemUTC()` or a configured zone. Tests can use `Clock.fixed(...)` for a constant instant or `Clock.offset(...)` to simulate time passing.

#### Deep dive

Many `java.time` factory methods have overloads accepting a `Clock`, such as `Instant.now(clock)` and `LocalDate.now(clock)`. That makes the dependency explicit without inventing a custom time provider.

#### Production angle

Use one application-level time source for business logic. This simplifies testing expiration, retries, billing periods, token validity, and scheduling. It also avoids tests that pass locally but fail on CI because the wall clock moved.

#### Traps / caveats

- Do not call `now()` directly deep inside domain logic if the value must be testable.
- Use the same clock consistently inside one operation; multiple `now()` calls can cross a boundary.
- Remember that a clock has a zone, which matters for `LocalDate.now(clock)`.
- A fixed clock is for deterministic tests, not for measuring elapsed performance time.

#### Optional Anki

Q: What problem does `Clock` solve in tests?
A: It replaces real wall-clock time with an injected, deterministic time source.

</details>

<details>
<summary><strong>🧠 JCORE-API-009. What are common traps with default locale, default charset and default time zone?</strong></summary>

#### Short answer

Defaults are environment-dependent. Locale affects case conversion and formatting, charset affects byte/string conversion, and time zone affects date/time interpretation. Backend code should make these choices explicit at system boundaries.

#### Interview answer

A classic locale trap is Turkish casing: case-insensitive identifiers can behave unexpectedly if code uses the default locale. For machine-readable text, use `Locale.ROOT` or a specified locale. For user-facing text, use the user's locale intentionally.

For bytes and strings, specify `StandardCharsets.UTF_8` instead of relying on platform defaults. Modern JDKs use UTF-8 as the default charset, but explicit charset is still clearer at API boundaries. For time, avoid `ZoneId.systemDefault()` in business logic unless that is truly the contract.

#### Deep dive

These defaults are global process settings, so they are especially dangerous in containers, tests, and multi-region deployments. A service may pass tests on a developer laptop but fail in CI or production where locale, charset, or time zone differ.

#### Production angle

Set process defaults deliberately where needed, but do not make core logic depend on them. Parse and format external data with explicit locale, charset, and zone. Add tests that run with non-default locale and time zone for critical code.

#### Traps / caveats

- Use `Locale.ROOT` for locale-independent machine strings.
- Use explicit `Charset`, usually `UTF_8`, at byte/string boundaries.
- Use explicit `ZoneId` for date/time business logic.
- Do not assume development-machine defaults match production.

#### Optional Anki

Q: What is the safe rule for locale, charset and zone?
A: Make them explicit at system boundaries and avoid hidden process defaults in business logic.

</details>
