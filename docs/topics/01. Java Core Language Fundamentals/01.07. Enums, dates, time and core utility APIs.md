# 7. Enums, dates, time and core utility APIs


<a id="jcore-api-001"></a>

<details>
<summary><strong>JCORE-API-001. What are enums good for in backend code?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Enums are good for small, closed sets of named values: statuses, modes, directions, roles inside code, feature states, and strategy choices. They give type safety, readable names, and a single place for behavior related to those values.</p>
</td>
<td valign="top" width="50%">

<p><code>enum</code> хорошо подходит для небольшого закрытого набора значений: статусов, режимов, направлений, внутренних ролей, состояний функции или вариантов стратегии. Он даёт типобезопасность, понятные имена и одно место для поведения, связанного с этими значениями.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In an interview I would say: use an enum when the set is controlled by the application and changes through code releases. Compared with strings or integers, enums make invalid values harder to pass around and make switch logic, validation, and serialization rules more explicit.</p>
<p>Enums can also carry behavior. For example, a payment status can expose whether it is terminal, or a pricing policy enum can implement different calculation logic per constant. That said, enums are not a replacement for database reference tables when business users need to add values without redeploying code.</p>
</td>
<td valign="top" width="50%">

<p>На интервью я бы сказал так: <code>enum</code> нужен, когда набор значений контролируется кодом приложения и меняется вместе с релизом. По сравнению со строками и числами он снижает риск передать недопустимое значение и делает проверки, <code>switch</code> и правила сериализации более явными.</p>
<p><code>enum</code> может хранить не только имя, но и поведение. Например, статус платежа может знать, является ли он конечным, а вариант тарификации — выполнять свою формулу. Но если значения должны добавляться пользователями через админку, обычно нужна таблица-справочник, а не <code>enum</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Every enum constant is a singleton instance of the enum type. This means enums can have fields, methods, interfaces, and constant-specific class bodies. The closed nature of enums also makes them useful with exhaustive switch logic, because the compiler knows the finite set of constants.</p>
</td>
<td valign="top" width="50%">

<p>Каждая константа <code>enum</code> — это единственный экземпляр соответствующего типа. Поэтому у <code>enum</code> могут быть поля, методы, реализация интерфейсов и даже отдельное поведение для конкретной константы. Закрытый набор значений также помогает писать исчерпывающий <code>switch</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In backend services, enums are useful for internal domain states and protocol-level values, but the external representation must be stable. Persist or expose a stable code or name deliberately; do not let an internal refactoring silently change API or database meaning.</p>
</td>
<td valign="top" width="50%">

<p>В серверных сервисах <code>enum</code> удобен для внутренних состояний и значений протокола, но внешнее представление должно быть стабильным. В БД и публичном API лучше явно хранить выбранный код или имя, чтобы рефакторинг не изменил смысл данных.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not use an enum for data that is open-ended or tenant-configurable.</li>
<li>Be careful when exposing enum names in public APIs: renaming a constant can become a breaking change.</li>
<li>Do not put heavy mutable state into enum constants.</li>
<li>Do not persist <code>ordinal()</code> as a business value.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не используйте <code>enum</code> для открытого или настраиваемого пользователями справочника.</li>
<li>Если имя константы попало в публичный API, переименование становится несовместимым изменением.</li>
<li>Не кладите в константы тяжёлое изменяемое состояние.</li>
<li>Не храните <code>ordinal()</code> как бизнес-значение.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: When is an enum a good model?<br>A: When the value set is small, closed, type-safe, and owned by the codebase.</p>
</td>
<td valign="top" width="50%">

<p>Q: Когда <code>enum</code> подходит для модели?<br>A: Когда набор значений небольшой, закрытый, типобезопасный и управляется кодом.</p>

</td>
</tr>

<details>
<summary><strong>JCORE-API-002. How can enums have fields, methods and constructors?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A Java enum is a special class. Its constants are instances created by private enum constructors during class initialization, so the enum type can define fields, methods, constructors, and constant-specific behavior.</p>
</td>
<td valign="top" width="50%">

<p><code>enum</code> в Java — это особый класс. Его константы являются экземплярами, созданными закрытыми конструкторами во время инициализации класса, поэтому у <code>enum</code> могут быть поля, методы, конструкторы и поведение, заданное для отдельной константы.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>An enum constructor is implicitly private; you cannot create enum instances with <code>new</code>. The constants at the top of the enum declaration call that constructor. For example, <code>ACTIVE("A")</code> can initialize a stable external code stored in a final field.</p>
<p>Methods can expose metadata, implement business decisions, or satisfy an interface. For more advanced cases, each constant can override an abstract method in a constant-specific class body.</p>
</td>
<td valign="top" width="50%">

<p>Конструктор <code>enum</code> фактически закрыт: создать новую константу через <code>new</code> нельзя. Константы в начале объявления вызывают этот конструктор. Например, <code>ACTIVE("A")</code> может заполнить стабильный внешний код в <code>final</code>-поле.</p>
<p>Методы могут возвращать метаданные, выражать бизнес-правило или реализовывать интерфейс. В более сложных случаях каждая константа может переопределить абстрактный метод в собственном теле константы.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A common pattern is to keep immutable fields in enum constants: a database code, display key, retry policy, or severity. Another pattern is enum-as-strategy, where constants implement a small variation of behavior. This can be clean for a closed set but becomes awkward if the set grows often.</p>
</td>
<td valign="top" width="50%">

<p>Распространённый приём — хранить в константах неизменяемые поля: код для БД, ключ для отображения, политику повторов или уровень серьёзности. Другой приём — <code>enum</code> как стратегия, когда константы реализуют разные варианты поведения. Это удобно для закрытого набора, но плохо масштабируется, если варианты часто появляются.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production code, enum fields should usually be immutable and initialized eagerly. If an enum needs dependencies from Spring or another container, prefer mapping from the enum to a service elsewhere instead of trying to inject mutable framework state into enum constants.</p>
</td>
<td valign="top" width="50%">

<p>В промышленном коде поля <code>enum</code> обычно должны быть неизменяемыми и заполняться при создании констант. Если для поведения нужны зависимости из Spring или другого контейнера, лучше вынести сопоставление <code>enum</code> с сервисом наружу, а не пытаться внедрять изменяемое состояние прямо в константы.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Enum constructors cannot be public or protected.</li>
<li>Constants must appear before fields and methods.</li>
<li>Avoid mutable fields in enum constants unless the state is carefully synchronized.</li>
<li>Constant-specific behavior is powerful, but overuse can hide complex business logic in a type that looks simple.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Конструктор <code>enum</code> не бывает <code>public</code> или <code>protected</code>.</li>
<li>Константы должны быть объявлены перед полями и методами.</li>
<li>Изменяемые поля в константах требуют синхронизации и обычно не нужны.</li>
<li>Поведение в отдельных константах удобно, но при злоупотреблении прячет сложную бизнес-логику в внешне простом типе.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why can an enum have a constructor?<br>A: Because enum constants are instances initialized by that constructor, but no new instances can be created by user code.</p>
</td>
<td valign="top" width="50%">

<p>Q: Зачем <code>enum</code> конструктор?<br>A: Им создаются константы <code>enum</code>, но пользовательский код не может создать новые экземпляры.</p>

</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>JCORE-API-003. Why is persisting enum <code>ordinal()</code> usually dangerous?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>ordinal()</code> is the declaration position of an enum constant. Persisting it is dangerous because inserting, removing, or reordering constants changes the stored meaning without any database schema change.</p>
</td>
<td valign="top" width="50%">

<p><code>ordinal()</code> — это позиция константы в объявлении <code>enum</code>. Хранить её опасно: добавление, удаление или перестановка констант меняет смысл уже сохранённых данных без изменения схемы БД.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>If <code>PENDING</code> has ordinal 0 and <code>PAID</code> has ordinal 1, then adding a new constant before them shifts the numbers. Old rows may suddenly be interpreted as different statuses. That is a silent data corruption risk.</p>
<p>Persist a stable representation instead: a string name if names are part of the contract, or better a dedicated stable code such as <code>"P"</code>, <code>"PAID"</code>, or a database lookup key.</p>
</td>
<td valign="top" width="50%">

<p>Если у <code>PENDING</code> был номер 0, а у <code>PAID</code> — 1, то новая константа в начале списка сдвинет номера. Старые строки могут начать читаться как другие статусы. Это риск тихой порчи данных.</p>
<p>Лучше хранить стабильное представление: имя, если оно стало частью контракта, или отдельный стабильный код вроде <code>"P"</code>, <code>"PAID"</code> либо ключ справочника.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>ordinal()</code> exists mainly for low-level enum infrastructure such as <code>EnumSet</code> and <code>EnumMap</code>. It is not a business identifier. A business identifier should remain stable across source-code reordering and refactoring.</p>
</td>
<td valign="top" width="50%">

<p><code>ordinal()</code> нужен в основном для низкоуровневой инфраструктуры <code>enum</code>, например <code>EnumSet</code> и <code>EnumMap</code>. Это не бизнес-идентификатор. Бизнес-идентификатор должен оставаться стабильным при перестановке кода и рефакторинге.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>With JPA, prefer <code>EnumType.STRING</code> over <code>EnumType.ORDINAL</code> for simple cases, or use an explicit converter for stable external codes. For public APIs, document unknown-value handling and backward compatibility expectations.</p>
</td>
<td valign="top" width="50%">

<p>В JPA для простых случаев обычно выбирают <code>EnumType.STRING</code>, а не <code>EnumType.ORDINAL</code>. Для стабильных внешних кодов лучше написать явный конвертер. В публичном API нужно отдельно описать совместимость и обработку неизвестных значений.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Reordering enum constants becomes a data migration if ordinal values are persisted.</li>
<li><code>name()</code> is safer than ordinal, but renaming constants can still break persisted data.</li>
<li>A stable code field is often the best persistence boundary.</li>
<li>Do not use <code>ordinal()</code> in JSON contracts or database columns unless the numbers are explicitly versioned protocol values.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Перестановка констант превращается в миграцию данных, если в БД лежит <code>ordinal()</code>.</li>
<li><code>name()</code> безопаснее номера, но переименование констант тоже ломает сохранённые данные.</li>
<li>Стабильное поле-код часто лучше подходит для границы с БД или API.</li>
<li>Не используйте <code>ordinal()</code> в JSON-контрактах и колонках БД без явно версионированного протокола.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why not store enum ordinal?<br>A: It depends on source declaration order, so code refactoring can change persisted meaning.</p>
</td>
<td valign="top" width="50%">

<p>Q: Почему не стоит хранить <code>ordinal()</code>?<br>A: Он зависит от порядка объявления, поэтому рефакторинг может изменить смысл сохранённых данных.</p>

</td>
</tr>

<a id="jcore-api-004"></a>

<details>
<summary><strong>JCORE-API-004. What should an API do with unknown enum values from clients or external systems?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>It should handle them deliberately. For client input, often reject unknown values with a clear validation error. For external systems, a tolerant reader may map unknown values to <code>UNKNOWN</code>, preserve the raw value, log/measure it, and avoid silently treating it as a valid known state.</p>
</td>
<td valign="top" width="50%">

<p>API должен обрабатывать неизвестные значения явно. В пользовательском запросе их часто лучше отклонить понятной ошибкой валидации. Для внешних систем может подойти устойчивое чтение: сопоставить значение с <code>UNKNOWN</code>, сохранить исходную строку, залогировать событие и не выдавать его за известное состояние.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The right policy depends on direction. Inbound commands from your clients usually need strict validation because an unknown enum means the client sent unsupported input. Inbound events from partner systems may need forward compatibility: their system can deploy a new enum before yours.</p>
<p>The important rule is not to default unknown values to a business meaning like <code>ACTIVE</code> or <code>STANDARD</code>. That hides incompatibility and can cause incorrect decisions.</p>
</td>
<td valign="top" width="50%">

<p>Политика зависит от направления обмена. Команды от ваших клиентов обычно требуют строгой валидации: неизвестное значение означает неподдерживаемый ввод. А события от партнёрской системы иногда нужно читать терпимо, потому что партнёр может выпустить новое значение раньше вас.</p>
<p>Главное — не подставлять неизвестному значению бизнес-смысл вроде <code>ACTIVE</code> или <code>STANDARD</code>. Такое поведение прячет несовместимость и ведёт к неправильным решениям.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A robust design separates parsing from decision-making. Parsing can produce a value object containing <code>knownEnum</code> and <code>rawValue</code>, or an enum with <code>UNKNOWN</code> plus metadata. Decision code should then explicitly decide whether unknown is allowed in that context.</p>
</td>
<td valign="top" width="50%">

<p>Надёжный дизайн отделяет разбор значения от принятия решения. Разбор может вернуть объект с известным <code>enum</code> и исходной строкой либо <code>enum</code> с вариантом <code>UNKNOWN</code> и дополнительными данными. Код, принимающий решение, должен отдельно проверить, допустимо ли неизвестное значение в этом сценарии.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In public REST APIs, return a stable error shape for unsupported values and document enum evolution. In event-driven systems, monitor unknown values and route them to dead-letter queues or compatibility paths if processing safely is impossible.</p>
</td>
<td valign="top" width="50%">

<p>В публичном REST API лучше возвращать стабильный формат ошибки и документировать правила развития <code>enum</code>. В событийных системах неизвестные значения стоит измерять метриками и при невозможности безопасной обработки отправлять в очередь недоставленных сообщений (dead-letter queue) или отдельный путь совместимости.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not silently coerce unknown values to a default business value.</li>
<li>Do not lose the raw external value if it is needed for diagnostics or replay.</li>
<li>A single <code>UNKNOWN</code> constant may not be enough if different unknown values must be preserved.</li>
<li>Strict validation and tolerant reading are both valid; choose by boundary and compatibility needs.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не подменяйте неизвестное значение бизнес-значением по умолчанию.</li>
<li>Не теряйте исходную строку, если она нужна для диагностики или повторной обработки.</li>
<li>Одной константы <code>UNKNOWN</code> может быть мало, если важно различать неизвестные значения.</li>
<li>Строгая валидация и терпимое чтение оба допустимы; выбор зависит от границы системы и требований совместимости.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the worst way to handle an unknown enum?<br>A: Silently map it to a valid business default.</p>
</td>
<td valign="top" width="50%">

<p>Q: Какой худший способ обработать неизвестный <code>enum</code>?<br>A: Молча заменить его допустимым бизнес-значением.</p>

<a id="jcore-api-005"></a>

<details>
<summary><strong>JCORE-API-005. How does the Java Date/Time API improve over <code>Date</code> and <code>Calendar</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The <code>java.time</code> API is clearer, mostly immutable, thread-safe by design, and separates concepts such as instant, local date, local date-time, offset, time zone, duration, and period. <code>Date</code> and <code>Calendar</code> are mutable and historically confusing.</p>
</td>
<td valign="top" width="50%">

<p>API <code>java.time</code> яснее, в основном неизменяемый и рассчитан на безопасное использование между потоками. Он разделяет разные понятия: момент времени, локальную дату, локальные дату и время, смещение, часовой пояс, длительность и календарный период. Старые <code>Date</code> и <code>Calendar</code> изменяемы и часто приводят к путанице.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>With the old API, a <code>Date</code> represents an instant but its name suggests a calendar date; formatting and time zones are handled elsewhere; <code>Calendar</code> is mutable and verbose. <code>java.time</code> gives types that say what they mean: <code>Instant</code> for machine time, <code>LocalDate</code> for a date without a zone, <code>ZonedDateTime</code> for a local date-time in a region zone.</p>
<p>The new API also has fluent operations, explicit formatters, better parsing, and a clear separation between human calendar arithmetic and machine-time arithmetic.</p>
</td>
<td valign="top" width="50%">

<p>В старом API <code>Date</code> фактически представляет момент времени, хотя название выглядит как календарная дата; форматирование и часовые пояса находятся в других классах; <code>Calendar</code> изменяемый и многословный. В <code>java.time</code> типы говорят точнее: <code>Instant</code> — машинный момент времени, <code>LocalDate</code> — дата без зоны, <code>ZonedDateTime</code> — локальные дата и время в региональном часовом поясе.</p>
<p>Новый API также даёт удобные операции, явные форматтеры, более понятный разбор строк и разделяет календарные вычисления для людей и арифметику машинного времени.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>Главное улучшение — явность. Если код хранит <code>LocalDateTime</code>, он говорит: «смещение и зона не указаны». Если хранит <code>Instant</code>, он говорит: «точка на временной шкале UTC». Это снижает число случайных преобразований через часовой пояс по умолчанию.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For backend services, prefer <code>Instant</code> for audit timestamps and event time, <code>LocalDate</code> for business dates such as birth date or invoice date, and explicit <code>ZoneId</code> when presenting or scheduling local times. Keep old API types mostly at integration boundaries.</p>
</td>
<td valign="top" width="50%">

<p>В серверных сервисах <code>Instant</code> обычно подходит для аудита и времени событий, <code>LocalDate</code> — для бизнес-дат вроде даты рождения или даты счёта, а для показа и расписаний нужен явный <code>ZoneId</code>. Старые типы лучше оставлять только на границах интеграции.</p>

</tr>
<tr>
<td valign="top" width="50%">

<summary><strong>JCORE-API-006. What is the difference between <code>Instant</code>, <code>LocalDateTime</code>, <code>OffsetDateTime</code> and <code>ZonedDateTime</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>Instant</code> is an absolute point on the UTC time-line. <code>LocalDateTime</code> is calendar date and wall-clock time without offset or zone. <code>OffsetDateTime</code> adds a fixed UTC offset. <code>ZonedDateTime</code> adds a region time zone with daylight-saving rules.</p>
</td>
<td valign="top" width="50%">

<p><code>Instant</code> — абсолютная точка на временной шкале UTC. <code>LocalDateTime</code> — календарные дата и время без смещения и зоны. <code>OffsetDateTime</code> добавляет фиксированное смещение от UTC. <code>ZonedDateTime</code> добавляет региональный часовой пояс с правилами перехода на летнее и зимнее время.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use <code>Instant</code> for storage and event timestamps when you need a precise moment. Use <code>LocalDateTime</code> only when the local date and time are meaningful without choosing a zone yet, for example a draft schedule form. <p>A fixed offset like <code>+02:00</code> is not the same as a time zone like <code>Europe/Berlin</code>. The zone contains historical and future rules; the offset is just one numeric shift at one moment.</p>
</td>
<td valign="top" width="50%">

<p><code>Instant</code> используют для хранения и времени событий, когда нужна точная точка во времени. <code>LocalDateTime</code> уместен, когда локальные дата и время важны сами по себе, но зона ещё не выбрана, например в черновике расписания. <code>OffsetDateTime</code> удобен в форматах обмена со смещением. <code>ZonedDateTime</code> нужен для правил, привязанных к региону, например <code>Europe/Berlin</code>.</p>
<p>Фиксированное смещение вроде <code>+02:00</code> не равно часовому поясу <code>Europe/Berlin</code>. Пояс содержит исторические и будущие правила, а смещение — только числовой сдвиг для конкретного момента.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>Направление преобразования важно. <code>LocalDateTime</code> вместе с <code>ZoneId</code> около переходов летнего времени может соответствовать нулю, одному или двум реальным моментам. А <code>Instant</code> вместе с зоной однозначно превращается в локальное представление.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A common backend rule is: store <code>Instant</code> for facts that already happened, store the user's <code>ZoneId</code> for presentation or scheduling, and avoid dropping offset/zone information accidentally when parsing request payloads.</p>
</td>
<td valign="top" width="50%">

<p>Практичное серверное правило: уже произошедшие факты хранить как <code>Instant</code>, пользовательский <code>ZoneId</code> хранить для отображения и расписаний, а при разборе запросов не терять случайно смещение или зону.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>LocalDateTime</code> has no time zone and is not a timestamp.</li>
<li><code>OffsetDateTime</code> has an offset but not full regional rules.</li>
<li><code>ZonedDateTime</code> can change offset depending on date because of zone rules.</li>
<li><code>Instant</code> is great for machines but not enough to express a local recurring schedule.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>LocalDateTime</code> не содержит часовой пояс и не является отметкой времени.</li>
<li><code>OffsetDateTime</code> содержит смещение, но не полные региональные правила.</li>
<li>У <code>ZonedDateTime</code> смещение может меняться в зависимости от даты.</li>
<li><code>Instant</code> удобен для машинного времени, но недостаточен для локального повторяющегося расписания.</li>
</ul>

<summary><strong>JCORE-API-007. Why are time zones and daylight saving time common backend bug sources?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Because local time is not a simple continuous line. Daylight-saving transitions can skip local times, repeat local times, and create days that are not 24 hours long. Time-zone rules also change by country and over time.</p>
</td>
<td valign="top" width="50%">

<p>Потому что локальное время не является простой непрерывной шкалой. Переходы летнего времени могут пропускать локальные моменты, повторять их и создавать дни длиной не 24 часа. Кроме того, правила часовых поясов различаются по странам и меняются со временем.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Bugs appear when code assumes that adding 24 hours means “same local time tomorrow,” that every local time exists, or that an offset uniquely identifies a time zone. They also appear when servers, databases, containers, and clients use different default zones.</p>
<p>For example, scheduling a job at 02:30 local time can fail on a spring-forward day because 02:30 may not exist. In autumn, the same local time may occur twice.</p>
</td>
<td valign="top" width="50%">

<p>Ошибки появляются, когда код считает, что прибавить 24 часа — это «то же локальное время завтра», что любое локальное время существует или что смещение однозначно задаёт часовой пояс. Ещё одна частая причина — разные зоны по умолчанию на сервере, в БД, контейнере и клиенте.</p>
<p>Например, запуск задачи в 02:30 по местному времени может сорваться в день весеннего перевода часов, потому что такого времени может не быть. Осенью тот же локальный момент может встретиться дважды.</p>

<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>Календарная арифметика и арифметика длительностей различаются. <code>plusDays(1)</code> в зоне означает «следующий календарный день», а <code>plus(Duration.ofHours(24))</code> — ровно через 24 часа. Около переходов летнего времени результаты могут отличаться.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, store facts as instants, store user or business zones explicitly, test DST boundaries, and avoid hidden defaults. For recurring schedules, persist the local rule and zone, not only the next computed instant.</p>
</td>
<td valign="top" width="50%">

<p>В промышленном коде уже произошедшие факты лучше хранить как <code>Instant</code>, пользовательскую или бизнес-зону — явно, а переходы летнего времени покрывать тестами. Для повторяющихся расписаний нужно хранить локальное правило и зону, а не только следующий рассчитанный <code>Instant</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not assume every day has 24 hours.</li>
<li>Do not assume every local time exists exactly once.</li>
<li>Do not treat offset and time zone as equivalent.</li>
<li>Do not rely on the system default zone in distributed services.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не считайте, что каждый день длится 24 часа.</li>
<li>Не считайте, что каждое локальное время существует ровно один раз.</li>
<li>Не путайте смещение и часовой пояс.</li>
<li>Не полагайтесь на системную зону по умолчанию в распределённых сервисах.</li>

<summary><strong>🧠 JCORE-API-009. What are common traps with default locale, default charset and default time zone?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Defaults are environment-dependent. Locale affects case conversion and formatting, charset affects byte/string conversion, and time zone affects date/time interpretation. Backend code should make these choices explicit at system boundaries.</p>
</td>
<td valign="top" width="50%">

<p>Значения по умолчанию зависят от окружения. Локаль влияет на преобразование регистра и форматирование, кодировка — на преобразование байтов и строк, часовой пояс — на интерпретацию даты и времени. В серверном коде эти решения лучше явно задавать на границах системы.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>

<tr>

<td valign="top" width="50%">

<p>Классическая ловушка локали — турецкие правила регистра: нечувствительные к регистру идентификаторы могут обрабатываться неожиданно, если использовать локаль по умолчанию. Для машинного текста выбирают <code>Locale.ROOT</code> или явно заданную локаль. Для пользовательского текста — локаль пользователя.</p>
<p>При преобразовании байтов и строк лучше указывать <code>StandardCharsets.UTF_8</code>, а не полагаться на платформу. В современных JDK кодировка по умолчанию — UTF-8, но явная кодировка на границе API всё равно понятнее. Для времени не стоит использовать <code>ZoneId.systemDefault()</code> в бизнес-логике, если это не часть контракта.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>These defaults are global process settings, so they are especially dangerous in containers, tests, and multi-region deployments. A service may pass tests on a developer laptop but fail in CI or production where locale, charset, or time zone differ.</p>
</td>
<td valign="top" width="50%">

<p>Эти настройки относятся ко всему процессу, поэтому особенно опасны в контейнерах, тестах и многорегиональных развёртываниях. Сервис может пройти тесты на ноутбуке разработчика и упасть в CI или в бою, где другая локаль, кодировка или зона.</p>

</td>
</tr>

<td valign="top" width="50%">
<p>Set process defaults deliberately where needed, but do not make core logic depend on them. Parse and format external data with explicit locale, charset, and zone. Add tests that run with non-default locale and time zone for critical code.</p>
