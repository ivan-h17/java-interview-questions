# 01.10. Classpath, modules, compatibility and runtime linkage

---

<a id="jcore-runtime-001"></a>

<details>
<summary><strong>JCORE-RUNTIME-001. What is binary compatibility in Java?</strong></summary>

#### Short answer

Binary compatibility means that already compiled client code can link against a changed library without being recompiled. It is about class-file linkage: names, descriptors, inheritance, fields and methods that existing bytecode expects must still be present in a compatible form.

#### Interview answer

In an interview I would separate this from source compatibility. A source change can be source-compatible but still change overload choices after recompilation, or it can be binary-compatible while new source would no longer compile cleanly. Binary compatibility is checked when the JVM resolves symbolic references from bytecode.

For example, adding a new method is usually binary-compatible. Removing a public method, changing a method descriptor, changing a field to a method, or changing class hierarchy in the wrong way can break already compiled clients with linkage errors.

#### Deep dive

Java bytecode does not store direct memory addresses for most application references. It stores symbolic references such as class names, method names and descriptors. At runtime those references are resolved. If the expected member or type cannot be found in the loaded version, the JVM throws a linkage-related error.

#### Production angle

For backend services this matters during library upgrades and shared model evolution. A dependency can compile in one module but fail in production if another version is placed on the runtime classpath. Treat public APIs and shared DTO/model libraries as compatibility contracts.

#### Traps / caveats

- Binary compatibility does not guarantee correct behavior.
- A clean compilation of one module does not prove the whole runtime classpath is consistent.
- Removing or changing public members is risky even when tests in the changed module pass.
- Linkage errors often appear only when the affected code path is executed.

#### Optional Anki

Q: What does binary compatibility protect?
A: Already compiled clients can link to a changed library without recompilation.

</details>

<a id="jcore-runtime-002"></a>

<details>
<summary><strong>JCORE-RUNTIME-002. What is the difference between source compatibility, binary compatibility and behavioral compatibility?</strong></summary>

#### Short answer

Source compatibility means old source code still compiles. Binary compatibility means old class files still link. Behavioral compatibility means the program still does the same meaningful thing. These are related, but they are not the same promise.

#### Interview answer

Source compatibility is checked by `javac`. Binary compatibility is checked by the JVM when resolving bytecode references. Behavioral compatibility is checked only by tests, monitoring and users, because the compiler cannot know whether a new implementation still satisfies business expectations.

A library can add an overload and remain binary-compatible, but after recompilation client source may bind to a different overload. A method can keep exactly the same signature and remain source- and binary-compatible while changing semantics in a breaking way.

#### Deep dive

The three categories answer different questions: “Can I compile?”, “Can I start/link?”, and “Will it behave correctly?”. Mature API evolution needs all three, especially when several services share libraries but are released independently.

#### Production angle

In production, compatibility should be tested at the integration boundary. Use dependency convergence checks, contract tests, canary releases and backward-compatible API evolution rules, not only local unit tests.

#### Traps / caveats

- Source-compatible changes may change overload resolution after recompilation.
- Binary-compatible changes may still break behavior.
- Behavioral compatibility is often the hardest one to specify and test.
- Semantic versioning is helpful only when maintainers follow it accurately.

#### Optional Anki

Q: Which compatibility type says old `.class` files still link?
A: Binary compatibility.

</details>

<a id="jcore-runtime-003"></a>

<details>
<summary><strong>JCORE-RUNTIME-003. How do Java version upgrades affect backend applications?</strong></summary>

#### Short answer

A Java version upgrade can affect compilation, runtime behavior, dependency compatibility, JVM flags, GC behavior, TLS/security defaults, reflection access, observability agents and container images. The application may compile but still fail because a dependency, framework or startup flag is no longer compatible.

#### Interview answer

The first question is what changes: the JDK used to build, the bytecode target, or the runtime JVM. `--release` controls which platform API and class-file target are used by `javac`. Running the same bytecode on a newer JVM is usually supported, but stronger encapsulation, removed options and library assumptions can still cause failures.

Backend upgrades also change the operating environment: Docker base image, CA certificates, timezone data, memory ergonomics and GC defaults. That is why a Java upgrade is an application release, not just a base-image replacement.

#### Deep dive

Common upgrade risks include dependencies using JDK internals, bytecode libraries that do not understand new class-file versions, frameworks relying on deep reflection, outdated monitoring agents, and JVM flags that were deprecated or removed.

#### Production angle

Before rollout, run the full test suite on the new runtime, check dependency support matrices, scan startup logs for illegal reflective access or removed options, benchmark critical paths, and deploy gradually with a rollback plan.

#### Traps / caveats

- Changing the build JDK is not the same as changing the runtime JVM.
- Newer Java can expose hidden dependency or reflection problems.
- GC and container-memory behavior can change latency and memory usage.
- Agents and bytecode tools often need upgrades together with the JDK.

#### Optional Anki

Q: Why is a Java runtime upgrade a production change?
A: It can change linkage, reflection access, JVM options, GC, security defaults and runtime libraries.

</details>

<a id="jcore-runtime-004"></a>

<details>
<summary><strong>JCORE-RUNTIME-004. What is a classloader, and why does it matter in Java applications?</strong></summary>

#### Short answer

A classloader is the runtime component that locates class definitions, loads bytecode and defines classes for the JVM. It matters because class identity in Java is not only the fully qualified class name; it is the pair of class name and defining classloader.

#### Interview answer

Classloaders make lazy loading, isolation and extension mechanisms possible. The JVM can load application classes, platform classes, plugin classes and generated classes through different loaders. That gives flexibility, but it also means dependency conflicts can become runtime problems.

Frameworks care about classloaders when scanning resources, loading drivers, discovering service providers, generating proxies, running tests or isolating applications in a container.

#### Deep dive

The classloader also determines resource lookup. Two JARs can contain the same resource name; which one is found depends on loader hierarchy and lookup order. In modular applications, classloaders also interact with module readability and encapsulation.

#### Production angle

In production, classloader issues usually appear as `ClassCastException`, `ClassNotFoundException`, `NoClassDefFoundError`, missing resources, broken SPI discovery or memory leaks after redeploys.

#### Traps / caveats

- The same class name loaded by different classloaders is not the same runtime type.
- Resource lookup follows classloader rules too.
- Thread pools can accidentally keep old classloaders alive.
- Framework code may need the thread context classloader rather than its own loader.

#### Optional Anki

Q: What defines class identity in Java?
A: The fully qualified class name plus the defining classloader.

</details>

<a id="jcore-runtime-005"></a>

<details>
<summary><strong>JCORE-RUNTIME-005. What is the difference between `ClassNotFoundException` and `NoClassDefFoundError`?</strong></summary>

#### Short answer

`ClassNotFoundException` is a checked exception from explicit class loading by name, such as `Class.forName()`. `NoClassDefFoundError` is an error raised when the JVM needs a class that was expected from compiled code but cannot define it at runtime.

#### Interview answer

The practical difference is the context. If application code asks a classloader to load a string name and it is absent, you see `ClassNotFoundException`. If bytecode already contains a reference to a class and that class is missing, failed during initialization, or cannot be loaded because of another problem, you can see `NoClassDefFoundError`.

A common example: code compiled with dependency A works in tests, but the production artifact misses one transitive JAR. The first execution path touching that missing type may fail with `NoClassDefFoundError`.

#### Deep dive

Both errors point to packaging, dependency, classloader or initialization problems, but they guide debugging differently. For `ClassNotFoundException`, inspect the explicit class name and loader. For `NoClassDefFoundError`, inspect the missing class plus the original cause in the logs.

#### Production angle

In backend deployments, verify the final runtime artifact, not only the IDE classpath. Fat JAR assembly, Docker layering, test-scoped dependencies and classloader isolation can all change what is visible at runtime.

#### Traps / caveats

- `NoClassDefFoundError` can also appear after a class initialization failure.
- The missing class may be a transitive dependency, not your direct code.
- Do not catch `Error` as normal control flow.
- The first stack trace often contains the real root cause; later attempts may show only the linkage symptom.

#### Optional Anki

Q: When do you expect `ClassNotFoundException`?
A: During explicit loading by name when the classloader cannot find the class.

</details>

<a id="jcore-runtime-006"></a>

<details>
<summary><strong>JCORE-RUNTIME-006. Why can `NoSuchMethodError` appear after a dependency upgrade?</strong></summary>

#### Short answer

`NoSuchMethodError` usually means the code was compiled against one version of a class, but at runtime another version was loaded and it does not contain the method with the expected name and descriptor.

#### Interview answer

The Java compiler verifies method calls against the compile-time classpath. Later, the JVM resolves that symbolic method reference against the class actually loaded at runtime. If dependency resolution, shading, container libraries or a transitive dependency selects an older or incompatible class, the JVM cannot resolve the call.

This is common when a framework module is upgraded but an extension module, plugin, driver or transitive library remains on an older version.

#### Deep dive

The descriptor includes parameter types and return type. Even a method with the same Java-looking name may not match if the signature changed, a return type changed in bytecode terms, or a bridge method expected by older compiled code is absent.

#### Production angle

Use dependency trees, lock files, Maven Enforcer or Gradle dependency insight to find the selected version. In production incidents, log the JAR location of the loaded class via `clazz.getProtectionDomain().getCodeSource()` when it is safe and useful.

#### Traps / caveats

- The problem may be in a transitive dependency, not in the dependency you upgraded directly.
- IDE and packaged application can resolve different dependency versions.
- Fat JAR merging can hide the source of the conflicting class.
- A full clean rebuild helps, but it does not fix a wrong runtime dependency graph.

#### Optional Anki

Q: What does `NoSuchMethodError` usually indicate?
A: Compile-time and runtime versions of a class do not match.

</details>

<details>
<summary><strong>JCORE-RUNTIME-007. How can classpath conflicts appear at runtime?</strong></summary>

#### Short answer

Classpath conflicts appear when the runtime contains duplicate or incompatible classes and resources. The JVM loads one definition according to classpath or classloader rules, while some compiled code expected another version.

#### Interview answer

The classic case is two versions of the same library. Maven or Gradle may choose one version globally, a container may provide another, and a fat JAR may include yet another. The application starts, but a particular code path fails with `NoSuchMethodError`, `NoClassDefFoundError`, `ClassCastException` or strange behavior.

Resources can conflict too: logging configuration, `META-INF/services` files, Spring metadata and SQL migration files can be overwritten or discovered in an unexpected order.

#### Deep dive

Classpath itself has no rich version model. It is mostly an ordered search space. Build tools solve versions before launch, but the JVM sees the resulting set of entries and classloaders.

#### Production angle

For services, enforce dependency convergence, review dependency trees in CI, keep framework families on a BOM, avoid mixing container-provided and bundled libraries accidentally, and test the same artifact that will be deployed.

#### Traps / caveats

- Nearest-wins dependency resolution can hide a newer transitive version.
- Duplicate classes can come from shaded dependencies.
- Resource conflicts are as real as class conflicts.
- The runtime classpath in Docker may differ from the local one.

#### Optional Anki

Q: Why can classpath conflicts be runtime-only?
A: The final loaded class version may differ from the version used during compilation.

</details>

<a id="jcore-runtime-008"></a>

<details>
<summary><strong>🧠 JCORE-RUNTIME-008. What are shading and relocation, and when can they help with dependency conflicts?</strong></summary>

#### Short answer

Shading packages dependency classes into your artifact. Relocation goes further and rewrites their package names, so your private copy no longer has the same class names as the normal library. This can reduce conflicts when two components need incompatible versions of the same dependency.

#### Interview answer

A typical use case is a command-line tool, Java agent, plugin or library that wants to carry an implementation dependency without forcing that version on the application. Relocation changes references from something like `com.foo.Json` to `my.tool.shadow.com.foo.Json`.

Shading without relocation only bundles classes; it does not remove name conflicts. Relocation is the part that gives a separate namespace, but it must also handle resources, service descriptors and reflective class names.

#### Deep dive

Relocation is a workaround, not a replacement for dependency hygiene. It increases artifact size, can hide vulnerable library versions and may break libraries that depend on exact package names, native code, serialization names or framework scanning.

#### Production angle

Use shading deliberately for private implementation dependencies and document it. In CI, still scan shaded libraries for vulnerabilities and verify license obligations, because the code is now inside your artifact.

#### Traps / caveats

- Shading without relocation may not solve duplicate-class conflicts.
- Relocation can break reflection, `META-INF/services`, serialization and resource lookup.
- Security scanners must still see shaded code.
- Do not relocate public API types that users are expected to import.

#### Optional Anki

Q: What does relocation add to shading?
A: It rewrites package/class names to give the bundled dependency a private namespace.

</details>

<a id="jcore-runtime-009"></a>

<details>
<summary><strong>JCORE-RUNTIME-009. What is the difference between classpath and module path?</strong></summary>

#### Short answer

The classpath is the traditional search path for classes and resources, mostly without explicit dependency or encapsulation rules. The module path is used by JPMS for named modules with descriptors, readability rules and package exports/opens.

#### Interview answer

On the classpath, all classes are effectively in the unnamed module, and public types from JARs are broadly visible if the classloader can find them. On the module path, a JAR can become a named module with `module-info.class`, and code can read only modules that are required.

The module path also lets Java detect some problems earlier, such as missing required modules or split packages between resolved modules.

#### Deep dive

Classpath favors compatibility and simplicity. Module path favors explicit boundaries. Many backend applications still run mostly on the classpath, but understanding modules matters because JDK internals and reflective access are now governed by module rules.

#### Production angle

During migration, avoid changing everything at once. Start by removing illegal JDK-internal dependencies, stabilizing module names and testing framework reflection requirements before moving application JARs onto the module path.

#### Traps / caveats

- A JAR can be on the classpath or module path, with different visibility rules.
- Automatic modules are useful for migration but are not a clean final design.
- Classpath ordering can still matter for resources and duplicate classes.
- Module path does not replace Maven or Gradle dependency resolution.

#### Optional Anki

Q: What extra information does module path use?
A: Module descriptors and JPMS rules such as `requires`, `exports` and `opens`.

</details>

<a id="jcore-runtime-010"></a>

<details>
<summary><strong>JCORE-RUNTIME-010. What is the Java module system used for?</strong></summary>

#### Short answer

The Java Platform Module System, JPMS, is used to describe explicit dependencies between modules and to enforce stronger encapsulation of packages. It helps build reliable configurations and clearer boundaries, especially for large codebases and the JDK itself.

#### Interview answer

A module declares what it requires and what packages it exports. Code outside the module cannot simply use every public class inside the JAR; only exported packages are part of the normal public surface. A module can also open packages for reflection.

JPMS is also used by tools such as `jlink` to build custom runtime images containing only selected modules and their dependencies.

#### Deep dive

JPMS is not primarily a dependency download tool. Maven and Gradle still resolve artifacts. JPMS describes module relationships and access rules after artifacts are available.

#### Production angle

In backend work, JPMS matters even when applications are not fully modular, because Java 9+ moved the JDK itself to modules. Reflection into JDK internals and non-exported packages is now restricted.

#### Traps / caveats

- JPMS boundaries are package-based, not class-by-class.
- A public class is not necessarily accessible if its package is not exported.
- Opening a package for reflection is different from exporting it for normal compilation.
- JPMS and build-tool dependency management solve different problems.

#### Optional Anki

Q: What are two main JPMS goals?
A: Reliable configuration and strong encapsulation.

</details>

<a id="jcore-runtime-011"></a>

<details>
<summary><strong>🧠 JCORE-RUNTIME-011. How did the Java module system affect reflection and strong encapsulation?</strong></summary>

#### Short answer

JPMS made package boundaries enforceable at runtime. Reflection is no longer a universal escape hatch: deep reflection into a non-open package can fail unless the package is opened by the module descriptor or by command-line options such as `--add-opens`.

#### Interview answer

Before modules, many frameworks and libraries accessed private JDK or application internals with `setAccessible(true)`. With JPMS, normal access depends on `exports`, while deep reflective access depends on `opens`. This became especially visible on Java 17+, where broad relaxed access to JDK internals was removed.

For application code, this means framework integration may require explicit `opens` declarations for packages containing entities, configuration classes or serialization targets.

#### Deep dive

The key distinction is readability versus deep access. A module may be readable and a package may be exported for normal public-member access, but private-field reflection still requires the package to be open.

#### Production angle

In production, avoid broad flags like opening large JDK packages to all unnamed modules unless it is a temporary migration step. Prefer upgrading libraries and using narrow module declarations or narrow launch flags.

#### Traps / caveats

- `exports` is not enough for private-field reflection.
- `--add-opens` is a migration escape hatch, not a clean design boundary.
- A framework may work on Java 8 and fail on Java 17+ because of stronger encapsulation.
- Opening application packages can expose internals to reflection-based misuse.

#### Optional Anki

Q: What does `opens` allow that `exports` does not?
A: Deep reflective access to members such as private fields and constructors.

</details>

<a id="jcore-runtime-012"></a>

<details>
<summary><strong>JCORE-RUNTIME-012. What is the parent delegation model in Java class loading?</strong></summary>

#### Short answer

Parent delegation means a classloader normally asks its parent to find a class or resource before trying to define it itself. This protects platform classes and gives a predictable hierarchy of visibility.

#### Interview answer

In the usual model, the application classloader delegates to the platform loader, which delegates toward the bootstrap loader. If the parent finds the class, the child uses that definition. If not, the child may search its own URLs or other sources.

The model avoids accidentally replacing core Java classes from the application classpath. It also means a child can usually see parent classes, but a parent cannot automatically see child-only application classes.

#### Deep dive

Some environments intentionally alter the model. Application servers, plugin systems and test frameworks may use child-first or isolated loaders to let applications carry their own library versions.

#### Production angle

When debugging, identify the defining loader for each important class. Parent delegation problems often look like “why is this old version used?” or “why can the framework not see my provider class?”.

#### Traps / caveats

- Parent-first is the common model, but not a law for every custom loader.
- Visibility is usually downward: child sees parent, parent does not see child.
- Child-first loading can solve one conflict and create another.
- Resources may also be affected by delegation order.

#### Optional Anki

Q: What is parent delegation?
A: A classloader asks its parent first before searching its own class source.

</details>

<a id="jcore-runtime-013"></a>

<details>
<summary><strong>JCORE-RUNTIME-013. What are bootstrap, platform and application classloaders?</strong></summary>

#### Short answer

They are the main built-in classloaders. The bootstrap loader loads core runtime classes. The platform loader loads selected platform modules. The application, or system, classloader usually loads application classes from the classpath and application modules from the module path.

#### Interview answer

Since Java 9, the old extension loader model was replaced by the platform classloader. The platform loader is a parent or ancestor of the application loader. The bootstrap loader is represented in APIs by a `null` classloader for classes it defines.

Most application classes are loaded by the application classloader, but containers and frameworks may create additional loaders beneath or beside it.

#### Deep dive

These names describe runtime roles, not separate processes. They form a hierarchy used for both class and resource loading, but actual implementation details can vary between JVM versions.

#### Production angle

Knowing the built-in loaders helps explain why user code cannot override `java.lang.String`, why some platform classes are visible to applications, and why classloader logs are useful during dependency incidents.

#### Traps / caveats

- `SomeClass.class.getClassLoader()` may return `null` for bootstrap-loaded classes.
- The platform loader is not the same as the application loader.
- Application servers may add their own classloader hierarchy.
- Do not hard-code assumptions that are not guaranteed by the API.

#### Optional Anki

Q: Which built-in loader usually loads application classpath classes?
A: The application, or system, classloader.

</details>

<a id="jcore-runtime-014"></a>

<details>
<summary><strong>JCORE-RUNTIME-014. Why can the same class name loaded by two classloaders be treated as different classes?</strong></summary>

#### Short answer

In Java, runtime type identity includes both the binary class name and the defining classloader. If two different classloaders define `com.example.User`, the JVM treats them as two different types even if the bytecode is identical.

#### Interview answer

This is how isolation works. A plugin can have its own copy of a library without polluting the host. An application server can run two applications using different versions of the same class. But if objects cross the boundary and the receiving side expects its own version of the type, casts and `instanceof` checks fail.

The typical confusing error is `com.example.User cannot be cast to com.example.User`. The message is not nonsense: the two names are equal, but the defining loaders differ.

#### Deep dive

Each classloader-defined copy also has its own static fields, cached singletons and class initialization state. That can create subtle bugs when code assumes a JVM-wide singleton but actually has one singleton per loader.

#### Production angle

Use shared API types from a loader visible to both sides when objects must cross plugin or container boundaries. Keep implementation classes isolated, but share contracts intentionally.

#### Traps / caveats

- Identical bytecode does not imply identical runtime type.
- Static state is per defined class, not per class name globally.
- Cross-loader casts are a common plugin/container bug.
- Serialization across classloader boundaries needs careful type resolution.

#### Optional Anki

Q: Why can `User` fail to cast to `User`?
A: The two `User` classes may have the same name but different defining classloaders.

</details>

<details>
<summary><strong>JCORE-RUNTIME-015. What is the thread context classloader, and why do frameworks use it?</strong></summary>

#### Short answer

The thread context classloader, TCCL, is a classloader associated with a thread. Frameworks use it so shared or parent-loaded code can discover and load application classes that are only visible from the application side.

#### Interview answer

Parent delegation creates a visibility problem for frameworks. A framework class may be loaded by a parent loader, while user implementations, JDBC drivers, serializers or service providers are loaded by a child application loader. If the framework used only its own classloader, it might not see user classes. The TCCL gives the framework a caller/application-oriented lookup point.

Common examples include `ServiceLoader`, resource scanning, XML parsers, logging providers and container integrations.

#### Deep dive

TCCL is mutable state on a thread. That makes it powerful but easy to misuse, especially with thread pools where a thread is reused by unrelated tasks.

#### Production angle

When temporarily changing the TCCL, always restore the previous value in a `finally` block. In executors, be careful not to leak application classloaders across redeploys or between tenants/plugins.

#### Traps / caveats

- TCCL is not the same as `SomeClass.class.getClassLoader()`.
- Forgetting to restore it can leak classloaders or affect later tasks.
- Async execution can lose the expected TCCL unless the framework propagates it.
- Using TCCL hides dependencies, so document why it is needed.

#### Optional Anki

Q: Why do frameworks use TCCL?
A: To load application-side classes and providers from code loaded by a parent/shared loader.

</details>

<a id="jcore-runtime-016"></a>

<details>
<summary><strong>🧠 JCORE-RUNTIME-016. When would a custom classloader be useful?</strong></summary>

#### Short answer

A custom classloader is useful when an application needs controlled loading, isolation, transformation or unloading of classes. Typical cases are plugin systems, application servers, test isolation, hot reload, instrumentation and loading generated or encrypted bytecode.

#### Interview answer

The key reason is isolation. A host can load each plugin with its own dependency set, unload it by dropping references to its loader, or transform bytecode before defining classes. Test frameworks can run code with a special loader to simulate different environments or instrument classes.

A custom loader is also a boundary. Shared API types should usually be loaded by a common parent, while plugin implementation details stay inside the plugin loader.

#### Deep dive

Custom classloading is advanced infrastructure code. It must define delegation rules, resource lookup, package sealing behavior, security assumptions and cleanup rules.

#### Production angle

Use existing framework mechanisms unless you are building infrastructure. For normal backend services, custom classloaders are rare; most teams should solve dependency issues with build tooling, module boundaries or process isolation.

#### Traps / caveats

- A custom loader can easily create memory leaks through static fields or threads.
- Child-first loading can accidentally shadow platform or framework classes.
- Unloading works only when all references to loaded classes and their loader are gone.
- Debugging classloader issues is significantly harder than debugging normal dependency resolution.

#### Optional Anki

Q: What is the most common reason for a custom classloader?
A: Isolation of plugins, applications, tests or generated/transformed classes.

</details>

<a id="jcore-runtime-017"></a>

<details>
<summary><strong>🧠 JCORE-RUNTIME-017. What classloader issues can appear in application servers, plugins or test frameworks?</strong></summary>

#### Short answer

Common issues are duplicate classes, parent/child visibility surprises, incompatible library versions, cross-loader casts, broken resource lookup, lost TCCL, service discovery failures and classloader leaks after redeploy or test runs.

#### Interview answer

Application servers often separate container classes from application classes. Plugins often separate host API from plugin implementation. Test frameworks may create temporary loaders to isolate or instrument tests. These boundaries are useful, but objects, singletons, resources and threads can accidentally cross them.

Symptoms include `ClassCastException` with identical class names, providers not found, old versions staying in memory, static caches not resetting between tests, and libraries resolving a class from the wrong layer.

#### Deep dive

Leaks often happen because something outside the child loader keeps a reference to a child-loaded class: a thread, `ThreadLocal`, static registry, logging framework, JDBC driver manager, scheduled task or lambda.

#### Production angle

For production containers and plugin systems, define clear ownership: which loader owns shared API, who creates threads, who closes resources, who deregisters drivers/listeners and how redeploy cleanup is verified.

#### Traps / caveats

- A test passing in IDE can fail in a runner with a different loader layout.
- Static state may belong to the test loader, not to the whole JVM.
- A leaked thread can keep an entire web application classloader alive.
- SPI files must be merged correctly in shaded or fat JARs.

#### Optional Anki

Q: Why can redeploy leak memory in an application server?
A: A parent or external object may still reference classes, threads or statics from the old application classloader.

</details>

<a id="jcore-runtime-018"></a>

<details>
<summary><strong>JCORE-RUNTIME-018. What is `ServiceLoader`, and when is it useful?</strong></summary>

#### Short answer

`ServiceLoader` is the standard Java mechanism for discovering implementations of a service interface at runtime. It is useful for plugin-like extension points, drivers, providers and framework integrations where the API should not hard-code implementation classes.

#### Interview answer

A service is usually an interface or abstract class. Providers implement it. On the classpath, providers are listed in `META-INF/services/<service-binary-name>`. In modules, providers are declared with `provides ... with ...`, and consumers declare `uses`.

`ServiceLoader` locates providers lazily, so loading and initialization may happen only when the iterator or stream is consumed.

#### Deep dive

The mechanism is simple and decoupled, but it is not dependency injection. It does discovery and instantiation according to Java rules; lifecycle, configuration and ordering often need an additional layer.

#### Production angle

In production, `ServiceLoader` is common for JDBC drivers, logging providers, crypto/security providers and framework SPIs. When building fat JARs, make sure service files are merged rather than overwritten.

#### Traps / caveats

- Missing or overwritten `META-INF/services` files break discovery.
- Provider constructors and initialization can throw at discovery time.
- Classloader choice affects which providers are visible.
- Provider ordering should not be assumed unless the API specifies it.

#### Optional Anki

Q: What problem does `ServiceLoader` solve?
A: Runtime discovery of service implementations without hard-coding implementation classes.

</details>

<a id="jcore-runtime-019"></a>

<details>
<summary><strong>JCORE-RUNTIME-019. What are unnamed and automatic modules, and why do they matter during JPMS migration?</strong></summary>

#### Short answer

The unnamed module contains code on the classpath. An automatic module is a non-modular JAR placed on the module path; JPMS gives it a module name and broad readability, export and open behavior. Both exist to ease migration from classpath applications to JPMS.

#### Interview answer

Classpath code belongs to the unnamed module and can read many named modules, but named modules do not normally read the unnamed module. This affects migration order: if modular code needs a classpath-only library, that library may need to move to the module path.

Automatic modules are a bridge. They let existing JARs participate in module resolution before they have `module-info.class`. But their generated names can be unstable, and their broad exports are weaker design boundaries than explicit modules.

#### Deep dive

A stable `Automatic-Module-Name` manifest entry can reduce naming risk, but it still does not provide a precise descriptor with explicit `requires`, `exports` and `opens`.

#### Production angle

During migration, treat automatic modules as temporary. Avoid exposing their generated names in long-term public documentation if the library owner may later publish an explicit module name.

#### Traps / caveats

- Named modules cannot freely depend on classpath-only code.
- Automatic module names can change if based on JAR filenames.
- Automatic modules export and open packages broadly, so they are not strong boundaries.
- Split packages can block automatic-module migration.

#### Optional Anki

Q: What is an automatic module?
A: A non-modular JAR on the module path that JPMS treats as a module for migration.

</details>

<details>
<summary><strong>🧠 JCORE-RUNTIME-020. What is a split package, and why is it problematic with modules?</strong></summary>

#### Short answer

A split package means the same Java package is spread across more than one module or JAR. JPMS treats split packages between resolved modules as problematic because package ownership becomes ambiguous and strong encapsulation cannot be enforced cleanly.

#### Interview answer

On the traditional classpath, split packages can exist accidentally: two JARs both contain `com.example.util`. The JVM will load classes according to classloader/search order. With modules, a package is expected to belong to one module in a resolved configuration, so duplicate ownership is rejected or leads to migration problems.

Split packages often appear after large libraries are divided into multiple artifacts, or when a project creates “extension” JARs in the same package as the base library.

#### Deep dive

The deeper issue is that packages are the unit of export and open rules in JPMS. If one package lives in multiple modules, it is unclear which module controls its API surface and reflective access.

#### Production angle

Fix split packages by refactoring package names, merging artifacts, creating a proper common module, or keeping the affected legacy code on the classpath until it can be cleaned up.

#### Traps / caveats

- Split packages may be tolerated on the classpath but fail on the module path.
- Adding `module-info.java` can expose old packaging mistakes.
- Relocation can help only when the duplicate package belongs to a private dependency.
- Do not publish new libraries that require users to split one package across artifacts.

#### Optional Anki

Q: Why do modules dislike split packages?
A: JPMS uses packages as ownership and encapsulation units, so one package should not belong to multiple resolved modules.

<details>
<summary><strong>🧠 JCORE-RUNTIME-021. What is the difference between `exports`, `opens`, `--add-exports` and `--add-opens`?</strong></summary>

#### Short answer

`exports` makes a module package accessible for normal compilation and public-member access. `opens` allows deep reflection into a package. `--add-exports` and `--add-opens` are command-line overrides used to break or adjust module boundaries, usually during migration.

#### Interview answer

Use `exports` for public API packages. Use `opens` for packages that frameworks must inspect or modify reflectively, such as entity classes or serialization targets. Both can be qualified to specific target modules.

`--add-exports` exposes a package from a module to another module from the command line. `--add-opens` opens a package for deep reflection. They are useful when you cannot immediately change a dependency or module descriptor, but they encode runtime policy outside the codebase.

#### Deep dive

A useful rule of thumb: `exports` is about ordinary Java access to public types; `opens` is about reflective access beyond ordinary Java access checks.

#### Production angle

In production launch scripts, keep any `--add-*` flags explicit, narrow and tracked. Broad flags such as opening to `ALL-UNNAMED` may be acceptable during migration, but they should have an owner and removal plan.

#### Traps / caveats

- `exports` does not imply deep reflection.
- `opens` does not make a package a normal compile-time API.
- Command-line `--add-*` flags can differ between local, CI and production runs.
- Depending on JDK internals via `--add-exports` is fragile.

#### Optional Anki

Q: Which directive is for deep reflection?
A: `opens`, or temporarily `--add-opens` from the command line.

</details>
