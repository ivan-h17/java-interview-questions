# 10. Classpath, modules, compatibility and runtime linkage



<a id="jcore-runtime-001"></a>

<details>
<summary><strong>JCORE-RUNTIME-001. What is binary compatibility in Java?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Binary compatibility means that already compiled client code can link against a changed library without being recompiled. It is about class-file linkage: names, descriptors, inheritance, fields and methods that existing bytecode expects must still be present in a compatible form.</p>
</td>
<td valign="top" width="50%">

<p>Двоичная совместимость (binary compatibility) означает, что уже скомпилированный клиентский код может связаться с изменённой библиотекой без повторной компиляции. Речь идёт о линковке <code>.class</code>-файлов: имена, сигнатуры, наследование, поля и методы, на которые ссылается существующий байткод, должны остаться доступными в совместимом виде.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In an interview I would separate this from source compatibility. A source change can be source-compatible but still change overload choices after recompilation, or it can be binary-compatible while new source would no longer compile cleanly. Binary compatibility is checked when the JVM resolves symbolic references from bytecode.</p>
<p>For example, adding a new method is usually binary-compatible. Removing a public method, changing a method descriptor, changing a field to a method, or changing class hierarchy in the wrong way can break already compiled clients with linkage errors.</p>
</td>
<td valign="top" width="50%">

<p>На собеседовании я бы сразу отделил это от совместимости исходного кода. Изменение может быть совместимо с исходниками, но после повторной компиляции выбрать другую перегрузку; и наоборот, старый байткод может продолжать работать, хотя новый исходный код уже не компилируется без правок. Двоичная совместимость проверяется, когда JVM разрешает символические ссылки из байткода.</p>
<p>Например, добавление нового метода обычно двоично совместимо. Удаление публичного метода, изменение дескриптора метода, замена поля методом или неудачное изменение иерархии классов могут сломать уже собранные клиенты ошибками линковки.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Java bytecode does not store direct memory addresses for most application references. It stores symbolic references such as class names, method names and descriptors. At runtime those references are resolved. If the expected member or type cannot be found in the loaded version, the JVM throws a linkage-related error.</p>
</td>
<td valign="top" width="50%">

<p>Байткод Java обычно не хранит прямые адреса для ссылок на прикладной код. Он хранит символические ссылки: имена классов, имена методов и дескрипторы. Во время выполнения эти ссылки разрешаются. Если в загруженной версии нет ожидаемого типа или члена класса, JVM выбрасывает ошибку, связанную с линковкой.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>For backend services this matters during library upgrades and shared model evolution. A dependency can compile in one module but fail in production if another version is placed on the runtime classpath. Treat public APIs and shared DTO/model libraries as compatibility contracts.</p>
</td>
<td valign="top" width="50%">

<p>В серверных сервисах это важно при обновлении библиотек и развитии общих моделей. Зависимость может успешно компилироваться в одном модуле, но падать в промышленной среде, если во время запуска подставлена другая версия. Публичные API и общие DTO/model-библиотеки нужно рассматривать как контракт совместимости.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Binary compatibility does not guarantee correct behavior.</li>
<li>A clean compilation of one module does not prove the whole runtime classpath is consistent.</li>
<li>Removing or changing public members is risky even when tests in the changed module pass.</li>
<li>Linkage errors often appear only when the affected code path is executed.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Двоичная совместимость не гарантирует правильное поведение программы.</li>
<li>Успешная компиляция одного модуля не доказывает согласованность всего classpath во время запуска.</li>
<li>Удаление или изменение публичных членов класса опасно, даже если тесты изменённого модуля проходят.</li>
<li>Ошибки линковки часто проявляются только при выполнении затронутого участка кода.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does binary compatibility protect?<br>A: Already compiled clients can link to a changed library without recompilation.</p>
</td>
<td valign="top" width="50%">

<p>В: Что защищает двоичная совместимость?<br>О: Уже скомпилированные клиенты могут связаться с изменённой библиотекой без повторной компиляции.</p>

</td>
</tr>
</tbody>
</table>

<a id="jcore-runtime-002"></a>

<details>
<summary><strong>JCORE-RUNTIME-002. What is the difference between source compatibility, binary compatibility and behavioral compatibility?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Source compatibility means old source code still compiles. Binary compatibility means old class files still link. Behavioral compatibility means the program still does the same meaningful thing. These are related, but they are not the same promise.</p>
</td>
<td valign="top" width="50%">

<p>Совместимость исходного кода (source compatibility) означает, что старые исходники всё ещё компилируются. Двоичная совместимость означает, что старые <code>.class</code>-файлы всё ещё линкуются. Поведенческая совместимость (behavioral compatibility) означает, что программа продолжает делать то же самое по смыслу. Это связанные, но разные гарантии.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Source compatibility is checked by <code>javac</code>. Binary compatibility is checked by the JVM when resolving bytecode references. Behavioral compatibility is checked only by tests, monitoring and users, because the compiler cannot know whether a new implementation still satisfies business expectations.</p>
<p>A library can add an overload and remain binary-compatible, but after recompilation client source may bind to a different overload. A method can keep exactly the same signature and remain source- and binary-compatible while changing semantics in a breaking way.</p>
</td>
<td valign="top" width="50%">

<p>Совместимость исходного кода проверяет <code>javac</code>. Двоичная совместимость проверяется JVM при разрешении ссылок из байткода. Поведенческую совместимость проверяют только тесты, мониторинг и пользователи, потому что компилятор не знает, сохраняет ли новая реализация бизнес-смысл.</p>
<p>Библиотека может добавить перегрузку и остаться двоично совместимой, но после повторной компиляции клиентский код может начать выбирать другую перегрузку. Метод может сохранить ту же сигнатуру и быть совместимым на уровне исходников и байткода, но изменить семантику и сломать клиентов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The three categories answer different questions: “Can I compile?”, “Can I start/link?”, and “Will it behave correctly?”. Mature API evolution needs all three, especially when several services share libraries but are released independently.</p>
</td>
<td valign="top" width="50%">

<p>Эти три вида совместимости отвечают на разные вопросы: «собирается ли код?», «запускается и линкуется ли байткод?» и «ведёт ли себя система правильно?». При развитии зрелого API нужны все три, особенно если несколько сервисов используют общие библиотеки и выпускаются независимо.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, compatibility should be tested at the integration boundary. Use dependency convergence checks, contract tests, canary releases and backward-compatible API evolution rules, not only local unit tests.</p>
</td>
<td valign="top" width="50%">

<p>В промышленной среде совместимость нужно проверять на границах интеграции. Нужны проверки согласованности зависимостей, контрактные тесты, canary-релизы и правила обратной совместимости API, а не только локальные unit-тесты.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Source-compatible changes may change overload resolution after recompilation.</li>
<li>Binary-compatible changes may still break behavior.</li>
<li>Behavioral compatibility is often the hardest one to specify and test.</li>
<li>Semantic versioning is helpful only when maintainers follow it accurately.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Изменение, совместимое с исходниками, может изменить выбор перегрузки после повторной компиляции.</li>
<li>Двоично совместимое изменение всё равно может сломать поведение.</li>
<li>Поведенческую совместимость обычно сложнее всего описать и проверить.</li>
<li>Семантическое версионирование (semantic versioning) помогает только тогда, когда авторы библиотек действительно его соблюдают.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Which compatibility type says old <code>.class</code> files still link?<br>A: Binary compatibility.</p>
</td>
<td valign="top" width="50%">

<p>В: Какой вид совместимости означает, что старые <code>.class</code>-файлы всё ещё линкуются?<br>О: Двоичная совместимость.</p>

</td>
</tr>
</tbody>
</table>

<details>
<summary><strong>JCORE-RUNTIME-003. How do Java version upgrades affect backend applications?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A Java version upgrade can affect compilation, runtime behavior, dependency compatibility, JVM flags, GC behavior, TLS/security defaults, reflection access, observability agents and container images. The application may compile but still fail because a dependency, framework or startup flag is no longer compatible.</p>
</td>
<td valign="top" width="50%">

<p>Обновление версии Java может затронуть компиляцию, поведение во время выполнения, совместимость зависимостей, JVM-флаги, поведение GC, настройки TLS и безопасности, доступ через рефлексию, агенты наблюдаемости (observability) и контейнерные образы. Приложение может компилироваться, но падать из-за несовместимой зависимости, фреймворка или стартового флага.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The first question is what changes: the JDK used to build, the bytecode target, or the runtime JVM. <code>--release</code> controls which platform API and class-file target are used by <code>javac</code>. Running the same bytecode on a newer JVM is usually supported, but stronger encapsulation, removed options and library assumptions can still cause failures.</p>
<p>Backend upgrades also change the operating environment: Docker base image, CA certificates, timezone data, memory ergonomics and GC defaults. That is why a Java upgrade is an application release, not just a base-image replacement.</p>
</td>
<td valign="top" width="50%">

<p>Сначала нужно понять, что именно меняется: JDK для сборки, целевая версия байткода или JVM для запуска. Опция <code>--release</code> управляет тем, какие API платформы и какая версия <code>.class</code>-файлов используются <code>javac</code>. Запуск старого байткода на новой JVM обычно поддерживается, но более строгая инкапсуляция, удалённые опции и предположения библиотек всё равно могут привести к сбоям.</p>
<p>Для серверного сервиса меняется и окружение: базовый Docker-образ, CA-сертификаты, данные часовых поясов, настройки памяти и значения GC по умолчанию. Поэтому обновление Java — это полноценный релиз приложения, а не простая замена базового образа.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Common upgrade risks include dependencies using JDK internals, bytecode libraries that do not understand new class-file versions, frameworks relying on deep reflection, outdated monitoring agents, and JVM flags that were deprecated or removed.</p>
</td>
<td valign="top" width="50%">

<p>Типичные риски обновления: зависимости используют внутренние API JDK, библиотеки работы с байткодом не понимают новые версии <code>.class</code>-файлов, фреймворки зависят от глубокой рефлексии, агенты наблюдаемости (observability) устарели, а некоторые JVM-флаги устарели или удалены.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Before rollout, run the full test suite on the new runtime, check dependency support matrices, scan startup logs for illegal reflective access or removed options, benchmark critical paths, and deploy gradually with a rollback plan.</p>
</td>
<td valign="top" width="50%">

<p>Перед выкладкой нужно прогнать полный набор тестов на новой JVM, проверить поддержку версий у зависимостей, посмотреть стартовые логи на незаконный рефлексивный доступ и удалённые опции, измерить критичные сценарии и выпускать постепенно с планом отката.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Changing the build JDK is not the same as changing the runtime JVM.</li>
<li>Newer Java can expose hidden dependency or reflection problems.</li>
<li>GC and container-memory behavior can change latency and memory usage.</li>
<li>Agents and bytecode tools often need upgrades together with the JDK.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Смена JDK для сборки — не то же самое, что смена JVM для запуска.</li>
<li>Новая Java может проявить скрытые проблемы зависимостей или рефлексии.</li>
<li>Поведение GC и расчёт памяти в контейнере могут изменить задержки и потребление памяти.</li>
<li>Агенты и инструменты работы с байткодом часто нужно обновлять вместе с JDK.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why is a Java runtime upgrade a production change?<br>A: It can change linkage, reflection access, JVM options, GC, security defaults and runtime libraries.</p>
</td>
<td valign="top" width="50%">

<p>В: Почему обновление JVM — это изменение для промышленной среды?<br>О: Оно может изменить линковку, доступ через рефлексию, JVM-опции, GC, настройки безопасности и библиотеки времени выполнения.</p>

</td>
</tr>

<details>
<summary><strong>JCORE-RUNTIME-004. What is a classloader, and why does it matter in Java applications?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A classloader is the runtime component that locates class definitions, loads bytecode and defines classes for the JVM. It matters because class identity in Java is not only the fully qualified class name; it is the pair of class name and defining classloader.</p>
</td>
<td valign="top" width="50%">

<p>Загрузчик классов (classloader) — это компонент времени выполнения, который находит определения классов, загружает байткод и определяет классы для JVM. Он важен потому, что идентичность класса в Java — это не только полное имя класса, а пара: имя класса и загрузчик, который этот класс определил.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Classloaders make lazy loading, isolation and extension mechanisms possible. The JVM can load application classes, platform classes, plugin classes and generated classes through different loaders. That gives flexibility, but it also means dependency conflicts can become runtime problems.</p>
<p>Frameworks care about classloaders when scanning resources, loading drivers, discovering service providers, generating proxies, running tests or isolating applications in a container.</p>
</td>
<td valign="top" width="50%">

<p>Загрузчики классов делают возможной ленивую загрузку, изоляцию и расширяемость. JVM может загружать классы приложения, платформы, плагинов и сгенерированные классы через разные загрузчики. Это даёт гибкость, но из-за этого конфликты зависимостей могут стать ошибками во время выполнения.</p>
<p>Фреймворкам загрузчики классов нужны при сканировании ресурсов, загрузке драйверов, поиске поставщиков сервиса, генерации прокси, запуске тестов и изоляции приложений в контейнере.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The classloader also determines resource lookup. Two JARs can contain the same resource name; which one is found depends on loader hierarchy and lookup order. In modular applications, classloaders also interact with module readability and encapsulation.</p>
</td>
<td valign="top" width="50%">

<p>Загрузчик классов также определяет поиск ресурсов. Два JAR-файла могут содержать ресурс с одинаковым именем; какой из них будет найден, зависит от иерархии загрузчиков и порядка поиска. В модульных приложениях загрузчики классов дополнительно связаны с читаемостью модулей и инкапсуляцией.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, classloader issues usually appear as <code>ClassCastException</code>, <code>ClassNotFoundException</code>, <code>NoClassDefFoundError</code>, missing resources, broken SPI discovery or memory leaks after redeploys.</p>
</td>
<td valign="top" width="50%">

<p>В промышленной среде проблемы с загрузчиками классов обычно выглядят как <code>ClassCastException</code>, <code>ClassNotFoundException</code>, <code>NoClassDefFoundError</code>, пропавшие ресурсы, сломанный поиск SPI или утечки памяти после повторного развёртывания (redeploy).</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>The same class name loaded by different classloaders is not the same runtime type.</li>
<li>Resource lookup follows classloader rules too.</li>
<li>Thread pools can accidentally keep old classloaders alive.</li>
<li>Framework code may need the thread context classloader rather than its own loader.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Один и тот же класс по имени, загруженный разными загрузчиками, не является одним и тем же типом во время выполнения.</li>
<li>Поиск ресурсов тоже следует правилам загрузчика классов.</li>
<li>Пулы потоков могут случайно удерживать старые загрузчики классов в памяти.</li>
<li>Коду фреймворка иногда нужен контекстный загрузчик потока, а не собственный загрузчик фреймворка.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What defines class identity in Java?<br>A: The fully qualified class name plus the defining classloader.</p>
</td>
<td valign="top" width="50%">

<p>В: Что определяет идентичность класса в Java?<br>О: Полное имя класса плюс загрузчик, который определил этот класс.</p>

</td>
</tr>

<a id="jcore-runtime-005"></a>

<details>
<summary><strong>JCORE-RUNTIME-005. What is the difference between <code>ClassNotFoundException</code> and <code>NoClassDefFoundError</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>ClassNotFoundException</code> is a checked exception from explicit class loading by name, such as <code>Class.forName()</code>. <code>NoClassDefFoundError</code> is an error raised when the JVM needs a class that was expected from compiled code but cannot define it at runtime.</p>
</td>
<td valign="top" width="50%">

<p><code>ClassNotFoundException</code> — проверяемое исключение при явной загрузке класса по имени, например через <code>Class.forName()</code>. <code>NoClassDefFoundError</code> — ошибка, когда JVM нужен класс, ожидаемый скомпилированным кодом, но во время выполнения его не удаётся определить.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The practical difference is the context. If application code asks a classloader to load a string name and it is absent, you see <code>ClassNotFoundException</code>. If bytecode already contains a reference to a class and that class is missing, failed during initialization, or cannot be loaded because of another problem, you can see <code>NoClassDefFoundError</code>.</p>
<p>A common example: code compiled with dependency A works in tests, but the production artifact misses one transitive JAR. The first execution path touching that missing type may fail with <code>NoClassDefFoundError</code>.</p>
</td>
<td valign="top" width="50%">

<p>Практическое различие — в контексте. Если прикладной код просит загрузчик загрузить класс по строковому имени и класс отсутствует, появляется <code>ClassNotFoundException</code>. Если байткод уже содержит ссылку на класс, а этот класс отсутствует, упал при инициализации или не может быть загружен по другой причине, возможен <code>NoClassDefFoundError</code>.</p>
<p>Типичный пример: код собрали с зависимостью A, тесты прошли, но в артефакт для промышленной среды не попал один транзитивный JAR. Первый участок выполнения, который тронет отсутствующий тип, может упасть с <code>NoClassDefFoundError</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Both errors point to packaging, dependency, classloader or initialization problems, but they guide debugging differently. For <code>ClassNotFoundException</code>, inspect the explicit class name and loader. For <code>NoClassDefFoundError</code>, inspect the missing class plus the original cause in the logs.</p>
</td>
<td valign="top" width="50%">

<p>Оба случая указывают на проблемы упаковки, зависимостей, загрузчиков классов или инициализации, но отлаживаются по-разному. Для <code>ClassNotFoundException</code> проверяют строковое имя класса и загрузчик. Для <code>NoClassDefFoundError</code> проверяют отсутствующий класс и исходную причину в логах.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In backend deployments, verify the final runtime artifact, not only the IDE classpath. Fat JAR assembly, Docker layering, test-scoped dependencies and classloader isolation can all change what is visible at runtime.</p>
</td>
<td valign="top" width="50%">

<p>В серверном развёртывании нужно проверять итоговый артефакт для запуска, а не только classpath в IDE. Сборка fat JAR, слои Docker, зависимости со scope <code>test</code> и изоляция загрузчиков могут изменить то, что видно во время запуска.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>NoClassDefFoundError</code> can also appear after a class initialization failure.</li>
<li>The missing class may be a transitive dependency, not your direct code.</li>
<li>Do not catch <code>Error</code> as normal control flow.</li>
<li>The first stack trace often contains the real root cause; later attempts may show only the linkage symptom.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>NoClassDefFoundError</code> может появиться и после ошибки инициализации класса.</li>
<li>Отсутствующий класс может быть транзитивной зависимостью, а не вашим прямым кодом.</li>
<li>Не стоит ловить <code>Error</code> как обычный способ управления потоком выполнения.</li>
<li>Первая трассировка стека (stack trace) часто содержит настоящую причину; последующие попытки могут показывать только симптом линковки.</li>
</ul>

</td>

<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>В: Когда ожидают <code>ClassNotFoundException</code>?<br>О: При явной загрузке по имени, если загрузчик не нашёл класс.</p>

<details>
<summary><strong>JCORE-RUNTIME-006. Why can <code>NoSuchMethodError</code> appear after a dependency upgrade?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>NoSuchMethodError</code> usually means the code was compiled against one version of a class, but at runtime another version was loaded and it does not contain the method with the expected name and descriptor.</p>
</td>
<td valign="top" width="50%">

<p><code>NoSuchMethodError</code> обычно означает, что код был скомпилирован против одной версии класса, а во время выполнения загрузилась другая версия, в которой нет метода с ожидаемым именем и дескриптором.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The Java compiler verifies method calls against the compile-time classpath. Later, the JVM resolves that symbolic method reference against the class actually loaded at runtime. If dependency resolution, shading, container libraries or a transitive dependency selects an older or incompatible class, the JVM cannot resolve the call.</p>
<p>This is common when a framework module is upgraded but an extension module, plugin, driver or transitive library remains on an older version.</p>
</td>
<td valign="top" width="50%">

<p>Компилятор Java проверяет вызовы методов по classpath во время компиляции. Позже JVM разрешает символическую ссылку на метод по классу, который реально загружен при запуске. Если разрешение зависимостей, shading, библиотеки контейнера или транзитивная зависимость подставили более старый или несовместимый класс, JVM не сможет разрешить вызов.</p>
<p>Такое часто бывает, когда обновили модуль фреймворка, но модуль расширения, плагин, драйвер или транзитивная библиотека остались на старой версии.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The descriptor includes parameter types and return type. Even a method with the same Java-looking name may not match if the signature changed, a return type changed in bytecode terms, or a bridge method expected by older compiled code is absent.</p>
</td>
<td valign="top" width="50%">

<p>Дескриптор включает типы параметров и возвращаемый тип. Даже метод с тем же именем в Java-коде может не подойти, если изменилась сигнатура, поменялся возвращаемый тип на уровне байткода или отсутствует bridge-метод, которого ожидает старый скомпилированный код.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use dependency trees, lock files, Maven Enforcer or Gradle dependency insight to find the selected version. In production incidents, log the JAR location of the loaded class via <code>clazz.getProtectionDomain().getCodeSource()</code> when it is safe and useful.</p>
</td>
<td valign="top" width="50%">

<p>Для поиска причины используют дерево зависимостей, lock-файлы, Maven Enforcer или Gradle dependency insight, чтобы увидеть выбранную версию. В инциденте иногда полезно залогировать путь к JAR загруженного класса через <code>clazz.getProtectionDomain().getCodeSource()</code>, если это безопасно и уместно.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>The problem may be in a transitive dependency, not in the dependency you upgraded directly.</li>
<li>IDE and packaged application can resolve different dependency versions.</li>
<li>Fat JAR merging can hide the source of the conflicting class.</li>
<li>A full clean rebuild helps, but it does not fix a wrong runtime dependency graph.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Проблема может быть в транзитивной зависимости, а не в той, которую обновили напрямую.</li>
<li>IDE и упакованное приложение могут выбрать разные версии зависимостей.</li>
<li>Сборка fat JAR может скрыть источник конфликтующего класса.</li>
<li>Полная чистая пересборка помогает убрать мусор, но не исправляет неправильный граф зависимостей во время запуска.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does <code>NoSuchMethodError</code> usually indicate?<br>A: Compile-time and runtime versions of a class do not match.</p>
</td>
<td valign="top" width="50%">

<p>В: На что обычно указывает <code>NoSuchMethodError</code>?<br>О: Версии класса при компиляции и при запуске не совпали.</p>

<summary><strong>JCORE-RUNTIME-007. How can classpath conflicts appear at runtime?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Classpath conflicts appear when the runtime contains duplicate or incompatible classes and resources. The JVM loads one definition according to classpath or classloader rules, while some compiled code expected another version.</p>
</td>
<td valign="top" width="50%">

<p>Конфликты classpath появляются, когда во время запуска доступны дублирующиеся или несовместимые классы и ресурсы. JVM загружает одно определение по правилам classpath или загрузчика классов, хотя часть скомпилированного кода ожидала другую версию.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The classic case is two versions of the same library. Maven or Gradle may choose one version globally, a container may provide another, and a fat JAR may include yet another. The application starts, but a particular code path fails with <code>NoSuchMethodError</code>, <code>NoClassDefFoundError</code>, <code>ClassCastException</code> or strange behavior.</p>

Приложение стартует, но конкретный путь выполнения падает с <code>NoSuchMethodError</code>, <code>NoClassDefFoundError</code>, <code>ClassCastException</code> или ведёт себя странно.</p>
<p>Конфликтовать могут и ресурсы: конфигурация логирования, файлы <code>META-INF/services</code>, Spring-метаданные и SQL-миграции могут перезаписываться или находиться в неожиданном порядке.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Classpath itself has no rich version model. It is mostly an ordered search space. Build tools solve versions before launch, but the JVM sees the resulting set of entries and classloaders.</p>
</td>
<td valign="top" width="50%">

<p>Сам classpath не имеет полноценной модели версий. Это в основном упорядоченное пространство поиска. Инструменты сборки разрешают версии до запуска, но JVM видит уже получившийся набор элементов и загрузчиков классов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>Для сервисов стоит проверять согласованность зависимостей, анализировать дерево зависимостей в CI, держать семейства фреймворков на BOM, не смешивать случайно библиотеки контейнера и приложения, а тестировать именно тот артефакт, который будет развёрнут.</p>

</td>
<td valign="top" width="50%">

<tr>

</tr>
<tr>
<td valign="top" width="50%">
<p>Shading packages dependency classes into your artifact. Relocation goes further and rewrites their package names, so your private copy no longer has the same class names as the normal library. This can reduce conflicts when two components need incompatible versions of the same dependency.</p>
</td>
<td valign="top" width="50%">

</tr>

</tr>

<td valign="top" width="50%">

<p>Relocation — это обходной приём, а не замена аккуратному управлению зависимостями. Он увеличивает размер артефакта, может скрыть уязвимые версии библиотек и сломать код, который зависит от точных имён пакетов, нативного кода (native code), имён при сериализации или сканирования фреймворком.</p>

</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>Shading стоит применять осознанно для приватных реализационных зависимостей и документировать это. В CI всё равно нужно сканировать shaded-библиотеки на уязвимости и проверять лицензии, потому что их код теперь находится внутри вашего артефакта.</p>

</td>
<td valign="top" width="50%">

<ul>

<details>
<summary><strong>JCORE-RUNTIME-009. What is the difference between classpath and module path?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The classpath is the traditional search path for classes and resources, mostly without explicit dependency or encapsulation rules. The module path is used by JPMS for named modules with descriptors, readability rules and package exports/opens.</p>
</td>
<td valign="top" width="50%">

<p>Classpath — традиционный путь поиска классов и ресурсов, в основном без явных правил зависимостей и инкапсуляции. Module path используется JPMS для именованных модулей с дескрипторами, правилами читаемости и указанием, какие пакеты экспортируются или открываются.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>On the classpath, all classes are effectively in the unnamed module, and public types from JARs are broadly visible if the classloader can find them. On the module path, a JAR can become a named module with <code>module-info.class</code>, and code can read only modules that are required.</p>
<p>The module path also lets Java detect some problems earlier, such as missing required modules or split packages between resolved modules.</p>
</td>
<td valign="top" width="50%">

<p>На classpath все классы фактически находятся в безымянном модуле, а публичные типы из JAR-файлов широко видимы, если загрузчик классов может их найти. На module path JAR может стать именованным модулем с <code>module-info.class</code>, а код может читать только те модули, которые объявлены как зависимости.</p>
<p>Module path также позволяет Java раньше обнаруживать некоторые проблемы, например отсутствующие требуемые модули или разделённые пакеты между разрешёнными модулями.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Classpath favors compatibility and simplicity. Module path favors explicit boundaries. Many backend applications still run mostly on the classpath, but understanding modules matters because JDK internals and reflective access are now governed by module rules.</p>
</td>
<td valign="top" width="50%">

</tr>
<tr>

</td>
<td valign="top" width="50%">

<summary><strong>🧠 JCORE-RUNTIME-011. How did the Java module system affect reflection and strong encapsulation?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>JPMS made package boundaries enforceable at runtime. Reflection is no longer a universal escape hatch: deep reflection into a non-open package can fail unless the package is opened by the module descriptor or by command-line options such as <code>--add-opens</code>.</p>

<td valign="top" width="50%">

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Before modules, many frameworks and libraries accessed private JDK or application internals with <code>setAccessible(true)</code>. <td valign="top" width="50%">

<p>До модулей многие фреймворки и библиотеки обращались к private-частям JDK или приложения через <code>setAccessible(true)</code>. Это стало особенно заметно на Java 17+, где широкий ослабленный доступ к внутренним API JDK был убран.</p>
<p>Для прикладного кода это означает, что интеграция с фреймворком может требовать явных <code>opens</code> для пакетов с классами сущностей (entities), конфигурациями или объектами сериализации.</p>

</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>Ключевое различие — читаемость модуля и глубокий доступ. Модуль может быть читаемым, а пакет экспортированным для обычного доступа к публичным членам, но рефлексия к private-полям всё равно требует, чтобы пакет был открыт.</p>

<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>В промышленной среде не стоит широко открывать большие пакеты JDK для всех безымянных модулей, если это не временный шаг миграции. Лучше обновлять библиотеки и использовать точечные объявления модулей или узкие стартовые флаги.</p>

<li><code>--add-opens</code> is a migration escape hatch, not a clean design boundary.</li>
<li>A framework may work on Java 8 and fail on Java 17+ because of stronger encapsulation.</li>
<li>Opening application packages can expose internals to reflection-based misuse.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>exports</code> недостаточно для рефлексии к private-полям.</li>
<li><code>--add-opens</code> — аварийный мостик для миграции, а не аккуратная граница дизайна.</li>

<summary><strong>JCORE-RUNTIME-012. What is the parent delegation model in Java class loading?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Parent delegation means a classloader normally asks its parent to find a class or resource before trying to define it itself. This protects platform classes and gives a predictable hierarchy of visibility.</p>
</td>
<td valign="top" width="50%">

<p>Модель родительского делегирования означает, что загрузчик классов обычно сначала просит родителя найти класс или ресурс и только потом пытается определить его сам. Это защищает классы платформы и задаёт предсказуемую иерархию видимости.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In the usual model, the application classloader delegates to the platform loader, which delegates toward the bootstrap loader. If the parent finds the class, the child uses that definition. If not, the child may search its own URLs or other sources.</p>
<p>The model avoids accidentally replacing core Java classes from the application classpath. It also means a child can usually see parent classes, but a parent cannot automatically see child-only application classes.</p>
</td>
<td valign="top" width="50%">

<p>В обычной модели application classloader делегирует platform loader, а тот — в сторону bootstrap loader. Если родитель нашёл класс, дочерний загрузчик использует это определение. Если нет, дочерний загрузчик может искать в собственных URL или других источниках.</p>
<p>Такая модель не даёт случайно заменить базовые классы Java из classpath приложения. Она также означает, что дочерний загрузчик обычно видит классы родителя, но родитель автоматически не видит классы, доступные только дочернему загрузчику.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Some environments intentionally alter the model. Application servers, plugin systems and test frameworks may use child-first or isolated loaders to let applications carry their own library versions.</p>
</td>
<td valign="top" width="50%">

<p>Некоторые окружения намеренно меняют эту модель. Серверы приложений, системы плагинов и тестовые фреймворки могут использовать child-first или изолированные загрузчики, чтобы приложения могли приносить собственные версии библиотек.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>When debugging, identify the defining loader for each important class. Parent delegation problems often look like “why is this old version used?” or “why can the framework not see my provider class?”.</p>
</td>
<td valign="top" width="50%">

<p>При отладке нужно определить загрузчик, который определил каждый важный класс. Проблемы родительского делегирования часто выглядят как «почему используется старая версия?» или «почему фреймворк не видит мой класс поставщика сервиса?».</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Parent-first is the common model, but not a law for every custom loader.</li>
<li>Visibility is usually downward: child sees parent, parent does not see child.</li>
<li>Child-first loading can solve one conflict and create another.</li>
<li>Resources may also be affected by delegation order.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Parent-first — обычная модель, но не обязательный закон для каждого пользовательского загрузчика.</li>
<li>Видимость обычно направлена вниз: дочерний загрузчик видит родителя, родитель не видит дочерние классы.</li>
<li>Child-first загрузка может решить один конфликт и создать другой.</li>
<li>На ресурсы порядок делегирования тоже влияет.</li>
</ul>

</td>
</tr>

</tr>

<tr>

</td>
<td valign="top" width="50%">

<p>В Java идентичность типа во время выполнения включает и бинарное имя класса, и загрузчик, который его определил. Если два разных загрузчика определили <code>com.example.User</code>, JVM считает их двумя разными типами, даже если байткод одинаковый.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>This is how isolation works. A plugin can have its own copy of a library without polluting the host. An application server can run two applications using different versions of the same class. But if objects cross the boundary and the receiving side expects its own version of the type, casts and <code>instanceof</code> checks fail.</p>
<p>The typical confusing error is <code>com.example.User cannot be cast to com.example.User</code>. The message is not nonsense: the two names are equal, but the defining loaders differ.</p>
</td>
<td valign="top" width="50%">

<p>Так работает изоляция. Плагин может иметь собственную копию библиотеки и не загрязнять приложение-хост. Сервер приложений может запускать два приложения с разными версиями одного класса. Но если объекты пересекают границу и принимающая сторона ожидает свою версию типа, приведения и проверки <code>instanceof</code> падают.</p>
<p>Типичная странная ошибка: <code>com.example.User cannot be cast to com.example.User</code>. Сообщение не бессмысленное: имена совпадают, но загрузчики, определившие классы, разные.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Each classloader-defined copy also has its own static fields, cached singletons and class initialization state. That can create subtle bugs when code assumes a JVM-wide singleton but actually has one singleton per loader.</p>
</td>
<td valign="top" width="50%">

<p>У каждой копии класса, определённой своим загрузчиком, есть собственные static-поля, кэши singleton и состояние инициализации класса. Это приводит к тонким ошибкам, когда код ожидает один singleton на всю JVM, а фактически получает один singleton на загрузчик.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use shared API types from a loader visible to both sides when objects must cross plugin or container boundaries. Keep implementation classes isolated, but share contracts intentionally.</p>
</td>
<td valign="top" width="50%">

<p>Если объекты должны пересекать границы плагина или контейнера, используйте общие API-типы из загрузчика, видимого обеим сторонам. Реализации можно изолировать, но контракты нужно разделять осознанно.</p>

</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Identical bytecode does not imply identical runtime type.</li>
<li>Static state is per defined class, not per class name globally.</li>
<li>Cross-loader casts are a common plugin/container bug.</li>
<li>Serialization across classloader boundaries needs careful type resolution.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Одинаковый байткод не означает одинаковый тип во время выполнения.</li>
<li>Static-состояние относится к конкретно определённому классу, а не к имени класса глобально.</li>
<li>Приведения через границу загрузчиков — типичная ошибка сред плагинов и контейнеров.</li>
<li>Сериализация через границы загрузчиков требует аккуратного разрешения типов.</li>

<details>
<summary><strong>JCORE-RUNTIME-015. What is the thread context classloader, and why do frameworks use it?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The thread context classloader, TCCL, is a classloader associated with a thread. Frameworks use it so shared or parent-loaded code can discover and load application classes that are only visible from the application side.</p>
</td>
<td valign="top" width="50%">

<p>Контекстный загрузчик потока (thread context classloader, TCCL) — это загрузчик классов, связанный с конкретным потоком. Фреймворки используют его, чтобы общий или загруженный родителем код мог находить и загружать классы приложения, видимые только со стороны приложения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Parent delegation creates a visibility problem for frameworks. A framework class may be loaded by a parent loader, while user implementations, JDBC drivers, serializers or service providers are loaded by a child application loader. If the framework used only its own classloader, it might not see user classes. The TCCL gives the framework a caller/application-oriented lookup point.</p>
<p>Common examples include <code>ServiceLoader</code>, resource scanning, XML parsers, logging providers and container integrations.</p>
</td>
<td valign="top" width="50%">

<p>Родительское делегирование создаёт для фреймворков проблему видимости. Класс фреймворка может быть загружен родительским загрузчиком, а пользовательские реализации, JDBC-драйверы, сериализаторы или поставщики сервисов — дочерним загрузчиком приложения. Если фреймворк использовал бы только собственный загрузчик, он мог бы не увидеть классы пользователя. TCCL даёт фреймворку точку поиска, ориентированную на вызывающий код или приложение.</p>
<p>Типичные примеры — <code>ServiceLoader</code>, сканирование ресурсов, XML-парсеры, поставщики логирования и интеграции с контейнерами.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>TCCL is mutable state on a thread. That makes it powerful but easy to misuse, especially with thread pools where a thread is reused by unrelated tasks.</p>
</td>
<td valign="top" width="50%">

<p>TCCL — изменяемое состояние потока. Это мощный механизм, но его легко использовать неправильно, особенно в пулах потоков, где один поток переиспользуется разными задачами.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>When temporarily changing the TCCL, always restore the previous value in a <code>finally</code> block. In executors, be careful not to leak application classloaders across redeploys or between tenants/plugins.</p>
</td>
<td valign="top" width="50%">

<p>Если TCCL временно меняется, предыдущий загрузчик нужно всегда восстанавливать в блоке <code>finally</code>. В пулах Executor важно не допускать утечки загрузчиков приложения между повторными развёртываниями (redeploy) или границами тенантов/плагинов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>TCCL is not the same as <code>SomeClass.class.getClassLoader()</code>.</li>
<li>Forgetting to restore it can leak classloaders or affect later tasks.</li>
<li>Async execution can lose the expected TCCL unless the framework propagates it.</li>
<li>Using TCCL hides dependencies, so document why it is needed.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>TCCL — не то же самое, что <code>SomeClass.class.getClassLoader()</code>.</li>
<li>Если не восстановить прежнее значение, можно протечь загрузчиками классов или повлиять на следующие задачи.</li>
<li>При асинхронном выполнении ожидаемый TCCL может потеряться, если фреймворк его не переносит.</li>
<li>Использование TCCL скрывает зависимости, поэтому причину нужно документировать.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why do frameworks use TCCL?<br>A: To load application-side classes and providers from code loaded by a parent/shared loader.</p>
</td>
<td valign="top" width="50%">

<p>В: Зачем фреймворкам TCCL?<br>О: Чтобы из кода, загруженного общим или родительским загрузчиком, находить классы и поставщиков приложения.</p>

</td>

<p>Пользовательский загрузчик классов полезен, когда приложению нужна управляемая загрузка, изоляция, преобразование или выгрузка классов. Типичные случаи — системы плагинов, серверы приложений, изоляция тестов, hot reload, инструментирование и загрузка сгенерированного или зашифрованного байткода.</p>

<th colspan="2" align="left">Deep dive</th>
</tr>

<tr>

</td>
<td valign="top" width="50%">

<p>Лучше использовать готовые механизмы фреймворков, если вы не пишете инфраструктуру. В обычных серверных сервисах пользовательские загрузчики редки; чаще проблемы зависимостей стоит решать инструментами сборки, границами модулей или изоляцией процессов.</p>

<details>
<summary><strong>JCORE-RUNTIME-018. What is <code>ServiceLoader</code>, and when is it useful?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>ServiceLoader</code> is the standard Java mechanism for discovering implementations of a service interface at runtime. It is useful for plugin-like extension points, drivers, providers and framework integrations where the API should not hard-code implementation classes.</p>
</td>
<td valign="top" width="50%">

<p><code>ServiceLoader</code> — стандартный механизм Java для поиска реализаций сервисного интерфейса во время выполнения. Он полезен для точек расширения, похожих на плагины (extension points), драйверов, поставщиков и интеграций фреймворков, где API не должен жёстко знать классы реализаций.</p>

<tr>
<th colspan="2" align="left">Interview answer</th>

<td valign="top" width="50%">

В модулях поставщики объявляются через <code>provides ... with ...</code>, а потребители — через <code>uses</code>.</p>
<p><code>ServiceLoader</code> ищет поставщиков лениво, поэтому загрузка и инициализация могут произойти только при обходе итератора или stream.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>Механизм простой и слабо связанный, но это не внедрение зависимостей (dependency injection). Он отвечает за поиск и создание экземпляров по правилам Java; жизненный цикл, конфигурация и порядок часто требуют дополнительного слоя.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, <code>ServiceLoader</code> is common for JDBC drivers, logging providers, crypto/security providers and framework SPIs. When building fat JARs, make sure service files are merged rather than overwritten.</p>
</td>
<td valign="top" width="50%">

<p>В промышленной среде <code>ServiceLoader</code> часто встречается у JDBC-драйверов, поставщиков логирования, поставщиков криптографии/безопасности и SPI фреймворков. При сборке fat JAR нужно убедиться, что файлы <code>META-INF/services</code> объединяются, а не перезаписываются.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Missing or overwritten <code>META-INF/services</code> files break discovery.</li>
<li>Provider constructors and initialization can throw at discovery time.</li>
<li>Classloader choice affects which providers are visible.</li>
<li>Provider ordering should not be assumed unless the API specifies it.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Отсутствующие или перезаписанные файлы <code>META-INF/services</code> ломают поиск поставщиков.</li>
<li>Конструкторы и инициализация поставщиков могут выбрасывать исключения во время поиска поставщиков.</li>
<li>Выбор загрузчика классов влияет на то, какие поставщики видимы.</li>
<li>На порядок поставщиков не стоит полагаться, если API явно его не задаёт.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">

</td>
<td valign="top" width="50%">

<p>В: Какую проблему решает <code>ServiceLoader</code>?<br>О: Поиск реализаций сервиса во время выполнения без жёсткой привязки к классам реализаций.</p>

<details>
<summary><strong>JCORE-RUNTIME-019. What are unnamed and automatic modules, and why do they matter during JPMS migration?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The unnamed module contains code on the classpath. An automatic module is a non-modular JAR placed on the module path; JPMS gives it a module name and broad readability, export and open behavior. Both exist to ease migration from classpath applications to JPMS.</p>
</td>
<td valign="top" width="50%">

<p>Безымянный модуль содержит код на classpath. Автоматический модуль — это немодульный JAR на module path; JPMS назначает ему имя модуля и даёт широкие правила читаемости, экспорта и открытия пакетов. Оба механизма нужны, чтобы упростить миграцию с classpath на JPMS.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Classpath code belongs to the unnamed module and can read many named modules, but named modules do not normally read the unnamed module. This affects migration order: if modular code needs a classpath-only library, that library may need to move to the module path.</p>
<p>Automatic modules are a bridge. They let existing JARs participate in module resolution before they have <code>module-info.class</code>. But their generated names can be unstable, and their broad exports are weaker design boundaries than explicit modules.</p>
</td>
<td valign="top" width="50%">

<p>Код на classpath принадлежит безымянному модулю и может читать многие именованные модули, но именованные модули обычно не читают безымянный модуль. Это влияет на порядок миграции: если модульному коду нужна библиотека только на classpath, её может потребоваться перенести на module path.</p>
<p>Автоматические модули — это мост. Они позволяют существующим JAR-файлам участвовать в разрешении модулей до появления <code>module-info.class</code>. Но их сгенерированные имена могут быть нестабильными, а широкие exports дают более слабые границы, чем явные модули.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A stable <code>Automatic-Module-Name</code> manifest entry can reduce naming risk, but it still does not provide a precise descriptor with explicit <code>requires</code>, <code>exports</code> and <code>opens</code>.</p>
</td>
<td valign="top" width="50%">

<p>Стабильная запись <code>Automatic-Module-Name</code> в manifest уменьшает риск с именем, но всё равно не заменяет точный дескриптор с явными <code>requires</code>, <code>exports</code> и <code>opens</code>.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>During migration, treat automatic modules as temporary. Avoid exposing their generated names in long-term public documentation if the library owner may later publish an explicit module name.</p>
</td>
<td valign="top" width="50%">

<p>При миграции автоматические модули лучше считать временным решением. Не стоит закреплять их сгенерированные имена в долгосрочной публичной документации, если автор библиотеки позже может выпустить явное имя модуля.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Named modules cannot freely depend on classpath-only code.</li>
<li>Automatic module names can change if based on JAR filenames.</li>
<li>Automatic modules export and open packages broadly, so they are not strong boundaries.</li>
<li>Split packages can block automatic-module migration.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Именованные модули не могут свободно зависеть от кода только на classpath.</li>
<li>Имена автоматических модулей могут измениться, если они получены из имени JAR-файла.</li>
<li>Автоматические модули широко экспортируют и открывают пакеты, поэтому это не строгие границы.</li>
<li>Разделённые пакеты могут заблокировать миграцию на automatic modules.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is an automatic module?<br>A: A non-modular JAR on the module path that JPMS treats as a module for migration.</p>
</td>
<td valign="top" width="50%">

<p>В: Что такое автоматический модуль?<br>О: Немодульный JAR на module path, который JPMS временно рассматривает как модуль для миграции.</p>

<details>
<summary><strong>🧠 JCORE-RUNTIME-020. What is a split package, and why is it problematic with modules?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A split package means the same Java package is spread across more than one module or JAR. JPMS treats split packages between resolved modules as problematic because package ownership becomes ambiguous and strong encapsulation cannot be enforced cleanly.</p>
</td>
<td valign="top" width="50%">

<p>Разделённый пакет (split package) означает, что один Java-пакет распределён между несколькими модулями или JAR-файлами. Для JPMS это проблема между разрешёнными модулями, потому что владение пакетом становится неоднозначным и строгую инкапсуляцию нельзя аккуратно обеспечить.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>On the traditional classpath, split packages can exist accidentally: two JARs both contain <code>com.example.util</code>. The JVM will load classes according to classloader/search order. With modules, a package is expected to belong to one module in a resolved configuration, so duplicate ownership is rejected or leads to migration problems.</p>
<p>Split packages often appear after large libraries are divided into multiple artifacts, or when a project creates “extension” JARs in the same package as the base library.</p>
</td>
<td valign="top" width="50%">

<p>На традиционном classpath split packages могут существовать случайно: два JAR-файла оба содержат <code>com.example.util</code>. JVM будет загружать классы по порядку поиска загрузчика. В модульной системе ожидается, что пакет в разрешённой конфигурации принадлежит одному модулю, поэтому двойное владение отвергается или мешает миграции.</p>
<p>Разделённые пакеты (split packages) часто появляются, когда большую библиотеку делят на несколько артефактов или когда проект создаёт «расширяющие» JAR-файлы в том же пакете, что базовая библиотека.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>The deeper issue is that packages are the unit of export and open rules in JPMS. If one package lives in multiple modules, it is unclear which module controls its API surface and reflective access.</p>
</td>
<td valign="top" width="50%">

<p>Главная причина в том, что в JPMS именно пакет является единицей для правил <code>exports</code> и <code>opens</code>. Если один пакет живёт в нескольких модулях, непонятно, какой модуль управляет его API-поверхностью и рефлексивным доступом.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Fix split packages by refactoring package names, merging artifacts, creating a proper common module, or keeping the affected legacy code on the classpath until it can be cleaned up.</p>
</td>
<td valign="top" width="50%">

<p>Разделённые пакеты исправляют через переименование пакетов, объединение артефактов, выделение корректного общего модуля или временное оставление проблемного legacy-кода на classpath до рефакторинга.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Split packages may be tolerated on the classpath but fail on the module path.</li>
<li>Adding <code>module-info.java</code> can expose old packaging mistakes.</li>
<li>Relocation can help only when the duplicate package belongs to a private dependency.</li>
<li>Do not publish new libraries that require users to split one package across artifacts.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Разделённые пакеты (split packages) могут работать на classpath, но падать на module path.</li>
<li>Добавление <code>module-info.java</code> может проявить старые ошибки упаковки.</li>
<li>Relocation помогает только если дублирующийся пакет относится к приватной зависимости.</li>
<li>Не стоит выпускать новые библиотеки, которые заставляют пользователей распределять один пакет по нескольким артефактам.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Why do modules dislike split packages?<br>A: JPMS uses packages as ownership and encapsulation units, so one package should not belong to multiple resolved modules.</p>
</td>
<td valign="top" width="50%">

<p>В: Почему модули плохо относятся к разделённым пакетам (split packages)?<br>О: JPMS использует пакеты как единицы владения и инкапсуляции, поэтому один пакет не должен принадлежать нескольким разрешённым модулям.</p>

</td>
</tr>

<details>
<summary><strong>🧠 JCORE-RUNTIME-021. What is the difference between <code>exports</code>, <code>opens</code>, <code>--add-exports</code> and <code>--add-opens</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>exports</code> makes a module package accessible for normal compilation and public-member access. <code>opens</code> allows deep reflection into a package. <code>--add-exports</code> and <code>--add-opens</code> are command-line overrides used to break or adjust module boundaries, usually during migration.</p>
</td>
<td valign="top" width="50%">

<p><code>exports</code> делает пакет модуля доступным для обычной компиляции и доступа к публичным членам. <code>opens</code> разрешает глубокую рефлексию в пакет. <code>--add-exports</code> и <code>--add-opens</code> — стартовые переопределения, которые ломают или корректируют границы модулей, обычно на время миграции.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use <code>exports</code> for public API packages. Use <code>opens</code> for packages that frameworks must inspect or modify reflectively, such as entity classes or serialization targets. Both can be qualified to specific target modules.</p>
<p><code>--add-exports</code> exposes a package from a module to another module from the command line. <code>--add-opens</code> opens a package for deep reflection. They are useful when you cannot immediately change a dependency or module descriptor, but they encode runtime policy outside the codebase.</p>
</td>
<td valign="top" width="50%">

<p><code>exports</code> используют для пакетов публичного API. <code>opens</code> — для пакетов, которые фреймворки должны читать или изменять через рефлексию, например классы сущностей (entities) или объекты сериализации. Оба объявления можно ограничивать конкретными целевыми модулями.</p>
<p><code>--add-exports</code> с командной строки экспортирует пакет одного модуля другому модулю. <code>--add-opens</code> открывает пакет для глубокой рефлексии. Они полезны, когда нельзя сразу изменить зависимость или дескриптор модуля, но такая политика оказывается спрятанной вне кодовой базы.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>A useful rule of thumb: <code>exports</code> is about ordinary Java access to public types; <code>opens</code> is about reflective access beyond ordinary Java access checks.</p>
</td>
<td valign="top" width="50%">

<p>Практическое правило: <code>exports</code> относится к обычному Java-доступу к публичным типам; <code>opens</code> относится к рефлексивному доступу глубже обычных проверок Java-доступа.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production launch scripts, keep any <code>--add-*</code> flags explicit, narrow and tracked. Broad flags such as opening to <code>ALL-UNNAMED</code> may be acceptable during migration, but they should have an owner and removal plan.</p>
</td>
<td valign="top" width="50%">

<p>В скриптах запуска промышленной среды любые <code>--add-*</code> флаги должны быть явными, узкими и отслеживаемыми. Широкие флаги вроде открытия для <code>ALL-UNNAMED</code> могут быть допустимы при миграции, но у них должен быть владелец и план удаления.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>exports</code> does not imply deep reflection.</li>
<li><code>opens</code> does not make a package a normal compile-time API.</li>
<li>Command-line <code>--add-*</code> flags can differ between local, CI and production runs.</li>
<li>Depending on JDK internals via <code>--add-exports</code> is fragile.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>exports</code> не означает глубокую рефлексию.</li>
<li><code>opens</code> не делает пакет обычным API для компиляции.</li>
<li>Флаги <code>--add-*</code> могут различаться между локальным запуском, CI и промышленной средой.</li>
<li>Зависимость от внутренних API JDK через <code>--add-exports</code> хрупкая.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: Which directive is for deep reflection?<br>A: <code>opens</code>, or temporarily <code>--add-opens</code> from the command line.</p>
</td>
<td valign="top" width="50%">

<p>В: Какая директива нужна для глубокой рефлексии?<br>О: <code>opens</code>, либо временно <code>--add-opens</code> с командной строки.</p>
