<a id="jcore-prod-001"></a>

<details>
<summary><strong>JCORE-PROD-001. How should backend code avoid precision bugs in money and quantity calculations?</strong></summary>

#### Short answer

Backend code should avoid binary floating-point types for money and exact decimal quantities. Use `BigDecimal` with explicit scale and rounding, or integer minor units when the domain has a fixed scale.

#### Interview answer

In an interview I would say: make precision part of the domain contract. Define currency or unit, allowed precision, scale, rounding mode and the place where rounding happens. Do not spread ad-hoc arithmetic across services; put the rule into a value object or a dedicated calculation service.

#### Deep dive

Persistence and API contracts must match the Java model. Database `DECIMAL`/`NUMERIC` precision and scale, JSON representation, serialization and validation should preserve the same exact value.

#### Production angle

Test edge cases: half values, currency conversion, tax rounding per item versus per invoice, very large amounts, negative corrections, database round-trips and overflow when using integer minor units.

#### Traps / caveats

- Do not construct `BigDecimal` from imprecise `double` input.
- Always specify `RoundingMode` for divisions that may not terminate.
- Do not use `BigDecimal.equals()` for money unless scale equality is intended.
- Integer minor units still need currency-specific scale rules.

#### Optional Anki

Q: What is the safe default for money calculations?
A: `BigDecimal` or integer minor units with explicit scale, currency and rounding.

</details>

<details>
<summary><strong>JCORE-PROD-002. How should backend code avoid time zone bugs in APIs, databases and scheduled jobs?</strong></summary>

#### Short answer

Use temporal types deliberately: `Instant` for moments, `LocalDate` for business dates, and `ZonedDateTime` or a `ZoneId` when civil time rules matter. Never rely on the server default time zone as an implicit business rule.

#### Interview answer

APIs should document whether a value is a UTC instant, an offset date-time, a local date-time with a region zone, or a pure business date. Scheduled jobs should declare the zone used for “midnight”, “business day” and “first day of month”.

#### Deep dive

Daylight saving time can create skipped and repeated local times. A job scheduled for 02:30 may not exist on one day and may be ambiguous on another. A fixed UTC offset is not the same as a region time zone with historical and future rules.

#### Production angle

Run services with explicit defaults, often UTC, but keep the business zone in the data when later local interpretation matters: billing cycles, reports, legal deadlines and user-facing schedules.

#### Traps / caveats

- `LocalDateTime` is not a point on the global timeline.
- Laptop, CI and production may have different default time zones.
- Database timestamp types differ by vendor and driver.
- Tests should cover DST transitions for relevant zones.

#### Optional Anki

Q: What should represent an event timestamp?
A: Usually `Instant`, plus zone information if later local interpretation matters.

</details>

<details>
<summary><strong>JCORE-PROD-003. How should public Java APIs document nullability and invalid inputs?</strong></summary>

#### Short answer

Public Java APIs should make nullability and invalid-input behavior explicit through types, annotations, Javadoc, validation and tests. Callers should know what may be `null`, what cannot, and which exception or result appears for invalid input.

#### Interview answer

Prefer non-null by default. Use project-standard `@Nullable`/`@NonNull` annotations where they are enforced by tooling. Return empty collections instead of `null`, and use `Optional` for absent single results when it improves clarity.

#### Deep dive

Absence is different from invalid input. “User not found” can be an empty result, `Optional.empty()` or HTTP 404. A negative page size or malformed currency code is usually a contract violation and should fail fast.

#### Production angle

Use the same policy across REST controllers, message consumers, repository APIs and shared client libraries. Stable error behavior matters because callers build retry, mapping and user-message logic around it.

#### Traps / caveats

- Do not mix `null`, empty collections and `Optional` randomly for the same concept.
- `Optional` is usually not a good DTO field or method parameter type.
- Document whether exceptions are part of the API contract.
- Fail fast near the boundary instead of deep in the call stack.

#### Optional Anki

Q: How should an API communicate possible `null`?
A: With type choice, nullability annotations, Javadoc and consistent implementation.

</details>

<a id="jcore-prod-004"></a>

<details>
<summary><strong>JCORE-PROD-004. Why is try-with-resources important for backend code?</strong></summary>

#### Short answer

`try-with-resources` closes `AutoCloseable` resources reliably on all exit paths. Backend code uses files, sockets, streams, database connections, statements, result sets and HTTP responses, so deterministic cleanup prevents resource leaks.

#### Interview answer

I would say it is safer than manual `finally`. Resources are closed in reverse declaration order, and if both the body and `close()` throw exceptions, Java keeps the primary exception and records close failures as suppressed exceptions.

#### Deep dive

Resource ownership should be visible in API design. A method either owns and closes a resource, or transfers ownership clearly to the caller. Ambiguous ownership creates leaks and double-close bugs.

#### Production angle

In production, leaked resources exhaust connection pools, file descriptors and HTTP client pools. Code review should treat missing ownership and missing close paths as reliability bugs.

#### Traps / caveats

- Do not return a resource from inside a block that will close it.
- Know whether closing a wrapper also closes the underlying resource.
- Use suppressed exceptions during diagnostics.
- Do not use try-with-resources when the resource must intentionally outlive the method.

#### Optional Anki

Q: What does try-with-resources prevent?
A: Resource leaks by reliably closing `AutoCloseable` resources.

</details>

<details>
<summary><strong>JCORE-PROD-005. What is the difference between `System.currentTimeMillis()` and `System.nanoTime()`?</strong></summary>

#### Short answer

`currentTimeMillis()` returns wall-clock time related to the Unix epoch and can move with system clock changes. `nanoTime()` is for measuring elapsed time and has an arbitrary origin.

#### Interview answer

Use `currentTimeMillis()` or, better, `Instant.now(clock)` when you need a timestamp. Use `nanoTime()` for durations, timeouts and latency measurements because it is not intended to represent calendar time.

#### Deep dive

Only differences between two `nanoTime()` readings in the same JVM are meaningful. Timeout checks should use subtraction, for example `System.nanoTime() - start >= timeoutNanos`, which is robust against overflow.

#### Production angle

Inject `Clock` for business time so tests can control current time. Use `nanoTime()` in infrastructure code for deadlines, metrics and elapsed-time measurement.

#### Traps / caveats

- Do not persist or log `nanoTime()` as a real timestamp.
- Do not measure elapsed time with wall-clock time if clock jumps matter.
- Nanosecond precision does not guarantee nanosecond resolution.
- Use JMH for serious microbenchmarks.

#### Optional Anki

Q: Which API should measure elapsed time?
A: `System.nanoTime()`, by comparing differences between readings.

</details>

<details>
<summary><strong>JCORE-PROD-006. What Java language or API choices commonly create hidden production bugs?</strong></summary>

#### Short answer

Common hidden bugs come from imprecise numeric types, ambiguous time handling, default locale/charset/time zone, mutable static state, weak nullability contracts, broken equality, mutable map keys, reflection/proxy surprises and dependency linkage conflicts.

#### Interview answer

The common pattern is implicit context. Java often provides a convenient default, but production needs an explicit domain decision: exact money rules, time zone semantics, stable equality, resource ownership and dependency version control.

#### Deep dive

A feature can be technically valid but semantically weak for an API contract. The answer is often not “ban the API”, but wrap the dangerous choice in a domain type or infrastructure abstraction that documents the rule.

#### Production angle

Use code review checklists, static analysis and integration tests against the packaged artifact. Pay attention to money in floating point, raw timestamps, missing `Clock`, unclosed resources, broad `catch(Exception)` and dependency convergence warnings.

#### Traps / caveats

- Convenient defaults are often environment-dependent.
- Mutable static state survives across requests and may break tests or redeploys.
- Reflection and proxies can change call paths and equality assumptions.
- Classpath conflicts may appear only in the final deployment artifact.

#### Optional Anki

Q: What do many Java production traps have in common?
A: An implicit default is used where the domain needed an explicit rule.

</details>

<details>
<summary><strong>🧠 JCORE-PROD-007. What should be checked before upgrading the Java runtime version of a production service?</strong></summary>

#### Short answer

Check build tooling, dependencies, framework support, bytecode tools, JVM flags, reflection/module access, GC and memory behavior, TLS/security defaults, observability agents, container images, performance baselines, tests and rollback strategy.

#### Interview answer

I would treat a runtime upgrade as a production dependency upgrade. Run CI on the target JDK, test the real packaged artifact, verify startup, database and messaging paths, serialization, TLS-handshake, monitoring agents and representative load.

#### Deep dive

Pay special attention to libraries that use reflection, bytecode generation, agents or JDK internals. Old JVM flags may be ignored, removed or change meaning. A newer JDK may also change security algorithms, certificates and time-zone data.

#### Production angle

Roll out gradually with a canary or blue/green deployment. Keep the previous runtime image available, monitor latency, errors, GC, memory, CPU and connection pools, and document rollback steps.

#### Traps / caveats

- Do not upgrade build JDK and runtime JDK independently without understanding `--release`.
- Do not copy old GC flags blindly.
- Agents and bytecode libraries often block upgrades.
- Rare endpoints may be the first place where linkage or reflection errors appear.

#### Optional Anki

Q: What is the safest mindset for a Java runtime upgrade?
A: Treat it as a production dependency upgrade with compatibility, performance and rollback checks.

</details>

<details>
<summary><strong>JCORE-PROD-008. What should be used instead of `finalize()` for resource cleanup?</strong></summary>

#### Short answer

Use explicit ownership with `AutoCloseable`/`Closeable` and try-with-resources. `Cleaner` can be a last-resort safety net, but not the primary cleanup mechanism.

#### Interview answer

`finalize()` is unreliable: it runs at an unspecified time, may never run before process exit, delays cleanup, complicates GC and has security/resurrection problems. Since Java 18, finalization has been deprecated for removal.

#### Deep dive

The better design is deterministic cleanup. Whoever owns a file, socket, native handle or pooled connection should close it in a known control path. APIs should make ownership obvious.

#### Production angle

In backend services, leaks of scarce resources become incidents. Prefer small resource scopes, try-with-resources, pool metrics, leak detection and tests that verify close behavior.

#### Traps / caveats

- `Cleaner` is a fallback, not deterministic cleanup.
- Cleaner actions must not capture the object being cleaned.
- Do not put business logic in cleanup handlers.
- Resource ownership should be visible in API design.

#### Optional Anki

Q: What replaces `finalize()` for normal cleanup?
A: `AutoCloseable`/`Closeable` with try-with-resources and explicit ownership.

</details>

<details>
<summary><strong>🧠 JCORE-PROD-009. What are suppressed exceptions in try-with-resources?</strong></summary>

#### Short answer

Suppressed exceptions are secondary exceptions recorded when closing resources while another exception is already being thrown. In try-with-resources, the body exception remains primary and close failures are attached through `Throwable.getSuppressed()`.

#### Interview answer

I would compare it with manual `finally`. Without suppression, a `close()` failure can hide the original exception. Try-with-resources preserves the original cause and still keeps cleanup failures for diagnostics.

#### Deep dive

If several resources are declared, they are closed in reverse order. If the body throws, close failures become suppressed exceptions. If the body does not throw, a close failure can itself become the primary exception.

#### Production angle

In backend incidents, suppressed exceptions can reveal failed commit/rollback, failed stream close, broken network cleanup or a resource-pool issue that happened while handling the primary failure.

#### Traps / caveats

- Do not log only `e.getMessage()`; full stack traces show suppressed exceptions.
- Custom exception wrappers should preserve suppressed exceptions when possible.
- Suppression can be disabled for some `Throwable` instances, though it is uncommon.
- Suppressed exceptions are diagnostic information, not a replacement for handling the primary error.

#### Optional Anki

Q: Where does try-with-resources store close failures when the body already failed?
A: In the primary exception’s suppressed exceptions.

</details>
