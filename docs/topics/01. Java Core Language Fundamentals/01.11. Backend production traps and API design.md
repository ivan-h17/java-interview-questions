# 11. Backend production traps and API design

<a id="jcore-prod-001"></a>

<details>
<summary><strong>JCORE-PROD-001. How should backend code avoid precision bugs in money and quantity calculations?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Backend code should avoid binary floating-point types for money and exact decimal quantities. Use <code>BigDecimal</code> with explicit scale and rounding, or integer minor units when the domain has a fixed scale.</p>
</td>
<td valign="top" width="50%">

<p>Серверный код не должен использовать бинарные числа с плавающей точкой для денег и точных десятичных количеств. Лучше применять <code>BigDecimal</code> с явным масштабом (scale) и режимом округления либо целые значения в минимальных денежных единицах (minor units), если масштаб в предметной области фиксирован.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In an interview I would say: make precision part of the domain contract. Define currency or unit, allowed precision, scale, rounding mode and the place where rounding happens. Do not spread ad-hoc arithmetic across services; put the rule into a value object or a dedicated calculation service.</p>
</td>
<td valign="top" width="50%">

<p>На интервью я бы сказал так: точность должна быть частью доменного контракта. Нужно определить валюту или единицу измерения, допустимую точность, масштаб, режим округления и место, где выполняется округление. Не стоит размазывать случайную арифметику по сервисам; правило лучше держать в объекте-значении (value object) или отдельном сервисе расчётов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Persistence and API contracts must match the Java model. Database <code>DECIMAL</code>/<code>NUMERIC</code> precision and scale, JSON representation, serialization and validation should preserve the same exact value.</p>
</td>
<td valign="top" width="50%">

<p>Модель хранения и API-контракт должны совпадать с Java-моделью. Точность и масштаб колонок <code>DECIMAL</code>/<code>NUMERIC</code>, JSON-представление, сериализация и валидация должны сохранять одно и то же точное значение.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Test edge cases: half values, currency conversion, tax rounding per item versus per invoice, very large amounts, negative corrections, database round-trips and overflow when using integer minor units.</p>
</td>
<td valign="top" width="50%">

<p>Проверяйте пограничные случаи: значения ровно посередине, конвертацию валют, округление налога по строкам и по счёту, очень большие суммы, отрицательные корректировки, чтение/запись через БД и переполнение при хранении сумм целыми единицами.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not construct <code>BigDecimal</code> from imprecise <code>double</code> input.</li>
<li>Always specify <code>RoundingMode</code> for divisions that may not terminate.</li>
<li>Do not use <code>BigDecimal.equals()</code> for money unless scale equality is intended.</li>
<li>Integer minor units still need currency-specific scale rules.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не создавайте <code>BigDecimal</code> из неточного <code>double</code>, если это не сделано осознанно.</li>
<li>Всегда задавайте <code>RoundingMode</code> для деления, которое может не завершиться конечной десятичной дробью.</li>
<li>Не используйте <code>BigDecimal.equals()</code> для денег, если равенство масштаба не является частью правила.</li>
<li>Целые минимальные денежные единицы всё равно требуют правил масштаба для каждой валюты.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What is the safe default for money calculations?<br>A: <code>BigDecimal</code> or integer minor units with explicit scale, currency and rounding.</p>
</td>
<td valign="top" width="50%">

<p>В: Безопасный подход к денежным расчётам?<br>О: <code>BigDecimal</code> или целые значения в минимальных денежных единицах с явным масштабом, валютой и округлением.</p>

</td>
</tr>
</tbody>
</table>
</details>

<details>
<summary><strong>JCORE-PROD-002. How should backend code avoid time zone bugs in APIs, databases and scheduled jobs?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use temporal types deliberately: <code>Instant</code> for moments, <code>LocalDate</code> for business dates, and <code>ZonedDateTime</code> or a <code>ZoneId</code> when civil time rules matter. Never rely on the server default time zone as an implicit business rule.</p>
</td>
<td valign="top" width="50%">

<p>Используйте типы времени осознанно: <code>Instant</code> для моментов, <code>LocalDate</code> для бизнес-дат, <code>ZonedDateTime</code> или <code>ZoneId</code>, когда важны правила гражданского времени. Не полагайтесь на часовой пояс сервера по умолчанию как на неявное бизнес-правило.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>APIs should document whether a value is a UTC instant, an offset date-time, a local date-time with a region zone, or a pure business date. Scheduled jobs should declare the zone used for “midnight”, “business day” and “first day of month”.</p>
</td>
<td valign="top" width="50%">

<p>API должны документировать, что именно передаётся: UTC-момент, дата-время со смещением, локальные дата и время с региональным часовым поясом или чистая бизнес-дата. Задачи по расписанию должны явно задавать часовой пояс для понятий «полночь», «рабочий день» и «первый день месяца».</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Daylight saving time can create skipped and repeated local times. A job scheduled for 02:30 may not exist on one day and may be ambiguous on another. A fixed UTC offset is not the same as a region time zone with historical and future rules.</p>
</td>
<td valign="top" width="50%">

<p>Летнее время может создавать пропущенные и повторяющиеся локальные времена. Задача на 02:30 в один день может не иметь допустимого локального времени, а в другой — быть неоднозначной. Фиксированное смещение UTC не равно региональному часовому поясу с историческими и будущими правилами.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Run services with explicit defaults, often UTC, but keep the business zone in the data when later local interpretation matters: billing cycles, reports, legal deadlines and user-facing schedules.</p>
</td>
<td valign="top" width="50%">

<p>Запускайте сервисы с явными значениями по умолчанию, часто с UTC, но сохраняйте бизнес-часовой пояс в данных, если позже важна локальная интерпретация: расчётные периоды, отчёты, юридические сроки и пользовательские расписания.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li><code>LocalDateTime</code> is not a point on the global timeline.</li>
<li>Laptop, CI and production may have different default time zones.</li>
<li>Database timestamp types differ by vendor and driver.</li>
<li>Tests should cover DST transitions for relevant zones.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li><code>LocalDateTime</code> не является точкой на глобальной временной шкале.</li>
<li>Локальная машина, CI и промышленная среда могут иметь разные часовые пояса по умолчанию.</li>
<li>Типы временных меток в БД отличаются между вендорами и драйверами.</li>
<li>Тесты должны покрывать переходы летнего времени для важных часовых поясов.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What should represent an event timestamp?<br>A: Usually <code>Instant</code>, plus zone information if later local interpretation matters.</p>
</td>
<td valign="top" width="50%">

<p>В: Чем обычно представлять временную метку события?<br>О: Обычно <code>Instant</code>, плюс часовой пояс, если позже важна локальная интерпретация.</p>

</td>
</tr>
</tbody>
</table>
</details>

<details>
<summary><strong>JCORE-PROD-003. How should public Java APIs document nullability and invalid inputs?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Public Java APIs should make nullability and invalid-input behavior explicit through types, annotations, Javadoc, validation and tests. Callers should know what may be <code>null</code>, what cannot, and which exception or result appears for invalid input.</p>
</td>
<td valign="top" width="50%">

<p>Публичные Java API должны явно описывать допустимость <code>null</code> (nullability) и поведение при неверном вводе через типы, аннотации, Javadoc, валидацию и тесты. Вызывающий код должен понимать, что может быть <code>null</code>, что не может, и какое исключение или результат появится при недопустимом значении.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Prefer non-null by default. Use project-standard <code>@Nullable</code>/<code>@NonNull</code> annotations where they are enforced by tooling. Return empty collections instead of <code>null</code>, and use <code>Optional</code> for absent single results when it improves clarity.</p>
</td>
<td valign="top" width="50%">

<p>По умолчанию лучше считать значения не допускающими <code>null</code>. Используйте принятые в проекте аннотации <code>@Nullable</code>/<code>@NonNull</code>, если их поддерживают инструменты. Возвращайте пустые коллекции вместо <code>null</code>, а <code>Optional</code> применяйте для отсутствующего одиночного результата там, где это делает контракт понятнее.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Absence is different from invalid input. “User not found” can be an empty result, <code>Optional.empty()</code> or HTTP 404. A negative page size or malformed currency code is usually a contract violation and should fail fast.</p>
</td>
<td valign="top" width="50%">

<p>Отсутствие результата отличается от неверного ввода. «Пользователь не найден» может быть пустым результатом, <code>Optional.empty()</code> или HTTP 404. Отрицательный размер страницы или некорректный код валюты обычно нарушают контракт и должны приводить к быстрой ошибке.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use the same policy across REST controllers, message consumers, repository APIs and shared client libraries. Stable error behavior matters because callers build retry, mapping and user-message logic around it.</p>
</td>
<td valign="top" width="50%">

<p>Используйте единую политику в REST-контроллерах, обработчиках сообщений, repository API и общих клиентских библиотеках. Стабильное поведение ошибок важно: вызывающие стороны строят вокруг него повторы, маппинг и пользовательские сообщения.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not mix <code>null</code>, empty collections and <code>Optional</code> randomly for the same concept.</li>
<li><code>Optional</code> is usually not a good DTO field or method parameter type.</li>
<li>Document whether exceptions are part of the API contract.</li>
<li>Fail fast near the boundary instead of deep in the call stack.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не смешивайте <code>null</code>, пустые коллекции и <code>Optional</code> случайно для одного и того же смысла.</li>
<li><code>Optional</code> обычно плохо подходит для поля DTO или параметра метода.</li>
<li>Документируйте, являются ли исключения частью контракта API.</li>
<li>Падайте быстро рядом с границей, а не глубоко в стеке вызовов.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: How should an API communicate possible <code>null</code>?<br>A: With type choice, nullability annotations, Javadoc and consistent implementation.</p>
</td>
<td valign="top" width="50%">

<p>В: Как API должен сообщать о возможном <code>null</code>?<br>О: Через выбор типа, nullability-аннотации, Javadoc и согласованную реализацию.</p>

</td>
</tr>
</tbody>
</table>
</details>

<details>
<summary><strong>JCORE-PROD-004. Why is try-with-resources important for backend code?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>try-with-resources</code> closes <code>AutoCloseable</code> resources reliably on all exit paths. Backend code uses files, sockets, streams, database connections, statements, result sets and HTTP responses, so deterministic cleanup prevents resource leaks.</p>
</td>
<td valign="top" width="50%">

<p><code>try-with-resources</code> надёжно закрывает ресурсы <code>AutoCloseable</code> на всех путях выхода. Серверный код работает с файлами, сокетами, потоками, соединениями с БД, statement/result set и HTTP-ответами, поэтому детерминированное закрытие предотвращает утечки ресурсов.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>I would say it is safer than manual <code>finally</code>. Resources are closed in reverse declaration order, and if both the body and <code>close()</code> throw exceptions, Java keeps the primary exception and records close failures as suppressed exceptions.</p>
</td>
<td valign="top" width="50%">

<p>Я бы сказал, что это безопаснее ручного <code>finally</code>. Ресурсы закрываются в порядке, обратном объявлению, а если исключение выбросили и тело блока, и <code>close()</code>, Java сохраняет основное исключение и записывает ошибки закрытия как подавленные исключения (suppressed exceptions).</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Resource ownership should be visible in API design. A method either owns and closes a resource, or transfers ownership clearly to the caller. Ambiguous ownership creates leaks and double-close bugs.</p>
</td>
<td valign="top" width="50%">

<p>Владение ресурсом должно быть видно в дизайне API. Метод либо владеет ресурсом и закрывает его, либо явно передаёт владение вызывающему коду. Неясное владение создаёт утечки и ошибки двойного закрытия.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>In production, leaked resources exhaust connection pools, file descriptors and HTTP client pools. Code review should treat missing ownership and missing close paths as reliability bugs.</p>
</td>
<td valign="top" width="50%">

<p>В промышленной среде утечки ресурсов исчерпывают пулы соединений, файловые дескрипторы и пулы HTTP-клиентов. При ревью кода отсутствие явного владения и пути закрытия стоит считать ошибкой надёжности.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not return a resource from inside a block that will close it.</li>
<li>Know whether closing a wrapper also closes the underlying resource.</li>
<li>Use suppressed exceptions during diagnostics.</li>
<li>Do not use try-with-resources when the resource must intentionally outlive the method.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не возвращайте ресурс из блока, который сразу его закроет.</li>
<li>Понимайте, закрывает ли обёртка (wrapper) нижележащий ресурс.</li>
<li>Используйте подавленные исключения (suppressed exceptions) при диагностике.</li>
<li>Не применяйте try-with-resources, если ресурс намеренно должен жить дольше метода.</li>
</ul>

</td>
</tr>
<tr>
<th colspan="2" align="left">Optional Anki</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Q: What does try-with-resources prevent?<br>A: Resource leaks by reliably closing <code>AutoCloseable</code> resources.</p>
</td>
<td valign="top" width="50%">

<p>В: Что предотвращает try-with-resources?<br>О: Утечки ресурсов за счёт надёжного закрытия <code>AutoCloseable</code>.</p>

</td>
</tr>
</tbody>

<details>
<summary><strong>JCORE-PROD-005. What is the difference between <code>System.currentTimeMillis()</code> and <code>System.nanoTime()</code>?</strong></summary>
<table>
<tbody>
<tr>
<th colspan="2" align="left">Short answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p><code>currentTimeMillis()</code> returns wall-clock time related to the Unix epoch and can move with system clock changes. <code>nanoTime()</code> is for measuring elapsed time and has an arbitrary origin.</p>
</td>
<td valign="top" width="50%">

<p><code>currentTimeMillis()</code> возвращает системное календарное время (wall-clock time), связанное с Unix epoch, и может изменяться при корректировке системных часов. <code>nanoTime()</code> нужен для измерения прошедшего времени и имеет произвольную точку отсчёта.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Interview answer</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Use <code>currentTimeMillis()</code> or, better, <code>Instant.now(clock)</code> when you need a timestamp. Use <code>nanoTime()</code> for durations, timeouts and latency measurements because it is not intended to represent calendar time.</p>
</td>
<td valign="top" width="50%">

<p>Используйте <code>currentTimeMillis()</code> или, лучше, <code>Instant.now(clock)</code>, когда нужна временная метка (timestamp). Для длительностей, таймаутов и измерения задержек используйте <code>nanoTime()</code>, потому что он не представляет календарное время.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Deep dive</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Only differences between two <code>nanoTime()</code> readings in the same JVM are meaningful. Timeout checks should use subtraction, for example <code>System.nanoTime() - start &gt;= timeoutNanos</code>, which is robust against overflow.</p>
</td>
<td valign="top" width="50%">

<p>Смысл имеет только разница между двумя значениями <code>nanoTime()</code> в одном экземпляре JVM. Проверки таймаута лучше писать через вычитание, например <code>System.nanoTime() - start &gt;= timeoutNanos</code>; такой вид устойчив к переполнению.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Production angle</th>
</tr>
<tr>
<td valign="top" width="50%">
<p>Inject <code>Clock</code> for business time so tests can control current time. Use <code>nanoTime()</code> in infrastructure code for deadlines, metrics and elapsed-time measurement.</p>
</td>
<td valign="top" width="50%">

<p>Для бизнес-времени внедряйте <code>Clock</code>, чтобы тесты могли управлять текущим временем. <code>nanoTime()</code> применяйте в инфраструктурном коде для deadline, метрик и измерения прошедшего времени.</p>

</td>
</tr>
<tr>
<th colspan="2" align="left">Traps / caveats</th>
</tr>
<tr>
<td valign="top" width="50%">
<ul>
<li>Do not persist or log <code>nanoTime()</code> as a real timestamp.</li>
<li>Do not measure elapsed time with wall-clock time if clock jumps matter.</li>
<li>Nanosecond precision does not guarantee nanosecond resolution.</li>
<li>Use JMH for serious microbenchmarks.</li>
</ul>
</td>
<td valign="top" width="50%">

<ul>
<li>Не сохраняйте и не логируйте <code>nanoTime()</code> как реальную временную метку.</li>
<li>Не измеряйте длительность календарным временем, если важны скачки системных часов.</li>

<tr>
