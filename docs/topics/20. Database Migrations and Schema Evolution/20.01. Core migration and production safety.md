# Core migration and production safety

---

<a id="mig-core-001"></a>

<details>
<summary><strong>MIG-CORE-001. What is a database migration?</strong></summary>

#### Short answer

A database migration is a versioned change to database schema or data that is applied in a controlled, repeatable way.

#### Interview answer

Migrations include actions like creating tables, adding columns, creating indexes, changing constraints, or backfilling data.

They are stored in version control and applied consistently across environments.

#### Deep dive

A migration system tracks which migrations were applied, prevents accidental reordering, and makes deployments reproducible.

Schema changes are part of application delivery and need review like code.

#### Production angle

In production, migrations must be safe for live traffic: avoid long locks, table rewrites, unbounded backfills and breaking old app versions.

Large migrations need rollout plans, monitoring, and rollback/recovery strategy.

#### Traps / caveats

- Migrations are not only DDL; they can include data changes.
- A migration that works locally can lock production.
- Manual hotfixes cause schema drift.
- Rollback is not always the reverse SQL.

#### Optional Anki

Q: What is a database migration?
A: A versioned, repeatable database schema/data change.

</details>

<a id="mig-core-002"></a>

<details>
<summary><strong>MIG-CORE-002. What are Flyway and Liquibase used for?</strong></summary>

#### Short answer

Flyway and Liquibase are tools for managing versioned database migrations across environments.

#### Interview answer

They keep a history table of applied migrations and run pending changes in order.

Flyway is commonly SQL-script oriented and convention-based. Liquibase is more feature-rich and supports multiple changelog formats.

#### Deep dive

Both help teams avoid manual schema drift and make deployments reproducible.

They do not automatically make a migration zero-downtime; the migration content still matters.

#### Production angle

In Java/Spring systems, these tools often run during application startup or CI/CD pipeline. For risky migrations, running as a separate controlled deployment step may be safer.

Migration failures must be observable and stop deployment.

#### Traps / caveats

- Do not run heavy migrations blindly on app startup.
- Version scripts carefully.
- Never edit already-applied migrations without a controlled repair process.
- Tooling does not replace production-safe DDL knowledge.

#### Optional Anki

Q: What do Flyway/Liquibase manage?
A: Versioned database migrations and applied-migration history.

</details>

<a id="mig-core-003"></a>

<details>
<summary><strong>MIG-CORE-003. What is a zero-downtime migration?</strong></summary>

#### Short answer

A zero-downtime migration changes schema or data without breaking old or new application versions while traffic continues.

#### Interview answer

The core idea is backward and forward compatibility. During deployment, old and new code may run at the same time, so the database must support both.

Typical strategy: expand schema, deploy code that supports both, backfill, switch reads/writes, then contract old schema later.

#### Deep dive

Zero-downtime migrations avoid destructive changes in the first step. Do not rename/drop/change meaning of a column while old code still uses it.

Data backfills should be chunked and observable.

#### Production angle

In production, plan deployments as multiple releases. Use feature flags, dual-write/dual-read carefully, validation queries, and rollback points.

Define what zero-downtime means for your SLA: no app errors, no write blocking, no read inconsistency.

#### Traps / caveats

- Zero-downtime is a process, not one SQL trick.
- Rollback after partial data migration may be hard.
- Dual writes can create inconsistencies.
- Long locks can still cause downtime.

#### Optional Anki

Q: What is zero-downtime migration?
A: A compatible multi-step change that keeps old and new app versions working during traffic.

</details>

<a id="mig-core-004"></a>

<details>
<summary><strong>MIG-CORE-004. What is expand-and-contract migration?</strong></summary>

#### Short answer

Expand-and-contract is a multi-step migration pattern: add new schema first, migrate usage, then remove old schema later.

#### Interview answer

Expand phase adds backward-compatible objects: new columns, tables, indexes or constraints. Migration phase updates code and backfills data. Contract phase removes old objects after they are unused.

It is the standard approach for zero-downtime schema evolution.

#### Deep dive

Example: add `full_name` while old `first_name`/`last_name` still exist; deploy code that writes both; backfill; read new column; remove old columns later.

Each step should be deployable and reversible enough.

#### Production angle

In production, separate expand and contract by at least one release. Verify metrics and logs before dropping old columns.

Keep compatibility across rolling deployments.

#### Traps / caveats

- Contract too early breaks old code.
- Dual-write logic must be tested.
- Backfills can take longer than planned.
- Old data and new data must be reconciled.

#### Optional Anki

Q: What are the phases of expand-and-contract?
A: Expand schema, migrate/backfill usage, then contract old schema.

</details>

<details>
<summary><strong>MIG-CORE-005. How would you add a nullable column safely?</strong></summary>

#### Short answer

Adding a nullable column without a heavy default is usually a safe, backward-compatible expand step.

#### Interview answer

A simple `ALTER TABLE ... ADD COLUMN new_col type` is generally compatible with old code because existing rows get NULL and old code ignores the column.

Then new code can start writing it.

#### Deep dive

Be careful with default values and NOT NULL. Some changes can rewrite a large table or take stronger locks depending on PostgreSQL version and expression.

If the column must eventually be mandatory, add it nullable first, backfill, then add constraint later.

#### Production angle

In production, check table size, lock behavior, replication, and migration timeout. Run during a safe window if the table is hot.

Deploy code that can tolerate NULL until backfill and constraint are complete.

#### Traps / caveats

- Nullable does not mean business-optional forever.
- Backfill and constraints need a later step.
- Adding default can change lock/rewrite behavior.
- Old app versions must ignore the new column.

#### Optional Anki

Q: Safe first step for new required column?
A: Add it nullable first, then backfill and constrain later.

</details>

<a id="mig-core-006"></a>

<details>
<summary><strong>MIG-CORE-006. How would you add a NOT NULL column to a huge table safely?</strong></summary>

#### Short answer

Add it nullable, backfill in batches, validate data, then add NOT NULL or a validated constraint in a separate step.

#### Interview answer

Adding a NOT NULL column with a value for every existing row can be risky on a huge table. The safe pattern is multi-step.

First add nullable column. Then deploy code writing it. Then backfill old rows in chunks. Then enforce non-null.

#### Deep dive

For enforcement, a common PostgreSQL pattern is: add `CHECK (new_col IS NOT NULL) NOT VALID`, validate it separately with `VALIDATE CONSTRAINT`, then set `NOT NULL` in a short controlled step.

Test the exact PostgreSQL version and lock behavior on staging before running it on a hot table.

#### Production angle

Backfill should be rate-limited, resumable and monitored. Use small transactions to avoid long locks, WAL spikes and replication lag.

Use `lock_timeout` and `statement_timeout` for DDL steps so the migration fails fast instead of joining a production lock queue. Application code should handle NULL until the final enforcement step.

#### Traps / caveats

- One huge UPDATE is dangerous.
- NOT NULL too early breaks old writes.
- Backfill can create bloat and WAL.
- Validation can still consume resources.

#### Optional Anki

Q: Safe pattern for NOT NULL on huge table?
A: Nullable column → code writes it → batched backfill → validate/enforce NOT NULL.

</details>

<a id="mig-core-007"></a>

<details>
<summary><strong>MIG-CORE-007. How would you add a new index on a large production table?</strong></summary>

#### Short answer

Use CREATE INDEX CONCURRENTLY when possible, run it separately, monitor progress, and validate it with real query plans.

#### Interview answer

A regular CREATE INDEX can block writes to the table. On large hot tables, that can cause downtime.

`CREATE INDEX CONCURRENTLY` avoids blocking normal writes for most of the build, but takes longer and has its own restrictions.

#### Deep dive

Before adding the index, confirm it is needed: inspect slow query, expected selectivity, existing indexes, write overhead, and possible redundancy.

After creation, run `EXPLAIN (ANALYZE, BUFFERS)` on representative queries.

#### Production angle

In production, avoid wrapping CREATE INDEX CONCURRENTLY in a transaction block. Schedule it, monitor locks/progress, disk usage, replication lag and failure cleanup.

If it fails, it may leave an invalid index that needs cleanup.

#### Traps / caveats

- Concurrent index build is safer but not free.
- It still consumes CPU/IO and disk.
- It can take much longer than regular CREATE INDEX.
- Too many indexes hurt writes.

#### Optional Anki

Q: How add index on hot large table?
A: Use CREATE INDEX CONCURRENTLY, monitor it, and validate with EXPLAIN.

</details>

<a id="mig-core-008"></a>

<details>
<summary><strong>MIG-CORE-008. Why can CREATE INDEX block writes?</strong></summary>

#### Short answer

Regular CREATE INDEX takes locks that prevent concurrent writes to the indexed table while the index is built.

#### Interview answer

PostgreSQL must build a consistent index over existing table data. A regular build is faster but more intrusive.

For hot tables, blocked writes can cascade into application timeouts and pool exhaustion.

#### Deep dive

This is why PostgreSQL provides `CREATE INDEX CONCURRENTLY`. It uses a more complex multi-phase process to allow writes, but with more time and overhead.

Reads are usually less of a concern than writes for a regular index build.

#### Production angle

In production, a blocking index build can look like a full application outage. Always know the lock behavior of DDL before running it.

Use lock timeouts and maintenance windows if needed.

#### Traps / caveats

- CREATE INDEX on large hot table is risky.
- Lock waits can exhaust app connection pools.
- DDL should be reviewed separately from small code changes.
- Rollback/cleanup plan is needed.

#### Optional Anki

Q: Why regular CREATE INDEX is risky?
A: It can block writes while building the index.

</details>

<a id="mig-core-009"></a>

<details>
<summary><strong>MIG-CORE-009. Why should CREATE INDEX CONCURRENTLY be used carefully?</strong></summary>

#### Short answer

It avoids most write blocking but is slower, more resource-intensive, cannot run inside a transaction block, and can leave invalid indexes on failure.

#### Interview answer

Concurrent index creation scans the table more than once and coordinates with concurrent transactions. This makes it safer for availability but heavier operationally.

If canceled or failed, cleanup may be required.

#### Deep dive

It still uses CPU, IO, WAL and disk. On replicas, it can increase lag. On primary, it can compete with production workload.

Also, not all migrations tools run it correctly unless configured, because it cannot be inside a transaction block.

#### Production angle

Run it as a separate migration or operational task. Monitor progress, locks, IO, replication lag, and invalid index state.

Plan cleanup for failed builds.

#### Traps / caveats

- Concurrent does not mean zero impact.
- It may fail and leave invalid index.
- Migration transaction wrappers can break it.
- Building many indexes concurrently can overload DB.

#### Optional Anki

Q: Why be careful with CREATE INDEX CONCURRENTLY?
A: It is availability-friendly but slower/heavier and has failure/transaction restrictions.

</details>

<a id="mig-core-010"></a>

<details>
<summary><strong>MIG-CORE-010. How would you backfill data safely?</strong></summary>

#### Short answer

Backfill in small, resumable batches with rate limiting, monitoring, and idempotent logic.

#### Interview answer

Backfill means populating new or corrected data for existing rows. A huge single UPDATE can create locks, WAL spikes, bloat, replica lag and long rollbacks.

Use a stable key range and commit after each batch.

#### Deep dive

Good backfills are restartable: if the job stops, it continues from last processed id or reprocesses safely.

Add progress metrics, dry-run mode, and validation queries. For worker-based jobs, `FOR UPDATE SKIP LOCKED` can let multiple workers claim rows without blocking each other.

```
UPDATE orders o
SET new_col = ...
WHERE o.id IN (
  SELECT id
  FROM orders
  WHERE new_col IS NULL
  ORDER BY id
  LIMIT 1000
  FOR UPDATE SKIP LOCKED
);
```

#### Production angle

In production, throttle based on DB load, replication lag and lock waits. Run during low traffic if necessary.

Backfill code should handle concurrent application writes.

#### Traps / caveats

- Huge updates create bloat.
- Backfill and live writes can race.
- Retries require idempotency.
- Validation is as important as writing.

#### Optional Anki

Q: Safe backfill principle?
A: Small idempotent batches with monitoring and validation.

</details>

<details>
<summary><strong>MIG-CORE-011. How would you rename a column without breaking old application versions?</strong></summary>

#### Short answer

Use expand-and-contract: add new column, dual-write or sync, migrate reads, then drop old column later.

#### Interview answer

A direct `ALTER TABLE RENAME COLUMN` breaks old code that still references the old name during rolling deploy.

Instead, keep both names available during the transition.

#### Deep dive

Possible steps: add new column; write both old and new; backfill new from old; read from new; stop using old; drop old in a later release.

Views or compatibility layers may help for some cases.

#### Production angle

In production, inspect all consumers: application versions, analytics, reports, ETL, ad hoc scripts, stored procedures.

Column rename is often more dangerous than it looks.

#### Traps / caveats

- Rolling deployments mean old and new code coexist.
- Direct rename is a breaking change.
- Dual-write requires reconciliation.
- Do not forget external consumers.

#### Optional Anki

Q: Safe column rename pattern?
A: Add new column, migrate usage, drop old column later.

</details>

<a id="mig-core-012"></a>

<details>
<summary><strong>MIG-CORE-012. How would you change a column type safely?</strong></summary>

#### Short answer

Add a new column with the new type, dual-write/backfill, switch reads, then remove the old column later.

#### Interview answer

Direct `ALTER COLUMN TYPE` can rewrite a table, lock writes, fail on bad data, or break old application versions.

The safer pattern is expand-and-contract.

#### Deep dive

For small tables or metadata-only compatible changes, direct type change might be acceptable. For huge hot tables, avoid large blocking rewrites.

Backfill conversion should be validated with edge cases.

#### Production angle

Production plan: add new column, update app to write both, backfill in batches, compare old/new values, switch reads, stop old writes, drop old later.

Keep rollback points between steps.

#### Traps / caveats

- Type conversion can lose data.
- Indexes and constraints may need changes too.
- ORM mappings must change in sync.
- Old consumers may still expect old type.

#### Optional Anki

Q: Safe large column type change?
A: New column, dual-write, backfill/validate, switch, drop old later.

</details>

<a id="mig-core-013"></a>

<details>
<summary><strong>MIG-CORE-013. How would you drop a column safely?</strong></summary>

#### Short answer

Stop all application reads and writes of the old column first, verify no consumers use it, then drop it in a later release.

#### Interview answer

Dropping a column is destructive and breaks old code immediately. It should be the final contract step, not the first migration.

Before dropping, search code, reports, ETL jobs, dashboards, stored procedures, and ad hoc integrations.

#### Deep dive

A common safe pattern is: stop using column in code, deploy, monitor, optionally rename to mark deprecated or revoke access, then drop after confidence window.

Backups do not replace a rollback plan.

#### Production angle

In production, watch query logs or dependency tracking to ensure no usage. Coordinate with BI/data teams.

Schedule drop during safe window if the table is huge or hot.

#### Traps / caveats

- Drop is not backward-compatible.
- Rollback may require restoring data from backup.
- External consumers are easy to miss.
- ORM generated SQL may still include the column.

#### Optional Anki

Q: When should you drop old column?
A: Only after all consumers have stopped using it and compatibility window passed.

</details>

<a id="mig-core-014"></a>

<details>
<summary><strong>🧠 MIG-CORE-014. How would you roll back a failed database migration?</strong></summary>

#### Short answer

Rollback depends on migration type: some can be reverted by SQL, but destructive/data migrations often need forward fixes or restore/reconciliation.

#### Interview answer

For simple additive migrations, rollback may mean dropping a newly added column or index. For data changes, rollback may require previous values, audit logs, backups, or compensating migration.

Do not assume down migration is always safe.

#### Deep dive

The safest rollback is often avoiding destructive first steps. Expand-and-contract gives you rollback points before contract/destructive stage.

For failed partial migrations, you may need to repair migration metadata carefully.

#### Production angle

In production, document rollback before running migration. Know whether you will roll back code, roll forward database, or restore data.

Practice restore procedures, not just schema rollback.

#### Traps / caveats

- Down migrations can lose new data.
- Failed migrations can leave locks or invalid objects.
- Code rollback may not match DB rollback.
- Backups must be tested.

#### Optional Anki

Q: Why rollback can be hard?
A: Data/destructive changes may not be reversible without backups or compensating logic.

</details>

<a id="mig-core-015"></a>

<details>
<summary><strong>MIG-CORE-015. Why are long DDL locks dangerous?</strong></summary>

#### Short answer

Long DDL locks can block application reads/writes and cascade into timeouts, pool exhaustion and outages.

#### Interview answer

DDL often needs table locks to change metadata safely. Even a short metadata lock can be dangerous if it waits behind a long transaction and blocks subsequent queries.

This is a common production migration failure mode.

#### Deep dive

Lock queues matter: a DDL waiting for an exclusive lock can block later compatible queries behind it, causing a traffic pile-up.

Use lock_timeout so migrations fail instead of waiting indefinitely.

#### Production angle

In production, check active transactions before DDL, use short lock timeouts, schedule risky changes, and monitor blocked sessions.

Use online/concurrent variants when available. A useful diagnostic path is `pg_stat_activity` + `pg_locks` + `pg_blocking_pids(pid)`, with query age and transaction age visible.

#### Traps / caveats

- A migration can block even before it acquires the lock.
- Idle-in-transaction sessions can block DDL.
- DDL lock waits can exhaust app threads.
- Killing blockers needs careful judgement.

#### Optional Anki

Q: Why use lock_timeout for migrations?
A: To fail fast instead of waiting and blocking production traffic.

</details>

<details>
<summary><strong>MIG-CORE-016. How do you deploy application code and database migrations safely together?</strong></summary>

#### Short answer

Use compatibility-first sequencing: apply backward-compatible DB changes, deploy code, backfill/switch, then remove old schema later.

#### Interview answer

The database is shared state. During rolling deployments, old and new app versions can run simultaneously, so migrations must support both.

Do not deploy code that requires a destructive DB change before all old instances are gone.

#### Deep dive

Safe sequence: expand schema; deploy code that can use old/new; backfill; switch reads/writes with feature flag; verify; contract old schema.

Automate migrations but separate risky ones from normal app startup.

#### Production angle

In production, include observability, rollback points, migration ownership, and communication with DB/ops teams.

CI/CD should make it hard to run destructive migrations accidentally.

#### Traps / caveats

- Rolling deploys require backward compatibility.
- Running heavy migrations on every app startup is risky.
- Feature flags do not replace data validation.
- Old services and background jobs also matter.

#### Optional Anki

Q: Safe DB/app deployment pattern?
A: Expand → deploy compatible code → backfill/switch → contract later.

</details>
