# PostgreSQL index migration safety

---

<a id="mig-idx-002"></a>

<details>
<summary><strong>MIG-IDX-002. What does `CREATE INDEX CONCURRENTLY` change in PostgreSQL?</strong></summary>

#### Short answer

It builds an index without blocking normal reads and writes for most of the operation, at the cost of more time and restrictions.

#### Interview answer

Regular `CREATE INDEX` can block writes while building the index. `CREATE INDEX CONCURRENTLY` uses a multi-phase process so application traffic can mostly continue, which makes it safer for large hot tables.

#### Deep dive

Concurrent index creation still takes locks at certain phases and must scan the table more than once. It cannot run inside a transaction block.

#### Production angle

Use it for large production tables, run it separately from transactional migration batches, and monitor progress, IO, locks, replication lag and disk usage.

#### Traps / caveats

- It is slower than regular index creation.
- It can still fail and leave invalid indexes.
- It cannot run inside a transaction block.
- It can still add heavy IO and CPU load.

#### Optional Anki

Q: Why use `CREATE INDEX CONCURRENTLY`?
A: To avoid blocking normal writes during index build on hot tables.

</details>

<a id="mig-idx-003"></a>

<details>
<summary><strong>MIG-IDX-003. Why can adding an index still hurt production even when it is concurrent?</strong></summary>

#### Short answer

Because it still consumes CPU, IO, memory, disk and replication capacity, and later adds write overhead.

#### Interview answer

Concurrent index creation reduces blocking, but the database still scans data, writes index pages and generates WAL. On a busy system, that can increase latency or replication lag.

After creation, every relevant insert, update or delete must maintain the index.

#### Deep dive

The index might also not be used by the planner, or it may duplicate an existing index. Adding indexes blindly can slow writes and increase storage without improving reads.

#### Production angle

Schedule carefully, monitor load, validate usefulness with real plans, and remove redundant indexes when safe.

#### Traps / caveats

- "Concurrent" does not mean "free."
- More indexes can hurt write-heavy services.
- Index builds can affect replicas and backups.
- An unused index is still maintained.

#### Optional Anki

Q: Main cost of an index after creation?
A: Extra storage and write maintenance overhead.

</details>

<details>
<summary><strong>MIG-IDX-004. How do you verify that a new index is actually useful?</strong></summary>

#### Short answer

Compare real query plans and metrics before and after, using representative parameters and data.

#### Interview answer

I would identify the target query, run `EXPLAIN (ANALYZE, BUFFERS)` on representative data, compare latency and rows read, then monitor production metrics after rollout.

#### Deep dive

Useful indexes should match actual predicates, sort order, joins and selectivity. For skewed data, test multiple parameter values because one tenant or status can behave very differently from another.

#### Production angle

Use `pg_stat_statements`, application traces and index usage stats. Keep enough time to observe real traffic before removing fallback options.

#### Traps / caveats

- Planner may ignore the index.
- Dev data can make a bad index look good.
- One query can improve while writes get slower.
- `idx_scan = 0` needs context before dropping an index.

#### Optional Anki

Q: Best evidence that an index helped?
A: Better real query plans and production latency/load metrics.

</details>

<a id="mig-idx-005"></a>

<details>
<summary><strong>MIG-IDX-005. How do you remove an unused index safely?</strong></summary>

#### Short answer

Confirm it is truly unused, check constraints/dependencies, then drop it in a controlled deployment.

#### Interview answer

I would inspect usage stats, query patterns, constraints, duplicate indexes and recent traffic windows. If safe, use `DROP INDEX CONCURRENTLY` where appropriate and monitor for plan regressions.

#### Deep dive

An index can be unused in a short stats window but important for monthly jobs, rare customer flows, incident queries or foreign-key related operations.

#### Production angle

Drop indexes one at a time for important tables. Keep rollback instructions ready, usually recreating the index concurrently.

#### Traps / caveats

- Unique indexes may enforce business invariants.
- Stats can reset after restart.
- Rare queries may not appear in the observation window.
- Dropping an index can change plans unexpectedly.

#### Optional Anki

Q: Why not drop every index with low usage immediately?
A: It may support constraints, rare queries or important operational paths.

</details>

<a id="mig-idx-009"></a>

<details>
<summary><strong>🧠 MIG-IDX-009. What can happen if `CREATE INDEX CONCURRENTLY` fails partway through?</strong></summary>

#### Short answer

It can leave an invalid index that takes space and may still add overhead until cleaned up.

#### Interview answer

Concurrent index creation has multiple phases. If it fails, PostgreSQL may leave an invalid index entry. That index is not usable for queries, but it can consume disk and may need explicit cleanup before retrying.

#### Deep dive

Common causes include duplicate data for unique indexes, canceled statements, deadlocks, lock timeout, disk exhaustion or operational interruption.

#### Production angle

After failure, inspect catalog state, drop invalid indexes safely, fix the root cause, and retry during a controlled window.

#### Traps / caveats

- A failed unique index may indicate real duplicate data.
- Retrying blindly can fail again.
- Invalid indexes can confuse operators during incidents.
- Cleanup itself should use safe locking behavior.

#### Optional Anki

Q: What may remain after failed `CREATE INDEX CONCURRENTLY`?
A: An invalid index that needs cleanup.

</details>

<a id="mig-idx-010"></a>

<details>
<summary><strong>🧠 MIG-IDX-010. Why can concurrent index creation conflict with migration tools that wrap migrations in a transaction?</strong></summary>

#### Short answer

Because PostgreSQL does not allow `CREATE INDEX CONCURRENTLY` inside a transaction block.

#### Interview answer

Many migration tools default to wrapping migration scripts in a transaction. That is useful for atomicity, but `CREATE INDEX CONCURRENTLY` must run outside such a transaction, so the tool needs special configuration or a separate migration step.

#### Deep dive

Flyway and Liquibase can be configured for non-transactional migrations, but teams must know the mechanism and review it carefully.

#### Production angle

Document this as a migration convention. Do not discover it during deployment to production.

#### Traps / caveats

- Disabling transactions for a file changes failure behavior.
- Non-transactional migrations need explicit cleanup plans.
- This is PostgreSQL-specific behavior.
- Some tools split statements in ways that matter.

#### Optional Anki

Q: Why configure migration tooling for `CREATE INDEX CONCURRENTLY`?
A: It cannot run inside a transaction block.

</details>
