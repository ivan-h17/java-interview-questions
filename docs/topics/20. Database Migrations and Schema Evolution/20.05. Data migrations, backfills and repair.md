# Data migrations, backfills and repair

---

<a id="mig-data-001"></a>

<details>
<summary><strong>MIG-DATA-001. What is a backfill, and why can it be risky?</strong></summary>

#### Short answer

A backfill populates or corrects existing rows, and it is risky because it can touch large amounts of production data.

#### Interview answer

Backfills are used after adding a new column, changing derived data, repairing old records or building a new read model. The risk is load, locks, WAL/binlog growth, replication lag, bad transformations and hard rollback.

#### Deep dive

A backfill is not just an `UPDATE`. It is a production job with batching, idempotency, progress tracking, throttling, validation and a repair plan.

#### Production angle

Run backfills with metrics: rows processed, rows remaining, error count, DB load, lock waits, replication lag and old/new value mismatch.

#### Traps / caveats

- A single huge transaction can create long rollback and bloat.
- A wrong transformation can corrupt real business data.
- Backfills can starve normal application traffic.
- Read paths must handle partially backfilled state.

#### Optional Anki

Q: Why are backfills risky?
A: They touch existing production data and can create load, locks, lag or bad data.

</details>

<details>
<summary><strong>MIG-DATA-003. How do you design a batched, idempotent and resumable backfill?</strong></summary>

#### Short answer

Process small chunks, make each chunk safe to repeat, store progress, and throttle based on production signals.

#### Interview answer

I would select a deterministic batch, update only rows that still need work, commit, record progress, and continue. If the job stops, it should resume without corrupting or duplicating effects.

#### Deep dive

Common patterns include primary-key ranges, cursor tables, status columns, `updated_at` checkpoints or worker queues with `SKIP LOCKED`. The update should be idempotent, for example `WHERE new_col IS NULL` or recomputing from authoritative source data.

#### Production angle

Throttle based on latency, lock waits, replication lag, CPU/IO and error rate. Add dry-run and validation modes when possible.

#### Traps / caveats

- Offset pagination can skip or repeat rows under writes.
- Chunk size must be tuned; too big hurts locks, too small wastes overhead.
- Progress markers can be wrong if sort keys are mutable.
- Retrying non-idempotent writes can corrupt data.

#### Optional Anki

Q: Three properties of a safe backfill?
A: Batched, idempotent and resumable.

</details>

<details>
<summary><strong>MIG-DATA-007. How do you validate that a data migration produced correct results?</strong></summary>

#### Short answer

Compare expected and actual data with targeted queries, counts, checksums, samples and business invariants.

#### Interview answer

Validation should be planned before the migration. I would check row counts, null counts, mismatch counts between old and new representation, referential integrity, constraints and representative business cases.

#### Deep dive

For large datasets, full comparison may be expensive. Use aggregates, checksums by partition/range, sampled audits and focused checks for edge cases.

#### Production angle

Expose validation metrics during rollout. Do not switch reads or drop old data until validation is clean or discrepancies are understood.

#### Traps / caveats

- Successful SQL execution does not prove business correctness.
- Sampling alone can miss rare but important cases.
- Validation must handle concurrent writes.
- Time zones, rounding and normalization differences can create subtle mismatches.

#### Optional Anki

Q: What should a data migration validate besides row count?
A: Business invariants and old/new value consistency.

</details>

<a id="mig-data-008"></a>

<details>
<summary><strong>MIG-DATA-008. When should a data migration be implemented in application code instead of SQL?</strong></summary>

#### Short answer

Use application code when transformation needs domain logic, external services, complex validation or operational control that SQL does not express well.

#### Interview answer

SQL is good for set-based updates close to the data. Application code is better when logic uses Java domain rules, needs retries, rate limiting, observability, feature flags, external calls or complex per-row handling.

#### Deep dive

Application-code migrations can reuse tested services, but they may be slower and must avoid holding long transactions. SQL migrations are concise but can be opaque and dangerous at scale if unbounded.

#### Production angle

For Java services, a migration worker should use separate transaction boundaries, bounded batches, connection-pool limits and clear metrics.

#### Traps / caveats

- Do not call slow external systems inside one DB transaction.
- Reusing application services can trigger side effects unintentionally.
- ORM entity loading can be too slow or memory-heavy for millions of rows.
- SQL and app code must use the same business semantics.

#### Optional Anki

Q: When choose app-code backfill?
A: When domain logic, retries, observability or complex per-row handling matter.

</details>

<details>
<summary><strong>🧠 MIG-DATA-009. How do replication lag, WAL volume or binlog volume affect large backfills?</strong></summary>

#### Short answer

Large backfills generate write-ahead/change logs and can make replicas fall behind or disks fill.

#### Interview answer

Every update must be logged for durability and replication. A high-volume backfill can increase WAL/binlog generation, saturate IO, delay replicas, and make read replicas serve stale data.

#### Deep dive

Lag can break read-after-write expectations, delay failover readiness, and affect downstream CDC consumers. If replication slots retain WAL while a consumer lags, disk usage can grow dangerously.

#### Production angle

Throttle based on replica lag and WAL/binlog growth. Coordinate with CDC pipelines, backups and reporting workloads.

#### Traps / caveats

- A backfill can look fine on primary while replicas fall behind.
- Read traffic routed to replicas may see mixed old/new data.
- WAL retention can fill disks if slots are stuck.
- Rollback of a huge transaction can also generate heavy load.

#### Optional Anki

Q: Why monitor replicas during backfill?
A: Backfills generate logs and can cause replication lag or WAL/binlog retention.

</details>

<a id="mig-data-010"></a>

<details>
<summary><strong>🧠 MIG-DATA-010. How do you design a repair plan if a backfill writes bad data?</strong></summary>

#### Short answer

Keep enough evidence to identify affected rows, stop further damage, restore or recompute correct values, and validate the repair.

#### Interview answer

Before a risky backfill, define how to detect bad writes and how to recover. Options include saving old values, using audit tables, keeping old columns during migration, restoring from backup, or recomputing from an authoritative source.

#### Deep dive

A good repair plan includes blast-radius detection, rollback or roll-forward choice, idempotent repair jobs, validation queries and communication. For critical data, dry runs and shadow comparisons reduce risk.

#### Production angle

If bad data is detected, pause the job, prevent consumers from relying on corrupted data if possible, estimate affected rows and run repair under review.

#### Traps / caveats

- Dropping old columns too early removes the easiest repair source.
- Backups may be too slow or too broad for targeted repair.
- Repair jobs can create new load and new mistakes.
- Audit logs must contain enough data to reconstruct values.

#### Optional Anki

Q: Best repair source during a schema transition?
A: The old authoritative representation kept until validation passes.

</details>
