# Safe schema changes, constraints and lock behavior

---

<a id="mig-schema-003"></a>

<details>
<summary><strong>MIG-SCHEMA-003. How do you add a default value without causing unexpected production impact?</strong></summary>

#### Short answer

Check database version and table size, then prefer a phased change if the default may rewrite or lock a large table.

#### Interview answer

Adding a column default can be cheap in modern PostgreSQL for constant defaults, but not every default or database behaves the same. For a large hot table, I would verify lock and rewrite behavior before applying it.

#### Deep dive

Safe options include adding the nullable column first, deploying code that supplies the value, backfilling old rows, then adding the default or constraint later.

Expression defaults, type changes and older database versions can be more expensive.

#### Production angle

Test on production-like data, set `lock_timeout`, monitor locks and replication lag, and avoid assuming local timing predicts production timing.

#### Traps / caveats

- Constant defaults and volatile expression defaults may behave differently.
- Defaults affect future rows, not necessarily old rows in the way the application expects.
- ORM mappings may assume non-null before old rows are backfilled.
- A metadata-only change can still wait behind locks.

#### Optional Anki

Q: Safe approach for a risky default on a huge table?
A: Add nullable column, backfill, then add default/constraint later.

</details>

<details>
<summary><strong>MIG-SCHEMA-006. How do you split or merge columns safely?</strong></summary>

#### Short answer

Use expand-and-contract with temporary dual-read/write logic and validation.

#### Interview answer

For a split, add the new columns, write old and new formats, backfill from old to new, validate, switch reads, then remove old later. For a merge, add the merged column, populate it from the old columns, dual-write, validate, then contract.

#### Deep dive

The hard part is preserving meaning. Splitting `full_name` into `first_name` and `last_name` may be lossy. Merging fields may hide validation or normalization differences.

#### Production angle

Use metrics for mismatch count, fallback-read count and rows remaining. Keep rollback possible until the old representation is no longer needed.

#### Traps / caveats

- Data transformation may be lossy.
- Existing bad data can break assumptions.
- Old app versions may keep writing the old columns.
- API contracts may need to evolve with the schema.

#### Optional Anki

Q: Safe pattern for splitting a column?
A: Add new columns, dual-write/backfill, switch reads, then drop old later.

</details>

<a id="mig-schema-009"></a>

<details>
<summary><strong>MIG-SCHEMA-009. How do you change enum-like values safely in a database-backed application?</strong></summary>

#### Short answer

Add support for new and old values first, migrate data carefully, then remove old values after all code is compatible.

#### Interview answer

Enum-like values appear in database constraints, Java enums, validation, API contracts, reporting and message schemas. I would deploy code that can read both old and new values before writing the new value.

#### Deep dive

If the database uses a PostgreSQL enum type, changing it has database-specific constraints. If it uses a text column with a check constraint, the constraint must be evolved safely.

For Java, avoid ordinal enum persistence; string values are safer but still require compatibility.

#### Production angle

Check all producers and consumers: services, batch jobs, analytics, Kafka consumers, API clients and dashboards.

#### Traps / caveats

- `EnumType.ORDINAL` can corrupt meaning when enum order changes.
- Old services may reject unknown new values.
- Removing a value before data is migrated can break reads.
- Constraints, code and docs must agree.

#### Optional Anki

Q: Safe enum-value migration principle?
A: Readers accept old and new values before writers produce the new value.

</details>

<a id="mig-schema-010"></a>

<details>
<summary><strong>MIG-SCHEMA-010. How do you make a nullable column non-null after a backfill?</strong></summary>

#### Short answer

Backfill and validate first, then enforce non-null in a separate controlled step.

#### Interview answer

First make sure all writers populate the column. Then backfill old rows in batches. Validate no `NULL` remains. Finally add the constraint with attention to locking and table validation behavior.

#### Deep dive

In PostgreSQL, one pattern is to add a `CHECK (col IS NOT NULL) NOT VALID`, validate it later, then set `NOT NULL` when appropriate. Exact mechanics depend on version and table size.

#### Production angle

Run validation queries, set lock timeout, watch for long transactions and coordinate with application rollout so no old code writes `NULL`.

#### Traps / caveats

- Backfill completion is not enough if old code can still write `NULL`.
- Validation can scan a large table.
- ORM `nullable = false` does not enforce existing database data.
- Direct `ALTER COLUMN SET NOT NULL` may be risky on huge hot tables.

#### Optional Anki

Q: Steps to make a nullable column non-null?
A: Ensure writers, backfill, validate, then enforce constraint.

</details>

<details>
<summary><strong>🧠 MIG-SCHEMA-011. What schema changes commonly rewrite or scan a large table?</strong></summary>

#### Short answer

Type changes, some defaults, constraint validation, column rewrites and large updates can scan or rewrite large tables.

#### Interview answer

Risky changes include `ALTER COLUMN TYPE`, adding some non-constant defaults, setting `NOT NULL`, validating constraints, rewriting data with `UPDATE`, and operations that require stronger table locks.

#### Deep dive

The exact behavior depends on database and version. PostgreSQL has optimized some cases over time, but a senior engineer should verify the actual operation rather than relying on memory.

#### Production angle

Check documentation for the target DB version, rehearse on production-like data, measure lock duration and watch WAL, IO, replication lag and autovacuum impact.

#### Traps / caveats

- A fast metadata change can still block behind existing transactions.
- "No rewrite" does not mean "no lock."
- Data size matters more than syntax length.
- Version-specific behavior should be verified.

#### Optional Anki

Q: Why verify large-table DDL behavior?
A: Some schema changes scan/rewrite tables or require locks depending on DB/version.

</details>

<a id="mig-schema-012"></a>

<details>
<summary><strong>🧠 MIG-SCHEMA-012. How do lock timeouts and statement timeouts reduce migration blast radius?</strong></summary>

#### Short answer

They make risky migration steps fail fast instead of waiting indefinitely or running too long.

#### Interview answer

`lock_timeout` limits how long a statement waits to acquire a lock. `statement_timeout` limits statement execution time. For migrations, these prevent a DDL command from joining a lock queue and causing wider application impact.

#### Deep dive

A waiting DDL can block later queries behind it if it needs a strong lock. A timeout lets the deployment stop and retry later instead of creating a production pile-up.

#### Production angle

Use timeouts per migration step, not as a substitute for understanding lock behavior. Monitor failures and retry during safer conditions.

#### Traps / caveats

- Too-short timeouts can make safe migrations flaky.
- A timed-out statement may still require cleanup depending on operation.
- Application timeouts and DB timeouts must be coordinated.
- Timeouts reduce blast radius; they do not make bad SQL good.

#### Optional Anki

Q: `lock_timeout` vs `statement_timeout`?
A: Lock wait time vs total statement execution time.

</details>

<a id="mig-idx-006"></a>

<details>
<summary><strong>MIG-IDX-006. How do you add a unique constraint safely when existing duplicate data may exist?</strong></summary>

#### Short answer

Detect and clean duplicates first, then add uniqueness with a phased, monitored migration.

#### Interview answer

Before adding a unique constraint, run duplicate detection queries for the exact key and semantics. Decide how to merge, delete or repair duplicates. Then add the unique constraint or unique index safely.

#### Deep dive

For large tables, creating the supporting unique index concurrently may reduce write blocking, but duplicate rows can make the operation fail. After cleanup, prevent new duplicates before or during the rollout.

#### Production angle

Coordinate with application logic: validation is not enough under concurrency. Use database uniqueness to enforce the invariant.

#### Traps / caveats

- `NULL` uniqueness semantics matter.
- Case-insensitive uniqueness may need normalized values or expression indexes.
- Concurrent writes can create new duplicates during cleanup.
- Failed unique index creation may leave cleanup work.

#### Optional Anki

Q: First step before adding a unique constraint to dirty data?
A: Detect and repair existing duplicates.

</details>

<details>
<summary><strong>MIG-IDX-007. How do you add a foreign key constraint safely to a large table?</strong></summary>

#### Short answer

Verify data first, ensure supporting indexes, then add and validate the constraint carefully.

#### Interview answer

I would check for orphan rows, add needed indexes, add the foreign key in a way that minimizes blocking, and validate it separately if the database supports that workflow.

#### Deep dive

In PostgreSQL, `NOT VALID` can let you add a constraint without immediately validating all existing rows, then `VALIDATE CONSTRAINT` later. New rows are checked while old rows are validated separately.

#### Production angle

Foreign keys improve correctness but add checks on writes and can affect deletes/updates. Monitor lock waits, write latency and query plans.

#### Traps / caveats

- Missing index on child or parent paths can hurt performance.
- Existing orphan data makes validation fail.
- Cascading deletes can surprise application behavior.
- Adding constraints changes write-path cost.

#### Optional Anki

Q: Safe PostgreSQL FK rollout keyword?
A: Add `NOT VALID`, then validate later when appropriate.

</details>
