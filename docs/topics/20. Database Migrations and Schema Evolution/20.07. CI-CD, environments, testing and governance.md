# CI-CD, environments, testing and governance

---

<a id="mig-ci-001"></a>

<details>
<summary><strong>MIG-CI-001. How should migrations be tested before production?</strong></summary>

#### Short answer

Run them from a clean schema and against a realistic existing schema with representative data.

#### Interview answer

CI should test that migrations apply in order, create the expected schema, and remain compatible with application code. For risky migrations, also test upgrade from a production-like snapshot or anonymized data.

#### Deep dive

Useful checks include migration tool validation, application startup, repository tests, constraint checks, rollback/repair plan review and performance rehearsal for large operations.

#### Production angle

Testing should answer: will it apply, how long can it take, what locks might it need, and will old/new app versions still work?

#### Traps / caveats

- Testing only on empty DB misses data problems.
- H2 can hide PostgreSQL-specific behavior.
- Small test data hides lock, rewrite and plan risks.
- CI success does not replace production rollout monitoring.

#### Optional Anki

Q: Two migration test modes?
A: From clean schema and from existing production-like schema/data.

</details>

<a id="mig-ci-002"></a>

<details>
<summary><strong>MIG-CI-002. Why should migrations be tested on production-like data volume?</strong></summary>

#### Short answer

Because lock duration, execution time, query plans and WAL/IO impact depend heavily on data size and distribution.

#### Interview answer

A migration that runs instantly on a small test database can take minutes or hours on production data. It can also scan tables, generate huge WAL, create replica lag or fail because real data violates new constraints.

#### Deep dive

Production-like data reveals duplicate keys, bad enum values, orphan rows, skewed distributions, long indexes and table bloat.

#### Production angle

For high-risk changes, rehearse on a restored or anonymized snapshot and record expected duration, lock behavior and resource usage.

#### Traps / caveats

- Row count alone is not enough; distribution matters.
- Staging hardware may differ from production.
- Anonymization can change data distribution.
- Rehearsal results should guide timeout and rollout planning.

#### Optional Anki

Q: Why test migrations with production-like volume?
A: To expose duration, locks, data violations and resource impact.

</details>

<a id="mig-ci-003"></a>

<details>
<summary><strong>MIG-CI-003. What should code review check in a database migration?</strong></summary>

#### Short answer

Correctness, compatibility, lock behavior, data volume impact, rollback/repair plan and observability.

#### Interview answer

A reviewer should ask whether the migration is backward-compatible, safe for rolling deployment, bounded in time, tested on realistic data, and coordinated with application changes.

#### Deep dive

Review SQL for table rewrites, unbounded updates, missing indexes, constraint validation, destructive changes, transaction behavior, idempotency and expected failure modes.

#### Production angle

The review should produce an operational plan: when to run, who owns it, what to monitor, and what to do if it fails.

#### Traps / caveats

- Reviewing syntax is not enough.
- Data migrations need business validation.
- Migration tool settings matter.
- Permissions and secrets should not be embedded in migration scripts.

#### Optional Anki

Q: Migration review dimensions?
A: Correctness, compatibility, operational impact and recovery.

</details>

<a id="mig-ci-005"></a>

<details>
<summary><strong>MIG-CI-005. How do you prevent schema drift between local, test, staging and production?</strong></summary>

#### Short answer

Make migrations the only normal path for schema changes and validate migration state in every environment.

#### Interview answer

Use the same migration tool and migration files everywhere. Avoid manual changes, rebuild environments from migrations, and check migration history during CI/CD and startup where appropriate.

#### Deep dive

Drift detection can include migration checksum validation, schema diff tools, database object audits and comparing expected permissions/extensions.

#### Production angle

When drift is found, treat it as a production risk. Fix through reviewed migrations or controlled repair, not ad hoc changes.

#### Traps / caveats

- Local developer shortcuts can leak into shared environments.
- Production hotfixes must be captured afterward.
- Permissions, indexes and extensions can drift too.
- Test containers should use the same database family as production.

#### Optional Anki

Q: Main schema drift prevention rule?
A: Apply schema changes through versioned migrations only.

</details>

<a id="mig-ci-006"></a>

<details>
<summary><strong>MIG-CI-006. How should JPA mappings and migrations be kept consistent?</strong></summary>

#### Short answer

Treat migrations as the source of production schema changes and verify that JPA mappings match them.

#### Interview answer

When changing an entity, add the corresponding migration and test the mapping against the real database. JPA annotations describe how Java maps to the schema; they should not silently create or mutate production schema.

#### Deep dive

Consistency checks include application startup validation, repository integration tests, Testcontainers, migration tests and review of column names, nullability, lengths, indexes, constraints and enum mappings.

#### Production angle

During rolling deployments, entity code must remain compatible with the intermediate schema states created by migrations.

#### Traps / caveats

- `nullable = false` is not the same as a database `NOT NULL`.
- Hibernate naming strategies can change expected names.
- Enum and ID generation mappings can break data compatibility.
- H2 tests can pass while PostgreSQL fails.

#### Optional Anki

Q: Who should own production schema, JPA or migrations?
A: Versioned migrations should own production schema changes.

</details>

<a id="mig-ci-007"></a>

<details>
<summary><strong>MIG-CI-007. Why should Hibernate `ddl-auto=update` not own production schema changes?</strong></summary>

#### Short answer

Because it is implicit, hard to review, limited in safety and not designed for controlled production evolution.

#### Interview answer

`ddl-auto=update` can change schema at startup based on entity mappings. That is convenient locally, but in production it bypasses migration review, compatibility planning and operational controls.

#### Deep dive

It cannot safely handle many real changes: renames, data migrations, phased rollouts, backfills, constraint validation, online index creation and destructive changes with business context.

#### Production angle

Use `validate` or explicit startup checks in production, and let Flyway/Liquibase or the deployment pipeline apply reviewed migrations.

#### Traps / caveats

- Entity mappings do not capture all database constraints and indexes.
- Startup schema mutation can delay or break deployments.
- Automatic updates can differ across environments.
- It gives false confidence that schema evolution is solved.

#### Optional Anki

Q: Recommended production role of Hibernate schema tooling?
A: Validate schema, not own schema changes.

</details>

<a id="mig-ci-008"></a>

<details>
<summary><strong>MIG-CI-008. How can CI detect missing or broken migrations?</strong></summary>

#### Short answer

Build the schema from migrations, run validation, start the app and execute integration tests against the target database.

#### Interview answer

CI should fail if migration files are invalid, out of order, checksum-broken, incompatible with JPA mappings, or unable to create the schema expected by tests.

#### Deep dive

Useful checks: apply migrations from scratch, apply migrations over previous release schema, run migration tool validation, run repository tests with Testcontainers, and verify generated SQL uses existing objects.

#### Production angle

For critical releases, CI can also require migration review labels, rollback notes and production-readiness checklist completion.

#### Traps / caveats

- From-scratch migration tests miss upgrade problems on dirty existing data.
- Mocked repositories do not test schema compatibility.
- Tests should use PostgreSQL if production is PostgreSQL.
- CI cannot prove runtime lock safety without realistic scale.

#### Optional Anki

Q: CI migration baseline test?
A: Apply all migrations and start/test the app against the resulting schema.

</details>

<a id="mig-ci-010"></a>

<details>
<summary><strong>🧠 MIG-CI-010. What should a migration readiness checklist include before a risky release?</strong></summary>

#### Short answer

Scope, compatibility, data volume, lock behavior, monitoring, owner, rollback/repair plan and communication.

#### Interview answer

Before a risky migration, I want to know exactly what changes, which code versions are compatible, expected runtime, lock behavior, backfill strategy, validation plan, metrics, alerting and who can make decisions during rollout.

#### Deep dive

The checklist should include dry-run results, production-like rehearsal, timeouts, maintenance window decision, replica/CDC impact, rollback versus roll-forward criteria and post-deployment verification.

#### Production angle

During rollout, the team should have a runbook: start, monitor, pause, cancel, repair, communicate and verify.

#### Traps / caveats

- A checklist without an owner is weak.
- Rollback can be impossible after destructive data changes.
- Communication matters when customer-facing latency or feature freezes are possible.
- Include background jobs, replicas and downstream consumers.

#### Optional Anki

Q: Risky migration checklist themes?
A: Compatibility, scale, observability, ownership and recovery.

</details>
