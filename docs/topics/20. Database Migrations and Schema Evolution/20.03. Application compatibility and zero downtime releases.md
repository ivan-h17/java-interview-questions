# Application compatibility and zero-downtime releases

---

<a id="mig-zd-002"></a>

<details>
<summary><strong>MIG-ZD-002. Why do rolling deployments make schema changes harder?</strong></summary>

#### Short answer

Because old and new application versions may run at the same time against one database.

#### Interview answer

During a rolling deployment, some instances may still use the old schema contract while others use the new one. A migration that drops, renames or changes a column too early can break old instances immediately.

#### Deep dive

The database is shared state. Schema evolution must support a period where multiple application versions, background jobs and consumers coexist.

That is why additive changes are safer than destructive changes in the first step.

#### Production angle

Plan migrations as multiple releases: expand schema, deploy compatible code, migrate data, switch behavior, then contract old schema after old code is gone.

#### Traps / caveats

- Background workers also need compatibility.
- Read replicas and reporting jobs may depend on old schema.
- Rollback means old code may return after new schema exists.
- Feature flags do not fix incompatible schema by themselves.

#### Optional Anki

Q: Why are rolling deployments hard for DB changes?
A: Old and new app versions share one database during rollout.

</details>

<a id="mig-zd-003"></a>

<details>
<summary><strong>MIG-ZD-003. How do you keep old and new application versions compatible with one schema?</strong></summary>

#### Short answer

Use backward-compatible schema changes and code that can tolerate both old and new states during the transition.

#### Interview answer

Add new columns or tables before using them. Deploy code that can read/write both shapes if needed. Backfill data. Switch reads or writes safely. Only then remove old schema in a later deployment.

#### Deep dive

Compatibility often requires temporary code: nullable reads, dual writes, fallback reads, feature flags, and validation jobs. The goal is to make every intermediate state valid.

#### Production angle

Track which versions are deployed, which write path is active, how much data is backfilled, and when it is safe to contract.

#### Traps / caveats

- Code rollback must be compatible with the current schema.
- Old API clients may still rely on old behavior.
- Avoid making a column mandatory before all writers populate it.
- Remove temporary compatibility code after the migration completes.

#### Optional Anki

Q: Safe schema evolution pattern for compatibility?
A: Expand, deploy compatible code, backfill/switch, then contract later.

</details>

<a id="mig-zd-004"></a>

<details>
<summary><strong>MIG-ZD-004. How do feature flags help during schema evolution?</strong></summary>

#### Short answer

They let you separate deployment from behavior activation.

#### Interview answer

A feature flag can keep new reads or writes disabled until the schema exists and the backfill is ready. It can also switch traffic gradually and provide a fast rollback of behavior without reverting code immediately.

#### Deep dive

Feature flags are useful for read-path switches, dual-write activation, new query paths and gradual rollout by tenant or percentage. They do not make a destructive schema change safe by themselves.

#### Production angle

Use flags with metrics: error rate, old/new value mismatch, backfill progress, query latency and database load.

#### Traps / caveats

- Flag state must be included in rollback planning.
- Dual-write flags can create inconsistent partial states.
- Long-lived flags become technical debt.
- Flags do not replace migration ordering.

#### Optional Anki

Q: What do feature flags separate in schema rollout?
A: Code deployment from behavior activation.

</details>

<a id="mig-zd-005"></a>

<details>
<summary><strong>MIG-ZD-005. What are backward-compatible and forward-compatible schema changes?</strong></summary>

#### Short answer

Backward-compatible changes do not break old code; forward-compatible code can run before or after a related schema change.

#### Interview answer

Adding a nullable column is usually backward-compatible because old code ignores it. Dropping or renaming a column is not. Forward-compatible code can tolerate the schema not being fully migrated yet, for example by handling `NULL` or falling back to the old column.

#### Deep dive

Safe rollouts often require both: the database change must not break old code, and the new code must tolerate transitional data/schema states.

#### Production angle

Before release, ask: can old code run on the new schema, can new code run if the migration is delayed, and can rollback still work?

#### Traps / caveats

- Adding `NOT NULL` without data can break writes.
- Changing column meaning can be breaking even if the column name stays.
- ORM validation can make otherwise additive changes fail.
- Compatibility must include batch jobs and consumers.

#### Optional Anki

Q: Example backward-compatible schema change?
A: Adding a nullable column that old code ignores.

</details>

<details>
<summary><strong>MIG-ZD-007. How should reads and writes be migrated when a field moves to a new column?</strong></summary>

#### Short answer

Use a phased transition: add new column, write both, backfill, read new with fallback, then stop old usage and drop later.

#### Interview answer

First expand the schema. Then deploy code that can write the old and new columns or derive one from the other. Backfill existing rows. Validate old and new values. Switch reads to the new column. Contract later.

#### Deep dive

The exact order depends on whether the old or new representation is authoritative during the transition. For risky changes, use reconciliation jobs and feature flags.

#### Production angle

Monitor mismatch count, write failures, backfill progress, query plans and latency. Keep a rollback point before dropping the old column.

#### Traps / caveats

- Dual writes can fail halfway.
- Fallback reads can hide incomplete migration forever.
- Old code may overwrite the old column only.
- Time zones, formats and normalization rules can corrupt migrated data.

#### Optional Anki

Q: Safe move-field sequence?
A: Add new field, dual-write/backfill, switch reads, then remove old later.

</details>

<a id="mig-zd-008"></a>

<details>
<summary><strong>MIG-ZD-008. How do dual-write and dual-read transitions work?</strong></summary>

#### Short answer

Dual-write writes old and new representations; dual-read can read either during migration.

#### Interview answer

Dual-write keeps both schemas updated while old and new code coexist. Dual-read lets new code read from the new place when present and fall back to the old place while backfill is incomplete.

#### Deep dive

These are temporary compatibility techniques. They need a clear source of truth, validation, monitoring and a removal plan.

#### Production angle

Use metrics to detect divergence: old/new value mismatch, fallback-read count, failed dual writes and remaining rows to migrate.

#### Traps / caveats

- Dual writes are not automatically atomic across systems.
- Fallback reads can mask missed backfills.
- Keeping both paths too long increases complexity.
- Partial failures require repair logic.

#### Optional Anki

Q: What should dual-read expose as a metric?
A: Fallback-read count and old/new value mismatch.

</details>

<a id="mig-zd-010"></a>

<details>
<summary><strong>MIG-ZD-010. Why should destructive schema changes be delayed until old code is gone?</strong></summary>

#### Short answer

Because old code may still read or write the old schema during rollout or rollback.

#### Interview answer

Dropping a column, removing a table, tightening a constraint or changing column meaning can break any app version that still depends on it. In rolling deployments, old code may still be serving requests.

#### Deep dive

The contract phase should happen only after all old application versions, workers and consumers are removed, data is migrated and monitoring proves the old path is unused.

#### Production angle

Before destructive changes, verify deploy state, traffic, background jobs, dashboards, reports and rollback plans.

#### Traps / caveats

- A code rollback may reintroduce old code.
- Analytics jobs can depend on old columns.
- Removing compatibility code before dropping schema can still be risky.
- Backups are not a substitute for compatibility.

#### Optional Anki

Q: When should old columns be dropped?
A: After old code is gone and new path is verified.

</details>

<a id="mig-zd-011"></a>

<details>
<summary><strong>🧠 MIG-ZD-011. What can go wrong with dual writes during partial failures?</strong></summary>

#### Short answer

One representation can be updated while the other is not, creating divergent state.

#### Interview answer

Dual writes inside one database transaction can be safe if both writes commit or roll back together. But if they cross services, queues, external systems or separate transactions, partial failure can leave old and new data inconsistent.

#### Deep dive

Problems include timeout ambiguity, retries writing only one side, old code still writing old columns, and validation jobs racing with live updates.

For cross-system changes, consider outbox, idempotency keys, repair jobs and making one side clearly authoritative.

#### Production angle

Monitor divergence and build reconciliation from the start. Do not switch reads fully until mismatch is understood and bounded.

#### Traps / caveats

- Retrying a failed request can duplicate side effects.
- "Best effort" dual write is usually not enough for critical data.
- Validation must handle concurrent updates.
- Dual writes should have an end date.

#### Optional Anki

Q: Main dual-write failure mode?
A: Partial success leaves old and new representations inconsistent.

</details>
