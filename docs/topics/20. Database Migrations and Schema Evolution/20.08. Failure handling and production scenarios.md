# Failure handling and production scenarios

---

<a id="mig-fail-002"></a>

<details>
<summary><strong>MIG-FAIL-002. When is a down migration unsafe or misleading?</strong></summary>

#### Short answer

When reversing the SQL does not restore the real previous business state.

#### Interview answer

Down migrations are unsafe for destructive changes, data transformations, partial backfills and changes where new writes happened after deployment. Dropping a column can be reversed syntactically by adding it back, but the lost data is not restored.

#### Deep dive

A useful rollback plan may be code rollback, roll-forward fix, backup restore, targeted repair or compatibility mode. The right choice depends on what changed and what data was written after the migration.

#### Production angle

For risky migrations, document recovery before rollout and test restore/repair procedures, not only a `down.sql` file.

#### Traps / caveats

- Down migration can destroy new valid data.
- Some operations are not transactionally reversible.
- Code rollback may be incompatible with the new schema.
- Backups may be too slow for normal incident response.

#### Optional Anki

Q: Why can down migrations be misleading?
A: They may reverse schema syntax but not restore lost or transformed data.

</details>

<details>
<summary><strong>MIG-FAIL-004. What would you do if a migration fails halfway through deployment?</strong></summary>

#### Short answer

Stop, identify actual database state, assess application impact, then choose repair, retry, rollback or roll-forward.

#### Interview answer

First I would not blindly rerun. I would inspect migration history, logs, locks, partial objects, changed rows and app health. Then I would decide the safest next step based on whether the migration was transactional and what already changed.

#### Deep dive

If nothing committed, retry may be safe after fixing the cause. If partial state exists, add a corrective migration or cleanup step. If application code was already deployed, evaluate compatibility and possible rollback.

#### Production angle

Communicate status, freeze related deployments, preserve evidence and keep a clear owner for decisions.

#### Traps / caveats

- Retrying can repeat non-idempotent data changes.
- Migration metadata may not match actual schema state.
- App instances may be running against a half-upgraded schema.
- Cleanup SQL needs review too.

#### Optional Anki

Q: First step after half-failed migration?
A: Inspect actual DB/app state before retrying.

</details>

<a id="mig-fail-005"></a>

<details>
<summary><strong>MIG-FAIL-005. How do you recover from a migration that succeeded in the database but failed in the application deployment?</strong></summary>

#### Short answer

Use compatibility: roll back code if the schema is backward-compatible, or roll forward/fix code if it is not.

#### Interview answer

If the database change was additive and old code can run on it, roll back the application and investigate. If the migration broke old code, you may need to roll forward with a fixed app or add a compatibility migration.

#### Deep dive

This is why migrations should be compatible-first. The database often cannot be rolled back as easily as stateless code, especially after writes have occurred.

#### Production angle

Keep the schema in a state that supports both versions until deployment is stable. Monitor errors, write paths and migration flags.

#### Traps / caveats

- Code rollback can fail if schema was contracted too early.
- New app may have already written data old app cannot understand.
- Do not drop compatibility columns in the same release.
- Roll-forward may be safer than rollback.

#### Optional Anki

Q: Why make DB migrations backward-compatible?
A: So application rollback remains possible after DB migration succeeds.

</details>

<a id="mig-fail-006"></a>

<details>
<summary><strong>MIG-FAIL-006. How do you handle a migration that is safe in staging but slow in production?</strong></summary>

#### Short answer

Pause or cancel if needed, investigate scale differences, then redesign with batching, concurrency-safe DDL or a safer rollout window.

#### Interview answer

I would check table size, data distribution, locks, IO, CPU, replication lag, autovacuum, indexes and hardware differences. If production impact is high, stop the migration if safe and reduce blast radius.

#### Deep dive

Staging may have less data, cleaner data, different indexes, different bloat, no real traffic or weaker replication requirements. A slow migration often means the rehearsal was not representative enough.

#### Production angle

Use smaller batches, off-peak execution, timeouts, progress metrics and production-like dry runs before retrying.

#### Traps / caveats

- Killing a huge transaction can cause long rollback.
- A waiting DDL can block normal traffic behind it.
- Staging success is not proof of production safety.
- Replicas and CDC can be the bottleneck, not primary CPU.

#### Optional Anki

Q: Why can staging miss migration risk?
A: It often lacks production data volume, traffic, bloat and replication load.

</details>

<a id="mig-fail-008"></a>

<details>
<summary><strong>MIG-FAIL-008. What should you check if application and schema versions do not match?</strong></summary>

#### Short answer

Check migration history, deployed app version, compatibility expectations, missing objects and whether rollback or roll-forward is safest.

#### Interview answer

If the app expects a column that does not exist, check whether the migration did not run, ran against the wrong database, failed, or the app was deployed too early. If old code cannot read the new schema, the contract step may have happened too soon.

#### Deep dive

Look at migration history table, deployment logs, active app versions, database connection target, feature flags and startup validation errors.

#### Production angle

Mitigate user impact first: stop rollout, route traffic to healthy version, run missing compatible migration, or roll forward with a fix.

#### Traps / caveats

- The app may connect to the wrong database/schema.
- Multiple services may share the same database contract.
- Rollback can be unsafe after destructive schema changes.
- Background jobs may fail even if HTTP endpoints look healthy.

#### Optional Anki

Q: First evidence for app/schema mismatch?
A: Migration history plus deployed app version and error logs.

</details>

<a id="mig-fail-011"></a>

<details>
<summary><strong>🧠 MIG-FAIL-011. How do you choose between rollback, roll-forward and manual repair after a failed migration?</strong></summary>

#### Short answer

Choose the path with the lowest data-loss and availability risk based on actual state, not on a generic preference.

#### Interview answer

Rollback is good when the change is reversible and no incompatible writes happened. Roll-forward is often better when the database is already partially changed and a small fix can restore service. Manual repair is needed when data or metadata is inconsistent.

#### Deep dive

Decision inputs: what committed, what app versions are running, whether data changed, whether old code can run, customer impact, backup/restore time, and whether the failure is understood.

#### Production angle

Use an incident owner and explicit decision log. Avoid simultaneous uncoordinated attempts to fix schema, app code and data.

#### Traps / caveats

- Rollback can make data worse.
- Roll-forward without root cause can repeat failure.
- Manual repair must be reviewed and documented.
- Restore from backup may cause data-loss windows.

#### Optional Anki

Q: Migration recovery decision basis?
A: Actual committed state, data risk, compatibility and service impact.

</details>

<a id="mig-fail-012"></a>

<details>
<summary><strong>🧠 MIG-FAIL-012. How do you prevent the same migration incident from recurring?</strong></summary>

#### Short answer

Turn the incident into better checks, safer rollout patterns and clearer ownership.

#### Interview answer

After recovery, identify why the migration failed: missing test data, unsafe DDL, no timeout, bad rollback plan, unclear ownership, tool misconfiguration or application/schema incompatibility. Then add controls that catch it earlier.

#### Deep dive

Prevention may include production-like rehearsals, CI checks, migration review checklist, lock-timeout conventions, safer templates, runbooks, alerting, feature-flag discipline and training.

#### Production angle

Track action items to completion. A postmortem without changed practice does not reduce migration risk.

#### Traps / caveats

- Do not stop at "human error."
- Add guardrails, not only documentation.
- Include DB, app and release-engineering perspectives.
- Verify that new checks would have caught the incident.

#### Optional Anki

Q: Best post-incident migration improvement?
A: A concrete guardrail that would have caught or limited the failure.

</details>
