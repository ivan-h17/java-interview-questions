# Migration fundamentals and tooling

---

<a id="mig-fund-001"></a>

<details>
<summary><strong>MIG-FUND-001. Why should production database schema changes be versioned?</strong></summary>

#### Short answer

Because schema is part of the application contract and must be reproducible, reviewable and traceable.

#### Interview answer

Versioned migrations let every environment move through the same ordered schema changes. They make deployments predictable and give the team a history of what changed, when, and why.

Without versioning, production can drift from staging or local development, and deployments become dependent on manual steps.

#### Deep dive

A migration history table records applied versions. The application code, database schema, test fixtures and rollback plan should evolve together.

Versioning also helps parallel team work because migration conflicts can be detected in review or CI instead of during production rollout.

#### Production angle

In production, versioned migrations support auditability, repeatable disaster recovery, environment rebuilds and safer rollbacks or roll-forwards.

#### Traps / caveats

- Versioned migration files still need careful review.
- A migration tool does not automatically make unsafe SQL safe.
- Already-applied migrations should not be edited casually.
- Manual hotfixes must be reconciled back into version control.

#### Optional Anki

Q: Why version database migrations?
A: To make schema changes reproducible, traceable and consistent across environments.

</details>

<details>
<summary><strong>MIG-FUND-002. What is the difference between schema migration and data migration?</strong></summary>

#### Short answer

A schema migration changes database structure; a data migration changes existing data.

#### Interview answer

Schema migrations include creating tables, adding columns, adding indexes and changing constraints. Data migrations include backfills, data corrections, normalization changes or moving data between columns.

Many real releases need both.

#### Deep dive

Schema migrations are often easier to reason about but can still lock or rewrite large tables. Data migrations are often riskier because they touch business data, can be slow, and may need validation or repair plans.

#### Production angle

For large systems, schema changes and data backfills are usually separated into phases so the app can remain compatible while data gradually catches up.

#### Traps / caveats

- Data migration rollback is often harder than schema rollback.
- A schema migration can trigger data rewrite internally.
- Backfills should usually be batched and restartable.
- Data changes need business validation, not only SQL success.

#### Optional Anki

Q: Schema migration vs data migration?
A: Schema changes structure; data migration changes existing rows.

</details>

<a id="mig-fund-006"></a>

<details>
<summary><strong>MIG-FUND-006. Why should manual production schema changes be avoided?</strong></summary>

#### Short answer

They create drift, bypass review and make future deployments unpredictable.

#### Interview answer

Manual schema changes are hard to reproduce and easy to forget. If production is changed by hand but staging and migration files are not updated, the next deployment may fail or behave differently.

Emergency manual fixes sometimes happen, but they must be documented and converted into a proper migration afterward.

#### Deep dive

Manual changes bypass normal controls: peer review, CI, automated tests, migration ordering and rollback planning. They also make disaster recovery harder because rebuilding from migrations no longer produces the real production schema.

#### Production angle

If a hotfix is unavoidable, record who did it, exact SQL, timestamp, reason, verification result and follow-up migration.

#### Traps / caveats

- "Small" manual changes can break ORM mappings.
- Manual index creation can hide missing migration files.
- Permissions should limit who can perform schema changes.
- Emergency changes still need post-incident cleanup.

#### Optional Anki

Q: Main risk of manual production schema changes?
A: Schema drift and unreproducible deployments.

</details>

<a id="mig-fund-007"></a>

<details>
<summary><strong>MIG-FUND-007. What is schema drift, and why is it dangerous?</strong></summary>

#### Short answer

Schema drift means environments no longer have the schema implied by the migration history and codebase.

#### Interview answer

Drift happens when someone changes a database manually, skips a migration, edits an already-applied migration, or has environment-specific objects. It is dangerous because code that works in staging may fail in production.

#### Deep dive

Drift can be structural, such as missing columns or indexes, or behavioral, such as different constraints, triggers, extensions or permissions.

It is especially painful with ORM validation, generated SQL and rolling deployments because the application assumes a schema contract that may not be true.

#### Production angle

Detect drift with migration history checks, schema diff tooling, startup validation where appropriate, and regular environment rebuilds from migrations.

#### Traps / caveats

- A migration history table can say "success" while manual drift still exists.
- Index and permission drift also matter, not only tables/columns.
- Drift can be hidden until a rarely used code path runs.
- Fixing drift should be reviewed like any production change.

#### Optional Anki

Q: What is schema drift?
A: A mismatch between actual database schema and the schema expected from versioned migrations/code.

</details>

<details>
<summary><strong>MIG-FUND-008. What makes a migration production-safe?</strong></summary>

#### Short answer

It is compatible, bounded, tested, observable and has a recovery plan.

#### Interview answer

A production-safe migration avoids breaking old and new app versions, avoids long locks and table rewrites on hot paths, runs in bounded batches when needed, and has monitoring plus a rollback or roll-forward plan.

#### Deep dive

Good migrations consider table size, lock modes, execution time, replication lag, WAL volume, connection pressure, application compatibility and failure behavior.

They are tested on production-like data and reviewed for operational impact.

#### Production angle

Use `lock_timeout`, `statement_timeout`, dry runs, feature flags, phased deployment, progress metrics and clear ownership during rollout.

#### Traps / caveats

- "Works locally" says little about production lock and data volume.
- Additive changes can still be expensive.
- A rollback script is not enough if data was changed.
- Application compatibility is as important as SQL correctness.

#### Optional Anki

Q: Production-safe migration checklist keywords?
A: Compatible, bounded, tested, observable and recoverable.

</details>

<details>
<summary><strong>🧠 MIG-FUND-009. How do transactional and non-transactional DDL differences affect migration planning?</strong></summary>

#### Short answer

Some DDL can roll back atomically, while other operations cannot run inside a transaction or have side effects that require manual cleanup.

#### Interview answer

PostgreSQL supports transactional DDL for many operations, but some commands, such as `CREATE INDEX CONCURRENTLY`, cannot run inside a transaction block. Other databases have different DDL behavior, so migration strategy must account for the actual database.

#### Deep dive

If a migration tool wraps every migration in a transaction, non-transactional or transaction-prohibited commands need special configuration. If a DDL operation fails after partial work, you may need to inspect and clean up invalid objects.

#### Production angle

For risky DDL, plan execution mode explicitly: separate migration file, no transaction wrapper, lock timeout, monitoring and failure cleanup steps.

#### Traps / caveats

- Transactional DDL does not mean no locks.
- Non-transactional DDL can leave partial state.
- Migration tool defaults differ.
- PostgreSQL behavior should not be assumed for MySQL, Oracle or SQL Server.

#### Optional Anki

Q: Why can `CREATE INDEX CONCURRENTLY` surprise migration tools?
A: It cannot run inside a transaction block.

</details>

<a id="mig-tool-003"></a>

<details>
<summary><strong>MIG-TOOL-003. Why should already-applied migrations not be edited casually?</strong></summary>

#### Short answer

Because environments that already applied the migration will not automatically replay the changed file, and checksums may fail.

#### Interview answer

Migration files are historical records. Editing one after it ran can make new environments build a different schema than existing environments, or cause Flyway/Liquibase checksum validation errors.

Usually the safe approach is to add a new migration that corrects the previous one.

#### Deep dive

Editing an applied migration breaks the idea that version `V10` means the same change everywhere. If the original change was wrong, create `V11` to repair it unless you are deliberately fixing an unreleased migration before it reaches shared environments.

#### Production angle

If an applied migration must be corrected, use the tool's repair process only after understanding which environments ran which SQL and what state they are in.

#### Traps / caveats

- Editing local-only migrations before sharing is different from editing production-applied migrations.
- Checksum repair does not fix a wrong schema.
- Repeatable migrations have different rules but still need review.
- Teams need clear conventions for migration conflicts.

#### Optional Anki

Q: Preferred fix for an already-applied bad migration?
A: Add a new corrective migration.

</details>

<a id="mig-tool-007"></a>

<details>
<summary><strong>MIG-TOOL-007. When should migrations run on application startup versus as a separate deployment step?</strong></summary>

#### Short answer

Startup migrations are fine for small safe changes; risky or long migrations should run as controlled deployment steps.

#### Interview answer

Running migrations on app startup is convenient, especially for simple services and local/test environments. In production, heavy DDL, large backfills or lock-sensitive changes should usually be separated from normal instance startup.

#### Deep dive

If every app instance tries to migrate at startup, only one may acquire the migration lock while others wait or fail. A slow migration can delay deployment, readiness and rollback.

#### Production angle

Use pipeline-controlled migrations for risky changes, with explicit monitoring and ownership. Keep app startup predictable.

#### Traps / caveats

- Startup migrations can block autoscaling or recovery.
- Multiple instances need migration locking.
- Some changes need app code compatibility before or after migration.
- Local convenience should not dictate production rollout.

#### Optional Anki

Q: When avoid startup migrations?
A: For long, risky, lock-sensitive or operationally monitored production changes.

</details>

<details>
<summary><strong>🧠 MIG-TOOL-008. What does a Flyway repair or Liquibase changelog correction need to consider?</strong></summary>

#### Short answer

It must consider both metadata and real database state; fixing checksums alone does not fix schema or data.

#### Interview answer

Repair operations can correct migration history metadata after a failed or edited migration, but they are dangerous if used to hide a real mismatch. Before repairing, inspect what SQL actually ran and what objects or data now exist.

#### Deep dive

A failed migration may leave partial objects, invalid indexes, rows already changed, or locks. A checksum mismatch may mean a file was edited after apply. The response can be repair metadata, add corrective migration, restore backup, or roll forward.

#### Production angle

Treat repair as an operational change: document the state, take backups if needed, get review, and verify every affected environment.

#### Traps / caveats

- Repair is not rollback.
- Metadata success does not prove schema correctness.
- Different environments may need different remediation.
- A rushed repair can make drift permanent.

#### Optional Anki

Q: What must migration repair check besides checksums?
A: The actual database schema/data state.

</details>
