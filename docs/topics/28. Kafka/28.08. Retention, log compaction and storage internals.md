# Retention, log compaction and storage internals

---

<a id="kf-log-001"></a>

<details>
<summary><strong>KF-LOG-001. How do Kafka retention policies delete old records?</strong></summary>

#### Short answer

Kafka deletes old log segments based on time or size retention settings.

#### Interview answer

Kafka stores partition logs in segments. With delete retention, old segments become eligible for deletion when they exceed configured retention time or size. Records are not deleted immediately one by one after consumption.

#### Deep dive

Retention is topic-level behavior with broker defaults. It controls how far consumers can lag and how much data can be replayed. It also controls storage cost.

#### Production angle

Retention must exceed expected outages, replay needs and downstream recovery windows. For audit topics, it may be driven by compliance.

#### Traps / caveats

- Consuming a record does not delete it.
- If retention expires, a lagging consumer cannot recover missing records from Kafka.

#### Optional Anki

Q: Does Kafka delete records after one consumer reads them?
A: No. Deletion is controlled by retention policy.

</details>

<a id="kf-log-002"></a>

<details>
<summary><strong>KF-LOG-002. What is the difference between delete retention and log compaction?</strong></summary>

#### Short answer

Delete retention removes old records by time/size; compaction keeps the latest record per key eventually.

#### Interview answer

With `cleanup.policy=delete`, Kafka removes old log segments based on retention. With `compact`, Kafka keeps at least the latest value for each key, eventually removing older values for the same key. A topic can also combine delete and compact policies.

#### Deep dive

Delete retention is good for event history with bounded lifetime. Compaction is useful for latest-state streams such as user profile updates or configuration snapshots.

#### Production angle

Consumers of compacted topics must understand they may not see every historical change if reading from the beginning after compaction.

#### Traps / caveats

- Compaction is asynchronous, not immediate.
- Compacted topics are not full audit logs.

#### Optional Anki

Q: What does log compaction preserve?
A: Eventually, the latest record per key.

</details>

<a id="kf-log-003"></a>

<details>
<summary><strong>KF-LOG-003. How are tombstone records used in compacted topics?</strong></summary>

#### Short answer

A tombstone is a record with a key and null value that marks the key for deletion during compaction.

#### Interview answer

In a compacted topic, sending a null value for a key tells Kafka that the key should eventually be removed. Consumers may see the tombstone and should interpret it as a delete event or removal marker.

#### Deep dive

Tombstones are retained long enough for consumers to observe deletion, then compacted away according to settings. This allows compacted topics to represent latest state including deletions.

#### Production angle

Consumers building local caches or projections must handle tombstones correctly, or deleted data can remain forever.

#### Traps / caveats

- Tombstones are not immediate physical deletion.
- Missing tombstone handling causes stale read models.

#### Optional Anki

Q: What is a Kafka tombstone?
A: A keyed record with a null value used to delete a key in compacted topics.

</details>

<a id="kf-log-004"></a>

<details>
<summary><strong>🧠 KF-LOG-004. What are the risks and limitations of compacted topics?</strong></summary>

#### Short answer

Compacted topics are eventually compacted latest-state logs, not complete ordered histories.

#### Interview answer

Compaction can remove older values for a key, so a consumer starting later may not see the full sequence of changes. Compaction timing is asynchronous, tombstones need correct retention, and keys must be stable and meaningful.

#### Deep dive

Compaction is powerful for state distribution, but dangerous if consumers rely on every transition. It also depends heavily on key quality; null keys cannot be compacted usefully.

#### Production angle

Use compacted topics for caches, reference data and latest-state restoration. Use delete-retained event topics for audit or workflow history.

#### Traps / caveats

- A compacted topic is not Event Sourcing by itself.
- Bad keys turn compaction into misleading storage behavior.

#### Optional Anki

Q: Why are compacted topics poor audit logs?
A: Older values for a key may be removed.

</details>

<a id="kf-log-005"></a>

<details>
<summary><strong>KF-LOG-005. How do retention settings and consumer lag interact?</strong></summary>

#### Short answer

If a consumer lags longer than retention, records can be deleted before it processes them.

#### Interview answer

Kafka retains records for configured time or size regardless of a specific consumer's progress. If a consumer group is down or too slow, retention may delete unprocessed records. The consumer then cannot continue from the missing offset normally.

#### Deep dive

Retention should be set using worst-case recovery assumptions: deploy pauses, outages, backfills, slow downstream systems and replay requirements.

#### Production angle

Alert on time lag approaching retention, not only record lag. A large retention window gives operational breathing room but costs storage.

#### Traps / caveats

- A consumer can be healthy but still too slow for retention.
- Offset lag alone does not say how close data is to deletion.

#### Optional Anki

Q: What happens if lag exceeds retention?
A: The consumer may lose access to unprocessed records.

</details>

<a id="kf-log-006"></a>

<details>
<summary><strong>KF-LOG-006. What happens if a consumer is down longer than topic retention?</strong></summary>

#### Short answer

Its committed offset may point to deleted data, forcing offset reset or manual recovery.

#### Interview answer

When the consumer restarts, Kafka may report that the offset is out of range. Depending on configuration, the consumer may start from earliest available, latest, or fail. Starting from latest can skip data; earliest available may still miss records that expired.

#### Deep dive

Recovery depends on whether data exists elsewhere: backup, source system, database, object storage or another topic. Kafka retention is not a substitute for business archival unless configured that way.

#### Production angle

Critical consumers need runbooks for offset out-of-range, replay source and business reconciliation.

#### Traps / caveats

- `auto.offset.reset=earliest` does not recover deleted records.
- Restarting blindly can skip or partially replay data.

#### Optional Anki

Q: What error class of situation appears when committed offset is deleted?
A: Offset out of range.

</details>

<a id="kf-log-007"></a>

<details>
<summary><strong>KF-LOG-007. How would you design retention for audit, analytics and operational event topics?</strong></summary>

#### Short answer

Match retention to business purpose: audit needs long retention, analytics may use export pipelines, operational events need recovery windows.

#### Interview answer

For audit, retention may be months or years and must align with compliance and privacy. For analytics, Kafka may retain enough to feed downstream storage, while long-term history lives in a data lake. For operational events, retention should cover consumer outages and replay needs.

#### Deep dive

Retention is a cost, compliance and recovery decision. Sensitive data may require shorter retention or data minimization. High-volume topics may need tiered storage or offloading.

#### Production angle

Document who owns retention, who can change it, and what happens when consumers fall behind.

#### Traps / caveats

- One default retention rarely fits all topics.
- Long retention of PII can become a compliance problem.

#### Optional Anki

Q: What drives Kafka retention?
A: Recovery, replay, compliance, cost and data sensitivity.

</details>

<details>
<summary><strong>🧠 KF-LOG-008. How do log segments, sequential I/O, zero-copy transfer and tiered storage affect Kafka storage behavior?</strong></summary>

#### Short answer

Kafka is efficient because it writes and reads log segments sequentially, can transfer data with low copying, and may offload older data with tiered storage.

#### Interview answer

Kafka partitions are split into log segments. Appending to logs and reading sequentially are disk-friendly. Kafka can use OS page cache and zero-copy transfer to reduce CPU overhead when sending data to consumers. Tiered storage, where available, moves older segments to remote storage to extend retention more cheaply.

#### Deep dive

These internals explain why Kafka can handle high throughput, but they also mean large messages, random access assumptions and disk saturation need careful treatment.

#### Production angle

Backend engineers do not usually tune segment internals daily, but should understand why disk, page cache, network and retention design matter.

#### Traps / caveats

- Fast sequential I/O does not make Kafka a general-purpose database.
- Tiered storage can change read latency for old data.

#### Optional Anki

Q: Why is Kafka efficient on disk?
A: It relies heavily on append and sequential I/O patterns.

</details>
