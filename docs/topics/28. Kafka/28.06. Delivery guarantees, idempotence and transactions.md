# Delivery guarantees, idempotence and transactions

---

<a id="kf-sem-001"></a>

<details>
<summary><strong>KF-SEM-001. What delivery guarantees does Kafka provide, and where do application guarantees begin?</strong></summary>

#### Short answer

Kafka provides broker-level durability and delivery mechanisms, but business correctness depends on application processing, commits and side effects.

#### Interview answer

Kafka can store records durably, preserve order within a partition and let consumers resume from committed offsets. Producer settings can improve durability and avoid some duplicate appends. But once a consumer updates a database, calls an API or sends an email, Kafka alone cannot guarantee the business effect happened exactly once.

#### Deep dive

Delivery guarantees are scoped. Producer-to-broker, broker storage, consumer offset commits and external side effects each have separate failure modes. Application design connects those pieces.

#### Production angle

Use idempotent consumers, database constraints, Outbox/Inbox patterns, explicit retry policy and observability for end-to-end reliability.

#### Traps / caveats

- Kafka guarantees do not automatically include your database.
- A committed offset is not proof that business state is correct.

#### Optional Anki

Q: Where do Kafka guarantees stop?
A: At Kafka's own produce, store, consume and transaction scopes.

</details>

<a id="kf-sem-002"></a>

<details>
<summary><strong>KF-SEM-002. What does exactly-once semantics actually mean in Kafka?</strong></summary>

#### Short answer

In Kafka, exactly-once mainly means consumed offsets and produced records can be committed atomically within Kafka's transaction scope.

#### Interview answer

Exactly-once semantics in Kafka is not a universal guarantee for all side effects. It combines idempotent producers and transactions so a consume-process-produce pipeline can commit output records and consumed offsets atomically, with duplicate Kafka writes prevented within the supported scope. Consumers using `read_committed` avoid reading aborted transactional records.

#### Deep dive

This is valuable for stream processing and Kafka-to-Kafka workflows. It does not make an external database update, HTTP call or payment charge exactly once unless that system participates through a separate correctness pattern.

#### Production angle

For database-backed services, Outbox and idempotent consumers are usually more relevant than relying on Kafka transactions alone.

#### Traps / caveats

- Exactly-once in Kafka is not exactly-once for email, payments or external APIs.
- It adds configuration and operational complexity.

#### Optional Anki

Q: What is Kafka EOS best suited for?
A: Kafka consume-process-produce workflows.

</details>

<a id="kf-sem-003"></a>

<details>
<summary><strong>🧠 KF-SEM-003. How do you configure exactly-once semantics for a consume-process-produce workflow?</strong></summary>

#### Short answer

Use a transactional producer, process input records, send output records and send consumed offsets to the same Kafka transaction.

#### Interview answer

The producer needs a stable `transactional.id`, idempotence, and transaction APIs. The consumer reads records, the application produces derived records inside a transaction, calls `sendOffsetsToTransaction` for the consumed offsets, and commits the Kafka transaction. Downstream consumers should use `isolation.level=read_committed`.

#### Deep dive

If processing fails, the transaction is aborted and output records are not visible to `read_committed` consumers. Since offsets are part of the transaction, the input can be retried.

#### Production angle

This is mostly used in stream processors or services that transform Kafka topics into other Kafka topics. Test transaction timeouts, producer fencing and restart behavior.

#### Traps / caveats

- External database writes are not included.
- `transactional.id` must be managed carefully across instances to avoid fencing surprises.

#### Optional Anki

Q: What API ties consumed offsets to a Kafka transaction?
A: `sendOffsetsToTransaction`.

</details>

<a id="kf-sem-004"></a>

<details>
<summary><strong>KF-SEM-004. How do idempotent producers and transactional producers differ?</strong></summary>

#### Short answer

An idempotent producer prevents duplicate appends from retries; a transactional producer groups multiple Kafka writes and offset commits atomically.

#### Interview answer

Producer idempotence is about safely retrying sends to Kafka without appending the same batch twice in its supported scope. Transactions are broader: they allow multiple records across partitions and consumed offsets to commit or abort together.

#### Deep dive

Idempotence is commonly enabled for safer production. Transactions are more specialized because they add state, coordinator interaction, timeouts and fencing behavior.

#### Production angle

Use idempotence for important producers. Use transactions when Kafka-to-Kafka atomicity is required and the team can operate the added complexity.

#### Traps / caveats

- Idempotence is not consumer idempotency.
- Transactions do not automatically include a relational database transaction.

#### Optional Anki

Q: Producer idempotence vs transactions?
A: Idempotence deduplicates retry appends; transactions atomically commit grouped Kafka work.

</details>

<a id="kf-sem-005"></a>

<details>
<summary><strong>🧠 KF-SEM-005. What are `transactional.id`, `sendOffsetsToTransaction` and `isolation.level=read_committed` used for?</strong></summary>

#### Short answer

They identify transactional producers, include consumed offsets in transactions, and hide uncommitted or aborted transactional records from consumers.

#### Interview answer

`transactional.id` gives a transactional producer a stable identity and enables fencing old instances. `sendOffsetsToTransaction` commits consumed offsets as part of the same Kafka transaction as produced output. `read_committed` makes consumers read only committed transactional data.

#### Deep dive

These pieces work together for Kafka-to-Kafka exactly-once semantics. Without offset commits in the transaction, output and input progress can diverge. Without `read_committed`, consumers may see records from aborted transactions.

#### Production angle

Misconfigured transactional IDs can cause producer instances to fence each other. Keep IDs stable for a producer instance across restarts, but unique per active instance.

#### Traps / caveats

- Reusing the same transactional ID across active instances is dangerous.
- `read_committed` may add perceived lag because uncommitted transactional data is hidden.

#### Optional Anki

Q: What does `read_committed` hide?
A: Aborted and not-yet-committed transactional records.

</details>

<a id="kf-sem-006"></a>

<details>
<summary><strong>KF-SEM-006. Can Kafka transactions make updates to an external database exactly once?</strong></summary>

#### Short answer

No. Kafka transactions do not include a normal external database transaction.

#### Interview answer

Kafka can atomically commit Kafka records and Kafka offsets. A relational database is a separate transaction manager. Unless you use a distributed transaction system, Kafka cannot guarantee that a DB update and Kafka transaction commit happen atomically together.

#### Deep dive

The failure window is the classic dual-write problem. The DB commit can succeed and Kafka publish fail, or Kafka publish can succeed and the DB update fail. Retrying can create duplicates unless the operation is idempotent.

#### Production angle

Use Transactional Outbox for DB-to-Kafka publication and Inbox/idempotency for Kafka-to-DB consumption.

#### Traps / caveats

- `@Transactional` in Spring does not automatically wrap Kafka and DB work into one atomic transaction.
- Two-phase commit is rarely the practical default in microservices.

#### Optional Anki

Q: What problem appears when updating DB and publishing Kafka separately?
A: The dual-write problem.

</details>

<a id="kf-sem-007"></a>

<details>
<summary><strong>KF-SEM-007. How do you keep a relational database and Kafka events consistent?</strong></summary>

#### Short answer

Use patterns like Transactional Outbox for publishing and idempotent Inbox processing for consuming.

#### Interview answer

For publishing, write the business row and an outbox row in the same database transaction. A relay later publishes the outbox row to Kafka and marks it sent. For consuming, process messages idempotently, usually recording event IDs or using natural unique constraints.

#### Deep dive

This accepts at-least-once publication and consumption but makes repeated attempts safe. The database remains the source of truth for business state, and Kafka becomes a reliable propagation channel.

#### Production angle

Monitor outbox lag, relay failures, duplicate rates and stuck messages. Design replay so it does not corrupt state.

#### Traps / caveats

- Publishing directly after commit can lose events if the service crashes.
- Publishing before commit can expose events for state that later rolls back.

#### Optional Anki

Q: How does Outbox solve DB-to-Kafka consistency?
A: It stores the event in the same DB transaction as the business change.

</details>

<a id="kf-sem-008"></a>

<details>
<summary><strong>KF-SEM-008. What are the Transactional Outbox and Inbox patterns?</strong></summary>

#### Short answer

Outbox reliably publishes local DB changes as events; Inbox reliably records consumed events to make handling idempotent.

#### Interview answer

With Outbox, a service writes business data and an event row in one local transaction. A relay publishes rows to Kafka. With Inbox, a consumer records a message ID before or during processing so duplicate deliveries can be detected and skipped safely.

#### Deep dive

Both patterns embrace at-least-once delivery. They do not prevent duplicates from existing; they prevent duplicates from causing repeated business effects.

#### Production angle

Outbox and Inbox tables need cleanup, indexes, monitoring, retry policy and dashboards for stuck records.

#### Traps / caveats

- Outbox relay must itself be idempotent.
- Inbox keys must represent the business operation, not a random processing attempt.

#### Optional Anki

Q: What is the goal of Inbox?
A: Idempotent consumption by recording processed message identity.

</details>

<a id="kf-sem-009"></a>

<details>
<summary><strong>KF-SEM-009. How do you design an idempotent consumer?</strong></summary>

#### Short answer

Give each event a stable ID or business key, record processed work, and make side effects safe to repeat.

#### Interview answer

An idempotent consumer can process the same event multiple times and produce the same final state. Techniques include unique constraints, processed-event tables, natural idempotency keys, conditional updates, version checks and business-state guards.

#### Deep dive

The correct key depends on the operation. For a payment charge, use a payment command ID or idempotency key. For a projection update, use aggregate ID plus event version. For a notification, decide whether duplicates are acceptable or must be suppressed.

#### Production angle

Duplicate events should be expected during retries, rebalances and replay. Track duplicate detection metrics.

#### Traps / caveats

- Deduplicating only by Kafka offset fails after replay to another group.
- A time-limited dedupe store may allow old replay duplicates.

#### Optional Anki

Q: What makes a consumer idempotent?
A: Reprocessing the same event does not repeat the business effect.

</details>

<a id="kf-sem-010"></a>

<details>
<summary><strong>KF-SEM-010. How do retries and offset commits interact with delivery guarantees?</strong></summary>

#### Short answer

Retries decide how failed processing is attempted again; offset commits decide whether Kafka considers records complete.

#### Interview answer

If processing fails and the offset is not committed, the same record can be retried. If it is sent to a DLQ and the offset is committed, the main consumer can move on. The commit point defines whether a failure causes retry, duplicate processing or skip.

#### Deep dive

Blocking retries preserve order but can block the partition. Retry topics avoid blocking but may change ordering. DLQs isolate poison messages but require later reprocessing policy.

#### Production angle

For critical consumers, define retry count, backoff, DLQ metadata, commit rules and idempotency before incidents.

#### Traps / caveats

- Committing after a failed side effect can lose the chance to retry.
- Retrying forever can block a partition indefinitely.

#### Optional Anki

Q: What does offset commit timing influence?
A: Loss, duplicate and retry behavior.

</details>

<a id="kf-sem-011"></a>

<details>
<summary><strong>🧠 KF-SEM-011. Why is end-to-end exactly-once difficult in distributed systems?</strong></summary>

#### Short answer

Because multiple systems can fail independently and usually cannot atomically coordinate every side effect.

#### Interview answer

A Kafka consumer may update a database, call a payment provider, publish another event and commit an offset. Each step can succeed, fail or time out independently. After a timeout, the system may not know whether the external side effect happened.

#### Deep dive

Distributed systems often settle for at-least-once execution plus idempotent operations, commutative updates, unique constraints and reconciliation. This is usually more practical than trying to coordinate global transactions.

#### Production angle

For money movement, design explicit idempotency keys and reconciliation jobs. Do not rely on transport semantics to protect business state.

#### Traps / caveats

- Unknown outcome is harder than known failure.
- Exactly-once marketing terms can hide external side-effect gaps.

#### Optional Anki

Q: Practical alternative to end-to-end exactly once?
A: At-least-once processing plus idempotent side effects and reconciliation.

</details>

<a id="kf-sem-012"></a>

<details>
<summary><strong>KF-SEM-012. What are duplicate and out-of-order events, and why can they happen?</strong></summary>

#### Short answer

Duplicates are repeated business events or repeated deliveries; out-of-order events are observed in a different order than the business expects.

#### Interview answer

Duplicates can come from retries, rebalances, producer uncertainty, replay or application bugs. Out-of-order events can happen when related records use different partitions, multiple producers publish related facts, retries reorder sends, or consumers process concurrently.

#### Deep dive

Kafka preserves order only inside a partition. Business order may require choosing the right key, using event versions, rejecting stale updates or designing operations to be commutative.

#### Production angle

Consumers should tolerate duplicates and stale events. For projections, store last processed version or timestamp where appropriate.

#### Traps / caveats

- Timestamp order is not always causal order.
- Duplicate delivery and duplicate business event are different problems.

#### Optional Anki

Q: Main Kafka ordering scope?
A: One partition.

</details>

<a id="kf-sem-013"></a>

<details>
<summary><strong>KF-SEM-013. How would you explain Kafka delivery semantics in a senior interview?</strong></summary>

#### Short answer

Explain guarantees by boundary: producer writes, broker durability, consumer offsets, Kafka transactions and external side effects.

#### Interview answer

I would avoid saying "Kafka is exactly once" without scope. Kafka can provide durable writes and per-partition ordering. Producers can be idempotent. Consumers choose commit timing, which creates at-most-once or at-least-once behavior. Kafka transactions help Kafka-to-Kafka workflows. External business effects still need idempotency and consistency patterns.

#### Deep dive

Senior answers should connect settings to failure modes: broker failure, retry after timeout, consumer crash after DB update, rebalance before commit, replay and schema change.

#### Production angle

The correct design usually combines `acks=all`, replication, idempotent producers, manual commits, idempotent consumers, Outbox/Inbox and observability.

#### Traps / caveats

- Do not give a one-word guarantee without describing the scope.
- Business correctness is a design property, not a Kafka setting.

#### Optional Anki

Q: How should Kafka delivery semantics be framed?
A: By scope and failure boundary.

</details>
