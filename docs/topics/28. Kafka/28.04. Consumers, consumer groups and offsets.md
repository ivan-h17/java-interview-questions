# Consumers, consumer groups and offsets

---

<a id="kf-cons-001"></a>

<details>
<summary><strong>KF-CONS-001. What is a Kafka consumer group, and why are consumer groups useful?</strong></summary>

#### Short answer

A consumer group is a set of consumers that share work for subscribed topic partitions.

#### Interview answer

Kafka assigns each partition to at most one consumer within the same group, so the group processes a topic in parallel without two consumers in that group processing the same partition at the same time. Different groups can independently read the same topic from their own offsets.

#### Deep dive

This gives Kafka both queue-like and pub-sub-like behavior. One group acts like a scalable worker pool. Multiple groups allow independent services such as billing, search indexing and analytics to consume the same event stream.

#### Production angle

Consumer group ID is part of application identity. Accidentally sharing a group ID between services can cause partitions to be stolen and messages to appear missing.

#### Traps / caveats

- More consumers than partitions means some consumers are idle.
- A new group may start from earliest or latest depending on offset reset policy.

#### Optional Anki

Q: What does a consumer group share?
A: Topic partitions and committed offsets for that group.

</details>

<a id="kf-cons-002"></a>

<details>
<summary><strong>KF-CONS-002. How are partitions assigned to consumers, and what happens when there are more consumers than partitions?</strong></summary>

#### Short answer

Kafka assigns partitions among consumers in a group; extra consumers remain idle if there are more consumers than partitions.

#### Interview answer

The group coordinator and assignment strategy decide which consumer owns which partitions. Each partition can be assigned to only one active consumer in a group. If a topic has four partitions and the group has six consumers, only four consumers can receive work for that topic.

#### Deep dive

Assignments can change during rebalances when consumers join, leave, crash or change subscription. Assignment strategy affects balance, movement and locality.

#### Production angle

Spring Kafka listener concurrency above partition count does not improve throughput for a single topic. It may only help if consuming multiple topics or if partition count is increased safely.

#### Traps / caveats

- Adding replicas does not increase consumer parallelism; partitions do.
- Idle consumers are not a Kafka bug when consumer count exceeds partition count.

#### Optional Anki

Q: Can two consumers in one group process the same partition at the same time?
A: No, not under normal group assignment.

</details>

<a id="kf-cons-003"></a>

<details>
<summary><strong>KF-CONS-003. What is an offset commit, and where are committed offsets stored?</strong></summary>

#### Short answer

An offset commit records a consumer group's progress for a topic partition, usually in Kafka's internal `__consumer_offsets` topic.

#### Interview answer

After processing records, a consumer commits the next offset it wants to read. If it restarts, Kafka uses the committed offset to resume. Offsets are stored per consumer group, topic and partition.

#### Deep dive

The committed offset represents progress, not necessarily business success unless the application commits only after successful processing. This distinction is central to delivery semantics.

#### Production angle

Offset commits are critical during deploys and incidents. Wrong commit timing can cause lost processing or duplicates.

#### Traps / caveats

- Kafka commits the next offset, not the last processed offset.
- Offset commits do not roll back external side effects.

#### Optional Anki

Q: What does a committed Kafka offset represent?
A: The next position a consumer group should read for a partition.

</details>

<a id="kf-cons-004"></a>

<details>
<summary><strong>KF-CONS-004. What is the difference between auto commit and manual commit?</strong></summary>

#### Short answer

Auto commit commits offsets on a timer; manual commit lets the application commit only after chosen processing points.

#### Interview answer

Auto commit is simpler but can commit offsets before business processing is safely complete. Manual commit gives more control: the service can commit after database updates, after a batch succeeds, or after publishing to a DLQ.

#### Deep dive

Manual commit is usually preferred for important business processing because offset position is part of correctness. The code can align offset commits with idempotent side effects and error handling.

#### Production angle

For payment or inventory consumers, commit timing should be reviewed like transaction boundaries.

#### Traps / caveats

- Auto commit can hide message loss scenarios.
- Manual commit still needs careful handling during rebalance and shutdown.

#### Optional Anki

Q: Why use manual Kafka commits?
A: To commit offsets only after controlled processing outcomes.

</details>

<a id="kf-cons-005"></a>

<details>
<summary><strong>KF-CONS-005. What can go wrong when offsets are committed before or after message processing?</strong></summary>

#### Short answer

Commit before processing risks message loss; commit after processing risks duplicate processing.

#### Interview answer

If the consumer commits first and crashes before business work, Kafka thinks the record is done and it may be skipped. If it processes first and crashes before commit, the record is read again after restart. That creates at-least-once behavior and requires idempotent processing.

#### Deep dive

There is no free commit point when external side effects are involved. You choose between losing work and duplicating work. Most business systems prefer duplicates plus idempotency over silent loss.

#### Production angle

Use database constraints, processed-event tables, natural idempotency keys, or Inbox patterns to make repeated processing safe.

#### Traps / caveats

- "Processed" must include all side effects, not just deserialization.
- Commit timing cannot make non-idempotent external APIs safe.

#### Optional Anki

Q: What happens if you commit after processing and crash before commit?
A: The record may be processed again.

</details>

<a id="kf-cons-006"></a>

<details>
<summary><strong>KF-CONS-006. What do at-most-once and at-least-once processing mean from a consumer perspective?</strong></summary>

#### Short answer

At-most-once may skip records after failure; at-least-once may process records more than once but should not skip acknowledged work.

#### Interview answer

At-most-once commits or advances before processing, so a crash can lose work. At-least-once processes first and commits later, so a crash can cause duplicate processing. Kafka consumers commonly use at-least-once plus idempotent handlers.

#### Deep dive

The terms describe delivery and processing attempts, not business correctness. A duplicate-safe consumer can turn at-least-once delivery into effectively-once business effects for a specific operation.

#### Production angle

For financial and inventory flows, at-least-once plus idempotency is usually safer than at-most-once.

#### Traps / caveats

- At-least-once does not mean exactly once.
- At-most-once can look fine in metrics while silently losing work.

#### Optional Anki

Q: Which semantic commonly requires idempotent consumers?
A: At-least-once.

</details>

<a id="kf-cons-007"></a>

<details>
<summary><strong>KF-CONS-007. How do polling, heartbeats, `session.timeout.ms` and `max.poll.interval.ms` interact?</strong></summary>

#### Short answer

Heartbeats show the consumer is alive; polling must happen often enough to avoid being considered stuck.

#### Interview answer

A consumer sends heartbeats to stay in the group. If heartbeats stop longer than the session timeout, the group considers it dead. `max.poll.interval.ms` protects against consumers that are alive but not polling; if processing takes too long between polls, the consumer can be removed and partitions reassigned.

#### Deep dive

Modern clients heartbeat in the background, but the application must still call `poll()` within the max poll interval. Long blocking processing inside the poll loop is a common cause of rebalances.

#### Production angle

For slow handlers, reduce batch size, use worker handoff carefully, pause/resume partitions, or increase the interval with clear reasoning.

#### Traps / caveats

- Increasing timeouts can hide slow processing rather than fix it.
- If a partition is reassigned while old processing continues, duplicates can occur.

#### Optional Anki

Q: What does `max.poll.interval.ms` protect against?
A: Consumers that stay alive but do not poll again in time.

</details>

<a id="kf-cons-008"></a>

<details>
<summary><strong>KF-CONS-008. How does `max.poll.records` affect processing time, retries and lag?</strong></summary>

#### Short answer

It limits how many records a poll returns; larger batches improve throughput but can make processing, retries and commits slower.

#### Interview answer

If `max.poll.records` is too high, one poll may take too long to process, risking `max.poll.interval.ms` violations and large retry units. If it is too low, overhead increases and throughput may suffer. The right value depends on handler cost and commit strategy.

#### Deep dive

Batch size affects failure handling. If one record fails in a large batch, the application needs a clear policy for partial success, retry, DLQ and offset commits.

#### Production angle

Tune it with processing-time metrics, p95/p99 handler latency and downstream capacity, not just Kafka fetch throughput.

#### Traps / caveats

- Large batches can overload database connection pools.
- Small batches can increase broker/client overhead.

#### Optional Anki

Q: What does `max.poll.records` control?
A: The maximum number of records returned by one poll.

</details>

<a id="kf-cons-009"></a>

<details>
<summary><strong>KF-CONS-009. What is consumer lag, and how do offset lag and time lag differ?</strong></summary>

#### Short answer

Consumer lag is how far a consumer group is behind the log; offset lag counts records, while time lag estimates delay.

#### Interview answer

Offset lag is the difference between the latest partition offset and the group's committed or current offset. Time lag asks how old the unprocessed events are. Offset lag can be misleading because 10,000 small events may be cheap, while 100 heavy events may be serious.

#### Deep dive

Lag must be interpreted per partition and per business flow. A batch analytics consumer may tolerate lag; a payment event consumer may not.

#### Production angle

Good alerts combine lag with event age, processing rate, error rate, DLQ growth and downstream health.

#### Traps / caveats

- Lag of zero does not prove side effects succeeded.
- Total lag can hide one badly lagging partition.

#### Optional Anki

Q: Why measure time lag?
A: It better reflects business delay than only record count.

</details>

<a id="kf-cons-010"></a>

<details>
<summary><strong>KF-CONS-010. When would you use `assign()` instead of `subscribe()`?</strong></summary>

#### Short answer

Use `assign()` when you need manual control over exact partitions and do not want consumer group subscription management.

#### Interview answer

`subscribe()` joins a consumer group and lets Kafka assign partitions. `assign()` directly assigns specific topic partitions to the consumer. This is useful for tools, targeted replay, diagnostics or specialized processing where the application controls partition ownership.

#### Deep dive

With `assign()`, you give up automatic group rebalancing for that assignment. The application must manage partition distribution, failover and scaling if needed.

#### Production angle

Most service consumers should use `subscribe()`. Use `assign()` carefully for controlled operations such as replaying a known partition range.

#### Traps / caveats

- Manual assignment can create duplicate processing if two instances read the same partition unintentionally.
- It is not a shortcut for scaling normal consumers.

#### Optional Anki

Q: Which Consumer API joins a group automatically?
A: `subscribe()`.

</details>

<a id="kf-cons-011"></a>

<details>
<summary><strong>KF-CONS-011. How would you implement consumer-side filtering, and what are the caveats?</strong></summary>

#### Short answer

Read records and skip irrelevant ones, but remember Kafka still delivers them and offsets still advance.

#### Interview answer

A consumer can filter by event type, header, key or payload after reading. This is simple, but it still consumes network, CPU and poll capacity. If many consumers filter most records, topic design may be wrong.

#### Deep dive

Filtering also affects offset commits. If skipped records are considered processed, their offsets must be committed. If filtering depends on evolving business logic, replay can produce different outcomes.

#### Production angle

For high-volume filtering, consider separate topics, better event routing, or Kafka Streams if transformation/routing is substantial.

#### Traps / caveats

- Kafka does not provide database-like server-side filtering for arbitrary payload fields.
- Filtering sensitive events in consumers does not replace topic-level access control.

#### Optional Anki

Q: Main caveat of consumer-side filtering?
A: The consumer still reads and commits through irrelevant records.

</details>

<a id="kf-cons-012"></a>

<details>
<summary><strong>🧠 KF-CONS-012. What do the group coordinator and assignment strategies do?</strong></summary>

#### Short answer

The group coordinator manages group membership and offset commits; assignment strategies decide how partitions are distributed among consumers.

#### Interview answer

For each group, Kafka coordinates members, detects joins/leaves, triggers rebalances and stores committed offsets. Assignment strategies such as range, round-robin, sticky or cooperative sticky influence balance and how many partitions move during rebalance.

#### Deep dive

Sticky and cooperative approaches can reduce partition movement and disruption compared with eager reassignment. This matters for stateful consumers or expensive warmups.

#### Production angle

When debugging rebalances, inspect group coordinator logs, client logs, assignment strategy, consumer restarts and poll interval violations.

#### Traps / caveats

- Assignment strategy affects operational behavior, not just distribution.
- Stateful consumers suffer more from frequent partition movement.

#### Optional Anki

Q: What triggers partition reassignment in a group?
A: A rebalance coordinated by Kafka after membership or subscription changes.

</details>
