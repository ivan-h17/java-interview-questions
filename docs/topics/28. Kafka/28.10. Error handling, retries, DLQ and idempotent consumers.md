# Error handling, retries, DLQ and idempotent consumers

---

<a id="kf-err-001"></a>

<details>
<summary><strong>KF-ERR-001. What kinds of errors can happen in Kafka consumers?</strong></summary>

#### Short answer

Consumer errors include deserialization, validation, business rule, downstream dependency, timeout, commit, rebalance and poison-message failures.

#### Interview answer

Not all consumer errors are the same. A malformed payload may never succeed. A database timeout may succeed later. A duplicate payment command may be safely ignored. A commit failure may cause repeat processing. The handling should depend on error type.

#### Deep dive

Classifying errors helps choose between retry, DLQ, skip, alert, circuit breaking or stopping the consumer. Treating all errors as infinite retries is dangerous.

#### Production angle

Dashboards should split deserialization failures, business validation failures, downstream failures, retry counts and DLQ writes.

#### Traps / caveats

- Poison messages can block a whole partition.
- Retrying permanent errors wastes capacity and hides bad data.

#### Optional Anki

Q: Why classify consumer errors?
A: Different errors need different retry, DLQ or alert behavior.

</details>

<a id="kf-err-002"></a>

<details>
<summary><strong>KF-ERR-002. What is a poison pill message, and when should it go to a DLQ?</strong></summary>

#### Short answer

A poison pill is a record that consistently fails processing and blocks progress; send it to DLQ when it cannot be processed safely after bounded attempts.

#### Interview answer

Examples include invalid schema, bad data, unsupported event type or a business state that cannot be handled. After a controlled number of retries, the consumer can publish the record and error metadata to a DLQ, commit the original offset, and continue.

#### Deep dive

The decision depends on ordering requirements. For strict order per key, skipping to DLQ may violate business sequence, so the team may need manual intervention or a quarantine workflow.

#### Production angle

DLQ is not success. It needs alerts, ownership, triage and reprocessing tools.

#### Traps / caveats

- A DLQ without a runbook becomes a data graveyard.
- Sending to DLQ and committing offset means the main flow has skipped that record.

#### Optional Anki

Q: What is a poison pill?
A: A message that repeatedly fails and blocks normal processing.

</details>

<a id="kf-err-003"></a>

<details>
<summary><strong>KF-ERR-003. What metadata should be included in a DLQ record?</strong></summary>

#### Short answer

Include original topic, partition, offset, key, timestamp, headers, error type, error message, stack/cause summary and retry count.

#### Interview answer

A DLQ record should be enough to debug and safely reprocess. I would include original coordinates, payload or a pointer to it, consumer name/version, exception class, failure reason, attempt count, correlation ID and processing timestamp.

#### Deep dive

DLQ metadata should preserve traceability without leaking secrets or excessive PII. If payloads are sensitive, store secure references or redacted payloads.

#### Production angle

Good metadata makes DLQ triage fast: is this a bad deploy, bad data, schema mismatch or downstream outage?

#### Traps / caveats

- Logging/storing full payloads can violate privacy rules.
- Without original offset and headers, replay and investigation are harder.

#### Optional Anki

Q: Essential DLQ metadata?
A: Original topic, partition, offset, key, error and retry context.

</details>

<a id="kf-err-004"></a>

<details>
<summary><strong>KF-ERR-004. What is the difference between blocking retry and non-blocking retry?</strong></summary>

#### Short answer

Blocking retry retries on the same consumer path and can block the partition; non-blocking retry moves failed records elsewhere for delayed retry.

#### Interview answer

Blocking retry is simple and preserves partition order, but one bad or slow record can stop later records in that partition. Non-blocking retry uses retry topics, delay queues or scheduled reprocessing so the main consumer can continue, but ordering may change.

#### Deep dive

The right choice depends on whether order is more important than throughput. For payment state transitions, blocking or per-key quarantine may be needed. For independent notifications, non-blocking retry is often better.

#### Production angle

Use bounded retries and clear retry exhaustion behavior. Monitor retry backlog separately from main lag.

#### Traps / caveats

- Non-blocking retries can process later events before earlier failed ones.
- Blocking retries can turn one bad message into a partition outage.

#### Optional Anki

Q: Main downside of blocking retry?
A: It can block the whole partition.

</details>

<a id="kf-err-005"></a>

<details>
<summary><strong>KF-ERR-005. How should backoff and jitter be used to avoid retry storms?</strong></summary>

#### Short answer

Use bounded exponential backoff plus jitter so many consumers do not retry at the same time.

#### Interview answer

If a downstream service fails, immediate retries from many consumers can amplify the outage. Backoff spaces attempts, exponential backoff increases delay after repeated failures, and jitter randomizes timing so retries do not synchronize.

#### Deep dive

Retry policy should include max attempts, max delay, error classification and circuit breaking or pause behavior when the dependency is clearly down.

#### Production angle

Track retry rate, downstream error rate and retry-topic backlog. A retry storm should alert before it exhausts connection pools or threads.

#### Traps / caveats

- Retrying non-idempotent operations can duplicate side effects.
- Infinite retries can hide permanent failures forever.

#### Optional Anki

Q: Why add jitter to retries?
A: To avoid synchronized retry waves.

</details>

<a id="kf-err-006"></a>

<details>
<summary><strong>KF-ERR-006. How do retries affect ordering and consumer lag?</strong></summary>

#### Short answer

Retries can preserve order by blocking or improve progress by moving failed records aside, but either choice affects lag semantics.

#### Interview answer

Blocking retries keep later records behind the failed record, preserving partition order but increasing lag. Non-blocking retries let the main consumer continue, reducing main lag, but later events may process before earlier failed ones.

#### Deep dive

Lag can move from the main topic to retry topics. That is not necessarily solved work; it is delayed work. Monitoring must include all retry paths.

#### Production angle

For per-entity ordering, consider retrying or quarantining by key. For independent events, non-blocking retry may be acceptable.

#### Traps / caveats

- Main consumer lag can look healthy while retry backlog grows.
- Retrying can reorder business effects.

#### Optional Anki

Q: What retry style preserves partition order best?
A: Blocking retry on the same partition.

</details>

<a id="kf-err-007"></a>

<details>
<summary><strong>KF-ERR-007. How should deserialization errors, validation errors and downstream failures be handled differently?</strong></summary>

#### Short answer

Deserialization and validation errors are often permanent; downstream failures are often transient and retryable.

#### Interview answer

A deserialization error usually means the consumer cannot even parse the record, so it may need a special error deserializer, DLQ and alert. Validation errors may be bad data or unsupported business state. Downstream failures like database timeout or HTTP 503 should use bounded retry, backoff and circuit breaking.

#### Deep dive

Treating all errors as retryable can block partitions. Treating all errors as DLQ can skip recoverable work. Classification is part of consumer design.

#### Production angle

Dashboards should show which class is increasing. A schema deploy problem and a database outage have different owners and fixes.

#### Traps / caveats

- A deserialization failure can prevent the listener from seeing the payload unless configured correctly.
- Validation errors may reveal producer contract bugs.

#### Optional Anki

Q: Which error class is commonly transient?
A: Downstream dependency failure.

</details>

<a id="kf-err-008"></a>

<details>
<summary><strong>KF-ERR-008. Should offsets be committed for messages sent to a DLQ?</strong></summary>

#### Short answer

Usually yes, after the DLQ write succeeds, if the policy is to skip the original record in the main flow.

#### Interview answer

If a poison message is successfully published to DLQ, committing the original offset lets the consumer continue. If the offset is not committed, the same failing record will be read again and may loop forever. The DLQ write and offset commit should be treated as the failure-handling outcome.

#### Deep dive

There is a failure window: DLQ publish can succeed but offset commit fail, causing another DLQ copy. DLQ consumers and reprocessors should also be idempotent.

#### Production angle

Monitor DLQ publish failures. If DLQ is unavailable, decide whether to stop the consumer or retry rather than silently skip.

#### Traps / caveats

- Commit only after DLQ write success.
- Committing means the main consumer will not process that record again unless manually replayed.

#### Optional Anki

Q: Why commit after DLQ?
A: To move the main consumer past a handled poison record.

</details>

<a id="kf-err-009"></a>

<details>
<summary><strong>KF-ERR-009. How do you reprocess DLQ messages safely?</strong></summary>

#### Short answer

Fix the root cause first, replay in controlled batches, preserve metadata, and rely on idempotent handlers.

#### Interview answer

I would classify DLQ records, identify whether the issue was code, schema, data or dependency, deploy the fix, then reprocess a small batch with monitoring. Reprocessing should preserve original key and important headers when ordering or routing depends on them.

#### Deep dive

Reprocessing may produce duplicates or out-of-order effects. Some records require manual correction, not blind replay.

#### Production angle

Build tooling with dry-run, rate limit, filters by error type/time/topic and audit logs. Alert on repeated DLQ failure.

#### Traps / caveats

- Blindly replaying a large DLQ can trigger another outage.
- Reprocessing old events can violate current business assumptions.

#### Optional Anki

Q: First step before DLQ replay?
A: Fix or classify the root cause.

</details>

<a id="kf-err-010"></a>

<details>
<summary><strong>🧠 KF-ERR-010. How would you store processed event IDs, and what are the Redis vs database trade-offs?</strong></summary>

#### Short answer

Use durable database records for critical idempotency; Redis can work for short-lived dedupe where expiration is acceptable.

#### Interview answer

A database table with a unique event ID gives durable deduplication and can participate in the same transaction as business updates. Redis is faster and useful for short TTL idempotency, but data can expire or be lost depending on persistence and failover.

#### Deep dive

For payments, I prefer a database unique constraint or domain idempotency key. For temporary notification dedupe, Redis may be fine. The dedupe retention must cover replay windows.

#### Production angle

Index the dedupe key, clean old records safely, and monitor duplicate detection. Avoid unbounded dedupe tables.

#### Traps / caveats

- TTL-based dedupe fails for old replays after expiration.
- Redis dedupe may not be durable enough for financial correctness.

#### Optional Anki

Q: Best dedupe store for critical DB side effects?
A: The same relational database transaction using unique constraints or an Inbox table.

</details>

<a id="kf-err-011"></a>

<details>
<summary><strong>KF-ERR-011. How do you handle partial batch failures?</strong></summary>

#### Short answer

Track which records succeeded, retry or DLQ failed records, and commit only safe progress.

#### Interview answer

If a batch has mixed success, you need a policy. For ordered processing, you may stop at the first failure and commit only before it. For independent records, you can process individually, send failed records to retry/DLQ and commit after safe handling.

#### Deep dive

Batch processing complicates offset commits because Kafka offsets advance sequentially per partition. You cannot commit around a failed earlier offset without deciding to skip or DLQ it.

#### Production angle

For important consumers, keep batch sizes reasonable and design per-record error reporting even inside batch handlers.

#### Traps / caveats

- Committing past a failed record skips it.
- Retrying the whole batch can duplicate side effects for records that already succeeded.

#### Optional Anki

Q: Why are partial batch failures hard in Kafka?
A: Offsets advance sequentially per partition.

</details>

<a id="kf-err-012"></a>

<details>
<summary><strong>KF-ERR-012. How would you design an error-handling policy for a payments consumer?</strong></summary>

#### Short answer

Use idempotency, strict error classification, bounded retries, careful ordering, DLQ/quarantine, alerts and reconciliation.

#### Interview answer

For payments, I would require stable payment IDs, unique constraints, idempotent provider calls and manual offset commits after safe processing. Transient dependency failures get bounded retry with backoff. Permanent validation or schema problems go to a high-priority DLQ or quarantine. Duplicate events are detected and ignored safely.

#### Deep dive

Payment flows need explicit handling for unknown outcomes: a provider timeout may still have charged the card. The consumer should reconcile with provider state instead of blindly retrying a non-idempotent charge.

#### Production angle

Add dashboards for lag, retries, DLQ, duplicate detection, provider errors and reconciliation gaps. Page on stuck or growing payment backlog.

#### Traps / caveats

- Never rely only on Kafka offset commits to prevent double charging.
- Infinite retries against a payment provider can create financial incidents.

#### Optional Anki

Q: Key property of a payments Kafka consumer?
A: Idempotent, reconciled side effects using stable business keys.

</details>
