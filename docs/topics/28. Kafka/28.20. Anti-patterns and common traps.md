# Anti-patterns and common traps

---

<a id="kf-trap-001"></a>

<details>
<summary><strong>KF-TRAP-001. Why is using Kafka as a database often an anti-pattern?</strong></summary>

#### Short answer

Kafka is a durable event log, not a general-purpose queryable transactional database.

#### Interview answer

Kafka can retain and replay records, but it does not provide normal database capabilities like indexed queries, constraints, transactions across arbitrary entities or ad hoc updates. Applications usually need a database or state store for serving queries and enforcing invariants.

#### Deep dive

Compacted topics can distribute latest state, but they are not a full replacement for data modeling and query access.

#### Production angle

Use Kafka for propagation and replay. Use databases/search stores/caches for query and transactional needs.

#### Traps / caveats

- Long retention does not make Kafka a database.
- Consumers rebuilding state need schema and replay compatibility.

#### Optional Anki

Q: Why is Kafka not a normal database?
A: It lacks general query, update and constraint semantics.

</details>

<a id="kf-trap-002"></a>

<details>
<summary><strong>KF-TRAP-002. Why is using Kafka for synchronous request-response often problematic?</strong></summary>

#### Short answer

It recreates RPC with more moving parts, harder timeouts and more complex correlation.

#### Interview answer

Request-response over Kafka needs reply topics, correlation IDs, timeout handling, cleanup and failure semantics. If the caller needs an immediate answer, HTTP or gRPC is usually clearer and easier to operate.

#### Deep dive

Kafka request-response can be valid for some asynchronous command workflows, but it should be deliberate, not a way to avoid service APIs.

#### Production angle

If using it, define timeout budgets, reply retention, idempotency and what happens when replies arrive late.

#### Traps / caveats

- Late replies can update state after the caller gave up.
- Reply topics can become operational clutter.

#### Optional Anki

Q: Better default for immediate answers?
A: Synchronous API such as HTTP or gRPC.

</details>

<a id="kf-trap-003"></a>

<details>
<summary><strong>KF-TRAP-003. Why is putting huge payloads into Kafka risky?</strong></summary>

#### Short answer

Huge payloads hurt memory, network, disk, retries, fetches and consumer stability.

#### Interview answer

Kafka works best with event-sized records. Large payloads increase producer buffers, broker storage, replication cost, consumer fetch memory and retry time. They also force max-size config changes across clients and brokers.

#### Deep dive

If the payload is a file or large document, Kafka should usually carry metadata and a pointer to object storage.

#### Production angle

Track payload size percentiles and reject or route oversized messages intentionally.

#### Traps / caveats

- Compression does not fully solve large-message risks.
- External references need lifecycle and access control.

#### Optional Anki

Q: Kafka alternative for large files?
A: Store file externally and send a reference event.

</details>

<a id="kf-trap-004"></a>

<details>
<summary><strong>KF-TRAP-004. Why are random keys, one-partition topics and excessive partitions common Kafka traps?</strong></summary>

#### Short answer

Random keys break ordering, one partition caps throughput, and too many partitions increase overhead.

#### Interview answer

Keys should match ordering and distribution needs. Random keys distribute load but lose per-entity order. One partition gives simple ordering but prevents parallel consumption. Excessive partitions increase broker metadata, file handles, rebalances and recovery cost.

#### Deep dive

Partitioning is a domain design decision, not only a scaling knob.

#### Production angle

Review key cardinality, partition count and expected consumer concurrency before creating production topics.

#### Traps / caveats

- More partitions do not fix low downstream capacity.
- One partition is rarely acceptable for high-volume topics.

#### Optional Anki

Q: What do random keys risk?
A: Losing per-entity ordering.

</details>

<a id="kf-trap-005"></a>

<details>
<summary><strong>KF-TRAP-005. Why are weak schema evolution and non-idempotent consumers dangerous?</strong></summary>

#### Short answer

They turn normal Kafka behavior like rolling deploys, retries and replay into production failures.

#### Interview answer

Schemas evolve while old and new services coexist. Without compatibility, consumers break. Kafka also delivers records at least once in many designs, so non-idempotent consumers can double-charge, duplicate emails or corrupt projections.

#### Deep dive

Schema compatibility and idempotency are not advanced polish; they are baseline event-driven correctness.

#### Production angle

Use schema checks, tolerant readers, event IDs, unique constraints and duplicate metrics.

#### Traps / caveats

- A compatible schema can still change business meaning.
- Idempotency must cover side effects, not just message parsing.

#### Optional Anki

Q: Why must Kafka consumers be idempotent?
A: Retries, rebalances and replay can process records more than once.

</details>

<a id="kf-trap-006"></a>

<details>
<summary><strong>KF-TRAP-006. Why are auto commit, swallowed exceptions and infinite retries dangerous?</strong></summary>

#### Short answer

They hide failure, skip work or block partitions indefinitely.

#### Interview answer

Auto commit can mark records as processed before business work is safe. Swallowed exceptions make failures invisible and may commit bad outcomes. Infinite retries can keep one poison message blocking a partition forever and overload dependencies.

#### Deep dive

A good consumer defines success, retryable failure, permanent failure, DLQ and commit policy explicitly.

#### Production angle

Make error paths observable with metrics, logs, DLQ ownership and alerts.

#### Traps / caveats

- "No errors in logs" can mean errors are swallowed.
- Infinite retry is not reliability; it is unbounded delay.

#### Optional Anki

Q: Why is auto commit risky?
A: It can commit offsets before business processing is complete.

</details>

<a id="kf-trap-007"></a>

<details>
<summary><strong>KF-TRAP-007. Why is treating exactly-once as a magic end-to-end guarantee dangerous?</strong></summary>

#### Short answer

Kafka exactly-once has scope; it does not automatically make external side effects exactly once.

#### Interview answer

Kafka transactions help with Kafka-to-Kafka workflows. They do not include ordinary database updates, HTTP calls, emails or payment provider operations. Those side effects still need idempotency, constraints and reconciliation.

#### Deep dive

The hard part is often unknown outcome: a call timed out, but the external system may have applied it. Kafka cannot solve that alone.

#### Production angle

For critical workflows, design around business idempotency keys and reconciliation, not slogans.

#### Traps / caveats

- Exactly-once producer settings do not make consumers idempotent.
- Offset commits do not roll back external systems.

#### Optional Anki

Q: Kafka EOS does not cover what?
A: External side effects like DB writes or payment API calls.

</details>

<a id="kf-trap-008"></a>

<details>
<summary><strong>KF-TRAP-008. Why can DLQs, consumer lag alerts and shared consumer group IDs hide production problems?</strong></summary>

#### Short answer

They can make the main pipeline look healthy while work is skipped, delayed or consumed by the wrong service.

#### Interview answer

A DLQ lets the main consumer continue, but failed records still need ownership and reprocessing. Lag alerts based only on record count can miss old or stuck business events. Shared group IDs can cause services to steal partitions from each other, making messages appear missing.

#### Deep dive

These are observability and ownership traps. Kafka may be operating correctly while the business flow is broken.

#### Production angle

Alert on DLQ growth, oldest event age, retry backlog and unexpected consumer group members. Give each service a unique group ID.

#### Traps / caveats

- A DLQ is not a fix; it is a quarantine.
- Lag of zero can coexist with many failed DLQ records.

#### Optional Anki

Q: Why is shared consumer group ID dangerous?
A: Different services can split partitions and miss records they expected to receive.

</details>
