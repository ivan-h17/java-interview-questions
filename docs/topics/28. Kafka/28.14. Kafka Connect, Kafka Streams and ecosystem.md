# Kafka Connect, Kafka Streams and ecosystem

---

<a id="kf-eco-001"></a>

<details>
<summary><strong>KF-ECO-001. When would you use Kafka Connect instead of writing a custom producer or consumer?</strong></summary>

#### Short answer

Use Kafka Connect for standard data movement between Kafka and external systems when an existing connector fits.

#### Interview answer

Kafka Connect is good for source and sink integration: databases, object storage, search indexes, data warehouses and CDC pipelines. It avoids custom boilerplate for offsets, retries, scaling and connector lifecycle. Custom code is better when business logic is complex.

#### Deep dive

Connect is infrastructure for data integration, not a replacement for domain-specific processing. A connector should not become a hidden business service.

#### Production angle

Operate connectors with monitoring, DLQ/error policy, schema management and capacity planning.

#### Traps / caveats

- A connector can still corrupt downstream data if configured badly.
- Existing connector quality varies.

#### Optional Anki

Q: Kafka Connect is mainly for what?
A: Moving data between Kafka and external systems.

</details>

<details>
<summary><strong>KF-ECO-002. How do source connectors, sink connectors, tasks and offsets work at a high level?</strong></summary>

#### Short answer

Source connectors write external data into Kafka; sink connectors write Kafka data to external systems; tasks do the parallel work and track offsets.

#### Interview answer

A connector defines the integration. Tasks are the runnable units that do the actual copying in parallel. Source connectors track source offsets so they know what was already imported. Sink connectors track Kafka offsets as they write to the target system.

#### Deep dive

Offsets are connector-specific and must match the external system's semantics. For databases, that might be log position; for files, it might be file and position.

#### Production angle

Monitor task failures, offset progress, connector restarts and target-system write errors.

#### Traps / caveats

- Task parallelism is limited by connector and source/sink capabilities.
- Offset tracking does not remove the need for idempotent sink behavior.

#### Optional Anki

Q: What is a Kafka Connect task?
A: A parallel worker unit for connector data movement.

</details>

<details>
<summary><strong>🧠 KF-ECO-003. What are the risks of CDC-based event publishing with Debezium or similar tools?</strong></summary>

#### Short answer

CDC reliably captures database changes, but can expose database shape, emit low-level changes and require careful ordering, schema and snapshot handling.

#### Interview answer

Debezium reads database change logs and publishes changes to Kafka. It is powerful for Outbox relays and data replication. Risks include coupling consumers to table schemas, handling snapshots, deletes, schema changes, transaction ordering and noisy updates that are not meaningful business events.

#### Deep dive

CDC is often best when paired with an Outbox table containing intentional event records. Publishing raw table changes as domain events can leak internals and break consumers during migrations.

#### Production angle

Monitor connector lag, replication slot/log growth, snapshot status and schema compatibility.

#### Traps / caveats

- Raw CDC is not automatically a good domain event contract.
- Connector downtime can create database log retention pressure.

#### Optional Anki

Q: Safer CDC event pattern?
A: CDC over an intentional Outbox table.

</details>

<details>
<summary><strong>KF-ECO-004. When would you use Kafka Streams instead of plain consumers?</strong></summary>

#### Short answer

Use Kafka Streams for stateful stream processing, joins, aggregations, windowing and Kafka-to-Kafka transformations.

#### Interview answer

Plain consumers are fine for simple message handling. Kafka Streams adds a processing model for transformations, repartitioning, state stores, joins and fault-tolerant local state. It is useful when the output is another Kafka topic or materialized stream state.

#### Deep dive

Kafka Streams runs inside your application process, unlike an external cluster framework. That makes deployment familiar for Java teams but still requires state, rebalance and changelog understanding.

#### Production angle

Use it when stream-processing semantics matter more than hand-coded consumer loops.

#### Traps / caveats

- Kafka Streams is not needed for every consumer.
- Stateful topologies require careful testing and monitoring.

#### Optional Anki

Q: What does Kafka Streams add over plain consumers?
A: Stateful stream-processing primitives.

</details>

<details>
<summary><strong>🧠 KF-ECO-005. What are KStreams, KTables, state stores, changelog topics and windowed aggregations?</strong></summary>

#### Short answer

They are Kafka Streams concepts for event streams, latest-state tables, local state durability and time-bounded aggregation.

#### Interview answer

A `KStream` represents a stream of events. A `KTable` represents a changelog-backed table of latest values by key. State stores hold local processing state. Changelog topics back up that state to Kafka. Windowed aggregations group records by time windows.

#### Deep dive

These concepts let applications compute counts, joins, projections and rolling metrics while recovering state after restarts.

#### Production angle

Stateful stream apps need enough disk, changelog retention, standby/recovery planning and topology compatibility during deploys.

#### Traps / caveats

- Repartitioning changes data flow and topic usage.
- Windowing depends on event time, processing time and late-event policy.

#### Optional Anki

Q: What backs up Kafka Streams state stores?
A: Changelog topics.

</details>

<a id="kf-eco-006"></a>

<details>
<summary><strong>🧠 KF-ECO-006. What are MirrorMaker and cross-cluster replication used for?</strong></summary>

#### Short answer

They replicate topics between Kafka clusters for migration, disaster recovery, regional distribution or data sharing.

#### Interview answer

Cross-cluster replication copies records from one Kafka cluster to another. It can support data center migration, active/passive disaster recovery, regional analytics or sharing selected topics between environments.

#### Deep dive

Replication across clusters introduces lag, offset translation, topic naming, conflict and failover questions. It is not the same as synchronous multi-region consistency.

#### Production angle

Define RPO/RTO, failover procedure, consumer offset strategy and which cluster is authoritative.

#### Traps / caveats

- Bidirectional replication can create loops or conflicts.
- Replicated offsets and consumer failover need planning.

#### Optional Anki

Q: What is cross-cluster replication for?
A: Copying Kafka data between clusters for DR, migration or regional use.

</details>

<details>
<summary><strong>KF-ECO-007. How do you decide between plain consumers, Kafka Streams and Kafka Connect?</strong></summary>

#### Short answer

Use plain consumers for business handling, Kafka Streams for stream processing, and Kafka Connect for standard data integration.

#### Interview answer

If the service consumes events and performs domain actions, a plain consumer or Spring Kafka listener is usually enough. If it transforms streams, joins, aggregates or maintains state, Kafka Streams fits. If it moves data to or from external systems with little business logic, Kafka Connect fits.

#### Deep dive

The decision should minimize custom infrastructure code without hiding business logic in the wrong tool.

#### Production angle

Consider team expertise, monitoring, deployment model, state management and failure handling before choosing.

#### Traps / caveats

- Do not write custom connectors when a mature connector already exists.
- Do not force business workflows into Connect transformations.

#### Optional Anki

Q: Which Kafka tool is best for standard data movement?
A: Kafka Connect.

</details>
