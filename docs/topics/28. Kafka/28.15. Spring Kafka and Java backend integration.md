# Spring Kafka and Java backend integration

<a id="kf-spring-001"></a>

<details>
<summary><strong>KF-SPRING-001. What are the main Spring Kafka components a backend engineer should know?</strong></summary>

#### Short answer

Know `KafkaTemplate`, `@KafkaListener`, listener containers, serializers/deserializers, acknowledgment modes, error handlers and transaction support.

#### Interview answer

`KafkaTemplate` is used to send records. `@KafkaListener` receives records through listener containers. Containers manage polling, concurrency, commits and error handling. Configuration defines brokers, group IDs, serializers, deserializers, retries and security.

#### Deep dive

Spring Kafka wraps the Kafka client, but the same Kafka concepts still apply: partitions, offsets, groups, rebalances, retries and idempotency.

#### Production angle

Teams should understand the container settings they rely on, because the annotation still uses normal Kafka consumer semantics.

#### Traps / caveats

- Spring abstractions do not remove Kafka delivery semantics.
- Defaults may be wrong for business-critical consumers.

#### Optional Anki

Q: What is `KafkaTemplate` used for?
A: Sending Kafka records from Spring applications.

</details>

<a id="kf-spring-002"></a>

<details>
<summary><strong>KF-SPRING-002. How do you send records and handle send success or failure with `KafkaTemplate`?</strong></summary>

#### Short answer

Use `KafkaTemplate` to send asynchronously and handle the returned future or callback result.

#### Interview answer

`KafkaTemplate.send()` sends a record and returns an async result. The application should handle success for observability and failure for retry, request failure, Outbox fallback or alerting. Important events should not ignore send failures.

#### Deep dive

The send can fail due to serialization, authorization, timeout, buffer exhaustion, unknown topic or broker problems. Some failures are retryable; some are configuration or data bugs.

#### Production angle

Add metrics and logs with correlation IDs. For DB-related business events, prefer Outbox over relying only on request-thread send success.

#### Traps / caveats

- Fire-and-forget hides publish failures.
- Blocking on every send can destroy throughput.

#### Optional Anki

Q: What should you not ignore when using `KafkaTemplate.send()`?
A: The asynchronous failure result.

</details>

<a id="kf-spring-003"></a>

<details>
<summary><strong>KF-SPRING-003. How does `@KafkaListener` container concurrency relate to partition count?</strong></summary>

#### Short answer

Listener concurrency creates multiple consumer threads, but useful parallelism for a topic is still limited by partition count.

#### Interview answer

If a listener has concurrency `4`, Spring can run four consumer instances in the same group. For one topic with two partitions, only two will receive work. For topics with enough partitions, concurrency can increase parallel consumption.

#### Deep dive

Concurrency must also respect downstream capacity. More listener threads may create more database writes, HTTP calls and transaction load.

#### Production angle

Size concurrency using partition count, processing cost, DB pool size and lag SLOs. Monitor idle consumers and downstream saturation.

#### Traps / caveats

- Increasing concurrency above partition count does not help.
- More concurrency can increase duplicate impact during rebalances.

#### Optional Anki

Q: What caps useful listener concurrency for one topic?
A: Number of partitions.

</details>

<a id="kf-spring-004"></a>

<details>
<summary><strong>KF-SPRING-004. How do Spring Kafka acknowledgment modes affect offset commits?</strong></summary>

#### Short answer

Ack modes define when the listener container commits offsets relative to records, batches, time/count thresholds or manual acknowledgment.

#### Interview answer

Spring Kafka can commit automatically after records or batches, periodically, or when the listener manually acknowledges. Manual modes give business code more control, which is useful when commits must happen only after safe processing or DLQ handling.

#### Deep dive

Ack mode is part of delivery semantics. If offsets are committed before database work is safe, messages can be lost from the business perspective. If committed after, duplicates are possible and must be safe.

#### Production angle

For critical consumers, review ack mode together with transaction boundaries, error handler and idempotency design.

#### Traps / caveats

- Acking a record is not the same as committing a database transaction.
- Manual ack requires disciplined error paths.

#### Optional Anki

Q: Why use manual ack mode?
A: To control offset commits after safe processing.

</details>

<a id="kf-spring-005"></a>

<details>
<summary><strong>🧠 KF-SPRING-005. How do `DefaultErrorHandler`, `DeadLetterPublishingRecoverer` and `@RetryableTopic` fit together?</strong></summary>

#### Short answer

They provide Spring Kafka mechanisms for retries, recovery and publishing failed records to dead-letter topics.

#### Interview answer

`DefaultErrorHandler` handles listener exceptions with configured backoff and recovery. `DeadLetterPublishingRecoverer` can publish failed records to a dead-letter topic after retries are exhausted. `@RetryableTopic` supports non-blocking retry through retry topics with delayed attempts.

#### Deep dive

Blocking error handlers preserve partition order better but can block progress. Retry topics let the main consumer move on but can change ordering. The choice should match business semantics.

#### Production angle

Configure retry count, backoff, DLT naming, headers, error classification and monitoring. Test failure paths explicitly.

#### Traps / caveats

- Default behavior may not match your commit and DLQ policy.
- Retry topics need monitoring as real backlog.

#### Optional Anki

Q: What publishes failed records to DLT in Spring Kafka?
A: `DeadLetterPublishingRecoverer`.

</details>

<a id="kf-spring-006"></a>

<details>
<summary><strong>KF-SPRING-006. How should deserialization errors be handled in Spring Kafka?</strong></summary>

#### Short answer

Configure deserialization error handling so bad payloads can be logged, routed to DLT or skipped according to policy.

#### Interview answer

Deserialization can fail before the listener method receives a domain object. Spring Kafka provides error-handling deserializer patterns so the listener/container can capture the failure and route the original record to a DLT with useful metadata.

#### Deep dive

Without proper configuration, a poison payload can repeatedly fail at deserialization and block the partition. The handler must preserve enough original data for triage while avoiding sensitive logging.

#### Production angle

Track deserialization failures separately because they often signal schema rollout or producer bugs.

#### Traps / caveats

- The listener may never be called for a deserialization error.
- Blindly dropping malformed records can hide contract breakage.

#### Optional Anki

Q: Why are deserialization errors special?
A: They can happen before listener business code runs.

</details>

<a id="kf-spring-007"></a>

<details>
<summary><strong>🧠 KF-SPRING-007. How do Spring Kafka transactions interact with database transactions?</strong></summary>

#### Short answer

They are separate transaction systems unless explicitly coordinated; `@Transactional` does not automatically make DB and Kafka atomic together.

#### Interview answer

Spring can manage database transactions and Kafka producer transactions, but a normal local DB transaction and a Kafka transaction are different resources. Spring can synchronize transaction managers in some designs, but that is not the same as simple, default, end-to-end atomicity and is rarely the simplest microservice choice.

#### Deep dive

If a service must update a DB and publish an event reliably, Transactional Outbox is usually simpler and more robust. Kafka transactions are stronger for Kafka-to-Kafka workflows.

#### Production angle

Review code that publishes inside DB transactions. Make sure event publication only reflects committed state.

#### Traps / caveats

- Publishing before DB commit can emit rolled-back state.
- Publishing after DB commit can be lost if the service crashes.

#### Optional Anki

Q: Common solution for DB transaction plus Kafka publish?
A: Transactional Outbox.

</details>

<a id="kf-spring-008"></a>

<details>
<summary><strong>KF-SPRING-008. How would you implement Transactional Outbox in a Spring Boot service?</strong></summary>

#### Short answer

Write business data and an outbox row in one DB transaction, then publish outbox rows asynchronously to Kafka.

#### Interview answer

Inside a Spring `@Transactional` service method, persist the domain change and an outbox record containing event type, aggregate ID, payload, headers and status. A scheduler, worker or CDC connector reads unsent rows, publishes to Kafka and marks them sent or retries.

#### Deep dive

The relay must be idempotent because it may publish and crash before marking sent. Consumers must also tolerate duplicate events.

#### Production angle

Monitor outbox table size, oldest unsent age, publish errors and retry count. Add cleanup for sent records.

#### Traps / caveats

- Outbox does not remove the need for consumer idempotency.
- Polling relay without indexes can overload the database.

#### Optional Anki

Q: What is written in the same transaction in Outbox?
A: Business state and outbox event row.

</details>

<a id="kf-spring-009"></a>

<details>
<summary><strong>KF-SPRING-009. How should a Spring service publish domain events after a database transaction commits?</strong></summary>

#### Short answer

For reliable publication, prefer Outbox; for lightweight local reactions, transaction-after-commit hooks can be used carefully.

#### Interview answer

If the event is business-critical, write it to an outbox in the same transaction and publish later. If it is non-critical or local, Spring transaction synchronization or transactional event listeners can run after commit, but a crash after commit before publish can still lose the event.

#### Deep dive

After-commit hooks solve the "published before rollback" problem, but not the "crashed before publish" problem. That is why Outbox remains the reliability pattern.

#### Production angle

Classify events by criticality. Audit, payment and integration events usually need durable outbox.

#### Traps / caveats

- `@TransactionalEventListener(AFTER_COMMIT)` is not a durable queue.
- Publishing from inside a transaction can expose uncommitted state.

#### Optional Anki

Q: What risk remains with after-commit publication?
A: Crash after DB commit before Kafka publish.

</details>

<a id="kf-spring-010"></a>

<details>
<summary><strong>KF-SPRING-010. How do you test Kafka producers and listeners in Spring Boot?</strong></summary>

#### Short answer

Unit test business logic separately, then integration test Kafka wiring with real broker behavior using Testcontainers or Embedded Kafka.

#### Interview answer

Producer tests should verify topic, key, headers, payload and error behavior. Listener tests should verify deserialization, processing, commits, retries, DLQ and idempotency. For realistic integration, Testcontainers Kafka is often closer to production than pure mocks.

#### Deep dive

Mocks are useful for logic, but they do not catch serialization, group ID, topic, offset or error-handler configuration issues.

#### Production angle

Use unique topic/group names per test or clean state carefully. Avoid `Thread.sleep()`; use Awaitility or polling assertions.

#### Traps / caveats

- Tests that only call listener methods miss container behavior.
- Shared consumer groups make tests flaky.

#### Optional Anki

Q: What should Kafka integration tests include?
A: Serialization, broker interaction, listener container and failure paths.

</details>

<a id="kf-spring-011"></a>

<details>
<summary><strong>KF-SPRING-011. How do you configure group IDs, serializers and deserializers in Spring Boot?</strong></summary>

#### Short answer

Configure them through Spring Boot Kafka properties or custom producer/consumer factories.

#### Interview answer

Spring Boot exposes `spring.kafka.*` properties for bootstrap servers, security, producer serializers, consumer deserializers, group ID and listener behavior. For advanced cases, define `ProducerFactory`, `ConsumerFactory`, `KafkaTemplate` or listener container factory beans.

#### Deep dive

Group IDs should be stable and unique to the consuming service. Serializers/deserializers should match the event format and schema strategy.

#### Production angle

Keep environment-specific config externalized and avoid accidental group ID reuse across services or tests.

#### Traps / caveats

- Random group IDs in production cause replay from reset policy.
- Wrong deserializer can create poison-message loops.

#### Optional Anki

Q: What should a production consumer group ID represent?
A: A stable consuming application identity.

</details>

<a id="kf-spring-012"></a>

<details>
<summary><strong>KF-SPRING-012. How do you propagate tracing or correlation IDs and avoid blocking listener threads?</strong></summary>

#### Short answer

Put trace/correlation context in headers and keep listener work bounded, offloading carefully only with safe offset handling.

#### Interview answer

The producer should add correlation or trace headers. The listener extracts them into logging/tracing context and includes them in downstream calls or produced events. Listener threads should avoid long blocking work; use bounded timeouts, smaller batches, pause/resume or controlled worker pools.

#### Deep dive

If work is offloaded asynchronously, commits must still reflect completed processing. Otherwise the consumer may commit before side effects are done.

#### Production angle

Use MDC/tracing cleanup to avoid leaking context between records. Monitor listener processing time and executor queues.

#### Traps / caveats

- ThreadLocal context does not automatically cross async boundaries.
- Async handoff can break commit semantics if not designed carefully.

#### Optional Anki

Q: Where should Kafka tracing context travel?
A: In record headers.

</details>
