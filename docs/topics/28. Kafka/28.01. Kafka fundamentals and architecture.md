# Kafka fundamentals and architecture

---

<a id="kf-fund-001"></a>

<details>
<summary><strong>KF-FUND-001. What backend problems does Apache Kafka solve?</strong></summary>

#### Short answer

Kafka solves durable, high-throughput, asynchronous event distribution between systems.

#### Interview answer

Kafka is useful when backend services need to publish facts once and let multiple consumers process them independently. It provides durable storage, replay, fan-out, buffering during traffic spikes, and partitioned processing for scale.

#### Deep dive

Kafka is not just a queue. It stores records in partitioned logs for a configured retention period, so consumers can process at their own pace and even replay old data. That makes it useful for integration events, audit streams, analytics feeds, CDC pipelines, and asynchronous workflows.

#### Production angle

Kafka helps decouple slow or unavailable consumers from the request path, but it adds operational and correctness work: schemas, ordering, idempotency, retries, DLQs, monitoring, and capacity planning.

#### Traps / caveats

- Kafka does not automatically make distributed systems reliable.
- It is a poor replacement for clear service ownership and transaction boundaries.

#### Optional Anki

Q: What core backend problem does Kafka solve?
A: Durable asynchronous event distribution with replay and scalable consumption.

</details>

<a id="kf-fund-002"></a>

<details>
<summary><strong>KF-FUND-002. How is Kafka different from a traditional message queue and a publish-subscribe broker?</strong></summary>

#### Short answer

Kafka stores events in durable partitioned logs; consumers track their own offsets instead of messages disappearing after one consumer reads them.

#### Interview answer

In a traditional queue, a message is usually consumed by one worker and then removed or acknowledged. In basic pub-sub, messages are broadcast to subscribers but may not be retained for replay. Kafka combines durable log storage with consumer groups: one group can share work, while different groups can read the same topic independently.

#### Deep dive

Kafka's retention model is central. The broker does not delete a record just because one consumer processed it. This enables replay, backfills, multiple independent downstream systems, and late-joining consumers, as long as the data is still retained.

#### Production angle

This model is powerful for analytics and microservice integration, but retention and replay must be planned. Old events may be reprocessed, so consumers must be idempotent.

#### Traps / caveats

- Kafka can behave like a queue when one consumer group shares partitions, but it is not limited to queue semantics.
- Replay is only possible while records are retained.

#### Optional Anki

Q: What makes Kafka different from a normal queue?
A: Durable retained logs plus consumer-managed offsets.

</details>

<a id="kf-fund-003"></a>

<details>
<summary><strong>KF-FUND-003. What does it mean that Kafka is an append-only distributed log?</strong></summary>

#### Short answer

Records are appended to ordered partition logs and read by offset; existing records are not updated in place.

#### Interview answer

Each Kafka partition is an ordered log. Producers append records to the end, Kafka assigns offsets, and consumers read records sequentially by offset. The log is distributed because partitions are spread across brokers and replicated for availability.

#### Deep dive

This design gives Kafka high throughput because appends and sequential reads are efficient. It also creates a clear ordering scope: Kafka can preserve order within one partition, but not globally across all partitions of a topic.

#### Production angle

The append-only model supports replay and audit-like flows, but applications must handle duplicates, compaction behavior, retention limits, and schema evolution over time.

#### Traps / caveats

- Append-only does not mean records live forever.
- Ordering is per partition, not per topic unless the topic has one partition.

#### Optional Anki

Q: What is Kafka's ordering unit?
A: A partition log.

</details>

<a id="kf-fund-004"></a>

<details>
<summary><strong>KF-FUND-004. What are brokers, topics, partitions, producers and consumers, and how do they work together?</strong></summary>

#### Short answer

Producers write records to topic partitions on brokers; consumers read those partitions, usually as part of consumer groups.

#### Interview answer

A broker is a Kafka server. A topic is a named stream of records. A topic is split into partitions, and each partition is an ordered log. Producers send records to topics, usually with a key that selects a partition. Consumers read records from partitions and commit offsets to remember progress.

#### Deep dive

Partitions are the unit of ordering, parallelism and replication. A consumer group can process a topic in parallel because different consumers in the group receive different partitions. Multiple groups can read the same topic independently.

#### Production angle

Good Kafka design starts with partitions and keys. They determine throughput, ordering, lag behavior, and how safely a service can scale consumers.

#### Traps / caveats

- More consumers than partitions in one group does not increase parallelism.
- A bad key can create hot partitions and uneven load.

#### Optional Anki

Q: What is the unit of Kafka parallelism?
A: A partition.

</details>

<a id="kf-fund-005"></a>

<details>
<summary><strong>KF-FUND-005. What guarantees does Kafka provide out of the box, and what does it not guarantee?</strong></summary>

#### Short answer

Kafka provides durable partitioned storage, per-partition ordering, replication, and consumer offsets. It does not automatically provide end-to-end exactly-once business processing.

#### Interview answer

Kafka can durably store records, replicate partitions, preserve order inside a partition, and let consumers resume using committed offsets. With proper producer settings, it can reduce duplicate writes from retries. But applications still need idempotent handlers, safe database integration, retry policy, schema compatibility, and monitoring.

#### Deep dive

Many guarantees are scoped. Ordering is per partition. Producer idempotence covers producer-to-broker duplicate appends for a producer session, not arbitrary external side effects. Kafka transactions can make consume-process-produce workflows atomic inside Kafka, but they do not automatically include a normal database transaction.

#### Production angle

For payment, order or inventory flows, the real guarantee comes from combining Kafka settings with database constraints, idempotency keys, Outbox/Inbox patterns, and replay-safe processing.

#### Traps / caveats

- "Exactly once" is often misunderstood as end-to-end business exactly once.
- Committing offsets is not the same as successfully applying business side effects.

#### Optional Anki

Q: What ordering guarantee does Kafka provide?
A: Ordering within a single partition.

</details>

<a id="kf-fund-006"></a>

<details>
<summary><strong>KF-FUND-006. When would you choose Kafka instead of RabbitMQ, SQS or synchronous REST calls?</strong></summary>

#### Short answer

Choose Kafka for durable event streams, replay, high throughput, multiple independent consumers, and partitioned processing.

#### Interview answer

Kafka is a good fit when events are important data, multiple teams need the same stream, consumers may lag or replay, and throughput is high. RabbitMQ or SQS can be better for simpler task queues. REST or gRPC is better when the caller needs an immediate authoritative answer.

#### Deep dive

Kafka's strength is long-lived streams, not simple command dispatch. If the event history itself is valuable, Kafka is attractive. If you only need background jobs with simple acknowledgement semantics, a queue may be simpler. If business logic needs a yes/no decision before continuing, synchronous communication may be clearer.

#### Production angle

The decision should include operational ownership, retention, schema governance, failure handling, and how users experience eventual consistency.

#### Traps / caveats

- Do not choose Kafka just because it is scalable.
- Kafka can add unnecessary complexity to low-volume, tightly coupled workflows.

#### Optional Anki

Q: When is Kafka stronger than a basic queue?
A: When durable replayable streams and multiple independent consumers matter.

</details>

<a id="kf-fund-007"></a>

<details>
<summary><strong>KF-FUND-007. When is Kafka a poor fit?</strong></summary>

#### Short answer

Kafka is a poor fit for simple request-response, tiny low-volume integrations, unclear ownership, and workflows needing immediate consistency.

#### Interview answer

If a service needs a direct answer to complete a request, Kafka usually complicates the design. It is also risky when teams have not defined event ownership, schemas, retention, idempotency, replay behavior, and failure handling. A database table, REST endpoint, or simple queue may be enough.

#### Deep dive

Kafka makes asynchronous communication easy to start but hard to own well. Once events become contracts, changes require compatibility rules. Once consumers can replay, handlers must tolerate duplicates and old data. Once lag exists, users may see stale state.

#### Production angle

Avoid Kafka for "fire and forget" business-critical work unless failures are observable and recoverable. Avoid it when nobody owns the topic contract.

#### Traps / caveats

- Using Kafka to hide a slow synchronous dependency often just moves the bottleneck.
- Kafka should not be used before defining who owns events and consumers.

#### Optional Anki

Q: Name one poor fit for Kafka.
A: A workflow requiring an immediate authoritative response.

</details>

<a id="kf-fund-008"></a>

<details>
<summary><strong>KF-FUND-008. What trade-offs does Kafka introduce in a microservice architecture?</strong></summary>

#### Short answer

Kafka reduces temporal coupling and supports fan-out, but adds eventual consistency, contract management, replay safety and operational complexity.

#### Interview answer

Kafka lets producers publish events without waiting for every consumer. That helps with scalability, resilience and independent evolution. The trade-off is that flows become asynchronous: state may be temporarily inconsistent, debugging crosses service boundaries, and every consumer must handle duplicates, ordering assumptions and failures.

#### Deep dive

Kafka shifts complexity from request call stacks into event contracts and operational pipelines. You need schema compatibility, correlation IDs, lag alerts, DLQ policy, retry limits, replay plans and ownership of old events.

#### Production angle

Kafka works best when product behavior accepts delayed propagation and teams invest in observability and runbooks.

#### Traps / caveats

- Event-driven does not mean loosely coupled if event schemas expose producer internals.
- Without idempotency, retries and replay can corrupt business state.

#### Optional Anki

Q: What complexity does Kafka add to microservices?
A: Eventual consistency, contract governance, replay safety and operations.

</details>

<a id="kf-fund-009"></a>

<details>
<summary><strong>KF-FUND-009. What should a senior backend engineer clarify before introducing Kafka into a system?</strong></summary>

#### Short answer

Clarify the business need, event ownership, consistency model, keys, retention, schemas, failure handling, observability and operational ownership.

#### Interview answer

Before adding Kafka, I would ask what problem it solves compared with a synchronous call or queue. Then I would define event contracts, topic ownership, partition keys, ordering needs, expected throughput, retention, replay behavior, idempotency strategy, schema evolution, DLQ policy and monitoring.

#### Deep dive

Kafka creates durable shared interfaces. A bad topic or event design can become hard to change because consumers depend on it. Senior design work is mostly about making the implicit contract explicit.

#### Production angle

The launch checklist should include dashboards, alerts, consumer lag SLOs, replay runbooks, schema compatibility checks, capacity estimates and access control.

#### Traps / caveats

- Starting with technology before business semantics leads to generic topics nobody owns.
- Retention and replay policy must be decided before incidents happen.

#### Optional Anki

Q: What must be clear before introducing Kafka?
A: Ownership, contracts, consistency, keys, failure handling and operations.

</details>

<details>
<summary><strong>🧠 KF-FUND-010. How do the Kafka controller, metadata management and cluster quorum affect availability?</strong></summary>

#### Short answer

Kafka needs a reliable metadata control plane to know brokers, topics, partitions, leaders and configuration. If the quorum or controller is unhealthy, cluster management and failover suffer.

#### Interview answer

The controller coordinates cluster metadata changes such as partition leadership, broker membership and topic changes. Modern Kafka uses KRaft mode, where Kafka brokers/controllers manage metadata through a Raft-based quorum instead of relying on ZooKeeper. This metadata layer is critical for leader election and cluster availability.

#### Deep dive

Data movement and metadata decisions are different concerns. Producers and consumers rely on accurate metadata to find partition leaders. If the controller cannot make progress, existing data paths may continue for a while, but leadership changes, broker failures and administrative operations become risky.

#### Production angle

Platform teams monitor controller health, quorum health, broker membership, metadata propagation and leader election behavior. Backend engineers should understand symptoms: metadata errors, unavailable partitions, unstable leadership and client reconnect storms.

#### Traps / caveats

- KRaft removes ZooKeeper as a dependency, but it does not remove the need for a healthy quorum.
- Application symptoms may look like producer or consumer bugs when the metadata plane is unstable.

#### Optional Anki

Q: Why does Kafka need a controller/quorum?
A: To manage cluster metadata and coordinate leader and membership changes.

</details>
