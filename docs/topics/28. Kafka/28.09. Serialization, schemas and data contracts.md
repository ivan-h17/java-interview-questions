# Serialization, schemas and data contracts

---

<a id="kf-schema-001"></a>

<details>
<summary><strong>KF-SCHEMA-001. What are Kafka serializers and deserializers?</strong></summary>

#### Short answer

Serializers convert keys and values to bytes for Kafka; deserializers convert bytes back to application objects.

#### Interview answer

Kafka stores records as byte arrays. Producers use serializers for keys and values before sending. Consumers use matching deserializers when reading. Common formats include JSON, Avro, Protobuf and String/byte payloads.

#### Deep dive

Serialization is part of the event contract. A consumer must know the format, schema and compatibility rules. Header metadata may also influence deserialization, such as schema ID or content type.

#### Production angle

Bad deserialization can block consumers, create poison messages or send records to DLQ. Monitor deserialization failures separately from business errors.

#### Traps / caveats

- Changing a Java class is not the same as evolving a stable event contract.
- Deserializing directly into internal entities couples consumers to producer internals.

#### Optional Anki

Q: What does Kafka store as payload?
A: Bytes.

</details>

<details>
<summary><strong>KF-SCHEMA-002. What are the trade-offs between JSON, Avro and Protobuf for Kafka events?</strong></summary>

#### Short answer

JSON is simple and readable; Avro and Protobuf are schema-driven, compact and stronger for compatibility governance.

#### Interview answer

JSON is easy to inspect and works well for simple integrations, but can be verbose and weakly governed without JSON Schema. Avro is common with Schema Registry and supports schema evolution well. Protobuf is compact, strongly typed and widely used across languages, but has its own evolution rules.

#### Deep dive

The choice affects payload size, validation, compatibility checks, generated code, debugging and cross-team contracts.

#### Production angle

For high-volume or multi-team event streams, schema registry and compatibility checks usually matter more than human readability.

#### Traps / caveats

- JSON without schema still breaks consumers.
- Binary formats need good tooling for debugging and support.

#### Optional Anki

Q: Why use Avro or Protobuf over plain JSON?
A: Stronger schemas, compatibility checks and more compact payloads.

</details>

<details>
<summary><strong>KF-SCHEMA-003. What is Schema Registry, and why is it useful?</strong></summary>

#### Short answer

Schema Registry stores schemas and enforces compatibility between producers and consumers.

#### Interview answer

Schema Registry lets producers and consumers agree on message structure. Producers register or reference schemas, payloads can include schema IDs, and compatibility rules can reject breaking changes before they reach production.

#### Deep dive

It turns event schemas into managed contracts instead of scattered code assumptions. It is especially useful when many services and teams consume the same topics.

#### Production angle

Use schema compatibility checks in CI/CD and monitor registry errors. Treat schema changes like API changes.

#### Traps / caveats

- A registry does not define good business semantics by itself.
- Compatibility mode must match consumer rollout strategy.

#### Optional Anki

Q: What problem does Schema Registry solve?
A: Managed event schemas and compatibility governance.

</details>

<a id="kf-schema-004"></a>

<details>
<summary><strong>KF-SCHEMA-004. What do backward, forward and full schema compatibility mean?</strong></summary>

#### Short answer

Backward means new readers can read old data; forward means old readers can read new data; full means both.

#### Interview answer

Backward compatibility lets a new consumer version read messages written with the old schema. Forward compatibility lets old consumers read messages written with the new schema. Full compatibility supports both directions, which is useful during rolling deployments and mixed producer/consumer versions.

#### Deep dive

Compatibility rules depend on the format. Common safe moves include adding optional fields with defaults and avoiding changes that remove required data or change meanings.

#### Production angle

Rolling deploys often require old and new versions to coexist. Compatibility should be tested before producers publish new schema versions.

#### Traps / caveats

- A schema-compatible change can still be semantically breaking.
- Required fields are harder to evolve safely.

#### Optional Anki

Q: What is forward compatibility?
A: Old readers can read data produced with a new schema.

</details>

<a id="kf-schema-005"></a>

<details>
<summary><strong>KF-SCHEMA-005. What makes a schema change safe or breaking?</strong></summary>

#### Short answer

A safe change does not break existing consumers; a breaking change changes required structure, type or semantics that consumers depend on.

#### Interview answer

Adding an optional field is often safe. Removing a field, changing a field type, changing enum values, renaming fields without aliases, or changing the meaning of a field can break consumers. The exact answer depends on the schema format and compatibility mode.

#### Deep dive

Semantic compatibility is just as important as structural compatibility. A field named `amount` changing from cents to dollars may pass schema checks but break business logic.

#### Production angle

Review schemas like public APIs. Include sample messages, compatibility tests and consumer impact review.

#### Traps / caveats

- Compatibility tooling cannot detect every meaning change.
- Consumers may rely on fields the producer thinks are unused.

#### Optional Anki

Q: Give one often-safe schema change.
A: Adding an optional field with a sensible default.

</details>

<a id="kf-schema-006"></a>

<details>
<summary><strong>KF-SCHEMA-006. How should you evolve an event schema without breaking consumers?</strong></summary>

#### Short answer

Use backward-compatible changes, deploy consumers first when needed, keep old fields during migration, and remove only after deprecation.

#### Interview answer

I would add new optional fields, deploy consumers that can handle both old and new shapes, then update producers. If a breaking change is unavoidable, introduce a new event version or topic with a planned migration. Compatibility tests should run in CI.

#### Deep dive

Schema evolution is also a rollout problem. Old producers, new producers, old consumers and new consumers may coexist during deployments and replay.

#### Production angle

Track schema versions, compatibility failures and consumer adoption. Document deprecation timelines.

#### Traps / caveats

- Changing producer first can break old consumers.
- Replaying old events tests whether new consumers really support old schemas.

#### Optional Anki

Q: Typical safe rollout for schema expansion?
A: Deploy tolerant consumers, then deploy producers emitting the new field.

</details>

<a id="kf-schema-007"></a>

<details>
<summary><strong>🧠 KF-SCHEMA-007. Should event versioning live in the topic name, headers or payload?</strong></summary>

#### Short answer

Prefer schema-managed payload evolution for compatible changes; use new topics or explicit versions for truly different contracts.

#### Interview answer

Putting version in the payload is useful when business logic needs it. Headers can carry technical metadata like schema ID or content type. Topic names should not change for every compatible schema version, but a new topic can be appropriate for a breaking contract or different event stream.

#### Deep dive

Versioning should support rollout and replay. If consumers must branch on behavior, payload version may be clearer. If the format is managed by Schema Registry, schema ID may already identify structure.

#### Production angle

Avoid topic-name version churn for minor changes. It creates operational sprawl and migration complexity.

#### Traps / caveats

- Version in a header can be lost if tooling ignores headers.
- New topic per small change creates too many streams.

#### Optional Anki

Q: Should every compatible schema change create a new topic?
A: No.

</details>

<a id="kf-schema-008"></a>

<details>
<summary><strong>KF-SCHEMA-008. What are Kafka headers useful for?</strong></summary>

#### Short answer

Headers carry metadata about a record without mixing it into the business payload.

#### Interview answer

Headers are useful for correlation IDs, trace context, content type, schema metadata, producer identity, retry count, original topic/partition/offset for DLQ records, and tenant or routing metadata when appropriate.

#### Deep dive

Headers should support infrastructure and processing concerns. Business facts that are part of the event contract usually belong in the payload, where they are validated and documented.

#### Production angle

Consistent headers make tracing, DLQ triage and replay easier across services.

#### Traps / caveats

- Do not put essential business state only in headers if consumers may lose or ignore them.
- Do not log sensitive headers blindly.

#### Optional Anki

Q: Common Kafka header use?
A: Correlation or trace context.

</details>

<a id="kf-schema-009"></a>

<details>
<summary><strong>KF-SCHEMA-009. How should consumers handle unknown or optional fields?</strong></summary>

#### Short answer

Consumers should ignore unknown fields and handle missing optional fields with defaults or explicit fallback behavior.

#### Interview answer

Tolerant consumers make schema evolution safer. They should not fail just because a producer added a field. For optional fields, consumers should define default behavior and distinguish missing, null and empty values when business semantics require it.

#### Deep dive

This is part of the robustness principle for event contracts. However, ignoring unknown fields does not mean ignoring unknown event types if the consumer cannot safely process them.

#### Production angle

Tests should include old messages, new messages and messages with additional fields. Replays often expose consumers that only worked with current data.

#### Traps / caveats

- Default values can hide business ambiguity.
- Unknown enum values need explicit handling.

#### Optional Anki

Q: Why ignore unknown fields?
A: To allow compatible producer evolution.

</details>

<a id="kf-schema-010"></a>

<details>
<summary><strong>KF-SCHEMA-010. How do schema contracts relate to consumer-driven contracts?</strong></summary>

#### Short answer

Schemas define structural compatibility; consumer-driven contracts add expectations about what consumers actually need and how they interpret events.

#### Interview answer

Schema Registry can say a message shape is compatible, but consumers may depend on semantics: field meaning, allowed values, ordering and when events are emitted. Consumer-driven contracts capture those expectations and help producers avoid breaking real consumers.

#### Deep dive

For shared event streams, contract governance should include sample events, compatibility tests, semantic documentation and consumer ownership.

#### Production angle

Before changing a high-value event, identify consumers and run contract tests or staged rollout. Compatibility checks alone are not enough.

#### Traps / caveats

- Structural compatibility can still break business logic.
- Unknown consumers make safe evolution harder.

#### Optional Anki

Q: What does schema compatibility not fully capture?
A: Business semantics and consumer expectations.

</details>
