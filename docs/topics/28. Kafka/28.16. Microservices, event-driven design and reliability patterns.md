<a id="kf-arch-001"></a>

<details>
<summary><strong>KF-ARCH-001. What is the difference between an event and a command in a Kafka-based system?</strong></summary>

#### Short answer

An event is a fact that happened; a command is a request for something to happen.

#### Interview answer

`OrderCreated` is an event: it states that the order already exists. `ReserveInventory` is a command: it asks another component to act. Kafka is often best for publishing facts, while commands need clearer ownership, response expectations and failure handling.

#### Deep dive

Commands over Kafka can be valid in workflow systems, but they should be explicit. Calling every Kafka message an event can hide control flow and make ownership unclear.

#### Production angle

Events should be safe for multiple consumers to observe. Commands should usually have a single responsible handler and clear idempotency.

#### Traps / caveats

- A command named like an event creates confusion.
- Events should not ask consumers to do hidden work.

#### Optional Anki

Q: Event vs command?
A: Event is a fact; command is a request.

</details>

<details>
<summary><strong>KF-ARCH-002. What is the difference between event notification and event-carried state transfer?</strong></summary>

#### Short answer

Event notification says something changed; event-carried state transfer includes enough data for consumers to act without calling back.

#### Interview answer

An event notification might say `OrderUpdated` with only an ID. Consumers then call the order service for details. Event-carried state transfer includes relevant order fields in the event, reducing synchronous callbacks but increasing payload and contract responsibility.

#### Deep dive

Notifications keep events small but can create thundering herds and temporal coupling to the producer API. State transfer improves autonomy but requires schema governance and privacy review.

#### Production angle

Use state transfer when consumers need reliable snapshots for projections. Avoid including fields consumers do not need.

#### Traps / caveats

- Too little data turns async flows back into synchronous dependencies.
- Too much data exposes internals and sensitive fields.

#### Optional Anki

Q: What does event-carried state transfer reduce?
A: The need for consumers to call back to the producer.

</details>

<details>
<summary><strong>KF-ARCH-003. How do you define event ownership and stable contracts between teams?</strong></summary>

#### Short answer

Assign one owning service/team per event stream, document schema and semantics, and enforce compatibility rules.

#### Interview answer

The producing domain should own the event contract. Ownership means defining event meaning, schema, compatibility policy, retention, deprecation and support. Consumers should know whether the event is public integration contract or internal implementation detail.

#### Deep dive

Stable contracts include field meanings, required ordering, keys, examples, versioning and consumer expectations. Schema checks help, but semantic review is also needed.

#### Production angle

Add schema compatibility tests and a consumer notification process for high-value events.

#### Traps / caveats

- A shared topic with no owner becomes impossible to evolve.
- Exposing database schemas as events creates tight coupling.

#### Optional Anki

Q: Who should own an event contract?
A: The domain/service that publishes the business fact.

</details>

<a id="kf-arch-004"></a>

<details>
<summary><strong>KF-ARCH-004. How does Kafka change transaction boundaries and consistency between microservices?</strong></summary>

#### Short answer

Kafka shifts cross-service consistency from synchronous transactions to asynchronous eventual consistency.

#### Interview answer

A service commits its own local transaction, publishes an event, and other services update their own state later. This avoids distributed database transactions but means consumers can lag, fail or process duplicates. Business workflows must accept and expose intermediate states.

#### Deep dive

Kafka does not remove consistency decisions. It makes them explicit: what state is authoritative, when is stale data acceptable, and how are failed steps retried or compensated?

#### Production angle

Product behavior must handle pending states, reconciliation and alerts for stuck flows.

#### Traps / caveats

- Eventual consistency is not a license for inconsistent business rules.
- Hidden synchronous callbacks from consumers can reintroduce coupling.

#### Optional Anki

Q: Kafka usually replaces distributed transactions with what?
A: Local transactions plus eventual consistency patterns.

</details>

<a id="kf-arch-005"></a>

<details>
<summary><strong>🧠 KF-ARCH-005. How can Kafka be used in Saga workflows, and what are the limitations?</strong></summary>

#### Short answer

Kafka can carry Saga events or commands between steps, but Saga state, timeouts and compensation still need explicit design.

#### Interview answer

In choreography, services publish events and react to each other. In orchestration, a coordinator sends commands and tracks state. Kafka can transport those messages reliably, but it does not decide compensation, retries, deadlines or business state transitions.

#### Deep dive

Saga workflows need idempotent steps, correlation IDs, step status, timeout handling and a way to detect stuck flows. For complex workflows, a workflow engine may be better than hand-rolled event choreography.

#### Production angle

Monitor Saga age, stuck steps, compensation failures and duplicate commands.

#### Traps / caveats

- Pure choreography can become hard to understand and debug.
- Compensation is business logic, not automatic rollback.

#### Optional Anki

Q: What does Kafka provide for Saga?
A: Durable message transport, not workflow correctness.

</details>

<a id="kf-arch-006"></a>

<details>
<summary><strong>KF-ARCH-006. What is an Outbox relay, and how does it affect reliability?</strong></summary>

#### Short answer

An Outbox relay reads committed outbox records from a database and publishes them to Kafka.

#### Interview answer

The service writes business state and outbox rows atomically. The relay is responsible for delivering those rows to Kafka. It can be a polling worker, Debezium connector or another reliable publisher. This removes the DB-commit/Kafka-publish crash gap from the request path.

#### Deep dive

The relay can publish duplicates if it crashes after send but before marking a row sent. That is acceptable if events have IDs and consumers are idempotent.

#### Production angle

Monitor oldest unsent row, relay error rate, retry count and table growth.

#### Traps / caveats

- Relay lag becomes event publication lag.
- Outbox payloads still need schema compatibility.

#### Optional Anki

Q: What does an Outbox relay publish?
A: Durable outbox rows created in local DB transactions.

</details>

<details>
<summary><strong>🧠 KF-ARCH-007. How are Kafka-based integration, Event Sourcing and CQRS different?</strong></summary>

#### Short answer

Kafka integration publishes events between systems; Event Sourcing stores state as events; CQRS separates write and read models.

#### Interview answer

Using Kafka for integration means services emit events after state changes. Event Sourcing means the event log is the system of record for an aggregate. CQRS separates command handling from query models, and Kafka can help update projections.

#### Deep dive

Kafka can support Event Sourcing or CQRS, but using Kafka does not automatically mean you are doing either. Many systems simply use Kafka as an integration log.

#### Production angle

Do not claim Event Sourcing unless you can rebuild authoritative state from the event log and maintain event immutability and versioning.

#### Traps / caveats

- Kafka retention may conflict with Event Sourcing requirements.
- CQRS can be useful without Event Sourcing.

#### Optional Anki

Q: Does using Kafka mean Event Sourcing?
A: No.

</details>

<a id="kf-arch-008"></a>

<details>
<summary><strong>KF-ARCH-008. How do you handle ordering, duplicates, late events and out-of-order events across services?</strong></summary>

#### Short answer

Define ordering scope, use stable keys, include event IDs/versions, make consumers idempotent and handle stale events explicitly.

#### Interview answer

For ordering, choose keys like `orderId` or `accountId`. For duplicates, use idempotency keys or processed-event records. For late or out-of-order events, include version, sequence or effective time and reject or reconcile stale updates.

#### Deep dive

Global order is expensive and rarely needed. Many workflows can use per-entity ordering plus commutative or state-aware updates.

#### Production angle

Projection consumers should store last processed version or event time when business rules require monotonic updates.

#### Traps / caveats

- Timestamp order is not always causal order.
- Ignoring late events can be wrong if they represent valid business facts.

#### Optional Anki

Q: Common way to preserve per-entity order?
A: Partition by entity ID.

</details>

<a id="kf-arch-009"></a>

<details>
<summary><strong>KF-ARCH-009. When should you not use Kafka between two services?</strong></summary>

#### Short answer

Avoid Kafka when the caller needs an immediate answer, consistency must be synchronous, or the integration is simple and low-value.

#### Interview answer

If service A cannot proceed without service B's response, HTTP/gRPC may be clearer. If the workflow requires immediate validation or strong consistency, Kafka may add complex pending states. If there is only one low-volume consumer and no replay/fan-out need, a simpler integration may be better.

#### Deep dive

Kafka is often misused to avoid defining APIs or service boundaries. Asynchrony can hide failures until later, making user experience and operations harder.

#### Production angle

Use Kafka where delayed processing and replay are useful. Do not force it into every service interaction.

#### Traps / caveats

- Request-response over Kafka often recreates RPC with worse ergonomics.
- Kafka can increase coupling if event contracts are poor.

#### Optional Anki

Q: When is synchronous API better?
A: When an immediate authoritative response is required.

</details>
