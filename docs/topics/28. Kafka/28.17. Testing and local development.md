<a id="kf-test-001"></a>

<details>
<summary><strong>KF-TEST-001. How do you unit test Kafka message processing logic?</strong></summary>

#### Short answer

Keep business logic separate from Kafka infrastructure and unit test it with plain inputs and outputs.

#### Interview answer

The listener should be thin: deserialize, validate, call a service, acknowledge or throw. The service that handles the event can be unit tested with normal objects, mocks for dependencies and cases for duplicates, invalid state and retryable errors.

#### Deep dive

Unit tests should not need a broker. They verify business decisions, idempotency keys, state transitions and error classification.

#### Production angle

Good separation makes failure behavior easier to test before integration tests cover Kafka wiring.

#### Traps / caveats

- Testing only listener annotations misses business edge cases.
- Testing only business logic misses container commit/error behavior.

#### Optional Anki

Q: How to make Kafka consumer code unit-testable?
A: Keep listener thin and move processing into a separate service.

</details>

<a id="kf-test-002"></a>

<details>
<summary><strong>KF-TEST-002. How do you integration test Kafka producers and consumers?</strong></summary>

#### Short answer

Run a real Kafka broker in tests and verify serialization, topics, keys, headers, listener behavior and side effects.

#### Interview answer

For a producer, send an action and consume from the topic to verify payload, key and headers. For a consumer, produce a test record and verify database updates, emitted events, commits or DLQ behavior. Use isolated topics and groups.

#### Deep dive

Integration tests catch configuration problems: wrong serializers, group IDs, topic names, security settings, error handlers and listener container behavior.

#### Production angle

Tests should cover failure paths, not only happy paths.

#### Traps / caveats

- Shared topics/groups across tests cause flakiness.
- Asynchronous assertions need polling, not sleeps.

#### Optional Anki

Q: What do Kafka integration tests catch that unit tests miss?
A: Broker, serialization, container and configuration behavior.

</details>

<details>
<summary><strong>KF-TEST-003. When is Embedded Kafka enough, and when is Testcontainers better?</strong></summary>

#### Short answer

Embedded Kafka is useful for fast Spring tests; Testcontainers is better for production-like broker behavior and integration fidelity.

#### Interview answer

Embedded Kafka can be convenient for listener tests inside Spring. Testcontainers runs Kafka as a container and is closer to how services integrate in real environments. Use Testcontainers when testing real networking, Dockerized dependencies, compatibility or multiple infrastructure components.

#### Deep dive

The more the test depends on broker behavior, client config and environment, the more useful Testcontainers becomes.

#### Production angle

For CI confidence in Kafka plus PostgreSQL plus Schema Registry flows, Testcontainers is often the better fit.

#### Traps / caveats

- Embedded tests can pass while deployment config is broken.
- Container tests are slower and need good isolation.

#### Optional Anki

Q: What is Testcontainers better for?
A: Production-like integration tests with real infrastructure.

</details>

<a id="kf-test-004"></a>

<details>
<summary><strong>KF-TEST-004. How do you test retry, DLQ, idempotency, duplicates and ordering assumptions?</strong></summary>

#### Short answer

Inject controlled failures and duplicate/out-of-order records, then assert retries, DLQ writes and final business state.

#### Interview answer

For retry, make a dependency fail temporarily and verify retry count/backoff outcome. For DLQ, send an invalid record and verify DLT metadata. For idempotency, send the same event twice and assert one business effect. For ordering, send ordered and out-of-order events for the same key.

#### Deep dive

Testing should include commit behavior. A record sent to DLQ should not block the main partition forever unless that is the intended policy.

#### Production angle

These tests prevent the most expensive Kafka incidents: double charge, stuck partition and silent data loss.

#### Traps / caveats

- Testing duplicates only in memory misses database transaction behavior.
- Ordering tests must use keys that map to expected partitions.

#### Optional Anki

Q: How to test idempotent consumer behavior?
A: Process the same event twice and assert one business effect.

</details>

<a id="kf-test-005"></a>

<details>
<summary><strong>KF-TEST-005. How do you test schema compatibility?</strong></summary>

#### Short answer

Validate new schemas against compatibility rules and test consumers with old, new and unknown-field messages.

#### Interview answer

Schema changes should be checked in CI using Schema Registry compatibility or equivalent tooling. Consumers should have tests with previous schema versions, added optional fields and unknown enum/field cases.

#### Deep dive

Compatibility is both structural and semantic. Tests should include realistic sample events and business meaning, not just generated schemas.

#### Production angle

Run compatibility checks before producer deploys. Replays are a strong test of old-data compatibility.

#### Traps / caveats

- A schema-compatible field meaning change can still break consumers.
- Only testing current messages misses replay failures.

#### Optional Anki

Q: What message versions should consumers be tested with?
A: Old and new schema versions.

</details>

<a id="kf-test-006"></a>

<details>
<summary><strong>KF-TEST-006. How do you avoid flaky Kafka tests without relying on `Thread.sleep()`?</strong></summary>

#### Short answer

Use polling assertions with timeouts, unique topics/groups, clean state and deterministic test data.

#### Interview answer

Kafka tests are asynchronous, so fixed sleeps are either too slow or unreliable. Use Awaitility or similar polling to wait until a condition is true: record consumed, DB row inserted, DLQ message produced or metric updated.

#### Deep dive

Isolation matters. Use unique consumer group IDs, topic names or cleanup between tests. Avoid tests that depend on global offsets from previous runs.

#### Production angle

Reliable tests make it safe to refactor error handling and listener configuration.

#### Traps / caveats

- Sleeping can hide race conditions and slow CI.
- Reusing group IDs can make tests start from unexpected offsets.

#### Optional Anki

Q: Better than `Thread.sleep()` in async Kafka tests?
A: Polling assertions with a timeout.

</details>

<a id="kf-test-007"></a>

<details>
<summary><strong>🧠 KF-TEST-007. How do you test Kafka Streams topologies or Kafka migrations before production?</strong></summary>

#### Short answer

Use topology test drivers or isolated integration tests, then run migration rehearsals with production-like data samples.

#### Interview answer

Kafka Streams topologies can be tested with test drivers for deterministic input/output and state-store assertions. For migrations, create old and new topics/schemas, replay representative data, validate outputs, lag, ordering and rollback steps.

#### Deep dive

Migrations should test mixed versions, old data replay, schema compatibility and consumer behavior during cutover.

#### Production angle

For critical topics, rehearse migration in staging with realistic volume and a clear rollback plan.

#### Traps / caveats

- A topology test driver does not replace operational tests.
- Migration tests with tiny clean data miss poison records and old schemas.

#### Optional Anki

Q: What should Kafka migration tests include?
A: Representative old data, schema compatibility, cutover and rollback behavior.

</details>
