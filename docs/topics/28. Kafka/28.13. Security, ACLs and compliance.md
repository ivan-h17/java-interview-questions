# Security, ACLs and compliance

---

<a id="kf-sec-001"></a>

<details>
<summary><strong>🧠 KF-SEC-001. How do Kafka authentication, authorization, TLS, SASL and ACLs fit together?</strong></summary>

#### Short answer

TLS protects transport, authentication proves client identity, and authorization/ACLs decide what that identity can do.

#### Interview answer

Kafka can use TLS for encryption in transit and sometimes client certificate authentication. SASL mechanisms can authenticate clients with credentials or tokens. Once Kafka knows the principal, ACLs authorize operations such as read, write, create or describe on topics, groups and transactional IDs.

#### Deep dive

Security is layered. Encrypting traffic does not mean every service may read every topic. Authentication without least-privilege authorization still leaves broad access risk.

#### Production angle

Each service should have its own principal and narrowly scoped permissions. Rotate credentials and audit access.

#### Traps / caveats

- Shared Kafka credentials make auditing and least privilege difficult.
- TLS does not replace ACLs.

#### Optional Anki

Q: What do Kafka ACLs control?
A: Which authenticated principals can perform operations on Kafka resources.

</details>

<a id="kf-sec-002"></a>

<details>
<summary><strong>KF-SEC-002. How would you apply least privilege to Kafka topics and service principals?</strong></summary>

#### Short answer

Give each service only the topic, group and transactional permissions it needs.

#### Interview answer

A producer service should have write access only to topics it owns. A consumer should have read access to required topics and access to its own consumer group. Administrative operations should be separate from runtime service credentials.

#### Deep dive

Least privilege also applies to Schema Registry, DLQ topics, retry topics and transactional IDs. Sensitive topics should be isolated with stricter ACLs and auditing.

#### Production angle

Use separate principals per service and environment. Review permissions during service decommission and incident response.

#### Traps / caveats

- Wildcard topic permissions are convenient but risky.
- Sharing a consumer group ID between services can become both a correctness and security issue.

#### Optional Anki

Q: Why avoid shared Kafka principals?
A: They weaken least privilege and auditing.

</details>

<a id="kf-sec-003"></a>

<details>
<summary><strong>KF-SEC-003. How should producer and consumer credentials be managed in Spring Boot services?</strong></summary>

#### Short answer

Store credentials in a secrets manager or secure platform mechanism, inject them at runtime, and rotate them safely.

#### Interview answer

Kafka credentials should not be committed to Git or baked into images. Spring Boot configuration should read them from environment-specific secure sources such as Kubernetes secrets, Vault or cloud secret managers. Rotation should be tested without full redeploy surprises.

#### Deep dive

Credentials include SASL passwords, client certificates, truststores, keystores and Schema Registry credentials. File permissions and logs matter too.

#### Production angle

Avoid logging full Kafka configs because they can contain secrets. Monitor authentication failures after rotation.

#### Traps / caveats

- Plain environment variables can leak through debug tooling if not managed carefully.
- Certificate expiration can create sudden outages.

#### Optional Anki

Q: Where should Kafka credentials not live?
A: Source code or container images.

</details>

<a id="kf-sec-004"></a>

<details>
<summary><strong>KF-SEC-004. What are the risks of putting PII or sensitive data into Kafka events?</strong></summary>

#### Short answer

Sensitive events can be retained, replayed, copied to many consumers and hard to delete completely.

#### Interview answer

Kafka's durability and fan-out are risks for PII. Data may persist for retention duration, appear in DLQs, logs, backups, analytics sinks and consumer databases. Every consumer becomes part of the data exposure surface.

#### Deep dive

Data minimization matters. Prefer IDs or masked fields when consumers do not need raw sensitive values. If sensitive data is required, control ACLs, retention, encryption, logging and downstream propagation.

#### Production angle

Security review should include topic retention, consumer list, access audit, DLQ handling and deletion/redaction obligations.

#### Traps / caveats

- Redacting only the original topic may miss DLQs and sinks.
- Long retention can conflict with privacy requirements.

#### Optional Anki

Q: Why is PII risky in Kafka?
A: It is durable, replayable and fan-outs to many systems.

</details>

<a id="kf-sec-005"></a>

<details>
<summary><strong>🧠 KF-SEC-005. How do retention, immutability, deletion and redaction affect compliance?</strong></summary>

#### Short answer

Kafka's immutable retained logs make compliance deletion and redaction harder than in mutable databases.

#### Interview answer

Kafka is designed to append and retain records, not update individual fields in place. Retention can eventually delete data, and compaction/tombstones can remove keys in compacted topics, but neither is the same as immediate precise redaction across all copies.

#### Deep dive

Sensitive data may exist in replicated logs, backups, mirrors, DLQs, consumer stores and data lakes. Compliance design should avoid putting unnecessary sensitive values into events.

#### Production angle

Use short retention, tokenization, encryption, separate sensitive topics and strict ACLs where needed. Document deletion limits clearly.

#### Traps / caveats

- Tombstones only apply to compacted keyed records.
- Consumers may have already copied the data elsewhere.

#### Optional Anki

Q: Best compliance strategy for sensitive Kafka data?
A: Minimize or avoid sensitive data in events where possible.

</details>

<a id="kf-sec-006"></a>

<details>
<summary><strong>KF-SEC-006. How do you secure Schema Registry access?</strong></summary>

#### Short answer

Use authentication, authorization, TLS, environment separation and controlled schema-change permissions.

#### Interview answer

Schema Registry controls event contracts, so unauthorized schema changes can break consumers. Secure it with TLS, service credentials, limited read/write permissions and CI/CD-controlled schema registration where possible.

#### Deep dive

Consumers may need read access to schemas, while only owning producer teams or deployment pipelines should register new versions. Audit schema changes like API changes.

#### Production angle

Monitor compatibility failures and registry authentication errors. Keep registry availability in mind because clients may depend on it at startup or serialization time.

#### Traps / caveats

- Open schema write access can become a production-breaking path.
- Registry credentials are secrets too.

#### Optional Anki

Q: Why secure Schema Registry?
A: It controls shared event contracts.

</details>

<a id="kf-sec-007"></a>

<details>
<summary><strong>KF-SEC-007. How do you prevent unauthorized consumers from reading sensitive topics?</strong></summary>

#### Short answer

Use per-service principals, topic ACLs, network controls, encryption and audit logs.

#### Interview answer

Sensitive topics should have read permissions only for approved service principals. Consumer group permissions should also be scoped. Network access, TLS, credential rotation and audit logs help enforce and verify access.

#### Deep dive

Topic naming and separation matter. Mixing sensitive and non-sensitive events in one topic makes least privilege harder.

#### Production angle

Review access periodically and alert on unexpected principals or consumer groups.

#### Traps / caveats

- Filtering sensitive records in the consumer is not access control.
- Shared credentials make it hard to know who read data.

#### Optional Anki

Q: What is the main Kafka control for topic read access?
A: ACLs for authenticated principals.

</details>

<a id="kf-sec-008"></a>

<details>
<summary><strong>KF-SEC-008. How do you design multi-tenant Kafka topic access and safe logging?</strong></summary>

#### Short answer

Separate tenants or data classes when needed, include tenant context in keys/contracts, enforce ACLs, and avoid logging sensitive payloads.

#### Interview answer

For multi-tenant systems, decide whether tenants share topics or have isolated topics based on data sensitivity, throughput and operational cost. Access should be scoped so one tenant's service cannot read another tenant's data. Logs should include correlation and tenant identifiers only when safe, not raw payloads.

#### Deep dive

Shared topics need careful key design, quota planning and consumer authorization boundaries. Separate topics improve isolation but increase topic count and operations.

#### Production angle

Audit logs, DLQs and traces must follow the same data-safety rules as primary topics.

#### Traps / caveats

- Tenant ID in payload does not enforce isolation by itself.
- Debug logging full events can leak secrets.

#### Optional Anki

Q: What is safer than logging full Kafka payloads?
A: Log correlation IDs, event type and safe metadata.

</details>
