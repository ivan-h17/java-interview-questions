# Performance, throughput, latency and backpressure

---

<a id="kf-perf-001"></a>

<details>
<summary><strong>KF-PERF-001. What affects Kafka producer throughput and latency?</strong></summary>

#### Short answer

Producer performance depends on batching, compression, message size, partition count, acknowledgments, retries, network and broker health.

#### Interview answer

Throughput improves with larger batches, compression, async sends and enough partitions. Latency is affected by `linger.ms`, broker request queues, replication, `acks`, retries, payload size and network/TLS overhead. Durability settings can also add latency.

#### Deep dive

Producer tuning is a trade-off between efficient bulk sending and predictable per-message latency. High throughput systems often accept a small batching delay. Low-latency systems may send smaller batches but pay more overhead.

#### Production angle

Watch producer request latency, record send rate, batch size, compression ratio, errors, retries and buffer exhaustion.

#### Traps / caveats

- Optimizing producer throughput can simply move the bottleneck to consumers.
- Low average latency can hide bad p99 retry spikes.

#### Optional Anki

Q: What producer features usually improve throughput?
A: Batching, compression and asynchronous sends.

</details>

<a id="kf-perf-002"></a>

<details>
<summary><strong>KF-PERF-002. What affects Kafka consumer throughput?</strong></summary>

#### Short answer

Consumer throughput depends on partition parallelism, fetch settings, handler speed, commit strategy and downstream capacity.

#### Interview answer

A consumer group can process in parallel up to the number of assigned partitions. Throughput also depends on `max.poll.records`, fetch sizes, deserialization cost, business logic, database/API latency, transaction cost and offset commit overhead.

#### Deep dive

Kafka may deliver records quickly while the application remains slow. In many Java services, the bottleneck is not Kafka but database writes, HTTP calls, locking, CPU-heavy mapping or small connection pools.

#### Production angle

Measure processing time separately from poll/fetch time. Track per-partition lag and downstream saturation.

#### Traps / caveats

- Adding consumer threads beyond partition count does not help a single topic group.
- Faster consumption can overload downstream dependencies.

#### Optional Anki

Q: What caps consumer group parallelism for a topic?
A: Partition count.

</details>

<a id="kf-perf-003"></a>

<details>
<summary><strong>KF-PERF-003. What affects end-to-end latency in a Kafka-based flow?</strong></summary>

#### Short answer

End-to-end latency includes producer delay, broker replication/storage, consumer lag, processing time and downstream side effects.

#### Interview answer

A record's total delay starts before Kafka receives it and ends only when the business effect is visible. Batching, compression, broker load, replication, partition backlog, consumer polling, retries, processing time and database/API calls all contribute.

#### Deep dive

Kafka metrics alone are insufficient. A topic can have low broker latency but high business latency because consumers are slow or retrying.

#### Production angle

Propagate event timestamps and correlation IDs. Measure publish-to-consume, consume-to-processed and total business completion time.

#### Traps / caveats

- Offset lag is not the same as end-to-end latency.
- Producer timestamp may not equal business event time.

#### Optional Anki

Q: What is end-to-end latency in Kafka flow?
A: Time from event creation/publication to completed consumer business effect.

</details>

<a id="kf-perf-004"></a>

<details>
<summary><strong>KF-PERF-004. How does partition count affect throughput, ordering and consumer concurrency?</strong></summary>

#### Short answer

More partitions allow more parallelism, but ordering remains only within each partition and operational overhead increases.

#### Interview answer

Each partition can be consumed by one consumer in a group, so partition count caps concurrency. More partitions can increase throughput and lag recovery speed. But if related records are split across partitions, cross-partition ordering is not guaranteed.

#### Deep dive

Partition count is both a scaling and correctness decision. Key choice determines which records share a partition. Increasing partitions later can alter key mapping for new records.

#### Production angle

Choose partition count with expected growth and ordering scope in mind. Avoid treating it as an easy runtime knob.

#### Traps / caveats

- More partitions do not preserve global order.
- More partitions can make rebalances and broker operations heavier.

#### Optional Anki

Q: More partitions give what main benefit?
A: More parallelism.

</details>

<a id="kf-perf-005"></a>

<details>
<summary><strong>KF-PERF-005. How do batch size, compression and message size affect performance?</strong></summary>

#### Short answer

Larger batches and compression improve efficiency, while large individual messages hurt latency, memory and broker/client load.

#### Interview answer

Batching reduces request overhead. Compression reduces network and disk usage, especially for repetitive payloads. But large messages increase memory pressure, fetch size requirements, retry cost and consumer processing time.

#### Deep dive

Kafka performs best with many reasonably sized records, not huge payloads. Oversized messages can force changes to producer, broker and consumer max-size settings and still create poor operational behavior.

#### Production angle

Track message size distribution, not only averages. A few very large records can cause p99 latency and consumer failures.

#### Traps / caveats

- Increasing max message size everywhere treats the symptom, not the design problem.
- Compression saves bytes but costs CPU.

#### Optional Anki

Q: Why are huge Kafka messages bad?
A: They increase memory, latency, retry and fetch pressure.

</details>

<a id="kf-perf-006"></a>

<details>
<summary><strong>KF-PERF-006. Why are very large Kafka messages risky, and what alternatives exist?</strong></summary>

#### Short answer

Large messages stress brokers and clients; store large payloads elsewhere and send references or compact summaries through Kafka.

#### Interview answer

Huge messages increase network usage, disk usage, memory allocation, fetch requirements, retry cost and failure blast radius. A common alternative is storing the blob in object storage or a database and publishing a Kafka event with metadata, URI, checksum and access rules.

#### Deep dive

Kafka is optimized for event streams, not file transfer. If consumers do not all need the full payload, sending it to every consumer wastes capacity.

#### Production angle

For documents, images or large exports, use Kafka to orchestrate processing, not to carry the full file.

#### Traps / caveats

- Pointer events need lifecycle management for the external object.
- Make sure consumers have permission and can handle missing referenced data.

#### Optional Anki

Q: Better pattern for huge payloads?
A: Store externally and publish a reference event.

</details>

<a id="kf-perf-007"></a>

<details>
<summary><strong>KF-PERF-007. How can a consumer apply backpressure with `pause()` and `resume()`?</strong></summary>

#### Short answer

A consumer can pause fetching from specific partitions while it drains work or waits for dependencies, then resume later.

#### Interview answer

`pause()` tells the consumer not to fetch more records from selected partitions. This helps when processing queues are full, a downstream dependency is overloaded, or a specific partition needs throttling. `resume()` restarts fetching.

#### Deep dive

The consumer must still poll to maintain group membership. Pausing does not remove the consumer from the group; it just controls fetching.

#### Production angle

Use pause/resume with metrics and limits. If paused too long, lag grows and retention risk increases.

#### Traps / caveats

- Do not stop polling while paused.
- Pause/resume is local flow control, not a full retry policy.

#### Optional Anki

Q: Does `pause()` remove a consumer from the group?
A: No. It stops fetching selected partitions.

</details>

<a id="kf-perf-008"></a>

<details>
<summary><strong>🧠 KF-PERF-008. How do `max.poll.records`, fetch settings and processing time affect consumer tuning?</strong></summary>

#### Short answer

They control how much data a consumer receives per poll and whether it can process that data within safe timing limits.

#### Interview answer

`max.poll.records` limits record count per poll. Fetch settings influence how much data the broker returns and how long it may wait to fill fetches. Processing time determines whether the consumer can poll again before `max.poll.interval.ms` and keep lag under control.

#### Deep dive

Large fetches improve throughput but can increase memory use and processing bursts. Small fetches reduce latency and memory but increase overhead. Tune based on handler p99 latency and downstream capacity.

#### Production angle

Look at poll interval, processing duration, records per poll, bytes per fetch, heap usage and connection pool saturation.

#### Traps / caveats

- Fetch tuning cannot fix slow business logic.
- Large batches complicate partial failure handling.

#### Optional Anki

Q: What should consumer batch tuning be based on?
A: Processing time, downstream limits and lag SLOs.

</details>

<a id="kf-perf-009"></a>

<details>
<summary><strong>KF-PERF-009. How do downstream database or API limits throttle Kafka consumers?</strong></summary>

#### Short answer

Consumers can only process as fast as their slowest required side effect.

#### Interview answer

If every message writes to PostgreSQL or calls an external API, that dependency becomes the throughput limit. Adding Kafka consumers can overload the database connection pool, increase lock contention, hit rate limits or create retry storms.

#### Deep dive

Kafka decouples ingestion from processing, but it does not remove downstream capacity constraints. Backpressure must be applied at the consumer and sometimes at the producer or business intake.

#### Production angle

Monitor DB pool usage, query latency, lock waits, API rate limits and retry rate together with Kafka lag.

#### Traps / caveats

- Scaling consumers horizontally can make the real bottleneck worse.
- Lag is often a symptom, not the root cause.

#### Optional Anki

Q: What happens if consumers exceed DB write capacity?
A: Lag, timeouts, retries and possible database overload.

</details>

<a id="kf-perf-010"></a>

<details>
<summary><strong>KF-PERF-010. How would you tune Kafka for high-throughput ingestion vs low-latency delivery?</strong></summary>

#### Short answer

High throughput favors batching and compression; low latency favors smaller waits, smaller payloads and predictable broker/consumer paths.

#### Interview answer

For high throughput, increase batching, use compression, ensure enough partitions and avoid synchronous per-record waits. For low latency, keep `linger.ms` low, avoid oversized batches, reduce unnecessary retries, keep payloads small and monitor p99 across producer, broker and consumer.

#### Deep dive

Both modes still need durability and correctness. Do not trade away `acks` or idempotency blindly. The right tuning depends on business SLOs.

#### Production angle

Run load tests with realistic message size, keys, consumer work and broker replication settings.

#### Traps / caveats

- Tuning producer only is incomplete.
- High throughput and low p99 latency can conflict.

#### Optional Anki

Q: What favors Kafka throughput?
A: Batching, compression, partitions and async sends.

</details>

<details>
<summary><strong>🧠 KF-PERF-011. How do you benchmark Kafka producers and consumers and separate broker-side from application-side bottlenecks?</strong></summary>

#### Short answer

Benchmark producers, brokers and consumers separately, then test the full flow with production-like payloads and dependencies.

#### Interview answer

I would first test raw Kafka throughput with simple producers/consumers, then add real serialization, business logic and downstream calls. Compare broker metrics such as request latency, disk, network and ISR with client metrics such as processing time, retries, buffer pressure and lag.

#### Deep dive

If a simple consumer keeps up but the application consumer lags, the bottleneck is likely application-side. If all consumers lag and broker request queues or disks are saturated, investigate cluster capacity.

#### Production angle

Use repeatable tests, fixed payload distributions, representative keys, real compression and realistic failure conditions.

#### Traps / caveats

- Benchmarks without downstream dependencies overstate capacity.
- Average throughput hides partition skew and p99 latency.

#### Optional Anki

Q: How to identify app-side Kafka bottleneck?
A: Compare raw client performance with real application processing metrics.

</details>
