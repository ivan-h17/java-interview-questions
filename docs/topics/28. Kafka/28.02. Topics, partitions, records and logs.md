# Topics, partitions, records and logs

---

<a id="kf-topic-001"></a>

<details>
<summary><strong>KF-TOPIC-001. What are Kafka topics, partitions and offsets, and why are offsets partition-local?</strong></summary>

#### Short answer

A topic is a named stream, a partition is an ordered shard of that stream, and an offset is a record position within one partition.

#### Interview answer

Kafka scales topics by splitting them into partitions. Each partition is an ordered log with monotonically increasing offsets. Offsets are partition-local because each partition is an independent sequence; offset `10` in partition `0` is unrelated to offset `10` in partition `1`.

#### Deep dive

This design lets Kafka spread a topic across brokers and consumers. It also means a consumer position is really a set of positions: one committed offset per assigned partition.

#### Production angle

When debugging lag or replaying data, always identify topic, partition and offset. A single offset number without a partition is ambiguous.

#### Traps / caveats

- There is no global topic offset.
- Ordering and replay are scoped to partitions.

#### Optional Anki

Q: Is a Kafka offset global across a topic?
A: No. It is local to a partition.

</details>

<a id="kf-topic-002"></a>

<details>
<summary><strong>KF-TOPIC-002. How are records stored and ordered inside a partition?</strong></summary>

#### Short answer

Records are appended to the end of a partition log and ordered by offset.

#### Interview answer

When a producer sends a record to a partition, Kafka appends it to that partition log and assigns the next offset. Consumers normally read in offset order. This gives Kafka strong ordering inside a partition, assuming the producer and retry settings do not reorder sends.

#### Deep dive

Kafka does not order records across partitions. If two records go to different partitions, their relative processing order depends on consumers, scheduling and broker behavior. For entity ordering, put related records under the same key so they land in the same partition.

#### Production angle

For order status, account balance or customer lifecycle events, define the ordering scope explicitly. Global ordering usually hurts scalability and is rarely needed.

#### Traps / caveats

- One partition gives simple ordering but caps parallelism.
- Multiple producers can still create semantic ordering problems if they publish competing event types.

#### Optional Anki

Q: How does Kafka order records?
A: By offset within a partition.

</details>

<a id="kf-topic-003"></a>

<details>
<summary><strong>KF-TOPIC-003. How do message keys and partitioners decide where records go?</strong></summary>

#### Short answer

The producer partitioner maps records to partitions, often by hashing the record key.

#### Interview answer

If a record has a key, the default behavior is to send the same key to the same partition while the partition count is unchanged. If a record has no key, the producer distributes records using its partitioning strategy. The key is therefore both a routing decision and often an ordering decision.

#### Deep dive

Partitioners can be customized, but that should be rare. Most backend systems use keys like `orderId`, `customerId` or `accountId` based on the required ordering and load distribution.

#### Production angle

A key choice affects hot partitions, consumer concurrency, replay behavior and how easy it is to reason about event order.

#### Traps / caveats

- Random keys destroy per-entity ordering.
- Low-cardinality keys can overload a few partitions.

#### Optional Anki

Q: What does a Kafka key usually control?
A: Partition routing and per-key ordering.

</details>

<a id="kf-topic-004"></a>

<details>
<summary><strong>KF-TOPIC-004. How should you choose a partition key for ordering, throughput and ownership?</strong></summary>

#### Short answer

Choose the smallest business key that matches the required ordering scope and has enough cardinality for balanced load.

#### Interview answer

If events must be processed in order per order, use `orderId`. If they must be ordered per customer, use `customerId`, but be aware that large customers can become hot keys. The key should match the invariant you need to protect, not just a convenient field.

#### Deep dive

Partition keys are a trade-off. Narrow keys improve distribution but may not preserve the desired order. Broad keys preserve more order but reduce parallelism and can create hot partitions.

#### Production angle

Validate key cardinality with real traffic distribution, not just average load. A few large tenants or customers can dominate traffic.

#### Traps / caveats

- Choosing `tenantId` may overload one partition for a large tenant.
- Changing partition count later can alter key-to-partition mapping.

#### Optional Anki

Q: Good Kafka partition key criteria?
A: Correct ordering scope plus enough cardinality for balanced partitions.

</details>

<a id="kf-topic-005"></a>

<details>
<summary><strong>KF-TOPIC-005. What is a hot partition, and how do you diagnose and fix it?</strong></summary>

#### Short answer

A hot partition receives much more traffic than others, limiting throughput and increasing lag for that partition.

#### Interview answer

I would compare per-partition produce rate, bytes, consumer lag and processing time. Then I would inspect keys: low-cardinality keys, one large tenant, or a default/null key can concentrate load. Fixes include better key design, splitting a heavy entity, adding routing logic, separate topics for heavy tenants, or redesigning ordering requirements.

#### Deep dive

Adding partitions alone may not fix a hot key because the same key still maps to one partition. If strict order is only needed within smaller substreams, you can shard by a composite key such as `customerId + bucket`.

#### Production angle

Hot partitions show up as uneven lag: one consumer is overloaded while others are idle.

#### Traps / caveats

- More consumers cannot help if only one partition is hot.
- Sharding a key can break ordering unless the business can tolerate it.

#### Optional Anki

Q: Why can a hot key limit Kafka throughput?
A: A key maps to one partition, so one consumer handles that key's stream.

</details>

<a id="kf-topic-006"></a>

<details>
<summary><strong>KF-TOPIC-006. How should you choose the number of partitions for a new topic?</strong></summary>

#### Short answer

Base it on expected throughput, required consumer parallelism, ordering needs, growth, and operational limits.

#### Interview answer

I start with the required write/read throughput and how many consumers may need to process in parallel. Then I check ordering scope: if all events must be globally ordered, partitions are limited, but that is rare. I also leave room for growth because increasing partitions later can affect key ordering assumptions.

#### Deep dive

Partition count affects broker file handles, memory, recovery time, leader distribution and consumer assignment. It is not only an application setting; it affects cluster operations.

#### Production angle

For important topics, size partitions using expected message rate, message size, consumer processing cost, and SLOs for lag recovery after downtime.

#### Traps / caveats

- Too few partitions cap parallelism.
- Too many partitions increase broker and operational overhead.

#### Optional Anki

Q: What does partition count control?
A: Parallelism, ordering scope and part of Kafka's operational overhead.

</details>

<a id="kf-topic-007"></a>

<details>
<summary><strong>KF-TOPIC-007. What are the trade-offs of having too many or too few partitions?</strong></summary>

#### Short answer

Too few partitions limit throughput and consumer parallelism; too many partitions increase cluster overhead and operational complexity.

#### Interview answer

Few partitions are simple and preserve broad ordering, but they create throughput and lag-recovery limits. Many partitions allow more parallelism, but increase metadata, open files, replication work, recovery time, memory usage and rebalance cost.

#### Deep dive

Partition count is often hard to reduce. Kafka supports increasing partitions, but not simply shrinking a topic's partition count in place. That makes initial sizing and future growth planning important.

#### Production angle

A topic with many partitions may behave fine on a quiet day but hurt during broker failover, consumer rebalances or partition reassignment.

#### Traps / caveats

- Partition count should not be chosen only from average throughput.
- More partitions do not fix slow downstream processing by themselves.

#### Optional Anki

Q: Main risk of too few partitions?
A: Limited parallelism and slower lag recovery.

</details>

<a id="kf-topic-008"></a>

<details>
<summary><strong>🧠 KF-TOPIC-008. What can go wrong when increasing the partition count of an existing topic?</strong></summary>

#### Short answer

Key-to-partition mapping can change, which may break assumptions about per-key ordering for future records.

#### Interview answer

Kafka can increase a topic's partition count, but hash-based partitioning depends on the number of partitions. After the change, the same key may map to a different partition for new records. Old records remain in the old partition, so a consumer may observe related records split across partitions.

#### Deep dive

This matters when consumers assume all events for one entity are in one partition for ordered processing. The risk is especially high for compacted topics, stateful consumers, and workflows where order is part of correctness.

#### Production angle

Before increasing partitions, check key usage, ordering requirements, consumer state, replay behavior, and deployment timing. For critical topics, consider a new topic and controlled migration.

#### Traps / caveats

- Increasing partitions is not a harmless throughput switch.
- Existing records are not redistributed automatically.

#### Optional Anki

Q: Why can increasing partitions break ordering assumptions?
A: The same key may map to a different partition after the partition count changes.

</details>

<a id="kf-topic-009"></a>

<details>
<summary><strong>KF-TOPIC-009. How would you design topics and keys for order events in an e-commerce system?</strong></summary>

#### Short answer

Use stable event contracts, partition by the ordering key such as `orderId`, and separate topics by ownership and consumer needs.

#### Interview answer

For order lifecycle events, I would usually have an `orders.events` topic owned by the order service with events like `OrderCreated`, `OrderPaid`, `OrderCancelled` or versioned equivalents. If ordering is needed per order, use `orderId` as the key. If downstream systems need different retention, sensitivity or schemas, split topics deliberately.

#### Deep dive

The design should avoid exposing the order table structure. Events should describe business facts. The topic should have retention, schema compatibility, DLQ policy and observability defined before production.

#### Production angle

Payment, inventory and notification consumers must be idempotent and tolerate late, duplicate or replayed events.

#### Traps / caveats

- Do not use one giant `events` topic without ownership.
- Do not use `customerId` if strict order status sequencing is per order.

#### Optional Anki

Q: Common partition key for order lifecycle ordering?
A: `orderId`.

</details>

<a id="kf-topic-010"></a>

<details>
<summary><strong>KF-TOPIC-010. Should one topic contain multiple event types, or should each event type have its own topic?</strong></summary>

#### Short answer

It depends on ownership, ordering, retention, schema compatibility, access control and consumer usage.

#### Interview answer

Multiple event types in one topic can be useful for an aggregate lifecycle where consumers need ordered changes for the same entity. Separate topics are better when events have different owners, retention, permissions, volume, schemas or consumers.

#### Deep dive

One-topic-per-event-type improves isolation and simpler schemas, but can fragment related event streams. A mixed topic can preserve order across related events, but consumers must filter types and handle schema evolution carefully.

#### Production angle

For sensitive events, separate topics often make ACLs, retention and audit simpler. For lifecycle events, one owned topic can be clearer.

#### Traps / caveats

- A mixed topic without clear schema strategy becomes hard to consume.
- Too many tiny topics create operational noise.

#### Optional Anki

Q: Key factors for topic split decisions?
A: Ownership, ordering, retention, ACLs, schema and consumer needs.

</details>

<a id="kf-topic-011"></a>

<details>
<summary><strong>🧠 KF-TOPIC-011. Which topic configurations should a Java backend engineer understand?</strong></summary>

#### Short answer

Understand retention, cleanup policy, replication factor, minimum ISR, partition count, max message size and compaction-related settings.

#### Interview answer

A backend engineer does not need to tune every broker setting, but should understand configs that change application behavior: retention time/size, `cleanup.policy`, replication factor, `min.insync.replicas`, partitions, max message size, and compaction/tombstone behavior.

#### Deep dive

These settings define whether data is replayable, when it disappears, whether consumers can catch up after downtime, how writes behave during broker failures, and whether keys are compacted into latest-state records.

#### Production angle

Before deploying a new topic, check retention against outage recovery time, DLQ/replay needs, compliance, storage cost and consumer SLOs.

#### Traps / caveats

- Broker defaults may be wrong for business-critical topics.
- A retention mistake can permanently remove data before a consumer catches up.

#### Optional Anki

Q: Which topic config controls delete vs compact behavior?
A: `cleanup.policy`.

</details>

<details>
<summary><strong>🧠 KF-TOPIC-012. What internal Kafka topics matter for consumers and transactions?</strong></summary>

#### Short answer

`__consumer_offsets` stores consumer group offsets and metadata; `__transaction_state` stores transaction coordinator state.

#### Interview answer

Consumers normally commit offsets to Kafka's internal `__consumer_offsets` topic. That allows groups to resume after restarts. Kafka transactions rely on internal transaction state so coordinators can track transactional producers and commit or abort transactional work.

#### Deep dive

These topics are managed by Kafka, not application teams. Still, backend engineers should know they exist because offset commit behavior, group state and transactional behavior depend on them.

#### Production angle

Problems with internal topics can surface as commit failures, unstable consumer groups or transaction errors. Platform teams typically monitor their health and replication.

#### Traps / caveats

- Do not manually write business records to internal Kafka topics.
- Losing offset state can make consumers reprocess or skip depending on reset policy.

#### Optional Anki

Q: What is `__consumer_offsets` used for?
A: Consumer group offset and group metadata storage.

</details>
