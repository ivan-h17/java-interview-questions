# Replication, ISR and fault tolerance

---

<a id="kf-rep-001"></a>

<details>
<summary><strong>KF-REP-001. How do replication factor, leader replicas, follower replicas and ISR work?</strong></summary>

#### Short answer

Each partition has replicas; one leader handles reads/writes, followers replicate it, and ISR is the set of replicas considered in sync.

#### Interview answer

Replication factor is the number of copies of a partition. One replica is leader; producers and consumers normally talk to the leader. Followers fetch data from the leader. In-sync replicas are followers that are caught up enough to be eligible for safe acknowledgement and leadership.

#### Deep dive

Replication gives availability and durability, but only if replicas are spread across brokers and kept in sync. If all replicas are on risky infrastructure, replication factor alone is not enough.

#### Production angle

For production topics, replication factor `3` is common, with rack awareness where available and appropriate `min.insync.replicas`.

#### Traps / caveats

- Replication is not a backup if retention deletes the data.
- More replicas increase broker storage and network traffic.

#### Optional Anki

Q: What is ISR?
A: The set of replicas currently considered in sync with the partition leader.

</details>

<a id="kf-rep-002"></a>

<details>
<summary><strong>🧠 KF-REP-002. What is the high watermark, and why do consumers usually read only committed records?</strong></summary>

#### Short answer

The high watermark marks the offset up to which records are safely replicated enough to be considered committed.

#### Interview answer

Kafka advances the high watermark when records have been replicated to the required in-sync replicas. Consumers normally read only up to committed positions so they do not see records that might disappear if the leader fails before replication.

#### Deep dive

This protects consumers from reading data that is present only on a leader that may be lost. It is part of Kafka's durability model around leader-follower replication.

#### Production angle

If replication is unhealthy, producers may see errors or consumers may appear delayed because records are not safely committed as expected.

#### Traps / caveats

- Reading committed records is about Kafka replication, not application transaction commits.
- Transactional `read_committed` adds another layer for Kafka transactions.

#### Optional Anki

Q: What does Kafka's high watermark indicate?
A: The committed replicated position of a partition log.

</details>

<a id="kf-rep-003"></a>

<details>
<summary><strong>KF-REP-003. What happens when a partition leader fails?</strong></summary>

#### Short answer

Kafka elects a new leader from suitable replicas, and clients refresh metadata to use the new leader.

#### Interview answer

If the leader broker fails, Kafka detects it and elects another in-sync replica as leader if possible. Producers and consumers may see temporary errors, timeouts or metadata refreshes, then continue with the new leader.

#### Deep dive

The quality of failover depends on ISR health. If no in-sync replica is available, the partition may become unavailable unless unclean leader election is allowed.

#### Production angle

Applications should tolerate transient retriable errors during leader changes. Dashboards should show leader elections, unavailable partitions and ISR shrink events.

#### Traps / caveats

- Leader failover is not invisible to clients.
- If clients use very aggressive timeouts, normal failover can look like an outage.

#### Optional Anki

Q: Who becomes new leader after failure?
A: Usually an in-sync replica.

</details>

<a id="kf-rep-004"></a>

<details>
<summary><strong>KF-REP-004. Why can unclean leader election cause data loss?</strong></summary>

#### Short answer

It can elect an out-of-sync replica as leader, losing records that existed only on the old leader or more up-to-date replicas.

#### Interview answer

Unclean leader election prioritizes availability over durability. If no in-sync replica is available, Kafka may elect a stale replica so the partition can become writable again. That stale replica may not contain the latest acknowledged records.

#### Deep dive

This creates log truncation risk. Consumers and producers may observe missing data or inconsistent history.

#### Production angle

For critical topics, unclean leader election is usually disabled. The system should prefer temporary unavailability over silent data loss.

#### Traps / caveats

- High availability and no data loss can conflict during severe failures.
- Application retries cannot recover records lost by unclean election.

#### Optional Anki

Q: What trade-off does unclean leader election make?
A: Availability over durability.

</details>

<a id="kf-rep-005"></a>

<details>
<summary><strong>KF-REP-005. How do `acks=all`, ISR and `min.insync.replicas` protect against data loss?</strong></summary>

#### Short answer

They require records to be acknowledged only when enough in-sync replicas have accepted them.

#### Interview answer

With `acks=all`, the leader waits for in-sync replicas before acknowledging. `min.insync.replicas` defines the minimum number of replicas that must be in sync for writes to succeed. If ISR shrinks below that threshold, writes fail rather than accepting under-replicated data.

#### Deep dive

This reduces the chance that a leader failure loses acknowledged records. It does not protect against all disasters, such as all replicas being lost or misconfigured unclean leader election.

#### Production angle

A common pattern is replication factor `3` and `min.insync.replicas=2` for important topics, with application handling for failed writes.

#### Traps / caveats

- Stronger durability can reduce write availability during broker problems.
- If the application ignores send failures, the protection is wasted.

#### Optional Anki

Q: What happens if ISR is below `min.insync.replicas`?
A: Writes requiring that minimum fail.

</details>

<a id="kf-rep-006"></a>

<details>
<summary><strong>KF-REP-006. What are under-replicated and under-min-ISR partitions?</strong></summary>

#### Short answer

Under-replicated partitions have replicas not fully caught up; under-min-ISR partitions have too few in-sync replicas for configured durability.

#### Interview answer

An under-replicated partition indicates at least one replica is lagging or unavailable. Under-min-ISR is more severe for writes: the partition does not have enough in-sync replicas to satisfy `min.insync.replicas`, so producers with strong acks may fail.

#### Deep dive

Causes include broker failure, network issues, disk saturation, overloaded brokers or large replication backlog.

#### Production angle

These metrics should alert platform teams and inform application incident response because producer errors may follow.

#### Traps / caveats

- Under-replication is not just a broker concern; it can affect application write success.
- A partition can be available but below desired redundancy.

#### Optional Anki

Q: Which condition can make strong producer writes fail?
A: Under-min-ISR partitions.

</details>

<a id="kf-rep-007"></a>

<details>
<summary><strong>KF-REP-007. How would you choose replication factor and rack awareness for a production topic?</strong></summary>

#### Short answer

Choose replication based on data criticality, availability target, failure domains, storage cost and write overhead.

#### Interview answer

For important production topics, replication factor `3` is common because it tolerates a broker loss while keeping redundancy. Rack awareness spreads replicas across failure domains such as racks or availability zones. The exact choice depends on business criticality and infrastructure.

#### Deep dive

Replication factor increases storage and network usage. Rack awareness improves resilience only if the cluster's failure-domain labels and placement are correct.

#### Production angle

For compliance, payments or order events, verify replica placement, `min.insync.replicas`, unclean election policy and monitoring.

#### Traps / caveats

- Replication across bad failure domains can create false confidence.
- Higher replication does not fix bad retention or consumer idempotency.

#### Optional Anki

Q: What does rack awareness protect against?
A: Losing replicas together in one failure domain.

</details>

<a id="kf-rep-008"></a>

<details>
<summary><strong>KF-REP-008. How can broker failures affect Java producers and consumers?</strong></summary>

#### Short answer

Clients may see timeouts, retriable errors, metadata refreshes, leader changes, slower writes and temporary consumption pauses.

#### Interview answer

When brokers fail, partition leadership may move, ISR may shrink and some partitions may become temporarily unavailable. Producers may retry or fail sends. Consumers may pause while metadata refreshes or group coordination changes.

#### Deep dive

The effect depends on which broker failed: partition leader, follower, group coordinator or controller-related node. Client settings determine whether the application waits, retries, fails fast or fills buffers.

#### Production angle

Java services should expose producer and consumer error metrics, have bounded timeouts, and avoid blocking critical threads indefinitely.

#### Traps / caveats

- Retriable Kafka errors still need latency budgets.
- A broker outage can surface as database pressure if consumers replay or catch up aggressively.

#### Optional Anki

Q: What should clients do after leader changes?
A: Refresh metadata and retry where appropriate.

</details>

<details>
<summary><strong>🧠 KF-REP-009. What are preferred leader election and partition reassignment used for?</strong></summary>

#### Short answer

Preferred leader election restores intended leadership balance; partition reassignment moves replicas across brokers.

#### Interview answer

Kafka assigns a preferred replica for each partition. After failures, leadership can become unbalanced, so preferred leader election moves leadership back when safe. Partition reassignment is used to add brokers, remove brokers, rebalance storage or move replicas across failure domains.

#### Deep dive

Both are operational tools. They can affect client latency and cluster load, so they should be planned and monitored.

#### Production angle

Backend engineers may not run these operations, but should recognize their symptoms: leadership movement, temporary latency spikes and metadata changes.

#### Traps / caveats

- Reassignment can create heavy network and disk load.
- Leadership balance affects broker hotspots.

#### Optional Anki

Q: What does partition reassignment move?
A: Partition replicas between brokers.

</details>
