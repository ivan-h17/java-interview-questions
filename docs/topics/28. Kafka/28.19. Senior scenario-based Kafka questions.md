# Senior scenario-based Kafka questions

---

<a id="kf-scen-001"></a>

<details>
<summary><strong>KF-SCEN-001. Design an order-created event pipeline with Kafka. What topics, keys, partitions and schemas would you choose?</strong></summary>

#### Short answer

Use an owned order event topic, key by `orderId`, define a stable schema, and publish through Outbox after the order transaction commits.

#### Interview answer

I would have the order service own an `orders.events` topic or `orders.created` topic depending on event strategy. `orderId` is the key if ordering is per order. The schema should include event ID, order ID, customer ID, occurred time, version and only fields consumers need.

#### Deep dive

Publishing should use Transactional Outbox so an order is not committed without its event. Consumers like payment, inventory and notifications must be idempotent.

#### Production angle

Define retention, schema compatibility, DLQ policy, lag alerts, ACLs and replay behavior before launch.

#### Traps / caveats

- Do not expose the full order database row as the event.
- Do not use random keys if order-level ordering matters.

#### Optional Anki

Q: Common key for order lifecycle events?
A: `orderId`.

</details>

<a id="kf-scen-002"></a>

<details>
<summary><strong>KF-SCEN-002. A payment consumer processes the same event twice. How do you prevent double charging?</strong></summary>

#### Short answer

Use a stable idempotency key and enforce it at the payment operation boundary.

#### Interview answer

The consumer should not rely on Kafka offsets to prevent double charge. It should use a payment ID, command ID or event ID as an idempotency key, store the result with a unique constraint, and call the payment provider with an idempotency key if supported.

#### Deep dive

Duplicate processing can happen after retry, rebalance or crash before offset commit. The payment operation must be safe even when the same event is delivered again.

#### Production angle

Add reconciliation against provider state for unknown outcomes and monitor duplicate detections.

#### Traps / caveats

- Deduplicating only in memory fails after restart.
- Retrying provider calls without idempotency can charge twice.

#### Optional Anki

Q: What prevents double charging?
A: Business idempotency key with durable enforcement.

</details>

<a id="kf-scen-003"></a>

<details>
<summary><strong>KF-SCEN-003. A consumer group lag grows after a deployment. What do you check first?</strong></summary>

#### Short answer

Check the deployment diff, error rate, processing time, rebalances, downstream latency and per-partition lag.

#### Interview answer

I would compare lag before/after deploy, inspect consumer logs, DLQ/retry metrics, deserialization errors, DB/API latency, thread pools, connection pools and rebalance activity. If the new version caused slow processing or failures, rollback may be the fastest mitigation.

#### Deep dive

Lag after deploy often means changed payload handling, new DB query, broken schema, bad group ID, changed concurrency or error-handler behavior.

#### Production angle

Use canary deploys and dashboards by service version to catch this early.

#### Traps / caveats

- Scaling replicas may worsen DB bottlenecks.
- Aggregate lag can hide one partition stuck on a poison message.

#### Optional Anki

Q: First suspicion when lag grows after deploy?
A: New code changed processing speed or failure rate.

</details>

<a id="kf-scen-004"></a>

<details>
<summary><strong>KF-SCEN-004. A single partition has much higher traffic than others. How do you diagnose and fix it?</strong></summary>

#### Short answer

Identify hot keys and decide whether to change keying, shard heavy entities or isolate traffic.

#### Interview answer

I would inspect per-partition record/byte rates and sample keys from the hot partition. If one tenant or customer dominates, the current key may be too coarse. Fixes include composite keys, separate heavy-tenant topics, or redesigning ordering requirements.

#### Deep dive

If strict ordering is required for that hot key, splitting it may not be safe. The business needs to decide whether order can be narrowed.

#### Production angle

Short term, throttle heavy producers or scale downstream for that partition if possible. Long term, redesign key strategy.

#### Traps / caveats

- Adding consumers does not split one partition.
- Increasing partitions does not solve one hot key.

#### Optional Anki

Q: What is the likely cause of one hot partition?
A: Skewed partition keys.

</details>

<a id="kf-scen-005"></a>

<details>
<summary><strong>KF-SCEN-005. A producer must publish an event only if a database transaction commits. How do you design this?</strong></summary>

#### Short answer

Use Transactional Outbox: write the event record in the same DB transaction and publish it after commit.

#### Interview answer

Inside the database transaction, persist the business change and an outbox row. A relay reads committed outbox rows and publishes to Kafka. This ensures rollback does not publish an event and commit does not depend on Kafka being available in the request path.

#### Deep dive

The relay may publish duplicates, so the event has an ID and consumers are idempotent. The outbox table needs retries and cleanup.

#### Production angle

Alert on outbox lag and failed publishes because they indicate delayed integration.

#### Traps / caveats

- Publishing after commit without Outbox can lose events on crash.
- Publishing before commit can emit rolled-back state.

#### Optional Anki

Q: Pattern for DB commit then Kafka event reliability?
A: Transactional Outbox.

</details>

<a id="kf-scen-006"></a>

<details>
<summary><strong>KF-SCEN-006. A Kafka event schema must change without breaking existing consumers. What is your rollout plan?</strong></summary>

#### Short answer

Make compatible changes, deploy tolerant consumers first, then producers, and remove old fields only after deprecation.

#### Interview answer

I would check compatibility rules, add optional fields with defaults, ensure consumers tolerate old and new messages, deploy consumers first if needed, then deploy producers. For breaking changes, create a new versioned contract or topic and migrate consumers deliberately.

#### Deep dive

Replay means new consumers must handle old events still in Kafka. Rolling deploys mean old consumers may see new events unless compatibility prevents that.

#### Production angle

Run schema compatibility checks in CI and monitor deserialization failures after rollout.

#### Traps / caveats

- Schema-compatible does not always mean semantically compatible.
- Removing fields too early breaks lagging consumers and replay.

#### Optional Anki

Q: Safe schema rollout order?
A: Tolerant consumers first, producers second.

</details>

<a id="kf-scen-007"></a>

<details>
<summary><strong>KF-SCEN-007. A consumer depends on a slow external API. How do you avoid blocking the whole pipeline?</strong></summary>

#### Short answer

Use timeouts, bounded concurrency, backpressure, retries with backoff, circuit breakers and possibly separate retry topics.

#### Interview answer

I would set strict timeouts, limit concurrent API calls, use backoff and circuit breaker behavior, and pause or throttle consumption when the API is unhealthy. If events are independent, non-blocking retry topics can prevent one failed call from blocking the main partition.

#### Deep dive

If ordering is required, moving failed records aside can violate order. In that case, per-key quarantine or blocking retry may be safer.

#### Production angle

Monitor API latency, consumer lag, retry backlog and thread/connection pool usage.

#### Traps / caveats

- Unbounded async calls can overload the API and the service.
- Retrying non-idempotent API calls can duplicate side effects.

#### Optional Anki

Q: Main protection against slow downstream API?
A: Bounded timeout/concurrency and backpressure.

</details>

<a id="kf-scen-008"></a>

<details>
<summary><strong>KF-SCEN-008. A service needs strict ordering per customer. What partition key would you use and what are the trade-offs?</strong></summary>

#### Short answer

Use `customerId` as the key, but watch for hot customers and reduced parallelism.

#### Interview answer

If strict order is per customer, all events for one customer must go to the same partition, so `customerId` is the natural key. The trade-off is that a large customer can become a hot key and all events for that customer are processed serially.

#### Deep dive

If only some operations require strict order, consider narrowing the ordering scope to account, order or workflow ID. If customer-level order is mandatory, capacity must account for worst-case customer traffic.

#### Production angle

Monitor per-key skew and per-partition lag. Large tenants may need isolation.

#### Traps / caveats

- Sharding `customerId` breaks strict customer ordering.
- `orderId` would not preserve order across all customer events.

#### Optional Anki

Q: Key for strict per-customer ordering?
A: `customerId`.

</details>

<a id="kf-scen-009"></a>

<details>
<summary><strong>KF-SCEN-009. A topic contains PII and retention is one year. What questions would you ask?</strong></summary>

#### Short answer

Ask why PII is needed, who can read it, retention justification, deletion obligations, masking and downstream copies.

#### Interview answer

I would ask which fields are PII, whether consumers need raw values, whether tokenized or referenced data is enough, who has ACL access, whether DLQ/logs/sinks also store it, and whether one-year retention satisfies privacy policy and regulations.

#### Deep dive

Kafka data can fan out and be replayed, so sensitive data spreads beyond the original topic. Deletion from Kafka is not as precise as updating a database row.

#### Production angle

Require security review, data classification, retention approval, encryption, access audit and redaction plan.

#### Traps / caveats

- DLQs and logs often leak the same PII.
- Compaction/tombstones do not guarantee immediate erasure everywhere.

#### Optional Anki

Q: First PII design question?
A: Does the event need raw PII at all?

</details>

<a id="kf-scen-010"></a>

<details>
<summary><strong>KF-SCEN-010. A DLQ is growing quickly. How do you triage the incident?</strong></summary>

#### Short answer

Classify errors, correlate with deploys/schema changes, stop new damage, and decide rollback, pause or fix-forward.

#### Interview answer

I would sample DLQ records, group by error type, check recent producer and consumer deployments, inspect schema/deserialization failures and downstream outages. If a bad release caused it, rollback. If downstream is down, throttle or pause. If data is bad, quarantine and notify owner.

#### Deep dive

Fast DLQ growth means the main flow is skipping records. The priority is to prevent more records from entering an unrecoverable path and preserve enough metadata for replay.

#### Production angle

Track DLQ rate, oldest DLQ age and affected business entities. Prepare a reprocessing plan after the fix.

#### Traps / caveats

- Replaying before root-cause fix loops records back to DLQ.
- Ignoring DLQ because main lag is low hides data loss from the normal path.

#### Optional Anki

Q: What does growing DLQ mean?
A: The normal consumer path is failing and skipping records by policy.

</details>

<a id="kf-scen-011"></a>

<details>
<summary><strong>KF-SCEN-011. A consumer must update PostgreSQL and publish another Kafka event. What reliability pattern would you use?</strong></summary>

#### Short answer

Use idempotent consumption plus a database transaction that writes business state and an Outbox row for the next event.

#### Interview answer

The consumer reads an event, checks idempotency, updates PostgreSQL and writes an outbox record in one transaction. It commits the Kafka offset only after the DB transaction succeeds. A relay publishes the outbox event to Kafka.

#### Deep dive

This avoids trying to atomically combine consumed offset, DB update and Kafka publish in fragile ways. Duplicates are handled through Inbox/idempotency.

#### Production angle

Monitor consumer lag, DB transaction failures, outbox lag and duplicate detections.

#### Traps / caveats

- Publishing the second event directly after DB commit can be lost on crash.
- Committing the input offset before DB commit can lose work.

#### Optional Anki

Q: Pattern for consume-update-then-publish?
A: Idempotent consumer plus Transactional Outbox.

</details>

<a id="kf-scen-012"></a>

<details>
<summary><strong>KF-SCEN-012. You need to replay one month of events. What are the operational risks?</strong></summary>

#### Short answer

Replay can duplicate side effects, overload dependencies, violate old schema assumptions and disturb current processing.

#### Interview answer

I would check retention, schemas, idempotency, downstream capacity, ordering, event age semantics and whether the replay should use the same consumer group or a separate one. I would rate-limit and run in batches with monitoring.

#### Deep dive

Old events may not mean the same thing under current business rules. Consumers must handle old schema versions and stale state safely.

#### Production angle

Use a replay runbook with approval, dry run, metrics, rollback and reconciliation.

#### Traps / caveats

- Replaying with the production group changes offsets.
- Replaying old commands can trigger real side effects again.

#### Optional Anki

Q: Biggest replay requirement?
A: Idempotent and replay-safe consumers.

</details>

<a id="kf-scen-013"></a>

<details>
<summary><strong>KF-SCEN-013. You need to migrate a topic from JSON to Avro. How would you do it safely?</strong></summary>

#### Short answer

Introduce Avro-compatible consumers first or create a new topic, then migrate producers and consumers with validation and rollback.

#### Interview answer

If keeping the topic, consumers must handle both formats during transition, often using headers/content type. Safer for breaking format changes is a new Avro topic with Schema Registry, dual publishing, consumer migration, validation and cutover.

#### Deep dive

The plan must handle replay of old JSON records and mixed producer versions. Schema compatibility and sample payload tests are required.

#### Production angle

Monitor deserialization failures, topic lag and output equivalence during dual-run.

#### Traps / caveats

- Switching producer format first can break existing consumers.
- Headers used to distinguish formats must be preserved through retries/DLQ.

#### Optional Anki

Q: Safer path for breaking serialization change?
A: New topic or dual-format migration with consumers ready first.

</details>

<a id="kf-scen-014"></a>

<details>
<summary><strong>KF-SCEN-014. You need to increase partition count for a heavily used topic. What can go wrong?</strong></summary>

#### Short answer

Key mapping can change, ordering assumptions can break, and consumers/stateful processing may need adjustment.

#### Interview answer

Increasing partitions can improve parallelism, but records for the same key may map to a different partition after the change. Old records stay where they are. Consumers assuming per-key order or local state by partition may behave incorrectly.

#### Deep dive

You also need to check broker capacity, consumer concurrency, rebalance impact and downstream capacity. More partitions are not free.

#### Production angle

For critical topics, consider a new topic and planned migration instead of in-place partition increase.

#### Traps / caveats

- Increasing partitions does not redistribute existing records.
- It may not fix hot keys.

#### Optional Anki

Q: Partition increase risk?
A: Changed key-to-partition mapping and broken ordering assumptions.

</details>

<a id="kf-scen-015"></a>

<details>
<summary><strong>KF-SCEN-015. How would you review a Kafka-based architecture before approving it for production?</strong></summary>

#### Short answer

Review fit, ownership, topics, keys, schemas, delivery semantics, failure handling, observability, security and operations.

#### Interview answer

I would ask why Kafka is needed, who owns each topic, what the partition keys are, what ordering is required, how schemas evolve, how DB consistency is handled, how consumers are idempotent, what retry/DLQ policy exists and what dashboards/runbooks are ready.

#### Deep dive

Then I would check capacity estimates, retention, ACLs, PII, deployment strategy, replay plan, offset reset policy and downstream bottlenecks.

#### Production angle

Approval should require load tests, failure tests, alerts, DLQ ownership and rollback plans for schema and consumer deploys.

#### Traps / caveats

- A design with no replay or DLQ plan is incomplete.
- A design with unclear ownership will be hard to evolve.

#### Optional Anki

Q: Senior Kafka review themes?
A: Fit, contracts, keys, correctness, failures, observability and ownership.

</details>
