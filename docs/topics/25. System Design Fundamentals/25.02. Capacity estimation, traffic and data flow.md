# Capacity estimation, traffic and data flow

---

<a id="sd-cap-001"></a>

<details>
<summary><strong>SD-CAP-001. How do you estimate daily active users, QPS and peak QPS?</strong></summary>

#### Short answer

Estimate active users, requests per user, seconds per day, and a peak multiplier.

#### Interview answer

I start with daily active users, multiply by average requests per user per day, and divide by 86,400 to get average QPS. Then I apply a peak multiplier, often 2x to 10x depending on user behavior. For example, 10 million users making 20 requests per day is about 2,300 average QPS; peak might be 10,000 to 20,000 QPS.

#### Deep dive

The exact number is less important than the order of magnitude. Estimation helps decide whether one database, read replicas, caching, queues, partitioning, or CDN support may be needed.

#### Production angle

Capacity estimates become inputs for load tests, autoscaling, database sizing, connection pool limits, queue capacity, and cost forecasts.

#### Traps / caveats

- Do not design only for average traffic.
- Do not pretend rough estimates are exact measurements.

#### Optional Anki

Q: How do you estimate average QPS?
A: Daily active users times requests per user per day divided by 86,400.

</details>

<a id="sd-cap-002"></a>

<details>
<summary><strong>SD-CAP-002. How do read/write ratios affect system design?</strong></summary>

#### Short answer

Read-heavy systems often benefit from caching and replicas; write-heavy systems need careful consistency, partitioning, batching, and backpressure.

#### Interview answer

If reads dominate, I can consider CDN, application cache, Redis, read replicas, projections, and denormalized read models. If writes dominate, the design must protect the primary database, choose good keys, avoid hot partitions, batch where possible, and handle retries safely. The ratio also affects indexes because indexes speed reads but add write cost.

#### Deep dive

Read/write ratio is not enough by itself. Some reads need strong consistency, and some writes are low-value logs that can be buffered. Access patterns and correctness requirements decide the final approach.

#### Production angle

Wrong assumptions about read/write ratio often lead to overloaded primaries, stale user-visible data, or excessive infrastructure cost.

#### Traps / caveats

- Do not send strongly consistent reads to lagging replicas.
- Do not add many indexes to a write-heavy table without considering write amplification.

#### Optional Anki

Q: What does a read-heavy design commonly use?
A: Caches, replicas, CDN, denormalized read models, and efficient indexes.

</details>

<a id="sd-cap-003"></a>

<details>
<summary><strong>SD-CAP-003. How do you estimate storage growth over time?</strong></summary>

#### Short answer

Estimate records created per period, average record size, indexes, replication, retention, and growth rate.

#### Interview answer

I estimate how much data is created per user or event, multiply by traffic, then add overhead for indexes, metadata, replicas, backups, and compression if relevant. For example, 100 million events per day at 1 KB each is about 100 GB per day before indexes and replication. Retention then decides whether this is a short-term operational store or long-term archive problem.

#### Deep dive

Storage growth changes database choice, partitioning, backup strategy, retention policy, and cost. Hot operational data and cold historical data may belong in different stores.

#### Production angle

Unplanned growth causes slow backups, expensive indexes, full disks, long migrations, and degraded query plans.

#### Traps / caveats

- Do not ignore index, replica, and backup overhead.
- Do not keep all historical data in the primary transactional database by default.

#### Optional Anki

Q: What factors affect storage growth?
A: Data volume, average size, indexes, replicas, backups, retention, and growth rate.

</details>

<a id="sd-cap-004"></a>

<details>
<summary><strong>SD-CAP-004. How do you estimate bandwidth and payload size at a high level?</strong></summary>

#### Short answer

Multiply request or response size by QPS, then consider peak traffic, compression, uploads, downloads, and replication traffic.

#### Interview answer

For APIs, I estimate average payload size and multiply by peak QPS. A 50 KB response at 10,000 QPS is about 500 MB/s before compression and protocol overhead. For media or file systems, object size and upload/download frequency matter more than JSON payloads.

#### Deep dive

Bandwidth affects CDN use, network cost, service-to-service calls, mobile performance, and cross-region replication. Large payloads may require pagination, streaming, object storage, pre-signed URLs, or background processing.

#### Production angle

Bandwidth spikes can saturate network links, load balancers, gateways, or downstream services before CPU becomes the bottleneck.

#### Traps / caveats

- Do not route large file uploads through application servers unless there is a reason.
- Do not ignore internal service-to-service and replication bandwidth.

#### Optional Anki

Q: How do you estimate API bandwidth?
A: Average payload size times peak QPS, adjusted for protocol overhead and compression.

</details>

<a id="sd-cap-005"></a>

<details>
<summary><strong>SD-CAP-005. How do you estimate cache size for hot data?</strong></summary>

#### Short answer

Estimate the hot working set, value size, key overhead, metadata overhead, TTL, and replication factor.

#### Interview answer

I identify which data is repeatedly read and how many distinct keys are hot during the TTL window. Then I multiply key count by average serialized value size and add overhead for keys, metadata, eviction structures, and replicas. If the hot set is 5 million objects at 2 KB each, the raw data is about 10 GB before overhead.

#### Deep dive

A cache does not need to hold all data. It needs to hold enough of the working set to produce a useful hit rate without causing eviction churn. The right size depends on access skew, TTL, and tolerance for misses.

#### Production angle

Undersized caches cause low hit rates and database load. Oversized caches waste memory and can hide invalidation problems.

#### Traps / caveats

- Do not use total database size as cache size.
- Do not ignore serialization and per-key overhead.

#### Optional Anki

Q: What is the hot working set?
A: The subset of data repeatedly accessed within a relevant time window.

</details>

<a id="sd-cap-006"></a>

<details>
<summary><strong>SD-CAP-006. How do capacity estimates influence database, cache and queue choices?</strong></summary>

#### Short answer

They reveal whether the system needs simple vertical scaling, read replicas, caching, partitioning, asynchronous processing, or specialized storage.

#### Interview answer

If the estimated load is modest, a relational database and stateless application tier may be enough. If reads are high, I consider caches or replicas. If writes are bursty, a queue can smooth load. If data grows beyond one node or operational limits, partitioning or a different storage model may be needed.

#### Deep dive

Capacity estimates should influence design, not dictate it blindly. Correctness, latency, team expertise, and operational complexity also matter. A lower-scale but strongly consistent system may still need careful transaction design.

#### Production angle

Good estimates prevent both underengineering and overengineering. They also give a baseline for load testing and alert thresholds.

#### Traps / caveats

- Do not choose distributed storage just because it sounds scalable.
- Do not ignore connection limits, index size, and write amplification.

#### Optional Anki

Q: How do capacity estimates guide architecture?
A: They identify likely bottlenecks and justify scaling, caching, queuing, or partitioning choices.

</details>

<a id="sd-cap-007"></a>

<details>
<summary><strong>SD-CAP-007. What are read path and write path in a backend design?</strong></summary>

#### Short answer

The read path is how data is fetched and returned; the write path is how changes are validated, stored, propagated, and observed.

#### Interview answer

For a product page, the read path might be client, CDN, API gateway, service, cache, database, and response. The write path for updating inventory might include validation, transaction, database update, outbox event, cache invalidation, and downstream consumers. Separating them helps reason about latency, consistency, failure modes, and scaling.

#### Deep dive

Read paths often optimize latency and throughput. Write paths often optimize correctness, durability, ordering, idempotency, and propagation. Some systems split them explicitly using CQRS or read models.

#### Production angle

Many incidents happen because the read path and write path disagree about freshness, invalidation, or ownership.

#### Traps / caveats

- Do not describe only the happy-path request.
- Do not forget cache invalidation, events, retries, and observability in the write path.

#### Optional Anki

Q: Why separate read path and write path?
A: They often have different latency, consistency, scaling, and failure requirements.

</details>

<a id="sd-cap-008"></a>

<details>
<summary><strong>SD-CAP-008. How do you identify the first likely bottleneck in a design?</strong></summary>

#### Short answer

Trace the critical path and compare expected load against the capacity of each component.

#### Interview answer

I look for shared resources, synchronous dependencies, hot keys, primary database writes, expensive queries, external APIs, and unbounded queues. Then I ask which component all requests must pass through and which one has the tightest limit. Often the first bottleneck is the database, a third-party dependency, a cache hot key, or an overloaded worker pool.

#### Deep dive

Bottlenecks depend on workload. CPU-heavy services, large uploads, fan-out calls, lock contention, slow queries, and cross-region hops all fail differently. A good answer explains how to measure and validate the guess.

#### Production angle

Bottleneck analysis drives load tests, dashboards, autoscaling policies, and fallback plans.

#### Traps / caveats

- Do not assume the application service is always the bottleneck.
- Do not ignore downstream limits and connection pools.

#### Optional Anki

Q: How do you find likely bottlenecks?
A: Trace the critical path and compare expected load to each component's limits.

</details>

<a id="sd-cap-009"></a>

<details>
<summary><strong>SD-CAP-009. Why should peak traffic matter more than average traffic?</strong></summary>

#### Short answer

Systems fail during bursts, not during comfortable averages.

#### Interview answer

Average QPS hides spikes from business hours, promotions, batch jobs, retries, mobile push campaigns, and regional traffic patterns. A system that handles 1,000 average QPS may still fail at 20,000 peak QPS. Design should consider peak load, burst duration, queue absorption, rate limits, autoscaling delay, and graceful degradation.

#### Deep dive

Peak traffic affects thread pools, database connections, cache capacity, queue depth, load balancers, and third-party quotas. Some bursts can be absorbed asynchronously; others must be served online.

#### Production angle

Peak readiness is what protects launches, incidents, flash sales, and traffic after dependency recovery.

#### Traps / caveats

- Do not use daily averages to size request-path dependencies.
- Do not assume autoscaling reacts instantly.

#### Optional Anki

Q: Why are average traffic numbers risky?
A: They hide bursts that can overload shared resources and dependencies.

</details>

<a id="sd-cap-010"></a>

<details>
<summary><strong>SD-CAP-010. How do retention requirements affect storage and cost?</strong></summary>

#### Short answer

Retention determines how long data is kept, where it is stored, how it is indexed, and how much it costs.

#### Interview answer

If data is needed for only 30 days, the operational database can stay smaller. If data must be retained for years, I may use partitioning, archival storage, object storage, or a warehouse. Retention also affects backups, deletion policies, compliance, and query performance.

#### Deep dive

Different data classes need different retention: transactions, logs, metrics, audit records, user content, and PII. Some data must be deleted after a period, while other data must be preserved for legal or financial reasons.

#### Production angle

Poor retention design creates expensive storage, slow queries, large backups, and compliance risk.

#### Traps / caveats

- Do not keep unlimited logs or events in the primary database.
- Do not ignore deletion requirements for sensitive user data.

#### Optional Anki

Q: Why does retention matter in system design?
A: It drives storage size, cost, partitioning, archival, backups, and compliance behavior.

</details>

<a id="sd-cap-011"></a>

<details>
<summary><strong>SD-CAP-011. How do you estimate fan-out cost for feeds, notifications or messaging systems?</strong></summary>

#### Short answer

Estimate how many recipients each write reaches and whether fan-out happens at write time, read time, or both.

#### Interview answer

For notifications, one event may target one user, thousands of followers, or all users. I estimate producers, average recipients, peak campaigns, delivery channels, and retries. Fan-out-on-write precomputes delivery but can create huge write bursts. Fan-out-on-read reduces writes but can make reads slow and complex.

#### Deep dive

The right strategy depends on access patterns. Celebrity feeds and large broadcasts often need special handling to avoid hot partitions and massive queues. Hybrid designs often fan out normal users and compute high-fan-out users differently.

#### Production angle

Fan-out mistakes create queue explosions, duplicate notifications, delayed feeds, and database hot spots.

#### Traps / caveats

- Do not multiply only by producers; multiply by recipients too.
- Do not ignore retries, deduplication, and per-channel rate limits.

#### Optional Anki

Q: What is fan-out cost?
A: The downstream work created when one write must be delivered to many readers or recipients.

</details>

<a id="sd-cap-012"></a>

<details>
<summary><strong>SD-CAP-012. How do you discuss capacity estimates when exact numbers are unknown?</strong></summary>

#### Short answer

Use reasonable assumptions, show the formula, and design for order of magnitude rather than fake precision.

#### Interview answer

I would state assumptions clearly: "If we assume 1 million daily users and 20 requests per user, average QPS is around 230; with a 10x peak, about 2,300 QPS." Then I explain how the design changes if the number is 10x higher or lower. This is more useful than pretending to know exact traffic.

#### Deep dive

Estimates are a communication tool. They expose which parameters matter: users, request rate, payload size, write ratio, retention, fan-out, and peak multiplier. Sensitivity analysis often matters more than the initial guess.

#### Production angle

Real teams refine estimates with logs, product analytics, load tests, and capacity models.

#### Traps / caveats

- Do not overfit architecture to one guessed number.
- Do not skip estimates entirely because numbers are uncertain.

#### Optional Anki

Q: What is the right attitude to rough estimates?
A: Be explicit, order-of-magnitude focused, and ready to revise assumptions.

</details>
