# Core architecture, APIs and edge building blocks

---

<a id="sd-arch-001"></a>

<details>
<summary><strong>SD-ARCH-001. What are the common building blocks in a backend system design?</strong></summary>

#### Short answer

Common blocks include clients, DNS, CDN, load balancers, gateways, services, databases, caches, queues, object storage, workers, and observability.

#### Interview answer

A typical backend design has clients calling an edge layer, then stateless services that read and write data stores. Supporting components may include caches for hot reads, queues for asynchronous work, background workers, object storage for large files, search indexes, and monitoring. The exact blocks should come from requirements, not from a memorized template.

#### Deep dive

Each block owns a role: route traffic, execute business logic, store durable data, absorb bursts, serve files, or provide operational visibility. Good design explains the interaction between blocks through read and write paths.

#### Production angle

Components add failure modes, operational work, cost, security boundaries, and deployment concerns.

#### Traps / caveats

- Do not add every possible block to every design.
- Do not draw components without explaining why they exist.

#### Optional Anki

Q: What are common backend system design building blocks?
A: Edge, services, databases, caches, queues, workers, object storage, and observability.

</details>

<details>
<summary><strong>SD-ARCH-002. What is the role of a load balancer?</strong></summary>

#### Short answer

A load balancer distributes traffic across healthy backend instances.

#### Interview answer

A load balancer sits in front of multiple service instances and routes requests based on health, capacity, algorithm, and sometimes routing rules. It improves availability because one failed instance can be removed from rotation. It also helps horizontal scaling by letting the service add or remove instances behind a stable endpoint.

#### Deep dive

Load balancers can operate at different layers. Layer 4 balances TCP connections; Layer 7 understands HTTP and can route by path, host, headers, or cookies. They often integrate with health checks, TLS termination, connection draining, and deployment strategies.

#### Production angle

Bad health checks or timeout settings can route traffic to broken instances or amplify incidents.

#### Traps / caveats

- A load balancer does not fix a stateful application that cannot run on multiple nodes.
- It can become a single point of failure if not deployed redundantly.

#### Optional Anki

Q: Why use a load balancer?
A: To distribute traffic across healthy instances and support availability and horizontal scaling.

</details>

<a id="sd-arch-003"></a>

<details>
<summary><strong>SD-ARCH-003. Why are stateless application servers easier to scale?</strong></summary>

#### Short answer

Any request can be handled by any instance, so instances can be added, removed, restarted, or replaced freely.

#### Interview answer

Stateless servers keep durable state in external systems such as databases, caches, object storage, or session stores. This makes load balancing simple because requests do not need to return to the same instance. It also improves deployability because an instance can be killed or replaced without losing user state.

#### Deep dive

Stateless does not mean the application has no state. It means local process memory is not the source of truth for business state. Caches and in-memory data may still exist, but they should be rebuildable or treated as best-effort.

#### Production angle

Stateless services work better with autoscaling, rolling deployments, failure recovery, and container orchestration.

#### Traps / caveats

- Do not store critical sessions only in local memory if instances can disappear.
- Externalizing state can move the bottleneck to the database or cache.

#### Optional Anki

Q: What does stateless application server mean?
A: Business state is not tied to one process, so any instance can handle a request.

</details>

<a id="sd-arch-004"></a>

<details>
<summary><strong>SD-ARCH-004. What is an API Gateway, and what should not be put into it?</strong></summary>

#### Short answer

An API Gateway is an edge entry point for APIs; it should not become a dumping ground for domain logic.

#### Interview answer

An API Gateway can handle routing, TLS termination, authentication integration, rate limiting, request size limits, protocol translation, logging, and sometimes response aggregation. It should not own core business rules, persistence logic, or complex workflows that belong to domain services.

#### Deep dive

Gateways are useful when clients need one stable entry point or when cross-cutting edge concerns should be centralized. However, putting too much logic there creates a bottleneck, deployment coupling, and a hidden monolith.

#### Production angle

Gateway outages can affect all APIs, so timeout, retry, rate limit, and observability settings must be treated carefully.

#### Traps / caveats

- Do not put order pricing, inventory rules, or payment decisions in the gateway.
- Do not let response aggregation create slow fan-out without timeouts.

#### Optional Anki

Q: What belongs in an API Gateway?
A: Edge concerns such as routing, auth integration, rate limiting, TLS, logging, and protocol handling.

</details>

<a id="sd-arch-005"></a>

<details>
<summary><strong>SD-ARCH-005. When is a CDN useful in a backend design?</strong></summary>

#### Short answer

A CDN is useful for serving cacheable content close to users and reducing origin load.

#### Interview answer

A CDN works well for static assets, images, public files, downloads, and sometimes cacheable API responses. It reduces latency by using edge locations and reduces load on application servers or object storage. It is less useful for highly personalized, sensitive, or strongly consistent data.

#### Deep dive

CDN behavior depends on cache keys, TTLs, invalidation, headers, compression, and geographic distribution. For APIs, content negotiation, authorization, cookies, and query parameters can make caching risky.

#### Production angle

A CDN can protect origin systems during traffic spikes, but stale or incorrectly cached content can become a correctness or security incident.

#### Traps / caveats

- Do not cache private user data under a shared key.
- Do not assume CDN invalidation is instant everywhere.

#### Optional Anki

Q: What problem does a CDN solve?
A: It reduces latency and origin load by serving cacheable content near users.

</details>

<a id="sd-arch-006"></a>

<details>
<summary><strong>SD-ARCH-006. What is service discovery, and why is it needed in distributed systems?</strong></summary>

#### Short answer

Service discovery lets clients or routers find healthy service instances whose addresses change over time.

#### Interview answer

In dynamic environments, service instances are created, destroyed, moved, and scaled. Service discovery provides a way to resolve a logical service name to available instances. It may be implemented through DNS, a service registry, Kubernetes Services, a load balancer, or a service mesh.

#### Deep dive

Discovery is closely tied to health checks and routing. A registry that contains stale or unhealthy instances can cause failed requests. Different approaches trade off simplicity, freshness, client complexity, and operational control.

#### Production angle

Broken discovery can turn a partial outage into a full outage because traffic keeps reaching bad instances.

#### Traps / caveats

- Do not confuse service discovery with configuration management.
- Do not rely on discovery without readiness and health signals.

#### Optional Anki

Q: Why is service discovery needed?
A: Service instance addresses change, so callers need a way to find healthy endpoints.

</details>

<a id="sd-arch-007"></a>

<details>
<summary><strong>SD-ARCH-007. What is a background worker, and when should work be moved out of the request path?</strong></summary>

#### Short answer

A background worker processes asynchronous tasks outside the user-facing request path.

#### Interview answer

Move work to a worker when it is slow, retryable, bursty, non-critical for the immediate response, or involves external systems. Examples include email sending, image processing, report generation, webhook delivery, search indexing, and event publication. The request can accept the command, persist state, enqueue work, and return quickly.

#### Deep dive

Asynchronous workers improve latency and absorb bursts, but introduce delayed completion, retry logic, ordering concerns, idempotency, monitoring, and dead-letter handling.

#### Production angle

Worker systems need queue depth alerts, retry limits, poison-message handling, idempotent execution, and operational tooling for reprocessing.

#### Traps / caveats

- Do not move work async if the user must know the final result immediately.
- Do not enqueue work without a durable state transition if losing it would matter.

#### Optional Anki

Q: When should work be moved to a background worker?
A: When it is slow, retryable, bursty, or not required for the immediate response.

</details>

<a id="sd-arch-008"></a>

<details>
<summary><strong>SD-ARCH-008. How do object storage, relational databases and caches serve different roles?</strong></summary>

#### Short answer

Object storage holds large blobs, relational databases hold structured durable state, and caches hold fast temporary copies.

#### Interview answer

A relational database is a good source of truth for transactional entities and queries with constraints. Object storage is better for large immutable or semi-immutable files such as images, PDFs, backups, and exports. A cache stores data that can usually be recomputed or reloaded to reduce latency or backend load.

#### Deep dive

The roles should not be mixed casually. Storing large files in a relational database can hurt backup and query performance. Treating cache as the source of truth can cause data loss. Storing complex transactional state only in object storage can make updates and queries difficult.

#### Production angle

Correct storage choice affects cost, latency, backup, security, retention, and operational recovery.

#### Traps / caveats

- Do not store large user files in database rows by default.
- Do not store critical durable state only in cache.

#### Optional Anki

Q: What is object storage good for?
A: Large blobs such as images, videos, documents, exports, backups, and logs.

</details>

<a id="sd-arch-009"></a>

<details>
<summary><strong>SD-ARCH-009. How do you design API contracts so clients and services can evolve independently?</strong></summary>

#### Short answer

Design stable, explicit contracts with clear schemas, compatibility rules, validation, error formats, and versioning strategy.

#### Interview answer

I would define resource models, request and response schemas, status codes, error payloads, idempotency behavior, pagination, filtering, and authentication expectations. The contract should tolerate additive changes and avoid exposing internal database models directly. For service-to-service contracts, consumer-driven tests or schema compatibility checks can help detect breaking changes.

#### Deep dive

Independent evolution requires loose coupling. Clients should not depend on field ordering, internal IDs without meaning, undocumented enum values, or timing assumptions. Servers should handle older clients during rollout windows.

#### Production angle

API contract mistakes cause mobile app breakage, failed partner integrations, and deployment coupling between teams.

#### Traps / caveats

- Do not use JPA entities as external API models.
- Do not remove or change field meaning without a migration plan.

#### Optional Anki

Q: What makes an API contract evolvable?
A: Stable schemas, compatibility rules, clear errors, versioning, and separation from internal models.

</details>

<details>
<summary><strong>SD-ARCH-010. How do backward compatibility and API versioning affect system design?</strong></summary>

#### Short answer

They let old and new clients coexist while the system evolves safely.

#### Interview answer

Backward compatibility means existing clients continue working after server changes. In practice, prefer additive response fields, optional request fields, tolerant readers, stable error formats, and deprecation periods. Versioning is needed when behavior or schema changes cannot remain compatible.

#### Deep dive

Versioning can be done through URL paths, headers, media types, or separate endpoints. The choice matters less than clear ownership, documentation, observability by version, and a retirement process. Mobile and external clients often require longer compatibility windows than internal services.

#### Production angle

Without compatibility, deployments become coordinated releases and rollbacks become dangerous.

#### Traps / caveats

- Do not assume all clients update immediately.
- Do not introduce a new version for every small additive change.

#### Optional Anki

Q: Why does backward compatibility matter?
A: It allows existing clients to keep working while services evolve.

</details>

<a id="sd-arch-011"></a>

<details>
<summary><strong>SD-ARCH-011. What is a Backend for Frontend, and when is it useful?</strong></summary>

#### Short answer

A Backend for Frontend is an API layer tailored to one client type, such as web, mobile, or partner API.

#### Interview answer

A BFF adapts backend services to the needs of a specific frontend. It can shape responses, aggregate data, hide backend complexity, and optimize payloads for a client. It is useful when mobile, web, and partner clients need different API shapes or release cadences.

#### Deep dive

A BFF should remain a presentation and composition layer, not a second domain layer. If it accumulates business rules, it creates duplication and inconsistent behavior across clients.

#### Production angle

BFFs can improve client performance and team autonomy, but add deployable services, monitoring, and ownership boundaries.

#### Traps / caveats

- Do not put core business invariants only in a BFF.
- Do not create a BFF per screen without a strong reason.

#### Optional Anki

Q: What problem does a BFF solve?
A: It adapts backend APIs to the needs of a specific client type.

</details>

<a id="sd-arch-012"></a>

<details>
<summary><strong>SD-ARCH-012. How do reverse proxies, API gateways and load balancers differ?</strong></summary>

#### Short answer

They overlap, but a load balancer distributes traffic, a reverse proxy fronts servers, and an API gateway adds API-specific edge policies.

#### Interview answer

A reverse proxy accepts client requests and forwards them to backend servers, often handling TLS, compression, or caching. A load balancer focuses on distributing traffic across healthy instances. An API Gateway is usually a reverse proxy with API concerns such as authentication integration, routing, rate limiting, request validation, and API observability.

#### Deep dive

In real platforms one product may perform all three roles. In an interview, explain responsibilities rather than product names. The key is where routing, policy enforcement, and application-specific behavior live.

#### Production angle

Confusing these roles can put too much logic into the edge or leave important limits unenforced.

#### Traps / caveats

- Do not assume each role must be a separate component.
- Do not put domain workflow logic into edge infrastructure.

#### Optional Anki

Q: What is the main difference between load balancer and API Gateway?
A: A load balancer distributes traffic; an API Gateway applies API routing and edge policies.

</details>

<details>
<summary><strong>SD-ARCH-013. What are common single points of failure in a typical backend architecture?</strong></summary>

#### Short answer

Common single points include one database primary, one cache node, one queue, one gateway, one region, one DNS dependency, or one critical third-party service.

#### Interview answer

I look for components whose failure stops the whole system: primary database, shared cache, message broker, load balancer, API Gateway, configuration service, identity provider, object storage, or payment provider. Then I discuss redundancy, failover, graceful degradation, local caching, retries with limits, and manual recovery procedures.

#### Deep dive

Not every single point must be eliminated. Some are acceptable if the cost of redundancy is higher than the business risk. Senior design explains what fails, how users experience it, and how the team recovers.

#### Production angle

Single points of failure should be visible in architecture reviews, disaster recovery plans, and incident runbooks.

#### Traps / caveats

- Do not count a replicated component as safe without understanding failover behavior.
- Do not ignore third-party and control-plane dependencies.

#### Optional Anki

Q: What is a single point of failure?
A: A component whose failure can make the whole system or critical flow unavailable.

</details>
