# Data modeling, storage and database scaling

---

<a id="sd-data-001"></a>

<details>
<summary><strong>SD-DATA-001. How do you choose between a relational database and a NoSQL database?</strong></summary>

#### Short answer

Choose based on data model, query patterns, consistency needs, transactions, scale, and operational maturity.

#### Interview answer

A relational database is usually a strong default for structured data, joins, constraints, transactions, and reporting. A NoSQL database can fit when the access pattern is simple and high-scale, the data model is document or key-value oriented, or horizontal partitioning is a core requirement. The choice should be tied to invariants and queries, not fashion.

#### Deep dive

Relational databases often scale very far with good indexing, partitioning, and replicas. NoSQL systems trade some relational features for availability, partitioning, write throughput, flexible schema, or specialized access patterns.

#### Production angle

The wrong store makes correctness, migrations, debugging, and operations harder for years.

#### Traps / caveats

- Do not choose NoSQL only because the system is "large".
- Do not choose relational storage if the primary workload is massive append-only events with simple key access.

#### Optional Anki

Q: What is a good default storage choice for transactional business data?
A: A relational database, unless requirements clearly point elsewhere.

</details>

<a id="sd-data-002"></a>

<details>
<summary><strong>SD-DATA-002. How do access patterns influence data modeling?</strong></summary>

#### Short answer

Data should be modeled so common reads and writes are efficient, correct, and maintainable.

#### Interview answer

Before choosing tables or documents, I ask how data is created, queried, updated, deleted, sorted, filtered, and joined. A system that mostly reads by user ID needs a different model than one that searches by many filters or aggregates by time. Access patterns drive indexes, partition keys, denormalization, read models, and API shapes.

#### Deep dive

Relational systems can support more flexible querying, but still need indexes and schema design. Many NoSQL systems require access patterns to be known earlier because queries outside the key design may be expensive or impossible.

#### Production angle

Access-pattern mistakes lead to table scans, hot partitions, N+1 queries, fragile reports, and expensive migrations.

#### Traps / caveats

- Do not model only entities and ignore queries.
- Do not denormalize before knowing how updates will stay consistent.

#### Optional Anki

Q: Why start data modeling from access patterns?
A: Because reads, writes, filters, sorting, and consistency needs drive storage shape.

</details>

<a id="sd-data-003"></a>

<details>
<summary><strong>SD-DATA-003. What is denormalization, and when is it useful?</strong></summary>

#### Short answer

Denormalization duplicates or precomputes data to make reads faster or simpler.

#### Interview answer

Instead of joining multiple tables or services at read time, denormalization stores data in a shape closer to the required response. It is useful for feeds, dashboards, search documents, reporting, and read-heavy APIs. The trade-off is that duplicated data must be updated, rebuilt, or allowed to become temporarily stale.

#### Deep dive

Denormalization can happen inside one database, in a materialized view, search index, cache, or separate read model. It should usually be driven by measured read cost or known access patterns.

#### Production angle

Denormalized data needs backfill, repair, freshness monitoring, and reconciliation strategies.

#### Traps / caveats

- Do not denormalize data with strict consistency needs without a plan.
- Do not forget how deleted or corrected data propagates.

#### Optional Anki

Q: What is the main trade-off of denormalization?
A: Faster reads at the cost of duplicated data and consistency maintenance.

</details>

<a id="sd-data-004"></a>

<details>
<summary><strong>SD-DATA-004. What is database replication, and what problems does it solve?</strong></summary>

#### Short answer

Replication copies data from one database node to others for availability, read scaling, and disaster recovery.

#### Interview answer

Replication keeps copies of data on multiple nodes. Read replicas can serve read traffic, while standby replicas can support failover if the primary fails. Replication can also move data across availability zones or regions for resilience.

#### Deep dive

Replication may be synchronous or asynchronous. Synchronous replication gives stronger durability before commit but adds latency and coupling. Asynchronous replication is common for performance, but allows lag and possible data loss after primary failure.

#### Production angle

Replication is not enough by itself; you need failover procedures, monitoring, backup, consistency expectations, and application behavior during lag.

#### Traps / caveats

- Do not assume replicas are always fresh.
- Do not send writes to read replicas unless the system supports it intentionally.

#### Optional Anki

Q: Why use database replicas?
A: For read scaling, failover, availability, and disaster recovery.

</details>

<a id="sd-data-005"></a>

<details>
<summary><strong>SD-DATA-005. What is replication lag, and how can it affect users?</strong></summary>

#### Short answer

Replication lag is the delay before changes on the primary appear on replicas.

#### Interview answer

If a user writes data and then reads from a lagging replica, they may not see their own change. This can cause missing orders, stale balances, old profile data, or confusing UI behavior. For read-after-write flows, the design may read from primary, use session stickiness, wait for a replica position, or tolerate stale data explicitly.

#### Deep dive

Lag increases under write spikes, slow replicas, network issues, large transactions, or maintenance. It can also break background jobs and reporting if they assume fresh data.

#### Production angle

Replica lag should be monitored and included in routing, alerts, and fallback decisions.

#### Traps / caveats

- Do not use replicas for strongly consistent reads by default.
- Do not ignore lag during failover or backfills.

#### Optional Anki

Q: What is read-after-write risk with replicas?
A: A user may read from a replica before their recent write has replicated.

</details>

<a id="sd-data-006"></a>

<details>
<summary><strong>SD-DATA-006. What is partitioning or sharding?</strong></summary>

#### Short answer

Partitioning splits data into pieces; sharding usually means distributing those pieces across nodes.

#### Interview answer

Partitioning can split a table by time, tenant, ID range, hash, or another key. Sharding distributes partitions across multiple database nodes to increase capacity or isolate workloads. It helps when one node cannot handle storage, writes, reads, or operational size.

#### Deep dive

Partitioning inside one database can improve maintenance and query pruning, but does not necessarily add write capacity. Sharding adds horizontal scale but complicates queries, joins, transactions, migrations, and operations.

#### Production angle

Sharding should be introduced when simpler options are insufficient because it changes application and operational complexity significantly.

#### Traps / caveats

- Do not shard before understanding query patterns and growth.
- Do not choose a key that creates hot shards.

#### Optional Anki

Q: What is sharding?
A: Splitting data across multiple database nodes, usually by a shard key.

</details>

<a id="sd-data-007"></a>

<details>
<summary><strong>SD-DATA-007. How do you choose a shard key?</strong></summary>

#### Short answer

Choose a key that distributes load evenly and matches common access patterns.

#### Interview answer

A good shard key has high cardinality, avoids hot spots, and lets common queries hit one shard when possible. Examples include tenant ID, user ID, account ID, or a hash of an entity ID. The key should also support growth, rebalancing, and data locality requirements.

#### Deep dive

The best shard key depends on workload. Tenant ID may isolate customers but create huge shards for large tenants. Random hashes distribute evenly but make range queries and multi-entity queries harder.

#### Production angle

Shard key mistakes are expensive because changing them later requires data migration and application changes.

#### Traps / caveats

- Do not choose a timestamp-only shard key for high-write current data.
- Do not ignore large tenants or celebrity users.

#### Optional Anki

Q: What makes a good shard key?
A: Even distribution, high cardinality, query alignment, and manageable rebalancing.

</details>

<a id="sd-data-008"></a>

<details>
<summary><strong>SD-DATA-008. What are hot partitions, and how can they be avoided?</strong></summary>

#### Short answer

A hot partition receives disproportionate traffic and becomes a bottleneck.

#### Interview answer

Hot partitions happen when many reads or writes target the same key, range, tenant, celebrity account, or current time bucket. Mitigations include better shard keys, hash suffixes, splitting large tenants, caching hot reads, write spreading, batching, and special handling for high-fan-out users.

#### Deep dive

Hot partitions are not only a database problem. They also affect Kafka partitions, Redis keys, queues, object storage prefixes, and rate limit counters.

#### Production angle

Hot partition monitoring should include per-key or per-partition throughput, latency, throttling, and error rates.

#### Traps / caveats

- Do not assume average load means every partition is healthy.
- Do not spread writes so much that reads become impossible without aggregation.

#### Optional Anki

Q: What is a hot partition?
A: A partition or key receiving much more traffic than others.

</details>

<a id="sd-data-009"></a>

<details>
<summary><strong>SD-DATA-009. How do indexes affect read performance and write cost?</strong></summary>

#### Short answer

Indexes speed matching, sorting, and uniqueness checks, but every write must maintain them.

#### Interview answer

Indexes can turn table scans into targeted lookups and support ordering, filtering, joins, and constraints. The cost is extra storage, slower inserts and updates, more memory pressure, and maintenance work. In high-write systems, too many indexes can become a serious bottleneck.

#### Deep dive

Good index design depends on query predicates, sort order, cardinality, selectivity, and covering needs. Indexes are not magic; a wrong index may be unused or worse than no index.

#### Production angle

Index changes should be tested with real query plans and deployed safely, especially on large tables.

#### Traps / caveats

- Do not add indexes without checking the query plan.
- Do not ignore write amplification and storage cost.

#### Optional Anki

Q: What is the trade-off of indexes?
A: Faster reads and constraints at the cost of storage and slower writes.

</details>

<a id="sd-data-010"></a>

<details>
<summary><strong>SD-DATA-010. How do you evolve database schemas without breaking running services?</strong></summary>

#### Short answer

Use backward-compatible, phased migrations that support old and new application versions at the same time.

#### Interview answer

A common approach is expand, migrate, contract. First add nullable columns or new tables in a compatible way. Then deploy application code that can read and write both old and new forms. Backfill data safely. Finally, after all old code is gone, remove the old schema.

#### Deep dive

Zero-downtime schema evolution requires understanding locks, default values, constraints, indexes, and application rollout order. Destructive changes should be delayed until compatibility is proven.

#### Production angle

Schema changes are production incidents when they lock large tables, break old app versions, or corrupt data during partial rollout.

#### Traps / caveats

- Do not rename or drop columns while old code still uses them.
- Do not run large blocking migrations during peak traffic.

#### Optional Anki

Q: What is expand-migrate-contract?
A: Add compatible schema, move code/data to it, then remove the old schema later.

</details>

<a id="sd-data-011"></a>

<details>
<summary><strong>SD-DATA-011. How should large backfills or data migrations be designed?</strong></summary>

#### Short answer

Run them incrementally, idempotently, rate-limited, observable, and safely resumable.

#### Interview answer

For a large backfill, I would process data in small batches, checkpoint progress, limit database impact, and make each batch idempotent. The application should tolerate partially migrated data during the transition. I would monitor throughput, errors, locks, replication lag, and business validation checks.

#### Deep dive

Backfills should avoid long transactions and table-wide locks. They may need pause, resume, rollback, or repair tooling. Sometimes dual-writing or read-repair is needed while migration is in progress.

#### Production angle

Poor backfills cause database overload, replica lag, lock waits, stale caches, and inconsistent user-visible data.

#### Traps / caveats

- Do not run one huge transaction for millions of rows.
- Do not assume the migration will complete without interruption.

#### Optional Anki

Q: What properties should a large backfill have?
A: Incremental, idempotent, rate-limited, observable, and resumable.

</details>

<a id="sd-data-012"></a>

<details>
<summary><strong>SD-DATA-012. What is consistent hashing, and where is it useful?</strong></summary>

#### Short answer

Consistent hashing maps keys to nodes so adding or removing nodes moves only part of the keyspace.

#### Interview answer

In simple modulo sharding, changing the number of nodes can remap most keys. Consistent hashing places nodes and keys on a logical ring, so when a node is added or removed, only nearby key ranges move. It is useful in distributed caches, storage systems, routing, and partition assignment.

#### Deep dive

Real systems often use virtual nodes to smooth distribution and make rebalancing easier. Consistent hashing helps with movement, but it does not solve hot keys, replication, consistency, or failure detection by itself.

#### Production angle

It reduces cache churn and migration blast radius when cluster membership changes.

#### Traps / caveats

- Do not confuse consistent hashing with strong consistency.
- Do not ignore uneven load and virtual node configuration.

#### Optional Anki

Q: What problem does consistent hashing solve?
A: It reduces key movement when nodes are added or removed.

</details>

<a id="sd-data-013"></a>

<details>
<summary><strong>SD-DATA-013. What are the operational costs of sharding a database?</strong></summary>

#### Short answer

Sharding adds complexity to queries, transactions, migrations, backups, rebalancing, failover, and debugging.

#### Interview answer

Once data is split across shards, cross-shard joins and transactions become harder. The application may need shard routing, fan-out queries, per-shard migrations, rebalancing workflows, tenant movement, and shard-aware monitoring. Failures become partial: one shard may be down while others work.

#### Deep dive

Sharding is often a one-way door in complexity. It can be necessary at high scale, but before adopting it I would consider vertical scaling, indexing, partitioning, read replicas, caching, archival, and workload separation.

#### Production angle

Shard operations need automation, runbooks, dashboards, and clear ownership, otherwise routine maintenance becomes risky.

#### Traps / caveats

- Do not shard just to avoid query tuning.
- Do not forget that backups and restores become per-shard problems.

#### Optional Anki

Q: Why is sharding operationally expensive?
A: It complicates routing, queries, transactions, migrations, rebalancing, backups, and debugging.

</details>
