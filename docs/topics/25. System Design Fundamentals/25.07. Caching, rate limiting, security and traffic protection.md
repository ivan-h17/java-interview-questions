# Caching, rate limiting, security and traffic protection

---

<a id="sd-protect-001"></a>

<details>
<summary><strong>SD-PROTECT-001. When should you add a cache to a system design?</strong></summary>

#### Short answer

Add a cache when repeated reads are expensive, data can tolerate staleness, and cache failure behavior is understood.

#### Interview answer

Caching is useful for hot data, expensive computations, repeated lookups, public content, and read-heavy APIs. Before adding it, I ask whether the data changes often, whether stale data is acceptable, how it will be invalidated, and what happens when the cache is unavailable.

#### Deep dive

A cache is not a free performance layer. It adds invalidation, memory cost, consistency questions, serialization, eviction policy, and operational failure modes. Sometimes a better index or query fix is simpler.

#### Production angle

Cache success should be measured through hit rate, latency, database load reduction, stale-data incidents, and cache error behavior.

#### Traps / caveats

- Do not cache data that must always be fresh unless you have strict invalidation.
- Do not use a cache to hide fundamentally broken queries forever.

#### Optional Anki

Q: When is caching appropriate?
A: When reads are repeated, expensive, and can tolerate the cache's consistency model.

</details>

<a id="sd-protect-002"></a>

<details>
<summary><strong>SD-PROTECT-002. What is cache-aside, and what trade-offs does it have?</strong></summary>

#### Short answer

Cache-aside means the application checks the cache first, loads from the source on miss, then stores the result in cache.

#### Interview answer

In cache-aside, the application controls cache reads and writes. On a miss, it reads from the database or source service and puts the value in cache with a TTL. The pattern is simple and flexible, but data can become stale and multiple callers can rebuild the same missing key.

#### Deep dive

Invalidation is usually separate from loading. Writes may delete the cache key, update it, or rely on TTL. Each option has different consistency and complexity trade-offs.

#### Production angle

Cache-aside needs metrics for hit rate, miss latency, error rate, key size, evictions, and rebuild pressure.

#### Traps / caveats

- Do not forget to handle cache failure by falling back or failing deliberately.
- Do not let many concurrent misses overload the database.

#### Optional Anki

Q: How does cache-aside work?
A: Check cache, load source on miss, store the value, then return it.

</details>

<a id="sd-protect-003"></a>

<details>
<summary><strong>SD-PROTECT-003. What are cache invalidation and stale data risks?</strong></summary>

#### Short answer

Invalidation removes or updates cached data; stale data is the risk that users see old or incorrect values.

#### Interview answer

Caches improve performance by serving copies, but those copies can outlive the source data. Invalidation can happen through TTL, explicit delete on write, event-driven updates, versioned keys, or cache refresh. The correct approach depends on how stale the data may be and how expensive invalidation is.

#### Deep dive

Some stale data is harmless, such as product recommendations. Some is dangerous, such as permissions, account balances, inventory, or pricing. Design should classify data by freshness and correctness needs.

#### Production angle

Stale cache incidents are hard to debug unless cache keys, versions, writes, and invalidation events are observable.

#### Traps / caveats

- Do not cache authorization decisions without tenant, role, and permission context.
- Do not assume event-driven invalidation always arrives.

#### Optional Anki

Q: What is cache invalidation?
A: Removing or updating cached values when the source data changes.

</details>

<a id="sd-protect-004"></a>

<details>
<summary><strong>SD-PROTECT-004. What is cache stampede, and how can it be reduced?</strong></summary>

#### Short answer

Cache stampede happens when many requests rebuild the same missing or expired cache entry at once.

#### Interview answer

If a hot key expires, thousands of requests can miss the cache and hit the database simultaneously. Mitigations include TTL jitter, single-flight request coalescing, per-key locks, stale-while-revalidate, refresh-ahead, and rate limits on rebuilds.

#### Deep dive

Stampedes often happen after cache restart, synchronized TTL expiry, deployments, or traffic spikes. The mitigation depends on whether serving stale data is acceptable and how expensive regeneration is.

#### Production angle

Stampede protection prevents cache problems from becoming database outages.

#### Traps / caveats

- Do not use a global lock that serializes unrelated keys.
- Do not serve stale data for correctness-critical values without explicit business approval.

#### Optional Anki

Q: How do you reduce cache stampede?
A: TTL jitter, request coalescing, locks, stale-while-revalidate, refresh-ahead, and rebuild limits.

</details>

<a id="sd-protect-005"></a>

<details>
<summary><strong>SD-PROTECT-005. What is negative caching, and when is it useful?</strong></summary>

#### Short answer

Negative caching stores "not found" or failure-like results briefly to avoid repeated expensive misses.

#### Interview answer

If many requests ask for nonexistent users, invalid tokens, missing products, or unsupported routes, each miss can hit the database. Negative caching stores that absence for a short TTL. It is useful against repeated misses, scans, or cache penetration.

#### Deep dive

Negative cache TTLs should usually be short because missing data may be created later. The key must include the same context as the lookup, such as tenant, locale, or permission scope if relevant.

#### Production angle

Negative caching can protect databases from repeated invalid requests and some abuse patterns.

#### Traps / caveats

- Do not cache permanent absence for data that may soon be created.
- Do not cache authorization failures without considering permission changes.

#### Optional Anki

Q: What is negative caching?
A: Caching absence or not-found results for a limited time.

</details>

<a id="sd-protect-006"></a>

<details>
<summary><strong>SD-PROTECT-006. What is rate limiting, and what problems does it solve?</strong></summary>

#### Short answer

Rate limiting controls how many requests or actions a client, tenant, user, or key can perform over time.

#### Interview answer

Rate limiting protects shared systems from abuse, accidental overload, scraping, runaway clients, and unfair usage. Limits may apply per IP, user, API key, tenant, endpoint, or operation. The response should be clear, usually with HTTP 429 and retry guidance when appropriate.

#### Deep dive

Rate limiting is different from capacity scaling. Scaling increases capacity; rate limiting controls demand and fairness. A robust design often uses both.

#### Production angle

Good rate limits protect databases, third-party APIs, expensive jobs, and multi-tenant fairness.

#### Traps / caveats

- Do not rely only on IP limits for authenticated APIs behind NATs or proxies.
- Do not let unlimited retries bypass the rate limit.

#### Optional Anki

Q: What status code commonly represents rate limiting?
A: HTTP 429 Too Many Requests.

</details>

<a id="sd-protect-007"></a>

<details>
<summary><strong>SD-PROTECT-007. What is the difference between fixed window, sliding window and token bucket rate limiting?</strong></summary>

#### Short answer

Fixed window counts in fixed intervals, sliding window smooths boundary bursts, and token bucket allows controlled bursts.

#### Interview answer

Fixed window is simple: allow N requests per minute. It can allow bursts at window boundaries. Sliding window estimates or records requests over the last rolling period, giving smoother control at higher cost. Token bucket refills tokens at a steady rate and allows bursts up to bucket capacity.

#### Deep dive

The right algorithm depends on desired behavior, accuracy, memory, and distributed complexity. Token bucket is common for APIs because it supports burst tolerance while controlling long-term rate.

#### Production angle

Rate limiter choice affects user experience, fairness, infrastructure cost, and abuse resistance.

#### Traps / caveats

- Fixed windows can allow nearly double the intended rate around boundaries.
- Sliding logs can be memory-heavy for high-cardinality keys.

#### Optional Anki

Q: Which rate limiter allows controlled bursts?
A: Token bucket.

</details>

<a id="sd-protect-008"></a>

<details>
<summary><strong>SD-PROTECT-008. Where can rate limiting be enforced: client, gateway, service or data store?</strong></summary>

#### Short answer

It can be enforced at several layers, but authoritative limits should usually be server-side.

#### Interview answer

Client-side limits improve user experience but cannot be trusted. Gateway limits protect the edge and shared APIs. Service-level limits can apply domain-specific rules. Shared-store counters, often backed by Redis or a database, can coordinate limits across instances. Critical limits often need layered enforcement.

#### Deep dive

Placement affects context and cost. A gateway may know IP and API key but not full business state. A service may know tenant plan and operation type but sees traffic after it has already reached the service.

#### Production angle

Layered limits protect against both external abuse and internal fan-out overload.

#### Traps / caveats

- Do not trust client-only throttling for security or fairness.
- Do not put every limit in a central store if local approximate limits are enough.

#### Optional Anki

Q: Why use layered rate limiting?
A: To protect the edge, services, dependencies, and business quotas at different points.

</details>

<a id="sd-protect-009"></a>

<details>
<summary><strong>SD-PROTECT-009. How do quotas protect shared systems?</strong></summary>

#### Short answer

Quotas cap resource usage over a longer period to preserve fairness, cost control, and capacity.

#### Interview answer

A quota might limit API calls per day, export jobs per hour, storage per tenant, messages per month, or expensive searches per user. Unlike short-term rate limiting, quotas often represent product plans, billing limits, or operational fairness across tenants.

#### Deep dive

Quotas need clear counting semantics, reset windows, overage behavior, admin override, and user feedback. They should also be hard to bypass through retries, multiple workers, or alternate endpoints.

#### Production angle

Quotas prevent one customer or feature from consuming shared database, queue, storage, or third-party capacity.

#### Traps / caveats

- Do not count quota usage only after expensive work has already completed.
- Do not forget observability and support tooling for quota disputes.

#### Optional Anki

Q: How do quotas differ from rate limits?
A: Quotas cap usage over longer business periods; rate limits control request rate over short windows.

</details>

<a id="sd-protect-010"></a>

<details>
<summary><strong>SD-PROTECT-010. How do authentication, authorization and tenant context affect a system design?</strong></summary>

#### Short answer

They define who the caller is, what they can do, and which tenant's data and limits apply.

#### Interview answer

Authentication verifies identity. Authorization decides allowed actions. Tenant context scopes data, cache keys, rate limits, quotas, audit logs, and metrics. In a design, I would propagate identity and tenant context through the gateway, services, background jobs, and data access layer.

#### Deep dive

Authorization should be enforced close to the business operation, not only at the edge. Edge checks are useful, but services still need protection because internal callers, jobs, and new endpoints can bypass gateway assumptions.

#### Production angle

Missing tenant or authorization context causes data leaks, broken rate limits, wrong cache entries, and audit gaps.

#### Traps / caveats

- Do not rely only on frontend hiding of unauthorized actions.
- Do not cache user-specific data without tenant and permission context.

#### Optional Anki

Q: Why must tenant context be propagated?
A: It scopes data access, caching, quotas, logs, metrics, and authorization.

</details>

<a id="sd-protect-011"></a>

<details>
<summary><strong>SD-PROTECT-011. How do you protect PII, secrets and sensitive data in a high-level architecture?</strong></summary>

#### Short answer

Minimize collection, restrict access, encrypt appropriately, audit usage, and avoid leaking sensitive data through logs, caches, or events.

#### Interview answer

I would classify sensitive data, store only what is needed, encrypt in transit and at rest, keep secrets in a secret manager, enforce least privilege, and audit access. PII should not be casually copied into logs, analytics, search indexes, caches, or event payloads.

#### Deep dive

Security is also architectural. Data boundaries, token scopes, key rotation, retention, deletion, masking, and incident response should be considered early. For multi-tenant systems, tenant isolation is a core design constraint.

#### Production angle

Sensitive data leaks often happen through secondary systems, such as logs, traces, metrics, exports, and dead-letter queues.

#### Traps / caveats

- Do not put secrets in configuration files, images, or source code.
- Do not include full PII in broad integration events unless there is a strong reason.

#### Optional Anki

Q: Where can sensitive data leak besides the database?
A: Logs, traces, metrics, caches, events, search indexes, exports, and DLQs.

</details>

<a id="sd-protect-012"></a>

<details>
<summary><strong>SD-PROTECT-012. How do you design a distributed rate limiter with acceptable accuracy?</strong></summary>

#### Short answer

Use shared counters or coordinated local limits, and choose the accuracy, latency, availability, and cost trade-off deliberately.

#### Interview answer

For more accurate global limits, instances can use Redis or another shared store with atomic operations and TTLs. For very high traffic, local per-instance buckets with periodic synchronization may be acceptable if approximate limits are allowed. The design should define key scope, algorithm, TTL, failure behavior, and what happens when the limiter store is unavailable.

#### Deep dive

Distributed rate limiting involves trade-offs. A central store improves accuracy but adds latency and a dependency. Local limits are faster and more available but less accurate during uneven traffic or instance changes.

#### Production angle

Rate limiter failures need a policy: fail open for availability, fail closed for protection, or degrade by endpoint and tenant risk.

#### Traps / caveats

- Do not make every request depend on a slow central limiter without a timeout.
- Do not ignore clock skew and atomicity in distributed counters.

#### Optional Anki

Q: What is the main trade-off in distributed rate limiting?
A: Accuracy versus latency, availability, dependency cost, and complexity.

</details>

<a id="sd-protect-013"></a>

<details>
<summary><strong>SD-PROTECT-013. How can retries, caches and rate limits accidentally amplify outages?</strong></summary>

#### Short answer

They can increase load during failure if they are unbounded, synchronized, or misconfigured.

#### Interview answer

Retries can multiply traffic to a struggling service. Cache misses after expiration or restart can stampede the database. Rate limits that fail closed can block all users, while fail-open behavior can overload dependencies. These controls need timeouts, jitter, bounded retries, stale fallback, and monitoring.

#### Deep dive

Protective mechanisms interact. A cache outage may cause database overload, which triggers retries, which exhausts thread pools, which causes more timeouts. The design should model these chains.

#### Production angle

Outage amplification is one of the most common failure patterns in backend systems.

#### Traps / caveats

- Do not retry non-idempotent operations blindly.
- Do not use identical retry delays across all clients.

#### Optional Anki

Q: How can retries worsen an outage?
A: They multiply load against an already unhealthy dependency.

</details>
