# Synchronous, asynchronous and event-driven design

---

<a id="sd-comm-001"></a>

<details>
<summary><strong>SD-COMM-001. How do you explain trade-offs between synchronous and asynchronous design?</strong></summary>

#### Short answer

Synchronous design is simpler and immediate; asynchronous design decouples work but adds delay, retries, ordering, and observability challenges.

#### Interview answer

Synchronous request/response is good when the caller needs an immediate answer and the dependency is reliable enough within the latency budget. Asynchronous design is useful when work is slow, bursty, retryable, or does not need to finish before responding. The trade-off is that async systems need durable queues, idempotent consumers, monitoring, and user-visible state.

#### Deep dive

The choice is often per workflow step, not per whole system. A checkout request may synchronously validate the cart and create an order, then asynchronously send email or update search indexes.

#### Production angle

Asynchronous design can improve resilience, but only if failures, retries, and stuck work are observable and repairable.

#### Traps / caveats

- Do not use async to hide mandatory correctness work.
- Do not use synchronous fan-out without timeouts and failure isolation.

#### Optional Anki

Q: What is the main async trade-off?
A: Less temporal coupling and better burst handling at the cost of delayed completion and operational complexity.

</details>

<a id="sd-comm-002"></a>

<details>
<summary><strong>SD-COMM-002. When is synchronous request/response communication the right choice?</strong></summary>

#### Short answer

Use it when the caller needs an immediate result and the dependency fits the latency and availability budget.

#### Interview answer

Synchronous communication fits validation, reads, authorization checks, small commands, and workflows where the user cannot proceed without the result. It is easier to reason about than messaging and often simpler to debug. The dependency should have clear timeouts, errors, and fallback behavior.

#### Deep dive

Synchronous does not mean unsafe. It can be reliable when bounded, observable, and limited in fan-out. Problems appear when a request calls many downstream services sequentially or waits indefinitely.

#### Production angle

Synchronous APIs need latency budgets, circuit breakers where appropriate, request tracing, and client retry rules.

#### Traps / caveats

- Do not leave HTTP clients with infinite or very long default timeouts.
- Do not build deep synchronous call chains without understanding failure propagation.

#### Optional Anki

Q: When is synchronous communication appropriate?
A: When the caller needs an immediate answer within a known latency and failure budget.

</details>

<a id="sd-comm-003"></a>

<details>
<summary><strong>SD-COMM-003. When should work be processed asynchronously?</strong></summary>

#### Short answer

Use async processing for slow, bursty, retryable, or non-immediate work.

#### Interview answer

Examples include sending emails, image processing, report generation, webhook delivery, search indexing, event publishing, billing reconciliation, and notification fan-out. The request path can persist intent and return accepted, while workers process the task later.

#### Deep dive

Async processing requires a state model. The user or caller should know whether the operation is pending, completed, failed, or needs manual action. Workers need idempotency, retry policy, DLQ handling, and monitoring.

#### Production angle

Async work needs backlog alerts, age-of-oldest-message metrics, worker health, retry counts, and reprocessing tools.

#### Traps / caveats

- Do not return success if only enqueueing happened and final work may fail, unless the API semantics say so.
- Do not process async tasks without idempotency.

#### Optional Anki

Q: What kind of work is good for async processing?
A: Slow, bursty, retryable, or non-immediate work.

</details>

<a id="sd-comm-004"></a>

<details>
<summary><strong>SD-COMM-004. What is temporal coupling?</strong></summary>

#### Short answer

Temporal coupling means two components must be available and responsive at the same time for work to complete.

#### Interview answer

In synchronous calls, the caller and callee must both be up, reachable, and fast enough during the request. A queue reduces temporal coupling because producers can publish work even if consumers process it later. This improves resilience but changes the user experience and consistency model.

#### Deep dive

Temporal coupling is not always bad. Immediate validation or authorization often needs it. The design question is whether the business operation requires immediate completion or can tolerate delay.

#### Production angle

Reducing temporal coupling helps absorb outages and traffic spikes, but requires durable storage and recovery workflows.

#### Traps / caveats

- Do not confuse reduced temporal coupling with guaranteed success.
- Queues can hide consumer outages until backlog becomes severe.

#### Optional Anki

Q: What is temporal coupling?
A: A dependency where components must be available at the same time to complete work.

</details>

<a id="sd-comm-005"></a>

<details>
<summary><strong>SD-COMM-005. How do queues help absorb traffic spikes?</strong></summary>

#### Short answer

Queues buffer work so producers can accept bursts while consumers process at a controlled rate.

#### Interview answer

If requests arrive faster than workers can process them, a queue can store tasks temporarily instead of overloading the workers or database. Consumers can scale horizontally, process at a safe rate, and retry failures. This is useful for emails, notifications, file processing, and event-driven workflows.

#### Deep dive

Queues trade immediate completion for controlled delay. The design must size queue retention, worker throughput, retry strategy, ordering, and backpressure. Infinite backlog is not a solution.

#### Production angle

Key metrics are queue depth, age of oldest message, processing rate, failure rate, retry count, and DLQ size.

#### Traps / caveats

- Do not accept work faster than it can ever be processed.
- Do not let queue growth hide a dependency outage.

#### Optional Anki

Q: How does a queue absorb spikes?
A: It buffers work so consumers can process at a controlled pace.

</details>

<a id="sd-comm-006"></a>

<details>
<summary><strong>SD-COMM-006. What are the risks of queues and asynchronous processing?</strong></summary>

#### Short answer

Risks include delayed completion, duplicates, out-of-order messages, poison messages, backlog growth, and harder debugging.

#### Interview answer

Asynchronous systems are not simpler; they move complexity. Consumers may process messages more than once, fail halfway, or receive messages out of order. Queues may fill up, retries may amplify load, and users may need to see pending or failed status.

#### Deep dive

Async workflows require idempotency, retry limits, DLQs, ordering strategy, schema compatibility, correlation IDs, tracing, and reprocessing tools.

#### Production angle

Without strong observability, async failures become silent data loss or delayed business operations.

#### Traps / caveats

- Do not assume queue publish means business completion.
- Do not ignore poison messages that fail on every retry.

#### Optional Anki

Q: What are common async processing risks?
A: Duplicates, ordering issues, backlog, poison messages, delayed failure, and observability gaps.

</details>

<a id="sd-comm-007"></a>

<details>
<summary><strong>SD-COMM-007. What is message ordering, and when does it matter?</strong></summary>

#### Short answer

Message ordering means processing events in the intended sequence; it matters when later events depend on earlier state.

#### Interview answer

Ordering matters for account state, inventory changes, workflow transitions, and per-user timelines. It may not matter for independent notifications or analytics events. Partitioned brokers such as Kafka preserve order within a partition, so the partition key should match the entity whose order matters.

#### Deep dive

Global ordering is expensive and often unnecessary. Per-aggregate ordering, such as per order ID or account ID, is usually enough. Consumers should still handle duplicates and late events defensively.

#### Production angle

Ordering bugs cause impossible states, missed transitions, negative balances, or stale projections.

#### Traps / caveats

- Do not assume order across Kafka partitions.
- Do not choose a random partition key if per-entity order matters.

#### Optional Anki

Q: Where does Kafka preserve ordering?
A: Within a single partition, not globally across all partitions.

</details>

<a id="sd-comm-008"></a>

<details>
<summary><strong>SD-COMM-008. How should duplicate messages be handled?</strong></summary>

#### Short answer

Design consumers to be idempotent and track processed operations when duplicates matter.

#### Interview answer

Most reliable messaging systems can deliver at least once, which means duplicates are expected. A consumer should use message IDs, business keys, deduplication tables, unique constraints, or idempotent state transitions. Reprocessing the same message should not create duplicate side effects.

#### Deep dive

Deduplication scope matters. A message ID may be unique globally, per topic, per producer, or per business entity. For long-running systems, deduplication retention must match the retry and replay window.

#### Production angle

Duplicate handling protects payments, emails, inventory adjustments, and external API calls.

#### Traps / caveats

- Do not rely on exactly-once marketing claims across external side effects.
- Do not deduplicate only in memory if consumers can restart.

#### Optional Anki

Q: What delivery model requires idempotent consumers?
A: At-least-once delivery.

</details>

<a id="sd-comm-009"></a>

<details>
<summary><strong>SD-COMM-009. What is a dead-letter queue, and when is it useful?</strong></summary>

#### Short answer

A dead-letter queue stores messages that could not be processed after retry limits or validation failures.

#### Interview answer

DLQs prevent poison messages from blocking normal processing forever. After a message fails repeatedly or is clearly invalid, it is moved to a separate queue with error metadata for inspection, alerting, repair, or replay.

#### Deep dive

A DLQ is not a trash can. It needs ownership, retention, dashboards, alerts, and a safe reprocessing procedure. Some failures are technical and retryable; others are business failures that need correction.

#### Production angle

DLQ growth is often a signal of schema mismatch, bad deploy, data corruption, or downstream outage.

#### Traps / caveats

- Do not move messages to DLQ silently without alerting.
- Do not replay DLQ messages without understanding whether the consumer is idempotent.

#### Optional Anki

Q: What is a DLQ for?
A: Isolating repeatedly failing messages for inspection, repair, and safe reprocessing.

</details>

<a id="sd-comm-010"></a>

<details>
<summary><strong>SD-COMM-010. How do you evolve event schemas safely?</strong></summary>

#### Short answer

Use compatible changes, versioning rules, tolerant consumers, schema validation, and staged rollout.

#### Interview answer

Event producers and consumers are often deployed independently. Safe changes are usually additive: add optional fields, keep old fields during migration, avoid changing meaning, and document compatibility. For breaking changes, introduce a new event version or topic and run old and new consumers during transition.

#### Deep dive

Consumers should ignore unknown fields and handle missing optional fields. Schema registries or contract tests can help detect incompatible changes before deployment.

#### Production angle

Event schema breakage can stop consumers, fill DLQs, corrupt projections, or cause silent data loss.

#### Traps / caveats

- Do not remove or rename fields while old consumers still depend on them.
- Do not reuse the same event name with changed semantics.

#### Optional Anki

Q: What event schema changes are usually safest?
A: Additive, optional changes with tolerant consumers.

</details>

<a id="sd-comm-011"></a>

<details>
<summary><strong>SD-COMM-011. What is the Outbox pattern, and what problem does it solve?</strong></summary>

#### Short answer

Outbox stores events in the same database transaction as business changes, then publishes them asynchronously.

#### Interview answer

The Outbox pattern solves the dual-write problem: updating the database and publishing a message cannot be atomic if done as two separate operations. Instead, the service writes business data and an outbox row in one local transaction. A relay later reads the outbox and publishes to the broker.

#### Deep dive

Outbox gives reliable publication, but consumers may still receive duplicates. The relay needs ordering, retries, locking or claiming, cleanup, and monitoring.

#### Production angle

Outbox is common for event-driven microservices because it preserves local transaction correctness while avoiding distributed transactions.

#### Traps / caveats

- Outbox does not remove the need for idempotent consumers.
- Do not forget relay lag and stuck outbox monitoring.

#### Optional Anki

Q: What problem does Outbox solve?
A: The dual-write problem between database commit and message publication.

</details>

<a id="sd-comm-012"></a>

<details>
<summary><strong>SD-COMM-012. How do you design reprocessing for failed asynchronous workflows?</strong></summary>

#### Short answer

Make reprocessing idempotent, observable, scoped, rate-limited, and auditable.

#### Interview answer

Failed messages should carry enough metadata to understand the cause: payload, headers, correlation ID, error, attempt count, and timestamps. Reprocessing should allow selecting a safe subset, fixing data or code first, replaying at a controlled rate, and tracking results. Consumers must handle duplicates and already-completed work.

#### Deep dive

Reprocessing can be from DLQ, original topic replay, outbox replay, or a repair job. The right method depends on retention, ordering, side effects, and whether downstream systems can tolerate duplicates.

#### Production angle

Without safe reprocessing, teams either lose data or perform risky manual database changes during incidents.

#### Traps / caveats

- Do not replay failed messages at full speed into a still-broken dependency.
- Do not replay operations with external side effects unless idempotency is proven.

#### Optional Anki

Q: What properties should reprocessing have?
A: Idempotent, scoped, rate-limited, observable, and auditable.

</details>
