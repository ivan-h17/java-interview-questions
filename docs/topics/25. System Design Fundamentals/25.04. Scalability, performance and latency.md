# Scalability, performance and latency

---

<a id="sd-scale-001"></a>

<details>
<summary><strong>SD-SCALE-001. What is the difference between vertical and horizontal scaling?</strong></summary>

#### Short answer

Vertical scaling makes one machine bigger; horizontal scaling adds more machines or instances.

#### Interview answer

Vertical scaling means increasing CPU, memory, disk, or network capacity of one node. Horizontal scaling means adding more nodes and distributing work across them. Vertical scaling is simpler, but has hardware and cost limits. Horizontal scaling can handle more load but requires stateless services, partitioning, load balancing, and more operational complexity.

#### Deep dive

Some components scale vertically more easily, such as a single database primary. Stateless application services usually scale horizontally better. Many real systems use both: bigger database nodes plus horizontally scaled app services and workers.

#### Production angle

Scaling choice affects deployment, failure domains, licensing, cost, and operational tooling.

#### Traps / caveats

- Horizontal scaling is not automatic if the workload has shared state or locks.
- Vertical scaling can postpone architectural work but not remove all limits.

#### Optional Anki

Q: What is horizontal scaling?
A: Adding more nodes or instances and distributing work across them.

</details>

<a id="sd-scale-002"></a>

<details>
<summary><strong>SD-SCALE-002. What makes a system horizontally scalable?</strong></summary>

#### Short answer

It can add instances and distribute work without shared bottlenecks or correctness problems.

#### Interview answer

A horizontally scalable system usually has stateless application instances, load balancing, externalized durable state, partitionable workloads, safe concurrency, and independent workers. It also needs shared dependencies, such as databases and caches, to scale or remain within capacity.

#### Deep dive

The application tier is often the easiest part to scale. The harder parts are data ownership, hot keys, queues, cross-node coordination, distributed locks, connection pools, and external dependencies.

#### Production angle

Horizontal scaling needs observability and autoscaling signals, otherwise adding instances may overload the database or downstream services faster.

#### Traps / caveats

- Adding app instances can increase pressure on the database.
- In-memory state, local sessions, and singleton schedulers can break horizontal scaling.

#### Optional Anki

Q: What is required for horizontal scalability?
A: Stateless or partitionable work, load balancing, externalized state, and scalable shared dependencies.

</details>

<a id="sd-scale-003"></a>

<details>
<summary><strong>SD-SCALE-003. How do you scale a read-heavy backend service?</strong></summary>

#### Short answer

Use efficient queries, indexes, caching, read replicas, CDN, pagination, and read models when needed.

#### Interview answer

I first optimize the access pattern and database queries. Then I consider indexes, pagination, response shaping, caching hot data, read replicas for non-critical reads, CDN for public cacheable content, and denormalized read models for complex views. The right choice depends on freshness and consistency requirements.

#### Deep dive

Read scaling often introduces staleness. A cache can serve old data, a replica can lag, and a read model can be delayed. The design must define which reads need fresh data and which can tolerate delay.

#### Production angle

Read-heavy systems should monitor cache hit rate, replica lag, slow queries, p95 and p99 latency, and database CPU and I/O.

#### Traps / caveats

- Do not send read-after-write flows to lagging replicas blindly.
- Do not cache authorization-sensitive data under an unsafe key.

#### Optional Anki

Q: What are common read-scaling techniques?
A: Indexes, caching, read replicas, CDN, pagination, and denormalized read models.

</details>

<a id="sd-scale-004"></a>

<details>
<summary><strong>SD-SCALE-004. How do you scale a write-heavy backend service?</strong></summary>

#### Short answer

Protect the write path with good data modeling, batching, partitioning, backpressure, idempotency, and careful indexing.

#### Interview answer

For write-heavy systems, I would check whether writes are transactional commands, append-only events, logs, or counters. Then I would reduce unnecessary indexes, batch where acceptable, partition by a good key, avoid hot keys, use queues for burst smoothing, and make retries idempotent. If one primary database is the limit, sharding or specialized storage may be needed.

#### Deep dive

Writes are harder to scale because they often carry correctness and ordering requirements. Caches rarely solve write capacity directly. They may even add invalidation work.

#### Production angle

Write-heavy systems need monitoring for lock waits, WAL or commit latency, disk I/O, replication lag, queue backlog, and retry storms.

#### Traps / caveats

- Do not add indexes casually to high-write tables.
- Do not use asynchronous writes when the user needs durable confirmation.

#### Optional Anki

Q: Why are writes harder to scale than reads?
A: They usually require durability, consistency, ordering, constraints, and conflict handling.

</details>

<a id="sd-scale-005"></a>

<details>
<summary><strong>SD-SCALE-005. How do you reduce end-user latency?</strong></summary>

#### Short answer

Reduce network distance, request work, dependency calls, payload size, slow queries, and blocking operations.

#### Interview answer

I would profile the request path and break latency into client, network, gateway, service, database, cache, and downstream calls. Improvements may include CDN, edge caching, regional placement, fewer round trips, parallel safe calls, smaller payloads, better indexes, caching, asynchronous processing, and timeouts.

#### Deep dive

Latency work should be evidence-driven. Optimizing CPU code will not help if p99 latency is caused by database locks or a slow third-party call. Reducing tail latency often matters more than improving the median.

#### Production angle

Latency budgets should be allocated per dependency, with tracing to identify where time is spent.

#### Traps / caveats

- Do not optimize code before measuring the bottleneck.
- Do not parallelize calls without bounding fan-out and downstream load.

#### Optional Anki

Q: What is a latency budget?
A: A target allocation of response time across components in the request path.

</details>

<a id="sd-scale-006"></a>

<details>
<summary><strong>SD-SCALE-006. What is tail latency, and why do p95 and p99 matter?</strong></summary>

#### Short answer

Tail latency describes the slowest requests; p95 and p99 show user pain hidden by averages.

#### Interview answer

If p99 latency is 2 seconds, then 1 percent of requests are slower than 2 seconds. In high-traffic systems, that can affect many users. Tail latency matters because slow database queries, GC pauses, lock contention, retries, queue waits, and noisy neighbors often appear in the tail before they affect averages.

#### Deep dive

Distributed systems amplify tail latency. If one request fans out to 20 services, the probability that at least one call is slow increases. Timeouts, hedging, caching, and reducing fan-out can help, but each has trade-offs.

#### Production angle

SLOs should usually use percentiles and error rates, not only average latency.

#### Traps / caveats

- Averages can look healthy while many users suffer.
- p99 metrics need enough traffic volume to be meaningful.

#### Optional Anki

Q: What does p99 latency mean?
A: 99 percent of requests are at or below that latency, and 1 percent are slower.

</details>

<a id="sd-scale-007"></a>

<details>
<summary><strong>SD-SCALE-007. How do caching, batching and pagination improve performance?</strong></summary>

#### Short answer

Caching avoids repeated work, batching reduces per-operation overhead, and pagination limits response and query size.

#### Interview answer

Caching can reduce database load and latency for repeated reads. Batching groups multiple operations to reduce network round trips, transaction overhead, or broker calls. Pagination prevents huge queries and responses by returning bounded chunks of data.

#### Deep dive

Each technique has trade-offs. Caching introduces staleness and invalidation. Batching increases delay and can complicate error handling. Pagination must be stable and efficient, often requiring keyset pagination for large datasets.

#### Production angle

These techniques protect shared dependencies, but they need metrics: hit rate, batch size, queue delay, page latency, and query plans.

#### Traps / caveats

- Do not use offset pagination blindly on very large tables.
- Do not batch so much that latency or retry blast radius becomes unacceptable.

#### Optional Anki

Q: What does pagination protect against?
A: Large unbounded queries, large responses, memory pressure, and slow user requests.

</details>

<a id="sd-scale-008"></a>

<details>
<summary><strong>SD-SCALE-008. What is backpressure, and why does it matter for scalability?</strong></summary>

#### Short answer

Backpressure is a way for overloaded consumers to slow or reject producers before the system collapses.

#### Interview answer

If producers send work faster than consumers can process it, queues grow, latency increases, memory fills, and retries make it worse. Backpressure can be implemented with bounded queues, rate limits, semaphores, load shedding, client throttling, or broker flow control. It keeps overload visible and bounded.

#### Deep dive

Backpressure is not just a reactive programming concept. It applies to HTTP APIs, worker pools, database connections, message consumers, file processing, and downstream integrations.

#### Production angle

Without backpressure, systems fail late and broadly instead of rejecting excess work early and predictably.

#### Traps / caveats

- Unbounded queues hide overload until recovery is harder.
- Backpressure must be paired with clear client error behavior and retry guidance.

#### Optional Anki

Q: What problem does backpressure solve?
A: It prevents fast producers from overwhelming slower consumers.

</details>

<a id="sd-scale-009"></a>

<details>
<summary><strong>SD-SCALE-009. What is load shedding, and when is it acceptable?</strong></summary>

#### Short answer

Load shedding intentionally rejects or drops lower-priority work to preserve critical functionality.

#### Interview answer

When a system is overloaded, it may be better to reject optional requests than to let everything time out. Examples include dropping recommendation requests, rejecting expensive exports, serving stale data, or returning 429 or 503 for non-critical traffic. The policy should protect critical paths and be visible to clients.

#### Deep dive

Load shedding should be explicit and prioritized. It can happen at a gateway, service, queue, worker, or dependency client. It is safer when operations are idempotent and clients know how to retry.

#### Production angle

Load shedding can turn a total outage into partial degradation.

#### Traps / caveats

- Do not shed critical writes such as payments without a business decision.
- Do not let clients retry shed requests immediately without backoff.

#### Optional Anki

Q: What is load shedding?
A: Intentionally rejecting or dropping work to protect system stability under overload.

</details>

<a id="sd-scale-010"></a>

<details>
<summary><strong>SD-SCALE-010. How do you decide whether to optimize code, database queries or architecture first?</strong></summary>

#### Short answer

Measure the bottleneck first, then choose the smallest change that addresses the real constraint.

#### Interview answer

I would look at metrics and traces: where is time spent, what resource is saturated, and which requests are slow. If the database query is slow, fix indexes or query shape. If CPU is saturated, optimize code or scale instances. If synchronous fan-out dominates, change architecture, add caching, or move work async.

#### Deep dive

Architecture changes are expensive and risky. Often the best first step is query tuning, better pagination, removing N+1 calls, or adding a missing timeout. But if the workload fundamentally exceeds a single component's limits, architecture must change.

#### Production angle

Evidence-based optimization avoids wasting weeks on changes that do not move user-facing metrics.

#### Traps / caveats

- Do not start with a rewrite before diagnosing.
- Do not optimize microbenchmarks while p99 is dominated by I/O or locks.

#### Optional Anki

Q: What should drive optimization priority?
A: Measurements from metrics, logs, traces, profiles, and query plans.

</details>

<a id="sd-scale-011"></a>

<details>
<summary><strong>SD-SCALE-011. What is the thundering herd problem?</strong></summary>

#### Short answer

A thundering herd happens when many clients or workers wake up and hit the same resource at once.

#### Interview answer

Common examples are many cache entries expiring simultaneously, many clients retrying after an outage, or many workers competing for the same lock or job. The result is a sudden spike that overloads a database, cache, API, or queue. Mitigations include jitter, request coalescing, single-flight, staggered TTLs, rate limits, and backoff.

#### Deep dive

The problem is often self-inflicted by synchronized timers, fixed retry delays, batch schedules, or cache TTLs. It is especially dangerous during recovery because systems are already degraded.

#### Production angle

Thundering herd can convert a small outage into a cascading failure.

#### Traps / caveats

- Do not set identical TTLs for millions of hot keys.
- Do not retry all failed requests after the same fixed delay.

#### Optional Anki

Q: How do you reduce thundering herd risk?
A: Use jitter, backoff, rate limits, staggered TTLs, and request coalescing.

</details>

<a id="sd-scale-012"></a>

<details>
<summary><strong>SD-SCALE-012. How do you prevent one noisy tenant or customer from degrading the whole system?</strong></summary>

#### Short answer

Use isolation, quotas, rate limits, fair scheduling, separate capacity pools, and tenant-aware observability.

#### Interview answer

A noisy tenant can consume too much CPU, database capacity, queue capacity, cache space, or third-party quota. I would enforce per-tenant rate limits and quotas, isolate heavy tenants when needed, apply fair queueing, cap expensive operations, and monitor usage by tenant. For large customers, dedicated resources or partitions may be justified.

#### Deep dive

Multi-tenant systems need tenant context in requests, data access, cache keys, metrics, logs, and billing. Isolation can be logical, such as tenant IDs and quotas, or physical, such as separate databases or clusters.

#### Production angle

Noisy-tenant protection preserves fairness and prevents one customer's workload from becoming an incident for everyone.

#### Traps / caveats

- Do not rely only on global rate limits.
- Do not forget tenant context in caches and background jobs.

#### Optional Anki

Q: What protects shared systems from noisy tenants?
A: Per-tenant quotas, rate limits, isolation, fair scheduling, and tenant-aware monitoring.

</details>
