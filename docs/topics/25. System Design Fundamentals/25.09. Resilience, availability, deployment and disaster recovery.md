# Resilience, availability, deployment and disaster recovery

---

<a id="sd-res-001"></a>

<details>
<summary><strong>SD-RES-001. What are availability, reliability and fault tolerance?</strong></summary>

#### Short answer

Availability is being usable, reliability is working correctly over time, and fault tolerance is continuing despite failures.

#### Interview answer

Availability answers "can users use it now?" Reliability answers "does it behave correctly over time?" Fault tolerance is the system's ability to handle component failures without total failure. A system can be available but unreliable if it returns wrong results, and reliable but unavailable if it is correct only when up.

#### Deep dive

These terms map to different design choices. Availability needs redundancy and failover. Reliability needs correctness, testing, monitoring, and recovery. Fault tolerance needs isolation, graceful degradation, retries, and fallback strategies.

#### Production angle

A senior design defines what failure means for each critical user flow, not just the whole system.

#### Traps / caveats

- Do not equate availability with correctness.
- Do not promise fault tolerance without discussing dependency failures.

#### Optional Anki

Q: What is fault tolerance?
A: The ability to continue operating, possibly degraded, despite component failures.

</details>

<a id="sd-res-002"></a>

<details>
<summary><strong>SD-RES-002. What is a single point of failure?</strong></summary>

#### Short answer

A single point of failure is a component whose failure can stop a critical part of the system.

#### Interview answer

Examples include one database primary without failover, one gateway, one queue, one cache used as a hard dependency, one availability zone, one configuration service, or one third-party provider. The design should identify these and decide whether to add redundancy, fallback, or accept the risk.

#### Deep dive

Not all single points are equally risky. A reporting service outage may be acceptable; payment provider outage may stop revenue. The business impact determines how much redundancy is justified.

#### Production angle

SPOFs should appear in architecture reviews, runbooks, disaster recovery plans, and monitoring.

#### Traps / caveats

- Do not assume managed services have no failure modes.
- Do not ignore operational single points such as DNS, secrets, or CI/CD.

#### Optional Anki

Q: What is an SPOF?
A: A component whose failure can stop a critical system function.

</details>

<a id="sd-res-003"></a>

<details>
<summary><strong>SD-RES-003. How do redundancy and failover improve availability?</strong></summary>

#### Short answer

Redundancy provides spare capacity or copies; failover switches traffic or responsibility when one part fails.

#### Interview answer

Running multiple app instances behind a load balancer gives redundancy. Database replicas, multi-AZ deployments, multiple queue brokers, and multiple gateways do the same for other layers. Failover moves work away from unhealthy components, ideally automatically and safely.

#### Deep dive

Redundancy only helps if failure detection and failover behavior work. Split brain, stale replicas, bad health checks, and overloaded remaining nodes can still cause outages.

#### Production angle

Failover should be tested regularly, not discovered for the first time during an incident.

#### Traps / caveats

- Do not assume failover is lossless with asynchronous replication.
- Do not run all replicas in the same failure domain.

#### Optional Anki

Q: What is failover?
A: Moving traffic or responsibility from a failed component to a healthy one.

</details>

<a id="sd-res-004"></a>

<details>
<summary><strong>SD-RES-004. What is graceful degradation?</strong></summary>

#### Short answer

Graceful degradation means preserving critical functionality while non-critical features fail or are reduced.

#### Interview answer

If recommendations are down, an e-commerce site can still show product pages and checkout. If a notification provider is slow, the order can still be created and notification retried later. The design should classify critical and optional features so failures do not take down everything.

#### Deep dive

Graceful degradation can use stale data, fallback content, disabled features, lower quality results, queueing, or read-only mode. It must be explicit so users and operators understand what is happening.

#### Production angle

Graceful degradation reduces blast radius and protects revenue-critical paths during partial outages.

#### Traps / caveats

- Do not degrade silently when users need to know the final state.
- Do not use fallback data that can violate business correctness.

#### Optional Anki

Q: What is graceful degradation?
A: Keeping critical functions available while reducing or disabling non-critical behavior.

</details>

<a id="sd-res-005"></a>

<details>
<summary><strong>SD-RES-005. What is a fallback, and when can it be dangerous?</strong></summary>

#### Short answer

A fallback is alternative behavior when the primary path fails; it is dangerous when it returns incorrect, unsafe, or misleading results.

#### Interview answer

Examples include serving cached data, using a default price, skipping recommendations, or routing to a backup provider. Fallbacks are useful for optional or degraded behavior. They are dangerous for payments, authorization, inventory, compliance decisions, and anything where stale or guessed data can violate rules.

#### Deep dive

Fallbacks need clear scope, freshness limits, observability, and business approval. A fallback that always succeeds can hide a major outage until data is wrong.

#### Production angle

Fallback usage should be tracked as a signal of dependency health.

#### Traps / caveats

- Do not fallback to "allow" for security checks.
- Do not use stale prices or balances unless the business accepts the risk.

#### Optional Anki

Q: When are fallbacks risky?
A: When stale or default data can break correctness, security, money, or compliance.

</details>

<a id="sd-res-006"></a>

<details>
<summary><strong>SD-RES-006. How do timeouts, retries and exponential backoff improve resilience?</strong></summary>

#### Short answer

Timeouts bound waiting, retries handle transient failures, and exponential backoff reduces pressure during recovery.

#### Interview answer

Timeouts prevent threads or event loops from waiting forever. Retries help when failures are temporary, such as packet loss or brief overload. Exponential backoff spaces retries out, and jitter prevents many clients from retrying at the same time.

#### Deep dive

Retries should be limited and used only when operations are idempotent or safely deduplicated. Timeout values should fit the caller's latency budget and dependency behavior. Retrying inside every layer can multiply traffic.

#### Production angle

Correct retry design can improve user experience; bad retry design can cause cascading failures.

#### Traps / caveats

- Do not retry non-idempotent writes blindly.
- Do not set timeouts longer than the caller's own deadline.

#### Optional Anki

Q: What does exponential backoff do?
A: It increases delay between retries to reduce load on an unhealthy dependency.

</details>

---

<a id="sd-res-007"></a>

<details>
<summary><strong>SD-RES-007. Why should retries use jitter?</strong></summary>

#### Short answer

Jitter randomizes retry delays so clients do not retry in synchronized waves.

#### Interview answer

Without jitter, thousands of clients may retry after exactly 1 second, then 2 seconds, then 4 seconds, creating repeated traffic spikes. Jitter spreads retries over time and makes recovery smoother. It is especially important for large fleets and public APIs.

#### Deep dive

Jitter can be full randomization or a bounded random adjustment around the backoff delay. The goal is to avoid synchronized behavior while still giving the dependency time to recover.

#### Production angle

Jitter reduces thundering herd risk during outages, deploys, and failovers.

#### Traps / caveats

- Do not use fixed retry delays at high scale.
- Jitter does not make unsafe operations safe to retry.

#### Optional Anki

Q: Why add jitter to retry backoff?
A: To avoid synchronized retry spikes.

</details>

<a id="sd-res-008"></a>

<details>
<summary><strong>SD-RES-008. What is a circuit breaker?</strong></summary>

#### Short answer

A circuit breaker stops calls to an unhealthy dependency temporarily so failures happen fast and recovery has room.

#### Interview answer

A circuit breaker tracks failures, timeouts, or slow calls. When the failure threshold is exceeded, it opens and rejects calls immediately or uses a fallback. After a delay, it allows limited trial calls in half-open state to see whether the dependency recovered.

#### Deep dive

Circuit breakers protect callers and dependencies from repeated expensive failures. They should be combined with timeouts, bulkheads, metrics, and clear fallback behavior.

#### Production angle

Circuit breaker state should be observable because an open breaker may explain sudden request failures.

#### Traps / caveats

- Do not use circuit breakers without sensible timeouts.
- Do not hide an open circuit behind silent fallback for critical operations.

#### Optional Anki

Q: What are common circuit breaker states?
A: Closed, open, and half-open.

</details>

<a id="sd-res-009"></a>

<details>
<summary><strong>SD-RES-009. What are RPO and RTO?</strong></summary>

#### Short answer

RPO is the maximum acceptable data loss window; RTO is the maximum acceptable recovery time.

#### Interview answer

Recovery Point Objective answers how much data the business can lose, such as 5 minutes of writes. Recovery Time Objective answers how long the system can be unavailable before recovery, such as 30 minutes. These targets shape backups, replication, failover, and disaster recovery design.

#### Deep dive

Lower RPO and RTO usually cost more. Near-zero data loss and near-instant recovery require strong replication, automation, testing, and operational maturity.

#### Production angle

RPO and RTO should be defined per business capability, not only for the whole company.

#### Traps / caveats

- Backups alone do not guarantee a low RTO if restore takes hours.
- Asynchronous replication may not meet zero RPO.

#### Optional Anki

Q: What is RPO?
A: The maximum acceptable amount of data loss after a failure.

</details>

<a id="sd-res-010"></a>

<details>
<summary><strong>SD-RES-010. How do dependency availability and SLOs affect the overall system?</strong></summary>

#### Short answer

The system cannot be more available than its critical dependencies unless it has fallbacks, redundancy, or degraded modes.

#### Interview answer

If every request requires a dependency with 99.5 percent availability, the user-facing path is limited by that dependency. Multiple serial dependencies reduce effective availability. To improve, the design can cache, degrade, queue, use multiple providers, remove the dependency from the critical path, or define a lower SLO for that feature.

#### Deep dive

Availability composition depends on whether dependencies are serial, parallel, optional, or redundant. Critical path mapping is needed before promising an SLO.

#### Production angle

SLOs should drive dependency choices, timeout budgets, fallback plans, and alert priorities.

#### Traps / caveats

- Do not promise 99.99 percent availability if a required provider offers much less and no fallback exists.
- Do not count optional degraded features as total outage unless the SLO defines it that way.

#### Optional Anki

Q: Why map critical dependencies?
A: They determine achievable availability, latency, and failure behavior.

</details>

<a id="sd-res-011"></a>

<details>
<summary><strong>SD-RES-011. How do health checks, readiness and liveness affect availability?</strong></summary>

#### Short answer

They control whether traffic is routed to an instance and whether the platform should restart it.

#### Interview answer

Readiness means the instance is ready to serve traffic. Liveness means the process is healthy enough to keep running. Startup checks can prevent slow-starting apps from being killed too early. Good checks prevent routing traffic to unready instances and help recover stuck ones.

#### Deep dive

Health checks should reflect the instance's ability to serve. A liveness check should not fail just because an external dependency is briefly down, or the platform may restart every instance during a dependency outage.

#### Production angle

Bad health checks cause deployment failures, restart loops, and traffic to broken instances.

#### Traps / caveats

- Do not make liveness depend on every downstream service.
- Do not mark readiness true before migrations, warmup, or required connections are ready.

#### Optional Anki

Q: What is readiness?
A: A signal that an instance is ready to receive traffic.

</details>

<a id="sd-res-012"></a>

<details>
<summary><strong>SD-RES-012. How do rolling, blue-green and canary deployments reduce release risk?</strong></summary>

#### Short answer

They limit blast radius by gradually or safely shifting traffic to a new version.

#### Interview answer

Rolling deployment replaces instances incrementally. Blue-green runs old and new environments side by side and switches traffic. Canary sends a small percentage of traffic to the new version first. All three reduce risk compared with replacing everything at once, especially when combined with metrics and rollback.

#### Deep dive

Deployment strategy must account for database compatibility, message schema compatibility, cache changes, and long-running jobs. Rollback is only safe if the old version can still run with the current data and schema.

#### Production angle

Canary metrics should include errors, latency, saturation, business metrics, and logs for the new version.

#### Traps / caveats

- Do not deploy code that requires a destructive schema change before old instances are gone.
- Do not call a canary safe if there is no automated or human monitoring.

#### Optional Anki

Q: What is a canary deployment?
A: Sending a small portion of traffic to a new version before full rollout.

</details>

<a id="sd-res-013"></a>

<details>
<summary><strong>SD-RES-013. How do you design for regional failure without overengineering?</strong></summary>

#### Short answer

Start from business RPO/RTO and decide whether multi-AZ, warm standby, active-passive, or active-active is justified.

#### Interview answer

Not every system needs active-active multi-region. I would first ask what outage duration and data loss are acceptable. Multi-AZ inside one region may be enough for many systems. If regional failure must be handled, options include backups, warm standby, active-passive failover, or active-active with careful data consistency design.

#### Deep dive

Multi-region design introduces data replication, latency, failover, DNS, conflict handling, secrets, observability, and operational testing. Active-active is powerful but complex.

#### Production angle

Disaster recovery plans must be tested, because untested failover is usually a theory.

#### Traps / caveats

- Do not add active-active multi-region without clear business need.
- Do not ignore data consistency and failback after a regional event.

#### Optional Anki

Q: What should drive regional failure design?
A: Business RPO, RTO, cost tolerance, and operational maturity.

</details>

<a id="sd-res-014"></a>

<details>
<summary><strong>SD-RES-014. How do container or Kubernetes resource limits affect system reliability?</strong></summary>

#### Short answer

Resource requests and limits affect scheduling, throttling, memory kills, autoscaling, and noisy-neighbor isolation.

#### Interview answer

CPU requests influence scheduling and autoscaling signals. CPU limits can cause throttling. Memory limits can cause OOM kills if the JVM, native memory, or buffers exceed the container limit. Correct sizing matters for Java services because heap, metaspace, thread stacks, direct buffers, and native memory all consume memory.

#### Deep dive

Reliability requires matching JVM options, container limits, connection pools, thread pools, and workload behavior. Too-low limits cause instability; too-high requests waste capacity and reduce bin packing.

#### Production angle

Monitor restarts, OOM kills, CPU throttling, memory usage, GC behavior, and latency during load.

#### Traps / caveats

- Do not set heap equal to the whole container memory limit.
- Do not ignore CPU throttling when investigating latency spikes.

#### Optional Anki

Q: Why can Kubernetes memory limits kill a Java service?
A: Container memory includes heap and non-heap memory such as metaspace, thread stacks, direct buffers, and native allocations.

</details>
