# Cache failure modes and correctness traps

---

<a id="cache-fail-001"></a>

<details>
<summary><strong>CACHE-FAIL-001. What is cache stampede, and how can it be mitigated?</strong></summary>

#### Short answer

A cache stampede happens when many requests miss the same key at once and all rebuild it from the source of truth.

#### Interview answer

For example, a hot product key expires and thousands of requests immediately query the database to rebuild it. The cache was meant to reduce load, but the synchronized miss can overload the database or downstream service.

#### Deep dive

Mitigations include TTL jitter, single-flight loading, distributed locks with short expiration, request coalescing, stale-while-revalidate, background refresh and cache warming. The right choice depends on whether stale data is acceptable and how expensive rebuilds are.

#### Production angle

Load-test the miss path, not only the hit path. A cache stampede often appears after deployments, Redis restart, bulk invalidation or synchronized TTL expiration.

#### Traps / caveats

- A distributed lock can become a bottleneck if held too long.
- If lock acquisition fails, decide whether to serve stale data, wait briefly or fail.
- Rebuilding many different keys at once can still overload the database.

#### Optional Anki

Q: What is cache stampede?
A: Many concurrent misses rebuild the same cached value from the source of truth.

</details>

<a id="cache-fail-002"></a>

<details>
<summary><strong>CACHE-FAIL-002. What is cache penetration?</strong></summary>

#### Short answer

Cache penetration happens when requests repeatedly ask for data that does not exist, so every request misses cache and hits the source.

#### Interview answer

If clients repeatedly request nonexistent product IDs, those IDs may never be cached because the database returns "not found". The result is a stream of cache misses that bypasses the cache and loads the database.

#### Deep dive

Mitigations include negative caching, input validation, rate limiting, Bloom filters for known existing IDs, and abuse detection. Negative cache entries should have short TTLs so newly created data is not hidden for too long.

#### Production angle

Cache penetration can be accidental, from bad clients, or hostile, from scanning and abuse. Watch miss rate by endpoint and by reason.

#### Traps / caveats

- Do not cache "not found" forever.
- A Bloom filter can have false positives, so it reduces source hits but does not prove existence.
- Cache penetration can look like normal low hit rate unless measured by key pattern.

#### Optional Anki

Q: What is a common mitigation for cache penetration?
A: Short-lived negative caching.

</details>

<a id="cache-fail-003"></a>

<details>
<summary><strong>CACHE-FAIL-003. What is cache avalanche?</strong></summary>

#### Short answer

Cache avalanche is a large wave of cache misses caused by many keys expiring or becoming unavailable at the same time.

#### Interview answer

If many hot keys share the same TTL, they can expire together and push a sudden load spike to the database. A similar avalanche can happen after Redis restart, region invalidation or cache flush.

#### Deep dive

Mitigations include TTL jitter, staggered warmup, avoiding bulk invalidation during peak traffic, preloading critical keys, rate limiting cache rebuilds and protecting the database with backpressure.

#### Production angle

Avalanches are common after cache maintenance or deployment events. Dashboards should show miss rate, database QPS and Redis restarts together.

#### Traps / caveats

- A high average hit rate before the event does not protect the database during avalanche.
- Blindly warming all keys can create another load spike.
- Large region invalidation should be treated as an operational event.

#### Optional Anki

Q: What is cache avalanche?
A: Many keys miss together and overload the source of truth.

</details>

<a id="cache-fail-004"></a>

<details>
<summary><strong>CACHE-FAIL-004. What is a hot key, and why is it dangerous?</strong></summary>

#### Short answer

A hot key is a cache key receiving disproportionately high traffic, which can overload one Redis node or one application path.

#### Interview answer

Even if total Redis traffic looks acceptable, one key can dominate requests. In Redis Cluster, that key lives on one hash slot and one primary node, so traffic cannot be spread naturally across all nodes.

#### Deep dive

Hot keys are common for global configuration, popular products, celebrity profiles, feature flags and shared counters. Mitigations include local L1 caching, key sharding for read-only values, request coalescing, replicas for reads when acceptable, and redesigning the access pattern.

#### Production angle

Look for uneven command distribution, high CPU on one Redis node, high latency for one endpoint and client-side metrics by cache name or key pattern.

#### Traps / caveats

- Adding more Redis Cluster nodes does not automatically split one hot key.
- Sharding a mutable counter requires merge logic.
- Replicas can serve stale data depending on the setup.

#### Optional Anki

Q: Why does a hot key matter in Redis Cluster?
A: One key maps to one hash slot and one primary node.

</details>

<a id="cache-fail-005"></a>

<details>
<summary><strong>CACHE-FAIL-005. How can TTL jitter reduce synchronized cache expiration?</strong></summary>

#### Short answer

TTL jitter adds random variation to expiration times so many keys do not expire at the exact same moment.

#### Interview answer

Instead of setting every entry to expire after exactly 10 minutes, the service might use 9 to 11 minutes. That spreads cache misses over time and reduces the chance of a sudden database spike.

#### Deep dive

Jitter is especially useful for caches populated in batches, deployment warmups, and keys created by the same scheduled job. It does not solve all miss storms, but it reduces synchronization.

#### Production angle

Use jitter for high-volume caches where a large number of entries are created or refreshed together. Keep the jitter range small enough that business staleness requirements are still respected.

#### Traps / caveats

- Jitter should not extend TTL beyond an unacceptable freshness window.
- It does not prevent stampede on one extremely hot key.
- Jitter should be applied consistently in shared cache utilities.

#### Optional Anki

Q: What problem does TTL jitter reduce?
A: Synchronized expiration and cache avalanche.

</details>

<a id="cache-fail-006"></a>

<details>
<summary><strong>CACHE-FAIL-006. How do locks or single-flight techniques reduce duplicate cache rebuilds?</strong></summary>

#### Short answer

They ensure only one request rebuilds a missing value while other requests wait, reuse stale data or skip rebuilding.

#### Interview answer

Single-flight means concurrent requests for the same key share one in-progress load. In one JVM, this can be done with a local future or cache loader. Across instances, a short-lived Redis lock can allow one instance to rebuild while others avoid hitting the database.

#### Deep dive

This is useful for expensive rebuilds and hot keys. The lock must have a short expiration, a unique owner value and safe release logic. Waiting clients need a timeout so they do not block indefinitely.

#### Production angle

Use this when miss amplification is a known risk. Measure lock wait time, rebuild time and fallback behavior.

#### Traps / caveats

- A lock without expiration can deadlock rebuilds.
- A lock with too short a TTL can allow duplicate rebuilds.
- Locking every key can add overhead and reduce throughput.

#### Optional Anki

Q: What does single-flight prevent?
A: Duplicate concurrent rebuilds for the same missing cache key.

</details>

<a id="cache-fail-007"></a>

<details>
<summary><strong>CACHE-FAIL-007. How should a service behave when cached data is stale but the database is slow?</strong></summary>

#### Short answer

It depends on the data: serve stale data only when business rules allow it, otherwise fail safely or degrade.

#### Interview answer

For non-critical data, serving a stale value may be better than timing out the user. For critical data like permissions, balances or checkout decisions, stale data may be unsafe and the service should fall back to the source of truth or fail closed.

#### Deep dive

Patterns include stale-while-revalidate, stale-if-error, background refresh, bounded waits, circuit breakers and explicit degraded responses. The key is to define the stale-data contract per cache, not globally.

#### Production angle

During incidents, stale reads can preserve availability, but they must be visible in metrics and logs. Product owners should understand where stale behavior is allowed.

#### Traps / caveats

- "Better stale than down" is not true for all data.
- Stale data can violate security and compliance.
- Silent stale fallback can hide a database outage.

#### Optional Anki

Q: When is serving stale data acceptable?
A: When the business can tolerate the stale value and the response is safer than failing.

</details>

<a id="cache-fail-008"></a>

<details>
<summary><strong>CACHE-FAIL-008. What can go wrong if user-specific data is cached under a shared key?</strong></summary>

#### Short answer

One user can receive another user's cached data, creating a correctness and security incident.

#### Interview answer

If an endpoint caches `profile:current` instead of including user ID, tenant ID or permission context, the first user's response may be served to later users. This can expose personal data or perform actions based on another user's state.

#### Deep dive

The same issue happens with role-dependent fields, feature flags, locale, currency and tenant-specific data. The cache key must include every input that can change the result, or the endpoint should not be cached at that level.

#### Production angle

Review cache keys for user-facing and multi-tenant APIs. Add tests with multiple users, tenants and roles, not only one happy-path user.

#### Traps / caveats

- Authentication token is usually not a good raw key component because it creates high cardinality and may be sensitive.
- Shared DTO caches can leak hidden fields.
- CDN, HTTP cache and application cache can all make this mistake.

#### Optional Anki

Q: What key context is usually required for user-specific cache?
A: User, tenant and permission-related context when they affect the result.

</details>

<a id="cache-fail-009"></a>

<details>
<summary><strong>CACHE-FAIL-009. What can go wrong if authorization-sensitive data is cached incorrectly?</strong></summary>

#### Short answer

Users may keep access after permissions are revoked or receive data they are not allowed to see.

#### Interview answer

Authorization-sensitive caching is risky because permissions can change independently of the cached resource. If the cache key ignores role, scope, organization, row-level access or permission version, the service may return data based on an old authorization decision.

#### Deep dive

Permission checks are often safer when performed at request time, while the underlying non-sensitive resource can be cached separately. If authorization results are cached, use short TTLs, explicit invalidation and careful scoping.

#### Production angle

Fail closed for security-sensitive data. Audit cache decisions that affect access control and include permission changes in invalidation testing.

#### Traps / caveats

- Caching "allowed" decisions is more dangerous than caching public data.
- Role changes and group membership changes must be considered.
- A cached DTO may contain fields hidden for some users.

#### Optional Anki

Q: Why is caching authorization decisions risky?
A: Permission changes can make cached decisions stale and unsafe.

</details>

<a id="cache-fail-010"></a>

<details>
<summary><strong>CACHE-FAIL-010. What is stale-while-revalidate, and when can it be acceptable?</strong></summary>

#### Short answer

Stale-while-revalidate serves an expired value immediately while refreshing it asynchronously in the background.

#### Interview answer

The user gets a fast response from a stale cache entry, and one background process refreshes the value for future requests. This is acceptable when slightly stale data is better than high latency or failure, such as product descriptions, public metadata or non-critical recommendation data.

#### Deep dive

The pattern needs two time windows: a normal freshness TTL and a maximum stale window. After the maximum stale window, the value should no longer be served. Refreshes should be coalesced to avoid background stampedes.

#### Production angle

Stale-while-revalidate is useful during database slowness, but services should expose metrics for stale responses and refresh failures.

#### Traps / caveats

- Do not use it for security decisions or financial correctness.
- Background refresh failures can keep data stale longer than expected.
- Without a maximum stale limit, stale data can live indefinitely.

#### Optional Anki

Q: What does stale-while-revalidate optimize for?
A: Low latency and availability when bounded staleness is acceptable.

</details>

<a id="cache-fail-011"></a>

<details>
<summary><strong>CACHE-FAIL-011. How can cache recovery after an outage overload the database?</strong></summary>

#### Short answer

After Redis is empty or unavailable, many requests miss at once and shift load to the database.

#### Interview answer

If Redis restarts, loses memory or is bypassed during an outage, the application may suddenly execute all previously cached reads against the database. This cold-cache traffic can exceed database capacity and turn a cache outage into a broader system outage.

#### Deep dive

Recovery risks include cold caches, synchronized warmup, retry storms, connection pool exhaustion and expensive recomputation. The service should limit cache rebuild concurrency and protect the source of truth.

#### Production angle

Use controlled warmup, rate limiting, backpressure, stale values where safe, TTL jitter, circuit breakers and database protection. Practice Redis restart behavior in staging with realistic traffic.

#### Traps / caveats

- Restarting Redis can be safe technically but still unsafe operationally.
- Cache warmup must be throttled.
- Autoscaling many app instances can amplify cold-cache misses.

#### Optional Anki

Q: What is cold-cache risk?
A: Many cache misses suddenly hit the source of truth after cache loss or restart.

</details>
