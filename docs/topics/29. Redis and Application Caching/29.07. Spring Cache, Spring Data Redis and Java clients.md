# Spring Cache, Spring Data Redis and Java clients

---

<a id="redis-spring-001"></a>

<details>
<summary><strong>REDIS-SPRING-001. How does Spring Cache use Redis?</strong></summary>

#### Short answer

Spring Cache can use Redis as the backing store through a `CacheManager`, usually `RedisCacheManager`.

#### Interview answer

Spring Cache is an abstraction. The application uses annotations such as `@Cacheable`, and the configured `CacheManager` decides where entries are stored. With Redis, Spring serializes keys and values and stores them in Redis with configured cache names and TTLs.

#### Deep dive

Spring Cache does not make Redis magic. Key generation, serialization, TTLs, transaction interaction, self-invocation and cache error handling still matter. Redis is just one provider behind the abstraction.

#### Production angle

Configure cache names, TTLs, serializers and metrics explicitly. Avoid one global Redis cache configuration for every use case unless the data has the same freshness and risk profile.

#### Traps / caveats

- Spring Cache is method-level caching, not HTTP caching.
- It caches based on method arguments by default.
- The abstraction can hide Redis-specific operational costs.

#### Optional Anki

Q: Which Spring component connects cache annotations to Redis?
A: A Redis-backed `CacheManager`, commonly `RedisCacheManager`.

</details>

<details>
<summary><strong>REDIS-SPRING-002. What do `@Cacheable`, `@CachePut` and `@CacheEvict` do?</strong></summary>

#### Short answer

`@Cacheable` reads through cache, `@CachePut` updates cache with the method result, and `@CacheEvict` removes entries.

#### Interview answer

`@Cacheable` checks the cache before invoking the method. On a miss, it runs the method and stores the result. `@CachePut` always runs the method and puts the result in cache. `@CacheEvict` removes one or more cache entries, often after a write operation.

#### Deep dive

These annotations are usually implemented through Spring AOP proxies. Conditions, `unless`, custom keys and cache names control behavior. The method result and arguments should be stable and safe to cache.

#### Production angle

Use `@Cacheable` mostly for read methods and `@CacheEvict` around writes. Be explicit about keys so reads and evictions target the same entries.

#### Traps / caveats

- `@CachePut` and `@Cacheable` on the same method are often confusing.
- `@CacheEvict(allEntries = true)` can create a load spike.
- Exceptions normally prevent caching unless configured otherwise.

#### Optional Anki

Q: What does `@Cacheable` do on a cache hit?
A: Returns the cached value without invoking the method.

</details>

<details>
<summary><strong>REDIS-SPRING-003. How does Spring generate default cache keys?</strong></summary>

#### Short answer

Spring's default key generator uses method parameters: no argument, one argument, or a composite key for multiple arguments.

#### Interview answer

By default, Spring generates a key from the method arguments. If there is one argument, that argument is often the key. If there are multiple arguments, Spring uses a composite `SimpleKey`. This is convenient but not always safe for public APIs or multi-tenant data.

#### Deep dive

Default keys do not automatically include tenant, locale, user permissions or application version unless they are method arguments. They also depend on stable `equals()` and `hashCode()` for complex argument objects.

#### Production angle

For important caches, use explicit SpEL keys or a custom `KeyGenerator`. Make the key format reviewable and consistent with invalidation code.

#### Traps / caveats

- Missing context in method arguments means missing context in the cache key.
- Mutable arguments can produce unstable keys.
- Different methods using the same cache and key can collide if not namespaced.

#### Optional Anki

Q: Why can Spring default cache keys be risky?
A: They may omit tenant, permission, locale or version context.

</details>

<a id="redis-spring-004"></a>

<details>
<summary><strong>REDIS-SPRING-004. When should you provide a custom cache key?</strong></summary>

#### Short answer

Use a custom key when default argument-based keys do not fully or clearly identify the cached result.

#### Interview answer

A custom key is needed when tenant, locale, currency, permission context, API version or selected fields affect the result. It is also useful when method arguments are complex objects and only some stable fields should be part of the key.

#### Deep dive

Good custom keys prevent collisions and make invalidation possible. They should avoid sensitive raw data and unbounded input. Prefer explicit domain-oriented key names over accidental object string representations.

#### Production angle

Keep key generation consistent between `@Cacheable` and `@CacheEvict`. If invalidation code cannot reproduce the key, stale entries will remain.

#### Traps / caveats

- Including too much context can kill hit rate.
- Including too little context can leak data.
- `toString()` on DTOs is rarely a stable cache key contract.

#### Optional Anki

Q: What is a common reason to use a custom Spring cache key?
A: Tenant or permission context affects the result.

</details>

<details>
<summary><strong>REDIS-SPRING-005. What are common mistakes with `@Cacheable` on methods inside the same class?</strong></summary>

#### Short answer

Self-invocation bypasses the Spring proxy, so the cache annotation may not run.

#### Interview answer

Spring caching is usually applied by AOP proxy. If one method in a bean calls another `@Cacheable` method on `this`, the call does not go through the proxy. As a result, the method executes normally and cache behavior is skipped.

#### Deep dive

This is the same class of issue as Spring `@Transactional` self-invocation. Solutions include moving the cached method to another bean, calling through the proxy carefully, or designing caching outside the internal method call.

#### Production angle

Self-invocation bugs can make cache metrics show unexpectedly low hit rate or no Redis calls. Tests should verify behavior at the Spring bean boundary.

#### Traps / caveats

- Private methods are not good targets for proxy-based caching.
- Unit tests without Spring proxies may not show real caching behavior.
- Calling the method from the same class can bypass both caching and transaction advice.

#### Optional Anki

Q: Why can Spring `@Cacheable` fail on self-invocation?
A: The call bypasses the AOP proxy.

</details>

<details>
<summary><strong>REDIS-SPRING-006. How do you configure per-cache TTLs with Redis Cache Manager?</strong></summary>

#### Short answer

Configure `RedisCacheManager` with cache-specific `RedisCacheConfiguration` entries, each with its own TTL and serialization settings.

#### Interview answer

In Spring Boot, you can define a `RedisCacheManager` bean and provide default cache configuration plus per-cache overrides. Each cache name can have a different TTL based on freshness requirements, such as short TTL for user permissions and longer TTL for product metadata.

#### Deep dive

Per-cache TTLs are important because different data has different stale-read tolerance. A single global TTL usually becomes too short for stable data and too long for volatile data.

#### Production angle

Name caches explicitly and document their TTL rationale. Validate TTLs with hit rate, stale-data incidents and database load.

#### Traps / caveats

- Cache name mismatch can silently use default TTL.
- TTL changes can cause sudden hit-rate changes.
- Some Redis cache configurations do not support per-entry dynamic TTL without customization.

#### Optional Anki

Q: Why use per-cache TTLs?
A: Different cached data has different freshness and risk requirements.

</details>

<a id="redis-spring-007"></a>

<details>
<summary><strong>REDIS-SPRING-007. How do you choose serializers for Redis values in a Spring Boot application?</strong></summary>

#### Short answer

Choose serializers based on compatibility, safety, size, speed and debuggability.

#### Interview answer

For keys, strings are usually best. For values, JSON is common because it is readable and language-neutral, but it must be configured carefully. Binary formats can reduce size and CPU but are harder to inspect. Avoid Java native serialization for most cache values.

#### Deep dive

Serializer choice affects rolling deployments. If old cached values cannot be read by new code, deployments may fail or produce cache errors. Polymorphic JSON with class metadata can also introduce security and coupling concerns.

#### Production angle

Use stable DTOs, explicit type mappings and versioned keys for incompatible changes. Monitor serialization failures separately from Redis connectivity failures.

#### Traps / caveats

- Changing class names can break cached values.
- Default serializers may not match your API compatibility needs.
- Never deserialize untrusted data with unsafe polymorphic configuration.

#### Optional Anki

Q: What serializer is usually safest for Redis keys?
A: A string serializer.

</details>

<a id="redis-spring-008"></a>

<details>
<summary><strong>REDIS-SPRING-008. How does transaction-aware cache behavior affect consistency?</strong></summary>

#### Short answer

Transaction-aware caching delays cache changes until the surrounding transaction commits, reducing rollback-related inconsistency.

#### Interview answer

If a method updates the database and evicts a cache entry inside a transaction, doing the eviction before commit can be wrong if the transaction rolls back. Transaction-aware cache behavior registers cache operations to run after commit, so the cache reflects committed data.

#### Deep dive

This helps with local database transaction boundaries, but it does not make Redis part of the database transaction. If the after-commit Redis operation fails, the database is still committed and the cache may be stale until TTL or retry.

#### Production angle

Use after-commit cache eviction for write paths. For cross-service invalidation, consider outbox events so the invalidation request is durable after commit.

#### Traps / caveats

- Transaction-aware caching does not create distributed transactions.
- Read-only cache population inside transactions can still see isolation effects.
- After-commit failure needs metrics, logs and fallback TTLs.

#### Optional Anki

Q: What does transaction-aware cache eviction prevent?
A: Evicting or updating cache for a database transaction that later rolls back.

</details>

<details>
<summary><strong>🧠 REDIS-SPRING-009. What are the trade-offs of lock-free versus locking Redis cache writers?</strong></summary>

#### Short answer

Lock-free writers are faster but can allow duplicate cache loads; locking writers reduce duplication but add latency and contention.

#### Interview answer

Spring Data Redis cache writers can be configured in ways that avoid cache-level locks or use locking for certain operations. Lock-free behavior has better throughput but can allow multiple clients to compute the same missing value. Locking can protect expensive operations but adds extra Redis commands and can slow hot caches.

#### Deep dive

This trade-off matters for `putIfAbsent`, clearing caches and high-contention keys. Locking at cache level is often too broad for busy systems; single-flight per key may be a better design for expensive loads.

#### Production angle

Choose based on contention and rebuild cost. Monitor duplicate loads, Redis command count, lock wait time and latency.

#### Traps / caveats

- Locking can reduce throughput for the whole cache region.
- Lock-free does not mean incorrect for all use cases.
- Expensive loaders need protection somewhere, even if not in the cache writer.

#### Optional Anki

Q: Main trade-off of locking Redis cache writers?
A: Less duplicate work, but more latency and contention.

</details>

<details>
<summary><strong>REDIS-SPRING-010. What are the practical differences between Lettuce and Jedis for Java services?</strong></summary>

#### Short answer

Lettuce is Netty-based and supports asynchronous/reactive usage; Jedis is traditionally simpler and synchronous, often used with pooling.

#### Interview answer

Both are common Redis Java clients. Lettuce is thread-safe for many connection use cases and integrates well with Spring Data Redis, including async and reactive APIs. Jedis is straightforward for synchronous code and commonly uses connection pools. The choice depends on the application model and Spring support.

#### Deep dive

The important interview point is not "one is always better", but understanding threading and connection behavior. A reactive service should avoid blocking Redis calls, while a servlet-based service may be fine with bounded synchronous access.

#### Production angle

Whichever client is used, configure timeouts, pooling or connection sharing, reconnect behavior, TLS, authentication and metrics.

#### Traps / caveats

- Do not assume a client is safe to share without checking its connection model.
- Reactive API does not help if the code blocks later.
- Client defaults may not match production latency budgets.

#### Optional Anki

Q: Which Java Redis client is commonly associated with Netty and reactive support?
A: Lettuce.

</details>

<a id="redis-spring-011"></a>

<details>
<summary><strong>REDIS-SPRING-011. How should Redis connections, pools and thread usage be configured in Java clients?</strong></summary>

#### Short answer

Use bounded resources, explicit timeouts, metrics and a connection model appropriate for blocking or non-blocking code.

#### Interview answer

For synchronous code, connection pools should be sized according to concurrency and Redis latency, not guessed. For async clients, shared connections and event-loop threads must not be blocked. Commands should have connect, command and socket timeouts so threads do not wait forever.

#### Deep dive

Too small a pool causes pool wait time and timeouts. Too large a pool can overload Redis and increase context switching. In async clients, blocking callbacks or heavy deserialization on event-loop threads can harm all commands.

#### Production angle

Monitor pool active/idle/wait metrics, command latency, timeouts, reconnects and event-loop saturation where available.

#### Traps / caveats

- Increasing pool size can move the bottleneck to Redis.
- Missing command timeouts can exhaust servlet threads.
- Pool wait time may look like Redis latency unless measured separately.

#### Optional Anki

Q: Why not just increase the Redis connection pool size?
A: It can overload Redis and hide the real bottleneck.

</details>

<a id="redis-spring-012"></a>

<details>
<summary><strong>REDIS-SPRING-012. What are the risks of using blocking Redis calls in reactive or event-loop based code?</strong></summary>

#### Short answer

Blocking calls can stall event-loop threads and degrade many unrelated requests.

#### Interview answer

In reactive systems, a small number of event-loop threads handle many connections. If one thread blocks waiting for Redis, it cannot process other work. This can create high latency, timeouts and cascading backpressure.

#### Deep dive

The issue is not only Redis. Serialization, decompression, lock waits or `Future.get()` can also block. If blocking Redis access is unavoidable, isolate it on a bounded worker scheduler and understand the capacity trade-off.

#### Production angle

Use reactive Redis APIs in reactive request paths. Monitor event-loop blocking, scheduler queue size and Redis latency.

#### Traps / caveats

- Wrapping blocking code in `Mono` does not make it non-blocking.
- A fast Redis call can still occasionally block during network issues.
- Thread starvation may appear as random API latency.

#### Optional Anki

Q: Why are blocking Redis calls bad on an event loop?
A: They prevent the event-loop thread from processing other work.

</details>

<details>
<summary><strong>REDIS-SPRING-013. How should Java Redis clients handle retries, reconnects and topology refresh after failover?</strong></summary>

#### Short answer

They should use bounded retries, short timeouts, automatic reconnects and topology refresh configured for Sentinel or Cluster deployments.

#### Interview answer

During failover, the client may briefly see connection errors, moved slots, stale primary information or command timeouts. The client should reconnect and refresh topology, but application retries must be bounded and safe. For non-idempotent operations, retries can duplicate effects unless the operation is designed for idempotency.

#### Deep dive

Redis Cluster clients need to follow redirections and update slot mappings. Sentinel clients need to discover the new primary. The application should distinguish a cache read failure, which may be bypassed, from a lock or idempotency failure, which may require safer handling.

#### Production angle

Test Redis failover with the actual Java client configuration. Monitor reconnects, topology refreshes, command errors, timeouts and retry counts.

#### Traps / caveats

- Infinite retries can exhaust threads and extend incidents.
- Retrying writes blindly can duplicate side effects.
- A successful reconnect does not mean cached data is fresh.

#### Optional Anki

Q: Why are retries dangerous for Redis writes?
A: The first attempt may have succeeded even if the client saw a timeout.

</details>
