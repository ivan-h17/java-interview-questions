# Cache keys, TTLs and invalidation

---

<a id="cache-inv-001"></a>

<details>
<summary><strong>CACHE-INV-001. How do you design cache keys?</strong></summary>

#### Short answer

Cache keys should be deterministic, explicit, versioned when needed, scoped by context and stable across deployments.

#### Interview answer

A good key identifies exactly what the cached value represents. It usually includes domain, entity or operation name, ID, tenant and other parameters that affect the result. For example, `product:v2:tenant:42:id:100`. If the response shape changes, a version in the key can prevent old serialized values from breaking new code.

#### Deep dive

Keys should avoid ambiguity and accidental collisions. They should also avoid unbounded raw input, huge strings and sensitive values. For Redis Cluster, key design may also consider hash slots when multi-key operations are needed.

#### Production angle

Use naming conventions so keys can be inspected, monitored and selectively invalidated. Avoid relying on `KEYS` in production for cleanup.

#### Traps / caveats

- Missing tenant or permission context can leak data.
- Raw user input can create huge key cardinality.
- Changing key format without migration can create cold-cache spikes.

#### Optional Anki

Q: What should a cache key identify?
A: The exact data, parameters and context used to compute the cached value.

</details>

<a id="cache-inv-002"></a>

<details>
<summary><strong>CACHE-INV-002. Why should cache keys include tenant, locale, version or permission context when relevant?</strong></summary>

#### Short answer

Because these contexts can change the result. If they are missing from the key, different users may receive the wrong cached value.

#### Interview answer

If a product description differs by locale, the locale must be in the key. If data is tenant-specific, tenant ID must be in the key. If permissions affect visible fields or rows, user role or permission version may need to be included. Otherwise one cached result can be accidentally reused for a different context.

#### Deep dive

Context omission is one of the most serious caching bugs because tests often use one tenant or one user role. Version context is also important when serialized DTOs change or when business rules produce a different result after deployment.

#### Production angle

For user-facing APIs, review cache keys during security and API reviews. Treat key design as part of the data access contract.

#### Traps / caveats

- Adding too much context can destroy hit rate.
- Adding too little context can leak or corrupt data.
- Permission changes may need explicit invalidation even if permission context is keyed.

#### Optional Anki

Q: What happens if tenant ID is omitted from a tenant-specific cache key?
A: Data from one tenant may be served to another tenant.

</details>

<a id="cache-inv-003"></a>

<details>
<summary><strong>CACHE-INV-003. What is cache invalidation, and why is it hard?</strong></summary>

#### Short answer

Cache invalidation removes or updates cached data when it may no longer match the source of truth.

#### Interview answer

It is hard because cached values may depend on many pieces of data, live in many services, and be read concurrently while writes happen. The system must know which keys are affected by a change and when it is safe to remove or update them.

#### Deep dive

Invalidating a single entity cache is often simple. Invalidating aggregate views, search pages, permission-dependent responses or cross-service read models is harder because one database update may affect many cached keys.

#### Production angle

Prefer simple cache shapes when possible. Use TTL as a safety net, explicit invalidation for critical changes, versioned keys for schema changes, and monitoring for stale-data reports.

#### Traps / caveats

- Deleting too little causes stale reads.
- Deleting too much can overload the database.
- Invalidating before a transaction commits can expose inconsistent state.

#### Optional Anki

Q: What is cache invalidation?
A: Removing or refreshing cached data that may no longer be correct.

</details>

<a id="cache-inv-004"></a>

<details>
<summary><strong>CACHE-INV-004. What is the difference between eviction and invalidation?</strong></summary>

#### Short answer

Eviction is cache removal due to cache policy. Invalidation is removal because the data may be logically stale.

#### Interview answer

Eviction happens when the cache decides to remove entries because of TTL, memory limits, LRU/LFU policy or max size. Invalidation happens when the application knows that a value changed or may have changed and removes the affected entry intentionally.

#### Deep dive

Eviction is operational: the cache manages capacity. Invalidation is correctness-related: the application manages freshness. Both can remove the same key, but the reason and expected behavior are different.

#### Production angle

High eviction rate can indicate Redis memory pressure or bad TTL/key design. Missing invalidation can cause stale business behavior even if Redis is healthy.

#### Traps / caveats

- Eviction should not be relied on as the only correctness mechanism.
- Invalidation can create load spikes if it removes many hot keys.
- TTL expiration is automatic removal, not proof that data was correct until expiration.

#### Optional Anki

Q: Eviction vs invalidation?
A: Eviction is policy/capacity-driven; invalidation is correctness-driven.

</details>

<a id="cache-inv-005"></a>

<details>
<summary><strong>CACHE-INV-005. How can stale cache data break business correctness?</strong></summary>

#### Short answer

Stale data can make users see old state, make decisions on wrong facts, or bypass security and business rules.

#### Interview answer

Examples include showing an old account status, using an outdated price, allowing a user with revoked permissions to access data, or displaying inventory as available after it was sold. The cache is not just a performance detail when its value influences business decisions.

#### Deep dive

The impact depends on the domain. Stale product descriptions may be acceptable for minutes. Stale balance, risk status or authorization data may be unacceptable even for seconds. This is why acceptable staleness must be explicit.

#### Production angle

For correctness-sensitive data, use short TTLs, explicit invalidation, source-of-truth checks before committing, or avoid caching in the decision path.

#### Traps / caveats

- Stale reads can be intermittent and hard to reproduce.
- Cache bugs may appear only after permission or pricing changes.
- Stale data can be a security incident, not only a data-quality issue.

#### Optional Anki

Q: Give an example of stale cache causing correctness failure.
A: A revoked permission remains cached and still allows access.

</details>

<a id="cache-inv-006"></a>

<details>
<summary><strong>CACHE-INV-006. When should you invalidate a single key versus a whole cache region?</strong></summary>

#### Short answer

Invalidate a single key when the affected data is known. Invalidate a region when many dependent keys are unknown or no longer trustworthy.

#### Interview answer

Single-key invalidation is safer for load because it removes only the entry that changed. Region invalidation is useful after a schema change, major rule change, tenant-level update or when many aggregate keys may be affected and tracking them individually is too complex.

#### Deep dive

Whole-region invalidation can be implemented by deleting many keys, bumping a region version in key names, or changing a cache namespace. Version bumping avoids scanning Redis but leaves old keys until TTL or eviction.

#### Production angle

Use region invalidation carefully during peak traffic. Removing many hot entries at once can produce a database spike, so stagger invalidation or warm important keys when needed.

#### Traps / caveats

- Key scans can hurt Redis if done incorrectly.
- Region invalidation can create cache avalanche.
- Single-key invalidation is wrong if aggregate/list caches also depend on the changed data.

#### Optional Anki

Q: Why is single-key invalidation usually preferred?
A: It limits cache churn and source-of-truth load.

</details>

<a id="cache-inv-007"></a>

<details>
<summary><strong>CACHE-INV-007. How should cache invalidation interact with database transactions?</strong></summary>

#### Short answer

Invalidate or update cache only after the database transaction commits successfully.

#### Interview answer

The database is the source of truth, so cache changes should follow a successful commit. If a service evicts or updates the cache before commit and the transaction rolls back, readers may reload or see a value that was never committed.

#### Deep dive

The usual pattern is: update database in a transaction, then after commit evict affected cache keys. In Spring, transaction-aware cache behavior or transaction synchronization can delay cache operations until commit. For cross-service invalidation, an outbox event can be published after commit.

#### Production angle

This matters when there are concurrent readers. Incorrect ordering can create short windows of stale or phantom data that are hard to diagnose.

#### Traps / caveats

- Updating cache inside a transaction does not make Redis part of the database transaction.
- Evicting before commit can cause dirty reloads.
- If after-commit invalidation fails, TTL should be a fallback, but not the only control for critical data.

#### Optional Anki

Q: When should cache eviction happen relative to DB commit?
A: After the database transaction commits.

</details>

<a id="cache-inv-008"></a>

<details>
<summary><strong>CACHE-INV-008. How do you handle cache invalidation across multiple services that read the same data?</strong></summary>

#### Short answer

Use clear data ownership, event-driven invalidation after commit, versioned keys, or short TTLs depending on required freshness.

#### Interview answer

The service that owns the data should publish a change event after the database commit. Other services can consume it and invalidate their own caches. If the data is shared through an API, consumers should avoid caching internal representations and should include versions or ETags when possible.

#### Deep dive

Cross-service invalidation is hard because consumers may have different key schemes and stale-tolerance requirements. Sometimes the better design is to avoid distributed cached copies and call the owning service, or to build a proper read model with event replay and observability.

#### Production angle

Use durable events, idempotent consumers, retries, dead-letter handling, lag monitoring and TTL as a safety net. Make stale behavior visible in product requirements.

#### Traps / caveats

- Pub/sub invalidation without durability can miss messages.
- Consumers may deploy independently and change key formats.
- Shared database reads across services make ownership and invalidation unclear.

#### Optional Anki

Q: Who should publish invalidation events?
A: The service that owns and commits the source-of-truth change.

</details>

<a id="cache-inv-009"></a>

<details>
<summary><strong>🧠 CACHE-INV-009. How can event-driven invalidation fail in production?</strong></summary>

#### Short answer

It can fail through lost events, lag, duplicates, out-of-order processing, consumer bugs or invalidation after the wrong transaction boundary.

#### Interview answer

If invalidation events are not durable, a service can miss them during restart. If consumers lag, stale data remains longer than expected. If events are duplicated, invalidation should still be safe. If events are processed out of order, an old event can remove or refresh the wrong version.

#### Deep dive

Invalidation events should usually contain enough identity and version information to make handling idempotent. For critical changes, use outbox after database commit rather than publishing inside a transaction before commit is guaranteed.

#### Production angle

Monitor consumer lag, dead letters, invalidation error rate and stale-data incidents. Keep TTLs as a backstop so one missed invalidation does not keep data wrong forever.

#### Traps / caveats

- Redis pub/sub is not a durable event log.
- Retrying invalidation may be safe, but retrying refresh can reintroduce old data if versions are ignored.
- Event delivery does not prove the cache key actually existed or was removed.

#### Optional Anki

Q: Why should invalidation handlers be idempotent?
A: Events may be duplicated or retried.

</details>
