# Redis commands, performance and memory behavior

---

<a id="redis-perf-001"></a>

<details>
<summary><strong>REDIS-PERF-001. Why should Redis commands be chosen with time complexity in mind?</strong></summary>

#### Short answer

Because Redis is fast only when commands and data sizes stay bounded; expensive commands can block other work and increase latency.

#### Interview answer

Many Redis commands are cheap, but not all. A command that scans a large collection, returns thousands of values or deletes a huge key can create latency spikes. Since Redis command execution is highly shared, one expensive operation can affect unrelated requests.

#### Deep dive

Always check command complexity and expected cardinality. `GET` is simple, `ZRANGE` with a huge range is not, and `KEYS` can scan the entire keyspace. Network response size also matters: returning a million elements is expensive even if the lookup starts quickly.

#### Production angle

Use bounded ranges, cursor-based scans, background cleanup, smaller keys and metrics for slow commands. Review Redis commands during code review just like SQL queries.

#### Traps / caveats

- Big-O depends on collection size and returned element count.
- A command can be cheap in staging and expensive in production data.
- Large responses can hurt clients and network, not only Redis.

#### Optional Anki

Q: Why check Redis command complexity?
A: Expensive commands can create latency spikes and affect other clients.

</details>

<a id="redis-perf-002"></a>

<details>
<summary><strong>REDIS-PERF-002. Why can large keys or large values hurt Redis performance?</strong></summary>

#### Short answer

Large keys and values increase memory use, network transfer, serialization cost and command latency.

#### Interview answer

A "big key" can be a huge string, hash, set or sorted set. Reading, writing, deleting or replicating it can block Redis or create client-side latency. Large serialized DTOs also increase Java allocation and GC pressure.

#### Deep dive

Large values hurt the whole path: Redis memory, network bandwidth, client buffers, deserialization and application heap. Large collections can also make operations like deletion, range reads or migration expensive.

#### Production angle

Track key sizes, value sizes and payload latency. Prefer bounded entries, pagination, chunking or different data modeling when values grow.

#### Traps / caveats

- One big key can be worse than many moderate keys.
- Deleting a huge key can cause latency; asynchronous unlinking may be safer.
- Compression can save memory but add CPU and compatibility complexity.

#### Optional Anki

Q: What is a Redis big-key problem?
A: A key or value is so large that operations on it hurt latency or memory.

</details>

<a id="redis-perf-003"></a>

<details>
<summary><strong>REDIS-PERF-003. Why is `KEYS` dangerous in production, and when should `SCAN` be used?</strong></summary>

#### Short answer

`KEYS` scans the whole keyspace at once and can block Redis; `SCAN` iterates incrementally with a cursor.

#### Interview answer

`KEYS pattern` is convenient locally, but in production with many keys it can consume CPU and block other commands. `SCAN` spreads work over multiple calls, making it safer for diagnostics, cleanup jobs and migrations.

#### Deep dive

`SCAN` is not a perfect snapshot. It can return duplicates and may miss keys that change during iteration, so callers must handle that. It is still much safer than one large blocking keyspace scan.

#### Production angle

Avoid production features that require scanning Redis keys on the request path. Use key namespaces, indexes, versioned keys or known-key tracking instead.

#### Traps / caveats

- `SCAN` can still be expensive if run too aggressively.
- Do not assume `SCAN` returns each key exactly once.
- Pattern-based cleanup can delete unexpected keys if naming is sloppy.

#### Optional Anki

Q: Why avoid `KEYS` in production?
A: It can scan and block the entire keyspace.

</details>

<a id="redis-perf-004"></a>

<details>
<summary><strong>REDIS-PERF-004. What is pipelining, and when does it help?</strong></summary>

#### Short answer

Pipelining sends multiple Redis commands without waiting for each response, reducing network round trips.

#### Interview answer

If a service needs to execute many independent Redis commands, sending them one by one pays network latency for each command. Pipelining batches the writes to Redis and reads responses later, improving throughput when round-trip time dominates.

#### Deep dive

Pipelining is not a transaction. Commands are still individual commands, and errors are returned per command. It also increases client and server buffering, so pipeline size should be bounded.

#### Production angle

Pipelining helps bulk reads/writes, cache warmup and batch invalidation. It is less useful for one command or when each command depends on the previous response.

#### Traps / caveats

- A huge pipeline can increase memory and latency.
- Pipelining does not make commands atomic.
- In Redis Cluster, commands may target different nodes.

#### Optional Anki

Q: What does Redis pipelining reduce?
A: Network round trips.

</details>

<a id="redis-perf-005"></a>

<details>
<summary><strong>REDIS-PERF-005. What is an atomic Redis command, and why does it matter?</strong></summary>

#### Short answer

An atomic Redis command completes as one indivisible operation from the perspective of other clients.

#### Interview answer

Commands like `INCR`, `SET key value NX PX`, `HINCRBY` and `SADD` are atomic. This matters because multiple clients can safely update the same key with one command without losing updates between read and write steps.

#### Deep dive

Atomic single commands are often better than client-side read-modify-write. For multi-step logic, use a Lua script, transaction with `WATCH`, or redesign to avoid shared mutable state.

#### Production angle

Rate limiters, idempotency markers, locks and counters should use atomic commands. If the operation is split into multiple client calls, crashes and races become likely.

#### Traps / caveats

- Atomic command does not mean durable command.
- Atomicity is usually scoped to Redis, not your database and Redis together.
- Multi-key atomicity in Redis Cluster has hash-slot constraints.

#### Optional Anki

Q: Why prefer `INCR` over GET plus SET for a counter?
A: `INCR` is atomic and avoids lost updates.

</details>

<a id="redis-perf-006"></a>

<details>
<summary><strong>REDIS-PERF-006. How do Redis eviction policies affect application behavior?</strong></summary>

#### Short answer

Eviction policies decide what Redis removes under memory pressure, which can change correctness, hit rate and failure behavior.

#### Interview answer

If Redis reaches `maxmemory`, the configured policy controls whether it evicts keys or returns errors. Policies can evict all keys, only keys with TTLs, least recently used keys, least frequently used keys, random keys, or keys near expiration depending on configuration.

#### Deep dive

For pure caches, eviction is expected but should be measured. For idempotency keys, locks or rate limiters, eviction can break correctness. `noeviction` may be safer for non-cache use, but then writes can fail under pressure.

#### Production angle

Set `maxmemory` and policy intentionally. Monitor used memory, evicted keys and write errors. Do not mix critical non-evictable state with best-effort cache entries without understanding policy impact.

#### Traps / caveats

- Eviction can remove keys before TTL.
- Evicted idempotency keys can allow duplicate processing.
- A cache with no eviction limit can cause broader memory incidents.

#### Optional Anki

Q: Why does Redis eviction policy matter?
A: It controls whether and which keys disappear under memory pressure.

</details>

<a id="redis-perf-007"></a>

<details>
<summary><strong>REDIS-PERF-007. How do serialization choices affect latency, memory and compatibility?</strong></summary>

#### Short answer

Serialization controls payload size, CPU cost, readability and whether old cached values remain compatible after code changes.

#### Interview answer

JSON is readable and easy to debug but can be larger. Binary formats can be smaller and faster but harder to inspect and evolve. Java native serialization is usually avoided for cache values because it is brittle, verbose and risky across class changes.

#### Deep dive

Serialization affects both Redis and the JVM. Large payloads increase Redis memory and network time, while deserialization creates allocations and can affect GC. Including Java class metadata in JSON can create security and compatibility concerns.

#### Production angle

Use stable DTOs and explicit serializers. Version keys or payloads when changing structure. Test rolling deployments where old and new code may read each other's cached values.

#### Traps / caveats

- Cached values can outlive the deployment that wrote them.
- Changing package/class names can break deserialization.
- Do not deserialize untrusted polymorphic payloads.

#### Optional Anki

Q: Why version cache keys during DTO changes?
A: To avoid new code reading incompatible old serialized values.

</details>

<a id="redis-perf-008"></a>

<details>
<summary><strong>🧠 REDIS-PERF-008. How can slow commands or big-key problems be diagnosed?</strong></summary>

#### Short answer

Use Redis slow logs, latency tools, key-size inspection, command stats and application-side latency metrics.

#### Interview answer

I would check Redis `SLOWLOG`, latency diagnostics, command statistics, CPU, memory, network, and application metrics by cache operation. For big keys, tools such as key sampling, `MEMORY USAGE`, `--bigkeys` style scans and targeted inspection help identify large strings or collections.

#### Deep dive

Diagnosis should separate server latency from client-side latency. A command may be fast on Redis but slow in the Java service because of network, connection pool waits, serialization or GC.

#### Production angle

Run key scans carefully, off-peak or with low rate limits. Add dashboards for command latency, payload size and cache names so future issues do not require blind scanning.

#### Traps / caveats

- A slow log entry shows server execution time, not total client latency.
- Sampling may miss short-lived keys.
- Diagnostic scans can themselves add load.

#### Optional Anki

Q: What does Redis `SLOWLOG` miss?
A: Network time, client pool waits, serialization and Java-side latency.

</details>

<a id="redis-perf-009"></a>

<details>
<summary><strong>🧠 REDIS-PERF-009. What are hot-key mitigation strategies in Redis?</strong></summary>

#### Short answer

Use local caching, request coalescing, read replicas when acceptable, key sharding for suitable data, or redesign the access pattern.

#### Interview answer

For read-mostly hot data, an in-process Caffeine cache can absorb most traffic. For expensive rebuilds, single-flight avoids duplicate loads. For counters or mutable state, sharding the key can distribute writes, then aggregate later if exact immediate values are not required.

#### Deep dive

Not every hot key can be safely sharded. A lock key or unique idempotency key relies on a single atomic location. For Redis Cluster, adding nodes does not split one key because a key maps to one hash slot.

#### Production angle

Identify hot keys by command volume and latency. Apply mitigation only after understanding whether the key is read-only, mutable, approximate, or correctness-critical.

#### Traps / caveats

- Sharded counters may be eventually consistent.
- Read replicas can return stale data.
- Local caching adds another invalidation layer.

#### Optional Anki

Q: What is the simplest mitigation for a read-only hot key?
A: Add a bounded local cache.

</details>

<a id="redis-perf-010"></a>

<details>
<summary><strong>REDIS-PERF-010. What are Redis transactions with `MULTI` and `EXEC`, and what do they not guarantee?</strong></summary>

#### Short answer

`MULTI` and `EXEC` execute a queued set of commands sequentially as one Redis transaction, but they do not provide SQL-style rollback.

#### Interview answer

After `MULTI`, Redis queues commands. `EXEC` runs them together without interleaving commands from other clients. This gives atomic execution in Redis. However, if a command fails at execution time, Redis does not roll back earlier successful commands like a relational database transaction would.

#### Deep dive

Redis transactions are useful for grouping simple operations, often with `WATCH` for optimistic locking. They do not make Redis and a database transactionally consistent together.

#### Production angle

Use Redis transactions for small bounded operations. For complex conditional logic, Lua may be clearer because it can read, branch and write atomically.

#### Traps / caveats

- No automatic rollback of already executed commands.
- Commands are queued, so intermediate results are not available before `EXEC`.
- In Redis Cluster, multi-key transactions require keys in the same hash slot.

#### Optional Anki

Q: Does Redis `MULTI`/`EXEC` provide SQL-style rollback?
A: No.

</details>

<a id="redis-perf-011"></a>

<details>
<summary><strong>REDIS-PERF-011. When would you use `WATCH` for optimistic locking in Redis?</strong></summary>

#### Short answer

Use `WATCH` when a transaction should only commit if watched keys were not modified by another client.

#### Interview answer

`WATCH` supports compare-and-set style logic. A client watches a key, reads it, computes a new value, starts `MULTI`, queues writes and calls `EXEC`. If another client changed the watched key before `EXEC`, the transaction aborts and the client can retry.

#### Deep dive

This is useful for occasional conditional updates. For high-contention keys, retries can become expensive, and a Lua script or different data model may be better.

#### Production angle

Bound retries and add metrics for aborted transactions. Do not use optimistic locking on a hot key without understanding contention.

#### Traps / caveats

- `WATCH` is per connection, so connection handling matters.
- High contention can cause repeated aborts.
- It still does not coordinate with database transactions.

#### Optional Anki

Q: What causes a Redis `WATCH` transaction to abort?
A: A watched key is modified before `EXEC`.

</details>

<a id="redis-perf-012"></a>

<details>
<summary><strong>REDIS-PERF-012. When should Lua scripts be used in Redis?</strong></summary>

#### Short answer

Use Lua scripts when several Redis reads and writes must execute atomically with conditional logic.

#### Interview answer

Lua is useful for rate limiters, safe lock release, conditional updates and multi-step operations that must not be interrupted by other clients. The script runs atomically inside Redis, so no other command interleaves while it executes.

#### Deep dive

Scripts should be short, deterministic and bounded. A long-running Lua script blocks Redis command processing and can create latency incidents. In Redis Cluster, scripts that access multiple keys must respect hash-slot rules.

#### Production angle

Version and test scripts carefully. Monitor script latency and avoid scripts that scan large collections or perform unbounded loops.

#### Traps / caveats

- Lua atomicity is Redis-only, not database-wide.
- Long scripts block Redis.
- Passing keys incorrectly can break cluster compatibility.

#### Optional Anki

Q: Why use Lua for releasing a Redis lock?
A: To check the owner value and delete the key atomically.

</details>

<a id="redis-perf-013"></a>

<details>
<summary><strong>REDIS-PERF-013. Why can multi-step commands such as `INCR` plus `EXPIRE` create correctness bugs?</strong></summary>

#### Short answer

Because another client or crash can occur between the steps, leaving partial state.

#### Interview answer

For a rate limiter, a service might call `INCR` and then `EXPIRE`. If the process crashes after `INCR` but before `EXPIRE`, the counter may never expire. If many clients race, expiration may be set incorrectly unless the logic is atomic.

#### Deep dive

The fix is to use an atomic pattern: Lua script, `MULTI`/`EXEC` where appropriate, or commands that combine options in one operation. For counters, set expiration only when the counter is first created, but do that atomically.

#### Production angle

Multi-step Redis logic should be reviewed like concurrent code. Bugs often show up as permanent rate-limit blocks, leaked locks or idempotency keys that never expire.

#### Traps / caveats

- A pipeline is not atomic.
- Retrying one step can make state worse.
- TTL bugs may appear only after crashes or timeouts.

#### Optional Anki

Q: Why is `INCR` followed by `EXPIRE` risky?
A: A crash or race between commands can leave a counter without TTL.

</details>
