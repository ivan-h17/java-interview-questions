# Testing, observability and production scenarios

---

<a id="redis-prod-001"></a>

<details>
<summary><strong>REDIS-PROD-001. How would you test code that uses Spring Cache?</strong></summary>

#### Short answer

Test business behavior, cache hit/miss behavior at the Spring bean boundary, and invalidation after writes.

#### Interview answer

For unit tests, keep business logic independent of caching where possible. For Spring cache behavior, use a Spring test context so proxies and annotations actually run. Verify that repeated calls avoid duplicate repository calls, and that write operations evict or update the expected keys.

#### Deep dive

Self-invocation, custom keys and transaction-aware eviction are hard to test without Spring. Tests should include different tenants, users or parameters when key context matters.

#### Production angle

Caching tests should prevent regressions where an endpoint silently stops caching or starts returning stale data after writes.

#### Traps / caveats

- Plain unit tests may bypass Spring AOP proxies.
- Testing only cache hits misses invalidation bugs.
- Do not make tests depend on arbitrary key serialization unless that is the contract.

#### Optional Anki

Q: Why use a Spring context for testing cache annotations?
A: To exercise the proxy-based caching behavior.

</details>

<a id="redis-prod-002"></a>

<details>
<summary><strong>REDIS-PROD-002. When should Redis integration tests use Testcontainers?</strong></summary>

#### Short answer

Use Testcontainers when behavior depends on real Redis commands, TTLs, serialization, transactions, Lua or client configuration.

#### Interview answer

Mocks are fine for simple business logic, but they do not validate Redis TTL behavior, serialization compatibility, Lua scripts, transactions, pub/sub, connection failures or Spring Data Redis configuration. Testcontainers gives the test a real Redis instance close to production behavior.

#### Deep dive

Integration tests should cover risky behavior: distributed locks, rate limiters, idempotency keys, custom serializers and cache invalidation. They do not need to cover every simple `GET`/`SET`.

#### Production angle

Use real Redis tests for code paths where a mismatch between fake and real Redis could cause incidents.

#### Traps / caveats

- Testcontainers tests are slower, so keep them focused.
- A single Redis container may not test Cluster or Sentinel behavior.
- Time-based TTL tests need tolerances to avoid flakiness.

#### Optional Anki

Q: What Redis behavior is hard to mock accurately?
A: TTLs, Lua scripts, transactions, serialization and client behavior.

</details>

<a id="redis-prod-003"></a>

<details>
<summary><strong>REDIS-PROD-003. How would you verify that caching actually reduces database load?</strong></summary>

#### Short answer

Compare cache hit/miss metrics with database query rate, latency and connection pool usage before and after caching.

#### Interview answer

I would instrument cache hits, misses and load times per cache name and endpoint. Then I would check database QPS, slow queries, CPU, connection pool wait time and API latency. A successful cache should reduce expensive database calls without increasing stale-data errors.

#### Deep dive

The verification should happen under representative traffic. A cache can look good in tests but fail in production if keys are too unique, TTLs are too short or invalidation constantly removes entries.

#### Production angle

Use dashboards and deployment markers. Watch p95/p99 latency, not only averages, and compare miss spikes with database pressure.

#### Traps / caveats

- A high hit rate on cheap queries may not matter.
- Cache can reduce database QPS but increase API errors if stale data breaks logic.
- Measure by endpoint or cache name, not only globally.

#### Optional Anki

Q: What should improve if caching works?
A: Source load and/or request latency for the cached path.

</details>

<a id="redis-prod-004"></a>

<details>
<summary><strong>REDIS-PROD-004. What Redis server metrics should be monitored?</strong></summary>

#### Short answer

Monitor Redis latency, CPU, memory, evictions, connections, command stats, replication, persistence and errors.

#### Interview answer

Important Redis metrics include used memory, maxmemory, evicted keys, expired keys, connected clients, blocked clients, ops/sec, command latency, slow commands, network I/O, CPU, replication lag, role changes, persistence status and keyspace size.

#### Deep dive

For Redis Cluster, also watch node balance, slot distribution and per-node load. For Sentinel or replicated deployments, watch failover events and replica health.

#### Production angle

Alerts should focus on user-impacting symptoms: high latency, high error rate, memory near limit, eviction spikes, replication lag and failover instability.

#### Traps / caveats

- Server metrics do not show Java client pool waits.
- Evictions may be normal for some caches but critical for idempotency keys.
- Average Redis latency can hide p99 spikes.

#### Optional Anki

Q: Name three Redis server metrics to monitor.
A: Memory usage, command latency and evicted keys.

</details>

<a id="redis-prod-005"></a>

<details>
<summary><strong>REDIS-PROD-005. What application cache metrics should be monitored?</strong></summary>

#### Short answer

Monitor hits, misses, load time, load failures, evictions, stale responses, bypasses and fallback behavior per cache.

#### Interview answer

Application metrics should show whether the cache is helping the service. Track hit rate, miss rate, cache get/put/evict latency, loader latency, loader errors, stale-if-error usage, single-flight waits and database calls caused by cache misses.

#### Deep dive

Metrics should be tagged carefully by cache name and operation, not by raw key or user ID. High-cardinality metric labels can damage the observability system.

#### Production angle

Cache metrics should connect to service SLOs and database dashboards. During incidents, you need to know whether Redis, the Java client, or the miss path is causing user impact.

#### Traps / caveats

- Do not use raw cache keys as metric labels.
- Hit rate without miss cost is misleading.
- Cache bypass counts are important during Redis incidents.

#### Optional Anki

Q: Why tag cache metrics by cache name?
A: To identify which cache is helping or failing without high cardinality.

</details>

<a id="redis-prod-006"></a>

<details>
<summary><strong>REDIS-PROD-006. How would you debug a cache that returns stale data?</strong></summary>

#### Short answer

Trace the key, value version, TTL, write path, invalidation path and transaction timing.

#### Interview answer

I would identify the exact cache key used for the stale response, inspect its TTL and value, compare it with the database, and check whether the write operation evicted or updated the same key. Then I would verify transaction boundaries, event-driven invalidation, consumer lag and whether key context such as tenant or permissions is missing.

#### Deep dive

Stale data is often caused by key mismatch, invalidation before rollback/commit, missing aggregate invalidation, event delivery failure, long TTLs or deserialization of old value versions.

#### Production angle

Add structured logs around cache key generation and invalidation for critical caches, but avoid logging sensitive key parts or values.

#### Traps / caveats

- The read key and eviction key may not be identical.
- A stale value may come from local L1 cache, not Redis.
- A replica read can be stale even if primary has the update.

#### Optional Anki

Q: First thing to check for stale cache?
A: The exact cache key used for read and invalidation.

</details>

<a id="redis-prod-007"></a>

<details>
<summary><strong>REDIS-PROD-007. How would you debug Redis memory growth?</strong></summary>

#### Short answer

Check key count, memory by data type, TTL coverage, big keys, write rate, eviction policy and recent deployments.

#### Interview answer

I would look at Redis used memory, keyspace size, evictions, expired keys and key patterns. Then I would sample keys to find large values or collections, check whether expected TTLs are missing, and correlate growth with new features or traffic.

#### Deep dive

Memory growth can come from missing TTLs, high-cardinality keys, negative cache abuse, large serialized objects, unbounded sorted sets, leaked idempotency keys or persistence overhead.

#### Production angle

Use low-impact scans and memory tooling carefully. Add guardrails: max key sizes, TTL defaults, per-cache memory budgets and alerts before maxmemory is reached.

#### Traps / caveats

- Big-key scans can miss short-lived spikes.
- Eviction may hide growth until important keys disappear.
- Application metrics may show key patterns more safely than production scans.

#### Optional Anki

Q: What is a common cause of Redis memory leak-like growth?
A: Keys written without TTL or with unbounded cardinality.

</details>

<a id="redis-prod-008"></a>

<details>
<summary><strong>REDIS-PROD-008. How would you handle a Redis outage during peak traffic?</strong></summary>

#### Short answer

Protect the service and source of truth: use short timeouts, bypass safe caches, shed load if needed and avoid retry storms.

#### Interview answer

First, confirm whether Redis is down, slow, or unreachable from clients. Reduce blast radius by opening cache circuit breakers or disabling non-critical Redis paths. For pure cache, fall back to the database with rate limits. For rate limits, locks or idempotency, apply the predefined fail-open or fail-closed policy.

#### Deep dive

The biggest risk is cascading failure: Redis fails, application threads block, retries multiply, database receives all cache misses, and the whole service degrades. Incident response should control traffic and concurrency.

#### Production angle

Use dashboards for Redis errors, client pool waits, API latency and database load. Communicate degraded behavior clearly if user-visible features are affected.

#### Traps / caveats

- Restarting Redis can create cold-cache pressure.
- Increasing retries during an outage usually makes things worse.
- A fail-open security control can become an abuse incident.

#### Optional Anki

Q: What is a major risk during Redis outage?
A: Cache misses and retries overloading the database and application threads.

</details>

<a id="redis-prod-009"></a>

<details>
<summary><strong>REDIS-PROD-009. How would you investigate a Redis latency spike?</strong></summary>

#### Short answer

Separate server, network and client causes, then inspect slow commands, big keys, resource usage and recent changes.

#### Interview answer

I would check whether latency is visible on Redis server metrics or only in application metrics. Then I would inspect slow logs, command stats, CPU, memory, evictions, network, connection count, replication or persistence activity, and recent deployments.

#### Deep dive

Client-side latency can come from connection pool waits, event-loop blocking, serialization, DNS, TLS, GC pauses or timeouts. Server-side latency can come from slow commands, big keys, fork/persistence work, CPU saturation or network bandwidth.

#### Production angle

Correlate Redis latency with API p99, database load and deployment markers. If one command or cache name dominates, mitigate that path first.

#### Traps / caveats

- Redis `SLOWLOG` does not include network and client queueing.
- A single hot key may not show as high total command volume.
- Persistence or failover events can create temporary spikes.

#### Optional Anki

Q: Why compare server and client Redis latency?
A: To distinguish Redis execution from network, pool and Java-side delays.

</details>

<a id="redis-prod-010"></a>

<details>
<summary><strong>REDIS-PROD-010. How would you diagnose Redis client connection pool exhaustion or command timeouts?</strong></summary>

#### Short answer

Check pool active/idle/wait metrics, command latency, timeout counts, thread dumps and traffic changes.

#### Interview answer

If the pool is exhausted, requests wait for a connection before even reaching Redis. I would inspect pool wait time, active connections, max pool size, Redis command latency, blocked threads and whether a deployment increased Redis calls per request.

#### Deep dive

Pool exhaustion can be caused by slow Redis, too much concurrency, missing timeouts, leaked connections, blocking callbacks, large pipelines or too many commands per request. Increasing pool size may help briefly but can also overload Redis.

#### Production angle

Set alerts on pool wait time and command timeouts. Use bulkheads for Redis-heavy paths and reduce unnecessary cache calls.

#### Traps / caveats

- Pool wait time can be mistaken for Redis server latency.
- Larger pools can amplify load during incidents.
- Leaked or long-held connections can starve the pool.

#### Optional Anki

Q: What metric reveals Redis pool exhaustion?
A: Connection pool wait time or pending acquire count.

</details>

<a id="redis-prod-011"></a>

<details>
<summary><strong>REDIS-PROD-011. How would you distinguish Redis server latency from network or client-side latency?</strong></summary>

#### Short answer

Compare Redis server metrics and slow logs with application-side timers, pool metrics and network observations.

#### Interview answer

If Redis server command latency is low but the application sees high Redis latency, the problem is likely client-side or network: pool wait, DNS, TLS, packet loss, GC, serialization or event-loop blocking. If Redis server latency is high too, inspect slow commands, big keys, CPU, memory and persistence.

#### Deep dive

Add separate timers for pool acquisition, command round trip and serialization if possible. Check whether all services see the latency or only one deployment, node, availability zone or client version.

#### Production angle

This distinction prevents wrong fixes. Scaling Redis will not fix a Java pool wait issue, and increasing client pools will not fix a slow Redis command.

#### Traps / caveats

- End-to-end Redis client timers include more than Redis execution.
- Server metrics may be healthy while one app node has network issues.
- TLS and serialization overhead can become visible under high throughput.

#### Optional Anki

Q: If Redis server latency is low but app latency is high, where do you look?
A: Client pool, network, serialization, GC and application threading.

</details>
