# Redis use cases beyond simple caching

---

<a id="redis-use-001"></a>

<details>
<summary><strong>REDIS-USE-001. How can Redis be used for rate limiting?</strong></summary>

#### Short answer

Redis can store counters or time-window data with TTLs so multiple application instances enforce a shared rate limit.

#### Interview answer

For example, each request increments a Redis key for a user, IP or API token. If the value exceeds the allowed limit, the service rejects or throttles the request. Because Redis is shared, the limit works across many application instances.

#### Deep dive

Rate limiter design depends on accuracy needs. Fixed window is simple but bursty at boundaries. Sliding window is more precise but costs more memory and commands. Token bucket smooths traffic and allows controlled bursts.

#### Production angle

Rate limiter Redis operations must be atomic and fast. Define behavior when Redis is unavailable: fail open, fail closed or use a local fallback depending on abuse risk and availability requirements.

#### Traps / caveats

- Missing TTL can create permanent limiter keys.
- Non-atomic `INCR` plus `EXPIRE` can leak counters.
- High-cardinality keys can grow memory quickly.

#### Optional Anki

Q: Why use Redis for distributed rate limiting?
A: It provides shared counters across application instances.

</details>

<a id="redis-use-002"></a>

<details>
<summary><strong>REDIS-USE-002. What are fixed window, sliding window and token bucket rate limiters?</strong></summary>

#### Short answer

Fixed window counts requests in fixed intervals, sliding window tracks a moving interval, and token bucket refills allowance over time.

#### Interview answer

Fixed window is simple: allow N requests per minute. It can allow bursts at boundaries. Sliding window smooths this by considering requests in the last moving time range. Token bucket adds tokens at a fixed rate and each request consumes one, allowing bursts up to bucket capacity.

#### Deep dive

Fixed window is easiest and cheapest. Sliding window with sorted sets gives better accuracy but more memory usage. Token bucket is often a good balance for APIs because it models sustained rate plus burst capacity.

#### Production angle

Choose by abuse risk and cost. Public login APIs may need stricter controls than internal low-risk APIs.

#### Traps / caveats

- Per-IP limits can harm users behind NAT.
- Per-user limits require authenticated identity.
- Distributed rate limits need consistent key design across services.

#### Optional Anki

Q: Which rate limiter allows controlled bursts?
A: Token bucket.

</details>

<a id="redis-use-003"></a>

<details>
<summary><strong>REDIS-USE-003. How can Redis be used for short-lived idempotency keys?</strong></summary>

#### Short answer

Redis can store a request ID or operation key with a TTL to detect duplicate requests within a retry window.

#### Interview answer

For an API like payment initiation, the client sends an idempotency key. The service stores that key in Redis with a status or response summary. If the same key appears again, the service can return the previous result or avoid starting the operation twice.

#### Deep dive

Correctness depends on when the key is written and what value is stored. A simple "seen" marker may block retries after a failed attempt. A better design stores states such as in-progress, succeeded and failed, or relies on a database uniqueness constraint for critical operations.

#### Production angle

Redis idempotency keys are good for short retry windows. For financial or durable business operations, use a database constraint or operation table as the final guarantee.

#### Traps / caveats

- Eviction or expiration can allow duplicates after the window.
- A key written before work starts can block legitimate retries if the process crashes.
- Idempotency keys must be scoped by user or tenant.

#### Optional Anki

Q: What does an idempotency key prevent?
A: Repeating the same logical operation during retries.

</details>

<a id="redis-use-004"></a>

<details>
<summary><strong>REDIS-USE-004. When is a Redis distributed lock appropriate?</strong></summary>

#### Short answer

It is appropriate for short, best-effort coordination where occasional failure is acceptable or recoverable.

#### Interview answer

Redis locks can be useful to prevent duplicate cache rebuilds, coordinate scheduled jobs, or serialize low-risk work across instances. The lock should have a unique owner value, expiration and safe release logic.

#### Deep dive

Redis locks are not a substitute for database constraints or transactions when protecting critical invariants. They coordinate clients but do not make the protected operation atomic with an external database.

#### Production angle

Use Redis locks for bounded work with clear timeout and recovery behavior. For money movement, uniqueness, inventory ownership or other critical state, prefer database-level guarantees.

#### Traps / caveats

- A lock can expire while the owner is still working.
- Network partitions and failover can break assumptions.
- Releasing a lock without checking owner value can delete someone else's lock.

#### Optional Anki

Q: What kind of work is Redis locking best suited for?
A: Short-lived, recoverable coordination.

</details>

<a id="redis-use-005"></a>

<details>
<summary><strong>REDIS-USE-005. What can go wrong with Redis distributed locks?</strong></summary>

#### Short answer

Locks can expire too early, be released by the wrong owner, be duplicated during failover, or fail to protect external state.

#### Interview answer

A client may acquire a lock, pause due to GC or network delay, and continue working after the lock expired. Another client can acquire the same lock and both perform the protected operation. If release is just `DEL`, one client can delete another client's lock.

#### Deep dive

Redis replication and failover add more edge cases because a lock write may not have reached a replica before failover. Even a correctly implemented Redis lock does not protect a database update unless the database also enforces the invariant.

#### Production angle

Use lock TTLs longer than expected work but short enough for recovery. Store unique values and release with an atomic check-and-delete script. Add fencing tokens when the protected resource can validate order.

#### Traps / caveats

- GC pauses can outlive lock TTL.
- Client clock is not a reliable lock authority.
- Locks need monitoring for wait time, failures and timeouts.

#### Optional Anki

Q: Why should Redis lock release check a unique value?
A: To avoid deleting a lock acquired by another client.

</details>

<a id="redis-use-006"></a>

<details>
<summary><strong>REDIS-USE-006. Why should Redis locks use a `SET NX PX`-style acquire, a unique value and an expiration?</strong></summary>

#### Short answer

`SET NX PX` atomically acquires only if absent and sets a TTL; the unique value identifies the owner.

#### Interview answer

`NX` prevents overwriting an existing lock. `PX` or `EX` sets an expiration so the lock eventually releases if the owner crashes. The unique value, such as a UUID, lets the owner release only its own lock.

#### Deep dive

The acquire operation must be one atomic command. Doing `SETNX` and `EXPIRE` separately can leave a lock without TTL if the client crashes between commands.

#### Production angle

Lock TTL must be chosen based on worst-case operation time and failure recovery. For long operations, consider whether a lock is the right design at all.

#### Traps / caveats

- TTL too short allows overlapping owners.
- TTL too long slows recovery after crashes.
- Lock extension also needs safe owner checks.

#### Optional Anki

Q: Why use `SET NX PX` for Redis lock acquire?
A: It atomically sets the lock only if absent and gives it an expiration.

</details>

<a id="redis-use-007"></a>

<details>
<summary><strong>REDIS-USE-007. When should a database constraint or transaction be preferred over a Redis lock?</strong></summary>

#### Short answer

Prefer the database when protecting durable business invariants or data that is stored in the database.

#### Interview answer

If the rule is "order number must be unique", "balance cannot go below zero", or "only one active subscription exists", the database should enforce it with constraints, transactions, locks or optimistic versioning. Redis can reduce duplicate attempts, but the database should be the final authority.

#### Deep dive

Redis locks can fail due to timeout, failover or client pauses. A database constraint remains attached to the data and is checked at commit time. This is usually stronger and simpler for critical correctness.

#### Production angle

Use Redis locks as an optimization or coordination aid, not as the only guard for financial, inventory or identity correctness.

#### Traps / caveats

- Application-level locks are easy to bypass from another code path.
- Database constraints also document invariants.
- A lock around a non-transactional sequence can still leave partial updates.

#### Optional Anki

Q: What should protect unique business records?
A: A database constraint or transaction, not only a Redis lock.

</details>

<a id="redis-use-008"></a>

<details>
<summary><strong>REDIS-USE-008. Why should Redis rate limiters use atomic commands or Lua scripts?</strong></summary>

#### Short answer

Because rate limiting usually reads, updates and expires state, and races can allow too many requests or leak limiter keys.

#### Interview answer

If multiple app instances increment and check a counter with separate commands, they can race. If expiration is set separately, a crash can leave permanent counters. Atomic commands or Lua scripts make the decision and state update happen together.

#### Deep dive

Fixed-window limiters often need "increment and set TTL if first request". Sliding-window limiters often need "remove old entries, add current request, count entries and decide". These are multi-step operations that should be atomic.

#### Production angle

Rate limiter bugs can either block legitimate users or fail to stop abuse. Keep scripts bounded and monitor limiter errors separately from normal Redis errors.

#### Traps / caveats

- Pipelining is not atomic.
- Client-side clocks can create inconsistent sliding windows.
- High-cardinality limiters need memory controls.

#### Optional Anki

Q: Why use Lua in a Redis sliding-window limiter?
A: To remove old entries, add the request and count atomically.

</details>

<a id="redis-use-009"></a>

<details>
<summary><strong>REDIS-USE-009. Why should releasing a Redis lock verify the unique value atomically?</strong></summary>

#### Short answer

Because the original lock may have expired and another client may now own the same lock key.

#### Interview answer

If client A acquires a lock and pauses, the lock may expire. Client B then acquires the lock. If client A later calls `DEL lockKey`, it deletes B's lock. The release operation must check "is the value still mine?" and delete only if true, atomically.

#### Deep dive

This is usually implemented with a small Lua script that compares the stored value with the expected token and deletes only on match. Doing `GET` then `DEL` as separate commands has the same race problem.

#### Production angle

Safe release is mandatory for Redis locks in shared production systems. Log lock ownership failures at debug or metric level so contention can be observed.

#### Traps / caveats

- `DEL` alone is unsafe for locks.
- `GET` plus `DEL` separately is also unsafe.
- Safe release does not solve lock expiration during long work.

#### Optional Anki

Q: How should a Redis lock be released?
A: Atomically compare the owner token and delete only if it matches.

</details>

<a id="redis-use-010"></a>

<details>
<summary><strong>🧠 REDIS-USE-010. What is the Redlock algorithm, and why is it controversial?</strong></summary>

#### Short answer

Redlock tries to acquire a distributed lock across multiple independent Redis masters, but its safety under failures has been debated.

#### Interview answer

The idea is to acquire the same lock on a majority of independent Redis nodes within a time limit, then treat the lock as acquired. It aims to reduce the risk of one Redis node failure breaking the lock. The controversy is around timing assumptions, network partitions, clock drift and whether it provides the safety people expect for critical distributed coordination.

#### Deep dive

For many Java backend use cases, the practical advice is simpler: use Redis locks only for recoverable coordination. For critical correctness, use database constraints, transactions, fencing tokens or a coordination system designed for strong consistency.

#### Production angle

If Redlock is considered, document the failure model and test it. Do not use it as a shortcut for financial or inventory correctness without deeper design review.

#### Traps / caveats

- More Redis nodes do not automatically mean a correct distributed lock.
- Timing assumptions are hard in distributed systems.
- Fencing tokens are often needed to protect external resources.

#### Optional Anki

Q: Why is Redlock controversial?
A: Its safety depends on timing and failure assumptions that may not match critical coordination needs.

</details>
