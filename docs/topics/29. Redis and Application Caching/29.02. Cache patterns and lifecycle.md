# Cache patterns and lifecycle

---

<a id="cache-pat-001"></a>

<details>
<summary><strong>CACHE-PAT-001. What is cache-aside?</strong></summary>

#### Short answer

Cache-aside means the application reads from cache first, loads from the source of truth on a miss, then stores the value in cache.

#### Interview answer

In cache-aside, the application owns cache access. For a read, it checks Redis or local cache. If the value is missing, it queries the database, returns the result and writes it to cache with a TTL. For writes, the application usually updates the database and then invalidates or updates the cache.

#### Deep dive

This pattern is simple and common in Java backend systems because it does not require the cache to know how to load data. It also means the application must handle stampedes, stale data, negative caching and invalidation.

#### Production angle

Cache-aside works well for read-heavy data where cache misses are acceptable. The miss path must be efficient and protected because traffic can suddenly shift to the database after expiration or Redis outage.

#### Traps / caveats

- Concurrent misses can rebuild the same value many times.
- Write and invalidation ordering matters.
- A failed cache write should usually not fail the main read.

#### Optional Anki

Q: Who loads data on a cache-aside miss?
A: The application.

</details>

<a id="cache-pat-002"></a>

<details>
<summary><strong>CACHE-PAT-002. What is read-through caching?</strong></summary>

#### Short answer

Read-through caching means the cache layer loads missing data from the source of truth instead of the application doing it explicitly.

#### Interview answer

With read-through caching, the application asks the cache for a value. If the value is missing, the cache abstraction calls a configured loader, stores the value and returns it. In Java, this is common with local caches such as Caffeine loaders. Redis itself is usually used with cache-aside unless a framework or custom layer provides the loader behavior.

#### Deep dive

The benefit is simpler application code and consistent loading behavior. The cost is that data loading becomes coupled to the cache abstraction, and failures can be less visible if the abstraction hides too much.

#### Production angle

Read-through is useful for reference data and computed values. It still needs metrics for hit rate, load time, load failures and eviction.

#### Traps / caveats

- Do not let cache loaders perform unbounded slow work.
- Loader failures must be handled explicitly.
- Read-through does not solve invalidation by itself.

#### Optional Anki

Q: What is read-through caching?
A: The cache abstraction loads missing values from the source.

</details>

<a id="cache-pat-003"></a>

<details>
<summary><strong>CACHE-PAT-003. What is write-through caching?</strong></summary>

#### Short answer

Write-through means writes go through the cache layer and are synchronously written to the source of truth.

#### Interview answer

In write-through caching, the application writes to the cache abstraction, and the cache writes the data to the database or underlying store before the operation is considered successful. The goal is to keep cache and source more aligned.

#### Deep dive

This pattern can reduce stale reads because the cache is updated as part of the write path. The downside is higher write latency and tighter coupling between cache and persistence. In many Spring backend systems, explicit database write plus cache eviction is more common than true write-through.

#### Production angle

Use write-through only when the abstraction is well controlled and write latency is acceptable. For critical data, the database should remain authoritative.

#### Traps / caveats

- A cache write must not become the only durable write unless Redis is intentionally the data store.
- Partial failures need clear behavior.
- Write-through does not avoid distributed transaction concerns across services.

#### Optional Anki

Q: Main downside of write-through caching?
A: It adds latency and coupling to the write path.

</details>

<a id="cache-pat-004"></a>

<details>
<summary><strong>CACHE-PAT-004. What is cache warming, and when is it useful?</strong></summary>

#### Short answer

Cache warming preloads important cache entries before real traffic needs them.

#### Interview answer

Cache warming is useful when cold misses are expensive or risky. For example, after deployment or Redis restart, a service may preload popular product metadata, configuration or read models so the first wave of user requests does not all hit the database.

#### Deep dive

Warming can be eager, where known keys are loaded at startup or after deployment, or gradual, where background jobs load popular keys. It must be rate-limited because aggressive warming can overload the database.

#### Production angle

Use warming for predictable hot data and high-traffic systems. Monitor database load during warmup and avoid making service readiness depend on loading a large cache unless that is truly required.

#### Traps / caveats

- Warmup jobs can cause the outage they are meant to prevent.
- Warming stale or wrong data is still a problem.
- Long startup warmup can slow deployments and autoscaling.

#### Optional Anki

Q: What is cache warming?
A: Preloading expected hot entries before traffic needs them.

</details>

<a id="cache-pat-005"></a>

<details>
<summary><strong>CACHE-PAT-005. What is negative caching, and when should it be used?</strong></summary>

#### Short answer

Negative caching stores "not found" or failed lookup results for a short time to avoid repeated expensive misses.

#### Interview answer

If many requests ask for a missing user, invalid token or nonexistent product ID, every request may hit the database unless the negative result is cached. Storing a short-lived marker for "not found" can reduce load and protect the source of truth.

#### Deep dive

Negative cache entries need short TTLs because the missing value may later be created. The cache must distinguish "key absent from cache" from "cached negative result". This is often done with a sentinel value or wrapper object.

#### Production angle

Negative caching is useful against repeated bad requests, cache penetration and expensive lookup misses. It is especially helpful for public APIs where clients may request invalid IDs.

#### Traps / caveats

- Long negative TTLs can hide newly created data.
- Do not cache authorization failures blindly without considering permission changes.
- Be careful not to store sensitive failure details.

#### Optional Anki

Q: Why use negative caching?
A: To avoid repeatedly loading known-missing data from the source of truth.

</details>

<a id="cache-pat-006"></a>

<details>
<summary><strong>CACHE-PAT-006. How do you choose TTL values?</strong></summary>

#### Short answer

Choose TTL based on acceptable staleness, update frequency, miss cost, traffic shape and failure behavior.

#### Interview answer

There is no universal TTL. For stable reference data, a longer TTL may be fine. For volatile or user-sensitive data, TTL should be short or replaced with explicit invalidation. I also consider how expensive a miss is, whether many keys expire together, and what happens if Redis or the database is slow.

#### Deep dive

TTL is a business and operational decision. A TTL should be long enough to give useful hit rate, but short enough to limit stale data. TTL jitter is often added so many keys do not expire at the same time.

#### Production angle

Track hit rate, miss rate, stale-data incidents, source load, evictions and key count after TTL changes. Roll out TTL changes gradually for high-traffic caches.

#### Traps / caveats

- Very long TTLs can turn bugs into long-lived correctness issues.
- Very short TTLs can make Redis overhead higher than benefit.
- Identical TTLs on many keys can cause cache avalanche.

#### Optional Anki

Q: What factors determine cache TTL?
A: Staleness tolerance, update frequency, miss cost, traffic and failure behavior.

</details>

<a id="cache-pat-007"></a>

<details>
<summary><strong>🧠 CACHE-PAT-007. How does write-behind caching affect durability and ordering?</strong></summary>

#### Short answer

Write-behind acknowledges writes before the source of truth is updated, improving latency but risking data loss and ordering bugs.

#### Interview answer

In write-behind, the application writes to a cache or buffer first, and a background process later writes to the database. This can improve write latency and batch writes, but it weakens durability unless the buffer is durable and carefully replayed.

#### Deep dive

The hard parts are failure recovery, ordering, duplicate writes and visibility. If two updates to the same entity are flushed out of order, the database can end up with an older value. If the cache crashes before flushing, acknowledged writes may be lost.

#### Production angle

For critical business data, prefer writing to the database or a durable log first. Write-behind is safer for derived data, analytics, counters or cases where loss and reordering are acceptable or repairable.

#### Traps / caveats

- Redis memory alone is not a reliable durable write buffer.
- Background flush errors need retry, dead-lettering and alerting.
- Ordering must be defined per entity or key, not globally assumed.

#### Optional Anki

Q: Main risk of write-behind caching?
A: Acknowledged writes can be lost or persisted out of order.

</details>
