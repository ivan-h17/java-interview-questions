# Availability, persistence and scaling

---

<a id="redis-ops-001"></a>

<details>
<summary><strong>REDIS-OPS-001. What should a Java service do if Redis is unavailable?</strong></summary>

#### Short answer

For pure cache reads, usually bypass Redis and use the source of truth with protection. For correctness-critical Redis state, fail safely.

#### Interview answer

The behavior depends on Redis's role. If Redis is only a cache, the service can log the error, increment a metric and fall back to the database or downstream service with rate limits. If Redis is enforcing rate limits, locks or idempotency, the service must decide whether fail-open or fail-closed is safer.

#### Deep dive

Fallbacks must be bounded. If every request bypasses Redis and hits the database, the database can fail next. Circuit breakers, short timeouts, bulkheads and request shedding may be needed.

#### Production angle

Define Redis failure behavior per cache or use case before an incident. Practice Redis outage scenarios with realistic traffic.

#### Traps / caveats

- Falling back to the database can overload it.
- Failing open for rate limits may allow abuse.
- Failing closed for public APIs may create a user-visible outage.

#### Optional Anki

Q: How should a service handle pure cache Redis failure?
A: Bypass cache and use the source of truth with bounded fallback.

</details>

<a id="redis-ops-002"></a>

<details>
<summary><strong>REDIS-OPS-002. How should timeouts be configured for Redis clients?</strong></summary>

#### Short answer

Redis timeouts should be explicit, short enough to protect request latency, and aligned with the caller's total latency budget.

#### Interview answer

A Redis cache call should not be allowed to hang for seconds if the API budget is 200 ms. Configure connect timeouts, command timeouts and socket/read timeouts. For cache reads, timeouts are usually short because the service can fall back or skip cache.

#### Deep dive

Timeouts should consider p95/p99 Redis latency, network distance, retry policy and thread-pool capacity. A retry after a timeout must still fit in the user's overall request budget.

#### Production angle

Monitor timeout counts, pool wait time and command latency. A rising timeout rate is often a better alert than Redis being fully down.

#### Traps / caveats

- No timeout can exhaust servlet or worker threads.
- Too aggressive timeouts can create unnecessary fallback load.
- Retrying after timeout can duplicate non-idempotent operations.

#### Optional Anki

Q: Why should Redis cache timeouts be short?
A: Redis is a remote dependency and should not consume the whole request budget.

</details>

<a id="redis-ops-003"></a>

<details>
<summary><strong>REDIS-OPS-003. Why should Redis calls usually have bounded latency budgets?</strong></summary>

#### Short answer

Because Redis is often on the critical request path, and unbounded waits can cascade into thread exhaustion and API timeouts.

#### Interview answer

Even if Redis is fast most of the time, network issues, failover, slow commands or pool exhaustion can make calls hang. A bounded latency budget ensures the service can stop waiting and choose fallback behavior.

#### Deep dive

Latency budget includes pool wait, serialization, network round trip, Redis execution and deserialization. Measuring only Redis server time misses important parts of the user-visible delay.

#### Production angle

Set budgets per operation type. A best-effort cache read may have a very small budget, while a required idempotency check may have a larger but still bounded one.

#### Traps / caveats

- A Redis dependency can break API SLOs even when the database is healthy.
- Pool wait time is often hidden.
- Infinite retries defeat latency budgets.

#### Optional Anki

Q: What does Redis latency budget include besides server execution?
A: Pool wait, serialization, network and client-side processing.

</details>

<a id="redis-ops-004"></a>

<details>
<summary><strong>REDIS-OPS-004. When is persistence unnecessary for a pure cache?</strong></summary>

#### Short answer

Persistence is unnecessary when every cached value can be safely rebuilt from the source of truth and cold-cache behavior is acceptable.

#### Interview answer

If Redis contains only derived cache entries, losing Redis data should not lose business data. In that case, persistence may add disk overhead and recovery complexity without much benefit. The service should be able to repopulate the cache gradually.

#### Deep dive

The main question is not "can data be rebuilt?" but "can the system survive rebuilding it under real traffic?" If cold-cache misses overload the database, persistence or controlled warmup may still be useful.

#### Production angle

For pure caches, many teams prioritize memory, eviction policy and warmup strategy over Redis durability. Document that Redis data loss is acceptable.

#### Traps / caveats

- "Pure cache" must be true for all keys in the Redis instance.
- Cold-cache recovery can still cause an outage.
- Mixed use with locks/idempotency/rate limits changes the persistence discussion.

#### Optional Anki

Q: When can Redis cache persistence be skipped?
A: When data is rebuildable and cold-cache recovery is safe.

</details>

<a id="redis-ops-005"></a>

<details>
<summary><strong>REDIS-OPS-005. What is Redis replication used for?</strong></summary>

#### Short answer

Replication copies data from a primary to replicas for high availability, read scaling in some cases and failover.

#### Interview answer

Redis replication allows replicas to maintain copies of a primary's data. If the primary fails, a replica can be promoted depending on the deployment. Replicas can also serve reads when stale reads are acceptable.

#### Deep dive

Replication is usually asynchronous, so a promoted replica may be missing recent writes. This matters for locks, idempotency keys and counters more than for best-effort cache entries.

#### Production angle

Replication improves availability but does not eliminate consistency risk. Monitor replication lag, failover events and role changes.

#### Traps / caveats

- Replication is not the same as strong consistency.
- Reading from replicas can return stale data.
- Failover can lose recent writes.

#### Optional Anki

Q: Is Redis replication usually synchronous?
A: No, it is commonly asynchronous.

</details>

<a id="redis-ops-006"></a>

<details>
<summary><strong>REDIS-OPS-006. What consistency and data-loss risks remain with Redis replication or failover?</strong></summary>

#### Short answer

Recent writes can be lost, reads from replicas can be stale, and clients can temporarily talk to outdated topology.

#### Interview answer

Because replication is commonly asynchronous, a primary may acknowledge a write before replicas receive it. If the primary fails immediately, the promoted replica may not have that write. During failover, clients may also see connection errors, timeouts or stale primary information.

#### Deep dive

This is acceptable for many cache entries but dangerous for locks, idempotency and rate limits if the application assumes perfect continuity. Failover behavior must be part of the correctness design.

#### Production angle

Test failover under traffic. Monitor replication lag, failover duration, command errors and client reconnect behavior.

#### Traps / caveats

- Redis high availability is not the same as no data loss.
- A successful write response can still be lost in a failover window.
- Retrying after failover may duplicate operations.

#### Optional Anki

Q: Why can Redis failover lose writes?
A: The acknowledged write may not have replicated before primary failure.

</details>

<a id="redis-ops-007"></a>

<details>
<summary><strong>REDIS-OPS-007. What is Redis Sentinel, and what problem does it solve?</strong></summary>

#### Short answer

Redis Sentinel monitors Redis primaries and replicas, detects failures and coordinates automatic failover.

#### Interview answer

Sentinel is used for high availability in non-clustered Redis deployments. It watches Redis instances, decides when a primary is down, promotes a replica and helps clients discover the current primary.

#### Deep dive

Sentinel does not shard data. It provides monitoring and failover for a primary-replica setup. Applications need clients configured to talk to Sentinels so they can find the new primary after failover.

#### Production angle

Use multiple Sentinel nodes so one Sentinel failure does not break failover decisions. Test application reconnection behavior, not just Redis promotion.

#### Traps / caveats

- Sentinel is for availability, not horizontal data scaling.
- Failover can still cause brief errors.
- Asynchronous replication means data-loss windows remain.

#### Optional Anki

Q: Does Redis Sentinel shard data?
A: No, it manages monitoring and failover.

</details>

<a id="redis-ops-008"></a>

<details>
<summary><strong>REDIS-OPS-008. What is Redis Cluster, and how do hash slots affect key placement?</strong></summary>

#### Short answer

Redis Cluster shards data across nodes using hash slots; each key maps to one slot and each slot belongs to a primary node.

#### Interview answer

Redis Cluster splits the keyspace into 16384 hash slots. A key is hashed to a slot, and the slot determines which node stores the key. This allows horizontal scaling and node-level failover, but clients must understand cluster redirections and topology.

#### Deep dive

Because one key maps to one slot, a single hot key is still limited by one node. Multi-key operations are restricted unless all keys are in the same slot.

#### Production angle

Use cluster-aware Java clients and test topology refresh. Watch for uneven key distribution, hot slots and resharding effects.

#### Traps / caveats

- Redis Cluster does not split one large key across nodes.
- Non-cluster-aware clients will fail or behave incorrectly.
- Multi-key commands have slot constraints.

#### Optional Anki

Q: How many hash slots does Redis Cluster use?
A: 16384.

</details>

<a id="redis-ops-009"></a>

<details>
<summary><strong>REDIS-OPS-009. Why do Redis Cluster multi-key operations need keys in the same hash slot?</strong></summary>

#### Short answer

Because Redis Cluster can only execute atomic multi-key operations when all involved keys are on the same node.

#### Interview answer

If two keys map to different slots, they may live on different primary nodes. Redis Cluster cannot execute many multi-key commands atomically across those nodes, so commands like multi-key operations or scripts require keys to be in the same slot.

#### Deep dive

This affects transactions, Lua scripts and commands that operate on multiple keys. Key tags can force related keys into the same slot, but overusing them can create hot slots.

#### Production angle

Design cluster key names before production. A non-clustered Redis design may break when moved to Redis Cluster if it relies on arbitrary multi-key operations.

#### Traps / caveats

- Key tags improve multi-key compatibility but reduce distribution.
- Same prefix does not automatically mean same hash slot.
- Cross-slot errors may appear only after moving to Cluster.

#### Optional Anki

Q: Why can a Redis Cluster command fail with cross-slot errors?
A: The keys map to different hash slots.

</details>

<a id="redis-ops-010"></a>

<details>
<summary><strong>🧠 REDIS-OPS-010. What are key tags in Redis Cluster, and when should they be used?</strong></summary>

#### Short answer

Key tags are the substring inside braces used by Redis Cluster hashing so related keys can be placed in the same slot.

#### Interview answer

For keys like `cart:{user123}:items` and `cart:{user123}:total`, Redis Cluster hashes only `user123` for slot placement. This lets multi-key commands or Lua scripts operate on related keys in the same slot.

#### Deep dive

Key tags should be used deliberately for small groups of related keys that need atomic multi-key behavior. If the tag has low cardinality, such as `{global}`, it can overload one slot and one node.

#### Production angle

Use key tags for per-entity groups, not entire cache regions. Check slot distribution during design and load testing.

#### Traps / caveats

- Overusing the same tag creates hot slots.
- Tags solve slot placement, not distributed consistency with databases.
- All clients and services must follow the same key convention.

#### Optional Anki

Q: What part of `cart:{user123}:items` is used as the Redis Cluster hash tag?
A: `user123`.

</details>

<a id="redis-ops-011"></a>

<details>
<summary><strong>REDIS-OPS-011. How should Java clients behave during Redis failover or topology changes?</strong></summary>

#### Short answer

They should reconnect, refresh topology, respect command timeouts and surface errors without creating retry storms.

#### Interview answer

During failover, commands may fail briefly or be redirected. A Java client should discover the new primary or updated cluster slots, retry only when safe, and avoid blocking request threads for too long. The application should know which Redis operations can be skipped and which require fail-safe behavior.

#### Deep dive

Cluster clients need to handle `MOVED` and `ASK` redirections. Sentinel clients need to discover promoted primaries. Application retries should be bounded and idempotency-aware.

#### Production angle

Include Redis failover in resilience tests. Watch reconnects, topology refresh counts, command timeouts, retry counts and p99 latency during failover.

#### Traps / caveats

- Default client settings may not refresh topology quickly enough.
- Retrying non-idempotent operations can duplicate effects.
- Failover can produce partial outages even when Redis recovers quickly.

#### Optional Anki

Q: What should Redis Cluster clients refresh after topology changes?
A: Slot-to-node mappings.

</details>

<a id="redis-ops-012"></a>

<details>
<summary><strong>REDIS-OPS-012. What is the difference between RDB and AOF persistence?</strong></summary>

#### Short answer

RDB stores point-in-time snapshots; AOF logs write operations so Redis can replay them on restart.

#### Interview answer

RDB is compact and efficient for snapshots, but it can lose changes since the last snapshot. AOF can reduce data loss depending on fsync settings because it records writes, but it uses more disk I/O and may need rewriting to stay compact.

#### Deep dive

Persistence choice depends on whether Redis data is rebuildable and how much loss is acceptable. For pure cache, persistence may be unnecessary. For short-lived operational state, persistence may help or may restore stale state unexpectedly.

#### Production angle

Understand persistence settings before relying on Redis data after restart. Monitor disk, fsync latency and rewrite behavior if AOF is enabled.

#### Traps / caveats

- Persistence does not make Redis equivalent to a relational database.
- AOF fsync settings trade durability for performance.
- Restored cache data can be stale after application or database changes.

#### Optional Anki

Q: RDB vs AOF in one line?
A: RDB snapshots state; AOF replays logged writes.

</details>

<a id="redis-ops-013"></a>

<details>
<summary><strong>REDIS-OPS-013. How do Redis restart, cache warmup and cold-cache behavior affect backend services?</strong></summary>

#### Short answer

Restart can remove or change cache contents, and cold-cache traffic can overload the source of truth unless warmup is controlled.

#### Interview answer

After Redis restart, the cache may be empty or restored from persistence. If empty, many requests miss and hit the database. If restored, values may be stale relative to recent database changes or new application code.

#### Deep dive

Warmup can reduce cold misses, but it must be throttled. Restored caches may require versioned keys to avoid incompatible serialized data after deployments.

#### Production angle

Plan restart procedures: whether to preserve data, flush data, warm key subsets, or let traffic refill gradually. Watch database load and cache miss rate during recovery.

#### Traps / caveats

- Automatic warmup can overload the database.
- Restoring old cache entries can resurrect stale data.
- Autoscaling creates many local cold caches even if Redis is warm.

#### Optional Anki

Q: What is the main risk after Redis cache restart?
A: Cold-cache misses overloading the source of truth.

</details>

<a id="redis-ops-014"></a>

<details>
<summary><strong>REDIS-OPS-014. How should Redis be secured in a production Java backend environment?</strong></summary>

#### Short answer

Restrict network access, require authentication, use TLS when needed, apply ACLs, avoid sensitive values where possible and monitor access.

#### Interview answer

Redis should not be publicly exposed. It should run in a private network, require credentials, use least-privilege ACLs where practical, and use TLS for untrusted networks or compliance needs. Cached sensitive data should have short TTLs and avoid unnecessary personal or secret values.

#### Deep dive

Security also includes operational hygiene: rotating credentials, not logging Redis URLs with passwords, protecting backups/AOF files, and preventing dangerous commands from application accounts if supported by the deployment.

#### Production angle

Treat Redis as a data store containing potentially sensitive data. Include it in threat modeling, secrets management, audit and incident response.

#### Traps / caveats

- "It is only cache" does not mean data is harmless.
- Redis backups and persistence files can contain sensitive data.
- Shared Redis instances need strong namespace and access boundaries.

#### Optional Anki

Q: Should Redis be exposed directly to the public internet?
A: No.

</details>

<a id="redis-ops-015"></a>

<details>
<summary><strong>🧠 REDIS-OPS-015. When can Redis persistence make a cache failure mode worse?</strong></summary>

#### Short answer

Persistence can restore stale or incompatible cache data, add disk latency, or preserve bad state that should have disappeared.

#### Interview answer

For a pure cache, restarting empty may be safer than restoring old values. If Redis restores cache entries written by an old application version, new code may fail to deserialize them. If it restores old authorization or configuration snapshots, stale behavior may continue after restart.

#### Deep dive

AOF and RDB also add operational costs such as disk usage, fsync latency and rewrite overhead. For some workloads, persistence increases Redis latency without improving correctness.

#### Production angle

Decide per Redis deployment whether persistence is needed. Use key versioning and TTLs so restored cache entries cannot live forever.

#### Traps / caveats

- Persistence can preserve poison cache entries.
- Disk pressure can become a Redis availability issue.
- Restored locks or idempotency state may not match real-world operation status.

#### Optional Anki

Q: Why can persistence be bad for a pure cache?
A: It can restore stale, incompatible or poison cache entries.

</details>
