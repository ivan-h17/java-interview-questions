# Caching fundamentals and fit

---

<a id="cache-fund-001"></a>

<details>
<summary><strong>CACHE-FUND-001. What problem does caching solve in backend applications?</strong></summary>

#### Short answer

Caching stores frequently used or expensive-to-compute data closer to the application so repeated reads are faster and cheaper.

#### Interview answer

In backend systems, caching mainly reduces latency, database load, network calls and repeated computation. Instead of asking the database or another service for the same data on every request, the application can reuse a previously computed value for a limited time.

#### Deep dive

A cache is useful when reads are frequent, the source of truth is slower or more expensive, and slightly stale data is acceptable. Common examples are product metadata, feature configuration, reference data, permission lookups, search results and expensive aggregations.

#### Production angle

Caching can protect a database during traffic spikes, improve p95 and p99 latency, and reduce infrastructure cost. It should be introduced with clear ownership, TTLs, invalidation rules and monitoring.

#### Traps / caveats

- Caching does not remove the need for a correct source of truth.
- A fast wrong answer can be worse than a slow correct answer.
- Caching can hide database problems until the cache is cold or unavailable.

#### Optional Anki

Q: What are the main reasons to use a cache?
A: Lower latency, lower backend load, fewer remote calls and less repeated computation.

</details>

<a id="cache-fund-002"></a>

<details>
<summary><strong>CACHE-FUND-002. What are the main trade-offs of adding a cache?</strong></summary>

#### Short answer

A cache improves latency and load, but adds consistency, invalidation, memory, operational and debugging complexity.

#### Interview answer

The benefit is faster reads and less pressure on the database or downstream service. The cost is that now there are two places where data can exist: the source of truth and the cache. The system must decide how fresh the cached data must be, how to invalidate it, what happens on cache failure, and how to monitor whether caching is actually helping.

#### Deep dive

Caching introduces failure modes such as stale data, stampedes, hot keys, cache avalanches, serialization compatibility issues, memory pressure and cross-service inconsistency. The more business-critical the data is, the more carefully the cache contract must be designed.

#### Production angle

Before adding a cache, define the expected latency improvement, acceptable staleness, fallback behavior, TTL policy, metrics and alerting. Otherwise caching often becomes accidental state.

#### Traps / caveats

- Do not cache just because an endpoint is slow. First understand the bottleneck.
- Do not assume high hit rate means correctness.
- Caches need capacity planning and operational ownership.

#### Optional Anki

Q: What is the main correctness cost of caching?
A: The application must handle stale or inconsistent data.

</details>

<a id="cache-fund-003"></a>

<details>
<summary><strong>CACHE-FUND-003. What is the difference between local cache and distributed cache?</strong></summary>

#### Short answer

A local cache lives inside one application instance. A distributed cache is shared by multiple instances over the network.

#### Interview answer

A local cache, such as Caffeine, is very fast because it avoids network calls, but each application instance has its own copy. A distributed cache, such as Redis, gives all instances a shared cache view, but every access has network cost and depends on the cache service availability.

#### Deep dive

Local caches are good for small, hot, mostly read-only data where per-instance duplication is acceptable. Distributed caches are better when many instances must share values, coordinate short-lived state, or keep cache behavior consistent across a fleet.

#### Production angle

Local caches can create inconsistent behavior after updates because one pod may have a newer value than another. Distributed caches simplify sharing but introduce timeouts, connection pools, failover and Redis capacity concerns.

#### Traps / caveats

- Local cache invalidation across many instances is hard.
- Distributed cache access is still a remote dependency.
- Combining both can help, but it creates two levels of staleness.

#### Optional Anki

Q: Why is a local cache usually faster than Redis?
A: It avoids network I/O and lives in the same process.

</details>

<a id="cache-fund-004"></a>

<details>
<summary><strong>CACHE-FUND-004. When is an in-process cache such as Caffeine better than Redis?</strong></summary>

#### Short answer

Caffeine is better for very low-latency, per-instance, small or medium-sized hot data where shared state is not required.

#### Interview answer

I would prefer Caffeine when the data is safe to duplicate across service instances and the application needs sub-millisecond access without a network dependency. Examples include parsed configuration, small reference dictionaries, computed validation rules, or frequently used metadata.

#### Deep dive

Caffeine provides high-performance eviction, size limits and time-based expiration inside the JVM. It avoids Redis round trips and removes Redis as a dependency from the hot path. The trade-off is that each instance has its own cache state.

#### Production angle

Caffeine is often a good first choice for read-only or rarely changing data. It is also useful as an L1 cache in front of Redis, but then TTLs, invalidation and memory limits must be coordinated.

#### Traps / caveats

- Do not use local cache for data that must be immediately consistent across instances.
- Memory usage grows in every JVM instance.
- Rolling deployments can temporarily run different cached values.

#### Optional Anki

Q: Main advantage of Caffeine over Redis?
A: Lower latency and no network dependency for cached reads.

</details>

<a id="cache-fund-005"></a>

<details>
<summary><strong>CACHE-FUND-005. When is Redis a better fit than an in-process cache?</strong></summary>

#### Short answer

Redis is better when cached data or short-lived state must be shared across multiple application instances.

#### Interview answer

Redis is a good fit when many service instances need the same cached values, when invalidation must affect the whole fleet, or when the use case needs Redis data structures and atomic commands. Examples include distributed cache, rate limiting, idempotency keys, sessions, feature snapshots, counters and short-lived locks.

#### Deep dive

Redis trades local speed for shared state. It can centralize cache entries and provide TTLs, eviction policies, replication and high-throughput operations. But it also becomes a remote dependency with its own latency, failure modes and capacity limits.

#### Production angle

Use Redis with explicit timeout budgets and fallback behavior. For pure caching, the service should usually degrade gracefully if Redis is unavailable instead of failing all requests.

#### Traps / caveats

- Redis should not automatically become the primary database.
- Network latency and client pool saturation matter.
- Hot keys can overload one Redis node even if average load looks fine.

#### Optional Anki

Q: When is Redis better than local cache?
A: When multiple instances need shared cached data or shared short-lived state.

</details>

<a id="cache-fund-006"></a>

<details>
<summary><strong>CACHE-FUND-006. When should you avoid caching?</strong></summary>

#### Short answer

Avoid caching when data changes too often, must be strongly consistent, has low reuse, or would create more correctness risk than performance benefit.

#### Interview answer

Caching is a poor fit when every request needs fresh authoritative data, the result is rarely reused, invalidation is unclear, or stale data can cause serious business or security problems. In those cases, it is better to optimize the query, fix indexing, reduce payload size, or redesign the workflow.

#### Deep dive

Bad cache candidates include per-request unique results, highly volatile balances, critical authorization decisions without strict invalidation, and data where the application cannot tolerate stale reads. Caching also should not be used to hide missing database indexes or N+1 queries without understanding them.

#### Production angle

Avoid caching until you know the read pattern, source latency, data volatility and acceptable staleness. A cache added without these facts often becomes a source of incidents.

#### Traps / caveats

- "Slow endpoint" does not always mean "needs cache".
- Caching mutable user-specific data is risky.
- Low hit rate can add overhead without benefit.

#### Optional Anki

Q: Name one reason to avoid caching.
A: The data must be strongly consistent or changes too frequently.

</details>

<a id="cache-fund-007"></a>

<details>
<summary><strong>CACHE-FUND-007. What data is safe to cache, and what data is risky to cache?</strong></summary>

#### Short answer

Safe data is read-heavy, reusable and tolerant of staleness. Risky data is security-sensitive, user-specific, highly volatile or correctness-critical.

#### Interview answer

Good cache candidates include product catalogs, country lists, feature configuration, public metadata and expensive read models. Riskier candidates include account balances, authorization decisions, personal data, inventory during checkout and anything whose stale value can let a user see or do the wrong thing.

#### Deep dive

The question is not only whether data can be cached, but how. User-specific data can be cached if keys include user, tenant, permission and version context, and if invalidation is reliable. Critical data may use very short TTLs or no cache at all.

#### Production angle

Classify data by sensitivity, volatility and stale-read impact. This helps choose TTLs, encryption, key design, invalidation and whether Redis should be part of the request path.

#### Traps / caveats

- Shared keys for user-specific data can leak data between users.
- Permission changes must invalidate or bypass cached authorization-sensitive views.
- Personally identifiable data in Redis still needs security controls.

#### Optional Anki

Q: What makes data risky to cache?
A: High volatility, sensitivity, user-specific context, or strong correctness requirements.

</details>

<a id="cache-fund-008"></a>

<details>
<summary><strong>CACHE-FUND-008. What is a cache hit rate, and why can it be misleading?</strong></summary>

#### Short answer

Cache hit rate is the percentage of cache lookups served from cache, but it can hide latency, correctness and uneven key distribution problems.

#### Interview answer

A hit means the requested key was found in cache. A high hit rate usually suggests the cache is effective, but it is not enough. For example, a cache can have a high hit rate while a few misses still overload the database, while a hot key creates Redis latency, or while cached data is stale and wrong.

#### Deep dive

Hit rate should be evaluated with request volume, miss cost, p95/p99 latency, eviction rate, key cardinality and business correctness. A 95% hit rate can still be bad if the 5% misses are expensive queries during peak traffic.

#### Production angle

Monitor hit rate together with cache latency, database load, miss rate by endpoint, evictions, Redis CPU, memory, network and error rate.

#### Traps / caveats

- Global hit rate can hide one bad endpoint.
- A hit can return stale or unauthorized data.
- Hit rate is less useful without knowing miss cost.

#### Optional Anki

Q: Why is cache hit rate not enough?
A: It does not show miss cost, stale data, latency distribution or hot-key problems.

</details>

<a id="cache-fund-009"></a>

<details>
<summary><strong>CACHE-FUND-009. How do read/write ratio and data volatility affect caching decisions?</strong></summary>

#### Short answer

Caching works best for read-heavy, low-volatility data. Frequent writes and high volatility make invalidation and stale reads harder.

#### Interview answer

If data is read many times for every write, a cache can save a lot of repeated work. If data changes constantly, the cache may spend more time being invalidated or serving stale values than helping. The acceptable staleness window matters as much as the raw read/write ratio.

#### Deep dive

For read-heavy stable data, longer TTLs are often reasonable. For volatile data, use shorter TTLs, explicit invalidation, versioned keys, event-based updates, or skip caching. Some write-heavy flows are better served by database indexes, materialized views or denormalized read models.

#### Production angle

Measure reads per key, update frequency and miss cost. A small number of hot stable keys can justify caching more than a large number of rarely reused keys.

#### Traps / caveats

- High read volume does not help if every read is for a unique key.
- Writes must be coordinated with cache invalidation.
- Volatile data can create churn and eviction pressure.

#### Optional Anki

Q: What data pattern is best for caching?
A: Read-heavy data with good reuse and acceptable staleness.

</details>

<a id="cache-fund-010"></a>

<details>
<summary><strong>🧠 CACHE-FUND-010. How can caching make a system less reliable instead of more reliable?</strong></summary>

#### Short answer

A cache can become an extra dependency, hide overload, serve stale data, amplify failures and create recovery spikes.

#### Interview answer

Caching improves reliability only when failure behavior is designed. It can make things worse if Redis downtime fails every request, cache misses stampede the database, stale entries violate business rules, or cache recovery causes a sudden flood of expensive reloads.

#### Deep dive

Common reliability failures include no timeout on cache calls, retry storms, global key invalidation during peak traffic, synchronized TTL expiration, hot keys, and assuming Redis is always faster than the database. A cache also adds more deployment, monitoring and capacity planning work.

#### Production angle

Design for Redis failure: short timeouts, limited retries, circuit breakers where useful, fallback to source of truth, stale-if-error for safe data, TTL jitter and controlled warmup.

#### Traps / caveats

- A cache miss path must be load-tested.
- Retrying Redis aggressively can increase latency and thread exhaustion.
- Caches can delay detection of database regressions.

#### Optional Anki

Q: How can a cache amplify an outage?
A: By causing many simultaneous misses or retries that overload the source of truth.

</details>

<a id="cache-fund-011"></a>

<details>
<summary><strong>CACHE-FUND-011. What is multi-level caching, such as Caffeine plus Redis, and what trade-offs does it introduce?</strong></summary>

#### Short answer

Multi-level caching uses a fast local cache in front of a shared cache, usually to reduce Redis latency and load.

#### Interview answer

A common setup is Caffeine as L1 inside each JVM and Redis as L2 shared by the fleet. The application checks Caffeine first, then Redis, then the database. This can reduce Redis round trips for very hot keys while still allowing a shared cache behind the local one.

#### Deep dive

The trade-off is more complex consistency. A value can be stale in Caffeine even after Redis was updated or invalidated. L1 TTLs are usually shorter, and some systems use pub/sub or events to invalidate local entries across instances.

#### Production angle

Multi-level caching is useful for extremely hot reads, but should be added only after Redis latency or load is a measured bottleneck. Track hit rates at each level separately.

#### Traps / caveats

- Two cache levels mean two staleness windows.
- Local invalidation across instances is hard.
- L1 memory usage scales with the number of application instances.

#### Optional Anki

Q: What is a common L1/L2 cache setup in Java services?
A: Caffeine as local L1 and Redis as shared L2.

</details>
