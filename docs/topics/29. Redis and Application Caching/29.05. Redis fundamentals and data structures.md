# Redis fundamentals and data structures

---

<a id="redis-fund-001"></a>

<details>
<summary><strong>REDIS-FUND-001. What is Redis commonly used for in Java backend systems?</strong></summary>

#### Short answer

Redis is commonly used as a distributed cache and as a fast store for short-lived operational state.

#### Interview answer

In Java backend systems, Redis is used for application caching, session-like state, rate limiting, idempotency keys, distributed locks, counters, leaderboards, queues in simple cases and feature/config snapshots. The most common use is reducing database or service load through shared caching.

#### Deep dive

Redis is an in-memory data structure server with TTL support, atomic commands and several useful data types. It is fast, but it is still a remote dependency and must be treated differently from an in-process map.

#### Production angle

Redis should have clear ownership: what data is stored, why TTLs are chosen, what happens on Redis failure, and whether losing the data is acceptable.

#### Traps / caveats

- Do not use Redis as an accidental primary database for critical data.
- Avoid putting unbounded or large payloads into Redis.
- Redis use cases beyond cache still need correctness design.

#### Optional Anki

Q: What is the most common Redis use in Java services?
A: Distributed caching.

</details>

<a id="redis-fund-002"></a>

<details>
<summary><strong>REDIS-FUND-002. Why is Redis fast for many cache workloads?</strong></summary>

#### Short answer

Redis keeps data in memory, uses efficient data structures, avoids disk on normal reads, and executes many operations with low overhead.

#### Interview answer

Redis is fast because most operations access in-memory data structures and many common commands are O(1) or O(log n). It also uses an event-driven model where command execution is simple and predictable for many workloads.

#### Deep dive

Redis speed does not mean every Redis operation is cheap. Large values, slow commands, big collections, network latency, serialization cost and hot keys can dominate performance. Newer Redis versions can use I/O threads for network handling, but command behavior and data modeling still matter.

#### Production angle

Measure end-to-end client latency, not only Redis server latency. For Java services, serialization, connection pools, GC and network hops can be significant.

#### Traps / caveats

- Redis is fast, not infinite.
- A single slow command can affect other clients.
- Large payloads can make Redis slower than expected.

#### Optional Anki

Q: Why is Redis usually fast for cache reads?
A: Data is stored in memory and common operations are efficient.

</details>

<a id="redis-fund-003"></a>

<details>
<summary><strong>REDIS-FUND-003. What Redis data structures are useful for backend services?</strong></summary>

#### Short answer

Useful Redis structures include strings, hashes, sets, sorted sets, lists, streams, bitmaps and probabilistic structures.

#### Interview answer

Strings are used for simple values, JSON blobs, counters and locks. Hashes store field-value data for one object. Sets represent unique membership. Sorted sets are useful for ranking and time-ordered scores. Lists and streams can support simple queue-like workflows, though Kafka or a real queue is often better for reliable messaging.

#### Deep dive

Redis data modeling should match access patterns. A huge hash or sorted set can become a big-key problem. Many tiny keys can increase metadata overhead. Structures such as HyperLogLog or Bloom filters trade precision for memory efficiency.

#### Production angle

Choose structures based on command complexity, expected cardinality, TTL needs, update pattern and observability. Monitor key size and memory usage by type.

#### Traps / caveats

- Do not store everything as one huge JSON string if partial updates are needed.
- Do not create huge collections without understanding command costs.
- Redis Streams are not a drop-in replacement for Kafka in all cases.

#### Optional Anki

Q: Which Redis structure is useful for leaderboards?
A: Sorted set.

</details>

<a id="redis-fund-004"></a>

<details>
<summary><strong>REDIS-FUND-004. When would you use a Redis string?</strong></summary>

#### Short answer

Use a Redis string for a single value, serialized object, counter, flag, token or simple lock value.

#### Interview answer

Strings are the simplest Redis type. They work well for cached DTOs, JSON values, counters with `INCR`, idempotency markers, feature snapshots and lock tokens with `SET NX PX`.

#### Deep dive

A Redis string can hold text or binary data, but large values increase network transfer, memory pressure and serialization cost. If you need to update individual fields frequently, a hash may be better.

#### Production angle

Use explicit key naming and TTLs. Keep values reasonably small and avoid storing large response bodies without measuring latency and memory impact.

#### Traps / caveats

- A cached JSON string must remain compatible with application code.
- Very large strings can cause latency spikes.
- Counters and locks need atomic command patterns.

#### Optional Anki

Q: What Redis type is commonly used for a cached JSON DTO?
A: String.

</details>

<a id="redis-fund-005"></a>

<details>
<summary><strong>REDIS-FUND-005. When would you use a Redis hash?</strong></summary>

#### Short answer

Use a Redis hash to store multiple fields under one key when field-level access or updates are useful.

#### Interview answer

A hash is useful for object-like data such as user profile fields, counters grouped by entity, or configuration properties. You can update one field without rewriting the whole serialized object.

#### Deep dive

Hashes can reduce key count and support field-level commands, but a very large hash can become a big key. TTL applies to the whole hash key, not individual fields in standard Redis.

#### Production angle

Hashes are useful when the access pattern often reads or updates selected fields. For cache entries where the whole object is always read together, a serialized string may be simpler.

#### Traps / caveats

- Field-level TTL is not the normal Redis hash behavior.
- Huge hashes can block operations and complicate migration.
- Hash field names still consume memory.

#### Optional Anki

Q: What is one advantage of Redis hash over a JSON string?
A: Individual fields can be updated without rewriting the whole value.

</details>

<a id="redis-fund-006"></a>

<details>
<summary><strong>REDIS-FUND-006. When would you use a Redis set?</strong></summary>

#### Short answer

Use a Redis set for unique unordered membership checks and set operations.

#### Interview answer

Sets are useful for "has this item been seen?", user membership, tags, unique IDs, blocked tokens, or computing intersections and differences between groups. Commands like `SISMEMBER`, `SADD` and `SREM` are common.

#### Deep dive

Sets are good when uniqueness matters and ordering does not. If ranking or ordering by score is needed, use a sorted set instead.

#### Production angle

Watch set cardinality. A set with millions of members can become expensive to scan, move or delete, and commands returning all members can create latency and memory spikes.

#### Traps / caveats

- Avoid `SMEMBERS` on very large sets in hot paths.
- TTL applies to the whole set key.
- Sets are not ordered.

#### Optional Anki

Q: Which Redis type is best for unique membership?
A: Set.

</details>

<a id="redis-fund-007"></a>

<details>
<summary><strong>REDIS-FUND-007. When would you use a Redis sorted set?</strong></summary>

#### Short answer

Use a sorted set when each member needs a score for ranking, ordering or range queries.

#### Interview answer

Sorted sets are useful for leaderboards, priority-like views, time-based indexes, recent activity, rate limiter windows and ranking results. Each member is unique and has a numeric score, and Redis can query by rank or score range.

#### Deep dive

Sorted sets are powerful but usually O(log n) for inserts and updates. Range queries can return many elements, so result sizes must be bounded.

#### Production angle

Use sorted sets for bounded rankings and time windows. Clean old entries regularly for sliding-window use cases to prevent unbounded growth.

#### Traps / caveats

- Large range reads can hurt latency.
- Scores are numeric, so timestamp precision and tie handling must be considered.
- One huge sorted set can become a hot key.

#### Optional Anki

Q: What is the Redis type for ranking by score?
A: Sorted set.

</details>

<a id="redis-fund-008"></a>

<details>
<summary><strong>REDIS-FUND-008. Why should Redis usually not be treated as the primary source of truth for critical data?</strong></summary>

#### Short answer

Redis is usually optimized for speed and memory access, not durable relational correctness for critical business records.

#### Interview answer

For critical data, a relational database or another durable store is usually better because it provides stronger durability, transactions, constraints, backup workflows and query capabilities. Redis can persist data, but many Redis deployments are configured as caches where data loss is acceptable.

#### Deep dive

Redis persistence and replication do not automatically give the same guarantees as a transactional database. Failover can lose recent writes depending on configuration, and constraints such as foreign keys or unique business invariants are not Redis strengths.

#### Production angle

Use Redis as a cache or short-lived state store unless the team has deliberately designed Redis as a primary database and accepts its operational model.

#### Traps / caveats

- "Redis has persistence" does not mean "safe for all critical data".
- Memory pressure and eviction policies can delete keys.
- Critical invariants are often better enforced in the database.

#### Optional Anki

Q: Why is Redis usually not the source of truth?
A: It lacks the durability, constraints and transaction model expected for critical business records.

</details>

<a id="redis-fund-009"></a>

<details>
<summary><strong>🧠 REDIS-FUND-009. What are Redis probabilistic data structures such as Bloom filters useful for?</strong></summary>

#### Short answer

They answer approximate questions with low memory usage, accepting a controlled error rate.

#### Interview answer

A Bloom filter can quickly answer "definitely not present" or "maybe present", which helps reduce database hits for nonexistent IDs. HyperLogLog estimates unique counts, such as approximate daily active users, using much less memory than storing every ID.

#### Deep dive

Bloom filters can have false positives but not false negatives when used correctly. HyperLogLog provides approximate cardinality, not exact membership. Some structures are available through Redis modules or Redis Stack rather than minimal core Redis deployments.

#### Production angle

Use probabilistic structures when approximate answers are acceptable and memory savings matter. Document the error tolerance and fallback behavior.

#### Traps / caveats

- A Bloom filter "maybe" result still needs source verification.
- False positives can reduce effectiveness but should not break correctness.
- Check whether the deployment supports the required module.

#### Optional Anki

Q: What does a Bloom filter false positive mean?
A: It says an item may exist even though it does not.

</details>
