# 16.15. Testing Spring Boot applications

---

<a id="sp-test-001"></a>

<details>
<summary><strong>SP-TEST-001. What is the testing pyramid in a Spring Boot application?</strong></summary>

#### Short answer

Use many fast unit tests, fewer focused integration/slice tests and a small number of end-to-end tests.

#### Interview answer

The pyramid means most tests should be cheap and targeted: plain unit tests for business logic, slice tests for MVC or repositories, integration tests for database and external boundaries, and a few full application or end-to-end tests for critical flows.

Spring should be used when Spring behavior matters, not for every test.

#### Deep dive

The goal is fast feedback plus confidence. A suite made mostly of full `@SpringBootTest` tests is often slow and fragile.

#### Production angle

A balanced suite catches wiring, transaction, serialization and persistence bugs without making CI unusable.

#### Traps / caveats

- High coverage with weak assertions is not confidence.
- Too many Spring context tests slow development.
- Too few integration tests miss configuration and database issues.

#### Optional Anki

Q: What should be the most numerous tests in the pyramid?
A: Fast unit tests.

</details>

<a id="sp-test-002"></a>

<details>
<summary><strong>SP-TEST-002. When should you write a plain unit test without Spring?</strong></summary>

#### Short answer

When testing business logic that can be constructed with ordinary Java objects and test doubles.

#### Interview answer

If a service method only needs collaborators that can be passed through constructors, a plain JUnit test is faster and clearer than a Spring test. Use mocks, fakes or in-memory implementations where appropriate.

Do not start the Spring context just to test simple branching, calculations or domain rules.

#### Deep dive

Constructor injection makes plain unit testing easy because dependencies are explicit.

#### Production angle

Fast unit tests encourage developers to test edge cases and run tests frequently.

#### Traps / caveats

- Do not mock so much that the test only verifies implementation details.
- Use Spring tests when proxies, validation, transactions or configuration binding are part of the behavior.
- Static calls and hidden dependencies make unit testing harder.

#### Optional Anki

Q: Best test style for pure business logic?
A: Plain unit test without Spring.

</details>

<a id="sp-test-003"></a>

<details>
<summary><strong>SP-TEST-003. What is @SpringBootTest?</strong></summary>

#### Short answer

`@SpringBootTest` loads a full Spring Boot application context for integration-style tests.

#### Interview answer

`@SpringBootTest` starts a Boot test context with application configuration and auto-configuration. It is useful for verifying wiring, configuration, full integration paths or behavior involving multiple layers.

It is heavier than slice or unit tests, so use it when the full context is valuable.

#### Deep dive

It can start with no web environment, a mock web environment or a real web server on a random/defined port.

#### Production angle

Full-context tests catch missing beans, configuration errors and integration issues before deployment.

#### Traps / caveats

- Overusing it makes CI slow.
- It may connect to real external systems if properties are not overridden.
- Context differences across tests can reduce caching and slow the suite.

#### Optional Anki

Q: What does `@SpringBootTest` usually load?
A: A full Spring Boot application context.

</details>

<a id="sp-test-004"></a>

<details>
<summary><strong>SP-TEST-004. What are Spring Boot test slices?</strong></summary>

#### Short answer

Test slices load only part of the application context for focused layer testing.

#### Interview answer

Spring Boot test slices such as `@WebMvcTest`, `@DataJpaTest` and JSON tests configure only the infrastructure needed for a specific layer. They are faster and more focused than full `@SpringBootTest`.

Slices are useful when you want Spring behavior for one layer without loading the entire application.

#### Deep dive

Slices intentionally exclude many beans. Collaborators often need to be imported or replaced with test doubles.

#### Production angle

Slices catch MVC binding, validation, serialization and repository behavior while keeping tests fast.

#### Traps / caveats

- Missing beans in a slice may be expected.
- Slice behavior is not the same as the full app.
- Too much manual importing can turn a slice into a confusing mini-application.

#### Optional Anki

Q: Why use a test slice?
A: To test one layer with Spring support without loading the full context.

</details>

<a id="sp-test-005"></a>

<details>
<summary><strong>SP-TEST-005. What is @WebMvcTest?</strong></summary>

#### Short answer

`@WebMvcTest` loads Spring MVC infrastructure and selected controllers for focused web-layer tests.

#### Interview answer

`@WebMvcTest` is used with MockMvc or similar tooling to test controller request mapping, validation, serialization, exception handling and security integration. It does not load the full application or real repositories by default.

Service dependencies are usually mocked or imported deliberately.

#### Deep dive

It is excellent for "does this endpoint handle this request and response correctly?" but not for full persistence or service integration.

#### Production angle

It protects API behavior and error contracts without making every controller test a full integration test.

#### Traps / caveats

- Security may be active and must be configured in tests.
- Mocked services can hide integration issues.
- Global controller advice and custom converters must be included if relevant.

#### Optional Anki

Q: Main use of `@WebMvcTest`?
A: Focused Spring MVC/controller testing.

</details>

<a id="sp-test-006"></a>

<details>
<summary><strong>SP-TEST-006. What is @DataJpaTest?</strong></summary>

#### Short answer

`@DataJpaTest` loads JPA-related components for repository and persistence tests.

#### Interview answer

`@DataJpaTest` configures repositories, entity manager and JPA infrastructure. It usually runs tests transactionally and rolls back after each test. By default it may use an embedded database unless configured otherwise.

For production PostgreSQL behavior, pair it with Testcontainers or a real test database.

#### Deep dive

It is useful for query correctness, mappings, constraints and repository behavior.

#### Production angle

Repository tests catch query and mapping bugs that mocks cannot.

#### Traps / caveats

- H2 can hide PostgreSQL-specific behavior.
- Transactional rollback can hide commit-time issues.
- It does not load service-layer business logic by default.

#### Optional Anki

Q: What does `@DataJpaTest` focus on?
A: JPA repositories and persistence mapping.

</details>

<a id="sp-test-007"></a>

<details>
<summary><strong>SP-TEST-007. When should you prefer @WebMvcTest or @DataJpaTest over @SpringBootTest?</strong></summary>

#### Short answer

Prefer slices when the behavior under test belongs to one layer and does not require the full application context.

#### Interview answer

Use `@WebMvcTest` for controller mapping, validation and error response behavior. Use `@DataJpaTest` for repository queries and mappings. Use `@SpringBootTest` when multiple layers, full auto-configuration or real app wiring matters.

The narrower test should be the default if it gives enough confidence.

#### Deep dive

Focused tests fail closer to the cause and run faster.

#### Production angle

Good slice tests keep CI fast while still catching framework integration bugs.

#### Traps / caveats

- Do not force a slice to include half the application.
- Full-context tests are still needed for important wiring paths.
- Mocking too much in a slice can make tests unrealistic.

#### Optional Anki

Q: Main reason to prefer a test slice?
A: Faster, focused Spring integration for one layer.

</details>

<a id="sp-test-008"></a>

<details>
<summary><strong>SP-TEST-008. What are @MockitoBean and @MockitoSpyBean used for, and how do they relate to older @MockBean-style tests?</strong></summary>

#### Short answer

They replace or wrap Spring beans in the test context with Mockito mocks or spies; they are the modern Spring testing annotations for this use case.

#### Interview answer

`@MockitoBean` registers a Mockito mock in the Spring test context, typically replacing an existing bean. `@MockitoSpyBean` wraps a real bean with a spy. Older Spring Boot tests often used `@MockBean` and `@SpyBean`; modern Spring testing has moved toward the framework-level Mockito bean annotations.

They are useful in slice or integration tests when one collaborator should be controlled.

#### Deep dive

If several beans match, use a qualifier or explicit bean name. Replacing beans changes the application context cache key, and even inconsistent mock field names can lead to extra cached contexts.

#### Production angle

Use these annotations to isolate boundaries, not to mock every layer and lose integration confidence.

#### Traps / caveats

- Over-mocking hides wiring and behavior problems.
- Spies can execute real side effects.
- Mocked beans can remove proxies or advice behavior you intended to test.
- Inconsistent mock declarations across test classes can slow the suite by fragmenting context caching.

#### Optional Anki

Q: What does `@MockitoBean` do?
A: Registers/replaces a Spring test context bean with a Mockito mock.

</details>

<a id="sp-test-009"></a>

<details>
<summary><strong>SP-TEST-009. How do transactional tests behave by default?</strong></summary>

#### Short answer

Spring transactional tests usually run each test method in a transaction and roll it back after the test.

#### Interview answer

When a Spring test is transactional, the framework starts a transaction before the test and rolls it back afterward by default. This keeps database state isolated between tests.

It is convenient, but it can hide behavior that occurs only on commit.

#### Deep dive

You can use annotations such as `@Commit`, `@Rollback`, `@BeforeTransaction` and `@AfterTransaction` for special cases.

#### Production angle

Tests for outbox events, constraints or transaction synchronization may need real commit behavior.

#### Traps / caveats

- Commit-time constraint failures may be hidden.
- Code under test may see the same transaction as the test.
- Rollback cleanup differs from production transaction flow.

#### Optional Anki

Q: Default end behavior of many transactional Spring tests?
A: Rollback.

</details>

<details>
<summary><strong>SP-TEST-010. What is @Sql used for?</strong></summary>

#### Short answer

`@Sql` runs SQL scripts before or after tests to set up or clean database state.

#### Interview answer

`@Sql` can create test data, clean tables or verify database setup for integration tests. It can be placed on classes or methods and configured for execution phase and transaction behavior.

It is useful when test data is easier or clearer as SQL.

#### Deep dive

For complex tests, builders or repository setup may be more maintainable than large SQL scripts.

#### Production angle

Reliable test data setup prevents order-dependent and flaky database tests.

#### Traps / caveats

- SQL scripts are database-specific.
- Cleanup must handle constraints and ordering.
- Excessive shared scripts become hard to understand.

#### Optional Anki

Q: What does `@Sql` do in Spring tests?
A: Executes SQL scripts around tests.

</details>

<a id="sp-test-011"></a>

<details>
<summary><strong>SP-TEST-011. What is the difference between @DynamicPropertySource and Spring Boot Testcontainers @ServiceConnection?</strong></summary>

#### Short answer

`@DynamicPropertySource` manually registers dynamic property values; `@ServiceConnection` lets Boot create connection details from supported Testcontainers containers.

#### Interview answer

With `@DynamicPropertySource`, a test adds properties such as JDBC URL, username and password from a running container. `@ServiceConnection` is a Boot Testcontainers integration that can detect supported containers and provide typed connection details to auto-configuration.

`@ServiceConnection` is less boilerplate when supported; dynamic properties are more general.

#### Deep dive

For generic containers, hints such as service name may be needed so Boot knows which connection details to create.

#### Production angle

Both approaches help tests use real infrastructure while keeping ports and credentials dynamic.

#### Traps / caveats

- `@ServiceConnection` requires the relevant Boot testcontainers support.
- Dynamic property methods must be static in typical JUnit usage.
- Container startup cost should be managed across the suite.

#### Optional Anki

Q: More general Testcontainers property integration?
A: `@DynamicPropertySource`.

</details>

<a id="sp-test-012"></a>

<details>
<summary><strong>SP-TEST-012. How do you use Testcontainers with Spring Boot to test against real PostgreSQL?</strong></summary>

#### Short answer

Start a PostgreSQL container for the test and connect Spring Boot to it through service connection support or dynamic properties.

#### Interview answer

In a repository or integration test, define a `PostgreSQLContainer`, start it with JUnit/Testcontainers, and provide its JDBC URL, username and password to Spring Boot. Modern Boot can use `@ServiceConnection`; otherwise use `@DynamicPropertySource`.

Run Flyway/Liquibase migrations and test against realistic PostgreSQL behavior.

#### Deep dive

Container reuse and lifecycle strategy affect speed. A per-class static container is common.

#### Production angle

PostgreSQL Testcontainers catch bugs hidden by H2: SQL dialect, indexes, JSON, locking, constraints and transaction behavior.

#### Traps / caveats

- Docker availability can make CI flaky if not provisioned.
- Migrations must run in tests.
- Tests should clean data deterministically.

#### Optional Anki

Q: Why prefer PostgreSQL Testcontainers over H2 for repository tests?
A: It matches production database behavior better.

</details>

<a id="sp-test-013"></a>

<details>
<summary><strong>SP-TEST-013. How would you test external HTTP integrations?</strong></summary>

#### Short answer

Use a fake HTTP server to verify request shape, response handling, errors, timeouts and retries.

#### Interview answer

For HTTP clients, run WireMock, MockWebServer or a similar fake server. Point the Spring client to the fake server through test properties. Verify headers, body, method, path, status handling, malformed responses, timeouts and retry behavior.

For consumer/provider compatibility, add contract tests where appropriate.

#### Deep dive

Mocking the client interface is fine for service unit tests, but client implementation tests need real HTTP behavior.

#### Production angle

External integration tests prevent outages caused by changed response shapes or missing error handling.

#### Traps / caveats

- Test slow and failing dependencies, not just happy paths.
- Avoid hitting real external services in CI.
- Keep stubs aligned with provider contracts.

#### Optional Anki

Q: What should HTTP client tests verify besides success?
A: Errors, timeouts, retries, headers and serialization.

</details>

<a id="sp-test-014"></a>

<details>
<summary><strong>🧠 SP-TEST-014. What is ApplicationContext caching in Spring tests?</strong></summary>

#### Short answer

Spring caches test application contexts with the same configuration so later tests can reuse them.

#### Interview answer

Starting a Spring context is expensive. The Spring TestContext framework caches contexts keyed by configuration: classes, properties, profiles, mocks and customizers. If another test needs the same context, it reuses it instead of rebuilding.

This is why consistent test configuration matters for performance.

#### Deep dive

Changing profiles, properties or mocked beans can create a new cache key.

#### Production angle

Efficient context caching can dramatically reduce CI time for Spring-heavy test suites.

#### Traps / caveats

- Overusing unique properties or mocks creates many contexts.
- Dirtying contexts prevents reuse.
- Shared cached context state must not leak between tests.

#### Optional Anki

Q: Why does Spring cache test contexts?
A: To avoid expensive repeated application context startup.

</details>

<a id="sp-test-015"></a>

<details>
<summary><strong>🧠 SP-TEST-015. What does @DirtiesContext do, and why should it be used carefully?</strong></summary>

#### Short answer

`@DirtiesContext` marks a test context as changed so Spring closes it and does not reuse it from the cache.

#### Interview answer

Use `@DirtiesContext` when a test mutates the application context or global bean state in a way that would affect later tests. It forces context rebuild, which protects isolation but slows the suite.

It should be rare; prefer cleaning data or avoiding global mutations.

#### Deep dive

It can be applied at method or class level with different timing modes.

#### Production angle

Overuse creates slow CI and hides poor test isolation.

#### Traps / caveats

- Do not use it as a default cleanup mechanism.
- It does not fix database state unless that state is tied to context lifecycle.
- Frequent context rebuilds make test suites painful.

#### Optional Anki

Q: Main cost of `@DirtiesContext`?
A: It prevents context cache reuse and slows tests.

</details>

<a id="sp-test-016"></a>

<details>
<summary><strong>SP-TEST-016. What are common reasons Spring tests become slow or flaky?</strong></summary>

#### Short answer

Too many full contexts, poor context caching, real external dependencies, shared mutable state, timing assumptions and slow containers.

#### Interview answer

Spring tests get slow when every test uses `@SpringBootTest`, each test has unique properties/mocks, contexts are dirtied often, and integration dependencies start repeatedly. Flakiness comes from shared database state, test order dependence, async timing, ports, real network calls and insufficient cleanup.

The fix is targeted test scope and deterministic isolation.

#### Deep dive

Use slices, context reuse, stable test data, fake servers, Testcontainers lifecycle control and Awaitility-style waiting for async code.

#### Production angle

Slow or flaky tests reduce trust in CI and delay deployments.

#### Traps / caveats

- Sleeping in tests is fragile.
- Parallel tests require stronger isolation.
- Real external services should not be required for PR tests.

#### Optional Anki

Q: Common cause of slow Spring tests?
A: Too many unique full application contexts.

</details>

<a id="sp-test-017"></a>

<details>
<summary><strong>SP-TEST-017. How would you structure tests for controller, service and repository layers, including transaction rollback behavior?</strong></summary>

#### Short answer

Use MVC slice tests for controllers, plain unit tests for service logic, and real database tests for repositories; add focused integration tests for transaction behavior.

#### Interview answer

Controllers should be tested for request/response mapping, validation, security and error handling with `@WebMvcTest`. Services should mostly use plain unit tests with fakes/mocks for collaborators. Repositories should use `@DataJpaTest` with a real database when SQL behavior matters.

Transaction rollback behavior needs tests that call through Spring proxies and sometimes commit or check rollback-only behavior explicitly.

#### Deep dive

Do not test transaction annotations on manually constructed service objects. Use the Spring context when proxy behavior is the subject.

#### Production angle

This structure gives fast feedback and catches the main integration risks: API contracts, business rules, persistence behavior and transaction boundaries.

#### Traps / caveats

- Transactional tests that always roll back may hide commit-time failures.
- Mocking repositories in service tests does not validate queries.
- Full-flow tests should cover only critical paths.

#### Optional Anki

Q: How should transaction proxy behavior be tested?
A: Through a Spring-managed bean, not a manually constructed object.

</details>
