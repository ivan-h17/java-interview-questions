# 16.01. Spring fundamentals, IoC and Dependency Injection

---

<a id="sp-core-001"></a>

<details>
<summary><strong>SP-CORE-001. What problems does Spring solve in Java backend applications?</strong></summary>

#### Short answer

Spring provides a container and common infrastructure so backend code can focus on business logic instead of wiring, transactions, web handling, configuration, security and integration boilerplate.

#### Interview answer

Spring solves object wiring, lifecycle management and cross-cutting infrastructure. Instead of each class creating its own dependencies, the Spring container creates beans, injects dependencies and applies infrastructure such as transactions, validation, security, caching and AOP.

In backend services, Spring Boot adds conventions and auto-configuration so a service can start with sensible defaults for MVC, JSON, data access, metrics, configuration and embedded servers.

#### Deep dive

The important idea is not just "less code". Spring centralizes infrastructure decisions at application boundaries: object graph creation, resource management, request handling, database transaction management and integration with external systems.

#### Production angle

Spring makes production behavior more consistent: configuration can be externalized, health checks and metrics can be exposed, transaction boundaries can be declared, and common concerns can be applied uniformly.

#### Traps / caveats

- Spring does not remove design responsibility; a poorly structured service remains poorly structured.
- Auto-configuration can hide behavior if the team does not know what beans are created.
- Spring abstractions still sit on real resources: threads, connections, sockets and transactions.

#### Optional Anki

Q: What is Spring's core value in backend applications?
A: Managed object wiring plus common infrastructure for web, data, transactions, configuration and operations.

</details>

<details>
<summary><strong>SP-CORE-002. What are Inversion of Control and Dependency Injection, and how are they related?</strong></summary>

#### Short answer

IoC means the framework controls object creation and wiring; Dependency Injection is the usual technique Spring uses to provide dependencies to objects.

#### Interview answer

Inversion of Control means application classes do not fully control how collaborators are created and assembled. That responsibility is inverted to a container. Dependency Injection is one implementation of IoC: dependencies are passed into a class, usually through a constructor, setter or field.

In Spring, the container creates beans, resolves their dependencies and injects them. The class asks for abstractions it needs; it does not manually construct the whole object graph.

#### Deep dive

IoC is the broader principle. DI is about dependencies. Other IoC examples include callback methods, lifecycle hooks and framework-invoked controllers.

#### Production angle

DI makes services easier to test, replace, configure and observe. For example, a payment service can depend on a `PaymentGateway` interface while production and test configurations provide different implementations.

#### Traps / caveats

- DI is not the same as Service Locator; with DI, dependencies are explicit.
- Too many injected dependencies often indicate a class with too many responsibilities.
- Injecting concrete infrastructure everywhere makes testing and replacement harder.

#### Optional Anki

Q: How are IoC and DI related?
A: DI is a common way to implement IoC by letting the container provide dependencies.

</details>

<details>
<summary><strong>SP-CORE-003. What is ApplicationContext, and how is it different from BeanFactory?</strong></summary>

#### Short answer

`ApplicationContext` is the main Spring container used by applications; it extends basic bean factory behavior with application services such as events, resources, environment, messages and integration features.

#### Interview answer

`BeanFactory` is the lower-level interface for creating and retrieving beans. `ApplicationContext` builds on that and is what most Spring applications use. It adds environment access, resource loading, internationalization, event publishing, application startup integration and convenient support for annotation-based configuration.

In a Spring Boot application, the context is created by `SpringApplication.run()` and holds the managed beans and infrastructure.

#### Deep dive

Historically, `BeanFactory` was the minimal container and `ApplicationContext` was the richer application container. In modern Spring backend work, you usually interact with `ApplicationContext` only for framework integration or diagnostics, not for routine dependency lookup.

#### Production angle

Knowing the context matters when debugging missing beans, profiles, conditional beans, event listeners and startup failures.

#### Traps / caveats

- Calling `applicationContext.getBean()` from business code is usually a smell.
- Multiple application contexts can exist in some applications or tests.
- A bean existing in the context does not mean it is the correct bean for an injection point.

#### Optional Anki

Q: Which container is normally used in Spring Boot applications?
A: `ApplicationContext`.

</details>

<a id="sp-core-004"></a>

<details>
<summary><strong>SP-CORE-004. What is the difference between constructor, setter and field injection?</strong></summary>

#### Short answer

Constructor injection passes dependencies through the constructor, setter injection uses methods after construction, and field injection writes directly into fields by reflection.

#### Interview answer

Constructor injection makes required dependencies explicit and supports immutable fields. Setter injection is useful for optional or reconfigurable dependencies. Field injection is concise but hides dependencies, makes plain unit tests harder and prevents `final` dependencies.

For service classes, constructor injection is usually the best default because the object cannot be created without the dependencies it needs.

#### Deep dive

Constructor injection also exposes circular dependencies early. Setter and field injection can sometimes let cycles appear later or be resolved through proxies, which may hide a design problem.

#### Production angle

Explicit dependencies make code review easier. A service with ten constructor parameters signals too many responsibilities faster than field injection spread across the class.

#### Traps / caveats

- Setter injection is not bad when the dependency is truly optional.
- Field injection works technically but is weaker for maintainability.
- Constructor injection can expose circular dependencies that were already a design issue.

#### Optional Anki

Q: Which injection style is the usual default for required dependencies?
A: Constructor injection.

</details>

<a id="sp-core-005"></a>

<details>
<summary><strong>SP-CORE-005. Which injection style is usually recommended in Spring and why?</strong></summary>

#### Short answer

Constructor injection is usually recommended because it makes dependencies explicit, supports immutability and improves testability.

#### Interview answer

I prefer constructor injection for required dependencies. It lets dependencies be `final`, makes invalid object construction impossible, and allows the class to be tested without a Spring context. The constructor signature also documents what the class needs.

Setter injection is reasonable for optional dependencies or framework extension points. Field injection is usually discouraged because dependencies are hidden and harder to supply in plain tests.

#### Deep dive

Spring can infer constructor injection when a class has a single constructor, so `@Autowired` is often unnecessary on that constructor.

#### Production angle

Constructor injection helps catch wiring errors at startup and makes refactoring safer because dependency changes are visible in the public construction contract.

#### Traps / caveats

- A large constructor is not a reason to use field injection; it is a design signal.
- Optional dependencies should be modeled clearly, for example with `ObjectProvider`, `Optional` or separate configuration.
- Framework-created objects may require special construction rules.

#### Optional Anki

Q: Why is constructor injection preferred?
A: It makes required dependencies explicit, immutable and easy to test.

</details>

<a id="sp-core-006"></a>

<details>
<summary><strong>SP-CORE-006. How does Dependency Injection improve testability and support the Dependency Inversion Principle?</strong></summary>

#### Short answer

DI lets classes depend on abstractions supplied from the outside, so tests can provide fakes or mocks without changing production code.

#### Interview answer

Dependency Inversion says high-level business code should not depend directly on low-level implementation details. With DI, a service can depend on interfaces or stable ports, while Spring supplies concrete adapters such as repositories, clients or gateways.

In tests, the same class can be constructed with a fake repository or mock HTTP client. That avoids booting the full Spring context for ordinary business logic tests.

#### Deep dive

DI does not require every dependency to be an interface. The key is that the class does not construct its collaborators and can be supplied with alternatives when needed.

#### Production angle

This makes migrations and incident work easier: an implementation can be swapped, decorated, proxied or configured without rewriting the service logic.

#### Traps / caveats

- Over-mocking can hide integration errors.
- Interfaces with only one implementation are useful when they represent a boundary, not just because "Spring needs interfaces".
- Static factories and direct `new` calls inside services reduce substitutability.

#### Optional Anki

Q: How does DI support testing?
A: It lets tests provide replacement dependencies directly.

</details>

<a id="sp-core-007"></a>

<details>
<summary><strong>SP-CORE-007. What are the Environment and Resource abstractions in Spring?</strong></summary>

#### Short answer

`Environment` exposes profiles and properties; `Resource` abstracts access to files, classpath resources, URLs and other resource locations.

#### Interview answer

`Environment` is Spring's abstraction for property values and active profiles. It is used by configuration binding, conditional beans and property resolution. `Resource` is Spring's abstraction for loading external or classpath content through a consistent API, such as `classpath:config.yml`, `file:/tmp/data.txt` or an HTTP URL.

Both abstractions keep code from depending directly on a single runtime location or configuration source.

#### Deep dive

In Spring Boot, `Environment` is assembled from many property sources: config files, environment variables, command line arguments, test properties and more.

#### Production angle

These abstractions matter when moving the same app between local dev, CI, containers and Kubernetes, where files and configuration often come from different places.

#### Traps / caveats

- Property source precedence can surprise you.
- Classpath resources are not normal writable files inside a packaged jar.
- Do not load secrets as generic resources and accidentally log their content.

#### Optional Anki

Q: What does Spring `Environment` mainly provide?
A: Profiles and property resolution.

</details>

<a id="sp-core-008"></a>

<details>
<summary><strong>SP-CORE-008. What is a circular dependency in Spring, and why are constructor-based cycles problematic?</strong></summary>

#### Short answer

A circular dependency means two or more beans require each other. Constructor cycles are problematic because neither bean can be fully created first.

#### Interview answer

If `A` needs `B` in its constructor and `B` needs `A` in its constructor, Spring cannot instantiate either one without already having the other. That usually indicates the design has mixed responsibilities or bidirectional service knowledge.

Setter or field cycles can sometimes be resolved through early references, but that does not make them healthy. Modern Spring Boot also tends to discourage circular dependencies by default.

#### Deep dive

Cycles are especially dangerous when proxies are involved, because the object seen during early construction may not be the final proxied bean with transactions or security applied.

#### Production angle

Circular dependencies make startup fragile and refactoring risky. They often correlate with service methods calling back and forth across unclear domain boundaries.

#### Traps / caveats

- `@Lazy` can break the startup cycle but may hide a design issue.
- Event publication or a third service is often cleaner than bidirectional calls.
- Constructor cycles should be treated as a design smell, not just a wiring error.

#### Optional Anki

Q: Why do constructor circular dependencies fail?
A: Each bean needs the other before either can be constructed.

</details>

<a id="sp-core-009"></a>

<details>
<summary><strong>SP-CORE-009. How would you refactor a circular dependency between services?</strong></summary>

#### Short answer

Break the bidirectional relationship by extracting a responsibility, moving shared logic, introducing a domain service, using events, or changing one dependency into a narrower abstraction.

#### Interview answer

I first ask why the services need each other. If they share logic, extract that logic into a separate component. If one service is doing orchestration, move orchestration to a higher-level use-case service. If the relationship is notification-like, publish an event instead of calling back directly.

The goal is not just to make Spring start. The goal is to make dependencies point in one direction and match business boundaries.

#### Deep dive

Sometimes a circular dependency appears because repositories, domain services and application services are mixed. Clarifying layers often removes the cycle naturally.

#### Production angle

Breaking cycles makes the service graph easier to reason about and reduces surprises with transactions, caching and security proxies.

#### Traps / caveats

- Injecting `ApplicationContext` and manually looking up the other bean usually makes the design worse.
- `@Lazy` is a tactical workaround, not a refactoring.
- Events should not be used to hide synchronous business coupling.

#### Optional Anki

Q: Good first question when refactoring a circular service dependency?
A: Which responsibility is in the wrong place?

</details>

<a id="sp-core-010"></a>

<details>
<summary><strong>SP-CORE-010. When is using @Lazy acceptable, and when is it hiding a design problem?</strong></summary>

#### Short answer

`@Lazy` is acceptable for expensive or rarely used beans; it is suspicious when used to work around unclear dependencies or circular service design.

#### Interview answer

`@Lazy` delays bean creation or dependency resolution until first use. It can be useful for expensive optional integrations, startup-time optimization, or breaking initialization order for infrastructure.

If it is used because two business services depend on each other, I treat it as a smell. The app may start, but the dependency graph is still hard to reason about and failures may move from startup to runtime.

#### Deep dive

Lazy dependencies are often injected as proxies. The target bean may fail only when the method is first called, which changes failure timing.

#### Production angle

Lazy initialization can improve startup time but may create first-request latency or runtime failures after deployment.

#### Traps / caveats

- Lazy startup can hide missing configuration until traffic arrives.
- It can make readiness checks pass before all important paths are initialized.
- It should not replace clear service boundaries.

#### Optional Anki

Q: Main risk of using `@Lazy` to fix circular dependencies?
A: It hides a design problem and moves failure to runtime.

</details>
