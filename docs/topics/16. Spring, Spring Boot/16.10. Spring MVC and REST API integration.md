# 16.10. Spring MVC and REST API integration

---

<a id="sp-web-001"></a>

<details>
<summary><strong>SP-WEB-001. How does Spring MVC process an HTTP request?</strong></summary>

#### Short answer

Spring MVC routes a request through `DispatcherServlet`, handler mappings, controller invocation, message conversion and response handling.

#### Interview answer

An HTTP request enters the servlet container and reaches `DispatcherServlet`. It asks handler mappings to find a matching controller method, invokes it through a handler adapter, binds arguments, validates input if configured, calls the method, handles the return value, converts the body through message converters and writes the response.

Filters and interceptors can run before and after parts of this flow.

#### Deep dive

Spring MVC separates concerns through extension points: mappings, argument resolvers, return value handlers, converters, validators and exception resolvers.

#### Production angle

Understanding the flow helps debug 404, 415, 406, validation failures, missing JSON conversion and controller methods not being called.

#### Traps / caveats

- Servlet filters run before Spring MVC handler mapping.
- Interceptors run only after a handler is mapped.
- Message conversion depends on content type, accept headers and configured converters.

#### Optional Anki

Q: Central servlet in Spring MVC request processing?
A: `DispatcherServlet`.

</details>

<a id="sp-web-002"></a>

<details>
<summary><strong>SP-WEB-002. What is DispatcherServlet?</strong></summary>

#### Short answer

`DispatcherServlet` is Spring MVC's front controller that coordinates request handling.

#### Interview answer

`DispatcherServlet` receives web requests and delegates to Spring MVC infrastructure. It finds handlers, invokes controllers, resolves exceptions, handles views or response bodies and coordinates message conversion.

In Spring Boot, it is auto-configured for servlet web applications.

#### Deep dive

It does not contain business logic. It is the central dispatcher that connects MVC extension points.

#### Production angle

If a request never reaches a controller, checking servlet registration, filters, security and handler mappings helps narrow where it stopped.

#### Traps / caveats

- Security filters may reject a request before MVC handles it.
- Static resources can be handled differently from controller mappings.
- WebFlux uses a different dispatcher model.

#### Optional Anki

Q: What pattern does `DispatcherServlet` implement?
A: Front controller.

</details>

<a id="sp-web-003"></a>

<details>
<summary><strong>SP-WEB-003. What is the difference between @Controller and @RestController?</strong></summary>

#### Short answer

`@Controller` is a web controller stereotype; `@RestController` adds `@ResponseBody` semantics to methods by default.

#### Interview answer

`@Controller` can return views or response bodies depending on method annotations. `@RestController` is a convenience annotation combining `@Controller` and `@ResponseBody`, so return values are written to the HTTP response body, usually as JSON.

For REST APIs, `@RestController` is the normal choice.

#### Deep dive

Returning a string from `@Controller` may be interpreted as a view name; returning a string from `@RestController` writes that string as the response body.

#### Production angle

Wrong controller annotation can produce confusing 404s or view resolution errors instead of JSON.

#### Traps / caveats

- `@RestController` does not design a REST API by itself.
- It still needs proper DTOs, validation, error handling and status codes.
- Returning entities directly is usually risky.

#### Optional Anki

Q: What does `@RestController` add to `@Controller`?
A: `@ResponseBody` behavior by default.

</details>

<details>
<summary><strong>SP-WEB-004. What are @RequestMapping, @GetMapping, @PostMapping, @PutMapping, @PatchMapping and @DeleteMapping used for?</strong></summary>

#### Short answer

They map HTTP requests to controller methods by path, method, headers, parameters or media types.

#### Interview answer

`@RequestMapping` is the general mapping annotation. `@GetMapping`, `@PostMapping`, `@PutMapping`, `@PatchMapping` and `@DeleteMapping` are composed shortcuts for common HTTP methods.

They should reflect HTTP semantics: reads with GET, creation or commands often with POST, full replacement with PUT, partial update with PATCH and deletion with DELETE.

#### Deep dive

Mappings can also constrain `consumes` and `produces`, which affects 415 and 406 errors.

#### Production angle

Correct mappings improve API clarity, client compatibility, caching and retry behavior.

#### Traps / caveats

- HTTP method semantics matter beyond annotation names.
- Overlapping mappings can create ambiguous handler errors.
- `consumes` and `produces` must match clients and converters.

#### Optional Anki

Q: Which annotation is the general Spring MVC mapping annotation?
A: `@RequestMapping`.

</details>

<a id="sp-web-005"></a>

<details>
<summary><strong>SP-WEB-005. What is the difference between @PathVariable and @RequestParam?</strong></summary>

#### Short answer

`@PathVariable` binds values from the URI path; `@RequestParam` binds query parameters or form parameters.

#### Interview answer

Use `@PathVariable` for identifiers that are part of the resource path, such as `/orders/{id}`. Use `@RequestParam` for optional modifiers such as filtering, pagination, sorting or search query values.

Both can be converted to typed Java values by Spring conversion services.

#### Deep dive

Path variables are often required by route matching. Request parameters can have defaults or be optional.

#### Production angle

Clear separation improves API design and documentation.

#### Traps / caveats

- Do not put sensitive data in URLs because they appear in logs and browser history.
- Validate and authorize identifiers from either source.
- Query parameter arrays/lists need clear API conventions.

#### Optional Anki

Q: Where does `@PathVariable` read from?
A: The URI path.

</details>

<a id="sp-web-006"></a>

<details>
<summary><strong>SP-WEB-006. What do @RequestBody and @ResponseBody do?</strong></summary>

#### Short answer

`@RequestBody` reads the HTTP body into an object; `@ResponseBody` writes a return value to the HTTP response body.

#### Interview answer

`@RequestBody` uses `HttpMessageConverter`s to deserialize the request body, commonly JSON into a DTO. `@ResponseBody` serializes a return value into the response body. `@RestController` applies response-body behavior by default.

Validation can be triggered by adding `@Valid` or `@Validated` to the request body parameter.

#### Deep dive

Message conversion depends on content type, accept headers, available converters and target Java types.

#### Production angle

Bad body mapping causes 400, 415 or deserialization failures. Response serialization can leak fields if DTOs are not designed carefully.

#### Traps / caveats

- A request body can usually be read only once unless wrapped/cached.
- Unknown JSON fields and null handling should be deliberate.
- Do not bind request bodies directly to JPA entities.

#### Optional Anki

Q: What component converts JSON bodies in Spring MVC?
A: An `HttpMessageConverter`, commonly Jackson-backed.

</details>

<a id="sp-web-007"></a>

<details>
<summary><strong>SP-WEB-007. What are HttpMessageConverters?</strong></summary>

#### Short answer

`HttpMessageConverter`s convert HTTP request and response bodies to and from Java objects.

#### Interview answer

Spring MVC uses message converters for `@RequestBody`, `@ResponseBody`, `ResponseEntity` and similar body handling. JSON is commonly handled by Jackson, strings by string converters and binary data by byte/resource converters.

Converters are selected based on Java type and media type.

#### Deep dive

The `Content-Type` request header affects reading. The `Accept` header and controller `produces` setting affect writing.

#### Production angle

Converter configuration affects API compatibility, date formats, enum handling and error cases like 415 or 406.

#### Traps / caveats

- Missing or wrong `Content-Type` can cause 415.
- Unsupported `Accept` values can cause 406.
- Custom converters can change behavior globally.

#### Optional Anki

Q: Which headers commonly influence message converter selection?
A: `Content-Type` and `Accept`.

</details>

<a id="sp-web-008"></a>

<details>
<summary><strong>SP-WEB-008. How does Spring use Jackson for JSON serialization and deserialization?</strong></summary>

#### Short answer

Spring Boot auto-configures Jackson and uses it through message converters to read and write JSON.

#### Interview answer

When Jackson is on the classpath, Boot configures an `ObjectMapper` and JSON message converters. For request bodies, Jackson deserializes JSON into DTOs. For responses, it serializes Java objects into JSON.

Jackson behavior can be customized through properties, modules, annotations or `ObjectMapper` customizers.

#### Deep dive

Important choices include date/time format, unknown fields, enum representation, null inclusion and bidirectional reference handling.

#### Production angle

JSON configuration is part of the public API contract. Changes can break clients or expose sensitive fields.

#### Traps / caveats

- JPA entities can cause lazy loading or recursive serialization.
- Unknown field handling should match API compatibility policy.
- Global `ObjectMapper` changes can affect all endpoints.

#### Optional Anki

Q: What Boot bean commonly controls JSON mapping?
A: Jackson `ObjectMapper`.

</details>

<details>
<summary><strong>SP-WEB-009. How do @Valid and @Validated integrate with Spring MVC request handling?</strong></summary>

#### Short answer

They trigger Bean Validation on controller method arguments such as request DTOs.

#### Interview answer

When a controller parameter is annotated with `@Valid` or `@Validated`, Spring validates it after binding/deserialization. If validation fails, Spring raises an exception that can be handled globally to return a structured 400 response.

`@Validated` is a Spring annotation that also supports validation groups.

#### Deep dive

Validation checks syntax and basic constraints. Business invariants often still belong in the service/domain layer.

#### Production angle

Consistent validation prevents invalid data from reaching business logic and gives clients predictable errors.

#### Traps / caveats

- Validation does not replace authorization.
- Nested objects may need `@Valid` on fields.
- Database constraints are still needed for integrity.

#### Optional Anki

Q: Which annotation supports validation groups in Spring?
A: `@Validated`.

</details>

<details>
<summary><strong>SP-WEB-010. What are validation groups, and when would you implement a custom Bean Validation constraint?</strong></summary>

#### Short answer

Validation groups select different constraint sets; custom constraints implement reusable validation rules not covered by built-in annotations.

#### Interview answer

Groups let the same DTO or model apply different rules in different contexts, such as create versus update. Custom constraints are useful for reusable checks such as valid country codes, business identifiers or cross-field constraints.

For complex business decisions, prefer service/domain validation rather than hiding too much logic in annotations.

#### Deep dive

Cross-field validation usually targets a class-level constraint, not a single field.

#### Production angle

Reusable constraints keep API validation consistent, but complicated validators need tests and clear error messages.

#### Traps / caveats

- Groups can make validation flow hard to follow.
- Validators should not perform slow remote calls.
- Custom messages should be safe for clients.

#### Optional Anki

Q: What problem do validation groups solve?
A: Different validation rules for different use cases.

</details>

<details>
<summary><strong>SP-WEB-011. How do you implement global exception handling with @ControllerAdvice?</strong></summary>

#### Short answer

Use `@ControllerAdvice` with `@ExceptionHandler` methods to map exceptions to consistent HTTP responses.

#### Interview answer

`@ControllerAdvice` applies exception handling across controllers. Methods annotated with `@ExceptionHandler` can convert validation errors, domain exceptions and unexpected exceptions into structured responses with the correct status code.

This keeps controllers clean and makes API error format consistent.

#### Deep dive

Spring also has `ResponseEntityExceptionHandler` and newer error response support that can be extended.

#### Production angle

Global error handling prevents stack traces and internal exception details from leaking to clients.

#### Traps / caveats

- Do not catch every exception and return 200.
- Log unexpected errors server-side with correlation IDs.
- Preserve meaningful status codes such as 400, 401, 403, 404 and 409.

#### Optional Anki

Q: Annotation for global Spring MVC exception handling?
A: `@ControllerAdvice`.

</details>

<details>
<summary><strong>SP-WEB-012. What is ProblemDetail, and how does it help with error responses?</strong></summary>

#### Short answer

`ProblemDetail` is Spring's representation of standard problem-details error responses for HTTP APIs.

#### Interview answer

`ProblemDetail` models structured error responses with fields such as type, title, status, detail and instance. It helps APIs return consistent machine-readable errors instead of ad hoc strings.

Spring MVC can use it in exception handling and error response support.

#### Deep dive

Applications often add safe custom properties such as application error codes, field errors or correlation IDs.

#### Production angle

Consistent error format improves client handling, observability and support workflows.

#### Traps / caveats

- Do not expose internal exception class names or stack traces.
- Keep error codes stable for clients.
- Validation field errors need a clear extension structure.

#### Optional Anki

Q: What does `ProblemDetail` help standardize?
A: HTTP API error response bodies.

<a id="sp-web-013"></a>

<details>
<summary><strong>SP-WEB-013. What is the difference between a Servlet Filter, a Spring HandlerInterceptor and ControllerAdvice?</strong></summary>

#### Short answer

Filters run at the servlet layer, interceptors run around mapped Spring MVC handlers, and controller advice handles controller-level exceptions and binding concerns.

#### Interview answer

A `Filter` sees requests before they enter Spring MVC and is used for security, logging, CORS or request wrapping. A `HandlerInterceptor` runs after a handler is selected and can inspect handler metadata. `@ControllerAdvice` handles exceptions, binding and model advice across controllers.

They operate at different layers of the request pipeline.

#### Deep dive

Spring Security is filter-based because security must run before controllers and often before MVC mapping.

#### Production angle

Choosing the wrong hook can mean code does not run for rejected requests, static resources or unmapped paths.

#### Traps / caveats

- Interceptors do not run if no handler is mapped.
- Filters must be ordered carefully.
- Controller advice is not a general request middleware mechanism.

#### Optional Anki

Q: Which runs before Spring MVC handler mapping?
A: Servlet filters.

</details>

<details>
<summary><strong>SP-WEB-014. What is WebMvcConfigurer used for?</strong></summary>

#### Short answer

`WebMvcConfigurer` customizes Spring MVC configuration without replacing Boot's MVC auto-configuration.

#### Interview answer

You can implement `WebMvcConfigurer` to add interceptors, CORS mappings, formatters, argument resolvers, message converters, resource handlers and other MVC settings.

It is safer than using `@EnableWebMvc` in Boot apps because it preserves Boot's default MVC configuration.

#### Deep dive

`@EnableWebMvc` gives more control but disables many Boot MVC defaults, so it should be rare in Boot applications.

#### Production angle

MVC customization affects all endpoints, so changes should be tested for serialization, validation, content negotiation and security interactions.

#### Traps / caveats

- Adding converters incorrectly can replace defaults.
- Interceptor order matters.
- Global formatters can break existing API contracts.

#### Optional Anki

Q: Preferred Boot-friendly MVC customization interface?
A: `WebMvcConfigurer`.

</details>

<a id="sp-web-015"></a>

<details>
<summary><strong>SP-WEB-015. How do you configure CORS in Spring MVC?</strong></summary>

#### Short answer

Configure allowed origins, methods, headers and credentials using MVC CORS configuration, controller annotations or Spring Security CORS integration.

#### Interview answer

CORS can be configured globally through `WebMvcConfigurer#addCorsMappings`, locally with `@CrossOrigin`, or in Spring Security so preflight requests are handled correctly. For secured APIs, security integration is usually important because CORS preflight should not be blocked by authentication.

Configuration should be specific, not wildcarded blindly.

#### Deep dive

CORS is a browser protection mechanism. It is not authentication or authorization.

#### Production angle

Bad CORS configuration can break browser clients or expose APIs to unintended browser origins.

#### Traps / caveats

- `Access-Control-Allow-Credentials` cannot be safely combined with arbitrary origins.
- Server-to-server calls are not protected by CORS.
- CORS and CSRF solve different problems.

#### Optional Anki

Q: Is CORS an authentication mechanism?
A: No.

</details>

<a id="sp-web-016"></a>

<details>
<summary><strong>SP-WEB-016. How should you design DTOs for Spring MVC APIs, and why is returning JPA entities usually a bad idea?</strong></summary>

#### Short answer

Use DTOs that represent the API contract; avoid returning JPA entities because they expose persistence internals and can trigger lazy loading or recursive JSON.

#### Interview answer

Request and response DTOs should model what the API accepts and returns, not the database schema. They allow validation, versioning, field naming, null handling and backward compatibility.

Returning entities directly couples clients to persistence, can leak fields, trigger lazy queries during serialization and create bidirectional reference problems.

#### Deep dive

Mapping can be manual or tool-assisted, but business decisions should stay explicit.

#### Production angle

DTOs protect API compatibility when the domain model or database schema changes.

#### Traps / caveats

- Do not use one DTO for every operation if create/update/response semantics differ.
- Avoid exposing internal IDs when public IDs are required.
- Entity serialization can cause N+1 queries.

#### Optional Anki

Q: Why avoid returning JPA entities from controllers?
A: It leaks persistence model and can trigger lazy loading or huge/recursive JSON.

</details>

<a id="sp-web-017"></a>

<details>
<summary><strong>SP-WEB-017. How do you avoid leaking internal exception details in REST responses?</strong></summary>

#### Short answer

Map exceptions to safe error responses, log details server-side and expose only stable client-facing codes and messages.

#### Interview answer

Use global exception handling to convert known exceptions into safe responses and unexpected exceptions into generic 5xx errors. Include a correlation ID or error code, but not stack traces, SQL, class names, credentials or internal service details.

The server logs should contain enough detail for diagnosis.

#### Deep dive

Validation errors can expose field names and messages, but those messages should still be safe and stable.

#### Production angle

Leaked internals help attackers and can expose PII, secrets or infrastructure details.

#### Traps / caveats

- Default error responses may expose more than desired if configured poorly.
- Logging full request bodies can leak sensitive fields.
- Different environments should not accidentally enable debug errors in production.

#### Optional Anki

Q: What should a client get for an unexpected internal error?
A: A generic safe error with status and correlation/error code, not a stack trace.

</details>

<a id="sp-web-018"></a>

<details>
<summary><strong>SP-WEB-018. How would you debug a request that never reaches the controller or fails with HTTP 415/406?</strong></summary>

#### Short answer

Check routing, filters/security, handler mappings, HTTP method/path, content type, accept header and message converters.

#### Interview answer

If the request never reaches the controller, I check the URL, HTTP method, context path, security filters, CORS preflight, servlet/filter logs and Actuator mappings. For 415, I check `Content-Type`, `consumes` and request body converters. For 406, I check `Accept`, `produces` and response converters.

I would reproduce with curl and enable targeted debug logs.

#### Deep dive

415 means the request media type cannot be consumed. 406 means the server cannot produce a response acceptable to the client.

#### Production angle

These errors often appear after client changes, API versioning changes or message converter customization.

#### Traps / caveats

- Browser preflight requests use `OPTIONS`.
- Security may block before MVC mapping.
- Missing `Content-Type: application/json` is a common 415 cause.

#### Optional Anki

Q: What does HTTP 415 usually indicate in Spring MVC?
A: Unsupported request `Content-Type` or missing converter.

</details>

<details>
<summary><strong>🧠 SP-WEB-019. How do argument resolvers and return value handlers work in Spring MVC?</strong></summary>

#### Short answer

Argument resolvers create controller method arguments; return value handlers process controller return values.

#### Interview answer

Spring MVC does not hard-code every parameter type. It uses `HandlerMethodArgumentResolver`s to resolve arguments such as `@RequestBody`, `@PathVariable`, `Principal`, pageable objects or custom context objects. `HandlerMethodReturnValueHandler`s process return values such as `ResponseEntity`, views, response bodies and async types.

Custom resolvers are useful for cross-cutting request context.

#### Deep dive

Resolvers and handlers are ordered. The first compatible one usually handles the parameter or return value.

#### Production angle

Custom argument resolvers can reduce controller boilerplate but can hide dependencies and security assumptions.

#### Traps / caveats

- Do not hide authorization checks in unclear resolver logic.
- Resolver order can conflict with framework defaults.
- Custom return handlers affect API behavior globally.

#### Optional Anki

Q: What does a `HandlerMethodArgumentResolver` do?
A: It supplies values for controller method parameters.

</details>
