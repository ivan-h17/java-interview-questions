# 16.06. Spring transaction management

---

<a id="sp-tx-001"></a>

<details>
<summary><strong>SP-TX-001. What does @Transactional do?</strong></summary>

#### Short answer

`@Transactional` declares that a method or class should run with Spring-managed transaction semantics.

#### Interview answer

`@Transactional` tells Spring to start or join a transaction around a method call, then commit on success or roll back on configured failures. It can define propagation, isolation, timeout, read-only hints and rollback rules.

In typical Spring services, it marks application-level transaction boundaries around a business use case.

#### Deep dive

The annotation itself does not open a transaction. Spring transaction infrastructure reads it and applies transaction advice through a proxy or AspectJ mode.

#### Production angle

Correct transaction boundaries protect data consistency and control how long database connections and locks are held.

#### Traps / caveats

- It applies only when the call goes through transaction infrastructure.
- By default, checked exceptions do not trigger rollback.
- It does not make remote service calls part of the database transaction.

#### Optional Anki

Q: What does `@Transactional` usually define?
A: A Spring-managed transaction boundary.

</details>

<a id="sp-tx-002"></a>

<details>
<summary><strong>SP-TX-002. How does @Transactional work under the hood in Spring?</strong></summary>

#### Short answer

Spring uses transaction metadata, a transaction manager and transaction advice, usually through an AOP proxy.

#### Interview answer

When a proxied transactional method is called, Spring's transaction interceptor reads the transaction attributes, asks a `PlatformTransactionManager` to start or join a transaction, invokes the method, then commits or rolls back based on the outcome.

Resources such as JDBC connections are bound to the current thread for the transaction duration.

#### Deep dive

The actual transaction implementation depends on the transaction manager: JDBC, JPA, JTA or reactive transaction management have different resource handling.

#### Production angle

Understanding the proxy and thread-bound resource model explains many failures involving self-invocation, async code and connection pool exhaustion.

#### Traps / caveats

- Transaction context usually does not cross threads automatically.
- Internal method calls bypass proxy advice.
- The database still enforces the real isolation and locking behavior.

#### Optional Anki

Q: Which Spring contract starts/commits/rolls back transactions?
A: `PlatformTransactionManager`.

</details>

<a id="sp-tx-003"></a>

<details>
<summary><strong>SP-TX-003. Why can @Transactional fail on self-invocation, private methods, final methods or calls from constructors?</strong></summary>

#### Short answer

In proxy mode, transaction advice applies only to interceptable calls through the Spring proxy.

#### Interview answer

Self-invocation uses `this.method()`, so it calls the target directly and bypasses the proxy. Private methods cannot be called through the proxy. Final methods cannot be overridden by class-based proxies. Constructor calls happen before the fully proxied bean is available.

So the annotation may exist, but no transaction advice runs.

#### Deep dive

Public method visibility and proxy type matter. Interface-based proxies expose interface methods; class-based proxies subclass the target and intercept overridable methods.

#### Production angle

This causes real bugs: expected rollback does not happen, lazy loading fails, or writes run outside the intended transaction.

#### Traps / caveats

- Moving the annotation to an internally called method may not help.
- `@PostConstruct` calls can have similar timing issues.
- Tests should call through Spring-managed beans when verifying transaction behavior.

#### Optional Anki

Q: Why does `this.transactionalMethod()` not start a transaction?
A: It bypasses the Spring proxy.

</details>

<a id="sp-tx-004"></a>

<details>
<summary><strong>SP-TX-004. How can you solve the @Transactional self-invocation problem?</strong></summary>

#### Short answer

Move the transactional method to another bean, call through a proxy, use `TransactionTemplate`, or in rare cases use AspectJ mode.

#### Interview answer

The cleanest fix is often to split responsibilities so one Spring bean calls another bean's transactional method. Then the call goes through the proxy. If the boundary is small or dynamic, `TransactionTemplate` can make the transaction explicit. Self-injecting a proxy is possible but usually less clean.

AspectJ mode can intercept self-invocation, but it adds complexity.

#### Deep dive

A self-invocation issue often indicates that the class is mixing orchestration and transactional sub-operations.

#### Production angle

The fix should make the transaction boundary obvious to reviewers, not just make the annotation "work".

#### Traps / caveats

- Self-injection can create circular dependencies or confusing code.
- `AopContext.currentProxy()` couples business code to AOP configuration.
- Moving code between beans can change visibility and transaction propagation behavior.

#### Optional Anki

Q: Cleanest common fix for transactional self-invocation?
A: Move the transactional operation to another Spring bean and call that bean.

</details>

<a id="sp-tx-005"></a>

<details>
<summary><strong>SP-TX-005. What is PlatformTransactionManager, and how does Spring choose a transaction manager?</strong></summary>

#### Short answer

`PlatformTransactionManager` is Spring's imperative transaction manager abstraction. Spring chooses a matching bean, often auto-configured by Boot.

#### Interview answer

`PlatformTransactionManager` defines operations to get, commit and roll back transactions. Implementations include `DataSourceTransactionManager` for JDBC and `JpaTransactionManager` for JPA.

If there is one transaction manager bean, Spring uses it. With multiple managers, you usually mark one `@Primary` or specify the manager by name in `@Transactional`.

#### Deep dive

Spring Boot auto-configures a transaction manager based on the available data access technology and beans. Multiple data sources or mixed persistence technologies require explicit configuration.

#### Production angle

Using the wrong transaction manager can mean the resource you care about is not actually participating in the transaction.

#### Traps / caveats

- `@Transactional("name")` selects a specific manager.
- Multiple databases are not automatically one atomic transaction.
- Reactive transactions use different infrastructure.

#### Optional Anki

Q: Spring abstraction for imperative transaction control?
A: `PlatformTransactionManager`.

</details>

<a id="sp-tx-006"></a>

<details>
<summary><strong>SP-TX-006. What is the difference between DataSourceTransactionManager and JpaTransactionManager?</strong></summary>

#### Short answer

`DataSourceTransactionManager` manages JDBC `Connection` transactions; `JpaTransactionManager` manages JPA `EntityManager` transactions and coordinates with JDBC when appropriate.

#### Interview answer

Use `DataSourceTransactionManager` for plain JDBC or `JdbcTemplate`. It works directly with a `DataSource` and JDBC connections. Use `JpaTransactionManager` for JPA/Hibernate because it knows about `EntityManager`, persistence context flushing and JPA transaction semantics.

Spring Boot usually configures the right one based on the application setup.

#### Deep dive

JPA transaction behavior includes persistence context synchronization and flush timing, which plain JDBC transaction management does not understand.

#### Production angle

Using a JDBC manager around JPA code can create confusing persistence context behavior; using JPA manager around mixed JPA/JDBC requires understanding connection sharing.

#### Traps / caveats

- Transaction manager choice should match the resource being used.
- JPA flush may happen before commit.
- Multi-resource transactions are not automatic.

#### Optional Anki

Q: Which manager is typical for Hibernate/JPA?
A: `JpaTransactionManager`.

</details>

<a id="sp-tx-007"></a>

<details>
<summary><strong>SP-TX-007. How do REQUIRED, REQUIRES_NEW and NESTED propagation differ?</strong></summary>

#### Short answer

`REQUIRED` joins or creates a transaction, `REQUIRES_NEW` suspends the current one and starts a new transaction, and `NESTED` uses a savepoint inside an existing transaction when supported.

#### Interview answer

`REQUIRED` is the normal default: participate in the current transaction or start one. `REQUIRES_NEW` creates an independent physical transaction, so it can commit or roll back separately, but it needs another connection. `NESTED` creates a savepoint inside the existing transaction, allowing partial rollback without a fully independent transaction.

#### Deep dive

`NESTED` support depends on the transaction manager and database savepoint support. It is not the same as `REQUIRES_NEW`.

#### Production angle

Propagation choices affect connection pool usage, audit logging, outbox writes and error handling.

#### Traps / caveats

- `REQUIRES_NEW` can exhaust pools under load.
- `NESTED` may not work as expected with JPA.
- Overusing propagation makes business flow harder to reason about.

#### Optional Anki

Q: Which propagation suspends the current transaction?
A: `REQUIRES_NEW`.

</details>

<a id="sp-tx-008"></a>

<details>
<summary><strong>SP-TX-008. How does Spring transaction isolation map to the database isolation level?</strong></summary>

#### Short answer

Spring passes the requested isolation level to the transaction manager and database connection, but the database defines the actual behavior.

#### Interview answer

`@Transactional(isolation = ...)` asks Spring to use a given isolation level such as read committed, repeatable read or serializable. For JDBC, this maps to connection isolation. The database engine then implements its own semantics.

The same nominal isolation level can behave differently between PostgreSQL, MySQL and other databases.

#### Deep dive

If isolation is left as default, the database default is used. Changing isolation may affect locks, snapshots, retries and throughput.

#### Production angle

Isolation choices should be tied to correctness needs. Higher isolation can reduce anomalies but increase contention or serialization failures.

#### Traps / caveats

- Spring does not make database isolation portable.
- Some databases do not support every level exactly.
- Existing transactions may not allow isolation changes mid-flow.

#### Optional Anki

Q: Who ultimately defines isolation behavior?
A: The database.

</details>

<a id="sp-tx-009"></a>

<details>
<summary><strong>SP-TX-009. Which exceptions trigger rollback by default, and how do checked exceptions and caught exceptions change that?</strong></summary>

#### Short answer

By default, Spring rolls back on unchecked exceptions and `Error`, but not checked exceptions unless configured.

#### Interview answer

Spring's default rollback rules roll back for `RuntimeException` and `Error`. Checked exceptions normally do not trigger rollback unless you configure `rollbackFor`. If a transactional method catches an exception and returns normally, Spring sees success and usually commits unless the transaction was marked rollback-only.

This is one of the most common transaction interview traps.

#### Deep dive

Rollback rules can be customized with `rollbackFor` and `noRollbackFor`, but broad rules should be used carefully.

#### Production angle

Wrong rollback behavior can commit partial business operations or lose important audit/error records.

#### Traps / caveats

- Catching and swallowing exceptions prevents default rollback.
- Checked business exceptions need deliberate rollback policy.
- `UnexpectedRollbackException` can happen when an inner operation marks a shared transaction rollback-only.

#### Optional Anki

Q: Does Spring roll back on checked exceptions by default?
A: No, not unless configured.

</details>

<a id="sp-tx-010"></a>

<details>
<summary><strong>SP-TX-010. What does readOnly=true mean in @Transactional, and can writes still happen?</strong></summary>

#### Short answer

`readOnly=true` is a hint to Spring, the persistence provider and sometimes the database; it is not a universal hard write blocker.

#### Interview answer

A read-only transaction says the method intends not to modify data. Spring and Hibernate may optimize flush behavior, and some databases can enforce or optimize read-only transactions depending on configuration.

But developers should not assume it always prevents writes. The actual behavior depends on transaction manager, driver and database.

#### Deep dive

For JPA/Hibernate, read-only often affects flush mode or dirty checking behavior. For JDBC/database, enforcement varies.

#### Production angle

Read-only transactions can reduce overhead for query paths, but relying on them as the only safety mechanism is dangerous.

#### Traps / caveats

- It is not a substitute for permissions or database constraints.
- Writes may still happen in some setups.
- Lazy loading can still occur and use connections.

#### Optional Anki

Q: Is `readOnly=true` always a hard write prevention mechanism?
A: No, it is primarily a hint with implementation-dependent enforcement.

</details>

<a id="sp-tx-011"></a>

<details>
<summary><strong>SP-TX-011. Where should transaction boundaries usually be placed in a layered Spring application?</strong></summary>

#### Short answer

Usually at the service/application use-case layer, not at controllers or only at repositories.

#### Interview answer

A transaction should cover a complete business operation. In a layered Spring app, that is typically a service method such as "place order" or "transfer money". Controllers should handle HTTP concerns, and repositories should perform persistence operations.

Putting boundaries at the service layer lets multiple repository calls participate in one logical transaction.

#### Deep dive

Repository-level transactions may be enough for simple CRUD, but complex business consistency usually needs a wider boundary.

#### Production angle

Bad boundaries cause partial updates, long-held connections, lazy loading surprises or transactions that include remote calls.

#### Traps / caveats

- Controller-level transactions can hold connections during request mapping, serialization or remote calls.
- Repository-only transactions can split one business action into several commits.
- Very large service transactions can hold locks too long.

#### Optional Anki

Q: Typical transaction boundary in Spring backend apps?
A: Service/application use-case method.

</details>

<a id="sp-tx-012"></a>

<details>
<summary><strong>SP-TX-012. How do class-level and method-level @Transactional declarations interact?</strong></summary>

#### Short answer

Class-level `@Transactional` provides defaults; method-level declarations override them for specific methods.

#### Interview answer

Annotating a class marks all applicable methods with the same transactional defaults. A method annotation can override propagation, isolation, read-only, timeout or rollback rules.

This is useful for classes where most methods are transactional but some methods need read-only or no transaction.

#### Deep dive

Only methods eligible for proxy interception are affected. Private/internal calls still have the usual proxy limitations.

#### Production angle

Method-level overrides should be obvious because they can change consistency and performance characteristics.

#### Traps / caveats

- Class-level annotations can accidentally make methods transactional when they should not be.
- Method-level read-only on queries is common, but writes under read-only are confusing.
- Self-invocation still bypasses method-level advice.

#### Optional Anki

Q: Which wins: class-level or method-level `@Transactional`?
A: Method-level metadata for that method.

</details>

<a id="sp-tx-013"></a>

<details>
<summary><strong>SP-TX-013. How can @Transactional accidentally hold a database connection for too long?</strong></summary>

#### Short answer

A transaction can keep a connection checked out while the method performs slow work, remote calls, large processing or waits.

#### Interview answer

When a transaction starts and touches the database, a connection is associated with the current thread. If the method then calls external APIs, processes large files, waits on locks, does slow serialization or performs many operations, the connection may be held longer than necessary.

That reduces pool capacity and can block other requests.

#### Deep dive

Some transaction managers acquire connections lazily, but once acquired, the connection is commonly bound until transaction completion.

#### Production angle

Long-held connections are a common cause of HikariCP exhaustion and high request latency.

#### Traps / caveats

- Do not wrap remote HTTP calls in database transactions unless strongly justified.
- Streaming large responses inside a transaction can be dangerous.
- `REQUIRES_NEW` may require another connection while one is already held.

#### Optional Anki

Q: Why are remote calls inside transactions risky?
A: They hold database resources while waiting on external systems.

</details>

<a id="sp-tx-014"></a>

<details>
<summary><strong>SP-TX-014. How does @Transactional interact with Hibernate lazy loading and Open Session in View?</strong></summary>

#### Short answer

Lazy loading needs an active persistence context; transactions usually provide it in services, while OSIV keeps it open into the web view/serialization phase.

#### Interview answer

Inside a transactional service method, Hibernate can load lazy associations because an `EntityManager`/session is active. If a controller accesses lazy fields after the transaction closes, `LazyInitializationException` can occur.

Open Session in View keeps the persistence context open for the web request, so lazy loading may work during serialization, but this can hide N+1 queries and move database access into the web layer.

#### Deep dive

OSIV does not mean every lazy query is inside the original business transaction. It mainly keeps the session open beyond the service boundary.

#### Production angle

Returning entities from controllers with OSIV can create huge JSON responses, surprise queries and connection pressure.

#### Traps / caveats

- Lazy loading during JSON serialization is usually a design smell.
- DTOs and explicit fetch plans are safer.
- Disabling OSIV can reveal hidden persistence boundary problems.

#### Optional Anki

Q: Why can OSIV hide performance problems?
A: It allows lazy queries during web rendering or JSON serialization.

</details>

<a id="sp-tx-015"></a>

<details>
<summary><strong>SP-TX-015. What is TransactionTemplate, and when would you use programmatic transactions?</strong></summary>

#### Short answer

`TransactionTemplate` executes code inside an explicit transaction block controlled in code.

#### Interview answer

`TransactionTemplate` is Spring's programmatic transaction helper. You pass it a callback, and it handles begin, commit and rollback. I use it when the transaction boundary must be explicit inside a method, when only part of a workflow should be transactional, or when avoiding proxy limitations is cleaner than restructuring annotations.

Declarative `@Transactional` remains the default for ordinary service methods.

#### Deep dive

Programmatic transactions make boundaries visible but can clutter business code if overused.

#### Production angle

It is useful for patterns like: validate outside transaction, perform a short database update transaction, then call external systems after commit.

#### Traps / caveats

- Do not mix programmatic and declarative transactions without understanding propagation.
- Callback exceptions still determine rollback behavior.
- Explicit boundaries should be covered by tests.

#### Optional Anki

Q: Main benefit of `TransactionTemplate`?
A: An explicit transaction boundary in code.

</details>

<a id="sp-tx-016"></a>

<details>
<summary><strong>🧠 SP-TX-016. What are transaction synchronization callbacks and @TransactionalEventListener?</strong></summary>

#### Short answer

They let code run at transaction lifecycle phases, such as before commit, after commit or after rollback.

#### Interview answer

Transaction synchronization callbacks hook into the current transaction lifecycle. `@TransactionalEventListener` is a higher-level way to handle application events relative to a transaction phase, commonly `AFTER_COMMIT`.

This is useful when something should happen only if the database transaction successfully commits, such as publishing a domain event or sending a notification trigger.

#### Deep dive

Events handled before commit still run inside transaction timing; events after commit cannot roll back the committed transaction.

#### Production angle

This helps avoid sending messages or emails for operations that later roll back, but it must be designed with retry and failure handling.

#### Traps / caveats

- After-commit work can fail after data is committed.
- It is not a durable message queue by itself.
- For reliable integration, use the outbox pattern.

#### Optional Anki

Q: Common phase for `@TransactionalEventListener` when publishing external effects?
A: `AFTER_COMMIT`.

</details>

<a id="sp-tx-017"></a>

<details>
<summary><strong>SP-TX-017. What happens when @Async and @Transactional are combined?</strong></summary>

#### Short answer

`@Async` runs work in another thread, and transaction context does not automatically cross that thread boundary.

#### Interview answer

If an async method is transactional and is called through the proxy, the transaction starts in the async thread. It does not inherit the caller's transaction. If a transactional method calls an async method internally, proxy rules may prevent async behavior entirely.

You must decide whether the async work should run after commit, in its own transaction, or outside a transaction.

#### Deep dive

Thread-local contexts such as transactions, security and request attributes require explicit propagation or redesign.

#### Production angle

Incorrect async/transaction assumptions cause missing data, stale reads, lost security context and events sent before commit.

#### Traps / caveats

- Async work can see database state before the caller commits.
- Self-invocation can disable both annotations.
- Exceptions in async methods may not propagate to the caller.

#### Optional Anki

Q: Does a Spring transaction automatically propagate to an `@Async` thread?
A: No.

</details>

<a id="sp-tx-018"></a>

<details>
<summary><strong>SP-TX-018. How would you debug a transaction that does not roll back or causes connection pool exhaustion?</strong></summary>

#### Short answer

Check proxy invocation, exception handling, rollback rules, transaction manager, propagation, long-running work and pool metrics.

#### Interview answer

For missing rollback, I check whether the method is called through a proxy, whether the exception is unchecked or configured with `rollbackFor`, whether it is caught, and whether the right transaction manager is used.

For pool exhaustion, I inspect Hikari metrics, active/idle/pending connections, long transactions, slow queries, remote calls inside transactions, `REQUIRES_NEW`, thread dumps and database activity.

#### Deep dive

Enable transaction debug logs carefully in lower environments and correlate with SQL logs, traces and pool metrics.

#### Production angle

Pool exhaustion is often a symptom of long work inside transactions, not simply "pool too small".

#### Traps / caveats

- Increasing pool size can overload the database.
- Logging all SQL with parameters in production can leak data.
- A caught exception can still mark a transaction rollback-only and later cause `UnexpectedRollbackException`.

#### Optional Anki

Q: First rollback debugging checks?
A: Proxy call path, exception type, caught exceptions and rollback rules.

</details>

<a id="sp-tx-019"></a>

<details>
<summary><strong>SP-TX-019. Why are distributed transactions usually avoided in microservice architectures?</strong></summary>

#### Short answer

They couple services tightly, reduce availability, complicate operations and often do not fit independent service ownership.

#### Interview answer

Distributed transactions try to make changes across multiple resources atomic. In microservices, that usually means coordination across service and database boundaries. It adds locking, coordinator failure modes, latency and operational complexity.

Instead, systems often use local transactions plus outbox, sagas, idempotent consumers, retries and compensating actions.

#### Deep dive

Avoiding distributed transactions does not mean ignoring consistency. It means modeling consistency boundaries explicitly.

#### Production angle

Local transactions with durable events are easier to monitor, retry and recover than a hidden cross-service transaction coordinator.

#### Traps / caveats

- Eventual consistency still needs invariants and reconciliation.
- Sagas can fail midway and need compensation.
- The outbox pattern requires reliable polling or streaming and idempotent consumers.

#### Optional Anki

Q: Common alternative to distributed transactions in microservices?
A: Local transaction plus outbox/saga/idempotent processing.

</details>
