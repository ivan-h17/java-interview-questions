# 16.04. Bean scopes, component scanning and stereotypes

---

<a id="sp-scope-001"></a>

<details>
<summary><strong>SP-SCOPE-001. What bean scopes exist in Spring?</strong></summary>

#### Short answer

Common scopes are singleton, prototype, request, session, application and websocket. Custom scopes are also possible.

#### Interview answer

`singleton` is the default: one bean instance per Spring container. `prototype` creates a new instance each time the bean is requested from the container. Web-aware scopes bind beans to an HTTP request, HTTP session, servlet context application, or websocket session.

In backend services, most beans are singleton because they are stateless services, repositories, controllers and infrastructure components.

#### Deep dive

Scope controls bean instance lifecycle, not Java visibility or business tenancy. A singleton bean can still be used by many users and requests concurrently.

#### Production angle

Choosing the wrong scope can cause memory leaks, shared mutable state bugs or excessive object creation.

#### Traps / caveats

- Singleton beans must be thread-safe if they hold mutable state.
- Request/session scopes require a web request context.
- Prototype destruction is not managed like singleton destruction.

#### Optional Anki

Q: What is the default Spring bean scope?
A: `singleton`.

</details>

<a id="sp-scope-002"></a>

<details>
<summary><strong>SP-SCOPE-002. What is the difference between singleton and prototype scope?</strong></summary>

#### Short answer

Singleton creates one shared instance per container; prototype creates a new instance when requested from the container.

#### Interview answer

A singleton bean is created once per application context and reused. A prototype bean is created every time Spring is asked for it. Singleton is the default and fits stateless services. Prototype is useful for stateful helper objects that should not be shared.

The important caveat is that injecting a prototype into a singleton does not automatically create a new prototype on every method call.

#### Deep dive

Spring manages the full lifecycle of singleton beans. For prototypes, Spring creates and configures the object, then mostly hands it off to the caller.

#### Production angle

Most backend bugs around scope come from mutable state in singletons or mistaken assumptions about prototype freshness.

#### Traps / caveats

- Singleton is per Spring container, not per JVM globally.
- Prototype beans are not automatically destroyed by the container.
- A singleton holding a prototype field keeps the same prototype instance.

#### Optional Anki

Q: Does injecting a prototype into a singleton create a new instance per call?
A: No, the singleton receives one prototype instance at injection time.

</details>

<a id="sp-scope-003"></a>

<details>
<summary><strong>SP-SCOPE-003. What are request, session, application and websocket scopes?</strong></summary>

#### Short answer

They are web scopes that bind bean instances to an HTTP request, HTTP session, servlet application context or websocket session.

#### Interview answer

`request` scope creates one bean per HTTP request. `session` creates one per HTTP session. `application` creates one per servlet context. `websocket` creates one per websocket session.

They are useful when a component must hold context tied to a specific web interaction, but they should be used carefully in stateless APIs.

#### Deep dive

These scopes depend on request context infrastructure. Accessing them from a background thread without context propagation can fail.

#### Production angle

Session-scoped beans can increase memory usage and complicate horizontal scaling. Stateless backend services usually prefer explicit request data and tokens over server-side session state.

#### Traps / caveats

- Request-scoped beans cannot be used outside an active request unless proxied or accessed through a provider.
- Session scope can break assumptions in distributed deployments.
- Do not store sensitive or large objects casually in session-scoped state.

#### Optional Anki

Q: Which scope creates one bean per HTTP request?
A: `request` scope.

</details>

<a id="sp-scope-004"></a>

<details>
<summary><strong>SP-SCOPE-004. What happens when a singleton bean depends on a prototype bean?</strong></summary>

#### Short answer

The prototype is created once when the singleton is created, so the singleton keeps the same prototype instance.

#### Interview answer

Spring resolves dependencies when creating the singleton. If a prototype dependency is injected directly, Spring creates one prototype instance and assigns it to the singleton field or constructor parameter. Later calls on the singleton reuse that same object.

If the singleton needs fresh instances, inject a provider, use lookup method injection or request the prototype from a factory.

#### Deep dive

Prototype scope affects calls to the container, not arbitrary method calls on a singleton.

#### Production angle

This matters for stateful objects such as builders, per-operation accumulators or non-thread-safe helpers.

#### Traps / caveats

- Direct prototype injection does not mean per-request or per-operation.
- `@Lazy` is not the same as "new every time".
- Consider whether the object should just be created with `new` if it is not a Spring-managed dependency.

#### Optional Anki

Q: How many prototype instances does a singleton get from direct injection?
A: One, at singleton creation time.

</details>

<a id="sp-scope-005"></a>

<details>
<summary><strong>SP-SCOPE-005. How can a singleton bean obtain a new prototype instance on demand?</strong></summary>

#### Short answer

Use `ObjectProvider`, `Provider`, lookup method injection, a factory bean or an explicit factory component.

#### Interview answer

The cleanest option is often injecting `ObjectProvider<MyPrototype>` and calling `getObject()` when a fresh instance is needed. Another option is a factory component that creates the object. Spring also supports `@Lookup`, where a method is overridden by the container to return a new bean instance.

I prefer an explicit provider or factory because the dependency is visible.

#### Deep dive

If the object has no Spring dependencies, plain object creation may be simpler than making it a prototype bean.

#### Production angle

Fresh instances are useful for per-job or per-request state that must not leak across threads.

#### Traps / caveats

- Repeated provider calls can create many objects; understand allocation cost.
- `@Lookup` uses method override mechanics and can be less obvious to readers.
- Do not use `ApplicationContext` directly in business code unless there is a strong reason.

#### Optional Anki

Q: Common typed way to get fresh prototype beans from a singleton?
A: Inject `ObjectProvider<T>` and call `getObject()`.

</details>

<a id="sp-scope-006"></a>

<details>
<summary><strong>🧠 SP-SCOPE-006. What is a scoped proxy?</strong></summary>

#### Short answer

A scoped proxy is a stable proxy injected into a longer-lived bean that delegates to the correct scoped target at runtime.

#### Interview answer

Scoped proxies solve lifetime mismatch. For example, a singleton service cannot directly hold a request-scoped bean instance because there is no single request. Instead, Spring injects a proxy. When the singleton calls it during a request, the proxy resolves the current request's target bean.

This is common for request-scoped context objects.

#### Deep dive

The proxy is usually singleton, but the target behind it changes according to the active scope.

#### Production angle

Scoped proxies can keep APIs convenient, but they hide context access. They can fail in background threads where no request context exists.

#### Traps / caveats

- Calling a request-scoped proxy outside a request can fail.
- Proxy limitations still apply: type, final classes and method interception details matter.
- Passing scoped proxies into asynchronous code can be misleading.

#### Optional Anki

Q: What problem does a scoped proxy solve?
A: Injecting a shorter-lived scoped bean into a longer-lived bean.

</details>

<a id="sp-comp-001"></a>

<details>
<summary><strong>SP-COMP-001. Where does component scanning start by default in Spring Boot?</strong></summary>

#### Short answer

By default, component scanning starts from the package of the class annotated with `@SpringBootApplication` and scans its subpackages.

#### Interview answer

`@SpringBootApplication` includes component scanning. The package containing the main application class becomes the base package, and Spring scans below it for components, controllers, services, repositories and configuration classes.

That is why the main application class is usually placed in the root package of the application.

#### Deep dive

You can customize scanning with `scanBasePackages` or `scanBasePackageClasses`, but doing so should be deliberate.

#### Production angle

Wrong package placement can cause beans to be missing in production or tests even though the code compiles.

#### Traps / caveats

- Sibling packages outside the scan root are not discovered automatically.
- Broad scanning can pick up classes from modules that should not be active.
- Test configurations can accidentally be scanned if placed in the wrong package.

#### Optional Anki

Q: Default Spring Boot component scan root?
A: The package of the `@SpringBootApplication` class.

</details>

<a id="sp-comp-002"></a>

<details>
<summary><strong>SP-COMP-002. How can incorrect package structure break component scanning?</strong></summary>

#### Short answer

If components are outside the scan root, Spring will not discover them unless scanning is configured explicitly.

#### Interview answer

In Boot, scanning starts from the main application package. If a service, repository or configuration class sits in a sibling or parent package, it may not be scanned. Then injections fail with missing bean errors, controllers do not register, or repositories are unavailable.

The fix is usually to move the main class to the root package or explicitly configure scan packages.

#### Deep dive

Multi-module builds often expose this problem because packages may not share a common root.

#### Production angle

Package moves during refactoring can create startup failures that only appear in the full application context.

#### Traps / caveats

- Adding broad scan packages can create duplicate or unintended beans.
- Repository scanning and entity scanning have related but separate configuration.
- Test slices may scan differently from the full app.

#### Optional Anki

Q: Best package placement for the Boot main class?
A: In the root package above application components.

</details>

<a id="sp-comp-003"></a>

<details>
<summary><strong>SP-COMP-003. What is the difference between @Component, @Service, @Repository and @Controller?</strong></summary>

#### Short answer

They all register components, but stereotypes express role: generic component, service, repository or web controller.

#### Interview answer

`@Component` is the generic stereotype. `@Service` marks service-layer components. `@Repository` marks persistence components and enables persistence exception translation. `@Controller` marks MVC controllers that return views or responses, and `@RestController` combines `@Controller` with response-body behavior.

Using the specific stereotype improves readability and lets framework behavior attach to the right layer.

#### Deep dive

These annotations are meta-annotated with `@Component`, so component scanning detects them.

#### Production angle

Clear stereotypes make code structure easier to review and help teams maintain layer boundaries.

#### Traps / caveats

- `@Service` has mostly semantic meaning, but that meaning is valuable.
- `@Repository` has extra exception translation behavior.
- `@Controller` is not the same as `@RestController`.

#### Optional Anki

Q: Which stereotype enables persistence exception translation?
A: `@Repository`.

</details>

<a id="sp-comp-004"></a>

<details>
<summary><strong>SP-COMP-004. What is exception translation in @Repository?</strong></summary>

#### Short answer

Spring can translate persistence-provider exceptions into Spring's consistent `DataAccessException` hierarchy for repository beans.

#### Interview answer

When a class is marked `@Repository`, Spring can apply persistence exception translation. Low-level exceptions from JDBC, JPA or Hibernate can be converted to unchecked Spring data access exceptions such as constraint violation or duplicate key style exceptions.

This gives application code a consistent exception model across data access technologies.

#### Deep dive

Translation is implemented by infrastructure post-processors and exception translators. It does not make all database errors identical; it normalizes common categories.

#### Production angle

Consistent exception categories help transaction rollback, error handling and logging without coupling service code to a specific provider.

#### Traps / caveats

- Do not catch broad `DataAccessException` and return success.
- Translation does not replace understanding database constraints and SQL states.
- Exception translation can affect rollback because translated exceptions are unchecked.

#### Optional Anki

Q: What exception hierarchy does Spring data access translation use?
A: `DataAccessException`.

</details>

<a id="sp-comp-005"></a>

<details>
<summary><strong>🧠 SP-COMP-005. What is a meta-annotation, and when would you create your own stereotype annotation?</strong></summary>

#### Short answer

A meta-annotation is an annotation used on another annotation. Custom stereotypes combine common Spring annotations and domain meaning.

#### Interview answer

Spring annotations are often composable. For example, `@Service` is itself a component stereotype. You can create a custom annotation such as `@UseCase` or `@Adapter` that is meta-annotated with `@Component` and perhaps qualifiers or transactional metadata.

This can make architecture boundaries visible in code.

#### Deep dive

Custom composed annotations can also use attribute aliases to expose selected options from underlying annotations.

#### Production angle

They help large teams enforce consistent patterns, such as marking inbound adapters, scheduled jobs or application services.

#### Traps / caveats

- Do not create custom stereotypes just for novelty.
- Too many custom annotations make code harder for new developers.
- Be careful composing behavior-heavy annotations like `@Transactional`.

#### Optional Anki

Q: What does a Spring custom stereotype usually include?
A: `@Component` plus semantic or configuration metadata.

</details>

<a id="sp-comp-006"></a>

<details>
<summary><strong>🧠 SP-COMP-006. How do basePackages, basePackageClasses and component-scan exclusions differ?</strong></summary>

#### Short answer

`basePackages` names packages as strings, `basePackageClasses` derives packages from class references, and exclusions remove matching components from scanning.

#### Interview answer

`basePackages` is flexible but string-based and easier to break during refactoring. `basePackageClasses` is type-safe because the package is derived from a class. Exclusion filters let you prevent specific annotations, types or patterns from being scanned.

For maintainability, class-based package markers are often safer than package-name strings.

#### Deep dive

Exclusions are useful in tests, modular apps or when a package contains classes that should not be active in a particular context.

#### Production angle

Wrong scan configuration can accidentally activate test, legacy or alternative infrastructure beans.

#### Traps / caveats

- Broad exclusions can hide required components.
- String package names do not refactor safely.
- Scanning too many packages can slow startup and create bean conflicts.

#### Optional Anki

Q: Why prefer `basePackageClasses` over `basePackages`?
A: It is type-safe and refactor-friendly.

</details>

<a id="sp-comp-007"></a>

<details>
<summary><strong>SP-COMP-007. What are common component scanning mistakes in multi-module projects?</strong></summary>

#### Short answer

Common mistakes are scan roots that miss module packages, scanning too broadly, duplicated configurations and accidental inclusion of test or alternative beans.

#### Interview answer

In multi-module projects, the main app may not scan packages from feature modules. Developers often fix that with broad scanning, which then pulls in unintended beans. Another issue is duplicate configuration: two modules define similar clients, mappers or repositories.

I prefer explicit imports or well-defined module package roots over scanning everything.

#### Deep dive

Entity scanning, repository scanning and component scanning may need separate configuration depending on the module layout.

#### Production angle

These mistakes cause startup failures, wrong bean selection or behavior differences between apps that reuse the same library module.

#### Traps / caveats

- A library should not accidentally auto-register application-specific beans unless designed as a starter.
- Package conventions matter.
- Test-only components can leak into production scans if placed under main packages.

#### Optional Anki

Q: Better alternative to scanning every module broadly?
A: Explicit imports or clear module package roots.

</details>

<a id="sp-comp-008"></a>

<details>
<summary><strong>🧠 SP-COMP-008. How can overly broad component scanning affect startup time and application correctness?</strong></summary>

#### Short answer

It can scan more classes, register unintended beans, create conflicts and activate configuration that should not belong to the application.

#### Interview answer

Broad scanning increases classpath scanning work and makes the container consider many candidates. More importantly, it can register beans from unrelated modules, old implementations, test helpers or alternative configurations.

That can lead to `NoUniqueBeanDefinitionException`, unexpected auto-wiring, changed transaction/security behavior or slower startup.

#### Deep dive

Startup time is not only scanning cost. Unintended beans may trigger expensive initialization, data source creation, clients, schedulers or message consumers.

#### Production angle

Accidental bean activation can cause real incidents: duplicate scheduled jobs, calls to wrong endpoints or unexpected background consumers.

#### Traps / caveats

- "Just scan the root package" is not safe if the root includes unrelated modules.
- Excluding after overly broad scanning can become fragile.
- Explicit module boundaries are easier to debug.

#### Optional Anki

Q: Biggest risk of overly broad component scanning?
A: Unintended beans and configuration become active.

</details>
