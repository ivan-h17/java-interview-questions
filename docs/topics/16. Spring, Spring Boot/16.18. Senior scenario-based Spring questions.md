# 16.18. Senior scenario-based Spring questions

---

<a id="sp-scen-001"></a>

<details>
<summary><strong>SP-SCEN-001. A @Transactional method does not roll back after an exception. How would you investigate?</strong></summary>

#### Short answer

Check proxy invocation, exception type, caught exceptions, rollback rules, transaction manager and whether the database work is inside the same transaction.

#### Interview answer

I would first confirm the method is called through a Spring proxy and is eligible for transaction advice. Then I would check whether the exception is unchecked, checked, caught, translated or configured with `rollbackFor`. I would verify the correct `PlatformTransactionManager` is used and that the repository work participates in the same transaction.

Logs or tests should confirm transaction boundaries.

#### Deep dive

An inner `REQUIRED` call can mark a transaction rollback-only, causing `UnexpectedRollbackException` later even if the exception was caught.

#### Production angle

Wrong rollback behavior can commit partial updates or create data inconsistencies that need repair.

#### Traps / caveats

- Checked exceptions do not roll back by default.
- Self-invocation bypasses the proxy.
- Catching and not rethrowing usually makes Spring see success.

#### Optional Anki

Q: First things to check when rollback does not happen?
A: Proxy call path, exception handling and rollback rules.

</details>

<a id="sp-scen-002"></a>

<details>
<summary><strong>SP-SCEN-002. A method is annotated with @Transactional, @Async, @Cacheable or @PreAuthorize, but the advice is not applied. What proxy-related reasons are possible?</strong></summary>

#### Short answer

The call may bypass the proxy, the method may be non-interceptable, the object may not be a Spring bean, or the relevant infrastructure may not be enabled.

#### Interview answer

I would check for self-invocation, private/final methods, constructor calls, manual `new`, wrong proxy type, missing annotation on the effective method, and disabled infrastructure such as transaction management, caching, async or method security.

Then I would inspect whether the runtime object is proxied and whether advisors match the method.

#### Deep dive

Interface-based proxies can expose only interface methods, while class-based proxies need overridable methods.

#### Production angle

This explains many silent failures: no rollback, cache miss, async running synchronously or missing authorization.

#### Traps / caveats

- Public visibility alone does not fix self-invocation.
- Mocks in tests can remove advice.
- Multiple advisors can apply in surprising order.

#### Optional Anki

Q: Common reason Spring method annotations do not apply?
A: The call did not go through the Spring proxy.

</details>

<a id="sp-scen-003"></a>

<details>
<summary><strong>SP-SCEN-003. A Spring Boot application starts locally but fails in Kubernetes. What would you check?</strong></summary>

#### Short answer

Check environment-specific configuration, secrets, profiles, resource limits, networking, startup probes, migrations and container image differences.

#### Interview answer

I would compare local and Kubernetes runtime inputs: active profiles, env vars, mounted config/secrets, command-line args, image version, Java version, memory/CPU limits, database URLs, DNS, network policy and service accounts. Then inspect pod logs, events, probes and the full startup exception.

Many failures are configuration or environment, not code.

#### Deep dive

Container memory limits affect JVM sizing and native memory. Missing secrets often show up as config binding or authentication failures.

#### Production angle

Reproducible deployment configuration and startup validation prevent environment drift incidents.

#### Traps / caveats

- Local `.env` or profile defaults may hide missing production config.
- Kubernetes probes can kill a slow-starting app.
- Config maps and secrets may not update running pods as expected.

#### Optional Anki

Q: First comparison for local works but Kubernetes fails?
A: Effective runtime configuration and environment.

</details>

<a id="sp-scen-004"></a>

<details>
<summary><strong>SP-SCEN-004. A production service suddenly returns many 503 responses during deployment. How would you investigate?</strong></summary>

#### Short answer

Check readiness, rolling update settings, graceful shutdown, capacity during rollout, dependency health and gateway/load-balancer behavior.

#### Interview answer

I would build a timeline around the deployment and inspect pod readiness transitions, termination events, probe failures, replica availability, gateway logs and service metrics. I would check whether new pods became ready too early or old pods were removed before draining.

Also verify database migrations and dependency readiness during the rollout.

#### Deep dive

Deployment 503s often come from readiness misconfiguration, insufficient surge capacity or slow startup.

#### Production angle

Fixes may include readiness gates, startup probes, graceful shutdown, preStop/drain delays, rollout settings and capacity planning.

#### Traps / caveats

- Liveness restarts can make deployment instability worse.
- Health green does not always mean ready for real traffic.
- One bad replica can cause intermittent errors.

#### Optional Anki

Q: What probe controls routing during deployment?
A: Readiness.

</details>

<a id="sp-scen-005"></a>

<details>
<summary><strong>SP-SCEN-005. An endpoint is slow, but the controller code is simple. How would you debug it?</strong></summary>

#### Short answer

Trace the request through service, database, HTTP clients, serialization, security, locks and thread pools.

#### Interview answer

Simple controller code often delegates to expensive work. I would inspect endpoint metrics and traces to find slow spans: repository queries, lazy loading, external calls, validation, security checks or serialization. Then I would check SQL count/timings, HTTP client metrics, thread dumps and logs with correlation IDs.

I would reproduce with production-like data.

#### Deep dive

Serialization can trigger lazy loading if entities are returned directly, making the controller look innocent.

#### Production angle

The fix may be a fetch plan, projection, index, timeout, cache, DTO mapping or dependency mitigation.

#### Traps / caveats

- A simple controller can hide N+1 queries.
- Averages hide p99 latency.
- Local data size often hides production slowness.

#### Optional Anki

Q: Best signal to locate slow work across layers?
A: Distributed trace spans plus query/client metrics.

</details>

<a id="sp-scen-006"></a>

<details>
<summary><strong>SP-SCEN-006. A Spring application has too many beans and slow startup. What would you do?</strong></summary>

#### Short answer

Measure startup, inspect bean count/origins, reduce scanning/starters, remove heavy initialization and review auto-configuration.

#### Interview answer

I would first measure where startup time goes using startup diagnostics, logs or profiling. Then I would inspect beans and auto-configuration, remove unused starters, narrow component scanning, split unnecessary configurations, avoid external calls in initialization and review JPA/migration cost.

Lazy initialization or AOT may help after root causes are understood.

#### Deep dive

Too many beans can be a symptom of overly broad scanning or a shared module that auto-registers too much.

#### Production angle

Slow startup hurts deployment speed, autoscaling and recovery.

#### Traps / caveats

- Do not hide critical failures with lazy init.
- Removing starters can remove useful production integration.
- Bean count alone is less important than expensive beans.

#### Optional Anki

Q: First step for slow Spring startup?
A: Measure startup phases and expensive bean creation.

</details>

<a id="sp-scen-007"></a>

<details>
<summary><strong>SP-SCEN-007. Auto-configuration creates an unexpected bean. How would you find the reason?</strong></summary>

#### Short answer

Inspect bean origin and the condition evaluation report to see which auto-configuration matched.

#### Interview answer

I would locate the bean in Actuator `beans`, IDE navigation or logs, then inspect the condition report for the auto-configuration class and method. I would check classpath dependencies, active properties and existing beans that caused conditions to match.

Then decide whether to configure, replace, customize or exclude.

#### Deep dive

Unexpected beans often appear after adding a starter or transitive dependency.

#### Production angle

Understanding the cause avoids broad exclusions that break other defaults.

#### Traps / caveats

- User beans can cause other auto-configurations to back off.
- Exclusions can be too blunt.
- The unexpected bean may come from an internal starter.

#### Optional Anki

Q: Main diagnostic for unexpected auto-configured beans?
A: Condition evaluation report.

</details>

<a id="sp-scen-008"></a>

<details>
<summary><strong>SP-SCEN-008. A repository test works locally but fails in CI. How would you investigate?</strong></summary>

#### Short answer

Compare database, migrations, test data, time zones, parallelism, container availability and active test properties.

#### Interview answer

I would check whether local and CI use the same database engine and version, whether migrations run, which profiles/properties are active, and whether tests depend on order or shared data. I would inspect CI logs, container startup, network/Docker availability and time-zone/locale differences.

Repository tests should be deterministic and isolated.

#### Deep dive

H2 locally and PostgreSQL in CI, or the reverse, often creates dialect-specific surprises.

#### Production angle

CI failures expose environment assumptions that can also affect staging or production.

#### Traps / caveats

- Parallel tests can conflict on shared database state.
- Transactional rollback may hide sequence/state issues.
- Time-dependent queries need fixed clocks.

#### Optional Anki

Q: Common reason repository tests differ between local and CI?
A: Different database/configuration or shared test state.

</details>

<a id="sp-scen-009"></a>

<details>
<summary><strong>SP-SCEN-009. The application exhausts database connections under load. What Spring-specific issues would you check?</strong></summary>

#### Short answer

Check long transactions, remote calls inside transactions, OSIV, `REQUIRES_NEW`, slow queries, pool settings and unbounded concurrency.

#### Interview answer

I would inspect Hikari metrics, active/pending connections, thread dumps and traces. Spring-specific causes include `@Transactional` methods doing slow external work, OSIV holding sessions during serialization, `REQUIRES_NEW` needing extra connections, async tasks sharing the same pool and missing query timeouts.

Then I would verify database capacity and query performance.

#### Deep dive

Pool exhaustion is usually a symptom, not the root cause.

#### Production angle

Mitigation may include reducing concurrency, shortening transactions, lowering timeouts, disabling problematic endpoints or scaling carefully.

#### Traps / caveats

- Increasing pool size can overload the database.
- Read-only transactions still use connections.
- Lazy loading during response serialization can hold resources longer.

#### Optional Anki

Q: Why can `REQUIRES_NEW` worsen pool exhaustion?
A: It may need another connection while the outer transaction holds one.

</details>

<a id="sp-scen-010"></a>

<details>
<summary><strong>SP-SCEN-010. A cache returns stale data after an update. How would you investigate?</strong></summary>

#### Short answer

Check cache key design, eviction/update path, transaction timing, TTL, multi-instance behavior and whether calls go through the cache proxy.

#### Interview answer

I would identify the cache name and key used for the stale value, inspect TTL and stored value, then trace the write path to see whether `@CacheEvict` or `@CachePut` ran. I would check self-invocation, transaction commit timing, multi-node Redis/local cache differences and tenant/user key dimensions.

If the cache is shared, I would consider targeted eviction or key versioning.

#### Deep dive

Evicting before commit can let readers repopulate stale values before the database update is committed.

#### Production angle

Stale caches can cause wrong business behavior even when the database is correct.

#### Traps / caveats

- Local caches on multiple replicas need coordinated invalidation.
- Wrong keys can leak data across users or tenants.
- TTL is not a correctness guarantee.

#### Optional Anki

Q: First cache stale-data checks?
A: Key, eviction path, transaction timing and proxy invocation.

</details>

<a id="sp-scen-011"></a>

<details>
<summary><strong>SP-SCEN-011. A security rule blocks an endpoint with 403 instead of 401. How would you debug it?</strong></summary>

#### Short answer

Check whether authentication succeeded, authorization failed, CSRF blocked the request or the wrong security chain matched.

#### Interview answer

401 means authentication is missing or invalid. 403 means the request is understood but forbidden, or CSRF/method security denied it. I would inspect the matched `SecurityFilterChain`, authentication object, authorities, CSRF status, method security and logs.

I would also verify test tokens or mock users map to the same authorities as production.

#### Deep dive

Spring Security debug logs can show matcher and authorization decisions in lower environments.

#### Production angle

Clear 401/403 handling improves client behavior and reduces support confusion.

#### Traps / caveats

- CSRF often produces 403.
- Role prefix mapping can cause authority mismatches.
- CORS preflight can fail before normal auth flow.

#### Optional Anki

Q: What can cause 403 besides missing role?
A: CSRF failure or wrong security chain/method security decision.

</details>

<a id="sp-scen-012"></a>

<details>
<summary><strong>SP-SCEN-012. A service uses @Async, but request context or security context disappears. Why?</strong></summary>

#### Short answer

The async method runs in a different thread, so thread-local request/security context is not automatically present.

#### Interview answer

Spring request attributes, security context and MDC are commonly thread-local. `@Async` moves execution to an executor thread, so those values disappear unless propagated. You can use task decorators, security delegation wrappers or pass explicit context values.

Prefer passing only what the async task truly needs.

#### Deep dive

Context propagation must also clean up after execution because thread-pool threads are reused.

#### Production angle

Lost context breaks authorization, tracing and log correlation for background work.

#### Traps / caveats

- Request-scoped beans are unsafe in async code without context.
- Propagating too much context can leak sensitive data.
- Async failures may not reach the original request.

#### Optional Anki

Q: Why does context disappear in `@Async`?
A: It runs on another thread.

</details>

<a id="sp-scen-013"></a>

<details>
<summary><strong>SP-SCEN-013. A background scheduled job runs twice after scaling replicas. What would you do?</strong></summary>

#### Short answer

Recognize that `@Scheduled` runs per instance and add coordination, external scheduling or idempotency.

#### Interview answer

In a scaled deployment, each replica executes its own scheduled methods. To avoid duplicate work, use leader election, distributed locking, Kubernetes CronJob, queue-based processing or partitioned work. The job should also be idempotent because coordination can fail.

For critical jobs, prefer durable external orchestration.

#### Deep dive

Distributed locks need timeout, renewal and failure handling. A stuck lock can stop all work.

#### Production angle

Duplicate scheduled work can create duplicate emails, payments, reports or data modifications.

#### Traps / caveats

- In-memory locks work only inside one JVM.
- Scaling changes scheduling behavior.
- CronJobs can also overlap unless configured.

#### Optional Anki

Q: Default behavior of `@Scheduled` in three replicas?
A: The job runs in all three replicas.

</details>

<a id="sp-scen-014"></a>

<details>
<summary><strong>SP-SCEN-014. A controller returns entities and causes LazyInitializationException or huge JSON responses. How would you fix the design?</strong></summary>

#### Short answer

Stop returning entities, define DTOs, fetch exactly what the endpoint needs and map inside clear transaction boundaries.

#### Interview answer

I would replace entity responses with DTOs designed for the API. The service/repository should use explicit fetch plans, projections, joins or entity graphs to load required data inside a transaction. Mapping should happen before leaving the service boundary if lazy fields are needed.

This removes reliance on OSIV and protects the API contract.

#### Deep dive

DTOs also avoid recursive serialization, sensitive field leakage and coupling to database schema.

#### Production angle

Explicit read models reduce slow endpoints, N+1 queries and accidental data exposure.

#### Traps / caveats

- Do not simply make all associations eager.
- Watch pagination with fetch joins.
- DTO mapping can still trigger lazy loading if done carelessly.

#### Optional Anki

Q: Main fix for entity serialization problems?
A: Return DTOs with explicit fetch planning.

</details>

<a id="sp-scen-015"></a>

<details>
<summary><strong>SP-SCEN-015. A health check is green, but the service cannot process real traffic. What should readiness check?</strong></summary>

#### Short answer

Readiness should check whether the instance can handle its critical traffic path, not just whether the process is alive.

#### Interview answer

I would separate liveness from readiness. Liveness can be shallow. Readiness should include application state needed to serve traffic: startup complete, required local initialization, critical dependencies when appropriate, message consumer state or migration status.

It should be fast, bounded and designed so dependency outages do not cause destructive restart loops.

#### Deep dive

Different endpoints or workloads may need different readiness groups.

#### Production angle

Bad readiness causes traffic to route to instances that cannot serve, creating 5xx during deploys or incidents.

#### Traps / caveats

- Do not put every optional dependency in readiness.
- Do not use liveness for dependency readiness.
- Probes themselves can overload dependencies if expensive.

#### Optional Anki

Q: What should readiness answer?
A: Can this instance serve real traffic now?

</details>

<a id="sp-scen-016"></a>

<details>
<summary><strong>🧠 SP-SCEN-016. A custom starter or Spring Boot upgrade changes auto-configuration or test behavior. How would you investigate?</strong></summary>

#### Short answer

Compare release notes, dependency versions, auto-configuration metadata, condition reports, bean definitions and test context configuration.

#### Interview answer

For a starter, I would verify its auto-configuration imports, conditions, ordering, properties metadata and whether the jar is on the runtime classpath. For a Boot upgrade, I would read migration notes, check removed/renamed properties, changed defaults, dependency versions and deprecated test annotations.

For tests, inspect context cache keys, mock bean annotations and slice behavior changes.

#### Deep dive

Auto-configuration can change because a dependency version adds/removes classes, a condition starts matching, or a user bean now causes backoff.

#### Production angle

Upgrades and internal starters need sample-app tests and compatibility checks before broad rollout.

#### Traps / caveats

- A transitive dependency can activate new auto-configuration.
- Old `@MockBean` style tests may need migration in modern Spring versions.
- Excluding auto-configuration can hide the real issue.

#### Optional Anki

Q: Best diagnostic for changed auto-configuration behavior?
A: Compare condition evaluation reports before and after the change.

</details>
