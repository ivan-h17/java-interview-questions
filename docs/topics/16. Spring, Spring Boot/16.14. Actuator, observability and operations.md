# 16.14. Actuator, observability and operations

---

<a id="sp-obs-001"></a>

<details>
<summary><strong>SP-OBS-001. What is Spring Boot Actuator?</strong></summary>

#### Short answer

Actuator adds production-ready operational endpoints and integrations for health, metrics, info, logging, environment and diagnostics.

#### Interview answer

Spring Boot Actuator exposes management capabilities for running applications. Common endpoints include health, metrics, prometheus, info, loggers, mappings, beans and conditions. It integrates with Micrometer for metrics and Boot observability features for tracing.

Actuator should be exposed and secured deliberately.

#### Deep dive

Actuator endpoints can be exposed over HTTP or JMX, and exposure configuration is separate from security configuration.

#### Production angle

Actuator is central to Kubernetes probes, monitoring, alerting and runtime diagnostics.

#### Traps / caveats

- Do not expose sensitive endpoints publicly.
- Health details can leak internals.
- Enabling an endpoint does not mean it is secured.

#### Optional Anki

Q: What is Spring Boot Actuator used for?
A: Production operations and diagnostics endpoints.

</details>

<a id="sp-obs-002"></a>

<details>
<summary><strong>SP-OBS-002. What are health, liveness and readiness endpoints?</strong></summary>

#### Short answer

Health reports application state; liveness says whether the process should be restarted; readiness says whether it should receive traffic.

#### Interview answer

A health endpoint gives status information. Liveness should indicate if the process is alive and not irrecoverably stuck. Readiness should indicate whether the instance is ready to handle real traffic, including critical dependencies or initialization state as appropriate.

In Kubernetes, liveness and readiness have different actions.

#### Deep dive

A dependency outage should not always fail liveness, because restarting every pod may make things worse. It may fail readiness if the instance cannot serve traffic.

#### Production angle

Correct probes prevent traffic from going to unready instances and avoid destructive restart loops.

#### Traps / caveats

- Do not put every dependency into liveness.
- Readiness should reflect actual serving ability.
- Health details should be restricted.

#### Optional Anki

Q: Which probe controls whether a pod receives traffic?
A: Readiness.

</details>

<a id="sp-obs-003"></a>

<details>
<summary><strong>SP-OBS-003. What is the difference between liveness and readiness in Kubernetes?</strong></summary>

#### Short answer

Failed liveness restarts the container; failed readiness removes it from service endpoints.

#### Interview answer

Liveness answers "should Kubernetes restart this process?" Readiness answers "should this instance receive traffic?" A temporary database outage should often make readiness fail for endpoints that require the database, but not necessarily liveness, because restarts will not fix the database.

These probes should be designed separately.

#### Deep dive

Startup probes can also be used when initialization is slow, preventing liveness from killing a slow-starting app.

#### Production angle

Wrong liveness checks can create cascading restarts during dependency incidents.

#### Traps / caveats

- Liveness should not depend on every downstream service.
- Readiness should fail during graceful shutdown before the process exits.
- Probe timeouts and thresholds matter.

#### Optional Anki

Q: What happens when readiness fails?
A: The instance is removed from traffic routing.

</details>

<a id="sp-obs-004"></a>

<details>
<summary><strong>SP-OBS-004. What are metrics in Spring Boot, and what is Micrometer?</strong></summary>

#### Short answer

Metrics are numeric measurements of application behavior; Micrometer is the metrics facade Spring Boot uses to publish them to monitoring systems.

#### Interview answer

Spring Boot collects metrics for HTTP requests, JVM, system, data sources, caches and more. Micrometer provides a common API and registry model so metrics can be exported to systems like Prometheus, Datadog or others.

Applications can also define custom counters, timers and gauges.

#### Deep dive

Metric names, tags and cardinality matter. Bad tags can overload monitoring systems.

#### Production angle

Metrics power dashboards and alerts for latency, error rate, throughput, pool usage and resource saturation.

#### Traps / caveats

- High-cardinality tags such as user ID are dangerous.
- Averages hide p95/p99 latency.
- Custom metrics need clear ownership and alert thresholds.

#### Optional Anki

Q: What is Micrometer?
A: A metrics facade used by Spring Boot.

</details>

<a id="sp-obs-005"></a>

<details>
<summary><strong>SP-OBS-005. What are traces, spans, correlation IDs and trace IDs?</strong></summary>

#### Short answer

A trace follows one request across services, spans represent operations inside it, and IDs correlate logs and telemetry.

#### Interview answer

A distributed trace is a tree or graph of spans representing work done for one request. Each span has timing and metadata. A trace ID identifies the full trace; span IDs identify operations. Correlation IDs or request IDs help connect logs, metrics and traces.

Spring Boot can integrate tracing with Micrometer observation and tracing bridges.

#### Deep dive

Trace context must be propagated through HTTP, messaging and async boundaries.

#### Production angle

Traces are essential for debugging latency in microservices because they show which dependency or operation consumed time.

#### Traps / caveats

- Sampling can hide rare slow requests.
- Do not put secrets or high-cardinality data into span tags.
- Async context propagation must be configured.

#### Optional Anki

Q: What does a trace ID identify?
A: One end-to-end distributed trace.

</details>

<a id="sp-obs-006"></a>

<details>
<summary><strong>SP-OBS-006. How does Spring Boot integrate with Prometheus and Grafana?</strong></summary>

#### Short answer

Boot exposes Micrometer metrics through a Prometheus endpoint, and Grafana visualizes metrics scraped by Prometheus.

#### Interview answer

With Actuator and the Prometheus registry, Spring Boot can expose metrics at an endpoint such as `/actuator/prometheus`. Prometheus scrapes that endpoint and stores time series. Grafana queries Prometheus to build dashboards.

The application should define useful tags and avoid high cardinality.

#### Deep dive

Prometheus is pull-based. Kubernetes service discovery is often used to find scrape targets.

#### Production angle

This setup supports alerting on latency, errors, saturation, JVM memory, GC, thread pools and connection pools.

#### Traps / caveats

- Exposing Prometheus publicly can leak internals.
- Too many tag values can overload Prometheus.
- Metrics need labels that support useful aggregation.

#### Optional Anki

Q: Which Actuator endpoint commonly exposes Prometheus metrics?
A: `/actuator/prometheus`.

</details>

<a id="sp-obs-007"></a>

<details>
<summary><strong>SP-OBS-007. How do you expose or restrict Actuator endpoints?</strong></summary>

#### Short answer

Configure endpoint exposure properties and secure access with Spring Security, network policy or a separate management port.

#### Interview answer

Boot controls which endpoints are exposed over HTTP or JMX through management properties. Security then controls who can access them. Many teams expose health/readiness internally while restricting diagnostics like env, beans, mappings, heapdump and loggers.

Management endpoints can also run on a separate port.

#### Deep dive

Endpoint availability, exposure and authorization are separate decisions.

#### Production angle

Operational endpoints are powerful and must be treated as internal administrative APIs.

#### Traps / caveats

- Do not expose `env`, `heapdump` or `logfile` publicly.
- A separate port still needs network controls.
- Health details may reveal dependency topology.

#### Optional Anki

Q: Are Actuator exposure and security the same thing?
A: No, exposure makes endpoints available; security restricts access.

</details>

<a id="sp-obs-008"></a>

<details>
<summary><strong>SP-OBS-008. How do you implement a custom HealthIndicator?</strong></summary>

#### Short answer

Create a bean implementing `HealthIndicator` or related health contributor APIs and return status/details based on a bounded check.

#### Interview answer

A custom `HealthIndicator` reports health for application-specific components such as a required downstream service, queue, cache or internal state. The check should be fast, bounded by timeouts and safe under repeated probing.

Expose only details that are safe for the audience.

#### Deep dive

Health groups can separate liveness and readiness contributors so not every check affects every probe.

#### Production angle

Custom health checks should reflect real serving ability without causing dependency overload.

#### Traps / caveats

- Do not perform expensive queries in health checks.
- Do not use liveness for dependency health.
- Health checks need their own timeouts.

#### Optional Anki

Q: What should a health check always be?
A: Fast, bounded and safe to call repeatedly.

</details>

<a id="sp-obs-009"></a>

<details>
<summary><strong>SP-OBS-009. How do you create custom metrics?</strong></summary>

#### Short answer

Use Micrometer's `MeterRegistry` to create counters, timers, gauges or distribution summaries with controlled tags.

#### Interview answer

Custom metrics should represent business or technical signals that operators need. Use counters for events, timers for durations and gauges for current values. Tags should be low-cardinality, such as dependency name or result category, not user ID or request ID.

Define metrics close to the behavior they measure.

#### Deep dive

Spring annotations and observation APIs can also instrument methods, but explicit metrics are often clearer for business events.

#### Production angle

Good metrics support alerting and capacity planning, not just dashboard decoration.

#### Traps / caveats

- High-cardinality tags are a common monitoring incident.
- Gauges need stable object references.
- Metrics without documentation are hard to use.

#### Optional Anki

Q: Which Micrometer type measures duration?
A: `Timer`.

</details>

<a id="sp-obs-010"></a>

<details>
<summary><strong>SP-OBS-010. How can you change logging levels at runtime?</strong></summary>

#### Short answer

Spring Boot Actuator can expose a `loggers` endpoint to view and change logger levels at runtime.

#### Interview answer

With Actuator loggers enabled and secured, operators can inspect logger levels and temporarily change a package or class to DEBUG or TRACE. This helps diagnose production issues without redeploying.

Changes should be temporary and controlled because verbose logs can be expensive or sensitive.

#### Deep dive

Runtime logging changes affect the running instance. In multiple replicas, changes may need to be applied consistently or only to one diagnostic instance.

#### Production angle

Dynamic log levels are useful during incidents, but they need audit and rollback discipline.

#### Traps / caveats

- TRACE logs can expose secrets or huge volumes.
- Restart may reset runtime changes.
- Do not expose the loggers endpoint publicly.

#### Optional Anki

Q: Which Actuator endpoint changes log levels?
A: `loggers`.

</details>

<a id="sp-obs-011"></a>

<details>
<summary><strong>SP-OBS-011. How would you debug a slow endpoint using logs, metrics and traces?</strong></summary>

#### Short answer

Use metrics to identify scope and trend, traces to locate the slow span, and logs to explain the exact failure path.

#### Interview answer

I would start with endpoint latency metrics by status and percentile. Then inspect traces for slow requests to see whether time is spent in controller logic, database queries, HTTP clients, locks or serialization. Logs with correlation IDs help explain errors or unusual branches.

If needed, add targeted diagnostics such as SQL timings or thread dumps.

#### Deep dive

Each signal answers a different question: metrics say how often and how bad, traces say where time went, logs say what happened.

#### Production angle

This avoids guessing and helps decide whether to optimize code, database, downstream calls or infrastructure.

#### Traps / caveats

- Logs alone rarely show latency distribution.
- Traces may be sampled.
- Missing correlation IDs make cross-signal debugging harder.

#### Optional Anki

Q: What do traces show in slow endpoint debugging?
A: Where time was spent across spans.

</details>

<a id="sp-obs-012"></a>

<details>
<summary><strong>SP-OBS-012. How would you monitor database connection pool usage, HTTP client failures and latency in Spring Boot?</strong></summary>

#### Short answer

Use Micrometer metrics, dependency-specific tags, traces and alerts for saturation, latency, error rate and timeout/retry volume.

#### Interview answer

For HikariCP, monitor active, idle, pending and max connections, plus acquisition timeouts. For HTTP clients, monitor request count, latency, status, exceptions, timeouts, retries and circuit breaker state. Traces should identify which dependency is slow.

Alert on symptoms that indicate user impact or imminent saturation.

#### Deep dive

Metrics should be split by dependency or pool name, but tag values must remain bounded.

#### Production angle

These signals reveal dependency degradation before the whole service fails.

#### Traps / caveats

- Pool usage without database metrics gives incomplete diagnosis.
- Retried calls can hide original failure rate.
- High-cardinality URI tags can break metrics storage.

#### Optional Anki

Q: Key Hikari metric to watch for pool pressure?
A: Pending threads/connection acquisition waiting plus active usage near max.

</details>

<details>
<summary><strong>SP-OBS-013. What are the risks of exposing operational endpoints publicly?</strong></summary>

#### Short answer

Operational endpoints can reveal internals, configuration, metrics, dependencies, logs, memory dumps or allow runtime changes.

#### Interview answer

Actuator endpoints are administrative surfaces. If exposed publicly, they can leak service topology, environment data, bean names, mappings, dependencies, logs or heap dumps. Some endpoints can also change runtime state, such as log levels or shutdown if enabled.

They should be restricted by authentication, network controls and minimal exposure.

#### Deep dive

Even "read-only" operational data can help attackers map systems or find vulnerable components.

#### Production angle

Public operational endpoints are a common security and compliance risk.

#### Traps / caveats

- Health details can reveal dependency names.
- Heap dumps can contain secrets and PII.
- Internal-only endpoints still need network policy and access control.

#### Optional Anki

Q: Why is exposing heapdump dangerous?
A: It can contain secrets, tokens and personal data.

</details>
