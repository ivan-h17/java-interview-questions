# 16.09. Configuration, properties and profiles

---

<a id="sp-conf-001"></a>

<details>
<summary><strong>SP-CONF-001. What are profiles in Spring, and how can you activate them?</strong></summary>

#### Short answer

Profiles are named environment labels that conditionally enable beans and configuration. They can be activated through properties, environment variables, command-line arguments or tests.

#### Interview answer

Spring profiles let the application choose configuration for environments or modes, such as `local`, `test` or `prod`. Beans annotated with `@Profile` are active only when matching profiles are active. Spring Boot can also load profile-specific configuration files.

Profiles can be activated with `spring.profiles.active`, environment variables, command-line arguments or test annotations.

#### Deep dive

Profiles are best for coarse environment differences, not for every feature switch or customer-specific behavior.

#### Production angle

Incorrect active profiles can connect to wrong services, enable unsafe defaults or disable production security.

#### Traps / caveats

- Profile explosion makes behavior hard to predict.
- Profiles should not be used as a secrets mechanism.
- Default profiles can surprise tests and local runs.

#### Optional Anki

Q: What property commonly activates Spring profiles?
A: `spring.profiles.active`.

</details>

<details>
<summary><strong>SP-CONF-002. What is externalized configuration in Spring Boot?</strong></summary>

#### Short answer

Externalized configuration means settings come from outside the code, such as files, environment variables, command-line arguments, config servers or secret stores.

#### Interview answer

Spring Boot lets the same artifact run in different environments by reading configuration from multiple property sources. Values can come from `application.yml`, profile-specific files, environment variables, command-line arguments, Kubernetes config maps, secrets or external config systems.

This keeps code immutable while deployment settings vary.

#### Deep dive

Externalized configuration is resolved into the Spring `Environment`, then consumed by `@Value`, `@ConfigurationProperties`, conditions and auto-configuration.

#### Production angle

This is essential for twelve-factor style deployments: build once, deploy with environment-specific configuration.

#### Traps / caveats

- Property precedence can override values unexpectedly.
- Secrets should not be committed in config files.
- Config changes need rollout and validation strategy.

#### Optional Anki

Q: Why externalize configuration?
A: To run the same artifact with different environment-specific settings.

</details>

<a id="sp-conf-003"></a>

<details>
<summary><strong>SP-CONF-003. What is property source precedence in Spring Boot?</strong></summary>

#### Short answer

When the same property exists in multiple places, Boot applies a defined precedence order to decide which value wins.

#### Interview answer

Spring Boot collects properties from many sources: defaults, config files, profile files, environment variables, system properties, command-line arguments and test properties. Higher-precedence sources override lower-precedence ones.

In practice, command-line and environment-specific sources often override packaged config.

#### Deep dive

The exact order can vary by Boot version and source type, so for precise debugging use the Environment/Actuator diagnostics rather than memory.

#### Production angle

Wrong precedence explains many incidents where the value in `application.yml` is not the value used at runtime.

#### Traps / caveats

- Environment variables can override file values.
- Test annotations can override production-like config in tests.
- Actuator `env` must be secured because it can reveal sensitive keys or values.

#### Optional Anki

Q: What happens when the same property appears in multiple sources?
A: The highest-precedence source wins.

</details>

<a id="sp-conf-004"></a>

<details>
<summary><strong>SP-CONF-004. What is the difference between @Value and @ConfigurationProperties?</strong></summary>

#### Short answer

`@Value` injects individual values; `@ConfigurationProperties` binds a structured group of properties to a typed object.

#### Interview answer

`@Value` is convenient for one-off simple values. `@ConfigurationProperties` is better for structured configuration such as client timeouts, pool settings, feature groups or nested credentials because it supports type-safe binding, validation, metadata and grouping.

For production configuration, I prefer `@ConfigurationProperties` for anything more than a trivial scalar.

#### Deep dive

Configuration properties can be immutable with constructor binding or records in modern Spring Boot styles.

#### Production angle

Typed, validated configuration catches bad values at startup instead of failing later under traffic.

#### Traps / caveats

- `@Value` string expressions can become scattered and hard to validate.
- Binding can fail if property names or types are wrong.
- Do not log configuration objects containing secrets.

#### Optional Anki

Q: Which annotation is better for structured config?
A: `@ConfigurationProperties`.

</details>

<a id="sp-conf-005"></a>

<details>
<summary><strong>SP-CONF-005. How can you validate configuration properties, and what is relaxed binding?</strong></summary>

#### Short answer

Use Bean Validation on `@ConfigurationProperties` classes; relaxed binding maps property names across formats like kebab-case, camelCase and environment variables.

#### Interview answer

A configuration properties class can be annotated with validation constraints and `@Validated`. Spring Boot then fails startup if required values are missing or invalid. Relaxed binding lets `my.service.base-url`, `my.service.baseUrl` and environment-variable style names map to the same Java property.

This makes configuration ergonomic while preserving type safety.

#### Deep dive

Validation is especially useful for timeouts, URLs, pool sizes, limits and feature configuration.

#### Production angle

Failing fast on invalid config is better than accepting bad values and failing during a real request.

#### Traps / caveats

- Relaxed binding does not mean every typo is accepted.
- Validation must be enabled/configured correctly.
- Defaults should be explicit when production behavior depends on them.

#### Optional Anki

Q: What is relaxed binding?
A: Flexible mapping from external property names to Java property names.

</details>

<a id="sp-conf-006"></a>

<details>
<summary><strong>🧠 SP-CONF-006. What is config data import?</strong></summary>

#### Short answer

Config data import lets Spring Boot import additional configuration sources through `spring.config.import`.

#### Interview answer

`spring.config.import` is used to load configuration from extra locations or systems, such as files, config trees or external configuration providers. It is part of Boot's config data processing and can participate in profile and property resolution.

It is useful when configuration comes from mounted secrets, config servers or environment-specific locations.

#### Deep dive

Imports can be optional or required depending on syntax. A missing required import can fail startup.

#### Production angle

Config imports are common in Kubernetes and centralized configuration setups, where values are mounted or fetched outside the packaged jar.

#### Traps / caveats

- A missing required import can prevent startup.
- Import order and precedence matter.
- External config systems need availability and rollback planning.

#### Optional Anki

Q: Property used for Boot config imports?
A: `spring.config.import`.

</details>

<a id="sp-conf-007"></a>

<details>
<summary><strong>SP-CONF-007. How do environment variables map to Spring Boot properties?</strong></summary>

#### Short answer

Spring Boot relaxed binding maps environment-variable style names to property names, commonly uppercase with underscores.

#### Interview answer

A property such as `my.service.base-url` can be supplied as an environment variable like `MY_SERVICE_BASE_URL`. Boot normalizes many naming formats through relaxed binding.

This is useful in containers, where environment variables are a common configuration mechanism.

#### Deep dive

Lists and maps can require special syntax, and exact behavior can be more subtle than simple scalar properties.

#### Production angle

Environment variables are easy to inject but can be hard to audit and may expose secrets through process or platform tooling.

#### Traps / caveats

- Typos create missing or default values.
- Case and underscore mapping can be confusing for nested structures.
- Secrets in environment variables may be visible to tooling depending on platform.

#### Optional Anki

Q: Environment variable form for `my.service.base-url`?
A: Commonly `MY_SERVICE_BASE_URL`.

</details>

<a id="sp-conf-008"></a>

<details>
<summary><strong>SP-CONF-008. How would you manage configuration across local, test, staging and production environments?</strong></summary>

#### Short answer

Keep defaults safe, externalize environment-specific values, validate typed properties and minimize profile-specific branching.

#### Interview answer

I would keep non-secret defaults in versioned config, supply environment-specific values through deployment configuration, and store secrets in a secret manager or platform secret mechanism. Typed `@ConfigurationProperties` with validation catches invalid settings.

Profiles can separate broad modes, but feature behavior should usually use explicit feature flags or properties.

#### Deep dive

Configuration should be reviewable and reproducible. Staging should be close enough to production to catch config issues.

#### Production angle

Safe config management includes rollout, rollback, auditing, ownership and monitoring after changes.

#### Traps / caveats

- Do not let local defaults accidentally work in production.
- Avoid one-off profile branches that nobody tests.
- Configuration changes can be as risky as code changes.

#### Optional Anki

Q: Good default for production-sensitive configuration?
A: Typed, externalized and validated.

</details>

<a id="sp-conf-009"></a>

<details>
<summary><strong>SP-CONF-009. How should secrets be handled in Spring Boot applications?</strong></summary>

#### Short answer

Store secrets outside code and images, inject them securely at runtime, restrict access and avoid logging them.

#### Interview answer

Secrets should live in a secret manager, Kubernetes secrets, Vault-like system or managed cloud secret service. The app reads them through environment/config integration. They should not be committed to Git, baked into Docker images or printed in logs.

Rotation should be planned, and access should follow least privilege.

#### Deep dive

Spring Boot can consume secrets like other configuration, but operational controls determine whether that is safe.

#### Production angle

Secret leakage requires incident response: revoke, rotate, audit access and prevent recurrence.

#### Traps / caveats

- Mask Actuator `env` and logs.
- Do not put secrets in error messages or trace tags.
- Environment variables are convenient but may not be the safest option everywhere.

#### Optional Anki

Q: Where should production secrets not be stored?
A: Git repositories or container images.

</details>

<details>
<summary><strong>SP-CONF-010. What are the risks of profile explosion, and when should you prefer feature flags?</strong></summary>

#### Short answer

Too many profiles create untested configuration combinations; feature flags are better for runtime behavior switches and gradual rollout.

#### Interview answer

Profiles are good for broad environment differences. If every feature, customer or rollout gets a profile, the number of combinations becomes impossible to reason about. Feature flags are better for enabling behavior gradually, targeting cohorts or turning features off without redeploying.

Configuration should make behavior explicit and testable.

#### Deep dive

Profiles are mostly startup-time selection. Feature flags can be runtime-managed, audited and rolled out progressively.

#### Production angle

Feature flags help reduce deployment risk, but stale flags need cleanup.

#### Traps / caveats

- Flags are not a substitute for authorization.
- Too many flags can become their own complexity.
- Critical flags need monitoring and ownership.

#### Optional Anki

Q: When are feature flags better than profiles?
A: Runtime rollout, targeting and kill-switch behavior.

</details>

<a id="sp-conf-011"></a>

<details>
<summary><strong>SP-CONF-011. How would you debug and prevent a production incident caused by a wrong property value?</strong></summary>

#### Short answer

Find the effective runtime value and its source, compare deployments, add validation/tests, and improve config review and rollout controls.

#### Interview answer

I would inspect the effective value through safe diagnostics, logs, config management history or Actuator if secured. Then I would identify the property source that won precedence: environment variable, command line, config map, secret, profile file or default.

Prevention means typed validation, safer defaults, config diff review, staging parity, canary rollout and alerts around behavior affected by the property.

#### Deep dive

Do not rely only on the value in the repository. The deployed value may come from platform configuration.

#### Production angle

Config incidents need the same post-incident discipline as code bugs: root cause, blast-radius reduction and automated guardrails.

#### Traps / caveats

- Actuator diagnostics can expose secrets if not secured.
- A rollback of code may not roll back config.
- Multiple active profiles can produce surprising overrides.

#### Optional Anki

Q: First step in debugging wrong Spring property behavior?
A: Determine the effective runtime value and which property source supplied it.

</details>
