# 16.17. Production readiness, performance and deployment

---

<a id="sp-prod-001"></a>

<details>
<summary><strong>SP-PROD-001. How would you make a Spring Boot service production-ready?</strong></summary>

#### Short answer

Configure health/readiness, metrics, logs, tracing, timeouts, pools, security, externalized config, graceful shutdown and safe deployment practices.

#### Interview answer

A production-ready Boot service needs more than working endpoints. I would configure Actuator health/readiness, metrics and tracing, structured logs with correlation IDs, secure endpoints, validated configuration, database migrations, HTTP timeouts, connection pools, thread pools, graceful shutdown and resource limits.

I would also add tests, dashboards, alerts and runbooks for common failures.

#### Deep dive

Production readiness is about operability: can the team detect, diagnose, mitigate and safely change the service?

#### Production angle

The goal is predictable behavior during deploys, dependency failures, traffic spikes and incidents.

#### Traps / caveats

- A service can pass functional tests and still be operationally unsafe.
- Defaults should be reviewed, especially security and timeouts.
- Observability without alerts and ownership is incomplete.

#### Optional Anki

Q: Production readiness is mostly about what?
A: Operability, safety and predictable behavior under real conditions.

</details>

<a id="sp-prod-002"></a>

<details>
<summary><strong>SP-PROD-002. What is graceful shutdown in Spring Boot, and how do you configure its timeout?</strong></summary>

#### Short answer

Graceful shutdown lets the server stop accepting new requests and finish in-flight work before the process exits, within a configured timeout.

#### Interview answer

Spring Boot can coordinate graceful shutdown for supported web servers. During shutdown, the app stops accepting new requests, waits for active requests to complete, closes the context and invokes lifecycle/destruction callbacks. The graceful shutdown period is controlled with Boot lifecycle/server properties depending on version and server.

The timeout must fit the platform termination grace period.

#### Deep dive

Background workers, schedulers and message listeners need their own shutdown behavior too.

#### Production angle

Graceful shutdown reduces failed requests, duplicate processing and half-completed work during deploys.

#### Traps / caveats

- Kubernetes may kill the process after its termination grace period.
- Readiness should fail before shutdown completes.
- Long requests may still be terminated if timeout expires.

#### Optional Anki

Q: What should happen to readiness during shutdown?
A: It should stop receiving new traffic.

</details>

<a id="sp-prod-003"></a>

<details>
<summary><strong>SP-PROD-003. Why are readiness probes important during deployments?</strong></summary>

#### Short answer

Readiness probes prevent traffic from being sent to instances that are starting, shutting down or unable to serve real requests.

#### Interview answer

During rolling deployments, a pod may be running but not ready: beans may still initialize, migrations may be running, caches may be cold, or shutdown may have started. Readiness tells the platform whether to route traffic to that instance.

Good readiness checks reduce 503s and startup/shutdown races.

#### Deep dive

Readiness should represent serving ability, not just process existence.

#### Production angle

Incorrect readiness is a common cause of deployment-related errors.

#### Traps / caveats

- Do not make readiness so strict that every dependency blip removes all pods.
- Do not make it so shallow that unready instances receive traffic.
- Probe thresholds and delays matter.

#### Optional Anki

Q: What does readiness protect during deploys?
A: Traffic routing to instances that can actually serve.

</details>

<a id="sp-prod-004"></a>

<details>
<summary><strong>SP-PROD-004. How can improper shutdown cause data loss or duplicate processing?</strong></summary>

#### Short answer

If the app stops mid-request, mid-message or mid-scheduled job without coordination, work may be lost, partially committed or retried.

#### Interview answer

Improper shutdown can kill in-flight HTTP requests, stop message consumers before acknowledgments, interrupt scheduled jobs or terminate async tasks. Depending on transaction and acknowledgment timing, that can lose work or cause duplicates after retry.

Design work to be idempotent and coordinate shutdown of consumers and executors.

#### Deep dive

Exactly-once behavior is rare. Most production designs assume at-least-once processing and enforce idempotency.

#### Production angle

Graceful shutdown, readiness draining and durable state transitions reduce deployment-related incidents.

#### Traps / caveats

- Acknowledging a message before committing data can lose work.
- Committing data before acknowledging can cause duplicates.
- In-memory queues are vulnerable during process termination.

#### Optional Anki

Q: Key design property for retryable background work?
A: Idempotency.

</details>

<a id="sp-prod-005"></a>

<details>
<summary><strong>SP-PROD-005. How do you configure thread pools, task execution and scheduling in Spring Boot?</strong></summary>

#### Short answer

Configure Boot task execution/scheduling properties or explicit `Executor` and `TaskScheduler` beans with bounded pools and queues.

#### Interview answer

Spring Boot auto-configures task executors and schedulers, but production workloads should define sizes, queues, thread names and rejection policies deliberately. Async work, scheduled jobs and application-specific background tasks may need separate pools.

Thread names and metrics help diagnose saturation.

#### Deep dive

CPU-bound work and I/O-bound work need different sizing. Large queues increase latency and hide overload.

#### Production angle

Poor executor configuration causes request latency, dropped tasks or memory pressure.

#### Traps / caveats

- Do not run blocking work on event loop threads.
- Do not share one pool for unrelated critical workloads.
- Monitor queue depth and rejected tasks.

#### Optional Anki

Q: Why are bounded queues important?
A: They expose overload instead of hiding it until memory or latency collapses.

</details>

<a id="sp-prod-006"></a>

<details>
<summary><strong>SP-PROD-006. How does Spring Boot support virtual threads?</strong></summary>

#### Short answer

Modern Spring Boot can use Java virtual threads for request handling and task execution when running on Java 21+ and configured with `spring.threads.virtual.enabled=true`.

#### Interview answer

With Java 21 or later, Spring Boot can configure parts of the application to use virtual threads, especially for blocking-style workloads. Virtual threads allow many concurrent blocking operations with lower thread overhead than platform threads.

They do not make blocking dependencies faster, but they reduce the cost of waiting.

#### Deep dive

Virtual threads work best when code blocks in JDK-friendly ways and does not pin carrier threads for long periods. When virtual threads are enabled, ordinary thread-pool sizing properties may no longer control those executors the same way, so configuration must be reviewed.

#### Production angle

They can improve concurrency for I/O-heavy services, but you still need timeouts, pools for external resources and database connection limits.

#### Traps / caveats

- Database connections remain limited.
- CPU-bound work does not become cheaper.
- Thread-local heavy code and pinning need attention.
- Background tasks may need keep-alive configuration if only daemon virtual threads remain.

#### Optional Anki

Q: What do virtual threads reduce?
A: The overhead of many concurrent blocking threads.

</details>

<a id="sp-prod-007"></a>

<details>
<summary><strong>SP-PROD-007. When are virtual threads a good fit in Spring Boot, and when are they not?</strong></summary>

#### Short answer

They fit blocking I/O-heavy workloads with many concurrent waits; they are less useful for CPU-heavy work or resource bottlenecks like database pools.

#### Interview answer

Virtual threads are attractive for servlet-style applications that make many blocking calls to databases or HTTP services. They let the app handle many concurrent waiting tasks without huge platform thread pools.

They do not solve slow databases, missing timeouts, CPU saturation or limited connection pools.

#### Deep dive

Measure under realistic load. The bottleneck may move from threads to connections, downstream systems or CPU.

#### Production angle

After enabling virtual threads, monitor DB pool usage, downstream latency, CPU and memory because concurrency can increase pressure elsewhere.

#### Traps / caveats

- More concurrency can overload dependencies.
- Some synchronized/native blocking can pin carrier threads.
- Debugging thread dumps looks different with many virtual threads.

#### Optional Anki

Q: Do virtual threads remove the need for database pool limits?
A: No.

</details>

<a id="sp-prod-008"></a>

<details>
<summary><strong>SP-PROD-008. How do you tune HikariCP and detect connection pool exhaustion?</strong></summary>

#### Short answer

Set pool size and timeouts based on database capacity and workload, then monitor active, idle, pending and timeout metrics.

#### Interview answer

HikariCP tuning starts with understanding request concurrency, transaction duration and database limits. Set maximum pool size, connection timeout, idle/lifetime settings and leak detection carefully. Detect exhaustion with metrics: active connections near max, pending threads, acquisition timeouts and long transaction traces.

Fix root causes before increasing pool size.

#### Deep dive

A smaller, well-sized pool often protects the database better than a large pool that allows too much concurrent SQL.

#### Production angle

Pool exhaustion often points to slow queries, long transactions, remote calls inside transactions or leaked connections.

#### Traps / caveats

- Bigger pool can make database saturation worse.
- `REQUIRES_NEW` can need extra connections.
- Connection leak detection is diagnostic, not a cure.

#### Optional Anki

Q: First question before increasing Hikari max pool size?
A: Why are connections held so long?

</details>

<a id="sp-prod-009"></a>

<details>
<summary><strong>SP-PROD-009. How would you reduce Spring Boot startup time?</strong></summary>

#### Short answer

Measure startup, remove unnecessary beans/work, narrow scanning, avoid heavy initialization, tune lazy/AOT options and review auto-configuration.

#### Interview answer

I would first measure startup with Boot startup diagnostics, logs or profiling. Then I would remove unnecessary starters, reduce broad component scanning, avoid remote calls in initialization, defer non-critical work, optimize migrations and check expensive bean creation.

Lazy initialization, AOT processing or native images may help in specific cases.

#### Deep dive

Do not optimize blindly. Startup time may be dominated by classpath scanning, bean initialization, migrations, JPA metamodel building or external checks.

#### Production angle

Faster startup improves scaling, deploy speed and recovery.

#### Traps / caveats

- Lazy initialization can move failures to first request.
- Skipping validation can make startup fast but unsafe.
- Native images trade startup for build complexity and runtime limitations.

#### Optional Anki

Q: First step in startup optimization?
A: Measure where startup time is spent.

</details>

<a id="sp-prod-010"></a>

<details>
<summary><strong>🧠 SP-PROD-010. What is Spring AOT processing?</strong></summary>

#### Short answer

Spring AOT analyzes the application ahead of time and generates optimized code and metadata for startup and native-image compatibility.

#### Interview answer

Ahead-of-time processing inspects the application context, bean definitions and framework usage at build time. It can generate code and hints that reduce runtime reflection and improve startup. It is especially important for GraalVM native images.

AOT changes some assumptions because more is determined at build time.

#### Deep dive

Dynamic runtime behavior may need explicit runtime hints for reflection, resources or proxies.

#### Production angle

AOT can improve startup and memory profile but adds build-time complexity and requires compatibility testing.

#### Traps / caveats

- Reflection-heavy libraries may need hints.
- Dynamic bean registration can be harder.
- Native/AOT builds need their own CI coverage.

#### Optional Anki

Q: Why is AOT important for native images?
A: It generates metadata and code needed when runtime reflection is limited.

</details>

<a id="sp-prod-011"></a>

<details>
<summary><strong>🧠 SP-PROD-011. What are GraalVM native images, and when are they useful for Spring Boot?</strong></summary>

#### Short answer

Native images compile the app ahead of time into a native executable with fast startup and often lower memory, at the cost of build complexity and runtime constraints.

#### Interview answer

GraalVM native images can make Spring Boot apps start very quickly and use less memory. They are useful for serverless, CLI tools, short-lived jobs, scale-to-zero platforms or memory-constrained services.

They are less compelling for long-running services where throughput, compatibility and build simplicity matter more.

#### Deep dive

Native images close the world at build time, so reflection, proxies, resources and dynamic class loading need metadata.

#### Production angle

Native images need dedicated performance, compatibility and observability validation before adoption.

#### Traps / caveats

- Build times are longer.
- Some libraries are incompatible or need hints.
- Peak throughput may differ from JVM JIT behavior.

#### Optional Anki

Q: Main native image benefit?
A: Fast startup and often lower memory usage.

</details>

<a id="sp-prod-012"></a>

<details>
<summary><strong>🧠 SP-PROD-012. What are common limitations of native images for reflection-heavy frameworks?</strong></summary>

#### Short answer

Reflection, dynamic proxies, resource loading, serialization and dynamic class loading need build-time metadata or may fail.

#### Interview answer

Frameworks often discover classes and call constructors or methods reflectively. Native images need to know this ahead of time. If hints are missing, code may compile but fail at runtime when a class, constructor, proxy or resource is unavailable.

Spring AOT supplies many hints, but application and library-specific cases remain.

#### Deep dive

Serialization libraries, JDBC drivers, security providers and dynamic plugin systems are common places to check.

#### Production angle

Native image incidents can be subtle because runtime behavior differs from the JVM version.

#### Traps / caveats

- Passing tests on JVM does not guarantee native image behavior.
- Reflection config should be minimal and tested.
- Dynamic loading patterns may be unsuitable for native images.

#### Optional Anki

Q: What does native image closed-world analysis affect?
A: Reflection, proxies, resources and dynamic loading.

</details>

<details>
<summary><strong>SP-PROD-013. How do you externalize configuration and handle secrets safely in containers and Kubernetes?</strong></summary>

#### Short answer

Use config maps or environment/config files for non-secrets, secret stores for secrets, validate properties and restrict access.

#### Interview answer

In containers, the image should not contain environment-specific config or secrets. Kubernetes config maps can provide non-sensitive configuration; secrets or external secret managers provide sensitive values. Spring Boot reads these through environment variables, mounted files or config imports.

Typed validation should fail fast on missing or invalid values.

#### Deep dive

Mounted secret files can be safer than environment variables in some platforms, but rotation and reload behavior must be designed.

#### Production angle

Safe config handling includes rotation, audit, least privilege and no secret logging.

#### Traps / caveats

- Do not bake secrets into images.
- Do not expose secrets via Actuator `env`.
- Config rollback must be coordinated with code rollback.

#### Optional Anki

Q: Should container images contain production secrets?
A: No.

</details>

<details>
<summary><strong>🧠 SP-PROD-014. How do you plan Spring Boot version upgrades and check for breaking changes?</strong></summary>

#### Short answer

Read official migration notes, update dependencies deliberately, run full tests, check deprecations, verify config changes and deploy gradually.

#### Interview answer

For Boot upgrades, I review release notes and migration guides, align Java and Spring Framework versions, update dependencies and plugins, check deprecated APIs/properties, run unit/integration/native if applicable tests, and verify observability/security behavior.

For major upgrades, I plan incremental steps and canary deployment.

#### Deep dive

Spring Boot upgrades can affect auto-configuration, dependency versions, property names, security defaults, test annotations and Jakarta namespace compatibility.

#### Production angle

Upgrades reduce security and maintenance risk, but they should be treated as production changes with rollback plans.

#### Traps / caveats

- Transitive dependency upgrades can change runtime behavior.
- Tests using deprecated mock annotations may break.
- Configuration properties may be renamed or removed.

#### Optional Anki

Q: First source for Boot upgrade planning?
A: Official release notes and migration guide.

</details>

<details>
<summary><strong>SP-PROD-015. How would you diagnose high memory usage, high CPU usage or slow startup in a Spring Boot service?</strong></summary>

#### Short answer

Collect metrics and profiles targeted to the symptom: heap/GC for memory, CPU profiles/thread dumps for CPU, startup steps/logs/profiles for startup.

#### Interview answer

For memory, I check heap, RSS, GC, allocation rate, caches, buffers and heap dumps. For CPU, I use CPU metrics, thread dumps and profilers/JFR to identify hot methods or busy loops. For slow startup, I inspect startup logs, Boot startup diagnostics, bean creation, migrations, JPA initialization and external calls.

Always correlate with deployments and traffic changes.

#### Deep dive

Spring may be the visible app, but the root cause can be JVM, database, dependency, container limits or traffic.

#### Production angle

Evidence-driven diagnostics prevents random tuning and unsafe restarts.

#### Traps / caveats

- Heap is not total process memory.
- High CPU may be GC, JSON serialization, logging or busy retry loops.
- Startup slowness can come from external dependency checks.

#### Optional Anki

Q: What tool is useful for CPU and allocation timeline evidence?
A: JFR.

</details>
