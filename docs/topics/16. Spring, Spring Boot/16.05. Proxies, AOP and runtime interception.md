# 16.05. Proxies, AOP and runtime interception

---

<a id="sp-aop-001"></a>

<details>
<summary><strong>SP-AOP-001. What is a proxy in Spring, and when does Spring create one?</strong></summary>

#### Short answer

A proxy is an object that stands in front of a target bean and intercepts method calls to add behavior such as transactions, security, caching or async execution.

#### Interview answer

Spring creates proxies when infrastructure needs to apply cross-cutting behavior around a bean. For example, a `@Transactional` service may be wrapped in a proxy that opens and commits or rolls back a transaction around method execution.

Other beans usually inject the proxy, not the raw target. Calls through the proxy can be intercepted; calls inside the target object usually cannot.

#### Deep dive

Spring commonly uses JDK dynamic proxies for interfaces and class-based proxies for concrete classes. The proxy delegates to the target after running advice.

#### Production angle

Many "annotation does not work" incidents are really "the call did not go through the proxy" incidents.

#### Traps / caveats

- `this.method()` bypasses the proxy.
- Objects created with `new` are not proxied.
- Runtime class names in logs may show proxy classes, not only your target class.

#### Optional Anki

Q: What must happen for Spring AOP advice to apply?
A: The method call must go through the Spring proxy.

</details>

<a id="sp-aop-002"></a>

<details>
<summary><strong>SP-AOP-002. What are aspect, advice, pointcut and join point in Spring AOP?</strong></summary>

#### Short answer

An aspect groups cross-cutting logic, advice is the logic to run, a pointcut selects where it runs, and a join point is a matched method execution.

#### Interview answer

In Spring AOP, the join point is usually a method execution. A pointcut is an expression that matches method executions. Advice is code that runs before, after or around the method. An aspect combines pointcuts and advice into one cross-cutting module.

For example, transaction management has advice around service methods selected by transactional metadata.

#### Deep dive

Spring AOP is proxy-based and method-execution focused. It is not a full bytecode weaving model like AspectJ.

#### Production angle

Clear pointcuts matter because accidental matches can apply behavior to too much code or miss critical methods.

#### Traps / caveats

- Pointcuts that are too broad can slow or change unrelated code.
- Pointcuts that rely on package names can break after refactoring.
- Spring AOP cannot intercept every possible Java join point.

#### Optional Anki

Q: In Spring AOP, what is the usual join point?
A: A method execution.

</details>

<a id="sp-aop-003"></a>

<details>
<summary><strong>SP-AOP-003. What types of advice exist in Spring AOP?</strong></summary>

#### Short answer

Common advice types are before, after returning, after throwing, after finally and around advice.

#### Interview answer

Before advice runs before the method. After returning runs only on successful completion. After throwing runs when an exception is thrown. After advice runs in a finally-like way. Around advice wraps the call and can decide whether and when to proceed.

Around advice is the most powerful and the easiest to misuse.

#### Deep dive

Most framework features that need control over success, failure and timing use around-style interception.

#### Production angle

Advice is useful for logging, metrics, tracing, transactions and security, but it must preserve exception and return semantics.

#### Traps / caveats

- Around advice must call `proceed()` unless intentionally short-circuiting.
- Swallowing exceptions changes transaction and error behavior.
- Advice ordering can change outcomes.

#### Optional Anki

Q: Which advice type can control whether the target method is called?
A: Around advice.

</details>

<a id="sp-aop-004"></a>

<details>
<summary><strong>SP-AOP-004. What is the difference between JDK dynamic proxies and CGLIB proxies?</strong></summary>

#### Short answer

JDK proxies implement interfaces; CGLIB-style class proxies subclass the target class.

#### Interview answer

JDK dynamic proxies are based on interfaces. If a bean is injected through an interface, the proxy can implement that interface and delegate to the target. Class-based proxies subclass the concrete class and intercept overridable methods.

Spring can use either depending on configuration and whether interfaces exist.

#### Deep dive

Class-based proxies cannot override final methods and have trouble with final classes. Interface proxies expose only interface methods.

#### Production angle

Proxy type can affect casts, method visibility, final methods and where annotations are detected.

#### Traps / caveats

- `final` classes or methods cannot be advised by subclass-based proxies.
- Private methods cannot be intercepted by normal Spring AOP.
- Casting a JDK proxy to the concrete class fails.

#### Optional Anki

Q: What is the main limitation of JDK dynamic proxies?
A: They proxy interfaces, not concrete class methods.

</details>

<a id="sp-aop-005"></a>

<details>
<summary><strong>SP-AOP-005. What are the main limitations of proxy-based AOP, including final methods, private methods and self-invocation?</strong></summary>

#### Short answer

Proxy-based AOP only intercepts calls that go through the proxy and can only advise methods the proxy can expose or override.

#### Interview answer

Self-invocation bypasses the proxy because `this.someMethod()` calls the target object directly. Private methods are not externally callable and cannot be proxied this way. Final methods cannot be overridden by class-based proxies. Final classes cannot be subclass-proxied.

This is why annotations such as `@Transactional`, `@Cacheable`, `@Async` or method security may appear to do nothing.

#### Deep dive

AspectJ weaving can handle some cases that proxy mode cannot, but it adds complexity and is not the common Spring Boot default.

#### Production angle

These limitations commonly cause missing transactions, missing security checks, cache misses and async methods running synchronously.

#### Traps / caveats

- Making a method public is not enough if it is called internally.
- Annotating private methods is misleading.
- Tests that call methods directly on the target can miss proxy behavior.

#### Optional Anki

Q: Why does self-invocation bypass Spring AOP?
A: The call uses `this`, not the Spring proxy.

</details>

<a id="sp-aop-006"></a>

<details>
<summary><strong>SP-AOP-006. How can you inspect whether a bean is proxied?</strong></summary>

#### Short answer

Check the runtime class, use Spring AOP utilities, inspect logs/Actuator beans, or debug the bean creation and advisors.

#### Interview answer

At runtime, `bean.getClass()` often reveals proxy classes. Spring utilities such as `AopUtils.isAopProxy(bean)`, `isJdkDynamicProxy()` and `isCglibProxy()` can confirm it. You can also inspect the application context, Actuator `beans`, debug logs and auto-configuration reports.

For a specific feature, verify that the relevant advisor or post-processor is active.

#### Deep dive

If the bean implements `Advised`, you can inspect advisors, but that is diagnostic code, not business logic.

#### Production angle

Proxy inspection helps diagnose missing transactions, security, caching, metrics or async behavior.

#### Traps / caveats

- In tests, you might be looking at a mock or target instead of the real proxy.
- JDK proxies may not be assignable to the concrete implementation.
- A bean can be proxied more than once conceptually, though Spring often composes advisors into one proxy.

#### Optional Anki

Q: Utility class commonly used to check Spring AOP proxies?
A: `AopUtils`.

</details>

<a id="sp-aop-007"></a>

<details>
<summary><strong>SP-AOP-007. Which Spring features commonly rely on proxies?</strong></summary>

#### Short answer

Transactions, caching, method security, `@Async`, retry, some metrics/tracing integrations and custom AOP commonly use proxies.

#### Interview answer

When Spring adds behavior around a method call, proxies are often involved. `@Transactional` wraps methods in transaction advice. `@Cacheable` checks or updates caches. Method security checks authorization. `@Async` submits execution to an executor. Retry and custom aspects can also wrap calls.

The common rule is that the method must be called through the proxy.

#### Deep dive

Not all Spring behavior uses AOP proxies. MVC request mapping, message conversion and many lifecycle features use other mechanisms.

#### Production angle

Understanding proxy-based features helps troubleshoot why behavior differs between an external call and an internal method call.

#### Traps / caveats

- Multiple annotations on the same method can have order interactions.
- Annotation presence alone does not guarantee interception.
- Proxy features do not cross process or HTTP boundaries.

#### Optional Anki

Q: Name three Spring features commonly implemented with proxies.
A: Transactions, caching and method security.

</details>

<a id="sp-aop-008"></a>

<details>
<summary><strong>SP-AOP-008. How do transactions, security, caching and @Async relate to proxies?</strong></summary>

#### Short answer

They are commonly implemented as advice around proxied method calls.

#### Interview answer

When a proxied method is called, Spring can run transaction advice, security advice, cache advice or async advice before delegating. Transaction advice opens or joins a transaction. Security advice checks authorization. Cache advice checks/updates cache entries. Async advice submits work to an executor and returns immediately for supported return types.

If the call bypasses the proxy, the annotation may not apply.

#### Deep dive

Order matters. For example, async execution changes the thread, so transaction and security context assumptions must be reviewed carefully.

#### Production angle

Combining these features without understanding boundaries can cause lost security context, missing transactions or stale caches.

#### Traps / caveats

- `@Async` and `@Transactional` on the same method often surprise developers.
- Caching a method that is called internally may not cache.
- Method security is not a replacement for object-level authorization design.

#### Optional Anki

Q: Common root cause when `@Transactional` or `@Cacheable` appears not to work?
A: The call did not go through the proxy.

</details>

<a id="sp-aop-009"></a>

<details>
<summary><strong>🧠 SP-AOP-009. What is an advisor in Spring AOP?</strong></summary>

#### Short answer

An advisor combines advice with the pointcut or metadata that says where the advice applies.

#### Interview answer

In Spring AOP internals, an advisor is the object that tells the proxy what interceptor should run and for which methods. For example, transaction infrastructure creates advisors that match transactional methods and apply transaction interceptors.

Most application developers do not create advisors directly, but understanding them helps debug proxy behavior.

#### Deep dive

Auto-proxy creators inspect candidate advisors and decide whether a bean needs a proxy.

#### Production angle

If a method is not intercepted, one question is whether any advisor actually matches that method.

#### Traps / caveats

- Advice without a matching advisor/pointcut does nothing.
- Multiple advisors can apply to the same method.
- Advisor order affects nested behavior.

#### Optional Anki

Q: What does an advisor combine?
A: Advice plus matching metadata such as a pointcut.

</details>

<a id="sp-aop-010"></a>

<details>
<summary><strong>🧠 SP-AOP-010. How are multiple advices ordered?</strong></summary>

#### Short answer

Spring orders advices using `Ordered`, `@Order`, framework-defined precedence and advisor ordering rules.

#### Interview answer

When several advisors apply to one method, Spring builds an interceptor chain. Ordering determines which advice wraps the others. Lower order values usually have higher precedence and run earlier on the way in, then later on the way out.

Framework features such as transactions, security, caching and async can interact, so order can affect semantics.

#### Deep dive

Around advice behaves like nested calls. The outer advice enters first and exits last.

#### Production angle

Wrong ordering can affect whether metrics include transaction time, whether security runs before expensive work, or whether async changes the thread before another advice expects context.

#### Traps / caveats

- Do not rely on unspecified ordering.
- Around advice can hide or alter exceptions for later advice.
- Combining custom aspects with framework aspects needs tests.

#### Optional Anki

Q: In ordered around advice, which advice exits last?
A: The outer/highest-precedence advice.

</details>

<a id="sp-aop-011"></a>

<details>
<summary><strong>🧠 SP-AOP-011. What is the difference between Spring AOP and AspectJ?</strong></summary>

#### Short answer

Spring AOP is proxy-based and method-focused; AspectJ is a full aspect language that can weave bytecode at compile time or load time.

#### Interview answer

Spring AOP is simpler and integrated with Spring beans. It intercepts method calls that go through Spring proxies. AspectJ supports more join points, including field access, constructors and self-invocation cases, because it weaves aspects into bytecode.

For most Spring Boot services, proxy-based AOP is enough and easier to operate.

#### Deep dive

AspectJ can solve some proxy limitations but introduces build/runtime complexity and requires stronger team familiarity.

#### Production angle

Prefer Spring AOP unless you truly need weaving. Operational simplicity matters more than theoretical power.

#### Traps / caveats

- AspectJ behavior can apply outside Spring-managed calls.
- Weaving can make debugging harder.
- Switching modes changes assumptions about self-invocation.

#### Optional Anki

Q: Main Spring AOP limitation compared with AspectJ?
A: It is proxy-based and only intercepts calls through the proxy.

</details>

<a id="sp-aop-012"></a>

<details>
<summary><strong>🧠 SP-AOP-012. What can go wrong with equals(), hashCode() and toString() on proxies?</strong></summary>

#### Short answer

Proxy classes can change identity, class checks and method interception behavior, which can break naive `equals()`, `hashCode()` or logging assumptions.

#### Interview answer

If `equals()` uses exact class comparison, a proxy subclass may not compare equal to the target class. If `toString()` touches lazy state or proxied behavior, logging can trigger work unexpectedly. `hashCode()` must remain stable if proxied objects are used in maps or sets.

This is especially relevant with JPA entities and Spring proxies.

#### Deep dive

JDK proxies expose interfaces, while class proxies are subclasses. Code that assumes a concrete runtime class can fail.

#### Production angle

Proxy-aware equality matters in caches, sets, logging, security principal objects and entity handling.

#### Traps / caveats

- Avoid exact `getClass()` checks where proxies are expected unless intentional.
- Do not put mutable proxied objects into hash-based collections carelessly.
- `toString()` should not trigger database access or expensive calls.

#### Optional Anki

Q: Why can exact class checks fail with proxies?
A: The runtime object may be a proxy class, not the target class.

</details>

<details>
<summary><strong>SP-AOP-013. How would you debug a method that should be intercepted but is not?</strong></summary>

#### Short answer

Check that the object is a Spring bean, the call goes through the proxy, the method is interceptable, the annotation/pointcut matches and the relevant infrastructure is enabled.

#### Interview answer

I would verify the bean is managed by Spring and proxied. Then I would check the call path for self-invocation, private/final methods, constructor calls or manual object creation. Next I would confirm the annotation is on the effective method, the pointcut matches, and the feature is enabled, such as transaction management, caching, security or async.

I would also inspect proxy type and advisor ordering if multiple features are involved.

#### Deep dive

Tests can help by asserting behavior through the application context, not by directly instantiating the target class.

#### Production angle

This approach quickly narrows incidents like missing rollback, cache not used, method security skipped or async not happening.

#### Traps / caveats

- Interface vs implementation annotations can matter depending on proxy mode.
- Test mocks can remove proxies.
- The method may be intercepted but advice may short-circuit or throw earlier.

#### Optional Anki

Q: First proxy debugging question?
A: Is the call going through a Spring-managed proxy?

</details>

<a id="sp-aop-014"></a>

<details>
<summary><strong>SP-AOP-014. What is an around advice, and why can it be dangerous if implemented incorrectly?</strong></summary>

#### Short answer

Around advice wraps a method call and can run code before and after it, but it can also skip, repeat, alter or swallow the call.

#### Interview answer

Around advice receives a `ProceedingJoinPoint`. It can call `proceed()` to execute the target method. Because it controls the call, it can measure time, manage transactions, retry, change arguments or handle exceptions.

It is dangerous because forgetting `proceed()`, calling it twice, changing return types or swallowing exceptions changes application behavior.

#### Deep dive

Around advice should preserve the target method contract unless it is explicitly designed to alter it.

#### Production angle

Bad around advice can cause missing writes, duplicate side effects, broken transactions, wrong metrics or hidden errors.

#### Traps / caveats

- Always handle exceptions deliberately.
- Preserve return values and checked contract expectations.
- Be careful with retries around non-idempotent operations.

#### Optional Anki

Q: What must around advice usually call?
A: `proceed()`.

</details>

<a id="sp-aop-015"></a>

<details>
<summary><strong>🧠 SP-AOP-015. What are the performance and debugging costs of AOP proxies, and when would you avoid AOP?</strong></summary>

#### Short answer

Proxy overhead is usually small, but AOP adds indirection, hidden control flow and debugging complexity. Avoid it when explicit code is clearer.

#### Interview answer

A proxy method call adds interception overhead, but for normal backend operations involving I/O, it is rarely the bottleneck. The bigger cost is cognitive: behavior is not visible at the call site, stack traces include proxy frames, and ordering between advices can be subtle.

I avoid AOP for core business decisions that should be explicit, or for highly performance-sensitive inner loops.

#### Deep dive

AOP works best for uniform cross-cutting concerns such as transactions, security, tracing, metrics and caching. It is weaker for business workflow logic.

#### Production angle

During incidents, hidden behavior slows diagnosis. Keep aspects focused, documented and tested.

#### Traps / caveats

- Do not use AOP as a substitute for clear design.
- Broad pointcuts can affect more code than intended.
- Proxy overhead can matter in very hot local method paths.

#### Optional Anki

Q: Biggest practical cost of Spring AOP in backend apps?
A: Hidden control flow and debugging complexity, more than raw call overhead.

</details>
