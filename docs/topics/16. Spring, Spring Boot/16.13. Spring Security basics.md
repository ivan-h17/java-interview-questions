# 16.13. Spring Security basics

---

<a id="sp-sec-001"></a>

<details>
<summary><strong>SP-SEC-001. What is Spring Security, and how does the Spring Security filter chain work?</strong></summary>

#### Short answer

Spring Security is Spring's authentication and authorization framework, implemented mainly through servlet filters for web requests.

#### Interview answer

In servlet applications, Spring Security installs a filter chain before Spring MVC controllers. Requests pass through filters that load security context, authenticate credentials, handle sessions or tokens, check authorization and process failures.

This happens before controller logic, which is why a blocked request may never reach MVC.

#### Deep dive

The security filter chain is selected and ordered separately from MVC interceptors. It is intentionally low in the web stack.

#### Production angle

Understanding the chain helps debug unexpected 401/403 responses, missing authentication and custom filter ordering issues.

#### Traps / caveats

- MVC interceptors are not a replacement for security filters.
- Filter order matters.
- Disabling security auto-configuration can remove more protection than intended.

#### Optional Anki

Q: Does Spring Security run before MVC controllers?
A: Yes, through servlet filters.

</details>

<a id="sp-sec-002"></a>

<details>
<summary><strong>SP-SEC-002. What is SecurityFilterChain, and how are multiple chains selected and ordered?</strong></summary>

#### Short answer

`SecurityFilterChain` defines security filters for matching requests; multiple chains are selected by request matcher and ordered by precedence.

#### Interview answer

A Spring application can define one or more `SecurityFilterChain` beans. Each chain has a matcher and a set of filters/rules. For an incoming request, Spring Security finds the first matching chain by order and applies it.

This allows separate security policies for APIs, Actuator, static resources or admin endpoints.

#### Deep dive

Multiple chains are powerful but can be confusing. The most specific matchers should generally have higher precedence.

#### Production angle

Wrong chain order can leave endpoints unprotected or protected by the wrong authentication mechanism.

#### Traps / caveats

- A broad matcher placed first can shadow later chains.
- `permitAll()` and ignoring security are different.
- Actuator endpoints should be reviewed separately.

#### Optional Anki

Q: How is a request matched to multiple security chains?
A: The first matching ordered `SecurityFilterChain` applies.

</details>

<a id="sp-sec-003"></a>

<details>
<summary><strong>SP-SEC-003. What is SecurityContext, and why does thread-local storage matter?</strong></summary>

#### Short answer

`SecurityContext` holds the current authentication, commonly stored in a thread-local holder for the request thread.

#### Interview answer

Spring Security stores the current authenticated principal and authorities in `SecurityContext`. In servlet apps, it is commonly associated with the current thread through `SecurityContextHolder`.

This is convenient for request handling, but it means async execution and new threads do not automatically have the same security context unless propagated.

#### Deep dive

Different strategies and integrations exist, but thread-local context is a common mental model for servlet applications.

#### Production angle

Lost security context in async jobs can cause authorization failures or accidental unauthenticated behavior.

#### Traps / caveats

- Thread pools reuse threads, so context must be cleared correctly.
- Do not assume security context crosses `@Async` boundaries.
- Context propagation must be deliberate.

#### Optional Anki

Q: What does `SecurityContext` hold?
A: The current `Authentication`.

</details>

<a id="sp-sec-004"></a>

<details>
<summary><strong>SP-SEC-004. What is the difference between authentication, authorization, role and authority in Spring Security?</strong></summary>

#### Short answer

Authentication identifies the user; authorization decides access. Authorities are granted permissions, and roles are conventionally authorities with a `ROLE_` prefix.

#### Interview answer

Authentication answers "who are you?" Authorization answers "what are you allowed to do?" In Spring Security, permissions are represented as `GrantedAuthority`. Roles are a common convention often represented as authorities prefixed with `ROLE_`.

Applications should define authorization rules around business actions and resources, not only generic roles.

#### Deep dive

Method security can check roles, authorities or expressions involving method arguments.

#### Production angle

Confusing roles and authorities can cause endpoints to be over-permissive or inaccessible.

#### Traps / caveats

- `hasRole("ADMIN")` and `hasAuthority("ROLE_ADMIN")` are related but not identical APIs.
- Role checks alone may not enforce object ownership.
- Authorization should be deny-by-default for new endpoints.

#### Optional Anki

Q: Authentication vs authorization?
A: Authentication identifies; authorization permits or denies actions.

</details>

<a id="sp-sec-005"></a>

<details>
<summary><strong>SP-SEC-005. What is PasswordEncoder, and why should BCrypt/Argon2-like hashing be used?</strong></summary>

#### Short answer

`PasswordEncoder` hashes and verifies passwords; slow salted password hashing algorithms make password cracking harder after a leak.

#### Interview answer

Spring Security uses `PasswordEncoder` to store password hashes, not plaintext passwords. Algorithms like BCrypt, Argon2, scrypt or PBKDF2 are intentionally slow and salted, making offline cracking more expensive.

Do not use plain SHA-256 or reversible encryption for password storage.

#### Deep dive

`DelegatingPasswordEncoder` supports algorithm identifiers in stored hashes, which helps migrations between encoders.

#### Production angle

Password hashing parameters should be reviewed as hardware improves and must not cause login endpoint overload.

#### Traps / caveats

- Never log raw passwords.
- Do not compare password strings manually.
- Account lockout and rate limiting are still needed.

#### Optional Anki

Q: Why should password hashing be slow?
A: To make offline brute-force cracking expensive.

</details>

<a id="sp-sec-006"></a>

<details>
<summary><strong>SP-SEC-006. What are CSRF and CORS, and how should they be handled in Spring APIs?</strong></summary>

#### Short answer

CSRF protects state-changing browser requests using ambient credentials; CORS controls which browser origins may call the API.

#### Interview answer

CSRF is relevant when browsers automatically send credentials such as cookies. Stateless token APIs that do not use cookies may not need CSRF in the same way. CORS is a browser mechanism that allows or blocks cross-origin JavaScript calls based on server response headers.

Spring Security and Spring MVC should be configured together so CORS preflight works correctly.

#### Deep dive

CORS is not authentication. It does not protect against non-browser clients.

#### Production angle

Wrong CSRF/CORS settings can either break browser clients or weaken protection for cookie-based apps.

#### Traps / caveats

- Disabling CSRF blindly is unsafe for cookie/session apps.
- Wildcard CORS with credentials is dangerous.
- Preflight requests may be blocked before authentication if not configured.

#### Optional Anki

Q: Is CORS a security authorization mechanism?
A: No, it is browser cross-origin access control.

</details>

<a id="sp-sec-007"></a>

<details>
<summary><strong>SP-SEC-007. How does JWT authentication work in a Spring Boot resource server?</strong></summary>

#### Short answer

The resource server validates the JWT signature and claims, then converts token claims into an authenticated principal and authorities.

#### Interview answer

In a resource server, Spring Security reads the bearer token, validates it against issuer configuration and keys, checks claims such as expiration and issuer, then builds an `Authentication`. Claims like scopes or roles can be mapped to authorities.

The API should not trust token contents without validation.

#### Deep dive

Key rotation uses JWK sets. Audience validation and custom authority mapping are common production needs.

#### Production angle

Bad JWT validation can allow tokens from wrong issuers, expired tokens or wrong audiences.

#### Traps / caveats

- Signature validation alone is not enough; validate issuer, expiration and audience where required.
- JWT revocation is harder than session invalidation.
- Do not log bearer tokens.

#### Optional Anki

Q: What must a resource server do before trusting JWT claims?
A: Validate signature and required claims.

</details>

<a id="sp-sec-008"></a>

<details>
<summary><strong>SP-SEC-008. What is method security with @PreAuthorize, and how can proxies affect it?</strong></summary>

#### Short answer

Method security applies authorization checks around method calls, often through proxies, using annotations such as `@PreAuthorize`.

#### Interview answer

`@PreAuthorize` evaluates an expression before invoking a method. It can check roles, authorities, arguments or custom authorization methods. Since method security is commonly proxy-based, self-invocation and non-interceptable methods can bypass it.

Use it for service-layer protection where business actions need authorization.

#### Deep dive

Method security complements URL security. URL rules protect endpoints; method rules protect actions and can use method arguments.

#### Production angle

Method security helps avoid authorization gaps when the same service method is called from multiple entry points.

#### Traps / caveats

- Self-invocation can bypass checks.
- Do not rely only on controller-level checks for reusable services.
- Expressions must be tested for object ownership, not just roles.

#### Optional Anki

Q: What can proxy-based method security fail on?
A: Self-invocation and non-interceptable methods.

</details>

<a id="sp-sec-009"></a>

<details>
<summary><strong>SP-SEC-009. Where should authorization rules live: controller, service or security configuration?</strong></summary>

#### Short answer

Use security configuration for request-level rules, service/domain layer for business authorization and controllers for request validation/orchestration only.

#### Interview answer

URL rules are good for endpoint access: authenticated, admin path, public endpoint. Service-layer checks are better for business permissions such as "can this user approve this order?" because they can use domain data and are reused across entry points.

Controllers should not become the only place where important authorization lives.

#### Deep dive

Object-level authorization often requires loading domain state before making a decision.

#### Production angle

Proper placement prevents BOLA/IDOR-style bugs where a user can change an ID and access another user's resource.

#### Traps / caveats

- Role-based URL checks are not enough for ownership.
- Duplicating rules across controllers leads to drift.
- Repository filters can help but should not hide business decisions completely.

#### Optional Anki

Q: Where should business authorization usually live?
A: Service/domain layer.

</details>

<a id="sp-sec-010"></a>

<details>
<summary><strong>SP-SEC-010. How do you secure Actuator endpoints?</strong></summary>

#### Short answer

Expose only needed endpoints, restrict access with Spring Security and avoid exposing sensitive diagnostics publicly.

#### Interview answer

Actuator endpoints can reveal health, metrics, environment, beans, mappings and logs. In production, expose only what is needed, put management endpoints on protected paths or ports, require authentication/authorization, and restrict sensitive endpoints.

Health/readiness may be public internally, while details should be controlled.

#### Deep dive

Actuator exposure and security are separate concerns: an endpoint must be exposed and then access-controlled.

#### Production angle

Public Actuator diagnostics can leak internal configuration, topology and operational data.

#### Traps / caveats

- Do not expose `env`, `beans`, `heapdump` or loggers publicly.
- Health details can leak dependency names.
- Kubernetes probes should use minimal endpoint permissions.

#### Optional Anki

Q: Should all Actuator endpoints be public?
A: No, expose and secure them deliberately.

</details>

<a id="sp-sec-011"></a>

<details>
<summary><strong>SP-SEC-011. What are common Spring Security misconfigurations, and why should disabling security auto-configuration be done carefully?</strong></summary>

#### Short answer

Common mistakes include broad permit rules, wrong chain order, disabled CSRF in cookie apps, unsafe CORS, exposed Actuator endpoints and accidental security exclusion.

#### Interview answer

Spring Security is safe only when rules match the application. Misconfigurations include `anyRequest().permitAll()`, broad ignored paths, wrong `SecurityFilterChain` order, missing method security, trusting headers from clients and exposing sensitive operational endpoints.

Disabling auto-configuration may remove default protections and expected beans, so it should be replaced with explicit security configuration.

#### Deep dive

"Ignoring" a request from security is different from allowing it through security with `permitAll()`.

#### Production angle

Security mistakes often deploy silently and are discovered only after access-control failures.

#### Traps / caveats

- New endpoints can be left unprotected if rules are not deny-by-default.
- CORS is not access control.
- Tests should assert both allowed and denied paths.

#### Optional Anki

Q: Safer default for unmatched endpoints?
A: Deny by default.

</details>

<a id="sp-sec-012"></a>

<details>
<summary><strong>SP-SEC-012. How would you test secured endpoints and debug unexpected 401 or 403 responses?</strong></summary>

#### Short answer

Test both allowed and denied cases, then debug authentication, authorities, filter chain selection, CSRF/CORS and method security.

#### Interview answer

For tests, use MockMvc/WebTestClient support with mock users, JWTs or real authentication setup depending on test level. Assert status codes and response bodies for authenticated, unauthenticated and unauthorized users.

For debugging, 401 usually means authentication failed or is missing; 403 means authenticated but forbidden or blocked by CSRF/authorization.

#### Deep dive

Enable targeted Spring Security debug logs in lower environments to see matcher and filter decisions.

#### Production angle

Security tests prevent regressions when endpoints, roles or chains change.

#### Traps / caveats

- 403 can be caused by CSRF, not only missing role.
- Mock users may not match real JWT authority mapping.
- Testing only happy paths misses access-control bugs.

#### Optional Anki

Q: High-level difference between 401 and 403?
A: 401 is unauthenticated; 403 is authenticated or request understood but forbidden.

</details>
