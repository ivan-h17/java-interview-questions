# 16.11. HTTP clients, resilience and external calls

---

<a id="sp-http-001"></a>

<details>
<summary><strong>SP-HTTP-001. What is the difference between RestTemplate, RestClient and WebClient?</strong></summary>

#### Short answer

`RestTemplate` is the older blocking client, `RestClient` is the modern blocking client API, and `WebClient` is the non-blocking reactive client.

#### Interview answer

`RestTemplate` has been widely used for synchronous HTTP calls but is legacy for new development. `RestClient` provides a modern fluent synchronous API. `WebClient` is reactive and non-blocking, useful with WebFlux or when a service is designed around reactive pipelines.

For ordinary servlet apps that need blocking calls, `RestClient` is a good default in modern Spring.

#### Deep dive

Choice of API does not remove the need for correct timeouts, error mapping, retries, metrics and connection pooling.

#### Production angle

HTTP client defaults directly affect latency, thread usage and outage behavior.

#### Traps / caveats

- Using `WebClient` and immediately blocking everywhere often adds complexity without benefit.
- Missing timeouts are dangerous for any client.
- Client choice should match the application's execution model.

#### Optional Anki

Q: Modern blocking HTTP client API in Spring?
A: `RestClient`.

</details>

<a id="sp-http-002"></a>

<details>
<summary><strong>SP-HTTP-002. How do you choose between blocking and non-blocking HTTP clients in a Spring Boot service?</strong></summary>

#### Short answer

Choose based on the application's threading model, dependency behavior and team expertise, not just because non-blocking sounds faster.

#### Interview answer

In a servlet MVC service, blocking clients are often simpler and fit the request-per-thread model. Non-blocking clients are useful when the application is reactive end-to-end or needs to handle many concurrent I/O waits with fewer threads.

Mixing models is possible, but blocking inside reactive flows can harm scalability.

#### Deep dive

Non-blocking clients require understanding backpressure, schedulers, context propagation and reactive error handling.

#### Production angle

The wrong model can cause thread starvation, complex debugging or no real performance gain.

#### Traps / caveats

- Non-blocking is not automatically faster.
- Blocking calls on event loop threads are dangerous.
- Database drivers and downstream libraries may still be blocking.

#### Optional Anki

Q: Biggest rule for reactive event loop threads?
A: Do not block them.

</details>

<a id="sp-http-003"></a>

<details>
<summary><strong>SP-HTTP-003. What are Spring HTTP interface clients, and when would you use them?</strong></summary>

#### Short answer

HTTP interface clients let you declare HTTP calls as annotated Java interfaces backed by clients such as `RestClient` or `WebClient`.

#### Interview answer

Spring can create client proxies from interfaces annotated with HTTP exchange metadata. This reduces boilerplate for typed clients and centralizes endpoint method definitions. The proxy is backed by an underlying adapter such as `RestClient` or `WebClient`.

They are useful for internal service clients with stable APIs and consistent configuration.

#### Deep dive

The interface is still only a client wrapper. You must configure base URLs, timeouts, error handling, security, observability and resilience around the underlying client.

#### Production angle

Interface clients improve consistency but should be tested against contract changes and failure modes.

#### Traps / caveats

- Do not hide retries or fallback behavior implicitly.
- Interface methods still need clear timeout and error semantics.
- Multiple clients for the same interface may need explicit grouping or qualifiers.

#### Optional Anki

Q: What creates runtime implementations for Spring HTTP interfaces?
A: Spring client proxy infrastructure backed by an HTTP client adapter.

</details>

<a id="sp-http-004"></a>

<details>
<summary><strong>SP-HTTP-004. How do you configure connection timeout, read timeout and response handling for an HTTP client?</strong></summary>

#### Short answer

Configure timeouts and status handling on the underlying HTTP client or builder used by `RestClient`, `WebClient` or the client factory.

#### Interview answer

Connection timeout limits time to establish a connection. Read or response timeout limits waiting for data after the request is sent. Response handling maps status codes and bodies to exceptions or domain results.

In Spring, the exact API depends on the underlying client library and whether you use `RestClient`, `WebClient` or interface clients.

#### Deep dive

Also consider connection pool limits, idle timeouts, TLS handshakes, DNS behavior and max response size.

#### Production angle

Timeouts should be shorter than user-facing deadlines and coordinated with retries and upstream timeouts.

#### Traps / caveats

- A retry policy without timeouts can still hang.
- Too-long timeouts consume threads and connections.
- Too-short timeouts can cause false failures during normal latency spikes.

#### Optional Anki

Q: What does connection timeout control?
A: Time allowed to establish the connection.

</details>

<a id="sp-http-005"></a>

<details>
<summary><strong>SP-HTTP-005. Why are missing HTTP timeouts dangerous in Spring applications?</strong></summary>

#### Short answer

Without timeouts, blocked outbound calls can tie up request threads, async workers or connection pool resources indefinitely.

#### Interview answer

If an external dependency slows down and the client has no timeout, calls can pile up. In servlet apps, request threads block. In async workers, executors fill. Connection pools can be exhausted. Eventually the service may fail even for unrelated endpoints.

Timeouts are a bulkhead against dependency failure.

#### Deep dive

Timeouts should be part of an end-to-end deadline budget that includes retries and downstream service limits.

#### Production angle

Missing timeouts are a classic cause of cascading failures.

#### Traps / caveats

- Default timeouts may be infinite or not what you expect.
- Retries multiply total latency.
- Timeouts should be observable through metrics and logs.

#### Optional Anki

Q: Main production risk of missing HTTP timeouts?
A: Threads and connections get stuck waiting on dependencies.

</details>

<a id="sp-http-006"></a>

<details>
<summary><strong>SP-HTTP-006. How should response status mapping and error handling be configured for outgoing HTTP calls?</strong></summary>

#### Short answer

Map HTTP statuses to clear domain or integration errors, preserve useful context and avoid treating every non-2xx response the same.

#### Interview answer

For client calls, decide how to handle 4xx, 5xx, timeouts, malformed bodies and empty responses. A 404 may mean "not found" in the domain, while a 503 may be retryable. The client layer should translate transport details into meaningful exceptions or results.

Also include safe diagnostic context such as dependency name and correlation ID.

#### Deep dive

Avoid leaking raw response bodies into logs because they may contain PII or secrets.

#### Production angle

Good error mapping makes retry, alerting and client behavior predictable.

#### Traps / caveats

- Retrying 4xx usually makes no sense except specific cases.
- Swallowing errors can hide dependency outages.
- Parsing error bodies should be resilient to schema changes.

#### Optional Anki

Q: Should all non-2xx responses be handled identically?
A: No, status semantics and dependency contract matter.

</details>

<a id="sp-http-007"></a>

<details>
<summary><strong>SP-HTTP-007. How should retries, idempotency, exponential backoff and jitter be combined for outgoing calls?</strong></summary>

#### Short answer

Retry only safe/idempotent operations or operations protected by idempotency keys, with bounded attempts, backoff and jitter.

#### Interview answer

Retries are useful for transient failures, but they can duplicate side effects. GET-like reads are usually safer. POST-like commands need idempotency keys or a server-side deduplication design.

Backoff spaces retry attempts. Jitter randomizes delays so many clients do not retry at the same time.

#### Deep dive

Retries must fit within the caller's timeout budget and should avoid retrying permanent failures.

#### Production angle

Bad retries amplify outages and overload dependencies.

#### Traps / caveats

- Never blindly retry non-idempotent writes.
- More retries can make p99 latency worse.
- Coordinate client retries with server rate limits and circuit breakers.

#### Optional Anki

Q: Why add jitter to retry backoff?
A: To avoid synchronized retry storms.

</details>

<a id="sp-http-008"></a>

<details>
<summary><strong>SP-HTTP-008. How can Circuit Breaker, Retry and TimeLimiter be integrated with Spring?</strong></summary>

#### Short answer

Use resilience libraries such as Resilience4j through Spring integration, annotations or decorated clients.

#### Interview answer

Spring applications commonly integrate Resilience4j with clients through decorators, annotations or configuration. TimeLimiter caps operation duration, Retry handles transient failures, and Circuit Breaker stops calls temporarily when failure rates are high.

The policies should be configured per dependency, not globally with one-size-fits-all settings.

#### Deep dive

Ordering matters: timeout, retry and circuit breaker composition affects observed failures and load.

#### Production angle

Resilience policies should emit metrics so teams can see open circuits, retry volume and timeout rates.

#### Traps / caveats

- Circuit breakers do not fix a broken dependency.
- Retrying behind an open circuit is pointless.
- Fallbacks must be correct, not just convenient.

#### Optional Anki

Q: What does a circuit breaker prevent?
A: Continued calls to a dependency that is currently failing beyond thresholds.

</details>

<a id="sp-http-009"></a>

<details>
<summary><strong>SP-HTTP-009. How do you propagate correlation IDs, trace context and authorization context in outgoing HTTP calls?</strong></summary>

#### Short answer

Use client interceptors/filters to copy or create safe headers for tracing, correlation and authorization as appropriate.

#### Interview answer

For outgoing calls, add interceptors or filters to propagate `traceparent`, correlation IDs and request IDs. Authorization propagation depends on architecture: sometimes forward user tokens, sometimes use service credentials, and sometimes exchange tokens.

This should be standardized so every client behaves consistently.

#### Deep dive

Context propagation differs between servlet threads, async execution and reactive pipelines.

#### Production angle

Without propagation, traces break across services and incidents become harder to diagnose.

#### Traps / caveats

- Do not blindly trust inbound user-supplied correlation or auth headers.
- Do not forward user tokens to services that should not receive them.
- Async boundaries can lose thread-local context.

#### Optional Anki

Q: Common W3C trace propagation header?
A: `traceparent`.

</details>

<a id="sp-http-010"></a>

<details>
<summary><strong>SP-HTTP-010. What are the risks of logging HTTP request and response bodies?</strong></summary>

#### Short answer

Bodies can contain PII, credentials, tokens, payment data or large payloads, and reading them can affect performance or stream behavior.

#### Interview answer

Logging full HTTP bodies is risky because it can leak sensitive data and create huge logs. It can also consume request/response streams or increase memory usage if wrappers buffer content.

Prefer structured metadata, redacted fields and targeted debug logging with strict controls.

#### Deep dive

Outbound client logging should redact headers like `Authorization`, cookies and API keys.

#### Production angle

Body leaks often become security incidents and compliance problems.

#### Traps / caveats

- Logs are often copied to third-party systems.
- Error logs may include response bodies from dependencies.
- Debug logging can accidentally remain enabled.

#### Optional Anki

Q: Why is full HTTP body logging risky?
A: It can leak sensitive data and increase resource usage.

</details>

<details>
<summary><strong>SP-HTTP-011. How would you test an external REST client with WireMock or a fake server?</strong></summary>

#### Short answer

Run a local fake server, point the Spring client to it, and verify success, errors, timeouts and malformed responses.

#### Interview answer

Use WireMock, MockWebServer or another fake server in integration tests. Override the client's base URL through test properties or dynamic properties. Test normal responses, 4xx/5xx mapping, timeouts, retries, headers and serialization.

This is better than mocking the HTTP client internals for client adapter behavior.

#### Deep dive

For Spring Boot tests, dynamic ports can be passed through `@DynamicPropertySource` or test configuration.

#### Production angle

Client tests protect against broken dependency contracts and unsafe error handling.

#### Traps / caveats

- Do not assert only that a method was called; verify actual HTTP request shape.
- Simulate slow and malformed responses.
- Keep fake server contracts aligned with real dependency behavior.

#### Optional Anki

Q: Why use a fake HTTP server for client tests?
A: To test real serialization, headers, status handling and client configuration.

</details>

<a id="sp-http-012"></a>

<details>
<summary><strong>SP-HTTP-012. How would you debug increased latency or connection pool exhaustion caused by an external dependency?</strong></summary>

#### Short answer

Correlate client metrics, traces, thread dumps, pool metrics, timeout/retry settings and dependency health.

#### Interview answer

I would check p95/p99 latency by dependency, error/timeout rates, retry counts, circuit breaker state, connection pool active/pending counts and thread dumps showing blocked calls. Traces should show which dependency spans dominate request time.

Then I would review timeout budgets, retry policy, pool sizing and recent dependency changes.

#### Deep dive

Connection pool exhaustion can come from slow responses, leaked response bodies, too much concurrency or no limits.

#### Production angle

Mitigation may include lowering timeouts, opening a circuit, reducing concurrency, disabling a feature or using cached/degraded responses.

#### Traps / caveats

- Increasing pool size can amplify load on a failing dependency.
- Retrying slow calls may worsen the outage.
- Missing dependency-level metrics makes diagnosis guesswork.

#### Optional Anki

Q: What telemetry identifies slow outbound calls in distributed systems?
A: Traces and client latency metrics by dependency.

</details>
