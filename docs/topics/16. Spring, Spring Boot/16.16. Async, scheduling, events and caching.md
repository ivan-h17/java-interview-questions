# 16.16. Async, scheduling, events and caching

---

<a id="sp-async-001"></a>

<details>
<summary><strong>SP-ASYNC-001. What does @Async do, and how does it work under the hood?</strong></summary>

#### Short answer

`@Async` runs a method through a Spring proxy that submits the work to an executor instead of running it on the caller thread.

#### Interview answer

When `@Async` is enabled and a proxied async method is called, Spring intercepts the call and submits it to a configured `Executor`. The caller returns immediately for `void`, `Future`, `CompletableFuture` or similar supported return types.

Like other proxy-based features, it does not apply to self-invocation.

#### Deep dive

The method runs in another thread, so thread-local contexts such as transaction, request and security context do not automatically follow.

#### Production angle

Async execution needs bounded executors, monitoring and clear failure handling; otherwise it can hide overload.

#### Traps / caveats

- Self-invocation bypasses `@Async`.
- Exceptions in `void` async methods do not reach the caller.
- Unbounded executors can create resource exhaustion.

#### Optional Anki

Q: What does `@Async` submit work to?
A: A Spring-configured `Executor`.

</details>

<a id="sp-async-002"></a>

<details>
<summary><strong>SP-ASYNC-002. How do you configure the Executor used by @Async?</strong></summary>

#### Short answer

Define an async executor bean or implement async configuration so Spring knows which executor to use.

#### Interview answer

Spring can use a default executor, but production applications should configure one explicitly with core/max pool size, queue capacity, thread name prefix and rejection policy. You can provide a bean named for async execution or implement `AsyncConfigurer`.

Different async workloads may need separate executors.

#### Deep dive

Thread pool sizing depends on whether tasks are CPU-bound or I/O-bound and on expected concurrency and latency.

#### Production angle

Executor metrics should be monitored: active threads, queue depth, completed tasks and rejected tasks.

#### Traps / caveats

- A shared executor can let one workload starve another.
- Large queues hide overload and increase latency.
- Rejection policy should match business requirements.

#### Optional Anki

Q: Why configure an explicit async executor?
A: To control concurrency, queueing and rejection behavior.

</details>

<a id="sp-async-003"></a>

<details>
<summary><strong>SP-ASYNC-003. How are exceptions handled in @Async methods?</strong></summary>

#### Short answer

For future-returning methods, exceptions are captured in the future; for `void` async methods, they go to an async exception handler.

#### Interview answer

If an async method returns `CompletableFuture` or `Future`, exceptions are available when the future is completed or joined. If it returns `void`, the caller cannot observe the exception directly, so Spring uses an `AsyncUncaughtExceptionHandler`.

Production async code should log, meter and retry or compensate deliberately.

#### Deep dive

Async exceptions do not roll back a caller's already-completed transaction or automatically notify the user.

#### Production angle

Lost async failures can silently drop notifications, exports or integration work.

#### Traps / caveats

- `void` async methods are easy to ignore.
- Exceptions may appear only in logs.
- Retry must be idempotent if side effects are possible.

#### Optional Anki

Q: Where do exceptions from `CompletableFuture` async methods appear?
A: In the completed future.

</details>

<a id="sp-async-004"></a>

<details>
<summary><strong>SP-ASYNC-004. Why can request context or security context disappear in @Async code?</strong></summary>

#### Short answer

`@Async` runs in another thread, and thread-local contexts are not automatically available there.

#### Interview answer

Request attributes, security context, MDC and transaction context are often thread-local. When work moves to an executor thread, those thread-local values are absent unless explicitly propagated.

Spring Security has delegation helpers, and logging context can be copied with task decorators, but propagation should be deliberate.

#### Deep dive

Blindly propagating context can leak data between tasks if thread-local cleanup is wrong.

#### Production angle

Missing context breaks authorization, tracing and log correlation for background work.

#### Traps / caveats

- Do not rely on request-scoped beans in async tasks.
- Clear propagated context after execution.
- Passing explicit IDs is often clearer than passing whole request context.

#### Optional Anki

Q: Why does security context often disappear in async code?
A: The work runs on a different thread.

</details>

<a id="sp-async-005"></a>

<details>
<summary><strong>SP-ASYNC-005. How do @Async and @Transactional interact?</strong></summary>

#### Short answer

Async work runs in a different thread, so it does not automatically share the caller's transaction.

#### Interview answer

If an async method is also transactional and is invoked through the proxy, the transaction starts in the async thread. It does not participate in the caller's transaction. If a transactional method schedules async work before commit, the async task may run before data is committed.

Use after-commit events or an outbox when async work depends on committed data.

#### Deep dive

Putting both annotations on one method can be confusing because async advice changes the execution thread before transaction assumptions are evaluated.

#### Production angle

Wrong assumptions cause stale reads, missing data, duplicate side effects or lost events.

#### Traps / caveats

- Self-invocation can disable async behavior.
- Caller rollback does not roll back already-started async work.
- Use durable messaging for critical async effects.

#### Optional Anki

Q: Does async work share the caller's transaction?
A: No, not automatically.

</details>

<a id="sp-async-006"></a>

<details>
<summary><strong>SP-ASYNC-006. What does @Scheduled do, and how do you configure scheduling threads?</strong></summary>

#### Short answer

`@Scheduled` runs methods on a schedule using Spring's task scheduling infrastructure.

#### Interview answer

`@Scheduled` can run methods with fixed rate, fixed delay or cron expressions. Scheduling must be enabled, and the scheduler can be configured with a `TaskScheduler` or Boot properties for thread pool size and naming.

Scheduled methods should be bounded, observable and safe to rerun.

#### Deep dive

Fixed rate schedules based on start times; fixed delay schedules after completion plus delay.

#### Production angle

Long-running scheduled tasks can block future executions if the scheduler has too few threads.

#### Traps / caveats

- A scheduled job runs in every application replica unless coordinated.
- Exceptions need logging and alerting.
- Cron timezone should be explicit when business time matters.

#### Optional Anki

Q: Difference between fixed delay and fixed rate?
A: Fixed delay waits after completion; fixed rate schedules by start interval.

</details>

<a id="sp-async-007"></a>

<details>
<summary><strong>SP-ASYNC-007. How do you prevent scheduled tasks from overlapping, especially after scaling replicas?</strong></summary>

#### Short answer

Use locks, leader election, external schedulers, idempotency or queue-based work distribution.

#### Interview answer

Within one JVM, a single-thread scheduler or explicit lock can prevent overlap. Across replicas, every instance runs the same `@Scheduled` method unless coordinated. Use distributed locks, leader election, Kubernetes CronJobs, a queue, or design the job to be idempotent and partitioned.

For critical jobs, prefer durable coordination over in-memory flags.

#### Deep dive

Libraries such as ShedLock-style approaches are common, but the lock backend and failure semantics matter.

#### Production angle

Duplicate scheduled jobs can send duplicate notifications, charge customers twice or corrupt batch state.

#### Traps / caveats

- In-memory locks do not work across replicas.
- Distributed locks need expiry and clock/failure handling.
- Idempotency is still needed because locks can fail.

#### Optional Anki

Q: Does `@Scheduled` run once per cluster by default?
A: No, it runs in each application instance.

</details>

<a id="sp-event-001"></a>

<details>
<summary><strong>SP-EVENT-001. What are Spring application events, and what is the difference between synchronous and asynchronous event listeners?</strong></summary>

#### Short answer

Spring events let beans publish and listen to in-process events; listeners are synchronous by default unless configured async.

#### Interview answer

An application event is an in-process notification published through Spring's event mechanism. By default, listeners run synchronously in the publisher's thread. If configured with async execution, listeners run through an executor.

Events can decouple components, but they are not a durable messaging system.

#### Deep dive

Synchronous listeners participate in the caller's call stack and may affect transaction timing.

#### Production angle

Use in-process events for local decoupling. Use Kafka, RabbitMQ or an outbox for reliable inter-service events.

#### Traps / caveats

- Async listener exceptions may be lost if not handled.
- Synchronous listeners can slow the publisher.
- Events disappear if the process crashes before handling.

#### Optional Anki

Q: Are Spring application events durable by default?
A: No, they are in-process events.

</details>

<a id="sp-event-002"></a>

<details>
<summary><strong>🧠 SP-EVENT-002. When would you use @TransactionalEventListener, and what are its limitations?</strong></summary>

#### Short answer

Use it to handle events at transaction phases, commonly after commit, but not as a durable integration mechanism.

#### Interview answer

`@TransactionalEventListener` runs an event listener relative to a transaction phase, such as after commit or after rollback. It is useful when a local action should happen only if the transaction succeeds.

For external messaging, it reduces premature side effects but does not guarantee delivery after a crash.

#### Deep dive

If no transaction exists, behavior depends on configuration such as fallback execution.

#### Production angle

For reliable external publication, pair transaction events with an outbox table and a separate publisher.

#### Traps / caveats

- After-commit listener failure cannot roll back the committed transaction.
- It is still in-process.
- Listener ordering and async behavior need care.

#### Optional Anki

Q: Reliable alternative for external events after DB commit?
A: Outbox pattern.

</details>

<a id="sp-cache-001"></a>

<details>
<summary><strong>SP-CACHE-001. What is Spring Cache abstraction?</strong></summary>

#### Short answer

Spring Cache is an abstraction that applies caching behavior to methods while delegating storage to providers such as Caffeine or Redis.

#### Interview answer

Spring Cache lets you use annotations like `@Cacheable`, `@CachePut` and `@CacheEvict` without hard-coding a specific cache provider. A `CacheManager` connects the abstraction to an implementation.

It is useful for deterministic, frequently read data where staleness policy is understood.

#### Deep dive

Spring Cache is method-level caching. It is not a full data consistency solution.

#### Production angle

Caching can reduce latency and load, but wrong keys or invalidation can return stale or incorrect data.

#### Traps / caveats

- Cache behavior is usually proxy-based.
- Mutable cached objects can leak changes between callers.
- Distributed caches need serialization and TTL design.

#### Optional Anki

Q: Which Spring component connects cache annotations to a provider?
A: `CacheManager`.

</details>

<a id="sp-cache-002"></a>

<details>
<summary><strong>SP-CACHE-002. What do @Cacheable, @CachePut and @CacheEvict do?</strong></summary>

#### Short answer

`@Cacheable` reads through cache, `@CachePut` updates cache after method execution, and `@CacheEvict` removes entries.

#### Interview answer

`@Cacheable` checks the cache first and may skip method execution on hit. `@CachePut` always runs the method and stores the result. `@CacheEvict` removes one or more cache entries, commonly after a write.

These annotations should match the consistency model of the data.

#### Deep dive

Conditions and SpEL expressions can control keys, cache names and whether to cache.

#### Production angle

Wrong eviction is the main source of stale cache bugs.

#### Traps / caveats

- `@CachePut` and `@Cacheable` on the same method can be confusing.
- Evict after commit may be needed with transactions.
- Cache null behavior depends on configuration.

#### Optional Anki

Q: Which annotation can skip method execution on cache hit?
A: `@Cacheable`.

</details>

<a id="sp-cache-003"></a>

<details>
<summary><strong>SP-CACHE-003. How are cache keys generated, and why can caching fail during self-invocation?</strong></summary>

#### Short answer

Keys are generated from method parameters by default or with custom SpEL/key generators; self-invocation bypasses the cache proxy.

#### Interview answer

By default, Spring uses method parameters to generate a key. You can customize keys with SpEL expressions or a `KeyGenerator`. The key must uniquely represent the cached result.

Because caching is proxy-based, calling a cached method from another method in the same class bypasses cache advice.

#### Deep dive

Stable key design matters for composite objects, locale, tenant, user permissions and optional parameters.

#### Production angle

Bad keys cause data leaks, stale results or low hit rates.

#### Traps / caveats

- Include tenant/user context if result depends on it.
- Mutable key objects are risky.
- Self-invocation is a common reason cache annotations appear ignored.

#### Optional Anki

Q: Why can `@Cacheable` fail on internal method calls?
A: The call bypasses the Spring proxy.

</details>

<a id="sp-cache-004"></a>

<details>
<summary><strong>SP-CACHE-004. What are the risks of caching mutable objects or stale data?</strong></summary>

#### Short answer

Mutable cached objects can be changed by callers, and stale data can break business correctness.

#### Interview answer

If a cached object is mutable and a caller modifies it, later callers may see modified data that was never intended to be cached. Stale data appears when source data changes but cache entries remain old.

Use immutable DTOs, defensive copies, TTLs and explicit eviction where appropriate.

#### Deep dive

In distributed caches, serialization may create copies, while local caches often share object references.

#### Production angle

Stale or corrupted cache entries can cause wrong prices, permissions, inventory or feature behavior.

#### Traps / caveats

- Caching authorization-sensitive data is risky.
- TTL alone may not satisfy correctness.
- Cache invalidation must be part of write design.

#### Optional Anki

Q: Why are mutable cached objects dangerous in local caches?
A: Callers may mutate the shared cached instance.

</details>

<a id="sp-cache-005"></a>

<details>
<summary><strong>SP-CACHE-005. What is cache stampede, and how can it be mitigated?</strong></summary>

#### Short answer

A cache stampede happens when many requests miss or expire the same key and all recompute or reload it at once.

#### Interview answer

If a popular cache entry expires, many threads or instances may simultaneously call the database or dependency to rebuild it. Mitigations include per-key locking, request coalescing, early refresh, TTL jitter, stale-while-revalidate and rate limiting.

The mitigation depends on whether stale data is acceptable.

#### Deep dive

Distributed systems need distributed coordination or provider support; local locks only help inside one JVM.

#### Production angle

Stampedes can turn a cache expiry into a database outage.

#### Traps / caveats

- Identical TTLs create synchronized expiry.
- Locking can become a bottleneck.
- Serving stale data must be acceptable for the domain.

#### Optional Anki

Q: Why add TTL jitter?
A: To avoid many cache entries expiring at the same time.

</details>

<a id="sp-cache-006"></a>

<details>
<summary><strong>SP-CACHE-006. How does Redis fit into Spring caching, and how would you debug stale or wrong cache data?</strong></summary>

#### Short answer

Redis can be the backing cache provider for Spring Cache; debug stale data by checking keys, TTLs, serialization, eviction paths and write transaction timing.

#### Interview answer

With a Redis cache manager, Spring cache annotations store entries in Redis. Redis is useful for shared cache state across replicas. Debugging wrong data means inspecting the generated key, tenant/user dimensions, serialized value, TTL, eviction annotations, transaction timing and whether all instances use the same cache configuration.

Also check whether the method is actually called through the cache proxy.

#### Deep dive

Serialization format changes can break old entries after deployments. Cache prefixes and versioned keys help.

#### Production angle

Redis cache issues can affect every replica at once, so bad data may need targeted eviction or cache versioning.

#### Traps / caveats

- Local and Redis caches behave differently.
- Key collisions can leak data between tenants.
- Evicting before transaction commit can expose stale reads.

#### Optional Anki

Q: First things to inspect for wrong Redis-backed cache data?
A: Cache key, TTL, serialized value and eviction path.

</details>
