# 16.02. Bean definitions, configuration and dependency resolution

---

<a id="sp-bean-001"></a>

<details>
<summary><strong>SP-BEAN-001. What is a bean in Spring?</strong></summary>

#### Short answer

A Spring bean is an object managed by the Spring container.

#### Interview answer

A bean is an object whose creation, dependencies, lifecycle and configuration are managed by Spring. Beans usually represent services, repositories, controllers, configuration objects, infrastructure components or adapters.

Instead of constructing these objects manually, the application registers bean definitions and Spring creates the object graph.

#### Deep dive

A bean definition describes how to create a bean: its class, factory method, scope, name, dependencies, lifecycle callbacks and conditional metadata.

#### Production angle

Most Spring behavior depends on beans: transactions, security, caching, configuration properties, controllers and data sources are all applied through managed beans.

#### Traps / caveats

- Not every object in a Spring application is a bean.
- Objects created with `new` inside business code are not automatically managed by Spring.
- A bean can be proxied, so the injected object may not be the raw class instance.

#### Optional Anki

Q: What is a Spring bean?
A: An object managed by the Spring container.

</details>

<a id="sp-bean-002"></a>

<details>
<summary><strong>SP-BEAN-002. How can you create a bean in Spring?</strong></summary>

#### Short answer

You can create beans through component scanning, `@Bean` methods, imports, auto-configuration, XML or programmatic registration.

#### Interview answer

The common ways are annotating a class with `@Component`, `@Service`, `@Repository` or `@Controller` and letting component scanning find it, or declaring a `@Bean` method in a configuration class.

Spring Boot also creates many beans through auto-configuration based on the classpath, properties and existing beans.

#### Deep dive

Programmatic registration is possible through registry post-processors or application context initializers, but that is usually infrastructure-level code.

#### Production angle

Knowing where a bean comes from is critical when debugging unexpected behavior: it may be user-defined, scanned, imported or auto-configured.

#### Traps / caveats

- Component scanning only sees packages under the configured scan roots.
- `@Bean` methods are useful for third-party classes you cannot annotate.
- Auto-configured beans can disappear if conditions stop matching.

#### Optional Anki

Q: Two common ways to define Spring beans?
A: Component scanning and `@Bean` methods.

</details>

<a id="sp-bean-003"></a>

<details>
<summary><strong>SP-BEAN-003. What is the difference between defining a bean with @Component and @Bean?</strong></summary>

#### Short answer

`@Component` marks a class for scanning; `@Bean` declares a bean from a method, usually in a configuration class.

#### Interview answer

Use `@Component` and stereotypes for classes owned by the application, such as services and controllers. Spring scans the class and creates the bean automatically.

Use `@Bean` when creation needs custom code, when configuring third-party classes, or when the bean is infrastructure-like, such as a client, mapper, executor or configuration object.

#### Deep dive

`@Bean` gives precise control over construction. It can call constructors, builders, factory APIs and use configuration properties.

#### Production angle

Configuration-heavy objects such as HTTP clients, thread pools and data sources should be explicit `@Bean`s so timeouts, pool sizes and credentials are visible in one place.

#### Traps / caveats

- Annotating third-party classes with `@Component` is usually impossible and undesirable.
- `@Bean` methods in full `@Configuration` classes have special proxy behavior.
- Component scanning can accidentally register classes if packages are too broad.

#### Optional Anki

Q: When is `@Bean` usually better than `@Component`?
A: When creating third-party or explicitly configured infrastructure objects.

</details>

<a id="sp-bean-004"></a>

<details>
<summary><strong>SP-BEAN-004. What is a @Configuration class?</strong></summary>

#### Short answer

A `@Configuration` class is a class that declares bean definitions and application configuration for the Spring container.

#### Interview answer

`@Configuration` marks a class as a source of bean definitions. It usually contains `@Bean` methods and may import other configurations, enable framework features or bind configuration properties.

In Spring Boot, configuration classes are often used to define explicit infrastructure: clients, serializers, executors, security chains or custom auto-configuration support.

#### Deep dive

Full `@Configuration` classes are enhanced by Spring so calls between `@Bean` methods can return the managed singleton instead of creating a new object directly.

#### Production angle

Good configuration classes make infrastructure decisions visible and reviewable, especially defaults that affect latency, security and resource usage.

#### Traps / caveats

- Putting business logic in configuration classes is a smell.
- Overusing broad `@ComponentScan` or `@Import` can make bean origins hard to trace.
- `proxyBeanMethods = false` changes behavior when `@Bean` methods call each other.

#### Optional Anki

Q: What does `@Configuration` primarily provide?
A: A source of bean definitions and configuration metadata.

</details>

<a id="sp-bean-005"></a>

<details>
<summary><strong>🧠 SP-BEAN-005. What is the difference between full @Configuration mode and lite @Bean mode, including calls between @Bean methods?</strong></summary>

#### Short answer

Full `@Configuration` classes are proxied so internal `@Bean` method calls return managed beans; lite mode does not intercept such calls.

#### Interview answer

In full mode, a class annotated with `@Configuration` is enhanced by Spring. If one `@Bean` method calls another, the call is intercepted and returns the container-managed bean, preserving singleton semantics.

In lite mode, such as `@Bean` methods on a plain `@Component` or `@Configuration(proxyBeanMethods = false)`, method calls are ordinary Java calls and may create new instances.

#### Deep dive

Lite mode is useful when `@Bean` methods are independent. It avoids proxy overhead and is common in Spring Boot auto-configuration where methods do not call each other.

#### Production angle

Incorrectly assuming full-mode behavior can create duplicate infrastructure objects such as clients, mappers or executors.

#### Traps / caveats

- `proxyBeanMethods = false` is safe only when `@Bean` methods do not depend on calling each other.
- Constructor injection between beans is often clearer than `@Bean` method calls.
- This is about calls inside configuration code, not normal dependency injection.

#### Optional Anki

Q: What happens when lite `@Bean` methods call each other?
A: They are normal Java calls and can create new instances.

</details>

<a id="sp-bean-006"></a>

<details>
<summary><strong>SP-BEAN-006. What is @Import used for?</strong></summary>

#### Short answer

`@Import` brings additional configuration classes or bean definitions into the current application context.

#### Interview answer

`@Import` is used to explicitly include configuration classes, selectors or registrars. It is common in framework integration, custom starters, modular configurations and tests.

Compared with component scanning, it is more explicit: the imported configuration is included because a specific class asked for it.

#### Deep dive

`@Import` can import regular configuration classes, `ImportSelector`s and `ImportBeanDefinitionRegistrar`s, which are often used by enabling annotations and auto-configuration-style infrastructure.

#### Production angle

Explicit imports help make optional modules predictable, especially in multi-module applications where component scanning can be too broad or too narrow.

#### Traps / caveats

- Imported configuration can create beans you did not expect.
- Import order can matter when conditions depend on existing beans.
- Do not use imports to hide unclear module boundaries.

#### Optional Anki

Q: Why use `@Import` instead of scanning?
A: To explicitly include known configuration or registrars.

</details>

<a id="sp-bean-007"></a>

<details>
<summary><strong>SP-BEAN-007. What is @Conditional used for?</strong></summary>

#### Short answer

`@Conditional` registers a bean or configuration only when a condition matches.

#### Interview answer

`@Conditional` lets Spring decide whether a bean definition should be active based on runtime metadata: classpath, properties, environment, existing beans, profiles or custom logic.

Spring Boot builds auto-configuration around conditional annotations, so defaults are applied only when they make sense.

#### Deep dive

Conditions are evaluated while the container is building bean definitions. They decide whether the definition is registered, not whether a method is called each time at runtime.

#### Production angle

Conditional beans allow one codebase to run in different environments, but they can also make startup behavior harder to understand without condition reports.

#### Traps / caveats

- Conditions can fail because a class is missing from the classpath.
- Bean-dependent conditions are sensitive to registration order.
- Conditional behavior should be documented for custom infrastructure.

#### Optional Anki

Q: What does `@Conditional` control?
A: Whether a bean or configuration is registered.

</details>

<a id="sp-bean-008"></a>

<details>
<summary><strong>SP-BEAN-008. How do @ConditionalOnClass, @ConditionalOnBean, @ConditionalOnMissingBean and @ConditionalOnProperty differ?</strong></summary>

#### Short answer

They match on classpath presence, existing beans, missing beans or configuration properties.

#### Interview answer

`@ConditionalOnClass` activates when a class is available. `@ConditionalOnBean` activates when a bean already exists. `@ConditionalOnMissingBean` activates only if no matching bean has been registered, which lets user beans override defaults. `@ConditionalOnProperty` activates based on configuration values.

These are common in Spring Boot auto-configuration.

#### Deep dive

The timing matters. Conditions based on beans only see definitions known at that point in processing, so auto-configuration ordering can affect outcomes.

#### Production angle

These annotations explain why adding a dependency, changing a property or defining a custom bean can silently change application behavior.

#### Traps / caveats

- `@ConditionalOnMissingBean` can back off if a bean exists but is not the one you intended.
- Property conditions can fail due to relaxed binding or wrong property source precedence.
- Classpath conditions mean dependencies can activate features automatically.

#### Optional Anki

Q: Which condition is commonly used to let user beans override Boot defaults?
A: `@ConditionalOnMissingBean`.

</details>

<a id="sp-bean-009"></a>

<details>
<summary><strong>SP-BEAN-009. What is the difference between @Primary and @Qualifier?</strong></summary>

#### Short answer

`@Primary` marks a default bean when several match by type; `@Qualifier` selects a specific bean at an injection point.

#### Interview answer

If multiple beans implement the same type, Spring needs to know which one to inject. `@Primary` says "use this one by default". `@Qualifier` says "use this specific one here".

`@Primary` is broad and central. `@Qualifier` is local and explicit. For important business choices, qualifiers often make the code easier to understand.

#### Deep dive

Qualifiers are not only bean names. Custom qualifier annotations can encode domain meaning, such as `@ExternalPayments` or `@InternalPayments`.

#### Production angle

Ambiguous injection errors often appear after adding a second implementation, such as another client, strategy or repository adapter.

#### Traps / caveats

- Overusing `@Primary` can hide which implementation is being used.
- Qualifier strings can become fragile if names are refactored manually.
- Collection injection includes all matching beans, not just the primary one.

#### Optional Anki

Q: What is the main difference between `@Primary` and `@Qualifier`?
A: `@Primary` chooses a default; `@Qualifier` chooses a specific bean at an injection point.

</details>

<a id="sp-bean-010"></a>

<details>
<summary><strong>SP-BEAN-010. How does Spring choose a bean for injection by type, name and qualifier?</strong></summary>

#### Short answer

Spring first finds beans assignable to the required type, then narrows candidates with qualifiers, primary markers, priority and sometimes the injection point name.

#### Interview answer

For a single-valued dependency, Spring resolves candidates by type. If there is exactly one candidate, it injects it. If multiple candidates exist, qualifiers, `@Primary`, priority/order metadata and the injection point name can disambiguate.

If Spring still cannot choose, it throws `NoUniqueBeanDefinitionException`. If no candidate exists, it throws `NoSuchBeanDefinitionException`.

#### Deep dive

The exact resolution algorithm has details, but in interviews the practical model is: type first, then qualifier or primary, then name as a fallback.

#### Production angle

Adding a new implementation can break startup if injection points were relying on a single candidate.

#### Traps / caveats

- Parameter names may not be available unless compiled with metadata.
- `@Primary` does not mean "only bean".
- Generics can also help narrow candidates in some cases.

#### Optional Anki

Q: What is the first step in Spring dependency resolution?
A: Find beans assignable to the required type.

</details>

<a id="sp-bean-011"></a>

<details>
<summary><strong>SP-BEAN-011. How can Spring inject all beans of a given type into a List or Map, and how do @Order and Ordered affect that?</strong></summary>

#### Short answer

Spring can inject all matching beans into a collection; `@Order` or `Ordered` controls ordering for ordered collections.

#### Interview answer

If a constructor asks for `List<PaymentHandler>`, Spring injects all beans of that type. For `Map<String, PaymentHandler>`, keys are bean names and values are beans. This is useful for strategies, validators, filters and plugin-like behavior.

Ordering can be controlled with `@Order`, `Ordered` or priority annotations. That matters when handlers are tried sequentially.

#### Deep dive

Collection injection is often cleaner than a large `if/else` or manually maintained registry. The strategy can expose a method like `supports(type)`.

#### Production angle

Ordered handlers are common in validation, routing, enrichment, pricing and integration pipelines. Wrong order can cause subtle behavior changes.

#### Traps / caveats

- `@Order` affects collection order, not normal single-bean priority in every case.
- Map keys are bean names, which may not be stable if generated.
- All matching beans are created unless lazy/provider patterns are used.

#### Optional Anki

Q: What does `Map<String, SomeType>` injection usually use as keys?
A: Spring bean names.

</details>

<a id="sp-bean-012"></a>

<details>
<summary><strong>SP-BEAN-012. How can you implement the Strategy pattern with Spring beans?</strong></summary>

#### Short answer

Define a common strategy interface, implement each strategy as a bean, inject a collection, and select the right strategy by a key or `supports()` method.

#### Interview answer

For example, each payment provider can implement `PaymentStrategy`. Spring injects `List<PaymentStrategy>` or `Map<String, PaymentStrategy>` into an orchestrator. The orchestrator selects a strategy based on provider, country, feature flag or request type.

This keeps the selection open for new implementations without changing a central switch every time.

#### Deep dive

For small fixed choices, an explicit map in configuration can be clearer. For larger extension points, collection injection plus validation at startup is often better.

#### Production angle

Strategy beans make feature rollout, provider migration and integration testing easier because implementations are isolated.

#### Traps / caveats

- Make selection deterministic; do not depend accidentally on classpath order.
- Validate duplicate keys at startup.
- Keep business fallback behavior explicit.

#### Optional Anki

Q: Common Spring-friendly way to implement Strategy?
A: Inject all strategy beans and choose by key or `supports()`.

</details>

<a id="sp-bean-013"></a>

<details>
<summary><strong>🧠 SP-BEAN-013. What is a FactoryBean, and how is it different from a regular factory method?</strong></summary>

#### Short answer

`FactoryBean<T>` is a special Spring contract where the bean produces another object as its exposed value.

#### Interview answer

A regular `@Bean` factory method returns the bean instance directly. A `FactoryBean` is itself a bean, but when you ask for its name, Spring usually returns the object produced by `getObject()`, not the factory instance.

It is used for framework-level integration when creating an object requires special logic, proxies or metadata.

#### Deep dive

To retrieve the factory itself, Spring uses the `&beanName` convention. Many developers rarely implement `FactoryBean` directly, but it appears in infrastructure such as proxy factories.

#### Production angle

Understanding `FactoryBean` helps explain why a bean's runtime type may not be the class that registered the bean definition.

#### Traps / caveats

- It is not the same as a static factory method.
- Type prediction can be tricky if `getObjectType()` is not accurate.
- Business applications usually do not need custom `FactoryBean`s.

#### Optional Anki

Q: What does a `FactoryBean` expose by default?
A: The object produced by `getObject()`.

</details>

<a id="sp-bean-014"></a>

<details>
<summary><strong>SP-BEAN-014. What is ObjectProvider, and how can it help with optional, lazy or dynamic dependencies?</strong></summary>

#### Short answer

`ObjectProvider<T>` lets code request a dependency lazily, optionally or as a stream of candidates from the Spring container.

#### Interview answer

`ObjectProvider` is useful when a dependency may not exist, should be resolved only when needed, or has multiple candidates. It provides methods like `getIfAvailable()`, `getObject()` and ordered streams.

It can avoid eager initialization and make optional infrastructure cleaner than injecting `ApplicationContext`.

#### Deep dive

`ObjectProvider` keeps the dependency typed and local to the injection point. It is often used in auto-configuration and reusable libraries where not every application supplies the same beans.

#### Production angle

Lazy lookup can avoid startup cost for rarely used integrations, but it can also move failures to runtime.

#### Traps / caveats

- Do not use `ObjectProvider` to hide poor boundaries.
- `getObject()` still fails if no bean exists.
- Lazy resolution should be covered by tests or readiness checks for critical paths.

#### Optional Anki

Q: Why prefer `ObjectProvider` over `ApplicationContext.getBean()`?
A: It keeps lookup typed, local and easier to test.

</details>

<a id="sp-bean-015"></a>

<details>
<summary><strong>SP-BEAN-015. How would you debug why a bean was not created or injected?</strong></summary>

#### Short answer

Check component scanning, conditions, profiles, properties, bean type, qualifiers, auto-configuration reports and startup logs.

#### Interview answer

I would first check whether the class is under the component scan path or declared through `@Bean` or `@Import`. Then I would inspect active profiles, conditional annotations, property values and whether the required dependency type actually matches.

In Spring Boot, the condition evaluation report, `--debug`, Actuator `conditions` and `beans` endpoints, and startup logs are useful.

#### Deep dive

For injection failures, distinguish "no bean exists" from "multiple beans exist" and from "the bean exists but does not match the required generic type or qualifier".

#### Production angle

Bean creation problems often appear after dependency upgrades, package moves, profile changes or missing environment variables.

#### Traps / caveats

- A bean can be excluded by profile or property even though its code is present.
- Proxies can change the visible runtime type.
- Test slices intentionally load only part of the application context.

#### Optional Anki

Q: Spring Boot tool for checking why auto-configuration matched or did not match?
A: The condition evaluation report.

</details>
