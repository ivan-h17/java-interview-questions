# 16.08. Auto-configuration and starters

---

<a id="sp-auto-001"></a>

<details>
<summary><strong>SP-AUTO-001. What is auto-configuration in Spring Boot?</strong></summary>

#### Short answer

Auto-configuration is Spring Boot's mechanism for creating sensible default beans based on the classpath, properties and existing beans.

#### Interview answer

Spring Boot looks at what libraries are present and what beans/properties already exist, then configures common infrastructure automatically. For example, if MVC and Jackson are on the classpath, Boot configures web MVC and JSON support. If JPA and a data source exist, it configures JPA infrastructure.

User-defined beans can override many defaults.

#### Deep dive

Auto-configuration is conditional configuration, not magic. It is ordinary Spring configuration guarded by conditions.

#### Production angle

It speeds up service development, but teams must know which defaults are active for security, timeouts, data access and observability.

#### Traps / caveats

- Adding a dependency can activate new auto-configuration.
- Defaults may not match production requirements.
- Auto-configuration can back off because of a custom bean.

#### Optional Anki

Q: What inputs does Boot auto-configuration commonly use?
A: Classpath, properties and existing beans.

</details>

<a id="sp-auto-002"></a>

<details>
<summary><strong>SP-AUTO-002. How does Spring Boot auto-configuration work?</strong></summary>

#### Short answer

Boot imports auto-configuration classes and evaluates conditions to decide which bean definitions to register.

#### Interview answer

During startup, Boot discovers auto-configuration classes from metadata, imports them, and evaluates conditional annotations. If the conditions match, those classes register beans. If user-defined beans already exist or required classes/properties are missing, the auto-configuration may back off.

The condition evaluation report shows these decisions.

#### Deep dive

Auto-configurations are ordered so foundational infrastructure is available before dependent configuration.

#### Production angle

Debugging Boot often means explaining why a specific auto-configuration matched, did not match, or created a bean with default settings.

#### Traps / caveats

- Conditions are evaluated during context creation, not dynamically per request.
- Ordering can affect bean-dependent conditions.
- Custom beans can disable expected defaults.

#### Optional Anki

Q: What report explains Boot auto-configuration decisions?
A: The condition evaluation report.

</details>

<a id="sp-auto-003"></a>

<details>
<summary><strong>SP-AUTO-003. How is auto-configuration discovered in modern Spring Boot?</strong></summary>

#### Short answer

Modern Boot discovers auto-configuration from `AutoConfiguration.imports` metadata in jars.

#### Interview answer

Spring Boot auto-configuration classes are listed in metadata under `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`. Boot reads those imports and applies them through its auto-configuration import mechanism.

Older Boot versions used `spring.factories` for this purpose, so version matters when creating custom starters.

#### Deep dive

The imported classes are still normal Spring configuration classes, commonly annotated with `@AutoConfiguration` and conditional annotations.

#### Production angle

When a custom starter does not work, checking whether its auto-configuration metadata is packaged correctly is one of the first steps.

#### Traps / caveats

- Using the old metadata style in a modern-only starter may fail.
- The file path and class names must be exact.
- The auto-configuration jar must actually be on the runtime classpath.

#### Optional Anki

Q: Modern Boot metadata file for auto-config imports?
A: `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`.

</details>

<a id="sp-auto-004"></a>

<details>
<summary><strong>SP-AUTO-004. What are conditional annotations in Spring Boot auto-configuration?</strong></summary>

#### Short answer

They are annotations that make auto-configuration apply only when specific classpath, bean, property, resource or environment conditions match.

#### Interview answer

Conditional annotations let Boot provide defaults without forcing them on every application. Examples include `@ConditionalOnClass`, `@ConditionalOnMissingBean`, `@ConditionalOnProperty`, `@ConditionalOnWebApplication` and `@ConditionalOnResource`.

They are what make "convention over configuration" safe enough for different applications.

#### Deep dive

Conditions can be placed on configuration classes or individual bean methods.

#### Production angle

A wrong property, missing dependency or unexpected custom bean can change which infrastructure is active.

#### Traps / caveats

- Conditions can interact in non-obvious ways.
- Negative conditions such as missing bean depend on timing.
- Do not assume an auto-configured bean exists without checking conditions.

#### Optional Anki

Q: Why does Boot use conditional annotations?
A: To apply defaults only when they fit the application.

</details>

<a id="sp-auto-005"></a>

<details>
<summary><strong>SP-AUTO-005. How do @ConditionalOnClass, @ConditionalOnBean, @ConditionalOnMissingBean and @ConditionalOnProperty affect auto-configuration?</strong></summary>

#### Short answer

They activate configuration based on class presence, bean presence, bean absence or property values.

#### Interview answer

`@ConditionalOnClass` means "configure this only if a library is present". `@ConditionalOnBean` means "only if some required bean exists". `@ConditionalOnMissingBean` means "create a default only if the user has not supplied one". `@ConditionalOnProperty` means "enable this based on configuration".

Together they let Boot adapt to many application shapes.

#### Deep dive

Bean conditions are evaluated against known bean definitions at that point, which is why auto-configuration ordering matters.

#### Production angle

Adding a jar, renaming a property or defining a custom bean can change startup behavior without changing business code.

#### Traps / caveats

- `@ConditionalOnMissingBean` can back off because of a bean from another module.
- Property values may come from surprising sources due to precedence.
- Classpath conditions can activate vulnerable or unwanted features if dependencies are added casually.

#### Optional Anki

Q: Which condition lets a user-defined bean override a Boot default?
A: `@ConditionalOnMissingBean`.

</details>

<a id="sp-auto-006"></a>

<details>
<summary><strong>SP-AUTO-006. How can user-defined beans override auto-configured beans?</strong></summary>

#### Short answer

Many auto-configurations use `@ConditionalOnMissingBean`, so defining your own bean of the expected type or name makes Boot back off.

#### Interview answer

If Boot is about to create a default `ObjectMapper`, client builder, security chain or data source helper, it often first checks whether the application already provides one. If a matching user bean exists, auto-configuration does not create its default.

This is the normal customization path: define explicit beans for behavior that matters.

#### Deep dive

Some customizations are better done through customizer beans rather than replacing the whole infrastructure bean.

#### Production angle

Replacing a default bean can remove Boot-provided settings such as metrics, converters, tracing or security integration.

#### Traps / caveats

- Matching by type can be broader than expected.
- Replacing a bean can disable auto-configured collaborators.
- Prefer documented customizer extension points when available.

#### Optional Anki

Q: Common Boot mechanism for backing off from defaults?
A: `@ConditionalOnMissingBean`.

</details>

<a id="sp-auto-007"></a>

<details>
<summary><strong>SP-AUTO-007. How can you exclude an auto-configuration?</strong></summary>

#### Short answer

Use `exclude` on `@SpringBootApplication`/`@EnableAutoConfiguration` or the `spring.autoconfigure.exclude` property.

#### Interview answer

If an auto-configuration should not apply, you can exclude its class in the application annotation or through configuration properties. This is sometimes needed when Boot defaults conflict with custom infrastructure.

I treat exclusions as a strong signal that the reason should be documented.

#### Deep dive

It is often better to customize or provide a bean than to exclude a large auto-configuration if only one default is unwanted.

#### Production angle

Exclusions can remove useful infrastructure unexpectedly, such as metrics, converters or security setup.

#### Traps / caveats

- Excluding broad auto-configuration can create missing-bean failures later.
- Class names can change across major upgrades.
- Prefer condition reports to confirm the exclusion did what you intended.

#### Optional Anki

Q: Property for excluding Boot auto-configurations?
A: `spring.autoconfigure.exclude`.

</details>

<a id="sp-auto-008"></a>

<details>
<summary><strong>SP-AUTO-008. How can you see why an auto-configuration was or was not applied?</strong></summary>

#### Short answer

Use the condition evaluation report, debug logging, Actuator `conditions` endpoint and bean inspection.

#### Interview answer

In Boot, running with `--debug` prints a condition evaluation report. Actuator can expose a `conditions` endpoint showing matched and unmatched auto-configurations. The `beans` endpoint and startup logs help confirm what was actually created.

For tests, failed condition reports often reveal missing classes, properties or existing beans.

#### Deep dive

The report shows positive and negative matches. Negative matches are often more useful for missing-bean debugging.

#### Production angle

Condition reports help explain environment-specific behavior, especially when staging and production have different properties or dependencies.

#### Traps / caveats

- Expose Actuator diagnostics carefully; they can reveal internals.
- Debug logs can be noisy.
- A matched auto-configuration may still not create every bean if method-level conditions fail.

#### Optional Anki

Q: Actuator endpoint for auto-configuration condition details?
A: `conditions`.

</details>

<a id="sp-auto-009"></a>

<details>
<summary><strong>SP-AUTO-009. What is the difference between a starter and auto-configuration?</strong></summary>

#### Short answer

A starter is a dependency bundle; auto-configuration is code that configures beans conditionally.

#### Interview answer

A Spring Boot starter usually brings a set of dependencies and may include or depend on auto-configuration. Auto-configuration contains the actual Spring configuration classes that register beans.

For example, a web starter brings MVC, JSON and server dependencies; auto-configuration configures MVC infrastructure and the embedded server.

#### Deep dive

A custom starter commonly has two artifacts or logical parts: the starter dependency package and the auto-configuration implementation.

#### Production angle

Adding a starter changes the classpath and can activate auto-configuration, so dependency review matters.

#### Traps / caveats

- A starter alone does not guarantee a feature is enabled; conditions still apply.
- Auto-configuration can exist without a starter.
- Starters can pull transitive dependencies that affect behavior.

#### Optional Anki

Q: Starter vs auto-configuration?
A: Starter packages dependencies; auto-configuration creates beans.

</details>

<a id="sp-auto-010"></a>

<details>
<summary><strong>SP-AUTO-010. What do common starters such as spring-boot-starter-web, spring-boot-starter-data-jpa and spring-boot-starter-security usually configure?</strong></summary>

#### Short answer

They bring dependencies that allow Boot to configure MVC/JSON/server support, JPA/data source integration and default security infrastructure.

#### Interview answer

`spring-boot-starter-web` usually brings Spring MVC, JSON support and an embedded servlet server. `spring-boot-starter-data-jpa` brings Spring Data JPA, Hibernate and transaction/data source integration. `spring-boot-starter-security` brings Spring Security and activates default security behavior if no custom configuration overrides it.

The exact beans depend on conditions and application properties.

#### Deep dive

Starters affect the classpath. Auto-configurations react to that classpath and existing beans.

#### Production angle

Adding `starter-security` can suddenly require authentication. Adding JPA can create database initialization behavior. These changes should be intentional.

#### Traps / caveats

- Starters include transitive dependencies.
- Default security is protective but not a complete application security policy.
- Data starters need correct pooling, migrations and transaction configuration.

#### Optional Anki

Q: What does `spring-boot-starter-web` commonly bring?
A: Spring MVC, JSON support and an embedded servlet server.

</details>

<a id="sp-auto-011"></a>

<details>
<summary><strong>🧠 SP-AUTO-011. How would you create a custom Spring Boot starter?</strong></summary>

#### Short answer

Package dependencies and auto-configuration metadata so applications can add one dependency and get conditional, overridable defaults.

#### Interview answer

I would define the library API, create auto-configuration classes with conditional beans, add configuration properties with metadata, register auto-configuration imports, and create a starter artifact that pulls the needed dependencies.

The defaults should back off when users define their own beans and should be documented.

#### Deep dive

Good starters expose customizer beans rather than forcing replacement of whole infrastructure objects.

#### Production angle

Internal starters standardize clients, observability, security defaults and integration policies across services.

#### Traps / caveats

- Do not create mandatory beans that cannot be overridden.
- Do not perform network calls during auto-configuration.
- Test the starter in a sample app and with missing optional dependencies.

#### Optional Anki

Q: What should a good starter default do when the app provides its own bean?
A: Back off where appropriate.

</details>

<a id="sp-auto-012"></a>

<details>
<summary><strong>🧠 SP-AUTO-012. How would you create custom auto-configuration?</strong></summary>

#### Short answer

Write a configuration class with conditional bean methods, register it in Boot auto-configuration metadata and test its conditions.

#### Interview answer

A custom auto-configuration should use `@AutoConfiguration`, `@ConditionalOnClass`, `@ConditionalOnProperty`, `@ConditionalOnMissingBean` and configuration properties where appropriate. Then register it in the auto-configuration imports file.

I would test positive and negative cases: dependency present/missing, property enabled/disabled, user bean present and absent.

#### Deep dive

Auto-configuration should configure infrastructure, not application-specific business logic.

#### Production angle

Reliable auto-configuration reduces copy-paste configuration across services while keeping local overrides possible.

#### Traps / caveats

- Missing metadata means the class is never imported.
- Conditions that are too broad activate unexpectedly.
- Conditions that are too narrow make the starter look broken.

#### Optional Anki

Q: What file registers modern Boot auto-configuration?
A: `AutoConfiguration.imports`.

</details>

<a id="sp-auto-013"></a>

<details>
<summary><strong>🧠 SP-AUTO-013. How do you order auto-configurations?</strong></summary>

#### Short answer

Use Boot ordering annotations such as auto-configure before/after when one auto-configuration depends on another.

#### Interview answer

Auto-configurations sometimes depend on beans or conditions created by other auto-configurations. Boot supports ordering metadata such as "before" and "after" relationships. Use it when there is a real dependency, for example configuring a client after core HTTP infrastructure.

Do not overuse ordering as a substitute for clear conditions.

#### Deep dive

Ordering controls when configuration classes are processed, which can affect bean conditions like `@ConditionalOnBean` and `@ConditionalOnMissingBean`.

#### Production angle

Wrong ordering can make a custom starter work in one application and fail in another because bean-dependent conditions see different state.

#### Traps / caveats

- Ordering does not force beans to be created eagerly.
- Avoid cycles in ordering relationships.
- Prefer robust conditions over fragile order assumptions.

#### Optional Anki

Q: Why can auto-configuration ordering matter?
A: Bean-dependent conditions may see different definitions depending on processing order.

</details>

<a id="sp-auto-014"></a>

<details>
<summary><strong>SP-AUTO-014. What are common dangers of relying blindly on auto-configuration?</strong></summary>

#### Short answer

You may accept defaults for security, timeouts, pools, serialization, migrations or observability without understanding their production impact.

#### Interview answer

Auto-configuration is useful, but it can hide important decisions. For example, default security may block endpoints, missing HTTP timeouts may hurt resilience, default Jackson settings may expose fields, or data source defaults may be too small or too large.

Senior developers should inspect and explicitly configure production-sensitive behavior.

#### Deep dive

The danger is not auto-configuration itself. The danger is treating it as unknowable magic.

#### Production angle

Production incidents often come from implicit defaults changing after dependency upgrades or starter additions.

#### Traps / caveats

- Defaults are starting points, not design decisions.
- Upgrades can change defaults.
- Explicit custom beans can accidentally disable useful Boot integration.

#### Optional Anki

Q: Main senior stance toward auto-configuration?
A: Use it, but know and override production-sensitive defaults.

</details>

<a id="sp-auto-015"></a>

<details>
<summary><strong>SP-AUTO-015. How would you debug an unexpected bean created by auto-configuration?</strong></summary>

#### Short answer

Find its origin in the bean list, inspect the condition report, identify matching conditions and decide whether to customize, override or exclude.

#### Interview answer

I would use Actuator `beans`, startup logs or IDE navigation to find the bean definition source. Then I would inspect the condition evaluation report for the auto-configuration class and bean method. I would check classpath dependencies, properties and existing beans that caused the condition to match.

Then I would choose the least invasive fix: property change, customizer bean, explicit replacement bean or exclusion.

#### Deep dive

Unexpected beans often appear after adding a starter or transitive dependency.

#### Production angle

This avoids random exclusions and helps document why a default was or was not appropriate.

#### Traps / caveats

- Excluding auto-configuration may remove more than the one bean.
- Defining a replacement bean may lose Boot customizers.
- The bean may be imported by a custom internal starter.

#### Optional Anki

Q: First diagnostic for unexpected Boot beans?
A: Inspect bean origin and the condition evaluation report.

</details>
