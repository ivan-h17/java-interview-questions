# 16.12. Spring Data JPA and persistence integration

---

<a id="sp-data-001"></a>

<details>
<summary><strong>SP-DATA-001. What is Spring Data JPA?</strong></summary>

#### Short answer

Spring Data JPA is a Spring Data module that simplifies repository implementation on top of JPA.

#### Interview answer

Spring Data JPA provides repository interfaces, query derivation, pagination, projections, specifications and integration with Spring transactions. It reduces boilerplate around common persistence operations while still using JPA providers such as Hibernate underneath.

It is not a replacement for understanding JPA, fetching, transactions and database performance.

#### Deep dive

Repositories are usually proxies generated by Spring. Method calls are translated into JPA operations or queries.

#### Production angle

Spring Data JPA speeds development but can hide expensive queries, N+1 problems and count queries if used casually.

#### Traps / caveats

- It does not make database access automatically efficient.
- Derived queries can become unreadable.
- Repository methods still need transaction and fetch-plan awareness.

#### Optional Anki

Q: What does Spring Data JPA build on?
A: JPA, commonly with Hibernate as the provider.

</details>

<a id="sp-data-002"></a>

<details>
<summary><strong>SP-DATA-002. What is the difference between CrudRepository, PagingAndSortingRepository and JpaRepository?</strong></summary>

#### Short answer

`CrudRepository` provides basic CRUD, `PagingAndSortingRepository` adds pagination/sorting, and `JpaRepository` adds JPA-specific operations.

#### Interview answer

`CrudRepository` has basic save, find, delete operations. `PagingAndSortingRepository` adds methods for paging and sorting. `JpaRepository` extends repository capabilities with JPA-specific methods such as flushing and batch delete variants.

Most Spring Data JPA repositories extend `JpaRepository` when they need the full JPA feature set.

#### Deep dive

Choosing a smaller interface can make the intended repository surface clearer, but many projects standardize on `JpaRepository`.

#### Production angle

Repository interface choice is less important than query design, transaction boundaries and fetch behavior.

#### Traps / caveats

- `save()` semantics depend on entity state.
- Flush-related methods can force SQL earlier than expected.
- Bulk delete/update operations can bypass normal entity state assumptions.

#### Optional Anki

Q: Which repository interface is JPA-specific?
A: `JpaRepository`.

</details>

<a id="sp-data-003"></a>

<details>
<summary><strong>SP-DATA-003. How do derived query methods work?</strong></summary>

#### Short answer

Spring Data parses repository method names and derives queries from property names and keywords.

#### Interview answer

A method such as `findByStatusAndCreatedAtAfter` is parsed into a query based on entity property names and supported keywords. Spring Data validates and creates the query at startup or repository initialization.

Derived queries are convenient for simple conditions but become hard to read for complex logic.

#### Deep dive

The method name is part of the query contract. Renaming entity properties without updating methods can break startup.

#### Production angle

Derived queries should be reviewed like SQL: expected indexes, result size, sorting and fetch plan still matter.

#### Traps / caveats

- Long method names are a smell.
- Derived queries do not automatically solve N+1.
- Ambiguous property names can create surprising parsing failures.

#### Optional Anki

Q: When should a derived query be replaced?
A: When the method name becomes complex or query behavior needs explicit control.

</details>

<a id="sp-data-004"></a>

<details>
<summary><strong>SP-DATA-004. When would you use @Query, Specification or a custom repository implementation?</strong></summary>

#### Short answer

Use `@Query` for explicit fixed queries, `Specification` for composable dynamic predicates, and custom repositories for complex or performance-sensitive logic.

#### Interview answer

`@Query` is good when the query should be explicit JPQL or native SQL. `Specification` works when filters are built dynamically from optional criteria. A custom repository implementation is better when query construction, joins, locking, batching or result mapping becomes too complex for repository method names.

The choice should make the query understandable and testable.

#### Deep dive

Native queries can use database-specific features but reduce portability and may need manual count queries for pagination.

#### Production angle

Complex read paths should be optimized deliberately rather than hidden inside derived method names.

#### Traps / caveats

- Specifications can become hard to optimize if composed blindly.
- Native queries need migration awareness.
- `@Query` does not define a fetch plan unless written to do so.

#### Optional Anki

Q: Best option for composable dynamic filters in Spring Data JPA?
A: `Specification`.

</details>

<a id="sp-data-005"></a>

<details>
<summary><strong>SP-DATA-005. How do Page, Slice, sorting and generated count queries affect API and database performance?</strong></summary>

#### Short answer

`Page` requires total count information, `Slice` only checks if there is a next page, and sorting must match database indexes for good performance.

#### Interview answer

`Page` returns content plus total elements/pages, so Spring Data often runs a count query. On large or complex joins, that count can be expensive. `Slice` avoids total count and is useful for "load more" APIs. Sorting can force expensive database work if not supported by an index.

Pagination should be designed with database access patterns in mind.

#### Deep dive

Offset pagination gets slower for deep pages. Keyset pagination may be better for large ordered datasets.

#### Production angle

Slow count queries and deep offsets are common causes of slow list endpoints.

#### Traps / caveats

- Generated count queries can be wrong or inefficient for complex joins.
- Sorting by non-indexed columns can hurt performance.
- Public APIs should set max page sizes.

#### Optional Anki

Q: When is `Slice` preferable to `Page`?
A: When the API only needs to know whether a next page exists.

</details>

<a id="sp-data-006"></a>

<details>
<summary><strong>SP-DATA-006. What are interface-based and class-based projections?</strong></summary>

#### Short answer

Projections let repository queries return selected fields instead of full entities, using interfaces, DTO classes or records.

#### Interview answer

Interface projections define getters for selected fields and Spring creates proxy-like results. Class-based projections use constructors, often DTOs or records. Projections reduce data loading and can make read models explicit.

They are useful when an endpoint needs only a subset of entity data.

#### Deep dive

Nested projections and open projections can trigger more work than expected. Constructor projections are often clearer for stable API read models.

#### Production angle

Projections can reduce memory and query cost, but only if the generated query actually selects fewer fields and avoids unwanted joins.

#### Traps / caveats

- Projection behavior depends on query type and provider.
- Open projections using expressions can be expensive.
- Do not treat projections as a replacement for API DTO design in all cases.

#### Optional Anki

Q: Why use Spring Data projections?
A: To return a focused read model without loading full entities.

</details>

<details>
<summary><strong>SP-DATA-007. What is EntityManager, and when would you use it directly?</strong></summary>

#### Short answer

`EntityManager` is the JPA API for managing persistence context, entities and queries.

#### Interview answer

Spring Data repositories cover common operations, but `EntityManager` is useful for custom queries, batch operations, explicit flush/clear, locking, hints, native queries or advanced persistence context control.

Use it when repository abstractions become too limiting or unclear.

#### Deep dive

The persistence context tracks managed entities and flushes changes to the database, usually within a transaction.

#### Production angle

Direct `EntityManager` use can improve performance for batch or custom query paths, but it requires stronger JPA knowledge.

#### Traps / caveats

- Forgetting to clear during large batch processing can grow memory.
- Flush timing can surprise developers.
- Native queries bypass some JPA portability.

#### Optional Anki

Q: What does `EntityManager` manage?
A: The JPA persistence context and entity operations.

</details>

<a id="sp-data-008"></a>

<details>
<summary><strong>SP-DATA-008. How should repository methods participate in service-layer transactions?</strong></summary>

#### Short answer

Repositories should usually run inside transactions defined by service/application methods.

#### Interview answer

Spring Data repository methods may have default transactional behavior, but business use cases usually need a service-layer transaction that covers multiple repository operations. Repositories should focus on persistence, not orchestrating business transactions.

This keeps consistency boundaries explicit.

#### Deep dive

Read-only repository methods can be used inside a read-only service transaction, while writes should be part of the service use case transaction.

#### Production angle

Service-level transactions prevent partial commits across multi-step business operations.

#### Traps / caveats

- Repository-only transactions can split one use case into multiple commits.
- Controller-level transactions can hold connections too long.
- Async boundaries do not preserve transactions automatically.

#### Optional Anki

Q: Where should complex business transaction boundaries usually live?
A: Service/application layer.

</details>

<a id="sp-data-009"></a>

<details>
<summary><strong>SP-DATA-009. What is Open EntityManager in View / Open Session in View, and why can it hide performance problems?</strong></summary>

#### Short answer

OSIV keeps the JPA persistence context open during web request rendering, allowing lazy loading outside service transactions.

#### Interview answer

Open EntityManager in View keeps an `EntityManager` available for the whole web request. This prevents some `LazyInitializationException`s when controllers or JSON serialization access lazy associations after service methods return.

The downside is that database queries can happen during serialization, outside clear service boundaries, often hiding N+1 problems.

#### Deep dive

OSIV can make simple apps convenient but weakens the discipline of explicit fetch planning and DTO mapping.

#### Production angle

OSIV can cause slow endpoints, connection pressure and unexpected SQL from JSON serialization.

#### Traps / caveats

- It can hide poor fetch design until load increases.
- Disabling OSIV may reveal real boundary issues.
- Returning entities from controllers makes OSIV problems worse.

#### Optional Anki

Q: Why is OSIV risky?
A: It allows lazy database access during web rendering/serialization.

</details>

<a id="sp-data-010"></a>

<details>
<summary><strong>SP-DATA-010. How can Spring Data JPA queries cause N+1 problems, and how can EntityGraph help?</strong></summary>

#### Short answer

Loading entities and then lazily accessing associations can issue one query per row; `EntityGraph` can request needed associations in the original fetch plan.

#### Interview answer

A repository may load a list of orders with one query. If code then accesses `order.customer` or `order.items` lazily for each row, Hibernate may issue additional queries per order. That is N+1.

`@EntityGraph` can tell JPA to fetch selected associations with the main query, making the fetch plan explicit.

#### Deep dive

Entity graphs are one tool. Join fetches, projections, batch fetching and query redesign are also options.

#### Production angle

N+1 problems often appear as endpoints that are fast in tests but slow with production-sized data.

#### Traps / caveats

- Fetching too much can create huge result sets.
- Pagination with fetch joins can be tricky.
- Entity graphs must match the endpoint's read model.

#### Optional Anki

Q: What is the N+1 query pattern?
A: One query for parents plus one query per parent for related data.

</details>

<details>
<summary><strong>SP-DATA-011. How do you configure database migrations with Flyway or Liquibase in Spring Boot?</strong></summary>

#### Short answer

Add the migration tool dependency, provide migration files and configure Boot properties for the data source and migration behavior.

#### Interview answer

Spring Boot auto-configures Flyway or Liquibase when the dependency is present. Migration scripts live in conventional locations unless configured otherwise. On startup, the tool checks schema history and applies pending migrations.

Production migration behavior should be deliberate: ordering, rollback strategy, locking and deployment compatibility matter.

#### Deep dive

Many teams run migrations as part of deployment rather than from every application replica, depending on platform and risk.

#### Production angle

Migrations must be backward compatible during rolling deployments.

#### Traps / caveats

- Do not let multiple replicas race unsafe migrations.
- Large blocking migrations can cause downtime.
- Schema changes and application rollout must be coordinated.

#### Optional Anki

Q: What does Boot do when Flyway is on the classpath?
A: It can auto-configure and run Flyway migrations.

</details>

<a id="sp-data-012"></a>

<details>
<summary><strong>SP-DATA-012. How does Spring Boot auto-configure a DataSource and HikariCP?</strong></summary>

#### Short answer

Boot creates a `DataSource` from configured properties and uses HikariCP as the common default connection pool when available.

#### Interview answer

With JDBC/JPA dependencies and database properties, Boot auto-configures a `DataSource`. HikariCP is commonly used as the default pool. Properties define URL, username, password, driver and pool settings such as max size, idle timeout and connection timeout.

If multiple data sources exist, explicit configuration is usually needed.

#### Deep dive

Boot also configures related infrastructure such as transaction managers, JDBC templates and JPA integration depending on dependencies.

#### Production angle

Pool sizing must match application concurrency and database capacity, not just CPU count.

#### Traps / caveats

- Too large a pool can overload the database.
- Missing timeouts can make failures slow.
- Secrets must be supplied securely.

#### Optional Anki

Q: Common default JDBC connection pool in Spring Boot?
A: HikariCP.

</details>

<details>
<summary><strong>SP-DATA-013. How do you configure SQL logging safely?</strong></summary>

#### Short answer

Use targeted SQL logging in lower environments and production diagnostics carefully, avoiding sensitive parameter leakage and excessive volume.

#### Interview answer

Hibernate SQL logging and parameter binding logs can help debug queries, but full SQL with values may leak PII or secrets and create huge logs. For production, prefer metrics, slow query logs, sampling, correlation IDs and database-side diagnostics.

Enable detailed SQL logging temporarily and with access controls.

#### Deep dive

Tools like datasource proxies can log timing and query count, but they should be configured safely.

#### Production angle

SQL visibility is essential for diagnosing slow endpoints and N+1, but unsafe logging can become a security incident.

#### Traps / caveats

- Parameter logs can expose personal data.
- Logging every query under load can hurt performance.
- SQL logs without request correlation are less useful.

#### Optional Anki

Q: Main risk of SQL parameter logging?
A: Sensitive data leakage.

</details>

<a id="sp-data-014"></a>

<details>
<summary><strong>SP-DATA-014. How do bulk repository updates interact with the persistence context?</strong></summary>

#### Short answer

Bulk updates bypass normal entity state tracking, so the persistence context may contain stale entities.

#### Interview answer

JPQL or native bulk update/delete operations execute directly against the database and do not update already-managed entity instances in the persistence context. After a bulk operation, managed entities may no longer match database state.

You may need to flush and clear the persistence context or avoid mixing bulk updates with loaded entities.

#### Deep dive

Spring Data modifying queries can be configured with flush/clear behavior, but use it deliberately.

#### Production angle

Stale persistence context state can lead to wrong responses or overwriting database changes later in the transaction.

#### Traps / caveats

- Entity callbacks and dirty checking do not apply normally to bulk updates.
- Bulk deletes can bypass cascade expectations.
- Test with realistic transaction boundaries.

#### Optional Anki

Q: Why can bulk JPQL updates make managed entities stale?
A: They update the database directly and bypass persistence context tracking.

</details>

<details>
<summary><strong>SP-DATA-015. How would you debug a slow endpoint caused by JPA queries?</strong></summary>

#### Short answer

Correlate endpoint traces with SQL count, query timings, execution plans, fetch behavior, transaction boundaries and database metrics.

#### Interview answer

I would capture traces and logs to identify which repository calls are slow and how many SQL statements execute. Then I would check for N+1 queries, slow count queries, missing indexes, bad joins, large result sets, lazy loading during serialization and long transactions.

Database `EXPLAIN` plans and production-like data are essential.

#### Deep dive

Slow endpoint debugging should include both Java-side evidence and database-side evidence.

#### Production angle

Mitigations may include projections, entity graphs, query rewrite, indexes, pagination changes or caching.

#### Traps / caveats

- H2 tests can hide PostgreSQL-specific performance issues.
- One slow endpoint may issue hundreds of fast-looking queries.
- Adding eager fetching everywhere can make things worse.

#### Optional Anki

Q: Common JPA cause of slow list endpoints?
A: N+1 queries.

</details>

<a id="sp-data-016"></a>

<details>
<summary><strong>🧠 SP-DATA-016. How would you review a repository layer for N+1 queries and transaction leaks?</strong></summary>

#### Short answer

Review fetch plans, returned entity graphs, DTO mapping, lazy access points, service transaction boundaries and query count tests.

#### Interview answer

I would inspect repository methods that return entities to web/API layers, derived queries over associations, pagination with joins, and DTO mapping that touches lazy fields. I would check that services define clear read/write transaction boundaries and that controllers do not rely on OSIV.

Tests should assert query counts for important paths and use a real database where behavior matters.

#### Deep dive

Transaction leaks include doing remote calls inside transactions, holding streams open and allowing lazy access after the service boundary.

#### Production angle

This review prevents endpoints from degrading as data grows.

#### Traps / caveats

- Small test datasets hide N+1.
- OSIV hides lazy access problems.
- Fetching all associations can create cartesian explosions.

#### Optional Anki

Q: What should a repository review check besides query correctness?
A: Fetch plan, transaction boundary and query count behavior.

</details>
