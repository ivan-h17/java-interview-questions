# 16.07. Spring Boot fundamentals and startup

---

<a id="sp-boot-001"></a>

<details>
<summary><strong>SP-BOOT-001. What is the difference between Spring Framework and Spring Boot?</strong></summary>

#### Short answer

Spring Framework provides the core programming model and infrastructure; Spring Boot adds conventions, auto-configuration and production-ready defaults for building applications faster.

#### Interview answer

Spring Framework includes IoC, DI, AOP, transactions, MVC, data integration and many core abstractions. Spring Boot sits on top and makes application setup easier with starters, auto-configuration, embedded servers, externalized configuration and Actuator.

Spring Boot does not replace Spring. It packages common Spring choices into a productive application model.

#### Deep dive

Boot's key idea is conditional configuration: based on classpath, properties and user beans, it configures useful defaults while allowing overrides.

#### Production angle

Boot standardizes packaging, configuration, observability, health checks and deployment behavior across services.

#### Traps / caveats

- Boot defaults are not always production policy.
- You still need to understand what auto-configuration created.
- Spring Framework knowledge is needed to debug Boot applications.

#### Optional Anki

Q: Does Spring Boot replace Spring Framework?
A: No, it builds on it with conventions and auto-configuration.

</details>

<a id="sp-boot-002"></a>

<details>
<summary><strong>SP-BOOT-002. What does @SpringBootApplication do?</strong></summary>

#### Short answer

`@SpringBootApplication` combines configuration, auto-configuration and component scanning.

#### Interview answer

`@SpringBootApplication` is a convenience annotation that includes `@SpringBootConfiguration`, `@EnableAutoConfiguration` and `@ComponentScan`. It marks the main application configuration class, enables Boot auto-configuration and scans components from its package downward.

It is usually placed on the main application class.

#### Deep dive

The package location of this class is important because it defines the default component scan root.

#### Production angle

Misplacing the main class can cause missing beans, repositories or controllers after refactoring.

#### Traps / caveats

- It does not automatically scan sibling packages outside the root.
- Excluding auto-configuration should be deliberate.
- Putting too much configuration in the main class can make startup hard to reason about.

#### Optional Anki

Q: What three concerns does `@SpringBootApplication` combine?
A: Configuration, auto-configuration and component scanning.

</details>

<a id="sp-boot-003"></a>

<details>
<summary><strong>SP-BOOT-003. What happens at a high level when SpringApplication.run() is called?</strong></summary>

#### Short answer

Boot prepares the environment, creates the application context, loads beans, starts the embedded server if needed and publishes startup events.

#### Interview answer

`SpringApplication.run()` bootstraps the application. It creates and configures the environment, determines the application type, creates an `ApplicationContext`, loads sources, applies initializers and listeners, refreshes the context, starts web infrastructure if applicable and runs startup callbacks.

If startup fails, Boot reports the failure and may use a `FailureAnalyzer`.

#### Deep dive

The context refresh is where bean definitions are processed, beans are instantiated and lifecycle callbacks run.

#### Production angle

Startup time and failure diagnostics usually point to work done during context refresh: bean creation, auto-configuration, database initialization or external checks.

#### Traps / caveats

- Heavy startup logic in beans slows deployments.
- Lazy initialization can shift errors from startup to runtime.
- Runners execute after the context is ready, but before the application is fully useful for all traffic patterns.

#### Optional Anki

Q: What major step creates most Spring beans during startup?
A: Application context refresh.

</details>

<a id="sp-boot-004"></a>

<details>
<summary><strong>SP-BOOT-004. What is an embedded web server in Spring Boot?</strong></summary>

#### Short answer

An embedded web server is a server such as Tomcat, Jetty, Undertow or Netty packaged and started inside the application process.

#### Interview answer

Spring Boot web apps usually run as standalone applications. Instead of deploying a WAR to an external servlet container, Boot starts an embedded server and registers the web application with it.

This simplifies deployment: the artifact contains the application and server runtime.

#### Deep dive

Servlet stack apps commonly use embedded Tomcat by default. Reactive WebFlux apps often use Reactor Netty.

#### Production angle

Embedded servers make container deployments simple, but server configuration such as threads, timeouts, compression and graceful shutdown still matters.

#### Traps / caveats

- Embedded does not mean untunable.
- Server thread pools differ between servlet and reactive stacks.
- Running behind a proxy requires correct forwarded header handling.

#### Optional Anki

Q: Default embedded servlet server commonly used by Spring Boot web apps?
A: Tomcat.

</details>

<details>
<summary><strong>SP-BOOT-005. What is a layered jar, and why is it useful for Docker images?</strong></summary>

#### Short answer

A layered jar separates application content into layers so container builds can cache stable layers such as dependencies.

#### Interview answer

Spring Boot can package executable jars with layer metadata. Typical layers separate dependencies, snapshot dependencies, the Boot loader and application classes/resources. Docker or buildpacks can then reuse dependency layers when only application code changes.

This reduces image build and pull times.

#### Deep dive

Layering is a packaging optimization, not a runtime architecture change. The application still runs as one process.

#### Production angle

Layered jars improve CI/CD efficiency and deployment speed, especially for many services with large dependency sets.

#### Traps / caveats

- Layering does not reduce application memory usage.
- Bad Dockerfile ordering can defeat caching.
- Native images and layered JVM jars have different trade-offs.

#### Optional Anki

Q: Main benefit of a layered Spring Boot jar in Docker?
A: Better image layer caching.

</details>

<a id="sp-boot-006"></a>

<details>
<summary><strong>SP-BOOT-006. What is Spring Boot dependency management, and what is a BOM?</strong></summary>

#### Short answer

Boot dependency management provides tested dependency versions; a BOM is a bill of materials that centralizes those versions.

#### Interview answer

Spring Boot publishes dependency management so compatible versions of Spring, Jackson, Tomcat, Hibernate, Micrometer and other libraries are used together. In Maven or Gradle, a BOM lets you omit many explicit versions and inherit a tested set.

This reduces version conflict risk.

#### Deep dive

You can override managed versions, but then you own compatibility testing for that dependency.

#### Production angle

Dependency alignment reduces runtime linkage errors and subtle incompatibilities during upgrades.

#### Traps / caveats

- A BOM does not add dependencies; it manages versions.
- Mixing unrelated BOMs can create surprising version choices.
- Overriding managed versions should be documented.

#### Optional Anki

Q: What does a BOM manage?
A: Dependency versions.

</details>

<a id="sp-boot-007"></a>

<details>
<summary><strong>SP-BOOT-007. What is the difference between CommandLineRunner and ApplicationRunner?</strong></summary>

#### Short answer

Both run after the application context starts; `CommandLineRunner` receives raw strings, while `ApplicationRunner` receives parsed application arguments.

#### Interview answer

`CommandLineRunner` has `run(String... args)`. `ApplicationRunner` has `run(ApplicationArguments args)`, which exposes parsed option and non-option arguments. Both are useful for startup tasks such as validating configuration, seeding local data or kicking off controlled jobs.

They should not hide long-running or fragile startup workflows.

#### Deep dive

Multiple runners can be ordered with `@Order` or `Ordered`.

#### Production angle

Startup runners can block deployment readiness or perform duplicate work if every replica runs them.

#### Traps / caveats

- Do not run one-time migrations in every replica unless safe.
- Avoid remote calls that make startup brittle.
- A failing runner can prevent the app from starting.

#### Optional Anki

Q: Which runner exposes parsed command-line options?
A: `ApplicationRunner`.

</details>

<a id="sp-boot-008"></a>

<details>
<summary><strong>🧠 SP-BOOT-008. What application events are published during Spring Boot startup?</strong></summary>

#### Short answer

Boot publishes lifecycle events such as starting, environment prepared, context initialized/prepared, started, ready and failed.

#### Interview answer

Spring Boot publishes startup events such as `ApplicationStartingEvent`, `ApplicationEnvironmentPreparedEvent`, `ApplicationContextInitializedEvent`, `ApplicationPreparedEvent`, `ApplicationStartedEvent`, `ApplicationReadyEvent` and `ApplicationFailedEvent`. Availability events for liveness/readiness are also part of the startup timeline in modern Boot.

Most application code should not depend heavily on low-level startup events unless it is infrastructure.

#### Deep dive

Events occur at different times. Early events can fire before the application context exists or before bean definitions are loaded, so not every listener can be registered as a bean and not every bean can be used.

#### Production angle

Startup events are useful for diagnostics, logging, metrics and framework integration.

#### Traps / caveats

- Event timing matters; using beans too early can fail.
- Prefer higher-level lifecycle hooks unless low-level events are required.
- Avoid side effects that make startup order fragile.

#### Optional Anki

Q: What does `ApplicationReadyEvent` roughly indicate?
A: The application has started and is ready for application-level work.

</details>

<a id="sp-boot-009"></a>

<details>
<summary><strong>🧠 SP-BOOT-009. What is a FailureAnalyzer?</strong></summary>

#### Short answer

A `FailureAnalyzer` turns certain startup exceptions into clearer diagnostic messages and suggested actions.

#### Interview answer

Spring Boot uses failure analyzers to improve startup error reporting. Instead of only a long stack trace, Boot may show a description of what went wrong and how to fix it, such as port conflicts, missing configuration or bean problems.

Custom starters can provide their own analyzers for domain-specific configuration failures.

#### Deep dive

Failure analyzers are infrastructure extension points. They should explain known failure modes, not hide exceptions.

#### Production angle

Good failure analysis reduces incident time when a service fails to start after deployment.

#### Traps / caveats

- Not every exception has an analyzer.
- The analyzer output does not replace reading the root cause.
- Custom analyzers must be maintained with the starter.

#### Optional Anki

Q: Purpose of a Spring Boot `FailureAnalyzer`?
A: Produce clearer startup failure diagnostics and actions.

</details>

<details>
<summary><strong>SP-BOOT-010. How would you debug a Spring Boot application that fails to start?</strong></summary>

#### Short answer

Read the root cause, identify the failing startup phase, check configuration, auto-configuration conditions, dependency versions and environment differences.

#### Interview answer

I start with the full exception chain and Boot failure analysis. Then I check whether the failure is bean creation, port binding, configuration binding, database migration, missing secret, dependency conflict or a runner failure.

For auto-configuration problems, I use the condition evaluation report, debug logs and Actuator endpoints in a comparable environment.

#### Deep dive

Reproduce with the same profile, environment variables and command-line arguments. Many startup failures are not code-only issues.

#### Production angle

Compare the failing deployment with the last successful one: image version, config maps, secrets, classpath, DB state and resource limits.

#### Traps / caveats

- Do not stop at the first wrapper exception.
- Local success does not prove production config is valid.
- Lazy initialization can hide startup failures until traffic arrives.

#### Optional Anki

Q: Boot feature for seeing why auto-configurations matched?
A: The condition evaluation report.

</details>
