# 16.03. Bean lifecycle and extension points

---

<a id="sp-life-001"></a>

<details>
<summary><strong>SP-LIFE-001. What are the main stages of the Spring bean lifecycle?</strong></summary>

#### Short answer

Spring creates the bean, injects dependencies, applies post-processors, runs initialization callbacks, exposes the bean for use and later runs destruction callbacks.

#### Interview answer

At a high level, Spring reads bean definitions, instantiates objects, populates dependencies, applies awareness callbacks, runs `BeanPostProcessor`s, invokes initialization callbacks such as `@PostConstruct`, and then the bean is ready.

On shutdown, singleton beans can receive destruction callbacks such as `@PreDestroy` or configured destroy methods.

#### Deep dive

Many framework features hook into this lifecycle. Autowiring, validation annotations, `@PostConstruct`, proxies and AOP are not magic; they are applied through container lifecycle extension points.

#### Production angle

Lifecycle timing matters for startup failures, slow startup, readiness checks and resource cleanup during shutdown.

#### Traps / caveats

- A bean may be wrapped in a proxy before other beans see it.
- Prototype beans are not fully managed through destruction by default.
- Heavy work during initialization can make deployments slow or fragile.

#### Optional Anki

Q: What happens after Spring instantiates a bean?
A: It injects dependencies and applies lifecycle/post-processor callbacks.

</details>

<a id="sp-life-002"></a>

<details>
<summary><strong>SP-LIFE-002. What is the difference between bean instantiation, dependency injection and initialization?</strong></summary>

#### Short answer

Instantiation creates the object, dependency injection populates collaborators, and initialization runs setup callbacks after dependencies are available.

#### Interview answer

Instantiation is the constructor or factory method call. Dependency injection is when Spring provides constructor arguments, sets properties or injects fields. Initialization happens after dependencies are in place, for example `@PostConstruct`, `InitializingBean.afterPropertiesSet()` or an init method.

These stages are separate, and code should not assume dependencies are available before injection has happened.

#### Deep dive

Constructor-injected dependencies are available during construction. Setter and field-injected dependencies are not. That is one reason constructor injection is safer for required dependencies.

#### Production angle

Confusing these stages can cause startup failures, null fields, premature external calls or work done before configuration is ready.

#### Traps / caveats

- Do not start background threads from constructors.
- Avoid calling overridable methods from constructors.
- `@PostConstruct` is not a good place for long blocking integration checks.

#### Optional Anki

Q: When should initialization logic run?
A: After required dependencies have been injected.

</details>

<a id="sp-life-003"></a>

<details>
<summary><strong>SP-LIFE-003. What do @PostConstruct, @PreDestroy, initMethod and destroyMethod do?</strong></summary>

#### Short answer

They define callbacks that run after bean initialization and before bean destruction.

#### Interview answer

`@PostConstruct` runs after Spring has injected dependencies. `@PreDestroy` runs during container shutdown for managed singleton beans. `initMethod` and `destroyMethod` are equivalent lifecycle methods configured on a `@Bean` definition, often for third-party classes you cannot annotate.

Use them for local setup and cleanup, not for heavy business workflows.

#### Deep dive

The annotation callbacks are handled by bean post-processors. Destroy callbacks depend on the bean scope and whether the context closes cleanly.

#### Production angle

Correct cleanup matters for thread pools, schedulers, clients and buffers. Bad initialization can block deployments or make readiness misleading.

#### Traps / caveats

- `@PreDestroy` may not run after abrupt process termination.
- Prototype beans do not get automatic destruction callbacks in the same way as singletons.
- External calls in `@PostConstruct` can make startup depend on fragile downstream systems.

#### Optional Anki

Q: When does `@PostConstruct` run?
A: After dependencies are injected and before the bean is used.

</details>

<a id="sp-life-004"></a>

<details>
<summary><strong>SP-LIFE-004. What are common mistakes in initialization logic inside Spring beans?</strong></summary>

#### Short answer

Common mistakes are doing heavy I/O, starting uncontrolled threads, relying on proxies too early, hiding failures or mixing business workflows into startup.

#### Interview answer

Initialization should prepare the bean, not execute a production workflow. I avoid long database queries, remote calls, message consumption, scheduled work or cache warmup unless it is controlled, observable and compatible with readiness.

Another trap is calling methods that are expected to be transactional, cached or secured from within initialization code before proxies are involved.

#### Deep dive

If startup work is necessary, make it explicit through runners, lifecycle beans or a startup coordinator, and decide whether failure should prevent the app from becoming ready.

#### Production angle

Bad initialization causes slow rollouts, cascading failures during dependency outages and apps that start but are not actually able to serve traffic.

#### Traps / caveats

- Do not swallow startup exceptions silently.
- Do not perform unbounded cache warmup.
- Do not assume every downstream dependency must be available before the process starts.

#### Optional Anki

Q: Why are remote calls in `@PostConstruct` risky?
A: They can make startup fail or hang because of downstream dependency issues.

</details>

<a id="sp-life-005"></a>

<details>
<summary><strong>🧠 SP-LIFE-005. What is BeanPostProcessor?</strong></summary>

#### Short answer

`BeanPostProcessor` is an extension point that can modify or wrap bean instances before and after initialization.

#### Interview answer

A `BeanPostProcessor` receives callbacks for each bean during creation. It can inspect the bean, inject metadata, run annotation logic or return a wrapped object such as an AOP proxy.

Many core Spring features are implemented through post-processors, including annotation processing and proxy creation.

#### Deep dive

Post-processors operate on bean instances, not just definitions. They are powerful because they participate in almost every bean's lifecycle.

#### Production angle

When debugging why a bean is proxied or why an annotation works, `BeanPostProcessor`s are often part of the answer.

#### Traps / caveats

- Custom post-processors can affect many beans and create hard-to-debug startup behavior.
- Ordering matters.
- Returning the wrong object can break type assumptions.

#### Optional Anki

Q: What can a `BeanPostProcessor` return?
A: The original bean or a modified/wrapped bean, often a proxy.

</details>

<a id="sp-life-006"></a>

<details>
<summary><strong>🧠 SP-LIFE-006. What is the difference between BeanPostProcessor, BeanFactoryPostProcessor and BeanDefinitionRegistryPostProcessor?</strong></summary>

#### Short answer

They run at different levels: bean instances, bean definitions and the bean definition registry.

#### Interview answer

`BeanPostProcessor` works with bean instances during creation. `BeanFactoryPostProcessor` works earlier and can modify bean definitions before beans are instantiated. `BeanDefinitionRegistryPostProcessor` is even earlier and can add or modify bean definitions in the registry.

Use instance post-processors for wrapping or initialization behavior, and factory/registry post-processors for changing what beans will exist.

#### Deep dive

Configuration class processing itself relies on registry/factory-level extension points. That is why these hooks are powerful and should be used carefully.

#### Production angle

Understanding the level helps debug startup: a bean may be missing because its definition was never registered, not because instantiation failed.

#### Traps / caveats

- Registry/factory post-processors run before normal beans are available.
- Using business services inside them is usually wrong.
- Ordering mistakes can make conditional registration unpredictable.

#### Optional Anki

Q: Which post-processor can add new bean definitions?
A: `BeanDefinitionRegistryPostProcessor`.

</details>

<a id="sp-life-007"></a>

<details>
<summary><strong>🧠 SP-LIFE-007. How do BeanPostProcessors relate to @Autowired, @PostConstruct and AOP proxies?</strong></summary>

#### Short answer

Spring uses post-processors to interpret annotations such as `@Autowired` and `@PostConstruct` and to wrap beans in AOP proxies.

#### Interview answer

Annotation support is implemented through infrastructure post-processors. For example, one processor handles dependency injection metadata for `@Autowired`, another handles lifecycle annotations such as `@PostConstruct`, and auto-proxy creators can wrap beans with proxies for transactions, security, caching or async behavior.

So these annotations are not handled directly by constructors; they are applied during container-managed creation.

#### Deep dive

Auto-proxy creators are specialized post-processors. They inspect advisors and decide whether a bean should be proxied.

#### Production angle

If a bean is created outside the Spring container, these annotations and proxies will not apply.

#### Traps / caveats

- Manually constructed objects do not get autowired or proxied automatically.
- Some lifecycle callbacks may run on the target before proxy wrapping is complete.
- Multiple post-processors can interact in order-dependent ways.

#### Optional Anki

Q: Why does `@Transactional` not work on objects created with `new`?
A: The object is not container-managed and not proxied.

</details>

<a id="sp-life-008"></a>

<details>
<summary><strong>🧠 SP-LIFE-008. What are SmartInitializingSingleton and SmartLifecycle used for?</strong></summary>

#### Short answer

`SmartInitializingSingleton` runs after singleton creation; `SmartLifecycle` controls coordinated start and stop phases.

#### Interview answer

`SmartInitializingSingleton` is useful when a bean needs to run logic after all regular singleton beans have been instantiated. `SmartLifecycle` is for components that need structured startup and shutdown, such as message listener containers, schedulers or integration endpoints.

`SmartLifecycle` also supports phases, auto-startup and asynchronous stop callbacks.

#### Deep dive

These are infrastructure-level hooks. They are more explicit than hiding work in constructors or random `@PostConstruct` methods.

#### Production angle

They help coordinate startup and shutdown of components that consume messages, open connections or process background work.

#### Traps / caveats

- Starting work too early can consume traffic before readiness.
- Wrong lifecycle phase ordering can break dependencies between background components.
- Long stop callbacks can delay shutdown beyond platform limits.

#### Optional Anki

Q: Which lifecycle interface supports ordered start and stop phases?
A: `SmartLifecycle`.

</details>

<a id="sp-life-009"></a>

<details>
<summary><strong>SP-LIFE-009. How does Spring handle bean destruction during application shutdown?</strong></summary>

#### Short answer

When the application context closes, Spring invokes destruction callbacks for managed singleton beans and stops lifecycle components.

#### Interview answer

On graceful shutdown, Spring closes the `ApplicationContext`. It stops lifecycle beans, calls destruction callbacks such as `@PreDestroy`, `DisposableBean.destroy()` and configured destroy methods, and releases managed infrastructure.

Spring Boot integrates this with JVM shutdown hooks and web server graceful shutdown support.

#### Deep dive

Destruction ordering considers dependencies so dependent beans are destroyed before the beans they depend on.

#### Production angle

Shutdown behavior matters for in-flight HTTP requests, message consumers, scheduled jobs, database pools and duplicate processing risks.

#### Traps / caveats

- Abrupt process kill may skip callbacks.
- Cleanup must be bounded; containers and orchestrators enforce termination deadlines.
- Do not rely on shutdown callbacks as the only place to commit critical business data.

#### Optional Anki

Q: What must happen for Spring destruction callbacks to run?
A: The application context must close cleanly.

</details>

<a id="sp-life-010"></a>

<details>
<summary><strong>🧠 SP-LIFE-010. How do proxies affect bean lifecycle callbacks?</strong></summary>

#### Short answer

Lifecycle callbacks usually run on the target bean during creation, while other beans may receive a proxy as the injected object.

#### Interview answer

Spring may create a target object, run dependency injection and initialization callbacks, and then expose a proxy around that target. Calls through the proxy can trigger transactions, security, caching or async behavior.

The important trap is that calls from within the target object, including initialization methods, do not go through the proxy.

#### Deep dive

AOP proxies are often created by post-processors after initialization callbacks. The exact timing depends on the proxying mechanism and processor, but the practical rule is to avoid relying on advice inside lifecycle callbacks.

#### Production angle

This explains why a `@Transactional` method called from `@PostConstruct` or another method in the same class may not behave as expected.

#### Traps / caveats

- Self-invocation bypasses proxy advice.
- `this.someMethod()` never goes through the Spring proxy.
- Bean type checks can see proxy classes rather than target classes.

#### Optional Anki

Q: Do calls inside `@PostConstruct` normally go through the Spring AOP proxy?
A: No, internal calls usually bypass proxy advice.

</details>

<a id="sp-life-011"></a>

<details>
<summary><strong>SP-LIFE-011. How would you debug a bean that fails during application startup?</strong></summary>

#### Short answer

Read the root cause in the startup exception, identify the bean being created, then check dependencies, conditions, configuration, profiles and lifecycle code.

#### Interview answer

I start from the bottom of the exception stack because the top often says only that context startup failed. I identify the failing bean, whether it failed during construction, dependency injection, initialization or post-processing.

Then I check missing or duplicate dependencies, bad properties, active profiles, conditional beans, `@PostConstruct` logic and auto-configuration reports.

#### Deep dive

Failures can be chained through several beans. The first meaningful cause may be a missing property, bad database URL, invalid constructor argument or exception thrown by custom initialization.

#### Production angle

Startup failures after deployment often come from environment differences: missing secrets, wrong profile, dependency version changes or absent infrastructure.

#### Traps / caveats

- Do not stop at `UnsatisfiedDependencyException`; inspect the nested cause.
- Test slices can hide failures that only appear in the full context.
- Lazy initialization may defer startup errors until first traffic.

#### Optional Anki

Q: Where is the useful cause in many Spring startup failures?
A: In the deepest relevant nested exception.

</details>
