# 12.03. Creating, completing and chaining stages

---

<a id="cf-create-001"></a>

<details>
<summary><strong>CF-CREATE-001. How do you create already completed or already failed `CompletableFuture` values?</strong></summary>

#### Short answer

Use `completedFuture(value)` for success and `failedFuture(error)` for failure.

#### Interview answer

`CompletableFuture.completedFuture(value)` creates a future that is already completed normally. `CompletableFuture.failedFuture(exception)` creates one already completed exceptionally.

For `CompletionStage`-only APIs, newer JDKs also provide stage-oriented variants such as `completedStage` and `failedStage`.

#### Deep dive

Already completed futures are useful for tests, cache hits, validation failures and branches where no async work is needed.

#### Production angle

Returning an already completed future can keep API shape consistent without scheduling unnecessary executor work.

#### Traps / caveats

- Do not call `supplyAsync()` just to return a known value.
- An already failed future still needs normal async error handling by callers.
- Version-specific factory methods should match the project's target JDK.

#### Optional Anki

Q: Which factory creates an already successful `CompletableFuture`?
A: `CompletableFuture.completedFuture(value)`.

</details>

<a id="cf-create-005"></a>

<details>
<summary><strong>CF-CREATE-005. What do `supplyAsync()` and `runAsync()` do, and when should you use each?</strong></summary>

#### Short answer

`supplyAsync()` runs work that returns a value. `runAsync()` runs work that returns no value.

#### Interview answer

`supplyAsync(Supplier<T>)` submits a supplier and returns `CompletableFuture<T>`. `runAsync(Runnable)` submits a runnable and returns `CompletableFuture<Void>`.

Use `supplyAsync` when downstream stages need the result. Use `runAsync` for side-effect work where completion or failure matters but no value is produced.

#### Deep dive

Both methods have overloads that accept an explicit `Executor`. In backend code, that overload is usually preferred for blocking or service-specific work.

#### Production angle

Avoid using the default executor for blocking I/O. Choose an executor that matches the workload and has clear metrics.

#### Traps / caveats

- `CompletableFuture<Void>` still represents failure.
- Fire-and-forget `runAsync()` can lose errors if ignored.
- `supplyAsync()` does not make blocking work non-blocking internally.

#### Optional Anki

Q: Which method should you use when the task produces a result?
A: `supplyAsync()`.

</details>

<a id="cf-create-008"></a>

<details>
<summary><strong>CF-CREATE-008. How does manual completion work, including exceptional completion?</strong></summary>

#### Short answer

Create an incomplete future and call `complete(value)` or `completeExceptionally(error)`.

#### Interview answer

Manual completion is useful when adapting callbacks or external events:

```java
CompletableFuture<Result> future = new CompletableFuture<>();
client.call(
    value -> future.complete(value),
    error -> future.completeExceptionally(error)
);
```

Once completed, dependent stages run according to their rules.

#### Deep dive

`complete` returns `true` if this call won completion and `false` if the future was already completed. The same applies to exceptional completion.

#### Production angle

Manual futures must complete on every path: success, failure, timeout and cancellation. Missing one path creates hangs.

#### Traps / caveats

- Do not complete the same future from unrelated owners.
- Be careful with callback APIs that can call both success and failure.
- Preserve the original exception instead of replacing it with a vague wrapper.

#### Optional Anki

Q: How do you complete a future with an error?
A: `completeExceptionally(Throwable)`.

</details>

<a id="cf-create-011"></a>

<details>
<summary><strong>🧠 CF-CREATE-011. What happens if multiple threads try to complete the same `CompletableFuture`?</strong></summary>

#### Short answer

Only one completion wins. Later normal or exceptional completion attempts are ignored by the ordinary completion methods.

#### Interview answer

`CompletableFuture` completion is thread-safe. If two threads race to call `complete`, `completeExceptionally` or `cancel`, one transition wins. The winning call returns `true`; losing calls return `false` or observe that the future is already completed.

Dependent stages see the winning result.

#### Deep dive

This behavior is useful when adapting racing callbacks, but it should not be used as a substitute for clear ownership. If multiple components legitimately race to complete the same future, the winning policy should be intentional.

#### Production angle

Log or metric suspicious losing completions if they indicate duplicate callbacks, retries or lifecycle bugs.

#### Traps / caveats

- `obtrudeValue` and `obtrudeException` are special dangerous overrides.
- Losing completion attempts can hide bugs if ignored.
- Side effects performed before completion are not undone.

#### Optional Anki

Q: What does `complete(value)` return when another thread already completed the future?
A: `false`.

</details>

<a id="cf-create-013"></a>

<details>
<summary><strong>🧠 CF-CREATE-013. What are `obtrudeValue()` and `obtrudeException()`, and why are they dangerous?</strong></summary>

#### Short answer

They forcibly overwrite what later callers observe from a `CompletableFuture`, even after completion.

#### Interview answer

`obtrudeValue` and `obtrudeException` are recovery/debugging-style methods that force a future's result or exception. They do not behave like normal completion and can create inconsistent observations: some dependent stages may already have run using the old result.

That makes them inappropriate for normal application control flow.

#### Deep dive

They exist for exceptional administrative scenarios, not routine retry, fallback or error handling.

#### Production angle

Using obtrusion in business code makes async behavior almost impossible to reason about. Prefer explicit new stages and recovery paths.

#### Traps / caveats

- Already triggered dependents are not magically replayed.
- Observers can see different logical histories.
- It can mask the real cause of a failed pipeline.

#### Optional Anki

Q: Should `obtrudeValue()` be used for normal fallback?
A: No, use explicit recovery stages instead.

</details>

<a id="cf-create-018"></a>

<details>
<summary><strong>CF-CREATE-018. How can you create a `CompletableFuture` around callback-based code?</strong></summary>

#### Short answer

Create an incomplete future and complete it from the callback's success or failure path.

#### Interview answer

The adapter pattern is:

```java
CompletableFuture<T> result = new CompletableFuture<>();
api.call(input, new Callback<>() {
    public void onSuccess(T value) { result.complete(value); }
    public void onFailure(Throwable error) { result.completeExceptionally(error); }
});
return result;
```

Add timeout and cancellation behavior if the callback API supports it.

#### Deep dive

The hard part is not the happy path. It is preventing double completion, handling synchronous callback invocation and making sure no failure path leaves the future incomplete.

#### Production angle

Callback adapters are integration boundaries. Add tests for success, failure, timeout, cancellation and duplicate callbacks.

#### Traps / caveats

- Some APIs call callbacks on event-loop threads; do not block there.
- A callback can be invoked before the adapter method returns.
- Cancellation of the future may not cancel the underlying operation.

#### Optional Anki

Q: What must every callback adapter guarantee?
A: The future completes on every success and failure path.

</details>

<a id="cf-create-020"></a>

<details>
<summary><strong>CF-CREATE-020. What are common mistakes when creating `CompletableFuture` instances manually?</strong></summary>

#### Short answer

Common mistakes are never completing, completing twice, losing errors and forgetting cancellation or timeout behavior.

#### Interview answer

Manual futures are easy to misuse. Developers often complete only the success path, forget `completeExceptionally`, ignore cancellation, race multiple callbacks, or leak captured request objects while the future remains incomplete.

Another mistake is exposing the mutable future directly when only a `CompletionStage` should be returned.

#### Deep dive

Manual completion should usually be isolated in adapter code. Business logic should mostly compose stages rather than create incomplete futures everywhere.

#### Production angle

Never-completed futures can cause request hangs and memory retention. Track timeouts and outstanding async operations.

#### Traps / caveats

- A timeout on the returned future may not cancel the external operation.
- Losing the original exception hurts incident diagnosis.
- Fire-and-forget manual futures often lose failures.

#### Optional Anki

Q: What is the most dangerous manual future bug?
A: A future that never completes.

</details>

<a id="cf-chain-003"></a>

<details>
<summary><strong>CF-CHAIN-003. What is the difference between `thenApply()`, `thenCompose()` and `thenCombine()`?</strong></summary>

#### Short answer

`thenApply` maps a value, `thenCompose` flat-maps to another future, and `thenCombine` joins two independent futures.

#### Interview answer

Use `thenApply(fn)` when you have `T -> U`. Use `thenCompose(fn)` when you have `T -> CompletionStage<U>` and want to avoid `CompletableFuture<CompletableFuture<U>>`. Use `thenCombine(other, fn)` when two independent stages both need to complete before producing a combined result.

#### Deep dive

These map to common functional shapes: map, flatMap and zip/combine.

#### Production angle

Choosing the right method keeps pipelines readable and avoids accidental serialization or nesting.

#### Traps / caveats

- Do not use `thenApply` for functions that already return futures.
- `thenCompose` models dependency, not parallel independent work.
- `thenCombine` waits for both stages and must handle either failure.

#### Optional Anki

Q: Which method prevents nested futures?
A: `thenCompose()`.

</details>

<a id="cf-chain-009"></a>

<details>
<summary><strong>CF-CHAIN-009. What is the difference between `thenApply()`, `thenAccept()` and `thenRun()`?</strong></summary>

#### Short answer

`thenApply` transforms a value, `thenAccept` consumes a value, and `thenRun` runs without using the value.

#### Interview answer

`thenApply` takes the previous result and returns a new result. `thenAccept` takes the previous result but returns `Void`. `thenRun` ignores the previous result and runs a no-argument action after completion.

Use the method that communicates intent: transformation, side effect with input, or follow-up action without input.

#### Deep dive

Returning `CompletableFuture<Void>` is acceptable for completion signals, but important side effects still need logging, metrics and failure handling.

#### Production angle

Use side-effect stages deliberately. Auditing, writes and notifications should not be hidden in casual `thenAccept` calls.

#### Traps / caveats

- `thenAccept` and `thenRun` discard values.
- Exceptions in side-effect stages still complete the returned stage exceptionally.
- Ignoring the returned `CompletableFuture<Void>` can lose failures.

#### Optional Anki

Q: Which continuation returns a transformed result?
A: `thenApply()`.

</details>

<a id="cf-chain-014"></a>

<details>
<summary><strong>CF-CHAIN-014. What is the difference between async and non-async continuations?</strong></summary>

#### Short answer

Non-async continuations may run in the thread that completes the previous stage. Async continuations are scheduled through an executor.

#### Interview answer

Methods like `thenApply` do not necessarily switch threads. If the upstream stage completes, the continuation can run in the completing thread, or immediately if already complete.

Methods like `thenApplyAsync` schedule the continuation on an executor. Without an explicit executor, they usually use the default async executor.

#### Deep dive

Non-async stages are cheaper but can surprise you if they run heavy work on an I/O callback, event loop or request thread.

#### Production angle

Use explicit async boundaries for heavy or blocking work. Keep lightweight mapping stages non-async when appropriate.

#### Traps / caveats

- `Async` does not mean a new thread per stage.
- Non-async continuations can run on sensitive threads.
- Default executors should not be used casually for blocking work.

#### Optional Anki

Q: What does the `Async` suffix usually imply?
A: The continuation is scheduled via an executor.

</details>

<a id="cf-chain-016"></a>

<details>
<summary><strong>CF-CHAIN-016. What thread executes a `CompletableFuture` continuation?</strong></summary>

#### Short answer

It depends on whether the continuation is async, whether the upstream is already complete and what executor is provided.

#### Interview answer

For non-async methods, a continuation may run in the thread that completes the upstream stage, or in the caller thread if the upstream is already complete when the continuation is attached.

For async methods, the continuation is submitted to the provided executor, or to the default executor if none is provided.

#### Deep dive

This is why `CompletableFuture` code should not assume stable thread identity. `ThreadLocal` context can disappear or be wrong unless propagated deliberately.

#### Production angle

Document executor behavior for async APIs and avoid blocking or heavy work in unknown completion threads.

#### Traps / caveats

- Non-async callbacks can execute immediately.
- Async callbacks can still be delayed by executor saturation.
- Thread names and tracing are essential for debugging.

#### Optional Anki

Q: Which thread can run a non-async continuation?
A: Often the thread that completes the upstream stage.

</details>

<a id="cf-chain-018"></a>

<details>
<summary><strong>🧠 CF-CHAIN-018. How do dependent stages behave when the upstream stage is already complete?</strong></summary>

#### Short answer

The dependent stage can be triggered immediately when it is attached.

#### Interview answer

If you attach a non-async continuation to an already completed future, the continuation may run immediately in the attaching thread. If you attach an async continuation, it is submitted to the relevant executor.

This can affect latency, stack traces, locks, context propagation and which thread performs side effects.

#### Deep dive

`CompletableFuture` is not purely "later". Completion may already have happened, so attaching a stage can become immediate computation.

#### Production angle

Avoid attaching heavy non-async continuations while holding locks or inside framework callbacks where synchronous execution would be harmful.

#### Traps / caveats

- Tests with already completed futures may execute more synchronously than production.
- Context may be captured differently depending on when stages are attached.
- Immediate failure propagation can surprise error handling code.

#### Optional Anki

Q: What can happen when `thenApply()` is attached to an already completed future?
A: The function may run immediately in the calling thread.

</details>

<a id="cf-chain-021"></a>

<details>
<summary><strong>🧠 CF-CHAIN-021. Are `CompletableFuture` continuations guaranteed to execute in registration order?</strong></summary>

#### Short answer

Do not rely on registration order for independent continuations.

#### Interview answer

If multiple dependent stages are attached to the same future, they are separate dependents. The API does not give a business-level guarantee that independent callbacks run in the order you registered them, especially when async executors are involved.

If ordering matters, encode it in the dependency chain: stage B should depend on stage A.

#### Deep dive

Composition order and execution order are different. A chain expresses dependency; multiple siblings express independent work.

#### Production angle

Side effects that require ordering should use explicit sequencing, a queue, a transaction or a workflow model.

#### Traps / caveats

- Sibling callbacks may run concurrently.
- Async executor scheduling changes observed order.
- Tests may accidentally pass because one executor happens to run in order.

#### Optional Anki

Q: How do you guarantee one continuation runs after another?
A: Chain it as a dependent stage, not as an independent sibling.

</details>

<a id="cf-chain-022"></a>

<details>
<summary><strong>CF-CHAIN-022. How do you keep `CompletableFuture` pipelines readable?</strong></summary>

#### Short answer

Use named methods, clear stage boundaries and explicit error handling instead of deeply nested lambdas.

#### Interview answer

Readable pipelines separate concerns: fetch, transform, combine, recover and observe. Prefer small named methods for non-trivial lambdas. Use `thenCompose` to flatten dependent async calls, `thenCombine` for independent joins and one clear recovery strategy.

Avoid mixing business decisions, retries, logging, transaction writes and DTO mapping in one expression.

#### Deep dive

If a pipeline becomes a control-flow language, extract orchestration into a service with explicit helper methods and tests.

#### Production angle

Readable async code is easier to debug during incidents. It also makes executor boundaries and error paths visible.

#### Traps / caveats

- Nested `thenApply` returning futures creates hard-to-read nested types.
- Too many inline lambdas hide stack trace meaning.
- Silent `exceptionally` fallbacks can obscure failures.

#### Optional Anki

Q: Which method helps avoid nested future pipelines?
A: `thenCompose()`.

</details>
