# 12.04. Combining, racing and coordinating multiple futures

---

<a id="cf-comb-001"></a>

<details>
<summary><strong>CF-COMB-001. How do you combine the results of multiple `CompletableFuture` instances?</strong></summary>

#### Short answer

Use `thenCombine` for two independent results and `allOf` plus result extraction for many futures.

#### Interview answer

If two futures are independent and both results are needed, use `thenCombine`. If you have a list of futures, use `CompletableFuture.allOf(...)` to wait for all, then collect each result.

For dependent work, use `thenCompose` instead of launching everything at once.

#### Deep dive

Combination should match semantics: dependency, independent join, race, partial success or fail-fast behavior.

#### Production angle

Combining futures is also a capacity decision. Fan-out should be bounded and downstream services protected.

#### Traps / caveats

- `allOf` does not return typed results.
- Failure behavior must be designed explicitly.
- Large fan-out can cause memory, thread and connection pressure.

#### Optional Anki

Q: Which method combines two independent future results?
A: `thenCombine()`.

</details>

<a id="cf-comb-006"></a>

<details>
<summary><strong>CF-COMB-006. What does `allOf()` do, and when should you use it?</strong></summary>

#### Short answer

`allOf()` returns a future that completes when all supplied futures complete.

#### Interview answer

`CompletableFuture.allOf(f1, f2, f3)` creates a coordination future. It completes normally when all inputs complete normally. If one or more complete exceptionally, the returned future completes exceptionally.

Use it for fan-in when you have already started several independent operations and need to wait for all of them.

#### Deep dive

`allOf` is not a scheduler and not a throttler. It only observes futures you pass to it.

#### Production angle

For large collections, combine `allOf` with concurrency limits, timeouts and careful result extraction.

#### Traps / caveats

- It does not start work by itself.
- It does not cancel sibling futures when one fails.
- It loses typed result information.

#### Optional Anki

Q: Does `allOf()` start async work?
A: No, it coordinates futures that already exist.

</details>

<a id="cf-comb-007"></a>

<details>
<summary><strong>CF-COMB-007. Why does `allOf()` return `CompletableFuture<Void>`, and how do you collect results?</strong></summary>

#### Short answer

It returns `Void` because it accepts heterogeneous futures. Collect results by reading the original futures after `allOf` completes.

#### Interview answer

`allOf` accepts `CompletableFuture<?>...`, so there is no single result type it can return safely. After the coordination future completes, collect from the original typed futures:

```java
CompletableFuture<List<T>> combined =
    CompletableFuture.allOf(futures.toArray(CompletableFuture[]::new))
        .thenApply(v -> futures.stream().map(CompletableFuture::join).toList());
```

#### Deep dive

Calling `join()` after successful `allOf` should not block for successful futures, but it can still rethrow if a future failed and you did not handle failure first.

#### Production angle

Keep the original list in input order if output order matters.

#### Traps / caveats

- Do not lose references to the original futures.
- Handle exceptions before blindly joining all results.
- Very large lists can create large retained graphs.

#### Optional Anki

Q: Why is the result of `allOf()` not `List<T>`?
A: The inputs can have different result types.

</details>

<a id="cf-comb-009"></a>

<details>
<summary><strong>CF-COMB-009. What happens if one future in `allOf()` fails?</strong></summary>

#### Short answer

The `allOf` result completes exceptionally, but other futures are not automatically stopped.

#### Interview answer

If any input future completes exceptionally, the `allOf` coordination future completes exceptionally after completion rules are satisfied. The failed cause is available through the returned future's exception.

Other futures continue unless they are independently cancelled or fail themselves.

#### Deep dive

`allOf` is not fail-fast cancellation. It is a completion coordinator. If you need fail-fast behavior, build it explicitly.

#### Production angle

For remote fan-out, decide whether one failed dependency should fail the whole request, return partial data or cancel remaining optional calls.

#### Traps / caveats

- Do not assume sibling futures are cancelled.
- Multiple failures may be hard to observe unless collected explicitly.
- Joining individual futures after failure can throw repeatedly.

#### Optional Anki

Q: Does `allOf()` automatically cancel other futures after one fails?
A: No.

</details>

<a id="cf-comb-011"></a>

<details>
<summary><strong>CF-COMB-011. How do you implement fail-fast behavior with multiple futures?</strong></summary>

#### Short answer

Complete a separate result future on the first failure and cancel or ignore remaining work according to your policy.

#### Interview answer

`allOf` is not enough for fail-fast behavior. A common approach is to create a result future and attach `whenComplete` handlers to each child. On first failure, complete the result exceptionally and optionally cancel siblings.

You still need to decide whether cancellation is best effort and how to handle late completions.

#### Deep dive

Fail-fast is a policy, not just an API call. It must define what happens to already running tasks, remote calls and side effects.

#### Production angle

Fail-fast helps reduce wasted work for critical dependencies, but careless cancellation can break optional partial-result behavior.

#### Traps / caveats

- `cancel(true)` may not interrupt running `CompletableFuture` tasks.
- Late completions can still run side effects.
- Failure should include enough context to identify which dependency failed.

#### Optional Anki

Q: Why is `allOf()` alone not fail-fast?
A: It coordinates completion and does not cancel siblings on first failure.

</details>

<a id="cf-comb-012"></a>

<details>
<summary><strong>CF-COMB-012. How do you collect partial successes when some futures fail?</strong></summary>

#### Short answer

Convert each future into a result wrapper that records success or failure, then wait for all wrappers.

#### Interview answer

Instead of letting one failure fail the whole `allOf`, handle each child:

```java
CompletableFuture<Result<T>> wrapped =
    call.handle((value, error) -> error == null ? Result.success(value) : Result.failure(error));
```

Then use `allOf` over wrapped futures and collect successes, failures and metadata.

#### Deep dive

This makes partial failure explicit. The service can decide which dependencies are required, optional or degraded.

#### Production angle

Partial responses should be observable: emit metrics for degraded dependencies and include safe response metadata when appropriate.

#### Traps / caveats

- Do not silently hide required dependency failures.
- Avoid logging the same exception once per wrapper and again at the top.
- Preserve input identity so failures are attributable.

#### Optional Anki

Q: Which method is useful for converting failure into a result wrapper?
A: `handle()`.

</details>

<a id="cf-comb-013"></a>

<details>
<summary><strong>CF-COMB-013. What does `anyOf()` do, and when is it useful?</strong></summary>

#### Short answer

`anyOf()` completes when the first supplied future completes, successfully or exceptionally.

#### Interview answer

`CompletableFuture.anyOf(f1, f2, f3)` is useful for races: first response wins, timeout sentinels, redundant sources or waiting for whichever operation finishes first.

The returned future has type `CompletableFuture<Object>` because inputs may have different result types.

#### Deep dive

`anyOf` does not mean "first successful result". If the first completion is a failure, the result is failed.

#### Production angle

For hedging or fallback races, explicitly define what to do with losing operations and failures.

#### Traps / caveats

- It is not type-safe for heterogeneous inputs.
- It does not cancel losers automatically.
- First failure may win even if another future would succeed later.

#### Optional Anki

Q: Does `anyOf()` wait for the first success only?
A: No, it completes on first completion, success or failure.

</details>

<a id="cf-comb-014"></a>

<details>
<summary><strong>🧠 CF-COMB-014. What are the type-safety limitations of `anyOf()`?</strong></summary>

#### Short answer

`anyOf()` returns `CompletableFuture<Object>`, so callers must recover type information themselves.

#### Interview answer

Because `anyOf` accepts futures with arbitrary result types, the JDK cannot return a precise generic type. Even if all inputs are `CompletableFuture<String>`, the method signature returns `CompletableFuture<Object>`.

For homogeneous races, you can wrap or cast carefully. For heterogeneous races, model the result with a sealed type, tagged wrapper or domain result object.

#### Deep dive

Type safety matters because async failures already make control flow harder. Avoid adding unchecked casts in the middle of complex pipelines.

#### Production angle

In public code, prefer typed wrappers over scattered casts so future maintenance does not introduce `ClassCastException`.

#### Traps / caveats

- A cast may pass tests if only one branch wins.
- Heterogeneous results should be modeled explicitly.
- `applyToEither` can be more type-friendly for two same-type stages.

#### Optional Anki

Q: What type does `CompletableFuture.anyOf()` return?
A: `CompletableFuture<Object>`.

</details>

<a id="cf-comb-015"></a>

<details>
<summary><strong>🧠 CF-COMB-015. How do you implement first-success-wins behavior?</strong></summary>

#### Short answer

Track completions and complete the result on the first success, while ignoring or collecting failures until success is impossible.

#### Interview answer

`anyOf` is not enough because first failure may win. First-success-wins needs custom logic: attach handlers to each future, complete the result when one succeeds, count failures, and only fail the result if all candidates fail.

After success, cancel or ignore losers depending on whether cancellation is supported and safe.

#### Deep dive

This pattern is common for redundant reads, mirrors or fallback providers. It is risky for operations with side effects.

#### Production angle

Add metrics for winning source, losing latency, cancellation success and all-failed cases.

#### Traps / caveats

- Do not use it blindly for writes.
- Late failures should not overwrite success.
- Cancellation of losers may be best effort only.

#### Optional Anki

Q: Why is `anyOf()` not enough for first-success-wins?
A: Because the first completed future may be a failure.

</details>

<a id="cf-comb-020"></a>

<details>
<summary><strong>CF-COMB-020. How would you limit concurrency when launching many futures?</strong></summary>

#### Short answer

Use a bounded executor, semaphore, batch processing, rate limiter or async library that supports concurrency limits.

#### Interview answer

Do not launch thousands of `supplyAsync` calls at once. Limit concurrency with a fixed-size executor for blocking work, a `Semaphore` around remote calls, batches, or a library operator that supports max concurrency.

The limit should reflect downstream capacity, connection pools, latency targets and retry behavior.

#### Deep dive

Concurrency limit is different from timeout. A timeout bounds waiting time; a concurrency limit bounds simultaneous pressure.

#### Production angle

Expose metrics for queued tasks, active calls, rejected work, latency and downstream error rate.

#### Traps / caveats

- A large executor is not a real downstream limit.
- Unbounded queues hide overload.
- Retries must also respect the same limit.

#### Optional Anki

Q: What is one simple way to limit blocking async work?
A: Use a dedicated bounded executor.

</details>

<a id="cf-comb-021"></a>

<details>
<summary><strong>CF-COMB-021. Why is mapping a large list to `supplyAsync()` dangerous without throttling?</strong></summary>

#### Short answer

It can submit too many tasks at once and overwhelm executors, memory, connection pools and downstream services.

#### Interview answer

`ids.stream().map(id -> supplyAsync(...))` over a large list creates all futures immediately. Even if the executor has limited threads, the backlog can become huge. If each task calls a database or remote service, you can overload shared resources.

Bounded concurrency is needed to keep work within system capacity.

#### Deep dive

The danger is not only active threads. Pending futures retain inputs, lambdas, request context and dependent stages.

#### Production angle

Prefer batching, bulk APIs, paging, bounded executors or backpressure-capable pipelines for large workloads.

#### Traps / caveats

- Executor queues can grow faster than workers drain them.
- Timeouts may expire before work even starts.
- Large fan-out can increase tail latency.

#### Optional Anki

Q: What is the main risk of unbounded `supplyAsync()` in a loop?
A: Unbounded task submission and resource pressure.

</details>

<a id="cf-comb-023"></a>

<details>
<summary><strong>CF-COMB-023. How do you preserve input order when collecting results from multiple futures?</strong></summary>

#### Short answer

Keep futures in the same order as inputs and collect from that list after completion.

#### Interview answer

If each input maps to one future, store them in a `List<CompletableFuture<T>>` in input order. After `allOf`, stream that same list and join each future. Completion order does not matter because collection order follows the list.

If results are wrapped, include the original index or input key.

#### Deep dive

Order preservation is separate from execution order. Futures can complete out of order while the final output remains ordered.

#### Production angle

For API responses, stable ordering prevents confusing clients and makes tests deterministic.

#### Traps / caveats

- Collecting into a concurrent collection may lose input order.
- Retrying individual calls should preserve the original index.
- Partial failures need placeholders or explicit omission rules.

#### Optional Anki

Q: How can futures complete out of order but results stay ordered?
A: Collect results from the original input-ordered future list.

</details>

<a id="cf-comb-025"></a>

<details>
<summary><strong>CF-COMB-025. How do you implement fan-out/fan-in with `CompletableFuture`?</strong></summary>

#### Short answer

Start bounded independent calls, attach per-call handling, wait with `allOf`, then aggregate results.

#### Interview answer

A safe fan-out/fan-in design usually includes:

- map inputs to async calls using a bounded executor or async client limit;
- apply per-call timeout and error handling;
- collect required and optional results separately;
- use `allOf` or typed wrappers for fan-in;
- enforce an overall deadline.

#### Deep dive

Fan-out is not just syntax. It is a distributed-systems design decision about concurrency, failure, partial results and downstream protection.

#### Production angle

Instrument each dependency separately and monitor fan-out size, latency, timeout count and partial-degradation count.

#### Traps / caveats

- Do not call `join()` inside each child pipeline.
- Do not ignore optional failures silently.
- Do not fan out beyond downstream capacity.

#### Optional Anki

Q: What must safe fan-out include besides `allOf()`?
A: Bounded concurrency, timeouts, failure policy and observability.

</details>
