# 12.01. Fundamentals and async mental model

---

<a id="cf-fund-001"></a>

<details>
<summary><strong>CF-FUND-001. What is asynchronous programming?</strong></summary>

#### Short answer

Asynchronous programming lets code start work and continue without waiting synchronously for the result.

#### Interview answer

In synchronous code, the caller waits until an operation finishes. In asynchronous code, the operation is represented by a future, callback, event or reactive signal, and the caller can attach continuation logic that runs later when the result is available.

In Java, `CompletableFuture` is one way to model this: it represents a value that may become available later and lets you compose follow-up stages.

#### Deep dive

Async programming separates "requesting work" from "waiting for work". It is useful when many operations spend time waiting for external resources such as HTTP services, databases, queues or timers.

#### Production angle

Async code must still control concurrency, timeouts, cancellation, error handling and observability. Otherwise it can create hidden overload instead of improving throughput.

#### Traps / caveats

- Async does not mean faster by default.
- Async code can still block if the underlying operation blocks.
- Unbounded async work can overwhelm thread pools and downstream systems.

#### Optional Anki

Q: What does asynchronous programming separate?
A: Starting work from waiting for or consuming its result.

</details>

<a id="cf-fund-002"></a>

<details>
<summary><strong>CF-FUND-002. What problem does asynchronous programming solve in backend systems?</strong></summary>

#### Short answer

It helps backend services coordinate waiting-heavy work without tying up the calling flow unnecessarily.

#### Interview answer

Backend services often call databases, remote services, queues and caches. Those operations spend much of their time waiting. Async programming lets a service start several independent operations, compose their results and avoid serial waiting where parallel waiting is safe.

For example, an endpoint can call inventory, pricing and recommendations in parallel, then combine the results.

#### Deep dive

Async is mostly about latency hiding and coordination. It does not remove capacity limits. The database connection pool, HTTP client pool, downstream rate limits and executor queues still define what the system can handle.

#### Production angle

Good async backend code uses bounded fan-out, deadlines, fallbacks, metrics and clear ownership of executors.

#### Traps / caveats

- Parallel remote calls can amplify downstream load.
- Async code can make failures harder to trace.
- Without timeouts, async pipelines can hang forever.

#### Optional Anki

Q: What is a common backend use case for async code?
A: Running independent remote calls concurrently and composing their results.

</details>

<a id="cf-fund-003"></a>

<details>
<summary><strong>CF-FUND-003. What is the difference between concurrency and parallelism?</strong></summary>

#### Short answer

Concurrency is dealing with multiple tasks at once. Parallelism is executing multiple tasks at the same time.

#### Interview answer

Concurrency is a design property: the program can manage overlapping tasks, interleaving progress between them. Parallelism is a runtime property: tasks literally run simultaneously on multiple CPU cores or workers.

`CompletableFuture` supports concurrent coordination. Whether stages run in parallel depends on the executor, available threads, CPU cores and whether the work is independent.

#### Deep dive

A single-threaded event loop can be concurrent without being parallel. A multi-threaded executor can provide both concurrency and parallelism.

#### Production angle

Confusing the two leads to bad designs. For blocking I/O, concurrency often helps. For CPU-heavy work, parallelism is limited by cores and can hurt if oversubscribed.

#### Traps / caveats

- More concurrent tasks do not mean more throughput.
- More threads do not guarantee useful parallelism.
- Shared state makes concurrent code harder even without parallel execution.

#### Optional Anki

Q: Can code be concurrent but not parallel?
A: Yes, for example an event loop interleaving many I/O operations on one thread.

</details>

<a id="cf-fund-004"></a>

<details>
<summary><strong>CF-FUND-004. What is the difference between asynchronous execution and parallel execution?</strong></summary>

#### Short answer

Asynchronous execution means the caller does not wait immediately. Parallel execution means work runs at the same time.

#### Interview answer

Async code returns a handle such as `CompletableFuture` before the result is ready. Parallel code performs multiple pieces of work simultaneously, usually on different threads or cores.

Calling `supplyAsync()` may create parallel execution if there is executor capacity. Creating `new CompletableFuture<>()` does not start anything. A completed future is asynchronous as an abstraction but may contain no asynchronous execution at all.

#### Deep dive

Async describes the API contract. Parallel describes runtime scheduling. A future can complete from an external callback, a timer, another thread or an already-known value.

#### Production angle

When reviewing async code, ask where work actually runs, what executor it uses and what resource it waits on.

#### Traps / caveats

- `CompletableFuture` is not itself a thread.
- Async APIs can still complete on the caller thread.
- Parallelism without throttling can increase load and latency.

#### Optional Anki

Q: Does creating a future imply parallel execution?
A: No, a future represents completion; it does not necessarily start work.

</details>

<a id="cf-fund-005"></a>

<details>
<summary><strong>CF-FUND-005. What is a callback, and what problems does callback-style programming have?</strong></summary>

#### Short answer

A callback is code passed to run later when an operation completes. Raw callbacks can become hard to compose, test and reason about.

#### Interview answer

Callback-style APIs accept success and failure handlers. They are simple for one operation, but nested callbacks can lead to "callback hell": deeply nested control flow, duplicated error handling and unclear ownership of cancellation or timeouts.

`CompletableFuture` improves this by representing completion as a value and offering composition methods such as `thenApply`, `thenCompose`, `handle` and `allOf`.

#### Deep dive

Callbacks also make it easy to forget failure paths, call the callback twice or never call it. A future centralizes the completion state.

#### Production angle

When adapting callback APIs, guard against double completion, missing error completion and cancellation that does not reach the underlying operation.

#### Traps / caveats

- Callback order may not be obvious.
- Exceptions thrown inside callbacks may be lost if not captured.
- Some callback APIs invoke handlers synchronously.

#### Optional Anki

Q: What problem does `CompletableFuture` solve compared with nested callbacks?
A: It makes completion composable as a value with explicit success and failure stages.

</details>

<a id="cf-fund-007"></a>

<details>
<summary><strong>CF-FUND-007. What is `CompletableFuture` in Java?</strong></summary>

#### Short answer

`CompletableFuture` is a Java class that represents a result that may complete later and can be composed with dependent stages.

#### Interview answer

`CompletableFuture<T>` can complete normally with a `T`, complete exceptionally with an error, or be cancelled. It implements both `Future<T>` and `CompletionStage<T>`.

Compared with old `Future`, it supports non-blocking composition: transformation, flat-mapping, combining multiple futures, racing, recovery and manual completion.

#### Deep dive

It is both a readable completion handle and a writable completion handle. That is powerful, but it is why APIs often return `CompletionStage` instead when callers should not complete the value themselves.

#### Production angle

`CompletableFuture` is useful for async orchestration, but production code must still manage executors, timeouts, cancellation, retries, context propagation and metrics.

#### Traps / caveats

- It does not automatically make blocking work non-blocking.
- Default async methods may use the common pool.
- Exposing it directly can allow external manual completion.

#### Optional Anki

Q: Which two main interfaces does `CompletableFuture` implement?
A: `Future<T>` and `CompletionStage<T>`.

</details>

<a id="cf-fund-008"></a>

<details>
<summary><strong>CF-FUND-008. How is `CompletableFuture` related to `CompletionStage`?</strong></summary>

#### Short answer

`CompletionStage` is the composition interface; `CompletableFuture` is the main JDK implementation.

#### Interview answer

`CompletionStage<T>` describes a stage in an async pipeline and exposes methods like `thenApply`, `thenCompose`, `thenCombine`, `handle` and `whenComplete`.

`CompletableFuture<T>` implements that interface and also adds `Future` methods plus manual completion methods such as `complete` and `completeExceptionally`.

#### Deep dive

Returning `CompletionStage` from an API narrows what callers can do. They can compose the result, but they do not receive the full mutable `CompletableFuture` API unless they downcast or convert.

#### Production angle

For public APIs, prefer the narrowest useful type. Return `CompletionStage` when callers should observe and compose, not complete or obtrude results.

#### Traps / caveats

- `CompletionStage` has no `join()` method.
- `toCompletableFuture()` may expose or create a `CompletableFuture` depending on implementation.
- A `CompletionStage` still needs clear threading and cancellation documentation.

#### Optional Anki

Q: Why return `CompletionStage` instead of `CompletableFuture`?
A: To expose composition without exposing manual completion.

</details>

<a id="cf-fund-010"></a>

<details>
<summary><strong>CF-FUND-010. What is the difference between a task and a future?</strong></summary>

#### Short answer

A task is work to execute. A future is a handle to a result that may be available later.

#### Interview answer

A task is usually represented by `Runnable`, `Callable` or a lambda passed to an executor. A future represents the completion of that work: success, failure or cancellation.

The distinction matters because a `CompletableFuture` can represent work started elsewhere, a value already known, a callback result, or manually completed state. It is not necessarily the task itself.

#### Deep dive

In `CompletableFuture.supplyAsync(supplier, executor)`, the supplier is the task and the returned `CompletableFuture` is the result handle.

#### Production angle

When debugging async systems, always ask both questions: what future are we waiting on, and what actual task or external operation is supposed to complete it?

#### Traps / caveats

- A future can exist without an active task.
- A task can run without anyone observing its future.
- Losing the future can mean losing error visibility.

#### Optional Anki

Q: Is a `CompletableFuture` always the task that runs?
A: No, it is usually the handle representing completion.

</details>

<a id="cf-fund-011"></a>

<details>
<summary><strong>CF-FUND-011. What is the difference between starting work and representing its result?</strong></summary>

#### Short answer

Starting work schedules or triggers execution. Representing its result gives callers a completion handle.

#### Interview answer

`supplyAsync()` starts work by submitting a supplier to an executor and returns a future for its result. `new CompletableFuture<>()` only creates an incomplete result container. A callback-based HTTP client may start network I/O itself and let you complete a future from its callback.

This distinction prevents a common mistake: assuming any method returning a future has necessarily started work in a new thread.

#### Deep dive

A future is a synchronization and composition object. Work can be started by an executor, an event loop, a scheduler, a remote callback, another future, or not started yet.

#### Production angle

Document whether an async API is hot or lazy, what triggers execution and who owns cancellation.

#### Traps / caveats

- A future can be returned before work is submitted.
- Work may already be running before the future is returned.
- Completion may happen synchronously on the caller thread.

#### Optional Anki

Q: What does `new CompletableFuture<>()` do?
A: It creates an incomplete future; it does not start work.

</details>

<a id="cf-fund-012"></a>

<details>
<summary><strong>CF-FUND-012. Does creating a `CompletableFuture` always start asynchronous work?</strong></summary>

#### Short answer

No. Creating a `CompletableFuture` does not by itself start work.

#### Interview answer

`new CompletableFuture<>()` creates an incomplete future. `completedFuture(value)` creates an already completed future. Neither starts asynchronous work.

Work is started by something else: `supplyAsync`, `runAsync`, an executor submission, a callback-based library, a scheduler or external completion. The future is the representation of completion, not necessarily the trigger.

#### Deep dive

This makes `CompletableFuture` useful as an adapter. You can create one future and complete it from a network callback, message listener or timer.

#### Production angle

If a future never completes, the bug may be in the code responsible for starting work or in the callback path responsible for completing it.

#### Traps / caveats

- An incomplete future can hang callers forever.
- A future created manually must complete on every success and failure path.
- An already completed future may run non-async continuations immediately.

#### Optional Anki

Q: Which common methods start executor work?
A: `supplyAsync()` and `runAsync()`.

</details>

<a id="cf-fund-016"></a>

<details>
<summary><strong>CF-FUND-016. What does it mean that `CompletableFuture` pipelines are non-blocking?</strong></summary>

#### Short answer

It means stages can be registered without blocking the caller while waiting for the previous stage to finish.

#### Interview answer

In a `CompletableFuture` pipeline, methods like `thenApply` and `thenCompose` attach continuations. The caller does not need to call `get()` after every step. When the upstream stage completes, the continuation is triggered.

That is non-blocking at the composition level. It does not guarantee that the work inside a stage is non-blocking.

#### Deep dive

For example, `future.thenApply(this::map)` does not block waiting for `future`. But if `map` performs a blocking database call, that continuation still blocks the thread running it.

#### Production angle

Review both the pipeline shape and the body of each lambda. Blocking calls inside async stages still consume threads.

#### Traps / caveats

- `thenApply` registration is non-blocking; the lambda may not be.
- `join()` and `get()` reintroduce blocking.
- Non-async continuations may run on a completion thread you did not expect.

#### Optional Anki

Q: What does non-blocking mean for `thenApply()` registration?
A: It attaches a continuation without waiting for the upstream result.

</details>

<a id="cf-fund-017"></a>

<details>
<summary><strong>CF-FUND-017. Can `CompletableFuture` make blocking code non-blocking by itself?</strong></summary>

#### Short answer

No. It can move blocking work to another thread, but the operation still blocks that thread.

#### Interview answer

Wrapping `blockingCall()` in `supplyAsync()` prevents the caller thread from blocking, but a worker thread still blocks. That may be acceptable for bounded I/O work, but it is not the same as using a genuinely asynchronous HTTP or database driver.

If you submit too many blocking calls, you can exhaust the executor, connection pools or downstream service.

#### Deep dive

`CompletableFuture` is a composition abstraction. Non-blocking I/O requires libraries and drivers that use non-blocking APIs underneath.

#### Production angle

When wrapping blocking calls, use a dedicated bounded executor, apply timeouts and monitor queue size and active threads.

#### Traps / caveats

- `supplyAsync()` without a custom executor may use the common pool.
- Thread-per-blocking-call can still be expensive under high fan-out.
- Timeouts on the future may not stop the underlying blocking call.

#### Optional Anki

Q: Does `supplyAsync(blockingCall)` make the call non-blocking internally?
A: No, it usually just blocks a different thread.

</details>

<a id="cf-fund-018"></a>

<details>
<summary><strong>CF-FUND-018. When is `CompletableFuture` a good fit?</strong></summary>

#### Short answer

It is a good fit for composing a bounded number of asynchronous or independently executable operations.

#### Interview answer

`CompletableFuture` works well for async orchestration: parallel remote calls, dependent calls, timeout and fallback logic, callback adapters and combining independent results.

It is especially useful when you need one result eventually, or a small graph of results, rather than an unbounded stream of data.

#### Deep dive

Typical patterns include `thenCompose` for dependent async calls, `thenCombine` for independent results, `allOf` for fan-in and `handle` or `exceptionallyCompose` for recovery.

#### Production angle

Use it with explicit executors, bounded concurrency, clear failure semantics and observability.

#### Traps / caveats

- It is not a backpressure framework.
- It is not ideal for long streaming pipelines.
- It does not replace durable messaging for business workflows that must survive process crashes.

#### Optional Anki

Q: What workload shape fits `CompletableFuture` best?
A: A bounded async result graph.

</details>

<a id="cf-fund-019"></a>

<details>
<summary><strong>CF-FUND-019. When is `CompletableFuture` a poor fit?</strong></summary>

#### Short answer

It is a poor fit for unbounded streams, durable workflows, uncontrolled fan-out or simple synchronous code.

#### Interview answer

If data arrives continuously and needs backpressure, reactive streams or messaging may be better. If work must survive restarts, use a queue, workflow engine or transactional outbox rather than in-memory futures. If the operation is simple and synchronous, `CompletableFuture` may add complexity without benefit.

It is also risky when teams use it to hide blocking code without executor and capacity design.

#### Deep dive

`CompletableFuture` graphs are unstructured by default. Child tasks can outlive request scope unless cancellation and ownership are designed explicitly.

#### Production angle

Prefer the simplest model that satisfies latency, reliability and capacity requirements. Async complexity has a real maintenance cost.

#### Traps / caveats

- Fire-and-forget futures can lose failures.
- Futures disappear on process crash.
- Async code can obscure transaction and security boundaries.

#### Optional Anki

Q: What does `CompletableFuture` not provide for streaming systems?
A: Backpressure.

</details>
