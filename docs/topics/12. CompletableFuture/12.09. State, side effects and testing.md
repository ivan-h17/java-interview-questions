# 12.09. State, side effects and testing

---

<a id="cf-state-001"></a>

<details>
<summary><strong>CF-STATE-001. Can you modify external mutable state inside `CompletableFuture` callbacks?</strong></summary>

#### Short answer

You can, but it is risky unless the state is properly synchronized and the side effect is intentional.

#### Interview answer

Callbacks may run on different threads and at different times. Modifying shared lists, maps, counters or domain objects from callbacks can create races, visibility bugs and ordering problems.

Prefer returning values through the pipeline and aggregating them with `thenCombine`, `allOf` or immutable result wrappers.

#### Deep dive

External mutation also makes retry and cancellation semantics harder: the side effect may happen before the final future completes.

#### Production angle

Keep async lambdas stateless when possible. If mutation is needed, use thread-safe structures and define ownership clearly.

#### Traps / caveats

- `ArrayList` is not safe for concurrent callback writes.
- Atomic counters do not make a whole object graph safe.
- Side effects can run even if callers later time out.

#### Optional Anki

Q: What is the safer alternative to mutating external state?
A: Return values and aggregate them explicitly.

</details>

<a id="cf-state-003"></a>

<details>
<summary><strong>CF-STATE-003. How do race conditions appear in `CompletableFuture` code?</strong></summary>

#### Short answer

They appear when multiple stages access shared mutable state without a clear ordering or synchronization.

#### Interview answer

Several futures may complete in any order. If their callbacks update the same object, collection, counter or status field, the final result can depend on timing. Race conditions also happen when success and timeout paths both try to perform side effects.

Use immutable values, explicit sequencing or synchronization.

#### Deep dive

`CompletableFuture` makes completion coordination easier, but it does not make your captured variables thread-safe.

#### Production angle

Race bugs are often rare and load-dependent. Treat shared mutable state in async code as a code review warning.

#### Traps / caveats

- Tests with direct executors may hide races.
- A timeout path can race with a late success path.
- Two sibling callbacks can run concurrently.

#### Optional Anki

Q: Does `CompletableFuture` make captured objects thread-safe?
A: No.

</details>

<a id="cf-state-005"></a>

<details>
<summary><strong>CF-STATE-005. Why is using a non-thread-safe collection from multiple async callbacks dangerous?</strong></summary>

#### Short answer

Concurrent writes can corrupt the collection, lose elements or throw runtime exceptions.

#### Interview answer

If multiple callbacks call `list.add(...)` on the same `ArrayList`, there is no thread-safety guarantee. The internal array and size field can be updated concurrently. Results may be missing, duplicated or corrupted.

Instead, collect each future's result separately and aggregate after `allOf`, or use a proper concurrent collection when mutation is truly needed.

#### Deep dive

Even thread-safe collections may not make compound operations or ordering semantics correct.

#### Production angle

Prefer input-ordered future lists and immutable final aggregation for API responses.

#### Traps / caveats

- `Collections.synchronizedList` still needs care for iteration.
- `ConcurrentHashMap` does not make values thread-safe.
- Completion order may differ from input order.

#### Optional Anki

Q: What is wrong with adding to one `ArrayList` from many callbacks?
A: `ArrayList` is not thread-safe.

</details>

<a id="cf-state-006"></a>

<details>
<summary><strong>CF-STATE-006. How do you aggregate results without shared mutable state?</strong></summary>

#### Short answer

Keep one future per result, wait for completion, then build a new aggregate value.

#### Interview answer

Map inputs to `CompletableFuture<T>` values and store them in a list. After `allOf`, collect from that list into a new `List`, DTO or domain result. For partial failure, map each child to a `Result<T>` wrapper first.

This avoids concurrent mutation during callbacks.

#### Deep dive

Functional-style aggregation makes data flow explicit: each stage returns data rather than pushing into external state.

#### Production angle

Immutable aggregates are easier to log, test and reason about in incident debugging.

#### Traps / caveats

- Do not call `join()` before `allOf` if it serializes or blocks unexpectedly.
- Keep input identity for error reporting.
- Large aggregations still need memory limits.

#### Optional Anki

Q: What pattern avoids shared mutable result lists?
A: One future per result, then aggregate after completion.

</details>

<a id="cf-state-007"></a>

<details>
<summary><strong>CF-STATE-007. How do you handle ordering when futures complete out of order?</strong></summary>

#### Short answer

Preserve input order separately from completion order.

#### Interview answer

Futures complete whenever their work finishes. If output order matters, keep futures in an input-ordered list or attach an index/key to each result. After all are done, sort or collect by the original order.

Do not rely on callback execution order.

#### Deep dive

This is especially important for API responses, CSV exports and batch workflows where clients expect stable order.

#### Production angle

Stable ordering makes tests deterministic and reduces client-side surprises.

#### Traps / caveats

- Concurrent collections may not preserve order.
- Completion order can vary under load.
- Retried items must keep their original index.

#### Optional Anki

Q: What order should API aggregation usually preserve?
A: Input or documented response order, not completion order.

</details>

<a id="cf-state-008"></a>

<details>
<summary><strong>CF-STATE-008. How do you avoid double execution of side effects?</strong></summary>

#### Short answer

Make side effects idempotent and ensure only one code path owns executing them.

#### Interview answer

Async pipelines can have retries, timeouts, cancellation and late completions. A side effect such as publishing an event or charging a card should be guarded by idempotency keys, unique constraints or durable command state.

Also avoid attaching the same side-effect continuation in multiple places.

#### Deep dive

Completing a future once does not undo side effects performed by losing branches or retried attempts.

#### Production angle

For critical side effects, use transactional outbox, idempotent consumers and explicit command IDs.

#### Traps / caveats

- Retrying after timeout can duplicate work.
- `whenComplete` may run on both success and failure.
- Fire-and-forget side effects can run after request cancellation.

#### Optional Anki

Q: What protects async side effects from duplicate retries?
A: Idempotency.

</details>

<a id="cf-state-010"></a>

<details>
<summary><strong>CF-STATE-010. Can two dependent callbacks run concurrently?</strong></summary>

#### Short answer

Yes, independent dependent callbacks attached to the same stage may run concurrently.

#### Interview answer

If one future has two sibling continuations, those continuations are independent. With async methods and executor capacity, they can run concurrently. If one continuation must happen after another, encode that dependency by chaining them.

Do not rely on registration order for synchronization.

#### Deep dive

Sequential-looking code can still create a graph with sibling branches rather than a single chain.

#### Production angle

Side effects on shared state must be synchronized or sequenced deliberately.

#### Traps / caveats

- Non-async callbacks may appear sequential in simple tests.
- Async executor scheduling can change behavior.
- A chain expresses ordering; siblings express independence.

#### Optional Anki

Q: How do you force callback B to run after callback A?
A: Chain B from A's returned stage.

</details>

<a id="cf-state-012"></a>

<details>
<summary><strong>CF-STATE-012. How do you safely publish results produced by `CompletableFuture`?</strong></summary>

#### Short answer

Complete the future only after constructing the result fully, and prefer immutable result objects.

#### Interview answer

Completing a future publishes the result to dependent stages. The object should be fully initialized before completion. If the result is mutable and later changed by another thread, callers can still observe races.

Prefer immutable DTOs, records or defensive copies.

#### Deep dive

`CompletableFuture` gives completion coordination, not ongoing protection for mutable objects after publication.

#### Production angle

Immutable results are safer for caching, logging, retries and multi-stage pipelines.

#### Traps / caveats

- Do not complete a future with a partially built object.
- Do not mutate a published result later without synchronization.
- Defensive copying may be needed for collections.

#### Optional Anki

Q: What kind of object is safest to complete a future with?
A: A fully initialized immutable object.

</details>

<a id="cf-state-013"></a>

<details>
<summary><strong>🧠 CF-STATE-013. What Java Memory Model guarantees does `CompletableFuture` completion provide?</strong></summary>

#### Short answer

Completion provides safe handoff of the completed result to dependent stages, but it does not make mutable state safe forever.

#### Interview answer

A correctly completed `CompletableFuture` acts as a synchronization point for consumers that observe its completion. Writes that happen before completing the future are visible to actions that depend on that completion.

However, if you complete with a mutable object and keep mutating it afterward, those later mutations still need normal synchronization.

#### Deep dive

Think of completion as publishing the result. Publication is not the same as making the published object immutable.

#### Production angle

Use immutable values and avoid sharing mutable aggregates through async pipelines.

#### Traps / caveats

- Completion does not protect later mutations.
- Captured mutable variables outside the result can still race.
- Do not rely on logging or timing to "fix" visibility bugs.

#### Optional Anki

Q: Does future completion make later mutations of the result thread-safe?
A: No.

</details>

<a id="cf-state-016"></a>

<details>
<summary><strong>CF-STATE-016. How do you handle cleanup side effects in async flows?</strong></summary>

#### Short answer

Attach cleanup with `whenComplete` or equivalent finalization and make it safe for success, failure and cancellation.

#### Interview answer

Cleanup includes releasing semaphores, closing resources, stopping timers or clearing context. Use `whenComplete` so cleanup runs after either success or failure. Wrap cleanup carefully so cleanup exceptions do not hide the original failure unless that is intended.

For resources used inside a stage, prefer try-with-resources in the stage body.

#### Deep dive

Cleanup must also cover timeout and cancellation paths. If a timeout returns a fallback while underlying work continues, resource ownership becomes more complex.

#### Production angle

Leaked permits, MDC values or client resources can cause slow production degradation.

#### Traps / caveats

- Cleanup code itself can throw.
- Late completions may run cleanup after caller already timed out.
- Shared resources need clear ownership.

#### Optional Anki

Q: Which stage is commonly used for success/failure cleanup?
A: `whenComplete()`.

</details>

<a id="cf-test-001"></a>

<details>
<summary><strong>CF-TEST-001. How do you test code with `CompletableFuture`?</strong></summary>

#### Short answer

Make async dependencies controllable and assert success, failure, timeout and cancellation paths.

#### Interview answer

Use completed or manually controlled futures for dependencies. Inject executors so tests can use a direct executor or deterministic test executor. Assert the returned future's result or failure at the boundary.

Avoid relying on arbitrary sleeps or real timing where possible.

#### Deep dive

Good async tests verify behavior, not implementation thread scheduling. For retry and timeout code, use fake schedulers or configurable clocks when possible.

#### Production angle

Tests should cover degraded dependency behavior, partial failures and context propagation because those fail most often in production.

#### Traps / caveats

- Ignored returned futures can make tests pass before work finishes.
- Sleeps create flaky tests.
- Direct executors can hide real concurrency races.

#### Optional Anki

Q: What should async tests avoid?
A: Arbitrary `Thread.sleep()`.

</details>

<a id="cf-test-004"></a>

<details>
<summary><strong>CF-TEST-004. How do you test timeout behavior?</strong></summary>

#### Short answer

Use controlled incomplete futures, short deterministic timeouts, or fake schedulers where possible.

#### Interview answer

A timeout test can pass an incomplete future and verify that the wrapper completes exceptionally or returns fallback after the configured timeout. For retry or delayed timeout logic, prefer injecting a scheduler/clock so the test can advance time deterministically.

Also verify that underlying cancellation is requested if the design requires it.

#### Deep dive

Testing only that a future times out is not enough. Test what happens after timeout: fallback, logging, metrics and late completion handling.

#### Production angle

Timeout bugs often waste resources after the caller has already given up.

#### Traps / caveats

- Real sleeps slow and flake tests.
- Too-short timeouts can fail on busy CI.
- Future timeout does not prove resource timeout.

#### Optional Anki

Q: What should timeout tests verify besides the returned failure?
A: Cancellation or cleanup behavior when required.

</details>

<a id="cf-test-005"></a>

<details>
<summary><strong>CF-TEST-005. Why should tests avoid `Thread.sleep()`?</strong></summary>

#### Short answer

Sleeps make tests slow, flaky and timing-dependent.

#### Interview answer

`Thread.sleep()` guesses how long async work needs. If the sleep is too short, the test flakes. If too long, the suite becomes slow. On busy CI machines, timing can change.

Prefer controlled futures, direct executors, latches with timeouts, Awaitility-style polling or fake schedulers.

#### Deep dive

Tests should wait for a condition, not for an arbitrary amount of time.

#### Production angle

Flaky async tests cause teams to ignore failures, which weakens confidence in concurrency-sensitive code.

#### Traps / caveats

- Polling without timeout can hang forever.
- Direct executors are deterministic but not a full concurrency test.
- Do not hide production timing bugs by over-mocking.

#### Optional Anki

Q: What should async tests wait for?
A: A condition or future completion, not a guessed delay.

</details>

<a id="cf-test-006"></a>

<details>
<summary><strong>CF-TEST-006. How can a direct executor make async code deterministic in tests?</strong></summary>

#### Short answer

A direct executor runs submitted tasks immediately on the calling thread.

#### Interview answer

If code accepts an `Executor`, tests can pass `Runnable::run`. That makes `thenApplyAsync` or `supplyAsync` work execute synchronously in the test flow, so assertions are deterministic and no real threads are needed.

This is useful for testing composition logic.

#### Deep dive

Direct executors are not a replacement for concurrency tests. They can hide races and scheduling behavior.

#### Production angle

Injecting executors improves both testability and production configuration.

#### Traps / caveats

- A direct executor can cause deep synchronous call stacks.
- It changes thread identity behavior.
- It may hide missing context propagation issues.

#### Optional Anki

Q: What is a direct executor in Java terms?
A: An executor that calls `run()` immediately.

</details>

<a id="cf-test-009"></a>

<details>
<summary><strong>CF-TEST-009. How do you test partial failure behavior?</strong></summary>

#### Short answer

Return controlled successful and failed futures from dependencies and assert the aggregate result and metrics.

#### Interview answer

For an aggregator, mock required and optional dependencies separately. Make optional calls fail and verify that the response contains degraded data or error markers. Make required calls fail and verify that the whole operation fails.

Also check that failures are logged or counted once.

#### Deep dive

Partial failure tests should preserve input identity so you can assert which dependency or item failed.

#### Production angle

Partial failure is a normal distributed-systems case. It should be tested like the happy path.

#### Traps / caveats

- Returning `null` from failed optional calls can hide bugs.
- Do not assert only "future completed"; assert response semantics.
- Verify no unexpected retries or duplicate side effects occurred.

#### Optional Anki

Q: What distinction should partial failure tests cover?
A: Required dependency failure vs optional dependency failure.

</details>

<a id="cf-test-010"></a>

<details>
<summary><strong>CF-TEST-010. How do you test cancellation?</strong></summary>

#### Short answer

Cancel the returned future and assert cancellation state plus any propagated cleanup or underlying cancellation behavior.

#### Interview answer

A cancellation test should verify that `cancel` results in `CancellationException` or cancelled state, and that child futures, semaphores, HTTP calls or resources are handled according to policy.

If cancellation is best effort, test that the request is made, not that the underlying task magically stops.

#### Deep dive

Cancellation behavior must be explicit because `CompletableFuture.cancel(true)` does not reliably interrupt running work.

#### Production angle

Cancellation tests protect against wasted work after client disconnects or shutdown.

#### Traps / caveats

- Do not assume interruption happened.
- Late completions can still occur.
- Shared futures should not be cancelled if other callers need them.

#### Optional Anki

Q: What should a cancellation test not assume?
A: That `cancel(true)` interrupted the running task.

</details>

<a id="cf-test-014"></a>

<details>
<summary><strong>CF-TEST-014. How do you test context propagation?</strong></summary>

#### Short answer

Set context in the submitting thread, run async work, and assert the worker sees it and then clears it.

#### Interview answer

For MDC/request ID/security context, inject a decorated executor in the test. Set the context before submitting work, then assert that the async stage observes the expected value. Also submit another task afterward to verify stale context was cleared.

Test success and failure paths.

#### Deep dive

Context leaks are often caused by missing `finally` cleanup in task wrappers.

#### Production angle

Correct context propagation keeps logs, traces and authorization decisions reliable in async workflows.

#### Traps / caveats

- Direct executors may not reveal cross-thread propagation bugs.
- Cleanup must be tested after exceptions.
- Avoid asserting on sensitive values in logs.

#### Optional Anki

Q: What second assertion helps catch context leaks?
A: A later task should not see stale context.

</details>
