# 12.08. Resilience, context propagation and observability

---

<a id="cf-res-001"></a>

<details>
<summary><strong>CF-RES-001. How do you implement retry logic with `CompletableFuture`?</strong></summary>

#### Short answer

Retry by composing another async attempt after a retryable failure, with limits, delay and deadline awareness.

#### Interview answer

A retry wrapper should call the async operation, inspect failure, and if retryable and within budget, schedule another attempt. Use `exceptionallyCompose` or equivalent composition to avoid blocking.

Production retry needs max attempts, backoff, jitter, idempotency and metrics.

#### Deep dive

Do not implement retry with a loop that blocks on `join()`. Async retry should return a future representing the eventual result.

#### Production angle

Retries are extra traffic during failure. They must respect downstream capacity and request deadlines.

#### Traps / caveats

- Retrying non-idempotent operations can duplicate side effects.
- Immediate retries can create storms.
- Retrying after the caller timed out wastes work.

#### Optional Anki

Q: What must async retry respect besides max attempts?
A: Deadline, backoff, jitter and idempotency.

</details>

<a id="cf-res-003"></a>

<details>
<summary><strong>CF-RES-003. How do you implement retry with exponential backoff and jitter?</strong></summary>

#### Short answer

Schedule each retry after an increasing delay and randomize the delay to avoid synchronized retry spikes.

#### Interview answer

After a retryable failure, calculate the next delay, add jitter, then schedule the next async attempt using a scheduler or delayed executor. The returned future should complete with the first success or final failure.

Backoff reduces pressure on a struggling dependency. Jitter prevents many clients from retrying at the same time.

#### Deep dive

Backoff should be capped and deadline-aware. If the next delay would exceed the request deadline, fail or return fallback instead.

#### Production angle

Expose metrics for attempt count, delay, final outcome and exhausted retries.

#### Traps / caveats

- Sleeping in executor workers wastes threads.
- Fixed retry intervals can synchronize load.
- Backoff without max attempts can still loop too long.

#### Optional Anki

Q: Why add jitter to retry backoff?
A: To avoid synchronized retry bursts.

</details>

<a id="cf-res-005"></a>

<details>
<summary><strong>CF-RES-005. How do you decide which failures are retryable?</strong></summary>

#### Short answer

Retry transient failures, not deterministic validation or business failures.

#### Interview answer

Retry candidates include timeouts, connection resets, temporary 503 responses and rate-limited responses when allowed by policy. Do not retry invalid input, authorization failures, most 4xx responses, constraint violations or non-idempotent commands without protection.

Classify errors near integration boundaries.

#### Deep dive

Retryability depends on operation semantics. A read is often safer to retry than a payment capture unless idempotency keys are used.

#### Production angle

Wrong retry classification can either reduce resilience or create duplicate side effects and overload.

#### Traps / caveats

- Not all timeouts are safe to retry.
- A timeout may mean the server completed the operation but the client did not receive the response.
- Retry policy should be observable and configurable.

#### Optional Anki

Q: Should validation errors be retried?
A: No.

</details>

<a id="cf-res-006"></a>

<details>
<summary><strong>CF-RES-006. How do you stop retrying after a deadline?</strong></summary>

#### Short answer

Track an absolute deadline and check remaining time before every attempt and delay.

#### Interview answer

Each retry attempt should know the caller's deadline. Before scheduling another attempt, verify that enough time remains for the delay and the operation timeout. If not, complete with a timeout or fallback.

This prevents retry logic from continuing after the request is already lost.

#### Deep dive

Deadline-aware retry is better than independent per-attempt timeouts because it respects the end-to-end latency budget.

#### Production angle

Retry metrics should show deadline exhaustion separately from max-attempt exhaustion.

#### Traps / caveats

- A retry scheduled after the deadline only adds load.
- Per-attempt timeouts can exceed total request time.
- Fallbacks also need to fit within the deadline.

#### Optional Anki

Q: What should be checked before scheduling another retry?
A: Remaining deadline budget.

</details>

<a id="cf-res-007"></a>

<details>
<summary><strong>CF-RES-007. How do you avoid retry storms with `CompletableFuture`?</strong></summary>

#### Short answer

Use bounded retries, backoff, jitter, rate limits, circuit breakers and deadline-aware cancellation.

#### Interview answer

A retry storm happens when many callers retry during the same downstream failure. Async code can make this worse because many attempts are launched concurrently. Limit attempts, add jittered backoff, stop at deadlines, respect bulkheads and open a circuit breaker when failure is systemic.

#### Deep dive

Retries should reduce user-visible transient failures, not become a load multiplier.

#### Production angle

Monitor retry rate, attempts per request, downstream error rate, queue size and circuit breaker state.

#### Traps / caveats

- Immediate retries under outage amplify traffic.
- Retrying all exceptions is dangerous.
- Retried writes require idempotency.

#### Optional Anki

Q: What is the main danger of immediate retries?
A: They can amplify load during failure.

</details>

<a id="cf-res-008"></a>

<details>
<summary><strong>CF-RES-008. What is the difference between fallback and retry in async code?</strong></summary>

#### Short answer

Retry tries the same operation again. Fallback uses an alternative result or path.

#### Interview answer

Retry is useful for transient failures when another attempt may succeed. Fallback is useful when the primary dependency is unavailable or optional: return cached data, a degraded response, a default value or call another provider.

Both can be asynchronous and both must fit the deadline.

#### Deep dive

Fallback changes semantics. It should be explicit to callers or at least observable internally.

#### Production angle

Track fallback usage. A service can appear healthy while relying heavily on degraded fallback.

#### Traps / caveats

- Fallback can hide outages.
- Retry before fallback can exceed latency budgets.
- A fallback dependency can also fail.

#### Optional Anki

Q: What does fallback do that retry does not?
A: It uses an alternative path or result.

</details>

<a id="cf-res-010"></a>

<details>
<summary><strong>CF-RES-010. How do circuit breakers, rate limiters and bulkheads fit with `CompletableFuture`?</strong></summary>

#### Short answer

They wrap or guard async calls to control failure, traffic and isolation.

#### Interview answer

A circuit breaker can fail fast when a dependency is unhealthy. A rate limiter controls request rate. A bulkhead limits concurrent work or isolates executors. With `CompletableFuture`, these policies should wrap the async operation and return a future representing accepted, rejected, failed or successful execution.

Use a resilience library for non-trivial policies.

#### Deep dive

The policy must handle async completion, not just synchronous method return. Success and failure should be recorded when the future completes.

#### Production angle

Expose metrics for permitted calls, rejected calls, open circuits, fallback usage and bulkhead saturation.

#### Traps / caveats

- Recording success before the future completes is wrong.
- Separate executors can act as bulkheads but still need bounded queues.
- Rejections must map to clear application behavior.

#### Optional Anki

Q: When should an async circuit breaker record success?
A: When the returned future completes successfully.

</details>

<a id="cf-res-019"></a>

<details>
<summary><strong>CF-RES-019. How do you avoid duplicate side effects when retrying async operations?</strong></summary>

#### Short answer

Use idempotency keys, operation identifiers and durable state to make repeated attempts safe.

#### Interview answer

For side-effect operations such as payments, emails or commands, a retry may execute after the first attempt actually succeeded but the response was lost. Use idempotency keys so the receiver can recognize repeated attempts and return the same result or ignore duplicates.

Also design consumers and database writes to tolerate duplicate messages.

#### Deep dive

Timeout does not mean failure. It means the client stopped waiting. The server may still commit the operation.

#### Production angle

Idempotency data often needs persistence and expiry. It should be part of the business workflow, not only an HTTP header.

#### Traps / caveats

- Retrying non-idempotent writes can duplicate charges or orders.
- Client-generated IDs must be unique enough.
- Idempotency must include request semantics, not just a random token.

#### Optional Anki

Q: Why can retry after timeout be dangerous?
A: The original operation may still complete successfully.

</details>

<a id="cf-res-020"></a>

<details>
<summary><strong>CF-RES-020. Why does retry require idempotency?</strong></summary>

#### Short answer

Because the same logical operation may be attempted more than once.

#### Interview answer

Retries happen when the caller is unsure whether an operation succeeded. Without idempotency, repeating the operation can create duplicate side effects: double payment, duplicate shipment, duplicate email or repeated state transition.

Idempotency makes repeated attempts safe by ensuring the same logical command has one effective outcome.

#### Deep dive

Idempotency is easiest for reads and harder for writes. For writes, use keys, unique constraints, command IDs or deduplication tables.

#### Production angle

Idempotency is a correctness requirement for reliable distributed systems, not just an optimization.

#### Traps / caveats

- HTTP method idempotency does not automatically make your business operation safe.
- Deduplication must survive process restarts.
- Retries from clients, gateways and services can stack.

#### Optional Anki

Q: What does idempotency protect against in retry logic?
A: Duplicate side effects.

</details>

<a id="cf-res-022"></a>

<details>
<summary><strong>CF-RES-022. How do you record metrics for retries, fallbacks and timeouts?</strong></summary>

#### Short answer

Record attempts, outcomes, latency, timeout source, fallback usage and dependency labels.

#### Interview answer

Useful metrics include initial calls, retry attempts, final success, final failure, retry-exhausted failures, deadline-exhausted failures, fallback count, timeout count, circuit breaker state, bulkhead rejections and latency per dependency.

Metrics should separate recovered failures from clean successes.

#### Deep dive

Async workflows need metrics at both child-call and aggregate levels. Otherwise partial degradation is invisible.

#### Production angle

Dashboards should show whether async resilience mechanisms are protecting users or masking an ongoing dependency incident.

#### Traps / caveats

- Low error rate with high fallback rate is still a problem.
- Label cardinality can explode if request IDs become metric labels.
- Record final outcome once, not at every stage.

#### Optional Anki

Q: Why track fallback count separately from success count?
A: Fallback success still indicates dependency degradation.

</details>

<a id="cf-res-024"></a>

<details>
<summary><strong>CF-RES-024. When should you prefer a resilience library over hand-written `CompletableFuture` retry code?</strong></summary>

#### Short answer

Prefer a library when policy is non-trivial, shared, observable or business-critical.

#### Interview answer

Hand-written retry is acceptable for small, local cases. Use a resilience library when you need consistent retries, backoff, jitter, circuit breakers, rate limiters, bulkheads, metrics, configuration and tests across services.

Libraries also reduce subtle async bugs around completion timing and policy recording.

#### Deep dive

The hard part is not calling again. It is doing so safely under concurrency, deadlines and partial failures.

#### Production angle

Standardized resilience policies make incidents easier to diagnose and tune.

#### Traps / caveats

- A library still needs correct configuration.
- Do not stack multiple retry layers unknowingly.
- Verify the library integrates correctly with `CompletionStage` completion.

#### Optional Anki

Q: What is a major benefit of resilience libraries?
A: Consistent, observable retry and protection policies.

</details>

<a id="cf-obs-001"></a>

<details>
<summary><strong>CF-OBS-001. Why can `ThreadLocal`-based context be lost in `CompletableFuture`?</strong></summary>

#### Short answer

Because async stages can run on different threads, and `ThreadLocal` values belong to a specific thread.

#### Interview answer

Logging MDC, security context, locale, tenant ID and trace context are often stored in `ThreadLocal`. When a `CompletableFuture` continuation runs on an executor thread, that thread does not automatically have the caller's `ThreadLocal` values.

The result is missing request IDs, lost security context or wrong tenant data.

#### Deep dive

Thread reuse makes this more dangerous: a worker may have stale context if cleanup is incorrect.

#### Production angle

Use framework-supported context propagation, task decorators or explicit context objects. Always clean up after setting thread-local context.

#### Traps / caveats

- `InheritableThreadLocal` is usually not a safe pool solution.
- Copying context blindly can leak secrets or stale users.
- Transaction context should not be propagated casually.

#### Optional Anki

Q: Why does MDC disappear in async callbacks?
A: The callback may run on a different thread.

</details>

<a id="cf-obs-003"></a>

<details>
<summary><strong>CF-OBS-003. How do you propagate MDC logging context and request IDs across `CompletableFuture` tasks?</strong></summary>

#### Short answer

Capture the context before scheduling work, set it in the worker thread, and clear it afterward.

#### Interview answer

Use a decorated executor or wrapper around `Runnable` and `Supplier` that captures MDC/request ID from the submitting thread. When the task runs, it installs the captured context, executes the work and restores or clears the previous context in a `finally` block.

Frameworks and observability libraries often provide this.

#### Deep dive

Restoring previous context matters because worker threads are reused.

#### Production angle

Correct propagation makes async logs searchable by request ID and avoids leaking one user's context into another task.

#### Traps / caveats

- Always clear context in `finally`.
- Do not propagate sensitive values unnecessarily.
- Context capture time matters; capture at submission, not at execution.

#### Optional Anki

Q: Why clear MDC after async task execution?
A: Executor threads are reused.

</details>

<a id="cf-obs-004"></a>

<details>
<summary><strong>CF-OBS-004. How do you propagate security and trace context across async boundaries?</strong></summary>

#### Short answer

Use framework-supported propagation or explicit context passing, and be selective about what is propagated.

#### Interview answer

Security and tracing context may be stored in `ThreadLocal`. For async tasks, propagate it through task decorators, executor wrappers, tracing instrumentation or explicit parameters. Security context should be captured at the right authorization point and cleared after use.

Trace/span context should create correct parent-child relationships across async stages.

#### Deep dive

Not every context should be propagated. Transaction context and mutable request-scoped objects can be unsafe across threads.

#### Production angle

Incorrect propagation can create authorization bugs or broken distributed traces.

#### Traps / caveats

- Stale security context is a serious bug.
- Missing trace context makes fan-out hard to debug.
- Blind propagation can keep large request objects alive.

#### Optional Anki

Q: What is safer than relying on implicit `ThreadLocal` context?
A: Framework-supported propagation or explicit context passing.

</details>

<a id="cf-obs-007"></a>

<details>
<summary><strong>CF-OBS-007. How do you avoid leaking `ThreadLocal` values in thread pools?</strong></summary>

#### Short answer

Set context in a bounded scope and always restore or clear it in `finally`.

#### Interview answer

Executor threads live beyond one request. If an async task sets MDC, tenant or security context and does not clear it, the next task on that thread may see stale data.

Use wrappers that save previous context, install the new one, run the task and restore the old context.

#### Deep dive

Leaks can be correctness bugs, security bugs and memory leaks if context references large request objects.

#### Production angle

Test context cleanup and inspect logs for impossible request/user mixing.

#### Traps / caveats

- Cleanup must happen on success and failure.
- Nested context changes should restore previous values.
- Avoid storing large mutable objects in `ThreadLocal`.

#### Optional Anki

Q: Where should `ThreadLocal` cleanup happen?
A: In a `finally` block.

</details>

<a id="cf-obs-013"></a>

<details>
<summary><strong>CF-OBS-013. How do you debug a `CompletableFuture` pipeline that never completes?</strong></summary>

#### Short answer

Find the stage responsible for completion, then inspect missing callbacks, blocked tasks, executor saturation and unhandled paths.

#### Interview answer

Start by identifying the future that callers wait on. Check whether upstream futures completed, whether any manual future misses a failure path, whether callbacks are invoked, and whether executor tasks are stuck in queues or blocked.

Add timeouts, structured logs at stage boundaries and metrics for outstanding work.

#### Deep dive

Never-completing pipelines often come from manual completion adapters, lost callbacks, swallowed exceptions, or waiting on tasks starved in the same executor.

#### Production angle

Thread dumps, executor metrics, trace spans and dependency timeout metrics are more useful than guessing from code.

#### Traps / caveats

- A swallowed exception can look like a hang.
- A future waiting on `allOf` may hide one child that never completes.
- Debug logging without request IDs is much less useful.

#### Optional Anki

Q: What is a common cause of a never-completing future?
A: A manual completion path that does not complete on failure.

</details>

<a id="cf-obs-014"></a>

<details>
<summary><strong>🧠 CF-OBS-014. How do you debug common-pool starvation?</strong></summary>

#### Short answer

Inspect thread dumps and metrics for common-pool workers blocked or overloaded, then identify who submitted blocking work.

#### Interview answer

Look for `ForkJoinPool.commonPool-worker-*` threads blocked on sockets, JDBC, locks or `join()`. Check whether `CompletableFuture` async methods or parallel streams are using default executors. Review queueing, CPU, latency and timeout patterns.

Fix by moving blocking work to dedicated bounded executors or true async clients.

#### Deep dive

Common-pool starvation can affect unrelated code because many libraries and JDK features may share it.

#### Production angle

Add executor-specific metrics and avoid relying on default async executors in important backend paths.

#### Traps / caveats

- Low CPU does not rule out starvation.
- Increasing common-pool parallelism may hide the root cause.
- Parallel stream regressions can be caused by unrelated common-pool blocking.

#### Optional Anki

Q: What thread dump clue suggests common-pool starvation?
A: Common-pool workers blocked on I/O or waiting for futures.

</details>

<a id="cf-obs-019"></a>

<details>
<summary><strong>CF-OBS-019. What should you log when a `CompletableFuture` times out?</strong></summary>

#### Short answer

Log operation name, dependency, timeout budget, elapsed time, request ID and whether underlying work was cancelled.

#### Interview answer

A timeout log should answer what timed out, after how long, in which request, and what the system did next. Include dependency name, operation, timeout type, remaining deadline, attempt number, fallback decision and safe input identifiers.

Avoid logging sensitive payloads.

#### Deep dive

Distinguish future timeout from HTTP client timeout, connection acquisition timeout, database statement timeout and overall request timeout.

#### Production angle

Good timeout logs make it possible to find misaligned timeouts and wasted late work.

#### Traps / caveats

- Logging only "TimeoutException" is not enough.
- Do not log PII or secrets.
- Log recovered timeouts as degraded outcomes, not clean successes.

#### Optional Anki

Q: What timeout distinction matters in logs?
A: Whether the future timed out or the underlying resource operation timed out.

</details>
