# 12.05. Exceptions, waiting, cancellation and timeouts

---

<a id="cf-err-001"></a>

<details>
<summary><strong>CF-ERR-001. How do you handle exceptions in a `CompletableFuture` chain?</strong></summary>

#### Short answer

Use stage methods such as `handle`, `exceptionally`, `exceptionallyCompose` and `whenComplete`, depending on whether you want to recover, transform or observe.

#### Interview answer

Exceptions thrown inside a stage usually complete the returned stage exceptionally. Downstream normal stages are skipped until a recovery stage handles the failure.

Use `exceptionally` for synchronous fallback, `exceptionallyCompose` for async fallback, `handle` when you need both success and failure branches, and `whenComplete` for observation without normal recovery.

#### Deep dive

Think of failure as part of the pipeline type: each stage can produce success or exceptional completion.

#### Production angle

Async failures need consistent mapping to domain errors, metrics and logs. Do not leave important futures unobserved.

#### Traps / caveats

- `whenComplete` is not usually a recovery method.
- `exceptionally` can accidentally swallow failures.
- Exceptions may be wrapped in `CompletionException` or `ExecutionException`.

#### Optional Anki

Q: Which method handles both success and failure and returns a new value?
A: `handle()`.

</details>

<a id="cf-err-004"></a>

<details>
<summary><strong>CF-ERR-004. What is the difference between `handle()`, `exceptionally()` and `whenComplete()`?</strong></summary>

#### Short answer

`handle` transforms success or failure, `exceptionally` recovers from failure, and `whenComplete` observes completion.

#### Interview answer

`handle((value, error) -> result)` always runs and returns a replacement result. `exceptionally(error -> fallback)` runs only on failure and returns a replacement value. `whenComplete((value, error) -> ...)` observes both cases but normally passes through the original result or failure.

Use `whenComplete` for logging or metrics, not for primary recovery.

#### Deep dive

If `whenComplete` itself throws, it can affect the resulting stage. Observation code should be careful and lightweight.

#### Production angle

Separate recovery from observability. This prevents logging code from accidentally changing business outcomes.

#### Traps / caveats

- `exceptionally` changes a failed pipeline into a successful one if it returns a value.
- `handle` can hide errors if used too broadly.
- `whenComplete` can duplicate logs if used at many levels.

#### Optional Anki

Q: Which method is best for logging without intended recovery?
A: `whenComplete()`.

</details>

<a id="cf-err-011"></a>

<details>
<summary><strong>🧠 CF-ERR-011. What is `exceptionallyCompose()`, and when is asynchronous recovery useful?</strong></summary>

#### Short answer

`exceptionallyCompose()` recovers from failure by returning another `CompletionStage`.

#### Interview answer

`exceptionally` is for synchronous fallback values. `exceptionallyCompose` is for fallback work that is itself asynchronous, such as calling a backup service, refreshing a token, or reading from a secondary source.

It avoids returning a nested future from an error handler.

#### Deep dive

It is the failure-side equivalent of `thenCompose`: flat-map recovery instead of mapping failure to a future object.

#### Production angle

Async fallback still needs timeouts, limits and observability. A backup dependency can fail or become overloaded too.

#### Traps / caveats

- Fallback should not hide systemic outages silently.
- Avoid infinite fallback loops.
- Check target JDK support before using newer API methods.

#### Optional Anki

Q: What is `exceptionallyCompose()` similar to on the success path?
A: `thenCompose()`.

</details>

<a id="cf-err-013"></a>

<details>
<summary><strong>CF-ERR-013. How do exceptions propagate through dependent stages?</strong></summary>

#### Short answer

An exceptional upstream completion usually skips normal continuations and propagates until a recovery stage handles it.

#### Interview answer

If a stage fails, downstream `thenApply`, `thenCompose` or `thenCombine` stages that require a normal value usually do not run. The failure is propagated to the returned stage. A recovery stage such as `handle` or `exceptionally` can convert the failure into a normal result.

If recovery code throws, the pipeline becomes exceptional again.

#### Deep dive

This is why each branch of an async graph needs clear failure semantics. A failure in one branch may prevent combination with another branch.

#### Production angle

Map low-level exceptions at system boundaries so callers receive useful domain errors instead of raw infrastructure failures.

#### Traps / caveats

- A single broad `exceptionally` can hide too much.
- Normal stages after recovery will run with the fallback value.
- Failure propagation can make some expected side effects not run.

#### Optional Anki

Q: What happens to normal `thenApply` stages after an upstream failure?
A: They are skipped unless the failure is recovered first.

</details>

<a id="cf-err-017"></a>

<details>
<summary><strong>CF-ERR-017. What is the difference between `CompletionException` and `ExecutionException`?</strong></summary>

#### Short answer

`join()` throws unchecked `CompletionException`; `get()` throws checked `ExecutionException`.

#### Interview answer

When a `CompletableFuture` fails, `join()` reports the failure by throwing `CompletionException`, which is unchecked. `get()` reports it by throwing `ExecutionException`, which is checked. In both cases, the original cause is usually available through `getCause()`.

`CompletionException` also commonly appears inside async chains as the wrapper for exceptional completion.

#### Deep dive

The wrapper exists because a future needs a uniform way to represent arbitrary failures.

#### Production angle

Centralize unwrapping near boundaries where you map technical failures to logs, metrics or API errors.

#### Traps / caveats

- Do not log only the wrapper message.
- Do not blindly unwrap forever without null checks.
- Cancellation is represented differently with `CancellationException`.

#### Optional Anki

Q: Which method throws `CompletionException`?
A: `join()`.

</details>

<a id="cf-err-019"></a>

<details>
<summary><strong>CF-ERR-019. How do you unwrap the root cause of a failed `CompletableFuture`?</strong></summary>

#### Short answer

Inspect `CompletionException` or `ExecutionException` and use their cause, while preserving useful context.

#### Interview answer

Typical code checks whether the throwable is a `CompletionException` or `ExecutionException` and has a cause. If so, use the cause for classification or mapping. Keep the wrapper context when it helps understand the async boundary.

Do not assume every throwable has a useful cause.

#### Deep dive

Unwrapping is mainly for error classification. For logging, include the full stack trace so async wrappers are not lost.

#### Production angle

Map root causes to retryable, client error, downstream unavailable or internal failure categories.

#### Traps / caveats

- Excessive unwrapping can hide where the failure crossed async boundaries.
- A `CancellationException` should usually be handled separately.
- Some libraries already wrap errors in domain exceptions.

#### Optional Anki

Q: Which method returns the wrapped cause?
A: `Throwable.getCause()`.

</details>

<a id="cf-err-021"></a>

<details>
<summary><strong>CF-ERR-021. How should you log exceptions in `CompletableFuture` chains?</strong></summary>

#### Short answer

Log once at a meaningful boundary with context, correlation ID and dependency information.

#### Interview answer

Use `whenComplete` or boundary-level handling to add structured logs and metrics. Include operation name, dependency, timeout budget, request ID, input key if safe and whether the failure was recovered.

Avoid logging the same exception in every stage and again at the caller.

#### Deep dive

Async stack traces may not show the full logical call path. Structured context matters more than a raw stack trace alone.

#### Production angle

Logs should answer: which async operation failed, for which request, after how long, and what the application did next.

#### Traps / caveats

- Do not log sensitive payloads.
- Do not swallow the exception after logging unless recovery is intentional.
- Make sure MDC or trace context is propagated.

#### Optional Anki

Q: Where should async exceptions usually be logged?
A: At a meaningful boundary, not in every stage.

</details>

<a id="cf-err-022"></a>

<details>
<summary><strong>CF-ERR-022. Why is swallowing exceptions in `exceptionally()` dangerous?</strong></summary>

#### Short answer

Because returning a fallback turns a failed future into a successful one, possibly hiding real outages.

#### Interview answer

`exceptionally` is recovery. If it returns a value, downstream stages see normal completion. That is correct for expected optional failures, but dangerous when used as "log and return null" or "ignore error".

Hidden failures can corrupt responses, lose side effects or make monitoring show success while work actually failed.

#### Deep dive

Fallbacks should be explicit and typed. A domain result like `Unavailable` is often clearer than `null`.

#### Production angle

Count and alert on recovered failures. A fallback path can become the normal path during an incident.

#### Traps / caveats

- Returning `null` can create later `NullPointerException`.
- Optional and required dependencies need different handling.
- Logging without rethrowing is recovery, not just observation.

#### Optional Anki

Q: What does `exceptionally` do if it returns a value?
A: It converts exceptional completion into normal completion.

</details>

<a id="cf-err-024"></a>

<details>
<summary><strong>CF-ERR-024. How do you handle checked exceptions inside `CompletableFuture` lambdas?</strong></summary>

#### Short answer

Catch them and wrap or map them to an unchecked or domain exception.

#### Interview answer

Functional interfaces used by `CompletableFuture` do not usually declare checked exceptions. If a method throws a checked exception, catch it inside the lambda and rethrow a suitable unchecked exception, or call a helper that performs the mapping.

At boundaries, unwrap and map the failure to a domain error.

#### Deep dive

Avoid generic wrappers that erase meaning. A checked `IOException` from a remote call may map to a retryable downstream failure, while a validation error should not.

#### Production angle

Exception mapping should preserve retryability, HTTP status mapping, metrics labels and diagnostic context.

#### Traps / caveats

- Do not use sneaky throws casually.
- Do not wrap everything in `RuntimeException` without classification.
- Preserve interruption when catching `InterruptedException`.

#### Optional Anki

Q: Why do checked exceptions need special handling in async lambdas?
A: The standard functional interfaces usually do not declare them.

</details>

<a id="cf-wait-001"></a>

<details>
<summary><strong>CF-WAIT-001. What is the difference between `join()` and `get()`?</strong></summary>

#### Short answer

Both wait for completion. `join()` throws unchecked wrappers; `get()` throws checked exceptions.

#### Interview answer

`join()` returns the result or throws `CompletionException` on failure. `get()` returns the result or throws checked `ExecutionException` and `InterruptedException`. `get` also has a timeout overload.

Both block the calling thread.

#### Deep dive

`join()` is convenient inside tests or final aggregation code, but it can hide interruption handling because it does not declare `InterruptedException`.

#### Production angle

Avoid blocking in request threads, common-pool workers and event-loop threads. Prefer composition and deadlines.

#### Traps / caveats

- `join()` can still block forever.
- `get()` requires careful interruption handling.
- Blocking may defeat the point of async composition.

#### Optional Anki

Q: Which method throws checked `ExecutionException`?
A: `get()`.

</details>

<a id="cf-wait-003"></a>

<details>
<summary><strong>CF-WAIT-003. When should you avoid `join()` or `get()`?</strong></summary>

#### Short answer

Avoid them inside async pipelines, limited worker pools, request hot paths and event-loop threads.

#### Interview answer

Calling `join()` or `get()` blocks the current thread. If that thread is needed to complete other futures, you can create starvation or deadlock. If it is a request thread, latency and throughput suffer. If it is an event loop, the whole event loop can stall.

Use composition methods instead.

#### Deep dive

Blocking may be acceptable at the very edge of an application, such as a command-line main method or a test assertion.

#### Production angle

During code review, search for blocking waits inside `thenApply`, `thenCompose`, controllers and executor tasks.

#### Traps / caveats

- `join()` inside `thenApply` is a common anti-pattern.
- Blocking on a future scheduled to the same small pool can deadlock.
- Timeout waits still consume a thread while waiting.

#### Optional Anki

Q: What should usually replace `join()` inside a pipeline?
A: Composition with `thenCompose`, `thenCombine` or related methods.

</details>

<a id="cf-wait-009"></a>

<details>
<summary><strong>CF-WAIT-009. What does `cancel()` do on `CompletableFuture`?</strong></summary>

#### Short answer

It completes the future with cancellation and causes dependent stages to see cancellation as exceptional completion.

#### Interview answer

Calling `cancel` attempts to transition the `CompletableFuture` into a cancelled state. If successful, methods like `join()` throw `CancellationException`, and dependent stages that require normal completion do not run normally.

It does not necessarily stop the underlying operation that was supposed to complete the future.

#### Deep dive

Cancellation is part of future state. Stopping work is a separate concern that must be supported by the task, executor, HTTP client, database driver or callback API.

#### Production angle

Design cancellation propagation explicitly for request cancellation, deadlines and shutdown.

#### Traps / caveats

- Cancellation may be best effort.
- Already running work can continue.
- Side effects already performed are not rolled back.

#### Optional Anki

Q: What exception usually represents cancellation?
A: `CancellationException`.

</details>

<a id="cf-wait-010"></a>

<details>
<summary><strong>🧠 CF-WAIT-010. Does `CompletableFuture.cancel(true)` interrupt the running task?</strong></summary>

#### Short answer

No reliable interruption should be assumed for `CompletableFuture` tasks.

#### Interview answer

Unlike some `Future` implementations returned by `ExecutorService.submit`, `CompletableFuture.cancel(true)` mainly cancels the future's completion state. The `mayInterruptIfRunning` parameter does not guarantee interruption of the underlying task.

If the task is already running in an executor, it may continue unless you design separate cancellation support.

#### Deep dive

`CompletableFuture` often does not own the running computation. It may be completed by callbacks, other threads or external systems.

#### Production angle

For remote calls, use client-level cancellation or timeouts. For CPU or blocking tasks, pass cancellation tokens or use APIs that honor interruption.

#### Traps / caveats

- Timeout plus cancel does not necessarily stop a database query.
- Ignoring this can waste capacity after clients disconnect.
- Cooperative cancellation must be tested.

#### Optional Anki

Q: Does `CompletableFuture.cancel(true)` reliably interrupt worker code?
A: No.

</details>

<a id="cf-wait-012"></a>

<details>
<summary><strong>🧠 CF-WAIT-012. How do you propagate cancellation across a `CompletableFuture` graph?</strong></summary>

#### Short answer

Attach explicit cancellation logic that cancels child futures or underlying operations when the parent is cancelled.

#### Interview answer

`CompletableFuture` does not automatically provide structured cancellation for an arbitrary graph. If a parent result is cancelled, you may need a `whenComplete` handler that detects `CancellationException` and calls cancellation APIs for child futures, HTTP calls or tasks.

The policy should define whether siblings are cancelled on failure, success, timeout or client disconnect.

#### Deep dive

Cancellation propagation is hardest when some stages have side effects. You need idempotency and clear ownership.

#### Production angle

Request-scoped async work should not continue indefinitely after the request deadline or client disconnects unless deliberately detached.

#### Traps / caveats

- Cancelling a future is not the same as stopping the resource operation.
- Late completions may still occur.
- Cancelling shared futures can affect other consumers.

#### Optional Anki

Q: Is cancellation propagation automatic across arbitrary future graphs?
A: No, design it explicitly.

</details>

<a id="cf-wait-014"></a>

<details>
<summary><strong>CF-WAIT-014. How do you implement timeout for `CompletableFuture`?</strong></summary>

#### Short answer

Use `orTimeout`, `completeOnTimeout`, a scheduled timeout future, or client-level timeouts.

#### Interview answer

For modern JDKs, `orTimeout(duration, unit)` completes the future exceptionally after the timeout. `completeOnTimeout(value, duration, unit)` completes it normally with a fallback value.

For older code or custom behavior, race the operation with a scheduled future. Also configure the underlying HTTP or database client timeout.

#### Deep dive

Future-level timeout controls the future's completion. Resource-level timeout controls the actual I/O or blocking operation.

#### Production angle

Use both per-call timeouts and an overall deadline for multi-call workflows.

#### Traps / caveats

- A timed-out future may not stop the underlying call.
- Fallback timeout values can hide outages.
- Missing timeout metrics makes incidents harder to diagnose.

#### Optional Anki

Q: Which method completes exceptionally after a timeout?
A: `orTimeout()`.

</details>

<a id="cf-wait-017"></a>

<details>
<summary><strong>CF-WAIT-017. What is the difference between `orTimeout()` and `completeOnTimeout()`?</strong></summary>

#### Short answer

`orTimeout` fails the future on timeout. `completeOnTimeout` supplies a normal fallback value.

#### Interview answer

`orTimeout(timeout, unit)` completes the future exceptionally, typically with a timeout exception, if it has not completed in time.

`completeOnTimeout(value, timeout, unit)` completes it normally with the given value. Use it only when a default or degraded result is correct.

#### Deep dive

Both affect the `CompletableFuture` completion. They do not necessarily cancel the underlying operation.

#### Production angle

Choose based on domain semantics. Required dependencies usually fail; optional dependencies may degrade with an explicit fallback.

#### Traps / caveats

- Normal fallback can make monitoring look successful.
- Timeout values should align with request deadlines.
- Late underlying operations can still consume resources.

#### Optional Anki

Q: Which timeout method returns a normal fallback?
A: `completeOnTimeout()`.

</details>

<a id="cf-wait-019"></a>

<details>
<summary><strong>CF-WAIT-019. How do timeouts interact with the underlying running task?</strong></summary>

#### Short answer

A future timeout usually completes the future; it may not stop the task or I/O operation.

#### Interview answer

If `orTimeout` fires, callers see a timeout failure. But the underlying HTTP request, database query or executor task can continue unless that operation has its own timeout or cancellation support.

This distinction is critical: future-level timeout controls what the caller waits for, not necessarily what resources keep running.

#### Deep dive

Late results may attempt to complete an already timed-out future and lose the completion race.

#### Production angle

Configure timeouts at every layer: future, HTTP client, connection pool, database statement and service deadline.

#### Traps / caveats

- Timed-out database queries can keep holding connections.
- Late side effects can still happen.
- Retrying after timeout can duplicate load while the original work continues.

#### Optional Anki

Q: Does `orTimeout()` guarantee the HTTP request stops?
A: No, the HTTP client must support and receive cancellation or timeout.

</details>

<a id="cf-wait-020"></a>

<details>
<summary><strong>CF-WAIT-020. How do you design a deadline across multiple async calls?</strong></summary>

#### Short answer

Use one overall deadline and derive per-call budgets from the remaining time.

#### Interview answer

For an aggregation request, decide the maximum total time. Each downstream call receives a timeout based on remaining budget and its importance. The final aggregation future also has an overall timeout.

Retries, fallbacks and hedged requests must fit within the same deadline.

#### Deep dive

A deadline is an absolute cutoff. A timeout is a duration. Passing deadlines through the call graph prevents each layer from spending its own full timeout and exceeding the client budget.

#### Production angle

Log remaining budget and timeout source. Many production latency bugs come from uncoordinated per-layer timeouts.

#### Traps / caveats

- Per-call timeouts that sum beyond the request timeout create wasted work.
- Retries without deadline awareness amplify overload.
- Optional calls should be skipped when too little time remains.

#### Optional Anki

Q: Why are deadlines better than independent timeouts in call graphs?
A: They keep all work within one end-to-end budget.

</details>
