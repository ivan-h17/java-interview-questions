# 12.10. Alternatives, performance, traps and senior scenarios

---

<a id="cf-comp-001"></a>

<details>
<summary><strong>CF-COMP-001. When is `CompletableFuture` better than reactive programming?</strong></summary>

#### Short answer

Use `CompletableFuture` when you need a bounded async result graph, not a streaming pipeline.

#### Interview answer

`CompletableFuture` is often simpler for a few independent or dependent async operations: call two services, combine results, apply timeout and fallback, return one response.

Reactive programming is more powerful but adds a larger programming model. If you do not need backpressure, stream operators or end-to-end reactive I/O, `CompletableFuture` can be easier to read and debug.

#### Deep dive

It is especially useful in mostly synchronous applications that need a small async orchestration island.

#### Production angle

Choose the model the team can operate correctly. Simpler code with explicit executors may beat a reactive stack used poorly.

#### Traps / caveats

- `CompletableFuture` has no backpressure.
- Blocking work still needs executor design.
- A complex graph can become hard to cancel.

#### Optional Anki

Q: What workload shape fits `CompletableFuture` better than reactive streams?
A: A bounded async result graph.

</details>

<a id="cf-comp-002"></a>

<details>
<summary><strong>CF-COMP-002. When is reactive programming better than `CompletableFuture`?</strong></summary>

#### Short answer

Reactive programming is better for asynchronous streams, backpressure and end-to-end non-blocking pipelines.

#### Interview answer

Use reactive APIs when data arrives over time, when producers can outpace consumers, or when you need operators over streams of values. Reactor `Flux`, for example, models many values and backpressure. `CompletableFuture` models one eventual result.

Reactive stacks also fit services that are fully built around non-blocking I/O.

#### Deep dive

Reactive programming has a steeper learning curve. Mixing blocking calls into reactive pipelines can destroy its benefits.

#### Production angle

Reactive systems need event-loop discipline, backpressure-aware clients, context propagation and strong observability.

#### Traps / caveats

- Do not use reactive only because it sounds modern.
- Blocking inside event loops is dangerous.
- Debugging reactive pipelines requires different tooling and habits.

#### Optional Anki

Q: What does reactive provide that `CompletableFuture` does not?
A: Backpressure-aware asynchronous streams.

</details>

<a id="cf-comp-004"></a>

<details>
<summary><strong>CF-COMP-004. Does `CompletableFuture` support backpressure?</strong></summary>

#### Short answer

No. `CompletableFuture` does not provide built-in backpressure.

#### Interview answer

`CompletableFuture` represents a single completion. It does not have a protocol for consumers to tell producers to slow down. If you create thousands of futures, they are created unless you add your own limits.

Use bounded executors, semaphores, queues, batching or reactive streams when backpressure is needed.

#### Deep dive

Backpressure matters when data production rate can exceed processing capacity.

#### Production angle

Without backpressure or limits, async fan-out can become memory pressure, queue buildup and downstream overload.

#### Traps / caveats

- `allOf` is not backpressure.
- A fixed thread pool with an unbounded queue is still unsafe.
- Timeouts do not limit task creation.

#### Optional Anki

Q: What must you add to `CompletableFuture` workflows to prevent overload?
A: Explicit concurrency limits or backpressure-capable infrastructure.

</details>

<a id="cf-comp-008"></a>

<details>
<summary><strong>🧠 CF-COMP-008. How do virtual threads change the need for `CompletableFuture`?</strong></summary>

#### Short answer

Virtual threads make many blocking workflows cheaper and simpler, reducing the need to wrap blocking code in complex future graphs.

#### Interview answer

With virtual threads, a service can often write straightforward blocking-style code while still supporting high concurrency for I/O-bound work. That can be simpler than composing many `CompletableFuture` stages around blocking calls.

However, virtual threads do not remove the need for timeouts, connection pool limits, cancellation or safe fan-out.

#### Deep dive

Virtual threads help with thread scalability. They do not make remote systems faster or database pools unlimited.

#### Production angle

For a new Java backend service, compare virtual-thread synchronous code with `CompletableFuture` orchestration before choosing complexity.

#### Traps / caveats

- Virtual threads do not speed up CPU-bound work.
- JDBC connection limits still apply.
- Structured cancellation may still need explicit design.

#### Optional Anki

Q: What do virtual threads simplify?
A: High-concurrency blocking-style I/O code.

</details>

<a id="cf-comp-010"></a>

<details>
<summary><strong>🧠 CF-COMP-010. When is `CompletableFuture` still useful with virtual threads?</strong></summary>

#### Short answer

It is still useful for async APIs, callback adaptation and explicit result composition.

#### Interview answer

Even with virtual threads, many libraries return `CompletionStage` or `CompletableFuture`. You may still need to compose independent async client calls, adapt callbacks, expose async API contracts or integrate with frameworks that expect futures.

`CompletableFuture` is also useful when you want a first-class value representing completion.

#### Deep dive

Virtual threads are an execution model; `CompletableFuture` is a result-composition model. They overlap but are not identical.

#### Production angle

Choose virtual threads for simpler blocking orchestration when suitable, and `CompletableFuture` where async composition is the natural API.

#### Traps / caveats

- Do not combine both models without clear ownership.
- Future cancellation and virtual-thread interruption are different mechanisms.
- Async APIs still need context propagation.

#### Optional Anki

Q: Are virtual threads a complete replacement for `CompletableFuture`?
A: No.

</details>

<a id="cf-comp-011"></a>

<details>
<summary><strong>🧠 CF-COMP-011. What is structured concurrency?</strong></summary>

#### Short answer

Structured concurrency treats related concurrent tasks as a scoped unit with clear lifetime, cancellation and failure handling.

#### Interview answer

Instead of launching independent tasks that can outlive their parent, structured concurrency groups child tasks inside a scope. The parent waits for them, handles failure policy and cancels remaining tasks when the scope exits or fails.

This makes concurrent code look more like structured control flow.

#### Deep dive

The exact Java API status is version-dependent, so verify your target JDK before relying on it in production.

#### Production angle

Structured concurrency helps avoid task leaks, unclear cancellation and orphaned work after request cancellation.

#### Traps / caveats

- It is not the same as `CompletableFuture.allOf`.
- It still needs timeouts and downstream limits.
- API maturity depends on the Java version in use.

#### Optional Anki

Q: What problem does structured concurrency address?
A: Unscoped concurrent tasks with unclear lifetime and cancellation.

</details>

<a id="cf-comp-012"></a>

<details>
<summary><strong>🧠 CF-COMP-012. How does structured concurrency differ from `CompletableFuture` graphs?</strong></summary>

#### Short answer

Structured concurrency gives tasks a lexical scope and parent-owned lifecycle; `CompletableFuture` graphs are generally unstructured.

#### Interview answer

With `CompletableFuture`, tasks and continuations can be created and passed around freely. That is flexible, but cancellation and ownership can become unclear.

Structured concurrency says: these child tasks belong to this scope, and the parent controls waiting, failure and cancellation. It is often easier to reason about request-scoped parallel work.

#### Deep dive

`CompletableFuture` is still powerful for callback-style APIs and result composition. Structured concurrency is better for scoped "do these tasks together" execution.

#### Production angle

Structured scopes can reduce orphaned work and simplify shutdown or request cancellation behavior.

#### Traps / caveats

- Scope cancellation still must reach underlying I/O.
- It does not remove downstream capacity limits.
- Migration from future graphs requires rethinking API contracts.

#### Optional Anki

Q: What does structured concurrency add that raw future graphs lack?
A: A clear parent scope and lifecycle for child tasks.

</details>

<a id="cf-comp-018"></a>

<details>
<summary><strong>CF-COMP-018. When should you use plain synchronous code instead of `CompletableFuture`?</strong></summary>

#### Short answer

Use synchronous code when work is simple, sequential, cheap or already naturally blocking within acceptable limits.

#### Interview answer

If there is no meaningful concurrency, no async API boundary and no latency benefit, `CompletableFuture` adds ceremony. Straight-line synchronous code is often easier to read, debug and test.

With virtual threads, synchronous style can also handle many I/O-bound requests without callback-style composition.

#### Deep dive

Async should solve a real problem: latency hiding, composition, non-blocking integration or API contract. It should not be a default style.

#### Production angle

Simple synchronous code often has clearer stack traces, transaction boundaries and context behavior.

#### Traps / caveats

- Avoid async for vanity.
- Do not block event loops or limited worker pools just because code is synchronous.
- Synchronous fan-out can still need deadlines and limits.

#### Optional Anki

Q: What is a good reason to avoid `CompletableFuture`?
A: It adds complexity without a real async benefit.

</details>

<a id="cf-comp-020"></a>

<details>
<summary><strong>CF-COMP-020. How do you choose between `CompletableFuture`, virtual threads, reactive streams and messaging?</strong></summary>

#### Short answer

Choose based on workload shape: bounded result graph, blocking I/O concurrency, streaming/backpressure, or durable asynchronous workflow.

#### Interview answer

Use `CompletableFuture` for bounded async composition. Use virtual threads for simpler high-concurrency blocking I/O. Use reactive streams for non-blocking streaming and backpressure. Use messaging for durable, decoupled workflows that must survive process restarts.

The choice should consider team skill, observability, reliability and framework ecosystem.

#### Deep dive

These tools can coexist, but mixing them without clear boundaries creates accidental complexity.

#### Production angle

Pick the model that matches failure handling and operational needs, not just the API that is fashionable.

#### Traps / caveats

- `CompletableFuture` is not durable messaging.
- Virtual threads do not provide backpressure.
- Reactive code with blocking calls loses many benefits.

#### Optional Anki

Q: Which model fits durable async workflows?
A: Messaging or a workflow engine, not in-memory futures.

</details>

<a id="cf-perf-001"></a>

<details>
<summary><strong>CF-PERF-001. What is the runtime overhead of many `CompletableFuture` stages?</strong></summary>

#### Short answer

Each stage adds objects, callbacks and scheduling overhead; many stages can increase allocation and latency.

#### Interview answer

`CompletableFuture` is efficient enough for normal orchestration, but thousands of tiny stages per request can create allocation pressure, retained references and executor scheduling overhead.

The overhead is usually worth it for I/O latency hiding, but not for trivial CPU transformations where a loop would be simpler.

#### Deep dive

Measure before optimizing. The main performance bug is often not the future object itself but unbounded fan-out or blocking on the wrong executor.

#### Production angle

Use profiling, allocation metrics and latency percentiles to confirm whether future overhead matters.

#### Traps / caveats

- Do not micro-optimize away readable orchestration prematurely.
- Do not create stage graphs for simple local loops.
- Captured objects may matter more than stage count.

#### Optional Anki

Q: What is a common cost of many future stages?
A: Allocation and scheduling overhead.

</details>

<a id="cf-perf-003"></a>

<details>
<summary><strong>CF-PERF-003. How can capturing large objects in lambdas cause memory retention?</strong></summary>

#### Short answer

Captured objects stay reachable while the future stage that references them is reachable.

#### Interview answer

If an async lambda captures a request object, large DTO, entity graph or buffer, that object may remain in memory until the future and its dependent stages complete and become unreachable.

This is especially problematic for long-running, timed-out or never-completing futures.

#### Deep dive

Capturing `this` can also retain an entire service object and its fields, though singleton services are usually already long-lived. Capturing request-scoped objects is more dangerous.

#### Production angle

Extract only the needed values before creating async lambdas, and avoid passing large mutable entities through stage graphs.

#### Traps / caveats

- Never-completed futures can retain large graphs forever.
- Lambdas can capture more than expected.
- Timeouts may not immediately release underlying task references.

#### Optional Anki

Q: Why can a future retain a request object?
A: A lambda in its stage graph captured it.

</details>

<a id="cf-perf-004"></a>

<details>
<summary><strong>CF-PERF-004. Can `CompletableFuture` cause memory leaks?</strong></summary>

#### Short answer

Yes, mainly through never-completed futures, retained dependent stages and captured objects.

#### Interview answer

`CompletableFuture` itself is not a leak by default. Problems appear when incomplete futures are stored in maps, callbacks never fire, stage graphs retain request data, or timeout paths leave underlying work and references alive.

Manual completion adapters are common sources of this problem.

#### Deep dive

Dependent stages usually remain reachable from upstream futures until completion processing can release them.

#### Production angle

Track outstanding async operations, add timeouts and clean maps or registries on success, failure and cancellation.

#### Traps / caveats

- A cache of pending futures needs eviction.
- `allOf` over many futures can retain the whole group.
- Captured JPA entities can retain persistence graphs.

#### Optional Anki

Q: What future state is most suspicious for memory retention?
A: Never-completed futures.

</details>

<a id="cf-perf-009"></a>

<details>
<summary><strong>CF-PERF-009. How do you diagnose executor saturation?</strong></summary>

#### Short answer

Check active threads, queue size, rejection count, task latency, thread dumps and dependency waits.

#### Interview answer

Executor saturation shows as growing queues, high active count, rejected tasks, increased async latency and timeouts. Thread dumps reveal whether workers are CPU-bound, blocked on I/O, waiting on locks or stuck on `join()`.

Correlate executor metrics with downstream latency and request traffic.

#### Deep dive

Saturation can be healthy backpressure or a sign of overload. The difference is whether latency and rejection behavior match the design.

#### Production angle

Every important async executor should have metrics and meaningful thread names.

#### Traps / caveats

- Low CPU with high latency often means blocking saturation.
- Unbounded queues can hide saturation until latency explodes.
- Rejection without alerting loses visibility.

#### Optional Anki

Q: What executor metric often reveals hidden overload?
A: Queue size.

</details>

<a id="cf-perf-011"></a>

<details>
<summary><strong>CF-PERF-011. Why is unlimited async fan-out bad for latency and memory?</strong></summary>

#### Short answer

It creates too many in-flight tasks, retained objects and downstream calls at once.

#### Interview answer

Unlimited fan-out may look fast in small tests, but in production it can flood executors, queues, HTTP connection pools, database pools and downstream services. It also retains one future and callback chain per item.

The result is higher tail latency, memory pressure and cascading failure.

#### Deep dive

Fan-out should be designed around capacity, not input size alone.

#### Production angle

Use concurrency limits, paging, batching, bulk APIs or backpressure-capable systems.

#### Traps / caveats

- Timeouts may fire before queued tasks start.
- Retries multiply fan-out.
- `allOf` over a huge list is not a capacity control.

#### Optional Anki

Q: What should bound async fan-out?
A: Downstream and executor capacity.

</details>

<a id="cf-perf-013"></a>

<details>
<summary><strong>CF-PERF-013. How do timeouts and retries affect load under failure?</strong></summary>

#### Short answer

Timeouts can free callers, but retries add load; under failure they can amplify pressure.

#### Interview answer

When a dependency slows down, callers time out and may retry. If original work continues, retries add new work while old work is still running. This can overload executors, connection pools and the dependency itself.

Retries need backoff, jitter, deadlines and idempotency.

#### Deep dive

Timeouts are not load shedding unless they also stop or limit underlying work.

#### Production angle

Watch retry rate, in-flight calls, timeout source and downstream saturation during incidents.

#### Traps / caveats

- Retrying timeouts blindly is dangerous.
- Future timeout may not cancel the underlying operation.
- Multiple retry layers can stack unexpectedly.

#### Optional Anki

Q: Why can retries make an outage worse?
A: They add extra load when the dependency is already slow or failing.

</details>

<a id="cf-perf-014"></a>

<details>
<summary><strong>CF-PERF-014. Why can `allOf()` over thousands of futures be problematic?</strong></summary>

#### Short answer

It can retain a large graph of tasks and does not limit how many run concurrently.

#### Interview answer

`allOf` over thousands of futures means thousands of futures, callbacks, captured inputs and possibly downstream calls are in flight or queued. `allOf` only waits; it does not throttle.

Large groups can create memory pressure, long queues and difficult failure aggregation.

#### Deep dive

For large workloads, process in batches or use a bounded-concurrency pattern.

#### Production angle

Prefer bulk APIs, streaming with backpressure or controlled batch processing for large inputs.

#### Traps / caveats

- One failed future can make result extraction tricky.
- Huge pending graphs retain memory.
- Completion storms can create latency spikes.

#### Optional Anki

Q: What does `allOf()` not do for thousands of futures?
A: It does not throttle concurrency.

</details>

<a id="cf-perf-018"></a>

<details>
<summary><strong>🧠 CF-PERF-018. What is Little's Law, and how can it help reason about async throughput?</strong></summary>

#### Short answer

Little's Law relates concurrency, throughput and latency: roughly, concurrency = throughput x latency.

#### Interview answer

If a service needs 100 requests per second and each downstream call takes 200 ms, it needs about 20 concurrent in-flight calls for that dependency, before retries and variance. This helps size pools, connection limits and bulkheads.

It is a reasoning tool, not a replacement for load testing.

#### Deep dive

Tail latency and burstiness mean real systems need headroom, queues and rejection policies.

#### Production angle

Use Little's Law to sanity-check whether executor size or connection pool limits match target traffic.

#### Traps / caveats

- Average latency hides tail behavior.
- Retries increase effective arrival rate.
- A larger pool cannot exceed downstream capacity safely.

#### Optional Anki

Q: What is the rough formula of Little's Law for services?
A: In-flight concurrency equals throughput times latency.

</details>

<a id="cf-trap-002"></a>

<details>
<summary><strong>CF-TRAP-002. What is the "join inside thenApply" anti-pattern?</strong></summary>

#### Short answer

It blocks inside a continuation instead of composing futures.

#### Interview answer

Code like `future.thenApply(x -> otherFuture.join())` blocks the thread running the continuation. If that thread belongs to a limited executor needed by `otherFuture`, it can cause starvation or deadlock.

Use `thenCompose` for dependent futures or `thenCombine` for independent futures.

#### Deep dive

This anti-pattern often appears when developers try to "extract" values from futures too early.

#### Production angle

Search for `join()` and `get()` inside async lambdas during code review.

#### Traps / caveats

- It may pass tests with already completed futures.
- It can block common-pool workers.
- It hides true dependencies in the code.

#### Optional Anki

Q: What should replace `join()` inside a continuation?
A: Proper composition such as `thenCompose()` or `thenCombine()`.

</details>

<a id="cf-trap-003"></a>

<details>
<summary><strong>CF-TRAP-003. What is the "async wrapper around blocking call without executor" anti-pattern?</strong></summary>

#### Short answer

It wraps blocking work in `supplyAsync()` without controlling where that blocking work runs.

#### Interview answer

`CompletableFuture.supplyAsync(() -> blockingHttpCall())` without an executor uses the default async executor, commonly the common pool. Under load, blocking calls can starve unrelated async work.

If you must wrap blocking I/O, use a dedicated bounded executor or consider virtual threads.

#### Deep dive

The caller thread is freed, but capacity is still consumed somewhere.

#### Production angle

Thread dumps with common-pool workers blocked on HTTP or JDBC are a strong signal of this issue.

#### Traps / caveats

- Async wrapper does not make the call non-blocking.
- Future timeout may not stop the blocking call.
- Unbounded submission can overload both executor and dependency.

#### Optional Anki

Q: What is missing from `supplyAsync(blockingCall)` in production code?
A: An explicit bounded executor or better I/O model.

</details>

<a id="cf-trap-007"></a>

<details>
<summary><strong>CF-TRAP-007. What is the "fire-and-forget without logging or retry" anti-pattern?</strong></summary>

#### Short answer

It starts async work and ignores the returned future, losing failures and completion visibility.

#### Interview answer

Fire-and-forget code like `runAsync(() -> sendEmail())` without observing the returned future means exceptions may be lost, retries are absent and shutdown may not wait for the work.

For important side effects, use durable messaging, outbox, explicit error handling or at least a monitored executor and `whenComplete` logging.

#### Deep dive

In-memory async work disappears on process crash. That may be fine for best-effort telemetry, not for business-critical operations.

#### Production angle

Every important async side effect needs an owner, failure path and operational signal.

#### Traps / caveats

- `CompletableFuture<Void>` can still fail.
- Logging alone may not be enough for business reliability.
- Request cancellation can leave detached work running.

#### Optional Anki

Q: What is the main risk of ignored futures?
A: Lost failures.

</details>

<a id="cf-trap-008"></a>

<details>
<summary><strong>CF-TRAP-008. What is the "timeout future but not underlying operation" trap?</strong></summary>

#### Short answer

The caller sees a timeout, but the actual HTTP call, DB query or task keeps running.

#### Interview answer

`orTimeout` can complete a future exceptionally after a duration. That does not guarantee the underlying operation stops. A database query may still hold a connection, and an HTTP request may still consume resources.

You need client or driver timeouts, cancellation support and deadline-aware retry.

#### Deep dive

This trap is especially dangerous when the caller retries, because the old work and new work can overlap.

#### Production angle

Monitor late completions, cancelled requests, DB statement timeouts and connection pool usage.

#### Traps / caveats

- Future timeout is not resource cancellation.
- Late side effects can still occur.
- Retrying timed-out operations requires idempotency.

#### Optional Anki

Q: What must be timed out besides the future?
A: The underlying resource operation.

</details>

<a id="cf-scen-001"></a>

<details>
<summary><strong>CF-SCEN-001. A REST endpoint calls three downstream services. One is required and two are optional. How would you implement this with `CompletableFuture`?</strong></summary>

#### Short answer

Run calls concurrently with limits and timeouts, fail the request on required failure, and return degraded optional results when optional calls fail.

#### Interview answer

Start the three calls using an async client or bounded executor. Apply per-call timeouts and an overall request deadline. The required call should propagate failure. Optional calls should be wrapped with `handle` into success/unavailable results.

Use `allOf` or typed composition to aggregate, then build a response that clearly represents degraded optional data.

#### Deep dive

The exact code matters less than the policy: criticality, timeout budget, bounded concurrency and error mapping.

#### Production angle

Emit metrics for each dependency and for degraded responses. Make sure client disconnect or timeout does not leave expensive work unmanaged.

#### Traps / caveats

- Do not use common pool for blocking calls.
- Do not silently convert required failures to empty data.
- Do not let optional retries exceed the overall deadline.

#### Optional Anki

Q: How should optional downstream failure be represented?
A: As an explicit degraded/unavailable result, not hidden failure.

</details>

<a id="cf-scen-003"></a>

<details>
<summary><strong>CF-SCEN-003. Consumer latency spikes after adding `allOf()` over hundreds of tasks. What would you investigate?</strong></summary>

#### Short answer

Check fan-out size, executor saturation, downstream capacity, connection pools, timeouts, retries and memory retention.

#### Interview answer

`allOf` over hundreds of tasks likely increased concurrency and resource usage. Inspect executor queues and active threads, HTTP/JDBC pool usage, downstream latency, retry rate, timeout rate and GC. Look for unbounded `supplyAsync`, common-pool blocking and queued tasks exceeding deadlines.

Then add batching, bounded concurrency or bulk APIs.

#### Deep dive

Latency spikes often come from tail behavior: one slow child can delay the whole aggregate.

#### Production angle

Use tracing to identify the slowest dependencies and how many calls each request creates.

#### Traps / caveats

- `allOf` is not the root cause by itself; unbounded fan-out often is.
- More threads can worsen downstream overload.
- Timeouts without cancellation can leave work running.

#### Optional Anki

Q: What should you suspect first with `allOf()` over hundreds of tasks?
A: Unbounded fan-out and resource saturation.

</details>

<a id="cf-scen-006"></a>

<details>
<summary><strong>CF-SCEN-006. A feature starts timing out, but database queries still continue running. What is happening?</strong></summary>

#### Short answer

The future or request timed out, but the underlying database operation was not cancelled or timed out.

#### Interview answer

`CompletableFuture.orTimeout` or an HTTP timeout may make the caller stop waiting. If the JDBC statement, transaction or database has no matching timeout/cancellation, the query can keep running and hold a connection.

Fix by setting statement/query timeouts, transaction deadlines, connection pool settings and cancellation propagation where supported.

#### Deep dive

If the caller retries, the original query and retry query may run at the same time.

#### Production angle

Check DB active queries, connection pool exhaustion, application timeouts and late completions.

#### Traps / caveats

- Future cancellation is not JDBC cancellation.
- DB work can continue after client disconnect.
- Retrying timed-out writes requires idempotency.

#### Optional Anki

Q: What timeout is missing when DB queries continue after future timeout?
A: A database/client-level query timeout or cancellation.

</details>

<a id="cf-scen-013"></a>

<details>
<summary><strong>CF-SCEN-013. How would you implement fan-out/fan-in with concurrency limits, timeouts and partial results?</strong></summary>

#### Short answer

Use bounded concurrency, wrap each result, apply per-call and overall deadlines, then aggregate successes and failures.

#### Interview answer

Start with a max concurrency based on downstream capacity. For each input, run the async call through that limiter. Apply a per-call timeout and convert each result with `handle` into a typed success/failure wrapper. Use `allOf` over wrapped futures, collect in input order, and enforce an overall deadline for the whole operation.

Required failures can fail the whole result; optional failures can produce degraded output.

#### Deep dive

For very large inputs, process in batches or use a streaming/backpressure model rather than creating all futures up front.

#### Production angle

Monitor in-flight calls, queue length, per-dependency latency, timeout count, partial failure count and cancellation behavior.

#### Traps / caveats

- Do not use unlimited task submission.
- Do not ignore failure wrappers after aggregation.
- Do not let retries bypass the concurrency limiter.

#### Optional Anki

Q: What should retries share with original calls in fan-out?
A: The same concurrency and deadline limits.

</details>

<a id="cf-scen-020"></a>

<details>
<summary><strong>CF-SCEN-020. How would you explain `CompletableFuture` trade-offs in a design review?</strong></summary>

#### Short answer

Explain what it improves, what it complicates and how the design controls capacity, failure and observability.

#### Interview answer

`CompletableFuture` can reduce latency by composing independent async work and avoiding unnecessary blocking. The trade-off is more complex execution, error handling, cancellation, context propagation and debugging.

In a design review, I would ask: where does work run, what executor is used, what are the limits, what happens on timeout, how are failures mapped, how is context propagated, and how do we observe the graph?

#### Deep dive

Also compare alternatives: synchronous code, virtual threads, reactive streams or messaging may be better depending on workload shape and reliability needs.

#### Production angle

The design is acceptable only if overload behavior and failure semantics are explicit and testable.

#### Traps / caveats

- Async is not automatically faster.
- In-memory futures are not durable.
- Complexity must be justified by latency or integration benefits.

#### Optional Anki

Q: What is the main senior review question for `CompletableFuture` design?
A: How execution, capacity, failure and observability are controlled.

</details>
