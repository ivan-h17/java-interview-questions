# 12.02. Future, CompletionStage and API boundaries

---

<a id="cf-fut-001"></a>

<details>
<summary><strong>CF-FUT-001. What is the difference between `Future` and `CompletableFuture`?</strong></summary>

#### Short answer

`Future` is mainly a blocking result handle. `CompletableFuture` adds completion, callbacks and composition.

#### Interview answer

`Future<T>` lets you check completion, cancel and block with `get()`. It is difficult to chain without blocking.

`CompletableFuture<T>` implements `Future<T>` but also implements `CompletionStage<T>`. It supports transformations, async composition, combining multiple stages, racing, recovery and manual completion.

#### Deep dive

Old `Future` is pull-based: the caller asks for the result. `CompletableFuture` can be push/composition-based: continuations run when completion happens.

#### Production angle

Use `Future` for simple executor task handles. Use `CompletableFuture` when the result participates in an async workflow.

#### Traps / caveats

- `CompletableFuture` still can be blocked with `get()` or `join()`.
- Composition does not remove the need for timeouts.
- Manual completion can be dangerous when exposed to callers.

#### Optional Anki

Q: What does `CompletableFuture` add over `Future`?
A: Non-blocking composition and manual completion.

</details>

<a id="cf-fut-003"></a>

<details>
<summary><strong>CF-FUT-003. Why is `Future` hard to compose?</strong></summary>

#### Short answer

Because `Future` has no standard callback or transformation API.

#### Interview answer

With `Future`, if one task depends on another, the usual approach is to call `get()`, which blocks a thread. Combining two `Future` values also requires manual waiting, polling or extra executor tasks.

`CompletableFuture` has methods like `thenApply`, `thenCompose`, `thenCombine` and `allOf`, so dependencies can be represented directly.

#### Deep dive

`Future` says "a result will exist later". It does not say "when it exists, run this next step". That missing continuation model is the composition problem.

#### Production angle

Blocking composition can cause thread starvation when tasks wait for other tasks in the same limited pool.

#### Traps / caveats

- Polling `isDone()` wastes complexity and can still race.
- `get()` without a timeout can hang forever.
- Wrapping everything in more tasks can hide deadlocks.

#### Optional Anki

Q: What method family makes `CompletableFuture` easier to compose?
A: `thenApply`, `thenCompose`, `thenCombine`, `allOf` and related stage methods.

</details>

<a id="cf-fut-004"></a>

<details>
<summary><strong>CF-FUT-004. How does `Future.get()` affect the calling thread?</strong></summary>

#### Short answer

`Future.get()` blocks the calling thread until the result is available, the task fails or waiting is interrupted.

#### Interview answer

Calling `get()` turns an async result back into synchronous waiting. The current thread cannot do other work while blocked. `get(timeout, unit)` bounds the wait, but still blocks during that time.

If many request threads or worker threads block on futures, the service can lose throughput or deadlock.

#### Deep dive

Blocking is sometimes acceptable at a boundary, for example in a test, CLI command or final aggregation point. It is dangerous inside limited executor pools or event-loop threads.

#### Production angle

Avoid waiting forever. Use deadlines, timeouts, cancellation and non-blocking composition where possible.

#### Traps / caveats

- `get()` wraps failures in `ExecutionException`.
- `get()` can throw `InterruptedException`.
- Blocking inside the same executor that must run the awaited task can starve the pool.

#### Optional Anki

Q: What is the main risk of `Future.get()` in a worker pool?
A: It blocks a worker and can cause starvation.

</details>

<a id="cf-fut-007"></a>

<details>
<summary><strong>CF-FUT-007. What is the difference between `Future` and `CompletionStage`?</strong></summary>

#### Short answer

`Future` focuses on waiting for a result. `CompletionStage` focuses on composing what happens after completion.

#### Interview answer

`Future` exposes blocking methods such as `get()` and cancellation. `CompletionStage` exposes pipeline methods such as `thenApply`, `thenCompose`, `thenCombine`, `handle` and `whenComplete`.

`CompletableFuture` implements both, so it can be used as a traditional future and as a composable stage.

#### Deep dive

`CompletionStage` is intentionally narrower than `CompletableFuture`: it does not expose direct manual completion methods like `complete`.

#### Production angle

Return `CompletionStage` from APIs when the caller should compose the result but should not own completion.

#### Traps / caveats

- `CompletionStage` does not provide `join()`.
- Some APIs still return `CompletableFuture` for convenience.
- Cancellation behavior through `CompletionStage` should be documented.

#### Optional Anki

Q: Which interface models async pipeline composition?
A: `CompletionStage`.

</details>

<a id="cf-fut-008"></a>

<details>
<summary><strong>CF-FUT-008. Why might an API return `CompletionStage` instead of `CompletableFuture`?</strong></summary>

#### Short answer

To expose composition without exposing manual completion and mutation methods.

#### Interview answer

Returning `CompletableFuture` gives callers methods like `complete`, `completeExceptionally`, `obtrudeValue` and `cancel`. That may let external code interfere with a result owned by the callee.

Returning `CompletionStage` communicates: "you may attach continuations, but this component owns completion."

#### Deep dive

This is the same API design principle as returning `List` instead of `ArrayList`, or an interface instead of a mutable implementation.

#### Production angle

For shared libraries and service interfaces, narrower async return types reduce accidental coupling and make contracts easier to maintain.

#### Traps / caveats

- `toCompletableFuture()` may still expose a future-like object.
- A narrow type does not fully document threading or cancellation.
- Internal code may still prefer `CompletableFuture` for implementation.

#### Optional Anki

Q: What capability does `CompletionStage` hide from callers?
A: Direct manual completion.

</details>

<a id="cf-fut-009"></a>

<details>
<summary><strong>CF-FUT-009. How can you adapt an old `Future` into a `CompletableFuture`?</strong></summary>

#### Short answer

Submit a task that waits for the old `Future` and completes a `CompletableFuture`, or complete it from the producer if you control the producer.

#### Interview answer

The simple adapter is:

```java
CompletableFuture<T> cf = CompletableFuture.supplyAsync(() -> {
    try {
        return future.get();
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new CompletionException(e);
    } catch (ExecutionException e) {
        throw new CompletionException(e.getCause());
    }
}, executor);
```

This still needs cancellation propagation where possible and a dedicated executor so blocking does not pollute the common pool.

#### Deep dive

If you control the original async source, a better design is to complete a `CompletableFuture` at the point where the operation actually succeeds or fails, instead of blocking a bridge thread.

#### Production angle

Adapting old `Future` APIs often consumes one thread per blocked wait. That must be bounded and monitored.

#### Traps / caveats

- Do not block the common pool with many adapter tasks.
- Preserve interruption.
- Decide what cancellation should do to the original future.

#### Optional Anki

Q: What is the main cost of adapting old `Future` by calling `get()`?
A: It blocks a thread while waiting.

</details>

<a id="cf-fut-010"></a>

<details>
<summary><strong>🧠 CF-FUT-010. What are the limitations of wrapping `Future` with `supplyAsync(() -> future.get())`?</strong></summary>

#### Short answer

It gives a composable wrapper, but it still blocks a worker thread and may not propagate cancellation cleanly.

#### Interview answer

`supplyAsync(() -> future.get())` is an adapter, not a real conversion to non-blocking execution. It uses one executor thread to wait. Under load, many wrappers can exhaust the adapter executor.

It also needs careful handling for `InterruptedException`, `ExecutionException`, timeout behavior and cancellation. Cancelling the `CompletableFuture` does not automatically guarantee the original `Future` is cancelled unless you wire that behavior.

#### Deep dive

The wrapper future and original future have separate lifecycles. A robust bridge needs to define how success, failure, interruption and cancellation flow both ways.

#### Production angle

Use this bridge sparingly and isolate it behind a bounded executor. Prefer native async APIs when available.

#### Traps / caveats

- It can cause thread starvation.
- It can hide interruption bugs.
- It does not make a blocking API non-blocking.

#### Optional Anki

Q: Why is `supplyAsync(() -> future.get())` not true non-blocking adaptation?
A: It blocks a worker thread until the old future completes.

</details>

<a id="cf-fut-011"></a>

<details>
<summary><strong>CF-FUT-011. What is the difference between `CompletableFuture` and `ExecutorService`?</strong></summary>

#### Short answer

`ExecutorService` runs tasks. `CompletableFuture` represents and composes their results.

#### Interview answer

`ExecutorService` owns worker threads, queues, scheduling and lifecycle. You submit `Runnable` or `Callable` tasks to it.

`CompletableFuture` is a completion and composition abstraction. It may use an executor to run async stages, but it is not itself a thread pool.

#### Deep dive

`supplyAsync(task, executor)` connects the two: the executor runs the supplier, and the `CompletableFuture` represents its eventual result.

#### Production angle

A production async design needs both: good composition and explicit executor ownership.

#### Traps / caveats

- A future does not control executor queue capacity.
- An executor does not automatically compose task results.
- Ignoring executor lifecycle can leak threads.

#### Optional Anki

Q: Which one owns threads?
A: `ExecutorService`.

</details>

<a id="cf-fut-012"></a>

<details>
<summary><strong>CF-FUT-012. When would you use `ExecutorService` directly instead of `CompletableFuture`?</strong></summary>

#### Short answer

Use `ExecutorService` directly when you mainly need task execution, lifecycle control or bulk task APIs.

#### Interview answer

Direct `ExecutorService` usage is reasonable for worker pools, background jobs, scheduled tasks, firewalled task submission, `invokeAll`, graceful shutdown and low-level concurrency control.

Use `CompletableFuture` when you need result composition: dependent calls, fan-out/fan-in, recovery stages or async API return values.

#### Deep dive

The two are often combined. The executor is the execution resource; futures are the result graph.

#### Production angle

For infrastructure code, explicit executors are often clearer. For service orchestration, `CompletableFuture` can make dependencies more readable.

#### Traps / caveats

- Do not use `CompletableFuture` only to avoid designing pool capacity.
- Do not use raw executor tasks when composition would remove blocking waits.
- Always shut down owned executors.

#### Optional Anki

Q: When does `CompletableFuture` add the most value over direct executor submission?
A: When task results need to be composed.

</details>

<a id="cf-fut-014"></a>

<details>
<summary><strong>🧠 CF-FUT-014. What is a minimal `CompletionStage` view?</strong></summary>

#### Short answer

It is a restricted stage view that exposes composition but not the full mutable `CompletableFuture` API.

#### Interview answer

`CompletableFuture.minimalCompletionStage()` returns a `CompletionStage` view backed by the same completion, but callers should not be able to complete it directly. This is useful when an implementation uses `CompletableFuture` internally but wants to expose a narrower read/compose contract.

#### Deep dive

It is stronger than merely returning a variable typed as `CompletionStage`, because the object itself is a restricted view rather than the original mutable future.

#### Production angle

Library APIs can use minimal views to reduce accidental external mutation, especially when completion is owned by internal infrastructure.

#### Traps / caveats

- Callers can still compose new stages from it.
- Exact behavior around conversion should be checked against the target JDK.
- It does not replace clear API documentation.

#### Optional Anki

Q: What problem does `minimalCompletionStage()` address?
A: It hides direct completion methods from API consumers.

</details>

<a id="cf-fut-015"></a>

<details>
<summary><strong>CF-FUT-015. Why can exposing `CompletableFuture` directly be risky in public APIs?</strong></summary>

#### Short answer

Because callers can complete, cancel or otherwise interfere with a future they should only observe.

#### Interview answer

`CompletableFuture` is mutable. If a public method returns the actual future used internally, external code may call `complete`, `completeExceptionally`, `cancel` or attach expensive continuations. That can violate ownership and make bugs hard to trace.

Returning `CompletionStage`, a minimal stage view or a domain-specific abstraction can make the contract safer.

#### Deep dive

The risk is not only malicious code. A test, integration or convenience wrapper can accidentally complete a shared future and create race conditions.

#### Production angle

Public async APIs should document result ownership, threading, cancellation, timeout behavior and whether returned stages are hot or lazy.

#### Traps / caveats

- Type narrowing alone may not hide the original object.
- Cancellation may have unclear semantics.
- Public futures can make binary compatibility harder if you later change async style.

#### Optional Anki

Q: Why is `CompletableFuture` a leaky public return type?
A: It exposes mutable completion and cancellation operations.

</details>

<a id="cf-api-001"></a>

<details>
<summary><strong>CF-API-001. Should service methods return `CompletableFuture` or plain values?</strong></summary>

#### Short answer

Return plain values for synchronous services; return async types only when asynchrony is part of the contract.

#### Interview answer

If a method performs normal synchronous business logic, returning `CompletableFuture` adds complexity without benefit. It forces callers into async composition and exposes threading concerns.

Return `CompletionStage` or `CompletableFuture` when the method genuinely starts or composes asynchronous work, or when the surrounding framework expects an async return type.

#### Deep dive

Avoid letting `CompletableFuture` leak into domain models. Async orchestration belongs at application, infrastructure or integration boundaries.

#### Production angle

A team should standardize async API contracts: executor ownership, cancellation, timeouts, context propagation and error mapping.

#### Traps / caveats

- Do not wrap every method in `completedFuture()` just for style.
- Do not hide blocking I/O behind async types without documenting it.
- Prefer `CompletionStage` for public composition-only APIs.

#### Optional Anki

Q: When should a service method expose an async return type?
A: When async behavior is part of its real contract.

</details>
