# 12.07. Backend integration, Spring and persistence boundaries

---

<a id="cf-be-001"></a>

<details>
<summary><strong>CF-BE-001. How do you correctly perform multiple parallel requests to microservices?</strong></summary>

#### Short answer

Start independent calls concurrently, apply timeouts and limits, then combine results with explicit failure policy.

#### Interview answer

For independent downstream calls, create one future per call using an async HTTP client or a bounded executor. Apply per-call timeouts, decide which calls are required, and combine with `thenCombine`, `allOf` or typed wrappers.

Do not just launch unlimited calls and call `join()` everywhere.

#### Deep dive

Parallel calls reduce latency only when the downstream work is independent and the system has capacity for the additional concurrency.

#### Production angle

Protect downstream services with concurrency limits, bulkheads, rate limits, retries with backoff and metrics per dependency.

#### Traps / caveats

- Parallel fan-out can amplify traffic.
- One slow dependency can hold the whole response without a deadline.
- Optional failures should be visible, not silently ignored.

#### Optional Anki

Q: What must accompany parallel microservice calls?
A: Timeouts, limits, failure policy and observability.

</details>

<details>
<summary><strong>CF-BE-003. How do you fail fast when one critical remote call fails?</strong></summary>

#### Short answer

Complete the aggregate result exceptionally on critical failure and cancel or ignore remaining work according to policy.

#### Interview answer

Mark dependencies as critical or optional. For a critical call, attach a handler that completes the parent future exceptionally when it fails. Remaining optional or sibling calls can be cancelled if supported, or allowed to finish while their results are ignored.

This should be distinct from partial-success behavior.

#### Deep dive

Fail-fast saves work only if cancellation reaches the underlying operation or prevents expensive downstream processing.

#### Production angle

Log which critical dependency failed and record cancellation and late-completion metrics for siblings.

#### Traps / caveats

- `allOf` is not fail-fast cancellation.
- Cancelling a future may not stop HTTP or DB work.
- Do not fail fast on optional dependency failures.

#### Optional Anki

Q: What is the first design decision for fail-fast aggregation?
A: Which dependencies are critical.

</details>

<a id="cf-be-004"></a>

<details>
<summary><strong>CF-BE-004. How do you return partial results when optional calls fail?</strong></summary>

#### Short answer

Wrap each optional result as success, failure or unavailable, then aggregate without failing the whole response.

#### Interview answer

Use `handle` on optional futures to convert failures into a typed degraded result. Required futures can still fail the whole request. The final response should distinguish missing optional data from real empty data when that matters.

Do not return `null` for failed optional dependencies unless the API contract is explicit.

#### Deep dive

Partial results are business semantics. They need product and API agreement, not just code fallback.

#### Production angle

Emit metrics for degraded responses, dependency failures and fallback usage.

#### Traps / caveats

- Silent partial responses can hide outages.
- Returning stale fallback data may need labeling.
- Optional failures should not break required invariants.

#### Optional Anki

Q: Which method is often used to convert optional failure into a typed result?
A: `handle()`.

</details>

<a id="cf-be-005"></a>

<details>
<summary><strong>CF-BE-005. How do you apply per-call timeouts and an overall timeout?</strong></summary>

#### Short answer

Give every downstream call its own timeout and also enforce one end-to-end deadline for the whole aggregation.

#### Interview answer

Each remote call should have an HTTP client timeout and usually a future-level timeout. The aggregate future should have an overall deadline so all calls, retries and fallbacks fit inside the request budget.

Per-call timeout protects individual dependencies. Overall timeout protects the caller.

#### Deep dive

Use remaining-time budgets rather than independent fixed timeouts at every layer.

#### Production angle

Timeout metrics should identify whether the timeout happened at the HTTP client, database, future aggregation or gateway.

#### Traps / caveats

- Future timeout alone may not stop the underlying call.
- Per-call retries can exceed the overall deadline.
- Timeouts should be shorter than upstream client timeouts.

#### Optional Anki

Q: What is the difference between per-call timeout and overall timeout?
A: Per-call bounds one dependency; overall bounds the entire workflow.

</details>

<a id="cf-be-006"></a>

<details>
<summary><strong>CF-BE-006. How do you avoid overwhelming downstream services with `CompletableFuture` fan-out?</strong></summary>

#### Short answer

Limit concurrency, batch where possible, use bulkheads and respect downstream rate limits.

#### Interview answer

Do not fan out one request into hundreds of concurrent downstream calls without control. Use bulk APIs, batching, a bounded executor, semaphore, rate limiter or async client max-concurrency setting.

Retries and hedged requests must count against the same budget.

#### Deep dive

Fan-out multiplies traffic. A service handling 100 requests per second with 20 downstream calls per request can create 2,000 downstream calls per second before retries.

#### Production angle

Monitor fan-out size, dependency QPS, concurrency, timeout rate, retry rate and circuit breaker state.

#### Traps / caveats

- Executor size is not the only limit.
- Downstream connection pools and rate limits matter.
- A retry storm can overwhelm a recovering service.

#### Optional Anki

Q: What does fan-out multiply?
A: Downstream request volume.

</details>

<a id="cf-be-008"></a>

<details>
<summary><strong>CF-BE-008. How do you combine `CompletableFuture` with HTTP clients?</strong></summary>

#### Short answer

Prefer HTTP clients that already return `CompletableFuture` or async completion stages.

#### Interview answer

Java's `HttpClient.sendAsync` returns a `CompletableFuture`. Other async clients may return similar futures, promises or callbacks that can be adapted. Compose those futures directly with timeouts and error handling.

For blocking clients, use a dedicated bounded executor if you must wrap calls in `supplyAsync`.

#### Deep dive

Native async clients usually avoid dedicating one platform thread per in-flight request, depending on implementation.

#### Production angle

Configure both client-level timeouts and future-level workflow deadlines. Track dependency metrics separately.

#### Traps / caveats

- Do not block event-loop or callback threads.
- Future cancellation may need explicit HTTP request cancellation.
- Wrapping a blocking client is not the same as non-blocking I/O.

#### Optional Anki

Q: Which Java HTTP client method returns a `CompletableFuture`?
A: `HttpClient.sendAsync()`.

</details>

<a id="cf-be-009"></a>

<details>
<summary><strong>CF-BE-009. What is the difference between an async HTTP client and wrapping blocking HTTP calls in `supplyAsync()`?</strong></summary>

#### Short answer

An async client can avoid blocking one worker per request; `supplyAsync` just moves blocking to another thread.

#### Interview answer

With a blocking client, each in-flight call occupies a thread. Wrapping it in `supplyAsync` frees the caller thread but consumes an executor thread.

An async HTTP client usually integrates with non-blocking I/O or an event-driven model and completes a future when the response arrives.

#### Deep dive

Async clients are not automatically better. They need correct event-loop usage, backpressure or concurrency control, timeouts and careful callback behavior.

#### Production angle

Choose based on workload, team familiarity, stack model and operational complexity. For many Java services, virtual threads may also be a simpler option for blocking HTTP.

#### Traps / caveats

- Blocking wrappers can exhaust executor threads.
- Async clients can still overload downstream services.
- Do not perform blocking work on async client callback threads.

#### Optional Anki

Q: What does `supplyAsync` do for a blocking HTTP call?
A: It blocks a worker thread instead of the caller thread.

</details>

<a id="cf-be-010"></a>

<details>
<summary><strong>CF-BE-010. Why can async code still exhaust a database connection pool?</strong></summary>

#### Short answer

Because async task submission can exceed the number of database connections available.

#### Interview answer

If many `CompletableFuture` tasks call JDBC or JPA concurrently, they still need real database connections. When concurrency exceeds the pool size, tasks block waiting for connections, time out or create queueing that increases latency.

Async code does not make the database pool larger.

#### Deep dive

JDBC is typically blocking. Using `supplyAsync` around JDBC means a worker thread may block while also waiting for a connection.

#### Production angle

Align async concurrency limits with HikariCP pool size, database capacity and transaction duration.

#### Traps / caveats

- More async threads can make DB timeouts worse.
- Connection pool exhaustion may look like application slowness.
- Retrying DB calls can multiply connection pressure.

#### Optional Anki

Q: What resource limits async JDBC concurrency?
A: The database connection pool and database capacity.

</details>

<a id="cf-be-011"></a>

<details>
<summary><strong>CF-BE-011. Why should you avoid sharing JPA `EntityManager` across `CompletableFuture` tasks?</strong></summary>

#### Short answer

`EntityManager` and its persistence context are not designed to be shared across threads.

#### Interview answer

JPA `EntityManager` represents a persistence context tied to a unit of work, often associated with a transaction and thread-bound framework context. Sharing it across async tasks can cause thread-safety bugs, lazy loading failures, inconsistent flushing and transaction boundary confusion.

Each async task that uses JPA should have its own transactional boundary and persistence context.

#### Deep dive

Managed entities also carry lazy-loading state. Moving them across threads after the session closes can trigger `LazyInitializationException`.

#### Production angle

Fetch required data into DTOs or immutable values before crossing async boundaries, or execute separate repository calls safely inside each task.

#### Traps / caveats

- JPA entities are not good async DTOs.
- Lazy collections can fail outside the transaction.
- Sharing mutable managed entities can corrupt assumptions.

#### Optional Anki

Q: Is `EntityManager` safe to share between async tasks?
A: No.

</details>

<a id="cf-be-012"></a>

<details>
<summary><strong>CF-BE-012. How does `@Transactional` behave across `CompletableFuture` async boundaries?</strong></summary>

#### Short answer

Spring transaction context is usually thread-bound and does not automatically propagate to async tasks.

#### Interview answer

In Spring, `@Transactional` typically binds transaction state to the current thread. If a method starts `CompletableFuture` work on another executor thread, that thread usually does not share the original transaction.

Async work may run outside the transaction, after commit, after rollback or with its own transaction if configured separately.

#### Deep dive

Blindly propagating transaction context to another thread is usually unsafe. Database connections and persistence contexts are not meant to be shared this way.

#### Production angle

For side effects after commit, use transaction synchronization, events after commit, messaging or the transactional outbox pattern.

#### Traps / caveats

- Async tasks inside a transaction can see uncommitted assumptions.
- Rollback does not undo async side effects already started.
- Self-invocation can bypass Spring proxies for both `@Transactional` and `@Async`.

#### Optional Anki

Q: Why does a Spring transaction usually not follow a `CompletableFuture` to another thread?
A: The transaction context is thread-bound.

</details>

<a id="cf-be-014"></a>

<details>
<summary><strong>CF-BE-014. How do you safely load data asynchronously with JPA/Hibernate?</strong></summary>

#### Short answer

Use separate transactional tasks or fetch needed data synchronously before crossing async boundaries.

#### Interview answer

If multiple async tasks need database data, each task should call a service/repository method with its own transaction and persistence context. Do not share an `EntityManager` or managed entities between tasks.

Alternatively, fetch all required data in one query or batch before starting async non-DB work.

#### Deep dive

Often the best solution is not async JPA at all. Better query design, joins, fetch graphs or batch loading may be simpler and safer.

#### Production angle

Async DB fan-out should be limited by connection pool size and measured carefully.

#### Traps / caveats

- Parallel DB calls can overload the database.
- Lazy loading after transaction end can fail.
- Async tasks must map exceptions and timeouts clearly.

#### Optional Anki

Q: What should each async JPA task have?
A: Its own safe transaction and persistence context.

</details>

<a id="cf-be-015"></a>

<details>
<summary><strong>CF-BE-015. How do you avoid N+1 or lazy-loading issues in async workflows?</strong></summary>

#### Short answer

Fetch the required shape deliberately before async processing, or use safe per-task queries with batching.

#### Interview answer

Async code can hide N+1 problems by running many lazy loads in parallel, but the database still receives too many queries. Prefer DTO projections, joins, entity graphs, batch fetching or bulk queries.

If async tasks need data, pass IDs or DTOs, not half-initialized entities.

#### Deep dive

Parallelizing N+1 often turns a latency problem into a database overload problem.

#### Production angle

Use SQL logs, query counts, database metrics and tracing to verify that async processing did not multiply queries.

#### Traps / caveats

- Lazy loading in callbacks may run after the session is closed.
- Parallel lazy loads can exhaust connections.
- DTO mapping should happen inside a clear persistence boundary.

#### Optional Anki

Q: Why is parallelizing N+1 a bad fix?
A: It can overload the database with many concurrent queries.

</details>

<a id="cf-be-016"></a>

<details>
<summary><strong>CF-BE-016. How do you integrate `CompletableFuture` with Spring `@Async`?</strong></summary>

#### Short answer

Return `CompletableFuture` from `@Async` methods and configure the executor explicitly.

#### Interview answer

Spring `@Async` runs methods through a proxy on an async executor. A method can return `CompletableFuture<T>` so callers can compose the result. Configure the executor with thread names, pool limits and rejection policy.

Remember that `@Async` usually requires a proxied external method call; self-invocation does not trigger it.

#### Deep dive

`@Async` and `CompletableFuture.supplyAsync` are two different ways to schedule work. Avoid mixing them randomly without knowing which executor is used.

#### Production angle

Spring async executors should be application-managed beans with metrics and graceful shutdown.

#### Traps / caveats

- Self-invocation bypasses `@Async`.
- Transaction and security context do not magically propagate.
- Ignored returned futures can lose exceptions.

#### Optional Anki

Q: What should be explicitly configured for `@Async`?
A: Its executor.

</details>

<a id="cf-be-017"></a>

<details>
<summary><strong>CF-BE-017. What are common pitfalls of returning `CompletableFuture` from Spring MVC controllers?</strong></summary>

#### Short answer

Pitfalls include lost context, unclear timeout behavior, blocking work on the wrong executor and unobserved async failures.

#### Interview answer

Spring MVC can support async return types, but the controller still needs safe execution policy. If the future wraps blocking work on the common pool, request threads may be freed while worker pools become overloaded. Security, MDC and tracing context may also be lost.

Timeouts must align with servlet, gateway and client timeouts.

#### Deep dive

Returning a future does not make the endpoint resilient. It changes where waiting happens.

#### Production angle

Use explicit executors, request deadlines, exception mapping, context propagation and metrics for async controller paths.

#### Traps / caveats

- Client disconnect may not cancel underlying work.
- Framework timeout may differ from future timeout.
- Errors must map to consistent HTTP responses.

#### Optional Anki

Q: What does returning `CompletableFuture` from MVC not solve by itself?
A: Capacity, timeout, context and failure policy.

</details>

<details>
<summary><strong>CF-BE-021. How do you handle audit logging or outbox writes in async flows?</strong></summary>

#### Short answer

Treat durable side effects as part of a reliable transaction or message flow, not as casual fire-and-forget futures.

#### Interview answer

Audit logs, outbox records and business events usually require reliability. If they must be consistent with database changes, write them in the same transaction or use a transactional outbox. Async processing can then publish or forward the durable record after commit.

Do not rely on in-memory `CompletableFuture.runAsync` for critical auditability.

#### Deep dive

Async side effects can run after rollback, fail silently or disappear on process crash unless made durable.

#### Production angle

For regulated or payment flows, require idempotency keys, durable storage, retries and dead-letter handling.

#### Traps / caveats

- Fire-and-forget audit writes can be lost.
- Async publish inside an open transaction can expose rolled-back data.
- Duplicate retries require idempotent consumers.

#### Optional Anki

Q: What pattern helps coordinate DB changes and async event publishing?
A: Transactional outbox.

</details>

<details>
<summary><strong>CF-BE-023. How do `CompletableFuture` timeouts relate to HTTP client and database timeouts?</strong></summary>

#### Short answer

Future timeouts control future completion; HTTP and database timeouts control the underlying resource operation.

#### Interview answer

`orTimeout` can make callers stop waiting on a future. But an HTTP request or DB query may continue unless the client, driver or database statement has its own timeout or cancellation.

A complete design uses coordinated timeouts at all relevant layers.

#### Deep dive

The same principle applies to connection acquisition, socket reads, request deadlines and transaction timeouts.

#### Production angle

Timeout logs should identify which layer timed out and whether the underlying operation was cancelled.

#### Traps / caveats

- Future timeout alone can leave DB queries running.
- HTTP client timeout longer than gateway timeout wastes work.
- Retrying after future timeout can duplicate load.

#### Optional Anki

Q: Does a future timeout always stop a database query?
A: No.

</details>

<a id="cf-be-025"></a>

<details>
<summary><strong>CF-BE-025. How do you design an async aggregation endpoint safely?</strong></summary>

#### Short answer

Define dependency criticality, concurrency limits, timeouts, failure policy, context propagation and observability before coding the futures.

#### Interview answer

A safe aggregator uses independent async calls only where they are truly independent. It sets per-call and overall deadlines, limits fan-out, separates required from optional dependencies, maps errors to domain responses and avoids sharing JPA/session state across tasks.

It also propagates trace/request context and records metrics per dependency.

#### Deep dive

The code shape might use `thenCombine`, `allOf` and typed result wrappers, but the design is mostly about resource and failure semantics.

#### Production angle

Load test slow, failing and partially failing dependencies. Verify degradation behavior and downstream protection.

#### Traps / caveats

- Do not make one request trigger unbounded downstream calls.
- Do not use common pool for blocking dependency calls.
- Do not return partial data without clear contract.

#### Optional Anki

Q: What is the core senior concern in async aggregation?
A: Safe resource, timeout and failure design, not just `allOf()` syntax.

</details>
