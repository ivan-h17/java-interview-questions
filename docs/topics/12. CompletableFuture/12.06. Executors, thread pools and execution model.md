# 12.06. Executors, thread pools and execution model

---

<a id="cf-exec-003"></a>

<details>
<summary><strong>CF-EXEC-003. What executor is used by default for async `CompletableFuture` methods?</strong></summary>

#### Short answer

Async methods without an explicit executor usually use the common `ForkJoinPool`.

#### Interview answer

Methods such as `supplyAsync`, `runAsync` and `thenApplyAsync` have overloads with and without an `Executor`. If you do not pass an executor, the JDK normally uses `ForkJoinPool.commonPool()` for async execution.

That default is convenient but should not be assumed safe for blocking backend I/O.

#### Deep dive

The exact execution details can depend on runtime configuration and JDK behavior, but the practical interview answer is: pass an executor when execution policy matters.

#### Production angle

Use explicit executors for service-specific work so you can size, name, monitor and isolate them.

#### Traps / caveats

- The common pool is shared process-wide.
- Blocking common-pool workers can affect unrelated code.
- Non-async continuations may not use an executor at all.

#### Optional Anki

Q: What should you do when async execution policy matters?
A: Pass an explicit `Executor`.

</details>

<a id="cf-exec-004"></a>

<details>
<summary><strong>CF-EXEC-004. What is `ForkJoinPool.commonPool()`, and why does it matter?</strong></summary>

#### Short answer

It is a shared JVM-wide `ForkJoinPool` used by default by several JDK async and parallel APIs.

#### Interview answer

The common pool is designed mainly for CPU-style fork/join work. `CompletableFuture` async methods without a custom executor often use it. Parallel streams also commonly use it.

It matters because blocking or long-running tasks submitted there can reduce capacity for unrelated code.

#### Deep dive

`ForkJoinPool` uses work stealing, which helps fine-grained CPU tasks. It is not a magic solution for blocking database or HTTP calls.

#### Production angle

Avoid using the common pool for backend blocking I/O. A slow downstream should not consume a shared global executor.

#### Traps / caveats

- Common-pool problems can look like random latency across the application.
- Thread names may not identify the business operation.
- Tuning the common pool affects the whole process.

#### Optional Anki

Q: Why is the common pool risky for blocking I/O?
A: It is shared and can be starved by blocked workers.

</details>

<a id="cf-exec-005"></a>

<details>
<summary><strong>CF-EXEC-005. How do you provide a custom `Executor` for `CompletableFuture`?</strong></summary>

#### Short answer

Use overloads that accept an `Executor`.

#### Interview answer

Most async methods have an executor overload:

```java
CompletableFuture.supplyAsync(this::load, ioExecutor)
    .thenApplyAsync(this::map, cpuExecutor);
```

Choose the executor based on workload: CPU work, blocking I/O, database access, remote calls or dedicated bulkhead.

#### Deep dive

Non-async stages do not take an executor and may run in the completing thread. Async stages with an executor create an explicit scheduling boundary.

#### Production angle

Owned executors need named threads, bounded queues, rejection policy, metrics and graceful shutdown.

#### Traps / caveats

- Do not create a new executor per request.
- Do not use the same executor for unrelated critical work.
- Executor overloads do not solve downstream capacity by themselves.

#### Optional Anki

Q: Which overload should production blocking work usually use?
A: The overload that accepts a custom `Executor`.

</details>

<a id="cf-exec-006"></a>

<details>
<summary><strong>CF-EXEC-006. When should you always provide a custom `Executor`?</strong></summary>

#### Short answer

Provide one when work is blocking, expensive, high-volume, business-critical or needs isolation.

#### Interview answer

Use a custom executor for blocking HTTP calls, database work, file I/O, CPU-heavy processing, tenant-specific workloads and anything whose overload behavior matters.

The default common pool is acceptable for small demos and some lightweight CPU tasks, but production backend services usually need explicit ownership.

#### Deep dive

Executor choice is part of the async API contract. It defines where code runs and how overload behaves.

#### Production angle

Separate pools can act as bulkheads: a slow recommendation service should not consume threads needed for payment processing.

#### Traps / caveats

- A custom executor with an unbounded queue can still fail badly.
- Too many pools can waste threads and complicate tuning.
- Missing metrics makes custom pools hard to operate.

#### Optional Anki

Q: What kind of work should not use the common pool casually?
A: Blocking or high-volume backend I/O.

</details>

<a id="cf-exec-007"></a>

<details>
<summary><strong>CF-EXEC-007. Why is the common pool dangerous for blocking I/O?</strong></summary>

#### Short answer

Blocking I/O occupies common-pool workers and can starve unrelated async or parallel work.

#### Interview answer

The common pool has limited workers. If many workers block on HTTP, JDBC or file I/O, fewer workers remain to run other `CompletableFuture` continuations or parallel stream tasks. This can create latency spikes or apparent deadlocks.

Blocking I/O should use a dedicated bounded executor or a true async client.

#### Deep dive

Fork/join work stealing helps when tasks are small and CPU-bound. It cannot make blocked threads useful.

#### Production angle

If thread dumps show `ForkJoinPool.commonPool-worker-*` blocked on sockets or JDBC, move that work to an appropriate executor and add limits.

#### Traps / caveats

- A timeout on the future may not unblock the worker.
- Retrying blocked calls can exhaust the pool faster.
- Parallel streams may be affected by common-pool saturation.

#### Optional Anki

Q: What should you use for blocking calls instead of the common pool?
A: A dedicated bounded executor or a true async client.

</details>

<a id="cf-exec-008"></a>

<details>
<summary><strong>CF-EXEC-008. How do you size an executor for CPU-bound tasks?</strong></summary>

#### Short answer

Size it close to available CPU cores, then validate with measurement.

#### Interview answer

CPU-bound tasks need CPU time, not many waiting threads. A pool near the number of available processors is usually a starting point. Too many threads add context switching and cache pressure without increasing CPU capacity.

The exact size depends on task cost, other workloads and latency goals.

#### Deep dive

If CPU tasks sometimes block, they are not purely CPU-bound and may need a different model.

#### Production angle

Use CPU utilization, run queue, latency, throughput and profiling data to tune. Do not tune by guessing alone.

#### Traps / caveats

- More threads can reduce throughput.
- CPU pools should not share blocking I/O.
- Container CPU limits matter more than host cores.

#### Optional Anki

Q: What is a common starting point for CPU-bound pool size?
A: Around the number of available CPU cores.

</details>

<a id="cf-exec-009"></a>

<details>
<summary><strong>CF-EXEC-009. How do you size an executor for blocking I/O-bound tasks?</strong></summary>

#### Short answer

Base it on expected concurrency, latency, downstream capacity and resource limits, not just CPU cores.

#### Interview answer

Blocking I/O tasks spend time waiting, so they may need more threads than CPU-bound work. But the limit should respect downstream service capacity, HTTP connection pools, JDBC pool size, memory and latency targets.

Little's Law can help: concurrency is roughly throughput times latency.

#### Deep dive

For JDBC, a thread count much larger than the connection pool may just create queued blocked work. For remote calls, downstream rate limits may be the real cap.

#### Production angle

Monitor active threads, queue size, connection pool usage, request latency and timeout rate.

#### Traps / caveats

- Bigger I/O pools can overload dependencies.
- Unbounded queues hide saturation.
- Retry traffic must be included in capacity calculations.

#### Optional Anki

Q: What resource often caps database async work?
A: The database connection pool.

</details>

<a id="cf-exec-010"></a>

<details>
<summary><strong>CF-EXEC-010. What is thread pool starvation?</strong></summary>

#### Short answer

Starvation occurs when tasks cannot get worker threads because existing workers are blocked or occupied.

#### Interview answer

In an executor, starvation means queued tasks cannot run in time. A common cause is all workers blocking on I/O, locks or futures. Another cause is tasks waiting for other tasks submitted to the same saturated pool.

The result is high latency, timeouts and sometimes apparent hangs.

#### Deep dive

Starvation is often a design problem: the pool is doing incompatible work, has an unsafe queue, or tasks depend on work that cannot be scheduled.

#### Production angle

Thread dumps, executor metrics and queue growth are key signals.

#### Traps / caveats

- Starvation can happen even when CPU is low.
- Increasing pool size may only delay the problem.
- Missing timeouts turns starvation into indefinite hangs.

#### Optional Anki

Q: Can a service be thread-starved while CPU is low?
A: Yes, if threads are blocked waiting.

</details>

<a id="cf-exec-011"></a>

<details>
<summary><strong>CF-EXEC-011. How can `CompletableFuture` pipelines cause thread pool starvation?</strong></summary>

#### Short answer

By blocking executor workers, submitting too many tasks, or waiting inside tasks for other tasks in the same pool.

#### Interview answer

Examples include `join()` inside `thenApply`, blocking HTTP calls in the common pool, unbounded `supplyAsync` loops, and a task that submits child tasks to the same small executor and waits for them.

The executor becomes full of tasks that cannot make progress.

#### Deep dive

Async composition should avoid blocking waits. If a task must wait, it should not block the same constrained pool needed to complete the work.

#### Production angle

Look for blocked worker threads, long queues, common-pool workers on sockets and task graphs with circular waits.

#### Traps / caveats

- `thenApplyAsync` can still starve if the executor is saturated.
- Timeouts may fire while tasks are still queued.
- Retrying into a starved pool worsens the outage.

#### Optional Anki

Q: What is a common CompletableFuture starvation anti-pattern?
A: Calling `join()` inside a stage running on the same limited pool.

</details>

<a id="cf-exec-012"></a>

<details>
<summary><strong>CF-EXEC-012. What happens if the executor rejects a `CompletableFuture` task?</strong></summary>

#### Short answer

The async stage usually completes exceptionally with the rejection failure.

#### Interview answer

If an executor cannot accept a task, it may throw `RejectedExecutionException`. For `CompletableFuture` async stages, that rejection generally becomes exceptional completion of the returned stage or is thrown during task submission depending on where it occurs.

The application should treat rejection as overload, not as a random technical error.

#### Deep dive

Rejection policy is part of backpressure. It decides whether work is failed, run by the caller, discarded or handled customly.

#### Production angle

Rejected async work should produce metrics, logs and a clear user-facing failure or load-shedding behavior.

#### Traps / caveats

- `CallerRunsPolicy` can block request threads unexpectedly.
- Silent discard policies are dangerous for business work.
- Retrying rejected work immediately can amplify overload.

#### Optional Anki

Q: What exception commonly represents executor rejection?
A: `RejectedExecutionException`.

</details>

<a id="cf-exec-014"></a>

<details>
<summary><strong>CF-EXEC-014. Why should you shut down custom `ExecutorService` instances?</strong></summary>

#### Short answer

Because executor threads are resources and can keep running after the component should stop.

#### Interview answer

An `ExecutorService` owns threads and queues. If you create one, you must define its lifecycle. Without shutdown, threads can leak, tests can hang, applications may not terminate and Kubernetes shutdown may leave in-flight work unmanaged.

In Spring, prefer managed executor beans when possible.

#### Deep dive

Shutdown should usually stop accepting new tasks, allow in-flight tasks a grace period, then cancel or reject remaining work according to policy.

#### Production angle

Graceful shutdown must align with server shutdown, message consumer stop, request deadlines and database connection cleanup.

#### Traps / caveats

- Do not create an executor per request.
- Daemon threads are not a real lifecycle strategy.
- Forced shutdown can interrupt tasks that are not interruption-safe.

#### Optional Anki

Q: Who should shut down an executor?
A: The component that owns its lifecycle.

</details>

<a id="cf-exec-015"></a>

<details>
<summary><strong>CF-EXEC-015. How do you name threads used by `CompletableFuture` executors?</strong></summary>

#### Short answer

Provide a `ThreadFactory` that assigns meaningful names.

#### Interview answer

When creating an executor, configure a `ThreadFactory` with names like `pricing-io-`, `payment-callback-` or `cf-aggregation-`. Many frameworks and libraries also expose thread name prefix settings.

Thread names should identify the pool and workload, not individual user data.

#### Deep dive

Good names make thread dumps, logs, metrics and profiling easier to interpret.

#### Production angle

During incidents, named async threads quickly show whether a service is blocked in HTTP, DB, CPU mapping or background work.

#### Traps / caveats

- Do not include sensitive request data in thread names.
- Thread names do not replace tracing context.
- Default common-pool names rarely explain business ownership.

#### Optional Anki

Q: Why name executor threads?
A: To make logs, dumps and metrics diagnosable.

</details>

<a id="cf-exec-016"></a>

<details>
<summary><strong>CF-EXEC-016. How do you separate executors for CPU work, database work and remote I/O?</strong></summary>

#### Short answer

Use different executors or concurrency limits for workloads with different capacity and failure behavior.

#### Interview answer

CPU transformations, JDBC calls and remote HTTP calls stress different resources. CPU work is core-limited, database work is connection-pool-limited, and remote I/O is downstream-limited.

Separate executors or bulkheads prevent one slow area from consuming all async capacity.

#### Deep dive

Separation should be coarse enough to operate. Too many tiny pools are difficult to tune, but one pool for everything couples failures.

#### Production angle

Monitor each pool separately: active count, queue size, rejection, latency and failure rate.

#### Traps / caveats

- Separate pools do not remove shared downstream bottlenecks.
- Queueing in one pool can still exceed request deadlines.
- Cross-pool dependencies can still deadlock if blocking waits are used.

#### Optional Anki

Q: Why separate DB and remote I/O executors?
A: They have different resource limits and failure modes.

</details>

<a id="cf-exec-017"></a>

<details>
<summary><strong>CF-EXEC-017. Why can mixing CPU-heavy tasks and blocking I/O in the same pool be harmful?</strong></summary>

#### Short answer

Because blocked I/O workers can starve CPU work, and CPU-heavy work can delay I/O completions.

#### Interview answer

CPU-heavy tasks need steady CPU time. Blocking I/O tasks occupy threads while waiting. In one shared pool, a burst of blocking calls can prevent CPU transformations from running, while CPU-heavy tasks can delay callbacks and increase I/O latency.

Different workloads need different sizing and overload policies.

#### Deep dive

Mixing also makes metrics ambiguous: high queue length does not tell you which workload is responsible.

#### Production angle

Use separate executors or bulkheads for critical classes of work and name them clearly.

#### Traps / caveats

- Simply increasing the pool can overload the host or downstream systems.
- Mixed workloads make incident diagnosis slower.
- Retry tasks should not share the same saturated pool without limits.

#### Optional Anki

Q: Why is one async pool for all work risky?
A: It couples unrelated workloads and failure modes.

</details>

<a id="cf-exec-020"></a>

<details>
<summary><strong>🧠 CF-EXEC-020. How does `ForkJoinPool` work stealing relate to `CompletableFuture`?</strong></summary>

#### Short answer

Default async `CompletableFuture` work may run in a `ForkJoinPool`, whose workers can steal tasks to improve CPU utilization.

#### Interview answer

`ForkJoinPool` is designed for many small tasks that split and join. Workers have queues and can steal work from others when idle. This helps CPU-bound fork/join workloads.

`CompletableFuture` can use the common `ForkJoinPool` for async stages, but work stealing does not make blocking calls safe.

#### Deep dive

Fork/join efficiency depends on tasks being short, non-blocking and decomposable. Long blocking calls defeat the model.

#### Production angle

If common-pool workers are blocked in thread dumps, work stealing will not save the service. Move blocking work elsewhere.

#### Traps / caveats

- Do not treat `ForkJoinPool` as a generic I/O pool.
- Work stealing can make execution order less obvious.
- Parallel streams and `CompletableFuture` may contend for the same common pool.

#### Optional Anki

Q: What workload is `ForkJoinPool` mainly optimized for?
A: Short CPU-bound fork/join-style tasks.

</details>

<a id="cf-exec-022"></a>

<details>
<summary><strong>🧠 CF-EXEC-022. How do async continuations choose their executor?</strong></summary>

#### Short answer

They use the executor you pass; otherwise they use the stage's default async execution facility.

#### Interview answer

For `thenApplyAsync(fn, executor)`, the provided executor runs the continuation. For `thenApplyAsync(fn)` without an executor, the default async executor is used, commonly the common pool for standard `CompletableFuture`.

Non-async methods such as `thenApply` do not schedule through an executor in the same way.

#### Deep dive

Subclasses can influence default executor behavior, but most application code should not rely on subtle defaults.

#### Production angle

Explicit executor parameters are clearer for code review, performance tuning and incident diagnosis.

#### Traps / caveats

- Async does not mean "same executor as the previous stage" unless you pass it.
- Non-async stages may run in completion threads.
- Executor rejection can fail the async stage.

#### Optional Anki

Q: What is the safest way to control where an async continuation runs?
A: Pass an explicit `Executor`.

</details>
