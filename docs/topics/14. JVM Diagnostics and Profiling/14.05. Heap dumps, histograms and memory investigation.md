# 14.05. Heap dumps, histograms and memory investigation

---

<a id="jvmd-heap-001"></a>

<details>
<summary><strong>JVMD-HEAP-001. How do you decide between a heap dump, class histogram and allocation profile?</strong></summary>

#### Short answer

Use a heap dump for retained objects, a histogram for quick class counts, and allocation profiling for object churn over time.

#### Interview answer

If I need to know "what is retaining memory now", I use a heap dump. If I need a fast, lower-detail view, I use a class histogram. If GC pressure is high but retained heap is stable, I use JFR or allocation profiling to find where short-lived objects are created.

The tool depends on retention versus allocation rate.

#### Deep dive

Heap dumps answer ownership questions. Allocation profiles answer creation-rate questions. Histograms are useful for quick comparison but lack reference paths.

#### Production angle

Choose the least disruptive diagnostic that can confirm or reject the hypothesis.

#### Traps / caveats

- Heap dumps can miss short-lived churn.
- Histograms do not show who retains objects.
- Allocation profilers sample and may miss rare allocations.

#### Optional Anki

Q: What tool is best for high allocation rate with stable retained heap?
A: Allocation profiling or JFR allocation events.

</details>

<a id="jvmd-heap-002"></a>

<details>
<summary><strong>JVMD-HEAP-002. How do you safely capture a heap dump in production?</strong></summary>

#### Short answer

Capture it only when justified, preferably from one drained replica, with enough disk, secure storage and expected pause impact understood.

#### Interview answer

Before taking a heap dump, I check service criticality, heap size, disk space, storage path, privacy rules and whether one instance can be removed from traffic. I use approved tooling such as `jcmd <pid> GC.heap_dump <file>` or preconfigured OOME dump flags.

For a large heap or hot service, I may start with a histogram or JFR instead.

#### Deep dive

Heap dump capture can be stop-the-world and the resulting file can be very large.

#### Production angle

The runbook should define where dumps are written, how they are encrypted, who can access them and when they are deleted.

#### Traps / caveats

- Dumping into a container filesystem can fill storage.
- Dumps can contain secrets and PII.
- Capturing during peak traffic can worsen the incident.

#### Optional Anki

Q: What should you check before a production heap dump?
A: Impact, disk, dump size, data sensitivity and traffic draining options.

</details>

<a id="jvmd-heap-003"></a>

<details>
<summary><strong>JVMD-HEAP-003. What risks come with collecting heap dumps from production services?</strong></summary>

#### Short answer

Heap dumps can pause the service, use heavy I/O, fill disk and expose sensitive application data.

#### Interview answer

A heap dump captures live Java heap objects, including request bodies, tokens, credentials, customer data, cached responses and configuration. Capturing it may pause the JVM and write a huge file. If storage is small, it can fail or destabilize the node.

It should be treated as sensitive production data.

#### Deep dive

Even if logs redact secrets, in-memory objects may still contain original values.

#### Production angle

Access control, encryption, retention policy and approved transfer paths are part of heap dump readiness.

#### Traps / caveats

- Do not upload raw dumps to unapproved tools.
- A heap dump may be bigger than expected.
- A normal heap dump does not explain all native memory usage.

#### Optional Anki

Q: Why are heap dumps security-sensitive?
A: They can contain secrets, PII and business data from memory.

</details>

<a id="jvmd-heap-004"></a>

<details>
<summary><strong>JVMD-HEAP-004. How do Eclipse MAT, VisualVM or commercial profilers help analyze heap dumps?</strong></summary>

#### Short answer

They load heap snapshots and help inspect object counts, retained memory, dominators, reference paths and leak suspects.

#### Interview answer

Tools such as Eclipse MAT show which objects retain the most memory and why they are reachable. They provide histograms, dominator trees, retained-size calculations and paths to GC roots. VisualVM and commercial profilers provide similar analysis plus integrated profiling features.

The tool helps, but the engineer still needs domain context.

#### Deep dive

Leak suspect reports are starting points. Large expected caches, queues or data snapshots can look suspicious without being bugs.

#### Production angle

Use heap analysis to find unbounded caches, retained request graphs, `ThreadLocal` values, static collections and classloader leaks.

#### Traps / caveats

- Opening a large dump requires a lot of workstation memory.
- Automated leak suspects can be false positives.
- Retained memory must be interpreted against expected behavior.

#### Optional Anki

Q: What heap analysis view helps find memory owners?
A: The dominator tree.

</details>

<a id="jvmd-heap-005"></a>

<details>
<summary><strong>JVMD-HEAP-005. What are retained size, shallow size, dominator tree and path to GC roots?</strong></summary>

#### Short answer

Shallow size is one object's own memory; retained size is memory freed if it became unreachable; dominators and GC-root paths explain ownership.

#### Interview answer

Shallow size is the memory of an object itself. Retained size includes the objects that would become collectible if this object were removed. A dominator tree groups objects by retention ownership. Path to GC roots shows why an object is still reachable from roots such as threads, static fields or JNI references.

These concepts are central to leak analysis.

#### Deep dive

A small object can retain a huge graph, for example a cache object retaining millions of entries.

#### Production angle

Focus on retained size and ownership, not just class count.

#### Traps / caveats

- The biggest object count may not be the biggest retained graph.
- GC-root paths can be expensive to compute.
- Roots can be legitimate, such as configured caches.

#### Optional Anki

Q: What does retained size estimate?
A: Memory that would be freed if an object became unreachable.

</details>

<a id="jvmd-heap-006"></a>

<details>
<summary><strong>JVMD-HEAP-006. How can `ThreadLocal`, classloader leaks and unbounded caches appear in a heap dump?</strong></summary>

#### Short answer

They appear as retained object graphs reachable from thread locals, old classloaders, static fields, maps, queues or cache structures.

#### Interview answer

`ThreadLocal` leaks often show values retained by long-lived pool threads. Classloader leaks show old application classloaders retained by statics, threads, drivers, logging, proxies or listeners. Unbounded caches show large maps or cache internals retaining values with high key cardinality.

The key is finding the retaining path, not only the object type.

#### Deep dive

Thread pools make leaks worse because worker threads live much longer than individual requests.

#### Production angle

Fixes usually include cleanup in `finally`, bounded caches, listener deregistration, proper shutdown and avoiding statics that retain application objects.

#### Traps / caveats

- A large cache is not automatically a leak if bounded and expected.
- `ThreadLocal.remove()` must happen reliably.
- Classloader leaks often show up after repeated redeployments.

#### Optional Anki

Q: What commonly retains `ThreadLocal` leaks?
A: Long-lived worker threads.

</details>

<a id="jvmd-heap-007"></a>

<details>
<summary><strong>JVMD-HEAP-007. Why can comparing histograms or heap dumps over time be more useful than one snapshot?</strong></summary>

#### Short answer

Comparison reveals growth trends and separates normal peak load from true retention leaks.

#### Interview answer

One dump shows memory at one point. Two or more snapshots, ideally after similar GC points or workload phases, show what grows. If the same owner retains more objects after each interval, that supports a leak hypothesis.

Histograms are lighter and useful for repeated comparisons.

#### Deep dive

For leaks, trend matters more than a single large object graph. Traffic, batch jobs and cache warmup can create legitimate growth.

#### Production angle

Compare memory artifacts with traffic, cache metrics, queue depth and deployment timeline.

#### Traps / caveats

- Snapshots under different load can mislead.
- GC timing affects what is visible.
- Growth in heap used is not always a leak.

#### Optional Anki

Q: Why compare heap evidence over time?
A: To identify growing retained object graphs.

</details>

<a id="jvmd-heap-008"></a>

<details>
<summary><strong>JVMD-HEAP-008. How do you distinguish high allocation rate from a retained-memory leak?</strong></summary>

#### Short answer

High allocation rate creates many short-lived objects; a retained-memory leak leaves live objects growing after GC.

#### Interview answer

If allocation rate is high but live heap returns to a stable baseline after GC, the issue is object churn and GC pressure. I would use JFR or allocation profiling. If old generation or retained heap grows after collections and dumps show retained owners, it suggests a leak or unbounded live set.

The fixes are different.

#### Deep dive

Object churn is often caused by serialization, mapping, logging, regex, temporary collections or large DTO transformations.

#### Production angle

A churn problem may need code-path optimization; a retained leak needs ownership cleanup, bounds or lifecycle fixes.

#### Traps / caveats

- Heap dumps can miss short-lived churn.
- Allocation profiles do not prove retention.
- Cache warmup can look like a leak until it reaches a bound.

#### Optional Anki

Q: What tool helps find short-lived allocation churn?
A: JFR allocation events or allocation profiling.

</details>
