# 14.08. GC logs, safepoints, JIT and runtime behavior

---

<a id="jvmd-run-001"></a>

<details>
<summary><strong>JVMD-RUN-001. What JVM evidence would you collect for GC-related latency?</strong></summary>

#### Short answer

Collect GC logs, pause metrics, heap trends, allocation rate, live set, promotion behavior, JFR events and latency correlation.

#### Interview answer

For GC-related latency, I inspect GC logs, pause duration distribution, pause causes, heap before/after collections, old-gen trend, allocation and promotion rate, Full GC frequency, safepoint timing and request latency around the same timestamps.

JFR can add allocation and thread context.

#### Deep dive

The key question is whether latency comes from stop-the-world pauses, allocation stalls, CPU pressure, high live set, humongous allocations or unrelated dependency waits.

#### Production angle

GC evidence should be correlated with p99 latency and deployment or traffic changes before changing collector or heap size.

#### Traps / caveats

- GC logs alone may not show allocation source.
- Bigger heap is not always better.
- GC pause metrics may not include all safepoint impact.

#### Optional Anki

Q: What should GC pauses be correlated with?
A: Request latency and incident timeline.

</details>

<a id="jvmd-run-002"></a>

<details>
<summary><strong>JVMD-RUN-002. How do you enable and read unified GC logging in modern Java?</strong></summary>

#### Short answer

Use `-Xlog` options for GC logging and read pause causes, durations, heap before/after, phases and timestamps.

#### Interview answer

Modern HotSpot uses unified logging, commonly through options like `-Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20M` for rotated logs. When reading logs, I look for collection type, pause duration, heap occupancy before/after, old-gen trend, allocation pressure, humongous objects, Full GC, concurrent cycle behavior and safepoint-related messages if enabled.

#### Deep dive

GC logs are much more useful when enabled before incidents with rotation and persistent storage.

#### Production angle

Do not enable verbose logs into ephemeral storage without rotation; log volume can become an operational issue.

#### Traps / caveats

- Old Java versions used different GC logging flags.
- Logs without timestamps are hard to correlate.
- Collector-specific terms need collector context.

#### Optional Anki

Q: What modern JVM option family controls GC logging?
A: `-Xlog`.

</details>

<a id="jvmd-run-003"></a>

<details>
<summary><strong>JVMD-RUN-003. How do you correlate GC pauses and safepoints with request latency?</strong></summary>

#### Short answer

Align timestamps from GC/JVM logs or JFR with request latency, traces, traffic and deployment markers.

#### Interview answer

I compare pause start/end times and durations with p95/p99 latency, error spikes, trace spans and traffic. If latency spikes line up with GC or safepoint pauses across the same instance, that supports a JVM pause hypothesis. If traces show dependency waiting outside the pause window, the cause may be elsewhere.

Instance-level correlation matters.

#### Deep dive

Cluster-wide latency can hide one bad pod. Per-instance metrics and logs are important.

#### Production angle

Dashboards should show GC pause distribution and request latency on the same timeline.

#### Traps / caveats

- Clock skew can break correlation.
- A GC pause may be a consequence of traffic surge, not root cause.
- Some latency comes from queueing before request instrumentation starts.

#### Optional Anki

Q: Why use per-instance correlation for GC latency?
A: One JVM can cause local spikes hidden in aggregate metrics.

</details>

<a id="jvmd-run-004"></a>

<details>
<summary><strong>JVMD-RUN-004. What are safepoints, and how can JFR or JVM logs help detect long safepoint pauses?</strong></summary>

#### Short answer

Safepoints are moments when JVM threads reach a state where the VM can perform coordinated operations; long safepoints can affect latency.

#### Interview answer

The JVM uses safepoints for operations such as some GC phases, deoptimization, code cache maintenance, class redefinition or other VM runtime operations. If threads take too long to reach a safepoint or the safepoint operation itself is long, application progress can pause.

JFR and JVM logging can show safepoint events, durations and causes.

#### Deep dive

Time to safepoint and time spent at safepoint are different. Both can matter for tail latency.

#### Production angle

If p99 latency spikes do not match normal GC pause metrics, inspect safepoint evidence.

#### Traps / caveats

- Not every latency spike is GC.
- Safepoint details depend on logging/JFR configuration.
- Some safepoint causes are JVM-version-specific.

#### Optional Anki

Q: What are the two useful safepoint timings?
A: Time to reach safepoint and time spent at safepoint.

</details>

<details>
<summary><strong>JVMD-RUN-005. How can JVM warmup and JIT compilation affect performance measurements?</strong></summary>

#### Short answer

Startup code may run interpreted or less optimized until profiling and JIT compilation produce optimized machine code.

#### Interview answer

After deployment, the JVM loads classes, initializes frameworks, fills caches and compiles hot methods. Early requests can be slower because code has not warmed up, JIT compilation consumes CPU, caches are cold or the service is still connecting to dependencies.

Performance measurements must separate warmup from steady state.

#### Deep dive

JIT decisions depend on observed execution profiles. A benchmark or load test that stops too early may measure startup behavior, not real steady-state performance.

#### Production angle

Readiness checks, warmup traffic, rollout strategy and autoscaling should account for startup and warmup behavior.

#### Traps / caveats

- First-minute slowness is not always a code regression.
- Warmup can hide later steady-state bottlenecks too.
- Profiles during warmup may overemphasize initialization code.

#### Optional Anki

Q: Why can a Java service be slow just after deployment?
A: Class loading, cold caches, JIT warmup and dependency initialization.

</details>

<a id="jvmd-run-006"></a>

<details>
<summary><strong>🧠 JVMD-RUN-006. How can Code Cache, deoptimization, tiered compilation and inlining affect profile interpretation?</strong></summary>

#### Short answer

JIT/runtime behavior can change which code is optimized, how stacks look and whether performance is stable.

#### Interview answer

The Code Cache stores compiled methods; if constrained or full, compilation can be disabled or limited. Tiered compilation means code can move through different optimization levels. Deoptimization can discard compiled assumptions and fall back to less optimized execution. Inlining can make stack traces and self/total time look different from source-level method boundaries.

These are advanced signals, but they matter for performance-heavy systems.

#### Deep dive

A profile is a view of the optimized runtime, not a simple source-code execution tree.

#### Production angle

Investigate these only after simpler causes are ruled out or when JFR/logs point to compiler/runtime behavior.

#### Traps / caveats

- Do not start tuning JIT flags casually.
- Inlined methods may not appear as expected.
- Compiler activity during warmup can be normal.

#### Optional Anki

Q: Why can source method boundaries differ from profile frames?
A: JIT inlining and optimization change runtime representation.

</details>

<details>
<summary><strong>🧠 JVMD-RUN-007. Why are JVM microbenchmarks unreliable without JMH, warmup and isolation?</strong></summary>

#### Short answer

Naive microbenchmarks are distorted by JIT warmup, dead-code elimination, constant folding, GC, CPU noise and unrealistic workloads.

#### Interview answer

The JVM aggressively optimizes code based on runtime profiles. A simple loop benchmark can measure interpreted code, optimized code, eliminated work, allocation effects or CPU noise rather than the operation being tested. JMH handles warmup, forks, measurement iterations, blackholes and isolation patterns.

For JVM code, benchmark design is part of the result.

#### Deep dive

Even JMH results must be tied back to production behavior. A faster microbenchmark may not improve request latency.

#### Production angle

Use JMH for small code decisions, then validate important changes with production-like load and real telemetry.

#### Traps / caveats

- `System.nanoTime()` loops are often wrong.
- Benchmarks without warmup measure startup.
- Microbenchmarks can optimize irrelevant hot paths.

#### Optional Anki

Q: What Java tool is designed for reliable microbenchmarks?
A: JMH.

</details>
