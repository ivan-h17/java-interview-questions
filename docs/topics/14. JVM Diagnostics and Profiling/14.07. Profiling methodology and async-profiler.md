# 14.07. Profiling methodology and async-profiler

---

<a id="jvmd-prof-001"></a>

<details>
<summary><strong>JVMD-PROF-001. What is profiling, and how is it different from monitoring?</strong></summary>

#### Short answer

Monitoring tracks ongoing health signals; profiling investigates where time, CPU, allocation or contention is spent.

#### Interview answer

Monitoring answers "is the service healthy?" with metrics such as latency, errors, CPU, memory and pool usage. Profiling answers "where is the cost coming from?" by sampling or instrumenting code paths, allocations, locks or wall-clock waits.

Monitoring tells you when to investigate. Profiling helps explain why.

#### Deep dive

Profiling is usually temporary and targeted, while monitoring should be continuous and cheap.

#### Production angle

Use monitoring to select the time window and hypothesis before profiling; otherwise profiles can be expensive noise.

#### Traps / caveats

- Profiling without a symptom can optimize irrelevant code.
- Monitoring averages can hide tail latency.
- Profiling results need realistic workload.

#### Optional Anki

Q: What does profiling answer?
A: Where runtime cost is spent.

</details>

<a id="jvmd-prof-002"></a>

<details>
<summary><strong>JVMD-PROF-002. How do sampling and instrumentation profilers differ, and how can profilers distort results?</strong></summary>

#### Short answer

Sampling periodically observes execution; instrumentation inserts measurement code. Both can add overhead or bias.

#### Interview answer

Sampling profilers take periodic samples of stacks or events and estimate where time is spent. They usually have lower overhead but can miss short or rare work. Instrumentation profilers add code around methods or events, giving precise counts or durations but often with higher overhead and behavior changes.

Any profiler can distort timing, inlining, allocation, locking or workload shape.

#### Deep dive

The profiler must be chosen for the question: CPU, wall time, allocation, lock contention or method tracing.

#### Production angle

Use the lowest-overhead mode that answers the question and validate findings with metrics after the change.

#### Traps / caveats

- Instrumentation can change method inlining and timing.
- Sampling can miss rare but important paths.
- Profiling staging data may not match production traffic.

#### Optional Anki

Q: What is the main trade-off between sampling and instrumentation?
A: Lower overhead estimates versus more intrusive precise measurement.

</details>

<a id="jvmd-prof-003"></a>

<details>
<summary><strong>JVMD-PROF-003. What is a flame graph, and how do you read it?</strong></summary>

#### Short answer

A flame graph visualizes sampled stack traces; width shows how often a stack frame appears, not how slow one call is.

#### Interview answer

In a flame graph, each box is a stack frame. Wider boxes mean more samples included that frame. Parent frames call child frames above them. Hot areas are wide stacks, especially where self time is high or where a broad path dominates total time.

For CPU profiles, width usually means CPU sample frequency; for allocation profiles, allocation sample weight.

#### Deep dive

The x-axis order is not a timeline. It is usually sorted/grouped stack data.

#### Production angle

Flame graphs are useful for communicating hotspots and verifying that a proposed optimization targets meaningful work.

#### Traps / caveats

- Width is not wall-clock duration unless the profile mode measures wall time.
- A wide parent can be wide because of children.
- Missing native frames can hide important work.

#### Optional Anki

Q: What does width represent in a flame graph?
A: Sample weight or frequency for that frame/stack.

</details>

<a id="jvmd-prof-004"></a>

<details>
<summary><strong>JVMD-PROF-004. What is the difference between CPU-time and wall-clock profiling?</strong></summary>

#### Short answer

CPU-time profiling shows where threads spend CPU; wall-clock profiling shows elapsed time including waiting, blocking and sleeping.

#### Interview answer

CPU profiling is good for hot computation, busy loops, serialization, parsing and algorithmic cost. Wall-clock profiling is better when latency is caused by waiting: locks, I/O, sleeps, parking, connection pools or downstream calls.

For backend latency, wall-clock evidence can be more useful than CPU alone.

#### Deep dive

A request can be slow with little CPU usage if most time is spent waiting for a database, socket, lock or queue.

#### Production angle

Choose profile mode based on the symptom: high CPU suggests CPU profiling; high latency with low CPU suggests wall-clock or JFR wait events.

#### Traps / caveats

- CPU profiles can miss off-CPU latency.
- Wall-clock profiles can include idle or expected waiting.
- Thread state and stack context are needed for interpretation.

#### Optional Anki

Q: Which profiling mode helps when CPU is low but latency is high?
A: Wall-clock or off-CPU style profiling.

</details>

<a id="jvmd-prof-005"></a>

<details>
<summary><strong>JVMD-PROF-005. How would you profile CPU hotspots, allocation pressure or lock contention in a Java service?</strong></summary>

#### Short answer

Pick the profiler mode that matches the symptom: CPU profiling for hot code, allocation profiling for churn, lock/JFR events for contention.

#### Interview answer

For CPU hotspots, I capture a CPU profile during representative load and inspect flame graphs. For allocation pressure, I use JFR allocation events or allocation profiling to find methods creating many objects. For lock contention, I inspect JFR monitor events, thread dumps and lock profiling.

I compare before and after changes under similar load.

#### Deep dive

The profile must cover the bad window. Profiling an idle or warmup phase can lead to wrong conclusions.

#### Production angle

Bound profile duration, label artifacts with version and traffic window, and avoid broad high-overhead profiling during peak impact.

#### Traps / caveats

- CPU and allocation hotspots are not always the same methods.
- Lock contention may be caused by slow work inside a critical section.
- Profiles from synthetic load can miss real tenant or payload patterns.

#### Optional Anki

Q: What tool type finds short-lived object churn?
A: Allocation profiling.

</details>

<a id="jvmd-prof-006"></a>

<details>
<summary><strong>JVMD-PROF-006. Why is it useful when a profiler shows Java, native and kernel frames together?</strong></summary>

#### Short answer

It shows whether time is spent in application code, JVM runtime, native libraries or the operating system.

#### Interview answer

Java-only profiles can hide work in compression, TLS, system calls, memory allocation, kernel networking, file I/O, JNI, GC or JVM compiler/runtime code. Seeing Java, native and kernel frames together helps avoid blaming the wrong layer.

This is especially useful for high CPU, native memory and I/O-heavy services.

#### Deep dive

Native frames can reveal costs from libraries that Java stacks show only as a single wrapper method.

#### Production angle

Layer-aware profiles improve escalation: application fix, JVM tuning, library update, container change or OS/platform investigation.

#### Traps / caveats

- Native symbols may be missing or hard to resolve.
- Kernel frames require platform permissions and tooling.
- JVM/runtime frames need careful interpretation.

#### Optional Anki

Q: Why are native frames useful in Java profiling?
A: They reveal work hidden below Java method stacks.

</details>

<a id="jvmd-prof-007"></a>

<details>
<summary><strong>JVMD-PROF-007. How do self time and total time differ in profiler output?</strong></summary>

#### Short answer

Self time is time spent directly in a frame; total time includes time spent in that frame and its callees.

#### Interview answer

If a method has high total time but low self time, it is mostly expensive because of what it calls. If it has high self time, the method's own work is expensive. Both are useful: total time identifies important paths, self time identifies direct hotspots.

Misreading them leads to optimizing wrapper methods instead of the real work.

#### Deep dive

In allocation profiles, the same idea applies to allocation weight: a caller may be responsible for a subtree even if allocation happens in constructors or libraries.

#### Production angle

Use self and total time together to decide whether to optimize a method, a dependency, an algorithm or a call pattern.

#### Traps / caveats

- A high-total controller may just call a slow service or database client.
- Inlining can change how frames appear.
- Async boundaries can split logical work across stacks.

#### Optional Anki

Q: What does high self time suggest?
A: The frame itself is doing expensive work.

</details>

<a id="jvmd-prof-008"></a>

<details>
<summary><strong>JVMD-PROF-008. What mistakes commonly make profiling results misleading?</strong></summary>

#### Short answer

Wrong workload, short duration, warmup effects, missing symbols, wrong profile mode, sampling bias and ignoring external waits can mislead.

#### Interview answer

Common mistakes are profiling a non-representative workload, profiling during startup/warmup, using CPU profiling for a waiting problem, running too briefly, ignoring GC/deployment/traffic context, using high-overhead instrumentation in production, and over-interpreting one flame graph.

Profiles answer a specific question under specific conditions.

#### Deep dive

A profile taken after a cache warms may differ from one taken during cold startup or a tenant-specific spike.

#### Production angle

Always record time window, version, traffic, instance, profile mode and settings with the artifact.

#### Traps / caveats

- The widest frame is not always the easiest or best optimization.
- Removing a hotspot may expose another bottleneck.
- Profiles do not replace correctness tests.

#### Optional Anki

Q: What must a useful production profile include besides the file?
A: Workload, time window, version, instance and profiler settings.

</details>

<details>
<summary><strong>🧠 JVMD-PROF-009. How does async-profiler reduce common Java profiling bias?</strong></summary>

#### Short answer

Async-profiler uses JVM and OS-level sampling mechanisms to reduce safepoint bias and capture Java plus native stacks.

#### Interview answer

Some profilers only observe threads at JVM safepoints, which can under-sample hot code that rarely reaches safepoints. Async-profiler is designed to sample running Java code with less safepoint bias and can include native/kernel frames depending on platform and mode.

It supports CPU, allocation, lock and wall-clock style investigations.

#### Deep dive

It is still a profiler, so settings, platform support, permissions and workload quality matter.

#### Production angle

Async-profiler is useful for targeted low-overhead investigation when JFR or ordinary dumps are not enough.

#### Traps / caveats

- It may require platform-specific permissions.
- Missing debug symbols can limit native interpretation.
- Sampling is not exact tracing.

#### Optional Anki

Q: What profiling bias is async-profiler known for reducing?
A: Safepoint bias.

</details>

<details>
<summary><strong>🧠 JVMD-PROF-010. When would you use `perf`, eBPF or another OS profiler together with JVM tools?</strong></summary>

#### Short answer

Use OS profilers when you suspect kernel, native library, system-call, scheduler, network, disk or allocator behavior beyond Java-only visibility.

#### Interview answer

If JVM tools show time in native or kernel frames, or if RSS, syscalls, networking, disk I/O or scheduler behavior looks suspicious, OS profilers can add missing context. They can help explain TLS/compression cost, kernel networking, filesystem stalls, allocator behavior, page faults or native library CPU.

They complement JFR, thread dumps and heap evidence.

#### Deep dive

For JVM stacks, OS profilers may need frame pointers, symbols or JVM-specific stack support to produce useful mixed stacks.

#### Production angle

OS profiling often requires elevated permissions, so it should be part of approved platform diagnostics, not improvised during an outage.

#### Traps / caveats

- OS profiles can be hard to map back to Java code.
- Permissions and security policy may block them.
- Kernel/native hotspots may be symptoms of application behavior.

#### Optional Anki

Q: When are OS profilers useful for Java?
A: When JVM tools point below Java into native or kernel behavior.

</details>
