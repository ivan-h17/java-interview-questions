# 14.01. Diagnostic mindset and production safety

---

<a id="jvmd-fund-001"></a>

<details>
<summary><strong>JVMD-FUND-001. How do you approach diagnosing a production JVM issue?</strong></summary>

#### Short answer

Start from impact and symptoms, collect evidence, form a hypothesis, choose the least risky diagnostic, then mitigate or fix based on what the evidence shows.

#### Interview answer

I first clarify user impact: latency, errors, throughput, crashes or resource exhaustion. Then I build a timeline around deployment, traffic, dependency and infrastructure changes. I compare JVM metrics with logs, traces, OS/container metrics and application metrics.

Only after that do I choose tools: thread dumps for blocking or CPU stacks, JFR for timeline and runtime events, heap dumps or histograms for retained heap, GC logs for pauses, and NMT or OS tools for native memory.

#### Deep dive

Good JVM diagnostics is not "run every tool". It is hypothesis-driven. For example, high CPU, low CPU with hung requests, growing RSS and growing heap all require different evidence.

#### Production angle

During an incident, the first goal is restoring service safely. Diagnostics should not make the outage worse.

#### Traps / caveats

- Starting with random JVM flags can hide the real cause.
- One snapshot rarely proves a trend.
- JVM symptoms can be caused by downstream systems, container limits or bad traffic.

#### Optional Anki

Q: What should JVM diagnostics start from?
A: User impact, symptoms, timeline and evidence.

</details>

<details>
<summary><strong>JVMD-FUND-002. What evidence would you collect before changing JVM flags or application code?</strong></summary>

#### Short answer

Collect symptoms, timelines, JVM metrics, GC evidence, thread or JFR data, OS/container metrics, logs, traces and recent change history.

#### Interview answer

Before changing anything, I want a baseline: Java version, command line, JVM flags, heap sizing, container limits, CPU and memory metrics, GC logs or pause metrics, request latency, throughput, error rate, dependency latency and recent deployments.

If the problem is active, I would capture low-risk diagnostics such as several thread dumps, a short JFR recording, class histogram or relevant logs before restarting.

#### Deep dive

The goal is to make the next action falsifiable. If someone proposes "increase heap", evidence should show whether the issue is heap pressure, live set growth, allocation rate or native memory.

#### Production angle

Evidence collected before a restart is often the only way to diagnose rare incidents after service is restored.

#### Traps / caveats

- Changing JVM flags without baseline evidence can create a second problem.
- Heap size is not the whole process memory budget.
- Averages can hide p99 latency or short spikes.

#### Optional Anki

Q: What should you collect before tuning the JVM?
A: Baseline runtime, JVM, OS/container, telemetry and change evidence.

</details>

<a id="jvmd-fund-003"></a>

<details>
<summary><strong>JVMD-FUND-003. How do you distinguish CPU, memory, lock, I/O and downstream dependency problems?</strong></summary>

#### Short answer

Compare resource metrics with stack evidence and request telemetry: CPU profiles, memory trends, thread states, JFR events, dependency traces and OS/container signals.

#### Interview answer

High CPU usually needs CPU profiles or high-CPU thread stack mapping. Memory issues need heap trends, GC behavior, dumps, histograms or native memory evidence. Lock issues show blocked threads, monitor events or lock profiling. I/O and downstream problems often show waiting threads, socket/file events, pool waits and traces pointing outside the service.

The same symptom, like high p99 latency, can come from any of these.

#### Deep dive

Thread state alone is not enough. `RUNNABLE` can mean executing Java code, blocked in native I/O, or waiting in kernel code depending on the stack and platform.

#### Production angle

Correct classification avoids bad fixes, such as adding threads when the database pool or downstream service is the real bottleneck.

#### Traps / caveats

- CPU high does not always mean useful work is happening.
- Low CPU with high latency often suggests waiting, queueing or external dependencies.
- Heap dumps do not explain native memory growth.

#### Optional Anki

Q: What evidence separates CPU work from waiting?
A: CPU metrics plus stack/profile/JFR evidence.

</details>

<a id="jvmd-fund-004"></a>

<details>
<summary><strong>JVMD-FUND-004. How do you correlate JVM evidence with logs, metrics, traces and deployment events?</strong></summary>

#### Short answer

Align timestamps and versions, then compare JVM events with request latency, errors, dependency calls, traffic, deploy markers and infrastructure changes.

#### Interview answer

I put JVM evidence on the same timeline as service telemetry. For example, I compare GC pauses, safepoints, CPU spikes, thread pool saturation, JFR socket reads and allocation spikes with p95/p99 latency, error rates, trace spans, log bursts, deployment time and traffic changes.

The strongest diagnosis is usually a correlation across multiple independent signals.

#### Deep dive

Use the same timezone and clock source where possible. A few minutes of skew can make a deployment, GC event or dependency outage look unrelated.

#### Production angle

Correlation helps decide whether to roll back, scale, shed load, tune resource limits or inspect a dependency.

#### Traps / caveats

- Correlation is not proof, but it narrows the search.
- Missing deploy markers make incidents harder to explain.
- Sampling in traces or profilers can hide rare slow paths.

#### Optional Anki

Q: Why align JVM data with deployment events?
A: Recent changes often explain new JVM behavior.

</details>

<a id="jvmd-fund-005"></a>

<details>
<summary><strong>JVMD-FUND-005. How do you decide whether to mitigate first or continue profiling?</strong></summary>

#### Short answer

Mitigate first when user impact is high or the system is unstable; continue profiling when risk is controlled and evidence is needed for a safe fix.

#### Interview answer

If users are heavily affected, error rate is rising, memory is near limit, or the service may crash, I prefer mitigation: rollback, scale out, disable a feature, shed load, increase limits temporarily or restart one replica after preserving evidence.

If the blast radius is small and the service is stable enough, I collect more targeted data before making changes.

#### Deep dive

Mitigation and diagnosis can run in parallel. For example, one instance can be removed from traffic for diagnostics while other replicas carry traffic.

#### Production angle

The right answer depends on impact, redundancy, business risk, available evidence and how disruptive the diagnostic action is.

#### Traps / caveats

- Restarting all replicas can erase the only useful evidence.
- Profiling a collapsing service can worsen impact.
- Temporary mitigations still need follow-up root cause analysis.

#### Optional Anki

Q: When should mitigation beat deeper profiling?
A: When user impact or instability is high.

</details>

<a id="jvmd-fund-006"></a>

<details>
<summary><strong>JVMD-FUND-006. What safe first diagnostics can usually be collected during a JVM incident?</strong></summary>

#### Short answer

Start with low-risk telemetry, logs, thread dumps, short JFR recordings, JVM command line, GC logs and OS/container metrics.

#### Interview answer

Safe first steps usually include service metrics, logs, traces, pod or host status, Java version and command line, JVM flags, GC logs, several thread dumps, a short JFR if enabled or attach is allowed, and OS/container CPU, memory, file descriptor and thread counts.

A class histogram may also be acceptable, but heap dumps require more caution.

#### Deep dive

The least risky diagnostic is the one that answers the current hypothesis with enough precision. For a hang, thread dumps may be better than a heap dump. For allocation churn, JFR may be better than a heap snapshot.

#### Production angle

Runbooks should define which commands are approved, where outputs go and who may access sensitive files.

#### Traps / caveats

- "Safe" depends on service size, load and JVM settings.
- Attach may be blocked in containers.
- Even low-overhead recordings need storage and privacy controls.

#### Optional Anki

Q: What is a common first diagnostic for a hung JVM service?
A: Several thread dumps over time.

</details>

<a id="jvmd-fund-007"></a>

<details>
<summary><strong>JVMD-FUND-007. What risks can diagnostic commands introduce in production?</strong></summary>

#### Short answer

Diagnostics can pause the JVM, increase CPU or I/O, fill disk, expose sensitive data, change timing or fail because of permissions and containers.

#### Interview answer

Thread dumps are usually low risk but can still create noise on huge thread counts. Heap dumps can pause the JVM, consume disk and expose secrets. JFR overhead depends on settings. Class histograms and GC-root analysis can pause. Native or OS profilers may require elevated permissions and can affect performance.

Diagnostics are production actions and need risk assessment.

#### Deep dive

Some commands are mostly observational, while others trigger expensive VM operations. The operational question is whether the expected value justifies the disruption.

#### Production angle

Prefer one replica, short recordings, approved storage locations and least-privilege access.

#### Traps / caveats

- Heap dumps can be as sensitive as database snapshots.
- Dumping to container ephemeral storage can cause another failure.
- Running a profiler without understanding mode and duration can distort results.

#### Optional Anki

Q: Name two production risks of JVM diagnostics.
A: Service disruption and sensitive data exposure.

</details>

<a id="jvmd-fund-008"></a>

<details>
<summary><strong>JVMD-FUND-008. How do you preserve useful JVM evidence before restarting a service?</strong></summary>

#### Short answer

Capture volatile evidence first: logs, metrics window, thread dumps, JFR, GC logs, JVM flags, heap or histogram if safe, and container exit context.

#### Interview answer

Before restart, I preserve what will disappear: current thread stacks, JFR ring buffer or recording, recent logs, GC log tail, JVM command line and flags, heap histogram or dump if appropriate, OS/container status, pod events and restart reason.

If the service is crashing, preconfigured dumps and logs are better than manual steps.

#### Deep dive

After restart, symptoms may vanish and memory, thread and JIT state reset. You may only have generic alerts unless diagnostic artifacts were captured.

#### Production angle

Automate evidence collection for recurring incident classes, especially OOME, crashes, high CPU and stuck request patterns.

#### Traps / caveats

- Restarting can be the right mitigation, but it should be deliberate.
- Automatic dumps need enough disk and secure storage.
- Evidence without timestamps and version data is much less useful.

#### Optional Anki

Q: Why capture evidence before restart?
A: Restart clears volatile JVM state needed for root cause analysis.

</details>
