# 14.09. Native memory, containers and Kubernetes diagnostics

---

<a id="jvmd-native-001"></a>

<details>
<summary><strong>JVMD-NATIVE-001. Why can process RSS grow while Java heap usage stays stable?</strong></summary>

#### Short answer

RSS includes heap plus native/off-heap memory, thread stacks, Metaspace, Code Cache, GC structures, memory maps and native allocator behavior.

#### Interview answer

Stable heap means managed Java heap is not growing, but the process may still consume more resident memory. Direct buffers, Netty pools, Metaspace, thread stacks, Code Cache, native libraries, memory-mapped files, JNI and allocator arenas can increase RSS.

In containers, RSS/cgroup memory can kill the process even when heap looks healthy.

#### Deep dive

Heap dumps only show Java heap objects. They may show wrappers for native memory, but not all native allocations.

#### Production angle

For RSS growth with stable heap, collect NMT, direct memory metrics, thread count, container memory, memory maps and library-specific metrics.

#### Traps / caveats

- Do not conclude "no leak" from stable heap alone.
- `-Xmx` is not the pod memory requirement.
- Native memory may not produce a Java heap OOME.

#### Optional Anki

Q: What should you investigate when RSS grows but heap is stable?
A: Native/off-heap memory and OS/container evidence.

</details>

<a id="jvmd-native-002"></a>

<details>
<summary><strong>JVMD-NATIVE-002. Which important JVM memory areas live outside the Java heap?</strong></summary>

#### Short answer

Metaspace, Code Cache, thread stacks, direct buffers, GC structures, JNI/native allocations and memory-mapped regions live outside the Java heap.

#### Interview answer

Important non-heap areas include Metaspace for class metadata, compressed class space, Code Cache for compiled code, thread stacks, direct buffers, memory-mapped files, GC/native runtime structures, compiler memory, JNI libraries and third-party native allocations.

These areas explain why process memory exceeds heap usage.

#### Deep dive

Some areas are controlled by JVM flags, some by libraries, and some by OS or allocator behavior.

#### Production angle

Container memory budgets must leave headroom beyond `-Xmx` for non-heap memory.

#### Traps / caveats

- `MaxDirectMemorySize` does not cover every native allocation.
- Thread count can be a memory problem.
- Metaspace growth can indicate classloader leaks.

#### Optional Anki

Q: Name three non-heap JVM memory areas.
A: Metaspace, Code Cache and thread stacks.

</details>

<a id="jvmd-native-003"></a>

<details>
<summary><strong>JVMD-NATIVE-003. What is Native Memory Tracking?</strong></summary>

#### Short answer

Native Memory Tracking is a HotSpot feature that categorizes JVM native memory reservations and commitments.

#### Interview answer

NMT helps explain where native memory is used by categories such as Java Heap reservation, Class, Thread, Code, GC, Compiler, Internal and other areas. It is useful when process memory is larger than heap or grows while heap stays stable.

It usually needs to be enabled at startup with summary or detail mode.

#### Deep dive

NMT can take baselines and show diffs, which is useful for growth investigations.

#### Production angle

Consider enabling NMT summary for services where native memory incidents are costly, after measuring overhead.

#### Traps / caveats

- NMT is not always enabled after the fact.
- Detail mode has more overhead than summary.
- NMT does not perfectly explain every third-party native allocation.

#### Optional Anki

Q: What does NMT help diagnose?
A: JVM native memory usage outside the Java heap.

</details>

<a id="jvmd-native-004"></a>

<details>
<summary><strong>JVMD-NATIVE-004. What is the difference between reserved and committed memory in NMT output?</strong></summary>

#### Short answer

Reserved memory is address space set aside; committed memory is memory the process has committed for use.

#### Interview answer

The JVM may reserve a large address range without physically using it. Committed memory is closer to memory the process has asked the OS to back. RSS is different again: it is memory currently resident in RAM.

NMT output must be read with these distinctions in mind.

#### Deep dive

Large reserved regions are normal for some JVM areas. The more urgent signal is often committed growth or RSS growth.

#### Production angle

Avoid alarming only on reserved memory. Compare committed memory, RSS and container usage.

#### Traps / caveats

- Reserved is not the same as resident.
- Committed is not always equal to RSS.
- Container OOM decisions use cgroup/process memory, not NMT alone.

#### Optional Anki

Q: Is reserved memory the same as physical memory used?
A: No.

</details>

<a id="jvmd-native-005"></a>

<details>
<summary><strong>JVMD-NATIVE-005. How do you diagnose direct buffer or Netty native memory pressure?</strong></summary>

#### Short answer

Compare RSS, heap, direct buffer metrics, Netty allocator metrics, NMT, request payload patterns and buffer lifecycle.

#### Interview answer

I first confirm heap is stable while process memory grows. Then I inspect direct buffer pool metrics, Netty pooled allocator metrics, `MaxDirectMemorySize`, request/response payload sizes, streaming behavior, leak detector output, NMT categories and recent code changes.

Heap dumps may show Java wrapper objects, but not all native memory.

#### Deep dive

Direct memory pressure often appears in high-throughput networking, large payload handling, file transfer, compression or reactive stacks.

#### Production angle

Expose direct memory and Netty allocator metrics for services that rely heavily on off-heap buffers.

#### Traps / caveats

- Direct buffer leaks may not dominate a heap dump.
- Enabling Netty leak detection at high level can be expensive.
- Large payload buffering can defeat streaming designs.

#### Optional Anki

Q: Why may a heap dump miss direct memory pressure?
A: The large payload memory is off-heap.

</details>

<a id="jvmd-native-006"></a>

<details>
<summary><strong>JVMD-NATIVE-006. How can Metaspace or classloading issues appear in diagnostics?</strong></summary>

#### Short answer

They appear as growing Metaspace, growing loaded class count, repeated classloader retention or `OutOfMemoryError: Metaspace`.

#### Interview answer

I check Metaspace metrics, loaded/unloaded class counts, NMT Class category, heap dumps for classloader retention, dynamic proxy/code generation, repeated redeployments and framework behavior. A classloader leak often retains old application classes through threads, statics, listeners, JDBC drivers or `ThreadLocal` values.

Classloading growth may be normal during startup but suspicious if continuous.

#### Deep dive

Increasing `MaxMetaspaceSize` can delay failure but does not fix a classloader leak.

#### Production angle

Track class count and Metaspace trends in services that generate classes or support redeploy/plugin behavior.

#### Traps / caveats

- Metaspace is native memory, not Java heap.
- Heap dump helps through classloader references, not native bytes alone.
- Dynamic proxies can be legitimate but still excessive.

#### Optional Anki

Q: What Java error indicates Metaspace exhaustion?
A: `OutOfMemoryError: Metaspace`.

</details>

<a id="jvmd-native-007"></a>

<details>
<summary><strong>JVMD-NATIVE-007. How can thread stacks and native threads contribute to memory pressure?</strong></summary>

#### Short answer

Each platform thread needs native resources and stack memory, so too many threads can grow RSS and hit process limits.

#### Interview answer

A Java platform thread maps to an OS thread with native stack and scheduling overhead. If a service creates too many threads or uses large stack size, native memory can grow even when heap is stable. It may fail with inability to create native thread or get OOMKilled in a container.

Thread dumps and OS thread counts help confirm it.

#### Deep dive

Virtual threads reduce the need for many platform threads, but carrier threads and external resource limits still matter.

#### Production angle

Monitor thread count, pool sizes, queue sizes and `-Xss`, especially in containers with tight memory limits.

#### Traps / caveats

- Thread leaks may look like native memory leaks.
- Increasing pod memory hides bad pool design.
- Reducing `-Xss` blindly can risk stack overflow.

#### Optional Anki

Q: Why can many platform threads increase RSS?
A: Each has native stack and OS thread overhead.

</details>

<a id="jvmd-native-008"></a>

<details>
<summary><strong>JVMD-NATIVE-008. What JVM diagnostics should be prepared for slim containers and Kubernetes?</strong></summary>

#### Short answer

Prepare metrics, GC logs, JFR, dump paths, JDK tools or debug containers, RBAC, storage and runbooks before incidents.

#### Interview answer

Slim images often omit diagnostic tools. A production plan should define whether the app image includes `jcmd`, whether ephemeral debug containers can join the right namespaces, where heap/JFR/crash dumps are written, how GC logs are persisted, what RBAC is needed and how sensitive artifacts are handled.

This should be tested in staging.

#### Deep dive

Locked-down production access is fine, but it requires preplanned observability and diagnostics.

#### Production angle

Prepare startup flags for GC logs, crash logs, OOME dumps if appropriate, JFR readiness and NMT if needed.

#### Traps / caveats

- OOMKilled pods may lose ephemeral evidence.
- Debug containers may not share all needed namespaces.
- Adding tools during an incident may violate policy.

#### Optional Anki

Q: Why are slim Java containers risky for diagnostics?
A: They may not include JDK diagnostic tools.

</details>

<details>
<summary><strong>🧠 JVMD-NATIVE-009. What can NMT not show, and when do you need OS or native tooling?</strong></summary>

#### Short answer

NMT may not fully attribute all native allocations, allocator behavior, memory maps or kernel effects; OS/native tools fill the gaps.

#### Interview answer

NMT is JVM-aware, but third-party native libraries, allocator arenas, memory mappings, shared libraries, page cache effects or kernel behavior may require OS tools. If NMT categories do not explain RSS growth, inspect process maps, allocator stats, direct library metrics, eBPF/perf evidence or platform memory diagnostics.

NMT is one signal, not the whole truth.

#### Deep dive

RSS can be affected by `mmap`, shared pages, fragmentation and allocator retention even when application allocation has stopped growing.

#### Production angle

Native-heavy services need platform support for diagnostics, not only Java-level runbooks.

#### Traps / caveats

- NMT committed memory is not identical to RSS.
- Native symbols may be missing.
- OS tools can require elevated permissions.

#### Optional Anki

Q: What should you use if NMT does not explain RSS growth?
A: OS/native tooling and library-specific metrics.

</details>
