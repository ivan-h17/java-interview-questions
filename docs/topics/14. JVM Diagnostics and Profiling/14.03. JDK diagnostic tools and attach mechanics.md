# 14.03. JDK diagnostic tools and attach mechanics

---

<a id="jvmd-tool-001"></a>

<details>
<summary><strong>JVMD-TOOL-001. What are `jcmd`, `jstack`, `jmap`, `jstat` and `jinfo` used for?</strong></summary>

#### Short answer

They are JDK diagnostic tools for inspecting live JVMs: commands, threads, heap, GC statistics and runtime flags/properties.

#### Interview answer

`jcmd` is the central tool for many diagnostic commands. `jstack` prints thread stacks. `jmap` historically provided heap maps and dumps. `jstat` shows lightweight GC/class/compiler counters. `jinfo` can inspect some flags and system properties.

In modern workflows, `jcmd` often replaces several older tool-specific commands.

#### Deep dive

The exact available commands depend on JVM version and target process. `jcmd <pid> help` shows what that JVM supports.

#### Production angle

Know the few commands you actually need in incidents instead of memorizing every tool option.

#### Traps / caveats

- Some commands are disruptive.
- Attach permissions can block tool usage.
- Tool behavior can differ across JVM versions.

#### Optional Anki

Q: Which JDK tool centralizes many live JVM diagnostic commands?
A: `jcmd`.

</details>

<a id="jvmd-tool-002"></a>

<details>
<summary><strong>JVMD-TOOL-002. Why is `jcmd` often preferred over older standalone JDK diagnostic tools?</strong></summary>

#### Short answer

`jcmd` exposes many JVM diagnostic commands through one interface and can show what commands a target JVM supports.

#### Interview answer

`jcmd` can print thread dumps, command line, flags, class histograms, heap dumps, JFR operations and native memory output. It reduces the need to remember separate tools and often gives clearer access to modern JVM diagnostics.

It is still attach-based, so permissions and environment matter.

#### Deep dive

Older tools are still useful in some environments, but for HotSpot diagnostics `jcmd` is usually the first command to reach for.

#### Production angle

Runbooks can standardize on `jcmd` commands, making incident response more repeatable.

#### Traps / caveats

- `jcmd` is not always present in slim runtime images.
- It cannot help if attach is disabled and no alternative is prepared.
- Some commands need output paths with enough disk space.

#### Optional Anki

Q: Why prefer `jcmd` in modern JVM diagnostics?
A: It exposes many diagnostic commands through one tool.

</details>

<a id="jvmd-tool-003"></a>

<details>
<summary><strong>JVMD-TOOL-003. What is `jcmd Thread.print`, and when would you use it instead of `jstack`?</strong></summary>

#### Short answer

`jcmd Thread.print` asks the JVM to print thread stacks and lock information, similar to a thread dump from `jstack`.

#### Interview answer

I use `jcmd <pid> Thread.print` to capture Java thread stacks, thread states and lock ownership/waiting information. It is useful for hangs, deadlocks, pool starvation, blocked requests and high CPU stack investigation.

It is often preferred because it fits the same `jcmd` workflow as other diagnostics.

#### Deep dive

For high CPU, take several dumps and map OS thread IDs to Java native thread IDs. For hangs, look for repeated stacks, blocked monitors, pool queues and dependency waits.

#### Production angle

Thread dumps are usually safer than heap dumps and are often the first useful JVM artifact during an incident.

#### Traps / caveats

- One dump can catch a harmless moment.
- Large thread counts create noisy dumps.
- Thread dumps do not provide full timing history.

#### Optional Anki

Q: What does `jcmd Thread.print` produce?
A: A Java thread dump with states and lock information.

</details>

<a id="jvmd-tool-004"></a>

<details>
<summary><strong>JVMD-TOOL-004. How do you choose between `jcmd GC.class_histogram` and `jcmd GC.heap_dump`?</strong></summary>

#### Short answer

Use a class histogram for a quick object-count summary; use a heap dump when you need the full object graph and retention paths.

#### Interview answer

`GC.class_histogram` shows classes, instance counts and approximate heap usage by class. It is useful for a quick signal or comparison over time. `GC.heap_dump` writes a full heap snapshot, useful for retained-size, dominator and GC-root analysis.

The heap dump is more powerful but also more disruptive and sensitive.

#### Deep dive

A histogram can show many `byte[]`, DTOs or cache entries, but it cannot prove who retains them. A heap dump can answer ownership questions.

#### Production angle

Start with the lowest-risk artifact that can test the hypothesis. Use a heap dump only when the value justifies the pause, disk and privacy cost.

#### Traps / caveats

- Object count is not retained size.
- Heap dumps can contain secrets and customer data.
- Both commands can affect the target JVM.

#### Optional Anki

Q: What does a heap dump show that a histogram does not?
A: The object reference graph and retention paths.

</details>

<a id="jvmd-tool-005"></a>

<details>
<summary><strong>JVMD-TOOL-005. What does `jstat` show, and what does it not show?</strong></summary>

#### Short answer

`jstat` shows lightweight JVM counters such as GC, heap generation and class/compiler statistics; it does not show object ownership or full event timelines.

#### Interview answer

`jstat` can sample GC-related counters, generation usage, collection counts and times. It is useful for quick observation when full telemetry is missing.

It does not explain why objects are retained, which methods allocate, which requests are slow or what a thread is waiting for.

#### Deep dive

`jstat` is a snapshot/counter tool. For deeper analysis, use GC logs, JFR, heap dumps, thread dumps or profilers.

#### Production angle

`jstat` can help during emergency access, but production services should expose durable metrics and logs instead of relying on manual polling.

#### Traps / caveats

- Counter interpretation requires JVM and collector context.
- Sampling interval can miss spikes.
- It is not a replacement for GC logs or JFR.

#### Optional Anki

Q: What kind of data does `jstat` provide?
A: Lightweight JVM counters, especially GC and memory-pool counters.

</details>

<a id="jvmd-tool-006"></a>

<details>
<summary><strong>JVMD-TOOL-006. What are JMX, JConsole and VisualVM useful for during JVM diagnostics?</strong></summary>

#### Short answer

They expose and visualize JVM/application management data such as memory, threads, GC, MBeans and simple profiling views.

#### Interview answer

JMX is the management interface. JConsole and VisualVM can connect to JVMs and inspect memory pools, thread counts, thread stacks, GC activity, MBeans and sometimes CPU or heap sampling. They are useful in development, staging and controlled production environments.

For serious production diagnostics, I still prefer planned telemetry, JFR and command-line artifacts.

#### Deep dive

JMX can expose application-specific MBeans too, which can be useful for feature state, caches, pools or runtime switches.

#### Production angle

Remote JMX must be secured carefully. Unauthenticated or public JMX is a serious risk.

#### Traps / caveats

- GUI tools are not always available in locked-down environments.
- Remote JMX can expose sensitive operations.
- Visual sampling can distort or oversimplify results.

#### Optional Anki

Q: What is the main security concern with remote JMX?
A: It can expose sensitive management access if not secured.

</details>

<details>
<summary><strong>JVMD-TOOL-007. What is an `hs_err_pid` file, and what does it tell you?</strong></summary>

#### Short answer

It is a JVM fatal error log created after a JVM crash, often from native code, JVM bugs, signals or serious runtime failures.

#### Interview answer

An `hs_err_pid` file contains crash details: signal, problematic frame, thread, native and Java stack context, JVM version, command line, flags, libraries, memory mappings and environment details.

It is useful when the whole JVM crashes, not just when Java throws an exception.

#### Deep dive

Common causes include JNI/native library crashes, JVM bugs, invalid memory access, container or OS interactions and hardware problems.

#### Production angle

Configure crash file locations so they are persisted and collected with incident artifacts.

#### Traps / caveats

- A JVM crash is different from an application exception.
- The problematic frame may be native code, not Java source.
- Crash logs can contain environment details that need access control.

#### Optional Anki

Q: When is an `hs_err_pid` file usually created?
A: After a fatal JVM crash.

</details>

<details>
<summary><strong>🧠 JVMD-TOOL-008. How does dynamic attach work, and why can it be disabled or unavailable?</strong></summary>

#### Short answer

Dynamic attach lets tools connect to a running JVM to request diagnostics or load agents, but security, JVM flags, users or containers can block it.

#### Interview answer

Attach-based tools communicate with a live JVM through JVM-specific mechanisms and require the right permissions. It can be unavailable if attach is disabled by JVM options or policy, the process runs as another user, namespaces isolate the process, temporary attach files are inaccessible, the image lacks tools or security settings block the operation.

This is why production diagnostics must be tested ahead of time.

#### Deep dive

Attach is powerful because it can request diagnostics without restart. It is also sensitive because agent loading or management access can change process behavior.

#### Production angle

If attach is intentionally disabled, prepare alternatives: startup JFR, GC logs, metrics, crash/OOME dumps and platform-level debug workflows.

#### Traps / caveats

- Do not assume `jcmd` works just because it works locally.
- Enabling attach has a security trade-off.
- Agent-based tools may be forbidden in regulated environments.

#### Optional Anki

Q: Why test JVM attach in staging?
A: Production permissions and containers may block it.

</details>
