# 14.04. Thread dumps, deadlocks and blocking

---

<a id="jvmd-thr-001"></a>

<details>
<summary><strong>JVMD-THR-001. What is a Java thread dump, and when is it useful?</strong></summary>

#### Short answer

A thread dump is a snapshot of Java threads, stack traces, states and lock information at one moment.

#### Interview answer

Thread dumps are useful when a service is hung, slow, deadlocked, blocked on a dependency, starved in a pool or consuming high CPU. They show what each thread is doing now: running code, waiting, blocked on locks, sleeping or sitting in pool workers.

They are usually one of the safest first JVM diagnostics.

#### Deep dive

A thread dump is a snapshot, not a timeline. Taking several dumps over time makes repeated patterns visible.

#### Production angle

Thread names, executor names and request correlation make dumps much easier to interpret during incidents.

#### Traps / caveats

- One dump can be misleading.
- Large thread counts create noisy output.
- A thread dump does not show allocation rate or retained memory.

#### Optional Anki

Q: What does a Java thread dump show?
A: Thread stacks, states and lock information at a point in time.

</details>

<a id="jvmd-thr-002"></a>

<details>
<summary><strong>JVMD-THR-002. How do you read a thread dump systematically?</strong></summary>

#### Short answer

Group threads by role, inspect states and stacks, look for repeated patterns, locks, pool starvation, dependency waits and high-CPU suspects.

#### Interview answer

I start by identifying thread groups: request workers, schedulers, executor pools, GC/JVM threads, database or HTTP client threads and message consumers. Then I inspect states and top stack frames, look for many threads blocked on the same monitor, waiting on the same pool, stuck in I/O, or repeatedly executing the same hot code.

For better confidence, I compare several dumps.

#### Deep dive

Names matter. A named thread pool like `payment-http-17` is much easier to diagnose than `pool-3-thread-17`.

#### Production angle

Thread dump review should be tied to metrics: pool active count, queue depth, dependency latency and CPU usage.

#### Traps / caveats

- Do not inspect only one suspicious thread.
- JVM internal threads are often normal.
- `RUNNABLE` does not always mean burning CPU.

#### Optional Anki

Q: Why group threads by role in a dump?
A: It reveals service-level patterns instead of isolated stacks.

</details>

<a id="jvmd-thr-003"></a>

<details>
<summary><strong>JVMD-THR-003. How do Java thread states help diagnose blocked, waiting and CPU-bound work?</strong></summary>

#### Short answer

Thread states are clues: `BLOCKED` suggests monitor contention, `WAITING` or `TIMED_WAITING` suggests parking, sleeping or waiting, and `RUNNABLE` needs stack/context interpretation.

#### Interview answer

`BLOCKED` means a thread is trying to enter a synchronized monitor. `WAITING` often means it is parked, joining or waiting without timeout. `TIMED_WAITING` means a timed wait, sleep, park or I/O wait pattern may be involved. `RUNNABLE` can mean executing Java code, ready to run or inside native code.

The stack trace tells what the state means in context.

#### Deep dive

Many `TIMED_WAITING` pool threads may be idle and healthy. Many request threads waiting on a database connection pool may indicate exhaustion.

#### Production angle

Interpret states with request traffic and resource metrics. Idle workers are not the same as stuck user requests.

#### Traps / caveats

- State names alone are not root cause.
- `RUNNABLE` may include native socket reads on some platforms.
- Waiting threads may be normal if the pool is idle.

#### Optional Anki

Q: What does `BLOCKED` usually indicate?
A: Waiting to acquire a synchronized monitor.

</details>

<a id="jvmd-thr-004"></a>

<details>
<summary><strong>JVMD-THR-004. How do you identify deadlock or lock contention in a thread dump?</strong></summary>

#### Short answer

Look for threads blocked on monitors or locks, owners of those locks, repeated contention points and deadlock sections reported by the JVM.

#### Interview answer

For deadlock, I look for cycles: thread A owns lock 1 and waits for lock 2, while thread B owns lock 2 and waits for lock 1. JVM thread dumps often report Java-level deadlocks explicitly.

For contention, I look for many threads blocked on the same lock or repeatedly waiting in the same synchronized section or `Lock` implementation.

#### Deep dive

Lock contention is not always a deadlock. It can be normal serialization, oversized critical sections or slow work performed while holding a lock.

#### Production angle

Fixes include reducing lock scope, moving I/O outside locks, changing data structures, using timeouts or redesigning shared mutable state.

#### Traps / caveats

- Database deadlocks will not always show as Java monitor deadlocks.
- Native locks may need JFR or profiler evidence.
- A lock owner may be blocked on an external dependency.

#### Optional Anki

Q: What is the key pattern in a Java deadlock?
A: A cycle of threads each holding a lock another needs.

</details>

<details>
<summary><strong>JVMD-THR-005. Why is it often useful to take several thread dumps over time?</strong></summary>

#### Short answer

Multiple dumps distinguish transient states from persistent blockage, hot loops, deadlocks, repeated waits and slow progress.

#### Interview answer

A single dump can catch a thread at an unlucky moment. If several dumps show the same request threads stuck in the same stack, the same worker pool blocked, or the same high-CPU thread executing similar frames, confidence increases.

Spacing dumps a few seconds apart often reveals whether work is progressing.

#### Deep dive

Repeated dumps create a crude timeline. For richer timeline data, use JFR or a profiler.

#### Production angle

Incident runbooks should capture several dumps with timestamps, not one unlabeled file.

#### Traps / caveats

- Dumps too close together may not show change.
- Dumps too far apart may miss short spikes.
- Without timestamps, comparison is painful.

#### Optional Anki

Q: What does repeated thread dumping help distinguish?
A: Transient waits from persistent stuck patterns.

</details>

<details>
<summary><strong>JVMD-THR-006. How do you map a high-CPU OS thread to a Java stack trace?</strong></summary>

#### Short answer

Find the high-CPU native thread ID from OS tools, convert it to the format used in the dump when needed, then match it to `nid`.

#### Interview answer

I identify high-CPU threads with OS tools, note the native thread ID, often convert decimal to hex, then find the matching `nid` in the Java thread dump. The matching thread's stack shows what Java or native code was running at that moment.

Several samples are better than one.

#### Deep dive

For sustained CPU, a CPU profiler is usually better than manual thread mapping, but mapping is fast and useful during incidents.

#### Production angle

This technique helps distinguish hot application code, GC/JIT activity, busy loops and native library work.

#### Traps / caveats

- PID namespace differences can confuse IDs.
- CPU can move between threads quickly.
- One sample may catch harmless work.

#### Optional Anki

Q: Which thread dump field is commonly matched with OS thread ID?
A: `nid`.

</details>

<a id="jvmd-thr-007"></a>

<details>
<summary><strong>JVMD-THR-007. How do executor pools, scheduler threads and queues appear in thread dumps?</strong></summary>

#### Short answer

They appear as worker threads waiting for tasks, executing tasks, blocked inside dependencies or waiting on queue/lock primitives.

#### Interview answer

Executor workers often show stack frames in `ThreadPoolExecutor`, queue `take()`/`poll()`, `FutureTask`, scheduling code or the submitted application task. A saturated pool may show all workers busy in slow calls, while request threads wait for futures, semaphores or queue space.

Good thread names make this visible.

#### Deep dive

A thread dump does not directly show queue size, so combine it with executor metrics.

#### Production angle

Diagnosing pool problems requires active thread count, queue depth, task latency, rejection count and dependency latency.

#### Traps / caveats

- Idle pool workers in waiting state are normal.
- An unbounded queue can hide overload until latency explodes.
- Blocking on work submitted to the same pool can create starvation.

#### Optional Anki

Q: What metric should you pair with executor thread dumps?
A: Queue depth and active worker count.

</details>

<a id="jvmd-thr-008"></a>

<details>
<summary><strong>🧠 JVMD-THR-008. What can thread dumps miss compared with JFR or a profiler?</strong></summary>

#### Short answer

Thread dumps miss fine-grained timing, allocation rate, historical events, short spikes and sampled CPU/off-CPU behavior.

#### Interview answer

A thread dump captures one instant. It may miss short lock contention, brief CPU bursts, allocation churn, intermittent socket waits, GC correlation and method-level hot paths. JFR records events over time. Profilers sample execution or wall-clock behavior and can show where time is spent across many samples.

Thread dumps are a starting point, not the whole story.

#### Deep dive

If latency spikes last 200 ms and dumps are taken every 10 seconds, the dump may never catch the cause.

#### Production angle

Use thread dumps for quick triage and JFR/profilers for timing-sensitive or intermittent problems.

#### Traps / caveats

- A clean dump does not prove there was no contention.
- Short-lived tasks may disappear between dumps.
- Allocation pressure usually needs JFR or allocation profiling.

#### Optional Anki

Q: What does JFR add beyond a thread dump?
A: Runtime events and timing over a period.

</details>

<details>
<summary><strong>🧠 JVMD-THR-009. How do virtual threads change thread dump analysis?</strong></summary>

#### Short answer

Virtual threads can create many more logical threads, so analysis shifts toward grouping, structured dumps, carrier behavior and pinned or blocked operations.

#### Interview answer

With virtual threads, there may be thousands or millions of logical threads. Traditional "count platform threads" reasoning becomes less useful. I look for common stack patterns, blocked resources, pinned operations, carrier thread saturation, JDBC/HTTP pool limits and structured concurrency boundaries.

The bottleneck often moves from thread count to external resource limits.

#### Deep dive

Virtual threads make blocking cheaper, but they do not make databases, sockets, locks or CPU unlimited.

#### Production angle

Observability needs to show resource pools and request context, not just raw thread count.

#### Traps / caveats

- Do not pool virtual threads like platform threads.
- ThreadLocal-heavy code can become expensive or confusing.
- Virtual threads do not fix connection pool exhaustion.

#### Optional Anki

Q: What resource limit still matters with virtual threads?
A: External limits such as JDBC connections, CPU and downstream capacity.

</details>
