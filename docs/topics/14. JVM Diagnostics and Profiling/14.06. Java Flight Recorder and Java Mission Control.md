# 14.06. Java Flight Recorder and Java Mission Control

---

<a id="jvmd-jfr-001"></a>

<details>
<summary><strong>JVMD-JFR-001. What is Java Flight Recorder?</strong></summary>

#### Short answer

Java Flight Recorder is a low-overhead JVM event recorder for profiling and production diagnostics.

#### Interview answer

JFR records structured events from the JVM and application over time: CPU samples, allocation events, GC, safepoints, thread activity, locks, exceptions, class loading, file and socket I/O and more. It is built for low overhead when configured carefully and is useful in production.

Recordings can be analyzed with Java Mission Control or the `jfr` command.

#### Deep dive

JFR is timeline-oriented, so it helps correlate different runtime causes inside one recording.

#### Production angle

JFR is often a strong first choice for unclear latency, CPU, allocation or blocking problems.

#### Traps / caveats

- Recording settings affect detail and overhead.
- JFR files can contain sensitive data.
- Short recordings can miss intermittent issues.

#### Optional Anki

Q: What kind of data does JFR collect?
A: Structured JVM and application runtime events over time.

</details>

<a id="jvmd-jfr-002"></a>

<details>
<summary><strong>JVMD-JFR-002. How does JFR differ from thread dumps, heap dumps and ordinary logs?</strong></summary>

#### Short answer

JFR records many low-level runtime events over time; thread dumps and heap dumps are snapshots, and logs are application-emitted text/events.

#### Interview answer

Thread dumps show stacks at a point in time. Heap dumps show retained heap at a point in time. Logs show what the application chose to write. JFR records JVM and application runtime events with timestamps and optional stack traces, so it can connect CPU, allocation, GC, locks, I/O and latency.

It complements the other artifacts rather than replacing them.

#### Deep dive

For retained-memory ownership, a heap dump is better. For allocation churn or latency timelines, JFR is often better.

#### Production angle

JFR can provide deep evidence without immediately taking a disruptive heap dump.

#### Traps / caveats

- JFR must capture the event type you need.
- Logs may contain business context JFR does not know.
- JFR analysis still requires workload and timeline context.

#### Optional Anki

Q: What is the main advantage of JFR over a single thread dump?
A: It records runtime events over time.

</details>

<a id="jvmd-jfr-003"></a>

<details>
<summary><strong>JVMD-JFR-003. What production issues can JFR help diagnose?</strong></summary>

#### Short answer

JFR helps with latency spikes, CPU hotspots, allocation pressure, GC pauses, lock contention, blocked I/O, exceptions and startup or warmup behavior.

#### Interview answer

JFR is useful when the problem is time-based. It can show method sampling, allocation events, GC and safepoint timing, monitor blocking, thread parking, socket reads/writes, file I/O, exceptions, class loading and compiler activity.

This makes it strong for "why was the service slow during this window?"

#### Deep dive

JFR can reveal whether latency was spent executing Java code, waiting on locks, waiting on I/O, allocating heavily or paused by the JVM.

#### Production angle

Use JFR with latency metrics and traces to connect JVM-level causes to user-visible impact.

#### Traps / caveats

- JFR will not automatically explain business-level correctness bugs.
- Low-frequency events may require longer recordings.
- More detailed settings can add overhead.

#### Optional Anki

Q: What kind of issue is JFR especially good at?
A: Time-window performance and latency investigation.

</details>

<a id="jvmd-jfr-004"></a>

<details>
<summary><strong>JVMD-JFR-004. How do you start, check, dump and stop a JFR recording with `jcmd`?</strong></summary>

#### Short answer

Use `jcmd <pid> JFR.start`, `JFR.check`, `JFR.dump` and `JFR.stop` with names, durations, settings and filenames.

#### Interview answer

A typical flow is to start a recording with a name and duration, check that it is running, dump it to an approved path, and stop it when done. For example, `jcmd <pid> JFR.start name=incident duration=120s filename=/path/file.jfr settings=profile` captures a bounded recording on modern HotSpot JVMs.

#### Deep dive

Bounded recordings reduce the risk of forgotten diagnostics. Continuous recordings can be configured as ring buffers and dumped when needed.

#### Production angle

Use safe filenames, enough disk, approved storage and short durations unless continuous recording is deliberately configured.

#### Traps / caveats

- The output path must exist and be writable.
- Recording settings affect overhead.
- Attach may be unavailable in hardened environments.

#### Optional Anki

Q: Which `jcmd` command writes a running JFR recording to a file?
A: `JFR.dump`.

</details>

<a id="jvmd-jfr-005"></a>

<details>
<summary><strong>JVMD-JFR-005. How do continuous, time-fixed, default and profile JFR recordings differ?</strong></summary>

#### Short answer

Continuous recordings run as ongoing buffers; time-fixed recordings capture a window; default settings are lower overhead; profile settings collect more detail.

#### Interview answer

A time-fixed recording is started for a specific duration during an incident. A continuous recording runs in the background, often as a bounded buffer that can be dumped after a problem. The default settings are designed for low overhead. Profile settings usually collect more data and stack traces, so they are better for short investigations but can cost more.

Choose based on risk and diagnostic need.

#### Deep dive

Continuous JFR is valuable because evidence exists before anyone logs in. The trade-off is storage, retention, privacy and overhead management.

#### Production angle

For critical services, consider always-ready low-overhead recording plus a runbook for short high-detail recordings.

#### Traps / caveats

- Profile settings should not be left running accidentally.
- Continuous buffers can overwrite old evidence.
- Recordings may contain sensitive event data.

#### Optional Anki

Q: Why use continuous JFR?
A: To preserve recent runtime evidence before an incident is noticed.

</details>

<a id="jvmd-jfr-006"></a>

<details>
<summary><strong>JVMD-JFR-006. How do Java Mission Control and the `jfr` command help analyze recordings?</strong></summary>

#### Short answer

JMC provides interactive visual analysis; the `jfr` command provides command-line inspection and summaries of `.jfr` files.

#### Interview answer

Java Mission Control helps inspect JFR timelines, hot methods, allocation pressure, GC events, lock contention, I/O events and automated analysis pages. The `jfr` command is useful in terminals or automation for viewing metadata, printing events, summarizing recordings or filtering event types.

Together they support both deep manual analysis and quick CLI checks.

#### Deep dive

JMC is better for exploratory visual work. CLI analysis is better for scripts, remote environments and quick event extraction.

#### Production angle

Store recordings with incident IDs and timestamps so analysis can be repeated and shared securely.

#### Traps / caveats

- JMC recommendations still need engineering judgment.
- Large recordings can be slow to open.
- CLI output can be overwhelming without filtering.

#### Optional Anki

Q: What is JMC commonly used for?
A: Visual analysis of JFR recordings.

</details>

<a id="jvmd-jfr-007"></a>

<details>
<summary><strong>JVMD-JFR-007. Which JFR events are useful for latency investigations?</strong></summary>

#### Short answer

Useful events include execution samples, GC pauses, safepoints, monitor blocking, thread parking, allocation, socket/file I/O, exceptions and class loading.

#### Interview answer

For latency, I inspect CPU samples for hot code, GC and safepoint events for JVM pauses, monitor and lock events for contention, thread park/sleep events for waiting, socket and file I/O for external waits, allocation events for GC pressure, and exception events for failure storms.

Then I align these with request latency and traces.

#### Deep dive

Latency is often "where time went", not only "what code used CPU". Wall-clock waiting events can be as important as CPU events.

#### Production angle

Combine JFR with endpoint, dependency and pool metrics to identify whether the latency is inside Java code, the JVM, or outside the service.

#### Traps / caveats

- Event thresholds may hide short events.
- Missing stack traces reduce root-cause value.
- I/O time may indicate downstream slowness, not a JVM bug.

#### Optional Anki

Q: Which JFR events help diagnose lock contention?
A: Monitor/blocking or lock-related events.

</details>

<details>
<summary><strong>🧠 JVMD-JFR-008. How do custom events, thresholds, stack traces and privacy concerns affect JFR usage?</strong></summary>

#### Short answer

They control what JFR captures, how expensive it is, how useful stacks are and what sensitive data may be recorded.

#### Interview answer

Custom events can add domain-specific timing, such as payment authorization or cache refresh phases, without relying only on logs. Thresholds reduce noise and overhead by recording events above a duration or size. Stack traces improve root cause analysis but add cost and can expose sensitive method/context details.

JFR settings must balance detail, overhead and privacy.

#### Deep dive

Custom events are useful when standard JVM events show waiting or CPU use but not the business operation phase.

#### Production angle

Review JFR files under the same data-handling policy as logs and dumps. Avoid recording raw customer data in event fields.

#### Traps / caveats

- Too-low thresholds can create large recordings.
- No stack traces can make events hard to act on.
- Custom events should not become noisy logging under another name.

#### Optional Anki

Q: Why do JFR thresholds matter?
A: They control event volume, overhead and diagnostic detail.

</details>
