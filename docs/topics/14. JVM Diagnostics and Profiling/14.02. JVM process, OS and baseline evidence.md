# 14.02. JVM process, OS and baseline evidence

---

<a id="jvmd-base-001"></a>

<details>
<summary><strong>JVMD-BASE-001. How do you identify the correct Java process on a host or inside a container?</strong></summary>

#### Short answer

Match PID, command line, user, container, port, service name and runtime metadata before running diagnostics.

#### Interview answer

On a host, I would use tools such as `jcmd`, `jps`, `ps`, service manager metadata and listening ports to identify the Java process. In containers, I also check the pod, container name, PID namespace and whether the PID inside the container differs from the host PID.

Before attaching tools, I verify command line, application name, version and owner.

#### Deep dive

Multiple Java processes may run on the same node: app, sidecar, build tool, admin process or test process. Attaching to the wrong one wastes time and can be disruptive.

#### Production angle

Runbooks should include the exact way to find the service PID in the deployment platform.

#### Traps / caveats

- Host PID and container PID can differ.
- Minimal containers may not include `jcmd` or `ps`.
- The user running the diagnostic tool may not be allowed to attach.

#### Optional Anki

Q: What must you verify before attaching JVM tools?
A: The correct process, user, container and command line.

</details>

<a id="jvmd-base-002"></a>

<details>
<summary><strong>JVMD-BASE-002. What JVM version, command line, flags and environment data are useful during diagnostics?</strong></summary>

#### Short answer

Collect Java version, vendor, command line, JVM flags, heap settings, GC choice, system properties, environment variables and container limits.

#### Interview answer

Useful baseline data includes JDK version and vendor, application artifact/version, JVM command line, active flags, heap and stack sizing, GC configuration, JFR/NMT/GC-log settings, classpath or module path, active Spring profile/config and relevant environment variables.

This explains what the JVM was actually running, not what the team thought it was running.

#### Deep dive

Runtime flags may come from Docker images, Helm charts, startup scripts, environment variables or platform defaults. The source of a bad flag can matter for prevention.

#### Production angle

Keep command line and build metadata visible in telemetry or diagnostics so incidents do not start with guesswork.

#### Traps / caveats

- Defaults differ by Java version, container limit and vendor.
- Config drift between pods can create partial outages.
- Some system properties and environment variables can contain secrets.

#### Optional Anki

Q: Why collect JVM command line during diagnostics?
A: It shows the runtime configuration actually used.

</details>

<a id="jvmd-base-003"></a>

<details>
<summary><strong>JVMD-BASE-003. What OS and container metrics should be collected together with JVM metrics?</strong></summary>

#### Short answer

Collect CPU, throttling, memory/RSS, disk I/O, network, file descriptors, thread count, process limits and container restarts/events.

#### Interview answer

JVM metrics need OS context. I would inspect CPU usage, run queue or load, cgroup throttling, RSS, page faults, disk I/O, network errors, socket counts, file descriptors, native thread count, process limits, pod memory and CPU limits, restarts and OOM events.

This helps separate JVM behavior from platform pressure.

#### Deep dive

A Java service can look slow because CPU is throttled, disk is saturated, DNS is failing, file descriptors are exhausted or the node is under pressure.

#### Production angle

Dashboards should show JVM and platform metrics side by side for the same instance.

#### Traps / caveats

- Host CPU graphs can hide container throttling.
- Heap usage alone does not explain process memory.
- Kubernetes restart reason can disappear from ordinary application logs.

#### Optional Anki

Q: Why collect container metrics with JVM metrics?
A: Platform limits can look like JVM performance problems.

</details>

<a id="jvmd-base-004"></a>

<details>
<summary><strong>JVMD-BASE-004. How do RSS and virtual memory differ from Java heap usage?</strong></summary>

#### Short answer

Heap usage is Java heap occupancy; RSS is resident process memory; virtual memory is address space reserved or mapped by the process.

#### Interview answer

Java heap usage tells how much of the managed heap is used. RSS tells how much process memory is resident in RAM from the OS perspective. Virtual memory can include reserved address space, memory mappings and regions that are not physically resident.

RSS includes heap, Metaspace, code cache, thread stacks, direct buffers, GC structures, native libraries and allocator behavior.

#### Deep dive

In containers, RSS and cgroup memory are often what decide OOM kills, not only `-Xmx`.

#### Production angle

If heap is stable but RSS grows, investigate native/off-heap memory, thread count, mmap, direct buffers, Metaspace and NMT.

#### Traps / caveats

- `-Xmx` is not the whole memory budget.
- Reserved memory is not the same as committed or resident memory.
- Heap dumps do not show all native allocations.

#### Optional Anki

Q: Which metric matters for container OOM kills?
A: Container/process memory such as RSS/cgroup usage, not only heap used.

</details>

<a id="jvmd-base-005"></a>

<details>
<summary><strong>JVMD-BASE-005. How do you inspect file descriptors, sockets and native threads for a Java process?</strong></summary>

#### Short answer

Use OS/container tools and JVM data: file descriptor counts, socket states, thread count, thread dumps and process limits.

#### Interview answer

For file descriptors, inspect open count, limit and the types of files/sockets held by the process. For sockets, check established, close-wait and listening connections plus dependency endpoints. For native threads, compare JVM thread count, OS thread count, stack size and process limits.

Thread dumps explain what Java threads are doing; OS tools show process resources.

#### Deep dive

Resource leaks may appear as `Too many open files`, growing `CLOSE_WAIT`, inability to create native threads or request hangs on connection acquisition.

#### Production angle

Track file descriptor and thread-count metrics continuously. They are cheap signals for resource leaks.

#### Traps / caveats

- Thread count can consume native memory through stacks.
- Socket leaks may be caused by HTTP client misuse or missing timeouts.
- OS inspection inside containers may need extra permissions.

#### Optional Anki

Q: What Java failure can native thread exhaustion cause?
A: `OutOfMemoryError: Unable to create new native thread`.

</details>

<a id="jvmd-base-006"></a>

<details>
<summary><strong>JVMD-BASE-006. How can container CPU throttling look like a JVM performance problem?</strong></summary>

#### Short answer

CPU throttling can make the JVM appear slow, extend pauses, delay request handling and distort profiles even when code did not change.

#### Interview answer

If a container hits its CPU quota, the process may be prevented from running for parts of each period. The service can show high latency, slow GC, delayed JIT, request timeouts or low throughput while host CPU does not look saturated.

Check cgroup throttling metrics, CPU limits and actual CPU demand.

#### Deep dive

JVM threads, GC workers and application workers all compete for the allowed CPU budget. A service can have many runnable threads but still make slow progress.

#### Production angle

CPU limits should be tested with production-like load. A too-low limit can create latency spikes that look like application bugs.

#### Traps / caveats

- Host-level CPU graphs can be misleading.
- Adding threads does not fix throttling.
- GC tuning cannot compensate for severe CPU starvation.

#### Optional Anki

Q: What metric should you check when containerized Java is slow but host CPU seems fine?
A: Container CPU throttling.

</details>

<a id="jvmd-base-007"></a>

<details>
<summary><strong>JVMD-BASE-007. Why can diagnostic tools fail because of users, permissions, PID namespaces or containers?</strong></summary>

#### Short answer

Attach-based tools often need the right user, JVM permissions, namespace visibility and JDK tools available in the runtime environment.

#### Interview answer

Tools such as `jcmd` need to see the target process and have permission to communicate with it. They can fail if run as another user, if attach is disabled, if the process is in another PID namespace, if `/tmp` or attach sockets are isolated, or if the image contains only a JRE-like runtime without diagnostic tools.

Containers make these assumptions visible.

#### Deep dive

Security hardening may intentionally disable attach or prevent ptrace-like access. That is reasonable, but teams need an alternate diagnostic plan.

#### Production angle

Validate diagnostic commands in staging using the same image, user, security context and Kubernetes settings as production.

#### Traps / caveats

- Installing tools during an incident may not be allowed.
- Running as root may violate security policy.
- Ephemeral debug containers still need namespace and permission alignment.

#### Optional Anki

Q: Why might `jcmd` fail in Kubernetes?
A: User, permission, namespace, attach or missing-tool issues.

</details>

<details>
<summary><strong>JVMD-BASE-008. What should a reusable JVM diagnostic snapshot include?</strong></summary>

#### Short answer

Include process identity, JVM config, OS/container metrics, thread dumps, GC evidence, recent logs, JFR when possible and relevant resource counts.

#### Interview answer

A useful snapshot captures Java version, app version, command line, JVM flags, heap/GC settings, container limits, CPU/memory/thread/file-descriptor data, recent GC logs, several thread dumps, a short JFR if allowed, process environment summary, pod/host status and timestamps.

The snapshot should be safe to run and easy to attach to an incident.

#### Deep dive

The snapshot should answer "what was this JVM doing and under what limits?" without requiring the engineer to remember many commands under pressure.

#### Production angle

Automate snapshots with redaction and approved storage. Manual copy-paste diagnostics are error-prone during outages.

#### Traps / caveats

- Snapshots can contain secrets.
- A snapshot is not a replacement for continuous telemetry.
- Commands must be tested against real production-like containers.

#### Optional Anki

Q: What makes a JVM diagnostic snapshot reusable?
A: It captures standard JVM, OS/container and timing evidence safely.

</details>
