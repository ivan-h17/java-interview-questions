# 14.10. Production JVM diagnostic scenarios

---

<a id="jvmd-scen-001"></a>

<details>
<summary><strong>JVMD-SCEN-001. A service has high CPU usage or high CPU with low throughput. How would you investigate it?</strong></summary>

#### Short answer

Correlate CPU with throughput and latency, map hot threads, capture CPU/JFR profiles, inspect GC/JIT activity and check whether CPU is useful work or spinning.

#### Interview answer

I first check whether traffic increased, whether errors or latency changed, and whether CPU throttling exists. Then I identify high-CPU threads and map them to Java stacks, or capture a short CPU profile/JFR. I also inspect GC frequency, JIT/compiler activity, retry loops, logging storms, serialization, compression and hot code paths.

High CPU with low throughput often means spinning, contention, retries, GC overhead or blocked progress elsewhere.

#### Deep dive

CPU usage alone does not say whether the service is doing useful work. Throughput and stack evidence decide that.

#### Production angle

Mitigate with rollback, traffic reduction, rate limiting or scaling if user impact is high, while preserving profile evidence.

#### Traps / caveats

- Adding CPU may hide a retry storm.
- A CPU profile during idle time is useless.
- Container throttling can mimic CPU saturation.

#### Optional Anki

Q: What is the first profile for unexplained high CPU?
A: A CPU profile or high-CPU thread stack mapping.

</details>

<a id="jvmd-scen-002"></a>

<details>
<summary><strong>JVMD-SCEN-002. A service has periodic p99 latency spikes. What JVM data would you inspect?</strong></summary>

#### Short answer

Inspect GC/safepoints, JFR events, thread pools, lock contention, allocation spikes, I/O waits, CPU throttling and deployment/traffic timing.

#### Interview answer

I align p99 spikes with per-instance GC logs, safepoint events, JFR recordings, CPU, allocation rate, thread pool metrics, lock events, socket/file I/O, dependency traces, container throttling and scheduled jobs. Periodicity often points to GC cycles, batch jobs, cache refresh, scheduled tasks or external dependency patterns.

The timeline matters more than one snapshot.

#### Deep dive

If spikes affect only one pod, inspect pod-specific CPU, memory, GC and resource limits.

#### Production angle

Use short JFR recordings around the spike or continuous JFR ring buffers for intermittent issues.

#### Traps / caveats

- Average latency can look normal.
- Cluster-level graphs can hide one bad instance.
- Scheduled jobs can cause JVM symptoms indirectly.

#### Optional Anki

Q: What JVM artifact is useful for intermittent latency spikes?
A: JFR recording around the spike.

</details>

<a id="jvmd-scen-003"></a>

<details>
<summary><strong>JVMD-SCEN-003. Requests hang, but CPU usage is low. What would you check first?</strong></summary>

#### Short answer

Check thread dumps, pool metrics, dependency waits, connection pools, locks, queues, timeouts and blocked I/O.

#### Interview answer

Low CPU with hung requests usually means waiting. I would take several thread dumps and inspect request threads, executor workers, database/HTTP pool waits, locks, queue operations, socket reads, futures and timeouts. I would also check traces and dependency metrics to see where requests stop progressing.

The issue may be outside the JVM but visible in JVM stacks.

#### Deep dive

A request can hang before instrumentation records a span if it is waiting in an executor or connection pool queue.

#### Production angle

Mitigate by enforcing timeouts, limiting concurrency, opening circuit breakers or rolling back bad dependency behavior.

#### Traps / caveats

- Low CPU does not mean the service is healthy.
- Thread pools can be exhausted while workers wait on slow dependencies.
- Missing timeouts turn slow dependencies into hung requests.

#### Optional Anki

Q: What does low CPU plus hung requests usually suggest?
A: Waiting, blocking or resource exhaustion.

</details>

<a id="jvmd-scen-004"></a>

<details>
<summary><strong>JVMD-SCEN-004. GC pauses or Full GC events increased after a deployment. How would you diagnose the change?</strong></summary>

#### Short answer

Compare before/after allocation rate, live set, heap occupancy, GC logs, traffic, payloads, cache behavior and code changes.

#### Interview answer

I compare old and new versions under similar traffic: allocation rate, object churn, old-gen after GC, live set, Full GC frequency, pause causes, heap sizing, container limits and request payload mix. Then I inspect recent changes: DTO mapping, logging, JSON parsing, cache changes, batch jobs, large collections or buffering.

JFR allocation events or allocation profiling can identify new churn.

#### Deep dive

Full GC can be caused by real leaks, undersized heap, humongous allocations, metadata pressure or explicit `System.gc()`.

#### Production angle

If impact is high and the deployment is correlated, rollback may be the safest mitigation while preserving evidence.

#### Traps / caveats

- More traffic after deployment can be the real difference.
- Increasing heap may reduce frequency but increase dump size and cost.
- GC tuning should follow evidence, not guesswork.

#### Optional Anki

Q: What profile helps after GC increased due to object churn?
A: Allocation profile or JFR allocation events.

</details>

<a id="jvmd-scen-005"></a>

<details>
<summary><strong>JVMD-SCEN-005. Native memory grows or the pod is `OOMKilled` while heap is stable. What would you check?</strong></summary>

#### Short answer

Check RSS/cgroup memory, direct buffers, Netty, thread count/stacks, Metaspace, Code Cache, NMT, memory maps and container limits.

#### Interview answer

I first confirm heap used and heap committed are stable while RSS or cgroup memory grows. Then I inspect NMT if enabled, direct buffer metrics, Netty allocator metrics, thread count, `-Xss`, Metaspace/class count, Code Cache, mmap usage, native libraries and pod memory limits/events.

Heap dump alone is not enough.

#### Deep dive

The OOM killer cares about process/container memory. Java heap may be only one part of the budget.

#### Production angle

Prepare NMT, direct memory metrics and persistent OOM evidence before incidents in containerized services.

#### Traps / caveats

- `OOMKilled` may not produce a Java `OutOfMemoryError`.
- Native memory pressure can be caused by too many threads.
- Direct memory leaks may show only wrapper objects in heap dumps.

#### Optional Anki

Q: What does stable heap plus growing RSS suggest?
A: Native or off-heap memory growth.

</details>

<a id="jvmd-scen-006"></a>

<details>
<summary><strong>JVMD-SCEN-006. A service is slow only during the first minutes after deployment. What JVM causes are likely?</strong></summary>

#### Short answer

Likely causes include cold caches, class loading, framework initialization, JIT warmup, connection warmup, TLS setup and initial GC behavior.

#### Interview answer

I would inspect startup timeline, readiness behavior, JFR startup recording, class loading, compiler activity, CPU usage, dependency connection creation, cache warmup and first-request latency. The JVM may still be warming hot methods and initializing classes while the service already receives traffic.

Not every first-minute problem is a steady-state performance bug.

#### Deep dive

Autoscaling can amplify this if new pods receive full traffic before they are warm.

#### Production angle

Use readiness checks, warmup requests, gradual rollout and realistic startup SLOs.

#### Traps / caveats

- Delaying readiness too long can slow rollouts.
- Warmup should not perform unsafe side effects.
- Profiles during startup should not be treated as steady-state profiles.

#### Optional Anki

Q: What JVM feature commonly affects first-minute performance?
A: JIT warmup.

</details>

<a id="jvmd-scen-007"></a>

<details>
<summary><strong>JVMD-SCEN-007. A thread pool is saturated, lock contention is suspected, or a deadlock may exist. Which JVM evidence helps?</strong></summary>

#### Short answer

Use thread dumps, executor metrics, JFR lock/thread events, queue metrics, dependency traces and high-CPU mapping when relevant.

#### Interview answer

For pool saturation, I check active threads, queue depth, task latency, rejection count and thread dumps showing what workers are doing. For lock contention or deadlock, I inspect blocked threads, lock owners, repeated blocked stacks and JFR monitor events. If CPU is involved, I map high-CPU threads or profile.

The goal is to find whether workers are busy, blocked, waiting or deadlocked.

#### Deep dive

Pool saturation often comes from slow downstream calls, missing timeouts, blocking inside async code, unbounded queues or work submitted back to the same pool.

#### Production angle

Mitigations include timeouts, bulkheads, bounded queues, rejection behavior, traffic shedding or disabling the slow path.

#### Traps / caveats

- Increasing pool size can overload dependencies.
- Deadlock in a database may not appear as Java monitor deadlock.
- Idle-looking workers may be waiting for scarce external resources.

#### Optional Anki

Q: What two signals diagnose executor saturation?
A: Thread dumps and executor queue/active metrics.

</details>

<a id="jvmd-scen-008"></a>

<details>
<summary><strong>JVMD-SCEN-008. Allocation rate is high, but retained heap is not growing. How do you profile it?</strong></summary>

#### Short answer

Use JFR allocation events or allocation profiling to find hot allocation sites under representative load.

#### Interview answer

If retained heap is stable but GC is busy, I suspect object churn. I capture a JFR or allocation profile during the bad window and inspect allocation hotspots by stack. Common causes include JSON serialization, mapping, logging, regex, temporary collections, boxing, large DTO graphs or repeated buffer creation.

Then I optimize only meaningful hot paths.

#### Deep dive

Short-lived objects may never appear in a heap dump because they die before the snapshot.

#### Production angle

Validate improvements with allocation rate, GC overhead and latency metrics, not just code review.

#### Traps / caveats

- Do not optimize every allocation.
- Allocation sampling can miss rare paths.
- Reducing allocation can trade off readability or correctness if overdone.

#### Optional Anki

Q: Why is heap dump weak for object churn?
A: Short-lived objects may already be gone.

</details>

<a id="jvmd-scen-009"></a>

<details>
<summary><strong>JVMD-SCEN-009. JFR shows high socket read or file I/O time. How do you interpret that?</strong></summary>

#### Short answer

Treat it as waiting evidence and determine whether the cause is downstream latency, large payloads, slow storage, missing timeouts or expected blocking.

#### Interview answer

High socket read time often means the thread is waiting for a remote peer, network, TLS, proxy or load balancer. High file I/O time may mean slow disk, large reads/writes, logging pressure, storage contention or inefficient file handling. I correlate with traces, dependency metrics, payload sizes, timeout settings and OS I/O metrics.

It is not automatically a JVM problem.

#### Deep dive

Wall-clock waiting can dominate p99 latency even when CPU profiles look clean.

#### Production angle

Fixes may involve timeouts, streaming, backpressure, client pool tuning, dependency mitigation or storage changes.

#### Traps / caveats

- Socket read time can be normal for long polling or streaming.
- File I/O may be log-related.
- Missing trace spans can make JVM I/O look like unexplained latency.

#### Optional Anki

Q: What does high socket read time usually suggest?
A: Waiting on network or downstream data.

</details>

<a id="jvmd-scen-010"></a>

<details>
<summary><strong>🧠 JVMD-SCEN-010. A profile shows mostly JVM, GC, compiler, native or kernel frames. How do you interpret it?</strong></summary>

#### Short answer

It means cost is below ordinary application frames, so inspect runtime, GC, native library, OS or workload causes before blaming business code.

#### Interview answer

JVM or GC frames can point to allocation pressure, high live set, safepoints or runtime work. Compiler frames may indicate warmup or heavy JIT activity. Native frames can indicate compression, TLS, JNI, memory allocation or third-party libraries. Kernel frames can indicate networking, filesystem, scheduling or syscalls.

The profile tells which layer needs the next investigation.

#### Deep dive

Application code can still be the root cause by driving excessive allocation, I/O, JNI calls or syscalls.

#### Production angle

Use mixed-stack profiling, JFR, GC logs, NMT and OS metrics together for cross-layer diagnosis.

#### Traps / caveats

- Native/kernel frames can be symptoms, not root cause.
- Missing symbols can make stacks vague.
- Runtime-heavy profiles during startup may be normal.

#### Optional Anki

Q: What should you do when profiles show mostly kernel frames?
A: Inspect OS/network/disk/syscall behavior and the Java code causing it.

</details>

<a id="jvmd-scen-011"></a>

<details>
<summary><strong>🧠 JVMD-SCEN-011. Production access is locked down and attach tools are unavailable. What should be prepared before incidents?</strong></summary>

#### Short answer

Prepare continuous telemetry, GC logs, startup JFR options, dump paths, crash/OOME handling, debug workflow, RBAC and runbooks.

#### Interview answer

If attach is unavailable, diagnostics must be designed into the service. I would prepare JVM metrics, secure logs, GC log rotation, optional continuous JFR, crash logs, OOME heap dump or histogram policy, NMT if justified, actuator/management endpoints, Kubernetes debug procedures and artifact storage.

The team should test the workflow before a real incident.

#### Deep dive

Security restrictions are reasonable. The failure is having no approved diagnostic path when production breaks.

#### Production angle

Runbooks should answer who can collect evidence, what commands are allowed, where files go and how sensitive data is handled.

#### Traps / caveats

- Minimal images and disabled attach remove common tools.
- Automatic dumps can fill disk if not bounded.
- Debug access without audit and policy is a security risk.

#### Optional Anki

Q: What is the alternative to production attach access?
A: Preplanned telemetry, recordings, logs, dumps and debug runbooks.

</details>
