# Observability, operations and API governance

<a id="rest-obs-001"></a>

<details>
<summary><strong>REST-OBS-001. What should and should not be logged for REST API requests?</strong></summary>

#### Short answer

Log request metadata and outcomes; avoid logging secrets, tokens, raw sensitive payloads and excessive personal data.

#### Interview answer

Useful logs include request ID, method, path template, status, latency, caller/client, tenant if safe, and error category. Avoid raw authorization headers, passwords, payment data, full documents and large payloads.

#### Deep dive

Use structured logs with route templates like `/orders/{id}`, not raw high-cardinality paths when possible. Put detailed diagnostics behind access controls.

#### Production angle

Good logs support incidents and audits. Bad logs create compliance and privacy incidents.

#### Traps / caveats

- Query strings can contain sensitive data.
- Debug logging often leaks more than responses.
- Logs need retention and access controls.

#### Optional Anki

Q: What should never be logged?
A: Tokens, secrets and sensitive raw payloads.

</details>

<a id="rest-obs-002"></a>

<details>
<summary><strong>REST-OBS-002. What is a correlation ID?</strong></summary>

#### Short answer

A correlation ID is an identifier used to connect logs and events belonging to the same request or workflow.

#### Interview answer

The edge service or first backend generates a request ID and passes it downstream. Each service logs it so engineers can follow one request across services.

#### Deep dive

Correlation IDs are related to but not identical to distributed tracing IDs. Many systems use both.

#### Production angle

Without correlation IDs, debugging multi-service incidents becomes slow and error-prone.

#### Traps / caveats

- Sanitize client-supplied IDs.
- Propagate across async boundaries.
- Do not use correlation IDs for authorization.

#### Optional Anki

Q: Correlation ID purpose?
A: Connect logs for the same request/workflow.

</details>

<a id="rest-obs-003"></a>

<details>
<summary><strong>REST-OBS-003. How would you trace a request across multiple services?</strong></summary>

#### Short answer

Propagate trace context through HTTP headers and emit spans for inbound and outbound calls.

#### Interview answer

Use distributed tracing with headers such as `traceparent`. Each service creates spans for handling the request and for downstream HTTP calls, database calls or messaging operations.

#### Deep dive

Trace context must be propagated through thread pools, async code and message boundaries. Sampling decisions should preserve useful incident visibility.

#### Production angle

Traces show where latency and errors occur across service boundaries.

#### Traps / caveats

- Missing context propagation breaks traces.
- High-cardinality span attributes are expensive.
- Do not put PII in trace attributes.

#### Optional Anki

Q: Header family for modern tracing?
A: W3C Trace Context, especially `traceparent`.

</details>

<a id="rest-obs-004"></a>

<details>
<summary><strong>REST-OBS-004. Which metrics are important for REST APIs?</strong></summary>

#### Short answer

Track request rate, error rate, latency, saturation and dependency metrics.

#### Interview answer

For each endpoint, monitor request count, status-code distribution, p50/p95/p99 latency and in-flight requests. Also monitor downstream HTTP calls, database latency, thread pools and queue sizes.

#### Deep dive

Use route templates as labels, not raw URLs, to avoid cardinality explosions.

#### Production angle

Metrics drive alerting, capacity planning and regression detection after deployment.

#### Traps / caveats

- Averages hide p99 latency.
- Too many label values can break metrics systems.
- Separate client errors from server errors.

#### Optional Anki

Q: Core API metrics?
A: Rate, errors, duration/latency and saturation.

</details>

<a id="rest-obs-005"></a>

<details>
<summary><strong>REST-OBS-005. What are RED metrics and latency percentiles?</strong></summary>

#### Short answer

RED means rate, errors and duration. Percentiles show latency distribution, such as p95 or p99.

#### Interview answer

Rate is how many requests arrive. Errors are failed responses or failures by policy. Duration is request latency. Percentiles show how slow the slowest fraction of requests are; p99 is the latency under which 99% of requests complete.

#### Deep dive

p95/p99 matter because users and upstream services feel tail latency, not averages.

#### Production angle

RED metrics are a good baseline dashboard for REST APIs and service dependencies.

#### Traps / caveats

- Define what counts as error.
- Percentiles need enough traffic to be meaningful.
- Separate endpoint-level and service-level views.

#### Optional Anki

Q: RED metrics?
A: Rate, errors, duration.

</details>

<a id="rest-obs-006"></a>

<details>
<summary><strong>REST-OBS-006. What is an SLO for an API endpoint?</strong></summary>

#### Short answer

An SLO is a target for service behavior, such as availability or latency, over a time window.

#### Interview answer

Example: 99.9% of `GET /orders/{id}` requests should complete successfully under 300 ms over 30 days. SLOs should reflect user experience and business importance.

#### Deep dive

SLOs often use error budgets. If the service burns too much budget, teams reduce risky changes or focus on reliability.

#### Production angle

Endpoint-specific SLOs help prioritize incidents and performance work.

#### Traps / caveats

- Do not set SLOs without measuring.
- Separate critical and non-critical endpoints.
- Exclude client errors only by clear policy.

#### Optional Anki

Q: SLO means?
A: Measurable reliability/latency target over time.

</details>

<a id="rest-obs-007"></a>

<details>
<summary><strong>REST-OBS-007. How do you detect an API error-rate spike?</strong></summary>

#### Short answer

Monitor status-code/error metrics by endpoint, client and deployment version, then alert on meaningful deviations.

#### Interview answer

I would check 5xx rate, selected 4xx rates, exception categories, recent deployments, dependency errors and affected endpoints. Compare with baseline and segment by version/region/tenant if safe.

#### Deep dive

A spike in 400 may be a bad client release; a spike in 500 may be server regression; a spike in 502/504 may be dependency failure.

#### Production angle

Dashboards should quickly show scope: all traffic, one endpoint, one client or one downstream.

#### Traps / caveats

- Do not alert on every small low-traffic blip.
- Use route templates to avoid metric cardinality.
- Include deployment markers.

#### Optional Anki

Q: First split for error spikes?
A: Endpoint, status class, client/version and dependency.

</details>

<a id="rest-obs-008"></a>

<details>
<summary><strong>🧠 REST-OBS-008. How would you debug increased API latency after deployment?</strong></summary>

#### Short answer

Compare before/after metrics, traces, logs, dependencies, database queries and resource saturation.

#### Interview answer

I would identify affected endpoints, check p95/p99 latency, inspect traces for where time is spent, compare database and downstream latency, review deployment/config changes, and check thread pools, connection pools and GC.

#### Deep dive

Latency can come from serialization, N+1 queries, new validation, cache misses, retries, downstream slowness or connection pool exhaustion.

#### Production angle

Use canaries and deployment markers to isolate regressions quickly.

#### Traps / caveats

- Average latency can look fine while p99 is bad.
- Retries can hide failures while increasing latency.
- Logs alone rarely show full timing.

#### Optional Anki

Q: Debug latency with?
A: Endpoint metrics plus traces and dependency/resource checks.

</details>

<a id="rest-obs-009"></a>

<details>
<summary><strong>REST-OBS-009. How should API access logs differ from application logs?</strong></summary>

#### Short answer

Access logs record request/response metadata; application logs record business and diagnostic events.

#### Interview answer

Access logs should include method, route, status, latency, request ID, client and response size. Application logs should explain meaningful internal events, decisions or errors.

#### Deep dive

Access logs are high-volume and should be structured and consistent. Application logs should avoid duplicating every request unless needed.

#### Production angle

Separating them helps security audit, traffic analysis and debugging without drowning business logs.

#### Traps / caveats

- Access logs can leak query strings.
- Application logs need context IDs.
- Do not log bodies by default.

#### Optional Anki

Q: Access log focus?
A: Request/response metadata and outcome.

</details>

<a id="rest-obs-010"></a>

<details>
<summary><strong>🧠 REST-OBS-010. How should health, readiness and liveness endpoints be designed?</strong></summary>

#### Short answer

Liveness says the process should be restarted; readiness says it can receive traffic; health may expose dependency status with appropriate access control.

#### Interview answer

Liveness should be simple and not depend on every downstream. Readiness should fail when the service cannot handle traffic, such as missing database connectivity or startup not complete. Detailed health should not be public if it exposes internals.

#### Deep dive

In Kubernetes, bad liveness checks can restart a slow but recoverable app repeatedly. Bad readiness checks can send traffic too early.

#### Production angle

Correct probes improve deployments and incident recovery.

#### Traps / caveats

- Do not expose secrets or internal topology publicly.
- Do not make liveness too strict.
- Readiness should reflect traffic-handling ability.

#### Optional Anki

Q: Readiness means?
A: Ready to receive traffic.

</details>

<details>
<summary><strong>🧠 REST-OBS-011. How should API contract changes be reviewed before release?</strong></summary>

#### Short answer

Review OpenAPI diff, compatibility, examples, error behavior, auth, clients, tests and rollout plan.

#### Interview answer

Before release, check whether the change is backward-compatible, whether generated clients change, whether error/status semantics changed, and whether docs/examples match implementation. Add or update contract and regression tests.

#### Deep dive

Review behavior, not only schemas. A response field meaning change or changed default sort can break clients even if OpenAPI still validates.

#### Production angle

Contract review prevents breaking partner, frontend, mobile and service clients.

#### Traps / caveats

- Generated spec diffs can hide important semantic changes.
- Old mobile clients may be impossible to upgrade quickly.
- Deprecation needs telemetry.

#### Optional Anki

Q: API contract review should include?
A: Compatibility, OpenAPI diff, tests, clients and rollout.

</details>
