# HATEOAS, hypermedia and discoverability

---

<a id="rest-hyp-001"></a>

<details>
<summary><strong>🧠 REST-HYP-001. What is HATEOAS?</strong></summary>

#### Short answer

HATEOAS means clients discover available actions through hypermedia links in responses.

#### Interview answer

Instead of hardcoding every next URL and action, a response includes links such as `self`, `cancel`, `payment` or `next`. The client can follow available transitions based on current resource state.

#### Deep dive

HATEOAS is part of strict REST's uniform interface idea, but many JSON APIs use documentation-driven clients instead.

#### Production angle

Hypermedia can help with workflow-heavy APIs but adds complexity and is not widely used deeply in many enterprise APIs.

#### Traps / caveats

- HATEOAS is not just adding a `self` link.
- Most generated clients still rely on OpenAPI/docs.
- Use it when it solves real client workflow problems.

#### Optional Anki

Q: HATEOAS means?
A: Hypermedia links describe available application state transitions.

</details>

<a id="rest-hyp-002"></a>

<details>
<summary><strong>🧠 REST-HYP-002. How can links and link relations help clients discover next actions?</strong></summary>

#### Short answer

Links can expose state-dependent actions so clients know what operations are currently valid.

#### Interview answer

An order response might include `cancel` only while the order is cancellable, and `pay` only while payment is pending. This reduces client-side guessing about workflow state.

#### Deep dive

Link relations need stable names and documentation. Clients should not infer semantics from URL text alone.

#### Production angle

Useful for public APIs with complex workflows where available actions depend on permissions and state.

#### Traps / caveats

- Links do not replace authorization.
- Missing link should not be the only server-side validation.
- Link relation names are part of the contract.

#### Optional Anki

Q: Benefit of action links?
A: They show valid next actions for current state.

</details>

<a id="rest-hyp-003"></a>

<details>
<summary><strong>🧠 REST-HYP-003. Why is HATEOAS rarely used deeply in many JSON APIs?</strong></summary>

#### Short answer

It adds complexity, and many teams prefer OpenAPI, generated clients and documented endpoints.

#### Interview answer

Deep hypermedia requires clients to interpret link relations and workflows dynamically. Many backend teams instead build stable documented APIs with generated clients and explicit contracts.

#### Deep dive

Hypermedia is more valuable when clients are generic or workflows are discoverable. It is less compelling when clients are tightly coordinated with the backend.

#### Production angle

Use HATEOAS pragmatically: links for navigation/status can be useful without fully committing to hypermedia-driven clients.

#### Traps / caveats

- Do not claim most JSON APIs are strict REST.
- Do not add links that nobody uses.
- Documentation still matters.

#### Optional Anki

Q: Why limited HATEOAS adoption?
A: Complexity and preference for documented/generated clients.

</details>

<a id="rest-hyp-004"></a>

<details>
<summary><strong>🧠 REST-HYP-004. How should a senior engineer discuss HATEOAS pragmatically in interviews?</strong></summary>

#### Short answer

Acknowledge it as part of strict REST, then discuss whether it adds enough value for the API's clients.

#### Interview answer

I would say HATEOAS is conceptually important, but many production JSON APIs are REST-style rather than strict REST. For most Java backend systems, consistent resources, methods, status codes, errors and OpenAPI contracts matter more day to day.

Use hypermedia when links genuinely simplify client workflows.

#### Deep dive

A senior answer avoids dogma. HATEOAS can be powerful, but it has client and documentation costs.

#### Production angle

Choose the level of hypermedia that your clients, tooling and team can maintain.

#### Traps / caveats

- Do not dismiss it as useless.
- Do not force it into every response.
- Be clear whether your API is strict REST or pragmatic REST-style HTTP.

#### Optional Anki

Q: Pragmatic HATEOAS stance?
A: Useful when it solves workflow discovery; not mandatory for every JSON API.

</details>
