# Pagination, filtering, sorting and search

---

<a id="rest-query-001"></a>

<details>
<summary><strong>REST-QUERY-001. How should pagination be designed in REST APIs?</strong></summary>

#### Short answer

Use explicit page size limits, stable ordering and clear metadata or cursors.

#### Interview answer

A paginated endpoint should define how clients request a slice, how many items are allowed, how ordering works and how clients know whether more data exists. Common styles are offset/limit and cursor-based pagination.

The API should have a maximum page size and deterministic sort order.

#### Deep dive

Offset pagination is simple but degrades for deep pages and can be inconsistent when data changes. Cursor/keyset pagination is better for large or changing datasets but more complex for clients.

#### Production angle

Unbounded list endpoints are a common source of latency, memory and database load incidents.

#### Traps / caveats

- Always define stable ordering.
- Enforce maximum page size server-side.
- Avoid returning total counts when they are expensive or misleading.

#### Optional Anki

Q: Two essentials of pagination?
A: Stable ordering and bounded page size.

</details>

<a id="rest-query-002"></a>

<details>
<summary><strong>REST-QUERY-002. What are the downsides of offset pagination?</strong></summary>

#### Short answer

Offset pagination becomes slow for deep pages and can skip or duplicate rows when data changes.

#### Interview answer

`LIMIT 50 OFFSET 100000` may force the database to scan and discard many rows. Also, if rows are inserted or deleted between requests, page 2 may not continue exactly after page 1.

#### Deep dive

Offset pagination is acceptable for small, stable datasets and admin screens. It is poor for very large tables or feeds where new data arrives continuously.

#### Production angle

Deep offset queries often appear as slow queries under real production data volumes.

#### Traps / caveats

- Indexes do not remove all deep-offset cost.
- Missing deterministic order makes results unreliable.
- Total counts can be expensive.

#### Optional Anki

Q: Main offset pagination problem?
A: Deep offsets are slow and unstable under changes.

</details>

<a id="rest-query-003"></a>

<details>
<summary><strong>🧠 REST-QUERY-003. What is the difference between cursor and keyset pagination?</strong></summary>

#### Short answer

Keyset pagination uses sort key predicates; cursor pagination exposes an opaque token that often encodes keyset state.

#### Interview answer

Keyset pagination asks for the next rows after a known sort key, such as `created_at < lastSeenCreatedAt`. Cursor pagination gives the client a token like `nextCursor`, hiding implementation details.

Cursor pagination is usually the public API shape; keyset is often the database technique behind it.

#### Deep dive

Cursors can include sort values, direction, filters, tenant, page size and signatures to prevent tampering.

#### Production angle

Cursor/keyset pagination performs better for large datasets and avoids many offset consistency problems.

#### Traps / caveats

- Sort order must be unique or include a tie-breaker.
- Cursor tokens should be opaque.
- Changing filters invalidates old cursors.

#### Optional Anki

Q: Cursor vs keyset?
A: Cursor is API token; keyset is sort-key-based paging technique.

</details>

<a id="rest-query-004"></a>

<details>
<summary><strong>REST-QUERY-004. Why is stable ordering required for reliable pagination?</strong></summary>

#### Short answer

Without stable ordering, items can move between pages, causing duplicates or missing records.

#### Interview answer

Pagination needs deterministic ordering. Sorting only by a non-unique column like `createdAt` can be unstable if many rows share the same timestamp. Add a tie-breaker such as ID.

#### Deep dive

Stable ordering is required for both offset and cursor pagination. Cursor pagination especially needs a unique ordering tuple to continue correctly.

#### Production angle

Unstable paging creates user-visible bugs in feeds, exports, admin lists and batch processing.

#### Traps / caveats

- Database default order is not stable.
- Sorting by mutable columns can move items.
- Ties need deterministic tie-breakers.

#### Optional Anki

Q: Why add ID as sort tie-breaker?
A: To make pagination order deterministic.

</details>

<a id="rest-query-006"></a>

<details>
<summary><strong>REST-QUERY-006. How should sorting and filtering parameters be designed?</strong></summary>

#### Short answer

Expose a small documented set of filter and sort fields with validation and clear operators.

#### Interview answer

Parameters should be explicit and stable, for example `status=PAID`, `createdFrom=...`, `sort=-createdAt,id`. Avoid exposing arbitrary SQL-like expressions unless you are building a carefully controlled query language.

#### Deep dive

Filtering should map to indexes and authorization rules. Sort fields should be whitelisted and documented with null handling and tie-breaker behavior.

#### Production angle

Unbounded flexible filtering can create slow queries and data leaks.

#### Traps / caveats

- Do not trust client sort field names directly in SQL.
- Validate enum and date filters.
- Limit combinations that create expensive query plans.

#### Optional Anki

Q: How design filter/sort params?
A: Whitelist documented fields and validate operators.

</details>

<a id="rest-query-007"></a>

<details>
<summary><strong>🧠 REST-QUERY-007. How would you design optional filters without creating unmaintainable endpoints?</strong></summary>

#### Short answer

Use one list/search endpoint with documented optional filters, backed by explicit query construction and limits.

#### Interview answer

Avoid creating many endpoints like `/paidOrders`, `/recentPaidOrders`, `/recentPaidOrdersByCustomer`. Use `GET /orders?status=PAID&customerId=...&createdFrom=...` and validate supported combinations.

#### Deep dive

Implementation can use a query builder/specification pattern, but the public contract should remain understandable and indexed for common use cases.

#### Production angle

Filter design must be reviewed with database indexes and expected cardinality.

#### Traps / caveats

- Optional filters can create accidental full scans.
- Authorization must be integrated into the query.
- Do not expose internal column names as public API.

#### Optional Anki

Q: How avoid endpoint explosion?
A: Use documented optional filters with validated combinations.

</details>

<a id="rest-query-008"></a>

<details>
<summary><strong>🧠 REST-QUERY-008. How do API filtering choices affect database indexes?</strong></summary>

#### Short answer

Filters and sort order determine which indexes are useful; flexible APIs can easily produce unindexed queries.

#### Interview answer

If clients filter by `tenantId`, `status` and sort by `createdAt`, the database likely needs an index aligned with those predicates and ordering. Allowing arbitrary filters makes indexing impossible for every combination.

#### Deep dive

Low-cardinality filters, range predicates and sort direction affect compound index usefulness. Pagination strategy also changes index needs.

#### Production angle

API design and database design must be reviewed together for high-traffic list endpoints.

#### Traps / caveats

- Adding an API filter is a performance change.
- Indexes have write and storage costs.
- Authorization predicates should be part of query planning.

#### Optional Anki

Q: Why review filters with DB indexes?
A: Filters shape query plans and production latency.

</details>

<a id="rest-query-010"></a>

<details>
<summary><strong>REST-QUERY-010. How should APIs limit page size and prevent expensive filter combinations?</strong></summary>

#### Short answer

Enforce maximum page sizes, whitelist filters/sorts, reject unsupported combinations and monitor slow queries.

#### Interview answer

The client can request `limit`, but the server decides the maximum. Expensive filters should be rejected or require asynchronous export/report flows. Sort and filter fields should be whitelisted.

#### Deep dive

For high-cardinality datasets, cursor pagination and precomputed/search indexes may be required. Returning "everything" should not be an API feature.

#### Production angle

Limits prevent accidental denial of service from dashboards, exports or poorly written clients.

#### Traps / caveats

- Do not rely on frontend limits only.
- Do not compute total counts blindly.
- Watch cardinality of metrics labels for filter values.

#### Optional Anki

Q: Who enforces max page size?
A: The server.

</details>

<a id="rest-query-011"></a>

<details>
<summary><strong>🧠 REST-QUERY-011. How should cursor tokens be made opaque and stable?</strong></summary>

#### Short answer

Cursor tokens should hide implementation details, encode enough paging state, and be signed or otherwise protected from tampering.

#### Interview answer

A cursor may encode last sort values, filters, direction, tenant and page size. Clients should treat it as an opaque string and pass it back unchanged. The server should reject invalid or mismatched cursors.

#### Deep dive

Opaque cursors let the server change internal pagination without breaking clients. Signing prevents clients from modifying sort keys or tenant scope.

#### Production angle

Stable cursors are important for exports, feeds and APIs with large datasets.

#### Traps / caveats

- Do not expose raw SQL offsets or internal IDs unnecessarily.
- Cursor validity may depend on filters and sort.
- Expiration policy should be documented.

#### Optional Anki

Q: How should clients treat cursors?
A: As opaque tokens.

</details>
