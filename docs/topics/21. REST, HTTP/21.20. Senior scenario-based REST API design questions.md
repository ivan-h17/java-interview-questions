# Senior scenario-based REST/API design questions

---

<a id="rest-scenario-001"></a>

<details>
<summary><strong>REST-SCENARIO-001. Design a REST API for creating an order with idempotent retries.</strong></summary>

#### Short answer

Use `POST /orders` with a required idempotency key, durable deduplication and consistent replay of the original result.

#### Interview answer

The client sends order details and `Idempotency-Key`. The server stores the key with request fingerprint and order creation result in the same transaction. If the client retries with the same key, return the original order response instead of creating another order.

#### Deep dive

Handle in-progress keys, succeeded keys and failed keys. Reject same key with different payload.

#### Production angle

This protects against duplicate orders after network timeouts, double-clicks or client retries.

#### Traps / caveats

- Unique constraint on idempotency key is required.
- Do not store key only in memory.
- Define key scope and retention.

#### Optional Anki

Q: Key order-create retry defense?
A: Transactional idempotency key storage.

</details>

<a id="rest-scenario-002"></a>

<details>
<summary><strong>REST-SCENARIO-002. Design an API for payment initiation where clients may retry requests.</strong></summary>

#### Short answer

Use idempotency keys, durable payment command state and provider-side idempotency where available.

#### Interview answer

Expose `POST /payments` or `/payment-intents`. Require idempotency key and store payment status: accepted, processing, succeeded, failed. If calling a payment provider, pass its idempotency key too and reconcile ambiguous outcomes.

#### Deep dive

Payment APIs should often return a payment resource with status rather than assuming immediate success.

#### Production angle

The design must prevent double charges and support reconciliation after provider timeouts.

#### Traps / caveats

- Timeout does not mean payment failed.
- Retrying without idempotency can charge twice.
- Audit logs are mandatory.

#### Optional Anki

Q: Payment timeout is what kind of outcome?
A: Ambiguous until checked/reconciled.

</details>

<a id="rest-scenario-003"></a>

<details>
<summary><strong>REST-SCENARIO-003. Design a REST API for long-running report generation.</strong></summary>

#### Short answer

Use `POST /reports` returning 202 and a report job resource.

#### Interview answer

The client submits report parameters. The API validates, creates a report job, returns `202 Accepted` with `Location: /report-jobs/{id}`. Clients poll job status and download the result when ready.

#### Deep dive

Store parameters, owner, status, progress, result URL and failure details. Use idempotency keys if duplicate submissions are likely.

#### Production angle

Report generation should run in workers, not request threads.

#### Traps / caveats

- Enforce parameter and date-range limits.
- Authorize both job status and result download.
- Clean up old artifacts.

#### Optional Anki

Q: Long report response?
A: 202 plus job resource.

</details>

<a id="rest-scenario-004"></a>

<details>
<summary><strong>REST-SCENARIO-004. Design a REST API for uploading and processing large files.</strong></summary>

#### Short answer

Use bounded upload, durable storage, validation/scanning and an asynchronous processing job.

#### Interview answer

For moderate files, accept multipart upload with metadata and strict limits. For large files, issue a pre-signed object-storage upload URL, then create a processing job. Return status and result endpoints.

#### Deep dive

Track checksum, size, content type, owner, scan status and processing state.

#### Production angle

Avoid buffering large files through the JVM and protect disk/memory.

#### Traps / caveats

- Do not trust filename or MIME type.
- Scan before use.
- Clean up failed/abandoned uploads.

#### Optional Anki

Q: Large upload pattern?
A: Object storage plus async processing job.

</details>

<a id="rest-scenario-005"></a>

<details>
<summary><strong>REST-SCENARIO-005. Design a REST API for bulk user import with partial failures.</strong></summary>

#### Short answer

Use an import job with per-row validation and result reporting.

#### Interview answer

Client uploads a file or submits import data. The API creates an import job and returns 202. The result resource reports counts and per-row errors, allowing the client to fix only failed rows.

#### Deep dive

Process in chunks, enforce limits and make row operations idempotent where possible.

#### Production angle

Bulk imports need observability, replay and support tooling.

#### Traps / caveats

- Do not fail the whole import without useful diagnostics unless atomicity is required.
- Avoid unbounded transaction size.
- Validate tenant/authorization per imported entity.

#### Optional Anki

Q: Bulk import result should include?
A: Per-item successes/failures and error details.

</details>

<a id="rest-scenario-006"></a>

<details>
<summary><strong>REST-SCENARIO-006. Design a paginated API for a table with hundreds of millions of rows.</strong></summary>

#### Short answer

Use cursor/keyset pagination, stable indexed ordering and strict filters/page limits.

#### Interview answer

Avoid deep offset pagination. Choose an indexed sort key, add a unique tie-breaker, return opaque next cursor and enforce maximum page size. Restrict filters to indexed fields.

#### Deep dive

For exports, use asynchronous jobs instead of forcing users to page through huge datasets interactively.

#### Production angle

Design must be reviewed with database indexes and query plans.

#### Traps / caveats

- Total counts may be expensive.
- Mutable sort fields can move records.
- Cursor tokens must include filter/sort context.

#### Optional Anki

Q: Large table pagination choice?
A: Cursor/keyset with stable indexed order.

</details>

<a id="rest-scenario-007"></a>

<details>
<summary><strong>REST-SCENARIO-007. A client reports duplicate orders after network timeouts. How would you debug and fix it?</strong></summary>

#### Short answer

Check retry behavior and idempotency; fix with durable idempotency keys and unique constraints.

#### Interview answer

I would inspect logs by request ID/client, compare timestamps, check whether timeouts happened after commit, and see if retries used the same idempotency key. Then I would add/repair idempotency handling and database uniqueness.

#### Deep dive

Network timeout means client did not receive response, not that server failed.

#### Production angle

Mitigate immediately by disabling unsafe retries or requiring keys for order creation.

#### Traps / caveats

- Do not just increase timeout.
- Deduplicate existing bad data carefully.
- Add monitoring for duplicate attempts.

#### Optional Anki

Q: Timeout after POST means?
A: Outcome is ambiguous.

</details>

<a id="rest-scenario-008"></a>

<details>
<summary><strong>REST-SCENARIO-008. An API latency p99 increased after deployment. What would you check?</strong></summary>

#### Short answer

Check endpoint metrics, traces, database queries, downstream calls, serialization, thread/connection pools and deployment/config changes.

#### Interview answer

First identify affected endpoints and traffic segments. Then use traces to find where latency moved: app code, DB, downstream, gateway or serialization. Compare with pre-deployment metrics.

#### Deep dive

Look for new N+1 queries, cache misses, retries, pool exhaustion, GC pressure and changed payload size.

#### Production angle

Use rollback or feature flags if user impact is high.

#### Traps / caveats

- p99 can rise while average remains stable.
- Retries may hide errors but increase latency.
- One client can skew tail latency.

#### Optional Anki

Q: First tool for p99 investigation?
A: Endpoint metrics plus traces.

</details>

<a id="rest-scenario-009"></a>

<details>
<summary><strong>REST-SCENARIO-009. Your downstream dependency returns many 503s. How should your API behave?</strong></summary>

#### Short answer

Classify dependency criticality, retry cautiously, degrade if safe, or return an appropriate 503/502 with retry guidance.

#### Interview answer

If the dependency is required, fail fast with a clear error and maybe `Retry-After`. If optional, return degraded data with telemetry. Avoid aggressive retries that make the dependency worse.

#### Deep dive

Circuit breakers and bulkheads can protect your service while the dependency recovers.

#### Production angle

Alert on dependency error rate and communicate impact through status/incident channels if needed.

#### Traps / caveats

- Do not hide critical correctness failures with fallback.
- Do not retry non-idempotent calls blindly.
- Preserve correlation IDs across calls.

#### Optional Anki

Q: Downstream 503 response strategy?
A: Fail fast or degrade safely, with bounded retries.

</details>

<a id="rest-scenario-010"></a>

<details>
<summary><strong>REST-SCENARIO-010. A mobile client must support old API versions for two years. How would you design evolution?</strong></summary>

#### Short answer

Use backward-compatible changes, explicit versioning when needed, telemetry and long deprecation windows.

#### Interview answer

Mobile clients update slowly, so avoid breaking changes. Add fields instead of replacing, keep old endpoints alive, version major changes, and track client versions in telemetry.

#### Deep dive

Feature flags can let the server support old and new behavior during migration.

#### Production angle

Support and security fixes must cover old versions until sunset.

#### Traps / caveats

- Do not require new request fields suddenly.
- Unknown enum values can break old clients.
- Document sunset dates early.

#### Optional Anki

Q: Mobile API evolution rule?
A: Assume old clients live for a long time.

</details>

<a id="rest-scenario-011"></a>

<details>
<summary><strong>REST-SCENARIO-011. A GET endpoint is expensive and heavily used. How would you optimize it?</strong></summary>

#### Short answer

Measure first, then improve query/indexing, reduce payload, add caching/ETags and consider precomputed read models.

#### Interview answer

I would inspect traces and query plans. If DB-bound, add indexes or projections. If payload-bound, reduce fields or paginate. If repeated, use HTTP caching, application cache or CDN if data is safe.

#### Deep dive

For very expensive computed data, precompute asynchronously and serve a read model.

#### Production angle

Optimize without breaking correctness or leaking cached personalized data.

#### Traps / caveats

- Caching is not safe for every GET.
- Avoid unbounded cache keys.
- Do not optimize without p95/p99 and load data.

#### Optional Anki

Q: First optimization step?
A: Measure where time is spent.

</details>

<a id="rest-scenario-012"></a>

<details>
<summary><strong>REST-SCENARIO-012. A DELETE endpoint sometimes returns 404 on retries. Is that a problem?</strong></summary>

#### Short answer

Not necessarily. DELETE can be idempotent even if repeated calls return different status codes.

#### Interview answer

If the first DELETE succeeded but response was lost, a retry may find the resource already absent and return 404. The final intended state is still "deleted". Clients should not treat this automatically as failure unless API policy says so.

#### Deep dive

Some APIs return 204 for already-absent resources to simplify retrying. Others use 404 to signal absence. Document the policy.

#### Production angle

Retries after timeouts need clear interpretation to avoid false incidents.

#### Traps / caveats

- Idempotent does not mean identical response.
- 404 can also mean wrong ID or unauthorized masking.
- Async deletes may need 202/status.

#### Optional Anki

Q: DELETE retry 404 always problem?
A: No; final state may already be deleted.

</details>

<a id="rest-scenario-013"></a>

<details>
<summary><strong>REST-SCENARIO-013. How would you design tenant isolation for a REST API?</strong></summary>

#### Short answer

Resolve tenant context securely, enforce it in authorization and data queries, and test cross-tenant denial.

#### Interview answer

Tenant can come from token claims, subdomain, path or header from trusted infrastructure. The service must verify the caller belongs to that tenant and include tenant predicates in data access.

#### Deep dive

Do not rely only on client-supplied tenant IDs. Tenant context should be immutable through the request and audited.

#### Production angle

Tenant isolation bugs are high-severity data breaches.

#### Traps / caveats

- Tenant in URL is not proof of access.
- Background jobs need tenant context too.
- Cache keys must include tenant.

#### Optional Anki

Q: Tenant isolation must be enforced where?
A: Authorization and data queries.

</details>

<a id="rest-scenario-014"></a>

<details>
<summary><strong>REST-SCENARIO-014. A user can access another user's data by changing an ID in the URL. What went wrong?</strong></summary>

#### Short answer

The API has broken object-level authorization.

#### Interview answer

Authentication proved the user identity, but the service failed to check whether that identity can access the specific object ID. Fix by enforcing ownership/tenant checks in service/data access and adding negative tests.

#### Deep dive

Opaque IDs reduce enumeration but do not fix authorization.

#### Production angle

This is a serious security incident requiring impact analysis, logs and possible disclosure process.

#### Traps / caveats

- Do not fix only in the frontend.
- Do not assume random UUIDs are enough.
- Check list/search endpoints too.

#### Optional Anki

Q: Changing URL ID exposes data means?
A: Broken object-level authorization.

</details>

<a id="rest-scenario-015"></a>

<details>
<summary><strong>REST-SCENARIO-015. How would you design a consistent error model across microservices?</strong></summary>

#### Short answer

Standardize status mapping, Problem Details shape, domain error codes, correlation IDs and logging rules.

#### Interview answer

Define shared guidelines: validation errors, auth errors, conflicts, dependency failures and unexpected failures. Use Problem Details or a similar consistent structure and stable machine-readable codes.

#### Deep dive

Keep domain-specific errors extensible without forcing every service into one giant enum.

#### Production angle

Consistent errors simplify clients, gateways, observability and support.

#### Traps / caveats

- Do not expose internal exception names.
- Do not hide all errors behind 500.
- Keep backward compatibility of error codes.

#### Optional Anki

Q: Error model should standardize?
A: Status, shape, codes, correlation and sanitization.

</details>

<a id="rest-scenario-016"></a>

<details>
<summary><strong>REST-SCENARIO-016. How would you prevent API clients from accidentally causing a retry storm?</strong></summary>

#### Short answer

Provide retry guidance, enforce rate limits, require idempotency for unsafe operations and design client policies with backoff/jitter.

#### Interview answer

The API should return clear retryable vs non-retryable errors, use `Retry-After`, and avoid encouraging immediate retries. SDKs should implement bounded retries with jitter and deadlines.

#### Deep dive

Server-side load shedding and client-side retry budgets prevent retry amplification.

#### Production angle

Retry storms can turn a partial outage into a full outage.

#### Traps / caveats

- Multiple retry layers multiply traffic.
- Non-idempotent retries need keys.
- Monitor retry attempts separately.

#### Optional Anki

Q: Retry storm prevention?
A: Bounded retries, backoff/jitter, retry budgets and idempotency.

</details>

<a id="rest-scenario-017"></a>

<details>
<summary><strong>REST-SCENARIO-017. How would you design graceful degradation when a recommendation service is down?</strong></summary>

#### Short answer

Treat recommendations as optional if business allows, return core data plus degraded/empty recommendations and record telemetry.

#### Interview answer

For a product page, core product/price may be required, while recommendations are optional. If recommendation calls fail, return the page without them or with cached fallback, and expose internal metrics/logs.

#### Deep dive

The API response can include metadata indicating partial/degraded data if clients need to know.

#### Production angle

Graceful degradation protects user-critical flows while preserving observability.

#### Traps / caveats

- Do not degrade correctness-critical data like price or permissions.
- Fallbacks can hide incidents if not monitored.
- Cached fallback must respect authorization.

#### Optional Anki

Q: Fallback safe for?
A: Optional, non-correctness-critical data.

</details>

<a id="rest-scenario-018"></a>

<details>
<summary><strong>REST-SCENARIO-018. How would you handle read-after-write consistency when reads go to replicas?</strong></summary>

#### Short answer

Use primary reads for critical immediate reads, session consistency tokens, delayed polling or explicit eventual-consistency UX.

#### Interview answer

After creating an order, redirecting to a replica-backed read may return 404 until replication catches up. Options include reading the created resource from primary briefly, returning the representation in the write response, or exposing status/polling until visible.

#### Deep dive

Consistency choice should match product expectations. Stronger read-after-write consistency costs capacity or latency.

#### Production angle

Replica lag causes intermittent user-visible bugs and support issues.

#### Traps / caveats

- Do not assume replicas are current.
- Search indexes may lag too.
- Communicate pending states clearly.

#### Optional Anki

Q: Replica read-after-write risk?
A: Newly written data may not be visible yet.

</details>

<a id="rest-scenario-019"></a>

<details>
<summary><strong>REST-SCENARIO-019. How would you review a new REST API before it is released publicly?</strong></summary>

#### Short answer

Review resource design, method/status semantics, payloads, security, compatibility, OpenAPI, tests, observability and operations.

#### Interview answer

I would check if URLs model resources, methods are correct, errors are consistent, DTOs avoid leaks, pagination/limits exist, authorization is tested, OpenAPI examples are accurate, and rollout/deprecation plans exist.

#### Deep dive

Public APIs need stricter backward compatibility and documentation than internal experimental endpoints.

#### Production angle

Once public clients integrate, changing contracts becomes expensive.

#### Traps / caveats

- Do not release without negative security tests.
- Include rate limits and support diagnostics.
- Review generated client impact.

#### Optional Anki

Q: Public API review areas?
A: Contract, semantics, security, compatibility, tests and operations.

</details>

<a id="rest-scenario-020"></a>

<details>
<summary><strong>REST-SCENARIO-020. A generated API client breaks after a REST API change. How would you investigate and prevent it?</strong></summary>

#### Short answer

Compare OpenAPI diffs, generated code changes and actual response/request behavior; prevent with compatibility checks and contract tests.

#### Interview answer

I would identify the breaking diff: removed/renamed field, changed type, new required field, enum change, status change or missing schema update. Then verify deployed behavior against OpenAPI and run old client tests.

#### Deep dive

Generated clients are strict about schemas, so changes that hand-written clients tolerate may break generated code.

#### Production angle

Add CI checks for OpenAPI diff severity and run consumer contract tests before release.

#### Traps / caveats

- Generated client break may reveal real contract drift.
- Adding enum values can break exhaustive switches.
- Do not fix by weakening all schemas blindly.

#### Optional Anki

Q: Generated client break prevention?
A: OpenAPI diff checks and consumer contract tests.

</details>
