<a id="rest-test-001"></a>

<details>
<summary><strong>REST-TEST-001. How do you test REST controllers in Spring Boot?</strong></summary>

#### Short answer

Use focused controller tests for HTTP behavior and integration tests for full request flow.

#### Interview answer

For controller behavior, use `@WebMvcTest` with MockMvc or WebTestClient, mocking service dependencies. Test routing, validation, status codes, response body and exception mapping.

For full wiring, use `@SpringBootTest` with real configuration and dependencies where needed.

#### Deep dive

Do not test all business logic through controllers. Keep service tests separate and use API tests to verify the HTTP contract.

#### Production angle

Controller tests catch accidental API contract regressions before clients see them.

#### Traps / caveats

- MockMvc slice tests do not prove database or security integration unless configured.
- Test error responses, not only 200.
- Keep fixtures realistic.

#### Optional Anki

Q: What should REST controller tests verify?
A: HTTP mapping, validation, status, body and error handling.

</details>

<details>
<summary><strong>REST-TEST-002. What is the difference between unit, slice and integration tests for REST APIs?</strong></summary>

#### Short answer

Unit tests isolate logic, slice tests test one framework layer, and integration tests test multiple real components together.

#### Interview answer

A unit test might test a service method. A web slice test tests controllers, validation and exception handling with mocked services. An integration test starts most or all application context and may use real database/test containers.

#### Deep dive

Use the smallest test that gives confidence. Not every endpoint needs a full `@SpringBootTest`, but critical flows should be tested end to end.

#### Production angle

Balanced test pyramids give fast feedback and catch wiring/contract bugs.

#### Traps / caveats

- Too many full integration tests slow CI.
- Too many mocks miss real serialization/security behavior.
- Slice tests need explicit security configuration if security matters.

#### Optional Anki

Q: Web slice test focus?
A: Spring MVC/controller layer behavior.

</details>

<a id="rest-test-003"></a>

<details>
<summary><strong>REST-TEST-003. What are @WebMvcTest and MockMvc used for?</strong></summary>

#### Short answer

`@WebMvcTest` loads the MVC slice; MockMvc performs HTTP-like requests against controllers without starting a real server.

#### Interview answer

They are used to test controller mappings, validation, JSON serialization, exception handlers and response status/body quickly. Service dependencies are usually mocked.

#### Deep dive

MockMvc uses the Spring MVC infrastructure, so it catches many framework-level issues while staying faster than full integration tests.

#### Production angle

Good MockMvc tests protect API contracts during refactoring.

#### Traps / caveats

- It is not a full application test.
- Filters/security may need explicit inclusion.
- It does not test real network behavior.

#### Optional Anki

Q: MockMvc starts real server?
A: No, it tests MVC infrastructure in-process.

</details>

<a id="rest-test-004"></a>

<details>
<summary><strong>REST-TEST-004. When should you use @SpringBootTest for API tests?</strong></summary>

#### Short answer

Use it when you need full application wiring, real configuration, security, persistence or cross-layer behavior.

#### Interview answer

`@SpringBootTest` is useful for critical API flows where controller, service, security, transactions, database and serialization must work together. Pair it with Testcontainers for realistic dependencies.

#### Deep dive

It is slower than slice tests, so reserve it for flows where integration risk matters.

#### Production angle

Full integration tests catch configuration and wiring bugs that mocks miss.

#### Traps / caveats

- Keep test data isolated.
- Avoid relying on test order.
- Full context tests can become slow and flaky if overused.

#### Optional Anki

Q: `@SpringBootTest` is best for?
A: Full application integration behavior.

</details>

<a id="rest-test-005"></a>

<details>
<summary><strong>REST-TEST-005. How do you test validation and exception handling?</strong></summary>

#### Short answer

Send invalid requests and assert status, Problem Details/error shape, field errors and sanitized messages.

#### Interview answer

Tests should cover missing required fields, invalid formats, invalid enum values, malformed JSON, business conflicts and unexpected exceptions. Assert not only status codes but also stable error codes and field paths.

#### Deep dive

Malformed JSON and semantic validation are different cases and may map to different error responses.

#### Production angle

Consistent error tests prevent clients from breaking when exception handling changes.

#### Traps / caveats

- Do not assert fragile full text if localization may change.
- Ensure sensitive values are not echoed.
- Test nested field paths.

#### Optional Anki

Q: Validation tests should assert?
A: Status plus structured error details.

</details>

<a id="rest-test-006"></a>

<details>
<summary><strong>REST-TEST-006. How do you test authorization rules for REST endpoints?</strong></summary>

#### Short answer

Test allowed and denied cases for roles, scopes, ownership and tenant boundaries.

#### Interview answer

For each protected endpoint, test unauthenticated, authenticated-but-forbidden and authorized cases. For object-level access, test that user A cannot access user B's resource.

#### Deep dive

Use Spring Security test support for mock users/tokens, and integration tests for critical real token/authority mapping.

#### Production angle

Authorization tests catch BOLA/IDOR bugs before release.

#### Traps / caveats

- Testing only happy-path admin access is not enough.
- Route security and service-level authorization both need coverage.
- Test filtering endpoints for data leaks.

#### Optional Anki

Q: Key authorization test?
A: One user cannot access another user's resource.

</details>

<a id="rest-test-007"></a>

<details>
<summary><strong>REST-TEST-007. How do you test pagination and filtering?</strong></summary>

#### Short answer

Test ordering, boundaries, invalid parameters, max page size, filter combinations and consistency.

#### Interview answer

Create data with known ordering and ties. Assert page contents, next cursor/metadata, max size enforcement, invalid sort rejection and expected filter behavior.

#### Deep dive

For cursor pagination, test that cursor tokens are opaque and cannot be reused with different filters if your API forbids it.

#### Production angle

Pagination bugs cause duplicate/missing rows in exports and user-visible lists.

#### Traps / caveats

- Do not rely on database default order.
- Include tie-breaker cases.
- Test authorization combined with filters.

#### Optional Anki

Q: Pagination test must include?
A: Stable ordering and boundary cases.

</details>

<a id="rest-test-008"></a>

<details>
<summary><strong>🧠 REST-TEST-008. How do you test idempotency, retries and timeouts?</strong></summary>

#### Short answer

Simulate duplicate requests, transient failures and slow dependencies, then assert no duplicate side effects and bounded time.

#### Interview answer

For idempotency, send the same key twice and assert the same result and one business record. For retries/timeouts, use fake servers like WireMock/MockWebServer and virtual time where possible.

#### Deep dive

Concurrency tests should cover two requests with the same idempotency key arriving simultaneously.

#### Production angle

These tests prevent duplicate orders/payments and retry-induced outages.

#### Traps / caveats

- Avoid sleeping in tests.
- Assert attempt count and deadline.
- Test non-retryable errors too.

#### Optional Anki

Q: Idempotency test assertion?
A: Duplicate request returns same result with one side effect.

</details>

<details>
<summary><strong>REST-TEST-009. What are contract testing and consumer-driven contract testing?</strong></summary>

#### Short answer

Contract testing verifies provider and consumer agree on API behavior; consumer-driven contracts are defined from consumer expectations.

#### Interview answer

Provider tests ensure the API satisfies a contract. Consumer tests ensure clients use the contract correctly. Consumer-driven contracts, such as Pact-style workflows, let consumers publish expected interactions that providers verify.

#### Deep dive

Contracts should include status codes, headers, schemas and important error cases, not only happy paths.

#### Production angle

Contract tests reduce deployment risk between independently released services.

#### Traps / caveats

- Contracts can become too narrow if they only cover one example.
- They do not replace integration or security tests.
- Version contract changes carefully.

#### Optional Anki

Q: Consumer-driven contract means?
A: Consumer expectations become provider-verifiable contracts.

</details>

<a id="rest-test-010"></a>

<details>
<summary><strong>REST-TEST-010. How do WireMock and Testcontainers help test REST APIs?</strong></summary>

#### Short answer

WireMock simulates HTTP dependencies; Testcontainers runs real infrastructure dependencies in containers.

#### Interview answer

WireMock helps test REST clients against controlled responses, delays and errors. Testcontainers helps run real PostgreSQL, Kafka, Redis or other dependencies for integration tests.

#### Deep dive

Use WireMock for deterministic HTTP behavior and Testcontainers when real dependency behavior matters.

#### Production angle

They catch integration issues without relying on shared unstable test environments.

#### Traps / caveats

- Keep stubs aligned with real contracts.
- Containers can slow CI if overused.
- Simulated dependencies do not cover every production failure mode.

#### Optional Anki

Q: WireMock is used for?
A: Simulating HTTP services in tests.

</details>

<details>
<summary><strong>🧠 REST-TEST-011. How would you test backward compatibility, OpenAPI contracts, rate limiting and large payloads?</strong></summary>

#### Short answer

Use contract/schema checks, regression fixtures, controlled limit tests and large-payload integration tests.

#### Interview answer

Backward compatibility can be tested by validating old request/response examples and OpenAPI diffs. Rate limiting tests should verify 429 and `Retry-After`. Large payload tests should verify limits, streaming behavior and no memory-heavy buffering.

#### Deep dive

OpenAPI validation should include errors and security, not just 200 responses.

#### Production angle

These tests protect clients and prevent resource-exhaustion regressions.

#### Traps / caveats

- Do not make large-payload tests flaky or too slow.
- Validate generated clients after contract changes.
- Rate-limit tests need deterministic clocks/counters.

#### Optional Anki

Q: OpenAPI contract tests should include?
A: Success, errors, schemas, headers and security behavior.

</details>
