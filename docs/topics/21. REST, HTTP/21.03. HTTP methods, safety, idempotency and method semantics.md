# HTTP methods, safety, idempotency and method semantics

---

<a id="http-method-002"></a>

<details>
<summary><strong>HTTP-METHOD-002. What is the difference between GET and POST?</strong></summary>

#### Short answer

GET retrieves a resource representation; POST submits data for processing or creates a subordinate resource when the server chooses the result URI.

#### Interview answer

GET should be safe and usually cacheable. It should not perform business state changes. POST is used for commands, form submissions, searches with complex bodies, or creation where the server assigns the resource identity.

GET parameters are visible in URLs and logs, so they are not suitable for secrets or large payloads.

#### Deep dive

The difference is semantic, not just "GET has no body" and "POST has body". Some frameworks technically accept unusual combinations, but clients, proxies and caches rely on normal method semantics.

#### Production angle

Wrong method choice breaks retries, caching, CDN behavior, monitoring and client expectations.

#### Traps / caveats

- Do not use GET for state-changing operations.
- Do not put sensitive data in query parameters.
- POST is not idempotent unless the application designs it to be.

#### Optional Anki

Q: GET vs POST?
A: GET retrieves; POST submits/processes and may create server-assigned resources.

</details>

<a id="http-method-003"></a>

<details>
<summary><strong>HTTP-METHOD-003. What is the difference between PUT and PATCH?</strong></summary>

#### Short answer

PUT replaces or creates a resource at a known URI; PATCH applies a partial modification.

#### Interview answer

PUT usually means the client sends the desired complete representation for the resource. Repeating the same PUT should produce the same resulting resource state.

PATCH is for partial updates, such as changing only `status` or `email`. Its semantics depend on the patch format and API contract, so it needs careful handling of omitted fields, null values and concurrency.

#### Deep dive

PATCH can be idempotent or non-idempotent depending on operation. Setting `status=ACTIVE` is idempotent; "increment balance by 10" is not.

#### Production angle

Partial updates are common sources of lost updates, accidental nulling and authorization bugs. Use validation and optimistic locking for important resources.

#### Traps / caveats

- PUT should not silently merge partial bodies unless documented.
- PATCH needs clear null-vs-absent semantics.
- Partial updates still require authorization per changed field.

#### Optional Anki

Q: PUT vs PATCH?
A: PUT replaces known resource state; PATCH partially modifies it.

</details>

<a id="http-method-004"></a>

<details>
<summary><strong>HTTP-METHOD-004. What is the difference between PUT and POST for resource creation?</strong></summary>

#### Short answer

Use POST when the server chooses the new resource URI; use PUT when the client chooses the target URI.

#### Interview answer

`POST /orders` is common for order creation because the server creates a new order and returns `201 Created` with `Location: /orders/{id}`. `PUT /users/{username}` can be appropriate when the client chooses the stable identifier and wants to create or replace that resource.

#### Deep dive

PUT is idempotent by method semantics: repeated identical PUT requests to the same URI should leave the same state. POST creation is not naturally idempotent unless protected by an idempotency key or unique business constraint.

#### Production angle

Creation semantics matter for retries after timeouts. POST without idempotency can create duplicates if the client retries after the server already committed.

#### Traps / caveats

- Do not use PUT when the server actually creates a different URI every time.
- POST can be safe to retry only with explicit deduplication.
- `201 Created` should usually include `Location`.

#### Optional Anki

Q: POST vs PUT for create?
A: POST server-chosen URI; PUT client-chosen target URI.

</details>

<a id="http-method-005"></a>

<details>
<summary><strong>HTTP-METHOD-005. What is the difference between safe and idempotent methods?</strong></summary>

#### Short answer

Safe means no intended state change; idempotent means repeating the same request has the same intended effect as once.

#### Interview answer

GET is safe because it should only retrieve. PUT and DELETE are idempotent because repeating them should not create additional intended effects, even though they change state.

POST is usually neither safe nor idempotent, but it can be made idempotent at the application level with idempotency keys.

#### Deep dive

Idempotent does not mean the response is identical every time. A DELETE may return 204 first and 404 later, while the intended final state still remains "resource absent".

#### Production angle

Safety and idempotency drive retry policy, load balancer behavior, crawlers, caches and client SDK design.

#### Traps / caveats

- Logging and metrics are allowed side effects for safe methods.
- Idempotency is about intended resource effect, not exact response body.
- Non-idempotent operations need special retry design.

#### Optional Anki

Q: Safe vs idempotent?
A: Safe does not change intended state; idempotent can be repeated with same intended effect.

</details>

<a id="http-method-007"></a>

<details>
<summary><strong>HTTP-METHOD-007. Why should GET not change server state?</strong></summary>

#### Short answer

GET is treated by clients, caches and crawlers as safe; changing state on GET can cause accidental or repeated side effects.

#### Interview answer

Many systems assume GET can be retried, prefetched, cached, bookmarked and crawled. If GET triggers actions like deleting data or charging a card, those actions may happen unexpectedly.

GET may still record logs or metrics, but it should not perform business state transitions.

#### Deep dive

State-changing GET endpoints also make CSRF and link-click attacks easier because a browser can issue GET requests through images, links or redirects.

#### Production angle

Keeping GET safe enables CDN caching, observability consistency and simpler client behavior.

#### Traps / caveats

- "Mark notification as read" via GET is a common bad shortcut.
- GET query strings are often logged.
- Safe does not mean response is free to compute.

#### Optional Anki

Q: Why keep GET safe?
A: Clients and intermediaries assume GET has no intended business side effects.

</details>

<a id="http-method-008"></a>

<details>
<summary><strong>HTTP-METHOD-008. Can POST be made idempotent at the application level?</strong></summary>

#### Short answer

Yes. POST can be made idempotent with an application-level idempotency key and durable deduplication.

#### Interview answer

For operations like payment or order creation, the client can send an idempotency key. The server stores that key with the operation status and result. If the same key is received again, the server returns the original outcome instead of executing the command twice.

#### Deep dive

The idempotency record must be stored transactionally with the business effect or protected by a unique constraint. Otherwise two concurrent retries can still both execute.

#### Production angle

This is critical for ambiguous failures: a client timeout does not prove the server rolled back. Idempotency lets clients retry safely.

#### Traps / caveats

- Key scope matters: per user, merchant, endpoint or operation.
- Store enough request fingerprint to reject key reuse with different payloads.
- Expire keys only after the retry window is safe.

#### Optional Anki

Q: How make POST idempotent?
A: Use a durable idempotency key tied to the original result.

</details>

<a id="http-method-009"></a>

<details>
<summary><strong>HTTP-METHOD-009. What is an idempotency key?</strong></summary>

#### Short answer

An idempotency key is a client-provided unique identifier that lets the server recognize repeated attempts of the same operation.

#### Interview answer

The key is sent with a non-idempotent command, often in a header. The server stores the key, request fingerprint, operation state and final result. Repeated requests with the same key return the same result or current operation status.

#### Deep dive

Good designs handle in-progress, succeeded and failed states. If a duplicate request arrives while the first is still running, the server may return 409/202 or wait depending on API policy.

#### Production angle

Idempotency keys reduce duplicate payments, orders, emails and external calls during retries, client crashes and network timeouts.

#### Traps / caveats

- A random key per retry defeats the purpose.
- Reusing a key for a different payload should be rejected.
- In-memory key storage is unsafe across restarts.

#### Optional Anki

Q: What does an idempotency key prevent?
A: Duplicate execution of the same retried command.

</details>

<a id="http-method-010"></a>

<details>
<summary><strong>🧠 HTTP-METHOD-010. Should DELETE return 200, 202, 204 or 404?</strong></summary>

#### Short answer

It depends on API policy: 204 is common for successful deletion, 200 can include a body, 202 means accepted asynchronously, and 404 may mean the resource is absent or hidden.

#### Interview answer

For synchronous deletion, `204 No Content` is common. Use `200 OK` if returning a representation or status. Use `202 Accepted` if deletion is queued or long-running.

Repeated DELETE calls can return 404 after the first deletion and still be idempotent because the final state is unchanged.

#### Deep dive

Some APIs choose DELETE to be "success if absent" and return 204 for repeated deletes. Others return 404 to signal that the target no longer exists. Both can be valid if documented.

#### Production angle

Clients need clear retry semantics. A retry after timeout should not treat a later 404 as proof that the first call failed.

#### Traps / caveats

- Idempotency does not require identical status codes.
- 202 needs a status resource or follow-up mechanism.
- 404 may be used to avoid revealing forbidden resources.

#### Optional Anki

Q: Can repeated DELETE return 404 and still be idempotent?
A: Yes; idempotency is about final intended state.

</details>

<a id="http-method-011"></a>

<details>
<summary><strong>🧠 HTTP-METHOD-011. What are the risks of using PATCH for partial updates?</strong></summary>

#### Short answer

PATCH can cause ambiguous null handling, lost updates, validation gaps and field-level authorization bugs.

#### Interview answer

Partial updates need a clear contract: omitted field means unchanged, null may mean clear value, and invalid combinations must be rejected. The service must validate the final state, not only the provided fields.

PATCH also needs concurrency protection when multiple clients update the same resource.

#### Deep dive

Patch formats matter. JSON Merge Patch and JSON Patch have different semantics. Custom partial DTOs are simpler but must document null/absence behavior carefully.

#### Production angle

PATCH bugs often appear as accidentally erased fields, overwritten concurrent changes or users modifying fields they should not control.

#### Traps / caveats

- Do not map PATCH DTO blindly onto an entity.
- Validate business invariants after applying the patch.
- Use ETags/version fields for important concurrent edits.

#### Optional Anki

Q: Main PATCH trap?
A: Ambiguous absent/null semantics and unsafe blind merging.

</details>

<a id="http-method-012"></a>

<details>
<summary><strong>HTTP-METHOD-012. How do method semantics affect retries and caching?</strong></summary>

#### Short answer

Safe/idempotent methods are generally easier to retry and cache; non-idempotent methods need explicit safeguards.

#### Interview answer

GET can often be retried and cached if headers allow it. PUT and DELETE can usually be retried after transient failures because repeated calls should have the same intended effect. POST should not be retried blindly unless protected by idempotency keys or equivalent deduplication.

#### Deep dive

Caching also follows method semantics. GET responses are the common cache target. POST responses can be cacheable in protocol terms only with explicit headers, but many systems do not rely on that.

#### Production angle

Retry configuration in Java HTTP clients must be tied to method and operation semantics, not only status codes.

#### Traps / caveats

- Retrying a timed-out POST can duplicate side effects.
- Retrying at multiple layers can amplify load.
- Cacheable does not mean safe for personalized data.

#### Optional Anki

Q: Why do method semantics matter?
A: They guide safe retry and caching behavior.

</details>

<a id="http-method-013"></a>

<details>
<summary><strong>🧠 HTTP-METHOD-013. How would you model business commands that do not fit CRUD naturally?</strong></summary>

#### Short answer

Model them as domain resources or command subresources when possible, and use POST for non-idempotent commands.

#### Interview answer

Not every operation is clean CRUD. For example, instead of forcing `/orders/{id}?action=cancel`, you can use `POST /orders/{id}/cancellations` or `POST /payment-authorizations`. The endpoint represents a domain concept or command request.

The API should make state transitions, idempotency and error behavior explicit.

#### Deep dive

Sometimes an action-like endpoint is acceptable if it reflects domain language and avoids awkward fake resources. REST is a tool for clarity, not a rule that every command must look like table CRUD.

#### Production angle

Command endpoints need strong validation, authorization, idempotency and audit logging because they usually change important state.

#### Traps / caveats

- Avoid generic `/execute`, `/process` or `/doAction`.
- Do not hide state transitions behind query parameters.
- Document retry and duplicate-request behavior.

#### Optional Anki

Q: How model non-CRUD commands?
A: Use domain command resources/subresources and explicit POST semantics.

</details>
