# HTTP caching and conditional requests

---

<a id="http-cache-001"></a>

<details>
<summary><strong>HTTP-CACHE-001. What is HTTP caching, and which methods are usually cacheable?</strong></summary>

#### Short answer

HTTP caching lets clients or intermediaries reuse responses. GET responses are the normal cache target.

#### Interview answer

Caching stores a response and reuses it according to headers like `Cache-Control`, `ETag` and `Expires`. GET is usually cacheable. Other methods are possible in protocol terms but are rarely relied on for typical REST APIs.

#### Deep dive

Caches may be private, such as a browser cache, or shared, such as a CDN or gateway cache. Shared caches require extra care with authentication and personalization.

#### Production angle

Caching can reduce latency and backend load, but wrong caching can leak data or serve stale results.

#### Traps / caveats

- Do not cache personalized responses in shared caches accidentally.
- Cache keys include URL and selected headers.
- POST caching is uncommon and needs explicit design.

#### Optional Anki

Q: Most commonly cached HTTP method?
A: GET.

</details>

<a id="http-cache-002"></a>

<details>
<summary><strong>HTTP-CACHE-002. What are the most important Cache-Control directives?</strong></summary>

#### Short answer

Important directives include `max-age`, `no-cache`, `no-store`, `private`, `public` and sometimes `stale-while-revalidate`.

#### Interview answer

`max-age` defines freshness lifetime. `no-cache` means the cache must revalidate before reuse. `no-store` means do not store at all. `private` means only private caches may store it. `public` allows shared caches.

#### Deep dive

`stale-while-revalidate` allows serving stale content briefly while refreshing in the background, useful for read-heavy non-critical data.

#### Production angle

Choose directives based on data sensitivity, freshness needs and whether shared caches are involved.

#### Traps / caveats

- `no-cache` does not mean "do not store".
- `public` is dangerous for user-specific data.
- Long `max-age` makes invalidation harder.

#### Optional Anki

Q: Which directive forbids storing?
A: `no-store`.

</details>

<a id="http-cache-004"></a>

<details>
<summary><strong>HTTP-CACHE-004. How would you generate and validate ETags for REST resources?</strong></summary>

#### Short answer

Generate ETags from a stable resource version or representation hash, and compare them on conditional requests.

#### Interview answer

For database resources, an ETag can be based on a version column or last update version. For computed representations, a hash of the representation may be used. The ETag must change when the representation relevant to the client changes.

#### Deep dive

If the representation varies by language, authorization or selected fields, the ETag must be scoped to that representation, not only the raw entity version.

#### Production angle

ETags support efficient caching and optimistic concurrency without locking.

#### Traps / caveats

- Do not generate weak/stale ETags for mutable critical data.
- Include representation-affecting fields.
- Respect user-specific representations.

#### Optional Anki

Q: What should an ETag represent?
A: The version of a specific resource representation.

</details>

<a id="http-cache-005"></a>

<details>
<summary><strong>HTTP-CACHE-005. How do If-None-Match and 304 Not Modified work?</strong></summary>

#### Short answer

The client sends its cached ETag in `If-None-Match`; if unchanged, the server returns 304 without a response body.

#### Interview answer

The first GET returns a body and ETag. Later the client revalidates with `If-None-Match`. If the current ETag matches, the server replies `304 Not Modified`, telling the client to reuse its cached body.

#### Deep dive

304 responses still include relevant headers that update cache metadata. The body is omitted, reducing bandwidth.

#### Production angle

Conditional GETs are useful for large or frequently polled resources.

#### Traps / caveats

- 304 is for conditional requests, not "empty result".
- ETags must be generated consistently across instances.
- Personalized responses need careful cache separation.

#### Optional Anki

Q: What does 304 mean?
A: Cached representation is still valid; no body returned.

</details>

<a id="http-cache-006"></a>

<details>
<summary><strong>🧠 HTTP-CACHE-006. How do If-Match and 412 Precondition Failed help prevent lost updates?</strong></summary>

#### Short answer

`If-Match` requires the resource version to match before applying an update; otherwise the server returns 412.

#### Interview answer

A client reads a resource and receives an ETag. When updating, it sends `If-Match` with that ETag. If another client changed the resource meanwhile, the ETag differs and the update is rejected.

#### Deep dive

This is HTTP-level optimistic locking. It prevents blind overwrites and forces the client to reload, merge or show a conflict.

#### Production angle

Useful for user profile edits, configuration changes, inventory records and collaborative workflows.

#### Traps / caveats

- If clients do not send `If-Match`, you need policy: reject or allow blind update.
- ETag must reflect all fields protected by the update.
- Use 409 for non-conditional business conflicts.

#### Optional Anki

Q: `If-Match` failed status?
A: 412 Precondition Failed.

</details>

<a id="http-cache-007"></a>

<details>
<summary><strong>🧠 HTTP-CACHE-007. What is optimistic concurrency control in REST APIs?</strong></summary>

#### Short answer

It is detecting concurrent changes using versions or ETags instead of locking the resource for the whole edit.

#### Interview answer

The client reads a resource version, sends that version back during update, and the server applies the change only if the current version still matches. If not, the API returns a conflict/precondition response.

#### Deep dive

The version can be an HTTP ETag, database version field or explicit `version` property. ETags keep the version in HTTP metadata; explicit fields can be easier for some clients.

#### Production angle

Optimistic concurrency avoids lost updates while scaling better than long locks.

#### Traps / caveats

- It does not merge changes automatically.
- All update paths must enforce the version rule.
- Clients need a UX for conflict resolution.

#### Optional Anki

Q: Optimistic concurrency purpose?
A: Prevent lost updates without long-held locks.

</details>

<a id="http-cache-008"></a>

<details>
<summary><strong>HTTP-CACHE-008. Why can caching personalized responses be dangerous?</strong></summary>

#### Short answer

Personalized responses can leak one user's data to another if shared caches store or reuse them incorrectly.

#### Interview answer

Responses depending on authentication, tenant, permissions or user preferences need careful cache headers. Shared caches should usually not store them unless the cache key includes all relevant variation and policy is deliberate.

#### Deep dive

Use `Cache-Control: private` for browser-only caching or `no-store` for highly sensitive data. If responses vary by headers, use `Vary` correctly.

#### Production angle

Cache leaks are severe incidents because data can be exposed at CDN/gateway scale.

#### Traps / caveats

- Authorization headers do not automatically make every cache safe.
- Missing `Vary` can mix languages, encodings or tenants.
- Query parameters can create high-cardinality cache keys.

#### Optional Anki

Q: Main personalized caching risk?
A: Serving one user's response to another user.

</details>

<a id="http-cache-010"></a>

<details>
<summary><strong>🧠 HTTP-CACHE-010. How would you design cache invalidation for REST APIs?</strong></summary>

#### Short answer

Prefer short freshness windows, validation with ETags, event-driven purges for critical resources and clear stale-data tolerance.

#### Interview answer

First define freshness requirements. Some resources can tolerate seconds or minutes of staleness; others need revalidation. Use `Cache-Control` and ETags for normal HTTP caching. For CDN/API gateway caches, purge by key or tag when important resources change.

#### Deep dive

Invalidation is hard when many URLs represent the same data through filters or projections. Sometimes a short TTL is more reliable than complex purging.

#### Production angle

Bad invalidation causes stale prices, stale permissions or support incidents. Monitor hit rate, stale serving and purge failures.

#### Traps / caveats

- Do not cache authorization-sensitive decisions blindly.
- Long TTLs need rollback/invalidation plans.
- Event-driven invalidation can miss events and needs reconciliation.

#### Optional Anki

Q: Simple cache invalidation strategy?
A: Short TTL plus ETag revalidation, with targeted purge where needed.

</details>

<a id="http-cache-011"></a>

<details>
<summary><strong>🧠 HTTP-CACHE-011. What are common HTTP caching mistakes, including missing Vary?</strong></summary>

#### Short answer

Common mistakes include caching private data, confusing `no-cache` with `no-store`, missing `Vary`, stale ETags and unbounded cache keys.

#### Interview answer

Missing `Vary` can cause a cache to serve the wrong representation, for example the wrong language, encoding or auth-dependent variant. Another frequent mistake is allowing shared caches to store user-specific responses.

#### Deep dive

Caches are part of the API contract. Headers need to be tested like application behavior, especially behind gateways/CDNs.

#### Production angle

Caching mistakes can become data leaks or stale-data incidents quickly because caches amplify responses.

#### Traps / caveats

- `private` is not the same as encrypted.
- ETags must be stable across instances.
- Cache key cardinality can explode with arbitrary query params.

#### Optional Anki

Q: What does `Vary` protect?
A: It tells caches which request headers affect the response representation.

</details>
