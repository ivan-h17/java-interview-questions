# Authentication, authorization and API security

---

<a id="rest-sec-001"></a>

<details>
<summary><strong>REST-SEC-001. What is the difference between authentication and authorization?</strong></summary>

#### Short answer

Authentication verifies who the caller is; authorization decides what that caller may do.

#### Interview answer

Authentication answers "who are you?" using credentials such as tokens, sessions or certificates. Authorization answers "are you allowed to perform this action on this resource?" using roles, scopes, ownership, tenant and business rules.

#### Deep dive

A user can be correctly authenticated and still forbidden from a specific resource. In REST APIs, authorization must usually include object-level checks, not only route-level checks.

#### Production angle

Most serious API security bugs are authorization bugs, especially missing ownership checks.

#### Traps / caveats

- Login success is not permission.
- Gateway authentication does not replace service authorization.
- Frontend-hidden buttons are not security controls.

#### Optional Anki

Q: Authentication vs authorization?
A: Identity vs permission.

</details>

<a id="rest-sec-002"></a>

<details>
<summary><strong>🧠 REST-SEC-002. What are Bearer tokens and JWTs, and what are common JWT pitfalls?</strong></summary>

#### Short answer

Bearer tokens grant access to whoever presents them. JWTs are self-contained signed tokens; pitfalls include weak validation, long lifetime and unsafe logging/storage.

#### Interview answer

A bearer token must be protected like a credential. A JWT commonly contains claims such as subject, issuer, audience, expiry and scopes. Resource servers must validate signature, issuer, audience, expiration and relevant claims.

#### Deep dive

JWTs are hard to revoke before expiry unless you use short lifetimes, introspection, revocation lists or key rotation strategy. They should not contain secrets or sensitive data just because they are signed.

#### Production angle

Token leakage through logs, browser storage or traces can become account takeover.

#### Traps / caveats

- Signing is not encryption.
- Do not accept `alg=none` or wrong algorithms.
- Validate `aud`, `iss` and expiry, not only signature.

#### Optional Anki

Q: Bearer token rule?
A: Whoever has it can use it, so protect it like a password.

</details>

<a id="rest-sec-003"></a>

<details>
<summary><strong>REST-SEC-003. What is the difference between 401 and 403 from a security perspective?</strong></summary>

#### Short answer

401 means the caller is not properly authenticated; 403 means the caller is authenticated or known but not allowed.

#### Interview answer

Missing, expired or invalid tokens usually produce 401. Valid identity with insufficient role, scope, ownership or tenant access usually produces 403.

For sensitive resources, an API may return 404 instead of 403 to avoid revealing existence.

#### Deep dive

The response should not reveal unnecessary details like "document exists but belongs to another user" unless the product intentionally exposes that.

#### Production angle

Correct distinction helps clients refresh tokens and helps security monitoring classify failures.

#### Traps / caveats

- Do not leak resource existence casually.
- Do not use 403 for expired tokens.
- Keep gateway and service behavior consistent.

#### Optional Anki

Q: Security meaning of 401 vs 403?
A: Not authenticated vs authenticated but forbidden.

</details>

<a id="rest-sec-004"></a>

<details>
<summary><strong>REST-SEC-004. What are BOLA / IDOR vulnerabilities in REST APIs?</strong></summary>

#### Short answer

BOLA/IDOR occurs when a caller can access another user's object by changing an identifier.

#### Interview answer

If `/users/123/orders/999` returns data to a user who does not own or have permission for that order, the API has broken object-level authorization. It is one of the most common API security issues.

#### Deep dive

Route-level authentication is not enough. The service must check object ownership, tenant membership or policy for the specific resource.

#### Production angle

BOLA bugs can leak large amounts of customer data and are often exploited by simple ID enumeration.

#### Traps / caveats

- Random IDs reduce guessing but do not replace authorization.
- Filtering after loading data can still leak or waste work.
- Test negative ownership cases.

#### Optional Anki

Q: What is IDOR?
A: Accessing unauthorized objects by changing IDs.

</details>

<a id="rest-sec-006"></a>

<details>
<summary><strong>REST-SEC-006. How should authorization be enforced in service methods?</strong></summary>

#### Short answer

Enforce authorization close to business operations and data access, not only in controllers.

#### Interview answer

Controllers can check coarse access, but service methods should enforce the real business rule: user, tenant, ownership, role/scope and operation state. Repository queries should include tenant/ownership predicates where possible.

#### Deep dive

Method-level security can help, but complex object-level checks often need explicit policy logic. Centralize reusable policy checks without hiding business context.

#### Production angle

Authorization in the service layer protects reuse from scheduled jobs, messaging handlers and other controllers.

#### Traps / caveats

- Controller-only checks are easy to bypass through new entry points.
- Self-invocation can affect proxy-based method security.
- Always test denied cases.

#### Optional Anki

Q: Where enforce object authorization?
A: In service/business logic and data queries, not only controllers.

</details>

<a id="rest-sec-007"></a>

<details>
<summary><strong>REST-SEC-007. What is mass assignment / over-posting?</strong></summary>

#### Short answer

It is when clients can set fields they should not control because the server binds broad input directly to an object.

#### Interview answer

If a user update endpoint binds request JSON directly to a `User` entity, an attacker may send `{"role":"ADMIN"}` or `{"balance":999999}`. The fix is narrow request DTOs and explicit mapping.

#### Deep dive

Mass assignment can appear after harmless-looking entity changes because newly added fields become writable automatically.

#### Production angle

This is a practical API security bug in Java apps that use reflection-based binding and broad models.

#### Traps / caveats

- Validation does not help if the field should not exist in the request.
- Do not trust frontend-hidden fields.
- Admin endpoints still need field-level authorization.

#### Optional Anki

Q: Mass assignment defense?
A: Narrow DTOs plus explicit allowed-field mapping.

</details>

<a id="rest-sec-008"></a>

<details>
<summary><strong>🧠 REST-SEC-008. How do you protect APIs from excessive data exposure?</strong></summary>

#### Short answer

Return only fields needed by the client, filtered by authorization and use case.

#### Interview answer

Do not return full entities and rely on the frontend to hide fields. Use DTOs/projections that exclude secrets, internal IDs, audit details and fields the caller is not allowed to see.

#### Deep dive

Field selection and "include" parameters need authorization too. A flexible response shape can accidentally expose fields across roles.

#### Production angle

Excessive data exposure causes privacy incidents and increases payload size.

#### Traps / caveats

- Frontend filtering is not protection.
- Generated `toString()` or logs can leak response data.
- Admin and normal user DTOs should usually differ.

#### Optional Anki

Q: How prevent excessive data exposure?
A: Server-side DTO/projection filtering with authorization.

</details>

<a id="rest-sec-009"></a>

<details>
<summary><strong>REST-SEC-009. Why are rate limiting and resource limits security features?</strong></summary>

#### Short answer

They limit abuse, brute force, scraping and resource exhaustion.

#### Interview answer

Authentication does not stop a valid client from overloading the system. Rate limits and quotas control request volume by user, token, IP, tenant or plan. Resource limits control payload size, page size, file count and expensive operations.

#### Deep dive

Limits should be enforced before expensive work when possible and should return clear 429/413-style errors with retry guidance.

#### Production angle

Without limits, one client can degrade the whole service or drive infrastructure cost.

#### Traps / caveats

- Per-IP limits can hurt NATed users.
- Per-user limits can miss distributed abuse.
- Limits need monitoring and business exceptions.

#### Optional Anki

Q: Why are limits security?
A: They prevent abuse and resource exhaustion.

</details>

<a id="rest-sec-010"></a>

<details>
<summary><strong>🧠 REST-SEC-010. How should APIs validate input and handle sensitive data in logs?</strong></summary>

#### Short answer

Validate at the boundary and business layer, and redact sensitive values from logs, errors and traces.

#### Interview answer

Validate syntax, types, sizes and formats at the API boundary. Validate business invariants in the service layer. Never log tokens, passwords, full payment data or sensitive documents.

#### Deep dive

Structured logging should use allowlists or redaction rules. Error handling should avoid echoing raw payloads or internal exception details.

#### Production angle

Sensitive data in logs is hard to remove and may become a compliance incident.

#### Traps / caveats

- Validation annotations are not complete business validation.
- Debug logs often leak more than responses.
- Traces and metrics labels can leak PII too.

#### Optional Anki

Q: API logging rule for secrets?
A: Redact or do not log them.

</details>

<a id="rest-sec-011"></a>

<details>
<summary><strong>🧠 REST-SEC-011. What is SSRF, and how should file upload or URL-fetching endpoints be secured?</strong></summary>

#### Short answer

SSRF is when attackers make your server fetch internal or unintended URLs. URL-fetching and upload features need strict allowlists and validation.

#### Interview answer

If an API accepts a URL and the backend fetches it, an attacker may target metadata services, internal admin panels or private networks. Defenses include allowlisted hosts/schemes, DNS/IP checks, redirect limits, timeouts and blocking private address ranges.

File uploads need size/type validation, scanning and safe storage.

#### Deep dive

SSRF checks must handle redirects, DNS rebinding, IPv6, encoded hosts and unusual URL forms.

#### Production angle

SSRF can expose cloud credentials or internal services.

#### Traps / caveats

- Block `localhost` and private IP ranges, not just strings.
- Do not trust content type or filename in uploads.
- Fetching through a proxy does not automatically make it safe.

#### Optional Anki

Q: SSRF risk?
A: Server is tricked into accessing internal or unintended resources.

</details>

<a id="rest-sec-012"></a>

<details>
<summary><strong>🧠 REST-SEC-012. Which OWASP API Security risks are most relevant to Java REST APIs?</strong></summary>

#### Short answer

The most common are broken object authorization, broken authentication, excessive data exposure, mass assignment, resource exhaustion and injection.

#### Interview answer

For Java REST APIs I would emphasize BOLA/IDOR, object property-level authorization, weak token handling, mass assignment through broad DTO/entity binding, unbounded pagination/uploads, SSRF and logging sensitive data.

#### Deep dive

Frameworks reduce boilerplate but do not remove design-level risks. Most API security failures are missing policy, missing limits or exposing too much data.

#### Production angle

Security review should include tests for denied access, tenant boundaries, payload limits and sensitive data handling.

#### Traps / caveats

- Prepared statements do not solve authorization.
- JWT does not solve object access.
- Rate limits do not fix expensive unbounded queries alone.

#### Optional Anki

Q: Most common API security risk?
A: Broken object-level authorization.

</details>
