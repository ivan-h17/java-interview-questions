# Request and response payload design

---

<a id="rest-payload-001"></a>

<details>
<summary><strong>REST-PAYLOAD-001. How should request DTOs differ from response DTOs?</strong></summary>

#### Short answer

Request DTOs model what clients may send; response DTOs model what the API promises to return.

#### Interview answer

Requests and responses often have different fields, validation rules and security concerns. A create request may include `productId` and `quantity`, while the response includes `id`, `status`, totals and timestamps.

Using separate DTOs prevents over-posting and avoids exposing internal fields.

#### Deep dive

Request DTOs should be narrow and command-specific. Response DTOs should be stable client contracts and may include derived or permission-filtered data.

#### Production angle

Separate DTOs make API evolution safer and reduce accidental data leaks from entity changes.

#### Traps / caveats

- Do not reuse JPA entities as request bodies.
- Do not let clients set server-owned fields.
- Keep DTO validation close to boundary semantics.

#### Optional Anki

Q: Why separate request and response DTOs?
A: They have different contracts, validation and security needs.

</details>

<a id="rest-payload-002"></a>

<details>
<summary><strong>REST-PAYLOAD-002. Why should APIs usually avoid exposing JPA entities directly?</strong></summary>

#### Short answer

JPA entities expose persistence internals, can leak fields and can trigger lazy loading or recursive serialization.

#### Interview answer

Entities are designed for persistence, not public API contracts. Returning them directly can expose internal IDs, audit fields, relationships or sensitive data. It can also trigger N+1 queries or infinite cycles during JSON serialization.

DTOs create a boundary between persistence and API representation.

#### Deep dive

Entity shape changes for database reasons should not automatically become API breaking changes. DTO mapping lets the API evolve independently.

#### Production angle

Direct entity serialization often causes performance and security bugs that appear only with real data graphs.

#### Traps / caveats

- `@JsonIgnore` on entities can become unmaintainable.
- Lazy loading during serialization hides query problems.
- DTOs still need authorization-aware field selection.

#### Optional Anki

Q: Main reason not to expose entities?
A: They couple the API to persistence and can leak data or trigger lazy loading.

</details>

<a id="rest-payload-003"></a>

<details>
<summary><strong>REST-PAYLOAD-003. How should optional, nullable and omitted fields be handled?</strong></summary>

#### Short answer

Define explicit semantics: absent means not provided, null means no value or clear value only if documented.

#### Interview answer

For create/update DTOs, optional fields need clear validation and defaults. In PATCH, omitted fields usually mean "leave unchanged"; null may mean "clear this value" or may be forbidden.

Ambiguity causes data loss and client bugs.

#### Deep dive

Java `Optional` is usually not ideal as a DTO field. It is often better to use explicit DTO types, validation rules and, for PATCH, a representation that can distinguish absent from null.

#### Production angle

Null/absent mistakes commonly erase user data or break backward compatibility when new fields are added.

#### Traps / caveats

- Do not treat missing and null the same accidentally.
- Defaults can hide client bugs.
- Unknown-field handling is part of compatibility policy.

#### Optional Anki

Q: PATCH omitted vs null?
A: Omitted usually unchanged; null may clear value if documented.

</details>

<a id="rest-payload-005"></a>

<details>
<summary><strong>REST-PAYLOAD-005. How should validation errors include field paths and rejected values safely?</strong></summary>

#### Short answer

Return field paths, stable error codes and safe messages; include rejected values only when they are not sensitive.

#### Interview answer

For nested payloads, clients need field paths such as `items[0].quantity`. Each error should include a machine-readable code and readable message. Avoid echoing passwords, tokens, documents or large raw payloads.

#### Deep dive

Cross-field errors can use a global path or object-level path. Keep the response shape stable so frontend clients can render errors generically.

#### Production angle

Good validation responses reduce support noise and frontend branching.

#### Traps / caveats

- Do not leak secrets in rejected values.
- Do not expose Java validator internals.
- Avoid localized text as the only machine-readable signal.

#### Optional Anki

Q: What should field validation errors contain?
A: Field path, stable code and safe message.

</details>

<a id="rest-payload-006"></a>

<details>
<summary><strong>REST-PAYLOAD-006. How should timestamps and time zones be represented in REST APIs?</strong></summary>

#### Short answer

Use explicit ISO-8601 formats and prefer instants or offsets for moments in time.

#### Interview answer

For event timestamps like `createdAt`, use an unambiguous format such as UTC instant `2026-06-10T12:34:56Z` or offset date-time. For date-only values, use `YYYY-MM-DD`. Avoid server-default time zones.

#### Deep dive

`LocalDateTime` without a zone is ambiguous for global APIs. It may be appropriate for domain concepts like store opening time, but not for audit timestamps.

#### Production angle

Time-zone bugs appear in sorting, expiry, billing, reports and cross-region systems.

#### Traps / caveats

- Do not serialize timestamps using locale-specific formats.
- Document precision and timezone.
- Test around daylight-saving transitions for local-time domains.

#### Optional Anki

Q: Best format for API instants?
A: ISO-8601 with UTC or explicit offset.

</details>

<a id="rest-payload-008"></a>

<details>
<summary><strong>REST-PAYLOAD-008. How should enums be represented, and what are the risks of changing enum values?</strong></summary>

#### Short answer

Use stable string codes for public enums; changing or removing values can break clients.

#### Interview answer

Public API enum values are contract values. `PAID`, `CANCELLED` or `PROCESSING` should be treated as stable. Renaming an enum constant in Java can accidentally break JSON clients if the serialized value changes.

#### Deep dive

Sometimes a dedicated code field is better than exposing Java enum names. Clients should be tolerant of unknown future values where possible, especially for response enums.

#### Production angle

Enum changes can break mobile apps, generated clients and downstream workflows.

#### Traps / caveats

- Do not expose ordinal values.
- Adding a response enum value can break strict clients.
- Document lifecycle and deprecation of values.

#### Optional Anki

Q: Why avoid enum ordinals in APIs?
A: They are unstable and unreadable as public contract values.

</details>

<a id="rest-payload-009"></a>

<details>
<summary><strong>🧠 REST-PAYLOAD-009. How should API payloads handle backward compatibility and unknown fields?</strong></summary>

#### Short answer

Add optional fields carefully, avoid changing meanings, and define tolerant-reader behavior for unknown fields.

#### Interview answer

Usually adding an optional response field is compatible, but only if clients ignore unknown fields. Adding a required request field is breaking. Renaming, removing or changing type/meaning is usually breaking.

Requests are trickier: ignoring unknown fields can improve compatibility but may hide client bugs.

#### Deep dive

Compatibility policy should be explicit in OpenAPI and tests. Some APIs reject unknown request fields for strictness while allowing unknown response fields for client tolerance.

#### Production angle

Backward compatibility matters for mobile clients, third-party integrations and rolling deployments.

#### Traps / caveats

- Adding enum values may break strict clients.
- Optional today can become required only through a versioned change.
- Changing field meaning is worse than adding a new field.

#### Optional Anki

Q: Is adding a required request field compatible?
A: No, it usually breaks existing clients.

</details>

<a id="rest-payload-010"></a>

<details>
<summary><strong>REST-PAYLOAD-010. How would you prevent over-posting / mass assignment vulnerabilities?</strong></summary>

#### Short answer

Use narrow request DTOs and explicitly map allowed fields instead of binding client payloads directly to domain/entity objects.

#### Interview answer

Mass assignment happens when clients can set fields they should not control, such as `role`, `balance`, `tenantId` or `isAdmin`. Prevent it by designing operation-specific DTOs and explicit mapping logic.

#### Deep dive

Validation is not enough if the field should never be accepted. The field should not exist in the request DTO for that operation.

#### Production angle

This is a common API security issue because adding a field to an entity can silently make it writable if binding is too broad.

#### Traps / caveats

- Do not trust hidden frontend fields.
- Do not map all non-null request fields blindly.
- Field-level authorization may be required for admin APIs.

#### Optional Anki

Q: Main defense against mass assignment?
A: Narrow request DTOs and explicit field mapping.

</details>

<a id="rest-payload-011"></a>

<details>
<summary><strong>🧠 REST-PAYLOAD-011. How would you handle large request payloads without buffering them fully in memory?</strong></summary>

#### Short answer

Set size limits, stream the body, process in chunks, and store large content outside the request thread when appropriate.

#### Interview answer

For large JSON, consider streaming parsers or batch formats. For files, use multipart streaming, direct-to-object-storage uploads or upload jobs. Never read an unbounded body into a `String`, byte array or `JsonNode`.

#### Deep dive

Large payloads need request limits at gateway and application layers, timeouts, cancellation handling and cleanup of partial data.

#### Production angle

Unbounded buffering causes memory spikes, GC pressure, thread exhaustion and denial-of-service risk.

#### Traps / caveats

- Validate size before expensive processing.
- Do not log large raw payloads.
- Beware temporary file cleanup and disk exhaustion.

#### Optional Anki

Q: Main large-payload rule?
A: Bound and stream; do not buffer unbounded bodies in memory.

</details>

<a id="rest-payload-012"></a>

<details>
<summary><strong>🧠 REST-PAYLOAD-012. How should multipart/form-data uploads be modeled and validated separately from JSON APIs?</strong></summary>

#### Short answer

Treat multipart uploads as a distinct contract with metadata, binary parts, size/type limits and security validation.

#### Interview answer

Multipart requests mix fields and file parts. Validate metadata like normal input, validate files separately, enforce count/size limits, scan content when needed and avoid trusting client-provided filenames or content types.

#### Deep dive

For large uploads, direct-to-object-storage patterns can be better than passing bytes through the API service. The API then manages metadata, authorization and processing status.

#### Production angle

Uploads are high-risk for resource exhaustion, malware, path traversal and slow-client issues.

#### Traps / caveats

- Do not trust file extension or MIME type.
- Store uploaded files outside executable paths.
- Generate server-side filenames/keys.

#### Optional Anki

Q: Why treat multipart separately?
A: It has binary, metadata, resource and security concerns beyond JSON validation.

</details>

<a id="rest-payload-013"></a>

<details>
<summary><strong>REST-PAYLOAD-013. How should APIs handle duplicate create requests?</strong></summary>

#### Short answer

Use idempotency keys, unique constraints or natural business keys to detect and safely return the original result.

#### Interview answer

Duplicate creates happen after retries, double-clicks, client crashes or network timeouts. For important commands, require an idempotency key and store it transactionally with the creation result.

For naturally unique data, use database constraints and map conflicts clearly.

#### Deep dive

If two duplicate requests race, the database must enforce uniqueness. Application-only checks are not enough.

#### Production angle

This prevents duplicate orders, payments, emails and external side effects.

#### Traps / caveats

- Do not generate a new idempotency key for each retry.
- Return consistent result for duplicate keys.
- Reject same key with different payload fingerprint.

#### Optional Anki

Q: How handle duplicate creates?
A: Idempotency keys plus transactional storage/unique constraints.

</details>
