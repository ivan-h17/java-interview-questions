# REST fundamentals and architectural constraints

---

<a id="rest-fund-001"></a>

<details>
<summary><strong>REST-FUND-001. What is REST?</strong></summary>

#### Short answer

REST is an architectural style for designing networked systems around resources, representations and standard interaction semantics.

#### Interview answer

In backend interviews, I would describe REST as a set of constraints for designing APIs, not as a protocol or framework. A REST API exposes resources through stable identifiers, transfers representations such as JSON, uses HTTP method semantics deliberately, and keeps requests self-contained.

The goal is to make APIs understandable, scalable and loosely coupled by relying on uniform conventions instead of custom operation contracts for every interaction.

#### Deep dive

REST came from Roy Fielding's dissertation and is broader than typical JSON-over-HTTP APIs. Real production APIs often implement only part of the style. The practical value for Java backend work is disciplined use of resources, HTTP methods, status codes, caching and statelessness.

#### Production angle

Good REST design improves client compatibility, observability, retry behavior, caching and gateway integration. Poor REST design often causes ambiguous retries, inconsistent error handling and endpoints that are hard to evolve.

#### Traps / caveats

- REST is not the same as "any HTTP JSON API".
- REST is not automatically better than RPC, GraphQL or gRPC.
- Naming URLs with nouns is not enough if method semantics and status codes are wrong.

#### Optional Anki

Q: What is REST?
A: An architectural style for resource-oriented APIs using representations and uniform interaction semantics.

</details>

<a id="rest-fund-002"></a>

<details>
<summary><strong>REST-FUND-002. Is REST a protocol, an architectural style, or a framework?</strong></summary>

#### Short answer

REST is an architectural style.

#### Interview answer

REST is not a protocol like HTTP and not a framework like Spring MVC. It is a set of architectural constraints that can be implemented over HTTP and by frameworks, but the framework does not make an API RESTful by itself.

For example, a Spring controller returning JSON can still be action-oriented RPC if every endpoint is `/doSomething` and HTTP methods/status codes are ignored.

#### Deep dive

HTTP is commonly used because it already provides methods, status codes, headers, caching and content negotiation. REST uses those mechanisms well, but REST itself describes design constraints such as statelessness, cacheability, uniform interface and layered systems.

#### Production angle

This distinction matters in reviews. You should evaluate the API contract and behavior, not just whether it uses `@RestController`.

#### Traps / caveats

- "REST endpoint" is often used loosely.
- Spring REST support helps implementation but does not guarantee RESTful design.
- REST constraints can be partially followed; be explicit about trade-offs.

#### Optional Anki

Q: REST is what kind of thing?
A: An architectural style, commonly implemented using HTTP.

</details>

<a id="rest-fund-003"></a>

<details>
<summary><strong>REST-FUND-003. What are the main REST architectural constraints?</strong></summary>

#### Short answer

The main REST constraints are client-server separation, statelessness, cacheability, uniform interface, layered system and optional code-on-demand.

#### Interview answer

The practical constraints I would emphasize are: clients and servers have separate responsibilities; every request contains enough context; responses should define caching behavior when useful; resources are manipulated through a uniform interface; and clients do not need to know whether they talk directly to the service or through gateways and proxies.

Code-on-demand exists in the original REST model but is rarely important for backend JSON APIs.

#### Deep dive

The uniform interface is the constraint that makes REST recognizable: resources have identifiers, clients exchange representations, messages are self-descriptive, and hypermedia can describe available transitions. Most enterprise APIs use the first three more than deep HATEOAS.

#### Production angle

These constraints support independent deployment, gateway routing, caching, retries, observability and horizontal scaling.

#### Traps / caveats

- Stateless does not mean the system has no database state.
- Cacheable does not mean every response should be cached.
- Uniform interface is more than pretty URLs.

#### Optional Anki

Q: Name core REST constraints.
A: Client-server, stateless, cacheable, uniform interface, layered system, optional code-on-demand.

</details>

<a id="rest-fund-004"></a>

<details>
<summary><strong>REST-FUND-004. What does stateless mean in REST, and how is it different from stateless application behavior?</strong></summary>

#### Short answer

REST statelessness means each request carries the context needed to process it; it does not mean the application stores no business state.

#### Interview answer

In REST, the server should not depend on hidden per-client conversational state stored between requests. Authentication context, resource ID, request body, headers and parameters should be enough to handle the request.

That is different from business state. An order service is obviously stateful because it stores orders. The point is that the protocol interaction should not require a server-side conversation session to interpret the next request.

#### Deep dive

HTTP sessions can still be used in web applications, but they weaken statelessness because routing, scaling and failover may depend on session storage. Token-based APIs are often easier to scale because any instance can validate the request if it has the necessary keys/configuration.

#### Production angle

Stateless request handling improves load balancing, retry behavior and horizontal scaling. It also reduces failure modes caused by sticky sessions or lost in-memory session state.

#### Traps / caveats

- Stateless REST can still use databases, caches and queues.
- JWT does not automatically make authorization correct.
- Do not put too much mutable authorization state into long-lived tokens.

#### Optional Anki

Q: What does REST statelessness mean?
A: Each request is self-contained; business data may still be stored server-side.

</details>

<details>
<summary><strong>REST-FUND-005. What is a resource in REST?</strong></summary>

#### Short answer

A resource is a conceptual thing exposed by the API and identified by a URI.

#### Interview answer

A resource can be an entity like an order, a collection like orders, or a domain concept like an invoice PDF or report job. Clients interact with resources through representations, not by directly manipulating server objects.

For example, `/orders/123` identifies an order resource. A GET returns a representation of that order, while PATCH may request a partial change.

#### Deep dive

Resources are not necessarily database rows. A resource may be computed, aggregate multiple data sources or represent an operation state, such as `/report-jobs/{id}`.

#### Production angle

Good resource modeling makes APIs easier to document, secure and evolve. Bad modeling often leaks persistence details or creates action endpoints that are hard to reason about.

#### Traps / caveats

- A resource is not the same as a JPA entity.
- Not every business action maps cleanly to CRUD.
- Collection and item resources have different semantics.

#### Optional Anki

Q: What is a REST resource?
A: A named API concept identified by a URI and exchanged through representations.

</details>

<a id="rest-fund-006"></a>

<details>
<summary><strong>REST-FUND-006. What is a representation in REST?</strong></summary>

#### Short answer

A representation is the transferred form of a resource, such as JSON, XML, HTML or a file stream.

#### Interview answer

The server owns the resource state. The client receives or sends a representation of that state. For example, an order may be stored across several tables, but the API returns a JSON representation designed for clients.

Representations are shaped by media type, versioning, permissions and use case.

#### Deep dive

A resource can have multiple representations: JSON for API clients, PDF for download, or a compact projection for list pages. Headers like `Content-Type`, `Accept`, `ETag` and `Cache-Control` describe representation semantics.

#### Production angle

Separating resource state from representation helps avoid leaking database schema, lazy-loading problems and accidental breaking changes.

#### Traps / caveats

- Do not expose persistence entities as representations by default.
- A representation can omit fields for security or performance.
- Changing representation shape can break clients even if database state is unchanged.

#### Optional Anki

Q: What is a representation?
A: The serialized form of a resource transferred over the API.

</details>

<a id="rest-fund-007"></a>

<details>
<summary><strong>REST-FUND-007. What is the difference between REST and HTTP?</strong></summary>

#### Short answer

HTTP is a protocol; REST is an architectural style often implemented using HTTP.

#### Interview answer

HTTP provides request/response messaging, methods, status codes, headers, caching and content negotiation. REST gives design constraints for how to structure interactions around resources and representations.

An API can use HTTP but still be non-RESTful if it treats every endpoint as a custom command and ignores HTTP semantics.

#### Deep dive

REST can theoretically use other protocols, but HTTP fits naturally. Most Java backend "REST APIs" are pragmatic REST-style HTTP APIs rather than strict REST with full hypermedia.

#### Production angle

Understanding HTTP is required for production REST work: retries, status codes, caching, auth headers, proxies and gateways all rely on HTTP behavior.

#### Traps / caveats

- `POST /getUser` over HTTP is not RESTful just because it returns JSON.
- HTTP semantics still matter behind Spring abstractions.
- REST design and transport configuration are separate concerns.

#### Optional Anki

Q: HTTP vs REST?
A: HTTP is the protocol; REST is a resource-oriented architectural style commonly using HTTP.

</details>

<a id="rest-fund-008"></a>

<details>
<summary><strong>🧠 REST-FUND-008. What trade-offs does REST make compared with RPC-style APIs?</strong></summary>

#### Short answer

REST favors standard resource semantics and broad interoperability; RPC favors explicit operations and often maps more directly to business commands.

#### Interview answer

REST is good when resources, caching, standard HTTP tooling, browser/gateway support and long-lived public contracts matter. RPC-style APIs can be clearer for command-heavy workflows where operations do not map naturally to resources.

The senior answer is pragmatic: choose the style that makes the contract clear, reliable and evolvable.

#### Deep dive

REST can become awkward when teams force every command into CRUD. RPC can become chaotic when every operation invents its own semantics for errors, retries and compatibility. gRPC adds strong schemas and efficient binary transport but has different browser and operational trade-offs.

#### Production angle

Use REST for public APIs, CRUD-ish resources and HTTP ecosystem leverage. Consider RPC/gRPC for internal high-throughput service-to-service calls with strict schemas and generated clients.

#### Traps / caveats

- REST is not automatically more "clean".
- RPC is not automatically an anti-pattern.
- Mixing styles is acceptable if contracts are consistent.

#### Optional Anki

Q: Main REST vs RPC trade-off?
A: REST standardizes resource semantics; RPC makes operations explicit.

</details>
