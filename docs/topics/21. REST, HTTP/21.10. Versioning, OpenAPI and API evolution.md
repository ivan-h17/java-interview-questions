# Versioning, OpenAPI and API evolution

---

<a id="rest-evo-001"></a>

<details>
<summary><strong>REST-EVO-001. How can REST APIs be versioned?</strong></summary>

#### Short answer

Common approaches are URI versioning, header versioning, media-type versioning and sometimes no explicit version with strict backward compatibility.

#### Interview answer

URI versioning uses paths like `/v1/orders`. Header versioning uses custom or standard headers. Media-type versioning encodes version in `Accept`. Many internal APIs avoid versioning until needed and rely on backward-compatible changes.

#### Deep dive

The best choice depends on client type, API gateway, documentation, caching and release process. Public APIs often prefer obvious URI versions; internal APIs may prefer compatibility plus contract tests.

#### Production angle

Versioning is not a substitute for compatibility discipline. Old clients may live longer than expected.

#### Traps / caveats

- Versioning every tiny change creates maintenance cost.
- Header/media versions can be harder to test manually.
- Removing old versions needs a migration plan.

#### Optional Anki

Q: Common API versioning styles?
A: URI, header, media type, or backward-compatible unversioned evolution.

</details>

<a id="rest-evo-002"></a>

<details>
<summary><strong>🧠 REST-EVO-002. What are the trade-offs of URI, header-based and media-type versioning?</strong></summary>

#### Short answer

URI versions are visible and simple; header/media versions keep URIs cleaner but are less obvious and can complicate caching and tooling.

#### Interview answer

URI versioning is easy for clients, logs and gateways, but it can imply that the whole API changes at once. Header versioning is flexible but less visible. Media-type versioning is semantically elegant for representations but more complex for many teams.

#### Deep dive

The operational ecosystem matters: OpenAPI docs, generated clients, CDN caching and gateway routing may support one approach better.

#### Production angle

Choose a versioning strategy that your deployment, support and client migration processes can actually handle.

#### Traps / caveats

- Versioning style does not define compatibility rules.
- Hidden header versions can surprise clients.
- Multiple live versions multiply test burden.

#### Optional Anki

Q: Main URI versioning benefit?
A: Visibility and operational simplicity.

</details>

<a id="rest-evo-004"></a>

<details>
<summary><strong>REST-EVO-004. What is a breaking change in a REST API?</strong></summary>

#### Short answer

A breaking change can cause existing correct clients to fail or behave incorrectly.

#### Interview answer

Examples include removing or renaming fields, changing field type or meaning, adding required request fields, removing enum values, changing status-code semantics, tightening validation unexpectedly or changing authentication requirements.

#### Deep dive

Breaking changes are not only schema changes. Behavior, error format, pagination, sorting defaults and rate limits can also break clients.

#### Production angle

Public/mobile clients may not update quickly. Breaking changes need versioning, migration windows and communication.

#### Traps / caveats

- "We only changed the backend" can still break the API.
- Adding response fields can break strict clients.
- Generated clients reveal breaking changes quickly.

#### Optional Anki

Q: What is a breaking API change?
A: A change that breaks existing correct clients.

</details>

<a id="rest-evo-005"></a>

<details>
<summary><strong>REST-EVO-005. Which changes are usually backward-compatible?</strong></summary>

#### Short answer

Adding optional request fields, adding response fields for tolerant clients, adding new endpoints and relaxing validation are usually compatible.

#### Interview answer

Backward-compatible changes should not require existing clients to change. Adding a new endpoint is safe. Adding an optional field is usually safe. Adding a response field is safe only if clients ignore unknown fields.

#### Deep dive

Compatibility depends on real client behavior, not only theory. Strict deserializers, generated clients or enum handling may turn "safe" changes into breakages.

#### Production angle

Contract tests and client telemetry help verify whether a supposedly compatible change is safe.

#### Traps / caveats

- Adding required request fields is breaking.
- Adding enum values can break switch statements.
- Changing defaults can be breaking.

#### Optional Anki

Q: Is adding an optional field usually compatible?
A: Yes, if existing clients can ignore it.

</details>

<a id="rest-evo-006"></a>

<details>
<summary><strong>REST-EVO-006. Is adding a response field or a required request field backward-compatible?</strong></summary>

#### Short answer

Adding a response field is usually compatible for tolerant clients; adding a required request field is breaking.

#### Interview answer

Existing clients do not send new required fields, so requiring one breaks them. Existing clients may receive new response fields safely only if their parsers ignore unknown properties.

#### Deep dive

For Java clients using Jackson, compatibility depends on settings like `FAIL_ON_UNKNOWN_PROPERTIES`. Generated clients may also enforce schemas strictly.

#### Production angle

Before adding fields to public APIs, check client behavior, OpenAPI generation and contract tests.

#### Traps / caveats

- A response field addition can break strict mobile clients.
- New fields may leak sensitive data.
- Required should usually be introduced through a new version or staged migration.

#### Optional Anki

Q: Required request field compatible?
A: No, existing clients will not send it.

</details>

<a id="rest-evo-007"></a>

<details>
<summary><strong>REST-EVO-007. How should APIs deprecate fields or endpoints?</strong></summary>

#### Short answer

Announce deprecation, keep behavior for a migration window, monitor usage and remove only after clients migrate.

#### Interview answer

Deprecation should be visible in documentation/OpenAPI, release notes and possibly response headers. Provide alternatives and timelines. Track usage by client before removal.

#### Deep dive

For fields, stop documenting as preferred, add replacement fields, support both for a period, then remove in a new version or after agreed sunset.

#### Production angle

Deprecation without usage telemetry is risky because unknown clients may still depend on the old contract.

#### Traps / caveats

- Do not remove immediately after marking deprecated.
- Communicate behavior and dates clearly.
- Keep old and new fields consistent during migration.

#### Optional Anki

Q: Deprecation needs what before removal?
A: Migration window, communication and usage monitoring.

</details>

<a id="rest-evo-008"></a>

<details>
<summary><strong>🧠 REST-EVO-008. How should clients be migrated from v1 to v2?</strong></summary>

#### Short answer

Provide a compatibility plan: documentation, dual support, tooling, telemetry, deadlines and fallback/rollback strategy.

#### Interview answer

I would publish v2 docs, explain breaking changes, provide examples or generated clients, run both versions during migration, monitor client adoption and set a realistic sunset date.

For critical clients, coordinate testing before cutting off v1.

#### Deep dive

Sometimes a gateway can route by version while services share most implementation. Avoid duplicating business logic without tests.

#### Production angle

Migration is operational work, not just code. Support teams need visibility into which clients still use v1.

#### Traps / caveats

- Do not assume all clients update quickly.
- Version routing must be observable.
- Keep security fixes applied to old supported versions.

#### Optional Anki

Q: API version migration needs?
A: Dual support, documentation, telemetry and sunset plan.

</details>

<a id="rest-evo-010"></a>

<details>
<summary><strong>REST-EVO-010. How should OpenAPI specs and API documentation be versioned?</strong></summary>

#### Short answer

Version API specs with the API contract and keep them in sync with deployed behavior.

#### Interview answer

OpenAPI should describe the real contract clients use: paths, schemas, status codes, auth, examples and error models. Store specs in version control, publish them per API version and test that implementation matches them.

#### Deep dive

Generated specs from code reduce duplication but can hide intentional design review. Contract-first specs improve API design discipline but require implementation sync.

#### Production angle

Stale docs are production bugs for client teams. Generated clients depend heavily on accurate specs.

#### Traps / caveats

- Do not treat OpenAPI as marketing documentation only.
- Include error responses and security schemes.
- Review generated diff noise carefully.

#### Optional Anki

Q: What should OpenAPI represent?
A: The actual deployed API contract.

</details>

<a id="rest-evo-012"></a>

<details>
<summary><strong>REST-EVO-012. What is tolerant reader pattern?</strong></summary>

#### Short answer

Tolerant readers ignore unknown data and depend only on fields they actually need.

#### Interview answer

In API evolution, clients should not fail just because the server adds a new response field. They should parse known fields and ignore unknown ones where safe.

This makes additive changes easier.

#### Deep dive

Tolerance does not mean accepting invalid required data. For requests, servers may choose stricter validation to catch client mistakes.

#### Production angle

Tolerant readers are important for microservices and mobile clients where provider and consumer deployments are independent.

#### Traps / caveats

- Unknown enum values still need handling.
- Tolerance can hide misspelled fields in requests.
- Do not rely on undocumented fields.

#### Optional Anki

Q: Tolerant reader means?
A: Ignore unknown data and depend only on documented needed fields.

</details>

<details>
<summary><strong>🧠 REST-EVO-013. How do API changes interact with database migrations and feature flags?</strong></summary>

#### Short answer

API changes often need backward-compatible database changes and staged rollout with feature flags.

#### Interview answer

If an API adds a new field backed by a new column, first add the column safely, deploy code that can handle old and new states, backfill if needed, then expose or require the field later. Feature flags can control rollout and rollback.

#### Deep dive

The API must remain compatible during rolling deployment when old and new app versions run at the same time.

#### Production angle

Coordinating API, database and client rollout avoids downtime and partial-release failures.

#### Traps / caveats

- Do not make a field required before data is backfilled.
- Contract changes can be harder to roll back than code.
- Feature flags need cleanup.

#### Optional Anki

Q: API evolution and DB migration rule?
A: Use backward-compatible staged changes.

</details>

<details>
<summary><strong>🧠 REST-EVO-014. How would you design an API compatibility review checklist?</strong></summary>

#### Short answer

Check schema, status codes, errors, behavior, auth, pagination, docs, generated clients and rollout/rollback.

#### Interview answer

I would verify whether any existing request/response fields changed, required fields were added, status/error semantics changed, enum values changed, authorization changed, pagination changed or OpenAPI docs drifted.

Then I would check contract tests and client impact.

#### Deep dive

Compatibility review should include examples and negative cases, not only happy-path schemas.

#### Production angle

A checklist catches breaking changes before public clients or other services fail after deployment.

#### Traps / caveats

- Behavior changes can break clients even if schema is unchanged.
- Error model changes matter.
- Generated client diffs need human review.

#### Optional Anki

Q: API compatibility review checks what?
A: Schema, behavior, errors, auth, docs, tests and rollout.

</details>

<details>
<summary><strong>🧠 REST-EVO-015. How would you prevent drift between OpenAPI documentation and deployed API behavior?</strong></summary>

#### Short answer

Use contract tests, generated validation, CI checks and review of OpenAPI diffs.

#### Interview answer

The API implementation and OpenAPI spec should be checked together. Tests can validate responses against the spec, request examples can be exercised, and CI can fail when generated spec diffs are unexpected.

#### Deep dive

Code-first and contract-first both have drift risks. Code-first can document accidental implementation. Contract-first can become stale if implementation ignores the spec.

#### Production angle

Spec drift breaks generated clients, partner integrations and support troubleshooting.

#### Traps / caveats

- Do not only test 200 responses.
- Include errors, auth and edge cases in the spec.
- Review generated clients after schema changes.

#### Optional Anki

Q: How prevent OpenAPI drift?
A: Contract tests and CI checks against deployed behavior.

</details>
