# Performance and protocol-level considerations

<a id="http-perf-001"></a>

<details>
<summary><strong>HTTP-PERF-001. How can REST API performance be improved?</strong></summary>

#### Short answer

Improve query efficiency, payload size, caching, pagination, serialization, connection reuse and dependency behavior.

#### Interview answer

Start by measuring. Common fixes include proper indexes, avoiding N+1 queries, limiting payloads, using pagination, adding HTTP/cache-layer caching, compressing where useful, tuning connection pools and reducing slow downstream calls.

#### Deep dive

Performance work should target the bottleneck: database, JSON serialization, network, CPU, locks, thread pools or dependencies.

#### Production angle

Use p95/p99 latency, traces and profiles before optimizing.

#### Traps / caveats

- Do not optimize blindly.
- Caching can create stale-data and security issues.
- Smaller payloads often beat more servers.

#### Optional Anki

Q: First step in API performance work?
A: Measure the bottleneck.

</details>

<a id="http-perf-002"></a>

<details>
<summary><strong>HTTP-PERF-002. When does response compression help, and when can it hurt?</strong></summary>

#### Short answer

Compression helps large text responses over slow networks; it can hurt small, already-compressed or CPU-bound responses.

#### Interview answer

JSON compresses well, so gzip/br can reduce bandwidth. But compression costs CPU and latency, and it is pointless for already-compressed files like JPEG or ZIP.

#### Deep dive

Compression thresholds matter. Very small responses may become slower or larger after compression overhead.

#### Production angle

Monitor CPU, response size and latency before and after enabling compression.

#### Traps / caveats

- Avoid compressing secrets with attacker-controlled input in sensitive contexts.
- Do not compress already-compressed content.
- Check proxy/gateway compression behavior.

#### Optional Anki

Q: Compression best for?
A: Large text responses like JSON.

</details>

<a id="http-perf-003"></a>

<details>
<summary><strong>HTTP-PERF-003. How should large responses be handled with pagination, streaming or download resources?</strong></summary>

#### Short answer

Avoid returning huge arrays; use pagination, streaming, async exports or file download resources.

#### Interview answer

For interactive lists, use pagination. For exports, create an async job and download the result when ready. For real-time large streams, stream carefully with timeouts and cancellation handling.

#### Deep dive

Large responses stress memory, serialization, network and clients. Sometimes a dedicated report/export resource is better than a giant query response.

#### Production angle

Huge responses cause p99 latency, OOMs and slow-client resource retention.

#### Traps / caveats

- Do not build the entire response in memory.
- Consider client cancellation.
- Enforce limits even for internal clients.

#### Optional Anki

Q: Alternative to huge response?
A: Pagination, streaming or async export/download.

</details>

<a id="http-perf-004"></a>

<details>
<summary><strong>HTTP-PERF-004. How should streaming responses handle cancellation, timeouts and slow clients?</strong></summary>

#### Short answer

Streaming must detect disconnects, bound duration/rate and release resources promptly.

#### Interview answer

A streaming endpoint should not hold database transactions or scarce resources indefinitely. It needs timeouts, backpressure or rate control, cancellation handling and cleanup when the client disconnects.

#### Deep dive

Streaming from database cursor to HTTP response can be dangerous if it keeps connections open for slow clients. Consider buffering to files/object storage for large exports.

#### Production angle

Slow clients can exhaust server threads, sockets and database connections.

#### Traps / caveats

- Do not stream while holding long transactions unnecessarily.
- Test client disconnects.
- Avoid unbounded producer queues.

#### Optional Anki

Q: Streaming endpoint must handle?
A: Slow clients, cancellation, timeouts and resource cleanup.

</details>

<a id="http-perf-005"></a>

<details>
<summary><strong>🧠 HTTP-PERF-005. What is chunked transfer encoding?</strong></summary>

#### Short answer

Chunked transfer encoding sends a response body in chunks when total length is not known upfront.

#### Interview answer

In HTTP/1.1, chunked encoding lets a server start sending data before computing the full `Content-Length`. It is useful for streaming or generated responses.

#### Deep dive

Application developers usually interact with streaming APIs rather than raw chunks. Proxies and clients must support the transfer behavior correctly.

#### Production angle

Chunked responses need timeout and slow-client handling just like other streams.

#### Traps / caveats

- Chunked is transfer framing, not application record framing.
- Do not assume clients receive useful partial JSON unless format supports it.
- Intermediaries may buffer.

#### Optional Anki

Q: Why use chunked encoding?
A: Send body incrementally without known total length.

</details>

<a id="http-perf-006"></a>

<details>
<summary><strong>HTTP-PERF-006. What is the N+1 problem in REST APIs?</strong></summary>

#### Short answer

It is when serving one API request triggers one query for a list and then additional queries per item.

#### Interview answer

Example: `GET /orders` loads 50 orders, then serialization accesses `order.customer` and runs 50 more queries. This often happens with JPA lazy loading and entity serialization.

#### Deep dive

Fixes include fetch joins, projections, batch fetching, DTO queries or precomputed read models.

#### Production angle

N+1 issues often appear only with production data sizes and cause high database load.

#### Traps / caveats

- Open Session in View can hide N+1 until production.
- Returning entities makes N+1 more likely.
- Logs/traces should show query counts.

#### Optional Anki

Q: N+1 in REST?
A: One list query plus one query per returned item.

</details>

<a id="http-perf-007"></a>

<details>
<summary><strong>🧠 HTTP-PERF-007. When are GraphQL or gRPC better fits than REST?</strong></summary>

#### Short answer

GraphQL can fit flexible client-driven reads; gRPC can fit internal high-performance typed service-to-service calls.

#### Interview answer

GraphQL helps when clients frequently need different shapes of related data and REST causes over/under-fetching. gRPC helps when teams control both sides, want strong schemas, streaming and efficient binary transport.

REST remains strong for public resource APIs, HTTP tooling and simple contracts.

#### Deep dive

GraphQL shifts complexity to query planning, authorization and limits. gRPC shifts operational concerns to protobuf, generated clients and load-balancer/proxy support.

#### Production angle

Choose based on client needs, tooling, observability, security and team experience.

#### Traps / caveats

- GraphQL does not remove authorization complexity.
- gRPC is less browser-native.
- REST is often good enough and simpler.

#### Optional Anki

Q: GraphQL is strongest for?
A: Flexible client-selected read shapes.

</details>

<a id="http-perf-008"></a>

<details>
<summary><strong>🧠 HTTP-PERF-008. How do HTTP connection pooling and slow clients affect server resources?</strong></summary>

#### Short answer

Connection pools bound outbound concurrency; slow clients can hold inbound connections, threads or buffers longer.

#### Interview answer

For outbound calls, pools prevent creating too many connections but can become bottlenecks if undersized or if downstream is slow. For inbound responses, slow clients can keep server resources occupied while data is written.

#### Deep dive

Sizing should consider latency, concurrency, downstream capacity and timeouts. Bigger pools are not always better.

#### Production angle

Pool metrics and in-flight request counts are essential for diagnosing latency under load.

#### Traps / caveats

- Pool exhaustion can look like downstream latency.
- Slow clients can hurt streaming endpoints.
- Virtual threads do not remove connection limits.

#### Optional Anki

Q: Why bound HTTP client pools?
A: To control outbound concurrency and protect dependencies.

</details>

<a id="http-perf-009"></a>

<details>
<summary><strong>HTTP-PERF-009. What is request body buffering?</strong></summary>

#### Short answer

Request body buffering means reading and storing the request body before processing it, often in memory or temporary files.

#### Interview answer

Frameworks, filters, gateways or logging middleware may buffer bodies for parsing, retries or inspection. This can be dangerous for large uploads or JSON payloads.

#### Deep dive

Some features require buffering, but it should be bounded and visible. Streaming avoids full buffering but complicates validation and error handling.

#### Production angle

Unexpected buffering causes memory spikes, disk usage and latency.

#### Traps / caveats

- Logging request bodies may force buffering.
- Multipart handling may use temp files.
- Set body size limits at gateway and app layers.

#### Optional Anki

Q: Request body buffering risk?
A: Memory/disk pressure from storing large bodies.

</details>

<a id="http-perf-010"></a>

<details>
<summary><strong>HTTP-PERF-010. What performance problems can an API gateway introduce?</strong></summary>

#### Short answer

Gateways can add latency, buffering, rate-limit overhead, TLS/proxy costs and bottlenecks if misconfigured.

#### Interview answer

Gateways are useful for routing, auth, rate limits and observability, but every filter adds work. They may buffer bodies, compress/decompress, transform headers or become a shared bottleneck.

#### Deep dive

Gateway timeouts and retry policies can conflict with service policies. Protocol translation may also change behavior.

#### Production angle

Monitor gateway latency separately from service latency.

#### Traps / caveats

- A 504 may be from gateway timeout, not app exception.
- Gateway retries can duplicate unsafe requests.
- Header/body limits may differ from backend limits.

#### Optional Anki

Q: Gateway latency should be?
A: Measured separately from backend service latency.

</details>

<a id="http-perf-011"></a>

<details>
<summary><strong>🧠 HTTP-PERF-011. How do payload shape and JSON serialization affect performance?</strong></summary>

#### Short answer

Large, deeply nested or entity-driven payloads increase CPU, memory, network and database work.

#### Interview answer

Serialization can be expensive if DTOs are huge, contain nested graphs, trigger lazy loading or include unused fields. Good API design returns the shape clients need and avoids serializing whole entities.

#### Deep dive

Jackson is usually fast enough, but allocation pressure, reflection, custom serializers and date/number formatting can matter at high throughput.

#### Production angle

Profile before optimizing. Often reducing payload size beats serializer tuning.

#### Traps / caveats

- Entity serialization can trigger N+1 queries.
- Field selection can complicate authorization.
- Do not log full JSON payloads for performance debugging.

#### Optional Anki

Q: Common JSON performance fix?
A: Return smaller DTO projections.

</details>

<a id="http-perf-012"></a>

<details>
<summary><strong>🧠 HTTP-PERF-012. When should APIs support CDN caching, HTTP/2 or range/resumable downloads?</strong></summary>

#### Short answer

Use them when access patterns justify the operational complexity: static/public hot data, many concurrent clients or large downloadable content.

#### Interview answer

CDN caching fits public or safely cacheable responses. HTTP/2 helps many concurrent requests over fewer connections. Range/resumable downloads fit large files where clients may pause or fail mid-transfer.

#### Deep dive

Each feature has contract and infrastructure implications: cache invalidation, protocol support, object storage, checksums, partial-content status and client behavior.

#### Production angle

These optimizations should be tested end to end with gateways, clients and observability.

#### Traps / caveats

- Do not CDN-cache private data.
- Range support needs correct `206 Partial Content` behavior.
- HTTP/2 changes connection-pool assumptions.

#### Optional Anki

Q: Range requests are useful for?
A: Large resumable downloads.

</details>
