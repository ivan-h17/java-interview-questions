# Asynchronous APIs and long-running operations

---

<a id="rest-async-001"></a>

<details>
<summary><strong>REST-ASYNC-001. How would you design an API for a long-running operation?</strong></summary>

#### Short answer

Return quickly with a job/resource ID, process asynchronously, and expose status/result endpoints.

#### Interview answer

The client submits work with POST. The API validates and creates a job resource, returns 202 with a `Location` to `/jobs/{id}`, and the client polls or receives webhook notification. The job resource exposes state, progress, result link and errors.

#### Deep dive

Use idempotency keys for duplicate submissions and define job states such as accepted, running, succeeded, failed and canceled.

#### Production angle

Long operations should not hold HTTP connections or request threads for minutes.

#### Traps / caveats

- Do not return 202 without a way to track status.
- Persist job state durably.
- Define retry and cancellation behavior.

#### Optional Anki

Q: Long-running API pattern?
A: 202 plus job/status resource.

</details>

<a id="rest-async-002"></a>

<details>
<summary><strong>REST-ASYNC-002. When should an API return 202 Accepted?</strong></summary>

#### Short answer

Return 202 when the request is accepted but processing has not completed.

#### Interview answer

Use 202 for queued or asynchronous work: report generation, file processing, batch import or delayed deletion. The response should describe how to check progress or get results.

#### Deep dive

202 does not guarantee success. It only means the server accepted the request for processing.

#### Production angle

202 lets services protect request threads and handle work with queues/workers.

#### Traps / caveats

- Do not use 202 for completed work.
- Provide status and error reporting.
- Clients need polling/backoff rules.

#### Optional Anki

Q: Does 202 mean success?
A: No, only accepted for processing.

</details>

<a id="rest-async-003"></a>

<details>
<summary><strong>REST-ASYNC-003. How would you design a job status resource?</strong></summary>

#### Short answer

Expose job ID, state, timestamps, progress, links to result, and error details when failed.

#### Interview answer

`GET /jobs/{id}` might return `status`, `createdAt`, `updatedAt`, `progress`, `resultUrl` and problem details for failure. Keep state transitions explicit and stable.

#### Deep dive

For secure systems, the job must be authorized like any other resource. A user should not access another user's job status.

#### Production angle

Job resources improve support because operators can inspect stuck or failed work.

#### Traps / caveats

- Do not expose internal worker exceptions.
- Avoid unbounded retention of old jobs.
- Status polling should be rate-limited.

#### Optional Anki

Q: Job resource should include?
A: State, progress/result links and safe error information.

</details>

<a id="rest-async-004"></a>

<details>
<summary><strong>REST-ASYNC-004. How do you prevent clients from polling too aggressively?</strong></summary>

#### Short answer

Return polling guidance, use backoff, rate limits and optionally webhooks or events.

#### Interview answer

The status response can include `Retry-After` or recommended polling interval. Clients should use exponential backoff or server-provided timing. The server should enforce rate limits.

#### Deep dive

For many clients or long jobs, webhooks or push mechanisms may be more efficient than frequent polling.

#### Production angle

Aggressive polling can overload the API and database even though no real work is progressing.

#### Traps / caveats

- Do not ask clients to poll every second by default.
- Cacheable status responses may help only for some cases.
- Rate-limited polling should return clear 429 responses.

#### Optional Anki

Q: Header useful for polling delay?
A: `Retry-After`.

</details>

<a id="rest-async-005"></a>

<details>
<summary><strong>🧠 REST-ASYNC-005. When would you use webhooks instead of polling?</strong></summary>

#### Short answer

Use webhooks when clients need event notification and polling would be inefficient or too slow.

#### Interview answer

For long-running jobs, payments or external integrations, the server can call a client-provided endpoint when the state changes. This reduces polling load and improves latency.

#### Deep dive

Webhooks require endpoint registration, authentication/signing, retry policy, replay protection and idempotent receivers.

#### Production angle

Webhooks shift reliability problems to delivery, retries and customer endpoint behavior.

#### Traps / caveats

- Webhook receivers may be down.
- Delivery can be duplicated or out of order.
- Sign payloads and include event IDs.

#### Optional Anki

Q: Webhook receiver must be what?
A: Idempotent and authenticated/verified.

</details>

<a id="rest-async-006"></a>

<details>
<summary><strong>🧠 REST-ASYNC-006. How should webhooks be secured and retried?</strong></summary>

#### Short answer

Sign webhook payloads, include timestamps/event IDs, use bounded retries with backoff and require idempotent handling.

#### Interview answer

The sender should sign each webhook using a shared secret or asymmetric key. The receiver verifies signature and timestamp, stores event IDs to handle duplicates, and processes idempotently.

Retries should be bounded, delayed and observable.

#### Deep dive

Do not rely only on source IP allowlists because infrastructure changes and proxies complicate them. Signatures protect payload integrity.

#### Production angle

Webhook failures need dashboards, dead-letter handling and manual replay tools for important integrations.

#### Traps / caveats

- Do not retry forever.
- Do not send secrets in URLs.
- Prevent replay attacks with timestamp windows.

#### Optional Anki

Q: Webhook security basics?
A: Signature, timestamp, event ID and idempotent receiver.

</details>

<a id="rest-async-008"></a>

<details>
<summary><strong>🧠 REST-ASYNC-008. How would you design cancelation and partial failures for long-running or batch operations?</strong></summary>

#### Short answer

Expose cancel requests and represent per-item results for batch operations.

#### Interview answer

Cancelation can be modeled as `POST /jobs/{id}/cancellation` or a state transition. The system should define whether cancelation is best-effort and what happens if work already completed.

For batch operations, return a job result with successes, failures and error details per item.

#### Deep dive

Cancelation must be cooperative in workers. Some external side effects cannot be undone and need compensating actions.

#### Production angle

Partial failure reporting is essential for imports, exports and bulk updates so users can repair only failed items.

#### Traps / caveats

- Cancelation is not always rollback.
- Batch APIs need idempotent item handling.
- Do not lose per-item error diagnostics.

#### Optional Anki

Q: Batch partial failure response should show?
A: Per-item success/failure details.

</details>

<a id="rest-async-009"></a>

<details>
<summary><strong>🧠 REST-ASYNC-009. How should APIs communicate eventual consistency to clients?</strong></summary>

#### Short answer

Be explicit about pending states, status resources, read-your-write limitations and expected delays.

#### Interview answer

If a write is accepted but read models update later, the API should not pretend data is immediately consistent. It can return 202, expose operation status, include resource state like `PROCESSING`, or document that list/search endpoints may lag.

#### Deep dive

Clients need guidance: should they poll, retry, wait, or use a direct resource read from primary data?

#### Production angle

Uncommunicated eventual consistency looks like random bugs to users and support teams.

#### Traps / caveats

- Do not return 200 "done" before visible effects are complete unless documented.
- Replica reads can break create-then-read flows.
- Avoid vague "try again later" without status.

#### Optional Anki

Q: Communicate eventual consistency with?
A: Explicit states, status endpoints and documented visibility delays.

</details>

<a id="rest-async-010"></a>

<details>
<summary><strong>REST-ASYNC-010. How do you make async API operations idempotent?</strong></summary>

#### Short answer

Use idempotency keys or client operation IDs and store them with job/command state.

#### Interview answer

When a client submits async work, it sends an idempotency key. If the request is repeated, the server returns the same job ID or current job status instead of enqueuing duplicate work.

#### Deep dive

Deduplication must happen before enqueueing side effects and must be durable across restarts.

#### Production angle

This prevents duplicate imports, reports, payments and background tasks after timeouts.

#### Traps / caveats

- Duplicate job creation can happen under concurrency.
- Store request fingerprint with the key.
- Define key retention and retry window.

#### Optional Anki

Q: Async idempotency returns what on duplicate?
A: Existing job/status instead of enqueueing duplicate work.

</details>

<a id="rest-async-011"></a>

<details>
<summary><strong>🧠 REST-ASYNC-011. How would you design upload processing that continues after the HTTP request ends?</strong></summary>

#### Short answer

Store the upload durably, create a processing job, return 202/status, and let workers process asynchronously.

#### Interview answer

The API accepts the file or metadata, stores it in object storage or durable staging, creates a processing job and returns a job resource. Workers scan, validate and process the file later.

#### Deep dive

For very large files, direct upload to object storage with pre-signed URLs may be better than proxying bytes through the app.

#### Production angle

This design protects request threads and supports retries, progress, failure reporting and cleanup.

#### Traps / caveats

- Clean up abandoned uploads.
- Scan before making content available.
- Make processing idempotent.

#### Optional Anki

Q: Async upload pattern?
A: Durable upload plus processing job/status resource.

</details>
