# HTTP fundamentals: resources, messages and semantics

---

<a id="http-core-001"></a>

<details>
<summary><strong>HTTP-CORE-001. What is HTTP, and why is it called stateless?</strong></summary>

#### Short answer

HTTP is an application-layer request/response protocol. It is stateless because each request is independent from the protocol's point of view.

#### Interview answer

HTTP defines how clients and servers exchange messages: requests include a method, target, headers and optional body; responses include a status code, headers and optional body.

It is called stateless because the protocol does not require the server to remember a previous request to understand the next one. Applications can still add state through databases, cookies, sessions or tokens.

#### Deep dive

Statelessness makes intermediaries possible: proxies, gateways, caches and load balancers can process requests without understanding a hidden conversation. Application-level sessions are layered on top of HTTP, not part of the core protocol semantics.

#### Production angle

Stateless HTTP supports horizontal scaling and rolling deployments. Hidden server-side session assumptions can create sticky-session needs and failover problems.

#### Traps / caveats

- HTTP statelessness does not mean no authentication.
- Cookies can create stateful application behavior.
- Retrying a request can still be unsafe if the method has side effects.

#### Optional Anki

Q: Why is HTTP stateless?
A: Each request is independent at the protocol level.

</details>

<details>
<summary><strong>HTTP-CORE-002. What is the structure of an HTTP request and response?</strong></summary>

#### Short answer

A request has a method, target, headers and optional body. A response has a status code, headers and optional body.

#### Interview answer

For an HTTP request, the important parts are: method such as GET or POST, request target such as `/orders/123`, headers such as `Authorization` or `Content-Type`, and optionally a body.

For a response, the important parts are: status code such as 200 or 404, response headers such as `Cache-Control` or `Location`, and optionally a response body.

#### Deep dive

HTTP/2 and HTTP/3 encode messages differently on the wire, but the semantic model remains methods, targets, headers, status and content. This is why application code can usually reason about HTTP semantics without caring about frame-level details.

#### Production angle

Many bugs come from putting information in the wrong part of the message: secrets in URLs, missing `Content-Type`, wrong status codes or bodies on responses that clients expect to be empty.

#### Traps / caveats

- Do not put credentials or sensitive data in query strings.
- Request body support depends on method semantics and server/framework behavior.
- Headers are metadata, not a substitute for authorization checks.

#### Optional Anki

Q: Main parts of HTTP request/response?
A: Request: method, target, headers, body. Response: status, headers, body.

</details>

<details>
<summary><strong>HTTP-CORE-004. What is the difference between URI, URL and URN?</strong></summary>

#### Short answer

A URI identifies a resource. A URL is a URI that tells how to locate it. A URN is a URI that names it without necessarily locating it.

#### Interview answer

In everyday API work, people usually say URL when they mean the web address of an endpoint, such as `https://api.example.com/orders/123`.

More precisely, URI is the broader term. URL is location-oriented and includes scheme, host and path. URN is name-oriented, like a persistent identifier.

#### Deep dive

For REST APIs, the practical concern is stable resource identification: paths should describe resources, query parameters should describe selection or filtering, and identifiers should not leak internal implementation unnecessarily.

#### Production angle

Clear URI design improves routing, gateway policy, logs, metrics and documentation. Poorly designed URLs can expose tenant IDs, internal database IDs or sensitive search parameters.

#### Traps / caveats

- In interviews, do not overfocus on terminology trivia.
- Fragments are handled client-side and are not sent to the server.
- Query strings often appear in logs, so avoid secrets there.

#### Optional Anki

Q: URI vs URL?
A: URI identifies; URL identifies and locates.

</details>

<details>
<summary><strong>HTTP-CORE-005. What is an origin, and why does it matter for browser clients?</strong></summary>

#### Short answer

An origin is the combination of scheme, host and port. Browsers use origins for same-origin policy and CORS decisions.

#### Interview answer

`https://app.example.com` and `https://api.example.com` are different origins because the host differs. `http://example.com` and `https://example.com` are also different because the scheme differs.

Origins matter because browser security rules restrict what frontend code can read across origins unless the server explicitly allows it with CORS headers.

#### Deep dive

The same-origin policy protects users from malicious pages reading sensitive responses from another site. CORS relaxes that policy in a controlled way; it is not authentication and does not protect non-browser clients.

#### Production angle

CORS misconfiguration can break frontend deployments or accidentally expose credentialed APIs. API teams should document allowed origins per environment.

#### Traps / caveats

- CORS is enforced by browsers, not by curl or backend services.
- `Access-Control-Allow-Origin: *` cannot be used with credentials.
- Origin is not the same as site or domain.

#### Optional Anki

Q: What defines an origin?
A: Scheme, host and port.

</details>

<a id="http-core-006"></a>

<details>
<summary><strong>🧠 HTTP-CORE-006. What does HTTPS/TLS protect, and what does it not protect?</strong></summary>

#### Short answer

HTTPS protects data in transit with encryption, integrity and server authentication. It does not validate business authorization or secure data after it reaches either endpoint.

#### Interview answer

TLS prevents passive network observers from reading traffic and helps clients verify they are talking to the expected server. It also protects against many in-transit tampering attacks.

It does not stop a legitimate client from sending malicious input, does not prevent broken authorization, and does not protect logs, databases or memory after the service receives the request.

#### Deep dive

TLS configuration still matters: certificate validity, hostname verification, supported protocol versions, trust stores and termination point. If TLS terminates at a load balancer, internal traffic may need separate protection depending on threat model.

#### Production angle

Always use HTTPS for APIs, especially when tokens, cookies or personal data are involved. Also secure logs, headers, tracing and backend-to-backend traffic where appropriate.

#### Traps / caveats

- HTTPS is not authorization.
- TLS termination changes where plaintext exists.
- Do not disable certificate or hostname verification in Java clients.

#### Optional Anki

Q: What does HTTPS not solve?
A: Authorization, input validation, endpoint compromise and data-at-rest/log exposure.

</details>

<a id="http-core-008"></a>

<details>
<summary><strong>HTTP-CORE-008. Why does HTTP semantics matter even if you use Spring MVC?</strong></summary>

#### Short answer

Spring handles mechanics, but your API contract still depends on HTTP methods, status codes, headers, caching and retries.

#### Interview answer

Spring MVC can route requests and serialize JSON, but it cannot decide correct semantics for your domain. You still need to choose whether an operation is GET, POST, PUT or PATCH; whether failures are 400, 409 or 500; whether a response can be cached; and whether a request can be retried safely.

#### Deep dive

Framework abstractions can hide protocol details until production: missing `Content-Type`, wrong status codes, buffered bodies, bad CORS config, or ambiguous error responses. Senior engineers should know the HTTP contract beneath the annotations.

#### Production angle

HTTP semantics affect client SDKs, API gateways, load balancers, caches, browser behavior, monitoring and incident response.

#### Traps / caveats

- `@PostMapping` for every endpoint loses useful semantics.
- Returning 200 for every error breaks clients and observability.
- Spring defaults should be reviewed for public API contracts.

#### Optional Anki

Q: Why know HTTP if Spring abstracts it?
A: Because clients, gateways, caches and retries rely on HTTP semantics.

</details>

<details>
<summary><strong>🧠 HTTP-CORE-009. What operational differences between HTTP/1.1, HTTP/2 and HTTP/3 matter for Java services?</strong></summary>

#### Short answer

HTTP/2 and HTTP/3 improve connection use and multiplexing, but they change tuning, proxy behavior, observability and failure modes.

#### Interview answer

HTTP/1.1 usually uses multiple TCP connections for concurrency. HTTP/2 multiplexes many streams over one TCP connection, reducing connection overhead but making flow control and connection-level issues more important. HTTP/3 uses QUIC over UDP, which can reduce some TCP head-of-line blocking and improve connection migration.

For most Java developers, the key is not frame internals but operational impact: client/server support, gateways, load balancers, timeouts, connection pools and metrics.

#### Deep dive

HTTP/2 multiplexing does not remove all bottlenecks. A single connection can still hit flow-control, server concurrency or packet-loss effects. Some intermediaries terminate one protocol and speak another upstream, so the protocol seen by the app may differ from the client-facing protocol.

#### Production angle

Validate protocol support end to end before enabling it. Monitor latency, connection counts, stream resets, gateway behavior and client compatibility.

#### Traps / caveats

- HTTP/2 does not make slow downstreams safe.
- One connection with many streams changes pool-sizing assumptions.
- Protocol upgrades can expose bugs in proxies or client libraries.

#### Optional Anki

Q: Main HTTP/2 operational change?
A: Multiplexed streams over fewer connections, with different pooling and flow-control concerns.

</details>
