# Headers, media types and content negotiation

---

<a id="http-head-001"></a>

<details>
<summary><strong>HTTP-HEAD-001. What is the difference between Content-Type and Accept?</strong></summary>

#### Short answer

`Content-Type` describes the body being sent; `Accept` describes what response media types the client can handle.

#### Interview answer

For a JSON request, the client sends `Content-Type: application/json`. If it wants JSON back, it may send `Accept: application/json`.

Servers use `Content-Type` to choose how to parse the request body and `Accept` to choose a response representation.

#### Deep dive

If `Content-Type` is missing or unsupported, the server may return 415. If the server cannot produce an acceptable response, it may return 406, though many APIs simplify this.

#### Production angle

Wrong headers cause confusing client bugs, especially with generated clients, file uploads and APIs supporting multiple formats.

#### Traps / caveats

- `Content-Type` is not the same as `Accept`.
- JSON endpoints should reject unexpected media types deliberately.
- Charset handling should be explicit where relevant.

#### Optional Anki

Q: Content-Type vs Accept?
A: Content-Type says what I send; Accept says what I can receive.

</details>

<a id="http-head-002"></a>

<details>
<summary><strong>HTTP-HEAD-002. What is content negotiation?</strong></summary>

#### Short answer

Content negotiation is selecting the best representation for a response based on client preferences and server capabilities.

#### Interview answer

A client can use headers such as `Accept` and `Accept-Language` to express preferred formats or languages. The server chooses a supported representation, for example JSON, XML or PDF.

Most backend APIs keep negotiation simple and support one main JSON media type.

#### Deep dive

Negotiation can also affect caching. If responses vary by `Accept-Language` or `Accept-Encoding`, caches need `Vary` to avoid serving the wrong representation.

#### Production angle

Explicit media types help versioning, generated clients and API gateways. Overly complex negotiation makes testing and caching harder.

#### Traps / caveats

- Do not implement negotiation accidentally through inconsistent controller methods.
- Document supported media types.
- Be careful when caches ignore `Vary`.

#### Optional Anki

Q: What is content negotiation?
A: Choosing a response representation based on client headers and server support.

</details>

<a id="http-head-004"></a>

<details>
<summary><strong>HTTP-HEAD-004. What is the Location header used for?</strong></summary>

#### Short answer

`Location` points to another URI, commonly the newly created resource after 201 or a redirect target with 3xx.

#### Interview answer

For `POST /orders`, a successful creation can return `201 Created` with `Location: /orders/{id}`. Clients can use that URI to fetch the created resource.

`Location` is also used in redirects, but REST APIs most often discuss it with creation and asynchronous workflows.

#### Deep dive

For `202 Accepted`, APIs may use `Location` to point to a job/status resource. If using absolute vs relative URIs, be consistent and account for proxies.

#### Production angle

Correct `Location` headers improve generated clients, documentation and API consistency.

#### Traps / caveats

- Do not return 201 without identifying the created resource when one exists.
- Reverse proxies can affect generated absolute URLs.
- Do not expose internal service hostnames.

#### Optional Anki

Q: `Location` after 201?
A: URI of the created resource.

</details>

<a id="http-head-005"></a>

<details>
<summary><strong>HTTP-HEAD-005. What is the Retry-After header?</strong></summary>

#### Short answer

`Retry-After` tells the client how long to wait before retrying, either as seconds or an HTTP date.

#### Interview answer

It is useful with `429 Too Many Requests` and `503 Service Unavailable`. It gives clients a concrete backoff hint instead of forcing them to guess.

Good clients should combine `Retry-After` with their own deadlines and retry budgets.

#### Deep dive

`Retry-After` is advisory. Clients may ignore it, and servers should still protect themselves with rate limits and load shedding.

#### Production angle

Returning retry guidance reduces retry storms during overload and improves third-party API integration.

#### Traps / caveats

- Do not return impossible retry times.
- Clients must parse both seconds and date formats.
- Retry guidance does not make non-idempotent operations safe.

#### Optional Anki

Q: When use `Retry-After`?
A: With rate limits or temporary unavailability to guide client backoff.

</details>

<a id="http-head-006"></a>

<details>
<summary><strong>🧠 HTTP-HEAD-006. How do ETag, If-None-Match and If-Match work?</strong></summary>

#### Short answer

`ETag` identifies a resource representation version. `If-None-Match` supports cache validation; `If-Match` supports conditional updates.

#### Interview answer

The server returns an `ETag` with a resource. Later, the client can send `If-None-Match` on GET; if unchanged, the server returns 304. For updates, the client can send `If-Match`; if the ETag no longer matches, the server rejects the update with 412.

#### Deep dive

ETags can be strong or weak. Strong ETags imply byte-equivalent representation, while weak ETags are useful for cache validation but not always for concurrency control.

#### Production angle

ETags reduce bandwidth and help prevent lost updates in APIs with concurrent edits.

#### Traps / caveats

- ETag generation must change when relevant representation changes.
- Do not use weak validators for critical update preconditions without understanding semantics.
- Personalized responses need user-aware cache behavior.

#### Optional Anki

Q: `If-Match` is used for what?
A: Conditional updates to avoid overwriting changed resources.

</details>

<a id="http-head-007"></a>

<details>
<summary><strong>HTTP-HEAD-007. What are Cache-Control and Expires?</strong></summary>

#### Short answer

They are response headers that tell clients and caches how a response may be cached and for how long.

#### Interview answer

`Cache-Control` is the modern, more flexible header. It can specify directives like `max-age`, `no-cache`, `no-store`, `private` and `public`. `Expires` provides an absolute expiration time and is less expressive.

#### Deep dive

`no-cache` means the cached response must be revalidated before reuse. `no-store` means do not store it at all. This distinction is important for sensitive data.

#### Production angle

Correct caching headers reduce load and latency. Wrong caching headers can leak personal data or serve stale business-critical information.

#### Traps / caveats

- `no-cache` does not mean "do not store".
- Personalized responses usually need `private` or `no-store`.
- Shared caches require careful `Vary` and authorization behavior.

#### Optional Anki

Q: `no-cache` vs `no-store`?
A: Revalidate before reuse vs do not store.

</details>

<a id="http-head-008"></a>

<details>
<summary><strong>HTTP-HEAD-008. What is the correlation ID / request ID header pattern?</strong></summary>

#### Short answer

It is a pattern of passing a unique request identifier through services so logs, metrics and traces can be connected.

#### Interview answer

A gateway or service creates or accepts a request ID, then propagates it to downstream calls and logs it. When a user reports a problem, engineers can find all logs for that request.

It is not a security token and should not be trusted for authorization.

#### Deep dive

Modern tracing often uses W3C Trace Context (`traceparent`) for distributed traces. A separate request ID may still be useful for support workflows and access logs.

#### Production angle

Correlation IDs are essential during incidents involving multiple Java services, gateways and async boundaries.

#### Traps / caveats

- Validate/sanitize externally supplied IDs before logging.
- Avoid high-cardinality labels in metrics.
- Propagate consistently through HTTP clients, messaging and async execution.

#### Optional Anki

Q: Why use correlation IDs?
A: To connect logs and diagnostics across services for one request.

</details>

<a id="http-head-010"></a>

<details>
<summary><strong>🧠 HTTP-HEAD-010. Why can trusting client-supplied forwarding headers be dangerous?</strong></summary>

#### Short answer

Headers like `X-Forwarded-For` can be spoofed by clients unless generated and sanitized by trusted proxies.

#### Interview answer

Applications often use forwarding headers to know original client IP, scheme or host behind a proxy. If the app trusts arbitrary client-supplied values, attackers can bypass IP allowlists, poison logs, generate wrong URLs or confuse security logic.

Only trust forwarding headers from known infrastructure boundaries.

#### Deep dive

The edge proxy should strip incoming untrusted forwarding headers and add canonical ones. The application should trust only configured proxy chains.

#### Production angle

This matters for rate limiting, audit logging, redirects, tenant routing and security decisions.

#### Traps / caveats

- Do not use raw `X-Forwarded-For` as identity.
- Configure Spring/proxy header support deliberately.
- Host header and forwarded host can affect generated links.

#### Optional Anki

Q: Why sanitize forwarding headers?
A: Clients can spoof them unless the trusted edge rewrites them.

</details>

<details>
<summary><strong>🧠 HTTP-HEAD-011. How do Transfer-Encoding and Content-Length differ, and why can conflicts be dangerous?</strong></summary>

#### Short answer

`Content-Length` gives a known body size; `Transfer-Encoding` describes how the body is transferred, such as chunked. Conflicts can cause request smuggling or parsing differences.

#### Interview answer

With `Content-Length`, the receiver knows how many bytes to read. With chunked transfer, the body is sent in chunks and ends with a terminator. If proxies and backend servers disagree about which header wins, an attacker may desynchronize request parsing.

#### Deep dive

Most application developers do not implement this parsing directly, but they should understand why edge proxies, servlet containers and gateway security updates matter.

#### Production angle

Reject ambiguous requests at the edge. Keep proxies, gateways and servlet containers patched and consistently configured.

#### Traps / caveats

- Do not forward malformed framing headers blindly.
- Request smuggling often exploits parser differences between intermediaries.
- Application logs may not show the original malformed wire request.

#### Optional Anki

Q: Why are conflicting body length headers dangerous?
A: They can make proxies and backends parse different request boundaries.

</details>
