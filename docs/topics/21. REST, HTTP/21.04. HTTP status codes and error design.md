# HTTP status codes and error design

---

<a id="http-status-002"></a>

<details>
<summary><strong>HTTP-STATUS-002. When should you return 200, 201, 202 or 204?</strong></summary>

#### Short answer

Use 200 for successful responses with content, 201 for created resources, 202 for accepted asynchronous work, and 204 for success with no body.

#### Interview answer

`200 OK` is the general successful response. `201 Created` is appropriate when a new resource was created, usually with a `Location` header. `202 Accepted` means the request was accepted but processing is not finished. `204 No Content` means success but no response body.

#### Deep dive

The choice communicates client behavior. A 202 should normally give a way to check status. A 201 should identify the created resource. A 204 should not include a JSON body.

#### Production angle

Correct 2xx codes make generated clients, monitoring and API documentation clearer.

#### Traps / caveats

- Do not return 200 with an error object.
- Do not use 202 if the work is already complete.
- Do not send response bodies with 204.

#### Optional Anki

Q: What does 202 mean?
A: Accepted for processing, not necessarily completed.

</details>

<a id="http-status-003"></a>

<details>
<summary><strong>🧠 HTTP-STATUS-003. When should you return 400 vs 422?</strong></summary>

#### Short answer

Use 400 for malformed or invalid requests generally; use 422 if your API distinguishes syntactically valid but semantically invalid content.

#### Interview answer

Many APIs use 400 for all validation failures, which is acceptable if consistent. Some use 422 when JSON is valid and parseable but violates business validation, such as an end date before a start date.

The important part is consistency and a useful error body.

#### Deep dive

For example, invalid JSON syntax is clearly 400. A valid JSON request with unsupported business values might be 400 or 422 by policy. Public APIs should document this.

#### Production angle

Clients should be able to distinguish fixable user input errors from server or dependency failures.

#### Traps / caveats

- Do not mix 400 and 422 randomly.
- Validation error details matter more than the exact choice.
- Avoid exposing internal validator or exception names.

#### Optional Anki

Q: 400 vs 422?
A: 400 is general bad request; 422 can mean valid syntax but invalid semantics by API policy.

</details>

<a id="http-status-004"></a>

<details>
<summary><strong>HTTP-STATUS-004. What is the difference between 401 and 403?</strong></summary>

#### Short answer

401 means authentication is missing or invalid; 403 means authentication may be valid but access is forbidden.

#### Interview answer

Return 401 when the client needs to authenticate or provide a valid token. Return 403 when the caller is known but lacks permission for the action or resource.

The names are confusing because `401 Unauthorized` historically means unauthenticated.

#### Deep dive

For bearer-token APIs, invalid, expired or missing tokens are usually 401. Valid token but missing scope/role/ownership is usually 403.

#### Production angle

Correct distinction helps clients refresh tokens, redirect to login, or show permission errors.

#### Traps / caveats

- Do not leak whether sensitive resources exist.
- Some APIs return 404 instead of 403 for resource enumeration protection.
- Gateway and service behavior should be consistent.

#### Optional Anki

Q: 401 vs 403?
A: 401 authenticate; 403 authenticated/known but forbidden.

</details>

<a id="http-status-005"></a>

<details>
<summary><strong>🧠 HTTP-STATUS-005. When is it acceptable to return 404 instead of 403?</strong></summary>

#### Short answer

Return 404 instead of 403 when revealing that the resource exists would leak sensitive information.

#### Interview answer

If `/users/{id}/documents/{docId}` belongs to another user, returning 403 may confirm the document exists. Some APIs deliberately return 404 for unauthorized resource access to reduce enumeration risk.

This policy should be consistent and not replace proper authorization.

#### Deep dive

The API can still log the real reason internally. The public response hides existence; telemetry and audit logs preserve security visibility.

#### Production angle

This matters in multi-tenant systems and systems with private resources, account IDs or documents.

#### Traps / caveats

- 404 masking must not hide authorization bugs from monitoring.
- Do not rely on obscurity instead of ownership checks.
- Use consistent response timing where enumeration risk is serious.

#### Optional Anki

Q: Why return 404 for forbidden resource?
A: To avoid revealing that the resource exists.

</details>

<a id="http-status-007"></a>

<details>
<summary><strong>HTTP-STATUS-007. When should you return 409 Conflict?</strong></summary>

#### Short answer

Return 409 when the request conflicts with current resource state or a business uniqueness/concurrency rule.

#### Interview answer

Examples include duplicate username, state transition not allowed, optimistic locking conflict, or trying to cancel an already shipped order.

409 tells the client the request may be valid structurally, but it cannot be applied because of current state.

#### Deep dive

409 is often better than 400 for conflicts that clients might resolve by refreshing state, choosing another value or retrying after a state change.

#### Production angle

Clear conflict responses help clients implement optimistic UI, retries and user-friendly messages.

#### Traps / caveats

- Do not use 409 for every validation failure.
- Include enough machine-readable detail for clients.
- Race conditions still need database constraints or locking.

#### Optional Anki

Q: What does 409 indicate?
A: A request conflicts with current resource or business state.

</details>

<a id="http-status-008"></a>

<details>
<summary><strong>🧠 HTTP-STATUS-008. When should you return 412 Precondition Failed?</strong></summary>

#### Short answer

Return 412 when a conditional request precondition, such as `If-Match`, evaluates false.

#### Interview answer

If a client sends `If-Match` with an old ETag while updating a resource, the server should reject the update with 412 because the resource changed since the client last read it.

This prevents lost updates without forcing heavy locking.

#### Deep dive

412 is tied to HTTP conditional request headers. If the conflict is not expressed as an HTTP precondition, 409 may be more appropriate.

#### Production angle

412 is useful in collaborative editing, account settings, inventory updates and any API where clients edit stale resource versions.

#### Traps / caveats

- Do not confuse 412 with generic validation errors.
- ETags must reflect the version being protected.
- Weak ETags are not suitable for all update preconditions.

#### Optional Anki

Q: When use 412?
A: A conditional request precondition failed.

</details>

<a id="http-status-010"></a>

<details>
<summary><strong>HTTP-STATUS-010. When should you return 429 Too Many Requests?</strong></summary>

#### Short answer

Return 429 when the client exceeded a rate limit, quota or request budget.

#### Interview answer

429 is a client-specific overload or quota response. It should often include `Retry-After` or rate-limit metadata so the client knows when or how to slow down.

Use it for per-user, per-token, per-IP or per-tenant limits, not for every server-side failure.

#### Deep dive

429 differs from 503: 429 usually says "this caller is sending too much"; 503 says "the service is unavailable or overloaded more generally".

#### Production angle

429 protects shared systems from abuse and noisy clients. Good client SDKs should respect it.

#### Traps / caveats

- Rate limits must align with business tiers.
- Avoid high-cardinality metrics from raw API keys or IPs.
- Do not return 429 after already doing expensive work.

#### Optional Anki

Q: What does 429 mean?
A: The caller exceeded a rate limit or quota.

</details>

<a id="http-status-011"></a>

<details>
<summary><strong>HTTP-STATUS-011. When should you return 500 Internal Server Error?</strong></summary>

#### Short answer

Return 500 for unexpected server-side failures that are not the client's fault and are not better classified.

#### Interview answer

500 is appropriate for unhandled exceptions, bugs or unexpected internal failures. It should not be used for validation errors, missing resources, authorization failures or known dependency gateway errors that have better 4xx/5xx mappings.

#### Deep dive

The public response should be generic, while logs and traces contain diagnostic details with correlation IDs.

#### Production angle

500 rates should be monitored as service errors. Frequent 500s usually mean bugs, unclassified failures or missing error handling.

#### Traps / caveats

- Do not expose stack traces.
- Do not hide client errors as 500.
- Preserve correlation IDs for debugging.

#### Optional Anki

Q: What is 500 for?
A: Unexpected server-side failure.

</details>

<a id="http-status-012"></a>

<details>
<summary><strong>🧠 HTTP-STATUS-012. When should you return 502, 503 or 504?</strong></summary>

#### Short answer

Use 502 for bad upstream response, 503 for temporary unavailability/overload, and 504 for upstream timeout.

#### Interview answer

In gateway or service-to-service flows, 502 means an upstream returned an invalid or failed response. 503 means the service is temporarily unavailable, overloaded or in maintenance. 504 means a gateway or service timed out waiting for an upstream.

#### Deep dive

Application services often map downstream failures carefully: a required dependency timeout may become 504, while optional dependency failure may degrade the response.

#### Production angle

These codes help clients decide whether to retry and help operators identify dependency vs local failures.

#### Traps / caveats

- Do not retry every 5xx blindly.
- 503 should often include `Retry-After` when known.
- Hiding dependency failures as 500 loses diagnostic signal.

#### Optional Anki

Q: 504 means what?
A: Timeout waiting for an upstream/dependency.

</details>

<a id="http-status-013"></a>

<details>
<summary><strong>HTTP-STATUS-013. What is the difference between 503 and 429?</strong></summary>

#### Short answer

503 is service unavailability; 429 is caller-specific rate limiting or quota exhaustion.

#### Interview answer

Use 429 when a particular client, user, token or tenant exceeded its allowed request rate. Use 503 when the service as a whole or a dependency is temporarily unavailable or overloaded.

Both may be retryable, but clients should back off and respect `Retry-After`.

#### Deep dive

The distinction matters for client behavior and dashboards. A spike in 429 may mean abuse or wrong client behavior; a spike in 503 may mean platform or dependency failure.

#### Production angle

Separate metrics for 429 and 503 prevent confusing client throttling with service incidents.

#### Traps / caveats

- Do not use 429 for every overload condition.
- Do not use 503 for a single caller exceeding quota.
- Include machine-readable retry guidance when possible.

#### Optional Anki

Q: 429 vs 503?
A: 429 caller is over limit; 503 service is unavailable/overloaded.

</details>

<a id="http-status-014"></a>

<details>
<summary><strong>HTTP-STATUS-014. How should validation errors be represented in REST APIs?</strong></summary>

#### Short answer

Return a 4xx response with structured field-level errors, stable codes and safe messages.

#### Interview answer

A good validation error response includes a general error type/code, human-readable message, field paths, rejected values only when safe, and per-field messages. It should be predictable for clients and not expose internal class names.

#### Deep dive

For nested JSON, field paths like `items[2].quantity` are useful. For cross-field validation, attach the error to a logical object or use a global validation error list.

#### Production angle

Consistent validation responses reduce frontend special cases and support localization and analytics on common input problems.

#### Traps / caveats

- Do not include secrets or full payloads.
- Do not expose Java exception names.
- Keep error codes stable across releases.

#### Optional Anki

Q: What should validation errors include?
A: Stable code/message plus safe field-level details.

</details>

<a id="http-status-015"></a>

<details>
<summary><strong>HTTP-STATUS-015. What is Problem Details for HTTP APIs?</strong></summary>

#### Short answer

Problem Details is a standard JSON/XML error format for HTTP APIs with fields like `type`, `title`, `status`, `detail` and `instance`.

#### Interview answer

Problem Details gives APIs a consistent shape for errors instead of custom ad hoc structures. It separates HTTP status from machine-readable problem type and allows extension fields for domain-specific details.

In Spring, `ProblemDetail` can be used to return this style of response.

#### Deep dive

The `type` should identify the problem category, ideally with a stable URI. `detail` is for this occurrence, while `title` is a short summary of the problem type.

#### Production angle

Problem Details improves consistency across services, gateways and client SDKs.

#### Traps / caveats

- Do not put stack traces in `detail`.
- Keep `type` stable.
- Add extensions carefully and document them.

#### Optional Anki

Q: Key Problem Details fields?
A: `type`, `title`, `status`, `detail`, `instance`.

</details>

<a id="http-status-016"></a>

<details>
<summary><strong>HTTP-STATUS-016. Should error responses expose internal exception details?</strong></summary>

#### Short answer

No. Public error responses should be safe and stable; internal details belong in logs and traces.

#### Interview answer

Clients need enough information to fix the request or handle the failure. They do not need stack traces, SQL messages, internal hostnames, class names or dependency secrets.

Use correlation IDs so support and engineers can find the detailed internal record.

#### Deep dive

Error messages are part of the API contract. Exposing exception text couples clients to implementation details and can leak security-sensitive information.

#### Production angle

Sanitized errors reduce information disclosure risk and make API behavior more stable across refactors.

#### Traps / caveats

- Do not log raw sensitive payloads either.
- Avoid different detailed messages that enable resource enumeration.
- Keep internal diagnostics accessible to operators.

#### Optional Anki

Q: Where should stack traces go?
A: Internal logs/traces, not public API responses.

</details>
