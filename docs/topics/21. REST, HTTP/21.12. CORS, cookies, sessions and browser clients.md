# CORS, cookies, sessions and browser clients

---

<a id="http-browser-001"></a>

<details>
<summary><strong>HTTP-BROWSER-001. What are CORS and the Same-Origin Policy?</strong></summary>

#### Short answer

The Same-Origin Policy restricts browser JavaScript from reading cross-origin responses; CORS is the server-controlled relaxation mechanism.

#### Interview answer

Browsers protect users by limiting scripts from one origin reading data from another origin. CORS lets an API say which origins, methods and headers are allowed for browser clients.

#### Deep dive

CORS is not authentication. It controls browser read access. Non-browser clients can call the API regardless, so server-side auth is still required.

#### Production angle

CORS misconfiguration can break frontend apps or expose credentialed responses to unintended origins.

#### Traps / caveats

- CORS is enforced by browsers.
- It is not a backend-to-backend security boundary.
- Allowed origins should be environment-specific.

#### Optional Anki

Q: What is CORS?
A: Browser cross-origin access control using server response headers.

</details>

<a id="http-browser-002"></a>

<details>
<summary><strong>HTTP-BROWSER-002. What is a CORS preflight request?</strong></summary>

#### Short answer

A preflight is an OPTIONS request the browser sends to check whether a cross-origin request is allowed.

#### Interview answer

Before certain cross-origin requests, the browser sends OPTIONS with requested method and headers. The server responds with allowed origins, methods and headers. If allowed, the browser sends the actual request.

#### Deep dive

Preflight happens for non-simple methods, custom headers or certain content types. It can be cached with `Access-Control-Max-Age`.

#### Production angle

APIs must allow unauthenticated OPTIONS handling where appropriate, otherwise real requests never reach controllers.

#### Traps / caveats

- Preflight failure is a browser-side block, not necessarily an API 500.
- Auth filters can accidentally reject OPTIONS.
- Curl does not reproduce browser CORS behavior by default.

#### Optional Anki

Q: Preflight method?
A: OPTIONS.

</details>

<a id="http-browser-003"></a>

<details>
<summary><strong>HTTP-BROWSER-003. Which headers are used in CORS?</strong></summary>

#### Short answer

Common headers include `Origin`, `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers` and `Access-Control-Allow-Credentials`.

#### Interview answer

The browser sends `Origin`. For preflight it also sends `Access-Control-Request-Method` and `Access-Control-Request-Headers`. The server responds with allowed origin, methods, headers and credentials policy.

#### Deep dive

When credentials are used, the allowed origin must be explicit, not `*`.

#### Production angle

CORS headers are often added at gateways or Spring config; duplicate/conflicting config causes hard-to-debug frontend failures.

#### Traps / caveats

- `Access-Control-Allow-Origin: *` with credentials is invalid.
- CORS headers do not grant application permissions.
- Missing allowed custom headers breaks bearer-token requests.

#### Optional Anki

Q: Which request header identifies browser origin?
A: `Origin`.

</details>

<a id="http-browser-004"></a>

<details>
<summary><strong>HTTP-BROWSER-004. Why is Access-Control-Allow-Origin: * dangerous with credentials?</strong></summary>

#### Short answer

Credentialed requests can expose user-specific responses; wildcard origins would allow any site to read them.

#### Interview answer

If cookies or authorization credentials are included, the server must explicitly choose trusted origins. A wildcard would let malicious websites make the user's browser send credentials and read the response.

#### Deep dive

Browsers reject `*` with `Access-Control-Allow-Credentials: true`, but misconfigured dynamic origin reflection can create a similar risk.

#### Production angle

Use allowlists and review origin matching carefully, especially with subdomains and preview environments.

#### Traps / caveats

- Do not reflect any `Origin` blindly.
- Wildcard subdomain matching can be too broad.
- CORS does not protect against CSRF by itself.

#### Optional Anki

Q: Credentials plus wildcard origin?
A: Unsafe/invalid; use explicit trusted origins.

</details>

<a id="http-browser-005"></a>

<details>
<summary><strong>HTTP-BROWSER-005. What is the difference between cookies and bearer tokens?</strong></summary>

#### Short answer

Cookies are automatically sent by browsers for matching sites; bearer tokens are usually sent explicitly in headers by client code.

#### Interview answer

Cookie-based auth is convenient for browser apps but needs CSRF protection depending on SameSite and request patterns. Bearer tokens in `Authorization` avoid automatic cross-site sending but are exposed to theft if stored unsafely in browser JavaScript-accessible storage.

#### Deep dive

The right choice depends on app type, threat model and identity provider. Both need TLS, expiration and secure storage.

#### Production angle

Token/cookie choice affects CSRF, XSS impact, logout, refresh flows and CORS configuration.

#### Traps / caveats

- Bearer tokens are not safer if stored in `localStorage` and XSS exists.
- Cookies need `HttpOnly`, `Secure` and `SameSite`.
- Logout is harder with stateless long-lived JWTs.

#### Optional Anki

Q: Cookie vs bearer token key difference?
A: Browser sends cookies automatically; bearer token is explicitly attached.

</details>

<a id="http-browser-006"></a>

<details>
<summary><strong>HTTP-BROWSER-006. What are HttpOnly, Secure and SameSite cookie attributes?</strong></summary>

#### Short answer

`HttpOnly` blocks JavaScript access, `Secure` sends only over HTTPS, and `SameSite` controls cross-site sending.

#### Interview answer

`HttpOnly` reduces token theft through XSS. `Secure` prevents sending cookies over plain HTTP. `SameSite=Lax` or `Strict` can reduce CSRF risk by limiting cross-site cookie sending.

#### Deep dive

`SameSite=None` is required for some cross-site flows but must be paired with `Secure`.

#### Production angle

Cookie attributes are part of API security and should be set consistently by authentication infrastructure.

#### Traps / caveats

- `HttpOnly` does not stop CSRF.
- `SameSite` behavior affects login redirects.
- Local development often differs from HTTPS production.

#### Optional Anki

Q: Which cookie flag blocks JS access?
A: `HttpOnly`.

</details>

<a id="http-browser-007"></a>

<details>
<summary><strong>🧠 HTTP-BROWSER-007. When is CSRF relevant for REST APIs?</strong></summary>

#### Short answer

CSRF is relevant when browsers automatically send credentials, usually cookies, to state-changing endpoints.

#### Interview answer

If authentication uses cookies, a malicious site may cause the browser to send a POST to your API with the user's cookies. CSRF protection, SameSite cookies or explicit anti-CSRF tokens may be needed.

Bearer-token APIs using `Authorization` headers are less exposed to CSRF because other sites cannot add that header without CORS permission, but they have different token theft risks.

#### Deep dive

CSRF is about unwanted authenticated requests, not reading the response.

#### Production angle

CSRF controls must match the browser auth model. Disabling CSRF blindly in Spring Security can be wrong for cookie-based APIs.

#### Traps / caveats

- CORS is not CSRF protection.
- Safe methods should not change state.
- SameSite may not cover every flow.

#### Optional Anki

Q: CSRF mainly affects which auth style?
A: Cookie/session auth in browsers.

</details>

<a id="http-browser-008"></a>

<details>
<summary><strong>🧠 HTTP-BROWSER-008. How can XSS affect REST clients and token storage?</strong></summary>

#### Short answer

XSS lets attacker-controlled JavaScript act as the user, steal accessible tokens and call APIs from the trusted origin.

#### Interview answer

If tokens are stored in JavaScript-accessible storage, XSS can read and exfiltrate them. Even with `HttpOnly` cookies, XSS can still perform actions through the app unless additional protections exist.

#### Deep dive

Defenses include output encoding, CSP, avoiding unsafe HTML injection, `HttpOnly` cookies, short-lived tokens and careful frontend dependency hygiene.

#### Production angle

API teams should not assume frontend XSS is irrelevant; it directly affects API misuse and token compromise.

#### Traps / caveats

- `HttpOnly` protects token reading, not action execution.
- Local storage is convenient but risky.
- API scopes and rate limits reduce blast radius.

#### Optional Anki

Q: XSS impact on bearer tokens?
A: JavaScript-accessible tokens can be stolen.

</details>
