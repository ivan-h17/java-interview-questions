# Resource naming, endpoint design and URL structure

---

<a id="rest-uri-001"></a>

<details>
<summary><strong>REST-URI-001. What is resource-oriented API design?</strong></summary>

#### Short answer

Resource-oriented design exposes domain concepts as resources with stable URIs and uses HTTP methods to operate on them.

#### Interview answer

Instead of designing endpoints as arbitrary functions, you identify resources such as orders, invoices, users, sessions or report jobs. The URI identifies the resource, while the method expresses the action: GET retrieves, POST creates/submits, PUT replaces, PATCH updates partially and DELETE removes.

#### Deep dive

Resources do not have to map one-to-one to database tables. They should model the public API contract, not internal persistence.

#### Production angle

Good resource design makes authorization, documentation, logging and client SDKs easier to reason about.

#### Traps / caveats

- Do not expose persistence internals blindly.
- Not every business operation is CRUD.
- Resource naming must match domain language.

#### Optional Anki

Q: What is resource-oriented design?
A: Modeling API concepts as resources identified by URIs and manipulated with HTTP methods.

</details>

<a id="rest-uri-002"></a>

<details>
<summary><strong>REST-URI-002. Should you use verbs in URLs?</strong></summary>

#### Short answer

Usually no for basic resource operations; use nouns for resources and HTTP methods for actions.

#### Interview answer

Prefer `GET /orders/{id}` over `GET /getOrder`, and `DELETE /orders/{id}` over `POST /deleteOrder`. This keeps the API aligned with HTTP semantics and easier to document.

Verbs can be acceptable for domain commands when the concept does not map naturally to CRUD.

#### Deep dive

The real issue is not grammar but clarity. `/orders/{id}/cancel` may be less clean than `POST /orders/{id}/cancellations`, but both may be understandable if documented.

#### Production angle

Consistent URI design improves gateway rules, access logs and client expectations.

#### Traps / caveats

- Avoid generic verbs like `/process` or `/execute`.
- Do not force awkward noun resources just to satisfy a rule.
- Method semantics still matter.

#### Optional Anki

Q: Why avoid verbs in URLs?
A: HTTP methods should express standard actions on resources.

</details>

<a id="rest-uri-003"></a>

<details>
<summary><strong>REST-URI-003. When can action-like endpoints be acceptable?</strong></summary>

#### Short answer

They are acceptable when they represent a clear domain command that does not fit normal CRUD well.

#### Interview answer

Operations like canceling an order, confirming an email, initiating payment or recalculating a report may be modeled as command resources or action-like endpoints. The key is to make the state transition, idempotency and response semantics explicit.

#### Deep dive

A good design often turns an action into a resource: `POST /orders/{id}/cancellations` creates a cancellation request. But a simple action endpoint may be fine for internal APIs if it is clear and consistent.

#### Production angle

Command endpoints usually need audit logging, authorization, idempotency and clear conflict behavior.

#### Traps / caveats

- Avoid hiding commands in query parameters.
- Avoid vague endpoint names.
- Do not ignore method semantics just because it is a command.

#### Optional Anki

Q: When are action endpoints okay?
A: For clear domain commands with explicit semantics.

</details>

<a id="rest-uri-004"></a>

<details>
<summary><strong>REST-URI-004. How should nested resources and subresources be designed?</strong></summary>

#### Short answer

Use nesting when the child resource is naturally scoped by the parent, but avoid deep nesting that makes APIs rigid.

#### Interview answer

`/orders/{orderId}/items` makes sense because order items belong to an order. But `/tenants/{t}/departments/{d}/users/{u}/orders/{o}/items/{i}` becomes hard to maintain and may leak authorization structure.

Use nesting to express containment or access scope, not every relationship.

#### Deep dive

If a child resource has a globally stable ID and is often accessed independently, a shorter top-level URI may be better. You can still filter by parent with query parameters.

#### Production angle

Deep URLs complicate authorization, routing, metrics and client code.

#### Traps / caveats

- Nesting does not replace authorization checks.
- Avoid duplicating many URI paths for the same resource.
- Keep identifiers stable and unambiguous.

#### Optional Anki

Q: When use nested resources?
A: When the child is naturally scoped by the parent.

</details>

<a id="rest-uri-005"></a>

<details>
<summary><strong>REST-URI-005. How should you model search endpoints?</strong></summary>

#### Short answer

Use query parameters for simple filtering; use a dedicated search resource or POST search endpoint for complex criteria.

#### Interview answer

For simple list filters, `GET /orders?status=PAID&createdFrom=...` is natural. For complex search with many fields, nested expressions or large criteria, a dedicated endpoint like `POST /orders/search` may be more practical.

#### Deep dive

GET is better for cacheable and bookmarkable searches. POST search may be acceptable when the criteria are too large or complex for a URL, but it should be documented as a query operation, not a state-changing command.

#### Production angle

Search endpoints can be expensive. Limit page size, sort options and filter combinations, and ensure database/search indexes support common queries.

#### Traps / caveats

- Do not allow arbitrary unbounded filters.
- Avoid secrets or large criteria in URLs.
- Search authorization must apply before or during querying, not only after results.

#### Optional Anki

Q: GET or POST for search?
A: GET for simple cacheable filters; POST can fit complex search criteria.

</details>

<a id="rest-uri-007"></a>

<details>
<summary><strong>🧠 REST-URI-007. How should you model file upload and download endpoints?</strong></summary>

#### Short answer

Model files as resources or upload jobs, separate metadata from binary content, and define limits and processing states.

#### Interview answer

For simple downloads, `GET /documents/{id}/content` can return the binary stream. For uploads, use multipart or pre-signed object storage URLs depending on size and architecture. If processing continues after upload, create an upload/job resource and return 202 or a status resource.

#### Deep dive

File APIs often need metadata, virus scanning, checksum validation, size limits and lifecycle state. The binary content may live in object storage while the REST API manages metadata and authorization.

#### Production angle

Large file handling should avoid buffering everything in memory and should support timeouts, cancellation and cleanup of partial uploads.

#### Traps / caveats

- Do not trust filename, content type or extension.
- Enforce size and type limits.
- Avoid exposing internal object-storage paths.

#### Optional Anki

Q: Key file API concern?
A: Separate metadata/content and enforce security, size and processing controls.

</details>

<a id="rest-uri-009"></a>

<details>
<summary><strong>REST-URI-009. When should data go in the path, query parameters or body?</strong></summary>

#### Short answer

Use path for resource identity, query parameters for selection/filtering, and body for complex input or representations.

#### Interview answer

`/orders/{id}` uses the path because `{id}` identifies the resource. `?status=PAID&page=2` uses query parameters because they select or shape a collection response. A POST or PUT body carries a representation or command input.

#### Deep dive

Do not put sensitive data in query parameters because URLs are often logged and cached. Do not use request bodies for simple GET filters unless there is a strong reason and client/proxy support is understood.

#### Production angle

Clear placement improves caching, routing, gateway policy and observability.

#### Traps / caveats

- Query parameters are part of cache keys.
- Path parameters should be stable identifiers.
- Bodies need schema validation and size limits.

#### Optional Anki

Q: Path vs query vs body?
A: Identity vs selection vs representation/complex input.

</details>

<a id="rest-uri-010"></a>

<details>
<summary><strong>🧠 REST-URI-010. How do public identifiers differ from internal database IDs?</strong></summary>

#### Short answer

Public identifiers are part of the API contract; internal database IDs are implementation details.

#### Interview answer

An internal primary key may be sequential, tenant-local or change during migration. A public ID should be stable, non-sensitive and safe to expose. Many APIs use UUIDs, ULIDs or domain-specific IDs as public identifiers.

#### Deep dive

Exposing database IDs is not always wrong, but it can enable enumeration, leak scale or couple clients to persistence choices. Public IDs create a boundary between API contract and storage.

#### Production angle

Public IDs help during database migrations, shard changes and tenant isolation improvements.

#### Traps / caveats

- Public IDs do not replace authorization.
- Random-looking IDs can still leak data if access checks are missing.
- Choose IDs with indexing and operational needs in mind.

#### Optional Anki

Q: Why use public IDs?
A: To avoid coupling the API to internal database identity.

</details>

<a id="rest-uri-011"></a>

<details>
<summary><strong>🧠 REST-URI-011. How should URLs avoid leaking tenant or user data?</strong></summary>

#### Short answer

Use non-sensitive identifiers, avoid secrets in URLs, and enforce tenant/user authorization server-side.

#### Interview answer

URLs appear in logs, browser history, analytics, proxies and error reports. Do not put tokens, personal data, emails or sensitive search terms in paths or query strings. Use opaque IDs where appropriate and check ownership for every resource access.

#### Deep dive

Multi-tenant APIs should decide whether tenant context comes from path, host, token claims or headers. Whatever the choice, the server must verify that the caller is allowed to access that tenant.

#### Production angle

URL leaks are hard to scrub because many systems log them by default. Prevention is easier than cleanup.

#### Traps / caveats

- Predictable IDs plus missing authorization cause IDOR.
- Tenant in URL is not authorization.
- Query strings can leak through referrers and logs.

#### Optional Anki

Q: Why avoid sensitive data in URLs?
A: URLs are commonly logged, stored and shared.

</details>

<details>
<summary><strong>REST-URI-012. How would you review a REST API URL design in a code review?</strong></summary>

#### Short answer

Check resource clarity, method semantics, identifier exposure, nesting, consistency, evolvability and authorization boundaries.

#### Interview answer

I would ask: Does the URI identify a resource? Is the HTTP method appropriate? Are path/query/body choices consistent? Are IDs safe to expose? Is nesting reasonable? Are error, pagination and versioning patterns consistent with the rest of the API?

#### Deep dive

Review the API as a client contract, not just controller code. Check OpenAPI docs, examples, backward compatibility and how the endpoint appears in logs/metrics.

#### Production angle

API URL decisions are hard to change after clients adopt them, especially public/mobile clients.

#### Traps / caveats

- Do not approve endpoint shape without checking authorization.
- Watch for accidental breaking changes.
- Keep consistency across services where possible.

#### Optional Anki

Q: REST URL review checklist?
A: Resource, method, parameters, IDs, nesting, consistency, security and compatibility.

</details>
