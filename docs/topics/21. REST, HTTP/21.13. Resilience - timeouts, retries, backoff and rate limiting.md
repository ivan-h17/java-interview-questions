# Resilience: timeouts, retries, backoff and rate limiting

---

<a id="rest-res-002"></a>

<details>
<summary><strong>REST-RES-002. What timeouts should an HTTP client configure?</strong></summary>

#### Short answer

Configure connection, pool acquisition, request/response and read timeouts, plus an overall operation deadline.

#### Interview answer

A Java service should not rely on defaults. It should limit time to acquire a connection, establish a connection, wait for response headers and read the body. The whole operation should fit within the caller's deadline.

#### Deep dive

Timeout names vary by client library. Understand whether DNS, TLS handshake and connection pool wait are covered.

#### Production angle

Missing timeouts lead to stuck request threads, full connection pools and cascading failures.

#### Traps / caveats

- Socket read timeout is not always an end-to-end deadline.
- Too-low timeouts create false failures.
- Retries must fit within the overall deadline.

#### Optional Anki

Q: Why explicit HTTP client timeouts?
A: To avoid hung calls exhausting service resources.

</details>

<a id="rest-res-003"></a>

<details>
<summary><strong>REST-RES-003. Why are missing timeouts dangerous?</strong></summary>

#### Short answer

Missing timeouts let slow dependencies hold threads, connections and memory indefinitely.

#### Interview answer

If a downstream stalls and callers wait forever, servlet threads or async workers can be exhausted. Then unrelated endpoints slow down, causing a cascading failure.

#### Deep dive

Timeouts are part of resource isolation. They should be paired with connection pool limits, bulkheads and backpressure/load shedding.

#### Production angle

Many incidents start with one slow dependency and no caller deadlines.

#### Traps / caveats

- A timeout should cancel/stop work where possible.
- Retrying after timeout can duplicate side effects.
- Timeout values should be based on latency budgets, not guesses.

#### Optional Anki

Q: Missing timeout failure mode?
A: Resource exhaustion from waiting forever.

</details>

<a id="rest-res-004"></a>

<details>
<summary><strong>REST-RES-004. When should an HTTP request be retried, and when should it not be retried?</strong></summary>

#### Short answer

Retry transient failures for safe/idempotent operations within a deadline; avoid retrying non-idempotent or permanent failures blindly.

#### Interview answer

Connection resets, timeouts before response and 503/504 may be retryable depending on operation semantics. 400/401/403/404 validation/auth errors are usually not retryable. POST commands need idempotency protection.

#### Deep dive

Retry decisions should consider method, operation, status code, exception type, deadline and downstream health.

#### Production angle

Bad retries amplify outages and increase p99 latency.

#### Traps / caveats

- Do not retry every 5xx automatically.
- Respect `Retry-After`.
- Stop retrying when caller deadline is nearly exhausted.

#### Optional Anki

Q: Retry rule?
A: Retry transient failures only when operation semantics make it safe.

</details>

<a id="rest-res-005"></a>

<details>
<summary><strong>REST-RES-005. Why should retries use backoff and jitter?</strong></summary>

#### Short answer

Backoff reduces pressure on a failing system; jitter prevents clients from retrying in synchronized waves.

#### Interview answer

Immediate retries can multiply load exactly when a dependency is unhealthy. Exponential backoff spaces attempts out. Jitter randomizes retry timing so many clients do not retry at the same instant.

#### Deep dive

Retries also need a maximum attempt count, maximum delay and overall deadline.

#### Production angle

Backoff and jitter are basic protection against retry storms.

#### Traps / caveats

- Backoff does not make unsafe operations safe.
- Long retry chains can exceed user-facing latency budgets.
- Multiple retry layers can multiply attempts.

#### Optional Anki

Q: Why jitter?
A: To avoid synchronized retry bursts.

</details>

<a id="rest-res-006"></a>

<details>
<summary><strong>REST-RES-006. What is a retry storm?</strong></summary>

#### Short answer

A retry storm happens when many clients retry failures and overload the already struggling service.

#### Interview answer

If a dependency slows down, callers may timeout and retry. Those retries add more load, causing more timeouts and even more retries. The system enters a feedback loop.

#### Deep dive

Retry storms are worse when retries happen at multiple layers: SDK, service, gateway and job scheduler.

#### Production angle

Use retry budgets, backoff, jitter, circuit breakers, load shedding and dashboards distinguishing original calls from retry attempts.

#### Traps / caveats

- Retrying can reduce availability.
- Retries should be measured separately.
- Rate limiting and retries can fight each other.

#### Optional Anki

Q: Retry storm cause?
A: Retrying overload-induced failures and adding more load.

</details>

<a id="rest-res-007"></a>

<details>
<summary><strong>REST-RES-007. How do idempotency keys make retries safer?</strong></summary>

#### Short answer

They let the server recognize retried commands and avoid executing side effects twice.

#### Interview answer

For payment/order creation, a timeout leaves the client unsure whether the server committed. With an idempotency key, the retry carries the same key and the server returns the original result instead of creating another order.

#### Deep dive

The key must be stored durably and atomically with the business operation.

#### Production angle

Idempotency keys are essential for reliable APIs over unreliable networks.

#### Traps / caveats

- Key reuse with different payload must be rejected.
- In-memory keys fail across restarts.
- Keys need a retention window.

#### Optional Anki

Q: Idempotency key benefit?
A: Safe retries for side-effecting commands.

</details>

<a id="rest-res-008"></a>

<details>
<summary><strong>🧠 REST-RES-008. How should payment or order creation endpoints handle retries?</strong></summary>

#### Short answer

Require idempotency keys, store command state durably, and return the original result for duplicate attempts.

#### Interview answer

The endpoint should treat timeout outcomes as ambiguous. The client retries with the same idempotency key. The server checks existing command state: in progress, succeeded or failed, and responds consistently without duplicating side effects.

#### Deep dive

Use database unique constraints on the idempotency key and store a request fingerprint to detect misuse.

#### Production angle

This prevents double charges and duplicate orders during network failures.

#### Traps / caveats

- External payment providers may have their own idempotency keys.
- Do not mark success before durable commit.
- Reconciliation jobs are still needed.

#### Optional Anki

Q: Payment retry requirement?
A: Durable idempotency and reconciliation.

</details>

<a id="rest-res-009"></a>

<details>
<summary><strong>REST-RES-009. What is the difference between server-side rate limiting and client-side throttling?</strong></summary>

#### Short answer

Server-side rate limiting rejects excess incoming traffic; client-side throttling limits outgoing traffic before sending it.

#### Interview answer

An API server may return 429 when a client exceeds quota. A Java service calling a downstream may throttle itself to respect documented limits and avoid causing overload.

Both can exist together.

#### Deep dive

Client-side throttling improves politeness and stability; server-side rate limiting enforces protection.

#### Production angle

Use both for third-party APIs and internal dependencies with limited capacity.

#### Traps / caveats

- Throttling is not authorization.
- Distributed rate limits need shared state or approximate algorithms.
- 429 should include retry guidance where possible.

#### Optional Anki

Q: Rate limiting vs throttling?
A: Server rejects excess; client slows itself before sending.

</details>

<a id="rest-res-010"></a>

<details>
<summary><strong>🧠 REST-RES-010. How do load shedding and backpressure differ?</strong></summary>

#### Short answer

Load shedding rejects work to protect the system; backpressure signals producers to slow down.

#### Interview answer

If a service is overloaded, it may shed load by returning 429/503 quickly. Backpressure is a broader flow-control mechanism where downstream capacity slows upstream production.

#### Deep dive

In synchronous REST, backpressure is limited; failing fast is often clearer than queuing unbounded work.

#### Production angle

Load shedding preserves availability for healthy requests and avoids collapse under overload.

#### Traps / caveats

- Queues can hide overload until latency explodes.
- Shedding must protect critical traffic.
- Clients need retry/backoff guidance.

#### Optional Anki

Q: Load shedding means?
A: Rejecting work intentionally to protect the service.

</details>

<a id="rest-res-011"></a>

<details>
<summary><strong>REST-RES-011. How should APIs return retry information to clients?</strong></summary>

#### Short answer

Use appropriate status codes, `Retry-After` when possible, and stable error codes explaining whether retry is safe.

#### Interview answer

For 429 or 503, include `Retry-After` if the service can estimate it. The body can include an error code, reason and documentation link. For non-idempotent operations, explain whether the client should retry with the same idempotency key or check operation status.

#### Deep dive

Clients also need to know when not to retry: validation errors, auth failures and business conflicts usually require user or client changes.

#### Production angle

Good retry guidance reduces traffic spikes and support issues.

#### Traps / caveats

- Do not tell clients to retry immediately.
- Do not expose internal capacity details.
- Retry guidance must respect idempotency.

#### Optional Anki

Q: Header for retry delay?
A: `Retry-After`.

</details>

<a id="rest-res-012"></a>

<details>
<summary><strong>🧠 REST-RES-012. How would you prevent one slow downstream API from exhausting your thread pool?</strong></summary>

#### Short answer

Use timeouts, separate pools/bulkheads, connection limits, circuit breakers and fast failure or degradation.

#### Interview answer

Each downstream should have bounded connections and request timeouts. Critical dependencies may get separate executor or bulkhead isolation. If the dependency is slow, fail fast or return degraded responses rather than consuming all request threads.

#### Deep dive

Virtual threads reduce thread cost but do not remove downstream capacity limits, database limits or need for deadlines.

#### Production angle

Dependency isolation prevents one failing integration from taking down unrelated endpoints.

#### Traps / caveats

- Unbounded queues are hidden outages.
- Retries can worsen pool exhaustion.
- Optional dependency failure should be visible in telemetry.

#### Optional Anki

Q: Protect from slow downstream?
A: Timeouts, bounded pools and dependency isolation.

</details>
