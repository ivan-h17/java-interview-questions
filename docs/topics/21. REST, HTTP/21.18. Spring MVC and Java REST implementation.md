<details>
<summary><strong>REST-SPRING-001. What is the difference between @Controller and @RestController?</strong></summary>

#### Short answer

`@RestController` is `@Controller` plus `@ResponseBody` semantics for all handler methods.

#### Interview answer

`@Controller` is often used for MVC views. `@RestController` is used for REST APIs where return values are written directly to the HTTP response body, usually as JSON through message converters.

#### Deep dive

With `@Controller`, you can still use `@ResponseBody` on individual methods. `@RestController` makes that the default.

#### Production angle

Use the annotation that matches the endpoint style. Avoid mixing view and API behavior accidentally.

#### Traps / caveats

- `@RestController` does not make the design RESTful.
- Serialization still depends on message converters.
- Errors need explicit handling.

#### Optional Anki

Q: `@RestController` equals?
A: `@Controller` plus default `@ResponseBody`.

</details>

<details>
<summary><strong>REST-SPRING-002. What are @RequestMapping and the HTTP-method mapping annotations?</strong></summary>

#### Short answer

They map HTTP requests to controller methods by path, method, headers, params and media types.

#### Interview answer

`@RequestMapping` is the general annotation. `@GetMapping`, `@PostMapping`, `@PutMapping`, `@PatchMapping` and `@DeleteMapping` are shortcuts for specific HTTP methods.

#### Deep dive

Mappings can also constrain `consumes` and `produces`, which is important for content negotiation and media type validation.

#### Production angle

Clear mappings make OpenAPI generation, security rules and route metrics easier.

#### Traps / caveats

- Avoid overlapping ambiguous mappings.
- Match method semantics to API behavior.
- Document consumed/produced media types.

#### Optional Anki

Q: What does `@GetMapping` specialize?
A: `@RequestMapping` for GET requests.

</details>

<details>
<summary><strong>REST-SPRING-003. What is the difference between @RequestBody and @ResponseBody?</strong></summary>

#### Short answer

`@RequestBody` reads the HTTP body into a Java object; `@ResponseBody` writes a Java return value to the HTTP body.

#### Interview answer

Spring uses HTTP message converters, typically Jackson for JSON, to deserialize request bodies and serialize responses.

#### Deep dive

Validation is commonly applied to `@RequestBody` DTOs with `@Valid` or `@Validated`.

#### Production angle

Correct body mapping affects error handling, validation, media type support and JSON compatibility.

#### Traps / caveats

- `@RequestBody` is not for query/path parameters.
- Missing or wrong `Content-Type` can break deserialization.
- Do not bind bodies directly to entities.

#### Optional Anki

Q: `@RequestBody` does what?
A: Deserializes request body into a Java object.

</details>

<a id="rest-spring-004"></a>

<details>
<summary><strong>REST-SPRING-004. What is the difference between @PathVariable and @RequestParam?</strong></summary>

#### Short answer

`@PathVariable` binds URI path variables; `@RequestParam` binds query parameters or form parameters.

#### Interview answer

Use `@PathVariable` for resource identity like `/orders/{id}`. Use `@RequestParam` for filtering, sorting, pagination and optional modifiers like `/orders?status=PAID`.

#### Deep dive

This mirrors API design: path identifies resource, query selects or shapes the response.

#### Production angle

Consistent use improves route design, metrics and client clarity.

#### Traps / caveats

- Do not put secrets in query parameters.
- Validate and parse both kinds of input.
- Optional path variables often make ambiguous routes.

#### Optional Anki

Q: PathVariable vs RequestParam?
A: Path identity vs query/form parameter.

</details>

<a id="rest-spring-005"></a>

<details>
<summary><strong>REST-SPRING-005. How does Spring map JSON to Java objects?</strong></summary>

#### Short answer

Spring uses an HTTP message converter, usually Jackson, to deserialize JSON into DTOs and serialize DTOs to JSON.

#### Interview answer

When a controller has `@RequestBody CreateOrderRequest`, Spring chooses a JSON message converter based on `Content-Type`, then Jackson creates the object using constructors, setters, records or configured creators.

#### Deep dive

ObjectMapper configuration controls dates, naming, null handling, unknown fields and modules.

#### Production angle

JSON mapper configuration is part of the API contract and should be tested.

#### Traps / caveats

- Different mappers across services/clients cause compatibility bugs.
- Unknown field behavior should be deliberate.
- Deserialization is not business validation.

#### Optional Anki

Q: What library commonly maps JSON in Spring?
A: Jackson.

</details>

<details>
<summary><strong>REST-SPRING-006. How should DTO validation be implemented with @Valid or @Validated?</strong></summary>

#### Short answer

Annotate request DTOs with Bean Validation constraints and trigger validation with `@Valid` or `@Validated`.

#### Interview answer

Use constraints like `@NotNull`, `@Size` and custom validators for boundary validation. Put `@Valid` on `@RequestBody` parameters so Spring rejects invalid requests before service logic.

#### Deep dive

Bean Validation handles structural rules well. Business invariants often belong in the service layer where context is available.

#### Production angle

Centralized validation reduces inconsistent error handling and protects services from bad input.

#### Traps / caveats

- Validation annotations do not replace authorization.
- Cross-field validation needs custom logic.
- Validate final domain state after PATCH.

#### Optional Anki

Q: `@Valid` on request body does what?
A: Triggers Bean Validation for the DTO.

</details>

<details>
<summary><strong>REST-SPRING-007. How do you implement global exception handling with @ControllerAdvice?</strong></summary>

#### Short answer

Use `@ControllerAdvice` with `@ExceptionHandler` methods to map exceptions to consistent HTTP responses.

#### Interview answer

A global handler can convert validation errors to 400, conflicts to 409, authorization failures to 403 and unexpected errors to sanitized 500 responses. It keeps controllers thin and error format consistent.

#### Deep dive

Spring 6+ supports `ProblemDetail`, which fits standard Problem Details responses.

#### Production angle

Centralized error mapping improves client behavior and observability.

#### Traps / caveats

- Do not swallow exceptions without logging/metrics.
- Do not expose stack traces.
- Preserve correlation IDs.

#### Optional Anki

Q: `@ControllerAdvice` used for?
A: Cross-controller exception/response handling.

</details>

<a id="rest-spring-008"></a>

<details>
<summary><strong>REST-SPRING-008. What is ResponseEntity used for?</strong></summary>

#### Short answer

`ResponseEntity` lets a controller control status, headers and body explicitly.

#### Interview answer

Use it when you need to set `201 Created` with `Location`, return `204 No Content`, add cache headers or choose a specific status with a body.

#### Deep dive

Simple methods can return DTOs directly, but `ResponseEntity` is useful when HTTP metadata is part of the contract.

#### Production angle

Explicit status and headers improve API correctness and documentation.

#### Traps / caveats

- Do not overuse it to hide inconsistent response logic.
- Avoid returning 200 for every outcome.
- 204 should not have a body.

#### Optional Anki

Q: ResponseEntity controls?
A: HTTP status, headers and body.

</details>

<details>
<summary><strong>REST-SPRING-009. How do you return RFC 9457 ProblemDetail responses in Spring?</strong></summary>

#### Short answer

Use Spring's `ProblemDetail` or `ErrorResponse` support in exception handlers to return standard problem responses.

#### Interview answer

In a `@ControllerAdvice`, create a `ProblemDetail` with the correct status, title, detail, type and optional extension properties. Map domain exceptions to stable problem types.

#### Deep dive

Problem Details should be sanitized and stable. Use extensions for field errors or domain codes where needed.

#### Production angle

Standard problem responses make error handling consistent across services and clients.

#### Traps / caveats

- Do not expose internal exception details.
- Keep `type` and domain error codes stable.
- Include correlation ID through headers or extensions if useful.

#### Optional Anki

Q: Spring type for Problem Details?
A: `ProblemDetail`.

</details>

<a id="rest-spring-010"></a>

<details>
<summary><strong>REST-SPRING-010. How should Spring controllers be kept thin?</strong></summary>

#### Short answer

Controllers should handle HTTP concerns and delegate business logic to services.

#### Interview answer

A controller should parse inputs, trigger validation, call a service, map the result and return the proper response. Business rules, transactions, authorization policy and persistence should not be buried in controller methods.

#### Deep dive

Thin controllers are easier to test and keep API concerns separate from domain logic.

#### Production angle

Separation helps reuse logic from jobs, messaging handlers and other APIs without duplicating behavior.

#### Traps / caveats

- Do not put transactions only around controller logic by accident.
- Do not skip service-level authorization.
- Mapping can still become complex; use clear DTO mappers when needed.

#### Optional Anki

Q: Controller responsibility?
A: HTTP boundary, validation trigger, delegation and response mapping.

</details>

<details>
<summary><strong>🧠 REST-SPRING-011. How does Spring handle content negotiation and HttpMessageConverter selection?</strong></summary>

#### Short answer

Spring uses request headers, handler metadata and configured converters to choose how to read/write bodies.

#### Interview answer

`Content-Type` influences request body parsing. `Accept` and `produces` influence response format. `HttpMessageConverter` implementations handle JSON, strings, byte arrays and other formats.

#### Deep dive

Jackson's JSON converter is usually selected for `application/json`. Custom converters or ObjectMapper changes can affect the whole API.

#### Production angle

Converter configuration is part of API behavior and should be tested after framework upgrades.

#### Traps / caveats

- Missing `Content-Type` can cause unexpected behavior.
- Multiple converters can create surprising output formats.
- Content negotiation should match OpenAPI docs.

#### Optional Anki

Q: What reads/writes HTTP bodies in Spring MVC?
A: `HttpMessageConverter`.

</details>

<details>
<summary><strong>REST-SPRING-012. How do you configure CORS and pagination in Spring MVC?</strong></summary>

#### Short answer

Configure CORS centrally and bind pagination parameters to validated request objects or Spring Data `Pageable` with limits.

#### Interview answer

CORS can be configured globally through MVC/Security configuration or per controller, but central config is usually safer. Pagination can use `page/size/sort` or custom cursor DTOs; always enforce max size.

#### Deep dive

Spring Security filters interact with CORS, so preflight handling must be configured correctly.

#### Production angle

Central policies avoid endpoint-by-endpoint drift and accidental open origins or unbounded pages.

#### Traps / caveats

- Do not allow all origins with credentials.
- Do not trust client page size.
- Spring Data page numbering is zero-based by default.

#### Optional Anki

Q: Pagination rule in Spring APIs?
A: Validate and cap page size server-side.

</details>

<a id="rest-spring-013"></a>

<details>
<summary><strong>🧠 REST-SPRING-013. How do Spring Security filters interact with REST controllers?</strong></summary>

#### Short answer

Security filters run before controllers and can authenticate, reject or authorize requests before handler execution.

#### Interview answer

Spring Security uses a filter chain around the servlet request. It may parse tokens, populate the security context, enforce authorization or reject the request before it reaches `@RestController`.

#### Deep dive

Method security may run inside service/controller methods, while URL security runs at the filter level. Both must be designed consistently.

#### Production angle

Understanding filter order helps debug 401/403/CORS issues and missing security context in async work.

#### Traps / caveats

- CORS preflight can be blocked if security is misconfigured.
- Thread-local security context may not propagate to async tasks.
- `permitAll` and ignoring security filters are different.

#### Optional Anki

Q: Do security filters run before controllers?
A: Yes.

</details>

<details>
<summary><strong>🧠 REST-SPRING-014. What is the difference between RestTemplate, WebClient and RestClient?</strong></summary>

#### Short answer

`RestTemplate` is older blocking API, `WebClient` is reactive/non-blocking, and `RestClient` is the modern blocking fluent client.

#### Interview answer

For new blocking Spring MVC services, `RestClient` is often a good fit. `WebClient` is useful for reactive applications or when composing non-blocking flows. `RestTemplate` is widely used in legacy code but is not the preferred modern choice for new development.

#### Deep dive

The client choice does not remove the need for timeouts, connection pooling, retries, tracing and error handling.

#### Production angle

Operational configuration matters more than API style: deadlines, pools, metrics and resilience policies must be explicit.

#### Traps / caveats

- Do not block carelessly inside reactive pipelines.
- Wrapping blocking calls in async code can just move the bottleneck.
- Defaults may lack production-safe timeouts.

#### Optional Anki

Q: Modern blocking Spring HTTP client?
A: `RestClient`.

</details>
